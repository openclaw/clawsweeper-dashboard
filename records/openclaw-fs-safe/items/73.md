The report identifies two concrete release-automation defects and a real operator impact: successful npm publication can still fail the workflow and skip GitHub Release creation.

## What This Changes

Fix the release workflow so it publishes the validated package tarball and waits long enough to verify a newly propagated npm package.

## System Context

The release workflow assembles and validates a package tarball, records its integrity in a release manifest, publishes the package to npm, then verifies the registry result before creating the GitHub Release. A mismatch or premature registry timeout breaks that final verification gate even when the package itself has published successfully.

## Architecture Diagram

flowchart LR
  A[Tag-triggered release] --> B[Assemble and validate package]
  B --> C[Validated tarball and release manifest]
  C --> D[Publish package to npm]
  D --> E[Poll npm registry]
  E --> F{Integrity and propagation confirmed?}
  F -->|Yes| G[Publish GitHub Release]
  F -->|No| H[Release workflow fails]

## Best Possible Solution

Preserve a single validated tarball through publication, then make registry confirmation resilient to normal propagation delay while retaining a strict integrity comparison once metadata is available.

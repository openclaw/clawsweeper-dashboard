## Summary

This issue remains necessary: the reported current-main path can admit unrelated in-process async callers to the same JSON-store critical section, allowing silent lost updates. The report also identifies a real compatibility decision around nested store calls, so it needs maintainer direction rather than an automatic one-line repair.

## What This Changes

Make `jsonStore({ lock: true })` serialize overlapping updates within one process instead of treating every same-process caller as a reentrant lock owner.

## System Context

`jsonStore` wraps a read–transform–write sequence with a sidecar file lock when locking is enabled. The JSON-store adapter feeds a target path and lock options into the lock manager; the manager's in-process held-lock state then decides whether to acquire, wait, or reenter before the write reaches the guarded atomic-write path.

flowchart TD
  A[Application update calls] --> B[JSON store]
  B --> C[Optional lock wrapper]
  C --> D[Sidecar lock manager]
  D --> E{Same logical lock owner?}
  E -->|Yes| F[Reenter safely]
  E -->|No| G[Serialize or wait]
  F --> H[Read transform write]
  G --> H[Read transform write]

## Best Possible Solution

Define reentrancy as belonging only to the same logical async owner, then add regression coverage for overlapping in-process updates and nested same-owner store calls; retain a documented fail-closed behavior for unrelated callers.

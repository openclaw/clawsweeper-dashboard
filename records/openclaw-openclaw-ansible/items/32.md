## Summary

Current main still grants the account running the OpenClaw gateway control of the rootful Docker daemon. The reported host-privilege boundary remains unresolved and requires an explicit maintainer security design rather than an isolated group-membership removal.

## What This Changes

Address the root-equivalent host privilege path created by assigning the OpenClaw service account to the rootful Docker group.

## Best Possible Solution

Move Docker-backed sandboxes to a rootless daemon owned by a dedicated runtime identity, keep the gateway account away from the rootful Docker socket, and ship an explicit migration with fresh-install, upgrade, reboot, sandbox, firewall, and rollback proof.

## Maintainer Decision

Question: Should the hardened installer make rootless Docker the supported sandbox runtime, or adopt another mediated design that keeps the gateway account away from the rootful Docker socket?

Rationale: The permanent fix changes the trust boundary and must preserve sandbox creation, one-command setup, reboot behavior, firewall guarantees, and upgrades; source inspection cannot safely choose that contract.

Likely owner: alauppe

Owner confidence: high

Options:

- **Adopt rootless Docker (recommended):** Provision and validate a rootless daemon and socket for sandbox workloads, then migrate existing users out of the rootful docker group.
- **Build a sandbox broker:** Keep rootful Docker behind a narrowly designed privileged service exposing only the operations and mounts required by OpenClaw sandboxes.
- **Accept and disclose authority:** Retain Docker-group membership but explicitly document that compromise of the OpenClaw account compromises the host and narrow the hardening claims.

## Reproduction Assessment

Yes. Current main starts rootful Docker, adds `openclaw_user` to the `docker` group, and runs the gateway as that user, providing a high-confidence source reproduction of the reported authority path.

## Solution Assessment

Deleting group membership alone is not the best fix because Docker-backed sandboxes would stop working. The narrowest durable solution is a maintainer-approved rootless or mediated runtime with tested migration behavior.

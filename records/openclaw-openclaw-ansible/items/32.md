## Summary

Keep this issue open: current main still gives the OpenClaw service account control of a rootful Docker daemon, so the reported host-privilege boundary remains unresolved and needs an explicit security design decision.

## What This Changes

Remove or redesign the OpenClaw account's Docker-group access so a compromise of that account cannot obtain root-equivalent host control through the Docker socket.

## Best Possible Solution

Adopt and document one supported least-privilege runtime model—preferably rootless Docker or a narrowly mediated root-owned service interface—then remove direct Docker-socket authority from the OpenClaw account and validate both installation and upgrade paths.

- **Use a root-controlled service boundary:** Keep rootful Docker host-managed but ensure the OpenClaw account cannot access its socket directly, exposing only the required lifecycle operations through a constrained service interface.
- **Retain current model with explicit acceptance:** Document Docker-group membership as root-equivalent and accept the reduced host-isolation claim for installations using this mode.

## Reproduction Assessment

Yes, at source level: the reported Docker-group assignment gives the service account access to the conventional rootful Docker socket, which is root-equivalent. A disposable-VM validation should confirm the selected replacement model rather than reproduce exploitation on a production host.

## Solution Assessment

Unclear: deleting the group assignment alone is not the best fix because the installer still needs a supported lifecycle model. A maintained rootless-Docker or root-controlled mediation design is the safer complete solution.

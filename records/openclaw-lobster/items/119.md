## Summary

Keep open: the process-level cancellation changes are useful and well-proven, but cancellation during an in-flight Gmail send still returns normal output and allows the pipeline runner to start a later stage.

## What This Changes

Propagates abort signals to Gmail search and GitHub monitor subprocesses, stops later Gmail drafts after cancellation, and adds process-lifecycle regression coverage.

## Best Possible Solution

Preserve the definitive result from an already-started send while explicitly halting the remaining pipeline as cancelled, then cover the contract with a downstream marker or external-command regression test.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When cancellation arrives during an in-flight side-effecting command, should Lobster preserve its completed partial results while halting later pipeline stages, or convert the whole run to an error/cancelled envelope?

Rationale: The implementation can mechanically stop downstream stages, but the public envelope semantics for a completed side effect plus parent cancellation determine whether callers receive partial results, a cancelled status, or an error.

Likely owner: steipete

Owner reason: The runtime and tool-envelope history makes steipete the strongest available owner for the cross-command cancellation contract.

Owner confidence: high

Options:

- **Halt with partial results (recommended):** Return the definitive completed-send results while marking or halting the run so no later pipeline stage starts.
- **Return cancellation error:** Raise cancellation after the in-flight send settles, preventing later stages but requiring callers to recover the completed side-effect result through an error contract.

## Reproduction Assessment

Yes, with high confidence from source: run a pipeline with `gog.gmail.send` followed by a marker command, abort during the first send, and the normal send result permits the marker stage to start. The submitted proof does not exercise that downstream-stage case.

## Solution Assessment

No. Owning subprocess termination in the affected commands is the right boundary, but a command-local loop break is insufficient unless it also communicates a workflow-level halt after the in-flight send settles.

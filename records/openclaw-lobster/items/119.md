## Summary

Keep this PR open but do not merge it yet: cancellation during an already-started Gmail send can still return normally and allow later pipeline stages to execute, so the central guarantee that canceled workflows stop external work is incomplete.

## What This Changes

Propagates parent cancellation to Gmail search and legacy GitHub monitor subprocesses, stops later drafts in a Gmail send batch, and adds process-lifecycle regression coverage.

## Best Possible Solution

Introduce an explicit cancellation-aware partial-result outcome that preserves receipts for already-completed sends while halting the pipeline before every later stage, with regression coverage for a send followed by another external command.

## Maintainer Decision

Required: true

Kind: product_direction

Question: After an in-flight Gmail send completes during parent cancellation, how should Lobster preserve that definitive result while guaranteeing that no later pipeline stage executes?

Rationale: The existing command and envelope contracts force a choice between returning the completed send as normal output, which permits downstream execution, and throwing cancellation, which can hide the definitive side-effect result; the permanent partial-result contract requires runtime-owner intent.

Likely owner: vignesh07

Owner reason: Their merged history is most directly connected to pipeline, resume, and workflow-result contracts needed to resolve this behavior.

Owner confidence: high

Options:

- **Add a halted partial-result outcome (recommended):** Preserve completed send results in a cancellation-aware outcome that prevents all later pipeline stages from starting.
- **Surface cancellation after completion:** Report the workflow as canceled after the in-flight send settles, accepting that ordinary successful output may no longer represent the completed send.
- **Keep the limited batch contract:** Explicitly accept that cancellation only stops later drafts within this command and may not stop subsequent pipeline stages.

## Reproduction Assessment

Yes, from source with high confidence: abort a pipeline while its first Gmail send is in flight and place another external command after that stage; the send completes, breaks normally, and the pipeline advances. The supplied proof does not run this final downstream stage.

## Solution Assessment

No. Moving signal ownership into read-only subprocess commands is appropriate, but the Gmail send branch needs a pipeline-level partial-result or halt contract rather than returning ordinary success after cancellation.

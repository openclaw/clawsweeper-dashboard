## Label Justifications

- `P1`: The changed resume cleanup can make existing approval or input workflows unrecoverable after an abort that started no work.
- `merge-risk: 🚨 session-state`: The patch changes deletion semantics for persisted approval and input resume state.
- `merge-risk: 🚨 message-delivery`: The affected resumes can include Gmail sends, so incorrect cleanup semantics can alter whether a completed send is safely retried or replayed.

## Summary

This PR addresses a real cancellation and replay-safety gap and includes strong after-fix runtime evidence, but its new unconditional abort cleanup can discard a resumable approval or input before any resumed stage runs. Keep it open for that session-state regression to be repaired before merge.

## What This Changes

The branch propagates cancellation through selected subprocess-backed commands and pipelines, halts subsequent work after cancellation, and consumes aborted resume state to prevent replay of completed side effects.

## Best Possible Solution

Consume a resume token only after resumed execution has crossed a side-effect-capable boundary; preserve it for a pre-start abort, while retaining the new cleanup for aborted runs that may have completed external work.

## Reproduction Assessment

Yes. The changed pre-stage abort check and unconditional aborted-resume cleanup provide a high-confidence source path: abort a saved approval or input resume before its first resumed stage, then attempt the same token again.

## Solution Assessment

No. The replay-prevention approach is right after work can have run, but deleting state for every aborted resume is broader than necessary; it should distinguish pre-start cancellation from an aborted execution that may have side effects.

## Summary

Keep this PR open: the process-termination fixes and proof are strong, but cancellation during an in-flight Gmail send still returns normally after preserving the completed result, allowing the unchanged pipeline runner to start a downstream stage. The current head is unchanged from the prior review that raised this blocker.

## What This Changes

The PR propagates parent cancellation to Gmail search and legacy GitHub monitor subprocesses, suppresses later Gmail drafts after cancellation, and adds process-lifecycle regression coverage.

## Best Possible Solution

Represent the completed send as partial definitive output while halting the pipeline before any downstream stage, then add a regression pipeline with a side-effect sentinel proving that the sentinel never starts.

Rationale: The runtime must preserve the definitive result of the completed email send while also preventing downstream execution; current contracts do not clearly designate whether an ordinary halt result or a distinct cancelled-partial-output outcome is intended.

Options:

- **Halt with completed output (recommended):** Return the completed send results with a pipeline halt so later stages do not start, documenting this as the supported partial-cancellation contract.
- **Add cancelled partial output:** Introduce an explicit runtime outcome that carries completed results while marking the overall workflow cancelled and suppressing later stages.
- **Fail after send settlement:** Throw after the in-flight send settles, preventing downstream work but omitting its completed result from the normal output.

## Solution Assessment

No. Moving subprocess cancellation ownership into the affected commands is appropriately narrow, but the in-flight send path also needs an explicit result-preserving halt or cancellation outcome before the fix is complete.

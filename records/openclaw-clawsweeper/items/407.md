## Summary

Keep open: the recoverable dispatch design is useful, but current head can still recover receipt-only duplicate successes and can still redispatch repeatedly after a stale-claim retry crash.

## What This Changes

The branch adds deterministic dispatch receipt keys, recoverable command-router claims, assist/repair workflow receipt dedupe, repair run-name matching, and focused tests for interrupted dispatch recovery.

## Best Possible Solution

Keep the deterministic receipt-key approach, but make recovery prove that the owner workflow actually proceeded and refresh the durable claim when redispatching stale or failed receipts.

## Reproduction Assessment

Yes, from source inspection: a duplicate receipt-only success plus a failed older owner run reproduces false recovery through `dispatchClaimDecision()`. A stale prior claim also reproduces immediate redispatch after a second crash because the retry path does not refresh `processed_at`.

## Solution Assessment

No, not yet; deterministic receipt keys are the right narrow direction, but the implementation still needs owner-run proof for recovery and a fresh claim timestamp for stale retries.

## Summary

Keep open: the recovery design is useful, but the new receiver-side receipt gates can turn duplicate dispatches into zero execution instead of exactly one execution. The PR needs a narrow workflow fix before merge.

## What This Changes

The PR adds deterministic dispatch receipt keys, recoverable durable command claims, receiver-side receipt dedupe for assist and repair workflows, active-run matching for keyed repair runs, focused tests, and a changelog entry.

## Best Possible Solution

Keep the recoverable receipt-key design, but make receiver dedupe choose exactly one winning run and skip only later duplicates, with focused workflow/source regression coverage.

## Reproduction Assessment

Yes by source inspection, though I did not run live GitHub dispatches. Two same-key assist or repair workflow runs can be visible to each other, and the new `any(... id != current)` receipt check lets both decide they are duplicates.

## Solution Assessment

No, not as currently implemented. The recoverable claim direction is narrow and useful, but the receiver-side dedupe must choose a single winner rather than letting every same-title run skip.

## Summary

This appears to be a concrete exact-review workflow reliability bug, but the durable queue’s completion-error contract has not been verified enough to safely treat the reported 409s as benign. Keep the issue open for a focused source-and-contract fix; the reporter’s sampled logs provide strong evidence that the current failure accounting is misleading.

## What This Changes

Distinguish terminal-safe durable-queue completion conflicts from real completion failures in exact-review runs, while logging unexpected response bodies.

## System Context

The exact-review workflow claims a durable queue lease, generates and publishes a review, then reports the terminal outcome to the queue. The completion response determines whether the workflow is marked successful and whether the queue may retry work that was already completed.

## Architecture Diagram

flowchart LR
  A[Exact-review workflow] --> B[Claim durable queue lease]
  B --> C[Generate and publish review]
  C --> D[Send completion callback]
  D --> E{Completion response}
  E -->|Terminal-safe conflict| F[Record non-failure outcome]
  E -->|Unexpected error| G[Fail with diagnostic body]
  F --> H[Accurate dashboards and retry behavior]
  G --> H

## Best Possible Solution

Define and test the completion endpoint’s typed 409 contract, then make only explicitly terminal-safe codes non-failing while logging redacted response bodies for every other non-2xx response.

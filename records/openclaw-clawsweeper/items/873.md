## Summary

Keep this PR open. Its durability direction is well motivated, but the new worker handoff can accept a durable intake record whose base64 job payload exceeds GitHub Actions’ workflow-dispatch input budget, leaving an accepted cluster repeatedly unable to start a worker. The author is a repository member, so this item also requires maintainer review rather than automated cleanup.

## What This Changes

The branch moves scheduled GitCrawl cluster intake to a durable Cloudflare append/materializer flow, adds selective live candidate filtering, and hardens repair-worker dispatch and result publication.

## System Context

Cluster repair intake turns GitCrawl issue and PR clusters into bounded repair jobs for the repair lane. The intake workflow appends durable intent, the state materializer projects job and ledger state and dispatches a worker, and result publication records the worker outcome.

## Architecture Diagram

flowchart LR
  A[GitCrawl cluster snapshot] --> B[Cluster intake workflow]
  B --> C[Durable intake queue]
  C --> D[State materializer]
  D --> E[Job and intake ledger]
  E --> F[Repair worker dispatch]
  F --> G[Result publication]

## Best Possible Solution

Keep exact job content durable, but use a dispatch-safe bounded payload contract: either reject or split oversized jobs before acceptance, or dispatch an authenticated reference that the worker resolves from the durable state surface; add a regression test at the maximum accepted size.

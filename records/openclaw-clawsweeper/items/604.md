## Label Justifications

- `P1`: A live issue-to-repair workflow can queue work that predictably fails at its first execution gate, leaving operator automation unhealthy.
- `impact:security`: The required decision controls which external repositories may receive automated branch and PR mutation authority.

## Summary

Current main still documents and dispatches viable issue implementation for eligible `steipete/*` repositories, while the repair worker uses a default `openclaw` owner boundary and the reported CrabFleet registration rejected `steipete/oracle`. This is a real, recent policy mismatch, and the issue is maintainer-authored, so it should remain open for an explicit execution-scope decision.

## What This Changes

Align external-repository issue implementation intake with the repository scope that the repair executor and CrabFleet are authorized to run.

## Best Possible Solution

Introduce one repository-level executable-scope policy consumed by every issue-intake and worker path; fail closed before committing jobs, record a clear policy-blocked audit result, and reconcile existing impossible jobs, while requiring explicit GitHub App and CrabFleet approval before any external repository becomes executable.

## Summary

Keep open: the report provides a concrete two-platform reproduction on the current release, and the available current documentation confirms that vault entries can carry `clientInfo` but does not show that dynamic-registration data is persisted automatically after authorization. The closed refresh and scope reports are adjacent rather than a replacement. Likely related people: `steipete` is the best available routing candidate, with low-confidence repository-history evidence.

## What This Changes

Persist the OAuth dynamic-client registration information produced during Atlassian authorization so the saved refresh token can be redeemed after the access token expires.

## System Context

MCPorter authenticates configured HTTP MCP servers through OAuth and stores credentials in a local vault. Later runtime requests use the stored token set and client-registration information to refresh expired access tokens before connecting to the MCP server.

## Architecture Diagram

flowchart LR
  A[HTTP MCP server config] --> B[OAuth authorization command]
  B --> C[Dynamic client registration]
  C --> D[Token exchange]
  D --> E[Local credential vault]
  E --> F[Expired-token refresh]
  F --> G[Authenticated MCP request]

## Best Possible Solution

Persist the DCR client record atomically with the issued token set, retain configured pre-registered client settings as the higher-priority source, and add regression coverage for an expired-token refresh after a fresh dynamic OAuth authorization.

## Summary

Keep this PR open for a narrow follow-up: the contributor’s updated branch addresses the earlier bounded-operation, first-frame, and changelog concerns and includes credible real runtime evidence, but the progress-cadence floor can still exceed an allowed caller idle deadline below 25 ms. That can reintroduce a transport restart/replay instead of returning the daemon’s intended operation timeout.

## What This Changes

The PR forwards the OAuth timeout through `listTools`, adds versioned daemon progress frames, and uses them to keep OAuth-backed paginated tool discovery alive without restarting the daemon.

## System Context

`mcporter auth` discovers a server’s tools while the OAuth browser authorization may be in progress. For keep-alive servers, the CLI sends that request through a local daemon; the daemon must distinguish a working multi-phase request from a silent or wedged one before returning the tool list.

## Best Possible Solution

Keep progress intervals strictly below every accepted positive idle deadline, or reject unsupported sub-floor deadlines consistently at the public timeout boundary, and cover the chosen contract with a socket-level regression test.

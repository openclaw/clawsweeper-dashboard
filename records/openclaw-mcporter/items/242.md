## Label Justifications

- `P1`: The PR touches OAuth launch behavior and can break ordinary Windows authorization URLs or preserve server-controlled command-shell interpretation.
- `merge-risk: 🚨 security-boundary`: The authorization URL crosses into `cmd.exe`, whose metacharacter parsing can turn URL text into command syntax.
- `merge-risk: 🚨 compatibility`: Existing Windows OAuth flows commonly include `&` query separators and may fail or truncate after this argument-shape change.

## Summary

Keep this PR open: the stated fix still sends the OAuth URL through `cmd.exe`, and ordinary OAuth URLs commonly contain `&`, which `cmd` can parse as a command separator unless the final command line is escaped for `cmd` itself. The prior changelog finding was addressed, but the P1 command-injection/truncation concern remains unresolved; the claimed proof is mocked argv inspection, not an after-fix Windows runtime result.

## What This Changes

The PR replaces a single Windows OAuth browser-launch shell string with separate `cmd /c start` arguments, adds mocked Windows-launch tests, and records the change under Unreleased.

## System Context

`mcporter auth` receives an OAuth authorization URL from provider metadata and hands it to the operating system’s browser launcher. On Windows, this path invokes `cmd.exe` and `start`, so Node’s process argument serialization must remain safe through the additional `cmd` parsing layer before the browser receives the URL.

## Architecture Diagram

flowchart LR
  A[OAuth provider metadata] --> B[Authorization URL]
  B --> C[mcporter auth]
  C --> D[Windows browser launcher]
  D --> E[cmd.exe parsing]
  E --> F[start command]
  F --> G[Default browser]

## Best Possible Solution

Avoid using `cmd.exe` for browser launch if a Windows shell-free launcher is available; otherwise construct and validate a cmd-safe invocation, add tests for the actual final command-line semantics, and show a redacted real Windows launch with normal and metacharacter-bearing authorization URLs.

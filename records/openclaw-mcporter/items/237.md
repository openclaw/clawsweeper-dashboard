## Summary

Keep this PR open: it fixes a real OAuth authorization timeout path and resolves the earlier direct/daemon plumbing findings, but its new fixed daemon socket budget can still time out and retry a paginated `listTools` request after a successful OAuth flow. Real after-fix evidence is also not attached to the PR yet.

## What This Changes

The PR forwards the configured OAuth timeout through `auth`, runtime, and keep-alive daemon calls so OAuth-triggered tool discovery can exceed the SDK’s default 60-second request limit.

## System Context

`mcporter auth` starts OAuth while discovering an MCP server’s tools. The request may run directly or through the keep-alive daemon, which connects to the server, waits for authorization, and then returns the discovered tools to the CLI.

## Architecture Diagram

  F --> G[CLI authorization result]

## Best Possible Solution

Use one explicit end-to-end listing deadline or daemon progress/remaining-budget mechanism that covers OAuth plus every cursor page, then prove both direct and keep-alive OAuth authorization against a paginated server without a duplicate attempt.

## Reproduction Assessment

Yes, from source: use a keep-alive OAuth server whose tool discovery returns at least two cursor pages and delay the later page so OAuth plus the first page consumes most of the configured timeout. The daemon’s static `2 * timeoutMs + 5s` deadline can then expire before the later page completes.

## Solution Assessment

No. Forwarding the timeout is the right repair boundary, but a static two-phase socket budget does not cover the existing cursor-pagination loop; the transport must account for all listing pages or enforce one shared end-to-end deadline.

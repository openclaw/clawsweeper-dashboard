## Summary

The latest commit is only a CI retry, so the three blockers from the prior review remain: reset ordering can hide a binding exhausted lane, provider exclusion is not model-family-aware, and highest-usage ranking can disagree with the rendered percentage. The live CLI output proves the production quota inputs but not the changed selection result, while the permanent automatic-selection contract requires maintainer direction.

## What This Changes

The PR makes Antigravity automatic menu-bar and highest-usage selection consider exhausted supported quota lanes, introduces time-aware reset ordering, and expands focused regression coverage.

## Best Possible Solution

Define mode-aware Antigravity semantics: reset-focused text may select by relevant reset behavior, while percentage, pace, and highest-usage flows should share one binding quota lane for ranking and rendering and exclude Antigravity when every model family is blocked.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Antigravity automatic selection use context-specific semantics—reset-oriented selection for reset text and a shared binding lane for percentage, pace, and highest usage—or should one global lane-selection rule govern every display mode?

Rationale: The shared resolver serves different user intents, and neither source behavior nor tests establish whether reset urgency or actionable quota pressure should take precedence across all modes.

Likely owner: steipete

Owner reason: This choice defines repository-wide menu-bar product semantics rather than a mechanical implementation detail.

Owner confidence: medium

Options:

- **Use context-specific selection (recommended):** Select by reset relevance for reset-focused text, but use one binding quota lane consistently for percentage, pace, provider ranking, and rendered highest-usage text.
- **Use one constrained-lane rule:** Always select the most binding supported quota lane and use reset time only as a tie-breaker across all automatic modes.
- **Preserve usable-lane behavior:** Continue suppressing exhausted lanes whenever another lane remains usable, accepting that reset-focused text will not surface the blocked quota.

## Reproduction Assessment

Yes from source and supplied live inputs: current main filters fully used Antigravity summary windows, and the redacted production output demonstrates exhausted five-hour lanes alongside usable weekly lanes. The final native menu selection was not captured, so this is source-reproducible rather than a complete observed UI reproduction.

## Solution Assessment

No, not yet. Surfacing exhausted lanes addresses the reported reset-time problem, but the shared resolver currently creates inconsistent reset, actionability, exclusion, ranking, and rendered-text behavior; a mode-aware shared-lane design is safer.

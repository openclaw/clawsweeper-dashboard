## Summary

The report identifies a plausible, bounded background-refresh bug: Chromium imports appear to be rejected before the existing no-UI Keychain preflight can establish that access is already allowed. Keep this issue open for source confirmation and a focused repair; the generic personal-repository policy does not permit auto-closing it.

## What This Changes

Allow non-interactive Chromium cookie imports when a no-prompt Keychain preflight confirms that the browser’s Safe Storage item is already accessible.

## System Context

CodexBar’s browser-cookie import path supplies authenticated web-session data to provider usage fetchers. The access gate decides whether a background refresh may read Chromium’s Keychain-protected Safe Storage key before the provider either reports account usage or chooses a fallback source.

## Architecture Diagram

flowchart LR
  A[Scheduled or CLI refresh] --> B[Provider usage fetcher]
  B --> C[Browser cookie import]
  C --> D[Chromium Keychain access gate]
  D --> E[No-prompt access preflight]
  E --> F[Cookie decryption]
  F --> G[Account usage or fallback result]

## Best Possible Solution

Make the background Chromium gate consult a no-UI preflight and allow import only for an explicit allowed result; retain conservative denial for disabled, uncertain, failed, or interaction-required access, with focused decision-table tests.

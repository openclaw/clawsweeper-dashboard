## Summary

Keep this PR open: its intended cost-refresh behavior is useful, but the current guard can permanently discard a menu-open forced refresh while a normal token sequence is running. The existing reviewer comment identifies the same still-unfixed P2 path, and the PR also needs after-fix evidence from a real CodexBar menu session before merge.

## What This Changes

This pull request makes the “Refresh all providers on menu open” path schedule a nonblocking forced token-cost refresh so the Cost row updates with provider usage.

## System Context

CodexBar creates a menu-open refresh plan from enabled providers and user settings, then the status-item controller runs the plan without blocking AppKit menu tracking. UsageStore performs token-cost scans and publishes the resulting snapshot, which the open menu observes to refresh its rows.

## Architecture Diagram

flowchart LR

  B --> C[Provider usage refresh]
  B --> D[Forced token-cost refresh]
  C --> E[Usage store snapshot]
  D --> E
  E --> F[Observed menu rows]

## Best Possible Solution

Preserve the nonblocking menu-open behavior, but coalesce a pending forced cost refresh behind any active non-forced sequence and demonstrate the resulting Cost-row update in a freshly built CodexBar session.

## Reproduction Assessment

Yes, from source: start a normal token-refresh sequence that can treat a provider’s cached cost as TTL-fresh, then open the menu with refresh-all enabled before that sequence finishes. The new guard returns without preserving the forced refresh request, so no forced follow-up occurs.

## Solution Assessment

No. The nonblocking approach is appropriate for AppKit menu tracking, but returning on any active sequence is too broad; the forced request should be serialized or coalesced after a non-forced sequence completes.

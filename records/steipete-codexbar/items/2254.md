## Maintainer Decision

Required: true

Kind: merge_risk

Question: Should CodexBar preserve retired and future-unknown provider records for rollback and restoration, or intentionally delete their stored settings during a later config save?

Rationale: The current branch deliberately codifies lossy decoding, but that policy can permanently erase credentials and also affects provider IDs beyond the two being retired; only the repository owner can authorize that compatibility tradeoff.

Likely owner: steipete

Owner reason: Authored both the provider-retirement policy and the implementation that selects the destructive config behavior.

Owner confidence: high

Options:

- **Round-trip unknown records (recommended):** Keep unknown provider records inert and hidden while preserving their raw configuration through subsequent saves.
- **Migrate retired records to backup:** Remove only the two known retired IDs after creating an explicit recoverable backup and clearly notifying affected users.
- **Accept destructive cleanup:** Keep the lossy decoder and explicitly accept that upgrades, downgrades, and later restoration can permanently lose provider settings.

## Reproduction Assessment

Yes, at source level: load a config containing an unrecognized provider record and then save any setting; the decoded model no longer contains that record, so the rewritten file loses it. A focused round-trip test should demonstrate the failure without accessing real credentials or Keychain.

## Solution Assessment

No. Retiring the providers may be an intentional policy outcome, but a generic lossy decoder is broader and more destructive than necessary; inactive opaque preservation or a narrow recoverable migration is safer.

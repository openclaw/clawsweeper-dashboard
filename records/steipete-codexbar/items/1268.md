## Summary

Keep open: current main supports opt-in multi-account Claude usage cards, but it does not implement separate account status-bar items; the status-item identity and storage remain provider-scoped. The owner’s July 1 architecture decision and July 17 cross-link direct the remaining product discussion to https://github.com/steipete/CodexBar/issues/1843, so this should remain available for that confirmed direction rather than be auto-closed.

Likely related people
- `steipete` — high confidence product and architecture owner for the documented multi-account/status-item direction.
- `optimiz-r` — medium confidence implementation contributor for the merged multi-account snapshot and menu-card foundation.

## What This Changes

Request an opt-in way to show multiple accounts for one provider as distinct status-bar indicators with separate usage visibility.

## Best Possible Solution

Implement the owner-documented selected-account mode only after confirming its UX contract: opt-in selection, a bounded four-item cap, aliases or ordinals instead of email, provider aggregate replacement rather than duplication, and mutual exclusion with Merge Icons.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should CodexBar proceed with the selected-account status-item mode described in the multi-account design, including aggregate-item replacement, a four-account cap, aliases/ordinals, and mutual exclusion with Merge Icons?

Rationale: Current main has the account-snapshot and stacked-menu foundation but no account identity, persistence, ordering, or coexistence contract for status items; the owner explicitly left these product choices for discussion.

Likely owner: steipete

Owner reason: The owner authored both the architecture decision and the issue comments that frame the remaining product choices.

Owner confidence: high

Options:

- **Sponsor the bounded selected-account mode (recommended):** Adopt the documented opt-in, capped account-item mode that replaces the provider aggregate item and is mutually exclusive with Merge Icons.
- **Retain menu-only account visibility:** Keep the current stacked account cards and defer status-bar fan-out until a stronger user need or interaction model is established.
- **Choose an additive account-item design:** Allow selected account items alongside the provider aggregate only after explicitly defining duplication, merge-mode, ordering, and migration behavior.

## Solution Assessment

No—the additive per-account toggle proposed in the discussion is not the best established path because it duplicates provider/account indicators and conflicts with Merge Icons semantics; the merged architecture document’s bounded replacement mode is the safer basis if maintainers sponsor it.

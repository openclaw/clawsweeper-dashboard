## Label Justifications

- `impact:ux-friction`: Unattributed generated sessions cause avoidable user confusion and investigation burden while the application otherwise remains usable.

## Summary

This appears to be a valid current-main bug: CodexBar still launches an interactive Claude CLI process for passive usage probing without an ephemeral or reusable session control, and the prior local-artifact cleanup does not address account-side sessions. Keep it open for a maintainer-approved privacy-safe probe design and live verification against a real Claude account.

## What This Changes

Prevent passive Claude CLI usage probes from creating a new durable empty account session on every launch.

## Best Possible Solution

Make passive Claude probing side-effect free; if the CLI cannot create an ephemeral session, use one deterministic account-scoped probe session with safe credential-change handling, focused launch tests, and redacted live proof that repeated refreshes do not add account sessions.

Rationale: Both choices affect provider availability and remote account state, and repository policy requires explicit sign-off for provider authentication, remote data handling, and privacy-sensitive behavior.

Likely owner: steipete

Owner confidence: high

Options:

- **Reuse one scoped session (recommended):** Keep CLI usage fallback but derive and reuse a probe-only session identifier scoped to the active Claude credential, with upgrade and account-switch tests.
- **Disable passive CLI probing:** Stop automatic interactive CLI launches and require OAuth or explicit user action, avoiding remote session creation at the cost of reduced fallback coverage.
- **Document current behavior:** Retain the current launch behavior but clearly disclose the generated sessions, which reduces confusion without preventing account-list pollution or rate-limit use.

## Reproduction Assessment

No, this review did not independently reproduce the account-side session creation on a real Claude account. The current launch path and the reporter's detailed local/account correlation make it highly source-reproducible, but repository policy discourages unsolicited live provider probes.

## Solution Assessment

Unclear: reusing a fixed session is the narrowest likely repair, but it is only safe if scoped to the active credential and proven not to mix accounts or retain unwanted content. Disabling passive CLI fallback is the safer fallback if those guarantees cannot be established.

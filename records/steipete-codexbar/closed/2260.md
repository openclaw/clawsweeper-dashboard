## Summary

Current main already provides provider-scoped browser-cookie cache clearing, but it does not eagerly import and persist a replacement cookie in the same operation, so the requested one-shot refresh remains distinct. VISION.md requires sign-off for new features affecting provider authentication or stored credentials.

- @QuarkAssistant — recent contributor to adjacent CodexBarCLI Keychain-cache behavior through https://github.com/steipete/CodexBar/pull/679 (medium confidence).

## What This Changes

Requests a CLI operation that clears and immediately re-imports browser cookies for one provider or all cookie-authenticated providers.

## Best Possible Solution

Extend the existing `codexbar cache clear --cookies --provider <id>` surface with an explicit eager re-import option backed by shared provider metadata or strategy APIs, starting provider-scoped and adding all-provider refresh only when eligibility and prompt behavior are deterministic.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should CodexBar support eager browser-cookie re-import from the CLI, and if so should it extend `cache clear` or introduce a separate `cookie refresh` command?

Rationale: Current main solves cache invalidation but not eager credential replacement; VISION.md reserves new authentication and storage behavior for sign-off, and the command shape determines whether CodexBar gains a parallel authentication-orchestration surface.

Likely owner: steipete

Owner reason: VISION.md makes this an explicit product and authentication-surface decision, and the repository owner is the clearest available decision owner.

Owner confidence: high

Options:

- **Extend cache clear (recommended):** Add a provider-scoped `--reimport` or `--refresh` option that reuses shared provider cookie-import strategy metadata and avoids a parallel command namespace.
- **Add cookie refresh:** Create a dedicated command with explicit provider eligibility, browser-order, Keychain, and all-provider semantics.
- **Keep two-step workflow:** Document cache clearing followed by a normal provider fetch as the supported account-switch recovery path and decline eager import.

## Reproduction Assessment

Yes at source level: current main reuses cached cookie entries and its CLI clear command only deletes them, so a still-valid old account cookie persists until the user explicitly clears it. A live browser or Keychain reproduction was intentionally not run because repository policy forbids unrequested credential probes.

## Solution Assessment

No, not exactly as proposed. The user need is valid, but extending the established cache command through shared provider strategy metadata is narrower and less likely to duplicate provider-specific authentication logic than a standalone command with direct importer dispatch.

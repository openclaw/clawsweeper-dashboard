## Label Justifications

- `P2`: The widget can display materially different data ages under one apparent refresh control, but setup and core runtime remain usable.
- `impact:ux-friction`: Users selecting a short refresh interval can still see token/cost rows remain up to an hour behind freshly updated quota data.

## Summary

Keep open for maintainer direction: current main retains an independent hourly token/cost refresh policy, and the recent widget-freshness work intentionally addressed sequencing and stale-age disclosure without changing that cadence.

## What This Changes

Requests that widget token/cost snapshot refresh eligibility follow the configured global refresh frequency rather than a fixed hourly interval.

## Best Possible Solution

Choose an explicit cadence contract, preferably using the global interval with in-flight coalescing plus a safe minimum or timeout backoff, or expose a separate token/cost interval if hourly isolation remains intentional.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should automatic token/cost scans follow the global refresh frequency, or remain independently throttled because local history scans can be expensive?

Rationale: Recent merged work deliberately preserved slower asynchronous scanning, so switching to the potentially one-minute global cadence requires an explicit performance and UX policy choice.

Likely owner: steipete

Owner reason: The recent history ties this person most directly to refresh-loop and widget token policy decisions.

Owner confidence: high

Options:

- **Global cadence with safeguards (recommended):** Use the configured global interval for eligibility while preserving coalescing and adding a minimum interval or timeout backoff for expensive scans.
- **Separate token cadence:** Keep token scans independent but add a dedicated setting and matching widget/preferences copy so the slower cadence is explicit.
- **Retain hourly policy:** Keep hourly automatic scans and clearly document that global refresh frequency applies to provider quota refreshes rather than local token history.

## Reproduction Assessment

Yes, at source level: current main retains a separate throttled token-refresh path and hourly user-facing cadence, matching the reported mixed-freshness behavior. A live WidgetKit run would strengthen runtime proof but is not necessary to establish the policy mismatch.

## Solution Assessment

Unclear until maintainers select the intended performance policy. Directly adopting a one-minute interval may be too aggressive for scans that can take minutes, so safeguards or a separate explicit cadence may be more maintainable.

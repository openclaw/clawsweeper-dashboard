## Summary

Keep this PR open for maintainer review: the retry and stale-cache work is useful, but the blanket `GET /user` rewrite changes existing authenticated `gh api /user` semantics and can silently remove private fields instead of falling back to real `gh`. The PR also has only test-summary proof, not real after-fix behavior proof.

## What This Changes

The PR rewrites relay `GET /user` to a token-free public profile, retries transient CLI relay fallbacks with configurable backoff, serves stale token-free cache on public-backend outages, extends active workflow-run-list TTL, and updates tests, docs, and release notes.

## Best Possible Solution

Preserve authenticated `GET /user` semantics by default, and make token-free identity probes an explicit narrow path such as a CLI `.login` special-case or opt-in public-profile mode with documented fallback behavior.

## Reproduction Assessment

Yes by source inspection: with jq installed, `octopool gh api /user --jq .total_private_repos` remains relay-safe, the Worker rewrites `/user` to `/users/:login`, and the sanitized public user body lacks the private field. I did not run the test suite because this review must keep the checkout read-only.

## Solution Assessment

No. The blanket server-side rewrite is not the safest solution because it cannot know whether the caller needs authenticated-only fields; a narrower CLI identity-probe path or explicit public-profile opt-in would preserve compatibility.

## Summary

Keep this recent, well-specified feature request open for an explicit repository-owner decision. Current main has no FxTwitter/FxEmbed transport, while the proposal is compatible with Birdclaw’s architecture and vision in principle; the unresolved question is whether core should assume the privacy, reliability, configuration, and long-term support obligations of an opt-in public third-party service.

## What This Changes

Add an explicitly selected FxTwitter transport for public post, thread, conversation, profile, timeline, and search reads, with self-hosted endpoint support and capability gating.

## Best Possible Solution

If sponsored, implement a phased, explicit-opt-in adapter limited initially to public post lookup, threads/conversations, profiles, public timelines, and search; reuse canonical persistence, expose precise capabilities and provenance, allow validated HTTPS self-hosting, use recorded fixtures, and never make it an implicit fallback.

## Risks / Open Questions

- The hosted service would receive requested post IDs, handles, search terms, and caller network metadata, so opt-in and disclosure semantics become part of Birdclaw’s privacy contract.
- FxTwitter availability, response compatibility, rate limits, and endpoint longevity are outside Birdclaw’s control and could create a recurring core-support burden.
- Normalizing public API results into canonical local records must preserve provenance and completeness without implying authenticated home, bookmark, like, mention, or DM membership.
- A configurable base URL introduces URL-validation and network-boundary requirements, including rejecting credential-bearing URLs and unsafe schemes.

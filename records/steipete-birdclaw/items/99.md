## Summary

Keep this recent feature proposal open for repository-owner review. Current main provides reusable transport, HTTP, normalization, persistence, and capability boundaries but does not implement FxTwitter; the request is potentially compatible with Birdclaw’s multi-source direction, yet committing to a third-party public service and configurable endpoint requires explicit product and security approval.

## What This Changes

Add an explicit opt-in FxTwitter read provider for public post, thread, profile, timeline, and search operations, with canonical persistence and configurable self-hosted endpoint support.

## Best Possible Solution

If approved, add one explicitly selected `fxtwitter` provider through the existing gateway and canonical ingestion path, initially limit it to documented public-read capabilities, require clear third-party disclosure, validate endpoint policy before requests, and cover decoding, pagination, idempotency, capability rejection, rate limiting, and fresh-versus-cached behavior with fixtures.

## Risks / Open Questions

- Public-service requests would disclose tweet IDs, handles, search terms, and caller network metadata to a third party, so consent and attribution behavior must be explicit.
- A configurable base URL needs a defined trust policy for schemes, URL credentials, redirects, DNS changes, private-network destinations, and deployments where requests can be initiated through Birdclaw's server surface.
- FxTwitter's availability, rate limits, response compatibility, and long-term API stability would become an ongoing core maintenance obligation.
- The appropriate permanent capability boundary remains unconfirmed: public search results must not be presented as authenticated home, bookmark, like, mention, or DM state.

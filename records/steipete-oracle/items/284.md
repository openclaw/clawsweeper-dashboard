- `impact:message-loss`: The observable failure is a completed assistant response that Oracle harvests as zero turns/output.

## Summary

Keep open. The report is concrete and still actionable for remote-CDP browser mode: current main has related response-capture and harvest-recovery hardening, but source inspection does not prove that remote runs persist the newly created ChatGPT `/c/<id>` URL before an external no-thinking watchdog kills the CLI.

## What This Changes

The issue requests browser-mode hardening so live ChatGPT runs are not misclassified as stalled when thinking-state selectors drift, and reattach/harvest re-resolves the conversation tab instead of trusting a stale CDP target.

## Best Possible Solution

Persist a recoverable ChatGPT conversation URL as soon as a remote submitted run discovers `/c/<id>`, make reattach/harvest prefer that URL over stale target ids, and keep the existing snapshot watchdog plus PR 278 stability guard as the response-capture layer.

## Reproduction Assessment

Yes, at source level but not as a live run: the issue gives concrete v0.15.0 remote-CDP symptoms, and current code shows remote metadata can remain on a non-conversation URL while recovery requires a saved `/c/<id>` URL. I did not run the opt-in ChatGPT Pro live smoke needed for a high-confidence runtime reproduction.

## Solution Assessment

Yes, the suggested direction is the right narrow repair: use outcome/conversation evidence instead of treating missing thinking-status UI as dead, and recover by saved conversation URL rather than CDP target id. The implementation should build on existing response polling, PR 278 stability behavior, and PR 226 recovery instead of adding a parallel harvest path.

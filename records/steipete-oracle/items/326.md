## Label Justifications

- `P1`: A confirmed submitted long Pro run can finish successfully in ChatGPT while Oracle loses the answer and leaves the session permanently running, breaking a real browser workflow.
- `impact:message-loss`: The completed assistant response is not captured into a transcript or response artifact despite remaining available in the live ChatGPT target.
- `impact:session-state`: The session and model run remain `running` with `chrome-disconnected` after the server-side response has completed, leaving stored state inconsistent with reality.

## Summary

Current main still handles `connection-lost` differently from assistant timeout: it preserves a submitted run as `running` and returns reattach guidance, but only the timeout path invokes automatic reattach. That matches the reported failure, and neither v0.16.0 nor the current 0.16.1 changelog records a fix for recoverable target-level CDP disconnects.

## What This Changes

Recover a submitted browser run after a target-level CDP client disconnect when Chrome and its ChatGPT target remain alive, preserving conversation identity and harvesting the completed response.

## Best Possible Solution

Add bounded, identity-safe reconnection for `connection-lost`, using the recorded target when still present and the saved conversation URL when available, then harvest and reconcile completed state while retaining the original disconnect diagnostic.

## Solution Assessment

Yes in direction: reusing the existing reattach and conversation-targeting machinery is narrower and safer than adding another recovery mode, provided reconnection verifies target or conversation identity and remains bounded.

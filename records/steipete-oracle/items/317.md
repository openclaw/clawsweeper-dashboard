## Summary

Current main still presents requested browser model keys as if they were observed model identities in launch, finish, completion, and compact session output, even though exact verified picker evidence is persisted. This is a narrow, actionable display/provenance bug with no open replacement PR, so the issue remains necessary.

## What This Changes

Distinguish requested browser model keys and picker targets from exact verified ChatGPT picker labels in user-facing CLI and session displays.

## Best Possible Solution

Add a shared browser display-identity helper that preserves the requested key as explicit provenance, uses the exact `resolvedLabel` only when selection evidence is verified, and is consumed consistently by launch, immediate finish, stored completion, status/session rows, and compact MCP text without changing structured `model` semantics.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes at source level: current-main launch, finish, stored completion, and compact session renderers directly use the requested/internal model while verified picker evidence is persisted separately. A live browser run is useful final proof but is not required to establish this deterministic display mismatch.

## Solution Assessment

Yes, with a small refinement: use one display-only resolver rather than changing model routing or the semantic `metadata.model` field. Exact verified labels should be shown verbatim, including bare `Pro`, with requested keys retained alongside them or used as fallback.

## Label Justifications

- `impact:ux-friction`: Users can incorrectly interpret a requested internal key as verified ChatGPT model identity, particularly with current/ignore strategies and the generic Pro picker label.

## Summary

Current main still appears to conflate requested browser model keys with observed model identity across launch, completion, status, and session displays. The clean, proof-backed linked pull request remains open and explicitly owns the fix, so this issue remains necessary until that PR is merged or closed.

## What This Changes

Distinguish requested browser model keys, intended picker targets, and verified picker labels in CLI and TUI output without changing API-mode behavior.

## Best Possible Solution

Review and land https://github.com/steipete/oracle/pull/318 so every browser display uses an exact non-empty verified picker label when available, otherwise fails closed to the requested key, while retaining both values in detailed provenance views.

Yes at source level: the supplied browser dry-run and current render paths show requested model metadata where an observed identity is implied, while persisted selection evidence can contain a different verified label. A fresh live browser run was not required to establish this display-path defect.

## Solution Assessment

Yes. A shared provenance-aware display helper that uses `resolvedLabel` only when non-empty and verified, otherwise retaining the requested key, is narrower and safer than changing model mapping, routing, or persisted schema.

## Summary

Keep open: this proposes a new execution architecture for accelerating clustered reviews, and the available current-main and related-work evidence does not establish the warmed snapshot-fork lifecycle as implemented. It needs a maintainer decision on the runtime, isolation, invalidation, and operator-safety contract before a bounded implementation can be chosen.

## What This Changes

Add a warmed per-repository workspace pool that snapshot-forks an isolated ready-to-run checkout for each issue worker instead of repeating clone, dependency, cache, and build setup.

## System Context

Clownfish turns GitHub issue and pull-request clusters into isolated Codex worker jobs. Repository preparation feeds those workers; this proposal would replace repeated setup with a pre-warmed base workspace and disposable per-item forks.

## Architecture Diagram

flowchart LR
  A[Repository job request] --> B[Warm base workspace]
  B --> C[Snapshot-fork per item]
  C --> D[Isolated Codex worker]
  D --> E[Review or repair result]
  E --> F[Discard fork and retain base]

## Best Possible Solution

Define a narrow workspace-pool contract first—immutable base revision, per-job writable fork, secret boundary, cleanup, invalidation, capacity limits, and fallback to the existing setup path—then implement it behind an operator-controlled rollout.

## Risks / Open Questions

- A reusable warmed base can leak mutable checkout state, credentials, caches, or generated artifacts between otherwise isolated worker jobs unless its snapshot and reset boundaries are explicit.
- A fork pool needs a defined invalidation and capacity policy so workers do not run against stale repository revisions, dependencies, or build outputs.
- The choice of external runtime versus an in-repository abstraction affects deployment, observability, cleanup guarantees, and operational support.

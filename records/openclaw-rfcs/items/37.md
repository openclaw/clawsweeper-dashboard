## Summary

Keep this RFC open for a maintainer product-direction decision. It is a documentation-only proposal, not an implemented change, and its own promotion order correctly makes RFC 0018 a prerequisite before the initial hosting-profile catalog is accepted.

## What This Changes

This PR adds a draft RFC and normative sidecar defining opt-in `local`, `container`, `reverse-proxy`, and `node-mode` Gateway hosting profiles that compose readiness criteria into release-tested support postures.

## System Context

OpenClaw’s Gateway exposes readiness information to operators and hosting environments. This proposal would add an optional profile-selection layer that groups existing and proposed readiness criteria into named deployment contracts, then feeds `/readyz`, support diagnostics, and packaged conformance scenarios.

## Architecture Diagram

flowchart LR
  Operator[Operator configuration] --> Selection[Optional profile selection]
  Selection --> Criteria[Readiness criteria]
  Criteria --> Evaluation[Gateway readiness evaluation]
  Evaluation --> Projection[Readiness and status output]
  Selection --> Conformance[Packaged conformance scenario]
  Projection --> Support[Named support posture]

## Best Possible Solution

Accept or revise RFC 0018 first, then have Gateway and security owners explicitly choose whether these four opt-in postures are the initial supported catalog and require exact-head packaged conformance evidence from the linked core implementation before it lands.

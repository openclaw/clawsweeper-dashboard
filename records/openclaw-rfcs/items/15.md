## Label Justifications

- `P2`: This is an actively reviewed, bounded product/API proposal with limited immediate user impact but meaningful design importance.
- `merge-risk: 🚨 compatibility`: The proposed payload and decision semantics require explicit behavior for older clients and alignment with existing allow-session and allow-always contracts.

## Summary

Keep this draft RFC open: current OpenClaw exposes generic plugin approval request and resolution methods, but the proposed externally verified resolver remains a distinct security-sensitive capability under active maintainer review, and the promised reference-implementation proof is still missing.

## What This Changes

Adds an 837-line draft RFC defining a plugin-owned external-verification route and an ownership-checked resolver for pending approvals.

## Best Possible Solution

Finalize a minimal contract that derives plugin identity from authenticated host context, makes any denial authoritative, version-gates registration, maps onto existing allow-once/session/always semantics, records verification start and end metadata, defines a safe default decision, and is backed by redacted AgentKit/OpenClaw runtime proof.

Options:

- **Refine the narrow seam (recommended):** Keep the RFC open and require the host-derived identity, deny-dominant composition, version gating, existing approval semantics, audit timing, safe default, and runtime proof before acceptance.
- **Reject plugin resolution authority:** Keep final approval resolution exclusively in core and require external verifiers to return evidence through a less-authoritative host callback.
- **Broaden the plugin contract:** Design a general plugin-defined approval-action API, accepting the larger compatibility and security surface instead of this narrow verifier-specific seam.

## Risks / Open Questions

- The resolver would cross an approval security boundary; accepting caller-supplied plugin identity could let one caller claim another plugin's pending approval.
- Older clients may fail closed or expose only denial unless registration is explicitly version-gated and fallback behavior is proven.
- The complete approval path must preserve deny dominance and existing session/permanent approval semantics rather than creating a competing policy source.
- The RFC's proposed reference flow has not yet been demonstrated with after-change runtime evidence.

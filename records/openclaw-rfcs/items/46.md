## Summary

Keep this PR open for maintainer product-direction review: it proposes a new, compatibility-sensitive lifecycle contract above the completed SQLite snapshot RFC, and the requested ownership split has not been accepted on the evidence available here.

## What This Changes

This PR adds three draft RFC 0013 sidecar specifications for composing SQLite snapshot artifacts into aggregate recovery points, host-protected handoff, and readiness-gated restored Gateway admission.

## System Context

RFC 0013 defines OpenClaw’s verified per-database SQLite snapshot boundary. This addendum would sit above that boundary, coordinating state-owner evidence, host acceptance, source retirement, restore, and the point at which a replacement Gateway may receive work.

## Architecture Diagram

flowchart LR
  A[State owners] --> B[Verified SQLite snapshot artifacts]
  B --> C[Aggregate recovery point]
  D[Host closure and acceptance] --> E[Final handoff]
  C --> E
  E --> F[Fresh-target restore]
  F --> G[Owner and scheduler reconciliation]
  G --> H[Gateway work admission]

## Best Possible Solution

Keep RFC 0013 focused on verified per-database SQLite artifacts, then accept the lifecycle sidecars only through an explicitly approved addendum or separate RFC that states the supported OpenClaw seam, host obligations, and compatibility commitment.

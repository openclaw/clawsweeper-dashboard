## Summary

Keep this PR open: it has a blocking upgrade-safety concern because broad persistent selectors can authorize future write tools without a configuration change, and the durable write-consent contract still needs explicit approval and inspectable runtime proof.

## What This Changes

The PR adds persistent global and per-account MCP capability ceilings, resolved-account pinning, account-policy migration, documentation, and focused tests.

## Best Possible Solution

Make durable write authorization upgrade-stable by requiring exact write-tool identifiers or a versioned reapproval mechanism, while allowing broad selectors for read-only narrowing if desired.

Options:

- **Require exact persistent writes (recommended):** Allow broad read selectors but require exact tool names for every persistently authorized write capability.
- **Accept dynamic selector expansion:** Document that service, risk, and wildcard selectors intentionally authorize present and future matching write tools within baked safety ceilings.
- **Keep runtime write consent:** Use stored config only as a non-widenable selector ceiling and continue requiring --allow-write for every write-enabled process.

Yes at the source level: add a new write tool whose service or risk matches a stored broad selector, and the next policy evaluation includes it without any config change. The current registry loop and selector matcher establish this path directly.

## Solution Assessment

No, not yet: the single fail-closed resolver and account pinning are sound foundations, but a durable authorization ceiling should not silently grow after upgrades unless maintainers explicitly choose and document that behavior.

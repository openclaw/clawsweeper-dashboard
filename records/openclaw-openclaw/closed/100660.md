## Summary

Keep open: current main and the latest release still resolve the guarded link fetch timeout from the first configured link model entry, so a slower later fallback can be skipped before it is tried.

## What This Changes

The issue requests changing link-understanding fetch timeout resolution so pre-CLI HTTP fetches are not capped by only the first model entry timeout.

## Best Possible Solution

Compute the pre-CLI fetch timeout from the global per-link budget when set, otherwise from the maximum valid model-entry timeout or the default, while keeping per-entry CLI execution timeouts unchanged.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, source-reproducible: configure multiple `tools.links.models` entries where the first has a shorter `timeoutSeconds` than a later fallback, and current main passes only the first entry's timeout to `fetchWithSsrFGuard` before any fallback can run.

## Solution Assessment

Yes, the narrow maintainable fix is to separate the fetch budget from per-entry CLI execution timeouts using existing config; adding a new config key would be unnecessary unless maintainers explicitly want a separate fetch knob.

## Summary

Keep open: current main still computes memory-wiki bridge artifact status from a process-wide artifact list without caller-agent scope, so the reported status/doctor metadata leak remains valid and security-sensitive.

## What This Changes

The issue asks memory-wiki `wiki_status` and `openclaw wiki doctor` to avoid revealing another agent's bridged memory artifacts through an unscoped count and derived warning.

## Best Possible Solution

Separate agent-visible status from operator diagnostics so agents cannot infer other agents' bridged memory artifacts, while retaining an explicitly authorized global doctor/status view if maintainers want one.

Options:

- **Scope agent-visible status (recommended):** Thread caller identity into agent-visible `wiki_status` and filter artifacts by `agentIds`, while keeping global counts only behind an explicitly operator-authorized diagnostic path.
- **Gate global status:** Treat the count as an operator diagnostic and restrict the exposed status/doctor method so untrusted agent callers cannot invoke it.
- **Accept global metadata:** Declare the count intentionally global and accept that agents may infer other agents' bridge artifacts from status output.

## Reproduction Assessment

Yes by source: current main still has a bridge-enabled status path that receives only `appConfig`, counts every active public artifact, and derives the missing-artifacts warning from that unscoped count. I did not run the reporter's live filesystem scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the boundary: filtering by `agentIds` is the likely narrow code fix for agent-visible status, but CLI/gateway doctor may need an explicit operator-global path instead of silently changing all diagnostics.

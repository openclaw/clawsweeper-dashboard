## Label Justifications

- `P2`: The report describes a bounded Slack channel media/context bug with real turn confusion and token waste, but it does not block the whole runtime.
- `impact:message-loss`: Stale Slack attachment references can be delivered to the agent as if the current reply included new media.
- `impact:session-state`: Previously uploaded thread-root media can drift into later Slack thread turns as current session context.

## Summary

Keep open: current main and the latest release still have a source-level path that hydrates Slack thread-starter files and passes them as effective inbound media on later text-only replies, while the prior direct fix PR was closed unmerged and the remaining repair needs a maintainer decision on the documented thread-root media inheritance contract.

## What This Changes

This issue asks OpenClaw to stop re-injecting Slack thread attachments uploaded once by the user as fresh inbound media on later text-only turns in the same thread.

## Best Possible Solution

Keep this as the canonical open issue and define a Slack-plugin-local, session-aware media policy: reply-owned media should be delivered, root-message media should be inherited only under the chosen documented contract, and previously delivered root files should not reappear as fresh uploads on later text-only turns.

## Reproduction Assessment

Yes at source level: current main hydrates `starter.files` into `threadStarterMedia` and then uses it as `effectiveMedia` for a Slack thread reply with no direct media. I did not run a live Slack reproduction in this read-only pass.

## Solution Assessment

No, the old unconditional-skip PR is not the best final fix because it conflicts with documented thread-root media inheritance. The safer solution is a session-aware Slack media policy that preserves the chosen first-turn/root-media behavior while preventing repeated fresh-media injection.

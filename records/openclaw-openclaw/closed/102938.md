## Summary

Keep open: current main and v2026.6.11 still pass the API-key index as the rotation callback `attempt`, but this helper is exported through the plugin SDK and the original key-rotation contract used `attempt` as the key-rotation index, so the fix needs an explicit callback-contract decision before changing semantics.

## What This Changes

The issue asks for `executeWithApiKeyRotation` retry callbacks to receive an operation attempt count instead of the API-key index.

## Best Possible Solution

Clarify the exported rotation callback contract, preferably by adding explicit `apiKeyIndex` and `attemptNumber` fields or a documented deprecation path instead of silently changing what `attempt` means.

## Maintainer Decision

Question: Should `executeWithApiKeyRotation` preserve the historical `attempt` key-rotation index, change it to an operation attempt count, or add explicit fields while leaving `attempt` compatible?

Rationale: The helper is plugin-SDK-visible and the historical implementation used `attempt` as the key-list index, so automation should not silently choose a breaking callback semantic.

Likely owner: steipete

Owner reason: He introduced the rotation helper and carried much of the follow-up retry contract work, making him the best available owner for the callback API decision.

Owner confidence: high

Options:

- **Add Explicit Fields (recommended):** Add `apiKeyIndex` and `attemptNumber` to the callback payload, keep `attempt` compatible or deprecate it, and cover both fields in focused tests.
- **Change `attempt` Semantics:** Make `attempt` mean operation attempt count and accept the compatibility risk for plugin callers that relied on the old rotation-index meaning.
- **Document Current Contract:** Keep the runtime unchanged and document that `attempt` is the key-rotation index while directing same-key retry logic to `transientRetry.shouldRetry`.

## Reproduction Assessment

Yes, source-reproducible: current main passes `apiKeyIndex` into `shouldRetry` and `onRetry` as `attempt` while separately tracking `attemptNumber` for transient retries. I did not run tests in the read-only checkout.

## Solution Assessment

Unclear until the SDK callback contract is decided. Replacing `attempt` with `attemptNumber` is plausible but not clearly the best fix because an additive explicit payload is safer for compatibility.

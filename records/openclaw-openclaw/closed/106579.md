## Label Justifications

- `P1`: A transient Telegram watermark persistence failure can cause already-processed updates to replay after restart and duplicate user-visible actions.
- `impact:data-loss`: The tracker discards an in-memory processed-update watermark when its persistence callback fails.
- `impact:message-loss`: The message-delivery impact taxonomy includes duplicated processing, which can occur when the stale persisted offset replays Telegram updates.

## Summary

This is an exact duplicate of the older open report at https://github.com/openclaw/openclaw/issues/105191 from the same author, covering the same persistence target, failure mode, impact, and requested retry behavior; the older issue should remain canonical.

## What This Changes

Preserve and retry the Telegram processed-update watermark when persistence fails instead of silently discarding it.

## Best Possible Solution

Keep https://github.com/openclaw/openclaw/issues/105191 as the canonical report and fix the tracker there by restoring the failed target with max-watermark merging, bounded retry/backoff, and focused concurrent-update persistence tests.

## Reproduction Assessment

Yes at source level: make the persistence callback reject while drainPersistQueue handles a target and observe that the captured watermark is no longer queued. A live current-main failure run was not established during this read-only review.

## Solution Assessment

Partly: retaining failed work is correct, but merely delaying the clear is insufficient around concurrent higher update IDs; the robust fix should merge the failed target back with any newly queued maximum and retry with bounded backoff.

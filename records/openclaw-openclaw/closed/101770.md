## Summary

Current main already rejects positive sub-millisecond cron durations after flooring, so the reported failure-alert cooldown path now throws before a zero-millisecond patch can be sent.

## What This Changes

The issue reports that `openclaw cron edit --failure-alert-cooldown 0.1ms` can persist a zero-millisecond failure-alert cooldown instead of rejecting the positive fractional duration.

## Best Possible Solution

Keep the shared cron CLI duration parser guard on main as the canonical fix; any broader policy change around explicit zero cooldowns should be a separate issue.

No current-main failing reproduction remains: source inspection shows `0.1ms` now resolves to `null` in the shared cron parser and the edit command throws before sending a failure-alert patch.

Yes. Rejecting floored-zero values in the shared cron CLI duration parser is the narrowest maintainable fix because it protects failure-alert cooldowns and sibling cron duration flags at the common input boundary.

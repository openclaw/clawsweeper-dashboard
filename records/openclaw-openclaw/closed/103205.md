## Summary

Current main still omits an event that the public plugin docs promise, and quiet trigger evaluations can durably advance the next wake without an existing completion notification. The request remains necessary, but the protected `maintainer` label and permanent public plugin API semantics require explicit feature-owner confirmation.

## What This Changes

Add a `scheduled` action to `cron_changed` and emit it after successful durable changes to a job’s effective next wake that are not already represented by add, update, or remove events.

## Best Possible Solution

Implement one owner-aligned durable wake-change invariant that emits an additive `scheduled` event only after successful persistence, suppresses explicit lifecycle duplicates, includes the current job snapshot and optional next wake, and documents coalesced full-list reconciliation rather than ordered delta delivery.

## Label Justifications

- `P2`: This is a normal-priority Docker sandbox robustness fix with limited blast radius.
- `merge-risk: 🚨 availability`: The proposed stdin handler can leave a Docker child running after a stream error, which can stall sandbox execution in a failure path CI does not fully cover.

## Summary

Keep open: the reported Docker stdin stream failure is real, but the PR is not merge-ready because the new stdin handler records the error without terminating the Docker child, so an input-waiting command can still hang; external real behavior proof is also missing.

## What This Changes

This PR adds a stdin error listener to `execDockerRaw`, plus a focused regression test and proof script for Docker sandbox stdin stream errors.

## Best Possible Solution

Use one Docker stream-error path that records the first stream error, terminates the child, rejects on close, and has a regression test plus redacted terminal proof for the stdin case.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes at source level: current `main` writes to `child.stdin` without an error listener, and the PR test demonstrates a stdin `error` event followed by child close. I did not run the failure path locally because this review is read-only.

## Solution Assessment

No: the change is in the right owner boundary, but close-time-only rejection is too narrow. The safer fix is to share the existing terminate-and-reject stream-error path used for stdout and stderr.

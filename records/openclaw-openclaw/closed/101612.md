## Summary

Keep open: the reported surrogate-pair bug is valid on current main, but this patch should not merge as-is because it changes the `maxChars` cap from UTF-16 units to code points instead of using the repository's existing UTF-16-safe truncation helper.

## What This Changes

The PR changes `readResponseTextSnippet` to truncate collapsed HTTP error response snippets by Unicode code points instead of raw UTF-16 code units.

## Best Possible Solution

Use `truncateUtf16Safe` in `readResponseTextSnippet`, preserve the existing `maxChars` cap, add a focused surrogate-boundary test in `src/infra/http-body.response.test.ts`, and include after-fix terminal proof from the actual function path.

Yes from source inspection. Current main uses raw UTF-16 slicing in `readResponseTextSnippet`, so an emoji crossing the `maxChars` boundary can leave a dangling surrogate; I did not execute tests in this read-only review.

## Solution Assessment

No. The narrow maintainable fix is to use the existing `truncateUtf16Safe` helper so the snippet remains surrogate-safe while preserving the current cap semantics.

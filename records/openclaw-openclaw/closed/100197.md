## Label Justifications

- `P1`: Mobile reconnect during an active chat can lose live event state and forces slow full-history recovery in stable mobile/Gateway surfaces.
- `impact:message-loss`: The issue is about chat events emitted while disconnected being unavailable to reconnecting clients.
- `impact:session-state`: The requested fix depends on preserving and reconciling per-session sequence state across WebSocket reconnects.
- `impact:ux-friction`: Users can continue only through heavy full-history refetching and iOS polling rather than a fast in-product reconnect path.
- `maturity:stable`: The affected Gateway runtime, Android app, and iOS app are all listed as M4 Stable in the maturity shortlist.

## Summary

Keep open: the requested sequence-cursor resume is not implemented on current main or the latest release, and the protected `maintainer` label requires explicit maintainer handling rather than cleanup closure.

## What This Changes

Request adding an optional `afterSeq` cursor to `chat.history` plus iOS/Android reconnect logic that resumes from the last applied sequence instead of refetching full history.

## Best Possible Solution

Define an additive `chat.history` delta-resume contract, preserve existing offset behavior, then update iOS and Android to track last applied sequence and fall back to full history for older gateways.

## Reproduction Assessment

Not applicable as a strict bug reproduction; this is an additive protocol/client feature request. Source inspection does confirm current main lacks `afterSeq` and uses full refresh or error handling on reconnect/gap paths.

## Solution Assessment

Unclear until maintainers settle the protocol shape. The proposed additive cursor is plausible and aligned with gateway compatibility guidance, but the final design must define sequence scope and fallback behavior across both mobile clients.

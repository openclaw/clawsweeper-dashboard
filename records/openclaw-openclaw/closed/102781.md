## Summary

The reconnect composer fix remains necessary and its main browser flow is well proven, but the latest head introduces a destructive retry hazard: a successful queued `/clear` can be marked failed when only the post-reset history refresh rejects, allowing a retry to clear newer conversation state.

## What This Changes

The PR enables ordinary Control UI text and attachment sends while reconnecting and reworks the existing sessionStorage composer queue into gateway/session/agent-scoped durable outboxes with hardened replay, command, route, and recovery handling.

## Best Possible Solution

Keep the scoped durable reconnect outbox, but treat a successful destructive command mutation as authoritative; surface any subsequent history refresh failure separately and remove the completed command from the outbox.

## Solution Assessment

No in its current form. Reusing the existing durable outbox is the right architectural boundary, but destructive command completion must not be reversed by a later read-only refresh failure.

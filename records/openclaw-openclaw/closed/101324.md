## Label Justifications

- `P1`: The reported default Telegram channel workflow could stop delivering inbound messages after a gateway restart.
- `impact:message-loss`: Fresh Telegram messages could queue behind replayed spooled updates and appear undelivered to the user.
- `impact:session-state`: The replayed update was described as mapping to an already-completed conversation turn, which can drift channel/session state.

## Summary

Current main and the checked latest release already solve the reported Telegram restart replay/blocking problem well enough: handled updates now advance a safe persisted watermark after dispatch, and current main also keeps spooled completion tombstones so refetched updates do not re-enter the pending lane.

## What This Changes

The issue asks OpenClaw to durably persist or otherwise advance Telegram isolated-ingress update offsets so restarts do not replay handled spooled updates and block later inbound messages.

## Best Possible Solution

Keep the current Telegram behavior: persist safe update watermarks after dispatch and rely on durable spool tombstones/dedupe so refetched handled updates cannot block the ingress lane.

## Solution Assessment

Yes. The current implementation is a better durable boundary than blindly persisting every spool write: it preserves retry semantics until dispatch completion while queue dedupe/tombstones prevent handled updates from blocking later delivery.

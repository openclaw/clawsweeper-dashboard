## Summary

Keep open. Current main and v2026.6.11 mitigate the original direct-Gemini tagged-mode trigger and Google baseUrl footgun, but the shared strict sanitizer fallback still has the source-level leak path described in the later discussion, so the WhatsApp/channel reasoning leak is not fully fixed.

## What This Changes

The issue asks OpenClaw to stop WhatsApp/Gemini `<think>/<final>` reasoning text from leaking through channel delivery after the earlier Telegram-focused fix.

## Best Possible Solution

Keep the direct-Gemini native reasoning mitigation, then make a maintainer-approved shared sanitizer or stream-parser decision for unclosed `<think>` plus `<final>` leakage with WhatsApp and Telegram regression coverage.

Rationale: The current fallback can recover an answer but may expose hidden reasoning; changing it is a security boundary and product-semantics choice rather than a purely mechanical WhatsApp fix.

Options:

- **Fix the shared sanitizer boundary (recommended):** Recover only validated final-answer text when a final marker exists, otherwise suppress malformed unclosed reasoning, and cover WhatsApp plus Telegram paths.
- **Fail closed on malformed reasoning:** Suppress all strict-mode output after an unclosed reasoning opener unless the stream parser has already separated a final answer.
- **Patch channels separately:** Add WhatsApp and sibling channel splitters while leaving the shared fallback unchanged, accepting continued drift risk across delivery surfaces.

## Reproduction Assessment

Yes at source level, but not as a live current-main channel run. Current main still strips `<final>` markers before returning all text after an unclosed `<think>` opener when strict mode would otherwise produce an empty result.

## Solution Assessment

No, a WhatsApp-only splitter is likely too narrow while the shared strict fallback remains. The maintainable fix belongs in the shared sanitizer or stream parser, with WhatsApp and Telegram coverage proving the channel behavior.

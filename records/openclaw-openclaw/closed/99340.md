## Summary

Keep open: current main’s non-stream fallback ignores `maxBytes`, and this PR correctly bounds the returned diagnostic snippet with focused coverage. The broader boundary-safety PR at https://github.com/openclaw/openclaw/pull/97774 overlaps this helper, but it is not a clearly safer reason to close this smaller, focused branch before maintainers choose the landing path.

## What This Changes

The branch updates `src/infra/http-error-body.ts` to byte-truncate non-stream response text before applying `maxChars` and adds focused Vitest coverage for the helper.

## Best Possible Solution

Land one canonical implementation for this helper, either this focused fix or the `readResponseTextSnippet`-based helper from the broader boundary-safety PR, then reconcile the overlapping branch.

## Reproduction Assessment

Yes, source-reproducible: construct a Response-like object with `body: null`, long `text()`, small `maxBytes`, and large `maxChars`; current main applies only `maxChars` in that fallback. The PR body also includes negative-control output showing 5000 bytes returned against a 100-byte limit before the patch.

## Solution Assessment

Yes for the returned diagnostic snippet: the shared helper is the right narrow owner because both MiniMax VLM and native PDF provider errors call it. If maintainers want a true non-stream memory-read cap or UTF-16-safe display truncation, the broader `readResponseTextSnippet` route in https://github.com/openclaw/openclaw/pull/97774 is the cleaner canonical path.

## Summary

Keep open: current main still does not clearly prevent an aborted heartbeat/Codex run from draining deferred raw output into Telegram delivery, and the only related merged recovery work covers the post-send queue symptom rather than the initial flood.

## What This Changes

The issue asks OpenClaw to stop aborted heartbeat runs from delivering raw tool output past the heartbeat reply cap and to avoid Telegram flood/queue recovery fallout.

## Best Possible Solution

Fix the heartbeat/embedded-run boundary so aborted heartbeat runs cannot flush deferred raw tool output to channel delivery, then consider a separate, explicitly scoped flood guard if maintainers want broader platform protection.

## Reproduction Assessment

No, not as a high-confidence live reproduction from this checkout. The report plus current source make the abort/deferred-delivery path source-reproducible, but the exact 91-message Telegram flood still needs the trajectory logs or a targeted regression harness.

## Solution Assessment

Unclear as a complete fix shape. The narrowest first fix appears to be suppressing or summarizing aborted heartbeat terminal payloads at the heartbeat/embedded-run boundary, while a generic flood guard should be a separate maintainer decision.

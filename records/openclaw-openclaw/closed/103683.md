## Summary

Current main has a same-day unreleased lock-cleanup fix that may reduce one stall path, but no source, test, or discussion proves it eliminates this intermittent pre-hook hang, and the progress-silent model-call gap remains observable.

## What This Changes

Prevent embedded agent runs from intermittently stalling after `embedded_run:started`, improve progress visibility during startup and model work, and enable safe recovery without restarting the gateway.

## Best Possible Solution

Add phase-specific diagnostic progress around session-lock acquisition, prompt-hook preparation, prompt submission, and model execution; then reuse existing abort-drain recovery only when a named phase is stale beyond its safe threshold, with regression coverage for both a dead pre-hook run and a quiet live model call.

## Reproduction Assessment

Yes at source level, but not yet as a controlled current-main live reproduction: the report provides a repeated production signature, and current code explains how a run can remain at `embedded_run:started` before hook or model progress with delayed or unavailable recovery. The exact intermittent blocking operation still needs phase instrumentation or a live trace.

## Solution Assessment

No, a bare timeout is not the best standalone fix because it cannot distinguish a dead startup path from a valid progress-silent model call. The narrower maintainable solution is phase-aware progress plus recovery through the existing embedded-run owner and abort-drain coordinator.

- `P0`: The issue describes a concrete owner-authorization bypass for writing live workspace skill content from a non-owner authorized sender.
- `impact:security`: The affected path controls who may approve and apply generated skill content into the shared workspace.

## Summary

Keep open: current main still shows a concrete security-boundary gap where an authorized non-owner can enter the Skill Workshop path and the approval resolver lacks owner identity.

## What This Changes

Require owner-tier authorization for `/learn` Skill Workshop authoring/apply and the `/approve` path, matching the `/plugins` write gate.

## Best Possible Solution

Enforce owner-tier authorization on every live Skill Workshop lifecycle mutation and approval-resolution path, with tests proving non-owner authorized senders cannot create, apply, or self-approve workspace skills while owner and explicitly trusted admin paths still work.

- **Fold into broader approval design:** Handle this under the broader Skill Workshop approval-evidence contract in https://github.com/openclaw/openclaw/issues/93278, accepting that this concrete bypass remains open until that design lands.

Yes, this is source-reproducible on current main: `/learn` uses the authorized-sender gate, `skill_workshop apply` has no sender owner input, and approval authorization does not receive `senderIsOwner`. I did not run a live channel transcript because this review is read-only.

## Solution Assessment

Unclear on exact implementation layer: owner enforcement is the right security direction, but a one-sided `/learn`-only fix would be too narrow. The best fix should cover entry, lifecycle mutation, and approval resolution paths or explicitly document any trusted exception.

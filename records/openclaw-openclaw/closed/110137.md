## Label Justifications

- `P0`: A normal plist-rewriting restart can leave the entire gateway unavailable until the operator performs manual launchctl recovery.
- `impact:crash-loop`: The gateway exits and the launchd service can remain unloaded rather than recovering automatically.
- `impact:ux-release-blocker`: Recovery from an automatic restart outage requires terminal-only launchctl knowledge with no in-product recovery path.

## Summary

This issue is still necessary. Current main waits for the gateway process to exit before the reload handoff touches launchd, so the reported three-second loop does not race the 300-second in-process drain; however, the reload path still gives asynchronous bootout only three seconds to disappear, then converts a failed bootstrap into `kickstart -k`, which cannot restore an already-unloaded label. That leaves the reported stranded-gateway failure mode unresolved.

## What This Changes

Fix macOS LaunchAgent reload handoffs so a plist-rewriting restart cannot leave the gateway deregistered after launchd bootout/bootstrap timing failures.

## Best Possible Solution

Replace the one-shot reload recovery with a bounded bootstrap-retry-and-verify sequence that preserves the new plist, confirms the service is registered with `launchctl print`, and leaves an explicit bootstrap recovery path rather than treating `kickstart -k` as recovery for an unloaded service.

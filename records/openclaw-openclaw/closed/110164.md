## Summary

This PR remains necessary, but the current head still preallocates the full configured payload cap on every credential-file read; with the default cap, that is a 64 MiB allocation before knowing the payload size. The contributor also needs to add current-head, redacted real-command proof after resolving that blocker.

## What This Changes

The PR replaces QA Lab credential payload stat-then-read handling with opened-handle bounded reads and adds regression coverage for boundary-size, growth-race, and FIFO payload paths.

## Best Possible Solution

Read payloads in bounded fixed-size chunks, retaining only the actual bytes up to the cap and probing one additional byte before parsing; then add a redacted current-head QA Lab credential-add transcript for an accepted boundary payload and an oversized rejection.

## Reproduction Assessment

Yes from source: every invocation reaches `Buffer.allocUnsafe(maxBytes + 1)` after opening a regular payload file, so a tiny valid payload still triggers the configured-cap allocation. A live memory-constrained command run was not available in the supplied evidence.

## Solution Assessment

No. The opened-handle and extra-byte boundary concept is appropriate, but preallocating the maximum configured payload size is not the narrowest safe implementation; a chunked bounded reader preserves the race protection without the unconditional 64 MiB default allocation.

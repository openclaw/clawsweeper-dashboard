## Label Justifications

- `P1`: Gateway routing can select a deterministically unusable node command on every connection for affected configurations, breaking a real remote browser workflow.
- `impact:other`: The issue makes remote node capability discovery inaccurate and causes deterministic routing failures outside the more specific owned impact categories.
- `maturity:stable`: The defect affects gateway-runtime Nodes and Remote Capabilities, which the current maturity shortlist scores M4 Stable.

## Summary

Current main still violates the documented node-capability contract: the headless host declares every registered plugin node command before the browser plugin's local disable checks run. The issue should remain open because the directly linked fix PR is still open, and the protected maintainer label requires explicit maintainer handling rather than cleanup.

## What This Changes

Prevent headless nodes from declaring the browser proxy command and capability when local browser or proxy configuration disables them.

## Best Possible Solution

Land a generic plugin-owned startup availability predicate used when building node declarations, have the browser plugin evaluate both existing disable settings there, and retain invocation-time checks as fail-closed defense.

## Reproduction Assessment

Yes, from current-main source with high confidence. Registration and declaration are unconditional, while the existing disable settings are checked only during invocation; a live Gateway transcript was not run in this read-only review.

## Solution Assessment

Yes, the linked direction is the narrowest maintainable fix: core performs generic filtering and the owning plugin decides local availability. Browser-specific filtering in the runner would violate the plugin boundary, while removing invocation checks would weaken defense in depth.

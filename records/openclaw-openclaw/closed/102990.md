## Summary

The reported unbounded cache growth is valid, but this exact head is not merge-ready: at capacity it evicts an unrelated endpoint before refreshing an existing key, and successful refreshes do not update Map order, so the implementation does not provide its claimed least-recently-refreshed behavior. The focused tests and green CI are useful, but the fake-server transcript is not real Synology Chat proof and misses both blocking full-cache cases.

## What This Changes

The PR caps the Synology Chat user-list cache at 100 entries, exports cache internals for testing, and adds regression tests for oldest-entry eviction and same-origin fallback preservation.

## Best Possible Solution

Treat successful writes as the canonical recency order: remove the current key first, evict the oldest remaining key only when adding it would exceed 100 entries, then reinsert the refreshed key as newest; cover both full-capacity refresh cases and provide redacted real Synology Chat proof.

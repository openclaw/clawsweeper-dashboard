## Label Justifications

- `P0`: The issue blocks a first-use macOS setup/onboarding path for users who already have a configured Gateway by sending them back into provider setup instead of the dashboard.
- `impact:ux-release-blocker`: A non-technical macOS user with an existing configured Gateway can be blocked in first-run onboarding with no in-product recovery path to the dashboard.

## Summary

Keep open: current main still has a source-reproducible macOS launch path where a configured Gateway can resolve to local mode while `openclaw.onboardingSeen` is false, and the app then schedules first-run onboarding instead of marking setup complete after a successful Gateway connection. The protected `maintainer` label and live assignment mean this should stay maintainer-owned rather than be auto-closed or queued by cleanup automation.

## What This Changes

The issue asks the macOS app to skip first-run onboarding and open the dashboard when an existing configured Gateway connects successfully despite a missing app-local onboarding marker.

## Best Possible Solution

Gate first-run macOS onboarding on actual configured Gateway readiness: once a configured Gateway connects successfully, mark the app-local onboarding marker complete and open the dashboard; keep onboarding for unconfigured or unreachable Gateways and add focused Swift regression coverage.

## Summary

Keep open: the fix direction is useful for the linked cron bug, but this head is not merge-ready because it drops cron task/active-marker state on caught run failures, can notify setup-timeout recovery for retired outcomes, and lacks current-head real behavior proof.

## What This Changes

The branch moves cron due-job outcome persistence into each worker, preserves running markers for still-unapplied due jobs during maintenance recompute, and adds two timer regression tests.

## Best Possible Solution

Keep the per-result persistence design, but carry taskRunId and activeJobMarker through error outcomes, return a finalized-result signal before setup-timeout recovery, add focused regressions, and include redacted live cron proof for this head.

## Reproduction Assessment

Yes at source level: current main buffers ordinary due-job outcomes until all workers finish, so a later stuck same-batch job can delay an earlier completion from clearing persisted running state. I did not run a live gateway reproduction in this read-only review.

## Solution Assessment

No as submitted: immediate per-result persistence is the right layer, but this implementation drops task/marker state in caught failures and loses the current finalized-result gate for setup-timeout recovery. The safer fix is to preserve those current-main safeguards while applying each completed result promptly.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.86

Full review comments:

- **[P2] Preserve task state in caught cron outcomes:** `src/cron/service/timer.ts:1297-1298`
  - body: This catch also handles `executeJobCoreWithTimeout` rejections after `taskRunId` and `activeJobMarker` have already been created. Returning both as `undefined` means `applyOutcomeToStoredJob` cannot finish the detached task row because `tryFinishCronTaskRun` returns when `taskRunId` is missing, so thrown cron runs can leave task ledger entries running instead of terminal. Keep the assigned values outside the try or carry them into the catch result.
  - confidence: 0.88
- **[P2] Gate setup-timeout recovery on finalized outcomes:** `src/cron/service/timer.ts:1408`
  - body: `applyCompletedResult` returns without telling the caller when the active marker is retired, but this branch still sets `setupTimeoutNotified` and calls `maybeNotifyIsolatedAgentSetupTimeout`. Current main skips that recovery path when `finalizeCompletedResults` returns no finalized result, so after a restart/generation advance this can fire recovery for a stale run and release reservations unnecessarily.
  - confidence: 0.82

## Label Justifications

- `P2`: This is a valid Docker sandbox cancellation bug with meaningful side-effect risk, but sandboxing is optional and the report is source-reproducible rather than a confirmed live outage.
- `impact:security`: The issue concerns sandbox process isolation and a cancelled untrusted command continuing to run after OpenClaw reports it stopped.
- `impact:data-loss`: A surviving container-side command can keep writing the workspace bind mount after cancellation, which can corrupt or overwrite user-visible files.
- `impact:session-state`: The report describes an orphaned container-side command that may still be running when the same sandbox is reused for a later session command.
- `maturity:stable`: The affected sandboxed exec lifecycle falls under the Gateway runtime remote-execution/security surface reported as M4 Stable.

## Summary

Keep open: current main and the latest release still launch Docker sandbox commands through plain `docker exec` while abort/timeout handling only kills the local supervised Docker client, so the container-side orphan risk remains source-reproducible.

## What This Changes

The issue requests that cancelling or timing out a Docker-sandbox exec stop the command running inside the container, not only the local `docker exec` client.

## Best Possible Solution

Add a Docker backend-owned exec lifecycle that can terminate the container-side process or process group on abort/timeout, prove it with live Docker before/after cancellation evidence, and treat SSH as a separate follow-up unless it is reproduced.

## Summary

Keep this PR open, but do not merge it as-is: the patch validates before distinguishing static operator-owned keys from templated external keys, and invalid templated values fall through to default/generated session routing instead of failing closed.

## What This Changes

The branch changes `src/gateway/hooks-mapping.ts` to render mapping `sessionKey` values through a new regex allowlist and drop values outside `[a-z0-9:._-]`.

## Best Possible Solution

Move session-key shape hardening to the hook session policy boundary after source classification, reject invalid external templated/request values with no dispatch, preserve static operator-owned keys, and cover both mapping-unit and server-hook behavior.

Full review comments:

- **[P1] Preserve static mapping session keys:** `src/gateway/hooks-mapping.ts:275`
  - body: This validates every mapped `sessionKey` before `getSessionKeyTemplateSource` can distinguish static operator config from templated external input. Static mapping keys are currently trusted by docs and tests, and valid existing keys can contain characters outside this allowlist, such as WhatsApp `+` numbers or Signal opaque IDs with `/` and `=`. Please apply the new validation only to externally supplied request/templated keys, or use a policy helper after source classification.
  - confidence: 0.89
- **[P1] Reject invalid rendered keys instead of falling back:** `src/gateway/hooks-mapping.ts:498`
  - body: Returning `undefined` here does not stop the webhook: `resolveHookSessionKey` treats an absent key as a request for `defaultSessionKey` or a generated `hook:<uuid>`. That means a payload with an invalid templated key still dispatches, just under an unintended session. For a security validation, return a mapping/session-key error so the request fails closed and add a server-level regression test that no agent run is queued.
  - confidence: 0.86

## Summary

Keep open: current main and the latest release still have the literal English `LISTENING` check in the CLI Windows force-free path, while the related diagnostics path has a separate parser, so the reported divergence remains actionable.

## What This Changes

The issue asks OpenClaw to stop missing Windows port listeners when localized `netstat -ano` output does not use the literal English `LISTENING` state.

## Best Possible Solution

Use one shared Windows TCP listener parsing rule for CLI force-free and diagnostics that parses the endpoint correctly and does not depend on a literal English listener state, with regression fixtures for localized state text and existing English rows.

## Reproduction Assessment

Yes, at source level: mock `process.platform` as `win32` and return a target-port netstat row whose listener state is localized instead of `LISTENING`; current `listPortListeners` will skip it before PID parsing. I did not run a live localized Windows host in this read-only review.

## Solution Assessment

Yes, the maintainable fix is a narrow shared parser or shared parser rule across the CLI and diagnostics Windows netstat paths. A simple switch from exact `LISTENING` to `includes("listen")` would reduce divergence but may still miss genuinely localized listener state text.

- `impact:auth-provider`: The issue concerns provider failure classification and the reason attached to model fallback routing.
- `impact:ux-friction`: Operators receive a false timeout diagnosis and may spend time changing connection or timeout settings that cannot address the upstream error.

## Summary

Keep open: current main still maps the exact provider-completed error `Provider finish_reason: error` into the timeout bucket and rewrites it as a literal LLM timeout. Merged history shows that broad bucket was introduced to preserve model fallback, so the diagnostic defect is real but the repair must keep candidate-failure and fallback behavior intact.

## What This Changes

Correct fast provider `finish_reason: error` responses being reported as LLM timeouts with timeout/408 diagnostics while preserving model fallback.

## Best Possible Solution

Separate retry eligibility from diagnostic classification: retain fallback for `finish_reason: error`, classify it as a provider/server error rather than a timeout, preserve the raw provider preview, and keep genuine abort/network timeout variants in their existing transient lanes.

## Label Justifications

- `P2`: The Gateway silently continues running stale plugin code, but a full process restart provides a reliable recovery path.
- `impact:ux-friction`: The documented restart command and success-looking registration log can falsely signal that updated workspace plugin code is active.
- `maturity:stable`: The issue affects Gateway Lifecycle within the M4 Stable gateway-runtime feature.

## Summary

Current main and the latest release both reproduce the reported architecture: no-respawn restart rebuilds the Gateway inside the same Node process, while workspace plugin imports reuse Jiti’s default module cache. The documented restart command therefore does not reliably activate changed workspace plugin code, and no linked fix or canonical duplicate exists.

## What This Changes

Make an in-process Gateway restart load updated workspace plugin code, or clearly distinguish cached-module re-registration from a disk reload.

## Best Possible Solution

Add a lifecycle-owned executable plugin cache reset before the next in-process Gateway iteration, rebuild activated plugin runtime from disk, prove that changed workspace source registers new behavior, and make logs and docs accurately describe the reload result.

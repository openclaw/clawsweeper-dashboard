- `impact:data-loss`: The parser and cloned strippers can silently reinterpret or drop user-authored Markdown command/hook/skill body content when it begins with a non-delimiter dash prefix.

## Summary

Keep open: current main and the latest release still use prefix-based frontmatter fence checks, so the reported Markdown edge case remains a real parser bug with a narrow core repair path.

## What This Changes

The issue requests that Markdown frontmatter parsing accept only a whole `---` delimiter line, not arbitrary leading `---` prefixes such as `---not`.

## Best Possible Solution

Require an exact frontmatter delimiter line after BOM/newline normalization and apply the same helper to parser and body-stripping callers, with regression cases for `---not`, `----`, and valid `---` blocks.

## Repair Work Prompt

Fix the Markdown frontmatter delimiter bug reported at https://github.com/openclaw/openclaw/issues/101769. In `packages/markdown-core/src/frontmatter.ts`, require opening and closing fences to be exact delimiter lines after BOM and newline normalization, so inputs such as `---not\nname: nope\n---not\nbody` and `----\nname: nope\n----\nbody` are treated as normal Markdown with no metadata. Audit cloned body-stripping/extraction helpers such as `src/plugins/bundle-commands.ts`, `src/skills/workshop/frontmatter.ts`, and `src/agents/utils/frontmatter.ts` so they use the same delimiter rule or a shared helper where appropriate. Add focused regression coverage for invalid prefixes and keep valid `---` blocks, BOM-prefixed valid frontmatter, CRLF normalization, and existing metadata parsing behavior working. Do not add config, compatibility flags, or CHANGELOG.md edits.

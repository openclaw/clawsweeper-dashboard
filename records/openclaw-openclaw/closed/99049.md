## Summary

Keep open: the reported WhatsApp Web socket-level send overlap is still present on current main, and an open linked candidate fix already owns the implementation path, so the issue should wait for that PR to land or be closed.

## What This Changes

The issue requests per-active-Baileys-socket serialization for concurrent WhatsApp Web outbound `sendMessage` calls.

## Best Possible Solution

Review and land the linked WhatsApp PR if its queue implementation and focused tests hold up, then close this issue from the merge.

## Reproduction Assessment

Yes, source-level: current main calls the same Baileys socket's `sendMessage` directly from both the Web send facade and timeout-adapter path, so two concurrent sends can reach the raw socket before the first settles. I did not run tests because this review is read-only.

## Solution Assessment

Yes, a per-socket FIFO at the Web send facade and shared timeout-adapter boundary appears to be the narrowest maintainable fix. The open linked PR should be reviewed rather than queuing another duplicate repair.

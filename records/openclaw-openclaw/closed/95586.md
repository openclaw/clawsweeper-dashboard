## Summary

## What This Changes

Reported bug: Kimi API keys configured through `openclaw.json` env can appear available in `models status` while a systemd-managed Gateway turn treats Kimi as auth-failed and falls back.

## Best Possible Solution

Define one managed-service provider-credential contract, then align service env rendering, Gateway runtime auth, `models status`, docs, and Linux systemd regression proof around it.

Rationale: The code already applies config env during snapshot reads, but service env generation, runtime process env, status reporting, and docs still leave users with conflicting signals about whether config env is a durable daemon credential.

Options:

- **Support both with explicit runtime status (recommended):** Keep config env usable for Gateway runtime where intended, but make status and diagnostics distinguish daemon-reachable credentials from CLI/config-only sources and add targeted systemd proof.

- **Prefer auth profiles for daemons:** Treat config env as setup/config convenience only, update docs/status to steer daemon users to per-agent auth profiles or state `.env`, and warn when status would otherwise mislead.

## Label Justifications

- `P1`: The issue describes a current Google provider request-shape bug that can turn Gemini 2.x image tool results into rejected 400 responses for provider-prefixed model ids.
- `impact:auth-provider`: The failure depends on provider-prefixed model ids and the Google provider capability/model-routing check.

## Summary

Keep open: current main and the latest release still use a Gemini-major-version check anchored to bare `gemini-*`, so provider-prefixed Gemini 2.x ids still bypass the image-turn fallback and no open PR owns the remaining fix.

## What This Changes

Provider-prefixed Gemini 2.x model ids should use the Gemini <3 image tool-result fallback instead of embedding image parts inside `functionResponse`.

## Best Possible Solution

Update the Google capability parser to tolerate `google/` and `models/` prefixes in both active Google conversion paths, then add focused provider-prefixed Gemini 2.x image tool-result regression coverage.

Yes as a high-confidence source-level path: `google/gemini-2.5-pro` misses the anchored Gemini regex, so an image tool result is put in `functionResponse.parts` and the separate image turn is skipped. I did not execute the full request-builder harness in this read-only review.

## Solution Assessment

Yes: a narrow prefix-tolerant Gemini major-version check, kept aligned across the plugin and core converters with regression tests, is the most maintainable fix; no new product surface is needed.

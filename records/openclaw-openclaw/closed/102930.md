## Summary

Keep open. Current main and the latest release both leave sender-scoped Crestodian rescue pending files intact when a new non-persistent rescue command runs, so a later approval can still apply the older persistent operation; the fix is narrow and source-reproducible.

## What This Changes

The issue asks for Crestodian message rescue to invalidate stale sender-scoped pending approvals when a non-persistent command runs before a later approval.

## Best Possible Solution

Bind `/crestodian yes` only to the currently presented rescue plan by clearing same-scope pending approval state on any new non-approval rescue command and replacing it only when a fresh persistent plan is emitted.

Yes, source-reproducible with high confidence: queue a persistent rescue command, run a non-persistent command such as status, then send `/crestodian yes`; current source still reads and executes the old pending file. I did not run the live message-channel flow in this read-only review.

## Solution Assessment

Yes, the narrow fix is to clear the same-sender pending file during general non-approval rescue command routing before executing read-only commands or writing a fresh persistent plan. Clearing only status/health would leave other new commands able to preserve stale approval state.

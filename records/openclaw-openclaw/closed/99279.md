## Label Justifications

- `P2`: This is a real Mattermost channel safety gap for multi-bot deployments, but it is limited to configured Mattermost bot-to-bot/open-policy workflows and needs design review rather than emergency handling.
- `impact:security`: The issue concerns a missing channel safety control for bot-authored inputs that can trigger automated agent replies without the shared bot-loop guard.
- `impact:message-loss`: Ungarded bot-to-bot loops can duplicate or flood channel messages once bot-authored Mattermost posts are admitted by existing sender policy.
- `impact:session-state`: Bot-authored Mattermost traffic admitted as ordinary senders can pollute or drift agent conversation state during looped multi-agent exchanges.

## Summary

Keep open. Current main still lacks Mattermost inbound bot-identity facts or a Mattermost bot-admission surface, so bot-authored posts that pass the existing sender policies can reach dispatch without the shared bot-pair loop guard.

## What This Changes

Mattermost should identify inbound bot-authored or webhook posts and apply bot-loop protection or an explicit bot-admission policy for multi-bot deployments.

## Best Possible Solution

Add Mattermost-owned bot identity resolution for inbound posts, wire admitted bot-authored turns into the shared pair-loop guard, and document/test the chosen default plus webhook handling.

## Reproduction Assessment

Yes at source level: current Mattermost code drops self/system posts but otherwise admits allowed senders without bot identity facts, and its strict config schema has no allowBots or Mattermost botLoopProtection surface. I did not run a live two-bot Mattermost deployment.

## Solution Assessment

Unclear as a final product shape: wiring reliable bot facts into the existing shared pair-loop guard is the right owner boundary, but maintainers still need to choose Mattermost defaults, allowBots semantics, and webhook handling.

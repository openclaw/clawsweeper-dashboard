## Label Justifications

- `P1`: The patch targets a startup hang in a core SQLite path, but the proposed boundary can still hang and can preserve unsafe WAL selection on affected network storage.
- `merge-risk: 🚨 compatibility`: A 10-second cutoff changes slow-but-successful mount detection into an error path that can alter journal-mode selection for existing deployments.
- `merge-risk: 🚨 session-state`: Misclassifying an unresponsive network-backed state database as local can retain WAL and endanger persisted OpenClaw state.

## Summary

The latest head still leaves both prior blockers unresolved: `execFileSync` does not provide a hard 10-second return boundary, and its timeout exception is still converted into “no network mount found,” allowing WAL on a filesystem the safety check could not classify. The PR also still has only test output rather than affected-environment proof.

## What This Changes

The PR adds a 10-second `SIGKILL` timeout to the synchronous `mount` fallback used during SQLite WAL filesystem detection.

## Best Possible Solution

Move mount discovery behind a boundary whose parent can return independently, represent timeout or indeterminate detection explicitly, select rollback journaling for that unsafe result, and prove the production opener returns boundedly on a real blocked-mount scenario.

## Label Justifications

- `P1`: Swift clients can be rejected before pairing on deployed v2-only gateways, leaving downstream apps stuck in Approval Pending or device-signature-invalid.
- `merge-risk: 🚨 compatibility`: Merging changes Swift connect signing behavior to preserve compatibility with older deployed gateways while relying on newer gateways' v2 fallback acceptance.
- `merge-risk: 🚨 security-boundary`: The temporary v2 payload no longer binds platform and deviceFamily into the Swift connect signature, even though the core device-auth fields remain signed.

## Summary

Keep open: this is a focused, proof-backed compatibility fix, and current main plus v2026.6.11 still sign Swift connect requests with the v3 payload while older deployed gateways may verify only v2. The remaining path is maintainer landing with the already-accepted temporary compatibility window, not conservative cleanup closure.

## What This Changes

The PR adds a Swift connect-only v2 compatibility payload, switches shared OpenClawKit and macOS wizard connect signing to it, and adds a Swift payload vector test.

## Best Possible Solution

Land the narrow connect-only compatibility helper after exact-head gates, then restore Swift connect signing to buildV3 or negotiated signature versions once supported gateways verify v3 before v2.

## Reproduction Assessment

Yes. Current main's Swift signers use buildV3, current gateway source verifies v3 then v2, and the PR body provides before/after live logs on an older v2-only gateway showing the failure and recovery.

## Solution Assessment

Yes. Given the maintainer-accepted transition window, this is the narrowest maintainable mitigation because it limits v2 signing to Swift connect requests instead of weakening server verification or adding a broad auth fallback.

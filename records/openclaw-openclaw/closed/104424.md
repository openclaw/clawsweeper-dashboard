## Label Justifications

- `P0`: A first-time macOS user relying on an existing provider subscription lacks an in-product sign-in path and must discover provider-specific terminal steps before the first useful run.
- `impact:auth-provider`: The request directly changes how provider OAuth and device-code credentials are initiated, validated, and persisted.

- `maturity:stable`: The affected CLI onboarding/auth setup and macOS Gateway host features are both listed as M4 Stable in the maturity shortlist.

## Summary

Current main does not provide provider-owned interactive sign-in in macOS onboarding: Crestodian exposes detected sessions and app-guided secrets, while the native UI only accepts API keys or tokens. The request aligns with current first-run priorities, but it adds public authentication and protocol capability on a protected maintainer-owned surface, so it should remain open for explicit design sponsorship rather than enter an autonomous fix lane.

## What This Changes

Add provider-owned OAuth and device-code sign-in to the macOS first-run “Connect your AI” flow.

## Best Possible Solution

Define one additive, typed Crestodian interactive-auth session backed by provider-owned login methods, let macOS render only portable prompts and actions, preserve the existing manual-key response for older clients, and persist auth/config only after a successful starter-model probe.

## Summary

Keep open: both v2026.6.11 and current main still materialize the full enabled MCP catalog whenever bundle MCP is reachable, no related item owns request-scoped subset activation, and maintainers should confirm the single generic run-policy owner before implementation.

## What This Changes

Add request-scoped MCP activation so embedded runs can select all, none, or a named subset of configured MCP servers before cataloging.

## Best Possible Solution

Extend the generic run tool-construction policy with a closed MCP activation mode, narrow the persistently enabled server set before transport setup or `tools/list`, and keep catalog lifecycle logic in the existing session runtime.

Yes, at high confidence from source and shipped-tag inspection: whenever bundle MCP is constructed, the runtime catalogs the full enabled server set before applying the request's concrete tool filter. A live 10-server environment was not rerun during this read-only review.

## Solution Assessment

No, the proposed optional array should not be accepted as the final API without owner clarification; the narrowest maintainable solution is to extend the existing generic run-policy boundary and pass a prepared activation decision into the MCP runtime.

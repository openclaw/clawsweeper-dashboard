## Summary

Keep open: current main still preserves raw rich HTML tables under the wide-table threshold and keeps rich-to-plain fallback logic split across Telegram send surfaces; the protected `maintainer` label also rules out conservative cleanup close.

## What This Changes

The issue requests a Telegram rich-message fix that normalizes raw HTML tables and consolidates rich-to-plain fallback across durable send, final reply, and draft-stream delivery.

## Best Possible Solution

Implement one Telegram-plugin normalizer/fallback boundary used by `send.ts`, `bot/delivery.send.ts`, and `draft-stream.ts`: normalize all raw rich HTML tables to the canonical grid or `<pre>` fallback, share one rich-to-plain downgrade helper with stable warning reasons, and cover it with targeted tests plus Telegram proof.

## Reproduction Assessment

Yes at source level: current main allows raw rich HTML tables through sanitization unless they exceed the wide-table limit, while generated Markdown tables use a different canonical renderer. I did not run live Telegram proof in this read-only review.

## Solution Assessment

Yes, the requested shared normalizer and fallback helper is the maintainable owner-boundary fix because the scoped Telegram guide requires send-funnel parity. The implementation should stay in the Telegram plugin and avoid adding config or a second compatibility path.

## Summary

This PR addresses a real restart-recovery race at the correct scheduler boundary, but it still permits a duplicate resume when the first RPC succeeds, clearing the persisted restart marker fails, and the queued follow-up starts with fresh de-duplication state. It also lacks after-fix proof from a real gateway restart setup.

## What This Changes

The PR replaces independent delayed recovery chains with a module-level single-flight scheduler that queues one follow-up scan, and adds an overlap regression test.

## Best Possible Solution

Maintain one accepted-session de-duplication set across the complete active-and-queued recovery lifecycle, including successful resumes whose marker write fails, and demonstrate through a real restart scenario that overlapping triggers emit one resume.

## Solution Assessment

No, not yet. Scheduler-level serialization is the right ownership boundary, but resetting accepted-session state before the queued follow-up leaves a documented persistence-failure path that violates the intended at-most-once behavior.

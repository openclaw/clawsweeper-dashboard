## Summary

Keep open: current main still allows Discord outbound media up to OpenClaw's 100 MB default and sends non-video caption text and the file in one Discord request, so an oversized MP3 can reject the whole reply; the queued reply path can also log dispatch completion before async delivery failures are counted.

## What This Changes

The issue requests preventing Discord replies with oversized media from silently losing both text and attachment and from reporting completed delivery after a 413.

## Best Possible Solution

Add a Discord outbound size preflight and 413 fallback at the channel boundary, deliver surviving text or a visible limit notice, and make delivery diagnostics reflect a completely undelivered reply without adding a new config option or bundling transcoding/chunking into the first fix.

## Reproduction Assessment

Yes at source level: send a non-video Discord media reply with text and a file larger than Discord's default 10 MiB upload limit. I did not run a live Discord send in this read-only review, but the issue logs, current send path, and Discord API contract line up.

## Solution Assessment

Yes for the bounded repair path: fix Discord-owned preflight/fallback and delivery accounting first. Automatic transcoding, chunking, or configurable upload policies would be broader product work and should not block the loss-prevention bug fix.

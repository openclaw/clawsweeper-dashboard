## Summary

Current main already prevents this false conflict: reply-session initialization now tracks only session identity, so `skillsSnapshot` representation or key-order changes cannot invalidate the commit. The fix is newer than v2026.6.11 and remains current-main-only relative to the provided latest release.

## What This Changes

Prevent semantically identical `skillsSnapshot` objects with different JSON property order from causing deterministic reply-session initialization conflicts on follow-up messages.

## Best Possible Solution

Keep the current identity-only revision guard and focused concurrency tests, then include the fix in the next stable release rather than adding a general recursive stable-stringify dependency to the session metadata comparison.

No, recursive stable stringify is broader than necessary. Current main uses the narrower concurrency contract: only `sessionId` and `sessionFile` changes indicate a competing session rotation, while concurrent metadata is merged safely.

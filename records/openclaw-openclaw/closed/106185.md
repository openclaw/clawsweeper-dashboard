## Label Justifications

- `P0`: An Android user in the affected staggered-upgrade path cannot connect or use the app and has no in-app recovery path until the Gateway is upgraded.
- `impact:ux-release-blocker`: The handshake rejects an otherwise compatible older Gateway, fully blocking the Android user and requiring an external Gateway upgrade to recover.

## Summary

Keep this issue open: current main still exposes a v4-only minimum, while the directly linked fix remains open and the protected `maintainer` label requires explicit maintainer handling. ([github.com](https://github.com/openclaw/openclaw/blob/main/packages/gateway-protocol/src/version.ts))

## What This Changes

Allow Android to negotiate Gateway protocol versions 3 through 4 while Swift and generic clients remain version-4-only.

## Best Possible Solution

Land the linked PR after confirming Android alone advertises 3-4, preserving 4-4 for other clients, retaining v3 message-only and v4 incremental replay coverage, and showing an actionable in-app upgrade message only for genuinely unsupported Gateways.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes at source level: connect the current Android build, which advertises a 4-4 range, to a protocol-v3 Gateway; the Gateway rejects the handshake because its version is outside that range. A live failing run was not performed in this read-only review.

## Solution Assessment

Yes. Generating an Android-specific 3-4 range from the existing compatibility constant is narrower and less drift-prone than lowering the global minimum or hand-editing generated Kotlin.

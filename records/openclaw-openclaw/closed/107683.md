## Summary

Keep open for an explicit security-boundary decision. Current durable allow-always entries preserve executable and optional argument patterns but no script-content binding, while SHA-256 revalidation protects only the prepared approval-to-dispatch window. Merged work intentionally made these interpreter grants reusable, so closing or automatically repairing this would silently choose a new persisted authorization contract. citeturn16view0turn12view0turn6view0

## What This Changes

Require reusable allow-always grants for interpreter scripts to be invalidated or re-approved when the script file content changes.

## Best Possible Solution

For strict-inline-eval interpreter file operands, persist canonical operand identity plus a SHA-256 binding, revalidate it on every durable reuse, and invalidate legacy unbound grants through the owned approval migration path; cover unchanged reuse, post-approval edits, replacement or symlink changes, and sibling exec hosts.

## Maintainer Decision

Kind: security_boundary

Question: Should an allow-always grant for a concrete interpreter script delegate continuing trust to its path and arguments, or only to the exact file content approved by the operator?

Rationale: Either choice changes the durable authorization contract: content pinning invalidates existing grants and increases prompts, while path trust deliberately permits later script edits to execute without re-approval.

Likely owner: luoyanglang

Owner reason: Their merged changes most directly established reusable strict-inline-eval interpreter approval semantics and the associated regression coverage.

Owner confidence: high

Options:

- **Pin approved content (recommended):** Persist and revalidate the script digest for durable grants, invalidating legacy entries that lack a binding.
- **Disable durable script grants:** Keep one-shot approvals but remove allow-always eligibility for mutable interpreter file operands under strict-inline-eval mode.
- **Keep path-scoped trust:** Retain current reuse semantics and explicitly document or warn that trusting a script path also trusts its future contents.

## Reproduction Assessment

Yes at source level. Approving a script creates durable executable-and-argument trust, whereas the mutable-file SHA-256 exists only in the one-shot approval plan, so a later identical command can match after the file changes.

## Solution Assessment

Unclear pending the security-boundary decision. Content-bound durable grants are the narrowest least-privilege fix, but the implementation must deliberately handle existing persisted grants and all sibling exec hosts.

## Label Justifications

- `P2`: The issue describes a normal-priority memory-core Dream Diary bug with significant but bounded impact to generated narrative output rather than a core runtime outage.
- `impact:data-loss`: Successful narrative text can be generated and then not persisted to DREAMS.md, leaving only fallback diary entries.
- `impact:session-state`: The failure depends on detached narrative session waiting, transcript/readback timing, and deletion of accepted attempt sessions.

## Summary

Keep open: current main and v2026.6.11 still have the fixed 60-second Dream Diary wait, the plugin manifest still rejects the reported timeout fields, and timeout/no-text cleanup still deletes accepted narrative attempt sessions after writing a fallback stub.

## What This Changes

The issue asks memory-core Dream Diary generation to stop counting lane-queue wait against a hardcoded 60-second timeout, expose the parsed timeout configuration, and preserve or intentionally handle late successful model output instead of writing fallback diary entries.

## Best Possible Solution

Define one memory-core Dream Diary lifecycle contract that wires the timeout surface intentionally, separates queued and executing waits or otherwise budgets them explicitly, and preserves or deliberately cancels late successful output without misleading fallback telemetry.

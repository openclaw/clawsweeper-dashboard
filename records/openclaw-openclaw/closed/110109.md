## Summary

Current main improves scheduler handling of lifecycle-claim conflicts, but the direct `/hooks/agent` fire-and-forget path still has no event-preserving ownership for same-session collisions. The report remains actionable; per-session serialization is safer than blind retries that could replay completed side effects. citeturn13view0turn14view0turn17view3

Likely related people: `steipete` (high confidence, recent lifecycle-claim retry owner), `SL4N` (medium confidence, introduced bounded pre-work retry classification), and `eleqtrizit` (medium confidence, recent direct hook-dispatch contributor).

## What This Changes

Prevent concurrent hook agent events targeting the same resolved session key from losing collided events during cron session lifecycle claiming.

## Best Possible Solution

Add a lifecycle-owned per-session dispatch queue around hook agent runs, preserving FIFO order only for identical resolved session keys while allowing different sessions to run concurrently; retain phase-aware bounded retry solely as a fallback for proven pre-execution conflicts, with collision, ordering, parallelism, cleanup, and failure-continuation coverage.

## Reproduction Assessment

Yes—a high-confidence path is to set `cron.maxConcurrentRuns` above one and send three near-simultaneous `/hooks/agent` requests with the same resolved `sessionKey`; the direct dispatch and claim paths explain the observed losers, though this read-only review did not execute the live reproduction.

## Solution Assessment

No, generic text-pattern retry alone is not the best solution because lifecycle conflicts can also occur after side effects. Per-session FIFO serialization at the hook-dispatch boundary is the narrower durable fix, with phase-aware retry only for residual pre-work conflicts.

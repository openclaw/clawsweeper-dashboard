## Summary

Keep open: current main and the latest release still spawn Windows `taskkill.exe` in `runCommandWithTimeout` without handling async spawn errors, so the reported cleanup gap remains a narrow core process reliability bug.

## What This Changes

The issue requests fixing Windows process-tree cleanup so asynchronous `taskkill.exe` spawn failures fall back to killing the child process instead of being missed.

## Best Possible Solution

Handle taskkill child `error` events in the Windows `runCommandWithTimeout` cleanup path, preserve trusted System32 lookup, and add focused Windows regression coverage for the async failure fallback.

## Repair Work Prompt

Fix the Windows `runCommandWithTimeout` process-tree cleanup bug reported in https://github.com/openclaw/openclaw/issues/101381. In `src/process/exec.ts`, make the graceful and forced `taskkill.exe` child processes handle async `error` events and fall back to `child.kill("SIGKILL")` when taskkill cannot be spawned; preserve `getWindowsSystem32ExePath("taskkill.exe")`, the existing timeout/abort result semantics, and non-Windows process-tree behavior. Add focused coverage in `src/process/exec.windows.test.ts` that simulates a taskkill child emitting `error` after spawn and proves the original child receives the fallback kill or the command settles correctly. Do not add config, change command wrapper resolution, edit `CHANGELOG.md`, or reintroduce PATH-based taskkill lookup; put any user-visible release-note context in the PR body.

## Label Justifications

- `P1`: A deterministic accepted cron configuration can leave real operators without the failure alerts they configured until a later runtime delivery error exposes the problem.
- `impact:message-loss`: The stored invalid channel type causes the configured cron failure-alert message not to reach its destination.

## Summary

This is a valid, shipped cron configuration bug that remains present on current main. The issue should stay open because its explicitly linked fix PR is still open and no merged replacement owns the exact failure-alert field.

## What This Changes

Reject unknown explicit cron failure-alert channel types during cron create or update instead of storing them until delivery fails.

## Best Possible Solution

The Gateway should validate every explicitly selected announce-mode failure-alert channel on both create and merged update state, while webhook alerts and unset channels continue using their existing semantics.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes at source level. The CLI writes `failureAlert.channel`, current Gateway create/update validation omits that field, the service persists it independently, and alert resolution later consumes the invalid value.

## Solution Assessment

Yes. Extending the existing Gateway-owned channel validator is the narrowest maintainable solution because it protects CLI and RPC clients without creating a competing CLI-only policy.

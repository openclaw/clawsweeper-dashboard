## Summary

Keep open: current main and the latest release still route successful `stopReason=stop` lifecycle ends through `console.error`, while the terminal outcome helper already treats `status=ok` plus `stopReason=stop` as completed. No duplicate or implemented-on-main evidence was found.

## What This Changes

The issue requests that successful agent run completions with `stopReason=stop` stop being emitted at error severity and asks whether duplicate raw/announce run-id completion logs should be deduplicated.

## Best Possible Solution

Use the canonical terminal outcome classification to log completed/benign run endings at info or not at all, reserve error severity for failed/timeout/aborted outcomes, and add focused regression coverage without broad subagent-liveness changes.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes from source inspection, but not from a live current-main run: a successful attempt with `meta.stopReason === "stop"` reaches `emitLifecycleEnd`, which calls `console.error` for every non-`end_turn` stop reason.

## Solution Assessment

No, the current implementation is not the best behavior because it classifies by raw stop-reason string instead of the normalized terminal outcome. The narrow maintainable fix is to align logging severity with completed/failed terminal status and separately verify any true duplicate announce logging.

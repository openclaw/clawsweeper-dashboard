## Summary

Keep open: the PR still has a blocking accounting-boundary bug because the new non-backlog diagnostic event is also used for the reply-run fallback path, which current code treats as a queued reply-run outcome rather than accepted active embedded-run steering. The contributor followed up with a new approach, but the provided evidence is still focused test output rather than real embedded-agent steering diagnostic proof.

## What This Changes

The PR adds `logEmbeddedAgentSteerEvent`, switches embedded-agent queue logging to that helper, and adds diagnostic queue-depth regression tests.

## Best Possible Solution

Use an active-run-only accounting boundary: exclude only messages accepted by an active embedded-run handle from backlog, keep reply-run fallback and normal queued messages on `logMessageQueued`, add focused coverage for that split, and require redacted real behavior proof before merge.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: current main can increment queueDepth multiple times for accepted active-run steering while active-run completion emits only one idle decrement. I did not run a live embedded-agent setup in this read-only review.

## Solution Assessment

No. The dedicated helper is a plausible direction, but this implementation applies it to the reply-run fallback too; the best fix is to keep the non-backlog event limited to accepted active embedded-run handle delivery.

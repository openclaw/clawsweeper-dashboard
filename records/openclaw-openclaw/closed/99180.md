## Summary

Keep open: current main still casts MCP loopback `tools/call.params.arguments` without validating object shape, while this PR is a focused boundary fix aligned with the pinned MCP SDK contract and backed by real loopback proof. The remaining maintainer decision is the intentional compatibility tightening for malformed clients.

## What This Changes

The PR rejects present non-object Gateway MCP loopback `tools/call.params.arguments` with JSON-RPC `-32602` and adds regression coverage for invalid, omitted, and object arguments.

## Best Possible Solution

Land this boundary validation after maintainer acceptance of the malformed-client compatibility tightening, while keeping omitted and object-shaped arguments unchanged and avoiding broader per-tool schema work in this PR.

## Reproduction Assessment

Yes. Current main source shows non-object `arguments` are cast through the loopback handler, and the PR body provides raw loopback proof for a malformed `tools/call` request.

## Solution Assessment

Yes. The raw HTTP loopback path is the path bypassing SDK request validation, and checking it before hooks/execution is narrower than changing stdio handling or per-tool schemas.

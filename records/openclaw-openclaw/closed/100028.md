## Summary

Keep open: the patch addresses a real negative-read failure path in `MicCaptureManager`, but it is not yet the best complete fix because the realtime `TalkModeManager` capture loop still uses the same `AudioRecord` wrapper and still treats every non-positive read as transient. The PR also needs real after-fix device proof for the Bluetooth/USB hot-unplug path before merge.

## What This Changes

The PR changes Android `MicCaptureManager` to treat negative `AudioRecord.read` results as fatal transcription failures and adds a helper that names known `AudioRecord.ERROR_*` codes.

## Best Possible Solution

Handle negative `AudioRecord.read` results consistently for both Android voice capture loops, preferably through a shared capture-result/error helper or matching fatal handling in both managers, then add focused regression coverage and redacted real-device hot-unplug proof.

## Reproduction Assessment

Yes, with medium confidence from source and dependency contracts: both Android capture loops can receive negative `AudioRecord.read` error codes, and current main treats them as transient. I did not run the physical Bluetooth/USB hot-unplug scenario.

## Solution Assessment

No, this is a plausible partial fix rather than the best complete fix. The same `AndroidAudioInputSession.read` negative-error invariant exists in realtime talk mode, so the maintainable solution should cover both sibling callers or centralize the error conversion.

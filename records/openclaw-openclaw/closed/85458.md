## Summary

Keep this open: current main and v2026.6.11 still have the direct missing-thread recovery retry after replacement Codex thread creation, and the related fix PRs are closed unmerged rather than safe canonical fixes.

## What This Changes

The issue reports a possible Codex app-server bound-thread leak when missing-thread recovery starts a replacement thread and the retry rejects before cleanup.

## Best Possible Solution

Define the intended bound-thread subscription lifecycle, then implement retry-rejection cleanup that preserves consecutive bound-turn delivery with focused regression coverage.

## Maintainer Decision

Question: Should Codex app-server bound conversation threads keep a persistent app-server subscription between inbound turns, or should OpenClaw reattach and unsubscribe per turn?

Rationale: Current behavior appears to rely on persistent subscriptions for later bound-turn notifications, while the reported leak would be fixed by cleanup only if reattach or binding-clear semantics are also settled.

Likely owner: steipete

Owner confidence: medium

Options:

- **Preserve persistent subscription by default (recommended):** Keep current multi-turn delivery semantics and add only targeted cleanup where the binding is cleared or the next turn is guaranteed to reattach.
- **Move to per-turn reattach and cleanup:** Change bound turns to explicitly attach before each turn/start and unsubscribe afterward, with consecutive-turn and missing-thread recovery tests.
- **Document current retention as intentional:** If the replacement thread should remain subscribed after retry failure for future turns, close the issue after adding a focused test or maintainer note that locks that contract.

Yes, at source level: current main can enter missing-thread recovery, create a replacement Codex thread, and retry without cleanup around that replacement-thread retry. No live hosted Codex orphan-count reproduction was provided or run.

## Solution Assessment

Unclear: the cleanup primitive exists, but the closed per-turn unsubscribe fix was too broad because it could break later bound-turn delivery. The best fix depends on the maintainer lifecycle decision above.

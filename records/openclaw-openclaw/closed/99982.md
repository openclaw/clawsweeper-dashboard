## Label Justifications

- `P2`: This is a normal, bounded auto-reply suppression bug affecting deployments that choose custom silent tokens.
- `impact:ux-friction`: Affected users can see transient silent-control fragments leak into channels instead of being suppressed.

## Summary

Keep open: current main and the latest release still reject streamed silent-token prefixes containing digits or punctuation, even though exact custom-token suppression accepts those tokens.

## What This Changes

Fix silent-reply prefix suppression so custom silent tokens containing digits or punctuation suppress streamed prefixes consistently with exact-token suppression.

## Best Possible Solution

Make prefix detection derive allowable prefixes from the configured token while preserving the existing uppercase and natural-language false-positive guards, then add digit and punctuation custom-token regression cases.

## Reproduction Assessment

Yes, from source inspection: calling `isSilentReplyPrefixText` with a digit or hyphen prefix for a matching custom token will hit the hard-coded `/[^A-Z_]/` guard and return false, while `isSilentReplyText` accepts exact custom tokens. I did not run a full channel repro in this read-only review.

## Solution Assessment

Yes, the best fix is a narrow helper-level repair plus regression tests; adding a config option or channel-specific workaround would create a second source of truth.

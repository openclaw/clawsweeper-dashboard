## Label Justifications

- `P1`: The original issue describes silent loss of inbound Telegram messages during ordinary gateway restart paths.
- `impact:message-loss`: The affected behavior was permanently dropped Telegram webhook payloads after OpenClaw had already acknowledged delivery.

## Summary

Close as implemented on main: current Telegram webhook mode persists authenticated updates before the 200 ACK, replays durable spool rows, and keeps the old failure behavior out of the latest main code; the fix has not shipped in v2026.6.11 yet.

## What This Changes

The issue requests durable persistence and replay for inbound Telegram webhook payloads so gateway restarts after receipt do not permanently drop already-acknowledged messages.

## Best Possible Solution

Keep the current shared SQLite ingress-spool implementation on main, close this narrow Telegram webhook tracker, and leave broader cross-channel catch-up or replay-dedupe work to its separate open items.

## Reproduction Assessment

Yes. The old v2026.6.11 source path ACKed 200 before bot.handleUpdate, while current main no longer has that failing path because durable spooling precedes the ACK.

## Solution Assessment

Yes. The main implementation is the maintainable fix shape because it reuses the shared ingress spool, returns non-200 on spool failure, and replays pending rows on startup instead of adding an ad hoc sidecar queue.

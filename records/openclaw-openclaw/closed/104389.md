## Label Justifications

- `P2`: The assistant remains operational and recovers, but deterministic notifications expose internal execution details to end users.
- `impact:security`: The reported user-facing card reveals internal agent identifiers, command lines, and filesystem paths across a trust boundary.
- `impact:ux-friction`: Non-technical users receive confusing implementation-level failure cards even when the assistant subsequently completes their request.

## Summary

Keep open: current main intentionally relays failed background-exec details through heartbeat processing, while Feishu cards expose fallback agent identity and model/provider metadata; resolving the leak requires an explicit privacy and notification-policy decision.

## What This Changes

Prevent auto-backgrounded exec failures from rendering raw internal agent identifiers, command lines, filesystem paths, and model/provider details directly to Feishu end users.

## Best Possible Solution

Define a core async-exec policy that keeps completion events available to the agent but permits only explicitly authored, privacy-filtered user summaries, then make Feishu use configured public identity or neutral card chrome instead of raw dynamic-agent identifiers.

## Reproduction Assessment

Yes, at source level. Current main creates a relayable failed-exec heartbeat event, explicitly asks the model to explain it to the user, and Feishu renders raw fallback agent identity plus model/provider metadata; a live Feishu run was not performed in this read-only review.

## Solution Assessment

Unclear pending the default notification and privacy contract. A Feishu-only text scrub is not the best solution because the underlying relay policy is channel-neutral, while a blanket suppression could hide useful failure notices.

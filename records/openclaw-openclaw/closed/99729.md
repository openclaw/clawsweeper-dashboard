## Summary

Keep open: current main and the latest release still hard-invalidate CLI session reuse on prompt-content hash drift, and the issue has the protected `maintainer` label plus an explicit stale-prompt/session-lifetime tradeoff that needs maintainer product direction.

## What This Changes

The issue requests a structural CLI session reuse contract that treats mechanical changes as hard invalidation but resumes through prompt-content drift with a per-turn drift note.

## Best Possible Solution

Keep this as a maintainer-owned design item: choose the session-lifetime contract, then implement one closed reuse result shape across CLI reuse, prepare-time history handling, binding persistence, and regression coverage.

## Reproduction Assessment

Yes at source level: current main still hard-invalidates when `extraSystemPromptHash`, `messageToolPolicyHash`, or `promptToolNamesHash` changes, and tests assert those content mismatches return `system-prompt`. I did not run a live Telegram or CLI-backend reproduction in this read-only review.

## Solution Assessment

Unclear as a product decision: the two-class split is a plausible structural fix, but maintainers must approve resuming through stale prompt-content drift and decide whether delivery-mode drift remains mechanical.

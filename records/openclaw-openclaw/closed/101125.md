## Summary

Current main and the v2026.6.11 release already treat explicit cron `toolsAllow` values as an exclusive cap rather than unioning default tools back in, so the reported `apply_patch` reinjection from v2026.6.10 is fixed.

## What This Changes

The issue reports that explicit cron `toolsAllow` lists that omit `apply_patch` are read back with `apply_patch` silently re-added.

## Best Possible Solution

Keep the released exclusive-capping behavior and direct any remaining opposite-direction cron tool materialization questions to the already open canonical tool-surface work.

## Label Justifications

- `P2`: This is a confirmed durability bug with meaningful but limited blast radius, triggered when automatic deletion coincides with a cron-store persistence failure.
- `impact:other`: The issue causes durable cron lifecycle divergence for external observers, a concrete maintainer-visible impact outside the narrower owned categories.

## Summary

Current `main` still publishes automatic cron `removed` events before the deletion is durably saved, so this fresh, concrete issue remains necessary. It is a narrow core correctness bug and carries the protected `maintainer` label for explicit handling.

## What This Changes

Ensure automatic cron `removed` lifecycle events publish only after durable deletion and always include the deleted job snapshot.

## Best Possible Solution

Buffer each deleted job snapshot during finalization, commit the canonical cron store, then publish exactly one snapshot-bearing `removed` event after success; add failed-save regressions for manual, invalid-spec, and scheduled completion paths.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes. Complete a successful `deleteAfterRun` one-shot and force the final store save to reject; current source deterministically publishes `removed` before that rejected save in both manual and scheduled paths.

## Solution Assessment

Yes. Deferring publication to the existing successful persistence boundary, while carrying the deleted snapshot, is the narrowest maintainable fix and matches the sibling CRUD and `scheduled` event patterns.

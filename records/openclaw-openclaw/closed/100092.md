## Label Justifications

- `P1`: The issue describes multiple real channel workflows where inbound attachments can silently lose usable media before the agent or sender gets a reliable outcome.
- `impact:data-loss`: Failed materialization can leave uploaded attachment bytes unavailable to OpenClaw even though the transport message was accepted.
- `impact:message-loss`: Media-only turns can be dropped or delivered to the agent as placeholder text without the corresponding media payload.
- `impact:ux-friction`: Senders may receive no actionable retry warning when their attachment failed to reach the agent.

## Summary

Keep open: the protected `maintainer` label prevents conservative cleanup closing, and current main still has representative channel paths where failed media materialization can leave placeholder text, empty media payloads, or a media-only turn without a durable user-visible outcome.

## What This Changes

The issue requests a shared inbound-media failure invariant across bundled channel plugins so failed attachment downloads do not look like successfully materialized media.

## Best Possible Solution

Define one channel-owned inbound media failure contract, then update the affected bundled plugins and focused regression tests so failed materialization never reaches the agent as successfully available media.

## Reproduction Assessment

Yes, at source level: representative channel handlers can be driven by failed download/staging calls and still build placeholder or empty-media outcomes. I did not run live WhatsApp, LINE, Signal, iMessage, Teams, Feishu, Mattermost, or Zalo transport replays in this read-only review.

## Solution Assessment

Unclear as one automatic patch: the invariant is right, but maintainers should first choose the shared warning/unavailable-marker contract and then implement it channel by channel. Telegram's current-main warning behavior is the strongest reference path.

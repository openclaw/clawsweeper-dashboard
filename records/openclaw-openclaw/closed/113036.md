## Label Justifications

- `P1`: The regression prevents affected local llama.cpp provider users from receiving any agent reply, but is limited to a provider-compatibility path.
- `impact:auth-provider`: The failure occurs while OpenClaw prepares the request schema for a configured model provider, before the provider can execute the model call.

## Summary

This report is a duplicate of the more complete, still-open llama.cpp schema-compatibility investigation. The canonical report documents the same 2026.7.1 regression, the same Qwen 3.6 27B llama.cpp setup, and the same parser error, and it is paired with an open focused fix PR.

## What This Changes

The issue requests restoring llama.cpp/OpenAI-compatible provider operation when tool schemas contain regular expressions that its grammar parser rejects after upgrading to OpenClaw 2026.7.1.

## System Context

Before an agent replies, OpenClaw builds JSON Schemas for enabled tools and sends them in the provider request. Some local llama.cpp servers convert those schemas to a grammar and reject unsupported regular-expression or schema constraints before inference begins.

## Architecture Diagram

  B --> C[Provider schema normalization]
  C --> D[OpenAI-compatible request]
  D --> E[llama.cpp grammar parser]
  E --> F[Model response or 400 error]

## Best Possible Solution

Keep one canonical diagnosis in https://github.com/openclaw/openclaw/issues/108580, validate its provider-side schema normalization against the reported llama.cpp setup, and land the focused fix only after it preserves supported provider behavior.

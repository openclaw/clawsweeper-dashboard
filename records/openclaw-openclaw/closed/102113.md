## Label Justifications

- `P1`: A real channel workflow can complete with no outbound user-visible error when an agent turn becomes non-deliverable.
- `impact:message-loss`: The reported failure is that channel plugins receive no outbound notification for a terminal turn, leaving the user with no delivered message.
- `impact:ux-friction`: Users and plugin authors are pushed toward plugin-specific workarounds or support because the core fallback is only visible when chat history is read.
- `maturity:stable`: The affected gateway/runtime channel delivery path maps to the `gateway-runtime` feature, currently listed as M4 Stable in the maturity shortlist.

## Summary

Keeping this issue open: current main and the latest release still project the non-deliverable fallback only for chat display, while the embedded run result and plugin channel outbound contract do not expose a terminal-failure notification for SDK channel plugins. The Octo-side tracker is useful related context, but the broader missing OpenClaw plugin/channel seam remains unresolved.

## What This Changes

The issue requests a generic way for channel plugins to receive or send a user-visible fallback when an agent turn ends as `non_deliverable_terminal_turn`.

## Best Possible Solution

Pick one generic delivery contract for non-deliverable terminal turns, implement it at the core/channel boundary or as a documented plugin SDK hook, and cover the behavior with gateway/channel tests while Octo continues its plugin-specific envelope repair in its own repository.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw surface `non_deliverable_terminal_turn` to channel plugins by automatically pushing a core fallback through normal outbound delivery, by adding a public plugin SDK terminal-failure hook, or by leaving this responsibility to individual channel plugins?

Rationale: Both viable fixes change user-visible delivery semantics and at least one option changes the plugin SDK contract, so automation should not choose the permanent owner boundary without maintainer intent.

Likely owner: Vincent Koc

Owner reason: Recent history ties this area to silent-turn fail-closed behavior and plugin SDK outbound reply routing.

Owner confidence: high

Options:

- **Core automatic fallback (recommended):** Core synthesizes and delivers the fallback text through the existing outbound path so current and future channel plugins get a visible failure by default.
- **Plugin SDK terminal hook:** OpenClaw adds a documented terminal-failure callback that gives plugins control but requires each channel plugin to implement the new API.
- **Plugin-owned workaround only:** OpenClaw leaves the core contract unchanged and expects Octo and other plugins to inspect run state or repair their own delivery loops.

## Reproduction Assessment

Yes at source level: current main records `non_deliverable_terminal_turn` and projects fallback text for display, but the run return shape and channel plugin outbound contract have no terminal-failure notification path. I did not run a live Octo session.

## Solution Assessment

Unclear until maintainers choose the owner boundary: core-side automatic fallback is the broadest user protection, while an SDK hook gives plugins control at the cost of a new public contract.

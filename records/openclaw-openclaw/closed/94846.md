## Summary

Keep open: current main and v2026.6.11 still retain the conservative fatal path for run-level/tool-error recovery, and a maintainer explicitly kept this issue open after closing the speculative PRs that inferred recovery from display text or final prose.

## What This Changes

The issue reports that scheduled isolated cron agent turns can recover from an early tool error and produce final output, but cron finalization can still treat the earlier tool error as fatal and skip delivery before dispatch.

## Best Possible Solution

Keep this issue open for a maintainer-approved cron/exec design that records typed subprocess failure-phase evidence, distinguishes preflight rejection from a process that ran and exited nonzero, and separates recovered degraded outcomes from true fatal and delivery failures.

## Reproduction Assessment

Yes. The issue has repeated sanitized field evidence, and current source/tests still show the conservative run-level-error and recovered-tool-warning gates that leave the remaining July 2 subprocess case unresolved without typed exec phase evidence.

## Solution Assessment

No, not as a simple final-text recovery rule or cleanup close. The best fix is the maintainer-described typed exec failure-phase/process-started signal consumed by cron, with a degraded/warning outcome if the process actually ran.

## Label Justifications

- `impact:ux-friction`: The misleading text can make a roughly 38-second progress failure appear to represent 48 hours of elapsed execution, wasting operator investigation time.

## Summary

Keep open: current main still routes a progress-triggered lane timeout through generic error formatting that presents the overall task budget as elapsed time, while the adjacent diagnostic records a much shorter actual duration.

## What This Changes

Make command-lane timeout diagnostics distinguish elapsed or idle duration, configured task budget, and the timeout arm that fired.

## Best Possible Solution

Keep timeout policy unchanged, but carry a typed timeout cause and report the measured elapsed or idle duration alongside the applicable budget, with focused coverage for both absolute and progress timeout arms.

## Reproduction Assessment

Yes at source level: enqueue a task with a large task budget and a short progress timeout, withhold progress, and observe that the resulting error reports the large task budget while the diagnostic duration remains short. This deterministic path was not executed during the read-only review.

## Solution Assessment

Yes, with a narrower implementation than merely interpolating another number: the error should identify the timeout cause and its measured duration while preserving the configured task budget as separate context.

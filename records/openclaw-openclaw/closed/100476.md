## Summary

This issue should stay open: current main still binds the macOS Dashboard WebView to a single resolved endpoint and origin-pinned native auth script, while endpoint-store updates are not observed by the Dashboard path. The issue also has the protected `maintainer` label, so cleanup automation should not close or auto-implement it.

## What This Changes

The issue asks for the macOS Dashboard window in remote SSH mode to refresh or update its WebView endpoint when the forwarded gateway tunnel is recreated on a new local port.

## Best Possible Solution

Keep the issue open and fix the macOS Dashboard owner path so an open window observes `GatewayEndpointStore` endpoint changes, refreshes origin-pinned native auth safely, and reloads or updates the page without requiring the user to reopen the window.

Options:

- **Reload on endpoint change (recommended):** Subscribe in the macOS Dashboard path, reinject auth for the new origin, and reload the WebView when the endpoint changes; this is narrower and easier to prove.
- **Bridge live endpoint updates:** Add a native-to-web update path so the running Control UI reconnects without a reload, which is smoother but creates a broader bridge contract.
- **Defer to tunnel stability work:** Wait for the orphaned-tunnel and web reconnect fixes first, accepting that an open remote Dashboard can stay stuck after a tunnel port change.

## Solution Assessment

Unclear until maintainers choose the UX shape: a reload after reinjecting native auth is the narrowest likely fix, while a live endpoint bridge may be better UX but broader product surface.

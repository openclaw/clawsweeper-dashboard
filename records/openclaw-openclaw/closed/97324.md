## Summary

Keep open: current main and v2026.6.11 still route the reported stopReason=stop, tools>0, payloads=0, replaySafe=no shape into the incomplete-turn user-error path, and the July 8 field comment adds provider-agnostic shipped evidence that empty retry, model fallback, and cron retry do not engage.

## What This Changes

The issue requests safer handling for replay-unsafe incomplete embedded-agent turns with tool calls but no payloads so malformed turns cannot poison replay, prompt construction, or later session state.

## Best Possible Solution

Define one embedded-runner policy for this malformed turn shape: retry or fail over only when current-attempt metadata proves no side effects can repeat, and otherwise persist a structured quarantine/repair outcome that replay and prompt construction exclude.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For a stopReason=stop turn with tool calls but zero payloads, should the embedded runner retry or fail over when the current attempt has no side effects, or always quarantine the turn as replay-unsafe?

Rationale: Both paths are plausible and compatibility-sensitive: retry/failover improves recovery for provider flakes, while quarantine is safer when the runtime cannot prove that tool-call side effects are absent.

Likely owner: steipete

Owner reason: steipete has the clearest maintainer-side review history on the adjacent incomplete-turn recovery and replay-safety policy decisions.

Owner confidence: high

Options:

- **Retry clean current attempts (recommended):** Use current-attempt side-effect metadata to consume empty retry/fallback budgets only when the malformed turn cannot repeat actions, and quarantine unsafe attempts.
- **Always quarantine tool-call empty turns:** Persist a structured terminal quarantine for every tools>0/payloads=0 stop turn and require explicit recovery instead of automatic retry.
- **Limit fix to cron fallback:** Rely on cron fallback work for scheduled jobs and leave interactive embedded turns on the existing incomplete-turn error path.

## Reproduction Assessment

Yes from source plus field logs, but not from a live current-main reproduction run in this review. Current main skips non-visible retry on replay-unsafe metadata and only retries silent assistant errors with stopReason=error, while the report shows stopReason=stop with tools and zero payloads.

## Solution Assessment

Unclear until maintainers choose the recovery policy. The best-shaped fix appears to be current-attempt-clean retry/failover plus quarantine for unsafe attempts, rather than an unconditional retry or the current generic incomplete-turn surfacing.

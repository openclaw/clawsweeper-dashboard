## Summary

Keep open: the PR targets a real unbounded-buffering bug, but it should not merge as-is because the shared text reader adds a whole-file 16 MiB cap to successful batch outputs and can reject valid large embedding batch results.

## What This Changes

The PR changes OpenAI embedding batch file-content downloads from `res.text()` to the shared bounded provider text response reader and adds a loopback HTTP regression test for oversized output content.

## Best Possible Solution

Stream OpenAI batch output JSONL row by row with a per-record or batch-aware limit so hostile responses are canceled without imposing a 16 MiB whole-file cap on valid results.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path for the reported memory bug: current main calls `res.text()` for successful batch file content, and the PR's loopback test exercises an oversized streamed output. The missing proof is the opposite path: a valid large output over 16 MiB still succeeding after the fix.

## Solution Assessment

No, this is not the best fix as written. The maintainable fix is to stream JSONL and bound individual records or a documented batch budget, rather than reusing a generic small text-response cap for whole batch output files.

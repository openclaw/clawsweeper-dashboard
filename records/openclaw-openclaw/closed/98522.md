## Summary

Keep this issue open. Current main still has a source-supported path where isolated cron embedded agent work can be aborted by stuck-session recovery after the diagnostic no-progress window, while the configured cron timeout is handled on a separate path and related cron timeout/recovery issues are still open.

## What This Changes

The issue reports that isolated cron `agentTurn` jobs with `timeoutSeconds: 600` are aborted around six minutes by stuck-session recovery instead of using the configured run budget.

## Best Possible Solution

Land one canonical cron timeout/recovery fix that lets explicit cron run/provider budgets and real model/tool progress govern long isolated runs while preserving stuck-session recovery for genuinely silent or wedged runs.

## Reproduction Assessment

Yes at source level, but not with a live Docker/DeepSeek run in this read-only review. Current main still has a path where stale embedded-run progress can trigger `abort_embedded_run` after the diagnostic abort window even when cron has a longer configured timeout.

## Solution Assessment

Unclear for implementation shape. The requested behavior is the right end state, but the fix should be coordinated with existing cron timeout and recovery policy rather than only raising or disabling the stuck-session abort threshold.

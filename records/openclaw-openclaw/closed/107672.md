## Summary

Keep this PR open: the prior availability concern is only partially addressed because the new fast path still fully allocates UTF-8 output for byte-oversized multibyte strings, and the supplied standalone script output does not exercise the actual Gateway or Control UI projection path.

## What This Changes

The PR changes shared avatar data-URL validation to enforce the limit using UTF-8 byte length, adds an initial UTF-16 length rejection, and adds multibyte boundary tests.

## Best Possible Solution

Use a browser-and-Node-compatible bounded UTF-8 counter that stops as soon as the byte limit is exceeded without materializing the full encoded array, cover a near-limit multibyte rejection case, and demonstrate one redacted persisted-avatar projection through the actual Gateway or Control UI path.

No. UTF-8 byte accounting is the correct boundary, but fully encoding the candidate string is not the safest implementation when a bounded early-exit counter can enforce the same contract without the temporary allocation.

## Label Justifications

- `P1`: Long-lived direct and channel sessions can repeatedly fail before producing an assistant reply on current shipped versions.
- `impact:message-loss`: Healthy channel ingress can end with no deliverable assistant response because replay is rejected before model output.
- `impact:session-state`: Persisted encrypted reasoning can poison a session so every later replay deterministically fails until the session is reset or repaired.
- `impact:auth-provider`: The failure depends on provider Responses replay contracts and has reproduced through GitHub Copilot, LiteLLM, and Bedrock Mantle routes.

## Summary

Keep open: current main has Copilot-specific replay sanitation seams, but fresh reports on the latest v2026.7.1 release show the same persisted encrypted-reasoning failure across GitHub Copilot, LiteLLM, and Bedrock Mantle Responses routes. Multiple open PRs remain candidate or partial fixes rather than merged proof that long-lived sessions recover reliably.

## What This Changes

Prevent persisted or replayed Responses encrypted-reasoning state from bricking later turns in long-lived direct and channel sessions.

## Best Possible Solution

Adopt one canonical two-layer policy: provider-owned cold-history sanitation where ciphertext lifetime is provider-specific, plus one bounded pre-output Responses recovery that removes only rejected reasoning ciphertext while preserving message, tool-call, tool-output, ordering, and compaction invariants; add cross-provider regression and live channel proof, and use an explicit doctor repair only if maintainers approve rewriting existing transcripts.

Rationale: The bug is established, but choosing between provider-specific cold sanitation, generic reactive recovery, and persisted transcript repair determines reasoning continuity, compaction safety, and ownership of durable-state migration.

Owner confidence: high

Options:

- **Combine prevention and bounded recovery (recommended):** Use provider-owned cold-history sanitation plus one generic pre-output retry for recognized encrypted-reasoning failures, leaving durable transcript rewriting to a separately approved doctor repair.
- **Limit the fix to provider adapters:** Land only provider-specific sanitation and require each Responses-compatible provider to define its own ciphertext replay lifetime and recovery behavior.
- **Repair persisted transcripts:** Strip or migrate encrypted reasoning in stored sessions, accepting the larger state-migration and reasoning-continuity implications.

## Reproduction Assessment

Yes at source level: replay an aged or corrupted Responses transcript containing stale encrypted reasoning through a long-lived direct session and the provider returns a deterministic 400 before output. The thread includes fresh v2026.7.1 runtime evidence, though this review did not execute the private credentialed scenario itself.

## Solution Assessment

No single open PR is yet proven to be the complete best fix across all reported providers. The narrowest maintainable direction combines owner-specific cold sanitation with one structurally conservative generic recovery path, rather than blanket persistence stripping or several competing sanitizers.

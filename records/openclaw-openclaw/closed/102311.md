## Summary

Close as implemented on current main: the reporter was right that stable v2026.6.11 lacks the fix, but current main contains the shared media-loader filename normalization and the fix is present in the v2026.7.1 beta train.

## What This Changes

The issue asks OpenClaw to ensure Telegram outbound file attachments in stable releases no longer expose media-store `---<uuid>` suffixes in recipient-visible filenames.

## Best Possible Solution

Keep the shared media-loader normalization on main and ensure the next stable train is cut from a commit containing `cf512f639b31c792ef53b936891ed3ec3bbfc9ce` or its equivalent.

## Maintainer Decision

## Reproduction Assessment

Yes. The v2026.6.11 tag still derives the outbound filename from the raw staged basename, while current main uses `resolveLocalMediaFileName` and regression coverage proves the UUID suffix is stripped for media-store paths.

## Solution Assessment

Yes. Fixing the shared media-loader filename boundary is the narrowest maintainable solution because Telegram and sibling outbound channels consume the same `media.fileName`; the current scoped implementation avoids changing arbitrary non-media-store local filenames.

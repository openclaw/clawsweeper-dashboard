## Summary

Current main already covers the reported listener leak: `src/entry.respawn.ts` delegates respawn signal handling to the shared bridge, and that bridge stores listener references and removes them on child exit/error.

## What This Changes

The issue asks for respawn SIGTERM/SIGINT handlers to stop accumulating listeners by removing old process listeners before new respawn hooks are attached.

## Best Possible Solution

Keep the shared child-process bridge as the single respawn signal-listener owner, with any future respawn lifecycle fixes extending that bridge or runner rather than adding new ad hoc process listeners.

## Solution Assessment

Yes: the existing shared bridge is the maintainable fix because it centralizes signal forwarding and listener detach for respawned children instead of requiring each respawn caller to remember paired `process.off` calls.

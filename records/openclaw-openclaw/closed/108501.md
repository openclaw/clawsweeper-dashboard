- `impact:data-loss`: The durable queue accepts user-visible reply data that later becomes unrecoverable because its referenced media is deleted.

## Summary

Keep this issue open: the current outbound path still durably enqueues normalized payloads without taking ownership of producer-temporary media, and the specifically linked fix remains an open, unmerged pull request. citeturn959327view0

## What This Changes

Ensure queued TTS voice replies remain deliverable when retry recovery runs after the producer-owned temporary audio file has been deleted.

## Best Possible Solution

Land a reviewed queue-owned media spool that stages only media authorized for the live send, keeps replayable artifacts until the queue reaches a terminal state, preserves accompanying text, and safely reclaims orphaned artifacts after process failure.

## Reproduction Assessment

Yes at source level: enqueue a TTS payload while delivery is unavailable, allow its five-minute temporary-media cleanup to run, then drain the pending queue from a fresh process. This review did not execute the scenario, but the current paths and linked before/after proof make it high confidence.

## Solution Assessment

Yes in principle: making the durable queue own replayable local media is the narrowest solution that fulfills its delivery promise; merely refusing recovery would avoid futile retries but would still discard the requested voice reply.

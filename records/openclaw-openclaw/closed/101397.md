## Summary

Keep open. The PR targets a valid Windows backup reliability bug, but it has no real Windows behavior proof and the cleanup-only retry still reuses the same temp archive path if the short rm retry window is exhausted.

## What This Changes

The branch wraps the backup tar retry cleanup `fs.rm` call in a three-attempt `EBUSY` retry loop with a 100ms delay.

## Best Possible Solution

Keep this as the candidate only if it is tightened to avoid reusing a locked partial archive, backed by focused regression coverage, and accompanied by redacted Windows backup proof.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes for a source-level path, but not a live Windows repro: current main reuses one temp archive path, catches cleanup failure, and then retries tar against the same path. The exact Windows `EBUSY` timing still needs real behavior proof.

## Solution Assessment

No. A short cleanup retry is a plausible mitigation, but the safer fix is to avoid reusing a locked partial archive or retry cleanup immediately before reuse, with regression coverage and Windows proof.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.86

Full review comments:

- **[P2] Avoid reusing the locked archive after cleanup gives up:** `src/infra/backup-create.ts:208`
  - body: The retry loop still falls through to the next `runTar` with the same `params.tempArchivePath` whenever the lock survives these three 100ms cleanup attempts. The outer 10s/20s sleep happens after cleanup gives up, so the helper never removes the old archive immediately before reusing it; a longer-lived Windows lock can still collapse the tar retry chain. Use an independent temp archive path per tar attempt, or retry cleanup at the point where the next write is about to reuse the path.
  - confidence: 0.78

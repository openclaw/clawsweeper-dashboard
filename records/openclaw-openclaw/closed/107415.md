## Summary

Current main partially addresses the reported incident by deferring recovery when a diagnostics heartbeat is over 90 seconds late, but the fixed cutoff does not scale with the configurable abort threshold; an explicitly configured threshold below 90 seconds can still abort healthy work using observer-inflated progress ages.

## What This Changes

Gate stuck-session classification and embedded-run aborts on gateway liveness so event-loop starvation cannot turn delayed progress telemetry into false recovery actions.

## Best Possible Solution

Make recovery telemetry validity relative to the effective abort threshold—preferably by deferring recovery when heartbeat drift can account for the apparent stale age—then require one healthy observation interval before aborting, without adding another config surface.

## Maintainer Decision

## Reproduction Assessment

Yes at source level: configure stuckSessionAbortMs below 90 seconds, delay a heartbeat longer than that threshold but less than 90 seconds, and the current fixed liveness guard can still permit recovery using inflated session and progress ages. The exact memory-pressure incident was not re-run in this read-only review.

## Solution Assessment

No, the fixed 90-second main implementation is only a partial solution because telemetry validity should scale with the configured recovery threshold. A threshold-relative gate plus a healthy recheck is narrower and more reliable than adding more tuning knobs or subtracting a process-wide p99 estimate unconditionally.

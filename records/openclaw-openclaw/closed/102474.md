## Summary

Keep open: the PR targets a valid Slack metadata bug, but the current patch also removes the `ReplyToId` current-message anchor used by Slack message-tool auto-threading for `first` and `batched` modes, and the submitted proof is unit-test only.

## What This Changes

This PR gates Slack `replyToId` calculation on `isThreadReply` with a `replyToMode: "all"` fallback and updates resolver test expectations.

## Best Possible Solution

Separate prompt-facing Slack reply metadata from internal Slack current-thread state so non-replies omit `reply_to_id` while `replyToMode=first|batched|all` tool sends keep their existing thread anchor.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, source-level: current main computes Slack `replyToId` as `incomingThreadTs ?? messageTs`, and the PR regression path is traceable because downstream Slack tool context derives `currentThreadTs` from `ReplyToId` when no other thread id exists.

## Solution Assessment

No. The resolver is the right owner boundary for the prompt metadata bug, but this patch removes an internal delivery anchor; the safer fix separates prompt-facing `reply_to_id` cleanup from Slack auto-threading state.

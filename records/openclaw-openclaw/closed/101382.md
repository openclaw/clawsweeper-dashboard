## Summary

Keep open. Current main and latest release still reuse one temp archive path across backup tar retries; if Windows keeps that partial archive locked, cleanup only logs and the next attempt writes to the same path instead of isolating the retry.

## What This Changes

Fix `openclaw backup create` so a locked temporary tar archive on Windows does not undermine the retry path after a live-write tar failure.

## Best Possible Solution

Keep the fix in `src/infra/backup-create.ts`: make retry attempts independent of a locked partial temp archive, and add a focused regression test for cleanup `EBUSY`/`EPERM` before considering broader Windows archiver or backup-scope changes.

## Repair Work Prompt

Fix the Windows locked-temp-archive retry bug reported in https://github.com/openclaw/openclaw/issues/101382. In `src/infra/backup-create.ts`, make `writeTarArchiveWithRetry`/`createBackupArchive` avoid reusing a temp archive path that could remain locked after a retryable tar EOF-class failure, or otherwise prove cleanup waits/retries safely before the next tar write. Keep the change narrow to backup archive retry behavior; do not add config/env options, switch to a different archiver, change backup scope, or alter stale-artifact startup sweep policy. Add focused regression coverage in `src/infra/backup-create.test.ts` for cleanup `EBUSY` or `EPERM` between retry attempts and for preserving the existing EOF retry/backoff behavior. If the implementation creates per-attempt temp paths, make final cleanup best-effort for all attempted temp archives and keep publish/no-overwrite behavior unchanged.

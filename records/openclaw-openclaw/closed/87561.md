## Summary

Keep open. Current main has partial durable delivery machinery, but source still shows final-response accounting paths that can treat a queued or merely non-suppressed final as visible delivery, and the live related Telegram PR is only a focused, still-open slice of the broader cross-channel contract.

## What This Changes

Define a shared core/channel contract so sanitized final fallback messages are delivered or explicitly reported as failed, suppressed, partial, or unknown instead of disappearing silently.

## Best Possible Solution

Keep this as the canonical maintainer issue, land or replace focused channel slices under it, and converge them on one shared core/SDK delivery-outcome contract with cross-channel tests plus live proof on at least one real channel.

## Reproduction Assessment

Yes at source level, but not by a live reproduction in this review. Current main still treats queued or merely non-suppressed final delivery as visible response in key paths, and the issue discussion includes concrete WhatsApp, Telegram, and Discord production-style reports.

## Solution Assessment

Yes at the product boundary: a shared core/channel delivery outcome contract is the maintainable fix shape. The open Telegram PR is a useful focused slice, but it is not a complete solution for the cross-channel contract.

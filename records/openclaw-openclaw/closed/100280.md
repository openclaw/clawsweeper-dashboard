## Summary

Keep open: current main and the latest release still produce and consume a single mobile setup-code URL, so the reported LAN-only pairing failure remains real; the protected `maintainer` label and route/security contract changes mean this needs maintainer direction before automation.

## What This Changes

The issue requests mobile pairing setup codes that advertise usable LAN and Tailnet routes, prefer secure Tailnet routes when present, and let mobile clients fall back across routes.

## Best Possible Solution

Define a backward-compatible setup-code route contract at the gateway protocol boundary, keep the legacy `url`, add validated route candidates with secure Tailnet preference, and update iOS/Android to try those candidates without weakening current cleartext restrictions.

## Summary

Keep open: the PR targets a real maxTokens fallback problem, but it is not merge-ready because the linked custom configured-model path can still synthesize the context-window-sized output cap, and the PR body provides only test-based proof.

## What This Changes

The PR adds an agent-level DEFAULT_MODEL_MAX_TOKENS constant, uses it for missing maxTokens in static-catalog model conversion, and adds static-catalog resolver coverage.

## Best Possible Solution

Fix the configured fallback resolver so custom provider models without maxTokens no longer synthesize a context-window output cap; add regression coverage for the reported Xiaomi config and keep the static-catalog default change only if maintainers want 8192 as the generic fallback.

## Reproduction Assessment

Yes from source inspection: a custom xiaomi model row without maxTokens and without a matching xiaomi static catalog row still falls through resolveConfiguredFallbackModel to DEFAULT_CONTEXT_TOKENS. I did not run a fresh live Xiaomi call in this read-only review.

## Solution Assessment

No: this patch is only a plausible partial fix because it changes static-catalog conversion, while the reported custom configured-model fallback path remains unchanged. The narrower maintainable fix is in the configured fallback resolver or a deliberate transport omission/default policy with matching regression coverage.

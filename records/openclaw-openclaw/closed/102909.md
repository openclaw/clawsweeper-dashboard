## Summary

Current main already handles the reported Anthropic 400/429 path through the Anthropic SDK before OpenClaw receives the raw Response, so the reported stream-parser failure should not occur on the SDK-backed provider path.

## What This Changes

The issue asks OpenClaw to validate Anthropic streaming HTTP responses before consuming the response body so API errors surface as provider status errors instead of stream parsing failures.

## Best Possible Solution

Keep the SDK-backed status handling path on current main; only reopen if a real non-SDK/injected-client path can produce a non-OK Response that reaches iterateAnthropicEvents.

## Maintainer Decision

Required: false

## Reproduction Assessment

No. Source and upstream SDK inspection show that SDK-backed Anthropic 400/429 responses throw typed API errors before OpenClaw can consume the response body as SSE; no live Anthropic error request was run in this read-only review.

## Solution Assessment

Yes. The current SDK-owned status gate is the right layer for SDK-created Anthropic responses; adding a second OpenClaw response.ok check would only be useful for a separately proven custom-client escape hatch.

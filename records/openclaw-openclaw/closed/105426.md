## Summary

Keep open: current main silently suppresses failure of its owner-only backup guarantee. Actual credential exposure is filesystem-dependent, but the source-level security gap is concrete and warrants focused security-owner review rather than cleanup closure.

## What This Changes

Report that config backup permission hardening suppresses chmod failures, potentially leaving credential-bearing backups readable by other local users.

## Best Possible Solution

Never leave a backup known to be group/world-readable: reuse the existing config permission-warning path, verify the resulting mode where meaningful, remove an unsafe newly created backup if hardening cannot be enforced, and preserve config-write compatibility on filesystems without POSIX mode support.

No high-confidence reproduction of the full credential disclosure was established: source inspection proves chmod errors are silently swallowed, while the inspected Linux copyFile path retained 0600. A focused permissive-destination or mixed-filesystem scenario is still needed to demonstrate exposure end to end.

## Solution Assessment

No, unconditional propagation alone is not the best fix because backup maintenance precedes config commit and mixed filesystems may reject POSIX chmod. The narrower maintainable path is visible warning plus verification and cleanup of any backup that remains unsafe.

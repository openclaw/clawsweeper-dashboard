## Label Justifications

- `P1`: Fresh non-interactive onboarding currently fails during a first-run agent/configuration flow and can leave an incomplete configuration.
- `merge-risk: 🚨 compatibility`: The proposed baseline rebasing can silently replace a concurrently written user or operator configuration change.

## Summary

Keep this PR open. It fixes a real fresh-install regression, but rebasing to a hash sampled after agent creation can also accept a concurrent foreign configuration write and then overwrite that write with the onboarding config; the existing optimistic-concurrency protection must remain authoritative.

## What This Changes

This PR changes non-interactive onboarding so its final configuration commit uses the hash observed after creating the first agent, preventing onboarding from rejecting its own intermediate configuration write.

## System Context

Non-interactive onboarding builds a complete OpenClaw configuration, creates the first roster agent when needed, and then commits provider, model, workspace, and gateway settings. The configuration hash is the optimistic-concurrency boundary that prevents that final commit from silently overwriting another writer.

## Architecture Diagram

flowchart LR
  A[Fresh non-interactive onboarding] --> B[Load config and baseline hash]
  B --> C[Create first roster agent]
  C --> D[Observe config state]
  D --> E[Build provider workspace and gateway settings]
  E --> F[Optimistic final config commit]
  F --> G[Configured agent and gateway]

## Best Possible Solution

Keep the original foreign-write guard intact by obtaining an exact, operation-owned post-write version from the agent-creation mutation itself, or by otherwise proving atomically that the adopted baseline is the write this onboarding run performed; add a regression test for an intervening external mutation.

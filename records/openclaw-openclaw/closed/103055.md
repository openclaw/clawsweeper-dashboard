## Summary

Keep open: current main still has the reported authorization/data-exposure path, and the latest release also contains the unscoped `/acp sessions` listing. This is a security-boundary issue, not conservative cleanup.

## What This Changes

The issue requests scoping or owner-gating `/acp sessions` so allowlisted non-owner senders cannot enumerate other gateway ACP sessions.

## Best Possible Solution

Fix the security boundary so `/acp sessions` can no longer enumerate gateway-wide ACP sessions for authorized non-owners; the docs-aligned end state is a tested requester/current-session scoped listing, with owner-only gating as a safe fallback if scoping cannot be proven quickly.

- **Keep gateway-wide visibility:** Only choose this if maintainers intentionally redefine `/acp sessions` as an owner/admin diagnostic and update the public contract accordingly.

Yes, from source inspection: current main lets authorized non-owner `/acp sessions` reach the handler, and that handler queries all ACP session rows without requester scoping. I did not run the live chat flow in this read-only review.

## Solution Assessment

Unclear until maintainers choose the security policy, but the narrow docs-aligned fix is to scope the query to the requester/current bound session. A fail-closed owner gate is the safer hotfix if scoped ownership cannot be proven quickly.

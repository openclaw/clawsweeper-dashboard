## Summary

Keep open. Current main already has the safe headless fallback and actionable headed/no-display text, but the remaining requested contract is still missing because browser route and client errors are still string-only instead of carrying a machine-readable reason/details payload.

## What This Changes

The issue requests policy-controlled no-display handling for managed browser launches, especially a structured error or safe fallback when headed mode is configured without a Linux display server.

## Best Possible Solution

Keep the current implicit-fallback versus explicit-headed-error policy, and add an additive typed browser error contract that preserves the existing human `error` string while exposing a closed `reason` and typed details through routes and the client.

## Reproduction Assessment

Yes, from source inspection: explicit headed/no-display failures become a message-only `BrowserProfileUnavailableError`, route JSON is only `{ error }`, and the client rethrows only the message. I did not run a live Linux no-display launch during this read-only review.

## Solution Assessment

Unclear until maintainers choose the public envelope, but the best technical shape is an additive structured reason/details contract rather than more automatic fallback for explicitly headed profiles.

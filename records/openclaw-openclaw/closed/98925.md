## Summary

Keep open: current main and v2026.6.11 still resolve target DNS in the strict managed-proxy branch before creating the env proxy dispatcher, so the reported proxy-only failure remains valid and security-sensitive.

## What This Changes

The issue reports that strict/default `fetchWithSsrFGuard` performs local DNS pinning before managed-proxy dispatch, causing proxy-only guarded fetches to fail before the proxy can resolve and enforce policy.

## Best Possible Solution

Update the shared guarded-fetch managed-proxy branch so strict/default traffic that should use the active proxy performs pre-DNS hostname/IP-literal checks and then dispatches through the proxy, while preserving direct strict DNS pinning, loopback bypass rules, redirect revalidation, and focused regression coverage.

## Reproduction Assessment

Yes from source, not from a live run: with `OPENCLAW_PROXY_ACTIVE=1`, proxy env configured, and strict/default mode, current main calls `resolvePinnedHostnameWithPolicy()` before the env proxy dispatcher. A focused regression can use a failing `lookupFn` to prove the proxy is never reached.

## Solution Assessment

Unclear until maintainer/security review: the shared fetch guard is the right layer because many callers default to strict mode, but maintainers need to accept the managed proxy as the final DNS/IP enforcement boundary for this branch.

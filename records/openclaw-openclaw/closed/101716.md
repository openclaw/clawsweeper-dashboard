## Summary

Keep open: current main still materializes and sorts the full task registry for each `tasks.list` page, and the related task-ledger follow-up/PR only covers adjacent ordering/UI issues, not this server-side cost.

## What This Changes

The issue asks for `tasks.list` to avoid full in-memory filtering and sorting before returning a requested page.

## Best Possible Solution

Add a bounded gateway/task-registry listing path that filters and selects only the requested page window without a full `listTaskRecords()` clone/sort, while preserving the current `tasks.list` response shape and ordering tests.

## Repair Work Prompt

Fix the `tasks.list` Gateway RPC performance bug reported in https://github.com/openclaw/openclaw/issues/101716. Current main calls `listTaskRecords()` and then filters/sorts/slices the full registry on every RPC call; add a bounded task-registry/gateway listing path that avoids cloning and sorting all task records when returning a page. Preserve the current `tasks.list` params/result shape and last-activity ordering, do not add config/env/protocol fields, and do not duplicate the adjacent PR https://github.com/openclaw/openclaw/pull/101028. Add regression coverage that proves large registries do not require a full `listTaskRecords()`-style clone/sort for a small first page, while existing status, agent/session filtering, cursor, ordering, and summary behavior remain covered. Coordinate with https://github.com/openclaw/openclaw/issues/100911 only for cursor-stability assumptions; stop and ask if the fix would require changing public cursor semantics.

## Summary

Current main behaves exactly as reported: `sessions_send(agentId=...)` resolves only agents configured in the active profile, and subsequent session RPCs use that profile’s gateway. The work remains necessary if OpenClaw intends to support native coordination between isolated gateways, but this is a new security-sensitive product capability rather than a bug in the documented single-gateway contract, so it needs maintainer direction.

## What This Changes

Add a supported profile-qualified route for agent-to-agent messages across isolated OpenClaw gateway profiles.

## Best Possible Solution

If maintainers support this topology, define an additive authenticated peer-gateway contract with explicit peer configuration, per-agent allowlists, preserved inter-session provenance, idempotency, and typed unavailable, denied, and not-found errors; do not make local agent ids silently search arbitrary profiles.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw make authenticated cross-profile gateway routing a first-class core capability, expose a narrow plugin seam for it, or keep separate profiles intentionally isolated?

Rationale: The limitation is real, but changing it expands the gateway trust model and requires product ownership of peer discovery, credentials, authorization, provenance, and failure behavior.

Likely owner: steipete

Owner reason: The strongest combined history signal spans inter-session provenance, core session behavior, gateway connectivity, and security-sensitive routing decisions.

Owner confidence: high

Options:

- **Design core peer routing (recommended):** Define explicit configured gateway peers, authentication, per-agent authorization, provenance, and typed failure behavior before implementation.
- **Expose a plugin seam:** Add only the minimum stable SDK or gateway protocol surface needed for an external routing plugin to own peer discovery and delivery.
- **Keep profiles isolated:** Document the existing CLI or external-orchestrator workflow and state that session tools remain scoped to one gateway profile.

## Reproduction Assessment

Yes. Current main checks `agentId` against the active profile’s configured agents and returns `agent not found` before any alternate gateway can be selected.

## Solution Assessment

No proposed variant is automatically the best solution: implicit profile lookup is unsafe, while an explicit peer-gateway contract or narrow plugin seam could preserve isolation and avoid duplicated protocol logic.

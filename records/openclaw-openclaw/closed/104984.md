## Summary

Keep this issue open: current main still derives owner authority from the origin channel’s ordinary allowlist, applies that owner result before resolving `/allowlist`’s target, and performs no target-identity authorization before persistence. The three cited merged PRs added neighboring owner and `configWrites` gates but do not fix this trigger, and canonical search found no separate issue or open PR owning the remaining work.

## What This Changes

Prevent a sender authorized only by one channel allowlist from modifying another channel’s allowlist through `/allowlist`.

## Best Possible Solution

Define one canonical privileged-command owner invariant before mutation: preferably require explicit global owner authority for cross-channel writes, then add focused regression coverage for same-channel and cross-channel config and store mutations.

Question: Should cross-channel `/allowlist` writes require an explicit global owner identity, or may target-channel allowlist membership confer mutation authority for that target?

Rationale: Both choices can close the reported hole, but they establish different long-term trust semantics for ordinary channel allowlists and privileged configuration commands.

Likely owner: steipete

Owner confidence: high

Options:

- **Require explicit global owner (recommended):** Reject cross-channel mutations unless the sender matches `commands.ownerAllowFrom` or carries internal `operator.admin` authority.
- **Authorize against target scope:** Permit the mutation when the sender independently matches an owner rule derived for the selected target channel and account.

## Reproduction Assessment

Yes at high confidence from source: the origin allowlist can become `ownerList`, that result sets `senderIsOwner` before target resolution, and the later target policy checks only `configWrites`. The supplied production-path harness also reports the resulting persisted mutation, although this read-only review did not execute it.

## Solution Assessment

Unclear as proposed: target-aware authorization addresses the trigger, but requiring explicit global owner authority for cross-channel writes is a simpler and safer invariant than making ordinary target-channel allowlist membership a configuration privilege.

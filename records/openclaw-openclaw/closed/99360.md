## Summary

Keep open: the unbounded success-path read is a real browser-control memory risk, but this patch cannot pass yet because it applies one global 16 MiB cap to every successful HTTP JSON response while current snapshot routing still has an explicit uncapped `maxChars=0` path, and the PR has no after-fix real behavior proof.

## What This Changes

The PR adds a 16 MiB success-body read limit to browser-control HTTP JSON responses by replacing `res.json()` in `fetchHttpJson` with `readResponseWithLimit` plus `JSON.parse`.

## Best Possible Solution

Land a bounded success-reader only after route/API compatibility is handled, focused success-overflow coverage is added, and redacted runtime proof shows the oversized response path behaves safely.

## Reproduction Assessment

Yes from source inspection: current main's HTTP success path in `fetchHttpJson` uses `res.json()` while the error path already uses capped `readResponseWithLimit`, so an oversized success body would be buffered before parsing. I did not run a live oversized-response repro because this review is read-only.

## Solution Assessment

No. The bounded reader is the right mitigation, but a single global cap is not the best safe merge shape until the explicit snapshot `maxChars=0` behavior is preserved or intentionally retired with tests/docs and proof.

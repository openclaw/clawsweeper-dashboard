## Label Justifications

- `P1`: The report describes an active Telegram channel becoming unavailable for an extended period until the Gateway is restarted.
- `impact:crash-loop`: The reported symptoms include repeated health-monitor restart attempts after a stopped or disconnected channel state.
- `impact:message-loss`: An offline Telegram polling channel can suppress normal inbound message handling and replies.

## Summary

The reported failure mode is already addressed: current channel lifecycle code preserves a bounded 5-second shutdown wait but explicitly recovers a timed-out task so the health monitor can restart the channel instead of leaving it stuck. The v2026.7.1 release notes also state that Telegram and other channels recover after timed-out shutdowns without requiring a Gateway restart. ([github.com](https://github.com/openclaw/openclaw/blob/main/src/gateway/server-channels.ts))

## What This Changes

Prevent Telegram polling from remaining offline after a timed-out channel shutdown or polling-runner restart.

## System Context

OpenClaw’s Gateway owns the shared lifecycle for channel accounts, while the Telegram plugin runs polling work within that lifecycle. A channel-stop timeout feeds into recovery state, cleanup of the stale task, and a controlled account restart so the message transport can resume.

## Architecture Diagram

flowchart TD
  A[Telegram long-poll task] --> B[Gateway channel lifecycle]
  B --> C[Abort and bounded stop wait]
  C --> D{Task stopped?}
  D -->|Yes| E[Normal cleanup]
  D -->|No| F[Timed-stop recovery state]
  F --> G[Clear stale task and abort handle]
  G --> H[Restart channel account]

## Best Possible Solution

Keep the bounded generic shutdown timeout and the existing stale-task recovery path; investigate only a fresh current-release reproduction that shows the replacement channel still fails to start.

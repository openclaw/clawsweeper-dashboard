## Summary

Keep open: current main still treats `yieldDetected` as terminal output by itself, so an interactive direct turn can return with no payload when `sessions_yield` fired but no accepted spawn, message-tool delivery, cron add, or other continuation source was recorded. The closest related issues and PRs cover adjacent wake/delivery failures, but none clearly owns this exact no-fresh-wake-source guard.

## What This Changes

The issue reports that `sessions_yield` can end an interactive direct turn successfully before the turn creates any fresh wake or continuation source, leaving the session silent until a new inbound message arrives.

## Best Possible Solution

Define and enforce a yield continuation invariant for interactive direct turns: a yielded turn should have a known continuation source or emit a visible fallback instead of silently parking.

## Reproduction Assessment

Yes at source level: `sessions_yield` sets `yieldDetected`, and current terminal-state logic treats that flag as sufficient terminal output even when no accepted spawn, message-tool delivery, or cron continuation was recorded. I did not run the full Telegram incident live.

## Solution Assessment

Unclear until maintainers choose the exact semantics for existing wake sources. The narrow maintainable direction is a runtime guard or visible fallback, not prompt-only guidance, but it must avoid rejecting valid waits on already-active child work.

## Summary

Keep open: current main and latest release still reset `reconnectAttempts` on every realtime transcription websocket `open`, so the configured cap and exponential backoff remain defeated for ready-then-close flapping sessions.

## What This Changes

The issue requests fixing realtime transcription websocket reconnect accounting so flapping-after-ready sessions back off exponentially and stop at `maxReconnectAttempts`.

## Best Possible Solution

Fix the shared websocket session helper so flapping after readiness consumes reconnect attempts and backs off, add one focused regression test, and leave provider-specific APIs/config unchanged.

## Repair Work Prompt

Fix https://github.com/openclaw/openclaw/issues/102251. In `src/realtime-transcription/websocket-session.ts`, the websocket `open` handler resets `reconnectAttempts` on every successful raw socket open, which prevents flapping-after-ready reconnects from ever reaching `maxReconnectAttempts` or increasing exponential backoff. Change the shared helper so repeated ready-then-close flaps consume reconnect attempts and stop with the existing reconnect-limit error after the configured cap. Preserve the initial `connect()` reset and normal explicit close behavior; do not add config/env options and do not patch individual providers unless the shared helper contract requires a tiny call-site adjustment. Add a focused regression in `src/realtime-transcription/websocket-session.test.ts` using a local `ws` server that accepts, marks the session ready, closes repeatedly, sets a small `reconnectDelayMs`, and asserts the delays grow and the reconnect-limit error fires after the configured attempts. Mention in the PR body that this is a realtime transcription reliability fix; do not edit `CHANGELOG.md`.

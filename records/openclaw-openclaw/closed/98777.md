- `impact:message-loss`: The central failure mode is inbound Telegram updates being acknowledged and then lost before they can be retried or processed.

## Summary

Keep open: the protected `maintainer` label blocks cleanup auto-close, and current `main` still has the source-proven Telegram webhook ACK-before-durable-processing loss window. The older open issue is canonical for the durable webhook design, but this report adds useful adjacent webhook startup, transport, and rate-limit context.

## What This Changes

The issue reports that Telegram webhook mode acknowledges updates before durable persistence, so crashes, restarts, or post-ACK handler failures can permanently lose inbound messages.

## Best Possible Solution

Keep this maintainer-labeled issue open as additional context, keep https://github.com/openclaw/openclaw/issues/42157 canonical for durable Telegram webhook ACK/replay semantics, and have maintainers decide whether to split startup retry, transport close, and rate-limit changes into focused issues or PRs.

## Reproduction Assessment

Yes for a source-level reproduction path: current main sends 200 before awaiting or durably persisting `bot.handleUpdate`, and tests assert processing can remain unfinished after ACK. I did not run a live Telegram crash/restart repro in this read-only review.

## Solution Assessment

Unclear as one bundled fix: durable webhook persistence likely belongs in the Telegram plugin and should use the existing SQLite ingress queue, but ACK/replay semantics plus the adjacent retry, transport-close, and rate-limit changes need maintainer direction or focused split work.

## Summary

Keep open: current main and v2026.6.11 still use env/service markers only for Windows Scheduled Task detection, and the open linked PR is the active candidate fix rather than a reason to close this issue.

## What This Changes

The issue asks Windows `/restart` to restart with a fresh gateway PID when a Scheduled Task exists but supervisor environment markers are missing.

## Best Possible Solution

Review and land a focused fix that probes the same Windows Scheduled Task target the restart handoff will run, keeps unmanaged detached respawn disabled, and includes redacted Windows `/restart` plus `/status` proof.

Rationale: This changes compatibility-sensitive restart fallback behavior: unsafe detached respawn was intentionally removed, but marker-only detection leaves a real Scheduled Task install unable to fresh-restart when the gateway was started manually.

Options:

- **Adopt exact Scheduled Task probing (recommended):** Allow env-less Windows gateways to use schtasks only after probing the same default/profile/custom task name the restart handoff will run, with live Windows proof before merge.
- **Keep marker-only supervision:** Treat manually started Windows gateways as unmanaged unless service markers are present, preserving the current conservative fallback but leaving this report's PID behavior unchanged.
- **Fold into broader Windows restart work:** Defer this edge case into a coordinated Windows restart reliability PR that also addresses schtasks failure diagnostics and wrong-task recovery.

## Reproduction Assessment

Yes, at source level: on win32 with no Scheduled Task env/service markers, current main returns no supervisor, disables detached respawn, and the run loop falls back in process. I did not run a live Windows Scheduled Task scenario in this read-only review.

## Solution Assessment

Unclear until the linked PR is reviewed: probing schtasks is safer than detached respawn, but it must query the exact handoff task and prove `/restart` changes PID or uptime on Windows.

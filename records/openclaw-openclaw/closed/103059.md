## Summary

Keep open: current main and v2026.6.11 still have the unguarded migration config merge path, and no linked fix PR or duplicate canonical item now owns the work.

## What This Changes

The issue reports that migration-import config patch merging can write prototype-bearing keys from imported config into live config objects.

## Best Possible Solution

Guard the shared migration config merge/write helper with the existing blocked-key primitive, add direct helper and Hermes provider/MCP/skill regression coverage, and preserve normal safe config merges.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should imported migration config patches reject or drop `__proto__`, `constructor`, and `prototype` keys at the shared SDK helper boundary?

Rationale: The bug is clear, but the public plugin SDK helper's failure semantics affect bundled and third-party migration providers and should be set deliberately for a security boundary.

Likely owner: steipete

Owner reason: Peter's commits introduced the generic migration provider helper and onboarding import path, making him the clearest owner for the SDK boundary decision.

Owner confidence: high

Options:

- **Guard Shared SDK Helper (recommended):** Block prototype-bearing keys in `mergeMigrationConfigValue` and `writeMigrationConfigPath`, with tests for direct helper and Hermes provider/MCP/skill imports.
- **Filter Hermes Only:** Sanitize Hermes provider/MCP/skill keys locally, which fixes the reported import but leaves other migration providers dependent on caller discipline.
- **Accept Trusted Import Risk:** Document tampered prior-tool configs as out of scope and keep the current merge behavior unchanged.

## Reproduction Assessment

Yes, source-level: the current merge helper assigns attacker-controlled object keys through bracket notation without `isBlockedObjectKey` filtering. A full interactive onboarding repro has not been run in this read-only review.

## Solution Assessment

Yes, the best fix is a narrow shared migration-helper guard using the existing blocked-key pattern. Maintainers still need to choose reject versus drop semantics for the public SDK contract.

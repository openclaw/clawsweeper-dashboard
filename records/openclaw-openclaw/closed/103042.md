## Label Justifications

- `P0`: The PR concerns a Windows command-injection hardening path for Azure CLI invocations in provider auth, which is a security-sensitive execution boundary.
- `merge-risk: 🚨 compatibility`: The patch changes how existing Windows Microsoft Foundry users launch the Azure CLI during upgrade-sensitive auth and onboarding flows.
- `merge-risk: 🚨 auth-provider`: If `az.cmd` cannot be launched directly, Entra token refresh and device-code login fail for Microsoft Foundry auth on Windows.

## Summary

Keep open: the security goal is valid, but the patch is not mergeable because it resolves to `az.cmd` and then launches it with Node `execFile`/`spawn` without a shell, which Node documents as unsupported on Windows; the submitted proof only covers Linux tests.

## What This Changes

The PR adds a cached Azure CLI command resolver and removes Windows `shell` options from Microsoft Foundry `execFileSync`, `execFile`, and `spawn` calls.

## Best Possible Solution

Keep the hardening goal, but implement Azure CLI invocation through a Node-supported Windows wrapper strategy or the existing plugin SDK Windows spawn helper, with Windows proof for `az version`, token refresh, and device-code login.

Required: false

## Reproduction Assessment

Yes for the PR regression from source and dependency contract: on Windows `resolveAzCommand()` can return `az.cmd`, and Node 22 documents that `.cmd` cannot be launched with `execFile`. I did not run a Windows host.

## Solution Assessment

No. Removing shell parsing is the right security direction, but resolving `az.cmd` and passing it to `execFile`/`spawn` without a shell is not a valid Windows execution strategy.

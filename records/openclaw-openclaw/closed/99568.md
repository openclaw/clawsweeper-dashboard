## Summary

Keep this PR open for maintainer review: current main still has the Android allowlist self-package policy gap, and the PR fixes it in the shared policy path without a concrete patch defect. The remaining blocker is accepting the intentional upgrade-visible behavior change for persisted allowlists that include the OpenClaw app package.

## What This Changes

The PR adds `selfPackageName` to Android notification forwarding policy, rejects that package before allow/blocklist evaluation, passes the app package from `SecurePrefs`, and adds policy/prefs regression tests.

## Best Possible Solution

Land the centralized policy guard once maintainers accept that Android self-notification forwarding is unsupported, while keeping broader native-channel notification ownership work tracked separately.

## Reproduction Assessment

Yes, at source level: current main and `v2026.6.11` can return true for the app package in allowlist mode because the shared policy helper only checks the configured package set. I did not rerun Android locally in this read-only review, but the PR body and CI provide after-fix proof.

## Solution Assessment

Yes. Centralizing self-package rejection in `NotificationForwardingPolicy` is the best fix shape because it covers queued/reconnect reauthorization and all policy consumers; a callback-only guard would leave the shared policy path inconsistent.

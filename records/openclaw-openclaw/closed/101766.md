## Summary

Keep open: the patch is a useful mitigation, but it is incomplete because it bounds only the transcript usage read while the same token-count path still awaits the parent transcript byte-estimate `fs.stat` before that timeout.

## What This Changes

The PR imports `withTimeout` and wraps the parent transcript usage read in `resolveParentForkTokenCountRuntime` with a 10 second deadline.

## Best Possible Solution

Put one bounded deadline around the whole stale parent-token probe after the fresh persisted-token fast path, preserve cached/byte-estimate fallback behavior when available, and cover both hung stat and hung transcript-read paths with focused regression proof.

## Maintainer Decision

Required: false

Yes, source inspection gives a high-confidence path: force the parent transcript `fs.stat` or read path to hang while creating a forked session, and current code still awaits that token-count decision. I did not run a live slow-filesystem reproduction in this read-only review.

## Solution Assessment

No: wrapping only the transcript usage read is too narrow because parent-token resolution still does an unbounded byte-estimate stat first. The maintainable fix is to bound the whole stale-token filesystem probe or both filesystem awaits together.

## Summary

Keep open. Current main and v2026.7.1 still show Telegram-specific isolated ingress without equivalent Discord WebSocket isolation, while multiple production reports support a continuing Discord latency and heartbeat-responsiveness problem under main-loop starvation. Likely related people: joshavant (high confidence, Telegram isolation precedent) and mgunnin (medium confidence, recent Discord ingress-ordering work).

## What This Changes

Isolate Discord gateway ingress from main-event-loop stalls, analogous to Telegram’s worker-backed durable ingress spool.

## Best Possible Solution

After a controlled current-main saturation reproduction, keep Discord transport ownership in the plugin, move heartbeat and socket receipt into an isolated worker only if profiling confirms that boundary, persist normalized inbound envelopes through the shared SQLite/plugin-KV seam, and prove ordering, reconnect/resume, restart recovery, and live Discord responsiveness without adding a config knob.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Discord adopt a plugin-owned worker and SQLite-backed ingress queue, or should OpenClaw first solve the shared event-loop starvation and backpressure path without adding a second channel-specific isolation architecture?

Rationale: Discord’s persistent gateway session has heartbeat, resume, sequence, and reconnect invariants that differ materially from Telegram polling, and the available production evidence does not yet establish which ownership boundary provides the safest durable fix.

Likely owner: joshavant

Owner reason: The Telegram worker/spool implementation provides the closest merged architectural precedent and its author is best positioned to assess which invariants carry over to Discord.

Owner confidence: high

Options:

- **Sponsor isolated Discord ingress (recommended):** Keep the WebSocket and heartbeat loop in a Discord-owned worker, bridge normalized events through SQLite-backed plugin state, and require saturation plus reconnect/resume proof.
- **Fix shared starvation first:** Profile the heavy tool-output and sidecar paths, add yielding or backpressure at the shared source, and reconsider channel isolation only if Discord remains vulnerable.
- **Accept the current coupling:** Retain the main-thread gateway architecture and document operational load limits, accepting intermittent latency and reconnect risk during severe stalls.

## Reproduction Assessment

No, there is not yet a high-confidence controlled reproduction on current main. The main-thread ownership path and multiple production logs make the failure source-reproducible, but a deliberate stall test must measure socket receipt, heartbeat handling, event forwarding, and agent dispatch separately.

## Solution Assessment

Unclear. Worker isolation is a credible plugin-owned fix and has a Telegram precedent, but it is not yet proven better than removing the shared starvation source because Discord must preserve persistent gateway heartbeat and resume state.

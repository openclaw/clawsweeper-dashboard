## Summary

Keep open: current main still exposes the Control UI Talk button and starts the browser Realtime path before the OpenAI SDP call; related auth fixes and diagnostics do not settle whether browser Talk should require explicit Realtime readiness or use implicit OpenAI/Codex credentials.

## What This Changes

The issue requests that the Control UI Talk button avoid starting an OpenAI Realtime WebRTC call when Realtime is not intentionally configured, or show a clear readiness/error state instead.

## Best Possible Solution

Make Gateway-owned Realtime readiness the single source for the Control UI Talk button and startup error after maintainers choose whether implicit OpenAI/Codex auth should enable browser Talk.

Options:

- **Gate on Gateway readiness (recommended):** Disable or block browser Talk before microphone startup unless `talk.catalog` or an equivalent Gateway preflight reports a usable Realtime provider.
- **Keep implicit credential activation:** Treat configured OpenAI/Codex Realtime auth as sufficient and narrow follow-up work to clearer diagnostics for provider/API failures.
- **Require explicit Realtime config:** Only show or start browser Talk when `talk.realtime` is explicitly configured, accepting upgrade and migration impact for existing users.

Yes at source level: current main still renders the Talk control, calls `talk.client.create` first, and the WebRTC transport posts SDP to OpenAI before surfacing a generic status error. I did not live-reproduce the external 500.

## Solution Assessment

Unclear until maintainers decide the enablement contract. A UI-only hide rule is not enough; the durable fix should use Gateway/provider readiness so UI, docs, and runtime routing stay aligned.

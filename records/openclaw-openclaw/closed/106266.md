## Summary

Keep open: this fresh, maintainer-labeled accessibility initiative addresses a meaningful Control UI gap, and current main still contains multiple custom modal, tooltip, splitter, menu, and settings-control implementations rather than the requested keyboard-complete component strategy. The native semantic repairs are well motivated, while adopting Web Awesome Core needs explicit dependency and design-system approval.

## What This Changes

Make Control UI composite controls keyboard-complete and assistive-technology accessible, first through native semantic repairs and then through a selective Web Awesome Core migration.

## Best Possible Solution

Land the native semantic fixes and an accessibility regression harness first, then pilot Web Awesome Core on one representative composite control and expand only after bundle, theming, focus, and browser proof establishes it as the maintainable default.

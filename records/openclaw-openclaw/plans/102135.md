## Summary

Keep open: current main and v2026.6.11 still run ACP media understanding and then forward raw ACP image attachments, while a sibling non-ACP path already filters described current images. This is a narrow ACP dispatch bug, not a duplicate of the broader agent-RPC opt-in or durable media-memory requests.

## Plan

Fix https://github.com/openclaw/openclaw/issues/102135. In ACP dispatch, when `applyMediaUnderstanding` produces `image.description` outputs for current-turn attachments, do not forward those same current images as raw ACP attachments to `acpManager.runTurn`. Implement this in `src/auto-reply/reply/dispatch-acp.ts` or a small shared helper by filtering `mediaAttachments` and their `attachmentIndexes` against described image attachment indexes from `ctx.MediaUnderstanding`. Preserve existing behavior for inline `params.images`, extracted PDF page images from `extractedFileImages`, undescribed current images, recent-history image context, attachment ordering, root/size limits, and ACP empty-prompt handling. Do not change the public `agent` RPC opt-in design from https://github.com/openclaw/openclaw/issues/93741 and do not attempt the durable media-memory work from https://github.com/openclaw/openclaw/issues/88646. Add focused regression coverage in `src/auto-reply/reply/dispatch-acp.test.ts` for a current image whose media-understanding mock returns an `image.description` at attachment index 0: `runTurn` should receive the text description context but no raw current image attachment. Include a mixed case if practical to prove extracted PDF page images or undescribed images still reach ACP. No changelog edit is expected unless user-visible wording changes.

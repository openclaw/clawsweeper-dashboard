## Summary

Keep this issue open. Current main still aborts device-code polling for any thrown error other than a timeout or caller cancellation, so a transient fetch/DNS/socket failure can end the interactive authorization window. The proposed unconditional retry is too broad because it would also hide local validation, SSRF-guard, and response-processing failures; a narrow retriable-error policy with the normal poll delay is the safer repair.

## Plan

Repair the OpenAI plugin’s interactive device-code polling path so transient transport failures do not abort an otherwise valid 15-minute authorization window. In `extensions/openai/openai-chatgpt-device-code.ts`, retain caller cancellation, deadline behavior, SSRF-guard/local validation failures, malformed success-payload errors, and terminal HTTP responses. Add an explicit classifier for safely retriable fetch-level transport errors and any deliberately supported transient HTTP statuses; after each retryable failure, wait through the existing deadline-aware poll-delay helper rather than looping immediately. Add regression coverage in `extensions/openai/openai-chatgpt-device-code.test.ts` for a successful user-code request followed by a transient poll failure and eventual authorization, plus a terminal error that still fails fast. Do not add config/env options, runtime fallbacks, or CHANGELOG.md edits. Check the Codex device-code implementation directly before deciding the final error taxonomy, then document any intentional OpenClaw divergence in the test or nearby invariant comment.

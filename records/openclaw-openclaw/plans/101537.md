## Summary

Keep open. Current main still treats disabled immediate heartbeats as terminal for recurring main-session cron wakes, while the previous merged repair only covers one-shot `at` jobs; the reporter's recurring `every` job can still lose the queued system event and advance as `skipped/disabled`.

## Plan

Fix the recurring main-session cron wake path reported in https://github.com/openclaw/openclaw/issues/101537. Current `executeMainSessionCronJob` enqueues the system event, then if `runHeartbeatOnce` returns `skipped` with reason `disabled`, removes the queued event and returns skipped. Existing retry handling from https://github.com/openclaw/openclaw/pull/92225 only applies to one-shot `schedule.kind === "at"` jobs, so recurring `every` or `cron` main-session jobs advance normally and lose that scheduled wake. Extend disabled-heartbeat handling for recurring main-session `wakeMode: "now"` jobs so a skipped/disabled immediate heartbeat does not silently drop the scheduled system event and advance as a normal skipped run. Preserve the previous safety invariant: do not mark a disabled heartbeat as successful unless the event is actually consumed or durably handed to a later wake path; remove failed-attempt queued events when retrying; do not affect busy skip handling, isolated jobs, command jobs, or `wakeMode: "next-heartbeat"`. Add focused regression coverage for a recurring `every` main-session systemEvent job where the first disabled heartbeat attempt is retried/backed off or otherwise remains deliverable, and prove no queued event is left behind on failed attempts and the run only records ok after the event is consumed or queued for a later wake. Do not add new config or provider behavior.

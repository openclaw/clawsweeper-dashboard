## Summary

This PR has strong real-runtime proof for releasing a wedged maintenance lane and fencing host-owned late transcript/task writes, but it still leaves a P1 compatibility and session-state defect: after the timeout releases the lane, the scheduler may begin a second same-session `ContextEngine.maintain()` while the first plugin invocation is still running. Requiring every existing engine to become re-entrant changes the plugin contract rather than preserving the host’s prior serialization guarantee, so this should remain open for a narrow scheduler repair.

## Plan

Repair the deferred context-engine maintenance timeout path for https://github.com/openclaw/openclaw/issues/96703. Preserve the opt-in timeout and host-side late-write fence, but do not allow a second same-session `ContextEngine.maintain()` invocation to start while a timed-out first invocation remains unsettled. Use a core-owned per-session invocation tail, coalescing, or equivalent scheduler state so queued foreground turns still proceed after timeout while subsequent deferred maintenance waits safely. Remove or narrow the new required re-entrant `maintain()` contract unless an explicit existing contract remains necessary. Add regression coverage for: first maintenance invocation timing out but continuing; queued foreground turn proceeding; no overlapping second same-session `maintain()` call before the first settles; and later maintenance being scheduled or coalesced correctly after settlement. Do not edit `CHANGELOG.md` and do not add a new public configuration setting.

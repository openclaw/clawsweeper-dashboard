## Summary

Keep open: current main still routes an empty Telegram native command-menu tap into the normal bare slash-command path, and the affected handlers return usage text rather than a ForceReply prompt. This is a useful Telegram UX improvement, but it needs maintainer product/API direction because the durable fix would add command prompt semantics rather than repair a broken existing contract.

## What This Changes

The issue requests a Telegram ForceReply prompt when a menu-selected Telegram command that requires arguments arrives without an argument.

## Best Possible Solution

Add a maintainer-approved opt-in command prompt descriptor or portable prompt action, then map that to Telegram ForceReply for selected missing freeform-argument commands while leaving usage-only commands unchanged.

Options:

- **Add opt-in prompt metadata (recommended):** Define a narrow command-level prompt descriptor, enable it only for selected missing freeform-argument commands, and implement Telegram ForceReply as the channel mapping.
- **Keep usage-only behavior:** Leave bare menu taps as usage replies until a broader native-command prompt design is approved.
- **Prototype in Telegram only:** Add a small Telegram-local allowlist for ForceReply while accepting possible drift from command metadata and other native surfaces.

## Reproduction Assessment

Yes, source-reproducible on current main: empty Telegram native command payloads become bare slash-command text, and /btw and /steer return usage text when no argument is present. I did not run a live Telegram bot repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the command contract; the best maintainable path is likely opt-in prompt metadata or a portable prompt action, not a blanket acceptsArgs behavior change or string inference in Telegram.

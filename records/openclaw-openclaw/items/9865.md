## Summary

Keep open. Current main still lacks provider-neutral Batch API routing for delayed/background agent turns, and the issue remains the canonical product/API tracker rather than a fixed or safely queueable repair.

## What This Changes

Request support for opting background OpenClaw work such as cron jobs, subagents, and heartbeat checks into provider Batch APIs for lower-cost delayed execution.

## Best Possible Solution

Define an additive delayed/batch agent-turn contract in provider runtime and the Plugin SDK, then expose explicit opt-ins across cron, sessions_send, sessions_spawn/subagents, and heartbeat/background runs with provider implementations and docs.

Question: Should OpenClaw add a generic delayed/batch agent-turn lifecycle across provider runtime, Plugin SDK, gateway protocol, and background execution surfaces, or intentionally defer provider Batch API support?

Rationale: The request crosses public API, provider auth eligibility, model routing, session/transcript state, delivery timing, fallback behavior, accounting, and config/protocol surfaces, so automation cannot choose the permanent contract safely.

Likely owner: steipete

Owner reason: steipete has the strongest combined history across the provider runtime and isolated cron execution boundaries that need the first design decision.

Owner confidence: high

Options:

- **Design generic delayed turns (recommended):** Add the provider-neutral lifecycle first, then implement OpenAI and Anthropic Batch API support through that seam for cron, sessions, subagents, and heartbeat.
- **Limit to a cron shortcut:** Implement a narrower cron/provider flag faster, accepting higher migration and behavior-drift risk across other background surfaces.
- **Defer Batch API support:** Keep current real-time execution as the supported behavior and document why provider Batch APIs are out of scope for now.

## Risks / Open Questions

## Summary

Keep open. Current main still lacks first-class provider Batch API routing for delayed/background agent turns, and the issue remains the canonical tracker for a product/API design rather than a fixed or safely queueable repair.

## What This Changes

Request batch/delayed provider API support for non-real-time background agent turns such as cron, subagents, and heartbeat work.

## Best Possible Solution

Define an additive delayed/batch agent-turn contract in provider runtime and the Plugin SDK, then expose explicit opt-ins for cron, sessions_send, sessions_spawn/subagents, and heartbeat/background runs with provider implementations, docs, accounting, cancellation, fallback, and delayed delivery semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic delayed/batch agent-turn contract across provider runtime, Plugin SDK, gateway protocol, and background execution surfaces, or intentionally defer Batch API support?

Rationale: The request is useful but crosses public API, provider auth eligibility, session/transcript state, delivery timing, fallback behavior, and config/protocol surfaces, so automation cannot choose the permanent contract safely.

Likely owner: steipete

Owner reason: steipete has the strongest combined history across provider runtime and isolated cron execution, which are the first design boundaries to settle.

Owner confidence: high

Options:

- **Design generic delayed turns (recommended):** Add a provider-neutral delayed-turn lifecycle first, then implement OpenAI and Anthropic Batch API support through that seam for cron, sessions, subagents, and heartbeat.
- **Limit to cron/provider shortcut:** Implement a narrower provider-local cron flag faster, accepting higher risk of inconsistent behavior and later migration work.
- **Defer the feature:** Keep current real-time execution as the supported behavior and document why provider Batch APIs are not in scope yet.

## Solution Assessment

Unclear until maintainer design: the useful direction is a generic delayed-turn contract, but a provider-local cron flag would be too narrow for the requested cron, sessions, subagent, heartbeat, provider, and delivery surfaces.

## Summary

Keep open. Current main and v2026.6.11 still lack first-class delayed/provider Batch API routing for background agent turns, and the issue discussion already treats this as the canonical product/API tracker rather than stale cleanup.

## What This Changes

Add opt-in provider Batch API routing for non-real-time background agent turns such as cron jobs, subagents, heartbeats, and scheduled maintenance.

## Best Possible Solution

Define one additive delayed/batch agent-turn contract in provider runtime and the Plugin SDK, then expose explicit opt-ins for cron, sessions_send, sessions_spawn/subagents, and heartbeat/background runs with provider implementations, docs, accounting, cancellation, fallback, and delayed-delivery semantics.

Rationale: The request crosses public API shape, provider auth eligibility, session/transcript state, delivery timing, fallback behavior, config/protocol fields, and provider-specific implementations, so automation cannot safely choose the permanent contract.

Likely owner: steipete

Owner confidence: high

Options:

- **Design generic delayed turns (recommended):** Add a provider-neutral delayed-turn lifecycle first, then implement OpenAI and Anthropic Batch API support through that seam for cron, sessions, subagents, and heartbeat.
- **Limit to cron shortcut:** Implement a narrower cron flag faster, accepting higher risk of inconsistent provider behavior and later migration work.
- **Defer Batch API support:** Keep real-time execution as the supported agent-turn behavior and document why provider Batch APIs are out of scope for now.

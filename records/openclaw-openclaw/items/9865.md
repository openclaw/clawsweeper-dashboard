## Summary

Keep open as the canonical tracker. Current main still appears to use immediate, stream-oriented provider execution for agent turns; no verified delayed Batch API lifecycle exists for submitting, polling, cancelling, accounting for, and delivering a background agent result. The closed related reports are duplicates, while the open continuation-marker request is a separate input-buffering problem.

## What This Changes

Add opt-in provider Batch API support for latency-tolerant background agent work such as cron jobs, subagents, and heartbeats.

## System Context

OpenClaw routes scheduled and background work through cron and session callers into the agent and provider runtime, then returns results to sessions or channels. Batch processing would add a delayed execution lifecycle between provider submission and the existing delivery path.

## Architecture Diagram

flowchart LR
  A[Scheduled or background work] --> B[Cron and session callers]
  B --> C[Agent runtime]
  C --> D[Provider execution contract]
  D --> E[Immediate stream or delayed batch result]
  E --> F[Session and channel delivery]

## Best Possible Solution

Define one additive delayed-turn provider/runtime contract, prove it first for isolated cron agent turns with explicit delivery and cancellation semantics, then expand to other background callers only after that contract is stable.

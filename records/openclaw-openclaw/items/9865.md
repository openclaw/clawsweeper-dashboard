## Summary

Keep open. Current main still lacks provider Batch API or delayed agent-turn support, and this remains canonical product/API design work rather than stale cleanup or a safe one-shot repair.

## What This Changes

The issue requests opt-in Batch API routing for non-real-time background work such as cron jobs, subagents, and heartbeats to reduce provider costs.

## Best Possible Solution

Define an additive delayed/batch agent-turn contract in provider runtime and the Plugin SDK, then expose explicit opt-ins for cron, sessions_send, sessions_spawn/subagents, and heartbeat/background runs with provider implementations, docs, accounting, cancellation, fallback, and delayed delivery semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic delayed/batch agent-turn contract across provider runtime, Plugin SDK, gateway protocol, and background execution surfaces, or intentionally defer provider Batch API support?

Rationale: The request is useful but crosses public API, provider auth eligibility, session/transcript state, delivery timing, fallback behavior, config/protocol fields, and provider-specific implementations, so automation cannot safely choose the permanent contract.

Likely owner: steipete

Owner reason: steipete has the strongest combined history across the provider runtime and isolated cron execution boundaries that need the first design decision.

Owner confidence: high

Options:

- **Design generic delayed turns (recommended):** Add a provider-neutral delayed-turn lifecycle first, then implement OpenAI and Anthropic Batch API support through that seam for cron, sessions, subagents, and heartbeat.
- **Limit to cron/provider shortcut:** Implement a narrower cron flag faster, accepting higher risk of inconsistent provider behavior and later migration work.
- **Defer Batch API support:** Keep real-time execution as the supported agent-turn behavior and document why provider Batch APIs are out of scope for now.

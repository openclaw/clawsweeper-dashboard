## Summary

Keep open. Current main and v2026.6.11 still execute agent turns through immediate stream-oriented provider hooks; durable background-task tracking now exists, but no provider Batch API lifecycle or matching open implementation PR owns the remaining work. The feature is valid but requires maintainer product and public API design before implementation.

## What This Changes

Add opt-in provider Batch API execution for latency-tolerant cron, heartbeat, subagent, and other background agent turns.

## Best Possible Solution

Add one provider-neutral asynchronous turn lifecycle backed by the existing task registry, initially limited to isolated cron agentTurn jobs, with explicit capability checks and documented cancellation, fallback, accounting, tool-use, restart, and delivery semantics before considering subagents or heartbeats.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should provider Batch API turns become a first-class asynchronous task type, and should the initial supported caller be isolated cron only or every background entry point?

Rationale: Current task infrastructure can own persistence, but the provider lifecycle and agent-loop semantics remain immediate and stream-oriented; choosing the permanent contract, fallback behavior, and initial scope requires maintainer product and API intent.

Likely owner: steipete

Owner reason: Their merged history covers the provider plugin boundary, subagent invocation, and heartbeat runtime affected by the decision.

Owner confidence: high

Options:

- **Start with isolated cron (recommended):** Define a generic delayed provider-turn contract backed by tasks, prove it for isolated cron agentTurn jobs, then evaluate subagents and heartbeat separately.
- **Design every entry point:** Specify cron, sessions_send, sessions_spawn, subagents, and heartbeat together before implementation, accepting a substantially broader initial program.
- **Decline full-agent batching:** Keep provider Batch APIs outside the OpenClaw agent loop and support only external pure-prompt batch workflows.

## Reproduction Assessment

Not applicable: this requests a new capability rather than reporting broken established behavior; current-source and released-source inspection confirm the capability is absent.

## Solution Assessment

No, adding independent provider-specific batch flags across cron, subagents, and heartbeat is not the best solution. The narrower maintainable direction is one generic delayed-turn lifecycle integrated with durable tasks and initially proven through isolated cron.

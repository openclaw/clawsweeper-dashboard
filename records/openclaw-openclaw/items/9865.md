## Label Justifications

- `P2`: This is a meaningful cost and capacity improvement for background workloads, but established functionality is not currently broken.
- `impact:session-state`: Delayed jobs must resume against the correct run, session, subagent, and delivery target across long waits and process restarts.
- `impact:auth-provider`: Batch eligibility, credentials, model routing, accounting, and fallback differ across provider APIs and authentication modes.

## Summary

Current main still models provider inference as immediate streaming turns and cron as immediate isolated execution; it has no durable provider Batch API lifecycle. This remains the canonical request, but maintainers must choose the public delayed-turn contract and initial scope before implementation.

## What This Changes

Add opt-in provider Batch API execution for latency-tolerant cron, heartbeat, subagent, and other background agent turns.

## Best Possible Solution

Define an additive provider-neutral delayed-turn lifecycle in the runtime and public Plugin SDK, persist correlation and completion state canonically, then launch with one provider and one opt-in background surface before expanding it.

Options:

- **Shared delayed-turn contract (recommended):** Design submit, poll, cancel, resume, accounting, and result delivery once, then launch with one provider and cron agentTurn as the first consumer.
- **Cron-only provider experiment:** Implement a narrowly scoped cron/provider path first, accepting that later generalization may require migration or API redesign.
- **Defer batch execution:** Retain immediate streaming turns until the lifecycle complexity receives explicit roadmap sponsorship.

## Summary

Keep open. Current main and v2026.6.11 still lack first-class delayed/provider Batch API routing for background agent turns, and the live discussion treats this as the canonical product/API tracker rather than stale cleanup.

## What This Changes

Request support for opt-in provider Batch API execution for non-real-time background work such as cron jobs, subagents, heartbeats, and scheduled maintenance.

## Best Possible Solution

Define one additive delayed/batch agent-turn contract in provider runtime and the Plugin SDK, then expose explicit opt-ins for cron, sessions_send, sessions_spawn/subagents, and heartbeat/background runs with provider implementations, docs, accounting, cancellation, fallback, and delayed-delivery semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic delayed/batch agent-turn contract across provider runtime, Plugin SDK, gateway protocol, and background execution surfaces, or intentionally defer provider Batch API support?

Rationale: The request crosses public API, provider auth eligibility, session/transcript state, delivery timing, fallback behavior, config/protocol fields, and provider-specific implementations, so automation cannot safely choose the permanent contract.

Likely owner: steipete

Owner reason: steipete has the strongest combined history across provider runtime, Plugin SDK, isolated cron execution, and session-tool boundaries.

Owner confidence: high

Options:

- **Design Generic Delayed Turns (recommended):** Add a provider-neutral delayed-turn lifecycle first, then implement OpenAI and Anthropic Batch API support through that seam for cron, sessions, subagents, and heartbeat.
- **Limit To Cron Shortcut:** Implement a narrower cron flag faster, accepting higher risk of inconsistent provider behavior and later migration work.
- **Defer Batch API Support:** Keep real-time execution as the supported agent-turn behavior and document why provider Batch APIs are out of scope for now.

## Reproduction Assessment

Not applicable: this is a feature request rather than a broken existing behavior report. Source inspection confirms the requested delayed/batch contract and opt-in fields are absent on current main and v2026.6.11.

## Solution Assessment

Unclear until maintainer design. The maintainable direction is a generic delayed-turn provider/runtime contract; a provider-local cron flag would be too narrow for the requested cron, sessions, subagent, heartbeat, provider, and delivery surfaces.

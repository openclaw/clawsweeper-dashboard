## Summary

Keep open. Current main and the latest release still lack a provider Batch API or delayed agent-turn contract, and the existing discussion already treats this as the canonical product/API design tracker rather than a stale duplicate.

## What This Changes

Request support for provider Batch APIs for non-real-time background work such as cron jobs, heartbeats, scheduled maintenance, and subagents.

## Best Possible Solution

Define an additive delayed/batch agent-turn contract in the provider runtime and public Plugin SDK, then expose explicit opt-ins for cron, sessions_send, sessions_spawn/subagents, and heartbeat/background runs with provider implementations and documented accounting, cancellation, fallback, and delivery semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic delayed/batch agent-turn contract across provider runtime, Plugin SDK, gateway protocol, and background execution surfaces, or intentionally defer provider Batch API support?

Rationale: The request crosses public API, provider auth eligibility, session/transcript state, delivery timing, fallback behavior, config/protocol fields, and provider-specific implementations, so automation cannot safely choose the permanent contract.

Likely owner: steipete

Owner reason: steipete has the strongest combined history across the provider runtime and isolated cron execution boundaries that need the first design decision.

Owner confidence: high

Options:

- **Design generic delayed turns (recommended):** Add a provider-neutral delayed-turn lifecycle first, then implement OpenAI and Anthropic Batch API support through that seam for cron, sessions, subagents, and heartbeat.
- **Limit to cron provider shortcut:** Implement a narrower cron flag faster, accepting higher risk of inconsistent provider behavior and later migration work.
- **Defer Batch API support:** Keep real-time execution as the supported agent-turn behavior and document why provider Batch APIs remain out of scope for now.

## Reproduction Assessment

Not applicable: this is a feature request rather than a broken existing behavior report. Source inspection confirms the requested delayed/batch contract and opt-in fields are absent on current main and v2026.6.11.

## Solution Assessment

Unclear until maintainer design: the durable direction is a generic delayed-turn provider/runtime contract, while a provider-local cron flag would be too narrow for the requested cron, sessions, subagent, heartbeat, provider, and delivery surfaces.

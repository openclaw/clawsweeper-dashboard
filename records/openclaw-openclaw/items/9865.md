## Summary

Keep open. Current main and v2026.6.11 still lack a provider Batch API lifecycle for background agent turns, no newer PR owns the work, and implementation requires an explicit product/API decision rather than a narrow repair.

## What This Changes

Add opt-in provider Batch API execution for latency-tolerant background work such as cron, heartbeat, and subagent runs.

## Best Possible Solution

Define an additive generic delayed-turn provider and Plugin SDK lifecycle with durable run state, then expose a conservative cron-first opt-in with explicit cancellation, accounting, fallback, and delivery semantics before considering heartbeat, sessions, or subagents.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a first-class delayed agent-turn lifecycle for provider Batch APIs, and should explicit cron agentTurn jobs be the initial supported surface?

Rationale: Automation cannot safely choose the permanent public Plugin SDK contract, durable state model, eligible auth/provider modes, or cancellation, fallback, accounting, transcript, and delivery semantics.

Likely owner: steipete

Owner reason: steipete has the strongest combined provider/plugin-boundary history and has already participated directly in the issue’s product/API review.

Owner confidence: high

Options:

- **Design cron-first delayed turns (recommended):** Approve a generic provider lifecycle and durable state contract, initially exposing it only to explicitly latency-tolerant cron agentTurn jobs.
- **Design every background surface:** Cover cron, heartbeat, sessions, and subagents in the initial contract, accepting substantially larger implementation and compatibility scope.
- **Decline agent-loop batching:** Keep immediate provider turns as the only core execution mode and leave raw Batch API workflows outside OpenClaw’s tool-using agent loop.

## Reproduction Assessment

## Solution Assessment

No, adding only a per-job batch flag would not be the best solution. The narrowest maintainable path begins with a generic delayed provider lifecycle and durable run-state contract, followed by a cron-first opt-in.

## Summary

Current main still exposes provider inference as immediate streaming turns and cron as immediate isolated execution, while provider Batch APIs require a durable submit, poll, cancel, resume, accounting, and delivery lifecycle. This remains a useful canonical request, but maintainers must choose the public delayed-turn contract and initial scope before implementation.

## What This Changes

Add opt-in provider Batch API routing for latency-tolerant cron, subagent, heartbeat, and other background agent turns.

## Best Possible Solution

Define one additive delayed agent-turn lifecycle in core and the public Plugin SDK, then let provider plugins implement OpenAI and Anthropic batch transports while cron, sessions, subagents, and heartbeat share consistent persistence, cancellation, delivery, accounting, and fallback semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw sponsor a first-class delayed agent-turn contract, and if so should the initial product scope be cron-only or shared across cron, sessions, subagents, and heartbeat?

Rationale: The current stream contract cannot safely express multi-hour provider jobs, and choosing persistence, tool-loop, fallback, delivery, and public config semantics is a product/API decision rather than a mechanical repair.

Likely owner: steipete

Owner reason: The existing review and feature history connect this person most directly to the cross-cutting provider, cron, and runtime contract decision.

Owner confidence: high

Options:

- **Design shared delayed turns (recommended):** Introduce a provider-neutral delayed-turn lifecycle and initially wire cron, with other background surfaces adopting the same contract afterward.
- **Narrow to cron only:** Specify an intentionally cron-scoped batch contract first, accepting later migration work if sessions and heartbeat need a broader abstraction.
- **Do not add batch routing:** Keep synchronous agent turns as the product contract and direct users to external batch pipelines for stateless workloads.

## Solution Assessment

Unclear until maintainers choose the public contract. A shared provider-neutral delayed-turn lifecycle is safer than separate provider-specific flags or a cron-only transport shortcut.

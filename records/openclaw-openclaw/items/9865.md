## Summary

Keep open as the canonical tracker: the latest provided maintainer/Codex review on July 13, 2026 found no delayed Batch API lifecycle for agent turns, while the related batch-API reports were closed as duplicates rather than implemented fixes. The remaining work is a cross-cutting provider/runtime and public-contract decision, not a safe autonomous repair.

## What This Changes

Request first-class Batch API routing for delayed/background agent turns, including cron, subagents, sessions, and heartbeat work.

## Best Possible Solution

Maintain a single additive delayed-turn lifecycle in the provider/runtime and public Plugin SDK, then scope an initial opt-in surface—likely isolated cron agent turns—before extending it to sessions, subagents, or heartbeats.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw introduce a public delayed/batch agent-turn lifecycle, and should the first supported caller be isolated cron jobs only or a broader shared background-turn contract?

Rationale: Provider batch APIs are asynchronous and provider-specific, while the requested behavior crosses public Plugin SDK, protocol, state, delivery, cancellation, accounting, and authentication boundaries; code review cannot safely choose those permanent contracts.

Likely owner: steipete

Owner reason: The available history and the latest substantive review connect this person most directly to the provider/runtime and cron decision surface.

Owner confidence: high

Options:

- **Cron-first delayed-turn contract (recommended):** Define an additive SDK/runtime lifecycle and initially expose it only for isolated cron agentTurn jobs, with explicit completion, cancellation, delivery, and provider-eligibility semantics.
- **Shared background-turn contract:** Design one broader delayed-turn API for cron, sessions, subagents, and heartbeat callers before shipping any provider implementation.
- **Keep external for now:** Defer core support and document external provider batch workflows until a stable OpenClaw lifecycle contract is sponsored.

## Solution Assessment

No, a standalone provider or cron-only flag is not yet the best solution. The maintainable path is an additive delayed-turn contract first, then a deliberately scoped provider implementation and caller opt-in.

## Label Justifications

- `P2`: The issue is a real Discord multi-account usability and command-routing problem with limited blast radius, not an emergency runtime outage.
- `impact:message-loss`: Duplicate slash commands can send a user's command to the wrong Discord app, where OpenClaw may reject it before the intended account sees it.
- `impact:ux-friction`: The Discord picker can show several indistinguishable copies of the same command, forcing users to manually pick the right app in normal multi-account use.
- `maturity:stable`: The affected Discord channel surface is scored M4 Stable in qa/maturity-scores.yaml.

## Summary

Keep open: current main and v2026.6.11 still register ordinary Discord native commands at the application/global command layer and enforce account/channel policy only when the command is invoked, so the requested command-picker visibility behavior remains unsolved.

## What This Changes

The issue requests a supported way for Discord slash-command visibility to match configured Discord account and channel routing in multi-account setups.

## Best Possible Solution

A maintainer-approved Discord plugin design should derive command visibility from existing account/guild/channel routing where Discord supports it, document propagation and fallback behavior, and keep execution auth as the final enforcement layer.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which Discord command-visibility policy should OpenClaw support for multi-account setups?

Rationale: Current source confirms execution-only auth, but syncing app command permissions, adding explicit reconcile/config controls, guild-scoped deployment, and namespacing have different Discord API, upgrade, and operator-control tradeoffs.

Likely owner: Vincent Koc

Owner reason: Recent history routes through Vincent Koc on the current Discord deploy and release surface, which is the central code path for this decision.

Owner confidence: medium

Options:

- **Derive Visibility From Routing (recommended):** Use existing Discord account/guild/channel routing as the desired command-visibility source after validating Discord permission semantics and propagation behavior.
- **Add Explicit Operator Controls:** Add a CLI or config-controlled reconciliation path so operators choose which accounts expose generic commands and when Discord permissions are rewritten.
- **Document Manual Discord Setup:** Keep OpenClaw execution auth as-is and document manual Discord app permission setup as the supported multi-account visibility workflow.

## Reproduction Assessment

Yes, at source level: current main builds ordinary native commands without guildIds, reconciles them globally per Discord application, and docs say commands may remain visible to unauthorized users. I did not run a live Discord UI reproduction.

## Solution Assessment

No automatic fix is clearly best yet. The maintainable path needs a maintainer-approved Discord command visibility policy because permission syncing, guild-scoped deployment, explicit controls, and namespacing carry different upgrade and operator tradeoffs.

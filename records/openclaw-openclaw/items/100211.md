## Label Justifications

- `P2`: This is a real Discord multi-account usability and command-routing problem with limited blast radius, not an emergency runtime outage.
- `impact:message-loss`: Duplicate slash commands can send a user's command to the wrong Discord app, where OpenClaw may reject it before the intended account sees it.
- `impact:ux-friction`: The Discord picker can show several indistinguishable copies of the same command, forcing users to manually pick the right app in normal multi-account use.
- `maturity:stable`: The affected Discord channel surface is in the M4 Stable maturity shortlist.

## Summary

Keep open: current main and v2026.6.11 still register Discord native commands as application/global command sets and only enforce OpenClaw account/channel policy at execution time, so the requested channel-aware command visibility remains real and unsolved.

## What This Changes

The issue requests a supported way for Discord native slash-command visibility to match configured Discord account and channel routing in multi-account setups.

## Best Possible Solution

A maintainer-approved Discord plugin design should derive command visibility from existing account/guild/channel routing where Discord supports it, document propagation and fallback behavior, and keep execution auth as the final enforcement layer.

## Reproduction Assessment

Yes, at source level: current main deploys native commands as global application commands and docs acknowledge that unauthorized commands may still be visible in Discord. I did not run a live Discord UI reproduction in this read-only review.

## Solution Assessment

No automatic fix is clearly best yet. The maintainable solution needs a maintainer-approved Discord command visibility policy because syncing permissions, guild-scoped deployment, include/exclude rules, and namespacing have different upgrade and operator tradeoffs.

## Label Justifications

- `P2`: The issue is a real Discord multi-account usability and routing problem with limited blast radius, not an emergency runtime outage.
- `impact:message-loss`: Duplicate slash commands can route a user's selection to the wrong Discord app, where OpenClaw may reject it before the intended account sees the command.
- `impact:ux-friction`: The Discord picker can show several indistinguishable copies of the same command, forcing users to manually choose the right app in normal multi-account use.
- `maturity:stable`: The affected Discord channel surface is scored M4 Stable in qa/maturity-scores.yaml.

## Summary

Keep open: current main and v2026.6.11 still reconcile ordinary Discord native commands at the global application-command layer and enforce account/channel policy only after a slash command is selected, so the requested command-picker visibility behavior remains unsolved.

## What This Changes

The issue requests a supported Discord behavior that hides or scopes native slash commands according to configured account/guild/channel routing in multi-account setups.

## Best Possible Solution

A maintainer-approved Discord plugin design should derive command visibility from existing account/guild/channel routing where Discord supports it, document propagation and fallback behavior, and keep execution auth as the final enforcement layer.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which Discord native command visibility policy should OpenClaw support for multi-account setups where account/channel routing already exists?

Rationale: Current source confirms execution-only authorization, but permission syncing, guild-scoped deployment, explicit reconcile/config controls, and namespacing have different Discord API, upgrade, and operator-control tradeoffs.

Likely owner: steipete

Owner reason: The strongest recent history for Discord deploy behavior and the documented current visibility contract points to steipete.

Owner confidence: medium

Options:

- **Derive Visibility From Routing (recommended):** Use configured Discord account/guild/channel routing as the desired command-visibility source after validating Discord permission semantics and cache propagation behavior.
- **Add Explicit Operator Controls:** Provide a CLI or config-controlled reconciliation path so operators choose which accounts expose generic commands and when Discord permissions are rewritten.
- **Document Manual Discord Setup:** Keep OpenClaw execution auth unchanged and document manual Discord app permission setup as the supported multi-account visibility workflow.

## Reproduction Assessment

Yes, at source level: current main globally reconciles ordinary Discord native commands per application while enforcing account/channel policy only after an interaction is selected. I did not run a live Discord UI reproduction.

## Solution Assessment

Unclear until maintainers choose the product policy. The request is valid, but permission syncing, guild-scoped deploys, explicit CLI/config controls, and namespacing have different Discord API and operator tradeoffs.

## Label Justifications

- `P2`: The issue is a real Discord multi-account usability and command-routing problem with limited blast radius, not an emergency runtime outage.
- `impact:message-loss`: Duplicate slash commands can send a user's command to the wrong Discord app, where OpenClaw may reject it before the intended account sees it.
- `impact:ux-friction`: The Discord picker can show several indistinguishable copies of the same command, forcing users to manually pick the right app in normal multi-account use.
- `maturity:stable`: The affected Discord native-controls surface is under the Discord channel surface, which is scored M4 Stable in qa/maturity-scores.yaml.

## Summary

Keep open: current main and v2026.6.11 still deploy ordinary Discord native commands at the application/global layer and enforce account/channel policy only after a command is selected, so the requested command-picker visibility behavior remains unsolved and needs maintainer product direction.

## What This Changes

Request supported Discord native command visibility scoped to configured account/guild/channel routing so multi-account slash-command pickers do not show duplicate commands.

## Best Possible Solution

A maintainer-approved Discord plugin design should derive command visibility from existing account/guild/channel routing where Discord supports it, document propagation and fallback behavior, and keep invocation auth as the final enforcement layer.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which Discord command-visibility policy should OpenClaw support for multi-account setups?

Rationale: Current source confirms execution-only auth, but syncing Discord command permissions, adding explicit reconcile/config controls, guild-scoped deployment, and namespacing have different Discord API, upgrade, and operator-control tradeoffs.

Likely owner: vincentkoc

Owner reason: The current source and recent history most directly route through vincentkoc on Discord command deploy and native command access behavior.

Owner confidence: high

Options:

- **Derive visibility from routing (recommended):** Use existing Discord account/guild/channel routing as the desired command-visibility source after validating Discord permission semantics, propagation behavior, and cleanup behavior.
- **Add explicit operator controls:** Add a CLI or config-controlled reconciliation path so operators choose which accounts expose generic commands and when Discord permissions are rewritten.
- **Document manual setup:** Keep OpenClaw execution auth unchanged and document manual Discord app permission setup as the supported multi-account visibility workflow.

## Reproduction Assessment

Yes, at source level: current main builds ordinary Discord native commands without guildIds, reconciles them globally per application, and only checks account/channel policy at invocation time. I did not run a live Discord UI reproduction.

## Solution Assessment

No automatic fix is clearly best yet. The maintainable path needs a maintainer-approved Discord command visibility policy because permission syncing, guild-scoped deployment, explicit controls, and namespacing carry different upgrade and operator tradeoffs.

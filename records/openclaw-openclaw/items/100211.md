## Label Justifications

- `P2`: This is a real Discord multi-account usability and command-routing problem with limited blast radius, not an emergency runtime outage.
- `impact:message-loss`: Duplicate slash commands can send a user's command to the wrong Discord app, where OpenClaw may reject it before the intended account sees it.
- `impact:ux-friction`: The Discord picker can show several indistinguishable copies of the same command, forcing users to choose the right app manually.
- `maturity:stable`: The affected Discord channel surface is scored M4 Stable in qa/maturity-scores.yaml.

## Summary

Keep open: current main and the latest release still register ordinary Discord native commands at the application/global command layer while enforcing account/channel policy only after invocation, so the requested command-picker visibility behavior remains unsolved.

## What This Changes

The issue requests a supported Discord policy so native slash-command visibility matches multi-account guild/channel routing instead of showing duplicate commands from every installed OpenClaw Discord app.

## Best Possible Solution

A maintainer-approved Discord plugin design should derive command visibility from account/guild/channel routing where Discord supports it, document propagation and fallback behavior, and keep execution auth as the final enforcement layer.

Question: Which Discord command-visibility policy should OpenClaw support for multi-account setups where several Discord apps expose the same native commands?

Rationale: Source inspection confirms the gap, but permission syncing, guild-scoped deployment, namespacing, explicit reconcile commands, and documentation-only support have different Discord API, upgrade, propagation, and operator-control tradeoffs.

Likely owner: vincentkoc

Owner reason: Vincent Koc is the best available routing candidate from current blame on the Discord deploy/docs surface and recent related Discord command history.

Owner confidence: medium

Options:

- **Derive Visibility From Routing (recommended):** Use existing Discord account/guild/channel routing as the desired command-visibility source after validating Discord permission semantics and propagation behavior.
- **Add Explicit Operator Controls:** Add a CLI or config-controlled reconciliation path so operators choose which accounts expose generic commands and when OpenClaw rewrites Discord permissions.
- **Document Manual Discord Setup:** Keep OpenClaw execution auth as-is and document manual Discord application command permission setup as the supported multi-account visibility workflow.

## Reproduction Assessment

Yes, at source level: current main builds ordinary native commands without guildIds, reconciles them globally per Discord application, and docs say commands may remain visible to unauthorized users. I did not run a live Discord UI reproduction.

## Solution Assessment

No automatic fix is clearly best yet. The maintainable solution needs a maintainer-approved Discord command visibility policy because syncing permissions, guild-scoped deployment, include/exclude rules, and namespacing have different upgrade and operator tradeoffs.

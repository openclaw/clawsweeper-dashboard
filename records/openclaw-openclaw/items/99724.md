## Label Justifications

- `P2`: This is a normal-priority Gateway cron lifecycle bugfix with a concrete blocking edge case limited to on-exit watchers and cron hot reload.
- `merge-risk: 🚨 compatibility`: The PR changes hot-reload behavior for a supported cron.store configuration key and can break existing store-switch workflows with active watchers.
- `merge-risk: 🚨 session-state`: An in-flight watcher can be associated with a different rebuilt cron store and update or fire the wrong job state.

## Summary

Keep open: this is a useful candidate fix for the linked cron hot-reload bug, but the current patch still reuses in-flight watchers across a supported `cron.store` change, which can complete a watcher against the wrong cron store.

## What This Changes

The PR changes Gateway cron hot reload to stop only the scheduler, reuse the existing on-exit watcher manager across cron rebuilds, refresh watcher callbacks, and add focused regression tests.

## Best Possible Solution

Reuse the watcher manager only when the resolved cron store path is unchanged; cancel or shut down old watchers when the store changes, then merge after the focused regression test and existing proof stay clean.

## Reproduction Assessment

Yes. Source inspection shows `cron.store` is supported, all `cron.*` changes trigger cron restart, and the PR head always passes old `exitWatchers` into the rebuilt service whose handlers now write through the new cron service.

## Solution Assessment

No. Reusing the watcher manager is the right same-store fix, but the implementation needs a resolved store-path guard so watcher completion cannot cross from one cron store into another.

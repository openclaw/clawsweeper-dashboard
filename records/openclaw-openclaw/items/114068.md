## Summary

Keep this PR open: the performance approach is promising and has credible live CLI measurements, but the new probe duplicates config-directory resolution while omitting the supported `OPENCLAW_HOME` route. That can print precomputed root help even when the actual configuration under `OPENCLAW_HOME` changes plugin help. Likely related people: FelixIsaac (prior area contributor; medium confidence).

## What This Changes

This PR adds a conservative raw-config and dotenv pre-probe so static root CLI help can avoid loading full configuration when plugin-related settings cannot change the rendered help.

## System Context

Root CLI help first decides whether static precomputed output is safe; configuration, dotenv files, and plugin settings can instead require live help rendering. The proposed probe sits before the normal config snapshot read and determines whether the CLI takes the fast or compatibility-sensitive path.

## Architecture Diagram

flowchart LR
  A[User runs root help] --> B[Root help probe]
  B --> C[Environment and config location]
  C --> D[Raw config and dotenv scan]
  D --> E{Plugin settings affect help?}
  E -->|No| F[Print precomputed help]
  E -->|Yes or uncertain| G[Load live config snapshot]
  G --> H[Render config-sensitive help]

## Best Possible Solution

Keep one lightweight, shared config-location contract for both the probe and the live configuration reader, then add an `OPENCLAW_HOME` regression case proving plugin-sensitive help still takes the live path.

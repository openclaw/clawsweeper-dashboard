## Summary

Keep this issue open for release/security-owner review. The report provides a concrete, security-relevant mismatch for an immutable npm correction package, while current main’s release workflow now uses GitHub OIDC and npm provenance; neither fact establishes what produced the historical `2026.7.1-2` tarball or permits a truthful retrospective signature without the original release evidence.

## What This Changes

The issue requests a signed, machine-verifiable attestation for the immutable `openclaw@2026.7.1-2` root tarball after an independent clean rebuild from the identified source revision produced a different archive.

## System Context

OpenClaw’s npm release system builds and verifies a root-package tarball in a preflight lane, then promotes that prepared artifact through a gated publish lane. The resulting npm tarball is the installable CLI distribution, so its build identity affects downstream supply-chain verification.

## Best Possible Solution

Have the release owner audit the correction publish’s retained artifacts and publish a narrowly scoped signed attestation only if they establish the exact tarball; otherwise record that the historical build cannot be attested and ensure future correction releases use the current OIDC provenance path.

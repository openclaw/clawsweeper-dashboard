## Best Possible Solution

Full review comments:

- **[P1] Keep remote session URLs behind the tool allowlist:** `src/agents/tools/sessions-send-tool.ts:84-88`
  - body: The new remote path passes `peerOpts.gatewayUrl` directly to `callGateway`, while the helper also accepts raw `gatewayUrl`/`gatewayToken` tool params. That bypasses the current agent-tool allowlist for loopback or configured `gateway.remote.url`, so a model with this tool can direct operator-authenticated WebSocket traffic at arbitrary hosts instead of an approved peer target.
  - confidence: 0.96
- **[P1] Include idempotencyKey in remote spawn requests:** `src/agents/tools/sessions-spawn-tool.ts:165-169`
  - body: The remote `sessions_spawn` path calls the gateway `agent` method with `message`, `sessionKey` or `label`, and delivery metadata, but no `idempotencyKey`. `AgentParamsSchema` requires `idempotencyKey`, so cross-gateway spawns will be rejected as invalid params before the remote run starts.
  - confidence: 0.97
- **[P2] Require peer tokens or support tokenless peers explicitly:** `src/agents/tools/gateway-peer.ts:56-59`
  - body: The new helper returns a peer override even when `gatewayToken` is undefined, and the config/test examples advertise tokenless peers. Current `callGateway` treats explicit URLs as untrusted redirects and requires explicit credentials, so these tokenless peers fail locally instead of reaching a no-auth or Tailscale-auth remote gateway.
  - confidence: 0.9

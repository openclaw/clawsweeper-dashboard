## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.93

Full review comments:

- **[P1] Keep raw gateway URLs behind the tool allowlist:** `src/agents/tools/gateway-peer.ts:66-67`
  - body: The helper returns arbitrary `gatewayUrl` values directly to the new session-tool fast paths, bypassing the existing `resolveGatewayOptions` allowlist that rejects non-loopback/non-configured Gateway targets. That reopens raw model-supplied WebSocket routing from agent tools; keep cross-gateway routing to configured peers or extend the approved resolver instead of accepting arbitrary URLs here.
  - confidence: 0.93
- **[P1] Include idempotencyKey in remote spawn requests:** `src/agents/tools/sessions-spawn-tool.ts:167-179`
  - body: The remote branch calls the Gateway `agent` method without `idempotencyKey`, but `AgentParamsSchema` requires it and the server validates before running the agent. Any cross-gateway `sessions_spawn` call will be rejected as invalid params before the remote run starts.
  - confidence: 0.98
- **[P2] Align tokenless peer behavior with callGateway auth:** `src/agents/tools/gateway-peer.ts:59-62`
  - body: The helper allows configured peers to omit `token`, and the PR body includes that as supported, but both remote fast paths pass the peer URL as an explicit `callGateway` override. `callGateway` requires explicit credentials for URL overrides, so tokenless peers fail before the remote request is attempted; either require tokens in the peer contract or add an intentional no-auth path with tests.
  - confidence: 0.9
- **[P2] Preserve sessionKey and label exclusivity remotely:** `src/agents/tools/sessions-send-tool.ts:71-80`
  - body: The remote `sessions_send` branch only rejects the case where neither target is provided, so callers can pass both `sessionKey` and `label` and silently get `sessionKey`. The local path rejects that combination, and the remote path should keep the same guard to avoid routing to an unintended session.
  - confidence: 0.88
- **[P3] Validate peer URLs as URLs, not only prefixes:** `src/config/zod-schema.ts:813-818`
  - body: The new schema only checks that the string starts with `ws://` or `wss://`, so malformed values with the right prefix still pass config validation and fail later during connection. Use the same URL parsing constraints as the existing Gateway tool path so config errors surface early.
  - confidence: 0.78

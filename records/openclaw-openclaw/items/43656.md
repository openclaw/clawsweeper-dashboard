## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.95

Full review comments:

- **[P1] Keep remote gateway URLs behind the tool allowlist:** `src/agents/tools/sessions-send-tool.ts:98-100`
  - body: The new cross-gateway path passes `peerOpts.gatewayUrl` directly into `callGateway`, so a model can provide `gatewayUrl`/`gatewayToken` and open an operator-authenticated WebSocket to any ws(s) host. Existing agent-tool URL handling is intentionally limited to loopback or configured `gateway.remote.url`, so this bypasses the security boundary instead of extending it.
  - confidence: 0.94
- **[P1] Include idempotencyKey in remote spawn requests:** `src/agents/tools/sessions-spawn-tool.ts:167-179`
  - body: The remote `sessions_spawn` branch calls the gateway `agent` method without an `idempotencyKey`, but `AgentParamsSchema` requires it. Any cross-gateway spawn reaches the remote gateway as invalid params before the child run can start.
  - confidence: 0.98
- **[P2] Reject tokenless peers before calling the gateway:** `src/agents/tools/gateway-peer.ts:59-62`
  - body: The helper still returns configured peers with `gatewayToken: undefined`, while `callGateway` treats the explicit URL as an override and requires explicit credentials. A peer like the PR's `studio` example fails locally with `gateway url override requires explicit credentials`; either make tokens required for peers or route through a contract that supports auth-none peers.
  - confidence: 0.91
- **[P2] Preserve sessionKey and label exclusivity remotely:** `src/agents/tools/sessions-send-tool.ts:74-80`
  - body: The remote `sessions_send` branch only rejects the case where both selectors are absent, so calls that provide both silently prefer `sessionKey`; the local path rejects that combination. This can send a cross-gateway message to the wrong session instead of surfacing the same input error.
  - confidence: 0.88

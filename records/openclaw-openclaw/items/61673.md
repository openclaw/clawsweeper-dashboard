## Summary

Keep open. Current main and the latest release still expose only static Docker bind arrays; the requested per-session pre-container bind resolver remains missing and is security/product-sensitive rather than cleanup-closeable.

## What This Changes

Requests a host-side pre-container hook or script that computes Docker sandbox bind mounts per session from channel/user metadata.

## Best Possible Solution

Design a maintainer-approved pre-container sandbox policy seam that resolves per-session bind decisions before Docker creation, reuses static bind validation, and documents the security, audit, and upgrade contract.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a trusted pre-container sandbox policy seam for per-session bind mounts, and if so should it be core config, plugin SDK API, or another sandbox-policy layer?

Rationale: The request changes who can decide host filesystem exposure before container creation and introduces possible host-side execution/config surface, so automation cannot safely choose the trust and API boundary.

Likely owner: steipete

Owner reason: Most of the central sandbox bind precedence and validation history in this area traces to steipete-authored commits.

Owner confidence: high

Options:

- **Design a sandbox policy seam (recommended):** Keep the issue open and have a sandbox/security owner define a narrow pre-container policy contract before any implementation PR.
- **Limit to static binds:** Reject dynamic per-session bind mounts for now and keep operators on explicit agent configs plus existing static bind validation.
- **Move toward plugin SDK only:** Treat this as a plugin API extension request and avoid adding a core `resolveBinds` executable config field.

## Reproduction Assessment

Not applicable as a bug reproduction. Source inspection gives high confidence that current main and `v2026.6.11` only accept static Docker bind arrays, so the requested dynamic pre-container capability is absent by design.

## Solution Assessment

Unclear whether the proposed executable `resolveBinds` field is the best final API. A pre-container bind decision point is plausible, but host execution, plugin boundary, timeout, failure, audit, and validation contracts need maintainer security/product review first.

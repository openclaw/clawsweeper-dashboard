## What This Changes

The PR makes OpenAI subscription routes use the configured validated loopback Codex proxy and warms profile-scoped live model metadata so token-backed dynamic models can materialize through that route.

## System Context

OpenClaw’s model-route resolver converts configured provider settings and chosen authentication profiles into physical API routes. The OpenAI plugin then uses that route to discover account-visible models, materialize a runtime model, and send Gateway inference requests.

## Architecture Diagram

flowchart LR
  Config[OpenAI provider configuration] --> Routes[Model route resolver]
  Profile[Selected token or OAuth profile] --> Routes
  Routes --> Proxy[Validated loopback subscription route]
  Proxy --> Catalog[Account model catalog warm-up]
  Catalog --> Model[Dynamic model materialization]
  Model --> Gateway[Gateway inference request]

## Best Possible Solution

Approve the generic route-context extension only if it is the intended plugin SDK boundary, then merge with focused coverage proving API-key routing remains on Platform endpoints while token/OAuth proxy profiles retain strict loopback validation through discovery and inference.

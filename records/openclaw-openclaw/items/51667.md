## Summary

Keep open: current main and v2026.6.11 still route inbound audio through transcription/text media-understanding, and the closest open implementation PR remains unmerged, conflicting, and blocked on provider, content-contract, proof, and raw-media security questions.

## What This Changes

The issue requests an opt-in native audio path that sends inbound voice/audio directly to audio-capable models instead of always using speech-to-text transcription.

## Best Possible Solution

Define a capability-gated native audio media contract with typed content blocks, provider serialization, explicit raw-media egress policy, fallback behavior, payload limits, and session/audit metadata before repairing or replacing the open implementation PR.

## Reproduction Assessment

Yes, source-level. Current main routes audio through `transcribeAudio` and stores `audio.transcription` text in the session context, while normalized LLM message content supports text/images only.

## Solution Assessment

Unclear. The requested opt-in flag captures the user control, but the best implementation needs maintainer decisions on typed content contracts, provider routing, fallback behavior, raw-media egress, and transcript/audit semantics before code should be queued.

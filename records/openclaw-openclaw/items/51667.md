## Summary

Keep open: current main and v2026.6.11 still route inbound audio through transcription text, while the requested native audio path needs maintainer decisions on typed media content, provider routing, raw-media egress, fallback behavior, and transcript/audit semantics. The open related PR is only a candidate and is still blocked by proof and compatibility/security concerns.

## What This Changes

The issue requests an opt-in native audio path that sends inbound voice/audio media directly to audio-capable omni-modal models instead of forcing STT transcription first.

## Best Possible Solution

Define a maintainer-approved native media contract with typed audio content blocks, provider serialization, explicit raw-media egress policy, fallback behavior, and transcript/audit metadata, then converge the open implementation candidate or a replacement on that design.

## Reproduction Assessment

Yes, source-level. Current main routes audio through provider.transcribeAudio and records audio.transcription text, while the strict tools.media.audio schema has no native or fallbackToTranscription option.

## Solution Assessment

Unclear for implementation. The requested opt-in behavior is plausible, but the best fix needs maintainer decisions on typed content contracts, provider fallback/routing, raw-media egress, and transcript/audit semantics before code should be queued.

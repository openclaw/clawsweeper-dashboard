## Summary

Keep open. Two July 2026 reports describe current `v2026.7.1` sessions carrying automatic fallback provenance into later turns, including one direct Telegram turn that returned to a stale Ollama model and timed out without a visible reply. The originally linked fallback-probe change in https://github.com/openclaw/openclaw/pull/82676 established the intended recovery behavior, but the issue discussion supplies credible evidence that automatic session state can still defeat it. Likely related people: `steipete` is the strongest routing candidate from the original fallback-probe implementation; confidence is medium.

## What This Changes

Fix automatic model-fallback session state so it does not keep a chat pinned to a stale provider or model after the configured route becomes usable again.

## System Context

OpenClaw resolves an agent’s configured primary model and fallbacks for each conversation, then records session-scoped override state when an automatic fallback is selected. That state feeds subsequent agent turns and can affect provider routing, model selection, and channel replies.

## Architecture Diagram

flowchart LR
  A[Agent model configuration] --> B[Fallback candidate selection]
  B --> C[Automatic fallback result]
  C --> D[Session override provenance]
  D --> E[Next conversation turn]
  E --> F[Primary recovery probe]
  F --> G[Configured model or fallback reply]

## Best Possible Solution

Repair the canonical automatic-fallback write and recovery path so auto-created provenance is tied to the configured primary and stale automatic pins recover safely, while preserving explicit user-sourced session choices; add focused regression coverage for both paths.

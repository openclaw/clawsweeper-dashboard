## Summary

Keep open: current main and v2026.6.11 still lack a between-turn Talk idle timeout or public Talk idle-timeout config, and the related items do not supersede this narrower Voice Wake-started Talk lifecycle request.

## What This Changes

Request adds a configurable Talk idle timeout that auto-deactivates Voice Wake-started Talk sessions after inactivity.

## Best Possible Solution

Define one additive Talk idle-timeout contract, expose it through config, protocol, docs, and native clients, and implement Talk so inactive sessions return to wake-word waiting without changing silenceTimeoutMs transcript-finalization semantics.

Options:

- **Approve additive Talk idle timeout (recommended):** Add a canonical Talk config field with explicit units, bounds, disabled behavior, and reset events, then wire it through config, protocol, docs, and native Talk runtime.
- **Scope only to Voice Wake sessions:** Track activation source and auto-deactivate only sessions started by Voice Wake, leaving manually started Talk sessions unchanged.
- **Defer to broader voice lifecycle design:** Keep this open until maintainers design a larger Talk and Voice Wake lifecycle policy that also covers realtime and mobile behavior.

## Reproduction Assessment

Yes, at source level: Voice Wake can enable Talk Mode, but Talk only has transcript-finalization silence handling and resumes listening after replies or errors. I did not run a live macOS audio scenario in this read-only review.

## Solution Assessment

Unclear as an implementation choice: the requested behavior is useful and bounded, but maintainers still need to choose the durable config and lifecycle contract before implementation.

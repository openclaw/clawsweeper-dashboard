## Summary

Keep open: current main and v2026.6.11 still lack a between-turn Talk idle timeout or public Talk idle-timeout config, so this remains valid product work rather than cleanup-closeable stale noise.

## What This Changes

The issue requests a configurable idle timeout that automatically deactivates Talk Mode after Voice Wake starts it and the user stops interacting.

## Best Possible Solution

Approve one additive Talk idle-timeout contract, expose it through validated config and talk.config, document it publicly, and implement macOS Talk so inactive sessions return to wake-word waiting without changing silenceTimeoutMs semantics.

Owner confidence: high

Options:

- **Approve additive Talk idle timeout (recommended):** Add a canonical Talk config field with explicit units, bounds, disabled behavior, and reset events, then wire it through config, protocol, docs, and macOS runtime.
- **Scope only to Voice Wake sessions:** Track activation source and auto-deactivate only sessions started from Voice Wake, leaving manually started Talk sessions unchanged.
- **Defer to broader voice lifecycle design:** Keep the issue open until maintainers design a larger Talk and Voice Wake lifecycle policy that also covers realtime and mobile behavior.

## Reproduction Assessment

Yes, at source level: Voice Wake can enable Talk Mode, but Talk only has transcript-finalization silence handling and resumes listening after replies or errors. No live macOS audio run was performed in this read-only review.

## Solution Assessment

Unclear as an implementation choice: the requested behavior is useful and bounded, but maintainers still need to choose the durable config and lifecycle contract before implementation.

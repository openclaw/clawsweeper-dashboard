## Summary

Keep open. Current main and the latest release still have Voice Wake-to-Talk activation and intra-turn Talk silence handling, but no between-turn idle deactivation or public Talk idle-timeout config contract.

## What This Changes

Request a configurable Talk Mode idle timeout that deactivates a Voice Wake-started Talk session after user inactivity and returns to wake-word waiting.

## Best Possible Solution

Define one additive Talk idle-timeout contract, expose it through config and talk.config, document it publicly, and implement the macOS Talk lifecycle so inactive sessions return to wake-word waiting without changing silenceTimeoutMs semantics.

Options:

- **Approve additive Talk idle timeout (recommended):** Add a canonical Talk config field with explicit units, limits, disabled behavior, and reset events, then wire it through config, protocol, docs, and macOS runtime.
- **Scope to Voice Wake-started sessions only:** Track the activation source and auto-deactivate only sessions started from Voice Wake, leaving manually started Talk sessions unchanged.
- **Defer to broader voice lifecycle work:** Keep the issue open but wait for a larger Talk/Voice Wake lifecycle design that also covers realtime sessions and mobile behavior.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: Voice Wake can enable Talk Mode, but the Talk runtime only finalizes non-empty transcripts after silence and then resumes listening after replies or errors. No live macOS audio run was performed in this read-only review.

## Solution Assessment

Unclear as an implementation choice. The requested behavior is valid and bounded, but maintainers still need to choose the public config name, scope, units, default, limits, reset events, and disabled behavior before a fix PR should implement it.

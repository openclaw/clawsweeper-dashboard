## Summary

Keep open: current main and v2026.6.11 still lack a between-turn Talk idle timeout or public Talk idle-timeout config, so the Voice Wake-triggered Talk deactivation request remains valid product work that needs maintainer direction.

## What This Changes

The issue requests a configurable between-turn Talk idle timeout that deactivates Voice Wake-started Talk Mode after user inactivity.

## Best Possible Solution

Define one additive Talk idle-timeout contract, expose it through config and talk.config, document it publicly, and implement macOS Talk so inactive sessions return to wake-word waiting without changing silenceTimeoutMs semantics.

Rationale: The source gap is clear, but the fix adds public lifecycle and configuration behavior that could affect cross-platform Talk semantics, so automation should not choose the permanent contract alone.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve additive Talk idle timeout (recommended):** Add a canonical Talk config field with explicit units, bounds, disabled behavior, and reset events, then wire it through config, protocol, docs, and macOS runtime.
- **Scope only to Voice Wake sessions:** Track activation source and auto-deactivate only sessions started from Voice Wake, leaving manually started Talk sessions unchanged.
- **Defer to broader voice lifecycle design:** Keep this open until maintainers design a larger Talk and Voice Wake lifecycle policy that also covers realtime and mobile behavior.

## Reproduction Assessment

Yes, at source level: Voice Wake can enable Talk Mode, but Talk only has transcript-finalization silence handling and resumes listening after replies or errors. No live macOS audio run was performed in this read-only review.

## Solution Assessment

Unclear as an implementation choice: the requested behavior is useful and bounded, but maintainers still need to choose the durable config and lifecycle contract before implementation.

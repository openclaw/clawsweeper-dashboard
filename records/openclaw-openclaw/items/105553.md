## What This Changes

The PR adds a private Mattermost WebSocket options builder with a 30-second opening-handshake timeout and regression coverage showing stalled upgrades return control to the reconnect loop.

## Best Possible Solution

Keep the timeout plugin-local and use the upstream `ws` option, landing the fixed 30-second default only after the Mattermost owner confirms that this cutoff is preferable to an unbounded wait without adding another configuration surface.

## Reproduction Assessment

Yes at source level: current main creates the Mattermost `ws` client without an opening-handshake bound, so an accepted TCP connection that never upgrades leaves `connectOnce` pending. ## Solution Assessment

Yes, the plugin-owned `ws.handshakeTimeout` option is the narrowest maintainable fix and directly bounds the failing operation; a separate timer around the reconnect caller would duplicate dependency behavior and cover a broader phase than necessary. Only acceptance of the fixed 30-second policy remains a human choice.

## Summary

Keep open: current main and v2026.6.11 still do not expose broad private-network access for arbitrary `web_fetch` URLs, and the remaining work is a security-sensitive config/product decision rather than cleanup-close material.

## What This Changes

Request to add an explicit `web_fetch` config opt-in so trusted agents can fetch localhost, LAN, RFC1918, ULA, or other private-network URLs.

## Best Possible Solution

Define a maintainer-approved `web_fetch` SSRF policy surface with dangerous naming, hard metadata/link-local handling, redirect/cache/provider/audit coverage, docs, and focused tests before landing the core config change.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose broad private-network access for arbitrary `web_fetch` URLs, and if so should it be global, per-agent, hostname-scoped, or folded into the broader egress-policy design?

Rationale: The lower-level primitive exists, but exposing it changes an SSRF boundary and public config contract; automation cannot choose the metadata/link-local, redirect, cache, provider-fallback, authorization, and audit policy safely without maintainer security intent.

Likely owner: steipete

Owner reason: They are the visible policy reviewer on this issue and have the strongest recent history across the guarded-fetch, SSRF, and web_fetch runtime surfaces.

Owner confidence: high

Options:

- **Approve Scoped Dangerous SSRF Policy (recommended):** Land a nested `tools.web.fetch.ssrfPolicy` design, optionally per-agent, with explicit dangerous naming and hard security semantics for metadata/link-local, redirects, caches, provider fallback, docs, and audit output.
- **Keep Current Narrow Opt-Ins:** Leave current main as-is with only fake-IP proxy exceptions and document that arbitrary private-network `web_fetch` remains intentionally unsupported for now.
- **Fold Into Egress Policy:** Route this into the broader web-tool egress firewall work so private-network access, domain allowlists, and per-agent authorization are designed together.

## Reproduction Assessment

No bug reproduction is applicable; this is a feature/config request. Source inspection gives high confidence that current main and v2026.6.11 still lack a broad private-network `web_fetch` opt-in while the lower SSRF guard already has the primitive.

## Solution Assessment

Unclear as proposed: a bare top-level `allowPrivateNetwork` flag is no longer the best shape. The maintainable path likely belongs under an explicit `ssrfPolicy` contract with audit, redirect, cache, provider-fallback, and authorization semantics.

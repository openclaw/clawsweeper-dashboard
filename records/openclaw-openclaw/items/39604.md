## Summary

Keep open: current main and the latest release still do not expose broad private-network access for arbitrary `web_fetch` URLs, and the remaining work is a security-sensitive public config/API decision with open but unmerged implementation directions.

## What This Changes

The issue requests a default-off `tools.web.fetch.allowPrivateNetwork` config option so `web_fetch` can reach loopback, LAN, and other private-network URLs when explicitly enabled.

## Best Possible Solution

Define one maintainer-approved nested `tools.web.fetch.ssrfPolicy` contract with dangerous naming, default-off behavior, hard metadata/link-local policy, redirect/cache/provider/audit coverage, docs, and focused tests before landing core config changes.

Options:

- **Approve scoped nested SSRF policy (recommended):** Add a default-off `tools.web.fetch.ssrfPolicy` capability with explicit dangerous naming, metadata/link-local rules, cache isolation, redirect checks, audit output, docs, and regression tests.
- **Fold into broader egress design:** Pause this specific flag and resolve it through the broader web-tool allow/deny egress policy tracked at https://github.com/openclaw/openclaw/issues/39685 or the proxy-owned egress direction.
- **Keep arbitrary private fetch blocked:** Leave current main limited to narrow fake-IP/proxy opt-ins and document that arbitrary private-network `web_fetch` is intentionally unsupported for now.

## Reproduction Assessment

Yes at source level: current main's strict schema and runtime accept only the two narrow fake-IP SSRF flags, not broad private-network access for arbitrary `web_fetch` URLs. A live localhost fetch is not needed to prove the missing config contract.

## Solution Assessment

No as proposed: a bare top-level `allowPrivateNetwork` key is plausible but not the safest permanent shape. The maintainable path is a maintainer-approved nested SSRF policy with explicit security semantics and coverage for redirects, cache keys, audit output, and docs.

## Summary

Keep open: current main and the latest release still keep arbitrary `web_fetch` private-network access blocked, and the remaining request is a security-sensitive config/product decision rather than cleanup-close material.

## What This Changes

The issue asks for an opt-in `web_fetch` config key that lets arbitrary `web_fetch` URLs reach private/internal network addresses.

## Best Possible Solution

Decide the SSRF policy shape first, likely a default-off, audited per-agent `tools.web.fetch.ssrfPolicy` path with cache isolation, requester authorization, docs, and focused SSRF tests if maintainers accept the boundary.

Rationale: The code can already enforce private-network policy when passed through, but exposing it changes the SSRF trust boundary and requires a maintainer choice about authorization, metadata/link-local handling, redirects, and audit semantics.

- **Fold into broader egress policy:** Defer this issue until the network allow/deny or interactive-confirmation design decides the permanent SSRF control model.

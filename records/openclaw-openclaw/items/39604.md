## What This Changes

The issue requests an opt-in `tools.web.fetch.allowPrivateNetwork` configuration key so arbitrary `web_fetch` requests can reach private/internal network addresses.

## Best Possible Solution

Land a maintainer-approved `web_fetch` SSRF policy shape with restrictive defaults, explicit dangerous naming, audit visibility, cache separation by effective policy, docs, and tests for private hosts, redirects, metadata/link-local blocking, and narrow proxy/fake-IP exceptions.

Rationale: The lower-level guard can allow private networks, but exposing it through `web_fetch` changes a security boundary and public config surface; automation cannot choose the acceptable operator trust model or metadata/redirect policy.

Likely owner: steipete

Owner confidence: high

Options:

- **Prefer per-agent SSRF policy (recommended):** Continue from the maintainer draft direction so private-network access can be restricted to named trusted agents and surfaced in audit output.
- **Accept a global dangerous flag:** Expose a global `tools.web.fetch.ssrfPolicy.dangerouslyAllowPrivateNetwork` knob with strong docs and tests, accepting broader operator blast radius.
- **Decline broad opt-in for now:** Keep arbitrary `web_fetch` strict and steer users toward trusted proxies, provider-specific exact-origin trust, or future allowlist/confirmation work.

## Summary

Keep open: current main and the latest release still do not expose broad private-network access for arbitrary `web_fetch` URLs, and the remaining work is a security-sensitive public config/API decision with unmerged candidate PRs.

## What This Changes

The issue requests a default-off `tools.web.fetch.allowPrivateNetwork` or equivalent config surface so `web_fetch` can reach operator-trusted private, loopback, or internal network targets.

## Best Possible Solution

Define one maintainer-approved nested `tools.web.fetch.ssrfPolicy` contract with dangerous naming, default-off behavior, hard metadata/link-local policy, redirect/cache/provider/audit coverage, docs, and focused tests before landing core config changes.

Rationale: The lower-level primitive exists, but exposing it changes an SSRF boundary and public config contract; automation should not choose the security semantics, API shape, or authorization model.

Owner confidence: high

Options:

- **Approve scoped nested SSRF policy (recommended):** Add a default-off `tools.web.fetch.ssrfPolicy` capability with explicit dangerous naming, metadata/link-local rules, cache isolation, redirect checks, audit output, docs, and regression tests.
- **Fold into broader egress design:** Pause this specific flag and resolve it through the broader web-tool allow/deny egress policy tracked at https://github.com/openclaw/openclaw/issues/39685.
- **Keep arbitrary private fetch blocked:** Leave current main limited to narrow fake-IP/proxy opt-ins and document that arbitrary private-network `web_fetch` is intentionally unsupported for now.

## Reproduction Assessment

Not applicable as a strict bug reproduction, but yes at source level for the requested gap: current main's strict schema and runtime accept only the two narrow fake-IP SSRF flags, not broad private-network access.

## Solution Assessment

Unclear as proposed: a bare top-level `allowPrivateNetwork` flag is plausible but not the best current shape. The safer maintainable solution is a maintainer-approved nested SSRF policy with explicit security semantics.

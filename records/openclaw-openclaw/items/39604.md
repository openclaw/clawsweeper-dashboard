## Summary

Keep open: current main and v2026.6.11 still keep arbitrary `web_fetch` private-network access blocked, and the remaining work is a security-sensitive config/product decision rather than cleanup-close material.

## What This Changes

The issue requests an opt-in `tools.web.fetch.allowPrivateNetwork` config key so `web_fetch` can reach private/internal network addresses while keeping the default blocked.

## Best Possible Solution

Define one default-off nested `web_fetch` SSRF policy, preferably scoped by agent or trusted host, with explicit metadata/link-local, redirect, cache, audit, docs, and upgrade behavior.

## Reproduction Assessment

Yes. Source inspection is enough: current main has a strict `tools.web.fetch` schema without broad private-network keys and the runtime only passes narrow fake-IP SSRF flags to the guarded fetch path.

## Solution Assessment

Unclear as proposed. A simple top-level `allowPrivateNetwork` boolean is plausible, but the safer direction is a nested, scoped SSRF policy with explicit metadata, redirect, cache, audit, and requester-authorization semantics.

## Summary

Keep open: current main and the latest release still do not expose broad private-network access for arbitrary `web_fetch` URLs, and the remaining work is a security/product decision with an unmerged draft PR rather than a cleanup-close candidate.

## What This Changes

The issue requests an opt-in `tools.web.fetch.allowPrivateNetwork` setting so `web_fetch` can reach private or internal network addresses when explicitly enabled.

## Best Possible Solution

Keep this issue open until maintainers choose and land one default-off web_fetch SSRF policy contract with tests, docs, cache isolation, and explicit security semantics for metadata/link-local targets and redirects.

## Reproduction Assessment

Yes, at source level: current main rejects the requested broad private-network `web_fetch` config path and tests still assert private/internal targets are blocked by default. I did not run a live localhost fetch because the missing public config contract is visible in source, docs, tests, and the v2026.6.11 tag.

## Solution Assessment

No for the exact top-level key as proposed; the safer route is a maintainer-approved nested or per-agent SSRF policy that composes with existing fake-IP flags and documents metadata, redirect, cache, provider-fallback, and operator-trust semantics.

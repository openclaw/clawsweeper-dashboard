## Summary

Keep open: current main and v2026.6.11 still lack a broad private-network opt-in for arbitrary web_fetch URLs, and the remaining work is a security-sensitive product decision with active same-root implementation and policy candidates.

## What This Changes

Request an opt-in tools.web.fetch.allowPrivateNetwork configuration key so web_fetch can access localhost and private/internal network addresses when explicitly enabled.

## Best Possible Solution

Keep this as the canonical product/security thread until maintainers land or reject a default-off, audited web_fetch private-network policy with explicit metadata/link-local, redirect, cache, docs, and upgrade behavior.

Question: Should OpenClaw expose private-network access for arbitrary web_fetch URLs, and if so should the approved contract be global, per-agent, host-scoped, confirmation-based, or part of the broader egress-policy design?

Rationale: The lower-level SSRF primitive exists, but exposing it to a model-callable URL fetch tool changes the security boundary and public config contract; automation cannot safely choose metadata, link-local, redirect, cache, provider-fallback, and requester-authorization semantics without maintainer intent.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve a scoped SSRF policy (recommended):** Land a reviewed default-off policy, preferably nested and scoped to trusted agents or hosts, with metadata/link-local blocks, redirect/cache safety, audit visibility, docs, and focused tests.
- **Fold into broader egress controls:** Defer private-network access until the hostname allowlist and network access-control work define one coherent policy for web_fetch egress.
- **Keep arbitrary web_fetch strict:** Reject broad private-network access for arbitrary web_fetch and document supported alternatives such as trusted proxies, browser policy, or explicit plugin/tool integrations.

## Reproduction Assessment

Yes. Source inspection is enough: current main has a strict web_fetch config schema without broad private-network keys, and runWebFetch only passes narrow fake-IP SSRF flags to the guarded fetch path.

## Solution Assessment

Unclear. A simple boolean key is plausible, but current code, docs, and related PRs point toward a safer nested/scoped SSRF policy with explicit metadata, redirect, cache, audit, and requester-authorization semantics.

## Summary

Keep open: current main and the latest release still keep arbitrary `web_fetch` private/internal targets blocked, and the remaining work is a security-sensitive public config contract rather than cleanup-close material.

## What This Changes

The issue requests an explicit opt-in config key so `web_fetch` can reach private or internal network addresses when an operator enables it.

## Best Possible Solution

Define a maintainer-approved nested `tools.web.fetch.ssrfPolicy` contract with dangerous naming, hard-deny behavior, redirect/cache/provider-fallback/audit coverage, focused tests, and docs before landing the core config change.

Rationale: The source shows the lower-level SSRF primitive exists, but exposing it changes a model-directed network boundary and a public config contract; automation should not choose the metadata/link-local, authorization, redirect, and cache semantics.

Owner confidence: high

Options:

- **Approve Scoped SSRF Policy (recommended):** Land a narrowly documented nested `tools.web.fetch.ssrfPolicy` design that enables private-network access only with explicit operator intent and complete security coverage.
- **Keep Current Strict Default Only:** Leave arbitrary `web_fetch` private-network access unsupported for now and document the existing fake-IP/proxy-only exceptions.
- **Fold Into Egress Policy:** Route this through the broader web-tool egress firewall work so private-network access, allowlists, and per-agent authorization are designed together.

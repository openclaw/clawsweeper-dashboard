## Summary

Keep open: current main and v2026.6.11 still do not expose a broad private-network opt-in for arbitrary `web_fetch` URLs, and the remaining work is a security-sensitive config/API decision with unmerged, conflicting candidate PRs.

## What This Changes

The issue requests an opt-in `tools.web.fetch.allowPrivateNetwork` setting so `web_fetch` can access localhost and RFC1918/private-network targets while preserving the default SSRF block.

## Best Possible Solution

Define one maintainer-approved, default-off `web_fetch` SSRF policy surface with dangerous naming, hard metadata/link-local semantics, redirect/cache/provider/audit coverage, docs, and focused tests before landing the config change.

Rationale: The lower-level primitive exists, but exposing it changes an SSRF boundary and public config contract that automation should not choose without maintainer/security intent.

Options:

- **Approve nested SSRF policy (recommended):** Land a narrowly documented `tools.web.fetch.ssrfPolicy` design that can allow private-network access only with explicit operator intent plus metadata, redirect, cache, provider, and audit safeguards.
- **Keep only narrow fake-IP support:** Leave current main as-is and document that arbitrary private-network `web_fetch` remains intentionally unsupported for now.
- **Fold into broader egress policy:** Route this through the broader web-tool egress firewall design so private access, domain allowlists, and per-agent authorization are decided together.

## Label Justifications

- `P1`: The report describes a real channel workflow where provider failover cleanup can block subsequent user messages after a visible reply has already been sent.
- `impact:message-loss`: Follow-up Telegram messages can be delayed or effectively suppressed behind a session lane that remains occupied after reply delivery.
- `impact:session-state`: The failure mode is session-lane admission state diverging from visible reply completion.
- `impact:auth-provider`: The reported trigger is provider overload/auth-profile fallback and cleanup keeping the lane occupied.

## Summary

Keep open: current main still ties same-session lane ownership to embedded run settlement, while observed reply delivery is only recorded in reply-path state and does not release the command-queue session lane; related recovery PRs address stale or wedged lanes, not this delivery-handoff behavior.

## What This Changes

The issue requests releasing a Telegram/session lane after a visible reply is emitted during provider failover so subsequent inbound messages are not blocked.

## Best Possible Solution

Define and implement a maintainer-approved visible-delivery handoff that admits follow-up turns only after durable reply/transcript invariants are safe, then prove it with focused source tests and live Telegram/provider-failover proof.

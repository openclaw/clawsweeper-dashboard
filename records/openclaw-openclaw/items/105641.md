## Label Justifications

- `P2`: Gateway restarts can repeatedly strand local credential-bearing files, but the demonstrated blast radius is host-local and does not show an emergency remote exploit.
- `impact:security`: Rendered loopback authentication material can remain on disk after the gateway generation and run that owned it have ended.
- `maturity:stable`: The affected gateway-runtime feature is M4 Stable and explicitly covers Gateway Lifecycle and Security Controls.

## Summary

Current main and v2026.6.11 still rely on process-local cleanup for credential-bearing bundled MCP temp configs, so gateway death can strand them. Keep this issue open while the linked fix receives the requested real-host safety proof and is reviewed or replaced.

## What This Changes

Fix bundled MCP temporary directories that can retain rendered loopback credentials after a gateway restart or crash interrupts an in-flight CLI run.

## Best Possible Solution

Add fail-closed orphan reclamation outside the dead gateway's callback, and land it only after real restart proof shows orphan removal while preserving persistent sessions, concurrent gateways, the prepare-to-spawn grace period, and Windows command-line visibility.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes at source level: current main creates the credential-bearing directory and can reclaim it only through a callback in the gateway process, so gateway termination during an in-flight run leaves no OpenClaw cleanup path. The reporter also provides a controlled reproduction on v2026.6.11; this read-only review did not execute the service restart itself.

## Solution Assessment

Yes in direction: reclamation must run outside the terminated gateway's callback and remain liveness-aware. The linked startup sweep is the narrowest active candidate, but it should not land until real host proof validates its cross-platform process-visibility assumptions.

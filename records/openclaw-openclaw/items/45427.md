## Summary

Keep open. Current main and the latest release still keep resolved sender identity out of the trusted inbound metadata envelope, while the active alternatives are unmerged or closed-unmerged and the identity authority needs maintainer security/product approval.

## What This Changes

Add a trusted sender identity/name field to inbound metadata so agents can route messages without relying on untrusted conversational context.

## Best Possible Solution

Keep this as the canonical trusted inbound identity decision, then land one approved contract that exposes a stable provider ID or configured principal without trusting conversational display names and with focused prompt, channel, privacy, and routing tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What sender identity authority should OpenClaw expose as trusted inbound metadata: raw resolved display names, stable provider IDs, or configured principals such as session.identityLinks?

Rationale: The current code deliberately keeps human names and per-turn identifiers out of trusted system metadata, so adding model-visible sender identity changes a security and privacy boundary rather than filling a mechanical omission.

Likely owner: steipete

Owner reason: The history pass ties this person to the adjacent trusted/untrusted inbound prompt boundary decisions.

Owner confidence: high

Options:

- **Use Configured Principals (recommended):** Expose a trusted principal only when a stable provider ID matches an operator-configured identity link, keeping raw display names in untrusted context.
- **Use Stable Provider IDs:** Expose stable provider IDs as trusted metadata and require agents or tools to resolve human-readable names outside the prompt contract.
- **Use Resolved Display Names:** Expose platform-resolved names directly, accepting higher privacy and spoofing-review burden for easier agent ergonomics.

## Reproduction Assessment

Yes, for the missing trusted metadata field: current main and v2026.6.11 exclude sender identity from the trusted system envelope and place sender id/name only in untrusted user context. The production misroute itself was not live-reproduced in this read-only review.

## Solution Assessment

Unclear. Adding a raw trusted display-name field is not obviously the safest fix; maintainers should choose a stable provider-ID or configured-principal contract that preserves privacy, cache stability, and routing correctness.

## Summary

Keep open. Current main and v2026.6.11 still keep sender identity out of the trusted inbound system metadata envelope, while the overlapping implementation candidates are unmerged and the sender authority/security contract remains unsettled.

## What This Changes

Request to add a trusted sender name or equivalent sender identity to the inbound metadata envelope so agents do not infer names from untrusted conversation context.

## Best Possible Solution

Keep this issue as the canonical security/product decision, then land one approved contract that exposes a stable provider ID or configured principal without trusting conversational display names, with focused prompt, channel, privacy, routing, and regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What identity authority should OpenClaw expose as trusted inbound sender metadata: platform-resolved display names, stable provider IDs, configured principals via session.identityLinks, or a broader SourceActor-style attribution contract?

Rationale: The current implementation intentionally keeps sender names and per-turn ids out of trusted system metadata, so adding sender identity changes a model-visible security/privacy/prompt-cache boundary rather than filling a purely mechanical field omission.

Likely owner: steipete

Owner reason: The strongest history signal for the trusted/untrusted prompt boundary and inbound context ownership points to steipete.

Owner confidence: high

Options:

- **Use Configured Principals (recommended):** Expose a trusted principal only when a stable provider ID matches an operator-configured identity link, keeping display names in untrusted context.
- **Use Stable Provider IDs:** Expose stable provider IDs as trusted metadata and require agents or tools to resolve human-readable names outside the prompt contract.
- **Use Resolved Display Names:** Expose platform-resolved names directly, accepting higher privacy and spoofing-review burden for easier agent ergonomics.

## Reproduction Assessment

Yes for the missing trusted metadata contract: current main and v2026.6.11 exclude sender identity from the trusted system envelope and place sender id/name in user-role untrusted context. The specific production misroute was not live-reproduced in this read-only review.

## Solution Assessment

Unclear. Adding a raw trusted display-name field is not obviously the safest fix; a stable provider-ID, configured-principal, or SourceActor-style contract needs maintainer security/product direction first.

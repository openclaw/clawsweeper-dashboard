## What This Changes

Request to add a platform-resolved trusted sender display-name or sender identity field to the inbound metadata envelope so agents do not infer recipients from untrusted conversation context.

## Best Possible Solution

Keep this issue as the canonical decision point and land one maintainer-approved contract that exposes a stable provider ID or configured principal in trusted metadata while keeping display names in untrusted context unless explicitly approved.

Question: What sender identity authority should OpenClaw expose as trusted inbound metadata: raw resolved display names, stable provider IDs, or configured principals such as session.identityLinks?

Rationale: Current code deliberately keeps human names and per-turn sender identifiers out of trusted system metadata, so adding a model-visible sender identity field changes a security and privacy boundary rather than filling a mechanical omission.

Likely owner: steipete

Owner reason: The history most strongly ties this person to the trusted/untrusted prompt boundary and adjacent sender-spoofing fixes.

Owner confidence: high

Options:

- **Use Configured Principals (recommended):** Expose a trusted principal only when a stable provider ID matches an operator-configured identity link, keeping raw display names in untrusted context.
- **Use Stable Provider IDs:** Expose stable provider IDs as trusted metadata and require agents or tools to resolve human-readable names outside the prompt contract.
- **Use Resolved Display Names:** Expose platform-resolved display names directly, accepting a higher privacy and spoofing-review burden for easier agent ergonomics.

## Reproduction Assessment

Yes for the missing trusted metadata field: current main excludes sender identity from the trusted system envelope and places sender id/name only in untrusted user context. The production misroute itself was not live-reproduced in this read-only review.

## Solution Assessment

Unclear. Adding a raw trusted display-name field is not obviously the safest fix; maintainers should choose a stable provider-ID or configured-principal contract that preserves privacy, cache stability, and routing correctness.

Question: Which sender identity fact should OpenClaw expose as trusted inbound metadata for agents: a raw platform display name, a stable provider ID, or a configured canonical principal such as session.identityLinks?

Rationale: The current code deliberately excludes human-readable names from trusted system metadata; changing that boundary affects spoofing resistance, privacy, prompt-cache stability, and message routing correctness.

Likely owner: steipete

Owner reason: The strongest history signal for the current trusted/untrusted metadata boundary is the sender-spoofing hardening commit in this area.

Owner confidence: medium

Options:

- **Use Configured Principal (recommended):** Expose only a canonical principal resolved from stable provider IDs through an operator-owned mapping such as session.identityLinks, while leaving display names in untrusted context.
- **Expose Raw Display Name:** Add a trusted sender display-name field from channel profile lookups, accepting the privacy and spoofing semantics as a product decision.
- **Defer To Chat Authorship Contract:** Pause this issue until the broader chat.send per-message author/provenance model defines a shared identity contract across gateway and channel ingress.

## Reproduction Assessment

Yes, for the missing trusted metadata field: current main excludes sender identity from the trusted system envelope and places sender id/name only in untrusted user context. The original production misrouting incident was not live-reproduced in this read-only review.

## Solution Assessment

Unclear. Adding a raw trusted display-name field is not obviously the safest fix; maintainers should choose a stable provider-ID or configured-principal contract that preserves privacy, cache stability, and routing correctness.

## Summary

Keep open. Current main and v2026.6.11 still exclude sender identity from the trusted inbound system envelope, while related implementation PRs are open/conflicting or closed unmerged, so this remains the canonical security/product decision point.

## What This Changes

The issue requests a trusted, platform-resolved sender display name or equivalent sender identity in inbound metadata so agents do not infer recipient identity from untrusted conversation context.

## Best Possible Solution

Keep this as the canonical issue until maintainers approve one trusted inbound identity contract, preferably a stable provider ID or configured principal that keeps display names out of the trusted prompt path unless explicitly accepted.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What sender identity authority should OpenClaw expose as trusted inbound metadata for agents: raw resolved display names, stable provider IDs, or configured principals such as session.identityLinks?

Rationale: Current code intentionally keeps human names and per-turn identifiers out of trusted system metadata, so adding this field changes a security, privacy, and prompt-cache boundary rather than filling a purely mechanical omission.

Likely owner: steipete

Owner reason: This handle has the strongest history signal on the trusted/untrusted inbound prompt boundary and is the best available owner for the security/product contract choice.

Owner confidence: high

Options:

- **Use Configured Principals (recommended):** Expose a trusted principal only when a stable provider ID matches an operator-configured identity link, keeping raw display names in untrusted context.
- **Use Stable Provider IDs:** Expose stable provider IDs as trusted metadata and require agents or tools to resolve human-readable names outside the prompt contract.
- **Use Resolved Display Names:** Expose platform-resolved names directly, accepting higher privacy and spoofing-review burden for easier agent ergonomics.

## Reproduction Assessment

Yes for the missing trusted metadata contract: current main and v2026.6.11 exclude sender identity from the trusted system envelope and put sender id/name in untrusted user context. The reported production DM misroute itself was not live-reproduced in this read-only review.

## Solution Assessment

Unclear. Adding a raw trusted display-name field is not obviously the safest fix; a stable provider-ID or configured-principal contract looks safer, but maintainers need to choose the authority boundary.

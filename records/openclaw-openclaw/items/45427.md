## Summary

Keep open. Current main and the latest release still do not expose a trusted sender name/principal in the inbound system metadata envelope, and the overlapping implementation attempts are either open and conflicting or closed unmerged, so this issue remains the canonical security/product decision point.

## What This Changes

Request to add a trusted sender name or equivalent identity field to inbound metadata so agents do not infer recipient identity from untrusted conversation context.

## Best Possible Solution

Keep this issue as the canonical trusted inbound identity decision, then land one approved contract that exposes a stable provider ID or configured principal without trusting conversational display names and with focused prompt, channel, privacy, and routing coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What sender identity authority should OpenClaw expose as trusted inbound metadata: raw resolved display names, stable provider IDs, or configured principals such as session.identityLinks?

Rationale: The current code intentionally keeps human names and per-turn identifiers out of trusted system metadata, so adding a model-visible sender identity field changes a security, privacy, and prompt-cache boundary rather than filling a purely mechanical omission.

Likely owner: steipete

Owner reason: The relevant history ties steipete to the trusted/untrusted prompt boundary and broader inbound context ownership.

Owner confidence: high

Options:

- **Use Configured Principals (recommended):** Expose a trusted principal only when a stable provider ID matches an operator-configured identity link, keeping raw display names in untrusted context.
- **Use Stable Provider IDs:** Expose stable provider IDs as trusted metadata and require agents or tools to resolve human-readable names outside the prompt contract.
- **Use Resolved Display Names:** Expose platform-resolved names directly, accepting higher privacy and spoofing-review burden for easier agent ergonomics.

## Reproduction Assessment

Yes for the missing trusted metadata contract: current main and v2026.6.11 exclude sender identity from the trusted system envelope and put sender id/name in untrusted user context. The production misroute itself was not live-reproduced in this read-only review.

## Solution Assessment

Unclear. Adding a raw trusted display-name field is not obviously the safest fix; a stable provider-ID or configured-principal contract looks safer, but maintainers need to choose the authority boundary.

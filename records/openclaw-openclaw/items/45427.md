## Summary

Keep open. Current main and the latest release still keep sender identity out of the trusted inbound system metadata envelope, and the related implementation work is open or closed-unmerged rather than a landed replacement.

## What This Changes

Request to add a trusted sender name or equivalent sender identity to inbound metadata so agents do not infer recipients from untrusted conversation context.

## Best Possible Solution

Keep this as the canonical security/product decision, then land one approved contract that exposes a stable provider ID or configured principal without trusting conversational display names, with prompt, channel, privacy, routing, and regression coverage.

Rationale: Current code intentionally keeps sender names and per-turn ids out of trusted system metadata, so adding this field changes a model-visible security, privacy, and prompt-cache boundary rather than filling a purely mechanical omission.

Options:

- **Use Configured Principals (recommended):** Expose a trusted principal only when a stable provider ID matches an operator-configured identity link, while keeping display names in untrusted context.
- **Use Stable Provider IDs:** Expose stable provider IDs as trusted metadata and require agents or tools to resolve human-readable names outside the prompt contract.
- **Use Resolved Display Names:** Expose platform-resolved display names directly, accepting the higher privacy and spoofing-review burden for easier agent ergonomics.

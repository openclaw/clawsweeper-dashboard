## Summary

Keep this issue open. The documented `/v1/responses` contract promises caller-provided function tools and structured `function_call` output, while Codex app-server dynamic tools require a bidirectional callback response; the native harness therefore needs an owner-approved delegation bridge rather than a cleanup close. ([docs.openclaw.ai](https://docs.openclaw.ai/nl/gateway/openresponses-http-api?utm_source=openai))

## What This Changes

Expose caller-provided `/v1/responses` function tools to the native Codex app-server harness and return their invocations as delegated client function calls.

## System Context

The Gateway translates OpenResponses HTTP requests into an agent attempt, carrying caller-owned function definitions for that turn. The native Codex harness then builds Codex app-server dynamic tools and must convert any selected client function back into the Gateway response without executing client-owned work locally.

## Architecture Diagram

flowchart LR
  A[OpenResponses client] --> B[Gateway request parser]
  B --> C[Agent attempt with client tools]
  C --> D[Native Codex harness]
  D --> E[Codex app-server dynamic tools]
  E --> F[Delegated client function call]
  F --> G[OpenResponses function_call output]

## Best Possible Solution

Define a plugin-owned Codex bridge that registers filtered client functions as ephemeral dynamic tools, records the invocation as `clientToolCalls`, and terminates or safely resolves the Codex turn without locally executing the caller-owned function; cover it with focused Gateway and Codex harness regressions.

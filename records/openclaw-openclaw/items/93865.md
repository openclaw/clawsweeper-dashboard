- **[P2] Bound the thread response before parsing it:** `extensions/mattermost/src/mattermost/client.ts:721`
  - body: `GET /posts/{id}/thread` defaults to returning every item, but this helper downloads and parses the full response before `historyLimit` is applied in the monitor. A long thread can therefore add an arbitrarily large allocation and delay to the inbound path despite the timeout. Pass a bounded `perPage` and direction derived from `historyLimit`, then restore chronological order before building history. This was present on the earlier reviewed head and is being raised late.
  - late: true
  - confidence: 0.98
- **[P2] Replace the accumulating compound-key set:** `extensions/mattermost/src/mattermost/monitor.ts:200-202`
  - body: Each new thread session permanently adds another `${historyKey}:${session}` entry, and every candidate recovery scans the entire process-lifetime set with `.some()`. Long-running gateways with many threads or resets therefore leak marker memory and make checks progressively more expensive. Keep one current marker per history key, including pending-adoption state. This was present on the earlier reviewed head and is being raised late.

## Summary

Keep open: current main and v2026.6.11 still expose one fixed `subagent` queue lane, and adding caller-selected lanes plus per-lane config is a product/API decision rather than conservative cleanup.

## What This Changes

The issue requests an additive `sessions_spawn.lane` parameter and per-lane subagent concurrency configuration for independent subagent workloads.

## Best Possible Solution

Define a maintainer-approved, additive `sessions_spawn.lane` contract that defaults to `subagent`, validates bounded lane names, forwards the lane through native and ACP paths, preserves the scalar default, and adds compatible per-lane caps with docs and regression tests.

- **Fold into scheduler design:** Keep this open while maintainers first settle per-agent caps, queue status, and lane observability as one concurrency model.
- **Keep one global lane:** Reject caller-selected lanes and improve capacity visibility or per-agent limits without exposing lane selection to agents.

## Reproduction Assessment

Yes, at source level: current main has no `sessions_spawn.lane` schema field and hard-codes both native and ACP dispatch to `subagent`. I did not run a live multi-lane workload because the requested input surface does not exist.

## Solution Assessment

Unclear until maintainers choose the public tool/config contract. The maintainable direction appears to be an additive, default-preserving lane parameter plus bounded per-lane caps that compose with adjacent concurrency and queue-visibility work.

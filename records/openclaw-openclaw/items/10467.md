## Summary

Keep open: current main and v2026.6.11 still expose `sessions_spawn` through one fixed `subagent` lane, while the requested caller-selected lanes and per-lane subagent concurrency would add new public tool/config semantics that need maintainer direction.

## What This Changes

The issue requests an optional `sessions_spawn.lane` parameter plus per-lane subagent concurrency configuration so independent subagent workloads can avoid one shared `subagent` queue.

## Best Possible Solution

Define a narrow additive scheduler contract: validated optional `sessions_spawn.lane`, default `subagent` compatibility, native and ACP forwarding, per-lane subagent concurrency config that preserves an aggregate safety cap, and matching docs plus regression tests.

## Reproduction Assessment

Yes, at source level: current main has no `lane` parameter in `sessions_spawn`, both native and ACP child dispatch hard-code the `subagent` lane, and config only exposes scalar `agents.defaults.subagents.maxConcurrent`. I did not run a live workload because the requested surface does not exist to exercise.

## Solution Assessment

Unclear until maintainers choose the public contract. The proposed lane parameter is plausible and fits the existing command queue, but lane naming, validation, per-lane config, and aggregate-cap behavior should be settled before implementation.

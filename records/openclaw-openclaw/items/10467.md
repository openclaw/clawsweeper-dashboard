## Summary

Keep this issue open: v2026.6.11 and current main still expose one global `subagent` lane and one scalar concurrency limit, while the remaining lane-identity, aggregate-budget, and configuration-precedence contract requires maintainer direction.

## What This Changes

Add selectable concurrency lanes to `sessions_spawn`, with compatible per-lane limits and the existing `subagent` lane as the default.

## Best Possible Solution

Provide predeclared, validated sub-agent lane IDs with per-lane caps beneath an aggregate sub-agent budget, preserve `subagent` and all existing defaults, and route both native and ACP spawns through the same resolver.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `sessions_spawn` select only operator-configured sub-agent lanes under an aggregate concurrency cap, or should OpenClaw keep one fixed global lane?

Rationale: The code change is bounded, but repository evidence cannot decide whether lane identity is trusted operator policy, an unrestricted model input, or better expressed through target-agent concurrency; that choice defines resource-exhaustion and compatibility behavior.

Likely owner: steipete

Owner reason: The feature and concurrency history most strongly connects this person to the public scheduling contract that needs a durable direction.

Owner confidence: high

Options:

- **Configured bounded lanes (recommended):** Add an optional lane selector that accepts only configured lane IDs, retains the existing default, and enforces both per-lane and aggregate sub-agent caps.
- **Target-agent limits only:** Address isolation through per-agent concurrency such as https://github.com/openclaw/openclaw/issues/8061, without introducing workload-class lane names.
- **Keep one global lane:** Retain the current scalar scheduler and document separate gateways or agent profiles as the isolation boundary.

## Reproduction Assessment

Yes at source level: current main and v2026.6.11 explicitly document one global `subagent` lane, expose only one scalar cap, and omit a lane parameter from `sessions_spawn`. No runtime experiment is needed to establish that capability gap.

## Solution Assessment

No, unrestricted arbitrary lane names are not the safest final design because they could bypass resource limits. A configured allowlist of lanes beneath an aggregate cap is the narrowest maintainable solution.

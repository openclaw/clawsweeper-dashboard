## Summary

Keep open: current main and the latest release still expose one fixed `subagent` queue lane for `sessions_spawn`, while this request adds a model-facing lane input and per-lane concurrency semantics that need maintainer API direction.

## What This Changes

Add an optional `sessions_spawn.lane` parameter plus per-lane subagent concurrency config so independent child-agent workloads can use separate queue lanes.

## Best Possible Solution

Define a maintainer-approved additive `sessions_spawn.lane` contract that defaults to `subagent`, validates bounded lane names, forwards the resolved lane through native and ACP spawn paths, preserves the current scalar default, and adds compatible per-lane caps with docs and regression tests.

Options:

- **Approve bounded additive lanes (recommended):** Add `sessions_spawn.lane` with a default `subagent` fallback, strict bounded lane names, compatible per-lane caps, and parity across native and ACP spawn paths.
- **Fold into scheduler design:** Keep this issue open while maintainers first settle per-agent caps, queue status, and lane observability as one concurrency model.
- **Keep one global lane:** Decline caller-selected lanes and instead improve capacity visibility or per-agent limits without exposing lane selection to agents.

## Reproduction Assessment

Yes, at source level: current main has no `sessions_spawn.lane` schema field and hard-codes both native and ACP dispatch to `subagent`. I did not run a live multi-lane workload because the requested input surface does not exist.

## Solution Assessment

Unclear until maintainers choose the public tool/config contract. The maintainable direction appears to be an additive, default-preserving lane parameter plus bounded per-lane caps that compose with adjacent concurrency and queue-visibility work.

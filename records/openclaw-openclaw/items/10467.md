## Summary

Keep open: the available source and issue-discussion evidence still describes one global `subagent` concurrency lane, while this request needs a new tool and configuration contract rather than a bug fix. The remaining decision is how to bound lane identity and concurrency so a caller-selected lane cannot bypass the intended aggregate resource budget.

## What This Changes

Add a `sessions_spawn` lane selector and configurable per-lane concurrency so independent sub-agent workflows do not all share the global `subagent` queue lane.

## Best Possible Solution

Define a bounded core sub-agent lane contract: retain `subagent` as the default, permit only configured/validated lane identifiers, enforce an aggregate sub-agent budget alongside per-lane caps, and forward the resolved lane consistently through native and ACP spawns with docs and regression coverage.

Rationale: This feature adds model-facing scheduling control and a new compatibility-sensitive configuration surface; the safe lane identity, precedence, and total-cap policy cannot be inferred mechanically from the existing single-lane behavior.

Likely owner: steipete

Owner confidence: high

Options:

- **Bounded configured lanes (recommended):** Add a validated `lane` selector that may reference only configured sub-agent lanes, preserves `subagent` by default, and retains an aggregate cap across all sub-agent work.
- **Keep one shared sub-agent pool:** Retain the existing scalar concurrency control and address priority or observability through separate scheduling work instead of exposing arbitrary lanes.
- **Use per-agent limits instead:** Prioritize per-agent concurrency policy so a selected target agent is constrained without introducing general-purpose caller-selected lanes.

## Reproduction Assessment

No high-confidence live reproduction was run. Source and the recent maintainer-side review identify a fixed global `subagent` scheduling path and scalar limit, which is sufficient to reproduce the missing capability from the current contract but not a runtime failure.

## Solution Assessment

No; accepting arbitrary caller-provided lane names would be too broad without an aggregate-cap and configuration-precedence contract. A predeclared, validated lane map with a preserved default is the safer maintainable direction.

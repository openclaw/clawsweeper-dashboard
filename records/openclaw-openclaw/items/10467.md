## Summary

Keep this issue open: current main still exposes one global sub-agent lane and scalar concurrency limit, while the active discussion shows real demand; implementation should wait for a maintainer decision on lane identity and aggregate resource limits.

## What This Changes

Add caller-selectable queue lanes to `sessions_spawn` with configurable per-lane concurrency and backward-compatible default behavior.

## Best Possible Solution

Add additive, configured sub-agent lane profiles that default to `subagent`, validate caller-selected names, apply consistently to native and ACP spawns, and enforce both per-lane limits and an aggregate sub-agent concurrency ceiling.

Options:

- **Configured lanes plus aggregate cap (recommended):** Allow only declared lane profiles, preserve `subagent` as the default, and enforce both each lane's limit and a total sub-agent limit.
- **Dynamic caller-created lanes:** Allow arbitrary lane names and accept the larger resource-governance, validation, and configuration-growth surface.
- **Keep one spawn lane:** Retain the global subagent lane and address isolation through per-agent limits, priorities, or queue visibility instead.

## Reproduction Assessment

Yes at source level: current main exposes no `sessions_spawn.lane`, describes one global subagent concurrency limit, and routes spawned work through the fixed subagent lane. A live saturation workload was not run for this review.

## Solution Assessment

No, not exactly as proposed: selectable lanes are plausible, but the design also needs a trusted lane namespace, consistent native/ACP semantics, and an aggregate resource ceiling to prevent concurrency-limit bypass.

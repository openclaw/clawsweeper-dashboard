## Summary

Keep open: current main still exposes one scalar subagent concurrency pool, while this request needs a new tool/configuration contract and a maintainer choice about how named lanes remain bounded by an aggregate resource budget.

## What This Changes

Add an optional `lane` argument to `sessions_spawn` and compatible per-lane concurrency configuration while preserving the existing `subagent` lane by default.

## Best Possible Solution

Adopt one bounded scheduling model: validate a caller-selected subagent lane, preserve `subagent` for existing callers, enforce an aggregate subagent ceiling alongside explicit lane caps, and carry the resolved lane through native and ACP paths with matching docs and regression coverage.

Question: Should spawned subagents receive caller-selected named lanes, and if so, what aggregate cap and lane-configuration policy prevents those lanes from bypassing the gateway's total subagent resource budget?

Rationale: The current implementation intentionally has one scalar subagent limit; choosing lane identity, defaulting, namespace ownership, per-lane limits, and aggregate enforcement defines a durable public tool and configuration contract.

Options:

- **Bounded named lanes (recommended):** Add a validated optional lane that defaults to `subagent`, with configured lane caps plus an aggregate subagent cap that continues to protect gateway resources.
- **Per-agent-only limits:** Keep one spawned-subagent lane and address isolation through target-agent concurrency controls rather than model-selected lanes.
- **Defer orchestration lanes:** Keep the scalar pool until a broader queue and scheduling design establishes shared limits and observability together.

## Solution Assessment

No, not as written: caller-selected lanes are plausible, but the proposal must also retain an aggregate subagent budget and define validation and precedence before it is the safest solution.

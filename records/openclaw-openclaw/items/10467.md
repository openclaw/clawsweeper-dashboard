## Label Justifications

- `impact:session-state`: The request concerns isolation, queue contention, and capacity management for concurrently running sub-agent sessions.

## Summary

Current main and the latest release still route both native and ACP sub-agent spawns through one fixed global `subagent` lane with one scalar concurrency cap, so the feature remains necessary; however, the durable lane ownership and configuration model requires maintainer product direction before implementation.

## What This Changes

Add caller-selectable sub-agent queue lanes and compatible per-lane concurrency controls to `sessions_spawn`.

## Best Possible Solution

Standardize one bounded sub-agent scheduling model across native and ACP runtimes, preserve the existing global lane as the compatibility default, and design lane ownership, capacity, validation, observability, reload behavior, and adjacent per-agent controls as one coherent contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose arbitrary caller-selected `sessions_spawn` lanes with per-lane configuration, or standardize bounded owner-derived isolation such as per-agent or per-parent lanes?

Rationale: The missing capability is proven, but lane naming authority and configuration semantics are permanent model-facing and operator-facing contracts that overlap other open concurrency proposals and cannot be selected safely from source behavior alone.

Likely owner: steipete

Owner reason: The original feature commits and current blamed implementation most strongly connect steipete to both spawn dispatch paths and the global concurrency contract.

Owner confidence: high

Options:

- **Bounded owner lanes (recommended):** Use per-agent or per-parent derived lanes with bounded capacity, retaining the current global lane as the compatibility default.
- **Caller-named lanes:** Expose a validated arbitrary `sessions_spawn.lane` value and an explicit per-lane concurrency map for advanced orchestration.
- **Fair single pool:** Retain one global sub-agent pool and address starvation through per-owner caps, fair scheduling, and queue visibility.

## Reproduction Assessment

Yes at source level: current main and v2026.6.11 both lack a lane input, dispatch native and ACP children on one fixed `subagent` lane, and expose one scalar concurrency cap. The reported production starvation severity was not independently reproduced live.

## Solution Assessment

Unclear: lane isolation is a plausible response to starvation, but arbitrary model-selected lanes are not yet proven better than bounded per-agent/per-parent isolation combined with fair scheduling and queue visibility.

## Label Justifications

- `P2`: The issue affects a bounded Telegram outbound media workflow with real user-visible attachment loss but does not crash or block the whole runtime.
- `impact:security`: Any fix that accepts additional absolute local media paths changes the host-local file-read and upload boundary.
- `impact:message-loss`: Blocked `MEDIA:` paths can prevent the intended Telegram attachment from being delivered to the user.
- `impact:ux-friction`: The current visible failure is generic, so users may need logs, docs, or CLI workarounds to understand why the attachment was dropped.

## Summary

Keep open: current main still has a security-sensitive Telegram `MEDIA:` policy/diagnostics gap where blocked host-local paths can be reduced to a generic media-failed reply, and broader root expansion needs maintainer/security direction rather than conservative cleanup closure.

## What This Changes

The issue asks OpenClaw to stop dropping Telegram `MEDIA:` attachments for absolute local paths outside managed roots, or clearly document and configure that root policy.

## Best Possible Solution

Keep `MEDIA:` reads tied to the file-read policy, add clear blocked-path feedback/docs for Telegram replies, and route persistent root expansion through https://github.com/openclaw/openclaw/issues/47002 or an approved `tools.fs.roots` design.

## Label Justifications

- `P1`: This PR targets a high-impact process lifecycle bug, and the current patch can terminate legitimate background agent work.
- `merge-risk: 🚨 compatibility`: The new default reconciliation behavior can change existing background exec behavior by cancelling runs that previously remained active.
- `merge-risk: 🚨 session-state`: The patch can drift between supervisor `sessionId` ownership and bash registry `ProcessSession.id`, mis-associating live session state.
- `merge-risk: 🚨 availability`: Misclassified sessions are actively cancelled, which can kill long-running background jobs and degrade runtime availability.

## Summary

Keep open: the in-process orphan-reconciliation idea is still relevant and is not implemented on current main, but this patch is not merge-ready because it can misclassify session-key-owned background runs as orphans and cancel legitimate work.

## What This Changes

The PR adds a `ProcessSupervisor.reconcileOrphans` API, calls it from exec and process-tool paths, adds a bash-session `hasSession` helper, and adds focused supervisor/process tests.

## Best Possible Solution

Keep the focused in-process reconciliation direction, but make ownership checks session-id/session-key aware, add keyed-run regression coverage, avoid closing the broader restart-loss issue unless durable reaping is included, and require real behavior proof before merge.

## Reproduction Assessment

Yes, source-reproducible. Current main stores bash sessions by generated `ProcessSession.id` while supervisor records can use `opts.sessionKey?.trim() || sessionId`; applying this PR's `hasSession` predicate makes keyed records look untracked.

## Solution Assessment

No. The supervisor layer is a plausible place for the mitigation, but the current ownership predicate is too narrow and the closing reference overclaims the broader restart-loss issue.

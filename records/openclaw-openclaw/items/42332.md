## Summary

Keep open: current main and the latest release still accept direct and mapped hook-agent deliveries with `200`/`runId`, and no same-session active-or-queued conflict policy is implemented. The related persistent-session and queued-webhook items overlap this surface but do not replace the requested webhook admission decision.

## What This Changes

Request to add a webhook same-session admission guard that returns `409 Conflict` when a delivery with the same resolved `sessionKey` is already active.

## Best Possible Solution

Define an explicit, compatibility-safe hook overlap policy at Gateway admission that covers active and queued same-session work while preserving idempotency replay and hook auth/prefix gates.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should hook-agent deliveries with the same resolved `sessionKey` be rejected, skipped, queued, or remain parallel by default, and should any `409` behavior be opt-in?

Rationale: The requested behavior changes an external webhook HTTP response contract and retry semantics, so automation cannot safely choose the default or compatibility policy without maintainer intent.

Likely owner: steipete

Owner reason: Peter has the strongest history signal for hook/session policy and prior product/security framing of this exact decision.

Owner confidence: medium

Options:

- **Add opt-in overlap policy (recommended):** Keep current accepted-by-default behavior and add documented reject, skip, or queue semantics that trusted hook mappings or callers can opt into.
- **Make 409 the default:** Reject same-session active deliveries by default, accepting that existing webhook integrations may need migration to avoid retry storms.
- **Fold into queued ingestion:** Treat this as part of the broader queued webhook design and do not add a separate 409 guard until that core queue policy is decided.

## Reproduction Assessment

Yes. Source inspection shows repeated direct or mapped hook-agent POSTs with the same resolved `sessionKey` and no shared idempotency key are accepted with `200`/`runId`, with no active-or-queued same-session `409` path.

## Solution Assessment

No for an unconditional default `409`. The safer solution is a maintainer-approved overlap policy that chooses reject, skip, queue, compatibility defaults, and active-plus-queued semantics before implementation.

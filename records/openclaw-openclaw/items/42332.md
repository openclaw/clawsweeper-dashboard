## Summary

Current main still lacks a caller-visible active-delivery guard for hook requests sharing a resolved sessionKey; related persistent-session and queued-webhook work overlaps but does not decide the requested 409/retry contract, so the item should stay open for maintainer API direction.

## What This Changes

Request a webhook delivery policy that returns HTTP 409 Conflict when another hook delivery with the same sessionKey is already active.

## Best Possible Solution

Add a maintainer-approved hook delivery overlap policy keyed by resolved dispatch sessionKey, preserving current default behavior unless explicitly configured, with tests for direct hooks, mapped hooks, idempotency replay, and active-run races.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should hook-agent deliveries with the same resolved sessionKey reject with 409, queue/serialize, or remain parallel by default, and should that behavior be opt-in per hook or mapping?

Rationale: The choice changes the public HTTP contract and retry behavior for existing webhook integrations and overlaps with broader persistent-session and queued-webhook designs.

Likely owner: steipete

Owner reason: The remaining decision is the public hook API/session policy shape, and steipete is the strongest product-boundary owner signal in the related review context.

Owner confidence: medium

Options:

- **Add opt-in overlap policy (recommended):** Introduce an explicit hook or mapping policy for same-sessionKey active deliveries while preserving current parallel acceptance by default.
- **Fold into queued webhooks:** Treat this as part of the queued webhook design so backlog and concurrency controls own the retry/serialization contract.
- **Use unconditional 409:** Make same-sessionKey active deliveries conflict everywhere, accepting a breaking change for current callers that rely on parallel 200/runId responses.

## Reproduction Assessment

Yes at source level: current direct and mapped hook handlers accept same-sessionKey deliveries unless the same idempotency key replays, and no active-run 409 path exists.

## Solution Assessment

Unclear: the requested 409 behavior is plausible, but an explicit opt-in overlap policy is safer than changing the default HTTP contract without maintainer approval.

## Summary

Keep open: current main still dedupes hook deliveries only by idempotency key and accepts direct or mapped hook-agent POSTs with 200/runId, while related persistent-session and queue work does not settle same-session overlap policy.

## What This Changes

The issue requests a sessionKey-based webhook admission guard that returns 409 Conflict when the same logical hook session already has active work.

## Best Possible Solution

Define a compatibility-safe hook overlap policy at gateway admission that covers active and queued same-session work while preserving idempotency replay and hook auth/sessionKey gates.

Rationale: The requested 409 response changes an external webhook response contract and retry semantics, so automation cannot safely choose the default compatibility and security policy without maintainer intent.

Owner confidence: medium

Options:

- **Opt-In Overlap Policy (recommended):** Preserve the current 200/runId default and add configured reject, skip, or queue semantics for trusted hook sessions with documented retry behavior.
- **Default 409 Conflict:** Reject same-session active hook deliveries by default, accepting that existing integrations may need migration to avoid retry loops.
- **Fold Into Queue Design:** Defer this item into the broader queued webhook ingestion design so durable backlog and concurrency semantics are decided together.

## Reproduction Assessment

Yes. Source inspection shows repeated direct or mapped hook-agent POSTs with the same resolved sessionKey and no shared idempotency key are accepted with 200/runId, with no active/queued same-session 409 path.

## Solution Assessment

No for an unconditional default 409; the safer path is a maintainer-approved overlap policy that chooses reject, skip, queue, compatibility defaults, and active-plus-queued semantics before implementation.

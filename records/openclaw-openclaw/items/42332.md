## Summary

Keep open: current main still accepts repeated direct and mapped hook-agent deliveries for the same resolved sessionKey with 200/runId, and related persistent-session or queue work does not settle the requested same-session overlap policy.

## What This Changes

Request adds a sessionKey-based webhook concurrency guard so callers can avoid overlapping hook-agent runs for the same logical session.

## Best Possible Solution

Define an explicit, compatibility-safe hook overlap policy at Gateway admission, keyed by resolved sessionKey and covering active plus queued work, while preserving current accepted-by-default behavior unless maintainers choose a breaking default.

Options:

- **Add Opt-In Overlap Policy (recommended):** Keep existing 200/default behavior and add a documented hook or mapping policy for reject, skip, or queue behavior keyed by resolved sessionKey.
- **Make 409 The Default:** Reject active same-session hook deliveries by default and accept that existing integrations may need migration to avoid retry storms.
- **Leave Locking To Callers:** Keep hook delivery accepted-by-default and document idempotency keys plus caller-managed locks as the supported overlap control.

## Reproduction Assessment

Yes. Source inspection shows repeated direct or mapped hook-agent POSTs with the same resolved sessionKey and no shared idempotency key are accepted with 200/runId before async session work admission can provide any caller-visible conflict.

## Solution Assessment

No for unconditional default 409. The best fix needs maintainer-approved overlap semantics for reject, skip, queue, compatibility defaults, and active-plus-queued coverage before implementation.

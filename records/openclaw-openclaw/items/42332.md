## Summary

Keep open: current main still lacks a caller-visible same-session active conflict guard for webhook deliveries, and the related persistent-session and queued-ingestion items overlap without deciding the requested 409/skip policy.

## What This Changes

Add a webhook delivery concurrency guard that returns 409 Conflict when a POST resolves to a sessionKey that already has an active turn.

## Best Possible Solution

Add a maintainer-approved hook delivery overlap policy using the resolved dispatch sessionKey, preserving current defaults unless explicitly changed, with tests for direct hooks, mapped hooks, idempotency replay, and active-run races.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should webhook deliveries with the same resolved sessionKey be rejected, queued, or left parallel by default, and should that behavior be opt-in per hook/mapping?

Rationale: This changes an external HTTP contract and retry semantics for existing webhook integrations, so automation should not choose the permanent 409 versus queue versus compatibility default policy.

Likely owner: steipete

Owner reason: The current hook/cron codepath blame and repository ownership trail make @steipete the best available owner for the compatibility and API-shape decision.

Owner confidence: medium

Options:

- **Opt-in overlap policy (recommended):** Add an explicit hook or mapping policy such as skip/queue/parallel while preserving today's default behavior for existing callers.
- **Unconditional 409 guard:** Implement the reporter's exact behavior for all same-session active hook deliveries, accepting the compatibility break for callers that currently expect 200/runId.
- **Fold into queued ingestion:** Defer the specific guard until the broader webhook queue design decides durable backlog, parallelism, and caller response semantics together.

## Reproduction Assessment

Yes, at source level: direct and mapped webhook deliveries with the same sessionKey can both pass the request handler and return 200/runId unless the same idempotency key replays. I did not run a live repro because this was a read-only cleanup review.

## Solution Assessment

Unclear: returning 409 is a plausible solution, but it is not clearly the safest default because it changes external webhook retry behavior. An explicit overlap policy that preserves current compatibility unless configured is the better maintainable direction pending maintainer approval.

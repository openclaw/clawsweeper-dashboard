## Summary

Keep open: current main and the latest release still accept direct and mapped hook-agent deliveries with `200` and a `runId`; the missing behavior is a public webhook overlap policy, not an implemented fix.

## What This Changes

Requested support for rejecting overlapping webhook deliveries with the same resolved `sessionKey` while a prior webhook-triggered turn is still active.

## Best Possible Solution

Define an explicit, compatibility-safe hook overlap policy at Gateway admission, keyed by the resolved `sessionKey`, covering active and queued work while preserving current accepted-by-default behavior unless maintainers intentionally choose a breaking default.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should same-session hook-agent deliveries be rejected with 409, skipped, queued, or left accepted by default, and should any non-parallel behavior be opt-in per hook or mapping?

Rationale: The source gap is clear, but the fix changes public webhook response semantics, retry behavior, and session-state policy, so automation should not choose reject/skip/queue/default compatibility without maintainer intent.

Likely owner: steipete

Owner reason: Peter has prior product-boundary history on webhook mappings and hook session behavior, while the unresolved choice is public Gateway API compatibility rather than a single-line code owner question.

Owner confidence: medium

Options:

- **Add Opt-In Overlap Policy (recommended):** Keep current accepted-by-default behavior and add a documented hook or mapping policy for reject, skip, or queue semantics keyed by the resolved `sessionKey`.
- **Make 409 The Default:** Reject active same-session hook deliveries by default and accept that existing webhook integrations may need migration to avoid retry storms.
- **Fold Into Webhook Queues:** Let the broader queued-webhook design own same-session concurrency, then narrow this issue after that design explicitly covers reject or skip behavior.

## Reproduction Assessment

Yes. Source inspection shows repeated direct or mapped hook-agent POSTs with the same resolved `sessionKey` and no shared idempotency key are accepted with `200`/`runId`; I did not run a live webhook scenario in this read-only review.

## Solution Assessment

No for unconditional default `409`. The maintainable solution needs a maintainer-approved overlap policy that covers reject, skip, queue, compatibility defaults, and active-plus-queued semantics before implementation.

## Summary

Keep open: current main and the latest release still return 200/runId for direct and mapped hook-agent deliveries, and the unresolved part is a webhook overlap policy choice rather than a completed implementation.

## What This Changes

Request to add an HTTP 409 concurrency guard for webhook deliveries when the same resolved sessionKey already has an active hook turn.

## Best Possible Solution

Define one hook overlap contract for direct and mapped hook-agent deliveries, then implement it with explicit compatibility and security defaults across source, tests, and docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should hook-agent deliveries with an already-active resolved sessionKey be rejected with 409, queued, serialized, or left parallel by default?

Rationale: The requested behavior changes an external webhook HTTP contract and overlaps with persistent-session and queued-webhook designs, so automation cannot safely choose the permanent API policy.

Likely owner: steipete

Owner reason: The decision is product/API policy across Gateway hook ingress and session-state safety, and Peter has prior routing signal in the related cleanup discussion.

Owner confidence: medium

Options:

- **Add Explicit 409 Guard (recommended):** Reject direct and mapped hook-agent deliveries when the resolved sessionKey is active, ideally behind a deliberate hook or mapping policy so existing callers keep current behavior.
- **Fold Into Queued Webhooks:** Let queued webhook ingestion own overlap control, backlog visibility, and per-queue parallelism instead of making immediate POSTs fail.
- **Keep Caller-Owned Locking:** Leave immediate hooks parallel and document that integrations should use idempotency keys, queues, or external locks until a broader design lands.

## Reproduction Assessment

Yes, at source level: direct and mapped hook-agent deliveries with the same resolved sessionKey can reach dispatchAgentHook and return 200/runId unless the same idempotency key replays. I did not run a live webhook because this was a read-only review.

## Solution Assessment

Unclear: returning 409 is plausible, but the safest maintainable fix likely needs an explicit overlap policy or queue contract so existing webhook callers are not silently broken.

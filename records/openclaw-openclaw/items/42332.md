## Summary

Keep open: current main and the latest release still accept direct and mapped hook-agent deliveries with `200` and a `runId`, and the remaining choice is public webhook overlap behavior rather than a completed implementation.

## What This Changes

The issue requests a sessionKey-based webhook delivery guard that returns `409 Conflict` when another delivery for the same logical session is already running.

## Best Possible Solution

Define an explicit, compatibility-safe hook overlap policy at Gateway admission, keyed by the resolved sessionKey and preserving current accepted-by-default behavior unless maintainers intentionally choose a breaking default.

Rationale: The source gap is clear, but the requested fix changes public webhook response semantics and retry behavior, so automation should not choose reject/skip/queue/default compatibility policy without maintainer intent.

Options:

- **Add Opt-In Overlap Policy (recommended):** Keep current accepted-by-default behavior and add a documented hook or mapping policy for reject, skip, or queue semantics keyed by the resolved sessionKey.
- **Make 409 The Default:** Reject active same-session hook deliveries by default and accept that existing webhook integrations may need migration to avoid retry storms.
- **Fold Into Webhook Queues:** Use the broader queued-webhook design to own same-session concurrency and close or narrow this issue after that design explicitly covers 409 or skip behavior.

## Reproduction Assessment

Yes. Source inspection shows repeated direct or mapped hook-agent POSTs with the same resolved sessionKey and no shared idempotency key are accepted with `200`/`runId`; I did not run a live webhook scenario in this read-only review.

## Solution Assessment

No for unconditional default `409`. The maintainable solution needs a maintainer-approved overlap policy that covers reject, skip, queue, compatibility defaults, and active-plus-queued semantics before implementation.

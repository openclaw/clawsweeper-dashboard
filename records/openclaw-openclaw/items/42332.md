## Label Justifications

- `P2`: The issue has source-reproducible operational impact for webhook-triggered agents, but no evidence of a core emergency outage or release-blocking first-run failure.
- `impact:session-state`: The requested guard is keyed by hook session identity and is meant to prevent overlapping work for the same logical session.

## Summary

Keep open: current main still accepts direct and mapped hook-agent deliveries with 200/runId and no caller-visible same-session active/queued conflict path; related persistent-session work overlaps the sessionKey surface but does not decide the requested webhook overlap policy.

## What This Changes

Request a sessionKey-based webhook delivery concurrency guard that returns 409 Conflict when a hook POST targets a session that already has active work.

## Best Possible Solution

Define an explicit, compatibility-safe hook overlap policy at gateway admission, likely opt-in, that covers active and queued same-session work while preserving idempotency replay and coordinating with persistent hook sessions.

## Reproduction Assessment

Yes. Source inspection shows repeated direct or mapped hook-agent POSTs with the same resolved sessionKey and no shared idempotency key are accepted with 200/runId, with no active/queued same-session 409 path.

## Solution Assessment

No for an unconditional default 409. The better path is a maintainer-approved overlap policy that chooses reject, skip, queue, compatibility defaults, and active-plus-queued semantics before implementation.

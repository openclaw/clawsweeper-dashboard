## Summary

Keep open: current main still returns 200/runId for direct and mapped hook-agent deliveries and does not expose the requested active-session 409 guard; the related persistent-session and queued-webhook items overlap but have not settled this HTTP overlap policy.

## What This Changes

Request to add a sessionKey-based webhook delivery guard so overlapping deliveries for an already-active resolved session can be skipped or rejected instead of starting another turn.

## Best Possible Solution

Add a maintainer-approved hook delivery overlap policy keyed by the resolved dispatch sessionKey, preserving current defaults unless explicitly changed, with coverage for direct hooks, mapped hooks, idempotency replay, active-run races, and docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should same-session webhook deliveries be rejected with 409, queued, serialized, or left parallel by default, and should that behavior be opt-in per hook or mapping?

Rationale: This changes an external HTTP webhook contract and retry semantics for existing integrations, so automation should not choose the permanent overlap policy.

Likely owner: steipete

Owner reason: This is a cross-cutting webhook/session compatibility decision, and Peter has adjacent hook and cron lifecycle history plus prior routing signal in related discussion.

Owner confidence: medium

Options:

- **Opt-in overlap policy (recommended):** Add an explicit hook or mapping policy such as skip, queue, or parallel while preserving today's default behavior for existing callers.
- **Unconditional 409 guard:** Implement the reporter's exact behavior for every same-session active hook delivery and accept the compatibility break for callers that currently expect 200/runId.
- **Fold into queued webhooks:** Defer this specific guard until the queued-webhook design chooses durable backlog, parallelism, and caller response semantics together.

## Reproduction Assessment

Yes, at source level: direct and mapped hook-agent deliveries with the same resolved sessionKey can reach dispatchAgentHook and return 200/runId unless the same idempotency key replays. I did not run a live repro because this was a read-only cleanup review.

## Solution Assessment

Unclear: returning 409 is plausible, but it is not clearly the safest default because it changes external webhook retry behavior. A compatibility-preserving overlap policy or queued-webhook design is the more maintainable direction.

## Summary

Keep open: current main still accepts direct and mapped hook-agent deliveries with 200/runId and only replay-dedupes when the caller supplies an idempotency key; related persistent-session and queued-ingestion work does not settle the requested same-session overlap policy.

## What This Changes

Request support for a sessionKey-based webhook delivery guard that returns 409 Conflict when another turn for the same sessionKey is already active.

## Best Possible Solution

Define an explicit compatibility-safe hook overlap policy at gateway admission, ideally opt-in at first, that covers active and queued same-session work while preserving idempotency replay and sessionKey prefix safety.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should hook-agent deliveries with the same resolved sessionKey be rejected, skipped, queued, or left parallel by default, and should a 409 conflict mode be opt-in?

Rationale: The requested guard changes the external webhook response contract and retry behavior, so automation should not choose the default or compatibility policy without maintainer intent.

Likely owner: steipete

Owner reason: Peter has the strongest recent session-lifecycle and hook-runtime history for this compatibility-sensitive product boundary.

Owner confidence: medium

Options:

- **Add opt-in overlap policy (recommended):** Keep current accepted-by-default behavior while allowing trusted hook mappings or direct hook calls to choose reject, skip, or queue semantics with documented retry behavior.
- **Make 409 the default:** Reject same-session active deliveries by default and require existing integrations to migrate if they depend on 200/runId acceptance.
- **Keep caller-managed locking:** Leave hook delivery admission unchanged and document idempotency keys plus client-side locks as the supported overlap control.

## Reproduction Assessment

Yes. Source inspection shows repeated direct or mapped hook-agent POSTs with the same resolved sessionKey and no shared idempotency key are accepted with 200/runId, with no active/queued same-session 409 path.

## Solution Assessment

No for an unconditional default 409. The better path is a maintainer-approved overlap policy that chooses reject, skip, queue, compatibility defaults, and active-plus-queued semantics before implementation.

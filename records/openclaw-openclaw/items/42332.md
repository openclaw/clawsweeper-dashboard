## Summary

Keep open: current main still accepts direct and mapped hook-agent deliveries with the same resolved sessionKey and returns 200/runId unless the idempotency replay key matches, so the requested active-session 409 guard is not implemented. The remaining work is a webhook HTTP-contract/product decision, not a safe automatic bug-fix lane.

## What This Changes

Request support for rejecting or otherwise guarding overlapping webhook agent deliveries keyed by the resolved sessionKey.

## Best Possible Solution

Define a maintainer-approved hook overlap policy keyed by the resolved dispatch sessionKey, preserving today's async 200 behavior by default unless maintainers intentionally choose a breaking default, with coverage for direct hooks, mapped hooks, idempotency replay, active-run races, and docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should same-session webhook deliveries be rejected with 409, queued, serialized, or left parallel by default, and should that behavior be opt-in per hook or mapping?

Rationale: This changes the external webhook HTTP contract and retry semantics for existing integrations, so automation should not choose the permanent overlap policy.

Likely owner: steipete

Owner reason: This is a cross-cutting webhook/session compatibility decision, and steipete has adjacent hook/session routing history plus explicit routing signal in the issue timeline.

Owner confidence: medium

Options:

- **Opt-in overlap policy (recommended):** Add an explicit hook or mapping policy such as skip, queue, or parallel while preserving today's default async behavior for existing callers.
- **Fold into queued webhooks:** Defer this specific guard until the queued-webhook design chooses durable backlog, parallelism, and caller response semantics together.
- **Unconditional 409 guard:** Implement the reporter's exact behavior for every same-session active hook delivery and accept the compatibility break for callers that currently expect 200/runId.

## Reproduction Assessment

Yes, source-reproducible: direct and mapped hook-agent deliveries with the same resolved sessionKey can reach dispatchAgentHook and return 200/runId unless the same idempotency key replays. I did not run a live webhook because this was a read-only cleanup review.

## Solution Assessment

Unclear: returning 409 is plausible, but it is not clearly the safest default because it changes external webhook retry behavior. A compatibility-preserving overlap policy or queued-webhook design is the more maintainable direction.

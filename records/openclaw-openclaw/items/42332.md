## Summary

Keep open: current main and the latest release still accept direct and mapped hook-agent deliveries with 200/runId and do not expose the requested same-session active 409 guard; related persistent-session and queued-webhook work overlaps but has not decided this HTTP overlap policy.

## What This Changes

The issue requests a sessionKey-based webhook delivery guard that returns 409 Conflict when a hook-agent turn for the same resolved sessionKey is already active.

## Best Possible Solution

Add a maintainer-approved hook delivery overlap policy keyed by the resolved dispatch sessionKey, preserving current defaults unless explicitly changed, with coverage for direct hooks, mapped hooks, idempotency replay, and active-run races.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should webhook deliveries with the same resolved sessionKey be rejected, queued, serialized, or left parallel by default, and should that behavior be opt-in per hook or mapping?

Rationale: This changes an external HTTP webhook contract and retry semantics for existing integrations, so automation should not choose the permanent 409 versus queue versus compatibility-default policy.

Likely owner: steipete

Owner reason: The decision is cross-cutting API/product compatibility, and Peter has both repository fallback ownership and earlier hook/cron runner history.

Owner confidence: medium

Options:

- **Opt-in overlap policy (recommended):** Add an explicit hook or mapping policy such as skip, queue, or parallel while preserving today's default behavior for existing callers.
- **Unconditional 409 guard:** Implement the reporter's exact behavior for every same-session active hook delivery and accept the compatibility break for callers that currently expect 200/runId.
- **Fold into webhook queues:** Defer this specific guard until the broader queued webhook design chooses durable backlog, parallelism, and caller response semantics together.

## Reproduction Assessment

Yes, at source level: direct and mapped hook-agent deliveries with the same sessionKey can both pass the request handler and return 200/runId unless the same idempotency key replays. I did not run a live repro because this was a read-only cleanup review.

## Solution Assessment

Unclear: returning 409 is a plausible solution, but it is not clearly the safest default because it changes external webhook retry behavior. A maintainer-approved overlap policy that preserves compatibility unless configured is the more maintainable direction.

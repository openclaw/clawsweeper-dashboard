## Summary

Keep open: current main still accepts direct and mapped hook-agent deliveries with 200/runId and no active-or-queued same-session conflict path, while related persistent-session and queued-ingestion work do not settle the requested admission policy.

## What This Changes

The issue requests a sessionKey-based concurrency guard so overlapping webhook deliveries for the same logical hook session can be rejected or skipped instead of starting duplicate agent turns.

## Best Possible Solution

Define an explicit, compatibility-safe hook overlap policy at Gateway admission that preserves existing defaults, idempotency replay, and hook auth/prefix gates, with opt-in reject/skip/queue semantics rather than an unconditional default 409.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should hook-agent deliveries with the same resolved sessionKey reject, skip, queue, or remain parallel by default, and should any 409 behavior be opt-in?

Rationale: The desired behavior changes externally observable webhook status codes, retry behavior, session-state admission, and security-sensitive liveness disclosure, so source inspection cannot choose the product contract safely.

Likely owner: steipete

Owner reason: The strongest history signal is around isolated cron/session-key routing and hook-agent session behavior, which is the policy surface this issue changes.

Owner confidence: medium

Options:

- **Add an opt-in overlap policy (recommended):** Preserve current 200/runId behavior by default and add an explicit mapping or request policy for reject, skip, or queue semantics after auth and session-key-prefix checks.
- **Fold this into queued webhook ingestion:** Use #100939/#100940 as the canonical design for durable backlog, concurrency, and inspection before adding a separate same-session 409 mode.
- **Make 409 the default:** Adopt the issue’s proposed non-2xx behavior for overlapping sessions and accept the compatibility and retry-contract migration burden.

## Reproduction Assessment

Yes, source inspection shows the direct and mapped hook-agent paths dispatch and return 200/runId without an active-or-queued same-session conflict branch; no live run was needed to establish that current-main behavior.

## Solution Assessment

No, an unconditional 409 is not clearly the best fix because it changes webhook retry semantics; the safer direction is a maintainer-approved overlap policy that keeps current defaults and offers explicit reject, skip, or queue behavior.

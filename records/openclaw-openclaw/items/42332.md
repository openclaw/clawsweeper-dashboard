## Summary

Keep open: current main and the latest release still accept direct and mapped hook-agent deliveries with 200/runId and do not expose a same-session active/queued 409 guard; related persistent-session and queue work overlaps but does not settle this webhook admission policy.

## What This Changes

Request to add a sessionKey-aware webhook concurrency guard so overlapping deliveries for the same hook session can be rejected or otherwise prevented.

## Best Possible Solution

Define an explicit, compatibility-safe hook overlap policy at Gateway admission that covers active and queued same-session work while preserving idempotency replay, hook auth, allowed session-key prefixes, and existing default behavior unless maintainers intentionally change it.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should hook-agent deliveries with the same resolved sessionKey be rejected, skipped, queued, or remain parallel by default, and should any 409 behavior be opt-in?

Rationale: The requested 409 changes an external webhook response contract and retry behavior, so automation cannot safely choose the compatibility and product policy.

Likely owner: steipete

Owner reason: Peter has the strongest product/security review signal for adjacent hook and session policy decisions.

Owner confidence: medium

Options:

- **Add opt-in overlap policy (recommended):** Keep current accepted-by-default behavior and let trusted direct hook calls or mappings opt into reject, skip, or queue semantics with documented retry behavior.
- **Make 409 the default:** Reject same-session active deliveries by default, accepting that existing webhook integrations may need migration to avoid retry storms.
- **Keep caller-managed locking:** Leave OpenClaw accepting hook deliveries and document idempotency keys plus client-side locks as the supported overlap control.

## Reproduction Assessment

Yes, source inspection is high confidence: repeated direct or mapped hook-agent POSTs with the same resolved sessionKey and no shared idempotency key are accepted with 200/runId, and the active-work tracking is not consulted before the HTTP response.

## Solution Assessment

No for an unconditional default 409. The safer solution is a maintainer-approved overlap policy that decides reject, skip, queue, compatibility defaults, and active-plus-queued semantics before implementation.

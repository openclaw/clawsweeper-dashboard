## Summary

Keep open: current main and the latest release still accept direct and mapped hook-agent deliveries with `200` and a `runId`; they only dedupe exact idempotency replays and do not implement the requested same-`sessionKey` active-delivery `409` guard.

## What This Changes

Request to add a `sessionKey`-keyed webhook concurrency guard so overlapping deliveries for the same hook session are rejected instead of launching duplicate LLM turns.

## Best Possible Solution

Choose an explicit hook overlap policy keyed by the resolved dispatch `sessionKey`, preferably opt-in per direct hook or mapping, with coverage for direct hooks, mapped hooks, idempotency replay, active-run races, security docs, and upgrade-safe defaults.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should same-session webhook deliveries be rejected with `409`, queued or serialized, or left parallel by default, and should that behavior be opt-in per hook or mapping?

Rationale: The source gap is clear, but the permanent overlap contract changes external HTTP retry semantics and session-state behavior for existing integrations, so automation should not choose it without maintainer intent.

Likely owner: steipete

Owner reason: The remaining blocker is product/security policy for hook overlap semantics, and steipete has the clearest adjacent Gateway and session-policy history among the likely owners.

Owner confidence: medium

Options:

- **Opt-in overlap policy (recommended):** Add an explicit hook or mapping policy such as skip, queue, or parallel while preserving today's default async acceptance for existing callers.
- **Unconditional 409 guard:** Implement the reporter's exact behavior for every same-session active hook delivery and accept the compatibility break for callers expecting `200`/`runId`.
- **Fold into queued webhooks:** Defer this guard until the queued-webhook design chooses durable backlog, per-queue parallelism, and caller response semantics together.

## Reproduction Assessment

Yes, at source level: direct and mapped hook-agent deliveries with the same resolved `sessionKey` can still reach `dispatchAgentHook` and return `200`/`runId` unless the same idempotency key replays. I did not run a live webhook scenario because this cleanup review is read-only.

## Solution Assessment

No for an unconditional `409` default: it is plausible but not clearly the safest external contract because it changes retry semantics. An explicit overlap policy or the queued-webhook design is the more maintainable direction.

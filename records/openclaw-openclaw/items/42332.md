## Summary

Keep open: current main still accepts direct and mapped hook-agent posts with the same resolved sessionKey, dedupes only exact idempotency replays, and has no active-session 409/queue/serialize admission policy; the remaining work is a public hook API/product decision, not a stale or already-implemented item.

## What This Changes

Add a sessionKey-based concurrency guard for webhook deliveries so overlapping hook-agent turns for the same session can be rejected or otherwise controlled.

## Best Possible Solution

Define an explicit hook overlap policy keyed by the resolved dispatch sessionKey, likely opt-in per direct hook and mapping, while preserving current async 200 behavior by default and coordinating it with queued-webhook semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should same-session hook-agent deliveries be rejected with 409, queued or serialized, or remain parallel by default, and should that policy be opt-in per direct hook and mapping?

Rationale: The source gap is clear, but the choice changes public HTTP retry semantics, session-state behavior, and security-sensitive hook routing, so automation should not choose the API contract.

Likely owner: steipete

Owner reason: The unresolved choice is a Gateway product/security policy decision, and prior related review comments route this exact decision through steipete.

Owner confidence: medium

Options:

- **Add explicit overlap policy (recommended):** Preserve current parallel async behavior by default and add a configured per-hook policy such as reject, queue, or parallel for trusted integrations.
- **Fold into queued webhooks:** Let the broader queued-webhook design own burst handling, backlog visibility, and concurrency controls before closing this narrower request.
- **Fail closed by default:** Return 409 for overlapping same-session deliveries by default and intentionally accept the compatibility cost for existing async webhook callers.

## Reproduction Assessment

Yes. Source inspection shows two distinct authenticated hook deliveries with the same resolved sessionKey and no matching idempotency replay both reach dispatchAgentHook and return 200/runId; I did not run a live webhook scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public overlap contract. The requested 409 behavior is plausible, but an explicit opt-in overlap policy or queued-webhook path is safer than changing the current async default unconditionally.

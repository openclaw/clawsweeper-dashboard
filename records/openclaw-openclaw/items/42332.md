## Summary

Keep open: current main and the latest release still accept direct and mapped hook-agent deliveries with `200`/`runId` and no active-session `409` guard; the related persistent-session and queued-webhook work overlaps but does not settle this HTTP overlap policy.

## What This Changes

Request sessionKey-scoped webhook overlap protection so a second delivery for an already-running hook session receives HTTP 409 instead of starting another agent turn.

## Best Possible Solution

Add a maintainer-approved, compatibility-preserving hook delivery overlap policy keyed by the resolved dispatch sessionKey, with coverage for direct hooks, mapped hooks, idempotency replay, active-run races, and docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should same-session webhook deliveries be rejected with 409, queued/serialized, or left parallel by default, and should any non-parallel behavior be opt-in per hook or mapping?

Rationale: This changes an external Gateway HTTP webhook contract and retry semantics for existing integrations, so automation should not choose the permanent overlap policy.

Likely owner: steipete

Owner reason: This is a cross-cutting Gateway hook/session compatibility decision, and steipete has adjacent hook-session and isolated-run history plus routing signal in the issue timeline.

Owner confidence: medium

Options:

- **Opt-in overlap policy (recommended):** Add an explicit hook or mapping policy such as `skip`, `queue`, or `parallel` while preserving today's default behavior for existing callers.
- **Unconditional 409 guard:** Implement the reporter's exact behavior for every same-session active hook delivery and accept the compatibility break for callers that currently expect `200`/`runId`.
- **Fold into queued webhooks:** Defer this specific guard until the queued-webhook design chooses durable backlog, parallelism, and caller response semantics together.

## Reproduction Assessment

Yes, source-level: direct and mapped hook-agent deliveries with the same resolved sessionKey can reach `dispatchAgentHook` and return `200`/`runId` unless the same idempotency key replays. I did not run a live repro because this was a read-only cleanup review.

## Solution Assessment

Unclear: returning 409 is plausible, but it is not clearly the safest default because it changes external webhook retry behavior. A compatibility-preserving overlap policy or queued-webhook design is the more maintainable direction.

## Summary

Keep open: current main still accepts distinct same-session hook deliveries, dedupes only exact idempotency replays, and returns 200/runId before the async agent run can observe any lifecycle conflict; choosing 409 versus queue/serialize/parallel remains a public hook API decision.

## What This Changes

Add a webhook delivery admission guard so a POST resolving to an already-active sessionKey returns 409 Conflict instead of starting another agent turn.

## Best Possible Solution

Add an explicit hook overlap policy keyed by the resolved dispatch sessionKey, likely opt-in per direct hook and mapping and coordinated with queued webhook design, while preserving the current async 200 default unless maintainers intentionally choose fail-closed behavior.

## Maintainer Decision

Question: Should hook-agent deliveries with the same resolved sessionKey reject with 409, queue/serialize, or remain parallel by default, and should that be configured per direct hook and mapping?

Rationale: This changes public HTTP retry semantics, session-state behavior, and security-sensitive hook routing, so source inspection can prove the gap but cannot choose the compatibility default.

Likely owner: steipete

Owner reason: The unresolved choice is Gateway API and session/security policy, and this handle appears in recent Gateway/session history and issue routing context.

Owner confidence: medium

Options:

- **Add explicit overlap policy (recommended):** Keep current async 200 behavior as the default and add a per-hook policy such as reject, queue, or parallel for trusted integrations.
- **Fold into queued webhooks:** Let the queued webhook design own burst handling, backlog visibility, and per-queue concurrency before closing this narrower request.
- **Fail closed by default:** Return 409 for overlapping same-session hook deliveries by default and accept the compatibility cost for existing async callers.

## Reproduction Assessment

Yes, source-level: direct and mapped hook-agent requests with the same resolved sessionKey and different or absent idempotency keys both reach dispatchAgentHook and return 200/runId. I did not run a live hook delivery repro in this read-only review.

## Solution Assessment

No, unconditional 409 is plausible but not clearly the best fix. A configured overlap policy or queued-webhook ownership is safer because it preserves existing async webhook callers while giving polling integrations a real guard.

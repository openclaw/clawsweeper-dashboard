## Summary

Keep open: current main still accepts direct and mapped hook-agent deliveries with 200/runId and does not expose the requested same-session active 409 guard; the remaining work is a maintainer decision about webhook overlap semantics rather than conservative cleanup.

## What This Changes

The issue requests a sessionKey-based webhook delivery guard that returns 409 Conflict when another run for the same hook session is already active.

## Best Possible Solution

Add a maintainer-approved hook delivery overlap policy keyed by the resolved dispatch sessionKey, preserving current defaults unless explicitly changed, with coverage for direct hooks, mapped hooks, idempotency replay, and active-run races.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should webhook deliveries with the same resolved sessionKey be rejected, queued, serialized, or left parallel by default, and should that behavior be opt-in per hook or mapping?

Rationale: The requested 409 changes an external HTTP webhook contract and retry semantics for existing integrations, while related persistent-session and queued-webhook work could choose a different same-session overlap policy.

Likely owner: steipete

Owner reason: This is a cross-cutting external API compatibility choice and steipete is the strongest available routing owner from prior hook/cron history and fallback ownership.

Owner confidence: medium

Options:

- **Opt-in overlap policy (recommended):** Add an explicit hook or mapping policy such as skip, queue, or parallel while preserving today's default behavior for existing callers.
- **Unconditional 409 guard:** Implement the reporter's exact fail-fast behavior for every same-session active hook delivery and accept the compatibility change.
- **Fold into webhook queues:** Defer this guard until queued webhook support decides durable backlog, parallelism, and caller response semantics together.

## Reproduction Assessment

Yes, at source level: direct and mapped hook-agent deliveries with the same sessionKey can both pass the request handler and return 200/runId unless the same idempotency key replays. I did not run a live repro because this was a read-only cleanup review.

## Solution Assessment

Unclear: returning 409 is a plausible solution, but it is not clearly the safest default because it changes external webhook retry behavior. A maintainer-approved overlap policy that preserves compatibility unless configured is the more maintainable direction.

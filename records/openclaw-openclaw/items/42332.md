## Summary

Keep open: current main still only dedupes exact idempotency replays and returns 200/runId for direct and mapped hook-agent posts with the same sessionKey; the requested overlap contract remains an explicit product/API decision.

## What This Changes

Request a sessionKey-based hook delivery admission guard that rejects or otherwise prevents overlapping webhook agent turns for the same resolved session key.

## Best Possible Solution

Choose an explicit hook overlap policy keyed by the resolved dispatch sessionKey, likely opt-in per direct hook and mapping, while preserving default async 200 behavior and existing hook auth/prefix/agent restrictions.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should same-session hook-agent deliveries be rejected with 409, queued or serialized, or remain parallel by default, and should that policy be opt-in per direct hook and mapping?

Rationale: The choice changes public HTTP retry semantics, session-state behavior, and security-sensitive hook routing, so automation should not choose it from source inspection alone.

Likely owner: steipete

Owner reason: The unresolved choice is a Gateway session/security policy decision rather than only a local hook dispatch implementation detail.

Owner confidence: medium

Options:

- **Add an explicit overlap policy (recommended):** Preserve current parallel async behavior by default and add a configured per-hook policy such as reject, queue, or parallel for trusted integrations.
- **Fold this into queued webhooks:** Make the broader queued webhook design own burst handling, backlog visibility, and concurrency controls before closing this narrower request.
- **Make same-session overlap fail closed:** Return 409 for overlapping deliveries by default and accept the compatibility cost for existing asynchronous webhook callers.

## Reproduction Assessment

Yes, source-level: two different deliveries with the same resolved sessionKey and no matching idempotency key both reach dispatchAgentHook and return 200/runId; no live run was performed.

## Solution Assessment

No, unconditional 409 is plausible but not clearly the best fix; an explicit overlap policy or the queued-webhook design is safer for existing callers.

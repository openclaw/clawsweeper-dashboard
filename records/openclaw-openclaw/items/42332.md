## Label Justifications

- `P2`: The issue has source-reproducible operational impact for webhook-triggered agents, but no evidence of a core emergency outage or first-run release blocker.
- `impact:session-state`: The requested guard is keyed by hook session identity and is meant to prevent overlapping work for the same logical session.

## Summary

Keep open: current main still accepts direct and mapped hook-agent POSTs with 200/runId after idempotency-key replay checks, and there is no same-session active or queued admission policy for returning 409 or otherwise suppressing overlap.

## What This Changes

Request support for a sessionKey-based webhook admission guard so recurring deliveries for an already-running hook session can be rejected or skipped instead of starting duplicate agent turns.

## Best Possible Solution

Define an explicit, compatibility-safe hook overlap policy at Gateway admission that covers active and queued same-session work, preserves idempotency replay, and coordinates with persistent hook sessions and queued webhook ingestion.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should hook-agent deliveries with the same resolved sessionKey be rejected, skipped, queued, or remain parallel by default, and should any 409 behavior be opt-in?

Rationale: The requested 409 changes an external webhook HTTP response contract and retry semantics, so automation cannot safely choose the compatibility, security, or default behavior without maintainer intent.

Likely owner: steipete

Owner reason: Peter has the clearest prior policy framing for the hook/session admission decision and appears in the current hook request-handler provenance.

Owner confidence: medium

Options:

- **Add Opt-In Overlap Policy (recommended):** Keep current accepted-by-default behavior, then let trusted hook mappings or direct hook calls opt into reject, skip, or queue semantics with documented retry behavior.
- **Make 409 The Default:** Reject same-session active deliveries by default and accept that existing webhook integrations may need migration to avoid retry storms.
- **Keep Caller-Managed Locking:** Leave OpenClaw accepting hook deliveries and document idempotency keys plus client-side locks as the supported overlap control.

## Reproduction Assessment

Yes. Source inspection shows repeated direct or mapped hook-agent POSTs with the same resolved sessionKey and no shared idempotency key are accepted with 200/runId, with no active-or-queued same-session 409 path.

## Solution Assessment

No for an unconditional default 409. The maintainable path is a maintainer-approved overlap policy that chooses reject, skip, queue, compatibility defaults, and active-plus-queued semantics before implementation.

## Summary

Keep open: current main still accepts direct and mapped hook-agent deliveries with `200/runId` and lacks a caller-visible same-session active/queued conflict policy; persistent-session work overlaps the `sessionKey` surface but does not decide webhook overlap behavior.

## What This Changes

The issue requests a webhook delivery guard that returns `409 Conflict` when another run for the same `sessionKey` is already active.

## Best Possible Solution

Define an explicit, compatibility-safe hook overlap policy at gateway admission that covers active and queued same-session work while preserving idempotency replay, hook auth, allowed agents, and `sessionKey` prefix restrictions.

## Maintainer Decision

Required: true

Question: Should hook-agent deliveries with the same resolved `sessionKey` be rejected, skipped, queued, or remain parallel by default, and should any `409` behavior be opt-in?

Rationale: The requested `409` behavior changes an external webhook response contract and retry semantics, so automation cannot safely pick the default or compatibility policy without maintainer intent.

Likely owner: steipete

Owner confidence: medium

Options:

- **Add opt-in overlap policy (recommended):** Keep current accepted-by-default behavior, then let trusted hook mappings or direct hook calls opt into reject, skip, or queue semantics with documented retry behavior.
- **Make conflict the default:** Reject same-session active deliveries by default, accepting that some existing webhook integrations may need migration to avoid retry storms.
- **Keep caller-managed locking:** Leave OpenClaw accepting hook deliveries and document idempotency keys plus client-side locks as the supported overlap control.

## Reproduction Assessment

Yes. Source inspection shows repeated direct or mapped hook-agent POSTs with the same resolved `sessionKey` and no shared idempotency key are accepted with `200/runId`, with no active/queued same-session `409` path.

## Solution Assessment

No for an unconditional default `409`; the better path is a maintainer-approved overlap policy that chooses reject, skip, queue, compatibility defaults, and active-plus-queued semantics before implementation.

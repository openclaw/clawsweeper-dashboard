- `P2`: The issue has source-reproducible operational impact for webhook-triggered agents, but no evidence of a core emergency outage or first-run release blocker.
- `impact:session-state`: The requested guard is keyed by hook session identity and is meant to prevent overlapping work for the same logical session.

## Summary

Keep open: current main still accepts direct and mapped hook-agent deliveries with 200/runId after idempotency-key replay checks, and there is no active-or-queued same-session admission policy; related persistent-session and webhook-queue work overlaps but does not implement the requested conflict decision.

## What This Changes

Request adding a sessionKey-based webhook admission guard that returns 409 Conflict when a webhook delivery targets a sessionKey that already has an active run.

## Best Possible Solution

Define an explicit, compatibility-safe hook overlap policy at gateway admission that covers active and queued same-session work, preserves idempotency replay, and coordinates with persistent hook sessions and queued webhook ingestion.

## Maintainer Decision

Question: Should hook-agent deliveries with the same resolved sessionKey be rejected, skipped, queued, or remain parallel by default, and should any 409 behavior be opt-in?

Rationale: The requested 409 changes an external webhook HTTP response contract and retry semantics, so automation cannot safely choose the default, compatibility, or security posture without maintainer intent.

Likely owner: steipete

Owner reason: Peter has the clearest prior policy framing for this hook/session admission decision and relevant hook security history.

Owner confidence: medium

Options:

- **Add Opt-In Overlap Policy (recommended):** Keep current accepted-by-default behavior, then let trusted hook mappings or direct hook calls opt into reject, skip, or queue semantics with documented retry behavior.
- **Make 409 The Default:** Reject same-session active deliveries by default and accept that existing webhook integrations may need migration to avoid retry storms.
- **Keep Caller-Managed Locking:** Leave OpenClaw accepting hook deliveries and document idempotency keys plus client-side locks as the supported overlap control.

## Reproduction Assessment

Yes. Source inspection shows repeated direct or mapped hook-agent POSTs with the same resolved sessionKey and no shared idempotency key are accepted with 200/runId, with no active-or-queued same-session 409 path.

## Solution Assessment

No, not as an unconditional default 409. The maintainable path is a maintainer-approved overlap policy that chooses reject, skip, queue, compatibility defaults, and active-plus-queued semantics before implementation.

- Changing same-session hook deliveries from 200/runId to 409 by default could break integrations that treat non-2xx webhook responses as failed delivery and retry aggressively.

- The open persistent-session PR may fix transcript reuse for trusted hooks, but it does not decide whether overlapping same-session deliveries reject, skip, queue, or remain caller-managed.
- Any policy keyed by sessionKey must preserve hook auth, allowed-agent checks, and allowed session-key prefixes because sessionKey is routing metadata, not authorization.

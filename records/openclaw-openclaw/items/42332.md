## Summary

Keep open: current main still accepts direct and mapped hook-agent webhook deliveries with 200/runId and has no same-session active/queued conflict policy; this remains a product/compatibility decision rather than implemented cleanup.

## What This Changes

Request adds a sessionKey-based webhook overlap guard that would return 409 Conflict when a prior delivery for the same logical hook session is still running.

## Best Possible Solution

Define an explicit, compatibility-safe hook overlap policy at Gateway admission that covers active and queued same-session work, preserves idempotency replay, and coordinates with persistent hook-session and queued webhook designs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should hook-agent webhook deliveries with the same resolved sessionKey be rejected with 409, skipped, queued, or left parallel by default, and should any overlap guard be opt-in?

Rationale: The requested behavior changes an external HTTP webhook contract and retry semantics, so automation cannot safely pick the default or compatibility policy without maintainer intent.

Likely owner: steipete

Owner reason: Peter has the strongest adjacent product/security-boundary history for session lifecycle and compatibility policy, even though Vincent owns much of the recent hook code path.

Owner confidence: medium

Options:

- **Add opt-in overlap policy (recommended):** Keep current 200/runId behavior by default, then let trusted hook mappings or direct hook calls opt into reject, skip, or queue semantics with documented retry behavior.
- **Fold into webhook queue design:** Let the queued webhook ingestion work own per-session concurrency controls and close this issue only once that design covers same-session polling duplicates.
- **Make 409 the default:** Reject same-session active deliveries by default, accepting that existing webhook producers may need migration to avoid retry storms.

## Reproduction Assessment

Yes. Source inspection shows repeated direct or mapped hook-agent POSTs with the same resolved sessionKey and no shared idempotency key reach dispatch and return 200/runId, with no active-session 409 path.

## Solution Assessment

No for an unconditional default 409. The better solution is a maintainer-approved overlap policy that chooses reject, skip, queue, compatibility defaults, and active-plus-queued semantics before implementation.

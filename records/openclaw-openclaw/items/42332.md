## Summary

Keep open: current main still returns 200/runId for direct and mapped hook-agent deliveries and has no caller-visible same-session active/queued conflict policy; related persistent-session and queued-webhook work overlap but do not decide this webhook overlap behavior.

## What This Changes

Add a webhook delivery overlap policy so a request with an active matching sessionKey can be rejected or otherwise guarded instead of starting another hook-agent turn.

## Best Possible Solution

Define an explicit, compatibility-safe hook overlap policy at Gateway admission that covers active and queued same-session work while preserving existing default behavior unless maintainers choose a breaking default.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should same-session hook-agent deliveries be rejected with 409, skipped, queued, or left parallel by default, and should any non-parallel behavior be opt-in per hook or mapping?

Rationale: The requested 409 response changes the public webhook response contract and retry semantics, while the alternatives create different queueing and compatibility behavior that automation should not choose without maintainer intent.

Likely owner: steipete

Owner confidence: medium

Options:

- **Add Opt-In Overlap Policy (recommended):** Keep current accepted-by-default behavior and add a documented hook or mapping policy for reject, skip, or queue semantics keyed by the resolved sessionKey.
- **Make 409 The Default:** Reject active same-session hook deliveries by default and accept that some existing senders may need migration to avoid retry storms.
- **Leave Locking To Callers:** Keep OpenClaw's hook endpoint parallel and document idempotency keys plus caller-managed locks as the supported overlap control.

## Reproduction Assessment

Yes. Source inspection shows repeated direct or mapped hook-agent POSTs with the same resolved sessionKey and no shared idempotency key are accepted with 200/runId before any async session work admission can run.

## Solution Assessment

No for unconditional default 409. The best fix needs a maintainer-approved overlap policy that chooses reject, skip, queue, compatibility defaults, and active-plus-queued semantics before implementation.

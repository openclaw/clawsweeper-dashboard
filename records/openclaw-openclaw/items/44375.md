## Label Justifications

- `P1`: Silent default-agent displacement can reroute live channel, heartbeat, and cron traffic away from the user's expected primary agent.
- `impact:session-state`: Changing the fallback agent changes agent-scoped session keys and can strand existing `main` history, memory, and auth state.
- `impact:security`: Unmatched traffic can be delivered into an unintended ACP runtime or workspace with different tools, auth, and sandbox policy.
- `impact:message-loss`: Channel traffic without a matching binding can be delivered to a different agent than the user intended after adding one ACP agent.

## Summary

Keep open: current main and the latest release still route unmatched traffic to `agents.list[].default` or the first listed agent, so adding one ACP agent can still displace the implicit `main` agent. The related open PRs address adjacent default or explicit-main-binding paths, but neither resolves this default-selection policy issue.

## What This Changes

The issue asks OpenClaw to warn, preserve `main`, or require an explicit default when adding an ACP agent to `agents.list` would silently reroute unmatched traffic away from the implicit main agent.

## Best Possible Solution

Maintainers should choose the compatibility policy, then update routing/config-write or doctor behavior, docs, and focused regression coverage so adding a bound ACP agent cannot silently change the default agent without an explicit user decision.

## Reproduction Assessment

Yes, source-level: a non-empty `agents.list` with no `default: true` resolves the first entry as the default, and unmatched route fallback uses that agent. I did not run a live gateway because this review is read-only.

## Solution Assessment

Unclear as a final implementation: warning, auto-preserving `main`, and requiring an explicit default each change documented routing semantics differently. The right fix needs a maintainer compatibility and security decision before code is changed.

## Label Justifications

- `P1`: Silent default-agent displacement can affect real channel routing, heartbeats, and session continuity for multi-agent users.
- `impact:session-state`: The report is about existing `main` sessions and memory/index state becoming orphaned when routes re-key to another agent.
- `impact:message-loss`: Unbound DMs, groups, topics, heartbeats, and crons can be misrouted to the unintended first `agents.list` entry.
- `impact:security`: Misrouting private traffic to a different ACP/runtime identity can cross an operator’s intended privacy boundary.

## Summary

Keep open: current main and the latest release still resolve an unmarked non-empty `agents.list` to the first list entry, so the reported implicit-`main` displacement remains. The related open pull requests cover adjacent default-agent consistency or explicit `main` bindings, but neither has merged nor made the product/security decision for this foot-gun.

## What This Changes

Warn or otherwise prevent adding an ACP-bound agent to `agents.list` from silently displacing the implicit `main` agent as the global default.

## Best Possible Solution

Keep existing runtime semantics for already-valid configs, but add a maintainer-approved config-set/doctor/onboarding warning or guided repair when a first `agents.list` write lacks `default: true` or explicit `main` while existing `main` state is present.

Yes, source inspection gives a high-confidence reproduction path: a config with one `agents.list` entry and no `default: true` makes that entry the default, and route fallback sends unmatched traffic there. I did not run a live gateway because this was a read-only review.

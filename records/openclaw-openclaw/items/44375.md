## Label Justifications

- `P1`: Silent default-agent displacement can reroute live channel, heartbeat, and cron traffic away from the user's expected primary agent.
- `impact:security`: Unmatched traffic can enter an unintended ACP runtime or workspace with different tools, credentials, and sandbox posture.
- `impact:message-loss`: Messages without a matching binding can be delivered to the wrong agent after adding one ACP agent.
- `impact:session-state`: The fallback agent change rewrites agent-scoped session keys and can strand existing `main` history, memory, and auth state.

## Summary

Keep open: current main and v2026.6.11 still resolve a non-empty `agents.list` without `default: true` to the first listed agent, and unmatched routing still falls through to that resolved default. This remains a real session/security/message-routing foot-gun, but the fix changes documented default-agent semantics and needs maintainer product direction.

## What This Changes

The issue requests safer behavior when a first ACP agent is added to `agents.list` so unmatched traffic does not silently move away from the implicit `main` agent.

## Best Possible Solution

Adopt a maintainer-approved transition path that makes default-agent displacement explicit during config-write/setup/doctor flows, preserves existing `main` continuity when appropriate, and documents the chosen compatibility rule with focused routing tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should first-time `agents.list` configuration be allowed to change the default agent by list order, or should OpenClaw require an explicit default, warning, or migration when implicit `main` would be displaced?

Rationale: The viable fixes intentionally change documented routing semantics, warning behavior, or config-write UX, and automation should not choose that product/security contract without maintainer intent.

Likely owner: steipete

Owner reason: The product/security decision sits closest to the original multi-agent routing behavior that `steipete` introduced.

Owner confidence: medium

Options:

- **Gate config writes with explicit default (recommended):** Keep runtime parsing compatible, but make CLI/UI/doctor flows prompt or fail when a first non-empty `agents.list` has no `default: true` and existing `main` state would be displaced.
- **Warn only:** Preserve first-entry fallback everywhere and add high-visibility warnings plus docs/doctor guidance for users adding their first listed agent.
- **Auto-preserve main:** Materialize `main` as the default when `main` state exists, protecting continuity but changing the meaning of first-entry-only configs.

## Reproduction Assessment

Yes. Source inspection shows that a non-empty `agents.list` without `default: true` resolves the first entry as the default, and unmatched route fallback uses that agent; I did not run a live gateway because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the policy. Warning, auto-preserving `main`, and requiring an explicit default each solve the foot-gun differently and carry different compatibility/security tradeoffs.

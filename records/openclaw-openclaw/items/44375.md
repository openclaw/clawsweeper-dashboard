## Label Justifications

- `P1`: Silent default-agent displacement can reroute live channel, heartbeat, and cron traffic away from the user's expected primary agent.
- `impact:session-state`: Changing the fallback agent changes agent-scoped session keys and can strand existing `main` history, memory, and auth state.
- `impact:security`: Unmatched traffic can be delivered into an unintended ACP runtime or workspace with different tools, credentials, and sandbox policy.
- `impact:message-loss`: Channel traffic without a matching binding can be delivered to a different agent than the user intended after adding one ACP agent.

## Summary

Keep open: current main still resolves a non-empty `agents.list` with no explicit default to the first listed agent, and unmatched traffic still falls through to that resolved default. The linked open PRs address adjacent explicit-main binding and hardcoded-main paths, but they do not settle the first-entry default-displacement policy reported here.

## What This Changes

The issue requests a warning, migration, or explicit-default requirement so adding an ACP agent to `agents.list` does not silently displace the implicit `main` agent for unmatched traffic.

## Best Possible Solution

Adopt a maintainer-approved transition that makes default-agent displacement explicit during config write/setup/doctor flows, preserves existing `main` continuity when appropriate, and covers the chosen behavior with routing plus config tests.

- **Auto-preserve main:** Materialize `main` as the default when `main` state exists, protecting continuity but changing the meaning of first-entry-only configs.

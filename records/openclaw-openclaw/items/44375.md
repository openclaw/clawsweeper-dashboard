## Label Justifications

- `P1`: Silent default-agent displacement can reroute live channel, heartbeat, and cron traffic away from the user's expected primary agent.
- `impact:session-state`: Changing the fallback agent changes agent-scoped session keys and can strand existing `main` history, memory, and auth state.
- `impact:message-loss`: Traffic without a matching binding can be delivered to a different agent than intended after adding one ACP agent.
- `impact:security`: Unmatched traffic can enter an unintended ACP runtime or workspace with different tools, credentials, and sandbox policy.

## Summary

Keep open: current main still selects `agents.list[].default` or the first listed agent before falling back to implicit `main`, and unmatched route fallback still uses that selected default. The related open PRs are adjacent explicit-main binding or hardcoded-main cleanup, not a fix for this first-entry default-displacement policy.

## What This Changes

The issue asks OpenClaw to stop silently changing the default route from implicit `main` to the first `agents.list` ACP agent when a user adds a topic-specific ACP agent.

## Best Possible Solution

Adopt a maintainer-approved transition that makes default-agent displacement explicit during config writes, setup, and doctor checks while preserving existing `main` continuity or giving users a deliberate migration path.

Question: Should first-time `agents.list` configuration be allowed to change the default agent by list order, or must OpenClaw require an explicit default or warning when implicit `main` would be displaced?

Rationale: The source bug is clear, but the viable fixes intentionally change documented routing semantics, config-write UX, or upgrade behavior; automation should not choose that product/security contract without maintainer intent.

Likely owner: steipete

Owner reason: The strongest history signal for the current resolver and routing contract is the original multi-agent routing commit.

Owner confidence: high

Options:

- **Gate config writes with explicit default (recommended):** Keep runtime compatibility but make CLI/UI/doctor flows prompt, warn, or fail when a first non-empty `agents.list` has no `default: true` and existing `main` state would be displaced.
- **Warn only:** Preserve first-entry fallback everywhere and add high-visibility warning plus docs/doctor guidance for users adding their first listed agent.
- **Auto-preserve main:** Materialize `main` as the default when `main` state exists, protecting continuity but changing the meaning of first-entry-only configs.

## Reproduction Assessment

Yes. Source inspection shows a non-empty `agents.list` without `default: true` resolves the first entry as the default, and unmatched route fallback uses that agent; I did not run a live gateway because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the policy. Warning, auto-preserving `main`, and requiring an explicit default each solve the foot-gun differently and carry different compatibility and security tradeoffs.

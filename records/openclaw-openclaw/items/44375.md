## Label Justifications

- `P1`: Silent default-agent displacement can reroute live channel, heartbeat, and cron traffic away from the user's expected primary agent.
- `impact:session-state`: Changing the fallback agent changes agent-scoped session keys and can strand existing `main` history and memory state.
- `impact:message-loss`: Messages without matching bindings can be delivered to an unintended agent after adding one ACP agent.
- `impact:security`: Unmatched traffic can enter an unintended ACP runtime/workspace with different tools, credentials, and sandbox policy.

## Summary

Keep open: current main and latest release still resolve a non-empty `agents.list` without `default: true` to the first listed agent, and unmatched routing uses that resolved default. The related open PRs cover explicit `main` bindings and configured-default propagation, but not the first-entry default-displacement policy.

## What This Changes

The issue requests a safer default-agent transition when adding an ACP agent to `agents.list` so the implicit `main` agent is not silently displaced for unrelated traffic.

## Best Possible Solution

Adopt a maintainer-approved transition that makes default-agent displacement explicit at config-write/setup time, preserves existing `main` continuity when appropriate, and documents the compatibility rule with focused routing and upgrade tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw continue allowing the first `agents.list` entry to become the default implicitly, or require/prompt for an explicit default when existing `main` state could be displaced?

Rationale: The viable fixes intentionally change routing semantics, warning behavior, or config-write UX, and automation should not choose that product/security contract without maintainer intent.

Likely owner: Peter Steinberger

Owner reason: The default-agent routing behavior originated in Peter Steinberger's multi-agent routing work and the current implementation is still most strongly tied to that history.

Owner confidence: high

Options:

- **Require explicit default on first listed-agent setup (recommended):** Make config-write/setup/doctor flows stop or prompt when a first non-empty `agents.list` has no `default: true` and existing `main` state would be displaced.
- **Warn but preserve first-entry fallback:** Keep runtime behavior compatible while adding high-visibility warning plus docs/doctor guidance for first-time listed-agent configs.
- **Auto-preserve `main` when state exists:** Materialize or prefer `main` as default when previous `main` state exists, protecting continuity but changing first-entry-only config meaning.

## Reproduction Assessment

Yes. Current source shows a non-empty `agents.list` without `default: true` resolves to the first entry, and unmatched routing uses that resolved default; I did not run a live gateway repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the policy. Explicit-default gating, warning-only behavior, and auto-preserving `main` each solve the foot-gun differently and carry different compatibility/security tradeoffs.

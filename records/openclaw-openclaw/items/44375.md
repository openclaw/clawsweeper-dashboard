## Label Justifications

- `P1`: Silent default-agent displacement can reroute live channel, heartbeat, and cron traffic away from the user's expected primary agent.
- `impact:session-state`: Changing the fallback agent changes agent-scoped session keys and can strand existing `main` history, memory, and auth state.
- `impact:security`: Unmatched traffic can be delivered into an unintended ACP runtime or workspace with different tools, credentials, and sandbox policy.
- `impact:message-loss`: Channel traffic without a matching binding can be delivered to a different agent than the user intended after adding one ACP agent.

## Summary

Keep open: current main still resolves a non-empty `agents.list` with no `default: true` to the first listed agent, and unmatched routing uses that default. The related open items cover explicit `main` bindings, hardcoded-main cleanup, or missing-binding diagnostics, but none owns this first-entry default-displacement policy.

## What This Changes

The issue requests warning, preservation, or explicit-default behavior when adding an ACP agent to `agents.list` would displace the implicit `main` agent for unmatched traffic.

## Best Possible Solution

Adopt a maintainer-approved transition that makes default-agent displacement explicit at config-write/setup time, preserves existing `main` continuity when appropriate, and documents the chosen compatibility rule with focused routing and config coverage.

Options:

- **Gate config writes with explicit default (recommended):** Keep runtime parsing compatible, but make CLI/UI/doctor flows prompt or fail when a first non-empty `agents.list` has no `default: true` and existing `main` state would be displaced.
- **Warn only:** Preserve first-entry fallback everywhere and add high-visibility warning plus docs/doctor guidance for users adding their first listed agent.
- **Auto-preserve main:** Materialize `main` as the default when `main` state exists, protecting continuity but changing the meaning of first-entry-only configs.

Unclear until maintainers choose the policy. Warning, auto-preserving `main`, and requiring an explicit default each solve the foot-gun differently and carry different compatibility/security tradeoffs.

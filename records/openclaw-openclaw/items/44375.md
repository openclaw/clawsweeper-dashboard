## Label Justifications

- `P1`: Silent default-agent displacement can reroute live channel, heartbeat, and cron traffic away from the user's expected primary agent.
- `impact:session-state`: The fallback agent change re-keys unmatched sessions from `main` to the first listed agent and can strand existing history and memory state.
- `impact:security`: Private traffic can cross into an unintended ACP/runtime workspace with different tools, credentials, and sandbox policy.
- `impact:message-loss`: Unmatched channel traffic can be delivered to the wrong agent after a normal multi-agent config edit.

## Summary

Keep open: current main and v2026.6.11 still resolve a non-empty `agents.list` to `default: true` or the first listed agent before falling back to implicit `main`, so the reported silent default-agent displacement remains unresolved and needs maintainer policy direction.

## What This Changes

The issue requests preventing or warning about silent default-agent displacement when an ACP entry is added to `agents.list` without an explicit `main` or `default: true` entry.

## Best Possible Solution

Adopt a maintainer-approved transition that makes default-agent displacement explicit at config-write/setup/doctor time while preserving a safe upgrade path for existing multi-agent configurations.

- **Require explicit default:** Reject or fail closed on non-empty `agents.list` without `default: true`, backed by doctor repair and compatibility messaging.

Yes. Source inspection shows a non-empty `agents.list` without `default: true` resolves the first entry as default, and unmatched route fallback uses that agent.

## Solution Assessment

Unclear until maintainers choose the policy. Warning and doctor guidance is likely the least disruptive repair, while changing the resolver or requiring explicit defaults needs upgrade proof.

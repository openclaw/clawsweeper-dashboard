## Label Justifications

- `P1`: Silent default-agent displacement can reroute live channel, heartbeat, and cron traffic away from the user's expected primary agent.
- `impact:session-state`: Changing the fallback agent changes agent-scoped session keys and can strand existing `main` history, memory, and auth state.
- `impact:security`: Unmatched traffic can be delivered into an unintended ACP runtime or workspace with different tools, credentials, and sandbox policy.
- `impact:message-loss`: Channel traffic without a matching binding can be delivered to a different agent than the user intended after adding one ACP agent.

## Summary

Keep open: current main and the latest release still use `agents.list[].default` or the first listed agent before falling back to implicit `main`, so the reported default-agent displacement remains possible. Related open PRs address explicit `main` bindings and hardcoded-main cleanup, but they do not change this first-entry default policy.

## What This Changes

The issue requests safer handling when adding an ACP agent to `agents.list` would make that agent the default for unmatched traffic instead of preserving implicit `main`.

## Best Possible Solution

Adopt a maintainer-approved transition path that makes default-agent displacement explicit during config-write/setup/doctor flows, preserves existing `main` continuity when appropriate, and updates routing docs plus focused regression tests.

- **Auto-preserve implicit main:** Materialize or select `main` as default when existing main state is detected, accepting a behavior change for first-entry-only configs.

## Label Justifications

- `P1`: Silent default-agent displacement can reroute live channel, heartbeat, and cron traffic away from the user's expected primary agent.
- `impact:security`: Unmatched traffic can be delivered into an unintended ACP runtime or workspace with different tools, credentials, and sandbox policy.
- `impact:message-loss`: Messages without a matching binding can be delivered to a different agent than the user intended after adding one ACP agent.
- `impact:session-state`: Changing the fallback agent changes agent-scoped session keys and can strand existing `main` history and memory state.
- `maturity:stable`: The affected gateway delivery fallback behavior maps to the Gateway runtime surface, which the checked-in maturity scorecard marks M4 Stable.

## Summary

Keep open: current main still selects `agents.list[].default`, then the first listed agent, then `main`, and unmatched routing still uses that resolved default. The related open PRs cover explicit-main binding preservation or hardcoded-main cleanup, but they intentionally do not settle this default-selection policy.

## What This Changes

The issue asks OpenClaw to prevent or warn about a first ACP entry in `agents.list` becoming the default agent for all unmatched traffic when the user intended only a topic-specific binding.

## Best Possible Solution

Adopt a maintainer-approved transition that makes default-agent displacement explicit at config-write or setup time, preserves existing `main` continuity when appropriate, and documents the chosen compatibility rule with focused routing/config coverage.

Rationale: The viable fixes intentionally change documented routing semantics, warning behavior, or config-write UX; automation should not choose that product and security contract without maintainer intent.

Likely owner: steipete

Owner confidence: high

Options:

- **Gate config writes with explicit default (recommended):** Keep runtime parsing compatible, but make CLI/UI/doctor flows prompt or fail when a first non-empty `agents.list` has no `default: true` and existing `main` state would be displaced.
- **Warn only:** Preserve first-entry fallback everywhere and add high-visibility warning plus docs/doctor guidance for users adding their first listed agent.
- **Auto-preserve main:** Materialize `main` as the default when `main` state exists, protecting continuity while changing the meaning of first-entry-only configs.

## Reproduction Assessment

Yes. Source inspection shows a non-empty `agents.list` without `default: true` resolves the first entry as the default, and unmatched route fallback uses that agent; I did not run a live gateway repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the policy. Warning, auto-preserving `main`, and requiring an explicit default each solve the foot-gun differently and carry different compatibility/security tradeoffs.

## Label Justifications

- `P1`: Silent default-agent displacement can reroute live channel, heartbeat, cron, and hook traffic away from the user's expected primary agent.
- `impact:session-state`: Changing the fallback agent changes agent-scoped session keys and can strand existing `main` history, memory, and auth state.
- `impact:security`: Unmatched traffic can be delivered into an unintended ACP runtime or workspace with different tools, credentials, and sandbox policy.
- `impact:message-loss`: Channel traffic without a matching binding can be delivered to a different agent than the user intended after adding one ACP agent.

## Summary

Keep open: current main and the latest release still make a populated `agents.list` choose `agents.list[].default` or the first entry as the default agent, so a single ACP agent can still receive unmatched traffic. The related open PRs cover explicit `main` bindings or other default-agent consistency paths, but they do not resolve this default-selection policy issue.

## What This Changes

The issue asks OpenClaw to prevent or warn about a newly added ACP agent in `agents.list` becoming the default for all unmatched traffic when the user intended only a topic-specific binding.

## Best Possible Solution

Maintainers should choose the compatibility policy, then update routing/config-write or doctor behavior, docs, and focused regression coverage so adding a bound ACP agent cannot silently displace `main` without an explicit operator decision.

- **Keep current behavior:** Leave first-list-entry fallback as the supported contract and rely on explicit `main` route bindings or docs for users who need continuity.

Yes, source-level: on current main, a non-empty `agents.list` with no `default: true` resolves the first entry as the default, and unmatched route fallback uses that agent. I did not run a live gateway because this review is read-only.

Unclear as a final implementation: warning, auto-preserving `main`, and requiring an explicit default each change documented routing semantics differently. The right fix needs a maintainer compatibility and security decision before code is changed.

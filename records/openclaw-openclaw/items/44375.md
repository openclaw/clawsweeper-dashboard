## Label Justifications

- `P1`: Silent default-agent displacement can reroute live channel, heartbeat, and cron traffic away from the user's expected primary agent.
- `impact:session-state`: The fallback agent change re-keys unmatched sessions from `main` to the first listed agent and can strand existing history and memory state.
- `impact:message-loss`: Unmatched channel traffic can be delivered to the wrong agent after a normal multi-agent config edit.
- `impact:security`: Private traffic can cross into an unintended ACP/runtime workspace with different tools, credentials, and sandbox policy.

## Summary

Keep open: current main and latest release still use `agents.list[].default` or the first listed agent before falling back to implicit `main`, so the reported default-agent displacement remains real and needs a maintainer policy decision rather than cleanup closure.

## What This Changes

The issue asks OpenClaw to prevent or warn about a first `agents.list` entry silently becoming the default route for unmatched traffic that previously used implicit `main`.

## Best Possible Solution

Adopt a maintainer-approved transition path that makes default-agent displacement explicit at config-write/setup/doctor time while preserving upgrade compatibility for existing multi-agent configurations.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw keep the documented first-entry default behavior and add warnings/doctor guidance, or change the default-selection contract so adding `agents.list` without `default: true` preserves implicit `main`?

Rationale: The issue is source-reproducible, but all viable fixes intentionally change documented routing semantics, warning behavior, or config-write UX, so automation should not choose the compatibility/security contract.

Likely owner: Peter Steinberger

Owner reason: The multi-agent default-routing policy introduction is the strongest available product-decision history signal.

Owner confidence: high

Options:

- **Warn and guide (recommended):** Keep first-entry default behavior, but add config/doctor/CLI warnings and docs that make default displacement explicit before or after first `agents.list` writes.
- **Preserve implicit main:** Change resolver or config normalization so implicit `main` stays default unless `default: true` is explicit, with migration/upgrade proof for existing configs.
- **Require explicit default:** Reject or fail-closed on non-empty `agents.list` without a default, requiring a doctor migration and compatibility plan.

## Reproduction Assessment

Yes. Source inspection shows a non-empty `agents.list` without `default: true` resolves the first entry as default, and unmatched route fallback uses that agent.

## Solution Assessment

Unclear until maintainers choose the policy. Warning/guidance is likely the least disruptive repair, while changing the resolver or requiring explicit defaults needs upgrade proof.

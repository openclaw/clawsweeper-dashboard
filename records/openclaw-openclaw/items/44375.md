## Label Justifications

- `P1`: Silent default-agent displacement can reroute live channel, heartbeat, and scheduled traffic away from the user's expected primary agent.
- `impact:session-state`: Changing the fallback agent changes agent-scoped session keys and can strand existing `main` history, memory, and auth state.
- `impact:message-loss`: Channel traffic without a matching binding can be delivered to a different agent than the user intended after adding one ACP agent.
- `impact:security`: Unmatched traffic can be delivered into an unintended ACP runtime or workspace with different tools, credentials, and sandbox policy.

## Summary

Keep open: current main and the latest release still route unmatched traffic to `agents.list[].default` or the first listed agent, so adding one ACP/named agent can still displace implicit `main`; the remaining fix needs maintainer policy direction rather than cleanup closure.

## What This Changes

The issue asks OpenClaw to warn, preserve implicit `main`, or require an explicit default when adding an ACP/named agent to `agents.list` would otherwise reroute unmatched traffic away from `main`.

## Best Possible Solution

Adopt a maintainer-approved transition that makes default-agent changes explicit in config/setup/doctor flows, preserves existing `main` continuity when appropriate, and documents the chosen compatibility rule with focused routing and session coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should adding the first `agents.list` entry be allowed to change the default agent by list order, or should OpenClaw require/warn about an explicit default when existing implicit `main` state would be displaced?

Rationale: Current main documents first-entry fallback, but the issue shows session continuity, message routing, and security risk when users add a specialized ACP agent; changing the fallback or only warning both carry compatibility tradeoffs.

Likely owner: steipete

Owner reason: The strongest history signal for the multi-agent routing/default behavior points to the original routing work and adjacent route-cache maintenance.

Owner confidence: high

Options:

- **Gate With Explicit Default (recommended):** Keep runtime parsing compatible, but make config/setup/doctor flows warn or fail when the first non-empty `agents.list` has no explicit default and existing `main` state would be displaced.
- **Warn Only:** Preserve first-entry fallback everywhere and add high-visibility warnings plus docs/doctor guidance for users adding their first listed agent.
- **Auto-Preserve Main:** Materialize or promote `main` as default when `main` state exists, protecting continuity while changing first-entry-only config meaning.

## Reproduction Assessment

Yes, source-level. Current main resolves a non-empty `agents.list` without `default: true` to the first entry, and unmatched route fallback uses that agent; I did not run a live gateway because this cleanup review is read-only.

## Solution Assessment

Unclear until maintainers choose the policy. Warning, auto-preserving `main`, and requiring an explicit default each solve the foot-gun differently and carry different compatibility and security tradeoffs.

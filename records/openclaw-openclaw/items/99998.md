- `P2`: This is focused Discord gateway hardening with limited surface area and no evidence of an active production outage.

## Summary

The current head appears to address the prior 1 MiB blocker by raising the Discord gateway receive cap to 16 MiB and proving under-cap and over-cap loopback behavior. Keep this PR open for maintainer review because it intentionally lowers the `ws` receive default from 100 MiB to 16 MiB, which is still a compatibility and availability-sensitive fail-closed change for Discord gateway traffic.

## What This Changes

The PR adds a 16 MiB `maxPayload` to Discord gateway WebSocket construction in both the internal gateway and monitor/proxy paths, with constructor-option tests.

## Best Possible Solution

Keep the bounded Discord gateway receive hardening if maintainers accept the 16 MiB upgrade cap; otherwise raise the cap or add live large-guild proof before merge.

## Reproduction Assessment

Yes for the hardening path: the source and `ws` contract show current sockets use the 100 MiB default, and the PR body includes loopback output proving the new cap accepts a large under-cap event and rejects an over-cap frame. I did not run a live Discord large-guild reproduction.

## Solution Assessment

Mostly yes: the owner boundary is the right Discord plugin socket construction path, and the current 16 MiB cap addresses the prior 1 MiB blocker. The remaining question is maintainer acceptance of the exact cap as an upgrade-sensitive fail-closed policy.

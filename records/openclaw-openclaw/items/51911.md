## Summary

## What This Changes

The issue asks OpenClaw to make Anthropic setup-token onboarding reliable across prompt guidance, credential persistence validation, and multi-agent auth propagation.

## Best Possible Solution

Settle the auth-store sharing contract, then land or replace a focused fix that improves setup-token guidance, validates the SQLite auth-profile write, and implements the chosen static-token inheritance or sync behavior without weakening OAuth isolation.

Question: Should Anthropic setup-token/static token auth be physically synced to sibling agent SQLite stores, inherited through runtime/read-through only, or exposed through an explicit operator-controlled repair/sync action?

Rationale: Each viable fix changes how sensitive provider credentials move across agent stores, and prior same-repo PRs were closed after auth-file and OAuth fanout concerns, so automation should not choose the permanent credential boundary.

Likely owner: steipete

Owner confidence: high

Options:

- **Operator-controlled token repair or sync (recommended):** Add doctor/status or models-auth repair behavior that validates the main token profile and copies only portable static token credentials after explicit user confirmation.
- **Runtime inheritance plus validation:** Keep credentials in the main store and improve startup/runtime validation and docs so secondary agents resolve inherited profiles without physical copies.
- **Automatic static-token sibling sync:** Copy portable Anthropic token profiles to sibling stores during setup-token and paste-token onboarding while explicitly excluding OAuth refresh credentials.

Unclear. Sibling sync is a plausible immediate repair for portable static tokens, but the best fix depends on the maintainer credential boundary because current main already has read-through inheritance and OAuth non-copying policy.

## Summary

Keep open: current main and v2026.6.11 still reject the whole DNS result set as soon as any resolved address is blocked, before the IPv4-first pinned lookup can use a safe public address. The direct fix PRs are closed unmerged, and the remaining change needs maintainer/security direction because it changes the strict SSRF DNS policy.

## What This Changes

The issue reports that web_fetch rejects public host fetches when DNS returns a mix of allowed IPv4 answers and blocked special-use IPv6 answers.

## Best Possible Solution

Adopt a narrowly tested SSRF resolver change that filters blocked DNS answers before pinning, rejects all-blocked sets, and preserves explicit config/proxy paths for private-network exceptions.

Options:

- **Approve filtered-address default (recommended):** Allow strict mode to proceed with only non-blocked resolved addresses, keep all-blocked sets rejected, and require focused SSRF pinning regression tests.
- **Keep fail-any-blocked default:** Preserve the current conservative DNS policy and document useTrustedEnvProxy or explicit fake-IP/private-network opt-ins as the supported workaround.
- **Add a new explicit opt-in:** Introduce a default-off mixed-DNS tolerance setting instead of changing strict mode for every existing web_fetch user.

## Reproduction Assessment

Yes, at source level: a lookup returning one public IPv4 address and one blocked IPv6 address reaches assertAllowedResolvedAddressesOrThrow, which throws before dedupeAndPreferIpv4 can choose the IPv4 candidate. I did not run a live dual-stack DNS repro in this read-only pass.

## Solution Assessment

Unclear until maintainers choose the security default. The proposed filtered-address fix is the narrowest code shape if the policy is approved, but current useTrustedEnvProxy and fake-IP opt-ins only cover specific trusted proxy setups, not the reported strict-mode mixed-answer case.

- `impact:security`: The issue is about the SSRF DNS-resolution guard for outbound `web_fetch` requests.

## Summary

Keep open: current main and the latest release still reject a DNS answer set as soon as any resolved address is blocked, before the IPv4-first pinned address ordering can use a safe public address. The direct fix PRs are closed unmerged, and the remaining blocker is maintainer/security approval for changing default SSRF DNS-answer semantics.

## What This Changes

The issue requests that `web_fetch` tolerate mixed DNS result sets by dropping blocked special-use addresses and using remaining allowed public addresses instead of rejecting the whole request.

## Best Possible Solution

Approve and land a focused SSRF fix that filters blocked resolved addresses out of the pinned candidate set, fails closed when none remain, preserves special-use blocking, and adds mixed-answer plus all-blocked regression coverage.

Rationale: The code change is small, but it changes the outbound fetch SSRF boundary and must reflect maintainer/security intent rather than an automated policy guess.

Owner confidence: high

Options:

- **Approve filtered mixed-answer semantics (recommended):** Allow requests only when at least one resolved address is allowed, pass only allowed addresses into the pinned dispatcher, and test mixed-answer plus all-blocked cases.
- **Keep any-blocked fail-closed:** Treat the current behavior as intentional strict SSRF protection and document trusted proxy or fake-IP opt-in paths for affected networks.
- **Make polluted DNS handling explicit opt-in:** Preserve the current default and add or reuse an operator-controlled SSRF policy knob for mixed polluted DNS environments.

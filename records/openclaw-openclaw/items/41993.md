## Summary

Keep open: current main and the latest release still reject mixed DNS answer sets as soon as any resolved address is blocked, and the direct candidate fixes for this issue are closed unmerged. The remaining decision is security-sensitive because it changes default SSRF handling for DNS results.

## What This Changes

The issue asks OpenClaw to let web_fetch proceed when DNS returns at least one allowed public address alongside blocked IPv6 special-use answers.

## Best Possible Solution

A maintainer-approved SSRF change should filter blocked resolved addresses out of the pinned candidate set, reject only when no allowed addresses remain, preserve all-blocked/private checks, and add mixed-answer regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw change the default SSRF DNS-answer rule from fail on any blocked resolved address to filtering blocked candidates and proceeding when at least one allowed address remains?

Rationale: The implementation shape is narrow, but this default controls outbound network safety under polluted or hostile DNS answers, so automation should not choose the security boundary by itself.

Likely owner: steipete

Owner reason: The strongest semantic history signal for the SSRF guard and DNS family-ordering boundary points to this owner.

Owner confidence: high

Options:

- **Approve filtered mixed-answer semantics (recommended):** Allow mixed DNS answer sets only after removing every blocked candidate from the pinned address pool, and add tests for mixed-allowed plus all-blocked results.
- **Keep any-blocked fail-closed:** Treat any blocked DNS answer as an intentional stop and document trusted proxy or fake-IP opt-in settings as the supported workaround.
- **Make the behavior opt-in:** Preserve the current default and add or reuse an explicit operator-controlled policy for DNS-polluted environments.

## Reproduction Assessment

Yes. A high-confidence source repro is a lookup returning one public IPv4 address plus one blocked IPv6 special-use address; current code throws before IPv4-first pinning can use the public candidate.

## Solution Assessment

Unclear until maintainer security review. Filtering blocked candidates before pinning is the narrow candidate fix, but changing the default SSRF mixed-answer rule needs an explicit security-boundary decision.

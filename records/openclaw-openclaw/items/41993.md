## Summary

Keep open: current `main` and latest release `v2026.6.11` still reject a DNS result set as soon as any resolved address is blocked, before IPv4-first pinning can use a safe public address. The direct candidate fix PRs are all closed unmerged, and the remaining choice is a security-sensitive default SSRF behavior decision.

## What This Changes

The issue reports that `web_fetch` rejects public dual-stack DNS responses when one returned IPv6 address is special-use, even when a usable public IPv4 address is also present.

## Best Possible Solution

A maintainer-approved SSRF fix should filter blocked resolved addresses before pinning, fail closed when no allowed address remains, preserve explicit private-network opt-ins, and add mixed-answer plus all-blocked regression tests.

Question: Should default SSRF DNS handling allow a mixed result set after removing blocked candidates, or keep rejecting the whole request when any resolved address is blocked?

Rationale: The code change is small, but it relaxes a default SSRF security boundary and must reflect maintainer/security intent.

Likely owner: Peter Steinberger

Owner reason: The current SSRF assertion path and nearby hardening history point here as the strongest routing candidate for the security-boundary choice.

Owner confidence: high

Options:

- **Approve filtered mixed-answer semantics (recommended):** Allow the request only when at least one resolved address is allowed, pass only allowed addresses to pinning, and test mixed plus all-blocked DNS results.
- **Keep any-blocked fail-closed:** Treat mixed blocked DNS answers as intentionally unsafe and document trusted proxy or fake-IP opt-in paths for affected deployments.
- **Make it explicit opt-in:** Preserve the strict default and expose or reuse a narrowly named operator-controlled policy for polluted DNS environments.

Unclear pending maintainer security review. Filtering blocked answers before pinning is the narrow maintainable fix, but the default SSRF mixed-answer policy needs owner approval.

## Summary

This PR remains necessary because current main still disables configured request policy in the xAI video path. The current head fixes that gap without an actionable correctness or security regression, and the controlled transport proof is sufficient; the lone failing CI annotation is in an unrelated gateway test.

## What This Changes

The PR applies configured xAI provider transport policy to video creation and polling, and applies network/dispatcher policy without provider headers to generated-video downloads.

## Best Possible Solution

Keep one canonical provider request-policy resolution and forward its network policy through every xAI video stage without leaking API credentials to generated-media origins; retain https://github.com/openclaw/openclaw/issues/103083 for the broader default SSRF-guard work across providers.

## Solution Assessment

Yes. Reusing the shared provider HTTP resolver and established guarded-fetch pattern is narrower and more maintainable than adding xAI-specific configuration or forwarding provider headers to arbitrary media origins.

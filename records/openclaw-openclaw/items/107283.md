## Summary

Keep this PR open but do not merge the current patch: `completed` means the process exited normally, not that its non-zero exit code was semantically successful, so the change would hide genuine command-failure warnings.

**Likely related people**
- `steipete` — high-confidence recent owner of exec outcome and agent-runtime behavior.
- `vincentkoc` — medium-confidence contributor to exec failure formatting and telemetry.

## What This Changes

The PR changes `isToolResultError()` so finite non-zero exit codes are not classified as errors when the tool result status is `completed`, and updates the classifier test accordingly.

## Best Possible Solution

Keep non-zero exits classified as failures by default and introduce an explicit producer-side accepted-exit or semantic-success signal only if maintainers want commands such as no-match searches to suppress warnings.

Rationale: The runtime's `completed` status only means normal process termination, so distinguishing an expected no-match from a genuine failed command requires an explicit product contract rather than this classifier inference.

- **Keep current behavior:** Retain all non-zero warnings and close the linked request as unsupported unless commands normalize expected exits themselves.
- **Suppress all normal exits:** Accept that genuine commands exiting 1–125 will no longer produce automatic channel failure warnings.

## Solution Assessment

No. Treating `completed` as semantic success is too broad because current main uses it for nearly every normal process exit; an explicit accepted-exit signal is the narrowest maintainable solution.

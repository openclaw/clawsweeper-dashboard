## Summary

Keep open: the proposed guard conflates normal process termination with command success, so it would suppress channel warnings for genuine shell-command failures. The same blocker from the previous review remains on the unchanged head, and the PR still lacks live behavior proof.

## What This Changes

Changes `isToolResultError()` so finite non-zero exit codes are not classified as errors when the tool-result status is `completed`, with corresponding classifier test updates.

## Best Possible Solution

Keep non-zero exits classified as failures by default and represent intentionally accepted exit codes through an explicit exec-owner signal or command-level normalization, with focused classifier tests and live channel proof for both accepted and genuine-failure cases.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw preserve shell exit-code failure semantics by default and require an explicit accepted-exit signal, or redefine every normally terminated non-zero command as non-failing for channel warnings?

Rationale: The runtime's `completed` status describes process termination, while whether a specific non-zero code is benign is command-dependent; source inspection cannot safely choose that user-facing warning policy without maintainer intent.

Likely owner: Swader

Owner reason: The strongest available history signal is prior work establishing user-visible tool-failure warning behavior in this agent path.

Owner confidence: medium

Options:

- **Require explicit accepted exits (recommended):** Keep non-zero exits warning by default and add or use a narrow owner-level signal only when the command intentionally accepts particular exit codes.
- **Suppress all completed non-zero exits:** Adopt the PR's broad interpretation and intentionally accept that normally terminated command failures will no longer produce tool-error warnings.

## Reproduction Assessment

Yes, at source level: a normally terminated process can return `status: completed` with a non-zero exit code, and this patch then suppresses its failure classification. A live channel run is still needed for behavioral proof.

## Solution Assessment

No. Checking only `status: completed` is too broad because it identifies normal process termination, not command success; a narrow accepted-exit contract is safer and preserves existing warning behavior.

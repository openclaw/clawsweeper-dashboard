## Summary

Keep open: the patch treats `status: "completed"` as semantic success, but the exec runtime uses it for every normally terminated process, including genuine command failures. The existing P1 correctness finding remains unresolved, and the PR still lacks after-fix live channel proof.

## What This Changes

The PR changes the shared tool-result classifier to ignore finite non-zero exit codes when the result status is `completed`, with adjacent classifier-test updates.

## Best Possible Solution

Keep non-zero exits classified as errors by default, and suppress a warning only when the exec owner supplies an explicit semantic-success or accepted-exit signal; cover both accepted and genuine non-zero outcomes through the shared classifier and live channel flow.

Rationale: The runtime’s `completed` state only means the process terminated normally; choosing whether to add accepted-exit metadata, alter notification policy, or retain all non-zero warnings is a product contract that source inspection cannot decide safely.

- **Suppress every normal non-zero exit:** Accept that channel users will no longer receive failure warnings for any process that exits normally with a non-zero code.
- **Keep current warning behavior:** Close this PR and continue treating every finite non-zero exec code as an error until a narrower contract is designed.

## Solution Assessment

No. Checking `completed` is too broad because that field records normal process termination, not whether the command’s exit code was semantically accepted; the narrow maintainable fix needs an explicit accepted-exit signal or a notification-layer contract.

## Summary

Keep this PR open for revision, but do not merge it as written: current `main` uses `completed` to mean the process terminated normally, not that its non-zero result was semantically successful, so the proposed guard is too broad.

Likely related people: Swader (medium confidence, introduced the user-facing tool-error warning path) and vincentkoc (medium confidence, recently refined tool-error detection).

## What This Changes

Changes `isToolResultError()` so results with `status: "completed"` are not classified as errors solely because they contain a finite non-zero exit code, with adjacent classifier-test updates.

## Best Possible Solution

Preserve non-zero exits as errors by default and introduce an explicit, owner-approved accepted-exit result contract at the exec boundary; then test classifier, event-hook, and channel-warning behavior for both accepted and genuine failures.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should non-zero process exits remain errors by default, with warning suppression limited to exit codes explicitly marked as accepted by the exec result contract?

Rationale: The runtime's `completed` status only confirms normal process termination, so source inspection cannot determine which non-zero codes the product should treat as successful without an explicit semantic contract.

Likely owner: Swader

Owner reason: The behavior appears tied most directly to the user-facing tool-error warning path introduced in `dbdc0eb`.

Owner confidence: medium

Options:

- **Add explicit accepted exits (recommended):** Keep generic non-zero failures visible and suppress warnings only when the exec result explicitly marks the exit code as accepted.
- **Suppress all completed exits:** Adopt this PR's interpretation that every normally terminated process is non-error, accepting that genuine command failures may become quiet.
- **Retain current behavior:** Keep all non-zero exits classified as errors and close the linked request unless a narrower contract is sponsored.

## Reproduction Assessment

Yes at source level: a result containing `status: "completed"` and `exitCode: 1` follows the changed branch, while current runtime code shows that both acceptable and failed commands can produce that shape. No live current-main channel reproduction was supplied.

## Solution Assessment

No. Using process-completion status as a success signal cannot distinguish `grep` no-match from failed tests or other meaningful non-zero outcomes; explicit accepted-exit metadata is the safer boundary.

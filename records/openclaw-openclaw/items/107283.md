## Summary

Keep open: the unchanged prior P1 blocker remains valid because `completed` means the process terminated normally, not that the command succeeded, and the PR still lacks real channel-behavior proof.

## What This Changes

The PR changes `isToolResultError()` so a finite non-zero exit code is ignored when the tool result has `status: "completed"`, with adjacent classifier-test updates.

## Best Possible Solution

Carry an explicit accepted or handled non-zero outcome from the exec/observer boundary, keep ordinary non-zero exits classified as failures by default, and prove both the quiet accepted case and retained genuine-failure warning in a real channel.

Question: Which non-zero exec outcomes should suppress user-visible channel failure warnings without hiding genuine command failures?

Rationale: The existing `completed` status describes process lifecycle rather than command success, so source inspection cannot infer whether maintainers want explicit accepted-exit metadata, unconditional non-zero warnings, or broadly quiet normal exits.

Likely owner: JoschkaT

Owner confidence: medium

Options:

- **Add an accepted-exit signal (recommended):** Preserve non-zero failure warnings by default and suppress them only when the exec or observer path explicitly marks the outcome as accepted or handled.
- **Quiet all normal exits:** Treat every `status: "completed"` result as non-error and intentionally accept that genuine normally exited command failures may no longer warn.
- **Keep current warning semantics:** Retain non-zero classification and require commands with expected non-zero outcomes to express that intent, such as through their command construction.

## Solution Assessment

No. Using `completed` as a success signal is broader than the runtime contract; an explicit accepted or handled outcome is the narrowest maintainable solution.

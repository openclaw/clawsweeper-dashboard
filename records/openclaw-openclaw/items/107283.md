## Summary

The linked bug remains valid, but this PR is not safe to merge because it treats every normally terminated non-zero command as successful, suppressing legitimate failure state and the only warning when an agent produces no reply; the prior blocker remains unresolved and real behavior proof is still absent.

## What This Changes

Changes `isToolResultError()` so finite non-zero exit codes are not classified as errors when the tool-result status is `completed`, with corresponding classifier test updates.

## Best Possible Solution

Define an explicit semantic-success signal for intentionally accepted exit codes, keep finite non-zero exits classified as failures by default, and cover both benign and genuine failure cases through the classifier, payload-warning path, and redacted live channel proof.

Question: What explicit contract should identify a non-zero exec result as expected and suppressible without hiding ordinary command failures?

Rationale: The existing `completed` status only means that the process terminated normally, so source inspection cannot infer which non-zero codes the product should consider semantically successful.

Likely owner: steipete

Owner confidence: high

Options:

- **Require explicit semantic success (recommended):** Preserve non-zero failure classification unless the exec producer or invocation supplies an explicit accepted-result signal, then test both accepted and failing outcomes.
- **Suppress warnings only:** Keep internal non-zero failure state but selectively suppress the final warning for an explicitly defined recoverable condition, accepting a narrower presentation-only policy.
- **Keep current behavior:** Retain non-zero failure warnings and require commands that intentionally accept a code to encode that intent in the shell invocation.

## Reproduction Assessment

Yes, source inspection gives a high-confidence current-main path: a normal non-zero exec outcome is classified as an error and becomes an exec warning when the run has no user-facing reply. A live channel reproduction was not supplied in the PR.

## Solution Assessment

No; `completed` describes normal process termination rather than successful command semantics, so using it as a blanket exception hides real failures. The safer fix requires an explicit accepted-exit signal or a narrowly defined warning-layer policy.

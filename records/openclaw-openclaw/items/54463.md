## Label Justifications

- `P2`: The issue is a scoped QMD memory-indexing robustness problem for users with broad workspace indexing and symlink-heavy temporary monorepos.
- `impact:session-state`: When QMD indexing becomes unhealthy or fails, memory retrieval can become stale or unavailable and affect agent memory/context state.

## Summary

Keep open: this is still the canonical QMD symlink-loop/runtime-boundary tracker, and the maintainer discussion explicitly keeps it in the active investigation lane. Current OpenClaw still hands plain QMD collections to external `qmd update`; latest upstream QMD source appears to avoid symlink following, so the remaining decision is whether OpenClaw should require/probe that QMD behavior, add doctor/docs guidance, or add its own guard.

## What This Changes

The issue asks OpenClaw to prevent QMD memory indexing from recursing through workspace-visible monorepo symlink loops until indexing fails with `ENAMETOOLONG`, while keeping runtime behavior and docs aligned.

## Best Possible Solution

Keep this issue open until maintainers recreate or disprove the symlink-loop fixture against current OpenClaw and current QMD, then either version-gate/doctor the fixed QMD behavior or add a narrow OpenClaw-side pre-update guard with regression coverage.

## Reproduction Assessment

Unclear. The issue has a strong historical scanner repro and OpenClaw still delegates traversal to `qmd update`, but latest upstream QMD source and v2.5.3 source show symlink following disabled, so a current-main/current-QMD failure was not established in this read-only pass.

## Solution Assessment

Unclear. A direct OpenClaw traversal guard may be the best compatibility fix for older QMD installs, but if current QMD already fixes scanning then the better OpenClaw solution may be version probing, doctor guidance, and docs cleanup.

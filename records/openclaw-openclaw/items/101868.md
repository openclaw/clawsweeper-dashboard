- `P1`: A long-running embedded agent can remain blocked after context overflow until a human notices and resets or starts a new session.

- `maturity:stable`: The recovery and diagnostics aspect overlaps the M4 Stable `gateway-runtime` surface, even though the narrower agent/session scorecards are M3.

## Summary

Keep open: current main and the latest release still end exhausted embedded-agent overflow recovery with a blocked result and manual `/reset` or `/new` guidance, while the requested persisted marker or auto-rotation changes core session recovery policy.

## What This Changes

Request automatic one-shot session rotation/retry or a persisted overflow-blocked marker when embedded-agent context-overflow recovery gives up.

## Best Possible Solution

Choose one core recovery policy, preferably a durable overflow-blocked marker with operator-visible recovery first, then add guarded one-shot rotation only if replay safety and loop caps are settled.

Owner confidence: medium

Options:

- **Persist blocked state first (recommended):** Add a durable overflow-blocked marker plus an operator-visible recovery affordance without silently replaying a turn on a new session.
- **Guarded one-shot rotation:** Rotate and replay once only after compaction and truncation are exhausted, with replay-safety gates and a per-session loop cap.
- **Keep manual recovery:** Keep the documented `/reset` or `/new` contract and improve only visibility, diagnostics, or docs.

## Reproduction Assessment

Yes, at source level. Current main still returns a blocked context-overflow result with `/reset` or `/new` guidance after overflow recovery is exhausted, and the durable session entry/update path has no explicit overflow-blocked marker.

## Solution Assessment

Unclear until maintainers choose the recovery policy. A persisted blocked marker is the least disruptive path; automatic rotation is plausible but must prove replay safety and avoid competing with model fallback or compaction-timeout repairs.

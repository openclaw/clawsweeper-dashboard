## Summary

Keep open: current main and the latest release still allow a delivery error result to become the outer isolated cron run status after nonfatal agent execution, and open linked PRs are implementation candidates rather than merged fixes.

## What This Changes

The issue reports scheduled isolated `agentTurn` runs recording parent cron `status=error` and `deliveryStatus=not-delivered` even though the isolated session ended successfully with final assistant output.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/95419 or a maintainer-approved replacement that preserves successful isolated execution separately from delivery/finalization failure with explicit `ok` versus `warning` semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For scheduled isolated agentTurn runs where execution succeeds but post-run delivery/finalization fails, should OpenClaw record primary cron status as `ok` with delivery fields, introduce a first-class `warning` status, or keep some delivery failures as primary `error`?

Rationale: The source-level bug is clear, but the fix changes persisted cron status, operator alerts, and retry/backoff behavior, so automation should not choose the public status contract on maintainers' behalf.

Likely owner: steipete

Owner reason: steipete has the strongest recent history on the cron finalizer and delivery/status boundary involved in this product contract.

Owner confidence: medium

Options:

- **Accept narrow status split (recommended):** Use `status=ok` for successful isolated execution and surface post-run send failures through `deliveryStatus`, `deliveryError`, diagnostics, and run-log fields.
- **Use first-class warning:** Defer the narrow fix and land a broader `warning` status contract across storage, Gateway schema, CLI/UI, docs, and plugin/API consumers.
- **Keep delivery failures as errors:** Preserve current primary-error behavior for delivery failures and instead improve diagnostics so users can distinguish execution failure from delivery failure.

## Reproduction Assessment

Yes at source level: current main can return an error-shaped delivery result through the isolated cron finalizer after a nonfatal payload, and the scheduler persists that returned status as the outer cron result. I did not live-reproduce the original WSL2/systemd/Feishu scheduled run.

## Solution Assessment

Unclear as final product direction: the finalizer/run-log boundary is the right layer, but maintainers still need to choose the narrow `ok` plus delivery-fields contract versus the broader warning-status contract.

## Summary

Current `main` intentionally narrows an unavailable explicit `tailnet` bind to loopback and now documents that behavior, so this is not an established fail-open vulnerability as reported. The silent loss of operator-selected Tailnet reachability remains worth resolving, but fail-closed startup versus an explicit degraded fallback is a security-boundary and availability decision.

## What This Changes

Change explicit `gateway.bind: "tailnet"` startup behavior to fail with a non-zero exit when no bindable Tailscale IPv4 address is available.

## Best Possible Solution

Preserve the exposure-narrowing loopback fallback, but emit a prominent startup warning and degraded gateway status with actionable Tailscale recovery guidance; switch to fatal startup only if the gateway/security owner explicitly chooses strict semantics for an explicit Tailnet bind.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: When `gateway.bind: "tailnet"` is explicit but no bindable Tailnet IPv4 exists, should gateway startup fail closed or continue loopback-only in a clearly reported degraded state?

Rationale: Both outcomes are defensible: failure strictly honors operator-selected network policy, while loopback fallback narrows exposure and preserves local recovery during transient Tailscale outages; current source and current-main documentation choose availability, but the latest release documentation does not clearly establish that contract.

Likely owner: steipete

Owner reason: The feature introduction and subsequent Tailscale security-boundary history most strongly trace to this owner candidate.

Owner confidence: high

Options:

- **Keep Degraded Fallback (recommended):** Continue loopback-only, but add an unmistakable startup warning and degraded status explaining that Tailnet access is unavailable and a restart is required.
- **Fail Explicit Tailnet:** Treat an unavailable explicit Tailnet bind as fatal with an actionable non-zero startup error, accepting the availability and upgrade impact.

## Reproduction Assessment

Yes from source, but not as a demonstrated remote bypass: when Tailnet IPv4 discovery or bindability fails and loopback is available, current `main` deterministically resolves an explicit Tailnet bind to loopback.

## Solution Assessment

No definitive best fix exists without owner intent. An unconditional fatal exit is stricter but upgrade-sensitive; a clearly surfaced degraded loopback state preserves the narrower exposure and local recovery path.

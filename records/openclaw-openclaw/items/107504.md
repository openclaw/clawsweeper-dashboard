## Summary

Keep this open for a gateway-owner decision. Current main deliberately falls back from an unavailable Tailnet address to loopback, so the reported remote security exposure is not established; however, that fallback silently violates the documented `tailnet` reachability intent and can leave operators believing remote access is available when it is not. Likely related people: openperf for recent gateway bind work, steipete for adjacent gateway/security policy work, and RenzoMXD as a lower-confidence routing contact from the issue timeline.

## What This Changes

Make explicit Tailnet gateway binding fail startup instead of silently falling back to loopback when the Tailscale address is unavailable or unbindable.

## Best Possible Solution

Treat explicit `gateway.bind: "tailnet"` as strict intent: fail startup with an actionable error when no bindable Tailnet IPv4 exists, retain graceful environment-dependent behavior only for `auto`, and add focused source tests plus operator-facing diagnostics for both missing-address and bind-failure cases.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should explicit `gateway.bind: "tailnet"` guarantee Tailnet reachability by failing startup when the requested address is unavailable, or preserve the current availability-first loopback fallback?

Rationale: Both behaviors are defensible but materially different: strict failure honors explicit operator intent and current documentation, while fallback preserves local availability and upgrade tolerance. Repository policy treats fallback and fail-closed startup behavior as product decisions rather than implementation conveniences.

Likely owner: openperf

Owner reason: They are the strongest available history-based candidate for the gateway bind surface where this contract is implemented.

Owner confidence: medium

Options:

- **Fail explicit Tailnet binds (recommended):** Make missing or unbindable Tailnet addresses fatal with a clear recovery message, while leaving `auto` as the availability-oriented mode.
- **Keep fallback with degradation:** Preserve loopback fallback but emit prominent startup and status warnings that requested Tailnet reachability was not achieved.
- **Add a strictness setting:** Introduce a compatibility knob for strict versus fallback behavior, at the cost of another gateway configuration surface and migration contract.

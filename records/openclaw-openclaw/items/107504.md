## Summary

Current source does silently degrade an explicit `tailnet` bind to loopback when no usable Tailnet address is available, but it does not support the reported network-exposure claim: loopback is host-local and gateway authentication remains configured. The issue remains useful because this fallback conflicts with the documented meaning of explicit `tailnet` mode and needs an upgrade-sensitive decision between availability and fail-closed startup.

## What This Changes

Make gateway startup fail with a non-zero exit when an explicitly requested Tailscale listener cannot be established.

## Best Possible Solution

Treat an explicitly configured `tailnet` bind as a strict operator intent: fail startup with an actionable diagnostic when the Tailnet address cannot be resolved or bound, while retaining availability-oriented fallback only for `auto` mode and documenting the upgrade behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When `gateway.bind` is explicitly `tailnet` and no usable Tailnet address exists, should startup fail or preserve the current loopback-only fallback?

Rationale: Both choices are defensible: fatal startup honors explicit configuration and avoids a silent mode change, while loopback fallback preserves local availability for existing installations; changing the current behavior is upgrade-sensitive.

Likely owner: steipete

Owner reason: The existing review and timeline identify @steipete as the strongest owner for gateway startup and compatibility policy.

Owner confidence: high

Options:

- **Fail explicit tailnet startup (recommended):** Return an actionable startup error for explicit `tailnet`, while keeping fallback behavior limited to `auto`.
- **Warn and remain loopback-only:** Preserve local availability but emit a prominent warning that the requested Tailnet listener was not created.
- **Keep silent fallback:** Retain current behavior without operator-visible failure or warning, prioritizing availability over explicit bind intent.

## Reproduction Assessment

Yes at source level: an explicit `tailnet` bind deterministically returns loopback when the Tailnet address is missing or unbindable. A live security exposure is not reproduced because the resulting listener is host-local and authentication is not disabled by this path.

## Solution Assessment

Yes, failing only an explicitly requested `tailnet` bind while retaining fallback for `auto` is the narrowest contract-aligned fix. Maintainer confirmation is still required because the change can stop existing gateways from starting after an upgrade.

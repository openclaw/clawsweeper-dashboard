## Summary

Keep this open for a gateway-owner decision: current main deliberately degrades an unavailable explicit Tailnet bind to loopback, so the reported remote security bypass does not occur, but the operator can silently lose requested Tailnet reachability. Likely related people: openperf for recent bind-resolution work, plus steipete and RenzoMXD from issue routing; ownership confidence is medium-to-low.

## What This Changes

Decide whether an explicit `gateway.bind: "tailnet"` request should fail startup instead of degrading to loopback when no bindable Tailscale IPv4 is available.

## Best Possible Solution

Preserve the safe loopback fallback for compatibility, but emit an unmistakable startup warning and expose the requested-versus-effective bind state through gateway status or readiness; a deliberate breaking switch to fatal startup should require explicit owner approval.

Options:

- **Diagnose degraded local mode (recommended):** Keep the loopback fallback, but warn prominently and report both requested and effective bind state in gateway diagnostics.
- **Fail explicit Tailnet startup:** Make an unavailable or unbindable explicit Tailnet address terminate startup with a non-zero exit code, accepting the compatibility change.

## Reproduction Assessment

Yes at source level: an unavailable or unbindable Tailnet address resolves to `127.0.0.1` on current main. The issue's claimed unauthenticated Tailnet exposure is not reproduced because the resulting listener is local-only.

## Solution Assessment

No, unconditional fatal startup is not clearly the best first change because it removes a documented compatibility fallback. Prominent degraded-state diagnostics preserve the safer local listener while resolving the silent operator failure.

## Label Justifications

- `P2`: The documented fallback is safe from remote exposure but creates a bounded, operator-visible reachability and diagnostics problem requiring a product decision.

## Summary

Keep this open for a maintainer product decision. Current `main` intentionally degrades an unavailable explicit `tailnet` bind to loopback, which does not create the reported remote security exposure but can silently defeat operator-selected Tailnet reachability; changing the documented fallback to a fatal startup error is compatibility- and availability-sensitive.

## What This Changes

Change gateway startup so an explicit Tailnet bind failure stops the process instead of falling back to loopback.

## Best Possible Solution

Preserve the security-narrowing loopback fallback, but emit a prominent startup warning and expose a degraded-bind state through gateway status or diagnostics; only make startup fatal if maintainers explicitly choose that compatibility break and add fresh-install, upgrade, and transient-failure proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When an explicitly configured `gateway.bind=tailnet` cannot resolve a bindable Tailscale IPv4 address, should the gateway remain available on loopback with a visible degraded-state warning, or fail startup?

Rationale: Both behaviors are defensible: loopback preserves local availability and reduces network exposure, while fatal startup more strictly enforces the operator's requested reachability. Current documentation promises the fallback, so automation should not change this contract without maintainer intent.

Likely owner: steipete

Owner reason: Recent Tailscale guidance work and live issue linkage make this the strongest available routing candidate for the compatibility-versus-availability decision.

Owner confidence: medium

Options:

- **Warn and degrade to loopback (recommended):** Keep the existing safe fallback, add a prominent startup warning and status/diagnostic indication, and cover the degraded path with focused tests.
- **Fail explicit Tailnet startup:** Reject startup when an explicit Tailnet bind is unavailable, with compatibility notes and proof covering upgrades, transient Tailscale failures, and service restart behavior.
- **Add an explicit strict policy:** Preserve the current default while adding an opt-in fail-closed policy, accepting the cost of another configuration surface.

## Reproduction Assessment

Yes for the observable fallback: current source deterministically returns loopback when explicit Tailnet address discovery fails. No high-confidence reproduction supports the claimed remote unauthenticated exposure, because this path narrows the listener to loopback.

## Solution Assessment

No, unconditional process exit is not yet established as the best fix because it replaces a documented availability fallback. A visible degraded-state warning and status signal addresses the silent failure without introducing an immediate compatibility break.

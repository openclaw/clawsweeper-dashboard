## Summary

Keep this issue open for a gateway-owner security-boundary decision. Current main source-reproduces a silent `tailnet`-to-loopback fallback; the gateway's unauthenticated-listener guard then accepts that loopback result, despite user documentation describing `tailnet` as binding to a Tailscale address and the FAQ saying unavailable explicit bind modes should not silently fall back.

## What This Changes

Make gateway startup fail visibly when an explicitly requested Tailscale listener cannot bind, rather than silently starting on loopback.

## Best Possible Solution

Treat explicit `gateway.bind: "tailnet"` as fail-closed when no bindable Tailnet IPv4 exists, emit an actionable startup error explaining how to start Tailscale or select another bind mode, and cover successful binding, missing-address failure, and authentication behavior in focused gateway tests.

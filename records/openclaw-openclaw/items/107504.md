## Summary

The reported security fail-open is not supported by current source: an unavailable Tailnet address degrades to loopback-only, and successful direct-tailnet mode already includes a loopback listener. Keep this open for a maintainer decision on whether explicit `tailnet` should warn and degrade or fail startup. Likely related people: @steipete (high confidence) and @RenzoMXD (medium confidence). citeturn948126view0turn980467view0

## What This Changes

Change explicit `gateway.bind: "tailnet"` startup behavior so an unavailable or unbindable Tailscale IPv4 does not silently degrade to loopback.

## Best Possible Solution

Preserve the loopback-only safety fallback, but emit a prominent startup/status diagnostic that explicit tailnet access is unavailable, and add focused tests plus consistent wording across the configuration reference and Tailscale guide; fail startup only if maintainers explicitly choose strict operator-intent semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When explicit `gateway.bind: "tailnet"` cannot obtain a bindable Tailscale IPv4, should startup remain locally available with a prominent degraded-state warning, or fail closed with a non-zero exit?

Rationale: Both choices are defensible: loopback fallback preserves local recovery and does not widen exposure, while fatal startup more strictly enforces explicit network intent; repository policy treats fallback removal and startup failure as compatibility-sensitive.

Likely owner: steipete

Owner reason: This account introduced explicit tailnet binding and has the strongest continuing history across gateway/Tailscale behavior and hardening.

Owner confidence: high

Options:

- **Warn and degrade locally (recommended):** Keep the loopback-only fallback, surface a clear startup/status warning, and add contract tests and aligned docs.
- **Fail explicit tailnet closed:** Exit non-zero whenever no bindable Tailnet IPv4 is available, accepting the resulting startup and upgrade availability impact.
- **Keep current silent fallback:** Retain current runtime behavior without new diagnostics, leaving remote failure as the main signal.

## Reproduction Assessment

Partly: source gives a high-confidence path for loopback fallback when no bindable Tailnet IPv4 exists, but it does not reproduce the claimed new unauthenticated exposure because loopback is already required in successful direct-tailnet mode and no LAN or public bind is added.

## Solution Assessment

No, unconditional fatal startup is not clearly the best fix; the narrower default is a visible degraded-state warning with contract tests, unless maintainers deliberately prioritize strict bind intent over local recovery.

## Label Justifications

- `P2`: The explicit Tailnet contract is violated and operators can receive a misleading healthy local gateway, but the gateway remains available on loopback and no remote security bypass is established.
- `impact:ux-friction`: Operators requesting Tailnet-only access receive no clear startup failure and must inspect networking or logs to discover that the gateway silently became local-only.

## Summary

Current `main` still turns an explicitly requested Tailnet-only bind into a loopback listener when no usable Tailscale IPv4 is found, so the documented bind contract remains unmet. The reported unauthenticated network exposure is overstated because the fallback is host-local and normal gateway authentication is not disabled, but choosing fail-fast startup instead of compatibility fallback requires an explicit gateway-owner decision.

## What This Changes

Make an explicitly configured Tailnet gateway bind fail visibly instead of silently falling back to loopback when no usable Tailscale IPv4 address exists.

## Best Possible Solution

Fail startup with an actionable diagnostic when an explicit `gateway.bind: "tailnet"` cannot resolve a Tailscale IPv4, while preserving tolerant behavior for automatic discovery modes and covering both transient-interface and no-address cases in focused tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should an explicitly configured `gateway.bind: "tailnet"` fail gateway startup when no Tailscale IPv4 is available, or remain available on loopback as a compatibility fallback?

Rationale: Both outcomes are defensible: fail-fast honors the explicit bind contract and makes operator failure visible, while loopback fallback preserves local availability during transient or restricted interface discovery failures.

Likely owner: steipete

Owner reason: Recent gateway bind and authentication history plus the issue mention make steipete the strongest available owner for this compatibility decision.

Owner confidence: high

Options:

- **Fail explicit Tailnet binds (recommended):** Reject startup with a clear Tailscale diagnostic only when the operator explicitly selected `tailnet`, while leaving automatic bind and discovery paths tolerant.
- **Keep fallback with warning:** Continue listening on loopback but emit a prominent degraded-state warning and expose the resolved bind mismatch through status and health output.
- **Add a strictness setting:** Preserve fallback by default and add an opt-in fail-fast setting, at the cost of another compatibility-sensitive configuration surface.

## Reproduction Assessment

Yes at source level: configure `gateway.bind` as `tailnet` on a host where no usable Tailscale IPv4 is returned, and the resolver path produces a loopback listener instead of rejecting the explicit bind. A live current-main run was not established during this read-only review.

## Solution Assessment

The proposed unconditional fatal behavior is not yet the best fix because it could regress transient-interface and restricted-host compatibility. The narrower approach is to fail only explicit Tailnet binds and retain tolerant automatic discovery behavior.

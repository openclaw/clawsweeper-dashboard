## Summary

Current `main` does not expose the gateway remotely when Tailnet address discovery fails; it degrades the explicit `tailnet` bind to loopback. The remaining valid problem is that this silently defeats operator-selected Tailnet reachability, and changing that shipped fallback to fail startup requires an explicit security-versus-availability decision.

## What This Changes

Make an explicitly Tailnet-bound gateway report a fatal startup error instead of silently degrading to loopback when no Tailnet address is available.

## Best Possible Solution

For an explicit `gateway.bind: "tailnet"`, perform a bounded Tailnet-readiness wait and then fail startup with a clear diagnostic and nonzero exit if no Tailnet address exists; retain the existing non-loopback safety guard and add tests for successful readiness, timeout, and absence of unintended listeners.

Rationale: Both outcomes are defensible but materially different: fail-closed preserves explicit operator intent while risking availability during Tailscale boot races, whereas loopback degradation is network-safe but silently removes the configured remote endpoint.

Owner confidence: medium

Options:

- **Wait, then fail closed (recommended):** Wait briefly for a Tailnet address, then exit clearly and nonzero rather than starting a loopback-only gateway.
- **Keep safe degradation:** Retain loopback fallback but emit a prominent startup warning and health/status signal that Tailnet reachability is unavailable.
- **Add an explicit fallback policy:** Introduce a configuration choice between strict Tailnet startup and loopback degradation, accepting additional configuration and upgrade surface.

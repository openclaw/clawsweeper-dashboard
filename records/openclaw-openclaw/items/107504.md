## Label Justifications

- `P2`: The explicit gateway bind contract is currently violated, but the fallback remains host-local and affects a bounded Tailscale setup path.
- `impact:ux-friction`: Operators can receive a running gateway on the wrong interface without a clear startup failure or recovery instruction.

## Summary

Current `main` still silently resolves an explicit `tailnet` bind request to loopback when no Tailscale IPv4 is available, contrary to the documented bind meaning. The fallback remains host-local and does not itself create unauthenticated remote access, but changing shipped startup behavior to fail closed requires an explicit compatibility decision.

## What This Changes

Make gateway startup fail with an actionable error when an explicitly requested Tailscale bind cannot be established, rather than silently binding to loopback.

## Best Possible Solution

For an explicit `gateway.bind: "tailnet"`, make startup distinguish a successful Tailscale address from loopback fallback and fail with an actionable message directing the operator to start Tailscale or choose `loopback`; keep non-startup discovery paths best-effort and add focused resolver and runtime-config tests without adding another config option.

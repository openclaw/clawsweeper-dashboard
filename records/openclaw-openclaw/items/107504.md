## Summary

Current `main` still converts an explicit `tailnet` bind request to loopback when no Tailscale IPv4 is available. That contradicts the documented meaning of the mode, although the loopback fallback does not itself create the reported remote authentication bypass; this should remain open for an upgrade-sensitive startup-policy decision.

## What This Changes

Make gateway startup report or fail when an explicitly requested Tailscale bind cannot resolve a Tailscale interface address.

## Best Possible Solution

Make explicit `gateway.bind: "tailnet"` fail startup with an actionable Tailscale diagnostic when no usable address exists, while keeping fallback behavior confined to modes such as `auto` where fallback is part of the contract, with focused resolver and startup tests.

## Reproduction Assessment

Yes at source level: make Tailscale address discovery return no IPv4 while resolving an explicit `tailnet` bind, and current `main` returns loopback. A live gateway reproduction was not established during this read-only review.

## Solution Assessment

The proposed fail-closed direction is reasonable, but changing `server-close.ts` is not the best implementation boundary; resolution and startup validation should distinguish an unavailable explicit bind from legitimate automatic fallback behavior.

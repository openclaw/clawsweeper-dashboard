- `impact:auth-provider`: The failure is in provider credential/profile routing and can select the wrong Copilot auth profile.

## Summary

Keep open: current main and v2026.6.11 still select GitHub Copilot auth profiles from raw stored-profile order in the implicit discovery/provider-auth path, while an open linked fork PR remains unmerged and conflicting.

## What This Changes

Make GitHub Copilot implicit discovery and provider auth honor `auth.order` instead of always using the first stored matching profile.

## Best Possible Solution

Refresh, adopt, or replace the open repair candidate so both Copilot plugin discovery and generic provider-auth resolution use `resolveAuthProfileOrder()` with regression coverage for config order, stored order, and unresolved tokenRef fallback.

## Reproduction Assessment

Yes, source-level: current main's Copilot helper selects `profileIds[0]` and the generic provider-auth resolver iterates raw `listAuthProfilesForProvider()` results while a focused test still asserts first-profile behavior. I did not run a live two-account Copilot setup.

## Solution Assessment

Yes. The narrow maintainable fix is to reuse `resolveAuthProfileOrder()` in the active Copilot discovery/provider-auth selection paths; the stale-order policy question in https://github.com/openclaw/openclaw/issues/83088 should stay separate.

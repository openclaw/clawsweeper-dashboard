## Summary

Keep open: current main and the latest release still load visible `sessions.usage` rows through one single-session cache read per visible entry, and the linked fix PR is open rather than merged. This issue should stay open until that PR, or an equivalent fix, lands and proves the dashboard/RPC memory-pressure warning is reduced.

## What This Changes

The issue reports transient `sessions.usage` RSS spikes on dashboard connect/reconnect caused by repeated usage-cost cache parsing and stale session-summary refresh work.

## Best Possible Solution

Land or replace the linked batched-loader fix so visible `sessions.usage` reads the usage-cost cache once per agent/request, while leaving diagnostic threshold knobs and reconnect-policy changes to separate decisions.

## Reproduction Assessment

Yes at source level: current main still creates one visible-session cache-summary task per returned visible session, and each task reads the durable usage-cost cache. I did not run a live RSS replay in this read-only review, but the reporter's release measurements match the inspected path.

## Solution Assessment

Yes, batching visible session-summary cache reads per agent with the existing batch helper is the narrowest maintainable fix. Raising diagnostics thresholds or changing Control UI reconnect behavior would mask or broaden the issue rather than remove the request-path cache parse multiplier.

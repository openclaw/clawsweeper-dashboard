## Summary

Keep open: current `main` and v2026.6.11 still run `sessions.usage` through one per-session cache-summary task, and each task reads/parses the durable usage-cost cache. This is narrower than the broader usage-cost memory-pressure tracker because it isolates the limit-sensitive dashboard/RPC false-alarm path and has a clear repair shape.

## What This Changes

Reduce transient RSS spikes and false memory-pressure warnings from dashboard `sessions.usage` by avoiding repeated usage-cost cache parses and batching stale session-summary refresh work.

## Best Possible Solution

Use a request-scoped or batched session-usage cache snapshot in `sessions.usage`, batch stale session-summary refreshes, and leave diagnostics-threshold knobs or broader worker isolation to separate maintainer decisions.

## Reproduction Assessment

Yes at source level, though I did not run a live RSS replay. Current main still builds one `loadSessionCostSummaryFromCache` task per returned session, and that loader reads/parses the durable cache on each invocation; the reporter also supplied v2026.6.11 limit=50 versus limit=1 RSS controls.

## Solution Assessment

Yes for the narrow repair: reusing the existing batch cache helper or an equivalent request-scoped cache snapshot is the smallest maintainable fix. Threshold configuration, dashboard reconnect work, and broader gateway isolation should not be bundled into the first PR.

## Summary

Keep open: current main still loads visible `sessions.usage` rows through one per-session cache-summary call that reads/parses the durable usage-cost cache each time, while the linked fix PR remains open and unmerged.

## What This Changes

The issue reports transient RSS spikes and false `rss_growth` memory-pressure warnings when dashboard `sessions.usage` reconnects repeatedly parse the usage-cost cache per visible session.

## Best Possible Solution

Keep this issue paired with https://github.com/openclaw/openclaw/pull/100054 until it lands; the end state should batch visible-session cache loads per agent and leave threshold tuning or reconnect policy to separate work.

## Reproduction Assessment

Yes at source level, though I did not run a live RSS replay. Current main still builds one cache-summary task per visible session, and each task reads/parses the durable cache; the reporter supplied v2026.6.11 limit=50 versus limit=1 RSS controls.

## Solution Assessment

Yes: reusing the existing batched cache helper for visible sessions is the narrow maintainable fix. Raising diagnostics thresholds or bundling dashboard reconnect changes would mask or broaden the first repair.

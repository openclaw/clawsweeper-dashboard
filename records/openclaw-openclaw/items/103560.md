## Label Justifications

- `P1`: Oversized attachments break a current Control UI chat-send workflow and trigger repeated reconnects.
- `impact:message-loss`: The accepted queued attachment message remains undelivered.
- `impact:crash-loop`: The oversized WebSocket frame causes repeated connection teardown and reconnect cycles.

## Summary

Keep open: current main still sends full base64 attachments through the size-limited WebSocket, and no related issue or PR owns support for larger-file transport; implementation should wait for a maintainer decision on the permanent upload boundary.

## What This Changes

Request an authenticated HTTP upload path for large Control UI attachments so WebSocket messages carry media references instead of base64 payloads.

## Best Possible Solution

Keep this as the canonical large-file transport tracker, coordinate with the stack-safe parser work, enforce serialized-size checks and terminal queue recovery immediately, and add a dedicated authenticated media-staging API only with approved quotas, cleanup, and untrusted-media semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support attachments above the WebSocket request budget through a dedicated authenticated media-staging HTTP API, or make the current budget an explicit Control UI attachment limit?

Rationale: The reconnect failure is source-reproducible, but the requested solution establishes a permanent core upload, storage, and security contract that the existing parser work intentionally leaves undecided.

Likely owner: steipete

Owner confidence: medium

Options:

- **Support staged uploads (recommended):** Approve a media-specific authenticated upload endpoint with opaque references, strict quotas, cleanup, and untrusted-content validation.
- **Enforce current ceiling:** Reject oversized attachments before reading or enqueueing them and recover any existing unsendable queued messages.

## Reproduction Assessment

Yes, from source with high confidence. Current main reads files into data URLs, embeds their base64 in `chat.send`, caps WebSocket payloads at 25 MiB, and retries reconnectable queued sends; no live current-main browser run was performed during this read-only review.

## Solution Assessment

The proposed transport separation is directionally the best solution if larger files are supported, but it should be a dedicated media-staging contract coordinated with the parser work rather than a generic workspace API or a larger WebSocket ceiling.

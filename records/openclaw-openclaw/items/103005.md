## Summary

Keep open: current main and v2026.6.11 still use exact-case Azure deployment-map lookup with per-call parsing, and this PR is a narrow candidate fix for the linked source-reproducible issue. I found no blocking patch defects, but maintainers should accept the case-insensitive env-map semantics before merge.

## What This Changes

The PR caches parsed Azure deployment maps in `packages/ai`, changes resolver lookups to lowercase model ids, and adds focused tests for case-insensitive matching, fallback casing, and cache reuse.

## Best Possible Solution

Land a helper-level fix that normalizes Azure deployment-map model ids once, preserves deployment-name values and fallback casing, and treats case-only duplicate keys as unsupported or explicitly documented.

Yes at source level: current main stores map keys as typed and performs an exact-case lookup, so a mixed-case model id misses and falls back to the raw model id. I did not establish a live Azure 404 with credentials.

## Solution Assessment

Yes: the shared helper is the right fix point because both Azure Responses callers use it; caller-level normalization would duplicate provider policy. The remaining question is only whether maintainers accept case-insensitive duplicate-key semantics.

## Summary

Keep this open as a bounded Control UI documentation and device-lifecycle triage item. Current protocol documentation confirms that browser clients must retain a stable key-derived device identity and the issued per-device token; the report gives a plausible case where Firefox permanent private browsing discards that client state, but current public guidance does not yet clearly set expectations or explain the resulting trusted-device accumulation. Likely related people: Control UI and gateway device-pairing contributors; repository history could not be inspected because the read-only command sandbox failed.

## What This Changes

Clarify why Firefox permanent private browsing re-pairs the Control UI after each restart and prevent or clearly explain the resulting accumulation of approved browser-device entries.

## System Context

The Control UI authenticates to the Gateway over WebSocket using a key-derived browser device identity and a token issued after pairing approval. The Gateway records each approved identity as a trusted device, so loss of browser-side identity state makes the next connection appear to be a new device.

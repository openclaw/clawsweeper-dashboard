## Label Justifications

- `P3`: This is a bounded presentation-consistency enhancement: widgets retain baked light/dark fallback palettes today, while forced and custom native themes lack exact live matching.
- `impact:ux-friction`: Native users can continue using widgets, but custom or forced theme choices may not be reflected accurately inside the embedded document.

## Summary

Keep open for native-app owner and product-direction review. The merged web work intentionally leaves iOS, macOS, and Android on baked system light/dark palettes, so this issue still describes a distinct capability; the existing `maintainer` label also requires explicit human handling.

## What This Changes

Add native iOS, macOS, and Android theme producers that send the existing `openclaw:widget-theme` snapshot to isolated widget web views.

## Best Possible Solution

Define one owned, typed native-to-widget token mapping aligned with the existing allowlist, implement each platform’s web-view message delivery, and add platform proof that live switching updates a loaded widget without weakening the wrapper validation.

Options:

- **Shared typed mapping (recommended):** Define one canonical native widget-token mapping and have iOS, macOS, and Android adapt their active theme values into that contract.
- **Platform-local mappings:** Let each native app derive the allowlisted snapshot independently, accepting separate maintenance and drift-prevention tests.

## Reproduction Assessment

Not applicable as a regression reproduction: this is a requested native capability. The described gap can be demonstrated by loading a widget under a forced or custom native theme and observing that it receives only its baked fallback palette.

## Solution Assessment

Unclear until maintainers choose the token-source ownership boundary. Reusing the existing allowlisted snapshot contract is the narrowest direction, but per-platform derivation versus a shared mapping is a product and maintenance decision.

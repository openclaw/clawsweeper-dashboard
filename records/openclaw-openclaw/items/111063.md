## Label Justifications

- `P1`: A fast-empty Telegram polling endpoint can currently busy-spin an ingress worker and pin a CPU core in a real deployment.
- `merge-risk: 🚨 message-delivery`: The new empty-poll wait can delay fetching an update that arrives during the one-second idle pacing interval on affected endpoints.

## Summary

The patch has strong real-runtime proof for the CPU-spin failure and no discrete correctness defect was established, but it intentionally trades up to one second of delivery delay after a fast empty response for protection against a tight polling loop. That fixed delivery policy needs Telegram-channel owner approval before merge.

## What This Changes

The PR adds an abortable one-second minimum interval after successful empty Telegram `getUpdates` polls and a regression test for immediately returned empty responses.

## Best Possible Solution

Have the Telegram channel owner explicitly accept the one-second fast-empty polling bound as the intended CPU-versus-idle-delivery tradeoff, or replace it with an owner-approved adaptive pacing policy that retains the spin protection.

## Summary

Keep open: current main and the latest release still force a build as soon as a watched source tree is dirty, before the mtime freshness check can run. The same-repo fix PR is closed unmerged, and the open fork copy is conflicting and not maintainer-editable, so the remaining action is a maintainer contract decision rather than cleanup closure.

## What This Changes

Avoid repeated `gateway:watch` rebuilds when a dirty watched source tree has no files newer than the build stamp.

## Best Possible Solution

Maintainers should choose the dirty-tree freshness contract, then either land a narrow replacement that updates `resolveBuildRequirement()`, run-node tests, and the gateway-watch regression helper together, or explicitly keep the conservative rebuild behavior and close the stale fix attempts.

Options:

- **Adopt mtime freshness for dirty trees (recommended):** Dirty watched trees would skip rebuilds when no watched file is newer than the build stamp, with tests and gateway-watch regression logic updated to match.

- **Design stronger freshness tracking:** Maintain the current rebuild behavior until a hash or stamp strategy can distinguish dirty-but-built files from dirty stale files without relying only on mtimes.

## Solution Assessment

Unclear until maintainers confirm the intended contract. The mtime fallthrough is the narrow plausible fix, but it should update the current test/helper contract together and preserve an explicit force-build escape hatch.

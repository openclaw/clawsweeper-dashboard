## Summary

This issue is still necessary: the documented hybrid contract converts FTS5 BM25 rank into lexical relevance before weighting, while the reported LIKE-on-MATCH-error path would bypass that normalization with a perfect score. The event counts do not independently prove every 1.0 result is spurious, so the focused repair should first reproduce the fallback path and lock down its score semantics. ([git.mineracks.com](https://git.mineracks.com/openclaw/openclaw/src/commit/6c0a01dc909e511b26c1806716c9a9010bd8b216/docs/concepts/memory.md?utm_source=openai))

## What This Changes

Fix hybrid memory ranking so a SQLite FTS LIKE fallback cannot assign every substring match a perfect lexical score and inflate the combined result score.

## System Context

The bundled `memory-core` plugin searches the same SQLite-backed memory index through vector similarity and FTS keyword retrieval. It normalizes each retrieval signal, merges candidates by chunk, and passes the ranked results to memory recall callers.

## Architecture Diagram

flowchart LR
  A[Memory query] --> B[Vector search]
  A --> C[FTS keyword search]
  C --> D{MATCH succeeds?}
  D -->|yes| E[BM25 relevance score]
  D -->|fallback| F[LIKE fallback relevance]
  B --> G[Hybrid score merge]
  E --> G
  F --> G
  G --> H[Ranked memory results]

## Best Possible Solution

Keep the FTS fallback for recall, but give its rows a bounded, non-perfect lexical relevance signal and add regression coverage that exercises a thrown MATCH query, the fallback rows, and hybrid ordering.

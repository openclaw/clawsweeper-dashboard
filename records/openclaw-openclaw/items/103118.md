## Summary

The current head fixes the prior plugin-policy finding, but it still conflates plugin-wide authentication metadata with credentials usable by the selected web-search provider. In the Google plugin, selecting Gemini while only the Vertex-specific `GOOGLE_CLOUD_API_KEY` is set returns true, so the small-model security audit can still report web-search exposure that runtime Gemini search cannot use.

## What This Changes

The PR rewrites web-search credential-presence detection and expands its regression matrix to account for selected providers, SecretRefs, plugin manifests, keyless providers, and plugin enable/allow/deny policy.

## Best Possible Solution

Keep the new plugin-policy filtering, but derive credential presence from the selected web-search provider entry's actual config, env, fallback, and auth contract; add a regression proving `GOOGLE_CLOUD_API_KEY` alone does not configure Gemini search while `GEMINI_API_KEY` or `GOOGLE_API_KEY` does.

## Label Justifications

- `P2`: The incomplete Gateway correlation contract can cause duplicate external deliveries but does not make the core runtime unavailable.
- `impact:message-loss`: External clients can duplicate or mis-associate assistant deliveries when completion events cannot identify the produced transcript message.
- `maturity:stable`: The affected gateway-runtime feature is M4 Stable and explicitly covers Gateway RPC APIs, events, and protocol compatibility.

## Summary

Keep open: current main and the latest release still lack a reliable run-to-transcript-message correlation field, while source inspection confirms external clients cannot derive that identity from the final event without transcript-tail inference.

## What This Changes

Add the produced assistant message’s stable identifier to the Gateway final run event so external clients can correlate, fetch, and deduplicate output.

## Best Possible Solution

Add an optional `messageId` to successful final events, populate it from the canonical run-owned assistant transcript append, omit it when no assistant row was persisted, and retain `chat.message.get` as the bounded content-fetch API.

Yes at source level: current main and v2026.6.11 separate stable transcript identity from message content and omit that identity from final events. The reported duplicate-delivery scenario was not run live, but the underlying API gap is directly reproducible from source.

## Solution Assessment

Yes, with persistence ownership: additive propagation from the canonical append is narrower and more reliable than having clients or the Gateway infer the transcript tail after completion.

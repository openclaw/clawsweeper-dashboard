## Summary

Keep open: this is useful cron webhook hardening, but the helper-level rejection changes shared validation without upgrade handling or real cron-path proof, so existing credential-bearing webhook targets can stop delivering after merge.

## What This Changes

The PR makes `normalizeHttpWebhookUrl` reject HTTP(S) cron webhook URLs whose parsed URL has a username or password.

## Best Possible Solution

Land an upgrade-safe security hardening that rejects or migrates credentialed cron webhook targets across create/update, runtime dispatch, and doctor, with focused tests and redacted real cron-path proof.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: the added helper branch returns `null` for parsed username/password, and current cron callers treat `null` as invalid or skipped webhook delivery. I did not run the PR branch end to end.

## Solution Assessment

No. The helper guard is a plausible security check, but it is not the best complete fix until cron upgrade behavior, doctor handling, and real cron-path proof cover the shared validation surface.

## Summary

Keep open: the credentialed-URL guard is useful security hardening, but this shared helper change can fail closed for existing cron webhook delivery and migration paths, and the contributor proof only exercises the helper directly rather than a real cron flow.

## What This Changes

The PR changes cron webhook URL normalization to reject http(s) URLs whose parsed URL includes username or password userinfo.

## Best Possible Solution

Keep the security guard only with maintainer-approved fail-closed policy plus upgrade behavior that warns, migrates, or otherwise gives operators a clear remediation path for existing credentialed cron webhook configurations.

## Reproduction Assessment

Yes, source-level: the PR changes the shared helper used by cron create/update, doctor migration, and runtime notification dispatch, and those callers reject or skip when it returns null. I did not run a live cron add/edit or webhook delivery flow in this read-only review.

## Solution Assessment

No. The helper-level guard is the right choke point for new inputs, but the PR is not the best mergeable fix until stored-job upgrade behavior and real cron-path proof are covered.

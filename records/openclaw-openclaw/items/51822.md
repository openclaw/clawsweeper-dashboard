## Summary

Keep open. The cron credentialed-URL rejection is a focused security hardening, but it is not merge-ready because the shared helper can invalidate stored cron webhook delivery targets after upgrade and the supplied screenshot only proves a direct helper call, not a real cron path.

## What This Changes

The PR makes `normalizeHttpWebhookUrl` reject HTTP(S) cron webhook URLs whose parsed URL contains a username or password.

## Best Possible Solution

Land an upgrade-safe cron credential policy that covers primary, completion, failure, and legacy doctor paths with focused tests, redacted warnings, and real cron-path proof, or get an explicit maintainer decision to fail closed for existing credential-bearing webhook URLs.

No. The helper guard is a plausible security check, but it is not the best complete fix until upgrade behavior, doctor handling, and real cron-path proof cover the shared validation surface.

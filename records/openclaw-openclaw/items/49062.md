## Summary

Keep open: current main and v2026.6.11 still do not define the Telegram `channel_post` plus sender-scoped per-chat `allowFrom` rule, and the linked explicit-chat PR is now closed unmerged rather than a canonical fix.

## What This Changes

The issue asks maintainers to define and document how Telegram `channel_post` commands should behave when `groups[chatId].allowFrom` is configured but Telegram does not expose a normal human sender identity.

## Best Possible Solution

Choose one Telegram `channel_post` authorization policy, preferably fail closed with a clear unsupported message when sender-scoped per-chat `allowFrom` is configured unless maintainers explicitly accept explicit-chat-only semantics, then update code, tests, docs, and live Telegram proof together.

Rationale: Either choice defines a command-authorization boundary on a Telegram surface where normal human sender identity is unavailable, and repository policy treats fallback/security-boundary choices as maintainer-owned product decisions.

- **Fail Closed For Sender-Scoped Overrides (recommended):** Reject `channel_post` commands when sender-scoped per-chat `allowFrom` is configured, with clear messaging and docs explaining that Telegram does not expose the required human sender identity.
- **Use Explicit Chat Allow Only:** Permit commands from explicitly configured channel chats and document that per-chat sender-scoped `allowFrom` is ignored on this surface.
- **Defer To Bot-To-Bot Policy Work:** Keep this open until broader Telegram bot-to-bot policy work defines channel, peer, sender, and loop-guard semantics together.

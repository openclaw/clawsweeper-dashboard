## Summary

Keep open: current main and the latest release still do not define the Telegram `channel_post` plus sender-scoped `groups[chatId].allowFrom` policy, and the official Telegram API shape confirms that channel posts may lack a human `from` sender. ([core.telegram.org](https://core.telegram.org/bots/api))

## What This Changes

Define and document how Telegram `channel_post` commands should behave when a configured Telegram group has sender-scoped `allowFrom`.

## Best Possible Solution

Choose one Telegram channel_post authorization policy, then update the Telegram runtime, docs, and focused tests so sender-scoped `allowFrom` is either clearly unsupported on channel posts or intentionally ignored after explicit chat allow.

Rationale: The code path is clear, but the correct behavior is a security/product policy choice because it decides whether channel-level authorization can substitute for sender-scoped authorization.

Owner confidence: low

Options:

- **Fail Closed With Clear Policy (recommended):** When `channel_post` lacks a human sender and a per-group sender allowlist is configured, reject the command and document the unsupported configuration.
- **Use Explicit Chat Allow:** Treat explicit `channels.telegram.groups[chatId]` allow as sufficient for channel posts and document that sender-scoped `allowFrom` is ignored on that surface.
- **Defer To Bot-To-Bot Policy:** Keep this issue open until a broader Telegram bot-to-bot policy PR defines the permanent channel-post authorization model.

## Reproduction Assessment

Yes from source, but not from a live Telegram run here: channel_post is normalized with `sender_chat.id`, while the configured `allowFrom` path expects a sender identity. ## Solution Assessment

No current fix is best yet because the remaining choice is the intended security policy. The best implementation depends on whether maintainers want explicit channel allow to substitute for sender allow, or want a clear fail-closed path.

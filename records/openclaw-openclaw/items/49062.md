## Summary

Keep open: current main and the latest release still leave Telegram channel_post command authorization undefined when sender-scoped per-chat allowFrom is configured, and the linked open PR intentionally leaves that policy out of scope.

## What This Changes

The issue asks maintainers to define and document Telegram channel_post native-command authorization when groups[chatId].allowFrom is configured but Telegram does not provide a normal human sender.

## Best Possible Solution

Choose one channel_post authorization rule, then update Telegram plugin code, focused native-command auth tests, public Telegram docs, and redacted live Telegram proof to match it.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For Telegram channel_post native commands, should a configured groups[chatId].allowFrom sender allowlist be ignored in favor of explicit chat allow, or should channel_post fail closed as unsupported when sender-scoped auth is configured?

Rationale: Telegram channel_post may not provide a human sender, while OpenClaw models groups[chatId].allowFrom as sender-scoped authorization; automation should not choose that security boundary without maintainer intent.

Likely owner: steipete

Owner reason: steipete has the strongest inspected history on Telegram access policy/docs and is the best available owner for deciding this security boundary.

Owner confidence: high

Options:

- **Fail Closed On Sender Allowlist (recommended):** Treat channel_post commands as unsupported when per-chat sender allowFrom is configured, return a clear denial or diagnostic, and document that no human sender is available.
- **Use Explicit Chat Allow Only:** Permit channel_post commands from explicitly configured channel chats and document that sender-scoped allowFrom is intentionally ignored for channel posts.
- **Defer To Bot-To-Bot Policy:** Keep this issue open until broader Telegram bot-to-bot policy work settles channel identity, peer-bot, and loop-control semantics together.

## Reproduction Assessment

No high-confidence live Telegram reproduction was run in this read-only review. Source inspection and the Bot API contract are enough to show the missing policy: native command auth is msg.from based, channel_post handling is separate, and docs/tests do not define groups[chatId].allowFrom behavior for senderless channel posts.

## Solution Assessment

Unclear until maintainers choose the security semantics. The safest narrow direction is fail-closed when sender-scoped allowFrom is configured on channel_post, but explicit-chat-only behavior could also be acceptable if documented, tested, and proven live.

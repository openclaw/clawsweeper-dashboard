## Label Justifications

- `P2`: This is a bounded Telegram authorization semantics issue with meaningful security impact but no evidence of a current core-runtime outage.

## Summary

Keep open: current main and the latest release still do not define Telegram channel_post native-command behavior when sender-scoped per-chat allowFrom is configured, and the related open PR https://github.com/openclaw/openclaw/pull/49063 explicitly leaves that policy out of scope.

## What This Changes

The issue asks OpenClaw to define and document how Telegram channel_post commands behave when groups[chatId].allowFrom is configured but Telegram does not expose the originating human sender.

## Best Possible Solution

Choose one Telegram channel_post authorization rule, then update the Telegram plugin code, focused native-command auth tests, public Telegram docs, and redacted live Telegram proof to match it.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For Telegram channel_post native commands, should a configured groups[chatId].allowFrom sender allowlist be ignored in favor of explicit chat allow, or should channel_post fail closed as unsupported when sender-scoped auth is configured?

Rationale: Telegram channel_post can lack a normal human sender, and current OpenClaw docs/code model groups[chatId].allowFrom as sender-scoped authorization, so automation cannot safely choose the security semantics.

Likely owner: steipete

Owner reason: This person has the strongest inspected history on Telegram sender-id auth and the docs where the final security policy should be encoded.

Owner confidence: high

Options:

- **Fail closed on sender-scoped allowFrom (recommended):** Treat channel_post commands as unsupported when per-chat sender allowFrom is configured, return a clear denial or diagnostic, and document that a human sender is unavailable on this surface.
- **Use explicit chat allow only:** Permit channel_post native commands from explicitly allowed channel chats and document that sender-scoped allowFrom is intentionally ignored for channel posts.
- **Defer to broader bot-to-bot policy:** Keep this issue open until the broader Telegram bot-to-bot policy work settles channel identity, peer-bot, and loop-control semantics together.

## Reproduction Assessment

No high-confidence live Telegram reproduction was run in this read-only review. Source inspection is enough to show the missing policy: native command auth is message/from based, channel_post handling is separate, and the docs/tests do not define groups[chatId].allowFrom behavior for senderless channel posts.

## Solution Assessment

Unclear until maintainers choose the security semantics. The safest narrow direction is fail-closed when sender-scoped allowFrom is configured on channel_post, but maintainers could intentionally choose explicit-chat-only behavior if docs and tests make that contract clear.

## Summary

No blocking findings. This is a focused, correctly layered Control UI bug fix: both renderers now read pending state using the same cancellation identifier already used by the action and state owner, with regression coverage and exact-head browser proof.

## What This Changes

Changes the Tasks page and chat background-task rail to key cancellation pending state by `taskId` and adds divergent-ID rendering regressions for both surfaces.

## Best Possible Solution

Land the narrow renderer changes and their two regression tests, preserving `task.id` for row/DOM identity while consistently using `task.taskId` for cancellation actions and pending state.

## Reproduction Assessment

Yes. The exact-head browser scenario supplies distinct `id` and `taskId` values through a deterministic mocked Gateway, clicks Cancel on the real `/tasks` route, and observes the current button-state failure before the fix and the disabled `Cancelling…` state afterward.

## Solution Assessment

Yes. Updating the two renderer lookups is the narrowest maintainable fix because the action and in-flight set already use `taskId`; changing the controller, collapsing protocol fields, or keying cancellation by row identity would put the repair at the wrong boundary.

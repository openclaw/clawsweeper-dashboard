## Summary

The underlying stalled-body bug is real and the shared reader is the right mechanism, but this head still loses the caller’s remaining deadline in Fal and MiniMax music paths, its shared mock does not faithfully model an absolute deadline, and the PR supplies only mocked—not real HTTP—behavior proof.

## What This Changes

The PR adds idle response-body timeouts and stall-specific errors to generated media download paths, updates provider HTTP test mocks, and adds an OpenAI stalled-stream regression test.

## Best Possible Solution

Before merge, propagate each operation’s remaining deadline into every body-read timeout, make the shared mock resolve elapsed absolute deadlines faithfully, add focused coverage for the deadline-sensitive Fal and MiniMax paths, and provide redacted terminal or live output from a local HTTP server that sends headers and then stalls its body.

Full review comments:

- **[P2] Use the remaining MiniMax timeout for the body read:** `extensions/minimax/music-generation-provider.ts:173`
  - body: `downloadTrackFromUrl` already receives the timeout remaining on the MiniMax operation deadline, but this new timer discards it and uses the 120-second default. If headers arrive near a short or nearly exhausted deadline and the body then stalls, the operation can remain pending far beyond its configured budget; pass `params.timeoutMs` with the default only as a fallback.
  - confidence: 0.98
- **[P2] Keep Fal image downloads within the operation deadline:** `extensions/fal/image-generation-provider.ts:635`
  - body: The Fal image flow has an operation deadline and resolves its request timeout from that deadline, but the new body timer resets to the fixed HTTP default. A stalled body can therefore outlive the user’s configured or remaining operation timeout; resolve the body timeout from the same deadline immediately before reading.
  - confidence: 0.96
- **[P2] Carry the Fal video deadline into the body timer:** `extensions/fal/video-generation-provider.ts:233`
  - body: The video body timer likewise uses the fixed HTTP default after submission and polling have consumed part of the operation budget. Pass the operation deadline into this download helper and resolve the remaining timeout before `readResponseWithLimit` so the final download cannot exceed the request deadline.
  - confidence: 0.95
- **[P3] Preserve elapsed time in the shared timeout mock:** `src/plugin-sdk/test-helpers/provider-http-mocks.ts:296`
  - body: This prior finding remains unresolved: reading `deadline.timeoutMs` grants the full original duration whenever the resolver is called and does not model time already consumed before the download. Resolve the remaining duration from the absolute deadline using the same production semantics so caller-path tests cannot mask deadline overruns.
  - confidence: 0.94

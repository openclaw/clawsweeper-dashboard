## Summary

Keep open: current `main` and `v2026.6.11` still provide authenticated Gateway WebSocket WebChat, device pairing, configurable DM session isolation, Matrix E2EE as a third-party channel option, and provider-backed Talk/WebRTC voice, but not the requested native no-third-party browser-held E2EE chat transport with encrypted message envelopes and per-device/per-agent browser keys.

## What This Changes

The issue proposes a native browser-based E2EE chat transport for OpenClaw with no third-party chat service, browser/device pairing, and per-agent encrypted channel isolation.

## Best Possible Solution

Define a maintainer-approved encrypted browser-channel capability and threat model first, then implement protocol/key lifecycle, per-device/per-agent routing isolation, transcript semantics, relay/recovery behavior, docs, and contract tests under the chosen core or plugin boundary.

Rationale: Current chat semantics expose message text to the Gateway, and the request changes encryption, browser/device trust, transcript storage, routing isolation, and relay fallback boundaries that automation cannot choose safely.

Likely owner: openclaw/openclaw-secops

- **Defer Native Transport:** Keep WebChat, Tailscale, Matrix E2EE, Signal, and dmScope isolation as supported paths unless maintainers later sponsor this direction.

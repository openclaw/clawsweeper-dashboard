## Summary

Keep open: current main and v2026.6.11 still expose WebChat as authenticated Gateway chat and partial third-party encrypted channel options, not native browser-held E2EE browser chat; this remains a maintainer security/product architecture decision.

## What This Changes

Request a native no-third-party browser chat transport with browser-held E2EE, per-device/per-agent keys, and isolated channels for each agent.

## Best Possible Solution

Define a maintainer-approved encrypted browser-channel capability and threat model first, then implement protocol/key lifecycle, per-device/per-agent routing, transcript semantics, relay/recovery behavior, docs, and contract tests under the chosen core or plugin boundary.

Question: Should OpenClaw pursue native no-third-party browser-held E2EE chat as a Gateway/WebChat capability, define Gateway/plugin seams for an external encrypted browser transport first, or defer this direction in favor of existing WebChat/Tailscale and encrypted channel plugins?

Rationale: Current chat semantics expose message text to the Gateway, and the request changes encryption, browser/device trust, transcript storage, routing isolation, and relay fallback boundaries that automation cannot choose safely.

Likely owner: openclaw/openclaw-secops

Owner confidence: medium

Options:

- **Approve Design-First Gateway Capability (recommended):** Define the threat model, encrypted envelope protocol, key lifecycle, transcript semantics, and Gateway/Control UI contracts before any implementation branch.
- **Make It Plugin-First:** Keep core lean by adding only the missing Gateway/plugin SDK seams needed for an external encrypted browser transport to integrate safely.
- **Defer Native Transport:** Keep WebChat, Tailscale, Matrix E2EE, Nostr, Signal, and dmScope isolation as supported paths unless maintainers later sponsor this direction.

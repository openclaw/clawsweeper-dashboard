## Summary

Keep open: current main and the latest release still provide authenticated Gateway/WebChat chat, encrypted third-party channel options, and Talk/WebRTC voice, but not the requested no-third-party browser-held E2EE chat transport with encrypted message envelopes and per-device/per-agent browser key lifecycle.

## What This Changes

Proposal to add native browser-based E2EE chat to OpenClaw so users can pair a browser and chat without a third-party messaging app or separate account.

## Best Possible Solution

Define a maintainer-approved encrypted browser-channel threat model first, then implement the chosen core or plugin-seam path with key lifecycle, encrypted envelopes, per-device/per-agent routing, transcript semantics, relay/recovery behavior, docs, and contract tests.

Summary: The issue is security-sensitive because native browser-held E2EE changes encryption, key ownership, browser/device trust, routing, relay fallback, and transcript visibility boundaries.

Concerns:

- **[medium] Define the E2EE plaintext and trust boundary:** `docs/gateway/security/index.md:198`
  - body: Current security docs treat dmScope as messaging-context isolation, not a hostile multi-tenant or host-admin boundary; native E2EE needs an explicit design for where plaintext may exist and how keys, recovery, transcripts, relays, tools, and compromised in-process code are handled.
  - confidence: 0.92
- **[medium] Avoid broad Gateway credentials for browser chat identity:** `docs/gateway/security/index.md:600`
  - body: Gateway shared-secret auth is documented as full operator access, so a native browser chat layer needs a narrower authenticated device/key model instead of reusing all-or-nothing credentials as the E2EE trust boundary.
  - confidence: 0.88

## Summary

Keep open: current main still supports authenticated Gateway WebSocket WebChat and existing channel plugins, but it does not implement native browser-held E2EE chat with encrypted per-device/per-agent channels.

## What This Changes

The issue requests a native browser-based E2EE chat transport for OpenClaw instances, avoiding third-party chat apps while isolating agent/device conversations with browser-held keys.

## Best Possible Solution

Define a maintainer-approved encrypted-browser-channel capability and threat model first, then implement protocol fields, browser key lifecycle, routing isolation, transcript semantics, relay/recovery behavior, docs, and contract tests under the chosen core or plugin boundary.

## Reproduction Assessment

Not applicable as a bug reproduction; this is a new transport and security architecture proposal. Source inspection verifies current main lacks encrypted browser chat fields and still routes chat.send plaintext through the Gateway.

## Solution Assessment

No, not yet: the WebRTC/WebCrypto sketch is plausible, but the best solution needs an explicit threat model, key lifecycle, relay fallback, transcript semantics, and core/plugin ownership decision before implementation.

## Summary

Keep open: current main and the latest release still provide authenticated Gateway WebSocket WebChat and provider-backed browser Talk, but not a browser-held E2EE chat transport with encrypted per-device/per-agent channels. The remaining work is product and security architecture, not conservative cleanup.

## What This Changes

Request a native browser-based E2EE chat layer for OpenClaw instances, avoiding third-party chat apps while isolating agent/device conversations with browser-held keys.

## Best Possible Solution

Define a maintainer-approved encrypted browser channel capability and threat model first, then implement protocol fields, browser key lifecycle, routing, transcript behavior, relay/recovery, UI, docs, and contract tests under the chosen core or plugin boundary.

## Reproduction Assessment

Not applicable as a bug reproduction; this is a new transport and security architecture proposal. Source and release inspection confirm current main and v2026.6.11 still lack encrypted browser chat fields and still route chat.send plaintext through the Gateway.

## Solution Assessment

No, not yet: the WebRTC/WebCrypto sketch is plausible, but the best solution needs an explicit threat model, key lifecycle, relay fallback, transcript semantics, and core/plugin ownership decision before implementation.

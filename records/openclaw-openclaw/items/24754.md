## Summary

Keep open: current main and v2026.6.11 still provide authenticated Gateway/WebChat chat, device pairing, Talk/WebRTC voice, and Matrix/Nostr encrypted channel options, but not the requested native no-third-party browser-held E2EE chat transport with encrypted envelopes and browser/device key lifecycle.

## What This Changes

The issue requests a native browser-based E2EE chat layer for OpenClaw instances, with per-device and per-agent encrypted channels and no third-party chat service.

## Best Possible Solution

Keep this open for maintainer-led product/security architecture: decide whether native E2EE browser chat belongs in core or behind a plugin/Gateway seam, then design encrypted envelopes, browser-held key negotiation, per-agent/per-device isolation, relay behavior, transcript policy, and Control UI/WebChat UX before implementation.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw pursue native no-third-party browser-held E2EE chat in core, define plugin/Gateway seams for an external transport first, or decline this direction in favor of existing WebChat plus channel plugins?

Rationale: Current chat semantics expose message text to the Gateway, and the request changes encryption, browser/device trust, transcript storage, routing isolation, and relay fallback boundaries that automation cannot choose safely.

Likely owner: Peter Steinberger

Owner reason: The blocking choice is primarily an encryption/key ownership and transcript visibility boundary, with WebChat product ownership following after the security model is accepted.

Owner confidence: medium

Options:

- **Approve design-first E2EE architecture (recommended):** Define the threat model, encrypted envelope protocol, key lifecycle, transcript semantics, and Gateway/Control UI contracts before any implementation branch.
- **Make it plugin-first:** Keep core lean by adding only the missing Gateway/plugin SDK seams needed for an external encrypted browser transport to integrate safely.
- **Defer native transport:** Keep WebChat/Tailscale, Matrix E2EE, Nostr encrypted DMs, Signal, and dmScope isolation as supported paths unless maintainers later sponsor this direction.

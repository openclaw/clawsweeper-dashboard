## Summary

Keep open: current main and the latest release still provide authenticated Gateway/WebChat chat with Gateway-visible message text, not the requested browser-held E2EE transport with encrypted envelopes, browser key negotiation, or per-device/per-agent encrypted browser channels.

## What This Changes

Requests a native no-third-party browser-based E2EE chat transport with per-device/per-agent isolated keys for OpenClaw Gateway/WebChat.

## Best Possible Solution

Define a maintainer-approved encrypted browser-channel capability and threat model first, then implement protocol/key lifecycle, per-device/per-agent routing isolation, transcript semantics, relay/recovery behavior, docs, and contract tests under the chosen core or plugin boundary.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw pursue native no-third-party browser-held E2EE chat as a core Gateway/WebChat capability, define Gateway/plugin seams for an external encrypted browser transport first, or defer this direction?

Rationale: Current chat semantics expose message text to the Gateway, and the request changes encryption, browser/device trust, transcript storage, routing isolation, relay fallback, and core-versus-plugin ownership boundaries that automation cannot safely choose.

Likely owner: openclaw/openclaw-secops

Owner reason: The blocking choice is primarily an encryption/key ownership and transcript visibility boundary, with WebChat product ownership following after the security model is accepted.

Owner confidence: medium

Options:

- **Approve Design-First Gateway Capability (recommended):** Define the threat model, encrypted envelope protocol, browser-held key lifecycle, transcript semantics, and Gateway/Control UI contracts before implementation.
- **Make It Plugin-First:** Keep core lean by adding only the missing Gateway/plugin SDK seams needed for an external encrypted browser transport to integrate safely.
- **Defer Native Transport:** Keep WebChat, Tailscale, Matrix E2EE, Signal, and dmScope isolation as supported paths until maintainers sponsor a native encrypted browser transport.

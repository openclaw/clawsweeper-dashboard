## Summary

Keep open: current main and the latest release still provide authenticated Gateway WebSocket WebChat and existing encrypted third-party/decentralized channel options, but not the requested browser-held native E2EE chat transport with per-device/per-agent encrypted channels. This remains product and security architecture work, not conservative cleanup.

## What This Changes

Request a native browser-based E2EE OpenClaw chat transport that does not require third-party chat apps, public exposure, account signup, or shared channel accounts.

## Best Possible Solution

Define a maintainer-approved encrypted browser-channel capability and threat model first, then implement protocol, UI, key lifecycle, routing isolation, transcript semantics, relay/recovery behavior, docs, and contract tests under the chosen core or plugin boundary.

## Reproduction Assessment

Not applicable as a bug reproduction; this is a new transport and security architecture proposal. Source and release inspection confirm current main and v2026.6.11 lack encrypted browser-chat fields and still route chat.send plaintext through the Gateway.

## Solution Assessment

No, not yet: the WebRTC/WebCrypto sketch is plausible but is not enough by itself. The best solution needs an explicit threat model, key lifecycle, relay fallback, transcript semantics, and core/plugin ownership decision before implementation.

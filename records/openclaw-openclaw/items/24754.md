## Summary

Keep open: current main and v2026.6.11 still provide authenticated Gateway/WebChat, device pairing, dmScope isolation, Matrix/Nostr encrypted channel alternatives, and browser Talk/WebRTC voice, but not the requested native no-third-party browser-held E2EE chat transport.

## What This Changes

The issue requests a built-in browser chat layer with browser-held end-to-end encryption, per-device/per-agent keys, no third-party chat app, and no public internet exposure.

## Best Possible Solution

Define a maintainer-approved encrypted browser-channel threat model and capability first, then implement the chosen core or plugin-seam path with key lifecycle, encrypted envelopes, per-device/per-agent routing, transcript semantics, relay/recovery behavior, docs, and contract tests.

Question: Should OpenClaw pursue native no-third-party browser-held E2EE chat as a Gateway/WebChat capability, define Gateway/plugin seams for an external encrypted browser transport first, or defer this direction in favor of existing encrypted channel options?

Rationale: Current chat semantics expose message text to the Gateway, and this request changes encryption, browser/device trust, transcript storage, routing isolation, relay fallback, and core-versus-plugin boundaries that automation cannot choose safely.

Likely owner: @openclaw/openclaw-secops

Owner confidence: medium

Options:

- **Make it plugin-first:** Keep core lean by adding only the missing Gateway/plugin SDK seams needed for an external encrypted browser transport to integrate safely.
- **Defer native transport:** Keep WebChat, Tailscale, Matrix E2EE, Nostr, Signal, and dmScope isolation as supported paths unless maintainers later sponsor this direction.

## Summary

Keep open: current main still has the reported replay-unsafe `stopReason=stop` / `tools>0` / `payloads=0` path, and the newer field report shows it is still affecting scheduled embedded runs on v2026.6.11. The remaining fix is safety-sensitive because current code intentionally fails closed when replay metadata has possible side effects, so maintainers need to decide the recovery/quarantine boundary rather than queue another automatic fix PR.

## What This Changes

The issue requests safer recovery, quarantine, and diagnostics for incomplete embedded turns that include tool activity but no user-visible payload.

## Best Possible Solution

Define a maintainer-approved recovery policy for replay-unsafe empty post-tool turns: safely retry or model-fallback only when current-attempt side effects are proven absent, and otherwise persist a durable quarantine/diagnostic record that prevents malformed assistant/tool state from poisoning later prompts.

## Label Justifications

- `P2`: This is a credible bounded gateway and companion-client improvement, but it does not block core runtime operation or lose durable transcript data.
- `impact:session-state`: Transcript-row pagination can make a valid conversation history appear incomplete when hidden tool traffic consumes most of the requested window.
- `impact:ux-friction`: Conversation clients must over-fetch large payloads or show nearly empty history pages, creating apparent data-loss confusion and avoidable support burden.

## Summary

Keep this issue open: current `main` still lacks a public `chat.history` request mode whose limit counts display-visible conversation messages, while existing Control UI filtering demonstrates the need without defining the general gateway contract.

## What This Changes

Add an optional `chat.history` projection that filters to visible user/assistant conversation messages and applies pagination limits and totals to that projected view.

## Best Possible Solution

Add an additive conversation projection, preferably an explicit view enum rather than overloading existing pagination, with stable transcript defaults and documented rules for visible roles, mixed content, cursors, totals, byte budgeting, and `chat.message.get` consistency.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `chat.history` gain an additive conversation-view projection, a separate conversation-history method, or remain transcript-oriented with clients responsible for oversampling?

Rationale: The need is source-reproducible, but choosing public pagination, total-count, cursor, compaction, and mixed-content semantics changes the long-lived Gateway protocol contract.

Likely owner: @steipete

Owner reason: They are already subscribed to the issue and are the strongest available routing candidate for the public Gateway contract decision.

Owner confidence: high

Options:

- **Add conversation view (recommended):** Add an optional `view: "conversation"` projection while retaining the current transcript view and pagination semantics as the default.
- **Add separate method:** Create a dedicated conversation-history RPC so transcript and presentation pagination contracts remain fully separate.
- **Keep client filtering:** Keep `chat.history` transcript-oriented and require clients to request larger pages and discard hidden rows.

## Reproduction Assessment

Yes, there is a high-confidence source reproduction: create a tool-heavy session, request `chat.history` with a small limit, and compare returned transcript rows with the visible user/assistant messages remaining after display projection. This review did not execute a fresh live current-main run.

## Solution Assessment

No final API shape is established yet. Server-side projection is the correct boundary, but an additive view contract is safer and more extensible than changing existing limit semantics or committing immediately to a narrowly defined boolean.

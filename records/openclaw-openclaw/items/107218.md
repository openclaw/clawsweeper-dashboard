## Label Justifications

- `P2`: This is a concrete, limited-blast-radius API improvement with significant efficiency and conversation-history usability impact, but it does not block core runtime operation.
- `impact:session-state`: The issue concerns how persisted session transcripts are projected and paginated for conversation clients, producing a misleadingly incomplete view of available history.
- `impact:ux-friction`: Tool-heavy sessions can appear nearly empty unless clients over-fetch and discard large payloads, creating avoidable confusion and support burden.

## Summary

Keep this issue open: current `main` and the latest release still expose transcript-row-oriented history pagination, while the report identifies a credible, source-reproducible mismatch for conversation clients; the remaining question is the public gateway contract, not whether the need exists.

## What This Changes

Requests a server-side `chat.history` view whose limit counts user-visible user/assistant conversation messages rather than raw transcript rows.

## Best Possible Solution

Add an additive typed conversation view that preserves the existing transcript view by default, applies display projection before page-size counting, uses a stable raw-position cursor, and avoids an exact visible total unless it can be computed within the bounded scan.

## Maintainer Decision

Question: What public `chat.history` view and pagination contract should companion clients use for user-visible conversation history?

Rationale: The choice affects the shared gateway protocol, cursor stability, payload compatibility, and bounded-history performance; source evidence cannot determine whether maintainers prefer a general view mode, a narrow boolean, or raw-only pagination.

Likely owner: @steipete

Owner confidence: high

Options:

- **Add typed conversation view (recommended):** Introduce an additive `view: "conversation"` mode with visible-message counting and stable cursor semantics while retaining the current default transcript view.
- **Add visible-only boolean:** Implement the proposed `visibleOnly` flag narrowly, document its interaction with offset pagination, and keep mixed-message content intact by default.
- **Keep raw pagination only:** Leave the server contract unchanged and require clients to page and aggregate raw history, accepting the documented bandwidth and shallow-page UX cost.

## Reproduction Assessment

Yes at source level: `chat.history` exposes transcript-oriented limits without a visible-message view, so tool-dense rows can consume a page before conversation messages are returned. The reported 18:1 deployment ratio was not independently reproduced live.

## Solution Assessment

Unclear: server-side projection is the correct ownership boundary, but a typed view with stable cursor semantics is safer and more extensible than coupling counting, content stripping, and exact totals to one boolean.

## Risks / Open Questions

- An exact `visibleTotal` may require scanning or materializing the whole transcript, conflicting with the bounded-tail design used to control memory and payload size.
- Offset semantics can become unstable if clients mix raw-transcript and conversation views unless the selected view is part of the pagination contract.
- Stripping non-text parts from mixed messages could remove content needed by other clients or disturb message-tool reply mirrors, so it should not be implicit in the counting mode.

## Label Justifications

- `P2`: The missing view causes inefficient and misleading history pages for tool-heavy sessions, but the transcript remains available through additional paging or over-fetching.
- `impact:session-state`: The request concerns how persisted transcript and session history is projected and paginated to operator chat clients.
- `impact:ux-friction`: Conversation clients can show only a few visible messages and appear to have lost history unless they over-fetch and filter large payloads.

## Summary

Current `main` still exposes transcript-oriented `chat.history` limits with no visible-message view, while the report provides credible deployment measurements showing that tool-heavy transcripts produce misleadingly shallow conversation pages. The public API shape needs maintainer direction before implementation.

## What This Changes

Add an optional `chat.history` view that filters display-projected history to visible user and assistant content so `limit` counts conversation messages.

## Best Possible Solution

Define an additive named history view with explicit visible-message inclusion rules, stable pagination and count metadata, preserved supported display blocks, and an unchanged raw-compatible default.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `chat.history` gain a first-class conversation-view pagination mode, and should that mode preserve supported non-text display blocks or return text/thinking-only content?

Rationale: This changes a public gateway contract and requires durable cursor, total-count, mixed-content, and compatibility semantics that implementation evidence cannot decide safely.

Likely owner: steipete

Owner confidence: high

Options:

- **Add a named conversation view (recommended):** Add an opt-in view with visible-message pagination and explicit visible totals while preserving the current default and supported display blocks.
- **Add the proposed boolean:** Add `visibleOnly` with text/thinking-only filtering, accepting a narrower contract that may require another mode for richer clients later.
- **Keep raw pagination only:** Require clients to paginate transcript rows, preserving API simplicity but retaining excessive transfer and shallow visible pages.

## Reproduction Assessment

Yes at source level: the current schema lacks a visible-message view, and the handler applies the requested limit through the history paging path before final response budgeting. The reported 273-row/15-visible-message deployment case was not independently executed against this checkout.

## Solution Assessment

The server boundary is appropriate because display projection already lives in the gateway, but the proposed boolean and optional part stripping are not yet the best durable contract; a named view with explicit pagination and mixed-content semantics is safer.

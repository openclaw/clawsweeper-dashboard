## Summary

Keep open: current main and the latest release still lack a separate Slack request-only sender boundary, and the protected maintainer label plus Slack authorization semantics require maintainer product/security review before implementation.

## What This Changes

Request a Slack per-channel `requestUsers` allowlist that lets admitted room messages remain observable while restricting which senders can create actionable requests.

## Best Possible Solution

Add a Slack-plugin-owned, restrictive-only `requestUsers` config that preserves omitted behavior and consistently gates actionability without granting admission beyond existing channel/sender checks.

## Reproduction Assessment

Yes, source-level: current main has no `requestUsers` field, Slack channel config resolves only `users`, and the inbound classifier keeps mentions, control text, aborts, and native commands as `user_request` under ambient mode. I did not run a live Slack workspace.

## Solution Assessment

Unclear until maintainer product/security approval: the proposed shape looks like the right owner boundary if it stays Slack-plugin-owned, restrictive-only, and preserves omitted behavior. The implementation should not move Slack-specific policy into core or grant access beyond existing admission gates.

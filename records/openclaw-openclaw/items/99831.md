## Summary

Keep open: current main still lacks a Slack request-only sender boundary, and the protected `maintainer` label plus new authorization/config semantics make this a maintainer product/security decision.

## What This Changes

Add a Slack per-channel `requestUsers` allowlist so a room can observe all admitted senders while only selected stable Slack user IDs can create actionable requests.

## Best Possible Solution

Add a Slack-plugin-owned, restrictive-only `requestUsers` config that preserves omitted behavior and enforces stable Slack user IDs consistently across message, control, abort, slash, and interaction ingress with focused tests and docs.

## Reproduction Assessment

Yes, source-level: current main lacks `requestUsers`, Slack channel config resolves only `users`, and source/docs show mentions, control text, abort text, and native commands stay `user_request`. I did not run a live Slack workspace.

## Solution Assessment

Unclear until maintainer product/security approval. The requested shape looks like the right end state if it stays Slack-plugin-owned, restrictive-only, preserves omitted behavior, and does not grant access beyond existing admission gates.

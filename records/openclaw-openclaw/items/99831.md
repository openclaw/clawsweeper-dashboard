- `P2`: This is a bounded Slack authorization/workflow improvement for ambient operators, not a current outage, data-loss event, or first-run release blocker.
- `impact:security`: The request is about who can turn observed Slack room traffic into actionable agent requests, which is an authorization boundary.
- `impact:ux-friction`: Operators currently must choose between dropping non-owner ambient messages or allowing admitted shared-channel senders to steer the agent.

## Summary

Keep open: current main still lacks a separate Slack request-only sender boundary, and the protected `maintainer` label plus new Slack authorization/config semantics require maintainer product and security review.

## What This Changes

Add `channels.slack.channels.<id>.requestUsers` so admitted Slack room traffic can remain ambient context while only an approved sender allowlist can create actionable agent requests.

## Best Possible Solution

Add a Slack-plugin-owned, restrictive-only `requestUsers` config that preserves omitted behavior and enforces stable Slack user IDs consistently across message, control, abort, slash, and interaction ingress with docs and tests.

## Reproduction Assessment

Yes, source-level: current main has no `requestUsers` field, Slack channel config resolves only `users`, and source/tests/docs show mentions, control text, abort text, and native commands stay `user_request`. I did not run a live Slack workspace.

## Solution Assessment

Unclear until maintainer product/security approval: a restrictive Slack-owned `requestUsers` option is the best-shaped end state if it preserves omitted behavior and does not grant access beyond existing admission gates.

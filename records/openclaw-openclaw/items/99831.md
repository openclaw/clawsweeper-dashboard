## Summary

Keep open: current main still lacks the requested Slack request-only sender boundary, and the protected `maintainer` label plus Slack authorization/config semantics require maintainer product and security review before implementation.

## What This Changes

The issue requests a Slack per-channel `requestUsers` allowlist so non-owner senders can remain observable room context without being able to create actionable agent requests.

## Best Possible Solution

Add a Slack-plugin-owned, restrictive-only `requestUsers` config after maintainer approval, preserving omitted behavior and applying consistently across message, slash, and interactive ingress without granting access beyond existing admission gates.

## Reproduction Assessment

Yes, source-level: current main has no `requestUsers` field, Slack channel config resolves only `users`, and the inbound classifier keeps mentions, controls, aborts, and native commands as `user_request` under ambient mode. I did not run a live Slack workspace.

## Solution Assessment

Unclear until maintainer product/security approval: the proposed shape looks like the right owner boundary if it stays Slack-plugin-owned, restrictive-only, and preserves omitted behavior. The implementation should not move Slack-specific policy into core or grant access beyond existing admission gates.

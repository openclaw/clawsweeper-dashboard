## Summary

Keep open: current main still lacks a separate Slack request-only sender boundary, the issue has the protected `maintainer` label, and the requested config changes Slack authorization/actionability semantics that need maintainer product and security review.

## What This Changes

Request a Slack per-channel `requestUsers` allowlist so admitted room senders can be observed as ambient context while only selected stable Slack IDs can create actionable requests.

## Best Possible Solution

Add a Slack-plugin-owned, restrictive-only `requestUsers` field that preserves omitted behavior, consistently gates message/slash/interactive actionability, and ships with schema, docs, and focused regression coverage.

## Reproduction Assessment

Yes, source-level: current main has no `requestUsers` field, Slack channel config resolves only `users`, and the ambient classifier keeps mentions, control text, aborts, and native commands as `user_request`. I did not run a live Slack workspace.

## Solution Assessment

Unclear until maintainer approval: the requested shape appears to be the right Slack-plugin boundary if it stays restrictive-only and preserves omitted behavior, but the authorization semantics are product/security-sensitive.

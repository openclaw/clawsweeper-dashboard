## Summary

Keep open: current main still lacks a separate Slack request-only sender boundary, and the protected `maintainer` label plus security-sensitive authorization semantics require maintainer judgment before implementation.

## What This Changes

Request to add a Slack `requestUsers` allowlist so a room can observe all admitted senders as ambient context while only selected senders can create actionable requests.

## Best Possible Solution

Add a Slack-plugin-owned, restrictive-only `requestUsers` config after maintainer approval, with docs and focused tests covering message mentions, implicit thread mentions, control/abort text, slash commands, interactions, empty/wildcard semantics, and omitted-key compatibility.

## Reproduction Assessment

Yes, source-level: current main has no `requestUsers` field, Slack channel config resolves only `users`, and the ambient classifier keeps mentions, control text, aborts, and native commands as `user_request`. I did not run a live Slack workspace.

## Solution Assessment

Unclear until maintainer product/security approval: the proposed shape looks maintainable if it remains Slack-plugin-owned, restrictive-only, and preserves omitted behavior. A core-wide actionability policy would be broader than the reported Slack-specific need.

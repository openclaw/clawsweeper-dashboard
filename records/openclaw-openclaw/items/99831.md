## Summary

Keep open: current main and the latest release still lack a separate Slack request-only sender boundary, and the live issue has the protected `maintainer` label plus product/security review labels.

## What This Changes

Request adding Slack `channels.slack.channels.<id>.requestUsers` so all admitted room senders can be observed while only configured senders can create actionable agent requests.

## Best Possible Solution

Add a Slack-plugin-owned, restrictive-only request-user allowlist that preserves omitted behavior and consistently gates actionability after existing admission checks.

## Reproduction Assessment

Yes, source-level: current main has no `requestUsers` field, Slack channel config resolves only `users`, and the inbound classifier keeps mentions, control text, aborts, and native commands as `user_request` under ambient mode. I did not run a live Slack workspace.

## Solution Assessment

Unclear until maintainer product/security approval: the proposed shape looks like the right owner boundary if it stays Slack-plugin-owned, restrictive-only, and preserves omitted behavior. The implementation should not move Slack-specific policy into core or grant access beyond existing admission gates.

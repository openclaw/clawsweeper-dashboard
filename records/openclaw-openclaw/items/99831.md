## Summary

Keep open: current main still lacks a separate Slack request-only sender boundary, and the protected `maintainer` label prevents cleanup auto-close even if a future implementation shape looks clear.

## What This Changes

Request a Slack `channels.slack.channels.<id>.requestUsers` allowlist so all admitted senders can be observed as ambient context while only selected Slack users can create actionable agent requests.

## Best Possible Solution

Add a Slack-plugin-owned, restrictive-only `requestUsers` config that preserves omitted behavior and enforces stable Slack user IDs consistently across message, control, abort, slash, and interaction ingress with focused tests and docs.

## Reproduction Assessment

Yes, source-level: current main lacks `requestUsers`, Slack channel config resolves only `users`, and source/tests show mentions, control text, abort text, and native commands stay `user_request`. I did not run a live Slack workspace.

## Solution Assessment

Unclear until maintainer product/security approval: `requestUsers` is the best-shaped end state if it stays Slack-plugin-owned, restrictive-only, and preserves omitted behavior. The implementation should not move Slack-specific policy into core or grant access beyond existing admission gates.

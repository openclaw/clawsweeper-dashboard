## Summary

Keep open: current main still lacks a separate Slack request-only sender boundary, and the protected `maintainer` label plus new Slack authorization/config semantics require maintainer product and security review.

## What This Changes

Request adds a Slack per-channel `requestUsers` allowlist so admitted room senders can remain ambient context without being able to create actionable agent requests.

## Best Possible Solution

Add a Slack-plugin-owned, restrictive-only `requestUsers` config that preserves omitted behavior and consistently gates actionability without granting access beyond existing admission checks.

## Reproduction Assessment

Yes, source-level: current main has no `requestUsers` field, Slack channel config resolves only `users`, and the inbound classifier keeps mentions, control text, aborts, and native commands as `user_request` under ambient mode. I did not run a live Slack workspace.

## Solution Assessment

Unclear until maintainer product/security approval: the proposed shape looks like the right owner boundary if it stays Slack-plugin-owned, restrictive-only, and preserves omitted behavior. The implementation should not move Slack-specific policy into core or grant access beyond existing admission gates.

## Summary

Keep open: current main still lacks a Slack request-only sender boundary, the issue has the protected `maintainer` label, and the remaining work is a security-sensitive product/config decision rather than conservative cleanup.

## What This Changes

Request adding Slack `channels.slack.channels.<id>.requestUsers` so ambient room observation can admit senders while only an allowlisted subset can create actionable requests.

## Best Possible Solution

Add a Slack-plugin-owned, restrictive-only `requestUsers` boundary that preserves omitted behavior and consistently gates actionability without granting access beyond existing admission checks.

## Reproduction Assessment

Yes, source-level: current main has no `requestUsers` field, Slack channel config resolves only `users`, and the inbound classifier keeps mentions, controls, aborts, and native commands as `user_request` under ambient mode. I did not run a live Slack workspace.

## Solution Assessment

Unclear until maintainer product/security approval: the proposed shape looks maintainable if it stays Slack-plugin-owned, restrictive-only, and preserves omitted behavior. The safer alternative is not to implement a broad core policy change or grant access beyond existing admission gates.

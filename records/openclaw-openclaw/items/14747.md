## Summary

Keep open. Current main and the latest release still hardcode the lane wait diagnostic default and do not expose `diagnostics.laneWaitWarnMs`; the open linked implementation PR is the active fix candidate but has not merged.

## What This Changes

Request to add a configurable lane wait diagnostic warning threshold so long-running cron or queued work can reduce non-actionable gateway log noise.

## Best Possible Solution

Land or replace the linked implementation with a narrow `diagnostics.laneWaitWarnMs` positive-ms setting that keeps the 2,000 ms default, updates schema/types/help/docs, proves runtime config updates, and leaves broader lane concurrency work separate.

## Reproduction Assessment

Yes. Source inspection shows the queue default is still `opts?.warnAfterMs ?? 2_000`, while the current diagnostics schema, typed config, and docs have no lane wait threshold field.

## Solution Assessment

Yes, the narrow `diagnostics.laneWaitWarnMs` direction is the best fit for this issue. Per-lane timeouts, adaptive thresholds, and session concurrency changes are broader product work and should remain separate.

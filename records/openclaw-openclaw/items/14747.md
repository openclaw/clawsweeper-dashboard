## Summary

Keep open. Current main and the latest release still hard-code the default lane wait diagnostic threshold at 2,000 ms and do not expose `diagnostics.laneWaitWarnMs`; the active closing PR is the right implementation path but remains open and conflicting.

## What This Changes

Request to make the command-lane wait diagnostic warning threshold configurable so long-running cron or background work does not flood gateway logs.

## Best Possible Solution

Land one focused implementation that preserves the 2,000 ms default and explicit per-call overrides while fully aligning schema, typed config, help/reference docs, and reload or restart-only semantics.

## Reproduction Assessment

Yes. Source inspection on current main and `v2026.6.11` shows queue entries without explicit overrides still use the hardcoded 2,000 ms threshold, matching the reported log-noise path.

## Solution Assessment

Yes, a focused `diagnostics.laneWaitWarnMs` setting is the narrowest maintainable shape if maintainers accept the config surface; broader per-lane or adaptive timeouts belong in separate concurrency work.

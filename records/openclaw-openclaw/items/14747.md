## Summary

Keep open. Current main and the latest release still use a hardcoded lane wait diagnostic threshold and do not expose `diagnostics.laneWaitWarnMs`; the linked implementation PR is the active fix candidate but remains open and conflicting.

## What This Changes

Request to add a configurable lane wait warning threshold so legitimate long-running cron or queued lane work does not flood gateway logs with the hardcoded 2-second diagnostic notice.

## Best Possible Solution

Land or replace the linked implementation with a narrow `diagnostics.laneWaitWarnMs` positive-ms setting that preserves the 2,000 ms default and explicit overrides while aligning schema, types, help/reference docs, tests, and reload or restart semantics.

## Reproduction Assessment

Yes. Source inspection shows the default is still `opts?.warnAfterMs ?? 2_000`, while the current diagnostics schema, typed config, generated labels/help, and docs do not expose a lane wait threshold field.

## Solution Assessment

Yes, the narrow `diagnostics.laneWaitWarnMs` direction is the best fit for this issue; per-lane timeouts, adaptive thresholds, and session concurrency changes are broader product work and should remain separate.

## What This Changes

Requests a configurable lane wait diagnostic warning threshold so long-running cron or queued work does not flood operator logs with non-actionable warnings.

## Best Possible Solution

Land or replace a narrow implementation that adds documented positive-ms `diagnostics.laneWaitWarnMs`, defaults to the current 2,000 ms behavior, updates schema/types/help/docs, proves runtime config updates, and keeps broader lane concurrency or auto-yield work separate.

Yes. Source inspection shows the queue default is still `opts?.warnAfterMs ?? 2_000` and the current diagnostics schema/docs have no lane wait threshold field.

## Summary

Keep open. Current `main` and the latest release still hard-code the lane wait warning default and do not expose `diagnostics.laneWaitWarnMs`; https://github.com/openclaw/openclaw/pull/86676 is the active closing implementation path but is still open and conflicting.

## What This Changes

The issue requests a configurable lane wait diagnostic warning threshold so long-running cron or background work can avoid non-actionable queue warning noise.

## Best Possible Solution

Land or replace https://github.com/openclaw/openclaw/pull/86676 with a narrow `diagnostics.laneWaitWarnMs` implementation that preserves the 2,000 ms default, preserves explicit per-call overrides, documents reload semantics, and covers schema plus queue tests.

## Reproduction Assessment

Yes from source, but I did not run a live repro: queue a second command behind a same-lane task for more than 2,000 ms without `opts.warnAfterMs`, and current `main` will compare against the hard-coded default. The config/schema/docs path has no `diagnostics.laneWaitWarnMs` escape hatch.

## Solution Assessment

Yes for the narrow direction: a diagnostics-scoped positive millisecond config with the current default is more maintainable than per-lane or adaptive timeout policy for this issue. The current open PR must still be rebased or replaced and reviewed for the new config surface before the issue can close.

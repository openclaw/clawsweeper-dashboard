## Label Justifications

- `P1`: The linked bug affects live channel availability during gateway cold start, and this PR is an active but currently incorrect candidate for that user-facing startup workflow.
- `merge-risk: 🚨 message-delivery`: Starting channels before the loaded channel registry is pinned can skip configured channel startup and leave inbound messages unavailable.
- `merge-risk: 🚨 availability`: The diff changes gateway startup ordering around sidecar readiness, so a wrong ordering can leave sidecars reported ready without the intended channel runtime actually running.

## Summary

Keep open for maintainer design review: the linked gateway startup bug remains valid, but this patch is not merge-ready because it can call channel startup before the loaded channel registry is pinned and then suppress the later real channel-start path.

## What This Changes

The branch adds an early `startChannels()` promise in `startGatewayPostAttachRuntime` and passes a wrapper into `startGatewaySidecars` so sidecar readiness awaits that promise instead of starting channels there.

## Best Possible Solution

Rework the startup path so channel registry state is pinned before channel startup, ACPX-dependent plugin work stays on its own readiness path, and live channel proof shows Telegram or Discord can connect before `plugins.runtime-post-bind` completes.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: the PR starts channels before runtime plugin loading pins the loaded channel registry, and `startChannels()` enumerates that registry. I did not run a live gateway in this read-only review.

## Solution Assessment

No. The requested dependency-driven startup direction is right, but this patch is not the best fix because it crosses the registry-ready boundary; a split channel-plugin load or explicit registry-ready handoff is safer.

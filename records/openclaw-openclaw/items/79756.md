## Summary

Keep open: the PR targets a valid gateway/channel startup bug, but this branch is still not merge-ready because it starts channels before the loaded channel registry is pinned and then prevents the later sidecar path from doing the real start.

## What This Changes

The PR starts gateway channels at the top of `startGatewayPostAttachRuntime()` and passes `startGatewaySidecars()` a wrapper that awaits that early channel-start promise.

## Best Possible Solution

Rework or replace the branch with a dependency-aware startup design that pins or loads channel registry state before channel startup, keeps ACPX-dependent work on its own readiness path, and proves a configured channel connects while post-bind work continues.

## Reproduction Assessment

Yes, at source level: the PR calls `startChannels()` before runtime plugin loading pins the channel registry, while channel startup enumerates loaded channel plugins from that registry. I did not run a live gateway in this read-only pass.

## Solution Assessment

No. The direction is valid, but this implementation is not the best fix because it moves channel startup earlier without first establishing a channel-registry-ready or split-loading seam.

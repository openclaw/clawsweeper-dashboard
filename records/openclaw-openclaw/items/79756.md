## Summary

Keep open: the PR targets a real P1 startup/channel availability bug, but the current patch is not merge-ready because it can run channel startup before the loaded channel registry is pinned and then skip the later registry-backed channel start.

## What This Changes

The PR starts channels early in `startGatewayPostAttachRuntime` and passes a wrapper into `startGatewaySidecars` so sidecar readiness awaits that early channel-start promise.

## Best Possible Solution

Rework the startup design so channel plugins are loaded and the channel registry is pinned before channel start, while ACPX-dependent runtime work can continue separately and sidecar readiness still reflects actual channel startup.

## Reproduction Assessment

Yes. Source inspection shows the PR starts channels before full runtime plugin loading pins the loaded channel registry, and the author's follow-up explains why the early 2.9ms trace is likely an empty-registry no-op.

## Solution Assessment

No. The dependency-decoupling goal is valid, but this implementation is not the best fix because channel startup must wait for registry readiness or a split channel-plugin load before ACPX-heavy work continues.

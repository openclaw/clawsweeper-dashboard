## Label Justifications

- `P1`: The PR targets a real gateway startup regression affecting live channel availability, but the current implementation can also leave channels unstarted.
- `merge-risk: 🚨 message-delivery`: Starting channels before the loaded registry is pinned can enumerate no channels and suppress the later normal Discord or Telegram startup path.
- `merge-risk: 🚨 availability`: The patch changes gateway startup ordering and can report sidecars ready while configured channel sidecars never actually started.

## Summary

Keep open: the linked startup bug is still real, but this patch is not safe to merge because it can run channel startup before the loaded channel registry is pinned, then skip the later normal channel-start path. The author acknowledged that registry-ordering blocker and asked for maintainer design guidance, while current main and the latest release still keep channel startup behind runtime-post-bind.

## What This Changes

The PR moves gateway channel startup into an early promise before `plugins.runtime-post-bind` and makes the sidecar phase await that promise instead of calling `startChannels` directly.

## Best Possible Solution

Keep the canonical issue open and either rework this branch or replace it with a dependency-aware startup design that pins channel registry state before channel start and proves a real channel connects before ACPX completes.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: the PR head calls `startChannels()` before the runtime plugin load that pins the channel registry, and `startChannels()` enumerates that registry. I did not run a live gateway in this read-only review.

## Solution Assessment

No. The direction of decoupling channels from ACPX is valid, but this implementation starts from the wrong side of the registry boundary; the safer fix is a split-phase channel load or an explicit registry-ready handoff.

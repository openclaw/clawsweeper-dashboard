## Label Justifications

- `P1`: The PR targets a live gateway/channel startup regression, but the current diff can suppress channel startup instead of decoupling it.
- `merge-risk: 🚨 message-delivery`: Starting channels before the loaded channel registry exists can make Discord, Telegram, and other channel plugins never start on normal boot.
- `merge-risk: 🚨 availability`: The patch changes core gateway startup ordering in a way that can leave sidecars marked ready while channel services are unavailable.

## Summary

Keep open, but the current patch is not merge-ready: it starts channels before the loaded channel registry is pinned, so the early start can resolve as a no-op and the later sidecar path will not start real channels.

## What This Changes

The PR moves gateway channel startup into an early promise before `plugins.runtime-post-bind` and makes the later sidecar channel-start path await that promise.

## Best Possible Solution

Rework or replace this PR with dependency-aware gateway startup that pins or loads the channel registry before channel start, keeps ACPX-dependent work on its own readiness path, and proves a real configured channel starts while ACPX/post-bind work continues.

## Reproduction Assessment

Yes, at source level: the PR calls `startChannels()` before runtime plugin loading pins the loaded channel registry, and channel startup enumerates loaded plugins from that registry. I did not run a live gateway in this read-only review.

## Solution Assessment

No. The direction is valid, but this implementation is not the best fix because it reorders the call without first establishing a channel-registry-ready seam.

## Label Justifications

- `P1`: The PR targets a live gateway/channel startup regression, but its current diff can suppress channel startup instead of decoupling it.
- `merge-risk: 🚨 message-delivery`: Starting channels before the loaded channel registry exists can make Discord, Telegram, and other channel plugins never start on normal boot.

## Summary

Keep open: the linked startup problem is real, but this PR is not merge-ready because it can call `startChannels()` before the loaded channel registry is pinned, then make the normal sidecar path await that no-op instead of starting configured channels.

## What This Changes

The PR starts gateway channels at the beginning of `startGatewayPostAttachRuntime` and makes the later sidecar phase await that early channel-start promise.

## Best Possible Solution

Rework or replace this branch with a dependency-aware startup seam that pins or loads the channel plugin registry before starting channels, keeps ACPX-dependent work separate, and includes focused tests plus redacted live channel startup proof.

## Reproduction Assessment

Yes, at source level: the PR calls `startChannels()` before runtime plugin loading pins the channel registry, while channel startup enumerates loaded channel plugins from that registry. I did not run a live gateway in this read-only pass.

## Solution Assessment

No. The direction is valid, but this implementation is not the best fix because it moves channel startup earlier without first establishing a channel-registry-ready seam.

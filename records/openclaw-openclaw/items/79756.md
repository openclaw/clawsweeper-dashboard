## Label Justifications

- `P1`: The PR targets a live gateway/channel startup regression, but the current patch can break configured channel startup during boot.
- `merge-risk: 🚨 message-delivery`: If channels enumerate as empty and the later start is skipped, inbound Discord or Telegram messages will not be handled after startup.
- `merge-risk: 🚨 availability`: The changed startup ordering can leave channel sidecars unavailable even though the gateway proceeds through the sidecar-ready path.

## Summary

Keep open, but the current patch is not merge-ready: it starts channels before the runtime plugin load pins the loaded channel registry, so configured channels can enumerate as empty and the later real channel-start path is skipped. The linked gateway startup issue remains open, and the contributor has already asked maintainers to choose the split-load or registry-ready design direction.

## What This Changes

The branch starts gateway channels at the beginning of `startGatewayPostAttachRuntime()` and passes a wrapper into `startGatewaySidecars()` so the later sidecar phase awaits that early channel promise.

## Best Possible Solution

Replace this with a dependency-aware startup path that pins channel registry state before channel start, then overlaps ACPX-dependent runtime work without skipping normal sidecar readiness.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: the patch calls `startChannels()` before `loadStartupPluginsIfNeeded()` pins the loaded channel registry, and `startChannels()` maps over `listChannelPlugins()`. I did not run a live gateway in this read-only review.

## Solution Assessment

No. Moving `startChannels()` earlier is directionally plausible, but this implementation is not the best fix because it runs before the channel registry is guaranteed to contain loaded channel plugins.

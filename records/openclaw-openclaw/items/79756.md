## Summary

Keep open: the PR is a focused attempt at the linked startup bug, but the patch starts channels before the full channel registry is loaded and then prevents the later sidecar path from retrying real channel startup.

## What This Changes

The PR starts gateway channels at the top of post-attach startup before plugin runtime post-bind, then makes the later sidecar channel step await that early promise.

## Best Possible Solution

Rework this PR or replace it with a dependency-aware startup design that pins the channel registry before channel start, preserves sidecar readiness semantics, and proves a real configured channel starts while ACPX/post-bind work continues.

## Reproduction Assessment

Yes at source level: the PR calls `startChannels()` before full startup plugin loading, while channel startup enumerates `listChannelPlugins()` from runtime registry state. I did not run a live gateway in this read-only review.

## Solution Assessment

No. The dependency-driven direction is reasonable, but this patch is the wrong layer because it starts channels before the channel registry contract is ready; the safer solution is a registry-ready or split-loading seam with tests and live channel proof.

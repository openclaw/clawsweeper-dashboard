## Summary

Keep open: the PR targets a real gateway startup bug, but the current branch appears incorrect because it starts channels before the runtime plugin load has pinned the loaded channel registry. The linked issue remains the canonical work, and the contributor’s later comment correctly identifies the registry-ordering blocker.

## What This Changes

The PR moves gateway channel startup into an early promise before `plugins.runtime-post-bind` and makes sidecar startup await that promise instead of directly starting channels.

## Best Possible Solution

Rework or replace this branch with a dependency-aware startup design that loads or pins configured channel plugins before starting channels, keeps ACPX-dependent work on its own readiness path, and proves a real configured channel starts before slow ACPX runtime completion.

## Reproduction Assessment

Yes, at source level: the proposed early `startChannels()` call runs before the normal runtime plugin load that pins the loaded channel registry, and `startChannels()` enumerates that registry. I did not run a live gateway in this read-only review.

## Solution Assessment

No. The requested direction is valid, but this patch is not the best fix because it starts channels before proving a populated channel registry; a split-phase channel load or explicit registry-ready handoff is safer.

## Summary

Keep open: this is a focused active fix attempt for an open gateway startup issue, but the current patch is not mergeable because it starts channels before the loaded channel registry is pinned and then suppresses the later real channel-start path.

## What This Changes

The branch starts `params.startChannels()` at the top of `startGatewayPostAttachRuntime` and passes a wrapper into `startGatewaySidecars` so the later sidecar phase awaits the early channel promise instead of starting channels itself.

## Best Possible Solution

Rework this PR around a dependency-aware startup seam that pins channel registry state before channel start, keeps one real channel-start path, and proves live Discord or Telegram availability while ACPX continues loading.

## Reproduction Assessment

Yes, source-reproducible: the early call happens before runtime plugin load pins the channel registry, while `startChannels()` enumerates `listChannelPlugins()` from that registry. I did not run a live gateway in this read-only review.

## Solution Assessment

No. Starting channels before the registry is guaranteed to be populated is the wrong implementation shape; maintainers should choose a split-load or registry-ready seam that preserves one real channel-start path.

## Summary

Keep open: the linked gateway/channel startup bug remains real, but this PR is not merge-ready because it can run channel startup before the loaded channel registry is pinned and then skip the later real sidecar channel-start path.

## What This Changes

The PR moves `startChannels()` into an early promise at the start of `startGatewayPostAttachRuntime` and passes an await-only wrapper into `startGatewaySidecars`.

## Best Possible Solution

Rework the startup sequence so channel plugin runtime is loaded and the channel registry is pinned before channel startup, then let slow ACPX-dependent work continue independently with focused lifecycle tests and live channel proof.

## Reproduction Assessment

Yes, at source level: the PR calls `startChannels()` before the runtime plugin load that pins the loaded channel registry, and `startChannels()` enumerates that registry. I did not run a live gateway in this read-only review.

## Solution Assessment

No. The requested dependency-driven startup direction is right, but this implementation starts channels before their registry source is guaranteed to contain loaded channel plugins; maintainers should choose a split-load or registry-ready design instead.

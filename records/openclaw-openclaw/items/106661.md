## Summary

Keep this issue open. Current source-level evidence supports a plausible audit false-negative for symlinked code, while the suggested blanket `realpath` traversal could escape the audit root and scan sensitive or unbounded filesystem trees; the intended security boundary needs an explicit decision before implementation.

**Likely related people:** `thebenignhacker` introduced the code-safety scanner, and `grp06` merged and integrated the original security-audit work; confidence is high.

## What This Changes

Harden deep code-safety audit traversal so symlinked code cannot evade scanning or cause unsafe filesystem traversal.

## Best Possible Solution

Teach the scanner to classify symlinks explicitly, resolve targets once, scan only targets contained within the declared trusted root with inode/realpath cycle detection and existing file limits, and emit a clear security finding for broken, cyclic, or out-of-root links; add focused file-link, directory-link, escape, and cycle tests.

Rationale: This choice defines whether audit follows runtime-reachable linked code and whether it is permitted to cross the caller's declared filesystem boundary; source inspection cannot safely infer that product-security policy.

Owner confidence: high

Options:

- **Bound and report links (recommended):** Resolve links, scan only targets contained within the declared root, detect cycles, and report out-of-root or invalid links as audit findings.
- **Reject all links:** Treat every symlink under an audited code tree as a security finding without traversing its target, prioritizing a simple fail-closed contract.
- **Keep skipping links:** Preserve the existing best-effort scanner behavior and document that symlinked payloads are outside deep code-safety coverage.

## Reproduction Assessment

Yes at source level: place a suspicious source file or directory behind a symlink inside an audited tree and the current entry-type traversal can omit it. A focused live fixture should still verify the exact plugin and skill root behaviors before implementation.

## Solution Assessment

No, not as proposed. Unconditionally switching recursive traversal to `realpath` can escape the audit root; contained resolution with cycle detection and explicit findings is the narrower maintainable solution.

## Summary

Keep this issue open. The report describes a narrow, source-reproducible correctness defect in the existing plugin inbound-claim seam: a call-dependent synchronous channel resolver can produce different conversation identities for the event and context delivered as one logical claim. The previously merged null-rejection fix addressed a different resolver outcome and does not establish pair-level reuse. The `maintainer` label and the public plugin API boundary warrant an owner review of the narrowly scoped repair.

## What This Changes

Make each plugin-owned `inbound_claim` event/context pair share one resolved inbound conversation identity instead of resolving it independently twice.

## System Context

Inbound channel messages are normalized into canonical hook data before OpenClaw dispatches them to plugin-owned conversation bindings. The hook mappers create the `inbound_claim` event and context that a bound plugin receives before normal agent handling continues or is claimed.

## Architecture Diagram

flowchart LR
  A[Inbound channel message] --> B[Canonical inbound hook data]
  B --> C[Conversation resolver]
  C --> D[Claim context]
  C --> E[Claim event]
  D --> F[Plugin-owned claim dispatch]
  E --> F
  F --> G[Handled or normal reply flow]

## Best Possible Solution

Introduce one canonical inbound-claim pair builder that resolves the channel conversation once, derives both payloads from that result, and adds a targeted plugin-owned dispatch regression using a sequential synchronous resolver; keep unrelated `message_received` cleanup separate.

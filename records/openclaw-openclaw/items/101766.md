## Summary

Keep open: the change is aimed at the right session-fork stability bug, but the timeout starts after an unbounded filesystem stat, so the reported slow-filesystem path can still block before the new wrapper runs.

## What This Changes

The PR imports `withTimeout` and wraps `readLatestRecentSessionUsageFromTranscriptAsync` in `src/auto-reply/reply/session-fork.runtime.ts` with a 10 second timeout.

## Best Possible Solution

Keep the fresh-token fast path, then bound the whole stale parent-token filesystem probe, including byte-estimate stat and transcript usage read, and return the existing cached or byte-estimate fallback on timeout with focused regression proof.

## Maintainer Decision

## Reproduction Assessment

Yes, from source inspection: current main and this PR still have an awaited `fs.stat` on the parent transcript before the new timeout begins. I did not run a live slow-filesystem reproduction in this read-only review.

## Solution Assessment

No. The timeout should cover the whole slow parent-token filesystem probe, because both the byte-estimate stat and transcript read can stall on the same slow filesystem; wrapping only the second await is too narrow.

## Summary

Keep open: current main and the latest release still route TUI `/new` through a local empty-session switch rather than the gateway reset/create lifecycle that emits `command:new` hooks, and the only open linked fix path is a conflicting fork PR rather than a safe close path.

## What This Changes

Restore hook-visible `command:new` behavior for TUI `/new` while preserving isolated per-client `tui-*` sessions.

## Best Possible Solution

Restore TUI `/new` through the existing gateway/session lifecycle so hooks observe the previous session while preserving unique `tui-*` isolation, preferably reusing the current parent-session hook pattern rather than adding a parallel TUI-only event.

## Reproduction Assessment

Yes at source level. Current TUI `/new` calls `setEmptySession(uniqueKey)` only, while the documented hook contract and gateway reset code show `command:new` hooks are emitted through the reset/create lifecycle.

## Solution Assessment

Partly. Restoring hook observability is the right fix, but the safest implementation should reuse the existing gateway/session lifecycle with correct previous-session attribution instead of emitting a separate synthetic TUI-only hook.

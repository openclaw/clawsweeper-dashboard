## Summary

Keep open: current `main` and the latest release still route TUI `/new` through a TUI-local empty-session switch, while the documented and tested hook-visible `command:new` lifecycle lives behind gateway reset/create paths. The only open closing PR is a conflicting fork PR, so this should stay open for maintainer follow-up rather than be closed or queued as a duplicate fix automatically.

## What This Changes

The issue reports a regression where TUI `/new` preserves per-client `tui-*` isolation but no longer emits hook-visible `command:new` behavior for session-memory and custom automation.

## Best Possible Solution

Restore TUI `/new` through the existing gateway/session lifecycle so `command:new`, `before_reset`, and session lifecycle hooks observe the session being left while preserving unique `tui-*` client isolation.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence reproduction path: TUI `/new` calls local `setEmptySession(uniqueKey)`, while docs and gateway reset/create code show `command:new` hooks are emitted through gateway lifecycle paths.

## Solution Assessment

No for current `main`: the reported behavior is still present. The safest repair should reuse the existing gateway/session lifecycle with correct previous-session attribution instead of adding a parallel TUI-only synthetic event.

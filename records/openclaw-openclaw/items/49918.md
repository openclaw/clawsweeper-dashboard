## Summary

Keep open: current main and the latest release still route TUI `/new` through a local empty-session switch rather than the gateway lifecycle path that emits `command:new` hooks, and the only linked closing PR is an open conflicting fork PR rather than a merged fix.

## What This Changes

Issue reports that TUI `/new` creates an isolated `tui-<uuid>` session without emitting hook-visible `command:new` new-session behavior.

## Best Possible Solution

Restore TUI `/new` through the existing gateway/session lifecycle so `command:new`, `before_reset`, and session lifecycle hooks observe the previous session while preserving unique `tui-*` isolation.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: TUI `/new` calls local `setEmptySession(uniqueKey)`, while the gateway reset/create paths are the code that emits `command:new` hooks.

## Solution Assessment

No for current main. The best repair should reuse the existing gateway/session lifecycle with correct previous-session attribution instead of adding a parallel TUI-only hook event or keeping a local-only empty-session switch.

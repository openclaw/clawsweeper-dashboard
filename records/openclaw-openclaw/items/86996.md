## Summary

Keep open: a reporter supplied a fresh recurrence on stable v2026.7.1, and the related work only addresses narrower facets such as oversized recall envelopes rather than the combined embedded-recall, Codex/native-hook, and delivery-stall behavior. This needs an explicit maintainer decision on the supported Active Memory execution model before a safe fix can be selected.

## What This Changes

The issue requests that Active Memory recall remain bounded and fail open instead of allowing its embedded Codex-backed path to delay replies, disrupt native hooks, or stall gateway delivery.

## Best Possible Solution

Choose and implement one supported, bounded fail-open Active Memory recall architecture that cannot hold the parent turn’s pre-prompt path or compete for its Codex/native-hook binding; cover direct chat, scheduled work, timeout cancellation, and successful recall with focused regression tests.

- **Adopt bounded fail-open recall (recommended):** Make recall opportunistic or independently bounded so a missed recall never delays the parent reply or shares its runtime binding.

- **Keep current semantics and document mitigation:** Preserve the existing architecture while documenting strict timeout and disablement guidance for Codex-backed deployments.

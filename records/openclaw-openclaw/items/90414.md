## Summary

Keep open for a maintainer-owned scope decision: current main has moved beyond the original one-time manager-cache theory, but recent reports still mix a gateway configuration-snapshot problem with an external `agentmemory__memory_search` tool and QMD behavior that source inspection cannot attribute to one remaining core defect.

## What This Changes

The issue asks for gateway-injected memory search to recover or give accurate remediation when CLI-visible memory indexes are healthy but the live tool reports missing or mismatched index metadata.

## System Context

Memory Core resolves an agent’s memory configuration, selects a manager for the configured backend, and exposes that manager to the gateway’s injected memory-search tool. The manager reads index state and returns either search results or an unavailable reason that the tool presents to the agent.

## Architecture Diagram

flowchart LR
  Config[Agent memory configuration] --> Resolver[Resolved memory settings]
  Resolver --> Cache[Per-agent manager cache]
  Cache --> Manager[Builtin or QMD memory manager]
  Manager --> Index[SQLite or QMD index]
  Manager --> Tool[Gateway memory-search tool]
  Tool --> Result[Search results or recovery guidance]

## Best Possible Solution

Have the memory-core owner split the mixed report into backend-specific cases: retain a canonical core issue only for a current builtin or QMD reproduction with exact tool name and gateway/CLI status, and route the installed AgentMemory integration path to its owner; then make unavailable guidance name the actual provider, index, or reload prerequisite rather than always recommending reindexing.

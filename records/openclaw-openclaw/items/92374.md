## Label Justifications

- `P1`: A documented outbound interception hook is silently bypassed on primary channel reply paths, affecting real safety and delivery workflows.
- `impact:security`: Safety, DLP, compliance, and audit plugins using `message_sending` can silently fail open on outbound agent replies.
- `impact:message-loss`: Plugin cancellation and rewrite decisions can be dropped, causing messages to be delivered without the requested suppression or modification.

## Summary

Keep this open: current main and the latest v2026.6.11 release still omit `message_sending` from the channel-configured `beforeDeliver` branch, and the open linked PRs are unmerged candidate fixes rather than implemented provenance.

## What This Changes

The issue reports that documented plugin `message_sending` hooks do not run on channel agent-reply paths when a channel supplies `dispatcherOptions.beforeDeliver`, especially Telegram.

## Best Possible Solution

Land one canonical fix that runs `message_sending` exactly once per visible outbound agent reply across shared dispatcher delivery and Telegram preview-finalized streaming, with focused regression tests and Telegram-equivalent proof.

## Reproduction Assessment

Yes. Source inspection on current main reproduces the bypass: configured `beforeDeliver` excludes `message_sending`, Telegram supplies that hook, and the existing test asserts the hook is not called; I did not run a live Telegram roundtrip in this read-only review.

## Solution Assessment

Yes as a direction: restoring the documented hook through an exactly-once delivery model is the right fix. A dispatcher-only one-liner is too narrow unless it also handles Telegram delivery-owned hooks and preview-finalized streaming without double invocation.

## Label Justifications

- `P1`: A documented pre-send safety hook is bypassed on real channel agent-reply paths, affecting deployed plugin guard and delivery workflows.
- `impact:security`: DLP, compliance, and content-filter plugins relying on `message_sending` can be silently bypassed before outbound delivery.
- `impact:message-loss`: The channel reply path ignores plugin cancel/rewrite decisions, so messages plugins intended to suppress or transform can be delivered unchanged.

## Summary

Keep this open: current main and the latest release still bypass the documented `message_sending` hook when a channel supplies `beforeDeliver`, and open linked PRs are candidate fixes rather than merged replacements.

## What This Changes

Ensure documented plugin `message_sending` hooks run on channel agent-reply delivery paths, including Telegram paths that supply their own `beforeDeliver`.

## Best Possible Solution

Land one canonical fix that composes `message_sending` into shared dispatcher paths without double-running Telegram delivery hooks, gates preview-finalized streamed finals, and includes focused regression tests plus live Telegram/security proof.

## Reproduction Assessment

Yes, by source inspection: current main and `v2026.6.11` compose channel-provided `beforeDeliver` without `buildMessageSendingBeforeDeliver`, and Telegram passes an identity `beforeDeliver` into that path. I did not run a live Telegram reproduction in this read-only sweep.

## Solution Assessment

Unclear which open PR is the best final branch, but the best fix shape is clear: preserve the documented `message_sending` contract across shared dispatch and Telegram streamed finals without double-running hooks. The narrower one-line PRs cover only part of the issue, while https://github.com/openclaw/openclaw/pull/93216 appears to target the full path but still needs maintainer handling.

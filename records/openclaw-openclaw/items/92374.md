## Label Justifications

- `P1`: A documented outbound interception hook is silently bypassed on primary channel reply paths, affecting real safety and delivery workflows.
- `impact:security`: Safety, DLP, compliance, and audit plugins using `message_sending` can silently fail open on outbound agent replies.
- `impact:message-loss`: Plugin cancellation and rewrite decisions can be ignored, causing messages to be delivered when a hook expected suppression or modification.

## Summary

Keep this open: current main and the latest v2026.6.11 tag still omit the documented `message_sending` gate whenever a channel supplies `beforeDeliver`, and the linked PRs are still open candidate fixes rather than merged implementation.

## What This Changes

Plugin `message_sending` hooks should run on channel agent-reply delivery paths, including Telegram configured `beforeDeliver` and preview-finalized replies, instead of being silently bypassed.

## Best Possible Solution

Land one canonical fix that runs `message_sending` exactly once per visible outbound agent reply across shared dispatcher delivery and Telegram preview-finalized streaming, with focused regression tests and Telegram proof.

## Reproduction Assessment

Yes. Current-main source deterministically chooses the configured `beforeDeliver` branch that excludes `message_sending`, and a July 4 comment reports the same Telegram symptom on v2026.6.9; I did not run a fresh live Telegram repro in this read-only review.

## Solution Assessment

Yes as a direction: restoring the documented pre-send hook through an exactly-once delivery model is the right fix. A shared dispatcher-only patch is too narrow because Telegram also has delivery-owned hook calls and a streamed-final path outside `deliverReplies`.

## What This Changes

The issue reports that `agents.defaults.sandbox.mode: "non-main"` makes `sessions_spawn` child sessions get accepted but never start, with no tokens, transcript, messages, or gateway log error.

## Best Possible Solution

Adopt one owner-approved startup failure contract for sandboxed subagents, then prove defaults-level `non-main` `sessions_spawn` starts normally and terminalizes or logs a forced Docker startup failure.

Rationale: Both designs can address the reported silent hang, but the choice affects the public async spawn contract, registry state, gateway wait behavior, and the overlapping startup lifecycle issue.

Options:

- **Terminalize async startup failure (recommended):** Keep the accepted response contract and add a typed logged terminal state that `sessions_history`, `subagents list`, and agent wait can show for Docker startup failures.
- **Preflight sandbox before accept:** Move enough Docker startup validation ahead of the accepted response and reject immediately, accepting added latency and compatibility implications.
- **Defer to lifecycle tracker:** Keep this issue as the sandbox-specific proof case while the broader startup lifecycle direction is decided in https://github.com/openclaw/openclaw/issues/58776.

## Reproduction Assessment

Source-reproducible but not live-reproduced here. Current main still classifies generated subagent keys as sandboxed under `non-main` and accepts the run before Docker backend startup, but the exact Docker hang was not replayed on current main.

## Solution Assessment

Unclear pending maintainer intent. A terminal async startup-failure state looks like the least disruptive fix, but the owner needs to choose that lifecycle contract over preflight rejection before implementation.

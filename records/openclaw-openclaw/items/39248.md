## Summary

Keep open: current main still supports the reported defaults-level `non-main` sandboxed `sessions_spawn` path, still lacks a typed startup-progress/failure projection for child startup, and the overlapping lifecycle PR is open, conflicting, and not a merged fix for this sandbox-specific stall.

## What This Changes

The issue reports that `agents.defaults.sandbox.mode: "non-main"` makes `sessions_spawn` accept subagent runs that then never start, leaving no tokens, messages, transcript, or useful error.

## Best Possible Solution

Adopt one owner-approved startup failure contract for sandboxed subagents, then prove defaults-level `non-main` `sessions_spawn` both starts normally and visibly logs or terminalizes a forced Docker startup failure.

- **Terminalize Async Startup Failure (recommended):** Keep the accepted response contract and add a typed logged terminal startup failure visible in session history, subagent list, and agent wait.
- **Preflight Sandbox Before Accept:** Move Docker startup validation before acceptance and reject immediately, accepting extra latency and compatibility implications.
- **Defer To Lifecycle Tracker:** Keep this issue as the sandbox-specific repro while resolving the broader startup lifecycle direction in https://github.com/openclaw/openclaw/issues/58776.

Yes at source level, but not as a live Docker reproduction here. Current source still routes generated subagent session keys through the `non-main` sandbox classification path and still lacks a typed startup-progress/failure projection; the exact Docker stall was not replayed on current main.

Unclear pending maintainer intent. A typed asynchronous startup failure looks like the least disruptive fix, but the owner should choose that contract over preflight rejection before implementation.

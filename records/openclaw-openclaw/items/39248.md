## Summary

Keep open: current main still supports `agents.defaults.sandbox.mode: "non-main"`, but the sandboxed subagent startup path still lacks a merged, live-proven contract that makes Docker/startup failure visible instead of leaving an accepted child run looking stuck.

## What This Changes

Report that sandboxed `sessions_spawn` child runs accepted under `agents.defaults.sandbox.mode: "non-main"` can stall silently with no transcript, tokens, or startup error.

## Best Possible Solution

Choose one owner-approved startup-failure contract, then add focused source coverage and live Docker proof that `non-main` sandboxed subagents either start normally or visibly terminalize with an actionable sandbox startup error.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should sandboxed subagent startup failures stay in the accepted-then-async run path with a visible terminal startup-failure state, or should `sessions_spawn` validate/start the sandbox before returning `accepted`?

Rationale: Both approaches can fix the silent stall, but they have different compatibility, latency, lifecycle-event, and gateway-wait semantics that automation should not choose alone.

Likely owner: steipete

Owner reason: This is a cross-runtime lifecycle and subagent contract decision, and steipete has the strongest current routing signal among the likely owners.

Owner confidence: medium

Options:

- **Terminalize async startup failure (recommended):** Keep the current accepted-run model, but emit/log a typed startup failure that updates session, subagent, and gateway wait state when sandbox startup fails.
- **Preflight before accepted:** Start or validate the sandbox before returning `accepted`, trading clearer immediate failure for extra latency and a stricter spawn contract.
- **Route through lifecycle tracker:** Keep this issue as the sandbox proof case while https://github.com/openclaw/openclaw/issues/58776 owns the broader `first-progress`/`startup-failed` lifecycle design.

## Reproduction Assessment

No live current-main Docker run was performed, so this is not fully reproduced. Source inspection gives a credible reproduction path: `non-main` classifies the child as sandboxed, Docker/backend startup happens during embedded run startup, and current lifecycle consumers still have no typed startup-failure state.

## Solution Assessment

Unclear until maintainers choose the lifecycle contract. A pure Docker error-string fix is too narrow; the durable solution should make the accepted child run visibly fail or reject before acceptance with focused upgrade-aware proof.

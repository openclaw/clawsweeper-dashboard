## Summary

Keep open: current main still supports the reported defaults-level `non-main` sandboxed `sessions_spawn` path, the latest release has no merged fix for the sandbox-specific startup stall, and the overlapping lifecycle work remains unmerged and not a proven replacement for this issue.

## What This Changes

The issue reports that `agents.defaults.sandbox.mode: "non-main"` makes `sessions_spawn` child runs return accepted but never initialize, leaving empty running sessions until timeout.

## Best Possible Solution

Adopt one owner-approved startup failure contract for sandboxed subagents, then prove defaults-level `non-main` `sessions_spawn` starts normally and visibly logs or terminalizes a forced Docker startup failure.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should sandboxed subagent startup failures stay in the accepted-then-async lifecycle path with a typed terminal startup failure, or should `sessions_spawn` preflight Docker sandbox startup before returning accepted?

Rationale: Both designs can address the silent hang, but the choice affects the public async spawn contract, registry state, gateway wait/session projections, and the overlapping startup lifecycle issue.

Likely owner: steipete

Owner reason: The history trail and path ownership point to this owner path for the async spawn, sandbox, and lifecycle contract decision.

Owner confidence: high

Options:

- **Terminalize Async Startup Failure (recommended):** Keep the accepted response contract and add a typed logged terminal state that `sessions_history`, `subagents list`, and agent wait can show for Docker startup failures.
- **Preflight Sandbox Before Accept:** Move enough Docker startup validation ahead of the accepted response and reject immediately, accepting added latency and compatibility implications.
- **Defer To Lifecycle Tracker:** Keep this issue as the sandbox-specific proof case while the broader startup lifecycle direction is decided in https://github.com/openclaw/openclaw/issues/58776.

## Reproduction Assessment

Source-reproducible but not live-reproduced here. Current main still classifies generated subagent keys as sandboxed under `non-main` and accepts the run before Docker backend startup, but the exact Docker hang was not replayed on current main.

## Solution Assessment

Unclear pending maintainer intent. A terminal async startup-failure state looks like the least disruptive fix, but the owner needs to choose that lifecycle contract over preflight rejection before implementation.

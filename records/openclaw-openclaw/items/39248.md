## Summary

Keep open: current main still supports the reported `non-main` sandboxed `sessions_spawn` path, and no merged fix or current-main live proof shows Docker-backed child runs now start or fail visibly instead of staying accepted and silent.

## What This Changes

The issue reports that `agents.defaults.sandbox.mode: "non-main"` causes Docker-backed subagents spawned through `sessions_spawn` to be accepted but never initialize, emit messages, create transcripts, or log errors.

## Best Possible Solution

Adopt one owner-approved startup failure contract for sandboxed subagents, then prove defaults-level `non-main` `sessions_spawn` starts normally and terminalizes or logs a forced Docker startup failure.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should sandboxed subagent startup failures stay in the accepted-then-async lifecycle path with a typed terminal failure, or should `sessions_spawn` preflight Docker sandbox startup before returning accepted?

Rationale: Both designs can address the silent hang, but the choice changes the public async spawn contract, session/run state, gateway wait behavior, and the overlap with the broader startup lifecycle issue.

Likely owner: steipete

Owner reason: The strongest combined history trail across subagent spawning, sandbox helpers, and lifecycle outcomes points to this owner path.

Owner confidence: high

Options:

- **Terminalize async startup failure (recommended):** Keep the accepted response contract and add a typed logged terminal state that `sessions_history`, `subagents list`, and `agent.wait` can show for Docker startup failures.
- **Preflight sandbox before accept:** Move enough Docker startup validation ahead of the accepted response and reject immediately, accepting added latency and compatibility implications.
- **Defer to lifecycle tracker:** Keep this issue as the sandbox-specific proof case while the broader startup lifecycle contract is decided in https://github.com/openclaw/openclaw/issues/58776.

## Reproduction Assessment

## Solution Assessment

Unclear pending maintainer intent. A terminal async startup-failure state looks like the least disruptive fix, but the owner needs to choose that lifecycle contract over preflight rejection before implementation.

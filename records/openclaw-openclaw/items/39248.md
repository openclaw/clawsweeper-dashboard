## Summary

Keep open: current main still supports the reported `non-main` sandboxed subagent path, accepts child runs before sandbox backend startup, and has no merged lifecycle fix that makes Docker startup failure visibly terminal.

## What This Changes

Report that `agents.defaults.sandbox.mode: "non-main"` makes `sessions_spawn` subagents appear accepted/running but never start, log, or produce transcript state.

## Best Possible Solution

Choose one startup failure contract, implement it consistently across sandboxed subagent spawn, lifecycle events, registry projections, and history/list surfaces, then prove it with live Docker success and forced-failure runs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should sandboxed subagent startup failures stay accepted and become a typed async terminal failure, or should `sessions_spawn` preflight Docker startup before returning accepted?

Rationale: Both designs can address the silent hang, but the choice changes the public non-blocking spawn contract, gateway wait behavior, and the broader startup lifecycle work in #58776.

Likely owner: steipete

Owner reason: The strongest historical signal is the existing sessions_spawn sandbox inheritance and sandbox backend ownership trail.

Owner confidence: high

Options:

- **Terminalize async startup failure (recommended):** Keep the immediate accepted response and add a typed, logged terminal state visible through subagent status/history/wait paths when sandbox startup fails.
- **Preflight sandbox before accept:** Move enough sandbox backend validation ahead of the accepted response and reject immediately, accepting added latency and compatibility impact.
- **Defer to lifecycle tracker:** Keep this issue as the sandbox-specific proof case while #58776 decides the broader startup progress/failure lifecycle contract.

## Reproduction Assessment

Source-reproducible but not live-reproduced here: current main classifies generated subagent keys as sandboxed under `non-main` and starts the sandbox backend in the async run path after the accepted response.

## Solution Assessment

Unclear pending maintainer intent; typed async startup failure appears least disruptive to the documented non-blocking contract, but maintainers must choose it over preflight rejection.

## Summary

Keep open: current main still supports the reported defaults-level `non-main` sandboxed subagent path, and I found no merged current-main fix or live proof that Docker-backed `sessions_spawn` now starts or fails visibly instead of remaining accepted and silent.

## What This Changes

The issue reports that `agents.defaults.sandbox.mode: "non-main"` causes native `sessions_spawn` child sessions to be accepted but never initialize or record progress.

## Best Possible Solution

Adopt one owner-approved startup failure contract for sandboxed subagents, then prove defaults-level `non-main` `sessions_spawn` starts normally and terminalizes or logs a forced Docker startup failure.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should sandboxed subagent startup failures stay in the accepted-then-async lifecycle path with a typed terminal startup failure, or should `sessions_spawn` preflight Docker sandbox startup before returning accepted?

Rationale: Both designs can address the reported silent hang, but the choice affects the public async spawn contract, registry state, gateway wait behavior, and the overlapping startup lifecycle issue.

Likely owner: steipete

Owner reason: The strongest history signal for the sandboxed `sessions_spawn` contract points to this owner path.

Owner confidence: high

Options:

- **Terminalize async startup failure (recommended):** Keep the accepted response contract and add a typed logged terminal state that `sessions_history`, `subagents list`, and agent wait can show for Docker startup failures.
- **Preflight sandbox before accept:** Move enough Docker startup validation before the accepted response and reject immediately, accepting added latency and compatibility implications.
- **Defer to lifecycle tracker:** Keep this issue as the sandbox-specific proof case while the broader lifecycle contract is settled in https://github.com/openclaw/openclaw/issues/58776.

## Reproduction Assessment

Source-reproducible but not live-reproduced here. Current main still classifies generated subagent keys as sandboxed under `non-main` and accepts the run through the async child path, but the exact Docker hang was not replayed on current main.

## Solution Assessment

Unclear pending maintainer intent. A typed async startup-failure state looks like the least disruptive fix, but the owner needs to choose that lifecycle contract over preflight rejection before implementation.

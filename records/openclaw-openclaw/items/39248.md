## Summary

Keep open: current main still supports the reported `non-main` sandboxed subagent path, still accepts `sessions_spawn` before Docker sandbox startup, and no merged fix proves the child now starts or fails visibly instead of remaining an accepted silent run.

## What This Changes

The issue reports that Docker-backed `sessions_spawn` subagents stall silently when `agents.defaults.sandbox.mode` is `non-main`.

## Best Possible Solution

Adopt one owner-approved startup failure contract for sandboxed subagents, then prove defaults-level `non-main` `sessions_spawn` starts normally and terminalizes or logs a forced Docker startup failure.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Docker-backed `sessions_spawn` startup failures remain accepted-then-async with a typed terminal startup failure, or should sandbox startup be preflighted before returning accepted?

Rationale: Both designs can address the silent hang, but the choice changes the public async spawn contract, registry/session state semantics, gateway wait behavior, and the overlap with the broader startup lifecycle tracker.

Likely owner: steipete

Owner reason: This handle has the strongest history signal across the current subagent spawn, sandbox runtime, and gateway dispatch contract involved in the decision.

Owner confidence: high

Options:

- **Terminalize async startup failure (recommended):** Keep the accepted response contract and add a typed logged terminal state that `sessions_history`, `subagents list`, and waits can show for Docker startup failures.
- **Preflight sandbox before accept:** Move enough Docker startup validation before the accepted response and reject immediately, accepting added latency and compatibility risk.
- **Defer to lifecycle tracker:** Keep this issue as the sandbox-specific proof case while deciding the broader startup lifecycle direction in https://github.com/openclaw/openclaw/issues/58776.

## Reproduction Assessment

Source-reproducible, but not live-reproduced here. Current main still classifies generated subagent keys as sandboxed under `non-main` and accepts the run before Docker backend startup; the exact Docker hang still needs live proof.

## Solution Assessment

Unclear pending maintainer intent. A typed async startup-failure terminal state looks least disruptive, but the owner needs to choose that lifecycle contract over preflight rejection before implementation.

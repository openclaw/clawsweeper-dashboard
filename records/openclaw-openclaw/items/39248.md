## Summary

Keep open: current main and the latest release still support the reported `non-main` sandboxed `sessions_spawn` path, and the code still accepts the child run before sandbox startup without a merged, proven lifecycle/error-state fix for Docker-backed subagent initialization.

## What This Changes

The issue reports that `agents.defaults.sandbox.mode: "non-main"` makes `sessions_spawn` return an accepted child run that never starts, produces no transcript or tokens, and logs no useful error.

## Best Possible Solution

Choose and implement one owner-approved startup-failure contract for sandboxed subagents, then prove `non-main` `sessions_spawn` both starts normally and reports a forced Docker startup failure visibly.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should sandboxed subagent startup failures remain in the accepted-then-async lifecycle path with a typed terminal startup failure, or should `sessions_spawn` preflight Docker sandbox startup before returning accepted?

Rationale: Both designs can fix the silent hang, but the choice affects the public non-blocking spawn contract, gateway wait semantics, session state, and the overlapping startup lifecycle issue.

Likely owner: steipete

Owner reason: The strongest source and history trail for the subagent spawn, sandbox classification, and gateway accepted-run contract points to this owner path.

Owner confidence: high

Options:

- **Terminalize async startup failure (recommended):** Keep the accepted response contract and add a typed logged terminal state that `sessions_history`, `subagents list`, and agent wait can show for Docker startup failures.
- **Preflight sandbox before accept:** Validate enough Docker sandbox startup before returning accepted, trading clearer immediate errors for added spawn latency and compatibility impact.
- **Defer to lifecycle tracker:** Keep this issue as the sandbox-specific repro case while the broader lifecycle direction is decided in https://github.com/openclaw/openclaw/issues/58776.

## Reproduction Assessment

Source-reproducible, but not live-reproduced here. Current main still classifies generated subagent keys as sandboxed under `non-main` and accepts the run before Docker backend startup, but the exact Docker hang was not replayed on current main.

## Solution Assessment

Unclear pending maintainer intent. A typed async startup-failure terminal state looks like the least disruptive fix, but an owner should choose that lifecycle contract over preflight rejection before implementation.

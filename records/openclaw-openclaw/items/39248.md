## Summary

Keep open: current main still supports the reported `non-main` sandboxed `sessions_spawn` path, still returns accepted child runs asynchronously, and still lacks a merged startup-failure/progress contract for this sandbox-specific stall; the overlapping lifecycle PR is open and conflicting rather than a safe replacement.

## What This Changes

The issue reports that `agents.defaults.sandbox.mode: "non-main"` causes native `sessions_spawn` child sessions to be accepted but remain empty, running, and silent until timeout.

## Best Possible Solution

Keep this as the sandbox-specific tracker, have maintainers choose the startup-failure contract, then prove both normal and forced-failure Docker `non-main` `sessions_spawn` behavior on current main while coordinating with the broader lifecycle issue.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should sandboxed native `sessions_spawn` keep the accepted asynchronous response and later terminalize with a typed/logged startup failure, or should it preflight enough sandbox startup work to reject before returning accepted?

Rationale: That choice changes gateway wait semantics, subagent registry/session state, user-visible diagnostics, and compatibility for the documented non-blocking spawn contract, so automation should not pick the permanent API behavior alone.

Likely owner: steipete

Owner reason: The product/API choice crosses the subagent lifecycle and terminal-outcome surfaces where steipete has the clearest historical ownership signal.

Owner confidence: high

Options:

- **Terminalize Async Startup Failure (recommended):** Keep the documented accepted response and add visible typed/logged terminal startup failure state in session history, subagent list, gateway wait, and completion handling.
- **Preflight Sandbox Before Accept:** Move enough sandbox startup validation before the accepted response so `sessions_spawn` fails fast, accepting extra spawn latency and compatibility review.
- **Resolve Through Lifecycle Tracker:** Keep this issue open while replacing the conflicting lifecycle PR with a current-main implementation that proves the sandbox-specific Docker path.

## Reproduction Assessment

Yes at source level, but not as live Docker proof. Current main still classifies generated child subagent keys as sandboxed under `non-main`, accepts the spawn asynchronously, and lacks a typed startup-failure/progress projection for accepted child runs.

## Solution Assessment

Unclear pending maintainer intent. A typed asynchronous startup failure looks least disruptive, but maintainers should choose that contract over pre-accept rejection before implementation.

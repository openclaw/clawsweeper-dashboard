## Label Justifications

- `P1`: The report describes a broken core subagent workflow where accepted child sessions never start and eventually time out.
- `impact:session-state`: The affected behavior is subagent session lifecycle state: accepted child sessions remain running with no transcript or token progress.
- `impact:crash-loop`: The user-visible failure is a hang-like availability issue for spawned agents until the run timeout fires.
- `maturity:stable`: `sessions_spawn` is covered by the Gateway runtime Session APIs (`agents.subagents`), and Gateway runtime is scored M4 Stable in the maturity scorecard.

## Summary

Keep open: current main still routes generated subagent keys into the sandbox under `non-main` and acknowledges `agent.run` before sandbox startup, and no merged current or shipped change proves Docker-backed subagent initialization failures become visible or recover cleanly.

## What This Changes

Reports that `agents.defaults.sandbox.mode: "non-main"` causes `sessions_spawn` subagents to be accepted but never initialize or produce session progress.

## Best Possible Solution

Keep this as the sandbox-specific tracker, choose the startup-failure contract, then implement and live-prove both successful and forced-failure Docker `non-main` `sessions_spawn` behavior on current main.

- **Terminalize async startup failures (recommended):** Keep the accepted response contract and make Docker startup failure visible as typed terminal state in logs, session history, subagent status, and waits.

- **Fold into lifecycle tracker:** Close or defer the sandbox-specific path only after https://github.com/openclaw/openclaw/issues/58776 has a current-main fix that proves this Docker startup case too.

Yes at source level, but not as a live Docker reproduction here. Current main still classifies generated subagent session keys as sandboxed under `non-main`, returns `accepted`, and starts sandbox resolution inside the child run.

## Solution Assessment

Unclear pending maintainer intent. A typed asynchronous startup failure path appears least disruptive, but maintainers should choose that contract over pre-accept sandbox rejection before implementation.

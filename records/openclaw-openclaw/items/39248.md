## Summary

Keep open: current main still has the reported shape where generated subagent keys are classified as `non-main` sandboxed, the gateway returns `accepted` before sandbox startup, and no merged current-main change proves the Docker-backed child initialization stall is resolved.

## What This Changes

The issue reports that `agents.defaults.sandbox.mode: "non-main"` causes `sessions_spawn` child agents to be accepted but never initialize or emit progress.

## Best Possible Solution

Keep this as the sandbox-specific tracker, choose the startup-failure contract, then prove both normal and forced-failure Docker `non-main` `sessions_spawn` behavior on current main.

Rationale: The choice changes the public async spawn contract, registry/session state semantics, and the overlap with the broader lifecycle-event work, so a maintainer should choose before another automated implementation attempt.

Options:

- **Terminalize Async Startup Failures (recommended):** Keep the accepted response contract and make sandbox startup failures visible as typed terminal state in logs, session history, subagent status, and waits.
- **Preflight Sandbox Before Accept:** Move enough sandbox initialization before the accepted response to fail fast, accepting extra latency and compatibility review for existing callers.
- **Defer To Lifecycle Tracker:** Leave this sandbox-specific issue open while maintainers settle the broader lifecycle contract in https://github.com/openclaw/openclaw/issues/58776.

## Reproduction Assessment

Yes at source level, but not as a live Docker reproduction here. Current main still routes generated subagent session keys through `non-main` sandbox classification, returns accepted asynchronously, and starts sandbox resolution inside the dispatched child run.

## Solution Assessment

Unclear pending maintainer intent. A typed asynchronous startup failure appears least disruptive, but maintainers should choose that contract over pre-accept sandbox rejection before implementation.

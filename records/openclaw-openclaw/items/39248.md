## Summary

Keep open: current `main` still supports and routes defaults-level `non-main` sandboxed subagent sessions, but there is no merged fix or live Docker-backed proof that the reported accepted-then-silent `sessions_spawn` stall now starts or terminalizes with an actionable sandbox startup failure.

## What This Changes

The issue reports that `agents.defaults.sandbox.mode: "non-main"` causes `sessions_spawn` subagents to be accepted but never initialize or surface an error.

## Best Possible Solution

Add one owner-approved startup failure contract for sandboxed subagents, then prove `sessions_spawn` with defaults-level `non-main` both starts normally and terminalizes/logs a forced Docker startup failure.

Kind: product_direction

Question: Should sandboxed subagent startup failures remain accepted asynchronous runs that terminalize with a typed startup failure, or should `sessions_spawn` preflight sandbox startup and reject before returning accepted?

Rationale: Both shapes can address the user-visible hang, but the choice affects gateway accepted semantics, subagent registry state, agent.wait behavior, and the overlapping startup lifecycle contract in https://github.com/openclaw/openclaw/issues/58776.

Likely owner: steipete

Owner confidence: high

Options:

- **Terminalize async startup failure (recommended):** Keep the accepted async spawn contract, but emit/log a typed startup failure and prove registry, session UI, and wait callers see it for Docker sandbox startup failures.
- **Preflight before accept:** Move enough sandbox startup validation ahead of the accepted response to fail fast, accepting the latency and compatibility implications for existing callers.
- **Defer to lifecycle issue:** Treat this issue as blocked on the broader lifecycle contract and keep it as the sandbox-specific proof case.

## Reproduction Assessment

Source-reproducible, not live-reproduced here: current source still accepts the child run before sandbox startup and then resolves Docker sandbox context downstream, matching the reported failure window. The exact Docker stall still needs a current-main live repro.

## Solution Assessment

Unclear pending maintainer intent: terminalizing asynchronous startup failure looks like the safer default, but the repository needs one owner-approved contract rather than parallel preflight and lifecycle fixes.

## Summary

Keep open: the supported `non-main` sandboxed subagent path is still present on current `main`, the gateway still acknowledges agent runs before the embedded runner resolves the Docker sandbox, and no merged fix or live current-main proof shows the reported silent Docker-backed stall is gone.

## What This Changes

Report that `agents.defaults.sandbox.mode: "non-main"` can make `sessions_spawn` accept a subagent run that never initializes, records messages, or logs an error.

## Best Possible Solution

Choose one owner-approved startup failure contract for sandboxed subagents, then implement it through sandbox startup, session state, user-visible diagnostics, and live Docker validation.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should a sandboxed subagent Docker startup failure remain an accepted asynchronous run that terminalizes visibly, or should `sessions_spawn` preflight the sandbox enough to reject before returning accepted?

Rationale: Both choices can fix the silent stall, but they change the public async spawn contract, session/run state semantics, and overlap with the broader lifecycle issue.

Likely owner: steipete

Owner reason: The strongest feature-history trail for `sessions_spawn` sandbox inheritance and gateway accepted semantics points to this owner path.

Owner confidence: high

Options:

- **Terminalize async startup failure (recommended):** Keep `sessions_spawn` non-blocking and add a typed logged terminal state that `sessions_history`, `subagents list`, and waits can show for Docker startup failures.
- **Preflight sandbox before accept:** Validate enough of Docker sandbox startup before returning accepted, trading compatibility and latency for immediate rejection.
- **Defer to lifecycle tracker:** Treat this issue as the sandbox-specific proof case while maintainers decide the broader lifecycle contract in https://github.com/openclaw/openclaw/issues/58776.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Source-reproducible but not live-reproduced here: current main still supports the reported config path and accepts the run before Docker sandbox startup, but I did not replay the exact Docker hang on current main.

## Solution Assessment

Is this the best way to solve the issue? Unclear pending maintainer intent: a typed terminal async startup failure looks least disruptive, but maintainers need to choose that contract over preflight rejection before implementation.

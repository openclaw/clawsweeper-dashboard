## Summary

Keep open: current main still keeps runtime auth on SQLite and does not read stranded canonical `auth-profiles.json`, while the safe JSON-to-SQLite import remains doctor-owned. The issue is still necessary because the overlapping open PR addresses only part of the auth recovery shape and is blocked on runtime-boundary concerns, and the fallback-chain startup diagnostic request remains unresolved.

## What This Changes

The issue reports that the 2026.6.x SQLite auth-store migration can leave existing JSON OAuth/token profiles unused after upgrade, causing provider auth and configured model fallbacks to fail silently.

## Best Possible Solution

Keep steady-state runtime reads SQLite-only, and add a maintainer-approved startup/update diagnostic or one-shot migration boundary that surfaces stranded auth profiles and warns when configured fallback chains have no resolvable authenticated providers.

## Reproduction Assessment

Yes at source level, but not with a live upgrade run. Current main reads per-agent auth profiles from SQLite, tests that legacy `auth-profiles.json` is not read at runtime, and wires the JSON import through doctor repair rather than startup/runtime.

## Solution Assessment

Unclear as an implementation choice. The bug is valid, but the best fix needs maintainer direction on a startup/update migration or warning boundary; a steady-state runtime JSON fallback is the wrong layer under current repository policy unless explicitly approved.

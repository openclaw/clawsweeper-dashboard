## Summary

Keep open: current main still preserves the SQLite-only runtime auth-store invariant, and the legacy JSON-to-SQLite import remains doctor/repair owned rather than a normal startup or runtime migration. Merged fixes cover verification-before-cleanup and config-only default-agent imports, but they do not fully cover this report's first-run/update warning or dead fallback-chain diagnostic request; the overlapping open PR is not a safe canonical close target yet.

## What This Changes

The issue reports that upgrading from 2026.5.x to 2026.6.x can strand legacy JSON auth profiles outside the new SQLite auth store, leaving providers unauthenticated and fallback chains failing without a clear startup warning.

## Best Possible Solution

Keep steady-state runtime auth reads SQLite-only, but add a maintainer-approved startup/update diagnostic or explicit one-shot migration for stranded legacy auth JSON, and surface when configured primary/fallback model providers have no usable auth after that migration boundary.

## Reproduction Assessment

Yes at source level: a canonical auth-profiles.json beside an empty or missing per-agent SQLite auth store is not loaded by current runtime auth profile reads. I did not run a live 2026.5.x-to-current upgrade in this read-only review.

## Solution Assessment

Unclear as a product decision: the recovery need is real, but the best implementation depends on maintainer choice between explicit startup/update migration and loud diagnostics that point to doctor repair. A steady-state runtime JSON fallback would conflict with the current repository policy and tests unless maintainers deliberately approve that boundary change.

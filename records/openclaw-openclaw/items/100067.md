## Summary

Keep open: current main still keeps runtime auth-profile reads SQLite-only and does not migrate or loudly warn about stranded canonical `auth-profiles.json` files during ordinary startup/update. Doctor can import the JSON when run, and the linked open PR covers part of the import problem, but it is not merged and has a reviewed runtime-boundary concern.

## What This Changes

The issue reports that upgrading from JSON auth-profile storage to SQLite leaves existing OAuth/token profiles stranded, causing provider auth and fallback model chains to fail without an actionable startup warning.

## Best Possible Solution

Keep steady-state runtime reads SQLite-only, and add a maintainer-approved startup/update diagnostic or one-shot migration boundary that names stranded legacy auth profiles and warns when configured fallback providers have no usable auth.

## Reproduction Assessment

Yes at source level: current main leaves a legacy per-agent `auth-profiles.json` unread when SQLite has no auth_profile_store row, while doctor, not runtime startup, owns the JSON-to-SQLite import path. I did not run a live release-to-release upgrade in this read-only review.

## Solution Assessment

Unclear as an implementation choice: the issue is real, but the best fix needs maintainer direction on automatic startup/update migration versus a loud startup/update warning plus doctor repair. A steady-state runtime JSON fallback remains the wrong layer under repository policy unless maintainers explicitly approve it.

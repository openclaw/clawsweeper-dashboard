## Summary

Keep open: current main still has buffered xAI TTS and the shared streaming speech hook, but the bundled xAI speech provider does not implement `streamSynthesize`; adjacent xAI realtime voice and streaming STT work does not cover this TTS WebSocket path.

## What This Changes

Add native xAI WebSocket streaming TTS support to the bundled xAI speech provider for shared `textToSpeechStream` callers while preserving buffered TTS and keeping realtime voice separate.

## Best Possible Solution

Implement a provider-local `streamSynthesize` path in `extensions/xai` using the native xAI `/v1/tts` WebSocket protocol, with focused tests and docs that keep streaming TTS distinct from realtime voice.

## Reproduction Assessment

Not applicable as a bug reproduction; this is a feature request. Source inspection gives a high-confidence current-main check: xAI lacks `streamSynthesize`, and the shared streaming path skips providers without that hook.

## Solution Assessment

Yes. The requested direction is the narrow owner-boundary path: add the existing streaming speech hook inside the xAI plugin, preserve buffered TTS, and avoid conflating it with realtime voice.

## Repair Work Prompt

Implement native xAI streaming TTS for the existing OpenClaw speech provider contract. Keep the work local to the bundled xAI plugin unless a small generic helper is clearly needed: add `streamSynthesize` to `extensions/xai/speech-provider.ts`, implement the native `wss://api.x.ai/v1/tts` WebSocket protocol in `extensions/xai/tts.ts`, send `text.delta` then `text.done`, stream decoded `audio.delta` bytes until `audio.done`, propagate timeout/error/release behavior, and keep buffered `synthesize` and `synthesizeTelephony` unchanged. Add focused tests for URL/host policy, event protocol, lifecycle/release, timeout/error handling, and `streamSynthesize` integration.

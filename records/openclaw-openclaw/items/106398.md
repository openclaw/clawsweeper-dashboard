## Summary

Keep open: the implementation is internally coherent, but it changes the timeout contract from releasing queue capacity to allowing indefinitely hung listeners to saturate all slots; a Discord owner should confirm that tradeoff, and the external contributor still has only controlled test proof rather than real-runtime evidence.

## What This Changes

The PR changes Discord gateway event-queue accounting so timed-out listeners retain concurrency slots until their underlying promises settle, with regression tests for queueing and late settlement.

## Best Possible Solution

Define one explicit listener lifecycle contract: preferably enforce the real execution bound while adding clear saturation metrics/logging and an operational recovery path, then document the post-timeout behavior and prove it against a real or controlled-runtime Discord gateway event before merge.

Rationale: Promises cannot be forcibly cancelled, so the implementation must deliberately choose between exceeding the configured execution bound after timeout and risking complete queue saturation; tests cannot resolve which operational contract maintainers want.

- **Preserve timeout capacity release:** Keep current behavior and clarify that `maxConcurrency` bounds active dispatch accounting rather than uncancellable background listener execution.
- **Design cancellation first:** Pause this patch and introduce an abortable listener contract before making timeout release both execution capacity and underlying work.

## Solution Assessment

Unclear: retaining the slot is a clean way to make `maxConcurrency` represent actual active listener work, but it replaces over-concurrency with possible indefinite queue starvation and needs an explicit owner decision plus operational safeguards.

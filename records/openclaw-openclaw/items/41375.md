## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.91

Full review comments:

- **[P1] Honor outbound suppression before hook replies:** `src/auto-reply/reply/dispatch-from-config.ts:213-218`
  - body: The new `message:received` drain routes hook-controlled text immediately after `triggerInternalHook`, before the current send-policy/source-delivery suppression decision can block automatic user delivery. A session with `sendPolicy: "deny"` or message-tool-only source delivery can still emit hook replies, so this needs to use the same suppression gate as normal replies before calling `routeReply`.
  - confidence: 0.91
- **[P1] Route direct hook replies to the sender:** `src/auto-reply/reply/dispatch-from-config.ts:218`
  - body: This fallback prefers `ctx.To` over `ctx.From`; on direct inbound transports `To` is commonly the bot/account address and `From` is the user. Without `OriginatingTo`, hook replies can be sent to the bot identity instead of the sender, and the added test currently asserts that wrong target.
  - confidence: 0.93
- **[P1] Pass the current reply kind to routeReply:** `src/auto-reply/reply/internal-hook-replies.ts:48-58`
  - body: Current main's `routeReply` contract requires a `replyKind` so `reply_payload_sending` hooks receive the correct lane. This new helper omits it, so the rebase needs to pass an explicit kind instead of introducing a parallel delivery path that misses the hook contract.
  - confidence: 0.86
- **[P2] Validate hook messages before trimming:** `src/auto-reply/reply/internal-hook-replies.ts:28`
  - body: Internal hook handlers are runtime-extensible, and a JavaScript hook can push a non-string into `event.messages`. Calling `.trim()` directly after handler error isolation can throw in the delivery helper and abort command hook reply handling, so normalize to strings before trimming.
  - confidence: 0.82

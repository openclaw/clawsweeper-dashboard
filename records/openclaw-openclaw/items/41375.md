## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.91

Full review comments:

- **[P1] Honor outbound suppression before hook replies:** `src/auto-reply/reply/dispatch-from-config.ts:213-218`
  - body: This delivers hook-controlled text immediately after `triggerInternalHook`, before the current `sendPolicy` and source-reply visibility policy are resolved. A session configured to deny automatic sends, or to require message-tool-only delivery, can still emit these hook replies; gate hook reply delivery with the current policy decision and add deny/message-tool regression coverage.
  - confidence: 0.91
- **[P1] Route direct hook replies to the sender:** `src/auto-reply/reply/dispatch-from-config.ts:218`
  - body: When `OriginatingTo` is absent, this fallback chooses `ctx.To` before `ctx.From`, but on direct inbound turns `ctx.To` is commonly the bot or account address and `ctx.From` is the user. The new test asserts the bot address, so the bug would survive CI; prefer the sender fallback and update the assertion.
  - confidence: 0.93
- **[P1] Update the helper for current routeReply metadata:** `src/auto-reply/reply/internal-hook-replies.ts:48-58`
  - body: The new helper calls `routeReply` without the current required `replyKind` field and without the sender/policy metadata carried by nearby routed reply paths. After rebasing onto current main this can fail typecheck or misclassify reply-payload-sending hooks for these hook-generated messages.
  - confidence: 0.88
- **[P2] Validate hook messages before trimming:** `src/auto-reply/reply/internal-hook-replies.ts:28`
  - body: Internal hooks are runtime-loaded JavaScript, so a hook can accidentally push a non-string into `event.messages`. Calling `.trim()` directly on every element lets one bad hook value throw out of reset/message hook delivery instead of skipping invalid entries and preserving the turn.
  - confidence: 0.76

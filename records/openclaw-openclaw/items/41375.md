Full review comments:

- **[P1] Pass replyKind to routeReply:** `src/auto-reply/reply/internal-hook-replies.ts:48-58`
  - body: Current main requires every `routeReply` call to provide `replyKind` for reply hook lifecycle classification, but the new helper calls it without that field. After this branch is rebased, this path will fail the current contract instead of cleanly delivering hook replies.
  - confidence: 0.93
- **[P1] Honor send policy before routing hook replies:** `src/auto-reply/reply/dispatch-from-config.ts:213-226`
  - body: This drains and sends hook-controlled `event.messages` immediately after `triggerInternalHook`, before the current dispatch code resolves `sendPolicy` and source-reply suppression. Sessions configured to deny automatic source delivery could still emit hook replies, so the drain needs to run after or be gated by the same policy decision as other outbound replies.
  - confidence: 0.91
- **[P2] Route direct hook replies to the inbound sender:** `src/auto-reply/reply/dispatch-from-config.ts:218`
  - body: When `OriginatingTo` is absent, this fallback prefers `ctx.To` before `ctx.From`; for direct inbound channel turns, `To` is commonly the bot/account address and `From` is the user. That can send the hook reply toward the bot-side identity, and the new test currently asserts that wrong target.
  - confidence: 0.87
- **[P2] Validate hook messages before trimming them:** `src/auto-reply/reply/internal-hook-replies.ts:24-25`
  - body: Internal hook handlers are runtime-loaded JavaScript, so `event.messages` can contain non-string values despite the TypeScript type. Calling `.trim()` directly on each value can throw and abort command or inbound hook processing; filter/narrow to strings before trimming.
  - confidence: 0.86

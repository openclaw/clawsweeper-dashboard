## Summary

Keep open. Current main and v2026.6.11 still generate the Claude CLI MCP config from enabled bundled/configured servers without threading the agent's effective `tools.deny` policy into that handoff, and the direct fix PR is closed unmerged.

## What This Changes

The issue asks OpenClaw to enforce per-agent `tools.deny` for MCP tools exposed through the `claude-cli` backend.

## Best Possible Solution

Materialize an effective per-agent MCP tool/server surface before CLI backend invocation, preserve deny-wins and exact-allow semantics without widening access, and fail closed or emit a clear startup error when a backend cannot enforce the requested boundary.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What enforcement contract should OpenClaw use for `tools.deny` and narrower MCP tool policy when a CLI backend like `claude-cli` can only receive generated server config or downstream CLI allow/deny flags?

Rationale: The bug is source-proven, but the previous fix attempt showed that representing OpenClaw's exact/wildcard tool policy at a CLI MCP handoff can either fix denial or accidentally widen allowed access unless maintainers choose the permanent security boundary.

Likely owner: steipete

Owner reason: The strongest history signal points to steipete's prior work on the Claude CLI loopback MCP bridge and shared bundle MCP config surface where the security boundary must be settled.

Owner confidence: high

Options:

- **Filter before CLI handoff (recommended):** Resolve the per-agent effective MCP policy before generating CLI MCP config, preserve exact-tool restrictions without server-wide widening, and fail closed when the backend cannot represent the restriction.
- **Map to Claude flags:** Use Claude-specific `--disallowedTools` mappings for deny entries while keeping the generated server config broad, accepting a provider-specific enforcement path that needs upstream contract proof.
- **Warn instead of enforce:** Document and doctor-warn that CLI MCP tool policy is not enforced, leaving current runtime behavior intact but no longer treating `tools.deny` as a hard boundary for this backend.

## Reproduction Assessment

Yes, source-level rather than live in this review. Current main and v2026.6.11 merge enabled MCP servers into the generated Claude CLI config without an agent deny-policy input, and the issue has independent live reports including v2026.6.11.

## Solution Assessment

No, this should not close as docs-only or implemented. The best fix is an owner-reviewed pre-handoff enforcement path that preserves OpenClaw policy semantics without widening exact MCP tool allows.

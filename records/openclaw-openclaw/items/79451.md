## Summary

Keep open. Current main still hands the generated Claude CLI MCP config a merged set of enabled MCP servers without applying the agent's effective `tools.deny`, and the direct fix PR is closed unmerged while newer open PRs are only candidate or partial repairs.

## What This Changes

The issue asks OpenClaw to enforce per-agent `tools.deny` for MCP tools handed to the `claude-cli` backend.

## Best Possible Solution

Apply a maintainer-approved Claude CLI MCP policy handoff that enforces effective per-agent deny rules before launch, preserves exact and wildcard deny-wins semantics, and fails closed when requested restrictions cannot be enforced.

- **Managed pre-handoff policy enforcement (recommended):** Filter or proxy OpenClaw-managed MCP tools before Claude sees them, preserving exact/wildcard deny-wins behavior and adding live generated-config proof.
- **Claude-native deny forwarding:** Map OpenClaw MCP deny entries to Claude `--disallowedTools` where possible, accepting a Claude-specific path with narrower implementation scope.
- **Document unsupported restrictions:** Clarify CLI backend limitations and keep runtime behavior permissive, leaving operators to avoid `claude-cli` for restricted MCP deployments.

## Solution Assessment

No. A docs-only clarification would leave a declared security boundary unenforced; the best fix is an owner-reviewed pre-handoff filter, native deny forwarding, or managed proxy that does not widen exact MCP tool policy.

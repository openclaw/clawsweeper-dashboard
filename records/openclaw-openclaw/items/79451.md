## Summary

Keep open. Current main and the latest release still do not pass the effective per-agent tool policy into the Claude CLI MCP config handoff, and the direct fix PR is closed unmerged after review found a permission-widening edge case.

## What This Changes

Enforce per-agent `tools.deny` for MCP tools exposed through Claude CLI backend generated config and preserve auditable tool-policy behavior.

## Best Possible Solution

Add maintainer-approved CLI MCP policy enforcement before the Claude CLI handoff, fail closed when the policy cannot be represented without widening access, and cover deny, wildcard, exact allow, profile-preserve, and live CLI proof paths.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What security semantics should OpenClaw require for per-agent MCP tool policy when a CLI backend consumes generated MCP config directly?

Rationale: The expected policy boundary is documented, but the closed direct PR showed a plausible implementation can widen exact MCP allow entries into whole-server access, so automation should not choose the permanent security behavior alone.

Likely owner: steipete

Owner reason: He has the strongest history on the affected CLI MCP bridge and is the best available owner for the security-boundary decision.

Owner confidence: high

Options:

- **Enforce before handoff without widening access (recommended):** Resolve effective per-agent policy before writing the CLI MCP config, include only server-wide or wildcard-safe entries, and fail closed for exact per-tool policies that cannot be represented safely.
- **Translate to backend-native deny flags:** Map OpenClaw deny entries into Claude CLI `--disallowedTools` when contract proof shows exact behavior, while keeping generated config filtering for backends without an equivalent deny surface.
- **Document and warn only:** Clarify that CLI-native MCP tools are outside OpenClaw enforcement and add doctor/audit warnings, accepting that `tools.deny` remains advisory for this backend path.

## Reproduction Assessment

Yes, source-level. Configure a Claude CLI agent with `mcp.servers` and `agents.list[].tools.deny`; current main writes the merged MCP server config without passing the effective policy into that handoff, though I did not run a live Claude turn in this read-only review.

## Solution Assessment

Unclear. Filtering before the generated config reaches Claude CLI is the right boundary, but the previous PR showed the implementation must avoid turning exact per-tool policy entries into whole-server authorization.

## Summary

This PR remains necessary: current main still performs Feishu message create/reply without transient-failure recovery, while the branch has strong live evidence that stable-UUID retries recover an ambiguous accepted request without duplicate delivery. No actionable patch defect was found; normal Feishu-owner review and exact-head merge gates remain.

## What This Changes

Adds opt-in transient retries with one stable UUID per logical Feishu text, card, image, or file message create/reply operation, plus regression coverage that keeps uploads and Card Kit mutations single-attempt.

## Best Possible Solution

Use one stable UUID and bounded transient retries only around Feishu message create/reply operations, retain single-attempt uploads and Card Kit mutations, and preserve focused tests for both recovery and duplicate prevention.

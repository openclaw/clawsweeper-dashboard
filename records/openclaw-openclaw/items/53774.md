## Summary

Keep open: current main and v2026.6.11 still render a fixed TUI footer, while `/usage`, `/status`, provider-usage APIs, and the related open PRs only cover narrower cost/quota surfaces. The remaining request is a product/API/security decision for a persistent TUI footer extension point.

## What This Changes

Request configurable TUI footer fields/templates for model, token, estimated cost, provider balance, and rate-limit or cooldown status.

## Best Possible Solution

Keep this as the canonical broad TUI footer observability tracker, preserve the current fixed footer default, and design a narrow opt-in plugin/config status surface that reuses cached provider-usage and cost data with documented security behavior.

## Reproduction Assessment

Not applicable as a bug reproduction; this is a feature request. Source and release inspection confirm that the requested persistent TUI footer template/status-provider behavior is absent while related `/usage` and `/status` surfaces exist.

## Solution Assessment

Unclear as proposed: a direct core template plus balance poller is not obviously the best long-term shape. A maintainer-approved Plugin SDK status-provider seam or cached provider-usage integration is likely cleaner, but the API and rendering semantics remain unsettled.

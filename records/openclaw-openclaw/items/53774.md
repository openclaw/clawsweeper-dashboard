## Summary

Keep open: current main still has a fixed persistent TUI footer and a separate per-reply `/usage` template surface, but it does not implement configurable persistent TUI footer fields or a merged plugin status-provider seam. The related open PRs cover narrower pieces and are not complete replacements for this broader product/API decision.

## What This Changes

Request configurable persistent TUI footer fields/templates for cost, provider balance, and rate-limit status.

## Best Possible Solution

Keep this as the broad TUI footer observability tracker, review the narrower PluginStatusProvider and `/usage` quota-footer PRs, then choose a plugin/API-driven persistent footer design with bounded provider-usage behavior.

Options:

- **Plugin/API Footer Seam (recommended):** Review or refresh the PluginStatusProvider path and add TUI rendering only after the SDK shape, ordering, truncation, and provider polling rules are accepted.
- **Core Config Template:** Add a first-class `tui.footerTemplate`/field config surface with schema, docs, compatibility handling, and explicit credential-backed provider usage policy.
- **Keep Existing Surfaces:** Keep provider quota and cost visibility in `/status` and `/usage` only, and narrow or close persistent footer customization as out of scope.

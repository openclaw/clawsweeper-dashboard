## Label Justifications

- `P2`: This is a normal-priority TUI observability improvement with real quota/cost friction but no blocked first-run path, outage, or data loss.

## Summary

Keep open: current main and v2026.6.11 still do not provide persistent TUI footer templates or fields for cost, balance, or cooldown/rate-limit state. Existing `/usage` templates, provider-usage summaries, and the open PluginStatusProvider work are useful partial paths, but they do not settle the broader TUI footer product/API decision.

## What This Changes

Request to customize the persistent TUI footer with model, token, estimated cost, provider balance, and rate-limit/cooldown fields.

## Best Possible Solution

Adopt a maintainer-approved plugin/API-first footer status design, then wire the TUI rendering and provider-usage fields with bounded caching, redaction, ordering, truncation, and docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should persistent TUI footer customization be solved as core TUI config, a PluginStatusProvider-style SDK plus TUI render path, or kept out of the persistent footer for now?

Rationale: The request crosses TUI rendering, public config, provider credentials/usage, and Plugin SDK boundaries, and current related PRs intentionally cover only narrower slices.

Likely owner: steipete

Owner reason: The relevant history spans usage footer modes, provider usage hooks, and plugin architecture commits authored by Peter Steinberger.

Owner confidence: high

Options:

- **Plugin/API-first footer seam (recommended):** Approve the PluginStatusProvider direction first, then add TUI rendering and provider-usage footer fields behind that supported extension boundary.
- **Core config template:** Add a first-class `tui` footer template/config surface and accept the schema, docs, migration, and compatibility burden for persistent footer customization.
- **Keep existing status surfaces:** Keep `/status`, `/usage`, CLI status, and menu-bar usage as the supported quota/cost surfaces and decline persistent footer customization for now.

Unclear until maintainers choose the product/API boundary. A plugin/API-driven footer seam looks more maintainable than hardcoding provider-specific fields into the TUI, but the exact SDK/config shape needs approval.

Rationale: The request crosses TUI layout, provider usage/quota data, auth-sensitive balance checks, public config, third-party cost tracking, and Plugin SDK extension points, so automation cannot safely choose the long-term product/API boundary.

Owner confidence: medium

Options:

- **Plugin/API-first footer seam (recommended):** Accept a status-provider-style extension boundary first, then add TUI rendering only after ordering, truncation, caching, redaction, and security policy are settled.
- **Core TUI footer template:** Add first-class TUI config for template fields and accept the public config compatibility and migration burden.
- **Keep existing status surfaces:** Treat /status, /usage, CLI status, and gateway usage APIs as the supported quota/cost surfaces and reject persistent footer customization for now.

## Best Possible Solution

Keep this as the broad TUI footer observability tracker, decide the core-config versus plugin/API boundary, and let the narrower /usage quota and PluginStatusProvider PRs land or close on their own merits.

Rationale: The feature crosses public config, TUI rendering, provider usage/auth calls, and Plugin SDK contracts, so automation cannot safely choose the long-term product boundary.

Owner confidence: medium

Options:

- **Plugin/API-first footer seam (recommended):** Use the PluginStatusProvider direction as the extension boundary, then add TUI rendering only after ordering, truncation, caching, and security policy are approved.
- **Core TUI config template:** Add a first-class tui footer template/config surface and accept the migration and compatibility burden of a new public config contract.
- **Keep existing status surfaces:** Leave /status, /usage, CLI status, and menu-bar usage as the supported quota/cost surfaces and reject persistent footer customization for now.

## Summary

Keep open: current main and v2026.6.11 still do not provide persistent TUI footer customization for cost, balance, or rate-limit status. The related PluginStatusProvider and `/usage` quota-footer items are useful but narrower, and the remaining decision crosses TUI config, provider/auth usage data, and Plugin SDK boundaries.

## What This Changes

Request configurable persistent TUI footer fields for model, token, estimated cost, provider balance, and rate-limit/cooldown status.

## Best Possible Solution

Use this as the broad footer-observability tracker, settle a plugin/API-first contribution boundary, and only then add TUI rendering plus bounded provider-usage fields without hardcoding provider-specific footer policy in core.

## Maintainer Decision

Rationale: The request is useful but spans public config, TUI rendering, provider credentials/usage APIs, and Plugin SDK contracts; automation cannot safely choose the long-term product boundary.

Likely owner: steipete

Owner confidence: high

Options:

- **Plugin/API-First Footer Seam (recommended):** Use the linked PluginStatusProvider direction as the extension boundary, then add TUI render integration and provider-usage fields after maintainers approve API shape, ordering, truncation, and caching policy.
- **Core Footer Template Config:** Add first-class `tui` footer template/config support, accepting the compatibility and migration burden of a new public config contract.
- **Keep Existing Status Surfaces:** Keep `/status`, `/usage`, CLI status, and menu-bar usage as the supported quota/cost surfaces and decline persistent footer customization for now.

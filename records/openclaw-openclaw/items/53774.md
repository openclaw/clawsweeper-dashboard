## Summary

Keep open: current main and v2026.6.11 still have a fixed persistent TUI footer, while the open related PRs cover only narrower PluginStatusProvider and per-response /usage quota pieces.

## What This Changes

Request configurable persistent TUI footer fields for model, token usage, estimated cost, provider balance, and rate-limit or cooldown status.

## Best Possible Solution

Keep this as the broad TUI footer observability tracker, decide the core-config versus plugin/API boundary, and let the narrower /usage quota and PluginStatusProvider PRs land or close on their own merits.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should persistent TUI footer customization be solved as core TUI config, as a plugin status-provider SDK plus TUI render seam, or rejected in favor of existing /status and /usage surfaces?

Rationale: The request crosses public TUI config, provider auth/usage calls, background caching, and Plugin SDK boundaries, so automation should not choose the long-term product/API contract.

Likely owner: steipete

Owner reason: History and related discussion tie this decision to provider-usage/status and plugin/API product boundaries.

Owner confidence: medium

Options:

- **Plugin/API-first footer seam (recommended):** Use a generic PluginStatusProvider-style seam and decide TUI ordering, truncation, caching, and security policy before adding provider-specific fields.
- **Core footer template config:** Add a first-class TUI footer template/config contract and accept the public config, migration, and compatibility burden.
- **Keep existing surfaces:** Declare /status, /usage, CLI status, and external plugins as the supported cost/quota surfaces and close persistent footer customization as out of scope.

## Summary

Keep open. Current main intentionally documents provider quota on `/status` while the built-in per-response footer remains a separate tokens, context, and cost surface; merged usage-state infrastructure makes this technically narrow, but no merged PR establishes that quota windows belong in the default footer.

## What This Changes

Add active-provider quota percentages, such as GitHub Copilot Premium and Chat remaining, to per-response usage footers.

## Best Possible Solution

Add generic active-provider quota windows to the built-in `/usage full` renderer from the prepared per-turn usage snapshot, keep `/usage tokens` compact, retain provider-specific fetching and normalization in plugins, and omit unavailable or stale windows without delaying reply delivery.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should active-provider quota windows become part of the built-in per-response footer, and if so should they appear only in `/usage full` or also in `/usage tokens`?

Rationale: Current main has the generic data seam, but the documented split between `/status` provider quota and per-response usage is an intentional user-visible policy boundary that code inspection cannot choose.

Likely owner: steipete

Owner reason: They own substantial provider-usage and response-usage history and already provided the maintainer-level implementation guidance on this issue.

Owner confidence: high

Options:

- **Add to full only (recommended):** Append generic prepared quota windows to `/usage full` while preserving `/usage tokens` as the compact token-only mode.
- **Add to both modes:** Show quota windows in both `/usage tokens` and `/usage full`, accepting a longer default per-response footer for users of either mode.
- **Keep status-only:** Retain provider quota in `/status` and custom usage templates, then close this request as not planned for the built-in footer.

## Reproduction Assessment

Yes at source level: current docs and the built-in usage contract separate `/status` quota windows from per-response token, context, and cost rendering, so the missing footer field is high-confidence without a live failure run.

## Solution Assessment

No, the earlier approach of fetching provider usage inside reply formatting is not the best fix; the narrow maintainable path is to render the already prepared provider-neutral snapshot after maintainers choose the footer policy.

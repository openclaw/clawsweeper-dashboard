## Summary

Keep open. Current main and v2026.6.11 still omit provider quota windows from per-response usage footers, every direct implementation PR closed unmerged, and the remaining blocker is a maintainer decision about automatic quota display and snapshot lifecycle.

## What This Changes

Add active-provider quota windows, such as GitHub Copilot Premium and Chat percentages, to per-response `/usage` footers.

## Best Possible Solution

Extend prepared reply-usage state with an optional provider-neutral quota snapshot produced by the existing plugin-owned usage pipeline, then render it without network or discovery work during reply finalization.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should provider quota windows become automatic per-response `/usage` footer content, and if so must reply finalization consume only a preloaded snapshot rather than perform a provider lookup?

Rationale: Current main lacks quota data in the reply usage contract, while prior implementations added bounded network work to final delivery; the UX, freshness, and lifecycle tradeoff requires maintainer intent.

Likely owner: steipete

Owner reason: The provider-usage and status history plus prior scoping on this issue make this the strongest available product and lifecycle owner.

Owner confidence: high

Options:

- **Use preloaded snapshots (recommended):** Add provider-neutral quota fields to prepared reply usage state and render them only when already available, avoiding reply-time discovery or network calls.
- **Allow bounded reply lookup:** Permit a timeout-bounded provider usage lookup during usage-enabled reply finalization and accept the possible latency and omission behavior.
- **Keep quotas in status surfaces:** Leave provider quota windows in `/status`, CLI, and Control UI rather than adding automatic per-response display.

## Reproduction Assessment

Yes at source level: the reply usage contract and default footer lack provider quota fields, while `/status` and provider usage services expose them. This is a missing feature, not a regression against an established footer contract.

## Solution Assessment

No. The earlier direct reply-time fetches are not the best default design because they add provider discovery and awaited network work to final delivery; carrying a prepared provider-neutral snapshot is safer.

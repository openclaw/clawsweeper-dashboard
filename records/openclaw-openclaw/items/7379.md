## Summary

Keep open. Current main and v2026.7.1 still separate provider quota windows from per-response usage footers: `/usage tokens` remains token-focused, `/usage full` has richer turn metadata, and the footer contract explicitly excludes provider rate-limit windows. The remaining choice is product policy—whether quota polling belongs on every eligible reply and in which usage mode—not an already-implemented fix. ([docs.openclaw.ai](https://docs.openclaw.ai/concepts/usage-tracking))

## What This Changes

Add active-provider quota percentages, especially GitHub Copilot Premium and Chat windows, to per-response `/usage` footers.

## Best Possible Solution

After product approval, extend the generic per-turn usage contract with a prepared or lifecycle-cached active-provider quota snapshot, render compact windows in `/usage full`, keep fetching and credential handling plugin-owned, and omit quota text without delaying or failing reply delivery.

Question: Should active-provider quota windows become part of the built-in per-response footer, and if so should they appear only in `/usage full` or also in `/usage tokens`?

Rationale: Current behavior deliberately keeps provider quotas in status and provider-usage surfaces while defining token and full footers separately; code inspection cannot decide the desired default visibility, polling cadence, or acceptable reply-path cost.

Likely owner: steipete

Owner reason: They have the strongest history across provider-usage loading, formatting, status presentation, and the prior product-boundary review for this issue.

Owner confidence: high

Options:

- **Add to full mode (recommended):** Expose cached active-provider quota windows in `/usage full` only, preserving `/usage tokens` as the lightweight token/cache/cost mode.
- **Add to both modes:** Append quota windows to both token and full modes for maximum per-response visibility at the cost of a less distinct lightweight mode.
- **Keep status-only:** Keep provider quotas in `/status`, CLI, Control UI, and app surfaces and close this footer request as intentionally out of scope.

## Reproduction Assessment

Yes, from source-level product documentation: current main explicitly says provider rate-limit windows are absent from the footer contract, while `/status` exposes provider usage. A live provider run is unnecessary to establish that the requested capability is missing. ([docs.openclaw.ai](https://docs.openclaw.ai/concepts/usage-tracking))

## Solution Assessment

No, a Copilot-specific fetch appended directly in the reply runner is not the best long-term fix. The maintainable path is a generic active-provider snapshot consumed by `/usage full`, with provider-specific network and auth behavior remaining inside plugins and no unbounded request-time discovery.

## Summary

Current main still keeps provider quota windows on status-oriented surfaces rather than per-response `/usage` footers. Four direct implementation PRs closed unmerged—including a proof-sufficient candidate—because the remaining question is product and lifecycle ownership: whether opted-in replies should show quota data and how to do so without network discovery in the reply hot path.

## What This Changes

Add active-provider quota percentages, especially GitHub Copilot Premium and Chat windows, to per-response `/usage tokens` or `/usage full` footers.

## Best Possible Solution

Maintain a lifecycle-owned, bounded provider-usage snapshot and let the reply footer consume that prepared snapshot without starting network discovery; keep fetching and authentication plugin-owned, omit unavailable or overly stale data, and document snapshot freshness.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should opted-in per-response usage footers display provider quota windows, and if so must they consume a prepared cached snapshot rather than perform a fresh provider lookup during reply finalization?

Rationale: The user value is established, but automatic quota display changes the reply hot path and requires an explicit choice about freshness, latency, failure coupling, and snapshot ownership.

Likely owner: steipete

Owner reason: The strongest history signal spans both the response usage footer and the provider-usage/status contracts requiring a unified ownership decision.

Owner confidence: high

Options:

- **Cached snapshot footer (recommended):** Show quota windows only from a lifecycle-owned provider usage snapshot, never blocking reply delivery on a fresh network call.
- **Live per-reply lookup:** Allow a bounded provider lookup during each opted-in reply and explicitly accept the added latency and availability coupling.
- **Keep status-only:** Leave provider quota windows on `/status` and CLI surfaces while keeping per-response footers limited to locally available turn and session data.

## Reproduction Assessment

Yes, at source and documentation level: per-response `/usage` footers expose local turn and session usage, while provider quota windows remain on status-oriented surfaces. This is a missing capability rather than a failing existing contract.

## Solution Assessment

Unclear until maintainers choose the display and freshness contract. The narrowest maintainable implementation is a generic cached-snapshot bridge, not a Copilot-specific fetch or a new network probe during reply finalization.

## Summary

Keep open. Current main has provider-neutral, credential-aware quota snapshots available during live reply delivery, but the built-in `/usage full` renderer deliberately excludes provider quota windows, so the requested behavior remains a product choice rather than an unimplemented data-fetching primitive. ([github.com](https://github.com/openclaw/openclaw/pull/89835))

## What This Changes

Add the active provider’s quota percentages, such as GitHub Copilot Premium and Chat windows, to per-response `/usage` footers.

## Best Possible Solution

Expose the already-prepared provider-neutral `usageState.limits` windows through the usage-bar contract and, if maintainers approve the default, append a compact summary only to `/usage full`; keep fetching plugin-owned, omit unavailable snapshots, and never add reply-hot-path network discovery.

Question: Should the built-in `/usage full` footer show the active provider’s prepared quota windows by default, or should those windows remain limited to status/UI surfaces or an advanced custom template?

Rationale: The technical snapshot and cache ownership now exist, but choosing the default chat density and replay semantics changes a user-visible product contract and cannot be inferred safely from implementation convenience.

- **Custom Templates Only:** Expose quota windows to `messages.usageTemplate` while keeping the built-in footer unchanged for users who want a quieter default.
- **Keep Status-Only:** Keep provider quotas on `/status`, CLI, Control UI, and app surfaces and close this request as outside the per-response footer contract.

## Reproduction Assessment

Yes, at source level. Current documentation explicitly defines the built-in footer fields and states that provider windows are absent from the renderer contract, while the prepared per-turn usage snapshot already carries those windows.

## Solution Assessment

Yes, conditionally. Consuming the existing credential-aware cached snapshot through the generic usage contract is the narrowest maintainable solution; adding a synchronous provider fetch to every reply would violate the established hot-path boundary.

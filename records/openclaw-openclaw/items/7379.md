## Summary

Keep open. Current main and v2026.7.1 still separate per-response token/context/cost footers from provider quota windows, and the exact credential-scoping concern was intentionally excluded from the merged usage-state contract. The live GitHub search now shows https://github.com/openclaw/openclaw/pull/96339 open as the candidate implementation, so this issue should remain open while maintainers decide the polling and mode policy and review that PR.

## What This Changes

Add active-provider quota percentages, especially GitHub Copilot Premium and Chat windows, to per-response `/usage` footers.

## Best Possible Solution

Use the existing generic provider-usage seam to append a compact, cached quota summary to `/usage full`, bound to the exact active credential/profile with a hard timeout and silent omission on failure; keep provider-specific network logic inside provider plugins and document the resulting polling behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should active-provider quota windows be fetched and displayed on each eligible reply, and should that behavior apply only to `/usage full` or also to `/usage tokens`?

Rationale: Current policy intentionally keeps provider quotas in `/status`, and moving them into every reply changes network frequency, latency, footer density, and credential-scoping requirements; repository evidence cannot choose those product tradeoffs.

Likely owner: obviyus

Owner reason: They merged and repaired the exact usage-state/footer boundary, including the deliberate removal of unsafe provider-limit correlation.

Owner confidence: high

Options:

- **Full mode, credential-scoped (recommended):** Show cached, timeout-bounded quota windows only in `/usage full`, tied to the exact active credential/profile and omitted on lookup failure.
- **Both usage modes:** Show quota windows in `/usage tokens` and `/usage full`, accepting a denser tokens mode and broader per-reply polling surface.
- **Keep status-only:** Retain provider quota exclusively in `/status` and keep reply footers limited to per-turn accounting.

## Reproduction Assessment

Yes at source level: with provider usage available, `/status` displays quota windows while current `/usage tokens` and `/usage full` contracts omit them. No live failing run is necessary because this is a documented feature gap, not a regression.

## Solution Assessment

Unclear until maintainers choose the footer mode and polling policy. The narrowest maintainable implementation is generic, credential-scoped, cached, timeout-bounded, and plugin-owned for provider fetching rather than unconditional provider-specific logic in the reply runner.

## Summary

Keep open for a maintainer product decision. The requested active-provider quota display is still distinct from the current per-response `/usage` footer, while the direct implementations in the supplied context were all closed unmerged; the remaining design question is whether a reply footer consumes a lifecycle-owned cached quota snapshot or may trigger a bounded provider lookup.

## What This Changes

Add active-provider quota windows, including GitHub Copilot Premium and Chat percentages, to the per-response `/usage` footer.

## Best Possible Solution

Add a generic footer renderer that consumes an already prepared, lifecycle-owned provider-usage snapshot; keep provider fetching and credential handling in provider plugins, define the refresh policy explicitly, and add focused reply-footer coverage for available, unavailable, and stale quota data.

Rationale: The feature is viable with existing generic provider-usage data, but putting provider loading on a per-reply hot path would set a lasting latency, freshness, and failure-policy contract that source inspection alone cannot choose.

Likely owner: steipete

Owner confidence: high

Options:

- **Cached snapshot for `/usage full` (recommended):** Render a compact generic quota summary only from a lifecycle-owned cached snapshot when `/usage full` is enabled, preserving a reply hot path with no provider fetch.
- **Support both usage modes:** Expose the same cached quota summary for both `tokens` and `full`, accepting a broader user-visible footer contract.
- **Keep quota status in `/status`:** Decline per-response quota rendering and retain `/status` as the explicit on-demand provider-usage surface.

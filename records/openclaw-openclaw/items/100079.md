## Summary

Keep open: current main and the latest release still route explicit Ollama web_search selection through Ollama's local proxy/hosted endpoints, while the reported DuckDuckGo-style bot-detection path needs live upstream proof and a maintainer contract decision before changing behavior or promising DuckDuckGo-free semantics.

## What This Changes

The issue requests that `tools.web.search.provider: "ollama"` either avoid DuckDuckGo-backed failures entirely or clearly document/warn about Ollama's upstream search dependency and recommend a reliable alternative.

## Best Possible Solution

Define the Ollama Web Search contract clearly: document local proxy and hosted behavior, point users who need DuckDuckGo-free search to existing API-backed or self-hosted providers, and only change routing after live proof of a safer Ollama endpoint.

## Reproduction Assessment

No, not end-to-end for the reported bot-detection symptom. Source inspection confirms the explicit Ollama path and no automatic fallback, but live signed-in Ollama evidence is still needed to prove the upstream DuckDuckGo dependency.

## Solution Assessment

Unclear. Adding another provider is not the best first fix because alternatives already exist; the narrow path is maintainer-confirmed contract/docs wording and possibly endpoint/error behavior after live upstream proof.

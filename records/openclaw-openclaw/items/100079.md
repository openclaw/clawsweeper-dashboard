## Label Justifications

- `P2`: This is a normal-priority provider/docs reliability issue affecting web_search users who explicitly choose Ollama, with limited blast radius and no current proof of a core outage.
- `impact:ux-friction`: The current provider name and docs can mislead users who switch away from DuckDuckGo expecting bot-detection avoidance, causing confusing failures and support burden.

## Summary

Keep open: current main still makes explicit Ollama web_search selection call Ollama's local proxy/hosted API path, while the docs do not clearly set expectations for users trying to avoid DuckDuckGo-style bot-detection entirely.

## What This Changes

The issue asks OpenClaw to make `tools.web.search.provider: "ollama"` avoid DuckDuckGo bot-detection at every layer, or document the upstream dependency and point users to a genuinely separate search provider path.

## Best Possible Solution

Define the Ollama Web Search contract clearly: document local proxy/hosted behavior and recommend existing API-backed or self-hosted alternatives for users avoiding DuckDuckGo; only change routing if a verified Ollama endpoint avoids the upstream challenge.

## Reproduction Assessment

No, not end-to-end for the bot-detection symptom: I did not run a live Ollama search against a signed-in host. Source inspection does show the selected Ollama provider calls the Ollama local proxy path first and explicit selection prevents automatic fallback to other providers.

## Solution Assessment

Unclear. Adding another provider is not the best first fix because Brave, SearXNG, Tavily, and other alternatives already exist; the safer path is maintainer-confirmed contract/docs and possibly endpoint-order/error-message work after upstream behavior is verified.

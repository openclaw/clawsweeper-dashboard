## Label Justifications

- `P2`: The issue reports intermittent web-search failures and misleading provider expectations with limited blast radius.
- `impact:ux-friction`: A user can configure an explicit provider yet still get confusing DuckDuckGo bot-detection symptoms without clear product guidance.

## Summary

Current main and the latest release already route explicit Ollama web search to Ollama endpoints, not OpenClaw's DuckDuckGo provider, but the user-facing confusion remains because docs/setup do not clearly state that the local Ollama proxy forwards to Ollama Cloud and is not a guaranteed escape from upstream bot-detection wording.

## What This Changes

The issue requests that `tools.web.search.provider: "ollama"` stop surfacing DuckDuckGo bot-detection failures, or document/warn that Ollama search may still depend on DuckDuckGo and point to a DuckDuckGo-free alternative.

## Best Possible Solution

Keep explicit Ollama routing as-is, but clarify docs and setup/error messaging that Ollama local search forwards to Ollama Cloud and is not guaranteed to bypass upstream bot-detection; direct bot-detection-sensitive users to existing explicit providers such as Brave, SearXNG, Tavily, Parallel, Perplexity, or Exa.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Partially: source inspection proves explicit Ollama selection uses Ollama endpoints and does not fall back to OpenClaw's DuckDuckGo provider, but I did not live-test a signed-in Ollama host to reproduce the upstream bot-detection message.

## Solution Assessment

Is this the best way to solve the issue? A docs and diagnostic clarification is the best narrow OpenClaw-side fix; adding another core provider is unnecessary because several explicit alternative web-search providers already exist as plugins.

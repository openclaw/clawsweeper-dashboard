## Summary

Keep open: current main has shared/iOS custom-header support from the merged iOS work, but macOS still carries only Gateway URL/token/password and has no secure custom-header UI/storage path, so the macOS parity work remains.

## What This Changes

The issue requests native iOS/macOS support for connecting to Gateways behind Basic-auth reverse proxies by sending HTTP credentials or headers on the WebSocket upgrade.

## Best Possible Solution

Add macOS parity by feeding GatewayConnection and Mac node-mode connections from a secure per-gateway custom-header store, reusing the shared sanitizer and TLS-only upgrade path with redacted settings UI.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should macOS adopt the same per-gateway custom-header contract as iOS/Android, and where should those proxy credentials live in macOS settings/storage?

Rationale: The low-level shared header seam exists, but macOS still needs a credential-bearing UI/storage contract that runs before Gateway auth and affects a security boundary.

Likely owner: steipete

Owner reason: steipete authored the landed iOS custom-header implementation and has the clearest recent history across this security/product boundary.

Owner confidence: high

Options:

- **Implement Keychain-backed macOS parity (recommended):** Use the existing shared sanitizer/TLS-only upgrade path and add macOS secure storage plus settings UI scoped per gateway.
- **Limit macOS to typed Basic/Bearer fields:** Expose narrower proxy-auth fields instead of arbitrary headers, reducing flexibility but shrinking the credential surface.
- **Defer macOS proxy credentials:** Keep macOS authenticated-proxy support unsupported for now and document VPN, Tailscale, SSH tunnel, or proxy-bypass alternatives.

## Reproduction Assessment

Yes, source-level for the remaining macOS path: current main's macOS GatewayConnection.Config carries only url/token/password, and the operator and node connections do not pass extraHeadersProvider. I did not run a live Caddy/nginx macOS reproduction.

## Solution Assessment

Unclear until maintainers confirm the macOS credential storage/UI contract. The best technical shape is to reuse the existing shared sanitized request-header seam rather than adding another WebSocket implementation path.

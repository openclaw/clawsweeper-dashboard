## Label Justifications

- `P2`: The issue blocks a bounded authenticated-proxy native app deployment shape, but it is not a general OpenClaw outage or default setup failure.
- `impact:security`: The requested behavior stores and replays reverse-proxy credentials before OpenClaw's normal Gateway authentication message runs.

- `maturity:stable`: The affected Gateway runtime WebSocket/auth surface is scored M4 Stable in qa/maturity-scores.yaml.

## Summary

Keep open: the iOS side is now implemented on current main, but macOS still lacks a stored custom-header credential surface and does not pass an extra-header provider into its Gateway WebSocket connections.

## What This Changes

The issue asks for native iOS/macOS Gateway connections to support reverse-proxy Basic-auth credentials on the WebSocket upgrade request.

## Best Possible Solution

Extend the landed custom-header contract to macOS with secure per-gateway storage, TLS-only sanitized Gateway upgrade injection for operator and node sessions, reset/redaction behavior, focused tests, and real authenticated-proxy proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should macOS adopt the same arbitrary per-gateway custom-header contract that landed for iOS/Android, or should macOS narrow this issue to typed Basic-auth proxy credentials first?

Rationale: The remaining code gap is clear, but the permanent macOS design decides how pre-Gateway proxy credentials are stored, redacted, cleared, and attached before the normal Gateway auth boundary.

Likely owner: steipete

Owner reason: Peter owns the landed iOS contract and explicitly identified macOS parity as the remaining issue scope.

Owner confidence: high

Options:

- **Use the landed custom-header contract (recommended):** Add macOS parity for arbitrary sanitized per-gateway headers with Keychain storage, TLS-only request-time injection, reset cleanup, and tests matching the iOS/Android contract.
- **Narrow to Basic auth only:** Implement only typed Basic username/password support for macOS, reducing the header surface but diverging from the broader mobile custom-header contract.
- **Defer macOS proxy credentials:** Document macOS as unsupported for authenticated reverse-proxy Gateway access until maintainers define a separate desktop credential model.

## Reproduction Assessment

Yes, source-level: current macOS GatewayConnection and MacNodeModeCoordinator do not pass an extraHeadersProvider, and the macOS remote config state has no custom-header or proxy credential field. I did not run a live macOS reverse-proxy repro in this read-only review.

## Solution Assessment

No, the issue is not fully solved yet: current main has the shared/iOS machinery but macOS still needs a first-class credential/storage/UI path. Reusing the landed secure custom-header contract is the narrowest maintainable direction unless maintainers choose a typed Basic-only desktop contract.

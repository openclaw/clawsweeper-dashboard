- `P2`: The issue blocks a bounded authenticated-proxy deployment shape for native apps but does not make OpenClaw generally unusable.
- `impact:security`: The remaining work involves storing and replaying reverse-proxy credentials before OpenClaw Gateway authentication runs.

- `maturity:stable`: The affected Gateway WebSocket/auth surface maps to Gateway runtime M4 Stable, and the original iOS side also maps to iOS app M4 Stable.

## Summary

Keep open: current main has landed the shared native header seam and the iOS/Android implementations, but the issue discussion explicitly keeps this report open for macOS parity and current macOS Gateway connections still do not read or attach custom proxy headers.

## What This Changes

Request native iOS/macOS support for supplying reverse-proxy Basic/custom HTTP headers on Gateway WebSocket upgrades.

## Best Possible Solution

Port the landed per-gateway custom-header contract to macOS, reusing the shared GatewayCustomHeaders sanitizer and adding secure macOS storage, UI, operator/node header providers, isolation tests, and real reverse-proxy proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should macOS adopt the same per-gateway custom-header contract already landed for iOS and Android, or should its reverse-proxy auth surface be narrower or deferred?

Rationale: The source gap is clear, but the macOS implementation would persist and send pre-Gateway credentials, so maintainers need to choose the storage, TLS, redaction, reset, and endpoint-scoping boundary before automation implements it.

Likely owner: steipete

Owner reason: steipete authored the landed mobile contract and recent adjacent native Gateway work, making him the best available owner for the security-boundary decision.

Owner confidence: high

Options:

- **Mirror the landed mobile contract (recommended):** Add macOS per-gateway custom headers with secure storage, TLS-only gateway attachment, reserved-header filtering, reset behavior, and parity tests matching the iOS/Android contract.
- **Limit macOS to typed proxy auth:** Expose only narrower Basic/Bearer-style fields first, reducing arbitrary-header risk but diverging from the mobile custom-header contract.
- **Defer macOS proxy credentials:** Keep macOS unsupported for authenticating reverse proxies for now and document direct, VPN, tunnel, or proxy-bypass alternatives.

## Reproduction Assessment

Yes for the remaining macOS gap from source inspection: macOS GatewayConnection and MacNodeModeCoordinator do not pass an extraHeadersProvider, and macOS settings expose Gateway URL/token but no proxy-header storage path. I did not run a live macOS plus Caddy/nginx Basic-auth reproduction in this read-only review.

## Solution Assessment

No, current main is only a partial solution: iOS and Android now have the custom-header path, but macOS still cannot supply headers on Gateway upgrades. The best fix is macOS parity with the landed shared sanitizer and credential lifecycle, not a separate Basic-only workaround unless maintainers choose that narrower contract.

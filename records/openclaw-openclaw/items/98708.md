## Label Justifications

## Summary

Keep open: current main has fixed the iOS side through the merged custom-header path, but live discussion and source inspection show the remaining macOS parity work is still missing.

## What This Changes

Request native iOS/macOS support for sending Basic-auth reverse-proxy credentials or custom headers on Gateway WebSocket upgrades.

## Best Possible Solution

Land a maintainer-approved macOS parity design that reuses the shared GatewayCustomHeaders sanitizer, stores per-gateway secrets securely, sends them only to Gateway wss:// upgrades, covers foreground and node connections, and includes real authenticated-proxy proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should macOS adopt the existing per-gateway custom-header contract for both foreground and node Gateway connections, and what secure-store/reset behavior should own those credentials?

Rationale: The transport seam exists after the iOS fix, but macOS would introduce credential-bearing settings and storage on a separate app surface, so automation should not choose the permanent security boundary alone.

Likely owner: steipete

Owner reason: He owns the merged iOS contract and explicitly marked this issue as the macOS parity tracker.

Owner confidence: high

Options:

- **Approve macOS parity on the existing contract (recommended):** Reuse GatewayCustomHeaders with macOS secure per-gateway storage, TLS-only delivery, reset behavior, and tests/proof for both foreground and node Gateway connections.
- **Limit macOS to typed Basic/Bearer fields:** Add a narrower macOS proxy-auth UI instead of arbitrary headers, reducing flexibility but tightening the credential surface.
- **Defer macOS proxy credentials:** Document macOS authenticated reverse proxies as unsupported for now and keep operators on VPN, SSH tunnel, Tailscale, or proxy-bypass alternatives.

## Reproduction Assessment

Yes, source-level: macOS GatewayConnection.Config carries only url/token/password, the foreground GatewayChannelActor is created without extraHeadersProvider, and MacNodeModeCoordinator also connects without one. I did not run a live macOS plus Basic-auth proxy reproduction.

## Solution Assessment

No, the issue is only partially solved on current main: iOS has the shared and UI path, but macOS still needs a secure settings/storage and connection integration. The best remaining shape is macOS parity on the existing shared header sanitizer rather than a new Gateway protocol path.

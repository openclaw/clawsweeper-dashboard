## Summary

Keep open: current main and v2026.6.11 still lack a global agent dry-run that previews all tool execution, and the related dry-run/safe-mode items only cover narrower command scopes or broader workflow-mode decisions.

## What This Changes

Requested a global `openclaw agent --dry-run` mode that keeps tools visible to the model while intercepting every tool call and returning/logging structured previews instead of executing side effects.

## Best Possible Solution

Define an additive, request-scoped dry-run contract for agent runs, including hook ordering, built-in/plugin/client tool handling, redaction, stderr/stdout behavior, and Gateway-local scope, before implementation.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What request-scoped dry-run security contract should OpenClaw expose for agent tool execution across CLI, Gateway or embedded runs, built-in tools, plugin tools, client tools, and hooks?

Rationale: Current main lacks the feature, but adding it changes a security-sensitive runtime contract and the issue’s proposed process-global adapter flag is not clearly safe for concurrent or Gateway-owned execution.

Likely owner: Peter Steinberger

Owner reason: The strongest feature-history signal for the adapter/hook execution contract points to Peter’s before_tool_call integration work.

Owner confidence: high

Options:

- **Design request-scoped core dry-run (recommended):** Specify CLI and runtime semantics first, then implement a bounded core contract with tests for built-in, plugin, client, Gateway, and embedded paths.
- **Defer to broader workflow modes:** Keep this blocked until the Ask/Plan/Modify or scoped-agent mode design chooses shared vocabulary and guarantees.
- **Reject global dry-run:** Continue using scoped command dry-runs, sandboxing, reader agents, and tool policy if maintainers decide a global preview boundary is too easy to misread as a sandbox guarantee.

## Reproduction Assessment

Yes, at source level: current main has no `openclaw agent --dry-run` flag or request field, and the shared tool adapter still calls `tool.execute`. I did not run a live CLI turn because this read-only review can establish the feature gap from source and release-tag inspection.

## Solution Assessment

Unclear. A global dry-run capability fits the safety goal, but the proposed process-global adapter flag is not yet the best design; request-scoped semantics across CLI, Gateway, embedded, plugin, and client-tool paths are safer.

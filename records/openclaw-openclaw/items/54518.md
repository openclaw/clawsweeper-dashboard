## Label Justifications

- `impact:data-loss`: The reported failure mode includes an agent modifying another workspace's skill files and corrupting local workspace state.

## Summary

Keep open: current main and v2026.6.11 still treat the agent workspace as the default cwd, not a hard filesystem boundary. The existing controls are opt-in (`tools.fs.workspaceOnly` and sandboxing), and the open related PRs only cover partial filesystem subsets rather than the full per-agent workspace confinement request.

## What This Changes

The issue requests hard per-agent filesystem confinement so agents cannot read or modify files outside their own workspace.

## Best Possible Solution

Keep this as the concrete workspace-confinement tracker while maintainers choose the default confinement, migration, exec/sandbox scope, and documentation story, then land focused code and regression coverage for that chosen policy.

## Reproduction Assessment

Yes from source: with `tools.fs.workspaceOnly` unset or false, current host read/write/edit tools are built without workspace guards and tests assert outside-workspace access succeeds. I did not run a live Feishu/minimax reproduction in this read-only review.

## Solution Assessment

Unclear as a direct implementation path: flipping `tools.fs.workspaceOnly` by default is plausible but compatibility-sensitive and does not settle exec/process access. The better next step is maintainer security/product review that defines the default, migration, and scope before a fix PR.

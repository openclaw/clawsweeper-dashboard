## Summary

Keep open: current main and the latest release still treat the agent workspace as a default cwd plus optional guardrails, not a hard per-agent filesystem boundary. The remaining fix is security- and compatibility-sensitive because file tools, exec/process, sandbox mode, and existing trusted host-wide workflows need one maintainer-approved policy.

## What This Changes

The issue reports that agents can read or modify paths outside their assigned workspace and asks for enforced per-agent filesystem containment.

## Best Possible Solution

Keep this as the concrete workspace-confinement tracker while maintainers choose the default confinement, upgrade compatibility, and exec/sandbox boundary, then land that policy with docs and regression coverage.

## Reproduction Assessment

Yes. Current source and tests show host read/write/edit are not workspace-confined when `tools.fs.workspaceOnly` is unset or false; I did not run the Feishu/minimax scenario in this read-only review.

## Solution Assessment

Unclear. Enabling workspace-only by default is plausible, but the repository treats this as a security/default compatibility decision and a file-tool-only fix would not settle exec/process access.

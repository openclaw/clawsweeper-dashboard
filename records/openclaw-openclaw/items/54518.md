## Summary

Keep open: current main and v2026.6.11 still treat an agent workspace as the default working directory, not a hard filesystem boundary. The source and tests preserve host read/write/edit access outside the workspace when `tools.fs.workspaceOnly` is unset or false, while the related open PRs are partial, conflicting, or broader product decisions rather than merged replacements.

## What This Changes

The issue requests enforced per-agent workspace isolation so agents cannot read or modify files outside their own working space.

## Best Possible Solution

Keep this as the concrete workspace-confinement tracker while maintainers choose the default confinement, compatibility story, and exec/sandbox scope, then land the chosen policy with docs and regression coverage.

## Reproduction Assessment

Yes from source: with `tools.fs.workspaceOnly` unset or false, host read/write/edit are built without the workspace guard and tests assert outside-workspace access succeeds. I did not run a live Feishu/minimax reproduction in this read-only review.

## Solution Assessment

Unclear as an implementation path: flipping existing workspace-only defaults is plausible but compatibility-sensitive and does not settle exec/process access. The safer next step is a maintainer security/product decision that defines the default, migration, and scope.

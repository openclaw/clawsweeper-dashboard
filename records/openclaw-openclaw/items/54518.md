## Summary

Keep open: current main and v2026.6.11 still treat the agent workspace as a default cwd plus optional hardening, not as a hard per-agent filesystem boundary. The related PRs and issues are useful context, but they are partial, broader architecture/config proposals, or unmerged, so none safely supersedes this concrete report.

## What This Changes

The issue asks for hard per-agent filesystem containment so an agent cannot read or modify paths outside its assigned workspace.

## Best Possible Solution

Keep this as the concrete workspace-confinement report while maintainers define the default boundary, migration story, and whether filesystem tools, exec/process, and sandboxing are solved together or split into narrower canonical subtasks.

## Reproduction Assessment

Yes. From source and tests, with `tools.fs.workspaceOnly` unset or false, current host read/write/edit are not wrapped in a workspace boundary and tests assert outside-workspace access succeeds; I did not run the Feishu/minimax scenario in this read-only review.

## Solution Assessment

Unclear as a one-step implementation. Flipping `tools.fs.workspaceOnly` by default would address file tools but is compatibility-sensitive and does not fully cover exec/process access, so the best path is a maintainer security/product decision on default, migration, and scope.

## Label Justifications

- `P2`: This is a normal-priority feature/design issue with meaningful Feishu group-chat impact but no current-main emergency or strict bug-fix path.
- `impact:session-state`: The request centers on per-user conversation memory, session isolation, and avoiding shared group context pollution.
- `impact:security`: Automatically mapping group senders to durable agents, skills, workspaces, config, and memory creates authorization and data-isolation boundaries.
- `impact:message-loss`: The issue describes misrouting and incorrect replies in Feishu group conversations when participants or agent roles share routing state.

## Summary

Keep open: current main and v2026.6.11 support Feishu group sender/topic session scoping, DM-only dynamic agents, and explicit thread-bound subagent hooks, but not automatic durable per-sender group agents with isolated workspaces, skills, config, memory, lifecycle, quotas, and authorization.

## What This Changes

Request automatic Feishu group-chat routing that provisions a per-sender subagent with isolated skills, configuration, memory, and session state, then relays that subagent's reply back to the group.

## Best Possible Solution

Define a maintainer-approved identity-to-agent binding plus authorization, quota/lifecycle, and shared/private memory contract first, then implement optional Feishu group-sender provisioning through channel/plugin routing seams.

## Maintainer Decision

Required: true

Question: Should Feishu group chat support automatic durable per-sender agent provisioning, and what identity, authorization, quota/lifecycle, and shared/private memory contract should govern it?

Rationale: The request changes durable agent creation, workspace/config mutation, memory isolation, routing authority, and cost/security boundaries rather than only fixing a Feishu session-key bug.

Likely owner: steipete

Owner reason: This decision spans Feishu routing, plugin API boundaries, subagent semantics, memory/security policy, and core-lean product direction.

Owner confidence: medium

Options:

- **Design Generic Contract First (recommended):** Approve a generic, admin-authorized identity-to-agent lifecycle and shared/private memory contract, then implement Feishu as one channel/plugin adopter.
- **Keep Explicit Routing Only:** Keep current group session scoping plus explicit thread-bound subagents and document external deployment patterns for per-user agent fleets.
- **Decline Automatic Provisioning:** Close this direction if group chat sender identities should not automatically create durable agents inside OpenClaw.

## Reproduction Assessment

Yes, source-level: current main can route Feishu group sessions by sender/topic and can create dynamic agents for DMs, but the group path never calls the dynamic-agent factory and Feishu subagent hooks require explicit thread-bound spawn.

## Solution Assessment

No, not as an implicit Feishu-only subagent factory; the safer solution is a generic admin-authorized identity-to-agent lifecycle and memory contract before any Feishu implementation.

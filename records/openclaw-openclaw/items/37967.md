## Summary

Keep open: current main and v2026.6.11 support adjacent Feishu DM dynamic agents, group sender/topic session scoping, and explicit thread-bound subagent hooks, but they do not implement automatic durable Feishu group-sender subagents with isolated workspaces, skills, config, memory, lifecycle, quotas, and authorization.

## What This Changes

The issue requests automatic Feishu group-chat per-sender subagents with isolated skills, config, memory, lifecycle, and routing.

## Best Possible Solution

Define a maintainer-approved identity-to-agent lifecycle, authorization/quota model, cleanup policy, and shared/private memory contract first, then implement optional Feishu group-sender provisioning through plugin-owned routing seams.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Feishu group chat support automatic durable per-sender agent provisioning, and what identity, authorization, quota/lifecycle, and shared/private memory boundaries should become the public contract?

Rationale: The missing behavior is clear, but implementing it would create durable agents, workspaces, configs, skills, memory namespaces, and message-routing authority from group-chat senders, which is a product and security boundary decision rather than a narrow bug fix.

Likely owner: steipete

Owner reason: This choice crosses Feishu plugin behavior, core routing contracts, security defaults, and VISION.md product guardrails, and steipete has the strongest recent history across those surfaces.

Owner confidence: high

Options:

- **Design generic contract first (recommended):** Create a generic admin-authorized identity-to-agent lifecycle and memory isolation contract, then let Feishu implement it as a channel-owned capability.
- **Keep session-only routing:** Keep current groupSessionScope and explicit thread-bound subagent mechanisms, documenting that full per-user group orchestration is not core behavior yet.
- **Reject automatic provisioning:** Close this feature direction if maintainers decide group identities must never create durable OpenClaw agents automatically.

## Reproduction Assessment

Yes, as a source-level feature gap: current Feishu group messages can be sender/topic-scoped as sessions and explicit thread-bound subagents can be bound, but the group path never calls the dynamic-agent factory and the dynamic-agent schema/docs are DM-only.

## Solution Assessment

No, not as an implicit Feishu-only subagent factory; the maintainable path is to settle a generic identity-to-agent lifecycle, memory, authorization, quota, and cleanup contract before wiring Feishu group senders into it.

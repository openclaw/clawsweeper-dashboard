## Summary

Keep open: current main and the latest release have Feishu sender/topic session scoping, DM-only dynamic agent creation, and explicit thread-bound subagent hooks, but they still do not automatically provision durable per-sender Feishu group agents with isolated workspaces, skills, config, memory, lifecycle, quotas, and authorization.

## What This Changes

Request automatic Feishu group-chat provisioning and routing of per-sender subagents with isolated skills, configuration, conversation memory, and lifecycle controls.

## Best Possible Solution

Define a maintainer-approved identity-to-agent binding with authorization, quota/lifecycle, shared/private memory, and plugin contract semantics first, then implement optional Feishu group-sender provisioning as one adopter.

- **Decline automatic provisioning:** Close this direction if group chat sender identities should not automatically create durable agents inside OpenClaw.

## Reproduction Assessment

Yes, source-level. Current Feishu group messages can be scoped by sender/topic and DMs can create dynamic agents, but the group path never calls the dynamic-agent factory and subagent hooks require an explicit thread-bound spawn.

## Solution Assessment

No, not as an implicit Feishu-only subagent factory. The safer path is a generic admin-authorized identity-to-agent lifecycle and memory contract before the Feishu implementation.

Summary: The issue is security-sensitive because it would create durable agents, workspaces, tools, and memory namespaces from group-chat identities.

- **[medium] Group senders would gain durable runtime identity:**
  - body: Automatic provisioning must define who may create agents, which group identities are trusted, and how per-user agents are authorized before they receive skills, config, or tool access.

  - body: The proposed design depends on preventing private sender memory from leaking through shared group memory or memory_search while still preserving group context.
  - confidence: 0.84
- **[low] Lifecycle and quota controls are part of the safety model:**
  - body: Without TTL, caps, cost attribution, and cleanup policy, a busy group could create unbounded agents and persistent state from ordinary messages.

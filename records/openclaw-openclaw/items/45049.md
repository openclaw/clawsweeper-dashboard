## Label Justifications

- `P1`: The issue affects real tool-enabled agent workflows and can leave users with fabricated tool-use claims or skipped intended actions.
- `impact:security`: The report concerns the protocol boundary for real tool invocation, pre-execution hooks, policy checks, and execution provenance.
- `impact:message-loss`: When a model emits prose or fake tool text instead of a structured call, the intended tool-mediated response or action can be silently absent.
- `impact:session-state`: The failure can leave transcripts with assistant claims or fake result text that are not backed by matching tool-call and tool-result ledger entries.

## Summary

Keep open: current main still has only partial handling. The Gateway HTTP `tool_choice` path rejects unsatisfied caller-supplied client-tool contracts, but the agent loop still dispatches tools only from structured `toolCall` content and otherwise treats JSON/XML/ReAct-style fake tool text as text with a warning.

## What This Changes

The issue requests stronger agent-loop enforcement when a model emits tool-call-looking assistant text instead of a real structured tool invocation.

## Best Possible Solution

Define a maintainer-approved protocol-boundary contract where real execution remains structured and hook-visible, fake tool-call text is either warned, suppressed, promoted, retried, or failed closed by explicit policy, and local-model docs/tests cover the chosen compatibility behavior.

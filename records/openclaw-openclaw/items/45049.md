## Label Justifications

- `P1`: The issue describes a core agent workflow reliability and trust problem where users can receive fake tool execution text instead of a trustworthy tool-backed result.
- `impact:security`: The issue concerns the tool-call protocol boundary and whether policy/audit hooks can trust that claimed tool execution passed through the real tool pipeline.
- `impact:message-loss`: When a user asks for tool-backed work, the agent can deliver ordinary text instead of performing and reporting the requested tool action.
- `impact:session-state`: Fake tool-call or tool-result-looking assistant text can be persisted in the session without a corresponding real tool-call ledger entry.

## Summary

Keep open: current main has partial mitigation for standalone serialized plain-text tool calls and warning diagnostics for JSON/XML/ReAct-looking tool text, but it still does not define a general agent-loop hard gate for the JSON-style fake tool call pattern in this report.

## What This Changes

The issue requests stricter agent-loop handling so model text that imitates or claims tool/tool-result execution is not accepted as equivalent to a real structured tool call.

## Best Possible Solution

Define a core agent-loop policy for fake tool-call text: keep execution limited to structured tool calls or narrowly approved repair formats, and decide whether other fake tool/result-looking final text should fail, be suppressed, or require an opt-in strict mode.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What should OpenClaw do when an ordinary agent turn ends with assistant text that looks like a tool call or tool result but no structured tool call was emitted?

Rationale: The source gap is concrete, but the default behavior is a product/security boundary because fail-closed enforcement, warning-only compatibility, bounded repair, and forced-tool retries have different local-model and upgrade tradeoffs.

Likely owner: steipete

Owner reason: The remaining choice is a core security/product boundary and the current related implementation history points to this owner most directly.

Owner confidence: medium

Options:

- **Fail or suppress by default (recommended):** Treat unstructured fake tool-call/tool-result final text as unsafe output, block normal delivery, and require a structured tool call or clear error path.
- **Keep warning-only compatibility:** Preserve current behavior, document provider-template fixes, and accept that fake tool-looking text can still reach users as text.
- **Add opt-in strict mode first:** Keep current defaults while adding a documented strict enforcement mode with tests for JSON, XML, ReAct, and false-positive cases.

## Reproduction Assessment

Yes from source inspection, but not from a live local-model run in this read-only review. Current main still has a path where JSON/XML/ReAct-looking fake tool text is detected and logged as text rather than generally failed or retried.

## Solution Assessment

Unclear: enforcing structured tool calls is the right security boundary, but the exact default is a maintainer choice because strict fail-closed behavior, warning-only compatibility, and opt-in strict mode all have different upgrade costs.

## Summary

Keep open: current main still lacks a maintainer-approved strict internal-agent enforcement path for simulated or tool-looking assistant text, while the merged Gateway HTTP work only covers caller-supplied OpenAI-compatible HTTP tool-choice contracts.

## What This Changes

The issue asks OpenClaw to prevent internal agent turns from treating simulated tool-call prose as successful work and to enforce real structured tool invocation when a tool is clearly required.

## Best Possible Solution

Keep arbitrary tool-looking assistant text non-executable, then add a maintainer-approved strict internal enforcement policy for explicitly tool-required turns with local-model compatibility guidance and regression coverage.

## Maintainer Decision

Question: Should internal OpenClaw agent turns add strict tool-call enforcement for clearly tool-required requests, and should that policy be default behavior or opt-in per agent/model?

Rationale: Current main intentionally mixes warning-only diagnostics, bounded text-tool promotion, and Gateway-only HTTP tool_choice enforcement, so tightening the internal loop changes both security posture and local-model compatibility.

Likely owner: steipete

Owner reason: The decision centers on the agent-core dispatch boundary and security/default tradeoff where recent relevant history points to steipete.

Owner confidence: high

Options:

- **Add opt-in strict enforcement (recommended):** Introduce a bounded strict policy for explicitly tool-required turns while preserving the current compatibility behavior by default until maintainers approve a default change.
- **Make strict behavior the default:** Fail or retry text-only tool-required turns across internal agent runs, accepting the upgrade risk as a stronger security default.
- **Fold into response gates:** Defer this to the broader pre-response enforcement design so tool-call enforcement and claim-vs-ledger checks share one policy model.

## Reproduction Assessment

Yes, at source level: current main executes only structured `toolCall` blocks with `stopReason: "toolUse"`, while unstructured tool-looking assistant text is diagnosed and treated as text. I did not run the reported vLLM/LiteLLM stack live in this read-only cleanup pass.

## Solution Assessment

Unclear as a final implementation direction: strict detection, forced retries, and deterministic routing are plausible, but the best fix needs maintainer policy because unconditional fail-closed behavior and text-tool promotion both carry compatibility and security tradeoffs.

## Label Justifications

- `impact:security`: The report concerns a protocol-boundary and policy-hook enforcement gap around tool execution provenance.
- `impact:message-loss`: When a model emits fake tool-call text or fake completion text, the user can receive a final message instead of the tool-backed result they requested.

## Summary

Keep open: current main still leaves the central internal-agent behavior unresolved. It executes structured tool calls, logs unstructured JSON/XML/ReAct-style tool-looking text as text, and keeps bounded compatibility promotion for standalone bracketed tool-call text; the merged Gateway HTTP work only enforces caller-supplied `tool_choice` contracts.

## What This Changes

The issue requests stricter agent-loop handling so simulated tool-call text cannot stand in for a real structured tool invocation, especially for local OpenAI-compatible model stacks.

## Best Possible Solution

Keep arbitrary tool-looking assistant text non-executable, then design a maintainer-approved strict internal enforcement path for tool-required turns with upgrade-safe defaults, local-model guidance, and tests across agent-core, provider streams, and Gateway HTTP.

Owner confidence: medium

Options:

- **Design opt-in strict enforcement (recommended):** Add a bounded strict mode or policy contract that retries/fails closed only when the turn is explicitly tool-required, while preserving current compatibility behavior by default until maintainers approve a default change.
- **Make strict behavior the default:** Treat clear tool-required text-only turns as failures across internal agent runs, accepting the upgrade and local-model compatibility risk as a security default change.
- **Fold into broader response gates:** Defer this item to the larger response-gate and ledger-verification direction tracked by related issues, trading a cleaner policy model for a larger design effort.

## Solution Assessment

Unclear as implementation direction: strict detection, retrying with forced `tool_choice`, and deterministic routing are plausible, but the best fix needs maintainer policy because default fail-closed behavior and text-tool promotion both carry compatibility and security tradeoffs.

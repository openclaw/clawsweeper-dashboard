## Label Justifications

- `P1`: The issue affects real tool-enabled agent workflows and can leave users with fabricated or skipped tool-backed work.
- `impact:security`: The report concerns the protocol boundary for real tool invocation, hook-visible execution, policy checks, and provenance.
- `impact:message-loss`: When a model emits fake tool text instead of a structured call, the intended tool-mediated action or reply can be silently skipped.
- `impact:session-state`: The failure can leave transcripts with assistant claims or fake result text that have no matching tool-call and tool-result ledger entries.

## Summary

Keep open: current main still treats JSON/XML/ReAct-style fake tool-call text as warning-only text, while the merged Gateway tool_choice work only enforces caller-supplied HTTP client tools and does not settle the general agent-loop policy.

## What This Changes

The issue asks OpenClaw to enforce real structured tool invocation when models emit text that simulates a tool call instead of a proper tool_calls/toolCall object.

## Best Possible Solution

Define a maintainer-approved protocol-boundary contract: real execution stays structured and hook-visible, fake tool-call text gets explicit warning, suppression, bounded promotion, retry, or fail-closed behavior, and docs/tests cover the chosen local-model compatibility story.

Owner confidence: high

Options:

- **Define bounded enforcement (recommended):** Choose the exact warning, suppression, promotion, retry, or fail-closed contract and implement it with focused agent-loop, provider-stream, Gateway, docs, and regression coverage.
- **Keep warning-only compatibility:** Document the current behavior as provider/model incompatibility and accept that fake tool-call text can still reach transcripts or visible replies without a real tool call.
- **Split response-gate work:** Limit this issue to syntactic fake tool-call text and leave natural-language success claims or mandatory validator policies to the broader response-gate tracking item.

## Reproduction Assessment

Yes, at source level: current main has a test and diagnostic path where JSON text pretending to call a registered tool logs a warning and is treated as text instead of being retried or rejected. I did not run a live local-model replay in this read-only review.

## Solution Assessment

Unclear. The protocol boundary is the right layer, but maintainers still need to choose the default behavior for fake text, bounded promotion, forced tool_choice, retries, suppression, and local-model compatibility.

## Label Justifications

- `P1`: The issue affects real tool-enabled agent workflows and can leave users with fabricated tool-use claims or skipped intended actions.
- `impact:security`: The report concerns the protocol boundary for real tool invocation, pre-execution hooks, policy checks, and execution provenance.
- `impact:message-loss`: When a model emits prose or fake tool text instead of a structured call, the intended tool-mediated response or action can be silently absent.
- `impact:session-state`: The failure can leave transcripts with assistant claims or fake result text that are not backed by matching tool-call and tool-result ledger entries.

## Summary

Keep open: current main has partial handling, not a complete fix. The agent loop still only dispatches structured `toolCall` content on `toolUse`, current diagnostics warn and treat unstructured tool-call-looking text as text, bounded local-model text promotion still exists for compatibility, and the merged Gateway work only enforces caller-supplied HTTP `tool_choice` contracts.

## What This Changes

The issue requests stricter agent-loop handling so model-authored text that looks like a tool invocation is not accepted as a real tool call, and so clearly required tools can be enforced or retried.

## Best Possible Solution

Define a maintainer-approved protocol-boundary contract where real execution stays structured and hook-visible, fake tool-call text gets explicit warning, suppression, promotion, retry, or fail-closed behavior, and local-model docs/tests cover the chosen compatibility story.

## Label Justifications

- `P1`: The issue affects real agent/tool workflows for local OpenAI-compatible providers and has security-sensitive implications, but it is not proven as an emergency security bypass on current main.
- `impact:security`: The report is about the protocol boundary that decides whether model-authored text can become an audited tool execution path.
- `impact:message-loss`: When required tools are not invoked, users can receive final prose instead of the intended fetched/searched/action result.
- `impact:session-state`: Simulated or promoted tool-call text affects transcript/tool-call ledger consistency and subsequent agent state.

## Summary

Keep open: current main partially addresses the Gateway HTTP `tool_choice` path, but the agent/provider runtime still has documented plain-text tool-call compatibility and warning-only handling for other simulated shapes, so the core security/default-policy question remains unresolved.

## What This Changes

Require agent/tool execution to rely on real structured tool calls instead of accepting, promoting, or delivering model-written simulated tool-call text, especially for local OpenAI-compatible providers.

## Best Possible Solution

Adopt a maintainer-approved protocol-boundary policy: structured tool calls only by default for security-sensitive agent runs, with any local-model plain-text repair explicit, bounded, audited, documented, and covered by agent/provider/Gateway tests.

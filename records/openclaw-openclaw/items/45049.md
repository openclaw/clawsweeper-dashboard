## Label Justifications

- `P1`: The issue affects real agent/tool workflows and a security-sensitive protocol boundary, but it still needs maintainer policy review rather than emergency closure or an immediate automated fix.
- `impact:security`: The report and current source concern whether executable tool intent can originate from assistant text instead of the structured tool-call protocol.
- `impact:message-loss`: When a model simulates tool use or completion in text, the user-visible reply can replace the intended tool-backed action or channel workflow.
- `impact:session-state`: Fake or promoted tool-call text can make the transcript and actual tool ledger diverge from the user's expected agent state.

## Summary

Keep open: current main has diagnostics and a shipped Gateway HTTP `tool_choice` fix, but the broader agent-runtime boundary still has an intentional standalone-text promotion path and no maintainer-approved strict policy for simulated tool-call text.

## What This Changes

The issue asks OpenClaw to prevent assistant text from simulating tool calls and to require real structured tool invocation through the agent tool pipeline.

## Best Possible Solution

Settle the tool-call security contract first, then implement one core path where assistant text is non-executable by default and any local-model repair is explicit, documented, tested, and audit-visible.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw make structured `toolCall`/`toolUse` protocol objects the only default executable tool boundary, or keep the current standalone assistant-text promotion for local-model compatibility?

Rationale: Current main deliberately combines diagnostic-only handling for unstructured fake-tool text with an executable promotion path for certain standalone text formats, and changing either side affects both security posture and local-model compatibility.

Likely owner: steipete

Owner reason: Recent blame points to this owner across the current runtime promotion, diagnostics, and documentation surfaces.

Owner confidence: high

Options:

- **Strict protocol by default (recommended):** Make assistant text non-executable by default and move any text repair behind an explicit provider compatibility path with warnings and regression coverage.
- **Keep compatibility promotion:** Retain standalone text promotion as supported behavior and narrow this issue to docs, warnings, and better forced-tool-choice guidance.
- **Defer to response gates:** Treat this as part of the broader pre-response enforcement design in https://github.com/openclaw/openclaw/issues/13583 instead of changing the tool-call boundary now.

## Reproduction Assessment

Yes at source level: current main still wraps live streams with standalone text-to-tool promotion and only logs unstructured fake-tool text as diagnostic text. I did not run the reported LiteLLM/vLLM stack live.

## Solution Assessment

No current implementation is only a partial mitigation: Gateway HTTP `tool_choice` enforcement helps client-supplied HTTP tools, but it does not settle the general agent runtime boundary or the standalone text promotion policy.

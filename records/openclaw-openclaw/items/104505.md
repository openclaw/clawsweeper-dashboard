## Label Justifications

- `merge-risk: 🚨 security-boundary`: The proposed guard runs after a parser that can materialize inherited configuration, so merging as written could misstate the protection at the config trust boundary.

## Summary

The two resolver changes do not fix the production fetch path: OpenClaw validates raw config with Zod first, and pinned Zod 4.4.3 reads shaped properties through the prototype chain and writes them into the parsed object, so the later `Object.hasOwn` check sees an own `firecrawl` property. The newest tests bypass that validator and add a duplicate schema instead, leaving the prior P1 unresolved.

## What This Changes

This PR changes two legacy Firecrawl config lookups to `Object.hasOwn`, exports the fetch resolver, adds a separate Firecrawl Zod schema, and adds three prototype-chain test suites plus extension-runner expectations.

## Best Possible Solution

Enforce own-property semantics on raw legacy Firecrawl configuration before `OpenClawSchema` materializes inherited fields, retain resolver checks only as secondary defense, and cover the actual validation path without a parallel schema or test-only API export.

No. `Object.hasOwn` is the right primitive, but applying it only after Zod parsing is too late for fetch config; the narrow maintainable fix belongs at the raw validation boundary with focused production-path coverage.

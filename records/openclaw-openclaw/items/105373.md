## Label Justifications

- `P2`: The deterministic stale state breaks worktree-management actions but remains recoverable through another refresh or page reload.
- `impact:ux-friction`: The page can offer an invalid repeated delete and hide the valid Restore action until the user refreshes again.

## Summary

Current `main` still contains the reported race: an older `worktrees.list` request can block the delete finalizer’s reload and later restore the deleted row as Active/Delete. No canonical replacement or open fix PR was found, and the protected `maintainer` label requires explicit maintainer handling.

Likely related people: `steipete` is the high-confidence feature owner and recent Worktrees race-fix contributor; `steipete-oai` authored the page’s lifecycle-boundary hardening.

## What This Changes

Fix the Worktrees page so an in-flight refresh cannot overwrite post-delete state with a stale active row.

## Best Possible Solution

Give list refreshes one canonical ownership mechanism that invalidates stale responses or guarantees a trailing post-mutation reload, then add a deferred-response regression test proving the row becomes Restorable/Restore after deletion.

Required: false

## Reproduction Assessment

Yes. The report provides a concrete real-Gateway Playwright ordering, and current `main` deterministically permits it because the delete finalizer’s reload is dropped while the older list request owns `loading`.

## Solution Assessment

Yes, if solved through the Worktrees page’s existing generation and operation-ownership model. Changing Gateway records or RPC semantics would be broader and would not fix the client-side stale-response owner.

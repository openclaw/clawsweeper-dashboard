## Label Justifications

- `P1`: The patch targets an indefinite database-startup hang, but the exact-head synchronous timeout still cannot guarantee recovery from a child that has not exited.

## Summary

The latest head still relies on a synchronous child-process probe whose timeout does not provide the claimed hard startup deadline, and the PR still lacks real-host proof for that failure mode; the central P1 blocker from the prior review remains.

## What This Changes

Adds a one-second timeout and conservative rollback-journal selection to SQLite’s fallback mount classification, with regression tests and deferred child-process loading.

## Best Possible Solution

Move mount classification out of the synchronous database-open path—using a genuinely bounded asynchronous or prepared probe, or a conservative no-probe fallback—and prove on a supported host that SQLite initialization proceeds after the deadline while preserving local-versus-network journal policy.

## Reproduction Assessment

Yes at source level: current main synchronously invokes `mount` during SQLite setup, and Node documents that the timeout path still waits for child exit; the supplied fixture demonstrates the ordinary timeout case but not a truly non-exiting real process.

## Solution Assessment

No. Adding a timeout to `execFileSync` is a plausible mitigation but not the best fix because it leaves database startup coupled to child termination; the probe must be removed from or made genuinely non-blocking for the database-open path.

## Label Justifications

- `P1`: A blocked mount fallback can prevent state and plugin databases from opening, breaking startup for affected users.
- `merge-risk: 🚨 compatibility`: Timeout classification changes existing installations from WAL to rollback journaling when their filesystem cannot be identified within one second.

## Summary

Keep this PR open: the reported startup hang is valid, but the latest head still relies on a synchronous Node subprocess whose timeout does not guarantee that database opening returns, and the claimed hard deadline therefore remains unproven.

## What This Changes

The PR adds a one-second timeout to fallback `mount` classification during SQLite opening, selects rollback journaling on timeout, and expands the related WAL policy tests.

## Best Possible Solution

Remove the system `mount` subprocess from synchronous database opening, use already-available filesystem metadata when definitive, and conservatively select rollback journaling when classification is unavailable; prove both local and unclassifiable paths on a supported host.

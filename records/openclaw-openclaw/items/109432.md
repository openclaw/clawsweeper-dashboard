## Label Justifications

- `P1`: A wedged fallback mount probe can leave state or plugin database startup unavailable, but the failure requires a specific host/filesystem condition rather than affecting every installation.
- `merge-risk: 🚨 compatibility`: A probe exceeding one second now switches the database to persistent rollback journaling, changing existing journal behavior and potential performance.
- `merge-risk: 🚨 availability`: The changed startup path still uses a synchronous primitive that can wait indefinitely for an unexited child despite the configured timeout.

## Summary

Keep open: the startup-hang report is valid, but this head does not establish a hard deadline because Node’s synchronous child-process API still waits for the child to exit after sending the timeout signal, while the supplied fixture exercises only a killable process.

## What This Changes

Adds a one-second SIGKILL timeout to fallback SQLite mount classification, selects rollback journaling on timeout, lazily loads probe dependencies, and adds regression tests.

## Best Possible Solution

Make filesystem classification non-blocking relative to database open—prefer an asynchronous pre-open probe with a real parent-side deadline and a prepared classification result, or explicitly adopt conservative rollback when classification is unavailable—then prove both local-WAL and network/unknown-rollback behavior on supported hosts.

## Solution Assessment

No. Adding timeout options to execFileSync is a useful mitigation for killable children, but it is not the best fix for a database-open path that must never wait indefinitely; classification must leave that synchronous boundary or be omitted conservatively.

## Summary

Keep open: current main fixed the default-marker path for new or marked CLI-backed cron jobs, but the corrected issue still has a source-reproducible residual where restricted agent-side `toolsAllow: null` is recapped and explicit or flagless allow-lists still fail closed on CLI backends.

## What This Changes

Agent-created isolated cron jobs can inherit a creator `toolsAllow` policy that conflicts with CLI-backed execution, while agent-side `toolsAllow: null` appears to clear the field but is recapped.

## Best Possible Solution

Preserve the explicit CLI fail-closed guard, make restricted agent-side clears return a clear error or approved narrow clear path, and add a tightly scoped doctor/operator repair for provably stale auto-default cron caps if maintainers accept the criteria.

Rationale: The current source intentionally recaps restricted agent updates and intentionally fails closed when a CLI backend receives a runtime allow-list it cannot enforce, so choosing between explicit rejection, narrow clearing, stale repair, or runtime relaxation changes a security boundary.

Owner confidence: high

Options:

- **Reject Or Explain Restricted Clears (recommended):** Keep the security boundary, return an explicit agent-facing error for blocked null clears, and add a narrow doctor/operator repair for provably auto-default stale caps.
- **Authorize Narrow Agent Clear:** Allow only inherited default caps to be cleared through the agent cron tool while preserving explicit restrictions and proving the distinction with tests.
- **Relax CLI Runtime Handling:** Warn and ignore selected inherited caps at runtime on CLI-backed jobs, accepting that those restrictions are not enforced by the backend.

Yes, at source level: current code and tests show restricted agent-side `toolsAllow: null` is recapped, and explicit or flagless cron allow-lists still reach the CLI fail-closed guard. I did not run the reporter's live cron jobs in this read-only review.

## Solution Assessment

Unclear until maintainers choose the security posture. A broad runtime ignore is not the best fix; the safer direction is explicit agent-facing feedback plus a narrow stale-default repair that preserves explicit restrictions.

## Label Justifications

- `P2`: The issue describes a real Feishu streaming usability problem with bounded channel-specific blast radius and no evidence of data loss, security bypass, crash loop, or unusable core runtime.
- `impact:ux-friction`: Feishu users can continue working, but streamed replies show avoidable progress noise and the documented hide-progress policy does not apply to Feishu.

## Summary

Keep open: current main and the latest release still leave Feishu with boolean-only streaming configuration while Feishu streaming cards append tool-progress status lines, so the Feishu opt-out/status-only behavior remains unresolved and needs product direction.

## What This Changes

The issue requests less misleading Feishu tool-progress rendering for benign non-zero exec outcomes plus a Feishu-specific way to keep streaming while hiding or sanitizing tool-progress command text.

## Best Possible Solution

Adopt the shared streaming preview policy for Feishu with backward-compatible boolean handling, schema/manifest/docs/tests, and default behavior preserved; keep `config.patch` protection unchanged unless maintainers separately approve a narrow operator-boundary change.

- **Only soften command wording:** Keep Feishu streaming config boolean-only and separately improve benign non-zero command-output wording, which reduces scary copy but still leaves no Feishu streaming-without-progress mode.

## Reproduction Assessment

Yes, source-level: Feishu registers `onToolStart` whenever streaming is enabled and appends the resulting status line into the live card text. I did not run a live Feishu websocket/Card Kit deployment, so this is source-reproducible rather than live-reproduced.

## Solution Assessment

Unclear until maintainers choose the Feishu config and operator-boundary contract. Reusing the shared preview policy looks like the narrowest maintainable direction, while one-off string filtering or broad `config.patch` allowlisting would leave policy drift or security-boundary risk.

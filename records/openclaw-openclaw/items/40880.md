## Summary

Keep open: current main and v2026.6.11 still enforce the fixed 5 MiB media-store and sandbox-staging cap, while the open related PR only covers one Telegram outbound reply-media slice.

## What This Changes

The issue requests making OpenClaw's hardcoded 5 MiB media-store and sandbox-staging limit configurable so larger files can be staged or delivered without patching built bundles.

## Best Possible Solution

Define one bounded, documented media-store and sandbox-staging limit contract, keep secure defaults, thread it through store, staging, gateway preflight, and reply-media callers, and keep the Telegram outbound slice aligned with that contract.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 still bind media store, sandbox staging, gateway preflight, and default reply-media persistence to the 5 MiB MEDIA_MAX_BYTES path. I did not run a live sandbox/container reproduction in this read-only review.

## Solution Assessment

Unclear as a final design. Making the cap configurable is plausible, but the best fix needs maintainer-approved precedence with existing mediaMaxMb settings, secure defaults, hard upper bounds, and upgrade behavior.

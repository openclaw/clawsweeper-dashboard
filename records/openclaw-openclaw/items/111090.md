## Label Justifications

- `P1`: A failed plugin registration can leave mutated process-global registry entries behind instead of rolling them back.
- `merge-risk: 🚨 compatibility`: The transaction snapshot defines rollback semantics for plugin-provided registry values, and shared mutable instances violate that compatibility contract.

## Summary

Keep open: the revised snapshot helper still retains non-Date custom-class instances by reference, so an in-transaction mutation of one of their own fields survives rollback—the same rollback invariant this PR is intended to restore.

## What This Changes

The PR replaces shallow plugin-registration transaction snapshots with recursive cloning and adds rollback coverage for nested objects, Dates, functions, and custom-class values.

## Best Possible Solution

Clone mutable custom instances into an object with the original prototype and recursively isolated own state, while retaining only genuinely immutable or non-clonable callable values by reference.

## Reproduction Assessment

Yes, from source: put a mutable custom-class instance in a registry entry, mutate one of its own fields after the transaction snapshot, then roll back. The snapshot fallback returns that same instance, so the mutation remains.

## Solution Assessment

No. Keeping custom instances by reference preserves their prototype but contradicts rollback isolation; a prototype-preserving recursive clone is the narrower solution.

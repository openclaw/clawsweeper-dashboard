## Label Justifications

- `P1`: The patch targets plugin-install rollback correctness, and the remaining collection-cloning defect can leave registry state invalid after a failed registration transaction.
- `merge-risk: 🚨 compatibility`: The new snapshot semantics can break existing plugin registration values that use `Map` or `Set` collections when fallback cloning is triggered.

## Summary

This PR addresses the linked rollback bug and includes credible runtime proof for nested objects, `Date`, functions, and custom-class instances, but it still mishandles collection values when `structuredClone` rejects a nested callback. A `Map` or `Set` then falls into the prototype-only object reconstruction path, which does not recreate collection entries or their internal collection state; the prior blocker remains on the unchanged head.

## What This Changes

The branch replaces shallow plugin-registry transaction snapshots with recursive cloning and adds rollback coverage for nested objects, `Date`, functions, and custom-class instances.

## Best Possible Solution

Clone `Map` and `Set` explicitly with recursively cloned entries before the typed-object fallback, preserve their collection semantics on rollback, and add focused rollback regressions for callback-bearing collections.

## Solution Assessment

No. Deep rollback snapshots are the right boundary, but the proposed generic object fallback is not sufficient for collection objects; explicit collection cloning is the narrower maintainable repair.

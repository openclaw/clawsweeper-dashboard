## What This Changes

## Best Possible Solution

Kind: product_direction

Question: How should a failed-cron dismissal re-arm when the Control UI does not observe the job’s recovery before it fails again?

Rationale: Job IDs alone cannot distinguish later incidents, while adding run timestamps would repeatedly resurface persistently failing jobs; the permanent snooze semantics therefore require a product-level incident or expiry rule.

Likely owner: steipete

Owner reason: This person has the strongest recent connection to the Control UI behavior and is best positioned to choose the intended snooze semantics.

Owner confidence: high

Options:

- **Add bounded re-arm (recommended):** Store dismissal time and expire or re-arm failed-cron snoozes after a defined interval so later incidents eventually surface without nagging on every failed run.
- **Use incident generations:** Derive a stable failure-generation identity from an authoritative cron transition field, if the runtime contract can reliably distinguish recovery and recurrence.
- **Keep observed-clear semantics:** Accept that recurrence only resurfaces after a tab observes recovery, and narrow the PR’s user-facing claims and tests to that limitation.

No. Client-local persistence is the correct ownership boundary, but the current gateway scope and failed-cron incident identity do not safely implement the promised resurfacing behavior.

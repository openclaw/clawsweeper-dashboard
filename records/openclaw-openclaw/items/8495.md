## Summary

Keep open: current main still denies unauthorized WhatsApp group traffic without leaving the group or exposing a join-specific notification/action. The change is feasible through the WhatsApp plugin and Baileys, but destructive departure behavior, privacy-sensitive event payloads, and the permanent configuration/tool contract require explicit product and security direction.

## What This Changes

Add optional automatic departure from unauthorized WhatsApp groups, a group-join event or webhook, and a manual leave-group action.

## Best Possible Solution

Implement a narrowly scoped, disabled-by-default WhatsApp plugin policy keyed to `channels.whatsapp.groups`, with `ignore` as the compatibility default and an explicit `leave` mode; detect self-add events account-safely, deduplicate them, verify the current group policy immediately before departure, and defer generic hooks or an agent-callable leave action to separately approved contracts.

## Risks / Open Questions

- `groupAllowFrom` authorizes senders inside groups, while `channels.whatsapp.groups` controls group membership admission; using the former as the departure list could remove the account from legitimate groups.
- Automatic departure is destructive and may fire on duplicated or replayed participant events, reconnect synchronization, stale account identity, or transient configuration state unless the operation is account-scoped and idempotent.
- A group-join event may disclose group names, identifiers, inviter identity, and participant metadata to sessions or plugins, requiring an explicit privacy and authorization contract.
- Combining auto-leave, a generic webhook, a system event, and an agent-callable leave action in one implementation would create several compatibility- and security-sensitive public surfaces at once.
- Baileys group and identity behavior remains volatile enough that live WhatsApp proof is required before accepting an implementation.

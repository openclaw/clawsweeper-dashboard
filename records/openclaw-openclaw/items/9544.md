## Summary

Keep open. Current main and v2026.6.11 still use Baileys `useMultiFileAuthState`; existing hardening protects `creds.json` but leaves Signal keys in the released multi-file store, and this member-authored security-sensitive migration needs an explicit storage and upgrade decision.

## What This Changes

Replace Baileys multi-file WhatsApp authentication state with a production database-backed store and safely migrate existing credentials and Signal keys.

## Best Possible Solution

Use a WhatsApp-owned relational SQLite store that implements the Baileys auth contract, migrate every released JSON credential and key category transactionally through the plugin doctor boundary, verify restart and key persistence before deleting legacy files, and make runtime consume only the canonical database state.

## Risks / Open Questions

- A one-way migration can irreversibly lose a linked session if every Baileys credential and key category is not copied, transactionally committed, and verified before cleanup.
- Credentials and Signal keys need explicit database permissions, redacted diagnostics, backup retention, logout deletion, corruption recovery, and rollback policy.
- The released JSON layout and public `authDir` override are upgrade contracts; changing them requires a doctor migration and clear operator recovery rather than runtime fallback.
- The generic plugin keyed-state store has JSON and per-value size constraints, so using it without proving suitability for every Baileys key category could create a second persistence failure mode.

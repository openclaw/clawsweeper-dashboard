## Summary

Keep open. Current main and the latest release still build the WhatsApp socket through Baileys `useMultiFileAuthState`, so the requested production auth-store replacement remains missing; the issue is MEMBER-authored and security/session-state-sensitive, which rules out conservative cleanup closure.

## What This Changes

Replace the bundled WhatsApp plugin's Baileys multi-file auth-state persistence with a production auth store for credentials and signal keys, with caching and safer retrieval by WhatsApp account.

## Best Possible Solution

Keep this open for a maintainer-owned WhatsApp plugin auth-store redesign that replaces Baileys multi-file persistence, migrates existing auth directories through the plugin or doctor boundary, preserves status/logout/setup behavior, updates docs, and proves fresh install, upgrade, corruption recovery, and key persistence.

## Reproduction Assessment

Yes, at source level: current main still calls Baileys `useMultiFileAuthState` and keeps Baileys signal keys in the multi-file auth store. No live current-main corruption or IO-growth reproduction was run in this read-only review.

## Solution Assessment

Unclear until maintainers choose the permanent storage and migration contract. Moving away from Baileys multi-file auth is directionally supported by current source and OpenClaw's database-first policy, but the exact custom store must be designed against SQLite, plugin-owned doctor migration, and security requirements.

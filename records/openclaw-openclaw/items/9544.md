## Summary

Keep open. Current main and the latest release still use Baileys multi-file auth for the bundled WhatsApp plugin, and the issue is maintainer-authored plus security-sensitive, so it is not eligible for conservative cleanup closure.

## What This Changes

Request replacing WhatsApp Baileys `useMultiFileAuthState` multi-file JSON storage with a production SQL-backed, cached auth state for credentials and signal keys.

## Best Possible Solution

Land a maintainer-approved WhatsApp plugin auth-store redesign that stores credentials and signal keys in SQLite through the appropriate OpenClaw state owner, migrates existing Baileys files via doctor, preserves login/status/logout semantics, and includes focused tests plus live WhatsApp proof.

## Reproduction Assessment

Yes for the source-level condition: current main still calls `useMultiFileAuthState(authDir)` and keeps Baileys multi-file key persistence. No live corruption or security reproduction was run in this read-only review.

## Solution Assessment

Unclear as an implementation, but the requested direction is valid. The durable fix should be a plugin-owned SQLite auth store with a tested migration path, not the closed single-file PR shape that broke fresh installs and risked silent key loss.

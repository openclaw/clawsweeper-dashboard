## Summary

Keep open. Current main and the latest release still use Baileys `useMultiFileAuthState` for WhatsApp, upstream Baileys still discourages that helper for production auth storage, and the only consolidated-store attempt at https://github.com/openclaw/openclaw/pull/66863 was closed unmerged with correctness concerns; this MEMBER-authored credential/session-store migration needs maintainer product and security direction.

## What This Changes

The issue requests replacing Baileys `useMultiFileAuthState` with a SQL/database-backed cached WhatsApp auth store for credentials and signal keys.

## Best Possible Solution

Keep this open until the WhatsApp plugin has a maintainer-approved production auth store, safe migration from existing Baileys credential and signal-key files, preserved status/logout/docs behavior, and focused tests for fresh install, migration, corruption recovery, and key persistence.

## Reproduction Assessment

Yes for source reproduction: current main and `v2026.6.11` still call `useMultiFileAuthState(authDir)` in the WhatsApp socket setup. I did not run a live WhatsApp account to reproduce corruption, CPU, or I/O load.

## Solution Assessment

Unclear. A database-backed or otherwise production-grade auth store is a plausible end state, but the exact storage, migration, doctor, and security contract need maintainer approval; current `creds.json` atomic hardening is not enough.

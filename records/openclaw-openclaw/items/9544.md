## Summary

Keep open. Current main and the latest release still use Baileys `useMultiFileAuthState` for the bundled WhatsApp plugin, and this MEMBER-authored, security-sensitive auth-store migration request needs maintainer product/security review rather than conservative cleanup closure.

## What This Changes

The issue requests replacing the WhatsApp plugin's Baileys multi-file credential and signal-key store with a production database-backed auth state plus caching and migration behavior.

## Best Possible Solution

Keep this open for a maintainer-approved WhatsApp plugin auth-store redesign that uses a canonical database-backed store, includes a safe migration or doctor path, preserves status/logout/setup behavior, updates docs, and proves fresh install, upgrade, corruption recovery, and key persistence.

## Reproduction Assessment

Yes, at source level: current main still calls Baileys `useMultiFileAuthState` and keeps signal keys in the Baileys multi-file auth store. No live corruption, CPU growth, or IO-growth reproduction was run in this read-only review.

## Solution Assessment

Unclear until maintainers choose the permanent storage and migration contract. Moving away from Baileys multi-file auth is directionally supported by current source, upstream guidance, and OpenClaw's database-first policy, but the exact store design is security-sensitive product work.

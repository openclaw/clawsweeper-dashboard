## Summary

Keep open. Current main and the latest release still build the WhatsApp socket through Baileys `useMultiFileAuthState`, so the requested production auth-store replacement remains missing; the issue is also MEMBER-authored and security/session-state-sensitive, which rules out cleanup closure.

## What This Changes

Issue requests replacing the bundled WhatsApp plugin’s Baileys multi-file auth-state storage with a SQL-backed production auth store for signal keys and credentials.

## Best Possible Solution

Keep this open for a maintainer-owned WhatsApp plugin auth-store redesign that replaces Baileys multi-file persistence, migrates existing auth directories through the plugin/doctor boundary, preserves status/logout/setup behavior, updates docs, and proves fresh install, upgrade, corruption recovery, and key persistence.

## Reproduction Assessment

Yes, at source level: current main still calls Baileys `useMultiFileAuthState` and keeps Baileys signal keys in the multi-file auth store. No live current-main failure reproduction was run for corruption or IO growth in this read-only review.

## Solution Assessment

Unclear. Moving away from Baileys multi-file auth is supported by current source and upstream guidance, but the exact custom SQL/Postgres shape should be decided against OpenClaw's SQLite, plugin-owned migration, doctor, and security requirements.

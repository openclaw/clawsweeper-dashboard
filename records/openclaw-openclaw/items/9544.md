## Summary

Keep open. Current main and the latest release still use Baileys `useMultiFileAuthState` for WhatsApp auth, and this MEMBER-authored, security-sensitive storage/migration request is not safe for conservative cleanup closure.

## What This Changes

The issue requests replacing Baileys multi-file WhatsApp auth-state storage with a production SQL-backed auth store for credentials and signal keys.

## Best Possible Solution

Adopt a plugin-owned SQLite-backed Baileys auth-state store with a tested doctor/plugin migration from existing multi-file auth dirs, while preserving `authDir`, status, logout, setup, backup, and fresh-install behavior.

## Reproduction Assessment

Yes, at source level: current main still calls Baileys `useMultiFileAuthState` and keeps signal keys in the Baileys multi-file auth store. No live corruption or IO-growth reproduction was run in this read-only review.

## Solution Assessment

Unclear until maintainers choose the permanent storage and migration contract. The direction is supported by current source, upstream Baileys guidance, and OpenClaw's database-first policy, but the safe implementation should likely use SQLite/shared storage rather than adding a broad Postgres config surface.

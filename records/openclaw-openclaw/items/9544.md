## Summary

Keep open. Current main and v2026.6.11 still use Baileys multi-file auth for the WhatsApp plugin, and this MEMBER-authored auth-storage migration request is security-sensitive maintainer work rather than cleanup-close material.

## What This Changes

Replace the bundled WhatsApp plugin's Baileys `useMultiFileAuthState` persistence with a production database-backed auth and signal-key store with safe caching and migration.

## Best Possible Solution

Implement a maintainer-owned WhatsApp plugin auth-store redesign that replaces Baileys multi-file persistence with canonical SQLite-backed key storage, adds doctor/plugin migration for existing auth directories, preserves status/logout/setup behavior, updates docs, and proves fresh install, upgrade, corruption recovery, and key persistence.

## Reproduction Assessment

Yes, at source level: current main still imports and calls Baileys `useMultiFileAuthState` and persists signal keys through that multi-file store. I did not run a live corruption or IO-growth reproduction in this read-only review.

## Solution Assessment

Directionally yes, but the exact implementation is not yet settled. The safest shape is a plugin-owned SQLite-backed store with an explicit migration and proof plan, not an ad hoc parallel auth format or broad new database configuration surface.

## Summary

The issue is still necessary: current main and v2026.6.11 retain Baileys multi-file authentication, while the upstream helper recommends a proper database for production use. Because this MEMBER-authored issue changes sensitive persistent session state and requires a permanent storage and migration boundary, it should remain open for explicit maintainer direction.

## What This Changes

Replace Baileys multi-file WhatsApp authentication persistence with a production database-backed credential and signal-key store.

## Best Possible Solution

Adopt a plugin-owned SQLite auth store with restrictive permissions and transactional account-scoped credentials and Signal-key tables, then provide one verified migration that retains a recoverable backup until fresh login, restart, reconnect, logout, and key-persistence proof succeeds before removing legacy files.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should WhatsApp auth state use a plugin-owned dedicated SQLite database or the shared OpenClaw state database, and what verification and rollback threshold must be met before legacy auth files are removed?

Rationale: The permanent owner determines credential isolation, transaction scope, backup lifecycle, account deletion semantics, and the security boundary for sensitive Signal and authentication material; repository evidence cannot choose that product and security contract.

Likely owner: steipete

Owner reason: This contributor appears in the original session history, recent persistence-boundary work, and the issue's maintainer-facing design discussion.

Owner confidence: high

Options:

- **Plugin-owned SQLite (recommended):** Use a dedicated WhatsApp SQLite store with transactional import, restrictive permissions, verified rollback, and delayed legacy-file cleanup.
- **Shared state database:** Use the shared state database only after explicitly approving its plugin ownership, backup, transaction, and high-volume Signal-key semantics.
- **Retain hardened files:** Continue hardening the multi-file store while accepting Baileys' production caveat and the existing file-count and lifecycle costs.

## Reproduction Assessment

Yes at source level: current main demonstrably uses Baileys multi-file auth for credentials and Signal keys. This read-only review did not establish a live corruption or performance reproduction, so it does not classify the reported consequences as a reproduced current-main bug.

## Solution Assessment

No, not as currently specified: database-backed storage is the right direction, but the proposed generic key/value schema omits the required SQLite owner, account identity, transactions, migration verification, rollback, permissions, and legacy cleanup contract.

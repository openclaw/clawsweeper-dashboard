## Summary

Keep open. Current main still uses Baileys multi-file authentication, upstream explicitly discourages that helper for production, and the closed replacement PR did not land; this MEMBER-authored, security-sensitive storage migration needs maintainer approval rather than cleanup. ([github.com](https://github.com/openclaw/openclaw/blob/main/extensions/whatsapp/src/session.ts))

## What This Changes

Replace the WhatsApp plugin’s Baileys multi-file credential and signal-key persistence with a production database-backed auth-state store and cache.

## Best Possible Solution

Implement one plugin-owned SQLite auth-state path through supported storage seams, with a verified one-time doctor migration from every Baileys file category, atomic transactions, secure permissions and backup handling, no steady-state dual reads, and focused fresh-install, upgrade, rollback, logout, corruption, and persistence proof.

- **Retain hardened files:** Keep multi-file auth temporarily and limit work to additional atomicity, diagnostics, and recovery hardening while documenting the production caveat.
- **Sponsor another backend:** Define a different supported storage contract only if SQLite cannot satisfy the plugin’s transaction, portability, or lifecycle requirements.

## Reproduction Assessment

Yes at source level: current main directly calls Baileys `useMultiFileAuthState`, and upstream identifies it as unsuitable for production use. A deterministic live corruption or CPU/IO benchmark has not been established, so this is source-reproducible rather than live-reproduced.

## Solution Assessment

Unclear pending maintainer direction. A plugin-owned SQLite store with one verified migration is consistent with upstream advice and repository storage policy, but the proposed generic KEY/VALUE/WHATSAPP_ID schema is not yet proven to be the best transaction, lifecycle, or upgrade design.

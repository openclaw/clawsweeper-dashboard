## Summary

Keep open. Current main and the latest release still use Baileys `useMultiFileAuthState` for the WhatsApp plugin, and this MEMBER-authored, security-sensitive storage/migration request should not be closed by conservative cleanup.

## What This Changes

The issue requests replacing the bundled WhatsApp plugin’s Baileys multi-file auth-state persistence with a production database-backed auth store.

## Best Possible Solution

Keep this open for a maintainer-owned WhatsApp plugin auth-store redesign that replaces Baileys multi-file persistence, migrates existing auth directories through plugin or doctor boundaries, preserves status/logout/setup behavior, updates docs, and proves fresh install, upgrade, corruption recovery, and key persistence.

## Reproduction Assessment

Yes, at source level: current main still calls Baileys `useMultiFileAuthState` and keeps signal keys in the Baileys multi-file auth store. No live corruption or IO-growth reproduction was run in this read-only review.

## Solution Assessment

Unclear until maintainers choose the permanent storage and migration contract. Moving away from Baileys multi-file auth is directionally supported by current source and OpenClaw's database-first policy, but the exact store design is a security-sensitive product decision.

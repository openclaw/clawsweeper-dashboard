## Summary

Keep open. Current main and v2026.6.11 still use Baileys multi-file authentication; this MEMBER-authored sensitive-state migration remains necessary but requires maintainer approval of the permanent database and upgrade boundary.

## What This Changes

Replace the bundled WhatsApp plugin's Baileys multi-file authentication state with a production database-backed store.

## Best Possible Solution

Make a plugin-owned SQLite schema the sole runtime store for Baileys credentials and signal keys, with one explicit migration owner that verifies a linked session and recovery before deleting legacy files and does not retain a steady-state file fallback.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should the bundled WhatsApp plugin make SQLite canonical for all Baileys credentials and signal keys, and what migration, rollback, backup, and legacy-file deletion guarantees must protect existing linked sessions?

Rationale: Repository policy and upstream guidance support replacing the file store, but selecting the permanent sensitive-state owner and its irreversible migration and retention rules requires maintainer intent.

Likely owner: mcaxtr

Owner confidence: high

Options:

- **Adopt canonical plugin SQLite (recommended):** Transactionally migrate all auth material into a plugin-owned SQLite schema, verify restart, reconnect, logout, and recovery, then remove legacy files only after successful validation.
- **Retain hardened multi-file state:** Continue atomic-write, recovery, and performance hardening without changing the persistent data model or deleting existing files.

## Reproduction Assessment

Yes at source level: current main demonstrably uses Baileys multi-file authentication and individual JSON signal-key records. The issue's corruption, CPU, I/O, and security consequences are plausible but are not established as one high-confidence live current-main reproduction.

## Solution Assessment

The database-backed direction is the best architectural end state under upstream guidance and repository policy, but only if it reuses a canonical plugin SQLite ownership seam and one migration path rather than introducing consolidated JSON, dual reads, or another compatibility store.

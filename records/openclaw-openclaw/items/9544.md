## Summary

Keep this issue open. Current main still uses Baileys’ multi-file auth state for the bundled WhatsApp plugin, while the related replacement PR was closed unmerged; because this is a MEMBER-authored, security- and persisted-session-sensitive migration, it needs an explicit maintainer storage and upgrade decision rather than automated cleanup.

## What This Changes

Replace the bundled WhatsApp plugin’s Baileys multi-file authentication state with a production-safe persisted signal-key store that safely migrates existing linked sessions.

## System Context

The bundled WhatsApp plugin initializes a Baileys socket from an account-specific authentication directory, then supplies the resulting credentials and signal-key store to message transport. That auth state also feeds status, identity, logout, backup recovery, and startup behavior, so replacing it affects linked-session durability and upgrade recovery.

## Architecture Diagram

flowchart LR
  A[WhatsApp account config] --> B[WhatsApp auth directory]
  B --> C[Baileys multi-file auth state]
  C --> D[Cached signal-key store]
  D --> E[Baileys socket]
  E --> F[WhatsApp message transport]
  C --> G[Auth status, identity, logout, recovery]

## Best Possible Solution

Design the store inside the WhatsApp plugin around OpenClaw’s canonical SQLite ownership, with an explicit one-time migration and verification path for existing Baileys files, then prove fresh install, upgrade, recovery, logout, status, and key persistence before landing.

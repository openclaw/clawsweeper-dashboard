## Summary

Keep open. Current main and the latest release still use Baileys multi-file WhatsApp auth state, the prior replacement PR was closed unmerged after correctness concerns, and the issue is maintainer-authored plus security/session-state sensitive.

## What This Changes

The issue requests replacing Baileys multi-file WhatsApp auth state with a production database-backed auth store.

## Best Possible Solution

Keep this issue as the canonical tracker until the WhatsApp plugin owns a durable SQLite-backed auth-state store, migrates existing Baileys multi-file credentials and signal keys, preserves status/logout/config behavior, updates docs, and adds focused fresh-install, migration, corruption-recovery, and key-persistence tests.

## Reproduction Assessment

Yes for source proof: current main still reaches `useMultiFileAuthState(authDir)` when creating the WhatsApp socket. I did not run a live WhatsApp repro in this read-only cleanup review, but the source path proves the requested replacement is absent.

## Solution Assessment

No, the current hardening is only a partial mitigation: atomic `creds.json` writes and backup recovery do not replace Baileys multi-file signal-key persistence. The maintainable fix is a plugin-owned durable store plus migration rather than another wrapper around the existing file layout.

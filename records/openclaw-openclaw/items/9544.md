## Summary

Keep open. Current main and the latest release still use Baileys `useMultiFileAuthState` for WhatsApp auth, the prior replacement PR closed unmerged, and this MEMBER-authored security/session-state storage migration needs maintainer direction rather than conservative cleanup closure.

## What This Changes

Replace the bundled WhatsApp plugin's Baileys multi-file auth state with a production database-backed auth store for credentials and signal keys.

## Best Possible Solution

Keep this as a maintainer-owned WhatsApp plugin auth-store redesign using the canonical SQLite/doctor migration boundary, preserving status/logout/setup behavior and proving fresh install, upgrade, corruption recovery, and key persistence.

## Reproduction Assessment

Yes at source level: current main still calls Baileys `useMultiFileAuthState` and keeps signal keys in the multi-file auth store. No live current-main corruption or IO-growth reproduction was run.

## Solution Assessment

Unclear. Moving away from Baileys multi-file auth is supported by current source and upstream guidance, but the exact database shape should be decided against OpenClaw's SQLite, plugin-owned migration, doctor, and security requirements.

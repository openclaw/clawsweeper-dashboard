## Summary

Keep open: current main and v2026.6.11 still recover only serialized plain-text tool calls with arguments, while the reported bare marker remains text. Adjacent fixes for XML dialects and code-mode diagnostics do not own this remaining provider recovery policy gap.

## What This Changes

The issue asks OpenClaw to handle non-Anthropic/provider-compatible models that emit bare plain-text tool markers instead of structured tool calls.

## Best Possible Solution

Define an explicit provider/tool-call recovery policy for bare leaked markers that avoids direct execution without arguments and backs retry, fallback, warning, or forced-tool behavior with live provider proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: How should OpenClaw handle bare leaked tool markers with no arguments from tool-enabled provider routes?

Rationale: The source gap is clear, but the correct behavior is not mechanical because executing a marker without arguments is unsafe and fallback/retry/blocking behavior changes provider compatibility.

Likely owner: vincentkoc

Owner reason: Recent merged work on provider/tool-call compatibility and adjacent fallback diagnostics makes this the strongest routing candidate from current history.

Owner confidence: medium

Options:

- **Retry or fail over without executing bare markers (recommended):** Detect the marker, keep it out of visible replies when appropriate, and retry or fall through only through a maintainer-approved capability policy with live provider proof.
- **Document as unsupported provider behavior:** Keep current execution behavior and improve diagnostics/docs so users know these model routes are not reliable for tool-enabled agents unless forced tool choice works.
- **Parse marker text into tool calls:** Attempting execution from a marker alone would need a new argument-inference policy and carries the highest safety risk.

## Reproduction Assessment

Yes for the source-level gap, not for a live current-main provider replay. The parser, stream wrapper, and tests show that a bare marker without arguments is not promoted, and the attached screenshots show the reported visible marker symptom.

## Solution Assessment

Unclear as a product path: directly executing a bare marker is not the best fix because it lacks arguments. The maintainable direction is an explicit retry, failover, blocking, forced-tool, or diagnostics policy in the existing repair/provider-routing layers.

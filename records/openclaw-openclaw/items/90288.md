## Summary

Keep open: current main and v2026.6.11 still only promote serialized plain-text tool calls that include parseable arguments, so the reported bare `[tool: exec]` marker is not safely recovered. Later related work covers adjacent QuickJS fallback errors and XML dialect leaks, but not this provider/runtime policy gap.

## What This Changes

The issue reports non-Anthropic or compatibility-layer models emitting plain-text tool-call markers instead of structured tool calls.

## Best Possible Solution

Keep this issue open until maintainers choose an explicit recovery policy for bare leaked tool markers, backed by live provider proof and focused regression coverage in the parser/stream-normalizer path.

## Reproduction Assessment

Yes for the source-level gap, not for a fresh live MiniMax/DeepSeek replay in this read-only review. Current main and v2026.6.11 still require a JSON/XML-ish payload after a bracket marker, so a bare marker cannot become an executable tool call.

## Solution Assessment

Unclear: executing a bare marker directly is not a safe complete fix because it has no arguments. The maintainable solution needs a maintainer-chosen policy such as retry, fallback, blocking, forced-tool guidance, or diagnostics rather than an unconditional parser shortcut.

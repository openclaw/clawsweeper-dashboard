## Summary

Keep open: current main still only repairs serialized tool-call text when it has parseable arguments, while the reported bare marker shape has no safe executable payload. The related XML and code-mode reports overlap, but they do not own this provider/runtime policy gap.

## What This Changes

The issue asks OpenClaw to recover, hide, retry, or otherwise handle non-native models that emit bare tool-call markers as assistant text instead of structured toolCall blocks.

## Best Possible Solution

Keep this issue open until maintainers choose and test an explicit provider/runtime policy for bare, argument-free tool markers; do not execute them as tools without arguments.

Options:

- **Detect and fail over or warn without execution (recommended):** Treat bare markers as tool-call incompatibility, keep them out of user-visible replies where feasible, and either retry/fall through or surface a clear provider-capability warning without inventing tool arguments.
- **Tune model/provider formatting first:** Document or configure forced tool-choice and reduced tool surfaces for affected models before adding automatic runtime recovery.
- **Promote only complete textual calls:** Keep current strict promotion semantics and only execute textual tool calls that include parseable arguments, leaving bare markers as diagnostics.

## Solution Assessment

Unclear: directly executing a bare marker is not the best fix because it lacks arguments. The safer direction is diagnostics plus a maintainer-chosen retry, failover, warning, forced-tool, or model-guidance policy.

## Summary

Keep open: current main and v2026.6.11 still only promote parseable serialized tool-call text with arguments, while the reported bare `[tool: exec]` marker is not safely recovered and related PRs cover different XML/code-mode variants.

## What This Changes

The issue asks OpenClaw to handle non-native providers that emit bare tool-call markers like `[tool: exec]` as visible text instead of structured tool calls.

## Best Possible Solution

Choose an explicit provider/runtime recovery policy for bare no-argument tool markers, never execute the marker directly, and back the chosen warning, retry, fallback, or block behavior with live provider proof plus focused regression tests.

Options:

- **Warn and recover without executing (recommended):** Detect bare markers, surface a clear diagnostic, then retry or fall back only under a maintainer-approved tool-capable policy; do not synthesize arguments.
- **Sanitize only:** Hide or warn on the marker and leave the user to retry, which avoids unsafe execution but keeps some sessions stuck.
- **Provider-specific opt-in:** Require affected providers or models to opt into special prompting/tool-choice behavior after live proof, leaving default behavior unchanged.

## Reproduction Assessment

Yes for the source-level gap, not for an independently replayed live provider failure. Current main still does not promote or diagnose the exact bare `[tool: exec]` marker shape without arguments.

## Solution Assessment

Unclear: executing a bare marker is not the best fix because it has no arguments. The maintainable direction is an explicit warning, retry, fallback, forced-tool, or provider-guidance policy chosen by maintainers.

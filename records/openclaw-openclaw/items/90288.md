## Summary

Keep open: current main and the latest stable release recover serialized plain-text tool calls only when arguments or parameter payloads are present; the reported bare `[tool: exec]` marker still has no safe executable payload and needs an explicit provider/runtime recovery policy.

## What This Changes

The issue reports non-Anthropic and compatibility-layer model routes emitting plain-text tool-call markers instead of structured tool-call blocks, leaving tool turns unexecuted and sessions stuck-looking.

## Best Possible Solution

Treat bare allowed-tool markers as a provider/tool-capability failure: surface a clear warning or fallback/retry path, while keeping executable promotion limited to text calls with explicit arguments.

Question: What should OpenClaw do when a configured provider emits only a bare allowed-tool marker such as `[tool: exec]` with no arguments and no structured tool call?

Rationale: The source gap is clear, but the safe behavior is a product/runtime policy choice because direct execution lacks arguments and fallback, retry, warning, or model restriction each affects provider compatibility differently.

Likely owner: steipete

Owner reason: The decision sits at the provider stream SDK/runtime boundary where recent ownership history is strongest.

Owner confidence: medium

Options:

- **Warn or fail over without executing (recommended):** Classify the bare marker as tool-capability failure, notify or fall through to a tool-capable model, and execute only repaired calls with explicit arguments.
- **Retry with stricter tool guidance:** Retry the turn once with provider-specific guidance or forced tool choice, accepting extra latency and possible repeated failure for weaker compatibility routes.
- **Promote bare markers to empty calls:** Convert known markers into zero-argument tool calls, which may unblock some tools but risks unsafe or misleading execution for tools that require arguments.

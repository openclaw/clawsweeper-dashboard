## Summary

Keep open: current main repairs payload-bearing serialized tool-call text and logs diagnostics for tool-shaped text, but a bare `[tool: exec]` marker still has no arguments to safely promote into a tool call. The related XML and fallback reports overlap, but they do not replace this provider/runtime policy decision.

## What This Changes

Detect and recover when non-native provider routes emit bare tool-call markers as assistant text instead of structured tool-call blocks.

## Best Possible Solution

Add a maintainer-approved guard for registered bare tool markers that retries, falls through to a tool-capable model, or shows a clear warning, while keeping executable promotion limited to payload-bearing tool calls.

Rationale: The source gap is clear, but the safe behavior is product policy because execution is impossible without arguments and fallback/blocking changes provider compatibility.

Options:

- **Retry or fallback with warning (recommended):** Detect bare registered-tool markers, avoid executing them, and route to retry/fallback or a clear user/operator warning for tool-dependent turns.
- **Document as unsupported:** Keep the current parser boundary and document affected models as manual-only or tools-disabled when they emit bare markers.
- **Attempt text-to-tool recovery:** Try a model-driven repair step to obtain arguments, accepting extra complexity and a higher safety review bar.

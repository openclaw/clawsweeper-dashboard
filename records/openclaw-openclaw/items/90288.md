## Summary

Keep open: current main and v2026.6.11 still only promote parseable plain-text tool-call payloads, while the reported bare marker-only output such as `[tool: exec]` has no executable arguments and is not safely recovered.

## What This Changes

The issue requests detection and recovery for non-native provider outputs like `[tool: exec]` that appear as visible assistant text instead of structured tool-use blocks.

## Best Possible Solution

Choose and implement a conservative no-argument marker policy with live provider proof; do not execute marker-only text as a tool call.

Rationale: Current source can safely recover serialized payloads, but marker-only output lacks executable arguments and the alternatives change provider/runtime fallback policy.

Options:

- **Warn and recover conservatively (recommended):** Detect marker-only output, keep it out of user-visible replies where possible, and retry or fall back to a known tool-capable model without executing missing arguments.
- **Treat affected routes as unsupported:** Warn or block MiniMax/DeepSeek-style routes for tool-enabled agents until they pass a real structured tool-call capability check.
- **Parse marker-only text as intent:** Attempt to convert bare markers into tool intent, accepting the risk that missing arguments require additional prompting or model-specific behavior.

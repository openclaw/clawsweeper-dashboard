## Summary

Keep open: current main repairs complete serialized tool-call text with arguments, but the reported bare `[tool: exec]` marker without executable arguments is still not safely recovered and needs a maintainer policy decision.

## What This Changes

The issue asks OpenClaw to handle non-native provider responses that emit tool intent as visible text like `[tool: exec]` instead of structured tool-use blocks.

## Best Possible Solution

Define a provider/runtime policy for no-argument tool-intent markers: do not synthesize an `exec` call from text alone; detect the failed tool intent and either retry, fall through to a known tool-capable model, or surface a clear user/operator warning with focused regression coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: How should OpenClaw handle a non-native provider response that contains only a bare tool marker such as `[tool: exec]` with no arguments or structured tool call?

Rationale: Executing a synthesized tool call is unsafe without arguments, while retry, fallback, blocking, or warning behavior all change provider/runtime compatibility policy.

Likely owner: steipete

Owner reason: Recent provider-stream policy and runtime refactor history makes this the best available owner for the product-direction choice.

Owner confidence: medium

Options:

- **Fallback or block safely (recommended):** Detect the bare marker as failed tool intent, avoid executing fabricated arguments, and fall back or warn/block when a tool-capable model is required.
- **Retry same provider:** Retry once with stronger tool-call instructions or forced tool choice, accepting that weak providers may repeat the stall.
- **Document as unsupported:** Keep promoting only complete serialized calls and document that bare markers from incompatible providers are not recoverable.

## Reproduction Assessment

We have a source-reproducible gap, not a fresh live provider replay: current parsers require parseable serialized payloads with arguments, while the reported bare marker has no executable arguments. The external MiniMax/DeepSeek behavior still needs live confirmation on current main before a final fix shape is chosen.

## Solution Assessment

Unclear: complete serialized text-to-tool promotion is already implemented, but recovering a bare marker is not the same fix. The safer direction is a maintainer-approved retry/fallback/block policy rather than parsing `[tool: exec]` into an executable call.

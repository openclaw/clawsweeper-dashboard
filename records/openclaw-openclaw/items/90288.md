## Label Justifications

- `P1`: The report describes a broken tool-enabled agent workflow where real provider/model turns show a marker to the user and then stop without executing the requested tool.
- `impact:session-state`: The failed turn leaves the session appearing stuck after the assistant emits only a malformed tool marker.
- `impact:message-loss`: The intended tool action is silently not delivered as a tool call, leaving the user with a misleading assistant message instead.
- `impact:auth-provider`: The issue is tied to provider/model routing and compatibility layers for non-native tool-call models.

## Summary

Keep open: current main and the latest release have partial plain-text tool-call repair, but the reported bare marker shape still lacks a safe recovery path and needs a maintainer policy decision.

## What This Changes

The issue asks OpenClaw to recover when non-native tool-call providers emit bare text such as `[tool: exec]` instead of structured `tool_use` or `toolCall` blocks.

## Best Possible Solution

Add a generic bare-marker failure policy that prevents the marker from being shown as a normal assistant reply and routes the turn through an explicitly chosen retry, fallback, warning, or block path.

## Maintainer Decision

Required: true

Kind: product_direction

Question: How should OpenClaw handle a bare model-emitted tool marker such as `[tool: exec]` when no arguments or structured tool call are present?

Rationale: The source can identify the bad shape, but execution cannot be safely reconstructed without deciding runtime policy for retry, fallback, user-visible warning, or provider blocking.

Likely owner: steipete

Owner reason: steipete merged the current tool-call repair wrapper work and is the best available owner for the provider/runtime policy choice.

Owner confidence: medium

Options:

- **Detect and recover without execution (recommended):** Treat bare markers as malformed tool intent, suppress the raw marker, and retry or fall through to a tool-capable model with a clear diagnostic.
- **Warn and stop the turn:** Hide the raw marker and tell the user/operator that the selected model cannot produce a valid tool call for this request.
- **Document as unsupported:** Keep current runtime behavior and document affected non-native providers as unreliable for tool-enabled agents.

## Reproduction Assessment

Yes, source-reproducible with medium confidence: current main requires JSON or parameter payloads after `[tool:name]`, so the reported bare marker has no promotion path. I did not run a live MiniMax/DeepSeek provider repro in this read-only review.

## Solution Assessment

No current solution is complete: existing repair only handles parseable serialized calls with arguments. The best fix is a maintainer-chosen malformed-tool-intent policy, not blind text-to-tool execution.

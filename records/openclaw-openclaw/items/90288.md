## Label Justifications

- `P1`: Tool-capable provider routes can leave real user agent turns stuck with visible tool markers and no executed tool result.
- `impact:session-state`: The transcript can record assistant text implying tool intent while the session/tool ledger has no matching structured invocation.
- `impact:message-loss`: The intended tool-backed response can be replaced by a marker or malformed tool text with no actual tool output.
- `impact:auth-provider`: The failure is tied to provider/model tool-call compatibility on Anthropic Messages and OpenAI-compatible routes.

## Summary

Keep open: current main and v2026.6.11 still only promote serialized plain-text tool calls when arguments are present, while the reported bare `[tool: exec]` marker has no executable payload and can still pass through as text. The related code-mode and XML-dialect items overlap the same compatibility area but do not close this bare-marker provider policy gap.

## What This Changes

The issue asks OpenClaw to recover or warn when non-native provider models emit bare plain-text tool markers such as `[tool: exec]` instead of structured `toolCall`/`tool_use` content.

## Best Possible Solution

Define a maintainer-approved recovery policy for bare leaked tool markers, avoid executing markers without arguments, and back the chosen retry/fallback/warn/block behavior with live provider proof plus focused regression coverage.

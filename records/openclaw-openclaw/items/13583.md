## Summary

Keep open. Current main still has adjacent pre-tool blocking, response revision, message cancellation, and HTTP client-tool enforcement, but it does not provide the requested fail-closed response gate with mandatory-tool accounting, typed validators, two-phase planning, fallback/retry semantics, and audit records.

## What This Changes

Request a core/plugin pre-response enforcement layer that mechanically blocks final output until mandatory tool calls or policy validators have run and passed.

## Best Possible Solution

Keep this as the canonical response-gate policy-as-code design item, with a versioned core/plugin API for mandatory-tool ledgers, typed validators, fail-closed final-response gating, bounded retry/fallback behavior, and audit records while domain policy packs live in plugins or ClawHub packages.

## Reproduction Assessment

Not applicable as a narrow bug repro, but source inspection gives high-confidence proof of the missing response-gate contract in current main. The existing hooks can revise, cancel, or block adjacent paths without providing a general mandatory-tool/validator/fail-closed final-delivery contract.

## Solution Assessment

Yes for keeping the item open as a design/API request; the current implementation does not already solve it. The best implementation path needs maintainer product/security review because the permanent boundary must define plugin trust, validator failures, audit retention, exact-payload approval, retries, and fallback behavior.

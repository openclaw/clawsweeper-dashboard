## Summary

Keep open: current main and v2026.6.11 still provide adjacent pre-tool blocking, final-answer revision, reply-dispatch, and message-cancel hooks, but not the requested fail-closed response gate with mandatory tool-call accounting, typed validators, two-phase planning, fallback semantics, and audit records.

## What This Changes

The issue requests a core/plugin pre-response enforcement layer that blocks final output until required tool calls and policy validators have run and passed.

## Best Possible Solution

Keep this as the canonical design item for a versioned core/plugin response-gate API, with domain-specific policy packs implemented as plugins or ClawHub packages once the runtime seam exists.

Question: Should OpenClaw add a versioned core/plugin response-gate API that can fail closed before final response or public-action delivery, and what validator/tool-accounting/audit semantics should be in the first supported contract?

Rationale: The remaining work changes a security boundary and product contract across final response delivery, plugin APIs, config/defaults, retry/fallback behavior, and audit logs; automation cannot choose those semantics safely.

Likely owner: vincentkoc

Owner reason: vincentkoc introduced the closest current finalization hook and has the strongest feature-history link to the plugin API surface that would need extension.

Owner confidence: high

Options:

- **Design response-gate API first (recommended):** Approve a focused design pass for mandatory tool-call accounting, typed response validators, fail-closed fallback modes, bounded retries, and audit records before any implementation PR.
- **Limit to existing plugin hooks:** Keep domain policies in current plugins and document that OpenClaw does not yet provide a hard final-response gate, leaving this issue open or deferring it explicitly.
- **Split narrower security items:** Move public-action approval and outbound pre-send enforcement to narrower issues while keeping this issue as the umbrella response-gate contract discussion.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 show adjacent hooks but no responseGate, mandatory-tool ledger, typed validator contract, or fail-closed final-response boundary. I did not run a live agent scenario because this read-only review only needed source and release inspection to verify the missing contract.

## Solution Assessment

Unclear as an implementation, but the requested direction is valid: a hard response gate belongs in a versioned core/plugin runtime seam, while domain-specific policies should remain in plugins or ClawHub packages. A small message-cancel or finalization-hook patch would not be the best solution because it would miss mandatory-tool accounting and audit semantics.

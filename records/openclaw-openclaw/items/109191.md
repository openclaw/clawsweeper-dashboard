## Label Justifications

- `P1`: The reported cap substitution causes active session eviction, deterministic cron failures, and dropped inbound messages on busy released installations.
- `impact:session-state`: Write-time maintenance can evict newly created or active session entries because it applies the wrong configured capacity.
- `impact:message-loss`: The report includes silently dropped inbound messages when their session entry is evicted during a turn.
- `impact:data-loss`: Session entries are removed under an unintended 500-entry cap despite the operator configuring a larger retention limit.

## Summary

Keep open: the released behavior has detailed production evidence, and current main still retains a default-to-500 path when write-time maintenance is not given the resolved configuration; the available source does not prove every gateway write and hot reload now supplies that value.

## What This Changes

Ensure session-store write-path maintenance honors the validated and hot-reloaded `session.maintenance.maxEntries` value instead of silently applying the built-in cap of 500.

## Best Possible Solution

Resolve the maintenance policy once at the gateway/config owner boundary, pass that validated snapshot through every session-store write, update it on config reload, and make production cap enforcement require an explicit resolved `maxEntries` rather than silently consulting an input-free default.

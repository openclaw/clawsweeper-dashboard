## Best Possible Solution

Estimate the mid-turn precheck against the same provider-boundary prompt history that will actually be sent, including per-result and aggregate tool-result projection, with regression coverage for the reported 250k-char tool-result and 16k aggregate-cap shape.

## Repair Work Prompt

Fix https://github.com/openclaw/openclaw/issues/101929 by making `context-overflow-midturn-precheck` estimate the same provider-boundary prompt history that will be sent to the model. In particular, do not estimate mid-turn tool-result pressure over full unprojected tool-result text when the provider stream transform will apply `truncateOversizedToolResultsInMessages` with the live per-result and aggregate caps. Keep the fix inside the agent runtime/precheck boundary; do not add config knobs or weaken unrelated overflow safety. Coordinate with related context-engine/precheck and aggregate-recovery work, and add regression coverage for a tool-loop history with roughly 250k chars of tool results, `toolResultMaxChars: 16000`, a 200k context window, and a 50k reserve where the post-projection prompt should not choose `truncate_tool_results_only` purely from the unprojected transcript. Preserve the existing retry/recovery behavior when the projected prompt truly exceeds budget.

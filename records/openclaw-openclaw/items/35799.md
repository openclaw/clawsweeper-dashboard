## Summary

Keep open. Current main covers stable heartbeat phase spreading, but cron `every` remains an anchored fixed-interval schedule with no phase, stagger, or prime cadence contract, so the unresolved part needs maintainer product/API direction.

## What This Changes

The issue requests prime-derived cadence and deterministic per-agent phase jitter for heartbeat and cron every-style schedules to reduce synchronized provider load spikes.

## Best Possible Solution

Keep the shipped heartbeat phase spreading, then have maintainers choose one canonical cron `every` phase/stagger/prime contract with schema, CLI, persistence, docs, and upgrade tests before implementation.

Options:

- **Add Opt-In Every Phase (recommended):** Preserve current exact `every` behavior by default, add one explicit phase/stagger option with persistence, CLI/docs, and upgrade tests.
- **Make Every Phase Default:** Spread load automatically for every jobs, but accept an upgrade-visible schedule timing change that needs stronger migration and release communication.
- **Document Existing Paths Only:** Leave cron `every` exact, keep top-of-hour stagger on cron expressions, and document heartbeat phase plus cron-expression stagger as the supported anti-herd paths.

## Reproduction Assessment

Yes, source-level. Current main shows heartbeat phase spreading exists, while cron `every` only supports `everyMs`/`anchorMs` and normalization explicitly removes `staggerMs` from every schedules.

## Solution Assessment

Unclear until maintainers choose the product contract. Prime cadence and new phase knobs are plausible, but a smaller opt-in cron `every` phase/stagger contract or preserving exact interval semantics may be the more maintainable solution.

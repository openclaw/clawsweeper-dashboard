## Summary

Keep open. Current main and the latest release already cover stable heartbeat phase spreading and cron-expression top-of-hour staggering, but the requested prime cadence and public cron `every` phase/jitter contract remain missing and need a scheduler/config product decision.

## What This Changes

Request add prime-derived heartbeat and cron `every` cadence controls plus deterministic per-agent phase jitter to reduce synchronized scheduling bursts.

## Best Possible Solution

Define one compatibility-preserving scheduler contract that reuses the existing deterministic phase/stagger machinery across heartbeat and cron `every`, adding prime cadence only if maintainers explicitly choose that public behavior.

Options:

- **Define unified scheduler contract (recommended):** Add one documented, compatibility-preserving phase/stagger model for heartbeat and cron `every`, with schema, CLI, docs, status/readback, and tests.
- **Limit to cron every stagger:** Extend the existing cron `staggerMs` concept to `every` schedules while leaving heartbeat on its current private stable phase behavior.
- **Decline new timing knobs:** Keep current fixed-interval semantics plus existing heartbeat phase and cron-expression staggering, and close only after maintainers state prime/phase controls are out of scope.

## Reproduction Assessment

Yes for the source-level feature gap, not as a failing bug: current main still exposes heartbeat as one `every` duration and cron `every` as fixed `everyMs`/`anchorMs`, while the requested public prime and phase-jitter controls are absent.

## Solution Assessment

Unclear as a final implementation shape: extending existing deterministic phase/stagger behavior looks more maintainable than separate prime-only fields, but maintainers need to choose the public contract and defaults first.

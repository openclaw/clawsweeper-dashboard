## Summary

Keep open. Current main covers stable heartbeat phase spreading and active-hours phase seeking, and cron-expression top-of-hour staggering exists, but cron `every` remains a fixed anchored interval with no prime, phase, or jitter public contract; the remaining request needs maintainer product/API direction rather than cleanup closure.

## What This Changes

Request to add prime-derived cadence and deterministic phase jitter controls for heartbeat and cron `every` schedules to reduce synchronized load spikes.

## Best Possible Solution

Keep the shipped heartbeat phase spreading and cron-expression stagger, then design one canonical opt-in contract for cron `every` phase/stagger or explicitly decide to keep `every` fixed.

Options:

- **Design narrow cron every phase/stagger contract (recommended):** Add one explicit interval scheduling contract with schema, CLI, docs, persistence, and upgrade tests before implementation.
- **Keep every fixed:** Preserve current fixed anchored `every` semantics and rely on heartbeat phase plus cron-expression stagger for anti-herd behavior.
- **Adopt broader prime mode:** Accept a larger product surface covering prime cadence transforms and deterministic phase controls for both heartbeat and cron, with migration and observability requirements.

## Reproduction Assessment

Yes, source-level. Current main shows heartbeat phase spreading exists, while cron `every` only supports `everyMs`/`anchorMs` and docs limit stagger controls to cron-expression schedules.

## Solution Assessment

Unclear until maintainers choose the product contract. Prime cadence and new phase knobs are plausible, but a smaller cron `every` phase/stagger contract or preserving fixed `every` semantics may be more maintainable.

## Summary

Keep open. Current main and the latest release already ship stable per-agent heartbeat phase scheduling, but cron `every` schedules still use fixed `everyMs`/`anchorMs` semantics with no prime, phase, or stagger contract, and the discussion shows a real operator need for a maintainer-owned scheduling API decision.

## What This Changes

The issue requests prime or prime-derived cadence modes plus deterministic per-agent phase jitter for heartbeat and cron `every` schedules to reduce synchronized traffic spikes.

## Best Possible Solution

Keep the shipped heartbeat phase spreading, then choose one canonical cron `every` phase/stagger/prime contract with schema, CLI/API, persistence, docs, upgrade behavior, and focused scheduling tests before implementation.

## Reproduction Assessment

Yes for the remaining missing capability: current source shows cron `every` only supports `everyMs`/`anchorMs`, strips `staggerMs`, and computes fixed interval slots. The heartbeat phase portion is already implemented and shipped.

## Solution Assessment

Unclear until maintainers choose the product contract. Prime cadence and phase jitter are plausible, but the narrower maintainable answer may be a cron `every` stagger/phase contract without additional heartbeat config knobs.

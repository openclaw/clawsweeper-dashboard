## Summary

This remains a useful, bounded fix for a real Control UI availability failure. The branch appears functionally sound and has strong browser before/after proof, but the fixed 30-second provider-startup deadline intentionally trades an indefinite stall for failure of unusually slow successful Google Live setup; that user-visible availability policy still needs a Control UI owner’s approval before merge.

Likely related people: VACInc and BunsDev were explicitly brought into this PR’s discussion by the review workflow, but the available read-only evidence does not establish feature-history ownership with high confidence.

## What This Changes

The PR makes Google Live Realtime Talk fail and release browser media after 30 seconds without Google protocol readiness, with regression coverage for stalled sockets, stale events, and video cleanup.

## System Context

Realtime Talk is the Control UI’s browser voice/video session layer. The Google Live transport creates microphone and optional camera streams, opens a provider WebSocket, waits for Google’s setup completion message, and then reports the session state back to the chat interface.

## Architecture Diagram

flowchart LR
  User[Control UI user] --> Session[Realtime Talk session]
  Session --> Media[Microphone and camera streams]
  Session --> Socket[Google Live WebSocket]
  Socket --> Setup[Google setup completion]
  Setup --> Ready[Listening session]
  Socket --> Deadline[30-second startup deadline]
  Deadline --> Cleanup[Stop socket and release media]
  Cleanup --> Error[Visible connection error]

## Best Possible Solution

Keep the provider-specific readiness deadline and cleanup design, then have the Control UI owner explicitly accept or adjust the 30-second startup policy after confirming that the healthy setup-completion path remains the intended contract.

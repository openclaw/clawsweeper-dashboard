## Summary

Current main has substantial adjacent safeguards, but the requested capability-grant layer remains missing. Open manifest and descriptor proposals cover narrower metadata phases rather than replacing the broader authorization, enforcement, and audit work, so this security-design item is still necessary.

## What This Changes

Add manifest-declared sensitive capabilities, explicit operator grants and revocations, default-deny filtering, execution-boundary authorization, and durable audit records for skills and tools.

## Best Possible Solution

Adopt a phased, plugin-agnostic contract: stabilize a small capability vocabulary and manifest descriptors, store explicit grants and revocations in canonical SQLite state with CLI/UI/doctor visibility, filter after existing tool-policy resolution, recheck the same authorization decision at every invocation boundary, persist redacted audit decisions, and leave contextual trust scoring or time-based governance to plugins.

Options:

- **Sponsor phased core contract (recommended):** Approve manifest descriptors followed by persisted grants, pre-exposure filtering, execution-boundary checks, and SQLite auditing, while keeping contextual governance plugin-owned.
- **Limit scope to visibility:** Make the inspect-only capability-manifest RFC canonical and defer grants and runtime enforcement until the trust and compatibility model is separately approved.
- **Retain current trust model:** Keep name-based policy, sandboxing, approvals, and blocking hooks as the supported boundary and document governance plugins as optional defense in depth.

## Reproduction Assessment

Yes at source level: current main exposes name/profile policies, sandbox controls, approvals, install scanning, and blocking hooks, while its documented skill and plugin contracts still lack declared sensitive capabilities and canonical operator grants. This is a verifiable architectural gap rather than a failing runtime scenario.

## Solution Assessment

Yes as a direction, but not as one large implementation change. The narrowest maintainable path is the phased contract described in the discussion, with one canonical authorization decision reused for model exposure and every execution surface; a hook-only or single broad PR would be incomplete.

## Risks / Open Questions

- A prematurely stabilized capability vocabulary could become a difficult-to-change public plugin and skill compatibility contract.
- Unconditional default denial could break existing installations unless fresh-install defaults, upgrade behavior, missing-manifest handling, and doctor remediation are explicitly designed.
- Pre-model filtering alone would be bypassable through HTTP, MCP, plugin, or other non-model invocation paths unless authorization is repeated at every execution boundary.
- Grant and audit state need a defined SQLite owner, retention policy, redaction rules, and separation from dynamic governance-hook decisions.
- The existing trusted-plugin model makes it unsafe to advertise capabilities as strong isolation until maintainers define the precise security guarantee.

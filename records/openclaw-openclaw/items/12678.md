## Summary

Keep open: current main and the latest release still provide adjacent name/profile tool policies, plugin hooks, skill metadata, and an HTTP deny list, but not the requested host-enforced capability manifest, grant/revocation state, default-deny high-risk filtering before tool exposure, cross-surface execution checks, or durable audit records.

## What This Changes

Request a capability-based permission model for skills/tools with manifest declarations, explicit grants and revocations, default-deny high-risk actions, and audit logs.

## Best Possible Solution

Keep this as the canonical core/plugin-API security-hardening umbrella and split implementation into maintainer-approved phases: schema/parser, grant state, pre-model filtering, execution-boundary checks, and durable audit, coordinated with narrower RFCs.

## Reproduction Assessment

Yes. Source inspection on current main and v2026.6.11 shows adjacent name/profile policies, hooks, and HTTP deny lists but no manifest-declared capability grants or default-deny enforcement model.

## Solution Assessment

Unclear as a final implementation. The direction is aligned, but maintainers need to decide taxonomy, grant persistence, upgrade behavior, and how static grants compose with dynamic hooks.

## Summary

Keep open: current main has adjacent name/profile tool policy, Gateway HTTP deny lists, before_tool_call/trusted-policy hooks, and the scoped conversation capability profile foundation, but it still lacks manifest-declared sensitive capabilities, explicit grants and revocations, pre-model default-deny filtering, cross-surface execution checks, and durable high-risk capability audit records.

## What This Changes

The issue requests capability-based, default-deny permissions for skills and tools, including manifests, grants/revocations, enforcement, and audit records.

## Best Possible Solution

Keep this as the core/plugin-API security design umbrella, align the narrower skill-manifest, tool-descriptor, MCP-consent, and audit-only slices under one approved vocabulary, then land schema, grant state, filtering, execution checks, and durable audit in separate PRs.

## Reproduction Assessment

Yes, source-reproducible: current main exposes name/profile tool policy, Gateway HTTP deny lists, hook-time governance, and skill/plugin metadata, but no first-class sensitive capability declaration plus grant/revoke enforcement model.

## Solution Assessment

No automated fix yet; the direction is aligned, but maintainers still need to decide the capability taxonomy, grant persistence, default-deny upgrade behavior, execution-boundary checks, and durable audit semantics.

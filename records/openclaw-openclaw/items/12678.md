## Summary

Keep open: current main and v2026.6.11 still have adjacent name/profile tool policy, before_tool_call hooks, skill metadata, and Gateway HTTP deny lists, but not the requested manifest-declared capabilities, explicit grants/revocations, pre-model default-deny filtering, cross-surface execution checks, or durable high-risk capability audit records.

## What This Changes

The issue requests a capability-based permission model for skills/tools with declared capabilities, explicit operator grants, default-deny high-risk actions, consent/revocation UX, and audit logging.

## Best Possible Solution

Keep this as the canonical core/plugin-API security-hardening umbrella and split implementation into maintainer-approved phases for schema, grants, filtering, execution checks, and durable audit records.

## Reproduction Assessment

Yes. This is source-reproducible as a feature gap: current main and v2026.6.11 expose name/profile tool policy, generic hooks, skill metadata, and surface deny lists, but no capability manifest plus grant/revoke enforcement model.

## Solution Assessment

Unclear as a final implementation path. The direction fits the security gap, but maintainers still need to decide taxonomy, grant persistence, upgrade/default-deny behavior, and how static grants compose with dynamic policy hooks.

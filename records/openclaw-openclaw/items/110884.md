## Label Justifications

- `P1`: A stale browser target can route a subsequent mutating operation to different page content after identity reuse.
- `merge-risk: 🚨 compatibility`: The PR changes the extension-relay’s externally visible CDP target-id contract from raw renderer IDs to public relay IDs.

## Summary

The PR fixes the wrong-tab inference, but its new relay target handle is reusable after a relay restart or Chrome tab-id reuse, so an old handle can identify different content. Keep this PR open for a bounded relay identity repair and a real paired-extension proof.

## What This Changes

The branch replaces route-level post-action tab-list inference with backend-reported target outcomes and changes extension-relay CDP target IDs to stable tab-derived public handles.

## Best Possible Solution

Allocate an opaque per-bridge target handle when a shared tab enters the relay, retain it only through that tab’s detach/reattach lifecycle, retire it on group removal or bridge restart, and prove the result through a live paired Chrome extension scenario.

Yes in source: `relayPublicTargetId` derives identity only from a reusable numeric tab ID, while the canonical contract requires stale handles to remain invalid after tab removal, reuse, or relay restart. The production paired-extension path has not been shown after this change.

## Solution Assessment

No. Backend-owned operation outcomes are the right replacement for route inference, but the relay handle must be allocated per relay/tab lifetime rather than reconstructed from Chrome's reusable tab ID.

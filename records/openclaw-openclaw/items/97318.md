- `P2`: This affects scheduled exec/cron workflows with real delivery impact, but it is not a crash loop, security bypass, or first-run blocker.
- `impact:message-loss`: The reported cron workflow can suppress the intended Slack alert when stdout from a semantic nonzero exit is promoted to tool failure.
- `impact:session-state`: The same completed exec result can be recorded in agent and cron state as a failed tool result.

## Summary

Keep open: current main still has the reported split semantics, where the exec runner preserves normal nonzero exits as completed output but the shared tool-result classifier promotes any nonzero `exitCode` to an agent/cron error.

## What This Changes

The issue asks for normal exec subprocess nonzero exits to preserve stdout, stderr, and exit code for agent logic instead of becoming framework-level tool failures.

## Best Possible Solution

Adopt a maintainer-approved semantic boundary where normal completed exec exits return output and exitCode without agent/cron failure state, while spawn errors, denials, timeouts, signals, and shell 126/127 remain failures.

Question: Should completed exec results with nonzero exit codes be nonfatal agent results by default across embedded-agent and isolated cron surfaces?

Rationale: Current code has competing semantics: the exec runtime treats normal nonzero exits as completed, but shared result classification and cron state still treat the same result as a tool failure.

Likely owner: steipete

Owner confidence: medium

Options:

- **Make normal nonzero exits nonfatal (recommended):** Update the shared classifier and cron/embedded-agent tests so completed exec exit codes preserve stdout/stderr and diagnostics without setting tool failure state.
- **Add explicit opt-in semantics:** Keep the current default but add a documented accepted-exit or nonfatal-exit policy surface, accepting extra configuration and upgrade complexity.
- **Keep failure semantics:** Document wrapper-based workarounds and close the behavior as intentional, accepting that semantic-exit cron jobs must force exit 0.

## Reproduction Assessment

Yes, at source level. Current main returns completed exec details for exit 1, but `isToolResultError` still classifies completed nonzero `exitCode` as an error and embedded-agent/cron paths consume that error state.

## Solution Assessment

Unclear pending maintainer direction. The cleanest technical fix is at the shared tool-result classification boundary, but that boundary also drives telemetry and non-exec soft-error semantics.

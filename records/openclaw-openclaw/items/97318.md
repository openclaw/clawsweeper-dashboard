## Summary

Keep open: current main still returns normal nonzero exec exits as completed results but downstream reclassifies any nonzero exitCode as a tool-result error, so the reported cron/message-delivery failure is not fully solved.

## What This Changes

The issue asks OpenClaw to preserve stdout, stderr, and exit-code semantics for completed subprocesses that exit nonzero, especially inside cron agentTurn workflows.

## Best Possible Solution

Choose the exec result contract, then align the shared classifier, cron outcome logic, regression tests, and docs so completed process exits remain observable without masking spawn, timeout, signal, or shell 126/127 failures.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should completed nonzero exec exits be normal agent-observable results by default, or should only explicit accepted exit codes suppress tool-error classification?

Rationale: Current main already treats normal nonzero process exits as completed at the exec runtime layer, but the shared classifier and cron path still treat them as errors; changing that default has compatibility impact for workflows that currently depend on nonzero exits being failures.

Likely owner: steipete

Owner reason: Current history points to steipete as the strongest recent carrier for the shared classifier/runtime files and this choice is a cross-surface product contract decision.

Owner confidence: medium

Options:

- **Default completed-exit semantics (recommended):** Treat ordinary reason=exit subprocess exits as non-tool-failure results by default, preserving stdout/stderr plus exitCode for the agent while keeping spawn, timeout, signal, and shell 126/127 failures on the error path.
- **Opt-in accepted exit codes:** Add an explicit accepted-exit-code policy for workflows that need semantic nonzero exits while preserving current failure behavior by default.
- **Document the wrapper workaround:** Keep current behavior and document the always-exit-zero wrapper pattern, accepting the ongoing cron prompt burden and user confusion.

## Reproduction Assessment

Yes from source inspection: current main returns completed nonzero exec outcomes but still classifies any nonzero exitCode as a tool-result error, and cron treats unrecovered error payloads as fatal. I did not run a live cron job in this read-only review.

## Solution Assessment

Unclear as a product contract: the narrow technical fix is traceable, but maintainers still need to choose default completed-exit semantics versus an explicit accepted-exit-code option.

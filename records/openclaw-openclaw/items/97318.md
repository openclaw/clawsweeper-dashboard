## Summary

Keep open: current main still converts completed exec results with nonzero exit codes into tool-error state downstream, and the latest live issue comment reports the same cron alert-loss pattern on 2026.7.1-beta.1.

## What This Changes

The issue requests that exec subprocess nonzero exits remain observable to agents as normal results with stdout/stderr and exit-code semantics instead of framework-level tool failures.

## Best Possible Solution

Make ordinary exec process exits observable to the agent as completed results with stdout/stderr/exitCode, while preserving hard failures for spawn errors, timeouts, signals, shell 126/127, command cron jobs, and documented security denials.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw make ordinary exec nonzero subprocess exits a normal completed tool result by default, or require an explicit accepted-exit-code/allow-nonzero policy?

Rationale: The code path is narrow, but the behavior is a product/API contract because some existing automations may depend on nonzero exec exits producing tool-error or cron-error state.

Likely owner: Peter Steinberger

Owner reason: Recent history shows ownership around the exec/tool runtime boundary, and the decision spans runtime behavior, cron delivery, and compatibility policy.

Owner confidence: medium

Options:

- **Default completed nonzero exits (recommended):** Treat normal exec exits 0-125 as completed results with exitCode and output, keeping spawn, timeout, signal, denial, and shell 126/127 failures on the error path.
- **Opt-in accepted exit codes:** Preserve current default error classification but add a documented exec option such as acceptedExitCodes or allowNonzeroExit for semantic scripts.
- **Document workaround only:** Keep the current behavior and document the wrapper pattern, accepting that semantic exit-code scripts need extra user logic.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: current main still classifies completed nonzero exec results as tool errors, and the live discussion reports the same cron alert-loss pattern on 2026.7.1-beta.1. I did not run a live cron job in this read-only checkout.

## Solution Assessment

Unclear until maintainers choose the contract: the narrow default fix is to stop treating ordinary completed exec exits as observer errors, but compatibility could justify an opt-in accepted-exit-code path.

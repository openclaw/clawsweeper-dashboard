## Label Justifications

- `P2`: This affects scheduled agent/exec workflows and cron alerts with limited blast radius, but it is not a crash loop, security bypass, or first-run blocker.
- `impact:message-loss`: The reported cron workflow can suppress the intended stdout/report delivery when a semantic nonzero exit is promoted to a tool failure.
- `impact:session-state`: The same misclassification can mark agent/cron tool state and run history as failed even though the exec process completed with output.

## Summary

Keep open: current main preserves normal nonzero exec exits at the lower runner layer, but the shared agent result classifier and embedded-agent/cron consumers still turn completed nonzero exec details into error state.

## What This Changes

The issue asks for exec subprocess nonzero exits to return stdout, stderr, and exitCode as normal agent-visible results instead of framework-level tool failures, especially for isolated cron workflows.

## Best Possible Solution

Treat normal completed exec results with semantic nonzero exit codes as nonfatal agent results through embedded-agent and cron classification, while preserving true tool failures for spawn errors, denials, timeouts, signals, and shell 126/127.

Rationale: Current code has competing semantics: the exec runner preserves nonzero exits as completed output, while shared agent and cron classifiers still promote the same result to error state; choosing the default affects all tool-result consumers.

Options:

- **Make normal exec nonzero nonfatal (recommended):** Update the shared classifier and cron/embedded-agent tests so completed exec exit codes preserve stdout/stderr and diagnostics without setting tool failure state.
- **Add explicit opt-in exit policy:** Keep current defaults but add a documented accepted-exit or nonfatal-exit policy surface, accepting extra configuration and upgrade complexity.
- **Keep failure semantics and document wrappers:** Document wrapper-based workarounds and close the behavior as intentional, accepting that semantic-exit cron jobs must force exit 0.

## Reproduction Assessment

Yes from source, but not from a live run in this read-only review. On origin/main, exec exit 1 returns completed details, while isToolResultError still returns true for completed exitCode 1 and embedded-agent/cron paths consume that error state.

## Solution Assessment

Likely yes for the issue's option A if maintainers choose that product boundary. The lower-layer fix already on main is necessary but insufficient; the remaining maintainable fix belongs at the shared classifier plus focused embedded-agent and cron coverage.

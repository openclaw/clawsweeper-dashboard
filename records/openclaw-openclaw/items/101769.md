## Summary

Keep open: current main and the latest release still accept any leading `---` prefix as a frontmatter fence, so the reported parser edge case remains valid and narrowly fixable.

## What This Changes

Require Markdown frontmatter parsing to treat only a whole `---` delimiter line as a metadata fence, not prefixes such as `---not` or `----`.

## Best Possible Solution

Use one shared whole-line delimiter check for Markdown frontmatter extraction and stripping, then add regression tests for `---not` and `----` while preserving valid `---` blocks and BOM handling.

## Repair Work Prompt

Fix the Markdown frontmatter delimiter bug reported in https://github.com/openclaw/openclaw/issues/101769. Require frontmatter opening and closing fences to be whole delimiter lines after BOM and newline normalization, so inputs beginning with `---not` or `----` are treated as normal Markdown, while valid `---` fenced blocks still parse. Prefer a small shared helper/predicate for the delimiter invariant and update sibling strip/body helpers that currently use the same prefix logic. Add focused regression tests for `parseFrontmatterBlock()` and any touched wrapper/helper behavior. Do not add config flags, compatibility shims, new public API, or unrelated Markdown validation policy.

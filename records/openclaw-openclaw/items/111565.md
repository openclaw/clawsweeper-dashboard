## Label Justifications

- `P1`: The patch addresses a real gateway session-control security boundary but currently regresses a legitimate multi-turn CLI workflow.
- `merge-risk: 🚨 compatibility`: Existing device-less shared-secret CLI and remote-onboarding flows can lose access to their own active system-agent session after a normal per-RPC reconnect.

## Summary

Keep this PR open: it closes the cross-client takeover path, but its connection-ID fallback rejects legitimate device-less shared-secret CLI conversations after their next RPC opens a new WebSocket. The prior P1 remains unresolved, so the security boundary needs a stable owner-contract decision before merge.

## What This Changes

The branch makes system-agent sessions require an owner key derived from explicit delegation, authenticated user, paired device, or gateway connection, and adds focused ownership tests.

## Best Possible Solution

Keep unidentifiable callers connection-bound for security, then make the affected onboarding/CLI conversation reuse one authenticated gateway connection across its system-agent turns; add an integration regression that proves both cross-client rejection and the device-less multi-turn path.

## Reproduction Assessment

Yes, from source: invoke the session once through a device-less loopback token/password CLI call, then send the next turn through its normal new WebSocket connection. The owner falls from the original connection ID to a different one and the session check rejects it.

## Solution Assessment

No. Binding unidentifiable clients to `connId` is a sound fail-closed default, but the PR must preserve the existing multi-turn caller lifecycle by reusing that connection or by using a genuinely server-verifiable per-caller identity.

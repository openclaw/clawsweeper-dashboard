## Summary

Keep open. Current main and v2026.6.11 still run sandbox-browser lifecycle through Docker-only code, while external CDP/noVNC endpoint support remains a real sandbox-browser config/API and security-boundary decision.

## What This Changes

Request support for externally managed CDP/noVNC endpoints so sandbox browser use can work without OpenClaw managing a Docker browser container.

## Best Possible Solution

Define a maintainer-approved sandbox-browser backend or external-endpoint contract that supports externally managed browsers while preserving CDP auth, SSRF policy, noVNC observer access, lifecycle semantics, docs, and focused tests.

## Maintainer Decision

Rationale: The implementation shape controls public config, CDP/noVNC authority, browser lifecycle ownership, and sandbox isolation guarantees, so code inspection cannot safely choose it without maintainer intent.

Owner confidence: high

Options:

- **Design endpoint contract first (recommended):** Define a typed sandbox-browser backend/external-endpoint contract with auth, SSRF, noVNC, lifecycle, docs, and tests before adding public config fields.
- **Add narrow endpoint fields:** This would unblock sidecar/CDP deployments faster but risks locking in an underdesigned security and configuration surface.
- **Fold into browser-backend API work:** This keeps core lean but should explicitly preserve this issue's sandbox-browser lifecycle and noVNC/CDP requirements in the broader design.

## Reproduction Assessment

Yes, at source level: current main still routes sandbox browser setup through Docker lifecycle and has no external CDP/noVNC sandbox-browser config fields. I did not run a live Kubernetes, Docker Compose, or external sidecar deployment in this read-only review.

## Solution Assessment

Unclear as proposed. External endpoint fields are a plausible unblocker, but the best fix needs maintainer agreement on backend ownership, auth, SSRF/noVNC policy, validation, and public config shape before implementation.

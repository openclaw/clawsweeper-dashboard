## Summary

Keep open. Current main and v2026.6.11 still use a Docker-managed sandbox-browser lifecycle, and the requested external CDP/noVNC endpoint support remains a security-sensitive feature/config decision rather than implemented or safely superseded.

## What This Changes

Request support for externally managed sandbox browser CDP/noVNC endpoints so browser automation can run without a Docker-managed browser container.

## Best Possible Solution

Define a maintainer-approved sandbox-browser backend or endpoint contract that supports externally managed browsers while preserving CDP auth, SSRF policy, noVNC observer tokens, lifecycle semantics, docs, and tests; keep browser.profiles.*.cdpUrl as the existing non-sandbox remote-CDP path.

## Reproduction Assessment

Yes, at source level. Current main still routes sandbox browser setup through Docker lifecycle and rejects browser support for non-browser-capable backends; I did not run a live Kubernetes, Docker Compose, or external CDP sidecar deployment in this read-only review.

## Solution Assessment

Unclear as proposed. Optional endpoint fields are a plausible unblocker, but the best fix needs maintainer agreement on backend ownership, auth, SSRF/noVNC policy, and the config/API contract rather than a one-off shortcut.

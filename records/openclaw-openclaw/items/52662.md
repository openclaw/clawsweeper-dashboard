## Summary

Keep open: current main still has a Docker-managed sandbox-browser lifecycle and no sandbox-browser external CDP/noVNC endpoint contract, while existing remote-CDP browser profiles are only a partial workaround through host/browser-profile routing.

## What This Changes

Request support for externally managed browser CDP/noVNC endpoints so sandboxed browser automation can work without requiring OpenClaw to manage a Docker browser container.

## Best Possible Solution

Define a maintainer-approved sandbox-browser external endpoint or backend contract that preserves CDP auth, SSRF policy, noVNC observer access, lifecycle semantics, docs, and focused regression tests, while documenting the existing remote-CDP host-profile workaround separately.

## Reproduction Assessment

Yes, at source level: current main still routes sandbox browser setup through Docker lifecycle, rejects browser-enabled non-browser-capable backends, and lacks sandbox-browser external CDP/noVNC config fields. I did not run a live Kubernetes or Docker Compose sidecar deployment in this read-only review.

## Solution Assessment

Unclear as proposed: external endpoint fields are a plausible unblocker, but the best fix needs maintainer agreement on endpoint ownership, auth, SSRF/noVNC policy, validation, redaction, docs, and whether this belongs under a broader browser-backend API.

## Summary

Keep open. Current main and the latest release still use a Docker-managed sandbox-browser lifecycle, while the requested external CDP/noVNC endpoint support remains a security-sensitive config/API product decision rather than implemented or safely superseded.

## What This Changes

The issue requests external CDP/noVNC endpoint support so sandboxed browser automation can use an externally managed browser instead of requiring the OpenClaw gateway to manage a Docker browser container.

## Best Possible Solution

Define a maintainer-approved sandbox-browser backend or external-endpoint contract that supports externally managed browsers while preserving CDP auth, SSRF policy, noVNC observer access, lifecycle semantics, docs, and focused tests.

## Reproduction Assessment

Yes, at source level for the missing capability: current main still routes sandbox browser setup through Docker lifecycle and has no external CDP/noVNC sandbox-browser config fields. I did not run a live Kubernetes, Docker Compose, or external sidecar deployment in this read-only review.

## Solution Assessment

Unclear as proposed. External endpoint fields are a plausible unblocker, but the best fix needs maintainer agreement on backend ownership, auth, SSRF/noVNC policy, validation, and public config shape before implementation.

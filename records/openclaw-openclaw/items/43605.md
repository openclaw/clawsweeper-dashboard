## Label Justifications

- `P1`: The issue blocks a real distributed-agent workflow for multi-machine users, but it is an advanced deployment feature rather than a first-run release blocker.
- `impact:session-state`: The requested behavior would route messages into sessions owned by another Gateway and must preserve correct session identity, history, and transcript context.
- `impact:security`: Cross-gateway messaging requires a trust model for sender identity, credentials, authorization scopes, injection prevention, and replay handling.

## Summary

Keep open: current main and v2026.6.11 still lack native cross-gateway session-tool routing, while the linked closing PR is open, conflicting, and still depends on a maintainer-approved trust and delivery contract.

## What This Changes

Request native cross-gateway messaging so `sessions_send` and related session tools can target agents on other Gateway instances instead of relying on SSH or external chat bridges.

## Best Possible Solution

Keep this as the concrete cross-gateway session-messaging tracker until maintainers approve the peer trust contract and either land a proven implementation or intentionally defer native core support to documented plugin, MCP, channel, or operator-run bridges.

## Best Possible Solution

Keep #60841 as the canonical tracker until a security-reviewed fix either materializes exact requested tools under deny/sandbox/provider gates or fails pre-dispatch with a non-ok cron result.

## Maintainer Decision

Required: true

Question: Should finite isolated cron `toolsAllow` requests for Codex native-owned shell/file names be materialized as exact OpenClaw dynamic tools, or should those runs fail pre-dispatch when exact exposure cannot be guaranteed?

Rationale: The upstream Codex app-server does not expose a granular per-turn native shell/file allowlist, and OpenClaw's current code intentionally fails closed for narrow native allowlists, so the permanent behavior is a security-boundary choice rather than a mechanical cleanup.

Likely owner: steipete

Owner confidence: medium

Options:

- **Fail closed unless exact exposure is proven (recommended):** Return a deterministic non-ok preflight result such as `TOOL_SURFACE_UNAVAILABLE` whenever a finite allowlist requests shell/file tools that cannot be exactly materialized under current gates.
- **Materialize exact OpenClaw dynamic tools:** Re-add only the requested OpenClaw dynamic `exec/read/write/edit` equivalents when deny, sandbox, provider, and Codex exclusion policy all allow them, with focused regression coverage.
- **Declare finite Codex native allowlists unsupported:** Document that only wildcard or omitted allowlists can use Codex native shell/file tools, but still fix false-green cron status for unavailable required tools.

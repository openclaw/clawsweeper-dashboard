## Summary

Keep open: current main and latest release `v2026.6.11` still use `zh-CN` and `zh-TW` as Control UI and CLI wizard locale contracts. The remaining work is a compatibility-sensitive product decision because it spans saved browser preferences, generated i18n assets, docs publish metadata, and documented wizard locale inputs.

## What This Changes

The issue requests renaming Chinese locale identifiers from `zh-CN`/`zh-TW` to script-based `zh-Hans`/`zh-Hant` across i18n code, generated locale assets, detection, language labels, and saved preference migration.

## Best Possible Solution

Decide the canonical Chinese locale-ID contract first, then migrate Control UI, CLI wizard, docs publish metadata, generated i18n assets, tests, and user-facing docs in one compatibility-aware change if maintainers choose script-based IDs.

## Reproduction Assessment

Yes. Source inspection on current main shows the Control UI locale type/registry, saved-preference validation, CLI wizard locale map, docs, and generated tooling still use `zh-CN` and `zh-TW`.

## Solution Assessment

No, not as a simple rename. The maintainable path is a maintainer-approved locale-ID contract with explicit migration and compatibility handling across UI, wizard, docs publish, and generated i18n artifacts.

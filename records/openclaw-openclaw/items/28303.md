## Summary

Keep open: current main and the latest release still expose `zh-CN` and `zh-TW` as canonical Control UI and CLI wizard locale IDs. The request is coherent, but changing shipped locale identifiers and saved preferences is a product/compatibility decision rather than a safe cleanup close.

## What This Changes

Rename Chinese locale identifiers from `zh-CN`/`zh-TW` to `zh-Hans`/`zh-Hant` across the Control UI, CLI wizard, docs/i18n generation, detection, and saved preference migration.

## Best Possible Solution

Decide the canonical locale-ID policy first, then land one coordinated migration across Control UI, CLI wizard, native/docs i18n generation, public docs, tests, and old saved-value handling.

## Maintainer Decision

Question: Should OpenClaw make `zh-Hans` and `zh-Hant` the canonical Chinese locale IDs across Control UI, CLI wizard, native/docs i18n generation, saved browser preferences, and public docs?

Rationale: The rename is technically reasonable but changes shipped public locale identifiers, documented setup environment values, and persisted browser preferences, so automation should not choose the compatibility policy without maintainer intent.

Likely owner: steipete

Owner reason: steipete has the strongest recent history across onboarding docs, wizard i18n follow-up, and setup policy, which is where the compatibility decision needs to land.

Owner confidence: high

Options:

- **Approve coordinated migration (recommended):** Make `zh-Hans` and `zh-Hant` canonical and require one migration PR that updates runtime, docs, generated artifacts, tests, and old-value handling together.
- **Keep region-code public IDs:** Leave `zh-CN` and `zh-TW` as OpenClaw's public runtime and CLI IDs while accepting script-form inputs only as aliases that resolve to the existing IDs.
- **Split docs from runtime IDs:** Keep runtime and CLI IDs unchanged while limiting script-based naming to docs publish metadata and navigation internals.

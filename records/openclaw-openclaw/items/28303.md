## Summary

Keep open: current main and the latest release still expose `zh-CN` and `zh-TW` as public Control UI and CLI wizard locale contracts. This remains a compatibility-sensitive product decision, not a narrow bug fix, because changing it affects saved browser preferences, generated locale assets, docs publishing metadata, and documented wizard environment values.

## What This Changes

Request to rename Chinese locale identifiers from `zh-CN`/`zh-TW` to `zh-Hans`/`zh-Hant` across the i18n registry, locale files, detection, storage migration, selector labels, and related docs/tooling.

## Best Possible Solution

Adopt one maintainer-approved Chinese locale-ID policy, then migrate the Control UI, CLI wizard, generated i18n assets, docs publish metadata, docs, tests, and saved-preference compatibility together.

## Reproduction Assessment

Yes. Source inspection on current main and `v2026.6.11` shows the Control UI locale registry, saved-preference validation, CLI wizard locale map, docs, and docs-sync tooling still use `zh-CN` and `zh-TW`.

## Solution Assessment

No, not as a simple rename. The maintainable solution is a maintainer-approved locale-ID contract with explicit migration and compatibility handling across UI, wizard, docs publish, and generated i18n artifacts.

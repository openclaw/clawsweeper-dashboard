## Summary

Keep open: current main and the latest release still expose `zh-CN` and `zh-TW` as public locale IDs in Control UI and CLI wizard surfaces. The request is valid cleanup, but it crosses saved browser preferences, documented `OPENCLAW_LOCALE` values, generated i18n tooling, docs publish behavior, and native locale mappings, so it needs a maintainer decision on the canonical locale contract and migration scope.

## What This Changes

The issue requests renaming Chinese locale identifiers from `zh-CN`/`zh-TW` to `zh-Hans`/`zh-Hant` across OpenClaw i18n surfaces, including migration for saved preferences.

## Best Possible Solution

Decide the canonical locale-ID policy first, then land one coordinated migration across Control UI, CLI wizard, docs publish, native locale mappings, generated metadata, tests, and public docs with explicit handling for existing saved and documented old values.

Options:

- **Approve coordinated script-code migration (recommended):** Make `zh-Hans`/`zh-Hant` canonical and require a single migration PR that updates generated artifacts, docs, tests, native mappings, and legacy saved/doc values intentionally.
- **Keep region codes public for now:** Leave `zh-CN`/`zh-TW` as the public OpenClaw locale IDs and optionally document that docs publishing may map them to script-based Mintlify language metadata.
- **Split docs language metadata from runtime IDs:** Keep runtime and CLI IDs unchanged while limiting script-based naming to docs publishing and navigation metadata where Mintlify expects it.

## Summary

Keep open: current main and the latest release still expose `zh-CN` and `zh-TW` as canonical Control UI and CLI wizard locale IDs, while `zh-Hans`/`zh-Hant` are only accepted as inputs that resolve back to the region-based IDs. Renaming shipped identifiers plus saved browser preferences and `OPENCLAW_LOCALE` behavior needs maintainer product direction before a safe implementation can be queued.

## What This Changes

The issue requests renaming Chinese locale identifiers from `zh-CN`/`zh-TW` to script-based `zh-Hans`/`zh-Hant` across Control UI i18n, locale detection, persistence, and selector surfaces.

## Best Possible Solution

Maintainers should first decide the canonical locale-ID policy; if the rename is accepted, implement it as one coordinated migration across the Control UI registry/types/generator, saved browser settings, wizard env locale resolution, docs i18n metadata, and tests, with explicit legacy handling for shipped `zh-CN`/`zh-TW` values.

## Summary

Keep open: current `main` and `v2026.6.11` still expose `zh-CN` and `zh-TW` as public Control UI and CLI wizard locale IDs, and changing them needs a maintainer decision on canonical IDs, aliases, and saved-preference migration.

## What This Changes

Request to rename Chinese i18n locale identifiers from `zh-CN`/`zh-TW` to `zh-Hans`/`zh-Hant` across runtime, docs, tests, and saved preferences.

## Best Possible Solution

Decide the canonical locale-ID policy first, then land one coordinated migration across Control UI, CLI wizard, docs publish metadata, generated i18n artifacts, tests, app mapping scripts, and old saved-value handling.

Question: Should OpenClaw make `zh-Hans` and `zh-Hant` the canonical Chinese locale IDs across Control UI, CLI wizard, docs publishing, saved browser preferences, and app locale mappings?

Rationale: The rename is technically reasonable, but it changes shipped public locale identifiers, documented CLI environment values, and persisted browser preferences, so automation should not choose the migration and alias policy without maintainer intent.

Likely owner: steipete

Owner reason: The decision crosses public setup behavior, docs, and migration policy, and steipete is the strongest available routing owner from related CLI onboarding i18n history.

Owner confidence: medium

Options:

- **Approve coordinated script-code migration (recommended):** Make `zh-Hans` and `zh-Hant` canonical and require one migration PR that updates runtime, docs, generated artifacts, tests, app mappings, and old-value handling together.
- **Keep region-code public IDs:** Leave `zh-CN` and `zh-TW` as OpenClaw's public runtime and CLI IDs while accepting script-form input only as aliases that resolve to the existing IDs.
- **Split docs metadata from runtime IDs:** Keep runtime and CLI IDs unchanged while limiting script-based naming to docs publish metadata and navigation internals.

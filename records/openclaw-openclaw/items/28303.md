## What This Changes

The issue requests renaming Chinese locale identifiers from `zh-CN`/`zh-TW` to `zh-Hans`/`zh-Hant` across UI, detection, stored preferences, and display surfaces.

## Best Possible Solution

Decide the canonical locale-ID policy first, then land one coordinated migration across Control UI, CLI wizard, generated i18n artifacts, public docs, tests, and old saved-value handling.

## Maintainer Decision

Question: Should OpenClaw make `zh-Hans` and `zh-Hant` the canonical Chinese locale IDs across Control UI, CLI wizard, docs publishing, saved browser preferences, and app locale mappings?

Rationale: The rename is technically reasonable, but it changes shipped public locale identifiers, documented CLI environment values, and persisted browser preferences, which automation should not choose without maintainer product intent.

Likely owner: steipete

Owner reason: steipete is the best available owner because the decision crosses CLI setup policy, docs, and the accepted wizard i18n contract he recently carried forward.

Owner confidence: high

Options:

- **Approve coordinated script-code migration (recommended):** Make `zh-Hans` and `zh-Hant` canonical and require one migration PR that updates runtime, docs, generated artifacts, tests, and old-value handling together.
- **Keep region-code public IDs:** Leave `zh-CN` and `zh-TW` as OpenClaw's public runtime and CLI IDs while accepting script-form input only as aliases that resolve to the existing IDs.
- **Split docs metadata from runtime IDs:** Keep runtime and CLI IDs unchanged while limiting script-based naming to docs publish metadata and navigation internals.

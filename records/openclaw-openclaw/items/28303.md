## What This Changes

Request to rename Chinese locale identifiers from `zh-CN`/`zh-TW` to `zh-Hans`/`zh-Hant` across the i18n code, generated locale files, detection logic, saved preferences, docs, and language selector labels.

## Best Possible Solution

Decide the canonical locale-ID policy first, then land one coordinated migration across Control UI, CLI wizard, generated i18n artifacts, docs, tests, and old saved-value handling.

Rationale: The rename is technically reasonable, but it changes shipped public IDs, documented setup inputs, generated artifact names, and persisted browser preferences, so automation should not choose the alias and migration policy without maintainer intent.

Owner confidence: high

Options:

- **Approve coordinated script-code migration (recommended):** Make `zh-Hans` and `zh-Hant` canonical and require one migration PR that updates runtime, docs, generated artifacts, tests, and old-value handling together.
- **Keep region-code public IDs:** Leave `zh-CN` and `zh-TW` as public runtime and CLI IDs while accepting script-form inputs only as aliases that resolve to the existing IDs.
- **Split docs metadata from runtime IDs:** Limit script-based naming to docs or publishing metadata while keeping runtime and CLI locale IDs unchanged.

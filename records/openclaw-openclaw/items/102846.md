## Label Justifications

- `P1`: A named-profile startup path can silently cross a profile isolation boundary and affect real second-gateway or isolated-test users, but the blast radius is bounded to legacy approval state migration.
- `impact:security`: The issue imports exec/plugin trust decisions from the default profile into an otherwise isolated profile.
- `impact:data-loss`: The migration can archive and remove the default profile approval file during a named-profile launch.
- `maturity:stable`: The affected approvals/profile-isolation behavior maps to M4 Stable Gateway runtime and macOS Gateway host scorecard surfaces.

## Summary

Keep open. Current main still treats a profile-derived state root as a bare `OPENCLAW_STATE_DIR` relocation for approval migrations, so a named profile can import/archive default-profile approval state; no merged canonical fix for this specific profile-isolation bug was found.

## What This Changes

Ensure named profiles do not import or archive default-profile exec and plugin-binding approval state while preserving the shipped bare `OPENCLAW_STATE_DIR` migration.

## Best Possible Solution

Add a narrow profile-aware guard so legacy default approval imports, archives, and fail-closed fallback run for explicit state-dir relocation but not for non-default named profiles, with regression tests for both paths.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, from source inspection. `--profile` derives an isolated `OPENCLAW_STATE_DIR`, and the current approval migration/fallback code treats any non-empty state dir as an explicit relocation without checking `OPENCLAW_PROFILE`; I did not run a writable repro during this read-only review.

## Solution Assessment

Yes, the best fix is narrow and owner-local. Keep explicit state-dir relocation migration intact, but make default-root approval migration and fallback profile-aware so named profiles do not inspect, import, or archive default-profile state.

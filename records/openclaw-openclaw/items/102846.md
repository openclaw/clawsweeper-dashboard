## Label Justifications

- `P1`: This is an urgent profile-isolation regression in the latest release path that can silently mutate approval policy state for users running named gateways or tests.
- `impact:data-loss`: The reported path renames the default profile's approval JSON to a migrated archive while launching a separate named profile.
- `impact:security`: Approval trust decisions can be imported across profile boundaries, weakening the expected isolation of exec and plugin approval policy.
- `maturity:stable`: The issue affects M4 stable gateway approvals/profile-isolation surfaces from the maturity shortlist.

## Summary

Keep open: current main and latest v2026.6.11 still treat profile-derived `OPENCLAW_STATE_DIR` like an explicit relocation, so named profile startup can migrate/archive default-profile approval state across the isolation boundary.

## What This Changes

The issue requests that named `--profile` startup skip default-profile approval migrations while preserving the shipped bare `OPENCLAW_STATE_DIR` migration.

## Best Possible Solution

Add a profile-aware guard so non-default `OPENCLAW_PROFILE` skips default-profile approval imports, archives, and legacy fail-closed fallback, while bare state-dir relocation keeps its tested migration path.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, at source level: `--profile` sets `OPENCLAW_PROFILE` plus a profile-derived `OPENCLAW_STATE_DIR`, while the approval migration and fallback detectors only test for a non-empty state dir. I did not run a writable startup repro because this review was read-only.

## Solution Assessment

Yes, the best fix is a narrow profile-aware migration guard plus regression coverage for named profile isolation and bare state-dir relocation. A new config option or runtime fallback would be broader than the established profile contract requires.

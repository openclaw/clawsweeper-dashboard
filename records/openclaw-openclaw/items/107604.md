## Label Justifications

- `P0`: The underlying workflow destructively removes user-authored configuration comments, which is a concrete configuration data-loss problem.

## Summary

This PR remains necessary, but the current head still leaves include-file warning delivery caller-dependent, emits that warning before later rejection checks, and lacks end-to-end proof through the actual CLI write path.

## What This Changes

The PR adds JSON5 comment-loss detection and warning output for root and single-file include config writes, with focused tests and CLI warning rendering.

## Best Possible Solution

Keep detection in the shared config-write owner, route it through a guaranteed default logger, emit it only after every non-mutating guard succeeds and immediately before the atomic write, then prove both root and include behavior through real `openclaw config set` or `unset` runs.

## Reproduction Assessment

Yes at source level: JSON5 comments are discarded when the parsed object is serialized for a config write, and the include path similarly formats its value as plain JSON. A full current-main live write was not run during this read-only review.

## Solution Assessment

No in its current form: warning before destructive serialization is a bounded mitigation, but the warning must be owned by the shared write path with a guaranteed sink and correct commit timing rather than by selected callers.

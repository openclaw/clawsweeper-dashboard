## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.93

Full review comments:

- **[P1] Reject workspace backup symlinks before creating roots:** `src/commands/workspace-backup.ts:350-351`
  - body: `workspaceBackupRunCommand` creates `backup.target/workspace/mirrors` and `.staging` before validating those target-side paths. If a synced/shared backup target already contains `workspace` or `mirrors` as a symlink, the mkdir/copy/rename/delete flow can operate outside the configured backup target before the later containment checks run.
  - confidence: 0.93
- **[P1] Reject symlinked snapshot-store parents before writes:** `src/backup/snapshot-store/provider-folder.ts:67`
  - body: Both atomic write helpers call recursive `mkdir` under `targetDir/snapshots/<installationId>` without walking existing parent segments for symlinks. A symlinked `snapshots` or installation directory can redirect payload/envelope writes outside `backup.target`, so uploads must ensure every traversed parent is a real directory before writing or renaming.
  - confidence: 0.92
- **[P1] Validate restore parents before rollback moves:** `src/commands/backup-restore.ts:443`
  - body: `applyRestoreOperations` moves an existing target into rollback before `copySourceToTarget` validates the parent path. If an existing target's parent includes a symlink segment, restore can create rollback directories and rename live files through that symlink before the protection runs.
  - confidence: 0.9
- **[P2] Validate tar entries while writing archives:** `src/infra/backup-create.ts:412-418`
  - body: Archive creation only pre-scans sources, then `tar.c` writes entries without rechecking the entry type. A source tree that changes after the scan can still emit symlinks, FIFOs, or other blocked tar entries, producing archives that OpenClaw restore later rejects and that external extractors may handle unsafely.
  - confidence: 0.88
- **[P2] Cap archive path depth before parent expansion:** `src/commands/backup-verify.ts:341-343`
  - body: Verification still builds every parent path for every normalized entry without a depth cap. A single path with millions of short segments can stay under the total path-byte cap while forcing excessive CPU and memory in `collectNestedArchiveParents`, affecting both verify and restore.
  - confidence: 0.9
- **[P2] Compare in-state restore paths before suppressing copies:** `src/commands/backup-restore.ts:715-722`
  - body: Full-host restore suppresses config and OAuth copy operations whenever both source and target are inside state, but it does not compare the relative source and target paths. If the backup used one in-state config or OAuth path and the restore host uses another, restore reports success while leaving the active target stale or missing.
  - confidence: 0.87

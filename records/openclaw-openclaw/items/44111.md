## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.84

Full review comments:

- **[P1] Reject snapshot directory symlinks before writes:** `src/backup/snapshot-store/provider-folder.ts:67`
  - body: The atomic writers create `${targetDir}/snapshots/...` parents recursively and then write or rename files there, but they do not reject symlinked `snapshots` or installation directories. A synced/shared backup target containing such a symlink can redirect snapshot files outside the configured backup target, so the store should walk and reject symlinked path segments before creating or writing.
  - confidence: 0.87
- **[P1] Validate workspace backup roots before mkdir:** `src/commands/workspace-backup.ts:350-351`
  - body: `workspaceBackupRunCommand` creates the mirror and staging roots before it validates backup safety and containment. If `backup.target/.openclaw-workspace-backup` is already a symlink, these `mkdir` calls can create/write mirror data outside the configured backup target and the later canonical containment check treats the symlink target as the root.
  - confidence: 0.86
- **[P1] Walk every existing restore parent segment:** `src/commands/backup-restore.ts:337`
  - body: `ensureDirectoryPathWithoutSymlinks` checks the deepest existing parent first. When the full parent exists through an intermediate symlink, `lstat(parent)` follows that intermediate segment and reports the target directory, so restore can still copy or rename through a symlinked path segment.
  - confidence: 0.83
- **[P2] Remove or enforce backup retention config:** `src/config/zod-schema.backup.ts:25`
  - body: The PR accepts `backup.retention` with daily, weekly, monthly, and max snapshot fields, but the diff only wires those names into the config schema/types and not into snapshot pruning. That creates a public config contract that silently does nothing for users relying on retention to limit stored backups.
  - confidence: 0.8

## Security Review

Status: needs_attention

Summary: The diff introduces encrypted backup, restore, and destructive filesystem write behavior, and target-side symlink redirection remains a concrete security concern.

Concerns:

- **[high] Snapshot target symlink redirection:** `src/backup/snapshot-store/provider-folder.ts:67`
  - body: Snapshot store writes create and publish files below backup-target subdirectories without first rejecting symlinked path segments, so a prepared backup target can redirect encrypted snapshot outputs outside the intended directory.
  - confidence: 0.87

  - body: Workspace mirroring creates backup roots before safety checks, allowing a symlinked backup-workspace root to redirect mirrored workspace writes or cleanup outside the configured target.
  - confidence: 0.86

  - body: The restore parent guard can miss intermediate symlinks when the final parent already exists, which matters because restore writes config, credentials, state, and workspace data to those paths.
  - confidence: 0.83

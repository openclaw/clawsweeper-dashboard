## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.92

Full review comments:

- **[P1] Reject symlinked workspace backup roots before mkdir:** `src/commands/workspace-backup.ts:350-351`
  - body: `workspaceBackupRunCommand` creates `mirrorRoot` and `.staging` before validating that the target-side backup tree is not a symlink. A synced/cloud backup folder can contain `backup.target/workspace` or `mirrors` as a symlink, causing the subsequent mkdir/cp/rm/rename operations to act outside the configured backup directory.
  - confidence: 0.93
- **[P1] Reject symlinked snapshot-store parents:** `src/backup/snapshot-store/provider-folder.ts:67`
  - body: `writeFileAtomic` and `copyFileAtomic` call recursive `mkdir` and then rename/copy under `targetDir/snapshots/...` without walking those directory segments with `lstat`. If `snapshots` or an installation directory is a symlink in the backup target, snapshot upload can write outside `backup.target`.
  - confidence: 0.93
- **[P1] Check restore parents before rollback moves:** `src/commands/backup-restore.ts:443`
  - body: `applyRestoreOperations` moves an existing target into a rollback directory before `copySourceToTarget` validates the target parent with `ensureDirectoryPathWithoutSymlinks`. For a target whose parent path is symlinked, restore can perform the rollback rename outside the intended restore tree before the safety check runs.
  - confidence: 0.88
- **[P2] Validate tar entries while writing archives:** `src/infra/backup-create.ts:412`
  - body: The pre-scan rejects symlinks and special files, but `tar.c()` does not re-check entry type while packing. A source tree that changes after the pre-scan can still emit a symlink, FIFO, or device entry that `backup verify` later rejects, producing unusable backups from a reported successful export.
  - confidence: 0.86
- **[P2] Cap archive path depth before parent expansion:** `src/commands/backup-verify.ts:337-347`
  - body: `advanceArchiveScanTotals` caps total path bytes, but `collectNestedArchiveParents` still expands every parent segment for each path. A single long path made of many tiny segments can stay under the byte cap while creating a huge parent set during verify/restore.
  - confidence: 0.84
- **[P2] Compare in-state paths before suppressing restores:** `src/commands/backup-restore.ts:715`
  - body: Full-host restore skips standalone config/OAuth restore whenever the source path was inside the archived state dir and the current target is inside the current state dir. If the relative path changed, the state restore writes the old location while the active `OPENCLAW_CONFIG_PATH` or `OPENCLAW_OAUTH_DIR` remains missing or stale.
  - confidence: 0.9
- **[P2] Remove unused backup retention config:** `src/config/zod-schema.backup.ts:25`
  - body: Late discovery: this schema was unchanged on the previously reviewed head. The PR accepts `backup.retention.keepDaily`, `keepWeekly`, `keepMonthly`, and `maxSnapshots`, but no command reads those fields, so users can set a public config contract that does nothing. Remove the fields until retention is implemented, or wire and test the retention behavior now.
  - late: true

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.84

Full review comments:

- **[P1] Reject snapshot store directory symlinks before writes:** `src/backup/snapshot-store/provider-folder.ts:66-85`
  - body: `writeFileAtomic` and `copyFileAtomic` create and rename under `targetDir/snapshots/<installationId>` without checking those directory segments for symlinks. Because backup.target can be a synced or shared folder, a planted `snapshots` or installation directory symlink can make encrypted snapshot writes escape the configured backup target.
  - confidence: 0.92
- **[P1] Validate workspace backup roots before mkdir:** `src/commands/workspace-backup.ts:350-351`
  - body: `workspaceBackupRunCommand` creates `workspace/mirrors` and `.staging` before validating the target-side backup root. Since containment canonicalization follows existing symlinks, a symlink inside the configured backup target can make mkdir/copy/rename/remove operations run outside the backup folder.
  - confidence: 0.91
- **[P1] Validate restore parents before rollback writes:** `src/commands/backup-restore.ts:425-428`
  - body: `moveTargetToRollbackPath` creates the rollback directory and renames the live target before using the safe parent-path helper that `copySourceToTarget` uses. Existing restore targets whose parent path is a symlink can therefore be moved through an unsafe parent before the guarded copy path runs.
  - confidence: 0.86
- **[P2] Reject special entries during tar packing:** `src/infra/backup-create.ts:406-420`
  - body: The export path pre-scans sources but then calls `tar.c` without a filter or write-entry type guard. tar 7.5.11 lstat's entries during packing and writes symlink entries unless the caller rejects them, so a source tree race can still produce archives that OpenClaw restore rejects and external extractors may handle unsafely.
  - confidence: 0.82
- **[P2] Remove or enforce backup retention config:** `src/config/zod-schema.backup.ts:22-26`
  - body: The schema accepts `backup.retention` (`keepDaily`, `keepWeekly`, `keepMonthly`, and `maxSnapshots`), but no backup command or snapshot store applies pruning. Users can configure retention and still accumulate snapshots indefinitely, and the PR creates a public config contract before behavior exists.
  - confidence: 0.9

## Security Review

Status: needs_attention

Summary: Needs attention because the PR changes encrypted backup and restore filesystem paths while several symlink and archive-entry validation gaps remain.

Concerns:

- **[high] Snapshot writes can follow target symlinks:** `src/backup/snapshot-store/provider-folder.ts:66`
  - body: Folder snapshot upload writes payloads and envelopes under targetDir without segment-by-segment lstat validation, allowing a symlinked target subdirectory to redirect writes.
  - confidence: 0.92
- **[high] Workspace mirror roots are created before validation:** `src/commands/workspace-backup.ts:350`
  - body: Workspace backup creates mirror and staging roots before proving they remain inside the configured backup root without symlink traversal.
  - confidence: 0.91
- **[high] Restore rollback parent is not guarded:** `src/commands/backup-restore.ts:425`
  - body: Rollback staging uses the target parent before reusing the existing non-symlink parent creation guard, leaving a restore-time path traversal gap.
  - confidence: 0.86
- **[medium] Tar packing lacks in-pack entry type enforcement:** `src/infra/backup-create.ts:406`
  - body: Backup export relies on a pre-scan but does not enforce file/directory-only entries during tar's own lstat/write path, so source races can still emit symlink entries.
  - confidence: 0.82

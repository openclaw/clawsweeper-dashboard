## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P1] Reject symlinked workspace backup roots before mkdir:** `src/commands/workspace-backup.ts:350-351`
  - body: `backup run` creates `backup.target/workspace/mirrors` and `.staging` before proving those target-side directories are not symlinks. If a synced/shared backup folder already has `workspace -> $HOME` or another directory symlink, these mkdir/copy/rename/remove operations are redirected outside `backup.target` while the later realpath containment checks still pass. This blocker was visible in earlier cycles and remains on this unchanged head.
  - confidence: 0.9
- **[P1] Reject symlinked snapshot-store parents:** `src/backup/snapshot-store/provider-folder.ts:67`
  - body: `writeFileAtomic` and `copyFileAtomic` recursively create the snapshot parent directories and then write through them without first walking `targetDir/snapshots/<installationId>` with `lstat`. A symlink planted under the backup target can redirect payload or envelope writes outside the configured backup folder, so upload should reject symlinked parent segments before any mkdir/write/rename.
  - confidence: 0.92
- **[P1] Validate restore parents before rollback moves:** `src/commands/backup-restore.ts:443`
  - body: `applyRestoreOperations` moves an existing target into a rollback path before `copySourceToTarget` checks the target parent for symlinked or non-directory segments. If the restore parent contains a symlink, rollback creation and rename can already operate outside the intended restore directory before the later guard runs.
  - confidence: 0.82
- **[P2] Validate tar entries while writing archives:** `src/infra/backup-create.ts:406-420`
  - body: The export path pre-scans sources for symlinks and special files, but `tar.c` still has no write-time type guard. A source tree can change after the pre-scan and before/during tar traversal, producing an archive with symlink or special entries unless `--verify` happens to catch it afterward; creation should reject those entries as they are written.
  - confidence: 0.78
- **[P2] Cap archive path depth before parent expansion:** `src/commands/backup-verify.ts:337-345`
  - body: `collectNestedArchiveParents` expands every parent for every normalized archive entry after only byte/count limits. A crafted archive can spend excessive CPU/memory in parent expansion with deeply nested paths that remain under the byte cap, so verification/restoration should cap path depth or build nested coverage without unbounded parent walking.
  - confidence: 0.75
- **[P2] Compare in-state paths before suppressing restores:** `src/commands/backup-restore.ts:715-716`
  - body: Full-host restore skips a standalone config operation whenever the source config and target config are both inside their respective state dirs. If the archived in-state config relative path differs from the current host's in-state config path, the state restore writes the old location and leaves the active target stale or missing after reporting success.
  - confidence: 0.84
- **[P2] Compare in-state OAuth paths before suppressing restores:** `src/commands/backup-restore.ts:741-742`
  - body: The credentials branch has the same issue: it skips a standalone credentials operation whenever both OAuth dirs are inside state, without comparing the archived relative path to the current target relative path. A restore can therefore leave the active in-state OAuth directory stale or missing while reporting success.
  - confidence: 0.82

Overall confidence: 0.86

Full review comments:

- **[P1] Reject symlinked workspace backup target parents:** `src/commands/workspace-backup.ts:350-352`
  - body: This path creates `backup.target/workspace/mirrors` and `.staging` before rejecting target-side symlinks, and the later containment check uses `realpath()` on both root and child. If a synced backup target contains `workspace` or `workspace/mirrors` as a symlink, backup run can copy, rename, remove stale mirrors, and write status outside the configured target. This was equally visible in the previous reviewed head; reject symlink path segments before any mkdir/copy/rename/rm.
  - late: true
  - confidence: 0.9
- **[P1] Reject symlinked snapshot-store parents:** `src/backup/snapshot-store/provider-folder.ts:85-95`
  - body: The snapshot store still creates the destination parent with recursive mkdir and then writes/renames the payload and envelope under `targetDir/snapshots/<installationId>` without checking existing path segments. A shared or synced backup target can replace `snapshots` or the installation directory with a symlink, causing encrypted snapshot files to be written outside `backup.target`. This previous blocker is still present.
  - confidence: 0.91
- **[P2] Validate tar entries as they are written:** `src/infra/backup-create.ts:412-418`
  - body: The pre-scan can be invalidated before node-tar's per-entry `lstat`. node-tar 7.5.11 calls `onWriteEntry` after `lstat` and can emit `SymbolicLink` entries, so a source tree swap during backup can still produce an archive that verify/restore reject or that unsafe external extractors mishandle. Re-check entry type in `filter` or `onWriteEntry` before remapping/writing.
  - confidence: 0.88
- **[P2] Cap archive path depth before expanding parents:** `src/commands/backup-verify.ts:337-347`
  - body: This loop materializes every parent directory for every normalized entry, but the earlier guard only caps total path bytes. A crafted entry with a very large number of short segments can still allocate a huge `Set` and burn CPU during verify/restore before the manifest check finishes. Bound segment depth or avoid full parent expansion.
  - confidence: 0.86
- **[P2] Copy config when the in-state target path changed:** `src/commands/backup-restore.ts:715-716`
  - body: This branch suppresses the explicit config restore whenever the source config was inside the archived state and the current config path is also inside the current state. If the archived config was `.openclaw/openclaw.json` but the current `OPENCLAW_CONFIG_PATH` points at `.openclaw/profiles/openclaw.json`, the state restore writes only the old relative path and leaves the active config missing or stale. Compare source and target relative paths before skipping the config operation.
  - confidence: 0.88
- **[P2] Copy OAuth dir when the in-state target path changed:** `src/commands/backup-restore.ts:741-742`
  - body: The OAuth restore path has the same in-state-relative-path bug: it skips the credentials copy when the archived OAuth dir was inside the old state and the current OAuth dir is inside the new state, even if the relative path changed. A restore can therefore report success while the active credentials directory remains missing or stale. Compare the archived and current relative paths before suppressing the credentials operation.
  - confidence: 0.88

Overall correctness: patch is incorrect

Overall confidence: 0.94

Full review comments:

- **[P1] Reject snapshot store directory symlinks before writes:** `src/backup/snapshot-store/provider-folder.ts:67`
  - body: `uploadSnapshot` still writes through `targetDir/snapshots/<installationId>` with recursive `mkdir` and `rename` but never validates the intermediate directories inside the backup target. A synced/shared backup folder can replace `snapshots` or an installation directory with a symlink and make snapshot payload/envelope writes land outside `backup.target`; add a no-symlink directory walk before writes and reads.
  - confidence: 0.93
- **[P1] Validate workspace backup roots before mkdir:** `src/commands/workspace-backup.ts:350-351`
  - body: `workspaceBackupRunCommand` creates `backup.target/workspace/mirrors` and `.staging` before validating that those target-side directories are not symlinks, and the later containment check canonicalizes through symlinks. If `backup.target/workspace` is swapped to a symlink, the mkdir/cp/rename/rm flow can operate outside the backup directory; lstat the target/workspace/mirror/staging path segments before any write.
  - confidence: 0.94
- **[P1] Validate restore parents before rollback writes:** `src/commands/backup-restore.ts:426-428`
  - body: `applyRestoreOperations` calls `moveTargetToRollbackPath` before `copySourceToTarget` validates the target parent with `ensureDirectoryPathWithoutSymlinks`. That means an existing restore target under a symlinked parent can create rollback directories and rename live data through the symlink before the safe-parent guard runs; validate the parent before access/rollback as well as before copy.
  - confidence: 0.9
- **[P2] Cap archive path depth during verification:** `src/commands/backup-verify.ts:337-346`
  - body: The added byte/count caps still allow a single multi-megabyte path with an enormous number of slash-separated segments, and `collectNestedArchiveParents` materializes one parent string per segment. A crafted backup can still consume excessive CPU/memory during verify/restore; add a segment/depth cap or avoid expanding every parent path.
  - confidence: 0.86
- **[P2] Reject special entries during tar packing:** `src/infra/backup-create.ts:412-418`
  - body: Archive creation only pre-scans sources before `tar.c`, but node-tar can still emit `SymbolicLink` entries if a source is swapped after the scan and `Link` entries for regular files with multiple hardlinks. The verifier now rejects those entry types, so `backup export` can create archives that later fail verify/restore; enforce the same policy in the tar filter/onWriteEntry path or disable hardlink entries.
  - confidence: 0.88
- **[P2] Remove or enforce backup retention config:** `src/config/zod-schema.backup.ts:25`
  - body: The schema accepts `backup.retention.keepDaily`, `keepWeekly`, `keepMonthly`, and `maxSnapshots`, but no backup command or folder store reads those values. Users who configure a retention limit will believe snapshots are pruned while they accumulate indefinitely, so either implement pruning with tests/docs or remove the config surface until it is real.
  - confidence: 0.91

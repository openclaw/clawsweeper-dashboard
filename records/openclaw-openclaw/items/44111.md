## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.89

Full review comments:

- **[P1] Reject workspace backup symlinks before creating roots:** `src/commands/workspace-backup.ts:350-352`
  - body: `workspaceBackupRunCommand` creates `backup.target/workspace/mirrors` and `.staging` before validating that those target-side path segments are not symlinks. A synced/shared backup folder can replace `workspace` with a symlink and cause mkdir/rename/remove work to happen outside the backup target, so the root and parents need no-symlink validation before any write.
  - confidence: 0.93
- **[P1] Reject symlinked snapshot-store parents before writes:** `src/backup/snapshot-store/provider-folder.ts:67-85`
  - body: Both atomic write helpers call `fs.mkdir(..., { recursive: true })` on the destination parent without rejecting symlinked `snapshots` or installation directories under `backup.target`. That lets a mutable backup folder redirect encrypted payload/envelope writes outside the configured target, so writes should create or validate each parent segment as a real directory first.
  - confidence: 0.93
- **[P1] Validate restore parents before rollback moves:** `src/commands/backup-restore.ts:426-428`
  - body: `applyRestoreOperations` moves an existing target into a rollback directory before `copySourceToTarget` validates the target parent with `ensureDirectoryPathWithoutSymlinks`. If the parent path contains a symlink, rollback creation and the first rename can already follow it before the later guard runs, so parent validation needs to happen before `moveTargetToRollbackPath`.
  - confidence: 0.9
- **[P2] Validate tar entries while writing archives:** `src/infra/backup-create.ts:412-418`
  - body: The export path pre-scans assets for symlinks/special files, then hands the same trees to `tar.c` without an at-write filter or blocked-entry check. A source tree can change after the pre-scan and produce an archive that restore/verify later rejects or that is unsafe for external extractors; the tar writer should reject blocked entry types as it writes.
  - confidence: 0.87
- **[P2] Cap archive path depth before parent expansion:** `src/commands/backup-verify.ts:337-346`
  - body: `collectNestedArchiveParents` expands every parent for every normalized entry, but the earlier limit caps only total path bytes, not segment depth. A single very deep path can still allocate a huge parent set during verify/restore, so the verifier should bound path segment depth or avoid materializing every ancestor string.
  - confidence: 0.86
- **[P2] Compare in-state restore paths before suppressing copies:** `src/commands/backup-restore.ts:715-722`
  - body: Full-host restore suppresses config/OAuth copies whenever the source path and current target are both inside their state dirs. If the archive used one in-state relative path and the restore host uses another, the state restore will not populate the active config or OAuth path, so the coverage check must compare the source and target relative paths before skipping the explicit copy.
  - confidence: 0.88

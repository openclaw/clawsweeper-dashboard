## Summary

Keep open. Current main and v2026.6.11 fix the `sessions_send` selector conflict, but the shared `message(action="send")` poll-field contract still has a source-visible failure path and is already tracked by the narrower open issue at https://github.com/openclaw/openclaw/issues/42820.

## What This Changes

The issue reports that schema-visible optional fields cause agents to send invalid `sessions_send` and `message` tool calls, blocking agent-to-agent communication.

## Best Possible Solution

Keep the shipped `sessions_send` precedence fix, then resolve the remaining shared message-tool contract through https://github.com/openclaw/openclaw/issues/42820 with action-scoped schemas or explicit send-side normalization.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For plain `message(action="send")`, should OpenClaw hide poll content fields from send-capable schemas, strip accidental poll fields at runtime, or keep rejecting content-bearing poll fields as explicit poll intent?

Rationale: The remaining behavior is a shared model-facing message-tool contract across multiple channels; changing it affects whether send reliability or strict poll-intent validation wins when a model supplies contradictory fields.

Likely owner: gumadeiras

Owner reason: Their merged poll gating and schema-consistency work is the strongest current history signal for the shared send/poll contract boundary.

Owner confidence: high

Options:

- **Action-scope poll fields (recommended):** Expose poll creation fields only for poll actions or channel-specific poll tools so models are less likely to fill them during plain sends while strict poll validation remains intact.
- **Strip on send:** Treat `action="send"` as authoritative and drop poll creation fields before delivery, improving send reliability but potentially hiding callers that meant to create a poll.
- **Keep strict guard:** Continue rejecting content-bearing poll fields on send and require stronger live evidence before changing the shared tool contract.

## Reproduction Assessment

Yes, at source level: current main still throws before delivery when `message(action="send")` includes non-empty `pollQuestion` or `pollOption`. I did not establish a live current-main model/channel reproduction showing that models still emit those content fields after the metadata-padding fix.

## Solution Assessment

Unclear: the current validator narrowing and `sessions_send` precedence repair are good partial fixes, but the durable remaining solution depends on a maintainer choice between action-scoped schemas, send-side sanitization, or preserving the strict poll-intent guard.

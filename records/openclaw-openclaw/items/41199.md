## Summary

Keep open. Current main and v2026.6.11 fix the `sessions_send` selector conflict, but the shared `message(action="send")` path still rejects content-bearing poll fields before delivery; the remaining work is already tracked by the narrower open message-tool issue and needs a contract decision.

## What This Changes

The issue reports that model-filled optional parameters make `sessions_send` and `message(action="send")` fail before agent-to-agent or channel message delivery.

## Best Possible Solution

Keep the shipped `sessions_send` precedence fix, then settle the remaining shared message-tool contract through the narrower open issue, preferably with action- or channel-scoped schemas that keep poll creation fields away from ordinary sends while preserving explicit poll validation.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For plain `message(action="send")`, should OpenClaw hide poll content fields from the send schema, strip accidental poll fields at runtime, or keep rejecting content-bearing poll fields as explicit poll intent?

Rationale: The current code intentionally allows metadata-only schema padding but rejects non-empty poll content fields; changing that boundary affects shared channel delivery semantics across Discord, Telegram, Feishu, and other message-tool channels.

Likely owner: gumadeiras

Owner reason: Their merged poll-guard and schema-consistency work is the strongest history signal for the shared send/poll contract boundary.

Owner confidence: high

Options:

- **Action-scope poll schema (recommended):** Expose poll creation fields only for explicit poll actions or channel-specific poll tools, reducing accidental model fill while preserving strict poll validation.
- **Strip on send:** Treat `action="send"` as authoritative and drop poll fields before delivery, improving send reliability while potentially masking poll-intent mistakes.
- **Keep strict guard:** Continue rejecting content-bearing poll fields on send and require live evidence before changing the tool contract further.

## Reproduction Assessment

Partly: source inspection shows current main still throws before delivery when `message(action="send")` includes non-empty `pollQuestion` or `pollOption`, but I did not establish a live current-main model/channel reproduction showing those content fields are still emitted after the metadata-padding fix.

## Solution Assessment

Is this the best way to solve the issue? Unclear: the current validator narrowing is a good partial fix, but the durable remaining solution depends on a maintainer choice between action-scoped schemas, send-side sanitization, or preserving strict poll-intent rejection.

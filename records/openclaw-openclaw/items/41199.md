## Summary

Keep open. Current main fixes the `sessions_send` selector conflict, but the shared `message(action="send")` path still rejects content-bearing poll fields before delivery, and the remaining message-tool contract is already tracked by a narrower open issue.

## What This Changes

The issue reports model-generated conflicting optional parameters in `sessions_send` and `message(action="send")`, causing agent-to-agent and channel message delivery failures.

## Best Possible Solution

Keep the `sessions_send` precedence fix, then resolve the shared message-tool contract through https://github.com/openclaw/openclaw/issues/42820, preferably with action-scoped or channel-scoped schemas that keep poll creation fields away from ordinary sends while preserving explicit poll validation.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For plain `message(action="send")`, should OpenClaw prevent models from seeing poll content fields in the send schema, strip accidental poll fields at runtime, or keep rejecting content-bearing poll fields as explicit poll intent?

Rationale: Current code intentionally accepts schema-padded poll modifiers but rejects non-empty poll content fields; changing that boundary affects shared channel delivery semantics across Discord, Telegram, Feishu, Slack, and other message-tool channels.

Likely owner: gumadeiras

Owner reason: Their merged poll-guard and schema-consistency work is the strongest history signal for the shared send/poll contract boundary.

Owner confidence: high

Options:

- **Action-scope poll fields (recommended):** Expose poll creation fields only for poll actions or channel-specific poll tools, reducing accidental model fill while preserving strict poll validation.
- **Strip on send:** Treat `action="send"` as authoritative and drop poll fields before delivery, improving reliability but potentially masking poll intent mistakes.
- **Keep strict guard:** Continue rejecting content-bearing poll fields on send and require callers or schema discovery to avoid generating them accidentally.

## Reproduction Assessment

Yes, at source level: current main still throws before delivery when `message(action="send")` includes non-empty `pollQuestion` or `pollOption`. I did not establish a live current-main model/channel reproduction showing that models still emit those content fields after the metadata-padding fix.

## Solution Assessment

Unclear: the current validator narrowing is a good partial fix, but the durable remaining solution depends on a maintainer choice between stricter action-scoped schemas, send-side sanitization, or preserving the strict poll-intent guard.

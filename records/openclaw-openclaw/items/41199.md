## Summary

Keep open. Current main fixes the `sessions_send` selector conflict, but the shared `message(action="send")` path still rejects content-bearing poll fields before delivery, and the remaining contract decision is tracked by the active narrower message-tool issue rather than solved here.

## What This Changes

The issue reports that agent-to-agent communication tools expose optional parameters that models overfill, causing `sessions_send` selector conflicts and `message` send/poll validation failures.

## Best Possible Solution

Keep the `sessions_send` precedence fix, then settle the shared message-tool contract through the active narrower issue: preferably narrow action/channel schemas so plain sends do not expose poll content fields, while preserving explicit poll validation for real poll actions.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For plain `message(action="send")`, should OpenClaw prevent models from seeing poll content fields in the send schema, strip accidental poll fields at runtime, or keep rejecting content-bearing poll fields as explicit poll intent?

Rationale: Current code intentionally accepts schema-padded poll modifiers but rejects non-empty poll content fields; changing that boundary affects shared channel delivery semantics across Discord, Telegram, Feishu, and other message-tool channels.

Likely owner: gumadeiras

Owner reason: Their merged poll-guard and schema-consistency work is the strongest history signal for the shared send/poll contract boundary.

Owner confidence: medium

Options:

- **Narrow schemas first (recommended):** Action-scoped or channel-scoped schemas keep poll fields away from ordinary sends while preserving strict poll validation when `action="poll"` is selected.
- **Strip on send:** Treat `action="send"` as authoritative and drop poll fields before delivery, improving reliability but potentially masking poll intent mistakes.
- **Keep strict guard:** Continue rejecting content-bearing poll fields on send and require callers or schema discovery to avoid generating them accidentally.

I did not establish a live current-main model/channel reproduction showing that GPT-family models still emit those content fields after the metadata-padding fix.

## Solution Assessment

Unclear: the current validator narrowing is a good partial fix, but the durable remaining solution depends on a maintainer choice between stricter action-scoped schemas and send-side sanitization.

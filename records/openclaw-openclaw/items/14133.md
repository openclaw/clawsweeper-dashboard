## Label Justifications

- `P3`: This is useful Control UI and scheduled-job ergonomics work, but it is not an urgent runtime failure or blocked setup path.
- `impact:ux-friction`: Reminder jobs currently appear in generic cron management with raw payload-oriented details, creating avoidable user-facing confusion without fully blocking progress.

## Summary

Keep open: current main and the latest release still expose reminders only through the generic cron surface, and the related cron tags/categories issue covers only part of the classification work. The remaining work needs a product decision on the shared cron purpose/display metadata contract and the Reminders-versus-Cron visibility policy.

## What This Changes

Add a dedicated Reminders tab in Control UI/Mission Control that separates one-shot reminder cron jobs from generic cron jobs and displays cleaned reminder details.

## Best Possible Solution

Define one additive cron purpose/display metadata contract, have reminder-producing paths set it, add typed reminder/non-reminder filters, then build the Reminders tab and Cron-tab visibility policy against that shared model.

## Reproduction Assessment

Yes. Source inspection on current main shows no Reminders route/render branch, no reminder-purpose/display fields in cron contracts, and no reminder/non-reminder filter path.

## Solution Assessment

Unclear as proposed. A dedicated Reminders UX is reasonable, but tags or payload extraction alone are not the best permanent fix until maintainers choose the shared cron purpose/display contract and visibility policy.

## What This Changes

Repair usage-cost refresh-lock ownership so a lock left by a crashed gateway is reclaimed when a restarted container reuses the same numeric PID.

## System Context

Usage-cost refreshes persist a small coordination lock beside or within the session-cost cache so concurrent refreshes do not duplicate work. Cache readers consult that lock before rebuilding usage rollups from session transcripts; an orphaned lock can therefore leave usage figures stale and make later refreshes repeatedly rescan transcripts.

## Architecture Diagram

flowchart TD
  A[Gateway usage-cost request] --> B[Read persisted refresh lock]
  B --> C[Evaluate lock ownership]
  C -->|held| D[Return cached usage state]
  C -->|stale or absent| E[Acquire refresh lock]
  E --> F[Rebuild session usage rollups]
  F --> G[Write refreshed cache]
  G --> H[Release refresh lock]

## Best Possible Solution

Land a narrowly reviewed fix that distinguishes a lock owned by the current process incarnation from an orphaned same-PID lock, with regression coverage for both stale-lock reclamation and active-lock exclusion.

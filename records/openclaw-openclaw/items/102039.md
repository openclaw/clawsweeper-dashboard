## Label Justifications

- `P1`: The PR changes service-manager restart behavior for Linux gateway installs and can break existing disabled-restart configurations during operator restarts.
- `merge-risk: 🚨 compatibility`: Generated systemd units would change the restart signal for existing installs, interacting with the documented `commands.restart=false` external-SIGUSR1 contract.
- `merge-risk: 🚨 availability`: When that contract disables external SIGUSR1, `systemctl restart` may wait for `TimeoutStopSec` and force-kill the gateway instead of performing a graceful restart.

## Summary

Keep open. The change targets a real Linux systemd restart gap, but the patch currently routes service-manager restarts through the same external SIGUSR1 path that existing `commands.restart=false` configurations explicitly disable, so it can turn `systemctl restart` into a timeout and force-kill path.

## What This Changes

The PR adds `RestartKillSignal=SIGUSR1` to generated Linux systemd gateway units and adds a unit test assertion for that generated output.

## Best Possible Solution

Keep the systemd managed-restart improvement only after the generated unit, SIGUSR1 policy, docs/tests, and real Linux proof preserve disabled-restart setups or explicitly change the contract with maintainer approval.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should generated systemd service-manager restarts be allowed to use the SIGUSR1 restart path when `commands.restart=false` blocks external SIGUSR1?

Rationale: The patch cannot distinguish a systemd `RestartKillSignal=SIGUSR1` from a manual external SIGUSR1 in Node, so preserving the documented disabled-restart contract versus enabling systemd managed restart recovery requires maintainer intent.

Likely owner: omarshahine

Owner reason: Recent merged history owns both the generated systemd unit template and the SIGUSR1 external-restart policy lines implicated by this compatibility choice.

Owner confidence: medium

Options:

- **Preserve disabled-restart compatibility (recommended):** Keep `commands.restart=false` from turning `systemctl restart` into an ignored SIGUSR1, even if that means using a different systemd handoff shape or deferring this directive until the policy can distinguish service-manager restarts.
- **Let generated systemd bypass the block:** Treat installed systemd units as trusted restart controllers and update code, docs, and tests to state that `commands.restart=false` does not block service-manager restarts for generated units.
- **Pause this systemd shortcut:** Leave generated units on SIGTERM restarts until a broader restart-policy design handles service-manager and manual OS-signal restarts separately.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence reproduction path: set `commands.restart=false`, run a generated systemd unit with `RestartKillSignal=SIGUSR1`, then `systemctl restart` sends an external SIGUSR1 that the run loop ignores.

## Solution Assessment

No. The current patch is too broad because it changes all generated systemd restarts without preserving the documented disabled-restart behavior; the fix needs either a compatible signal policy or a maintainer-approved contract change.

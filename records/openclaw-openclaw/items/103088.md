## Summary

Keep open: current main still computes memory-wiki bridge artifact status from a process-wide public artifact list without caller agent scope, and no merged related item fixes this status/doctor metadata leak. The sibling report at https://github.com/openclaw/openclaw/issues/103087 is more severe and shares the bridge scoping root cause, but this issue remains a distinct status/doctor surface that needs maintainer security-boundary direction.

## What This Changes

The issue reports that `wiki_status` and `openclaw wiki doctor` expose a process-wide bridge memory artifact count instead of scoping the count to the calling agent.

## Best Possible Solution

Separate agent-visible status from operator diagnostics so agents cannot infer other agents' bridged memory artifacts, while retaining a clearly authorized global doctor/status view if maintainers want that behavior.

- **Scope agent-visible status (recommended):** Thread caller identity into agent-visible `wiki_status` and filter artifacts by `agentIds`, while keeping or adding only an explicitly operator-authorized global diagnostic path.
- **Keep global status with access gating:** Treat the count as an operator diagnostic and restrict the exposed status/doctor method so untrusted agent callers cannot invoke it.
- **Close as accepted global metadata:** Declare the count intentionally global, accepting that agents may infer other agents' bridge artifacts from status output.

## Solution Assessment

Unclear until maintainers choose the boundary: filtering by `agentIds` is the likely narrow code fix for agent-visible status, but CLI/gateway doctor may need an explicit operator-global path instead of silently changing all diagnostics.

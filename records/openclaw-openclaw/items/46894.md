## Label Justifications

- `P2`: This is a normal-priority WebUI regression with a clear source path and limited blast radius around local model slash commands.
- `impact:auth-provider`: The failure is in model choice/provider routing: an informational subcommand is sent as a model override and rejected as an invalid provider/model selection.
- `impact:ux-friction`: Users see avoidable `model not allowed` errors for reasonable `/model status` and `/model list` inputs, but the core runtime remains usable through other paths.

## Summary

Keep open: current main and the latest release still route every non-empty `/model` argument through `sessions.patch`, so `/model status` and `/model list` remain source-reproducible as model-setting attempts. An open linked fix candidate exists, but it is unmerged and conflicts against the current file layout, so it is not implementation proof.

## What This Changes

The issue reports that Control UI/WebUI parses `/model status` and `/model list` as model ids and sends them to `sessions.patch` instead of showing model information.

## Best Possible Solution

Review, rebase, or replace https://github.com/BingqingLyu/openclaw/pull/753 with a narrow current-main fix in `ui/src/pages/chat/chat-command-executor.ts` that routes `/model status`, `/model list`, and `/model info` to the model-info branch and adds regression tests proving they do not call `sessions.patch`.

## Reproduction Assessment

Yes at source level: current main sends every non-empty `/model` argument to `sessions.patch`, so `/model status` and `/model list` follow the failing path described by the logs. I did not run a fresh live browser session in this read-only review.

## Solution Assessment

Yes, the best fix is a small pre-patch guard that treats `status`, `list`, and `info` like bare `/model` while preserving `/model <provider/model>` as the model-setting path. The linked fix candidate has the right shape but needs to be brought onto the current file layout and validated.

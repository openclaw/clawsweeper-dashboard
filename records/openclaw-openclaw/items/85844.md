## Summary

Keep open. The merged managed-plugin retention work in https://github.com/openclaw/openclaw/pull/95589 resolves a documented slice, but the issue’s Linux and Windows reports plus the maintainer analysis leave the broader old-process/new-files failure mode unresolved for raw/manual swaps, shutdown, and recovered Codex turns. The remaining choice is availability-sensitive and already has an assigned owner, so it needs an explicit maintainer decision and fresh current-version proof rather than another automatic fix attempt.

## What This Changes

Prevent package or plugin rotation from leaving a running gateway or recovered Codex turn trying to dynamically import a removed content-hashed bundle chunk.

## System Context

OpenClaw’s update flow replaces core and plugin package trees while the Gateway continues to serve channels and agent turns. Those long-lived processes can later lazy-load code from their original module graph, so a rotation that removes old hashed chunks can fail an in-flight task or message path unless the old generation remains available or the process transitions safely.

## Architecture Diagram

flowchart TD
  A[Update or plugin rotation] --> B[Package generation swap]
  B --> C[Running gateway and active turns]
  C --> D[Lazy dynamic import]
  D --> E{Referenced chunk remains available?}
  E -->|Yes| F[Turn and channel processing continue]
  E -->|No| G[Stale import failure]
  G --> H[Controlled recovery or restart state]

## Best Possible Solution

Make managed core and plugin updates generation-safe until the prior gateway and in-flight work have exited, then define an explicit restart-required or bounded stale-own-dist recovery path for uncoordinated swaps; prove the chosen contract with redacted Linux and Windows update/recovery runs without treating arbitrary missing dependencies as stale-chunk events.

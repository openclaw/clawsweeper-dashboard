Keep open: the PR addresses a real heartbeat prompt bug, but it is still not the best fix shape and lacks contributor-provided real heartbeat behavior proof.

## What This Changes

The PR adds a provider-string guard in `buildInboundUserContextPrefix` plus tests so heartbeat, cron-event, and exec-event synthetic contexts omit the `Conversation info` block while real QQ bot messages retain it.

## Best Possible Solution

Land one canonical caller-owned fix that skips inbound user context for `opts.isHeartbeat` in `runPreparedReply`, keeps `buildInboundUserContextPrefix` provider-agnostic, and includes redacted real heartbeat prompt/log proof.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes for source reproduction: current main builds heartbeat contexts with `OriginatingTo`, then unconditionally feeds that context into `buildInboundUserContextPrefix`, which can emit `Conversation info.chat_id`. I did not live-run the downstream QQ/M3 warning path.

## Solution Assessment

No: suppressing heartbeat inbound context is the right direction, but this PR puts the provider-id guard in the generic metadata builder instead of using the caller's `opts.isHeartbeat` signal. The narrower maintainable solution is to skip the inbound user-context prefix at `runPreparedReply` for heartbeat runs.

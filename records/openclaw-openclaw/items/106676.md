## Summary

The reported cross-user access assumes a hostile multi-tenant boundary that OpenClaw explicitly does not provide: authenticated gateway operators share one trust domain, and the security policy specifically excludes shared-gateway `chat.history` IDOR claims unless an actual authentication or operator-scope bypass is demonstrated. ([github.com](https://github.com/openclaw/openclaw/blob/main/SECURITY.md))

## What This Changes

Add per-account ownership checks to historical message fetches so one authenticated gateway user cannot retrieve another user’s messages.

## Best Possible Solution

Keep history access behind the documented operator scopes, deploy separate gateways and OS-user or host boundaries for mutually untrusted users, and privately report any reproducible path that retrieves history without the required gateway authentication or `operator.read` scope.

## Reproduction Assessment

No. The report supplies no current endpoint request, affected version, two-identity setup, or evidence that a caller without `operator.read` can retrieve history; the described cross-operator behavior is expected inside one gateway trust domain.

## Solution Assessment

No. Binding messages to an `accountId` would introduce an unsupported per-user tenant authorization model; the maintainable solution for mutually untrusted users is separate gateway and host or OS-user boundaries.

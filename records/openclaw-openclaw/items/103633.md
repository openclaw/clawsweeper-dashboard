## Label Justifications

- `P0`: A managed gateway can enter a persistent silent crash loop during a normal self-update and leave a non-technical user without an in-product recovery path.
- `impact:crash-loop`: launchd repeatedly attempted to execute a pnpm path whose package contents had been pruned, eventually leaving the gateway unavailable.
- `impact:ux-release-blocker`: Recovery required technical log inspection and a fresh host-side install because the gateway, updater, and restart mechanisms were all unavailable.
- `maturity:stable`: The failure affects M4 Stable CLI update, gateway lifecycle, and macOS gateway-host service-management features.

## Summary

Keep open: current main prevents self-pruning only when the running gateway already contains the post-exit handoff; the reported upgrade was initiated by vulnerable `v2026.5.7` code, so first upgrades from older shipped versions remain uncovered even though future self-updates are protected.

## What This Changes

Make gateway-initiated package updates safe when launchd still references a pnpm installation that the update can prune.

## Best Possible Solution

Provide an installer-owned, host-side upgrade bootstrap for vulnerable pre-handoff releases that preserves or rewrites the launchd target before package pruning, verifies the replacement gateway, and exposes a visible Doctor/Fix recovery path instead of requiring log inspection and a manual reinstall.

Question: Should OpenClaw support gateway-initiated upgrades from pre-`v2026.5.18` managed installations with a retrofit-safe bootstrap, or declare that legacy versions must update from an outside shell?

Rationale: The current handoff is correct for gateways that already contain it, but old shipped binaries cannot consume that logic before their first package mutation; choosing a retrofit mechanism versus a documented support boundary requires maintainer upgrade-policy judgment.

Likely owner: steipete

Owner reason: Recent history shows broad ownership across updater recovery, handoff verification, and merge decisions for this lifecycle surface.

Owner confidence: high

Options:

- **Add legacy upgrade bootstrap (recommended):** Implement a narrowly guarded host-side or target-installer path that safely rewrites and verifies the managed service when a vulnerable old gateway initiates its first upgrade.
- **Require outside-shell upgrade:** Declare pre-`v2026.5.18` gateway self-update unsupported, add prominent detection and recovery guidance where current surfaces can expose it, and direct users to update from a host shell.

## Reproduction Assessment

Yes at source level: run `v2026.5.7` as a pnpm-global launchd service and invoke control-plane `update.run`; that tagged handler mutates the package in-process and can leave launchd referencing the pruned absolute path. A destructive live rerun was not performed.

## Solution Assessment

No, the existing current-main handoff is only a future-safe partial solution: it correctly protects installations that already contain it but cannot govern the first upgrade executed by a vulnerable older binary.

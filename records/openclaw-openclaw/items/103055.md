## Label Justifications

- `P0`: The issue reports a command authorization boundary bypass where an allowlisted non-owner can see other users’ ACP session metadata.
- `impact:security`: The affected behavior exposes session labels, agent ids, runtime state, backend, and thread bindings across an authorization boundary.

## Summary

Keep open: current main still lets an authorized non-owner reach `/acp sessions`, and that handler formats the unfiltered gateway-wide ACP session list despite docs saying the command is requester-scoped.

## What This Changes

The issue asks OpenClaw to prevent allowlisted non-owner senders from enumerating gateway-wide ACP session metadata through `/acp sessions`.

## Best Possible Solution

Keep `/acp sessions` non-owner-safe by returning only the requester’s current or bound ACP session, while preserving explicit owner/internal-admin gateway-wide diagnostics only if maintainers want that capability.

## Maintainer Decision

Rationale: The current docs define a non-owner requester-scoped command, but the current implementation is gateway-wide and exposes session metadata, so maintainers should confirm the security boundary before repair.

Likely owner: steipete

Owner confidence: high

Options:

- **Scope Non-Owner Results (recommended):** Keep the documented non-owner command but filter results to the current bound/requester session and add two-session regression coverage.
- **Make Sessions Owner-Only:** Move `sessions` into the owner/admin gate and update docs/tests if maintainers decide any session listing is too sensitive for non-owners.
- **Accept Gateway-Wide Visibility:** Retain the current broad listing only with an explicit maintainer security decision and docs that describe it as owner-equivalent diagnostics.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: configure an authorized non-owner, create another ACP session, and `/acp sessions` reaches the unfiltered SQLite-backed listing; I did not run an end-to-end channel command in this read-only review.

## Solution Assessment

Yes, the narrow best fix is to enforce the documented requester scope before formatting session rows. If that ownership model is not reliable enough, the safer fallback is making `/acp sessions` owner/internal-admin-only and updating docs/tests.

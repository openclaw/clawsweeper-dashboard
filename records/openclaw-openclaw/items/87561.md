## Label Justifications

- `P1`: Silent final fallback delivery loss can break active agent/channel workflows for real users across supported messaging channels.
- `impact:message-loss`: The issue is directly about user-visible final fallback messages being suppressed, dropped, or treated as delivered without proof.
- `impact:session-state`: The requested diagnostics and pending-final semantics affect recovery's ability to distinguish delivered, suppressed, failed, and unknown terminal outcomes.

## Summary

Keep open. Current main has partial durable delivery-status plumbing, but the cross-channel contract is still unresolved: routed final replies can still treat non-hook durable suppression as a successful routed final without a message id, and the issue has active maintainer/product-decision labels plus a newer Telegram production repro.

## What This Changes

Define and enforce cross-channel durable final fallback delivery semantics so sanitized final fallback messages are delivered or reported as real delivery failures instead of silently disappearing.

## Best Possible Solution

Keep this as the canonical maintainer-owned delivery contract and land targeted slices only after the core/SDK outcome semantics and cross-channel conformance plan are explicit.

## Reproduction Assessment

Yes. Source inspection establishes the contract gap: sendDurableMessageBatch can return suppressed for no identity, routeReply maps non-hook suppression to ok:true without a message id, and dispatch-from-config counts that as delivered final cleanup.

## Solution Assessment

Current main is only a partial solution. The best fix is a shared core/SDK contract that preserves explicit sent, suppressed, failed, partial, and unknown outcomes through route-reply and dispatcher cleanup, then conformance tests and targeted channel fixes such as Telegram #96095.

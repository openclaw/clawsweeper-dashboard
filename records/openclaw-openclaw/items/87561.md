## Summary

Keep open: current main and the latest release still have source-backed paths where visible final fallback delivery can be treated as successful or non-failed without proven platform delivery, and the new Telegram production repro plus open PR #96095 cover only a partial channel slice.

## What This Changes

The issue asks OpenClaw to define and enforce durable final fallback delivery semantics so sanitized final fallback messages are delivered or reported with explicit failure/suppression outcomes across durable text-capable channels.

## Best Possible Solution

Keep #87561 as the canonical maintainer-owned delivery contract, land or replace partial slices such as #96095, then add SDK/core conformance and diagnostics coverage across durable text-capable channels.

## Reproduction Assessment

Yes. Source inspection shows WhatsApp can return an empty identity for final isError payloads while routed final dispatch treats ok as queued, and the new Telegram comment reports the same class through queuedFinal timeout clearing pending-final state.

## Solution Assessment

Yes. A broad core/channel delivery contract is the right fix shape; channel-specific PRs are useful slices but cannot alone settle SDK semantics, explicit delivery outcomes, recovery visibility, and conformance coverage.

## Label Justifications

- `P1`: The issue describes a real agent/channel safety gap where risky tool calls can modify files, send messages, or run host actions before the user can answer visible confirmation text.
- `impact:data-loss`: The missing gate can allow unintended file edits, deletes, or config mutations when the model emits a risky tool call alongside confirmation text.
- `impact:security`: The request is about enforcing a human-consent boundary before sensitive tool execution instead of relying on model narration or prompt compliance.

## Summary

Keep open: current main still has plugin-level `before_tool_call.requireApproval`, trusted tool policies, and exec approvals, but it does not provide the requested built-in `tools.confirmation` config, response-level risk classifier, or same-response assistant-text-aware hold before the first tool executes.

## What This Changes

The issue requests a configurable core tool-confirmation gate that can pause risky tool calls for human approval before execution.

## Best Possible Solution

Define a backward-compatible core confirmation design with deterministic tool-risk classification, explicit approve/deny/timeout behavior, transcript handling for skipped calls, config/docs/schema coverage, and regression tests that preserve existing plugin approval hooks.

## Reproduction Assessment

Yes, at source level. Current main has strict config schemas without `tools.confirmation`, a before-tool hook event without assistant text, and tool execution continues immediately after existing hook approval/block checks.

## Solution Assessment

Unclear until maintainers choose the product/security semantics. A core confirmation gate is a plausible right layer, but the text-question heuristic should be replaced or constrained by deterministic authorization and risk-tier rules.

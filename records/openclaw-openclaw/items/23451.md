## Summary

Keep open: current main still has lower-level plugin and exec approval primitives, but it does not implement the requested configurable response-level confirmation gate before risky same-response tool calls execute.

## What This Changes

The issue requests a disabled-by-default tool confirmation policy that can classify tool-call risk, flush assistant text, pause execution, and wait for explicit user approval before running risky tools.

## Best Possible Solution

Design a core confirmation policy that composes with existing plugin approvals, uses deterministic risk and current-turn authorization signals, flushes visible assistant text before holding tools, and documents approve, deny, timeout, transcript, and channel behavior with regression coverage.

Owner confidence: medium

Options:

- **Design core gate (recommended):** Approve a maintainer-led core design with disabled-by-default config, deterministic risk/current-turn authorization rules, explicit approve/deny/timeout behavior, and regression coverage around existing plugin approvals.
- **Keep plugin-only:** Leave core behavior unchanged and require operators to implement contextual approvals through `before_tool_call.requireApproval` or trusted tool policies, accepting that no built-in same-response confirmation gate exists.
- **Defer into broader policy work:** Wait for related action-level deny, response-gate, and HITL interrupt designs to settle into one authorization model before adding a new config surface.

## Reproduction Assessment

Yes, at source level: current main has no `tools.confirmation` type/schema and the tool execution path proceeds after existing lower-level hooks when they do not block. I did not run a destructive live scenario.

## Solution Assessment

Unclear until maintainers choose the policy; a runtime gate between parsed tool calls and execution is the right layer, but text-pattern auto-confirm should be constrained or replaced by deterministic risk/current-turn authorization signals.

## Label Justifications

- `P1`: The issue covers a broken safety workflow where same-response tool calls can perform sensitive actions before the user can answer an apparent confirmation question.
- `impact:data-loss`: Unconfirmed risky tool execution can modify or delete files/config/state before the user has a chance to decline.
- `impact:security`: The requested gate is a security/consent boundary for tool execution and side-effecting external actions.

## Summary

Keep open: current main still has plugin/exec approval primitives but no configurable core tool-confirmation gate that can inspect same-response assistant text before first tool execution.

## What This Changes

Request a disabled-by-default `tools.confirmation` policy that risk-classifies tool calls and can pause execution for human approval before running risky same-response tool calls.

## Best Possible Solution

Design a backward-compatible core confirmation gate that composes with plugin `before_tool_call.requireApproval`, trusted tool policies, exec approvals, streaming delivery, and transcript handling.

## Reproduction Assessment

Yes from source inspection for the missing capability: strict config schemas reject the proposed surface and the pre-tool hook/adapter path does not receive assistant text or hold execution.

## Solution Assessment

Partly: a runtime gate at the parsed-tool boundary is the right layer, but a durable solution should rely on deterministic risk classification rather than only natural-language question detection.

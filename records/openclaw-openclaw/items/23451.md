## Summary

Keep open: current main and the latest release still provide lower-level exec/plugin approval primitives, but not the requested configurable response-level confirmation gate that can inspect same-response assistant text before the first risky tool executes.

## What This Changes

Request a disabled-by-default `tools.confirmation` policy that pauses risky tool calls for human approval before execution.

## Best Possible Solution

Keep this open for a maintainer-designed core confirmation policy with deterministic risk semantics, schema/docs coverage, and regression tests around tool execution ordering and existing approval primitives.

## Reproduction Assessment

Yes, at source level: current main lacks `tools.confirmation` config/schema support, the pre-tool event lacks same-response assistant text, and unblocked tools execute after the lower-level hook path.

## Solution Assessment

Unclear until maintainers choose the security model; a core gate is likely the right layer for same-response tool calls, but it must not duplicate or bypass existing approval seams.

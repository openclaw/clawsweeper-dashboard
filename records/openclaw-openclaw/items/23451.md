## Summary

Keep open: current main and latest release still lack a built-in response-level `tools.confirmation` gate; existing exec and plugin approvals are adjacent primitives, not the requested configurable confirmation layer.

## What This Changes

Request a configurable tool confirmation gate that can pause risky model-proposed tool calls before execution and wait for explicit human approval.

## Best Possible Solution

Design a disabled-by-default core confirmation policy that composes with existing plugin and exec approvals, uses deterministic risk/current-turn authorization signals, flushes visible text before holding tools, and documents approve, deny, timeout, transcript, and channel behavior.

- **Keep Plugin-Only Approvals:** Leave core behavior unchanged and require operators or plugins to enforce contextual approval through `before_tool_call.requireApproval` or trusted tool policies.
- **Fold Into Broader Policy Work:** Wait for action-level deny, response-gate, and HITL interrupt designs to converge before adding another config surface.

## Reproduction Assessment

Yes, at source level: current main has no `tools.confirmation` type/schema and the tool execution path proceeds after existing lower-level policies when they do not block; I did not run a destructive live scenario.

## Solution Assessment

Unclear until maintainers choose the policy. A runtime gate between parsed tool calls and execution is the right layer, but the proposed text-pattern auto tier should be constrained or replaced with deterministic risk/current-turn authorization signals.

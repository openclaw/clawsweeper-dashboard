## Label Justifications

- `P1`: The issue describes side-effecting tool calls executing before a user can decline a same-response confirmation prompt in real agent/channel workflows.
- `impact:data-loss`: The missing gate can affect destructive file, config, and host actions that may modify or remove persisted user state.
- `impact:security`: The request is about enforcing a human authorization boundary before sensitive host, messaging, gateway, or credential-bearing tool calls execute.

## Summary

Keep open: current main still lacks the requested built-in, configurable tool-level confirmation gate. Existing exec approvals and plugin `before_tool_call.requireApproval` are useful lower-level primitives, but they do not provide a core risk-tier classifier, `tools.confirmation` config, or same-response assistant-text-aware hold before the first normal tool executes.

## What This Changes

The issue requests a configurable, runtime-enforced tool confirmation gate that can pause generated tool calls for human approval before execution.

## Best Possible Solution

Run a maintainer design pass for a backward-compatible core confirmation policy that composes with plugin `before_tool_call.requireApproval`, exec approvals, and trusted tool policies, with deterministic risk/authorization semantics and focused regression coverage.

## Reproduction Assessment

Yes, at source level. Current main has plugin/exec approval primitives and strict tool config schemas, but no `tools.confirmation` config or core same-response assistant-text-aware gate before the first normal tool executes.

## Solution Assessment

Unclear until maintainers choose the product and security model. A core gate is the right layer for the reported same-response problem, but the `auto` semantics should likely use deterministic authorization context rather than only text-pattern matching.

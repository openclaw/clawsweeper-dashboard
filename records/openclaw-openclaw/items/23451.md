## Label Justifications

- `impact:data-loss`: The issue explicitly covers destructive file/config operations that can modify or delete user data before consent.

## Summary

Keep open: current main still has exec and plugin approval primitives, but it does not provide the requested configurable core confirmation gate that can inspect same-response assistant text before the first risky tool executes.

## What This Changes

Request a configurable core tool-level confirmation gate that can pause risky tool execution for human approval before execution.

## Best Possible Solution

Design a backward-compatible core confirmation policy that composes with existing exec/plugin approvals, classifies tool/action risk deterministically, flushes visible assistant text before holding tools, and records explicit approve/deny/timeout outcomes for skipped calls.

## Reproduction Assessment

Yes, from source inspection: current main has hook/plugin/exec approval paths but no built-in tools.confirmation schema or same-response assistant-text-aware core gate before first tool execution. I did not run a live destructive-tool scenario in this read-only review.

## Solution Assessment

Yes in direction, but not as a narrow automatic patch: the right layer is a deterministic pre-execution gate, while the exact risk tiers, same-turn authorization heuristic, timeout behavior, and channel UX need maintainer product/security design.

## Label Justifications

- `P1`: The issue describes a high-impact agent/channel workflow gap where risky tool calls can execute before a user can deny the action.
- `impact:data-loss`: The reported class includes file writes/deletes and config edits that can mutate or lose user state before approval.

## Summary

Keep open: current main has lower-level exec and plugin approval primitives, but still lacks the requested built-in `tools.confirmation` schema/config surface and response-level gate that can inspect same-response assistant text before the first risky tool executes.

## What This Changes

Add a configurable, risk-aware tool confirmation gate that can pause tool execution for explicit user approval before risky calls run.

## Best Possible Solution

Design a backward-compatible core execution gate that composes with exec approvals and plugin `before_tool_call.requireApproval`, uses deterministic risk/intent classification, documents timeout/deny behavior, and preserves transcript/tool-result consistency.

## Reproduction Assessment

Yes, at source level: current schemas reject the proposed `tools.confirmation` surface and the pre-tool execution path has no same-response assistant-text gate before `tool.execute`. I did not run a live destructive scenario in this read-only review.

## Solution Assessment

Unclear: a built-in execution gate is the right layer, but the proposed natural-language question detector is likely not the final best shape. The safer solution is deterministic risk/intent classification that composes with existing plugin and exec approval mechanisms.

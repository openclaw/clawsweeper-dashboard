## Label Justifications

- `P1`: The issue targets a broken consent boundary that can let chat-channel agents perform sensitive tool effects before the user can decline.
- `impact:data-loss`: Unconfirmed write, edit, delete, config, or message-send tools can modify or remove user data before explicit approval.
- `impact:security`: The requested gate is about enforcing a human authorization boundary before side-effecting or sensitive tools run.

## Summary

Keep open: current main and v2026.6.11 still lack the requested built-in, configurable tool confirmation gate before execution. Existing `before_tool_call.requireApproval` and exec approvals are useful lower-level gates, but they do not provide a `tools.confirmation` config surface, risk-tier classifier, or response-level hold that can inspect same-response assistant text before the first tool executes.

## What This Changes

Request a configurable tool-level confirmation gate that can pause risky model-emitted tool calls for human approval before execution.

## Best Possible Solution

Design a backward-compatible core tool confirmation policy that classifies risky tool intents before execution, flushes user-visible text before holding tools, records explicit approve/deny/timeout outcomes, and preserves existing plugin and exec approval paths as lower-level mechanisms.

## Reproduction Assessment

Yes at source level. Current main has no `tools.confirmation` config/schema surface and the agent loop proceeds from a model-emitted tool-use message into prepared tool execution unless an existing lower-level hook blocks it; I did not run a destructive live repro.

## Solution Assessment

Unclear as proposed because the exact risk tiers and `auto` heuristic need maintainer security/product design. The maintainable direction is a deterministic pre-execution intent gate that composes with plugin approvals and exec approvals, not a prompt-only or text-pattern-only convention.

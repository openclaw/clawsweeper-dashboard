## Label Justifications

- `P1`: The issue describes a real safety gap where agents can execute destructive or externally visible tools before the user can answer a same-response confirmation question.
- `impact:data-loss`: The requested gate is meant to prevent unintended file writes, edits, deletes, and config mutations before execution.

## Summary

Keep open: current main has lower-level plugin and exec approval primitives, but still lacks the requested built-in configurable confirmation gate that can hold same-response tool execution before the first risky tool runs.

## What This Changes

The issue requests a configurable tool-level confirmation gate that pauses risky tool calls for explicit human approval before execution.

## Best Possible Solution

Keep this open for maintainer-owned core design: a disabled-by-default tools.confirmation surface, deterministic risk/current-turn authorization semantics, same-response text awareness, user-visible flush before hold, explicit approve/deny/timeout transcript handling, and regression coverage preserving existing plugin approvals.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction of the missing capability: tool-use messages are dispatched to executeToolCalls and the current config/schema has no tools.confirmation gate. I did not run a live model prompt that emits text plus a tool call in the same response.

## Solution Assessment

Partly. The execution-boundary confirmation gate is the right layer, but the proposed auto tier based mainly on assistant question text needs stronger deterministic authorization semantics before it is the best fix.

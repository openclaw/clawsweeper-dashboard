## Label Justifications

- `P1`: Risky same-response tool execution can affect real users through unintended file changes, outbound messages, gateway actions, or other side effects.
- `impact:data-loss`: The requested gate is meant to prevent destructive or mutating tool calls such as deletes, writes, edits, config changes, and restarts from executing before user consent.
- `impact:security`: The issue concerns the authorization boundary between model-proposed tool calls and host, channel, gateway, or credential-bearing execution.

## Summary

Keep open: current main still has exec and plugin approval primitives, but it does not implement the requested configurable response-level confirmation gate before risky same-response tool calls execute.

## What This Changes

The issue requests a configurable tool-level confirmation gate that can pause risky tool execution for human approval before execution.

## Best Possible Solution

Design a core confirmation policy that composes with existing plugin approvals, uses deterministic risk and current-turn authorization signals, flushes visible assistant text before holding tools, and documents approve, deny, timeout, transcript, and channel behavior with regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a built-in response-level tool confirmation gate, and what deterministic risk/current-turn authorization rules should decide allow, require-confirm, deny, and timeout behavior?

Rationale: Source inspection proves the requested gate is missing, but the permanent behavior defines a new core authorization boundary and config contract that automation cannot choose safely.

Likely owner: steipete

Owner reason: This decision spans security defaults, config compatibility, and the core agent execution loop, and prior review already routed it to core product/security design.

Owner confidence: medium

Options:

- **Design core confirmation gate (recommended):** Approve a maintainer-led core design with disabled-by-default config, deterministic risk/current-turn authorization rules, explicit approve/deny/timeout behavior, and regression coverage around existing plugin and exec approvals.
- **Keep plugin-only approvals:** Leave core behavior unchanged and require operators or plugins to implement contextual approvals through before_tool_call.requireApproval, accepting that no built-in same-response confirmation gate exists.
- **Fold into broader policy model:** Wait for related action-level deny, response-gate, HITL interrupt, and MCP consent work to settle into one authorization model before adding a new config surface.

## Reproduction Assessment

Yes, at source level: current main has no tools.confirmation type/schema and the tool execution path proceeds after existing lower-level hooks when they do not block. I did not run a destructive live scenario.

## Solution Assessment

Unclear until maintainers choose the policy; a runtime gate between parsed tool calls and execution is the right layer, but text-pattern auto-confirm should be constrained or replaced by deterministic risk/current-turn authorization signals.

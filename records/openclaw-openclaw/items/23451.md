## Label Justifications

- `P1`: The issue covers a high-impact agent/channel workflow gap where risky same-response tool calls can execute before the user can approve or deny.
- `impact:data-loss`: Unconfirmed write, edit, delete, or config tool execution can alter or remove user state before consent.
- `impact:security`: The request is about a runtime authorization and consent boundary before sensitive tool execution.

## Summary

Keep open. Current main has adjacent exec approvals and plugin `before_tool_call.requireApproval`, but it still lacks a built-in `tools.confirmation` policy, risk-tier classifier, same-response assistant-text-aware hold point, and transcript-safe approve/deny/timeout behavior before the first risky tool executes.

## What This Changes

Requests a configurable tool-confirmation layer that can pause risky tool calls for explicit human approval before execution.

## Best Possible Solution

Design a documented, backward-compatible `tools.confirmation` contract that classifies tool risk deterministically, can inspect same-response assistant text or intent evidence before execution, flushes visible text before holding risky tools, records approve/deny/timeout outcomes safely, and composes with existing plugin and exec approval primitives.

## Reproduction Assessment

Yes at source level. Current main lacks the requested `tools.confirmation` config/schema surface, and the before-tool event does not carry same-response assistant text needed for the proposed auto-confirm decision.

## Solution Assessment

Unclear until maintainers choose the security model. The right direction is a deterministic runtime confirmation/intent gate that reuses existing approval infrastructure, not a prompt-only instruction or a standalone natural-language question detector.

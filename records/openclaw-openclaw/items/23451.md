## Label Justifications

- `P1`: The issue describes a real agent/channel safety gap where risky tool calls can modify files, send messages, or execute host actions before a user can answer visible confirmation text.
- `impact:data-loss`: The missing gate can allow unintended file edits, deletes, or config mutations when the model emits a risky tool call alongside confirmation text.
- `impact:security`: The request is about enforcing a human-consent boundary before sensitive tool execution instead of relying on model narration or prompt compliance.

## Summary

Keep open: current main still has exec approvals, trusted tool policies, and plugin `before_tool_call.requireApproval`, but it does not provide the requested built-in `tools.confirmation` config, deterministic risk-tier classifier, or same-response assistant-text-aware hold before the first tool executes.

## What This Changes

The issue requests a configurable tool-level confirmation gate that can pause risky tool execution until human approval.

## Best Possible Solution

Define a backward-compatible core tool-confirmation design with deterministic risk classification, approve/deny/timeout behavior, transcript handling for skipped calls, docs/config/schema coverage, and regression tests that preserve existing plugin approval hooks.

## Reproduction Assessment

Yes, at source level. Current main lacks the requested `tools.confirmation` schema and the tool execution path proceeds after existing hook checks rather than using a response-level confirmation hold.

## Solution Assessment

Unclear until maintainers choose product/security semantics. A core confirmation gate is plausible, but it should use deterministic authorization and risk rules rather than relying only on natural-language question detection.

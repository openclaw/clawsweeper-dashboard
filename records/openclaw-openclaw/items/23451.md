## Label Justifications

- `P1`: The issue describes a real agent/channel safety gap where model-issued tool calls can modify files, send messages, or execute host actions before the user can answer a visible confirmation question.
- `impact:data-loss`: Without a hard confirmation boundary, model-issued file edits, deletes, or config mutations can alter persisted user data before consent.
- `impact:security`: The requested work is about enforcing a human-consent boundary before sensitive tool execution instead of relying on model narration or prompt compliance.

## Summary

Keep open: current main still has lower-level plugin approval hooks and exec approvals, but not the requested built-in `tools.confirmation` config, deterministic risk-tier classifier, or response-level hold before the first risky tool executes.

## What This Changes

The issue requests a configurable built-in confirmation gate that can pause risky tool calls before execution based on risk tiers and human approval.

## Best Possible Solution

Define a backward-compatible core confirmation design with deterministic risk classification, approve/deny/timeout behavior, transcript handling for skipped tool calls, config/docs/schema coverage, and regression tests that preserve existing approval hooks.

## Reproduction Assessment

Yes, at source level. Current main has strict config schemas without `tools.confirmation`, lower-level approval hooks only, and tool execution proceeds after existing hook checks without a built-in response-level confirmation wait.

## Solution Assessment

Unclear until maintainers choose the product and security semantics. A core confirmation gate is a plausible right layer, but the proposed natural-language question heuristic should be constrained by deterministic authorization and risk-tier rules.

## Summary

Keep open: current main and the latest release still have lower-level exec/plugin approval primitives, but no built-in configurable confirmation gate that can hold risky same-response tool calls before execution.

## What This Changes

The issue requests a configurable tool-level confirmation gate with risk tiers, approval/deny/timeout behavior, and same-response assistant-text awareness before tool execution.

## Best Possible Solution

Design a core confirmation policy that composes with existing plugin and exec approval paths, uses deterministic risk/current-turn authorization signals, flushes visible assistant text before holding tools, and documents approve, deny, timeout, transcript, and channel behavior with regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a built-in response-level tool confirmation gate, and what deterministic risk/current-turn authorization rules should decide allow, require-confirm, deny, and timeout behavior?

Rationale: Source inspection proves the gate is missing, but the permanent behavior defines a new authorization boundary and config contract across agent execution, tools, approvals, channels, Gateway scope, denial, timeout, and transcript handling.

Likely owner: steipete

Owner reason: This decision spans security defaults, config compatibility, and the core agent execution loop, and prior live review already routed it to core product/security design.

Owner confidence: medium

Options:

- **Design core confirmation gate (recommended):** Add a disabled-by-default core gate with deterministic risk/current-turn authorization rules, explicit approve/deny/timeout behavior, and tests proving composition with existing plugin and exec approvals.
- **Keep policy plugin-only:** Leave core behavior unchanged and require operators to implement contextual confirmation through before_tool_call.requireApproval or trusted tool policies, accepting that no built-in same-response gate exists.
- **Defer into broader policy model:** Wait for the related action-level deny, response-gate, and HITL interrupt designs to settle before adding a new config surface.

## Reproduction Assessment

Yes, at source level: current main has no tools.confirmation type/schema and the tool execution path proceeds after existing lower-level hooks when they do not block. I did not run a destructive live scenario.

## Solution Assessment

Unclear until maintainers choose the policy. A runtime gate between parsed tool calls and execution is the right layer, but the natural-language auto tier should be constrained or replaced by deterministic risk/current-turn authorization signals.

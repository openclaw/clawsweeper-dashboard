## Label Justifications

- `P1`: Same-response tool execution can affect real agent/channel users by running unintended file, exec, message, gateway, or other side-effecting actions before consent.
- `impact:data-loss`: The requested gate is meant to prevent destructive or mutating tool calls such as deletes, writes, edits, config changes, and restarts from executing before user approval.
- `impact:security`: The issue concerns the authorization boundary between model-proposed tool calls and host, channel, gateway, or credential-bearing execution.

## Summary

Keep open: current main and v2026.6.11 still lack a built-in configurable response-level tool confirmation gate; existing exec and plugin approvals are lower-level primitives, and the only direct PR attempt was closed unmerged as an unmergeable branch.

## What This Changes

Request a configurable risk-aware runtime gate that can pause same-response tool calls until the user explicitly approves or denies execution.

## Best Possible Solution

Design a core confirmation policy that composes with existing approval primitives, uses deterministic risk and current-turn authorization signals, flushes visible assistant text before holding tools, and documents approve, deny, timeout, transcript, and channel behavior with regression coverage.

## Reproduction Assessment

Yes, at source level: current main has no tools.confirmation type/schema and the tool execution path proceeds after existing lower-level hooks when they do not block. I did not run a destructive live scenario.

## Solution Assessment

Unclear until maintainers choose the policy. A runtime gate between parsed tool calls and execution is the right layer, but the proposed text-pattern auto tier should be constrained or replaced with deterministic risk and current-turn authorization signals.

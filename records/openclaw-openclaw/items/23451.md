## Label Justifications

- `P1`: The issue describes a real agent/channel safety gap where model-issued tool calls can modify files, send messages, or execute host actions before the user can answer a visible confirmation question.
- `impact:data-loss`: The missing gate can allow unintended file edits, deletes, or config mutations when the model emits a risky tool call alongside confirmation text.
- `impact:security`: The request is about enforcing a human-consent boundary before sensitive tool execution instead of relying on model narration or prompt compliance.

## Summary

Keep open: current main still has plugin `before_tool_call.requireApproval`, trusted policies, and exec approvals, but no built-in `tools.confirmation` config, response-level risk classifier, or same-response assistant-text-aware hold before the first tool executes.

## What This Changes

Request a configurable tool-level confirmation gate that can pause generated tool calls before execution based on tool risk and user-confirmation context.

## Best Possible Solution

Define a backward-compatible core tool-confirmation design with deterministic risk classification, approve/deny/timeout behavior, transcript handling for skipped calls, docs/config/schema coverage, and regression tests that preserve existing plugin approval hooks.

## Reproduction Assessment

Yes, at source level. Current main has strict config schemas without `tools.confirmation`, a before-tool hook event without assistant text, and tool execution continues immediately after existing hook approval/block checks.

## Solution Assessment

Unclear until maintainers choose the product/security semantics. A core confirmation gate is a plausible right layer, but the text-question heuristic should be replaced or constrained by deterministic authorization and risk-tier rules.

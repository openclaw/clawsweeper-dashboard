## Label Justifications

- `P1`: The issue describes a real agent/channel safety gap where model-issued tool calls can modify files, send messages, or execute host actions before the user can answer visible confirmation text.
- `impact:data-loss`: The missing gate can allow unintended file edits, deletes, or config mutations when a model emits a risky tool call alongside confirmation text.
- `impact:security`: The request is about enforcing a human-consent boundary before sensitive tool execution rather than relying on prompt compliance or model narration.

## Summary

Keep open: current main still has plugin `before_tool_call.requireApproval`, trusted tool policies, and exec approvals, but it still lacks the requested built-in `tools.confirmation` config, core risk-tier classifier, and same-response assistant-text-aware hold before the first tool executes.

## What This Changes

Request a configurable core tool confirmation gate that can pause risky tool calls for human approval before execution.

## Best Possible Solution

Define a backward-compatible core tool-confirmation design with deterministic risk classification, approve/deny/timeout behavior, transcript handling for skipped calls, docs/schema coverage, and regression tests that preserve existing plugin approval hooks.

## Reproduction Assessment

Yes, at source level. Current main has strict config schemas without `tools.confirmation`, a before-tool hook event without assistant text, and tool execution continues immediately after existing hook approval/block checks.

## Solution Assessment

Unclear until maintainers choose the product/security semantics. A core confirmation gate is a plausible right layer, but the proposed text-question heuristic needs deterministic authorization and risk-tier rules before implementation.

## Label Justifications

- `P1`: The issue targets risky same-response tool execution that can affect real users through unintended file changes, outbound messages, or other side effects.
- `impact:data-loss`: The proposed gate is meant to prevent destructive or mutating tool calls such as deletes, writes, edits, config changes, and restarts from executing before user consent.
- `impact:security`: This is about the authorization boundary between model-proposed tool calls and host/channel execution for sensitive actions.

## Summary

Keep open: current main still has lower-level plugin and exec approval primitives, but it does not implement the requested built-in, configurable, response-level tool confirmation gate before the first risky tool executes.

## What This Changes

The issue requests a configurable tool-level confirmation gate that can pause risky tool calls before execution when assistant text asks for user confirmation.

## Best Possible Solution

Design a core tool-execution confirmation policy that composes with plugin requireApproval, uses deterministic risk/intent signals where possible, flushes assistant text before holding tools, and documents deny/timeout/transcript/channel behavior with config-schema coverage.

## Reproduction Assessment

Yes, as a source-level reproduction: current main has no tools.confirmation type/schema and the agent loop proceeds from a tool-use assistant message into tool execution without a built-in response-level confirmation gate. I did not run a live destructive scenario because the missing feature is clear from source inspection.

## Solution Assessment

Unclear: a runtime gate between parsed tool calls and execution is the right layer, but the proposed natural-language auto tier needs product/security design. A safer solution should lean on deterministic risk and current-turn authorization signals while preserving the existing plugin approval seam.

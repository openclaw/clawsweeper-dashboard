## Label Justifications

- `P1`: The issue targets risky same-response tool execution that can affect real users through unintended file changes, outbound messages, or other side effects.
- `impact:data-loss`: The requested gate is meant to prevent destructive or mutating tool calls such as deletes, writes, edits, config changes, and restarts from executing before user consent.

## Summary

Keep open: current main still has lower-level exec and plugin approval primitives, but it does not implement the requested built-in configurable confirmation gate before the first risky same-response tool call executes.

## What This Changes

Add a configurable core tool confirmation gate that can pause risky tool calls before execution and wait for human approval based on tool risk or same-response intent.

## Best Possible Solution

Design a core tool-execution confirmation policy that composes with existing plugin and exec approvals, uses deterministic risk and intent signals where possible, and documents deny, timeout, transcript, and channel behavior with schema and regression coverage.

## Reproduction Assessment

Yes, as a source-level reproduction: current main has no tools.confirmation type/schema and the agent loop proceeds from a tool-use assistant message into tool execution without a built-in response-level confirmation gate. I did not run a live destructive scenario because the missing feature is clear from source inspection.

## Solution Assessment

Unclear: a runtime gate between parsed tool calls and execution is the right layer, but the proposed natural-language auto tier needs product and security design. A safer solution should lean on deterministic risk and current-turn authorization signals while preserving the existing plugin approval seam.

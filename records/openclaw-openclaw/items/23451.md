## Label Justifications

- `P1`: The issue describes a high-risk agent/tool workflow where normal tool calls can mutate files or send messages before the user can answer an apparent confirmation question.
- `impact:data-loss`: The requested gate targets destructive or mutating tool calls such as deletes, edits, and config changes that can alter user state without explicit consent.
- `impact:security`: The issue is about enforcing a security boundary between model-proposed actions and host/channel execution rather than relying on model text conventions.

## Summary

Keep open: current main has exec approvals and plugin-controlled `before_tool_call.requireApproval`, but it still lacks the requested built-in `tools.confirmation` config, deterministic risk-tier classifier, and same-response assistant-text gate before the first tool executes.

## What This Changes

Request a configurable core tool confirmation gate that can pause risky tool calls for human approval before execution.

## Best Possible Solution

Design a backward-compatible core confirmation policy that sits between parsed tool calls and execution, composes with plugin `requireApproval` and exec approvals, flushes visible assistant text before holding tools, and records approve/deny/timeout outcomes in transcript state.

## Reproduction Assessment

Yes, at source level: current main has no accepted `tools.confirmation` schema/config and the pre-tool hook event lacks same-response assistant text. I did not run a live destructive-agent scenario because the missing gate is directly visible in the source path.

## Solution Assessment

Unclear as proposed: the core need is real, but the exact `auto` heuristic based on assistant text needs maintainer security/product design. A safer direction is a deterministic intent/authorization gate that composes with existing plugin and exec approval primitives.

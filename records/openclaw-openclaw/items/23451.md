## Label Justifications

- `P1`: The issue describes a real agent/channel safety gap where model-issued tool calls can modify files, send messages, or run host actions before the user can answer a visible confirmation question.
- `impact:data-loss`: Without a hard gate, same-response tool calls can cause unintended file edits, deletes, config mutations, or other state changes before human consent.
- `impact:security`: The request is about enforcing a human-consent boundary before sensitive tool execution instead of relying on prompt compliance or assistant narration.

## Summary

Keep open: current main still has lower-level plugin `before_tool_call.requireApproval`, trusted tool policies, and exec approvals, but it does not provide the requested built-in `tools.confirmation` config, response-level risk classifier, or same-response assistant-text-aware hold before the first tool executes.

## What This Changes

The issue requests a configurable tool-level confirmation gate that can pause risky tool calls for human approval before execution.

## Best Possible Solution

Define a backward-compatible core tool-confirmation design with deterministic risk classification, approve/deny/timeout behavior, transcript handling for skipped calls, docs/config/schema coverage, and regression tests that preserve existing plugin approval hooks.

## Reproduction Assessment

Yes, at source level. Current main lacks the proposed config/schema surface, the pre-tool hook does not carry same-response assistant text, and tool execution proceeds immediately after the existing hook approval/block checks.

## Solution Assessment

Unclear until maintainers choose the product/security semantics. A core confirmation gate is a plausible right layer, but the naive text-question heuristic should be replaced or constrained by deterministic authorization and risk-tier rules.

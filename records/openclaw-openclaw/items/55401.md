## What This Changes

Request to add per-agent plugin configuration overrides for multi-agent setups so different agents can use different plugin config, credentials, accounts, or memory scopes.

## Best Possible Solution

Define a maintainer-approved agent-scoped plugin config contract with precedence, SecretRef/redaction, manifest/schema validation, lifecycle/restart behavior, doctor/upgrade rules, docs, and two-agent regression coverage.

Rationale: The request would let different agents use different plugin credentials and state boundaries, so automation cannot safely choose the permanent security and compatibility contract from source evidence alone.

Likely owner: Peter Steinberger

Owner confidence: high

Options:

- **Design generic agent-scoped plugin config (recommended):** Add a shared core/plugin SDK contract for per-agent plugin config with explicit merge precedence, SecretRef handling, schema validation, restart semantics, and migration/docs coverage.
- **Keep plugin config global:** Leave `plugins.entries` global and solve memory/wiki/provider needs through plugin-owned agent maps or dedicated plugin settings, reducing core surface but fragmenting operator UX.
- **Defer to per-agent installation:** Treat independent installs as the isolation boundary and route this issue behind the per-agent install design, trading config simplicity for a larger lifecycle/install change.

## Reproduction Assessment

Yes. At source level, current main and v2026.6.11 reject `agents.list[].plugins` through the strict agent schema and resolve plugin config only from global `plugins.entries[id].config`.

## Solution Assessment

Unclear. The requested deep-merge model is plausible, but the best fix needs maintainer decisions on precedence, SecretRef/redaction, validation, plugin lifecycle, restart behavior, and whether generic per-agent config or plugin-specific scoping owns each use case.

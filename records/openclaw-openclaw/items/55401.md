## Summary

Keep open: current main and v2026.6.11 still expose plugin configuration only as global `plugins.entries.<id>.config`, while the issue discussion shows real multi-agent credential, memory, and capability isolation needs that require a maintainer-owned product/security contract before implementation.

## What This Changes

The issue requests per-agent plugin configuration overrides so multi-agent gateways can give the same plugin different config, credentials, and state per agent.

## Best Possible Solution

Define a maintainer-approved agent-scoped plugin config contract with precedence, SecretRef/redaction, manifest/schema validation, lifecycle/restart behavior, doctor/upgrade rules, docs, and two-agent regression coverage.

Options:

- **Design generic agent-scoped plugin config (recommended):** Add a shared core/plugin SDK contract for per-agent plugin config with explicit merge precedence, SecretRef handling, schema validation, restart semantics, and migration/docs coverage.
- **Keep config global and solve narrower plugins:** Leave `plugins.entries` global and handle memory/wiki/provider needs through plugin-owned agent maps or dedicated plugin settings, reducing core surface but fragmenting operator UX.
- **Defer to per-agent plugin installation:** Treat independent installs as the isolation boundary and route this issue behind the per-agent install design, trading config simplicity for a larger lifecycle/install change.

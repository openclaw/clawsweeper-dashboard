## Label Justifications

- `P2`: The issue causes avoidable prompt contamination and recurring token cost in multi-session setups, but operators can disable passive digest injection and use explicit wiki tools.
- `impact:session-state`: A compiled memory digest intended for an interactive session can still be injected into unrelated tactical cron sessions.

## Summary

Current main completed the agent/session context plumbing and per-agent digest selection, but Memory Wiki still has no session/channel inclusion policy, so the reported Telegram-versus-cron prompt contamination remains. The next step is a bounded but compatibility-sensitive product choice about whether filtering belongs only to Memory Wiki or becomes a generic plugin SDK policy.

## What This Changes

Requests per-agent or per-session-key scoping for Memory Wiki compiled-digest prompt injection and generic memory prompt supplements.

## Best Possible Solution

Memory Wiki should apply an opt-in include/exclude policy to the already-provided `agentSessionKey` before reading or appending its digest, with exclusions taking precedence, unchanged default behavior, aligned schema/manifest/docs, and Telegram-versus-cron regression coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should session/channel inclusion rules be owned by Memory Wiki configuration, or standardized as a policy for every registered memory prompt supplement?

Rationale: Both designs are technically possible now, but a generic policy creates a lasting public SDK/config commitment without evidence that another supplement needs the same abstraction.

Likely owner: steipete

Owner reason: They own the most recent cross-surface groundwork and explicitly framed this narrower unresolved policy decision.

Owner confidence: high

Options:

- **Keep policy in Memory Wiki (recommended):** Add documented include/exclude session-key rules under Memory Wiki context configuration while leaving the generic builder contract contextual but policy-neutral.
- **Standardize supplement policy:** Define reusable inclusion semantics for every memory prompt supplement and accept the broader plugin SDK and configuration contract.

## Reproduction Assessment

Yes, at source level: enable the compiled digest and build prompts for the same agent's Telegram and cron session keys; both reach a Memory Wiki builder that ignores `agentSessionKey`. This read-only review did not run a live prompt capture.

## Solution Assessment

No, the issue's generic SDK-policy option is not the best-supported first fix. Plugin-owned filtering is narrower and more maintainable because core already supplies all required context and no second supplement demonstrates a shared policy need.

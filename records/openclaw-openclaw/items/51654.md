- `impact:security`: The request is about passing API keys or endpoint credentials into spawned ACP subprocess environments.

- `impact:auth-provider`: The primary examples involve provider API keys, provider endpoints, and model/provider isolation for ACP sessions.

## Summary

Keep open: current main and the latest release still lack a `sessions_spawn.env` parameter or an ACP manager bridge that passes per-session environment variables into ACP harness startup. The related per-agent and per-call env items overlap, but they do not implement this credential-bearing per-spawn ACP API, so the remaining blocker is maintainer security/product direction.

## What This Changes

Request adding per-spawn environment variables to ACP sessions created through `sessions_spawn`, so individual ACP harness processes can receive overridden credentials or endpoints.

## Best Possible Solution

Choose one security-reviewed env-injection contract for ACP spawns, preferably operator-controlled or explicitly redacted, then wire it through `sessions_spawn`, ACP spawn, manager initialization, runtime validation, docs, and regression tests without duplicating the per-agent/per-call env surfaces.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose per-spawn ACP environment variables through the model-callable `sessions_spawn` tool, or keep credential env injection on an operator-controlled surface such as configured agent env or trusted gateway/API input?

Rationale: This changes how credentials reach subprocesses and may expose secrets through model-visible tool arguments, transcripts, logs, or persisted session metadata unless maintainers choose the trust boundary first.

Likely owner: steipete

Owner reason: He introduced `sessions_spawn` and is the clearest routing owner for the product/security boundary around a model-callable session-spawn surface.

Owner confidence: high

Options:

- **Prefer operator-controlled env (recommended):** Keep raw credential values out of model-callable `sessions_spawn` and use per-agent config or a trusted non-model-visible gateway/API path for env injection.
- **Add guarded `sessions_spawn.env`:** Expose the requested tool parameter only with strict env-name validation, redaction, transcript handling, and clear docs about the secret exposure model.
- **Defer to adjacent env work:** Wait for the per-agent env PR and per-call sandbox-env discussion to settle before deciding whether ACP needs a separate session-level API.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction of the missing capability: current `sessions_spawn` schema and ACP spawn forwarding have no env field, and the manager does not pass env into `runtime.ensureSession`. I did not run a live ACP harness because the absence is visible at the public tool/schema boundary.

## Solution Assessment

Unclear: the requested `sessions_spawn.env` parameter is a plausible implementation path, but it may not be the safest boundary for credentials because the model supplies tool arguments. A maintainer should choose between model-visible per-spawn env, configured per-agent env, or a trusted non-model-visible API path before implementation.

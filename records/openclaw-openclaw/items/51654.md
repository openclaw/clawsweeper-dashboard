## Label Justifications

- `P2`: This is a real ACP API gap with security implications, but it needs product/security design rather than urgent runtime repair.
- `impact:session-state`: The requested env map would make ACP subprocess environment state session-scoped and affect isolation, reuse, and initialization semantics.
- `impact:security`: The issue explicitly proposes passing API keys and endpoint overrides into host ACP harness subprocesses.
- `impact:auth-provider`: The requested use cases involve per-session provider credentials, base URLs, model/provider isolation, and auth routing.

## Summary

Keep open: current main and the latest release still lack a public `sessions_spawn.env` path for ACP sessions. The related per-agent and per-call env work is useful context, but it does not settle this credential-bearing per-spawn ACP API.

## What This Changes

Request adding a session-level env map to `sessions_spawn` for ACP/acpx sessions so per-spawn credentials and endpoint settings can override inherited gateway environment.

## Best Possible Solution

Define one maintainer-approved ACP session env contract, including source of trust, validation, redaction, persistence/reuse semantics, and ACPX adapter mapping, or explicitly route users to configured per-agent env and SecretRef/operator-trusted mechanisms instead.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose a per-spawn `sessions_spawn.env` map for ACP sessions, and if so what credential boundary should govern it?

Rationale: The requested API can carry secrets into host ACP harness subprocesses and overlaps with open per-agent and per-call env designs, so implementation should not proceed until maintainers choose the permanent boundary.

Likely owner: steipete

Owner reason: The question is product/security policy for an ACP and credential boundary, and steipete has adjacent merger/reviewer history plus issue discussion routing.

Owner confidence: medium

Options:

- **Design a constrained per-spawn ACP env contract (recommended):** Allow the capability only with explicit validation, blocked key filtering, redaction, docs, and tests across tool schema, ACP manager, ACPX, and session reuse.
- **Route callers to configured per-agent env:** Treat per-spawn env as too risky and let https://github.com/openclaw/openclaw/pull/96229 or its successor cover operator-configured subprocess env instead.
- **Defer to broader per-call secret injection design:** Keep this issue open behind https://github.com/openclaw/openclaw/issues/80329 until the trusted-caller secret delivery model is chosen.

## Reproduction Assessment

Yes. Source inspection of current main and `v2026.6.11` shows no `sessions_spawn.env` parameter and no env forwarding through ACP spawn, manager initialization, or ACPX session options.

## Solution Assessment

No, not as a raw env-map patch alone. The maintainable path needs a maintainer-approved credential boundary for validation, redaction, source of trust, persistence/reuse behavior, and interaction with inherited-env scrubbing.

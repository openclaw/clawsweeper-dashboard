## What This Changes

The issue reports a latent Codex app-server bound-thread subscription leak when missing-thread recovery creates a replacement thread and the retrying bound turn rejects.

## Best Possible Solution

Define the Codex bound-thread subscription lifecycle, then implement retry-failure cleanup with reattach-or-persist semantics and focused regression coverage for consecutive bound turns.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Codex app-server conversation bindings keep a persistent subscription between bound turns, or should each bound turn explicitly reattach and then unsubscribe in cleanup?

Rationale: Both choices can be valid, but the code change is unsafe without maintainer intent because naive unsubscribe fixes the reported leak while risking follow-up message delivery for saved bound threads.

Likely owner: steipete

Owner reason: steipete committed the recovery behavior and has adjacent Codex app-server lifecycle history in the affected paths.

Owner confidence: high

Options:

- **Per-turn reattach and cleanup (recommended):** Before each bound turn, explicitly ensure the app-server connection is subscribed to the saved thread, then best-effort unsubscribe in finally so retry failures cannot strand subscriptions.
- **Persistent binding subscription:** Treat the subscription as part of the active conversation binding lifecycle, document that the replacement thread remains subscribed, and close or narrow this report to detach/unbind cleanup only.
- **Target only failed replacement threads:** Clean up only replacement-thread retry failures and add a follow-up guard so the next bound turn can reattach or fail with a clear recovery path.

## Reproduction Assessment

Yes, at source level: current main can enter missing-thread recovery, create a replacement Codex thread, and retry the turn without cleanup around that replacement-thread retry. No live hosted Codex orphan-count reproduction was established.

## Solution Assessment

Unclear until the maintainer selects the subscription lifecycle. The best repair should either preserve persistent delivery intentionally or reattach before every bound turn and unsubscribe afterward.

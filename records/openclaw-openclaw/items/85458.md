## Summary

Keep this open: current main and the latest release still have the missing-thread recovery path creating a replacement Codex app-server thread and then directly retrying the bound turn, while the linked fix attempts are closed unmerged and one broad unsubscribe approach carried a follow-up delivery risk.

## What This Changes

The issue reports a source-level Codex app-server bound-thread lifecycle leak when missing-thread recovery creates a replacement thread and the retry then rejects.

## Best Possible Solution

Define the bound-thread subscription lifecycle, then implement recovery-retry cleanup that covers rejection after replacement-thread creation while preserving consecutive bound-turn delivery.

## Reproduction Assessment

Yes at source level: current main can enter missing-thread recovery, create a replacement Codex thread, and retry the turn without cleanup around that replacement-thread retry. No live hosted Codex orphan-count reproduction was provided or run.

## Solution Assessment

No linked solution is clearly best yet: the cleanup primitive exists, but unconditional per-turn unsubscribe was shown to risk follow-up bound-turn delivery. The safer solution needs an explicit persistent-subscription versus reattach-before-turn decision.

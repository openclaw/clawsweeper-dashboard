## Summary

Keep this open: current main and v2026.6.11 still retry the recreated Codex app-server bound thread without a cleanup or reattach decision, and the related fix PRs are closed unmerged rather than safe canonical fixes.

## What This Changes

This issue asks OpenClaw to avoid leaving a newly recreated Codex app-server bound thread subscribed when missing-thread recovery retries and the retry fails.

## Best Possible Solution

Define the Codex app-server bound-thread subscription lifecycle, then implement retry-failure cleanup with regression coverage for both failed recovery and consecutive bound turns.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Codex app-server conversation bindings keep a persistent subscription across turns, or should OpenClaw reattach before each bound turn and unsubscribe after each turn or failure?

Rationale: The source issue is clear, but the repair changes subscription ownership for persistent bound conversations, and prior cleanup attempts showed that unconditional unsubscribe can break follow-up delivery.

Likely owner: steipete

Owner reason: steipete is tied to the original recovery commit as committer and to adjacent Codex app-server lifecycle work, making them the best available owner for the lifecycle direction call.

Owner confidence: medium

Options:

- **Reattach Before Each Turn (recommended):** Make each bound turn explicitly attach or resume the Codex app-server listener before turn/start, then allow cleanup on success and failure with two-turn regression coverage.
- **Keep Persistent Subscription:** Treat the retained subscription as intentional lifecycle state, document or test that contract, and only clean up when the binding itself is cleared or abandoned.
- **Clear Binding On Retry Failure:** On replacement retry rejection, unsubscribe and clear or mark the saved binding so the next inbound message creates a fresh thread instead of using an unsubscribed one.

## Reproduction Assessment

Yes at source level: current main can enter missing-thread recovery, create a replacement Codex thread, and retry the turn without cleanup around that replacement-thread retry. No live hosted Codex orphan-count reproduction was provided or run.

## Solution Assessment

No linked solution is currently best: the cleanup primitive exists, but prior unconditional unsubscribe attempts risk breaking later bound-turn delivery without an explicit reattach or persistence decision.

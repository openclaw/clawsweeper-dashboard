## What This Changes

Request to prevent a potential Codex app-server bound-thread subscription leak when missing-thread recovery creates a replacement thread and the retry rejects.

## Best Possible Solution

Codify the bound-thread subscription lifecycle, then either prove replacement subscriptions are intentionally persistent or implement reattach/cleanup with regression coverage for retry failure and consecutive bound turns.

Options:

- **Preserve persistent subscriptions (recommended):** Treat the replacement thread subscription as intentional session state unless the binding is cleared, and add tests/documentation that make this lifecycle explicit before closing or narrowing the issue.
- **Use per-turn reattach and cleanup:** Change bound turns to reattach before each `turn/start` and unsubscribe after completion or rejection, with regression tests for two consecutive bound turns and retry failure.
- **Narrow cleanup to failed recovery only:** Only clean up the replacement thread when maintainers decide a failed retry should not leave a reusable binding, and cover that behavior with focused tests.

## Solution Assessment

No current linked solution is clearly best: the cleanup primitive exists, but the prior unconditional unsubscribe approach risks later bound-turn delivery unless reattach or persistent-subscription semantics are settled.

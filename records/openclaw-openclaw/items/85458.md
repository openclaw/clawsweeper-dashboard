## Summary

Keep this open: current main and v2026.6.11 still call `startCodexConversationThread` during missing-thread recovery and then directly await the retrying `runBoundTurn`, while Codex upstream auto-subscribes `thread/start` connections and uses `thread/unsubscribe` to release that subscription. The linked cleanup PRs are closed unmerged, so a maintainer still needs to settle the bound-thread subscription lifecycle before a safe fix.

## What This Changes

The issue asks OpenClaw to prevent a Codex app-server replacement thread spawned during missing-thread recovery from being left subscribed when the retrying bound turn rejects.

## Best Possible Solution

Define the Codex app-server bound conversation subscription owner, then patch missing-thread recovery so replacement threads are either unsubscribed on retry failure or intentionally retained with tested reattach/sweeper semantics.

## Summary

Keep this open: current main and v2026.6.11 still have the direct Codex missing-thread recovery retry after replacement thread creation, while the closed fix attempts are not safe canonical fixes for the remaining bound-thread lifecycle question.

## What This Changes

The issue reports a source-level potential session-state leak when Codex missing-thread recovery starts a replacement app-server thread and the retry fails before cleanup.

## Best Possible Solution

Define the intended bound-thread subscription lifecycle, then implement cleanup that covers replacement-retry failure while preserving consecutive bound-turn delivery with focused regression coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Codex app-server bound conversation threads keep a persistent subscription across turns, or should OpenClaw reattach before each bound turn and unsubscribe after every turn including failed recovery retries?

Rationale: Both source and Codex contract evidence show that cleanup is possible, but changing subscription ownership can either leak loaded threads or break later bound-turn notifications unless maintainers choose the lifecycle contract.

Likely owner: steipete

Owner reason: steipete is tied to the recovery commit as committer and to adjacent app-server lifecycle cleanup work.

Owner confidence: medium

Options:

- **Reattach before each turn (recommended):** Make bound turns explicitly reattach or resume before turn/start, then unsubscribe in all terminal paths including recovery retry failure, with two-consecutive-turn coverage.
- **Keep persistent subscriptions:** Treat the current persistent subscription as intentional for conversation bindings and limit the issue to documentation or observability around loaded thread lifetime.
- **Clear failed replacement binding:** On replacement retry failure, clear the saved binding so the next inbound creates a fresh subscribed thread, accepting loss of continuity after that failure.

## Reproduction Assessment

Yes at source level: current main can enter missing-thread recovery, create a replacement Codex thread, and retry the turn without cleanup around that replacement-thread retry. No live hosted Codex orphan-count reproduction was provided or run.

## Solution Assessment

No current linked solution is clearly best: the cleanup primitive is available, but unconditional per-turn unsubscribe was already shown to risk later bound-turn delivery. The safer solution needs an explicit persistent-subscription versus reattach-before-turn decision.

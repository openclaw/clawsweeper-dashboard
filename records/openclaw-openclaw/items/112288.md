## Summary

Keep this PR open for maintainer security-boundary review. The guard fixes the proposed raw-header scenario, but it also removes the documented configuration-free direct LAN/Tailnet Control UI path for every non-loopback socket; the PR does not establish that a standards-compliant browser can create the claimed attacker-controlled Host-and-Origin CSRF request.

## What This Changes

The PR makes gateway browser-origin checks reject private-IP, `.local`, and `.ts.net` Host-derived same-origin matches whenever the connecting client is not local, while documenting explicit allowlist and dangerous-fallback alternatives.

## System Context

Gateway browser connections pass an Origin header, request host, configured allowlist, and client-locality signal into the origin policy before the Control UI connection is accepted or rejected. The changed helper is the compatibility boundary for direct LAN and Tailnet Control UI access as well as reverse-proxy deployments.

## Best Possible Solution

Preserve the documented direct private-network Control UI behavior unless maintainers confirm a browser-reproducible exploit; if they choose a stricter policy, ship an explicit upgrade plan and prove both direct-LAN and reverse-proxy behavior on a real gateway.

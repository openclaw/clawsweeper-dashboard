## Summary

Keep open: current main and v2026.6.11 still allow paths-only browser upload arming, and the Browser agent file-chooser client still wraps `/hooks/file-chooser` with a fixed 20s outer timeout. Merged selector/batch work helps adjacent stale-ref workflows, but it does not settle the upload contract or prove the dynamic-page timeout/stale-ref behavior is fixed.

## What This Changes

The issue asks for browser file chooser uploads to prefer an atomic upload-and-trigger flow and to keep stale-click or action-timeout errors specific instead of reporting a browser-control outage.

## Best Possible Solution

Make the Browser upload contract explicit: preserve paths-only arming with correct timeout/error semantics or steer agent/tool uploads to the existing atomic ref/inputRef/element path, then cover the chosen behavior with Browser plugin tests and live dynamic-page proof.

Question: Should Browser upload keep paths-only arm-then-later-click as a supported API, or should agent/tool flows be moved toward atomic upload-with-trigger behavior for dynamic pages?

Rationale: Both behaviors are currently supported and tested; changing the default could improve reliability but may affect callers that intentionally arm a chooser before a later trigger.

Likely owner: steipete

Options:

- **Compatibility-first atomic preference (recommended):** Keep paths-only arming supported, but update agent/tool guidance and timeout/error handling to prefer the existing atomic trigger path with focused tests and live proof.
- **Retire paths-only arming:** Require a trigger ref/inputRef/element or direct input selector for upload, with migration guidance for callers that depended on delayed triggering.
- **Document current workaround:** Leave runtime behavior unchanged and document stale-ref recovery plus selector/batch mitigations, accepting that the underlying flake remains possible.

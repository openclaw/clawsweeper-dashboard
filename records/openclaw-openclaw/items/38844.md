## Summary

Keep open: current main partially fixes local dispatcher timeout wording, but the current and latest shipped Browser upload client still allow paths-only arming with a fixed 20s outer `/hooks/file-chooser` timeout, and the atomic upload-trigger contract needs maintainer direction plus live dynamic-page proof.

## What This Changes

The issue asks for browser upload/file chooser flows to avoid stale split upload/click failures and preserve action-specific timeout errors instead of reporting healthy browser control as unreachable.

## Best Possible Solution

Make the Browser upload contract explicit, then either preserve paths-only arming with corrected timeout/error semantics or steer agents toward the existing atomic upload-with-trigger path with focused tests and live dynamic-page proof.

Rationale: Both behaviors are currently supported and shipped, so reliability changes may affect callers that intentionally arm a chooser before a later trigger.

- **Prefer atomic without breaking paths-only (recommended):** Keep paths-only arming supported, but update agent/tool guidance, timeout handling, and tests so chooser-trigger uploads prefer the existing same-request ref/input path where possible.

- **Document current limitations:** Leave runtime behavior unchanged and document stale-ref recovery plus selector/batch mitigations, accepting that the underlying flake remains possible.

No high-confidence live current-main reproduction was run. Source inspection confirms that paths-only upload arming and a later stale-ref click remain possible, and docs state refs are not stable across navigation, but the exact dynamic-page timeout sequence still needs live proof.

## Solution Assessment

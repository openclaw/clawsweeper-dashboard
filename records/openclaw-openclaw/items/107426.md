## Summary

Keep open: the stable package-update path has a concrete report of silently invoking mutating Doctor repair, while no merged fix or narrower canonical item currently owns this update-specific approval-boundary question. Maintainer direction is needed because removing automatic repair improves operator consent but may leave upgraded installations with unmigrated configuration.

## What This Changes

Make normal package updates run non-mutating post-update checks and reserve `doctor --fix` for an explicitly authorized update repair path disclosed by dry-run and JSON output.

## Best Possible Solution

Use read-only Doctor lint or post-upgrade probes during ordinary updates, route mutation through the existing `openclaw update repair` surface or an equally explicit opt-in, and make dry-run and JSON enumerate every planned write, migration, plugin repair, and service action.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should ordinary `openclaw update` remain an automatic migration-and-repair transaction, or should it become non-mutating after package replacement unless the operator explicitly selects update repair?

Rationale: Both choices protect a real product invariant: automatic repair helps upgrades converge, while explicit repair preserves operator approval boundaries; source inspection alone cannot choose which contract maintainers intend.

Likely owner: shakkernerd

Owner reason: The behavior appears to originate in their package post-update Doctor work, so they are best positioned to explain the migration invariant the automatic repair was intended to protect.

Owner confidence: medium

Options:

- **Separate update and repair (recommended):** Run read-only post-upgrade checks by default and require `openclaw update repair` or another explicit opt-in before invoking `doctor --fix`.
- **Keep repair, disclose it:** Continue automatic `doctor --fix`, but document it prominently and expose the exact planned mutations in dry-run and JSON output before confirmation.
- **Preserve current behavior:** Treat package update authorization as including safe Doctor migrations and make only documentation or output wording changes.

## Reproduction Assessment

Yes, from the exact npm update command and the established package post-verification callback that invokes `doctor --non-interactive --fix`; a live replay against current main was not performed.

## Solution Assessment

Yes in direction: separating ordinary update checks from the existing explicit update-repair surface is narrower and more maintainable than adding another parallel repair system, but maintainers must confirm the desired upgrade contract.

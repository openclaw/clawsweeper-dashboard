## Summary

Keep open: the package-update path intentionally invokes mutating Doctor repair, but current CLI disclosure does not resolve whether package-update consent also authorizes broad configuration repair. No merged fix or narrower canonical item owns this update-specific approval boundary, so maintainers must choose the upgrade contract before implementation.

## What This Changes

Require package updates to disclose and explicitly authorize mutating post-update Doctor repairs instead of silently invoking `doctor --fix`.

## Best Possible Solution

Give the updater a narrow, auditable migration contract: preview required post-update migrations in dry-run and JSON output, require explicit consent before applying them, and keep unrelated Doctor repairs outside the update transaction; when consent is absent, stop with an actionable rerun command rather than silently mutating or starting an incompatible runtime.

Options:

- **Separate required migrations (recommended):** Run only explicitly versioned update migrations after disclosed consent, leaving broad Doctor repairs as a separate operator action.
- **Require repair opt-in:** Default to non-mutating checks and require an update flag such as `--allow-doctor-fix`, failing safely when repair is required.
- **Keep automatic repair:** Treat update confirmation as authorization for Doctor repair, but disclose the exact mutating step in dry-run, JSON, and CLI documentation.

## Reproduction Assessment

Yes—source and a stable 2026.7.1 update transcript establish that the npm package path invokes `doctor --non-interactive --fix`; a live current-main update was not rerun during this read-only review.

## Solution Assessment

Unclear as proposed: explicit consent is the right goal, but simply removing automatic repair could break upgrades that require migrations. A dedicated, disclosed required-migration path is narrower and safer than either broad implicit repair or no repair.

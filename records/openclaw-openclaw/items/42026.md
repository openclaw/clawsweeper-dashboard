## Summary

Keep open: current main and v2026.6.11 still document and implement one Gateway-owned runtime with embedded agent execution, while the related execution-backend and Kubernetes-auth items cover narrower slices rather than the full control-plane/runtime split.

## What This Changes

The issue proposes splitting the Gateway into a control plane and separate per-agent runtime processes for isolation, scaling, lifecycle control, and secret scoping.

## Best Possible Solution

Keep this as the canonical distributed-runtime RFC and require a maintainer-approved local-split milestone covering protocol, trust, lifecycle, session ownership, channel delivery, and upgrade behavior before implementation.

## Risks / Open Questions

- A distributed runtime protocol would create new trust, registration, authorization, revocation, replay, secret-scoping, and network-exposure decisions.
- Session ownership, transcript persistence, channel delivery, cron/hooks, and agent-to-agent relay could be dropped, duplicated, or mis-associated without explicit protocol and migration semantics.
- The scope spans Gateway protocol, agent execution, config/schema, deployment topology, docs, and security boundaries, so an autonomous fix PR would choose architecture prematurely.
- Related work such as https://github.com/openclaw/openclaw/issues/82017 and https://github.com/openclaw/openclaw/pull/84758 is useful but partial and should not be treated as the full RFC implementation.

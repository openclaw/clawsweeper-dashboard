## Label Justifications

- `P2`: This is a useful cron automation feature with real operator impact, but it is not a confirmed outage, data loss, crash loop, or first-run blocker.
- `impact:security`: The requested hook kinds include persisted shell and webhook actions that could execute unattended commands or outbound calls from scheduled automation.
- `impact:session-state`: The requested hooks can skip, repeat, transform, or escalate scheduled agent runs, affecting cron run state and session execution lifecycle.

## Summary

Keep open. Current main and the latest release still lack persisted cron pre/post/onError hooks or a per-job pre-agent gate, while related implementation attempts are closed unmerged and the remaining shell/webhook semantics need product and security direction.

## What This Changes

Request to add configurable cron lifecycle hooks that can run agent turns, system events, shell commands, or webhooks before, after, or on failed cron executions.

## Best Possible Solution

Settle a maintainer-approved cron hook or deterministic gate API across persisted job/protocol schemas, scheduled/startup/manual execution paths, CLI/UI/docs/tests, and an explicit trust model, or explicitly route the capability to plugin/ClawHub patterns if core should stay out of this surface.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw core expose persisted per-cron lifecycle hooks that can run shell or webhook actions, and what trust boundary/API should own that behavior?

Rationale: The remaining work defines public cron config/protocol behavior and can execute unattended commands or outbound calls, which requires maintainer product and security intent rather than a mechanical fix.

Likely owner: steipete

Owner reason: steipete has the strongest current routing signal from the prior issue review plus recent cron protocol/status work.

Owner confidence: high

Options:

- **Approve a narrow core hook API (recommended):** Define an additive CronJob hook/gate contract with explicit command/webhook permissions, phases, failure semantics, upgrade-safe docs, and coverage across all cron execution paths.
- **Route hooks to plugins or ClawHub:** Declare command cron plus plugin hooks as the supported path and document the external pattern instead of adding persisted CronJob.hooks to core.
- **Defer the feature:** Leave the issue open as an acknowledged gap until maintainers are ready to own the API and trust model.

## Reproduction Assessment

Yes at source level: current cron types, Gateway schemas, and due/manual/startup execution paths omit persisted lifecycle hooks or a per-job pre-agent gate. This is a missing feature rather than a broken existing behavior contract.

## Solution Assessment

Unclear: a core hook system is plausible, but command cron jobs and plugin hooks already solve adjacent subsets, so maintainers need to choose the permanent core versus plugin boundary before implementation.

## Summary

Keep this issue open. The report describes a bounded Control UI regression in which a route-resolution failure feeds the same missing session key back into route replacement, so the UI does not settle; the path introduced by the merged session-URL resolver is recent and no current-main fix or replacement PR is evidenced. The `maintainer` label also requires explicit maintainer handling rather than automated cleanup.

## What This Changes

Make an unresolved chat-session route settle into a not-found or empty state instead of repeatedly attempting to resolve the same missing session key.

## System Context

The Control UI turns a chat URL into a session selection, consulting the gateway when the browser does not already have that session row. A successful resolution mounts the chat view or redirects to the stored board face; a failed resolution must end navigation cleanly rather than feeding the failed selection back into the router.

## Architecture Diagram

flowchart LR
  A[Chat URL] --> B[Chat route resolver]
  B --> C[Gateway session list]
  C --> D{Session resolved?}
  D -->|Yes| E[Select session and mount chat]
  D -->|No| F[Settle not-found or empty view]
  F --> G[User can navigate elsewhere]

## Best Possible Solution

Add a one-way failed-resolution state at the Control UI route boundary so a key already confirmed missing cannot be reselected; render the chosen not-found or empty state and add an E2E regression test that verifies route-replacement calls stop.

Options:

- **Render route-level not found (recommended):** Keep the attempted URL visible, mark the route terminally unresolved, and provide in-app navigation back to a valid session.
- **Clear selection to start view:** Discard the missing active key and replace the route with the normal empty or start screen.

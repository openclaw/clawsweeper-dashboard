## Summary

Keep open. Current main and the latest release already handle the safe implicit Linux no-display headless fallback and an actionable explicit-headed error, but the remaining requested machine-readable route/client error contract is still missing and needs maintainer API/product direction.

## What This Changes

Request a structured degraded/no-display result or policy-gated fallback for managed browser profiles when headed launch is configured without a display server.

## Best Possible Solution

Preserve the current implicit fallback policy and add an additive, typed no-display error envelope that carries a closed reason and safe typed details through the browser route and client contracts, with docs and focused regression coverage.

Rationale: The source gap is clear, but the permanent route/client error shape and whether to broaden fallback semantics are public API and compatibility choices rather than a purely mechanical bug fix.

- **Add Typed Error Envelope (recommended):** Keep explicit headed mode fail-closed and add an additive `reason: "no_display_for_headed_profile"` plus typed details through route and client errors.
- **Broaden Fallback Policy:** Allow more explicit headed profiles to fall back to headless, accepting the compatibility risk of overriding visible-browser intent.
- **Document Current Behavior Only:** Declare the current text-only actionable error sufficient and close the request without adding machine-readable branching fields.

## Reproduction Assessment

Yes, at source level. Explicit headed local managed launches on Linux without DISPLAY/WAYLAND_DISPLAY produce an actionable `BrowserProfileUnavailableError`, then the route and client layers expose only a string error instead of the requested structured result.

## Solution Assessment

Unclear until maintainers choose the contract. The best maintainable direction appears to be an additive typed error envelope while preserving the current implicit-only fallback policy.

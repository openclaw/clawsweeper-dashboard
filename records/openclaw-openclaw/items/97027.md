## Summary

Keep open. Current main and v2026.6.11 already handle the safe implicit fallback and human-readable explicit-headed no-display error, but the browser route/client boundary still exposes this as a string-only failure rather than the requested branchable contract.

## What This Changes

Managed browser tooling should expose a structured no-display degradation result when headed launch is selected on a host without DISPLAY or WAYLAND_DISPLAY.

## Best Possible Solution

Preserve the existing implicit no-display headless fallback, then add a maintainer-approved structured BrowserProfileUnavailableError reason/details envelope through route and client boundaries and document it.

- **Add policy-controlled fallback:** Allow selected explicit headed profiles to fall back to headless, but require a clear profile/config policy and upgrade documentation.

## Reproduction Assessment

Yes, by source inspection. Explicit headed local managed launches without DISPLAY/WAYLAND_DISPLAY reach BrowserProfileUnavailableError, but route/client helpers still expose only a message string.

## Solution Assessment

No, the broad auto-fallback direction is not the best default without maintainer approval. The safer path is an additive structured error contract that preserves the existing implicit fallback and explicit headed failure policy.

## Summary

Keep open: current main still has a source-visible managed-worktree GC concurrency gap, even though the exact fresh-row deletion described in the report was not live-reproduced and the snapshot-prune loop now uses a fresh registry list.

## What This Changes

The issue reports that managed worktree GC can delete or orphan a concurrently created checkout because cleanup decisions are made from registry/path state observed before destructive operations.

## Best Possible Solution

Make managed worktree GC revalidate or serialize destructive cleanup against concurrent create and restore, then add regression coverage for the interleavings without adding config or weakening snapshot-before-delete behavior.

## Repair Work Prompt

Fix the managed worktree GC/create TOCTOU reported in https://github.com/openclaw/openclaw/issues/101721. In `src/agents/worktrees/service.ts` and registry helpers as needed, ensure GC does not remove/prune/reconcile a worktree path or registry row from stale state after a concurrent `create()` or `restore()` has made it live. Prefer a small service-owned serialization or conditional registry re-read/delete guard around destructive GC operations; do not add config/env surface, do not weaken snapshot-before-delete, and do not change the gateway protocol unless the existing contract cannot support the fix. Add focused regression tests that force GC interleavings with create/restore, including orphan reconciliation and snapshot retention, and keep the fix limited to managed worktree lifecycle correctness.

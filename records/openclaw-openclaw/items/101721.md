## Summary

Keep open: current main still has a source-visible managed-worktree GC concurrency gap, even though the issue's exact fresh-row deletion theory is not fully proven and the snapshot-prune loop now re-lists the registry before deleting rows.

## What This Changes

The issue asks for managed worktree GC to avoid deleting or deregistering worktrees created concurrently from a stale registry snapshot.

## Best Possible Solution

Make managed worktree GC revalidate or serialize destructive cleanup against concurrent create and restore, then add interleaving regression tests without adding config or weakening snapshot-before-delete behavior.

## Summary

Keep open: current main and v2026.6.11 still use a 30s `sessions_send(timeoutSeconds=0)` A2A announce budget plus a 60s A2A wait cap, and the remaining fix requires a maintainer decision on public timeout/default/config semantics.

## What This Changes

The issue requests configurable or longer A2A announce timeout behavior for `sessions_send` because the hardcoded fire-and-forget path can lose late replies.

## Best Possible Solution

Define one canonical A2A announce/delivery timeout contract, then update `sessions_send`, A2A tests, schema/help/docs, and live proof around that contract together.

Options:

- **Define A2A-specific contract (recommended):** Add or document the canonical A2A timeout/default behavior under the sessions_send/session.agentToAgent owner, then implement tests and docs against it.
- **Reuse subagent announce timeout:** Treat `agents.defaults.subagents.announceTimeoutMs` as the shared announce budget and remove the remaining sessions_send-specific caps if maintainers want one owner for both flows.
- **Choose durable delivery instead:** Keep timeout knobs narrow and solve fire-and-forget reliability through durable/push result delivery or explicit one-way semantics rather than longer waits.

No high-confidence live reproduction was run. Source inspection shows `timeoutSeconds=0` still uses a 30s A2A announce budget and the A2A wait helper still caps target waits at 60s, so the timing shape is source-reproducible.

Unclear. A configurable timeout is plausible, but maintainers should first choose whether the best contract is a longer default, reuse of the subagent announce timeout, a new A2A option, or durable one-way delivery semantics.

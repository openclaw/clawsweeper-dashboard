## Summary

Keep open: current main and v2026.6.11 still keep `systemEvent` cron payloads text-only and only honor per-job model fields on `agentTurn`, so the main-session cron model/provider override request remains a real product/API gap.

## What This Changes

Request first-class cron model/provider override support for `sessionTarget: "main"` jobs that use `payload.kind: "systemEvent"`.

## Best Possible Solution

Maintainers should choose one explicit cron override contract, validate it through the normal allowed provider/model route, persist or audit it intentionally, and prove both wake-now and next-heartbeat main-session behavior without manual session-store edits.

## Maintainer Decision

Question: Should main-session `systemEvent` cron jobs gain a supported model/provider override contract, and if so should it be `payload.model`, a top-level job override, or a dedicated `sessionOverride` block?

Rationale: The source gap is clear, but the fix changes public cron schema, session/provider precedence, persistence, and upgrade behavior; automation should not pick that API shape without maintainer intent.

Owner confidence: high

Options:

- **Extend `systemEvent` payload.model (recommended):** Add `payload.model` to `systemEvent` cron payloads with explicit provider/model validation and main-session heartbeat/session routing proof.
- **Add job-level override fields:** Introduce top-level model/provider override fields that can apply across payload kinds, accepting a broader public schema and docs surface.
- **Keep main-session system events text-only:** Document isolated `agentTurn` as the supported per-job model path and leave main-session system events tied to the target session's model state.

## Reproduction Assessment

Yes. Source inspection is enough: current schema, runtime types, payload merging, and main-session cron execution still keep `systemEvent` payloads text-only while model fields live on `agentTurn`.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` for `systemEvent` is the narrowest API shape, but top-level job overrides or a dedicated session override block remain plausible product choices.

## Summary

Keep open. Current main still keeps main-session `systemEvent` cron payloads text-only; merged cron model work covers isolated or agent-turn jobs and the Control UI now deliberately omits model selection for silent system-event jobs.

## What This Changes

Request job-level provider/model selection for `sessionTarget: "main"` cron jobs with `payload.kind: "systemEvent"` so stable main-session cron runs can use a cheaper model without manual session-store edits.

## Best Possible Solution

Choose one explicit cron-owned provider/model override contract, validate it like isolated cron payload models, and prove the override is per-run for both wake-now and next-heartbeat without leaking into main-session state.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support explicit provider/model overrides for main-session systemEvent cron jobs, and should the public contract be `payload.model`, top-level cron fields, or a `sessionOverride` block?

Rationale: Current code treats main-session systemEvent jobs as text-only injections, and enabling overrides crosses provider routing, session state, cron persistence, CLI/UI/docs, and heartbeat execution semantics.

Likely owner: steipete

Owner reason: The recent merged cron runtime/schema work makes this the strongest available owner for the API and session-state direction decision.

Owner confidence: high

Options:

- **Design explicit override contract (recommended):** Add a public cron-owned provider/model override shape, validate it like isolated cron payload models, and require proof that the choice is scoped to one cron run.
- **Keep systemEvent text-only:** Document main-session systemEvent jobs as unsupported for model selection and steer cheaper scheduled model calls to isolated/current/custom-session agentTurn jobs.
- **Defer to broader cron API work:** Track the decision with broader cron schema and cost-control work so model, context, timeout, fallback, and spend semantics are decided together.

## Reproduction Assessment

Yes, at source level. Current schema/types keep systemEvent text-only, normalization prunes model-like fields, and main-session execution enqueues only text without provider/model override data.

## Solution Assessment

Unclear until maintainers choose the public contract. `payload.model` is plausible, but a dedicated cron/session override block may better reflect that systemEvent only queues text and the heartbeat performs the model call.

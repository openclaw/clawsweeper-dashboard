- `impact:session-state`: The reported workaround manually edits session metadata, and the requested fix would alter how main-session cron runs pick or isolate session model state.

## Summary

Keep open. Current main still treats `systemEvent` cron payloads as text-only main-session injections and only honors `payload.model` for model-backed `agentTurn` jobs, while the related merged UI work intentionally excludes silent system-event jobs.

## What This Changes

This issue requests first-class per-job model/provider selection for `sessionTarget: "main"` cron jobs that use `payload.kind: "systemEvent"`.

## Best Possible Solution

Define an explicit main-session cron override contract, with provider/model validation and no manual session-store edits, or deliberately document that stable cheap-model scheduling should use isolated `agentTurn` jobs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support explicit provider/model overrides for main-session `systemEvent` cron jobs, and if so should the public contract be `payload.model`, top-level cron fields, or a `sessionOverride` block?

Rationale: Current code intentionally treats system events as text-only main-session injections; enabling a model override crosses provider routing, session state, cron persistence, UI/CLI, and heartbeat semantics that automation should not choose without maintainer intent.

Likely owner: steipete

Owner reason: Recent cron runtime/schema history and product-sensitive cron work make this the strongest routing candidate from the available evidence.

Owner confidence: medium

Options:

- **Design an explicit override contract (recommended):** Add a public cron-owned provider/model override shape, validate it like isolated cron payload models, and prove main-session wake modes do not leak or corrupt session state.
- **Keep systemEvent text-only:** Close or document this path as unsupported and steer cheap scheduled model calls to isolated/current/custom-session `agentTurn` jobs.
- **Defer behind broader cron schema work:** Track this with the broader cron schema and cost-control API work so model, context, timeout, and spend semantics are decided together.

## Reproduction Assessment

Yes, at source level. Current main keeps `systemEvent` payloads text-only, deletes `model` during normalization, and only resolves `payload.model` for `agentTurn` cron jobs.

## Solution Assessment

Unclear until maintainers choose the product contract. `payload.model` is plausible, but the safer shape may be an explicit cron/session override because main-session system events do not start a model call by themselves.

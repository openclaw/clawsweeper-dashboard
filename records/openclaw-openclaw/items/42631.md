## Summary

Keep open: current main and the latest release still keep main-session `systemEvent` cron payloads text-only, while the recently merged UI work deliberately covers only the existing `agentTurn` model contract.

## What This Changes

The issue requests a first-class per-cron model/provider override for jobs using `sessionTarget: "main"` with `payload.kind: "systemEvent"`.

## Best Possible Solution

Define one explicit cron override contract, validate it through the normal provider/model allowlist, persist or audit it intentionally, and prove both wake-now and next-heartbeat main-session behavior without manual session-store edits.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session `systemEvent` cron jobs gain a supported model/provider override contract, and should that contract be `payload.model`, job-level override fields, or an explicit `sessionOverride` block?

Rationale: The source gap is clear, but the fix changes public cron schema, session/provider precedence, persistence, and upgrade behavior, so automation should not pick the API shape without maintainer intent.

Likely owner: steipete

Owner confidence: high

Options:

- **Extend systemEvent payload.model (recommended):** Add `payload.model` to `systemEvent` cron payloads with explicit provider/model validation and direct proof for wake-now and next-heartbeat main-session routing.
- **Add job-level override fields:** Introduce top-level model/provider or `sessionOverride` fields that apply across payload kinds, accepting the broader schema and docs surface.
- **Keep systemEvent text-only:** Document isolated `agentTurn` and heartbeat model configuration as the supported per-job or recurring-model paths and leave main-session system events tied to session state.

## Reproduction Assessment

Yes, source-level. Current schema, payload types, persistence, and main-session execution show `systemEvent` cron jobs cannot carry or apply a supported model/provider override.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` for `systemEvent` is the narrowest option, but job-level or explicit session overrides remain plausible product choices.

## Summary

Keep open. Current main still treats main-session `systemEvent` cron jobs as text-only wake injections, while model override support is implemented only for `agentTurn` cron jobs and the merged UI work intentionally excludes silent/systemEvent overrides.

## What This Changes

Request job-level provider/model selection for `sessionTarget: "main"` plus `payload.kind: "systemEvent"` cron jobs so recurring main-session automation can use a cheaper model without changing the interactive session default.

## Best Possible Solution

Define one cron-owned main-session override contract that validates provider/model selection, works for immediate and next-heartbeat wake modes without context-key encoding, documents precedence against session defaults, and updates protocol, store, tool/CLI/UI, docs, and tests together.

## Maintainer Decision

Required: true

Rationale: The issue asks for a new compatibility-sensitive cron/API behavior that crosses scheduling, provider routing, session state, persistence, docs, and UI/tool schema boundaries; the previous direct PR was closed unmerged after a contract bug, so automation should not choose the permanent shape alone.

Likely owner: steipete

Owner reason: This person has the strongest available recent history signal around cron runtime/schema direction and was also identified in prior issue review as the likely owner for this product-sensitive choice.

Owner confidence: medium

Options:

- **Add an explicit cron override contract (recommended):** Add a first-class job-level override shape with validation, documented precedence, persistence/schema/tool/UI support, and tests for both immediate and next-heartbeat execution.
- **Reuse `payload.model` for system events:** Extend `systemEvent` payloads to accept `model` while still defining session-preference precedence and heartbeat transport safely.
- **Keep systemEvent text-only:** Document this route as unsupported for explicit model calls and direct model-specific automation to isolated/current/custom-session `agentTurn` jobs.

## Reproduction Assessment

Yes, at source level: main/systemEvent payloads are text-only, normalization removes model fields, persistence stores no systemEvent model, and the main enqueue path carries no provider/model override.

## Solution Assessment

Unclear until maintainers choose the product contract; `payload.model` is plausible, but an explicit cron/session override may be safer because systemEvent jobs do not themselves start a model call.

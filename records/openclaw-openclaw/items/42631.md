## Label Justifications

- `P2`: This is a bounded cron/model-routing feature with cost and stability impact, but it is not an urgent outage or shipped-regression blocker.
- `impact:session-state`: The current workaround edits persisted session metadata, and any fix must keep cron-specific overrides isolated from the main session.
- `impact:auth-provider`: The request directly changes per-job provider/model selection, validation, and auth-profile routing for scheduled runs.

## Summary

Keep open: current main still keeps main-session `systemEvent` cron payloads text-only, persists no payload model for that variant, and enqueues only text/session context, so the requested per-job model/provider override remains a real cron API/product gap rather than cleanup.

## What This Changes

The issue requests a supported job-level model/provider override for cron jobs that run as `sessionTarget: "main"` with `payload.kind: "systemEvent"`.

## Best Possible Solution

Define one explicit cron override contract for main-session systemEvent jobs, validate it through existing provider/model routing, isolate it to the cron run session, and cover wake-now plus next-heartbeat behavior in tests/docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session systemEvent cron jobs gain a supported model/provider override contract, and should that contract be `payload.model`, top-level job fields, or a dedicated `sessionOverride` block?

Rationale: The source gap is clear, but adding it changes public cron schema, provider precedence, persisted job/session semantics, and upgrade behavior; automation should not choose that API shape without maintainer intent.

Likely owner: vincentkoc

Owner reason: Recent cron runtime ownership and the main/detached dispatch split make this the best available routing owner for the code/API decision.

Owner confidence: medium

Options:

- **Extend systemEvent payload.model (recommended):** Add `payload.model` to systemEvent cron payloads with normal provider/model validation, run-scoped session isolation, and wake-now/next-heartbeat proof.
- **Add job-level override fields:** Introduce top-level cron model/provider fields that apply across payload kinds, accepting a broader schema and docs surface.
- **Keep systemEvent text-only:** Document isolated agentTurn cron jobs as the supported per-job model path and leave main-session system events bound to the target session's model state.

## Reproduction Assessment

Yes, source-level. Current protocol, runtime types, normalization, persistence, and main-session execution all show that systemEvent cron payloads cannot carry a supported model/provider override.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` is the narrowest option, but job-level fields or an explicit override block remain plausible product/API choices.

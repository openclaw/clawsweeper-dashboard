- `impact:session-state`: The current workaround requires editing session metadata, and any supported fix must define how cron-specific session overrides are applied and isolated from the main session.

## Summary

Keep open: current main still lacks a supported model/provider override for main-session `systemEvent` cron jobs. The related isolated-agentTurn runtime work and active Control UI PRs help adjacent model-selection paths, but they intentionally do not solve this main-session product/API gap.

## What This Changes

Request first-class per-job model/provider selection for cron jobs that run through `sessionTarget: "main"` with `payload.kind: "systemEvent"`, avoiding manual session metadata edits.

## Best Possible Solution

Maintainers should choose one supported cron override contract for main-session systemEvent jobs, validate it against allowed provider/model routes, persist or audit it explicitly, and prove both wake-now and next-heartbeat behavior without requiring manual session-store edits.

## Reproduction Assessment

Yes, source-level. Current schema, normalization, and main-session execution show explicit `systemEvent` payloads cannot carry a supported model/provider override, and the enqueue path only forwards text/session context.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` for explicit `systemEvent` or adding a job-level override block are plausible, but either choice needs product/API and upgrade semantics before implementation.

## Summary

Keep open: current main and the latest release still keep main-session `systemEvent` cron payloads text-only, and the merged UI work only exposes model selection for `agentTurn` jobs.

## What This Changes

The issue requests a supported job-level model/provider override for `sessionTarget: "main"` cron jobs that use `payload.kind: "systemEvent"`.

## Best Possible Solution

Maintainers should choose one explicit, run-scoped cron model/provider override contract, validate it through the normal allowed provider/model route, and prove both wake-now and next-heartbeat main-session behavior without requiring manual session-store edits.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session `systemEvent` cron jobs gain a supported model/provider override contract, and should that contract be `payload.model`, top-level job fields, or a dedicated override block?

Rationale: The source gap is clear, but the fix changes public cron schema, provider/model precedence, session-state isolation, docs, and upgrade behavior, so automation should not choose the API shape without maintainer intent.

Likely owner: steipete

Owner reason: Recent cron session-target and model-routing history makes this the strongest available owner for the product/API contract choice.

Owner confidence: high

Options:

- **Extend systemEvent payload overrides (recommended):** Add `payload.model` or a provider/model ref to `systemEvent` cron payloads with run-scoped application, explicit validation, docs, and wake-now plus next-heartbeat tests.
- **Add job-level override fields:** Introduce top-level cron `model` and `provider` fields that apply across payload kinds, accepting a broader schema and UI/CLI migration surface.
- **Keep systemEvent text-only:** Document isolated `agentTurn` cron jobs as the supported model-selectable path and leave main-session system events tied to the target session's existing model state.

## Reproduction Assessment

Yes, source-level. Current schema, normalization, docs, and main-session execution show `systemEvent` cron payloads cannot carry a supported model/provider override and only enqueue text/session context.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` for `systemEvent` is the narrowest apparent path, but top-level or explicit override blocks remain plausible product choices.

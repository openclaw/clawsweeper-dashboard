## Summary

Keep open: current main and v2026.6.11 still keep main-session `systemEvent` cron jobs text-only and do not provide a supported provider/model override path; the remaining work is a public cron API and session-state product decision, not stale cleanup.

## What This Changes

The issue requests job-level provider/model selection for `sessionTarget: "main"` plus `payload.kind: "systemEvent"` cron jobs so recurring work can use a cheaper model without manual session metadata edits.

## Best Possible Solution

Define one supported cron override contract for main-session `systemEvent` jobs that sets provider/model for the per-run session, documents validation and fallback behavior, and removes the need for manual session metadata edits.

Options:

- **Add explicit sessionOverride contract (recommended):** Introduce a typed cron `sessionOverride` block for provider/model with explicit validation, docs, and regression coverage for `wakeMode: "now"` and next-heartbeat execution.
- **Extend systemEvent payload.model:** Reuse the existing `payload.model` shape for `systemEvent` if maintainers prefer parity with `agentTurn`, but wire it through a direct model propagation path rather than encoded context state.
- **Keep overrides unsupported:** Document dedicated session keys plus session model selection as the supported workaround and leave job-level main-systemEvent overrides out of cron for now.

## Reproduction Assessment

Yes, at source level. Current main accepts model fields only on `agentTurn` cron payloads, prunes those fields from `systemEvent`, and the main-session `systemEvent` runtime path enqueues heartbeat work without provider/model override state.

Unclear. Job-level model selection is the right user problem, but the best fix needs maintainer choice on API shape and failure semantics before implementation.

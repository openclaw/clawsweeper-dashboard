## Summary

Keep open: current main still keeps main-session `systemEvent` cron jobs text-only, while per-job model selection remains limited to `agentTurn` cron payloads and adjacent UI display work.

## What This Changes

The issue requests first-class per-job provider/model overrides for cron jobs that use `sessionTarget: "main"` with `payload.kind: "systemEvent"`.

## Best Possible Solution

Maintainers should choose one explicit cron override contract, validate it through the normal provider/model allowlist path, keep cron-run overrides isolated from interactive session defaults, and prove both wake-now and next-heartbeat main-session behavior.

## Maintainer Decision

Rationale: The source gap is clear, but the fix changes public cron schema, provider/model precedence, session metadata behavior, and upgrade/docs expectations, so automation should not choose the API shape.

Options:

- **Extend `systemEvent` payloads (recommended):** Allow `payload.model` and provider resolution for `systemEvent` cron payloads, matching the existing agent-turn style with focused main-session proof.
- **Add job-level overrides:** Introduce top-level provider/model fields that apply across payload kinds, accepting a broader schema and migration/docs contract.
- **Keep `systemEvent` text-only:** Document isolated `agentTurn` as the supported per-job model path and leave main-session system events tied to session state.

## Reproduction Assessment

Yes, source-level. Current schema, normalization, storage, UI mapping, and main-session enqueue code show that `main` + `systemEvent` cron jobs cannot carry or apply a supported model/provider override.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` for `systemEvent` is the narrowest visible option, but top-level job fields or an explicit session override block are still plausible product/API choices.

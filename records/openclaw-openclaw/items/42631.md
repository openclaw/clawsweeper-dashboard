## Summary

Keep open. Current main still treats main-session `systemEvent` cron jobs as text-only session injections, while model/provider selection is only supported for model-backed `agentTurn` cron jobs and related UI/isolated-cron work does not implement this route.

## What This Changes

The issue requests a first-class per-job provider/model override for cron jobs that use `sessionTarget: "main"` with `payload.kind: "systemEvent"`.

## Best Possible Solution

Define an explicit main-session cron override contract with provider/model validation and per-run isolation, or deliberately document that stable cheap-model scheduled work must use `agentTurn` jobs instead of `systemEvent`.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support explicit provider/model overrides for main-session `systemEvent` cron jobs, and if so should the public contract be `payload.model`, top-level cron fields, or a dedicated `sessionOverride` block?

Rationale: Current code treats system events as text-only main-session injections; changing that crosses provider routing, session state, cron persistence, UI/CLI behavior, and heartbeat semantics that automation should not choose without maintainer intent.

Likely owner: steipete

Owner reason: The product-sensitive cron/session/provider boundary overlaps recent cron runtime and prior model-override merge history tied to this owner signal.

Owner confidence: medium

Options:

- **Design an explicit override contract (recommended):** Add a public cron-owned provider/model override shape, validate it like isolated cron payload models, and prove both wake modes cannot leak or corrupt session model state.
- **Keep systemEvent text-only:** Document this path as unsupported for model selection and steer cheaper scheduled model calls to isolated, current, or custom-session `agentTurn` jobs.
- **Fold into broader cron schema work:** Defer this to the broader cron schema and cost-control discussion so model, context, timeout, and spend semantics are decided together.

## Reproduction Assessment

Yes, at source level. Current main keeps `systemEvent` payloads text-only, strips `model` during normalization, and only resolves `payload.model` for `agentTurn` cron jobs.

## Solution Assessment

Unclear until maintainers choose the public contract. `payload.model` is plausible, but a dedicated cron/session override may be safer because main-session system events do not start a model call by themselves.

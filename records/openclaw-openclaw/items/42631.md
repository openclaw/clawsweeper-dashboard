## Label Justifications

- `P2`: This is a bounded but compatibility-sensitive cron/model-routing feature with a clear source gap and limited blast radius.
- `impact:session-state`: The current workaround edits session metadata, and a supported fix must define how cron-specific session overrides are isolated from the main session.
- `impact:auth-provider`: The requested behavior directly affects per-job provider/model routing and validation for scheduled runs.

## Summary

Keep open: current main and the latest release still keep `systemEvent` cron payloads text-only and only honor `payload.model` on `agentTurn`, so the main-session cron model/provider override request remains a real product/API gap.

## What This Changes

Request a supported per-cron model/provider override for main-session `systemEvent` cron jobs so scheduled automation can use a cheaper model than the main session default.

## Best Possible Solution

Maintainers should choose one explicit cron override contract, validate it through the normal allowed provider/model route, persist or audit it intentionally, and prove both wake-now and next-heartbeat main-session behavior without requiring manual session-store edits.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session `systemEvent` cron jobs gain a supported model/provider override contract, and if so should it be `payload.model`, a top-level job override, or a dedicated `sessionOverride` block?

Rationale: The source gap is clear, but the fix changes public cron schema, session/provider precedence, persistence, and upgrade behavior; automation should not pick that API shape without maintainer intent.

Likely owner: steipete

Owner reason: Recent cron runtime and model-routing history makes this the best available routing owner for the product/API decision.

Owner confidence: medium

Options:

- **Extend systemEvent payload.model (recommended):** Add `payload.model` to `systemEvent` cron payloads with explicit provider/model validation and direct heartbeat/session routing proof, matching the existing `agentTurn` override style.
- **Add job-level override fields:** Introduce a top-level model/provider override that can apply across cron payload kinds, at the cost of a broader contract and migration/docs surface.
- **Keep main-session systemEvent text-only:** Document isolated `agentTurn` as the supported per-job model path and leave main-session system events tied to the target session's model state.

## Reproduction Assessment

Yes, source-level. Current schema, normalization, and main-session execution show `systemEvent` payloads cannot carry a supported model/provider override, and the enqueue path only forwards text/session context.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` for `systemEvent` is the narrowest option, but top-level or explicit session overrides remain plausible product choices.

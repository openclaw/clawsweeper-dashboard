## Summary

Keep open: current `main` still treats `systemEvent` cron payloads as text-only, and the merged UI work deliberately avoids exposing model selection for silent/main-session jobs because the runtime would ignore it.

## What This Changes

The issue requests a first-class cron job model/provider override for `sessionTarget: "main"` jobs whose payload is `kind: "systemEvent"`.

## Best Possible Solution

Maintainers should define one explicit cron override contract, validate it through the normal provider/model allowlist route, persist or audit it intentionally, and prove both wake-now and next-heartbeat main-session behavior without manual session-store edits.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session `systemEvent` cron jobs gain a supported model/provider override contract, and should that contract be `payload.model`, job-level model/provider fields, or a dedicated session override block?

Rationale: The source gap is clear, but the fix changes public cron schema, session/provider precedence, persistence shape, and upgrade behavior, so automation should not choose the API shape.

Likely owner: steipete

Owner reason: Recent cron runtime and schema work makes this the clearest routing owner for the API/precedence decision.

Owner confidence: high

Options:

- **Extend systemEvent payloads (recommended):** Allow `payload.model` and provider resolution for `systemEvent` cron payloads, matching the existing agent-turn style while adding main-session proof.
- **Add job-level overrides:** Introduce top-level model/provider fields that apply across payload kinds, with broader schema, docs, migration, and precedence rules.
- **Keep systemEvent text-only:** Document isolated `agentTurn` as the only supported per-job model path and leave main-session system events tied to session state.

## Reproduction Assessment

Yes, at source level. Current schema, normalization, storage, UI mapping, docs, and main-session enqueue code all show that `main` + `systemEvent` cron jobs cannot carry or apply a supported model/provider override.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` for `systemEvent` is the narrowest option, but top-level or explicit session overrides remain plausible product choices.

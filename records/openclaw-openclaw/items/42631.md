## Summary

Keep open: current main and v2026.6.11 still do not provide a supported model/provider override for main-session systemEvent cron jobs, and the merged cron model UI work intentionally covers agentTurn jobs only.

## What This Changes

The issue requests first-class per-cron model/provider selection for jobs using `sessionTarget: "main"` with `payload.kind: "systemEvent"`.

## Best Possible Solution

Define one canonical cron job model/provider override contract, validate it through existing allowlist and fallback rules, and route it into main-session heartbeat execution with schema, runtime, UI, docs, and regression coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session systemEvent cron jobs support a first-class model/provider override, and which single public API shape should own it?

Rationale: The request changes public cron protocol plus provider/session routing semantics, so automation should not choose between `payload.model`, top-level job fields, or a `sessionOverride` block without maintainer intent.

Likely owner: vincentkoc

Owner reason: Current-line blame and recent cron protocol/runtime maintenance make this the best available owner for choosing the API shape.

Owner confidence: medium

Options:

- **Add canonical job-level override (recommended):** Define one job-level override contract, validate it through the current model allowlist/fallback logic, and pass it to main-session heartbeat execution without encoding routing state into event text.
- **Reuse payload.model on systemEvent:** Extend the existing payload field as the smallest schema change, accepting that text-only system events would also carry run-routing metadata.
- **Keep main systemEvent default-only:** Document that per-cron cheap models require isolated or custom agent-turn jobs and leave main-session system events on their session/default model.

## Reproduction Assessment

Yes, at source level: current schema/types make `systemEvent` text-only, main cron jobs require `systemEvent`, normalization strips `model`, and main execution never passes a model/provider override into heartbeat execution.

## Solution Assessment

Unclear until maintainers choose the public API shape; `payload.model` is the smallest extension, but a top-level or `sessionOverride` contract may better express run-level routing without overloading system-event payload text.

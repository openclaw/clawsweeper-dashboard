- `impact:session-state`: The current workaround edits session metadata, and a correct fix must define how cron-specific overrides stay isolated from main-session state.

## Summary

Keep open: current main still treats `main` + `systemEvent` cron payloads as text-only and deliberately limits `payload.model` to agent-turn cron jobs, so the requested main-session cron model/provider override remains a real product/API gap.

## What This Changes

Request job-level provider/model selection for cron jobs that use `sessionTarget: "main"` with `payload.kind: "systemEvent"` so scheduled work can use a cheaper model than the main session default.

## Best Possible Solution

Maintainers should choose one explicit per-run provider/model override contract for main-session `systemEvent` cron jobs, validate it through the normal allowed-model route, and prove both wake-now and next-heartbeat behavior without persistent session override leakage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session `systemEvent` cron jobs gain a supported per-run provider/model override, and if so should the public contract be `payload.model`, top-level job fields, or an explicit `sessionOverride` block?

Rationale: The source gap is clear, but the fix changes cron's public schema, session/provider precedence, persistence expectations, and upgrade semantics, so automation should not choose the API shape.

Likely owner: steipete

Owner reason: Recent cron runtime, protocol, session-target, and documentation history makes this the best available owner for the product/API direction.

Owner confidence: high

Options:

- **Add an explicit sessionOverride block (recommended):** Introduce a dedicated cron override object for `provider` and `model` that is applied only to the cron-triggered main-session run and never persisted as the user's main session choice.
- **Extend systemEvent payload.model:** Reuse the existing agent-turn field name on `systemEvent` payloads, keeping the API compact but overloading a payload kind that docs currently describe as text-only.
- **Keep systemEvent text-only:** Document isolated `agentTurn` cron jobs as the supported per-job model path and leave main-session system events tied to the target session model state.

## Reproduction Assessment

Yes, source-level. Current schema, normalization, persistence, and main-session execution all show that `systemEvent` payloads cannot carry a supported model/provider override and that the enqueue path does not forward one.

## Solution Assessment

Unclear until maintainers choose the public contract. An explicit per-run override block appears safer than mutating session metadata or overloading a text-only payload, but the product/API choice is still open.

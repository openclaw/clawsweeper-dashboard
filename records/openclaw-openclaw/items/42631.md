## Summary

Keep open: current main and v2026.6.11 still keep `systemEvent` cron payloads text-only and only apply cron model selection to agent-turn/isolated paths, so the requested main-session model/provider override remains unresolved.

## What This Changes

The issue requests a first-class job-level model/provider override for cron jobs that use `sessionTarget: "main"` with `payload.kind: "systemEvent"`.

## Best Possible Solution

Maintainers should choose one explicit cron override contract, validate it through the normal provider/model allowlist route, persist or audit it intentionally, and prove both wake-now and next-heartbeat main-session behavior without manual session-store edits.

## Maintainer Decision

Question: Should main-session `systemEvent` cron jobs gain a supported model/provider override contract, and should that contract be `payload.model`, top-level job fields, or a dedicated `sessionOverride` block?

Rationale: The source gap is clear, but the fix changes public cron schema, session/provider precedence, persistence shape, and upgrade behavior, so automation should not choose the API shape.

Likely owner: steipete

Owner confidence: high

Options:

- **Extend `systemEvent` payloads (recommended):** Allow `payload.model` and provider resolution for `systemEvent` cron payloads, matching the existing agent-turn style while adding main-session proof.
- **Add job-level overrides:** Introduce top-level model/provider fields that apply across payload kinds, with a broader schema and migration/docs contract.
- **Keep `systemEvent` text-only:** Document isolated `agentTurn` as the only supported per-job model path and leave main-session system events tied to session state.

## Reproduction Assessment

Yes, source-level. Current schema, normalization, storage, UI mapping, docs, and main-session enqueue code all show that `main` + `systemEvent` cron jobs cannot carry or apply a supported model/provider override.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` for `systemEvent` is the narrowest option, but top-level or explicit session overrides remain plausible product choices.

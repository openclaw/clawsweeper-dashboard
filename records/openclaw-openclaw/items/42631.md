## Summary

Keep open. Current main still treats main-session `systemEvent` cron jobs as text-only system-event injections, while model selection remains limited to `agentTurn` cron payloads and related merged UI work explicitly avoids silent system-event jobs.

## What This Changes

Request job-level provider/model selection for cron jobs using `sessionTarget: "main"` with `payload.kind: "systemEvent"`.

## Best Possible Solution

Define an explicit main-session cron override contract with provider/model validation and session-state isolation, or deliberately document that cheap-model scheduling should use model-backed `agentTurn` jobs instead.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support provider/model overrides for main-session `systemEvent` cron jobs, and which public contract should own that override?

Rationale: Current code intentionally keeps `systemEvent` payloads text-only and the fix would add or change cron API, provider routing, heartbeat, persistence, UI/CLI, and session-state semantics.

Likely owner: Vincent Koc

Owner reason: The current runtime dispatch and payload lines route most directly through recent cron refactor/history owned by this contributor.

Owner confidence: medium

Options:

- **Design explicit override contract (recommended):** Add a cron-owned provider/model override shape with validation, persistence, UI/CLI/docs alignment, and proof that main-session state does not leak.
- **Keep systemEvent text-only:** Document that main-session system events do not select models and steer model-specific recurring work to `agentTurn` jobs.
- **Fold into broader cron schema work:** Defer this decision to the broader cron schema and cost-control API work so model, context, timeout, and spend semantics are decided together.

## Reproduction Assessment

Yes, at source level. Current main keeps `systemEvent` payloads text-only, strips `model` during normalization, and only forwards text/session context when executing main-session cron jobs.

## Solution Assessment

Unclear until maintainers choose the public contract. `payload.model` is plausible, but an explicit cron/session override may be safer because main-session system events do not start a model call by themselves.

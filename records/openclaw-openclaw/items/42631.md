## Label Justifications

- `P2`: The issue affects cron cost/model-routing ergonomics for scheduled automation, but it is a bounded feature/API decision rather than an outage.
- `impact:session-state`: The reported workaround manually edits session metadata, and the requested fix would alter how main-session cron runs choose or isolate session model state.
- `impact:auth-provider`: The requested behavior directly affects provider/model routing, allowlist validation, and billing model choice for scheduled jobs.

## Summary

Keep open. Current main and v2026.6.11 still keep main-session `systemEvent` cron payloads text-only and only honor per-job `payload.model` for model-backed `agentTurn` cron jobs, so the central requested capability remains missing and needs maintainer product/API direction.

## What This Changes

Allow cron jobs using `sessionTarget: "main"` with `payload.kind: "systemEvent"` to choose a per-job provider/model without editing internal session metadata.

## Best Possible Solution

Define an explicit cron-owned provider/model override contract for main-session system events, validate it through the existing model allowlist/routing rules, and prove the override is scoped to the cron run without manual session-store edits.

Rationale: Current code and docs intentionally treat system events as text-only main-session injections, while the requested fix crosses provider routing, cron persistence, heartbeat execution, session state, CLI/UI, and upgrade semantics that automation should not choose alone.

Owner confidence: high

Options:

- **Design an explicit override contract (recommended):** Add a public cron-owned provider/model override shape, validate it like isolated cron payload models, and prove main-session wake modes do not leak or corrupt session state.
- **Keep systemEvent text-only:** Document this path as unsupported and steer cheap scheduled model calls to isolated/current/custom-session `agentTurn` jobs.
- **Fold into broader cron schema work:** Decide model, context, timeout, and spend semantics together with the broader cron schema/cost-control trackers.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 keep `systemEvent` cron payloads text-only, delete model fields during normalization, and only resolve `payload.model` for `agentTurn` jobs.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` is plausible, but an explicit cron/session override block may be safer because main-session system events enqueue text before a later heartbeat model call.

## Label Justifications

- `P2`: This is a bounded cron/model-routing feature with clear source evidence and limited blast radius, but it needs product/API review before implementation.
- `impact:session-state`: The workaround edits session metadata, and a supported fix must keep cron-only model choices from leaking into normal main-session state.

## Summary

Keep open: current main and the latest release still keep explicit main-session `systemEvent` cron payloads text-only; the merged related work covers isolated `agentTurn` model overrides or UI display, not the requested main-session override contract.

## What This Changes

Request job-level provider/model selection for main-session `systemEvent` cron jobs so recurring jobs can use a cheaper model without editing session metadata.

## Best Possible Solution

Maintainers should choose one explicit cron override contract, validate provider/model through the normal allowlist, scope the override to the cron run, and update schema, normalization, persistence, execution, docs, UI, and focused wake-now/next-heartbeat proof together.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session `systemEvent` cron jobs gain a supported model/provider override contract, and should that contract be `payload.model`, job-level fields, or an explicit `sessionOverride` block?

Rationale: The source gap is clear, but the fix changes public cron API shape, provider/model precedence, persisted cron rows, and main-session state behavior, so automation should not choose the contract without maintainer intent.

Likely owner: steipete

Owner reason: He has the strongest history across cron runtime, session-target semantics, and adjacent model-routing contract work.

Owner confidence: high

Options:

- **Extend `systemEvent` payload.model (recommended):** Add model/provider override support to explicit `systemEvent` payloads as the narrowest extension of the existing cron payload model contract.
- **Add job-level override fields:** Introduce top-level `model`/`provider` or `sessionOverride` fields that apply across payload kinds, accepting a broader persisted API and UI/docs surface.
- **Keep system events session-bound:** Document isolated `agentTurn` jobs and explicit session model selection as the supported recurring-model paths and leave main-session system events tied to session state.

## Reproduction Assessment

Yes, at source level. Current main prunes `model` from explicit `systemEvent` payloads, stores no system-event model, and the main-session enqueue path passes no provider/model override.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` for explicit `systemEvent` jobs looks narrowest, but job-level or explicit session override fields are plausible product choices with different upgrade semantics.

## Summary

Keep open: current main still treats main-session `systemEvent` cron payloads as text-only, strips `model`, and enqueues the run without a provider/model override; the merged Control UI work only covers the existing `agentTurn` model contract.

## What This Changes

The issue requests a first-class per-cron model/provider override for `sessionTarget: "main"` jobs whose payload is `kind: "systemEvent"`.

## Best Possible Solution

Maintainers should choose one explicit cron override contract, validate it through the normal provider/model allowlist path, and prove both wake-now and next-heartbeat main-session behavior without requiring manual session-store edits.

## Maintainer Decision

Required: true

Question: Should main-session `systemEvent` cron jobs gain a supported model/provider override contract, and should that contract be `payload.model`, top-level job fields, or a dedicated override block?

Rationale: The source gap is clear, but the fix changes public cron schema, provider precedence, session-state isolation, and upgrade behavior, so automation should not pick the permanent API shape alone.

Likely owner: steipete

Owner confidence: high

Options:

- **Extend systemEvent payload.model (recommended):** Add model/provider validation and transient run-scoped application to the existing payload-style contract, with tests proving no main-session override leakage.
- **Add explicit job override fields:** Create a top-level or `sessionOverride` contract that applies across payload kinds, accepting the broader schema/docs and migration surface.
- **Keep systemEvent text-only:** Document isolated `agentTurn` as the supported per-job model path and leave main-session system events tied to the target session's model state.

## Reproduction Assessment

Yes, source-level. Current schema, normalization, persistence, and main-session execution show `systemEvent` payloads cannot carry a supported model/provider override and the enqueue path forwards only text/session context.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` for `systemEvent` is the narrowest existing-style option, but a top-level or explicit override block remains a plausible product choice.

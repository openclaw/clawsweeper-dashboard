## Summary

Keep open: current main still has no supported model/provider override for `sessionTarget: "main"` plus `payload.kind: "systemEvent"` cron jobs. The merged cron model work covers isolated `agentTurn` jobs and the Control UI now intentionally omits the model choice for silent `systemEvent` jobs.

## What This Changes

Request support for choosing a cheaper job-level model/provider for main-session systemEvent cron jobs without manually editing session metadata.

## Best Possible Solution

Choose one canonical job-level override contract, validate it through existing model allowlist/fallback rules, pass it into the main-session heartbeat/session path directly, and cover schema, runtime, UI, docs, and upgrade behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session systemEvent cron jobs support a first-class model/provider override, and what single public API shape should own it?

Rationale: The request changes public cron protocol and main-session provider/session routing semantics, so automation should not choose between `payload.model`, top-level job fields, or a `sessionOverride` contract without maintainer intent.

Likely owner: Vincent Koc

Owner reason: The current cron protocol, types, and main execution path blame to Vincent Koc's recent maintenance refactor, making him the best code-path owner for the API decision packet.

Owner confidence: medium

Options:

- **Add one canonical cron run override (recommended):** Define a single job-level override contract, route it through allowlist/fallback validation, and pass it to heartbeat/session execution without contextKey encoding.
- **Reuse payload.model on systemEvent:** Extend `systemEvent` payloads with `model` as the smallest schema change, accepting that event text payloads now carry run-routing metadata.
- **Keep main systemEvent default-only:** Document that cheaper per-cron models require isolated `agentTurn` jobs and leave main-session systemEvent jobs on the session/default model.

## Reproduction Assessment

Yes at source level: current schema/types make systemEvent text-only, main cron jobs require systemEvent, and the main execution path never passes a model/provider override into heartbeat execution.

## Solution Assessment

Unclear until maintainers choose the public API shape; `payload.model` is the smallest extension, but a top-level/sessionOverride contract may better express run-level routing.

## Summary

Keep open: current main and v2026.6.11 still keep `systemEvent` cron payloads text-only and only resolve per-job model overrides on `agentTurn`/isolated paths, so this remains a real cron provider/model API gap that needs maintainer product direction.

## What This Changes

Add a first-class per-cron provider/model override for main-session `systemEvent` cron jobs so recurring work can use a cheaper model without manually editing session metadata.

## Best Possible Solution

Maintainers should choose one explicit transient cron override contract, validate it through the allowed model route, and prove wake-now plus next-heartbeat main-session behavior without persisting or leaking the override into the interactive session.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session `systemEvent` cron jobs gain a supported transient model/provider override contract, and if so should that contract be `payload.model`, top-level job fields, or a dedicated override block?

Rationale: The source gap is clear, but the fix changes public cron schema, provider/model precedence, session-state isolation, and upgrade expectations; automation should not pick that API shape without maintainer intent.

Likely owner: tyler6204

Owner reason: CONTRIBUTING.md lists Tyler Yust for cron, and this decision is primarily cron product/API direction rather than a narrow code repair.

Owner confidence: medium

Options:

- **Extend `systemEvent` with transient `payload.model` (recommended):** Allow `systemEvent` payloads to carry a model ref, validate it through existing allowed-model routing, and thread it as a one-run override through main-session cron heartbeat execution without writing permanent session metadata.
- **Add top-level job override fields:** Introduce job-level model/provider fields that apply across payload kinds, accepting a broader cron schema and documentation surface for a more uniform API.
- **Keep systemEvent text-only:** Document isolated/current/session `agentTurn` as the supported per-job model path and leave main-session system events tied to the target session's model state.

## Reproduction Assessment

Yes, source-level. Current schema and runtime types keep `systemEvent` text-only, normalization deletes model fields for explicit system events, and main-session cron enqueue forwards no model/provider override.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` is the narrowest extension, but top-level fields or an explicit override block remain plausible product choices with different upgrade and session-state implications.

## Summary

Keep open: current main and v2026.6.11 still do not provide a supported model/provider override for `sessionTarget: "main"` plus `payload.kind: "systemEvent"`; the merged cron model UI work deliberately covers `agentTurn` jobs only.

## What This Changes

The issue requests a first-class cron job model/provider override for stable main-session `systemEvent` jobs without manually editing session metadata.

## Best Possible Solution

Define one supported cron job override contract for main-session `systemEvent` jobs that sets provider/model on the per-run session before heartbeat, documents validation and fallback behavior, and removes the need for manual session metadata edits.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session `systemEvent` cron jobs accept model/provider overrides via `payload.model`, top-level cron fields, or an explicit session override block, and what should invalid-model/fallback behavior be?

Rationale: The source gap is clear, but the permanent public API shape affects cron protocol compatibility, session state, provider/auth routing, fallback semantics, and upgrade expectations.

Likely owner: steipete

Owner reason: steipete has the strongest recent product/runtime context from cron event-trigger work and the adjacent model UI landing decision.

Owner confidence: high

Options:

- **Design explicit session override block (recommended):** Add a typed cron `sessionOverride` contract for provider/model with explicit validation, fallback, docs, and tests for both `wakeMode` paths.
- **Reuse payload.model on systemEvent:** Extend `systemEvent` payloads with `model` if maintainers want parity with `agentTurn`, but require a direct model propagation path rather than context-key encoding.
- **Keep systemEvent model pinned to session state:** Document dedicated session keys plus `/model` or session metadata as the supported workaround and leave job-level overrides unsupported for now.

## Reproduction Assessment

Yes, at source level: current main accepts model fields only on `agentTurn` cron payloads and the main-session `systemEvent` path enqueues text without provider/model override state. I did not run a live provider job because the schema and runtime path already show the requested contract is absent.

## Solution Assessment

Unclear: job-level model selection is the right user problem, but the best fix needs maintainer choice on API shape and failure semantics. The safest direction is a typed override contract that uses existing session/model override helpers rather than encoding model state in `contextKey`.

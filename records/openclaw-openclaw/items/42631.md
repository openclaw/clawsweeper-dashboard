## Summary

Keep open: current main still treats main-session `systemEvent` cron jobs as text-only system-event injections, while per-job model selection remains limited to `agentTurn`/isolated-style cron paths, so the requested runtime/API behavior is not implemented.

## What This Changes

The issue requests a supported job-level provider/model override for cron jobs that use `sessionTarget: "main"` with `payload.kind: "systemEvent"`.

## Best Possible Solution

Maintainers should choose one explicit cron override contract, validate it through the normal allowed provider/model route, keep the override scoped to the cron run, and prove both wake-now and next-heartbeat main-session behavior without manual session-store edits.

Question: Should main-session `systemEvent` cron jobs gain a supported provider/model override contract, and if so should the contract be `payload.model`, top-level job fields, or an explicit `sessionOverride` block?

Rationale: The source gap is clear, but the fix changes public cron schema, session/provider precedence, persistence behavior, and upgrade expectations; automation should not choose that API shape without maintainer intent.

Owner confidence: high

Options:

- **Extend systemEvent payload.model (recommended):** Allow `payload.model` on `systemEvent` jobs and implement a transient per-run provider/model override with validation and wake-now/next-heartbeat proof.
- **Add an explicit job override block:** Introduce a dedicated `sessionOverride` or top-level provider/model contract that can apply across payload kinds, accepting the broader schema/docs surface.
- **Keep systemEvent text-only:** Document isolated `agentTurn` jobs as the supported per-job model path and leave main-session system events tied to the target session's existing model state.

## Reproduction Assessment

Yes, source-level. Current schema, normalization, storage, CLI/UI creation, and main-session execution show `systemEvent` payloads cannot carry a supported model/provider override while `agentTurn` payloads can.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` for `systemEvent` is the narrowest apparent path, but a top-level or explicit session override remains a product/API choice.

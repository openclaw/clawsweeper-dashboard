## Summary

Keep open: current main still has no supported model/provider override for main-session `systemEvent` cron jobs; the recent merged UI work covers agent-turn jobs and deliberately omits silent/systemEvent model selection.

## What This Changes

Request job-level model/provider selection for cron jobs that run through `sessionTarget: "main"` with `payload.kind: "systemEvent"`.

## Best Possible Solution

Define one explicit cron override contract, validate it through the normal provider/model allowlist, scope it to the cron run, update docs/UI/tool schema as needed, and prove both wake-now and next-heartbeat main-session behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session `systemEvent` cron jobs gain a supported model/provider override contract, and should that contract be `payload.model`, job-level fields, or an explicit `sessionOverride` block?

Rationale: The source gap is clear, but the fix changes public cron schema, provider/model precedence, persisted cron shape, and session-state behavior, so automation should not choose the API shape without maintainer intent.

Likely owner: steipete

Owner reason: He has the strongest recent history on cron session-target semantics and adjacent model-routing behavior.

Owner confidence: high

Options:

- **Extend `systemEvent` payload.model (recommended):** Add `payload.model` to systemEvent cron payloads with explicit provider/model validation and focused proof for wake-now and scheduled main-session routing.
- **Add job-level override fields:** Introduce top-level model/provider or `sessionOverride` fields that apply across payload kinds, accepting the broader API, docs, and migration surface.
- **Keep systemEvent text-only:** Document isolated `agentTurn` and stored cron-session model selection as the supported recurring-model paths and leave main-session system events tied to session state.

## Reproduction Assessment

Yes. Source inspection shows the schema, runtime type, normalizer, persistence codec, UI mapping, and main-session enqueue path have no supported place to carry or apply a `systemEvent` model/provider override.

## Solution Assessment

Unclear until maintainers choose the public API contract. Reusing `payload.model` for `systemEvent` is the narrowest option, but job-level or explicit session overrides are still plausible product choices.

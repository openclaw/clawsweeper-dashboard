## Label Justifications

- `P2`: The request affects cron cost and model-routing ergonomics but is a bounded feature/API decision rather than an outage.
- `impact:session-state`: The current workaround manually edits session metadata, and the requested fix would change how main-session cron runs select or isolate session model state.
- `impact:auth-provider`: The requested behavior directly affects provider/model routing, allowlist validation, and model billing for scheduled jobs.

## Summary

Keep open. Current main still keeps `systemEvent` cron payloads text-only and main-session execution enqueues only text/session context, while merged UI work deliberately scopes model selection to `agentTurn` jobs, so this remains an unresolved product/API decision.

## What This Changes

Request job-level provider/model selection for `sessionTarget: "main"` plus `payload.kind: "systemEvent"` cron jobs so recurring work can use a cheaper model without manual session-store edits.

## Best Possible Solution

Define an explicit public cron/session override contract with provider/model validation for main-session system events, or deliberately document that cheap scheduled model calls must use isolated/current/custom-session `agentTurn` jobs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support explicit provider/model overrides for main-session `systemEvent` cron jobs, and if so should the public contract be `payload.model`, top-level cron fields, or a `sessionOverride` block?

Rationale: Current code treats system events as text-only main-session injections; adding model overrides crosses provider routing, cron persistence, session-state, UI/CLI, and heartbeat semantics that automation should not choose without maintainer intent.

Likely owner: steipete

Owner reason: Peter has the strongest current mix of cron runtime/schema history and product-sensitive scope decisions for the related UI work.

Owner confidence: high

Options:

- **Design an explicit override contract (recommended):** Add a public cron-owned provider/model override shape, validate it like isolated cron payload models, and prove both wake modes do not leak or corrupt session state.
- **Keep system events text-only:** Document this path as unsupported and steer cheap scheduled model calls to isolated/current/custom-session `agentTurn` jobs.
- **Defer into broader cron schema work:** Track this with the broader cron schema and cost-control API work so model, context, timeout, and spend semantics are decided together.

## Reproduction Assessment

Yes, at source level. Current main keeps `systemEvent` payloads text-only, strips `model` during normalization, and only resolves `payload.model` for `agentTurn` cron jobs.

## Solution Assessment

Unclear until maintainers choose the product contract. `payload.model` is plausible, but an explicit cron/session override may be safer because main-session system events do not start a model call by themselves.

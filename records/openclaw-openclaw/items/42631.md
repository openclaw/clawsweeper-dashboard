## Summary

Keep open: current `main` and v2026.6.11 still keep `systemEvent` cron payloads text-only and only honor per-job model selection on `agentTurn`, so the main-session cron model/provider override request remains a real product/API gap.

## What This Changes

The issue requests a first-class per-cron model/provider override for `sessionTarget: "main"` jobs using `payload.kind: "systemEvent"`, so stable main-session cron jobs can run on cheaper models without editing session metadata.

## Best Possible Solution

Maintainers should choose one explicit run-scoped model override contract for main-session `systemEvent` cron jobs, validate provider/model through the normal allowed-model route, and prove both wake-now and next-heartbeat behavior without requiring manual session-store edits.

Options:

- **Extend `systemEvent` with `payload.model` (recommended):** Reuse the existing per-job model contract for the system-event branch, with strict validation and run-scoped application to the cron child session.
- **Add explicit job/session override fields:** Introduce top-level `model`/`provider` or a `sessionOverride` block that can apply across payload kinds, accepting a broader protocol and docs surface.
- **Keep system events text-only:** Document isolated `agentTurn` as the supported per-job model path and leave main-session system events tied to the target session's current model state.

## Reproduction Assessment

Yes, source-level. Current protocol, runtime types, normalization, and main-session execution show `systemEvent` payloads cannot carry or apply a supported model/provider override, while `agentTurn` can.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` for `systemEvent` is the narrowest-looking option because it matches existing cron model selection, but top-level or explicit session overrides remain plausible product choices.

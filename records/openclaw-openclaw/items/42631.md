## Summary

Keep open: current main still treats `main` + `systemEvent` cron jobs as text-only system-event enqueues, while model/provider override support remains on the agent-turn/isolated path. The related merged UI work improves agent-turn cron model selection but intentionally hides model selection for silent system-event jobs because the Gateway runtime would ignore it.

## What This Changes

The issue requests a supported per-job model/provider override for cron jobs that use `sessionTarget: "main"` with `payload.kind: "systemEvent"`.

## Best Possible Solution

Maintainers should choose one explicit cron override contract, validate it through the normal provider/model allowlist path, and prove both wake-now and next-heartbeat main-session behavior without manual session-store edits.

Options:

- **Extend `systemEvent` payloads (recommended):** Allow `payload.model` and provider resolution for `systemEvent` cron payloads, matching the existing agent-turn style while adding main-session proof.
- **Add job-level overrides:** Introduce top-level model/provider fields that apply across payload kinds, accepting a broader cron schema and migration/docs contract.
- **Keep `systemEvent` text-only:** Document isolated `agentTurn` as the supported per-job model path and leave main-session system events tied to session state.

## Reproduction Assessment

Yes, source-level. Current schema, normalization, tests, docs, UI mapping, and main-session enqueue code all show that `main` + `systemEvent` cron jobs cannot carry or apply a supported model/provider override.

## Solution Assessment

Unclear until maintainers choose the public contract. Reusing `payload.model` for `systemEvent` is the narrowest apparent implementation, but top-level job fields or an explicit session override block are still product choices.

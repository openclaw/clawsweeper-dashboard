## Summary

Keep open: current main still does not support model/provider overrides for `main` + `systemEvent` cron jobs. The merged related UI work only exposes the existing agent-turn model contract and explicitly avoids silent/systemEvent jobs, so the central runtime/API request remains unresolved.

## What This Changes

The issue requests first-class per-job model/provider selection for cron jobs that run via `sessionTarget: "main"` and `payload.kind: "systemEvent"`.

## Best Possible Solution

Keep this open and choose one canonical override contract, ideally a job-level model/provider selection that can be validated consistently across schema, normalization, runtime, CLI/docs, and UI without manual session-store edits.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session `systemEvent` cron jobs gain their own model/provider override contract, and should that contract reuse `payload.model`, add top-level `model`/`provider`, or add an explicit `sessionOverride` block?

Rationale: Current code intentionally treats `systemEvent` as text-only and main-session execution as a heartbeat/system-event enqueue; changing it affects public schema, stored cron jobs, session state, provider validation, and docs/UI behavior.

Likely owner: Peter Steinberger

Owner reason: The choice changes core cron/provider/session API semantics and needs maintainer product ownership beyond a narrow repair.

Owner confidence: medium

Options:

- **Add top-level cron override (recommended):** Add job-level `model`/`provider` fields that apply across payload kinds and validate before enqueueing or waking.
- **Reuse payload.model:** Extend `systemEvent` payloads with model/provider fields, accepting a narrower diff but mixing agent-turn-only fields into the text-event payload contract.
- **Defer main-session overrides:** Keep main-systemEvent jobs text-only and document isolated/custom-session agentTurn as the supported per-job model path.

## Reproduction Assessment

Yes from source: current schemas reject `model` on `systemEvent`, normalization prunes it, and the main-session runtime enqueue path has no model/provider parameter. A live Gateway repro was not run because the source contract is explicit.

## Solution Assessment

Unclear until maintainer direction: the requested behavior is valid, but `payload.model`, top-level `model`, and `sessionOverride` have different compatibility and ownership costs.

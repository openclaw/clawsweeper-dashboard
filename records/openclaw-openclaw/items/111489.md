## Summary

Keep open as a product-direction feature request, not a confirmed regression: current main's Workboard gateway dispatch starts only the embedded `subagent.run` path, while the model-facing `workboard_dispatch` tool only advances card lifecycle state. The requested ACP-worker selection would add a new runtime contract and must account for Workboard's claim, heartbeat, completion, and run-record invariants rather than directly substituting an ACP spawn call.

## What This Changes

Add a Workboard worker-runtime selection that can launch cards through configured ACP backends such as OpenCode, Codex, or Claude Code instead of the embedded subagent runtime.

## Best Possible Solution

Define a generic Workboard worker-runtime seam owned by the Workboard plugin and an ACP adapter that maps ACP completion and failure state into the existing card lifecycle, then expose only the selected supported runtime/backend contract with focused lifecycle tests.

- **Keep Workboard embedded-only:** Retain the current embedded-subagent contract and close the request as an unsupported orchestration mode if maintainers do not want ACP workers in Workboard.
- **Externalize the orchestration feature:** Prefer a separately maintained plugin once a sufficient runtime-dispatch extension point exists, keeping bundled Workboard focused on its current embedded worker contract.

## Reproduction Assessment

No, not as a regression: no existing Workboard ACP-worker contract is documented or exposed. Source inspection does reproduce the structural gap—current dispatch selects only the embedded subagent runtime and accepts no ACP runtime/backend option.

## Solution Assessment

No—the proposed direct reuse of ACP spawning is not yet the best supported fix because it bypasses the existing typed Workboard worker lifecycle. A generic runtime seam with explicit ACP lifecycle mapping is the narrower maintainable design if maintainers approve the capability.

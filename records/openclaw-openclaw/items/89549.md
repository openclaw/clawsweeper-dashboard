## Summary

Keep open: current main still has source-level evidence that native `sessions_spawn` child runs persist model/provider fields before starting but do not carry the parent session's effective auth/runtime override into the fresh child session, so the accepted-then-OpenAI-401 failure remains plausible and needs maintainer direction rather than stale cleanup.

## What This Changes

The issue asks for native `sessions_spawn(..., mode:"run")` child runs to avoid accepting work that later fails on a different OpenAI auth/provider route with missing `api.responses.write` scope.

## Best Possible Solution

Define the child-run runtime/auth inheritance contract, then either persist the parent effective runtime/auth-profile state into the child before the `agent` call or reject `sessions_spawn` before acceptance with a direct route/auth error.

Options:

- **Inherit parent runtime/auth by default (recommended):** For same-agent child runs without an explicit incompatible route, copy the parent's effective runtime and auth-profile state into the child and add fail-fast validation for missing scopes.
- **Fail fast on divergent child auth:** Keep child route selection separate but reject `sessions_spawn` before acceptance whenever the child route cannot prove the required OpenAI scope/profile.
- **Delegate to broader OAuth fallback work:** Track only the missing OpenAI OAuth scope/fallback behavior in the related OAuth issue and explicitly document that child sessions do not inherit parent auth context.

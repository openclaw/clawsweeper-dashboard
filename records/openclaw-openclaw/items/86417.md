## Summary

Keep open: current main and the latest release still scope `OPENCLAW_NO_AUTO_UPDATE` to configured startup/background auto-update applies, while supervised `update.run` can still start a managed-service handoff, schedule an `update.run` restart, and write the reported restart-handoff metadata. This remains a maintainer product-contract decision rather than stale cleanup.

## What This Changes

The issue asks for macOS launchd-managed Gateway `update.run` restarts to document and honor an auto-update kill-switch, preferably `OPENCLAW_NO_AUTO_UPDATE=1`, before creating a `gateway-update` restart handoff.

## Best Possible Solution

Maintainers should decide the kill-switch scope, then either gate Gateway-originated managed `update.run` handoffs before restart scheduling and update public docs/tests, or document explicit `update.run` as outside the kill-switch and keep launchd handoff reliability under the broader update-run tracker.

Options:

- **Broaden kill-switch to update.run (recommended):** Treat `OPENCLAW_NO_AUTO_UPDATE=1` as an operator-level block for managed `update.run` handoffs before restart scheduling, with tests/docs for launchd and background auto-update behavior.
- **Keep env scoped to auto-update:** Document that `OPENCLAW_NO_AUTO_UPDATE` only blocks configured background applies and handle no-op/launchd handoff reliability through the broader update-run issue.
- **Add a separate explicit control knob:** Keep the current env behavior and introduce a new documented operator policy for control-plane update execution after security and compatibility review.

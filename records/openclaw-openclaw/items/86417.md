## Summary

Keep open: current main and the latest release still scope `OPENCLAW_NO_AUTO_UPDATE` to configured startup/background auto-update applies, while supervised Gateway `update.run` can still create a managed handoff and schedule an `update.run` restart. The remaining blocker is a maintainer product-contract decision, not stale cleanup.

## What This Changes

The issue asks OpenClaw to document and optionally honor the existing auto-update kill-switch for macOS launchd Gateway `update.run` restart handoffs.

## Best Possible Solution

Maintainers should decide the kill-switch scope, then either gate Gateway-originated managed `update.run` handoffs before restart scheduling and update the public docs, or explicitly document `update.run` as outside the kill-switch and keep launchd handoff reliability tracked under the broader update-run issue.

Rationale: The source fix is narrow, but the behavior changes an operator-requested update path and the public meaning of an existing environment kill-switch; automation should not choose that contract.

Owner confidence: high

Options:

- **Extend the kill-switch to Gateway handoffs (recommended):** Treat the env var as a supervised/headless package-update restart kill-switch, gate `update.run` handoff creation, and document the broader scope.
- **Keep the current narrower scope:** Leave `OPENCLAW_NO_AUTO_UPDATE` limited to configured background auto-update applies and document that explicit `update.run` can still restart managed services.
- **Introduce a separate explicit update-run policy:** Keep the existing env var stable and add a new maintainer-approved config or env policy for blocking explicit control-plane update restarts.

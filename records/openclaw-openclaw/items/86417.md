## Summary

Keep open: current main and v2026.6.11 still scope `OPENCLAW_NO_AUTO_UPDATE` to configured background `update.auto` applies, while supervised Gateway `update.run` can still create a managed handoff and schedule an `update.run` restart. This is not stale cleanup; the remaining blocker is a maintainer product contract decision for the kill-switch scope.

## What This Changes

The issue asks OpenClaw to document and optionally extend the auto-update kill-switch so macOS launchd-managed Gateway `update.run` restarts can be suppressed for headless/supervised deployments.

## Best Possible Solution

Maintainers should choose the kill-switch contract, then either gate Gateway-originated managed `update.run` handoffs before restart scheduling and update docs/tests, or document explicit `update.run` as outside the kill-switch and keep launchd handoff reliability under the broader update-run tracker.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `OPENCLAW_NO_AUTO_UPDATE` suppress explicit Gateway/control-plane `update.run` managed-service handoffs for supervised/headless Gateway installs, or remain limited to configured background `update.auto` applies?

Rationale: Current source, tests, and docs define the env var as a background-auto-update kill-switch, but the reported headless launchd use case wants an operator-wide update-restart block; automation cannot safely broaden that public contract without maintainer intent.

Likely owner: vincentkoc

Owner reason: They introduced the current kill-switch behavior and are the clearest owner signal for deciding whether its public scope should expand.

Owner confidence: high

Options:

- **Broaden the existing kill-switch:** Make `OPENCLAW_NO_AUTO_UPDATE=1` reject or skip Gateway-originated managed `update.run` handoffs before any restart handoff is created, and update docs/tests for that expanded contract.
- **Keep the current split (recommended):** Leave `OPENCLAW_NO_AUTO_UPDATE` scoped to configured background auto-updates and document that explicit `update.run` remains an operator/requested update path.
- **Add a separate explicit update-run guard:** Introduce a distinct operator guard for control-plane `update.run` restarts so background auto-update policy and explicit update commands do not share one ambiguous variable.

Yes for source-level reproduction: current main reads `OPENCLAW_NO_AUTO_UPDATE` in startup/background auto-update code, while supervised `update.run` managed handoff has no matching guard. I did not establish a fresh live macOS launchd repro in this read-only review.

## Solution Assessment

Unclear until maintainers decide the product contract. Reusing the existing env var is a narrow implementation, but it broadens the variable from configured auto-update applies to explicit control-plane update requests.

## Summary

Keep open: current main still keeps `OPENCLAW_NO_AUTO_UPDATE` scoped to configured startup/background auto-update applies, while supervised `update.run` can still start a managed-service handoff and schedule an `update.run` restart. The remaining blocker is a product contract decision about whether the env kill-switch should also block explicit Gateway control-plane updates.

## What This Changes

The issue asks OpenClaw to document and reliably honor an auto-update kill-switch for macOS launchd-managed Gateway update restarts, preferably before any `gateway-update` handoff is created.

## Best Possible Solution

Maintainers should decide the kill-switch scope, then either document the current split clearly or add a guarded `update.run` handoff refusal before `startManagedServiceUpdateHandoff` with focused docs, tests, and live macOS launchd proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `OPENCLAW_NO_AUTO_UPDATE=1` block only configured background `update.auto` applies, or should it also block supervised Gateway `update.run` handoffs from the control plane on headless installs?

Rationale: Current code, docs, and tests deliberately split automatic startup/background applies from explicit `update.run`; changing that split affects operator-requested updates, availability recovery, and update safety semantics.

Likely owner: vincentkoc

Owner reason: vincentkoc introduced the kill-switch behavior and has recent issue-review context on the macOS update.run handoff proof boundary.

Owner confidence: high

Options:

- **Keep the current split (recommended):** Document that `OPENCLAW_NO_AUTO_UPDATE` blocks configured background applies only, while explicit `update.run` reliability stays on the launchd update tracker.
- **Broaden the env kill-switch:** Make supervised `update.run` refuse before managed handoff when `OPENCLAW_NO_AUTO_UPDATE=1`, and update docs/tests/live proof for that new contract.
- **Add a separate update.run policy:** Introduce a distinct operator-controlled setting for control-plane update handoffs instead of overloading the existing auto-update kill-switch.

## Reproduction Assessment

Yes for source-level reproduction: current main still reads `OPENCLAW_NO_AUTO_UPDATE` only in startup auto-update code, while the supervised `update.run` managed handoff path has no matching guard. I did not run a live macOS launchd repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product contract. Reusing the existing env var is a narrow implementation option, but it changes that variable from a background auto-update kill-switch into a blocker for explicit control-plane updates.

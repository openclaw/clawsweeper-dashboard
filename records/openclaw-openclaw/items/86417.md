## Summary

Keep open: current main still treats `OPENCLAW_NO_AUTO_UPDATE` as a configured background auto-update kill-switch, while supervised control-plane `update.run` can still start a managed-service handoff and schedule an `update.run` restart. This is not stale cleanup; it needs a maintainer decision on the headless Gateway update contract.

## What This Changes

The issue requests a documented operator kill-switch for supervised macOS Gateway package/update restarts, preferably by honoring `OPENCLAW_NO_AUTO_UPDATE` before a launchd `gateway-update` handoff is created.

## Best Possible Solution

Define one documented headless Gateway update policy, then align `update.run`, startup auto-update docs, and macOS launchd proof around that policy.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `OPENCLAW_NO_AUTO_UPDATE` suppress supervised control-plane `update.run` managed-service handoffs for headless Gateways, or remain scoped to configured background auto-update applies?

Rationale: Current code and docs intentionally split background auto-update suppression from explicit control-plane update requests, and changing that split affects operator/UI update behavior rather than only fixing a local implementation bug.

Likely owner: steipete

Owner reason: This is a product contract decision across the core updater, Gateway restart loop, and macOS service behavior, where steipete has both recent and foundational history.

Owner confidence: high

Options:

- **Extend the existing kill-switch (recommended):** Treat `OPENCLAW_NO_AUTO_UPDATE=1` as a hard block for Gateway-originated managed update handoffs before restart scheduling, with focused update handler/docs/tests and macOS launchd proof.
- **Keep it background-only:** Document that the env var only suppresses configured automatic applies and route explicit `update.run` restart reliability to the existing launchd handoff issues.
- **Add a separate headless policy:** Introduce a distinct opt-out for supervised control-plane package update restarts, accepting a new config/env surface to avoid overloading the existing variable.

## Reproduction Assessment

Yes for source-level reproduction: current main still reads `OPENCLAW_NO_AUTO_UPDATE` only in startup auto-update code, while the supervised `update.run` managed handoff path has no matching guard. I did not establish a fresh live macOS launchd reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers decide the contract: using the existing env var is the narrowest implementation, but it broadens a background auto-update kill-switch into explicit control-plane update behavior. The safer review outcome is to keep this open for that decision before implementation.

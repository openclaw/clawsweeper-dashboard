## Summary

Keep open: current main and v2026.6.11 still clear device-less shared-token/password WebSocket operator scopes outside narrow local preservation paths, checked-in tests assert the resulting missing-scope behavior, and the remaining fix is a Gateway auth/security policy decision rather than conservative cleanup.

## What This Changes

The issue asks OpenClaw to stop clearing operator scopes for non-local token-authenticated WebSocket operator clients so write-scoped calls such as chat.send can succeed.

## Best Possible Solution

Land a bounded, documented Gateway token-scope or device-token policy with security approval, upgrade proof, and focused WebSocket auth regression coverage.

Question: Should device-less shared-token/password WebSocket operator clients ever receive operator scopes on non-local connections, and if so through which bounded server-derived policy?

Rationale: Current source, docs, and tests intentionally clear self-declared scopes for this class of device-less connection, while the report shows real remote operator workflows need a trusted path; choosing that trust boundary is a maintainer security/product decision.

Likely owner: steipete

Owner confidence: high

Options:

- **Land bounded token scopes (recommended):** Add or land a documented gateway.auth.tokenScopes-style policy with exposure guards, tests, upgrade behavior, and real Gateway proof for trusted headless/shared-token deployments.
- **Trust shared-token scopes:** Treat successful token/password WebSocket auth as sufficient to retain declared operator scopes, accepting the broader shared-secret trust boundary.
- **Require device identity:** Keep clearing device-less self-declared scopes and document that remote write access requires approved device identity or device tokens.

## Reproduction Assessment

Yes, source-reproducible: current main still clears scopes for device-less token/password operator WebSocket connections outside narrow exceptions, and checked-in tests expect the resulting missing-scope behavior. I did not run a live remote Gateway repro in this read-only review.

## Solution Assessment

No for unconditional self-declared scope retention: it fixes the reporter workflow but is too broad for the current security boundary. A bounded server-derived token-scope or device-token policy is the safer maintainable path.

## Summary

Keep open: current main and the latest release still clear device-less shared-token WebSocket operator scopes outside the narrow direct-local backend exception, and checked-in tests assert the resulting missing-scope behavior. The remaining work is security-sensitive policy/design, not stale cleanup.

## What This Changes

Remote shared-token WebSocket operator clients need a supported way to retain or receive write-capable operator scopes instead of connecting successfully and then failing write-scoped methods.

## Best Possible Solution

Settle the shared-token WebSocket scope policy with maintainer security approval, likely through a bounded configured grant model such as `gateway.auth.tokenScopes`, then update the gateway auth tests so remote token-auth operator workflows regain write capability without trusting arbitrary self-declared scopes.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: current connect policy and tests still clear device-less shared-token operator scopes and expect missing-scope failures. I did not run a live remote WebSocket repro in this read-only cleanup review.

## Solution Assessment

No, the issue should not be solved by blindly preserving requested scopes for every valid token client. The best fix needs an explicit, bounded shared-token scope policy with security review and regression coverage for both remote backend workflows and overgrant prevention.

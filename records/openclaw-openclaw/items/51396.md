## Summary

Keep open: current main and v2026.6.11 still clear device-less shared-token WebSocket operator scopes outside narrow local exceptions, and the remaining repair is a Gateway auth boundary decision rather than cleanup-closeable work.

## What This Changes

The issue requests retaining operator scopes for non-local device-less shared-token WebSocket clients so write-scoped calls like chat.send work after successful auth.

## Best Possible Solution

Land a maintainer-approved Gateway shared-token scope policy, such as bounded configured token scopes or a device-bound trust path, with tests, docs, and real Gateway proof.

Owner confidence: high

Options:

- **Use bounded token-scope policy (recommended):** Grant scopes through a maintainer-approved config or device-bound trust contract with non-loopback safeguards, docs, and regression proof.
- **Retain declared scopes by default:** Make valid shared-token clients keep requested scopes without device identity, accepting a broader shared-secret trust model for exposed gateways.
- **Keep current clearing behavior:** Leave device-less network shared-token clients scope-empty and document device identity or configured token scopes as the supported path.

Yes, at source level. Current main still clears scopes for device-less token/password operator WebSocket connections outside narrow local exceptions, and checked-in tests assert the resulting missing-scope behavior.

## Solution Assessment

No for unconditional client-declared scope retention. The maintainable repair needs a security-reviewed Gateway token-scope or device-bound trust policy rather than simply trusting remote connect params.

## Summary

Keep open: current main and the latest release still clear device-less shared-token WebSocket operator scopes outside narrow local preservation paths, tests assert the resulting missing-scope behavior, and the linked fix/design paths are still open rather than merged.

## What This Changes

The issue asks the Gateway WebSocket auth path to preserve operator scopes for non-local clients that successfully authenticate with a shared token or password.

## Best Possible Solution

Keep this issue open until maintainers choose and land a documented Gateway auth policy, ideally preserving safe defaults while giving headless trusted deployments an explicit token-scope path with WebSocket regression coverage.

Rationale: Current source and docs intentionally preserve scopes only for narrow local paths, while the report and related PRs ask to broaden remote token-auth behavior on a Gateway auth boundary.

Options:

- **Default-safe token-scope policy (recommended):** Keep remote device-less scope clearing as the default and land an explicit configured token-scope mechanism for trusted headless deployments.
- **Restore remote token retention:** Treat valid shared token/password auth as enough for non-local WebSocket operators to retain requested scopes by default, accepting the broader security boundary.
- **Close as unsupported remote device-less use:** Document that remote WebSocket operator clients must pair or use a supported token-scope configuration instead of retaining self-declared scopes.

## Solution Assessment

Unclear as a straight bug fix: preserving all remote token-declared scopes would fix the report but conflicts with current docs and security posture. The safer solution is a maintainer-approved token-scope policy or documented remote-operator path with focused WebSocket tests.

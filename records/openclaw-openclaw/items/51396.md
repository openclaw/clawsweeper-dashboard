## Summary

Keep open: current main and the latest v2026.6.11 release still clear device-less shared-token/password WebSocket operator scopes, checked-in tests assert the resulting missing-scope behavior, and the remaining fix needs Gateway security/product review rather than cleanup closure.

## What This Changes

The issue requests that non-local token-auth WebSocket operator clients retain requested operator scopes so write-scoped calls such as chat.send work after a successful handshake.

## Best Possible Solution

Keep this issue open until maintainers land or reject a bounded Gateway auth scope policy; a safe fix should avoid trusting remote self-declared scopes without explicit security approval and focused WebSocket proof.

## Reproduction Assessment

Yes, at source level: current main clears device-less shared-token/password WebSocket scopes and tests expect missing-scope behavior for a valid shared-token operator connection. I did not run a live remote WebSocket reproduction in this read-only review.

## Solution Assessment

Unclear: preserving all client-declared scopes is not clearly the best security boundary because current docs intentionally clear them. The better path is a maintainer-approved bounded policy, such as configured token scopes or a device-token flow, with real Gateway proof.

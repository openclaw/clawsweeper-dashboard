## Summary

Keep open: current main and the latest release still clear device-less shared-token/password WebSocket operator scopes outside narrow local preservation paths, while the remaining fix direction overlaps an open security-sensitive token-scopes proposal rather than an implemented fix.

## What This Changes

The issue asks OpenClaw to preserve operator scopes for non-local WebSocket clients that authenticate with a valid shared token or password so write-scoped RPCs like chat.send do not fail after hello-ok.

## Best Possible Solution

Keep this issue open until maintainers land or reject a bounded Gateway token-scope/device-token policy with security review, upgrade proof, WebSocket auth tests, and docs for trusted remote operator clients.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should non-local device-less shared-token/password WebSocket operator clients receive operator scopes, and should that be unconditional or gated by configured token scopes or device identity?

Rationale: Current source, tests, and docs intentionally clear self-declared scopes for this class of connection, while the report shows real remote operator workflows need a trusted write-capable path; choosing that trust boundary needs maintainer intent.

Likely owner: steipete

Owner reason: steipete owns the open tokenScopes proposal and recent Gateway auth/config work tied to the remaining decision path.

Owner confidence: high

Options:

- **Land bounded token-scope policy (recommended):** Add or land a documented gateway.auth.tokenScopes-style policy with exposure guards, tests, and real Gateway proof for trusted headless/shared-token deployments.
- **Preserve shared-token scopes:** Treat successful token/password WebSocket auth as sufficient to retain declared operator scopes and accept the broader shared-secret trust boundary.
- **Require device identity:** Keep clearing device-less self-declared scopes and document that remote clients must use approved device identity or device tokens for write access.

## Reproduction Assessment

Yes at source level: current main clears scopes for device-less token/password operator WebSocket connections outside narrow exceptions, and checked-in tests expect the resulting missing-scope behavior. I did not run a live gateway repro because this review is read-only.

## Solution Assessment

No for unconditional client-declared scope retention: it is a plausible repair for the reporter's workflow but too broad for the current security boundary. The safer maintainable path is a bounded maintainer-approved token-scope or device-token policy.

## Summary

Keep open: current main and the latest release still clear self-declared scopes for device-less shared-token WebSocket operator clients outside narrow local/backend exceptions, so the reported `operator.write` failure remains source-reproducible and needs a maintainer auth-boundary decision rather than cleanup closure.

## What This Changes

The issue reports that non-local token-authenticated Gateway WebSocket clients lose requested operator scopes, causing `chat.send` and other `operator.write` RPCs to fail after successful auth.

## Best Possible Solution

Resolve the auth policy on this canonical issue with a maintainer-approved server-derived scope or device-token contract, plus docs, tests, and live Gateway proof, rather than silently trusting remote client-declared scopes by default.

## Reproduction Assessment

Yes, at source level: current main clears scopes for device-less token/password operator connects outside narrow local/backend exceptions, and checked-in tests expect scoped RPCs to fail with `missing scope`. I did not run a live remote WebSocket reproduction because this review is read-only and tests could create artifacts.

## Solution Assessment

No, simply preserving remote client-declared scopes is not yet proven to be the best fix because it changes a Gateway auth boundary. The maintainable path should use server-derived configured scopes or device-token approval with explicit maintainer security review.

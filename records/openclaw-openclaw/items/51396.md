## Summary

Keep open: current main and the latest release still clear device-less shared-token WebSocket operator scopes outside narrow local preservation paths, and the remaining fix is an auth-boundary product/security decision with open related work rather than an implemented change.

## What This Changes

The issue requests restoring or defining operator scope retention for non-local device-less WebSocket clients authenticated with a valid shared gateway token or password.

## Best Possible Solution

Land a maintainer-approved Gateway auth policy that keeps safe defaults while giving trusted headless clients an explicit, documented token-scope or device-token path with WebSocket regression coverage.

Question: Should non-local device-less WebSocket clients authenticated with a shared token/password retain operator scopes by default, or should trusted remote/headless deployments use an explicit token-scope/device policy?

Rationale: Current source and docs deliberately clear device-less shared-token scopes except for named local trust paths, while the report asks to broaden remote token-auth behavior on a Gateway authorization boundary.

Likely owner: steipete

Owner confidence: high

Options:

- **Explicit Token-Scope Policy (recommended):** Keep remote device-less scope clearing as the default and land a bounded configured token-scope or device-token path for trusted headless deployments.
- **Restore Remote Token Retention:** Treat valid shared token/password auth as enough for non-local WebSocket operators to retain requested scopes by default, accepting the broader bearer-token trust boundary.
- **Document Unsupported Default:** Keep the current default and document that remote WebSocket operator clients must pair or use a maintainer-approved token-scope path instead of retaining self-declared scopes.

## Reproduction Assessment

Yes, at source level: current main clears device-less shared-token operator scopes outside named local preservation paths, and the default-token suite asserts the connected-with-cleared-scopes missing-scope behavior. I did not run a live remote WebSocket repro in this read-only review.

## Solution Assessment

Unclear as a straight default-retention fix: preserving all remote token-declared scopes would address the report but conflicts with current docs and security posture. The safer solution is a maintainer-approved token-scope or device-token policy with focused WebSocket tests.

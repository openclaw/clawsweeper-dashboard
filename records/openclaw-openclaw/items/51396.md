## Summary

Keep open: current main and the latest release still clear device-less shared-token/password WebSocket operator scopes outside named exceptions, so the reported write-scope failure remains a real auth-boundary issue rather than cleanup-closeable.

## What This Changes

The issue reports that non-local WebSocket clients authenticated with a valid gateway token lose requested operator scopes and then fail write-scoped calls such as chat.send.

## Best Possible Solution

Keep this issue open until maintainers choose and land a security-reviewed Gateway token-scope or device-identity policy, likely through https://github.com/openclaw/openclaw/issues/80836 and https://github.com/openclaw/openclaw/pull/81792 or a successor.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw grant operator scopes to device-less shared-token/password WebSocket clients, and if so should that happen through configured token scopes, a device-bound trust flow, or not at all?

Rationale: Current main, docs, and tests intentionally clear self-declared scopes for this class of client, while the reported workflow needs write-capable remote/headless operators; changing that boundary is a security/product choice, not a mechanical cleanup.

Likely owner: steipete

Owner reason: steipete owns the current tokenScopes implementation candidate and has recent history on the affected Gateway auth/config surface.

Owner confidence: high

Options:

- **Bound Configured Token Scopes (recommended):** Land a reviewed tokenScopes-style policy that grants only configured scopes with explicit network/admin safety bounds and regression proof.
- **Require Device Identity:** Keep device-less shared-token clients scope-empty and document that remote/headless operators must use device tokens or pairing to obtain write/admin scopes.
- **Preserve Client-Declared Scopes:** Allow successful shared-token/password clients to retain requested scopes, accepting the larger shared-secret trust boundary after explicit maintainer approval.

## Reproduction Assessment

Yes, at source level. Current main still clears scopes for device-less token/password operator connections outside narrow exceptions, and checked-in tests expect the resulting missing-scope behavior; no live remote WebSocket repro was run in this read-only review.

## Solution Assessment

No for unconditional self-declared scope retention. The maintainable path is a security-reviewed Gateway policy such as configured token scopes or a device-bound trust path, because current docs and tests intentionally clear device-less self-declared scopes by default.

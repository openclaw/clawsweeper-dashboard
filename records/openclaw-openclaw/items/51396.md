## Summary

Keep open: current main and v2026.6.11 still clear device-less shared-token/password WebSocket operator scopes outside narrow local backend exceptions, checked-in tests assert the resulting missing-scope behavior, and the remaining repair is a security-sensitive Gateway auth policy decision rather than conservative cleanup closure.

## What This Changes

The issue requests that non-local WebSocket clients authenticated with a valid Gateway token retain operator scopes so write-scoped methods such as `chat.send` do not fail after `hello-ok`.

## Best Possible Solution

Keep this issue open until maintainers choose and land a bounded, security-reviewed Gateway policy for shared-token WebSocket scopes, likely through the tokenScopes design path or an equivalent device-bound trust contract.

Required: true

Question: Should device-less shared-token/password WebSocket operator clients be allowed to receive `operator.write` or stronger scopes, and should that come from client-declared scopes, configured token scopes, or a device-bound trust path?

Rationale: The source-level bug is clear, but the repair decides how much authority a network client with only the shared Gateway secret can obtain, which is a security and product boundary rather than a mechanical cleanup choice.

Likely owner: steipete

Owner reason: `steipete` owns the open tokenScopes implementation candidate and has recent commits on the cleared-scope baseline, making them the best current routing target for the product/security choice.

Owner confidence: high

Options:

- **Bounded configured token scopes (recommended):** Continue through the `gateway.auth.tokenScopes` or successor design, with explicit exposure guards, docs, upgrade behavior, and Gateway auth regression proof before closing this issue.
- **Trust requested scopes after shared auth:** Allow valid shared-token/password WebSocket clients to retain their requested scopes directly, accepting the larger network shared-secret authority boundary.
- **Keep fail-closed default:** Preserve scope clearing for device-less network clients and document that remote write/admin access requires pairing, tokenScopes, or another explicit trust mechanism.

## Reproduction Assessment

Yes, at source level. Current main still clears scopes for device-less token/password operator connections outside narrow exceptions, and checked-in tests expect the resulting missing-scope behavior; I did not run a live remote WebSocket repro in this read-only review.

## Solution Assessment

No for unconditional self-declared scope retention. The maintainable path is a security-reviewed Gateway policy such as configured token scopes or a device-bound trust path, because current docs and tests intentionally clear device-less self-declared scopes by default.

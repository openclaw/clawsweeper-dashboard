## Summary

Keep open: current main and v2026.6.11 still clear device-less shared-token/password WebSocket operator scopes outside narrow trusted-local exceptions, and the remaining fix is a Gateway auth boundary decision rather than conservative cleanup closure.

## What This Changes

The issue asks OpenClaw to retain operator scopes for non-local clients that successfully authenticate to the Gateway with a shared token before calling write-scoped methods such as chat.send.

## Best Possible Solution

Keep this issue open until maintainers choose and land a security-reviewed Gateway token-scope or device-identity policy, likely through https://github.com/openclaw/openclaw/issues/80836 and https://github.com/openclaw/openclaw/pull/81792 or a successor.

Kind: security_boundary

Question: Should OpenClaw grant operator scopes to device-less shared-token WebSocket clients, and if so should those scopes come from a bounded server-side tokenScopes policy rather than client-declared connect scopes?

Rationale: Current source and docs intentionally clear self-declared scopes for device-less shared-token clients, while the report asks to preserve them; changing that behavior decides who can receive operator.write/admin over a network token-auth boundary.

Likely owner: steipete

Owner reason: steipete owns the current tokenScopes proposal and has recent history on the default-token scope baseline.

Owner confidence: high

Options:

- **Adopt bounded tokenScopes policy (recommended):** Review and land a server-configured token-scope contract with real Gateway proof, upgrade behavior, and privileged-scope guardrails.
- **Restore client-declared scope retention:** Treat successful shared-token auth as enough to retain requested connect scopes, accepting the broader trust model for device-less network clients.
- **Keep current device-bound policy:** Keep clearing self-declared scopes by default and document that non-local operator clients need device identity or an explicit server-side trust path.

## Reproduction Assessment

Yes, at source level. Current main still clears scopes for device-less token/password operator connections outside narrow exceptions, and checked-in tests expect the resulting missing-scope behavior; I did not run a live remote WebSocket repro in this read-only review.

## Solution Assessment

No for unconditional self-declared scope retention. The maintainable path is a security-reviewed Gateway policy such as configured token scopes or a device-bound trust path, because current docs and tests intentionally clear device-less self-declared scopes by default.

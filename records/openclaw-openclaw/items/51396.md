## Summary

Keep open: current main and v2026.6.11 still clear device-less shared-token/password WebSocket operator scopes outside narrow local preservation paths, and the active token-scopes path is still an unmerged security/product decision.

## What This Changes

The issue requests that non-local token-auth WebSocket operator clients retain requested operator scopes after successful shared-token auth instead of having those scopes cleared.

## Best Possible Solution

Keep this issue open until maintainers land a bounded, documented Gateway token-scope or device-token policy with security review, upgrade proof, and focused WebSocket auth regression coverage.

Question: Should device-less shared-token/password WebSocket operator clients receive operator scopes on non-local connections, and if so through what bounded policy?

Rationale: Current source, tests, and docs intentionally clear self-declared scopes for this class of connection, while the report shows real remote operator workflows need a trusted path; choosing the trust boundary needs maintainer security/product intent.

Likely owner: steipete

Owner confidence: high

Options:

- **Land bounded token scopes (recommended):** Add or land a documented gateway.auth.tokenScopes-style policy with exposure guards, tests, and real Gateway proof for trusted headless/shared-token deployments.
- **Preserve shared-token scopes:** Treat successful token/password WebSocket auth as sufficient to retain declared operator scopes and accept the broader shared-secret trust boundary.
- **Require device identity:** Keep clearing device-less self-declared scopes and document that remote clients must use approved device identity or device tokens for write access.

## Reproduction Assessment

Yes, at source level: current main clears scopes for device-less token/password operator WebSocket connections outside narrow exceptions, and checked-in tests expect the resulting missing-scope behavior. I did not run a live gateway repro because this review is read-only.

## Solution Assessment

No for unconditional client-declared scope retention: it is a plausible repair for the reporter's workflow but too broad for the current security boundary. The safer maintainable path is a bounded maintainer-approved token-scope or device-token policy.

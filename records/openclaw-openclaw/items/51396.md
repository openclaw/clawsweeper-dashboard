## Summary

Keep open: current main and v2026.6.11 still clear device-less shared-token/password WebSocket operator scopes outside explicit exceptions, checked-in tests and docs preserve that behavior, and the remaining fix is unmerged security/product-sensitive Gateway auth work.

## What This Changes

The issue requests that non-local token-authenticated Gateway WebSocket operator clients retain requested operator scopes so write-scoped methods such as chat.send do not fail after a successful handshake.

## Best Possible Solution

Keep this issue open until maintainers choose and land a bounded, security-reviewed Gateway token-scope or device-token policy, likely through https://github.com/openclaw/openclaw/issues/80836 and https://github.com/openclaw/openclaw/pull/81792 or a successor.

- **Require Device Identity:** Keep remote device-less shared-token clients scope-empty and close or retarget linked work to document device-token/pairing requirements for write-capable clients.
- **Defer Auth Direction:** Leave this and the tokenScopes design open until Gateway/security owners choose the trust model for headless deployments.

## Reproduction Assessment

Yes, at source level. Current main still clears scopes for device-less token/password operator connections outside narrow exceptions, and checked-in tests expect the resulting missing-scope behavior; I did not run a live remote WebSocket repro in this read-only review.

## Solution Assessment

No for unconditional self-declared scope retention. The maintainable path is a security-reviewed Gateway policy such as configured token scopes or a device-bound trust path, because current docs and tests intentionally clear device-less self-declared scopes by default.

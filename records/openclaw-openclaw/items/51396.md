## Summary

Keep open: current main and the latest release still clear device-less shared-token/password WebSocket operator scopes outside narrow local preservation paths, checked-in tests assert the resulting missing-scope behavior, and the remaining fix is a Gateway auth/security policy choice rather than conservative cleanup.

## What This Changes

The issue reports that non-local token-authenticated Gateway WebSocket operator clients lose requested operator scopes and then fail write-scoped methods such as chat.send.

## Best Possible Solution

Keep this issue open until maintainers land a bounded, documented Gateway token-scope or device-token policy with security review, upgrade proof, and focused WebSocket auth regression coverage.

Rationale: Current tests and docs intentionally clear self-declared scopes for this class of device-less connection, while the user report shows real remote operator workflows need a trusted path; choosing that trust boundary is a maintainer security/product decision.

Likely owner: steipete

Owner confidence: high

Options:

- **Land bounded token scopes (recommended):** Add or land a documented gateway.auth.tokenScopes-style policy with exposure guards, tests, and proof for trusted headless/shared-token deployments.
- **Preserve shared-token scopes:** Treat successful token/password WebSocket auth as sufficient to retain declared operator scopes, accepting the broader shared-secret trust boundary.
- **Require device identity:** Keep clearing device-less self-declared scopes and document that remote clients must use approved device identity/device tokens for write access.

Yes, at source level: current main still clears scopes for device-less token/password operator WebSocket connections outside narrow exceptions, and checked-in tests expect the resulting missing-scope behavior. I did not run a live gateway repro because this review is read-only.

## Solution Assessment

No for unconditional self-declared scope retention: it is a plausible repair for the reporter's workflow but too broad for the current security boundary. The safer maintainable path is a bounded maintainer-approved token-scope or device-token policy.

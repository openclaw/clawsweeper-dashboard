## Summary

Keep open: current main still allows device-less shared-token/password operator connects while clearing their requested scopes outside narrow local/control-ui exceptions, and checked-in gateway auth tests still assert the resulting missing-scope behavior. The linked PR/design work is not a merged fix, so this remains a security-sensitive gateway auth bug rather than conservative cleanup closure.

## What This Changes

The issue asks OpenClaw to preserve operator scopes for non-local WebSocket clients that successfully authenticate with a gateway token so write-scoped methods such as chat.send do not fail after hello-ok.

## Best Possible Solution

Resolve this in the WebSocket gateway auth policy by preserving only explicitly authorized operator scopes for valid remote shared-token/password clients, while keeping unauthorized, node-role, Control UI, trusted-proxy, and local-backend exceptions covered by focused regression tests.

## Reproduction Assessment

Yes. Source inspection and checked-in gateway auth tests show that a device-less valid shared-token operator connect is allowed but scopes are cleared, producing missing operator.write on write-scoped calls.

## Solution Assessment

No. Closing is not the best way to solve this issue; the maintainable path is a security-reviewed gateway connect-policy change with regression coverage, not a stale cleanup close or a broad config workaround.

## Label Justifications

- `P1`: The defect can permanently strand inter-agent replies in an unmonitored session, breaking an active agent communication workflow.
- `impact:message-loss`: Replies are delivered to a ghost session rather than the session the sending agent monitors, making them effectively lost to that workflow.
- `impact:session-state`: The problem is caused by divergent canonical and historical session keys creating separate conversation state.

## Summary

Current main still propagates the caller’s persisted session key into inter-session provenance, so the reported ghost-session routing failure remains credible. The open linked fix PR is the canonical implementation candidate, and this issue should remain open until that PR is reviewed and merged or replaced.

## What This Changes

Normalize the source session key used by `sessions_send` so replies return to the dmScope-resolved session rather than a stale historical session key.

## Best Possible Solution

Land one bounded fix that computes the dmScope-canonical requester key once at the `sessions_send` boundary and reuses it across every downstream routing consumer, with focused legacy-key and non-main-scope regression coverage.

Yes at source level: seed a caller with a historical per-account/channel/peer key while `dmScope` is `main`, send through `sessions_send`, and observe that the reply address differs from the currently monitored `agent:<id>:main` session. A live current-main run was not performed.

## Solution Assessment

Yes in direction: canonicalizing at the `sessions_send` owner boundary is narrower and safer than changing global turn resolution, provided the resulting key is shared by every A2A routing consumer and non-main scopes are covered.

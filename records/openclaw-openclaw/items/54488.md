## Summary

Keep open: current main still admits active non-heartbeat same-session work into the follow-up queue and drains that queue until empty without a foreground-yield or priority check, so the reported session-lane starvation is still a real core scheduler issue.

## What This Changes

The issue requests a fix for follow-up queue draining monopolizing a per-session lane and delaying inbound or outbound channel work for many minutes.

## Best Possible Solution

Define a core scheduler policy where fresh foreground user/control work can overtake, interrupt, or defer accumulated background/follow-up work while preserving ordering within each priority class and one active writer per session.

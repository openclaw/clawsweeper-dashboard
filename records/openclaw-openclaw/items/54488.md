## Summary

Keep open: current main still admits active same-session non-heartbeat work into the follow-up FIFO and drains that queue until empty, so fresh foreground messages can still sit behind accumulated follow-up/background work. Recent fixes improved dormant-drain startup, queued TUI ownership, command-lane priority, and lane timeouts, but they do not implement the scheduler fairness policy reported here.

## What This Changes

The issue reports that follow-up drain work can monopolize a per-session lane so fresh Discord, WhatsApp, and CLI messages wait many minutes behind queued background turns.

## Best Possible Solution

Define core scheduler fairness so fresh user/control work can overtake, yield, or interrupt accumulated background/follow-up work while preserving one active writer per session and route/collect ordering within each priority class.

## Reproduction Assessment

Yes, at source level: active non-heartbeat follow-up turns still enter the same follow-up queue, the queue appends FIFO, and the drain loop awaits queued work until empty. I did not run the full live Discord/WhatsApp timing scenario in this read-only pass.

## Solution Assessment

Unclear as an automated fix: the right owner boundary is the core auto-reply/session scheduler, but maintainers need to choose the foreground-vs-background policy before a repair branch is safe.

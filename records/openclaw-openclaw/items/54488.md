## Summary

Keep open: current main still enqueues active non-heartbeat same-session work into the follow-up queue and drains that queue until empty, so the reported session-lane starvation remains meaningful. Recent fixes added priority mechanics and fixed narrower dormant-drain/recovery cases, but they do not define the foreground-vs-background scheduler policy this issue needs.

## What This Changes

The issue asks OpenClaw to prevent queued follow-up/background work from monopolizing a session lane and delaying fresh inbound or control messages for many minutes.

## Best Possible Solution

Define a core scheduler policy where fresh foreground user/control work can overtake, interrupt, or defer accumulated background/follow-up work while preserving one active writer per session and deterministic ordering within each priority class.

## Reproduction Assessment

Yes at source level: active non-heartbeat work still enters the follow-up queue, the queue appends FIFO, and the drain loop awaits queued follow-ups until empty. I did not run the full 20-30 minute Discord/WhatsApp live scenario in this read-only review.

## Solution Assessment

Unclear for automation: the owner boundary is core reply/session scheduling, but maintainers need to choose the user-priority, background-abort/yield, and transcript-ordering semantics before a repair PR is safe.

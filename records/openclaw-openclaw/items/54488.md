## Summary

Keep open: current main still enqueues non-heartbeat same-session work behind active runs and drains queued follow-up work until empty, so the reported foreground starvation remains a real scheduler issue rather than a stale report.

## What This Changes

Reports that follow-up queue draining monopolizes a session lane and delays inbound or outbound channel work for many minutes.

## Best Possible Solution

Define a core scheduler policy where fresh user/control work can overtake, interrupt, or defer background follow-up drains while preserving one active writer per session and ordering within each priority class.

## Reproduction Assessment

Yes at source level: current main still routes active non-heartbeat work into the follow-up queue and drains queued work until empty. I did not run the full 20-30 minute Discord/WhatsApp live scenario in this read-only review.

## Solution Assessment

Unclear as an automated fix: the implicated owner boundary is core reply/session scheduling, but maintainers need to choose foreground priority, background abort/yield, and transcript ordering semantics before implementation.

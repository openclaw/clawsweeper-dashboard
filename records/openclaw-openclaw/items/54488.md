## Summary

Keep open: current main and v2026.6.11 still admit active non-heartbeat turns into the follow-up queue, append them FIFO, and drain follow-up work until empty, so the reported foreground starvation is not implemented away.

## What This Changes

The issue reports that follow-up/background session work can monopolize a single-session lane and delay inbound Discord, WhatsApp, and other user dispatch for many minutes.

## Best Possible Solution

Define a core scheduler policy where fresh foreground user/control work can overtake, interrupt, or defer accumulated background/follow-up work while preserving ordering within each priority class, then cover follow-up drain, active-reply admission, and stale recovery with regression tests.

## Reproduction Assessment

Yes. Source inspection shows active non-heartbeat turns still enqueue into the same FIFO follow-up queue and the drain loop continues until empty; I did not run a long live multi-channel stall reproduction in this read-only pass.

## Solution Assessment

Unclear as a final implementation. A cap, priority insert, or admission bypass could reduce starvation, but maintainers need to choose the foreground/background scheduler semantics before this is safe to automate.

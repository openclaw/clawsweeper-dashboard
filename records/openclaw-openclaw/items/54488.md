## Summary

Keep open: current main still routes active non-heartbeat same-session work into the follow-up queue and drains that queue until empty, so the foreground starvation problem remains. Open related PRs and issues cover narrower admission or recovery slices, but none is a merged canonical fix for the scheduler-fairness behavior.

## What This Changes

The issue reports that follow-up/background drain work can monopolize a single-session lane and delay inbound Discord, WhatsApp, and other user dispatch for minutes.

## Best Possible Solution

Define one core scheduler policy where fresh user/control work can overtake, interrupt, or defer accumulated background/follow-up work while preserving ordering within each priority class and a single active writer per session.

## Reproduction Assessment

Yes at source level: active non-heartbeat work still enqueues as follow-up, accepted queue items append without priority, and the drain loop awaits queued follow-ups until the queue/dropped work is empty. I did not run the full 20-30 minute Discord/WhatsApp live scenario in this read-only review.

## Solution Assessment

Unclear as an automated fix: the owner boundary is core reply/session scheduling, but maintainers need to choose the policy for user priority, background abort/yield, and session-state safety before a new repair branch is safe.

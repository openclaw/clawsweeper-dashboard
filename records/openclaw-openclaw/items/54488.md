## Summary

Keep open: current main and latest release v2026.6.11 still enqueue active non-heartbeat follow-up work into a FIFO follow-up queue and drain it until empty, so the reported foreground starvation is not fixed. Recent fixes and open PRs address narrower admission, dormant-drain, cron-binding, or recovery slices, but they do not replace this canonical scheduler-fairness issue.

## What This Changes

The issue reports session-lane starvation where follow-up/background work monopolizes a single session lane and delays inbound dispatch or outbound sends for many minutes.

## Best Possible Solution

Define a core scheduler policy where fresh foreground user/control work can overtake, interrupt, or defer accumulated background/follow-up work while preserving ordering within each priority class and one safe active writer per session.

## Reproduction Assessment

Yes, at source level: active non-heartbeat follow-up turns still enqueue, the queue appends FIFO, and the drain loop awaits queued follow-ups until the queue/dropped work is empty. I did not run the full 20-30 minute Discord/WhatsApp live scenario in this read-only review.

## Solution Assessment

Unclear as an automated fix: the owner boundary is core reply/session scheduling, but maintainers need to choose the policy for foreground priority, background abort/yield, and session-state safety before a repair PR is safe.

## Summary

Keep open: current main and the latest release still enqueue active non-heartbeat turns into the same follow-up queue and drain that queue until empty, so the foreground scheduler-fairness problem is not fixed. Related fixes and PRs cover narrower drain-start, admission, or recovery slices, but they do not supersede this canonical starvation report.

## What This Changes

Reports that same-session follow-up drain and active reply work can monopolize the session lane, delaying inbound/outbound channel messages and stop/control turns for minutes.

## Best Possible Solution

Define one core scheduler policy where fresh foreground user and stop/control work can overtake, interrupt, or defer accumulated background/follow-up work while preserving one active writer per session and ordering within each priority class.

## Reproduction Assessment

Yes at source level: current main still sends active non-heartbeat follow-up work into the same queue and drains that queue until empty. I did not run the full 20-30 minute Discord/WhatsApp live scenario in this read-only review.

## Solution Assessment

Unclear as an automated fix: the right owner boundary is core reply/session scheduling, but maintainers need to choose foreground priority, background abort/yield, and transcript-safety semantics before implementation.

## Summary

Keep open: current main has partial foreground/deadlock handling, but active non-heartbeat work still enters the follow-up queue and the drain still runs until empty, so the reported scheduler fairness and message-delay problem remains. Field comments through OpenClaw 2026.6.9 and open related items support this as the canonical session-lane starvation tracker, not a stale duplicate.

## What This Changes

This issue reports follow-up drain monopolizing a shared session lane, causing Discord, WhatsApp, Telegram, and CLI message dispatch to wait 20-30 minutes behind queued follow-up/background work.

## Best Possible Solution

Define a core scheduler policy where fresh user/control work can overtake, yield, or interrupt accumulated background/follow-up work while preserving ordering within each priority class and one active writer per session.

Question: What scheduler invariant should OpenClaw use when fresh user/control work arrives while same-session background or follow-up work is queued or running?

Rationale: The bug is source-backed, but the durable fix requires choosing between foreground preemption, bounded drain fairness, and preserving current follow-up ordering semantics; code alone cannot pick that product/safety tradeoff.

Likely owner: steipete

Owner reason: He owns the most recent adjacent foreground-delivery and current-main queue/drain changes and is the best available routing candidate for the scheduler-policy decision.

Owner confidence: high

Options:

- **Foreground-over-background scheduler (recommended):** Make fresh user/control work overtake or abort/defer background follow-up work while preserving serialization and ordering inside each priority class.
- **Bounded follow-up drain:** Cap consecutive follow-up turns or elapsed drain time before yielding, which reduces starvation but may not fully fix stop/control semantics during active background work.
- **Keep current queue semantics:** Document and rely on existing followup/collect waiting behavior plus diagnostics/recovery, accepting that foreground messages can remain delayed behind backlogs.

## Summary

Keep open: current main still routes active non-heartbeat same-session work into the follow-up queue, appends it FIFO, and drains that queue until empty, so the reported foreground starvation is not implemented away. Related open PRs cover narrower admission or cron-trigger slices but do not replace this canonical scheduler-fairness issue.

## What This Changes

The issue reports session-lane starvation where follow-up/background drain work monopolizes per-session execution and delays inbound channel dispatch for many minutes.

## Best Possible Solution

Define a core scheduler policy where fresh foreground user/control work can overtake, interrupt, or defer accumulated background/follow-up work while preserving ordering within each priority class and one active writer per session.

## Reproduction Assessment

Yes, at source level: active non-heartbeat follow-up-mode turns still enqueue, queue items append FIFO, and the drain loop awaits queued follow-ups until the queue/dropped work is empty. I did not run the full 20-30 minute Discord/WhatsApp live scenario in this read-only review.

## Solution Assessment

Unclear as an automated fix: the owner boundary is core reply/session scheduling, but maintainers need to choose the foreground-priority, background abort/yield, and session-state safety policy before a repair PR is safe.

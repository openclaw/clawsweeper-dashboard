## Summary

Keep open: current main and merged #100205 address a narrower foreground-delivery deadlock, but active same-session work still enters the follow-up queue and the drain still runs until empty through maxConcurrent=1 session lanes, so the reported starvation remains.

## What This Changes

The issue requests that follow-up/background drain work stop monopolizing a session lane and delaying fresh inbound or outbound channel work.

## Best Possible Solution

Define a default scheduler policy that yields or deprioritizes background/followup drain work for fresh user-visible same-session turns, with focused regression coverage for ordering, cancellation, and channel routing.

Question: What scheduler semantics should OpenClaw use when fresh user/channel turns arrive while follow-up or background work is draining the same session?

Rationale: The source path is clear, but the durable fix must choose how to balance foreground responsiveness against transcript ordering, collect batching, cancellation, and existing followup behavior.

Likely owner: steipete

Owner reason: Recent #100205 work touched the same foreground/followup admission boundary and is the closest current maintainer context.

Owner confidence: medium

Options:

- **Foreground-yielding drain (recommended):** Fresh user-visible turns preempt or pause background/followup drain work while preserving queued delivery context and transcript ordering invariants.
- **Bounded FIFO batches:** Keep FIFO semantics but cap consecutive followup drain work and reschedule the remainder so fresh work gets periodic admission.
- **Keep strict FIFO:** Leave the current model intact and document long same-session waits as expected for followup-heavy sessions.

## Reproduction Assessment

Yes at source level: active non-heartbeat turns still enqueue as followups, followups append to a FIFO queue, and the drain runs until empty through serialized session lanes.

## Solution Assessment

Unclear until maintainer policy is chosen; foreground-yielding drain behavior appears strongest, but ordering and cancellation semantics need owner review.

## Summary

Current main already implements the central behavior: provider-side AbortError("This operation was aborted") is allowed to advance to the configured fallback candidate while caller/client aborts still stop the run. The fix is backed by merged PR 90908 and current regression coverage, but it does not appear to be in the latest release tag I inspected.

## What This Changes

The issue reports that provider transport AbortError messages like "This operation was aborted" are not classified as timeouts, so configured model fallbacks are skipped after a primary provider timeout.

## Best Possible Solution

Keep the current main provider-side AbortError fallback contract from merged PR 90908, and ask users on the latest release to retest after the next release that contains the fix.

## Reproduction Assessment

Yes at source level: current main has a regression test that drives runWithModelFallback through provider-side AbortError("This operation was aborted") and verifies the fallback candidate runs. I did not run a live custom-provider timeout in this read-only review.

## Solution Assessment

Yes: the merged runtime-boundary fix is better than the regex-only suggestion because it preserves caller/client abort cancellation while allowing provider-owned AbortErrors to continue the fallback chain.

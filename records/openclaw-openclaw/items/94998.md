## Summary

Close: current main now solves the central provider-side AbortError fallback path by distinguishing provider aborts from caller aborts and proving `AbortError("This operation was aborted")` advances to a fallback when no external abort signal is set. This is current-main-only cleanup; I could not prove the full current-main behavior is included in the latest release.

## What This Changes

The issue reports that provider transport `AbortError` timeouts with message `This operation was aborted` are not detected as timeouts, so configured model fallbacks are skipped.

## Best Possible Solution

Keep the current provider-side AbortError versus caller-abort split on main and let the next release carry it rather than reopening the regex-only report.

## Reproduction Assessment

Yes for the source-level behavior: current main has regression coverage showing provider `AbortError("This operation was aborted")` advances to the next model when no external abort signal is set. I did not run a live custom-provider timeout.

## Solution Assessment

Yes. The current-main solution fixes the model-fallback abort boundary instead of only broadening the regex, preserving no-fallback behavior for caller aborts while allowing provider-side aborts to fail over.

## Summary

Keep this PR open. It is a plausible server-side complement to the client-side backoff proposed in https://github.com/openclaw/openclaw/pull/114266, but the new cache also retains rejected Git-operation promises for its full 10-second TTL; that turns a transient local Git failure into repeated unavailable responses. It also needs after-fix real behavior proof before merge.

## What This Changes

The branch extracts session pull-request local Git discovery into a helper and adds two bounded 10-second process-local caches so Control UI summaries do not respawn Git for every request.

## System Context

The gateway serves Control UI session pull-request summaries by resolving the session checkout, reading local Git branch facts, and querying GitHub for matching pull requests. These summaries feed sidebar indicators and chat suggestions, so their local Git work is on a repeated request path.

## Architecture Diagram

flowchart LR
  A[Control UI sidebar and chat] --> B[Gateway session PR request]
  B --> C[Resolve session checkout]
  C --> D[Local Git context cache]
  D --> E[Branch facts cache]
  E --> F[GitHub pull request lookup]
  F --> G[PR summaries for UI]

## Best Possible Solution

Cache only successful local Git results, evict the exact entry when its promise rejects, add regression coverage for retry after a transient failure, and attach redacted after-fix runtime evidence showing cold, warm, expiry, and recovery behavior.

## Reproduction Assessment

No high-confidence live reproduction was provided for the patched behavior. The supplied profile and the request path make the repeated Git-spawn problem source-reproducible, while the new rejection-caching regression follows directly from the cache implementation.

## Solution Assessment

No; caching local Git facts is a reasonable direction, but caching the raw in-flight promise is not the narrowest safe implementation because it preserves transient failures for the entire TTL. Cache successful results and evict failed loads instead.

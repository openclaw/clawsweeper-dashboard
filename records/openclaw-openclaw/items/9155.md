## Summary

Keep open: current main still lacks `cron.defaults.delivery` or an equivalent configurable primary cron delivery target, and the related closed duplicate/broader issues plus the open hard-coded fallback PR do not replace this focused product/security decision.

## What This Changes

Request to add `cron.defaults.delivery` so cron jobs can inherit a default delivery channel and target instead of repeating per-job delivery config or falling back to the last reply target.

## Best Possible Solution

Keep this focused tracker open and, if maintainers approve the policy, implement one canonical cron delivery default across config types, strict schema/help/docs, service/API creation, CLI and Control UI creation/editing, and regression tests proving per-job delivery wins before the global default and any `last` fallback.

## Reproduction Assessment

Yes for the source-level gap: current main omits `cron.defaults.delivery` from config types/schema/docs and still defaults missing detached cron delivery to announce/last. This is not a failing-bug reproduction because the item requests a new config capability.

## Solution Assessment

Unclear until maintainers approve the recipient-default policy. The best implementation shape is a single canonical config/default path with explicit per-job precedence and coverage across service, CLI, UI, docs, and tests.

## Summary

This issue remains necessary: the requested primary cron delivery default is not established by the current documented cron configuration, while the recent cron delivery fix only makes omitted-delivery behavior consistent across creation paths. The request is security-sensitive because an implicit last-route fallback can send scheduled output to an unintended recipient, so maintainers should choose a durable inheritance and retargeting contract before adding another configuration surface.

## What This Changes

Add a `cron.defaults.delivery` setting that supplies a channel and recipient for cron jobs whose delivery routing is omitted, while preserving explicit per-job delivery as the highest-priority choice.

## System Context

Cron job creation turns CLI, gateway, and declarative inputs into persisted schedules; when a job runs, its delivery plan sends the result to a configured channel target. This request would insert a configuration-derived target between explicit job delivery and the current implicit routing behavior.

## Architecture Diagram

flowchart LR
  A[CLI, gateway, or declarative cron input] --> B[Cron job creation]
  C[Per-job delivery fields] --> D[Delivery resolution]
  E[Configured cron delivery default] --> D
  D --> F[Persisted cron job]
  F --> G[Scheduled agent run]
  G --> H[Channel delivery target]

## Best Possible Solution

Adopt one creation-time, persisted delivery-default contract: explicit job delivery wins; otherwise a validated `cron.defaults.delivery` is copied into newly created jobs; existing jobs keep their stored delivery unchanged. Keep failure-notification routing separate, document the privacy boundary, and add regression coverage for CLI, gateway, and declarative creation paths.

- **Persist defaults only for new jobs (recommended):** Add a validated cron delivery default that is copied only when creating jobs with omitted delivery, preserving existing jobs and explicit per-job routing.
- **Evaluate defaults at each run:** Let config changes retarget jobs that still lack explicit delivery, accepting a broader operational and privacy impact.
- **Keep per-job routing only:** Retain the current explicit channel/target workflow and decline another global recipient configuration surface.

## Reproduction Assessment

No live reproduction was run in this read-only review, but the source-backed path is clear: create an isolated cron job without explicit channel/target and inspect its resolved persisted delivery. The supplied prior review shows no configuration default exists to participate in that resolution.

## Solution Assessment

Unclear until maintainers choose the lifecycle contract. A creation-time persisted default is safer than runtime inheritance because later configuration edits should not silently retarget already scheduled jobs.

## Summary

Keep this issue open for maintainer product and security review. Current documentation exposes only `cron.failureDestination` as a global destination and continues to require primary cron delivery to be configured per job; the recent merged cron fix restores consistent implicit announce behavior but does not add a durable primary recipient default. This remains the focused tracker for the requested policy.

Likely related people:
- cxbAsDev — recent cron delivery implementation contributor (medium confidence).
- Chris Zhang — earlier cron/config delivery-surface contributor identified by feature history (low confidence).

## What This Changes

Add a `cron.defaults.delivery` configuration value that supplies a primary channel and recipient when cron jobs do not define their own delivery route.

## Best Possible Solution

Define one security-reviewed core cron recipient policy, then implement it through canonical config/schema/help plus tests for explicit-job precedence, default application, account selection, and upgrade behavior; do not overload failure-alert routing or add a parallel plugin workaround.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a persistent core default recipient for primary cron announce delivery, and should that default be copied into a job when it is created or resolved dynamically when the job runs?

Rationale: The choice determines whether config edits can silently retarget existing scheduled output and therefore sets the durable privacy, upgrade, and operator contract.

Likely owner: cxbAsDev

Owner reason: Their recent merged work owns the central initial-delivery invariant that the chosen policy would extend.

Owner confidence: medium

Options:

- **Creation-time defaulting (recommended):** Use `cron.defaults.delivery` only to fill omitted delivery at job creation, persist the resolved route on the job, and keep later config changes from retargeting existing jobs.
- **Runtime inheritance:** Resolve omitted primary delivery from current config at every run, accepting that a later config change intentionally retargets existing jobs.
- **Keep explicit-only routing:** Retain per-job delivery and captured-route behavior without adding a global primary recipient default.

## Solution Assessment

Unclear: a default could reduce repeated per-job configuration, but the proposed global field needs a maintainer decision on creation-time versus runtime inheritance before it is the safest solution.

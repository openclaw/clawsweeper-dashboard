## Summary

Keep this issue open: current main has safer active-chat capture and validated fallback routing, but it still lacks a configurable primary cron delivery destination. The remaining work is a security-sensitive product decision about recipient precedence and inheritance timing, not conservative cleanup.

## What This Changes

Add a global cron delivery default so newly created jobs can use a configured channel and recipient when they lack an explicit destination.

## Best Possible Solution

Add an operator-visible creation-time default for new jobs only, with precedence `explicit job destination > trusted captured creation origin > configured cron default > existing validated fallback`, while leaving stored existing jobs unchanged and showing the resolved route before save/run.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should a configured cron delivery default be copied into new jobs at creation time, or inherited dynamically whenever each job runs, and should it override a trusted active-chat origin?

Rationale: These choices determine whether config changes can reroute existing scheduled output and whether a global recipient may displace the chat that authorized the job; source inspection cannot establish that security and UX policy.

Likely owner: tyler6204

Owner reason: The strongest feature-history trail for cron delivery modes and routing points to this contributor.

Owner confidence: high

Options:

- **Snapshot safe fallback (recommended):** Copy the configured default into new jobs only when neither an explicit destination nor a trusted creation origin exists, leaving existing jobs unchanged.
- **Always prefer configured default:** Apply the global destination ahead of captured chat context, making fleet routing predictable but potentially surprising users creating reminders from another chat.
- **Dynamic runtime inheritance:** Resolve the default on every run so config edits update all jobs, accepting that existing jobs can silently change recipients.

## Reproduction Assessment

Yes at source level: current main documents a global failure-notification destination but no primary cron delivery default, while successful announce delivery still depends on per-job or captured routing data. This establishes the missing capability without requiring a failing runtime test.

## Solution Assessment

Unclear as proposed: a global config default is plausible, but placing it ahead of captured creation context could create new misrouting. Creation-time fallback after explicit and trusted-origin routing is the narrower, safer design.

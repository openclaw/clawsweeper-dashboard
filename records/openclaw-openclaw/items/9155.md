## Summary

Keep open. Current main and release v2026.6.11 still lack a primary cron delivery-default route, the same-request duplicate was closed in favor of this issue, and the remaining work needs an explicit recipient-inheritance product decision.

## What This Changes

Add a `cron.defaults.delivery` configuration object that supplies omitted delivery settings for cron jobs while preserving explicit job-level values.

## Best Possible Solution

Define `cron.defaults.delivery` as a validated creation-time template for new jobs, persist the resolved route, preserve explicit job fields, and expose identical precedence and preview behavior in the CLI, Control UI, schema help, and docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `cron.defaults.delivery` be snapshotted into newly created jobs, or dynamically inherited by jobs with omitted fields whenever global configuration changes?

Rationale: The inheritance model determines whether later configuration edits can silently redirect unattended output and affects storage, previews, editing, privacy expectations, and upgrade behavior.

Likely owner: steipete

Owner reason: Peter has the strongest combined signal from recent initial-default history and the prior focused product review of this issue.

Owner confidence: medium

Options:

- **Snapshot new jobs (recommended):** Merge and validate defaults during creation, persist the route on the job, and keep existing recipients stable after configuration changes.
- **Dynamic inheritance:** Resolve omitted fields from current global configuration on every run, enabling centralized retargeting but allowing silent recipient changes.
- **No inherited recipient:** Keep recipients explicit per job and improve only CLI or Control UI creation defaults and safe `last` resolution.

## Reproduction Assessment

No bug reproduction is applicable because this is a feature request. The capability gap is high-confidence from the current strict configuration schema, job-creation resolver, docs, and latest release.

## Solution Assessment

Yes, with clarified semantics: a cron-owned delivery default is the narrowest maintainable solution, but it should be a persisted creation-time template rather than an unspecified dynamic recipient fallback.

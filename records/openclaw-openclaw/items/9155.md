## Summary

Keep this issue open: current documentation still requires a per-job delivery route or captured active-chat target and does not expose a global primary cron delivery destination; deciding how a persisted default may select recipients is a security-sensitive product contract.

## What This Changes

The issue requests a `cron.defaults.delivery` configuration object that supplies a default announce channel and target when a cron job omits its own delivery route.

## Best Possible Solution

Define one explicit, validated primary-delivery-default contract for new cron jobs, with job-level delivery taking precedence and existing stored jobs left unchanged unless a deliberate migration is approved.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a global primary `cron.defaults.delivery` recipient, and should that default be copied into newly created jobs or resolved dynamically when each job runs?

Rationale: This choice sets durable recipient authority and upgrade behavior across channels and accounts; source and documentation show supported per-job and captured-session routes, but no existing contract chooses between creation-time inheritance and runtime retargeting.

Likely owner: steipete

Owner reason: Recent cron/configuration work and the prior issue review make steipete the strongest available decision-routing candidate.

Owner confidence: medium

Options:

- **Creation-time default with explicit storage (recommended):** Apply a validated default only when a new job omits delivery, store the resolved route on that job, and preserve existing jobs unchanged.
- **Runtime-resolved global default:** Resolve omitted job routes from current config at execution time, accepting that a configuration edit can retarget future runs of existing jobs.
- **Keep per-job routes only:** Retain explicit CLI/API delivery fields and captured active-chat targets without adding another persisted configuration surface.

## Reproduction Assessment

Yes, at source/documentation level: create an isolated announce cron job without a stored channel and target, then observe that supported resolution uses the captured route or `last`/configured fallback rather than a user-defined global cron default. A live Gateway run was not needed to establish that the requested configuration surface is absent.

## Solution Assessment

Unclear: a global default can remove repetitive job configuration, but the proposed shape is not safely complete until maintainers choose creation-time versus runtime inheritance and define recipient/account validation.

## Label Justifications

- `P2`: This is a normal-priority cron delivery configuration feature with concrete privacy and routing impact but no current core outage by itself.
- `impact:security`: The request is intended to reduce scheduled cron output falling back to unintended prior chat targets and exposing sensitive content.
- `impact:message-loss`: Without a stable default target, cron output can route to the wrong destination or fail when the implicit `last` route is stale or unsuitable.

## Summary

Keep open. Current main and v2026.6.11 still lack `cron.defaults.delivery` or an equivalent configurable primary cron delivery target; existing context inference and failure-notification defaults do not cover the requested fleet-wide primary recipient default.

## What This Changes

Add a `cron.defaults.delivery` configuration default so cron jobs can inherit an announce delivery channel and recipient instead of repeating per-job delivery or falling back to `last`.

## Best Possible Solution

Implement a maintainer-approved cron primary delivery default across config schema, service/runtime precedence, CLI/UI/API/docs, and regression tests, with job-level delivery taking priority over the global default and `last` remaining the final fallback.

## Reproduction Assessment

Yes for source-level behavior: current code lacks `cron.defaults.delivery`, stores omitted isolated delivery as announce-only, and resolves omitted detached output delivery to `last`. A live cron run is not required to confirm this feature/config gap.

## Solution Assessment

Unclear until maintainers choose the product policy. The requested precedence model is coherent, but a new default-recipient config is privacy-sensitive and overlaps adjacent cron delivery policy work, so this should remain a maintainer-reviewed feature rather than an automatic repair.

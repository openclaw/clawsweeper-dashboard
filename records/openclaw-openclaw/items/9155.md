## Summary

Keep this issue open: current main still has no configurable primary cron delivery destination, while omitted isolated-agent delivery is persisted as announce-only and therefore still depends on later target resolution. The request remains useful, but recipient precedence and inheritance timing are security-sensitive product choices rather than conservative cleanup.

## What This Changes

Add a global `cron.defaults.delivery` setting that supplies a default cron announcement channel and recipient when a job does not specify one.

## Best Possible Solution

Adopt a creation-time default for new isolated announce jobs—snapshotting a validated channel, target, and optional account into the stored job—while preserving explicit per-job delivery, leaving existing jobs unchanged, and aligning schema, help, docs, CLI, Control UI, and precedence tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should a global cron delivery destination be snapshotted into newly created jobs, inherited dynamically at each run, or remain an explicit per-job setting?

Rationale: Each choice changes recipient stability, upgrade behavior, and whether later config edits can silently reroute scheduled output, so repository policy and security intent are required before implementation.

Likely owner: steipete

Owner reason: The available history and issue discussion connect this person most directly to current configuration policy, documentation, and the prior product-triage decision to keep the focused request open.

Owner confidence: medium

Options:

- **Snapshot New Jobs (recommended):** Add a validated global default that is copied into newly created jobs, with explicit per-job delivery winning and existing jobs remaining unchanged.
- **Resolve At Runtime:** Have jobs without explicit delivery inherit the current global destination on every run, accepting that config changes can reroute existing jobs.
- **Keep Explicit Delivery:** Decline the new config surface and instead improve cron creation flows so users visibly choose and persist a destination for each job.

## Reproduction Assessment

Yes at source level. Current main exposes no primary cron delivery-default config, and omitted isolated-agent delivery is stored only as `{ mode: "announce" }` without a channel or recipient.

## Solution Assessment

No, not completely as proposed. The config key is plausible, but the maintainable solution must define creation-time versus runtime inheritance, existing-job behavior, account isolation, validation, and precedence across all creation surfaces.

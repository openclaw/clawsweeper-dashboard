## Label Justifications

- `P2`: This is a normal-priority cron delivery configuration feature with concrete privacy and routing impact but no current core outage by itself.
- `impact:security`: The request is intended to reduce scheduled cron output falling back to unintended prior chat targets and exposing sensitive content.
- `impact:message-loss`: Without a stable default target, cron output can route to the wrong destination or fail when the implicit `last` route is stale or unsuitable.

## Summary

Keep open. Current main and v2026.6.11 still lack `cron.defaults.delivery` or an equivalent configurable primary cron delivery target, and the open related PRs address adjacent hard-coded fallback/no-channel behavior rather than this config surface.

## What This Changes

The issue requests a new `cron.defaults.delivery` configuration surface so cron jobs can inherit a default announce channel and target before falling back to `last`.

## Best Possible Solution

Keep this issue open as the focused product tracker and implement a maintainer-approved cron delivery default across config schema, service/runtime precedence, CLI/UI/API/docs, and regression tests, with job-level delivery taking priority.

## Reproduction Assessment

Yes for source-level behavior: current code lacks `cron.defaults.delivery`, stores omitted isolated delivery as announce, and resolves omitted detached output delivery to `last`. A live cron run was not attempted because this was a read-only review of a feature/config request.

## Solution Assessment

Unclear until maintainers choose the product policy. The requested precedence model is coherent, but a new default-recipient config is privacy-sensitive and overlaps open cron delivery policy PRs, so it should stay open for maintainer review rather than be auto-implemented.

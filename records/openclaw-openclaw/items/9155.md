## Summary

Keep open. Current main now fails closed instead of inheriting an unsafe keyless recipient from shared session state, but it still has no configurable general cron delivery destination; this remains a distinct, recently supported product and recipient-security decision.

## What This Changes

Add an operator-configured default delivery destination for cron jobs that omit job-level channel and recipient settings.

## Best Possible Solution

Preserve fail-closed protection against guessed recipients and, if sponsored, add a validated opt-in destination that is copied into newly created jobs, with explicit job delivery taking precedence and announce mode requiring a concrete channel-compatible recipient.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should a configured cron delivery destination be copied into new jobs or dynamically inherited by existing jobs whose delivery fields are omitted?

Rationale: The choice determines whether later configuration changes may silently redirect already-created unattended jobs, which is a recipient-security and product contract decision rather than a mechanical implementation detail.

Likely owner: steipete

Owner reason: The initial-delivery centralization commit and prior focused triage make this the strongest available owner for the destination-stability decision.

Owner confidence: high

Options:

- **Copy On Creation (recommended):** Persist the configured destination into each new job so later config changes cannot silently retarget existing jobs.
- **Inherit At Runtime:** Resolve omitted job delivery from current config on every run, enabling centralized changes but allowing existing jobs to be retargeted.
- **Keep Explicit Only:** Retain job-level recipient configuration and improve CLI/UI templates, previews, and warnings instead of adding inheritance.

## Reproduction Assessment

Yes for the reported feature gap: current types, strict schema, creation logic, and docs expose no general configured cron delivery destination. The historical unsafe-recipient path is now separately source-reproducible as a fail-closed refusal rather than current misdelivery.

## Solution Assessment

No, dynamic runtime precedence is not yet the best proven solution. Copying a validated operator default into newly created jobs better removes repetitive setup while preserving each job's recipient across later configuration changes.

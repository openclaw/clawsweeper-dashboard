## Summary

Keep this issue open. Current main and v2026.6.11 still lack a primary cron delivery-recipient default, the same focused request is not owned by a viable replacement PR, and recent discussion confirms real demand; implementation should wait for a maintainer decision on safe inheritance semantics.

## What This Changes

Add a global cron delivery default so new jobs without explicit delivery can use a configured channel and recipient.

## Best Possible Solution

Use a creation-time default copied into newly created jobs, preserve explicit per-job precedence, leave existing jobs unchanged, reject incomplete or ambiguous recipient settings, and show the resolved delivery in CLI and Control UI before saving.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should cron jobs inherit a configured default recipient, and should that inheritance apply only when a job is created or dynamically on every run?

Rationale: This choice changes recipient-routing semantics, inspectability, security posture, and upgrade behavior; repository source cannot establish the intended product contract.

Likely owner: steipete

Owner reason: They introduced the current create-time resolver and have the strongest recent history across the cron and config decision surfaces.

Owner confidence: high

Options:

- **Creation-time default (recommended):** Copy the configured default into new jobs so every persisted job has a stable, inspectable recipient while existing jobs remain unchanged.
- **Run-time default:** Resolve omitted delivery against current configuration on every run, enabling centralized changes but silently retargeting existing jobs.
- **Keep recipients explicit:** Do not add recipient inheritance; instead improve warnings and setup surfaces so users must confirm each job destination.

## Reproduction Assessment

Yes at source level: current main’s strict cron schema has no primary delivery default, and job creation only preserves explicit delivery or injects announce mode without a recipient. No runtime execution was needed to establish this feature gap.

## Solution Assessment

No, not exactly as proposed: dynamically falling back to cron.defaults.delivery could silently retarget existing jobs. Copying a validated default into each new job at creation time is safer and easier to inspect.

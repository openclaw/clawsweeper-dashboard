## Summary

Current main still lacks a configurable primary cron delivery recipient, and adjacent open work changes fallback behavior rather than implementing this request. Keep the issue open because choosing recipient inheritance versus explicit or silent delivery is a real product and security-boundary decision.

## What This Changes

Add a `cron.defaults.delivery` configuration that supplies a default announce channel and recipient when a cron job omits them.

## Best Possible Solution

Define one security-conscious precedence across config, creation, CLI, Control UI, and runtime: explicit job delivery wins; an opt-in configured default may fill omitted announce destinations; otherwise use a clearly documented safe fallback, with validation and regression tests preventing cross-mode or stale-recipient inheritance.

Options:

- **Opt-in configured recipient (recommended):** Add a narrow cron channel and recipient default that fills omitted announce destinations while preserving explicit per-job overrides.
- **Require explicit job routing:** Diagnose announce jobs without a concrete destination and keep recipient selection entirely job-local.
- **Silent when omitted:** Run detached jobs without delivery unless each job explicitly opts into announcement routing.

## Reproduction Assessment

Yes for the current limitation: current-main source shows no primary cron recipient default, create-time omission produces only announce mode, and runtime falls back to channel last. This is source-reproducible rather than a live failing test.

## Solution Assessment

Unclear pending maintainer direction. The proposed opt-in config is the best of the presented inheritance options, but explicit per-job routing or silent-by-default execution remain legitimate security policies that cannot be selected mechanically.

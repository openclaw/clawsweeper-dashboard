## Summary

Current main and the latest release still lack a global normal cron delivery recipient default. This remains the focused tracker, but unattended-recipient inheritance and upgrade behavior require an explicit maintainer product/security decision before implementation.

## What This Changes

Add `cron.defaults.delivery` so jobs without explicit delivery routing can use a configured default mode, channel, and recipient.

## Best Possible Solution

Materialize the configured route into newly created jobs, leave existing jobs unchanged, and expose the resolved recipient consistently in CLI and Control UI; use runtime inheritance only if maintainers explicitly accept implicit fleet-wide retargeting.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `cron.defaults.delivery` be copied into newly created jobs, or dynamically inherited on every run by jobs that omit delivery routing?

Rationale: This determines whether a global config edit can silently change recipients for existing unattended jobs; source evidence cannot decide that security and upgrade contract without maintainer intent.

Likely owner: steipete

Owner reason: Peter introduced the centralized create-time default, has the broadest recent cron/config history, and already participated in this issue's product triage.

Owner confidence: high

Options:

- **Materialize on creation (recommended):** Copy the configured route into new jobs so recipients remain explicit, inspectable, and stable across later config changes.
- **Inherit at runtime:** Resolve omitted routes from current global config on every run, accepting that existing jobs can be retargeted without editing their records.
- **Keep routes job-local:** Avoid a global recipient and reduce repetition through CLI and Control UI presets that persist explicit per-job delivery.

## Reproduction Assessment

Yes, at high confidence from source inspection: current main has no global normal-delivery default, create-time omission persists announce-only delivery, and runtime resolves the missing recipient through `last`. This establishes a feature gap rather than a broken existing contract.

## Solution Assessment

No, not yet as specified. The capability is useful, but dynamic runtime precedence is not the safest proven design; materializing the configured route when a job is created better preserves auditability and upgrade stability.

## Label Justifications

- `P2`: This is a useful, bounded cron ergonomics and routing improvement with explicit per-job workarounds, but recipient semantics need product review before implementation.
- `impact:security`: An unstable or inherited default recipient can expose scheduled output to an unintended chat or channel.
- `impact:message-loss`: The current fallback can misroute delivery or fail closed when the last-route destination is unsuitable or unavailable.

## Summary

Keep this issue open: current main still documents explicit per-job delivery, active-chat capture, and `channel: "last"` fallback without a configurable primary cron recipient default; the focused request remains useful, but recipient inheritance is a security-sensitive product decision rather than an automatic fix. ([docs.openclaw.ai](https://docs.openclaw.ai/cli/cron))

## What This Changes

Add a `cron.defaults.delivery` configuration surface that supplies default channel and recipient fields when a cron job does not specify them.

## Best Possible Solution

Materialize a validated default recipient into newly created jobs only when their announce delivery omits routing fields, preserve explicit job and active-chat targets, leave existing jobs unchanged, and expose the resolved route before saving or running the job.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a global cron recipient default, and if so should it be materialized into new jobs at creation time rather than inherited dynamically at every run?

Rationale: Both approaches reduce repetitive configuration, but runtime inheritance can silently retarget existing scheduled output after a config edit, while creation-time materialization is safer but does not centrally retarget an existing fleet.

Likely owner: @tyler6204

Owner reason: Cron runtime and delivery behavior fall directly within the documented cron ownership area, with @joshavant as the adjacent security/config reviewer.

Owner confidence: high

Options:

- **Materialize On Creation (recommended):** Apply configured channel, target, account, and thread fields only while creating jobs that omit them, then store the resolved delivery explicitly so later config edits cannot silently reroute existing jobs.
- **Dynamic Runtime Inheritance:** Resolve missing delivery fields from current config at every run, accepting that a global config edit can immediately retarget existing scheduled output.
- **Keep Explicit Delivery:** Do not add another config surface; instead improve CLI and Control UI templates, route previews, and warnings so users choose a deterministic target for each job.

## Summary

Keep this PR open: the revised branch bounds memory, but it now hashes only the first 50 MiB of every larger file, so different file contents beyond that prefix produce the same installed-plugin index hash. The submitted evidence is focused test output only and does not show an after-fix installed-plugin indexing run.

## What This Changes

The PR changes oversized installed-plugin file hashing from an unbounded whole-file synchronous read to a bounded 64 KiB synchronous read loop capped at 50 MiB, with a sparse-file regression test.

## Best Possible Solution

Keep bounded memory but remove the byte cap from the hashing loop so oversized regular files are read in fixed-size chunks through EOF, then prove an actual installed-plugin index refresh with an oversized valid metadata file.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, from source: create two regular files larger than 50 MiB with identical first 50 MiB and different trailing bytes; the proposed loop returns the same digest for both, while current main hashes their complete contents.

## Solution Assessment

No. Fixed-size chunking is the right bounded-memory approach, but stopping at 50 MiB is not compatible with the current full-content SHA-256 contract; the loop should continue through EOF.

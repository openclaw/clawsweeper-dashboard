## Summary

Keep open: the reported false-unknown behavior remains on current main, but this patch treats evidence of a prior vector write as proof that the vector store is ready now. Persisted dimensions can survive a later sqlite-vec load or installation failure, so the new fast-path result can become a false positive and contradict the documented unprobed-status semantics.

## What This Changes

The PR makes plain builtin-memory status infer vector-store readiness from persisted `vectorDims` metadata when vector search is enabled and adds regressions for indexed, chunks-only, and vector-disabled databases.

## Best Possible Solution

Keep the fast path non-probing, expose persisted vector-index presence separately from live store readiness, and reserve `ready` for a successful current-runtime probe; cover stale metadata plus extension-load failure and align the CLI documentation with the final states.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, from source and supplied real proof: a fresh status-purpose manager has no vector probe result, so current main renders the store as unknown even after a real vector index was previously written.

## Solution Assessment

No, not in its current form. Persisted dimensions are a good signal that an index exists, but they are not sufficient evidence that the vector extension is available now; the maintainable fix should represent those states separately.

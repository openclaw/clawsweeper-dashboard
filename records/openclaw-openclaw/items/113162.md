## Summary

This draft PR addresses a real MCP catalog-loading failure and includes credible after-fix SDK integration evidence, but it still bypasses the SDK’s `listTools()` metadata setup on its fallback path and deliberately accepts responses outside the MCP SDK’s declared tool-schema contract. Keep it open for an explicit MCP interoperability decision and a design that preserves SDK metadata before merge.

## What This Changes

The PR retries MCP `tools/list` with a restricted parser when the SDK rejects an object-only composed input or output schema solely because it omits a root `type: "object"`, then uses that path in bundled-agent and node-host MCP discovery.

## System Context

OpenClaw connects to configured MCP servers, requests their tool catalog, and turns accepted tool definitions into callable agent and node-host tools. The MCP SDK validates the catalog first; this PR adds a fallback parser between that SDK boundary and OpenClaw’s downstream schema validation.

## Best Possible Solution

Choose the compatibility policy explicitly; if OpenClaw supports object-only composed roots, implement it through an SDK-supported path that preserves all normal tool metadata and limit the exception to the demonstrated input-schema case unless output-schema support is separately justified.

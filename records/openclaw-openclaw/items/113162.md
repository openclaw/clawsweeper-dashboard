## Summary

Keep this draft open. The linked report is a real current regression, but the fallback accepts schemas that the MCP protocol and installed SDK reject without proving they describe object arguments, and it bypasses the SDK metadata cache needed by later tool calls.

## What This Changes

This draft PR retries MCP `tools/list` with a relaxed response schema when the SDK rejects a tool schema solely because it lacks a root-level `type: "object"`, then uses that helper in bundled-agent and node-host MCP catalog loading.

## System Context

OpenClaw connects to configured MCP servers, loads their paginated tool catalogs, and exposes those tools to agent runtimes and node-host callers. The MCP SDK validates each catalog response and also caches tool output-schema and task-support metadata for subsequent calls.

## Architecture Diagram

flowchart LR
  A[MCP server] --> B[tools/list response]
  B --> C[MCP SDK validation]
  C --> D[Catalog loader]
  D --> E[Agent tool catalog]
  D --> F[Node-host tools]
  E --> G[Later tools/call requests]

## Best Possible Solution

Keep the supported SDK path as the catalog authority. If maintainers want an interoperability exception, first obtain or add an SDK-level API that validates only demonstrably object-only composed schemas while preserving list-tools metadata caching, then cover discovery and later tool-call behavior together.

## Label Justifications

- `P2`: This is a bounded cron scheduler reliability bug that can silently miss one deferred startup catch-up run after a second restart.
- `impact:other`: The concrete impact is cron scheduler catch-up reliability, which is maintainer-visible but outside the more specific owned impact labels.

## Summary

Keep open: current main still stores the startup catch-up deferral marker only in process-local cron service state while persisting the deferred `nextRunAtMs`, so a second fresh startup can still lose the marker. Two open pull requests currently claim this issue with closing references, but neither is merged, so this issue should remain the canonical tracker until one lands or is replaced.

## What This Changes

Preserve startup overflow cron catch-up deferrals across a second gateway restart so staggered catch-up runs are not silently advanced to their next natural cron slots.

## Best Possible Solution

Land one narrow durable cron runtime marker fix, hydrate it before startup maintenance repair, keep ordinary stale-future repair enabled for unrelated jobs, clear the marker when the deferred slot fires or the job becomes irrelevant, then close this issue.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, at source level: seed more than the missed-job budget, let startup persist a staggered non-agentTurn cron `nextRunAtMs`, then construct a fresh service state before that slot and run startup maintenance. I did not execute the repro because this is a read-only review, but the current code path matches the reported failure.

## Solution Assessment

Yes. The best fix is a durable internal cron runtime marker or equivalent persisted derivation; broad repair suppression, a new config knob, or a separate JSON sidecar would be weaker boundaries.

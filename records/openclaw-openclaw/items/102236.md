## Label Justifications

- `impact:other`: The concrete impact is cron scheduler catch-up reliability, which is maintainer-visible but outside the more specific owned impact labels.

## Summary

Keep open: current main still stores the startup catch-up deferral marker in process-local cron service state, so the reported cross-restart missed-run path remains plausible. Two open PRs now specifically claim this fix, so this issue should stay open until one reviewed implementation lands or both are closed.

## What This Changes

The issue reports that startup overflow cron catch-up deferral markers are process-local, so a second gateway restart before the deferred slot fires can silently advance the job to its next natural cron slot.

## Best Possible Solution

Land one reviewed fix that persists or durably derives the pending startup catch-up deferral marker in canonical cron runtime state, keeps unrelated future-slot repair enabled, clears the marker when the slot is consumed or invalidated, and then close this issue.

Yes, at source level: persist a staggered non-agentTurn overflow catch-up slot, construct a fresh cron service state before that slot, and run startup maintenance. I did not run tests in this read-only cleanup pass, but current main still matches the reported failure path.

## Solution Assessment

Yes. A durable marker in SQLite-backed cron runtime state, or an equivalent durable derivation, is the narrow maintainable fix; broad repair disablement or a new user config knob would be the wrong boundary.

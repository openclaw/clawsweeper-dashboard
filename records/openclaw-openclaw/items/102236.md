## Summary

Keep open: current main still stores the startup catch-up deferral exemption only in process-local cron service state, so a fresh gateway process can retain the persisted staggered `nextRunAtMs` without retaining the exemption marker. The merged same-process fixes around https://github.com/openclaw/openclaw/pull/93810 and https://github.com/openclaw/openclaw/pull/94022 are useful context but do not close this cross-restart gap.

## What This Changes

Report that non-agentTurn startup overflow cron catch-up deferrals can be silently lost if the gateway restarts again before the staggered slot fires.

## Best Possible Solution

Persist or durably derive the pending startup catch-up deferral identity in the SQLite-backed cron runtime state, hydrate it before startup maintenance repair, keep stale-future repair enabled for unrelated jobs, and clear the marker when the deferred slot is consumed or invalidated.

## Repair Work Prompt

Fix https://github.com/openclaw/openclaw/issues/102236. Current main protects startup overflow catch-up deferrals with `state.pendingCatchupDeferralJobIds`, but that Set is process-local; if the gateway restarts again before a staggered non-agentTurn cron deferral fires, the fresh process can repair the persisted `nextRunAtMs` to the natural cron slot and silently miss the catch-up. Implement a durable SQLite-backed cron runtime marker or equivalent persisted derivation, hydrate it before startup maintenance recompute, keep ordinary stale-future repair enabled for unrelated jobs, and clear the marker when the deferred slot is reached, the job runs, or the job is disabled/removed. Add a regression that seeds more than `maxMissedJobsPerRestart` non-agentTurn cron jobs, starts once to defer an overflow daily cron slot, constructs a fresh service state against the same store before the staggered slot, and verifies the slot survives and fires. Do not add config/env options, sidecar JSON files, broad fallback readers, or a blanket `repairFutureCronNextRunAtMs: false`; keep release-note context in the PR body rather than editing `CHANGELOG.md`.

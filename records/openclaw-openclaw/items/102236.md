## Label Justifications

- `P2`: The issue describes a bounded cron scheduler bug that can silently miss a deferred startup catch-up run after a second restart.
- `impact:other`: The concrete impact is cron scheduler reliability, which is meaningful but outside the owned message, auth, session, crash, security, and data-loss labels.
- `maturity:stable`: The issue affects gateway-runtime Gateway Lifecycle behavior, which the maturity shortlist reports as M4 Stable.

## Summary

Keep open: current main protects startup overflow catch-up deferrals only with a process-local `pendingCatchupDeferralJobIds` set, while the persisted cron job state can retain the staggered `nextRunAtMs` across restart without retaining the exemption marker. The merged same-process fixes around https://github.com/openclaw/openclaw/pull/93810 and https://github.com/openclaw/openclaw/pull/94022 are useful context, but they do not cover this cross-restart gap.

## What This Changes

Preserve startup overflow cron catch-up deferrals across a second gateway restart before the deferred slot fires.

## Best Possible Solution

Persist or durably derive the pending catch-up deferral identity in the SQLite-backed cron runtime state, hydrate it on startup, keep ordinary stale-future repair enabled for other jobs, and clear the marker when the deferred slot is reached or consumed.

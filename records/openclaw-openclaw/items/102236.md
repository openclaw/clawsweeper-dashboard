## Summary

Keep open: current main still stores the startup catch-up deferral marker only in process-local cron service state, and two open PRs already claim this issue with closing syntax, so the issue should remain open until one reviewed fix lands.

## What This Changes

Fix a cron scheduler bug where overflow startup catch-up deferral markers are process-local, letting a second gateway restart silently advance a deferred catch-up run to its natural schedule.

## Best Possible Solution

Land one focused SQLite-backed cron runtime marker fix that hydrates before startup maintenance, preserves unrelated stale-future repair, and clears the marker when the deferred slot fires or becomes invalid.

Yes. Persisting or durably deriving the marker inside the SQLite-owned cron runtime state is the narrow maintainable fix; disabling repair broadly or adding a sidecar state file is a weaker boundary.

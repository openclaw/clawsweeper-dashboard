## Summary

Keep open: current main still keeps the startup catch-up deferral exemption in a process-local `Set`, so a fresh restart before the deferred slot fires can lose the marker. Two open PRs now claim this issue with closing references, so the issue should stay open until one durable fix lands.

## What This Changes

Reports that startup overflow cron catch-up deferral markers are process-local, allowing a second gateway restart before the staggered slot fires to silently skip the deferred run.

## Best Possible Solution

Land one durable SQLite-backed cron-state fix that persists the catch-up deferral marker with the deferred slot, keeps public cron read views/schema clean, clears the marker after execution or invalidation, and preserves ordinary stale-future repair.

## Reproduction Assessment

Yes. The source path is clear on current main: startup writes the deferred slot plus an in-memory marker, while later maintenance repair depends on that marker; I did not run a live repro in this read-only pass.

## Solution Assessment

Yes. The maintainable fix is to persist the deferral exemption with durable cron state and keep it internal, rather than relying on a process-local marker or adding a second runtime state path.

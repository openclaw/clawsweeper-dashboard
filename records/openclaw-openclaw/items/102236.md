## Summary

Keep open: current main still stores startup catch-up deferral protection in a fresh process-local Set, while two open linked fix candidates, https://github.com/openclaw/openclaw/pull/102292 and https://github.com/openclaw/openclaw/pull/102874, have not merged. This issue should remain the canonical tracker until a durable cron-state fix lands.

## What This Changes

The issue reports that overflow startup catch-up cron deferrals can be lost after a second gateway restart because the persisted staggered slot is protected only by an in-memory marker.

## Best Possible Solution

Land one durable SQLite-owned internal marker or equivalent persisted cron runtime state, hydrate it before startup maintenance, clear it when the deferred slot is consumed or invalidated, then close this issue from the merged fix.

Yes, at source level: seed more than the missed-job budget, let startup persist a staggered non-agentTurn cron nextRunAtMs, then construct a fresh service state before that slot and run startup maintenance. ## Solution Assessment

Yes for the issue direction: the narrow fix is to persist or durably derive the pending startup catch-up deferral identity with the cron runtime state. A broad repair disablement, config knob, or non-transactional sidecar would be a weaker boundary.

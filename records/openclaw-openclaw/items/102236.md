## Summary

Keep open: current main still keeps the startup catch-up deferral marker only in process-local cron service state, so a fresh gateway process can load the persisted staggered `nextRunAtMs` without the marker that prevents startup maintenance from advancing it. The linked open PRs are candidate fixes, but this issue should remain canonical until one lands cleanly.

## What This Changes

The issue requests that overflow cron startup catch-up deferrals survive a second gateway restart before the deferred slot fires.

## Best Possible Solution

Persist the pending startup catch-up deferral identity in the SQLite-owned cron runtime state or an equivalent durable internal row-level shape, hydrate it before startup maintenance repair, keep unrelated stale-future repair enabled, and clear the marker when consumed or invalidated.

## Reproduction Assessment

Yes, at source level. Seed more than the missed-job budget, let startup persist a staggered non-agentTurn cron `nextRunAtMs`, then construct a fresh `CronServiceState` before that slot and run startup maintenance with an empty deferral set.

## Solution Assessment

Yes for the issue direction: the narrow fix is durable internal marker persistence plus hydration before maintenance repair. The best landing shape should keep that marker internal to cron runtime storage and avoid a separate sidecar or public protocol field unless maintainers explicitly choose that contract.

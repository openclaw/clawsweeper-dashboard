## Label Justifications

- `P2`: The issue is a bounded cron scheduler missed-run bug affecting overflow startup catch-up after a rapid second restart.
- `impact:other`: The issue can silently miss an intended cron catch-up run, which is concrete scheduler impact outside the more specific owned labels.

## Summary

Keep open: current main still loses the startup catch-up deferral marker across a fresh process, and two open linked PRs now own candidate fixes but have unresolved review blockers.

## What This Changes

The issue reports that startup overflow cron catch-up deferral markers are process-local, so a second restart before the deferred slot fires can silently advance the job to its natural next cron slot.

## Best Possible Solution

Land one durable SQLite-owned cron marker fix that hydrates before startup maintenance, preserves public cron protocol compatibility, keeps ordinary stale-future repair for unrelated jobs, and clears stale markers correctly.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes. Current-main source shows the deferred `nextRunAtMs` is persisted while its repair exemption marker remains process-local; a fresh state on restart loses that exemption before startup maintenance runs.

## Solution Assessment

Yes in direction, but not yet landed. A durable cron runtime marker is the narrow fix; the open PR candidates still need PR-side resolution for protocol compatibility or SQLite storage ownership.

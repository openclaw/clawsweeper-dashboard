- `impact:other`: The issue concerns duplicated background work and retained timers, watchers, sockets, or clients, which is meaningful operational impact outside the more specific impact taxonomy.

## Summary

Current main replaces internal-hook registrations without owning module-created resources, so the reported lifecycle gap remains. The issue should stay open for an explicit decision on whether internal hooks gain a disposal contract or resource-owning integrations must use plugin lifecycle services.

## What This Changes

Define cleanup behavior for process-level resources created by managed or workspace hook modules when handlers are reloaded or disabled.

## Best Possible Solution

Keep one documented resource-ownership model: prefer plugin `gateway_start` and `gateway_stop` lifecycle for long-running resources, or—if maintainers intentionally support such resources in internal hooks—add a single async `dispose` contract invoked once per imported module in reverse load order before replacement or disable, with isolated failures and focused reload tests.

## Risks / Open Questions

- Adding `dispose` would create a new hook-module contract whose async semantics, ordering, deduplication, error handling, and compatibility expectations need explicit ownership.
- Leaving the contract undefined allows trusted hook modules with background resources to duplicate work or retain handles after in-process reloads.
- A second lifecycle system for internal hooks could drift from the existing plugin gateway lifecycle and encourage service-style behavior in a lightweight hook surface.

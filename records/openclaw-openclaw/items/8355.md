## Summary

Keep open. Current main and the latest release still batch the classic Voice Call STT to embedded-agent to telephony TTS path, while realtime voice and the open compaction-wait PR address adjacent paths rather than the requested provider-generic sentence-level telephony streaming pipeline.

## What This Changes

The issue requests a provider-generic streaming TTS pipeline for classic voice calls so LLM output can be split at sentence level, synthesized incrementally, and sent to Twilio/Telnyx audio streams before the full response is complete.

## Best Possible Solution

Keep this as the canonical provider-generic classic Voice Call latency feature and design an additive telephony streaming speech contract plus Twilio/Telnyx playback semantics before implementation.

## Reproduction Assessment

Yes, at source level: current main awaits a completed embedded-agent result and completed telephony audio Buffer before Twilio sends chunks. I did not run a live Twilio/Telnyx call to measure the reported latency numbers.

## Solution Assessment

Yes for triage: keeping this open is the best outcome because realtime voice is a separate bypass, the open compaction-wait PR is narrower, and prior sentence-level streaming PRs are closed unmerged. The maintainable fix needs a maintainer-approved provider-generic telephony streaming API and playback/fallback shape.

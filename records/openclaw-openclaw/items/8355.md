## Summary

Keep open. Current main and the latest release still batch the classic voice-call STT to embedded-agent to telephony-TTS path; realtime voice and general ElevenLabs streaming support are adjacent capabilities, not the requested provider-generic sentence-level telephony pipeline.

## What This Changes

Request streaming voice-call LLM output through sentence-level TTS and audio playback so callers hear first audio sooner in the classic STT-to-LLM-to-TTS path.

## Best Possible Solution

Implement an additive provider-generic telephony streaming contract plus voice-call sentence pipeline that preserves buffered fallback, barge-in cancellation, playback ordering, and realtime voice as a separate bypass mode.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a provider-generic telephony streaming contract for the classic voice-call STT-to-LLM-to-TTS path, and what fallback/provider semantics should it require?

Rationale: The missing capability is clear, but the permanent API shape affects bundled and external speech providers, Twilio/Telnyx playback adapters, fallback behavior, and user-visible latency expectations.

Likely owner: steipete

Owner reason: The decision spans voice-call product behavior and plugin SDK surface, and the strongest cross-boundary history signal is steipete.

Owner confidence: high

Options:

- **Design additive provider-generic streaming (recommended):** Add a telephony audio stream capability to the speech/plugin SDK, wire sentence-level text delivery through voice-call, and keep buffered synthesis as fallback for unsupported providers.
- **Use realtime voice as the low-latency path:** Document realtime voice as the supported low-latency solution and leave the classic STT-to-LLM-to-TTS path buffered.
- **Approve a narrower provider experiment:** Allow a Twilio/OpenAI or ElevenLabs-first implementation, with follow-up API work required before Telnyx and other providers can share it.

## Reproduction Assessment

Yes, at source level. Current main still awaits a complete embedded-agent response and complete telephony TTS buffer before Twilio chunking begins; this read-only review did not run a live call.

## Solution Assessment

Unclear as an implementation, but the requested direction addresses the right remaining gap. Maintainers still need to choose the provider-generic telephony streaming API and fallback semantics before this is safe to implement.

## Summary

Keep open. Current main and the latest release still batch the classic voice-call STT to embedded-agent to telephony-TTS path; newer generic TTS streaming, realtime voice, and the open compaction-wait PR are adjacent work rather than the requested provider-generic sentence-level telephony streaming pipeline.

## What This Changes

The issue requests a streaming TTS pipeline for classic voice calls so sentence-level LLM output can feed TTS and audio playback before the full response and full audio buffer are complete.

## Best Possible Solution

Keep this as the canonical provider-generic classic voice-call latency feature: add an explicit streaming telephony speech contract, wire embedded-agent partial spoken text through a sentence splitter, stream provider audio chunks into Twilio/Telnyx playback with barge-in and ordering tests, and keep realtime voice documented as a separate bypass mode.

## Reproduction Assessment

Yes, at source level: current main still awaits a complete embedded-agent result and a complete telephony audio buffer before playback chunks are sent. I did not run a live Twilio or Telnyx call in this read-only review.

## Solution Assessment

Unclear for implementation shape, but keeping this issue open is the right triage result. The proposed sentence-level pipeline is directionally appropriate, yet the maintainable solution needs a deliberate streaming telephony contract and provider fallback semantics rather than reusing the ordinary speech stream path accidentally.

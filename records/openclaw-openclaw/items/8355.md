## Label Justifications

- `P2`: Classic voice calls remain functional, but multi-second first-audio latency is a meaningful, limited-blast-radius conversational quality improvement rather than an outage.
- `impact:ux-friction`: Users can complete voice calls, but the fully batched response and synthesis path creates avoidable dead air that makes conversation feel stalled.

## Summary

Current main reduces one adjacent post-turn compaction delay, but the classic voice-call path still waits for completed response text and a complete telephony audio buffer before carrier playback; realtime voice is a separate bypass architecture, and all direct sentence-streaming implementation PRs closed unmerged. Keep this canonical feature open for a maintainer product decision. Likely related people: steipete and xialonglee (high confidence), joshavant and dguido (medium confidence).

## What This Changes

Add a provider-generic sentence-level pipeline that streams incremental LLM output through telephony TTS into ordered carrier audio playback.

## Best Possible Solution

Define an additive provider-generic streaming speech contract, implement one end-to-end classic path with sentence boundaries and incremental audio chunks, preserve buffered fallback before first audio only, and prove ordered playback, barge-in, cancellation, and partial-failure behavior on both fresh and existing Voice Call setups.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should classic Voice Call gain a supported provider-generic sentence/audio streaming contract, and which initial TTS-provider plus carrier combination should define that contract?

Rationale: The implementation changes shared speech and embedded-agent boundaries plus user-visible partial-playback recovery semantics; code inspection cannot safely choose that permanent API and rollout policy without maintainer intent.

Likely owner: steipete

Owner reason: The history shows the broadest ownership across Voice Call response generation, telephony playback, realtime architecture, and the recent early-delivery merge boundary.

Owner confidence: high

Options:

- **Sponsor additive streaming contract (recommended):** Add optional incremental text and telephony-audio APIs, start with one proven provider/carrier combination, and retain the existing buffered path for unsupported providers and pre-audio failures.
- **Use realtime voice only:** Keep classic STT-to-agent-to-TTS deliberately buffered and direct low-latency users to the separate OpenAI or Gemini full-duplex realtime architecture.
- **Defer pending narrower design:** Keep the issue canonical but require a smaller API proposal and live carrier benchmark before accepting implementation work.

## Reproduction Assessment

Yes at source level: configure the classic Twilio media-stream path, trigger a multi-sentence agent response, and observe that response generation and telephony synthesis each complete before audio chunks are sent. A fresh live carrier timing run was not performed in this read-only review.

## Solution Assessment

Yes in direction, but not yet in contract detail: an additive provider-generic streaming seam with ordered, abortable playback and a bounded buffered fallback is preferable to replacing the classic path or treating full-duplex realtime voice as equivalent.

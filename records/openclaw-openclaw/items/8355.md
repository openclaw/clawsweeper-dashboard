## Summary

Keep this open. Current main has reduced part of the wait by handing the first completed block to TTS before post-turn compaction, and the voice-call docs describe streaming telephony speech, but neither the merged work nor the documented contract establishes the requested provider-generic sentence-level LLM-to-TTS pipeline. This remains a real product/API design decision rather than a safe autonomous fix.

## What This Changes

The issue requests a provider-generic classic voice-call pipeline that streams LLM output sentence-by-sentence through TTS and carrier playback.

## Best Possible Solution

Approve a bounded, additive streaming speech contract owned by the voice-call and speech-provider seams, then implement it first for one carrier/provider pair with ordered sentence delivery, cancellation, barge-in, buffered fallback, and live latency proof before extending it to Telnyx or other providers.

Options:

- **Sponsor a bounded streaming contract (recommended):** Define an additive async telephony-audio capability, implement and prove it first for Twilio plus one provider, then expand only after the queue and abort semantics are stable.
- **Keep early-block delivery as the supported latency path:** Retain the current onBlockReply-to-TTS improvement and defer sentence-level streaming until a carrier-neutral contract has an owner and acceptance criteria.
- **Prefer realtime voice for new low-latency calls:** Document realtime mode as the supported low-latency option while leaving the classic pipeline buffered apart from its existing early-block optimization.

## Solution Assessment

Yes, keeping this open for a bounded shared-contract decision is the best path. Realtime voice and early-block delivery address related latency sources but do not supply the requested provider-generic classic streaming pipeline.

## Summary

Keep this issue open. Current main has reduced one latency source by delivering an early completed reply block before post-turn compaction, but the classic voice-call path still lacks the requested provider-generic sentence-level text-to-TTS-to-carrier streaming contract; realtime voice remains a separate full-duplex architecture, and the direct implementation PRs closed unmerged. Likely related people are steipete (high confidence), joshavant (medium confidence), and dguido (medium confidence), based on merged voice-call, TTS, and playback-queue history.

## What This Changes

Add provider-generic sentence-level LLM-to-TTS-to-audio streaming for classic voice calls while preserving ordered playback, fallback, abort, and barge-in behavior.

## Best Possible Solution

Define an additive provider-owned streaming speech contract that accepts complete spoken segments and yields audio chunks, prove it first through one provider/carrier pair, retain buffered synthesis before playback begins as the compatibility fallback, and integrate ordering, abort, partial-failure, and barge-in semantics without conflating the feature with realtime voice.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should classic Voice Call adopt a provider-generic streaming speech contract now, and which provider/carrier pair plus fallback semantics should define the first supported implementation?

Rationale: The request crosses the plugin speech API, embedded-agent spoken-output boundary, carrier playback lifecycle, provider economics, and recovery behavior; those permanent contracts cannot be selected safely as a mechanical repair.

Likely owner: steipete

Owner reason: This person has the strongest history across the voice-call plugin, carrier adapters, telephony TTS, and the separate realtime architecture.

Owner confidence: high

Options:

- **Approve phased generic contract (recommended):** Add an additive provider-generic stream contract, prove it first with Twilio and ElevenLabs, preserve buffered fallback before any audio is emitted, and add Telnyx through the same contract afterward.
- **Use realtime voice only:** Make OpenAI and Gemini full-duplex realtime mode the supported low-latency path and decline a new classic-pipeline streaming API.
- **Require plugin-local prototype:** Keep the shared API unchanged until an external voice-call prototype demonstrates latency, interruption, ordering, and failure behavior on a real carrier.

## Reproduction Assessment

Yes at source level: the classic path still passes completed spoken text into a complete-result telephony synthesis contract before carrier playback. No fresh live carrier latency run was performed during this read-only review.

## Solution Assessment

No, not exactly as proposed: exposing raw LLM tokens directly to TTS would conflict with the spoken-output boundary and leave provider ownership, ordering, fallback, and interruption semantics underspecified. An additive stream of validated spoken segments plus provider audio chunks is the narrower maintainable design.

## Summary

Keep open. Current main and v2026.6.11 still batch the classic Voice Call STT-to-agent-to-telephony-TTS path, while realtime voice and the open compaction-wait PR address adjacent latency paths rather than the requested provider-generic sentence-level TTS pipeline.

## What This Changes

Request to add a provider-generic sentence-level streaming TTS pipeline for classic Voice Call responses so LLM text, telephony TTS, and Twilio/Telnyx playback can overlap.

## Best Possible Solution

Keep this as the canonical provider-generic classic Voice Call latency feature, then design an additive telephony streaming speech contract and Twilio/Telnyx playback path with fallback, ordering, barge-in, provider-contract tests, and redacted live call proof.

## Reproduction Assessment

Yes, at source level: current main awaits a completed embedded-agent result and completed telephony audio Buffer before Twilio sends chunks. I did not run a live Twilio, Telnyx, or ElevenLabs latency measurement.

## Solution Assessment

Yes for triage: keeping this open is the best outcome because realtime voice and the open compaction-wait PR solve adjacent paths, not this provider-generic sentence-level TTS pipeline. The implementation itself needs maintainer-approved API and playback semantics before it is safe to automate.

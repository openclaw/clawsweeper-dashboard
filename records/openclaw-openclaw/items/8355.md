## Summary

Keep open. Current main and v2026.6.11 still batch the classic Voice Call STT to embedded-agent to telephony TTS path, and the realtime voice path plus the open compaction-wait PR address adjacent latency paths rather than this provider-generic sentence-level telephony streaming pipeline.

## What This Changes

The issue requests a provider-generic sentence-level LLM-to-TTS audio streaming pipeline for classic voice-call flows.

## Best Possible Solution

Keep this as the canonical provider-generic classic Voice Call latency feature and design an additive telephony streaming speech contract plus Twilio/Telnyx playback semantics before implementation.

## Reproduction Assessment

Yes, at source level: current main awaits a completed embedded-agent response and a completed telephony audio Buffer before Twilio sends the non-keepalive audio chunks. I did not run a live Twilio/Telnyx call to measure the reported latency numbers.

## Solution Assessment

Yes for triage: keeping this open is the best outcome because realtime voice is a separate bypass, the open compaction-wait PR is narrower, and prior sentence-level streaming PRs are closed unmerged. The maintainable fix needs a maintainer-approved provider-generic telephony streaming API and playback/fallback shape.

## Summary

Current main reduces one adjacent delay by delivering a completed reply block before compaction and already supports generic provider audio streams, but the classic voice-call path still does not pipeline incremental LLM text through streaming telephony synthesis and ordered transport playback. The prior implementation attempts are closed unmerged, realtime voice is a separate bypass architecture, and no open replacement owns the remaining provider-generic work.

Likely related people:
- steipete — strongest current history signal across voice response, TTS, and transport boundaries (high confidence).
- xialonglee — authored the adjacent early-delivery behavior now used before compaction (high confidence).
- joshavant — authored adjacent Twilio playback and stream-reliability work the feature must preserve (medium confidence).

## What This Changes

Add provider-generic sentence-level LLM-to-TTS streaming to the classic voice-call pipeline so audio playback can begin before the complete response and audio buffer are ready.

## Best Possible Solution

Add an optional provider-generic streaming telephony synthesis contract alongside the existing buffered hook, feed it accepted incremental spoken-text units, and preserve one ordered per-call queue with abort, cleanup, zero-audio fallback, and no full-response replay after partial delivery; prove the initial supported provider/transport combinations with live call latency and barge-in evidence.

## Reproduction Assessment

Yes, at source level. Current main has a deterministic path from a completed accepted text block through Promise<Buffer> telephony synthesis to post-buffer Twilio framing, although this read-only review did not run a live call to confirm the reported 5–8 second measurement.

## Solution Assessment

The provider-generic objective is the best direction, but replacing the existing return types with iterators would be unnecessarily breaking. An additive streaming telephony contract with explicit buffered fallback, cancellation, ordering, and partial-playback semantics is the narrower maintainable solution.

## Risks / Open Questions

- A new streaming telephony hook would be public plugin API surface, so its result shape, resource cleanup, cancellation, and buffered compatibility contract need explicit ownership.
- Fallback after partial audio playback is unresolved: replaying the full buffered response can duplicate speech, while failing closed can leave callers with a truncated answer.
- The first supported matrix is a product choice because Twilio can accept bidirectional media frames, Telnyx currently uses its carrier speak action, and providers expose different streamed audio formats and sample rates.

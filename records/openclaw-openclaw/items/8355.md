## Label Justifications

- `P2`: The missing pipeline causes meaningful conversational latency but does not make the voice-call runtime unusable.
- `impact:ux-friction`: Classic voice callers can experience several seconds of silence before hearing an agent response, making conversations feel slow and unnatural.

## Summary

Current main has narrower early-response and provider-streaming pieces, but the classic voice path still lacks the requested provider-generic sentence-level LLM-to-TTS pipeline. Realtime voice remains a separate full-duplex architecture, and the direct implementation PRs closed unmerged, so this issue remains necessary as the canonical product-design item.

## What This Changes

Requests provider-generic sentence-level streaming from LLM output through telephony TTS and carrier audio playback to reduce first-audio latency in classic voice calls.

## Best Possible Solution

Define additive plugin capabilities for validated partial spoken text and streaming telephony audio, then implement one provider/carrier pair while preserving buffered fallback, deterministic ordering, barge-in cancellation, and protection against duplicate or partial replay.

- **Run a narrow experiment:** Keep the new path private to the voice-call plugin and initially support only ElevenLabs with Twilio before deciding whether to publish a general API.
- **Prefer realtime providers:** Leave the classic pipeline buffered and direct latency-sensitive deployments to the existing full-duplex realtime architecture.

## Reproduction Assessment

No live latency reproduction was run, but the bottleneck is source-reproducible with high confidence: completed agent text feeds a complete telephony Buffer that Twilio only frames after synthesis finishes.

## Solution Assessment

The pipeline direction is appropriate, but replacing existing return types is not the best compatibility shape; additive streaming capabilities with the buffered path retained as fallback are safer and more maintainable.

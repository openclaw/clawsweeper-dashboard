## Summary

Keep open. Current main and the latest release still batch the classic voice-call STT to embedded-agent to telephony-TTS path; realtime voice and the open compaction-wait PR are adjacent latency work, not the requested provider-generic sentence-level telephony streaming pipeline.

## What This Changes

The issue requests a provider-generic streaming voice-call pipeline that feeds sentence-level LLM output into streaming TTS audio playback instead of waiting for full text and full audio buffers.

## Best Possible Solution

Implement an additive provider-generic telephony streaming contract plus voice-call sentence pipeline that preserves buffered fallback, barge-in cancellation, ordering, and realtime voice as a separate bypass mode.

Options:

- **Design additive provider-generic streaming (recommended):** Add a telephony audio stream capability to the speech/plugin SDK, wire sentence-level text delivery through voice-call, and keep buffered synthesis as fallback for unsupported providers.
- **Use realtime voice as the low-latency path:** Document realtime voice as the supported low-latency solution and leave the classic STT to LLM to TTS path buffered.
- **Accept a provider-specific experiment:** Allow a narrower Twilio/OpenAI or ElevenLabs-first implementation, with follow-up API work needed before Telnyx and other providers can share it.

## Reproduction Assessment

Yes, at source level. Current main still awaits a complete embedded-agent response and complete telephony TTS buffer before Twilio chunking begins; this read-only review did not run a live call.

## Solution Assessment

Unclear as an implementation, but the requested direction addresses the right remaining gap. Maintainers still need to choose the provider-generic telephony streaming API and fallback semantics before this is safe to implement.

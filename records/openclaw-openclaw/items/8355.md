## Summary

Current main addresses an adjacent delay and provides generic provider audio streams, but it still does not pipeline incremental LLM text through telephony synthesis and transport playback. The closed implementation attempts are not viable replacements, so this remains the canonical provider-generic architecture request.

## What This Changes

Add provider-generic incremental LLM-to-TTS-to-call-audio playback for classic voice calls, including cancellation-safe barge-in behavior.

## Best Possible Solution

Reuse the existing generic speech audio stream, add the smallest format/sample-rate-aware telephony adaptation, and feed accepted incremental spoken units through the existing ordered abortable queue with fallback allowed only before any audio is delivered.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should streaming telephony become a narrow public speech runtime contract now, or remain private to the voice-call plugin until Twilio and a second transport prove the cancellation and partial-failure semantics?

Rationale: Current main supplies the provider audio-stream primitive but has no permanent telephony stream result or agreed recovery policy after partial playback; automation cannot safely choose that public API boundary.

Likely owner: steipete

Owner reason: The strongest history signal spans both the voice-call implementation and the public plugin/runtime boundary needed for this decision.

Owner confidence: high

Options:

- **Public telephony stream (recommended):** Add a narrow format/sample-rate-aware streaming contract and prove it end to end with one speech provider and Twilio before adding other transports.
- **Private adapter first:** Consume generic speech streams inside voice-call and defer SDK expansion until a second transport implementation validates the abstraction.
- **Realtime-only latency path:** Keep classic calls buffered and treat full-duplex realtime providers as the supported low-latency architecture.

## Reproduction Assessment

Yes, from current-main source: the classic path hands off a completed spoken block, telephony synthesis returns a complete Buffer, and Twilio waits for that Buffer before sending frames. This read-only review did not run a live call latency benchmark.

## Solution Assessment

No, the original proposal should not add another independent provider streaming API now that generic speech streaming exists. The better solution is a narrow telephony adaptation of the existing stream contract plus incremental classic-call orchestration and explicit partial-playback semantics.

## Label Justifications

- `P2`: Several queued messages can consume most of a mobile viewport, but users can still proceed by scrolling or managing individual items.
- `impact:ux-friction`: The current full queue rows crowd the conversation and composer on mobile without completely blocking the workflow.

## Summary

Keep open: current main still renders every queued message as a full action row, the reported mobile density problem remains, and neither related issue owns the same behavior.

## What This Changes

Add a compact, collapsible queued-message section to mobile WebChat while preserving access to per-message controls.

## Best Possible Solution

Use a phone-width compact queue summary with an explicit accessible toggle, preserve all existing actions in the expanded view, keep manual expansion stable while items remain, and collapse again when the queue empties rather than using a timer.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should queued messages default to collapsed only on phone-width layouts, and should manual expansion remain until the queue empties?

Rationale: The space problem is clear, but viewport scope and automatic disclosure-state changes are user-experience policy rather than correctness questions.

Likely owner: cy123

Owner reason: Historical WebChat interaction ownership provides the strongest available routing signal for this product choice.

Owner confidence: medium

Options:

- **Phone-only collapse (recommended):** Default to a compact count on narrow viewports, retain desktop behavior, and reset the disclosure state when the queue empties.
- **Collapse on all layouts:** Use the compact default everywhere for consistency, accepting reduced immediate queue visibility on desktop.
- **Compact rows without collapse:** Keep all items visible as single-line previews, reducing height without adding disclosure state.

## Reproduction Assessment

Yes, from source: use a phone-width WebChat viewport, keep an agent run active, and enqueue several messages; the composer renders each as a separate action row. A live iOS Safari run was not included, so this is source-reproducible rather than directly reproduced.

## Solution Assessment

Yes, with a narrower default than the original proposal: phone-only collapsing fixes the constrained viewport while avoiding an unnecessary desktop behavior change, and queue-empty reset is more predictable than a timeout.

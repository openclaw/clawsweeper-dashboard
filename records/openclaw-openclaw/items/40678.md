## Label Justifications

- `P2`: This is a normal-priority power-user TUI/channel visibility feature with workarounds and bounded blast radius, but it needs maintainer policy before implementation.
- `impact:session-state`: The request is about seeing activity across sessions and channels without collapsing the isolated TUI session state.
- `impact:message-loss`: The reported user impact is that channel messages and agent responses are not visible in the active TUI unless the user switches to raw logs or reloads a specific session.
- `impact:security`: Any cross-channel observer can expose transcripts across channel, identity, and session boundaries if the authorization policy is wrong.

## Summary

Keep open: current main and v2026.6.11 still lack an opt-in TUI observe/mirror mode, and the open related PR only addresses the narrower selected-session live update gap. The remaining request needs maintainer product and security policy because it would expose transcript activity across channel and session boundaries.

## What This Changes

Add an opt-in TUI mode or config/flag that mirrors or observes iMessage, Telegram, and other channel activity for the same agent without undoing isolated TUI sessions.

## Best Possible Solution

Define a read-only-first, explicitly opt-in TUI observer policy with agent, identity, channel, and session visibility bounds, then build it on the existing Gateway session event/history surfaces without changing default session isolation.

- **Interactive bidirectional mirror:** Allow the TUI to both observe and send across mirrored channels, accepting a larger delivery, message-loss, and privacy-policy surface before implementation.
- **Keep logs as the workaround:** Reject core observer/mirror mode for now and leave `openclaw logs --follow` plus explicit session selection as the supported monitoring path.

## Reproduction Assessment

Yes at source level for the missing capability: current main has no TUI observe/mirror CLI or config surface and filters live TUI events to the selected session. I did not run a fresh live iMessage/Telegram/TUI observer scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the security boundary: the best likely shape is a read-only, opt-in observer scoped by existing session visibility before any interactive bidirectional mirroring. The open selected-session live-update PR is a good narrow fix but not the full solution for this issue.

## Summary

This issue remains necessary. Current Telegram ingress is routed through the shared channel-ingress monitor, but the reviewed path still converts delivery exceptions into retryable outcomes while queue mutation failures are state-store-dependent; the report identifies a credible corruption case where the configured cap cannot be durably enforced. The correct repair boundary is likely the shared ingress/state-store failure policy, not a Telegram-only retry counter. Likely related people: OpenClaw Telegram ingress history is unresolved from the accessible provenance trail (low confidence).

## What This Changes

Prevent Telegram’s durable ingress spool from releasing and retrying an update beyond its configured limit when the shared SQLite state database is corrupt and cannot persist the terminal result.

## System Context

Telegram polling and webhook transport append incoming updates to a durable channel ingress queue. A shared monitor claims queued updates, dispatches them to the agent runtime, then completes, releases, or marks the claim failed in the same state store.

## Architecture Diagram

flowchart LR
  A[Telegram update] --> B[Durable ingress queue]
  B --> C[Shared ingress monitor]
  C --> D[Telegram dispatch]
  D --> E{Dispatch outcome}
  E -->|success| F[Complete queue record]
  E -->|retryable failure| G[Release or fail queue claim]
  G --> H[SQLite state store]
  H -->|corrupt| I[Operator recovery needed]

## Best Possible Solution

Add a shared corruption-aware ingress circuit breaker that stops claims/releases for the affected state store, emits bounded diagnostics, and resumes only after an explicit verified recovery path; cover both fresh corruption and recovery after restart with regression tests.

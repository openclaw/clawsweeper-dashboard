## Summary

## What This Changes

Manual advanced setup validates gateway port input with loose `Number(...)` but persists it with `Number.parseInt(..., 10)`, allowing non-decimal numeric-looking values to save as a different port.

## Best Possible Solution

Reuse the existing strict TCP port parser for both validation and persisted setup settings, then cover loose numeric strings in the focused setup gateway config test.

## Reproduction Assessment

Yes for source-level reproduction: current main validates with `Number(...)` but persists with `Number.parseInt(..., 10)`, and a Node probe shows `1e3` validates as `1000` while persisting as `1`. I did not run the interactive wizard in this read-only review.

## Solution Assessment

Yes. The narrow maintainable fix is to reuse the existing strict TCP port parser for both validation and storage in the manual setup helper, rather than adding a new config option or another one-off parser.

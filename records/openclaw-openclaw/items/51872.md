## Label Justifications

- `P2`: This is a meaningful authenticated-proxy gap for mobile Gateway deployments, but it is a feature request rather than a current core outage.
- `impact:security`: The requested behavior would make mobile clients store and send proxy credentials before the normal Gateway auth boundary.
- `impact:auth-provider`: The issue is about authentication material needed on the HTTP/WebSocket transport before the Gateway receives the connection.
- `maturity:stable`: The affected Gateway runtime, Android app, and iOS app surfaces are scored M4 Stable in qa/maturity-scores.yaml and docs/maturity/scorecard.md.

## Summary

Keep open: current main still lacks a shared mobile transport-auth/header contract, Android and iOS cannot attach pre-upgrade proxy credentials, the open iOS PR is only a conflicting Basic-auth subset, and the closed Android PR did not land.

## What This Changes

Request mobile setup and connection flows to support transport-level reverse-proxy authentication such as bearer, Basic, fixed headers, cookies, and possibly OIDC before the Gateway WebSocket upgrade.

## Best Possible Solution

Define a maintainer-approved shared mobile proxy-auth contract, likely splitting static Basic/bearer/header support from OIDC, then land proof-backed Android/iOS slices with explicit credential lifecycle and security rules.

## Reproduction Assessment

Yes for the source-level gap: current mobile connection paths do not carry proxy Authorization/custom headers before the WebSocket upgrade. I did not run a live mobile client through Caddy or nginx in this read-only review.

## Solution Assessment

No as one broad implementation; static Basic/bearer headers are a plausible first slice, but arbitrary headers/cookies/OIDC and cross-platform credential lifecycle need maintainer product and security decisions before a best fix can be chosen.

## Summary

Keep open: current main and v2026.6.11 still lack mobile transport-auth metadata and WebSocket upgrade-header support for authenticated reverse proxies; the closed Android PR did not land, and the open iOS PR covers only a narrower Basic-auth slice with unresolved blockers.

## What This Changes

Request to add Android/iOS setup-code and manual-connection support for reverse-proxy transport authentication before the Gateway WebSocket upgrade.

## Best Possible Solution

Define a shared mobile transport-auth contract for setup-code and manual Gateway connections, split static-header support from OIDC if needed, and require secure storage, clearing, redaction, TLS behavior, and real proxy proof for each platform slice.

Rationale: This crosses the authentication boundary before Gateway pairing, introduces mobile credential storage/replay, and may involve OIDC browser/app-link token handling, so code alone cannot choose the acceptable product and security contract.

Likely owner: steipete

Owner reason: The history ties steipete to setup-code bootstrap, Gateway auth/protocol, and security-facing contract work that this decision extends.

Owner confidence: medium

Options:

- **Approve static-header slice first (recommended):** Support Basic/Bearer/fixed-header credentials in setup/manual mobile config with secure storage, TLS-only sending, reset/redaction rules, Android/iOS parity, and leave OIDC for a separate design.
- **Design OIDC-first contract:** Pause static header work until maintainers approve a browser-return flow, token ownership model, and platform credential lifecycle for identity-aware proxies.
- **Keep proxy auth outside mobile setup:** Document VPN/tunnel/Tailscale Serve or direct Gateway auth as the supported mobile path and close proxy-credential injection work as out of scope.

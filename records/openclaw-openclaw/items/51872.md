## Label Justifications

- `P2`: The issue blocks authenticated-proxy native mobile deployments but is a bounded feature gap, not a general OpenClaw runtime outage.
- `impact:security`: The requested behavior would store and replay proxy credentials before OpenClaw's normal Gateway authentication boundary.
- `impact:auth-provider`: The failure is an authentication-layer mismatch where reverse-proxy credentials must be supplied on the HTTP/WebSocket upgrade before Gateway auth can run.
- `maturity:stable`: The affected Gateway runtime, Android app, and iOS app surfaces are scored M4 Stable in qa/maturity-scores.yaml.

## Summary

Keep open: current main and v2026.6.11 still lack a shared native transport-auth contract for authenticated reverse proxies, and the related Android/iOS work is either closed unmerged or only covers a narrower iOS Basic-auth slice.

## What This Changes

Requested support for passing reverse-proxy authentication details such as bearer, Basic, fixed headers, cookies, and OIDC from setup/manual mobile flows into Android and iOS gateway connection requests.

## Best Possible Solution

Define a shared mobile transport-auth contract for setup-code and manual Gateway connections, stage static header support separately from OIDC, and require secure storage, clearing, redaction, TLS, endpoint-change handling, and real proxy proof before landing platform slices.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which native mobile reverse-proxy transport-auth contract should OpenClaw support before implementation: static bearer/Basic/header fields only, OIDC browser handoff too, or no native proxy credentials for now?

Rationale: The source gap is clear, but the durable boundary controls pre-Gateway credentials, mobile storage, setup-code metadata, and OIDC redirect handling, so automation should not choose it alone.

Likely owner: steipete

Owner reason: steipete has the strongest current setup-code and Gateway auth contract history, and this decision is primarily about the security boundary before platform implementation.

Owner confidence: high

Options:

- **Approve staged static proxy auth (recommended):** Define bearer, Basic, and fixed-header fields first with strict credential lifecycle, TLS, redaction, setup-code, Android, and iOS requirements, leaving OIDC for a later design.
- **Design the full proxy-auth suite:** Cover static headers, cookies, and OIDC together before implementation, accepting a broader design and validation cycle.
- **Decline native proxy credentials:** Document authenticated reverse proxies as unsupported for native mobile clients and recommend VPN, tunnel, WebChat, or proxy configuration alternatives.

## Reproduction Assessment

Yes. Source inspection shows setup-code payloads, Android connection config, Android WebSocket construction, and iOS shared WebSocket/config paths have no proxy-auth or upgrade-header fields; I did not run a live authenticated-proxy mobile scenario.

## Solution Assessment

Unclear. Static bearer/Basic headers are a plausible first slice, but the full request needs maintainer-approved credential lifecycle, Android/iOS parity, setup-code metadata, and OIDC browser-return boundaries.

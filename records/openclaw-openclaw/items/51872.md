## Summary

Keep open: current main and v2026.6.11 still lack a shared Android/iOS transport-auth contract for authenticated reverse proxies, and the related Android and iOS PRs do not land the broad requested behavior.

## What This Changes

Requests shared mobile transport-auth support so QR/manual Android and iOS gateway connections can include proxy Basic, bearer, fixed-header, cookie, or OIDC credentials before the WebSocket upgrade.

## Best Possible Solution

Define a shared mobile transport-auth contract for setup-code and manual Gateway connections, stage static header support separately from OIDC, and require secure storage, clearing, redaction, TLS, endpoint-change, and real proxy proof before landing platform slices.

## Maintainer Decision

Kind: product_direction

Question: Which mobile reverse-proxy transport-auth contract should OpenClaw support before implementation: static bearer/Basic/header fields first, OIDC browser handoff too, or no native proxy credentials for now?

Rationale: The source gap is clear, but the durable product boundary controls pre-Gateway credentials, mobile storage, setup-code metadata, TLS requirements, and OIDC redirect handling, so automation should not choose it alone.

Likely owner: steipete

Owner reason: steipete has recent setup-code and Gateway auth contract history, and this decision is primarily about the security boundary before platform implementation.

Owner confidence: high

Options:

- **Approve staged static proxy auth (recommended):** Define bearer, Basic, and fixed-header support first with strict credential lifecycle, TLS, redaction, setup-code, Android, and iOS requirements, leaving OIDC for a later design.
- **Design the full proxy-auth suite:** Cover static headers, cookies, and OIDC together before implementation, accepting a broader design and validation cycle.
- **Decline native proxy credentials:** Document authenticated reverse proxies as unsupported for native mobile clients and recommend VPN, tunnel, WebChat, or proxy configuration alternatives.

## Reproduction Assessment

Yes. Source inspection shows setup-code payloads, Android connection config, Android WebSocket construction, and iOS shared WebSocket/config/settings paths have no proxy-auth/header fields before the upgrade.

## Solution Assessment

Unclear as a complete implementation. Static bearer/Basic headers are a plausible first slice, but the full request needs maintainer-approved credential lifecycle, Android/iOS parity, setup-code metadata, TLS behavior, and OIDC browser-return boundaries.

## Summary

Keep open: current main has useful shared-session safeguards, but the central initializer still has a terminal `reply session initialization conflicted` throw and WebChat/heartbeat still convert that into failed/error outcomes rather than preserving the inbound event for retry.

## What This Changes

The issue reports that reply-session initialization conflicts can silently drop or terminalize non-Telegram inbound events instead of retrying, spooling, or coalescing them.

## Best Possible Solution

Resolve this at the shared reply-session initialization boundary, or make an explicit maintainer decision to add retry/coalescing parity to every affected inbound surface so future channels do not drift.

## Summary

Keep open: current main and v2026.6.11 still provide fixed-window receive-time inbound debounce, while incremental/count/typing-aware timing remains an unresolved product and config decision.

## What This Changes

Request adaptive inbound message debouncing that starts with a shorter wait, extends on subsequent same-window messages, and caps the delay with new config.

## Best Possible Solution

Decide the minimal core/channel policy first, then implement adaptive timing through the existing debouncer seam with focused config, docs, and cross-channel regression coverage.

## Reproduction Assessment

Not applicable as a bug reproduction: this is a feature request. Source inspection does confirm the current implementation is fixed-window debounce rather than adaptive debounce.

## Solution Assessment

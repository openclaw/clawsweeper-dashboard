## Summary

Keep open: current main and v2026.6.11 still implement fixed-window same-key inbound debounce only, while incremental/max-window/count/typing-aware behavior would add public config and change cross-channel turn-boundary semantics. The related issue history supports this as the canonical smarter-debounce product/API decision rather than a duplicate to close.

## What This Changes

The issue requests adaptive inbound debounce timing that starts with a short wait, grows for rapid follow-up messages, and caps at a configurable maximum.

## Best Possible Solution

Keep fixed inbound debounce as the baseline and have maintainers choose one opt-in smarter debounce contract covering adaptive, count, and typing-aware behavior with schema, docs, and cross-channel tests before implementation.

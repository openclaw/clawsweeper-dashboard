## Summary

Keep open: current main and v2026.6.11 still implement fixed-window same-key inbound debounce only, while the requested incremental/max/typing-aware behavior would add public config and change cross-channel turn-boundary timing. Related reports make this the canonical smarter-debounce discussion rather than an obsolete duplicate.

## What This Changes

The issue requests an opt-in adaptive inbound debounce strategy that starts with a shorter delay, extends on successive same-window messages up to a cap, and may add new config fields.

## Best Possible Solution

Define one opt-in adaptive inbound debounce contract, or explicitly keep fixed debounce as the supported baseline, before changing schema, docs, and channel behavior.

Options:

- **Design one opt-in adaptive contract (recommended):** Add a single generic inbound debounce policy with explicit initial/increment/max or equivalent semantics, plus schema, docs, and representative channel tests.

- **Require a channel/plugin seam first:** Defer core config until a typed channel or plugin ingress hook can expose provider-specific typing or count signals without growing global message config.

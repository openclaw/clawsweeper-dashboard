## Summary

Keep open: current main and v2026.6.11 still provide fixed-window same-key inbound debounce only, while adaptive/count/typing-aware timing remains a real product and config decision. The related issue history makes this the canonical smarter-debounce tracker rather than a duplicate to close.

## What This Changes

Request an incremental/adaptive inbound debounce strategy that starts with a short wait, extends on subsequent same-window messages, caps the delay, and may add new debounce config fields.

## Best Possible Solution

Keep fixed inbound debounce as the baseline, and have maintainers choose one opt-in smarter debounce contract covering adaptive/count/typing behavior with schema, docs, and regression tests before implementation.

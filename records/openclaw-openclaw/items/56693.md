## Summary

Keep open: current main has a narrow `deactivated_workspace` failover classifier, but OpenAI/Codex OAuth still stores and reuses one token-derived ChatGPT account id without validating or recovering an active workspace for multi-workspace users.

## What This Changes

The issue requests that OpenAI Codex OAuth avoid or recover from binding multi-workspace ChatGPT users to a deactivated workspace.

## Best Possible Solution

Add an OpenAI-plugin-owned workspace validation and recovery policy that selects and persists a usable ChatGPT accountId across login, refresh, provider catalog, and Codex app-server paths, with focused tests and live multi-workspace proof.

Rationale: The remaining fix changes auth-profile semantics, provider routing, and fallback/remediation behavior; the source shows several viable owners, but code alone cannot choose whether OpenClaw should auto-select, retry, persist, or only guide reauthentication.

Owner confidence: high

Options:

- **OpenAI plugin owns recovery (recommended):** Validate or recover a usable ChatGPT accountId after OAuth and on `deactivated_workspace`, then persist the recovered id for provider and app-server use.
- **Remediation only:** Keep the classifier mitigation and add clearer in-product guidance or doctor/onboarding recovery without automatically changing stored workspace selection.
- **Use explicit workspace selection:** Expose or derive an explicit upstream-compatible workspace selection contract, then enforce it instead of guessing among available workspaces.

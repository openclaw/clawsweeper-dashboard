## Summary

Keep open: current main has the merged `deactivated_workspace` failover classifier, but the OpenAI/Codex OAuth path still derives, stores, and reuses a single token-provided ChatGPT account id without validating that the workspace is active or recovering to another active workspace.

## What This Changes

The issue asks OpenClaw to avoid binding OpenAI/Codex OAuth to a deactivated ChatGPT workspace for multi-workspace accounts and to provide active-workspace recovery or clearer remediation.

## Best Possible Solution

Add an OpenAI-plugin-owned workspace validation and recovery path that reuses current Codex auth contracts, selects or persists a usable active ChatGPT account id, and provides a clear Doctor/setup remediation path when automatic recovery is unsafe.

## Reproduction Assessment

Yes for source reproduction: current main stores one token-derived ChatGPT account id and reuses it in usage and Codex app-server paths, while multiple users reported the same `deactivated_workspace` failure after OAuth succeeded. A live multi-workspace account is still needed to prove the exact upstream response sequence.

## Solution Assessment

No, the current merged classifier mitigation is useful but not the best complete fix. The durable fix needs a maintainer-approved OpenAI/Codex auth policy for when OpenClaw validates, retries, persists, or prompts for active workspace recovery.

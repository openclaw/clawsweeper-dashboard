## Summary

Keep open for maintainer review: the PR fixes a real current-main response-limit gap with focused tests and sufficient live-output proof, but it changes SDK-visible invalid-argument behavior and needs explicit compatibility acceptance before merge.

## What This Changes

Adds a finite, non-negative `maxBytes` guard in the shared HTTP response prefix reader and regression coverage for invalid response body/snippet limits.

## Best Possible Solution

Merge the shared-prefix guard once maintainers accept finite non-negative response byte caps as the SDK contract; if unbounded reads must be supported, add an explicit opt-in API instead of relying on non-finite sentinels.

## Reproduction Assessment

Yes, by source inspection. Current main compares response byte counts with `maxBytes` without validating it first, so `NaN` and `Infinity` bypass the intended cap.

## Solution Assessment

Yes, with maintainer compatibility acceptance. Validating once in `readResponsePrefix` is the narrowest maintainable fix because it covers both response APIs and matches the sibling byte-stream helper contract.

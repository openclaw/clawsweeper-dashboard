## Summary

Keep open: current main and v2026.6.11 still lack an agent-facing `queue_status` or equivalent workload/capacity surface, while the nearest queue diagnostics PR was closed unmerged and explicitly did not add the in-agent tool.

## What This Changes

Request an agent-facing `queue_status` tool that exposes queue/lane depth, active/max concurrency, and per-agent workload so dispatchers can choose idle agents before calling `sessions_spawn`.

## Best Possible Solution

Design one shared, read-only queue/workload snapshot backend in core, then expose a maintainer-approved subset through a permissioned `queue_status` agent tool with catalog/profile/policy entries, docs, and focused tests.

## Reproduction Assessment

Yes, as a source-level feature gap: current main has internal queue snapshots but no `queue_status`, no `sessions_capacity`, and no equivalent model-facing workload/capacity tool. I did not run a live workload because the requested public surface is absent.

## Solution Assessment

Unclear until maintainers choose the public metadata and permission contract. The likely best shape is a shared read-only queue snapshot backend reused by a permissioned agent-facing tool and any future operator surface.

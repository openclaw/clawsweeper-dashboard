## Summary

Keep open: current main and the latest release still lack an agent-facing `queue_status`, `sessions_capacity`, or `diagnostics.queue` surface for workload-aware dispatch, while the related queue diagnostics PR was closed unmerged and explicitly scoped out the in-agent tool.

## What This Changes

Request an agent-facing `queue_status` tool that exposes lane queue depth, active versus max concurrency, and per-agent workload so dispatchers can route `sessions_spawn` work intelligently.

## Best Possible Solution

Design one shared read-only queue/workload snapshot backend in core and expose it through a permissioned `queue_status` agent tool with catalog/profile/policy entries, docs, and focused tests.

## Reproduction Assessment

Yes. Source inspection shows current main lacks `queue_status`, `sessions_capacity`, and `diagnostics.queue`, while existing `agents_list`, `sessions_list`, and `session_status` omit active/queued/max-concurrent workload fields.

## Solution Assessment

Unclear until maintainers settle the public metadata contract. The likely best direction is a shared read-only queue snapshot backend reused by a permissioned agent-facing tool and any future operator surface.

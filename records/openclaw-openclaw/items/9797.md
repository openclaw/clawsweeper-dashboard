## Summary

Keep open: current main still has internal queue/lane snapshot helpers, but no stable agent-facing `queue_status`, no `sessions_capacity`, and no `diagnostics.queue` surface for workload-aware dispatch. The closed operator-diagnostics PR and closed capacity issue both point back to this issue as the canonical remaining tracker.

## What This Changes

Request an agent-facing `queue_status` tool that exposes lane queue depth, active versus max concurrent runs, and per-agent workload so dispatch agents can route work intelligently before calling `sessions_spawn`.

## Best Possible Solution

Design one shared read-only queue/workload snapshot backend in core, then expose it through a permissioned `queue_status` agent tool with catalog/profile/policy entries, docs, and focused tests.

## Reproduction Assessment

Yes, as a source-level feature gap: current main has internal queue snapshots but no `queue_status`, no `diagnostics.queue`, and no equivalent model-facing workload/capacity tool. I did not run a live workload because the requested public surface is absent.

## Solution Assessment

Unclear until maintainers choose the public metadata contract. The likely best shape is a shared read-only queue snapshot backend reused by a permissioned agent-facing tool and any future operator surface.

## Summary

Keep open: current main still lacks an agent-facing `queue_status` tool, any `sessions_capacity` equivalent, or a `diagnostics.queue` operator snapshot, while the related diagnostics PR was closed unmerged and explicitly did not add the in-agent tool.

## What This Changes

Request to add a `queue_status` agent tool exposing lane queue depth, active/max concurrency, and per-agent workload so agents can dispatch `sessions_spawn` work intelligently.

## Best Possible Solution

Design one shared read-only queue/workload snapshot backend in core and expose it through a permissioned `queue_status` agent tool with catalog/profile/policy entries, docs, and focused tests.

## Reproduction Assessment

Yes, as a source-level feature gap: current main has internal queue snapshots but no `queue_status`, no `sessions_capacity`, and no `diagnostics.queue` equivalent. I did not run a live workload because the requested public surface is absent.

## Solution Assessment

Unclear until maintainers choose the public metadata contract. The likely best shape is a shared read-only queue snapshot backend reused by a permissioned agent-facing tool and any future operator surface.

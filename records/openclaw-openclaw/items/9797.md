## Summary

Keep this issue open: current main and v2026.6.11 provide internal lane snapshots, but agents still cannot inspect queue depth or available concurrency before dispatching work. The remaining capability is well-defined, canonical, and supported by multiple related requests, but implementation should wait for a maintainer decision on workload visibility and authorization scope.

## What This Changes

Add an agent-facing read-only queue workload surface exposing lane depth, active concurrency, and dispatch capacity.

## Best Possible Solution

Expose deterministic advisory capacity through one canonical read-only snapshot provider, filtered to targets the caller may spawn or observe, and reuse that contract for any later operator or UI consumer without adding scheduling policy or reservation guarantees.

Rationale: The internal data exists, but current session and tool authorization contracts do not decide whether callers may inspect unrelated lane or agent activity; that boundary affects privacy, multi-user deployments, and the public API shape.

Options:

- **Scoped Dispatch Capacity (recommended):** Expose active, queued, and maximum capacity only for authorized spawn targets, omitting unrelated session identifiers and documenting the result as advisory.
- **Full Workload Snapshot:** Expose all lanes and per-agent workload to suitably privileged agents through an explicit diagnostics permission.
- **Operator-Only Diagnostics:** Keep workload visibility in authenticated CLI, RPC, or UI surfaces and do not expose it to agents.

## Solution Assessment

Unclear. Reusing the internal snapshot backend is the right foundation, but a broad new queue_status contract is not the best final API until maintainers choose the caller visibility boundary and whether scoped fields belong in an existing status tool.

## Summary

Keep open: current main has internal lane snapshots, diagnostics events, session listing, and subagent listing, but still lacks the requested agent-facing `queue_status` or equivalent workload/capacity tool for dispatch decisions. The related operator diagnostics PR was closed unmerged and explicitly scoped out the in-agent tool.

## What This Changes

Issue requests a new agent-facing `queue_status` tool that exposes lane queue depth, active/max concurrency, and per-agent workload state for intelligent task dispatch.

## Best Possible Solution

Design a shared read-only queue/workload snapshot in core and expose it through a permissioned `queue_status` tool with catalog/profile/policy wiring, docs, and focused tests; any future operator CLI/RPC can reuse that backend.

## Reproduction Assessment

Yes, as a source-level feature gap: current main has no `queue_status`, no `diagnostics.queue`, and no equivalent model-facing workload/capacity tool. I did not run a live workload because the requested surface is absent.

## Solution Assessment

Unclear until maintainers choose the public metadata contract. The likely best direction is a shared read-only queue snapshot backend reused by a permissioned agent-facing tool, rather than grafting partial capacity fields onto `agents_list` or `sessions_list`.

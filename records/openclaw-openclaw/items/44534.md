## Label Justifications

- `P3`: This is a low-risk diagnostic wording and ergonomics issue, not a runtime outage, data loss, security problem, or blocked setup path.
- `impact:ux-friction`: The raw `target-none` wording can send operators into unnecessary channel/session routing debugging even though delivery is disabled by configuration.

## Summary

Keep open: current main and v2026.6.11 still expose the raw `target-none` heartbeat skip reason without a disabled-delivery hint, and the direct fix PRs are closed unmerged, so the remaining work is a maintainer choice about the diagnostic contract.

## What This Changes

The issue asks OpenClaw to make heartbeat skips for default `target: "none"` read as intentionally disabled delivery rather than a missing target.

## Best Possible Solution

Preserve `target-none` as the machine-readable reason unless maintainers explicitly approve a rename, and add a human-readable disabled-delivery explanation to heartbeat-last/status output with focused coverage.

- **Add a disabled-delivery hint (recommended):** Keep `reason: "target-none"`, add an optional human-facing hint or display field, and render it in heartbeat-last/status surfaces with tests.
- **Rename the reason:** Change the exposed reason to a clearer value such as `delivery-disabled`, accepting compatibility risk for consumers of the old string.
- **Leave output as-is:** Rely on docs to explain `target: "none"`, accepting continued low-priority operator confusion.

## Reproduction Assessment

Yes. Source inspection shows unset or explicit `target: "none"` resolves to `reason: "target-none"`, and the CLI/gateway path returns that stored heartbeat event without a disabled-delivery hint.

## Solution Assessment

Unclear until maintainers choose the diagnostic contract. The additive-hint path is the safest apparent fix because it improves the operator-facing text without changing the existing machine reason.

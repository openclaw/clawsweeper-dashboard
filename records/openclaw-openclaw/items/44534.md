## Summary

Keep open: current main and the latest release still expose disabled heartbeat delivery as `reason: "target-none"` without a human-readable disabled-delivery explanation, while the direct fix PRs are closed unmerged. The remaining blocker is maintainer product direction on whether to preserve the machine reason and add an additive hint/display or rename the reason itself.

## What This Changes

The issue asks OpenClaw to make disabled-by-default heartbeat delivery diagnostics clearer than `reason: "target-none"` in `openclaw system heartbeat last` and related status/log output.

## Best Possible Solution

Keep the existing machine reason stable unless maintainers explicitly approve a rename, and add a disabled-delivery hint or display path that reaches heartbeat-last and deep status output with focused tests.

Rationale: The source repro is clear, but this changes exposed diagnostics for a default configuration path, and repository policy treats config/default diagnostic surfaces as compatibility-sensitive when operators may parse them.

Owner confidence: high

Options:

- **Add additive hint/display (recommended):** Keep `reason: "target-none"`, add disabled-delivery explanatory text or a companion field, and update CLI/status formatting plus focused tests.
- **Rename the machine reason:** Change the exposed reason to a clearer value such as `delivery-disabled`, accepting parser compatibility risk for any operator tooling that reads the current reason.
- **Leave current output:** Keep relying on docs and accept the current low-priority operator confusion around `target-none`.

Yes. Source inspection on current main shows unset or explicit `target: "none"` resolves to `reason: "target-none"`, and `openclaw system heartbeat last` returns the raw heartbeat event.

Unclear until maintainers choose the diagnostic contract. The additive-hint shape is the best current candidate because it fixes operator-facing wording without breaking the existing machine reason.

## Summary

Keep open: current main and v2026.6.11 still emit the raw `target-none` heartbeat skip reason without a disabled-delivery hint, and the two direct repair PRs are closed unmerged, so the remaining work is a small diagnostic contract decision.

## What This Changes

Clarify disabled heartbeat delivery so operators do not misread `reason: "target-none"` as a missing recipient or session-routing failure.

## Best Possible Solution

Preserve `target-none` as the machine-readable reason and add an additive human-readable disabled-delivery hint/status presentation with focused resolver and formatter coverage after maintainer approval.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw keep `target-none` as the machine-readable heartbeat skip reason and add an additive disabled-delivery hint, or rename the reason string itself?

Rationale: Both approaches reduce operator confusion, but the rename has compatibility risk while the additive hint creates a small new diagnostic payload surface.

Likely owner: steipete

Owner reason: The default-disabled heartbeat behavior traces to the merged heartbeat-default work and this is now a compatibility/product choice for that diagnostic contract.

Owner confidence: high

Options:

- **Add hint, keep reason (recommended):** Keep `reason: "target-none"` stable and surface a human-readable disabled-delivery hint in heartbeat events/status output.
- **Rename reason:** Change the machine reason to a clearer value such as `delivery-disabled`, accepting potential parser/log compatibility churn.
- **Document only:** Leave runtime output unchanged and rely on docs/troubleshooting text, which avoids API churn but leaves the confusing CLI/log signal in place.

## Reproduction Assessment

Yes by source inspection. Current resolver/tests show unset and explicit `target: "none"` produce `reason: "target-none"`, and the status formatter has no disabled-delivery hint path.

## Solution Assessment

Unclear until maintainers choose the diagnostic contract. The additive hint/status rendering approach appears safest because it preserves the existing reason string while fixing the operator-facing message.

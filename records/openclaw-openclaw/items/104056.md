## Summary

The feature remains necessary on current `main` and already has an open implementation candidate. Because it transfers reusable authentication state from a real browser into an agent-controlled profile, the protected `maintainer` label and repository security policy require an explicit human decision on defaults and consent.

**Likely related people**
- `steipete` — high confidence; introduced the existing-session browser path and moved browser ownership into the bundled plugin.

- `odysseus0` — medium confidence; hardened and simplified existing-session lifecycle behavior.
- `velvet-shark` — medium confidence; extended existing-session profiles to non-Chrome user-data directories.

## What This Changes

Add macOS support for importing selected cookies from Chrome-family system profiles into persistent OpenClaw-managed browser profiles through CLI, agent-tool, and host-local route surfaces.

## Best Possible Solution

Ship the import within the bundled browser plugin only after maintainers approve an opt-in, host-local design with per-import human consent, explicit source, destination, and domain display, redacted outputs, reliable profile reset or revocation, and live macOS proof that remote nodes and sandboxes cannot invoke it.

## Risks / Open Questions

- The feature decrypts and copies reusable authentication cookies into an agent-controlled persistent profile, expanding the consequences of prompt injection or an over-broad browser-tool invocation.
- A default-on kill switch would expose the capability to existing installations without an affirmative operator choice; Keychain consent alone may not communicate which domains or managed profile receive the session state.
- Agent, CLI, route, gateway, and node-routing exposure creates several authorization surfaces that must all remain host-local and fail closed.
- Imported sessions can outlive the one-time Keychain prompt, so reset, revocation, auditability, and user-visible recovery behavior need explicit ownership.

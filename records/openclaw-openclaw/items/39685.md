## Summary

Keep open: current `main` and latest release still lack a generic operator-controlled domain allow/deny egress firewall for `web_fetch` and managed `web_search`; the related open PRs are partial, draft, or competing security-boundary directions rather than merged replacements.

## What This Changes

The issue requests `allowedDomains`/`denyDomains` network access control for OpenClaw web tools, especially `web_fetch` and `web_search`.

## Best Possible Solution

Define one maintainer-approved web egress security contract, then land schema, runtime enforcement, cache/provider-fallback behavior, docs, audit output, and upgrade handling around that contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw's public web-tool egress boundary be a scoped `web_fetch` domain policy, a shared `web_fetch`/`web_search`/browser policy, or an operator-managed proxy contract?

Rationale: This would add an operator-trusted security/config boundary, and the open related PRs encode different answers that automation should not choose without maintainer security intent.

Likely owner: Peter Steinberger

Owner reason: Peter Steinberger has the strongest history across SSRF, guarded fetch, and web-tool security code paths implicated by this boundary choice.

Owner confidence: high

Options:

- **Define Shared Egress Contract (recommended):** Set the cross-tool semantics first, including allow/deny precedence, redirects, caches, provider fallback, hosted search, browser navigation, proxy ownership, docs, and upgrade behavior.
- **Land Scoped web_fetch First:** Sponsor the narrow `web_fetch` hostname-allowlist path as an interim contract while keeping deny domains, search, browser, and proxy coverage tracked separately.
- **Use Managed Proxy As Boundary:** Make `proxy.enabled` plus external proxy policy the primary egress firewall and avoid adding local domain firewall semantics to web tools.

## Reproduction Assessment

Yes for the missing capability by source inspection: current `main` has strict `web_fetch` config and runtime wiring without generic domain allow/deny policy, while lower-level SSRF primitives already support hostname allowlists. This is not a bug reproduction because the issue requests a new security/config capability.

## Solution Assessment

Unclear until maintainers set the boundary. `SsrFPolicy.hostnameAllowlist` is a good primitive for direct `web_fetch`, but deny semantics and coverage across search, redirects, cache, provider fallback, browser, and proxy paths need approval.

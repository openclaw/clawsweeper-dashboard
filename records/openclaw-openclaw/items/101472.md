## Summary

The bounded-read idea is useful, but this PR should stay open because the implementation reopens the canonical path after `openRootFileSync` has established the root-boundary file descriptor, creating a security-boundary regression under path-swap races.

## What This Changes

The PR adds 1 MiB caps for hook workspace `package.json` and `HOOK.md` reads and tests that oversized hook metadata is skipped.

## Best Possible Solution

Keep the byte cap, but implement the bounded read against the already-opened root-boundary fd, with regression coverage that preserves the existing symlink/hardlink containment behavior.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, from source inspection: current `main` reads hook `package.json` and `HOOK.md` through `fs.readFileSync(opened.fd)` without a byte cap, and the PR’s tests model oversized files. I did not execute the test run in this read-only review.

## Solution Assessment

No. The cap is the right direction, but reopening `opened.path` is not the best fix because it discards the validated fd; a bounded fd read preserves both OOM protection and root-boundary integrity.

- **[P1] Preserve the validated root fd for the bounded read:** `src/hooks/workspace.ts:309`
  - body: This reopens `opened.path` after `openRootFileSync` has already validated and pinned the root-boundary target.

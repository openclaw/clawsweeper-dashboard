## Label Justifications

- `P1`: The issue reports a real agent workflow failure where long-running CLI-backed turns are terminated mid-flight and can surface as all models failed.
- `impact:session-state`: The timeout can kill an in-flight resumed CLI session before the agent consumes the result of long-running work.
- `impact:crash-loop`: The failure mode is process-level availability: OpenClaw terminates the CLI process after the no-output watchdog fires.

## Summary

Keep open: current main and v2026.6.11 still preserve the 180-second no-output watchdog ceiling for ordinary inherited resumed CLI user runs, while the remaining default/disable behavior is a maintainer timeout-policy decision rather than a completed fix.

## What This Changes

The issue requests raising or removing the CLI no-output watchdog cap so long-running CLI-backed agent turns are not killed while legitimately silent.

## Best Possible Solution

Choose a bounded inherited-resume watchdog policy, then land a focused change that updates the resolver/defaults, preserves existing per-backend override behavior, and proves both long-silent healthy runs and stuck-process guard behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For ordinary inherited resumed CLI user runs with no explicit timeout intent, should OpenClaw keep the 180-second no-output guard, raise it to a longer bounded default, or support disabling it?

Rationale: The source-level problem is real, but the remaining change intentionally trades faster stuck-process recovery for fewer false kills during legitimate long-silent work; automation should not choose that product/safety default.

Likely owner: vincentkoc

Owner reason: They authored and verified the most recent merged timeout-provenance fix and explicitly preserved this inherited-resume guard in that work.

Owner confidence: high

Options:

- **Raise to a bounded longer default (recommended):** Use a larger inherited-resume ceiling, keep positive per-backend overrides for stricter setups, and avoid adding a disable mode unless later evidence needs it.
- **Keep the 180-second guard:** Document the current safety tradeoff and ask operators with known long-silent backends to configure backend-specific watchdog values.
- **Add an explicit disable mode:** Allow `0` or `null` only with clear docs and tests proving the outer run timeout still protects users from unbounded stalls.

## Reproduction Assessment

Yes, at source level: current main has a focused resolver test showing an ordinary resumed user run with a 600,000 ms overall timeout still resolves to a 180,000 ms no-output watchdog. I did not run a live 180-second silent CLI stall in this read-only review.

## Solution Assessment

Unclear until maintainers choose the timeout policy. The safest implementation path is a narrow resolver/defaults change after deciding the safety tradeoff, rather than landing a broad TUI plus CLI config PR without proof.

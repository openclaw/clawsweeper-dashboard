## Label Justifications

- `impact:session-state`: A watchdog kill can end an in-flight CLI-backed session before the agent completes or preserves the turn state.

## Summary

Keep open: current main and v2026.6.11 still preserve the 180-second no-output ceiling for ordinary inherited resumed CLI-backed user runs, while merged work only fixed configured or explicit timeout intent and the remaining raise/disable behavior is a maintainer timeout-policy choice.

## What This Changes

Request to raise, remove, or make tunable the CLI no-output watchdog cap that terminates long silent resumed CLI-backed agent requests after about three minutes.

## Best Possible Solution

Land a narrow maintainer-approved CLI watchdog policy change through the existing defaults/config surface, with resolver coverage and real long-silent CLI proof; keep adjacent TUI streaming-watchdog configuration on its own tracker.

## Maintainer Decision

Question: Should ordinary inherited resumed CLI-backed user runs keep the 180-second no-output guard, move to a longer bounded default, or gain explicit disable/tuning semantics?

Rationale: Current main intentionally preserves the inherited resume guard after the configured-timeout fix, and changing the default or disable semantics trades long-task availability against stuck-process recovery and config compatibility for existing users.

Likely owner: vincentkoc

Owner reason: vincentkoc merged and co-authored the most recent timeout-provenance PR that defines the current remaining policy boundary.

Owner confidence: high

Options:

- **Approve a bounded longer default (recommended):** Raise the inherited resume ceiling through the existing watchdog defaults, keep the watchdog enabled, and require resolver plus real behavior proof for long silent work and stalled-process recovery.
- **Add explicit disable or tuning semantics:** Accept 0/null-style disable behavior only with schema, docs, upgrade, and compatibility proof for existing configs.
- **Keep the 180-second inherited guard:** Leave current behavior intact and document per-backend watchdog overrides for operators with known long silent CLI workloads.

## Reproduction Assessment

Yes, at source level. Current main has focused coverage showing an ordinary resumed user run with a 600s outer timeout still resolves to a 180s no-output watchdog, and the runner uses that value in the termination path.

## Solution Assessment

No complete fix is on main yet. A bounded default change through the existing watchdog surface looks like the narrowest likely implementation path, while disabling or changing public config semantics needs maintainer approval and upgrade proof.

## Summary

Keep this PR open for explicit maintainer review. It has credible live-provider and upgrade evidence, but it intentionally changes the GitHub Copilot runtime credential contract and request identity for existing profiles; the remaining question is whether maintainers accept that compatibility boundary, especially without enterprise-tenant proof.

## What This Changes

The branch replaces GitHub Copilot’s retired runtime token exchange with source-credential validation, account-specific endpoint resolution, and provider-owned `copilot-developer-cli` request headers so fine-grained GitHub tokens work across Copilot runtime surfaces.

## System Context

The GitHub Copilot plugin converts a stored GitHub credential into prepared runtime authentication: it validates access, resolves a trusted Copilot API endpoint, and supplies request headers. OpenClaw’s catalog, chat streaming, embeddings, usage, and image paths consume that prepared authentication when making provider requests.

## Architecture Diagram

flowchart LR
  Credential[Stored GitHub credential] --> RuntimeAuth[Copilot runtime authentication]
  RuntimeAuth --> Endpoint[Trusted Copilot API endpoint]
  RuntimeAuth --> Headers[Provider-owned request headers]
  Endpoint --> ProviderRuntime[OpenClaw provider runtime]
  Headers --> ProviderRuntime
  ProviderRuntime --> Surfaces[Chat, catalog, embeddings, usage, media]

## Best Possible Solution

Accept the provider-owned source-credential path only after the Copilot owners confirm that the CLI integration identity is the supported compatibility contract for public and enterprise tenants; retain the explicit trusted-endpoint validation and provider-local legacy-profile normalization.

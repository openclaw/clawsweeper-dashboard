## Summary

Keep open: current main and v2026.6.11 still have a source-level path where configured TTS provider SecretRefs are collected during startup and any unresolved startup secret aborts the Gateway. The exact fix needs maintainer intent because changing which SecretRefs fail closed at startup is a product/security-boundary choice.

## What This Changes

Allow the Gateway to start when an optional ElevenLabs/TTS API-key SecretRef is missing, degrading only TTS/ElevenLabs while chat, runtime, and unrelated plugins remain available.

## Best Possible Solution

Define a generic optional-capability SecretRef degradation path for TTS/provider keys: Gateway startup stays up, auth/core required secrets still fail closed, status/doctor/audit report the missing key, and TTS calls return a clear unavailable error.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `messages.tts.providers.*.apiKey` and related optional TTS provider SecretRefs be non-fatal at Gateway startup while gateway auth and other required runtime secrets remain fail-closed?

Rationale: The code can support a repair, but choosing which configured SecretRefs are optional at startup changes the product's fail-closed boundary and needs maintainer intent.

Likely owner: joshavant

Owner reason: The decision centers on the SecretRef runtime framework and active/inactive assignment semantics introduced in the broad SecretRef coverage work.

Owner confidence: high

Options:

- **Degrade optional TTS secrets (recommended):** Treat unresolved optional TTS provider keys as configured-unavailable at startup and keep the Gateway running, while preserving strict startup failure for gateway auth and explicitly required secrets.
- **Keep all configured refs strict:** Preserve the current fail-closed startup behavior for every collected active SecretRef, accepting that optional TTS misconfiguration can take down the Gateway.
- **Only skip inactive providers:** Resolve only provider keys that are selected by active TTS config, which reduces some false failures but still fails startup when the selected optional TTS provider key is missing.

## Reproduction Assessment

Yes, source-level: current main collects `messages.tts.providers.*.apiKey` SecretRefs into the runtime secret snapshot, resolves all collected refs, and wraps startup resolution failure as a fatal required-secret error. I did not run a live Gateway startup repro in this read-only review.

## Solution Assessment

Unclear until the maintainer decision is made. The best maintainable fix is a generic optional-secret degradation boundary for TTS/provider capabilities, not an ElevenLabs-only bypass or a blanket removal of TTS SecretRef resolution.

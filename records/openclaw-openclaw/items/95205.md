## Summary

Keep open: the stale Anthropic OAuth user-agent fix is real, but this branch still moves version discovery into request/header construction with synchronous first-on-PATH command execution and unproven Windows npm-global behavior.

## What This Changes

## Best Possible Solution

Keep the two-call-site stale-header fix, but prepare and cache a cross-platform Claude Code version at an owned setup or provider boundary before OAuth request construction.

## Reproduction Assessment

Yes from source: current main and v2026.6.11 still send `claude-cli/2.1.75` from both Anthropic OAuth builders, and https://github.com/openclaw/openclaw/issues/94716 provides a concrete Windows/OpenClaw reproduction. I did not run a live Anthropic OAuth request in this read-only review.

## Solution Assessment

No: fixing both OAuth builders is the right scope, but synchronous first-on-PATH CLI discovery during header construction is not the safest owner boundary. A prepared and cached cross-platform version source before request construction is the better fix.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.88

Full review comments:

- **[P1] Resolve Claude version outside the auth request path:** `src/llm/utils/claude-code-version.ts:35-38`
  - body: Both patched OAuth builders call `claudeCodeUserAgent()` while constructing headers, and the default resolver synchronously executes the first `claude` on PATH with a 2s timeout before package fallback. That makes Anthropic OAuth request/client construction depend on ambient command execution and can stall or fail closed for existing users; resolve and cache this at an owned setup or provider boundary instead.
  - confidence: 0.9
- **[P1] Handle Windows npm shims before relying on execFile:** `src/llm/utils/claude-code-version.ts:35`
  - body: The linked bug is reported on Windows with a global npm Claude Code install, and this PR's repro simulates `claude.cmd` on Windows, but the resolver calls `execFileSync("claude")`. That leaves the reported install path unproven; resolve the package/bin source or explicit shim path instead of relying on a bare execFile lookup.
  - confidence: 0.86

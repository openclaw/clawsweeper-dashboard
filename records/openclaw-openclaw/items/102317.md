## Label Justifications

- `P2`: This is a normal-priority config validation bug with limited blast radius: malformed heartbeat active-hours windows can be accepted and run at the default cadence.
- `impact:ux-friction`: A user can configure an invalid active-hours window and get surprising 24/7 heartbeat behavior instead of an actionable config error.

## Summary

This issue should stay open: current main still returns from `HeartbeatSchema.superRefine` when `every` is omitted, so malformed `activeHours.start`/`end` bypass the existing HH:MM validation and then hit the runtime's permissive invalid-window path.

## What This Changes

Request validation of heartbeat `activeHours.start` and `activeHours.end` even when `heartbeat.every` is omitted and the default cadence is used.

## Best Possible Solution

Keep the runtime fallback unchanged and move `activeHours` time validation outside the `every` guard in `HeartbeatSchema`, with defaults and per-agent schema regression coverage.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, source inspection gives a high-confidence repro path: parse a heartbeat object with `activeHours.start` or `end` malformed and `every` omitted, and current main skips the active-hours checks. I did not run the safeParse command in this read-only review.

## Solution Assessment

Yes, validating active-hours times in the existing schema regardless of `every` is the narrowest fix. Runtime should keep its permissive fallback for already-invalid internal input, while config load rejects malformed user config.

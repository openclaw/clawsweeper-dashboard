## Summary

Keep open: the provider-specific picker reduction is well targeted, but the current head still makes inherited OpenAI Fast/Standard look selected while the click handler compares only the stored override, so clicking the selected value can persist a session-level override. Real after-fix Control UI proof is also still missing.

## What This Changes

The PR changes the Control UI fast-mode resolver so OpenAI shows Standard and Fast instead of Default, Fast, Standard, and Auto, adds resolver coverage, and adds a changelog line.

## Best Possible Solution

Keep the OpenAI Standard/Fast picker, but make inherited selected values no-op on click or visibly distinguish them from explicit overrides, then add redacted real Control UI proof before merge.

## Reproduction Assessment

Yes from source inspection: current main always returns Default, Fast, Standard, and Auto for supported fast-mode providers, and the PR head still pairs effective OpenAI selection with a stored-only click no-op check. I did not run the Control UI live in this read-only review.

## Solution Assessment

No: reducing OpenAI to Standard/Fast is the right direction for the existing boolean speed control, but the selected inherited state must not write a session override on an unchanged click. A safer fix compares against effective mode or distinguishes inherited/default selection in the UI before patching.

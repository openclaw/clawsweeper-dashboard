## Label Justifications

- `P1`: Multiple Feishu users report that normal bot operation pressures organizations toward broad contact-directory permissions or noisy authorization prompts.
- `impact:security`: The issue concerns organization contact-directory access being used for basic Feishu sender display-name behavior.
- `impact:auth-provider`: The failure mode is tied to Feishu permission scopes, authorization prompts, and credentialed contact API access.
- `impact:ux-friction`: Users can proceed only by granting sensitive permissions, disabling sender-name lookup, or tolerating degraded sender labels and permission noise.

## Summary

Keep open: current main and the latest release still use Feishu contact-directory APIs for default sender-name lookup and live peer listing, while an open maintainer-owned Feishu display-name PR only partially overlaps the broader contact-free default requested here.

## What This Changes

The issue asks for Feishu sender-name resolution and live directory listing to stop depending on broad contact-directory permissions during basic bot use.

## Best Possible Solution

Make basic inbound Feishu messages contact-free by default, use verified lower-scope metadata or stable sender ids, and require explicit opt-in for contact-backed sender lookup and live user-directory listing with docs and regression coverage.

- **Land Narrow Display-Name PR First:** Resolve https://github.com/openclaw/openclaw/pull/73399 first for DM fallback behavior, then keep this issue open for the broader contact-free default and live-directory decision.

Yes, at source level: current main defaults Feishu sender-name resolution on and the resolver still calls the Feishu contact user API. I did not run a live Feishu tenant, but current source, tests, docs, comments, and the latest release preserve the reported dependency.

## Summary

Keep open: current main and v2026.6.11 still default Feishu sender-name resolution to a contact-backed lookup, live peer listing still uses the Feishu contact directory, and the overlapping open PR only partially addresses the display-name path while remaining human-review/security blocked.

## What This Changes

The issue asks OpenClaw to remove Feishu basic sender-name resolution's dependency on the broad `contact:contact.base:readonly` contact-directory permission.

## Best Possible Solution

Make default Feishu inbound sender attribution contact-free, fall back quietly to a stable sender id, and gate contact-backed profile or live user-directory lookup behind explicit operator opt-in with docs and regression tests.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: current main defaults `resolveSenderNames` on and still calls Feishu contact user APIs for sender names and live peer listing. I did not run a live Feishu tenant in this read-only review.

## Solution Assessment

Yes on direction, but the exact implementation needs maintainer choice. The Feishu plugin is the right boundary, but maintainers should choose the low-scope metadata source and opt-in semantics before changing defaults.

## Summary

Keep open: current main and v2026.6.11 still default Feishu sender-name resolution to a contact-backed lookup, and live peer listing still calls the contact directory. The issue is valid, security-sensitive, and overlapping with an open maintainer-labeled PR, but that PR is partial and human-review blocked rather than a landed fix.

## What This Changes

The issue asks OpenClaw to make basic Feishu sender-name handling work without requiring broad contact-directory permission.

## Best Possible Solution

Make basic inbound Feishu messages contact-free by default: use verified event or chat-member metadata when available, fall back quietly to the stable sender id, and require explicit opt-in plus docs/tests for contact-backed profile lookup and live user-directory listing.

## Reproduction Assessment

Yes. Source inspection on current main shows the default inbound Feishu sender-name path still calls `client.contact.user.get`, while live directory peer listing still calls `client.contact.user.list`; I did not run a live Feishu tenant repro in this read-only review.

## Solution Assessment

Unclear as a final implementation choice. The requested security direction is sound, but the exact replacement should be maintainer-approved because it changes Feishu default identity behavior and may need an explicit opt-in surface for contact-backed enrichment.

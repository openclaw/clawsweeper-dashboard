- `impact:security`: The issue concerns broad organization contact-directory access being used for basic sender display names.
- `impact:auth-provider`: The failure mode is tied to Feishu permission scopes, authorization prompts, and credentialed API access.
- `impact:ux-friction`: Users can proceed only by granting sensitive permissions, disabling sender-name lookup, or tolerating degraded labels and noisy permission behavior.

## Summary

Keep open: current main and the latest release still use contact-backed Feishu sender-name lookup by default, so the broad contact-directory permission problem remains real and needs maintainer-owned security/product follow-up.

## What This Changes

The issue requests making Feishu sender-name resolution avoid the broad contact-directory permission for basic inbound Feishu message handling.

## Best Possible Solution

Make basic inbound Feishu messages contact-free by default: use verified event or chat-member metadata when available, fall back quietly to the stable sender id, and require explicit opt-in for contact-backed profile lookup and live user-directory listing with docs and regression coverage.

## Reproduction Assessment

Yes, by source inspection: current main and v2026.6.11 default Feishu sender-name resolution on and the resolver still calls the Feishu contact user API. I did not run a live Feishu workspace, but the current code, tests, docs, and release tag all preserve the reported dependency.

## Solution Assessment

Unclear as an exact implementation path: the contact-free default is the right end state, but maintainers need to decide whether event metadata, chat-member lookup, a static mapping, or an explicit contact-lookup opt-in should be the permanent product contract.

## Summary

Keeping this issue open: current main and the latest release still default Feishu sender-name resolution to a contact-backed lookup, the docs still describe manual opt-out, and live peer listing still reaches the contact directory. The report remains security/auth-sensitive, but it is assigned and already routed for maintainer/product/security review with an overlapping open maintainer-labeled PR, so cleanup closure or a competing automated fix would be premature.

## What This Changes

The issue asks for the Feishu plugin to stop requiring the broad contact-directory permission for basic sender-name resolution and to make contact-backed directory access explicit rather than default.

## Best Possible Solution

Make basic inbound Feishu sender attribution contact-free by default, fall back quietly to a stable sender id, and gate contact-backed profile lookup plus live user-directory listing behind explicit operator opt-in with docs and regression tests.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: with `resolveSenderNames` unset or true, inbound Feishu messages call `resolveFeishuSenderName`, which calls `client.contact.user.get`; live peer listing also calls `client.contact.user.list`.

## Solution Assessment

Unclear. The contact-free default is the right end state for safer basic messaging, but maintainers still need to choose the trusted Feishu metadata source and opt-in semantics before changing defaults.

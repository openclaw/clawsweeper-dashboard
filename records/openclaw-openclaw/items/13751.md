## Label Justifications

- `impact:security`: The reported behavior pressures operators to grant organization-wide contact directory access for a narrow sender-name feature.

## Summary

Keep open: current main and latest release still default Feishu sender-name resolution to a contact-backed lookup, live peer listing still uses the Feishu contact directory, and the active overlapping Feishu PR is open, conflicting, and marked for human review rather than owning the full contact-free default.

## What This Changes

The issue requests changing Feishu sender-name and directory behavior so basic inbound messages no longer depend on the broad contact directory permission.

## Best Possible Solution

Make basic inbound Feishu messages contact-free by default: use verified event or chat-member metadata when available, fall back quietly to the stable sender id, and require explicit opt-in for contact-backed sender profiles or live user-directory listing with docs and regression proof.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: current main defaults `resolveSenderNames` to true and then calls `client.contact.user.get` for inbound sender attribution. I did not run a live Feishu tenant in this read-only review.

## Solution Assessment

Yes on direction, but not yet on final implementation shape: suppressing noisy errors alone is too narrow, while a maintainable fix should make the default path contact-free and make contact-backed lookup an explicit operator choice.

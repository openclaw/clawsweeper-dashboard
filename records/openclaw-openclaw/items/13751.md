## Summary

Keep open: current main and the latest release still default Feishu sender-name resolution to contact-backed lookup and still use the contact directory for live peer listing. The issue is valid and security/auth-sensitive, but it is assigned and overlaps an open maintainer-labeled Feishu display-name PR, so the next step is maintainer coordination rather than cleanup closure or a competing automated fix.

## What This Changes

The issue requests that Feishu basic sender attribution and peer listing stop depending on broad contact-directory permissions by default.

## Best Possible Solution

Make basic inbound Feishu sender attribution contact-free by default, fall back quietly to a stable sender id, and gate contact-backed profile lookup plus live user-directory listing behind explicit operator opt-in with docs and regression tests.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: with `resolveSenderNames` unset or true, inbound Feishu messages call `resolveFeishuSenderName`, which calls `client.contact.user.get`; live peer listing also calls `client.contact.user.list`.

## Solution Assessment

Unclear. A contact-free default is the right security end state for basic messaging, but maintainers still need to choose the trusted Feishu metadata source and opt-in semantics before changing defaults.

## Label Justifications

- `P1`: Multiple Feishu users report normal bot operation pushing them toward broad organization contact permissions or noisy authorization prompts.
- `impact:security`: The issue concerns broad organization contact-directory access being used for basic sender display-name behavior.
- `impact:auth-provider`: The failure mode is tied to Feishu permission scopes, authorization prompts, and credentialed API access.
- `impact:ux-friction`: Users can proceed only by granting sensitive permissions, disabling sender-name lookup, or tolerating degraded sender labels and permission noise.

## Summary

Keep open: current main and v2026.6.11 still use contact-backed Feishu sender-name lookup by default and live peer listing still enumerates contact users, so the broad contact-directory permission concern remains real and needs maintainer-owned security/product direction.

## What This Changes

Request contact-free default Feishu sender-name resolution and explicit opt-in behavior for contact-backed profile or directory lookup.

## Best Possible Solution

Make basic inbound Feishu messages contact-free by default, use verified event or chat-member metadata only when safe, fall back quietly to the stable sender id, and require explicit opt-in for contact-backed profile lookup and live user-directory listing with docs and regression coverage.

Options:

- **Contact-free default with explicit opt-in (recommended):** Default basic inbound messages to no contact-directory calls, use only verified lower-scope metadata or stable sender ids, and add or reuse explicit opt-in behavior for contact-backed lookup and live directory listing.
- **Keep current opt-out model:** Preserve resolveSenderNames default true and document the sensitive permission tradeoff, accepting the current security and UX friction.
- **Land narrower DM fallback first:** Resolve the paused Feishu PR first for DM display names, then keep this issue open for the remaining contact-free default and live-directory decision.

Yes, by source inspection: current main defaults Feishu sender-name resolution on and the resolver still calls the Feishu contact user API. I did not run a live Feishu workspace, but current source, tests, docs, and the latest release preserve the reported dependency.

## Solution Assessment

Unclear as an exact implementation path: a contact-free default is the right end state, but maintainers need to choose whether event metadata, chat-member lookup, static config, or explicit contact lookup should be the permanent Feishu contract.

## Label Justifications

- `P1`: Basic Feishu channel use can still depend on a sensitive organization contact-directory permission path for sender attribution.
- `impact:security`: The issue is about avoiding default access to organization-wide contact directory data for ordinary sender attribution.

## Summary

Keep open: current main and the latest release still default Feishu sender-name resolution to a contact-backed lookup, and live Feishu peer listing still uses the contact directory API, so the sensitive-permission dependency remains.

## What This Changes

The issue asks for basic Feishu inbound sender attribution to stop depending on `contact:contact.base:readonly` or broad contact-directory access by default.

## Best Possible Solution

Make default Feishu inbound sender attribution contact-free, fall back quietly to a stable sender id, and require explicit operator opt-in for contact-backed profile lookup and live user-directory listing with docs and regression tests.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 still default sender-name resolution on and call Feishu contact APIs for sender names and live peer listing. I did not run a live Feishu tenant in this read-only pass.

## Solution Assessment

Yes on direction, but the exact patch still needs maintainer choice. The Feishu plugin is the right owner boundary, while maintainers should choose the low-scope sender metadata path and opt-in semantics before changing defaults.

## Label Justifications

- `P1`: Basic Feishu channel use can still depend on a sensitive organization contact-directory scope and user-facing permission prompts.
- `impact:security`: The issue is about avoiding default access to sensitive organization contact-directory data for ordinary sender attribution.
- `impact:auth-provider`: The behavior depends on Feishu authorization scopes and permission-grant handling for the channel integration.
- `impact:ux-friction`: Users can encounter noisy permission guidance or organization-policy friction during normal Feishu message handling.

## Summary

Keep open: current main and v2026.6.11 still default Feishu sender-name resolution to a contact-backed lookup, and live user listing still uses the contact directory. The issue remains valid, but it is security/default-sensitive and overlaps an open maintainer PR that is paused for human review.

## What This Changes

The issue asks to remove Feishu basic bot behavior's dependency on organization-wide contact directory permissions for sender-name resolution.

## Best Possible Solution

Make Feishu inbound sender attribution contact-free by default, fall back quietly to a stable sender id, and gate contact-backed profile and live user-directory lookup behind explicit operator opt-in with docs and regression tests.

## Reproduction Assessment

Yes, at source level: current main still defaults sender-name lookup on and calls Feishu contact user APIs for sender names and live peer listing. I did not run a live Feishu tenant in this read-only review.

## Solution Assessment

Yes on direction, but the exact implementation needs maintainer choice. The Feishu plugin is the right boundary, but maintainers should choose the low-scope sender metadata path and opt-in semantics before changing defaults.

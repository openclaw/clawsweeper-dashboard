## Label Justifications

- `P1`: Basic Feishu channel use can still depend on a sensitive organization contact-directory scope and user-facing permission prompts.
- `impact:security`: The issue is about avoiding default access to sensitive organization contact-directory data for ordinary sender attribution.
- `impact:auth-provider`: The behavior depends on Feishu authorization scopes and permission-grant handling for the channel integration.
- `impact:ux-friction`: Users can encounter noisy permission guidance and organization-policy friction during normal Feishu message handling.

## Summary

Keep open: current main and the latest release still use contact-backed Feishu sender-name lookup by default, and live peer listing still calls the contact directory; the active overlapping PR only partially addresses the path and is paused for human/security review.

## What This Changes

The issue asks for Feishu sender-name resolution and peer discovery to stop requiring broad organization contact-directory permission for basic bot use.

## Best Possible Solution

Make Feishu inbound sender attribution contact-free by default, fall back quietly to a stable sender id, and gate contact-backed profile and live user-directory lookup behind explicit operator opt-in with docs and regression tests.

## Reproduction Assessment

Yes. Source inspection on current main shows resolveSenderNames defaults on and still calls Feishu contact user APIs for sender names and live peer listing; I did not run a live Feishu tenant in this read-only review.

## Solution Assessment

Yes on direction, but the exact patch still needs maintainer choice. The Feishu plugin is the right owner boundary, but maintainers should choose the low-scope sender metadata path and opt-in semantics before changing defaults.

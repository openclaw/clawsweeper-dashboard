## Summary

Keep open: current main and v2026.6.11 still lack a manifest-level install-time config intent contract, and the remaining question is the security/product boundary for third-party config mutation.

## What This Changes

Request to let plugin manifests declare an install-time `configPatch` that `openclaw plugins install` would merge into the user's config automatically.

## Best Possible Solution

Define a documented manifest config-intent contract with scoped allowed paths, validation before write, operator-visible diff and skip behavior, conflict and array rules, provenance for uninstall guidance, and coverage across all plugin install routes.

## Maintainer Decision

Question: Should OpenClaw add manifest-declared install-time config intent for third-party plugins, and what allowed paths, confirmation, conflict/array behavior, provenance, and uninstall guidance must it require?

Rationale: This changes plugin install from enabling package metadata to letting package metadata mutate persisted user configuration, which crosses security, upgrade-safety, and product boundaries that automation cannot choose.

Likely owner: steipete

Owner reason: They provided the clearest current product/security framing on this issue and show recent ownership signals in the manifest/install surfaces.

Owner confidence: high

Options:

- **Define Guarded Config Intent (recommended):** Approve a narrow manifest contract that validates pending config, shows a diff with a skip path, records provenance, and classifies or blocks sensitive paths before writing.
- **Keep Manual Setup For Now:** Reject manifest-driven writes and keep plugins using docs, setup flows, provider auth, or explicit `openclaw config patch` commands until a safer contract is designed.
- **Gate Through ClawHub Trust:** Require ClawHub/package trust metadata or plugin setup approval to carry install-time config requests before core accepts them.

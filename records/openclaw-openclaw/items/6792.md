## Summary

Keep open: current main still has no manifest-level install-time config intent path, and the remaining work is a product/security boundary decision rather than conservative cleanup.

## What This Changes

The issue requests a plugin manifest field that can apply required OpenClaw config changes automatically during plugin install.

## Best Possible Solution

Define an auditable install-time plugin config-intent contract with allowlisted surfaces, validation before commit, visible diff and skip behavior, conflict and array semantics, uninstall provenance, docs, and install-route tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw support third-party manifest-declared install-time config mutation, and if so should it be an allowlisted config-intent contract rather than arbitrary raw deep-merge patches?

Rationale: The source gap is clear, but accepting plugin metadata that mutates persistent user config affects security, auth/provider routing, config data loss, and upgrade expectations; automation cannot choose that trust boundary safely.

Likely owner: vincentkoc

Owner reason: Recent live path history points most strongly to plugin manifest/install implementation ownership across the central files.

Owner confidence: high

Options:

- **Design allowlisted config intent (recommended):** Define a constrained manifest contract with allowed config surfaces, validation, diff/skip UX, provenance, and install-route tests before implementation.
- **Reject install-time mutation:** Keep plugin install limited to plugin state and require setup/auth/doctor flows or manual config patch commands for broader config changes.
- **Accept raw configPatch:** Allow arbitrary manifest deep-merge patches during install, accepting higher config and security risk for plugin setup convenience.

## Summary

Keep open: current main and the latest release still lack a manifest-level install-time config intent contract, and the remaining work is a product/security decision about how external plugin metadata may mutate persisted user config.

## What This Changes

The issue requests a plugin manifest field that lets `openclaw plugins install` apply required config changes automatically during installation.

## Best Possible Solution

Define a documented, auditable plugin install-time config intent contract with validation before commit, visible diff/skip behavior, conflict and array rules, uninstall provenance, and coverage for every install route.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What install-time config mutation contract, if any, should external plugin manifests be allowed to use?

Rationale: This decides whether untrusted plugin metadata may modify persisted user config and what guardrails prevent silent provider, tool, secret, or setup drift.

Likely owner: steipete

Owner reason: steipete posted the prior design-focused review and has strong recent history across plugin install persistence and manifest metadata.

Owner confidence: high

Options:

- **Design guarded config intent (recommended):** Allow manifest-owned config intent only with validation, visible diff, skip or confirmation behavior, conflict rules, and uninstall provenance.
- **Keep manual setup:** Reject manifest-level writes for now and improve plugin docs/setup hints so users intentionally apply config themselves.
- **Defer to config pre-apply hook:** Wait for the broader config pre-apply validation hook before adding any plugin install-time mutation surface.

## Reproduction Assessment

Not applicable as a bug reproduction, but source inspection gives a high-confidence way to verify the missing capability: manifests do not expose `configPatch`, install results cannot carry it, and install persistence cannot apply it.

## Solution Assessment

Unclear until maintainers choose the contract; a raw deep-merge `configPatch` is not the best solution without validation, visible diff, skip behavior, conflict semantics, and uninstall provenance.

## Label Justifications

- `P3`: This is a useful but non-urgent feature/API design request for plugin setup ergonomics, not a current broken core workflow.
- `impact:data-loss`: The requested behavior would write persisted config during plugin install, so conflict and array semantics must protect existing user config from accidental overwrites.
- `impact:security`: Third-party plugin metadata would be able to request config changes at install time, which is a security and trust-boundary design area.
- `impact:auth-provider`: The motivating examples include provider/search/tool routing and provider-auth-style config patches that can affect model, tool, or provider selection.

## Summary

Keep open: current main still lacks a manifest-level install-time config intent contract, and the remaining question is a product/security boundary for third-party plugin metadata mutating persisted user config.

## What This Changes

The issue requests a manifest-level `configPatch` field that lets `openclaw plugins install` apply plugin-declared config changes automatically.

## Best Possible Solution

Define a documented, auditable manifest config-intent contract with validation, operator-visible diff/skip behavior, scoped permissions, conflict and array rules, provenance, and uninstall guidance before accepting install-time config writes.

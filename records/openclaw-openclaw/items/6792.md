## Label Justifications

- `P3`: This is a useful plugin-install ergonomics and API proposal, but it needs product and security direction before implementation and is not a current runtime outage.
- `impact:data-loss`: The proposal is about automated writes to user config, where bad merge semantics could overwrite or drop existing configuration values.
- `impact:security`: A manifest-level patch field would let third-party plugin metadata request changes to sensitive OpenClaw configuration during install.
- `impact:auth-provider`: The motivating examples include provider/search/model routing config such as provider defaults, web search routing, and auth-adjacent model setup.
- `maturity:stable`: The affected `openclaw plugins install` workflow is part of the M4 Stable CLI surface in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and v2026.6.11 still do not expose a manifest-level install-time config patch or safer config-intent contract, and the direct implementation attempt closed unmerged with unresolved product and security questions.

## What This Changes

Plugin manifests should be able to declare install-time configuration changes that `openclaw plugins install` applies automatically.

## Best Possible Solution

Define a documented, auditable install-time plugin config-intent contract with scoped allowed surfaces, pre-commit validation, visible diff and skip behavior, conflict and array rules, provenance for uninstall guidance, and coverage for every install route.

## Reproduction Assessment

Not applicable as a bug reproduction, but yes for source-level proof: current main has no manifest `configPatch` field, install result carrier, or install persistence hook for manifest-declared config mutation.

## Solution Assessment

Unclear as proposed: the feature fits plugin setup ergonomics, but a raw deep-merge manifest patch is not the safest contract without explicit trust boundaries, conflict behavior, visible confirmation, and provenance.

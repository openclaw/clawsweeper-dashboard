## Summary

Keep open. Current main and v2026.6.11 still route Discord reactions into session-scoped system events, while the public plugin hook names, handler map, runner surface, and docs do not expose reaction add/remove events; cedricjanssens's production workaround and concrete payload proposal add useful design signal but do not remove the need for a maintainer API decision.

## What This Changes

The issue requests public plugin hook events for Discord reaction add/remove events so plugins can automate on user reactions.

## Best Possible Solution

Land a maintainer-approved observation-only reaction event contract, ideally generic across reaction-capable channels and emitted after existing channel authorization and reaction-notification filters, with plugin docs and focused Discord tests.

Owner confidence: medium

Options:

- **Adopt Generic Reaction Hooks (recommended):** Add observation-only reaction_added/reaction_removed hooks with a portable payload and wire Discord first without changing wake/agent-turn behavior.
- **Defer To Broader Event API:** Use https://github.com/openclaw/openclaw/issues/100447 as the API design umbrella and keep this issue as the Discord acceptance case.
- **Ship Discord-Only Hook:** Expose a narrowly scoped Discord reaction hook sooner, accepting a later compatibility pass if the generic channel event API differs.

## Reproduction Assessment

Yes at source level. Current main handles accepted Discord reactions by enqueueing system events, while the plugin hook name list, handler map, runner, and docs have no reaction add/remove hook path.

## Solution Assessment

Unclear until maintainers choose the public API shape. Generic observation-only hooks emitted after existing channel filters look safer than overloading message_received or adding a Discord-only permanent API.

## Summary

Keep open. Current main and v2026.6.11 still expose Discord reactions only as routed system events, while the public plugin hook name list, handler map, runner surface, and hook docs do not provide reaction add/remove hooks; cedricjanssens's production workaround and payload proposal are useful design evidence but do not remove the maintainer API decision.

## What This Changes

Request to expose Discord reaction add/remove events through the plugin Hooks system so plugins can implement reaction-driven automation.

## Best Possible Solution

Define a maintainer-approved observation-only reaction event contract, preferably generic across reaction-capable channels, then wire Discord after existing filters with plugin docs and focused regression tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add observation-only reaction_added/reaction_removed hooks to the public plugin API now, and should the first implementation be Discord-only or part of a broader non-message event contract?

Rationale: Source inspection proves the gap, but the permanent hook names, payload shape, enrichment model, and cross-channel scope are public plugin API choices automation should not choose alone.

Likely owner: vincentkoc

Owner reason: The request primarily changes the plugin hook contract, and git history points to vincentkoc for recent hook contract work.

Owner confidence: medium

Options:

- **Adopt Generic Reaction Hooks (recommended):** Add observation-only reaction_added/reaction_removed hooks with a portable payload and wire Discord first without changing reaction wake or agent-turn behavior.
- **Defer To Broader Event API:** Use https://github.com/openclaw/openclaw/issues/100447 as the API design umbrella and keep this issue as the Discord acceptance case.
- **Ship Discord-Only Hook:** Expose a narrowly scoped Discord reaction hook sooner, accepting a later compatibility pass if the generic channel event API differs.

## Reproduction Assessment

Yes at source level. Current main handles accepted Discord reactions by enqueueing system events, while the plugin hook name list, handler map, runner, registration type, and docs have no reaction add/remove hook path.

## Solution Assessment

Unclear until maintainers choose the public API shape. Generic observation-only hooks emitted after existing channel filters look safer than overloading message_received or adding a permanent Discord-only API.

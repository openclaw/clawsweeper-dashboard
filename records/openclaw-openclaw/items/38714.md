## Summary

Keep open. Current main and the latest release still route Discord reactions into session-scoped system events, while the public plugin hook contract has no reaction add/remove hook names, handler entries, runner methods, or docs; the open wake-policy PR is adjacent and does not replace plugin hook delivery.

## What This Changes

The issue requests Discord reaction add/remove events be exposed through the plugin Hooks system so plugins can automate reaction-driven workflows.

## Best Possible Solution

Define a maintainer-approved observation-only reaction hook contract, then wire Discord through the existing authorized reaction notification path while keeping agent-turn wakeups in the separate wake-policy track.

## Reproduction Assessment

Yes, at source level. Current main handles Discord reactions and queues system events, but the public hook registry, handler map, runner, docs, and latest release have no reaction add/remove hook path.

## Solution Assessment

Unclear until maintainers approve the public contract. Dedicated observation-only hooks look cleaner than overloading `message_received`, but names, payload shape, enrichment, and cross-channel scope need product/API direction.

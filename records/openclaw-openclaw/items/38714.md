## Summary

Keep open. Current main and v2026.6.11 still turn accepted Discord reactions into routed system events, but they do not expose reaction add/remove events through the public plugin hook contract; the open wake-policy PR and cross-channel wake issue are adjacent, not replacements.

## What This Changes

The issue requests public plugin hook support for Discord reaction add/remove events so plugins can run automation from reaction input.

## Best Possible Solution

Approve a generic observation-only reaction hook contract, then wire Discord through the existing authorized reaction notification path while keeping reaction-triggered agent wakeups in the separate wake-policy track.

Options:

- **Approve Generic Observation Hooks (recommended):** Add reaction_added and reaction_removed as observation-only public hooks with a shared payload shape, wire Discord first with tests and docs, and leave room for channel parity.
- **Scope Discord First:** Accept a Discord-specific first step now, with explicit follow-up criteria so payload and names do not become permanent cross-channel drift.
- **Defer The API:** Keep reaction automation on system events and external workarounds until maintainers sponsor a broader non-message plugin event design.

## Reproduction Assessment

Yes, at source level. Current main handles Discord reactions and queues system events, but the hook name list, handler map, runner surface, docs, and latest release have no reaction add/remove hook path.

## Solution Assessment

Unclear until maintainers approve the public API shape. Dedicated observation-only reaction hooks look more maintainable than overloading message_received, but the names, payload, enrichment, and cross-channel scope need product/API direction.

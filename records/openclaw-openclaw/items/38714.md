## Summary

Keep open: current main and v2026.6.11 still expose Discord reactions as routed system events, not as plugin Hook events, and the remaining work is a compatibility-sensitive plugin API/product decision rather than cleanup-safe implementation work.

## What This Changes

Request to expose Discord reaction add/remove events through the plugin Hooks system so plugins can automate on reactions instead of only seeing queued system events.

## Best Possible Solution

Choose one public contract for observation-only reaction events, then wire Discord reactions through that contract with structured payloads, docs, and focused hook/security tests while preserving the existing system-event path.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add dedicated observation-only reaction Hooks for Discord now, fold this into a broader non-message event API, or document the existing system-event path as the supported plugin automation surface?

Rationale: The source gap is clear, but the permanent API shape affects third-party plugin compatibility and overlaps with broader inbound event and wake-policy work.

Likely owner: steipete

Owner reason: The decision spans Discord reaction handling, plugin SDK boundaries, and product direction, and steipete is the strongest recent history match across those surfaces.

Owner confidence: high

Options:

- **Add generic reaction hooks (recommended):** Define `reaction_added` and `reaction_removed` as observation-only plugin Hooks with a structured cross-channel payload, then wire Discord first with docs and tests.
- **Fold into non-message events:** Make this request part of the broader public non-message inbound event contract so reactions, edits, typing, and read receipts share one SDK surface.
- **Document system events only:** Declare routed system events as the supported plugin path for reactions and close hook-specific requests if maintainers do not want a new Hook API.

## Reproduction Assessment

Yes, at source level. Current hook types and handler maps have no reaction hook names, while the Discord reaction listener only enqueues routed system events.

## Solution Assessment

Unclear until maintainers choose the public API direction. Dedicated observation hooks are a plausible narrow fix, but the names, payload, and cross-channel scope should be settled before implementation.

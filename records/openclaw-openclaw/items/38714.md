## Label Justifications

- `P2`: This is a normal-priority feature gap for reaction-driven Discord/plugin automation with limited blast radius and no first-run blocker.
- `impact:message-loss`: Discord reaction events are detected as system events but are not delivered to plugin hook consumers that need to observe them.
- `maturity:stable`: The affected Discord channel surface is M4 Stable in docs/maturity/scorecard.md, even though plugin and automation hook surfaces are M3.

## Summary

Keep open. Current main still routes Discord reactions into session-scoped system events, but the public plugin hook names, handler map, runner surface, and docs do not expose reaction add/remove events; the detailed production workaround and payload proposal in the discussion are useful design evidence, but this remains a maintainer API decision rather than cleanup.

## What This Changes

The issue requests Discord reaction add/remove events in the plugin Hooks system so plugins can automate based on user reactions.

## Best Possible Solution

Add a maintainer-approved, documented observation-only reaction hook contract in the plugin SDK, then wire Discord reactions through it without changing the existing session system-event behavior unless a separate wake-policy item lands.

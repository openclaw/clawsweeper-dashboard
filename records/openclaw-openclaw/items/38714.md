## Summary

Keep open. Current main and v2026.6.11 still turn accepted Discord reactions into passive system events, but they do not expose `reaction_added`/`reaction_removed` or any equivalent plugin hook; the remaining work is a compatibility-sensitive plugin API/product decision rather than stale cleanup.

## What This Changes

Request to expose Discord reaction add/remove events through the OpenClaw Hooks/plugin hook system so plugins can automate on user reactions.

## Best Possible Solution

Define one observation-only reaction event contract for plugin authors, wire Discord through the existing authorized reaction notification path, and document/test the payload and cross-channel extension plan before implementation.

Options:

- **Approve Generic Reaction Hooks (recommended):** Add `reaction_added` and `reaction_removed` as observation-only plugin hooks, start with Discord behind existing reaction notification gates, and document the cross-channel payload contract.
- **Route Through Broader Inbound Events:** Defer this specific hook until the broader inbound non-message event API in https://github.com/openclaw/openclaw/issues/100447 or related PR work defines the canonical contract.
- **Keep System Events Only:** Leave reactions as passive system events for now and close or defer plugin-specific reaction automation until a stronger maintainer-sponsored use case appears.

## Reproduction Assessment

Yes, at source level. Current main has Discord reaction listeners that enqueue system events, while the typed plugin hook list and handler map have no reaction add/remove hook and `message_received` is emitted from the normal inbound dispatch path.

## Solution Assessment

Unclear until maintainers choose the API contract. A generic observation-only reaction hook looks cleaner than synthetic `message_received` events, but it should be aligned with broader inbound event and reaction wake work before implementation.

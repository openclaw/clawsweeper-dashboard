## Review Findings

Overall confidence: 0.9

Full review comments:

- **[P1] Port Mermaid handling to the markdown-it renderer:** `ui/src/ui/markdown.ts:263-264`
  - body: Current main renders code fences through `md.renderer.rules.fence`/`renderCodeBlock`, but this PR adds the Mermaid branch to the old `marked.Renderer` path. GitHub reports the PR as conflicting, and after rebase this code will either not apply or will bypass the current code-block contracts, so the feature needs to be ported before merge.
  - confidence: 0.96
- **[P2] Scope Mermaid blocks to views that actually render them:** `ui/src/ui/markdown.ts:263-264`
  - body: `toSanitizedMarkdownHtml()` is shared by non-chat views such as the markdown sidebar, but only the chat lifecycle calls `scheduleMermaidRender()`. Converting every Mermaid fence here would leave those consumers with blank render slots and hidden source unless the renderer is opt-in for chat or scheduled for every consumer that can produce Mermaid blocks.
  - confidence: 0.9
- **[P2] Call Mermaid bindFunctions after SVG insertion:** `ui/src/ui/mermaid.ts:186-187`
  - body: Mermaid 11.13.0's `RenderResult` includes optional `bindFunctions` for interactions after the SVG is inserted, but this wrapper erases that field and only injects `svg`. Diagrams that rely on Mermaid click handlers or tooltips would render as static SVG with interactions silently lost.
  - confidence: 0.87
- **[P2] Let failed Mermaid blocks retry after transient failures:** `ui/src/ui/mermaid.ts:150`
  - body: The loader resets `mermaidApiPromise` after an import failure, but each affected block is stamped `data-mermaid-status="error"` while future passes only query blocks without that attribute. A temporary chunk or network failure therefore stays broken until the DOM is rebuilt instead of retrying on the next scheduled render.
  - confidence: 0.86

## What This Changes

The branch changes the Control UI mobile pairing overlay so setup-code publication no longer waits for pending-device list refresh, and adds an E2E regression that defers `device.pair.list`.

## Best Possible Solution

Land this narrow overlay publish-order fix after maintainer review and green required checks, keeping QR rendering independent from pending-device refresh.

## Reproduction Assessment

Yes from source inspection, though I did not run the browser E2E in this read-only pass. Current main can keep the dialog on the generating state when `device.pair.setupCode` resolves but `device.pair.list` remains pending because the final publish waits for both operations.

## Solution Assessment

Yes. The overlay owns both setup-code publication and pending-count refresh, so awaiting only the setup operation while letting the guarded list refresh publish separately is narrower than changing gateway methods or rendering rules.

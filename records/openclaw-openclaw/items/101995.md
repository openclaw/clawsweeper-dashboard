## Summary

Keep open: current main and the latest release still have the Teams long-thread reply pagination bug, but this PR head remains incorrect because it still feeds absolute `@odata.nextLink` values back through the relative Graph helper and lacks matching real behavior proof.

## What This Changes

The PR changes `fetchThreadReplies` from one `$top` request to a custom loop that accumulates Teams Graph reply pages and returns the last requested slice.

## Best Possible Solution

Route reply pagination through `fetchGraphAbsoluteUrl` or `fetchAllGraphPages` with a typed paged response, a hard page cap, focused tests, and redacted live Teams/Graph proof or an explicit proof override.

- **[P1] Route nextLink through the absolute Graph helper:** `extensions/msteams/src/graph-thread.ts:139-143`
  - body: The loop assigns `path = res["@odata.nextLink"]` and then calls `fetchGraphJson` on the next iteration. Microsoft Graph returns a full nextLink URL, while `fetchGraphJson` prepends `GRAPH_ROOT`, so page 2 can request a malformed URL and drop reply context; use `fetchGraphAbsoluteUrl` or the shared pagination helper with a paged response type.
  - confidence: 0.98
- **[P2] Cap pagination by page count:** `extensions/msteams/src/graph-thread.ts:138`
  - body: The loop stops on `allReplies.length < 500`, not on request count. Microsoft Graph pages can contain zero or few items while still returning another nextLink, so this can issue far more sequential Graph calls than intended from the inbound Teams path; add a hard page counter before following another nextLink.
  - confidence: 0.9

## Summary

Keep open: current main and the latest release still do not extract Office-style Telegram document contents, and the remaining work is not owned by a merged PR or a narrower canonical issue. Text/PDF handling has improved, but the Office/document-container path needs maintainer decisions around parser scope, resource limits, and plugin boundaries before implementation.

## What This Changes

The issue requests extracting readable text from Telegram document attachments such as PDFs, text files, and Office documents so the agent sees contents instead of only a media placeholder.

## Best Possible Solution

Extend the shared document extraction path, not Telegram-only code, with maintainer-approved Office MIME scope, parser/dependency ownership, archive/XML limits, untrusted-content wrapping, and Telegram plus input_file coverage.

Owner confidence: high

Options:

- **Approve narrow shared extraction (recommended):** Add DOCX-first support through the document-extractor/media-understanding path with explicit MIME allowlists, archive/XML limits, tests, docs, and live Telegram proof.
- **Extend external plugin seam first:** Keep bundled behavior unchanged until external document-extractor plugins can safely own Office formats through ClawHub without core changes.
- **Defer Office extraction:** Keep text/PDF behavior only and document Office files as unsupported until a broader file/document input direction is settled.

## Reproduction Assessment

Yes, at source level: Telegram documents flow into shared media context with MIME metadata, but Office MIME types are classified as binary and skipped before extraction. I did not run live Telegram proof in this read-only cleanup pass.

## Solution Assessment

The requested outcome is valid, but a Telegram-only parser or a new channel config toggle would be the wrong layer. The maintainable solution is a shared document-extractor/media-understanding change, or first extending the plugin seam if maintainers want Office support outside bundled core.

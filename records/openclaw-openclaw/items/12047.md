## Summary

Keep open: current main and v2026.6.11 still download and forward Telegram document attachments, and text/PDF extraction exists, but Office-style document contents remain deliberately skipped before extraction. The remaining work needs maintainer product and security boundary decisions before implementation.

## What This Changes

The issue requests extracting text from Telegram document attachments such as DOCX, PDF, TXT, and Markdown so the agent receives document contents instead of only a media placeholder.

## Best Possible Solution

Implement a maintainer-approved Office document subset through the shared document-extract, media-understanding, and input_file paths with bounded resource limits, untrusted-content wrapping, Telegram coverage, and user-facing docs.

- **Keep Office External For Now:** Leave core at text/PDF extraction and document a ClawHub or MCP plugin path until maintainers approve an in-process Office parser boundary.
- **Defer To Provider-Native Design:** Fold the remaining work into the broader provider-native file/document forwarding design instead of adding local Office extraction first.

## Reproduction Assessment

Yes, at source level: saved Telegram document paths and MIME types flow into shared media context, but Office MIME types are classified as binary and skipped before extraction. I did not run a live Telegram bot reproduction in this read-only cleanup pass.

## Solution Assessment

The requested outcome is valid, but a Telegram-only parser or new default config toggle would be the wrong layer. The maintainable solution is shared document extraction after maintainers settle parser, dependency, limit, and security boundaries.

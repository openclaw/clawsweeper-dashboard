## Label Justifications

- `P2`: The issue affects common Telegram document workflows but is a bounded feature gap requiring product and security review rather than emergency repair.
- `impact:message-loss`: Telegram can receive and store unsupported document attachments while their readable contents are omitted from agent-visible message context.

## Summary

Keep open: current main and v2026.6.11 handle Telegram document download plus text/PDF extraction, but Office-style document contents are still intentionally skipped before extraction and the only DOCX implementation PR was closed unmerged after proof and security blockers.

## What This Changes

Request to extract readable text from Telegram document attachments so agents can process documents instead of receiving only media placeholders.

## Best Possible Solution

Implement maintainer-approved Office document support through the shared document-extractor, media-understanding, and input_file paths with bounded MIME scope, resource limits, untrusted-content wrapping, Telegram coverage, and docs.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What Office-document extraction boundary should OpenClaw support for Telegram and shared attachment context?

Rationale: The remaining gap is source-proven, but parsing untrusted Office containers changes dependency, MIME, resource-limit, and prompt-injection boundaries that automation should not choose alone.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Bound Shared Extractor Support (recommended):** Add a maintainer-approved DOCX/XLSX/PPTX subset through the shared document-extractor/media-understanding path with explicit archive/XML limits and security tests.
- **Keep Office External For Now:** Leave core at text/PDF extraction and document a ClawHub, MCP, or plugin path until maintainers approve an in-process Office parser boundary.
- **Defer To Provider-Native Design:** Fold the remaining work into the broader provider-native document/file forwarding design instead of adding local Office extraction first.

## Reproduction Assessment

Yes, at source level: saved Telegram document paths and MIME types flow into shared media context, but Office MIME types are classified as binary and skipped before extraction. I did not run a live Telegram bot reproduction in this read-only cleanup pass.

## Solution Assessment

Unclear as an implementation until maintainers choose the parser, dependency, limits, and security boundary. A Telegram-only parser or new default config toggle would be the wrong layer; the maintainable direction is shared document extraction with explicit security limits.

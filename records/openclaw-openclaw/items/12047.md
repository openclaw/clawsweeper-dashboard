## What This Changes

The issue requests agent-visible text extraction for document attachments sent through the Telegram channel.

## Best Possible Solution

Extend the shared document extraction path, not Telegram-only code, with maintainer-approved Office MIME scope, parser/dependency ownership, archive/XML limits, untrusted-content wrapping, and Telegram plus input_file coverage.

Options:

- **Approve narrow shared extraction (recommended):** Add maintainer-approved DOCX-first support through the document-extractor/media-understanding path with explicit MIME allowlists, archive/XML limits, tests, docs, and live Telegram proof.
- **Extend external plugin seam first:** Keep core behavior unchanged until external document-extractor plugins can safely own Office formats through ClawHub without bundled core changes.
- **Defer Office extraction:** Keep text/PDF behavior only and document Office files as unsupported until a broader file/document input direction is settled.

## Reproduction Assessment

Yes, at source level: Telegram documents flow into shared media context with MIME metadata, but Office MIME types are classified as binary and skipped before extraction. I did not establish a live Telegram reproduction in this read-only cleanup pass.

## Solution Assessment

The requested outcome is valid, but a Telegram-only parser or a new channel config toggle would be the wrong layer. The maintainable solution is a shared document-extractor/media-understanding change, or first extending the plugin seam if maintainers want Office support outside bundled core.

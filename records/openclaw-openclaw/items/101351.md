## Label Justifications

- `P1`: The report describes a deterministic Control UI authentication failure that blocks access for users running multiple same-origin path-routed gateways.
- `impact:security`: The issue concerns scoping and migration of bearer device credentials stored in the browser.
- `impact:auth-provider`: The failure is in the gateway authentication path where a cached device token for one gateway is sent to another gateway.
- `impact:session-state`: Browser-held Control UI auth state can drift between gateway endpoints and reconnect with the wrong credential.
- `maturity:stable`: The issue maps to the M4 Stable gateway-runtime feature, specifically Device Auth and Pairing plus WebSocket Connection behavior.

## Summary

Keep open: current main and v2026.6.11 still use one unscoped browser device-auth record, and the open linked PR is the right candidate to review rather than closing this issue early.

## What This Changes

This issue reports that Control UI gateway-issued device tokens are stored under one origin-wide browser key, causing same-origin path-routed gateways to overwrite each other's fresh-tab credentials.

## Best Possible Solution

Review and land or reject the linked PR that scopes device-auth records by normalized gateway endpoint while keeping device identity shared and shared gateway tokens ephemeral.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes at source level: current main and v2026.6.11 both read and write one unscoped `openclaw.device.auth.v1` browser record, while connect auth selects cached tokens without a gateway URL scope. I did not run the browser repro in this read-only review.

## Solution Assessment

Yes, the linked PR direction appears to be the right owner-boundary fix: scope the existing device-auth cache by normalized gateway endpoint and migrate the legacy unscoped key. The issue should stay open until that PR is reviewed and merged or replaced.

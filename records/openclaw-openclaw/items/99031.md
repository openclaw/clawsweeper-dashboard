## Summary

Keep open: current main still has the reported source-level failure path and still presents discovered gateways as connectable before the no-TLS/no-pin guard returns the unrecoverable error. This is not implemented on main; the remaining work needs maintainer security/product direction rather than an automatic close.

## What This Changes

The issue asks OpenClaw to define a safe, actionable first-use behavior when iOS discovers a Gateway that has no TLS advertisement and no stored fingerprint.

## Best Possible Solution

Keep the discovery trust boundary explicit, then make the iOS discovered-gateway UI either unavailable with setup guidance or route into a maintainer-approved TLS/fingerprint trust flow.

## Reproduction Assessment

Yes. Source inspection on current main shows a no-TLS discovered gateway with no stored pin reaches the exact guard that returns the reported error, while quick setup and settings still expose Connect actions for that gateway.

## Solution Assessment

Unclear until maintainers pick the security/UX policy. The safest direction is to preserve TLS-only discovery by default and fix the iOS presentation/setup path rather than silently permitting unauthenticated plaintext discovery.

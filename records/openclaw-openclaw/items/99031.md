## Summary

Keep open: current main still exposes discovered iOS Gateways as connectable in some surfaces even when the controller will immediately return the reported missing-TLS/no-pin error. The underlying TLS-only discovery policy is documented, so the remaining work is to align the iOS UX and trust/setup path with that policy rather than close this as implemented.

## What This Changes

The issue requests supported first-connection behavior for iOS Bonjour-discovered Gateways that do not advertise TLS and have no stored trusted fingerprint.

## Best Possible Solution

Keep discovery TLS-only by default, then make every iOS discovered-gateway surface either show an actionable TLS/trust setup path or mark non-TLS/no-pin gateways unavailable; only add plaintext discovery behavior if maintainers explicitly approve that security policy.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: a discovered gateway with `tlsEnabled == false` and no stored fingerprint reaches the guard in `connectDiscoveredGateway`, while multiple UI surfaces still offer a Connect action before that guard returns the reported error; I did not run a live iOS device repro.

## Solution Assessment

Unclear until maintainers pick the UX policy. The safest maintainable direction appears to preserve the documented TLS-only discovery rule and fix the iOS UI/setup guidance rather than silently allowing plaintext discovered connections.

## Summary

Keep open: current main still has the exact discovered-gateway no-TLS/no-pin preconnect failure, and the follow-up live testing narrows the remaining problem toward Tailscale Serve reachability diagnostics rather than proving the iOS UX is fixed.

## What This Changes

Improve iOS discovered Gateway first-use behavior so no-TLS/no stored-fingerprint cards either use an approved secure trust flow or show actionable Tailscale/TLS guidance instead of an unrecoverable error.

## Best Possible Solution

Keep discovery TLS-only by default, then make the iOS discovered-gateway surfaces either block/mark non-TLS no-pin gateways as unavailable or route users to a clear Tailscale Serve/TLS trust setup diagnostic.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: a discovered gateway with `tlsEnabled == false` and no stored fingerprint reaches the exact guard that returns the reported error, while current UI surfaces still offer Connect. I did not run a live iOS device reproduction.

## Solution Assessment

Unclear until maintainers choose the security/UX policy. The safer direction is to preserve the documented TLS-only discovery rule and fix the iOS presentation/diagnostic path rather than silently allowing plaintext discovered connections.

## Label Justifications

- `P1`: A normal Gateway reconnect can leave a core New Session workflow using device, repository, folder, and base-ref state from the previous connection.
- `impact:session-state`: Gateway-owned New Session draft and discovery state can drift from the active connection and be submitted to the wrong runtime context.

## Summary

Keep this issue open: it documents a fresh, concrete reconnect regression in a maintainer-protected Control UI surface, and no merged fix or current-main replacement is identified. The reported lifecycle trace and real-Gateway RPC counts support a focused fix, but the exact source history could not be fully verified in this review environment.

## What This Changes

Make the Control UI New Session page invalidate and reload Gateway-owned node, branch, base-ref, and folder-browser discovery whenever the Gateway client is replaced, while retaining user-authored message text.

## Best Possible Solution

Treat Gateway client identity as an explicit New Session lifecycle boundary: cancel or epoch-guard outstanding discovery, clear Gateway-owned selections and browser state, reload discovery through the new client, preserve only user-authored message text, and add focused reconnect tests plus real-Gateway Playwright proof.

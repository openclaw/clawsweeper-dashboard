## Summary

Keep open: current main and v2026.6.11 still resolve `$VAR` and `${VAR}` path placeholders literally before ClawHub skill install targets are built, and the only open linked fix is an unmerged fork PR that needs maintainer review rather than a cleanup close.

## What This Changes

The issue reports that a ClawHub skill install in Docker treats `${XDG_CONFIG_HOME}` as a literal path segment instead of expanding the environment variable.

## Best Possible Solution

Land, adopt, or explicitly reject a shared resolver/path policy that expands approved `$VAR` and `${VAR}` placeholders without unsafe missing-variable fallback, with focused tests for skill install paths and compatibility semantics.

## Reproduction Assessment

Yes, by source inspection: current `resolveHomeRelativePath` does not expand `$VAR` or `${VAR}`, and the skill install target preserves a literal workspace path. I did not run the Docker/ClawHub install flow in this read-only review.

## Solution Assessment

Unclear. Expanding shared user-path placeholders is likely the right layer if maintainers want config/env interpolation, but the final fix must choose safe unknown-variable and broader dotenv/config semantics rather than copying the unsafe empty-string fallback from a closed PR.

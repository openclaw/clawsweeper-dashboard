## Summary

Keep open: the underlying eviction-order bug is valid, but this patch changes an attacker-reachable hard-cap path from constant-time work to a 10,000-entry scan and provides no representative full-cap latency proof.

## What This Changes

Changes gateway control-plane rate-limit eviction from deleting the first map entry to scanning for the bucket with the smallest `windowStartMs`.

## Best Possible Solution

Keep eviction constant-time by moving an expired existing bucket to the end when its window resets, preserving map order by current window age, then retain first-entry eviction and add ordering regression coverage plus full-cap churn latency proof.

## Reproduction Assessment

Yes, from source: populate 10,000 buckets, reset the earliest-inserted key into a newer window, then insert another identity and observe current main evict the recently reset key. The branch has not demonstrated this path or its latency in a representative runtime harness.

## Solution Assessment

No. Selecting by `windowStartMs` is correct, but repeatedly scanning the entire capped map is not the safest fix for an attacker-controlled hot path; maintaining eviction order during window reset preserves correctness and constant-time eviction.

## Summary

The underlying insertion-order bug is credible, but this implementation turns every new identity after saturation into a full 10,000-bucket scan, creating attacker-controlled CPU amplification in a gateway security boundary; the unchanged prior blocker and missing saturated runtime proof still prevent merge.

## What This Changes

Changes gateway control-plane rate-limit bucket eviction to scan for the bucket with the smallest `windowStartMs` instead of deleting the first map entry.

## Best Possible Solution

Preserve oldest-window eviction while keeping the saturated path constant-time—for example, move a bucket to the end when its window resets so map order tracks window age—then add a churn regression and redacted runtime proof.

## Solution Assessment

No. Selecting by `windowStartMs` fixes the ordering mistake, but a linear scan in an attacker-influenced saturated path is not the safest implementation; maintaining age order during window rollover avoids the competing availability regression.

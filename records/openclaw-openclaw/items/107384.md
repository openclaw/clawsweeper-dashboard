## Summary

The same-head P1 blocker remains: the diagnosis is sound, but the proposed repair makes every new identity at a saturated map scan all 10,000 buckets, increasing denial-of-service leverage inside the gateway rate limiter. The PR also still provides only focused test and lint output rather than after-fix saturated-path proof.

## What This Changes

Changes gateway control-plane rate-limit eviction from deleting the first inserted bucket to scanning for the bucket with the smallest `windowStartMs`.

## Best Possible Solution

When an existing bucket starts a new window, delete and reinsert it so map order tracks `windowStartMs`; retain first-entry cap eviction, add a reset-order regression test, and demonstrate bounded latency under repeated saturated identity churn.

Yes at source level: saturate the map and submit repeated unseen device/IP keys; every request enters the new full-map scan. The original unfair-eviction case is also source-reproducible by resetting an early-inserted bucket without moving its map position.

## Solution Assessment

No. Choosing the oldest window is correct, but a full scan in an attacker-influenced capped path is not the narrowest safe fix; maintaining age order during window resets preserves correct O(1) eviction.

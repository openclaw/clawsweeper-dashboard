## Label Justifications

- `P2`: The original fairness bug is real but limited to an extreme high-cardinality gateway, while the proposed implementation still needs a bounded repair.
- `merge-risk: 🚨 security-boundary`: The patch changes a limiter path explicitly designed to resist rapid unique-key resource exhaustion and introduces attacker-amplifiable CPU work.
- `merge-risk: 🚨 availability`: Repeated synchronous scans of 10,000 entries can stall gateway request processing after the bucket map reaches capacity.

## Summary

Keep open: the underlying eviction bug is valid, but this implementation is not merge-ready because it replaces constant-time cap eviction with a repeatable full-map scan, and the external PR lacks after-fix real behavior proof.

## What This Changes

Changes control-plane rate-limit eviction to scan all buckets and delete the entry with the smallest `windowStartMs` instead of deleting the first inserted entry.

## Best Possible Solution

Refresh insertion order when an existing bucket starts a new window—delete it before reinserting—then retain constant-time first-key eviction and add regression plus repeated full-cap timing coverage.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, source inspection gives a deterministic reproduction: reset an early-inserted bucket's window without repositioning it, age a later bucket, fill the map, then insert a new identity and observe insertion-order eviction select the recently reset bucket.

## Solution Assessment

No. Selecting the minimum timestamp is semantically correct, but scanning the full capped map on each subsequent unique identity is not the safest implementation; maintaining chronological insertion order preserves the intended eviction with bounded work.

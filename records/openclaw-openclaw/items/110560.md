## Label Justifications

- `P1`: The patch can break existing ACP-backed agent spawning by removing still-valid authorization targets from persisted allowlists.
- `merge-risk: 🚨 compatibility`: The new persisted-config cleanup changes existing `allowAgents` behavior and can silently deny a previously valid ACP target after upgrade.

## Summary

Keep this PR open: it usefully makes Gateway cleanup failures observable, but the current patch still hides those outcomes in offline `--json` deletes and can revoke valid ACP targets when it prunes `allowAgents`. The `maintainer` label also requires explicit maintainer handling rather than automatic cleanup.

## What This Changes

The PR adds Gateway/CLI reporting for agent-delete Trash cleanup results and prunes deleted local agent IDs from default and per-agent subagent allowlists.

## Best Possible Solution

Use one cleanup-outcome contract for both Gateway and offline deletion, and prune `allowAgents` only for identifiers that are no longer valid local or configured ACP targets.

Yes, from source: delete a local agent whose ID is also configured as an ACP target, then attempt an ACP spawn through a pruned `allowAgents` list; the new predicate removes that still-valid target. The offline JSON gap is likewise directly traceable through the Gateway-only result forwarding.

## Solution Assessment

No. Honest cleanup reporting is the right direction, but the implementation must cover the offline fallback and preserve configured ACP targets rather than treating every matching identifier as stale.

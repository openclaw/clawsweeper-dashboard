## Summary

Keep open: the rewritten PR still applies the cap only after `res.text()` has already materialized the fallback body, so it does not fix the stated unbounded-allocation problem. The prior core blocker remains on the new shared-helper path, and the proof only shows post-allocation return-value truncation.

## What This Changes

The PR adds post-read truncation to the `readResponseText()` `.text()` fallback and a regression test for a text-only Response-like object.

## Best Possible Solution

Make `readResponseText()` enforce `maxBytes` before any fallback allocation, or fail closed for fallback shapes that cannot be byte-bounded, with byte-measured regression coverage.

## Reproduction Assessment

Yes: source inspection gives a high-confidence path where a Response-like object with no readable body and no working `arrayBuffer()` reaches `await res.text()` before any `maxBytes` cap can apply. I did not run tests because this was a read-only review.

## Solution Assessment

No: this is not the best fix because it slices the returned string after `res.text()` resolves, so it does not bound the memory allocation the PR claims to fix. A safer fix must avoid the unbounded fallback read or fail closed when a byte-bounded source is unavailable.

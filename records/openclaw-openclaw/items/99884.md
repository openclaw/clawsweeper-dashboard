## Summary

Keep open: the latest live head reintroduced the prior blocker by awaiting `res.text()` before enforcing `maxBytes`, so a capped text-only Response-like object can still allocate the full payload before truncation. The PR body proof is also stale because it describes the older fail-closed behavior, not the current head.

## What This Changes

The PR changes `readResponseText()` so the `.text()` fallback encodes text to bytes and truncates after reading when `maxBytes` is exceeded, with a multibyte fallback test.

## Best Possible Solution

Restore the capped text-only fallback so it does not call `.text()` before enforcement, or have maintainers explicitly accept post-read truncation and update the proof/body to match that policy.

## Reproduction Assessment

Yes. Source inspection at the current PR head shows a Response-like object with no stream or arrayBuffer reaches `await res.text()` before the `maxBytes` check, reproducing the full-allocation path by construction.

## Solution Assessment

No. Byte-accurate truncation is useful after the full read, but the best fix must enforce the cap before reading or fail closed when no bounded byte source exists.

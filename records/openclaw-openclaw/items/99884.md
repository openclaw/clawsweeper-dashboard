## Summary

Keep open: this is a focused hardening PR, but the no-Content-Length path still awaits `response.text()` before applying the cap, so the advertised MCP HTTP OOM protection remains incomplete.

## What This Changes

The PR adds a 16 MiB Content-Length precheck and post-read text truncation for bodyless foreign MCP HTTP responses, plus a regression test for small, oversized, and declared oversized responses.

## Best Possible Solution

Land a true byte-bounded MCP response fallback: stream and cancel when a body exists, and for bodyless text-only foreign responses call `.text()` only after a strict under-cap Content-Length or deliberately fail closed with focused tests and proof for undeclared, malformed, underdeclared, and multibyte bodies.

## Reproduction Assessment

Yes from source inspection: the added no-Content-Length scenario reaches `await response.text()` before the cap is checked, so the full foreign text body is already allocated. I did not run tests because this was a read-only review.

## Solution Assessment

No: the Content-Length precheck helps declared oversized bodies, but post-read truncation is not a memory bound and the cap is measured as string length rather than bytes. The safer fix is to avoid calling `.text()` unless a trustworthy byte bound is known, or fail closed for bodyless text-only responses that cannot be bounded.

## Review Findings

Full review comments:

- **[P1] Bound the body before calling text():** `src/agents/mcp-http-fetch.ts:86`
  - body: The no-Content-Length path still calls `await response.text()` before the 16 MiB check runs. Undici's body consumer fully reads before resolving, so a hostile text-only foreign response can still allocate the oversized body and OOM before this truncation happens; the added test only proves the returned text was shortened after that allocation. The fix needs to avoid `.text()` unless a strict under-cap byte length is trusted, or fail closed for bodyless responses that cannot be streamed safely.
  - confidence: 0.93
- **[P2] Measure the cap in bytes:** `src/agents/mcp-http-fetch.ts:87-92`
  - body: The new limit is named and messaged as bytes, but `text.length` and `slice()` count UTF-16 code units. A non-ASCII body can pass the `<= 16 MiB` check while producing a UTF-8 `Response` body larger than 16 MiB, so any retained text fallback should enforce the cap with byte length and byte-safe truncation.
  - confidence: 0.86

## Summary

Keep this PR open for revision: the current head still checks `maxBytes` only after `res.text()` has materialized the full fallback body, and the new fallback also treats a byte limit as UTF-16 code units. The PR body proof shows the returned string is sliced, but it does not prove the memory-bounding behavior the change claims to fix.

## What This Changes

The branch adds post-read truncation and a text-only fallback regression test for `readResponseText()` when `maxBytes` is set.

## Best Possible Solution

Make `readResponseText()` enforce `maxBytes` before any fallback allocation, or fail closed when only `text()` is available, with byte-based regression coverage.

## Reproduction Assessment

Yes: source inspection shows a Response-like object with no readable `body` and no usable `arrayBuffer()` reaches `await res.text()` before any `maxBytes` cap can apply. I did not run tests because this review is read-only.

## Solution Assessment

No: this is not the best fix because it slices the returned string after the unbounded `text()` read. A safer fix should use a byte-bounded source or fail closed when a byte-bounded source is unavailable.

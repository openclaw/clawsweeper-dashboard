## Summary

Keep open: current main and the latest release still have the text-only fallback, but this PR is not land-ready because it only truncates after `response.text()` has already materialized the full string. The prior P1 availability blocker remains unresolved, so maintainer fallback-policy review is still needed.

## What This Changes

The PR encodes text-only fallback output as UTF-8, truncates returned text to `maxBytes`, reports byte length, and adds a multibyte regression test.

## Best Possible Solution

Use a maintainer-approved bounded-source policy for capped text-only fallbacks, preferably skipping `text()` when no bounded byte source exists and covering that behavior with a regression test.

## Reproduction Assessment

Yes. Source inspection of the PR head shows a text-only Response-like object with `maxBytes` reaches `await res.text()` before any byte cap is enforced; the PR body also includes terminal proof for the returned-byte behavior.

## Solution Assessment

No. Post-read UTF-8 truncation fixes returned length accounting, but the best bounded-read fix must avoid calling `text()` when the caller requested a byte cap and no bounded byte source is available, or explicitly document that narrower policy.

## Summary

Keep open: the focused bugfix idea is valid, but the current head is still not merge-ready because the fallback still awaits an unbounded `text()` read before applying the cap and still measures a byte budget with string length.

## What This Changes

The branch adds a post-read `maxBytes` check to `readResponseText()`'s `.text()` fallback and adds a text-only Response-like regression test.

## Best Possible Solution

Make capped reads rely on byte-counted stream or byte-buffer sources only; for text-only fallbacks under `maxBytes`, fail closed or use an explicitly approved compatibility policy, with UTF-8 byte regression coverage.

## Reproduction Assessment

Yes, source-reproducible. The PR head visibly awaits `res.text()` before checking `maxBytes`, and the current test/proof uses ASCII so it misses both full-allocation and UTF-8 byte-limit failures.

## Solution Assessment

No. The proposed fix is a plausible post-read truncation, but the best fix must avoid unbounded reads when a byte cap is requested and must measure any remaining fallback in UTF-8 bytes.

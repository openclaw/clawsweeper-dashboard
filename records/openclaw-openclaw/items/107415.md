## Label Justifications

- `P1`: False recovery aborts can terminate active cron and interactive runs, dropping user-visible results during real gateway pressure.
- `impact:message-loss`: The reported aborts produced failed cron deliveries and a silently dropped interactive user turn.
- `impact:session-state`: The defect misclassifies healthy active session state and mutates it through diagnostic recovery.

## Summary

Current main now defers stuck-session recovery when the diagnostics heartbeat itself arrives more than 90 seconds late, which likely covers the reported multi-minute starvation incident. Keep this issue open because the fixed 90-second cutoff is not tied to the configurable abort threshold, so lower configured thresholds can still permit recovery based on observer-inflated progress ages.

## What This Changes

Gate stuck-session classification and active-run aborts on gateway liveness, and ensure recovery thresholds remain safe when diagnostics timing is unreliable.

## Best Possible Solution

Carry heartbeat lateness into the recovery decision and refuse active abort until a healthy observation interval has occurred, with the gate scaled to the effective abort threshold and regression coverage for default and low custom thresholds.

- **Keep the fixed cutoff:** Treat the current 90-second guard as sufficient for supported defaults and document that unusually low custom abort thresholds reduce false-positive protection.

## Reproduction Assessment

Yes for the shipped v2026.7.1 behavior: the report provides a timestamped chain from multi-minute event-loop starvation to false stall classification and active-run abort. Current main contains a partial guard, so the remaining low-threshold case is source-reproducible rather than live-reproduced.

## Solution Assessment

Not fully. Deferring recovery after a very late heartbeat is the correct boundary, but a fixed 90-second cutoff is less robust than tying telemetry validity to the effective abort window and requiring a healthy recheck.

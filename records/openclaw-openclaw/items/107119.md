## Summary

This PR has a useful bounded-concurrency goal, but the `p-map` substitution is not mechanically equivalent to the existing `Promise.all` batches when an individual mapper fails: it can leave later generated assets unprocessed. It also still needs real command-path proof on the latest head, not only a standalone limiter simulation.

## What This Changes

The PR caps concurrent capability-CLI media reads and generated image/video asset writes at 20 by replacing selected `Promise.all(...map(...))` batches with the existing `p-map` dependency.

## System Context

Capability CLI commands read local media, call image or video providers, save returned assets, and print structured command results. The changed helpers sit on the filesystem and media-processing portions of that pipeline, before provider input and after provider output.

## Best Possible Solution

Use a bounded scheduling approach that preserves the existing all-item scheduling and rejection behavior, add focused failure and over-20-item coverage, then provide redacted terminal proof from a real capability-CLI invocation on the updated head.

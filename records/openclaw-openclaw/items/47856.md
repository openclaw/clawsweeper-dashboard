## Summary

Keep open: current main and the latest release still lack a public configurable image/media local-root allowlist, while the narrow iMessage attachment-root symptom is only partially addressed through channel-scoped inbound roots. The remaining work is a security-sensitive host filesystem access policy decision and overlaps the open broader filesystem-roots PR.

## What This Changes

The issue requests a `tools.image.mediaLocalRoots`-style configuration field so image/media tools can read operator-approved local attachment directories outside the default OpenClaw roots.

## Best Possible Solution

Adopt one explicit root policy for host-local media reads, then align schema, types, docs, doctor/upgrade expectations, and focused image/PDF/media tests around that single contract.

- **Add A Narrow Media Allowlist:** Expose a dedicated media-tool local-root config with strict absolute non-root validation, docs, and regression tests if maintainers want media isolated from general filesystem policy.
- **Keep Current Roots Only:** Decline new host-root config for now and keep current default/workspace plus channel-scoped inbound roots, leaving copying or staging as the supported workaround.

## Reproduction Assessment

Yes, at source level. Current main routes image-tool local media through fixed default/workspace roots plus scoped inbound roots, and the strict public schemas expose no `mediaLocalRoots`-style config field.

## Solution Assessment

Unclear as requested: a narrow image-tool knob would solve this report, but a single filesystem/media-root policy is likely more maintainable and less confusing than another per-tool allowlist.

## Summary

Keep open: current main and v2026.6.11 still do not expose a configurable image/media local-root allowlist. The narrower iMessage attachment-root path has shipped through scoped inbound roots, but the requested operator-controlled host-root policy remains a security-sensitive product/config decision with an open broader candidate PR.

## What This Changes

The issue requests a configurable local-media root allowlist for image/media tools so trusted attachment paths outside OpenClaw-managed directories can be read without manual copying.

## Best Possible Solution

Choose one canonical, security-reviewed operator root policy, likely `tools.fs.roots` or an equivalent shared contract, then wire it through schema, docs, shared media loaders, and regression tests without adding a separate per-tool allowlist.

Options:

- **Adopt shared filesystem roots (recommended):** Use the reviewed `tools.fs.roots` direction, or a narrowed equivalent, so image/media tools, outbound media, and FS access share one policy surface.
- **Add media-only roots:** Accept a smaller `tools.mediaLocalRoots` or `tools.image.mediaLocalRoots` surface, but own the long-term drift risk between media, channel inbound roots, and FS tools.
- **Keep managed roots only:** Decline broad host-root configuration and keep users on workspace, managed media, channel inbound roots, symlinks, or copy workflows.

## Reproduction Assessment

Yes, at source level. Current main resolves image-tool local reads through default/workspace roots plus scoped inbound roots, and the strict config schemas expose no persistent extra-root field for the requested host directories.

## Solution Assessment

No for an ad hoc per-tool field. The maintainable fix is one security-reviewed root policy shared by image/media tools and related filesystem/media paths, with docs and tests for safe defaults and upgrade behavior.

## Summary

Keep open: current main and v2026.6.11 still lack a public configurable image/media local-root allowlist. The narrower iMessage attachment-root path is handled through scoped inbound roots, but the requested operator-controlled host-root policy remains a security-sensitive product/config decision with an open broader candidate PR.

## What This Changes

The issue requests a configurable image/media local-root allowlist so local attachment paths outside OpenClaw-managed directories can be used by media tools without manual copying.

## Best Possible Solution

Adopt one security-reviewed operator-controlled filesystem/media-root policy, keep scoped channel inbound roots separate from broad host-local reads, and wire the accepted policy through schema, docs, shared media loaders, and focused tests.

Question: Should OpenClaw accept a public operator-configured host-root policy for image/media tools, and should that be the broad tools.fs.roots model instead of a per-tool mediaLocalRoots field?

Rationale: The requested capability changes a filesystem read boundary and the repository already has overlapping channel-inbound and broader filesystem-root designs that automation should not choose permanently.

Likely owner: steipete

Owner confidence: medium

Options:

- **Adopt central roots policy (recommended):** Use a single reviewed tools.fs.roots-style policy for image tools, outbound media, prompt images, and related host-read surfaces.
- **Add narrow media roots:** Add a smaller media-only config surface with explicit validation and docs, accepting the cost of a separate trust boundary.
- **Keep current boundaries:** Decline broad configurable roots and keep only managed OpenClaw roots plus scoped channel inbound roots.

## Reproduction Assessment

Yes, at source level. Current main validates image-tool local paths through fixed/default roots plus scoped inbound roots, while the strict config schema exposes no tools.image.mediaLocalRoots, tools.media.localRoots, or tools.fs.roots field.

## Solution Assessment

No for an ad hoc per-tool config patch. The safer maintainable solution is a single reviewed filesystem/media-root policy so image tools, outbound media, webchat previews, and workspaceOnly behavior do not grow conflicting allowlists.

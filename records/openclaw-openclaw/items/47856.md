## Summary

Keep open: current main and v2026.6.11 still lack a public configurable image/media local-root allowlist. The iMessage attachment-root path is partly handled through scoped inbound roots, but the broader operator-controlled host-root policy remains a security-sensitive product/config decision with an open candidate implementation.

## What This Changes

Request to add a configurable local media-root allowlist for the image tool so trusted attachment directories can be read without copying files into OpenClaw-managed roots.

## Best Possible Solution

Choose one security-reviewed filesystem/media-root contract, keep channel inbound roots distinct from broad host-local reads, and wire the accepted policy through schema, docs, shared media loaders, and focused tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which local filesystem/media-root policy should OpenClaw expose for image and media tools: shared tools.fs roots, scoped channel inbound roots only, or a narrow media-only allowlist?

Rationale: The choice defines a public config surface and host filesystem read boundary, and the current code already shows separate partial designs with different security and compatibility tradeoffs.

Likely owner: steipete

Owner reason: steipete has the strongest history on the filesystem policy and outbound media access boundary that this decision extends.

Owner confidence: high

Options:

- **Adopt shared tools.fs roots (recommended):** Use or repair the open tools.fs.roots design as the canonical policy for file tools and media surfaces, with explicit security docs and upgrade tests.
- **Keep only scoped inbound roots:** Treat iMessage attachment access as solved by channel-scoped roots and decline broad host-local media root configuration for now.
- **Add media-only allowlist:** Approve a narrower tools.media or tools.image localRoots config, accepting the cost of a separate media trust boundary.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 expose no mediaLocalRoots-style config field, and the image tool still validates arbitrary local paths against fixed/default roots plus scoped inbound roots.

## Solution Assessment

No for an ad hoc per-tool config patch. The safer maintainable solution is a single reviewed filesystem/media-root policy so image tools, outbound media, webchat previews, and workspaceOnly behavior do not grow conflicting allowlists.

## Summary

Keep open: current main and the latest release have the narrower iMessage attachment-root fix, but they still do not expose a public configurable media-local-root allowlist. The remaining work changes a host filesystem read boundary and overlaps the open, conflicting https://github.com/openclaw/openclaw/pull/52951 design, so it needs maintainer product/security direction rather than cleanup closure.

## What This Changes

The issue requests a config field such as `tools.image.mediaLocalRoots` so image/media tools can read additional host-local directories, especially iMessage attachment roots, without copying files into the workspace.

## Best Possible Solution

Choose one security-reviewed filesystem/media-root policy, keep scoped channel inbound roots separate from broad host-local reads, and wire the accepted contract through schema, docs, shared media loaders, and focused upgrade/security tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which host-local media-root policy should OpenClaw support for image/media tools: shared `tools.fs.roots`, a narrower media-only root field, or no persistent host-root expansion?

Rationale: The requested config changes what model-facing media tools may read from disk, and repository policy treats filesystem boundaries plus new config surfaces as maintainer/security decisions.

Likely owner: Peter Steinberger

Owner reason: The decision is about the media/root filesystem security boundary, and this history includes prior narrowing of default local attachment roots.

Owner confidence: medium

Options:

- **Use shared filesystem roots (recommended):** Adopt a single security-reviewed `tools.fs.roots`-style contract for filesystem tools and media paths so OpenClaw does not grow competing allowlists.
- **Add media-only roots:** Add a narrower media-root config if maintainers want image/PDF/media reads decoupled from read/write/edit filesystem policy, with explicit docs and tests for the split boundary.
- **Keep current boundary:** Continue requiring managed inbound media, channel-scoped attachment roots, copies, or symlinks instead of persistent host-root expansion.

## Reproduction Assessment

Yes, source-level: current main exposes no `mediaLocalRoots`-style public config and `resolveMediaToolLocalRoots()` still ignores configurable roots. The scoped iMessage channel-root path is covered by tests, but it does not reproduce the requested general configurable-root capability.

## Solution Assessment

No for the exact per-tool config as stated; it is only a plausible shape. The safer solution is a single maintainer-approved filesystem/media-root policy that avoids competing allowlists across image tools, outbound media, webchat, and `workspaceOnly` behavior.

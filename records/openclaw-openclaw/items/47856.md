## Summary

Keep open: current main and v2026.6.11 still lack a public configurable media-local-root allowlist, and the remaining work is a security-sensitive host filesystem policy decision rather than a safe cleanup close.

## What This Changes

The issue requests a configurable `mediaLocalRoots`-style setting so the image tool can read trusted local media paths outside OpenClaw-managed roots.

## Best Possible Solution

Choose one canonical, security-reviewed filesystem/media-root policy, keep scoped channel inbound roots separate from broad host-local reads, and wire the accepted contract through schema, docs, shared media loaders, and focused tests.

## Maintainer Decision

Required: true

Question: Which host-local media-root policy should OpenClaw support for image/media tools: shared `tools.fs.roots`, a narrower media-only root field, or no persistent host-root expansion?

Rationale: The requested config changes what model-facing media tools may read from disk, and repository policy treats filesystem boundaries plus new config/default surfaces as maintainer/security decisions rather than safe autonomous fixes.

Likely owner: Peter Steinberger

Owner reason: Current-main ownership and prior media-root policy history make this the best available security-boundary routing owner.

Owner confidence: medium

Options:

- **Use shared filesystem roots (recommended):** Adopt a single security-reviewed `tools.fs.roots`-style contract for filesystem tools and media paths so OpenClaw does not grow competing allowlists.
- **Add media-only roots:** Add a narrower media-root config if maintainers want image/PDF/media reads decoupled from read/write/edit filesystem policy, with explicit docs and tests for the split boundary.
- **Keep current boundary:** Continue requiring copies, symlinks, managed inbound media, or scoped channel attachment roots instead of persistent host-root expansion.

## Reproduction Assessment

Yes, source-level. Current main routes image local paths through fixed/default roots plus scoped inbound roots, and strict public schemas expose no `mediaLocalRoots`-style field.

## Solution Assessment

No for an ad hoc per-tool config patch. The safer maintainable solution is a single reviewed filesystem/media-root policy so image tools, outbound media, webchat previews, and `workspaceOnly` behavior do not grow conflicting allowlists.

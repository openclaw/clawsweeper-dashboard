## Summary

Keep open: current main and v2026.6.11 still lack a public configurable media-root allowlist for the image/media tools. The iMessage attachment-root bug has a narrower shipped fix through scoped inbound roots, but this issue’s broader operator-controlled host-root policy remains a security-sensitive product/config decision.

## What This Changes

Request to add a `tools.image.mediaLocalRoots`-style config field so image/media tools can read operator-approved local attachment directories outside default OpenClaw roots.

## Best Possible Solution

Choose one canonical security-reviewed filesystem/media-root policy, keep scoped channel inbound roots separate from broad host-local reads, and wire the accepted policy through schema, docs, shared media loaders, and focused tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which canonical operator-controlled host-root policy should OpenClaw support for image/media tools: shared `tools.fs.roots`, a narrower media-only root field, or no persistent host-root expansion?

Rationale: The requested config changes what model-facing media tools may read from the host, and repository policy treats config/default surfaces and filesystem boundaries as maintainer/security decisions rather than safe autonomous fixes.

Likely owner: jacobtomlinson

Owner reason: This decision is closest to the local-root policy and security boundary work in merged PRs 55946 and 57770.

Owner confidence: high

Options:

- **Use shared filesystem roots (recommended):** Adopt a single security-reviewed `tools.fs.roots`-style contract for filesystem tools and media paths so OpenClaw does not grow competing allowlists.
- **Add media-only roots:** Add a narrower media-root config if maintainers want image/PDF/media reads decoupled from read/write/edit filesystem policy, with explicit docs and tests for the split boundary.
- **Keep current boundary:** Do not add persistent host-root expansion and continue requiring copies, symlinks, managed inbound media, or channel-scoped attachment roots for local media access.

## Reproduction Assessment

Yes at source level. Current main routes image local paths through fixed/default roots plus scoped inbound roots, and the strict public config schema exposes no `mediaLocalRoots`-style field.

## Solution Assessment

No for an ad hoc per-tool config patch. The safer maintainable solution is a single reviewed filesystem/media-root policy so image tools, outbound media, webchat previews, and `workspaceOnly` behavior do not grow conflicting allowlists.

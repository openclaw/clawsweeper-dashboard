## Summary

Keep open: current main and v2026.6.11 still do not expose a configurable image/media local-root allowlist. The narrower channel-scoped iMessage inbound-root path is now handled separately, but the general operator-controlled host-root policy remains a security-sensitive config/product decision, and the broader candidate PR is still open and conflict-marked.

## What This Changes

The issue requests an operator-configurable allowed-root list for the image/media tool so local attachments outside OpenClaw-managed directories can be read without copying.

## Best Possible Solution

Settle one shared filesystem/media-root policy, likely through a reviewed tools.fs.roots-style surface or an explicitly narrower alternative, with schema/docs/tests/security review while preserving channel-scoped inbound roots and workspaceOnly semantics.

## Maintainer Decision

Question: Should OpenClaw expose operator-configured host roots for image/media reads, and should the accepted surface be the broader tools.fs.roots policy or a narrower media-only allowlist?

Rationale: This expands host filesystem read scope for model-facing tools and intersects workspaceOnly, inbound channel attachment roots, outbound media, and config compatibility, so code inspection alone cannot choose the product/security boundary.

Likely owner: steipete

Owner reason: The decision is mostly security/config policy rather than a local code edit, and recent history plus VISION guidance tie that policy area to steipete's work.

Owner confidence: medium

Options:

- **Adopt shared roots policy (recommended):** Refresh and review the broader tools.fs.roots-style design so filesystem tools, media reads, outbound media, and prompt-image loading share one explicit operator-controlled boundary.
- **Narrow to media-only roots:** Add a smaller image/PDF/media-only allowlist if maintainers want to avoid changing general filesystem tool policy, accepting the risk of a separate root source of truth.
- **Keep current strict model:** Reject configurable host roots and keep requiring channel-scoped inbound roots, OpenClaw-managed media, workspace placement, or explicit copy/staging for external files.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 resolve image/media local roots from fixed defaults plus workspace and strict channel-scoped inbound roots, while the schema exposes no configurable extra-root field. A local path outside those roots would still hit the existing allowed-directory rejection path.

## Solution Assessment

No for a per-tool-only tools.image.mediaLocalRoots knob as the final shape. The better solution is a shared filesystem/media-root policy so image, PDF, outbound media, prompt-image loading, and filesystem trust boundaries do not drift.

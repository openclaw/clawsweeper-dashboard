## Summary

Keep open: current main and v2026.6.11 still lack a configurable image/media local-root allowlist. The iMessage attachment-root subset is handled through scoped inbound roots, but the requested operator-controlled host-root policy remains a product and security-boundary decision with an open broader candidate PR.

## What This Changes

Request to add a configurable media local-root allowlist for the image tool so attachment-heavy workflows can analyze host-local files without copying them into OpenClaw-managed directories.

## Best Possible Solution

Choose one canonical operator-controlled filesystem/media-root policy, keep scoped channel inbound roots separate from broad host-local reads, then wire the accepted policy through schemas, shared media loaders, docs, and focused tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw solve configurable media/tool host roots through the broader tools.fs.roots policy, a narrower media-only config, or continue requiring staging into OpenClaw-managed roots?

Rationale: The implementation shape changes what model-facing tools may read from the host and overlaps an open broad filesystem-root proposal, so automation should not choose the permanent trust boundary.

Likely owner: jacobtomlinson

Owner reason: The recent merged local-root policy work is the closest current-main provenance for the trust-boundary decision.

Owner confidence: medium

Options:

- **Adopt a central roots policy (recommended):** Use a reviewed shared filesystem/media-root policy such as tools.fs.roots so image, outbound media, prompt-image loading, and filesystem tools share one operator-controlled boundary.
- **Add media-only roots:** Create a narrower media-local-root config only if maintainers intentionally want media tools to have a separate access boundary from filesystem tools.
- **Keep managed staging only:** Document copying, managed inbound media, and channel-scoped attachment roots as the supported path while rejecting arbitrary host-root configuration.

## Reproduction Assessment

Yes. Source inspection shows image-tool local paths flow through fixed/default roots plus scoped inbound roots, while current schemas expose no tools.image.mediaLocalRoots or equivalent config field.

## Solution Assessment

No for an ad hoc image-only config patch. The safer maintainable path is a single reviewed filesystem/media-root policy so image tools, outbound media, webchat previews, and workspaceOnly behavior do not grow conflicting allowlists.

## Summary

Keep open: current main and v2026.6.11 still do not provide the requested configurable image/media local-root allowlist. The iMessage attachment-root regression has a narrower scoped inbound-root fix, but the broader operator-controlled host-root policy remains security-sensitive and overlaps the open `tools.fs.roots` candidate.

## What This Changes

Request to add a configurable local media root allowlist, such as `tools.image.mediaLocalRoots`, so image-tool reads can include trusted attachment directories outside the default roots.

## Best Possible Solution

Choose one canonical operator-controlled filesystem/media-root policy, keep scoped channel inbound roots separate from broad host-local reads, and wire the accepted policy through schema, docs, shared loaders, and focused tests.

Rationale: The implementation changes which host paths model-facing media tools can read, and repository policy treats new config plus filesystem/media-root access as a security and compatibility boundary that automation should not choose alone.

- **Adopt central fs roots (recommended):** Use a single reviewed `tools.fs.roots`-style policy for read/media surfaces so OpenClaw does not grow competing allowlists.
- **Design media-only roots:** Add a narrower media-root field only after documenting why it should differ from filesystem-tool roots and channel inbound roots.
- **Keep current boundary:** Decline configurable host roots and require copying, symlinking, or channel-scoped inbound-root handling instead.

## Reproduction Assessment

Yes. Source inspection shows current main and v2026.6.11 have fixed/default local roots plus scoped inbound roots, and no public `tools.image.mediaLocalRoots` or equivalent config field.

## Solution Assessment

No for an ad hoc per-tool config patch. The safer maintainable solution is a single reviewed filesystem/media-root policy so image tools, outbound media, webchat previews, and `workspaceOnly` behavior do not grow conflicting allowlists.

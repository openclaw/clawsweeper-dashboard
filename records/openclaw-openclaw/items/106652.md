## Label Justifications

- `P2`: The report identifies a plausible, bounded terminal-status correctness problem, but provides no evidence of data loss, unavailable runtime, or a broadly broken agent workflow.
- `impact:ux-friction`: Affected users may see a cancellation error after receiving apparently complete output, creating avoidable confusion about whether the run succeeded.

## Summary

Current main explicitly makes cancellation sticky, so the reported outcome is source-reproducible; however, changing that precedence without tracing completion, cancellation, and timeout projections could misreport a user-cancelled run as successful.

## What This Changes

Change terminal-outcome merging so a completed run with valid output can supersede a concurrent cancellation outcome.

## Best Possible Solution

Define one tested terminal-state invariant for completion racing with user cancellation, then update the central merge helper and every user-visible projection together rather than adding caller-specific exceptions.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When user cancellation races with a model completion containing output, should explicit cancellation remain authoritative, or should committed completion output make the run successful?

Rationale: Both outcomes are defensible user-facing semantics, and the central helper intentionally owns precedence for all projections; source inspection alone cannot determine the intended product contract.

Likely owner: steipete

Owner reason: This cross-path terminal-state contract needs repository-level agent-runtime ownership rather than a caller-local choice.

Owner confidence: low

Options:

- **Committed completion wins (recommended):** Treat completion as successful only when the response was fully committed to the transcript or delivery path before cancellation became authoritative.
- **Cancellation always wins:** Keep cancellation sticky and clarify that concurrently generated output does not change the final run status.
- **Expose a distinct race outcome:** Represent completed-after-cancel as a separate terminal outcome so projections can explain that output finished while cancellation was requested.

## Reproduction Assessment

No high-confidence runtime reproduction is provided, but the precedence is reproducible from source: an existing `cancelled` outcome is returned unchanged when an incoming `completed` outcome is merged.

## Solution Assessment

Unclear. Allowing every completion payload to override cancellation is too broad; the safer fix must distinguish fully committed user-visible completion from late or partial work produced after cancellation.

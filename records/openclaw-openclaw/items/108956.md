## Summary

The implementation is narrow, technically sound, and backed by convincing live curl behavior proof, but this security-labeled CI policy change needs OpenGrep owner approval and the prior P3 guard-test finding remains unresolved.

## What This Changes

The PR replaces pipe-to-bash OpenGrep installer fetches in two CI workflows with bounded temporary-file downloads and adds a workflow guard test.

## Best Possible Solution

Keep the staged commit-pinned download, make the guard independently assert `-o "$opengrep_install"` and `bash "$opengrep_install"`, and land only after the OpenGrep workflow owner confirms the 10/120-second policy.

Owner confidence: high

Options:

- **Approve the proposed bounds (recommended):** Keep the 10/120-second limits after correcting the guard assertions, accepting bounded scan failures during exceptionally slow upstream responses.
- **Retune the transfer deadline:** Choose a longer maximum transfer time if maintainers prefer greater tolerance for transient GitHub raw-content slowness.
- **Retain only the outer timeout:** Decline per-download limits and continue relying on the workflow-level timeout, preserving tolerance at the cost of potentially long stuck scans.

## Reproduction Assessment

Yes. A connected local TCP server that withholds response data reproduces the unbounded current-main curl pipeline, while the proposed bounded command exits near its configured deadline.

## Solution Assessment

Yes, with a small test correction. Downloading the immutable-commit installer completely before execution is the narrowest maintainable fix and avoids streaming partial content into bash; the guard should protect the two critical command relationships explicitly.

## Label Justifications

- `impact:message-loss`: The attachment bytes are silently lost while the accompanying caption is still delivered to the active run.

## Summary

Keep open. The current shared active-run path accepts an attachment-bearing turn but forwards only its text through steering, while the complete media payload remains available only to the follow-up path. Codex steering already accepts image inputs, so this is a bounded implementation bug rather than a product or configuration decision. citeturn917712view0turn567300view0

## What This Changes

Fix shared active-run handling so attachment-bearing inbound turns retain their media instead of steering only caption text.

## Best Possible Solution

Extend the shared steering request to carry ordered image inputs for capable harnesses, and atomically enqueue the complete attachment-bearing FollowupRun whenever media steering is unavailable or rejected.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes at source level: an image-bearing FollowupRun reaches a steering call that forwards only prompt text, while the queued path retains the ordered images. A live current-main run was not performed during this read-only review.

## Solution Assessment

The proposed forced-follow-up guard would prevent data loss, but it is not the best complete solution because the Codex steering contract already supports image inputs. Prefer media-capable shared steering with a guaranteed queued fallback for unsupported or rejected cases.

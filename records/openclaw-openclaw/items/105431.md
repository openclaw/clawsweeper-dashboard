## Summary

The report is valid against both current main and the latest release: one transient snapshot read or write failure permanently disables later snapshot attempts for that config path during the process. No related issue or pull request currently owns the repair, so this should remain open as a focused reliability fix.

## What This Changes

Retry the pre-update config snapshot after a transient read or write failure instead of permanently treating the path as successfully snapshotted.

## Best Possible Solution

Use once-on-success, in-flight-coalesced bookkeeping: concurrent callers for one path share a single attempt, successful completion remains recorded for the process, and failed attempts are removed so a later update phase can retry without blocking the update.

## Reproduction Assessment

Yes at source level: reject the first snapshot read or write, then invoke the helper again for the same config path; the second invocation returns before performing I/O because the path remains recorded. No executable test was run because this review was required to remain read-only.

## Solution Assessment

Yes, with concurrency protection: completion should be retained only after a successful snapshot write, while simultaneous callers should share or serialize the attempt so later config bytes cannot replace the original snapshot.

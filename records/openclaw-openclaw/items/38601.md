## Label Justifications

- `P2`: This is a normal-priority exec/sandbox correctness issue with limited blast radius, not a runtime outage or data-loss emergency.
- `impact:security`: The issue concerns sandboxed shell execution and whether an explicit high-power PTY request is visibly denied.
- `impact:ux-friction`: Silently ignoring `pty: true` can leave users debugging why interactive terminal tools behave differently in sandbox mode.

## Summary

Keep open: current main and v2026.6.11 still turn explicit sandboxed `pty: true` requests into non-PTY execution without a sandbox-specific warning, and the same-repo fix attempts are closed unmerged while a remaining warning-only candidate exists only in a fork.

## What This Changes

The issue asks OpenClaw to warn or fail clearly when `exec` is called with `pty: true` but sandbox mode prevents PTY execution.

## Best Possible Solution

Keep PTY disabled under sandbox by default, add a clear warning through the existing exec warning channel when explicit `pty: true` is ignored, document the sandbox limitation, and cover both sandbox and non-sandbox PTY paths.

Rationale: The report accepts either warning or error behavior, and changing from silent fallback to fail-closed would alter the sandboxed exec contract beyond a mechanical warning fix.

Options:

- **Warn And Continue (recommended):** Emit a clear warning when sandbox mode disables explicit PTY while preserving current non-PTY sandbox execution behavior.
- **Fail Explicit PTY:** Reject sandboxed exec calls that explicitly request PTY so the user must choose a different host or elevated path.
- **Document Only:** Clarify the sandbox limitation in docs without changing runtime output, leaving the silent tool-result behavior in place.

## Reproduction Assessment

Yes by source inspection: current main resolves sandboxed explicit PTY requests to `usePty=false` and lacks a sandbox-specific warning branch. I did not run a live sandboxed exec command in this read-only review.

## Solution Assessment

Yes for the warning-only path: the existing warnings channel is the narrowest maintainable place to explain the ignored explicit request without weakening the sandbox boundary. Failing the call instead is also defensible but needs maintainer security intent.

## Summary

Keep open: current main and the latest release still use a prompt-facing SKILL.md read-and-follow model, while the requested role, memory, tool-authority, and behavioral-monitoring boundaries are not implemented and remain security/product design work.

## What This Changes

The issue requests instruction isolation for SKILL.md content, including role locking, filtering or monitoring for prompt injection, and per-skill authority metadata.

## Best Possible Solution

Define one maintainer-approved skill trust and capability contract, then enforce it consistently through prompt selection, SKILL.md loading, tool execution, memory access, sandbox policy, regression tests, and docs.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 instruct the model to read and follow selected SKILL.md files, while skill policy only exposes invocation and prompt-visibility controls. I did not run a live malicious-skill exploit.

## Solution Assessment

Unclear as a final implementation path: the requested direction addresses a real security-hardening gap, but maintainers still need to define the trusted/untrusted skill contract, compatibility defaults, and enforcement scope.

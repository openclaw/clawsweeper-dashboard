## Summary

Keep open. Current main and v2026.6.11 still expose skills through a model-facing available-skills catalog and read-and-follow flow, while the requested instruction isolation, role locking, per-skill memory/tool authority, and runtime monitoring remain unresolved security/product design work.

## What This Changes

The issue requests instruction-isolation, role-locking, behavioral monitoring, and capability enforcement so malicious SKILL.md content cannot influence agent role, memory, or tool authority through the prompt/context path.

## Best Possible Solution

Define one maintainer-approved skill trust and capability contract, then enforce it consistently through prompt selection, SKILL.md loading, tool execution, memory access, sandbox policy, tests, and docs.

## Reproduction Assessment

Yes, at source level: current main still tells the model to read and follow selected SKILL.md files, while skill policy only exposes invocation and prompt-visibility controls. I did not run a live malicious-skill exploit because this read-only review only needed source proof of the missing boundary.

## Solution Assessment

Unclear as a final implementation path: the requested direction addresses a real security-hardening gap, but maintainers still need to define the trusted/untrusted skill contract, compatibility defaults, capability metadata, and enforcement scope.

## Summary

Keep open. Current main still exposes skills through a model-facing `available_skills` read-and-follow path, while existing controls cover prompt visibility, proposal scanning, and general security guidance rather than instruction isolation, role locking, per-skill memory/tool authority, or runtime monitoring.

## What This Changes

The issue requests a core security architecture that isolates untrusted `SKILL.md` instructions from trusted agent/system context and adds role, memory, tool, and monitoring boundaries.

## Best Possible Solution

Define one maintainer-approved skill trust and capability contract, then enforce it consistently through prompt selection, `SKILL.md` loading, tool execution, memory access, sandbox policy, tests, and docs.

Unclear as a final implementation path: the requested direction addresses a real security-hardening gap, but maintainers still need to define the trusted/untrusted skill contract, compatibility defaults, and enforcement scope.

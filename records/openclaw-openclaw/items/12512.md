## Summary

Keep open. Current main and v2026.6.11 still expose skills through a model-facing `available_skills` read-and-follow path, while the implemented policy surface covers prompt visibility and invocation only, not instruction isolation, role locking, per-skill memory/tool authority, or runtime monitoring.

## What This Changes

The issue requests a new instruction-isolation and permission boundary for untrusted `SKILL.md` content, including role locking, capability metadata, filtering, and monitoring.

## Best Possible Solution

Define one maintainer-approved skill trust and capability contract, then enforce it consistently through prompt selection, `SKILL.md` loading, tool execution, memory access, sandbox policy, tests, and docs.

## Reproduction Assessment

Yes, at source level: current main still instructs the model to read and follow selected `SKILL.md` files, while skill policy only exposes invocation and prompt-visibility controls. I did not run a live malicious-skill exploit in this read-only review.

## Solution Assessment

Unclear as a final implementation path: the requested direction addresses a real security-hardening gap, but maintainers still need to define the trusted/untrusted skill contract, compatibility defaults, and enforcement scope.

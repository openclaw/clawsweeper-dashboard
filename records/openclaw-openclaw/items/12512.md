## Summary

Keep open. Current main still exposes skills through a model-facing `available_skills` read-and-follow path, while the implemented controls cover prompt visibility, proposal scanning, and general security guidance rather than the requested instruction isolation, role locking, per-skill memory/tool authority, or runtime monitoring.

## What This Changes

The issue requests a security architecture that isolates untrusted `SKILL.md` instructions from trusted agent context and adds related role, memory, tool, and monitoring controls.

## Best Possible Solution

Define one maintainer-approved skill trust and capability contract, then enforce it consistently through prompt selection, `SKILL.md` loading, tool execution, memory access, sandbox policy, tests, and docs.

## Reproduction Assessment

Yes, at source level: current main still instructs the model to read and follow selected `SKILL.md` files, while skill policy only exposes invocation and prompt-visibility controls. I did not run a live malicious-skill exploit.

## Solution Assessment

Unclear as a final implementation path: the requested direction addresses a real security-hardening gap, but maintainers still need to define the trusted/untrusted skill contract, compatibility defaults, and enforcement scope.

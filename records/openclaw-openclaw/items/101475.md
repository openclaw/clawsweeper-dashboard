## Summary

Keep open. Current main still reads the session-memory transcript with `fs.readFile`, but this PR is not merge-ready because the new 16 MiB cap is checked only after the shared reverse reader has produced and retained a complete line, so a huge single-line transcript entry can still be buffered and the PR body proof is contradicted by source.

## What This Changes

The PR replaces session-memory transcript `fs.readFile` extraction with a shared reverse JSONL stream capped at 16 MiB and adds an oversized-transcript regression test.

## Best Possible Solution

Enforce the session-memory cap before a cap-crossing transcript row can be buffered or retained, likely by using a bounded tail-range reader or adding an explicit max-byte/max-line mode to the shared reverse stream, then prove huge early content is excluded while recent messages remain available.

## Reproduction Assessment

Yes, at source level. Current main reads the whole transcript with `fs.readFile`, and PR head still applies the byte cap after the reverse reader has yielded a complete line, so the oversized-line failure path is clear without running tests.

## Solution Assessment

No. Reusing the shared reverse reader is a reasonable direction for normal multi-line tails, but this implementation is not the best fix because the helper intentionally preserves complete lines and the caller cap is enforced after buffering/retention.

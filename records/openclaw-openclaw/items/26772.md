## Label Justifications

- `P2`: This is a valid reliability improvement for long builtin memory indexing runs, but it is not a security bypass, crash loop, or first-run release blocker.
- `impact:data-loss`: Interrupted long reindexes can discard hours of generated embedding/index progress and force users to recompute from zero.
- `impact:session-state`: The missing checkpoint/resume state affects memory index generation state and whether memory/session context remains available after an interrupted rebuild.

## Summary

Keep open: current main still rebuilds the builtin memory index in a fresh random shadow SQLite database, publishes only after the rebuild completes, and deletes or age-cleans shadow databases rather than resuming committed progress. The related memory reliability reports and the open WAL metadata PR are adjacent but do not supersede the checkpoint/resume request.

## What This Changes

The issue requests durable checkpoint/resume behavior, and optionally memorySearch indexing config, so interrupted long-running builtin memory reindexes do not restart from zero.

## Best Possible Solution

Add a maintainer-approved memory-core checkpoint/resume design that persists generation progress, resumes interrupted full reindexes safely, reports incomplete generations honestly, and includes focused interruption/restart regression coverage.

## Maintainer Decision

Question: Should builtin memory-core add durable checkpoint/resume for forced/full reindex operations, and should that behavior be automatic or exposed as memorySearch indexing configuration?

Rationale: The source-proven gap is real, but the repair changes durable index-generation state, safe-publish semantics, and possibly public configuration, so automation should not choose the permanent product contract alone.

Likely owner: steipete

Owner confidence: high

Options:

- **Sponsor automatic resume (recommended):** Design memory-core to resume interrupted full reindexes by default while preserving safe publish semantics and adding status/tests/docs for incomplete generations.
- **Use explicit opt-in config:** Add checkpoint/resume behind a documented memorySearch option with upgrade proof for default compatibility and opt-in behavior.
- **Defer resume and improve recovery:** Keep all-or-nothing rebuilds for now and focus narrower work on retry, metadata repair, stale shadow cleanup, and clearer operator status.

## Reproduction Assessment

Yes, at source level: forced/full reindex still creates a fresh random shadow database, publishes only after completion, and removes or ages out shadow DBs instead of resuming from a persisted cursor. I did not run a live multi-hour crash test in this read-only review.

## Solution Assessment

No, the proposed config-heavy shape is not automatically the best fix yet because maintainers must choose the durable generation contract. The best direction is a memory-core-owned resume design that keeps incomplete generations out of clean search/status paths.

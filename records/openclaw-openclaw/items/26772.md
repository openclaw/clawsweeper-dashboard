## Summary

Keep open: current main still rebuilds the builtin memory index through a fresh random shadow SQLite database and publishes only after a complete run, with no durable checkpoint cursor or restart resume path. Related memory reliability issues cover embedding retries, dirty status, WAL durability, or search/reindex races, but they do not replace this checkpoint/resume request.

## What This Changes

The issue requests durable checkpoint/resume support for long-running memory indexing so interrupted full reindexes do not restart from zero.

## Best Possible Solution

Keep this issue open until memory-core has a durable checkpoint/generation design that can resume committed file or chunk progress after restart while keeping incomplete generations out of clean search/status results.

## Reproduction Assessment

Yes, at source level. A forced full reindex creates a fresh random shadow DB, publishes only after completion, and has no durable cursor or reusable temp discovery path for restart resume; I did not run a destructive kill/restart scenario in this read-only review.

## Solution Assessment

Unclear as proposed. Checkpoint/resume is the right product outcome, but the exact Option C/config shape needs maintainer design so it does not weaken atomic-publish safety or add unnecessary memorySearch knobs.

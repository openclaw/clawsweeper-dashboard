## Summary

Keep open: current main and the latest release still create a fresh shadow SQLite database for full memory reindexing, publish only after completion, and remove or age out shadow DBs instead of resuming them. The remaining work is real, but it needs maintainer direction because it changes durable memory generation semantics and incomplete-index status/search behavior.

## What This Changes

The issue requests checkpoint/resume support for long-running memory indexing so interrupted full reindexes can continue instead of restarting from zero.

## Best Possible Solution

Add memory-core-owned durable checkpoint/resume metadata for validated shadow full reindexes, resume only compatible incomplete generations, preserve safe publish/status semantics, and keep public config minimal unless maintainers choose knobs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should memory-core implement checkpoint/resume as a validated resumable shadow generation, as direct incremental writes to the live DB, or defer resumable full reindexing for now?

Rationale: Source inspection proves the gap, but the fix changes durable memory index generation identity, incomplete-index status/search semantics, and possibly public memorySearch config, so automation should not choose the product contract.

Likely owner: steipete

Owner reason: The earlier safe reindex lineage and prior keep-open review both route the product-shape decision most directly to steipete.

Owner confidence: high

Options:

- **Resumable shadow generation (recommended):** Persist generation/checkpoint state for the shadow DB and publish only after validation, preserving the current safe-rebuild invariant while allowing restart resume.
- **Direct incremental live writes:** Write checkpointed progress into the live DB with explicit incomplete-generation filtering and status semantics, accepting a larger migration and config surface.
- **Defer resume support:** Keep the current atomic full rebuild behavior and rely on embedding-cache reuse and stale-shadow cleanup until maintainers prioritize a broader memory indexing redesign.

## Reproduction Assessment

Yes from source inspection, but not from a live destructive run in this review. Current main still creates a fresh random shadow database for a full reindex and has no durable cursor to reuse after a process kill.

## Solution Assessment

Unclear until maintainer direction is set. A validated resumable shadow generation appears safer than direct live writes because it preserves the known-good-index invariant, but maintainers need to decide the durable semantics and config surface.

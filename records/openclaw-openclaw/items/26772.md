## Label Justifications

- `P2`: The issue is a valid reliability improvement for large builtin memory reindexes, but it is not a security bypass, crash loop, or first-run release blocker.
- `impact:data-loss`: Interrupted long reindexes can discard hours of generated embedding/index progress and force users to recompute from zero.
- `impact:session-state`: The missing checkpoint/resume state affects memory index generation state and whether memory/session context remains available after an interrupted rebuild.

## Summary

Keep open: current main and v2026.6.11 still rebuild builtin memory with a fresh shadow SQLite database, publish only after the full build succeeds, and remove or age-clean shadow files instead of resuming committed progress. The adjacent memory metadata/reindex-race reports and PRs are useful context, but none supersedes the checkpoint/resume request.

## What This Changes

Request durable checkpoint/resume support for long-running builtin memory full reindexes, possibly with memorySearch config and progress/status reporting.

## Best Possible Solution

Add a memory-core-owned SQLite generation/checkpoint design that resumes interrupted full reindexes safely, reports incomplete generations honestly, and includes restart/interruption regression coverage without adding public config unless maintainers choose that contract.

Options:

- **Sponsor automatic resume (recommended):** Implement resume by default in memory-core with SQLite-backed generation/checkpoint state while preserving the safe publish invariant and adding status/docs/tests for incomplete generations.
- **Use explicit opt-in config:** Add documented memorySearch indexing controls such as resume and checkpoint intervals with upgrade proof for default compatibility and opt-in behavior.
- **Defer resume work:** Keep all-or-nothing rebuilds for now and focus only on narrower metadata durability, stale-shadow cleanup, retries, and clearer operator status.

## Reproduction Assessment

Yes, at source level: forced/full reindex still creates a fresh random shadow database, publishes only after completion, and removes or ages out shadow DBs instead of resuming from a persisted cursor. I did not run a live multi-hour crash test in this read-only review.

## Solution Assessment

No, the issue's config-heavy proposal is not automatically the best fix yet. The best direction is a memory-core-owned resume design that keeps incomplete generations out of clean search/status paths, with config only if maintainers intentionally choose it.

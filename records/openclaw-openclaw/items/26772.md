## Label Justifications

- `P2`: This is a valid reliability improvement for long builtin memory indexing runs, but it is not a security bypass, crash loop, or first-run release blocker.
- `impact:data-loss`: Interrupted long reindexes can discard hours of generated embedding/index progress and force users to recompute from zero.
- `impact:session-state`: The missing checkpoint/resume state affects memory index generation state and whether memory/session context remains available after an interrupted rebuild.

## Summary

Keep open: current main still builds forced/full builtin memory reindexes in a fresh random shadow SQLite database, publishes only after a complete build, and removes or ages out shadow databases rather than resuming partial progress. The related memory reliability reports are adjacent, not replacements for checkpoint/resume.

## What This Changes

The issue requests durable checkpoint/resume support for long-running builtin memory indexing so interrupted reindexes do not lose all progress.

## Best Possible Solution

Add a maintainer-approved memory-core checkpoint/resume design that persists generation progress, resumes interrupted full reindexes safely, reports incomplete generations honestly, and includes focused restart/interruption regression coverage.

Options:

- **Sponsor automatic resume (recommended):** Design memory-core to resume interrupted full reindexes by default while preserving safe publish semantics and adding status, docs, and interruption tests.
- **Use explicit opt-in config:** Add checkpoint/resume behind a documented memorySearch option with upgrade proof for both default compatibility and opt-in behavior.
- **Defer resume and improve recovery:** Keep all-or-nothing rebuilds for now and focus narrower work on retry, metadata repair, stale shadow cleanup, and clearer operator status.

## Reproduction Assessment

Yes, at source level: forced/full reindex still creates a fresh random shadow database, publishes only after completion, and removes or ages out shadow DBs instead of resuming from a persisted cursor. I did not run a live multi-hour crash test in this read-only review.

## Solution Assessment

No, the issue's proposed config-heavy shape is not automatically the best fix yet because maintainers must choose the durable generation contract. The best direction is a memory-core-owned resume design that keeps incomplete generations out of clean search/status paths.

## Label Justifications

- `P2`: Interrupted large memory reindexes can discard hours of embedding/indexing work, but the affected surface is bounded to memory indexing reliability.
- `impact:data-loss`: The issue is about losing persisted memory-index progress and generated embedding work after an interrupted long-running reindex.

## Summary

Keep open: current main and the latest release still build a fresh builtin memory shadow database for each forced/full reindex, publish it only after completion, and clean up abandoned shadows rather than preserving a durable checkpoint for resume.

## What This Changes

Request durable checkpoint/resume support for long-running builtin memory full reindexes so interrupted runs do not restart from zero.

## Best Possible Solution

Add memory-core-owned durable shadow-generation checkpoint/resume metadata for full reindexes, target the per-agent SQLite path, and keep new public config minimal unless maintainers approve knobs.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: a forced full memory reindex creates a fresh random shadow DB, publishes only after completion, and has no durable cursor to reuse after a process kill.

## Solution Assessment

No. The exact direct-write plus public config proposal is not clearly the best default; a validated resumable shadow generation better preserves the current database publish invariant.

## Summary

Keep open: current main and the latest release still rebuild full builtin memory indexes through a fresh shadow SQLite database and remove or age-clean shadow files instead of resuming interrupted progress. Related memory-index durability work is useful, but it does not replace this checkpoint/resume request.

## What This Changes

The issue requests durable checkpoint/resume support for long-running builtin memory indexing so interrupted full reindexes can continue instead of restarting from zero.

## Best Possible Solution

Add memory-core-owned durable checkpoint metadata for validated resumable shadow full reindexes, resume only compatible incomplete generations, and keep public config minimal unless maintainers choose explicit knobs.

## Maintainer Decision

Kind: product_direction

Question: Should memory-core implement resumable full reindexing as a validated resumable shadow generation, direct incremental writes to the live DB, or defer resume support for now?

Rationale: Source inspection proves the reliability gap, but durable generation identity, incomplete-index search/status behavior, orphan cleanup policy, and any public memorySearch configuration are product/API choices rather than a strict mechanical repair.

Likely owner: steipete

Owner reason: The previous issue discussion and historical atomic reindex lineage make steipete the best available owner for the product-shape decision, with vincentkoc likely owning implementation details.

Owner confidence: high

Options:

- **Resumable Shadow Generation (recommended):** Persist generation/checkpoint state for the shadow DB and publish only after validation, preserving the current known-good-index invariant while allowing restart resume.
- **Direct Incremental Live Writes:** Write checkpointed progress into the live DB with explicit incomplete-generation filtering and status semantics, accepting a larger migration and config surface.
- **Defer Resume Support:** Keep atomic full rebuild behavior and rely on cache reuse, retry, and orphan cleanup until maintainers prioritize a broader memory indexing redesign.

## Reproduction Assessment

Yes, at source level: forced/full reindex still creates a fresh random shadow DB, publishes only after completion, and removes or age-cleans the shadow instead of resuming it. I did not run a destructive kill/restart scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the contract. A validated resumable shadow generation appears safer than direct live writes because it preserves the current known-good-index invariant while adding resume semantics.

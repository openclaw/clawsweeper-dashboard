## Summary

Keep open: current main and the latest release still rebuild the builtin memory index into a fresh shadow SQLite database and publish only after completion, without durable checkpoint metadata or resume of interrupted shadow progress. The remaining work is valid but needs maintainer direction because it changes memory generation identity, incomplete-index status/search semantics, and possibly public config.

## What This Changes

Add checkpoint/resume support for long-running builtin memory indexing so interrupted full reindex work can continue instead of restarting from zero.

## Best Possible Solution

Add memory-core-owned durable checkpoint/resume metadata for validated shadow full reindexes, resume only compatible incomplete generations, and keep public config minimal unless maintainers choose knobs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should memory-core implement checkpoint/resume as a validated resumable shadow generation, as direct incremental writes to the live DB, or defer resumable full reindexing for now?

Rationale: The repair changes durable memory index generation semantics, incomplete-index status/search behavior, and possibly public memorySearch config, so code inspection can prove the gap but not choose the product contract.

Likely owner: steipete

Owner reason: steipete authored the safe reindex lineage and previously commented on this issue's keep-open direction, making him the best available decision owner from the history trail.

Owner confidence: medium

Options:

- **Resumable shadow generation (recommended):** Persist generation/checkpoint state for the shadow DB and publish only after validation, preserving the current safe-rebuild invariant while allowing restart resume.
- **Direct incremental live writes:** Write checkpointed progress into the live DB with explicit incomplete-generation filtering and status semantics, accepting a larger migration and config surface.
- **Defer resume support:** Keep the current atomic full rebuild behavior and rely on embedding-cache reuse and cleanup until maintainers prioritize a broader memory indexing redesign.

## Reproduction Assessment

Yes. Source inspection shows a forced full memory reindex creates a fresh random shadow DB, publishes only after completion, and has no durable cursor to reuse after a process kill; I did not run a destructive kill/restart scenario in this read-only review.

## Solution Assessment

No, the direct-write plus public config proposal is not clearly the best default shape. A validated resumable shadow generation appears safer because it preserves the current database-first publish invariant with less new config surface, but maintainers need to choose the final semantics.

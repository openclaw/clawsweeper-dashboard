## Label Justifications

- `P2`: This is a normal-priority reliability improvement for large builtin memory indexes with limited blast radius and no evidence of a current release-blocking outage.
- `impact:session-state`: The issue is about memory index generation state losing progress and restart continuity during long-running reindexes.
- `impact:data-loss`: Interrupted reindexes discard hours of generated index/embedding progress rather than resuming from committed work.

## Summary

Keep open: current main and the latest release still build builtin full reindexes in a fresh random shadow SQLite database, publish only after completion, and delete or later clean orphan shadows rather than resuming interrupted progress. Related memory PRs/issues address adjacent metadata, race, and cleanup failures, but none owns durable checkpoint/resume for this issue.

## What This Changes

Request durable checkpoint/resume for long-running builtin memory reindexing so interrupted forced/full indexes do not restart from zero, with optional memorySearch indexing controls and status.

## Best Possible Solution

Add a durable SQLite-backed memory reindex generation/checkpoint design that can resume interrupted source-wide work while keeping search/status honest about incomplete generations and avoiding unnecessary new config unless maintainers approve it.

- **Keep only adjacent hardening:** Continue landing narrower metadata, WAL, lock, and cleanup repairs while leaving long-running checkpoint/resume as a later product design.
- **Decline configurable resume:** Reject the new config surface and document that forced full reindex remains all-or-nothing, relying on smaller paths and provider reliability instead.

## Reproduction Assessment

Yes, source inspection gives a high-confidence path: a forced/full builtin reindex creates a fresh random shadow DB, rebuilds, publishes only after completion, and removes or later cleans the shadow without a checkpoint cursor. I did not run a live multi-hour crash reproduction because this review is read-only and the source path is direct.

## Solution Assessment

Unclear until maintainers choose the durable state model; a narrow cleanup or WAL fix is not the best solution for this issue because those do not resume interrupted progress. The maintainable direction is a deliberate generation/checkpoint design in memory-core with status/search semantics and regression coverage.

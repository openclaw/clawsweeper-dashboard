## Summary

Keep open: current main and v2026.6.11 still rebuild builtin memory indexes through a fresh random shadow SQLite database and only publish after completion, with no durable checkpoint cursor or abandoned-shadow resume path. Related retry, WAL durability, and safe-reindex race work is useful but does not replace the checkpoint/resume request.

## What This Changes

Add checkpoint/resume support for long-running memory indexing so interrupted full reindexes do not discard hours of generated progress.

## Best Possible Solution

Implement a memory-core-owned resumable shadow-generation design with durable checkpoint metadata, compatibility validation before reuse, incomplete-generation status, and focused interrupted-reindex regression tests while keeping public config minimal unless maintainers choose otherwise.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should memory-core implement checkpoint/resume as a validated resumable shadow generation, direct incremental writes to the live DB, or defer resumable full reindexing for now?

Rationale: Source inspection proves the reliability gap, but generation identity, incomplete-index search/status behavior, orphan cleanup policy, and any public memorySearch configuration are product/API decisions rather than a strict mechanical fix.

Likely owner: steipete

Owner reason: The earlier reindex lineage and prior keep-open review route the product-shape decision most directly to steipete, with vincentkoc as the likely implementation owner for recent SQLite/reindex mechanics.

Owner confidence: high

Options:

- **Resumable shadow generation (recommended):** Persist checkpoint state for the shadow DB and publish only after validation, preserving the current known-good-index invariant while allowing restart resume.
- **Direct incremental live writes:** Write checkpointed progress into the live DB with explicit incomplete-generation filtering and status semantics, accepting a larger migration and config surface.
- **Defer resume support:** Keep atomic full rebuild behavior and rely on cache reuse, retry, and orphan cleanup until maintainers prioritize a broader memory indexing redesign.

## Reproduction Assessment

Yes, at source level: forced/full reindex still creates a fresh random shadow DB, rebuilds there, publishes only after completion, and removes or later cleans the shadow instead of resuming it. I did not run a destructive kill/restart scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the contract. A validated resumable shadow generation appears safer than direct live writes because it preserves the current known-good-index invariant while addressing restart resume.

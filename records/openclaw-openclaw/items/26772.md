- `impact:data-loss`: The issue is about losing persisted memory-index progress and generated embeddings after an interrupted long-running reindex.
- `impact:session-state`: The affected builtin memory index is durable memory/session recall state used by memory_search.

## Summary

Keep open: current main and v2026.6.11 still rebuild the default builtin memory index through a fresh shadow SQLite database and remove the shadow after the run, so interrupted long reindexes still cannot resume from committed progress.

## What This Changes

Requests durable checkpoint/resume support for long-running builtin memory full reindexes so interrupted indexing can continue instead of restarting from zero.

## Best Possible Solution

Add memory-core-owned durable checkpoint/resume metadata for validated shadow full reindexes, resume only compatible incomplete generations, and keep public config minimal unless maintainers choose explicit knobs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should memory-core implement checkpoint/resume as a validated resumable shadow generation, direct incremental writes to the live DB, or defer resumable full reindexing for now?

Rationale: Source inspection proves the reliability gap, but durable generation identity, incomplete-index search/status behavior, orphan cleanup policy, and any public memorySearch configuration are product/API decisions rather than a strict mechanical fix.

Likely owner: steipete

Owner reason: The earlier reindex lineage and prior keep-open review make steipete the best available owner for the product-shape decision, with vincentkoc as the likely implementation owner.

Owner confidence: high

Options:

- **Resumable shadow generation (recommended):** Persist compatible generation/checkpoint state for the shadow DB and publish only after validation, preserving the current known-good-index invariant while allowing restart resume.
- **Direct incremental live writes:** Write checkpointed progress into the live DB with explicit incomplete-generation filtering and status semantics, accepting a larger migration and config surface.
- **Defer resume support:** Keep atomic full rebuild behavior and rely on cache reuse, retry, and orphan cleanup until maintainers prioritize a broader memory indexing redesign.

## Reproduction Assessment

Yes, at source level: forced/full reindex still creates a fresh random shadow DB, rebuilds there, publishes only after completion, and removes the shadow on exit. I did not run a destructive kill/restart scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the contract. A validated resumable shadow generation appears safer than direct live writes because it preserves the current known-good-index invariant.

## Summary

Keep open: current main and the latest release still build a forced/full builtin memory reindex in a fresh shadow SQLite database, publish only after completion, and delete or age-clean shadow files instead of resuming them. The issue remains valid, but it needs maintainer direction because the fix changes durable memory generation identity, incomplete-index search/status behavior, and possibly public `memorySearch` config.

## What This Changes

The issue requests durable checkpoint/resume support for long-running memory indexing so interrupted forced/full reindexes can recover without losing all completed work.

## Best Possible Solution

Add memory-core-owned durable checkpoint/resume metadata for validated shadow full reindexes, resume only compatible incomplete generations, and keep public config minimal unless maintainers choose knobs.

## Maintainer Decision

Kind: product_direction

Question: Should memory-core implement checkpoint/resume as a validated resumable shadow generation, as direct incremental writes to the live DB, or defer resumable full reindexing for now?

Rationale: The source-level gap is real, but the repair changes durable memory index generation semantics, incomplete-index status/search behavior, and possibly public `memorySearch` config, so source inspection cannot choose the product contract.

Likely owner: steipete

Owner reason: Prior issue review and available commit history tie steipete most directly to safe reindex semantics and the earlier keep-open product decision.

Owner confidence: high

Options:

- **Resumable shadow generation (recommended):** Persist generation/checkpoint state for the shadow DB and publish only after validation, preserving the current safe-rebuild invariant while enabling restart resume.
- **Direct incremental live writes:** Write checkpointed progress into the live DB with explicit incomplete-generation filtering and status semantics, accepting a larger migration and config surface.
- **Defer resume support:** Keep the current atomic full rebuild behavior and rely on embedding-cache reuse and stale-shadow cleanup until maintainers prioritize a broader memory indexing redesign.

## Reproduction Assessment

Yes from source inspection, but not from a live destructive kill/restart run in this review. Current main creates a fresh random shadow DB for a full reindex, publishes only after completion, and has no durable cursor to reuse after a process kill.

## Solution Assessment

No final implementation choice is proven. A validated resumable shadow generation appears safer than direct live writes because it preserves the current known-good-index invariant, but maintainers need to decide durable semantics and config surface.

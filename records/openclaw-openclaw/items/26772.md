## Summary

Keep open: current main and the latest release still build a fresh shadow SQLite database for full memory reindexing, publish only after completion, and clean up orphans instead of resuming interrupted progress. The remaining gap is real, but the fix needs maintainer product direction because it changes durable generation state, incomplete-index search/status semantics, and possibly public memorySearch configuration.

## What This Changes

The issue requests durable checkpoint/resume support for long-running builtin memory reindexes so interrupted work can continue instead of starting from zero.

## Best Possible Solution

Implement memory-core-owned resumable shadow generation with durable checkpoint metadata, compatible resume validation, incomplete-generation status/search semantics, and focused interrupted-reindex tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should memory-core implement checkpoint/resume as a validated resumable shadow generation, direct incremental writes to the live DB, or defer resumable full reindexing for now?

Rationale: Source inspection proves the reliability gap, but durable generation identity, incomplete-index visibility, orphan cleanup policy, and any public memorySearch configuration are product/API choices rather than a strict mechanical fix.

Likely owner: steipete

Owner reason: The earlier reindex lineage and prior keep-open review route the product-shape decision most directly to steipete, with vincentkoc as a likely implementation owner.

Owner confidence: high

Options:

- **Resumable shadow generation (recommended):** Persist generation/checkpoint state for a compatible shadow DB and publish only after validation, preserving the known-good-index invariant while allowing restart resume.
- **Direct incremental live writes:** Write checkpointed progress into the live DB with explicit incomplete-generation filtering and status semantics, accepting a larger migration and config surface.
- **Defer resume support:** Keep atomic full rebuild behavior and rely on cache reuse, retry, and orphan cleanup until maintainers prioritize a broader memory indexing redesign.

## Reproduction Assessment

Yes, at source level: forced/full reindex still creates a fresh random shadow DB, rebuilds there, publishes only after completion, and removes or ages out the shadow instead of resuming it. I did not run a destructive kill/restart scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the contract. A validated resumable shadow generation appears safer than the issue's direct live-write option because it preserves the current known-good-index invariant.

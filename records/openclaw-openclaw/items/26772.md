## Summary

Keep open: current main and the latest release still rebuild the builtin memory index into a fresh shadow SQLite database, publish only after the rebuild completes, and discard shadow databases instead of resuming interrupted progress.

## What This Changes

Request durable checkpoint/resume support for long-running builtin memory indexing so interrupted full reindexes do not restart from zero.

## Best Possible Solution

Add memory-core-owned durable checkpoint/resume metadata for validated shadow full reindexes, resume only compatible incomplete generations, and keep public config minimal unless maintainers choose knobs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should memory-core implement checkpoint/resume as a validated resumable shadow generation, as direct incremental writes to the live DB, or defer resumable full reindexing for now?

Rationale: The gap is source-proven, but the repair changes durable memory generation semantics, incomplete-index status/search behavior, and possibly public memorySearch config, so maintainer intent is needed before implementation.

Likely owner: steipete

Owner reason: steipete is tied to the safe reindex lineage and prior review direction, making him the best available owner for the product-contract choice.

Owner confidence: high

Options:

- **Resumable shadow generation (recommended):** Persist generation/checkpoint state for the shadow DB and publish only after validation, preserving the current safe-rebuild invariant while allowing restart resume.
- **Direct incremental live writes:** Write checkpointed progress into the live DB with explicit incomplete-generation filtering and status semantics, accepting a larger migration and config surface.
- **Defer resume support:** Keep the current atomic full rebuild behavior and rely on embedding-cache reuse and cleanup until maintainers prioritize a broader memory indexing redesign.

## Reproduction Assessment

Yes. Source inspection shows a forced full memory reindex creates a fresh random shadow DB, publishes only after completion, and has no durable cursor to reuse after process death; I did not run a destructive kill/restart scenario in this read-only review.

## Solution Assessment

No, the direct-write plus public config proposal is not clearly the best default shape. A validated resumable shadow generation appears safer because it preserves the current publish invariant with less new config surface, but maintainers need to choose final semantics.

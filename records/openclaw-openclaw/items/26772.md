## Label Justifications

- `P2`: This is a valid reliability improvement for long builtin memory indexing runs, but it is not a security bypass, crash loop, or first-run release blocker.
- `impact:data-loss`: Interrupted long reindexes can discard hours of generated embedding/index progress and force users to recompute from zero.
- `impact:session-state`: The missing checkpoint/resume state affects memory index generation and whether memory/session context remains available after an interrupted rebuild.

## Summary

Keep open: current main and the latest release still build forced/full builtin memory reindexes in a fresh shadow SQLite database, publish only after the rebuild completes, and clean or retry shadow state rather than resuming interrupted progress.

## What This Changes

The issue requests durable checkpoint/resume support for long-running builtin memory indexing so interrupted reindexes do not restart from zero.

## Best Possible Solution

Add a memory-core-owned checkpoint/resume design that persists generation progress, safely reuses or discards incomplete shadow databases, keeps incomplete generations out of clean search/status, and adds interruption regression coverage.

## Maintainer Decision

Rationale: The gap is source-proven, but the fix changes durable memory generation semantics and may add public configuration or status behavior, so automation should not choose the permanent contract alone.

Options:

- **Sponsor automatic resume (recommended):** Implement resumable full reindex by default while preserving all-or-nothing publish semantics and adding status/tests for incomplete generations.
- **Make resume opt-in:** Add a documented memorySearch checkpoint/resume option with proof for both default compatibility and opt-in behavior.
- **Defer checkpointing:** Keep all-or-nothing rebuilds for now and focus narrower work on retry, metadata repair, stale-shadow cleanup, and clearer operator status.

## Reproduction Assessment

Yes, at source level: forced/full reindex still creates a fresh random shadow database, publishes only after completion, and removes or ages out shadow DBs instead of resuming from a persisted cursor. I did not run a live multi-hour crash test in this read-only review.

## Solution Assessment

Unclear that the proposed config-heavy shape is the best fix; maintainers need to choose the durable generation contract. The best direction is a memory-core-owned resume design that keeps incomplete generations out of clean search/status paths.

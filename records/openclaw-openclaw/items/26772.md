## Label Justifications

- `impact:data-loss`: The issue is about losing committed indexing progress for memory search after an interrupted long-running reindex.

## Summary

Keep open: current main still creates a fresh shadow memory database for each full reindex, publishes it only after the build completes, and deletes or later sweeps shadow databases rather than resuming interrupted progress. The request remains valid, but the right fix needs maintainer direction because it changes memory generation identity, checkpoint metadata, locking, and status/search semantics.

## What This Changes

The issue requests durable checkpoint/resume support for long-running memory indexing so interrupted full reindexes can continue instead of restarting from zero.

## Best Possible Solution

Add memory-core-owned durable generation/checkpoint metadata for resumable shadow full reindexes, preserving the atomic publish invariant and exposing status/config only where maintainers explicitly approve it.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence reproduction path: a forced full memory reindex creates a fresh random shadow DB, publishes only after completion, and has no durable cursor to reuse after a process kill.

## Solution Assessment

No. The requested durable resume capability is valid, but the direct-write plus public config proposal is not clearly the best default shape; a validated resumable shadow generation better preserves the existing database publish invariant.

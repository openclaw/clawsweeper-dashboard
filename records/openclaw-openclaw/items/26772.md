## Summary

Keep open: current main still uses a fresh random shadow SQLite database for forced/full builtin memory reindexing, publishes only after a complete rebuild, and has cleanup for abandoned shadows but no durable checkpoint/resume contract. The remaining work is valid, but it needs maintainer direction because it changes memory generation identity, incomplete-index search/status semantics, and possibly public memorySearch config.

## What This Changes

The issue requests durable checkpoint/resume support for long-running memory indexing so interrupted full reindexes do not lose all progress.

## Best Possible Solution

Implement a memory-core-owned resumable shadow generation that records compatible checkpoint state, resumes only validated incomplete generations, publishes only after full validation, and keeps public config minimal unless maintainers choose explicit knobs.

Question: Should memory-core solve interrupted full reindexing with a validated resumable shadow generation, direct incremental writes to the live DB with incomplete-generation filtering, or defer checkpoint/resume support for now?

Rationale: Source inspection proves the gap, but the repair changes durable memory generation semantics, incomplete-index search/status behavior, and possibly public memorySearch config, so automation should not choose the product contract.

Likely owner: vincentkoc

Owner reason: The current shadow publish semantics come from the database-first memory work he authored and reviewed, so he is the best available owner for the generation-contract choice.

Owner confidence: high

Options:

- **Resumable shadow generation (recommended):** Persist and validate generation/checkpoint state for the shadow DB, resume compatible incomplete work, and publish only after the completed generation passes the current safety checks.
- **Direct live incremental writes:** Write checkpointed progress into the live DB with explicit incomplete-generation status/search filtering, accepting a larger migration and compatibility surface.
- **Defer resume support:** Keep the current safe full rebuild behavior and rely on embedding-cache reuse plus orphan cleanup until maintainers prioritize a broader memory indexing redesign.

Yes, from source inspection; a live destructive kill/restart run was not performed. Current main still creates a fresh random shadow DB for a full reindex, publishes only after completion, and has no durable cursor or compatible-shadow reuse path.

## Solution Assessment

No final solution has been chosen. A validated resumable shadow generation appears safer than direct live writes because it preserves the current known-good-index invariant, but maintainers need to choose the durable semantics and config surface.

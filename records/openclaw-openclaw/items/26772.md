## Label Justifications

- `P2`: This is a valid reliability improvement for long builtin memory indexing runs, but it is not a security bypass, crash loop, or first-run release blocker.
- `impact:data-loss`: Interrupted long reindexes can discard hours of generated embedding/index progress and force users to recompute from zero.
- `impact:session-state`: The missing checkpoint/resume state affects memory index generation state and whether memory/session context remains available after an interrupted rebuild.

## Summary

Keep open: current main and the latest release still rebuild builtin memory indexes in a fresh shadow SQLite database, publish only after full completion, and clean failed shadows instead of resuming persisted progress.

## What This Changes

The issue requests durable checkpoint/resume behavior for long-running memory indexing so interrupted full reindexes do not discard hours of progress.

## Best Possible Solution

Add a maintainer-approved memory-core checkpoint/resume design that persists generation progress, resumes interrupted full reindexes safely, reports incomplete generations honestly, and adds interruption/restart regression coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should builtin memory-core add durable checkpoint/resume for forced/full reindex operations, and should that behavior be automatic or exposed as memorySearch indexing configuration?

Rationale: The source-proven gap is real, but the repair changes durable index-generation state, safe-publish semantics, and possibly public configuration/status behavior.

Likely owner: steipete

Owner confidence: high

Options:

- **Sponsor automatic resume (recommended):** Design memory-core to resume interrupted full reindexes by default while preserving safe publish semantics and adding status/tests/docs for incomplete generations.
- **Use explicit opt-in config:** Add checkpoint/resume behind documented memorySearch options with proof for default compatibility and opt-in behavior.
- **Defer resume:** Keep all-or-nothing rebuilds for now and focus narrower work on retry, metadata repair, stale shadow cleanup, and clearer operator status.

## Reproduction Assessment

Yes at source level: forced/full reindex still creates a fresh random shadow database, publishes only after completion, and removes or ages out shadow DBs instead of resuming from a persisted cursor. I did not run a live multi-hour crash test in this read-only review.

## Solution Assessment

Unclear: the issue's config-heavy proposal is plausible, but the best maintainable direction needs a maintainer decision. The implementation should be memory-core-owned and must keep incomplete generations out of clean search/status paths.

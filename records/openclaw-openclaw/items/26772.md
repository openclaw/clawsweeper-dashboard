## Label Justifications

- `P2`: Interrupted large memory reindexes can discard hours of generated embedding/indexing work, but the affected surface is bounded to memory indexing reliability.
- `impact:data-loss`: The issue is about losing persisted memory-index progress after an interrupted long-running reindex.

## Summary

Keep open: current main and the latest release still build each forced builtin memory reindex into a fresh random shadow SQLite database, publish only after the rebuild completes, and clean abandoned shadows rather than resuming them. The issue remains valid, but the fix needs maintainer design because it changes generation identity, locking, status/search semantics, and possibly config surface.

## What This Changes

Request durable checkpoint/resume support for long-running builtin memory indexing so interrupted full reindexes do not lose all progress.

## Best Possible Solution

Add memory-core-owned durable generation/checkpoint metadata for validated resumable shadow full reindexes, and keep public config minimal unless maintainers explicitly choose operator knobs.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence reproduction path: a forced full memory reindex creates a fresh random shadow DB, publishes only after completion, and has no durable cursor to reuse after a process kill; I did not run a destructive kill repro in this read-only review.

## Solution Assessment

No. The direct-write plus public config proposal is not clearly the best default shape; a validated resumable shadow generation better preserves the current database-first publish invariant with less new config surface.

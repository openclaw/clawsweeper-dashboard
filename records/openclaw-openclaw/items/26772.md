## Label Justifications

## Summary

Keep open: current main and the latest release still rebuild builtin memory indexes through a fresh random shadow SQLite database, publish only after the rebuild finishes, and clean up orphan shadows instead of resuming interrupted progress. The remaining work is valid, but it needs maintainer product direction because it changes durable generation state, search/status semantics, and possibly public `memorySearch` configuration.

## What This Changes

The issue requests durable checkpoint/resume support for long-running memory indexing so interrupted full reindexes can continue instead of starting over.

## Best Possible Solution

Add memory-core-owned durable checkpoint/resume metadata for validated full-reindex generations, resume only compatible incomplete work, and keep public config minimal unless maintainers choose explicit knobs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should memory-core implement resumable full reindexing as a validated resumable shadow generation, direct incremental live-DB writes, or defer checkpoint/resume support for now?

Rationale: Source inspection proves the reliability gap, but durable generation identity, incomplete-index search/status behavior, orphan cleanup policy, and any public `memorySearch` configuration are product/API decisions rather than a strict mechanical bug fix.

Likely owner: steipete

Owner reason: The earlier reindex lineage and prior keep-open review route the product-shape decision most directly to steipete, with vincentkoc as a likely implementation owner for the current SQLite/reindex path.

Owner confidence: high

Options:

- **Approve resumable shadow generation (recommended):** Persist generation/checkpoint state for the shadow DB and publish only after validation, preserving the current known-good-index invariant while allowing restart resume.
- **Use direct incremental live writes:** Write checkpointed progress into the live DB with explicit incomplete-generation filtering and status semantics, accepting a larger migration and compatibility surface.
- **Defer resume support:** Keep atomic full rebuild behavior and rely on cache reuse, retry, and orphan cleanup until maintainers prioritize a broader memory indexing redesign.

## Reproduction Assessment

Yes. Source inspection shows forced/full reindex creates a fresh random shadow DB, publishes only after completion, and deletes or ages out shadow DBs instead of discovering a checkpoint and resuming partial work.

## Solution Assessment

Unclear until maintainers choose the contract. Checkpoint/resume is the right end state, but the issue's direct-write/config proposal is not proven best; a validated resumable shadow generation appears safer because it preserves the known-good-index invariant.

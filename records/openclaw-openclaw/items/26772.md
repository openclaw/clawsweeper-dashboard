## Summary

Keep open: current main still uses a fresh random shadow SQLite database for full memory reindexing, publishes only after completion, and has no durable checkpoint cursor or compatible shadow-generation resume path. The remaining work is valid but needs maintainer product direction because it changes memory generation state, search/status semantics, and possibly public `memorySearch` configuration.

## What This Changes

The issue requests durable checkpoint/resume support for long-running builtin memory indexing so interrupted full reindex work is not lost.

## Best Possible Solution

Add memory-core-owned durable checkpoint/resume metadata for validated shadow full reindexes, resume only compatible incomplete generations, and keep public config minimal unless maintainers choose explicit knobs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should memory-core implement checkpoint/resume as a validated resumable shadow generation, direct incremental writes to the live DB, or defer resumable full reindexing for now?

Rationale: Source inspection proves the reliability gap, but durable generation identity, incomplete-index search/status behavior, orphan cleanup policy, and any public `memorySearch` configuration are product/API decisions rather than a strict mechanical fix.

Likely owner: steipete

Owner reason: The prior keep-open review and current reindex lineage route the product-shape decision most directly to steipete, with vincentkoc likely relevant for implementation review.

Owner confidence: high

Options:

- **Resumable shadow generation (recommended):** Persist generation/checkpoint state for the shadow DB and publish only after validation, preserving the known-good-index invariant while allowing restart resume.
- **Direct incremental live writes:** Write checkpointed progress into the live DB with explicit incomplete-generation filtering and status semantics, accepting a larger migration and config surface.
- **Defer resume support:** Keep atomic full rebuild behavior and rely on cache reuse, retry, and orphan cleanup until maintainers prioritize a broader memory indexing redesign.

## Reproduction Assessment

Yes, at source level: forced/full reindex still creates a fresh random shadow DB, rebuilds there, publishes only after completion, and removes or later cleans up shadows instead of resuming them. I did not run a destructive kill/restart scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the contract. A validated resumable shadow generation appears safer than direct live writes because it preserves the current known-good-index invariant while addressing lost progress.

## Label Justifications

- `P2`: This is a real memory indexing reliability gap for large deployments, but it is a bounded improvement rather than an emergency core-runtime outage.
- `impact:data-loss`: Interrupted long-running reindexes can discard hours of completed embedding/indexing progress and paid remote embedding work.
- `impact:session-state`: Memory/session index state can remain stale or require a full restart of indexing work after an interrupted rebuild.

## Summary

Keep open: current main and the latest release still build full builtin memory reindexes in a fresh shadow SQLite database, publish only after the build finishes, and remove or age-clean abandoned shadow files instead of resuming committed progress.

## What This Changes

Request durable checkpoint/resume support for long-running builtin memory indexing so interrupted reindexes do not restart from zero.

## Best Possible Solution

Adopt a maintainer-approved memory-core design that stores durable generation/progress state in SQLite, resumes or safely discards incomplete shadow builds, reports incomplete status honestly, and avoids new `memorySearch` config unless maintainers choose it.

Kind: product_direction

Question: What durable checkpoint/resume design should builtin memory-core use for interrupted full reindexes?

Rationale: The source-proven gap is real, but the permanent fix changes persisted memory-index state, search/status semantics during incomplete generations, and possibly public config defaults, which are maintainer product/API choices.

Likely owner: steipete

Owner reason: The safe reindex and atomic-helper history makes steipete the strongest routing candidate for the design tradeoff.

Owner confidence: high

Options:

- **SQLite-backed resume state (recommended):** Persist generation/progress metadata in the memory-owned SQLite schema, resume compatible interrupted shadow builds, and keep search/status on the last complete generation until publish succeeds.
- **Retry and cleanup only:** Keep the current atomic full-rebuild model and limit this issue to better retry, stale-shadow cleanup, and status diagnostics, accepting that process death restarts from zero.
- **Require explicit config design first:** Pause implementation until maintainers decide whether checkpoint intervals or resume behavior should become public `memorySearch` configuration.

## Reproduction Assessment

Yes at source level: current main creates a fresh shadow reindex database, builds the full index before publishing, and removes or later cleans shadow files instead of resuming them. I did not run a live kill-and-restart repro in this read-only review.

## Solution Assessment

Unclear as proposed: checkpoint/resume is the right product direction, but the specific config and partial-index semantics need maintainer design. A SQLite-backed generation/progress model that preserves atomic publish is the safer end state.

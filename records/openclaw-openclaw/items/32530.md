- `P2`: This is a normal-priority multi-agent ergonomics feature with real security and live-routing design impact but no current outage or blocked first-run flow.
- `impact:security`: The proposed scanner would decide which external workspace config files are trusted enough to affect agent behavior, tools, model selection, and paths.

- `maturity:stable`: The issue touches Gateway runtime agent/config RPC behavior, and `gateway-runtime` is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and the latest release still have explicit agent registration plus manual Gateway agent mutation APIs, but no trusted external-workspace agent-config discovery path; the remaining work needs product and security direction before implementation.

## What This Changes

Request auto-discovery of agent configuration files from configured external workspace directories instead of requiring every agent to be registered manually in central config.

## Best Possible Solution

Define the trusted discovery model first; if accepted, implement a narrow opt-in scanner with deterministic precedence, validation, diagnostics, live reload semantics, and docs, otherwise keep improving explicit hot agent management.

Options:

- **Design trusted discovery first (recommended):** Keep this issue open while maintainers define trusted roots, file format, precedence, reload/removal behavior, diagnostics, and security constraints before implementation.
- **Prefer explicit hot management:** Close or narrow scanner work and invest in `agents.create/update/delete`, CLI, and Gateway hot reload so operators can add agents without external config scanning.
- **Move to extension convention:** Keep core lean by documenting a plugin or workspace convention for external tooling to generate central `agents.list` entries without making runtime scan arbitrary workspaces.

## Solution Assessment

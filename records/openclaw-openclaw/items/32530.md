## Summary

Keep open: current main and the latest release still rely on explicit configured agents and explicit agent-management RPCs, while the requested trusted external-workspace config discovery remains a product and security-boundary decision.

## What This Changes

The issue requests automatic discovery and loading of agent configurations from external workspace directories instead of requiring every agent in central config.

## Best Possible Solution

Maintain explicit registration by default unless maintainers first design a trusted discovery contract covering roots, precedence, validation, reload semantics, and security proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add core trusted workspace-agent discovery, or keep agent registration explicit through agents.list and agents.create/update/delete unless a narrower missing API is identified?

Rationale: This is not a broken existing contract; it adds config surface, filesystem scanning, live routing semantics, and security trust boundaries that repository policy reserves for maintainer product/security intent.

Likely owner: Peter Steinberger

Owner reason: Peter Steinberger introduced the agent-list discovery tool and has the strongest history signal for deciding the model-visible multi-agent discovery boundary.

Owner confidence: medium

Options:

- **Keep Explicit Registration (recommended):** Continue using central config and explicit agent-management RPCs, and document or improve that path before adding filesystem discovery.
- **Design Trusted Discovery:** Define a core discovery contract with trusted roots, file schema, conflict precedence, reload behavior, and security validation before implementation.
- **Defer To Plugin Or Tooling:** Leave external workspace scanning to operator tooling or a plugin until a concrete missing OpenClaw extension API is identified.

## Reproduction Assessment

Yes at source level: current main derives agents from explicit agents.list entries plus explicit agent RPC/config mutation, and no agents.autoDiscover or workspace config-pattern surface exists. This is a missing feature, not a broken existing behavior reproduction.

## Solution Assessment

No for the proposed shape without design: glob-based auto-loading is plausible but not clearly the safest boundary. The safer path is to decide trusted roots, precedence, validation, reload behavior, and whether existing agents.create/update/delete should be extended first.

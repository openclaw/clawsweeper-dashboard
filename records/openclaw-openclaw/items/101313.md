## Summary

Keep this PR open: it fixes the earlier missing/NaN Content-Length and UTF-8 decoder issues, but the capped no-reader path still trusts an under-declared Content-Length and then materializes the full `arrayBuffer()` before truncating, so the central availability bug is not fully fixed.

## What This Changes

The PR exports `readResponsePrefix`, routes `readResponseBodySnippet` through it for no-reader responses, adds Content-Length/null-body guards, and updates focused infra tests.

## Best Possible Solution

Land one canonical fix that never calls whole-body fallbacks for capped no-reader responses, preserves UTF-8 truncation, and includes real after-fix proof.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes. Source inspection gives a high-confidence reproduction path: a no-reader Response-like object can declare `Content-Length: 50` while `arrayBuffer()` returns a much larger body, and PR head still allocates that whole buffer before truncation.

## Solution Assessment

No. The current approach is a useful subset mitigation, but the best fix is to fail closed or use a bounded source whenever a capped read has no stream reader instead of trusting a declared size before `arrayBuffer()`.

## Summary

The PR’s intent is useful, but the check-then-read implementation does not actually guarantee a bounded source read: the file can be replaced or enlarged after `statSync` and before `readFileSync`. It also still needs redacted real runtime proof that an oversized extension completes the Jiti fallback.

## What This Changes

The PR adds a 10 MiB pre-read size check for JavaScript extension sources and adds an oversized-source test that expects Jiti loading.

## Best Possible Solution

Read through one opened file descriptor and enforce the maximum while reading, then add a regression test for the check/read race or equivalent bounded-read contract and attach redacted terminal proof of a real oversized extension loading through Jiti.

## Reproduction Assessment

Yes, from source: change an extension path after `statSync` observes a small file but before `readFileSync` executes, and the second operation can read an arbitrarily larger file. This review did not execute that race in the read-only checkout.

## Solution Assessment

No. A separate path-level size check is not a reliable source-read bound; a descriptor-backed bounded read is the narrower solution that preserves the intended Jiti fallback while closing the check-to-use gap.

## Best Possible Solution

Land the strict lsof PID handling after exact-merge validation against current main, keeping diagnostics from fabricating PIDs and keeping cleanup fail-closed with fuser recovery where ownership cannot be trusted.

## Reproduction Assessment

Yes. Source inspection shows current main uses `Number.parseInt` on lsof `p` fields, so a malformed token such as `p111abc` is deterministically accepted as PID 111; I did not run a live malformed lsof stream in this read-only review.

## Solution Assessment

Yes. The best fix is to enforce the existing strict positive-integer contract at each lsof PID boundary, preserve socket evidence without fabricated PID identity, and fail closed in cleanup while keeping fuser recovery available.

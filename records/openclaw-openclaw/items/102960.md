## Summary

Keep open: current main and the latest release still derive numeric `toolSummary.failures` from a boolean `lastToolError` check, so the reported aggregate undercount is still present and narrow enough to fix.

## What This Changes

The issue asks for `toolSummary.failures` to report an actual per-attempt failed-tool count instead of a 0/1 value derived from `lastToolError`.

## Best Possible Solution

Preserve `failures` as a numeric trace field, tally each error-classified tool execution per attempt, keep `lastToolError` for terminal warning semantics, and add focused regression coverage for multi-failure turns.

## Repair Work Prompt

Fix `toolSummary.failures` so it is a real per-attempt count of error-classified tool executions, not a boolean derived from `lastToolError`. Likely approach: add attempt/subscription state for a tool failure count, increment it in `handleToolExecutionEnd()` when `isToolError` is true, reset it with the attempt state on compaction retry, carry it through `EmbeddedRunAttemptForRunner`, and pass it into `buildTraceToolSummary()`. Keep `lastToolError` behavior unchanged for terminal warnings and failure-signal logic. Preserve the existing `failures` numeric field; do not rename it or broaden this PR into the richer `agent_end`/`after_tool_call` payload work tracked separately. Add focused regression coverage that proves multiple failed tool calls in one attempt produce `failures > 1` while `calls` and `tools` remain correct.

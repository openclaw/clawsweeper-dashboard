## Label Justifications

- `P2`: The issue degrades bundled memory-core Dream Diary reliability for real installs, but core chat, cron dispatch, and normal agent workflows remain usable.
- `impact:data-loss`: The report describes generated narrative output being silently replaced by fallback stubs and later discarded.

## Summary

Keep open: current main and v2026.6.11 still use the fixed 60-second Dream Diary wait, the strict memory-core manifest still exposes only model under dreaming execution, and timeout/no-text fallback still cleans up accepted attempt sessions before any late successful output can be recovered. The open timeout PR overlaps, but it is timeout-only and does not settle queue-time accounting or timeout cleanup semantics.

## What This Changes

The issue asks OpenClaw to fix memory-core Dream Diary narrative timeout handling so queued runs, configurable execution timeouts, and late successful model output are handled without silently writing fallback stubs.

## Best Possible Solution

Define one maintainer-approved memory-core Dream Diary contract that wires timeout behavior through manifest/runtime, distinguishes queued versus executing deadlines, and preserves or intentionally terminates late successful output without misleading fallback telemetry.

## Label Justifications

- `P2`: Multiple live reports show Dream Diary output degrading to fallback entries while normal foreground use remains available.
- `impact:data-loss`: Generated narrative content can be replaced by a synthetic diary entry despite a successful underlying completion.
- `impact:session-state`: The failure path deletes accepted narrative sessions and can orphan or discard transcript-backed results.

## Summary

Keep open: current main still uses a fixed 60-second narrative wait, exposes no supported timeout setting, and writes a fallback before cleanup deletes accepted narrative sessions; the open timeout PR is useful but does not yet cover the full queue-time and successful-output-discard path.

## What This Changes

Report that Dream Diary narrative runs time out while queued or slow, cannot use the parsed timeout settings through supported configuration, and may discard output after fallback cleanup.

## Best Possible Solution

Keep the bounded detached queue, define the timeout boundary and late-result ownership explicitly, preserve a completed narrative when safe, and only then expose a documented, validated timeout control if maintainers choose an operator override.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should memory-core keep one fixed bounded narrative deadline, or support a bounded user-configurable/per-phase deadline while separating timeout cleanup from the ownership of an in-flight result?

Rationale: The implementation must choose a public plugin configuration contract and a deliberate lifecycle policy for runs that exceed the caller wait without treating the current fallback-and-delete sequence as an incidental implementation detail.

Likely owner: steipete

Owner reason: The choice changes bundled-plugin product policy and public configuration surface, and the available Dreaming and vision evidence points to this project-direction owner.

Owner confidence: low

Options:

- **Define lifecycle first, then bounded config (recommended):** Make timeout completion and session disposal non-destructive to a valid late result, then add a validated bounded timeout setting with focused upgrade and runtime proof.
- **Keep one fixed deadline:** Retain a global fixed limit but move queue admission outside the timed window and document that slow providers may receive a fallback after that bound.
- **Treat as performance-only:** Rely on the no-tools and concurrency work without adding timeout control, accepting that slow local and queued runs can still fall back at the fixed limit.

## Reproduction Assessment

Yes for the fixed-wait/configuration path: current main still passes the hardcoded 60-second value to the narrative wait, and a July 17, 2026 report reproduces the symptom on v2026.7.1. The provider-cancellation and fallback-result sequence needs a controlled current-main trace to prove its exact timing contract.

## Solution Assessment

No single partial fix is sufficient: the open timeout PR addresses supported configuration and propagation, while this issue also needs an explicit queue/deadline and post-timeout session-ownership design.

## Summary

This is a useful, well-proven fix, and the previously requested boundary tests are now present. One blocking gap remains: the new counter only recognizes tables whose delimiter rows start and end with pipes, so explicit card mode can still send six valid standard-Markdown tables and hit the same delivery failure.

## What This Changes

The PR adds a five-table limit guard at three Feishu static-card routing points and adds regression tests for card-versus-post routing.

## Best Possible Solution

Use one shared, parser-consistent Feishu static-card table counter in both routing modules, cover outer-pipe and no-outer-pipe syntax at the five/six boundary, and keep the unverified streaming CardKit path unchanged.

## Maintainer Decision

Yes—current main's static-card routing, the production 230099/11310 logs, and Feishu's documented five-table limit provide a high-confidence reproduction path using a reply with six tables. The no-outer-pipe variant is source-reproducible against the PR counter but was not shown in the supplied live proof.

## Solution Assessment

No, not yet. Preflight fallback at the static-card owner boundary is the right approach, but the limit check must share the renderer's supported table grammar rather than rely on a narrower duplicated regex.

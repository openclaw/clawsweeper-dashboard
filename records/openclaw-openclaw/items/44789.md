## Summary

Keep open: current main and the latest release still route the named LiteLLM interactive auth choice through the generic API-key setup, so it can preserve an existing base URL or fall back to localhost but does not prompt for the proxy URL before model selection.

## What This Changes

The issue requests restoring LiteLLM interactive onboarding so users can enter an API key, set the LiteLLM server URL, and choose from discovered models instead of getting only the default model.

## Best Possible Solution

Restore a safe provider-owned LiteLLM interactive setup path that collects or confirms the proxy URL before model selection, preserves existing base URLs, and clearly separates localhost defaults from remote-proxy discovery.

## Reproduction Assessment

Yes, at source level: selecting the named LiteLLM API-key path reaches the generic API-key prompt, then `applyLitellmConfig` preserves an existing URL or falls back to localhost and one default model. I did not run a live interactive TTY with a LiteLLM proxy.

## Solution Assessment

Unclear. A LiteLLM-specific URL prompt is a plausible fix, but maintainers should decide whether the durable shape is provider-owned setup metadata, reuse of the self-hosted/custom provider flow, or explicit live-discovery policy.

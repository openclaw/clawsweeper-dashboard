## Summary

The remaining question is a maintainer UX/API boundary decision, not a cleanup-close candidate.

## What This Changes

The issue asks for LiteLLM onboarding to collect the proxy URL and API key, then list discovered LiteLLM models instead of falling back to one default model.

## Best Possible Solution

Choose and implement one supported LiteLLM setup boundary: either add an interactive LiteLLM base-URL/model-discovery step, or make Custom Provider the documented remote LiteLLM proxy path in prompts and docs.

## Summary

Keep open: current main and v2026.6.11 still route the named LiteLLM interactive onboarding choice through the generic API-key path, so it prompts for a key, preserves an already configured URL or falls back to localhost, and then offers the single bundled default model instead of collecting a proxy URL first. The later non-interactive `--custom-base-url` fix is useful but only covers scripted setup, not the interactive flow reported here.

## What This Changes

The issue asks for LiteLLM onboarding to prompt for API key plus server URL and then populate model choices from the configured LiteLLM proxy.

## Best Possible Solution

Restore a safe LiteLLM interactive setup path that captures the proxy URL before model selection, preserves existing base URLs, keeps the scripted `--custom-base-url` path working, and adds coverage for localhost default, remote proxy, and model-picker behavior.

## Reproduction Assessment

Yes, at source level: selecting the LiteLLM API-key auth path enters the generic API-key prompt, then `applyLitellmConfig` preserves an existing URL or falls back to localhost and one default model. I did not run a live interactive TTY session against a LiteLLM proxy.

## Solution Assessment

Unclear: adding a LiteLLM-specific URL prompt may be the right fix, but maintainers should decide whether the durable shape is provider-owned setup metadata, reuse of the Custom Provider/self-hosted setup flow, or explicit live-discovery policy.

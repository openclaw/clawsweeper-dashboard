## Summary

Keep open: current main and v2026.6.11 still route the named LiteLLM interactive onboarding choice through the generic API-key path; only the non-interactive `--custom-base-url` case has shipped, so the interactive URL/model-selection gap remains and needs maintainer direction.

## What This Changes

The issue asks for LiteLLM onboarding to collect the proxy API key and server URL, then discover and present available models instead of defaulting to a single localhost-backed model.

## Best Possible Solution

Add a maintainer-approved LiteLLM interactive setup path that captures or confirms the proxy URL before model selection, preserves the shipped non-interactive flag behavior, and documents when to use LiteLLM versus Custom Provider.

## Summary

Keep open: current main and the latest release still leave the named LiteLLM interactive auth choice on the generic API-key path, so the reported URL/model setup gap remains real and needs maintainer direction rather than cleanup closure.

## What This Changes

The issue reports that interactive LiteLLM onboarding skips server URL configuration and falls back to a single model option instead of discovering models from the configured LiteLLM server.

## Best Possible Solution

Add a maintainer-approved LiteLLM interactive setup path that captures or confirms the proxy base URL before model selection, preserves existing/non-interactive behavior, and clearly documents when users should choose LiteLLM versus Custom Provider.

## Reproduction Assessment

Yes, at source level: selecting LiteLLM reaches the generic provider API-key method, which prompts for only the API key, and the LiteLLM config applier falls back to localhost plus one default model when no base URL already exists. I did not run a live interactive TTY/LiteLLM proxy session.

## Solution Assessment

Unclear. A LiteLLM-specific URL prompt may be correct, but maintainers should choose whether the best shape is provider setup metadata, reuse of Custom Provider, or an explicit credentialed discovery policy.

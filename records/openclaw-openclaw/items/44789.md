## Summary

Keep open: current main and v2026.6.11 still give the named LiteLLM onboarding choice only the generic API-key path, with localhost/default-model fallback unless a base URL already exists or the non-interactive custom-base-url flag is used. The remaining work needs maintainer UX/API direction rather than cleanup closure.

## What This Changes

The issue asks for interactive LiteLLM onboarding to prompt for the proxy URL/API key and list available models instead of falling back to localhost and one default model.

## Best Possible Solution

Add a maintainer-approved LiteLLM interactive setup path that captures or confirms the proxy base URL before model selection, or clearly make Custom Provider the supported remote LiteLLM proxy path in prompts and docs.

## Maintainer Decision

Required: true

Question: Should the named LiteLLM onboarding choice grow its own interactive base-URL and model-discovery setup, or should remote LiteLLM users be routed to the existing Custom Provider path?

Rationale: Both outcomes are technically plausible, but the choice changes provider-owned onboarding UX, credentialed endpoint probing, and the boundary between bundled provider setup and generic custom endpoints.

Likely owner: steipete

Owner reason: steipete owns the recent LiteLLM pluginization and non-interactive custom-base-url behavior that shape the decision point.

Owner confidence: high

Options:

- **Add LiteLLM URL Prompt (recommended):** Have litellm-api-key ask for or confirm the proxy base URL before model selection while preserving non-interactive --custom-base-url behavior.
- **Route To Custom Provider:** Keep LiteLLM as localhost/default-model setup and update prompts/docs so remote LiteLLM proxies use Custom Provider.
- **Wait For Catalog Policy:** Defer this until maintainers settle the broader credentialed model-discovery contract for provider plugins.

## Reproduction Assessment

Yes, at source level: selecting LiteLLM reaches the generic provider API-key method, and the LiteLLM config applier falls back to localhost plus one default model when no base URL already exists. I did not establish a live interactive LiteLLM proxy run in this read-only review.

## Solution Assessment

Unclear until maintainers choose the boundary. A LiteLLM-specific URL prompt may be the best user fix, but routing remote proxies to Custom Provider could also be intentional if documented in the picker and provider docs.

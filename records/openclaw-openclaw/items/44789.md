## Summary

Keep open: current main still routes LiteLLM interactive onboarding through the generic API-key auth method, so remote LiteLLM proxy users can still miss the proxy URL setup and fall back to the localhost default plus one seeded model.

## What This Changes

The issue asks for LiteLLM onboarding to prompt for API key, proxy server URL, and usable model selection instead of skipping URL setup.

## Best Possible Solution

Add a maintainer-approved LiteLLM setup path that captures or confirms the proxy base URL before model selection, while preserving Custom Provider and non-interactive `--custom-base-url` paths.

Rationale: Both directions can solve the user problem, but they set different provider-owned setup UX, endpoint probing, and model-catalog ownership boundaries.

Options:

- **Add LiteLLM URL Prompt (recommended):** Have LiteLLM interactive onboarding ask for or confirm the proxy base URL before model selection while keeping non-interactive URL support intact.
- **Route To Custom Provider:** Keep `litellm-api-key` as localhost/default-model setup and update prompts or docs so remote proxy users choose Custom Provider for URL and model setup.
- **Defer To Dynamic Catalog:** Leave this issue open until the broader credentialed `/v1/models` catalog policy in https://github.com/openclaw/openclaw/issues/74481 is settled.

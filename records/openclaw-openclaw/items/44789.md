## Summary

Keep open: current main and v2026.6.11 still leave the named LiteLLM interactive onboarding choice on the generic API-key path, so the URL/model-selection gap remains even though the related non-interactive `--custom-base-url` bug was carried forward.

## What This Changes

The issue asks for LiteLLM interactive onboarding to prompt for the proxy URL/API key and populate available models instead of defaulting to localhost with one model.

## Best Possible Solution

Add or document a maintainer-approved LiteLLM setup boundary that captures a proxy base URL before model selection while preserving the existing non-interactive `--custom-base-url` behavior.

- **Defer Dynamic Discovery:** Leave the issue open until the broader credentialed provider catalog and discovery policy is settled.

## Reproduction Assessment

Yes, at source level: selecting LiteLLM reaches the generic provider API-key method, which prompts only for the API key, and the config applier falls back to localhost plus one default model when no base URL already exists.

## Solution Assessment

Unclear. A LiteLLM-specific URL prompt is plausible, but maintainers should choose whether the best permanent shape is provider setup metadata, reuse of Custom Provider, or an explicit credentialed discovery policy.

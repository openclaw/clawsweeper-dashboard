## Summary

Keep open: current main still routes LiteLLM interactive onboarding through the generic API-key/default-model path, so a remote LiteLLM proxy user can miss the base URL setup and fall back to the localhost default plus the seeded model list. The existing Custom Provider and non-interactive custom-base-url paths are useful workarounds, but they do not fully satisfy the LiteLLM-specific interactive onboarding behavior reported here.

## What This Changes

The issue requests that LiteLLM onboarding prompt for API key and server URL before discovering and selecting the default model.

## Best Possible Solution

Make LiteLLM remote-proxy setup explicit in the supported onboarding surface, preferably in the LiteLLM plugin or a generic provider setup seam, with catalog discovery using the chosen URL before default-model selection.

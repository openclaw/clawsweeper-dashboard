## Summary

Current and released code do evaluate a cached ESM import expression for every accepted gateway request, but the report does not demonstrate that this is a material latency or CPU problem. The surrounding lazy-loading architecture is intentional startup-performance work, so this should remain open only as a low-priority, benchmark-first cleanup rather than accepting the proposed static import.

## What This Changes

## Best Possible Solution

Add a repeatable warmed-dispatch benchmark first; if it shows a meaningful improvement, cache the `server-methods.js` import promise at message-handler module scope while retaining lazy WebSocket loading, current error responses, and the startup import-boundary test.

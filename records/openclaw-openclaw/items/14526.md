## Summary

Current main and v2026.6.11 substantially improve staged updates, repair, restart verification, and backup integrity, but the requested update-coupled snapshot, retention, real channel/agent checks, and automatic package-plus-state restoration remain missing. The issue should stay open for an explicit product and security decision.

## What This Changes

Add an opt-in safe-update transaction that snapshots critical state, verifies gateway, channel, and agent behavior after updating, and rolls back code plus state when validation fails.

## Best Possible Solution

Implement a phased core safe-update transaction with a versioned rollback manifest: verify a protected snapshot, record package and schema versions, use the existing staged updater, run doctor and plugin convergence plus non-destructive health checks, automatically reverse only proven-safe transitions, and otherwise provide a guided offline restore path with bounded retention and secret-safe permissions.

## Risks / Open Questions

- Automatic restoration could pair an older binary with state already migrated to a newer schema or overwrite valid post-update writes unless rollback eligibility is versioned and transactionally recorded.
- Broad snapshots contain credentials, auth profiles, sessions, and plugin state, making automatic retention or remote destinations high-value secret archives.
- Channel and real-agent smoke turns may send visible messages, spend provider quota, mutate sessions, or invoke tools unless they use explicit non-destructive contracts.
- The permanent process owner remains unresolved: the workflow could live in the current CLI handoff or a future external updater, but must not create competing update engines.

- **[P1] Keep suppression out of the exported formatter:** `src/pairing/pairing-messages.ts:10-13`
  - body: `buildPairingReply` is exported through the plugin SDK on current main, so widening it to `string | null` makes every external or bundled caller handle silent suppression.   - confidence: 0.91
- **[P1] Wire advertised config through strict schemas:** `src/config/types.discord.ts:223-224`
  - body: This adds `unpairedResponse` to public Discord/Slack/LINE type and help surfaces, but the matching strict schemas on the branch do not all accept the field. Operators can configure the documented key and then fail validation or get no behavior change.
  - confidence: 0.9
- **[P1] Pass the response mode into IRC pairing replies:** `src/config/zod-schema.providers-core.ts:1081`
  - body: The branch exposes `channels.irc.unpairedResponse`, but the IRC runtime still calls `buildPairingReply` without `mode`, and the plugin-local strict schema omits the field. `silent` and `code-only` are therefore rejected or ignored for IRC.
  - confidence: 0.88
- **[P2] Honor silent mode for pending Discord pairings:** `src/discord/monitor/agent-components.ts:533-540`
  - body: When a Discord component user already has a pending pairing request, this path still sends the hardcoded `Pairing already requested` response even if `unpairedResponse` is `silent`. That leaks a reply on the repeat-attempt path the new mode is supposed to suppress.
  - confidence: 0.87
- **[P3] Record outbound activity only after sending:** `extensions/nextcloud-talk/src/inbound.ts:187-192`
  - body: Nextcloud Talk updates `lastOutboundAt` even when `buildPairingReply` returns no text and no message is sent. Move the status update inside the send guard so silent mode does not look like an outbound delivery.
  - confidence: 0.82

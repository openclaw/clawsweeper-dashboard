## Summary

Keep open: current main still runs the silent agentic memory flush only in the reply/compaction maintenance path, while reset rollover clears or replaces session state and emits lifecycle hooks without giving the agent the requested pre-reset memory turn. The remaining work needs maintainer product and security direction rather than cleanup closure.

## What This Changes

The issue requests a silent, tool-capable memory-flush agent turn before manual `/new`/`/reset` and automatic daily/idle session rollovers destroy the current session.

## Best Possible Solution

Define one maintainer-approved reset-lifecycle memory preservation policy covering explicit, daily, and idle rollovers, with opt-out/config, timeout, dedupe, sandbox, consent, audit, and plugin-hook boundaries before implementation.

Rationale: The source-level gap is clear, but the permanent behavior changes reset latency, silent model/tool execution, durable memory retention, plugin boundaries, and security expectations, so automation should not choose the policy alone.

Likely owner: steipete

Owner confidence: high

Options:

- **Define a bounded pre-reset flush (recommended):** Approve an explicit reset-memory policy with timeout, dedupe, opt-out/config, audit, sandbox, and security constraints before implementation.
- **Keep reset persistence mechanical:** Treat session-memory hook improvements such as PR #61675 as the supported reset boundary and narrow or reject silent agent execution on reset.
- **Push continuity to memory plugins:** Require memory plugins or MCP-backed memory services to own continuous persistence and extend only missing core lifecycle events or APIs.

Unclear. Reusing the compaction flush machinery is plausible, but blocking/background behavior, config defaults, plugin contracts, and silent tool-execution security boundaries need maintainer selection first.

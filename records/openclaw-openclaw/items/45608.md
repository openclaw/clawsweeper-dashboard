## Label Justifications

- `P2`: The issue reports a real session-memory preservation gap with broad but non-emergency impact and a product/security decision before implementation.
- `impact:session-state`: The requested behavior changes how session context and memory survive manual and automatic session replacement.
- `impact:data-loss`: Without a reset-time preservation path, useful in-session context can be archived or lost before the agent curates durable memory.
- `impact:security`: The proposed fix would silently process and persist private transcript content through model/tool-capable memory maintenance.

## Summary

Keep open: current main still has only compaction-threshold agentic memory flush plus command/background reset hooks; it does not run the same silent agent turn before manual, daily, or idle reset destroys the old session. The remaining choice is product/security-sensitive, so this should stay with maintainer review rather than be closed or queued as an autonomous fix.

## What This Changes

Request a silent agentic memory flush before `/new`, `/reset`, and daily/idle reset rollovers so durable memory is curated before the session is replaced.

## Best Possible Solution

Define a guarded reset-memory lifecycle contract, likely opt-in at first, that reuses the memory plugin/flush capability or an explicit core seam with timeout, provider/privacy, audit, and dedupe rules across manual, daily, and idle resets.

## Maintainer Decision

Kind: security_boundary

Question: Should OpenClaw run a silent agentic memory flush before manual and automatic session resets, and if so what default, timeout, provider/privacy, and plugin-boundary contract should own it?

Rationale: The source-level gap is clear, but the fix would add silent tool-capable model execution at a destructive lifecycle boundary and may require new config or plugin API behavior; automation should not choose that security/product boundary.

Likely owner: steipete

Owner reason: They introduced both the original pre-compaction flush and `/new` reset behavior, making them the best available owner for the cross-boundary product/security decision.

Owner confidence: high

Options:

- **Design guarded opt-in contract (recommended):** Add reset-time agentic flush only behind an explicit lifecycle contract with timeout, audit/redaction, provider routing, empty-session skips, and regression tests for `/new`, `/reset`, daily, and idle rollover.
- **Land hook-only preservation first:** Treat the open daily/idle hook PR as the near-term path and defer agentic flush until after hook dedupe and privacy behavior are proven.
- **Keep reset memory plugin-owned:** Require memory plugins or ClawHub packages to own reset persistence unless they can show a missing generic core/plugin API.

## Reproduction Assessment

Yes. Source inspection on current main shows `runMemoryFlushIfNeeded` is only called from the reply/compaction flow, while manual and daily/idle reset paths mint replacement sessions and emit hooks without running an agentic memory flush.

## Solution Assessment

Unclear. Reusing the compaction flush machinery is plausible, but the best fix needs maintainer choices about blocking versus background execution, opt-in configuration, privacy/provider routing, and whether the memory plugin API or core reset path owns the contract.

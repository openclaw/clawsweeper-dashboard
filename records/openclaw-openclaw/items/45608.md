## Label Justifications

- `P2`: The issue affects normal memory/session continuity and needs product/security design, but it is not an immediate core-runtime outage.
- `impact:data-loss`: The report is about learned context and curated memory being lost when sessions reset before an agent can persist it.
- `impact:session-state`: The affected surface is reset-time session rollover across session IDs, transcripts, hooks, and memory state.
- `impact:security`: The requested fix would run silent tool-capable agent work that can persist workspace or session context at a lifecycle boundary.

## Summary

Keep open: current main still keeps reset rollover separate from the agentic memory-flush path. Reset paths preserve some transcript and plugin-hook context, but they do not run a silent tool-capable pre-reset agent turn, so the remaining work needs maintainer product and security policy.

## What This Changes

Request a silent agentic memory flush before `/new`, `/reset`, daily reset, and idle reset replace the current session so curated memory can survive session rollover.

## Best Possible Solution

Define one maintainer-approved reset-memory lifecycle covering explicit, daily, and idle rollovers, with timeout, dedupe, audit, consent, plugin, security, and config boundaries before implementation.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw run a silent tool-capable memory-flush agent turn before explicit, daily, and idle resets, and what default/config/security contract should govern it?

Rationale: The source-level gap is clear, but the permanent behavior affects latency, cost, silent agent execution, provider/auth selection, sensitive memory persistence, and plugin boundaries, so automation should not choose the policy alone.

Likely owner: steipete

Owner reason: They have the strongest combined history on both the existing pre-compaction flush primitive and `/new` reset behavior that this decision spans.

Owner confidence: high

Options:

- **Approve guarded opt-in pre-reset flush (recommended):** Add a reset-scoped agentic flush behind an explicit or clearly documented config/policy with timeout, dedupe, sandbox, consent, and audit requirements.
- **Keep reset persistence mechanical:** Treat session-memory/reset-hook improvements as the supported reset boundary and narrow this issue away from silent tool-capable agent execution.
- **Delegate to memory plugins:** Require memory plugins or MCP-backed services to own continuous persistence and extend core lifecycle APIs only where current hooks are insufficient.

## Reproduction Assessment

Yes. Source inspection shows reset rollover and the agentic memory-flush execution are separate current-main paths, so explicit or stale reset can rotate the session without invoking a pre-reset agent write.

## Solution Assessment

Unclear. Reusing `runMemoryFlushIfNeeded` is plausible, but the best fix depends on maintainer choices for blocking versus background execution, config defaults, plugin boundaries, provider/auth routing, and security policy.

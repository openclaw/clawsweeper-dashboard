## Summary

Keep open: current main and the latest release still separate reset rollover from the silent tool-capable memory flush, so the requested reset-time agentic curation remains unresolved and needs maintainer product/security direction.

## What This Changes

The issue requests a silent agentic memory flush before `/new`, `/reset`, daily reset, and idle reset destroy the current session.

## Best Possible Solution

Define one maintainer-approved reset-lifecycle memory preservation design covering explicit, daily, and idle rollovers with clear latency, consent, sandbox, audit, and plugin/config boundaries.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw run a silent tool-capable memory-flush agent turn before explicit, daily, and idle resets, and what blocking/background/config rules should constrain it?

Rationale: The source gap is clear, but the permanent behavior affects reset latency, silent tool execution, durable memory persistence, and plugin/config contracts, so automation should not choose the policy alone.

Likely owner: steipete

Owner reason: The strongest history trail connects this decision to the original reset behavior and the pre-compaction flush primitive.

Owner confidence: high

Options:

- **Approve bounded pre-reset flush (recommended):** Define a reset-memory policy with timeout, dedupe, opt-out/config, audit, and security constraints before implementation.
- **Keep reset persistence mechanical:** Treat session-memory hook improvements such as https://github.com/openclaw/openclaw/pull/61675 as the supported reset boundary and narrow this issue away from silent agent execution.
- **Defer to memory plugins:** Require memory plugins or MCP-backed memory services to own continuous persistence and only extend core events where current plugin APIs are insufficient.

## Reproduction Assessment

Yes. Source inspection shows explicit and stale reset paths can mint a new session and clear memory-flush metadata without invoking `runMemoryFlushIfNeeded`; the issue is source-reproducible without running a live channel.

## Solution Assessment

Unclear. Reusing the existing memory-flush turn is plausible, but the best fix depends on maintainer choices about blocking vs background execution, config defaults, plugin event ownership, and security boundaries.

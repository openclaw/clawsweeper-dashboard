## Label Justifications

- `P2`: The issue affects real session continuity and memory preservation, but the remaining work is product/security-sensitive rather than an emergency runtime outage.
- `impact:session-state`: The reported gap is about session rollover losing the agent's opportunity to carry curated context into future sessions.
- `impact:data-loss`: Important learned context can be discarded at reset boundaries when it has not reached compaction or been manually written to memory.
- `impact:security`: The proposed automatic flush would process and persist potentially sensitive transcript content during reset lifecycle handling.

## Summary

Keep open: current main still limits the agentic memory flush to the post-turn compaction/threshold path, while explicit and stale daily/idle resets rotate the session first and only have mechanical or lifecycle hook surfaces.

## What This Changes

Request to run a silent agentic memory flush before `/new`, `/reset`, daily reset, and idle reset rotate or destroy the current session.

## Best Possible Solution

Define one maintainer-approved reset-memory lifecycle that covers explicit, daily, and idle resets with bounded execution, privacy-safe defaults, docs, and regression coverage, then wire the agentic flush or a selected plugin API through that lifecycle.

## Reproduction Assessment

Yes at source level. Current main shows reset rollover and memory flush are separate paths: reset commits the new session before lifecycle hooks, while `runMemoryFlushIfNeeded` is only called from the normal reply runner.

## Solution Assessment

Unclear. An agentic pre-reset flush is plausible, but the best fix needs maintainer selection of blocking/background behavior, config/default policy, plugin API shape, and security boundaries before implementation.

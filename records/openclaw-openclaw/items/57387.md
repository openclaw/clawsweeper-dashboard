## Summary

Keep open. Current main has Gateway auth, operator scopes, sessions visibility/allowlist controls, and inter-session provenance labels, but it still lacks the requested cryptographic sender verification, replay protection, verifier, and key lifecycle for `sessions_send`; the IdentyClaw ClawHub plugin/skill is useful workaround evidence, not a core close reason.

## What This Changes

Request HMAC/token-based mutual authentication for `sessions_send` so receiving sessions can verify the claimed sender in multi-agent deployments.

## Best Possible Solution

Define a maintainer-approved inter-session auth contract at the Gateway/session boundary, with signed envelopes or scoped-token verification, replay handling, key lifecycle, default/migration behavior, docs, and regression coverage; keep external identity plugins as optional workarounds until that contract exists.

## Reproduction Assessment

Yes for source inspection: current main accepts `sessions.send` without HMAC/signature fields and `sessions_send` records provenance rather than verifying a cryptographic sender. I did not run a live exploit scenario because the remaining question is product/security design, not whether these fields exist.

## Solution Assessment

Unclear. HMAC is a plausible minimum, but maintainers need to choose the durable contract among per-message signatures, scoped tokens, signed envelopes, or plugin/hook extension points before implementation.

## Summary

Keep open. Current main and v2026.6.11 still provide Gateway caller auth, `operator.write` scope, session visibility/A2A allowlists, and inter-session provenance, but not the requested per-message HMAC/token sender verification, replay protection, verifier, or key lifecycle; the IdentyClaw plugin/skill is useful workaround evidence, not a core close reason.

## What This Changes

The issue requests cryptographic sender verification for inter-agent `sessions_send` messages using per-session HMAC or token-based mutual authentication.

## Best Possible Solution

Define one maintainer-approved inter-session trust contract that composes provenance, sender authorization, replay protection, key lifecycle, scoped tokens, plugin workarounds, docs, and upgrade-safe defaults before implementation.

## Reproduction Assessment

Yes. Source inspection shows current main and v2026.6.11 accept and forward `sessions_send`/`sessions.send` messages with provenance and ordinary Gateway auth, but without a cryptographic per-message sender verifier or replay-proof payload.

## Solution Assessment

Unclear. HMAC is plausible, but maintainers need to choose the security model, token/key lifecycle, sender graph semantics, plugin/API boundaries, and compatibility behavior before a fix PR is safe.

## Summary

Keep this issue open: current main can repeatedly send pending draft updates without honoring the configured interval between successful sends. The report overstates event-loop blocking because each transport await yields, but the underlying throttle-bypass concern is valid from source inspection. ([github.com](https://github.com/openclaw/openclaw/blob/main/src/channels/draft-stream-loop.ts))

## What This Changes

Bound successive draft-stream flush iterations so continuously arriving text cannot bypass the configured transport throttle.

## Best Possible Solution

Enforce the configured minimum interval inside the canonical loop between successive successful transport writes, while preserving stop, retry, explicit flush, and finalization behavior; add a controlled-promise regression test for continuously arriving updates.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes at source level for the throttle bypass: repopulating `pendingText` during each awaited send keeps `flush()` chaining without consulting the configured delay. The stronger claim that this blocks the JavaScript event loop is not reproduced because each awaited transport promise yields.

## Solution Assessment

No, an arbitrary batch or wall-clock cutoff is only a mitigation. Applying the existing throttle contract between loop iterations is narrower and avoids leaving pending final text undrained.

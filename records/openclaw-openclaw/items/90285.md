## Summary

Keep open: current main still has internal cron running-state reservations and store-locked mutation paths, but it does not expose the requested public claim/lease, CAS-aware `cron rm`, claim-conflict exit code, or documented single-flight contract.

## What This Changes

The issue requests a new public cron dispatch/removal precondition contract so external automation can safely retire scheduled jobs while the scheduler may be dispatching them.

## Best Possible Solution

Pick one additive public cron precondition contract, preferably the narrowest remove/CAS shape maintainers will support, then align the Gateway schema, service result, CLI help, docs, and concurrency tests around it.

## Maintainer Decision

Question: Which public cron dispatch/removal contract should OpenClaw support for jobs that may be in-flight: a narrow CAS/if-unclaimed remove, a full lease-token claim API, or no new core API for now?

Rationale: The implementation is not blocked by a narrow code location; it is blocked by public RPC, CLI, stored-state, and exit-code semantics that need maintainer intent before automation should change core cron behavior.

Likely owner: steipete

Owner confidence: medium

Options:

- **Add narrow remove preconditions (recommended):** Add `cron rm --if-unclaimed` or an expected-state/version check around existing `runningAtMs` state, with a documented conflict result and focused concurrency tests.
- **Design full lease tokens:** Expose claim tokens, expiry, holder metadata, and lease validation through show/remove/run paths, accepting a broader API and persisted-state contract.
- **Decline core API for now:** Keep the existing internal scheduler reservations and require external systems to remain idempotent until a stronger core use case is accepted.

## Solution Assessment

Unclear until maintainers choose the public contract. A narrow additive CAS or `--if-unclaimed` remove path looks smaller than a full lease-token system, but either choice defines public cron API behavior.

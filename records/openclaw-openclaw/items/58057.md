## Summary

## What This Changes

The issue requests dynamic DM/group sender authorization for allowlists, including HTTP or hook-backed identity resolution and optional unknown-sender routing.

## Best Possible Solution

Define a maintainer-approved dynamic authorization contract in the shared channel ingress/access-group layer, with fail-closed behavior, iMessage integration, docs, and focused security regression coverage.

Rationale: The need is valid, but the permanent API changes config, plugin SDK, channel authorization, and security failure semantics in ways automation should not choose alone.

Options:

- **Extend ingress access groups (recommended):** Add a shared dynamic access-group resolver contract with explicit fail-closed semantics, then wire iMessage or plugin-owned resolvers through that seam.
- **Add dynamic policy modes:** Add dmPolicy/groupPolicy dynamic plus resolver config directly, accepting a larger config surface and possible overlap with access groups.
- **Decline core resolver:** Keep current static access groups and pairing behavior, and require external operators to sync allowFrom through existing config or plugin-specific tools.

## Reproduction Assessment

Yes, at source level: current config/schema and shared ingress policy only accept static DM/group policy values, and iMessage drops or pairs unauthorized senders before dispatch. I did not run a live channel repro because this review is read-only.

## Solution Assessment

Unclear: the need is real, but HTTP resolver config, pre-allowlist hooks, unknown-sender routing, and dynamic access-group membership are different security/API shapes. The safest direction is a shared ingress/access-group seam rather than an ad hoc per-channel resolver.

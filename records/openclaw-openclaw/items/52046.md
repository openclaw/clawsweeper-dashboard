## Summary

Keep open: current main and v2026.6.11 still defer/retry heartbeat work through shared runner/wake paths and await the normal reply path, so the requested independent/non-blocking heartbeat execution model is not implemented. The related retry-cadence and default-isolation items cover narrower pieces, not this broader architecture decision.

## What This Changes

The issue requests running heartbeat checks outside the main message-processing path to avoid user-message delays during heartbeat execution.

## Best Possible Solution

Define and land a maintainer-approved heartbeat isolation model that keeps normal message delivery responsive while preserving session state, delivery ordering, retry semantics, and tool side-effect boundaries; keep narrower retry-cadence and default-isolation bugs on their own canonical items.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Partially: source inspection shows current main still defers/retries heartbeat work and awaits the normal reply path, but I did not establish a live transport reproduction of the exact visible stall duration.

## Solution Assessment

Is this the best way to solve the issue? Unclear: a background worker or separate execution lane is plausible, but the best fix needs a maintainer-defined isolation contract for session state, delivery ordering, retries, and tool side effects.

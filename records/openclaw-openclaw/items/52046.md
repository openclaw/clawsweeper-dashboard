## Summary

Keep open: current main and the latest release still run heartbeats through shared runner/wake/reply paths with skip-and-retry backpressure, so the requested non-blocking heartbeat execution model is not implemented. This remains a product/architecture item rather than a narrow scheduler bug.

## What This Changes

Request to run heartbeat checks without blocking normal message processing, likely via a separate worker or execution lane.

## Best Possible Solution

Keep this as the broad tracker for a maintainer-approved heartbeat isolation contract, with narrow retry-cadence work handled separately by the linked retry issue and PR.

Question: Should OpenClaw pursue a separate heartbeat execution lane or worker, or keep the current serialized/deferred heartbeat model with narrower retry and idle mitigations?

Rationale: Current code intentionally uses shared runner, wake, reply, session, and delivery paths; changing that boundary affects ordering, session state, and tool side effects, so automation should not choose the permanent architecture.

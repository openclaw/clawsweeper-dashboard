## Summary

Keep open: current main still exposes only singular `runId`/`clientRunId` on public Gateway agent/chat events, while merged queued execution can aggregate multiple submitted runs without carrying their original run IDs into the event payload.

## What This Changes

The issue requests original submitted run IDs on merged queued Gateway agent events so clients can correlate replies to each original message.

## Best Possible Solution

Add a maintainer-approved additive lineage field to Gateway agent/chat event contracts and propagate queued source run IDs from follow-up/collect aggregation without changing the canonical executed `runId`.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should merged queued Gateway events preserve the executed run ID and add an original/source run ID array, or should merged execution reuse one of the source run IDs as the public run ID?

Rationale: Current code retains queued identities internally, but exposing them changes a stable public Gateway event contract and the issue proposes multiple possible semantics that automation should not choose unilaterally.

Likely owner: steipete

Owner reason: The decision is about public Gateway event semantics and current Gateway protocol history points most strongly to steipete for product/API direction.

Owner confidence: medium

Options:

- **Add additive lineage array (recommended):** Preserve the executed `runId` and add a named array such as `originalRunIds` or `sourceRunIds` to public event schemas and projections.
- **Reuse one source ID:** Make merged execution appear under the first or last queued source ID, which may help simple clients but hides multi-source lineage and changes run identity semantics.
- **Keep current contract:** Leave clients to correlate through accepted/final events and session history, accepting that merged queued execution cannot be mapped one-to-one from live agent events.

## Reproduction Assessment

Yes, at source level. Current main tracks queued submitted run IDs internally, but public Gateway agent/chat schemas and event projections still expose only a singular run identity.

## Solution Assessment

Unclear until maintainers choose the API shape. An additive lineage field is the safest apparent direction; reusing a first or last queued ID would be a product semantics change.

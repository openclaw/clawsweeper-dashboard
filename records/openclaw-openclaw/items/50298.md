## Summary

Keep open: current main and v2026.6.11 still expose only singular Gateway `runId`/`clientRunId` values, while followup/collect queue paths retain original queued identities only for internal cancellation and lifecycle bookkeeping. The remaining work is a public Gateway event-contract decision, not a conservative cleanup close.

## What This Changes

The issue requests Gateway agent events to include the original `chat.send` run IDs when queued messages are merged into a later executed run.

## Best Possible Solution

Add a maintainer-approved additive lineage field to Gateway agent/chat events and propagate queued source run IDs from followup/collect aggregation while preserving the canonical executed `runId`.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should merged queued Gateway events preserve the executed `runId` and add an original/source run ID array, or should merged execution reuse one of the queued source run IDs as the public run ID?

Rationale: Current source can keep queued identities internally, but this issue proposes competing public API semantics on an M4 stable Gateway event contract.

Likely owner: steipete

Owner reason: This is a Gateway protocol/product semantics choice, and steipete is the strongest routing signal from issue timeline and Gateway history.

Owner confidence: medium

Options:

- **Add additive lineage array (recommended):** Preserve the executed `runId` and add a named array such as `sourceRunIds` or `originalRunIds` to public event schemas and projections.
- **Reuse one queued ID:** Make merged execution appear under the first or last queued source ID, simplifying some clients while hiding multi-source lineage.
- **Keep current contract:** Leave clients to correlate through accepted/final events and history, accepting that merged queued execution is not one-to-one in live events.

## Reproduction Assessment

Yes. Source inspection on current main shows queued identities are retained for internal cancellation/lifecycle paths, while public Gateway agent/chat schemas and projections expose only singular run identifiers.

## Solution Assessment

Unclear until maintainers choose the API shape. An additive lineage field appears safest because it preserves executed-run identity, while reusing first or last queued IDs would change public run semantics.

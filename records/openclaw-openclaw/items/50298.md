## Summary

Keep open: current main and the latest release still expose only singular `runId`/`clientRunId` on Gateway agent/chat events, while the steering queue keeps original queued `runIds` only for internal lease/ack handling. This remains valid core Gateway protocol work, but it needs maintainer API direction before implementation.

## What This Changes

The issue requests original queued run IDs on merged agent execution events so WebSocket clients can correlate replies to the original `chat.send` requests.

## Best Possible Solution

Add a maintainer-approved additive lineage field to Gateway agent/chat event contracts and propagate queued source run IDs from steering lease state into emitted events, with protocol/schema, projection, docs, and queue regression coverage.

## Reproduction Assessment

Yes. Source inspection on current main shows internal steering batches retain source `runIds`, while public Gateway agent/chat event schemas and projections expose only singular run identifiers.

## Solution Assessment

Unclear until maintainers choose the public API shape. An additive lineage field looks safer than overloading `runId`, while selecting the first or last queued ID would be a product decision.

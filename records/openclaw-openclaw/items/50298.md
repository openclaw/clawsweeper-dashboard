## Summary

Keep open: current main and latest release still expose only singular Gateway `runId`/`clientRunId` fields, while queued steering/collect paths can merge or route user turns in ways that leave external clients without original-run lineage.

## What This Changes

Request Gateway agent/chat events to include the original run ID set when queued messages are merged, steered, or processed under a later run.

## Best Possible Solution

Add a maintainer-approved additive lineage field to Gateway agent/chat event contracts and propagate queued source run IDs from steering/collect state into emitted events with focused regression coverage.

## Reproduction Assessment

Yes. Source inspection shows current Gateway event schemas and projections expose only singular run identifiers, while queue/steering code can merge or consume multiple queued run IDs internally.

## Solution Assessment

Unclear until maintainers choose the public API shape. An additive lineage field is safer than overloading `runId`, while selecting the first or last queued ID would be a product-level semantic change.

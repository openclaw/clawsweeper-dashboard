## Summary

Keep open: current main still exposes only singular Gateway run identifiers on public agent/chat events, while queued follow-up or collect aggregation can finalize the original client run and later execute under a different aggregate run without carrying the source run IDs.

## What This Changes

The issue requests preserving original queued chat.send run IDs on public Gateway agent/chat events when merged queued messages run under a different execution run ID.

## Best Possible Solution

Add a maintainer-approved additive lineage field to Gateway agent/chat event contracts and propagate queued source run IDs from follow-up/collect aggregation without changing the canonical executed runId.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should merged queued Gateway events preserve the executed runId and add an original/source run ID array, or should merged execution reuse one of the source run IDs as the public runId?

Rationale: Current code tracks queued identities internally, but this issue changes a stable public Gateway event contract and proposes competing API semantics that automation should not choose unilaterally.

Likely owner: steipete

Owner reason: The central decision is a public Gateway protocol/API contract question, and steipete has the strongest protocol and Gateway feature-history signal among the likely owners.

Owner confidence: high

Options:

- **Add additive lineage array (recommended):** Preserve the executed runId and add a named array such as originalRunIds or sourceRunIds to public event schemas and projections.
- **Reuse one source ID:** Make merged execution appear under the first or last queued source ID, which may help simple clients but hides multi-source lineage and changes run identity semantics.
- **Keep current contract:** Leave clients to correlate through accepted/final events and session history, accepting that merged queued execution cannot be mapped one-to-one from live agent events.

## Reproduction Assessment

Yes, from source inspection. Current main exposes only singular runId/clientRunId fields while queued follow-up admission finalizes the original client run and later aggregate execution owns a different run ID.

## Solution Assessment

Unclear until maintainers choose the API shape. An additive lineage field is the safest apparent direction because it preserves executed run identity while exposing source correlation.

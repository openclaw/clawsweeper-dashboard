## Summary

Keep open: current main and the latest release still expose only singular Gateway run identity on agent/chat event payloads, so merged queued turns still cannot carry the original queued run ID set requested for one-to-one client correlation.

## What This Changes

The issue asks for Gateway agent/chat events for merged queued messages to carry the original queued run ID set so clients can correlate replies to the original chat.send requests.

## Best Possible Solution

Define an additive Gateway event lineage contract for merged queued work, propagate the queued source run IDs into public agent/chat events, and preserve existing singular-run behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What public Gateway event contract should represent source-run lineage when multiple chat.send requests merge into one executed agent run?

Rationale: Current code can identify queued chat turns, but automation should not choose stable API semantics for field naming, ordering, duplicate handling, or whether public runId remains the execution ID.

Likely owner: steipete

Owner reason: steipete has the strongest recent-history and timeline signal for Gateway event semantics and queue behavior.

Owner confidence: high

Options:

- **Add a lineage array (recommended):** Keep runId as the executed/public run ID and add an ordered originalRunIds or sourceRunIds-style field to agent/chat events for merged work.
- **Reuse one source ID:** Make merged execution use the first or last queued runId as the public runId, which helps simple clients but loses full lineage.
- **Keep current contract:** Leave clients to correlate through accepted responses, session state, and history, accepting that live merged events have no source-run lineage.

## Reproduction Assessment

Yes. Source inspection shows collect/followup queue paths retain queued run IDs internally, while current Gateway agent/chat event schemas and projections expose only a singular public runId.

## Solution Assessment

Unclear until maintainers choose the API shape. An additive lineage field appears safest because it preserves existing runId semantics while giving clients exact correlation data.

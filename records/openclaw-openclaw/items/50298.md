## Summary

Keep open: current main and the latest release still expose only singular `runId`/`clientRunId` on public Gateway agent/chat events, while the steering queue keeps original queued `runIds` only for internal lease/ack handling. This remains valid core protocol work that needs maintainer API direction.

## What This Changes

The issue requests original queued run IDs on merged agent events so gateway clients can correlate replies to the submitted messages.

## Best Possible Solution

Maintainers should approve an additive queued-run lineage field for Gateway agent/chat events, propagate leased steering `runIds` into emitted events, and avoid overloading the primary `runId` with first/last-item semantics.

## Reproduction Assessment

Yes, at source level: current main keeps queued steering `runIds` internally but public Gateway agent/chat event schemas and projections expose only one run identifier. I did not run a live queued-message scenario because this review is read-only and the code contract is already clear.

## Solution Assessment

Unclear until maintainers choose the public API shape. An additive lineage field appears safer than selecting the first or last queued ID, because it preserves the primary run identity while exposing the original queued IDs for correlation.

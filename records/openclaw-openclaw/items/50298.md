## Summary

Keep open: current main still exposes only singular Gateway run identity on agent/chat event payloads, so merged queued turns still cannot carry the original queued run ID set requested for one-to-one client correlation.

## What This Changes

The issue asks Gateway agent events to preserve the original queued run IDs when multiple queued messages are merged and executed under a new run ID.

## Best Possible Solution

Define an additive Gateway event lineage contract for merged queued work, propagate the queued source run IDs from collection into public agent/chat events, and preserve existing singular-run behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What public Gateway event contract should represent source-run lineage when multiple chat.send requests merge into one executed agent run?

Rationale: Current code can identify queued chat turns, but the fix requires a stable API choice about field naming, ordering, duplicate handling, and whether public runId should remain the execution ID or become one of the source IDs.

Likely owner: steipete

Owner reason: steipete has the strongest recent-history and timeline signal for Gateway event semantics and queue behavior.

Owner confidence: high

Options:

- **Add a lineage array (recommended):** Keep runId as the executed run ID and add an ordered originalRunIds/sourceRunIds-style field to agent/chat events for merged work.
- **Reuse one source ID:** Make merged execution use the first or last queued runId as the public runId, which helps simple clients but loses full lineage.
- **Keep current contract:** Leave clients to correlate through accepted responses, session state, and history, accepting that live merged events have no source-run lineage.

## Reproduction Assessment

Yes. Source inspection shows collect-mode can aggregate multiple queued turns, while current Gateway agent/chat event schemas and projections expose only singular run identity with no original queued run ID set.

## Solution Assessment

Unclear until maintainers choose the API shape. An additive lineage field appears safest because it preserves existing runId semantics while giving clients exact correlation data.

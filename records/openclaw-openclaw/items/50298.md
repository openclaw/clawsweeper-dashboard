## Label Justifications

- `P2`: This is a normal-priority Gateway protocol improvement with real external-client routing impact, but it requires API/product direction rather than emergency runtime repair.
- `impact:message-loss`: Clients can mis-correlate or effectively lose replies when merged queued execution cannot be mapped back to the original submitted messages.
- `maturity:stable`: The affected Gateway runtime RPC/event surface is scored M4 Stable, including Gateway RPC APIs and Events.

## Summary

Keep open: current main and the latest release still expose singular Gateway `runId`/`clientRunId` event identifiers, while the merged steering queue preserves source `runIds` only internally. The remaining work is a real Gateway protocol/API design decision, not conservative cleanup.

## What This Changes

Request that merged queued-message execution events carry the original submitted run IDs so Gateway clients can correlate replies with the `chat.send` acknowledgements.

## Best Possible Solution

Add a maintainer-approved additive lineage field to Gateway agent/chat event contracts and propagate queued source run IDs from steering lease state into emitted events, with focused regression coverage and protocol docs if the public schema changes.

## Reproduction Assessment

Yes. Source inspection shows internal merged steering batches retain source `runIds`, while current main and `v2026.6.11` public Gateway agent/chat event schemas and projections expose only singular run identifiers.

## Solution Assessment

Unclear until maintainers choose the public API shape. An additive lineage field looks safer than overloading `runId`, while selecting the first or last queued ID would be a semantic product decision.

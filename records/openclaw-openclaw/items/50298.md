## Summary

Keep open: current main still exposes only singular `runId`/`clientRunId` on Gateway agent/chat events; queued steering keeps source `runIds` internally but does not propagate them to public events, so this remains valid Gateway protocol work needing maintainer API direction.

## What This Changes

The issue requests that merged queued message execution events expose the original `chat.send` run IDs so clients can correlate replies to submitted messages.

## Best Possible Solution

Add a maintainer-approved additive lineage field to Gateway agent/chat event contracts and propagate queued source run IDs from steering lease state into emitted events without changing the canonical executed `runId`.

Question: Should Gateway agent/chat events gain an additive original-run lineage field for merged queued work, and what exact field semantics should clients rely on?

Rationale: The implementation shape is clear, but the stable public Gateway event contract needs maintainer-owned naming and correlation semantics before automation changes it.

Likely owner: steipete

Owner reason: He appears in the feature history for the agent steering queue and is the strongest available routing owner for the public lineage decision.

Owner confidence: medium

Options:

- **Add additive lineage field (recommended):** Expose all original queued run IDs, such as `originalRunIds`, while keeping the executed `runId` unchanged for compatibility.
- **Canonicalize to one queued ID:** Select the first or last queued ID as the public run ID, trading simpler clients for ambiguous merged-message lineage.
- **Document existing correlation paths:** Leave events singular and direct clients toward history/idempotency correlation, which does not solve live merged-event correlation for this report.

## Reproduction Assessment

Yes. Source inspection on current main shows internal steering batches retain source `runIds`, while public Gateway agent/chat event schemas and projections expose only singular run identifiers.

## Solution Assessment

Unclear until maintainers choose the public API shape. An additive lineage field looks safer than overloading `runId` or selecting the first/last queued ID.

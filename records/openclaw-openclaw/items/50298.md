## Summary

Keep open: current main and v2026.6.11 still expose only singular `runId`/`clientRunId` on Gateway agent/chat events, while the steering queue retains original queued `runIds` only internally. The request is valid core Gateway protocol work, but it needs maintainer API direction before implementation.

## What This Changes

Request to expose the original queued run IDs in Gateway websocket agent events when merged queued messages execute under a different run ID.

## Best Possible Solution

Add a maintainer-approved additive lineage field to Gateway agent/chat event contracts and propagate queued source run IDs from steering/collect lease state into emitted events, with protocol/schema, docs, and regression coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What public Gateway event contract should represent merged queued-run lineage for clients: an additive original/source run ID array, one selected queued run ID, or a different correlation model?

Rationale: The code can carry the internal IDs, but the permanent API semantics affect stable Gateway events and downstream client correlation behavior.

Likely owner: steipete

Owner reason: Peter has the clearest feature-history connection to the steering queue and Gateway protocol surfaces that need the API decision.

Owner confidence: high

Options:

- **Additive lineage field (recommended):** Add a new optional array field such as `originalRunIds` or `sourceRunIds` while keeping the executed `runId` canonical.
- **Canonical queued ID selection:** Reuse the first or last queued run ID as the merged run identity, accepting that this changes current correlation semantics.
- **Defer protocol change:** Keep current events unchanged and document external clients must correlate by another supported surface until a broader telemetry design lands.

## Reproduction Assessment

Yes. Source inspection on current main shows public Gateway agent/chat event schemas and projections expose only singular run identifiers, while the steering queue and runner retain leased source `runIds` internally.

## Solution Assessment

Unclear until maintainers choose the public API shape. An additive lineage field looks safer than overloading `runId`, while selecting the first or last queued ID is a product semantics decision.

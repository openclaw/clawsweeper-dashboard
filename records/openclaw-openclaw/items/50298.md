## Summary

Keep open: current main still exposes only singular `runId`/`clientRunId` on public Gateway agent/chat event paths, while queued follow-up and collect internals do not publish the original source run ID set.

## What This Changes

The issue asks Gateway websocket events for merged queued messages to carry the original `chat.send` run ID set, or otherwise reuse a source run ID, so IM proxies can correlate replies to submitted messages.

## Best Possible Solution

Add a maintainer-approved additive lineage field to Gateway agent/chat event contracts and propagate queued source run IDs from collect/follow-up aggregation while preserving the canonical executed `runId`.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should merged queued Gateway agent/chat events preserve the executed run ID and add an additive original/source run ID array, or should merged execution reuse one of the source run IDs as the public run ID?

Rationale: Current code tracks enough queue lifecycle internally to explain the gap, but choosing public event semantics changes a stable Gateway API contract and should be a maintainer decision.

Likely owner: steipete

Owner reason: He is the strongest recent owner signal for the current Gateway event projection surface and public API landing decisions in this area.

Owner confidence: high

Options:

- **Add additive lineage array (recommended):** Preserve the executed `runId` and add a named array such as `sourceRunIds` or `originalRunIds` to public schemas and projections.
- **Reuse one source run ID:** Make merged execution appear under the first or last queued source ID, which helps simple clients but hides multi-source lineage and changes run identity semantics.
- **Keep singular contract:** Leave clients to correlate through final events and session/history data, accepting that merged queued execution is not one-to-one in live events.

## Reproduction Assessment

Yes for the source-level gap. Current main shows queued source identities are internal while public agent/chat schemas and projections expose only singular run identifiers.

## Solution Assessment

Unclear until maintainers choose the API shape. An additive lineage field appears safest, while reusing the first or last queued ID would change run identity semantics.

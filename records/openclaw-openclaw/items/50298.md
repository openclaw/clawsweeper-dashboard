## Summary

Keep open: current main still exposes only singular `runId`/`clientRunId` on Gateway agent/chat events, while collect-mode queue aggregation can complete multiple queued source identities without carrying those original IDs into the public event payload.

## What This Changes

The issue requests original queued `runId` lineage on Gateway/WebSocket agent events after queued messages are merged and processed.

## Best Possible Solution

Add a maintainer-approved additive lineage field to Gateway agent/chat event contracts and propagate queued source run IDs from follow-up/collect aggregation without changing the canonical executed `runId`.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should merged queued Gateway events preserve the executed run ID and add an original/source run ID array, or should merged execution reuse one of the source run IDs as the public run ID?

Rationale: Current code tracks queued identities internally, but this issue changes a stable public Gateway event contract and offers two different API semantics that automation should not choose unilaterally.

Likely owner: steipete

Owner reason: The current protocol/event lines and queue aggregation history route this public Gateway API decision most strongly to steipete.

Owner confidence: high

Options:

- **Add additive lineage array (recommended):** Preserve the executed `runId` and add a named array such as `originalRunIds` or `sourceRunIds` to public event schemas and projections.
- **Reuse one source ID:** Make merged execution appear under the first or last queued source ID, which may help simple clients but hides multi-source lineage and changes run identity semantics.
- **Keep current contract:** Leave clients to correlate through accepted/final events and session history, accepting that merged queued execution cannot be mapped one-to-one from live agent events.

## Reproduction Assessment

Yes. Source inspection on current main shows queued identities are retained for internal lifecycle/cancellation paths, while public Gateway agent/chat schemas and projections expose only singular run identifiers.

## Solution Assessment

Unclear until maintainers choose the API shape. An additive lineage field is the safest apparent direction, while reusing the first or last queued ID would be a product semantics decision.

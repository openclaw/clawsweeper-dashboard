- `impact:message-loss`: External clients can mis-correlate or effectively lose replies when merged queued execution cannot be mapped back to the original submitted messages.
- `maturity:stable`: The issue affects `gateway-runtime` / `Gateway RPC APIs and Events`, an M4 Stable surface with Stable 90/90 category scores.

## Summary

Keep open: current main still exposes singular Gateway `runId`/`clientRunId` values on agent and chat event surfaces, and queued collect/follow-up execution can still move later aggregate work onto a separate run identity without carrying the original queued run IDs.

## What This Changes

The issue requests that merged queued message execution expose the original `chat.send` run ID set in Gateway agent events so external clients can correlate replies to submitted messages.

## Best Possible Solution

Add a maintainer-approved additive lineage field to Gateway agent/chat event contracts and propagate queued source run IDs from collect/follow-up aggregation without changing the canonical executed `runId`.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should merged queued Gateway events preserve the executed `runId` and add an original/source run ID array, or should merged execution reuse one of the queued source run IDs as the public run ID?

Rationale: Current code can track queued identities internally, but the public Gateway event contract is stable and the issue proposes two different API semantics that automation should not choose unilaterally.

Likely owner: steipete

Owner reason: The current protocol/event lines and Gateway projection history most strongly route this API-shape decision to `steipete`.

Owner confidence: high

Options:

- **Add additive lineage array (recommended):** Preserve the executed `runId` and add a named array such as `originalRunIds` or `sourceRunIds` to public event schemas and projections.
- **Reuse a source run ID:** Make merged execution appear under the first or last queued source ID, which helps simple clients but hides multi-source lineage and changes run identity semantics.
- **Keep the current contract:** Leave clients to correlate through accepted/final events and history, accepting that merged queued execution cannot be mapped one-to-one from live agent events.

## Reproduction Assessment

Yes. Source inspection on current main shows queued identities are retained for internal cancellation/lifecycle handling, while public Gateway agent/chat schemas and projections expose only singular run identifiers.

## Solution Assessment

Unclear until maintainers choose the API shape. An additive lineage field is the safest apparent direction, while reusing the first or last queued ID would be a product semantics decision.

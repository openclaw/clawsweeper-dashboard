## Summary

Keep open: current main and the latest release still expose only singular Gateway `runId`/`clientRunId` event fields, while queued follow-up and steering paths can carry multiple original run IDs internally; the remaining work is a public API shape decision.

## What This Changes

Request to include the original queued run ID set in Gateway agent events when queued chat messages are merged or processed under modes such as steer/collect.

## Best Possible Solution

Add a maintainer-approved additive lineage field to Gateway agent/chat event contracts and propagate queued source run IDs from steering/collect state into emitted events with focused regression coverage.

## Reproduction Assessment

Yes. Source inspection shows current Gateway event schemas and projections expose only singular run identifiers, while queue/steering code can merge or consume multiple queued run IDs internally.

## Solution Assessment

Unclear until maintainers choose the public API shape. An additive lineage field is safer than overloading `runId` or selecting the first/last queued ID.

## Summary

Keep open: current main still lacks original queued-run lineage in public Gateway events; related merged work improved delivery and run-alias handling but does not solve multi-source correlation.

## What This Changes

Request that Gateway events for merged queued messages carry the original queued run IDs so clients can correlate replies to submitted messages.

## Best Possible Solution

Add a maintainer-approved additive lineage field to Gateway agent/chat event contracts and propagate queued source run IDs from follow-up/collect aggregation while preserving the executed run ID.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should merged queued Gateway events preserve the executed runId and add an original/source run ID array, or should merged execution reuse one queued source run ID as the public runId?

Rationale: Current code has enough internal queued-turn identity to design a fix, but the remaining choice changes a stable public Gateway event contract and should not be chosen by automation alone.

Likely owner: steipete

Owner reason: This is a public Gateway protocol/event semantics choice, and steipete is the strongest current-history signal for that surface.

Owner confidence: medium

Options:

- **Add additive lineage array (recommended):** Preserve the executed run identity and add a named field such as sourceRunIds or originalRunIds to public event schemas and projections.
- **Reuse one source ID:** Use the first or last queued source run ID as the merged public run ID, simplifying simple clients but hiding multi-source lineage.
- **Keep current contract:** Leave clients to correlate through accepted/final events and session history, accepting that merged queued execution has no live source-run lineage.

## Reproduction Assessment

Yes. Source inspection on current main shows queued identities are retained for internal lifecycle/cancellation paths, while public Gateway agent/chat schemas and projections expose only singular run identifiers.

## Solution Assessment

Unclear until maintainers choose the API shape. An additive lineage field is the safest apparent direction, while reusing the first or last queued ID would be a product semantics decision.

## Summary

Keep this PR open. It has strong real SQLite proof for recovery after a corrupted state write, but the central no-restart recovery claim remains incomplete because state reads retain the poisoned cached handle after a read-time corruption error.

## What This Changes

The PR centrally classifies SQLite corruption errors and evicts the cached shared state-database handle after a corrupted write so a repaired database can reopen without restarting the gateway.

## System Context

The shared state database persists gateway, channel, audit, and agent state. Gateway work opens a cached SQLite handle and uses it for both reads and write transactions, so a handle that remains open but has a poisoned pager can affect multiple product paths.

## Architecture Diagram

flowchart LR

  C --> D{Read or write operation}
  D --> E[SQLite corruption error]
  E --> F[Evict cached handle]
  F --> G[Reopen and integrity verification]
  G --> H[Recovered gateway state access]

## Best Possible Solution

Add an owner-safe corruption recovery mechanism that covers both shared-state reads and writes, with focused proof that a repaired file becomes usable through the affected read path; if maintainers intentionally limit recovery to the next write, narrow the title and user-impact contract accordingly.

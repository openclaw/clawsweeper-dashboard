## Label Justifications

- `P2`: This is a bounded cron performance defect that can cause latency or disconnections under large session/task loads but is not established as an emergency across normal deployments.
- `merge-risk: 🚨 availability`: The unconditional task snapshot adds synchronous work and a new task-store failure dependency to every reaper tick, which could stall or disrupt gateways after merge.

## Summary

Keep this PR open, but do not merge the current head: the one-shot batching direction is sound, yet the snapshot is now built unconditionally on every reaper sweep, adding a full task-registry scan even when no cron continuation needs it. The supplied gateway transcript also does not demonstrate the changed behavior under a representative populated workload.

## What This Changes

The PR adds a batched snapshot of pending generated-media session keys and changes the cron session reaper from repeated per-session task scans to set lookups.

## Best Possible Solution

Build the pending-media set lazily when the first cron continuation is encountered, reuse it for the rest of that sweep, add coverage proving zero registry scans without continuations and exactly one with multiple continuations, then provide redacted workload-specific runtime or profiling evidence.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes at source level: the prior loop conditionally called a helper that snapshots the global registry for each continuation row, establishing the repeated-scan path. A representative live current-main reproduction with event-loop measurements was not provided.

## Solution Assessment

No in its current form. Lifting the repeated scan is the correct boundary, but the snapshot should be lazy so sweeps without continuations retain the previous zero-scan behavior.

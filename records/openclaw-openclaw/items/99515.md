## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.91

Full review comments:

- **[P1] Preserve component media fanout:** `extensions/discord/src/outbound-payload.ts:227-234`
  - body: This new guard makes any Discord component/presentation payload with more than one `mediaUrls` entry throw before delivery. Current behavior, still covered by the unchanged adjacent test, sends the component message and then a media follow-up while preserving `replyTo`; merging this would turn those replies into hard failures.
  - confidence: 0.94
- **[P2] Batch plain mediaUrls before the fallback adapter:** `extensions/discord/src/outbound-payload.ts:177-186`
  - body: The new batch helper only runs inside the native components/embeds/filename branch. A normal payload with text plus `mediaUrls` and no Discord-specific channelData still returns through `sendTextMediaPayload`, which sends each URL through scalar `sendMedia`, so the common case for the linked feature remains unimplemented.
  - confidence: 0.92
- **[P2] Forward mediaUrls from Discord action entrypoints:** `extensions/discord/src/send.outbound.ts:41`
  - body: Adding `mediaUrls` to the low-level send options does not make the public Discord `send` or `sendMessage` actions accept it. Those action handlers still read only `mediaUrl`/`path`/`filePath`, so callers using `mediaUrls` through the documented action surface will not reach this new code.
  - confidence: 0.88
- **[P2] Retry each overflow batch independently:** `extensions/discord/src/outbound-payload.ts:100-113`
  - body: `sendDiscordMediaBatch` wraps one `sendMessageDiscord` call in the high-level retry helper, but `sendMessageDiscord` can post multiple batches for more than ten files. If a later batch hits a retryable error after the first batch succeeded, the outer retry can repost the earlier attachments and duplicate delivery.
  - confidence: 0.86

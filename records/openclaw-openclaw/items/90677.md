- `P2`: The issue blocks a scoped Google Chat multi-agent workflow but does not make ordinary Google Chat human-authored messages or the core runtime unusable.

## Summary

Keep open: current main and v2026.6.11 still require Google Chat to deliver a `MESSAGE` webhook before `allowBots` or bot-loop protection can run, and the docs still do not warn that peer Chat-app messages may never arrive. The existing `sessions_send` A2A path is a deliberate tool-routed mechanism, not the automatic same-chat Google Chat bridge requested here.

## What This Changes

The issue asks OpenClaw to document Google Chat's app-to-app delivery limitation and/or add a channel-independent path for two configured agents to converse without relying on Google Chat to emit peer app messages.

## Best Possible Solution

Document the Google Chat app-to-app event-delivery limitation now, and only add an opt-in bridge if maintainers choose a design that reuses the existing `sessions_send`, `tools.agentToAgent`, and `session.agentToAgent` safety boundaries.

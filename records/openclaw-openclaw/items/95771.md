## Summary

Keep open: the observability idea is focused, but the current patch still has a blocking diagnostic correctness issue and lacks after-fix real behavior proof. Current main clears unresolved cron retries through the existing cron guard, so the new transient-error warning would misstate the cron outcome as an error-backoff fallback.

## What This Changes

The branch adds cron warning logs and regression tests for paths where `nextRunAtMs` becomes `undefined` after completion, transient retry, or maintenance recompute.

## Best Possible Solution

Keep the observability work only after the transient-error warning matches the actual scheduling outcome and the contributor adds redacted real runtime or terminal proof.

## Reproduction Assessment

Yes. Source inspection shows the PR logs the transient-error warning when `normalNext` is undefined before the schedule-kind branch, while current main later clears cron schedules through `resolveCronNextRunWithLowerBound`.

## Solution Assessment

No. Adding warnings is a useful direction, but the transient-error warning should be schedule-specific or reworded, and malformed `every` schedule cases need to respect the validation/doctor boundary called out in related maintainer feedback.

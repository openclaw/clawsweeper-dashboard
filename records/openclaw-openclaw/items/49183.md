## Summary

Keep open: current main and v2026.6.11 have sender/group/provider/agent tool-policy primitives, but they still do not implement a scope-keyed bridge from Gateway operator scopes into agent tool access. The remaining work is a security/product decision about whether operator scopes should become a tool-policy input at all.

## What This Changes

The issue requests session-level tool policy controls that connect gateway operator scopes to agent tool access.

## Best Possible Solution

Approve a typed scope-aware tool-policy contract only after maintainers settle the threat model, config location, precedence with sender/group/agent policy, and documented upgrade behavior.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Gateway operator scopes become an input to agent tool-policy resolution, and if so where should the durable scope-aware policy contract live?

Rationale: The choice defines an authorization boundary across Gateway auth, agent tool filtering, config precedence, and multi-user trust semantics, so automation should not choose the guarantee or default behavior.

Likely owner: steipete

Owner reason: steipete has the strongest recent history across the scoped conversation capability foundation and Gateway trust-model documentation that frame this security boundary.

Owner confidence: high

Options:

- **Design scope-aware tool policy (recommended):** Keep this issue open and approve a typed `toolsByScope` or equivalent contract with enforcement layer, precedence rules, docs, and upgrade behavior before implementation.
- **Use existing session/sender primitives:** Route the need through `toolsBySender`, group policy, session envelopes, conversation identity modes, or tenant RBAC instead of adding operator-scope-keyed config.
- **Decline scope-based RBAC:** Document operator scopes as control-plane only and direct stronger multi-user isolation to separate Gateways or the broader tenant RBAC design.

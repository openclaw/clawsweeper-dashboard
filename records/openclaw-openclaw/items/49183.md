## Summary

Keep open: current main and v2026.6.11 have agent/provider/group/sender tool-policy primitives, but they still do not bridge Gateway operator scopes into agent tool access; the remaining blocker is a security and product decision about whether operator scopes should become a tool-policy input.

## What This Changes

The issue requests a per-session or scope-keyed tool policy layer, such as `toolsByScope`, that connects Gateway operator scopes to agent tool filtering.

## Best Possible Solution

Approve a typed scope-aware tool-policy contract only after maintainers settle the threat model, config location, precedence with sender/group/agent policy, and documented upgrade behavior.

Rationale: This choice defines an authorization boundary across Gateway auth, agent tool filtering, config precedence, and multi-user trust semantics, so automation should not choose the guarantee or default behavior.

Owner confidence: high

Options:

- **Design scope-aware tool policy (recommended):** Keep this issue open and approve a typed `toolsByScope` or equivalent contract with enforcement layer, precedence rules, docs, and upgrade behavior before implementation.
- **Use existing session or sender primitives:** Route the need through `toolsBySender`, group policy, session envelopes, conversation identity modes, or tenant RBAC instead of adding operator-scope-keyed config.
- **Decline scope-based RBAC:** Document operator scopes as control-plane only and direct stronger multi-user isolation to separate Gateways or the broader tenant RBAC design.

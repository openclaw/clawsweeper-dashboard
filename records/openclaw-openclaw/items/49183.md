## Summary

Keep open: current main and v2026.6.11 still do not implement a scope-keyed bridge from Gateway operator scopes into agent tool-policy resolution. The remaining blocker is a security/product decision about whether operator scopes should become a durable tool-policy input, not a cleanup-close condition.

## What This Changes

The issue requests per-session tool filtering that maps Gateway operator scopes, such as `operator.read` or `operator.admin`, into agent tool-policy overrides.

## Best Possible Solution

Approve a typed scope-aware tool-policy contract only after maintainers settle the threat model, config location, precedence with sender/group/agent policy, and upgrade behavior.

Rationale: The choice defines an authorization boundary across Gateway auth, agent tool filtering, config precedence, and multi-user trust semantics, so automation should not choose the guarantee or default behavior.

Owner confidence: high

Options:

- **Design Scope-Aware Tool Policy (recommended):** Keep this issue open and approve a typed `toolsByScope` or equivalent contract with enforcement layer, precedence rules, docs, and upgrade behavior before implementation.
- **Use Existing Session And Sender Primitives:** Route the need through `toolsBySender`, group policy, session envelopes, conversation identity modes, or tenant RBAC instead of adding operator-scope-keyed config.
- **Decline Scope-Based RBAC:** Document operator scopes as control-plane only and direct stronger multi-user isolation to separate Gateways or the broader tenant RBAC design.

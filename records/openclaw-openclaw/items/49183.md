## Summary

Keep open: current main has sender/group tool policies and a scoped conversation-capability foundation, but it still has no operator-scope-aware tool-policy bridge. The remaining work is a security/product decision about whether gateway operator scopes should become a runtime tool-authorization input.

## What This Changes

Requests a per-session tool-policy layer that maps gateway operator scopes such as operator.read and operator.admin into agent tool filtering.

## Best Possible Solution

Maintainers should decide the durable authorization model, then either add a typed scope-aware policy layer with docs, tests, threat-model notes, and upgrade behavior, or route this need to sender policies, session envelopes, conversation identity, or tenant-RBAC work.

Rationale: This would define a new authorization/config boundary across gateway auth, session identity, and agent tool filtering, and current docs intentionally limit operator scopes to a trusted operator domain.

Likely owner: steipete

Owner reason: steipete has the strongest history across the scoped conversation profile and gateway/tool-policy security boundary.

Owner confidence: high

Options:

- **Design Scope-Aware Tool Policy (recommended):** Keep this issue open and approve a narrow operator-scope policy contract with precedence, docs, tests, and explicit threat-model language before implementation.
- **Use Existing Session/Sender Surfaces:** Decline toolsByScope and document sender/group policy, session envelopes, and conversation identity as the supported tool-restriction paths.
- **Fold Into Tenant RBAC:** Treat this as a subproblem of the broader multi-tenant RBAC FRD and defer scope-to-tool behavior until tenant-scoped scopes are designed.

## Summary

Keep open: current main and v2026.6.11 still have Gateway method scopes plus layered tool policy, sender, and group policy primitives, but no operator-scope-to-tool-policy bridge or `toolsByScope` config. The remaining work is a security/product decision about whether operator scopes should become a per-session tool authorization layer or whether the need should be handled through session envelopes, sender/group policies, or tenant RBAC.

## What This Changes

The issue requests session-level tool policy that maps Gateway operator scopes or identities into agent tool access.

## Best Possible Solution

Decide the durable authorization model first, then either add a typed scope-aware tool-policy layer with documented precedence or route this need to session envelopes, sender/group policies, or the broader tenant RBAC design.

## Reproduction Assessment

Not applicable: this is an RFC for a new authorization/config capability, not a broken existing behavior with reproduction steps. Source and release inspection show the requested scope-to-tool-policy bridge is absent rather than failing.

## Solution Assessment

Unclear: `toolsByScope` is a plausible slice, but current docs define operator scopes as a trusted-domain control-plane guardrail. Maintainers should choose between scope-aware tool policy, session envelopes, sender/group policies, and tenant RBAC before implementation.

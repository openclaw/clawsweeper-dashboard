## Summary

Keep open: current main and v2026.6.11 have sender, group, provider, and agent tool-policy primitives, but they still lack a scope-keyed bridge from Gateway operator scopes into agent tool access. The remaining blocker is a product/security decision about whether operator scopes should become a tool-policy input.

## What This Changes

The issue requests a new per-session or per-scope tool-policy capability that connects Gateway operator scopes to agent tool filtering.

## Best Possible Solution

Approve or reject a typed scope-aware tool-policy contract only after maintainers settle the threat model, config location, precedence with sender/group/agent policy, and documented upgrade behavior.

Rationale: The choice defines an authorization boundary across Gateway auth, agent tool filtering, config precedence, shared-secret behavior, and multi-user trust semantics, so automation should not choose the guarantee or default behavior.

Likely owner: steipete

Owner confidence: high

Options:

- **Design scope-aware tool policy (recommended):** Keep this issue open and approve a typed `toolsByScope` or equivalent contract with enforcement layer, precedence rules, docs, and upgrade behavior before implementation.
- **Use existing identity primitives:** Route the need through `toolsBySender`, group policy, session envelopes, conversation identity modes, or tenant RBAC instead of adding operator-scope-keyed config.
- **Decline scope-based RBAC:** Document operator scopes as control-plane only and direct stronger multi-user isolation to separate Gateways or the broader tenant RBAC design.

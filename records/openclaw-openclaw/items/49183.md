## Summary

Keep open: current main has useful sender/group tool-policy primitives and the newly landed scoped conversation capability profile foundation, but it still does not expose or enforce the requested operator-scope-to-tool-policy bridge. The remaining work is a security/product decision about trust boundaries, config shape, and policy precedence rather than conservative cleanup.

## What This Changes

The issue requests session-level tool filtering that maps gateway operator scopes or sender identity into agent tool-policy resolution.

## Best Possible Solution

Decide the durable authorization model first, then either add a typed, documented scope-aware tool-policy layer with upgrade-safe precedence or explicitly route this need to sender/group policies, session envelopes, conversation identity, or tenant RBAC work.

## Reproduction Assessment

Not applicable: this is an RFC for a new authorization/config capability rather than a report of broken current behavior. Source and release inspection show the requested scope-to-tool-policy bridge is absent, while adjacent sender/group/profile primitives exist.

## Solution Assessment

Unclear: toolsByScope is a plausible slice, but current docs frame operator scopes as trusted-domain control-plane guardrails. Maintainers should choose between scope-aware tool policy, sender/group policy, session envelopes, conversation identity, and tenant RBAC before implementation.

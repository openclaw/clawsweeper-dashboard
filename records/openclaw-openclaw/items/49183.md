## Summary

This issue is still necessary: current main has adjacent sender/group policy and a landed conversation-capability-profile foundation, but it does not expose `toolsByScope` or bridge gateway operator scopes into runtime tool-policy resolution, so the security/product boundary remains unresolved.

## What This Changes

Request a scope-aware per-session tool policy mechanism, such as `toolsByScope`, that maps gateway operator scopes to agent runtime tool access.

## Best Possible Solution

Use the landed capability-profile seam and existing sender/group policy primitives only after maintainers decide the supported trust boundary, precedence order, and config shape for scope-aware tool policy.

## Reproduction Assessment

Yes at source level: current config and policy-resolution code can be inspected to show `toolsByScope` and operator-scope policy inputs are absent, but this is a feature gap rather than a failing bug reproduction.

## Solution Assessment

Unclear: `toolsByScope` is plausible, but maintainers first need to decide whether this should be scope-aware policy, session-envelope identity, broader tenant RBAC, or documented separate-gateway isolation.

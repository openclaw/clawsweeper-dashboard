## Summary

Keep open: current main has useful sender/group policies, a scoped conversation capability profile, and Gateway direct-tool guardrails, but it still does not expose or enforce the requested operator-scope-to-agent-tool-policy bridge. The remaining work is a security/product decision about whether `toolsByScope` should exist, be replaced by session envelopes or conversation identity modes, or stay under broader tenant RBAC.

## What This Changes

The issue requests per-session tool policy enforcement that connects Gateway operator scopes or sender identity to agent tool access.

## Best Possible Solution

Keep this as the focused scope-to-tool-policy RFC until maintainers decide the durable model, then either add a typed scope-aware policy layer with docs/tests or explicitly route the need to session envelopes, conversation identity modes, or tenant RBAC.

## Reproduction Assessment

Not applicable: this is an RFC for a new authorization/config capability, not a broken existing behavior. Source and release inspection show the requested scope-to-tool-policy bridge is absent rather than failing.

## Solution Assessment

Unclear: `toolsByScope` is a plausible slice, but current docs make operator scopes a trusted-domain control-plane guardrail and current main now has sender/group policy plus a conversation capability profile. Maintainers should choose between scope-aware tool policy, session envelopes, conversation identity, binding policy, and tenant RBAC before implementation.

## Summary

I found no blocking correctness or security finding; exact-head CI should still finish before merge.

## What This Changes

The branch adds a no-op `error` listener to the Chrome launch stderr pipe immediately after the diagnostic `data` listener.

## Best Possible Solution

Land the focused stderr error guard after exact-head CI finishes, keeping process exit and CDP readiness diagnostics as the authoritative launch outcome.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, source-reproducible: current main attaches a Chrome stderr data listener without an error listener, and a local Node stream probe confirmed unhandled stream `error` events throw while a no-op listener suppresses them. I did not trigger a real Chrome EPIPE race locally.

## Solution Assessment

Yes, this is the narrowest maintainable fix: the guard belongs on the same stderr stream that is being read for launch diagnostics. Broader alternatives like changing stdio or catching around the readiness loop would either lose diagnostics or miss the stream-level `error` event.

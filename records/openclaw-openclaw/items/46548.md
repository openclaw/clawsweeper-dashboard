## Label Justifications

- `P2`: The issue affects confusing and potentially unsafe tool-failure reporting in agent/channel workflows, but it needs product policy and is not a core outage.
- `impact:security`: Surfacing richer failure reasons into chat can leak paths, commands, provider output, or other sensitive operational details without a redaction policy.
- `impact:message-loss`: A stale failed-tool warning after successful external sends can mislead an operator into duplicate or incorrect follow-up messaging.

## Summary

Keep open: current main and v2026.6.11 still show compact chat-visible tool warnings without ordinary failure reasons and clear retry state internally without a recovered or retry-success chat confirmation; the remaining fix is product/security policy, not conservative cleanup.

## What This Changes

Request that chat-visible tool failure warnings include a sanitized failure reason and indicate when a retry or recovery succeeds.

## Best Possible Solution

Define a channel-safe diagnostics policy that surfaces redacted actionable reasons only where appropriate and emits recovered-state notices only for matching resolved failures with safe side-effect semantics.

Question: Should user-visible chat warnings show redacted tool failure reasons and recovered or retry-success notices, or should OpenClaw keep these details internal and rely on agent-authored summaries?

Rationale: The source path is clear, but the safe default depends on maintainer intent for channel trust, redaction, and external side-effect recovery semantics.

Likely owner: steipete

Owner confidence: medium

Options:

- **Add redacted recovery-aware policy (recommended):** Surface sanitized actionable reasons and bounded recovered notices only when the channel, tool class, and side-effect state make that safe.
- **Keep details internal by default:** Suppress standalone raw details and require the agent or diagnostics surfaces to summarize failures instead.
- **Append sanitized reasons only:** Solve failure-reason visibility first while leaving retry-success confirmation to the broader native recovery-loop work.

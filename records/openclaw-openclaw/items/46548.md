## Label Justifications

- `P2`: The issue affects confusing and potentially unsafe tool-failure reporting in channel workflows, but the remaining work is a bounded policy/UX fix rather than an outage.
- `impact:security`: Failure-reason surfacing can expose commands, paths, provider output, customer data, or secrets across a chat boundary unless redacted.
- `impact:message-loss`: A stale or unclear failure warning after successful external sends can prompt duplicate retries and misrepresent delivered message state.

## Summary

Keep open: current main and the latest release still hide ordinary non-verbose failure reasons and do not emit a chat-visible retry/recovery confirmation. The remaining work is valid, but it needs maintainer product/security direction because the safe behavior depends on redaction, channel trust, and external side-effect semantics.

## What This Changes

The issue asks for chat-visible tool failure warnings to include a useful failure reason and to show when a retry or recovery later succeeds.

## Best Possible Solution

Define a channel-safe tool-failure notification policy that shows redacted actionable reasons when appropriate and emits recovered-state notices only when a matching failed action is later resolved.

Options:

- **Adopt redacted recovery-aware chat policy (recommended):** Surface sanitized failure reasons and recovered notices only for allowed tools/channels and matched successful retries.
- **Keep details internal by default:** Continue hiding ordinary raw reasons in normal chat and rely on agent summaries, diagnostics, or verbose/trusted modes for detail.
- **Split reason and recovery decisions:** Define a narrow redacted reason policy first, then track retry-success confirmation under the broader native recovery work.

## Reproduction Assessment

Yes. Source inspection shows current main can emit compact tool warnings without the failure reason and only clears retry state internally after a matching success; I did not run tests because this review is read-only.

## Solution Assessment

No for a simple always-append-raw-error patch; it would satisfy part of the request but risks leaking sensitive detail. The maintainable solution is a redacted, channel-aware notification and recovery-state policy with focused tests.

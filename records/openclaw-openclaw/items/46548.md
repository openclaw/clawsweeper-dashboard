## Label Justifications

- `P2`: The issue affects confusing and potentially unsafe channel-visible tool failure reporting, but it is a bounded policy improvement rather than a core outage.
- `impact:security`: Changing normal-chat failure-reason visibility can expose commands, paths, provider output, customer data, or secrets unless redacted.
- `impact:message-loss`: The production Telegram/Dialpad example shows a stale failure warning after accepted sends can prompt duplicate outreach or misrepresent delivery state.
- `impact:ux-friction`: Operators cannot tell whether a visible tool failure was transient or recovered without checking logs or internal session state.

## Summary

Keep open: current main and the latest release still intentionally omit ordinary non-verbose failure reasons from chat warnings and clear retry state internally without emitting the requested recovery confirmation. The remaining behavior is valid but security- and product-sensitive because raw tool errors and side-effect receipts can cross chat boundaries.

## What This Changes

The issue requests chat-visible tool failure reasons plus a clear retry/recovery confirmation when a later matching action succeeds.

## Best Possible Solution

Define a channel-safe tool-failure notification policy that surfaces redacted actionable reasons only when appropriate and emits recovered-state notices only for matched successful recovery of a previously visible failure.

Options:

- **Adopt redacted recovery-aware chat policy (recommended):** Show sanitized failure reasons and recovered notices only for allowed tools/channels and matched successful retries.
- **Keep details internal by default:** Continue hiding ordinary raw reasons in normal chat and rely on agent summaries, diagnostics, or verbose/trusted modes for details.
- **Split reason and recovery policy:** Define a narrow redacted failure-reason policy first and track retry-success confirmation under broader native recovery work.

## Reproduction Assessment

## Solution Assessment

No for a simple always-append-raw-error patch; it would satisfy part of the request but risks leaking sensitive details. The maintainable solution is a redacted, channel-aware notification and recovery-state policy with focused tests.

## Label Justifications

- `P2`: The issue affects confusing and potentially unsafe tool-failure reporting in real channel workflows, but it is a bounded product/security policy fix rather than an outage.
- `impact:security`: Showing failure reasons in chat can expose commands, paths, provider output, customer data, or secrets unless redaction and trust rules are defined.
- `impact:message-loss`: A stale or unclear failure warning after successful external sends can prompt duplicate retries and misrepresent delivered message state.

## Summary

Keep open: current main and v2026.6.11 still hide ordinary non-verbose tool-error reasons and only clear retry state internally, while the Telegram/Dialpad production data shows the remaining behavior can mislead operators after external side effects. A safe fix needs maintainer product/security direction on redaction, channel trust, and recovery semantics.

## What This Changes

The issue requests chat-visible tool-failure messages that include a safe failure reason and indicate when a later retry or recovery succeeded.

## Best Possible Solution

Define a channel-safe tool-failure notification policy that surfaces redacted actionable reasons when appropriate and emits recovery confirmations only for matched resolved failures, backed by focused payload and tool-state tests.

- **Split reason and recovery decisions:** Define a narrow redacted reason policy first and track retry-success confirmation under the broader native recovery work.

## Reproduction Assessment

Yes at source level. Current main gates ordinary failure reasons behind verbose/full, appends the raw reason only when that gate passes, and tests assert that an edit warning omits the underlying `missing` reason.

## Solution Assessment

No for a simple always-append-raw-error patch; it would satisfy part of the request but risks leaking sensitive detail. The maintainable solution is a redacted, channel-aware notification and recovery-state policy with focused tests.

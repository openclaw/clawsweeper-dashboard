## Label Justifications

- `P2`: The issue affects confusing and potentially unsafe tool-failure reporting in channel workflows, but the remaining work is a bounded policy/UX fix rather than an outage.
- `impact:security`: Failure-reason surfacing can expose commands, paths, provider output, customer data, or secrets across a chat boundary unless redacted.
- `impact:message-loss`: A stale failure warning after successful external sends can prompt duplicate retries and misrepresent the delivered message state.

## Summary

Keep open: current main and v2026.6.11 still omit ordinary compact failure reasons and do not emit a chat-visible retry/recovery confirmation; the remaining change needs product/security direction rather than a blind formatting patch.

## What This Changes

The issue requests chat-visible tool failure warnings that include the failure reason and a clear retry or recovery-success indication.

## Best Possible Solution

Define a channel-safe tool-failure notification policy that shows redacted actionable reasons when appropriate and emits recovered-state notices only when a matching failed action is later resolved.

Question: Should OpenClaw show redacted tool failure reasons and retry/recovery confirmations in user-visible chat by default, or keep those details internal unless an explicit trusted/verbose policy allows them?

Rationale: The source path is clear, but the safe default depends on maintainer policy for channel trust, redaction, mutating side effects, and operator-facing recovery semantics.

Options:

- **Adopt redacted recovery-aware chat policy (recommended):** Surface sanitized failure reasons and recovered notices only for allowed tools/channels and matched successful retries.
- **Keep details internal by default:** Continue suppressing ordinary raw reasons in chat and rely on agent summaries, diagnostics, or verbose/trusted modes for detail.
- **Split reason and recovery work:** First define a narrow redacted reason policy, then track retry-success confirmation under the broader native recovery issue.

## Reproduction Assessment

Yes, source-level with high confidence: `buildEmbeddedRunPayloads` can be called with assistant output plus `lastToolError` to produce a compact warning that omits the reason, and the retry-success path only clears `lastToolError`. I did not run tests because this review is read-only.

## Solution Assessment

No for the simple always-append-raw-error approach; it would satisfy part of the request but risks leaking sensitive detail. The maintainable solution is a redacted, channel-aware notification and recovery-state policy with focused tests.

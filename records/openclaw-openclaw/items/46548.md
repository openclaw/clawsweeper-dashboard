## Label Justifications

- `P2`: The issue affects confusing and potentially unsafe channel-visible tool failure reporting, but it is a bounded policy/UX improvement rather than a core outage.
- `impact:security`: Changing failure-reason visibility can expose commands, paths, provider output, customer data, or secrets across a chat boundary unless redacted.
- `impact:message-loss`: The production Telegram/Dialpad example shows a stale failure warning after accepted sends can prompt duplicate outreach or misrepresent delivery state.
- `impact:ux-friction`: Operators cannot tell whether a visible tool failure was transient or recovered without checking logs or internal session state.

## Summary

Keep open: current main and the latest release still hide ordinary non-verbose failure reasons and only clear retry state internally, while the requested chat-visible recovery behavior needs product and security policy first.

## What This Changes

Request chat-visible tool failure warnings that include a safe failure reason and show a recovery or retry-success state when a later matching tool call succeeds.

## Best Possible Solution

Define a channel-safe tool-failure notification policy that shows redacted actionable reasons when appropriate and emits recovered-state notices only when a matching failed action is later resolved.

Options:

- **Adopt redacted recovery-aware chat policy (recommended):** Surface sanitized failure reasons and recovered notices only for allowed tools/channels and matched successful retries.
- **Keep details internal by default:** Continue hiding ordinary raw reasons in normal chat and rely on agent summaries, diagnostics, or verbose/trusted modes for detail.
- **Split reason and recovery policy:** Define a narrow redacted reason policy first, then track retry-success confirmation under broader native recovery work.

## Reproduction Assessment

Yes. Source inspection shows current main can emit compact tool warnings without the failure reason and only clears retry state internally after a matching success; I did not run tests because this was a read-only review.

## Solution Assessment

No for a simple always-append-raw-error patch; it would satisfy part of the request but risks leaking sensitive detail. The maintainable solution is a redacted, channel-aware notification and recovery-state policy with focused tests.

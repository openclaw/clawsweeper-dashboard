## Label Justifications

- `P2`: The issue affects confusing and potentially unsafe tool-failure reporting in channel workflows, but the remaining work is a bounded policy/UX fix rather than an outage.
- `impact:security`: Failure-reason surfacing can expose commands, paths, provider output, customer data, or secrets across a chat boundary unless redacted.
- `impact:message-loss`: A stale or unclear failure warning after successful external sends can prompt duplicate retries and misrepresent delivered message state.

## Summary

Keep open: current main and the latest release still omit ordinary compact failure reasons and do not emit a chat-visible retry/recovery confirmation. The remaining work is valid but needs maintainer product/security direction because surfacing reasons and recovered states crosses channel trust, redaction, and external side-effect semantics.

## What This Changes

Request chat-visible tool failure warnings that include a safe failure reason and confirm recovery when a later matching retry succeeds.

## Best Possible Solution

Define a channel-safe tool-failure notification policy that shows redacted actionable reasons when appropriate and emits recovered-state notices only when a matching failed action is later resolved.

Options:

- **Adopt redacted recovery-aware chat policy (recommended):** Surface sanitized failure reasons and recovered notices only for allowed tools/channels and matched successful retries.
- **Keep details internal by default:** Continue suppressing ordinary raw reasons in chat and rely on agent summaries, diagnostics, or verbose/trusted modes for detail.
- **Split reason and recovery work:** First define a narrow redacted reason policy, then track retry-success confirmation under the broader native recovery issue.

Yes, source-level with high confidence: `buildEmbeddedRunPayloads` can produce a compact warning that omits the reason, and the retry-success path only clears `lastToolError`. I did not run tests because this review is read-only.

## Solution Assessment

No for a simple always-append-raw-error patch; it would satisfy part of the request but risks leaking sensitive detail. The maintainable solution is a redacted, channel-aware notification and recovery-state policy with focused tests.

- `impact:security`: The requested failure reason could expose raw tool errors, commands, paths, provider text, or other sensitive operational details in chat.

## Summary

Keep open: current main and v2026.6.11 still omit ordinary compact tool failure reasons and only clear internal retry state, while the production Telegram/Dialpad comment adds a credible duplicate-side-effect risk that needs maintainer security/product policy.

## What This Changes

Requests chat-visible tool failure warnings include a safe failure reason and indicate when a failed tool is later retried or recovered successfully.

## Best Possible Solution

Define a core warning policy that emits redacted, allowlisted failure summaries plus a recovered-before-final status for matching retries, while preserving raw diagnostics internally and keeping channel privacy boundaries explicit.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What default chat-visible policy should OpenClaw use for tool failure reasons and same-turn retry recovery across trusted operator chats and external-recipient channels?

Rationale: The source gap is clear, but the safe behavior depends on maintainer intent for redaction, channel trust, operator noise, and duplicate-side-effect risk rather than a purely mechanical code fix.

Likely owner: steipete

Owner reason: The current warning-detail gate and centralized tool-error visibility policy trace most directly to this owner history, and the unresolved question is a core security/product policy choice.

Owner confidence: high

Options:

- **Adopt safe summaries (recommended):** Show redacted or allowlisted failure reasons and a recovered-before-final state when a matching failed action later succeeds, with tests for compact, verbose, and channel-sensitive behavior.
- **Keep compact defaults:** Leave compact warnings without reasons by default and rely on verbose mode or suppressToolErrors for operators who prefer a different privacy/noise tradeoff.
- **Defer to native recovery:** Treat the visible warning change as dependent on the broader native recovery design tracked in https://github.com/openclaw/openclaw/issues/85914.

## Reproduction Assessment

Yes. Source inspection shows compact warning payloads omit ordinary failure reasons, tests assert those details are absent, and same-action retry success only clears lastToolError without a visible recovery confirmation.

## Solution Assessment

No. Directly appending raw lastToolError.error would solve only the surface gap and could leak sensitive details; the better solution is a maintainer-approved redaction and recovery policy.

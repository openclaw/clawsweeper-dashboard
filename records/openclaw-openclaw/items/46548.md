## Summary

Keep open: current main and latest release still intentionally keep ordinary compact chat-visible tool warnings without the failure reason, and retry recovery clears internal `lastToolError` without a visible recovered/success confirmation. Recent merged PRs improved adjacent heartbeat, Discord, and exec-label cases, but they do not close the central operator-safety request here.

## What This Changes

The issue requests chat-visible tool failure warnings that include a failure reason and make recovered retry/success state clear to operators.

## Best Possible Solution

Define a core warning policy that exposes safe, redacted failure reasons and marks same-turn recovered tool failures without leaving operators with a retry-worthy stale failure after successful side effects.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: build payloads for a compact non-verbose mutating or exec tool failure and the error reason is intentionally omitted; later same-action success clears `lastToolError` without a visible recovery confirmation.

## Solution Assessment

Unclear. The current code already suppresses some stale warnings, but the best complete fix needs maintainer policy for redaction, warning ordering, and recovered-side-effect semantics before a safe patch.

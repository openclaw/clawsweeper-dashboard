## Label Justifications

- `P2`: The issue affects confusing and potentially unsafe tool-failure reporting in channel workflows, but it is bounded and needs product policy rather than emergency repair.
- `impact:security`: Any failure-reason policy must prevent paths, commands, provider output, customer data, or secrets from leaking into chat.
- `impact:message-loss`: A stale failure warning after successful side effects can cause duplicate send/retry decisions and misrepresent the delivered message state.

## Summary

Keep open: current main and v2026.6.11 still intentionally omit ordinary compact failure reasons and do not emit a chat-visible retry or recovery confirmation; the remaining fix needs product/security policy rather than a blind formatting patch.

## What This Changes

The issue asks for chat-surfaced tool failures to include the failure reason and to confirm when a later retry or recovery succeeds.

## Best Possible Solution

Define a channel-safe tool-failure notification policy that shows redacted actionable reasons when appropriate and emits recovered-state notices only when a matching failed action is later resolved.

Question: Should OpenClaw show redacted tool failure reasons and retry/recovery confirmations in user-visible chat by default, or keep those details internal unless an explicit verbose/trusted policy allows them?

Rationale: The source path is clear, but the safe default depends on maintainer policy for channel trust, redaction, mutating side effects, and operator-facing recovery semantics.

Owner confidence: medium

Options:

- **Add redacted recovery-aware chat policy (recommended):** Surface sanitized reasons and recovered notices only for allowed tools/channels and matched successful retries.
- **Keep details internal by default:** Continue suppressing raw reasons in normal chat and rely on agent summaries, diagnostics, or full verbose mode for details.
- **Split failure reasons from recovery:** First add a narrowly redacted reason policy, then track retry-success confirmation under the broader native recovery work.

## Reproduction Assessment

Yes. Source inspection and current tests show normal compact warnings omit ordinary failure reasons, and successful retries clear internal state without producing a visible recovery confirmation.

## Solution Assessment

Unclear as requested: always appending raw failure reasons would solve part of the report but is not the safest policy. The better path is a redacted, channel-aware notification and recovery-state design.

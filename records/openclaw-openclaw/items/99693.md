## Summary

Keep open: current main still lets a non-recoverable Telegram chunk send reject out of the loop before later chunks are attempted, while the requested blanket catch-and-continue behavior needs a maintainer-defined recoverable-versus-fatal error contract. The related open PR https://github.com/openclaw/openclaw/pull/99745 only covers the empty-rich/content-required subset, not this broader per-chunk abort policy.

## What This Changes

The issue requests Telegram per-chunk send failure handling so one failed chunk does not abort delivery of the remaining chunks.

## Best Possible Solution

Define recoverable Telegram chunk failures in shared send predicates, retry those chunks as plain text where possible, and only continue/drop chunks when the error contract says partial delivery is acceptable.

## Reproduction Assessment

Yes at source level: current tests and source show a later chunk rejection rejects the whole durable send after earlier chunk delivery. I did not run a live Telegram repro, and the common HTML-parse/rich invalid-entity cases already have per-chunk fallback on current main.

## Solution Assessment

No for the broad proposed minimum as written: blindly catching and continuing every chunk send error is not the best fix because fatal Telegram errors should remain loud. The safer path is a shared recoverability contract plus durable and streaming send-funnel tests.

## Label Justifications

- `P2`: This is a normal-priority Telegram delivery reliability bug limited to long chunked outbound replies and recovery semantics.
- `impact:message-loss`: A rejected middle Telegram chunk can cause the remaining chunks of the same outbound reply to go unsent.

## Summary

Keep open: current main still has Telegram chunk loops where a later chunk rejection aborts the send, and the adjacent tests currently expect only already-sent chunks to be reported before the rejection. Existing rich/plain fallback work covers several recoverable Telegram 400s, but the remaining request needs a maintainer decision on which per-chunk failures may continue versus which must stay loud.

## What This Changes

The issue asks for Telegram chunked outbound sends to handle individual chunk failures so one rejected chunk does not drop every remaining chunk.

## Best Possible Solution

Add Telegram-owned per-chunk recovery only for classified recoverable validation/formatting errors, keep fatal routing/auth/topic/transport failures loud, and apply the same policy to durable and streaming send funnels with regression coverage.

## Reproduction Assessment

Yes from source: current main directly awaits each Telegram chunk send, and the focused test for a second-chunk failure expects the whole send to reject after only the first chunk is reported. I did not run a live Telegram Bot API repro in this read-only review.

## Solution Assessment

Unclear as requested: continuing after every per-chunk error is too broad because current policy keeps routing, topic, auth, and non-validation transport failures loud. The best fix is a narrow recoverable-error policy shared by the durable and streaming Telegram send funnels.

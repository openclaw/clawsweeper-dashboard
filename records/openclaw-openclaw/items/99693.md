## Label Justifications

- `P2`: The issue is a normal-priority Telegram delivery reliability bug with limited blast radius to long chunked outbound replies.
- `impact:message-loss`: The reported failure can drop the remaining chunks of an outbound Telegram reply after one chunk send rejects.

## Summary

Keep open: current main still aborts the durable Telegram chunk loop on an unhandled per-chunk send rejection, so the central tail-loss problem is not implemented on main. The issue is actionable, but the safest fix needs a maintainer decision about which Telegram send errors are recoverable versus fatal before changing partial-delivery semantics.

## What This Changes

The issue reports that one failed Telegram chunked send can abort the remaining chunks of a long outbound reply.

## Best Possible Solution

Add Telegram-owned per-chunk failure handling that preserves later chunk delivery for recoverable validation/send failures while keeping fatal routing/auth errors loud and auditable.

## Reproduction Assessment

Yes at source level: a mocked rejection from a middle send in sendTelegramTextChunks, or any non-rich-entity rejection in sendTelegramRichTextChunks, exits the current loop before later chunks are attempted. I did not run a live Telegram Bot API scenario in this read-only review.

## Solution Assessment

Unclear as requested: continuing after every Telegram error is not the best fix because it can hide fatal topic/routing failures. The maintainable path is a narrow recoverable-error policy or partial-delivery contract inside the Telegram send funnel.

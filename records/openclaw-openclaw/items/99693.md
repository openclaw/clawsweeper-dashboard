## Label Justifications

- `P2`: The issue is a normal-priority Telegram delivery reliability bug limited to long chunked outbound replies.
- `impact:message-loss`: A rejected middle Telegram chunk can cause the remaining chunks of an outbound reply to never be delivered.

## Summary

Keep open: current main still aborts Telegram chunk delivery when a middle chunk send rejects, and the latest release has the same loop shape. The report is actionable, but a maintainer should choose the recoverable-versus-fatal Telegram error contract before a fix changes partial-delivery semantics.

## What This Changes

Make Telegram chunked outbound sending handle a failed chunk without silently dropping all later chunks, preferably with recoverable plain-text retry and a visible or logged partial-delivery signal.

## Best Possible Solution

Add Telegram-owned per-chunk recovery only for classified recoverable validation or formatting failures, keep fatal delivery errors loud, and apply the same policy across durable and streaming send funnels with focused tests and live Telegram proof.

## Reproduction Assessment

Yes from source: the current durable text loop directly awaits each chunk send, and the current test suite expects the whole send to reject after a later chunk fails. I did not run a live Telegram Bot API repro in this read-only review.

## Solution Assessment

Unclear as requested: continuing after every Telegram error is not the best fix because it can hide fatal routing, auth, topic, or transport failures. The maintainable path is a narrow recoverable-error policy inside the Telegram send funnel.

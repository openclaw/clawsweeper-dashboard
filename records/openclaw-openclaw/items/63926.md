## Label Justifications

- `P2`: This is a significant but bounded Control UI/product improvement for authenticated browser workflows, not an emergency runtime outage.
- `impact:security`: The requested panel would expose and control authenticated browser sessions, so scopes, redaction, and trust boundaries are central to the work.
- `impact:session-state`: The acceptance criteria require the user to log in and then let the agent resume against the same managed browser profile/tab state.
- `impact:ux-friction`: Users currently have to rely on agent instructions or CLI commands to reach the managed browser during login handoff, which creates avoidable confusion without fully blocking all browser use.

## Summary

Keep open: current main and the latest release still expose browser CLI/RPC/control primitives, but they do not provide the requested visible Control UI browser-login handoff panel. The issue is also explicitly treated in discussion as the canonical browser-login handoff tracker, with related browser-preview and plugin-entry-point work only partially overlapping.

## What This Changes

Request to add a visible Control UI browser panel for managed-browser status, tab management, manual login handoff, and resuming agent work against the same browser state.

## Best Possible Solution

Keep this as the canonical product/security design issue, then implement an admin-scoped browser handoff surface that reuses browser.request primitives, reports structured manual-action state, shows exact profile/tab context, and coordinates with https://github.com/openclaw/openclaw/issues/27574 and https://github.com/openclaw/openclaw/pull/80388.

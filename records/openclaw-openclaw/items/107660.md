## Summary

The updated head resolves the previously reported in-flight-load race and appears to fix the reproduced stale-cache bug through the correct macOS ownership boundary. The implementation is focused and has regression coverage, but this external PR still needs real native-app after-fix proof before merge.

## What This Changes

The PR refreshes the loaded macOS Skills model after local-node reconnect and coalesces forced refreshes that arrive during an in-flight status request.

## Best Possible Solution

Keep the gateway as the sole skill-eligibility authority, perform one coalesced Skills refresh after the local node route and inventory are ready, and demonstrate the visible unavailable-to-available transition in a real macOS app run.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes. On release 2026.7.1, opening Skills before the local node reconnects can cache an unavailable response and leave the card stale even after live `skills.status` and `system.which` report readiness.

## Solution Assessment

Yes. Refreshing the loaded macOS view from authoritative `skills.status` at the node-ready boundary, with coalescing for an in-flight initial request, is narrower and safer than polling or duplicating skill eligibility policy.

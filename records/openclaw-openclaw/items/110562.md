## Summary

The latest revision addresses the earlier Windows tree-termination finding at the helper level, but the timeout sequence still sends `SIGTERM` to the root process before invoking `taskkill /T /F`. On Windows, that can terminate the wrapper first and orphan descendants, leaving the stated full-tree guarantee unproven and potentially allowing the workflow check to remain stuck.

## What This Changes

The PR converts workflow-check subprocess execution to bounded asynchronous runs with timeout escalation, adds a capped timeout environment override, and adds focused timeout and Windows taskkill-command tests.

## Best Possible Solution

Make Windows timeout handling terminate the original process tree before the wrapper PID can disappear, then add a Windows-capable descendant fixture or equivalent live proof showing that the command exits and leaves no child running.

## Solution Assessment

No. The bounded runner is the right design, but Windows must target the process tree before a direct-child signal can make the root PID unavailable; the current helper test does not prove the promised end-to-end behavior.

## Summary

Keep open. Current main and v2026.6.11 still expose skills as `SKILL.md` roots with same-name replacement precedence, and there is no supported `preferences.md` or `conventions.md` sidecar that is appended only when that skill is selected; this remains a product/API decision, not stale cleanup.

## What This Changes

The issue requests a supported per-skill user preference or conventions mechanism that avoids full `SKILL.md` overrides and global context files.

## Best Possible Solution

Define one maintainer-approved skill preference contract, preferably a small markdown sidecar loaded with the selected skill and covered by prompt-version, watcher, security, and docs behavior, or explicitly decide that users should keep using full skill overrides and Skill Workshop.

Rationale: Source evidence shows the requested behavior is missing, but adding it changes a public skill-loading and prompt-context contract rather than repairing an already-defined bug.

Likely owner: steipete

Owner confidence: high

Options:

- **Standardize a markdown sidecar (recommended):** Add a documented `preferences.md` or `conventions.md` sidecar that is loaded with the selected skill, lower precedence than `SKILL.md`, and included in prompt-version, watcher, and security behavior.
- **Use structured skill config:** Keep preferences under `skills.entries.*.config` and require each skill or plugin to interpret them, avoiding markdown prompt composition while making natural-language conventions less ergonomic.
- **Decline core support:** Keep the current model of full skill overrides, custom skills, or global context files, and close this direction as not planned if maintainers do not want another skill-loading surface.

## Reproduction Assessment

Yes. Source inspection shows OpenClaw discovers and prompts `SKILL.md` files only, while current docs and v2026.6.11 do not define a `preferences.md` or `conventions.md` sidecar path.

## Solution Assessment

Unclear until maintainers choose the product contract. A markdown sidecar appears to fit the reported natural-language convention use case best, but the loader, watcher, prompt snapshot, security, and docs behavior need an explicit API decision first.

## Summary

Keep open. Current main and the latest release still define skills around `SKILL.md`, source precedence, and structured per-skill runtime config, but they do not support a `preferences.md` or `conventions.md` sidecar that is loaded only when a skill is triggered; this remains a maintainer product/API decision.

## What This Changes

Requests a supported per-skill user preference or convention sidecar/config that loads only when that skill is triggered.

## Best Possible Solution

Define one maintainer-approved per-skill preference contract with filename or config shape, precedence, containment, prompt-version invalidation, docs, and regression tests before implementing loader behavior.

## Reproduction Assessment

Yes, as a source-level feature gap. Current main still loads `SKILL.md` as the skill unit, replaces same-named skills by source precedence, and has no supported `preferences.md` or `conventions.md` sidecar contract.

## Solution Assessment

Unclear. A markdown sidecar is plausible, but maintainers still need to choose the canonical filename, precedence, refresh behavior, security boundary, and whether this belongs in loader behavior or another documented skill/config contract.

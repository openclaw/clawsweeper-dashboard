## Summary

Keep open. Current main and v2026.6.11 still treat `SKILL.md` as the loaded skill contract and same-name higher-precedence skills as replacements, with no supported `preferences.md` or `conventions.md` sidecar; this remains a real product/API decision rather than stale cleanup.

## What This Changes

The issue requests an official per-skill user preference or convention file that loads only when that skill is used.

## Best Possible Solution

Define one maintainer-approved skill preference contract, preferably a small markdown sidecar loaded with the selected skill and covered by prompt-version, watcher, security, sandbox, and docs behavior, or explicitly decide that users should keep using full skill overrides and Skill Workshop.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support a first-class per-skill user preference sidecar, and if so should the permanent contract be markdown sidecar, structured `skills.entries.*.config`, or no core support?

Rationale: The source evidence shows the requested behavior is not implemented, but adding it changes the public skill-loading and prompt-context contract rather than fixing a broken existing behavior.

Likely owner: steipete

Owner reason: The decision touches skill-loading public API shape, docs, and product scope, and steipete has the strongest combined history and prior routing signal for this area.

Owner confidence: high

Options:

- **Standardize a markdown sidecar (recommended):** Add a documented `preferences.md` or `conventions.md` sidecar that loads with the selected skill, has lower precedence than `SKILL.md`, participates in prompt versioning, and is watched for refresh.
- **Use structured skill config only:** Keep preferences under `skills.entries.*.config` and require each skill or plugin to interpret them, avoiding prompt-side markdown composition but leaving natural-language conventions less ergonomic.
- **Decline core support:** Keep the current model where users maintain a higher-precedence skill override, create a personal skill, or use global context files, and close this direction as not planned.

## Reproduction Assessment

Yes, as a source-level feature gap. Current main and v2026.6.11 discover and prompt `SKILL.md` files only, while docs and code do not define a `preferences.md` or `conventions.md` sidecar path.

## Solution Assessment

Unclear until maintainers choose the product contract. A markdown sidecar looks like the narrowest fit for natural-language conventions, but loader, watcher, prompt snapshot, security, sandbox, and docs behavior need an explicit API decision first.

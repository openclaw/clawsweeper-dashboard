## Summary

Keep open. Current main and v2026.6.11 still treat skills as `SKILL.md` units with whole-skill precedence and existing per-skill runtime config, but no supported markdown preferences/conventions sidecar that is loaded with the skill context.

## What This Changes

Request standardizes a per-skill user preferences or conventions sidecar, or equivalent scoped config, loaded only when that skill is used.

## Best Possible Solution

Define a narrow skill-preference contract at the skill-loading boundary with explicit precedence, authority, watcher/versioning, security docs, and tests across prompt snapshots and explicit skill invocation.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support user-authored per-skill preferences as a markdown sidecar, a structured config-only mechanism, or leave this to skill/package authors for now?

Rationale: The implementation shape changes public skill-loading semantics and prompt authority, and repository policy requires maintainer intent before adding new config or context-loading surfaces.

Likely owner: Chunyue Wang

Owner reason: The current local source history for the skill loader and skill docs points to this person as the best available area-routing candidate.

Owner confidence: medium

Options:

- **Adopt a markdown sidecar (recommended):** Standardize a user-authored `preferences.md` or `conventions.md` sidecar with lower authority than `SKILL.md`, include it in version/watch invalidation, and document the security boundary.
- **Use structured config only:** Keep natural-language preferences out of automatic prompt loading and document `skills.entries.<key>.config` as the supported per-skill customization path when skill code can consume it.
- **Defer to package authors:** Do not add core loading behavior yet; ask skill authors to document optional companion files inside their own `SKILL.md` until broader skill composition decisions settle.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: current main and v2026.6.11 discover and version `SKILL.md` files only, and targeted search found no supported preferences/conventions sidecar. There is no failing bug path to run because this is a feature request.

## Solution Assessment

Unclear until maintainers choose the product contract. A markdown sidecar is plausible and matches the discussion, but the best implementation must first settle precedence, authority, watcher/versioning, and whether existing structured config is enough for runtime-owned preferences.

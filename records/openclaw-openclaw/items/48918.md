## Summary

Keep open. Current main and the latest release still treat `SKILL.md` as the skill unit, with replacement-by-precedence and no supported `preferences.md` or `conventions.md` sidecar loaded on skill trigger, so this remains a product/API decision rather than cleanup-close material.

## What This Changes

The issue requests a standard per-skill user preferences or conventions file that loads only when that skill triggers.

## Best Possible Solution

Define one maintainer-approved per-skill preference contract, including filename or config shape, precedence, containment, prompt-version invalidation, docs, and regression tests before implementing loader behavior.

Rationale: The source gap is clear, but the right behavior changes skill loading precedence, prompt contents, watcher invalidation, and possibly config surface area, so automation should not pick the product contract alone.

Options:

- **Standardize a markdown sidecar (recommended):** Adopt one documented markdown file such as `preferences.md`, load it with the selected skill, and update prompt-version/watch/test behavior around that contract.
- **Use structured skill config:** Keep prompt guidance in `SKILL.md` and express user preferences through `skills.entries.*.config`, accepting the extra config-schema and docs burden.
- **Keep current behavior:** Leave user conventions as manual skill-authored behavior until a stronger product need or a broader skill personalization design is approved.

Yes, as a source-level feature gap. Current main still loads `SKILL.md` as the skill unit, replaces same-named skills by source precedence, and has no supported `preferences.md` or `conventions.md` sidecar contract.

## Solution Assessment

Unclear. A markdown sidecar is plausible and has supportive issue discussion, but maintainers still need to choose the canonical filename, precedence, refresh behavior, security boundary, and whether this belongs in loader behavior or structured skill config.

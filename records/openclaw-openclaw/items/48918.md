## Summary

Keep open. Current main and v2026.6.11 still define skills around `SKILL.md`, source precedence, and structured `skills.entries` config; there is no supported `preferences.md` or `conventions.md` sidecar, and the related open items are adjacent rather than canonical replacements.

## What This Changes

Request to add a standard per-skill user preferences or conventions file that loads only when that skill is triggered.

## Best Possible Solution

Define one maintainer-approved per-skill preference contract with filename, precedence, prompt-version invalidation, watcher behavior, docs, and regression coverage before implementing loader behavior.

Owner confidence: high

Options:

- **Approve a markdown sidecar contract (recommended):** Standardize a narrow `preferences.md`-style file with lower precedence than `SKILL.md`, explicit version/watcher semantics, docs, and tests.
- **Use structured skill config only:** Extend or document `skills.entries.<key>.config` for machine-readable preferences, accepting that natural-language conventions remain less ergonomic.
- **Keep override-only behavior:** Leave preferences in full `SKILL.md` overrides or global context files and close this direction as outside the current core scope.

## Reproduction Assessment

Yes, as a source-level feature gap: current main and v2026.6.11 load `SKILL.md` as the skill unit, compute versions from that content, and document re-reading `SKILL.md`; no sidecar preference contract exists.

## Solution Assessment

Unclear. A markdown sidecar is plausible, but the best fix depends on a maintainer decision about filename, precedence, prompt-version invalidation, watcher behavior, and whether this belongs in loader behavior or structured skill config.

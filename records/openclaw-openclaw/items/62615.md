## Summary

Keep open. Current main has several narrower protections and a partial session-suspension path, but it still lacks the requested first-class session-level circuit breaker with consecutive failure receipts, retry admission, recovery policy, auto-rotation, and operator/UI surfacing.

## What This Changes

The issue requests a gateway/runtime circuit breaker that detects unhealthy sessions after repeated failures and stops or reroutes automatic retries with clear recovery state.

## Best Possible Solution

Define one core session-health receipt/state contract that composes with existing retry, failover, suspension, idle-timeout, tool-loop, and compaction guards, then implement the minimal runtime, persistence, config, and operator surfaces behind upgrade-safe defaults.

Options:

- **Design unified session-health receipts (recommended):** Define failure signatures, counters, last-success timestamps, retry admission, suggested recovery, persistence, cooldown or half-open semantics, and operator recovery behavior before implementation.
- **Land a narrow no-progress breaker:** Limit the first change to a bounded consecutive no-progress counter in the embedded run loop and leave receipts, persistence, cooldowns, UI, and auto-rotation as follow-up work.
- **Defer to narrower guards:** Keep idle-timeout, tool-loop, compaction, provider, cron, and subagent guard tracks separate and narrow or close this umbrella later if those surfaces cover the real failures.

Yes at source level: current main has partial retry, failover, idle-timeout, tool-loop, and suspension mechanisms, but no general consecutive unhealthy-session breaker with the requested receipt and recovery state. I did not run a live retry-storm reproduction in this read-only review.

## Solution Assessment

Unclear as an implementation plan: a simple counter is plausible, but the best fix should extend or unify the existing session-suspension, failover, idle-timeout, and loop-guard contracts rather than adding another competing retry policy.

## Summary

Keep open: current main and v2026.6.11 still build Claude CLI epochs from the local credential part when present plus the selected auth-profile part, so a storage-presence flip can still invalidate live sessions; the related PRs remain closed, overlapping, or blocked on auth-boundary decisions.

## What This Changes

The issue requests stable CLI auth epochs when local Claude credential storage presence changes but the authenticated identity is unchanged.

## Best Possible Solution

Land or sponsor a focused Claude CLI auth-epoch policy fix that keeps unchanged identity stable across local storage-presence flips while still resetting on logout, real account switches, and unprovable identity changes.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What should be the Claude CLI auth identity boundary for reusable sessions when an OpenClaw auth profile exists but the local Claude credential source appears or disappears?

Rationale: The source bug is clear, but the repair can either preserve sessions across a cosmetic storage flip or accidentally preserve them across an unproven credential identity change, so maintainer security/product intent is required before automation changes the boundary.

Likely owner: steipete

Owner reason: The initial auth invalidation behavior and current session-reuse boundary trace to steipete's commit history, and the open question is an auth/session policy call.

Owner confidence: high

Options:

- **Adopt a narrow identity-stable fix (recommended):** Make Claude CLI auth epochs ignore storage-shape churn only when the implementation can prove unchanged identity, with tests for storage flips, logout, and real account changes.
- **Keep fail-closed behavior:** Leave the current epoch composition in place and document that users may see resets when credential sources churn because identity cannot be proven safely.
- **Choose a host-identity model:** Require an identity-bearing host Claude credential fingerprint and coordinate the overlapping PRs around that internal contract instead of profile-canonical behavior.

## Reproduction Assessment

Yes at source level: current main still changes the auth-epoch part set when a Claude CLI local credential read flips between absent and present while an auth profile is selected, and same-version epoch mismatches invalidate session reuse. I did not run a live credential-file/keychain flip in this read-only review.

## Solution Assessment

Unclear as a final implementation: the proposed direction is plausible, but maintainers still need to choose the Claude CLI identity boundary so unchanged storage presence does not reset sessions while real or unproven auth changes still do.

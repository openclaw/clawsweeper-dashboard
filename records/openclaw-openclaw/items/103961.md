## Summary

The patch targets the correct lock leak, but the current head still clears active lock ownership without retiring the corresponding refresh queue and promise. That permits pre-restart and post-restart refreshes to overlap on the same cache, and the promised live gateway recovery proof is still absent.

## What This Changes

The PR tracks process-local usage-cost refresh lock tokens, reclaims unregistered same-process locks, clears holder registrations during in-process gateway restart, and adds same-PID, foreign-PID, and restart-hook regression tests.

## Best Possible Solution

Make the refresh queue, lock tokens, timers, and completions share one restart generation or retire them as one lifecycle-owned unit, preventing old work from acquiring, writing, rescheduling, or deleting current-generation state; then demonstrate the repaired gateway path with redacted runtime output.

## Reproduction Assessment

Yes at source level: an active `UsageCostRefreshState` survives the restart hook while its lock token is cleared, allowing another acquire to reclaim the still-active same-PID lock. The reporter's exact host-level transition still lacks a live transcript.

## Solution Assessment

No. Reclaiming genuinely abandoned same-process locks is appropriate, but clearing only the holder registry violates the queue/lock ownership invariant; the queue and completion path must share the lifecycle reset.

## Summary

The exact PR head has strong real-world proof and fixes the reported leaked self-PID lock path, but it still leaves two restart ownership races: generation is captured after lock publication, and revocation is checked before—not at—the asynchronous atomic rename. Either window can let pre-restart work overlap or overwrite a post-restart refresh, so this PR is not ready to merge.

## What This Changes

The PR adds same-process usage-cache lock ownership tracking, restart-time queue and holder reset, and generation fencing intended to reclaim leaked locks without allowing stale refreshes to overwrite newer cache state.

## Best Possible Solution

Use a closed refresh-ownership result that binds token and restart generation before lock publication, and pass an ownership assertion into the atomic writer's `beforeRename` hook so a revoked lifecycle cannot commit its temp file.

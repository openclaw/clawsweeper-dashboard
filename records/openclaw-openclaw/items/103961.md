## Label Justifications

- `P2`: The PR targets a persistent but subsystem-limited usage-cost reporting stall.
- `merge-risk: 🚨 availability`: Clearing lock ownership while old refresh work remains active can admit concurrent cache writers and leave usage reporting stale or unreliable.

## Summary

The final-head queue identity checks resolve stale rescheduling and map deletion, but a refresh already inside its scan/write operation remains active when restart clears its holder token, so a new refresh can reclaim the lock and write the same cache concurrently.

## What This Changes

The PR tracks same-process usage refresh lock holders, reclaims unowned self-pid locks, and resets queued refresh ownership during in-process gateway restarts.

## Best Possible Solution

Generation-scope or abort/drain in-flight usage refreshes together with holder tokens, timers, queue entries, cache writes, lock release, and completion, then prove with a controlled overlap regression that stale work cannot overwrite the post-restart cache.

## Summary

The PR has strong proof and addresses the reported lock leak directly, but the prior atomic-replacement blocker remains: a refresh superseded during temporary-file preparation can still rename stale cache contents after post-restart work commits.

## What This Changes

Adds same-process usage-cost lock reclamation, restart-generation fencing, refresh-queue reset, and deterministic restart-overlap regression coverage.

## Best Possible Solution

Thread the captured restart generation into each usage-cache write, reject superseded work through `replaceFileAtomic.beforeRename`, map that expected cancellation to `busy`, and add a deterministic restart-after-temp-write regression before rebasing and re-reviewing.

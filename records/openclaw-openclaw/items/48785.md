## Summary

Keep open. Current main and the latest release still use one string-valued `tools.sessions.visibility` scope for list, history, send, and status, while the requested per-capability authorization model remains unimplemented and security-sensitive.

## What This Changes

The issue requests a backward-compatible object form for `tools.sessions.visibility` so operators can separately authorize session send, history, list, and metadata access.

## Best Possible Solution

Define one maintainer-approved, backward-compatible session-tool authorization model that preserves existing string shorthands, adds only approved capability controls, keeps sandbox and A2A gates intact, and updates schema, docs, and tests together.

- **Approve unified capability object (recommended):** Adopt a backward-compatible object form for send, history, list, and metadata after reconciling it with allowlist, per-agent, sandbox, and A2A semantics.
- **Use adjacent policy axes instead:** Make the open allowlist, per-agent A2A, or send-only proposals canonical if maintainers decide those satisfy the send-without-read privacy goal better than per-capability flags.
- **Keep current fail-closed model:** Continue requiring broad visibility for cross-agent session tools and document the privacy-versus-coordination tradeoff as intentional for now.

## Reproduction Assessment

Yes. Source inspection shows a high-confidence current-main reproduction of the gap: all session actions share one `SessionToolsVisibility` path, so no config can allow cross-agent send while denying cross-agent history, list, or status.

## Solution Assessment

Unclear. Per-capability visibility is a plausible privacy model, but the exact config semantics should be chosen alongside the active allowlist, per-agent, sandbox, and A2A proposals before implementation.

## Summary

Keep open: current main still has a source-reproducible path where transcript-only `delivery-mirror` assistant usage can be selected for compaction token accounting, and the compaction write path still accepts that value as `tokensBefore` without a finite-number guard.

## What This Changes

The issue reports that `delivery-mirror` usage can poison compaction `tokensBefore`, preventing safeguard transcript truncation and causing repeated compaction thrash.

## Best Possible Solution

Fix the existing compaction pipeline so transcript-only delivery mirrors cannot supply usage for `tokensBefore`, and make compaction replay/truncation depend on the summary boundary rather than fragile token telemetry.

## Reproduction Assessment

Yes, at source level: construct a branch whose last successful assistant is `openclaw`/`delivery-mirror` with OpenAI-shaped usage missing top-level cache and total fields, then `prepareCompaction` can propagate a non-finite `tokensBefore`. I did not run a live channel session in this read-only review.

## Solution Assessment

Unclear whether every suggested hardening step is needed, but the best fix is narrow: skip transcript-only mirrors in compaction usage sampling and normalize or guard token counts so telemetry cannot invalidate a valid compaction boundary.

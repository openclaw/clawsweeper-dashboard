## Summary

Keep open: current main still stores followup queues in process memory and rejects new command-lane work once restart draining begins, while the durable SQLite followup-queue fix is still an open PR rather than merged behavior.

## What This Changes

The issue requests durable handling for queued followups, in-flight work, and drain-window inbound messages so gateway restarts do not silently drop user messages.

## Best Possible Solution

Land or replace with one canonical SQLite-backed followup/inbound recovery path that preserves pending user work across restart, replays it once, and leaves channel-specific ACK/catch-up semantics explicit.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: queue a followup, trigger restart so the process exits or enters drain, and the in-memory `FOLLOWUP_QUEUES`/drain-window rejection path has no durable replay on current main. I did not run a live channel restart in this read-only review.

## Solution Assessment

No, the original `state/pending-messages.json` sidecar proposal is no longer the best implementation under current repository policy. The maintainable direction is a shared SQLite-backed queue/recovery path with focused replay and channel ACK/catch-up decisions, matching the shape of the open SQLite PR.

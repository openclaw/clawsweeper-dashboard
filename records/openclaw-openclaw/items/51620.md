## Summary

Keep open: current main and the latest release still keep followup queues in process memory and reject drain-window command enqueues, while the directly linked fixes are open, conflicting, or partial.

## What This Changes

The issue asks OpenClaw to persist and replay queued or drain-window inbound messages across gateway restarts instead of silently dropping them.

## Best Possible Solution

Land a maintainer-approved SQLite-backed restart recovery path that preserves followup queue entries, handles drain-window arrivals without duplicate or misrouted delivery, and splits provider catch-up or channel ACK policy into explicit follow-ups.

## Reproduction Assessment

Yes, at source level: current main keeps followup queues in a process-global Map and rejects new command-lane enqueues once restart draining starts. I did not run a live channel restart in this read-only review.

## Solution Assessment

No, the original JSON sidecar approach is not the best repository fit because OpenClaw policy requires SQLite for runtime state and doctor-owned migration paths. The SQLite-backed direction in https://github.com/openclaw/openclaw/pull/82572 is closer, but it is still open/conflicting and needs maintainer review.

## Summary

Keep open: current main and the latest release still keep followup queues in process memory, reject new command-lane work during restart drain, and only have unmerged PRs for durable restart recovery.

## What This Changes

The issue asks OpenClaw to preserve queued and in-flight inbound messages across gateway restarts, including followup queues, drain-window arrivals, and channel-level acknowledgment timing.

## Best Possible Solution

Land or reject the SQLite-backed followup queue persistence/replay path first, then split drain-window capture and provider ACK/offline catch-up into explicit follow-up work.

## Reproduction Assessment

Yes, at source level: current main keeps followup queues in memory and rejects new command-lane enqueues once restart draining starts. I did not run a live channel restart in this read-only review.

## Solution Assessment

No, not as the original JSON-sidecar sketch: OpenClaw policy prefers SQLite-backed runtime state. The best current path is a maintainer-reviewed SQLite recovery implementation plus narrower follow-ups for drain-window and provider ACK semantics.

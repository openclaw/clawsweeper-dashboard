## Summary

Keep open: current main and the latest release still keep followup queues in process memory and reject new command-lane work during restart drain, while the direct recovery PRs remain open and unmerged.

## What This Changes

The issue asks for gateway restart to durably preserve and replay queued or in-flight inbound messages instead of dropping followup queues, drain-window arrivals, or provider-downtime messages.

## Best Possible Solution

Land a rebased SQLite/doctor-backed durable followup recovery path with exactly-once replay proof, then split remaining provider downtime catch-up and channel ACK semantics into narrower follow-ups.

Yes, at source level: current main keeps followup queues in a process-global map and rejects new command-lane enqueues once restart draining starts. I did not run a live channel restart in this read-only review.

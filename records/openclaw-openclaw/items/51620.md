## Summary

Keep open: current main and the latest release still keep accepted followup queues in process memory and reject new command-lane work once restart draining starts, while the linked fix PRs remain open and need maintainer decisions before one path lands.

## What This Changes

The issue asks OpenClaw to preserve queued, in-flight, and drain-window inbound messages across gateway restarts instead of silently dropping them.

## Best Possible Solution

Land one maintainer-approved SQLite/doctor-backed recovery path that preserves full route and session context, proves exactly-once real channel replay after restart, and treats drain-window or channel-ACK semantics as explicit follow-up scope if they cannot land in the same focused change.

## Reproduction Assessment

Yes, at source level: current main keeps followup queues in a process-global map and rejects new command-lane enqueues once restart draining starts. I did not run a destructive live channel restart in this read-only review.

## Solution Assessment

No single open path is ready yet. The right direction is durable SQLite-backed followup recovery plus explicit replay/ACK semantics, but the current linked PRs still need maintainer review, proof, and in some cases architectural repair.

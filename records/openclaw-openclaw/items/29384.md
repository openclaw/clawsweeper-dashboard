## Summary

Keep this open: current main and v2026.6.11 already cover the GPU half through typed `sandbox.docker.gpus`, but host IPC and generic Docker flag passthrough remain absent and require a sandbox security-boundary decision.

## What This Changes

Request to allow Docker sandbox users to pass GPU and host IPC Docker parameters such as `--gpus all` and `--ipc=host`.

## Best Possible Solution

Keep the shipped typed GPU support, and only add a narrow audited host IPC break-glass field if security owners approve the sandbox tradeoff; avoid generic raw Docker argument passthrough.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose host IPC for Docker sandboxes, and if yes should it be a narrow explicit `sandbox.docker.ipc` break-glass field instead of raw Docker argument passthrough?

Rationale: GPU passthrough is already implemented and shipped, while host IPC changes the sandbox isolation boundary and config contract in a way automation should not choose alone.

Likely owner: steipete

Owner reason: They have the strongest recent history on sandbox namespace hardening and security-sensitive sandbox contract updates.

Owner confidence: high

Options:

- **Add narrow host IPC field (recommended):** Add an explicit opt-in IPC setting with schema, docs, config hashing, create-args tests, security-audit coverage, and warnings while keeping raw Docker args unsupported.
- **Reject host IPC in core:** Document that host IPC weakens sandbox isolation and keep GPU passthrough as the supported high-power Docker path.
- **Design broader namespace policy:** Pause implementation until maintainers define one policy for IPC, PID, network namespace joins, capabilities, and other dangerous Docker options.

## Reproduction Assessment

Yes. Source inspection reproduces the current state: `sandbox.docker.gpus` is accepted, resolved, documented, and emitted, while host IPC and raw Docker run arguments are absent from schema, config resolution, docs, and Docker create args.

## Solution Assessment

No for the proposed generic Docker-flag passthrough. The maintainable path is either no host IPC support or a narrow typed break-glass setting with security-owner approval and targeted tests.

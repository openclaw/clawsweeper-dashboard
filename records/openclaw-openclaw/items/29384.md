## Summary

Keep this open: GPU passthrough is already implemented and shipped, but host IPC or generic raw Docker argument passthrough is still absent and remains a sandbox security-boundary product decision.

## What This Changes

Request to allow Docker sandbox options such as `--gpus all` and `--ipc=host` for GPU and IPC-heavy workloads.

## Best Possible Solution

Keep the shipped typed GPU support, and add host IPC only if maintainers approve a narrow audited break-glass config field with schema, docs, config hashing, Docker create-args support, security-audit coverage, and tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose Docker host IPC for agent sandboxes, and if yes should it be a narrow typed `sandbox.docker.ipc` break-glass field instead of generic raw Docker argument passthrough?

Rationale: The remaining request changes the sandbox isolation boundary and public config contract; current code already solved GPU passthrough but intentionally keeps Docker options typed and audited.

Likely owner: steipete

Owner reason: This choice is closest to the sandbox security-boundary and dangerous Docker override policy history connected to steipete's recent commits.

Owner confidence: high

Options:

- **Add narrow IPC break-glass field (recommended):** Expose a typed opt-in IPC setting with schema, docs, config hashing, Docker create args, security-audit coverage, warnings, and tests while keeping raw Docker args unsupported.
- **Reject host IPC in core:** Document GPU passthrough as the supported high-power Docker path and keep host IPC unavailable because it weakens sandbox isolation.
- **Define broader namespace policy first:** Pause implementation until maintainers define one policy for IPC, PID, network namespace joins, capabilities, and other dangerous Docker options.

Yes. Source inspection reproduces the current state: typed `sandbox.docker.gpus` is accepted and emitted, while host IPC and raw Docker run arguments are absent from the config type, strict schema, resolver/create-args path, docs, and security-audit surface.

## Solution Assessment

No for generic Docker-flag passthrough. The maintainable solution is either no host IPC support or a narrow typed break-glass setting with maintainer security review and targeted validation.

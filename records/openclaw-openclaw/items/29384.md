## Summary

Keep this open: current main and v2026.6.11 already cover the GPU half with typed `sandbox.docker.gpus`, but host IPC or generic Docker argument passthrough is still absent and needs maintainer/security direction.

## What This Changes

The issue requests Docker sandbox configuration for parameters such as GPU passthrough and host IPC/raw Docker flags.

## Best Possible Solution

Keep the shipped typed GPU support, and add host IPC only if maintainers approve a narrow audited break-glass config field instead of generic raw Docker argument passthrough.

## Maintainer Decision

Required: true

Question: Should OpenClaw expose host IPC for Docker sandboxes, and if yes should it be a narrow `sandbox.docker.ipc` break-glass field instead of generic raw Docker argument passthrough?

Rationale: GPU passthrough is already implemented and shipped, while host IPC or raw Docker args would change the sandbox isolation boundary and public config contract.

Likely owner: steipete

Owner reason: The closest current-main history signal is their Docker namespace-join hardening and dangerous Docker override work.

Owner confidence: high

Options:

- **Add narrow IPC break-glass field (recommended):** Expose a typed opt-in IPC setting with schema, docs, config hashing, Docker create args, security-audit coverage, warnings, and tests while keeping raw Docker args unsupported.
- **Reject host IPC in core:** Document GPU passthrough as the supported high-power Docker path and keep host IPC unavailable because it weakens sandbox isolation.
- **Define broader namespace policy first:** Pause implementation until maintainers define one policy for IPC, PID, network namespace joins, capabilities, and other dangerous Docker options.

## Solution Assessment

No for generic Docker-flag passthrough. The maintainable solution is either no host IPC support or a narrow typed break-glass setting with maintainer security review and targeted validation.

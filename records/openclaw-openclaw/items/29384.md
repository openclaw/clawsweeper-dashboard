## Summary

Keep this open: current `main` and `v2026.6.11` satisfy the GPU part through typed `sandbox.docker.gpus`, but there is still no host IPC or raw Docker-argument passthrough, and the remaining request is a sandbox security-boundary product decision.

## What This Changes

The issue requests configurable Docker sandbox parameters for GPU access and host IPC, especially Docker flags like `--gpus all` and `--ipc=host`.

## Best Possible Solution

Keep the shipped typed GPU support, and only add a narrow audited host IPC break-glass field if security owners approve that sandbox tradeoff; do not add generic raw Docker argument passthrough.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose host IPC for Docker sandboxes, and if yes should it be a narrow explicit `sandbox.docker.ipc` break-glass field instead of raw Docker argument passthrough?

Rationale: Current source and release evidence show GPU passthrough is already implemented, while the remaining host IPC/raw-args request changes Docker sandbox isolation and the public config contract.

Likely owner: steipete

Owner reason: They have the strongest recent history on sandbox namespace hardening and source-backed sandbox security contracts.

Owner confidence: high

Options:

- **Add narrow host IPC field (recommended):** Add an explicit opt-in IPC setting with schema, docs, config hashing, Docker create-args, security-audit coverage, and tests while keeping raw Docker args unsupported.
- **Reject host IPC in core:** Document that host IPC weakens sandbox isolation and keep typed GPU passthrough as the supported high-power Docker path.
- **Design broader namespace policy:** Pause implementation until maintainers define a consistent policy for IPC, PID, network namespace joins, capabilities, and other dangerous Docker options.

## Reproduction Assessment

Yes. Source inspection reproduces the gap: `sandbox.docker.gpus` is accepted and emitted, while host IPC and raw Docker run arguments are absent from schema, config resolution, docs, and Docker create args.

## Solution Assessment

No for generic Docker-flag passthrough. The maintainable path is either no host IPC support or a narrow typed break-glass setting with security review, docs, audit coverage, and focused tests.

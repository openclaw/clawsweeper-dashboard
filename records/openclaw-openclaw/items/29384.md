## Summary

Keep this open: typed GPU passthrough is already implemented and shipped, but the host IPC/raw Docker-argument part remains missing and changes the sandbox security boundary.

## What This Changes

Request adding sandbox Docker configuration for custom Docker run parameters such as `--gpus all` and `--ipc=host`.

## Best Possible Solution

Keep the shipped typed GPU support, then either add a narrow audited `sandbox.docker.ipc` break-glass setting with docs/audit/tests or explicitly document host IPC as unsupported; avoid generic raw Docker args.

## Maintainer Decision

Rationale: The remaining request changes sandbox namespace isolation and the public config contract; automation can identify the shape, but maintainers must decide the acceptable security tradeoff.

Owner confidence: high

Options:

- **Add narrow host IPC field (recommended):** Implement explicit opt-in IPC support with schema, docs, config hashing or recreate behavior, security-audit/dangerous-flag coverage, and Docker argv tests while keeping raw args unsupported.
- **Reject host IPC in core:** Keep GPU passthrough as the supported high-power Docker path and document host IPC/raw args as unsupported because they weaken sandbox isolation.
- **Design broader namespace policy:** Pause implementation until maintainers define one policy for IPC, PID, network namespace joins, capabilities, and other dangerous Docker options.

## Solution Assessment

No for generic Docker-flag passthrough. The maintainable path is either an explicit audited host-IPC break-glass setting or a documented decision that host IPC stays unsupported.

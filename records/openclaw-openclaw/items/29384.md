## Summary

Keep this open: the GPU half is already implemented and shipped through typed `sandbox.docker.gpus`, but host IPC or raw Docker flag passthrough is still absent and would change the sandbox security boundary.

## What This Changes

The issue requests custom Docker sandbox parameters such as `--gpus all` and `--ipc=host` for GPU and host-IPC workloads.

## Best Possible Solution

Keep the shipped typed GPU support, and add host IPC only if maintainers approve a narrow audited break-glass config field with schema, docs, config hashing, Docker create-args support, security-audit coverage, and tests.

Rationale: The remaining request changes the sandbox isolation boundary and public config contract; source evidence shows GPU passthrough is solved, but host IPC/raw args are not a routine bug fix.

Options:

- **Add narrow IPC break-glass field (recommended):** Expose a typed opt-in IPC setting with validation, docs, config hashing, Docker create-args support, security-audit coverage, and focused tests while keeping raw Docker args unsupported.
- **Reject host IPC in core:** Document GPU passthrough as the supported high-power Docker path and keep host IPC unavailable because it weakens sandbox isolation.
- **Define namespace policy first:** Pause implementation until maintainers define one policy for IPC, PID, network namespace joins, capabilities, and other dangerous Docker options.

Yes. Source inspection reproduces the current state: typed `sandbox.docker.gpus` is accepted and emitted, while host IPC and raw Docker run arguments are absent from the strict config, resolver, Docker create-args, docs, and audit surface.

## Solution Assessment

No for generic Docker-flag passthrough. The maintainable solution is either no host IPC support or a narrow typed break-glass setting with maintainer security review and targeted validation.

## Label Justifications

- `impact:message-loss`: The reported pattern completes a child run without delivering its final result back to the originating external channel.
- `impact:session-state`: The issue centers on subagent registry completion metadata and delivery state for plugin-created child sessions.

## Summary

Keep open: current main and the latest release still register plugin-runtime subagent runs with completion delivery disabled, so the reported `subagent_delivery_target` and final external delivery path remains unresolved. The source gap is clear, but the fix changes public plugin-runtime delivery semantics and needs maintainer API/default direction.

## What This Changes

Request plugin-runtime subagent runs launched from `before_dispatch` to participate in subagent completion target resolution and deliver the final child result back to the external requester, or clearly document that this pattern is unsupported.

## Best Possible Solution

Define an explicit plugin-runtime completion-delivery contract, likely an opt-in `subagent.run` mode or documented unsupported behavior, then wire registry registration, announce delivery, `subagent_delivery_target`, docs, and regression tests without surprising existing background-run defaults.

## Reproduction Assessment

Yes, at source level: current main marks plugin-runtime runs as tracked subagents but registers them with `expectsCompletionMessage: false`, and that skips the announce path that would run `subagent_delivery_target`. I did not run a live iMessage/plugin harness in this read-only review.

## Solution Assessment

Unclear pending maintainer API/default direction. Flipping the default is risky; an explicit opt-in completion-delivery mode with docs and regression coverage is the safer likely solution.

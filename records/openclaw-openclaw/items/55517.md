## Summary

Keep open: current main and the latest release still register plugin-runtime `subagent.run()` child runs with completion delivery disabled, so `subagent_delivery_target` and final external delivery do not run for this path. The source gap is clear, but changing it needs maintainer API/defaults direction because existing plugin background runs could start sending new user-visible final messages.

## What This Changes

The issue requests a supported core path for plugin `before_dispatch` hooks that start `api.runtime.subagent.run()` child work to later deliver the child completion back through `subagent_delivery_target` to the originating external channel.

## Best Possible Solution

Define a maintainer-approved explicit plugin-runtime completion-delivery contract, likely an opt-in `subagent.run` mode, then wire registry registration, announce delivery, `subagent_delivery_target`, docs, and regression tests around that contract while preserving existing background-run defaults unless maintainers intentionally change them.

## Reproduction Assessment

Yes, at source level: current main marks plugin-runtime runs as tracked subagents but registers them with `expectsCompletionMessage: false`, and that skips the announce path that would run `subagent_delivery_target`. I did not execute a live iMessage/plugin harness in this read-only review.

## Solution Assessment

Unclear pending maintainer API/default direction. Flipping the default is risky; an explicit opt-in completion-delivery mode with docs and regression coverage is the safer likely solution.

## Summary

Keep open: current main and the latest release still register plugin-runtime subagent runs with completion delivery disabled, so the reported final external delivery and `subagent_delivery_target` path remains unresolved. The merged related PR fixed lifecycle tracking for `subagent_ended`, but it intentionally keeps plugin-created runs out of completion announce delivery.

## What This Changes

The issue asks for `api.runtime.subagent.run()` calls made from `before_dispatch` to participate in subagent completion delivery so the final child result can reach the originating external channel.

## Best Possible Solution

Add a maintainer-approved explicit plugin-runtime completion-delivery contract, likely an opt-in `subagent.run` mode, then wire registry metadata, announce delivery, `subagent_delivery_target`, docs, and tests around that contract.

## Reproduction Assessment

Yes, at source level: current main marks plugin-runtime runs as tracked subagents but registers them with `expectsCompletionMessage: false`, which skips the announce path that would run `subagent_delivery_target`. I did not run a live iMessage/plugin harness in this read-only review.

## Solution Assessment

Unclear pending maintainer API/default direction. Flipping the existing default is risky; an explicit opt-in completion-delivery mode with docs and regression coverage is the safer likely solution.

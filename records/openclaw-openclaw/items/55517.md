## Summary

Keep open: current main and v2026.6.11 still treat plugin-runtime `api.runtime.subagent.run()` runs as background subagents with completion delivery disabled, so the reported final external delivery path remains unresolved and needs a maintainer API/default decision.

## What This Changes

Plugin authors want `api.runtime.subagent.run()` called from `before_dispatch` to support deferred final delivery through `subagent_delivery_target` back to the originating external channel.

## Best Possible Solution

Add a maintainer-approved, explicit plugin-runtime completion-delivery contract, likely opt-in, then wire it through registry metadata, announce delivery, `subagent_delivery_target`, docs, and focused upgrade-safe tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should plugin-runtime `api.runtime.subagent.run()` support requester-visible completion delivery, and if so should it be opt-in or the default?

Rationale: The source gap is clear, but the choice changes public Plugin SDK semantics and could make existing background plugin tasks start sending user-visible final messages.

Likely owner: steipete

Owner reason: Recent merged work and adjacent announce-delivery history make this the best available owner for the public API/default decision.

Owner confidence: high

Options:

- **Add Opt-In Completion Delivery (recommended):** Introduce an explicit completion-delivery option or mode that records requester/origin metadata and runs the existing announce plus `subagent_delivery_target` path only when requested.
- **Make Completion Delivery Default:** Treat plugin-runtime subagent runs like core subagent spawns by default, accepting compatibility risk for existing background tasks.
- **Document Background-Only Semantics:** Keep `api.runtime.subagent.run()` detached/background-only and document that plugins must poll and send their own deferred results.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 register plugin-runtime subagent runs with `expectsCompletionMessage: false`, and that skips the announce path that would run `subagent_delivery_target`; I did not run a live iMessage/plugin harness in this read-only review.

## Solution Assessment

Unclear pending maintainer API/default direction. Flipping the default is risky; an explicit opt-in completion-delivery mode with docs and regression coverage is the safer likely solution.

## Summary

Keep open: current main and v2026.6.11 still register plugin-runtime subagent runs with completion delivery disabled, so the reported `subagent_delivery_target` and final external delivery path remains unresolved; the related merged PR fixed lifecycle tracking only.

## What This Changes

The issue asks for plugin-runtime subagent runs launched from `before_dispatch` to participate in `subagent_delivery_target` and final external delivery.

## Best Possible Solution

Define an explicit plugin-runtime completion-delivery contract, likely opt-in, then wire it through registry registration, announce delivery, `subagent_delivery_target`, docs, and regression tests while preserving current background-run defaults unless maintainers choose otherwise.

## Reproduction Assessment

Yes, at source level: current main registers plugin-runtime subagent runs with `expectsCompletionMessage: false`, and the completion-delivery hook path is gated on that flag being true. I did not run a live iMessage/plugin harness in this read-only review.

## Solution Assessment

Unclear pending maintainer API/default direction. Flipping the default is risky; an explicit opt-in completion-delivery mode with docs and regression coverage is the safer likely solution.

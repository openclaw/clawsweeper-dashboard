## Summary

Keep open: current main and v2026.6.11 still register plugin-runtime subagent runs with completion delivery disabled, so the reported final external delivery and `subagent_delivery_target` path remains unresolved; changing that behavior needs maintainer API/default direction.

## What This Changes

Request support or clear documentation for `api.runtime.subagent.run()` started from `before_dispatch` to participate in subagent completion delivery and `subagent_delivery_target`.

## Best Possible Solution

Define a maintainer-approved explicit plugin-runtime completion-delivery contract, likely opt-in on `subagent.run`, then wire requester origin, registry metadata, announce delivery, `subagent_delivery_target`, docs, and tests around that contract while preserving existing background-run defaults unless maintainers decide otherwise.

## Reproduction Assessment

Yes at source level: current main marks plugin-runtime runs as tracked subagents but registers them with `expectsCompletionMessage: false`, which prevents the announce path that would run `subagent_delivery_target`. I did not run a live iMessage/plugin harness in this read-only review.

## Solution Assessment

Unclear until maintainers decide the public API/default semantics. An unconditional default flip is risky; an explicit opt-in completion-delivery mode or clearly documented unsupported path is the safer product shape.

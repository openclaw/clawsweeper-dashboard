- `impact:message-loss`: The reported pattern completes a child run without delivering its final result back to the originating external channel.

## Summary

Keep open: current main and v2026.6.11 still register plugin-runtime subagent runs with completion delivery disabled, so the reported `subagent_delivery_target` and final external delivery path remains unresolved. The related merged PR fixed the adjacent `subagent_ended` lifecycle gap, but the remaining behavior needs an explicit plugin-runtime delivery contract rather than conservative cleanup closure.

## What This Changes

The issue asks for plugin runtime `api.runtime.subagent.run()` calls started from `before_dispatch` to participate in `subagent_delivery_target` and final external completion delivery, or for that unsupported behavior to be documented.

## Best Possible Solution

Approve an explicit plugin-runtime completion-delivery contract, likely opt-in, then wire requester-origin capture, registry metadata, announce delivery, `subagent_delivery_target`, docs, and regression coverage while preserving existing background-run defaults unless maintainers intentionally change them.

## Reproduction Assessment

Yes, at source level: current main marks plugin-runtime runs as tracked subagents but registers them with `expectsCompletionMessage: false`, and that prevents the completion-origin hook path from running. I did not execute a live iMessage/plugin harness in this read-only review.

## Solution Assessment

Unclear pending maintainer API/default direction. Flipping the default is risky; an explicit opt-in completion-delivery mode with docs and regression coverage is the safer likely solution.

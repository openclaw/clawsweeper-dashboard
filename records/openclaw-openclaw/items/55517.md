## Summary

Keep open: current main and the latest release still register plugin-runtime subagent runs with completion delivery disabled, so the reported `subagent_delivery_target` and final external delivery path remains unresolved; this now needs maintainer API/default direction rather than conservative cleanup closure.

## What This Changes

Request to make plugin-runtime `api.runtime.subagent.run()` started from `before_dispatch` participate in completion delivery so `subagent_delivery_target` can resolve and deliver the final child result to the original external requester.

## Best Possible Solution

Approve an explicit plugin-runtime completion-delivery contract, likely opt-in, then wire it through registry registration, announce delivery, `subagent_delivery_target`, docs, and focused upgrade-safe tests while preserving background-run defaults unless maintainers choose otherwise.

Options:

- **Add opt-in completion delivery (recommended):** Introduce an explicit plugin-runtime option or mode that registers expected completion delivery and routes through the existing announce and delivery-target machinery.
- **Document background-only semantics:** Keep plugin-runtime subagent runs detached by default and document that plugins must poll or handle completion themselves.
- **Make completion delivery default:** Flip plugin-runtime subagent runs into expected-completion delivery by default, accepting the compatibility risk for existing plugins.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 register plugin-runtime runs with `expectsCompletionMessage: false`, which skips the announce path that would run `subagent_delivery_target`. I did not execute a live iMessage/plugin harness in this read-only review.

## Solution Assessment

Unclear pending maintainer API/default direction. Flipping the default is risky; an explicit opt-in completion-delivery mode with docs and regression coverage is the safer likely path.

## Summary

Keep open: current main and v2026.6.11 still register plugin-runtime subagent runs as tracked background subagents with completion delivery disabled, so the reported `subagent_delivery_target` and final external delivery path remains unresolved. The source gap is clear, but changing it needs maintainer API/default direction because plugin `api.runtime.subagent.run()` is a public SDK surface.

## What This Changes

The issue asks for plugin-runtime `api.runtime.subagent.run()` calls started from `before_dispatch` to have a supported path for later completion delivery through `subagent_delivery_target` back to the original external requester.

## Best Possible Solution

Add a maintainer-approved explicit plugin-runtime completion-delivery contract, likely an opt-in `subagent.run` mode, then wire it through registry registration, announce delivery, `subagent_delivery_target`, docs, and upgrade-safe tests while preserving background-run defaults unless maintainers decide otherwise.

Question: Should plugin-runtime `api.runtime.subagent.run()` support requester-visible completion delivery, and if so should it be opt-in or the default?

Rationale: The source gap is clear, but the choice changes public Plugin SDK semantics and could make existing background plugin tasks start sending user-visible final messages.

Likely owner: steipete

Owner confidence: high

Options:

- **Add Opt-In Completion Delivery (recommended):** Introduce an explicit completion-delivery option or mode that registers requester/origin metadata and runs the existing announce plus `subagent_delivery_target` path only when requested.
- **Make Completion Delivery Default:** Treat plugin-runtime subagent runs like core subagent spawns by default, accepting the compatibility risk that current background tasks may start producing external final messages.
- **Document Background-Only Semantics:** Keep `api.runtime.subagent.run()` detached/background-only and update docs to require plugins to poll and send their own deferred results.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 register plugin-runtime subagent runs with `expectsCompletionMessage: false`, and that skips the announce path that would run `subagent_delivery_target`; I did not run a live iMessage/plugin harness in this read-only review.

## Solution Assessment

Unclear pending maintainer API/default direction. Flipping the default is risky; an explicit opt-in completion-delivery mode with docs and regression coverage is the safer likely solution.

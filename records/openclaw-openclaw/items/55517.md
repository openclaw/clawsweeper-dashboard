## Summary

Keep open: current main and the latest release still register plugin-runtime subagent runs with completion delivery disabled, so this remains a valid plugin-runtime delivery contract gap rather than an already-fixed issue.

## What This Changes

The issue asks for `api.runtime.subagent.run()` calls started from `before_dispatch` to participate in final external completion delivery through `subagent_delivery_target`.

## Best Possible Solution

Define an explicit, maintainer-approved plugin-runtime completion-delivery contract, likely an opt-in `subagent.run` mode, then wire it through Gateway registration, registry delivery state, announce target resolution, docs, and upgrade-safe tests while preserving the current background-run default unless maintainers choose otherwise.

## Reproduction Assessment

Yes, at source level: current main marks plugin-runtime runs as tracked subagents but registers them with `expectsCompletionMessage: false`, and the lifecycle code skips the announce path that would run `subagent_delivery_target`. I did not run a live iMessage/plugin harness in this read-only review.

## Solution Assessment

Unclear pending maintainer API/default direction. Flipping the default is risky; an explicit opt-in completion-delivery mode with docs and regression coverage is the safer likely solution.

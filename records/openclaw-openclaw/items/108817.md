## Summary

Keep this PR open: the fallback goal is useful, but the current creation-time heuristic can resolve a different widget than the newest successfully delivered button when same-channel tool calls run concurrently. The sequential regression test does not cover that race, and no after-fix live Discord proof is attached.

## What This Changes

Changes Discord Activity launches without a custom ID from rejecting multiple channel widgets to selecting the newest stored widget, with matching tests and documentation.

## Best Possible Solution

Record a monotonic successful-delivery order after each Discord send and use that order for missing-ID fallback while preserving exact-ID lookup; cover reversed send completion in a regression test and demonstrate the result in a redacted live Discord run.

## Reproduction Assessment

Yes, the source provides a high-confidence reproduction path: start two same-channel widget tool calls, delay the earlier-created send until after the later-created send, then launch the newest visible button without a custom ID. This path was not executed during the read-only review.

## Solution Assessment

No. Selecting by pre-send createdAt is plausible for sequential calls but does not represent visible Discord delivery order; a post-delivery monotonic signal is the narrower reliable fix.

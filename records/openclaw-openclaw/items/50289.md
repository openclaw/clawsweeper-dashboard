## Summary

Keep open: current main and latest release still walk and linearly match large `commands.ownerAllowFrom` arrays during command authorization, and both linked fix attempts are closed unmerged.

## What This Changes

The issue reports severe gateway slowdown when a very large `commands.ownerAllowFrom` allowlist is processed during per-message command authorization.

## Best Possible Solution

Keep this as the canonical bug and fix command authorization by compiling or caching provider-scoped owner authorization lookup state so repeated message authorization avoids rebuilding and linearly scanning large allowlists.

## Reproduction Assessment

Yes. Source inspection on current main shows the reported authorization path still walks and linearly checks large owner allowlists; I did not run a live 9,000-entry Gateway benchmark.

## Solution Assessment

Yes for keeping it open. The best fix belongs in command-auth/runtime authorization, should preserve the existing config shape, and should make repeated lookup work cached or O(1) instead of adding a new workaround surface.

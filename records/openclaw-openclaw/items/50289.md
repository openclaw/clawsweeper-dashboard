## Label Justifications

- `P2`: This is a bounded Gateway command-authorization performance bug with severe latency under unusually large owner allowlists but limited blast radius.
- `impact:crash-loop`: The reported 15-27 second message latency and lane wait warnings can make affected Gateway deployments effectively unavailable.
- `maturity:stable`: The issue affects Gateway runtime command authorization, and `gateway-runtime` is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and v2026.6.11 still walk and linearly check large `commands.ownerAllowFrom` arrays during command authorization, and both linked fix attempts are closed unmerged.

## What This Changes

The issue reports severe Gateway message latency when `commands.ownerAllowFrom` contains thousands of IDs because authorization normalizes and scans the list on each message.

## Best Possible Solution

Land a narrow command-auth fix that caches or compiles provider-scoped owner authorization lookups and uses Set-based membership while preserving existing owner authorization semantics.

## Reproduction Assessment

Yes at source level: current main still normalizes large `commands.ownerAllowFrom` arrays and performs linear owner membership checks in the message authorization path. I did not run a live 9,000-entry Gateway benchmark in this read-only review.

## Solution Assessment

Yes for triage: keeping this issue open and queueing a narrow command-auth repair is the best path. A wildcard workaround or new config surface would trade away security semantics instead of fixing the hot path.

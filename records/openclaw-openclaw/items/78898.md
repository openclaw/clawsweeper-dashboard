## Summary

Keep open: current main and the latest release still have the QQBot RECONNECT/4009 session-clearing bug, and this PR is a useful candidate fix, but it is not merge-ready because it bypasses close-code policy too broadly and lacks after-fix live QQBot proof.

## What This Changes

The PR adds a GatewayConnection flag that skips close handling after QQBot GatewayOp.RECONNECT so sessionId and lastSeq survive for a later RESUME attempt.

## Best Possible Solution

Land a narrow QQBot reconnect-policy fix that preserves session only for RECONNECT plus 4009, leaves invalid and fatal close codes on handleClose, and includes focused regression coverage plus redacted live QQBot proof.

## Reproduction Assessment

Yes. Source inspection shows RECONNECT closes the socket, the close handler routes 4009 through clearSession, and the next HELLO cannot RESUME without sessionId and lastSeq; I did not run a live QQBot connection in this read-only review.

## Solution Assessment

No, not yet. Preserving state for RECONNECT plus 4009 is the right boundary, but this implementation should scope the close-handler bypass to the resumable 4009 case and leave other close codes on the existing policy path.

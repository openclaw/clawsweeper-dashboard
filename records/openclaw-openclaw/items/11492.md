## Label Justifications

- `P3`: This is a useful but non-regression Slack discovery enhancement with limited blast radius and an unresolved policy choice.
- `impact:other`: Agents cannot translate Slack channel IDs into human-readable channel context through the message tool, creating a concrete usability limitation outside the specific impact categories.

## Summary

The issue remains necessary because current main still exposes neither requested Slack discovery action, and no merged related change replaces that agent-facing capability.

## What This Changes

Add Slack `channel-info` and `channel-list` message actions so agents can resolve channel IDs and enumerate workspace conversations.

## Best Possible Solution

Adopt one focused Slack-plugin implementation that adds both actions, paginates Slack results, applies the existing read-token and channel-policy model to metadata disclosure, documents scopes and gates, and includes focused tests plus redacted live Slack proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `channel-list` expose every conversation visible to the selected Slack read token, or only conversations allowed by OpenClaw's configured Slack channel policy?

Rationale: The codebase defines authorization for reads targeting a known channel, but it does not define the disclosure boundary for agent-initiated workspace enumeration; that choice affects private-channel and DM metadata.

Likely owner: steipete

Owner reason: This person has the strongest recent history across Slack action discovery, runtime, tests, and documentation and is best positioned to resolve the disclosure contract.

Owner confidence: high

Options:

- **Filter through channel policy (recommended):** Expose both actions but return only conversations authorized by the effective Slack group/channel policy, with private and DM discovery excluded unless explicitly allowed.
- **Return token-visible conversations:** Expose every conversation returned by Slack for the selected read token behind the existing `channelInfo` action gate.
- **Ship channel-info only:** Allow lookup of a supplied channel ID while deferring workspace enumeration until a separate discovery policy is designed.

## Reproduction Assessment

Yes at source level: current Slack action registration, runtime dispatch, and documentation omit both `channel-info` and `channel-list`, so the requested calls are unavailable on current main.

## Solution Assessment

Partly. Implementing both actions in `extensions/slack` follows the correct owner boundary, but direct Discord parity is incomplete until Slack token selection, pagination, and enumeration authorization are explicitly defined.

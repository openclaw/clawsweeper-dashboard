## Summary

This feature remains necessary: current main can resolve Slack conversation names internally for authorization, but agents still cannot invoke `channel-info` or `channel-list`. The same-repository implementation attempts closed unmerged, while the currently linked fork branch covers listing but not the requested per-channel lookup.

## What This Changes

Requests agent-facing Slack `channel-info` and `channel-list` message actions for resolving channel IDs and discovering workspace channels.

## Best Possible Solution

Implement both actions within `extensions/slack`, use cursor pagination, align lookup credentials with the selected account, filter or authorize returned conversations under an explicit policy, reuse the existing `channelInfo` gate unless maintainers approve a separate listing gate, and add focused contract tests, Slack docs, and redacted live-workspace proof.

Owner confidence: high

Options:

- **Policy-filtered discovery (recommended):** Expose both actions through the existing `channelInfo` gate and return only conversations allowed by the configured Slack channel policy.
- **Token-visible discovery:** Expose every conversation visible to the selected Slack token behind an explicit, separately approved listing gate.
- **Channel lookup only:** Add per-ID `channel-info` now and defer workspace enumeration until maintainers define its disclosure contract.

## Solution Assessment

Not yet. Implementing the APIs inside the Slack plugin is the correct owner boundary, but the proposal must first define pagination, channel-policy filtering, credential selection, and whether the existing gate covers enumeration.

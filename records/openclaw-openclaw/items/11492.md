## Summary

This feature remains necessary: current main has internal Slack channel-name lookup for authorization, but still does not expose agent-facing `channel-info` or `channel-list`; the linked implementation candidate adds listing and unrelated search but omits `channel-info`, so it does not fully own the request. citeturn841437view0turn239402view0

## What This Changes

Expose Slack `channel-info` and `channel-list` message actions so agents can resolve channel IDs and discover accessible workspace conversations.

## Best Possible Solution

Implement target-scoped `channel-info` and an explicitly opt-in, access-policy-filtered `channel-list` in `extensions/slack`, with pagination, scope documentation, focused tests, and redacted live Slack proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack agents enumerate every conversation visible to their token, or should `channel-list` be separately gated and filtered to OpenClaw-authorized channels while `channel-info` remains target-scoped?

Rationale: Targeted metadata lookup and workspace-wide enumeration have materially different disclosure and permission boundaries, so code structure alone cannot determine the intended product policy.

Likely owner: steipete

Owner reason: Their recent history spans Slack action configuration, discovery, dispatch, runtime, tests, and documentation, covering the full decision surface.

Owner confidence: high

Options:

- **Scoped lookup and filtered listing (recommended):** Expose target-scoped `channel-info`, then make `channel-list` separately opt-in and return only conversations allowed by OpenClaw channel policy.
- **Shared discovery gate:** Enable both actions under one existing discovery gate and explicitly document that listing may enumerate every conversation visible to the selected Slack token.
- **Land lookup only:** Implement `channel-info` now and track workspace enumeration separately after its access-policy and token-scope behavior is decided.

## Reproduction Assessment

Not applicable as a regression; source inspection gives high-confidence confirmation that current Slack action discovery and runtime omit both requested agent-facing actions.

## Solution Assessment

No—the direct Discord-parity proposal does not sufficiently separate target lookup from workspace enumeration; the safer design uses distinct gating and applies Slack channel access policy to listing.

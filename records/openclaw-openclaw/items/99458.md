## Summary

Keep open: current main and the latest release still reject a root-level `paperclip` field on `agent` RPC params, and all prior implementation PRs for this exact Paperclip gateway compatibility issue are closed unmerged. The remaining work is real, but the protocol shape needs maintainer API judgment before a fix should be queued.

## What This Changes

Request to let Gateway `AgentParamsSchema` accept Paperclip adapter metadata, either through a `paperclip` field or a generic adapter metadata namespace, so Paperclip heartbeats are not rejected before dispatch.

## Best Possible Solution

Choose and land an additive Gateway protocol contract in `packages/gateway-protocol/src/schema/agent.ts`, update generated client artifacts and focused validator coverage, then close this issue once Paperclip heartbeats validate on the chosen shape.

## Reproduction Assessment

Yes, source-level: a valid `agent` request with an extra root `paperclip` property reaches the closed `AgentParamsSchema`, and the handler returns `invalid agent params` before dispatch. I did not run a live Paperclip gateway deployment in this read-only review.

## Solution Assessment

Unclear as proposed: accepting every unknown property would weaken the closed protocol contract, while a generic `adapterMeta` namespace plus a temporary `paperclip` alias is plausible but needs maintainer approval as a public wire-contract addition.

## Summary

Keep open: current main still starts automatic remote bin probes for connected macOS app-backed nodes that advertise `system.which` or `system.run`; the latest stable release has the same core probe shape, and the related PRs are either closed as not planned or still open but not a safe canonical fix.

## What This Changes

The issue asks OpenClaw to stop macOS app-backed node remote skill bin probes from timing out during gateway startup or reconnect, especially when the app node is co-located with the gateway.

## Best Possible Solution

Settle a narrow macOS app-node readiness and probe policy in `src/skills/runtime/remote.ts`, preserve valid `system.which` and `system.run` support, and prove the result with a real macOS app node.

Question: Should automatic remote skill bin probing for macOS app-backed nodes be deferred with backoff, skipped only for proven co-located app nodes, or disabled by default for app nodes?

Rationale: The current macOS app node intentionally advertises and handles `system.which` and `system.run`, so the fix affects product semantics for remote skills and node execution rather than being a purely mechanical timeout patch.

Likely owner: steipete

Owner confidence: high

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but wait for stronger app-node readiness and add bounded retry/backoff after failed probes.
- **Skip Proven Co-located App Nodes:** Avoid probing loopback or same-host app nodes that add no remote skill value while preserving remote app-node probing.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless explicitly enabled, reducing warning noise at the cost of default remote skill support.

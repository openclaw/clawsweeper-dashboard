## Summary

Keep open: current main and the latest stable release still automatically probe connected macOS app-backed nodes that advertise `system.which` or `system.run`; the original missing-handler theory is partly obsolete, but the connect-readiness, co-location, and retry/backoff policy remains unresolved.

## What This Changes

Report that automatic remote skill binary probing times out for macOS app-backed nodes on gateway startup or reconnect, especially when the app node is co-located with the gateway.

## Best Possible Solution

Settle a narrow macOS app-node readiness and probe policy in the active `src/skills/runtime/remote.ts` path, preserve valid `system.which`/`system.run` support, and prove it with a real macOS app node.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should automatic remote skill bin probing for macOS app-backed nodes be deferred with backoff, skipped only for proven co-located app nodes, or disabled by default for app nodes?

Rationale: Current code intentionally supports macOS app-node `system.which` and `system.run`, so the fix affects product semantics for remote skills and node execution rather than a purely mechanical timeout patch.

Likely owner: steipete

Owner reason: The strongest feature-history signal spans remote skills, mac node exec policy, and the remote probe behavior under review.

Owner confidence: high

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but wait for stronger app-node readiness and add bounded retry/backoff after failed probes.
- **Skip Co-located App Nodes:** Avoid probing loopback or same-host app nodes that add no remote skill value while preserving remote app-node probing.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless explicitly enabled, reducing warning noise at the cost of default remote skill support.

## Reproduction Assessment

No live high-confidence current-main reproduction was run. Source inspection still shows automatic probing of connected macOS app nodes that expose `system.which` or `system.run`, and the issue comments provide real macOS app-node timeout evidence.

## Solution Assessment

Unclear as a final implementation: removing command support or adding a broad config flag is not the best fix. A narrow readiness, co-location, or backoff policy that preserves valid remote macOS node execution is the maintainable direction.

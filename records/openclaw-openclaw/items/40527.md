## Summary

Keep open: current main and v2026.6.11 still automatically probe connected macOS app-backed nodes that advertise `system.which` or `system.run`; the remaining repair needs a maintainer choice on readiness timing, co-located-node handling, and retry/backoff semantics.

## What This Changes

The issue reports macOS app-backed node remote skill bin probes timing out during gateway startup or reconnect, especially when the app node is co-located with the gateway.

## Best Possible Solution

Settle a narrow macOS app-node readiness and probe policy in `src/skills/runtime/remote.ts`, preserve valid `system.which` and `system.run` support, and prove it with a real macOS app node.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should automatic remote skill bin probing for macOS app-backed nodes be deferred with backoff, skipped only for proven co-located app nodes, or disabled by default for app nodes?

Rationale: Current code intentionally supports macOS app-node `system.which` and `system.run`, so the fix changes product semantics for remote skills and node execution rather than being a purely mechanical timeout patch.

Likely owner: steipete

Owner reason: The strongest feature-history signal spans remote skills, mac node exec policy, and the remote probe behavior under review.

Owner confidence: high

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but wait for stronger app-node readiness and add bounded retry/backoff after failed probes.
- **Skip Co-located App Nodes:** Avoid probing loopback or same-host app nodes that add no remote skill value while preserving remote app-node probing.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless explicitly enabled, reducing warning noise at the cost of default remote skill support.

## Reproduction Assessment

No live high-confidence current-main reproduction was run. Source inspection still shows the automatic macOS app-node probe path, and the issue discussion provides real macOS app-node timeout evidence.

## Solution Assessment

Unclear as a final implementation: removing command support or adding a broad config flag is not the best fix. A narrow readiness, co-location, or backoff policy that preserves valid remote macOS node execution is the maintainable direction.

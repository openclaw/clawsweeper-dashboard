## Summary

Keep open: current main and the latest release still automatically probe connected macOS nodes that expose `system.which` or `system.run`; the original missing-handler theory is partly obsolete, but the readiness, co-location, and backoff policy remains unresolved.

## What This Changes

The issue asks OpenClaw to stop macOS app-backed remote skill binary probes from timing out and warning during gateway startup or node reconnect.

## Best Possible Solution

Define a narrow macOS app-node remote bin probe policy in the gateway remote-skill path: defer until readiness is stronger, add bounded retry/backoff, skip proven co-located app nodes only when they add no remote value, and preserve valid `system.which`/node exec support.

Owner confidence: high

Options:

- **Defer and back off probes (recommended):** Keep app-node `system.which` support, but delay initial probing until node readiness is stronger and add bounded retry/backoff after failures.
- **Skip co-located app nodes:** Avoid probing loopback or same-host app nodes while continuing to probe remote macOS nodes that can provide skill binaries.
- **Disable app-node probing by default:** Remove automatic app-node remote skill eligibility unless explicitly enabled, reducing warnings at the cost of default remote macOS skill support.

## Summary

Keep open: current `main` and the latest release have mitigations around desktop host-command defaults, but they still immediately run the remote skill bin probe when a macOS app-backed node advertises `system.which` or `system.run`; the related repair PRs are open/conflicting or closed unmerged.

## What This Changes

The issue asks OpenClaw to avoid remote skill bin probe timeouts and misleading gateway warnings for macOS app-backed nodes, especially when the app node is co-located with the gateway or not ready immediately after connect.

## Best Possible Solution

Keep this issue open and settle a narrow gateway/macOS node policy: probe only after real readiness/capability proof, preserve desktop host-command safety, add bounded retry/backoff, and validate both co-located and remote macOS app-node scenarios with live proof.

Rationale: The code can be fixed several plausible ways, but each changes user-visible remote skill availability, startup latency, and the security-sensitive boundary between app nodes and host-command nodes.

Owner reason: He is the clearest feature-history owner for the remote skills probe and mac node exec policy surfaces.

Owner confidence: high

Options:

- **Require readiness-aware probe policy (recommended):** Keep macOS app node command support, but defer the first bin probe until connectivity/readiness is proven and add bounded backoff after failed probes, with live co-located and remote-node proof.
- **Split app and host capabilities:** Make app-backed nodes omit host-command capability until the app can actually service the probe path, leaving CLI/node-host sessions as the immediate probe targets.
- **Add an operator opt-out:** Add a config flag only if maintainers decide users need a manual escape hatch after the default readiness behavior is fixed.

## Reproduction Assessment

No live current-main reproduction was run here. Source inspection gives a medium-confidence reproduction path: a connected macOS node advertising `system.which` or `system.run` and a Darwin skill bin requirement still triggers the remote bin probe immediately, with a 2s connectivity preflight and 15s invoke timeout.

## Solution Assessment

Unclear as a final implementation path. Skipping co-located app nodes, capability declaration, app-vs-host defaults, and probe backoff are all plausible, but the best maintainable fix should first choose the readiness/capability contract and then prove it on real macOS app nodes.

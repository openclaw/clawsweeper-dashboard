## Summary

Keep open: current main and the latest release still immediately probe connected macOS app-backed nodes that advertise `system.which` or `system.run`; the original missing-handler part has changed, but the remaining readiness/co-location/backoff policy is unresolved and no merged PR owns it.

## What This Changes

The issue reports remote skill binary probe timeouts for macOS app-backed nodes, especially when the app node is co-located with the gateway.

## Best Possible Solution

Settle the macOS app-node readiness, co-location, and retry/backoff policy in `src/skills/runtime/remote.ts` while preserving valid `system.run`/`system.which` node execution, then prove it with a real macOS app node.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should automatic remote skill bin probing for macOS app-backed nodes be deferred/backed off, skipped only for proven co-located app nodes, or disabled by default for app nodes?

Rationale: Current code supports macOS app-node `system.run` and `system.which`, so the remaining fix crosses readiness timing, co-location detection, retry policy, and node exec compatibility rather than a purely mechanical source patch.

Likely owner: steipete

Owner reason: The feature history for remote mac node skills, bin probing, and node command policy makes this the best routing owner for the product-boundary decision.

Owner confidence: high

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but delay the initial app-node probe until readiness is stronger and add bounded retry/backoff after failed probes.
- **Skip Only Co-located App Nodes:** Avoid probing loopback or same-install app nodes that cannot add remote skill value, while preserving remote app-node probing for hosts that can execute skills.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless explicitly enabled, reducing warning noise at the cost of default remote skill support.

## Solution Assessment

Is this the best way to solve the issue? Not yet; a broad config flag or command-surface removal is not the best fix, while the maintainable direction is a narrow readiness, co-location, or backoff policy in the active remote-skills runtime.

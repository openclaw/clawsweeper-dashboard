## Summary

Keep open: current main fixed part of the original report by adding macOS app `system.which` handling and removing desktop host commands from static defaults, but the active runtime still automatically probes approved macOS app-backed nodes that advertise `system.which` or `system.run`, and no merged PR has settled the readiness/backoff or co-located-node policy.

## What This Changes

The issue reports remote macOS app-backed node skill binary probes timing out during startup or reconnect when the node is co-located with the gateway or not ready for immediate probing.

## Best Possible Solution

Settle the macOS app-node readiness and remote-bin probe policy in the active `src/skills/runtime/remote.*` path so probes wait for a ready node or back off cleanly without disabling legitimate remote node execution.

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but delay initial app-node probes until readiness is stronger and add bounded retry/backoff for failed probes.
- **Skip Co-located App Nodes:** Avoid probing loopback or co-located app nodes while preserving remote app-node probing for hosts that can execute skills.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless users explicitly enable it, reducing warnings at the cost of default remote skill support.

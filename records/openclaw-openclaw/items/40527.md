## Summary

Keep open: current main and the latest stable release still automatically probe connected macOS app-backed nodes that expose `system.which` or `system.run`; the original missing-handler theory is partly obsolete, but the readiness, co-location, and retry/backoff policy remains unresolved.

## What This Changes

The issue asks OpenClaw to stop automatic remote skill binary probes from timing out or warning for macOS app-backed nodes, especially co-located gateway/app setups.

## Best Possible Solution

Settle a narrow macOS app-node readiness and probe policy in the active `src/skills/runtime/remote.ts` path, preserve valid `system.which`/`system.run` support, and prove it with a real macOS app node.

Question: Should automatic remote skill bin probing for macOS app-backed nodes be deferred with backoff, skipped only for proven co-located app nodes, or disabled by default for app nodes?

Rationale: Current code intentionally supports macOS app-node `system.which` and `system.run`, so the fix affects product semantics for remote skills and node execution rather than being a purely mechanical timeout patch.

Likely owner: steipete

Owner reason: This owner has the strongest feature-history signal across remote skills, mac node exec policy, and remote probe logging.

Owner confidence: high

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but wait for stronger app-node readiness and add bounded retry/backoff after failed probes.
- **Skip Co-located App Nodes:** Avoid probing loopback or same-host app nodes that add no remote skill value while preserving remote app-node probing.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless explicitly enabled, reducing warning noise at the cost of default remote skill support.

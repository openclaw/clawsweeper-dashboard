## Summary

Keep open: current main has moved past the original “macOS app lacks handlers” diagnosis, but it still automatically probes app-backed macOS nodes that advertise `system.which` or `system.run`; the remaining readiness, co-location, and backoff policy is not settled.

## What This Changes

The issue reports timeout noise and startup delay from remote skill binary probes against macOS app-backed nodes, especially when the app node is co-located with the gateway.

## Best Possible Solution

Keep the issue open until maintainers choose and validate the canonical remote-bin-probe policy for macOS app nodes: readiness/defer behavior, co-located-node handling, and bounded retry/backoff without breaking documented `exec host=node` skill support.

Question: Should OpenClaw treat macOS app-backed nodes as immediately eligible for automatic remote skill bin probing, or should the gateway defer/skip/back off probes for app/co-located nodes until explicit readiness is proven?

Rationale: The current code supports macOS app `system.which` and `system.run`, so the remaining fix is a policy choice across startup latency, remote skill discoverability, co-located app behavior, and documented node exec behavior.

Likely owner: steipete

Owner confidence: high

Options:

- **Defer and back off app-node probes (recommended):** Keep remote macOS skill support but delay initial probes and add bounded backoff/readiness checks for app-backed nodes.
- **Skip co-located app nodes:** Avoid probing app nodes on the gateway host while continuing to probe true remote macOS nodes that advertise shell commands.
- **Keep current immediate probing:** Accept startup/reconnect warnings as the cost of making remote skill bin availability visible as soon as a node connects.

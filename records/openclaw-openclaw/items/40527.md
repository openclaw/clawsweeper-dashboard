## Summary

Keep open: current main and the latest release still immediately probe connected macOS app-backed nodes that advertise `system.which` or `system.run`; the original missing-handler diagnosis is partly obsolete, but the readiness, co-location, and backoff problem remains unresolved.

## What This Changes

The issue asks OpenClaw to stop remote skill binary probes from timing out for macOS app-backed nodes, especially when the macOS app and gateway are co-located.

## Best Possible Solution

Preserve macOS app-node remote execution, then make remote bin probing readiness-aware with bounded defer/backoff or a narrow loopback skip, backed by real macOS app plus gateway proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should macOS app-backed nodes be probed immediately on connect, probed only after a stronger readiness/deferred backoff signal, or skipped only when co-located with the gateway?

Rationale: Current main supports macOS `system.which` and `system.run`, but the remaining behavior crosses app-node readiness timing, co-location detection, retry/backoff policy, and the node exec contract; choosing that boundary is maintainer product intent rather than a mechanical bug fix.

Likely owner: steipete

Owner reason: The remote skill probe, mac node exec policy, and node command catalog history make this the strongest routing owner for the product-boundary decision.

Owner confidence: high

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but delay initial app-node probes until readiness is stronger and add bounded retry/backoff for failed probes.
- **Skip Only Co-located App Nodes:** Avoid probing loopback or same-host app nodes while preserving remote app-node probing for hosts that can execute skills.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless users explicitly enable it, reducing warning spam at the cost of default remote skill support.

## Reproduction Assessment

No live current-main reproduction was run here. Source inspection shows current main still automatically probes connected macOS app-backed nodes that expose `system.which` or `system.run`, while the issue discussion provides concrete logs from real 2026.3.7 and 2026.4.2 setups.

## Solution Assessment

Unclear as a final implementation path. The broad config-disable and blanket command-removal options are not the best fix; the maintainable direction is a narrow readiness, co-location, or backoff policy in the active remote-skills runtime.

## Summary

Keep open: current main and the latest stable release still start automatic remote skill bin probes for macOS app-backed nodes that advertise `system.which` or `system.run`, while the co-location/readiness/backoff policy remains unresolved.

## What This Changes

The issue asks OpenClaw to avoid remote skill bin probe timeout warnings and startup/reconnect delay for macOS app nodes, especially when the app is co-located with the gateway.

## Best Possible Solution

Define a narrow gateway/macOS app-node probe policy that preserves valid remote `system.which`/`system.run`, skips or defers probes until readiness is proven, and validates the path on a real macOS app node.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should automatic remote skill bin probing for macOS app-backed nodes be deferred with backoff, skipped only for proven co-located app nodes, or disabled by default for app nodes?

Rationale: Current code intentionally supports macOS app-node `system.which` and `system.run`, so the fix changes remote skill and node-exec product semantics rather than only shortening a timeout.

Likely owner: steipete

Owner reason: steipete has the strongest feature-history signal across remote skills, mac node exec policy, and probe logging.

Owner confidence: high

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but wait for stronger app-node readiness and add bounded retry/backoff after failed probes.
- **Skip Co-located App Nodes:** Avoid probing loopback or same-host app nodes that add no remote skill value while preserving remote app-node probing.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless explicitly enabled, reducing warning noise at the cost of default remote skill support.

No high-confidence live reproduction was run in this read-only review. Source inspection still shows the automatic connect-time probe path, and the issue comments provide credible real macOS timeout evidence.

## Solution Assessment

Unclear as a final implementation: removing command support or adding a broad config flag is not the best fit. A narrow readiness, co-location, or retry/backoff policy that preserves valid remote macOS node execution is the maintainable direction.

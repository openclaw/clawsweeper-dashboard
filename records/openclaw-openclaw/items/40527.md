## Summary

Keep open: current main and the latest release still automatically probe connected macOS nodes that expose `system.which` or `system.run`; the original missing-handler diagnosis is partly obsolete, but the readiness, co-location, and retry/backoff policy remains unresolved.

## What This Changes

The issue asks OpenClaw to stop noisy/slow remote skill binary probes for macOS app-backed nodes when the app is co-located with the gateway or not yet ready after reconnect.

## Best Possible Solution

Settle a narrow macOS app-node readiness, co-location, and retry/backoff policy in `src/skills/runtime/remote.ts`, preserve valid `system.run`/`system.which` remote execution, and prove it with a real macOS app node.

Rationale: Current code intentionally supports macOS app-node `system.run` and `system.which`, so the remaining fix crosses readiness timing, co-location detection, retry policy, and documented node exec compatibility rather than being a purely mechanical patch.

Owner confidence: high

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but delay the initial app-node probe until readiness is stronger and add bounded retry/backoff after failed probes.
- **Skip Only Co-located App Nodes:** Avoid probing loopback or same-install app nodes that cannot add remote skill value while preserving remote app-node probing.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless explicitly enabled, reducing warning noise at the cost of default remote skill support.

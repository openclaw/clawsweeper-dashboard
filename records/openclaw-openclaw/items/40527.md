## Summary

Keep open: current main narrows the original missing-handler/default-allowlist cause, but it still immediately probes macOS app-backed nodes that advertise `system.which` or `system.run`, and the related repair PR is conflicting and not a safe canonical fix.

## What This Changes

The issue asks OpenClaw to avoid startup and reconnect remote skill-bin probe timeouts for macOS app-backed nodes without disabling legitimate remote node execution.

## Best Possible Solution

Keep the macOS app node exec contract intact, but make remote skill-bin refresh readiness-aware with bounded deferral/backoff and live macOS proof for both co-located and remote app-backed nodes.

Question: For macOS app-backed nodes, should OpenClaw preserve advertised `system.which`/`system.run` and make remote skill-bin probing readiness-aware, or should it skip/disable probes for co-located app nodes?

Owner confidence: medium

Options:

- **Defer and back off readiness-aware probes (recommended):** Preserve the macOS app node command surface, delay the initial probe until the node is ready, add bounded retry/backoff, and require live co-located plus remote macOS proof.
- **Skip only co-located app probes:** Suppress the local gateway/app warning case while leaving remote macOS app timing and retry behavior to a separate follow-up.
- **Add an operator disable flag:** Provide a global suppression knob, but accept new config surface and leave the underlying node-readiness behavior unresolved.

Unclear until maintainers choose the product contract. A readiness-aware probe/backoff path looks more maintainable than a broad config disable or removing approved macOS node exec commands.

## Summary

Keep open: current main and the latest release still automatically start remote skill bin probes for connected macOS app-backed nodes that advertise `system.which` or `system.run`; the old “no handler” diagnosis is partly obsolete, but the co-located/readiness/backoff problem is not proven fixed.

## What This Changes

The issue asks OpenClaw to stop remote skill binary probes from timing out and spamming gateway logs when a macOS app-backed node is co-located with the gateway or probed too early after connect.

## Best Possible Solution

Preserve macOS app-node remote execution, then make `src/skills/runtime/remote.ts` readiness-aware with bounded defer/backoff or a narrow loopback skip, backed by real macOS app plus gateway proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should macOS app-backed nodes be probed immediately on connect, probed only after a stronger readiness/deferred backoff signal, or skipped only when co-located with the gateway?

Rationale: Current main supports macOS `system.which` and `system.run`, so fixing the warning spam crosses app-node readiness timing, co-location policy, retry/backoff behavior, and the remote skill execution contract.

Likely owner: steipete

Owner reason: The remote skills and node command-policy history makes this the strongest routing owner for the product-boundary choice.

Owner confidence: high

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but delay initial app-node probes until readiness is stronger and add bounded retry/backoff for failed probes.
- **Skip Only Co-located App Nodes:** Avoid probing loopback or same-host app nodes while preserving remote app-node probing for hosts that can execute skills.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless users explicitly enable it, reducing warning spam at the cost of default remote skill support.

## Summary

Keep open: current main and v2026.6.11 still automatically probe connected macOS nodes that advertise `system.which` or `system.run`; the original missing-handler diagnosis is partly obsolete because the macOS app now implements `system.which`, but the readiness, co-location, and retry/backoff policy remains unresolved.

## What This Changes

The issue reports remote skill binary probe timeouts and gateway startup/reconnect delay for macOS app-backed nodes, especially when the app node is co-located with the gateway.

## Best Possible Solution

Settle a narrow macOS app-node readiness, co-location, and retry/backoff policy in `src/skills/runtime/remote.ts`, preserve declared `system.which` and `system.run`, and prove it with a real macOS app node.

Question: Should automatic remote skill bin probing for macOS app-backed nodes be deferred and backed off, skipped only for proven co-located app nodes, or disabled by default for app nodes?

Rationale: Current main intentionally supports macOS app-node `system.which` and `system.run`, so the remaining fix affects readiness timing, co-location detection, retry policy, and documented node exec compatibility rather than a purely mechanical bug patch.

Likely owner: steipete

Owner reason: The strongest history signal spans the original remote skills runtime, mac node exec policy, and `system.which` probe behavior that this decision must preserve or adjust.

Owner confidence: high

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but delay the initial app-node probe until readiness is stronger and add bounded retry/backoff after failed probes.
- **Skip Only Co-located App Nodes:** Avoid probing loopback or same-install app nodes that cannot add remote skill value while preserving remote app-node probing.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless explicitly enabled, reducing warning noise at the cost of default remote skill support.

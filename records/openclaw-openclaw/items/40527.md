## Summary

Keep open: current main narrows the original default-allowlist cause, but it still immediately probes approved or live macOS app-backed nodes that advertise `system.which` or `system.run`, and the remaining readiness/backoff behavior needs maintainer direction plus live macOS proof.

## What This Changes

The issue asks OpenClaw to avoid remote skill-bin probe timeouts and misleading gateway warnings for co-located and app-backed macOS nodes.

## Best Possible Solution

Preserve the approved macOS node exec contract, but make remote skill-bin refresh readiness-aware with bounded deferral/backoff and live proof for both co-located and remote app-backed macOS nodes.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For macOS app-backed nodes, should OpenClaw keep advertised `system.which`/`system.run` and make remote skill-bin probing readiness-aware, or should it suppress probes for co-located app nodes?

Rationale: The code path can be fixed several ways, but the choice affects remote execution compatibility, skill availability freshness, warning noise, and operator expectations for app-backed nodes.

Owner confidence: medium

Options:

- **Readiness-Aware Probe (recommended):** Delay the initial probe until the node is ready, add bounded retry/backoff, and require live macOS proof while preserving the existing node command surface.
- **Skip Co-Located App Probes:** Suppress the local gateway/app warning case first and leave remote macOS app timing/backoff to a narrower follow-up.
- **Add Disable Configuration:** Introduce an operator suppression knob, accepting new config surface while leaving the underlying readiness behavior mostly unchanged.

## Reproduction Assessment

No live high-confidence current-main reproduction was run. Source inspection still shows eager macOS node probing after connect, and issue comments provide live evidence that automatic probing can time out even when manual `system.which` succeeds.

## Solution Assessment

Unclear until maintainers choose the product contract. A readiness-aware deferral/backoff path looks more maintainable than a broad config disable or removing approved macOS node exec commands.

## Summary

Keep open: current main and v2026.6.11 still start automatic remote skill bin probing for connected macOS nodes that advertise `system.which` or `system.run`; the old missing-handler diagnosis is partly obsolete, but the readiness/co-location/backoff policy remains unresolved and no merged PR supersedes it.

## What This Changes

The issue reports timeout and warning churn from automatic remote skill binary probes against macOS app-backed nodes, especially when the app node is co-located with the gateway.

## Best Possible Solution

Settle a narrow macOS app-node probe readiness policy, preferably deferred first probe plus bounded backoff, while preserving legitimate remote macOS `system.which` and `system.run` workflows.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should automatic remote skill bin probing for macOS app-backed nodes be deferred/backed off, skipped only for proven co-located app nodes, or disabled by default for app nodes?

Rationale: Current code supports macOS app-node `system.which` and `system.run`, so the remaining fix crosses startup timing, co-location semantics, retry policy, and documented remote-node execution compatibility.

Likely owner: steipete

Owner reason: The central remote probe and macOS node policy history points most strongly to steipete for this owner-boundary decision.

Owner confidence: high

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but delay the initial app-node probe until readiness is stronger and add bounded retry/backoff after failed probes.
- **Skip Only Co-located App Nodes:** Avoid probing loopback or same-host app nodes that add no remote skill value, while preserving remote app-node probing for actual remote Macs.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless explicitly enabled, reducing warning noise at the cost of default remote skill support.

## Reproduction Assessment

Yes from source for the automatic-probe path: current main still probes connected macOS nodes that expose `system.which` or `system.run`. A live co-located macOS app timeout was not reproduced in this read-only review.

## Solution Assessment

Unclear as a final implementation. A broad config flag or command-surface removal is not the best fix; the maintainable direction is a narrow readiness, co-location, or backoff policy that preserves remote macOS node execution.

## Summary

Keep open: current main has several partial improvements, but it still starts an automatic macOS remote skill-bin refresh for connected nodes that advertise `system.which` or `system.run`, and the related open PRs are conflicting/unproven rather than safe canonical fixes.

## What This Changes

The issue requests preventing automatic remote macOS skill-bin probes from timing out or warning when a macOS app-backed node is co-located with, or newly connected to, the gateway.

## Best Possible Solution

Keep the macOS app node exec contract intact, but make the remote skill-bin refresh readiness-aware with bounded deferral/backoff and live macOS proof for both co-located and remote app-backed nodes.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For macOS app-backed nodes, should OpenClaw preserve advertised `system.which`/`system.run` and make remote skill-bin probing readiness-aware, or should it skip/disable probes for co-located app nodes?

Rationale: Current main has partial mitigations but no live proof that startup/reconnect probe timing is fixed; choosing skip, defer, retry, and backoff semantics affects node exec compatibility and user-visible skill availability.

Likely owner: steipete

Owner reason: Recent history shows broad ownership of gateway node policy, docs, and node protocol maintenance decisions around this surface.

Owner confidence: medium

Options:

- **Defer and back off readiness-aware probes (recommended):** Preserve the macOS app node command surface, delay the initial probe until the node is ready, add bounded retry/backoff, and require live proof for co-located and remote macOS app nodes.
- **Skip only co-located app probes:** Avoid the local gateway/app warning case, but leave the reported remote macOS app timing issue as a separate unresolved path.
- **Add a global disable flag:** This would suppress symptoms for operators but adds config surface and leaves the core node-readiness behavior unresolved.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Not live on current main; the source path still shows automatic macOS node probing during connected-node refresh, but the exact timeout needs a real co-located or remote macOS app-node run after recent mitigations.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainers choose the product contract; the maintainable direction is a readiness-aware probe/backoff path rather than a broad config disable or removing approved macOS node exec commands.

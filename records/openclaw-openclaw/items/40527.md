## Summary

Keep open: current main and the latest release still automatically probe connected macOS app-backed nodes that advertise `system.which` or `system.run`; the original missing-handler diagnosis is partly obsolete, but the readiness/co-location/backoff problem remains and the overlapping PRs are not safe merged resolutions.

## What This Changes

The issue asks OpenClaw to stop timing out or warning during remote skill binary probes for macOS app-backed nodes, especially when the macOS app node is co-located with the gateway.

## Best Possible Solution

Preserve macOS app-node remote execution, then make `src/skills/runtime/remote.ts` readiness-aware with bounded defer/backoff or a narrow loopback skip, backed by real macOS app plus gateway proof.

Question: Should macOS app-backed nodes be probed immediately on connect, probed only after a stronger readiness/deferred backoff signal, or skipped only when co-located with the gateway?

Rationale: Current main supports macOS `system.which` and `system.run`, but the remaining behavior crosses app-node readiness timing, co-location detection, retry/backoff policy, and the node exec contract.

Likely owner: steipete

Owner confidence: high

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but delay initial app-node probes until readiness is stronger and add bounded retry/backoff for failed probes.
- **Skip Only Co-located App Nodes:** Avoid probing loopback/co-located app nodes while preserving remote app-node probing for hosts that can execute skills.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless users explicitly enable it, reducing warning spam at the cost of default remote skill support.

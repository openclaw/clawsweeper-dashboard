## Summary

Keep open: current main still automatically probes connected macOS app-backed nodes that advertise `system.which` or `system.run`; the original missing-handler diagnosis is partly obsolete, but readiness, co-location, and backoff policy remain unresolved and the related PRs are not landed fixes.

## What This Changes

Issue requests stopping noisy and delayed remote skill binary probes for macOS app-backed nodes, especially when the app node is co-located with the gateway.

## Best Possible Solution

Settle a narrow macOS app-node readiness, co-location, and retry/backoff policy in `src/skills/runtime/remote.ts`, preserve declared `system.run` and `system.which`, and prove it with a real macOS app node.

Question: Should automatic remote skill bin probing for macOS app-backed nodes be deferred/backed off, skipped only for proven co-located app nodes, or disabled by default for app nodes?

Rationale: Current main intentionally supports macOS app-node `system.run` and `system.which`, so the remaining fix crosses readiness timing, co-location detection, retry policy, and documented node exec compatibility rather than a purely mechanical patch.

Likely owner: steipete

Owner confidence: medium

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but delay the initial app-node probe until readiness is stronger and add bounded retry/backoff after failed probes.
- **Skip Only Co-located App Nodes:** Avoid probing loopback or same-install app nodes that cannot add remote skill value while preserving remote app-node probing.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless explicitly enabled, reducing warning noise at the cost of default remote skill support.

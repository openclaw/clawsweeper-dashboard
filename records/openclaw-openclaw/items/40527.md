## Summary

Keep open: current main still automatically probes connected macOS app-backed nodes that advertise `system.which` or `system.run`, and the related open PRs are not safe canonical fixes for the remaining readiness, co-location, and backoff policy question.

## What This Changes

The issue reports startup and reconnect timeouts from automatic remote skill bin probes against macOS app-backed nodes, especially when the app node is co-located with the gateway.

## Best Possible Solution

Settle a narrow macOS app-node readiness, co-location, and retry/backoff policy in `src/skills/runtime/remote.ts`, preserve declared `system.run` and `system.which`, and prove it with a real macOS app node.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should automatic remote skill bin probing for macOS app-backed nodes be deferred/backed off, skipped only for proven co-located app nodes, or disabled by default for app nodes?

Rationale: Current code intentionally supports macOS app-node `system.run` and `system.which`, so automation should not choose a policy that changes node execution availability, startup behavior, or co-located app semantics without maintainer intent.

Likely owner: steipete

Owner reason: This decision spans the remote skills runtime, gateway node command policy, and macOS app-node behavior where the history signal is strongest.

Owner confidence: high

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but delay the initial app-node probe until readiness is stronger and add bounded retry/backoff after failed probes.
- **Skip Proven Co-located App Nodes:** Avoid probing loopback or same-install app nodes that cannot add remote skill value while preserving remote app-node probing.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless explicitly enabled, reducing warning noise at the cost of default remote skill support.

## Reproduction Assessment

No live high-confidence current-main reproduction was run. Source inspection still shows the connect-time probe path for macOS nodes that expose `system.which` or `system.run`, and issue comments provide real macOS app-node timeout evidence.

## Solution Assessment

Unclear as a final implementation. Blanket command removal or a broad config flag is not the best fix; the maintainable path is a narrow readiness, co-location, or backoff policy that preserves valid remote macOS node execution.

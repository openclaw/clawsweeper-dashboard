## Summary

Keep open: current main has narrowed the original macOS app command-surface problem, but it still automatically probes approved macOS app-backed nodes on connect, and the remaining co-location/readiness/backoff policy is not resolved by a merged PR or shipped release.

## What This Changes

The issue reports automatic remote skill binary probes timing out for macOS app-backed nodes, especially when the app node is co-located with the gateway, causing startup/reconnect delay and misleading warnings.

## Best Possible Solution

Settle and implement a macOS app-node probe policy that waits for node readiness or backs off cleanly while preserving legitimate remote macOS skill execution.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should macOS app-backed nodes be probed immediately on connect, probed only after a readiness/deferred backoff signal, or skipped when co-located with the gateway?

Rationale: Current main has macOS system.which/system.run support, but the remaining behavior crosses readiness timing, co-location detection, retry/backoff policy, and remote skill eligibility rather than being a purely mechanical one-line bug fix.

Likely owner: steipete

Owner reason: Peter Steinberger has the strongest combined history signal across the gateway policy boundary and macOS app-node ownership surface.

Owner confidence: medium

Options:

- **Defer And Back Off Probes (recommended):** Keep remote macOS skills supported, but delay initial app-node probes until readiness is stronger and add bounded retry/backoff for failed probes.
- **Skip Co-located App Nodes:** Avoid probing loopback or same-host app nodes while preserving probing for remote app nodes that can execute skills.
- **Disable App-node Probing By Default:** Stop automatic app-node remote skill eligibility unless users explicitly enable it, reducing warnings at the cost of default remote skill support.

## Reproduction Assessment

No high-confidence live reproduction was established in this review. The source path and issue comments give a medium-confidence repro: approved macOS app-backed nodes that expose system.which or system.run are still probed automatically on connect.

## Solution Assessment

Unclear as a final implementation path. A broad config disable is not the best fix; the maintainable direction is a narrow readiness, co-location, or backoff policy in the active remote-skills runtime.

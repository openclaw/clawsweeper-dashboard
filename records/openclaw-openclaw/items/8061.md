## Summary

Keep open: current main still lacks target-specific subagent concurrency control, and the concrete resource-isolation use case is distinct from related lane and parent-limit requests. The remaining blocker is maintainer approval of the public configuration and scheduling contract.

## What This Changes

Add a per-target-agent concurrency limit so one resource-heavy subagent can be serialized without throttling unrelated subagents.

## Best Possible Solution

Use one hierarchical admission model: retain the global subagent lane as the outer safety budget, add an approved per-target cap under the target agent’s subagent policy, and enforce the same target accounting for native and ACP spawns.

- **Keep one global cap:** Decline another configuration surface and document separate gateways or external model-capacity controls as the operational boundary.

## Reproduction Assessment

Yes at source level: current main exposes and enforces only `agents.defaults.subagents.maxConcurrent`, while the strict per-agent configuration has no target concurrency field. A live failing run is unnecessary to establish that the requested capability is absent.

## Solution Assessment

No, the proposed top-level `agents.list[].maxConcurrent` field is not yet the best final shape because it could be confused with top-level inbound-run concurrency. The existing namespace favors `agents.list[].subagents.maxConcurrent`, subject to maintainer approval of hierarchical target accounting.

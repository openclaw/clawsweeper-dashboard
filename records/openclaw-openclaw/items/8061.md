## Summary

Keep open: current main and v2026.6.11 still only enforce one global subagent concurrency cap, while the requested target-agent-specific cap remains absent and needs maintainer-approved config and scheduler semantics.

## What This Changes

Request adding a per-target-agent subagent concurrency cap so one configured target agent can serialize spawned work while other subagents remain parallel.

## Best Possible Solution

Add a maintainer-approved per-target subagent cap, likely agents.list[].subagents.maxConcurrent, validate it in schema/types/help/docs, and enforce it for both native and ACP spawned runs alongside the existing global cap.

Rationale: The source gap is clear, but the fix creates new public config and scheduler semantics that must coordinate with adjacent lane/concurrency proposals and preserve aggregate resource limits.

Likely owner: steipete

Owner confidence: high

Options:

- **Use agents.list[].subagents.maxConcurrent (recommended):** Add the cap under the existing per-agent subagent namespace and keep agents.defaults.subagents.maxConcurrent as the aggregate safety limit.
- **Fold into broader lane design:** Defer implementation until maintainers settle caller-selected subagent lanes and foreground per-agent lane semantics as one scheduler API.
- **Decline the new config surface:** Keep only the global subagent cap and document local-model serialization workarounds, accepting that target-specific throttling remains unavailable.

## Reproduction Assessment

Yes, at source level: current main has no accepted per-target cap in strict per-agent schema/types, resolves one global subagent cap, and dispatches native and ACP spawns to the fixed subagent lane. I did not run a live TTS/local-model workload because the requested config surface is not implemented.

## Solution Assessment

Unclear as originally proposed: top-level agents.list[].maxConcurrent could conflict with foreground agent concurrency semantics. A namespaced agents.list[].subagents.maxConcurrent contract that preserves the existing global cap appears safer, but maintainers need to choose it.

## Summary

Current `main` still lacks a target-agent concurrency cap, and the related reports address different scheduler scopes. The issue should remain open for a maintainer decision on a narrow target-keyed gate versus a broader unified lane model.

## What This Changes

Requests a per-agent concurrency cap for subagent targets so one constrained agent can serialize while other agents remain parallel.

## Best Possible Solution

Add one canonical target-agent concurrency gate beneath the existing global subagent cap, preferably configured as `agents.list[].subagents.maxConcurrent`, and enforce it consistently for native and ACP child runs without requiring callers to select the correct lane.

## Reproduction Assessment

Yes, at source level with high confidence: both native and ACP paths resolve a target agent but enqueue every child run into the same globally capped subagent lane, and the strict per-agent config has no concurrency field. A live overload run was not needed to establish that the requested control is absent.

## Solution Assessment

No, not exactly as proposed: top-level `agents.list[].maxConcurrent` is ambiguous with foreground agent concurrency. A nested target-agent subagent cap is the narrowest maintainable solution unless maintainers intentionally adopt a unified lane model that covers this invariant.

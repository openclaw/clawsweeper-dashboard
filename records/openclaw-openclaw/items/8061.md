## Summary

Keep open: current main and the latest release still expose only a global `agents.defaults.subagents.maxConcurrent` cap and a fixed `subagent` lane, while this issue asks for a target-agent-specific subagent cap with confirmed user demand.

## What This Changes

Request adding an optional per-target subagent concurrency cap so one configured subagent can serialize while other subagents remain parallel.

## Best Possible Solution

Add one validated per-target-agent subagent cap, likely under `agents.list[].subagents`, enforce it alongside the global cap for native and ACP spawns, and update schema, docs, and focused concurrency tests.

## Reproduction Assessment

Yes, at source level: current main has a strict per-agent schema with no target cap, one global subagent resolver, and fixed native/ACP dispatch to the `subagent` lane. I did not run a live TTS/local-model workload because the requested config surface does not exist.

## Solution Assessment

Unclear as originally proposed: the capability is well-scoped, but the public key should likely fit the existing `agents.list[].subagents.*` namespace and must compose with related lane and scheduler controls.

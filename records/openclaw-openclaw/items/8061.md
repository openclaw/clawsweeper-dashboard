## Summary

Keep open: current main still lacks a per-target-agent subagent concurrency cap, and the existing global subagent lane plus per-requester active-child cap do not solve the local TTS/fragile worker use case. The remaining work needs maintainer API and scheduler direction because it adds public config surface and overlaps adjacent lane-concurrency proposals.

## What This Changes

The issue requests an optional per-agent subagent concurrency limit so one configured target agent can be serialized while other subagents remain parallel.

## Best Possible Solution

Add a maintainer-approved per-target subagent cap under the existing subagent config namespace, enforce it alongside the global safety cap for native and ACP spawns, and document/test the behavior without changing existing defaults.

## Reproduction Assessment

Yes, from source inspection: strict config/schema/types expose only global `agents.defaults.subagents.maxConcurrent`, and current spawn code dispatches native subagents through the shared subagent lane. I did not run a live gateway scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API shape. A per-agent `subagents.maxConcurrent` setting looks more consistent than a top-level `agents.list[].maxConcurrent`, but it should be decided against the broader lane-concurrency issues before implementation.

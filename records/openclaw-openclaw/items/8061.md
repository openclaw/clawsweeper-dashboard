## Summary

Keep open: current main and v2026.6.11 still only provide the global `agents.defaults.subagents.maxConcurrent` cap and fixed `subagent` lane, while this issue asks for a per-target-agent subagent cap with confirmed user demand.

## What This Changes

Add an optional per-target-agent subagent concurrency cap so one configured subagent can be serialized while other subagents can still run in parallel.

## Best Possible Solution

Add a maintainer-approved, validated `agents.list[].subagents.maxConcurrent`-style per-target cap enforced for native and ACP spawns alongside the global cap, with schema, docs, and focused concurrency tests.

## Reproduction Assessment

Yes, at source level: current main has a strict per-agent schema with no target cap, one global subagent resolver, and fixed native/ACP dispatch to the `subagent` lane. I did not run a live TTS/local-model workload.

## Solution Assessment

Unclear as originally proposed: the capability is well scoped, but the public key likely belongs under the existing `agents.list[].subagents.*` namespace and must compose with adjacent scheduler controls.

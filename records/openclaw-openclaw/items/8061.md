## Summary

Keep open: current main and v2026.6.11 still expose only a global subagent concurrency cap, while this request is for a target-agent-specific cap with confirmed user demand and unresolved public config/scheduler semantics.

## What This Changes

Request adding an optional per-agent subagent concurrency cap so one target agent can be serialized while other subagents remain parallel.

## Best Possible Solution

Add a maintainer-approved per-target subagent cap, likely under `agents.list[].subagents.maxConcurrent`, validate it in schema/types/docs, and enforce it alongside the global cap for native and ACP spawns with focused regression tests.

## Reproduction Assessment

Yes, at source level: current main has a strict per-agent schema with no target cap, one global subagent resolver, and fixed native dispatch to the `subagent` lane. I did not run a live TTS/local-model workload because the requested config surface does not exist.

## Solution Assessment

Unclear as originally proposed: the capability is well-scoped, but the public key should likely fit the existing `agents.list[].subagents.*` namespace and must compose with related lane and scheduler controls.

## Summary

Keep open: current main still has pending-final persistence and restart/success cleanup paths, but no proven live-session drain for a completed `done` session whose final text remains in `pendingFinalDelivery` until later activity. The existing open recovery PRs are relevant, but they still need maintainer direction and proof before this issue can be treated as fixed or superseded.

## What This Changes

The issue reports completed gateway sessions whose final reply is persisted in `pendingFinalDeliveryText` but not delivered to the UI until another message flushes the path.

## Best Possible Solution

Choose and land a shared pending-final recovery design that delivers or records explicit failure for terminal saved finals without wrong-route or duplicate sends, then close this issue from merged implementation evidence.

## Reproduction Assessment

No high-confidence live reproduction was run for the reporter's multi-agent Ollama/load setup. Source inspection does show a current-main gap: `done` sessions with pending final text are not covered by the running-plus-aborted restart recovery path, and no merged reaper exists.

## Solution Assessment

Unclear as implementation: the requested behavior is the right bug target, but the best fix must settle durable send/clear idempotency and exact-route recovery semantics. A narrow channel-specific flush or stale replay path would not be safe enough.

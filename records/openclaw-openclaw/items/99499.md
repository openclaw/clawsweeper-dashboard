## Summary

Keep open: current main and v2026.6.11 still have source-backed paths where policy-visible final text is stored as pending final delivery rather than proven delivered, and this fresh report is a plausible user-visible message-loss case rather than an implemented or duplicate-only cleanup item.

## What This Changes

The issue reports completed OpenClaw sessions whose final reply remains in `pendingFinalDeliveryText` and is not shown in the UI until a later inbound message flushes it.

## Best Possible Solution

Define and implement the shared final-delivery invariant so completed user-visible final text is delivered to Control/WebChat or a source channel, or records an explicit failed/suppressed outcome, without waiting for a later inbound turn.

## Reproduction Assessment

We have a source-level reproduction signal, not a live one: current source and tests show user-facing pending final text can remain durable pending state, and the reporter supplied concrete v2026.6.11 session JSON evidence. I did not reproduce the Debian/Ollama concurrent-load timing path.

## Solution Assessment

Unclear as a narrow fix: forcing an immediate flush may solve this symptom, but the best maintainable solution should align with the existing durable-final delivery contract and record explicit delivery outcomes.

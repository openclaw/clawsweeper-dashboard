## Summary

Keep open: current main and v2026.6.11 still expose the shared message tool `channel` parameter as an undescribed optional string, while https://github.com/openclaw/openclaw/pull/84589 is the open linked fix candidate rather than a merged fix.

## What This Changes

The issue asks for the message tool `channel` parameter schema to describe that it expects a messaging provider id and, optionally, to constrain values with an enum.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/84589 if description-only closure is acceptable; track enum support separately only if maintainers want registry-derived constraints.

## Reproduction Assessment

Yes, at source level. Current main exposes `channel` without schema guidance, and outbound channel selection can reject destination-like values as `Unknown channel` when no valid fallback applies.

## Solution Assessment

Yes for the description gap: TypeBox metadata plus a focused schema assertion is the narrow maintainable repair. Enum support is a separate product/API decision because a static enum could drift from registered channel/plugin ids.

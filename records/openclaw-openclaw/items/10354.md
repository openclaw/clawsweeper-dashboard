## Summary

Keep open. Current main and v2026.6.11 still expose the message tool `channel` parameter without provider-name schema metadata, and the active path is to review the open linked implementation PR rather than closing this issue before it merges.

## What This Changes

Request to add provider-name guidance, and possibly enum metadata, to the message tool `channel` parameter so agents do not pass destination conversation IDs as channel providers.

## Best Possible Solution

Review and land the linked schema/test PR if provider-name description is sufficient, then track registry-derived enum support separately only if maintainers still want it.

## Reproduction Assessment

Yes, at source level. Current main exposes `channel` without schema metadata, and the outbound channel-selection path can still reject destination-like values as unknown channels when no valid provider fallback applies.

## Solution Assessment

Yes for the description gap: a narrow TypeBox description plus focused schema assertion is the maintainable repair. The enum portion is a product/API decision because channel availability is registry/plugin-derived rather than a fixed static list.

## What This Changes

Clarify that the message tool’s optional `channel` argument accepts a messaging provider or channel-plugin identifier rather than a destination conversation ID, and decide whether its values should be dynamically enumerated.

## System Context

An agent calls the shared message tool with a provider selection and a destination target. The tool schema guides the model before outbound routing resolves the selected provider or plugin and delivers the message to the requested conversation.

## Architecture Diagram

flowchart LR

## Best Possible Solution

Keep `channel` optional, add concise provider-versus-destination guidance to the shared schema, and add an enum only if it is derived from the active registered channel/plugin catalog with stable ordering and explicit compatibility coverage for the existing fallback path.

Question: Should the shared message-tool schema add only provider-oriented guidance, or should it also enforce a dynamically derived enum that can reject previously accepted arbitrary `channel` strings before routing fallback runs?

Rationale: The description is a narrow usability clarification, but an enum changes a model-facing validation contract across bundled and external channel plugins and can alter existing fallback behavior.

Likely owner: steipete

Owner confidence: medium

Options:

- **Land description-only guidance (recommended):** Clarify that `channel` is a provider or channel-plugin identifier and retain current permissive validation plus runtime fallback behavior.
- **Add a dynamic enum with compatibility proof:** Derive stable values from registered channel/plugin identifiers and prove fresh, plugin, and fallback behavior before changing validation.
- **Defer the enum decision:** Land no schema constraint until maintainers define the permanent plugin/catalog contract for model-facing channel selection.

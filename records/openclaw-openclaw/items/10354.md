## Summary

Current main and v2026.6.11 still omit the model-facing `channel` guidance, while the open linked pull request remains unmerged; this issue is still necessary and should stay open until that candidate is refreshed and resolved.

## What This Changes

Clarify that the message tool’s optional `channel` parameter selects a messaging provider or channel plugin rather than a destination ID, with enum support considered only if derived from registered channel metadata.

## Best Possible Solution

Refresh and land the linked description/test repair with wording that says provider or channel-plugin identifier and directs destination IDs to `target` or `targets`; defer enum enforcement unless it is derived through a lightweight canonical registered-channel helper.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes at source level: the schema accepts an arbitrary destination ID as `channel`, while downstream routing expects a registered channel identifier and can throw `Unknown channel`. This read-only review did not execute a live current-main agent turn.

## Solution Assessment

Yes for the description and focused schema-test scope: it repairs the existing model-facing routing contract without changing runtime behavior. A static enum is not the best fix because channel plugin IDs are dynamic.

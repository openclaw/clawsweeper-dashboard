## Summary

Keep open. Current main still exposes the shared message tool `channel` parameter as an undocumented optional string, and the latest release has the same gap; the issue is now paired with an open fixing PR, so the right cleanup is to review that PR rather than close or queue another fix.

## What This Changes

Request to add provider-name schema guidance, and possibly enum support, to the message tool `channel` parameter so agents do not pass destination channel IDs as provider names.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/84589 after deciding the linked-issue closure scope; defer enum support unless it can be derived from the registered/configured channel ids without a static drift-prone list.

## Reproduction Assessment

Yes, at source level. Current main exposes `channel` without schema metadata, while current outbound selection treats explicit `channel` values as provider/channel ids and can reject destination-like values as `Unknown channel`.

## Solution Assessment

Yes for the description gap: adding TypeBox metadata plus a focused schema assertion is the narrow maintainable repair. Enum support still needs maintainer direction because a static enum can drift from registered plugin/channel availability.

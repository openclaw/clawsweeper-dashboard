- `P2`: This is a normal-priority WebChat formatting bug affecting CJK readability and multiline table-cell ergonomics without blocking core runtime use.
- `impact:ux-friction`: Users can continue chatting, but normal Japanese/CJK Markdown and `<br>` table-cell formatting render confusingly or literally in WebChat.
- `maturity:stable`: The issue affects the M4 Stable `gateway-runtime` feature area, specifically its Hosted Web Surface/WebChat category.

## Summary

Keep open: current main only partially addresses the CJK emphasis problem in shared markdown-core, while the WebChat/Control UI renderer still uses its own markdown-it instance and still intentionally escapes raw HTML such as `<br>`.

## What This Changes

The issue asks for CJK-aware WebChat Markdown rendering, safe handling or documentation for `<br>` in table cells, and Japanese/non-ASCII Markdown regression tests.

## Best Possible Solution

Apply CJK-friendly emphasis to the Control UI/WebChat renderer with Japanese/CJK tests, then make an explicit `<br>` policy: narrow sanitized support or documented unsupported raw HTML, never blanket HTML enablement.

Yes, source-level. Current WebChat renders through `toSanitizedMarkdownHtml`; that renderer lacks the CJK-friendly plugin and explicitly escapes raw HTML tokens, matching the reported failures without a live browser run.

## Solution Assessment

No current fix fully solves this issue. Shared markdown-core already fixed CJK flanking for channel IR, but the best WebChat solution must update the Control UI renderer and settle the `<br>` security policy explicitly.

## Summary

Keep open. Current main and v2026.6.11 still split Control UI HTTP bearer auth from WebSocket shared-secret auth, so proxy-injected `Authorization`/token header bootstrap remains a security-sensitive Gateway design item rather than implemented cleanup.

## What This Changes

Requested support for bootstrapping Control UI authentication from proxy-supplied authorization headers instead of URL/manual token entry.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model, preferably either a trusted same-origin bootstrap endpoint that issues a short-lived browser session credential or a tightly scoped opt-in header path for the WebSocket upgrade.

## Reproduction Assessment

Yes, at source level. Current main accepts bearer auth for Control UI HTTP reads, but WebSocket shared-secret auth consumes only connect-frame credentials and has no header-to-session bridge for proxy-injected credentials.

## Solution Assessment

Unclear until maintainers choose the trust model. Direct header acceptance is plausible, but a short-lived same-origin session credential or purpose-specific opt-in header is safer than automatically treating forwarded `Authorization` as a Gateway token.

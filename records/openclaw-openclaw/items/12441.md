## Summary

Keep open: current main and v2026.6.11 still do not bridge a reverse-proxy-injected shared-secret header into Control UI WebSocket auth, and the remaining work changes the Gateway operator-auth trust boundary.

## What This Changes

Allow Control UI reverse-proxy deployments to bootstrap the gateway token from `Authorization: Bearer ...` or `X-OpenClaw-Token` instead of relying on URL fragments or manual UI token entry.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model in Gateway auth, with trusted-proxy and origin checks, rate limiting, clear session or WebSocket-upgrade semantics, backward-compatible URL/manual token flows, docs, and focused Gateway/UI tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which reverse-proxy shared-secret bootstrap model should Control UI support for turning proxy-provided headers into WebSocket credentials?

Rationale: The source gap is clear, but the choice affects spoofing protections, trusted proxy requirements, browser origin handling, rate limits, pairing/device semantics, and credential lifetime.

Likely owner: steipete

Owner reason: He already reviewed this exact auth design gap and has the strongest recent Gateway HTTP/WebSocket auth-boundary history.

Owner confidence: high

Options:

- **Use a short-lived browser session (recommended):** Validate Authorization or X-OpenClaw-Token on a same-origin bootstrap endpoint and mint a bounded browser credential for the WebSocket path.
- **Validate on WebSocket upgrade:** Accept a purpose-built shared-secret header during trusted WebSocket upgrades after origin, proxy, and rate-limit checks.
- **Keep current auth paths:** Decline shared-secret header bootstrap and keep connect.params auth plus identity-bearing Tailscale/trusted-proxy modes as the supported Control UI paths.

## Reproduction Assessment

Yes. Source-level reproduction is high confidence: current main accepts bearer tokens on HTTP Control UI reads, while WebSocket shared-secret auth is still taken from `connect.params.auth` in the browser connect frame.

## Solution Assessment

Unclear until maintainers choose the trust model. The maintainable path is not a quick header passthrough, but a named reverse-proxy bootstrap design with explicit proxy, origin, rate-limit, session, and test semantics.

## Summary

Keep open. Current main and v2026.6.11 still accept bearer auth for Control UI HTTP/bootstrap reads, but shared-secret WebSocket auth still comes only from the connect frame; this remains a Gateway auth trust-boundary feature, not conservative cleanup.

## What This Changes

The issue requests a Control UI reverse-proxy auth path that can bootstrap from Authorization or X-OpenClaw-Token headers instead of URL/manual token entry.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model, either validating Authorization/X-OpenClaw-Token on the WebSocket upgrade after existing proxy/origin/rate-limit checks or issuing a short-lived same-origin browser session credential from an authenticated bootstrap endpoint.

## Reproduction Assessment

Yes, at source level. Current main accepts bearer auth for Control UI HTTP/bootstrap reads, but WebSocket shared-secret auth consumes only connect-frame auth and has no header-to-session bridge for proxy-injected credentials.

## Solution Assessment

Unclear until maintainers choose the trust model. Direct header bootstrap is plausible, but a short-lived same-origin session credential or purpose-specific opt-in header is likely safer than treating any forwarded Authorization bearer as a Gateway token.

## Risks / Open Questions

- Any implementation must preserve URL-fragment/manual token flows, device pairing, rate limits, origin checks, Tailscale identity auth, and trusted-proxy identity mode.

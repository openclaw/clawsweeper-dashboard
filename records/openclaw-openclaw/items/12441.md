## Summary

Keep open. Current main and v2026.6.11 still support bearer headers for Control UI HTTP reads, but shared-secret Control UI WebSocket auth remains browser connect-frame based, so the requested reverse-proxy header bootstrap is still a security-sensitive product/design item.

## What This Changes

The issue requests Control UI shared-secret auth bootstrap from reverse-proxy-provided HTTP headers instead of only URL/hash/manual browser token state.

## Best Possible Solution

Define one explicit opt-in reverse-proxy shared-secret bootstrap model, preferably a same-origin bootstrap endpoint that validates a proxy-owned header and issues a short-lived browser session credential, or a tightly scoped WebSocket-upgrade header path with origin, proxy, rate-limit, pairing, docs, and tests.

## Reproduction Assessment

Yes, at source level. Current main accepts bearer auth for Control UI HTTP reads, but WebSocket shared-secret auth consumes only connect-frame auth and has no header-to-session bridge for proxy-injected credentials.

## Solution Assessment

Unclear until maintainers choose the trust model. Direct header bootstrap is plausible, but a short-lived same-origin session credential or purpose-specific opt-in header is likely safer than treating any forwarded Authorization value as a Gateway token.

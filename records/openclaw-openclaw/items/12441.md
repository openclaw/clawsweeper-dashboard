## Summary

Keep open. Current main still does not implement reverse-proxy shared-secret bootstrap for the Control UI WebSocket path: bearer headers work for HTTP reads, but browser WebSocket auth still depends on connect-frame credentials or existing identity-proxy modes, so this remains a security-sensitive product decision.

## What This Changes

The issue requests Control UI shared-secret auth bootstrap from proxy-provided Authorization or X-OpenClaw-Token headers instead of relying on URL/manual token entry.

## Best Possible Solution

Define one explicit opt-in reverse-proxy shared-secret bootstrap model, preferably a same-origin bootstrap endpoint that validates the proxy header and issues a short-lived browser session credential, or a tightly scoped WebSocket-upgrade header path with origin, proxy, rate-limit, pairing, docs, and tests.

## Reproduction Assessment

Yes, at source level. Current main accepts bearer auth for Control UI HTTP reads, but WebSocket shared-secret auth consumes only connect-frame auth and has no header-to-session bridge for proxy-injected credentials.

## Solution Assessment

Unclear until maintainers choose the trust model. Direct header bootstrap is plausible, but a short-lived same-origin session credential or purpose-specific opt-in header is likely safer than treating any forwarded Authorization value as a Gateway token.

## Summary

Keep open. Current main and v2026.6.11 still accept bearer tokens for Control UI HTTP reads, but they do not bridge a reverse-proxy-injected shared-secret header into the browser WebSocket connect path; this remains a security-sensitive Gateway auth design decision.

## What This Changes

The issue requests Control UI shared-secret bootstrap from reverse-proxy HTTP headers such as Authorization: Bearer or X-OpenClaw-Token instead of URL/manual token entry.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model in Gateway auth, with trusted-proxy/origin checks, rate limiting, clear session or WebSocket-upgrade semantics, backward-compatible URL/manual token flows, docs, and focused Gateway/UI tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which reverse-proxy shared-secret bootstrap model should OpenClaw support for Control UI?

Rationale: The code can support several shapes, but choosing how proxy headers become Gateway operator credentials affects spoofing protections, origin handling, rate limits, pairing/device semantics, and credential lifetime.

Likely owner: steipete

Owner reason: steipete already reviewed this exact issue and has recent Gateway auth history on the same trust-boundary surface.

Owner confidence: high

Options:

- **Use a short-lived browser session (recommended):** Validate the proxy header on a same-origin bootstrap endpoint and mint a short-lived browser credential for the WebSocket path.
- **Validate headers on WebSocket upgrade:** Accept a purpose-built header such as X-OpenClaw-Token during trusted-proxy WebSocket upgrades after origin, proxy, and rate-limit checks.
- **Keep current supported paths:** Decline shared-secret header bootstrap and keep connect.params auth plus identity-bearing Tailscale/trusted-proxy modes as the documented paths.

## Reproduction Assessment

Yes, for source-level reproduction of the missing capability: current main accepts bearer tokens on HTTP Control UI reads, while WebSocket shared-secret auth is still taken from connect.params.auth in the browser connect frame. This is not a broken existing contract; it is an unimplemented feature request.

## Solution Assessment

Unclear until maintainers choose the trust model. The maintainable path is not a quick header passthrough, but a named reverse-proxy bootstrap design with explicit proxy, origin, rate-limit, session, and test semantics.

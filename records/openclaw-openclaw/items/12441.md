## Summary

Keep open. Current main and v2026.6.11 still accept bearer auth for Control UI HTTP reads, but they do not bridge a reverse-proxy-injected shared-secret header into the browser WebSocket connect path; this remains a security-sensitive Gateway auth design item.

## What This Changes

The issue requests Control UI support for reverse-proxy-supplied gateway tokens via Authorization or a similar header instead of token-in-URL/manual bootstrap only.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model in Gateway auth, with trusted-proxy and origin checks, rate limiting, a clear session or WebSocket-upgrade credential path, backward-compatible URL/manual token flows, docs, and focused Gateway/UI tests.

## Reproduction Assessment

Yes for source-level reproduction of the missing capability: current main accepts bearer tokens on HTTP Control UI reads, while WebSocket shared-secret auth is still taken from connect.params.auth in the browser connect frame. This is not a broken existing contract; it is an unimplemented feature request.

## Solution Assessment

Unclear until maintainers choose the trust model. The maintainable path is not a quick header passthrough, but a named reverse-proxy bootstrap design with explicit origin, proxy, rate-limit, session, and test semantics.

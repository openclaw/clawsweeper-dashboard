## Summary

Keep open. Current main and v2026.6.11 still split Control UI HTTP bearer auth from WebSocket shared-secret auth, so proxy-injected header bootstrap remains an unimplemented, security-sensitive Gateway product decision.

## What This Changes

Request to let Control UI bootstrap Gateway shared-secret auth from reverse-proxy-provided Authorization or X-OpenClaw-Token headers instead of relying on URL/manual token entry.

## Best Possible Solution

Define one explicit opt-in reverse-proxy shared-secret bootstrap model, preferably a same-origin bootstrap endpoint that validates the proxy header and issues a short-lived browser session credential, with docs and focused Gateway/UI tests.

## Reproduction Assessment

Yes, at source level. Current main accepts bearer auth for Control UI HTTP reads, but WebSocket shared-secret auth consumes only connect-frame credentials and has no header-to-session bridge for proxy-injected credentials.

## Solution Assessment

Unclear until maintainers choose the trust model. Direct header bootstrap is plausible, but a short-lived same-origin session credential or purpose-specific opt-in header is safer than treating any forwarded Authorization value as the Gateway secret.

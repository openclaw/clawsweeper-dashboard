## Summary

Keep open: current main and v2026.6.11 still do not bridge a reverse-proxy-provided shared-secret header into the Control UI WebSocket auth path, and the remaining work is a security/product decision about Gateway operator credentials.

## What This Changes

The issue requests Control UI authentication bootstrap from reverse-proxy-provided Authorization-style headers instead of token-in-URL or manual UI token entry.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model in Gateway auth, with trusted-proxy and origin checks, rate limiting, clear session or WebSocket-upgrade semantics, backward-compatible URL/manual token flows, docs, and focused Gateway/UI tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which reverse-proxy shared-secret bootstrap model should Control UI support for turning proxy-provided headers into WebSocket credentials?

Rationale: The source gap is clear, but the choice changes how request headers become Gateway operator credentials and affects spoofing protections, trusted proxy requirements, browser origin handling, rate limits, device identity, pairing, and credential lifetime.

Likely owner: steipete

Owner reason: steipete has prior review context on this exact issue and authored the semantic HTTP/WebSocket Gateway auth boundary refactors.

Owner confidence: high

Options:

- **Use Short-Lived Browser Session (recommended):** Validate Authorization or X-OpenClaw-Token on a same-origin bootstrap endpoint and mint a bounded browser credential for the WebSocket path.
- **Validate WebSocket Upgrade Header:** Accept a purpose-built shared-secret header during trusted WebSocket upgrades after origin, proxy, and rate-limit checks.
- **Keep Current Auth Paths:** Decline shared-secret header bootstrap and keep connect-frame auth plus identity-bearing Tailscale/trusted-proxy modes as the supported Control UI paths.

## Reproduction Assessment

Yes. Source inspection shows current main accepts bearer tokens on HTTP Control UI reads, while WebSocket shared-secret auth is still taken from connect.params.auth in the browser connect frame; this is an unimplemented feature request rather than a broken existing contract.

## Solution Assessment

Unclear until maintainers choose the trust model. Header bootstrap is a plausible direction, but the maintainable solution is a named reverse-proxy bootstrap design with explicit proxy, origin, rate-limit, session, and test semantics rather than a raw header passthrough.

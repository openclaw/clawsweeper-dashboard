## Summary

Keep open. Current main and v2026.6.11 still split bearer auth for Control UI HTTP reads from WebSocket shared-secret auth, so proxy-injected header bootstrap remains a security-sensitive Gateway feature decision rather than implemented cleanup.

## What This Changes

The issue requests Control UI support for reverse-proxy-provided gateway tokens via `Authorization` or a similar HTTP header, avoiding URL token bootstrap.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model, preferably either a same-origin bootstrap endpoint that issues a short-lived browser session credential or a tightly scoped opt-in header path for the WebSocket upgrade.

## Reproduction Assessment

Yes, at source level. Current main accepts bearer auth for Control UI HTTP reads, but WebSocket shared-secret auth consumes connect-frame auth and has no header-to-session bridge for proxy-injected credentials.

## Solution Assessment

Unclear until maintainers choose the trust model. Direct header bootstrap is plausible, but a short-lived same-origin session credential or purpose-specific opt-in header may be safer than treating forwarded `Authorization` as a Gateway token.

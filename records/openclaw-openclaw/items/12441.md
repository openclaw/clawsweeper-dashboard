## Summary

Keep open: current main and the latest release still split Control UI HTTP bearer auth from WebSocket shared-secret auth, so reverse-proxy header bootstrap remains an unimplemented security/product decision.

## What This Changes

Control UI should accept a reverse-proxy-provided gateway token from Authorization or X-OpenClaw-Token during bootstrap or handshake so users do not need token-in-URL or manual token entry.

## Best Possible Solution

Define one explicit opt-in reverse-proxy shared-secret bootstrap model: either validate a purpose-specific header on the WebSocket upgrade after origin/proxy/rate-limit checks, or validate it on a same-origin bootstrap endpoint and issue a short-lived browser session credential.

## Reproduction Assessment

Yes, at source level. Current main accepts bearer auth for Control UI HTTP reads, but WebSocket shared-secret auth consumes only connect-frame auth and has no header-to-session bridge for proxy-injected credentials.

## Solution Assessment

Unclear until maintainers choose the trust model. Direct header-to-WebSocket auth is plausible, but a short-lived same-origin session credential or explicit opt-in header is safer than treating every forwarded Authorization bearer as a gateway token.

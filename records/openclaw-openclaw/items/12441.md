## Summary

Keep open. Current main and v2026.6.11 still split bearer-header HTTP reads from browser WebSocket connect-frame auth, so reverse-proxy shared-secret header bootstrap remains an unresolved security-sensitive Gateway auth design decision.

## What This Changes

The issue requests Control UI bootstrap support for reverse-proxy-injected bearer or OpenClaw token headers instead of requiring URL/manual token state for the browser WebSocket connection.

## Best Possible Solution

Define one explicit opt-in reverse-proxy shared-secret bootstrap model, preferably a same-origin bootstrap endpoint that validates the proxy header and issues a short-lived browser session credential, or a tightly scoped WebSocket-upgrade header path with origin, proxy, rate-limit, pairing, and docs/tests coverage.

## Reproduction Assessment

Yes, at source level. Current main accepts bearer auth for Control UI HTTP reads, but WebSocket shared-secret auth consumes only connect-frame auth and has no header-to-session bridge for proxy-injected credentials.

## Solution Assessment

Unclear until maintainers choose the trust model. Direct header bootstrap is plausible, but a short-lived same-origin session credential or purpose-specific opt-in header is likely safer than treating any forwarded Authorization value as a Gateway token.

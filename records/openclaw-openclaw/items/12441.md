## Summary

Keep open: current main and v2026.6.11 still do not convert a reverse-proxy-provided shared-secret header into Control UI WebSocket auth, and the remaining decision is a security-sensitive Gateway auth design choice.

## What This Changes

The issue requests Control UI bootstrap support for proxy-injected Authorization or X-OpenClaw-Token headers so reverse-proxy deployments do not need URL-token or manual-token auth.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model with trusted-proxy/source and origin checks, rate limiting, bounded session or WebSocket-upgrade semantics, backward-compatible manual/URL-token flows, docs, and focused Gateway/UI tests.

Question: Which reverse-proxy shared-secret bootstrap model should Control UI support for turning proxy-provided Authorization or X-OpenClaw-Token headers into WebSocket credentials?

Rationale: The implementation can be shaped several ways, but the choice changes spoofing protections, trusted proxy requirements, browser origin handling, rate limits, device-pairing semantics, and credential lifetime.

Likely owner: steipete

Owner reason: steipete already reviewed this exact item and has the clearest recent history on the Gateway HTTP/WebSocket auth surface split.

Owner confidence: high

Options:

- **Use a short-lived browser session (recommended):** Validate Authorization or X-OpenClaw-Token on a same-origin bootstrap endpoint and mint a bounded browser credential for the WebSocket path.
- **Validate on WebSocket upgrade:** Accept a purpose-built shared-secret header during trusted WebSocket upgrades after origin, proxy, and rate-limit checks.
- **Keep current auth paths:** Decline shared-secret header bootstrap and document connect.params auth plus identity-bearing Tailscale/trusted-proxy modes as the supported Control UI paths.

## Reproduction Assessment

Yes, at source level. Current main accepts bearer tokens on HTTP Control UI reads, while shared-secret WebSocket auth is still taken from connect.params.auth in the browser connect frame.

## Solution Assessment

Unclear until maintainers choose the trust model. A short-lived same-origin browser session looks safer than a raw header passthrough, but either path needs explicit proxy, origin, rate-limit, lifetime, and pairing semantics.

## Summary

Keep open. Current main still accepts bearer auth for HTTP Control UI reads and supports trusted-proxy/Tailscale identity as separate modes, but it does not bridge a proxy-injected shared-secret header into the browser WebSocket connect path; this remains a security-sensitive Gateway auth product decision.

## What This Changes

The issue requests Control UI reverse-proxy bootstrap auth from an HTTP Authorization or X-OpenClaw-Token header instead of URL/manual token entry.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model in Gateway auth, with origin/proxy/rate-limit checks, either WebSocket-upgrade validation or a short-lived browser session credential, backward-compatible URL/manual token flows, docs, and focused Gateway/UI tests.

## Reproduction Assessment

Yes for source-level reproduction: current main accepts bearer tokens on HTTP Control UI reads, while WebSocket shared-secret auth is still taken from connect.params.auth in the browser connect frame. This is not a broken existing contract; it is an unimplemented feature request.

## Solution Assessment

Unclear until maintainers choose the trust model. The maintainable path is not a quick header passthrough, but a named reverse-proxy bootstrap design with explicit origin/proxy/rate-limit/session semantics and tests.

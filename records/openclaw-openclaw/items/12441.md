## Summary

Keep open. Current main and latest release still support bearer headers only for Control UI HTTP reads, while the browser WebSocket admin session remains connect-frame or identity-proxy based; this is a valid but security-sensitive feature decision rather than cleanup.

## What This Changes

The issue requests Control UI authentication bootstrap from a reverse-proxy supplied Authorization or X-OpenClaw-Token header instead of URL-token or manual-token input.

## Best Possible Solution

Define one explicit opt-in reverse-proxy shared-secret bootstrap model, preferably a same-origin bootstrap endpoint that validates the proxy header and issues a short-lived browser session credential, or a tightly scoped WebSocket-upgrade header path with origin, proxy, rate-limit, pairing, docs, and tests coverage.

## Reproduction Assessment

Yes, at source level. Current main accepts bearer auth for Control UI HTTP reads, but WebSocket shared-secret auth consumes only connect-frame auth and has no header-to-session bridge for proxy-injected credentials.

## Solution Assessment

Unclear until maintainers choose the trust model. Direct header bootstrap is plausible, but a short-lived same-origin session credential or purpose-specific opt-in header is likely safer than treating any forwarded Authorization value as a Gateway token.

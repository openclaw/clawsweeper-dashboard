## Summary

Keep open. Current main still supports bearer auth for HTTP Control UI reads and separate trusted-proxy/Tailscale identity modes, but it does not bridge a proxy-injected shared-secret header into the browser WebSocket connect path; this remains a security-sensitive Gateway auth product decision.

## What This Changes

Request that Control UI bootstrap shared-secret auth from proxy-injected Authorization or X-OpenClaw-Token headers instead of relying on URL/manual token entry.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model in Gateway auth, with origin/proxy/rate-limit checks, either WS-upgrade validation or a short-lived browser session credential, backward-compatible URL/manual token flows, docs, and focused Gateway/UI tests.

## Reproduction Assessment

Yes for source-level reproduction of the missing capability: current main accepts bearer tokens on HTTP Control UI reads, while WebSocket shared-secret auth is still taken from connect.params.auth in the browser connect frame. This is not a broken existing contract; it is an unimplemented feature request.

## Solution Assessment

Unclear until maintainers choose the trust model. The maintainable path is not a quick header passthrough, but a named reverse-proxy bootstrap design with explicit origin/proxy/rate-limit/session semantics and tests.

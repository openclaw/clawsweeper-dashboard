## Summary

Keep open: current main still authenticates shared-secret Control UI WebSockets through browser-held connect-frame credentials; proxy identity headers remain separate auth modes, so the requested header-to-WebSocket bridge is still a security-sensitive product decision. ([github.com](https://github.com/openclaw/openclaw/blob/main/ui/src/ui/gateway.ts))

## What This Changes

Allow Control UI authentication to bootstrap from a reverse-proxy-injected bearer or dedicated token header instead of requiring URL or manually entered credentials.

## Best Possible Solution

Validate the injected header only through an explicitly trusted proxy and same-origin bootstrap path, then issue a short-lived, origin- and device-bound browser credential for the WebSocket while preserving existing auth flows and adding focused Gateway, UI, upgrade, and security tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should reverse-proxy shared-secret bootstrap use a short-lived browser session credential, direct WebSocket-upgrade header authentication, or remain unsupported in favor of trusted-proxy identity mode?

Rationale: Each option changes how proxy-controlled headers become full Gateway operator authority, and source inspection cannot determine the intended permanent trust and credential-lifetime policy.

Likely owner: steipete

Owner reason: The current history and prior issue review connect steipete most strongly to Control UI authentication architecture and this exact decision.

Owner confidence: high

Options:

- **Issue short-lived session (recommended):** Validate the injected secret behind explicit proxy and origin checks, then mint a short-lived browser credential bound to the Control UI session and device.
- **Authenticate upgrade header:** Accept the shared secret directly on the WebSocket upgrade only from configured trusted proxies while retaining origin, pairing, and rate-limit enforcement.
- **Use trusted-proxy identity:** Keep shared-secret headers unsupported and document `gateway.auth.mode: "trusted-proxy"` as the canonical reverse-proxy authentication model.

## Reproduction Assessment

Yes at source level: the browser cannot access a proxy-injected request header, creates its WebSocket without custom headers, and supplies shared-secret auth only through the connect frame. ([github.com](https://github.com/openclaw/openclaw/blob/main/ui/src/ui/gateway.ts))

## Solution Assessment

Unclear: directly mapping an injected header into WebSocket authentication is plausible, but a short-lived same-origin bootstrap credential is safer; maintainers must decide whether that model or existing trusted-proxy identity should be canonical.

## Risks / Open Questions

- Accepting a proxy-injected shared secret can grant full trusted-operator access to every request that reaches a misconfigured or spoofable proxy path.
- A page-request credential needs a browser-to-WebSocket handoff that does not expose the long-lived Gateway secret through URLs, JavaScript-readable state, broad cookies, or replayable bootstrap responses.
- The design must preserve origin validation, proxy allowlisting, rate limits, device identity and pairing, and existing token/password/Tailscale/trusted-proxy behavior.

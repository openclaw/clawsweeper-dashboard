## Summary

Keep open. Current main and v2026.6.11 still support bearer auth for Control UI HTTP reads, but they do not bridge a proxy-injected shared-secret header into the browser WebSocket connect path; this remains a valid security-sensitive Gateway auth product decision.

## What This Changes

Request to let Control UI bootstrap Gateway shared-secret auth from reverse-proxy HTTP headers such as Authorization or X-OpenClaw-Token instead of requiring URL/manual UI token input.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model in Gateway auth, with trusted-proxy and origin checks, rate limiting, clear session or WebSocket-upgrade credential semantics, backward-compatible URL/manual token flows, docs, and focused Gateway/UI tests.

## Reproduction Assessment

Yes for source-level reproduction of the missing capability: current main accepts bearer tokens on HTTP Control UI reads, while WebSocket shared-secret auth is still taken from connect.params.auth in the browser connect frame. This is not a broken existing contract; it is an unimplemented feature request.

## Solution Assessment

Unclear until maintainers choose the trust model. The maintainable path is not a quick header passthrough, but a named reverse-proxy bootstrap design with explicit origin, proxy, rate-limit, session, and test semantics.

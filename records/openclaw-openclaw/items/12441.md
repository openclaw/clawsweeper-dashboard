## Summary

Keep open. Current main and v2026.6.11 still accept bearer auth for Control UI HTTP/bootstrap reads, but they do not bridge a reverse-proxy-provided shared secret into the browser WebSocket auth path, so the central feature request remains a Gateway auth product/security decision.

## What This Changes

The issue requests Control UI support for reverse-proxy-provided gateway tokens via HTTP headers instead of only URL/manual token bootstrap.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model in Gateway auth: either validate Authorization/X-OpenClaw-Token on the WebSocket upgrade after existing proxy, origin, and rate-limit checks, or validate it on a same-origin bootstrap endpoint and issue a short-lived browser session credential for the WebSocket.

## Reproduction Assessment

Yes, at source level. Current main accepts bearer auth for Control UI HTTP/bootstrap reads, but WebSocket shared-secret auth consumes only connect-frame auth and has no header-to-session bridge for proxy-injected credentials.

## Solution Assessment

Unclear until maintainers choose the trust model. Direct header bootstrap is plausible, but a short-lived same-origin session credential or purpose-specific opt-in header may be safer than treating any forwarded Authorization bearer as a Gateway token.

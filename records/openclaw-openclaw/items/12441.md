## Summary

Keep open. Current main and the latest release still split HTTP bearer auth for Control UI reads from WebSocket shared-secret auth, so proxy-injected header bootstrap remains an unimplemented, security-sensitive Gateway auth feature decision.

## What This Changes

Request to let Control UI authenticate from a reverse-proxy-supplied gateway token header instead of only URL/manual token flows.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model in Gateway auth, preferably a trusted same-origin bootstrap endpoint that issues a short-lived browser session credential or a tightly scoped opt-in header path for the WebSocket upgrade.

## Reproduction Assessment

Yes, at source level. Current main accepts bearer auth for Control UI HTTP reads, but WebSocket shared-secret auth consumes connect-frame auth and has no header-to-session bridge for proxy-injected credentials.

## Solution Assessment

Unclear until maintainers choose the trust model. Direct header bootstrap is plausible, but a short-lived same-origin session credential or purpose-specific opt-in header may be safer than treating forwarded Authorization as a Gateway token.

## Summary

Keep open. Current main and v2026.6.11 still accept bearer auth for Control UI HTTP reads, but they do not bridge a reverse-proxy-provided shared-secret header into the browser WebSocket connect path; this remains a security-sensitive Gateway auth design item rather than cleanup to close.

## What This Changes

Request that Control UI bootstrap shared-secret auth from proxy-provided Authorization or X-OpenClaw-Token headers instead of relying on URL or manually entered token state for WebSocket auth.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model in Gateway auth, with trusted-proxy and origin checks, rate limiting, a clear session or WebSocket-upgrade credential path, backward-compatible URL/manual token flows, docs, and focused Gateway/UI tests.

## Reproduction Assessment

Yes for source-level reproduction of the missing capability: current main accepts bearer tokens on Control UI HTTP reads, while WebSocket shared-secret auth is still taken from connect.params.auth in the browser connect frame. This is not a broken existing contract; it is an unimplemented feature request.

## Solution Assessment

Unclear until maintainers choose the trust model. The maintainable path is not a quick header passthrough, but a named reverse-proxy bootstrap design with explicit origin, proxy, rate-limit, session, and test semantics.

## Summary

Keep open. Current main and v2026.6.11 still allow bearer auth for HTTP Control UI reads, but they do not bridge a proxy-injected shared-secret header into the browser WebSocket connect path; this remains a security-sensitive Gateway auth product decision.

## What This Changes

The issue requests Control UI authentication bootstrap from proxy-injected Authorization or X-OpenClaw-Token headers instead of relying on URL-token or manual UI-token flows.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model in Gateway auth, either WS-upgrade validation or a short-lived browser session credential, with origin/proxy/rate-limit checks, backward-compatible URL/manual token flows, docs, and focused Gateway/UI tests.

## Reproduction Assessment

Yes for source-level reproduction of the missing capability: current main accepts bearer tokens on HTTP Control UI reads, while WebSocket shared-secret auth is still taken from connect.params.auth in the browser connect frame. This is an unimplemented feature request, not a broken existing contract.

## Solution Assessment

Unclear until maintainers choose the trust model. The maintainable path is not a quick header passthrough, but a named reverse-proxy bootstrap design with explicit origin, proxy, rate-limit, session, and pairing semantics.

## Summary

Keep open. Current main and the latest release still accept bearer auth for Control UI HTTP reads, but they do not bridge a proxy-injected Authorization or X-OpenClaw-Token header into the browser WebSocket shared-secret auth path, so this remains a security-sensitive Gateway auth feature decision.

## What This Changes

The issue requests Control UI auth bootstrap from reverse-proxy-provided Authorization or X-OpenClaw-Token headers instead of relying on URL, fragment, or manual token entry.

## Best Possible Solution

Define an explicit reverse-proxy shared-secret bootstrap model, preferably either a trusted same-origin bootstrap endpoint that issues a short-lived browser session credential or a tightly scoped opt-in header path for WebSocket upgrade after origin, proxy, and rate-limit checks.

## Reproduction Assessment

Yes, source-level. Current main accepts bearer auth for Control UI HTTP reads, but WebSocket shared-secret auth consumes only connect-frame auth and has no header-derived session or WebSocket credential bridge.

## Solution Assessment

Unclear until maintainers choose the trust model. Direct header bootstrap is plausible, but a short-lived same-origin session credential or purpose-specific opt-in header is safer than treating forwarded Authorization as a Gateway token by default.

## Summary

Keep open. Current main and the latest release still support bearer auth for HTTP Control UI reads and separate trusted-proxy/Tailscale identity modes, but they do not bridge a proxy-injected shared-secret header into the browser WebSocket connect path; this remains a security-sensitive Gateway auth product decision.

## What This Changes

The issue requests Control UI support for bootstrapping gateway auth from proxy-injected Authorization or token headers instead of requiring URL/manual token flow.

## Best Possible Solution

Define one explicit reverse-proxy shared-secret bootstrap model in Gateway auth: either validate Authorization/X-OpenClaw-Token during the WebSocket upgrade after existing origin/proxy/rate-limit checks, or validate the header on a same-origin bootstrap endpoint and issue a short-lived browser session credential for the WebSocket; keep URL/manual token flows and trusted-proxy identity mode backward compatible with docs and focused Gateway/UI tests.

## Reproduction Assessment

Yes, for source-level reproduction of the missing capability: current main accepts bearer tokens on HTTP Control UI reads, while WebSocket shared-secret auth is still taken from connect.params.auth in the browser connect frame. This is an unimplemented feature, not a broken existing behavior contract.

## Solution Assessment

Unclear until maintainers choose the trust model. The maintainable solution is a named reverse-proxy bootstrap design with explicit origin, proxy, rate-limit, lifetime, and pairing semantics, not an ad hoc header passthrough.

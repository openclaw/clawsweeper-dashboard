## Summary

Keep open: current main now offers editable `streaming.mode: "progress"` status drafts for Slack, Discord, Telegram, Matrix, and Microsoft Teams, but the requested portable acknowledgement remains unavailable for WhatsApp, WebChat, Feishu, and other channels, and there is no shared customizable text-and-scope contract. The narrower Slack, Discord, and Telegram items overlap with individual delivery strategies but do not replace this cross-channel product/API decision.

## What This Changes

Add a reliable configurable text acknowledgement that appears before agent processing and normal reply dispatch across messaging channels.

## Best Possible Solution

Extend the existing portable progress/presence architecture: core should define one capability-aware lifecycle with customizable starter text and scope, while channel plugins own send, edit, delete, threading, and fallback behavior; unsupported channels should degrade predictably to typing or reactions rather than adding a competing acknowledgement path.

## Maintainer Decision

Kind: product_direction

Question: Should cross-channel acknowledgement text become an extension of the existing `streaming.mode: "progress"` lifecycle, a separate global `messages.ackText` contract, or remain limited to existing reactions, typing, and channel-specific progress drafts?

Rationale: Current main has converged on shared progress drafts for some channels, so adding another global configuration surface without choosing the permanent ownership model would duplicate behavior and leave lifecycle semantics inconsistent.

Likely owner: steipete

Owner confidence: high

Options:

- **Extend progress lifecycle (recommended):** Add customizable starter text, scope, capability negotiation, and cleanup semantics to the shared progress/presence path, then implement it in additional channel plugins.
- **Add global ack text:** Introduce `messages.ackText` and scope fields as a separate pre-dispatch send-and-continue feature across capable channels.
- **Keep existing signals:** Treat progress drafts, typing indicators, and acknowledgement reactions as sufficient and decline a new portable text contract.

## Reproduction Assessment

Yes at source level: current docs expose progress drafts only on selected channels and reaction-only acknowledgement controls elsewhere, while the terminal `before_dispatch` hook cannot send an interim message and continue normal processing. A live WhatsApp, WebChat, or Feishu turn with a delayed agent response provides the direct user-level path.

## Solution Assessment

No, a new standalone `messages.ackText` path is not clearly the best solution now that current main has a shared progress-draft model. The narrower maintainable direction is to extend that portable lifecycle and its channel capability contract rather than create a second source of presence behavior.

## Label Justifications

## Summary

The requested cross-channel text acknowledgement remains absent from current main and the latest release; existing reactions, typing, terminal hooks, and channel-specific progress surfaces are adjacent but do not replace the unresolved product/API decision.

## What This Changes

Add an automatic, scoped text acknowledgement that is sent before agent processing begins across messaging channels.

## Best Possible Solution

Define one typed progress-message lifecycle in the shared channel/plugin contract, while each plugin owns its text, scope, threading, edit/delete, cleanup, and per-account configuration semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should visible pre-processing text be a shared messages configuration contract or a plugin-owned channel capability built on a common lifecycle API?

Rationale: Reactions have reasonably uniform shared semantics, while visible text placeholders affect channel-specific threading, editing, deletion, failure handling, transcripts, and `NO_REPLY`; repository evidence cannot determine the intended permanent product boundary.

Likely owner: steipete

Owner reason: His recent merged work spans the shared dispatch lifecycle, source reply delivery, typing, and acknowledgement cleanup central to this product/API choice.

Owner confidence: high

Options:

- **Typed plugin lifecycle (recommended):** Add a shared lifecycle/capability seam and keep text configuration plus transport-specific send, edit, delete, threading, and cleanup behavior in each channel plugin.
- **Global ack text:** Add `messages.ackText` and shared scope resolution, requiring supported plugins to implement an equivalent cross-channel contract.
- **Separate channel features:** Let each channel add independent placeholder settings without creating a shared lifecycle contract.

## Reproduction Assessment

Yes at source level: current config, schema, dispatch, and docs expose reactions and typing but no supported cross-channel text acknowledgement that sends and then continues processing. This is a clearly demonstrated capability gap, not a regression reproduction.

## Solution Assessment

No, the proposed global config alone is not yet proven to be the best boundary. A common typed lifecycle with plugin-owned transport semantics is narrower and avoids duplicating global and channel-specific placeholder systems.

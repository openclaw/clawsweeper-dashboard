## Summary

Keep open: current main and v2026.6.11 still lack a supported cross-channel text acknowledgement that sends before agent processing and then continues normal dispatch. The gap is source-reproducible, but the permanent boundary between global config, channel placeholders, and plugin hooks needs maintainer product/API direction.

## What This Changes

Request adds a configurable text acknowledgement sent before agent processing, analogous to ackReaction, across messaging channels.

## Best Possible Solution

Define one default-off send-and-continue acknowledgement contract, then align config/schema/help, public docs, channel docs, and focused regression coverage around that chosen boundary.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw solve pre-processing text acknowledgements as a global messages config, as channel-owned placeholder behavior, or as a non-terminal plugin/channel hook contract?

Rationale: The gap is real, but adding config/default surface or a plugin API affects compatibility and overlaps existing reactions, typing, status reactions, and channel-specific placeholder work.

Likely owner: steipete

Owner reason: This handle is the strongest current-history and prior-review routing candidate for the shared dispatch/config boundary.

Owner confidence: high

Options:

- **Design a generic send-and-continue contract (recommended):** Add a default-off API/config seam that can send interim acknowledgement text without terminating normal model dispatch, then migrate channel implementations through that one path.
- **Keep it channel-specific first:** Let Slack, Telegram, Discord, WhatsApp, and Feishu solve placeholders independently, accepting UX divergence while avoiding a premature core contract.
- **Decline new core/API surface:** Keep ack reactions and typing indicators as the supported acknowledgement mechanisms and route richer behavior to plugin-specific implementations only.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 expose reactions, typing indicators, terminal hooks, receive-ack policy, and final replies, but no supported send-and-continue acknowledgement-text path. No live transport run is needed to prove the requested capability is absent.

## Solution Assessment

Unclear until maintainers choose the product/API boundary. messages.ackText is plausible, but a non-terminal plugin or channel hook may be the cleaner long-term seam for cross-channel and channel-specific behavior.

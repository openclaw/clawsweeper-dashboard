## Summary

Keep open: current main still has reactions, lifecycle status signals, typing, and final-delivery hooks, but no supported cross-channel text acknowledgment that is sent before processing while normal dispatch continues; the open Slack, Discord, and Telegram items cover narrower channel-specific variants rather than replacing this product/API decision. ([docs.openclaw.ai](https://docs.openclaw.ai/gateway/config-agents))

## What This Changes

Requests an opt-in cross-channel text acknowledgment sent immediately after message receipt and before normal agent processing continues.

## Best Possible Solution

Define one typed pre-run acknowledgment lifecycle with shared scope policy and channel-owned send/edit/delete rendering, then expose only the minimum opt-in configuration needed for supported channels.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should immediate text acknowledgment be a shared `messages.*` product contract, a generic plugin/channel SDK lifecycle, or remain limited to existing reaction and native-status signals?

Rationale: The choice creates new configuration and delivery semantics across multiple channel owners, and current hooks do not settle ownership, continuation, cleanup, or compatibility behavior.

Likely owner: steipete

Owner reason: They are the strongest available routing candidate across shared dispatch, acknowledgment lifecycle, channel delivery, and prior issue review context.

Owner confidence: high

Options:

- **Add a generic channel lifecycle (recommended):** Introduce a typed pre-run acknowledgment contract in the public channel SDK, keep native send/edit/delete behavior in channel plugins, and layer shared scope policy above it.
- **Add global ackText config:** Implement `messages.ackText` centrally with per-channel/account overrides and require each supported channel to map the same lifecycle semantics.
- **Keep status-only feedback:** Decline posted text acknowledgments and standardize reactions, typing, and native status surfaces as the supported liveness UX.

## Reproduction Assessment

Yes at source level: current configuration and hook documentation show reaction/status feedback but no supported text reply that can be emitted before processing and then continue the same turn; no live runtime reproduction was needed to establish the missing capability.

## Solution Assessment

No, not yet: `ackText` is a plausible UX surface, but the maintainable fix first needs a generic lifecycle and channel-capability contract so Slack, WhatsApp, WebChat, Feishu, Telegram, and other plugins do not develop competing delivery semantics.

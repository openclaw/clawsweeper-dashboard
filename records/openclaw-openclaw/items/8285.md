## Summary

Keep open: shipped progress drafts now reduce silent waits on several edit-capable channels, but current main still lacks an immediate, portable text acknowledgment contract for channels such as WhatsApp and Feishu, and maintainers must choose whether this belongs in the shared progress lifecycle or a separate persistent-send feature.

## What This Changes

Requests a configurable cross-channel text acknowledgment sent immediately before agent processing begins.

## Best Possible Solution

Extend the shared live-preview/progress lifecycle with an operator-configurable immediate generic receipt, capability-gated per channel and account, with explicit finalization and non-editable-channel fallback semantics rather than adding a parallel model-driven acknowledgment path.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should immediate text acknowledgment become a shared progress-draft lifecycle option, or a separate persistent message contract for channels that cannot safely edit or delete a draft?

Rationale: Current main has a strong shared progress implementation, but an unconditional pre-processing send changes message clutter, cleanup, privacy, transport capability, and configuration semantics; repository evidence cannot determine the intended product policy.

Likely owner: vincentkoc

Owner reason: Recent history most strongly connects Vincent to the shared progress-draft and channel message-lifecycle surfaces where this direction would be implemented.

Owner confidence: high

Options:

- **Extend progress lifecycle (recommended):** Add configurable immediate-start timing and a generic operator-authored label to shared progress drafts, with capability-aware fallbacks for channels without safe edit support.
- **Add persistent ack text:** Introduce a separate scoped acknowledgment-message contract that sends a permanent text reply before every qualifying agent run.
- **Keep channel-specific behavior:** Continue using progress drafts, typing indicators, and reactions per transport without promising one cross-channel text acknowledgment contract.

## Reproduction Assessment

No live current-main reproduction was run, but the gap is source-reproducible with high confidence: current configuration exposes reactions and channel progress modes, while progress drafts are delayed, work-gated, and unavailable as a portable immediate text acknowledgment.

## Solution Assessment

No, a parallel global `messages.ackText` send is not yet demonstrated to be the best solution. The narrower maintainable direction is to extend the existing shared progress/live-message lifecycle and define capability-aware behavior for transports that cannot safely edit or remove a draft.

## Risks / Open Questions

- A separate persistent acknowledgment send could clutter chats, duplicate the shared progress-draft lifecycle, and require cleanup semantics on failure or `NO_REPLY`.
- Non-editable channels need an explicit policy for whether acknowledgments remain as permanent messages, are deleted when supported, or fall back to reactions and typing indicators.
- Dynamic intent text generated before dispatch could expose request details or imply understanding before the agent has actually interpreted the message; a generic operator-authored label is safer.

## Label Justifications

- `P2`: The missing acknowledgment creates recurring cross-channel uncertainty and perceived latency, but users can continue and reaction-based acknowledgment remains available.
- `impact:ux-friction`: Users wait through long processing gaps without the requested visible text signal, increasing confusion without fully blocking message processing.

## Summary

Keep open: released progress drafts now reduce the silent wait on several edit-capable channels, but current main still lacks a portable pre-processing text acknowledgment for WhatsApp, WebChat, Feishu, and other channels, and the root message contract still exposes reactions rather than acknowledgment text. ([raw.githubusercontent.com](https://raw.githubusercontent.com/openclaw/openclaw/main/docs/concepts/streaming.md))

## What This Changes

Add a configurable, scoped text acknowledgment that is sent immediately after accepting an inbound message and before normal agent processing continues.

## Best Possible Solution

Extend the shared channel streaming/presence contract with a capability-gated pre-dispatch initial status text, scope controls, and defined cleanup/final-delivery semantics, then implement it for WhatsApp, WebChat, Feishu, and other capable channels without creating parallel channel-specific policies.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should portable pre-processing acknowledgment text become an initial phase of the existing channel streaming/progress lifecycle, or a separate global messages.ackText contract?

Rationale: Both designs are feasible, but they create different long-term ownership, configuration, plugin-API, notification, and cleanup contracts; repository policy sets a high bar for adding another root config surface.

Likely owner: steipete

Owner reason: The available history and prior issue review most directly connect steipete to shared reply lifecycle behavior and the cross-channel product boundary.

Owner confidence: high

Options:

- **Extend progress lifecycle (recommended):** Add a portable pre-dispatch status phase to shared streaming/presence contracts, with channel capability fallbacks and explicit cleanup semantics.
- **Add messages.ackText:** Create a separate global acknowledgment-text configuration mirroring ackReaction scopes, accepting a second source of visible progress policy.
- **Keep existing signals only:** Rely on reactions, typing, and current per-channel progress drafts without promising portable immediate text.

## Reproduction Assessment

Yes at source level: current config and streaming documentation show no portable pre-processing text acknowledgment, while the reported channels include unsupported WhatsApp, WebChat, and Feishu paths. No live multi-channel reproduction was run.

## Solution Assessment

No, a standalone messages.ackText option is not yet proven to be the best design because it would overlap with the newer shared streaming/progress lifecycle; extending that lifecycle is the narrower long-term direction if maintainers want portable behavior.

## Summary

Keep open. The requested portable pre-processing text acknowledgement is still not established as a supported cross-channel capability, and the existing reactions, typing, channel-specific presence work, and terminal hook behavior do not settle the shared lifecycle or configuration contract. A maintainer product decision is needed before implementation. Likely related people are listed below for routing.

## What This Changes

Add a supported configurable text acknowledgement that is sent immediately before normal agent processing across messaging channels.

## Best Possible Solution

Choose one supported shared pre-dispatch progress lifecycle, then implement either a narrowly scoped portable acknowledgement-text contract or a non-terminal plugin/channel hook with explicit capability, ordering, cleanup, and per-channel override semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw provide a shared pre-dispatch text-acknowledgement lifecycle, and if so should it be a portable `messages` configuration contract or an explicit non-terminal plugin/channel hook?

Rationale: Both routes add compatibility-sensitive public surface and determine where channel-specific placeholder, typing, and cleanup behavior belongs; current code does not make that ownership decision automatically.

Likely owner: steipete

Owner reason: The recent reply-dispatch and acknowledgement lifecycle history provides the strongest routing signal for choosing the shared boundary.

Owner confidence: high

Options:

- **Define a portable lifecycle (recommended):** Specify one shared acknowledgement lifecycle and a minimal portable configuration contract, with channels mapping it only where their transport supports it.
- **Add a non-terminal extension seam:** Expose a documented send-and-continue hook so channel plugins or external plugins own visible interim text without a global messages option.
- **Keep channel-specific UX only:** Leave visible progress to channel-owned presence, typing, and placeholder features instead of promising cross-channel text parity.

## Reproduction Assessment

No high-confidence runtime reproduction is needed to establish the request: source inspection shows no supported portable acknowledgement-text field or send-and-continue hook. A live multi-channel scenario would be needed after maintainers select the intended contract.

## Solution Assessment

Unclear. The proposed `messages.ackText` shape is plausible, but it is not yet proven to be the best solution because the shared lifecycle, plugin boundary, and channel fallback behavior remain undecided.

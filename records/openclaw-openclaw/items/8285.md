## Summary

Current main still lacks a supported cross-channel text acknowledgment that sends before ordinary agent processing and then continues the run. Reactions, typing, Slack thread status, Telegram plugin-command placeholders, and the terminal `before_dispatch` hook are useful precedents but do not satisfy the broad request; the remaining choice is a maintainer-owned product/API direction.

## What This Changes

Add configurable visible acknowledgment text before agent processing across messaging channels, with scope comparable to acknowledgment reactions.

## Best Possible Solution

Define an opt-in typed processing-feedback lifecycle carrying start, optional update, and finish intent plus correlation; let each channel plugin choose native status, reaction, placeholder message, edit, delete, or no-op behavior according to its capabilities.

Options:

- **Portable lifecycle seam (recommended):** Add typed processing-start, update, and finish intent while channel plugins own transport-specific rendering and cleanup.
- **Channel-local features:** Keep Slack, Discord, Telegram, Feishu, WhatsApp, and WebChat implementations independent with channel-specific configuration.
- **Static global ack text:** Add only a shared acknowledgment string and scope without standardized edit, failure, concurrency, or cleanup behavior.

## Reproduction Assessment

Yes. Current main has no acknowledgment-text field in shared message config, and the closest shared pre-dispatch hook ends the turn when it sends text instead of continuing agent processing.

## Solution Assessment

No, the proposed `messages.ackText` shape alone is not the best solution; a typed lifecycle with channel-owned presentation is narrower at the ownership boundary and handles existing native-status and editable-placeholder differences.

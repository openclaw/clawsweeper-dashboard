## Summary

Current main still lacks a supported cross-channel text acknowledgment that sends before agent work and then continues normal dispatch. Reactions, lifecycle reactions, typing, and the existing claiming `before_dispatch` hook are adjacent but do not satisfy the request, so this remains a valid product/API decision rather than cleanup.

## What This Changes

Add an opt-in text acknowledgment sent before agent processing while normal dispatch continues.

## Best Possible Solution

Define a distinct typed, non-terminal, capability-aware acknowledgment lifecycle that preserves the existing claiming hook, keeps transport sends in channel plugins, and specifies create, cleanup, failure, concurrency, and `NO_REPLY` behavior before consolidating narrower channel work.

Options:

- **Shared non-terminal lifecycle (recommended):** Add a distinct typed hook and channel capability contract while leaving acknowledgment wording and enablement to plugins or deployments.
- **Core messages configuration:** Add shared acknowledgment policy under `messages` and route delivery through channel-owned adapters.
- **Channel-specific placeholders:** Keep each transport's placeholder, edit, and cleanup semantics independent without a shared API.

## Reproduction Assessment

Yes at source level: current main supports acknowledgment reactions, lifecycle reactions, typing, and terminal pre-dispatch handling, but no supported text acknowledgment that sends and then continues normal processing.

## Solution Assessment

No, the proposed bare `ackText` fields are not the best complete solution because they omit lifecycle, cleanup, channel-capability, strict-delivery, failure, concurrency, and `NO_REPLY` semantics; a distinct typed non-terminal lifecycle is safer.

## Summary

Keep open: current main and the latest release intentionally require an explicit Slack owner ID for bot-authored room messages, but the report identifies a real message-loss and UX gap around a documented but surprising `allowBots` configuration. Changing this path is security-sensitive because it controls whether Slack bot messages can reach an agent without an owner-presence signal.

## What This Changes

Request to make Slack `allowBots: true` with wildcard `allowFrom` useful for bot-authored room messages, or at least warn when that config cannot admit bot messages.

## Best Possible Solution

Keep the conservative owner-presence default, then add a maintainer-approved Slack doctor/setup/status diagnostic or an explicit opt-in mode only if maintainers accept the bot-to-bot relay tradeoff.

Options:

- **Keep gate and add diagnostics (recommended):** Preserve explicit-owner presence and add a visible doctor/setup/channel-status warning for `allowBots` with wildcard-only `allowFrom`, plus docs that name the supported config.
- **Add explicit permissive mode:** Introduce a clearly named opt-in mode such as `allowBots: "all"` with loop-protection and security docs so users can choose the tradeoff without weakening the default.
- **Treat wildcard as owner presence:** Make `allowFrom: ["*"]` satisfy the current gate, accepting that bot-authored room messages can reach the agent whenever the channel is otherwise allowed.

## Solution Assessment

Unclear. The current gate is a maintainable security hardening, but the best user-facing fix is probably a visible diagnostic or explicit opt-in mode rather than silently making wildcard owner presence permissive.

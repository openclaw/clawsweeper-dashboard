## Label Justifications

- `P1`: The issue reports a current released Slack channel workflow where bot/app messages are silently dropped in production under a plausible `allowBots` configuration.
- `impact:security`: The affected path is the Slack bot-room owner-presence gate that prevents bot relays from running without an explicit owner in the room.
- `impact:message-loss`: The observable failure is dropped Slack bot-authored channel messages before agent dispatch.
- `impact:ux-friction`: The drop is only verbose-logged and short config help says `allowBots` allows bot-authored messages without warning that wildcard-only owner config is inert for rooms.

## Summary

Keep open: current main and the latest tagged release still drop Slack bot-authored room messages when `allowBots` is enabled but `allowFrom` is wildcard-only, and changing that path affects the owner-presence security guard created for https://github.com/openclaw/openclaw/issues/59284.

## What This Changes

The issue asks OpenClaw to make Slack `allowBots: true` with wildcard-only `allowFrom` either admit bot messages, expose an explicit all-bot mode, or warn that the configuration is inert for room bot messages.

## Best Possible Solution

Keep the owner-presence guard by default, add clear Slack doctor/startup/config UI diagnostics for ownerless `allowBots` room setups, and only add an explicit all-bot mode if maintainers deliberately accept that security boundary with docs and tests.

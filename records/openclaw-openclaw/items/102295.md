## Label Justifications

- `P1`: The issue reports a current released Slack workflow where bot/app messages are silently dropped in production under a plausible `allowBots` configuration.
- `impact:security`: The affected code is the Slack bot-room owner-presence gate that controls whether bot-authored messages can reach agent dispatch.
- `impact:message-loss`: The observable failure is dropped Slack bot-authored room messages before OpenClaw dispatches them.
- `impact:ux-friction`: The drop is only verbose-logged and config help does not clearly warn that wildcard-only owner config is inert for room bot messages.

## Summary

Keep open: current main and v2026.6.11 still fail-close wildcard-only Slack `allowBots` room bot messages, and the remaining fix is a maintainer security/UX decision rather than a stale or already-implemented item. The contributor's prototype branch is useful context for an explicit all-bot mode, but no open PR currently owns the final direction.

## What This Changes

This issue asks Slack `allowBots` wildcard-only configs to stop silently dropping bot-authored room messages, either by changing admission semantics, adding an explicit all-bot mode, or warning on inert configs.

## Best Possible Solution

Keep the owner-presence guard as the default, add clear Slack doctor/startup/config diagnostics for wildcard-only `allowBots` room setups, document the supported per-channel `users` or explicit-owner paths, and add an explicit all-bot mode only if maintainers deliberately approve that security boundary.

## Label Justifications

- `P1`: The issue reports a current released Slack channel workflow where bot/app messages are silently dropped in production under a plausible documented-looking `allowBots` configuration.
- `impact:message-loss`: The observable failure is dropped Slack bot-authored channel messages before agent dispatch.
- `impact:security`: The affected behavior is the Slack bot-room owner-presence gate that protects bot-to-bot relays from running without an explicit owner in the room.
- `impact:ux-friction`: The drop is only verbose-logged and the short config help says `allowBots` allows bot-authored messages without warning that wildcard-only owner config is inert for rooms.

## Summary

Keep open: current main still drops Slack bot-authored room messages when `allowBots` is enabled but `allowFrom` is wildcard-only, and changing that behavior would touch the security guard added for https://github.com/openclaw/openclaw/issues/59284.

## What This Changes

Requests changing or warning on Slack `allowBots: true` with wildcard `allowFrom` because the current owner-presence gate drops bot-authored room messages unless an explicit owner ID or per-channel bot user is configured.

## Best Possible Solution

Keep the owner-presence guard by default, add a clear Slack doctor/security-audit/startup warning for `allowBots` with no explicit owner or per-channel bot allowlist, and only add an explicit all-bot mode if maintainers deliberately accept that security boundary with docs and tests.

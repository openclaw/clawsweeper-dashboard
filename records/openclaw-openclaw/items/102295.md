## Label Justifications

- `P1`: The issue reports a current released Slack workflow where bot/app messages are silently dropped in production under a plausible `allowBots` configuration.
- `impact:security`: The affected path is the Slack bot-room owner-presence gate that prevents bot relays from running without an explicit owner in the room.
- `impact:message-loss`: The observable failure is dropped Slack bot-authored channel messages before agent dispatch.
- `impact:ux-friction`: The drop is only verbose-logged, while shorter config help does not warn that wildcard-only owner config is inert for Slack rooms.

## Summary

Keep open: current main and v2026.6.11 still source-prove the wildcard-only Slack `allowBots` drop, and resolving it requires a maintainer Slack security/compatibility choice rather than cleanup closure.

## What This Changes

The issue asks OpenClaw to stop silently dropping Slack bot-authored room messages for wildcard-only `allowBots` configurations, either by changing admission semantics, adding an explicit all-bot mode, or warning on inert config.

## Best Possible Solution

Keep the owner-presence guard as the default, add clear Slack doctor/startup/config diagnostics for ownerless `allowBots` room setups, and add an explicit all-bot mode only if maintainers deliberately accept that security boundary with docs, tests, and live proof.

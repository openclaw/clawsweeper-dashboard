## Label Justifications

- `P1`: A released Slack workflow can silently drop bot/app messages in production under a plausible `allowBots` configuration.
- `impact:security`: The affected path is the Slack bot-room owner-presence gate that limits bot relays without an explicit owner in the room.
- `impact:message-loss`: The observable failure is Slack bot-authored channel messages being dropped before agent dispatch.
- `impact:ux-friction`: The failure is only verbose-logged and short config help does not make the ownerless wildcard behavior clear.

## Summary

Keep open: current main still drops Slack bot-authored room messages for wildcard-only `allowFrom`, and the remaining fix requires a maintainer decision because relaxing that path changes the owner-presence security guard from the prior Slack bot-relay issue.

## What This Changes

The issue asks OpenClaw to stop silently dropping Slack bot/app room messages when `allowBots` is enabled with wildcard-only `allowFrom`, either by changing semantics, adding an explicit all-bot mode, or warning on inert config.

## Best Possible Solution

Keep the owner-presence guard as the default, add clear Slack doctor/startup/config diagnostics for ownerless `allowBots` room setups, and only add an explicit all-bot mode if maintainers deliberately accept that security boundary with docs and regression tests.

Options:

- **Warn and preserve guard (recommended):** Add Slack doctor/startup/config UI diagnostics for wildcard-only or ownerless `allowBots` setups while keeping explicit owner presence or per-channel bot allowlists required for room bot messages.
- **Add explicit all-bot mode:** Introduce `allowBots: "all"` as an intentionally unsafe opt-in that skips owner-presence authorization while preserving mention rules and bot loop protection.
- **Treat wildcard as owner presence:** Let wildcard `allowFrom` satisfy the room bot gate, restoring intuitive wildcard behavior but weakening the prior owner-presence security boundary for existing configs.

## Reproduction Assessment

## Solution Assessment

Unclear pending maintainer intent. The linked `allowBots: "all"` branch is a plausible option, but diagnostics that preserve the owner-presence guard are the safer first direction unless maintainers explicitly accept the bypass.

## Summary

Keep this issue open: current `main` and the latest release still have the reported Telegram sent-message cache rewrite path, the issue has the protected `maintainer` label, and an open closing PR already owns the candidate fix.

## What This Changes

The issue reports that Telegram sent-message cache persistence rewrites all live entries to SQLite on every outbound send.

## Best Possible Solution

Review and land the linked Telegram PR, or replace it with an equivalent narrow cache persistence fix that writes only the newly recorded row while preserving the existing namespace, TTL, and cap behavior.

## Reproduction Assessment

Yes from source: on current `main`, every `recordSentMessage` call reaches `persistSentMessages`, which loops over all cached messages and registers each one with the sync plugin-state store. I did not run a load repro because this read-only review already establishes the write-amplification path.

## Solution Assessment

Yes: persisting only the newly recorded sent-message row is the narrowest maintainable fix because the store already has per-entry TTL and max-entry enforcement. The linked PR appears to target that boundary directly, so the issue should stay open for that PR review path.

## What This Changes

Adds a global `messages.pairingTemplate` setting and applies it through shared pairing generation, Plugin SDK helpers, config metadata, tests, and pairing documentation.

## Best Possible Solution

If maintainers sponsor this capability, keep one validated global configuration path, prevent per-channel or per-call overrides from leaking into the public Plugin SDK, require the rendered template to carry an approval credential, and prove both configured and unchanged-default behavior on a real pairing-capable channel.

## Review Findings

Overall confidence: 0.9

Full review comments:

- **[P1] Keep template overrides out of the public pairing SDK:** `src/plugin-sdk/channel-pairing.ts:40-49`
  - body: The feature is described as one global config value, but this exported function now exposes both a `resolvePairingTemplate` option and, through the inferred `Omit`, a per-challenge `pairingTemplate` argument. Third-party plugins can therefore create per-account or per-message behavior that the product explicitly says is out of scope, leaving a parallel public contract that will be difficult to remove. Resolve the global value behind the controller/internal implementation and explicitly omit the template field from the public challenge type.
  - confidence: 0.93
- **[P2] Reject templates that cannot communicate an approval code:** `src/config/zod-schema.session.ts:155`
  - body: The schema accepts an empty string or text containing neither `{code}` nor `{approveCommand}`. Because the request is persisted before the reply is sent and an existing pending request is not replied to again, such a configuration can strand new senders without any usable approval credential. Validate that at least one of those placeholders is present and cover the rejection path.
  - confidence: 0.9

## Summary

Keep open. Current main still isolates Slack DM/main and channel sessions, mirrors outbound sends into the destination session, and defaults session tools to tree-only visibility. A broad same-agent visibility mode exists, but it exposes more sibling-session history than the requested privacy-scoped recall, so the remaining work needs an explicit security and product contract. citeturn8view0turn9view0turn10view0turn11view0

## What This Changes

Add privacy-scoped recall of an agent’s own Slack channel messages from a separate DM session.

## Best Possible Solution

Provide a narrowly authorized self-activity query backed by canonical agent-scoped SQLite state or an equivalent indexed transcript projection, containing only self-authored outbound messages and their Slack workspace/account, destination, thread, message ID, timestamp, edit, and deletion metadata; do not merge full sessions or widen default sibling-session access.

- **Scoped self-activity view (recommended):** Expose only self-authored outbound Slack activity through a separately authorized agent-scoped query with workspace, account, destination, thread, edit, and deletion boundaries.
- **Document agent-wide visibility:** Treat tools.sessions.visibility=agent as the supported solution, accepting that the caller can inspect full same-agent sibling-session history.
- **Preserve strict isolation:** Keep the existing boundary and document that DM sessions cannot recall activity from sibling Slack conversations.

## Reproduction Assessment

Yes, at source level. A channel-targeted Slack send is mirrored to the destination session, while the requesting DM/main session defaults to tree-only visibility and cannot inspect that sibling session.

## Solution Assessment

No, the broad session-merging and blanket cross-session-history options are not the best solution. A dedicated self-authored activity view is narrower, preserves conversation isolation, and avoids creating a competing session source of truth.

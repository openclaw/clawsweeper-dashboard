## What This Changes

Make `doctor --fix` migrate large legacy Memory Core databases with bounded WAL growth, observable progress, safe interruption, and durable resumption.

## Best Possible Solution

Use an explicit migration-state record and deterministic row cursor to copy and validate bounded batches, checkpoint WAL between batches, report phase and row progress, preserve the source until final cross-table verification, and provide an in-product safe-abort/resume path before the gateway depends on the destination.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should legacy Memory Core migration become a resumable sequence of committed batches, or remain fully atomic and refuse large stores until an offline migration path is available?

Rationale: The current single savepoint is atomic but operationally unbounded, while naïve batching could expose partial canonical state; repository policy does not by itself choose the permanent upgrade contract between these safety properties.

Likely owner: vincentkoc

Owner reason: They co-authored the released migration and have adjacent Memory Core and doctor ownership history.

Owner confidence: high

Options:

- **Resumable staged migration (recommended):** Commit idempotent batches behind a durable migration-state marker, keep runtime access disabled until final verification, and resume safely after interruption.
- **Offline atomic migration:** Retain one atomic transaction but preflight large stores and require an explicit offline migration flow with progress and sufficient disk-space checks.
- **Defer automatic migration:** Stop `doctor --fix` from importing oversized indexes and leave the legacy database authoritative until a dedicated migration tool is ready.

## Reproduction Assessment

Yes at source level: current `main` deterministically performs the complete multi-table import and validation under one savepoint, matching the observed zero-visible-rows and large-WAL behavior. A controlled multi-gigabyte runtime reproduction was not run during this read-only review.

## Solution Assessment

No, committing every N rows alone is not sufficient because runtime could observe partial canonical state. The best fix combines bounded batches with a durable migration-state gate, idempotent cursors, final verification, progress reporting, and source preservation.

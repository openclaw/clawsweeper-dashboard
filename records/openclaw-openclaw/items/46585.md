## Summary

## What This Changes

The issue requests that `openclaw nodes camera snap --facing front --device-id <iPhone Continuity Camera>` use the iPhone front camera instead of always capturing from the rear camera.

## Best Possible Solution

Live-test the current macOS companion with a paired iPhone, then either implement a supported Continuity front/back selector with focused tests/docs or document a clear limitation while preserving exact `deviceId` semantics.

## Maintainer Decision

Required: true

Question: Should macOS camera capture keep `deviceId` as an exact selector when `facing` is also provided for an iPhone Continuity Camera device that reports `position: unspecified`?

Rationale: The current implementation treats `deviceId` as exact across platforms, while the issue expects `facing` to select a lens behind one Continuity Camera device; automation cannot choose that compatibility contract without maintainer intent and live AVFoundation proof.

Options:

- **Preserve exact device IDs pending live proof (recommended):** Keep `deviceId` exact by default and add a diagnostic or docs limitation unless live proof shows a supported narrow Continuity lens selector.
- **Implement Continuity lens selection:** If live AVFoundation proof shows a reliable front/back selector for the same iPhone device, implement that narrow macOS path with tests and docs.
- **Let facing override device ID:** Change selector precedence so `facing` can replace an explicit device id, accepting compatibility risk for existing multi-camera users.

## Solution Assessment

Unclear. A direct precedence swap is not clearly the best fix because `deviceId` is a precise selector across camera implementations; the maintainable path depends on live AVFoundation behavior and maintainer intent.

Full review comments:

- **[P1] Prove and type the union_id source before matching on it:** `extensions/feishu/src/probe.ts:137`
  - body: This line reads `bot?.union_id`, but this PR head's `FeishuBotInfoResponse` type only declares `bot_name` and `open_id`, so it does not typecheck as written. Even after typing is fixed, the linked issue and same-author closed sibling say this bot info path did not return `union_id`, so the fallback may never populate.
  - confidence: 0.93
- **[P2] Cover post mentions with the fallback identity:** `extensions/feishu/src/bot.ts:479`
  - body: The new fallback only participates in the top-level `message.mentions` branch. Rich-text post mentions still compare parsed mention IDs to `botOpenId`, so the same app-scoped mismatch can still make a post @mention look unmentioned and be dropped.
  - confidence: 0.84
- **[P2] Strip fallback-matched mentions before command parsing:** `extensions/feishu/src/bot.ts:797`
  - body: This can set `mentionedBot` through `botUnionId`, but content normalization still strips only by `botOpenId`. A multi-bot `@Bot /help` that matched by union_id can keep the raw mention before `/help`, undermining the slash-command behavior this parser comment protects.
  - confidence: 0.87
- **[P2] Carry fallback identity through debounce batching:** `extensions/feishu/src/monitor.account.ts:251`
  - body: Passing `botUnionId` to the final handler is not enough because the debounce path still parses text and filters merged mentions with `botOpenId` only. A burst where the target mention is only in an earlier event can still produce a merged dispatch that fails the requireMention gate.
  - confidence: 0.8

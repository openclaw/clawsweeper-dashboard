Full review comments:

- **[P1] Prove the union_id source before relying on it:** `extensions/feishu/src/probe.ts:137`
  - body: This stores `botUnionId` from `bot?.union_id`, but the local response type and the linked issue evidence say the bot info path only provides bot name/open_id. If that remains true, the fallback never populates and the reported multi-bot mention loss is unchanged.
  - confidence: 0.93
- **[P2] Cover post mentions with the fallback identity:** `extensions/feishu/src/bot.ts:473`
  - body: The new fallback only participates in the top-level `message.mentions` branch. Rich-text post mentions still compare parsed IDs only to `botOpenId`, so the same app-scoped mismatch can still make a post @mention look unmentioned.
  - confidence: 0.82
- **[P2] Strip fallback-matched mentions before command parsing:** `extensions/feishu/src/bot.ts:790`
  - body: This can set `mentionedBot` through `botUnionId`, but content normalization still strips only by `botOpenId`. A multi-bot `@Bot /help` that matched by union_id can keep the raw mention before `/help`, undermining the slash-command behavior this parser comment protects.
  - confidence: 0.86
- **[P2] Carry fallback identity through debounce batching:** `extensions/feishu/src/monitor.account.ts:251`
  - body: Passing `botUnionId` to the final handler is not enough because the debounce path still parses text and filters merged mentions with `botOpenId` only. A burst where the target mention is only in an earlier event can still produce a merged dispatch that fails the requireMention gate.
  - confidence: 0.8

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P1] Prove the bot union_id source before relying on it:** `extensions/feishu/src/probe.ts:137`
  - body: `probeFeishu` stores `bot?.union_id`, but the PR head's `FeishuBotInfoResponse` type only declares `bot_name` and `open_id`, and the linked canonical discussion says `bot/v3/info` does not return `union_id` for this bot workflow. When that field is absent, `botUnionIds` stays empty and the multi-bot mention bug remains; use a documented/proven identity source and cover it with tests and live proof.
  - confidence: 0.9
- **[P2] Cover post mentions with the fallback identity:** `extensions/feishu/src/bot.ts:790`
  - body: The changed call now passes `botUnionId` into `checkBotMentioned`, but the helper's rich-text `post` branch still compares parsed mention ids only to `botOpenId`. A Feishu post/rich-text @mention with the same app-scoped open_id mismatch will still be treated as unmentioned under `requireMention`.
  - confidence: 0.86
- **[P2] Strip fallback-matched mentions before command parsing:** `extensions/feishu/src/bot.ts:797`
  - body: `mentionedBot` can become true through `union_id`, but `normalizeMentions` still strips only the stored `botOpenId`. In the exact multi-bot mismatch case, `@Bot /model` keeps the bot mention in `ctx.content`, so command probing can miss the leading slash even though the bot was addressed.
  - confidence: 0.88
- **[P2] Carry fallback identity through debounce batching:** `extensions/feishu/src/monitor.account.ts:251`
  - body: Adding `botUnionId` to the final dispatch is not enough: the debounce path still builds text with `parseFeishuMessageEvent(event, botOpenId, ...)` and filters merged mentions by `mention.id.open_id`. Batched messages can therefore lose the fallback-matched bot mention and still be dropped by the group mention gate.
  - confidence: 0.85

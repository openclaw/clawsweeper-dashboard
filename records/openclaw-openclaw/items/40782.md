Full review comments:

- **[P1] Prove the union_id source before relying on it:** `extensions/feishu/src/probe.ts:137`
  - body: This reads `bot?.union_id`, but the linked issue and closed same-author sibling say the Feishu bot info path does not return `union_id`. If that remains true, `botUnionId` is always undefined and the fallback never fixes the reported multi-bot mention loss.
  - confidence: 0.93
- **[P2] Cover post mentions with the fallback identity:** `extensions/feishu/src/bot.ts:477-479`
  - body: The fallback only participates in the top-level `message.mentions` branch. Rich-text post mentions still flow through the open_id-only post branch, so the same app-scoped mismatch can still make a post @mention look unmentioned.
  - confidence: 0.82
- **[P2] Strip fallback-matched mentions before command parsing:** `extensions/feishu/src/bot.ts:797`
  - body: `parseFeishuMessageEvent` accepts `botUnionId`, but content normalization still strips only by `botOpenId`. A multi-bot `@Bot /help` that matched by union_id can keep the raw mention in front of `/help`, undermining the slash-command behavior this parser comment protects.
  - confidence: 0.86
- **[P2] Carry fallback identity through debounce batching:** `extensions/feishu/src/monitor.account.ts:251`
  - body: This final handler call receives `botUnionId`, but the debounced batch path still resolves text and merged bot mentions with `botOpenId` only. A burst where the target mention is only in an earlier event can still dispatch a merged event that fails the requireMention gate.
  - confidence: 0.8

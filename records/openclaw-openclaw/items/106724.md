## Summary

Keep this security report open for maintainer review: the named GitHub-auth and SQLite files do not exist on current main, but the underlying concern is real because GitHub Copilot device authentication writes a token into the per-agent auth profile and current documentation states that OAuth credentials remain plaintext rather than using SecretRef. The report therefore identifies a valid security-design question, although its storage path, attack narrative, and proposed provider-specific solution need correction. citeturn377867view0turn285644view0

## What This Changes

Define secure at-rest storage and migration behavior for rotating GitHub OAuth credentials currently persisted in per-agent auth profiles.

## Best Possible Solution

Design one generic rotating-credential storage contract for all OAuth providers, preferably backed by OS credential storage or another explicit key-custody abstraction, with atomic refresh writes, a tested doctor migration, backup/recovery behavior, and a documented compatibility fallback; do not add GitHub-specific encryption or an unconditional new master-key environment variable.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw extend its security boundary to encrypt rotating OAuth credentials at rest, and if so which cross-platform key-custody and compatibility model should become the canonical auth-profile contract?

Rationale: Current documentation intentionally treats OAuth credentials as plaintext residuals protected by file permissions and OS isolation; changing that boundary affects every OAuth provider, upgrades, headless deployments, recovery, and runtime token rotation.

Likely owner: joshavant

Owner reason: Recent SecretRef hardening work most directly defines the current credential-storage boundary that this decision would extend.

Owner confidence: high

Options:

- **Generic secure credential store (recommended):** Create a provider-neutral rotating-credential store with OS-backed or explicitly configured key custody plus doctor migration and compatibility tests.
- **Harden existing plaintext boundary:** Retain plaintext auth profiles but strengthen permission enforcement, diagnostics, documentation, and threat-model guidance.
- **Require external credential proxy:** Move rotating OAuth custody out of OpenClaw and require a documented external credential service for hardened deployments.

## Reproduction Assessment

Partially yes: current source documentation establishes that GitHub device authentication persists a token and that rotating OAuth credentials remain plaintext in per-agent auth profiles. The claimed shared SQLite path, named files, and path-traversal exploit were not reproduced.

## Solution Assessment

No. Provider-specific envelope encryption using `OPENCLAW_MASTER_KEY` would create a parallel credential path and another secret-management surface; the maintainable fix is a generic rotating-credential contract with explicit key custody, migration, and recovery semantics.

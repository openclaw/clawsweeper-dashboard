## Summary

Keep open: this is a useful linked implementation, but the current head still disables the app-level notification-serving preference after hosted-relay disclosure for denied/checking/unknown system status, so enabling notifications in iOS Settings can leave OpenClaw delivery suppressed.

## What This Changes

The PR moves iOS notification controls into Settings > Privacy as a toggle, adds a UserDefaults-backed notification-serving preference, and adds APNs registration acknowledgement/unregister handling between the iOS app and gateway.

## Best Possible Solution

Preserve the user's enable intent through relay disclosure and app-settings recovery, keep notification delivery gated by system permission plus an explicit off toggle, and prove fresh-install and upgrade APNs state before merge.

## Reproduction Assessment

Yes for the PR defect from source inspection. In a hosted-relay build with notification status denied, checking, or unknown, accepting the disclosure writes the app-level preference off before opening iOS Settings, while registration later requires that preference on.

## Solution Assessment

No. Moving Notifications into Privacy is a plausible product direction, but this implementation must preserve the user's enable intent through disclosure/settings and prove the new APNs registration state behavior.

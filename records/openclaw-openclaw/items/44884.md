- **[P1] Wire the new gateway config into schema:** `src/config/types.gateway.ts:443-450`
  - body: The PR adds operator-facing config keys here, but the strict zod schema still does not accept `gateway.ipAllowlist`, `gateway.ipBlocklist`, `gateway.requestRateLimit`, or `gateway.tls.terminatedUpstream`. Users following the PR description would have config rejected before these runtime paths can work, so the schema/help/docs/tests need to be updated with the new surface.
  - confidence: 0.93
- **[P1] Keep request throttling behind an approved default:** `src/gateway/server.impl.ts:531`
  - body: This creates a request limiter on every Gateway start, and the limiter defaults to 120 requests/minute for all non-loopback HTTP and WebSocket traffic when no config is set. That changes existing public Gateway behavior from opt-in auth throttling to default request throttling, so it needs an explicit maintainer default decision, upgrade proof, and ideally an opt-in/default-compatible path.
  - confidence: 0.9
- **[P1] Keep HSTS opt-in unless the default is approved:** `src/gateway/server-runtime-config.ts:201-202`
  - body: Current main treats HSTS as an explicit `gateway.http.securityHeaders.strictTransportSecurity` setting, but this branch emits `max-age=31536000` for any TLS-enabled gateway. Existing self-signed, staging, or reverse-proxy deployments can inherit a browser-persistent header unexpectedly, so this default needs maintainer approval and docs/upgrade proof before merge.
  - confidence: 0.88
- **[P1] Define audit-log retention before enabling it by default:** `src/gateway/server.impl.ts:534`
  - body: The server now creates the auth audit logger unconditionally, which adds persistent JSONL logging of security events under the OpenClaw state directory without a user-visible enable/disable, retention, or privacy policy. For a security feature that can record client IPs and users, make the storage behavior explicit before turning it on for existing deployments.
  - confidence: 0.86
- **[P2] Pass the audit logger into auth checks:** `src/gateway/auth.ts:85-94`
  - body: The PR adds `auth_success` and `auth_failure` logging inside `authorizeGatewayConnect`, but the HTTP and WebSocket auth call chains inspected here still pass only rate limiter/proxy inputs and never thread this new logger through. As a result, the advertised audit trail records IP blocks/rate limits but misses normal credential outcomes.
  - confidence: 0.84

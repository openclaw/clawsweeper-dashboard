- **[P1] Wire the new gateway config into validation:** `src/config/types.gateway.ts:443-450`
  - body: The PR exposes `ipAllowlist`, `ipBlocklist`, `requestRateLimit`, and `tls.terminatedUpstream` in the config types and PR body, but the PR head's zod schema still lacks those fields. Because `gateway` is strict and `tls` does not declare `terminatedUpstream`, users cannot reliably set the new controls that the hardening depends on.
  - confidence: 0.92
- **[P1] Keep request throttling behind an approved default:** `src/gateway/server.impl.ts:531`
  - body: `createRequestRateLimiter()` is created unconditionally, so existing Gateway clients can start receiving `429` responses after upgrade even when operators never opted into request-level throttling. This needs an explicit maintainer-approved default or an opt-in/upgrade path with proof for existing deployments.
  - confidence: 0.88
- **[P1] Keep HSTS opt-in unless the default is approved:** `src/gateway/server-runtime-config.ts:201-202`
  - body: This now sends `Strict-Transport-Security: max-age=31536000` for every TLS-enabled Gateway that has no explicit header configured. Existing staging or reverse-proxy deployments that intentionally manage HSTS at the edge can get long-lived browser behavior they did not choose, so the default needs maintainer approval and upgrade proof before merge.
  - confidence: 0.86
- **[P1] Define audit-log retention before enabling it by default:** `src/gateway/server.impl.ts:534`
  - body: Gateway startup now always creates the auth audit logger, and the logger persists client IPs plus auth outcome metadata to a JSONL file under the state logs path. Before this is default-on, the PR needs a clear opt-in/default policy, retention/redaction story, and user-facing documentation for that sensitive operational data.
  - confidence: 0.84
- **[P2] Thread the audit logger into auth verification callers:** `src/gateway/auth.ts:86-94`
  - body: The new `auditLogger` parameter is only used inside `authorizeGatewayConnect`, but the PR head does not pass it from the HTTP or WebSocket auth verification callers. As written, the advertised `auth_success` and `auth_failure` audit events still do not fire for normal Gateway auth paths.
  - confidence: 0.82

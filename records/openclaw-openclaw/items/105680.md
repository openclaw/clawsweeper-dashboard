## What This Changes

Prevent separate OpenClaw processes from racing while creating the shared LanceDB memory table.

## Best Possible Solution

Use LanceDB's native atomic create mode with `existOk`, keep the fix inside the memory-lancedb plugin, make schema-seed cleanup idempotent, and add a real two-process regression test without introducing a filesystem-lock dependency.

## Repair Work Prompt

Fix the concurrent initialization race in the memory-lancedb plugin. Replace the `tableNames()` check-then-create sequence with `@lancedb/lancedb` 0.30.0's atomic create mode using `existOk`, ensure both racing processes receive a usable table, and make deletion of the temporary `__schema__` row idempotent. Add focused two-process regression coverage sharing one temporary local `dbPath` and verify each process can perform a table operation after initialization. Preserve `storageOptions` and object-store behavior; do not add `proper-lockfile`, any new dependency, config/default surface, fallback stack, or compatibility shim. Do not edit `CHANGELOG.md`. Keep https://github.com/openclaw/openclaw/issues/58139 and https://github.com/openclaw/openclaw/pull/80683 out of scope because they address Windows bind-mount visibility rather than this race.

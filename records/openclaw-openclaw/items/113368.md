## Summary

Keep this PR open, but do not merge it as written: each isolated-polling spool write acknowledges its update independently, so a later update can persist a higher offset before an earlier concurrent spool write succeeds. If that earlier write then fails, Telegram will not redeliver it and the original message-loss class remains. Likely related people: marin19 is connected through the proposed implementation, but current-main feature ownership still needs a local history check (low confidence).

## What This Changes

The PR changes isolated Telegram polling so an update offset is persisted after the update is written to the durable ingress spool, with ordering and failure-path tests plus diagnostic logs.

## System Context

Telegram isolated polling forwards received updates from a worker to the parent session, which writes each update to a durable spool before the normal ingress drain dispatches it. The persisted Telegram offset tells subsequent polls which updates have been acknowledged, so it must never advance past an update that has not durably reached the spool.

## Best Possible Solution

Serialize isolated-ingress acknowledgement, or maintain a contiguous durable-update frontier, so the persisted offset advances only through the highest consecutive update ID whose spool write has completed successfully; prove it with an out-of-order multi-update regression and a redacted real isolated-polling run.

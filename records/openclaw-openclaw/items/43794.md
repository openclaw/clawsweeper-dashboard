## Summary

Keep open: current main and v2026.6.11 still support plaintext credential storage, with SecretRefs as an opt-in mitigation rather than native encrypted-at-rest credential storage.

## What This Changes

Request native encrypted-at-rest storage for sensitive OpenClaw credentials, using keychain or master-password decryption while preserving upgrade compatibility.

## Best Possible Solution

Adopt a maintainer/security-approved credential-at-rest design covering openclaw.json, backups, auth-profile SQLite storage, SecretRefs, doctor migration, recovery, and rotation.

Options:

- **Design native encrypted-at-rest storage (recommended):** Define a keychain or passphrase-backed storage model with doctor migration, recovery behavior, rotation guidance, and tests for config plus auth-profile SQLite storage.
- **Keep SecretRefs as the supported mitigation:** Explicitly decide that transparent native encryption is out of scope for now and narrow this issue to docs, audit guidance, and SecretRef migration coverage.
- **Land partial hardening first:** Use a smaller auth-store or resolver-backed step while keeping this issue open for config, backups, key management, and migration coverage.

Yes, as a source-level missing-capability check. Current source and docs show plaintext storage remains supported, SecretRefs are opt-in, and auth-profile payloads are persisted as JSON rather than encrypted envelopes.

## Solution Assessment

Unclear. The security goal is valid, but maintainers still need to choose the key-management model, migration path, recovery behavior, startup behavior, and rotation guarantees before implementation.

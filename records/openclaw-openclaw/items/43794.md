## Summary

Keep open: current main and the latest release still support plaintext credential storage, with SecretRefs as an opt-in mitigation rather than native encrypted-at-rest storage; the remaining work needs maintainer security/product design.

## What This Changes

The issue requests encrypted-at-rest or system-keychain handling for sensitive OpenClaw credentials stored in config and auth-profile files.

## Best Possible Solution

Land a maintainer/security-approved credential-at-rest design that covers openclaw.json, config backups, active SQLite auth-profile storage, doctor migration, key management, recovery, and rotation while keeping SecretRefs as a supported mitigation.

Question: Which credential-at-rest design should OpenClaw support for core config and auth-profile storage: native OS keychain, master/passphrase sealing, SecretRef-only migration, or a staged combination?

Rationale: The implementation choice defines the security boundary, unattended-startup behavior, recovery/rotation model, and upgrade path for existing plaintext credentials, so automation should not choose it.

Likely owner: steipete

Owner reason: Best available owner signal from merged SecretRef review history plus auth-profile persistence refactor history; the final choice still needs maintainer/security consensus.

Owner confidence: medium

Options:

- **Staged core design (recommended):** Define a staged design that preserves SecretRefs, adds explicit encrypted-at-rest storage for core-owned credentials, and includes doctor migration plus recovery/rotation docs.
- **SecretRef-only policy:** Declare SecretRefs plus OS isolation as the supported at-rest mitigation and close native encryption as out of scope after updating the threat-model and docs language.
- **Passphrase sealing first:** Adopt optional passphrase sealing as an interim hardening path, accepting operator-action and unattended-startup tradeoffs.

Yes, as a source-level missing-capability check. Current source and docs show plaintext storage remains supported, SecretRefs are opt-in, and active auth-profile payloads are stored as JSON rather than encrypted envelopes.

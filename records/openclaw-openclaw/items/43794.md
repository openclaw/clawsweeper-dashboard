## Summary

Keep open: current main and v2026.6.11 still rely on plaintext-compatible config/auth storage plus opt-in SecretRefs, so the requested encrypted-at-rest credential model remains unresolved and needs maintainer security/product design.

## What This Changes

The issue requests encrypted-at-rest storage for tokens and API keys in OpenClaw config and auth credential stores, preferably via system keychain or master-password backed decryption with migration compatibility.

## Best Possible Solution

Adopt a maintainer/security-approved credential-at-rest design that covers openclaw.json, config backups, SQLite auth-profile storage, doctor migration, key management, recovery, and rotation while keeping SecretRefs as a supported mitigation.

Rationale: The implementation boundary is clear, but the permanent model changes key custody, unattended startup, migration, recovery, and auth-provider compatibility, so automation should not choose it without maintainer/security intent.

Options:

- **Design native encrypted credential storage (recommended):** Define a supported keychain or passphrase-backed storage model with doctor migration, recovery behavior, rotation guidance, and tests for config plus SQLite auth profiles.
- **Keep SecretRefs as the mitigation:** Explicitly decide that transparent encrypted-at-rest storage is out of scope and narrow this issue to docs, audit, and migration guidance.
- **Use partial sealing as a stepping stone:** Keep the open auth-store sealing work as an experimental path while leaving this issue open for openclaw.json, backups, SQLite, and migration coverage.

Yes, as a source-level missing-capability check: current source and docs show plaintext storage remains supported, SecretRefs are opt-in, and active auth-profile payloads are stored as JSON in SQLite rather than encrypted envelopes.

Unclear. The requested security goal is valid, but maintainers still need to choose the key-management model, migration path, recovery behavior, service-startup behavior, and rotation guarantees before implementation.

## Summary

Keep open: current main and v2026.6.11 still document plaintext credential storage as supported and SecretRefs as opt-in mitigation, while the requested encrypted-at-rest/keychain design remains unresolved.

## What This Changes

The issue requests encrypted storage for tokens and API keys in OpenClaw config/auth files, using a system keychain or master password with backward-compatible migration.

## Best Possible Solution

Land a maintainer/security-approved credential-at-rest design that covers openclaw.json, config backups, the active SQLite auth-profile store, doctor migration, key management, recovery, and rotation while keeping SecretRefs as a supported mitigation.

## Reproduction Assessment

Yes, as a source-level missing-capability check. Current source and docs show plaintext storage remains supported, SecretRefs are opt-in, and active auth-profile payloads are stored as JSON in SQLite rather than encrypted envelopes.

## Solution Assessment

Unclear. The request targets a real security gap, but maintainers still need to choose the key-management model, migration path, recovery behavior, service-startup behavior, and rotation guarantees before implementation.

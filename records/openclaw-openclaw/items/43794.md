## Summary

Keep open: current main and v2026.6.11 still keep plaintext-compatible credential storage, with SecretRefs as an opt-in mitigation rather than native encrypted-at-rest config/auth storage.

## What This Changes

The issue requests encrypted-at-rest or keychain-backed protection for sensitive credentials stored in OpenClaw config and auth-profile state.

## Best Possible Solution

Adopt a maintainer/security-approved credential-at-rest design covering openclaw.json, auth-profile SQLite storage, backups, SecretRefs, doctor migration, recovery, and rotation.

Question: Which credential-at-rest model should OpenClaw support for openclaw.json, auth-profile SQLite storage, generated residues, and backups?

Rationale: The code path is source-reproducible, but the permanent fix changes key custody, unattended startup, recovery, rotation, migrations, and auth/provider compatibility, so automation should not choose it without maintainer/security intent.

Likely owner: steipete

Owner reason: He has the strongest feature-history signal across auth-profile persistence and config write behavior, which are the central migration surfaces.

Owner confidence: high

Options:

- **Design native encrypted-at-rest storage (recommended):** Define a keychain or passphrase-backed storage model with doctor migration, recovery behavior, rotation guidance, and tests for config plus auth-profile storage.
- **Keep SecretRefs as the supported mitigation:** Decide that transparent native encryption is out of scope for now and narrow this issue to docs, audit guidance, and SecretRef migration coverage.
- **Land partial hardening first:** Use a smaller auth-store or resolver-backed step while explicitly keeping the broader credential-at-rest tracker open for key management and migration coverage.

## Reproduction Assessment

Yes. Current source and docs show plaintext credential storage remains supported, SecretRefs are opt-in, and auth-profile secrets are stored as JSON payloads rather than encrypted envelopes.

## Solution Assessment

Unclear. The security goal is valid, but the best implementation needs maintainer choice on key custody, migration, recovery, unattended startup, and rotation before a code path is safe to implement.

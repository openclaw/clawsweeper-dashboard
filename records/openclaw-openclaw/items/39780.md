## Summary

Keep open: current main still renders the insecure-context recommendation as manual config text, while the existing before/after diff and Apply controls are scoped to user-edited Config drafts rather than recommendation cards. The remaining work needs a maintainer product/security decision because it would let the browser UI persist auth and hardening config changes.

## What This Changes

Request that Control UI config upgrade and security recommendation cards provide an Apply flow with before/after diff, accept/dismiss, and confirmation instead of sending users to manual config edits.

## Best Possible Solution

Define a reusable, allowlisted Control UI recommendation-action model over existing config RPCs with exact before/after diff, explicit accept/dismiss, confirmation, redaction, restart/audit handling, and security-sensitive copy.

Rationale: The requested flow persists security and auth-related config from a browser UI, so automation should not choose the policy boundary or which hardening suggestions are safe to mutate.

Owner confidence: high

Options:

- **Define Allowlisted Recommendation Actions (recommended):** Create a generic allowlisted UI action model that reuses config.patch/config.apply validation and shows exact diff, confirmation, dismissal, restart/audit, and redaction behavior for approved recommendations.
- **Keep Risky Auth Changes Manual:** Leave auth/security downgrade or recovery suggestions as docs/manual guidance while allowing only low-risk non-auth recommendations to become one-click actions.
- **Split By Recommendation Class:** Implement separate policies for hardening, compatibility, and recovery recommendations so secure-by-default changes can be one-click while downgrade paths require stronger consent.

## Solution Assessment

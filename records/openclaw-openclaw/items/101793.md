## Label Justifications

- `P1`: A real channel workflow can silently drop a user confirmation prompt and let the agent proceed as if the user saw it.
- `impact:message-loss`: The core symptom is assistant text recorded in the transcript but not delivered to the Signal client.
- `impact:session-state`: The agent/session state can diverge from what the user actually saw, causing later replies to be interpreted against missing context.
- `impact:data-loss`: The report describes a financial record being written with unconfirmed fields because the confirmation message was silently absent from the user’s channel.

## Summary

Keep open. The report has concrete transcript-versus-Signal evidence, and current main’s #76477 guard covers terminal `toolUse` turns that never produce a post-tool answer, but it does not settle this case where pre-tool text is recorded in the transcript while only a later `stop` turn reaches Signal.

## What This Changes

Ensure Signal channel delivery does not silently lose assistant text that precedes a same-turn tool call, or explicitly marks that text as undelivered to the agent.

## Best Possible Solution

Define one channel-agnostic contract: text recorded as user-visible must either be durably delivered before later user interpretation, or be represented to the agent as suppressed/undelivered so later replies cannot be treated as confirmations.

Question: For `stopReason:"toolUse"` assistant text that precedes a tool call, should OpenClaw deliver it automatically to messaging channels, or suppress it while making the suppression explicit to the agent/session state?

Rationale: The reported bug is real delivery-state drift, but related open work asks to suppress intermediate tool text to avoid channel leaks; automation should not pick the permanent visibility policy without maintainer intent.

Likely owner: Vincent Koc

Owner reason: The current incomplete-turn and payload-selection code most directly connected to the policy is in recent commits by this author.

Owner confidence: medium

Options:

- **Surface suppression to the agent (recommended):** Keep intermediate pre-tool text out of channels unless it is intentionally deliverable, but annotate/session-signal the suppression so the agent cannot assume the user saw it.
- **Deliver pre-tool text before tools:** Flush pre-tool text to the channel before executing the tool, accepting the risk that some intermediate narration becomes visible.
- **Require explicit send semantics:** Move messaging-channel visibility toward final text or message-tool sends only, with docs and regression coverage for transcript/client consistency.

## Reproduction Assessment

Yes at source/report level, but not as a live Signal run. The issue body provides transcript/client evidence, and current code shows the related delivery and terminal-turn paths without a regression that guarantees pre-tool text delivery or agent-visible suppression.

## Solution Assessment

Unclear until maintainers choose the visibility contract. The best fix is not a Signal-only patch; it should align payload construction, outbound delivery outcomes, and agent-visible session state for pre-tool text across channels.

## Summary

Keep open. Current main and the latest release still expose mutable, priority-ordered plugin hooks with coarse prompt/conversation gates only, so the requested hook provenance, mutation audit, and per-hook permission model remains real security-boundary design work.

## What This Changes

The issue requests tamper-evident hook-chain integrity, mutation audit logging, and per-hook permission controls for plugin hooks.

## Best Possible Solution

Define host-owned hook provenance and redacted mutation-audit semantics, distinguish in-process plugins from any future isolated-plugin IPC boundary, then add a compatible per-hook permission policy with docs and focused runtime/config tests.

Rationale: The source gap is clear, but implementing checksums, audit logs, or per-hook allowlists would encode a plugin trust boundary and compatibility policy that current code and docs do not settle.

Owner confidence: high

Options:

- **Define audit and trust boundary first (recommended):** Document the threat model, redaction and retention rules, and compatibility plan before changing hook runner behavior or config.
- **Ship redacted audit first:** Add host-owned audit events for modifying hooks while deferring checksum enforcement and per-hook allowlists.
- **Defer to isolated plugin IPC:** Keep the checksum portion blocked on process-isolation work so integrity checks are designed around a real boundary.

## Reproduction Assessment

Yes, at source level: current main shows mutable, ordered hook execution and only coarse prompt/conversation gates, with no hook-chain integrity, per-handler mutation audit, or per-hook allowlist. This is a reproducible security capability gap, not a broken existing behavior contract.

## Solution Assessment

Unclear as proposed: the security goal fits current priorities, but cryptographic checksums alone are not the best proven fix until maintainers choose the hook trust boundary, audit semantics, compatibility plan, and relationship to isolated plugin IPC.

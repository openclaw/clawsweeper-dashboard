## Summary

Keep open. Current main and the latest release still expose mutable sequential plugin hooks without hook-chain integrity, per-handler mutation audit semantics, or a per-hook permission allowlist; related open items cover sandboxing, security profiles, outbound verification, or one permission slice without replacing this broader security-design request.

## What This Changes

Request host-owned integrity verification, audit logging, and permission policy for plugin hook chains that can mutate messages, tool results, and agent context.

## Best Possible Solution

Define a maintainer-approved host-owned hook provenance and redacted mutation-audit model, distinguish in-process native plugins from any isolated-plugin IPC boundary, then add a compatible per-hook permission policy with docs and focused runtime/config tests.

## Reproduction Assessment

Yes, at source level: current main shows ordered mutable hook execution and no hook-chain integrity, per-handler mutation audit, or per-hook allowlist state. This is a reproducible security capability gap rather than broken behavior under an existing contract.

## Solution Assessment

Unclear as proposed: the security goal is valid, but cryptographic checksums alone are not established as the best fix until maintainers choose the hook trust boundary, audit semantics, compatibility plan, and relationship to isolated plugin IPC.

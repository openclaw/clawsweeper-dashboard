- `impact:security`: The issue concerns plugin trust boundaries, tamper detection, hook permission gating, and auditability of security-relevant mutations.

## Summary

Keep open. Current main and v2026.6.11 still expose mutable, sequential plugin hook paths with coarse prompt/conversation gates only; hook-chain provenance, mutation audit, and per-hook permission policy remain security-sensitive product design work.

## What This Changes

The issue requests hook-chain integrity, modification auditing, and per-hook permissions so plugin hooks cannot silently tamper with messages or agent context.

## Best Possible Solution

Define host-owned hook provenance and redacted mutation-audit semantics, distinguish in-process from isolated-plugin trust boundaries, then add a compatible per-hook permission policy with docs and focused runtime/config tests.

## Reproduction Assessment

Yes, at source level: current main shows ordered mutable hook execution and no hook-chain integrity, per-handler mutation audit, or per-hook allowlist state. This is a reproducible security capability gap, not a broken existing behavior contract.

## Solution Assessment

Unclear as proposed: the security goal is valid, but cryptographic checksums alone are not established as the best fix until maintainers choose the hook trust boundary, audit semantics, compatibility plan, and relationship to isolated plugin IPC.

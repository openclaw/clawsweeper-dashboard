## Summary

Keep open. Current main and the latest release still have mutable sequential plugin hooks, coarse hook policy only, and no hook-chain integrity/audit contract; this is security-sensitive plugin-runtime design work rather than a narrow cleanup close.

## What This Changes

Request to add hook-chain integrity verification, mutation audit logging, and per-hook permission policy for plugin hooks.

## Best Possible Solution

Define host-owned hook provenance and redacted mutation-audit semantics, distinguish in-process from isolated-plugin trust boundaries, then add a compatible per-hook permission policy with docs and focused tests.

## Reproduction Assessment

Yes, at source level: current main still shows ordered mutable hook execution with no hook-chain integrity, per-handler mutation audit, or per-hook allowlist state. This is a reproducible security capability gap, not broken behavior under an existing contract.

## Solution Assessment

Unclear as proposed: the security goal is valid, but cryptographic checksums alone are not established as the best fix until maintainers choose the hook trust boundary, audit semantics, and compatibility plan.

## Summary

Keep open. Current main and the latest release still expose mutable, priority-ordered plugin hooks with coarse conversation/prompt gates only, so hook-chain provenance, mutation audit, integrity semantics, and per-hook permissions remain unresolved security-boundary design work.

## What This Changes

Request adds hook-chain integrity verification, per-handler mutation audit logging, and per-hook permission policy for mutable plugin hooks.

## Best Possible Solution

Define host-owned hook provenance and redacted mutation-audit semantics, distinguish in-process plugins from any future isolated-plugin IPC boundary, then add a compatible per-hook permission policy with docs and focused runtime/config tests.

Question: What hook-chain security model should OpenClaw support for mutable plugin hooks: host-owned audit/provenance for today’s in-process plugins, integrity checks across a future isolated-plugin IPC boundary, or per-hook permission gating first?

Rationale: The source gap is clear, but implementing checksums, audit logs, or per-hook allowlists would encode plugin trust-boundary and compatibility policy that current code and docs do not settle.

Likely owner: vincentkoc

Owner reason: vincentkoc has the strongest recent history across the hook runner, hook types, and registry surfaces needed to carry the decision into implementation.

Owner confidence: high

Options:

- **Define audit and trust boundary first (recommended):** Document the threat model, redaction and retention rules, and compatibility plan before changing hook runner behavior or config.
- **Ship redacted audit first:** Add host-owned audit events for modifying hooks while deferring checksum enforcement and per-hook allowlists.
- **Defer checksum to isolated plugin IPC:** Keep checksum enforcement blocked on process-isolation work and limit near-term work to permissions or audit surfaces that fit in-process plugins.

## Reproduction Assessment

Yes, at source level: current main shows mutable, ordered hook execution and only coarse prompt/conversation gates, with no hook-chain integrity, per-handler mutation audit, or per-hook allowlist. This is a reproducible security capability gap, not a broken existing behavior contract.

## Solution Assessment

Unclear as proposed: the security goal fits current priorities, but cryptographic checksums alone are not the best proven fix until maintainers choose the hook trust boundary, audit semantics, compatibility plan, and relationship to isolated plugin IPC.

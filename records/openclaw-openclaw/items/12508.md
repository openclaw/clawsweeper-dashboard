## Summary

Keep open. Current main and v2026.6.11 still expose mutable, priority-ordered plugin hook paths with only coarse prompt/conversation gates, so the requested hook provenance, mutation audit, and per-hook permission model remains security-sensitive product design work.

## What This Changes

The issue requests hook-chain provenance, tamper detection, audit logging, and per-hook permissions for OpenClaw plugin hooks.

## Best Possible Solution

Define host-owned hook provenance and redacted mutation-audit semantics, distinguish in-process from isolated-plugin trust boundaries, then add a compatible per-hook permission policy with docs and focused runtime/config tests.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 show mutable, ordered hook execution and no hook-chain integrity, per-handler mutation audit, or per-hook allowlist state. This is a reproducible security capability gap, not a broken existing behavior contract.

## Solution Assessment

Unclear as proposed: the security goal fits current priorities, but cryptographic checksums alone are not established as the best fix until maintainers choose the hook trust boundary, audit semantics, compatibility plan, and relationship to isolated plugin IPC.

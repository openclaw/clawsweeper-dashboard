## Label Justifications

- `P2`: This is meaningful plugin-runtime security architecture work, but it is a feature/design request rather than an urgent outage, active exploit, or confirmed regression.
- `impact:security`: The issue concerns plugin trust boundaries, tamper detection, hook permission gating, and auditability of security-relevant mutations.
- `impact:session-state`: The affected hooks can rewrite outbound content, persisted messages, and agent/tool context seen by later handlers or storage.

## Summary

Keep open. Current main and the latest stable release still expose mutable, priority-ordered plugin hook paths with only coarse prompt/conversation gates, so hook provenance, mutation audit, and per-hook permission design remain unsolved core/plugin-runtime security work.

## What This Changes

Request to add hook-chain integrity checks, tamper detection, mutation audit logging, and fine-grained hook permissions for plugin hooks.

## Best Possible Solution

Define host-owned hook provenance and redacted mutation-audit semantics, distinguish in-process from isolated-plugin trust boundaries, then add a compatible per-hook permission policy with docs and focused runtime/config tests.

## Reproduction Assessment

Yes, at source level: current main shows mutable, ordered hook execution and no hook-chain integrity, per-handler mutation audit, or per-hook allowlist state. This is a reproducible security capability gap, not a broken existing behavior contract.

## Solution Assessment

Unclear as proposed: the security goal is valid, but cryptographic checksums alone are not established as the best fix until maintainers choose the hook trust boundary, audit semantics, compatibility plan, and relationship to isolated plugin IPC.

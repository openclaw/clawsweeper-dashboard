## Summary

Keep open. Current main and the latest release still expose mutable, priority-ordered plugin hooks with coarse prompt/conversation gates only; the requested hook provenance, mutation audit, integrity boundary, and per-hook permission model remain real security/product design work.

## What This Changes

The issue requests hook-chain integrity checks, mutation audit logging, and per-hook permission gating to detect or constrain message tampering by plugins.

## Best Possible Solution

Define host-owned hook provenance and redacted mutation-audit semantics, distinguish in-process plugins from any future isolated-plugin IPC boundary, then add a compatible per-hook permission policy with docs and focused runtime/config tests.

Question: What hook-chain security model should OpenClaw support for mutable plugin hooks: host-owned audit/provenance for current in-process plugins, integrity checks across a future isolated-plugin boundary, or per-hook permission gating first?

Rationale: The source gap is clear, but implementing checksums, audit logs, or per-hook allowlists would encode a plugin trust boundary, audit-retention policy, and compatibility contract that current code and docs do not settle.

Likely owner: vincentkoc

Owner reason: Vincent has the clearest current-main and recent-history connection to the hook runner, typed hook policy, and plugin config surfaces that would carry this decision into implementation.

Owner confidence: high

Options:

- **Define audit and trust boundary first (recommended):** Document the threat model, redaction and retention rules, protected boundary, and compatibility plan before changing hook runner behavior or config.
- **Ship redacted audit first:** Add host-owned audit events for modifying hooks while deferring checksum enforcement and per-hook allowlists.
- **Defer checksums to isolated plugins:** Keep checksum enforcement blocked on isolated-plugin IPC work so integrity checks are designed around a real boundary.

## Solution Assessment

Unclear as proposed: the security goal fits current priorities, but cryptographic checksums alone are not the best proven fix until maintainers choose the hook trust boundary, audit semantics, compatibility plan, and relationship to isolated plugin IPC.

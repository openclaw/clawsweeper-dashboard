## Summary

Keep open. Current main and v2026.6.11 still expose mutable sequential plugin hooks with coarse hook policy only, and the related open items cover narrower sandbox, profile, outbound-verification, or permission slices rather than replacing this broad hook-chain integrity design request.

## What This Changes

The issue requests tamper-evident hook-chain integrity, per-handler mutation auditing, and per-hook permission policy for plugin hooks that can modify messages or agent context.

## Best Possible Solution

Define host-owned hook provenance and redacted mutation-audit semantics, distinguish in-process from isolated-plugin trust boundaries, then add a compatible per-hook permission policy with docs and focused tests.

## Reproduction Assessment

Yes, at source level: current main shows ordered mutable hook execution and no hook-chain integrity, per-handler mutation audit, or per-hook allowlist state. This is a reproducible security capability gap rather than broken behavior under an existing contract.

## Solution Assessment

Unclear as proposed: the security goal is valid, but cryptographic checksums alone are not established as the best fix until maintainers choose the trust boundary, audit semantics, compatibility plan, and relationship to isolated plugin IPC.

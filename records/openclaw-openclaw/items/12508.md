## Summary

Keep open. Current main still permits trusted plugins to mutate hook payloads without host-owned provenance or per-handler audit records, while native plugins share the Gateway process boundary; the request therefore remains valid but requires an explicit security and product design decision. ([raw.githubusercontent.com](https://raw.githubusercontent.com/openclaw/openclaw/main/src/plugins/hooks.ts))

## What This Changes

Add hook-chain mutation provenance, tamper detection, audit records, and fine-grained authorization for plugin hook registration.

## Best Possible Solution

Define host-owned typed hook capabilities and redacted mutation provenance for all plugins, while reserving cryptographic integrity enforcement for an actual host-controlled process or privilege boundary and providing an explicit upgrade plan.

Question: What security guarantee should OpenClaw provide for mutable plugin hooks: audit-only provenance for trusted in-process plugins, enforced integrity for isolated plugins, or one permission model spanning both?

Rationale: In-process plugins share core authority, while isolation, audit retention, and hook authorization alter security and compatibility contracts that source inspection cannot choose safely.

Likely owner: steipete

Owner reason: The issue discussion already records this person retaining the item for plugin-runtime security design, and supplied history connects them to the central hook and policy surfaces.

Owner confidence: medium

Options:

- **Boundary-aware design (recommended):** Add typed permissions and redacted provenance generally, but enforce cryptographic integrity only across a host-controlled isolation boundary.
- **Audit and permissions only:** Add mutation audit records and fine-grained authorization without claiming tamper prevention for in-process plugins.
- **Defer until isolation:** Retain current behavior until plugin process isolation provides a meaningful enforcement boundary.

## Reproduction Assessment

Yes at the source level: current main clearly executes mutable hook paths without provenance records and exposes only coarse hook permissions. This establishes the capability gap, although the issue does not demonstrate a concrete exploit against current main.

## Solution Assessment

No. Per-stage checksums are not meaningful protection from native plugins sharing process authority; the narrowest maintainable solution must tie enforcement to a host-controlled boundary and separately define audit, redaction, permissions, and upgrade semantics.

## Label Justifications

- `P2`: This is meaningful plugin-runtime security architecture work, but it is a feature/design request rather than an urgent outage or regression.
- `impact:security`: The request concerns plugin trust boundaries, tamper detection, hook permission gating, and auditability of security-relevant mutations.
- `impact:session-state`: The affected hooks can rewrite outbound content, persisted transcript messages, and agent/tool context seen by later handlers or storage.

## Summary

Keep open. Current main and the latest release still expose mutable, sequential plugin hooks with coarse prompt/conversation gates only; related open items cover sandbox, profiles, outbound verification, or one permission slice without replacing this broader security design request.

## What This Changes

Request hook-chain integrity verification, mutation audit logging, and per-hook permission declarations for plugin hooks.

## Best Possible Solution

Define host-owned hook provenance and redacted mutation-audit semantics, distinguish in-process from isolated-plugin trust boundaries, then add a compatible per-hook permission policy with docs and focused tests.

## Reproduction Assessment

Yes, at source level: current main shows ordered mutable hook execution with no hook-chain integrity state, per-handler mutation audit, or per-hook allowlist. This is a reproducible security capability gap rather than broken behavior under an existing contract.

## Solution Assessment

Unclear as proposed: the security goal is valid, but cryptographic checksums alone are not established as the best fix until maintainers choose the hook trust boundary, audit semantics, compatibility plan, and relationship to isolated plugin IPC.

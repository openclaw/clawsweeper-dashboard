## Summary

Keep open: current main has narrow cron/tool-error hardening, but it still permits final assistant text to become cron output without a broad structured fail-closed finalization contract for failed, missing, or unverified tool work.

## What This Changes

The issue requests cron and unattended sessions to suppress or clearly fail instead of delivering fabricated or unsupported output after tool failures or missing data.

## Best Possible Solution

Define a core cron/unattended finalization policy that derives deliverability from structured run and tool state, preserves verified recovery, and suppresses or clearly fails unsupported success-looking assistant text before delivery.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What cron/unattended finalization contract should OpenClaw enforce when failed, missing, or unverified tool work is followed by success-looking final assistant text?

Rationale: The current code intentionally allows some final assistant text to recover warning/error paths, and changing that default affects security posture, operator trust, and compatibility for existing cron jobs.

Likely owner: steipete

Owner reason: This is the strongest routing candidate because of recent adjacent agent-runtime hardening and the related #68051 plugin-scope decision.

Owner confidence: high

Options:

- **Fail closed on unrecovered structured failures (recommended):** Treat unattended runs with failed or missing required tool state as non-deliverable unless a later structured success proves recovery, while preserving verified recovery output.
- **Add opt-in strict mode first:** Keep existing delivery behavior by default and introduce a documented strict cron policy so maintainers can measure over-suppression before changing defaults.
- **Keep generic claim checks in plugins only:** Limit core to narrow fatal signals and leave broader success-claim verification to ClawHub plugins, accepting that this issue remains only partially addressed in cron core.

## Reproduction Assessment

Yes at source level: current source and tests still allow final assistant visible text to become cron output after some warning/error paths when no narrow fatal signal is present; no live model run was performed in this read-only review.

## Solution Assessment

No complete fix is present; current targeted denial and warning handling is useful but the best fix needs a structured finalization contract rather than marker-word filters or isolated fatal-denial handling.

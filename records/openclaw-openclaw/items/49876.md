## Label Justifications

- `impact:session-state`: The delivered transcript/output can drift from the actual tool ledger and run state.
- `impact:security`: Users may act on fabricated operational results or destructive instructions after failed tool work.

## Summary

Keep open: current main still allows non-fatal failed or missing tool work to be followed by final assistant text that can become cron delivery output, so the unattended trust boundary remains unresolved even though broad claim verification was routed out of core.

## What This Changes

The issue asks cron and isolated sessions to fail closed instead of delivering final assistant text when required tool work fails, is missing, or cannot be verified.

## Best Possible Solution

Define a narrow core cron fail-closed invariant for unrecovered tool failures or missing required tool evidence before delivery, while leaving broad natural-language claim verification to plugin or ClawHub scope unless maintainers choose otherwise.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What fail-closed contract should unattended cron delivery use when a run has unrecovered tool errors, missing required tool calls, or unverifiable final output?

Rationale: Current source has diagnostic and fatal-structured-error handling, but it intentionally permits some recovered/non-terminal warnings and final assistant text; maintainers must choose the default delivery semantics and the boundary between core cron safety and plugin claim-verification policy.

Likely owner: steipete

Owner reason: steipete has recent cron delivery history and made the related product-boundary decision on issue 68051.

Owner confidence: high

Options:

- **Narrow core cron fail-closed invariant (recommended):** Suppress normal cron delivery and record or alert failure when known tool errors or required tool evidence remain unrecovered, without adding broad regex-based claim verification to core.
- **Plugin-only claim verification boundary:** Keep core limited to structured fatal signals and route all unsupported success-claim checking to ClawHub/plugin implementations.
- **Defer to native recovery work:** Wait for the broader native tool-failure recovery design and document the current unattended cron risk meanwhile.

## Reproduction Assessment

Yes at source level, not live: failed or warning payloads plus final assistant-visible text can become non-fatal deliverable output through cron outcome resolution and delivery dispatch.

## Solution Assessment

Unclear pending maintainer policy: a narrow cron fail-closed gate is likely the best core fix, while broad success-claim verification should stay plugin/ClawHub unless maintainers reverse that boundary.

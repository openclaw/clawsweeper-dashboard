## Label Justifications

- `P1`: Unattended cron jobs can deliver plausible false operational results after tool failure, breaking a real user automation workflow without a crash.
- `impact:session-state`: The issue is about cron run state and tool-result evidence diverging from the assistant's delivered final state.
- `impact:security`: Fabricated success output after failed tools can cause operators to trust and act on false automation data in unattended workflows.

## Summary

Keep open: current main has targeted cron/tool-error hardening, but cron can still treat ordinary failed or missing tool work followed by final assistant text as successful scheduled output.

## What This Changes

The issue asks OpenClaw cron and isolated runs to fail closed or suppress delivery when tool failures or missing data would otherwise produce fabricated final output.

## Best Possible Solution

Define a narrow core cron/unattended delivery contract that blocks success-looking final text after failed or missing required tools unless structured recovery or delivery evidence exists, while leaving broad claim verification to ClawHub/plugins.

Question: What should OpenClaw do by default when an unattended cron run has failed or missing tool evidence but then produces success-looking final assistant text?

Rationale: The choice changes a security-sensitive delivery boundary and can alter existing cron announce behavior, so automation should not invent the default policy.

Likely owner: steipete

Owner confidence: high

Options:

- **Core fail-closed cron finalization (recommended):** Treat unsupported final assistant text after failed or missing required tool evidence as a cron failure unless structured recovery or verified delivery evidence exists.
- **Plugin-only claim verification:** Keep broad success-claim detection outside core and only add minimal core signals needed for plugins to enforce stricter delivery policy.
- **Keep current recovery semantics:** Preserve current final-text recovery behavior and document operator workarounds, accepting that unattended jobs may still deliver unsupported prose after some tool failures.

## Reproduction Assessment

Yes at source level: current main and tests show final assistant text can recover warning/error payloads and proceed to cron delivery unless narrow fatal metadata is present; no live model repro was run in this read-only pass.

## Solution Assessment

The best fix is not an autonomous broad regex verifier; it needs a maintainer-owned cron delivery policy that separates verified recovery from unsupported success prose.

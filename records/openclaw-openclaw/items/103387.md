## Summary

Keep this issue open: current main and v2026.6.11 intentionally expose caption health through a 50-line browser buffer and five-line status window, so the requested full-session retrieval remains missing. The feature fits the Google Meet plugin, but durable retention of sensitive meeting content requires an explicit product decision.

Likely related people: @steipete is the highest-confidence owner from the original plugin and caption-health history; @BsnizND and @vincentkoc are medium-confidence adjacent contributors.

## What This Changes

Add reliable full-session retrieval of Chrome-captured Google Meet captions instead of exposing only the current rolling transcript window.

## Best Possible Solution

Add a plugin-owned, bounded in-memory caption stream with monotonic cursor identity at the Chrome capture owner; expose incremental retrieval without new configuration initially, and treat SQLite-backed restart persistence as a separately approved retention feature.

Options:

- **Ephemeral Session Stream (recommended):** Keep complete bounded captions and cursor state in memory until the session or gateway ends.
- **Persistent SQLite Transcript:** Store captions across restarts with explicit retention, deletion, access, and migration behavior.
- **Keep Diagnostic Window:** Leave live caption status bounded and rely on existing post-meeting Google Meet transcript artifacts for durable records.

## Reproduction Assessment

Yes, at source level: current main deterministically removes caption entries beyond 50 and returns only the final five, matching the reported long-session failure mode. This is the implemented contract rather than a failing regression test.

## Solution Assessment

No, not exactly as proposed: poll-side merging can still leave gaps, and JSONL runtime persistence conflicts with repository state policy. Capture-owner cursor accumulation is the narrower and safer foundation.

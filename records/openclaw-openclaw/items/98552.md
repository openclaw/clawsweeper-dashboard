## Summary

Keep open: current main still leaves the macOS Settings/onboarding path token-only and tells users password auth is unsupported, while the runtime already accepts `gateway.remote.password`. The linked open draft https://github.com/openclaw/openclaw/pull/98553 is the active fix candidate, so this issue should remain open until that PR lands or is replaced.

## What This Changes

Expose secure macOS Settings and onboarding controls for `gateway.remote.password`, preserve untouched non-plaintext password config, and route password-auth failures to the password field.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/98553, or an equivalent narrow macOS fix, with password-field UI, explicit dirty tracking, non-plaintext preservation, and AppState/onboarding coverage.

## Reproduction Assessment

Yes from source inspection: current main has password-capable runtime code but the macOS Settings and onboarding UI only expose `remoteToken`, and password auth failures map to unsupported-auth copy. I did not run a live macOS UI repro in this read-only review.

## Solution Assessment

Yes, the requested direction is the right owner-boundary fix because `gateway.remote.password` already exists and is consumed by the runtime. The maintainable fix belongs in macOS AppState/UI/probe handling plus focused Swift tests, not in a new config schema or gateway auth mode.

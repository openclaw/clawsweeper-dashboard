## Summary

Keep open: current main still does not expose a supported way for Gateway CLI WebSocket clients to send custom HTTP headers. The mobile custom-header work has landed for iOS and Android, but the CLI/env/config request remains a credential-bearing gateway-auth surface that needs maintainer product and security direction.

## What This Changes

The issue requests custom HTTP header support for remote gateway CLI WebSocket connections through a repeatable CLI flag, an environment variable, and a config field.

## Best Possible Solution

Define one secret-safe Gateway WebSocket header contract at the gateway-client/call boundary, then expose only maintainer-approved CLI, env, or config sources with reserved-header rejection, redaction, docs, and focused tests for fresh and upgrade behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add custom Gateway CLI WebSocket headers, and which credential-safe input sources should become the supported public contract?

Rationale: The source gap is clear, but arbitrary headers affect reverse-proxy credentials, public CLI/config/env surface, and the gateway auth boundary, so automation should not choose the permanent product and security contract.

Likely owner: steipete

Owner reason: The recent mobile header implementations made the closest product/security decisions for the same authenticated-proxy deployment class.

Owner confidence: high

Options:

- **Approve a narrow secret-safe contract (recommended):** Add header forwarding through approved sources only, with sanitizer, redaction, SecretInput/env handling where applicable, docs, and tests for WebSocket upgrade behavior.
- **Limit support to per-invocation headers:** Support only a repeatable CLI flag first, avoiding durable config persistence while still allowing scripted operators to reach authenticated proxies.
- **Decline core CLI header support:** Keep tunnels, Tailscale, VPNs, or proxy bypasses as the supported remote-management path and document that header-authenticating proxies remain outside the CLI contract.

## Reproduction Assessment

Yes. Source inspection shows current main has no Gateway CLI header option, no header field in the call/client option chain, no WebSocket header merge, and no gateway.remote.headers schema.

## Solution Assessment

Unclear until maintainers choose the product and security contract. The proposed threading is plausible, but CLI/env/config precedence and credential handling should be approved before implementation.

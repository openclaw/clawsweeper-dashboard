## Summary

Keep open: current main and the latest release still lack a supported way to pass custom HTTP headers from shared Gateway CLI commands into the WebSocket upgrade. The request is source-reproducible and useful for authenticated reverse proxies, but it adds credential-bearing CLI/env/config surface that needs maintainer product and security review before implementation.

## What This Changes

The issue requests repeatable CLI, environment, and config support for custom HTTP headers on remote Gateway WebSocket connections.

## Best Possible Solution

Define one secret-safe Gateway WebSocket header contract in the gateway client/call path, then expose only approved CLI/env/config surfaces with redaction, SecretInput handling, docs, and focused tests.

## Reproduction Assessment

Yes, at source level: current main exposes no shared Gateway CLI --header option, no OPENCLAW_GATEWAY_HEADERS handling, no gateway.remote.headers config field, and no header forwarding into GatewayClient. I did not run a live Cloudflare Access repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product and security contract. The proposed owner boundary is plausible, but the exact flag/env/config precedence and secret-handling model should be approved before implementation.

## Summary

Keep open: current main and v2026.6.11 still do not expose a supported way for Gateway CLI WebSocket clients to send custom HTTP headers. The gap is source-proven, and the requested CLI/env/config surfaces carry credential and auth-boundary implications that need maintainer product/security direction before implementation.

## What This Changes

Request custom HTTP header support for remote Gateway CLI WebSocket connections through a repeatable CLI flag, environment variable, and/or `gateway.remote.headers` config.

## Best Possible Solution

Define one secret-safe Gateway WebSocket header contract at the Gateway client/call boundary, then expose only maintainer-approved CLI/env/config sources with redaction, SecretInput/env handling, docs, and focused tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add custom Gateway CLI WebSocket headers, and which credential-safe input sources and precedence should become the supported public contract?

Rationale: The source gap is clear, but arbitrary headers can carry reverse-proxy credentials and change the Gateway connection/auth boundary, so automation should not choose the permanent CLI/env/config contract.

Likely owner: steipete

Owner reason: Peter has the strongest combined history on Gateway WebSocket design, remote Gateway config, and the sibling mobile credential-header decision.

Owner confidence: high

Options:

- **Approve a narrow secret-safe contract (recommended):** Add header forwarding through maintainer-approved sources only, with SecretInput/env substitution, redaction, docs, and tests for fresh and upgrade behavior.
- **Limit support to explicit CLI headers:** Support only repeatable per-invocation headers for now, avoiding durable config/env persistence at the cost of CI and automation ergonomics.
- **Decline core header support:** Keep SSH, Tailscale, and local proxy workflows as the supported paths and document reverse-proxy header injection as outside OpenClaw CLI.

## Reproduction Assessment

Yes, source-level: current main exposes no shared Gateway CLI `--header` option, no headers field in the Gateway RPC/call/client option chain, no `wsOptions.headers` forwarding, and no `gateway.remote.headers` schema. I did not run a live Cloudflare Access repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product and security contract. The proposed threading is plausible and dependency-supported, but the exact CLI/env/config precedence and secret-handling model should be approved before implementation.

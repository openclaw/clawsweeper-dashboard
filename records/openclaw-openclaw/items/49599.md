## Summary

Keep open: current main and the latest release still lack custom-header input and forwarding for Gateway CLI WebSocket connections. The request is useful for secured remote Gateway operations, but it adds credential-bearing CLI/env/config surface that needs maintainer product and security review before implementation.

## What This Changes

The issue requests support for custom HTTP headers on remote Gateway CLI WebSocket connections via CLI flag, environment variable, and config.

## Best Possible Solution

Define one secret-safe Gateway WebSocket header contract at the Gateway client boundary, then expose only maintainer-approved CLI/env/config inputs with redaction, SecretInput/env handling, docs, and focused regression tests.

## Reproduction Assessment

Yes. Source inspection shows current main has no shared Gateway CLI `--header` option, no headers on `GatewayRpcOpts`, `CallGatewayBaseOptions`, or `GatewayClientOptions`, and no `gateway.remote.headers` config field, so a remote auth proxy cannot receive custom headers from this path.

## Solution Assessment

Unclear. The proposed owner boundary is plausible, but the exact flag/env/config precedence, secret-handling model, and persistence/redaction contract need maintainer product and security approval before implementation.

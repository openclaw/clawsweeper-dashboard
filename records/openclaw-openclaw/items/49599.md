## Summary

Keep open: current main and v2026.6.11 still do not expose a supported way for Gateway CLI WebSocket clients to send custom HTTP headers, and the exact implementation attempt is closed unmerged. The source gap is clear, but the requested CLI/env/config surfaces can carry proxy-auth credentials and need maintainer product/security direction before implementation.

## What This Changes

The issue requests custom HTTP headers for CLI WebSocket connections to remote gateways via CLI flags, environment variables, and/or `gateway.remote.headers` config.

## Best Possible Solution

Define one secret-safe Gateway WebSocket header contract in the gateway-client/call boundary, then expose only maintainer-approved CLI/env/config sources with redaction, SecretInput handling, docs, and focused tests.

Options:

- **Approve narrow secret-safe contract (recommended):** Add header forwarding through maintainer-approved sources with SecretInput/env substitution, redaction, docs, and fresh plus upgrade tests.
- **Limit to explicit CLI headers:** Support only repeatable per-invocation `--header` values for now, avoiding durable config/env persistence at the cost of CI and automation ergonomics.
- **Decline core header support:** Keep SSH, Tailscale, and local proxy workflows as the supported paths and document that reverse-proxy header injection stays outside the OpenClaw CLI.

Unclear until maintainers choose the product and security contract. The proposed threading is plausible and dependency-supported, but CLI/env/config precedence, SecretInput support, persistence, and redaction need approval before implementation.

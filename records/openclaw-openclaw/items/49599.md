- `impact:auth-provider`: The missing capability blocks authentication-header forwarding for Gateways behind identity-aware reverse proxies before Gateway auth can run.

## Summary

Keep open: current main still lacks a supported way for Gateway CLI WebSocket clients to attach custom HTTP headers, while related Android/iOS work only solved the sibling mobile surfaces. The remaining CLI/env/config contract is credential-bearing and needs maintainer product/security direction before implementation.

## What This Changes

Allow Gateway CLI WebSocket connections to pass custom HTTP headers through a repeatable CLI flag, environment variable, and/or `gateway.remote.headers` config.

## Best Possible Solution

Define one secret-safe Gateway WebSocket header contract at the gateway-client/call boundary, then expose only maintainer-approved CLI/env/config sources with redaction, SecretInput handling, docs, and focused tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add custom Gateway CLI WebSocket headers, and which credential-safe input sources and precedence should become the supported public contract?

Rationale: The source gap is clear, but arbitrary headers can carry reverse-proxy credentials and change the Gateway connection/auth boundary, so automation should not choose the permanent CLI/env/config contract.

Likely owner: steipete

Owner reason: Peter has the strongest combined history on Gateway WebSocket design and the sibling mobile credential-header decisions.

Owner confidence: high

Options:

- **Approve narrow secret-safe contract (recommended):** Add header forwarding only through maintainer-approved sources, with SecretInput/env substitution, redaction, reserved-header validation, docs, and tests for fresh and upgrade behavior.
- **Limit to explicit CLI headers:** Support only repeatable per-invocation headers for now, avoiding durable config/env persistence at the cost of automation ergonomics.
- **Decline core header support:** Keep SSH, Tailscale, and local proxy workflows as the supported paths and document that reverse-proxy header injection stays outside OpenClaw CLI.

## Reproduction Assessment

Yes, source-level: current main exposes no shared Gateway CLI `--header` option, no headers field in the Gateway RPC/call/client option chain, no `wsOptions.headers` forwarding, and no `gateway.remote.headers` schema. I did not run a live Cloudflare Access repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product and security contract. The proposed threading is plausible, but the exact CLI/env/config precedence, secret handling, validation, and docs need approval before implementation.

## Summary

Keep open: current main and v2026.6.11 still lack a custom-header path for Gateway CLI WebSocket connections, and the exact implementation PR is closed unmerged. The request is valid source-level work, but it adds credential-bearing CLI/env/config surface and should stay in maintainer product/security review rather than auto-close or auto-implement.

## What This Changes

Request support for custom HTTP headers on CLI WebSocket connections to remote gateways via a repeatable flag, environment variable, and optional remote-gateway config.

## Best Possible Solution

Define one secret-safe Gateway WebSocket header contract in packages/gateway-client and callGateway, then expose only approved CLI/env/config sources with redaction, SecretInput/env handling, docs, and focused tests.

## Reproduction Assessment

Yes, at source level: current main exposes no shared Gateway CLI --header option, no headers field in call/client options, no wsOptions header forwarding, and no gateway.remote.headers schema. I did not run a live Cloudflare Access repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product and security contract. The proposed threading is plausible, but the exact flag/env/config precedence and secret-handling model should be approved before implementation.

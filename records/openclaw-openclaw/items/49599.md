## Summary

Keep open: current main and the latest release still lack custom-header input and forwarding for Gateway CLI WebSocket connections, and the exact implementation PR is closed unmerged. ## What This Changes

Request support for custom HTTP headers on remote Gateway CLI WebSocket connections through a repeatable CLI flag, environment variable, and/or `gateway.remote.headers` config.

## Best Possible Solution

Define one secret-safe Gateway WebSocket header contract in the Gateway client/call path, then expose approved CLI/env/config surfaces with redaction, SecretInput/env handling, docs, and focused upgrade tests after maintainer product/security approval.

## Reproduction Assessment

Yes, at source level for the missing capability: current main exposes no shared Gateway CLI `--header` option, no header field on the Gateway RPC/call/client option path, and no `gateway.remote.headers` config shape. I did not run a live Cloudflare Access repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product and security contract. The requested owner boundary is plausible, but the exact flag/env/config precedence, secret handling, and persistence model should be approved before implementation.

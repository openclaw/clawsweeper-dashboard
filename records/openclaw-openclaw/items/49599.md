## Summary

Keep open: current main and v2026.6.11 still do not expose or forward custom HTTP headers for Gateway CLI WebSocket connections. The gap is source-proven, but the requested flag/env/config surfaces can carry secrets, so this needs maintainer product and security review before implementation.

## What This Changes

Requests custom HTTP header support for remote Gateway CLI WebSocket connections through a repeatable CLI flag, an environment variable, and/or `gateway.remote.headers` config.

## Best Possible Solution

Define one secret-safe Gateway WebSocket header contract in the Gateway client/call path, then expose only approved CLI/env/config inputs with redaction, SecretInput/env handling, docs, and focused tests.

## Reproduction Assessment

Yes, at source level: current main exposes no shared Gateway CLI `--header` option, no header field in the CLI/call/client option chain, and no `gateway.remote.headers` schema. I did not run a live Cloudflare Access repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product and security contract. The proposed owner boundary is plausible, but the exact flag/env/config precedence and secret-handling model should be approved before implementation.

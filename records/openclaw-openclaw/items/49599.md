## Summary

Keep open: current main and v2026.6.11 still do not expose supported custom HTTP headers for Gateway CLI WebSocket connections. The exact CLI PR attempts are closed unmerged, while merged iOS/Android work solves the same reverse-proxy class only for native mobile clients, so the CLI request still needs maintainer product/security direction.

## What This Changes

Requested support for credential-bearing custom HTTP headers on Gateway CLI WebSocket connections via CLI, environment, or config sources.

## Best Possible Solution

Define one secret-safe Gateway WebSocket header contract at the Gateway client/call boundary, then expose only maintainer-approved CLI/env/config sources with redaction, SecretInput/env handling, docs, and focused tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Gateway CLI accept custom WebSocket HTTP headers, and which CLI/env/config sources, precedence, and credential safeguards should become the supported public contract?

Rationale: The source gap is clear and ws supports request options, but arbitrary headers change the proxy-auth boundary and may carry credentials, so automation should not choose the permanent contract.

Likely owner: steipete

Owner reason: Peter owns the closest Gateway/WebSocket and mobile custom-header decisions and is the best available security-boundary decision owner from history.

Owner confidence: high

Options:

- **Approve a narrow secret-safe contract (recommended):** Add header forwarding through maintainer-approved sources only, with SecretInput/env substitution, reserved-header filtering, redaction, TLS guidance, docs, and tests for fresh and upgrade behavior.
- **Limit support to per-invocation CLI headers:** Support only repeatable explicit CLI headers first, avoiding durable config/env persistence at the cost of CI and automation ergonomics.
- **Decline core header support:** Keep SSH, Tailscale, and local proxy workflows as the supported paths and document reverse-proxy header injection as outside the Gateway CLI contract.

## Reproduction Assessment

Yes, source-level: current main exposes no shared Gateway CLI --header option, no headers field in the Gateway RPC/call/client option chain, no wsOptions.headers forwarding, and no gateway.remote.headers schema. I did not run a live Cloudflare Access or Basic-auth proxy repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product and security contract. The proposed threading is plausible and dependency-supported, but the CLI/env/config precedence and secret-handling model should be approved before implementation.

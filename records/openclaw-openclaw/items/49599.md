## Summary

Keep open: current main and v2026.6.11 still lack a supported way for Gateway CLI WebSocket clients to send custom HTTP headers, and the exact implementation PR is closed unmerged. The source gap is clear, but this adds credential-bearing CLI/env/config surface and needs maintainer product/security direction before implementation.

## What This Changes

Allow Gateway CLI WebSocket calls to send custom HTTP headers through a repeatable flag, environment variable, and/or gateway.remote config.

## Best Possible Solution

Define one secret-safe Gateway WebSocket header contract in packages/gateway-client and callGateway, then expose only approved CLI/env/config sources with redaction, SecretInput handling, docs, and focused tests.

Options:

- **Approve a narrow secret-safe contract (recommended):** Add header forwarding only through maintainer-approved sources, with SecretInput/env substitution, redaction, docs, and tests for fresh and upgrade behavior.
- **Limit to explicit CLI headers only:** Avoid durable config/env persistence for now and require operators to pass headers explicitly per invocation, reducing secret-storage surface at the cost of automation ergonomics.
- **Decline core header support:** Keep SSH, Tailscale, and local proxy workflows as the supported paths and document that authenticating reverse-proxy header injection stays outside OpenClaw CLI.

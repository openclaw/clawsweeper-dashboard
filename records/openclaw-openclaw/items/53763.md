## Summary

Keep open. Current main has a bundled managed/headless browser tool, but the central request is still broader than that: `web_fetch` and `web_search` remain HTTP/provider paths, the managed browser still resolves a local Chromium-family executable, and proxy/session/container security choices are covered by separate open product issues rather than an implemented first-class browser-backed web-access layer.

## What This Changes

Request to add first-class headless browser-backed web access for JS-rendered and login-required pages without relying on user Chrome sessions or third-party extraction APIs.

## Best Possible Solution

Keep this as the broad product/security tracker, benchmark the current HTTP/provider/browser paths on representative URLs, then split approved work into browser-backed extraction semantics, browser/runtime packaging, profile/session persistence, proxy policy, and container backend follow-ups.

## Reproduction Assessment

Yes, at source level: current `web_fetch` is explicitly HTTP/readability-based and current `web_search` is provider-based, while browser execution is a separate tool surface. I did not run live zsxq, Xiaohongshu, or WeChat benchmarks in this read-only review.

## Solution Assessment

No, not as one automatic implementation. The direction is useful, but the maintainable solution needs staged maintainer decisions on ownership, browser binary/runtime packaging, rendered extraction semantics, session persistence, proxy credentials, and browser security policy.

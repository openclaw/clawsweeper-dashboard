## Summary

Keep open. Current main has a bundled managed browser plugin with headless/local/remote CDP support, but the central request is still not implemented because `web_fetch` and `web_search` remain HTTP/provider paths rather than a first-class browser-backed web-access layer.

## What This Changes

Request a built-in headless Chromium-backed web access capability for JS-rendered and login-required pages, with session persistence, proxy support, and no dependency on the user's Chrome or third-party APIs.

## Best Possible Solution

Keep this as the canonical product/security tracker, then split implementation into browser-backed extraction semantics, browser/runtime packaging, profile/session storage, proxy policy, and benchmarked acceptance criteria.

## Reproduction Assessment

Yes, at source level: current `web_fetch` and `web_search` are still HTTP/provider tools, while docs route JS-heavy or login-required pages to the separate browser tool. I did not run live benchmarks against the named sites in this read-only review.

## Solution Assessment

No, not as one automatic implementation. The direction is useful, but the maintainable solution needs staged maintainer decisions on browser ownership, rendered extraction semantics, session persistence, proxy credentials, packaging, and security policy.

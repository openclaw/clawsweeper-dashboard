## Summary

Keep open. Current main and v2026.6.11 already have a managed browser plugin, but the central request is still unresolved: web_fetch and web_search remain HTTP/provider tools, the browser plugin uses playwright-core with an installed Chromium-family executable rather than a bundled browser binary, and browser-backed rendered extraction with session/proxy/security semantics needs maintainer product direction.

## What This Changes

Request a built-in headless Chromium-backed web access path that can render JavaScript, preserve login sessions, support proxies, and work without the user's Chrome or third-party APIs.

## Best Possible Solution

Keep this as the canonical product/security tracker, then split approved work into browser runtime packaging, rendered extraction semantics, session/proxy policy, and benchmarked acceptance criteria.

Rationale: The implementation path changes public tool semantics, browser packaging, logged-in session handling, proxy behavior, and security boundaries; source inspection cannot choose that product contract safely.

Options:

- **Approve staged browser-backed extraction design (recommended):** Define a gated design for rendered extraction that preserves external-content wrapping, browser SSRF policy, session storage rules, proxy credential handling, and benchmarks before code lands.
- **Keep browser explicit for now:** Leave web_fetch and web_search as lightweight/provider tools and document when users should enable the browser tool, Firecrawl, or another provider for JS-heavy or login-required pages.
- **Split into narrower trackers:** Route proxy/isolation, cookie persistence, backend packaging, and search/fetch extraction into separate canonical issues, then close or narrow this umbrella after owners agree.

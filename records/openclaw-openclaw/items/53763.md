## Summary

Keep open. Current main has a substantial bundled browser plugin with managed/headless browser support, but the central product request is still unresolved because `web_fetch` and `web_search` remain HTTP/provider tools and browser-backed extraction, binary packaging, session persistence, proxy behavior, and security policy still need maintainer decisions.

## What This Changes

The issue requests a built-in headless Chromium-backed web access layer for JavaScript-rendered and login-required pages without relying on the user's Chrome or third-party APIs.

## Best Possible Solution

Keep this as the canonical product/security tracker, then split any implementation into benchmarked browser-backed extraction, browser runtime packaging, session/proxy policy, and acceptance criteria that preserve the existing browser and web-tool security boundaries.

## Reproduction Assessment

Yes, at source level. Current docs and code show `web_fetch` remains HTTP-only, `web_search` remains provider-backed, and JS-heavy or login-required pages are routed to the separate browser tool rather than a first-class browser-backed web access layer.

## Solution Assessment

No, not as a one-shot automatic implementation. The direction is useful, but the maintainable solution needs staged maintainer decisions on ownership, browser binary packaging, rendered extraction semantics, session persistence, proxy credentials, and browser security policy.

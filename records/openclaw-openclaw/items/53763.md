## Summary

Keep open. Current main and v2026.6.11 already have a bundled managed browser plugin, but the central request is still missing: web_fetch and web_search remain HTTP/provider tools, and browser-backed rendered extraction with session, proxy, packaging, and security semantics needs maintainer product design.

## What This Changes

Request a built-in headless Chromium/browser-backed web-access path for reliable JS-rendered and login-required page retrieval without relying on the user's Chrome or third-party APIs.

## Best Possible Solution

Keep this as the canonical browser-backed web-access product/security tracker, then split approved work into staged browser plugin/API changes with a benchmark matrix, session/proxy policy, packaging decision, and docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What product shape should OpenClaw use for browser-backed web access: integrate rendered extraction into web_fetch/web_search, keep browser automation as a separate explicit tool with stronger guidance, or delegate advanced extraction to plugins/providers?

Rationale: The current gap is real, but choosing where rendered extraction lives determines security boundaries, plugin/core ownership, config surface, session storage, proxy semantics, and user-visible defaults; automation cannot safely choose that product contract.

Likely owner: steipete

Owner reason: steipete has the clearest recent history across bundled browser ownership, browser docs, and current web-fetch/browser boundary wording.

Owner confidence: medium

Options:

- **Stage Browser-Backed Extraction (recommended):** Use this issue as the canonical design tracker and approve narrower follow-up work for rendered extraction, session/proxy policy, benchmarked acceptance criteria, and security review.
- **Keep Tools Separate:** Keep web_fetch/web_search as lightweight HTTP/provider tools and improve routing/docs so agents switch to the existing browser tool for JS-heavy or login-required pages.
- **Plugin/Provider First:** Require advanced rendered extraction to ship as a plugin or provider contract first, extending core only for missing generic plugin APIs.

## Reproduction Assessment

Yes, at source level for the missing capability: current web_fetch is documented and implemented as HTTP fetch without JavaScript, and web_search routes through providers rather than a browser. I did not run live benchmarks against the listed zsxq.com, Xiaohongshu, or WeChat examples in this read-only review.

## Solution Assessment

No, not as one automatic built-in bundle. The maintainable path is a staged maintainer-approved design for browser-backed extraction, security boundaries, session/proxy semantics, and plugin/API ownership rather than a single broad implementation.

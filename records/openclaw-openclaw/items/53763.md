## Summary

Keep open. Current main and v2026.6.11 have a managed browser plugin and remote-CDP options, but the central request is still not implemented: `web_fetch` and `web_search` remain HTTP/provider paths, and a browser-backed rendered extraction/search product with session, proxy, packaging, and security semantics still needs maintainer design.

## What This Changes

Request to provide first-class built-in headless-browser web access for JS-rendered, login-required, and proxy-sensitive pages without relying on the user's Chrome or third-party APIs.

## Best Possible Solution

Keep this as the canonical product/security tracker, then split approved work into browser runtime packaging, browser-backed extraction semantics, session/proxy policy, and benchmarked acceptance criteria that reuse the existing browser plugin/web-tool seams where possible.

## Reproduction Assessment

Yes, at source level for the missing capability: current `web_fetch` and `web_search` remain HTTP/provider paths, and docs route JS-heavy or login-required pages to the separate browser tool. I did not run live benchmarks against the cited sites in this read-only review.

## Solution Assessment

No, not as one automatic implementation. The useful direction needs staged maintainer decisions on ownership, browser binary/runtime packaging, rendered extraction semantics, session persistence, proxy credentials, and browser security policy.

## Summary

Keep open: current main and the latest release still allow the reported ACP pending-identity and ready-from-persisted-metadata behavior, so the restart-storm routing problem is not already implemented away.

## What This Changes

The issue asks OpenClaw to recover ACP-bound persisted session identity after gateway restart storms so messages continue routing to the intended ACP agent.

## Best Possible Solution

Implement status- or liveness-backed recovery for persistent ACP-bound sessions after gateway restart, keep ensure-sourced IDs provisional until confirmed, and prove configured-channel dispatch after restart.

## Maintainer Decision

Question: Should ACP restart recovery prefer a status/liveness-backed persistent-session re-ensure path while keeping ensure-sourced IDs provisional, or should pending identities with stable IDs be treated as resolved immediately?

Rationale: The source-backed bug is credible, but the permanent recovery contract changes persisted ACP session semantics and overlaps adjacent startup/recovery work.

Likely owner: steipete

Owner confidence: high

Options:

- **Status-Backed Recovery (recommended):** Keep ensure-created IDs provisional, probe or recreate live runtime state for persistent bound sessions, and require restart-channel proof before closing this issue.
- **Resolve Pending IDs:** Treat pending identities with stable IDs as resolved, accepting the risk that stale ensure IDs become authoritative without status confirmation.
- **Defer To Adjacent ACP Work:** Wait for the open startup reconcile PR and any follow-up warm-restore work, then re-check whether this persistent restart-storm path remains uncovered.

## Reproduction Assessment

Yes at source level, but not as a live Feishu restart-storm reproduction. Current main can persist ensure-sourced pending identities with stable IDs, report stored ACP metadata as ready, and accept configured binding readiness without live runtime proof.

## Solution Assessment

No for the proposed direct pending-plus-IDs shortcut, because that can make stale ensure IDs authoritative. The safer fix is a liveness/status-backed persistent recovery path with configured-channel restart proof.

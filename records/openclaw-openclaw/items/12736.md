## Summary

Keep open: current main and the latest release still lack a cron-scoped tool deny policy or explicit inheritance from subagent tool policy. The remaining work is a security-sensitive config/product decision because current behavior is limited to per-job `toolsAllow` and cron delivery safeguards.

## What This Changes

Request to add a cron-scoped tool deny policy or make cron sessions inherit the existing subagent tool policy so scheduled jobs can be hard-blocked from tools like `message`.

## Best Possible Solution

Approve a cron-scoped tool-policy contract only after maintainers define precedence, upgrade behavior, docs/schema shape, and regression coverage for isolated cron message-tool denial across delivery modes.

Rationale: This choice defines a scheduled-run tool-access boundary and public config contract, including whether existing announce-mode cron jobs that directly use `message` remain compatible by default.

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence, schema/types/help/docs updates, and tests for message-tool denial across cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions as well, reducing config surface while coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the security boundary. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

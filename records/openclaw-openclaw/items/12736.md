## Label Justifications

- `P2`: This is a normal-priority security/control improvement for cron automation with limited blast radius and no evidence of an emergency runtime outage.
- `impact:security`: The requested config controls whether scheduled runs can access powerful tools such as `message`, `exec`, or `tts`.
- `impact:message-loss`: The motivating evidence is duplicated or misrouted cron announce delivery when a model can send directly with the `message` tool.

## Summary

Keep open: current main still has per-job cron `toolsAllow` and message-delivery safeguards, but it does not provide the requested operator-enforced cron-scoped allow/deny policy or cron inheritance from `tools.subagents.tools`.

## What This Changes

The issue requests a cron-scoped tool policy, especially `tools.cron.tools.deny`, to prevent isolated cron jobs from using tools such as `message` directly.

## Best Possible Solution

Add a maintainer-approved cron tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add `tools.cron.tools.allow/deny`, make cron inherit `tools.subagents.tools`, or keep cron limited to per-job `toolsAllow` plus delivery safeguards?

Rationale: The choice creates a public config surface and defines the scheduled-run tool-execution security boundary, so automation should not choose the permanent precedence or compatibility behavior.

Likely owner: steipete

Owner reason: The prior issue review plus adjacent cron delivery merge history make steipete the strongest available owner for the cron/config/security-boundary decision.

Owner confidence: high

Options:

- **Add cron-specific policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against existing policy layers and per-job `toolsAllow`, then document and test upgrade behavior.
- **Inherit subagent policy:** Treat isolated cron sessions as covered by `tools.subagents.tools`, reducing config surface but coupling cron and subagent semantics.
- **Keep current safeguards:** Leave cron control to per-job `toolsAllow` and message-delivery safeguards, keeping config smaller but not solving the requested operator deny boundary.

## Reproduction Assessment

Yes, as source-level feature-gap proof: current schemas, exported types, docs, and runtime policy resolution contain subagent/sandbox/per-job paths but no cron-scoped policy path. I did not run a live cron job because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the boundary. `tools.cron.tools.allow/deny` is the cleanest explicit contract, while cron inheritance from `tools.subagents.tools` is a plausible lower-surface alternative.

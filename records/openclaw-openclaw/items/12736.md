## Summary

Keep open: current main has per-job cron `toolsAllow` and duplicate-delivery safeguards, but it still lacks a cron-scoped hard allow/deny config policy or documented inheritance from subagent policy. This remains a security-boundary product decision, not conservative cleanup.

## What This Changes

The issue requests a cron-specific tool policy such as `tools.cron.tools.deny` so scheduled isolated jobs can be prevented from using tools like `message` without relying on prompts or per-job allowlists.

## Best Possible Solution

Add a core cron-scoped tool policy only after maintainers choose the security and compatibility semantics, then align schema, exported types, config help, docs, diagnostics, and regression coverage for cron message-tool denial across embedded and CLI-backed runs.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should scheduled cron agentTurn sessions get a first-class hard tool policy such as `tools.cron.tools.allow/deny`, and where should it sit relative to per-job `toolsAllow` and existing subagent/sandbox policy layers?

Rationale: This would add a public config surface and a scheduled-execution security boundary; choosing inheritance or precedence incorrectly could either leave cron overpowered or break existing jobs that rely on current tool exposure.

Likely owner: steipete

Owner reason: He is the strongest current routing signal from prior review and current blame on the relevant config and cron policy surfaces.

Owner confidence: high

Options:

- **Add first-class cron policy (recommended):** Introduce `tools.cron.tools.allow/deny` as a distinct cron layer, define deny/allow precedence against per-job `toolsAllow`, and document upgrade-safe behavior.
- **Inherit subagent policy:** Treat cron sessions as sharing `tools.subagents.tools` to avoid a new config block, accepting that subagent and scheduled-job semantics become coupled.
- **Keep per-job allowlists only:** Leave `--tools` and payload `toolsAllow` as the supported boundary and close or narrow this request to docs and safer defaults.

## Reproduction Assessment

Yes, at source level: current main has no `tools.cron.tools` schema/type surface, and subagent policy only applies to subagent-envelope sessions while cron sessions are classified separately. I did not run a live cron job because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the security boundary. A distinct cron policy looks cleaner than inheriting subagent policy, but the final implementation must define precedence with per-job `toolsAllow` and CLI-backed runtimes.

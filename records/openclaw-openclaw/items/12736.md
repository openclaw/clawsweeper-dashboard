## Summary

Keep open: current main has unreleased safeguards that skip fallback announce after verified message-tool delivery, but it still has no cron-scoped `tools.cron.tools.allow/deny` policy and cron sessions do not inherit `tools.subagents.tools`.

## What This Changes

Add a system-level cron tool restriction config such as `tools.cron.tools.deny`, or make cron sessions inherit the existing subagent tool policy.

## Best Possible Solution

Approve a cron-scoped tool-policy contract, preferably `tools.cron.tools.allow/deny`, with explicit precedence, docs/schema/types updates, and regression coverage that preserves the current duplicate-delivery safeguard.

Rationale: The choice defines a public scheduled-run tool-access boundary with security and upgrade implications, so automation should not choose the default or precedence contract.

Likely owner: steipete

Owner confidence: high

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence against existing policy layers and per-job `toolsAllow`.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two execution modes with different semantics.
- **Keep per-job policy only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level: current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the security boundary; a cron-scoped policy appears cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

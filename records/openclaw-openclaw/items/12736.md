## Summary

Keep open: current main and latest release still lack an enforceable cron-scoped tool deny policy, while the existing per-job `toolsAllow` and cron delivery safeguards only partially mitigate the reported duplicate-message and tool-boundary risk.

## What This Changes

The issue requests a cron-scoped tool policy, such as `tools.cron.tools.deny`, so scheduled isolated runs can restrict tools like `message` without relying on prompt instructions.

## Best Possible Solution

Keep this as the cron-scoped policy tracker until maintainers choose explicit `tools.cron.tools.allow/deny` or documented cron inheritance, then implement schema/types/docs/help/tests with clear precedence and upgrade behavior.

## Reproduction Assessment

Yes, for the missing capability: current main has no `tools.cron.tools` config surface and cron sessions do not enter the subagent-only policy layer. No live cron run was executed because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the product/security shape. `tools.cron.tools.deny` is plausible, but the maintainable solution must define precedence against existing policy layers, per-job `toolsAllow`, and delivery behavior before implementation.

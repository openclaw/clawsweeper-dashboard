## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool deny config surface, while existing per-job `toolsAllow` and message-delivery safeguards only partially cover the reported scheduled-message risk.

## What This Changes

The issue requests a cron-scoped tool restriction config such as `tools.cron.tools.deny` or inheritance from subagent tool policy.

## Best Possible Solution

Keep this as the cron-scoped policy tracker until maintainers choose explicit `tools.cron.tools.allow/deny` or documented cron inheritance, then update schema/types/docs and add regression coverage across announce, none, webhook, and per-job `toolsAllow` precedence.

Options:

- **Add explicit cron policy (recommended):** Add `tools.cron.tools.allow/deny` with documented precedence against existing policy layers and per-job `toolsAllow`, plus focused cron delivery regression tests.
- **Inherit subagent policy:** Make cron sessions reuse `tools.subagents.tools` semantics, accepting the simpler config surface but documenting any compatibility impact on existing jobs.
- **Keep current model:** Decline the new config surface and document per-job `--tools` plus delivery safeguards as the supported mitigation.

Yes for the missing capability: current main and the latest release have no `tools.cron.tools` config surface, and cron delivery prompting only responds to per-job `toolsAllow`. No live current-main cron run was executed because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the security/product shape. `tools.cron.tools.deny` is plausible, but the best solution must define precedence, defaults, and upgrade behavior before implementation.

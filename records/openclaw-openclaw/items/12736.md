## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool allow/deny policy or an explicit inheritance path from `tools.subagents.tools`, while the sanitized duplicate-message evidence shows the missing boundary still matters for scheduled-run security and message delivery.

## What This Changes

The issue requests cron-job tool restrictions such as `tools.cron.tools.deny`, or cron inheritance from subagent tool policy, so isolated scheduled runs cannot call disallowed tools like `message`.

## Best Possible Solution

Add a maintainer-approved cron tool-policy contract in the existing config/runtime path: either `tools.cron.tools.allow/deny` or documented cron inheritance from subagent policy, with clear precedence, schema/types/help/docs alignment, and regression coverage for isolated cron `message` denial with announce delivery.

Options:

- **Add cron-specific policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against existing policy layers and per-job `toolsAllow`, then document and test upgrade behavior.
- **Inherit subagent policy:** Treat cron isolated sessions as covered by `tools.subagents.tools`, reducing config surface but coupling two different runtime concepts.
- **Keep current safeguards only:** Leave cron control to per-job `toolsAllow` and duplicate-delivery safeguards, which keeps config smaller but does not solve the requested operator deny boundary.

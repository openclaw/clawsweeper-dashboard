## Summary

Keep open: current main still lacks a cron-scoped tool deny config surface, and the existing per-job `toolsAllow` plus message-delivery safeguards only partially address the reported scheduled-message risk.

## What This Changes

The issue requests a cron-scoped tool deny policy, such as `tools.cron.tools.deny`, so scheduled isolated jobs can be prevented from using tools like `message`.

## Best Possible Solution

Keep this as the cron-scoped policy tracker until maintainers choose explicit `tools.cron.tools.allow/deny` or documented cron inheritance, then update schema/types/help/docs and add regression coverage for delivery-mode and per-job precedence.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should cron runs get an explicit `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or keep the current per-job `toolsAllow` plus delivery safeguards model?

Rationale: The choice defines a scheduled-run tool-access boundary, a public config/default precedence contract, and possible upgrade behavior for existing jobs, so automation should not choose it without maintainer security/product intent.

Likely owner: steipete

Owner reason: He authored the prior detailed review on this issue and has the strongest current routing signal across cron, config, and tool-policy boundaries.

Owner confidence: high

Options:

- **Add explicit cron policy (recommended):** Add `tools.cron.tools.allow/deny` with documented precedence against existing policy layers and per-job `toolsAllow`, plus focused cron delivery regression tests.
- **Inherit subagent policy:** Make cron sessions reuse `tools.subagents.tools` semantics, accepting the simpler config surface while documenting compatibility impact on existing jobs.
- **Keep current model:** Decline the new config surface and document per-job `--tools` plus delivery safeguards as the supported mitigation.

## Reproduction Assessment

Yes for the missing capability: current main has no `tools.cron.tools` config surface and cron sessions do not enter the subagent policy layer. No live cron run was executed because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the security/product shape. `tools.cron.tools.deny` is plausible, but the best solution must define precedence, defaults, and upgrade behavior before implementation.

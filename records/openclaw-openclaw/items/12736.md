## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool allow/deny policy or cron inheritance from `tools.subagents.tools`; the existing per-job `toolsAllow` and message-delivery safeguards reduce duplicates but do not provide the requested operator-enforced cron tool boundary.

## What This Changes

Request a cron-scoped tool allow/deny config policy, especially to deny `message` for isolated cron runs without relying on prompt instructions.

## Best Possible Solution

Add a maintainer-approved cron tool-policy contract with clear precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Question: Should OpenClaw add a cron-specific tool policy such as `tools.cron.tools.allow/deny`, make cron inherit `tools.subagents.tools`, or keep only per-job `toolsAllow` plus delivery safeguards?

Rationale: This defines a scheduled-run tool-execution boundary and a new public config surface, so automation should not choose the permanent precedence or compatibility behavior without maintainer intent.

Likely owner: steipete

Owner reason: The prior issue review and recent cron/config/security-adjacent history make `steipete` the best available decision owner.

Owner confidence: high

Options:

- **Add cron-specific policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against existing policy layers and per-job `toolsAllow`, then document and test the upgrade behavior.
- **Inherit subagent policy:** Treat cron isolated sessions as covered by `tools.subagents.tools`, reducing config surface but coupling cron and subagent semantics.
- **Keep current safeguards only:** Leave cron control to per-job `toolsAllow` and duplicate-delivery safeguards, which keeps config smaller but does not solve the requested operator deny boundary.

## Reproduction Assessment

Yes, as source-level feature-gap proof: current schemas, exported types, docs, and runtime tool-policy resolution contain subagent/sandbox/per-job policy paths but no cron policy path.

## Solution Assessment

Unclear until maintainers choose the boundary: `tools.cron.tools.allow/deny` is the cleanest explicit contract, but cron inheritance from `tools.subagents.tools` is a plausible lower-surface alternative.

## Summary

Keep open: current main still lacks a cron-scoped tool allow/deny policy or inheritance from `tools.subagents.tools`; cron can only be narrowed per job through `payload.toolsAllow`, so the requested operator-wide cron restriction remains unresolved.

## What This Changes

The issue requests an operator-enforced cron tool policy such as `tools.cron.tools.deny`, or explicit cron inheritance from `tools.subagents.tools`, to prevent cron jobs from using tools like `message` directly.

## Best Possible Solution

Add a maintainer-approved cron tool-policy layer, with explicit precedence and upgrade behavior, then update schema/types/help/docs and regression tests for isolated cron `message` denial across announce and non-announce delivery modes.

Question: Should OpenClaw add a first-class `tools.cron.tools.allow/deny` policy layer, make cron inherit `tools.subagents.tools`, or keep cron limited to per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: This is a permanent public config and security boundary choice, and the safer precedence relative to existing policy layers and stored cron jobs is not something automation should decide.

Likely owner: steipete

Owner reason: steipete is tied to the current subagent policy lines and already reviewed this exact issue as requiring maintainer follow-up.

Owner confidence: high

Options:

- **Add explicit cron policy layer (recommended):** Introduce `tools.cron.tools.allow/deny` as a named cron-only policy layer, document precedence against per-job `toolsAllow`, and cover fresh and upgrade behavior in tests.
- **Inherit subagent policy for cron:** Treat isolated cron sessions as subagent-like for tool restrictions, reducing new config surface but coupling cron behavior to spawned-agent semantics.
- **Keep per-job only:** Leave `payload.toolsAllow` and delivery safeguards as the supported path, avoiding new config but leaving no operator-wide cron deny knob.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: current main has no `tools.cron.tools` schema/type surface, and the subagent policy path only applies when the session is classified as a subagent. I did not run a live cron job in this read-only review.

## Solution Assessment

Unclear until maintainers choose the policy shape; an explicit cron policy layer is the cleanest fit for the report, but inheriting subagent policy is also plausible if maintainers accept that semantic coupling.

## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool allow/deny policy or cron inheritance from `tools.subagents.tools`; the existing per-job `toolsAllow` and announce-delivery safeguards do not provide the requested operator-enforced cron tool boundary.

## What This Changes

Request a cron-scoped tool policy so isolated cron jobs can block tools like `message` instead of relying on per-job allowlists or prompt instructions.

## Best Possible Solution

Define a maintainer-approved cron tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Rationale: This choice creates a public config surface and defines the scheduled-run tool-execution security boundary, so automation should not choose the permanent precedence or compatibility behavior.

Options:

- **Add cron-specific policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against existing policy layers and per-job `toolsAllow`, then document and test upgrade behavior.
- **Inherit subagent policy:** Treat isolated cron sessions as covered by `tools.subagents.tools`, reducing config surface but coupling cron and subagent semantics.
- **Keep current safeguards:** Leave cron control to per-job `toolsAllow` and message-delivery safeguards, keeping config smaller but not solving the requested operator deny boundary.

## Reproduction Assessment

Yes, as source-level feature-gap proof: current schemas, exported types, docs, and runtime policy resolution contain subagent/sandbox/per-job paths but no cron-scoped policy path.

## Solution Assessment

Unclear until maintainers choose the boundary. `tools.cron.tools.allow/deny` is the cleanest explicit contract, while cron inheritance from `tools.subagents.tools` is a plausible lower-surface alternative.

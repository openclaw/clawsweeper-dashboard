## Summary

Keep open: current main and v2026.6.11 still do not provide a cron-scoped tool allow/deny policy or cron inheritance from `tools.subagents.tools`; the remaining work is a public config and security-boundary decision, not stale cleanup.

## What This Changes

The issue requests a `tools.cron.tools.deny` config option, or equivalent cron inheritance, so scheduled isolated cron runs can be prevented from directly using tools such as `message`.

## Best Possible Solution

Adopt one maintainer-approved cron tool-policy contract, document its precedence and upgrade behavior, and add regression coverage for isolated cron message-tool denial across delivery modes.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a cron-specific tool policy such as `tools.cron.tools.allow/deny`, make cron inherit `tools.subagents.tools`, or keep only per-job `toolsAllow` plus delivery safeguards?

Rationale: The choice defines a scheduled-run tool-execution boundary and a new public config surface, so automation should not choose the permanent precedence, compatibility behavior, or security guarantee.

Likely owner: steipete

Owner reason: steipete has the strongest recent history in scoped conversation/tool-policy plumbing and already reviewed this issue as a cron policy decision.

Owner confidence: high

Options:

- **Add cron-specific policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against existing policy layers and per-job `toolsAllow`, then document and test the upgrade behavior.
- **Inherit subagent policy:** Treat cron isolated sessions as covered by `tools.subagents.tools`, reducing config surface but coupling cron and subagent semantics.
- **Keep current safeguards:** Leave cron control to per-job `toolsAllow` and delivery safeguards, keeping config smaller but not solving the requested operator-level deny boundary.

## Reproduction Assessment

Yes, as source-level feature-gap proof: current schemas, exported types, docs, and runtime tool-policy resolution contain subagent/sandbox/per-job policy paths but no cron policy path.

## Solution Assessment

Unclear until maintainers choose the boundary. `tools.cron.tools.allow/deny` is the cleanest explicit contract, while cron inheritance from `tools.subagents.tools` is a plausible lower-surface alternative.

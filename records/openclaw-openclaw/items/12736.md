## Label Justifications

- `P2`: The issue requests a normal-priority security/control improvement for cron automation with limited blast radius and no evidence of an emergency runtime outage.
- `impact:security`: The requested config controls whether scheduled runs can access powerful tools such as `message`, `exec`, or `tts`.
- `impact:message-loss`: The motivating evidence is duplicated or misrouted cron announce delivery when a model can send directly with the `message` tool.

## Summary

Keep open: current main still lacks a cron-scoped tool allow/deny policy or cron inheritance from `tools.subagents.tools`; existing `payload.toolsAllow` and announce-delivery safeguards reduce some duplicate-message cases but do not provide the requested operator-enforced cron deny boundary.

## What This Changes

Request a cron-scoped tool deny policy, or cron inheritance from subagent tool policy, so scheduled isolated jobs can be blocked from tools such as `message`.

## Best Possible Solution

Add a maintainer-approved cron tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across announce, none, and webhook delivery modes.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should cron runs get an explicit `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or keep only per-job `toolsAllow` plus delivery safeguards?

Rationale: This defines a scheduled-run tool-execution boundary and new public config semantics, so automation should not choose the permanent security and compatibility contract without maintainer intent.

Likely owner: steipete

Owner reason: steipete has the strongest prior-review and recent cron/tool-policy history for choosing this security boundary.

Owner confidence: high

Options:

- **Add cron-specific policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence against existing policy layers and per-job `toolsAllow`.
- **Inherit subagent policy:** Treat isolated cron sessions as covered by `tools.subagents.tools`, reducing config surface but coupling cron and subagent semantics.
- **Keep current safeguards:** Leave cron control to per-job `toolsAllow` and announce delivery safeguards, accepting that there is no global cron deny boundary.

## Reproduction Assessment

Yes, as source-level feature-gap proof: current schemas, exported types, docs, and runtime tool-policy resolution contain subagent/sandbox/per-job policy paths but no cron policy path. I did not run a live cron because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the boundary. `tools.cron.tools.allow/deny` is the cleanest explicit contract, while inheriting `tools.subagents.tools` is a plausible lower-surface alternative.

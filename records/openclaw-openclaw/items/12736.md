## Summary

Keep open: current main still lacks a cron-scoped allow/deny policy or explicit inheritance from `tools.subagents.tools`; per-job `toolsAllow` and delivery safeguards are useful mitigations but do not satisfy the requested operator-level cron deny policy.

## What This Changes

Request a system-wide cron tool restriction policy, preferably `tools.cron.tools.deny`, so isolated cron jobs cannot use blocked tools such as `message`.

## Best Possible Solution

Define and implement a cron tool-policy contract with schema/types/help/docs updates and regression tests for message denial across cron delivery modes and per-job `toolsAllow` precedence.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should isolated cron jobs get first-class `tools.cron.tools.allow/deny`, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: This choice defines scheduled-run tool access, public config semantics, and upgrade behavior for jobs that may intentionally use direct `message` delivery.

Likely owner: steipete

Owner reason: steipete has the strongest combined signal from prior issue review and recent cron/tool-policy-adjacent history.

Owner confidence: high

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface while coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes, at source level: current schema/types still lack `tools.cron.tools`, and runtime policy resolution only applies `tools.subagents.tools` to subagent envelopes.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainers choose the security boundary; a cron-scoped policy looks cleaner than overloading subagent semantics, but precedence and upgrade behavior must be specified first.

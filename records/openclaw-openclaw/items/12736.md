## Summary

Keep open: current main and v2026.6.11 still do not provide `tools.cron.tools.allow/deny` or explicit cron inheritance from `tools.subagents.tools`, and the remaining choice is a security-sensitive public config/default decision rather than a closeable cleanup item.

## What This Changes

Request a cron-scoped tool restriction option, or equivalent inheritance from subagent tool policy, so isolated cron jobs can be denied tools such as `message` system-wide.

## Best Possible Solution

Approve a typed cron tool-policy design, or explicit inheritance rule, with precedence rules, schema/types/docs, and regression coverage for isolated cron message-tool denial across announce/none delivery modes.

Question: Should isolated cron jobs get their own `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or use a delivery-mode-specific default such as denying `message` during announce delivery?

Rationale: This decides a public config surface and unattended-execution security boundary, including how existing per-job `toolsAllow` and delivery behavior interact with global tool policy.

Likely owner: steipete

Owner reason: steipete has the strongest recent history across cron delivery/session runtime and shared tool-policy diagnostics, which frame this security boundary.

Owner confidence: high

Options:

- **Add explicit cron policy (recommended):** Add `tools.cron.tools.allow/deny` with documented precedence over or under per-job `toolsAllow`, plus schema/types/docs and regression tests.
- **Inherit subagent policy:** Treat cron isolated sessions as subagent-like for tool policy while documenting why cron and delegated sessions share the same boundary.
- **Use delivery-aware defaults only:** Avoid a new broad config key and instead deny or suppress direct `message` sends for announce delivery unless explicitly allowed.

## Reproduction Assessment

Yes, at source level: current main has no `tools.cron.tools` schema/type/pipeline layer, while cron still relies on per-job `payload.toolsAllow` and delivery-aware prompting. I did not run a live cron job in this read-only review.

## Solution Assessment

Unclear until maintainers choose the security boundary. A cron-scoped config option is plausible, but inheriting subagent policy or adding delivery-aware message-tool defaults could be safer depending on the intended operator contract.

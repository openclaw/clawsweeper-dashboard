## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped hard tool allow/deny policy, while the issue has concrete duplicate-delivery and security-boundary evidence. The remaining work is a maintainer security/config precedence decision, not stale cleanup.

## What This Changes

Request a cron-scoped tool policy such as `tools.cron.tools.deny`, or cron inheritance from `tools.subagents.tools`, so isolated cron jobs cannot call denied tools like `message`.

## Best Possible Solution

Make a maintainer-owned security decision for cron tool policy, then implement one hard enforcement path with schema, exported types, config metadata/help/labels, docs, and regression coverage for isolated cron delivery behavior.

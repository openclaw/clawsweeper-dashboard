## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped global tool deny policy or explicit inheritance from `tools.subagents.tools`, so this remains a security-sensitive config/product decision rather than conservative cleanup.

## What This Changes

The issue requests a `tools.cron.tools.deny`-style cron tool policy or cron inheritance from subagent tool policy to prevent scheduled jobs from using tools such as `message`.

## Best Possible Solution

Approve a cron-scoped tool-policy contract with explicit precedence against global, sender, sandbox, subagent, inherited, and per-job policies, then update schema/types/docs and regression coverage for isolated cron delivery modes.

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence, docs, and tests for message-tool denial across delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions as well, reducing config surface while coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

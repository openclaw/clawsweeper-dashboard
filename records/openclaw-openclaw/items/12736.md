## Summary

Keep open: current `main` and `v2026.6.11` still lack a cron-scoped tool deny policy, and existing per-job `toolsAllow` plus cron message-delivery safeguards do not provide the requested enforceable config surface.

## What This Changes

Request a cron-scoped tool restriction config such as `tools.cron.tools.deny`, or explicit cron inheritance from the existing subagent tool policy, so scheduled isolated cron jobs cannot call disallowed tools like `message`.

## Best Possible Solution

Keep this as the narrow cron tool-policy tracker until maintainers choose explicit `tools.cron.tools.allow/deny` or documented cron inheritance, then implement schema/types/help/docs and regression coverage for isolated cron message-tool denial across delivery modes.

## Reproduction Assessment

Yes, for the missing capability: current main has no `tools.cron.tools` config surface and cron sessions do not enter the subagent policy layer. No live cron run was executed because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the product/security shape. `tools.cron.tools.deny` is plausible, but the maintainable fix must define precedence against existing policy layers and per-job `toolsAllow` before implementation.

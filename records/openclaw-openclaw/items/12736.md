## Summary

Keep open: current main and v2026.6.11 still have per-job cron `toolsAllow` and subagent-specific policy, but no cron-scoped allow/deny policy and no cron inheritance from `tools.subagents.tools`; the remaining work is a security/product decision about the public config contract and precedence.

## What This Changes

Request to add an operator-enforced cron job tool allow/deny policy, or make cron sessions inherit the existing subagent tool deny policy.

## Best Possible Solution

Add a maintainer-approved cron tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add `tools.cron.tools.allow/deny`, make cron inherit `tools.subagents.tools`, or keep cron limited to per-job `toolsAllow` plus delivery safeguards?

Rationale: The choice defines a scheduled-run tool-execution security boundary and a new public config/default surface, so automation should not choose the permanent precedence or compatibility behavior.

Likely owner: steipete

Owner reason: steipete has the strongest recent history across cron, agent tool-policy, and the prior review routing for this security/config decision.

Owner confidence: high

Options:

- **Add cron-specific policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against existing policy layers and per-job `toolsAllow`, then document and test upgrade behavior.
- **Inherit subagent policy:** Treat isolated cron sessions as covered by `tools.subagents.tools`, reducing config surface but coupling cron and subagent semantics.
- **Keep current safeguards:** Leave cron control to per-job `toolsAllow` and message-delivery safeguards, keeping config smaller but not solving the requested operator deny boundary.

## Reproduction Assessment

Yes, as source-level feature-gap proof: current schemas, exported types, docs, and runtime policy resolution contain subagent/sandbox/per-job paths but no cron-scoped policy path. I did not run a live cron because this review was read-only.

## Solution Assessment

Unclear until maintainers choose the boundary. `tools.cron.tools.allow/deny` is the cleanest explicit contract, while cron inheritance from `tools.subagents.tools` is a plausible lower-surface alternative with different semantics.

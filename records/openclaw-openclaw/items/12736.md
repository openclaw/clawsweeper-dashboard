## Summary

Keep open: current main and latest release still do not provide `tools.cron.tools.allow/deny` or explicit inheritance from `tools.subagents.tools`; per-job `toolsAllow` and duplicate-delivery guards help, but they do not satisfy the requested system-wide cron tool boundary.

## What This Changes

Request a cron-scoped tool policy, such as `tools.cron.tools.deny`, so isolated cron jobs can be hard-restricted from tools like `message`.

## Best Possible Solution

Approve and implement a cron-scoped tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Rationale: This defines a scheduled-run tool-access boundary and public config contract, including whether existing announce-mode cron jobs that directly use `message` keep working by default.

Owner confidence: high

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface while coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

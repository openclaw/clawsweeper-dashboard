## Summary

Keep open: current main and latest v2026.6.11 still lack a cron-scoped tool allow/deny config or explicit inheritance from subagent policy, and the remaining work is a security-sensitive config/product decision.

## What This Changes

The issue requests a system-level cron tool restriction option, such as `tools.cron.tools.deny`, or explicit cron inheritance from `tools.subagents.tools`.

## Best Possible Solution

Approve or explicitly decline a typed cron tool-policy contract after defining precedence, announce/message defaults, schema/docs/config metadata, and regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a first-class cron-scoped tool policy, make cron inherit subagent policy, or keep per-job `payload.toolsAllow` as the only hard cron tool boundary?

Rationale: The choice defines a public config surface and enforcement boundary for scheduled automation, including whether existing announce jobs keep direct `message` access by default.

Likely owner: steipete

Owner reason: They have the strongest recent history across scoped conversation capability profiles, cron/session behavior, and prior review context for this issue.

Owner confidence: high

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` or an equivalent typed cron policy with explicit precedence, docs, config metadata, and tests for announce/message behavior.
- **Inherit subagent policy:** Treat isolated cron sessions as a policy peer of subagents so `tools.subagents.tools` also applies to cron, accepting and documenting the broader coupling.
- **Keep per-job only:** Decline a global cron config surface and document that operators must use per-job `payload.toolsAllow` or runtime delivery safeguards for cron restrictions.

## Reproduction Assessment

Yes, at source level. Current main has per-job `payload.toolsAllow` and subagent/sandbox policy wrappers, but no cron-scoped allow/deny config or cron inheritance path; I did not run a live cron in this read-only review.

## Solution Assessment

Unclear until maintainers choose the policy shape. A cron-specific allow/deny config is plausible, but inheritance from subagent policy or staying with per-job `toolsAllow` are product/security choices with different upgrade behavior.

## Summary

Keep open: current main has per-job `toolsAllow` and cron message-delivery mitigations, but it still lacks a cron-scoped config policy or explicit inheritance from `tools.subagents.tools`.

## What This Changes

The issue requests a cron-scoped tool restriction config, such as `tools.cron.tools.deny`, so isolated cron jobs can be hard-blocked from tools like `message`.

## Best Possible Solution

Choose one canonical cron tool-policy design, define its precedence with existing policy layers and per-job `toolsAllow`, then update schema/types/help/docs and add cron regression coverage for `message` denial across delivery modes.

Options:

- **Add explicit cron policy (recommended):** Add `tools.cron.tools.allow/deny` as the canonical scheduled-agent policy with documented precedence over broad config and interaction with per-job `toolsAllow`.
- **Inherit subagent policy:** Treat isolated cron runs like subagent envelopes for tool-policy purposes, reducing config surface but coupling two distinct execution modes.
- **Keep per-job only:** Decline a new global cron policy and document `payload.toolsAllow` / `openclaw cron --tools` as the supported hard restriction path.

## Reproduction Assessment

Yes, at source level: current main lacks `tools.cron.tools.*`, and subagent tool policy is gated to subagent or ACP envelope sessions, not cron. I did not run a live cron job; the issue discussion supplies sanitized duplicate-message evidence from v2026.5.18.

## Solution Assessment

Unclear until maintainers choose the policy shape. A dedicated cron policy is the cleanest fit for this request, but inheritance from `tools.subagents.tools` would avoid another config surface if maintainers want both execution modes coupled.

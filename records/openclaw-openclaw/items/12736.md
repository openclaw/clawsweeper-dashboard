## Summary

Keep open: current main and latest v2026.6.11 still lack a cron-scoped `tools.cron.tools.allow/deny` policy or cron inheritance from `tools.subagents.tools`, and the existing per-job `toolsAllow` plus cron delivery safeguards only partially mitigate the reported duplicate/misrouted message risk.

## What This Changes

Request a cron-scoped tool restriction policy, such as `tools.cron.tools.deny` or explicit inheritance from subagent tool policy, for isolated scheduled jobs.

## Best Possible Solution

Keep this as the cron-scoped policy tracker until maintainers choose explicit `tools.cron.tools.allow/deny` or documented cron inheritance, then implement schema/types/help/docs, precedence, upgrade guidance, and regression coverage for isolated cron message-tool denial across delivery modes.

## Reproduction Assessment

Yes for the missing capability: current main has no `tools.cron.tools` config surface and cron sessions do not enter the subagent policy layer. No live cron run was executed because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the product/security shape. `tools.cron.tools.deny` is plausible, but the maintainable solution must define precedence against existing policy layers and per-job `toolsAllow` before implementation.

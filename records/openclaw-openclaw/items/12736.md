## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped hard tool policy such as `tools.cron.tools.allow/deny`; merged per-job `toolsAllow` and cron delivery safeguards address adjacent failure modes but do not provide the requested operator config boundary.

## What This Changes

The issue asks for a `tools.cron.tools.deny`/allow policy, or cron inheritance from `tools.subagents`, so isolated cron jobs can hard-block tools such as `message`.

## Best Possible Solution

Define one cron-owned hard tool-policy path, document its precedence against existing policy layers and per-job `toolsAllow`, and add schema/types/help/docs plus focused cron message-tool and CLI/embedded regression coverage.

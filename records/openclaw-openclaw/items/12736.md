- `P2`: This is meaningful security and delivery-policy work for scheduled automation, but it is a bounded feature/design gap rather than an urgent runtime outage.

## Summary

Keep open: current main still lacks a cron-scoped tool policy, and the remaining behavior is per-job `payload.toolsAllow` plus delivery-mode prompt handling rather than a system-level deny for isolated cron sessions.

## What This Changes

Requested a `tools.cron.tools.deny` option or equivalent cron inheritance so isolated cron jobs can block tools such as `message` at the policy layer.

## Best Possible Solution

Add a typed cron tool-policy layer, or explicitly document cron inheritance from an existing policy layer, with precedence rules, schema/types/docs, and tests for message denial across announce, none, and webhook delivery modes.

Rationale: This defines a public config contract and scheduled-run security boundary across tool access, message delivery, and existing policy precedence, so automation should not choose it without maintainer intent.

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` as the explicit scheduled-run policy layer and document/test how it composes with per-job `toolsAllow` and delivery requirements.
- **Inherit subagent policy:** Make cron sessions participate in `tools.subagents.tools` only if maintainers want cron and subagents to share one operator-facing restriction model.
- **Keep per-job tools only:** Decline a new config surface and instead document `payload.toolsAllow` as the cron restriction mechanism while adding targeted duplicate-delivery safeguards if needed.

## Reproduction Assessment

Yes for the source-level gap: current main has no `tools.cron.tools` schema/type path, and cron sessions do not enter the subagent policy branch. A live duplicate-message cron was not rerun in this read-only review.

## Solution Assessment

Unclear until maintainers choose the policy boundary. A cron-specific policy looks cleaner than silently inheriting subagent policy because cron has distinct per-job allowlists and delivery modes.

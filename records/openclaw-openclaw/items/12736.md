## Summary

Keep open: current main still lacks a cron-scoped tool allow/deny config layer or explicit inheritance from subagent tool policy, and the remaining work is a security-sensitive product/config decision rather than an already-implemented cleanup target.

## What This Changes

Request a hard cron job tool-restriction policy such as `tools.cron.tools.deny`, or explicit inheritance from `tools.subagents.tools`, so scheduled isolated runs can be prevented from using tools like `message`.

## Best Possible Solution

Keep this open until maintainers approve a cron tool-policy contract with explicit precedence, upgrade behavior, schema/types/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions as well, reducing config surface but coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

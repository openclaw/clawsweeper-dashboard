## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped deny policy or inheritance from `tools.subagents.tools`, and the remaining work is a security-sensitive config/defaults decision rather than conservative cleanup.

## What This Changes

Request to add `tools.cron.tools.deny` or an equivalent inheritance rule so isolated cron jobs can be restricted from tools such as `message` at the system-policy layer.

## Best Possible Solution

Keep this open for a maintainer-approved cron tool-policy design that defines cron allow/deny or explicit inheritance, precedence against existing policy layers and per-job `toolsAllow`, schema/docs updates, and regression coverage for announce delivery.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should isolated cron runs get a first-class `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: The choice defines a scheduled-run tool-access boundary and public config/default contract, including compatibility and precedence with existing policy layers, so automation should not choose it without maintainer intent.

Likely owner: steipete

Owner reason: steipete has the strongest combined signal from current-main history, the prior issue review, and recent cron/security policy work.

Owner confidence: high

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface while coupling two different execution modes.
- **Keep per-job only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, documentation, and delivery-mode safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow`.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

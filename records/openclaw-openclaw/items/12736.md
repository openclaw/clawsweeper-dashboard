Keep open: current main still lacks `tools.cron.tools.allow/deny` or cron inheritance from `tools.subagents.tools`; the remaining work is a security-sensitive public config/default decision, not conservative cleanup.

## What This Changes

Request cron-scoped tool policy configuration so scheduled isolated jobs can deny tools such as `message` independently of subagent tool policy.

## Best Possible Solution

Approve a cron-scoped tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron `message` denial across delivery modes.

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence against existing policy layers and per-job `toolsAllow`.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface while coupling two execution modes.
- **Keep per-job policy only:** Avoid new global cron config and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

Yes, at source level. Current main still has no `tools.cron.tools` schema/type/doc surface and only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the product/security direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best implementation must define precedence and upgrade behavior first.

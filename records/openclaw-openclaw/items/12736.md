## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool deny policy or inheritance from `tools.subagents.tools`; this remains a security-sensitive config/product decision rather than conservative cleanup.

## What This Changes

Add a cron-scoped system-level tool allow/deny policy, or make cron sessions inherit subagent tool policy, so isolated cron jobs can be denied tools such as `message`.

## Best Possible Solution

Keep this open until maintainers approve a cron tool-policy design that defines cron allow/deny or explicit inheritance, precedence, docs/schema/type updates, and regression coverage for announce/direct delivery behavior.

Question: Should isolated cron jobs get a first-class `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: The choice defines a scheduled-run tool-access boundary and public config/default contract, including how hard denies interact with existing policy layers and current cron jobs that use direct delivery.

Likely owner: steipete

Owner confidence: high

Options:

- **Add cron-specific policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against existing policy layers and per-job `toolsAllow`, then document and test upgrade behavior.
- **Inherit subagent policy:** Treat isolated cron sessions as covered by `tools.subagents.tools`, reducing config surface but coupling cron and subagent semantics.
- **Keep current safeguards:** Leave cron control to per-job `toolsAllow` and message-delivery safeguards, keeping config smaller but not solving the requested operator deny boundary.

## Reproduction Assessment

Yes, as source-level feature-gap proof: current schemas, exported types, docs, and runtime policy resolution contain subagent/sandbox/per-job paths but no cron-scoped policy path.

## Solution Assessment

Unclear until maintainers choose the boundary. `tools.cron.tools.allow/deny` is the cleanest explicit contract, while cron inheritance from `tools.subagents.tools` is a plausible lower-surface alternative.

- `impact:message-loss`: The reported cron announce path can duplicate visible messages when the agent also sends directly through the message tool.

## Summary

Keep open: current main and the latest release still provide per-job cron `toolsAllow` and delivery safeguards, but not the requested system-wide cron tool policy or cron inheritance from `tools.subagents.tools`.

## What This Changes

The issue requests a `tools.cron.tools.deny` policy, or equivalent inheritance, so isolated cron jobs can be denied tools such as `message` at configuration level.

## Best Possible Solution

Keep this open for maintainer-approved cron tool-policy design that either adds `tools.cron.tools.allow/deny` or explicitly defines inheritance, with schema/types/docs and regression coverage for delivery/message behavior.

Options:

- **Add cron-scoped policy (recommended):** Add `tools.cron.tools.allow/deny`, define precedence against existing policy layers and per-job `toolsAllow`, and cover message delivery behavior in tests and docs.
- **Inherit subagent policy:** Treat isolated cron sessions as covered by `tools.subagents.tools` with explicit documentation and tests showing the shared semantics.
- **Keep per-job controls only:** Decline a global cron policy and document `--tools` plus delivery safeguards as the supported mitigation for duplicate or unsafe message sends.

Yes at source level: schemas/types lack `tools.cron.tools`, and runtime policy applies `tools.subagents.tools` only to subagent envelopes while cron uses per-job `toolsAllow`.

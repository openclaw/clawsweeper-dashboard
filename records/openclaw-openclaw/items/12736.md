## Summary

Keep open: current main and the latest release still lack a cron-scoped tool deny policy or inheritance from `tools.subagents.tools`; the remaining work is a security-sensitive config and precedence decision, not conservative cleanup.

## What This Changes

The issue requests a system-wide cron tool restriction surface, such as `tools.cron.tools.deny`, so isolated cron jobs cannot call tools like `message` unless allowed.

## Best Possible Solution

Keep this open for a maintainer-approved cron tool-policy design that defines cron allow/deny or explicit inheritance, precedence against existing policy layers and per-job `toolsAllow`, docs/schema updates, and regression coverage for announce delivery.

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two different execution modes.
- **Keep per-job only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, documentation, and delivery-mode safeguards for scheduled runs.

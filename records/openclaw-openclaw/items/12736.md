## Summary

Keep this open: current main and the latest release still lack a system-wide cron-scoped tool deny policy, while the existing mitigations are per-job `toolsAllow` plus cron delivery safeguards.

## What This Changes

The issue requests a system-wide cron-scoped tool deny policy such as `tools.cron.tools.deny` so scheduled agent turns can be prevented from calling tools like `message` directly.

## Best Possible Solution

Keep the issue open for a maintainer-approved cron tool-policy design with explicit precedence, schema/types/help/docs coverage, and regression tests for isolated cron message-tool denial across delivery modes.

Question: Should cron jobs get their own `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or keep the current per-job `toolsAllow` model with delivery safeguards?

Rationale: This choice defines a new or changed security-sensitive config boundary for autonomous scheduled runs, so automation should not choose the default or precedence semantics.

Likely owner: steipete

Owner reason: steipete has the strongest recent history across cron/session policy surfaces and already reviewed this issue's remaining policy question.

Owner confidence: high

Options:

- **Add cron-scoped policy (recommended):** Introduce a first-class cron tool-policy layer with explicit precedence against existing tool policies and per-job `toolsAllow`.
- **Inherit subagent policy:** Reuse `tools.subagents.tools` for cron runs, reducing config surface but coupling different execution modes.
- **Keep per-job only:** Do not add global cron policy and rely on `payload.toolsAllow`, docs, and delivery-mode safeguards.

## Reproduction Assessment

Yes at source level: current schemas, exported types, docs, and runtime policy resolution still lack `tools.cron.tools`, while per-job `toolsAllow` remains the only cron-specific tool restriction path inspected.

## Solution Assessment

Unclear until maintainers choose the product and security direction; a cron-scoped policy is the cleanest likely shape, but the final design must define precedence and default behavior.

## Summary

Keep open: current main still lacks a cron-scoped tool policy such as `tools.cron.tools.allow/deny`, and announce cron runs still intentionally keep the `message` tool available; the remaining work is a security-sensitive product/config decision rather than a closeable duplicate or already-implemented request.

## What This Changes

Request a cron-scoped tool restriction config, or equivalent cron inheritance from subagent tool policy, so isolated cron jobs can be prevented from using tools such as `message`.

## Best Possible Solution

Maintainers should settle a typed cron tool-policy contract, or explicitly decide to rely on per-job `toolsAllow` plus delivery safeguards, then update schema/types/docs and add regression coverage for message-tool denial across cron delivery modes.

Rationale: This choice defines a public config and authorization boundary for scheduled automation, including whether existing cron jobs keep today’s message-tool behavior or become subject to a new inherited/global deny layer.

Options:

- **Add explicit cron policy (recommended):** Add a typed cron policy layer with deny-wins precedence against existing tool policy layers and per-job `toolsAllow`, plus docs and regression tests.
- **Rely on per-job allowlists:** Keep the existing `payload.toolsAllow` / `openclaw cron --tools` path as the supported hard restriction and document that cron does not inherit subagent policy.
- **Inherit subagent policy:** Treat cron like delegated execution by applying `tools.subagents.tools`, accepting the compatibility risk for existing scheduled jobs.

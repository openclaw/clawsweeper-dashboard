## Summary

Keep open: current main and the latest release still do not expose a system-level cron tool policy such as `tools.cron.tools.allow/deny`; the current controls are per-job `toolsAllow`, subagent-only policy, sandbox policy, and delivery-mode prompt handling, which do not fully solve the requested cron-wide deny boundary.

## What This Changes

The issue requests a cron-scoped tool deny policy so isolated cron jobs can be prevented from calling tools such as `message` directly.

## Best Possible Solution

Have maintainers choose a cron tool-policy model, then implement `tools.cron.tools.allow/deny` or explicit cron inheritance with schema/types/help/docs, precedence tests, and cron message-delivery regression coverage.

## Reproduction Assessment

Yes, source inspection reproduces the reported policy gap: cron sessions are distinct from subagents, and current policy resolution has no `tools.cron.tools` layer. The duplicate-message symptom also has sanitized release-era evidence, but I did not perform a live cron run in this read-only sweep.

## Solution Assessment

Unclear until maintainers choose the policy shape. A cron-scoped policy is plausible, but the best fix must define precedence with existing tool policy layers and per-job `toolsAllow` rather than adding a one-off deny check.

## Summary

Keep open: current main and the latest release still lack a cron-scoped tool policy such as `tools.cron.tools.allow/deny`; per-job `toolsAllow` and announce/message delivery safeguards are useful partial controls, but they do not provide the requested system-level cron deny policy.

## What This Changes

Request a cron-scoped tool policy such as `tools.cron.tools.deny` or cron inheritance from `tools.subagents.tools` so scheduled isolated agent runs can block tools like `message`.

## Best Possible Solution

Keep this as the cron-scoped policy tracker until maintainers choose either explicit `tools.cron.tools.allow/deny` or documented cron inheritance from subagent policy, with schema/types/help/docs alignment, precedence rules, upgrade behavior, and regression coverage.

Yes for the missing capability from source inspection: current main has no `tools.cron.tools` config surface and cron sessions do not enter the subagent policy path. I did not run a live cron job in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product/security shape. `tools.cron.tools.deny` is plausible, but the best implementation must define precedence against existing policy layers, per-job `toolsAllow`, and announce/message delivery behavior.

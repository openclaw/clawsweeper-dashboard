## Summary

Keep open: current main and the latest release still lack a cron-scoped allow/deny policy or inheritance from `tools.subagents.tools`; this is a real security-sensitive config/product decision, not cleanup.

## What This Changes

Request a `tools.cron.tools.deny` configuration option, or equivalent inheritance, so isolated cron jobs can be restricted from tools such as `message` at system policy level.

## Best Possible Solution

Keep this open until maintainers approve a cron tool-policy design that defines cron allow/deny or explicit inheritance, precedence, schema/types/help/docs updates, and regression coverage for announce and direct delivery.

Rationale: The answer defines a scheduled-run tool-access boundary and public config/default contract, including how hard denies interact with existing policy layers and current cron jobs that use direct delivery.

Likely owner: steipete

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface while coupling different execution modes.
- **Keep per-job only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, documentation, and delivery-mode safeguards.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow`.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

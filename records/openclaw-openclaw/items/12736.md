## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped hard tool allow/deny policy, and the issue discussion includes concrete duplicate-message evidence that per-job `toolsAllow` does not replace an operator-wide cron deny rule.

## What This Changes

Requested addition of a cron-scoped tool deny policy so scheduled isolated cron jobs can be prevented from using tools such as `message` without relying on prompts or per-job allow-lists.

## Best Possible Solution

Add or explicitly decline a cron-owned hard tool policy after defining precedence for global/agent/provider/group/sandbox/subagent policy layers, per-job `toolsAllow`, default creator caps, and CLI-backed runtimes.

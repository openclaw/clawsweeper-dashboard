## Summary

Keep open: current main and the latest release still lack a cron-scoped hard tool policy, and the existing per-job `toolsAllow` plus announce duplicate-suppression behavior does not replace an operator-configured cron deny layer.

## What This Changes

The issue requests a `tools.cron.tools.deny` policy, or explicit cron inheritance from existing tool policy, so cron jobs can be prevented from using tools such as `message`.

## Best Possible Solution

Define a cron-owned tool-policy layer, or an explicit inheritance rule, then align schema/types/help/docs/generated config metadata and add focused coverage for `message` denial across isolated announce, webhook, none, embedded, and CLI-backed runs.

Rationale: This changes a security-sensitive public config surface and policy precedence across cron delivery, per-job `toolsAllow`, and backend-specific enforcement, so automation should not choose the permanent contract alone.

Options:

- **Add cron-scoped policy (recommended):** Add `tools.cron.tools.allow/deny` with documented precedence and tests for embedded and CLI-backed cron behavior.
- **Inherit subagent policy:** Treat isolated cron runs as covered by `tools.subagents.tools`, reducing config surface but coupling two different execution concepts.
- **Keep per-job toolsAllow only:** Avoid a new global config surface but leave operators without a hard cron-wide deny for tools such as `message`.

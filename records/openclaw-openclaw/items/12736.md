- `impact:security`: The request is about hard enforcement of which tools scheduled cron agents may access, rather than relying on prompt instructions.

## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped hard tool allow/deny policy, while the issue has concrete security and duplicate-message evidence that per-job `toolsAllow` does not replace an operator-wide cron default.

## What This Changes

The issue requests a cron-scoped hard tool restriction policy such as `tools.cron.tools.deny` or explicit inheritance from subagent tool policy.

## Best Possible Solution

Keep this issue open for a maintainer-approved cron hard tool-policy design: preferably an explicit `tools.cron.tools.allow/deny` layer, or a documented inheritance rule, with clear precedence and regression coverage for isolated cron delivery/message-tool behavior.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a first-class hard tool policy for cron jobs, and should that be an explicit `tools.cron.tools.allow/deny` layer or inheritance from `tools.subagents.tools`?

Rationale: This chooses a public config contract and security boundary for scheduled automation, including how it composes with existing policy layers and per-job `toolsAllow`, so automation should not pick the permanent semantics.

Likely owner: steipete

Owner reason: steipete has the strongest recent history across the config/tool-policy files and the prior maintainer-facing review for this issue.

Owner confidence: high

Options:

- **Add Explicit Cron Tool Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence, schema/types/help/docs metadata, and tests for message-tool denial across cron delivery modes.
- **Make Cron Inherit Subagent Policy:** Treat cron sessions as part of the existing subagent policy path, which avoids another config block but may blur two different runtime identities.
- **Keep Only Per-Job `toolsAllow`:** Decline a global cron default and document per-job `--tools` as the supported enforcement mechanism, accepting that operators must configure each job separately.

## Reproduction Assessment

Yes, at source level. Current main has no cron-scoped tool-policy schema/type/docs surface, and cron sessions do not enter the subagent-policy branch; I did not run a live cron job in this read-only review.

## Solution Assessment

Unclear until maintainers choose the security contract. An explicit cron-scoped policy looks cleaner than implicit subagent inheritance, while per-job `toolsAllow` is not enough for the requested operator-wide default.

## Summary

Keep open: current `main` and `v2026.6.11` still lack a cron-scoped tool policy, and the existing per-job `toolsAllow` plus cron message-delivery safeguards do not provide the requested central deny config.

## What This Changes

The issue requests a cron-scoped tool deny policy, such as `tools.cron.tools.deny`, so scheduled isolated jobs can be prevented from using tools like `message`.

## Best Possible Solution

Keep this open for a focused maintainer product/security decision, then implement either `tools.cron.tools.allow/deny` or explicit cron inheritance with schema/types/docs and regression coverage for announce delivery and per-job `toolsAllow` precedence.

## Reproduction Assessment

Yes, by source inspection: current schemas and exported config types lack a cron-scoped tool policy, and cron execution only forwards per-job `toolsAllow`. I did not run a live cron job because this review is read-only.

## Solution Assessment

No current implementation is the complete solution; per-job `--tools` and direct-fallback suppression are useful mitigations, but they do not provide central cron deny enforcement. The best fix is a maintainer-approved cron policy layer or explicit inheritance rule with precedence tests.

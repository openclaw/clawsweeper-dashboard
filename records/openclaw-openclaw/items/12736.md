## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool deny policy or inheritance from `tools.subagents.tools`; the remaining work is a security-sensitive config and precedence decision, not conservative cleanup.

## What This Changes

The issue requests a system-level cron tool restriction such as `tools.cron.tools.deny`, or explicit cron inheritance from `tools.subagents.tools`, so scheduled isolated jobs can be prevented from using tools like `message`.

## Best Possible Solution

Keep this open for a maintainer-approved cron tool-policy design that defines cron allow/deny or explicit inheritance, precedence against existing policy layers and per-job `toolsAllow`, schema/docs updates, and regression coverage for announce delivery.

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface while coupling two different execution modes.
- **Keep per-job only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, documentation, and delivery-mode safeguards for scheduled runs.

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

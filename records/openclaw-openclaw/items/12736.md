## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool allow/deny policy or explicit cron inheritance from `tools.subagents.tools`, and the issue now has sanitized duplicate-message evidence for cron announce delivery.

## What This Changes

Add a cron-scoped tool policy, or make isolated cron sessions inherit subagent tool restrictions, so scheduled jobs can hard-block tools such as `message`.

## Best Possible Solution

Approve a cron tool-policy contract with explicit precedence, schema/types/docs metadata, and regression coverage for isolated cron message denial across delivery modes.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should isolated cron jobs get first-class `tools.cron.tools.allow/deny`, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: This defines a scheduled-run tool-access boundary and public config contract, and the wrong default could either leave autonomous cron jobs overpowered or break existing direct-message cron workflows.

Likely owner: steipete

Owner reason: steipete has the strongest recent history around the scoped conversation policy foundation that would host this decision.

Owner confidence: high

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence and tests for message denial across cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution applies `tools.subagents.tools` only to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

## Summary

Keep open: current main and latest v2026.6.11 still lack a cron-scoped `tools.cron.tools.allow/deny` policy or explicit inheritance from `tools.subagents.tools`; the remaining work is a security-sensitive config and product decision, not stale cleanup.

## What This Changes

The issue requests a cron-scoped tool deny policy so isolated cron jobs can be blocked from directly using tools like `message`.

## Best Possible Solution

Approve a cron tool-policy contract only after maintainers choose cron-specific config versus subagent inheritance versus per-job-only policy, then align schema/types/docs/config metadata and add regression coverage for announce and direct `message` behavior.

Question: Should OpenClaw add a first-class cron-scoped tool policy, make cron inherit subagent policy, or keep per-job `payload.toolsAllow` as the only hard cron tool boundary?

Rationale: The choice defines a public config surface and scheduled-automation security boundary, including whether existing announce jobs keep direct `message` access by default.

Likely owner: steipete

Owner confidence: high

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` or an equivalent typed cron policy with explicit precedence, docs, config metadata, migration/default behavior, and tests for announce/message behavior.
- **Inherit subagent policy:** Treat isolated cron sessions as policy peers of subagents so `tools.subagents.tools` applies to cron, accepting the coupling and documenting the shared behavior.
- **Keep per-job only:** Decline a global cron config surface and document that operators must use per-job `payload.toolsAllow` or runtime/prompt safeguards for cron restrictions.

## Reproduction Assessment

Yes, at source level: current main has per-job `payload.toolsAllow` plus subagent/sandbox policy wrappers, but no cron-scoped allow/deny config or cron inheritance path. I did not run a live cron job in this read-only review.

## Solution Assessment

Unclear until maintainers choose the policy shape. A cron-specific allow/deny config is plausible, but inheritance from subagent policy or staying with per-job `toolsAllow` are product/security choices with different upgrade behavior.

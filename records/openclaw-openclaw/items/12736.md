## Summary

Keep open: current main and the latest release still do not provide `tools.cron.tools.allow/deny` or explicit inheritance from `tools.subagents.tools`, so the requested cron tool boundary remains a security-sensitive product/config decision.

## What This Changes

The issue requests a system-wide cron job tool restriction policy, either as `tools.cron.tools.deny` or by inheriting `tools.subagents.tools`.

## Best Possible Solution

Approve and implement a cron-scoped tool-policy contract with explicit precedence, schema/types/help/label/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Rationale: This choice defines a public security/config contract and default behavior for scheduled autonomous runs, including whether existing announce-mode cron jobs that directly use `message` keep working by default.

Likely owner: steipete

Owner confidence: high

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against global, sender, sandbox, subagent, inherited, and per-job policies.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface while coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level: current schema/types lack `tools.cron.tools`, and current policy resolution only applies subagent policy to subagent envelopes while cron relies on per-job `toolsAllow`.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy appears cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

## Label Justifications

- `impact:security`: The issue asks for hard enforcement of tool access for autonomous scheduled runs instead of prompt-only guidance.
- `impact:message-loss`: The reported use case can duplicate or misroute visible messages when direct `message` sends and announce delivery both fire.

## Summary

Keep open: current main still has per-job cron `toolsAllow` and delivery safeguards, but no cron-scoped `tools.cron.tools.allow/deny` policy and no inheritance from `tools.subagents.tools`, so the requested security boundary remains unresolved.

## What This Changes

The issue requests a system-level cron tool policy, such as `tools.cron.tools.deny`, so isolated scheduled runs can be restricted without relying on prompt instructions or per-job allowlists.

## Best Possible Solution

Approve a cron-scoped tool-policy contract, preferably `tools.cron.tools.allow/deny`, with explicit precedence, schema/types/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should isolated cron jobs get first-class `tools.cron.tools.allow/deny`, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: The choice defines a public scheduled-run tool-access boundary with security, delivery, and config-upgrade implications, so automation should not choose the default or precedence contract.

Likely owner: steipete

Owner reason: steipete has the strongest current history across cron runtime work and this exact policy discussion.

Owner confidence: high

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence against existing policy layers and per-job `toolsAllow`.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two execution modes with different semantics.
- **Keep per-job policy only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the security boundary. A cron-scoped policy appears cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

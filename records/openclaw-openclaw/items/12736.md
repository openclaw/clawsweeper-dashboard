- `P2`: The issue is a bounded security/tool-policy improvement for cron runs with meaningful impact but no evidence of a current P0/P1-wide outage.
- `impact:security`: The request is about denying a tool capability from scheduled runs and preventing unintended message-send authority.
- `impact:message-loss`: The reported failure mode includes unwanted or duplicate scheduled messages caused by cron runs retaining the message tool.

## Summary

Keep open: current main and the latest inspected release still lack a cron-scoped tool deny policy or cron inheritance from subagent tool policy, while the existing per-job `toolsAllow` and message-delivery safeguards only partially address the reported duplicate-message/tool-exposure risk.

## What This Changes

Request a cron-scoped tool restriction config such as `tools.cron.tools.deny`, or explicit cron inheritance from subagent tool policy, so scheduled runs can deny tools like `message`.

## Best Possible Solution

Define a maintainer-approved cron tool-policy model with explicit precedence, schema/types/docs, upgrade behavior, and regression coverage before changing runtime inheritance semantics.

- **Keep current model:** Leave cron with per-job `--tools` / `toolsAllow` and delivery safeguards only, and document that cron does not have a cron-wide deny policy.

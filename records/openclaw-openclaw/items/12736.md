## Summary

Keep open: current main and v2026.6.11 still do not provide a cron-scoped tool deny policy, and cron sessions do not inherit the subagent tool-policy path; the issue remains a valid security/product configuration request.

## What This Changes

The issue requests a `tools.cron.tools.deny` policy, or explicit cron inheritance from `tools.subagents.tools`, so isolated cron jobs can be restricted from tools such as `message`.

## Best Possible Solution

Define a maintainer-approved cron tool-policy contract, preferably explicit `tools.cron.tools.allow/deny`, with clear precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Question: Should isolated cron runs get an explicit `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or continue relying on per-job `toolsAllow` plus delivery safeguards?

Rationale: This chooses a public config surface and security boundary for scheduled automation, including how cron message delivery interacts with tool authorization and existing policy layers.

Likely owner: steipete

Owner reason: steipete has the strongest recent history on the centralized capability-profile policy path and previously reviewed this exact cron policy gap.

Owner confidence: high

Options:

- **Add explicit cron policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence over or under per-job `toolsAllow`, and test message-tool denial for announce, none, and webhook modes.
- **Inherit subagent policy:** Treat cron isolated sessions as sharing `tools.subagents.tools`, reducing config surface but coupling two session classes with different delivery semantics.
- **Keep per-job only:** Document per-job `toolsAllow` as the supported restriction path and avoid a global cron config knob, accepting that operators must configure each cron job.

## Reproduction Assessment

Yes for the config gap: current main lacks `tools.cron.tools` and only applies subagent policy when the session is a subagent envelope. I did not run a live duplicate-message cron repro in this read-only review.

## Solution Assessment

Unclear until maintainers decide the policy boundary. An explicit cron-scoped policy looks cleaner than overloading subagent policy, but the final shape must define precedence with per-job `toolsAllow` and delivery fallback behavior.

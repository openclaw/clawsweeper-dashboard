- `impact:message-loss`: The reported `message` tool use case can produce duplicated or misrouted visible messages when direct sends and announce delivery both fire.

## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped `tools.cron.tools.allow/deny` policy or explicit inheritance from `tools.subagents.tools`; only per-job `toolsAllow` and delivery safeguards exist, so the remaining work is a security-sensitive config/product decision.

## What This Changes

Request to add a cron-scoped tool deny policy, or cron inheritance from subagent policy, so scheduled isolated agent jobs can be restricted system-wide.

## Best Possible Solution

Approve and implement a cron-scoped tool-policy contract with explicit precedence, schema/types/help/label/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should isolated cron jobs get a first-class `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: This chooses the scheduled-run tool-access boundary and public config contract, including whether existing announce-mode cron jobs that directly use `message` keep working by default.

Likely owner: steipete

Owner reason: He has the strongest combined signal from recent cron config/runtime work and prior review context for this issue.

Owner confidence: high

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level: current schema/types lack `tools.cron.tools`, and current policy resolution only applies subagent policy to subagent envelopes while cron relies on per-job `toolsAllow`.

## Solution Assessment

Unclear until maintainers choose the security and product direction; a cron-scoped policy looks cleaner than overloading subagent semantics, but precedence and upgrade behavior must be decided first.

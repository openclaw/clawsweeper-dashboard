## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool policy or explicit inheritance from subagent tool policy, so the requested hard cron tool boundary remains unresolved and needs maintainer direction.

## What This Changes

The issue requests a `tools.cron.tools.deny` config option, or equivalent subagent-policy inheritance, so cron jobs can be prevented from using tools such as `message` directly.

## Best Possible Solution

Approve and implement a narrow cron tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should isolated cron jobs get a first-class `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: This choice defines a scheduled-run tool-access boundary and public config/default contract, including compatibility for cron jobs that currently send direct messages.

Likely owner: steipete

Owner reason: `steipete` has the strongest current history across the policy resolver, schema surface, and recent cron runtime work.

Owner confidence: high

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence and tests for message-tool denial across cron delivery modes.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two execution modes.
- **Keep per-job policy only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

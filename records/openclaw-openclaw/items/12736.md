## Summary

Keep open: current main still lacks a cron-scoped tool deny policy or explicit inheritance from subagent policy, so this remains a security-sensitive config design choice rather than cleanup.

## What This Changes

Add a system-level cron tool restriction config, or cron inheritance from subagent tool policy, so scheduled jobs can be prevented from using tools such as `message`.

## Best Possible Solution

Keep this open until maintainers approve cron-scoped policy semantics, update schema/types/docs, and add regression coverage for message-tool denial across cron delivery modes.

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface while coupling two different execution modes.
- **Keep per-job only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, documentation, and delivery-mode safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow`.

## Solution Assessment

Unclear until maintainers choose the boundary. `tools.cron.tools.allow/deny` is the cleanest explicit contract, while cron inheritance from `tools.subagents.tools` is a plausible lower-surface alternative.

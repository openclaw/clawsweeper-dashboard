## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool allow/deny policy or explicit inheritance from subagent policy, so this remains a security-sensitive config/product decision rather than conservative cleanup.

## What This Changes

The issue asks for `tools.cron.tools.deny` or equivalent inheritance so isolated cron jobs can be restricted from tools such as `message` at the system policy layer.

## Best Possible Solution

Approve a cron-scoped tool-policy contract only after maintainers settle precedence, default behavior, docs/schema/type updates, and regression coverage for message-tool denial across cron delivery modes.

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface while coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

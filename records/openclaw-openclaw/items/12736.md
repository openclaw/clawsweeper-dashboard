## Summary

Keep open: current main still lacks a cron-scoped tool policy or documented cron inheritance from `tools.subagents.tools`, and the remaining work is a security-sensitive config/product decision rather than stale cleanup.

## What This Changes

The issue requests a system-level `tools.cron.tools.deny` policy, or equivalent cron inheritance, so scheduled cron agent turns can be prevented from calling selected tools such as `message`.

## Best Possible Solution

Have maintainers choose the cron tool-policy model, then implement either `tools.cron.tools.allow/deny` or explicit cron inheritance with schema/types/help/docs and focused tests for policy precedence plus cron message-delivery behavior.

## Reproduction Assessment

Yes. Source inspection reproduces the policy gap: current main has no `tools.cron.tools` schema/type/runtime layer, while cron still relies on per-job `toolsAllow` and delivery handling.

## Solution Assessment

Unclear until maintainers choose the policy shape. A cron-scoped policy is plausible, but the best fix must define precedence with existing tool-policy layers and per-job `toolsAllow` rather than adding a one-off deny check.

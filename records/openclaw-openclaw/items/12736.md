## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool allow/deny policy or cron inheritance from subagent tool policy; the remaining work is a maintainer security/product decision about scheduled-run tool precedence.

## What This Changes

Request to add a cron-scoped tool allow/deny policy, or make cron sessions inherit subagent tool policy, so scheduled runs can be restricted from tools such as `message`.

## Best Possible Solution

Add a maintainer-approved cron tool-policy contract with clear precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

## Maintainer Decision

Kind: security_boundary

Question: Should cron jobs get their own `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or remain controlled only by per-job `toolsAllow` plus delivery safeguards?

Rationale: The choice defines a scheduled-run tool-execution boundary and a new public config contract, so automation should not choose the permanent precedence or compatibility behavior.

Likely owner: steipete

Owner reason: Prior issue review plus recent cron/scoped-capability history make `steipete` the best available owner for this policy choice.

Owner confidence: high

Options:

- **Add Cron-Specific Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against existing policy layers and per-job `toolsAllow`, then document and test upgrade behavior.
- **Inherit Subagent Policy:** Treat isolated cron sessions as covered by `tools.subagents.tools`, reducing config surface but coupling cron and subagent semantics.
- **Keep Current Safeguards:** Leave control to per-job `toolsAllow` and delivery-mode safeguards, keeping config smaller while leaving the requested operator deny boundary unsolved.

## Reproduction Assessment

Yes. Source inspection reproduces the feature gap: current main has subagent, sandbox, global, group, sender, inherited, and per-job tool policy paths, but no cron-scoped policy path.

## Solution Assessment

Unclear until maintainers choose the boundary. A cron-specific `tools.cron.tools.allow/deny` contract is the cleanest explicit solution, while inheriting subagent policy is a plausible lower-surface alternative.

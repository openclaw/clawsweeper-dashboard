## Label Justifications

- `P2`: This is a normal-priority security/control improvement for cron automation with limited blast radius and no evidence of an emergency runtime outage.
- `impact:security`: The request controls whether scheduled runs can access powerful tools such as `message`, `exec`, or `tts`.
- `impact:message-loss`: The motivating evidence is duplicated visible cron output when an announce run can also use the `message` tool directly.

## Summary

Keep open: current main and latest v2026.6.11 still lack a cron-scoped tool allow/deny policy or cron inheritance from `tools.subagents.tools`; existing per-job `toolsAllow` and message-delivery safeguards do not provide the requested operator-enforced cron tool boundary.

## What This Changes

Request a `tools.cron.tools.deny`-style configuration surface, or cron inheritance from `tools.subagents.tools`, so isolated cron jobs can be restricted from tools such as `message` and `tts`.

## Best Possible Solution

Add a maintainer-approved cron tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add an explicit `tools.cron.tools.allow/deny` policy, make cron inherit `tools.subagents.tools`, or keep cron control limited to per-job `toolsAllow` and delivery safeguards?

Rationale: The choice defines a scheduled-run tool-execution boundary and a new public config contract, so automation should not choose the permanent security semantics or compatibility behavior without maintainer intent.

Likely owner: steipete

Owner reason: steipete has the strongest prior review and cron-runtime routing history for this exact policy decision.

Owner confidence: high

Options:

- **Add cron-specific policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence against global, agent, group, sandbox, subagent, inherited, and per-job `toolsAllow` policy.
- **Inherit subagent policy:** Treat isolated cron sessions as covered by `tools.subagents.tools`, reducing config surface but coupling cron and subagent semantics.
- **Keep current safeguards:** Continue relying on per-job `toolsAllow` plus delivery-mode safeguards, preserving today’s config surface while leaving this operator-wide deny request unsolved.

## Reproduction Assessment

Yes, as source-level feature-gap proof: current schemas, exported types, docs, and runtime policy resolution contain subagent/sandbox/per-job policy paths but no cron policy path. The May 19 sanitized v2026.5.18 comment also gives real-world duplicate-message evidence for the motivating risk.

## Solution Assessment

Unclear until maintainers choose the boundary. `tools.cron.tools.allow/deny` is the cleanest explicit contract, but cron inheritance from `tools.subagents.tools` is a plausible lower-surface alternative.

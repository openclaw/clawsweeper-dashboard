## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool policy or inheritance from `tools.subagents.tools`, so the requested hard deny boundary remains a security-sensitive product/config decision rather than conservative cleanup.

## What This Changes

The issue requests a system-level cron tool restriction such as `tools.cron.tools.deny` so isolated cron jobs can be prevented from using tools like `message`.

## Best Possible Solution

Approve and implement a cron-scoped tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Question: Should isolated cron jobs get a first-class `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: This choice defines a hard tool-access boundary for scheduled autonomous runs and a public config/default contract, including compatibility for cron jobs that currently send direct messages.

Likely owner: steipete

Owner reason: `steipete` has the strongest current history across scoped capability profiles and recent cron runtime work.

Owner confidence: high

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence and tests for message-tool denial across cron delivery modes.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two execution modes.
- **Keep per-job policy only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level: current schema/types lack `tools.cron.tools`, and current policy resolution only applies subagent policy to subagent envelopes while cron relies on per-job `toolsAllow`.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy appears cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

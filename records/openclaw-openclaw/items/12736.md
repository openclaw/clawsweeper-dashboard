## Summary

Keep open: current main and v2026.6.11 still lack a system-wide cron-scoped tool deny policy or inheritance from `tools.subagents.tools`; the existing per-job `toolsAllow` and message-delivery safeguards are useful but do not satisfy the requested operator-level boundary.

## What This Changes

The issue requests a `tools.cron.tools.deny` config option, or equivalent cron inheritance from subagent tool policy, to restrict tools in isolated cron jobs.

## Best Possible Solution

Approve a cron-specific tool-policy design that keeps per-job `toolsAllow` intact, adds or rejects a global cron allow/deny layer explicitly, documents precedence, and tests message-tool denial across cron delivery modes.

Question: Should isolated cron jobs get a first-class `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: This defines a scheduled autonomous-run tool-access boundary and public config contract, so automation should not choose the default or precedence semantics without maintainer intent.

Likely owner: steipete

Owner reason: steipete has the strongest combined signal from prior issue review plus recent cron runner and scoped policy foundation work.

Owner confidence: high

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against existing policy layers and per-job `toolsAllow`.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions as well, reducing config surface but coupling distinct execution modes.
- **Keep per-job only:** Avoid new global config and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow`.

## Solution Assessment

Unclear until maintainers choose the security boundary. A cron-scoped policy is the cleanest fit for this report, but the implementation must define precedence and upgrade behavior before a fix PR is safe.

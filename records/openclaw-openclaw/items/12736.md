## Summary

Keep open: current main still lacks a cron-scoped tool deny config or cron inheritance from `tools.subagents.tools`, and the remaining behavior is per-job `toolsAllow` plus delivery safeguards rather than the requested enforceable policy surface.

## What This Changes

Request a cron-scoped tool-policy config such as `tools.cron.tools.deny`, or cron inheritance from `tools.subagents.tools`, so isolated scheduled runs can enforce message/tool restrictions.

## Best Possible Solution

Keep this as the cron-scoped policy tracker until maintainers choose explicit `tools.cron.tools.allow/deny` or documented cron inheritance with precedence, docs, schema/type coverage, upgrade guidance, and regression tests.

## Reproduction Assessment

Yes, for the source-level gap: current main has no `tools.cron.tools` config surface and cron sessions do not enter the subagent policy layer. No live cron run was executed because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the product/security shape. `tools.cron.tools.deny` is plausible, but the maintainable solution must define precedence against existing policy layers and per-job `toolsAllow` before implementation.

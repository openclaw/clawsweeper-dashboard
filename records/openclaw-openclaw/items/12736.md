## Summary

Keep open: current main still lacks a cron-scoped tool policy such as `tools.cron.tools.allow/deny`, and the related open issues do not supersede this narrower security and message-delivery request.

## What This Changes

Requests a system-level cron tool restriction policy, such as `tools.cron.tools.deny` or inheritance from `tools.subagents.tools`, to prevent scheduled jobs from directly using tools like `message`.

## Best Possible Solution

Approve a cron-scoped tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Solution Assessment

Unclear until maintainers choose the product and security direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

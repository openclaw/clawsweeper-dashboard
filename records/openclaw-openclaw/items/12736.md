## Label Justifications

- `P2`: The issue describes meaningful cron hardening, but it is a bounded product/config decision rather than an urgent outage.
- `impact:security`: The issue asks for a hard tool-access boundary for autonomous scheduled runs.
- `impact:message-loss`: The reported message-tool use case can duplicate or misroute visible messages when direct sends and announce delivery both occur.

## Summary

Keep open: current main still lacks `tools.cron.tools.allow/deny` and does not make cron sessions inherit `tools.subagents.tools`; the request remains a security-sensitive public config/default decision rather than conservative cleanup.

## What This Changes

Request a first-class cron tool deny policy so isolated cron jobs cannot access tools such as `message` when operators need hard routing safeguards.

## Best Possible Solution

Approve and implement a cron-scoped tool-policy contract, or deliberately choose subagent inheritance, with explicit precedence and tests for message-tool denial across cron delivery modes.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should isolated cron jobs get first-class `tools.cron.tools.allow/deny`, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: The choice creates a public security/config boundary for scheduled runs and may change existing announce-mode cron behavior that currently can use the `message` tool directly.

Likely owner: steipete

Owner reason: He has the strongest combined signal from scoped capability/tool-policy ownership and prior review context for this issue.

Owner confidence: high

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and focused tests for isolated cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface while coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on job `toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types/docs still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron uses per-job `toolsAllow` and delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the policy shape. A cron-specific allow/deny config is plausible, but inheritance from subagent policy or staying with per-job `toolsAllow` are product/security choices with different upgrade behavior.

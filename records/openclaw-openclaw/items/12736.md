## Summary

Keep open: current main has per-job cron `toolsAllow` handling and message-delivery guidance, but it still lacks a system-wide cron-scoped tool policy such as `tools.cron.tools.allow/deny` and cron sessions still do not inherit `tools.subagents.tools`.

## What This Changes

Request a cron-scoped tool policy, such as `tools.cron.tools.deny` or cron inheritance from subagent tool policy, to restrict tools available to isolated cron jobs.

## Best Possible Solution

Approve an explicit cron tool-policy contract, then implement schema/types/docs/runtime precedence and regression coverage for announce-mode message denial without weakening per-job `toolsAllow` or existing deny/sandbox gates.

Question: Should cron jobs get their own tool-policy layer, and should that layer be an explicit `tools.cron.tools.allow/deny` contract or inheritance from `tools.subagents.tools`?

Rationale: This decides a new security/default boundary for scheduled automation and message delivery, including upgrade behavior for existing cron jobs that may intentionally use `message`.

Likely owner: steipete

Owner reason: steipete has the strongest current-history signal across the config/tool-policy paths and prior review context for this security-sensitive cron policy decision.

Owner confidence: medium

Options:

- **Add explicit cron policy (recommended):** Define `tools.cron.tools.allow/deny` with documented precedence against existing policy layers and per-job `toolsAllow`, then add focused cron/message-delivery tests.
- **Inherit subagent policy:** Treat cron sessions as inheriting `tools.subagents.tools`, accepting the compatibility risk that existing scheduled jobs may lose tools under a policy originally named for subagents.
- **Keep per-job policy only:** Decline the global cron config surface and document `payload.toolsAllow` plus delivery-mode guidance as the supported restriction mechanism.

## Reproduction Assessment

Yes, source-reproducible: current main has no `tools.cron.tools` schema/type/docs surface, cron sessions do not classify as subagent sessions, and the resolver applies `tools.subagents.tools` only to subagent envelopes. The May 19 comment adds sanitized release-era evidence that direct cron `message` use can duplicate announce delivery.

## Solution Assessment

Unclear until maintainers choose the policy shape. An explicit cron-scoped policy looks cleaner than subagent inheritance because cron has distinct session keys and delivery semantics, but either path needs documented precedence and upgrade tests.

## Summary

Keep open: current main still lacks a cron-scoped deny or inheritance config, and the remaining work is a security-sensitive public config/product decision; current code only offers per-job `payload.toolsAllow` plus creator-surface capping.

## What This Changes

Request adding cron-scoped tool restrictions, such as `tools.cron.tools.deny`, so isolated cron jobs cannot call tools like `message` directly.

## Best Possible Solution

Define a first-class cron tool policy or explicit inheritance rule, enforce it consistently for embedded and CLI-backed cron runs, align schema/types/help/docs, and add regression coverage for announce-mode `message` denial.

Rationale: The implementation changes public config and a security boundary, and the wrong default could either leave scheduled jobs over-permissive or break existing cron jobs during upgrade.

Owner confidence: high

Options:

- **Add explicit cron policy (recommended):** Add `tools.cron.tools.allow/deny` with documented precedence against existing policy layers and per-job `toolsAllow`, then test embedded and CLI-backed cron behavior.
- **Inherit subagent policy:** Treat isolated cron sessions as delegated execution for tool-policy purposes, with docs explaining that `tools.subagents.tools` also governs cron jobs.
- **Keep per-job only:** Do not add a global config surface; instead document `payload.toolsAllow` and add runtime safeguards only for duplicate announce/message delivery.

## Solution Assessment

Unclear until maintainers choose the policy shape: either a cron-scoped policy or explicit subagent-policy inheritance could be maintainable. The safest solution needs documented precedence and upgrade behavior before implementation.

- `impact:security`: The issue asks for a hard tool-access boundary for autonomous scheduled runs.
- `impact:message-loss`: The reported `message` tool use case can produce duplicated or misrouted visible messages when direct sends and announce delivery both fire.

## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool deny policy or explicit inheritance from subagent tool policy. The remaining work is a security-sensitive config/product decision; current behavior is per-job `payload.toolsAllow` plus cron delivery safeguards, not a system-wide cron policy.

## What This Changes

Add a cron-scoped tool restriction policy such as `tools.cron.tools.deny`, or define cron inheritance from `tools.subagents.tools`, so isolated cron jobs can be prevented from using tools like `message`.

## Best Possible Solution

Approve a cron-scoped tool-policy contract only after maintainers define precedence, upgrade behavior, docs/schema shape, and regression coverage for isolated cron message-tool denial across delivery modes.

Options:

- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions as well, reducing config surface while coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, documentation, and delivery safeguards for scheduled runs.

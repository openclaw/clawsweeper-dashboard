## Summary

Keep open: current main still lacks a cron-scoped hard tool allow/deny policy, and the existing per-job `toolsAllow` plus announce-delivery safeguards do not replace the requested public security boundary.

## What This Changes

The issue requests a new cron-scoped tool restriction policy, such as `tools.cron.tools.deny`, or explicit inheritance from `tools.subagents.tools`.

## Best Possible Solution

Define the cron tool-policy contract first, then implement one hard enforcement path with schema, exported types, config metadata, docs, and regression coverage for isolated cron delivery modes.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should cron get a dedicated `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or wait for the broader per-session tool-policy design to define cron enforcement and precedence?

Rationale: The choice changes a public config surface and scheduled tool-execution security boundary, so automation should not decide the default guarantee, precedence rules, or relationship to per-job `toolsAllow`.

Owner confidence: high

Options:

- **Design cron policy in session-policy model (recommended):** Use the broader per-session/capability-policy direction to define cron precedence first, then add one canonical cron enforcement path with docs and tests.
- **Add a dedicated cron scope now:** Introduce `tools.cron.tools.*` as a narrow global cron policy with explicit precedence over per-job allowlists and delivery-mode behavior.
- **Document per-job tools only:** Decline a global cron policy and make per-job `--tools` plus announce-delivery safeguards the supported operator workflow.

Yes. Source inspection shows no cron-scoped policy schema or subagent-policy inheritance path for cron sessions, and the issue discussion includes a concrete duplicate-message cron example.

## Solution Assessment

Unclear as proposed. A hard cron policy is the right class of solution, but maintainers need to choose between a dedicated cron config key, subagent-policy inheritance, or a broader session-policy model before implementation.

## Summary

Keep open: current main still lacks a first-class `tools.cron.tools.allow/deny` policy or cron inheritance from `tools.subagents.tools`; existing per-job `toolsAllow` and delivery safeguards only cover narrower cases.

## What This Changes

The issue requests a cron-scoped tool restriction config, or explicit inheritance from subagent tool policy, so isolated cron jobs can be denied tools such as `message` system-wide.

## Best Possible Solution

Approve a cron-scoped tool-policy contract, preferably `tools.cron.tools.allow/deny`, with explicit precedence, schema/types/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Rationale: The choice defines a public scheduled-run tool-access boundary with security and upgrade implications, so automation should not choose the default or precedence contract.

Likely owner: steipete

Owner confidence: medium

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` or an equivalent cron-owned policy with documented precedence and focused migration/proof for existing cron jobs.
- **Inherit subagent policy:** Treat isolated cron sessions as subagent-like for tool policy, reducing new config surface but coupling cron behavior to subagent semantics.
- **Keep per-job controls only:** Leave global cron defaults unimplemented and rely on `--tools`/`payload.toolsAllow` plus delivery safeguards for every scheduled job.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent policy while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the boundary; a cron-scoped policy appears cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior.

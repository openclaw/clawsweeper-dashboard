## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped hard tool deny policy or explicit inheritance from `tools.subagents.tools`, and the remaining work is a security-sensitive config/product decision rather than conservative cleanup.

## What This Changes

Request a cron-scoped tool deny configuration so isolated cron jobs can be prevented from using tools such as `message` when operators need hard enforcement.

## Best Possible Solution

Keep this open until maintainers approve a cron tool-policy design that defines cron allow/deny or explicit inheritance, precedence, docs/schema/type updates, and regression coverage for direct-message and announce delivery behavior.

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface while coupling two different execution modes.
- **Keep per-job only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, documentation, and delivery-mode safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current main lacks `tools.cron.tools`, and current policy resolution only applies the subagent tool-policy layer to subagent envelopes while cron relies on per-job `toolsAllow`.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

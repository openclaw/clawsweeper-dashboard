## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool allow/deny policy or inheritance from `tools.subagents.tools`; the remaining work is a security-sensitive config/product decision, not conservative cleanup.

## What This Changes

The issue requests a cron-scoped tool deny option, such as `tools.cron.tools.deny`, so isolated cron jobs can be blocked from tools like `message` system-wide.

## Best Possible Solution

Approve a cron tool-policy contract that either adds explicit `tools.cron.tools.allow/deny` or intentionally inherits subagent policy, with documented precedence, upgrade behavior, schema/types/docs updates, and regression coverage for announce delivery.

Question: Should isolated cron jobs get a first-class `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: The choice defines a scheduled-run tool-access boundary and public config/default contract, including how hard denies interact with existing policy layers and existing cron jobs that use direct delivery.

Likely owner: steipete

Owner confidence: high

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions too, reducing new config surface while coupling two different execution modes.
- **Keep per-job only:** Avoid a global cron policy and rely on `payload.toolsAllow`, documentation, and delivery-mode safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current main lacks `tools.cron.tools` in schema/types and only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow`; no live cron run was executed in this read-only review.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

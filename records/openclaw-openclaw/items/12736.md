## Best Possible Solution

Add a maintainer-approved cron tool-policy contract with clear precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Options:

- **Add cron-specific policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against existing policy layers and per-job `toolsAllow`, then document and test fresh-install and upgrade behavior.
- **Inherit subagent policy:** Treat isolated cron sessions as covered by `tools.subagents.tools`, reducing config surface but coupling cron and subagent semantics.
- **Keep current safeguards:** Leave cron control to per-job `toolsAllow` and duplicate-delivery safeguards, which keeps config smaller but does not solve the requested operator deny boundary.

Yes, as source-level feature-gap proof: current schemas, exported types, docs, and runtime tool-policy resolution contain subagent/sandbox/per-job policy paths but no cron policy path.

## Solution Assessment

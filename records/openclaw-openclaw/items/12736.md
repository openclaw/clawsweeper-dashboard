## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool deny policy or explicit inheritance from subagent tool policy, while the issue includes concrete duplicate-message evidence for scheduled runs.

## What This Changes

The issue requests a cron-scoped tool allow/deny policy, or inheritance from subagent tool policy, so isolated cron jobs can be denied tools such as `message`.

## Best Possible Solution

Keep this issue open until maintainers approve a cron tool-policy design with explicit precedence, schema/types/docs updates, and regression coverage for isolated cron `message` denial across announce, none, and webhook delivery modes.

Question: Should isolated cron jobs get a first-class `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: This choice defines a scheduled-run tool-access boundary and public config/default contract, including whether existing jobs that directly use `message` under announce delivery keep working by default.

Likely owner: steipete

Owner reason: steipete has the strongest combined history across scoped capability policy and prior issue routing for this security/config decision.

Owner confidence: high

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence and tests for message denial across cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution applies `tools.subagents.tools` only to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool policy or subagent-policy inheritance for cron, while current code only provides per-job `toolsAllow` and delivery safeguards. The remaining work is security-sensitive public config/product design, not a narrow automatic bug fix.

## What This Changes

Request to add a cron-scoped tool restriction config such as `tools.cron.tools.deny`, or explicit inheritance from `tools.subagents.tools`, so cron jobs cannot call blocked tools directly.

## Best Possible Solution

Approve and implement a cron-scoped tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Rationale: This choice defines a scheduled-run tool-access boundary and public config contract, including whether existing announce-mode cron jobs that directly use `message` keep working by default.

Owner confidence: high

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, current policy resolution only applies `tools.subagents.tools` to subagent envelopes, and cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

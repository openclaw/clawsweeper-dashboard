## Summary

Keep open: current main and latest v2026.6.11 still do not provide `tools.cron.tools.allow/deny` or explicit inheritance from `tools.subagents.tools`; the remaining work is a security-sensitive config/product decision for cron tool boundaries.

## What This Changes

Request to add a cron-scoped tool restriction config, such as `tools.cron.tools.deny`, or make cron sessions inherit subagent tool restrictions.

## Best Possible Solution

Approve a cron tool-policy contract only after maintainers choose the default, precedence, migration, docs, and security posture for direct cron `message` use versus runner-owned announce delivery.

Question: Should OpenClaw add a first-class cron-scoped tool policy, make cron inherit subagent policy, or keep per-job `payload.toolsAllow` as the only hard cron tool boundary?

Rationale: This choice defines a public config surface and security boundary for scheduled automation, including whether existing announce jobs keep direct `message` access by default.

Likely owner: steipete

Owner confidence: high

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` or an equivalent typed cron policy with explicit precedence, docs, config metadata, and tests for announce/message behavior.
- **Inherit subagent policy:** Treat isolated cron sessions as a policy peer of subagents so `tools.subagents.tools` also applies to cron, accepting the broader coupling and documenting it.
- **Keep per-job only:** Decline a global cron config surface and document that operators must use per-job `payload.toolsAllow` or prompt/runtime safeguards for cron restrictions.

## Reproduction Assessment

Yes, at source level for the requested gap: current main has per-job `payload.toolsAllow` and subagent/sandbox policy wrappers, but no cron-scoped allow/deny config or cron inheritance path. I did not run a live cron job in this read-only review.

## Solution Assessment

Unclear until maintainers choose the policy shape. A cron-specific allow/deny config is plausible, but inheritance from subagent policy or staying with per-job `toolsAllow` are product/security choices with different upgrade behavior.

## Summary

Keep open: current main and the latest release still lack a cron-scoped tool allow/deny policy or cron inheritance from `tools.subagents.tools`; existing behavior is per-job `toolsAllow` plus message-delivery safeguards, which does not provide the requested operator-enforced deny boundary.

## What This Changes

Request cron-scoped tool restriction config so scheduled jobs can deny tools such as direct `message` sends.

## Best Possible Solution

Add a maintainer-approved cron tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Rationale: This choice creates a public config surface and defines the scheduled-run tool-execution security boundary, so automation should not choose the permanent precedence or compatibility behavior.

Options:

- **Add cron-specific policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence against existing policy layers and per-job `toolsAllow`, then cover fresh and upgrade behavior in tests and docs.
- **Inherit subagent policy:** Treat isolated cron sessions as covered by `tools.subagents.tools`, reducing config surface but coupling cron and delegated-subagent semantics.
- **Keep current safeguards:** Continue relying on per-job `toolsAllow` and delivery safeguards, keeping config smaller but leaving the requested operator deny boundary unsolved.

Yes, as source-level feature-gap proof: current main schemas, exported types, docs, and runtime policy resolution contain subagent/sandbox/per-job paths but no cron-scoped policy path.

## Solution Assessment

Unclear until maintainers choose the boundary. `tools.cron.tools.allow/deny` is the cleanest explicit contract, while cron inheritance from `tools.subagents.tools` is a plausible lower-surface alternative.

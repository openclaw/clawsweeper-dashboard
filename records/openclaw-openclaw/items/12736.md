- `impact:security`: The issue is about hard-enforcing which tools cron agents may use instead of relying on prompt instructions.

## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool policy or explicit cron inheritance from subagent policy, while source and tests show only per-job `payload.toolsAllow` can suppress `message` guidance today.

## What This Changes

Request a cron-scoped tool deny/allow policy, such as `tools.cron.tools.deny`, so isolated cron jobs can be restricted without relying on per-job allowlists or prompt instructions.

## Best Possible Solution

Choose one maintainer-approved cron/session tool-policy model, then implement schema/types/help/docs/runtime/tests so operators can deny `message` for all isolated cron jobs without prompt wording or per-job repetition.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should cron tool restriction be a dedicated `tools.cron.tools.allow/deny` config surface, explicit inheritance from `tools.subagents.tools`, or part of a broader per-session policy design such as https://github.com/openclaw/openclaw/issues/49183?

Rationale: This adds security-sensitive public config/default behavior, and the wrong precedence could either leave the gap open or break existing cron jobs that rely on message/tool access.

Likely owner: Peter Steinberger

Owner reason: Current blame and prior review history place Peter closest to the config/tool-resolution decision surface.

Owner confidence: high

Options:

- **Add cron-scoped policy (recommended):** Implement `tools.cron.tools.allow/deny` with documented precedence against global policy, per-job `payload.toolsAllow`, delivery modes, and CLI-backed runtimes.
- **Reuse subagent policy:** Make cron sessions explicitly inherit `tools.subagents.tools` only if maintainers accept the semantic coupling and document it as a shared delegated-session policy.
- **Fold into broader session policy:** Keep this issue open but defer implementation until the broader per-session policy RFC defines one policy model for cron, spawned, sender, and scope-based sessions.

## Reproduction Assessment

Yes at source level: current schema/types have no cron-scoped tool policy, and runtime/tests show `message` remains available under announce unless a per-job `toolsAllow` excludes it. I did not run a live cron job in this read-only review.

## Solution Assessment

Unclear until maintainers choose the policy shape. Per-job `payload.toolsAllow` is useful but not the best system-wide solution for operators who need a default cron deny policy.

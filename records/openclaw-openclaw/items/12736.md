## Summary

Keep open: current main and v2026.6.11 still do not provide `tools.cron.tools.allow/deny` or explicit inheritance from `tools.subagents.tools`; current code has per-job `toolsAllow` and duplicate-delivery safeguards, but the requested system-wide cron tool boundary remains a security-sensitive product/config decision.

## What This Changes

The issue requests a cron-scoped tool deny policy, or cron inheritance from subagent tool policy, so scheduled isolated jobs can be hard-restricted from tools such as `message`.

## Best Possible Solution

Approve and implement a cron-scoped tool-policy contract with explicit precedence, schema/types/help/label/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for message-tool denial across cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface while coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

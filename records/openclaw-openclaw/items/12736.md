## Summary

Keep open: current main still has per-job cron `toolsAllow` and delivery safeguards, but no first-class cron-scoped allow/deny policy or inheritance from subagent tool policy, so the requested security boundary remains a product/config decision.

## What This Changes

The issue requests a cron-level tool policy such as `tools.cron.tools.deny` so scheduled agent runs can restrict direct tool access independently of ordinary session tools.

## Best Possible Solution

Define one maintainer-approved cron tool-policy contract with explicit precedence, safe defaults, schema/types/docs alignment, and focused regression tests for isolated cron runs across direct `message` use and announce delivery.

## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool allow/deny policy or explicit inheritance from subagent tool policy; newer cron delivery fixes reduce duplicate-message risk but do not provide the requested system-level restriction.

## What This Changes

Request a cron-scoped tool restriction config such as `tools.cron.tools.deny`, or explicit inheritance from `tools.subagents.tools`, so scheduled isolated cron jobs can be denied tools like `message`.

## Best Possible Solution

Approve a cron tool-policy contract with explicit precedence, schema/types/docs metadata, and regression coverage for isolated cron message denial across announce, none, and webhook delivery modes.

## Maintainer Decision

Question: Should isolated cron jobs get first-class `tools.cron.tools.allow/deny`, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: The choice defines a hard scheduled-run tool-access boundary and public config/default contract, including whether existing cron jobs that directly use `message` under announce delivery keep working by default.

Likely owner: steipete

Owner reason: steipete has the strongest combined recent history across scoped capability policy, cron/session behavior, and prior issue routing for this boundary choice.

Owner confidence: high

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence and tests for message denial across cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution applies `tools.subagents.tools` only to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

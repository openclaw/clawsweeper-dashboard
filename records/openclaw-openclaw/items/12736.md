## Summary

Keep open: current main and v2026.6.11 still do not provide `tools.cron.tools.allow/deny` or cron inheritance from `tools.subagents.tools`, so the requested operator-enforced cron tool boundary remains missing.

## What This Changes

Request a cron-scoped tool allow/deny policy, or cron inheritance from subagent tool policy, to restrict scheduled job tool access such as direct `message` sends.

## Best Possible Solution

Approve and implement a cron tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Question: Should OpenClaw add `tools.cron.tools.allow/deny`, make cron inherit `tools.subagents.tools`, or keep cron limited to per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: The choice defines a public scheduled-run tool-execution boundary and can widen or narrow access to message, TTS, shell, and channel tools, so automation should not pick the permanent security and compatibility semantics.

Likely owner: steipete

Owner reason: steipete has the strongest prior review and adjacent code-history signal for the cron/config/security-boundary choice.

Owner confidence: high

Options:

- **Add cron-specific policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against existing policy layers and per-job `toolsAllow`, then document and test upgrade behavior.
- **Inherit subagent policy:** Treat isolated cron sessions as covered by `tools.subagents.tools`, reducing config surface but coupling cron and subagent semantics.
- **Keep current safeguards:** Leave cron control to per-job `toolsAllow` and message-delivery safeguards, keeping config smaller but not solving the requested operator deny boundary.

Yes, as source-level feature-gap proof: current schemas, exported types, docs, and runtime policy resolution contain subagent/sandbox/per-job paths but no cron-scoped policy path. ## Solution Assessment

Unclear until maintainers choose the boundary. `tools.cron.tools.allow/deny` is the cleanest explicit contract, while cron inheritance from `tools.subagents.tools` is a plausible lower-surface alternative with different semantics.

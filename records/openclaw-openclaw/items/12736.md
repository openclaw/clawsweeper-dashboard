## Summary

Keep open: current main and latest v2026.6.11 still lack a cron-scoped tool allow/deny policy or explicit inheritance from `tools.subagents.tools`; cron currently has per-job `payload.toolsAllow` plus delivery/message-tool safeguards, so the requested hard cron boundary remains unresolved.

## What This Changes

The issue requests a cron-scoped tool restriction config, such as `tools.cron.tools.deny`, so isolated cron jobs can be hard-denied from tools like `message` instead of relying on prompt instructions.

## Best Possible Solution

Approve a cron tool-policy contract with explicit precedence, then implement it across schema/types/runtime/docs/tests so scheduled runs have an operator-controlled hard boundary instead of prompt guidance alone.

Rationale: The choice defines a security-sensitive scheduled-run config contract and can affect existing jobs that currently call `message` directly during cron delivery.

Likely owner: steipete

Owner confidence: high

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with documented precedence and tests for message denial across cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types/help still lack `tools.cron.tools`, and current policy resolution applies `tools.subagents.tools` only to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

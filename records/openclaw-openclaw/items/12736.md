## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped hard allow/deny policy or subagent-policy inheritance, so per-job `toolsAllow` and delivery safeguards only partially address the reported security and duplicate-message gap.

## What This Changes

The issue requests a cron-scoped tool deny policy, such as `tools.cron.tools.deny`, so isolated cron agent runs can block tools like `message` without relying on prompt instructions.

## Best Possible Solution

Define one maintainer-approved cron tool-policy contract, then implement it across schema, exported types, generated config metadata/help, docs, runtime policy resolution, and regression tests for isolated cron delivery modes.

Options:

- **Design Cron Policy In Session Model (recommended):** Use the broader per-session/capability-policy direction to define cron precedence first, then add one canonical cron enforcement path with docs and tests.
- **Add Dedicated Cron Scope Now:** Introduce `tools.cron.tools.*` as a narrow global cron policy with explicit deny precedence over per-job allowlists and delivery-mode behavior.
- **Document Per-Job Tools Only:** Decline a global cron policy and make per-job `--tools` plus announce-delivery safeguards the supported operator workflow.

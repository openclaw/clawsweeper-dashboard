## Summary

Keep open: current main and latest v2026.6.11 still lack a cron-scoped tool deny policy or explicit inheritance from subagent tool policy, while the issue has concrete security and duplicate-message delivery evidence.

## What This Changes

Request a cron-scoped tool restriction config, such as `tools.cron.tools.deny`, so isolated scheduled jobs can be hard-blocked from tools like `message`.

## Best Possible Solution

Keep this issue open until maintainers approve a cron tool-policy design with explicit precedence, schema/types/docs updates, and regression coverage for isolated cron `message` denial across announce, none, and webhook delivery modes.

Rationale: The choice defines a scheduled-run tool-access boundary and public config contract, including whether existing jobs that directly use `message` under announce delivery keep working by default.

Likely owner: steipete

Owner confidence: high

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence and tests for `message` denial across cron delivery modes.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

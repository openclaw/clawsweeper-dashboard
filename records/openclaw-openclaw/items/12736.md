## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool allow/deny policy or explicit inheritance from subagent policy, while the issue has concrete security and duplicate-message evidence.

## What This Changes

The issue requests a hard cron tool-restriction policy, either `tools.cron.tools.deny` or cron inheritance from `tools.subagents.tools`.

## Best Possible Solution

Approve an explicit cron tool-policy contract with precedence, then implement it through schema, types, runtime policy resolution, docs, and regression coverage for cron message-tool denial across delivery modes.

Options:

- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

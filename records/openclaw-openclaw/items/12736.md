## What This Changes

The issue requests a cron-scoped tool restriction policy so isolated cron jobs can be prevented from using tools such as `message` directly.

## Best Possible Solution

Approve and implement a cron-scoped tool-policy contract with explicit precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

Question: Should isolated cron jobs get a first-class `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: This choice defines a public config and security boundary for scheduled autonomous runs, including whether existing announce-mode cron jobs that directly use `message` keep working by default.

Likely owner: steipete

Owner reason: steipete has the strongest combined signal from current tool-policy pipeline ownership and prior review context for this issue.

Owner confidence: high

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against existing policy layers and per-job `toolsAllow`.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the security and product direction. A cron-scoped policy looks cleaner than overloading subagent semantics, but the best fix must define precedence and upgrade behavior first.

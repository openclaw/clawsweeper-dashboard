## Summary

Keep open: current main still lacks a system-wide cron tool allow/deny policy, and the remaining choice is a security-sensitive product/config decision rather than a stale or already-implemented request.

## What This Changes

The issue requests a `tools.cron.tools.deny` style config option, or explicit cron inheritance from `tools.subagents.tools`, so scheduled cron runs can be hard-restricted from tools such as `message`.

## Best Possible Solution

Approve and implement an explicit cron-scoped tool-policy contract with clear precedence, schema/types/help/docs updates, and regression coverage for isolated cron message-tool denial across delivery modes.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should isolated cron jobs get a first-class `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or continue with only per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: This choice creates a public config/security boundary and can change how existing announce-mode cron jobs use the `message` tool, so automation should not choose the product contract by itself.

Likely owner: steipete

Owner reason: He has the strongest current-main history signal on the scoped capability/tool-policy pipeline and prior review context for this issue.

Owner confidence: high

Options:

- **Add Cron-Scoped Policy (recommended):** Introduce `tools.cron.tools.allow/deny` with explicit precedence against existing policy layers and per-job `toolsAllow`, plus upgrade-safe docs and tests.
- **Inherit Subagent Policy:** Apply `tools.subagents.tools` to cron sessions as well, reducing config surface but coupling two different execution modes.
- **Keep Per-Job Only:** Avoid a new global cron policy and rely on `payload.toolsAllow`, docs, and delivery safeguards for scheduled runs.

## Reproduction Assessment

Yes, at source level. Current schema/types still lack `tools.cron.tools`, and current policy resolution only applies `tools.subagents.tools` to subagent envelopes while cron relies on per-job `toolsAllow` plus delivery safeguards.

## Solution Assessment

Unclear until maintainers choose the product/security contract. A cron-scoped policy looks cleaner than overloading subagent semantics, but the final fix must define precedence and upgrade behavior first.

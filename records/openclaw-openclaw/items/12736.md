## Label Justifications

- `P2`: The issue is a normal-priority security/tool-policy improvement for cron automation with limited blast radius and no current core-runtime outage.
- `impact:security`: The request is about hard-enforcing tool restrictions for unattended cron jobs rather than relying on prompt instructions.
- `impact:message-loss`: The reported `message` use case can duplicate or misroute visible cron output when a job sends directly and announce delivery also publishes the final reply.

## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped config tool policy; the newer per-job `toolsAllow` and announce-delivery safeguards mitigate some cases but do not provide the requested operator-wide deny rule.

## What This Changes

Requests a cron-scoped tool policy config such as `tools.cron.tools.deny`, or explicit cron inheritance from `tools.subagents.tools`, so isolated cron jobs cannot use denied tools like `message`.

## Best Possible Solution

Define a maintainer-approved cron tool-policy boundary, then implement one canonical config path with schema/types/help/docs and regression coverage for isolated announce jobs and per-job `toolsAllow` precedence.

Question: Should cron jobs get a dedicated `tools.cron.tools.allow/deny` policy, inherit `tools.subagents.tools`, or continue relying on per-job `payload.toolsAllow` plus delivery safeguards?

Rationale: This chooses a public config and security boundary for automated jobs, and repository policy treats new config/default surfaces and fallback behavior as compatibility-sensitive maintainer decisions.

Likely owner: steipete

Owner reason: steipete already reviewed this issue as an open cron policy decision and has recent cron/config history in the touched path.

Owner confidence: high

Options:

- **Add dedicated cron policy (recommended):** Introduce `tools.cron.tools.allow/deny` as an additive operator-wide policy with documented precedence over per-job `toolsAllow` and no silent inheritance surprises.
- **Inherit subagent policy:** Treat isolated cron sessions as subagent-like for tool policy, reducing config surface but coupling two execution modes that may need different defaults.
- **Keep per-job controls only:** Leave `payload.toolsAllow` and delivery safeguards as the supported path and close or narrow this request after documenting that product choice.

## Reproduction Assessment

Yes, source-level reproduction is high-confidence: current schema/types/docs expose subagent and sandbox tool policies but no cron-scoped config, and runtime tool resolution does not classify cron sessions as subagents. I did not run a live cron job because this review is read-only.

## Solution Assessment

Unclear pending maintainer direction: `tools.cron.tools.deny` is a plausible narrow solution, but inheriting subagent policy or folding cron into a broader per-session policy would change the long-term config model. The current per-job `toolsAllow` mitigation is not equivalent to an operator-wide deny rule.

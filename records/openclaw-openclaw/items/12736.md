## Summary

Keep open: current main and latest v2026.6.11 still lack `tools.cron.tools.allow/deny` or explicit cron inheritance from `tools.subagents.tools`, so this remains a security-sensitive config/product decision.

## What This Changes

Request a first-class cron job tool-deny policy, or explicit inheritance from subagent tool policy, so isolated cron jobs can be prevented from directly using tools such as `message`.

## Best Possible Solution

Approve a cron tool-policy contract only after maintainers choose the default behavior, precedence, docs, migration expectations, and security posture for direct cron `message` use versus runner-owned announce delivery.

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` or an equivalent typed cron policy with explicit precedence, docs, config metadata, and tests for announce/message behavior.
- **Inherit subagent policy:** Treat isolated cron sessions as a policy peer of subagents so `tools.subagents.tools` also applies to cron, accepting and documenting that coupling.
- **Keep per-job only:** Decline a global cron config surface and document that operators must use per-job `payload.toolsAllow`, delivery settings, or prompt/runtime safeguards for cron restrictions.

## Reproduction Assessment

Yes, at source level: current main has per-job `payload.toolsAllow` and subagent/sandbox policy wrappers, but no cron-scoped allow/deny config or cron inheritance path. I did not run a live cron job in this read-only review.

## Solution Assessment

Unclear until maintainers choose the policy shape. A cron-specific allow/deny config is plausible, but inheritance from subagent policy or staying with per-job `toolsAllow` have different upgrade and security behavior.

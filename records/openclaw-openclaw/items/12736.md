## Summary

Keep open: current main and v2026.6.11 still lack a cron-scoped tool policy such as `tools.cron.tools.allow/deny`, and the remaining work is a security-sensitive public config/default decision rather than a stale or already-implemented request.

## What This Changes

Request adding a cron-scoped tool allow/deny policy, or explicit inheritance from subagent policy, so isolated cron jobs can enforce restrictions on tools such as `message`.

## Best Possible Solution

Define a cron-owned policy layer with explicit precedence and defaults, update schema/types/help/docs/generated config metadata, and add regression coverage for announce/message-tool behavior plus embedded and CLI runtime handling.

Rationale: This changes a public configuration and security boundary, and the right default/precedence choice can affect existing cron jobs and message delivery behavior.

Options:

- **Add cron-scoped policy (recommended):** Introduce `tools.cron.tools.allow/deny` with compatibility-preserving defaults and explicit precedence against existing policy layers and per-job `toolsAllow`.
- **Inherit subagent policy:** Apply `tools.subagents.tools` to cron sessions too, reducing config surface but conflating two different runtime ownership boundaries.
- **Keep per-job only:** Decline the global knob and document `payload.toolsAllow` plus delivery-mode safeguards as the supported cron restriction path.

## Solution Assessment

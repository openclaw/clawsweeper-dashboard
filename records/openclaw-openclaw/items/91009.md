## Summary

Keep open: current main and v2026.6.11 still use synchronous process-per-event Codex hook relays, recent reports reproduce gateway stalls and OOM restarts, and no linked candidate PR has merged a complete fix.

## What This Changes

Prevent Codex native hook relay subprocess fan-out from exhausting CPU or memory and stalling or restarting the OpenClaw gateway.

## Best Possible Solution

Preserve required gating semantics, omit events without real local work, and replace full-runtime-per-event execution with a minimal relay client or a concurrency bound applied before the expensive process starts, proven under concurrent multi-agent Codex load.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw fix the default relay architecture by making remaining hooks lightweight and pre-spawn bounded, or use operator-configurable relay policy as the primary mitigation?

Rationale: The availability defect is established, but architectural cost removal preserves the default safety contract while an opt-out or event policy adds compatibility-sensitive configuration and shifts responsibility to operators.

Likely owner: steipete

Owner reason: Recent merged work owns the current Codex harness boundary and is the strongest history-based candidate to choose its permanent default and compatibility contract.

Owner confidence: medium

Options:

- **Lightweight bounded relay (recommended):** Retain required native gating hooks while eliminating full-runtime startup cost and bounding concurrency before expensive execution.
- **Configurable relay policy:** Expose enabled events or an opt-out, accepting a new configuration surface and operator responsibility for disabled policy coverage.
- **Disable relay by default:** Make native relay opt-in, reducing overhead but changing existing approval, loop-detection, and diagnostic behavior.

## Reproduction Assessment

Yes, at source level with high confidence. Current main installs synchronous relay command hooks, upstream Codex spawns a process per matching handler, and multiple reports on current June and July builds show the resulting CPU/RSS fan-out and gateway failure.

## Solution Assessment

No, idle-PreToolUse omission alone is not the best complete fix because every remaining enabled event still pays the full subprocess cost. The default relay path should become lightweight or pre-spawn bounded while retaining necessary gating behavior.

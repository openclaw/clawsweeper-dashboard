## Label Justifications

- `P2`: The bug weakens configuration rollback protection after an uncommon transient filesystem failure, with limited but meaningful blast radius.
- `impact:data-loss`: A poisoned snapshot marker can leave later configuration changes without the intended pre-update recovery copy.

## Summary

Keep this issue open: current `main` again marks a snapshot complete before either file operation and swallows failures without clearing that marker, so the reported retry suppression remains real. A prior fix shipped in v2026.5.20, making the current behavior an apparent regression rather than a stale duplicate. ([github.com](https://github.com/openclaw/openclaw/blob/main/src/config/backup-rotation.ts))

## What This Changes

Allow a later configuration pre-update snapshot attempt to retry after an earlier read or write failure.

## Best Possible Solution

Keep in-flight deduplication, but clear the snapshot key when either read or write fails; add regression coverage proving a rejected first attempt is retried, a later success writes the snapshot, and subsequent successful calls remain deduplicated.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes at source level: call `createPreUpdateConfigSnapshot` twice for one path with the first `readFile` rejecting and the second succeeding; current code skips the second read because the key remains set. This path was not executed during the read-only review.

## Solution Assessment

Yes, with one refinement: preserve pre-I/O in-flight deduplication and delete the key on failure rather than moving insertion after all I/O, which could permit concurrent duplicate snapshots.

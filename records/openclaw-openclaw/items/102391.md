## Summary

Keep open. Current main and the latest release still let `/export-session` pass an authorized non-owner through to a direct user-supplied filesystem write, and I found no linked or duplicate fix for the session-export path.

## What This Changes

The issue reports that an authorized non-owner can invoke `/export-session` with an arbitrary output path and write outside the workspace.

## Best Possible Solution

Make `/export-session` owner-only at the chat command boundary and enforce workspace-contained output paths in the exporter, with regression tests for both the non-owner case and traversal/absolute paths.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `/export-session` become owner-only, workspace-contained for authorized non-owners, or both owner-only and workspace-contained?

Rationale: The outside-workspace write is a clear bug, but current docs do not explicitly say whether in-workspace HTML session export should remain available to authorized non-owner senders.

Likely owner: pgondhi987

Owner reason: They recently landed the adjacent `/export-trajectory` owner-gate hardening and touched the relevant command boundary.

Owner confidence: medium

Options:

- **Owner-only plus contained paths (recommended):** Treat session HTML exports like the sibling trajectory export and also prevent absolute or traversal paths from escaping the workspace/export area.
- **Contain paths only:** Keep authorized non-owner session export for in-workspace outputs but reject or rewrite paths that would leave the workspace.
- **Private approval route:** Route `/export-session` through an owner approval/private delivery flow similar to sensitive trajectory exports, at the cost of more implementation surface.

## Reproduction Assessment

Yes from source inspection: current main accepts any authorized sender for `/export-session`, then resolves and writes a provided output path without workspace containment. I did not run the reporter’s write repro because this review is read-only.

## Solution Assessment

Likely yes: applying the sibling owner gate plus workspace containment is the narrowest safe fix. The only open choice is whether maintainers intentionally want to preserve in-workspace non-owner exports.

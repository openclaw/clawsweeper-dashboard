## Summary

Keep this issue open for measured startup evidence and a lifecycle-policy decision. Current main does start plugin services serially, but the Gateway listener is bound first, so the report does not establish that a slow asynchronous plugin prevents incoming connections; it may instead delay readiness-gated methods and the final ready state.

## What This Changes

Run registered plugin services concurrently and impose a timeout or quarantine policy for slow service initialization.

## Best Possible Solution

Add per-service startup timing first, then define explicit dependency, readiness, failure, and cancellation semantics; only independent services should start concurrently, with abortable timeouts and deterministic cleanup rather than blanket Promise.allSettled behavior.

- **Keep ordered startup:** Retain deterministic serial initialization and require plugins to make service start lightweight and move remote connection work into managed background tasks.
- **Adopt bounded concurrency:** Extend the plugin API with dependency metadata and AbortSignal support, then concurrently start only services proven independent.

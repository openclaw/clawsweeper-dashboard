## Summary

Keep this issue open. The report identifies a plausible source-level credential-routing failure with billing implications, but the safe behavior after an xAI OAuth-resolution failure—visible warning while falling back, or keeping the OAuth route unavailable—needs an owner decision before a repair should proceed.

## What This Changes

Report that xAI OAuth credential-resolution errors can silently fall through to an available paid API-key catalog and route requests to `api.x.ai` without telling the user.

## System Context

The bundled xAI plugin builds the provider catalog from configured OAuth and API-key credentials. That catalog is consumed by model routing, which then sends agent traffic to either the Grok subscription OAuth proxy or the xAI API-key endpoint.

## Architecture Diagram

flowchart LR
  A[Configured xAI credentials] --> B[xAI provider catalog]
  B --> C[Resolve OAuth credential]
  C -->|resolved| D[Grok OAuth proxy]
  C -->|resolution error| E[Fallback decision]
  E -->|API key available| F[xAI API-key provider]
  E -->|no API key| G[No provider published]
  D --> H[Agent model routing]
  F --> H

## Best Possible Solution

Preserve the intentional OAuth-first/API-key-fallback contract, but make an OAuth-resolution failure observable through a typed redacted diagnostic and a clear pre-fallback warning; add focused coverage for both OAuth-only and OAuth-plus-API-key configurations.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When xAI OAuth credential resolution throws while an API key is available, should OpenClaw retain API-key fallback with a visible redacted warning, or mark the OAuth route configured-unavailable and require explicit user recovery?

Rationale: Both outcomes change what existing OAuth-plus-API-key users experience during transient or migration-related credential failures, and repository policy treats provider fallback and auth routing as upgrade-sensitive product behavior.

Likely owner: jzakirov

Owner reason: They have recent detailed xAI OAuth routing context, although a current-main history owner should confirm the final provider contract.

Owner confidence: low

Options:

- **Warn, then preserve fallback (recommended):** Keep the established OAuth-first/API-key-fallback behavior, but emit a typed redacted warning naming the failed credential owner and the API-key route selected.
- **Fail the OAuth route closed:** Do not publish the API-key catalog after OAuth-resolution errors, so users must repair or migrate the OAuth credential before requests proceed.

## Reproduction Assessment

No high-confidence live reproduction is available. The report gives a concrete source path: make xAI OAuth resolution throw while an API key is also available, then observe the catch fall through to API-key catalog publication.

## Solution Assessment

Unclear. A redacted visible warning before preserving the intentional fallback appears to be the narrowest compatibility-preserving repair, but maintainers must choose whether silent fallback is acceptable after OAuth resolution fails.

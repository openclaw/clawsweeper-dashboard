## Summary

Keep open: current main and the latest release still do not provide a jobs.d/storeDir-style declarative cron definition source, and the only implementation candidate was closed unmerged; the remaining question is product/API direction around declarative files versus the current SQLite-backed cron store.

## What This Changes

The issue requests optional directory-backed cron job definitions so GitOps/NixOS users can manage one cron job per JSON file instead of editing one aggregate cron store.

## Best Possible Solution

Decide the declarative cron source model first, then implement a documented convergence path into the current SQLite runtime store with stable job identity, safe path handling, doctor/docs updates, and focused cron store/Gateway tests.

- **Keep SQLite-only runtime for now:** Close or defer file-backed cron source work and document CLI/RPC/plugin workflows as the supported maintenance path.
- **Build core jobs.d directly:** Accept the extra config/storage surface and require upgrade, symlink, delete/rename, state-preservation, doctor, and security proof before merge.

## Reproduction Assessment

Yes, source inspection gives a high-confidence current-main reproduction: cron config has no directory option, the schema is strict, Gateway passes one storePath, and the store reads SQLite rows keyed by that path. I did not run a runtime test because this review is read-only.

## Solution Assessment

Unclear; a literal jobs.d loader is plausible but not obviously the best solution after cron moved to SQLite. A safer direction is a maintainer-approved declarative source or plugin/API sync model that preserves SQLite as the runtime store.

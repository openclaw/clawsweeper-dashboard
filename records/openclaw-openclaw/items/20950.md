## Summary

Keep open: current main and v2026.6.11 still lack jobs.d/storeDir cron support, the prior implementation PR was closed unmerged, and the remaining request is a product/compatibility decision around SQLite runtime state versus a declarative file surface.

## What This Changes

Request to support a jobs.d-style per-job cron definition directory for declarative NixOS/GitOps management.

## Best Possible Solution

Choose one supported declarative cron path: either a maintained core import/sync surface that keeps SQLite as the runtime source of truth, or a ClawHub plugin using the cron SDK/hooks with documented safety and compatibility semantics.

- **Route to ClawHub plugin:** Close or redirect the request if maintainers decide a directory-to-cron sync plugin is sufficient with existing cron SDK and hook surfaces.
- **Sponsor core declarative sync:** Approve a core design that documents import/sync semantics, preserves SQLite runtime state, and covers doctor, docs, and focused cron tests.

## Reproduction Assessment

Yes for the missing capability by source inspection: current main only accepts cron.store and persists cron jobs through SQLite rows, with no storeDir/jobs.d branch in config, Gateway startup, or cron store code. This is a feature gap rather than a failing current behavior bug.

## Solution Assessment

Unclear. A direct core storeDir implementation is plausible, but VISION.md and current storage policy favor SQLite runtime state and optional capability in plugins unless maintainers approve a core declarative-sync contract.

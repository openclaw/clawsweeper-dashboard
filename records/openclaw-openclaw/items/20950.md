## Summary

Keep open: current main has SQLite-backed cron storage and a declaration-key upsert path, but no `jobs.d`/`storeDir` loader, sync contract, or one-file-per-job workflow; the earlier implementation PR is closed unmerged, so this remains a product/storage-direction decision.

## What This Changes

The issue requests `jobs.d`/`storeDir` support so cron schedules can be declared as one JSON file per job for NixOS/GitOps workflows.

## Best Possible Solution

Choose one supported declarative cron path: either a maintained core import/sync surface that keeps SQLite as the runtime source of truth, or a documented ClawHub/plugin/API workflow built on `declarationKey`.

Yes by source inspection: current main accepts `cron.store` but no `storeDir`/`jobsDir`, Gateway resolves one store key, and cron persistence uses SQLite rows rather than directory scans or per-file writes. This is a missing feature, not a failing current behavior bug.

## Summary

Keep open. Current main and v2026.6.11 still do not provide a `jobs.d`, `storeDir`, or per-job JSON cron source, and the only matching implementation PR is closed unmerged, so this remains a product-direction tracker rather than a cleanup close.

## What This Changes

The issue requests support for managing cron jobs as one JSON file per job in a directory for NixOS/GitOps-style declarative deployments.

## Best Possible Solution

Define a maintainer-approved declarative cron import or reconcile path that keeps SQLite canonical unless OpenClaw explicitly chooses a new runtime storage contract, then update config/schema, doctor, docs, and focused cron store/Gateway tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a declarative per-job cron file workflow, and if so should it be an import/reconcile artifact feeding SQLite or a steady-state jobs.d runtime store?

Rationale: Current code and docs make SQLite the canonical cron store, while this request adds new config and storage behavior with identity, deletion, migration, and path-safety implications that automation should not choose unilaterally.

Likely owner: steipete

Owner reason: The current cron persistence and SQLite storage boundary most directly traces through steipete's merged cron store work.

Owner confidence: high

Options:

- **Reconcile Into SQLite (recommended):** Add a documented deterministic import/export or reconcile surface that validates per-job JSON and writes canonical SQLite rows without making file polling the runtime store.
- **Runtime Directory Store:** Add a directory-backed cron store mode with explicit migration, symlink, path-safety, stable filename, and upgrade semantics owned by maintainers.
- **Decline Core Storage Mode:** Keep the supported path as CLI/Gateway API plus external user-side merge or import scripts for now.

## Reproduction Assessment

Yes, at source level: current main has no `storeDir`, `jobs.d`, or per-job JSON reconcile path, and the docs say active cron storage is SQLite-backed. This is a missing feature rather than a failing existing behavior path.

## Solution Assessment

No for the exact steady-state runtime `jobs.d` store proposal. The maintainable direction needs a maintainer-chosen import/reconcile or storage contract with explicit SQLite, migration, validation, and path-safety semantics.

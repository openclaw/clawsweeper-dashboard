## Summary

Keep open: current main and v2026.6.11 still lack `jobs.d`/`storeDir` cron support, the prior implementation PR is closed unmerged, and the remaining work is a product/storage-direction decision because cron jobs are now SQLite-backed and edited through CLI/Gateway APIs.

## What This Changes

The issue requests directory-backed cron job definitions so declarative NixOS/GitOps setups can manage one file per job.

## Best Possible Solution

Choose one supported declarative cron path: either a maintained core import/sync surface that keeps SQLite as the runtime source of truth, or a ClawHub plugin using existing cron SDK/hooks; avoid adding an unreviewed second runtime store.

## Reproduction Assessment

Yes for the missing capability by source inspection: current main only accepts `cron.store` and persists cron jobs through SQLite rows, with no `storeDir`/`jobs.d` branch in config, Gateway startup, or cron store code. This is a feature gap rather than a failing current behavior bug.

## Solution Assessment

Unclear. A direct core `cron.storeDir` implementation is plausible but not proven best because current design treats `cron.store` as a logical SQLite key, and existing plugin hooks/SDK may be enough for a ClawHub directory-sync package if maintainers prefer to keep core lean.

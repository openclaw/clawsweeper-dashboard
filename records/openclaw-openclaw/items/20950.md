## Summary

Keep open. Current main and v2026.6.11 still lack a `jobs.d`, `storeDir`, or per-job cron JSON source, and the existing declaration-key/plugin hooks are not a user-facing NixOS/GitOps file source.

## What This Changes

The issue requests directory-backed cron job definitions, with one JSON file per cron job, for declarative NixOS/GitOps management.

## Best Possible Solution

Define a maintainer-approved declarative cron import or reconcile contract that feeds canonical SQLite rows unless the project explicitly chooses a new runtime storage mode.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a declarative per-job cron file workflow, and should that workflow reconcile into SQLite or become a steady-state directory-backed runtime store?

Rationale: Current code and docs make SQLite the canonical cron store, while this request adds new storage/config behavior with migration, identity, deletion, and path-safety implications that automation should not choose unilaterally.

Likely owner: steipete

Owner reason: The current cron persistence and SQLite storage boundary most directly traces through steipete's merged cron store work.

Owner confidence: high

Options:

- **Reconcile Into SQLite (recommended):** Add a documented deterministic import/export or reconcile path that validates per-job JSON and writes canonical SQLite rows without making file polling the runtime store.
- **Runtime Directory Store:** Add a new directory-backed cron store mode with explicit migration, symlink, path-safety, stable filename, and upgrade semantics.
- **Decline Core Storage Mode:** Keep the supported path as CLI/Gateway API plus external user-side scripts or a ClawHub plugin for file reconciliation.

## Reproduction Assessment

Yes, at source level: current main has no `storeDir`, `jobs.d`, or per-job JSON source path, and the docs say active cron storage is SQLite-backed. This is a missing feature rather than a failing existing behavior path.

## Solution Assessment

No for the exact steady-state runtime `jobs.d` store proposal as-is. The safer maintainable path is a maintainer-chosen import/reconcile design, or an explicitly approved runtime store mode with migration and safety semantics.

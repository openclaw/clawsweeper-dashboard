## Summary

Keep open: current main and the latest release still lack jobs.d/storeDir cron support, the prior implementation pull request was closed unmerged, and the remaining request now needs a maintainer product decision because cron jobs are SQLite-backed and edited through CLI/Gateway APIs.

## What This Changes

Request support for a jobs.d-style directory where each cron job is declared in its own JSON file for NixOS/GitOps management.

## Best Possible Solution

Choose one supported declarative cron path: either a maintained core import/sync surface that keeps SQLite as the runtime source of truth, or a ClawHub plugin using the existing cron SDK/hooks; avoid adding an unreviewed second runtime store.

## Reproduction Assessment

Yes for the missing capability by source inspection: current main only accepts cron.store and persists cron jobs through SQLite rows, with no storeDir/jobs.d branch in config, Gateway startup, or cron store code. This is a feature gap rather than a failing current behavior bug.

## Solution Assessment

Unclear. A direct core cron.storeDir implementation is plausible but not proven best because current design treats cron.store as a logical SQLite key, and existing plugin hooks/SDK may be enough for a ClawHub directory-sync package if maintainers prefer to keep core lean.

## Summary

Keep open. Current main and the latest release still lack a `jobs.d`, `storeDir`, or per-job JSON cron source; the current `--declaration-key` path partially supports idempotent convergence, but the requested file-backed declarative workflow still needs a maintainer product/storage decision because cron persistence is now SQLite-canonical.

## What This Changes

The issue requests support for a directory-backed cron job store with one JSON file per cron job for declarative NixOS/GitOps workflows.

## Best Possible Solution

Define a maintainer-approved declarative cron import or reconcile path that keeps SQLite canonical unless the project explicitly chooses a new storage contract, then update config/schema, doctor, docs, and focused cron store/Gateway tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a declarative per-job cron file workflow, and if so should it be an import/reconcile artifact feeding SQLite or a steady-state jobs.d runtime store?

Rationale: Current code and docs make SQLite the canonical cron store, while this request adds new config/storage behavior with identity, deletion, migration, and path-safety implications that automation should not choose unilaterally.

Likely owner: steipete

Owner reason: The current cron persistence and SQLite storage boundary most directly traces through steipete's merged cron store work.

Owner confidence: high

Options:

- **Reconcile into SQLite (recommended):** Add a documented deterministic import/export or reconcile surface that validates per-job JSON and writes canonical SQLite rows without making file polling the runtime store.
- **Runtime directory store:** Add a new directory-backed cron store mode with explicit migration, symlink, path-safety, stable filename, and upgrade semantics owned by maintainers.
- **Decline core storage mode:** Keep the supported path as CLI/Gateway API plus external user-side merge/import scripts for now.

## Reproduction Assessment

Yes, at source level: current main has no `storeDir`, `jobs.d`, or per-job JSON reconcile path, and the docs say active cron storage is SQLite-backed. This is a missing feature rather than a failing existing behavior path.

## Solution Assessment

No for the exact steady-state runtime `jobs.d` store proposal. The safer maintainable direction is an explicit import/export or reconcile surface with deliberate SQLite, migration, validation, and path-safety semantics.

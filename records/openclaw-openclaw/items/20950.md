## Summary

Keep open. Current main and the latest release still do not provide a `jobs.d`, `storeDir`, or per-job declarative cron source, and the earlier implementation PR is closed unmerged, so this remains a maintainer product/storage decision rather than cleanup-closeable work.

## What This Changes

The issue requests optional cron `jobs.d`-style directory storage so each scheduled job can be managed as an individual declarative JSON file for NixOS/GitOps workflows.

## Best Possible Solution

Define a maintainer-approved declarative cron import or reconcile path that keeps SQLite canonical unless the project explicitly chooses a new directory-backed runtime storage contract, then update config/schema, doctor, docs, and focused cron store/Gateway tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support declarative per-job cron files, and should that be a runtime `jobs.d` store or an import/reconcile artifact feeding SQLite?

Rationale: Current code and policy make SQLite the canonical cron runtime store, while this request adds new config/storage semantics with migration, identity, deletion, and path-safety implications that automation should not choose unilaterally.

Likely owner: steipete

Owner reason: The SQLite cron persistence and current storage boundary most directly trace through steipete's merged cron store work and docs updates.

Owner confidence: high

Options:

- **Reconcile Into SQLite (recommended):** Add a documented deterministic import/export or reconcile surface that validates per-job JSON and writes canonical SQLite rows without making file polling the runtime store.
- **Runtime Directory Store:** Add a new directory-backed cron store mode with explicit migration, symlink, path-safety, stable filename, and upgrade semantics owned by maintainers.
- **Decline Core Storage Mode:** Keep supported cron management on the CLI/Gateway API and leave declarative file merging to external user-side tooling for now.

## Reproduction Assessment

Yes, at source level: current main has no `storeDir`, `jobsDir`, `jobs.d`, or per-job JSON reconcile path, and cron docs describe SQLite as the active storage contract. This is a missing feature/product direction, not a failing existing behavior path.

## Solution Assessment

No for the exact steady-state runtime `jobs.d` store as proposed. The safer maintainable direction is a deliberate import/export or reconcile surface unless maintainers explicitly choose a new directory-backed runtime store contract.

## Summary

Keep open: current main and the latest release still do not support a `jobs.d`/`storeDir` cron directory, and the remaining work is a product/storage-boundary decision rather than a narrow bug fix.

## What This Changes

The issue requests one-file-per-cron-job declarative storage for NixOS/GitOps workflows, likely through a `jobs.d` directory or `cron.storeDir`-style configuration.

## Best Possible Solution

Choose one supported declarative cron path: a maintained core import/sync surface that keeps SQLite as runtime truth, or a ClawHub plugin using existing cron SDK/hooks; document conflict, delete, security, doctor, and test semantics before implementation.

## Reproduction Assessment

Yes for the missing capability by source inspection: current main only accepts `cron.store` and persists cron jobs through SQLite rows, with no `storeDir` or jobs.d branch in config, Gateway startup, or cron store code. This is a feature gap rather than a failing current behavior bug.

## Solution Assessment

Unclear. A direct core `cron.storeDir` implementation is plausible, but existing plugin cron hooks and SDK helpers may support a ClawHub directory-sync package if maintainers prefer to keep core lean and SQLite as runtime truth.

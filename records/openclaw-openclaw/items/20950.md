## Summary

Keep this issue open: current main has SQLite-backed cron storage and recent declaration-key upserts, but it still does not support a `jobs.d` or per-job JSON directory source for NixOS/GitOps management.

## What This Changes

The issue requests a directory-backed cron job definition store so declarative setups can manage one JSON file per job instead of a single aggregate cron store.

## Best Possible Solution

Keep SQLite as the canonical runtime store; if maintainers sponsor this, design a documented per-job JSON import/sync surface that converges by declaration key, preserves existing jobs and runtime history, and updates schema, doctor, docs, and focused cron tests.

## Reproduction Assessment

No bug reproduction is applicable, but the missing feature is source-reproducible: current main has no cron directory-store config key and no directory scan/load path for per-job JSON files.

## Solution Assessment

Unclear as proposed: startup-loading arbitrary per-job JSON files is not obviously the best fit for the current SQLite-canonical store. A safer solution would make per-job files a maintainer-approved declarative import/sync layer over SQLite.

## Summary

Keep open. Current main and the latest release still do not provide `jobs.d`, `storeDir`, or another per-job declarative cron-file source, and the matching implementation PR is closed unmerged, so this remains a product-direction tracker rather than cleanup-close material.

## What This Changes

The issue requests directory-backed cron job definitions so NixOS/GitOps users can manage one JSON file per scheduled job instead of a single aggregate `jobs.json`.

## Best Possible Solution

Define a maintainer-approved declarative cron import or reconcile path that keeps SQLite canonical unless the project explicitly chooses a new directory storage contract, then update config/schema, doctor, docs, and focused cron store/Gateway tests.

- **Runtime Directory Store:** Add a new directory-backed cron store mode with explicit migration, symlink, path-safety, stable filename, and upgrade semantics owned by maintainers.
- **Decline Core Storage Mode:** Keep the supported path as CLI/Gateway API plus external user-side merge/import scripts for now.

## Reproduction Assessment

Yes, at source level: current main has no `storeDir`, `jobs.d`, or per-job JSON reconcile path, and the docs say active cron storage is SQLite-backed. This is a missing feature rather than a failing existing behavior path.

## Solution Assessment

Unclear for the exact steady-state `jobs.d` store proposal. The safer maintainable direction appears to be an explicit import/export or reconcile surface with deliberate SQLite, migration, validation, and path-safety semantics unless maintainers choose a new runtime storage contract.

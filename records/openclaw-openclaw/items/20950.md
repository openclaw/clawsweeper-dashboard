## Summary

Keep open: current main and the latest release still lack jobs.d/storeDir cron support, the prior implementation PR is closed unmerged, and the remaining path is a cron storage product-boundary decision.

## What This Changes

The issue requests a directory-backed cron job definition store so NixOS/GitOps users can manage one JSON file per scheduled job instead of one aggregate cron store key.

## Best Possible Solution

Choose one supported declarative cron path: either a maintained core import/sync surface that keeps SQLite as the runtime source of truth, or a ClawHub/plugin sync package if existing cron APIs are sufficient.

## Reproduction Assessment

Yes for the missing capability by source inspection: current main only accepts cron.store and persists cron jobs through SQLite rows, with no storeDir/jobs.d branch in config, Gateway startup, or cron store code. This is a feature gap rather than a failing current behavior bug.

## Solution Assessment

Unclear. A direct core jobs.d implementation is plausible, but current design treats cron.store as a logical SQLite key and a ClawHub/plugin sync package may be the better boundary if existing cron APIs are enough.

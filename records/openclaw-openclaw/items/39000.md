## Summary

Keep open: current main has a reserved Gateway dispatch helper for authenticated plugin HTTP routes, but it still does not provide the ordinary plugin-to-plugin Gateway method caller requested here. The remaining work is a Plugin SDK product and security-boundary decision, not conservative cleanup.

## What This Changes

The issue requests a plugin API such as `api.callGatewayMethod()` so one plugin can invoke another plugin's registered Gateway methods through a supported OpenClaw surface.

## Best Possible Solution

Keep this as the canonical design item for a narrow, authorized Plugin SDK Gateway-call contract with caller attribution, explicit method exposure rules, docs, and contract tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should ordinary plugin runtime code be allowed to call plugin-registered Gateway methods, and what API and authorization shape should carry plugin caller identity?

Rationale: The implementation substrate exists, but choosing between raw dispatch, allowlisted Gateway calls, or typed plugin service/capability contracts changes the public Plugin SDK and Gateway security boundary.

Likely owner: steipete

Owner reason: The current route-scoped dispatch contract and Plugin SDK boundary history point most strongly to this account for the API/security decision.

Owner confidence: high

Options:

- **Design an authorized SDK contract (recommended):** Expose only approved methods or typed capabilities with plugin caller attribution, explicit authorization, docs, and contract tests.
- **Keep HTTP-route dispatch only:** Decline ordinary plugin-to-plugin Gateway calls and keep Gateway dispatch reserved for authenticated plugin HTTP routes plus existing curated runtime helpers.
- **Expose raw Gateway dispatch:** Add a generic method-string caller and accept the larger security and compatibility surface as an explicit maintainer-owned product decision.

## Reproduction Assessment

Yes. Source inspection on current main and v2026.6.11 shows plugins can register Gateway methods, but ordinary plugin runtime/hooks/services still have no general caller; the only public SDK dispatcher is restricted to authenticated plugin HTTP-route scopes.

## Solution Assessment

No for the raw `callGatewayMethod(method, params)` shape as proposed. The safer solution is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, lifecycle handling, docs, and contract tests.

## Summary

Keep open: current main now has a restricted `api.runtime.gateway.request` path for bundled or trusted official plugins, but the reported external plugin-to-plugin caller remains intentionally rejected and still needs a maintainer security/API decision.

## What This Changes

The issue requests a plugin SDK method for one plugin to invoke gateway methods registered by another plugin.

## Best Possible Solution

Keep this as the canonical design item for external plugin-to-plugin Gateway calls, and decide whether the permanent API should be a narrow authorized capability/service contract, a trusted-only surface, or an explicit not-planned boundary.

## Maintainer Decision

Kind: security_boundary

Question: Should OpenClaw expose plugin-to-plugin Gateway method calls to ordinary external plugins, and if yes what authorization and API shape should make that safe?

Rationale: Current code proves the runtime can dispatch Gateway methods for trusted plugins, but extending that to arbitrary external plugins changes the public Plugin SDK and plugin isolation boundary.

Likely owner: steipete

Owner confidence: medium

Options:

- **Design a narrow authorized contract (recommended):** Expose only approved plugin-owned methods or typed service capabilities with caller attribution, docs, and contract tests.
- **Keep the trusted-only surface:** Treat current `api.runtime.gateway.request` as the supported boundary and decline ordinary external plugin-to-plugin Gateway calls.
- **Allow raw method dispatch:** Expose a generic method-string caller and explicitly accept the larger compatibility and security surface.

## Reproduction Assessment

Yes. Source inspection shows current main has no top-level `api.callGatewayMethod`, and its newer `api.runtime.gateway.request` path rejects arbitrary external plugins, matching the reported external inter-plugin gap.

## Solution Assessment

No for the raw proposed shape. A safer solution should first define caller identity, method exposure, and authorization; current main's trusted-only request API is a useful partial implementation but not the external plugin contract requested here.

## Summary

Keep open: current main has `api.runtime.gateway.request`, but source, docs, and tests limit it to bundled or trusted official plugins, so the ordinary external plugin-to-plugin use case still needs a product/security decision.

## What This Changes

The issue requests a Plugin SDK API for one plugin to invoke gateway methods registered by another plugin.

## Best Possible Solution

Keep the trusted-official helper and decide a narrow external inter-plugin contract, such as manifest-declared capabilities or allowlisted methods with caller attribution, scopes, docs, and contract tests.

Owner confidence: high

Options:

- **Design a narrow external contract (recommended):** Expose only approved or manifest-declared methods/capabilities with caller attribution, trust-tier behavior, docs, and focused contract tests.
- **Keep trusted-official only:** Document that community plugins cannot use in-process Gateway RPC dispatch unless promoted to the trusted official install path.
- **Allow broad raw dispatch:** Expose a generic method-string caller to more plugins and accept the larger compatibility and security surface as an explicit product decision.

## Reproduction Assessment

Yes. Current main shows the registration side exists and trusted plugins can call `api.runtime.gateway.request`, while tests and docs explicitly reject arbitrary external plugins.

## Solution Assessment

No for the proposed raw `api.callGatewayMethod(method, params)` shape. The safer path is a maintainer-approved narrow SDK contract that defines allowed methods, caller identity, trust tier, and sensitive-method handling.

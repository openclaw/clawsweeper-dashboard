## Summary

Keep open: current main only partially addresses the Gateway call gap for bundled or trusted official plugins, while the original third-party inter-plugin use case is still intentionally rejected and needs maintainer product/security direction.

## What This Changes

The issue requests a plugin SDK API for one plugin to invoke Gateway methods registered or exposed by another plugin.

## Best Possible Solution

Keep this as the canonical design item for a narrow, authorized Plugin SDK Gateway-call or service contract with caller attribution, explicit method exposure policy, docs, and contract tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should ordinary external plugins be allowed to invoke plugin-registered Gateway methods, and under what authorization and exposure model beyond the current bundled/trusted-official-only path?

Rationale: The remaining work changes the public Plugin SDK and Gateway authorization boundary, so automation cannot safely choose raw dispatch, curated capabilities, trusted-only access, or no third-party access.

Likely owner: steipete

Owner reason: He merged the current trusted-only Gateway runtime path and has the strongest recent history around this Gateway/Plugin SDK security boundary.

Owner confidence: high

Options:

- **Design a narrow authorized contract (recommended):** Expose only approved Gateway methods or typed plugin capabilities with caller attribution, explicit trust/allowlist policy, docs, and contract tests.
- **Keep trusted-only access:** Treat the current main implementation as the intended boundary and require external plugins to use another documented seam or trusted-official distribution.
- **Allow broad raw dispatch:** Expose a generic method-string caller to more plugins, accepting the broader security and compatibility surface as an explicit product decision.

## Reproduction Assessment

Yes. Source inspection shows current main only exposes `api.runtime.gateway.request` to bundled or trusted official plugin scopes and tests reject a global third-party plugin; v2026.6.11 lacks `PluginRuntime.gateway` entirely.

## Solution Assessment

No for the raw `api.callGatewayMethod(method, params)` shape as proposed. The safer solution is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, docs, and tests.

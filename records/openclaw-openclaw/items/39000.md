## Summary

Keep open: current main and v2026.6.11 still do not provide an ordinary plugin hook/service/runtime caller for invoking another plugin's registered Gateway method. The route-scoped `gateway-method-runtime` helper and the shipped `openclaw gateway call` fix are useful adjacent surfaces, but they do not solve this issue's inter-plugin API and authorization decision.

## What This Changes

Request to add a plugin API such as `api.callGatewayMethod()` so one plugin can invoke Gateway methods registered by another plugin.

## Best Possible Solution

Keep this as the canonical inter-plugin Gateway-call design item and land only a narrow, documented Plugin SDK contract with caller attribution, explicit method exposure rules, security tests, and migration/docs updates after maintainer approval.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should ordinary plugin runtime code be allowed to call plugin-registered Gateway methods, and if so should the SDK expose a raw dispatcher, a curated allowlisted gateway surface, or typed capability/service contracts?

Rationale: The source gap is real, but the API shape changes the public Plugin SDK and Gateway authorization boundary, so automation should not choose the permanent contract or security policy.

Likely owner: steipete

Owner reason: The strongest history for the current Gateway dispatch contract and Plugin SDK boundary points to steipete for the API/security direction call.

Owner confidence: high

Options:

- **Design a narrow authorized SDK contract (recommended):** Expose approved methods or typed capabilities with plugin caller identity, explicit authorization, docs, and contract tests.
- **Keep HTTP-route dispatch only:** Decline ordinary plugin-to-plugin Gateway calls and require plugins to use existing HTTP route, runtime helper, or capability seams.
- **Expose raw Gateway dispatch:** Add a generic method-string caller and accept the larger security and compatibility surface as a maintainer-owned product decision.

## Reproduction Assessment

Yes. Source inspection shows plugins can register Gateway methods, but ordinary plugin runtime/hooks/services still have no general caller; the only public dispatcher is restricted to authenticated plugin HTTP-route scopes.

## Solution Assessment

No for the raw `callGatewayMethod(method, params)` shape as proposed. The safer solution is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, docs, and contract tests.

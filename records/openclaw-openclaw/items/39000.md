## Summary

Keep open: current main still lacks an ordinary plugin-to-plugin Gateway method caller, and the existing dispatch helper remains reserved for authenticated plugin HTTP routes. The linked external metabolism/stability plugin report shows a real integration need, but the fix is a public Plugin SDK and Gateway authorization design decision rather than conservative cleanup.

## What This Changes

Request to add a Plugin SDK API that lets one plugin call Gateway methods registered by another plugin.

## Best Possible Solution

Keep this as the canonical design item for a narrow, authorized Plugin SDK inter-plugin Gateway-call contract with caller attribution, explicit exposure rules, docs, and contract tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose ordinary plugin runtime access to plugin-registered Gateway methods, and what authorization/API shape should carry caller identity?

Rationale: The implementation would change the public Plugin SDK and Gateway authorization boundary, so automation cannot safely choose between raw dispatch, allowlisted calls, or typed service/capability contracts.

Likely owner: steipete

Owner reason: He authored the existing Gateway method dispatch contract and is the strongest history match for the Plugin SDK/Gateway boundary decision.

Owner confidence: high

Options:

- **Design a narrow authorized SDK contract (recommended):** Expose only approved methods or typed capabilities with plugin caller attribution, explicit authorization, docs, and contract tests.
- **Keep HTTP-route dispatch only:** Decline ordinary plugin-to-plugin Gateway calls and require plugins to use existing HTTP route or capability seams.
- **Expose raw Gateway dispatch:** Add a generic method-string caller and accept the larger security and compatibility surface as a maintainer-owned product decision.

## Reproduction Assessment

Yes. Source inspection on current main and v2026.6.11 shows plugin Gateway method registration exists, but ordinary PluginRuntime code has no Gateway caller; the only public dispatcher is restricted to authenticated plugin HTTP-route scopes.

## Solution Assessment

No for the raw callGatewayMethod(method, params) shape as proposed. The safer solution is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, docs, and contract tests.

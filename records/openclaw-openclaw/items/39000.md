## Summary

Keep open: current main now has `api.runtime.gateway.request`, but it is restricted to bundled or trusted official plugins, so the external plugin-to-plugin use case remains an unresolved Plugin SDK and Gateway authorization design item.

## What This Changes

Request a Plugin SDK API that lets one plugin call Gateway methods registered by another plugin.

## Best Possible Solution

Keep the trusted-only runtime request as the partial safe path, then design a narrow external plugin contract with caller identity, method exposure or typed capabilities, docs, and contract tests before enabling cross-plugin Gateway calls.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose plugin-to-plugin Gateway method calls to external plugins, and if so should that be raw dispatch, an allowlisted request API, or a typed service/capability contract?

Rationale: The requested surface changes the public Plugin SDK and Gateway authorization boundary; automation cannot safely choose the permanent security model or API shape.

Likely owner: Peter Steinberger

Owner reason: steipete merged the current trusted Gateway runtime seam and is the clearest recent decision owner for this boundary.

Owner confidence: high

Options:

- **Design a narrow authorized SDK contract (recommended):** Expose only approved methods or typed capabilities with plugin caller attribution, explicit authorization, docs, and contract tests.
- **Keep trusted/route-scoped dispatch only:** Decline ordinary external plugin-to-plugin Gateway calls and direct plugins to existing HTTP route, manifest, or capability seams.
- **Allow raw Gateway dispatch:** Expose a generic method string caller and accept the larger security and compatibility surface as a maintainer-owned product decision.

## Reproduction Assessment

Yes. Source inspection shows registration exists and current main can dispatch Gateway methods for trusted plugins, but ordinary external plugin-to-plugin calls are still rejected or limited to authenticated HTTP-route scopes.

## Solution Assessment

No for the raw `callGatewayMethod(method, params)` shape as proposed. The safer path is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, lifecycle handling, docs, and contract tests.

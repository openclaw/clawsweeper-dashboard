## Summary

Keep open: current main now has a partial `api.runtime.gateway.request` path for bundled or trusted official plugins, but the reported ordinary third-party plugin-to-plugin Gateway call remains rejected by design and needs a Plugin SDK security-boundary decision.

## What This Changes

Request to add a plugin-facing Gateway method caller so one plugin can invoke methods registered by another plugin.

## Best Possible Solution

Define a narrow authorized Plugin SDK gateway-call or service/capability contract with caller attribution, explicit exposure rules, docs, and contract tests; keep the current trusted-official-only path until that decision is made.

Rationale: This changes the public Plugin SDK and Gateway authorization boundary, so automation cannot safely choose the permanent API shape or security model.

Options:

- **Design a narrow authorized contract (recommended):** Expose only approved plugin-owned methods or typed capabilities with plugin caller attribution, explicit authorization, docs, and contract tests.
- **Keep trusted-official only:** Leave `api.runtime.gateway.request` limited to bundled or trusted official plugins and ask arbitrary third-party plugins to use existing HTTP or capability seams.
- **Allow raw Gateway dispatch:** Expose a generic method-string caller and accept the larger security, compatibility, and schema-stability surface as an explicit product decision.

Yes. Source inspection on current main shows a trusted-official `api.runtime.gateway.request` path, but tests and docs confirm arbitrary external plugins are still rejected.

## Solution Assessment

No for the raw `api.callGatewayMethod(method, params)` shape as proposed. The safer path is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, docs, and contract tests.

## Summary

Keep open: current main added a trusted-only `api.runtime.gateway.request` path, but it explicitly rejects arbitrary external plugins, so the linked metabolism/stability plugin-to-plugin use case is still unresolved and needs a Plugin SDK security-boundary decision.

## What This Changes

Request to expose a plugin API call side for plugin-registered Gateway methods so one plugin can invoke another plugin's Gateway RPC without file coupling or parsing message context.

## Best Possible Solution

Keep this as the canonical design item for an authorized inter-plugin Gateway or service contract that defines external-plugin trust, method exposure, caller attribution, docs, and contract tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw extend `api.runtime.gateway.request` beyond bundled/trusted official plugins to ordinary external plugin-to-plugin calls, and what authorization or capability contract should gate that access?

Rationale: The remaining work changes the public Plugin SDK and Gateway authorization boundary, so automation cannot safely choose whether external plugins may invoke arbitrary plugin-owned Gateway methods.

Likely owner: steipete

Owner reason: He merged the current trusted-only Gateway runtime surface and is the strongest history match for the plugin/Gateway security boundary.

Owner confidence: high

Options:

- **Design explicit capability contract (recommended):** Expose external plugin-to-plugin calls only through declared capabilities or allowlisted Gateway methods with caller attribution, scope checks, docs, and tests.
- **Keep trusted-only runtime Gateway calls:** Leave current main's bundled/trusted-official restriction in place and direct external plugins toward existing context, hook, or future service APIs.
- **Allow raw method dispatch:** Expose a general method-string caller for more flexibility, accepting a larger compatibility and security surface.

## Reproduction Assessment

Yes. Source inspection shows ordinary external plugins are rejected by `dispatchTrustedPluginGatewayMethod`, and the linked external plugin issue demonstrates the scoped-API failure mode.

## Solution Assessment

No for the raw `callGatewayMethod(method, params)` shape as proposed. A narrower capability or allowlisted Gateway request contract is safer because it can preserve plugin caller identity and method authorization.

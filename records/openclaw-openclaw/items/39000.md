## Summary

Keep open: current main now has a trusted-only `api.runtime.gateway.request` surface, but source, docs, and tests still reject arbitrary external plugins, so the reported external plugin-to-plugin use case remains a Plugin SDK and Gateway security-boundary decision.

## What This Changes

The issue requests a Plugin SDK call surface so one plugin can invoke another plugin's registered Gateway RPC instead of relying on scoped `api` object hacks.

## Best Possible Solution

Keep this as the canonical design item until maintainers choose and document a narrow caller-attributed, allowlisted Plugin SDK contract for external plugin-to-plugin Gateway calls, or explicitly reject that boundary.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should ordinary external plugins be allowed to invoke other plugins' Gateway methods, and if so through which caller-attributed and allowlisted Plugin SDK contract?

Rationale: This changes the public Plugin SDK and Gateway authorization boundary; automation cannot safely choose whether raw dispatch, curated capabilities, or trusted-only access is the permanent product/security contract.

Likely owner: Peter Steinberger

Owner reason: He introduced the current route-scoped Gateway dispatch contract and is the strongest history match for the security-boundary decision.

Owner confidence: high

Options:

- **Design an allowlisted external-plugin contract (recommended):** Expose only approved plugin methods or typed capabilities with caller identity, authorization checks, docs, and contract tests.
- **Keep Gateway calls trusted-only:** Leave `api.runtime.gateway.request` limited to bundled or trusted official plugins and ask external plugins to use existing HTTP routes or future typed service seams.
- **Reject inter-plugin Gateway RPCs:** Close this direction and require plugin authors to publish shared services or parse documented outputs outside the Gateway RPC surface.

## Reproduction Assessment

Yes. Source and test inspection show external/global plugins are rejected from `runtime.gateway.request`, and no `api.callGatewayMethod` or `gateway.dispatchMethod` symbol exists for ordinary external plugin-to-plugin calls.

## Solution Assessment

No for the raw `api.callGatewayMethod(method, params)` shape as proposed. The maintainable path is a maintainer-approved SDK contract with caller identity, explicit exposure or allowlisting, authorization rules, docs, and contract tests.

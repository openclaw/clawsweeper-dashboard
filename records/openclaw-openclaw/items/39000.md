## Summary

Keep open: current main and the latest release still do not provide an ordinary plugin runtime or `OpenClawPluginApi` caller for another plugin's registered Gateway method. The existing SDK dispatcher is intentionally limited to authenticated plugin HTTP-route scopes, so this remains a public Plugin SDK and Gateway authorization design item.

## What This Changes

The issue requests a plugin API such as `api.callGatewayMethod()` so one plugin can invoke Gateway methods registered by another plugin.

## Best Possible Solution

Keep this as the canonical design item for a narrow, authorized Plugin SDK Gateway-call contract with caller attribution, explicit method exposure rules, docs, and contract tests.

Question: Should OpenClaw expose ordinary plugin runtime access to plugin-registered Gateway methods, and what authorization/API shape should carry plugin caller identity?

Rationale: This changes the public Plugin SDK and Gateway authorization boundary, so automation cannot safely choose between raw dispatch, allowlisted calls, or typed service/capability contracts.

Likely owner: steipete

Owner confidence: high

Options:

- **Design a narrow authorized SDK contract (recommended):** Expose only approved methods or typed capabilities with plugin caller attribution, explicit authorization, docs, and contract tests.
- **Keep HTTP-route dispatch only:** Decline ordinary plugin-to-plugin Gateway calls and require plugins to use existing HTTP route, runtime helper, or capability seams.
- **Expose raw Gateway dispatch:** Add a generic method-string caller and accept the larger security and compatibility surface as a maintainer-owned product decision.

## Reproduction Assessment

Yes. Source inspection on current main shows plugins can register Gateway methods, but ordinary plugin runtime/hooks/services still have no general caller; the only public SDK dispatcher is restricted to authenticated plugin HTTP-route scopes.

## Solution Assessment

No for the raw `callGatewayMethod(method, params)` shape as proposed. The safer solution is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, lifecycle handling, docs, and contract tests.

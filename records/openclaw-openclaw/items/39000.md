## Summary

Keep open: current main partially added `api.runtime.gateway.request` for bundled or trusted official plugins, but the reported external inter-plugin caller remains blocked because arbitrary external plugins are still rejected.

## What This Changes

The issue requests a Plugin SDK call so one plugin can invoke Gateway methods registered by another plugin instead of parsing message or context text.

## Best Possible Solution

Have maintainers choose a narrow authorized SDK contract for inter-plugin or host Gateway calls, with caller attribution, explicit exposure rules, docs, and contract tests.

Options:

- **Design an authorized SDK contract (recommended):** Expose only approved methods or typed capabilities with plugin caller attribution, method authorization, docs, and contract tests.
- **Keep trusted-only Gateway requests:** Treat the new `api.runtime.gateway.request` surface as limited to bundled or trusted official plugins and decline arbitrary third-party inter-plugin dispatch.
- **Allow raw method dispatch:** Expose a generic method string caller and accept the broader compatibility and security surface as an explicit product decision.

## Reproduction Assessment

Yes. Source inspection shows ordinary external plugins still hit the trusted-official guard when calling the new Gateway runtime surface, while the route-scoped helper remains reserved for authenticated HTTP routes.

## Solution Assessment

No for the raw `api.callGatewayMethod(method, params)` shape as proposed. A safer solution is a maintainer-approved SDK contract with caller identity, allowlisting or typed capabilities, authorization rules, docs, and tests.

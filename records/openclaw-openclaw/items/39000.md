## Summary

Keep open: current main now has `api.runtime.gateway.request`, but it is intentionally limited to bundled or trusted official plugins; the requested ordinary external plugin-to-plugin Gateway caller remains a product and security-boundary decision.

## What This Changes

Request a plugin API for one plugin to invoke Gateway methods registered by another plugin.

## Best Possible Solution

Keep the current trusted-plugin `api.runtime.gateway.request` subset, and decide a narrower public inter-plugin contract with caller attribution, explicit method exposure or allowlisting, docs, and contract tests before supporting external plugins.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose Gateway method calls to ordinary external plugins, and if so should the API be raw method dispatch, an allowlisted request surface, or typed inter-plugin service contracts?

Rationale: This choice changes the public Plugin SDK and Gateway authorization boundary; automation cannot safely choose which methods external plugins may invoke or which schemas become stable plugin contracts.

Likely owner: steipete

Owner reason: He introduced the current route-scoped dispatch contract and is the strongest history match for the Gateway/plugin authorization boundary.

Owner confidence: high

Options:

- **Design a narrow authorized contract (recommended):** Expose only approved methods or typed capabilities with plugin caller attribution, explicit authorization, docs, and contract tests.
- **Keep trusted-only Gateway requests:** Treat current `api.runtime.gateway.request` as sufficient for bundled/trusted official plugins and decline ordinary external plugin-to-plugin dispatch for now.
- **Allow raw Gateway dispatch:** Expose a generic method string caller and intentionally accept the larger security and compatibility surface.

## Reproduction Assessment

Yes. Source inspection shows current main supports only bundled/trusted official plugin Gateway requests and rejects arbitrary external plugins, so the reported external plugin-to-plugin call path remains unavailable.

## Solution Assessment

No for the raw `api.callGatewayMethod(method, params)` shape as proposed. The safer path is a maintainer-approved SDK contract with caller identity, explicit authorization, and stable method exposure rules.

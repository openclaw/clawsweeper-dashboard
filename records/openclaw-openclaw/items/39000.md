## Summary

Keep open: current main now has a partial `api.runtime.gateway.request` path, but it is intentionally limited to bundled or trusted official plugins, so the reported external plugin-to-plugin use case still needs a public Plugin SDK and authorization design decision.

## What This Changes

The issue requests a Plugin SDK call surface so one plugin can invoke another plugin's registered Gateway method without parsing message text or coupling to files.

## Best Possible Solution

Keep the trusted-only runtime request as the partial safe path, then design a narrow external plugin contract with caller identity, method exposure or typed capabilities, docs, and contract tests before enabling cross-plugin Gateway calls.

Likely owner: Peter Steinberger

Owner confidence: high

Options:

- **Design a narrow authorized contract (recommended):** Expose only approved methods or typed capabilities with caller attribution, explicit authorization, docs, and regression tests.
- **Keep trusted-only Gateway requests:** Leave arbitrary external plugin-to-plugin Gateway calls unsupported and document route-scoped HTTP or purpose-built capability alternatives.
- **Expose raw Gateway dispatch:** Add a generic method-string caller and accept the larger security and compatibility surface as an explicit product decision.

## Reproduction Assessment

Yes. Source inspection on current main shows plugin Gateway method registration exists, but ordinary external plugins are rejected by `api.runtime.gateway.request` and the older SDK dispatcher remains limited to authenticated plugin HTTP routes.

## Solution Assessment

No for the raw `api.callGatewayMethod(method, params)` shape as proposed. The maintainable path is a narrower approved SDK contract with caller attribution, method policy, docs, and contract tests.

## Summary

Keep open: current main and v2026.6.11 still do not expose an ordinary plugin-runtime caller for plugin-registered Gateway methods. The remaining work is a public Plugin SDK and Gateway authorization-boundary decision, not conservative cleanup.

## What This Changes

The issue requests a Plugin SDK API that lets one plugin invoke a Gateway method registered by another plugin.

## Best Possible Solution

Keep this as the canonical design item for a narrow, authorized PluginRuntime Gateway-call contract with caller attribution, explicit method exposure rules, docs, and contract tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should ordinary plugin runtime code be allowed to call plugin-registered Gateway methods, and what caller identity, allowlist, and authorization model should that API use?

Rationale: The request changes both the public Plugin SDK and the Gateway method authorization boundary, so automation cannot safely choose between raw dispatch, curated accessors, or typed service/capability contracts.

Likely owner: Peter Steinberger

Owner reason: He introduced the existing route-scoped dispatch contract and has the clearest recent history across the Gateway/plugin SDK boundary.

Owner confidence: high

Options:

- **Design a narrow authorized SDK contract (recommended):** Expose approved methods or typed capabilities with plugin caller attribution, explicit authorization, docs, and contract tests.
- **Keep dispatch limited to HTTP routes:** Decline ordinary plugin-to-plugin Gateway calls and require plugins to use existing HTTP route, runtime helper, or capability seams.
- **Expose raw Gateway dispatch:** Add a generic method-string caller and accept the larger security and compatibility surface as a maintainer-owned product decision.

## Reproduction Assessment

Yes. Source inspection on current main and v2026.6.11 shows plugins can register Gateway methods, but PluginRuntime has no ordinary gateway/callGatewayMethod surface and the only dispatch helper is limited to authenticated plugin HTTP routes.

## Solution Assessment

No for the raw callGatewayMethod shape as proposed. The safer solution is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, lifecycle handling, docs, and contract tests.

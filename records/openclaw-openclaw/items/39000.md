## Summary

Keep open: current main and v2026.6.11 still do not provide an ordinary plugin-to-plugin Gateway method caller; the remaining work is a public Plugin SDK and Gateway authorization design decision, not cleanup.

## What This Changes

The issue requests a plugin-facing way to invoke Gateway methods registered by other plugins, such as `api.callGatewayMethod()`.

## Best Possible Solution

Keep this as the canonical design item for a narrow, authorized Plugin SDK inter-plugin or host Gateway-call contract with caller attribution, explicit exposure rules, docs, and contract tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose an ordinary plugin runtime caller for plugin-registered Gateway methods, and should that caller be raw dispatch, an allowlisted request API, or a typed service/capability contract?

Rationale: This changes the public Plugin SDK and Gateway authorization boundary, so automation cannot safely choose the caller identity, method policy, or permanence of the API.

Likely owner: steipete

Owner reason: He introduced and merged the current route-scoped Gateway method dispatch contract and is the strongest history match for this security boundary decision.

Owner confidence: high

Options:

- **Design a narrow authorized SDK contract (recommended):** Expose approved methods or typed capabilities with plugin caller attribution, explicit authorization, docs, and contract tests.
- **Keep only the route-scoped helper:** Decline ordinary plugin-to-plugin Gateway calls and require plugins to use existing HTTP route, event, or capability seams.
- **Allow raw Gateway dispatch:** Expose a generic method-string caller and accept the broader security and compatibility surface as an explicit product decision.

## Reproduction Assessment

Yes. Source inspection on current main and v2026.6.11 shows plugins can register Gateway methods, but ordinary plugin runtime/hooks/services still have no general caller; the only public SDK dispatcher is restricted to authenticated plugin HTTP-route scopes.

## Solution Assessment

No for the raw `callGatewayMethod(method, params)` shape as proposed. The safer solution is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, lifecycle handling, docs, and contract tests.

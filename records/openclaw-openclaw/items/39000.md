## Summary

Keep open: current main and v2026.6.11 still do not expose a general plugin-to-plugin Gateway method caller. The existing dispatch helper is intentionally limited to authenticated plugin HTTP routes, and the remaining work is a public Plugin SDK and security-boundary design decision.

## What This Changes

The issue requests a plugin SDK API for one plugin to call another registered Gateway method from ordinary plugin code.

## Best Possible Solution

Keep this as the canonical maintainer design item for a safe inter-plugin Gateway-call SDK surface with caller attribution, explicit exposure or allowlisting, lifecycle semantics, docs, and contract tests.

## Reproduction Assessment

Yes. Source inspection on current main shows plugins can register Gateway methods and the in-process dispatcher can use active plugin handlers, but ordinary plugin runtime/hooks/services still have no general caller; the only public SDK dispatcher is restricted to authenticated plugin HTTP-route scopes.

## Solution Assessment

No for the raw callGatewayMethod(method, params) shape as proposed. The safer solution is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, lifecycle handling, docs, and contract tests.

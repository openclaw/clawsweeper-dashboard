## Summary

Keep open: current main now has trusted-official `api.runtime.gateway.request`, but ordinary external plugin-to-plugin Gateway calls are still rejected, so the requested public Plugin SDK boundary remains unresolved.

## What This Changes

Request a plugin API that lets one plugin invoke Gateway methods registered by another plugin.

## Best Possible Solution

Keep the current trusted-only helper, then design a narrow external inter-plugin Gateway contract with explicit allowlisting, caller identity, scopes, docs, and contract tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should ordinary external plugins be allowed to invoke plugin-registered Gateway methods, and if so should access use raw method names, manifest-declared allowlists, or typed capability/service contracts?

Rationale: The remaining request changes the public Plugin SDK authorization boundary; automation cannot choose which third-party plugins may call which Gateway methods or how sensitive and mutating methods are exposed.

Likely owner: steipete

Owner reason: He merged the current trusted-only Gateway runtime caller and is the strongest available owner signal for the permanent Plugin SDK/Gateway boundary.

Owner confidence: high

Options:

- **Design a narrow external contract (recommended):** Expose only approved or manifest-declared methods/capabilities with caller attribution, scopes, trust-tier behavior, docs, and contract tests.
- **Keep trusted-official only:** Document that community plugins cannot use in-process Gateway RPC dispatch unless promoted to a trusted official install path.
- **Allow broad raw dispatch:** Expose a generic method-string caller to more plugins and accept the larger compatibility and security surface as a deliberate product decision.

## Reproduction Assessment

Yes. Source and tests on current main show plugins can register Gateway methods and trusted official plugins can call Gateway methods, but ordinary external plugins are rejected from `api.runtime.gateway.request`.

## Solution Assessment

No for the proposed raw `api.callGatewayMethod(method, params)` shape. A safer solution needs a maintainer-approved SDK contract that defines caller identity, allowed methods, trust tier, and documentation before broad external use.

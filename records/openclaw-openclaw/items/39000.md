## Summary

Keep open: current main still does not provide an ordinary plugin-to-plugin Gateway method caller. The available dispatcher is intentionally limited to authenticated plugin HTTP routes, so this remains a Plugin SDK product and security-boundary decision.

## What This Changes

Request to add a plugin-facing `callGatewayMethod` API so one plugin can invoke another plugin's registered Gateway RPC method.

## Best Possible Solution

Keep this as the canonical design item for a narrow authorized Plugin SDK inter-plugin or host Gateway-call contract with caller attribution, explicit exposure rules, docs, and contract tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose an ordinary plugin runtime caller for plugin-registered Gateway methods, and should that surface be raw dispatch, an allowlisted request API, or typed service/capability contracts?

Rationale: This changes the public Plugin SDK and Gateway authorization boundary, so automation cannot safely choose the permanent API shape or security model.

Likely owner: steipete

Owner reason: He introduced the current route-scoped dispatch contract and is the strongest history match for the Gateway/Plugin SDK boundary.

Owner confidence: high

Options:

- **Design a narrow authorized SDK contract (recommended):** Expose only approved methods or typed capabilities with plugin caller attribution, explicit authorization, docs, and contract tests.
- **Keep route-scoped dispatch only:** Decline ordinary plugin-to-plugin Gateway calls for now and direct plugins to existing HTTP route or purpose-built capability seams.
- **Allow raw Gateway dispatch:** Expose a generic method-string caller and accept the larger compatibility and security surface as a maintainer-owned product decision.

## Reproduction Assessment

Yes. Source inspection on current main shows plugins can register Gateway methods, but ordinary plugin runtime/hooks/services still have no general caller; the only public dispatcher is restricted to authenticated plugin HTTP-route scopes.

## Solution Assessment

No for the raw `callGatewayMethod(method, params)` shape as proposed. The safer solution is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, lifecycle handling, docs, and contract tests.

Keep open: current main and v2026.6.11 still do not provide an ordinary plugin-to-plugin Gateway method caller. The remaining work is a public Plugin SDK and Gateway authorization design decision, not conservative cleanup.

## What This Changes

Keep this as the canonical design item for a narrow, authorized plugin Gateway-call or inter-plugin capability contract with caller attribution, explicit exposure rules, docs, and contract tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose plugin-to-plugin Gateway method calls, and if so should the permanent SDK surface be a raw method-string caller, an allowlisted Gateway request API, or a typed service/capability contract?

Rationale: The choice changes the public Plugin SDK and the Gateway authorization boundary, so automation should not pick the method exposure, caller-attribution, or compatibility contract.

Likely owner: steipete

Owner reason: He has the strongest available history signal for Gateway method policy and plugin architecture decisions adjacent to this API boundary.

Owner confidence: medium

Options:

- **Design a narrow authorized SDK contract (recommended):** Expose only approved methods or typed capabilities with plugin caller attribution, explicit authorization, documentation, and contract tests.
- **Keep only route-scoped dispatch:** Decline ordinary plugin-to-plugin Gateway calls for now and require plugins to use existing HTTP route or capability seams.
- **Allow raw Gateway method dispatch:** Expose a generic method-string caller and explicitly accept the larger security and compatibility surface as a product decision.

## Reproduction Assessment

Yes. Source inspection on current main shows plugins can register Gateway methods, but ordinary plugin runtime/hooks/services still have no general caller; the only public SDK dispatcher is restricted to authenticated plugin HTTP-route scopes.

## Solution Assessment

No for the raw `callGatewayMethod(method, params)` shape as proposed. The safer solution is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, docs, and contract tests.

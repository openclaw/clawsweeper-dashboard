## Label Justifications

- `P2`: This is a real Plugin SDK capability gap for advanced integrations, but it is not an urgent core runtime outage.
- `impact:security`: The requested surface would let plugin code invoke Gateway methods, so authorization, trust tier, and sensitive method exposure are central to the issue.
- `maturity:stable`: The issue affects the M4 Stable `gateway-runtime` surface, specifically the Stable `Gateway RPC APIs and Events` category.

## Summary

Keep open: current main partially addresses this space with trusted-official `api.runtime.gateway.request`, but ordinary external plugins are still intentionally rejected, so the reported community plugin-to-plugin Gateway-call use case remains a product/security-boundary decision.

## What This Changes

Requests a public plugin API for one plugin to invoke another plugin's registered Gateway method instead of relying on message parsing, direct sharing, or file coupling.

## Best Possible Solution

Keep the trusted-official helper, then design a narrow external inter-plugin contract with manifest or capability declarations, caller attribution, scopes, sensitive-method policy, docs, and contract tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should ordinary external plugins be allowed to invoke plugin-registered or host Gateway methods, and if so should access be raw, manifest-allowlisted, or exposed through typed service/capability APIs?

Rationale: This changes the public Plugin SDK authorization boundary, and automation cannot safely choose which third-party plugins may invoke which Gateway methods or how sensitive and mutating methods are exposed.

Likely owner: steipete

Owner reason: steipete merged the current trusted-only helper and is the strongest history match for the Gateway/Plugin SDK boundary decision.

Owner confidence: high

Options:

- **Design a narrow external contract (recommended):** Expose only approved or manifest-declared methods/capabilities with caller identity, trust-tier behavior, docs, and contract tests.
- **Keep trusted-official only:** Document that community plugins cannot use in-process Gateway RPC dispatch unless promoted to a trusted official install path.
- **Allow broad raw dispatch:** Expose a generic method-string caller to more plugins and accept the larger compatibility and security surface as a deliberate product decision.

## Reproduction Assessment

Yes. Source and tests on current main show the call side exists only for bundled or trusted official plugins, while the reported ordinary external plugin caller is rejected.

## Solution Assessment

No for the proposed raw `api.callGatewayMethod(method, params)` shape. The safer solution is a maintainer-approved narrow SDK contract that defines caller identity, allowed methods, trust tier, and docs before broad external use.

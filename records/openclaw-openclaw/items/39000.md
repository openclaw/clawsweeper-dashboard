## Summary

Keep open: current main now has a trusted-official `api.runtime.gateway.request` subset, but arbitrary external plugin-to-plugin Gateway calls like the reported metabolism-to-stability use case are still intentionally blocked pending a public SDK and security-boundary decision.

## What This Changes

The issue requests a plugin API caller for invoking Gateway methods registered by other plugins.

## Best Possible Solution

Define a narrow, documented PluginRuntime Gateway contract that preserves plugin caller identity and allows only approved cross-plugin or host methods, with contract tests for allowed and denied calls.

- **Keep Gateway calls trusted-only:** Treat the current bundled/trusted-official `runtime.gateway.request` surface as the supported boundary and decline ordinary external plugin-to-plugin calls.
- **Allow raw method dispatch:** Expose a generic method-string caller to plugins and accept the larger compatibility and security surface as an intentional product decision.

Yes. Source inspection confirms the exact `api.callGatewayMethod` API is absent and the current main `runtime.gateway.request` path rejects ordinary external plugins, so the reported external plugin-to-plugin use case remains reproducible from source.

## Solution Assessment

No for the raw `callGatewayMethod(method, params)` shape as proposed. A maintainer-approved contract with caller attribution, explicit method exposure or allowlisting, authorization rules, docs, and tests is the safer path.

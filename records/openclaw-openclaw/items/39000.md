## Summary

Keep open: current main and v2026.6.11 still do not provide an ordinary plugin-to-plugin Gateway method caller. The remaining work is a public Plugin SDK and Gateway authorization design decision, not conservative cleanup.

## What This Changes

The issue requests a Plugin SDK API for one plugin to invoke Gateway methods registered by another plugin.

## Best Possible Solution

Keep this as the canonical design item for a narrow, authorized Plugin SDK inter-plugin or host Gateway-call contract with caller attribution, explicit exposure rules, docs, and contract tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose a plugin runtime caller for plugin-registered Gateway methods, and should that surface be raw method dispatch, an allowlisted request API, or a typed service/capability contract?

Rationale: The implementation shape changes the public Plugin SDK and Gateway authorization boundary, so automation cannot safely choose the method exposure, caller identity, or API permanence policy.

Likely owner: steipete

Owner reason: He introduced the current route-scoped dispatch contract and is the strongest history match for the Gateway/Plugin SDK boundary.

Owner confidence: high

Options:

- **Design a narrow authorized SDK contract (recommended):** Expose only approved methods or typed capabilities with plugin caller attribution, explicit authorization, docs, and contract tests.
- **Keep the route-scoped helper only:** Decline ordinary plugin-to-plugin Gateway calls and ask plugins to use existing HTTP route or capability seams instead.
- **Allow raw Gateway dispatch:** Expose a generic method-string caller, accepting the larger security and compatibility surface as a product decision.

## Reproduction Assessment

Yes. Source inspection on current main and v2026.6.11 shows plugins can register Gateway methods, but ordinary plugin runtime/hooks/services still have no general caller; the only public SDK dispatcher is restricted to authenticated plugin HTTP-route scopes.

## Solution Assessment

No for the raw `callGatewayMethod(method, params)` shape as proposed. The safer solution is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, lifecycle handling, docs, and contract tests.

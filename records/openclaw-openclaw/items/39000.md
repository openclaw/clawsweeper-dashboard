## What This Changes

## Best Possible Solution

Keep this as the canonical design item for a narrow, authorized Plugin SDK Gateway-call contract with caller attribution, explicit exposure rules, docs, and contract tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should ordinary external plugins be allowed to invoke plugin-registered Gateway methods, and if so under what authorization model beyond the current bundled/trusted-official-only `api.runtime.gateway.request` path?

Rationale: The remaining behavior changes the public Plugin SDK and Gateway authorization boundary, so automation cannot safely choose between raw dispatch, allowlisted capabilities, trusted-official gating, or no third-party access.

Likely owner: steipete

Owner reason: steipete merged the current trusted-only Gateway runtime path and has the clearest recent routing signal for this Gateway/Plugin SDK security boundary.

Owner confidence: high

Options:

- **Design a narrow authorized contract (recommended):** Expose only approved Gateway methods or typed capabilities with caller attribution, explicit trust or allowlist policy, docs, and contract tests.
- **Keep trusted-only access:** Treat current main as the intended boundary and tell external plugins to use another documented seam or become trusted official installs.
- **Allow raw method dispatch:** Expose a generic method-string caller to more plugins while consciously accepting the broader security and compatibility surface.

## Reproduction Assessment

Yes. Source inspection shows current main rejects arbitrary external plugin Gateway requests, and v2026.6.11 does not ship `PluginRuntime.gateway` at all, so the third-party inter-plugin use case remains source-reproducible.

## Solution Assessment

No for the raw `api.callGatewayMethod(method, params)` shape as proposed. The safer path is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, authorization rules, docs, and tests.

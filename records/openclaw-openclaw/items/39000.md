## Summary

Keep open: current main partially adds trusted-only `api.runtime.gateway.request`, but arbitrary external plugin-to-plugin Gateway calls remain intentionally rejected, so the remaining work is a product and security API decision rather than cleanup.

## What This Changes

The issue requests a Plugin SDK/API method for one plugin to invoke Gateway methods registered by the host or another plugin.

## Best Possible Solution

Keep this as the canonical design item for deciding whether external plugins may call plugin-owned Gateway methods, then land either a documented trust/capability contract with caller attribution and tests or an explicit decision to keep the current trusted-only surface.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw extend the current trusted-only `api.runtime.gateway.request` surface to support arbitrary external plugin-to-plugin Gateway method calls, and what authorization contract should govern that access?

Rationale: Current main intentionally restricts Gateway runtime requests to bundled or trusted official plugins, so widening the public SDK surface changes product direction and the plugin security boundary.

Likely owner: steipete

Owner reason: He is the strongest history match for the plugin architecture, Gateway dispatch contract, and current partial Gateway runtime caller merge.

Owner confidence: high

Options:

- **Design an authorized external-plugin contract (recommended):** Allow external plugin-to-plugin calls only through explicit trust, capability, or allowlist metadata with caller attribution, docs, and contract tests.
- **Keep trusted-only Gateway requests:** Treat the current bundled/trusted-official surface as the supported contract and require community plugins to use other extension seams or trusted official distribution.
- **Expose raw method dispatch broadly:** Permit arbitrary plugin method strings and accept the wider compatibility and security surface as an intentional product decision.

## Reproduction Assessment

Yes. Current main source and tests show `api.runtime.gateway.request` exists but rejects arbitrary external plugins, which preserves the reported community plugin-to-plugin gap.

## Solution Assessment

No for the raw `callGatewayMethod(method, params)` shape as proposed. A safer solution is a maintainer-approved SDK contract with caller identity, explicit method exposure or allowlisting, docs, and contract tests.

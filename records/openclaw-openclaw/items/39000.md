## Summary

Keep open: current main and v2026.6.11 still do not expose a general `api.callGatewayMethod()` or ordinary `PluginRuntime.gateway` caller for plugin-to-plugin registered Gateway methods. The existing Gateway dispatcher is deliberately limited to authenticated plugin HTTP routes, so the remaining work is a public Plugin SDK and security-boundary decision.

## What This Changes

Request to add a plugin API for invoking another plugin's registered Gateway method from ordinary plugin code.

## Best Possible Solution

Keep this as the canonical inter-plugin Gateway-call API design item; if approved, add a narrow SDK contract with caller attribution, explicit method exposure or allowlisting, lifecycle/replay semantics, docs, and contract tests while keeping raw Gateway dispatch internal.

## Reproduction Assessment

Yes. Source inspection on current main and v2026.6.11 shows plugins can register Gateway methods, but ordinary plugin runtime/hooks/services have no matching general caller; the only SDK dispatcher is reserved for authenticated plugin HTTP routes.

## Solution Assessment

Unclear as proposed. The raw `callGatewayMethod(method, params)` shape is probably too broad; the safer solution needs maintainer-approved caller identity, method exposure or allowlisting, authorization rules, lifecycle behavior, docs, and tests.

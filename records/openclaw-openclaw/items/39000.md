## Summary

Keep open: current main added a main-only `api.runtime.gateway.request` surface for bundled or trusted official plugins, but the implementation, docs, and tests still reject arbitrary external plugins, so the linked metabolism/stability inter-plugin use case remains a product and security-boundary decision.

## What This Changes

The issue requests a plugin SDK method for calling registered Gateway methods from plugin code so plugins can communicate through the Gateway RPC surface.

## Best Possible Solution

Keep the trusted-official `api.runtime.gateway.request` surface and design any third-party inter-plugin calls as an explicit authorized SDK or capability contract with docs and contract tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw broaden `api.runtime.gateway.request` beyond bundled/trusted official plugins to support third-party inter-plugin Gateway calls, or keep third-party plugins on a different capability/service contract?

Rationale: The remaining choice changes the public Plugin SDK and Gateway authorization boundary, and automation cannot safely choose whether arbitrary external plugins may invoke method-string Gateway RPCs.

Likely owner: steipete

Owner reason: This is primarily a Plugin SDK and Gateway security-boundary product decision rather than a mechanical follow-up to the partial implementation.

Owner confidence: medium

Options:

- **Design an explicit external-plugin contract (recommended):** Add a documented third-party inter-plugin or capability API with caller attribution, permission checks, allowed methods or typed services, and contract tests.
- **Keep the trusted-only Gateway request boundary:** Treat `api.runtime.gateway.request` as an official-plugin-only surface and ask third-party plugins to use another explicit service/capability mechanism.
- **Allow raw method-string dispatch broadly:** Expose generic Gateway method calls to external plugins, accepting a larger compatibility and authorization surface.

## Reproduction Assessment

Yes. Source inspection on current main shows a trusted-only `api.runtime.gateway.request` caller, and the tests/docs explicitly reject arbitrary external plugins, which leaves the linked external plugin-to-plugin path unsupported.

## Solution Assessment

No for the raw `api.callGatewayMethod(method, params)` shape as proposed. The safer path is a maintainer-approved SDK or capability contract with explicit authorization instead of unrestricted Gateway method dispatch.

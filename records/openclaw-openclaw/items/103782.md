## Label Justifications

- `P2`: A stable browser reference can silently direct a same-agent action to the wrong signed-in page or workflow, but the defect is bounded to browser automation and does not cross the per-agent trust boundary.
- `impact:other`: The concrete impact is browser target-identity drift and wrong-tab action targeting, which is meaningful but outside the narrower owned impact categories.

## Summary

Keep this issue open: current main and the latest release still contain both reported wrong-tab paths, existing tests do not cover duplicate-URL replacement groups, and no duplicate or implementation PR now owns the work.

## What This Changes

Prevent browser aliases, labels, and sticky selection from transferring to the wrong tab during ambiguous duplicate-URL target replacement.

## Best Possible Solution

Use one complete-set reconciliation rule across transports: migrate only singleton or unique one-to-one URL groups, issue fresh monotonic handles for ambiguous groups, update sticky selection only for proven migration, and require explicit reselection after unresolved prior-target loss.

## Reproduction Assessment

Yes, at high confidence from current-main source: two stale and two new targets sharing one URL all satisfy the pairwise confidence predicate, and stale iteration plus `find` determines which replacement inherits each alias. This read-only review did not execute the live browser scenario.

## Solution Assessment

Yes. Complete-set uniqueness in the existing alias owner plus fail-closed unresolved sticky selection is the narrowest maintainable correction and avoids new config, protocol, persistence, compatibility, or parallel identity surfaces.

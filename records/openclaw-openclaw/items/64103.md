## Summary

Keep open: current main and the latest release still expose terminal-looking session `status` values without a model-visible resumability signal or status-semantics guidance, and the previously linked fix PR is closed unmerged.

## What This Changes

The issue requests clearer session status semantics or resumability metadata so agents resume existing sessions instead of spawning duplicates after last-turn `done`, `failed`, or `timeout` states.

## Best Possible Solution

Define a backward-compatible session resumability/status-semantics contract, then land a focused fix with agent-visible guidance and regression coverage while avoiding breaking status renames unless maintainers explicitly approve versioning or migration.

Owner confidence: medium

Options:

- **Add resumability metadata and guidance (recommended):** Expose a backward-compatible `resumable` signal where maintainers want the contract to live, and update model-facing wording/tests so agents prefer `sessions_send` for resumable ended rows.
- **Rename or version status values:** Make the status names semantically precise, but require explicit compatibility/versioning work because the existing values are already shipped.
- **Keep the hint agent-only:** Leave Gateway/client rows unchanged and add only model-facing sessions_list guidance if maintainers do not want to grow the shared row contract.

## Reproduction Assessment

Yes, from source inspection: current main exposes terminal-looking statuses without a resume signal, while `sessions_send` can reactivate ended subagent sessions. I did not run a live orchestrator reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the contract. Additive metadata plus model-facing guidance appears safer than renaming shipped status values, but the Gateway-row versus agent-projection scope is a product/API decision.

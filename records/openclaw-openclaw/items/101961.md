## Label Justifications

## Summary

Keep open: current main has a `node_exec` dynamic tool, but it is only appended when the effective Codex exec host is already `node`; this issue asks for a mixed-session path where local Codex execution stays default and remote node exec is exposed as a separate, soft-failing capability.

## What This Changes

Request first-class scoped node-host shell execution for Telegram/Codex agent lanes, with retryable stale-node failure semantics and local gateway exec left as the default.

## Best Possible Solution

Define a maintainer-approved mixed-session `node_exec`/`node_process` or node-tool contract that keeps Codex-native local execution available, pins host/node internally, preserves `systemRunPlan` approval binding, and returns a structured retryable node-unavailable result for stale nodes.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Codex app-server sessions expose a separate remote-node exec tool when the effective exec host remains `auto`/local, and what structured stale-node failure contract should that tool return?

Rationale: Automation cannot safely decide whether to broaden model-visible remote shell access alongside native local shell, because that changes the operator-controlled remote-code-execution boundary and overlaps existing node approval and stale-node work.

Likely owner: steipete

Owner reason: This decision spans the current Codex dynamic-tool path, gateway/node execution boundary, and security policy direction where steipete has the strongest recent routing signal.

Owner confidence: medium

Options:

- **Approve Explicit Mixed-Session Node Exec (recommended):** Expose a pinned OpenClaw-owned node exec/process surface for configured nodes, require the existing approval binding, and return retryable structured unavailable results before timeouts feel like hangs.
- **Require Whole-Session Host Node:** Keep `node_exec` visible only when the session's effective exec host is `node`, and document that mixed local-plus-node execution is not supported yet.
- **Defer To Node Tool Design:** Route this through broader node-registered or node-hosted tool work instead of adding a generic shell surface now.

## Reproduction Assessment

No live high-confidence reproduction was run against a Telegram/Codex lane and MacBook node. Source inspection does reproduce the missing mixed-session path: `auto` resolves to local/sandbox, and `node_exec` is only appended when the effective exec host is `node`.

## Solution Assessment

No, the existing `node_exec` implementation is only a partial solution for this report. The best path is a maintainer-approved mixed-session remote-node exec surface with explicit security and stale-node semantics, while leaving the approval-denial and node-readiness subproblems to their canonical related threads where appropriate.

## Summary

Keep open: current main and v2026.6.11 contain the partial `node_exec` dynamic tool, but it is still gated on the session's effective exec host being `node`; the requested mixed local-Codex plus scoped remote-node exec path and structured stale-node soft-fail behavior remain unresolved.

## What This Changes

The issue requests a first-class agent-lane path for approval-backed shell execution on a selected paired node while local exec remains the default, plus retryable structured failures for stale/offline nodes.

## Best Possible Solution

Define a maintainer-approved mixed-session `node_exec`/`node_process` contract that pins host/node internally, preserves `systemRunPlan` approval binding, keeps local Codex execution available, and returns a structured retryable node-unavailable result before long timeouts.

- **Defer to broader node-tool design:** Route this through node-hosted tool/capability work instead of adding a generic shell surface now.

No live high-confidence reproduction was run against a Telegram/Codex lane and MacBook node. Source inspection does reproduce the missing mixed-session path because `node_exec` is appended only when the effective exec host is already `node`.

## Solution Assessment

No, the current shipped `node_exec` path is only a partial solution for this issue. The best path is a maintainer-approved mixed-session remote-node exec surface with explicit security and stale-node semantics.

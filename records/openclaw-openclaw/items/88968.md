## Label Justifications

- `P1`: The PR targets a broken agent reply workflow where repeated memory-flush failure can prevent real user replies from being delivered.
- `merge-risk: 🚨 compatibility`: The diff changes the behavior of the existing notifyUser config option for users who already opted into compaction notices.
- `merge-risk: 🚨 message-delivery`: The diff intentionally changes memory-flush visible errors from terminal reply payloads into logged maintenance failures while the main reply continues.
- `merge-risk: 🚨 session-state`: The diff automatically rotates exhausted sessions and clears persisted compaction/memory-flush state, affecting active session identity and recovery behavior.

## Summary

Keep open for maintainer review: the patch appears correct and well-proven, but it intentionally changes fail-open reply delivery, exhausted-session rotation, and the meaning of an existing user-notice option.

## What This Changes

The PR logs memory-flush maintenance errors instead of failing the user reply, rotates exhausted sessions while preserving old transcripts, clears stale memory-flush state on reset, and updates docs/tests for the degraded notice behavior.

## Best Possible Solution

Land or revise one owner-approved fail-open recovery that preserves the prior transcript, lets normal replies continue after memory-flush exhaustion, and documents the accepted notifyUser behavior.

## Reproduction Assessment

Yes. Source inspection shows current main and v2026.6.11 fail the reply when memoryFlush emits visible error payloads before the main agent turn; I did not run a live provider-crash repro in this read-only review.

## Solution Assessment

Yes for the code shape: keeping recovery in runReplyAgent, reusing resetReplyRunSession, preserving old transcripts, and adding regression coverage is a bounded fix. The remaining question is maintainer acceptance of the fail-open rotation and notice semantics, not a discrete patch defect.

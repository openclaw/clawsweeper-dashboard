- `P1`: The PR addresses a real agent/channel reply-delivery wedge where memory-flush maintenance failure can prevent normal user replies.

- `merge-risk: 🚨 message-delivery`: The patch changes memory-flush visible errors from terminal reply payloads into log-and-continue behavior, directly changing reply delivery semantics.

## Summary

Keep open for maintainer review: current main still has the terminal visible-memory-flush abort path, and this PR is the active candidate with credible live Gateway proof. I found no blocking code defect, but the fail-open session rotation and expanded notice behavior are compatibility-sensitive.

## What This Changes

The branch changes reply pre-run memoryFlush handling to log visible flush errors, continue the main reply, rotate exhausted sessions without deleting old transcripts, clear flush state on reset, and document the expanded `notifyUser` notice behavior.

## Best Possible Solution

Land this PR or an equivalent maintainer-approved recovery after accepting the fail-open, non-destructive session-rotation semantics and after exact-head CI completes; keep the canonical issue open until that recovery is merged.

## Reproduction Assessment

Yes. Source inspection of current main shows visible memory-flush error payloads still call `replyOperation.fail("run_failed")` before the main reply; the contributor also supplied a live Gateway run showing the patched path continues replies under repeated mock 500 flush failures.

## Solution Assessment

Yes, as a bounded mitigation for the delivery wedge: it keeps memoryFlush failure tracking in the existing helper, changes only the outer reply policy, and rotates on exhaustion without deleting old transcripts. The remaining question is maintainer acceptance of fail-open recovery semantics, not a mechanical code defect I can prove from this pass.

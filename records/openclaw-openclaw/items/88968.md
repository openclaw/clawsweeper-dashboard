## Label Justifications

- `P1`: The PR targets a broken agent reply workflow where memory-flush failure can prevent real user replies from being delivered.
- `merge-risk: 🚨 compatibility`: The diff changes the behavior of the existing `notifyUser` config option for users who already opted into compaction notices.
- `merge-risk: 🚨 message-delivery`: The diff intentionally changes memory-flush visible errors from terminal reply payloads into logged maintenance failures while the main reply continues.
- `merge-risk: 🚨 session-state`: The diff automatically rotates exhausted sessions and clears persisted compaction/memory-flush state, which can affect active session identity and recovery behavior.

## Summary

Keep open: current main and the latest release still abort the reply when memory flush emits visible errors, while this PR changes that path and adds focused tests/proof. I found no concrete line-level blocker, but the session rotation, message-delivery, and expanded `notifyUser` behavior need maintainer signoff before merge.

## What This Changes

The PR changes `runReplyAgent` so memory-flush maintenance errors are logged instead of returned as terminal replies, rotates exhausted sessions while preserving old transcripts, clears stale flush state on reset, and updates tests/docs for the expanded notice behavior.

## Best Possible Solution

Land or revise one owner-approved fail-open recovery that logs flush failures, rotates exhausted sessions without deleting the prior transcript, and documents the existing `notifyUser` notice expansion after current-head validation is acceptable.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: current main and `v2026.6.11` turn visible memory-flush payloads into `replyOperation.fail("run_failed")` before the main reply. I did not run a live repro in this read-only review.

## Solution Assessment

Yes, this appears to be a good bounded fix shape: the changed runtime path stays in `runReplyAgent`, uses existing reset/session helpers, preserves old transcripts, and adds regression coverage. The remaining question is maintainer acceptance of the fail-open rotation and notice semantics, not a mechanical code defect.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.89

Full review comments:

- **[P1] Require opt-in before loading `.backupignore`:** `src/infra/backup-exclude.ts:189-194`
  - body: This runs for every backup unless `--include-all` is set, even when the user passed no exclude flags. A writable state file can silently change archive contents, which breaks the PR's no-flag compatibility promise and can make restores incomplete. Load this file only through an explicit flag or a maintainer-approved default migration.
  - confidence: 0.93
- **[P1] Apply excludes to external backup assets:** `src/infra/backup-exclude.ts:362-364`
  - body: The filter returns `true` for every entry outside `baseDir`, while `createBackupArchive()` constructs one filter rooted at the state directory. External workspaces, config, or credentials therefore remain archived in full despite `--exclude` or `.backupignore`; a warning does not provide the requested filtering and can still leak or bloat backups.
  - confidence: 0.91
- **[P2] Avoid rescanning the full archive during create:** `src/infra/backup-create.ts:528-535`
  - body: After writing the backup, this reads the complete `.tar.gz` and stores every entry name before publishing. For the large-state backups this PR targets, that adds a second full archive pass and O(entry count) memory, which can recreate the stall or memory-pressure class the change is supposed to reduce.
  - confidence: 0.88
- **[P2] Preserve gitignore rule order:** `src/infra/backup-exclude.ts:225-233`
  - body: This deduplicates rules before passing them to `ignore`, but gitignore rules are order-sensitive and duplicates can intentionally re-ignore after a negation, such as `*.log`, `!important.log`, `*.log`. This was visible in earlier review cycles and was also noted in an older review thread, but it still means files can be included or excluded contrary to the user's rule file.
  - late: true
  - confidence: 0.84

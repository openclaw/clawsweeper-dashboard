## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.88

Full review comments:

- **[P1] Require opt-in before loading `.backupignore`:** `src/infra/backup-exclude.ts:170-178`
  - body: This auto-loads `stateDir/.backupignore` even when the user did not pass `--exclude-file` or an explicit opt-in flag. An existing file can silently change catastrophic backup contents after upgrade, so this should be behind an explicit flag or documented config choice instead of an ambient state-dir file.
  - confidence: 0.91
- **[P1] Apply excludes to every backup asset root:** `src/infra/backup-create.ts:378-388`
  - body: This warning acknowledges that external workspaces and custom config paths bypass the exclude filter, but the backup still archives them in full. A user who passes `--exclude '*.pem'` or `--smart-exclude` can still get sensitive or bulky external assets in the archive, so the filter needs per-asset roots or the command should fail/require opt-in for that gap.
  - confidence: 0.9
- **[P2] Avoid rescanning large archives during create:** `src/infra/backup-create.ts:528-529`
  - body: The create path reads the finished `.tar.gz` back into an array of every entry and then scans it for each asset. On the multi-GB backups this PR targets, that adds a full second pass plus O(entry count) memory, which can recreate the stall/OOM class the feature is meant to avoid.
  - confidence: 0.86
- **[P2] Preserve ordered gitignore rules:** `src/infra/backup-exclude.ts:214-221`
  - body: Deduplicating patterns before passing them to `ignore` changes gitignore's order-sensitive semantics. A sequence like `*.log`, `!important.log`, `*.log` intentionally re-excludes the file, but this code drops the final duplicate and flips the result.
  - confidence: 0.87

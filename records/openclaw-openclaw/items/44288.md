## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P1] Require explicit opt-in for `.backupignore`:** `src/infra/backup-exclude.ts:187-194`
  - body: `resolveExcludePatterns` auto-loads `stateDir/.backupignore` for every backup unless `--include-all` is passed. That makes an existing or injected state-dir file silently change backup contents without the user choosing an exclude file, which is a new restore/security policy surface. Keep this explicit, or get maintainer-approved default/docs/security proof before merge.
  - confidence: 0.9
- **[P1] Apply excludes to each backup asset root:** `src/infra/backup-create.ts:364-368`
  - body: The exclude filter is rooted at `stateDir`, so external workspaces and custom config/credential assets bypass all exclude patterns and are archived in full. A warning is not enough for a flag named `--exclude`: users can still unintentionally back up the large or sensitive files they explicitly tried to omit.
  - confidence: 0.9
- **[P2] Avoid rescanning large archives during create:** `src/infra/backup-create.ts:528-529`
  - body: The post-create integrity check reads the finished `.tar.gz` and stores every entry path in memory on every backup, even when the user did not request `--verify`. That adds a second full archive pass to the large-backup path this PR is trying to improve and can recreate the runtime/memory pressure reported by linked users.
  - confidence: 0.86
- **[P2] Preserve duplicate gitignore rules:** `src/infra/backup-exclude.ts:225-233`
  - body: Gitignore rules are order-sensitive, and `ignore` evaluates the rule list in insertion order. Removing later duplicates changes cases like `*.log`, `!important.log`, `*.log`, where the final duplicate intentionally re-excludes the file.
  - confidence: 0.86

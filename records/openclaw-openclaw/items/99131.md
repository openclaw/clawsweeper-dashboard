- `P1`: The report describes repeated loss of user-visible answers and cascading abandoned background work in a real Claude CLI gateway workflow.

## Summary

Keep open. Current main and the latest release still route an empty Claude CLI JSONL result through `empty_response` and reused-session clearing, while the overlapping open PRs address adjacent parser/classifier pieces but do not yet prove the notification-consuming resume path will deliver or preserve the later real answer.

## What This Changes

The issue reports that Claude CLI reused sessions with queued task notifications emit a synthetic empty result before the real answer, causing OpenClaw to clear the session and lose in-flight work.

## Best Possible Solution

Coordinate this with the open Claude CLI parser/classifier PRs and land a focused fix that detects the synthetic notification-consuming resume result before `empty_response` clearing, then either keeps reading the same process or preserves the session with a well-tested retry/status path.

## Reproduction Assessment

Yes, at source level with strong report evidence. The issue's logs match the current path: empty Claude CLI output becomes `empty_response`, and any `FailoverError` on a reused Claude CLI session clears the stored binding; I did not run a live Claude Code task-notification repro.

## Solution Assessment

Unclear. Detecting the exact synthetic placeholder before session clearing is the right boundary, but maintainers still need to choose whether the runtime should keep reading the same process, retry on the same session, or route through the existing fallback/status machinery.

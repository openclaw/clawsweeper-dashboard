## Summary

Keep open. Current main still converts empty Claude CLI output into `empty_response` and clears the reused Claude CLI session on any `FailoverError`; the open closing PR is a mitigation candidate, not a merged fix for the lost later-answer cascade.

## What This Changes

The issue reports Claude CLI reused sessions with queued task notifications emitting a synthetic empty result that OpenClaw treats as `empty_response`, clearing session state before the later real response can be delivered.

## Best Possible Solution

Review the open closing PR as a mitigation candidate, coordinate it with the synthetic-placeholder parser work, and close this issue only after a merged fix proves the notification-consuming resume path no longer clears or abandons the reused Claude session before the real answer is handled.

## Reproduction Assessment

Yes, at source level. The issue logs match current main: empty Claude CLI output becomes `FailoverError(reason="empty_response")`, and any `FailoverError` on a reused Claude CLI session clears the stored binding; I did not run a live queued task-notification repro.

## Solution Assessment

Unclear as a complete fix. Preserving the binding is a useful mitigation, but maintainers still need to choose whether the runtime should keep reading the same process, retry the same session, classify the synthetic placeholder through fallback/status, or combine those paths.

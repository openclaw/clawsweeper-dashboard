## Summary

Keep open. Current main and the latest release still lack generic action-aware tool allow/deny; the message-specific action allowlist is only a partial workaround, while gateway remains a single multiplexed tool and the requested trusted approval/bypass semantics still need maintainer security design.

## What This Changes

Request action-aware tool policy so operators can deny side-effecting actions such as message sends or gateway config writes while keeping read/search actions available.

## Best Possible Solution

Define a maintainer-approved typed action-aware tool-policy contract with documented grammar, wildcard behavior, precedence, and pre-execution enforcement for multiplexed tools such as message and gateway.

## Reproduction Assessment

Yes, as a source-level gap: current main filters generic tool policy by whole tool name before action arguments are read, so entries such as message:send or gateway:config.patch cannot express the requested policy today.

## Solution Assessment

Unclear until maintainers choose the security model. The maintainable direction is a generic action-aware policy grammar and enforcement boundary, not a one-off message or gateway shim.

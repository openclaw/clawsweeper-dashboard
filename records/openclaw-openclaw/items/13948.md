## Summary

Keep open. Current main still lacks a generic action-level `tools.allow`/`tools.deny` contract; the message-only action allowlist and plugin hook paths are useful partial alternatives, but they do not cover generic deny syntax, gateway action splits, or trusted approval-bypass semantics.

## What This Changes

Request a typed config contract for allowing or denying individual actions inside multiplexed tools such as `message:send` and `gateway:config.patch` instead of only whole-tool policy.

## Best Possible Solution

Define a maintainer-approved, typed action-aware tool-policy contract with documented grammar, wildcard behavior, precedence, and pre-execution enforcement for multiplexed tools.

## Reproduction Assessment

Yes. As a source-level gap, current main filters generic tool policy by whole tool name before action arguments are read, so entries such as `message:send` or `gateway:config.patch` cannot express the requested policy today.

## Solution Assessment

Unclear until maintainers choose the security model. The maintainable path is a generic action-aware policy grammar and enforcement boundary rather than a one-off message or gateway shim.

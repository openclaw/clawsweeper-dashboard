## Summary

Keep open. Current main still lacks a generic action-aware tool policy contract; the message-specific `tools.message.actions.allow` path is only a partial workaround and does not cover `tools.deny` grammar, gateway actions, or trusted approval-bypass semantics.

## What This Changes

The issue requests action-level tool allow/deny so operators can block sensitive actions such as `message:send` while keeping read/search/react actions available.

## Best Possible Solution

Keep this as the canonical core tracker for a maintainer-approved, typed action-aware tool-policy contract with documented grammar, wildcard behavior, precedence, gateway/message coverage, and trusted approval-path semantics.

## Reproduction Assessment

Yes. Source inspection shows a high-confidence gap: generic tool policy is parsed and applied by whole tool name before `message` or `gateway` action arguments are read, so entries such as `message:send` or `gateway:config.patch` cannot express the requested policy today.

## Solution Assessment

Unclear until maintainers choose the security model. A generic action-aware policy grammar and enforcement boundary is the maintainable direction, but the exact syntax, precedence, wildcard behavior, and trusted bypass semantics need product/security design first.

## Summary

Keep open. Current main still cannot express generic action-level allow/deny such as `message:send` or `gateway:config.patch`; the newer message action allowlist is a useful partial control but does not cover generic policy grammar, gateway actions, or trusted approval-bypass semantics.

## What This Changes

Request action-level tool allow/deny so operators can block side-effecting actions such as `message:send` or `gateway:config.patch` while retaining read-only actions on the same multiplexed tool.

## Best Possible Solution

Define a maintainer-approved, typed action-aware tool-policy contract with documented grammar, wildcard behavior, precedence, and pre-execution enforcement for multiplexed tools such as `message` and `gateway`.

## Reproduction Assessment

Yes, as a source-level gap: current main filters generic tool policy by whole tool name before action arguments are read, so `message:send` and `gateway:config.patch` are not enforceable through `tools.deny` today. I did not run tests because this was a read-only review.

## Solution Assessment

Unclear until maintainers choose the security model. The maintainable direction is a generic action-aware policy grammar and enforcement boundary, not treating the existing message-only action allowlist as a complete solution.

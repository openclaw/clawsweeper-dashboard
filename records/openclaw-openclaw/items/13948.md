## Summary

Keep open. Current main and the latest release have partial safety controls, including message-specific action allowlists and guarded gateway config writes, but they still do not provide a generic action-aware `tools.allow`/`tools.deny` contract for entries like `message:send` or `gateway:config.patch`; the related gateway-specific reports are closed back to this as the canonical tracker, while the open confirmation-gate issue is adjacent rather than a replacement.

## What This Changes

Request action-aware tool policy so operators can deny specific `message` or `gateway` actions while leaving other actions available.

## Best Possible Solution

Keep this as the canonical core tracker for a maintainer-approved, typed action-aware tool-policy contract with documented grammar, wildcard behavior, precedence, trusted-context semantics, and pre-execution enforcement for multiplexed tools such as `message` and `gateway`.

## Reproduction Assessment

Yes. Current source shows generic policy is typed, parsed, and enforced by whole tool name before action arguments are available, so action-qualified entries such as `message:send` or `gateway:config.patch` cannot express the requested policy today.

## Solution Assessment

Unclear until maintainers choose the security model. The maintainable path is a generic action-aware policy contract and enforcement boundary, not a one-off message or gateway shim; the existing message action allowlist is useful but incomplete for this request.

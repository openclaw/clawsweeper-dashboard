## Summary

Keep open. Current main and the latest release still enforce generic tool policy at whole-tool inventory level, while `message` and `gateway` choose individual actions only inside their executors; the remaining work is a core authorization design decision, not a cleanup-close candidate.

## What This Changes

The issue requests action-level tool policy so operators can deny outbound actions such as `message:send` while preserving read/search/react actions.

## Best Possible Solution

Keep this as the canonical core tracker and design a typed, documented action-aware policy contract enforced before multiplexed actions execute, with explicit precedence and trusted-context semantics for `message` and `gateway`.

Yes. Source inspection shows generic tool policy is applied by whole tool name before action arguments are available, so entries like `message:send` or `gateway:config.patch` cannot express the requested policy today.

## Solution Assessment

Unclear until maintainers choose the security model. The maintainable direction is a generic action-aware policy contract and enforcement boundary, not a one-off message or gateway shim.

## Summary

Keep open. Current main still lacks a generic action-aware `tools.allow`/`tools.deny` contract; `tools.message.actions.allow` is a useful message-only partial control, but it does not cover generic deny syntax, gateway action splits, or trusted approval-bypass semantics.

## What This Changes

Request support for action-level tool allow/deny policy so operators can block side-effecting actions such as `message:send` while preserving read-only actions on the same multiplexed tool.

## Best Possible Solution

Define a maintainer-approved, typed action-aware tool-policy contract with documented grammar, wildcard behavior, precedence, and trusted-bypass semantics, enforced before multiplexed tool actions execute.

## Reproduction Assessment

Yes. As a source-level gap, current main filters generic tool policy by whole tool name before action arguments are read, so entries such as `message:send` or `gateway:config.patch` cannot express the requested policy today.

## Solution Assessment

Unclear until maintainers choose the security model. The existing message action allowlist is useful but incomplete; the maintainable path is a generic action-aware policy grammar and enforcement boundary rather than a one-off message or gateway shim.

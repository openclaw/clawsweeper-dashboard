## Summary

Keep open. Current main still lacks the requested generic action-level tool allow/deny contract: base tool policy is typed and enforced by whole tool name, while the newer message action allowlist is message-specific and does not cover gateway actions or trusted approval-bypass semantics.

## What This Changes

The issue requests action-level allow/deny policy so multiplexed tools such as message and gateway can block send/write actions while preserving read-only actions.

## Best Possible Solution

Keep this as the canonical core tracker for a maintainer-approved action-aware tool-policy contract with documented grammar, precedence, wildcard behavior, trusted-context semantics, and regression coverage for message and gateway actions.

## Reproduction Assessment

Yes, source-level. Current main filters tools by whole tool name before reading action arguments, so entries such as message:send or gateway:config.patch cannot express the requested policy today.

## Solution Assessment

Unclear until maintainers choose the security contract. The maintainable path is a generic action-aware policy boundary, not a one-off message or gateway shim.

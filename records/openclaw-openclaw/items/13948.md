## Summary

Keep open. Current main and the latest release still lack a generic action-aware `tools.allow`/`tools.deny` contract: policy types, schema, matching, and inventory filtering remain whole-tool based, while `tools.message.actions.allow` only partially mitigates the message side and does not cover gateway actions or trusted approval-bypass semantics.

## What This Changes

The issue requests action-level tool policy so operators can block side-effecting actions such as message sends or gateway writes while preserving read-style actions on the same multiplexed tool.

## Best Possible Solution

Keep this as the canonical core tracker and design a typed, documented action-aware tool-policy contract that enforces tool name plus action before execution for multiplexed tools such as `message` and `gateway`, while composing cleanly with `toolsBySender`, message action allowlists, and approval hooks.

## Reproduction Assessment

Yes. Current source shows generic tool policy filtering by whole tool name before action arguments are read, so entries such as `message:send` or `gateway:config.patch` cannot express the requested policy today.

## Solution Assessment

Unclear until maintainers choose the security model. The maintainable direction is a generic action-aware policy grammar and enforcement boundary, not a one-off message or gateway shim; the current message action allowlist is useful but incomplete for this request.

## Summary

Keep open. Current main provides message-specific action allowlisting, but the generic tool policy still filters by tool name and cannot separately govern multiplexed `gateway` actions or define a safe privileged-workflow delegation contract.

## What This Changes

Add action-level allow/deny controls for multiplexed tools while preserving explicitly approved outbound workflow paths.

## Best Possible Solution

Define one typed action-aware core policy contract with wildcard and precedence rules, enforce it immediately before multiplexed action execution, preserve the message-specific controls through the canonical path, and require explicit capability-scoped delegation for approved workflows rather than an implicit Lobster bypass.

- **Per-tool policies only:** Keep action controls owner-specific, extend `tools.message.actions.allow` and similar settings independently, and do not add generic `tool:action` grammar.
- **Approval gate instead:** Address outbound actions through the separate confirmation-gate design without adding static action-level allow/deny policy.

## Solution Assessment

The goal is sound, but the proposed implicit workflow bypass is not the safest solution; the best design is a generic action policy plus explicit capability-scoped delegation.

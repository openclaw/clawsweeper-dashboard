## Summary

Keep open. Current main still lacks the requested generic action-level tool deny contract: tool policy config and matching remain whole-tool based, while the newer message-specific action allowlist does not cover `tools.deny` grammar, gateway actions, or trusted approval-bypass semantics. The issue is the canonical tracker for closed gateway/message authorization reports and needs maintainer product/security design before implementation.

## What This Changes

The issue requests config-enforced action-level allow/deny for multiplexed tools so operators can block write/send actions while preserving read/search actions.

## Best Possible Solution

Keep this as the canonical core security-policy tracker until maintainers approve a typed action-aware tool-policy contract covering message and gateway read/write splits, grammar, wildcard behavior, precedence, docs, compatibility or doctor behavior if needed, and tests for default compatibility plus new enforcement.

## Reproduction Assessment

Yes. Current source shows generic tool policy filtering by whole tool name before action arguments are read, so entries such as `message:send` or `gateway:config.patch` cannot express the requested policy today.

## Solution Assessment

Unclear until maintainers choose the security model. The maintainable path appears to be a generic action-aware policy grammar and enforcement boundary, not a one-off message or gateway shim; the existing message action allowlist is useful but incomplete for this request.

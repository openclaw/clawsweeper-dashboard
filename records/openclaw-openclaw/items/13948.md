## Summary

Keep open. Current main still has only whole-tool `allow`/`deny` policy for the generic tool pipeline; the message-specific action allowlist is a partial workaround and does not cover generic `tools.deny`, gateway action splits, or trusted approval-bypass semantics.

## What This Changes

Request action-level tool policy so operators can deny side-effecting actions such as `message:send` while keeping read-only actions available.

## Best Possible Solution

Keep this as the canonical core tracker for a maintainer-approved, typed, documented action-aware tool-policy contract that defines syntax, precedence, wildcard behavior, sender/profile interactions, gateway/message coverage, and trusted approval-path semantics.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence reproduction of the gap: generic tool policy is parsed and applied by whole tool name before `message` or `gateway` action arguments are evaluated, so `message:send` and `gateway:config.patch` are not representable in `tools.deny` today.

## Solution Assessment

Unclear until maintainers choose the contract. A generic action-aware authorization design is the maintainable direction, but the syntax, precedence, wildcard behavior, and trusted bypass semantics need product/security review first.

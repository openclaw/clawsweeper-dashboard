## Summary

Keep open. Current main still lacks generic action-aware tool allow/deny; the existing message action allowlist is a partial message-only control and does not cover generic `tools.deny` grammar, gateway actions, or approved privileged-send semantics.

## What This Changes

Request action-level tool policy so operators can block side-effecting actions like `message:send` or `gateway:config.patch` while keeping read-only actions on the same tool available.

## Best Possible Solution

Keep this as the canonical core tracker and define a maintainer-approved, typed action-aware tool-policy contract with documented grammar, wildcard behavior, precedence, trusted bypass semantics, and pre-execution enforcement across multiplexed tools.

## Reproduction Assessment

Yes, as a source-level gap: current main filters generic tool policy by whole tool name before action arguments are read, so entries such as `message:send` or `gateway:config.patch` cannot express the requested policy today. I did not run tests because this was a read-only review.

## Solution Assessment

Unclear until maintainers choose the security model. The maintainable path is a generic action-aware policy grammar and enforcement boundary, not a one-off message or gateway shim; the existing message action allowlist is useful but incomplete for this request.

## Summary

Keep open. Current main still lacks generic action-aware tool allow/deny: whole-tool policy is documented and implemented by tool name, while the newer message action allowlist only partially covers `message` and does not cover `gateway` actions or trusted approval-bypass semantics.

## What This Changes

The issue requests action-level tool policy so operators can block side-effecting actions such as `message:send` or `gateway:config.patch` while preserving read-only actions.

## Best Possible Solution

Keep this as the canonical core tracker for a maintainer-approved, typed action-aware tool-policy contract with documented grammar, wildcard behavior, precedence, and pre-execution enforcement for multiplexed tools such as `message` and `gateway`.

## Reproduction Assessment

Yes. Current source shows generic tool policy filtering by whole tool name before action arguments are read, so entries such as `message:send` or `gateway:config.patch` cannot express the requested policy today.

## Solution Assessment

Unclear until maintainers choose the security model. The maintainable path is a generic action-aware policy grammar and enforcement boundary, not a one-off message or gateway shim; the existing message action allowlist is useful but incomplete for this request.

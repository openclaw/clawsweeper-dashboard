## Summary

Keep open. Current main has a useful message-specific action allowlist, but the requested generic action-level tool policy still does not exist for `tools.allow`/`tools.deny`, `gateway` actions, sender-scoped action policy, or approved-workflow bypass semantics.

## What This Changes

Request a config-enforced action-level allow/deny policy so multiplexed tools can block actions such as message sends while preserving read-style actions.

## Best Possible Solution

Keep this as the canonical core tracker and design a typed, documented action-aware policy contract enforced before multiplexed actions execute, with explicit precedence and trusted-context semantics for message and gateway.

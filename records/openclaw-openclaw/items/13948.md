## Summary

Keep open. Current main still lacks a generic action-aware tool allow/deny contract: base tool policy is typed and enforced by whole tool name, while the newer message action allowlist is message-specific and does not cover `gateway` actions or trusted approval-bypass semantics.

## What This Changes

The issue requests config-level action-deny support such as denying `message:send` while keeping read/search actions available for approved workflows.

## Best Possible Solution

Keep this as the canonical core tracker for a typed action-aware tool-policy contract with documented grammar, wildcard behavior, precedence, trusted-context semantics, and pre-execution enforcement for multiplexed tools such as `message` and `gateway`.

## Reproduction Assessment

Yes. Current source shows generic tool policy filtering by whole tool name before action arguments are read, so entries such as `message:send` or `gateway:config.patch` cannot express the requested policy today.

## Solution Assessment

Unclear until maintainers choose the security model. The maintainable path is a generic action-aware policy contract and enforcement boundary, not a one-off message or gateway shim.

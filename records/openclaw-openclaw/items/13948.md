## Summary

Keep open. Current main still does not provide the requested generic action-level tool allow/deny contract: normal tool policy remains typed and enforced by tool name, and the newer message action allowlist is message-specific rather than a `message:send` / `gateway:config.patch` policy grammar with documented precedence and trusted approval semantics.

## What This Changes

The issue requests action-level tool deny/allow policy so operators can block outbound or high-risk actions such as `message:send` while keeping read-only actions available.

## Best Possible Solution

Keep this as the canonical core tracker for a maintainer-approved, typed action-aware tool-policy contract with documented grammar, wildcard behavior, precedence, trusted-context semantics, and pre-execution enforcement for multiplexed tools such as `message` and `gateway`.

## Reproduction Assessment

Yes. Current source shows generic tool policy filtering by whole tool name before action arguments are read, so `message:send` or `gateway:config.patch` cannot express the requested generic policy today.

## Solution Assessment

Unclear until maintainers choose the security contract. The maintainable path is a generic action-aware policy and enforcement boundary, not a one-off message or gateway shim; the existing message action allowlist is useful but incomplete for this request.

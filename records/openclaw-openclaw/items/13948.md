## Summary

Keep open. Current main still does not provide the requested generic action-level tool deny/allow contract: whole-tool policy is enforced by tool name before action arguments are available, and the newer message action allowlist is message-specific rather than a shared policy grammar.

## What This Changes

The issue requests config-enforced action-level tool policy so operators can deny high-risk actions such as message sends or gateway writes while preserving read-only actions on the same multiplexed tool.

## Best Possible Solution

Define a maintainer-approved, typed, documented action-aware tool-policy contract that covers shared grammar, precedence, wildcard behavior, gateway/message read-write splits, and trusted approval-bypass semantics before implementing enforcement.

## Reproduction Assessment

Yes, from source inspection: shared tool policy filters tool inventory by whole tool name before message or gateway action arguments are read. I did not run a live agent because the source path directly proves the feature gap rather than a flaky runtime symptom.

## Solution Assessment

Unclear until maintainers choose the security contract. The maintainable solution is a generic action-aware policy and enforcement boundary, not a one-off message or gateway shim; the existing message action allowlist is useful but incomplete for this request.

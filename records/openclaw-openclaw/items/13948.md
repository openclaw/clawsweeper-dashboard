## Summary

Keep open. Current main still lacks a generic action-aware tool allow/deny contract: whole-tool policy is still typed, documented, and enforced by tool name, while the newer message action allowlist is message-specific and does not cover `gateway` actions or trusted approval-bypass semantics. Related gateway-specific reports are already closed back to this issue as the canonical tracker, and https://github.com/openclaw/openclaw/issues/23451 is adjacent confirmation-gate work rather than a replacement.

## What This Changes

Request adds action-level tool policy so operators can block side-effecting actions such as message send or gateway config.patch while preserving read and diagnostic actions.

## Best Possible Solution

Keep this as the canonical core tracker for a maintainer-approved, typed action-aware tool-policy contract with documented grammar, wildcard behavior, precedence, trusted-context semantics, and pre-execution enforcement for multiplexed tools such as `message` and `gateway`.

## Reproduction Assessment

Yes. Current source shows generic tool policy filtering by whole tool name before action arguments are read, so entries such as `message:send` or `gateway:config.patch` cannot express the requested policy today.

## Solution Assessment

Unclear until maintainers choose the security model. The maintainable path is a generic action-aware policy contract and enforcement boundary, not a one-off message or gateway shim; the existing message action allowlist is useful but incomplete for this request.

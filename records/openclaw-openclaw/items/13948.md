## Summary

Keep open. Current main and v2026.6.11 still lack the requested generic action-aware `tools.allow`/`tools.deny` contract; the existing `tools.message.actions.allow` path is message-specific and does not cover gateway actions or trusted approved-send semantics.

## What This Changes

The issue requests config-level action-aware tool policy so operators can block side-effecting actions such as message sends while preserving read actions and approved workflows.

## Best Possible Solution

Keep this as the canonical core tracker for a maintainer-approved action-aware tool-policy contract, enforced before multiplexed actions execute and covered for `message`, `gateway`, and trusted invocation paths.

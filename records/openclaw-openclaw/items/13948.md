## Summary

Keep open. Current main has a message-specific `tools.message.actions.allow` workaround, but it still lacks the requested generic action-aware `tools.allow`/`tools.deny` contract for multiplexed tools such as `message` and `gateway`.

## What This Changes

Requests action-level tool policy so operators can deny side-effecting actions like `message:send` while preserving read/search-style actions on the same tool.

## Best Possible Solution

Keep this as the canonical core tracker and define a typed, documented action-aware tool-policy contract with pre-execution enforcement for multiplexed tools and a clear trusted approval path.

## Reproduction Assessment

Yes. Source inspection shows current main filters generic tool policy by whole tool name before action arguments are read, so entries such as `message:send` or `gateway:config.patch` cannot express the requested policy.

## Solution Assessment

Unclear until maintainers choose the security model. The message action allowlist is a useful partial mitigation, but the maintainable solution is a generic action-aware policy contract with explicit precedence and trusted bypass semantics.

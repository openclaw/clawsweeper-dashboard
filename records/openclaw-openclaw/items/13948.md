## Summary

Keep open: current main still has only whole-tool allow/deny plus a message-specific action allowlist, so the requested generic action-level deny contract for multiplexed tools such as message and gateway remains unresolved.

## What This Changes

The issue requests action-level allow/deny policy so multiplexed tools such as `message` and `gateway` can block risky actions while preserving safe read actions.

## Best Possible Solution

Keep this as the canonical core tracker and design a typed, documented action-aware policy contract covering message and gateway actions, precedence, wildcards, trusted approval-path semantics, migrations or doctor behavior, and focused tests.

## Reproduction Assessment

Yes by source inspection: current policy filters tools by name before multiplexed action dispatch, while message and gateway actions are still encoded inside tool arguments.

## Solution Assessment

The generic action-aware contract is the right direction, but the exact config syntax, precedence, wildcard semantics, and trusted bypass behavior need maintainer product and security decisions before implementation.

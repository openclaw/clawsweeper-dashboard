## Summary

Keep open: current main has a message-only action allowlist, but generic tool policy is still whole-tool/name-based and cannot express `message:send` or `gateway:config.patch` deny rules across multiplexed tools.

## What This Changes

Request action-level tool allow/deny policy so operators can block side-effecting message or gateway actions while preserving read-only actions and approved workflows.

## Best Possible Solution

Define a maintainer-approved generic action-aware tool-policy contract with typed grammar, wildcard and precedence rules, trusted bypass semantics, docs, and regression coverage for message and gateway actions.

## Reproduction Assessment

Yes, as a source-level gap: current main filters generic tool policy by whole tool name before action arguments are read, so entries such as `message:send` or `gateway:config.patch` cannot express the requested policy. I did not run tests because this was a read-only review.

## Solution Assessment

Unclear until maintainers choose the security model. A generic action-aware policy contract is the maintainable direction; the existing message action allowlist is useful but incomplete for this request.

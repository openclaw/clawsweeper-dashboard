## Summary

Keep open. Current main still lacks a generic action-aware tool policy: the base config/schema and matcher operate on whole tool names, while the existing message action allowlist is message-specific and does not cover gateway actions or trusted approval-bypass semantics.

## What This Changes

Request action-level tool allow/deny so operators can block side-effecting actions such as `message:send` or `gateway:config.patch` while preserving safe read/search actions.

## Best Possible Solution

Keep this as the canonical core tracker for a typed action-aware tool-policy contract with documented grammar, precedence, trusted-context semantics, and pre-execution enforcement for multiplexed tools such as message and gateway.

Options:

- **Design generic action policy (recommended):** Add a typed, documented action-aware policy grammar enforced before multiplexed tool actions execute, with explicit precedence and trusted-context tests for message and gateway.
- **Narrow to message and gateway:** Add separate message and gateway action controls only, reducing immediate scope but risking parallel policy surfaces and future drift.
- **Defer to confirmation work:** Leave static action deny out of core for now and rely on the related confirmation-gate design, accepting that deny-style least privilege remains unavailable.

## Reproduction Assessment

Yes. Current source shows generic tool policy filtering by whole tool name before action arguments are read, so entries such as `message:send` or `gateway:config.patch` cannot express the requested policy today.

## Solution Assessment

Unclear until maintainers choose the security model. The maintainable direction is a generic action-aware policy contract and enforcement boundary, not a one-off message or gateway shim.

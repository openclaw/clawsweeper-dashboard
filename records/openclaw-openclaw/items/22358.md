## Label Justifications

- `impact:message-loss`: A stated use case is detecting failed subagent completion announcement delivery and triggering fallback notification.

## Summary

Keep open: current main and the latest release still expose only adjacent subagent observation/routing hooks, not the requested post-completion/pre-announcement hook that can inspect, enrich, suppress, or observe delivery outcomes. The remaining work is a public lifecycle/plugin API design item with security and message-delivery implications.

## What This Changes

Request a public extension hook after spawned subagent completion and before the parent announcement so plugins can inspect output, persist artifacts, enrich or filter the announcement, and react to delivery failure.

## Best Possible Solution

Define a maintainer-approved public lifecycle/delivery hook contract with bounded child/run metadata, safe completion-output access, delivery status/error visibility where appropriate, explicit return semantics, docs, and focused ordering/security tests.

## Maintainer Decision

Question: Should OpenClaw expose a post-subagent-completion/pre-announcement hook as a typed plugin lifecycle hook, a broader generic delivery boundary, or keep completion processing observation-only?

Rationale: The choice controls public plugin API names, payload sensitivity, hook ordering, delivery-failure semantics, and whether plugins may modify or suppress user-visible completion output.

Likely owner: steipete

Owner reason: The recent subagent lifecycle refactors and the maintainer review closing the overlapping guard-hook PR make this the clearest available design-routing signal.

Owner confidence: medium

Options:

- **Design a generic completion/delivery boundary (recommended):** Define one typed contract that covers subagent completion inspection, safe output filtering, delivery failure visibility, and announcement mutation without adding narrow one-off hooks.
- **Add a narrow subagent completion hook:** Expose only the requested subagent-specific post-completion/pre-announcement hook with strict payload and return limits, leaving broader delivery guards for later.
- **Keep hooks observation-only:** Do not let plugins modify completion announcements; instead improve observability and channel delivery failure reporting through existing lifecycle events.

## Reproduction Assessment

Yes for the source-level API gap: current main can be checked by inspecting the plugin hook catalog, subagent_ended payload/runner, and announce delivery flow. No runtime failure repro is needed because this is a missing extension point rather than a broken existing hook contract.

## Solution Assessment

Unclear as proposed: the requested seam is valid, but a one-off post_subagent_complete hook is not obviously the best permanent API until maintainers decide the broader lifecycle/delivery boundary and security model.

## Label Justifications

- `P2`: This is a normal-priority plugin API and delivery reliability feature with clear source evidence, but it is not an urgent regression or runtime outage.
- `impact:message-loss`: The issue asks for deterministic handling around subagent completion announcement delivery, fallback notification, and suppression/filtering of noisy completions.
- `impact:session-state`: The requested hook would inspect child session completion state and support trajectory, memory, or index updates after subagent work completes.
- `impact:security`: The proposed hook may expose child run output or history to plugins and allow announcement mutation at a sensitive lifecycle boundary.

## Summary

Keep open: current main and the latest release expose adjacent subagent observation and routing hooks, but not the requested post-completion/pre-announcement plugin interception point. This remains a plugin API, delivery, and security design item rather than conservative cleanup.

## What This Changes

Request to add a public hook after a subagent completes and before the parent completion announcement is sent, with access to completion data and possible announcement enrichment or suppression.

## Best Possible Solution

Define a maintainer-approved typed lifecycle/delivery hook at the post-completion, pre-announcement boundary with bounded payloads, safe child-output access, delivery-status visibility where appropriate, and explicit return semantics for enrichment, suppression, filtering, errors, and timeouts.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 expose only adjacent subagent hooks, and the announce flow builds and delivers the completion event without a public plugin interception point.

## Solution Assessment

Unclear pending maintainer API and security design. A post-completion hook is plausible, but the best solution must settle payload bounds, delivery-result visibility, ordering, failure handling, and whether this belongs in a broader lifecycle/delivery contract.

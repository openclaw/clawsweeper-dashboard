## Summary

Keep open: current main and v2026.6.11 still have adjacent subagent lifecycle and delivery-target hooks, but not a post-subagent-completion/pre-announcement hook with result/history access, delivery-result visibility, or announcement mutation semantics. The remaining work is a product and security-boundary decision, especially after the related guard-hook PR was closed as the wrong permanent API shape.

## What This Changes

Add a programmatic hook after a spawned subagent completes and before its completion announcement is sent so plugins can inspect the finished run, persist artifacts, and enrich, suppress, or filter the announcement.

## Best Possible Solution

Define a maintainer-approved lifecycle/delivery boundary that covers post-subagent completion with a safe payload, explicit delivery-result visibility, and documented mutation or suppression semantics, preferably as a generic plugin API rather than a one-off subagent rewrite path.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose post-subagent completion handling as a dedicated subagent hook, as part of a generic delivery/output boundary, or keep it observation-only with separate delivery-policy issues?

Rationale: The source gap is clear, but the permanent API affects plugin authority, sensitive child-session data, message delivery semantics, and compatibility with the recently rejected subagent-only guard-hook shape.

Likely owner: steipete

Owner reason: The latest explicit API-direction signal is the closure of the related guard-hook PR, which framed completion/output filtering as a generic product boundary rather than another subagent-only hook.

Owner confidence: medium

Options:

- **Generic delivery boundary (recommended):** Design one plugin-facing completion/output boundary that can cover subagent completion review, filtering, and fallback notification with shared security and delivery semantics.
- **Dedicated subagent hook:** Add a narrow post-subagent-completion hook with bounded payload and return semantics, accepting that it becomes a separate public contract from broader delivery/output policy.
- **Observation only:** Keep subagent lifecycle hooks observational and route suppression, fallback notification, and verification through narrower delivery-policy or plugin-runtime issues.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 list only adjacent subagent hooks, and the announce flow builds and delivers the completion without a public post-completion/pre-announcement interception point.

## Solution Assessment

Unclear as proposed. A hook is plausible, but the best solution needs maintainer approval on whether this belongs in a dedicated subagent hook or a generic completion/output delivery boundary with explicit security and message-delivery semantics.

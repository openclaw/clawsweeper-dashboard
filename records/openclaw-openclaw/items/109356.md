## Label Justifications

- `P2`: The missing provenance creates recurring approval friction and weaker operator decisions in multi-agent setups, but does not block execution or make the core runtime unusable.
- `impact:security`: The request concerns the information an operator uses at the exec-approval boundary before authorizing host command execution.
- `impact:ux-friction`: Operators must infer the requesting agent and purpose from cwd or other indirect details when several agents share an approval channel.

## Summary

Keep open: current main carries agent/session identity through approval requests and one generic forwarding formatter already shows the agent, but shared/native approval rendering does not consistently expose it and no canonical bounded task label exists; the remaining task-context design needs a maintainer choice because it affects approval trust and privacy.

## What This Changes

Request approval notifications consistently show the originating agent and a concise session or scheduled-task context.

## Best Possible Solution

Add one canonical approval-context projection that always renders authoritative agent identity and optionally renders a short, sanitized label derived from existing trusted cron/session metadata, with length limits and omission fallback; reuse it across native and generic exec/plugin approval renderers without adding a new config surface or model-generated summary.

## Solution Assessment

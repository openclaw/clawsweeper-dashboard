## Label Justifications

- `P1`: Untracked long-lived PTY process trees can accumulate helpers and degrade real gateway or agent availability after restart/session loss.
- `impact:session-state`: The central failure is drift between OpenClaw's tracked exec/session state and live OS process ownership.
- `impact:crash-loop`: The reported orphan helper trees can drive memory growth and process-level availability pressure.

## Summary

Keep open: current main and the latest release still keep background exec sessions and supervisor ownership in process memory only, while the linked closing PR remains open/conflicting and explicitly covers only the in-process half of the restart-loss problem.

## What This Changes

The issue asks OpenClaw to prevent PTY-backed background exec runs from surviving restart or session-state loss as untracked orphan process trees.

## Best Possible Solution

Define one core-owned supervisor lifecycle policy for previous-epoch PTY exec ownership, then land or replace the linked PR with durable startup reconciliation, focused regression coverage, and operator-visible logging.

## Maintainer Decision

Kind: product_direction

Question: Should OpenClaw kill, reattach/re-register, or intentionally ignore PTY-backed background exec runs that survive a gateway restart without tracked session ownership?

Rationale: The source-level bug is clear, but the durable fix changes long-running task semantics and operator expectations, so automation should not choose the permanent policy alone.

Owner confidence: high

Options:

- **Kill stale previous-epoch PTY runs (recommended):** On startup, terminate persisted PTY exec runs from a prior gateway epoch that cannot be safely re-owned, with logging and tests for normal finalize cleanup.
- **Reattach previous runs:** Persist enough metadata to validate and re-register surviving process trees after restart, accepting more complexity to preserve legitimate long-running work.
- **Land in-process cleanup only:** Treat the open PR's session-drift reconciliation as a partial mitigation and leave cold-start orphan reaping for a later policy decision.

## Reproduction Assessment

Yes, at source level: current main keeps supervisor/process-session state in memory, process list reads those maps, and the docs say sessions are lost on restart. I did not run a live restart/orphan-process proof in this read-only review.

## Solution Assessment

Unclear as a final fix: durable ownership and startup reconciliation belong in core, but maintainers still need to choose kill versus reattach semantics. The open linked PR is a useful partial mitigation, not the complete restart-loss solution.

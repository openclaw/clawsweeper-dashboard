## Summary

The reported setup intentionally starts two independent reply-producing agent turns for one inbound WhatsApp message: the route binding runs `main`, while the external `openclaw agent --agent <other-id> ... --deliver` call overrides bindings and explicitly sends its own reply. The two provider message IDs therefore do not establish one delivery handler firing twice.

## What This Changes

The issue requests a fix for two WhatsApp messages sent after an inbound message when a bound agent and an externally dispatched non-bound agent both deliver replies.

## Best Possible Solution

Use exactly one delivery owner per inbound WhatsApp event: retain the route-bound reply and remove `--deliver` from the external turn, or disable the binding and let the external dispatcher own the reply; include run IDs and `deliveryStatus` only if a single logical turn still yields two provider IDs.

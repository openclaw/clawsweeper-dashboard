## Summary

Keep open: this PR is a plausible implementation candidate for user-scoped memory, but the current head still has blocking defects in the default-on isolation path and public config contract, is conflicting against main, and only shows unit/typecheck-style proof rather than real two-user Gateway behavior.

## What This Changes

The PR adds a `memory.isolation` config block, isolation identity resolution, encoded per-user memory paths, and userId propagation through memory-core builtin and QMD memory paths.

## Best Possible Solution

Rebase, make the isolation default and accepted config fields match the actual runtime contract, add upgrade plus two-user builtin/QMD proof, then let maintainers decide whether this is the right implementation for the canonical memory isolation tracker.

## Reproduction Assessment

Yes, at source level for the PR defects: a config with no memory.isolation block still resolves memory search isolation as enabled, while resolveIsolationIdentity returns undefined and leaves memory tools unscoped. No live two-user Gateway run was established in this read-only review.

## Solution Assessment

No, not yet: the broad approach is plausible, but the current branch exposes config/default semantics that do not match runtime behavior and still lacks upgrade and real two-user proof. A safer path is one canonical isolation contract wired through identity, builtin paths, QMD paths, docs, and tests before merge.

## What This Changes

The PR changes iOS gateway status and onboarding precedence so retained connection errors remain visible during reconnects, clears errors when selecting a different gateway, and adds focused Swift regression tests.

## Best Possible Solution

Use one target-aware onboarding connection state that retains an error only for a same-target reconnect, clears it on every explicit target switch or reset, lets new setup-code progress replace stale local failures, and exposes an in-flight flag that disables problem actions until the attempt finishes; then demonstrate those transitions in a redacted simulator or device recording.

- **[P2] Preserve the error through same-target reconnect setup:** `apps/ios/Sources/Onboarding/OnboardingWizardTypes.swift:54`

  - confidence: 0.97
- **[P2] Clear retained errors after a route reset:** `apps/ios/Sources/Model/NodeAppModel.swift:10685-10688`
  - body: The helper returns when both `activeGatewayConnectConfig` and `connectedGatewayID` are nil. Setup-link and deep-link target resets intentionally clear those identifiers before starting the replacement connection, so the previous gateway's problem survives and outranks the new progress; clear on this explicit reset state or carry the previous target identity through the switch.
  - confidence: 0.96
- **[P2] Let setup-code progress replace stale local failures:** `apps/ios/Sources/Onboarding/OnboardingWizardTypes.swift:53`
  - body: `localFailure` now wins over `connectingDetail`, but starting setup-code resolution does not clear the prior local failure until the later manual-connect stage. Scanning or applying a valid setup code can therefore keep showing an old failure instead of the active setup progress; clear that failure when the setup attempt starts or prioritize setup-code progress.
  - confidence: 0.95
- **[P2] Disable retained-error actions during reconnect:** `apps/ios/Sources/Onboarding/OnboardingWizardTypes.swift:54`
  - body: When both `problem` and `connectingDetail` are present, this resolver stays in `.failed`, so the banner continues rendering its enabled Retry or Trust action while an attempt is in flight. Those handlers lack a matching in-flight guard, allowing repeated taps to overlap, cancel, or restart the current handoff; carry busy state into the failed presentation and disable its action.
  - confidence: 0.96

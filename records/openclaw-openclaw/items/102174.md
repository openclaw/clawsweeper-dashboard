## Label Justifications

- `P1`: The report describes a broken real cron/channel workflow where long-running executor work can be killed while the operator receives a successful placeholder announcement.
- `impact:data-loss`: The reported Bash subprocess was killed after partial mutations and before writing its expected output and summary files.
- `impact:message-loss`: The announced Telegram digest can be replaced by a placeholder, with no later completion message for the actual work.
- `impact:session-state`: The cron run record and session state can say ok/delivered while CLI-owned tool work was still in flight and then killed.
- `maturity:stable`: The affected Gateway runtime lifecycle/delivery surface maps to `gateway-runtime`, which is M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main still has the cron/Claude CLI lifecycle shape where an isolated cron CLI run can treat returned CLI text as the run result and then close the Claude live session, while the related open issues cover overlapping process-tree cleanup rather than this issue's cron ok/delivered and partial-state invariant.

## What This Changes

The issue reports that cron `agentTurn` can return a placeholder before a foreground Claude Bash subprocess completes, mark the run ok and delivered, then kill the subprocess and leave partial state.

## Best Possible Solution

Define an owner-approved cron/Claude CLI lifecycle contract where foreground native tool work cannot produce a green cron result until its tool result is terminal, or the run records a typed pending/failed-tool state instead of delivering a placeholder.

Question: Should isolated cron `agentTurn` on `claude-cli` block terminal success on foreground native tool completion, fail/telemetry-mark runs with pending native work, or route this pattern to command cron instead?

Rationale: The fix crosses cron success semantics, Claude CLI process cleanup safety, and operator-facing delivery truth, and a cleanup opt-out or new telemetry surface would be a product/runtime contract change.

Likely owner: steipete

Owner confidence: medium

Options:

- **Block or fail pending native tool work (recommended):** Make cron `agentTurn` treat pending foreground native tool work as non-terminal, either waiting within the job timeout or recording a typed error/pending state before cleanup.
- **Telemetry first:** Keep cleanup behavior but add explicit run-record diagnostics for killed or pending CLI-owned native tool work so monitors no longer see a green run.
- **Route scripts to command cron:** Document and enforce that long deterministic shell scripts should use command cron, leaving model-backed `agentTurn` for digesting already-materialized state.

Unclear: the issue identifies the right failure class, but the best permanent fix needs maintainer direction. A bounded terminal-tool contract plus typed run-record diagnostics is safer than a broad cleanup opt-out, while existing command cron is only a workaround for deterministic script output.

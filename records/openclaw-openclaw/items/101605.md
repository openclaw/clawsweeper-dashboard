## Summary

Keep open: the reported commitments truncation bug is valid, but this patch is not ready because it reimplements UTF-16-safe truncation with code-point semantics that can overflow the fixed-width table columns, and it lacks proof from the real command path.

## What This Changes

The PR changes the `openclaw commitments` table truncation helper to build truncated prefixes with `Array.from(...).slice(...).join(...)` so emoji are not split.

## Best Possible Solution

Use `truncateUtf16Safe(value, maxChars - 1)` or an equivalent shared command helper, add a commitments-table regression with emoji at the truncation boundary, and provide redacted real `openclaw commitments list` output proof.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes from source inspection: current main truncates commitments table fields with raw UTF-16 slicing before appending an ellipsis, so a surrogate pair crossing the boundary can leave a dangling high surrogate.

## Solution Assessment

No. The patch is a plausible mitigation, but the best fix is the existing `truncateUtf16Safe` helper because it preserves the current code-unit cap while avoiding split surrogate pairs.

- **[P1] Use the UTF-16 truncation helper instead:** `src/commands/commitments.ts:29-31`
  - body: This helper feeds fixed-width cells via `padEnd(16)` and `padEnd(28)`, so its return value needs to stay within the existing `maxChars` UTF-16 cap. `Array.from(...).slice(...)` caps code points instead; a value made of emoji can return 27 emoji plus an ellipsis for a 28-char Scope cell, which is far wider than the column and shifts the rest of the row.

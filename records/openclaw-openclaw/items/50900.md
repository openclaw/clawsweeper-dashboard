## Summary

Keep open: current main and v2026.6.11 still expose global session-maintenance retention plus narrow fixed cleanup paths, not ordered per-pattern or per-type retention rules. The request is useful, but it adds destructive public config semantics and needs maintainer product/API approval before implementation.

## What This Changes

Requests ordered per-pattern or per-type `session.maintenance` retention rules so ephemeral cron/subagent sessions can be pruned sooner than interactive sessions.

## Best Possible Solution

Keep this as the canonical product/API decision, then implement one additive typed retention-rule contract with schema, docs, cleanup-preview output, and regression coverage once matcher and safety semantics are approved.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 expose only global `session.maintenance` fields plus narrow fixed cleanup paths, not ordered per-pattern retention rules. This is a feature-gap reproduction rather than a failing runtime bug repro.

## Solution Assessment

Unclear until maintainer design approval. Ordered retention rules are plausible, but the best fix should use a stable typed matcher and explicit destructive-cleanup safety semantics rather than defaulting to raw key globs.

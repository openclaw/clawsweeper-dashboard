## Summary

Keep open: current main still lacks ordered per-pattern or per-type session retention rules. The related open issues cover narrower preserve-key, per-label keep-N, archive semantics, and broader store-pressure concerns, so this remains a valid product/API decision rather than a closeable duplicate or implemented item.

## What This Changes

The issue requests ordered per-pattern or per-type session maintenance retention rules so ephemeral cron/subagent sessions can expire sooner than interactive sessions.

## Best Possible Solution

Keep this as the canonical broader retention-rules product/API decision, then implement one additive typed retention-rule contract after matcher and destructive-cleanup safety semantics are approved.

## Reproduction Assessment

Yes. Source inspection shows current main exposes only global session.maintenance pruning plus a fixed model-run special case, so the requested per-pattern matcher cannot be configured today.

## Solution Assessment

Unclear until maintainer design approval. Ordered retention rules are plausible, but the best solution should use a stable typed matcher and explicit destructive-cleanup safety semantics rather than defaulting to raw key globs.

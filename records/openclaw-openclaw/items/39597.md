## Summary

Keep open. Current main and v2026.6.11 already distinguish browser/WebChat and native Mac clients at the Gateway WebSocket connect layer, but that identity still is not exposed as an agent-facing WebChat client type in chat.send context or the runtime prompt line.

## What This Changes

The issue requests an agent-visible way to distinguish WebChat client types such as native Mac app, browser, and mobile web.

## Best Possible Solution

Define one additive Gateway-owned client metadata contract with explicit trusted/untrusted semantics, then propagate it through browser and native WebChat chat.send paths into agent runtime metadata with focused protocol, prompt, and security tests.

- **Expose Untrusted Diagnostic Hint:** Surface only a clearly labeled untrusted hint for debugging and forbid agents from treating it as a capability or permission signal.
- **Decline Runtime Exposure:** Keep client identity limited to Gateway diagnostics until a stronger client-attestation design exists.

Yes, as a source-level gap: current main carries distinct client metadata in the WebSocket connect frame, but chat.send, WebChat MsgContext, and the runtime prompt lack an explicit agent-facing client-type field.

Unclear. The custom header or config flag sketch is plausible, but the maintainable path is to reuse or extend the Gateway client metadata contract with explicit trust semantics instead of adding a WebChat-only side channel.

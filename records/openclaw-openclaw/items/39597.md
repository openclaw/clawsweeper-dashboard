## Summary

Keep open. Current main and the latest release already track WebChat/Gateway connection identity, but agent-facing runtime context still does not distinguish macOS app, browser, or mobile WebChat clients, and exposing that metadata needs a maintainer trust-boundary decision.

## What This Changes

Request to expose WebChat client type, such as macOS app versus browser or mobile web, to agent runtime context.

## Best Possible Solution

Define a typed, maintainer-approved client metadata contract that exposes trusted Gateway connect identity to agents while keeping untrusted browser or app hints diagnostic-only.

- **Expose trusted Gateway identity only (recommended):** Add a typed agent-facing field derived from validated Gateway client info, such as client id/mode/platform, and keep ad hoc hints out of agent authority.

- **Keep diagnostics only:** Leave client identity in Gateway logs and do not expose it to agent runtime until a stronger use case or security model is approved.

## Solution Assessment

No for the suggested ad hoc header/config shape as-is. The safer solution is a typed trusted Gateway identity contract, with any caller-supplied hints kept explicitly untrusted or diagnostic.

## Summary

Keep open. Current main already distinguishes WebChat browser/control-ui and native Mac clients in gateway connect-frame metadata, but that metadata is not yet exposed as an agent-facing WebChat client type in chat context or the runtime prompt line; exposing it needs a maintainer product/security decision about trusted versus untrusted client identity.

## What This Changes

Expose the specific WebChat client type, such as native Mac app versus browser/mobile web, to agents at runtime instead of only `channel=webchat`.

## Best Possible Solution

Define a gateway-owned client metadata contract that exposes only approved, bounded client class fields to agents, preferably derived from validated connect-frame metadata and clearly separating any untrusted diagnostic hints.

Owner confidence: medium

Options:

- **Expose Coarse Validated Class (recommended):** Map known connect-frame ids and modes to a bounded runtime field such as `client=macos-app` or `client=browser-webchat`, and keep raw headers/User-Agent out of agent context.
- **Keep Identity Diagnostic-Only:** Continue using client identity in gateway logs and debugging surfaces while leaving the agent runtime prompt at `channel=webchat`.
- **Expose Untrusted Hints Explicitly:** Allow client-supplied hints for debugging but label and sanitize them as untrusted so agents and plugins do not treat them as authorization or capability facts.

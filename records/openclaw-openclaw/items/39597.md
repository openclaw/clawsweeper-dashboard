## Summary

Keep open. Current main and v2026.6.11 already carry distinct Gateway connect client IDs for browser/Control UI and native macOS clients, but that identity still is not exposed as an agent-facing WebChat client type in `chat.send` context or the runtime prompt; the remaining work needs a security/product decision on trusted versus untrusted client metadata.

## What This Changes

The request is to expose WebChat client type, such as native Mac app versus browser or mobile web, to agents and runtime context.

## Best Possible Solution

Define one additive Gateway-owned client metadata contract with explicit trusted versus untrusted semantics, reuse existing `connect.client` metadata, and propagate only the approved sanitized fields into WebChat agent context and runtime prompt tests.

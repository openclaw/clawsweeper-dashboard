Keep open. Current main already carries distinct Gateway client identity during WebSocket connection setup, but the requested agent-facing WebChat client type is still absent from chat.send context and needs maintainer security/product direction before implementation.

## What This Changes

The issue requests an agent-visible WebChat client subtype so native Mac app, browser, and mobile web clients can be distinguished.

## Best Possible Solution

Define one additive Gateway-owned client metadata contract with explicit trusted/untrusted semantics, then propagate it through WebChat/native chat.send paths into agent runtime metadata with focused protocol, prompt, and security tests.

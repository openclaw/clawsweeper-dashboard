## Summary

Keep open. Current main and v2026.6.11 already distinguish browser/native clients at the Gateway connect-contract layer, but the agent-facing runtime prompt still exposes only the WebChat channel; the remaining work needs a maintainer security/product decision about trusted versus advisory client metadata.

## What This Changes

The issue requests an agent-visible way to distinguish WebChat client types such as native Mac app, browser, and mobile web.

## Best Possible Solution

Define one additive Gateway-owned client metadata contract with explicit trusted/advisory semantics, then propagate only the approved sanitized fields into WebChat agent runtime context with focused protocol, prompt, and security tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should WebChat agent context expose gateway client identity, and if so which fields are trusted versus advisory?

Rationale: The gateway already knows client ids and modes, but making them model-visible may influence native-only behavior, debugging, deep links, or privileged UX, so automation should not choose the trust semantics.

Likely owner: steipete

Owner reason: The choice spans Gateway protocol identity, runtime prompt metadata, and security semantics already tied to steipete's history on these surfaces.

Owner confidence: high

Options:

- **Expose Sanitized Advisory Metadata (recommended):** Propagate a narrow client class such as browser, macos, ios, or android into runtime context and document it as non-authoritative for security or permission decisions.
- **Expose Only Attested Native Identity:** Surface native/app identity only when backed by device-auth or pairing evidence, leaving browser-provided hints out of agent-visible context.
- **Keep Identity Internal:** Leave client identity in Gateway policy/logging only and solve specific UX differences through explicit capability APIs or diagnostics.

## Reproduction Assessment

Yes, as a source-level reproduction: current main carries distinct client metadata in the WebSocket connect frame, while the agent runtime prompt and RuntimeInfoInput lack an explicit client-type field.

## Solution Assessment

No for the exact custom-header/config shape; the maintainable path is to reuse or narrowly extend the existing Gateway connect.client metadata contract after maintainers define trust semantics.

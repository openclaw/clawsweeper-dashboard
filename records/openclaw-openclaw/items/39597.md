## Summary

Keep open. Current main and v2026.6.11 still have Gateway connect-time client identity, but they do not expose a dedicated trusted WebChat client type in the agent-facing chat turn or Runtime line; the remaining blocker is a maintainer product/security decision on trust semantics.

## What This Changes

Request to distinguish WebChat-originated agent turns by client type, such as native macOS app versus browser or mobile web.

## Best Possible Solution

Define one additive Gateway-owned client metadata contract with explicit trusted/untrusted semantics, then propagate it through WebChat/native chat.send paths into runtime metadata with focused protocol, Gateway, prompt, UI, and native-client proof.

Kind: security_boundary

Question: Should agent-visible WebChat client type be exposed as gateway-attested connect metadata, as an explicitly untrusted client hint, or not exposed to agents?

Rationale: Agents could use this field for native-only behavior, deep links, diagnostics, or privileged UX, so automation should not choose the spoofing and trust semantics for client metadata.

Likely owner: steipete

Owner reason: The decision centers on the Gateway client/protocol metadata boundary that steipete recently extracted and maintained.

Owner confidence: high

Options:

- **Gateway-attested metadata (recommended):** Propagate the validated connect.client identity into a narrow runtime metadata field and document exactly what agents may trust.
- **Untrusted diagnostic hint:** Expose only a clearly labeled untrusted hint for debugging and forbid agents from treating it as a capability or permission signal.
- **Decline runtime exposure:** Keep client identity limited to Gateway connection diagnostics until a stronger client-attestation design exists.

## Reproduction Assessment

Yes, as a source-level reproduction. Current main carries client metadata in the WebSocket connect frame, but chat.send, WebChat MsgContext, and the Runtime line still lack an explicit agent-facing client-type field.

## Solution Assessment

Unclear. The suggested custom header or config flag is plausible, but the maintainable solution is to reuse or extend the Gateway client metadata contract with explicit trust semantics instead of adding a WebChat-only side channel.

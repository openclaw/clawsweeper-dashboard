## Label Justifications

- `P2`: The issue affects everyday session navigation for users with many sessions, but it is a bounded UX/product improvement rather than an urgent runtime failure.
- `impact:session-state`: The request concerns persistent per-session metadata used to identify, list, switch, and manage sessions.

## Summary

Keep open: current main has meaningful label plumbing, Control UI label editing, derived-title label fallback, and the merged `/name <title>` command, but it still lacks the requested CLI `openclaw sessions label` flow and friendly CLI text listing. The remaining work is tied to the active `label` versus `title` contract discussion in https://github.com/openclaw/openclaw/pull/95182, so it needs maintainer product review rather than a new automated fix PR.

## What This Changes

Add persistent human-readable session labels or nicknames and surface them in CLI and programmatic session listings so users can identify sessions without raw generated keys.

## Best Possible Solution

Decide the canonical session-name contract, then expose one consistent name field through Gateway, chat commands, Control UI, and `openclaw sessions` text/JSON without competing `label` and `title` semantics.

## Reproduction Assessment

Yes. Source inspection shows the CLI has no `sessions label` subcommand and the text table still renders the key column without a friendly-name column, while Gateway, Control UI, and chat paths only partially cover labels.

## Solution Assessment

No, current main is only partial; a narrow CLI-only patch would risk conflicting with the active title/label contract PR, so the best fix is a unified contract followed by CLI, UI, docs, and protocol alignment.

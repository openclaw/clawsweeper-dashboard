## Label Justifications

- `P2`: This is a source-backed Slack interaction delivery bug with limited blast radius and an unresolved maintainer product decision.
- `impact:message-loss`: A clicked Slack reply control can fail to produce a visible user-facing reply or can consume the interaction outside the reply delivery path.
- `impact:session-state`: The current heartbeat wake path can handle the interaction outside the normal reply turn/session flow, creating state and in-flight-turn ambiguity.

## Summary

Keep open. Current main still routes Slack reply-button/select interactions through a queued `slack:interaction` system event plus an immediate heartbeat wake, while the normal Slack message path uses the inbound reply dispatcher; no open or merged PR now owns the requested delivery-owner change.

## What This Changes

The issue requests routing Slack reply-button/select clicks through the inbound reply pipeline as synthetic user turns instead of waking the session with a heartbeat.

## Best Possible Solution

Decide the delivery owner explicitly, then make Slack reply buttons/selects either use the inbound reply pipeline with delivery/coalescing tests and live Slack proof, or keep heartbeat as owner only with equivalent prompt, reply, and retry guarantees documented and tested.

Options:

- **Use Inbound Reply Turns (recommended):** Route user-initiated Slack reply controls through the same inbound reply pipeline as normal Slack messages, with coalescing/retry behavior and live Slack proof.
- **Keep Heartbeat Owner:** Keep the current heartbeat wake design but add explicit Slack interaction prompt rendering, reply-delivery guarantees, and conflict retry coverage so clicks are not silently lost.
- **Defer To Broader Channel Action Model:** Pause this issue until a generic channel-action callback contract is designed, accepting that Slack reply controls remain fragile in the meantime.

## Solution Assessment

Unclear until maintainers choose the owner boundary. The requested inbound reply path is a strong candidate because it matches normal user-initiated Slack messages, but heartbeat could remain valid only if it gains equivalent prompt, delivery, and retry guarantees.

## Summary

Keep open. Current main and v2026.6.11 still route Slack reply button/select clicks through a queued Slack interaction system event plus an immediate heartbeat wake, while the remaining request is whether user-initiated controls should instead enter the inbound reply path for stronger delivery and coalescing semantics.

## What This Changes

The issue asks OpenClaw to deliver Slack `openclaw:reply_button` and `reply_select` interactions as synthetic inbound reply turns instead of heartbeat wake events.

## Best Possible Solution

Choose one canonical user-click delivery contract for Slack controls, then prove that selected button/select values reach the same Slack thread exactly once and survive active reply-session contention without relying on a generic heartbeat wake as the user-facing delivery mechanism.

Yes for the implementation mismatch: current main and v2026.6.11 still enqueue Slack interactions and request a hook heartbeat, and current tests assert that path. The intermittent visible reply-drop and active-run race still need live Slack proof on current main.

## Solution Assessment

Unclear until maintainers choose the owner boundary. Inbound-turn dispatch is a plausible repair for user-initiated controls, but it changes the current heartbeat-owned path and must be weighed against hardening heartbeat plus the shared conflict work.

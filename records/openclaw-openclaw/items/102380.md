## Summary

Keep open. Current main still routes Slack reply controls as queued `slack:interaction` system events plus an immediate heartbeat wake rather than inbound reply turns; related closed work covers thread wake and value surfacing, and the open conflict report covers one race, but no merged/current item settles the Slack delivery-owner decision.

## What This Changes

The issue asks Slack reply-button/select clicks to dispatch as synthetic inbound reply turns instead of using an immediate heartbeat wake.

## Best Possible Solution

Maintainers should choose one owner for user-initiated Slack controls, then require regression coverage and live Slack proof that clicked values reach the session model and visible replies return to the originating thread while plugin/approval paths stay separate.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 still enqueue Slack reply-control interactions and request an immediate hook heartbeat instead of dispatching an inbound reply turn. I did not run a live Slack click-through reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the owner boundary. Inbound-turn dispatch is a plausible best fix for user-initiated controls, but it changes the current heartbeat-owned interaction design and must be coordinated with plugin/approval early returns and session-conflict handling.

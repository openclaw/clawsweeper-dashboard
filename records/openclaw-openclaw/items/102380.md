## Summary

Keep open. Current main and the latest release still route Slack reply controls by enqueueing a `slack:interaction` system event and requesting an immediate hook heartbeat; https://github.com/openclaw/openclaw/issues/99544 covers the value-surfacing dispute and https://github.com/openclaw/openclaw/issues/102400 covers the broader init-conflict race, but neither resolves this Slack delivery-owner decision.

## What This Changes

The issue asks Slack reply buttons and selects to dispatch as synthetic inbound reply turns instead of heartbeat wakes.

## Best Possible Solution

Choose one delivery owner for user-initiated Slack reply controls, preferably inbound-turn dispatch with tests and live Slack proof for value, thread delivery, and busy-run behavior while preserving plugin and approval early returns.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack reply button/select clicks remain heartbeat-owned system events, or should Slack synthesize normal inbound reply turns for user-initiated controls?

Rationale: Current source proves the path is still heartbeat-owned, but changing it would replace a recently accepted Slack system-event design and must preserve plugin interactive handlers, native approvals, thread routing, and the separate session-conflict recovery work.

Likely owner: steipete

Owner reason: This decision crosses the core system-event drain path and the prior closure that separated value surfacing from the remaining delivery-owner question.

Owner confidence: high

Options:

- **Move Reply Controls To Inbound Turns (recommended):** Treat user-initiated Slack reply controls like normal channel input, with regression and live proof for clicked value, thread delivery, and active-run behavior.
- **Keep Heartbeat And Harden It:** Retain the system-event heartbeat design, but require end-to-end proof that clicked values, visible replies, and retry behavior are reliable.
- **Defer To Shared Conflict Work:** Wait for the general session-init conflict decision, then retest Slack interactions against that chosen recovery layer before changing the delivery owner.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 still enqueue Slack reply-control interactions and request an immediate hook heartbeat. The intermittent visible reply-drop and active-run race still need live Slack proof on current main.

## Solution Assessment

Unclear until maintainers choose the owner boundary. Inbound-turn dispatch is a plausible best fix for user-initiated controls, but it changes the current heartbeat-owned interaction design and must be coordinated with plugin/approval early returns and session-conflict handling.

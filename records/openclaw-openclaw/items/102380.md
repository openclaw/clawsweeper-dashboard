## Summary

Keep open. Current main and v2026.6.11 still route Slack reply controls through a queued `slack:interaction` system event plus an immediate hook heartbeat; the closed predecessor covers value surfacing, and the open conflict issue covers one race, but no merged/current item resolves the heartbeat-vs-inbound-turn delivery-owner decision.

## What This Changes

Request Slack reply-button/select interactions to dispatch as synthetic inbound reply turns instead of waking the session through heartbeat-owned system events.

## Best Possible Solution

Maintainers should choose one delivery owner: preferably inbound-turn dispatch for user-initiated Slack reply controls with regression and live Slack proof, while leaving plugin/approval handlers and idle heartbeat behavior intact.

- **Wait For Shared Conflict Review:** Defer this delivery-owner choice until the related session-init conflict work is reviewed, then retest Slack interactions against the chosen recovery layer.

Yes at source level: current main and v2026.6.11 still enqueue Slack reply-control interactions and request an immediate hook heartbeat, and current tests assert that path. The intermittent visible reply-drop and active-run race still need live Slack proof on current main.

## Solution Assessment

Unclear until maintainers choose the owner boundary. Inbound-turn dispatch is a plausible best fix for user-initiated controls, but it changes the current heartbeat-owned interaction design and must be coordinated with plugin/approval early returns and session-conflict handling.

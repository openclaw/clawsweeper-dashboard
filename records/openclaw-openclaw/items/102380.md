## Summary

Keep open. Current main and the latest release still route Slack reply-button/select interactions through queued `slack:interaction` system events plus an immediate heartbeat wake, while the requested behavior is a maintainer-level choice to make user-initiated controls normal inbound reply turns.

## What This Changes

The issue asks for Slack reply button/select clicks to dispatch through the inbound reply pipeline instead of waking the session through the heartbeat path.

## Best Possible Solution

Maintainers should choose one delivery owner; the likely best end state is inbound-turn dispatch for user-initiated Slack reply controls with regression and live Slack proof, while preserving plugin/approval paths and idle heartbeat behavior.

Options:

- **Keep Heartbeat And Harden It:** Retain the system-event heartbeat design, but require proof that values, visible replies, and retry behavior are reliable end to end.
- **Wait For Shared Conflict Review:** Defer the owner choice until the broader reply-session init conflict work is reviewed, then retest Slack interactions against that recovery layer.

Yes, at source level. Current main still enqueues Slack reply-control interactions and requests an immediate hook heartbeat, and current tests assert that path; live Slack proof is still needed for the intermittent reply-drop symptom.

## Solution Assessment

Unclear until maintainers choose the owner boundary. Inbound-turn dispatch is a plausible best fix for user-initiated controls, but it must preserve plugin interactive handlers, native approvals, thread routing, and session-conflict behavior.

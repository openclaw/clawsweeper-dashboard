## Summary

Keep open. Current main and v2026.6.11 still route Slack reply controls through a queued system event plus an immediate heartbeat wake, while the remaining request is an owner-boundary/product decision about user-initiated interaction delivery rather than a completed fix or stale duplicate.

## What This Changes

The issue asks Slack reply button/select clicks to dispatch as synthetic inbound reply turns instead of queued system events followed by an immediate heartbeat wake.

## Best Possible Solution

Make Slack reply button/select clicks one reliable user-initiated delivery path: either synthesize inbound reply turns with focused Slack proof, or keep heartbeat delivery only if maintainers prove value delivery, visible replies, and busy-run retry behavior end to end.

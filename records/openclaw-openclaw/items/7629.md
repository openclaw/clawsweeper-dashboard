## Summary

Keep open: current main and v2026.6.11 still leave memory-lancedb on vector-only LanceDB retrieval, while the direct implementation PR is closed unmerged and adjacent memory work covers different backends or reranking surfaces.

## What This Changes

The issue requests hybrid BM25 plus vector retrieval for the memory-lancedb plugin so exact keyword matches participate in recall alongside semantic vectors.

## Best Possible Solution

Keep this issue open as the canonical memory-lancedb parity request, and implement it only as a focused plugin change with typed config, FTS index lifecycle, query-text propagation, vector fallback, docs, and targeted tests against @lancedb/lancedb 0.30.0.

## Reproduction Assessment

Yes, at source level: memory_recall, memory_forget, CLI search, auto-recall, and duplicate checks embed text then pass only vectors into MemoryDB.search, which calls LanceDB vectorSearch. This proves the requested BM25/hybrid path is absent without needing a runtime failure repro.

## Solution Assessment

Unclear as a final implementation: adding LanceDB hybrid retrieval in memory-lancedb is the right owner boundary, but maintainers still need to choose defaults, reranker strategy, index maintenance, and vector-only fallback behavior.

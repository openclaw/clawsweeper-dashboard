## Summary

Keep this PR open for normal review. The proposed lazy cache-key construction is a narrow performance optimization and the supplied benchmark is directly relevant, but the branch is still a draft and no evidence identifies a current-main replacement or superseding PR.

## What This Changes

The PR defers building the reusable workspace skill snapshot cache key so hashing the runtime configuration happens only when the resolved-skills cache is read or written.

## System Context

Reusable workspace skill snapshots carry resolved skills between reply-processing stages. Inbound reply admission and session updates request those snapshots; hydration can reuse an existing resolved-skills payload, while rebuild paths consult or update the small in-memory cache.

## Architecture Diagram

flowchart LR
  A[Inbound reply processing] --> B[Workspace skill snapshot resolver]
  B --> C{Existing resolved skills?}
  C -->|Yes| D[Return hydrated snapshot]
  C -->|No or refresh| E[Build snapshot cache key]
  E --> F[Resolved-skills cache]
  F --> G[Build or reuse resolved skills]
  G --> H[Reply session update]

## Best Possible Solution

Preserve the single cache-key format and land the lazy construction only after a current-base review confirms that hydration still invokes rebuild without arguments and that the key is computed on every cache read/write path that needs it.

## Summary

Keep this PR open for contributor follow-up: its latest revision preserves FIFO behavior and includes credible terminal proof, but the claimed safety improvement is redundant because Node’s supported `fs.promises.readFile(path)` implementation already opens the path to a `FileHandle`, reads through that descriptor, and closes it. The extra helper creates a second equivalent file-reader path without solving a current OpenClaw bug.

## What This Changes

The branch replaces capability-CLI media `fs.readFile` calls with explicit `fs.open` plus `FileHandle.readFile`, and adds regular-file, concurrent-read, missing-file, and POSIX FIFO tests.

## Best Possible Solution

Retain the existing `fs.readFile` implementation and its single Node-owned reader contract; only introduce an explicit FileHandle path if a concrete OpenClaw requirement needs operations on that handle beyond a whole-file read.

No. The claimed path-swap gap is not reproducible as a distinct current behavior: Node 24.15.0 implements `fs.promises.readFile(path)` by opening the path to a FileHandle and reading through that descriptor before closing it.

## Solution Assessment

No. The branch is not the best solution because it reimplements the same descriptor lifecycle already used by the supported Node API; keeping `fs.readFile` is narrower and avoids maintenance drift.

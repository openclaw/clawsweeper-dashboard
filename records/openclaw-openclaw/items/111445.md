## Summary

Keep this PR open: its snapshot-hydration path still compares gateway-rewritten client run IDs with approval requests that retain engine run IDs, so a normal Control UI run that reconnects or mounts after the lifecycle event will not show the waiting-for-approval state. Likely related people: steipete (high confidence, merged approval UI and lifecycle work).

## What This Changes

The PR adds a Control UI chat status and accessibility label that show “Waiting for approval…” when an active run is parked on an exec approval.

## Best Possible Solution

Use an explicit gateway/UI correlation contract for the engine and client run identifiers, then prove a live approval, remount or reconnect, resolution, and terminal-run clearing sequence in the Control UI.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, from source: allow a Control UI run to park on approval, miss its live lifecycle event through mount or reconnect, then hydrate from the queued approval. The gateway supplies a client-facing run ID while the approval retains the engine ID, so the new equality check rejects the approval.

## Solution Assessment

No. The UI-only comparison is not the best fix because it joins two different run-ID namespaces; the boundary needs an explicit correlation mapping or a stable identifier exposed by the gateway before snapshot hydration can be reliable.

## Summary

Keep open: current main and v2026.6.11 still route explicit `OPENCLAW_HOME=/path/.openclaw` through helpers that append another `.openclaw`, and the open closing PR is still the active fix candidate rather than a merged implementation.

## What This Changes

The issue reports that `openclaw onboard` writes config and state under `$OPENCLAW_HOME/.openclaw` when `OPENCLAW_HOME` already points at a `.openclaw` state directory.

## Best Possible Solution

Land or replace https://github.com/openclaw/openclaw/pull/87255 with a compatibility-safe basename guard that updates state, config-dir, and config-candidate resolution together and handles already-nested state through `openclaw doctor --fix`.

## Reproduction Assessment

Yes. Source inspection of current main and v2026.6.11 shows `resolveStateDir`, `resolveConfigDir`, and default config candidates still append `.openclaw` after resolving explicit `OPENCLAW_HOME`, matching the reported nested path without a live onboarding run.

## Solution Assessment

Yes for keeping this issue open behind the active linked PR. The best code solution is a narrow known-state-directory basename guard plus doctor-owned recovery for already-nested data, not a broad direct-`OPENCLAW_HOME` behavior change or runtime fallback.

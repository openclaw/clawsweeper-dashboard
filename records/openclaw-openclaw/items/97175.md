## Label Justifications

- `P1`: An enabled timeout can create concurrent same-session maintenance workers in an interactive session path.
- `merge-risk: 🚨 compatibility`: The PR adds an opt-in compaction configuration key whose timeout semantics must remain safe for existing third-party context engines.
- `merge-risk: 🚨 session-state`: Concurrent maintenance can conflict around the same session even when the timed-out worker’s late core writes are fenced.
- `merge-risk: 🚨 availability`: The change intentionally releases a lane while the original worker can remain live, so an unresolved worker-lifecycle contract can affect later session work.

## Summary

Keep this PR open for a maintainer decision before merge: its timeout releases the logical lane while the timed-out plugin worker can still be executing, so the existing per-session coalescing guarantee is no longer preserved after a timeout.

## What This Changes

The branch adds an opt-in per-task timeout and late-side-effect fence for deferred context-engine turn maintenance, documents the new setting, and backs off repeated `session.stalled` warnings.

## Best Possible Solution

Keep foreground turns unblocked at timeout, but retain a per-session physical-worker ownership record until the original maintenance promise settles so later maintenance requests coalesce into one deferred rerun; introduce plugin cancellation only through an explicitly approved contract.

Question: After an opt-in maintenance timeout releases a foreground turn, should OpenClaw continue coalescing same-session maintenance until the original plugin worker settles, or should it establish a new cancellable maintenance contract before allowing replacement workers?

Rationale: The command queue can release scheduling ownership without terminating the plugin-owned work, and neither the existing ContextEngine maintenance seam nor this PR proves a safe concurrent-maintenance contract.

Likely owner: Jerry-Xin

Owner confidence: low

Options:

- **Retain physical-worker coalescing (recommended):** Keep a separate per-session settlement record after timeout, fence the timed-out worker, and schedule at most one rerun only after that original worker settles.
- **Design explicit cancellation:** Add a maintainer-approved ContextEngine cancellation/abort contract, then permit replacement maintenance only after the old worker acknowledges cancellation.

## Reproduction Assessment

Yes in source terms: current main’s deferred maintenance enqueue has no task timeout, while the queue contract explicitly allows a timed-out task to continue unwinding after its lane is released. The PR also supplies a credible real Gateway reproduction of the configured timeout path.

## Solution Assessment

No: fencing late core side effects is necessary, but it is not sufficient if the timeout permits another same-session maintenance worker to start before the first plugin call settles.

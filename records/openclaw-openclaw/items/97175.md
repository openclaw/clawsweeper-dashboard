## Summary

This PR has credible real-runtime proof for releasing a wedged maintenance lane and fencing host-owned late writes, but it still changes the public context-engine behavior so a second same-session `maintain()` may run while the first remains active. Existing engines were not previously required to be re-entrant, so this remains a P1 compatibility and session-state blocker until maintainers choose a serialization or cancellation contract.

## What This Changes

Adds an opt-in deferred context-engine maintenance timeout, fences late host-side writes after timeout, documents a new `maintain()` concurrency expectation, and throttles repeated stalled-session warnings.

## System Context

Deferred context-engine maintenance runs after an agent turn and shares a per-session lane with follow-up work. The scheduler invokes plugin-owned maintenance, then updates task state and transcript data that the next same-session turn may read.

## Architecture Diagram

flowchart LR

  C --> D[Plugin context engine maintain]
  C --> E[Timeout and fence]
  D --> F[Transcript and task updates]
  E --> G[Queued foreground turn]
  F --> G

## Best Possible Solution

Keep foreground progress independent from a wedged maintenance lane while preserving at-most-one active same-session plugin maintenance invocation through a core-owned tail/coalescing barrier, or introduce a deliberately reviewed cancellable plugin contract before permitting overlap.

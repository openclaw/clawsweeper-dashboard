## Summary

Keep this PR open: it addresses the session-liveness symptom and has credible real-runtime proof, but the current patch still releases the maintenance lane while the timed-out plugin call continues. Its new public contract permits a second same-session `maintain()` before the first settles, leaving plugin-owned locks, stores, and side effects concurrent; the host fence only protects host-owned writes. This repeats the existing P1 blocker at the unchanged head rather than introducing a new late finding.

## What This Changes

This PR adds an opt-in per-task timeout for deferred context-engine maintenance, fences late host-side effects after timeout, documents a new engine concurrency expectation, and throttles repeated stalled-session warnings.

## System Context

After an agent turn, background-capable context-engine plugins run deferred maintenance on a per-session lane before later same-session work proceeds. The command queue, task state, transcript rewrite path, and session diagnostics together determine whether a wedged maintenance run delays user turns or can safely be bypassed.

## Architecture Diagram

flowchart TD
  A[Completed agent turn] --> B[Deferred maintenance scheduler]
  B --> C[Per-session maintenance lane]
  C --> D[Context-engine plugin maintain call]
  D --> E[Transcript and task updates]
  C --> F[Queued same-session user turn]
  G[Configured timeout] --> C
  G --> H[Host-side fence]
  H --> E

## Best Possible Solution

Keep foreground user-turn liveness by releasing the blocked wait, but retain a core-owned per-session invocation tail or coalescing barrier so a replacement maintenance invocation cannot overlap the abandoned plugin call; document and test that bounded lifecycle instead of shifting serialization responsibility to every existing engine.

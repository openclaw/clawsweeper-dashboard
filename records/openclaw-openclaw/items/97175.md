## Summary

This PR remains necessary for the reported deferred-maintenance stall, and its latest branch appears to address the prior late-persist concern with a bounded persistence checkpoint. The remaining merge decision is whether the new opt-in timeout has the intended lifecycle semantics when plugin-owned maintenance continues after the lane is released; that needs an owner review rather than an automated close.

## What This Changes

The branch adds an opt-in deferred context-engine maintenance timeout and timeout fence, documents the new compaction setting, and throttles repeated `session.stalled` warnings.

## Best Possible Solution

Land only after the context-engine owners confirm and document one canonical timed-out-worker lifecycle: preserve foreground liveness while preventing a still-running plugin maintenance task from creating overlapping same-session maintenance work or stale side effects.

Options:

- **Define retained coalescing ownership (recommended):** Keep the timed-out run as the maintenance coalescing owner until its plugin promise settles, while allowing foreground turns to proceed behind the bounded checkpoint.
- **Accept fenced overlap:** Treat the fence and checkpoint as sufficient and document that a later deferred run may begin while the timed-out plugin call is still unwinding.
- **Use cooperative cancellation first:** Extend the supported context-engine lifecycle only if maintainers want plugins to receive and honor a formal cancellation contract.

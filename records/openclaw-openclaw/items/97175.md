## Label Justifications

- `P1`: A configured timeout can turn an existing plugin’s serialized same-session maintenance into concurrent execution, risking real interactive session failures.
- `merge-risk: 🚨 compatibility`: The PR adds a configuration surface and changes the effective lifecycle expectations for existing context-engine plugins.
- `merge-risk: 🚨 session-state`: Overlapping maintenance calls can race through plugin-owned session state even when OpenClaw fences its own transcript and task writes.
- `merge-risk: 🚨 availability`: The patch changes the balance between releasing queued turns and preserving maintenance sequencing, which can affect whether a session stays responsive.

## Summary

Keep this PR open: its timeout releases the per-session lane while the prior plugin `maintain()` can still run, and the new SDK documentation changes the contract to permit a second same-session invocation before the first settles. Host-side transcript fencing does not protect engine-owned locks, storage, or side effects, so existing context-engine plugins can still race.

## What This Changes

This PR adds an opt-in timeout for deferred context-engine maintenance, fences late host-side writes after timeout, documents a re-entrant maintenance expectation, and throttles repeated stalled-session warnings.

## System Context

After an agent turn, OpenClaw can defer context-engine maintenance on a session-specific lane before later same-session work proceeds. The scheduler, command queue, task state, transcript persistence, and plugin-maintained state must preserve ordering while still allowing a wedged maintenance operation to stop blocking user turns.

## Architecture Diagram

flowchart LR
  Turn[Completed agent turn] --> Scheduler[Deferred maintenance scheduler]
  Scheduler --> Lane[Per-session maintenance lane]
  Lane --> Engine[Context-engine plugin maintain call]
  Lane --> Timeout[Optional task timeout]
  Timeout --> Fence[Host-side late-write fence]
  Engine --> PluginState[Plugin-owned state and locks]
  Fence --> HostState[Transcript and task updates]
  Lane --> NextTurn[Queued same-session turn]

## Best Possible Solution

Keep the foreground turn unblocked after timeout, but retain a core-owned per-session invocation tail or coalescing barrier so no replacement maintenance call starts until the abandoned call settles; do not make re-entrancy a requirement for existing context-engine plugins without explicit SDK ownership approval and a migration plan.

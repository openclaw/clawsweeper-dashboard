## Summary

This PR has strong real-runtime proof for releasing a wedged maintenance lane and fencing host-owned late transcript/task writes, but it still leaves a P1 compatibility and session-state defect: after the timeout releases the lane, the scheduler may begin a second same-session `ContextEngine.maintain()` while the first plugin invocation is still running. Requiring every existing engine to become re-entrant changes the plugin contract rather than preserving the host’s prior serialization guarantee, so this should remain open for a narrow scheduler repair.

## What This Changes

The branch adds an opt-in timeout for deferred background context-engine maintenance, fences late host-side effects after a timeout, documents a new engine concurrency expectation, and throttles repeated stalled-session warnings.

## System Context

After an agent turn, OpenClaw may schedule context-engine maintenance in a per-session background lane; that maintenance can update task state and rewrite the session transcript. The next foreground turn waits on the session’s ordering barriers, so timeout handling must restore responsiveness without allowing stale or concurrent maintenance work to mutate the same session.

## Architecture Diagram

  G[Configured timeout] --> C

## Best Possible Solution

Keep the opt-in lane timeout and host-side fence, but retain a core-owned per-session invocation tail: release the foreground turn at timeout while coalescing or deferring later maintenance until the abandoned plugin call settles. Do not make re-entrant same-session `maintain()` a mandatory compatibility requirement for existing engines without an explicit plugin-API decision.

No: the host-side fence is a useful part of the fix, but documenting plugin re-entrancy is not the best compatible solution because the core scheduler previously owned same-session serialization. A core-owned invocation tail or coalesced deferred rerun preserves both liveness and existing engine assumptions.

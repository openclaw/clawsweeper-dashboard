## Label Justifications

- `P1`: A timed-out maintenance run can block or overlap same-session maintenance in a path affecting queued interactive turns.
- `merge-risk: 🚨 compatibility`: The new config option defines a new operational mode for existing context-engine plugins and needs a stable post-timeout contract.
- `merge-risk: 🚨 session-state`: The timeout releases the session lane while the original worker may still unwind, so overlapping maintenance can violate the existing single-owner session invariant.
- `merge-risk: 🚨 availability`: Concurrent or repeatedly requeued maintenance after a timeout can reintroduce plugin lock contention and session stalls.

## Summary

Keep this PR open: it has credible live proof and addresses a current-main liveness gap, but the latest head still drops the per-session coalescing record as soon as the timeout releases the lane, allowing another deferred maintenance worker to start while the timed-out plugin call is still unwinding. That can recreate concurrent same-session plugin maintenance despite the late-side-effect fence.

## What This Changes

The branch adds an opt-in `agents.defaults.compaction.turnMaintenanceTaskTimeoutMs` timeout and late-side-effect fence for deferred context-engine maintenance, documents the option, and backs off repeated `session.stalled` warnings.

## Best Possible Solution

Preserve one maintenance owner per session after a timeout—allow the foreground turn to proceed, but coalesce later maintenance requests until the timed-out worker settles, unless maintainers first adopt an explicit cancellable context-engine contract with equivalent safety guarantees.

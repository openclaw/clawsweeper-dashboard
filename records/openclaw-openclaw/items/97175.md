## Summary

Keep this PR open: it has strong real-runtime evidence for releasing a wedged maintenance lane, but its timeout path changes the existing ContextEngine plugin contract by allowing a second same-session `maintain()` call while the first may still run. The added documentation describes that break rather than preserving the legacy serialization invariant, so it remains a P1 compatibility and session-state blocker.

## What This Changes

Adds an opt-in timeout for deferred background context-engine maintenance, fences late host-side transcript and task writes, documents the resulting engine concurrency expectation, and throttles repeated stalled-session warnings.

## System Context

After an agent turn, the embedded runner may queue context-engine maintenance on a per-session background lane before later work continues. The proposed timeout releases that lane for responsiveness, while transcript rewrites and task lifecycle updates affect the session state the next foreground turn reads.

## Best Possible Solution

Release the foreground session lane on timeout, but retain a separate per-session maintenance-invocation barrier so legacy engines are never called concurrently; coalesce or defer successor maintenance until the timed-out invocation settles.

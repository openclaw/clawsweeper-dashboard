## Summary

Keep open: current main and v2026.6.11 still hardcode OpenClaw-owned prompt sections and do not expose the requested Safety/template-level user override; this remains a product and security-boundary decision, not a stale cleanup close.

## What This Changes

The issue requests a user-editable template or file-backed override for fixed OpenClaw system prompt sections such as Safety.

## Best Possible Solution

Decide the trusted customization contract first; if approved, implement a narrow opt-in section override model with explicit precedence, security docs, and prompt regression coverage, otherwise document the existing provider and hook paths as the supported customization surfaces.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve a narrow opt-in section contract (recommended):** Define the allowed editable section ids, precedence against provider/hook contributions, file or schema location, and required docs/tests before implementation.
- **Keep existing hooks/provider overlays only:** Close or document this direction as intentionally unsupported for core sections while pointing users to before_prompt_build, agent:bootstrap, and provider-owned overlays.
- **Split into narrower decisions:** Track identity, additive rules, and safety-section overrides separately so each can be approved or rejected with smaller blast radius.

## Reproduction Assessment

Yes, at source level. Current main still renders Safety and other OpenClaw-owned sections as literals, restricts typed section overrides to three provider-owned ids, and rejects SAFETY.md-style bootstrap names.

## Solution Assessment

No, the broad “editable as much as possible” direction is not yet the best fix. The maintainable path is a maintainer-approved narrow override contract with explicit trust, precedence, docs, and regression tests, or a documented decision to keep the existing hook/provider paths only.

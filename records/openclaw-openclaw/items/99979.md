## Summary

Keep open: current `main` and the latest release still let `truncateLine` exceed the requested limit by appending `...` after the slice, and no duplicate issue or merged PR owns this max-length fix. The bug is small and source-proven, with existing tests currently encoding the overflow behavior.

## What This Changes

The issue reports that `truncateLine` appends an ellipsis after slicing to the requested limit, causing truncated subagent display text to exceed `maxLength`.

## Best Possible Solution

Update `truncateLine` to reserve ellipsis width while keeping UTF-16-safe truncation, define tiny-limit behavior, and adjust focused formatter/list tests so returned label/task strings never exceed the requested limit.

## Reproduction Assessment

Yes, source-reproducible: current `main` slices to `maxLength` and then appends `...`, and existing tests expect outputs longer than the requested limit. I did not run Vitest because this review was read-only.

## Solution Assessment

Yes. The best fix is at the shared helper boundary, not at each caller, because both label and task display paths use `truncateLine` and should share the same length and surrogate-safety invariant.

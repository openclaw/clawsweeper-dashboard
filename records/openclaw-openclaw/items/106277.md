## Summary

The failing schema belongs to Codex’s native `automation_update` tool as forwarded through the third-party CC Switch Codex proxy, while OpenClaw’s supported DeepSeek path uses the dedicated DeepSeek provider rather than the Codex runtime.

## What This Changes

Investigate an HTTP 400 caused by a null tool-input schema type when a CC Switch Codex endpoint routes Codex’s native automation tool to DeepSeek.

## Best Possible Solution

Use OpenClaw’s dedicated DeepSeek provider for `deepseek/deepseek-v4-flash`; if CC Switch must proxy a Codex session, report or normalize the native `automation_update` schema in CC Switch or the Codex app/runtime that emits it, not in OpenClaw’s bridged-tool layer.

## Summary

Keep open. A July 23 report reproduces the delayed failure on v2026.7.1-2: hot reload rejects an invalid snapshot while the process remains live, but the same file later fails managed startup and takes Telegram and WhatsApp offline. Current related work protects rejected RPC writes and narrows last-known-good recovery, but does not settle this external-edit/restart recovery policy.

## What This Changes

Request managed gateway recovery that prevents an invalid on-disk configuration, previously rejected by hot reload, from taking channels offline on a later restart.

## System Context

The Gateway reads `openclaw.json` to start channels and watches it while running. Invalid external edits can be rejected during live reload while the current runtime remains active, but a managed restart loads the persisted file again and can fail before message channels come back.

## Architecture Diagram

flowchart LR
  A[External config edit] --> B[Config validation]
  B -->|Valid| C[Gateway runtime]
  C --> D[Telegram and WhatsApp channels]
  B -->|Invalid during hot reload| E[Keep active runtime]
  E --> F[Invalid file remains on disk]
  F --> G[Managed restart]
  G --> H[Startup validation fails]
  H --> I[Channels unavailable]

## Best Possible Solution

Add a narrowly scoped, auditable recovery design: preflight the exact on-disk file before a managed restart, preserve the active runtime when it is invalid, retain a timestamped rejected artifact, and provide a visible Doctor or recovery action; add automatic last-known-good restoration only if maintainers explicitly accept and test its stale-snapshot semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For invalid base configuration that hot reload has already rejected, should a managed Gateway restart automatically restore a validated last-known-good snapshot, or should it block the restart and require an explicit in-product recovery action?

Rationale: Automatic restoration protects message availability but can revert intended configuration, whereas a restart block preserves operator intent but still requires a usable recovery surface for remote-only deployments.

Likely owner: jalehman

Owner reason: Their merged recovery-policy work is the strongest available ownership signal for the stale-config versus availability tradeoff.

Owner confidence: high

Options:

- **Block restart and expose recovery (recommended):** Preflight the persisted file, keep the current Gateway running when it is invalid, and surface an explicit Doctor or recovery action that preserves the rejected file.
- **Restore last-known-good automatically:** Restore only a validated base-config snapshot, preserve the rejected file, notify the owner after startup, and add stale-snapshot safeguards.
- **Retain fail-closed startup:** Keep manual Doctor recovery as the only path and document that invalid external edits must be repaired before any restart.

## Reproduction Assessment

Yes, with high confidence from the reported release reproduction and the described reload/startup contract: save an invalid external edit while the Gateway runs, confirm reload rejects it while runtime stays alive, then restart the managed Gateway and observe startup validation fail on the persisted file.

## Solution Assessment

Unclear. Blocking a managed restart on the exact invalid file is the narrowest availability protection, but automatic last-known-good restoration is not safely decidable without maintainer intent because stale recovery can overwrite desired settings.

## Summary

Keep open. A fresh July 23, 2026 report reproduces the delayed outage on OpenClaw 2026.7.1-2: invalid configuration is rejected during reload but remains on disk, then a systemd restart fails repeatedly and takes Telegram and WhatsApp offline. The requested automatic last-known-good restore is not a routine bug fix because it can silently roll back intentional configuration; maintainers need to choose the managed-startup recovery contract.

## What This Changes

Add a safe managed-gateway path that prevents an invalid on-disk `openclaw.json` from becoming a channel outage after a later restart when a verified last-known-good snapshot exists.

## System Context

The configuration subsystem validates the file used by hot reload and gateway startup, while the gateway lifecycle brings channels online after startup succeeds. A rejected live-reload candidate can leave the in-memory gateway running, but a later managed restart re-reads the persisted file and can prevent all configured channels from starting.

## Architecture Diagram

flowchart LR

  B --> C[Live reload validation]
  C -->|invalid snapshot| D[Existing gateway keeps running]
  D --> E[Managed restart]

## Best Possible Solution

Define one explicit managed-restart recovery contract: block a restart when the live process has rejected the exact on-disk snapshot, and decide whether startup may restore only a verified, policy-eligible snapshot with durable operator notification; retain fail-closed behavior when no safe recovery candidate exists.

Question: Should a managed gateway automatically restore a verified last-known-good configuration after invalid startup input, or should it remain fail-closed and only suppress restarts while the current valid process is still alive?

Rationale: Both choices protect a real user need but trade channel availability against the risk of silently reverting intentional configuration. Existing recovery work explicitly distinguishes unsafe stale-snapshot cases, so source inspection alone cannot choose the permanent contract.

Likely owner: jalehman

Owner reason: Their merged recovery-policy work is the closest concrete ownership signal and already documents the stale-rollback boundary this decision must preserve.

Owner confidence: high

Options:

- **Adopt bounded managed recovery (recommended):** Restore only a validated, policy-eligible last-known-good snapshot, preserve the rejected file for inspection, and notify the operator after channels return.
- **Keep startup fail-closed:** Block restart when a live valid gateway rejects the disk snapshot, but require explicit Doctor or operator repair after a cold-start validation failure.
- **Defer to a broader rollback design:** Fold this path into the canonical rollback proposal so startup, config writes, plugin validation, and update behavior share one documented policy.

## Evidence

- **Fresh managed-service reproduction:** A July 23, 2026 comment reports OpenClaw 2026.7.1-2 on Ubuntu with systemd: reload logged both a rejected hooks configuration and an applied hot reload; the invalid file remained on disk, and five later restart attempts failed, taking configured WhatsApp and Telegram channels offline.

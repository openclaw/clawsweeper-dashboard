## Summary

Keep open. Current main and the latest release have cron error classification, generic transient retry/backoff, and failure alerts, but they still do not implement the requested recurring reason-aware guard layer, job-level cooldown/disabled guard state, Retry-After-aware scheduling, or full client-visible policy surface.

## What This Changes

The issue requests reason-aware cron guardrails that classify quota, auth, rate-limit, timeout, format, and unknown failures to choose backoff, circuit-break, alerting, and visible job-state behavior.

## Best Possible Solution

Keep this as the canonical broad cron guardrail item until maintainers approve a policy that covers recurring cron classification, guard state, protocol/UI visibility, docs, tests, and provider cooldown coordination.

## Reproduction Assessment

Yes for the source-level gap: current recurring cron scheduling can be traced through applyJobResult, where error handling still uses generic retry/backoff and lacks guard-state fields. I did not establish a live provider retry-storm reproduction.

## Solution Assessment

Unclear as an implementation plan until maintainers choose the default policy. The narrowest maintainable solution should not be a timer-only branch; it needs state/schema/docs/client visibility and clear interaction with provider cooldowns.

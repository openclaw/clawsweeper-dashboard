## Summary

Keep open. Current main and the latest release have useful partial pieces, including last error classification and transient cron retry/backoff, but recurring cron still lacks the requested reason-aware guard layer, job-level cooldown/disabled circuit state, Retry-After-aware recurring scheduling, and maintainer-approved default policy.

## What This Changes

Request reason-aware cron guardrails that classify quota, auth, rate-limit, timeout, format, and unknown failures, then back off, circuit-break, notify, persist state, and expose that state with safe configurable defaults.

## Best Possible Solution

Define one maintainer-approved cron guard policy that classifies terminal run errors once, persists/display guard state, respects Retry-After where available, coordinates with auth-profile/provider cooldowns, and adds focused docs plus regression coverage across recurring cron, one-shot cron, protocol, and UI surfaces.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 record lastErrorReason and run transient retry/backoff, but they lack recurring cron circuit-break fields and billing/auth/format-specific disable or cooldown policy. I did not live-replay a provider retry storm.

## Solution Assessment

Unclear as a single implementation: the requested direction is maintainable, but the best fix needs maintainer policy decisions for defaults, upgrade behavior, config shape, provider cooldown interaction, and user-visible recovery.

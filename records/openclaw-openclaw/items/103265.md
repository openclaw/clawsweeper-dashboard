## Label Justifications

- `P1`: The observed multi-megabyte core RPC response can repeatedly break the mobile agent-list workflow on slow real-world links.
- `impact:ux-friction`: Affected users wait for timeouts and receive an empty placeholder agent list, while increasing the timeout is only a fragile workaround.
- `maturity:stable`: The issue affects the M4 Stable Gateway runtime, specifically its Gateway RPC APIs and Events capability.

## Summary

Current `main` still permits full base64 avatar projection up to the shared 2 MiB limit, so the gateway payload problem remains. An open PR targets it, but its global 256 KiB cap would also change previously accepted upload and configured-avatar behavior, requiring a maintainer choice before landing.

## What This Changes

Bound avatar data projected into gateway agent listings so response size stays predictable as the number and source size of agent avatars grow.

## Best Possible Solution

Centralize a bounded visual projection in `src/agents/identity-avatar.ts`, preserve the existing accepted source policy, and let metadata-only callers omit avatar bytes; use a lazy reference only if maintainers explicitly want the broader protocol change.

- **Lazy Avatar Fetch:** Add a reference and authenticated fetch surface, then migrate clients to lazy cached loading at greater protocol and client cost.

## Reproduction Assessment

Yes at source level. Current code deterministically allows each workspace avatar to add up to 2 MiB before base64 overhead, and the report provides a measured 4.15 MB live response with a resulting Android timeout.

## Solution Assessment

The bounded-projection goal is the right fix, but the open shared-cap patch is not yet the best demonstrated implementation because it changes accepted avatar behavior outside the problematic response.

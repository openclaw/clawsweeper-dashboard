## Summary

Keep open: current main has iMessage-specific recovery and some narrower Telegram/queue work, but it still does not provide the requested provider-wide missed-inbound catch-up for Discord/Slack-style gateway downtime windows.

## What This Changes

Request a configurable, provider-aware startup catch-up or replay mechanism so inbound channel messages sent during gateway downtime are not silently lost.

## Best Possible Solution

Keep this as the canonical design tracker and land provider-owned recovery paths, adding shared SDK/core durability seams only where provider plugins cannot safely implement replay, dedupe, policy gating, and operator controls themselves.

## Reproduction Assessment

Yes at source level: current main has iMessage recovery but no Slack/Discord catch-up surface, and restart drain still rejects new command-lane work. I did not perform a live Discord or Slack restart test in this read-only review.

## Solution Assessment

Unclear as a single implementation. The last-outbound anchor is plausible, but the maintainable solution should be channel-owned per provider with shared durable receive/replay seams only where the plugin API needs them.

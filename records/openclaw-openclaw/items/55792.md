## Summary

Keep open: current main has iMessage downtime recovery and Telegram-specific durable spooling, but it still does not implement the requested cross-channel missed-inbound catch-up for Discord/Slack-style gateway downtime windows. The issue remains the best canonical tracker because related items are provider-specific, partial, closed, or still unmerged.

## What This Changes

Request a configurable post-startup catch-up/replay path that recovers inbound channel messages sent while the gateway was restarting or offline.

## Best Possible Solution

Keep this as the canonical design tracker and land provider-owned replay or durable-ingress implementations, adding shared SDK/core seams only where the current plugin API cannot express safe idempotent recovery.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: current main has iMessage and Telegram-specific recovery paths, but no Slack/Discord startup history catch-up or generic provider replay surface; no live Discord or Slack restart run was performed.

## Solution Assessment

Is this the best way to solve the issue? Unclear as one generic last-outbound implementation; the maintainable path is likely provider-owned recovery with shared durable replay/idempotency seams only where needed.

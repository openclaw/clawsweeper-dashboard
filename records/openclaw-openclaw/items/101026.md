## Label Justifications

- `P1`: A documented outbound interception and observation hook path is silently bypassed for a real channel auto-reply workflow, with security and delivery-policy consequences.
- `impact:message-loss`: Plugin rewrite, cancel, and sent-observation decisions can be skipped even while the user-visible Feishu message is delivered.
- `impact:security`: DLP, moderation, audit, or safety plugins that rely on outbound hooks can fail open on the uncovered Feishu direct-dispatch path.
- `impact:session-state`: Post-send analytics and session-correlated hook consumers can miss Feishu outbound delivery events and normal inbound claim decisions.

## Summary

Keep open: current main appears to have repaired the durable `message` tool path through shared outbound delivery, but same-channel Feishu auto-reply still uses a prebuilt dispatcher that bypasses the documented outbound hook seam, and normal inbound `inbound_claim` remains intentionally binding-only in source and tests.

## What This Changes

The issue requests uniform Feishu auto-reply, durable `message` sends, and normal inbound processing coverage for `message_sending`, `reply_payload_sending`, `message_sent`, and `inbound_claim` plugin hooks.

## Best Possible Solution

Every Feishu outbound path should pass through one canonical hook-aware delivery seam, and any normal-inbound `inbound_claim` expansion should be explicitly documented with exactly-once and first-claim semantics.

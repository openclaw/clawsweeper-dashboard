## Label Justifications

- `P1`: The reported behavior silently drops all inbound channel events while presenting the channel as healthy, affecting a live message workflow.
- `merge-risk: 🚨 compatibility`: Existing source-loaded external channel installations will change from misleading runtime operation to an explicit startup failure requiring operator remediation.
- `merge-risk: 🚨 message-delivery`: The shared ingress monitor controls whether inbound channel events are admitted and drained, so its startup semantics directly affect delivery.

## Summary

This is a targeted fix for a real message-delivery failure mode: an untrusted channel plugin can appear healthy while its durable ingress queue repeatedly fails. The branch’s fail-fast approach is plausible and preserves the existing trust boundary, but it changes shared channel startup behavior and needs maintainer confirmation plus after-fix runtime proof before merge.

## What This Changes

The PR opens a channel plugin’s durable ingress queue before polling begins, so a trust-gate denial fails channel startup rather than silently dropping inbound messages and repeatedly logging drain errors.

## System Context

Channel plugins accept transport events and place them into a durable ingress queue before the shared inbound-reply flow processes them. The plugin runtime grants that queue only to bundled or trusted official installations, so a denied queue must be surfaced to channel startup rather than treated as a usable connected channel.

## Best Possible Solution

Keep the trust restriction intact, make an unavailable durable ingress queue a clear failed channel state, and add redacted live proof that an untrusted Slack load fails visibly while a properly installed Slack plugin receives an inbound event.

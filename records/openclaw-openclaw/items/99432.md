## Best Possible Solution

Land one focused classifier fix that preserves overloaded payload classification before generic 429 rate_limit fallback, keeps billing and plain 429 behavior unchanged, and then close this issue and the older duplicate cluster together.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: a 429 signal with an overloaded payload can derive overloaded from the message, but the 429 status branch then returns rate_limit after only checking billing cases.

## Solution Assessment

Yes. The narrow maintainable fix is to preserve overloaded inside the shared 429 classifier while leaving plain rate-limit and billing-shaped 429 responses on their existing paths.

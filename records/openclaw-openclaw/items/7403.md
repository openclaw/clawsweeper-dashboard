## Summary

Keep open: current main still has no enforceable Private/Secret/Incognito session contract; existing context-injection controls only suppress bootstrap context while session creation, transcript, history, and session-state paths remain durable and lack a private marker.

## What This Changes

Add a Mission Control Private Mode that suppresses workspace context and prevents private sessions from reading or writing durable workspace, memory, and history state.

## Best Possible Solution

Design one additive private/ephemeral session contract across Gateway protocol, SessionEntry, transcript/store writes, memory flush/indexing, plugin SDK visibility, channel triggers/defaults, and Control UI, with tests proving no private context reads or durable writes.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What exact privacy boundary should OpenClaw promise for Private Mode before implementation: context-only demo mode, or a hard per-session no-read/no-write/no-persistence mode?

Rationale: The requested behavior changes a security and privacy promise across protocol, persistence, memory, plugin, tool, channel, logs, and UI semantics, so automation should not choose the threat model or public contract.

Likely owner: steipete

Owner reason: steipete already reviewed this as the canonical private-mode tracker and framed the product/security boundary questions that remain unresolved.

Owner confidence: high

Options:

- **Hard per-session ephemeral contract (recommended):** Add a session-level protocol and state marker that gates transcript/store writes, memory reads/writes, plugin persistence, channel defaults, and UI status; this best matches the issue and duplicate reports.
- **Context-only demo mode:** Limit the feature to suppressing bootstrap/context injection and label it clearly as not private, no-persist, or memory-safe.
- **Defer for plugin/session API design:** Keep the issue open while designing the plugin SDK and session lifecycle hooks needed for third-party persistence enforcement.

## Solution Assessment

The requested direction is valid, but the best fix is a maintainer-approved core privacy contract rather than a UI-only toggle or config-only validation; contextInjection: "never" is only a partial context-suppression mitigation.

## Summary

Keep open: current main and v2026.6.11 still have no enforceable per-session private/no-persist contract, while the discussion and closed duplicates establish this issue as the canonical privacy-mode tracker requiring maintainer-approved security and product semantics.

## What This Changes

Add a per-session private mode that suppresses workspace and memory context, prevents durable history and workspace writes, uses temporary working state, and displays its status in Control UI.

## Best Possible Solution

Define one additive core private-session contract across Gateway protocol, runtime admission, transcript and session storage, bootstrap and memory reads, tool/media/plugin persistence, channel activation, and Control UI, with explicit scope wording and regression proof that private sessions neither load protected workspace context nor leave OpenClaw-owned conversational artifacts.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw promise an enforceable per-session private mode, and exactly which reads, writes, providers, tools, plugins, logs, and lifecycle events must that promise cover?

Rationale: A privacy badge is a security promise; implementation cannot safely begin until maintainers choose the threat model, activation authority, persistence boundary, and behavior across restart and child-session flows.

Likely owner: steipete

Owner reason: The recent canonical review and session-area history make this the strongest available routing candidate for the product and security decision.

Owner confidence: high

Options:

- **Approve full private-session contract (recommended):** Design an additive core mode with explicit guarantees and enforcement across every OpenClaw-owned context and persistence surface before exposing the UI toggle.
- **Limit scope to context suppression:** Offer a clearly named demo-context mode that suppresses bootstrap injection but explicitly does not claim incognito or no-persistence guarantees.
- **Decline the mode:** Keep existing contextInjection and cleanup controls, document their limitations, and avoid presenting them as a privacy guarantee.

## Reproduction Assessment

Yes at source level: current session protocol, stored session type, configuration schema, persistence documentation, and Control UI-facing session model expose no private or no-persist contract. This is a missing capability rather than a runtime failure needing a live repro.

## Solution Assessment

No—the original UI toggle alone is not the best solution because it could imply guarantees that lower layers do not enforce. The maintainable solution is a single core session policy propagated through every read and persistence boundary before adding UI and channel triggers.

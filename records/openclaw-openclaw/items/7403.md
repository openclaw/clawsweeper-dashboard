## Summary

Current main still lacks an enforceable per-session private or ephemeral contract across Gateway schemas, persisted session state, workspace-memory handling, and Control UI, while current behavior remains durably session-oriented. citeturn745029view0turn541080view0turn368667view0turn774502view0

## What This Changes

Add an enforceable per-session private mode that suppresses personal workspace context and prevents durable transcript, memory, and related session-state writes.

## Best Possible Solution

Define one additive, server-authoritative private-session capability with a precise threat model, explicit retained-metadata policy, no private workspace or memory reads, no durable content writes across core and plugin hooks, safe provider semantics, visible UI state, and end-to-end negative persistence tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What exact guarantee should a private session make about workspace reads, durable content writes, remote-provider transmission, retained operational metadata, and who may activate or override it?

Rationale: A UI toggle cannot safely define this security boundary; the answer determines protocol shape, storage behavior, plugin and channel enforcement, provider policy, recovery semantics, and whether the product may claim “private” or “incognito.”

Likely owner: steipete

Owner reason: This person supplied the latest substantive canonical-tracker review and is the strongest available routing signal across the affected session and config surfaces.

Owner confidence: high

Options:

- **Full private session contract (recommended):** Guarantee no private workspace or memory reads and no durable content persistence across core and participating plugins, with explicitly documented minimal metadata and provider behavior.
- **No-history mode only:** Prevent transcript and memory persistence but keep normal workspace context and remote-provider behavior under a narrower, non-incognito name.
- **Do not add a guarantee:** Keep existing reset, retention, context-injection, and sandbox controls separate and avoid presenting them as a private session mode.

## Reproduction Assessment

Yes, at source level: current-main protocol, config, persisted session type, and Control UI lack a private or no-persist field, while current documentation explicitly describes durable transcript and memory behavior.

## Solution Assessment

The requested guarantee is worthwhile, but a Mission Control toggle plus bootstrap suppression is not sufficient. The narrow maintainable approach is one server-authoritative session contract enforced at every context-read and persistence boundary, with the UI only controlling and displaying that contract.

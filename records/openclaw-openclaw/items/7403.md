## Summary

Keep open: current main and v2026.6.11 still lack an enforceable per-session private/no-persist contract, while the discussion and closed duplicates establish this as the canonical tracker for a security-sensitive product capability requiring maintainer-approved semantics.

## What This Changes

Add an enforceable per-session private mode that suppresses workspace and memory context, prevents durable history writes, uses temporary state, and exposes Mission Control controls and status.

## Best Possible Solution

Define one additive private-session policy at the Gateway/session owner boundary, propagate it as prepared runtime state, and prove that every covered read and persistence sink fails closed while the UI clearly states exclusions and restart behavior.

## Maintainer Decision

Question: What exact privacy guarantee and activation authority should OpenClaw support for private sessions across core and plugin-owned persistence surfaces?

Rationale: The implementation cannot safely proceed until maintainers define whether the feature means only no transcript and workspace context, or a broader zero-durable-trace promise covering memory, tools, media, logs, plugins, metrics, backups, and channel policy.

Likely owner: steipete

Owner reason: The strongest available routing signal is the recent canonical-session review plus repeated history across the central protocol, session-server, and persisted-state files.

Owner confidence: high

Options:

- **Bounded private sessions (recommended):** Guarantee no workspace or memory injection and no durable transcript/session content, while explicitly documenting allowed operational metadata and plugin limitations.
- **Zero durable trace:** Require all core and plugin persistence, logs, media, indexing, metrics, and recovery artifacts to remain memory-only or be rejected, accepting substantially larger architecture and compatibility work.
- **Defer the feature:** Keep existing context-injection controls and deletion/pruning tools without presenting a new security guarantee until the full boundary can be enforced.

## Reproduction Assessment

Yes at source level: session creation still establishes durable store and transcript state, and the protocol and persisted session model have no private/no-persist field. A live failure run is unnecessary to establish that the requested capability is absent.

## Solution Assessment

Unclear until maintainers define the security promise. A UI toggle or validation-only config is not sufficient; the best implementation must originate at the session owner boundary and cover every approved read and persistence sink.

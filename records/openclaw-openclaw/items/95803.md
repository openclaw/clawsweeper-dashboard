## Summary

The PR is still necessary because current main keeps pending fallback tool media after a successful messaging-tool media send, and the submitted patch is a focused handler-level fix with regression coverage for the stale-flag case. It should stay open because this is visible message-delivery behavior and the after-fix real transport proof remains insufficient: the PR has source-level tests and a pre-fix production observation, but no post-fix Telegram/log proof showing the generated media is delivered once.

## What This Changes

The PR clears pending fallback tool media whose basename matches media successfully sent by the message tool and adds regression coverage for success, failure, partial-drain, and global pending-media flags.

## Best Possible Solution

Land the handler-level suppression only after maintainers accept an explicit proof override or obtain redacted runtime/Telegram evidence showing one generated-media plus message-tool run sends once while failed or unmatched sends still preserve fallback delivery.

## Reproduction Assessment

Yes, at source level: current main records successful message-tool media separately from pending fallback media, and the completion path later reads pending media for source-reply delivery. I did not establish a live current-main Telegram reproduction in this review.

## Solution Assessment

Yes, the proposed layer is a reasonable narrow fix because handleToolExecutionEnd sees whether the message-tool send succeeded before suppressing fallback media. The remaining blocker is proof of the live transport behavior, not an identified code-shape defect.

## Summary

Keep open: the merged skill-creator bypass fix removed the narrow live-write path, but current main still lacks a skill-creation authority or routing model that can make a custom workflow run before the model selects `skill_workshop`.

## What This Changes

The issue requests an extensible Skill Workshop architecture so custom skill-creation workflows can run before Skill Workshop proposal persistence.

## Best Possible Solution

Define a maintainer-approved skill-creation authority model that lets custom tools or plugins prepare and validate proposal content while keeping Skill Workshop as the single persistence and apply boundary.

## Maintainer Decision

Question: Should OpenClaw add a first-class skill-creation authority/routing API, or should custom skill creators rely on explicit invocation and existing tool policy around `skill_workshop`?

Rationale: The source gap is real, but choosing between a new hook, policy/config surface, or meta-skill workflow convention changes public plugin/tool semantics and cannot be settled safely by cleanup automation.

Owner confidence: medium

Options:

- **Design a narrow authority API (recommended):** Add a maintainer-owned design for one pre-selection skill-creation authority path that composes with Skill Workshop proposal persistence and avoids a second write path.
- **Keep current explicit workflow model:** Document that custom skill creators must be explicitly invoked or tool policy must hide `skill_workshop`, with no new core routing API.
- **Defer to meta-skill orchestration:** Wait for the broader native meta-skill PR or successor design to prove this workflow before adding a separate Skill Workshop extension point.

## Reproduction Assessment

Not applicable as a bug reproduction: this is a feature/API-direction request. Source inspection does verify the current gap: `skill_workshop` is prompt-preferred when available, while current hooks and tool policy do not define a pre-selection skill-creation authority interface.

## Solution Assessment

Unclear pending maintainer direction. A dedicated hook or config model may be right, but current code already has plugin tools, tool policy, `before_tool_call`, and a proposal-content primitive, so the permanent boundary should be chosen before implementation.

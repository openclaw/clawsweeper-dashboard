## Summary

The report treats WebSocket protocol frames as application-level binary messages, but the stated `ws`-style message contract reassembles fragmented messages before the default binary handler receives them. No reproduction, frame trace, or code path shows that OpenClaw opts into fragment delivery, so the requested manual FIN buffering would duplicate the transport layer and risks changing message semantics.

## What This Changes

The issue requests manual buffering of fragmented binary WebSocket frames before forwarding reassembled audio data to realtime transcription.

## Best Possible Solution

Keep the normal WebSocket message abstraction; reopen with a minimal current-version reproduction that proves the server is configured to expose fragments or shows corrupted bytes after a complete `message` event.

## Label Justifications

- `P2`: The report describes a real but bounded sessions_send/WhatsApp delivery failure that needs maintainer review rather than emergency handling.
- `impact:message-loss`: The central symptom is an explicit group message request being suppressed as `REPLY_SKIP`, `ANNOUNCE_SKIP`, or `NO_REPLY` instead of being delivered.

## Summary

Keep open: current main and the latest release still route `sessions_send` turns as generic `inter_session` data, still teach exact skip/no-reply control tokens, and still suppress those tokens before channel delivery. The related structured handoff issue and open requester-return-path PR overlap, but neither has merged as the canonical fix for this WhatsApp explicit-delivery symptom.

## What This Changes

The issue asks OpenClaw to prefer explicit WhatsApp group delivery intent over `inter_session` skip-token heuristics when a `sessions_send` turn is meant to emit a normal channel message.

## Best Possible Solution

Review and either land or supersede https://github.com/openclaw/openclaw/pull/97311, then align the final behavior with the structured handoff direction in https://github.com/openclaw/openclaw/issues/33478 so explicit delivery intent outranks skip tokens without reintroducing ping-pong or duplicate delivery.

## Reproduction Assessment

No live high-confidence WhatsApp repro was run in this read-only review. The source path is reproducible from current main: `sessions_send` injects generic `inter_session` context, model-facing prompts still allow skip tokens, and the A2A flow suppresses those tokens before delivery.

## Solution Assessment

Unclear as a final implementation choice: a narrow prompt/message-tool repair is plausible, but the clean product answer may require a structured delivery-intent contract. Because that changes model-facing delivery semantics and overlaps open PR/design work, maintainer review is the right next step.

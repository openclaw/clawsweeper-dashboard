## Summary

The reported SQLite check-then-invalidate path is not present on current main. Bootstrap-token verification is serialized under the pairing lock, binds a token to the first device identity, persists that binding before returning, and rejects later use by a different identity; the report’s cited files and one-time-token premise do not match this implementation.

## What This Changes

The issue alleges that two concurrent device-authentication requests can redeem the same one-time pairing token before it is invalidated.

## Best Possible Solution

Keep the existing serialized first-device binding and bounded bootstrap-redemption contract; reopen only with a minimal concurrent reproduction against current main that shows two different device identities being accepted for one bootstrap token.

Keep open: current main and latest release still accept Telegram `direct.<peer>.tools`/`toolsBySender` in schema and types, but the active enforcement path remains group/channel-scoped and does not read Telegram `direct` entries. The duplicate issue was already closed to this issue, the attempted repair PR was closed unmerged, and the broader binding-policy issue only partially overlaps.

## What This Changes

The issue asks whether Telegram per-DM `direct.<peer>.tools` configuration is an intended runtime enforcement surface and, if so, to fix the mismatch where prompts apply but tool policy does not.

## Best Possible Solution

Choose one explicit contract: either enforce Telegram `direct.<peer>.tools`/`toolsBySender` end to end with direct-aware resolver coverage and Telegram proof, or remove/doctor/document the schema surface so operators cannot mistake it for a hard safety boundary.

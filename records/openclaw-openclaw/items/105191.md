## Label Justifications

- `P1`: A transient database failure can silently leave Telegram’s durable offset stale and replay already processed updates after restart.
- `impact:data-loss`: The uncommitted pending watermark is discarded from retry state while runtime state treats it as advanced.
- `impact:security`: Restarting from a stale offset can replay updates and repeat message-triggered or privileged side effects.

## Summary

Current main has a confirmed two-layer persistence bug, and the linked open PR repairs only one layer. Keep the issue open until the monitor propagates failed commits, the tracker preserves the newest retry target, and focused regression coverage proves the complete path.

## What This Changes

Ensure failed Telegram update-watermark database writes remain retryable and are not reported as successfully persisted.

## Best Possible Solution

Update `lastUpdateId` only after a successful offset-store commit, propagate write failures to a tracker that retains the maximum pending target, and add deterministic tracker and monitor tests for rejection, later retry, and concurrent coalescing.

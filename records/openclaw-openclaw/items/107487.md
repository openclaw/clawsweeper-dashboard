## Summary

This remains a valid source-reproducible session-lifecycle bug: current main has same-process freshness safeguards, but the inspected ACPX store surface still lacks demonstrated durable deletion of the closed resume identity, and no current-release restart reproduction proves the stale file is harmless. Likely related person: @steipete for the cross-boundary ACP lifecycle decision, with low confidence because exact file-history attribution was unavailable. ([github.com](https://github.com/openclaw/openclaw/blob/main/extensions/acpx/src/runtime.ts))

## What This Changes

Ensure `/acp close` clears ACPX persisted resume identity and the manager runtime handle so the next persistent turn creates a new backend session.

## Best Possible Solution

Give the ACPX plugin a durable, plugin-owned session-record clear operation, invoke it during manager close alongside runtime-handle eviction, and prove that both immediate reuse and post-restart reuse select a fresh backend session; longer term, remove duplicate file-backed identity if canonical SQLite state can own the lifecycle.

## Reproduction Assessment

Yes at source level: close a persistent ACPX session, restart before starting the replacement turn, then observe whether the persisted record causes resume rather than new-session creation. This exact path has not yet been executed against current main or v2026.7.1.

## Solution Assessment

The general cleanup direction is correct, but deleting files directly from the core manager is not the best ownership boundary; ACPX should expose the durable clear operation while core coordinates cache eviction and lifecycle ordering.

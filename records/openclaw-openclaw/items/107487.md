## Summary

This remains a credible ACP session-lifecycle bug: `/acp close` is documented as ending the OpenClaw session, but the source-backed report and prior review show that duplicate ACPX resume state may survive outside the canonical SQLite record and silently revive the closed identity. A focused current-release live reproduction is still needed before choosing the cross-boundary repair. Likely related people: osolmaz for the original ACP runtime work, dutifulbob for persistent channel bindings, amknight for recent ACP close controls, and steipete for the current lifecycle decision.

## What This Changes

Ensure `/acp close` clears or invalidates every persistent ACPX resume identity so the next turn creates a new session rather than resuming the closed one.

## Best Possible Solution

Make close a single lifecycle operation that evicts the manager handle and durably marks or removes the ACPX resume record so both the same process and a restarted gateway must use `session/new`; add focused regression coverage and avoid parallel OpenClaw-owned JSON state where the canonical SQLite store can own the lifecycle.

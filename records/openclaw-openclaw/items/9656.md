## Summary

Keep this issue open. Current main still normalizes Signal edit envelopes as ordinary inbound messages, and the only Signal-specific candidate PR closed unmerged without resolving transcript supersession or edit-triggered response policy.

## What This Changes

Add explicit handling for Signal `editMessage` envelopes so edited content retains its relationship to the original message and avoids duplicate context or responses.

## Best Possible Solution

Define one Signal edit contract—typed target identity, explicit correction metadata, deterministic transcript or pending-history supersession, and clear active-turn wake rules—then implement it in the Signal plugin with focused tests and only add a generic session seam if plugin ownership cannot express the chosen semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When Signal receives an edit for a message that may already be in session context or driving an active run, should OpenClaw replace the original turn, append a structured correction, or cancel and re-dispatch the corrected content?

Rationale: Signal transport parsing is straightforward, but transcript mutation and whether an edit wakes or cancels agent work define user-visible session semantics that cannot be selected safely from the issue alone.

Likely owner: steipete

Owner reason: The current Signal receive and routing behavior most strongly traces to this feature history, including the owner boundary where the policy would first be applied.

Owner confidence: high

Options:

- **Structured Correction (recommended):** Record the edit against the target timestamp, supersede pending history when possible, and append a structured correction without rewriting persisted transcript history or automatically waking unmentioned group runs.
- **Replace Original Turn:** Rewrite the original transcript entry and make subsequent context use only the corrected content, requiring a reliable persisted transcript mutation contract.
- **Cancel And Re-dispatch:** Cancel active work for the target message and dispatch the edited content as a new instruction, aligning with the broader cross-channel behavior proposed in https://github.com/openclaw/openclaw/issues/55691.

## Reproduction Assessment

Yes at source level: a Signal `editMessage` is flattened into the normal inbound path and identified by the new envelope timestamp. No live Signal run was needed to establish that the requested edit relationship and policy are absent.

## Solution Assessment

No, the issue's proposed list is useful direction but not yet one safe solution because it combines transport parsing, transcript mutation, deduplication, and wake policy. A structured correction contract with explicit maintainer-approved active-run semantics is the narrowest maintainable starting point.

## Label Justifications

- `P2`: Edited Signal messages can duplicate context and trigger unwanted replies, but the impact is bounded to one bundled channel workflow and needs a product decision before repair.
- `impact:session-state`: Original and edited Signal messages can both enter the conversation context, causing transcript and agent-state drift.
- `impact:message-loss`: Corrected Signal content is not linked to the original source message and can be represented as a separate inbound event.

## Summary

Keep open. Current main and the latest release still flatten Signal `editMessage.dataMessage` into the normal inbound path, do not model or use `editMessage.targetSentTimestamp`, and the direct fix attempt is closed unmerged.

## What This Changes

Handle Signal `editMessage` envelopes by preserving the original target timestamp, marking or replacing edited content, and avoiding duplicate responses when appropriate.

## Best Possible Solution

Implement a Signal-owned edit path that models `targetSentTimestamp`, carries explicit edit metadata into context, applies a maintainer-approved transcript or dedupe policy, suppresses non-mentioned group edit replies, and adds focused Signal tests.

## Reproduction Assessment

Yes, at source level. A Signal receive payload with `envelope.editMessage.dataMessage` follows the normal inbound path while `targetSentTimestamp` is neither typed nor used for message identity.

## Solution Assessment

Unclear as a final design. A plugin-local Signal edit path is the right boundary, but transcript replacement, dedupe, and reply-trigger semantics need maintainer choice before implementation.

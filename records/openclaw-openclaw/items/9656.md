## Label Justifications

- `P2`: Edited Signal messages can duplicate context and cause extra responses, but the impact is bounded to one bundled channel workflow.
- `impact:session-state`: Current Signal edits can appear as separate context entries rather than preserving the original-to-edited relationship.
- `impact:message-loss`: The corrected Signal content is not tied to the original message identity, so downstream handling can misrepresent or duplicate the message.

## Summary

Keep open. Current main still flattens Signal `editMessage.dataMessage` into the ordinary inbound path, does not type or use `editMessage.targetSentTimestamp`, and has no edit-aware transcript replacement, dedupe, marker, or reply-suppression behavior; the direct Signal fix attempts are closed unmerged.

## What This Changes

The issue requests Signal editMessage envelope handling so edited Signal messages preserve their relationship to the original message and avoid duplicate context or responses.

## Best Possible Solution

Add a Signal-owned edit-message path with typed targetSentTimestamp, explicit edit metadata or marker, maintainer-approved transcript/dedupe semantics, mention-gated reply policy, and focused Signal tests.

## Reproduction Assessment

Yes, at source level: an event containing envelope.editMessage.dataMessage follows the normal Signal inbound path while targetSentTimestamp is neither typed nor used for message identity. I did not run a live Signal edit flow during this read-only review.

## Solution Assessment

Unclear as a final design. A plugin-local edit path is the right foundation, but transcript replacement versus marker-only behavior and reply-suppression rules need maintainer product direction.

## Label Justifications

- `P2`: Edited Signal messages can duplicate context and trigger unwanted replies, but the affected workflow is bounded to one bundled channel and needs product semantics before repair.
- `impact:session-state`: The original and edited Signal message versions can both enter session context without a preserved edit relationship.
- `impact:message-loss`: Corrected Signal content is treated as a separate inbound message instead of updating or linking to the original content.

## Summary

Keep open. Current main and v2026.6.11 still flatten Signal `editMessage.dataMessage` into the normal inbound path, do not model `editMessage.targetSentTimestamp`, and the direct Signal fix attempt is closed unmerged while the broader lifecycle issue is only a partial overlap.

## What This Changes

Handle Signal `editMessage` envelopes so edited content is linked to the original message and does not create duplicate context or unwanted replies.

## Best Possible Solution

Implement a Signal-owned edit path that types `targetSentTimestamp`, carries explicit edit metadata or marker into context, applies maintainer-approved transcript/dedupe semantics, suppresses non-mentioned group edit replies, and adds focused Signal tests.

## Reproduction Assessment

Yes, at source level. A Signal receive payload with `envelope.editMessage.dataMessage` follows the normal inbound path while `targetSentTimestamp` is neither typed nor used for message identity; no live Signal transport replay was run in this read-only review.

## Solution Assessment

Unclear as a final design. A plugin-local Signal edit path is the right boundary, but transcript replacement, dedupe, and reply-trigger behavior need maintainer choice before implementation.

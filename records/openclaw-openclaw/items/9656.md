- `P2`: Signal edits can duplicate context and trigger unwanted replies, but the affected scope is one channel workflow and the remaining work needs product semantics before repair.
- `impact:message-loss`: Corrected Signal content is detached from the original target timestamp, so the intended edit relationship can be lost or duplicated in message handling.

## Summary

Keep open. Current main and the latest release still flatten Signal `editMessage.dataMessage` into ordinary inbound handling, do not model `editMessage.targetSentTimestamp`, and the direct Signal edit PR was closed unmerged; the remaining transcript, dedupe, and reply-trigger semantics need maintainer direction.

## What This Changes

Request Signal `editMessage` envelope handling so edited messages preserve their target timestamp relationship, avoid duplicate context or replies, and carry edit metadata into the session.

## Best Possible Solution

Adopt a documented Signal-owned edit policy that types `targetSentTimestamp`, carries edit metadata into context, applies the chosen transcript/dedupe behavior, suppresses non-mentioned group edit replies, and adds focused Signal tests.

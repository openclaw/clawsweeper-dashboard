## Label Justifications

- `P2`: Signal edit handling is a real channel workflow improvement with duplicate context/reply impact, but it is bounded and requires product semantics rather than emergency handling.
- `impact:message-loss`: The Signal edit relationship to the original message is lost because `targetSentTimestamp` is not modeled or preserved.
- `impact:session-state`: Edited Signal content can be recorded as a separate turn, causing transcript and context drift.

## Summary

Keep open. Current main still flattens Signal `editMessage.dataMessage` into the ordinary inbound message path, does not type or use `editMessage.targetSentTimestamp`, and the only direct Signal fix PR is closed unmerged.

## What This Changes

The issue requests Signal `editMessage` envelope handling so edited messages preserve their original-message relationship, avoid duplicate context, and avoid unwanted duplicate replies.

## Best Possible Solution

Implement an explicit Signal edit path in the bundled Signal plugin: type `targetSentTimestamp`, preserve edit metadata or an `[edited]` marker, use the target timestamp for dedupe/transcript replacement, and suppress non-mentioned group edit replies according to maintainer-approved semantics.

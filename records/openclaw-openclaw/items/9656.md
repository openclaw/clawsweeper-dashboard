## Label Justifications

- `P2`: Signal edits can duplicate context and trigger unwanted replies, but the affected scope is one channel workflow and the remaining work needs product semantics before repair.
- `impact:session-state`: Edited Signal content currently enters context as a separate ordinary message rather than updating or marking the original message state.
- `impact:message-loss`: The corrected Signal content is not linked to the original target timestamp, so the intended edit relationship can be lost or duplicated.

## Summary

Keep open. Current main and v2026.6.11 still flatten Signal `editMessage.dataMessage` into the ordinary inbound path, do not type or use `editMessage.targetSentTimestamp`, and the direct Signal edit PR is closed unmerged.

## What This Changes

The issue asks OpenClaw to handle Signal `editMessage` envelopes by linking edits to the original message, preserving edited-content context, and avoiding duplicate responses.

## Best Possible Solution

Implement a Signal-owned edit path that models `targetSentTimestamp`, carries explicit edit metadata into context, applies a maintainer-approved transcript/dedupe policy, suppresses non-mentioned group edit replies, and adds focused Signal tests.

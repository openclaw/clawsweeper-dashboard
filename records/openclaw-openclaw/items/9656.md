## Label Justifications

- `P2`: Signal edits can duplicate context and trigger unwanted replies, but the scope is one channel workflow and the remaining behavior needs product semantics before repair.
- `impact:message-loss`: Corrected Signal content is detached from the original target timestamp, so the intended edit relationship can be lost or duplicated in message handling.
- `impact:session-state`: Edited Signal content currently enters session context as a separate ordinary message rather than updating or marking original message state.

## Summary

Keep open. Current main and the latest release still flatten Signal `editMessage` envelopes into ordinary inbound messages, do not type or use `editMessage.targetSentTimestamp`, and leave transcript, dedupe, and reply-trigger semantics undecided.

## What This Changes

Handle Signal `editMessage` envelopes by linking edits to `targetSentTimestamp`, marking or updating context, deduping against the original message, and suppressing non-mentioned edit replies.

## Best Possible Solution

Adopt a documented Signal-owned edit policy that types `targetSentTimestamp`, carries edit metadata into context, applies the chosen transcript or dedupe behavior, suppresses non-mentioned group edit replies, and adds focused Signal tests.

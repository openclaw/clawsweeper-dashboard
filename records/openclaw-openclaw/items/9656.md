## Label Justifications

- `P2`: Edited Signal messages can duplicate context and trigger unwanted replies, but the impact is bounded to one bundled channel workflow and needs a product decision before repair.
- `impact:session-state`: Original and edited Signal versions can both enter conversation context, causing transcript and agent-state drift.
- `impact:message-loss`: Corrected Signal content is not linked to the original message and can be misrepresented or duplicated as a separate inbound event.

## Summary

Keep open. Current main and v2026.6.11 still flatten Signal `editMessage.dataMessage` into the ordinary inbound path, do not model or use `editMessage.targetSentTimestamp`, and the direct Signal fix PR is closed unmerged while the broader lifecycle issue only partially overlaps.

## What This Changes

The issue asks OpenClaw to handle Signal `editMessage` envelopes as edits instead of treating them as unrelated inbound messages.

## Best Possible Solution

Add a Signal-owned edit-message path with typed `targetSentTimestamp`, explicit edit metadata or marker, maintainer-approved transcript and dedupe semantics, mention-gated reply policy, and focused Signal tests.

## Reproduction Assessment

Yes, at source level. A Signal receive payload with `envelope.editMessage.dataMessage` follows the normal inbound path while `targetSentTimestamp` is neither typed nor used for message identity.

## Solution Assessment

Unclear as a final design. A plugin-local edit path is the right boundary, but transcript replacement, dedupe, and reply-trigger semantics need maintainer choice before implementation.

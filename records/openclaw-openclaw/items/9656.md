## Label Justifications

- `P2`: Edited Signal messages can duplicate context and trigger unwanted replies, but the impact is bounded to one bundled channel workflow and needs product design.
- `impact:message-loss`: Corrected Signal content is not linked back to the original `targetSentTimestamp`, so the edit relationship is lost.

## Summary

Keep open. Current main still flattens Signal `editMessage.dataMessage` into the normal inbound message path, does not model or use `editMessage.targetSentTimestamp`, and the direct Signal fix PR was closed unmerged while the broader lifecycle issue only partially overlaps.

## What This Changes

The issue requests Signal `editMessage` envelope handling so edited messages preserve their original timestamp relationship, avoid duplicate context, and avoid unnecessary replies.

## Best Possible Solution

Implement a Signal-owned edit path that models `targetSentTimestamp`, carries explicit edit metadata into context, applies maintainer-approved transcript/dedupe semantics, suppresses non-mentioned group edit replies, and adds focused Signal tests.

## Reproduction Assessment

Yes, at source level. A Signal receive payload with `envelope.editMessage.dataMessage` follows the ordinary inbound path, while `targetSentTimestamp` is neither typed nor used for message identity.

## Solution Assessment

Unclear as a final design. A plugin-local Signal edit path is the right boundary, but transcript replacement, dedupe, and reply-trigger semantics need maintainer choice before implementation.

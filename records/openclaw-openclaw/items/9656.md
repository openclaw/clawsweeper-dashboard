## Label Justifications

- `P2`: Edited Signal messages can duplicate context and trigger unwanted replies, but the impact is bounded to one bundled channel workflow and needs a product decision before repair.
- `impact:session-state`: The original and edited Signal messages can both enter conversation context, causing transcript and agent-state drift.
- `impact:message-loss`: Corrected Signal content is not linked to the original message and can be represented as a separate inbound event rather than the updated source message.

## Summary

Keep open. Current main still flattens Signal `editMessage.dataMessage` into the ordinary Signal inbound path, does not type or use `editMessage.targetSentTimestamp`, and the only direct Signal edit PR is closed unmerged; the remaining transcript, dedupe, and reply-trigger semantics need maintainer product review.

## What This Changes

The issue requests Signal `editMessage` envelope handling so edited messages keep their original-message relationship, avoid duplicate context, and do not trigger unwanted replies unless explicitly mentioned.

## Best Possible Solution

Implement a Signal-owned edit path that models `targetSentTimestamp`, carries explicit edit metadata into context, applies a maintainer-approved transcript/dedupe policy, suppresses non-mentioned group edit replies, and adds focused Signal tests.

## Reproduction Assessment

Yes, at source level. A Signal receive payload with `envelope.editMessage.dataMessage` follows the normal inbound path while `targetSentTimestamp` is neither typed nor used for message identity.

## Solution Assessment

Unclear as a final design. A plugin-local Signal edit path is the right boundary, but transcript replacement, dedupe, and reply-trigger semantics need maintainer choice before implementation.

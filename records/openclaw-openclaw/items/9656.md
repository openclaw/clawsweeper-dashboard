## Label Justifications

- `P2`: Edited Signal messages can duplicate context and trigger unwanted replies, but the impact is bounded to one bundled channel workflow and needs a product decision before repair.
- `impact:session-state`: Original and edited Signal messages can both enter conversation context, causing transcript and agent-state drift.

## Summary

Keep open. Current main and the latest release still flatten Signal `editMessage.dataMessage` into the ordinary inbound path, do not type or use `editMessage.targetSentTimestamp`, and the direct fix PR is closed unmerged.

## What This Changes

Request to handle Signal signal-cli `editMessage` envelopes by preserving the original target timestamp, marking or replacing edited content, deduping transcript context, and suppressing non-mentioned edit replies.

## Best Possible Solution

Implement a Signal-owned edit path that types `targetSentTimestamp`, carries explicit edit metadata into context, and applies maintainer-approved transcript, dedupe, and reply-suppression semantics with focused tests.

## Reproduction Assessment

Yes, at source level. A Signal receive payload with `envelope.editMessage.dataMessage` follows the normal inbound path while `targetSentTimestamp` is neither typed nor used for message identity.

## Solution Assessment

Unclear as a final design. A plugin-local Signal edit path is the right boundary, but transcript replacement, dedupe, and reply-trigger semantics need maintainer choice before implementation.

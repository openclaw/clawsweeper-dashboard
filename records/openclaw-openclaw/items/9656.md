## Summary

Keep this issue open: current main recognizes Signal edit payload content and targets replies at the edited message’s original timestamp, but it still sends the edit through the ordinary inbound turn path with the new envelope timestamp as its identity. That does not provide an edit-aware transcript update/dedupe contract or prevent an unwanted turn, while the only Signal-specific implementation PR was closed unmerged.

## What This Changes

Add Signal `editMessage` handling that retains the original-message relationship and avoids duplicate context or unintended replies for edited inbound messages.

## Best Possible Solution

Define a Signal-plugin edit event contract that preserves both the edit envelope timestamp and `targetSentTimestamp`, records explicit edit metadata or a transcript replacement, and suppresses non-mentioned group edits only after maintainers choose the active-run policy.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should a Signal message edit only update/edit-mark transcript context, or should it also cancel/supersede an active turn that began from the original message?

Rationale: Current main has a partial native-reply linkage but no durable semantics for transcript replacement, inbound dedupe, or an in-flight turn; choosing that behavior affects user expectations and the boundary with the broader cancellation proposal.

Likely owner: steipete

Owner reason: The current Signal inbound monitor and its routing/dispatch behavior have the strongest history connection to this area.

Owner confidence: high

Options:

- **Adopt a bounded Signal edit contract (recommended):** Keep the change in the Signal plugin, carry both timestamps as explicit edit metadata, update or annotate transcript context, and suppress a new group turn unless the edit explicitly mentions the agent.
- **Include active-turn cancellation:** Define edits as a cancellation-and-rerun signal, which requires a shared, cross-channel run-control contract and should be coordinated with https://github.com/openclaw/openclaw/issues/55691.
- **Retain ordinary inbound treatment:** Keep the existing generic inbound behavior and document that Signal edits may create a new turn, accepting duplicate-context risk.

## Reproduction Assessment

No live Signal reproduction was available in this read-only review, but source inspection gives a high-confidence source-level path: an `editMessage` is flattened to ordinary inbound content and retains the new envelope timestamp as its message identity.

## Solution Assessment

No; treating an edit as a normal inbound message is not the requested durable behavior, and the closed marker-only PR does not settle transcript or active-run semantics. A plugin-owned explicit edit contract is the narrowest maintainable solution after the product decision.

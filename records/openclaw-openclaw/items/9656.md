## Label Justifications

- `P2`: Edited Signal messages can duplicate context and trigger unwanted replies, but the impact is bounded to one bundled channel workflow and needs product semantics before repair.
- `impact:session-state`: Original and edited Signal messages can both enter the conversation context, causing transcript and agent-state drift.
- `impact:message-loss`: Corrected Signal content is not linked to the original message and can be misrepresented or duplicated as a separate inbound event.

## Summary

Keep open. Current main and the latest release still flatten Signal `editMessage.dataMessage` into the ordinary inbound path, do not model or use `editMessage.targetSentTimestamp`, and the closed Signal attempt at https://github.com/openclaw/openclaw/pull/9701 did not merge.

## What This Changes

The issue requests Signal `editMessage` envelope handling so edited messages carry edit identity or metadata instead of entering context as unrelated new messages.

## Best Possible Solution

Implement a Signal-owned edit path that models `targetSentTimestamp`, carries explicit edit metadata or a marker, applies maintainer-approved transcript/dedupe behavior, suppresses non-mentioned group edit replies, and adds focused Signal tests.

## Reproduction Assessment

Yes, at source level. A receive payload with `envelope.editMessage.dataMessage` follows the normal Signal inbound path while `targetSentTimestamp` is neither typed nor used for message identity.

## Solution Assessment

Unclear as a final design. A plugin-local Signal edit path is the right boundary, but transcript replacement, dedupe, and reply-trigger semantics need maintainer choice before implementation.

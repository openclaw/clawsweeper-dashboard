## Label Justifications

- `P2`: Signal edits can duplicate context and trigger unwanted replies, but the affected scope is one channel workflow and the remaining behavior needs product semantics before repair.
- `impact:message-loss`: Corrected Signal content is detached from the original target timestamp, so the intended edit relationship can be lost or duplicated in message handling.
- `impact:session-state`: Edited Signal content currently enters session context as a separate ordinary message rather than updating or marking original message state.

## Summary

Keep open. Current main and v2026.6.11 still flatten Signal `editMessage` envelopes into the ordinary inbound path, do not type or use `editMessage.targetSentTimestamp`, and the remaining transcript, dedupe, and reply-trigger semantics need maintainer direction.

## What This Changes

The issue requests Signal-specific handling for `editMessage` envelopes so edited messages keep their original-message relationship, update or mark context, and avoid duplicate responses.

## Best Possible Solution

Adopt a documented Signal-owned edit policy that types `targetSentTimestamp`, carries edit metadata into context, applies the chosen transcript or dedupe behavior, suppresses non-mentioned group edit replies, and adds focused Signal tests.

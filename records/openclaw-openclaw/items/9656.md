## Label Justifications

- `P2`: Signal edits can duplicate context and trigger unwanted replies, but the affected scope is one channel workflow and the remaining work needs product semantics before repair.
- `impact:message-loss`: Corrected Signal content is detached from the original target timestamp, so the intended edit relationship can be lost or duplicated in message handling.
- `impact:session-state`: Edited Signal content currently enters session context as a separate ordinary message rather than updating or marking original message state.

## Summary

Keep open. Current main still flattens Signal `editMessage.dataMessage` into ordinary inbound handling, does not type or use `editMessage.targetSentTimestamp`, and the only direct Signal edit PR is closed unmerged.

## What This Changes

The issue requests Signal plugin handling for signal-cli `editMessage` envelopes, including target timestamp linkage, edited markers or transcript updates, and mention-gated reply behavior.

## Best Possible Solution

Define a Signal-owned edit contract, then type `targetSentTimestamp`, carry edit metadata into context, apply the chosen transcript/dedupe behavior, suppress non-mentioned group edit replies, and add focused Signal tests.

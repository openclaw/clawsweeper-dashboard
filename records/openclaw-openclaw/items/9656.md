## Summary

Keep open. Current main still flattens Signal `editMessage.dataMessage` into the ordinary inbound path, does not model or use `editMessage.targetSentTimestamp`, and the direct Signal edit PR was closed unmerged; the remaining transcript/dedupe/reply semantics need maintainer direction.

## What This Changes

The issue requests Signal-specific handling for signal-cli `editMessage` envelopes so edited messages do not create duplicate or outdated session context or automatic replies.

## Best Possible Solution

Implement a Signal-owned edit path that models `targetSentTimestamp`, carries explicit edit metadata into context, applies a maintainer-approved transcript/dedupe policy, suppresses non-mentioned group edit replies, and adds focused Signal tests.

## Label Justifications

- `P2`: Signal edits can produce stale duplicate context and unintended responses, but the blast radius is limited to edit events in one optional channel.
- `impact:message-loss`: Corrected Signal content can be duplicated or mis-associated with outdated original text, causing the agent to act on the wrong version.
- `impact:session-state`: The session currently has no authoritative relationship between an original Signal turn and its edited replacement.

## Summary

Keep this issue open. Current main has partial Signal reply-target support, but edit envelopes still enter the ordinary inbound path with a new message identity and no defined supersession, edit marker, deduplication, or response-trigger policy. The closed unmerged candidate PR is useful prior art, while the broader cross-channel cancellation issue does not replace this Signal-specific work.

## What This Changes

Handle Signal `editMessage` envelopes as edits linked to the original message, preventing stale duplicate context and unintended duplicate responses.

## Best Possible Solution

Represent the Signal edit explicitly with its target identity, retain an auditable correction event, project only the corrected content as authoritative context, and apply a documented mention-gated policy for starting a new response.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When Signal delivers an edit, should OpenClaw supersede the original turn in future context, append both versions as linked turns, or update context without immediately starting another agent run?

Rationale: Signal supplies enough metadata to detect edits, but OpenClaw has no established contract for mutating prior inbound turns or deciding whether an edit should retrigger an active conversation.

Likely owner: steipete

Owner reason: The strongest available history connects this contributor to the Signal inbound and dispatch paths where these semantics must be chosen.

Owner confidence: high

Options:

- **Supersede in context (recommended):** Keep an auditable edit event but treat the corrected content as authoritative in future context and require an explicit mention before a group edit starts another run.
- **Append linked edit:** Keep both versions as distinct turns with structured edit metadata and an `[edited]` presentation marker.
- **Context-only correction:** Update future context from the edit but never dispatch an immediate agent response from an edit event.

Yes at source level: `editMessage.dataMessage` enters ordinary Signal ingestion while queued identity and dispatch still follow the new envelope timestamp. A live Signal scenario was not run.

Not yet. A marker-only or dedupe-only patch is incomplete; the maintainable solution needs explicit correction, context-authority, and response-trigger semantics before implementation.

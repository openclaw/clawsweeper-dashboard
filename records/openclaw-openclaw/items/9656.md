## Label Justifications

- `P2`: Signal edits can duplicate context and trigger unwanted replies, but the affected scope is one bundled channel workflow and needs product semantics before repair.
- `impact:session-state`: Edited Signal content can enter transcript context as a separate event rather than updating or marking the original message state.
- `impact:message-loss`: The corrected Signal content is not linked to the original target timestamp, so the intended edit relationship can be lost or duplicated.

## Summary

Keep open. Current main and the latest release still flatten Signal `editMessage.dataMessage` into ordinary inbound Signal messages, do not type or use `editMessage.targetSentTimestamp`, and the direct Signal edit PR is closed unmerged.

## What This Changes

The issue asks OpenClaw to recognize Signal `editMessage` envelopes, preserve the original target timestamp relationship, avoid duplicate context, and suppress edit-triggered replies unless explicitly mentioned.

## Best Possible Solution

Implement a Signal-owned edit path that models `targetSentTimestamp`, carries explicit edit metadata into context, applies a maintainer-approved transcript/dedupe policy, suppresses non-mentioned group edit replies, and adds focused Signal tests.

## Reproduction Assessment

Yes, at source level. A Signal receive payload with `envelope.editMessage.dataMessage` follows the normal inbound path while `targetSentTimestamp` is neither typed nor used for message identity.

## Solution Assessment

Partly. A plugin-local Signal edit path is the right boundary, but transcript replacement, dedupe, and reply-trigger semantics need maintainer choice before implementation.

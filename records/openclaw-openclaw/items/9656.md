## Label Justifications

- `P2`: Edited Signal messages can duplicate context and trigger unwanted replies, but the impact is bounded to one bundled channel workflow and needs a product decision before repair.
- `impact:session-state`: Original and edited Signal versions can both enter conversation context, causing transcript and agent-state drift.
- `impact:message-loss`: Corrected Signal content is not linked to the original message and can be misrepresented or duplicated as a separate inbound event.

## Summary

Keep open. Current main and the latest release still flatten Signal `editMessage.dataMessage` into the ordinary inbound path, do not model or use `editMessage.targetSentTimestamp`, and the direct Signal fix attempt at https://github.com/openclaw/openclaw/pull/9701 is closed unmerged while https://github.com/openclaw/openclaw/issues/55691 is only a broader partial overlap.

## What This Changes

The issue requests Signal plugin handling for signal-cli `editMessage` envelopes so edits keep their relationship to the original message instead of creating duplicate or stale context and replies.

## Best Possible Solution

Implement a Signal-owned edit path that models `targetSentTimestamp`, carries explicit edit metadata or a marker into context, updates or dedupes transcript state by maintainer-approved policy, suppresses non-mentioned group edit replies, and adds focused Signal tests.

## Reproduction Assessment

Yes, at source level. A Signal receive payload with `envelope.editMessage.dataMessage` follows the normal inbound path while `targetSentTimestamp` is neither typed nor used for message identity.

## Solution Assessment

Unclear as a final design. A plugin-local Signal edit path is the right boundary, but transcript replacement, dedupe, and reply-trigger semantics need maintainer choice before implementation.

## Label Justifications

- `P2`: Edited Signal messages can duplicate context and trigger unwanted replies, but the impact is bounded to one channel and the remaining behavior needs a product decision.
- `impact:session-state`: Original and edited Signal messages can both enter conversation context, causing transcript and agent-state drift.
- `impact:message-loss`: Corrected Signal content is not linked to the original message and may be represented as a separate inbound event rather than the current version.

## Summary

Keep open. Current main and the latest release still flatten Signal `editMessage.dataMessage` into the normal inbound message path, do not model `editMessage.targetSentTimestamp`, and the direct Signal fix PR is closed unmerged while the broader lifecycle issue only partially overlaps.

## What This Changes

Request Signal plugin support for signal-cli `editMessage` envelopes by preserving the original target timestamp relationship, marking or replacing edited content, and avoiding duplicate replies.

## Best Possible Solution

Implement a Signal-owned edit path that models `targetSentTimestamp`, carries explicit edit metadata into context, applies a maintainer-approved transcript/dedupe policy, suppresses non-mentioned group edit replies, and adds focused Signal tests.

## Reproduction Assessment

Yes, at source level. A Signal receive payload with `envelope.editMessage.dataMessage` follows the normal inbound path while `targetSentTimestamp` is neither typed nor used for message identity.

## Solution Assessment

Unclear as a final design. A plugin-local Signal edit path is the right boundary, but transcript replacement, dedupe, and reply-trigger semantics need maintainer choice before implementation.

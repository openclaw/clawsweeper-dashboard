## Label Justifications

- `P2`: Edited Signal messages can duplicate context and trigger unwanted replies, but the impact is bounded to one bundled channel workflow and needs product semantics before repair.
- `impact:session-state`: Original and edited Signal messages can both enter conversation context, causing transcript and agent-state drift.
- `impact:message-loss`: Corrected Signal content is not linked to the original message and can be represented as a separate inbound event.

## Summary

Keep open. Current main still treats Signal `editMessage.dataMessage` as ordinary inbound content, does not model or use `editMessage.targetSentTimestamp`, and the direct Signal fix PR is closed unmerged while the broader lifecycle issue only partially overlaps.

## What This Changes

The issue requests Signal `editMessage` envelope handling so edited messages preserve their original timestamp relationship, avoid duplicate context, and avoid unwanted duplicate replies.

## Best Possible Solution

Implement a Signal-owned edit path that models `targetSentTimestamp`, carries explicit edit metadata into context, applies a maintainer-approved transcript/dedupe policy, suppresses non-mentioned group edit replies, and adds focused Signal tests.

## Reproduction Assessment

Yes, at source level. A Signal receive payload with `envelope.editMessage.dataMessage` follows the normal inbound path while `targetSentTimestamp` is neither typed nor used for message identity.

## Solution Assessment

Partly. A plugin-local Signal edit path is the right boundary, but transcript replacement, dedupe, and reply-trigger semantics need maintainer choice before implementation.

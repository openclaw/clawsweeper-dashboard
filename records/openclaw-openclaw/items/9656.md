## Label Justifications

- `P2`: Signal edits can duplicate context and trigger unwanted replies, but the affected scope is one channel workflow and the remaining work needs product semantics before repair.
- `impact:message-loss`: Corrected Signal content is detached from the original target timestamp, so the intended edit relationship can be lost or duplicated in message handling.
- `impact:session-state`: Edited Signal content currently enters session context as a separate ordinary message rather than updating or marking original message state.

## Summary

Keep open. Current main and the latest release still flatten Signal `editMessage.dataMessage` into the ordinary inbound path, omit `editMessage.targetSentTimestamp` from the typed envelope, and leave transcript/dedupe/reply-trigger policy undecided.

## What This Changes

The issue asks the Signal plugin to detect Signal `editMessage` envelopes, preserve the original target timestamp relationship, mark or replace edited content, and avoid duplicate replies for non-mentioned edits.

## Best Possible Solution

Adopt a documented Signal-owned edit policy that types `targetSentTimestamp`, carries edit metadata into context, applies the chosen transcript or dedupe behavior, suppresses non-mentioned group edit replies, and adds focused Signal tests.

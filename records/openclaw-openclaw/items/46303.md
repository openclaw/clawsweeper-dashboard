## Best Possible Solution

Keep the useful restart-drain direction, but make the drain bypass core-private, make drain waiting mirror the followup queue pending predicate including overflow summaries, rebase/repair the dirty branch, and require exact-head real behavior proof before merge.

Full review comments:

- **[P1] Count summary overflow before declaring followups drained:** `src/auto-reply/reply/queue/drain-all.ts:21`
  - body: `waitForFollowupQueueDrain()` only counts queued items plus a draining sentinel, but the real drain loop keeps running while `droppedCount > 0`. A capped queue can retain summary-only followup work with no `items`, so SIGUSR1 can report drained and continue shutdown before that overflow summary is delivered.
  - confidence: 0.9
- **[P1] Keep the gateway-drain bypass out of the public SDK:** `src/plugin-sdk/channel-lifecycle.core.ts:33-36`
  - body: Adding `enqueueInternal` to exported `ChannelRunQueue` makes the restart-drain escape hatch visible to plugin authors, and that method bypasses the normal `isGatewayDraining()` admission gate. Keep this capability core-private or behind an unexported runtime token so it does not become a permanent plugin API/security boundary.
  - confidence: 0.87

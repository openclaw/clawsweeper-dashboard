## Summary

The issue remains necessary: current main accepts a launchd Node Gateway only when its `dist/index.js` path contains an exact `openclaw` component, so a valid renamed checkout reaches the destructive local sweep as an unexpected listener. The existing LaunchAgent status path exposes an exact runtime PID, making this a narrow lifecycle fix rather than a reason to broaden the path allowlist. The issue is actively assigned and protected by the `maintainer` label, so it should remain open for explicit maintainer handling.

Likely related people:
- @steipete — high confidence; current assignee and long-running owner of the macOS PortGuardian/app-launch path.
- @vincentkoc — high confidence; authored the recent matcher change in https://github.com/openclaw/openclaw/pull/100867.

## What This Changes

Prevent the macOS app from terminating the exact launchd-owned Gateway listener when its source checkout directory is renamed.

## Best Possible Solution

Resolve the loaded LaunchAgent's runtime PID once before each local PortGuardian sweep, preserve it only when that PID currently owns the configured listener, and retain the existing conservative command matcher as the fallback for missing, malformed, stale, or non-listening status.

## Reproduction Assessment

Yes at source level: the reported renamed-checkout command deterministically fails the exact-directory matcher and reaches the local termination branch. The issue also provides a repeated signed-app and launchd timeline, but this read-only review did not independently execute the macOS scenario.

## Solution Assessment

Yes, with an ownership check: using the loaded LaunchAgent's exact listening PID is narrower and safer than allowing arbitrary `openclaw-*` directory names. The implementation should fall back to current matching when status cannot prove live listener ownership.

## Summary

Keep open: current main still lacks default CLI guided live verification and masked manual-key onboarding, and the protected maintainer label makes the default-onboarding UX a maintainer product decision.

## What This Changes

Requests a default guided CLI onboarding flow that live-tests detected AI access before persistence, falls through candidates on failure, supports masked manual API-key verification, and preserves classic/non-interactive contracts.

## Best Possible Solution

Ship a maintainer-approved deterministic CLI guided verifier around detectSetupInference/activateSetupInference, with masked manual-key entry, candidate fall-through, explicit classic/Crestodian/skip escape hatches, and updated CLI docs/tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should default interactive CLI onboarding switch from chat-first setup to a deterministic guided verifier that reuses detectSetupInference/activateSetupInference, while preserving classic and non-interactive contracts?

Rationale: The verified engine exists, but changing the default first-run CLI UX and fallback ladder is a product/API compatibility choice, and the live issue has the protected maintainer label.

Likely owner: steipete

Owner reason: They authored the current onboarding surfaces and the verified setup engine this issue proposes reusing for CLI.

Owner confidence: high

Options:

- **Adopt guided verifier as CLI default (recommended):** Use the structured setup inference engine for default interactive CLI onboarding and keep Crestodian chat, classic wizard, and skip setup as explicit escape hatches.
- **Narrow to verification only:** Live-test the detected model before persistence without adding manual key entry or a new guided flow.
- **Keep chat-first onboarding:** Leave the current conversational setup default and accept that first live model failure happens after setup unless a separate recovery path is added.

## Reproduction Assessment

Yes, source inspection shows default CLI onboarding reaches conversational Crestodian setup, which selects a detected backend and applies setup without the activateSetupInference live-completion path. A live stale-credential run would require real provider/auth state and was not run in this read-only review.

## Solution Assessment

Yes directionally, but maintainer intent is needed for the default UX. Reusing the existing setup-inference engine is the maintainable boundary; the open choice is how much guided CLI flow to make default.

## Label Justifications

- `P1`: The issue reports a real Signal restart race that can break channel delivery and leave orphaned daemon processes during routine config-triggered restarts.
- `impact:message-loss`: The reported failure mode includes Signal send failures after restart races against the old daemon listener or config lock.
- `impact:crash-loop`: The issue concerns process-level availability: orphaned signal-cli daemons, held ports/config locks, and failed restarts.

## Summary

Keep open: current main and the latest release still have synchronous Signal daemon shutdown, and the open linked PR is the active unmerged fix candidate for the reported restart race.

## What This Changes

The issue requests fixing Signal daemon restart shutdown so OpenClaw waits for signal-cli to exit, escalates if needed, and avoids orphaned processes and send failures.

## Best Possible Solution

Review and land the focused Signal lifecycle fix in https://github.com/openclaw/openclaw/pull/71863, or an equivalent Signal-owned patch that awaits daemon exit, escalates after a bounded timeout, and keeps monitor teardown pending until shutdown completes.

## Reproduction Assessment

Yes. Current main source shows Signal daemon stop sends SIGTERM without awaiting child exit, while Signal config hot reload can stop and restart the channel; I did not run a live linked Signal restart.

## Solution Assessment

Yes. The best fix belongs in the Signal daemon lifecycle and monitor cleanup rather than a gateway delay or broad child-process rewrite; the linked PR is the active focused implementation candidate.

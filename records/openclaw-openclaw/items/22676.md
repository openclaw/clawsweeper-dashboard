## Label Justifications

- `P1`: The issue reports a real Signal restart race that can break channel delivery and leave orphaned daemon processes during routine config-triggered restarts.
- `impact:message-loss`: The reported failure mode includes Signal send failures after restart races against the old daemon listener or config lock.

## Summary

Current `main` and the latest release still have synchronous SIGTERM-only Signal daemon shutdown, and the open linked PR is the active closing candidate, so this issue should stay open.

## What This Changes

The issue reports that Signal channel hot-restart can orphan `signal-cli` because daemon stop sends SIGTERM without waiting for process exit before restart.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/71863, or an equivalent focused Signal-owned lifecycle fix that awaits daemon exit after SIGTERM, escalates after a bounded timeout, and awaits monitor shutdown before restart.

## Reproduction Assessment

Yes. The current main source shows Signal daemon stop sends SIGTERM without awaiting child exit, while Signal config hot reload can stop and restart the channel; I did not run a live linked Signal restart.

## Solution Assessment

Yes. The best fix belongs in the Signal daemon lifecycle and monitor cleanup, not in a gateway delay or broad child-process rewrite; the linked PR is the active focused implementation candidate.

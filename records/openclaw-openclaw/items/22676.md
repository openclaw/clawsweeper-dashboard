## Label Justifications

- `P1`: The bug can break an active Signal channel workflow after config/SIGUSR1 restart by leaving old signal-cli processes holding the port or config lock.
- `impact:message-loss`: The reported stale/orphaned daemon state produces Signal send failures after restart.
- `impact:crash-loop`: The issue concerns process lifecycle availability: orphaned signal-cli processes and restart races can leave the channel unable to recover without manual process cleanup.

## Summary

Keep open: current main and v2026.6.11 still use fire-and-forget Signal daemon shutdown, and the focused closing fix at https://github.com/openclaw/openclaw/pull/71863 remains open and unmerged.

## What This Changes

Make Signal daemon restart shutdown wait for signal-cli process exit and escalate after a bounded timeout so hot reloads do not leave orphaned daemons or stale send targets.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/71863 or an equivalent Signal-owned lifecycle fix that awaits daemon exit after SIGTERM, escalates after a bounded timeout, and keeps monitor teardown open until cleanup finishes.

Yes. Source-level reproduction is high confidence: current main still sends SIGTERM from Signal daemon `stop()` and returns without awaiting child exit, while config hot reload stops and starts the Signal channel in sequence.

## Solution Assessment

Yes. The narrow maintainable fix belongs in the Signal daemon/monitor lifecycle so `stopChannel` naturally waits for daemon cleanup, rather than adding a gateway-level delay or preserving fire-and-forget process shutdown.

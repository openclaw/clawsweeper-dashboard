## Label Justifications

- `P1`: The bug can break an active Signal channel workflow after config/SIGUSR1 restart by leaving old signal-cli processes holding the port or config lock.
- `impact:message-loss`: The reported stale/orphaned daemon state produces Signal send failures after restart.
- `impact:crash-loop`: The issue concerns process lifecycle availability: orphaned signal-cli processes and restart races can leave the channel unable to recover without manual cleanup.

## Summary

Keep open: current main and latest release v2026.6.11 still use fire-and-forget Signal daemon shutdown, and the focused closing fix at https://github.com/openclaw/openclaw/pull/71863 remains open and unmerged.

## What This Changes

The issue reports that Signal daemon restart sends SIGTERM without waiting for signal-cli to exit, causing orphaned processes and send failures.

## Best Possible Solution

Keep this issue open and land https://github.com/openclaw/openclaw/pull/71863, or an equivalent Signal-owned lifecycle fix that awaits daemon exit after SIGTERM, escalates after a bounded timeout, and keeps monitor teardown open until cleanup finishes.

Yes. Source-level reproduction is high confidence: current main still sends SIGTERM from Signal daemon stop and returns without awaiting child exit, while gateway stop/start relies on the monitor task to keep cleanup open.

## Solution Assessment

Yes. The narrow maintainable fix belongs in the Signal daemon/monitor lifecycle so gateway channel stop naturally waits for daemon cleanup, rather than adding a gateway-level delay or preserving fire-and-forget process shutdown.

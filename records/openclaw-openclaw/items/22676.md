## Label Justifications

- `P1`: The issue reports a real Signal restart race that can break channel delivery and leave orphaned daemon processes during routine config-triggered restarts.
- `impact:message-loss`: The reported failure mode includes Signal send failures after restart races against the old daemon listener or config lock.
- `impact:crash-loop`: The issue concerns process-level availability through orphaned signal-cli daemons, held ports/config locks, and failed restarts.

## Summary

Keep open: current main and latest release still use synchronous Signal daemon shutdown, while https://github.com/openclaw/openclaw/pull/71863 is the open unmerged candidate that directly closes the reported restart race.

## What This Changes

The issue requests a Signal-owned fix so daemon shutdown waits for signal-cli exit, escalates after a bounded timeout, and keeps channel restart teardown from racing the old process.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/71863, or an equivalent focused Signal lifecycle fix, before closing this issue.

## Reproduction Assessment

Yes. Current main source shows Signal daemon stop sends SIGTERM without awaiting child exit, and Signal config hot reload can stop and immediately start the channel; I did not run a live linked Signal restart.

## Solution Assessment

Yes. The best fix belongs in the Signal daemon lifecycle and monitor cleanup rather than a gateway delay or broad child-process rewrite; the linked PR is the active focused implementation candidate.

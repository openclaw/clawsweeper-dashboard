## Label Justifications

- `P1`: The issue describes a real Signal channel restart failure that can break sends and require manual process cleanup.
- `impact:message-loss`: The reported daemon race can make Signal RPC sends fail after restart because the new daemon races a stale daemon still holding the port or config lock.
- `impact:crash-loop`: The failure leaves orphaned signal-cli processes and can keep the Signal channel restart path from becoming available cleanly.

## Summary

Keep open: current main and the latest release still use synchronous Signal daemon shutdown, and the focused closing fix is still open at https://github.com/openclaw/openclaw/pull/71863.

## What This Changes

The issue reports that Signal hot restart sends SIGTERM to the auto-spawned signal-cli daemon without waiting for exit, leaving orphaned processes that can break later sends.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/71863 or an equivalent Signal-owned lifecycle fix that makes daemon stop async, idempotent, bounded by SIGKILL fallback, and awaited through monitor teardown.

## Reproduction Assessment

Yes from source inspection, though I did not run a live Signal account repro in this read-only review. Current main still sends SIGTERM synchronously and lets monitor teardown finish without waiting for signal-cli exit.

## Solution Assessment

Yes. The async SIGTERM -> wait -> bounded SIGKILL repair belongs in the Signal daemon lifecycle and monitor teardown, and the existing linked PR uses that focused owner-boundary fix instead of adding gateway delay churn.

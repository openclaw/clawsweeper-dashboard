## Label Justifications

- `P1`: The bug can break an active Signal channel workflow after config/SIGUSR1 restart by leaving old signal-cli processes holding the port or config lock.
- `impact:message-loss`: The reported stale or orphaned daemon state produces Signal send failures after restart.

## Summary

Keep open: current main and v2026.6.11 still use fire-and-forget Signal daemon shutdown, and the focused closing fix at https://github.com/openclaw/openclaw/pull/71863 remains open and unmerged.

## What This Changes

The issue reports that Signal daemon shutdown returns before the signal-cli child exits, causing restart races, orphaned processes, and send failures.

## Best Possible Solution

Keep this issue open and land https://github.com/openclaw/openclaw/pull/71863 or an equivalent Signal-owned lifecycle fix that awaits daemon exit after SIGTERM, escalates after a bounded timeout, and keeps monitor teardown open until cleanup finishes.

Yes. Source-level reproduction is high confidence: current main sends SIGTERM from Signal daemon `stop()` and returns without awaiting child exit, while hot reload stops and starts the Signal channel in sequence.

## Solution Assessment

Yes. The narrow maintainable fix belongs in the Signal daemon/monitor lifecycle so `stopChannel` naturally waits for daemon cleanup, rather than adding a gateway-level delay or preserving fire-and-forget process shutdown.

## Label Justifications

- `P1`: The issue reports a real Signal restart race that can break channel delivery and leave orphaned daemon processes during routine config-triggered restarts.
- `impact:message-loss`: The reported failure mode includes Signal send failures after restart races against the old daemon listener or config lock.
- `impact:crash-loop`: The issue is about process lifecycle availability: orphaned `signal-cli` daemons, held ports/config locks, and failed restarts.

## Summary

Keep open. Current main and the latest release still have synchronous SIGTERM-only Signal daemon shutdown, and the linked closing PR is open rather than merged.

## What This Changes

The issue requests fixing Signal daemon shutdown during gateway SIGUSR1/config restarts so old signal-cli processes exit before a new daemon starts.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/71863, or an equivalent focused Signal-owned lifecycle fix that awaits daemon exit after SIGTERM, escalates after a bounded timeout, and awaits monitor shutdown before restart.

## Reproduction Assessment

Yes, at source level. Current main still sends SIGTERM without awaiting child exit, while Signal config reload can stop and restart the channel; I did not run a live linked Signal restart.

## Solution Assessment

Yes. The best fix belongs in the Signal daemon lifecycle and monitor cleanup rather than a gateway delay or broad child-process rewrite, and the open linked PR is the active focused implementation candidate.

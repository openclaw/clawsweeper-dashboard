## Label Justifications

- `P1`: The issue reports a real Signal restart race that can break channel delivery and leave orphaned daemon processes during routine config-triggered restarts.
- `impact:message-loss`: The reported failure mode includes Signal send failures after restart races against the old daemon listener or config lock.
- `impact:crash-loop`: The issue concerns process-level availability: orphaned signal-cli daemons, held ports/config locks, and failed restarts.

## Summary

Keep open: current main and the latest release still have the synchronous SIGTERM-only Signal daemon shutdown, and https://github.com/openclaw/openclaw/pull/71863 is the open unmerged fix candidate with closing syntax for this issue.

## What This Changes

The issue reports that Signal daemon restarts send SIGTERM without awaiting child process exit, causing orphaned signal-cli processes and failed sends during hot reload.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/71863, or an equivalent focused Signal-owned lifecycle fix that awaits daemon exit after SIGTERM, escalates after a bounded timeout, and awaits monitor cleanup before restart.

## Reproduction Assessment

Yes. Current main source shows Signal daemon stop sends SIGTERM without awaiting child exit, while Signal config hot reload can stop and restart the channel; I did not run a live linked Signal restart.

## Solution Assessment

Yes. The best fix belongs in the Signal daemon lifecycle and monitor cleanup, not in a gateway delay or broad child-process rewrite; the linked PR is the active focused implementation candidate.

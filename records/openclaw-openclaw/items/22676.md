## Label Justifications

- `P1`: The issue describes a user-facing Signal restart regression that can break sends and require manual process cleanup.
- `impact:message-loss`: The race can make Signal RPC sends fail after restart because a new daemon can race the stale daemon.
- `impact:crash-loop`: The failure leaves orphaned signal-cli processes and affects channel process availability during restart.

## Summary

Keep open: current main and v2026.6.11 still use synchronous Signal daemon shutdown, and the focused closing fix remains open at https://github.com/openclaw/openclaw/pull/71863.

## What This Changes

The issue reports that Signal auto-start daemon shutdown returns immediately during SIGUSR1/config reload, leaving old signal-cli processes to race new starts and break sends.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/71863, or an equivalent Signal-owned fix that makes daemon stop async, idempotent, bounded by SIGKILL fallback, and awaited through monitor teardown.

## Solution Assessment

Yes. The async SIGTERM -> wait -> bounded SIGKILL repair, awaited through monitor teardown, is the narrow owner-boundary fix; the existing open PR is the best path rather than queueing duplicate issue work.

## Label Justifications

- `P1`: The issue reports a real channel restart regression that can orphan `signal-cli` processes and break Signal sends for affected users.
- `impact:message-loss`: The reported race can cause Signal RPC send failures after hot-reload restarts.

## Summary

Current `main` still leaves the Signal daemon shutdown path synchronous, and an open linked PR is already the active closing implementation candidate, so this issue should remain open until that PR or an equivalent fix lands.

## What This Changes

The issue requests a Signal daemon restart fix so `signal-cli` shutdown is awaited before hot-reload starts a replacement process.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/71863 or an equivalent focused Signal fix that makes daemon shutdown async, idempotent, bounded, and awaited through monitor teardown before restart.

## Reproduction Assessment

Yes for source reproduction: current `main` still sends SIGTERM in `SignalDaemonHandle.stop` without awaiting child exit, while hot-reload stop/start can restart the channel immediately after monitor cleanup. I did not run a live Signal daemon reproduction in this read-only review.

## Solution Assessment

Yes, the best fix is the linked focused Signal lifecycle repair: make daemon stop return and reuse a promise, wait for process exit after SIGTERM, escalate to SIGKILL after a bounded timeout, and await it from monitor shutdown.

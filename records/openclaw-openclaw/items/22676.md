## Label Justifications

- `P1`: The issue reports a real Signal restart race that can break channel delivery and leave orphaned daemon processes during routine config-triggered restarts.
- `impact:message-loss`: The reported failure mode includes Signal send failures after restart races against the old daemon listener or config lock.
- `impact:crash-loop`: The issue is about process lifecycle availability: orphaned signal-cli daemons, held ports/config locks, and failed restarts.

## Summary

Keep open: current main and the latest release still use synchronous SIGTERM-only Signal daemon shutdown, and the open linked PR is the focused closing candidate for the reported restart race.

## What This Changes

The issue asks OpenClaw to await Signal daemon shutdown, with bounded SIGKILL escalation, before restarting the Signal channel during SIGUSR1/config hot reloads.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/71863, or an equivalent focused Signal lifecycle fix that awaits daemon exit after SIGTERM, escalates after a bounded timeout, and awaits monitor shutdown before restart.

## Reproduction Assessment

Yes. Current main shows Signal daemon stop sends SIGTERM without awaiting child exit, while Signal config hot reload can stop and immediately restart the channel; I did not run a live linked Signal restart.

## Solution Assessment

Yes. The best fix belongs in the Signal daemon lifecycle and monitor cleanup rather than a gateway sleep or broad child-process rewrite, and the linked PR is the active focused implementation candidate.

## Label Justifications

- `P1`: The bug affects a real channel restart workflow and can leave Signal unable to send messages until manual process cleanup or a full restart.
- `impact:message-loss`: The reported race causes Signal RPC send failures when the new daemon races an old listener or config lock.

## Summary

Keep open: current main and the latest release still use synchronous Signal daemon shutdown, while a focused open closing PR already owns the fix path.

## What This Changes

The issue requests making Signal daemon shutdown wait for signal-cli exit, with bounded SIGKILL escalation, before restart paths start a new daemon.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/71863, or an equivalent Signal-owned fix that makes daemon stop async/idempotent, waits for exit after SIGTERM, escalates after a bounded timeout, and awaits that cleanup before restart.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, by source inspection: Signal hot reload can await gateway stop/start while Signal monitor cleanup only sends SIGTERM and returns before signal-cli exits. I did not run a live Signal daemon repro in this read-only review.

## Solution Assessment

Yes, the linked PR shape is the narrow maintainable fix: put the wait/escalation in the Signal daemon lifecycle and await it from monitor teardown, rather than adding a gateway-level delay or a duplicate restart workaround.

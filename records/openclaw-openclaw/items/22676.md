## Label Justifications

- `P1`: The issue reports a real Signal restart race that can break channel delivery and leave orphaned daemon processes during routine config-triggered restarts.
- `impact:message-loss`: The reported failure mode includes Signal send failures when a new daemon races the old listener or config lock.
- `impact:crash-loop`: The issue concerns process-level availability through orphaned signal-cli daemons, held ports/config locks, and failed restarts.

## Summary

Keep open: current main and latest release still use synchronous Signal daemon shutdown, and https://github.com/openclaw/openclaw/pull/71863 is the open unmerged fix candidate that directly closes the reported restart race.

## What This Changes

The issue asks for Signal daemon shutdown to await signal-cli exit with bounded SIGKILL escalation so SIGUSR1/config reload restarts do not orphan old daemons or fail sends.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/71863, or an equivalent focused Signal lifecycle fix, before closing this issue.

## Reproduction Assessment

Yes. Current main source shows Signal daemon stop sends SIGTERM without awaiting child exit, while Signal config reload can stop and immediately start the channel; I did not run a live linked Signal restart.

## Solution Assessment

Yes. The best fix belongs in the Signal daemon lifecycle and monitor cleanup rather than a gateway delay or broad child-process sweep; the linked PR is the active focused implementation candidate.

## Label Justifications

- `P1`: The issue reports a routine Signal restart race that can leave the channel unusable with orphaned daemon processes and failed sends.
- `impact:message-loss`: The reported failure mode includes Signal send failures when restart races against the old daemon listener or config lock.
- `impact:crash-loop`: The issue concerns process-level availability: orphaned signal-cli daemons, held ports/config locks, and failed restart recovery.

## Summary

Keep open: current main and the latest release still use synchronous SIGTERM-only Signal daemon shutdown, and https://github.com/openclaw/openclaw/pull/71863 is the active open fix candidate for the reported restart race.

## What This Changes

The issue reports that Signal daemon shutdown during config-triggered gateway restart returns before signal-cli exits, leaving orphaned processes and causing Signal send failures.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/71863, or land an equivalent focused Signal-owned lifecycle fix that awaits daemon exit after SIGTERM, escalates after a bounded timeout, and keeps monitor cleanup open before restart.

## Reproduction Assessment

Yes from source inspection: current main still sends SIGTERM without awaiting child exit, while Signal config reload can stop and then restart the channel. I did not run a live linked Signal account restart in this read-only review.

## Solution Assessment

Yes. The narrow maintainable fix belongs in the Signal daemon lifecycle and monitor cleanup rather than a gateway delay or broad child-process rewrite, and the linked PR is already the focused implementation candidate.

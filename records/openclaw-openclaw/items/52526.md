## Summary

Keep open. Current main and v2026.6.11 still build CLI JSON payloads from raw CLI output after transcript persistence applies `before_message_write`, and the stale related PR was closed in favor of this issue.

## What This Changes

The issue asks for `agent --json` payloads to reflect the finalized assistant message after `before_message_write` hooks rather than raw pre-hook CLI output.

## Best Possible Solution

Make the current CLI JSON result path consume the same finalized assistant message accepted by the transcript write-hook path, with explicit non-leaking behavior for hook-blocked replies.

## Maintainer Decision

Question: When `before_message_write` rewrites or blocks a CLI assistant message, what should `agent --json` expose to callers?

Rationale: The source-level mismatch is clear, but changing blocked-hook output affects a public machine-readable result surface and a plugin-enforced safety boundary.

Likely owner: steipete

Owner confidence: high

Options:

- **Return finalized or suppressed output (recommended):** Use the post-hook assistant text for rewrites and return a structured suppressed/blocked result without raw text when the hook blocks persistence.
- **Thread hook output only for rewrites:** Fix rewritten-message mismatches first while requiring a separate maintainer decision for blocked-message JSON shape.
- **Document persistence-only semantics:** Leave `before_message_write` as transcript-only and explicitly document that `agent --json` may expose raw CLI output, accepting the security tradeoff.

Yes, at source level: current main persists through `beforeMessageWrite` and then returns payloads from raw `output.text`, and a current test preserves the blocked-hook mismatch. I did not run a live plugin/CLI reproduction in this read-only review.

Unclear until maintainers choose blocked-hook JSON semantics. The best implementation should target current `src/agents/cli-runner.ts` and the transcript append seam, not the closed stale `pi-embedded-runner` PR path.

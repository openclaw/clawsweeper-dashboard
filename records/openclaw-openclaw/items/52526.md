## Summary

Keep open. Current main and the latest release still apply `before_message_write` only on the transcript append path while `agent --json` builds returned payloads from raw CLI output, so the JSON/transcript mismatch remains; the linked PR targets removed pi-runner files and is not a viable fix for current main.

## What This Changes

The issue asks for `agent --json` to return the same finalized assistant message produced by `before_message_write` hooks and persisted to the session transcript.

## Best Possible Solution

Make the current CLI JSON result path consume the same finalized assistant message accepted by the transcript write-hook path, with explicit non-leaking behavior for hook-blocked replies.

Owner confidence: medium

Options:

- **Suppress blocked assistant payload (recommended):** Treat a blocked `before_message_write` result as suppressing the JSON assistant payload too, with optional non-sensitive metadata explaining the hook block.
- **Return a safe placeholder:** Return a fixed non-sensitive placeholder payload so callers receive a terminal result without seeing blocked content.
- **Keep raw JSON output:** Preserve the current raw-payload behavior and accept that `before_message_write` does not protect the CLI JSON surface.

## Reproduction Assessment

Yes, at source level: current `persistCliAssistantTranscript` applies `beforeMessageWrite`, while `buildCliRunResult` builds returned `payloads` from `output.text`. A current reliability test also locks in the blocked mismatch by expecting raw CLI output while the transcript remains empty.

## Solution Assessment

Unclear until maintainers choose blocked-hook JSON semantics. The best implementation should update `src/agents/cli-runner.ts` and the transcript append return contract rather than revive the stale pi-runner PR path.

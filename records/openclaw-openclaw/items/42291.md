## Label Justifications

- `P1`: The report describes a broken auth-provider workflow where gateway model calls can keep using stale credentials after a node-host login consumes or stores OAuth credentials locally.
- `impact:data-loss`: The wrong-host write can make the refreshed OAuth credential unusable for the gateway and leave the prior gateway credential stale.
- `impact:security`: The issue concerns where OAuth credentials and refresh tokens are stored and consumed across host boundaries.
- `impact:auth-provider`: The affected path is provider authentication and auth-profile routing for model execution.
- `maturity:stable`: The issue affects CLI auth/setup and gateway/node credential behavior under M4 Stable CLI and gateway surfaces in the maturity scorecard.

## Summary

Keep open: current main and the latest release still let `models auth login` persist provider auth profiles through the local agent directory, while node-host config can point at a remote gateway where model execution actually happens.

## What This Changes

The issue asks OpenClaw to prevent or correctly route OAuth credentials when `openclaw models auth login` is run from a node host connected to a remote gateway.

## Best Possible Solution

Land a focused auth-login fix that detects remote node-host configs with shared gateway loopback semantics and either blocks before provider auth runs or forwards credentials through an explicitly approved gateway-side path.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should remote node-host `models auth login` fail closed with an instruction to run on the gateway host, or should OpenClaw add a gateway credential-forwarding flow?

Rationale: Both options prevent the wrong-host credential write, but forwarding OAuth credentials changes a security-sensitive gateway/auth surface while fail-closed changes existing CLI behavior for remote-node users.

Likely owner: vincentkoc

Owner reason: He has the strongest current history and linked follow-up context for the auth-login/node-host boundary.

Owner confidence: high

Options:

- **Fail closed before auth (recommended):** Block remote node-host auth login before starting provider auth, reuse shared loopback checks, and tell the user to run the command on the gateway host.
- **Design credential forwarding:** Add an explicit gateway RPC or setup flow for credential transfer, with security review and upgrade proof before implementation.
- **Warn but allow:** Emit a warning and still allow local writes, accepting that users can still consume OAuth credentials on the wrong host.

## Reproduction Assessment

Yes, source-reproducible: current main persists returned provider auth profiles to the local `agentDir`, while node-host config can target a remote gateway. I did not run a live remote gateway OAuth flow in this read-only review.

## Solution Assessment

Unclear until maintainer intent is set. A fail-closed guard is the narrowest safe mitigation, while gateway credential forwarding is broader and security-sensitive.

## Label Justifications

- `P1`: The issue describes a real remote-gateway auth-provider workflow where OAuth refresh-token material can be consumed locally and leave model calls failing.
- `impact:data-loss`: Provider OAuth refresh credentials can be consumed into the wrong local store, making the intended gateway credential unrecoverable.
- `impact:security`: Sensitive provider credential material can cross the wrong node/gateway trust boundary without a clear user decision.
- `impact:auth-provider`: The failure directly affects provider OAuth state, model auth routing, and recovery from refresh-token reuse errors.
- `maturity:stable`: The issue affects the Gateway/node remote boundary, and `gateway-runtime` is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and the latest release still persist `models auth login` profiles through the local agent auth store, while node-host config can point at a remote gateway and the only linked implementation candidates are closed or an unmergeable fork PR.

## What This Changes

The issue asks `openclaw models auth login` on remote node hosts to avoid silently writing OAuth credentials to the node-local auth store instead of the gateway-owned store.

## Best Possible Solution

Land a focused pre-auth remote-node guard, or an explicitly approved gateway-forwarding design, that prevents wrong-host credential writes before any OAuth refresh material is consumed and covers remote-block plus loopback-allow cases.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should remote node-host `openclaw models auth login` fail closed before provider auth starts, or should OpenClaw support gateway-side credential forwarding for this flow?

Rationale: Both options change a provider credential boundary, and automation should not decide whether node hosts may acquire and transfer gateway-owned OAuth material without maintainer intent.

Likely owner: vincentkoc

Owner reason: Vincent already authored the maintainer repair direction and recently touched the auth/node-host implementation paths.

Owner confidence: high

Options:

- **Fail closed before auth starts (recommended):** Block non-loopback remote node-host auth login with a clear instruction to run the command on the gateway host while preserving loopback and tunnel setups.
- **Design credential forwarding:** Add an authenticated gateway-owned flow for moving provider auth material to the gateway store without consuming or persisting it on the node first.
- **Warn but permit:** Keep the current local-write behavior with a warning, accepting the wrong-host credential risk for compatibility.

## Reproduction Assessment

Yes, at source level. Current main resolves a local `agentDir`, runs provider auth, and persists returned profiles there while node-host config can record a non-loopback gateway target.

## Solution Assessment

Unclear until maintainer intent is set. A pre-auth fail-closed guard is the narrowest safe fix if maintainers accept that behavior; transparent gateway credential forwarding needs a separate design.

## Summary

Keep open: current main and the latest release still run provider auth login against the locally resolved agent auth store, while node-host config can point at a remote gateway and no same-repo fix PR is currently viable.

## What This Changes

The issue asks OpenClaw to prevent `openclaw models auth login` on a remote node host from consuming OAuth credentials into the node-local auth store instead of the gateway-used auth store.

## Best Possible Solution

Land a focused maintainer-owned or adopted fix that blocks non-loopback node-host auth before provider auth starts, or explicitly design a secure gateway-forwarding path before allowing node hosts to acquire gateway-owned OAuth material.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should remote node-host `openclaw models auth login` fail closed before provider auth starts, or should OpenClaw support a gateway-side credential forwarding flow for this case?

Rationale: The choice determines whether a node host may acquire and transfer provider OAuth material for a gateway-owned model runtime, which is both a credential-boundary and product behavior decision.

Likely owner: vincentkoc

Owner reason: He authored the maintainer draft for this exact guard and already framed the fail-closed behavior and verification path.

Owner confidence: high

Options:

- **Fail closed before auth starts (recommended):** Block auth login when node-host config points at a non-loopback gateway and instruct the user to run the command on the gateway host; this is the narrowest safe repair.
- **Design gateway credential forwarding:** Add an authenticated gateway-side flow that stores the provider credential in the gateway auth store without first consuming it into the node-local store.
- **Warn but allow local write:** Keep local writes possible with an explicit warning, accepting that users can still consume credentials on the wrong host.

## Reproduction Assessment

Yes, source-reproducible: current main resolves a local `agentDir`, runs provider auth, and upserts profiles there while node-host config can point at a remote gateway. I did not run a live OAuth flow because this read-only review should not consume real credentials.

## Solution Assessment

Unclear until maintainer intent is set. A pre-auth fail-closed guard is the narrowest safe repair if maintainers accept it, while transparent gateway forwarding needs separate protocol and security design.

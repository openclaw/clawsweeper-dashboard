## Summary

Keep open: current main and the latest release still run `openclaw models auth login` against the local agent auth store, while node-host config can point at a non-loopback gateway and the linked fix attempts are not merged into this repository.

## What This Changes

The issue requests preventing or redirecting `openclaw models auth login` when run on a node host connected to a remote gateway so OAuth credentials do not get stored on the wrong host.

## Best Possible Solution

Land a focused pre-auth guard that detects non-loopback remote node-host gateway config before provider auth starts, blocks or clearly redirects the user before any credential write, reuses shared loopback handling, and covers remote-block plus local-loopback cases in tests.

Rationale: Both directions change a sensitive provider credential boundary, and automation should not choose whether node hosts may acquire and transfer gateway-owned OAuth material without maintainer intent.

Options:

- **Fail closed before auth starts (recommended):** Block non-loopback remote node-host auth login with an actionable gateway-host instruction and preserve local loopback/tunnel setups with shared loopback semantics.
- **Forward credentials to the gateway:** Design an authenticated gateway RPC or setup flow that moves provider auth material to the gateway store without consuming tokens locally first.
- **Warn but keep permissive:** Warn node-host users that auth will only affect the local node, accepting the current wrong-host credential risk for compatibility.

Yes. Source inspection shows current main resolves a local `agentDir`, invokes provider auth, and persists returned profiles there while node-host config can point at a non-loopback gateway.

## Solution Assessment

Unclear until maintainer intent is set. A pre-auth fail-closed guard is the narrowest safe implementation if maintainers accept that product/security behavior, while transparent gateway credential forwarding needs a separate design.

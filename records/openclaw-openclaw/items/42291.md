## Label Justifications

- `P1`: The issue describes a real remote-gateway auth workflow where OAuth refresh-token material can be consumed locally and leave model calls failing.
- `impact:data-loss`: Provider OAuth refresh credentials can be rotated or consumed into the wrong local store, making the intended gateway credential unusable.
- `impact:security`: Sensitive provider credential material can cross the wrong node/gateway trust boundary without warning.
- `impact:auth-provider`: The failure directly affects provider OAuth state, model auth routing, and recovery from refresh-token reuse errors.
- `maturity:stable`: The affected gateway/node remote boundary maps to `gateway-runtime`, which is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current `origin/main` and `v2026.6.11` still run `models auth login` through the local agent auth store with no remote node-host guard or gateway forwarding, and the same-repo fix attempts are closed unmerged while the live fork PR is conflicting and not maintainer-editable.

## What This Changes

The issue requests preventing `openclaw models auth login` on a remote node host from silently writing provider OAuth credentials into the node-local auth store instead of the gateway-owned store.

## Best Possible Solution

Approve the credential-boundary direction, then land a focused pre-auth guard or gateway-forwarding design that prevents wrong-host credential writes before any OAuth refresh token is consumed.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `openclaw models auth login` on non-loopback remote node hosts fail closed before provider auth starts, or should OpenClaw support forwarding the resulting credentials to the gateway?

Rationale: Both choices change where sensitive provider OAuth material may be acquired and persisted, so automation should not decide this credential boundary without maintainer intent.

Likely owner: vincentkoc

Owner reason: Vincent already authored the maintainer repair direction and verification for the exact remote-node auth guard.

Owner confidence: high

Options:

- **Fail closed before auth starts (recommended):** Block non-loopback remote node-host auth login with a clear instruction to run the command on the gateway host, while preserving local loopback and tunnel setups.
- **Design gateway credential forwarding:** Add an authenticated gateway-side credential transfer/session flow so node-host login can safely update the gateway-owned auth store.
- **Warn but allow local write:** Keep the existing permissive behavior with a warning, accepting that users can still consume credentials into the wrong store.

## Reproduction Assessment

Yes. Source inspection shows current main writes provider auth profiles through the local `agentDir`, while node-host config can persist a non-loopback gateway with no auth-login guard.

## Solution Assessment

Unclear until maintainer intent is set. A pre-auth fail-closed guard is the narrowest safe fix if maintainers accept that behavior, while transparent gateway credential forwarding needs a separate security design.

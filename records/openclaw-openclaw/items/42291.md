## Summary

Keep open: current main still runs provider auth login against the local agent auth store with no remote node-host preflight, and the only open closing candidate is a conflicting, non-maintainer-editable fork PR rather than an implemented fix.

## What This Changes

The issue asks OpenClaw to prevent `openclaw models auth login` on a remote node host from silently consuming OAuth credentials into the node-local auth store instead of the gateway-owned store.

## Best Possible Solution

Land a focused pre-auth guard that detects non-loopback remote node-host gateway config before provider auth starts, blocks or clearly redirects the user before any credential write, reuses shared loopback handling, and covers remote-block plus local-loopback cases in tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should remote node-host `openclaw models auth login` fail closed before provider auth starts, or should OpenClaw design gateway-side credential forwarding for this flow?

Rationale: Both options change a sensitive provider credential boundary, and automation should not choose whether node hosts may acquire and transfer gateway-owned OAuth material without maintainer intent.

Likely owner: vincentkoc

Owner reason: This contributor already authored and verified the maintainer repair direction for the exact remote-node auth guard.

Owner confidence: high

Options:

- **Fail closed before auth starts (recommended):** Block non-loopback remote node-host auth login with an actionable gateway-host instruction and preserve local loopback/tunnel setups with shared loopback semantics.
- **Forward credentials to gateway:** Design an authenticated gateway RPC or setup flow that moves provider auth material to the gateway store without consuming tokens locally first.
- **Keep permissive with a warning:** Warn node-host users that auth will only affect the local node, accepting the current wrong-host credential risk for compatibility.

## Reproduction Assessment

Yes, source-reproducible. Current main resolves a local `agentDir`, runs provider auth, and upserts returned profiles there while node-host config can point at a non-loopback gateway.

## Solution Assessment

Unclear until maintainer intent is set. A pre-auth fail-closed guard is the narrowest safe implementation if maintainers accept that product/security behavior, while transparent gateway credential forwarding needs a separate design.

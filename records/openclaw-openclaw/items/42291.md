## Label Justifications

- `P1`: The issue describes a real remote-gateway auth workflow where OAuth refresh credentials can be consumed locally and leave gateway model calls failing.
- `impact:data-loss`: Provider OAuth refresh material can be rotated or consumed into the wrong local auth store, making the intended gateway credential unusable.
- `impact:security`: Sensitive provider credential material can cross the wrong node/gateway trust boundary without warning.
- `impact:auth-provider`: The failure directly affects provider OAuth state, model auth routing, and recovery from refresh-token reuse errors.
- `maturity:stable`: The issue affects the gateway/node remote boundary, and `gateway-runtime` is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and the latest release still run provider auth login against the resolved local agent auth store, while node-host config can point at a non-loopback gateway; the same-repo fix attempts are closed unmerged and the only live fork PR is conflicting and not maintainer-editable.

## What This Changes

The issue requests preventing `openclaw models auth login` on a remote node host from silently storing OAuth credentials in the node-local auth profile store instead of the gateway-owned store.

## Best Possible Solution

End with remote node-host auth login unable to consume or store provider OAuth material on the node; the narrow default is a pre-auth non-loopback node-host guard unless maintainers explicitly choose a gateway-side credential-forwarding design.

Rationale: The source-level fix shape is clear, but the permanent behavior decides whether a node host may acquire and transfer gateway-owned OAuth material, which is a product/security boundary automation should not choose alone.

Options:

- **Fail closed before auth starts (recommended):** Block non-loopback remote node-host auth login with an actionable instruction to run auth on the gateway host, while preserving loopback/tunnel setups.
- **Forward credentials to the gateway:** Design a credential-transfer RPC or setup flow that writes directly to the gateway-owned auth store without leaving node-local OAuth material behind.
- **Warn but allow local writes:** Keep the current permissive behavior with a warning, accepting that users can still consume OAuth credentials into the wrong store.

Yes. Source inspection shows current main resolves a local `agentDir`, runs provider auth, and upserts OAuth profiles there while node-host gateway metadata can point at a non-loopback gateway; I did not run the live OAuth flow in this read-only review.

Unclear until maintainer intent is set. A pre-auth fail-closed guard is the narrowest maintainable fix if maintainers accept that security behavior, while transparent credential forwarding needs an explicit design.

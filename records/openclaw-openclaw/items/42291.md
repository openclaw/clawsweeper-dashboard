- `P1`: The issue describes a real remote-gateway auth-provider workflow where OAuth refresh-token material can be consumed locally and leave gateway model calls failing.

## Summary

Keep open: current main and the latest release still persist model auth login profiles through the locally resolved agent store, while the only open closing candidate is a conflicting fork PR and the same-repo attempts are closed unmerged.

## What This Changes

The issue requests preventing `openclaw models auth login` on a remote node host from silently storing OAuth credentials in the node-local auth profile store instead of the gateway-used store.

## Best Possible Solution

Land or adopt a focused fix that blocks non-loopback node-host auth before OAuth starts, or explicitly designs a secure gateway credential-forwarding flow before allowing node hosts to acquire gateway-owned OAuth material.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should remote node-host `openclaw models auth login` fail closed before provider auth starts, or should OpenClaw support a gateway-side credential-forwarding flow for this case?

Rationale: The choice determines whether a node host may acquire and transfer provider OAuth material for a gateway-owned model runtime, which is both a product behavior and credential-boundary decision.

Likely owner: vincentkoc

Owner reason: He authored the maintainer draft for this exact guard and has recent auth CLI write-locking history on the affected path.

Owner confidence: high

Options:

- **Fail closed before auth starts (recommended):** Block auth login when node-host config points at a non-loopback gateway and instruct the user to run the command on the gateway host.
- **Design gateway credential forwarding:** Add an authenticated gateway-side flow that stores provider credentials in the gateway auth store without first consuming them into the node-local store.
- **Warn but allow local writes:** Keep local writes possible with an explicit warning, accepting that users can still consume credentials on the wrong host.

## Reproduction Assessment

Yes, source-reproducible: current main resolves a local `agentDir`, runs provider auth, and upserts returned profiles there while node-host config can point at a non-loopback gateway. I did not run a live OAuth flow because this read-only review should not consume real credentials.

## Solution Assessment

Unclear until maintainer intent is set. A pre-auth fail-closed guard is the narrowest safe repair if maintainers accept it, while transparent gateway forwarding needs separate protocol and security design.

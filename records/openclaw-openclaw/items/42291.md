## Summary

Keep open: current main and the latest release still run provider auth login against the local agent auth store, while node-host config can point at a non-loopback gateway and no same-repo fix has landed.

## What This Changes

The issue reports that `openclaw models auth login` on a remote node host persists OAuth credentials to the node-local auth store instead of the gateway-owned auth store.

## Best Possible Solution

Land a focused pre-auth guard or maintainer-approved gateway-forwarding design that prevents wrong-host provider credential writes before OAuth material is consumed, with tests for non-loopback remote nodes and allowed loopback/tunnel setups.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should remote node-host `openclaw models auth login` fail closed before provider auth starts, or should OpenClaw design gateway-side credential forwarding for this flow?

Rationale: Both directions change where sensitive provider OAuth material may be acquired and stored, and automation should not choose that node/gateway credential boundary without maintainer intent.

Likely owner: vincentkoc

Owner reason: Vincent already authored and verified the maintainer repair direction for this exact remote-node auth guard.

Owner confidence: high

Options:

- **Fail closed before auth starts (recommended):** Block non-loopback remote node-host auth login with an actionable gateway-host instruction while preserving local loopback and tunnel setups through shared loopback semantics.
- **Forward credentials to the gateway:** Design an authenticated gateway RPC or setup flow that moves provider auth material to the gateway store without first consuming tokens into the node-local store.
- **Warn but keep permissive:** Warn node-host users that auth affects only the local node, accepting the existing wrong-host credential risk for compatibility.

## Reproduction Assessment

Yes. Source inspection shows current main resolves a local `agentDir`, invokes provider auth, and persists returned profiles there while node-host config can point at a non-loopback gateway.

## Solution Assessment

Unclear until maintainer intent is set; a pre-auth fail-closed guard is the narrowest safe implementation if maintainers accept that behavior, while transparent gateway credential forwarding needs a separate design.

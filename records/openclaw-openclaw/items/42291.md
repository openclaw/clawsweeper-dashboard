## Label Justifications

- `P1`: The issue affects a real remote-gateway auth-provider workflow where provider credentials can be consumed locally and leave gateway model calls failing.
- `impact:data-loss`: Refresh/OAuth credential state can be rotated or consumed into the wrong local store, making the intended gateway credential unusable.
- `impact:security`: Sensitive provider credential material can cross the node/gateway trust boundary without warning.
- `impact:auth-provider`: The failure directly affects provider OAuth state, model auth routing, and recovery from refresh-token reuse errors.
- `maturity:stable`: The affected gateway/node/auth boundary maps to the `gateway-runtime` surface, which is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main still runs provider auth against the locally resolved agent store and upserts returned credentials there, while node-host config can point at a non-loopback gateway; the only open closing PR is a conflicting, non-maintainer-editable fork rather than an implemented fix.

## What This Changes

Fix `openclaw models auth login` on remote node hosts so OAuth credentials are not consumed into the node-local auth store while model calls use the gateway store.

## Best Possible Solution

Land a focused pre-auth guard for non-loopback node-host gateway configs, or explicitly design a gateway-side credential-forwarding flow before any OAuth/token material is collected.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should remote node-host `openclaw models auth login` fail closed before provider auth starts, or should OpenClaw implement authenticated gateway-side credential forwarding for this flow?

Rationale: Both options change where sensitive provider credential material is acquired and stored across the node/gateway boundary, so automation should not choose that security boundary without maintainer intent.

Likely owner: vincentkoc

Owner reason: Vincent already authored and verified the maintainer repair direction for this exact remote-node auth guard.

Owner confidence: high

Options:

- **Fail closed before auth starts (recommended):** Block non-loopback remote node-host auth login with an actionable instruction to run the command on the gateway host while preserving accepted loopback/tunnel forms.
- **Forward credentials to gateway:** Design and review a gateway RPC/setup flow that stores provider auth material on the gateway without first consuming tokens into the node-local store.
- **Warn but allow local writes:** Warn node-host users that login affects only the node and accept the wrong-host credential risk for compatibility.

## Reproduction Assessment

Yes, source-reproducible: current main resolves a local `agentDir`, runs provider auth, and upserts returned profiles there while node-host config can persist a non-loopback gateway target.

## Solution Assessment

Unclear until maintainer intent is set. A pre-auth fail-closed guard is the narrowest safe fix if maintainers accept that behavior; transparent credential forwarding needs explicit design and protocol review.

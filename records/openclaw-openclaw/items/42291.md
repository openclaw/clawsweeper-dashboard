## Summary

Keep open: current main still persists provider auth profiles to the CLI-resolved local agent directory and only refreshes gateway auth status afterward, while the latest release has the same wrong-host behavior and the linked fix attempts are not merged.

## What This Changes

The issue asks OpenClaw to prevent `openclaw models auth login` on a remote node host from silently storing OAuth credentials only in node-local auth state while model calls use the gateway.

## Best Possible Solution

Add a focused auth-boundary fix that detects non-loopback remote node-host mode before provider OAuth starts and either fails closed with gateway-host instructions or uses an explicitly approved gateway-owned credential-sync API.

Options:

- **Fail Closed On Remote Node Hosts (recommended):** Block the login before OAuth/token creation when `node.json` points at a non-loopback gateway and tell the operator to run auth on the gateway host.
- **Design Gateway Credential Sync:** Keep the workflow convenient by adding an explicit gateway API for credential transfer, with security review and upgrade tests.
- **Accept Node-Local Auth Writes:** Document that node-host auth login affects only the node-local store and require operators to authenticate directly on the gateway.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path without a live OAuth run: current main resolves a local `agentDir`, writes OAuth profiles there, and only asks the gateway to refresh auth status afterward. The latest release still has the same local-write path and no node-host remote-gateway guard.

## Solution Assessment

No, the current behavior is not the best solution because it lets credential-bearing OAuth state land on the wrong host. A fail-closed node-host preflight looks like the smallest safe fix, but maintainers need to choose that over a gateway credential-sync design.

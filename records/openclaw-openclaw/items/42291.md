## Summary

Keep open: current main and the latest release still persist `models auth login` credentials through the locally resolved agent auth store, while node-host gateway metadata is separate and the same-repository fix attempts are closed unmerged.

## What This Changes

The issue reports that running `openclaw models auth login` on a remote node host stores OAuth credentials locally instead of making them available to the gateway that performs model calls.

## Best Possible Solution

Land a focused pre-auth remote-node guard, or an explicitly approved gateway-forwarding design, that prevents wrong-host credential writes before OAuth refresh material is consumed and covers remote-block plus loopback-allow cases.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should remote node-host `openclaw models auth login` fail closed before provider auth starts, or should OpenClaw support gateway-side credential forwarding for this flow?

Rationale: Both choices define where sensitive provider OAuth material may be acquired or transferred across the node/gateway boundary, so automation should not pick the permanent behavior without maintainer intent.

Likely owner: vincentkoc

Owner reason: He is the strongest history match for both the current auth/node-host code and the closed maintainer draft for this credential-boundary fix.

Owner confidence: high

Options:

- **Fail closed before auth starts (recommended):** Block non-loopback remote node-host auth login with a clear instruction to run the command on the gateway host while preserving loopback and tunnel setups.
- **Design credential forwarding:** Add an authenticated gateway-owned flow that moves provider auth material to the gateway store without consuming or persisting it on the node first.
- **Warn but permit:** Keep local-write behavior with a warning, accepting the wrong-host credential risk for compatibility.

## Reproduction Assessment

Yes, at source level. Current main resolves a local `agentDir`, runs provider auth, and persists returned profiles there while node-host config can record a non-loopback gateway target.

## Solution Assessment

Unclear until maintainer intent is set. A pre-auth fail-closed guard is the narrowest safe fix if maintainers accept that behavior; transparent gateway credential forwarding needs a separate security design.

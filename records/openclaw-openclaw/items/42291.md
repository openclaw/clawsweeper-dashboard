## Label Justifications

- `P1`: The report describes a real remote-gateway auth-provider workflow where OAuth refresh-token material can be consumed locally and leave gateway model calls failing.
- `impact:data-loss`: Provider OAuth refresh credentials can be consumed into the wrong local store, making the intended gateway credential unrecoverable.
- `impact:security`: Sensitive provider credential material can cross the wrong node/gateway trust boundary without a clear user decision.
- `impact:auth-provider`: The failure directly affects provider OAuth state, model auth routing, and recovery from refresh-token reuse errors.
- `maturity:stable`: The issue affects Gateway/node trust-boundary behavior under `gateway-runtime`, which is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and the latest release still write `models auth login` results into the locally resolved agent auth store before any node-host remote-gateway guard, and the only linked fix paths are closed or an open conflicting fork PR.

## What This Changes

The issue asks OpenClaw to prevent `openclaw models auth login` on a remote node host from consuming OAuth credentials into the node-local auth store instead of the gateway auth store.

## Best Possible Solution

Land a focused pre-auth remote-node guard, or an explicitly approved gateway-forwarding design, that prevents wrong-host credential writes before OAuth refresh material is consumed and covers both remote-block and loopback-allow cases.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should remote node-host `openclaw models auth login` fail closed before provider auth starts, or should OpenClaw support gateway-side credential forwarding for this flow?

Rationale: Both options change where provider OAuth material may be acquired, persisted, or transferred across the node/gateway boundary, so automation should not choose the permanent credential-boundary behavior without maintainer intent.

Likely owner: vincentkoc

Owner reason: He authored the maintainer draft for this exact fix direction and is a recent contributor on the auth CLI surface.

Owner confidence: high

Options:

- **Fail closed before auth starts (recommended):** Block non-loopback remote node-host auth login with a clear instruction to run the command on the gateway host while preserving loopback and tunnel setups.
- **Design credential forwarding:** Add an authenticated gateway-owned flow that moves provider auth material to the gateway store without first consuming or persisting it on the node.
- **Warn but permit:** Keep local-write behavior with a strong warning, accepting the wrong-host credential risk for compatibility.

## Reproduction Assessment

Yes, at source level. Current main resolves a local `agentDir`, runs provider auth, and persists returned profiles there while node-host config can record a non-loopback gateway target.

## Solution Assessment

Unclear until maintainer intent is set. A pre-auth fail-closed guard is the narrowest safe fix if maintainers accept that behavior; transparent gateway credential forwarding needs a separate design.

## Summary

Keep open: current main and the latest release still persist provider auth profiles through the local agent auth store, and the only live closing PR is an open conflicting fork PR rather than a merged OpenClaw implementation.

## What This Changes

The issue asks OpenClaw to prevent `openclaw models auth login` on a remote node host from consuming OAuth credentials into the node-local auth store instead of the gateway.

## Best Possible Solution

Land a focused pre-auth guard that detects non-loopback remote node-host gateway config before provider auth starts, blocks or redirects the user before any credential write, reuses shared loopback handling, and covers remote-block plus local-loopback cases in tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should remote node-host `openclaw models auth login` fail closed before provider auth starts, or should OpenClaw design gateway-side credential forwarding for this flow?

Rationale: Both options change a sensitive provider credential boundary, and automation should not decide whether node hosts may acquire and transfer gateway-owned OAuth material without maintainer intent.

Likely owner: vincentkoc

Owner reason: Vincent already authored and verified the maintainer repair direction for this exact remote-node auth guard.

Owner confidence: high

Options:

- **Fail closed before auth starts (recommended):** Block non-loopback remote node-host auth login with an actionable gateway-host instruction while preserving loopback/tunnel setups through shared loopback semantics.
- **Forward credentials to the gateway:** Design an authenticated gateway RPC or setup flow that transfers provider auth material into the gateway store without consuming tokens locally first.
- **Warn but keep permissive:** Warn node-host users that auth only affects the local node, accepting the current wrong-host credential risk for compatibility.

## Reproduction Assessment

Yes. Source inspection shows current main resolves a local `agentDir`, invokes provider auth, and persists returned profiles there while node-host config can point at a non-loopback gateway.

## Solution Assessment

Unclear until maintainer intent is set. A pre-auth fail-closed guard is the narrowest safe implementation if maintainers accept that behavior, while transparent gateway credential forwarding needs a separate design.

## Label Justifications

- `P1`: The bug can break real remote-gateway model auth by consuming OAuth credentials on the wrong host while the active gateway continues using stale tokens.
- `impact:data-loss`: The reported refresh token can be consumed or rotated into a local store that the gateway does not use, making the usable credential state effectively lost for that workflow.
- `impact:security`: The issue concerns OAuth credential placement across a node/gateway trust boundary.
- `impact:auth-provider`: The affected path is provider OAuth login, auth-profile persistence, and model-call credential resolution.
- `maturity:stable`: The issue affects the gateway runtime boundary, and `gateway-runtime` is scored M4 Stable in the maturity scorecard.

## Summary

Keep open: current main and v2026.6.11 still persist `openclaw models auth login` OAuth results into the local agent auth store, while remote gateway docs say the gateway owns auth profiles and the linked fix attempts remain unmerged or unsafe as canonical closure targets.

## What This Changes

The issue asks OpenClaw to stop or correctly route OAuth login credentials when `openclaw models auth login` is run from a node host connected to a remote gateway.

## Best Possible Solution

Land a focused pre-auth guard that detects non-loopback remote node-host gateway config before provider auth begins, blocks with a gateway-host instruction unless maintainers explicitly choose credential forwarding, and covers remote-block plus local-allowed tests.

Question: Should remote node-host `openclaw models auth login` fail closed before OAuth starts, or should OpenClaw design authenticated gateway-side credential forwarding?

Rationale: Both options can fix the reported loss, but they make different product and security-boundary commitments for where OAuth credentials may be accepted and stored.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Block remote node-host login before OAuth (recommended):** Treat non-loopback node-host gateway config as a wrong-host auth attempt and instruct the user to run login on the gateway host.
- **Design gateway credential forwarding:** Add an authenticated gateway-side credential update flow with explicit protocol, authorization, and upgrade proof before allowing node-host login to continue.
- **Warn but still write locally:** Keep local writes after a warning, accepting that users can still consume a token that does not update the active gateway.

## Reproduction Assessment

Yes: source inspection shows the login flow persists OAuth results to the locally resolved `agentDir` and lacks a node-host remote-gateway guard before provider auth begins.

## Solution Assessment

Unclear until maintainers choose the credential-boundary policy; a fail-closed pre-auth guard is the safest narrow fix, while gateway forwarding needs a larger security design.

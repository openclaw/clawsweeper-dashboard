- `P1`: The issue describes a real remote-gateway auth workflow where OAuth refresh-token material can be consumed locally and leave model calls failing.

## Summary

Keep open: current main still sends provider auth-login results into the resolved local agent auth store without checking node-host remote gateway state, and the only live closing candidate is an open conflicting fork PR rather than an implemented same-repo fix.

## What This Changes

The issue asks OpenClaw to prevent `models auth login` on a remote node host from silently writing OAuth credentials to the node-local auth store instead of the gateway-owned auth store.

## Best Possible Solution

Land a focused pre-auth guard that detects non-loopback remote node-host gateway config before provider auth starts, blocks with an actionable gateway-host instruction, preserves shared loopback/tunnel behavior, and covers both block and allow paths in tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should remote node-host `openclaw models auth login` fail closed before provider auth starts, or should OpenClaw design a gateway-side credential-forwarding flow for this command?

Rationale: Both choices change where sensitive provider OAuth material may be acquired and stored, and automation should not choose that credential boundary without maintainer intent.

Likely owner: vincentkoc

Owner reason: This person already authored and verified the maintainer repair direction for the exact remote-node auth guard.

Owner confidence: high

Options:

- **Fail closed before auth starts (recommended):** Block non-loopback remote node-host auth login with a gateway-host instruction and preserve loopback or SSH-tunnel setups through shared loopback semantics.
- **Design credential forwarding:** Add an authenticated gateway-side flow that moves provider auth material into the gateway store without consuming tokens into the node-local store first.
- **Warn but allow:** Keep the permissive local write path but tell node-host users it will not update the gateway, accepting the current wrong-host credential risk for compatibility.

## Reproduction Assessment

Yes, source-reproducible. Current main resolves a local `agentDir`, runs provider auth, and upserts returned profiles there while node-host config can point at a non-loopback gateway.

## Solution Assessment

Unclear until maintainer intent is set. A pre-auth fail-closed guard is the narrowest safe implementation if maintainers accept that behavior, while transparent gateway credential forwarding needs a separate design.

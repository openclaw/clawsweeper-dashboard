## Summary

Keep open: current main and the latest release still persist `models auth login` credentials through the local agent auth store, while node-host config can point at a remote gateway and the linked same-repo fixes remain closed unmerged.

## What This Changes

The issue asks for remote node-host `openclaw models auth login` to avoid consuming OAuth credentials into the node-local auth store instead of the gateway-owned auth store.

## Best Possible Solution

Land a focused pre-auth guard or maintainer-approved gateway-forwarding design that prevents wrong-host credential writes before OAuth/token material is consumed, with regression coverage for non-loopback remote nodes and accepted loopback/tunnel forms.

## Maintainer Decision

Kind: security_boundary

Question: Should remote node-host `openclaw models auth login` fail closed before provider auth starts, or should OpenClaw support gateway-side credential forwarding for this flow?

Rationale: Both options change a sensitive provider credential boundary, and automation should not decide whether node hosts may acquire or transfer gateway-owned OAuth material without maintainer intent.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Fail closed before auth starts (recommended):** Block non-loopback remote node-host auth login with an actionable instruction to run the command on the gateway host while preserving loopback/tunnel setups.
- **Forward credentials to the gateway:** Design an authenticated gateway RPC or setup flow that moves provider auth material to the gateway store without first consuming credentials locally.
- **Warn but keep permissive:** Warn node-host users that login only affects the local node, accepting the existing wrong-host credential risk for compatibility.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: current main resolves a local `agentDir`, invokes provider auth, and persists returned profiles there while node-host config can identify a non-loopback gateway.

## Solution Assessment

Unclear until maintainer intent is set. A pre-auth fail-closed guard is the narrowest safe fix if maintainers accept that behavior, while transparent gateway credential forwarding needs separate design.

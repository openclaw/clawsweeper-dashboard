## Label Justifications

## Summary

Keep this PR open: its real onboarding proof and focused scope are strong, but the new batch-level suppression of a superseded auth-refresh error can also hide a concurrent genuine owner refresh failure, leaving that owner stale without the intended warning. The protected `maintainer` label also requires explicit maintainer handling rather than cleanup closure.

## What This Changes

The branch makes web first-run onboarding resilient to session-key canonicalization, makes route drafts one-shot, preserves reserved setup runtime rebinding, and suppresses expected superseded auth-refresh warnings.

## Best Possible Solution

Handle supersession per refreshed owner, or inspect all owner refresh outcomes after settlement so expected supersession is ignored without swallowing genuine failures; add a mixed-owner regression test.

Yes for the proposed regression: source inspection and the supplied reviewer report describe a deterministic two-owner auth-mutation batch where one refresh is superseded and another fails. The supplied live evidence supports the onboarding fixes, but does not demonstrate this mixed failure path.

## Solution Assessment

No. The onboarding changes are narrowly targeted, but the current aggregate catch is not the safest error boundary; it should distinguish individual superseded outcomes from genuine concurrent refresh failures.

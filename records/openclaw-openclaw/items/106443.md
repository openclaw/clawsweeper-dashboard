Rationale: The code can implement either ownership model, but choosing the durable wake’s terminal meaning, reset-generation behavior, and responsibility after queue retry exhaustion defines a persisted product contract that automation cannot infer safely.

Options:

- **Accept queue ownership transfer (recommended):** Treat successful idempotent enqueue as durable delivery, retain explicit `session_delivery_queue` and `noExternalSend` evidence, and make later queue recovery solely responsible for consumption.

- **Introduce a handed-off state:** Add a distinct persisted state between pending and delivered so queue ownership transfer cannot be confused with consumption, at the cost of broader schema, protocol, and migration work.

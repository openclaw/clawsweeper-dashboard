## Label Justifications

- `P2`: The original report was a bounded Mattermost channel/session routing bug with real misrouted replies but no core outage or security emergency.
- `impact:message-loss`: The reported behavior sent proactive Mattermost replies outside the intended thread, causing the expected message to be missed in the active conversation.
- `impact:session-state`: The bug depended on thread-scoped session context not being inherited by proactive delivery paths.

## Summary

Current main and release v2026.6.11 cover the reported Mattermost proactive-thread cases: the message tool now inherits same-thread context through the Mattermost threading adapter, and routed cron/heartbeat replies recover the thread id from the thread-scoped session key before Mattermost delivery.

## What This Changes

The issue asks for proactive Mattermost sends, including message-tool sends and cron/heartbeat wakes, to inherit the active thread-scoped session context instead of posting to the channel root or DM.

## Best Possible Solution

Keep the shipped v2026.6.11 implementation and treat the older open candidate PRs for this issue as superseded by current main unless maintainers identify a new, distinct Mattermost thread-routing failure.

## Reproduction Assessment

Yes, historically at source level: the reported paths are the message-tool send path and routed cron/heartbeat replies from a thread-scoped session key. Current main no longer exposes the failing source path because those paths now resolve and pass the Mattermost thread id into delivery.

## Solution Assessment

Yes. The implemented shape is the maintainable fix: Mattermost owns its threading adapter behavior, while shared outbound routing and reply delivery consume the generic thread/reply contract instead of adding Mattermost-specific cron or message-tool branches.

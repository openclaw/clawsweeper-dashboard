## Summary

Keep open: current main and the latest shipped release have session, agent, channel, model, provider, date-range, `/usage`, and Dashboard usage surfaces, but they still lack first-class per-user token accounting or quota/billing boundaries. This remains a product and security design item rather than a narrow bug fix.

## What This Changes

Add per-user token usage accounting for input/output/total tokens with daily, weekly, and monthly reporting through `/usage` or the Dashboard.

## Best Possible Solution

Define a canonical identity-attribution and authorization model first, then extend usage storage, RPC, Dashboard, and `/usage` surfaces to expose per-user totals without treating session keys as auth.

Rationale: The source gap is clear, but solving it changes identity, privacy, storage, authorization, and quota/billing semantics in a project whose documented Gateway model is single-operator by default.

Owner confidence: high

Options:

- **Core identity accounting (recommended):** Define the user identity, authorized readers, storage schema, aggregation RPCs, Dashboard and `/usage` behavior, and privacy/retention rules before implementation.
- **Plugin or external reporting first:** Keep core usage as session/agent/channel/model/provider aggregates and let a plugin or export pipeline build user billing reports until the core identity model is approved.
- **No multi-user accounting:** Keep OpenClaw's single-operator model and narrow future work to existing session, agent, and model usage improvements.

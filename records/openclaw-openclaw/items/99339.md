## Label Justifications

- `P1`: A configured Telnyx inbound conversation can answer and greet but then sit silent with no caller transcript reaching the configured STT provider or agent response.
- `impact:message-loss`: Caller audio is not delivered into the expected transcript and reply flow for the reported Telnyx streaming configuration.
- `impact:other`: Setup reports a provider-specific voice-call mode as enabled even though the current runtime cannot complete that conversation flow.

## Summary

Keep this issue open. Current main and v2026.6.11 still do not make classic `streaming.enabled` transcription work for Telnyx: Telnyx only receives `stream_url` on the separate `realtime.enabled` path, while the classic streaming handler remains Twilio-shaped and setup still reports the unsupported provider combination as enabled.

## What This Changes

The issue asks for Telnyx `streaming.enabled` STT in voice-call conversation mode to start caller audio streaming to the configured realtime transcription provider instead of going silent after the greeting.

## Best Possible Solution

Choose the supported product behavior: either implement Telnyx classic streaming transcription into the realtime-transcription path with Telnyx frame handling and live carrier proof, or explicitly reject `provider: telnyx` plus `streaming.enabled` in setup/config/docs and point users to supported Telnyx realtime or native transcription paths.

## Reproduction Assessment

Yes, at source level. Current main only passes Telnyx `streamUrl` when `realtime.enabled` is true, while the reported `streaming.enabled` media handler parses Twilio start/media frames; I did not run a live Telnyx call.

## Solution Assessment

Unclear until maintainers choose the product behavior. The narrow safe outcome is either real Telnyx classic streaming support with live carrier proof or an explicit unsupported-mode rejection that prevents green setup for a dead-end configuration.

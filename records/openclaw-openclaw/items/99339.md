## Label Justifications

- `P2`: The issue blocks Telnyx voice-call conversation mode for affected users but is provider-specific and the voice-call channel is still experimental.
- `impact:message-loss`: Caller audio/transcripts are never delivered into the OpenClaw conversation path when Telnyx is used with streaming STT.
- `impact:session-state`: The reported flow never creates the expected agent session after the inbound greeting.

## Summary

Keep open: current main and the latest release still leave `streaming.enabled` transcription on the Twilio-shaped path, while Telnyx stream attachment is only wired for `realtime.enabled`; the reported Telnyx streaming STT conversation gap remains real.

## What This Changes

Support Telnyx inbound voice-call conversation mode with streaming STT by attaching Telnyx media streaming and feeding that audio into the voice-call transcription path.

## Best Possible Solution

Decide whether `streaming.enabled` should support Telnyx STT; if yes, implement it inside the voice-call plugin by reusing provider-shaped stream attach/frame parsing, otherwise make setup/docs fail clearly for unsupported Telnyx streaming STT.

## Reproduction Assessment

Yes at source level: configure voice-call with `provider: "telnyx"` and `streaming.enabled: true`; current main only wires streaming STT into Twilio and the STT media handler expects Twilio frames. I did not run a live Telnyx call.

## Solution Assessment

Unclear until maintainers choose the product path: the requested behavior is valid, but the best implementation likely reuses the existing Telnyx realtime stream adapter and Telnyx stream attach contract instead of bolting Telnyx onto the Twilio parser. Telnyx documents both `streaming_start` and answer-time `stream_url` behavior. ([developers.telnyx.com](https://developers.telnyx.com/api-reference/call-commands/streaming-start?utm_source=openai))

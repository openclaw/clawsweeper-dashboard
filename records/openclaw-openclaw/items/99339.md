## Label Justifications

- `P1`: A Telnyx inbound conversation can answer and greet but then leave callers without transcription or an agent response in the reported streaming mode.
- `impact:message-loss`: Caller audio is not converted into the expected transcript or agent reply when Telnyx is configured with classic streaming transcription.
- `impact:other`: Setup can report a provider/mode combination as enabled even though the runtime does not start the compatible Telnyx media stream.

## Summary

Keep this issue open. Current main and v2026.6.11 still do not make Telnyx `streaming.enabled` transcription work: Telnyx only receives media stream URLs on the separate `realtime.enabled` path, while classic streaming remains Twilio-shaped and setup can still report the unsupported Telnyx streaming mode as enabled.

## What This Changes

The issue reports that classic voice-call streaming transcription in conversation mode does not start for Telnyx calls, leaving inbound callers silent after the greeting.

## Best Possible Solution

Make the Telnyx classic streaming path explicit and safe: either implement Telnyx media streaming into the realtime-transcription provider path with live carrier proof, or reject the unsupported provider/mode during setup and document supported realtime or native transcription alternatives.

## Reproduction Assessment

Yes at source level: current main and v2026.6.11 only attach Telnyx media streams for `realtime.enabled`, while setup can still accept the reported `streaming.enabled` configuration. I did not run a live Telnyx call.

## Solution Assessment

Unclear until maintainers choose the product behavior: implementing Telnyx classic streaming is a new provider capability, while rejecting the unsupported mode is a smaller setup/docs bug fix.

## Label Justifications

- `P1`: A real Telnyx inbound voice workflow can answer and speak the greeting but then fail to produce the expected conversation turn, blocking production voice agents.
- `impact:message-loss`: The reported failure suppresses the caller transcript/agent-response loop after the greeting, so the voice conversation effectively loses the user's spoken message.
- `impact:other`: The issue also exposes a provider/setup capability mismatch where setup reports streaming transcription as enabled for a Telnyx configuration that current code cannot drive through the classic stream path.

## Summary

Keep this open: current main and v2026.6.11 still do not implement Telnyx classic `streaming.enabled` transcription with Deepgram, and the merged Telnyx work only covers the separate `realtime.enabled` media-stream path.

## What This Changes

Request Telnyx support for voice-call classic streaming transcription in conversation mode, or a clear setup/docs rejection for unsupported Telnyx `streaming.enabled` configurations.

## Best Possible Solution

Maintainers should either implement a Telnyx-owned classic media-stream transcription path with provider-specific frames and live Telnyx proof, or make setup/docs fail clearly for Telnyx `streaming.enabled` and point users to supported realtime/native transcription paths.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: Telnyx classic conversation flow does not pass `streamUrl` into Telnyx unless `realtime.enabled` is true, while the classic media stream handler remains Twilio-shaped. I did not run a live Telnyx call in this read-only review.

## Solution Assessment

Unclear as a final product direction. Implementing Telnyx `streaming.enabled` media transcription is plausible, but maintainers should first decide whether classic streaming should be extended for Telnyx or whether setup/docs should reject it and steer users to realtime/native transcription.

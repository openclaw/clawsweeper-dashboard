## Summary

Keep open: current main still has a source-reproducible Control UI path where a stale `chatRunId` keeps chat busy and blocks queue flushing, while the same-repo closing fix candidate remains open, conflicting, and proof-gated.

## What This Changes

The issue asks for Control UI chat to recover automatically after a long `chat.send` run finishes on the gateway so queued follow-up messages flush without another manual prompt.

## Best Possible Solution

Adapt or replace the linked fix so current Control UI chat uses an authoritative run-state recovery path, such as `agent.wait`, to clear stale local busy state and flush queued sends, with focused unit coverage plus Control UI browser proof.

## Reproduction Assessment

No live current-main reproduction was run. Source inspection gives a medium-confidence reproduction path: a stale `chatRunId` makes `isChatBusy` true, queues the next send, and prevents `flushChatQueue` from draining until local run state is cleared.

## Solution Assessment

Yes, the requested direction is a maintainable fix shape if implemented against the current chat modules: use backend run-state proof to clear stale local busy state, then flush the existing queue without changing gateway queue semantics.

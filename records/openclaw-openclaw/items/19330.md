## Label Justifications

- `P2`: The issue is a real multi-agent privacy and correctness gap, but it needs product/security design rather than emergency runtime mitigation.
- `impact:security`: The reported behavior lets agents with different trust levels read media received for another agent through the shared managed inbound store.

## Summary

Keep open: current main and v2026.6.11 still leave the central privacy/correctness problem unresolved because representative channel media saves use the shared inbound bucket, managed inbound references only model first-level `media/inbound/<id>` files, and managed inbound paths bypass per-agent media roots before normal local-root checks.

## What This Changes

The issue requests per-agent or per-account isolation for inbound media so media received for one agent is not visible through the shared managed inbound media store.

## Best Possible Solution

Keep this issue as the canonical core media-isolation tracker and define a scoped inbound-media contract that threads route/account or resolved agent ownership through channel saves, managed references, access checks, sandbox staging, cleanup, docs, and regression coverage.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: representative channel media saves still write to `inbound`, and another agent can address first-level managed inbound media before per-agent root checks. I did not run a live two-agent deployment in this read-only pass.

## Solution Assessment

No, the proposed save-time account subdirectory is only a partial solution. The best fix needs a maintainer-approved scoped managed-media contract across saving, URI/path resolution, sandbox staging, access policy, cleanup, compatibility, and tests.

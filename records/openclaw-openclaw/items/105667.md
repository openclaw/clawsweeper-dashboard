## Summary

Current main intentionally rejects Windows drive-relative bind sources, so the requested acceptance behavior is not a broken supported workflow. The report does expose a misleading parse/error detail, but adding implicit path resolution requires security-owner direction.

## What This Changes

The issue requests support for Windows drive-relative sandbox bind sources by changing bind separator parsing and resolving those sources before validation.

## Best Possible Solution

Keep absolute bind sources mandatory; preserve a leading drive-relative source as one parser token so validation reports the full invalid path, and consider acceptance only through an explicit security-owner-approved design with deterministic resolution semantics.

No: relaxing the regex and implicitly resolving drive-relative paths is not the safest or narrowest solution. The maintainable default is accurate parsing plus the existing rejection unless security owners intentionally approve deterministic support.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P1] Keep plugin entry pages inside the sandbox:** `ui/src/components/app-sidebar.ts:1307-1322`
  - body: This new public API lets a plugin choose `same-window` or `new-window`, then the sidebar launches the plugin route outside the Control UI iframe. That gives plugin-served UI a top-level same-origin page with the launch/session authority instead of the intended sandboxed embed boundary, so the first version should keep entries in an in-app sandbox or require a separate maintainer-approved top-level auth model.
  - confidence: 0.89
- **[P1] Force plugin entry frames to stay opaque:** `ui/src/pages/plugin/plugin-page.ts:180`
  - body: Plugin entry frames reuse the user-configurable embed sandbox, and `trusted` mode adds `allow-same-origin` alongside scripts. Because plugin entry pages are gateway-local routes, that combination removes the opaque-origin isolation this API relies on, so plugin entries need a fixed opaque sandbox such as `allow-scripts` at most.
  - confidence: 0.91
- **[P2] Fail closed when entry launch fails:** `ui/src/pages/plugin/plugin-page.ts:157-160`
  - body: If `plugins.uiEntryPointLaunch` rejects because the entry is unavailable or the caller lacks scope, the catch block still points the iframe at the raw plugin route. That can either show an auth failure or load with broader ambient gateway auth instead of the entry-scoped launch token, so the UI should show an unavailable/error state and avoid navigation.
  - confidence: 0.86

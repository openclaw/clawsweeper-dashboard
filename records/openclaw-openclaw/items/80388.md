## Summary

Keep this PR open, but it is not merge-ready: current main still lacks plugin Control UI entry points and the contributor supplied strong exact-head browser/Gateway proof, but the patch exposes plugin pages in same-origin top-level modes that bypass the sandboxed iframe boundary.

## Best Possible Solution

Ship only sandboxed in-app plugin entry points until maintainers approve an isolated-origin or otherwise explicit top-level plugin-page trust model, then align docs, protocol, and tests with that chosen model.

Yes for the blocking review finding: source inspection shows same-window and new-window entries navigate directly to same-origin plugin routes while Control UI token state lives in sessionStorage. The feature itself is not a current-main bug reproduction.

## Solution Assessment

No. The sandboxed in-app path is a plausible first version, but exposing same-origin top-level plugin pages is not the best fix without an isolated-origin design or explicit maintainer security approval.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.88

Full review comments:

- **[P1] Keep plugin entry pages inside the sandbox:** `ui/src/ui/app-render.helpers.ts:352-361`
  - body: The `same-window` and `new-window` paths navigate directly to `/plugins/<id>/...` on the Control UI origin. A plugin page opened this way is not the sandboxed iframe from `renderPluginUiEntryPointFrame`, so its JavaScript can read same-origin Control UI storage such as gateway token/settings state. Keep v1 entries sandboxed or move top-level plugin pages to an isolated origin before exposing these modes.

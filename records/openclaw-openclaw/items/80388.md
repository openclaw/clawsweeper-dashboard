## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.88

Full review comments:

- **[P1] Keep entry-point launches sandboxed:** `ui/src/components/app-sidebar.ts:1307-1322`
  - body: This still honors `same-window` and `new-window` by minting a plugin launch path and navigating the top-level window to it. That runs plugin-owned UI as a same-origin page outside the iframe sandbox, which defeats the isolation expected for plugin UI entry points. Keep entry points in an opaque iframe or require a separate-origin model before exposing this API.
  - confidence: 0.9
- **[P1] Use a fixed opaque sandbox for plugin entry frames:** `ui/src/pages/plugin/plugin-page.ts:180`
  - body: The plugin entry iframe inherits `embedSandboxMode`; when the operator config is `trusted`, `resolveEmbedSandbox` adds `allow-same-origin`. A plugin-authenticated UI route should not inherit the hosted-embed trust override, because `allow-scripts allow-same-origin` weakens the plugin isolation boundary. Use a fixed opaque sandbox such as `allow-scripts` for these frames.
  - confidence: 0.9
- **[P2] Fail closed when entry launch fails:** `ui/src/pages/plugin/plugin-page.ts:157-160`
  - body: If `plugins.uiEntryPointLaunch` rejects because the entry is unavailable, scope checks fail, or token minting fails, the catch falls back to the raw plugin path. That turns an authorization failure into a direct protected-route navigation and bypasses the short-lived launch-token/session boundary whenever another auth path is present. Render an unavailable/error state instead; the sidebar launch helper has the same fallback.
  - confidence: 0.86

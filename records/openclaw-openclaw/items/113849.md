## Summary

This remains a concrete feature request, not an already-fixed bug: it asks for a new plugin-observation capability at a channel access-policy boundary. The request has a plausible audit/logging use case, but it introduces a compatibility-sensitive hook and configuration surface, so it needs maintainer direction on whether the contract should be a generic inbound lifecycle event rather than a WhatsApp-specific hook.

## What This Changes

Add an opt-in plugin hook so a plugin can archive group messages rejected by channel access policy without allowing those messages to activate an agent response.

## System Context

Inbound channel adapters receive a group message, evaluate configured sender/group access policy, and either hand the allowed message to normal agent dispatch or drop it. The requested hook would expose the drop decision to plugins as a side effect while preserving the existing access-control result.

## Architecture Diagram

  C -->|Allowed| D[Agent dispatch]
  C -->|Blocked group message| E[Optional plugin observation]
  E --> F[Archive or audit plugin]
  C -->|Blocked| G[No agent response]

## Best Possible Solution

Define a documented, privacy-reviewed plugin-SDK observation contract at the normalized inbound access-decision boundary, then implement it consistently for supported group channels or deliberately scope the initial channel support with clear semantics and tests.

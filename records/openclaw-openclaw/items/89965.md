## Summary

Keep open: the timeout notice is useful and well proven, but the latest head still omits the existing `message_tool_only` source-reply delivery signal from the new no-payload timeout gate, so it can duplicate a reply after one was already delivered.

## What This Changes

The PR adds a user-visible embedded-runner timeout notice, a pure decision helper, and regression coverage for timed-out turns that would otherwise return no visible payload.

## Best Possible Solution

Keep the terminal-boundary timeout notice, but gate it on delivered source-reply evidence as well and add a focused timed-out source-reply regression before merge.

## Reproduction Assessment

Yes, at source level. A timed-out attempt with `didDeliverSourceReplyViaMessageTool: true`, no mirror payloads, and no ordinary messaging-tool delivery evidence reaches the new timeout-notice branch before the shared terminal path can preserve the existing source-reply suppression contract.

## Solution Assessment

No, not yet. The embedded-runner terminal boundary is the right layer for the notice, but the gate needs to include delivered source-reply evidence before this is the best fix.

## Summary

Keep open: the latest head fixes the prior client-tool/yield blocker, but the timeout notice still ignores `message_tool_only` source-reply delivery evidence, so a turn that already visibly replied through the message tool can receive an extra timeout error.

## Best Possible Solution

Keep the terminal-boundary timeout notice, but gate it on delivered source-reply evidence as well and add a focused regression for `timedOut` plus `didDeliverSourceReplyViaMessageTool`.

## Reproduction Assessment

Yes, at source level. A timed-out attempt with `didDeliverSourceReplyViaMessageTool: true`, no mirror payloads, and no ordinary messaging-tool evidence can still reach the new timeout-notice branch before the terminal path suppresses automatic replies.

## Solution Assessment

No, not quite. The embedded-runner terminal boundary is the right layer for the notice, but the gate needs to preserve the existing source-reply delivery terminal state before this is the best fix.

## Summary

The repeated preparation is real in current source, but the report does not establish material impact in an OpenClaw workload, and the proposed unbounded cache with finalizers is not yet the safest design. Keep this open for a focused benchmark and maintainer confirmation before adding cache complexity to the unreleased facade.

## What This Changes

Request prepared-statement reuse in the synchronous Kysely SQLite facade to avoid calling `DatabaseSync.prepare()` for the same SQL on every execution.

## Best Possible Solution

Add a representative Node 22 benchmark first; if repeated preparation is material, implement one small bounded per-database LRU shared by execute and iterate paths, clear it through `clearNodeSqliteKyselyCacheForDatabase`, and cover reuse, eviction, schema changes, iterators, and database close/reset.

## Summary

Keep open. Current main and v2026.6.11 still do not expose `affinityKey` or `mode="persistent"` on `sessions_spawn(runtime="acp")`, still create ACP spawn session keys with a random UUID, and still reject ACP `mode="session"` without `thread=true`; the related items cover broader thread decoupling, hub delegation, or cron scheduling rather than this cron/hook affinity contract.

## What This Changes

Requested a non-thread persistent ACP affinity path for cron and orchestrator `sessions_spawn` sessions, using a separate persistent mode and affinity key without changing thread-bound `mode="session"`.

## Best Possible Solution

Define a narrow, maintainer-approved ACP affinity contract for cron/hook requesters that uses owner-scoped deterministic keys, preserves failed dispatch state safely, documents the API, and leaves thread-bound `mode="session"` semantics unchanged.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: current main has no `affinityKey` or `mode="persistent"` `sessions_spawn` path, and ACP `mode="session"` without `thread=true` returns a `thread_required` error. I did not run a live cron/hook ACP flow because the missing API contract is directly visible in source and docs.

## Solution Assessment

Unclear. A separate explicit persistent-affinity path is safer than relaxing `mode="session"`, but maintainers still need to approve the API name, requester limits, owner scoping, and security model before a fix PR should be queued.

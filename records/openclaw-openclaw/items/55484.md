## Label Justifications

- `impact:session-state`: The request is about preserving and reusing ACP harness session context across cron, hook, and orchestrator invocations without thread binding.
- `impact:security`: Persistent affinity can cross requester, workspace, backend, or privilege boundaries if the scoping contract is wrong.

## Summary

Keep open. Current main and v2026.6.11 still lack a `sessions_spawn({ runtime: "acp", mode: "persistent", affinityKey })` contract, still restrict ACP spawn modes to `run` and thread-bound `session`, and related cron/hook persistence work does not implement deterministic ACP affinity reuse.

## What This Changes

Request support for non-thread ACP persistent affinity for cron, hook, and orchestrator `sessions_spawn` calls.

## Best Possible Solution

Define a narrow ACP affinity contract for cron/hook/orchestrator callers, scoped by requester identity, backend, cwd, and affinity key, with explicit lifecycle/security rules plus schema, docs, and regression coverage while leaving thread-bound `mode="session"` intact.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 have no `affinityKey` or `mode="persistent"` `sessions_spawn` path, and ACP `mode="session"` still requires `thread=true`. I did not run a live cron/hook ACP flow because the requested contract is absent from source, docs, and release-tag source.

## Solution Assessment

Unclear as a final product shape. The downstream `mode="persistent"` plus `affinityKey` proposal is plausible, but maintainers still need to choose the ownership, lifecycle, and security boundaries before implementation.

## Summary

Keep open: current main and the latest release still expose only boolean all-off suppression plus narrower warning-leak fixes, while the requested success-aware normal-chat `all | final | off` policy remains absent and needs a maintainer product/config decision.

## What This Changes

The issue requests a normal-chat configuration policy for suppressing transient tool error warnings after recovered or successful agent turns.

## Best Possible Solution

Keep default-visible safety behavior, retain the existing all-off operator escape hatch, and add any final-outcome-gated mode only as a maintainer-approved opt-in with schema, docs, upgrade notes, and channel/runtime tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a public normal-chat tool-error delivery policy beyond `messages.suppressToolErrors`, and what should happen when a mutating tool fails but the assistant final reply sounds successful?

Rationale: Source inspection confirms the UX gap, but choosing `all | final | off` semantics changes public config and failed-side-effect visibility safety, so automation cannot safely decide the product contract.

Likely owner: vincentkoc

Owner reason: They have the strongest recent history on the current warning-policy path and authored the merged related PR that explicitly left this broader issue open.

Owner confidence: high

Options:

- **Add explicit opt-in delivery policy (recommended):** Define a default-compatible enum such as `all | final | off` that preserves current visible warnings by default while allowing hosted or group-chat operators to opt into final-only or off behavior with focused tests.
- **Keep boolean-only policy:** Treat `messages.suppressToolErrors` as the supported all-off escape hatch and close or defer the success-aware enum after documenting that boundary.
- **Move policy to channels:** Let team-chat plugins own warning visibility where channel UX differs, avoiding another global message config key.

## Reproduction Assessment

Yes, source-level: current tests still expect success-looking mutating and exec failures to produce visible warnings when suppression is not configured. I did not run a live channel reproduction in this read-only review.

## Solution Assessment

Unclear pending maintainer direction: the requested enum directly addresses the hosted-operator UX, but the safest solution may be a default-compatible enum, documentation of the existing boolean, or channel-specific policy.

## Summary

Keep open: current main has default-visible mutating tool-error warnings plus an all-off boolean, but it still does not implement the requested success-aware normal-chat delivery policy; the remaining work needs maintainer product and safety direction.

## What This Changes

The issue requests a configurable normal-chat policy, such as `all | final | off`, for suppressing transient tool-error warning bubbles after successful agent recovery.

## Best Possible Solution

Define one default-compatible normal-chat tool-error delivery contract, keep current safety-preserving warnings as the default, and add any `final` or `off` behavior only with schema, docs, payload, progress, and channel coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a public success-aware tool-error delivery policy for normal chat surfaces, and if so what exact modes should it expose?

Rationale: Source inspection confirms the UX gap, but choosing success-aware suppression changes public config and failed-side-effect visibility semantics, so automation cannot safely choose the product contract.

Likely owner: Vincent Koc

Owner reason: They have the strongest inspected history on the current warning-policy path and authored the merged related PR that explicitly kept this broader issue open.

Owner confidence: high

Options:

- **Add explicit opt-in policy (recommended):** Define a default-compatible enum such as `all | final | off` where `all` preserves current warnings and hosted/team-chat operators can opt into final-only or off behavior with focused safety tests.
- **Keep boolean-only policy:** Treat `messages.suppressToolErrors` as the supported all-off escape hatch and close or defer the success-aware enum after documenting that boundary.
- **Move policy to channels:** Let channel plugins own warning visibility where chat UX differs, avoiding another global message config key.

## Reproduction Assessment

Yes, at source level: current tests still assert that success-looking assistant text plus failed mutating `write` or `exec` tools yields a second visible warning by default. I did not run a live Telegram or Discord replay in this read-only review.

## Solution Assessment

Unclear. The requested `all | final | off` policy is plausible, but the best fix depends on a maintainer safety decision because current behavior intentionally warns about failed side effects to avoid silent false success.

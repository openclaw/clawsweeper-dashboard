## Summary

Keep open: current main and the latest release still support only the all-off `messages.suppressToolErrors` boolean, while success-looking mutating tool failures still produce a visible warning by default. The remaining `all | final | off` normal-chat policy is a real operator UX request, but it needs maintainer product/safety direction before implementation.

## What This Changes

Request a public config policy to suppress or delay transient tool-error warning bubbles when a run ultimately produces a successful or useful final reply.

## Best Possible Solution

Keep default-visible safety behavior, retain the existing all-off escape hatch, and add any final-outcome-gated mode only as a maintainer-approved opt-in with schema, docs, upgrade notes, and channel/runtime tests.

Rationale: The source-level UX gap is clear, but choosing `all | final | off` semantics changes public config and failed-side-effect visibility safety, so automation cannot safely decide the product contract.

Owner confidence: high

Options:

- **Add opt-in delivery policy (recommended):** Define a default-compatible enum such as `all | final | off` that preserves current visible warnings by default while allowing hosted or group-chat operators to opt into final-only or off behavior with focused tests.
- **Keep boolean-only policy:** Treat `messages.suppressToolErrors` as the supported all-off escape hatch and close or defer the success-aware enum after documenting that boundary.
- **Move policy to channels:** Let team-chat plugins own warning visibility where channel UX differs, avoiding another global message config key.

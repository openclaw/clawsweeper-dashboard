## Summary

Keep open: current main and the latest release support an all-off `messages.suppressToolErrors` boolean, but they intentionally still show mutating-tool warnings when the assistant appears to claim success; the requested normal-chat `all | final | off` policy remains a product and safety decision.

## What This Changes

The issue requests a configurable normal-chat tool-error delivery policy so transient recovered tool failures can be hidden from user-facing channels while remaining available to the agent and logs.

## Best Possible Solution

Keep the current safe default, and only add a documented opt-in delivery policy if maintainers choose semantics that preserve agent context/logs and test mutating failures, explicit failure acknowledgements, success-looking replies, and progress payload delivery.

Rationale: The remaining change is not a narrow bug fix: it adds public config surface and changes when users see failed side effects after an apparently successful turn.

Options:

- **Add a conservative opt-in policy (recommended):** Keep current default behavior, then add a documented opt-in mode for hosted/team deployments with focused tests for safe failure visibility and suppression.
- **Keep the existing boolean only:** Treat `messages.suppressToolErrors: true` as the operator escape hatch and decline success-aware suppression until a clearer safety model exists.
- **Defer to run-loop recovery design:** Route this need into broader native tool-failure recovery work so the agent can explicitly resolve or narrate failures instead of relying on delivery filtering.

## Reproduction Assessment

Yes from source inspection and tests: `buildEmbeddedRunPayloads` with success-looking assistant text plus a mutating `lastToolError` still emits a visible warning unless the all-off suppression flag is set. I did not run a live channel scenario in this read-only review.

## Solution Assessment

No, the currently requested `final` policy is not yet a proven best fix because existing code deliberately preserves warnings for success-looking mutating failures. The best next step is a maintainer-chosen opt-in policy or run-loop recovery design that avoids hiding real failed side effects.

## Summary

Keep this issue open: current main still combines shallow transaction snapshots with in-place mutation of nested registry entries, so rollback can retain changes made during a failed plugin registration. The report identifies a valid bounded integrity defect, although its proposed generic deep clone is not the safest repair.

## What This Changes

Ensure failed plugin-registration transactions restore nested mutable registry state rather than only restoring top-level arrays and maps.

## Best Possible Solution

Make registration rollback isolate every transaction-owned mutable field—prefer immutable replacement or explicit cloning of mutable records and entries—while preserving function-bearing handlers by reference, then add regression coverage for both PluginRecord counters/lists and an existing capability entry mutated before failure.

## Reproduction Assessment

Yes at source level: start with an existing plugin record, begin a registration transaction, invoke an API that mutates `toolNames` or a counter, then force rollback; the shallow snapshot restores the containing array but retains the mutated record. A focused automated test still needs to execute this path.

## Solution Assessment

No, cloning the entire registry with `structuredClone` is not the best fix because registry entries contain executable handlers and other non-cloneable values. The narrow maintainable repair is explicit isolation of only the mutable transaction state, backed by rollback tests for every in-place mutation class.

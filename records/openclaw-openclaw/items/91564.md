## Summary

Keep open: current main has recovery for stale Telegram spool claims and an in-process lane guard, but it does not establish that a full gateway restart can permanently suppress one forum topic’s fresh inbound messages. The recent direct-message report also supports the acknowledged-without-dispatch symptom, while explicitly stopping short of claiming the same root cause.

## What This Changes

The issue requests a fix for Telegram polling updates that are acknowledged but never dispatched to an agent for one forum topic after stuck-session recovery.

## System Context

Telegram polling turns Bot API updates into durable spool entries, associates them with a chat or topic lane, then dispatches them into an agent session. Timeout recovery and restart behavior must preserve the single-handler safety invariant without leaving later inbound messages permanently undispatchable.

## Architecture Diagram

flowchart LR
  update[Telegram update] --> polling[Polling offset and spool]
  polling --> lane[Chat or topic lane guard]
  lane --> dispatch[Inbound session dispatch]
  dispatch --> agent[Agent run and reply]
  lane --> recovery[Timeout and recovery handling]
  recovery --> polling

## Best Possible Solution

Instrument and reproduce the no-ingress path with a real Telegram forum topic, then bound guarded-lane recovery behind a hard handler or process-stop boundary before allowing the next update to drain.

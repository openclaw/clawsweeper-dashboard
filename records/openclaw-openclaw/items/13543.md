## Summary

Keep open: current main and v2026.6.11 still provide session-scoped sandbox activation, sandbox tool filtering, sandboxed browser settings, and exec elevated escape behavior, but not the requested per-tool host-vs-sandbox placement contract. The live discussion also has an unresolved security-boundary choice between operator-configured always/never placement and a tool/plugin-declared gateway-run contract.

## What This Changes

Requests a new core config and runtime contract for routing selected tools such as `web_fetch` and `browser` into a sandbox while keeping trusted tools host-routed in the same session.

## Best Possible Solution

Define one documented core tool-placement contract with explicit precedence between session sandbox mode, tool/plugin declarations, browser and `web_fetch` behavior, gateway-owned tools, cron, and elevated exec, then test placement separately from tool availability filtering.

- **Design Core Placement Contract (recommended):** Define a narrow schema and runtime decision point that keeps placement, filtering, browser behavior, `web_fetch` behavior, gateway-owned tools, cron, plugin tools, and elevated exec explicitly separate.
- **Keep Current Session Model:** Reject per-tool placement for now and document session sandboxing plus elevated exec and sandbox tool policy filtering as the intended model.
- **Fold Into Broader Sandbox Program:** Make the broader sandbox architecture tracker the design home while preserving this issue as the per-tool placement acceptance case.

## Summary

Keep open: current main and v2026.6.11 still provide session-scoped sandbox activation and sandbox tool filtering, not selective per-tool execution placement; the discussion also leaves the security model and product contract unresolved.

## What This Changes

Add a configurable policy that can execute selected tools inside a sandbox while other tools in the same session remain host-routed.

## Best Possible Solution

Define a generic typed tool-placement and privilege contract at tool registration, preserve a safe session-level default, explicitly model rare gateway-only capabilities, and test both process isolation and the downstream authority granted to untrusted tool output.

Options:

- **Adopt typed placement capabilities (recommended):** Add a generic placement capability to tool registration plus an operator policy, with secure defaults and explicit prompt-injection threat-model tests.
- **Keep session-first sandboxing:** Retain one sandbox boundary per session and allow only narrowly defined tool-owned gateway operations through an audited privilege mechanism.
- **Reject mixed-trust sessions:** Treat sessions that consume untrusted external content as wholly sandboxed and document subagents or separate agents as the supported isolation boundary.

## Reproduction Assessment

Not applicable as a bug reproduction: this is a new capability request, although current source clearly confirms that the proposed per-tool placement contract is absent.

## Solution Assessment

No, the proposed always/never tool-name lists are not yet the best solution because process placement alone does not contain prompt injection and the lists would create a brittle second policy system; a typed placement and authority contract is safer.

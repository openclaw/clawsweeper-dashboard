## Summary

Keep open: current main and the latest release still expose session/agent-scoped sandbox activation plus sandbox tool allow/deny filtering, but not the requested per-tool host-vs-sandbox placement contract; the discussion also shows the desired security model is still a maintainer product/security decision.

## What This Changes

The issue requests configurable per-tool sandbox execution so untrusted-content tools can be forced into a sandbox while trusted tools remain host-routed in the same session.

## Best Possible Solution

Design one documented core placement contract with explicit precedence between session sandbox mode, tool/plugin declarations, gateway-owned tools, browser/web_fetch behavior, and elevated exec, then test placement separately from tool filtering.

## Reproduction Assessment

Yes at source level: current schema and runtime status expose session/agent sandbox selection and filtering, not a per-tool placement mode. As a bug reproduction it is not applicable because this asks for a new capability rather than a failing shipped behavior.

## Solution Assessment

No, not as the proposed always/never schema alone. The security goal is aligned, but maintainers should first choose the placement owner and precedence model before committing to operator maps or tool-declared gateway escape semantics.

## Summary

Keep open: current main and v2026.6.11 still provide session-level sandbox modes plus sandbox tool allow/deny filtering, not the requested per-tool host-vs-sandbox placement contract; the issue remains security-sensitive product/API design work.

## What This Changes

The issue requests selective sandbox placement so tools such as `web_fetch` and `browser` can be forced into a sandbox while trusted tools remain host-routed in the same session.

## Best Possible Solution

Define one documented core placement contract with explicit precedence between sandbox mode, tool/plugin declarations, gateway-owned tools, browser/web_fetch behavior, and elevated exec, then test placement separately from tool availability filtering.

## Reproduction Assessment

Not applicable as a bug reproduction: this issue asks for a new execution-placement capability. Source and release inspection confirm current main and v2026.6.11 do not have that per-tool placement mode.

## Solution Assessment

Unclear: the security goal is aligned, but the proposed always/never map is not established as the best contract. The discussion raises a competing model where sandboxed sessions run most tools inside the sandbox and only declared tools escape to the gateway, so maintainers need to choose the owner and precedence model first.

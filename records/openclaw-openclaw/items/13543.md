## Summary

Keep open: current main and v2026.6.11 still expose session-level sandbox modes plus sandbox tool allow/deny filtering, not a per-tool host-vs-sandbox placement contract, and the discussion shows unresolved product/security direction.

## What This Changes

The issue requests a tool-level sandbox placement policy so selected tools can be forced into sandbox execution while other tools remain host-routed in the same session.

## Best Possible Solution

Define one documented core placement contract with explicit precedence between sandbox mode, tool/plugin declarations, gateway-owned tools, browser/web_fetch behavior, and elevated exec, then test placement separately from tool availability filtering.

## Reproduction Assessment

Yes for the missing capability by source inspection: current main and v2026.6.11 expose session-level sandbox activation and sandbox tool filtering, but no per-tool placement resolver accepting a tool name.

## Solution Assessment

No, not as the proposed schema alone. The security goal is aligned, but maintainers should first choose the placement owner and precedence model before committing to an always/never map or a tool-declared gateway contract.

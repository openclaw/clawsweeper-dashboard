## Summary

Keep open: current main and v2026.6.11 still have session-level sandbox activation and sandboxed-session tool allow/deny filtering, not a schema-backed per-tool host-vs-sandbox placement contract. The discussion also shows unresolved security/product direction around operator-selected always/never maps versus a tool/plugin-declared gateway execution contract.

## What This Changes

Request per-tool sandbox placement so untrusted web_fetch/browser work can be sandbox-routed while trusted exec/message/cron/gateway work remains host-routed in the same session.

## Best Possible Solution

Design one documented core sandbox/tool placement contract that separates execution location from tool filtering and elevated exec, then add schema, runtime routing, docs, doctor/audit guidance, and regression coverage for mixed host/sandbox sessions.

## Reproduction Assessment

Not applicable as a feature request; source inspection confirms current main does not expose the requested per-tool host-vs-sandbox placement surface. The existing behavior can be verified from schema, runtime, docs, and tests rather than a failing runtime repro.

## Solution Assessment

Unclear: the requested always/never operator map is plausible, but not yet proven to be the best permanent contract. Thinkscape's comment suggests a competing sandbox-by-default plus tool/plugin-declared gateway-execution model, so maintainers should choose the security contract first.

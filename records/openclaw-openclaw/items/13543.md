## Summary

Keep open: current main and v2026.6.11 still provide session/agent sandbox activation, sandbox tool allow/deny filtering, browser target selection, and exec host routing, but not the requested per-tool host-vs-sandbox placement policy. The discussion also shows unresolved security/product direction for whether placement should be operator configured, tool/plugin declared, or governed by a stricter precedence model.

## What This Changes

The issue requests configurable per-tool sandbox placement so selected untrusted tools such as web_fetch and browser can run in a sandbox while other tools stay host-routed in the same session.

## Best Possible Solution

Define one documented core placement contract with explicit precedence between sandbox mode, tool/plugin declarations, gateway-owned tools, browser/web_fetch behavior, and elevated exec, then test placement separately from tool availability filtering.

## Reproduction Assessment

Not applicable as a bug reproduction: this issue asks for a new execution-placement capability. Source and release inspection confirm current main and v2026.6.11 do not have that per-tool placement mode.

## Solution Assessment

No, not as the proposed schema alone. The security goal is aligned, but maintainers should choose the placement owner and precedence model before committing to an always/never map or a tool-declared gateway contract.

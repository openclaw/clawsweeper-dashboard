## Summary

Keep open: current main and the latest release still route Android `camera.list` through `ProcessCameraProvider.getInstance()`, and the merged snap/clip cleanup PRs do not cover this pre-capture metadata path. The full app-open green-dot symptom still needs live Android proof, but the source path remains concrete enough that this should not be cleaned up as stale or implemented.

## What This Changes

The issue reports that opening the Android app initializes CameraX through camera device listing and triggers Android's camera privacy indicator before any capture command.

## Best Possible Solution

Keep this issue open for maintainer/security review and real Android proof, then make Android `camera.list` use metadata-only Camera2 enumeration while leaving CameraX initialization inside intentional `camera.snap` and `camera.clip` capture paths.

## Reproduction Assessment

Yes for the narrower source path: invoking Android `camera.list` on current main reaches CameraX provider initialization. No for the full app-open symptom: source inspection did not prove that simply reopening the app invokes `camera.list`, and live Android privacy-indicator proof is still missing.

## Solution Assessment

Unclear for the full issue until live proof confirms the app-open trigger. For the proven code path, replacing Android `camera.list` with Camera2 metadata while reserving CameraX for capture is the narrowest maintainable fix shape.

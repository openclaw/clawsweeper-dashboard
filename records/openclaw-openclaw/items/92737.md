## Summary

Keep open: current main and the latest release still route Android `camera.list` through `ProcessCameraProvider.getInstance()`, and the merged snap-cleanup PR explicitly left this broader eager CameraX initialization issue unresolved. The full app-open privacy-indicator trigger still needs real Android proof before a privacy-sensitive repair is queued.

## What This Changes

The issue reports that the Android app can initialize CameraX on app open or metadata listing, showing the camera privacy indicator before an explicit `camera.snap` or `camera.clip` request.

## Best Possible Solution

Make Android `camera.list` use metadata-only Camera2 APIs, keep CameraX provider initialization inside intentional capture commands, and verify on Android 13+ that app launch and metadata listing do not show the camera privacy indicator.

## Reproduction Assessment

No for the full app-open privacy-indicator symptom; this read-only review did not run a real Android device or emulator repro. Yes at source level for the narrower path: current main still routes `camera.list` through `ProcessCameraProvider.getInstance()`.

## Solution Assessment

Yes directionally: replacing the Android metadata listing path with Camera2 metadata while leaving `snap` and `clip` on CameraX is the narrowest maintainable fix. The app-open caller and privacy-indicator behavior should be proven on-device before repair lands.

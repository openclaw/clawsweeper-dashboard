- `P2`: The issue reports a privacy-sensitive Android camera behavior with a narrow affected command surface and no evidence of data loss, security bypass, or core runtime outage.

## Summary

Keep open: current main still routes Android `camera.list` through `ProcessCameraProvider.getInstance()`, and the merged adjacent snap-cleanup PR explicitly did not address this eager CameraX initialization path.

## What This Changes

Avoid eager Android CameraX initialization on app open or metadata listing so the camera privacy indicator appears only for intentional camera capture.

## Best Possible Solution

Move Android `camera.list` to Camera2 metadata (`CameraManager`/`CameraCharacteristics`), keep CameraX provider initialization inside `camera.snap` and `camera.clip`, and verify app launch plus metadata listing on a real Android 13+ device.

## Reproduction Assessment

No, not for the full app-open behavior: I did not run a real Android repro, and current source does not prove app open directly calls `listDevices()`. Source inspection does reproduce the narrower `camera.list` path that reaches `ProcessCameraProvider.getInstance()`.

## Solution Assessment

Yes for the confirmed code path: replacing Android `camera.list` with Camera2 metadata is the narrowest maintainable fix. The app-open trigger should be verified before changing gateway command advertisement or command policy.

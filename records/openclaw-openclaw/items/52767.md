## Summary

Keep open: current main and v2026.6.11 still run BOOT.md whenever the boot-md gateway-startup hook fires and BOOT.md exists. Related merged work fixed same-workspace duplicates, startup-readiness blocking, and boot-session isolation, but the requested cross-restart run-once lifecycle remains a maintainer product/state decision.

## What This Changes

Request to make the bundled boot-md gateway startup hook stop re-running BOOT.md on every gateway restart and instead run once or idempotently.

## Best Possible Solution

Maintainers should decide the BOOT.md lifecycle first; if run-once wins, store completion/reset state in canonical OpenClaw state, preserve isolated boot sessions, and update docs plus regression tests to distinguish startup checks from first-run initialization.

Options:

- **Preserve Per-Startup Default (recommended):** Keep BOOT.md as a documented startup checklist and document idempotent BOOT.md patterns or hook disablement for users who need one-time initialization.
- **Adopt Run-Once Lifecycle:** Change boot-md to record canonical completion state with an explicit reset or doctor path, then update docs and tests around the new lifecycle.
- **Add Explicit Mode Later:** Keep the current default but design a separate opt-in run-once mode only after maintainers agree on the config or state surface.

## Reproduction Assessment

Yes for the central behavior at source level: the handler queues runBootOnce on each gateway startup event, and runBootOnce skips only missing or empty BOOT.md before agentCommand. A live restart freeze or channel-stall reproduction was not run in this read-only review.

## Solution Assessment

No for the suggested flag-file shape: it would address the symptom, but it adds ad hoc state and leaves reset, upgrade, and current per-startup semantics unsettled. The safer path is a maintainer-approved BOOT.md lifecycle contract backed by canonical state ownership and tests.

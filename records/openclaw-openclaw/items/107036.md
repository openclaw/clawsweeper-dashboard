## Summary

Keep open for a narrow product decision, not as a confirmed bug. Current OpenClaw intentionally uses non-blocking, push-based child completions with stable child/run identity, and v2026.7.1 added aggregation for parents waiting on several children; the report does not show a result attached to the wrong child or another current-main failure that spawn-order buffering would fix. ([docs.openclaw.ai](https://docs.openclaw.ai/tools/subagents))

## What This Changes

The issue requests deterministic parent-context ordering for results from concurrently invoked subagents.

## Best Possible Solution

Preserve identified completion events and multi-child aggregation; first add a focused current-main regression case with intentionally reversed child latencies, then change only the path that demonstrably loses or misattributes child identity.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should concurrent child results remain completion-ordered and identity-labelled, or should a yielded parent always receive them in original spawn order after every required child settles?

Rationale: Both contracts are technically viable, but spawn-order buffering changes latency, timeout, and partial-failure behavior; the existing documentation and shipped implementation currently favor event-driven completion and final-child aggregation.

Likely owner: tyler6204

Owner reason: The contributor guide routes agents/subagents ownership here, and this question defines the public coordination contract for that surface.

Owner confidence: high

Options:

- **Keep completion order (recommended):** Retain push-based completion semantics, require stable child identity in every result, and fix only a demonstrated misassociation or aggregation defect.
- **Adopt spawn-order batches:** Buffer all required child results and flush them in invocation order, accepting head-of-line blocking and defining timeout/failure placeholders.

## Reproduction Assessment

No. The issue supplies no executable scenario or transcript showing current main attaching a result to the wrong child, while current documentation and v2026.7.1 describe identified completion events and combined multi-child resumption.

## Solution Assessment

No. Unconditional spawn-order buffering is not yet the best fix because it would alter the non-blocking completion contract and can block faster results behind a slow or failed earlier child; a focused misassociation reproduction should determine the narrow repair boundary.

## Label Justifications

- `P3`: The reported behavior is a low-risk session-storage interpretation issue that current main’s rollover contract already addresses.
- `impact:session-state`: The report concerns the relationship between a reset session, its persisted row, and its transcript history.

## Summary

Current `main` treats a reset as a session-key rollover, not deletion of the session-key record: it mints a replacement session ID, persists the replacement entry, and retires the prior session state. The reported expectation that the session-row reference disappear would remove the mapping needed for the fresh session. ([github.com](https://github.com/openclaw/openclaw/blob/main/src/auto-reply/reply/session.ts))

## What This Changes

The issue requests that `/reset` remove a session-store record when it retires the prior session transcript.

## Best Possible Solution

Keep the current rollover model: retain one current session-row mapping per session key, create a new session ID on reset, and archive or clean up only prior-session artifacts according to the session-maintenance contract.

## Maintainer Decision

Required: false

## Reproduction Assessment

No. Current main’s reset path intentionally keeps the session-key mapping while assigning it a new session ID; the old transcript is retired rather than left as the active record. ([github.com](https://github.com/openclaw/openclaw/blob/main/src/auto-reply/reply/session.ts))

## Solution Assessment

No. Deleting the row on `/reset` would discard the canonical pointer for the newly created session; the maintainable behavior is to replace the row’s active session ID and retire the old session’s artifacts. ([github.com](https://github.com/openclaw/openclaw/blob/main/docs/reference/session-management-compaction.md))

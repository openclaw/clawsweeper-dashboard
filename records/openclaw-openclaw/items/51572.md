## Label Justifications

- `P2`: The issue affects session-memory reliability for automatic lifecycle paths with real user impact, but it is bounded to memory/session behavior and needs design selection rather than emergency repair.
- `impact:session-state`: The reported gap is about session rollover and prune paths discarding context before memory finalization runs.

## Summary

Keep open: current main and v2026.6.11 still leave bundled session-memory command-scoped, while automatic daily/idle rollover and maintenance prune follow separate lifecycle/maintenance paths that do not run that hook. The open reset PR only covers part of the request and still needs maintainer direction on hook semantics, privacy, and proof.

## What This Changes

The issue requests firing session-memory or an equivalent memory-finalization hook before automatic daily/idle resets and maintenance prune delete or rotate session context.

## Best Possible Solution

Define one maintainer-approved memory-finalization lifecycle for automatic rollover and destructive prune, with bounded async behavior, privacy/retention semantics, docs, and regression coverage for the bundled hook or plugin API.

## Reproduction Assessment

Yes. Source inspection on current main shows the bundled handler only accepts command:new/command:reset, while daily/idle rollover emits session_end and maintenance prune removes stale entries without invoking that hook.

## Solution Assessment

Unclear as a final design. The desired preservation behavior is valid, but the best fix needs a maintainer-selected lifecycle contract rather than replaying command hooks into every reset/prune path by default.

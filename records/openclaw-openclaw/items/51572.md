## Label Justifications

- `P2`: The issue affects real memory/session continuity for long-running agents but requires lifecycle/API design rather than emergency runtime repair.
- `impact:session-state`: The reported gap concerns session rollover and maintenance paths that can discard context before memory finalization observes it.
- `impact:data-loss`: Users relying on session-memory can lose transcript context when automatic reset or prune removes the old session without a memory write.
- `impact:security`: The requested automatic hook would persist or expose transcript content during lifecycle cleanup, so sensitive-data handling is part of the issue.

## Summary

Keep open: current main still leaves the core request unsatisfied because bundled session-memory only handles command new/reset events, while automatic daily/idle rollover uses session lifecycle hooks and destructive session-store maintenance prunes entries without a memory-finalization hook.

## What This Changes

The issue requests that bundled session-memory finalization run before automatic daily/idle session rollover and destructive session-store pruning, not only on existing command-driven or compaction-adjacent paths.

## Best Possible Solution

Define a maintainer-approved memory-finalization lifecycle for automatic daily/idle rollover and destructive store pruning, with bounded async behavior, privacy rules, no manual-reset double-fire, docs, and focused regression coverage.

## Reproduction Assessment

Yes, at source level. A stale daily/idle session follows the lazy rollover path that emits session_end/session_start, and bundled session-memory only handles command:new and command:reset; maintenance pruning removes stale entries without a memory hook.

## Solution Assessment

Unclear as a final design. The requested behavior is valid, but the best fix depends on a maintainer-selected lifecycle contract, timeout behavior, privacy policy, and interaction with open partial implementation candidates.

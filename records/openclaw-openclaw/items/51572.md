## Label Justifications

- `P2`: The issue affects memory/session continuity for real users but needs bounded lifecycle design rather than an emergency runtime repair.
- `impact:session-state`: The reported gap concerns session rollover, pruning, transcript lifecycle, and context continuity across session boundaries.
- `impact:data-loss`: Useful session context can be silently dropped when automatic reset or prune paths remove old session state before memory finalization runs.
- `impact:security`: The requested automatic memory capture would persist or expose private transcript content at lifecycle boundaries and needs explicit privacy boundaries.

## Summary

Keep open: current main and the latest release still leave bundled session-memory command-only while automatic daily/idle rollover and destructive maintenance pruning can retire session context without that hook running. The remaining work is real, but it needs maintainer selection of the lifecycle contract, privacy bounds, and overlap with existing candidate PRs.

## What This Changes

Request that session-memory run before automatic daily/idle reset and session maintenance prune paths so context can be preserved before the old session disappears.

## Best Possible Solution

Define and land a maintainer-approved lifecycle contract that covers automatic daily/idle rollover and destructive maintenance prune before data removal, with bounded async behavior, privacy/dedupe rules, docs, and focused regression tests.

## Reproduction Assessment

Yes, at source level. A stale daily/idle session follows the lazy rollover path that emits typed session lifecycle hooks while bundled session-memory only handles command:new and command:reset; maintenance prune removes store entries without a memory-finalization hook.

## Solution Assessment

Unclear as a final implementation. The requested behavior is valid, but the best fix depends on a maintainer-approved lifecycle contract, timeout behavior, privacy semantics, and how to reconcile the open daily/idle candidate.

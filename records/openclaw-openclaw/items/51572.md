## Label Justifications

- `P2`: The issue affects session-memory reliability for automatic lifecycle paths, but it is bounded to memory/session behavior and needs lifecycle design selection.
- `impact:session-state`: The reported gap is about session rollover and prune paths discarding context before memory finalization runs.
- `impact:data-loss`: Users relying on session-memory can lose transcript context when stale sessions reset or prune without a preservation hook firing.
- `impact:security`: The requested automatic capture would persist more transcript content, so privacy and retention boundaries are part of the issue.

## Summary

Keep open: current main and v2026.6.11 still leave the bundled session-memory hook command-scoped, while automatic daily/idle rollover and maintenance prune use separate lifecycle/maintenance paths that do not run that hook.

## What This Changes

The issue requests firing the bundled session-memory preservation path before automatic session reset and stale-session prune paths, not only during command-triggered resets.

## Best Possible Solution

Define one maintainer-approved memory-finalization lifecycle for automatic rollover and destructive prune, with bounded async deadlines, privacy/retention semantics, docs, and regression coverage for the bundled hook or plugin API.

## Reproduction Assessment

Yes. Source inspection shows current main can rotate daily/idle sessions and prune stale store entries while bundled session-memory handles only internal command:new and command:reset events; I did not run a live gateway scenario because this review is read-only.

## Solution Assessment

Unclear. The requested behavior is valid, but the best fix needs a maintainer-selected lifecycle contract rather than replaying command hooks into every reset/prune path by default.

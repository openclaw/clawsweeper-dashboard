## Label Justifications

- `P2`: This is a normal-priority session/memory persistence gap with real user impact but no core outage or first-run blocker.
- `impact:session-state`: The issue concerns session rollover, transcript lifecycle, and memory continuity across reset/prune boundaries.
- `impact:data-loss`: Users relying on session-memory can lose useful transcript context when automatic reset or pruning removes old session state before capture runs.
- `impact:security`: Any reset/prune hook design changes what transcript or tool metadata is persisted or exposed to hook/plugin handlers, so sensitive-data boundaries matter.

## Summary

Keep open: current main and the latest checked stable release still do not run session-memory before automatic daily/idle rollover or destructive session-store pruning, and the open implementation candidates cover only parts of the request while still needing maintainer API/security decisions.

## What This Changes

Request a lifecycle hook or persistence path so session-memory can save context before automatic daily/idle reset and maintenance pruning remove old session state.

## Best Possible Solution

Define a maintainer-approved bounded lifecycle contract that lets session-memory preserve context before automatic daily/idle rollover and destructive maintenance prune, with privacy, dedupe, timeout, docs, and regression coverage.

## Reproduction Assessment

Yes. Source inspection shows automatic daily/idle rollover and maintenance prune paths can remove old session state while bundled session-memory only handles command:new and command:reset; no live gateway scenario was run because this review is read-only.

## Solution Assessment

Unclear as a final design. The requested preservation behavior is valid, but maintainers must choose the reset/prune lifecycle contract, delivery deadline, and privacy semantics before implementation.

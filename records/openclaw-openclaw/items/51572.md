## Label Justifications

- `P2`: The issue reports a real session-memory lifecycle gap with limited blast radius and no current core outage.
- `impact:data-loss`: Session context can be reset or pruned before the configured memory preservation hook sees the outgoing transcript.
- `impact:session-state`: The affected behavior is session rollover, prune retention, transcript handling, and cross-session memory continuity.
- `impact:security`: The requested hook behavior can expose and persist transcript-derived content, so the security and privacy boundary must be explicit.

## Summary

Keep open: current main still has command-only session-memory capture, lifecycle-only automatic daily/idle rollover, and maintenance prune that deletes stale session rows without a pre-delete memory hook. Related reset PRs cover only the daily/idle slice and are not merged, so this broader reset-plus-prune request is still necessary.

## What This Changes

The issue requests firing the session-memory preservation path before idle/daily session rollover and maintenance prune, not only on compaction or manual reset.

## Best Possible Solution

Define a maintainer-approved reset/prune lifecycle preservation contract, then land a focused implementation that covers daily/idle rollover and pre-prune deletion timing, keeps manual reset hooks single-fired, documents the security/privacy semantics, and adds regression coverage for reset plus prune.

Rationale: The source-level gap is clear, but the permanent fix affects plugin-visible hook semantics, transcript exposure, async deletion timing, memory persistence, and potentially security-sensitive content retention, so automation should not choose the contract alone.

Likely owner: steipete

Owner reason: steipete has the strongest current-history signal across pre-compaction memory flush, reset/session initialization, and recent central-path ownership.

Owner confidence: high

Options:

- **Define a typed lifecycle surface (recommended):** Add or extend a session lifecycle hook that explicitly covers before-reset and before-prune with documented payload, timing, timeout, and privacy semantics, then wire session-memory to that contract.
- **Refine the active daily/idle PR first:** Accept the daily/idle reset part through https://github.com/openclaw/openclaw/pull/61675 after rebase/proof and keep prune as a separate follow-up item.
- **Use existing plugin/external memory paths:** Decline new core reset/prune hook behavior and require memory plugins or external snapshot systems to use existing session_end/session_start or continuous-persistence patterns.

## Reproduction Assessment

Yes. Source inspection shows daily/idle stale rollover can create a new session while bundled session-memory only handles command:new and command:reset, and maintenance prune deletes stale rows without a pre-prune memory hook; I did not run a live filesystem rollover in this read-only review.

## Solution Assessment

Unclear as a final design. Persisting before reset/prune is the right end state, but the best fix depends on maintainer choice between synthetic command events, typed lifecycle hooks, before_reset/session_end expansion, or plugin/external memory ownership.

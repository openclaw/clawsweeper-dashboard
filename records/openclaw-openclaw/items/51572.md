## Label Justifications

- `P2`: The issue affects memory/session persistence reliability for real users but needs bounded design work rather than emergency runtime repair.
- `impact:session-state`: The reported gap is about session rollover and pruning paths discarding session context before lifecycle memory finalization runs.
- `impact:data-loss`: Users relying on session-memory can lose transcript context when automatic reset or maintenance prune removes the old session without the bundled hook firing.

## Summary

Keep open: current main still limits bundled session-memory to internal command new/reset events, while automatic daily/idle rollover and session-store maintenance prune use separate lifecycle/store paths. The issue is valid but needs maintainer product/security direction before a fix shape is safe.

## What This Changes

The issue requests firing session-memory finalization before automatic session reset and session-store pruning so session context can be preserved before it is discarded.

## Best Possible Solution

Define a maintainer-approved lifecycle contract for memory finalization before automatic daily/idle rollover and destructive maintenance prune, with bounded async behavior, privacy/dedupe rules, docs, and regression coverage.

## Reproduction Assessment

Yes. Source inspection shows session-memory handles only command new/reset events, while automatic daily/idle rollover and session-store prune use separate lifecycle/store paths; I did not run a live gateway scenario because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the lifecycle contract. The requested behavior is valid, but the best fix depends on event shape, async deadline, plugin ownership, privacy semantics, and how it should overlap with existing session_end/before_reset hooks.

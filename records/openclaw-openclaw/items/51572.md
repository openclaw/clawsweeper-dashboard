## Label Justifications

- `P2`: The issue affects session memory reliability for configured users but needs lifecycle/API design rather than emergency runtime repair.
- `impact:session-state`: The reported gap is specifically about session rollover and pruning discarding context before memory finalization runs.
- `impact:data-loss`: Users relying on session-memory can lose transcript context when automatic reset or prune paths remove the old session without this hook firing.
- `impact:security`: The requested automatic capture changes when sensitive transcript content is persisted to workspace memory files.

## Summary

Keep open: current main and latest release still keep bundled session-memory on command-only events while automatic daily/idle rollover and maintenance prune use separate lifecycle/maintenance paths; the remaining fix needs maintainer-selected hook, timeout, and privacy semantics.

## What This Changes

The issue requests that session-memory finalization run before automatic daily/idle session rollover and destructive maintenance prune, not only on explicit reset/new-style command paths.

## Best Possible Solution

Define a maintainer-approved lifecycle contract for memory finalization before automatic rollover and destructive maintenance prune, then implement bounded, privacy-reviewed behavior with docs and regression coverage.

## Reproduction Assessment

Yes. Source inspection shows the bundled session-memory hook handles only command:new/command:reset while automatic daily/idle rollover and maintenance prune use separate code paths; I did not run a live gateway scenario because this review is read-only.

## Solution Assessment

Unclear. The user-visible need is valid, but directly firing the existing hook everywhere is not necessarily the best fix until maintainers choose the lifecycle event, timeout, dedupe, and privacy contract.

## Label Justifications

- `P2`: The issue affects real session-memory continuity but requires product and security review rather than emergency repair.
- `impact:session-state`: The affected behavior is session rollover, prune lifecycle, previous transcript handling, and continuity across session IDs.

- `impact:security`: The requested lifecycle hook could persist or expose sensitive transcript content at automatic reset and prune boundaries.

## Summary

Keep open: current main and the latest release still keep bundled session-memory on command-style reset events only; automatic daily/idle rollover has only typed lifecycle hooks, maintenance prune has no memory-finalization hook, and the active reset PR covers only part of this issue.

## What This Changes

The issue requests firing session-memory or an equivalent pre-loss memory hook when sessions reset automatically or are pruned by maintenance.

## Best Possible Solution

Define one maintainer-approved lifecycle policy for session reset and maintenance-prune memory preservation, then wire the chosen bounded hook surface with regression tests and docs while avoiding duplicate fires for manual resets.

## Maintainer Decision

Question: Should OpenClaw broaden session-memory or reset lifecycle hooks to automatic daily/idle rollover and maintenance prune, and which event contract should own that behavior?

Rationale: The source-level gap is clear, but the permanent API affects plugin-visible lifecycle semantics, sensitive transcript retention, reset latency, and maintenance-prune timing, so automation should not choose it alone.

Likely owner: steipete

Owner reason: steipete has the strongest combined history across reset behavior, memory-flush policy, and recent lifecycle-hook product decisions.

Owner confidence: high

Options:

- **Define a lifecycle contract first (recommended):** Approve a bounded reset/prune memory-preservation contract, including payload, timeout, dedupe, retention, and security rules, before implementation.
- **Land the reset subset only:** Use https://github.com/openclaw/openclaw/pull/61675 or a replacement for daily/idle rollover and keep maintenance prune as a separate product decision.
- **Keep persistence plugin-owned:** Do not add core session-memory behavior now; ask memory plugins or external services to use existing lifecycle surfaces and only reopen for a concrete missing API.

## Reproduction Assessment

Yes, source-level reproduction is high confidence. Current main can replace stale daily/idle sessions and prune stale session-store entries while bundled session-memory only handles command:new and command:reset.

## Solution Assessment

Unclear as a final design. Reusing the same preservation surface is plausible, but the best fix depends on maintainer choice for event naming, pre-delete timing, async bounds, duplicate suppression, and transcript privacy.

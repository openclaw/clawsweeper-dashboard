## Label Justifications

- `P2`: This is a real session-memory reliability gap with limited blast radius, but it needs lifecycle/API/security choices rather than emergency repair.
- `impact:session-state`: The issue is about session rollover and pruning paths that can discard context before memory finalization runs.
- `impact:data-loss`: Users relying on session-memory can lose transcript context when automatic reset or prune paths remove the old session without the bundled hook firing.

## Summary

Keep open: current main and v2026.6.11 still leave bundled session-memory tied to manual command events while automatic daily/idle rollover and maintenance pruning use separate lifecycle/cleanup paths. The reset half has an open candidate PR, and the prune half overlaps separate hook work, so this needs maintainer lifecycle/security direction rather than cleanup closure.

## What This Changes

Request to fire the bundled session-memory preservation path when sessions are reset by idle/daily policy or pruned by maintenance, not only during existing memory-triggered/manual paths.

## Best Possible Solution

Define and land a maintainer-approved lifecycle contract for pre-reset and pre-prune memory finalization, covering daily/idle rollover, destructive maintenance prune, bounded async behavior, privacy/dedupe rules, docs, and focused regression proof.

## Reproduction Assessment

Yes. Source inspection shows daily/idle rollover can replace the session while only session_end/session_start hooks run, maintenance prune removes entries through store cleanup, and bundled session-memory still handles only command:new and command:reset.

## Solution Assessment

Unclear as a final implementation. The requested behavior is valid, but the best fix depends on a maintainer-approved hook contract, async deadline, privacy policy, and whether reset and prune should share one lifecycle surface.

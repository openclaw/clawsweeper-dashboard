## Label Justifications

- `P2`: This is a bounded memory-network reliability bug with meaningful but limited blast radius.
- `merge-risk: 🚨 compatibility`: The hardcoded fallback can supersede an existing operator-selected batch timeout for callers that do not yet forward it.
- `merge-risk: 🚨 availability`: Legitimate remote memory operations lasting over 120 seconds could begin failing after merge even though they previously remained active.

## Summary

Keep this PR open: the hang is real and the shared-helper direction is sound, but the unconditional 120-second fallback can terminate legitimate batch requests despite a longer configured batch budget, and the external-PR evidence remains test-harness-only.

## What This Changes

The PR adds a 120-second default timeout to memory-host remote HTTP, composes it with caller cancellation, forwards explicit timeout overrides through `postJson`, and adds regression coverage.

## Best Possible Solution

Thread each batch operation's remaining configured deadline into `withRemoteHttpResponse`, retain the 120-second fallback only for callers without an owning product timeout, and prove both paths with focused tests plus a redacted standalone runtime transcript.

## Reproduction Assessment

Yes from source and focused evidence: current memory remote callers can enter guarded fetch without a deadline, and a peer that never writes headers leaves that promise pending. The supplied hung-server tests demonstrate the path, although they were not independently run during this read-only review.

## Solution Assessment

No, not yet. A shared fallback is the right owner boundary, but the best fix must first honor the existing configured batch deadline for batch-owned calls instead of imposing the fallback universally.

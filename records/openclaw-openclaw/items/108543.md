## Label Justifications

- `P1`: An unsafe upgrade sequence can break APNs-backed wake and approval delivery for existing paired iOS users.
- `merge-risk: 🚨 compatibility`: The PR replaces a shipped persistent JSON authority with SQLite and requires operator migration before old registrations remain available.
- `merge-risk: 🚨 message-delivery`: Merging without a guaranteed migration gate can suppress APNs wake and approval notifications by making existing registrations appear absent.

## Summary

Keep this PR open, but do not merge yet: the SQLite migration architecture is aligned with the database-first policy, while the current patch leaves a source-reproducible upgrade gap where existing APNs registrations can become silently unavailable unless Doctor ran before the gateway begins using the new store.

## What This Changes

Moves APNs direct and relay registrations from the legacy JSON sidecar into shared Kysely-backed SQLite, adding tombstones, an explicit Doctor migration, schema updates, and migration-focused tests.

## Best Possible Solution

Keep one SQLite authority, but add an actionable startup or upgrade preflight that refuses to treat an existing legacy APNs file as an empty store, then prove a real v2026.7.1-to-head Doctor migration, restart, direct/relay push, invalidation, and cleanup flow.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, from source and the described upgrade contract: start with a shipped JSON-only APNs registration, upgrade without running Doctor, and the new SQLite-only loader has no canonical row to return. A live upgrade run is still needed as merge proof.

## Solution Assessment

Not yet. Moving durable APNs state to shared SQLite with Doctor-owned migration is the correct boundary, but the safest implementation also prevents an unmigrated legacy file from being mistaken for no registration.

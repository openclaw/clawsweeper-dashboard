## Label Justifications

- `P1`: Default Telegram long turns can leave a group unresponsive and then abort otherwise healthy reply work after the 25-minute spooled handler timeout.
- `impact:message-loss`: Same-lane inbound Telegram messages are held upstream of session admission, and timeout recovery can fail the active spooled update instead of delivering a normal reply path.
- `impact:session-state`: The transport lane prevents mid-turn Telegram messages from entering active session queue or steering admission while a reply operation is running.

## Summary

Keep open: current main and the latest release still hold the Telegram isolated-ingress lane across the full update handler, and the protected maintainer label plus replay/ordering blast radius make this a maintainer design item rather than cleanup-close material.

## What This Changes

The issue requests decoupling Telegram isolated ingress lane ownership from full agent-turn execution so same-chat/topic updates can reach session admission during long turns.

## Best Possible Solution

Define a Telegram ingress handoff contract that releases the per-chat/topic spool lane after durable session-admission handoff, preserves replay safety and control-lane escapes, and splits claude-cli steering/progress gaps into narrower follow-ups.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Telegram isolated ingress release the per-chat/topic spool lane after durable handoff to session admission instead of after the full agent turn completes?

Rationale: The source-level bug is clear, but the permanent fix changes Telegram transport ordering, duplicate/replay safety, timeout semantics, and downstream session admission ownership, so maintainers need to choose the contract before automation edits code.

Likely owner: obviyus

Owner reason: They are the current assignee and authored the related run-lifecycle work that frames the downstream session-admission contract.

Owner confidence: high

Options:

- **Detach After Durable Handoff (recommended):** Move the Telegram spool lane lifetime to ingestion/classification plus durable session handoff, then let session admission own active-run ordering and steering.
- **Keep Lane Ownership And Narrow Mitigations:** Preserve the current one-handler-per-lane model and tune timeout, progress, or error visibility while accepting that same-lane messages still cannot reach steering during a long turn.
- **Split Into Narrow Follow-Ups:** Track handler-timeout visibility, collect starvation, and claude-cli queueMessage support separately while keeping this issue as the lane-ownership design decision.

## Reproduction Assessment

Yes, at source level: current main awaits the full Telegram update handler while marking the lane active, blocks later same-lane spooled updates, and has tests expecting timeout failure behavior. I did not run a live Telegram long-turn reproduction in this read-only review.

## Solution Assessment

Unclear until maintainer design review: detaching after durable handoff appears to be the right ownership direction, while only tuning the timeout would leave same-lane steering blocked. The chosen solution must preserve Telegram replay, tombstone, ordering, and reply-fence contracts.

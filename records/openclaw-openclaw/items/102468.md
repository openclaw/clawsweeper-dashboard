## Label Justifications

- `P1`: Default Telegram long turns can leave a group unresponsive and then abort otherwise healthy reply work after the 25-minute spooled handler timeout.
- `impact:message-loss`: Same-lane inbound messages are held upstream of session admission, and timeout recovery can fail the active spooled update rather than deliver a normal reply path.
- `impact:session-state`: The transport lane prevents mid-turn Telegram messages from entering the active session queue or steering admission while a reply operation is running.

## Summary

Keep open: current main still holds a Telegram isolated-ingress lane while the full agent turn runs, and the protected `maintainer` label plus the replay/ordering blast radius make this a design item for owner review rather than cleanup closure.

## What This Changes

The issue asks to detach Telegram isolated-ingress lane ownership from full agent-turn execution so same-chat messages can reach session-level admission during long turns and healthy long turns are not killed by the 25-minute handler timeout.

## Best Possible Solution

Define a Telegram ingress handoff design that completes the spooled lane claim after durable handoff to session admission, while preserving replay safety, control-lane escapes, reply-fence cleanup, crash/restart behavior, and live Telegram proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Telegram isolated ingress release the per-chat/topic spool lane after durable handoff to session admission instead of after the full agent turn completes?

Rationale: The source-level bug is clear, but the permanent fix changes Telegram transport ordering, duplicate/replay safety, timeout semantics, and downstream session admission ownership, so maintainers need to choose the contract before automation edits code.

Likely owner: obviyus

Owner reason: They are assigned to this issue and have recent authorship on both the Telegram spooled-update lifecycle and the related run-lifecycle design work.

Owner confidence: high

Options:

- **Detach After Durable Handoff (recommended):** Move the Telegram spool lane lifetime to ingestion/classification plus durable session handoff, then let session admission own active-run ordering and steering.
- **Keep Lane Ownership And Tune Timeout:** Preserve the current one-handler-per-lane model and only adjust watchdog/user feedback, accepting that same-lane messages still cannot reach steering during a long turn.
- **Split Into Narrow Follow-Ups:** Track handler-timeout visibility and collect starvation separately while leaving this issue as the umbrella design decision for lane ownership.

## Reproduction Assessment

Yes, at source level: current main awaits the full Telegram update handler while marking the lane active, blocks later same-lane spooled updates, and has tests expecting timeout failure behavior. I did not run a live Telegram long-turn reproduction in this read-only review.

## Solution Assessment

Unclear until maintainer design review: detaching after durable handoff appears to be the right ownership direction, but it must preserve Telegram replay, tombstone, ordering, and reply-fence contracts.

## Label Justifications

- `P1`: Default Telegram long turns can leave same-chat/group messages stuck upstream of session admission and then abort otherwise healthy reply work at the spooled handler timeout.
- `impact:message-loss`: Same-lane inbound messages are held at the Telegram transport layer and can miss the session steering path before handler-timeout recovery fails the active update.
- `impact:session-state`: The transport lane currently defeats session-level active-run, followup, and steering invariants while a reply operation is running.

## Summary

Keep open: current main and the latest release still hold a Telegram isolated-ingress lane while the awaited bot handler can run the full agent turn, and the protected `maintainer` label plus replay/ordering/watchdog blast radius make this a maintainer design item rather than cleanup closure.

## What This Changes

The issue asks to detach Telegram isolated-ingress lane ownership from long agent-turn execution so same-chat updates can reach session-level steering and healthy long turns are not killed by the 25-minute ingress handler watchdog.

## Best Possible Solution

Define a Telegram ingress handoff contract that completes the spooled lane claim after durable session-admission handoff, while preserving replay safety, control-lane escapes, reply-fence cleanup, crash/restart behavior, and live Telegram proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Telegram isolated ingress release the per-chat/topic spool lane at durable dispatch handoff instead of holding it for the full agent turn, and what contract should own replay, ordering, and timeout recovery after that handoff?

Rationale: The source-level failure is clear, but the permanent fix changes Telegram transport ordering, duplicate/replay safety, timeout semantics, and downstream session admission ownership, so maintainers need to choose the contract before implementation.

Likely owner: obviyus

Owner reason: They are assigned to this issue and have the strongest recent history on the current Telegram lane code and adjacent run-lifecycle work.

Owner confidence: high

Options:

- **Detach after durable handoff (recommended):** Move Telegram spool lane lifetime to ingestion/classification plus durable session handoff, then let session admission own active-run ordering and steering.
- **Keep lane ownership:** Preserve one-handler-per-lane through the full turn and address only watchdog, visibility, or dead-letter symptoms.
- **Split narrower follow-ups:** Track timeout visibility, collect starvation, and claude-cli steering injection separately while leaving this issue as the lane-ownership design decision.

## Reproduction Assessment

Yes, at source level: current main awaits the full Telegram update handler while marking the lane active, blocks later same-lane spooled updates, and has tests preserving same-lane blocking until the active handler settles. I did not run a live Telegram long-turn reproduction in this read-only review.

## Solution Assessment

Unclear until maintainer design review: detaching after durable handoff appears to be the right ownership direction, but it must preserve Telegram replay, tombstone, ordering, and reply-fence contracts. A timeout-only or progress-only fix would not solve the transport lane preventing session admission from seeing mid-turn messages.

## What This Changes

This PR changes Doctor’s system-Node warning so a failed version probe is reported separately from a known unsupported installed Node version.

## System Context

Doctor checks the system Node executable and its runtime capabilities before OpenClaw installs or reports the daemon runtime. The result becomes either a silent supported-runtime result or an operator-facing warning that identifies the selected daemon runtime and the remediation path.

## Architecture Diagram

  C -->|Known unsupported version| F[Supported-range warning]
  E --> G[Doctor or gateway setup output]
  F --> G

## Best Possible Solution

Retain the explicit null-version diagnostic branch, land it after final exact-head checks, and keep the existing unsupported-version and SQLite-safety branches as the single compatibility decision path.

Yes, source-reproducible: the warning helper receives a system Node record with `version: null` after the runtime probe cannot identify a version, and the PR adds a direct regression case for that input. The submitted focused test evidence reports the changed behavior passing on the PR head.

## Solution Assessment

Yes. Splitting the null-version state before the known-version compatibility checks is the narrowest maintainable fix: it avoids falsely describing an unavailable probe as a detected unsupported version while preserving the existing range and SQLite-safety logic.

- `impact:security`: The issue concerns whether a scheduled isolated run can receive a workspace-mutating tool that the job's explicit tool list did not name.

## Summary

Keep open for maintainer review: current main still lets a cron `toolsAllow` entry of `write` match `apply_patch`, but that comes from an intentional global tool-policy rule rather than a simple default-union bug.

## What This Changes

The issue asks OpenClaw to treat explicit cron `toolsAllow` as an exclusive concrete tool list so `apply_patch` is not added when it was omitted.

## Best Possible Solution

Maintainers should choose and document one cron contract, then align `capCronAgentTurnToolsAllow()`, cron CLI/MCP docs, and regression tests with that contract.

- **Make cron toolsAllow concrete (recommended):** Treat explicit cron `toolsAllow` entries as exact normalized tool ids after group expansion, so `write` no longer implies `apply_patch` for cron payload persistence, with docs and tests updated.
- **Keep policy semantics:** Keep `write` granting `apply_patch` everywhere and update cron docs/CLI wording so users know `apply_patch` must be excluded through broader policy rather than an omitted cron allow entry.
- **Add a cron deny surface:** Add a separate per-cron deny or restriction surface so users can keep `write` while explicitly denying `apply_patch`, accepting the extra API/config surface.

## Reproduction Assessment

Yes, source-reproducible on current main: when the creator surface includes `apply_patch`, a cron payload containing `write` but omitting `apply_patch` is filtered through a matcher that treats `write` as allowing `apply_patch`. I did not run a live Windows cron in this read-only review.

## Solution Assessment

Unclear until maintainers choose the intended security contract. A narrow code change in `capCronAgentTurnToolsAllow()` is plausible, but current tests and docs deliberately preserve the global `write` to `apply_patch` allow rule.

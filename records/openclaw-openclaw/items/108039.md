## Label Justifications

- `P1`: Incorrect Mattermost root handling can visibly misroute real threaded replies and break an active channel workflow.
- `merge-risk: 🚨 message-delivery`: The patch changes root selection for every threaded Mattermost send and can silently move replies to channel top level on lookup failure.

## Summary

The central bug is real and the identifier split is the right direction, but the outbound resolver can silently flatten an intended threaded reply when its new lookup fails, and the external PR still lacks after-fix live Mattermost proof.

## What This Changes

The PR separates Mattermost thread roots from generic reply IDs, resolves child posts to their root for outbound sends, and hydrates inbound thread-starter and reply context.

## Best Possible Solution

Keep `threadId` as the canonical Mattermost root without refetching it, resolve only ambiguous generic reply IDs, fail rather than silently flatten when a required root cannot be established, and retain best-effort inbound context hydration with redacted live proof.

## Reproduction Assessment

Yes, at source level with high confidence: current main can pass a child reply identifier toward Mattermost `root_id`, while Mattermost rejects non-root posts as thread roots. No live current-main run was performed.

## Solution Assessment

No, not yet. Separating `threadId` from `replyToId` is the correct boundary, but refetching a canonical thread root and silently dropping it on lookup failure is less safe than trusting explicit roots and failing closed for unresolved generic replies.

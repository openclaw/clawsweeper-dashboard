## Summary

Keep open: current main and latest release still create a Feishu document with title only when `content` is supplied, and the remaining choice is the Feishu tool contract plus partial-failure behavior.

## What This Changes

The issue requests that `feishu_doc` `create` stop silently dropping supplied `content`, preferably by creating and populating the document in one call.

## Best Possible Solution

Adopt one Feishu plugin contract: preferably support create-time content through the existing write path with explicit partial-failure handling and live Feishu proof, or reject `content` on create with a clear error and matching tests/docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `feishu_doc` `create` support initial `content`, or should supplied `content` be rejected as unsupported?

Rationale: Both fixes are mechanically small, but they define the user-facing Feishu tool contract and the create-then-write partial-failure semantics, so automation should not choose the product behavior alone.

Likely owner: Takhoffman

Owner reason: They have direct history in the create branch contract and were already pulled into the prior create-with-content discussion.

Owner confidence: high

Options:

- **Support create-time content (recommended):** Create the document, write supplied markdown through the existing write path, and preserve created metadata or roll back if the write step fails.
- **Reject content on create:** Keep `create` title-only but fail clearly when callers supply `content`, with docs and tests that point users to create then write.
- **Defer the contract:** Leave the issue open while maintainers defer the behavior choice, but do not close it as fixed because direct calls can still silently drop content.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path for direct or flattened-provider calls that include `content`: the `create` branch returns after `createDoc` and does not write or reject that value.

## Solution Assessment

No, the current behavior is not the best solution. Maintainers should choose either create-plus-write with explicit partial-failure handling or a clear unsupported-parameter rejection, rather than preserving silent ignore behavior.

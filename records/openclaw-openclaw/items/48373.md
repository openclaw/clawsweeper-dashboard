## Summary

Keep open: current main and the latest release still route Feishu document creation through `createDoc` without writing supplied content, and the remaining decision is whether maintainers want one-call create-and-write semantics or explicit rejection of create-time content.

## What This Changes

Requests that `feishu_doc` creation stop silently discarding a supplied `content` parameter, preferably by creating and populating the document in one tool call.

## Best Possible Solution

Remove the silent-drop path by making a maintainer-owned contract choice: either land create-then-write with focused tests and recoverable failure details, or reject create-time content clearly at the tool boundary.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `feishu_doc` support one-call create-with-content, or should create-time content be rejected and documented as a two-step create/write workflow?

Rationale: Both choices fix the silent drop, but they define different Feishu tool semantics and recovery expectations after a partial create/write failure.

Likely owner: m1heng

Owner reason: The Feishu plugin is documented as community maintained by @m1heng, and this is a Feishu tool contract choice.

Owner confidence: medium

Options:

- **Support create with content (recommended):** Land the create-then-write path only with schema coverage, focused tests, and a response/error shape that preserves created document identity when possible.
- **Reject content on create:** Keep create as title-only and make supplied content fail fast with docs/skill text pointing agents to the explicit write action.

## Reproduction Assessment

Yes from source inspection: current `main` calls only `createDoc` in the `create` branch, while content writes are implemented only in separate write-style branches. I did not run a live Feishu API call in this read-only cleanup review.

## Solution Assessment

Unclear until maintainers choose the contract. The linked create-then-write approach is a plausible narrow UX fix, but explicit rejection is the safer alternative if create should remain title-only.

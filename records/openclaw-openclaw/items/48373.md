## Summary

Keep open: current main and the latest release still create a Feishu document by calling `createDoc` only, so supplied body content is neither written nor clearly rejected; related same-repo fixes are closed unmerged and the open fork PR has not landed in the target repository.

## What This Changes

The issue reports that `feishu_doc` `create` accepts a `content` argument but returns success after creating a title-only document.

## Best Possible Solution

Adopt one Feishu plugin contract: preferably support create-time markdown through the existing write path with explicit partial-failure handling and live Feishu proof, or reject `content` on create with a clear error plus matching docs/tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `feishu_doc` `create` support initial `content`, or should supplied `content` be rejected as unsupported?

Rationale: Both choices are mechanically small, but they define the user-facing Feishu tool contract and the recovery semantics when create succeeds but the follow-up write fails.

Likely owner: Takhoffman

Owner reason: They worked in the same create-branch contract area and were already pulled into the prior create-with-content discussion.

Owner confidence: high

Options:

- **Support create-time content (recommended):** Create the document, write supplied markdown through the existing write path, and preserve created metadata or roll back if the write step fails.
- **Reject content on create:** Keep `create` title-only but fail clearly when callers supply `content`, with docs and tests pointing users to create then write.
- **Defer the contract:** Keep the issue open until maintainers choose the Feishu tool behavior, without treating the current silent ignore as fixed.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path for direct or permissive tool calls that include `content`: the `create` branch returns after `createDoc` and does not write or reject that value.

## Solution Assessment

No, the current behavior is not the best solution. Maintainers should choose either create-plus-write with explicit partial-failure handling or a clear unsupported-parameter rejection, rather than preserving silent ignore behavior.

## Summary

Keep open: current main and v2026.6.11 still route Feishu document creation through `createDoc` only, while content-writing remains in the separate `writeDoc` path. The remaining maintainer choice is whether `create` should support initial content or reject that argument clearly.

## What This Changes

The issue asks Feishu document creation to stop silently accepting a `content` argument that produces an empty document, either by writing the content or rejecting it.

## Best Possible Solution

Have maintainers define the Feishu `create` contract, then either add tested create+write support with recoverable partial-failure output or fail fast with a clear unsupported-argument error.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Feishu `feishu_doc` `create` support an optional `content` field, or should OpenClaw explicitly reject `content` for `create` and document the two-step workflow?

Rationale: Current main no longer documents `content` on `create`, but the runtime path can still silently drop an unexpected content value; choosing write-on-create versus fail-fast rejection is a user-facing tool contract decision.

Likely owner: Takhoffman

Owner reason: They recently owned Feishu doc-create security behavior and were already pulled into the create-with-content discussion.

Owner confidence: high

Options:

- **Support create with content (recommended):** Add `content` to the create schema, call the existing markdown write path after creation, and return enough partial-failure detail for recovery if the write step fails.
- **Reject content on create:** Keep creation title-only, tighten validation or add an explicit runtime error for `content`, and document `create` followed by `write` as the supported workflow.

## Reproduction Assessment

Yes, by source inspection: current main's `create` branch never reads `p.content` and only calls `createDoc`, while `writeDoc` is separate. I did not run a live Feishu API reproduction because credentials and external service proof are not available in this read-only review.

## Solution Assessment

Unclear: create+write is a plausible user-friendly fix, but fail-fast rejection is also valid now that the current schema/docs do not define `content` for `create`. Maintainers should choose the tool contract before another repair PR lands.

Keep open: current main and the latest release still do not write or reject create-time content for `feishu_doc`, and the same-repository fix attempts are closed unmerged; maintainers still need to choose the Feishu create contract.

## What This Changes

Request that `feishu_doc` create with a supplied `content` value either populate the new document or stop silently accepting and dropping that content.

## Best Possible Solution

Adopt one Feishu plugin contract: support create-time markdown through the existing write path with partial-failure handling and live proof, or reject supplied content on create with a clear error plus matching tests/docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `feishu_doc` create support initial `content` by writing it immediately, or should supplied `content` be rejected as unsupported?

Rationale: Both repair shapes are mechanically small, but they define the user-facing Feishu tool contract and the partial-failure semantics after a document has already been created.

Likely owner: Takhoffman

Owner reason: They merged or authored adjacent Feishu create-contract changes and were already pulled into prior create-with-content discussion.

Owner confidence: high

Options:

- **Support create-time content (recommended):** Create the document, write the supplied markdown through the existing write path, and preserve created metadata or roll back if the write step fails; this best matches the reporter's expectation.
- **Reject content on create:** Keep create title-only but fail clearly when callers supply `content`, with tests and docs pointing users to create then write.
- **Defer the contract choice:** Keep this issue open while maintainers defer the behavior decision, because silent success with dropped content remains unresolved.

## Reproduction Assessment

Yes. Source inspection shows provider-facing union flattening can expose `content` with `action: "create"`, and the current dispatcher returns after `createDoc` without writing or rejecting that value.

## Solution Assessment

No. The current behavior is not the best solution; maintainers should choose either create-plus-write with explicit partial-failure handling or a clear unsupported-parameter rejection.

## Summary

Keep open: current main still has memory diagnostics and configuration docs, but onboarding, setup, configure, and Crestodian do not provide a first-class memory embedding setup/readiness step, and the mandatory-versus-optional policy remains a product decision.

## What This Changes

Request to add a mandatory onboarding/configure step for memorySearch embedding provider, model, API key or SecretRef setup, and readiness verification.

## Best Possible Solution

Add a maintainer-approved memory setup/readiness path in onboarding and configure that uses existing memorySearch and SecretRef surfaces, verifies readiness, documents the chosen mandatory-versus-optional policy, and preserves an explicit FTS-only/no-network path.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should first-run onboarding and openclaw configure treat memory embedding setup as mandatory, prominently optional, or diagnostic-only, and what credential/probe UX should it use?

Rationale: The missing setup surface is clear in current main, but requiring embeddings changes first-run completion, provider cost/network assumptions, SecretRef/plaintext handling, daemon environment expectations, and FTS-only workflows, so automation should not choose the policy.

Likely owner: Takhoffman

Owner reason: Takhoffman is the current issue assignee and participated in the product-scope discussion on this exact setup behavior.

Owner confidence: medium

Options:

- **Prominent Optional Setup (recommended):** Add a visible but skippable memory setup/readiness step that writes existing memorySearch provider/model and SecretRef or API-key config, then points users to memory status verification.
- **Mandatory Memory Gate:** Require users to configure embeddings or explicitly choose FTS-only before onboarding completes, improving recall readiness at the cost of first-run friction and provider dependency.
- **Diagnostic Only:** Keep onboarding lean and rely on doctor, memory status, and documentation, accepting that some users may miss memory readiness until after setup.

## Reproduction Assessment

Yes, at source level. The setup, onboarding, configure, and Crestodian orchestrators still lack a dedicated memorySearch credential/readiness step, and the docs list no memory step in onboarding.

## Solution Assessment

Partly. A first-class memory setup/readiness flow is the maintainable direction, but making it universally mandatory is not yet proven best across FTS-only, local, headless, and no-network setups.

## Summary

Keep open: current main still lacks a first-run or configure path for memory embedding setup, and the remaining mandatory-versus-optional policy is a maintainer product decision rather than conservative cleanup.

## What This Changes

The issue requests a prominent mandatory onboarding step to configure and verify `memorySearch` embedding provider, model, and credentials.

## Best Possible Solution

Add a maintainer-approved memory setup/readiness path in onboarding and `openclaw configure` that writes existing `memorySearch` or SecretRef config, verifies readiness, and documents the chosen mandatory-versus-optional policy.

Required: true

Rationale: The missing setup surface is clear, but mandatory embeddings affect first-run completion, provider cost, credential storage, daemon environment behavior, local/FTS-only workflows, and security posture.

Owner confidence: medium

Options:

- **Prominent Optional Setup (recommended):** Add a visible skippable memory setup/readiness path that configures the existing provider/model and SecretRef or API-key fields, then verifies with a probe or memory status guidance.
- **Mandatory Memory Gate:** Require users to configure embeddings or explicitly choose FTS-only before onboarding completes, improving recall readiness at the cost of first-run friction.
- **Diagnostic Only:** Keep onboarding lean and rely on doctor, status, and memory CLI guidance, accepting that some users may miss memory readiness until later.

## Summary

Keep open: current main and v2026.6.11 have adjacent progress drafts, task-ledger states, and channel busy snapshots, but they still do not provide the requested persistent per-channel-turn status object with durable done, failed, unknown, or interrupted semantics.

## What This Changes

The issue requests a first-class persistent task-status surface for long-running channel turns, starting with Discord, with explicit terminal and unknown/interrupted states.

## Best Possible Solution

Define an additive runtime-owned channel-turn status contract that reuses progress/session/task signals, persists only the ownership needed to fail closed to unknown or interrupted, and projects first to Discord as best-effort transport.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a persistent channel-turn status surface now, and should its canonical owner be the runtime/session layer, the task ledger, or the channel progress-draft transport?

Rationale: The remaining work is not a small bug fix; it chooses user-visible terminal semantics, restart ownership, channel rollout, and how several existing status surfaces avoid becoming competing sources of truth.

Likely owner: steipete

Owner reason: The strongest adjacent history is in progress drafts, Discord preview transport, and channel streaming surfaces, while the decision still needs coordination with task/status owners.

Owner confidence: medium

Options:

- **Design a runtime-owned status contract (recommended):** Create a generic run/session status owner first, then let Discord render it as a best-effort editable status message without making progress drafts or task records the source of truth.
- **Narrow to progress-draft enhancement:** Treat the feature as Discord progress-draft UX only, accepting that unknown/interrupted durability remains out of scope until a later runtime state model exists.
- **Defer behind session activity work:** Keep this issue open but wait for the broader session activity API to define canonical run-state semantics before adding channel-visible status messages.

Unclear as a concrete implementation plan. The one-message status model is plausible, but maintainers need to choose ownership, persistence, restart semantics, and channel rollout before code work is safe.

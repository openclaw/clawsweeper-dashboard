## Summary

Keep open: current main and the latest release still contain the OpenAI transport predicate that can rewrite explicit `api: "openai-completions"` config to `openai-responses`. The linked fix PR is open and unmerged, so this issue should close only after a reviewed fix lands.

## What This Changes

The issue reports that `openai/*` model routing ignores provider-level and per-model `api: "openai-completions"` config and forces Responses transport, causing OpenAI fallback runs to hang until timeout.

## Best Possible Solution

Land a source-aware OpenAI provider transport fix that respects explicit provider/per-model `openai-completions` config while preserving default native OpenAI Responses routing, then close this issue after the fix merges.

## Reproduction Assessment

Yes. Source inspection shows configured provider/per-model API values flow into OpenAI transport normalization, where explicit `openai-completions` can be rewritten to `openai-responses`; I did not run a live OpenAI request in this read-only review.

## Solution Assessment

No, not as currently proposed by the open PR. The right boundary is the OpenAI provider transport helper, but the final fix should distinguish explicit user config from catalog/default OpenAI rows rather than broadly inverting the predicate.

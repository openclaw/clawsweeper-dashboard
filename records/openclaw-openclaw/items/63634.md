## Summary

This PR is still necessary because current main still uses the strict MCP SDK `listTools()` path for bundle MCP cataloging, but the current patch is not merge-ready: it rebuilds the SDK metadata cache per page and the branch is conflicting with current main.

## What This Changes

The PR changes bundle MCP tool cataloging to accept `tools/list` entries whose root `inputSchema.type` is missing, normalize accepted schemas, skip explicit non-object roots, and add bundle MCP regression coverage.

## Best Possible Solution

Keep the relaxed single-response parse, but rebuild MCP SDK metadata once from the final accepted tool set after pagination and filtering, then rebase onto current main for maintainer review of the private SDK seam.

## Reproduction Assessment

Yes by source inspection: current main calls the strict MCP SDK `client.listTools()` in the bundle MCP catalog path, while the pinned SDK requires root `inputSchema.type` to be the literal `object`. I did not run a live repro in this read-only review.

## Solution Assessment

No. The relaxed single-response validation is the right direction, but metadata caching needs to run on the final accepted tool set rather than each page, and the conflict with current main must be resolved before this is mergeable.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.88

Full review comments:

- **[P1] Cache metadata after collecting every accepted page:** `src/agents/agent-bundle-mcp-runtime.ts:327`
  - body: `cacheToolMetadata()` clears the SDK's output-schema and task metadata caches before rebuilding them. Calling it inside the pagination loop means page 2 erases validators and required-task guards for page 1 tools that remain in the OpenClaw catalog, so newly accepted typeless tools on earlier pages can later be called without the SDK checks this PR is trying to preserve. Build the final accepted tool set first, then rebuild the cache once from that set.
  - confidence: 0.88

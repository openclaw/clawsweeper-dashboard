## Summary

Keep open: current main and v2026.6.11 still only guide users through IPv4/self-loop CDP failures, while the reported IPv4-vs-IPv6 Windows/WSL2 case remains unaddressed and the attempted fix was closed unmerged for overbroad Chrome-version wording.

## What This Changes

The issue asks OpenClaw to document and diagnose Windows/WSL2 Chrome CDP cases where Windows Chrome answers on IPv6 loopback and a v4tov4 portproxy returns empty replies.

## Best Possible Solution

Land a maintainer-approved docs and diagnostic update that tells users to check Windows netstat/curl for the IPv4-vs-IPv6 CDP split and use v4tov6 only when Windows Chrome is actually listening on ::1, without universal Chrome-version claims or a misleading WSL-side IPv6 probe.

## Reproduction Assessment

Yes for the source-level OpenClaw gap: current main still has only the self-loop empty-reply hint and IPv4-only WSL2 guide checks, while the reports give Windows curl/netstat evidence for the IPv6 split. I did not run a live affected Windows/WSL2 Chrome host in this read-only review.

## Solution Assessment

Unclear until maintainers approve the exact wording and proof bar. A scoped docs and diagnostic hint for the observed netstat/curl split is the best direction; an automatic WSL-side [::1] probe or universal Chrome-version claim is not.

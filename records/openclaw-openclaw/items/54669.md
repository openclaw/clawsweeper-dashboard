## What This Changes

The issue asks OpenClaw to document and diagnose Windows/WSL2 Chrome CDP failures where Chrome answers on IPv6 loopback and an IPv4 `v4tov4` portproxy returns empty replies.

## Best Possible Solution

Land a narrow docs and diagnostic update that tells users how to distinguish the self-loop portproxy case from an IPv4/IPv6 CDP split and when `v4tov6` is appropriate, without adding a misleading WSL-side `[::1]` auto-probe or a universal Chrome-version claim.

## Reproduction Assessment

Yes for the OpenClaw source gap: current docs, diagnostics, and tests still omit the reported `[::1]`/`v4tov6` path. I did not reproduce the actual Windows/WSL2 Chrome binding on live hardware in this read-only review.

## Solution Assessment

Yes, if scoped carefully: docs plus actionable diagnostic wording is the maintainable fix. A blanket Chrome-version claim or automatic probe of `[::1]` from WSL2 is not the best solution because WSL loopback is not the Windows Chrome listener.

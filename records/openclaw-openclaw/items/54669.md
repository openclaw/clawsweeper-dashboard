The issue requests WSL2/Windows browser CDP docs and diagnostics for Chrome listening on IPv6 [::1] so v4tov4 portproxy failures do not stay silent.

Land a scoped docs and diagnostic update that tells users how to distinguish IPv4 self-loop failures from Windows Chrome listening on [::1] and when to use v4tov6, without claiming every Chrome 136+ install is IPv6-only or adding a misleading WSL-side [::1] probe.

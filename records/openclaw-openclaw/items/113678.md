## Summary

Keep this issue open. The reported outbound-listener loss closely overlaps the runtime-context failure fixed by https://github.com/openclaw/openclaw/pull/110762, but that merged work specifically covers plugin registry reloads; the supplied report describes forced status-499 watchdog reconnects and gateway restarts, so current `main` coverage of this lifecycle remains unproven.

## What This Changes

Repair the WhatsApp watchdog reconnect path so a non-logout `app-silent` reconnect preserves both inbound handling and the active outbound listener for the affected account.

## System Context

The WhatsApp channel owns a live connection controller for each linked account. The watchdog can close and reconnect a quiet connection, after which inbound processing and outbound delivery both depend on the replacement controller being registered in the shared runtime context.

  F --> G[Reply or queued delivery]

## Best Possible Solution

Trace the forced status-499 reconnect through controller replacement and runtime-context registration, then add a regression test proving that the affected account has an active outbound listener after reconnect without a QR/login flow.

## Label Justifications

- `P2`: This is a real exec-output visibility bug with workarounds and a limited core tool-result surface, not a crash loop or total runtime outage.
- `impact:data-loss`: Current source inspection shows exec output characters can be silently dropped before the result is stored or shown.
- `impact:session-state`: Exec output is appended into session/process state only after sanitization, so the session transcript can diverge from what the command actually emitted.

## Summary

Keep open: current main still strips ESC and other non-tab/newline/carriage-return C0 controls before exec output is appended or rendered, so the central sanitizer bug is not fixed. The safe repair needs maintainer judgment on the display policy because preserving raw controls could reintroduce terminal/log spoofing; a visible escaped-text fallback is the safer direction.

## What This Changes

The issue reports that `sanitizeBinaryOutput` removes low ASCII control characters from exec output, making ANSI/SSH/control-byte-heavy output invisible or placeholder-like instead of model-readable text.

## Best Possible Solution

Define a display-safe exec-output normalization policy that keeps legitimate terminal output model-readable by escaping unsafe controls, then add focused coverage for ANSI/SSH/control-byte output through the shared exec sanitizer and result-rendering path.

## Reproduction Assessment

Yes for the sanitizer behavior: current main drops ESC and other non-tab/newline/carriage-return C0 controls before appending exec output. The full SSH/image-placeholder rendering symptom still needs live reproduction or a focused regression test.

## Solution Assessment

Unclear as written: preserving raw ANSI/ESC is not the safest fix. The better solution is a display-safe escaped text fallback at the shared exec-output normalization boundary, with tests proving legitimate output remains visible without raw terminal-control injection.

## Summary

Keep open. The report identifies a concrete cron/session-state race that is not shown to be solved on current main: the merged admission protection covers identities after admission, while the reported create-to-claim gap and deletion-versus-takeover handling remain distinct. The related open PR addresses the unsatisfiable-cap deletion trigger, but it does not establish recovery from other loss of the cron row.

## What This Changes

Prevent isolated cron startup from losing a newly created session row to maintenance before admission, and handle a missing row differently from an ownership change.

## System Context

Isolated cron runs create a durable session entry before claiming lifecycle admission to run agent work. Session-store maintenance can prune entries during unrelated writes, and the admission step decides whether cron execution may proceed.

## Architecture Diagram

flowchart LR
  A[Isolated cron job] --> B[Create session row]
  B --> C[Preparation window]
  D[Unrelated session write] --> E[Session maintenance]
  E --> F[Session store]
  C --> G[Claim work admission]
  F --> G
  G -->|row intact| H[Run cron payload]
  G -->|row missing or ownership changed| I[Startup failure or recovery]

## Best Possible Solution

Make admission protection cover the cron session from its initial write through claim, then retain the ownership-mismatch stand-down while treating an absent row through a bounded recreate-and-retry path with regression coverage.

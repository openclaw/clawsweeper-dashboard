## Summary

Keep open: the latest head fixes the simple changed-pricing path, but it can still collapse an existing mixed v4 cache to the first entry's fingerprint and then strip the remaining per-entry fingerprints, making stale cost totals reload as fresh.

## What This Changes

The PR stores the usage-cost cache pricing fingerprint once at the cache-file level, strips it from serialized entries, restores it on load, clears entries when the cache-level fingerprint changes, and adds a cold round-trip test.

## Best Possible Solution

Land one canonical fix that stores the fingerprint once while either dropping old v4 caches or validating every old entry fingerprint before stripping, with regression coverage for mixed old-format checkpoint caches.

## Reproduction Assessment

Yes, source-level: construct a version-4 cache with mixed per-entry fingerprints where the first entry matches the current pricing and a later entry does not; the PR can lift the first fingerprint to the file level and then strip the later stale fingerprint on write.

## Solution Assessment

No as submitted. Cache-level fingerprint storage is the right narrow direction, but the best fix must avoid collapsing old mixed entry fingerprints, preferably by dropping old v4 caches or validating all entry fingerprints before serialization.

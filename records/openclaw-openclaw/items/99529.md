## Summary

Keep open: the linked cache bloat problem is real, but this patch is not safe to merge because it strips per-entry fingerprints without ensuring the current top-level fingerprint is written, so cold or refreshed caches can become permanently stale after the next read.

## What This Changes

The PR adds a top-level usage-cost cache `pricingFingerprint` field and strips `pricingFingerprint` from each persisted cache entry during serialization.

## Best Possible Solution

Persist the active pricing fingerprint as the canonical cache-level value before every checkpoint and final write, then cover cold cache, old cache, append-only, and pricing-change invalidation round trips.

## Reproduction Assessment

Yes, at source level: write a cold cache through the PR path, then read it back; entries have no durable `pricingFingerprint` and the top-level value was never set, so freshness checks compare `undefined` to the active fingerprint. I did not run tests because this review was constrained to read-only inspection.

## Solution Assessment

No. Storing the fingerprint once is the right direction, but the implementation needs the refresh/write boundary to own the active file-level fingerprint and tests to prove cold-cache and pricing-change invalidation behavior.

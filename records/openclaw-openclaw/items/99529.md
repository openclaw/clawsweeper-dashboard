## Summary

Keep open: the PR is a useful candidate for the usage-cost cache bloat issue, but the persisted-cache upgrade path is still unsafe because old mixed-fingerprint entries can lose their per-entry freshness marker during a checkpoint or partial refresh.

## What This Changes

This PR stores the usage-cost cache pricing fingerprint once at the cache-file level, strips it from serialized entries, restores it on load, clears entries when the cache-level fingerprint changes, and adds a cold round-trip test.

## Best Possible Solution

Land one canonical fix that stores the fingerprint once while either dropping old version-4 caches or validating every old entry fingerprint before stripping, with regression coverage for mixed old-format checkpoint caches.

## Reproduction Assessment

Yes, source-level: construct a version-4 cache with mixed per-entry pricing fingerprints where one entry matches current pricing and another does not, then let a checkpoint or partial refresh write the stripped format before all stale entries are rebuilt.

## Solution Assessment

No as submitted. Cache-level fingerprint storage is the right narrow direction, but the best fix must avoid collapsing old mixed entry fingerprints, preferably by dropping old version-4 caches or validating all entry fingerprints before serialization.

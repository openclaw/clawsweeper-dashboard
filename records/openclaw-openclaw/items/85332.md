## Summary

Keep open: current main and the latest release still only support extra APT packages at image-build time, while the requested pulled-image or production-safe prebuild path remains a product and security decision.

## What This Changes

Request to let slim Docker deployments configure extra APT packages without manually entering containers after image pulls or updates.

## Best Possible Solution

Define an explicit derived-image or prebuild/restart workflow with docs, tests, and package-trust guidance, while keeping startup-time APT installation out of the default gateway downtime path unless maintainers deliberately approve it.

Question: Should OpenClaw support deployer-configured APT packages for pulled official Docker images, and should that be a derived-image prebuild flow rather than a startup-time installer?

Rationale: The implementation choice affects official image hardening, package-manager trust, runtime privileges, downtime, and the documented env/CLI contract, so code inspection alone cannot choose the product/security boundary.

Likely owner: steipete

Owner confidence: medium

Options:

- **Design a derived-image prebuild flow (recommended):** Keep the issue open and specify a prebuild command or documented Dockerfile.extend pattern that builds from the official image before restarting the gateway.
- **Allow startup-time installer:** Accept the downtime and root package-manager risk by adding an explicit first-boot or entrypoint installer with caching, logging, and failure semantics.
- **Keep build-time customization only:** Close or defer this direction and continue steering operators to source/local Docker builds or custom Dockerfiles for extra packages.

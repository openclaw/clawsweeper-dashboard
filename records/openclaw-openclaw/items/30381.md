## Summary

Keep open. Current main and the latest release still reject generic request-body `model` values even when a valid `x-openclaw-agent-id` selects the agent, and relaxing that behavior is a public Gateway API precedence decision rather than conservative cleanup.

## What This Changes

The issue asks `/v1/chat/completions` to ignore arbitrary request-body `model` values when `x-openclaw-agent-id` resolves to a configured agent, so the agent's configured model is used.

## Best Possible Solution

Define one explicit Gateway precedence contract: either approve a narrow valid-agent-header compatibility exception and document/test it, or reaffirm the current `openclaw/default` plus `x-openclaw-model` path.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: with a valid agent header and a body model such as `gpt-4`, the handler selects the header agent but then rejects the body model because it is not an OpenClaw agent target. I did not run a live Gateway in this read-only review.

## Solution Assessment

Unclear until maintainers choose the contract. A narrow valid-header exception is plausible for SDK compatibility, but the current documented contract deliberately uses body `model` for agent targeting and `x-openclaw-model` for backend overrides.

## Summary

Keep open. Current main and the latest release still enforce the documented agent-first `model` contract even when a valid agent header selects the agent, so the requested compatibility change needs an explicit Gateway API-precedence decision rather than cleanup closure.

## What This Changes

Request that `/v1/chat/completions` ignore or tolerate the request body `model` when `x-openclaw-agent-id` selects a configured agent.

## Best Possible Solution

Have Gateway owners choose a consistent OpenAI-compatible model/header precedence contract, then update the shared resolver, docs, and focused tests for Chat Completions and any sibling endpoints covered by that contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should a valid `x-openclaw-agent-id` make OpenAI-compatible requests tolerate a generic body `model`, or should the body `model` remain restricted to OpenClaw agent-target values?

Rationale: The mechanical code change is small, but it changes a documented public API contract and may need parity across Chat Completions, Responses, and embeddings.

Likely owner: Vincent Koc

Owner reason: Vincent Koc introduced the current agent-first OpenAI-compatible model contract this issue would change.

Owner confidence: high

Options:

- **Adopt Header Precedence (recommended):** Treat the valid agent header as authoritative and ignore or tolerate generic body model strings for the endpoint set maintainers choose.
- **Preserve Agent-First Model Contract:** Keep rejecting generic body model strings and document that SDK clients should send `openclaw`, `openclaw/default`, or `openclaw/<agentId>` with optional `x-openclaw-model`.
- **Choose Per-Endpoint Semantics:** Limit the change to Chat Completions only and explicitly document why Responses and embeddings keep stricter model validation.

## Reproduction Assessment

Yes, source-level. A request with a valid `x-openclaw-agent-id` still passes the original body `model` into `resolveOpenAiCompatModelOverride`, which rejects generic model strings before agent dispatch.

## Solution Assessment

Unclear until maintainers choose the API contract. The narrow implementation would be in the shared gateway resolver path, but the best solution must define parity with Responses and embeddings before changing public behavior.

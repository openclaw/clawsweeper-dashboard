## Summary

Keep open. Current main and v2026.6.11 still validate the request-body `model` after resolving a valid `x-openclaw-agent-id`, while current docs define `model` as an OpenClaw agent target, so this remains a real API-precedence/product decision rather than cleanup closure.

## What This Changes

Request to make `/v1/chat/completions` treat a valid `x-openclaw-agent-id` header as authoritative and ignore a generic request-body `model` value.

## Best Possible Solution

Define one stable precedence contract for OpenAI-compatible HTTP endpoints; if the header should win, update the shared resolver, sibling endpoint tests, and docs while keeping backend model override behavior on `x-openclaw-model`.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should a valid `x-openclaw-agent-id` header make the request-body `model` compatibility metadata, or must `model` continue to be an OpenClaw agent-target id even when the header is present?

Rationale: The current code is internally consistent with the documented agent-first contract, but the reporter has repeated production evidence that standard OpenAI SDK clients send generic model ids and need an explicit-agent compatibility path.

Likely owner: Vincent Koc

Owner reason: Vincent introduced and recently maintained the agent-first OpenAI-compatible model contract that this decision would change.

Owner confidence: high

Options:

- **Support header precedence (recommended):** When a valid agent header is present, ignore generic body `model` values for agent validation and keep `x-openclaw-model` as the only backend model override path.
- **Keep current contract:** Require clients to send `openclaw`, `openclaw/default`, or `openclaw/<agentId>` in the body even when `x-openclaw-agent-id` is present, and clarify the SDK workaround in docs.
- **Add an explicit compatibility mode:** Introduce a documented opt-in mode or header for SDK compatibility, accepting the added API surface to avoid changing default precedence.

## Reproduction Assessment

Yes, source-reproducible: send `/v1/chat/completions` with a valid `x-openclaw-agent-id` and a generic body `model` such as `gpt-4`; the current handler resolves the header and then rejects the body model before running the agent. I did not run a live test because this review is read-only and test execution can create artifacts.

## Solution Assessment

Unclear until maintainers choose the API contract. Skipping body-model validation when a valid agent header exists is a narrow implementation, but the best solution must be applied consistently across the OpenAI-compatible sibling endpoints and docs.

## Summary

Keep open. Current main and v2026.6.11 still reject a generic body `model` after a valid `x-openclaw-agent-id`, so the remaining work is a product/API precedence decision rather than conservative cleanup.

## What This Changes

The issue requests that `/v1/chat/completions` use the targeted agent's configured model and ignore an OpenAI-compatible request body `model` when `x-openclaw-agent-id` is present.

## Best Possible Solution

Gateway owners should choose one shared OpenAI-compatible precedence rule, then implement it in the shared resolver with docs and focused parity tests for Chat Completions plus any sibling endpoints they want covered.

Question: Should a valid `x-openclaw-agent-id` make OpenAI-compatible requests ignore or tolerate a generic OpenAI body `model`, and should that rule apply beyond `/v1/chat/completions`?

Rationale: The code change is bounded, but it changes the public model-selection contract and may need parity across Responses and embeddings rather than a one-endpoint workaround.

Likely owner: vincentkoc

Owner reason: vincentkoc introduced the agent-first contract and the related OpenAI-compatible endpoint expansion, making them the strongest history-based owner for the API precedence choice.

Owner confidence: high

Options:

- **Adopt header precedence consistently (recommended):** A valid agent header selects the agent, generic body models are treated as client compatibility metadata, and docs/tests are updated across the chosen OpenAI-compatible endpoints.
- **Preserve the agent-first body contract:** Clients must continue sending `openclaw`, `openclaw/default`, or `openclaw/<agentId>` in `model`, with `x-openclaw-model` reserved for backend provider/model overrides.
- **Add a chat-only exception:** Only `/v1/chat/completions` tolerates generic body models with a valid agent header, accepting the risk of endpoint-specific semantics.

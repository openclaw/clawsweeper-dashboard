## Summary

Keep open. Current main and latest release behavior still reject a generic body `model` after a valid `x-openclaw-agent-id`, and changing that would alter the documented agent-first OpenAI-compatible API contract rather than being safe cleanup.

## What This Changes

The issue requests that `/v1/chat/completions` use the agent selected by `x-openclaw-agent-id` and ignore or tolerate the request body `model` field.

## Best Possible Solution

Gateway owners should choose a documented header/body-model precedence rule, then update the shared resolver, docs, and focused tests consistently for the OpenAI-compatible endpoint set they want covered.

Rationale: The mechanical code change is narrow, but it changes public API semantics for model selection and needs a parity decision across Chat Completions, Responses, and possibly embeddings.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Adopt Header Precedence Consistently (recommended):** Treat a valid agent header as the selected agent and accept generic body models as client compatibility metadata, with docs and tests for the chosen endpoint set.
- **Preserve Agent-First Model Contract:** Keep requiring body `model` values such as `openclaw`, `openclaw/default`, or `openclaw/<agentId>` and document SDK integrations to send those values.
- **Allow Chat-Only Compatibility:** Change only `/v1/chat/completions`, accepting a smaller immediate fix while intentionally allowing endpoint semantics to diverge.

## Reproduction Assessment

Yes, source-level. A request with a valid `x-openclaw-agent-id` and generic body model reaches `resolveOpenAiCompatModelOverride`, which rejects non-OpenClaw agent-target model strings before dispatch; I did not run a live gateway request in this read-only review.

## Solution Assessment

Unclear until maintainers decide the public API contract. The narrow implementation would be small, but the best solution must define whether header precedence applies consistently across sibling OpenAI-compatible endpoints.

## Summary

Keep open. Current main and v2026.6.11 still validate the request body `model` after a valid agent header, while current docs define `model` as an OpenClaw agent target, so the remaining issue is a public gateway precedence decision rather than cleanup closure.

## What This Changes

Requests that `/v1/chat/completions` ignore a generic body `model` and use the selected agent's configured model when a valid `x-openclaw-agent-id` header is present.

## Best Possible Solution

Choose one documented gateway contract, then update the shared helper, chat-completions, sibling endpoint tests, and public docs so valid agent headers either intentionally bypass generic body-model validation or explicitly continue to reject non-OpenClaw model values.

Rationale: The source fix is narrow, but it changes a public API precedence contract that is currently documented as agent-first and shared by sibling gateway endpoints.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Agent header wins (recommended):** Treat the body `model` as SDK compatibility filler when a valid agent header is present, and use `x-openclaw-model` as the only backend-model override surface.
- **Keep current validation:** Continue requiring the body `model` to be omitted or use an OpenClaw agent target even when `x-openclaw-agent-id` is present, and document that more explicitly.
- **Add explicit compatibility mode:** Preserve current default behavior and add a documented opt-in path for SDKs that must send generic OpenAI model ids with agent headers.

## Reproduction Assessment

Yes. Source inspection shows a valid agent header is resolved first, but the same body `model: "gpt-4"` would then fail `resolveOpenAiCompatModelOverride` because it is not an OpenClaw agent target.

## Solution Assessment

Unclear until maintainer direction is set. A shared helper change is the likely best implementation once the public model/header precedence contract is chosen, but accepting generic body models is a product/API decision.

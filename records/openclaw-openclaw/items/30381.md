## Summary

Keep open. Current main and the latest release still reject generic request-body `model` values even after a valid `x-openclaw-agent-id` selects an agent, and relaxing that precedence is a public Gateway API/product decision rather than conservative cleanup.

## What This Changes

Requests that `/v1/chat/completions` ignore a generic request-body `model` when a valid `x-openclaw-agent-id` header selects an agent, so the agent's configured model is used.

## Best Possible Solution

Maintainers should define one explicit Gateway precedence contract, then update source, tests, and docs consistently for both chat completions and any sibling OpenAI-compatible endpoint that should share the rule.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should a valid `x-openclaw-agent-id` header make `/v1/chat/completions` ignore arbitrary OpenAI SDK `model` values and use the selected agent's configured model instead?

Rationale: Current code and docs intentionally treat request-body `model` as an OpenClaw agent target and reserve backend model selection for `x-openclaw-model`, so accepting generic SDK model strings changes a public Gateway API precedence rule.

Likely owner: Vincent Koc

Owner reason: They authored the current agent-first Gateway contract that this issue would relax or reaffirm.

Owner confidence: high

Options:

- **Approve narrow header precedence (recommended):** Allow arbitrary body `model` values to be ignored only after `x-openclaw-agent-id` resolves to a known agent, while preserving strict validation when no valid agent header is present.
- **Keep current agent-target contract:** Continue requiring `model` to be `openclaw`, `openclaw/default`, or `openclaw/<agentId>` and direct integrations to use `x-openclaw-model` for backend model overrides.

## Reproduction Assessment

Yes, at source level. A body model like `gpt-4` cannot resolve via `resolveAgentIdFromModel`, so `resolveOpenAiCompatModelOverride` returns a 400 even after `resolveGatewayRequestContext` can select the header agent.

## Solution Assessment

Unclear until maintainers choose the contract. A narrow valid-header precedence exception is plausible for SDK compatibility, but the current docs and tests deliberately define `model` as an agent target and `x-openclaw-model` as the backend override.

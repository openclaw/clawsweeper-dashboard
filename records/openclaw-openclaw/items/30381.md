## Summary

Keep open. Current main and v2026.6.11 still reject a non-OpenClaw request-body `model` after resolving a valid `x-openclaw-agent-id`, while the docs define `model` as an agent target; changing that precedence is a public Gateway API/product decision rather than conservative cleanup.

## What This Changes

Request to let `/v1/chat/completions` use the targeted agent's configured model and ignore a generic request-body `model` when `x-openclaw-agent-id` is valid.

## Best Possible Solution

Maintainers should choose and document one Gateway contract: either a narrow valid-header compatibility mode that ignores generic body `model` values across OpenAI-compatible endpoints, or the strict agent-target model contract with explicit client guidance.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenAI-compatible HTTP requests with a valid `x-openclaw-agent-id` ignore non-OpenClaw request-body `model` values and use the targeted agent's configured model, or should the strict agent-target `model` contract remain required?

Rationale: The implementation change is small, but it changes a documented public Gateway API precedence rule for model selection and provider override semantics.

Likely owner: Vincent Koc

Owner reason: He introduced the current agent-first Gateway contract and has recent history in the resolver surface.

Owner confidence: high

Options:

- **Accept narrow header compatibility (recommended):** When a valid agent header selects an agent, ignore non-OpenClaw body `model` values for selection/validation, keep backend overrides in `x-openclaw-model`, and update docs plus sibling endpoint tests.
- **Keep strict model contract:** Continue requiring `model` to be `openclaw` or an OpenClaw agent target even with the header, and improve docs/errors for OpenAI SDK clients that must send a model string.

## Reproduction Assessment

Yes at source level: the handler resolves the agent header, then `resolveOpenAiCompatModelOverride` still rejects a body `model` that is not an OpenClaw agent target. I did not run a live gateway request in this read-only review.

## Solution Assessment

Unclear until maintainers decide the API contract. The narrow maintainable fix would be to skip body-model validation only after a valid header selects an agent, and to update docs plus Chat/Responses sibling coverage together.

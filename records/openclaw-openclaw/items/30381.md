## Summary

Keep open. Current main and the latest release still reject a generic request-body `model` after resolving a valid `x-openclaw-agent-id`, and the existing docs intentionally define `model` as an OpenClaw agent target, so this is a real Gateway API precedence decision rather than cleanup closure.

## What This Changes

The issue requests that `/v1/chat/completions` ignore generic request-body `model` values when `x-openclaw-agent-id` targets a valid agent and use the agent's configured model instead.

## Best Possible Solution

Define one stable precedence contract for OpenAI-compatible Gateway HTTP endpoints, then update the shared resolver, sibling endpoint coverage, and public docs together if valid agent headers should win over generic body model values.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should a valid `x-openclaw-agent-id` header make the request-body `model` compatibility metadata, or must `model` continue to be an OpenClaw agent-target id even when the header is present?

Rationale: The current code and docs deliberately use an agent-first body `model` contract, while the report gives repeated production evidence that OpenAI SDK-compatible clients send generic model ids and need a header-selected-agent path.

Likely owner: Vincent Koc

Owner reason: Vincent introduced and recently maintained the current agent-first OpenAI-compatible model contract that this decision would change.

Owner confidence: high

Options:

- **Let the agent header win (recommended):** When `x-openclaw-agent-id` resolves to a valid agent, treat generic body `model` as compatibility metadata and keep backend model changes on `x-openclaw-model`.
- **Keep current agent-first contract:** Continue requiring body `model` to be `openclaw`, `openclaw/default`, or an OpenClaw agent target even when the header is present, and document the SDK workaround clearly.
- **Add explicit compatibility opt-in:** Require a documented opt-in header or mode for generic SDK model values, accepting extra API surface to avoid changing default precedence.

## Reproduction Assessment

Yes, source-reproducible: send `/v1/chat/completions` with a valid `x-openclaw-agent-id` and a generic body `model`; current code resolves the header, then rejects the body model before dispatching the agent run. I did not run live tests because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the API contract. Ignoring body-model validation after a valid agent header is a narrow implementation shape, but the best solution must be consistent across OpenAI-compatible sibling endpoints and docs.

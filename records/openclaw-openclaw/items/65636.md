## Summary

Keep open: current main and the latest release still do not expose a supported create-time custom cron job ID, and an open linked implementation PR still needs maintainer product/API review before this issue can close.

## What This Changes

Request support for an optional `openclaw cron add --id <id>` field so new cron jobs can use stable human-readable IDs instead of generated UUIDs.

## Best Possible Solution

Land or reject a maintainer-approved cron create ID contract through the linked PR or a narrow replacement, preserving default UUID behavior while adding validation, duplicate rejection, docs, and focused CLI/Gateway/service tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw make cron job IDs caller-supplied at creation via a public `cron add --id` and Gateway `cron.add.id` contract, and what validation/collision rules should that contract use?

Rationale: This is a new public CLI/API creation field for persisted scheduler identity, so automation can verify the missing behavior but should not choose the permanent ID contract on its own.

Likely owner: Peter Steinberger

Owner reason: He introduced the cron scheduler surface and has the strongest historical ownership signal for a public cron identity contract.

Owner confidence: high

Options:

- **Approve bounded custom IDs (recommended):** Add optional create-time IDs with a conservative slug-like validation rule, explicit duplicate rejection, unchanged UUID defaults, docs, and coverage across CLI, Gateway schema, service, and relevant clients.
- **Keep UUID-only creation:** Leave create-time IDs server-generated and improve discoverability through listing, display, or name-based workflows instead of adding a new identity field.
- **Defer pending broader cron API design:** Keep the issue open until maintainers decide the larger cron identity/API model, including agent-created jobs and generated-client compatibility.

## Reproduction Assessment

Yes. Source inspection is enough: current main has no `cron add --id` flag, `CronJobCreate` omits `id`, the closed protocol schema has no `id`, and `createJob` always generates a UUID.

## Solution Assessment

Unclear until maintainers choose the public ID contract. The requested direction is bounded and plausible, but the best implementation needs explicit validation, collision, docs, generated-client, and non-CLI create-path decisions.

## Summary

Keep open: this PR targets the active Teams long-thread context bug, but it is not merge-ready because the proposed pagination path now uses the raw `limit` after clamping the Graph request and the PR still has only mocked/unit proof for live Microsoft Graph behavior.

## What This Changes

The PR changes the Microsoft Teams thread-reply helper to page through Graph replies, select the newest reply window by `createdDateTime`, and add mocked unit coverage for paginated replies.

## Best Possible Solution

Use a single effective 1..50 reply limit for both page size and returned slicing, keep the helper-level pagination/newest-window approach, and land only after redacted live Teams/Graph proof or explicit maintainer acceptance of the bounded mocked-only risk.

## Reproduction Assessment

Yes for the source-level path: current main fetches one `$top=50` replies page and the monitor handler injects that result into thread context. Live Microsoft Teams proof for an over-50-reply thread is still missing.

## Solution Assessment

No as submitted. The helper-level pagination approach is the right owner boundary, but the patch should use the clamped effective limit for returned items and needs live proof or explicit maintainer acceptance for the Graph fanout risk.

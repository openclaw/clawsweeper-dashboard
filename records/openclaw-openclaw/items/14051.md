## Summary

Keep open: current main and the latest release still do not expose or honor an activity-based heartbeat idle timeout, and the open related items/PRs cover narrower missing-file, stale-session, retry, voice, or non-blocking heartbeat cases rather than replacing this canonical product/config tracker.

## What This Changes

The issue requests an activity-based heartbeat idle timeout that pauses scheduled heartbeats after a configured period without allowed inbound user activity.

## Best Possible Solution

Keep this as the canonical heartbeat idle-timeout tracker and define a maintainer-approved heartbeat activity policy before implementation: exported config, strict schema/help/docs, runtime gating on recent allowed inbound activity at the agent/session/channel boundary, and regression coverage that preserves active-hours, busy deferral, wake/cron/commitment paths, lightContext, isolatedSession, and delivery behavior.

Rationale: This adds public heartbeat configuration and changes scheduled background behavior, so automation cannot safely choose the config contract, defaults, bypass rules, and upgrade semantics without maintainer intent.

Owner confidence: high

Options:

- **Approve explicit idle-timeout config (recommended):** Add a heartbeat-owned idle timeout option with documented activity semantics and tests for scheduled runs versus wake/event bypasses.
- **Reuse session freshness only:** Gate scheduled heartbeat on existing session reset freshness without adding a new heartbeat config key, reducing surface but giving users less direct control.
- **Fold into broader heartbeat safety policy:** Keep this issue open until maintainers design combined idle, cost-cap, OK-backoff, and provider-error backoff semantics.

Not applicable as a strict bug, but yes for source-level absence: current main has no heartbeat idle-timeout config/schema field and the runner/scheduler do not consult recent inbound activity before scheduled runs.

## Summary

Keep open: current main and the latest release still lack heartbeat activity/idle-timeout configuration and runtime gating on recent allowed inbound user activity. This remains the canonical tracker, but it needs maintainer product direction before implementation because it adds a public heartbeat config surface and must define which activity re-arms scheduled heartbeats.

## What This Changes

Request an activity-based heartbeat idle timeout so scheduled heartbeats pause after a configurable period without allowed inbound user activity and resume on the next conversation.

## Best Possible Solution

Keep this as the canonical heartbeat activity-idle tracker and have maintainers choose a public config/activity contract before implementing schema, docs, runtime gating, and regression coverage.

## Reproduction Assessment

Yes, at source level: current heartbeat types/schema/docs lack the proposed key, and the runner/scheduler paths do not consume recent allowed inbound activity before scheduled heartbeat runs. I did not run a live gateway reproduction because this review is read-only.

## Solution Assessment

No implementation path is ready for automation yet. The maintainable fix needs a maintainer decision on config naming, activity source, allowed-sender scope, and wake exceptions before code changes.

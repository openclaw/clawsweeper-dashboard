## Summary

Keep open: current `main` and the latest release still lack heartbeat activity-idle configuration and runtime gating on recent allowed inbound user activity. The issue remains the broad canonical tracker, while open related items cover narrower heartbeat token-burn or delivery-delay cases.

## What This Changes

Add heartbeat idle-timeout behavior so scheduled heartbeats start after user activity and pause after the configured inactivity window.

## Best Possible Solution

Keep this as the canonical heartbeat activity-idle tracker and have maintainers choose a public config/activity contract before implementation across types, strict schema, help/docs, inventory, runtime gating, and regression coverage.

## Reproduction Assessment

Yes, at source level: current heartbeat types/schema/docs lack the proposed key, and the runner/scheduler paths do not consume recent allowed inbound activity before scheduled heartbeat runs. I did not run a live gateway reproduction because this review is read-only.

## Solution Assessment

Unclear: an activity-based heartbeat gate is plausible and likely belongs in core heartbeat scheduling, but the exact config name, activity source, allowed-sender scope, and wake exceptions need maintainer product direction first.

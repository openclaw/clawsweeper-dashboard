## Summary

The reported non-loopback probe bug is valid, but this patch is not merge-ready: it incorrectly reroutes wildcard LAN binds away from available loopback and duplicates existing bind-to-client-host resolution instead of establishing one canonical path.

## What This Changes

The PR changes shared CLI gateway connection details to target discovered tailnet, LAN, or custom bind addresses instead of always using loopback.

## Best Possible Solution

Introduce one shared bind-to-client-host resolver used by both gateway connection details and Control UI links, preserve loopback for wildcard lan/auto listeners, resolve exact tailnet/custom binds consistently, add focused mode/fallback tests, and provide a redacted live non-loopback CLI transcript.

## Reproduction Assessment

Yes at source level: tailnet and exact custom binds can exclude loopback while the current shared resolver hardcodes 127.0.0.1, matching the linked issue's deterministic failure. The issue's LAN claim is not generally valid because gateway.bind=lan resolves to the wildcard 0.0.0.0 listener.

## Solution Assessment

No. Resolving exact non-loopback listeners is appropriate, but the patch should preserve loopback for wildcard binds and reuse a single shared bind-to-client-host implementation rather than copying Control UI logic.

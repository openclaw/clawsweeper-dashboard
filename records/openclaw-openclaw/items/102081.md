## Summary

Keep open: current main and the latest release still force approval for allowlisted POSIX shell-shaped commands when the enforced command renderer cannot safely pin the execution plan, while the public `ask` mode docs say allowlist matches should run directly. The remaining choice is a security-boundary decision, not cleanup-closeable stale work.

## What This Changes

The issue requests that macOS `security: "allowlist"` plus `ask: "on-miss"` auto-execute matching commands, or clearly document and explain the shell-shape gate that forces approval for commands using tilde expansion, redirections, pipes, or chains.

## Best Possible Solution

Maintainers should choose the security posture: either make common shell-shaped matches enforceable with explicit renderer support and live macOS proof, or keep the fail-closed gate while documenting the limitation and improving the warning to name the command-shape blocker.

Options:

- **Keep fail-closed, improve UX (recommended):** Keep the current explicit-approval requirement for unenforceable shell-shaped commands, document the Darwin/POSIX command-shape limitation, and make the warning name the specific blocker such as tilde expansion or shell wrapper payload.
- **Add narrow enforceable support:** Permit no-prompt auto-execution only for shell shapes the planner can rewrite to pinned executables and arguments, with regression tests and live macOS proof for each newly supported shape.
- **Relax allowlist matches broadly:** Allow static allowlist matches to run even when the enforced renderer cannot pin the command, accepting a larger exec authorization risk for operator convenience.

Unclear until maintainer/security review decides the intended boundary. The maintainable fix is either narrow renderer support for provably enforceable shell shapes, or docs and warning updates that make the fail-closed behavior explicit.

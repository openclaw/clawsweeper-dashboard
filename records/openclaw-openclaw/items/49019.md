## Summary

Keep open: current main and v2026.6.11 still expose an async-only `POST /hooks/agent` contract with run-id-only responses, and the open linked implementation candidate still needs maintainer product/security review before this issue can be resolved.

## What This Changes

Request an opt-in result-return mode for `POST /hooks/agent` so external automations can wait for a hook-triggered agent run and receive a deterministic result without polling session history.

## Best Possible Solution

Review the linked implementation candidate and either land a maintainer-approved opt-in result-return API with explicit hook security boundaries, or document the product decision and supported alternative.

## Reproduction Assessment

Not applicable as a bug reproduction, but the feature gap is source-reproducible: current main still exposes only the async `/hooks/agent` request fields and run-id response path.

## Solution Assessment

Unclear until maintainer review; extending `/hooks/agent` is plausible, but the exact synchronous result contract may need a different endpoint or result-fetch model for security and operational safety.

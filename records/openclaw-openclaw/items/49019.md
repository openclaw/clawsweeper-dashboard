## Summary

Keep open: current main and v2026.6.11 still expose `POST /hooks/agent` as an async, run-id-only hook, while the linked implementation candidate remains open and needs maintainer API/security direction before this issue can resolve.

## What This Changes

Request an opt-in result-return mode for `POST /hooks/agent` so authenticated external automations can wait for a hook-triggered agent run and receive a deterministic result without polling session history.

## Best Possible Solution

Review the linked implementation candidate and either land a maintainer-approved opt-in result-return API with explicit hook security boundaries, or document the chosen supported alternative such as polling or a short-lived result fetch.

- **Decline core API change:** Document `/hooks/agent` plus `sessions_history` as the supported pattern and leave synchronous callback behavior to downstream integrations for now.

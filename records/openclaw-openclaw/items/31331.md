## Summary

Keep open. Current main and the latest release still pass Gateway-visible container paths directly into Docker bind specs for sandbox workspace mounts, and prior direct fix attempts are closed unmerged while the newer open candidate covers a narrower materialized-skill case and is not merge-ready.

## What This Changes

The issue reports that Docker-install sandbox `workspaceAccess` uses Gateway-container-internal paths as bind sources in Docker-outside-of-Docker setups instead of host-resolvable workspace paths.

## Best Possible Solution

Keep this issue as the canonical Docker/DooD sandbox bind-source bug and land a security-reviewed host-path mapping contract for workspace, agent, browser, custom-bind, and materialized-skill mounts with schema/docs/tests and live DooD proof.

## Reproduction Assessment

Yes at source level: current main resolves Gateway-visible workspace paths and formats them directly into Docker bind specs, while the docs state DooD bind sources are evaluated in the host namespace. I did not run a live Docker Gateway reproduction in this read-only review.

## Solution Assessment

Unclear. Host-path translation is the right class of fix, but the best implementation needs a maintainer-approved contract that preserves sandbox bind validation, browser mounts, custom binds, docs, and live DooD proof.

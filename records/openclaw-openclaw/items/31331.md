## Summary

Keep open. Current main and v2026.6.11 still build Docker sandbox bind sources from Gateway-visible paths, while the issue discussion keeps this as the canonical Docker Gateway/DooD workspaceAccess path-mapping failure requiring maintainer/security direction.

## What This Changes

The issue reports that Docker-installed Gateways using Docker-outside-of-Docker pass container-internal sandbox workspace paths to the host Docker daemon, breaking `workspaceAccess` mounts.

## Best Possible Solution

Define one security-reviewed Docker Gateway/DooD host-path contract for managed workspace, agent workspace, materialized skills, browser mounts, docs, and doctor or setup guidance, then close the cluster after live DooD proof.

- **Land Only Narrow Skill Repair:** Treat the open materialized-skills PR as a partial fix while leaving this canonical workspaceAccess issue open for the broader managed-mount contract.

Yes, at source level: current main resolves sandbox workspace paths in the Gateway namespace and formats them directly as Docker bind sources, while docs confirm Docker evaluates those paths in the host namespace for DooD. ## Solution Assessment

Unclear until maintainers choose the host-path contract. Automatic remapping is plausible, but it must be security-reviewed against bind allowlists, reserved targets, browser mounts, custom binds, and upgrade/operator behavior.

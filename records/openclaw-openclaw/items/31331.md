## Label Justifications

- `P1`: Docker-installed gateways with sandboxing can have unusable workspace access across real user setups and released versions.
- `impact:session-state`: The affected path decides which workspace state is mounted into sandboxed agent sessions, causing the sandbox to see the wrong or empty workspace.
- `impact:security`: The issue and its durable fix touch Docker sandbox bind-source boundaries, and the reported workaround requires dangerous bind override flags.

## Summary

Keep open. Current main and the latest release still pass Gateway-visible sandbox paths directly into Docker bind creation; the docs now describe the DooD host-path parity contract, but the direct remapping PRs are closed unmerged and the remaining fix is security/product-sensitive.

## What This Changes

Fix Docker-installed Gateway sandbox workspaceAccess so sandbox containers receive host-resolvable bind sources instead of Gateway-container paths.

## Best Possible Solution

Keep this canonical issue open until maintainers land or replace a security-reviewed Docker Gateway/DooD bind-source contract shared by workspace, agent, materialized skill, browser, and custom mounts, with docs/setup alignment, focused tests, and live DooD proof.

Yes, at source level. Current main resolves Gateway-visible sandbox paths and formats them directly into Docker bind specs, while the docs confirm DooD bind paths are resolved in the host namespace; I did not run a live Docker/DooD repro.

## Solution Assessment

Unclear. Host-path remapping is plausible and has prior unmerged attempts, but the best fix needs a maintainer-approved operator contract and sandbox validation before it is safe to land.

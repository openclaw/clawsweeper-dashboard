## Summary

Keep open. Current main and the latest release still pass Gateway-visible sandbox workspace paths directly into Docker bind specs, while the canonical discussion and related items show this Docker-outside-of-Docker host/container path mismatch still needs maintainer/security direction rather than cleanup closure.

## What This Changes

The issue reports that Docker-installed Gateway running Docker-outside-of-Docker creates sandbox workspace bind mounts from container-internal paths instead of host paths, breaking `workspaceAccess`.

## Best Possible Solution

Land or replace the related work with one security-reviewed host/container path mapping contract for Docker gateway sandboxes, covering managed workspace, agent workspace, materialized skills, and relevant browser/custom bind paths with schema/docs and live DooD proof.

## Reproduction Assessment

Yes at source level: current main still formats Gateway-visible workspace paths into Docker bind specs, and the docs confirm DooD bind paths are resolved in the host namespace. I did not run a live Docker-in-Docker setup in this read-only review.

## Solution Assessment

Unclear. Host-path remapping is plausible, but the best fix needs a maintainer-approved operator/security contract, schema and docs alignment if config changes, and live DooD proof before this issue can close.

## Label Justifications

- `P1`: Docker-install sandbox workspace access is broken for multiple real users and affects a core agent/tool execution workflow.
- `impact:security`: The issue concerns sandbox Docker bind sources and the safe boundary between Gateway paths, host Docker paths, and dangerous bind overrides.
- `impact:session-state`: Incorrect bind sources can put sandboxed sessions in an empty or wrong workspace instead of the intended agent workspace.
- `impact:ux-friction`: The documented workaround requires manual config, a dummy workdir, and dangerous override flags instead of an in-product repair path.

## Summary

Keep open. Current main and the latest release still construct automatic Docker sandbox binds from Gateway-visible workspace paths, while this issue remains the canonical Docker Gateway/DooD `workspaceAccess` bind-source mismatch that needs maintainer security/product direction.

## What This Changes

The issue reports that Docker-hosted Gateway sandbox containers bind-mount `/workspace` from the Gateway container’s internal path instead of the host path Docker can resolve.

## Best Possible Solution

Define a maintainer-approved Docker/DooD host-path mapping contract for sandbox-created binds, preserve sandbox security validation after remap, update Docker install docs or doctor guidance, and prove it with a real Docker Compose Gateway plus sandbox smoke.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Docker-hosted Gateway installs automatically remap sandbox bind sources from Gateway-container paths to host Docker paths, or should OpenClaw require operators to configure identical host/container workspace paths?

Rationale: This choice changes the sandbox bind-source trust model and Docker install contract, so automation should not choose between implicit remapping and stricter operator setup on its own.

Likely owner: steipete

Owner reason: He has the strongest merged-history signal for the sandbox workspace mount and shared sandbox plumbing that the decision would change.

Owner confidence: high

Options:

- **Approve explicit host-path remapping (recommended):** Add a narrow remap path based on the Gateway container mount table, then validate remapped sources against the existing blocked-path and allowed-root policy with real DooD proof.
- **Require identical host/container paths:** Keep runtime strict, but add doctor/docs diagnostics that detect mismatched Docker Gateway volume maps and tell operators how to fix them without dangerous bind overrides.
- **Limit the fix to materialized skills:** Handle only the state/skill mount subset tracked by the related open issue, leaving workspaceAccess users to configure matching paths manually.

## Reproduction Assessment

Yes, source-reproducible with medium confidence: current main builds Docker `-v` specs from `workspaceDir` and `agentWorkspaceDir` as seen by the Gateway process, and the docs state DooD requires host-resolvable paths. I did not run a live Docker Compose/DooD repro in this read-only review.

## Solution Assessment

No final fix shape is approved yet. The current workaround is unsafe and awkward; the maintainable solution needs an explicit host-path mapping or strict-diagnostics decision with security validation and real DooD proof.

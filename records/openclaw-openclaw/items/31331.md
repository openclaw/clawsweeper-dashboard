## Label Justifications

- `P1`: Docker-installed gateways with sandboxing can have unusable sandbox workspace access across real user setups and released versions.
- `impact:session-state`: The affected path decides which workspace state is mounted into sandboxed agent sessions, causing the sandbox to see the wrong or empty workspace.
- `impact:security`: The issue and its durable fix touch Docker sandbox bind-source boundaries, and the reported workaround requires dangerous bind override flags.

## Summary

Keep open. Current main and v2026.6.11 still format Gateway-visible sandbox workspace paths directly into Docker bind specs, the docs confirm DooD bind sources are resolved in the host namespace, and the direct fix PRs are closed unmerged while the open related PR covers a narrower materialized-skills variant with blockers.

## What This Changes

The issue reports Docker-installed Gateways using container-internal workspace paths as Docker sandbox bind sources, breaking workspaceAccess in Docker-outside-of-Docker setups.

## Best Possible Solution

Land or replace the closed direct remap work with one security-reviewed Docker Gateway/DooD bind-source contract shared by workspace, agent, skill, browser, and custom mounts, with docs/setup alignment and live DooD proof.

## Reproduction Assessment

Yes, at source level. Current main resolves Gateway-visible workspace paths and formats them directly into Docker bind specs, while the docs confirm host Docker evaluates DooD bind sources in the host namespace; no live DooD run was executed in this read-only review.

## Solution Assessment

Unclear. Host-source remapping is plausible and has prior direct PRs, but the best fix needs maintainer approval of the operator contract and sandbox validation before it is safe to land.

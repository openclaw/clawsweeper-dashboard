## Summary

Keep open. Current main and the latest release still build Docker sandbox bind specs from Gateway-visible paths without a host-namespace remap, while this issue is explicitly kept as the canonical Docker-install/DooD `workspaceAccess` bind-mount failure and the direct fix attempts were closed unmerged.

## What This Changes

The issue reports that Docker-installed Gateway sandboxing binds the sandbox workspace from the Gateway container's internal path instead of the host path, breaking `workspaceAccess` for Docker-outside-of-Docker installs.

## Best Possible Solution

Keep this canonical issue open until maintainers approve and land one Docker Gateway/DooD path-mapping or setup contract with security review, docs, and live DooD proof.

## Reproduction Assessment

Yes, at source level. Current main still derives sandbox workspace paths in the Gateway namespace and formats them directly into Docker `-v` bind specs, while the docs confirm DooD bind sources are resolved in the host namespace; I did not run a live DooD environment.

## Solution Assessment

Unclear. Automatic host-path remapping is plausible, but the direct remap PRs were closed unmerged and current docs instead require host-path parity, so maintainers need to choose the secure setup or mapping contract before implementation.

## Summary

Keep open. Current main still builds Docker sandbox bind sources from the Gateway-visible workspace paths, while the issue remains the canonical Docker Gateway/DooD `workspaceAccess` host/container namespace mismatch; the closed remap PRs did not land and the current docs only document an operator path-mapping contract, not an automatic fix.

## What This Changes

The issue reports that Docker-installed Gateway sandboxing with Docker-outside-of-Docker binds the sandbox workspace from the Gateway container path instead of the host workspace path.

## Best Possible Solution

Keep this issue as the canonical thread and have maintainers choose a security-reviewed Docker Gateway/DooD host-path contract, then prove it with regression coverage and real Docker-host sandbox proof.

Question: Should OpenClaw automatically translate Gateway-container paths to host paths for Docker-outside-of-Docker sandbox binds, or should Docker Gateway installs continue to require an explicit identical host/container path mapping?

Rationale: Both directions affect the sandbox security boundary: automatic translation broadens trusted bind-source resolution, while the current documented contract leaves Docker users with fragile manual setup for `workspaceAccess`.

Options:

- **Sponsor a bounded host-path mapping design (recommended):** Add a narrow, audited mapping mechanism that preserves bind-source allowlists, rejects Docker socket/credential exposure, updates Docker setup/docs, and includes DooD E2E proof.
- **Keep the explicit identical-path contract:** Treat this as an operator setup requirement, improve doctor/setup diagnostics, and close or narrow related code-fix proposals that try to infer host paths automatically.

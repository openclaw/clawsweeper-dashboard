## Label Justifications

- `P1`: The issue affects Docker-installed sandbox execution for multiple users and can break agent workspace access in real channel workflows.
- `impact:session-state`: Incorrect workspace mounting can make sandboxed sessions see the wrong workspace or an empty generated sandbox workspace instead of the intended agent workspace.
- `impact:security`: The workaround requires dangerous sandbox bind flags and manually exposes host paths, which is a sandbox boundary concern.

## Summary

Keep open. Current main still passes Gateway-visible sandbox workspace paths directly into Docker bind specs, the latest release has the same behavior, and the open candidate PR has not landed because the durable host-path mapping contract needs maintainer/security/product review.

## What This Changes

The issue reports that Docker-installed Gateway sandboxing uses container-internal workspace paths for Docker-outside-of-Docker bind mounts, preventing `workspaceAccess` from mounting the host workspace correctly.

## Best Possible Solution

Land or replace the open host-path mapping fix with one security-reviewed, schema/docs-backed Docker sandbox path contract shared by shell and browser sandbox mounts, then close this broader issue after redacted live DooD proof.

## Reproduction Assessment

Yes at source level: current main formats Gateway-visible sandbox paths directly into Docker bind specs, and the docs confirm DooD bind paths are resolved in the host namespace. I did not run a live Docker repro in this read-only review.

## Solution Assessment

No final solution is on main yet. Host-path translation is plausible, but the best fix needs maintainer/security agreement on the durable config or setup contract instead of relying on manual dangerous binds or docs-only parity guidance.

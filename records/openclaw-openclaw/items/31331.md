## Summary

Keep open. Current main and the latest release still pass Gateway-visible workspace paths directly into Docker bind specs, while the discussion and duplicate cleanup keep this as the canonical Docker Gateway/DooD workspaceAccess bind-source failure.

## What This Changes

The issue reports that Docker-install Gateway setups using Docker-outside-of-Docker sandboxing mount the container-internal workspace path instead of the host workspace path.

## Best Possible Solution

Define one security-reviewed Docker Gateway/DooD host-path contract for managed workspace, agent workspace, materialized skills, browser/custom binds, docs, and doctor/setup guidance, then close the cluster after live DooD proof.

- **Keep identical-path contract:** Document and enforce that Docker Gateway deployments must mount the same host path inside the Gateway container and provide an in-product doctor warning for mismatched setups.
- **Land only narrow skill repair:** Treat the open materialized-skills PR as a partial fix while leaving this canonical workspaceAccess issue open for the broader managed-mount contract.

Yes, at source level: current main resolves sandbox workspace paths in the Gateway namespace and formats them directly as Docker bind sources, while docs confirm Docker evaluates those paths in the host namespace for DooD. ## Solution Assessment

Unclear until maintainers choose the host-path contract. Automatic remapping is plausible, but it must be security-reviewed against bind allowlists, reserved targets, browser mounts, custom binds, and upgrade/operator behavior.

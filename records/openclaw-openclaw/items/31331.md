## Label Justifications

- `P1`: Docker-installed gateways with sandboxing can have unusable sandbox workspace access across real user setups and released versions.
- `impact:session-state`: The affected code decides which workspace state is mounted into sandboxed agent sessions, so the sandbox can see the wrong or empty workspace.
- `impact:security`: The issue and durable fix touch Docker sandbox bind-source boundaries, and the reported workaround requires dangerous bind override flags.

## Summary

Keep open. Current main and v2026.6.11 still pass Gateway-visible sandbox workspace paths directly into Docker bind specs, while the Docker-outside-of-Docker docs confirm those sources are resolved in the host namespace; the direct fix PRs are closed unmerged and the remaining open PR covers a narrower materialized-skills variant with blockers.

## What This Changes

The issue asks OpenClaw Docker Gateway sandboxing to mount the host workspace correctly when `workspaceAccess` is enabled under Docker-outside-of-Docker.

## Best Possible Solution

Land or replace the closed direct remap work with one security-reviewed Docker Gateway/DooD bind-source contract shared by workspace, agent, skill, browser, and custom mounts, with docs/setup alignment and live DooD proof.

## Reproduction Assessment

Yes, at source level. Current main resolves Gateway-visible workspace paths and formats them directly into Docker bind specs, while the docs confirm host Docker evaluates DooD bind sources in the host namespace; no live DooD run was executed in this read-only review.

## Solution Assessment

Unclear. Host-source remapping is plausible and has prior direct PRs, but the best fix needs maintainer approval of the operator contract and sandbox validation before it is safe to land.

## Summary

Keep this PR open for maintainer product review and a focused correctness repair: pacing is documented and exposed for recurring jobs, but the current validation path accepts one-shot schedules where a successful `next_check` proposal is silently not scheduled. The PR also needs real after-fix runtime proof before merge; its described Vitest coverage is valuable supplemental evidence but not that proof.

## What This Changes

Adds optional per-job cron pacing bounds, CLI flags, protocol/tool schema support, and a self-scoped `next_check` action that clamps a successful isolated run’s requested next execution time.

## Best Possible Solution

Accept pacing only for recurring `every` and `cron` schedules at the canonical cron create/update boundary, reject incompatible schedule edits, add regression coverage for all schedule transitions, then attach redacted live/Testbox proof of a paced isolated run being clamped and scheduled.

Keep open: the reported rapid ACP child-session launch failure is still plausible, and current main plus the latest release still intentionally allow different ACP child sessions to initialize and run in parallel without live proof that the first-child no-output path is fixed.

## What This Changes

The issue asks OpenClaw to make rapid consecutive `sessions_spawn(runtime="acp")` calls reliably launch both ACP/Claude child sessions instead of leaving the first accepted child with no process output.

## Best Possible Solution

Run a current live ACPX/Claude rapid two-spawn smoke; if it reproduces, fix the confirmed launch-readiness boundary while preserving distinct-session parallelism unless maintainers deliberately choose a narrower concurrency gate.

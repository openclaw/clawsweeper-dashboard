## Summary

The previous blocking concern remains on the latest head: the request guard starts earlier, stays armed through body consumption, and receives effectively the same timeout as the new chunk-idle timer, so a real stalled download can still produce the generic request timeout before the claimed xAI-specific error. The patch also lacks after-fix proof of that timer race through the unmocked guarded-fetch path.

## What This Changes

The PR adds an xAI generated-video body chunk-idle timeout and provider-specific stall error, with mocked and loopback regression tests.

## Best Possible Solution

Define one explicit provider-download policy with a body-idle deadline meaningfully shorter than the hard request deadline, apply it consistently to affected provider siblings, and prove with an unmocked loopback stall that the xAI-specific idle error occurs before the generic request timeout.

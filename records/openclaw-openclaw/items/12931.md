## Summary

Keep open: current main and v2026.6.11 still lack a public reset-start policy for cheaper reset greetings, explicit greeting suppression, or opt-in startup/model turns; this remains a compatibility-sensitive product/config decision rather than cleanup-close material.

## What This Changes

The issue requests configurable bare `/new` and `/reset` greeting behavior, either by using a cheaper model for the greeting turn or by suppressing the greeting/model invocation.

## Best Possible Solution

Define one maintainer-approved reset-start policy that covers acknowledgements, startup/model turns, prompt text, greeting suppression, and optional greeting-model routing across auto-reply, Gateway, schema, docs, and tests.

Options:

- **Add explicit reset-start policy (recommended):** Keep current acknowledgement behavior unless maintainers choose otherwise, and add one typed policy that covers startup turns, prompt text, suppression, and greeting-model routing.
- **Restore startup turns by default:** Make bare resets run the startup/model turn again and explicitly accept the token-cost, latency, and upgrade behavior change.
- **Defer new reset controls:** Keep current acknowledgement-only behavior and use `/new <message>` plus the narrower prompt-text tracker until a broader reset policy is approved.

Yes. At source level, current main and v2026.6.11 have terminal acknowledgement branches for bare resets and strict schemas without the requested greeting model, suppression, or unified reset-start policy keys; I did not run a live reset flow in this read-only review.

## Solution Assessment

Unclear until maintainers choose the reset-start contract. A standalone `resetGreetingModel` or `resetGreeting` flag is plausible, but the safer solution is one typed policy that aligns prompt text, startup turns, suppression, model routing, and Gateway behavior.

## Summary

Keep open: current main and v2026.6.11 solve the original token-burn path for ordinary bare resets by returning static acknowledgements, but they still do not provide the requested typed reset-greeting policy, cheaper greeting model routing, or configurable restore/suppress behavior across reset surfaces.

## What This Changes

Request to make bare `/new` and `/reset` greeting behavior configurable by routing greeting turns to a cheaper model or suppressing the model-run greeting.

## Best Possible Solution

Define one reset-greeting policy for chat acknowledgements, reply-producing reset turns, and Gateway agent resets, with schema/types/help/docs/tests covering suppression, explicit model selection, and the chosen default.

- **Unified policy, current no-model default (recommended):** Keep today’s static acknowledgement as the default, but add a typed opt-in policy for model greeting and optional cheaper reset-greeting model routing.
- **Restore model greeting by default:** Make bare resets run the model again by default, with an explicit suppress/static-ack option for users optimizing token spend.
- **Close config request:** Keep current static acknowledgements and leave reset prompt/model selection unconfigurable, accepting that users who want greeting behavior must use follow-up text or another workflow.

Yes at source level. Current main and v2026.6.11 show static acknowledgement behavior for bare resets, a hardcoded reset prompt when a model path is reached, and no reset-greeting model or suppression/restore config keys in schema/docs.

## Solution Assessment

Unclear until maintainers choose the product contract. The narrow implementation should not be ad hoc config keys; it should be one typed reset-greeting policy shared by the command, reply-run, Gateway, schema, docs, and tests surfaces.

## Summary

Keep open: current `main` and the latest release provide acknowledgement-only bare reset behavior and startup-context tuning, but they still do not expose the requested typed policy to choose a reset-specific greeting model, suppress/opt into greeting turns, or align that behavior across chat and Gateway surfaces.

## What This Changes

The issue requests a configurable bare `/new` and `/reset` greeting policy, either to suppress the greeting or run it on a cheaper reset-specific model.

## Best Possible Solution

Define one maintainer-approved reset-start policy covering acknowledgement-only resets, optional startup/greeting turns, prompt customization, reset-specific model routing, schema/types/help/docs, and focused tests across auto-reply and Gateway.

## Reproduction Assessment

Yes, at source level. Current main has acknowledgement-only bare reset paths, hardcoded downstream reset prompts for model-run resets, and strict config schemas with `startupContext` but no reset greeting model or reset greeting policy key.

## Solution Assessment

No, not as independent ad hoc keys yet. The issue identifies a real reset-start policy gap, but the best fix should be one typed cross-surface policy chosen by maintainers before adding public config.

## Summary

Keep open: current main and v2026.6.11 partially solve the token-burn case with static acknowledgements for ordinary bare resets, but they still lack a supported reset-greeting model, suppression, or unified reset-start policy; the remaining work is a compatibility-sensitive product/config decision.

## What This Changes

The issue requests a configurable cheaper model or suppression option for model-generated greetings after bare `/new` or `/reset`.

## Best Possible Solution

Define one maintainer-approved reset-start policy that covers acknowledgements, startup/model turns, prompt text, greeting suppression, and optional greeting-model routing across auto-reply, Gateway, schema, docs, and tests.

- **Restore startup turns by default:** Make bare resets run the startup/model turn again and explicitly accept the token-cost, latency, and upgrade behavior change.
- **Defer new reset controls:** Keep acknowledgement-only bare resets and leave prompt/fallthrough requests in their narrower trackers until the broader policy is approved.

Unclear until maintainers choose the reset-start contract. A standalone `resetGreetingModel` or `resetGreeting` flag is plausible, but the safer solution is one typed policy that aligns prompt text, startup turns, suppression, model routing, and Gateway behavior.

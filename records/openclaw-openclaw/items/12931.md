## Summary

Keep open: current main has partly addressed the original token-burn concern by making ordinary bare reset commands return static acknowledgements, but it still lacks the requested configurable reset-start policy for opting into a greeting turn, choosing a cheaper reset-specific model, or suppressing/acknowledging behavior consistently across chat and Gateway surfaces.

## What This Changes

The issue requests a configurable reset greeting policy for bare `/new` or `/reset`, either to use a cheaper greeting model or suppress the greeting/model turn entirely.

## Best Possible Solution

Define one maintainer-approved reset-start policy covering acknowledgement-only resets, optional startup/greeting turns, prompt customization, reset-specific model routing, schema/types/help/docs, and focused tests across auto-reply and Gateway.

## Reproduction Assessment

Yes, at source level. Current main has acknowledgement-only bare reset paths, a hardcoded downstream reset prompt for model-run resets, and strict config schemas with `startupContext` but no reset greeting model or reset greeting policy key.

## Solution Assessment

Unclear. The suggested keys are plausible, but the best fix should be one typed cross-surface reset-start policy rather than independent config knobs that diverge chat, Gateway, prompt, and model-routing semantics.

## Summary

Keep open: current main still lacks the requested reset-greeting model or typed suppression policy. Bare reset commands are acknowledgement-only today, while the downstream reset prompt/model paths remain hardcoded or body-dependent, so this needs maintainer product/config direction rather than cleanup closure.

## What This Changes

Add configurable /new and /reset greeting behavior so users can suppress the greeting or run it on a cheaper model instead of the session default.

## Best Possible Solution

Define one typed reset-start policy covering acknowledgement-only resets, optional startup/greeting turns, prompt customization, and reset-specific model routing across schema, auto-reply, Gateway, docs, and tests.

## Reproduction Assessment

Yes, at source level: current main has acknowledgement-only bare reset paths, a hardcoded downstream reset prompt, and no resetGreeting/resetGreetingModel config key. I did not run a live Gateway scenario for this read-only review.

## Solution Assessment

Unclear. The proposed keys are plausible, but the best fix is a single maintainer-approved reset-start policy rather than independent knobs that could diverge across chat, Gateway, startupContext, and model override paths.

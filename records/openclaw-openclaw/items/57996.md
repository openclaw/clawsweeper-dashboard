## Summary

Keep open. Current main and the latest release still route QMD through an agent-local XDG cache and `qmd/index.sqlite`; related work only addresses adjacent embed scheduling, write serialization, or export-cache behavior, not the reported multi-agent QMD store multiplication, compaction, eviction, or write-amplification problem.

## What This Changes

The issue reports excessive disk I/O from per-agent QMD SQLite caches in multi-agent deployments and asks for shared storage, maintenance, reduced-write modes, or cache limits.

## Best Possible Solution

Move QMD's durable per-agent index sidecar toward the database-first plan, or choose a narrower owner-approved maintenance policy, then validate with a live multi-agent workload that measures DB size, WAL sidecars, disk writes, and gateway recovery.

## Reproduction Assessment

Yes for the core layout claim from source: current main still gives each agent its own QMD XDG cache and `index.sqlite`. No for the exact 19-agent macOS disk-write and forced-logout magnitude because this read-only review did not run that live workload.

## Solution Assessment

Unclear. The requested directions are plausible, but the best maintainable fix needs memory/QMD owner judgment between automatic QMD maintenance, shared or temporary materialized storage, eviction, reduced-write behavior, and explicit config.

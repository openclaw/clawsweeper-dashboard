## Summary

Keep open. Current main and the latest release still give each agent its own QMD `xdg-cache/qmd/index.sqlite`, and the existing write lock explicitly allows different agents to write their separate stores in parallel; related PRs address adjacent same-store contention or session-export churn, not the reported multi-agent cache layout, compaction, eviction, or write-amplification problem.

## What This Changes

The issue requests reducing QMD SQLite cache write amplification and disk growth for multi-agent deployments that run many independent per-agent QMD indexes.

## Best Possible Solution

Have the memory/QMD owner choose one canonical multi-agent QMD storage and maintenance policy, then validate it with live multi-agent disk-write, WAL, DB-size, and gateway-recovery measurements.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes for the source-level layout claim: current main still gives each agent its own QMD `xdg-cache/qmd/index.sqlite`; no for the exact 19-agent macOS disk-write magnitude because this review did not run that live workload.

## Solution Assessment

Is this the best way to solve the issue? Unclear: the suggested fixes are plausible, but shared QMD storage, automatic cleanup, eviction, and reduced-write/config modes carry different dependency, migration, and operator tradeoffs.

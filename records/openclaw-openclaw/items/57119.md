## Summary

Keep open. Current main and v2026.6.11 still treat `skills.entries.<key>.enabled: false` as skill visibility/eligibility rather than a hard read/exec access boundary, so this needs maintainer security/product direction.

## What This Changes

Request to make `skills.entries.<key>.enabled: false` block direct read and exec access to that skill directory, not only remove it from skill selection and prompt surfaces.

## Best Possible Solution

Define the disabled-skill security contract, then enforce a single central access policy across skill discovery, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

## Maintainer Decision

Kind: security_boundary

Question: Should `skills.entries.<key>.enabled:false` become a hard read/exec access boundary for that skill, or should hard skill isolation use a separate strict policy while `enabled:false` remains a visibility toggle?

Rationale: The source repro is clear, but either answer changes public disabled-skill semantics and crosses filesystem, exec, sandbox, UI/status, docs, and upgrade expectations.

Likely owner: steipete

Owner reason: This is primarily a product-security boundary decision, and recent history links steipete to skill install hardening and shared sandbox/gateway security plumbing.

Owner confidence: medium

Options:

- **Make `enabled:false` a hard deny boundary (recommended):** Treat prompt-only hiding as `disable-model-invocation` and deny disabled skill roots centrally for read, write/edit/apply_patch where relevant, exec, sandbox materialization, UI/status, and docs.
- **Add a separate strict isolation policy:** Keep `enabled:false` as an eligibility toggle for compatibility and add an explicit operator-controlled hard isolation policy for disabled-skill file and exec denial.
- **Document current semantics only:** Clarify that disabled skills are hidden from prompt/selection only and require sandboxing, tool deny lists, OS users, or containers for enforcement.

## Reproduction Assessment

Yes, at source level. Current main filters disabled skills out of eligibility and prompt/status surfaces, while read and exec access still use generic filesystem, sandbox, approval, and safe-bin policy instead of disabled skill paths.

## Solution Assessment

Unclear as an implementation path. The security direction is valid, but maintainers need to choose whether `enabled:false` becomes a hard compatibility boundary or whether a separate strict policy owns hard isolation.

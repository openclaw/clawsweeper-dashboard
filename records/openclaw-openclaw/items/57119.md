## Summary

Keep open. Current main and v2026.6.11 still treat disabled skills as eligibility and prompt/status visibility, while read and exec access are governed by generic filesystem, sandbox, approval, and tool policy rather than a disabled-skill access boundary.

## What This Changes

The issue asks for `skills.entries.<name>.enabled:false` and skill disabling surfaces to block read and exec access to the disabled skill directory, not only hide it from prompt or auto-matching.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce one central skill-access policy across discovery, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `skills.entries.<key>.enabled:false` become a hard read/exec access boundary for that skill, or should hard skill isolation use a separate explicit policy while `enabled:false` remains an eligibility toggle?

Rationale: The source-level gap is clear, but either answer changes public disabled-skill semantics across filesystem tools, exec, sandbox materialization, UI/status, docs, and upgrade expectations.

Likely owner: steipete

Owner reason: This is primarily a security/product boundary choice, and the strongest history signal is recent skill install security hardening and adjacent trust-surface work.

Owner confidence: medium

Options:

- **Make `enabled:false` a hard deny boundary (recommended):** Treat prompt-only hiding as `disable-model-invocation` and centrally deny disabled skill roots for file tools, exec, sandbox materialization, UI/status, and docs.
- **Add separate strict isolation policy:** Keep `enabled:false` as an eligibility toggle for compatibility and add an operator-controlled policy for disabled-skill file and exec denial.
- **Document current semantics only:** Clarify that disabled skills are hidden from prompt and selection only, and require sandboxing, tool deny lists, OS users, or containers for hard enforcement.

## Solution Assessment

Unclear as an implementation path: the security direction is valid, but maintainers need to choose whether `enabled:false` becomes a hard compatibility boundary or whether a separate strict policy owns hard isolation.

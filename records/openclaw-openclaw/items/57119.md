## Summary

Keep open. Current main and v2026.6.11 still treat `skills.entries.<skillKey>.enabled:false` as skill eligibility and prompt/status visibility, while read and exec access remain governed by generic filesystem, sandbox, approval, and tool policy; the related filesystem-roots PR is open, conflicting, and explicitly leaves exec unchanged.

## What This Changes

Request that `skills.entries.<skillKey>.enabled:false` hard-deny agent read and exec access to that skill's files and scripts, not only remove it from skill matching and prompt visibility.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce one central skill-access policy across discovery, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

Options:

- **Make `enabled:false` a hard boundary (recommended):** Treat prompt-only hiding as `disable-model-invocation` and centrally deny disabled skill roots for read, write/edit/apply_patch where relevant, exec, sandbox materialization, UI/status, and docs.
- **Add separate strict isolation policy:** Keep `enabled:false` as an eligibility toggle for compatibility and add an explicit operator-controlled policy for disabled-skill file and exec denial.
- **Document current semantics only:** Clarify that disabled skills are hidden from prompt/selection only and tell mixed-trust deployments to use sandboxing, tool deny lists, OS users, containers, or separate gateways for enforcement.

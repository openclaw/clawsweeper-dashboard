## Summary

Keep open. Current main still treats `skills.entries.<key>.enabled: false` as skill eligibility and prompt/status visibility, while file reads and shell execution are governed by generic filesystem, sandbox, approval, and tool policy rather than a disabled-skill access boundary.

## What This Changes

The issue asks OpenClaw to make disabled skills inaccessible to agent read and exec paths, not only hidden from skill auto-matching or prompt exposure.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce one central skill-access policy across discovery, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

Options:

- **Make `enabled:false` a hard deny boundary (recommended):** Treat prompt-only hiding as `disable-model-invocation` and centrally deny disabled skill roots for read, write/edit/apply_patch where relevant, exec, sandbox materialization, UI/status, and docs.
- **Add a separate strict isolation policy:** Keep `enabled:false` as an eligibility toggle for compatibility and add an explicit operator-controlled policy for disabled-skill file and exec denial.
- **Document current semantics only:** Clarify that disabled skills are hidden from prompt/selection only and tell multi-user deployments to use sandboxing, tool deny lists, OS users, or containers for enforcement.

Yes, at source level: current main filters disabled skills out of eligibility and prompt/status surfaces, while read and exec access still use generic filesystem, sandbox, approval, and safe-bin policy instead of disabled skill paths. I did not run a live exploit because this review is read-only.

## Solution Assessment

Unclear as an implementation path: the security direction is valid, but maintainers need to choose whether `enabled:false` becomes a hard compatibility boundary or whether a separate strict policy owns hard isolation.

## Summary

Keep open. Current main still only uses `skills.entries.<name>.enabled: false` to remove a skill from eligibility/prompt/status surfaces; generic `read` and `exec` access remains controlled by workspace, sandbox, approval, and tool policy rather than a disabled-skill boundary, so the requested security semantics still need maintainer security/product review.

## What This Changes

The issue requests that disabled skills become inaccessible to agent file reads and script execution, not merely hidden from automatic skill matching.

## Best Possible Solution

Maintainers should define the intended trust model for disabled skills first, then implement one consistent enforcement boundary with docs and upgrade guidance across read, exec, sandbox, and UI/config surfaces.

## Reproduction Assessment

Yes, source inspection gives a high-confidence path: disabled skills are removed from eligibility, while read and exec enforcement still comes from generic tool policies rather than a disabled-skill deny boundary.

## Solution Assessment

Unclear; the issue identifies a real gap, but the best fix requires maintainer choice about whether `enabled:false` should become hard authorization, whether exec should be disabled or sandboxed separately, and how to preserve upgrade expectations.

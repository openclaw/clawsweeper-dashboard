## Summary

Keep open. Current main and v2026.6.11 still treat `skills.entries.<key>.enabled: false` as a skill eligibility/prompt-visibility control, while read and exec access are governed by generic filesystem, sandbox, approval, and tool policy rather than disabled-skill roots.

## What This Changes

Request to make disabled skills enforce a read/exec access boundary instead of only hiding them from skill eligibility and prompt surfaces.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce one central skill-access policy across discovery, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

Options:

- **Make `enabled:false` a hard deny boundary (recommended):** Treat prompt-only hiding as `disable-model-invocation` and centrally deny disabled skill roots for read, write/edit/apply_patch where relevant, exec, sandbox materialization, UI/status, docs, and tests.
- **Add a separate strict isolation policy:** Keep `enabled:false` as an eligibility toggle for compatibility and add an explicit operator-controlled policy for disabled-skill file and exec denial.
- **Document current semantics only:** Clarify that disabled skills are hidden from prompt/selection only and tell multi-user deployments to use sandboxing, tool deny lists, OS users, or containers for enforcement.

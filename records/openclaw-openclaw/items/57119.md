## Summary

Keep open. Current main and v2026.6.11 still treat `skills.entries.<key>.enabled: false` as eligibility and prompt/status visibility, while read and exec remain governed by generic filesystem, sandbox, approval, and tool policies rather than a disabled-skill access boundary.

## What This Changes

The issue asks for `skills.entries.<name>.enabled: false` to block reads and script execution from that skill directory, not just remove the skill from model-visible matching.

## Best Possible Solution

Define the disabled-skill security contract first, then enforce one central skill-access policy across discovery, read/write/edit/apply_patch, exec/sandbox materialization, Gateway/UI status, docs, and focused tests.

Question: Should `skills.entries.<key>.enabled:false` become a hard read/exec access boundary, or should hard skill isolation use a separate strict policy while `enabled:false` remains an eligibility and prompt-visibility toggle?

Rationale: The code change crosses public skill semantics, filesystem reads, shell execution, sandbox behavior, UI wording, and security documentation; automation cannot choose that compatibility/security tradeoff safely.

Likely owner: steipete

Options:

- **Make disabled a hard boundary (recommended):** Treat `enabled:false` as a deny rule for the skill directory across model exposure, direct skill invocation, read/write/edit/apply_patch, exec, sandbox materialization, UI, docs, and tests.
- **Add strict isolation separately:** Keep current `enabled:false` compatibility as an eligibility toggle and add an explicit operator-controlled strict policy for disabled-skill filesystem and exec denial.
- **Document current trust model:** Leave enforcement to existing filesystem, sandbox, exec approval, and plugin governance controls while making the non-boundary semantics explicit in UI and docs.

Yes, source-reproducible: current main filters disabled skills from eligibility and prompt/status surfaces, while read and exec paths do not enforce disabled skill directories as deny roots; no live exploit was run during this read-only review.

## Summary

Keep open. Current main and v2026.6.11 still treat `skills.entries.<key>.enabled: false` as eligibility, prompt, and status filtering rather than a hard read/exec access boundary, and the related filesystem-roots PR is still open and explicitly leaves exec/tool allow-deny behavior unchanged.

## What This Changes

Request to make disabled skills inaccessible to file reads and script execution instead of only hiding them from automatic skill matching.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce one central skill-access policy across discovery, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

Rationale: The source repro is clear, but either answer changes public disabled-skill semantics and crosses filesystem, exec, sandbox, UI/status, docs, and upgrade expectations.

Options:

- **Make disabled mean hard deny (recommended):** Treat prompt-only hiding as `disable-model-invocation` and centrally deny disabled skill roots for read, write/edit/apply_patch where relevant, exec, sandbox materialization, UI/status, and docs.
- **Add strict isolation separately:** Keep `enabled:false` as an eligibility toggle for compatibility and add an explicit operator-controlled policy for disabled-skill file and exec denial.
- **Document current semantics:** Clarify that disabled skills are hidden from prompt/selection only and direct multi-user deployments to sandboxing, tool deny lists, OS users, or containers for enforcement.

Unclear as an implementation path: the security direction is valid, but maintainers need to choose whether `enabled:false` becomes a hard compatibility boundary or whether a separate strict policy owns hard isolation.

## Summary

Keep open. Current main and v2026.6.11 still treat `skills.entries.<key>.enabled: false` as skill eligibility and prompt/status filtering, while `read` and `exec` remain governed by generic filesystem, sandbox, approval, and tool policy controls rather than a disabled-skill access boundary.

## What This Changes

The issue requests that `skills.entries.<name>.enabled: false` become an enforced boundary that blocks agents from reading or executing files inside the disabled skill directory.

## Best Possible Solution

Make the disabled-skill security contract explicit, then enforce it through one central policy surface or deliberately route hard access control to a broader capability/filesystem policy instead of leaving the UI toggle as a security claim.

Options:

- **Define a hard disabled-skill boundary (recommended):** Treat disabled skill directories as centrally denied roots and make exec either deny those paths, run under isolation that enforces them, or clearly disable exec for that guarantee.
- **Keep enabled as eligibility-only:** Document and rename the UI/config semantics so operators know hard access control must be handled by tool policy, sandboxing, or filesystem roots.
- **Fold into capability policy:** Canonicalize this under the broader skill/tool capability model and keep #57119 linked as the disabled-toggle acceptance case.

## Reproduction Assessment

Yes at source level: current main filters disabled skills out of eligibility and prompt/status surfaces, while read and exec access still use generic filesystem, sandbox, approval, and tool policy instead of disabled-skill paths.

## Solution Assessment

No single best implementation is established yet; direct disabled-path enforcement is plausible, but exec makes a path-only fix too narrow unless the design also addresses shell isolation or routes the work into the broader capability policy.

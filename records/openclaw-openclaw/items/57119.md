## Summary

Keep open. Current main and the latest release still treat `skills.entries.<key>.enabled: false` as skill eligibility and prompt/status filtering, not as a hard read or exec access boundary; the related filesystem-roots PR is only partial overlap and is still open/conflicting with exec explicitly unchanged.

## What This Changes

Request to make `skills.entries.<name>.enabled: false` enforce a hard access boundary that blocks reading and executing files from that skill directory.

## Best Possible Solution

Define a maintainer-approved disabled-skill security contract, then enforce one central skill-access policy across prompt exposure, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

Question: Should `skills.entries.<key>.enabled: false` become a hard read/exec access boundary for that skill's files, or remain a visibility-only control with a separate isolation policy?

Rationale: The current behavior is source-reproducible, but changing it affects security semantics and compatibility for existing operators who may rely on generic tool, sandbox, and OS controls.

Likely owner: Peter Steinberger

Owner reason: The decision crosses security posture, exec policy, and compatibility boundaries where local history points most strongly to Peter's prior work.

Owner confidence: medium

Options:

- **Make disabled skills a hard boundary (recommended):** Treat `enabled:false` as a deny rule for prompt exposure plus skill-root read/write/edit/apply_patch, exec, and sandbox materialization, with docs and upgrade proof.
- **Add separate strict isolation policy:** Keep `enabled:false` as visibility-only and add an explicit strict skill isolation mode for deployments that need this boundary.
- **Document trusted-code limitation:** Keep current runtime behavior and clarify that disabled skills are not an authorization boundary, relying on sandboxing, tool policy, OS users, and install policy.

## Reproduction Assessment

Yes, at source level: disabled skills are filtered out of eligibility/prompt snapshots, while read and exec still use generic filesystem, sandbox, approval, and tool policy. I did not run a live exploit because this review is read-only.

## Solution Assessment

Unclear as an implementation path: the security direction is valid, but maintainers need to choose whether `enabled:false` changes semantics or a separate strict policy carries the hard boundary.

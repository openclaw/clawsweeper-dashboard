## Summary

Keep open. Current main and v2026.6.11 still treat `skills.entries.<key>.enabled:false` as skill eligibility/prompt visibility, while hard read and exec access remain governed by generic filesystem, sandbox, approval, and tool policy rather than a disabled-skill access boundary.

## What This Changes

Request to make `skills.entries.<name>.enabled:false` block reading or executing files under disabled skill directories, not only remove the skill from prompt and auto-match surfaces.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce one central skill-access policy across discovery, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

- **Document current semantics only:** Clarify that disabled skills are hidden from prompt/selection only and tell multi-user deployments to use sandboxing, tool deny lists, OS users, or containers for enforcement.

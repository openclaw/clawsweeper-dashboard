## Summary

Keep open. Current main still filters disabled skills out of eligible skill snapshots, but `read` and `exec` are governed by generic filesystem, sandbox, approval, and tool-policy controls rather than a disabled-skill access boundary; the related filesystem-roots PR is open and explicitly leaves `exec` unchanged.

## What This Changes

Request that `skills.entries.<skillKey>.enabled: false` become an enforced read/exec access boundary for that skill directory, not only a skill-discovery and prompt toggle.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce one central skill-access policy across prompt exposure, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

Question: Should `skills.entries.<skillKey>.enabled: false` become a hard read/exec deny boundary for that skill directory, or should OpenClaw keep it prompt-only and add a separate strict skill-access policy?

Rationale: Both options change operator expectations: hard denial improves safety but can be a compatibility break, while a separate strict mode preserves current behavior but leaves the reported security gap unless operators opt in.

Likely owner: Peter Steinberger

Owner reason: The decision crosses secops-owned agent/sandbox paths and Peter has recent security and exec-policy history in the affected area.

Owner confidence: medium

Options:

- **Make `enabled:false` a hard boundary (recommended):** Treat disabled skill directories as denied roots everywhere the agent can read, write, materialize, or execute skill files, with docs and upgrade notes for the behavior change.
- **Add an explicit strict skill-access policy:** Keep current `enabled:false` prompt semantics and add a separate operator-controlled enforcement mode for deployments that require a hard skill filesystem boundary.
- **Document prompt-only semantics:** Declare disabled skills as prompt/eligibility-only and rely on sandbox, tool policy, install policy, and OS isolation for hard security boundaries.

## Summary

Keep open. Current main and v2026.6.11 still treat `skills.entries.<key>.enabled: false` as an eligibility and prompt/status filter, while file access and shell execution remain governed by generic tool, filesystem, sandbox, and exec policy rather than a disabled-skill access boundary.

## What This Changes

Request to make disabled skills inaccessible to agent file reads and script execution, not only hidden from automatic skill matching.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce it through one central skill-access policy reused by prompt exposure, file tools, sandbox materialization, exec guidance or gating, Gateway/UI status, docs, and regression tests.

Question: Should `skills.entries.<key>.enabled: false` become a hard security boundary that denies agent reads and execution from that skill directory, or should OpenClaw keep it as an eligibility-only control with a separate strict isolation policy?

Rationale: Both choices are plausible: hard-deny matches user expectations and security wording, but it changes existing semantics and `exec` cannot be made safe by simple command-text filtering.

Options:

- **Make disabled skills hard-denied (recommended):** Treat `enabled:false` as a central deny policy for skill-owned file exposure and document how exec/sandbox deployments must enforce the remaining boundary.
- **Add a separate strict isolation mode:** Keep current compatibility for `enabled:false` and add an explicit operator-controlled policy for deployments that need disabled-skill path denial.
- **Document eligibility-only semantics:** Leave runtime behavior unchanged and update UI/docs to avoid implying disabled skills are sandboxed or inaccessible.

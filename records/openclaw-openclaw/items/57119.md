## Summary

Keep open. Current main still treats `skills.entries.<key>.enabled: false` as skill eligibility and prompt/status visibility, while direct read and exec access are governed by generic filesystem, sandbox, approval, and tool policy instead of a disabled-skill access boundary.

## What This Changes

The issue asks OpenClaw to make disabled skills inaccessible to agent read and exec paths, not only hidden from automatic skill matching.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce one central skill-access policy across discovery, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

Question: Should `skills.entries.<key>.enabled:false` become a hard read/exec access boundary for that skill, or should hard skill isolation use a separate strict policy while `enabled:false` remains an eligibility toggle?

Rationale: The source reproduction is clear, but either answer changes public disabled-skill semantics and crosses filesystem, exec, sandbox, UI/status, docs, and upgrade expectations.

Likely owner: steipete

Owner reason: This is primarily a security/product boundary decision, and his history is the strongest match for skill trust and sandbox boundary direction.

Owner confidence: medium

Options:

- **Make disabled mean hard deny (recommended):** Treat prompt-only hiding as `disable-model-invocation` and centrally deny disabled skill roots for file tools, exec, sandbox materialization, UI/status, docs, and tests.
- **Add strict isolation policy:** Keep `enabled:false` as an eligibility toggle for compatibility and add an explicit operator-controlled policy for disabled-skill file and exec denial.
- **Document current semantics:** Clarify that disabled skills are hidden from prompt/selection only and tell multi-user deployments to use sandboxing, tool deny lists, OS users, or containers for enforcement.

## Reproduction Assessment

Yes, at source level. Current main filters disabled skills out of eligibility and prompt/status surfaces, while read and exec access still use generic filesystem, sandbox, approval, and safe-bin policy rather than disabled skill paths.

## Solution Assessment

Unclear as an implementation path. The security direction is valid, but maintainers need to choose whether `enabled:false` becomes a hard compatibility boundary or whether a separate strict policy owns hard isolation.

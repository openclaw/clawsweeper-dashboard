## Summary

Keep open. Current main and v2026.6.11 still treat `skills.entries.<key>.enabled:false` as an eligibility and visibility control, while read and exec access remain governed by generic filesystem, sandbox, approval, and tool policy rather than disabled-skill roots.

## What This Changes

The issue requests that disabled skills become an enforced read/exec access boundary, not only hidden from skill auto-selection.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce one central skill-access policy across discovery, read/write/edit/apply_patch, exec/sandbox handling, Gateway/UI status, docs, and regression tests.

Options:

- **Make enabled:false a hard deny boundary (recommended):** Treat prompt-only hiding as `disable-model-invocation` and centrally deny disabled skill roots for read, write/edit/apply_patch where relevant, exec, sandbox materialization, UI/status, and docs.
- **Add separate strict isolation policy:** Keep `enabled:false` as a compatibility-preserving eligibility toggle and add an explicit operator-controlled policy for disabled-skill file and exec denial.
- **Document current trusted-skill semantics:** Clarify that disabled skills are hidden from selection only and tell multi-user deployments to use sandboxing, tool denies, OS users, or containers for enforcement.

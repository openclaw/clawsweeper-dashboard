## Summary

Keep open. Current main and the latest release still treat `skills.entries.<skillKey>.enabled: false` as eligibility/prompt/status filtering, not as a read/exec deny boundary for files under the disabled skill directory.

## What This Changes

Request to make disabled skills enforceable so `enabled: false` blocks agent read and execution access to that skill's files and scripts.

## Best Possible Solution

Define an explicit disabled-skill security contract and enforce it centrally across skill exposure, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `skills.entries.<skillKey>.enabled: false` become a hard read/exec access boundary, or remain a prompt/status visibility setting while a separate capability-grant model handles enforcement?

Rationale: Both choices are plausible but compatibility-sensitive: the security request aligns with safe defaults, while changing existing `enabled:false` semantics affects operator expectations and multiple execution surfaces.

Likely owner: steipete

Owner reason: Current history and related security-capability discussions point to steipete as the best available owner for the security-boundary product decision.

Owner confidence: medium

Options:

- **Make disabled skills deny access (recommended):** Treat `enabled:false` as an enforceable deny boundary for the skill directory and add upgrade-facing docs/tests for read, write/edit/apply_patch, exec, and sandbox paths.
- **Route through capability grants:** Keep `enabled:false` visibility-only and require the broader capability-manifest/grant model in https://github.com/openclaw/openclaw/issues/12678 before enforcing per-skill runtime access.
- **Document trusted-code model:** Leave disabled skills as prompt/status filtering and document that skill folders remain trusted host code unless operators restrict filesystem and exec access separately.

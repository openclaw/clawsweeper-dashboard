## Summary

Keep open. Current main still treats `skills.entries.<key>.enabled: false` as skill discovery/prompt eligibility, while `read` and `exec` remain governed by generic filesystem, sandbox, and exec policy rather than a disabled-skill deny boundary.

## What This Changes

The issue asks for disabled skills to become an enforced filesystem and execution boundary, not only a discovery and prompt toggle.

## Best Possible Solution

Maintainers should define the intended trust model for disabled skills, then implement one consistent boundary across skill discovery/status, host file tools, sandbox materialization, exec policy, UI/docs wording, and upgrade guidance.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `skills.entries.<key>.enabled:false` become a hard authorization boundary for skill directories, or remain an eligibility/prompt control with isolation handled by sandbox and tool policy?

Rationale: Both choices are plausible but have different security and compatibility meanings, and the repo policy treats security boundaries, config semantics, and fail-closed behavior as maintainer-owned decisions.

Likely owner: vincentkoc

Owner reason: Recent work spans both the skill loader and agent tool policy layers that would need to agree on the boundary.

Owner confidence: medium

Options:

- **Define a hard disabled-skill boundary (recommended):** Make disabled skills unreadable and non-executable through the supported tool surfaces, with tests and docs that name any sandbox or exec limitations.
- **Keep eligibility-only semantics:** Document that disabling a skill hides it from discovery/prompting but does not isolate files or scripts, and direct operators to sandbox/tool policy for hard boundaries.
- **Add an explicit strict mode:** Preserve current upgrade behavior by default and add a separately named strict security mode for deployments that want disabled skill directories denied.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: disabled skills are filtered from eligible/model-visible skill surfaces, while file reads and shell execution are still controlled by generic tool policy rather than disabled-skill directory denial.

## Solution Assessment

Unclear. The report identifies a real security semantics gap, but the best fix requires maintainer choice about whether to redefine `enabled:false`, add an explicit strict mode, or document the existing sandbox/tool-policy trust model.

## Summary

Keep open. Current main still treats `skills.entries.<key>.enabled: false` as skill eligibility and prompt/status visibility, while read and exec access are governed by general filesystem, sandbox, approval, and tool policy rather than a disabled-skill access boundary.

## What This Changes

The issue requests making disabled skills inaccessible to agent read and exec paths instead of only removing them from skill discovery and prompts.

## Best Possible Solution

Define the disabled-skill security contract, then enforce the chosen policy centrally across skill discovery, filesystem tools, exec/sandbox materialization, UI/status, docs, and regression tests.

Rationale: The source-level gap is clear, but either outcome changes a security boundary and compatibility expectations across skills, filesystem tools, exec, sandboxing, UI/status, and docs.

Options:

- **Add explicit strict isolation policy (recommended):** Keep `enabled:false` compatible as a visibility/eligibility toggle, add a separate operator-controlled hard isolation policy, and make the UI/docs distinguish the two states.
- **Make disabled mean hard deny:** Treat `enabled:false` as a central deny boundary for disabled skill roots across read, write/edit/apply_patch where relevant, exec, sandbox materialization, UI/status, and docs.
- **Document current semantics only:** Leave the runtime unchanged and make docs/UI say disabled skills are hidden from discovery, while sandboxing, OS users, and tool policy own hard isolation.

Yes. Source inspection shows disabled skills are filtered out of eligible skill loading and prompt/status surfaces, while read and exec policy construction does not receive disabled skill roots to block.

## Solution Assessment

Unclear. Hard enforcement is a valid security direction, but maintainers first need to choose whether existing `enabled:false` semantics may change or whether a separate strict isolation control should own hard denial.

## Summary

Keep open. Current main and latest release still treat `skills.entries.<key>.enabled: false` as skill eligibility and prompt/status filtering, while `read` and `exec` remain governed by generic filesystem, sandbox, approval, and tool-policy controls rather than a disabled-skill access boundary.

## What This Changes

Request to make `skills.entries.<name>.enabled: false` block read and execution access to that skill directory, not only remove it from skill matching.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce one central skill-access policy across prompt exposure, filesystem tools, exec/sandbox materialization, Gateway/UI status, and docs.

Rationale: This changes a security boundary and public config semantics across trusted personal-agent and multi-user deployments, so automation cannot safely choose the permanent contract.

Options:

- **Define a hard disabled-skill boundary (recommended):** Make disabled skills inaccessible through central policy and update read/write/edit/apply_patch, exec, sandbox materialization, UI/status, docs, and regression tests around that contract.
- **Add a separate strict access policy:** Keep `enabled:false` as visibility/eligibility and introduce an explicit strict security mode for deployments that need disabled-skill filesystem and execution denial.
- **Document existing trusted-code model:** Keep current behavior and clarify that operators must use sandboxing, tool policy, install policy, and filesystem controls rather than `enabled:false` for access isolation.

## Reproduction Assessment

Yes. Source inspection shows disabled skills are filtered out of eligible/prompt-visible skill lists, while `read` and `exec` use generic filesystem, sandbox, approval, and exec policy inputs with no disabled-skill deny root.

## Solution Assessment

Unclear. The security direction is valid, but the best implementation depends on maintainer agreement about whether `enabled:false` is a hard boundary or whether a separate strict policy should own access denial.

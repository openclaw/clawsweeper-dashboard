## Summary

Keep open. Current main and v2026.6.11 still treat disabled skills as eligibility/prompt visibility, while read and exec access are governed by generic filesystem, sandbox, approval, and tool policy rather than a disabled-skill access boundary.

## What This Changes

The issue requests that `skills.entries.<key>.enabled:false` and the UI skill toggle also block agent read/exec access to that skill directory.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce one central skill-access policy across discovery, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `skills.entries.<key>.enabled:false` become a hard read/exec access boundary for that skill, or should hard skill isolation use a separate strict policy while `enabled:false` remains a visibility/loading toggle?

Rationale: The source repro is clear, but either answer changes public disabled-skill semantics and crosses filesystem, exec, sandbox, UI/status, docs, and upgrade expectations.

Likely owner: steipete

Owner reason: This is primarily a security/product boundary decision, and recent history links this owner to skill install hardening and security direction around skill trust surfaces.

Owner confidence: medium

Options:

- **Make disabled skills a hard boundary (recommended):** Treat prompt-only hiding as `disable-model-invocation` and centrally deny disabled skill roots for file access, exec, sandbox materialization, UI/status, docs, and tests.
- **Add a separate strict isolation policy:** Keep `enabled:false` as a compatibility-preserving eligibility toggle and add an explicit operator-controlled policy for disabled-skill file and exec denial.
- **Document current semantics only:** Clarify that disabled skills are hidden from prompt/selection only and tell multi-user deployments to use sandboxing, tool deny lists, OS users, or containers for enforcement.

## Reproduction Assessment

Yes, at source level: current main filters disabled skills out of eligibility and prompt/status surfaces, while read and exec access still use generic filesystem, sandbox, approval, and safe-bin policy instead of disabled skill paths. I did not run a live exploit because this review is read-only.

## Solution Assessment

Unclear as an implementation path: the security direction is valid, but maintainers need to choose whether `enabled:false` becomes a hard compatibility boundary or whether a separate strict policy owns hard isolation.

## Summary

Keep open. Current main and v2026.6.11 still treat `skills.entries.<key>.enabled: false` as skill eligibility/prompt visibility, while read and exec access remain governed by generic filesystem, sandbox, approval, and tool policy rather than a disabled-skill access boundary.

## What This Changes

The issue requests making disabled skills unreadable and non-executable rather than only removing them from automatic/model-visible skill selection.

## Best Possible Solution

Maintainers should define the disabled-skill security contract first, then implement one centralized enforcement path across skills, filesystem tools, exec/sandbox materialization, UI status, docs, and regression tests.

## Maintainer Decision

Question: Should `skills.entries.<key>.enabled:false` become a hard read/exec access boundary for that skill, or should hard skill isolation use a separate strict policy while `enabled:false` remains an eligibility toggle?

Rationale: The fix changes public disabled-skill semantics and can affect existing trusted workflows, while the durable security boundary crosses skill loading, filesystem tools, exec, sandboxing, Gateway/UI status, and docs.

Likely owner: Peter Steinberger

Owner reason: He is the clearest local history owner for the active skill filtering, skill security, and exec boundary surfaces involved in this choice.

Owner confidence: high

Options:

- **Make disabled a hard boundary (recommended):** Treat `enabled:false` as a deny policy for skill files and scripts, with upgrade notes and tests for read, exec, sandbox, UI, and docs behavior.
- **Add a separate strict isolation policy:** Keep `enabled:false` as a visibility/eligibility toggle and introduce an explicit strict skill isolation control for operators who need enforcement.
- **Document current semantics only:** Clarify that disabling a skill removes it from invocation surfaces but does not isolate host files or shell execution, and point users to sandboxing/tool-deny/OS isolation.

## Reproduction Assessment

Yes, at source level: current main filters disabled skills from eligible/model-visible snapshots while read and exec paths do not receive disabled-skill deny policy.

## Solution Assessment

Unclear until maintainers choose the contract: enforcing `enabled:false` is the strongest security answer, but it is compatibility-sensitive and must be designed as a central policy rather than a local filter.

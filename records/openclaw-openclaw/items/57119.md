## Summary

Keep open. Current main still treats `skills.entries.<key>.enabled: false` as skill eligibility and visibility filtering, while file reads and shell execution remain governed by generic filesystem, sandbox, approval, and tool policy controls rather than a disabled-skill access boundary.

## What This Changes

The issue asks OpenClaw to enforce disabled skills as a read/exec access boundary, not only as auto-match filtering.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce any chosen boundary through central skill-access policy shared by prompt exposure, filesystem reads/writes, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

## Reproduction Assessment

Yes, at source level: current main filters disabled skills out of eligibility and prompt/snapshot surfaces, while read and exec still use generic filesystem, sandbox, approval, and tool policy controls. I did not run a live exploit because this review is read-only.

## Solution Assessment

Unclear as an implementation path: the security direction is valid, but maintainers need to decide whether `enabled:false` becomes a hard compatibility boundary or whether a separate strict policy owns this behavior.

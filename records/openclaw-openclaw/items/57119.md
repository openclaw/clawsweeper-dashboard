## Summary

Keep open. Current main still treats `skills.entries.<key>.enabled:false` as a skill eligibility, prompt, and sandbox-sync filter rather than a hard read/exec authorization boundary, and the remaining work needs a maintainer security/product decision.

## What This Changes

Request to make disabled skills inaccessible to agent read and exec paths, not just hidden from skill matching and prompt visibility.

## Best Possible Solution

Choose and document the disabled-skill security contract, then enforce one central policy across discovery, filesystem tools, exec/sandbox materialization, Gateway/UI status, and regression tests.

- **Make `enabled:false` a hard deny boundary (recommended):** Treat prompt-only hiding as a different concept and centrally deny disabled skill roots for read, write/edit/apply_patch where relevant, exec, sandbox materialization, UI/status, and docs.
- **Add a separate strict isolation policy:** Keep `enabled:false` as an eligibility toggle for compatibility and add an explicit operator-controlled policy for disabled-skill file and exec denial.
- **Document current semantics only:** Clarify that disabled skills are hidden from prompt/selection only and tell multi-user deployments to use sandboxing, tool deny lists, OS users, or containers for enforcement.

Yes, at source level: current main filters disabled skills out of eligibility and prompt/status surfaces while read and exec access still use generic filesystem, sandbox, approval, and tool policy.

## Solution Assessment

Unclear until maintainers decide semantics: making `enabled:false` a hard deny is defensible, but a separate strict isolation policy may be safer for compatibility.

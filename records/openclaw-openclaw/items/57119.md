## Summary

Keep open. Current main and the latest release still treat `skills.entries.<key>.enabled: false` as discovery/prompt/status filtering, while read and exec access remain governed by generic filesystem, sandbox, and exec policy rather than a disabled-skill boundary.

## What This Changes

The issue requests that disabled skills be blocked from manual `SKILL.md` reads and script execution, not only removed from automatic skill matching.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce it through a central skill-access policy reused by prompt exposure, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

Question: Should `skills.entries.<key>.enabled: false` become a hard read/write/exec access boundary for that skill directory, or remain only a discovery, prompt, and command-visibility control?

Rationale: The current wording and UI say a skill is disabled, but enforcing that as isolation would change public config semantics and touch security-sensitive tool and sandbox boundaries.

Likely owner: steipete

Owner reason: The decision crosses security posture, skill semantics, sandboxing, and public UX, and the history points to steipete as the strongest available routing owner for that boundary choice.

Owner confidence: medium

Options:

- **Make disabled skills inaccessible (recommended):** Keep the existing UI/config wording and enforce denied skill roots for file tools and exec paths, with compatibility notes and targeted regression coverage.
- **Keep disable discovery-only:** Document and rename the behavior as visibility-only, then point operators to sandbox, filesystem, and exec policies for real isolation.
- **Introduce a separate strict policy:** Preserve current `enabled:false` compatibility and add an explicit strict skill-access policy for multi-user or untrusted-code deployments.

## Summary

Keep open. Current main still treats `skills.entries.<key>.enabled: false` as an eligibility and prompt/status filter, not as a hard filesystem or command-execution boundary for disabled skill directories.

## What This Changes

The issue requests that disabling a skill also block agents from reading or executing files under that skill directory.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce it through a central skill-access policy across discovery, filesystem tools, exec, sandbox materialization, Gateway/UI status, docs, and regression tests.

- **Make `enabled:false` hard deny (recommended):** Treat prompt-only hiding as `disable-model-invocation` and enforce disabled skill roots centrally for read, write/edit/apply_patch where relevant, exec, sandbox materialization, UI/status, and docs.
- **Add strict isolation policy:** Keep `enabled:false` as an eligibility toggle for compatibility and add an explicit operator-controlled policy for disabled-skill file and exec denial.
- **Document current semantics:** Clarify that disabled skills are hidden from prompt/selection only and instruct multi-user deployments to use sandboxing, tool deny lists, OS users, or containers for enforcement.

Yes, at source level: current main filters disabled skills out of eligibility and prompt/status surfaces, while read and exec access still use generic filesystem, sandbox, approval, and safe-bin policy. I did not run a live exploit because this review is read-only.

Unclear as an implementation path: the security direction is valid, but maintainers need to choose whether `enabled:false` becomes a hard compatibility boundary or whether a separate strict policy owns hard isolation.

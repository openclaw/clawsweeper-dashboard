## Summary

Keep open. Current main still treats `skills.entries.<key>.enabled: false` as skill eligibility and prompt/status filtering, while read and exec remain governed by generic filesystem, workspace, sandbox, and tool policy rather than a disabled-skill access boundary; the related filesystem-roots PR is open, conflicting, and explicitly leaves exec unchanged.

## What This Changes

The issue requests hard enforcement so disabled skills cannot be read from or executed through agent tools.

## Best Possible Solution

Define the disabled-skill security contract first, then enforce it through a central skill-access policy reused by prompt exposure, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `skills.entries.<name>.enabled: false` become a hard read/exec denial boundary for skill directories, or should OpenClaw keep it as visibility-only and add a separate strict skill-access policy?

Rationale: The code can enforce either shape, but the choice changes security semantics and compatibility for existing trusted setups, so automation should not choose it alone.

Likely owner: steipete

Owner reason: This is a security-boundary and product-semantics call, and Peter Steinberger has adjacent security hardening and project-direction history.

Owner confidence: medium

Options:

- **Make `enabled:false` a hard deny (recommended):** Disabled skills would be excluded from prompt/status surfaces and blocked centrally from read, write/edit/apply_patch, exec, and sandbox materialization paths, with docs and upgrade notes updated accordingly.
- **Add a separate strict policy:** Keep current visibility semantics for compatibility while adding an explicit operator-controlled hard-deny policy for untrusted or shared deployments.
- **Document current trust model only:** Treat skill folders as trusted code and clarify that disabling a skill only hides it from invocation surfaces, leaving filesystem isolation to sandbox and tool policies.

Unclear as an implementation path: the security direction is valid, but the best fix depends on maintainer agreement about whether `enabled:false` becomes a hard compatibility boundary or a separate strict policy is needed.

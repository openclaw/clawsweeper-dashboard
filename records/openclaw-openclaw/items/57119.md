## Summary

Keep open. Current main and v2026.6.11 still treat `skills.entries.<skillKey>.enabled:false` as skill eligibility and prompt/status visibility, while file and exec access remain governed by generic tool policy rather than a disabled-skill access boundary.

## What This Changes

Request to make `skills.entries.<skillKey>.enabled:false` block agent read and exec access to that skill directory, not only hide the skill from matching and prompt surfaces.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce one central skill-access policy across discovery, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

## Maintainer Decision

Kind: security_boundary

Question: Should `skills.entries.<skillKey>.enabled:false` become a hard read/exec access boundary for that skill, or should hard skill isolation use a separate strict policy while `enabled:false` remains an eligibility toggle?

Rationale: The source-level gap is clear, but either answer changes public disabled-skill semantics and crosses filesystem, exec, sandbox, UI/status, docs, and upgrade expectations.

Likely owner: steipete

Owner reason: The unresolved choice is primarily a security/product boundary decision, and recent history links this handle to skill install hardening and security direction around skill trust surfaces.

Owner confidence: medium

Options:

- **Make `enabled:false` a hard deny boundary (recommended):** Treat prompt-only hiding as a different mechanism and centrally deny disabled skill roots for read, write/edit/apply_patch where relevant, exec, sandbox materialization, UI/status, and docs.
- **Add a separate strict isolation policy:** Keep `enabled:false` as an eligibility toggle for compatibility and add an explicit operator-controlled policy for disabled-skill file and exec denial.
- **Document current semantics only:** Clarify that disabled skills are hidden from prompt/selection only and tell multi-user deployments to use sandboxing, tool deny lists, OS users, or containers for hard enforcement.

## Reproduction Assessment

Yes, at source level: current main filters disabled skills out of eligibility and prompt/status surfaces, while read and exec access still use generic filesystem, sandbox, approval, and safe-bin policy instead of disabled skill paths. I did not run a live exploit because this review is read-only.

## Solution Assessment

Unclear as an implementation path: the security direction is valid, but maintainers need to choose whether `enabled:false` becomes a hard compatibility boundary or whether a separate strict policy owns hard isolation. The open filesystem-roots PR is only a partial overlap because it leaves exec and disabled-skill semantics unchanged.

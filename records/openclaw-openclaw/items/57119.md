## Summary

Keep open. Current main and the latest release still treat `skills.entries.<key>.enabled: false` as skill eligibility/prompt visibility, while read and exec access remain governed by generic filesystem, sandbox, approval, and tool policy rather than a disabled-skill access boundary.

## What This Changes

The issue requests that disabled skills become an enforced read/exec/file-access boundary instead of only being removed from automatic skill matching and prompt surfaces.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce one central skill-access policy across discovery, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `skills.entries.<key>.enabled:false` become a hard read/exec/file-access deny boundary for that skill, or should hard skill isolation use a separate strict policy while `enabled:false` remains an eligibility toggle?

Rationale: The source-level gap is clear, but either answer changes public disabled-skill semantics and crosses filesystem, exec, sandbox, UI/status, docs, and upgrade expectations.

Likely owner: steipete

Owner reason: The decision is primarily a security/product boundary choice, and this person has the strongest recent history around skill install hardening and skill trust surfaces.

Owner confidence: medium

Options:

- **Make `enabled:false` a hard deny boundary (recommended):** Treat prompt-only hiding as `disable-model-invocation` and centrally deny disabled skill roots for read, write/edit/apply_patch where relevant, exec, sandbox materialization, UI/status, and docs.
- **Add a separate strict isolation policy:** Keep `enabled:false` as an eligibility toggle for compatibility and add an explicit operator-controlled policy for disabled-skill file and exec denial.
- **Document current semantics only:** Clarify that disabled skills are hidden from prompt/selection only and tell multi-user deployments to use sandboxing, tool deny lists, OS users, or containers for enforcement.

## Summary

Keep open. Current main and v2026.6.11 still treat `skills.entries.<key>.enabled: false` as skill eligibility and prompt/status filtering, while manual `read` and `exec` access are governed by generic filesystem, sandbox, approval, and tool policy controls rather than a disabled-skill access boundary.

## What This Changes

Request that disabled skills become an enforced security boundary that blocks manual reads of skill files and execution of skill scripts.

## Best Possible Solution

Define the disabled-skill security contract explicitly, then enforce it through a central skill-access policy across skill discovery, filesystem tools, exec/sandbox execution, Gateway/UI status, docs, and regression tests.

Options:

- **Make `enabled:false` a hard deny boundary (recommended):** Treat prompt-only hiding as `disable-model-invocation` and enforce disabled skill roots centrally for read, write/edit/apply_patch where relevant, exec, sandbox materialization, UI/status, and docs.
- **Add a separate strict isolation policy:** Keep `enabled:false` as an eligibility toggle for compatibility and add an explicit operator-controlled policy for disabled-skill file and exec denial.
- **Document current semantics only:** Clarify that disabled skills are hidden from prompt/selection only and instruct multi-user deployments to use sandboxing, tool deny lists, OS users, or containers for enforcement.

## Reproduction Assessment

Yes, at source level: current main filters disabled skills out of eligibility and prompt/status surfaces, while read and exec access still use generic filesystem, sandbox, approval, and safe-bin policy instead of disabled skill paths. I did not run a live exploit because this review is read-only.

## Solution Assessment

Unclear as an implementation path: the security direction is valid, but maintainers need to choose whether `enabled:false` becomes a hard compatibility boundary or whether a separate strict policy owns hard isolation.

## Label Justifications

- `impact:other`: The concrete impact is sustained resource exhaustion and request flooding, which does not fit the more specific issue-impact labels.

## Summary

This is a valid Telegram polling availability bug: current `main` immediately begins another successful poll after an empty result, while only failures receive backoff. Keep the issue open because the linked pull request is an active implementation candidate and has not merged.

## What This Changes

Add pacing for successful empty Telegram `getUpdates` responses so early-returning Bot API endpoints cannot cause a busy polling loop.

## Best Possible Solution

Review and land the linked narrow worker-loop fix if it preserves immediate shutdown, existing error backoff, and full-speed processing for non-empty update batches.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes from source inspection: a fetch implementation that immediately returns `{ ok: true, result: [] }` exercises the successful loop path, which currently performs no wait before starting the next poll. A live self-hosted Bot API reproduction was not run in this read-only review.

## Solution Assessment

Yes, conditionally: an abortable minimum interval only after a successful empty response is the narrowest repair because it retains existing retry behavior and does not slow delivery of actual updates.

## Summary

Current main and v2026.6.11 still provide only a Markdown-specific assistant-message copy action, so the requested capability remains missing; keep this open for a maintainer decision on the interaction and conversion semantics.

## What This Changes

Add a plain-text clipboard format option alongside Markdown copying for assistant messages in the Control UI.

## Best Possible Solution

Add a compact Markdown/plain-text choice to the existing assistant footer action, define a dedicated conversion contract with focused clipboard and UI tests, and avoid a persisted preference unless maintainers explicitly approve the additional settings surface.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should assistant-message copying expose Markdown and plain-text choices, and what content should the plain-text representation preserve for links, code blocks, lists, tables, and truncated messages?

Rationale: Current behavior intentionally exposes Markdown, while neither the second interaction nor its representation semantics are defined by existing docs or tests; a saved preference would also introduce broader product and settings surface.

Likely owner: steipete

Owner reason: The original implementation history provides the strongest available ownership signal for this product choice.

Owner confidence: high

Options:

- **Add compact format selector (recommended):** Offer Markdown and plain text from the existing footer action with explicit conversion behavior and focused clipboard/UI proof.
- **Keep Markdown only:** Preserve the current explicit Markdown action and decline the additional copy representation.
- **Add persisted default:** Store a preferred copy format, accepting a broader settings and compatibility surface.

## Reproduction Assessment

Yes. Current source deterministically derives assistant Markdown and passes it unchanged to the sole action labeled “Copy as markdown,” with no alternate format wiring found.

## Solution Assessment

The requested capability is reasonable, but the best path is a per-click format selector with an explicit conversion contract rather than a new persisted preference or direct reuse of a TTS-oriented stripping helper.

## Summary

Keep this PR open, but it is not merge-ready: the bounded reader is a valid mitigation for the unbounded HTTP JSON success path, but the patch applies a global 16 MiB cap that can break the existing uncapped `/snapshot?maxChars=0` contract, and the new proof only exercises the helper rather than the changed browser-control HTTP path.

## What This Changes

The PR changes `extensions/browser/src/browser/client-fetch.ts` to replace successful `res.json()` reads with `readResponseWithLimit` plus `JSON.parse` using a new 16 MiB cap.

## Best Possible Solution

Keep the success-body OOM mitigation, but preserve the `/snapshot?maxChars=0` compatibility contract or make a maintainer-approved contract change with focused tests, docs, and real HTTP-path proof.

## Reproduction Assessment

Yes from source inspection: absolute browser-control URLs use `fetchHttpJson`, whose current success path uses `res.json()`, so oversized successful JSON can be buffered before parsing. I did not run a live oversized endpoint because this review is read-only.

## Solution Assessment

No. The bounded reader is the right mitigation, but applying one global cap is not the best safe merge shape until the existing snapshot response-size contract is preserved or intentionally changed with tests/docs and proof.

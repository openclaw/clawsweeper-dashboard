## Summary

Keep open. Current main and the latest release still have the source-proven Telegram ingress failure mode, and https://github.com/openclaw/openclaw/pull/98775 is an open candidate fix that explicitly closes this issue.

## What This Changes

The issue asks for Telegram isolated polling to treat transient getUpdates 429/5xx and non-JSON 502 responses as retryable, honoring retry_after while keeping 401/404 fatal and 409 parent-owned.

## Best Possible Solution

Land a focused Telegram worker fix that retries 429 and 5xx getUpdates failures, honors retry_after, converts non-JSON 5xx responses into status-bearing retryable errors, and preserves fatal handling for 401/404 plus parent-owned 409 recovery.

## Reproduction Assessment

Yes from source inspection, not from a live Telegram run: returning 429, 500, 502, or a non-JSON 502 from getUpdates reaches the current worker retry gate or parser path and can terminate the worker. A focused regression test can inject those responses into the worker runtime.

## Solution Assessment

Yes for this issue: the maintainable fix belongs in the Telegram isolated-ingress worker retry policy, reusing shared Telegram API error classification and preserving the existing 409 parent recovery boundary. The open candidate at https://github.com/openclaw/openclaw/pull/98775 appears to target that shape, but it still needs PR review/merge before this issue can close.

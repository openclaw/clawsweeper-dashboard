## Summary

Keep open: current main and latest release v2026.6.11 still enforce the exact single-file memory-flush write guard, user comments report recurrence after the attempted fix PR closed unmerged, and relaxing this guard needs maintainer product/security review rather than cleanup closure.

## What This Changes

The issue reports that memory-flush compaction locks the write tool to the daily memory file and blocks unrelated file edits during active work.

## Best Possible Solution

Define and land a maintainer-approved memory-flush write-authority contract that either preserves the single-target append guard or allows narrowly validated non-memory exceptions with tests, docs, and explicit security/upgrade reasoning.

## Maintainer Decision

Question: Should memory-triggered compaction runs continue to have single-target append-only write authority, or may they pass through unrelated non-memory writes under the normal workspace/sandbox write policy?

Rationale: The source repro is clear, but the fix changes a silent housekeeping run's write authority and current policy treats this as a security/product boundary, not a mechanical bug fix.

Likely owner: frankekn

Owner reason: The strongest merged history for the current strict memory-flush guard and path-forwarding behavior points to frankekn-authored PRs.

Owner confidence: high

Options:

- **Keep single-target guard:** Leave memory-triggered runs restricted to the daily memory file and accept that unrelated writes must wait until the flush completes.
- **Allow narrow non-memory passthrough (recommended):** Permit writes outside the memory-flush target only after normal workspace/sandbox validation, with regression tests and docs that define the exception.
- **Design explicit override:** Add a deliberate user/operator-controlled unlock or config mode instead of changing default memory-run authority.

## Reproduction Assessment

Yes, at source level: current main routes memory-triggered tool calls through `wrapToolMemoryFlushAppendOnlyWrite`, and any path other than the configured `memoryFlushWritePath` throws the reported error. I did not run a live long-session compaction in this read-only review.

## Solution Assessment

Unclear: the bug is real, but the proposed soft limit, config switch, or magic unlock would relax a security-sensitive write boundary. The best path is a maintainer-approved narrow contract rather than automatic broad passthrough.

Full review comments:

- **[P1] Register workspace methods through core descriptors:** `src/gateway/server-methods.ts:8`
  - body: The PR wires the new handlers by importing them into the old eager `server-methods.ts` aggregator, but current main builds the Gateway method table from `CORE_GATEWAY_METHOD_SPECS` plus lazy handler families. After rebase these methods need descriptor entries and lazy registration, or they will be unadvertised, unscoped, or fail to dispatch under the current registry.
  - confidence: 0.92
- **[P1] Move workspace schemas to the protocol package:** `src/gateway/protocol/schema/agents-workspace.ts:1`
  - body: The new public schemas are added under `src/gateway/protocol`, but current main removed that protocol tree and uses `packages/gateway-protocol` as the canonical source for validators, generated types, and clients. Reintroducing the old path would create a parallel protocol surface that drifts from generated clients and current imports.
  - confidence: 0.9
- **[P1] Use supported fs-safe APIs before importing the handler:** `src/gateway/server-methods/agents-workspace.ts:4-8`
  - body: This handler imports `mkdirPathWithinRoot` and `removePathWithinRoot`, which current `src/infra/fs-safe.ts` no longer exports; it now exposes `root(rootDir).read/write` and selected advanced helpers. A current-main rebase would fail to typecheck unless the workspace handler moves to the supported root API or adds an intentional shared helper.
  - confidence: 0.91
- **[P1] Bound recursive workspace listings:** `src/gateway/server-methods/agents-workspace.ts:143-145`
  - body: When `recursive` is true, this read-scoped RPC recurses through every directory and appends all entries without a depth, entry-count, or response-size limit. A large workspace can make a single list request consume Gateway CPU, memory, and bandwidth, so the API needs pagination or a hard traversal budget before merge.
  - confidence: 0.88

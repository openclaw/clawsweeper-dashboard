## Summary

Keep open: current main and the latest release still lack an actual-runtime-model response metadata contract for the OpenAI-compatible Gateway HTTP endpoints, and the remaining work needs maintainer API/SSE direction rather than an automatic fix PR.

## What This Changes

The issue requests an HTTP response metadata surface, proposed as `X-Actual-Model`, that reports the actual runtime model used by Gateway OpenAI-compatible requests.

## Best Possible Solution

Define and document one Gateway actual-model metadata contract across `/v1/chat/completions` and `/v1/responses`, including non-streaming responses and streaming/SSE behavior, then wire selected provider/model data from the existing model-selection callback or equivalent run metadata with focused tests.

## Reproduction Assessment

Yes. Source inspection is enough to reproduce the gap: current main has no requested actual-runtime-model response header, and both OpenAI-compatible handlers continue to use request-side model values; I did not run a live Gateway request because the missing contract is directly visible in source and docs.

## Solution Assessment

No, not as proposed by only adding a plain response header. A header may work for non-streaming responses, but streaming needs a maintainer-approved metadata/SSE contract because the selected model can be known only after headers have already been flushed.

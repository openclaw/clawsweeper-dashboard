## Summary

Keep open: current main still lacks an actual-runtime-model response surface for the OpenAI-compatible Gateway HTTP endpoints, and the remaining work needs a maintainer-owned HTTP/SSE metadata contract decision rather than conservative cleanup.

## What This Changes

Request to expose the actual model that processed each Gateway OpenAI-compatible HTTP response, proposed as an `X-Actual-Model` response header.

## Best Possible Solution

Define one documented actual-selected-model metadata contract across `/v1/chat/completions` and `/v1/responses`, including non-streaming and SSE behavior, then wire it from the existing selected-model signal with focused Gateway tests.

Rationale: The source gap is real, but normal response headers cannot cover late fallback selection after SSE headers flush, so implementation needs maintainer intent on the public API shape.

Likely owner: steipete

Owner confidence: high

Options:

- **Define unified HTTP/SSE metadata (recommended):** Document and implement a single actual-model contract for Chat Completions and Responses across non-streaming metadata and streaming SSE-compatible metadata.
- **Limit first pass to non-streaming:** Expose actual-model metadata only where it is known before headers are sent, and document streaming attribution as a limitation or follow-up.
- **Defer to broader runtime metadata:** Keep the transport response surface deferred until the overlapping resolved-model/session-status contract is decided.

## Reproduction Assessment

Yes. Source inspection on current main shows no actual-model Gateway response header or documented equivalent, and both OpenAI-compatible handlers still return request-side model values while actual selected-model plumbing remains below the HTTP layer.

## Solution Assessment

No for the header-only proposal. The maintainable solution needs a unified body/header/SSE metadata contract so fallback attribution remains accurate after streaming headers have flushed.

## Summary

Keep open: current main still lacks an actual-runtime-model response surface for the OpenAI-compatible Gateway HTTP endpoints, and the remaining work needs a public HTTP/SSE API contract decision.

## What This Changes

The issue requests an `X-Actual-Model`-style response header so HTTP clients can see which provider/model actually processed each Gateway request.

## Best Possible Solution

Define one documented actual-selected-model metadata contract across `/v1/chat/completions` and `/v1/responses`, including SSE semantics, then wire it from selected-model/runtime metadata with focused Gateway tests and docs.

Options:

- **Define unified HTTP/SSE metadata (recommended):** Document and implement one actual-model contract for Chat Completions and Responses across non-streaming response metadata and streaming SSE-compatible metadata.
- **Limit first pass to non-streaming:** Add actual-model metadata only where the value is known before headers are sent and explicitly document streaming as unsupported follow-up work.
- **Defer to broader runtime metadata:** Wait for the broader resolved-model/session-status contract before adding transport-level response attribution.

## Reproduction Assessment

Yes, from source inspection: current Gateway handlers return the request-side `model` and do not wire the existing selected-model signal into HTTP responses. No live fallback run was executed in this read-only cleanup review.

## Solution Assessment

No for the literal header-only proposal. The maintainable fix needs a unified body/header/SSE metadata contract so fallback attribution remains accurate after streaming headers have flushed.

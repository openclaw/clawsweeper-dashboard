## Summary

Keep open: current main and the latest release still lack an actual-runtime-model response contract for the Gateway OpenAI-compatible HTTP endpoints; this needs maintainer API/SSE product direction before implementation.

## What This Changes

Request to expose the actual runtime provider/model selected for each OpenAI-compatible Gateway HTTP response, proposed as an `X-Actual-Model` response header.

## Best Possible Solution

Define one documented actual-selected-model metadata contract across `/v1/chat/completions` and `/v1/responses`, including non-streaming and SSE behavior, then wire it from the existing selected-model signal with focused Gateway tests and live routing-proxy proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What actual-runtime-model contract should Gateway expose for non-streaming and streaming OpenAI-compatible HTTP responses?

Rationale: Current code has selected-model metadata below the HTTP layer, but normal response headers are flushed too early for streaming fallback cases; maintainers need to choose the public API shape before implementation.

Likely owner: steipete

Owner reason: steipete already reviewed this exact Gateway API-contract gap and has the strongest recent history signal for the affected endpoint/docs surface.

Owner confidence: high

Options:

- **Define unified metadata contract (recommended):** Document and implement a single contract for non-streaming body/header metadata plus streaming SSE-compatible metadata across Chat Completions and Responses.
- **Limit to non-streaming headers:** Add a header only where the selected model is known before response headers are sent, accepting that streaming clients need a separate follow-up.
- **Defer HTTP response metadata:** Keep the work behind broader session/runtime resolved-model observability if maintainers do not want to add a transport-level response surface yet.

## Reproduction Assessment

Yes. Source inspection on current main shows no actual-model Gateway response header or documented equivalent, and both OpenAI-compatible handlers return request-side model values while actual selected-model plumbing remains below the HTTP layer.

## Solution Assessment

No for the header-only proposal. The maintainable solution is a unified body/header/SSE metadata contract so fallback attribution remains accurate after streaming headers have flushed.

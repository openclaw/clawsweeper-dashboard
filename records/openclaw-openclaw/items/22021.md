## Summary

Keep open: current main and the latest release still lack actual-runtime-model response metadata for the OpenAI-compatible Gateway HTTP endpoints, and the remaining work is a public HTTP/SSE API contract decision rather than conservative cleanup.

## What This Changes

The issue requests an HTTP response header or equivalent Gateway transport metadata that reports the actual runtime model used for each OpenAI-compatible HTTP response.

## Best Possible Solution

Define one documented actual-selected-model metadata contract across `/v1/chat/completions` and `/v1/responses`, including non-streaming and SSE behavior, then wire it from the existing selected-model signal with focused Gateway tests and live routing-proxy proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What actual-runtime-model contract should Gateway expose for non-streaming and streaming OpenAI-compatible HTTP responses?

Rationale: Current code has selected-model metadata below the HTTP layer, but normal response headers are flushed too early for streaming fallback cases; maintainers need to choose the public API shape before implementation.

Likely owner: steipete

Owner reason: steipete already reviewed this exact Gateway API-contract gap and has the strongest recent history signal for the affected endpoint/docs surface.

Owner confidence: high

Options:

- **Define unified metadata contract (recommended):** Document and implement one contract for non-streaming body/header metadata plus streaming SSE-compatible metadata across Chat Completions and Responses.
- **Limit to non-streaming headers:** Add a header only where the selected model is known before response headers are sent and track streaming visibility separately.
- **Defer HTTP response metadata:** Keep this behind broader session/runtime resolved-model work if maintainers do not want a transport-level response surface yet.

## Reproduction Assessment

Yes. Source inspection on current main shows no actual-model Gateway response header or documented equivalent, and both OpenAI-compatible handlers return request-side model values while actual selected-model plumbing remains below the HTTP layer.

## Solution Assessment

No for the header-only proposal. The useful end state needs a unified body/header/SSE metadata contract so fallback attribution remains accurate after streaming headers have flushed.

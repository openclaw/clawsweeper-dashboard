## Summary

Keep open: current main still lacks actual-runtime-model metadata on the OpenAI-compatible Gateway HTTP response surface, and the remaining work is a public HTTP/SSE contract decision rather than conservative cleanup.

## What This Changes

The issue requests an `X-Actual-Model` response header or equivalent transport-level metadata showing which runtime model actually processed each Gateway HTTP request.

## Best Possible Solution

Define one documented actual-selected-model metadata contract across `/v1/chat/completions` and `/v1/responses`, including SSE semantics, then wire it from selected-model or agent metadata with focused Gateway tests and docs.

Rationale: The source gap is clear, but the requested response header is a public API contract and normal headers cannot represent late fallback selection after SSE headers flush.

Options:

- **Define unified HTTP/SSE metadata (recommended):** Document and implement one actual-model contract for Chat Completions and Responses across non-streaming body/header metadata and streaming SSE-compatible metadata.
- **Limit first pass to non-streaming:** Expose actual-model metadata only where it is known before headers are sent, and explicitly track streaming attribution as a follow-up limitation.
- **Defer to runtime metadata contract:** Hold transport response attribution until the broader resolved-model/session-status metadata direction is settled.

## Reproduction Assessment

Yes. Source inspection is high-confidence: current Gateway handlers return the request-side `model` and do not wire the existing selected-model signal into HTTP responses; no live fallback run was executed in this read-only cleanup review.

## Solution Assessment

No for the literal header-only proposal. The maintainable fix needs a unified body/header/SSE metadata contract so fallback attribution remains accurate after streaming headers have flushed.

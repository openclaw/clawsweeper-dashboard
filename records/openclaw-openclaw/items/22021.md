## Summary

Keep open: current main still lacks an actual-runtime-model response metadata surface for the Gateway OpenAI-compatible HTTP endpoints. The remaining work is real, but the literal header proposal needs maintainer API-contract direction because streaming responses flush headers before fallback-selected model metadata may be known.

## What This Changes

Request to expose the actual runtime model used by Gateway OpenAI-compatible HTTP requests, preferably through an `X-Actual-Model` response header.

## Best Possible Solution

Define one documented actual-selected-model metadata contract across `/v1/chat/completions` and `/v1/responses`, including SSE semantics, then wire it from the selected-model signal or agent metadata with focused Gateway tests and docs.

Options:

- **Define Unified HTTP/SSE Metadata (recommended):** Document and implement one actual-model contract for Chat Completions and Responses across non-streaming body/header metadata and streaming SSE-compatible metadata.
- **Limit First Pass To Non-Streaming:** Expose actual-model metadata only where it is known before headers are sent and leave streaming attribution as an explicit follow-up limitation.
- **Defer To Broader Runtime Metadata:** Keep transport response attribution deferred until the broader resolved-model and session-status metadata contract is decided.

Yes. Source inspection is high-confidence: the current Gateway handlers return the request-side `model` and do not wire the existing selected-model signal into HTTP responses; no live fallback run was executed in this read-only cleanup review.

## Solution Assessment

No for the literal header-only proposal. The maintainable fix needs a unified body/header/SSE metadata contract so fallback attribution remains accurate after streaming headers have flushed.

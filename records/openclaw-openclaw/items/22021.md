## Summary

Keep open: current main and the latest release still lack actual-runtime-model response metadata for the Gateway OpenAI-compatible HTTP endpoints, and the remaining work is an HTTP/SSE API contract decision rather than conservative cleanup.

## What This Changes

Request to expose the model that actually handled each Gateway OpenAI-compatible HTTP request, proposed as an `X-Actual-Model` response header.

## Best Possible Solution

Define one documented actual-selected-model metadata contract across `/v1/chat/completions` and `/v1/responses`, including non-streaming and SSE behavior, then wire it from the existing selected-model signal with focused Gateway tests and live routing-proxy proof.

Question: What actual-runtime-model contract should Gateway expose for non-streaming and streaming OpenAI-compatible HTTP responses?

Rationale: Current code has selected-model metadata below the HTTP layer, but normal response headers are flushed too early for streaming fallback cases; maintainers need to choose the public API shape before implementation.

Likely owner: steipete

Owner confidence: high

Options:

- **Define unified metadata contract (recommended):** Document and implement one contract for non-streaming response metadata plus streaming-compatible SSE metadata across Chat Completions and Responses.
- **Limit to non-streaming headers:** Add a header only where the selected model is known before response headers are sent, accepting that streaming clients need a separate follow-up.
- **Defer HTTP response metadata:** Keep the work behind broader session/runtime resolved-model issues if maintainers do not want a transport-level response surface yet.

## Reproduction Assessment

Yes. Source inspection on current main shows no actual-model Gateway response header or documented equivalent, and both OpenAI-compatible handlers return request-side model values while actual selected-model plumbing remains below the HTTP layer.

## Solution Assessment

No for the header-only proposal. The maintainable solution needs a unified body/header/SSE metadata contract so fallback attribution remains accurate after streaming headers have flushed.

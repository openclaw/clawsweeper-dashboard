## Summary

Keep open: current main still lacks an actual-runtime-model response contract for the Gateway OpenAI-compatible HTTP endpoints, and the remaining work is a public API/SSE product decision rather than conservative cleanup.

## What This Changes

The issue asks for a Gateway HTTP response metadata surface, proposed as `X-Actual-Model`, that exposes the provider/model that actually served each OpenAI-compatible request.

## Best Possible Solution

Define one documented actual-selected-model metadata contract across `/v1/chat/completions` and `/v1/responses`, including non-streaming JSON/header and streaming SSE semantics, then wire it from existing model attribution signals with focused Gateway tests.

Rationale: Current code has actual selected-model metadata below the HTTP layer, but ordinary response headers are flushed too early for streaming fallback cases; maintainers need to choose the public API shape before implementation.

Options:

- **Define unified metadata contract (recommended):** Document and implement one additive contract for non-streaming response metadata and streaming SSE-compatible actual-model metadata across Chat Completions and Responses.
- **Limit to non-streaming headers:** Add an actual-model header only where the selected model is known before response headers are sent, leaving streaming clients to a separate follow-up.
- **Defer transport metadata:** Keep this behind broader resolved-model/session-runtime work if maintainers do not want a transport-level response surface yet.

## Reproduction Assessment

Yes. Source inspection on current main and `v2026.6.11` shows no actual-model response header or documented equivalent, and both OpenAI-compatible handlers return request-side model values while actual selected-model plumbing remains below the HTTP layer.

## Solution Assessment

No for the header-only proposal. The maintainable solution is a unified body/header/SSE metadata contract so fallback attribution remains accurate after streaming headers have flushed.

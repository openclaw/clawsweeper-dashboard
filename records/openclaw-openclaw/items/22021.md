## Summary

Keep open: current main still lacks an actual-runtime-model response surface for the OpenAI-compatible Gateway HTTP endpoints. The request is valid, but it needs a maintainer-owned HTTP/SSE API contract decision because a header-only design cannot cover streaming fallback selection after headers flush.

## What This Changes

Request to add HTTP response metadata, proposed as `X-Actual-Model`, so clients can see the model that actually processed each Gateway request.

## Best Possible Solution

Define one documented actual-selected-model metadata contract across `/v1/chat/completions` and `/v1/responses`, including JSON and SSE behavior, then wire it from the existing selected-model signal with focused Gateway tests and live routing-proxy proof.

Yes. Source inspection on current main shows no actual-model Gateway response header or documented equivalent, and both OpenAI-compatible handlers return request-side model values while actual selected-model plumbing remains below the HTTP layer.

## Solution Assessment

No for the header-only proposal. The useful end state needs a unified body/header/SSE metadata contract so fallback attribution remains accurate after streaming headers have flushed.

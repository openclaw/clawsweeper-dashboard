## Summary

Keep open: current main still lacks an actual-runtime-model response surface for the Gateway OpenAI-compatible HTTP endpoints, and the related issues are overlapping rather than replacements for this transport contract.

## What This Changes

Request an `X-Actual-Model` header or equivalent response metadata exposing the actual runtime model used by Gateway HTTP responses.

## Best Possible Solution

Define one documented, additive Gateway actual-model metadata contract for `/v1/chat/completions` and `/v1/responses`, covering non-streaming and streaming behavior, then wire it from existing selected-model/runtime metadata with focused tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What public Gateway contract should expose the actual runtime model for non-streaming and streaming OpenAI-compatible responses?

Rationale: This is a public API/product choice because ordinary response headers cannot cover late streaming fallback selection, while changing the response `model` field could conflict with the documented agent-target model contract.

Likely owner: steipete

Owner reason: Peter Steinberger has the strongest sampled history on the Gateway HTTP contract and related maintainer review context for this issue.

Owner confidence: high

Options:

- **Add streaming-safe metadata contract (recommended):** Define an additive response-body/SSE metadata surface, with a header only where it is reliable, while preserving the current agent-target `model` field semantics.
- **Header-only narrow contract:** Expose a header for non-streaming or pre-selected cases and document that streaming fallback identity may be unavailable or separate.
- **Fold into broader observability work:** Move the remaining transport decision under the broader resolved-model/session observability effort and keep this issue as the HTTP-specific acceptance criterion.

## Reproduction Assessment

Yes, from source inspection: current main has no `X-Actual-Model` response surface, and both Gateway HTTP handlers still build responses from the request-side agent target model. I did not run a live Gateway request because the missing path is visible in the current handler code and docs.

## Solution Assessment

The requested direction is valid, but a header-only implementation is not the best full solution because streaming headers flush before late fallback selection is known. The maintainable fix is a documented response metadata contract that handles both non-streaming and streaming responses without breaking the agent-target `model` field.

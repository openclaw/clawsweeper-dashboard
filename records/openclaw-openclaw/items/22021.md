## Summary

Keep open: current main still lacks a Gateway actual-runtime-model response contract, and the requested behavior is a public API/SSE product decision rather than conservative cleanup.

## What This Changes

Request to expose the model that actually processed each Gateway OpenAI-compatible HTTP request, proposed as an `X-Actual-Model` response header.

## Best Possible Solution

Define one documented actual-selected-model metadata contract across `/v1/chat/completions` and `/v1/responses`, including non-streaming JSON/header and streaming SSE semantics, then wire it from existing model attribution signals with focused Gateway tests.

Rationale: Current code has selected-model metadata below the HTTP layer, but ordinary headers are flushed too early for streaming fallback cases; maintainers need to choose the public API shape before implementation.

Likely owner: steipete

Owner confidence: high

Options:

- **Define unified metadata contract (recommended):** Document and implement one contract for non-streaming body/header metadata plus streaming SSE-compatible metadata across Chat Completions and Responses.
- **Limit to non-streaming headers:** Add a header only where the selected model is known before response headers are sent, accepting that streaming clients need a separate follow-up.
- **Defer HTTP response metadata:** Keep this behind the broader session/runtime resolved-model work if maintainers do not want a transport-level response surface yet.

## Reproduction Assessment

Yes. Source inspection on current main is high-confidence: no actual-model response header or documented equivalent exists, both HTTP handlers return request-side model values, and the actual selected-model signal remains below the HTTP layer.

## Solution Assessment

No for the header-only proposal. The maintainable solution is a unified body/header/SSE metadata contract so fallback attribution stays accurate after streaming headers have flushed.

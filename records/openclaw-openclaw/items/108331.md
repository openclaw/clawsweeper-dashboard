## What This Changes

Restore a usable session after a provider timeout or 503 so later messages are not silently stranded behind stale session state.

## System Context

Inbound channel messages enter the auto-reply dispatcher, which admits or recovers a persisted agent session before starting an embedded model run. Stuck-run recovery must leave both the persisted session record and the reply-operation registry in a terminal state so the next inbound message can be safely dispatched or clearly failed.

## Architecture Diagram

flowchart TD
  A[Feishu or other channel message] --> B[Auto-reply dispatcher]
  B --> C[Session admission and stale-run recovery]
  C --> D[Persisted session state]
  C --> E[Embedded model run]
  E --> F[Provider timeout or 503]
  F --> G[Force-clear and terminal-state persistence]
  G --> H[Next message recovery or user-visible error]

## Best Possible Solution

Keep the merged terminal-state persistence fix, reproduce the provider-timeout path on current main, and then implement one bounded recovery contract: terminal sessions admit a new turn or surface a visible reset/retry action, while any fallback preserves the user’s selected model preference between turns.

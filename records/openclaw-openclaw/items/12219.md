## Summary

This remains necessary: current main improves skill trust visibility and install-policy hooks, but it does not provide the requested standardized permission declaration, consent semantics, signing/attestation model, and enforcement contract. Likely related people: vincentkoc for the current skills/ClawHub paths and steipete for the recorded product-security direction.

## What This Changes

The issue proposes a standardized `skill.yaml` permission manifest with install-time consent, audit/trust reporting, signatures, attestations, and related enforcement hooks.

## Best Possible Solution

Consolidate the capability-manifest, signing/provenance, and runtime-enforcement tracks into a phased contract: start with one versioned declaration surface and clear inspect/install messaging, then add consent, update diffs, and enforcement only after their compatibility and trust semantics are agreed.

Options:

- **Phase the declaration first (recommended):** Adopt the narrow capability vocabulary proposed by https://github.com/openclaw/openclaw/issues/74594, keep it explicitly non-enforcing, and specify later phases separately.

- **Keep policy external:** Rely on ClawHub verification and `security.installPolicy` integration without standardizing a core manifest for now.

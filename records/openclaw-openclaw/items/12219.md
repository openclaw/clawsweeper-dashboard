## Summary

Keep open: the request remains a security-sensitive product-design decision rather than a bounded cleanup. The later RFC at https://github.com/openclaw/openclaw/issues/74594 overlaps on a minimal declaration/inspection v0, but it deliberately excludes the install consent, enforcement, signing, and attestation work requested here, so it does not yet safely supersede this issue. Likely related people: vincentkoc for the current skills and ClawHub implementation paths, and steipete for the recorded product-security direction.

## What This Changes

Define a standardized skill permission manifest with user-visible install review, audit/trust reporting, and a future relationship to runtime enforcement.

## System Context

OpenClaw skills are package-style instruction bundles installed from local sources or ClawHub and then exposed to agents. A permission manifest would sit between skill metadata and install/runtime policy, affecting what users can inspect before enabling a skill and what later enforcement can reliably consume.

## Architecture Diagram

flowchart LR

  B --> C[Skill installer]
  C --> D[User consent and audit view]
  B --> E[Policy and hook layer]
  E --> F[Agent tool execution]
  C --> G[ClawHub skill listing]

## Best Possible Solution

Choose a staged security model: first decide whether the narrowly scoped inspect-only capability vocabulary in https://github.com/openclaw/openclaw/issues/74594 is the canonical v0, then separately specify consent, enforcement, provenance, and attestation only where OpenClaw can honor them end to end.

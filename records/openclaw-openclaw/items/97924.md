## Summary

Keep open: current main has `session_end` plugin lifecycle hooks and cron's existing `on-exit` event trigger, but it still does not expose a durable session archive/rotation event schedule that cron jobs can subscribe to. The remaining work is a product and security decision about whether to add a core cron event contract, expose a narrower plugin seam, or leave this plugin-owned.

## What This Changes

The issue requests a session archive or rotation lifecycle event that cron jobs can subscribe to for event-driven post-session automation.

## Best Possible Solution

Choose a narrow lifecycle-event contract that reuses the existing `session_end` source and cron run pipeline while keeping session metadata scoped, permissioned, durable, and auditable.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should session archive/rotation become a first-class cron event trigger, a narrower plugin SDK/lifecycle hook, or remain plugin-owned without core cron config?

Rationale: The source has the lifecycle signal and cron machinery, but binding them creates a new public automation/config/security contract around session metadata and durable event dispatch.

Likely owner: dongdong

Owner reason: Current blame points to the central session and cron contracts in dongdong's recent commit, making this the best available routing candidate from local history.

Owner confidence: medium

Options:

- **Design core cron event trigger (recommended):** Add a durable, scoped session lifecycle event schedule to cron with permission checks, dedupe, and trace records before exposing it in config or CLI.
- **Expose plugin-owned hook only:** Keep core cron unchanged and document a plugin/SDK pattern that lets memory or automation plugins handle `session_end` without a public cron event surface.
- **Defer lifecycle automation:** Leave the current polling/new-session workaround as the supported path until a broader automation event bus design is approved.

Yes, at the source-contract level: current main emits `session_end` plugin hooks during reset/compaction-style session rotation, while `CronSchedule` has no event/session lifecycle kind. I did not run a live gateway scenario because this is a missing feature surface, not a failing existing command.

## Solution Assessment

Unclear until maintainers choose the product boundary. The best shape appears to be a narrow durable lifecycle-event seam feeding cron, or a plugin-owned hook if core should avoid adding a new cron config surface.

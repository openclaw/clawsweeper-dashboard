## Summary

Keep open: current main has session_end plugin hooks and cron schedule types, but it still lacks a durable session-archive/session-rotation cron trigger or event schedule contract. The request is a real feature gap, but adding it crosses cron schema, session lifecycle, permissions, and traceability, so it needs maintainer product/security direction before implementation.

## What This Changes

The issue requests a session rotation/archive lifecycle event that cron jobs can subscribe to so an agent turn can run at session archive boundaries.

## Best Possible Solution

Define a maintainer-approved lifecycle trigger contract that either extends cron with durable scoped session events or explicitly documents the plugin-only path, with protocol/schema, security, trace, docs, and focused tests kept in sync.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw core expose durable session archive/rotation events as cron triggers, or should this remain a plugin/session_end integration pattern?

Rationale: The source gap is clear, but the fix would add public cron/config/protocol surface and can launch unattended agent turns from session-state changes, so automation should not choose the security and product boundary.

Likely owner: steipete

Owner reason: steipete has the strongest current history across cron, Gateway, and product/security review surfaces for this decision.

Owner confidence: high

Options:

- **Add Narrow Core Event Trigger (recommended):** Define a durable session lifecycle event schedule for cron with scoped metadata, idempotency, permissions, trace records, and tests across reset/rotation paths.
- **Keep It Plugin-Owned:** Treat session_end plugin hooks as the supported integration point and document how a plugin can run post-session automation without adding cron event schedules.
- **Fold Into Broader Cron Hooks:** Track this as a subcase of the broader cron hook lifecycle design at https://github.com/openclaw/openclaw/issues/9465 before adding any new schema.

## Reproduction Assessment

Yes, at source level. Current cron types and protocol schemas omit a session lifecycle event schedule, while existing session_end hooks are plugin observation hooks rather than durable cron triggers.

## Solution Assessment

Unclear until maintainers choose the boundary. A core event trigger is plausible, but existing session_end/cron_changed hooks and the broader cron-hook issue mean the durable API and security model should be settled first.

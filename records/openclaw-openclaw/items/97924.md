## Summary

Keep open: current main has session lifecycle plugin hooks and cron job lifecycle hooks, but it still lacks a durable session archive/rotation event that cron can subscribe to and dispatch with scoped session metadata. The remaining work is a product and security boundary decision, not conservative cleanup.

## What This Changes

The issue requests a session rotation/archive lifecycle event that can trigger cron jobs or agent turns at the session boundary.

## Best Possible Solution

Define one maintainer-approved session-lifecycle automation contract with scoped metadata, durable event ids, permission checks, traceability, and a clear boundary between core cron, plugin SDK hooks, and plugin-owned workflows.

## Maintainer Decision

Required: true

Question: Should OpenClaw expose session archive/rotation as a durable automation event, and should the supported boundary be core cron schedule syntax, a plugin SDK lifecycle/API seam, or a plugin-owned workflow?

Rationale: The missing source capability is clear, but the permanent shape affects cron config, plugin API stability, sensitive session metadata, and silent agent-turn execution policy, so automation should not choose it alone.

Owner confidence: medium

Options:

- **Design a durable lifecycle event contract (recommended):** Approve a scoped `session_end`/archive event model with event id, minimal metadata, permission/audit rules, and cron/plugin dispatch semantics before implementation.
- **Keep lifecycle handling plugin-only:** Treat existing `session_end` hooks as the supported boundary and ask plugin authors to implement automation outside cron until a concrete missing SDK operation is specified.
- **Defer to ClawHub package design:** Ask for this as a ClawHub plugin or bundle first, then add only the narrow core/plugin API that package proves is missing.

## Reproduction Assessment

Yes, at source level: current cron schedules do not include a generic event/session lifecycle kind, while session lifecycle is only exposed as plugin hooks. I did not run a live gateway scenario because this read-only review can prove the missing contract from current source and docs.

## Solution Assessment

Unclear: the proposed `schedule.kind: event` shape is plausible, but the best solution depends on maintainer choice between core cron syntax, a plugin SDK event/API, or plugin-owned automation with a narrower core seam.

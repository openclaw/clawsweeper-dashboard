## Summary

Current source does not reproduce the reported normal crash/redelivery failure: the outer middleware creates an active claim before handlers run, commits the recent key only after completed processing, and explicitly permits failed update IDs to retry. The fallback `recentUpdates.check(key)` is genuinely mutating and under-tested, so this fresh report should remain open until a real middleware path proves it reachable or confirms it is unnecessary.

**Likely related people**
- @steipete — high confidence; introduced and repeatedly maintained the Telegram update-tracker and retry-routing path.
- @udaymanish6 — medium confidence; authored merged polling-routing work that carried tracker replay fixes.
- @joshavant — medium confidence; recently maintained the adjacent Telegram spool replay/adoption boundary.

## What This Changes

Investigate whether Telegram’s handler-dispatch dedupe mutates completed state too early and suppresses legitimate update retries after processing failures.

## Best Possible Solution

Add an integration-level tracker test that runs the real middleware with a throwing message handler and redelivers the identical update; then remove the no-active fallback if unreachable, or give it explicit claim, commit, and rollback semantics if it is a supported path.

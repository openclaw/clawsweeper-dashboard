## Summary

Keep this PR open for maintainer review. The deletion transaction addresses a real P1 lifecycle and authority-retention problem, but normal recreation appears unable to claim a completed deletion tombstone because the new claim is conditional on the deleted agent still being present in the locked config; that conflicts with the intended post-deletion state and can leave the agent permanently fenced. The `maintainer` label also requires explicit human handling.

## What This Changes

The branch makes agent deletion coordinate config removal, cron cleanup, exec-approval cleanup, state-database leases, filesystem archival, and durable recovery fencing.

## Best Possible Solution

Claim a completed deletion tombstone whenever recreation proceeds for that agent id, independent of whether the deleted roster entry remains in the locked config, then add an end-to-end delete/recreate regression test using the actual post-deletion configuration shape.

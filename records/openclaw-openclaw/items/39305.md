## Label Justifications

- `P1`: The issue has comment-backed production evidence of a Telegram/channel workflow staying blocked for hours behind a stuck sessions_spawn with no automatic recovery.
- `impact:session-state`: The requested recovery depends on accurate subagent run state, parent wait state, liveness, and terminal-state reconciliation.
- `impact:message-loss`: A stuck subagent can leave channel messages queued or unsurfaced until manual intervention, making message delivery effectively unavailable for that session.

## Summary

Keep open: current main still lacks the requested two-stage sub-agent inactivity watchdog, and the existing hard timeout, stale-run pruning, diagnostics, and manual kill-related work do not provide the requested nudge-to-kill recovery contract.

## What This Changes

Request automatic sub-agent stall recovery that nudges after tool inactivity, then kills and notifies after continued inactivity.

## Best Possible Solution

Define one maintainer-approved subagent recovery contract that reuses timeout, control, diagnostics, and session-activity primitives rather than adding an independent liveness truth.

Options:

- **Define a core recovery policy (recommended):** Adopt a maintainer-owned design that specifies deterministic activity tracking, compatibility-safe defaults, staged nudge delivery, terminal escalation, and bounded parent/channel notification before implementation.
- **Prototype default-off recovery:** Allow a narrower opt-in experiment with explicit config and tests while leaving existing long-running subagent behavior unchanged by default.
- **Defer to timeout and manual controls:** Keep automatic activity-based kill out of core and route remaining recovery to explicit runTimeoutSeconds, status APIs, and manual kill/reap controls.

## Solution Assessment

Unclear until maintainers choose the policy; the best fix should consolidate with runTimeoutSeconds, subagent control, diagnostics, and sessions activity instead of creating a competing liveness path.

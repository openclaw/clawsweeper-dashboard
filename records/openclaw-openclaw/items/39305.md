## Label Justifications

- `P1`: The issue has production chat-channel evidence of a stuck sessions_spawn blocking a group conversation for minutes to hours with no automatic recovery.
- `impact:session-state`: The requested behavior depends on accurate subagent run liveness, parent wait state, terminal reconciliation, and recovery state.
- `impact:message-loss`: A stuck subagent can leave later channel messages queued or unsurfaced until manual intervention, making delivery effectively unavailable for that session.

## Summary

Keep open: current main and the latest release still do not implement the requested activity-based two-stage subagent recovery; existing behavior covers explicit wall-clock run timeouts, stale-run cleanup, restart recovery, and manual/diagnostic surfaces, but not a tool-inactivity nudge followed by automatic kill and parent/channel notification.

## What This Changes

The issue requests configurable two-stage subagent stall recovery that sends a nudge after tool-call inactivity and kills the child run if activity does not resume.

## Best Possible Solution

Keep this as the canonical design item until maintainers choose one subagent recovery contract that reuses existing timeout, control, diagnostics, and session-activity primitives rather than adding an independent liveness source.

Options:

- **Define a core recovery policy (recommended):** Adopt a maintainer-owned design that specifies deterministic activity tracking, compatibility-safe defaults, staged nudge delivery, terminal escalation, and bounded parent/channel notification before implementation.
- **Prototype default-off recovery:** Allow a narrower opt-in experiment with explicit config and tests while leaving existing long-running subagent behavior unchanged by default.
- **Defer to timeout and manual controls:** Keep automatic activity-based kill out of core and route remaining recovery to explicit runTimeoutSeconds, status APIs, and manual kill/reap controls.

## Summary

Keep open: repeated reports through July 19, 2026 describe inbound Telegram outages after channel-stop timeouts, and the merged health-monitor recovery work appears to cover only one stale-task retry path rather than the still-reported unabortable polling-task case.

## What This Changes

The issue requests reliable recovery after a channel stop times out so stale lifecycle state cannot make later channel starts silently no-op.

## Best Possible Solution

Land one owner-reviewed recovery design that makes timeout state truthful, gives each channel a safe way to terminate or isolate an unresponsive task, and verifies that a fresh start restores inbound delivery without creating concurrent pollers.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should timed-out channel stops use a generic forced-recovery contract, or should transport owners such as Telegram provide explicit task/socket disposal before the gateway releases lifecycle ownership?

Rationale: The reported task can remain live after abort; choosing between generic store cleanup and transport-specific destruction determines whether recovery risks concurrent channel ownership or continues to wedge.

Likely owner: sheyanmin

Owner reason: Their merged recovery work is the closest current-main implementation on the affected restart path.

Owner confidence: medium

Options:

- **Define explicit transport recovery ownership (recommended):** Require the affected channel owner to expose a bounded disposal/recovery hook, then let the gateway release task state only after that contract is satisfied.
- **Use gateway-only forced map cleanup:** Clear the gateway lifecycle maps after timeout and accept the risk that an unresponsive old task may overlap the new task.
- **Escalate to a process recovery boundary:** Keep task ownership intact and add a bounded operator-visible gateway restart escalation after repeated failed channel recoveries.

## Reproduction Assessment

No high-confidence synthetic current-main reproduction is established here: reporters provide consistent real incidents, but the decisive case requires an established long-poll whose abort does not settle within the timeout.

## Solution Assessment

No: clearing stale state alone is not yet demonstrated as the best fix because the remaining reports indicate the underlying transport task and sockets can survive abort; recovery ownership must be made explicit before allowing a replacement task.

## Summary

Keep open: current main and v2026.6.11 still use committed-success-only message-tool evidence, so the duplicate-delivery timing gap remains; the safe repair needs a maintainer decision on deferred hold-and-release semantics before implementation.

## What This Changes

The issue requests preventing duplicate channel delivery when a failed message-tool send is retried in the same turn while a matching assistant reply is also flushed.

## Best Possible Solution

Implement same-route deferred hold-and-release for in-flight message-tool sends after maintainers choose release-by-default behavior and the route/text match key.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should matching assistant replies be held while a same-route message-tool retry is in flight, then dropped on confirmed delivery and released on failure or unresolved turn end?

Rationale: The source proves the duplicate timing gap, but choosing release timing and match granularity changes user-visible fallback behavior and could trade duplicate messages for suppressed replies.

Likely owner: steipete

Owner reason: The decision crosses embedded message-tool bookkeeping, channel fallback semantics, and current integration history for this delivery surface.

Owner confidence: medium

Options:

- **Hold And Release Same Route (recommended):** Hold matching replies for in-flight message-tool sends, drop them only after confirmed delivery, and release by default if the send fails or never resolves before turn end.
- **Keep Current Fallback Semantics:** Leave committed-success-only suppression in place until a broader delivery lifecycle design can avoid both duplicates and silent drops.
- **Suppress On Pending Send:** Treat pending sends as already delivered, accepting the risk that failed or unresolved sends can leave the user with no visible reply.

## Reproduction Assessment

Yes, by source inspection: failed message-tool sends clear pending evidence without committing sent evidence, while retry-time block/final suppression checks only committed successful sends. I did not run a live Telegram retry replay.

## Solution Assessment

No for the originally proposed pending-as-sent fix because current tests intentionally preserve fallback replies after message-tool errors. The maintainable direction is deferred hold-and-release for matching in-flight sends, with explicit release behavior if delivery never succeeds.

## Summary

Keep open: current main still uses committed-only message-tool suppression evidence, so the failed-send then in-flight retry duplicate path remains source-reproducible, and the safe repair needs a maintainer decision on hold-and-release fallback semantics.

## What This Changes

The issue reports duplicate channel delivery when a failed message tool send is retried in the same turn and the normal text reply flushes before the retry commits successful-delivery evidence.

## Best Possible Solution

Implement same-route deferred hold-and-release for in-flight message-tool sends after maintainers choose the release-by-default behavior and route/text match key.

## Reproduction Assessment

Yes, by source inspection: current main tracks in-flight message sends separately from committed delivery evidence, and both streaming and final-payload suppression ignore pending sends. I did not run a live Telegram retry replay in this read-only review.

## Solution Assessment

No for the issue's original pending-as-sent proposal: current tests intentionally preserve fallback replies after message-tool errors. The safer solution is deferred hold-and-release for same-route in-flight sends with explicit release behavior if delivery never succeeds.

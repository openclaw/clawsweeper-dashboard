## Summary

Keep open: current main and latest release still use committed-success-only message-tool suppression, so the failed-send plus in-flight retry timing gap remains; the safe repair needs a maintainer decision because treating pending sends as already sent can drop the user's only fallback reply.

## What This Changes

The issue reports duplicate Telegram delivery when a failed `message(action=send)` call is retried in the same turn and the assistant text reply is delivered before the retry succeeds.

## Best Possible Solution

Implement same-route deferred hold-and-release for in-flight message-tool sends, with release-by-default fallback unless maintainers explicitly choose a stricter policy.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should same-route assistant text that matches an in-flight `message(action=send)` retry be held and released by default if the pending send never confirms, using full route plus content as the match key?

Rationale: The source proves the timing gap, but choosing pending-as-sent versus hold-and-release changes user-visible fallback behavior and can trade duplicate messages for silent drops.

Likely owner: steipete

Owner reason: This decision sits in the embedded handler and reply-dedupe policy surface where steipete has the strongest recent feature-history trail.

Owner confidence: medium

Options:

- **Hold and release by default (recommended):** Hold matching replies while a same-route send is pending, drop them only after confirmed delivery, and release them if the pending send fails or never resolves.
- **Suppress against pending sends:** Treat pending sends as delivered for suppression, which reduces duplicates but can leave the user with no response after failed or abandoned retries.
- **Keep committed-only suppression:** Preserve the current fallback guarantee and accept duplicate delivery during retry timing windows until a broader delivery policy changes.

## Reproduction Assessment

Yes, at source level: failed message-tool sends clear pending evidence without committing sent evidence, while both streaming and final-payload suppression only read committed successful sends. I did not run a live Telegram retry replay.

## Solution Assessment

No for the original pending-as-sent proposal, because current tests intentionally preserve fallback replies after message-tool errors. The maintainable fix is deferred hold-and-release after maintainers choose the fallback and match-key semantics.

## Summary

Keep open: current main and v2026.6.11 still use committed-success-only message-tool evidence, so the retry duplicate timing gap remains; the safe repair needs a maintainer choice on deferred hold-and-release semantics.

## What This Changes

The issue reports duplicate channel delivery when a failed message-tool send is retried in the same turn before automatic reply suppression sees a committed send.

## Best Possible Solution

Implement same-route deferred hold-and-release for matching in-flight message-tool sends, dropping the held reply only after confirmed delivery and releasing it by default on failure or unresolved turn end.

Question: Should matching assistant replies be held while a same-route message-tool retry is in flight, then dropped on confirmed delivery and released on failure or unresolved turn end?

Rationale: The source proves the duplicate timing gap, but choosing release timing and match granularity changes user-visible fallback behavior and can trade duplicate messages for suppressed replies.

Likely owner: steipete

Owner reason: steipete has recent central commits in the embedded handler surface and the decision crosses message-tool bookkeeping, reply fallback semantics, and delivery-policy ownership.

Owner confidence: medium

Options:

- **Hold And Release Same Route (recommended):** Hold matching replies for in-flight message-tool sends, drop them only after confirmed delivery, and release by default if the send fails or never resolves before turn end.
- **Keep Committed-Only Suppression:** Leave current fallback semantics in place until a broader delivery lifecycle design can avoid both duplicates and silent drops.
- **Suppress On Pending Send:** Treat pending sends as already delivered and accept the risk that failed or unresolved sends can leave the user with no visible reply.

## Reproduction Assessment

Yes, by source inspection: failed message-tool sends clear pending evidence without committing sent evidence, while retry-time block/final suppression checks only committed successful sends. I did not run a live Telegram retry replay.

## Solution Assessment

No for the originally proposed pending-as-sent fix because current tests intentionally preserve fallback replies after message-tool errors. The maintainable direction is deferred hold-and-release for matching in-flight sends, with explicit release behavior if delivery never succeeds.

## Summary

Keep open: current main and v2026.6.11 still have the committed-only suppression timing gap described in the report, and the later discussion correctly identifies that the original pending-as-sent fix would risk dropping the only fallback reply when every send attempt fails. This needs a maintainer decision on hold-and-release behavior before a repair PR is safe.

## What This Changes

The issue reports duplicate messaging-channel delivery when a failed `message` tool send is retried in the same turn and an assistant text reply is delivered before the retry commits successful delivery evidence.

## Best Possible Solution

Add a bounded hold-and-release path for same-route in-flight message-tool sends: hold matching block/final replies, drop them if the send commits successful delivery, and release them if the send fails or never confirms under the chosen turn-end policy.

## Reproduction Assessment

Yes, by source inspection rather than a live Telegram replay. Current main still clears failed pending message-tool evidence without committing sent evidence, while both streaming and final-payload suppression only consult committed successful sends.

## Solution Assessment

No for the original proposed pending-as-sent fix, because existing fallback-on-error coverage shows it can drop the user's only response. The maintainable solution is hold-and-release for matching in-flight sends, with maintainer-owned fallback semantics.

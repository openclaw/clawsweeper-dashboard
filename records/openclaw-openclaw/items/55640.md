## Summary

Keep open: current main and the latest release still use committed-success-only message-tool suppression, so a failed send followed by an in-flight retry can still race the assistant text reply and produce duplicate delivery. The issue discussion also correctly identifies that the originally proposed pending-as-sent fix is unsafe because it can drop the only fallback reply after a failed send.

## What This Changes

The issue requests a fix for duplicate messaging-channel delivery when a failed `message(action=send)` call is retried in the same turn and the assistant text reply is delivered too.

## Best Possible Solution

Implement same-route hold-and-release for in-flight message-tool sends: hold matching assistant replies while a retry is pending, drop them only after delivery confirms, and release the fallback when delivery fails or remains unresolved.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: failed message-tool attempts clear pending evidence without committed sent evidence, while retry-time block/final suppression only reads committed successful sends. I did not run a live Telegram retry replay.

## Solution Assessment

No for the issue's proposed pending-as-sent fix because current tests intentionally preserve fallback replies after message-tool errors. The better solution is a hold-and-release design that waits for the in-flight same-route send to confirm or fail before dropping or releasing the assistant reply.

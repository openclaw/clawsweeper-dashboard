## Summary

Keep this issue open. It describes a narrow macOS regression in the recently added local-model onboarding path: gateway-owned progress frames are rendered but do not trigger the next long-poll request, so the sheet appears hung and never reaches its terminal result. The `maintainer` label also requires explicit maintainer handling rather than cleanup closure.

Likely related people: `steipete` is the strongest routing candidate (high confidence) from the merged setup-progress and macOS/web onboarding work.

## What This Changes

Fix macOS onboarding so gateway-driven local-model download or pull progress continues requesting wizard updates until completion rather than stopping after the first progress frame.

## System Context

The macOS onboarding sheet starts a gateway-backed provider preparation session for local models and renders wizard steps returned by the Gateway. Gateway progress is delivered as successive long-poll responses, so the client must request the next step until a user-input or terminal step is reached.

## Architecture Diagram

flowchart LR
  A[MacOS onboarding] --> B[Start local model preparation]
  B --> C[Gateway wizard session]
  C --> D[Gateway progress frame]
  D --> E[MacOS progress sheet]
  E --> F{Gateway owns next step?}
  F -->|Yes| C
  F -->|No: user or terminal| G[Answer or finish setup]

## Best Possible Solution

Add the same gateway-step continuation rule used by the web wizard runner to the macOS onboarding result handler, retain its existing attempt/session guards, add focused progress-through-completion coverage, and capture a redacted macOS live run showing advancing progress and automatic completion.

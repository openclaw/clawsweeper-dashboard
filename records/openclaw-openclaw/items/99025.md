## Summary

Keep this PR open: it targets a real source-level find-tool cleanup asymmetry, but the current patch broadens cleanup so normal fd close paths call child.kill() after the child has already exited, and the contributor proof still does not show the patched OpenClaw find/fd path running after the fix.

## What This Changes

The branch adds a sentinel-guarded stopChild path and a mocked regression test for fd-backed find cleanup on child error and close events.

## Best Possible Solution

Keep cleanup readline-only, invoke a guarded stop hook only from failure or abort paths that can leave fd alive, add coverage that normal close does not call kill, and require real patched find/fd terminal or log proof before merge.

Yes for the source-level asymmetry: current main's fd child error handler closes readline and rejects without invoking the child stop hook. No high-confidence runtime reproduction has proven an orphaned fd process on current main.

## Solution Assessment

No. The sentinel idea is useful, but putting stopChild inside shared cleanup makes normal close paths send a signal after fd has exited; a narrower failure-path stop is the safer fix.

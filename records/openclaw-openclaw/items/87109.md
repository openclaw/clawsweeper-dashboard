## Summary

Keep open: multiple macOS reports describe Gateway memory pressure coinciding with stalled tool calls and interrupted cron/session work, while the provided evidence does not establish one verified current-main root cause or show that failure reporting remains reliable after the Gateway event loop is wedged. The corrected PortGuardian restart report is separate, so it should not be treated as a fix for this issue.

## What This Changes

Investigate long-running macOS Gateway heap/RSS growth and ensure cron/session failures are recorded or surfaced when memory pressure stalls the Gateway process.

## System Context

The Gateway hosts agent sessions, scheduled cron jobs, provider calls, and memory-index work in one long-running Node process. When that process is memory-pressured or event-loop-starved, cron completion, tool delivery, and in-process failure alerts can all be affected together.

## Architecture Diagram

flowchart LR
  A[Scheduled cron jobs] --> B[Gateway process]
  C[Memory index and provider work] --> B
  B --> D[Node heap and event loop]
  D --> E[Tool and provider calls]
  D --> F[Cron completion reporting]
  E --> G[User-visible responses]
  F --> H[Failure alerts and recovery]

## Best Possible Solution

Establish a reproducible macOS long-uptime profile that identifies retained heap/RSS owners and separately decide whether interrupted cron runs need durable, restart-aware lifecycle accounting outside the unhealthy execution path.

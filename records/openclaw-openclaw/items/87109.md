Keep the issue open for maintainer-led current-main macOS launchd validation and a durable cron failure/recovery design that reports started-but-unfinished jobs after a wedged or restarted Gateway.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should cron failure reporting for a wedged or killed Gateway remain in-process only, or should OpenClaw add durable started-without-terminal-result recovery that can surface failure after restart?

Rationale: The remaining gap spans product semantics for failure alerts, task history, and restart recovery, not only the already-fixed memory-core watcher leak.

Likely owner: Vincent Koc

Owner reason: Recent task/session reliability history makes this the best available owner signal for the durable failure-reporting decision.

Owner confidence: medium

Options:

- **Add Durable Recovery (recommended):** Treat stale started cron runs without terminal outcomes as a recoverable failure/lost state and surface that through task history or failure alerts after restart.
- **Diagnostics Only:** Keep memory and liveness diagnostics as the supported surface and document that failureAlert is best-effort while the Gateway process is wedged.
- **External Watchdog:** Move this class of failure reporting to a launchd or doctor watchdog path instead of extending cron runtime semantics.

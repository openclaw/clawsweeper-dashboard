## Summary

Keep open: the PR is a useful follow-up to the merged Discord stream-error fix, but the current helper still suppresses the intended SIGKILL escalation after an earlier SIGTERM because it checks `ffmpeg.killed`.

## What This Changes

The PR updates Discord voice playback to kill the spawned ffmpeg process when stdout or stderr emit errors and extends the audio tests to assert SIGKILL on those stream errors.

## Best Possible Solution

Keep the targeted lifecycle helper, but separate actual process close from signal delivery so ordinary close can stay graceful while readable-pipe failures can still escalate to SIGKILL until ffmpeg has actually closed.

No, not yet: the PR is the right owner boundary, but the helper must allow force-kill escalation after a prior graceful signal instead of treating `ffmpeg.killed` as process-exited state.

- **[P2] Allow SIGKILL after an earlier SIGTERM:** `extensions/discord/src/voice/audio.ts:114`
  - body: `subprocess.killed` flips after `kill()` successfully sends a signal, not after the child exits. If playback closes first, `killFfmpeg()` sends SIGTERM and sets this flag; a later stdout/stderr error then calls `killFfmpeg("SIGKILL")`, but this guard suppresses the escalation while ffmpeg may still be running, leaving the exact orphan-process case this PR is meant to fix. Keep the `ffmpegClosed` guard, but let SIGKILL through after a prior SIGTERM and cover that ordering. ([nodejs.org](https://nodejs.org/api/child_process.html?utm_source=openai))

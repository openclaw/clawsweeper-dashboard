## Summary

Keep open: the PR targets a real missing stdout/stderr stream-error guard in the bundled Local CLI TTS provider, but the proposed no-op listener can hide real readable-pipe failures and missing after-fix real behavior proof still blocks merge.

## What This Changes

The branch adds no-op stdout/stderr error listeners to the bundled `tts-local-cli` speech provider child-process run path.

## Best Possible Solution

Settle child stdout/stderr stream errors through the `runCli` failure path so speech-core fallback and diagnostics see a real provider failure instead of silent suppression.

## Maintainer Decision

Required: false

## Reproduction Assessment

Source-reproducible, not live-reproduced: current main leaves child stdout/stderr without `error` listeners, and Node throws unhandled `error` events with no listener. The PR defect is also source-visible because the new listeners consume the stream errors without failing synthesis.

## Solution Assessment

No. Adding stdout/stderr listeners is the right surface, but the best fix is to reject the CLI synthesis on readable stream errors rather than no-op them, because stdout may carry the audio bytes.

- **[P2] Reject readable pipe errors instead of swallowing them:** `extensions/tts-local-cli/speech-provider.ts:218-220`
  - body: The new handler consumes any stdout/stderr `error` and lets `close` continue. Handle these events by settling `runCli` as failed, and terminate the child if needed, while still preventing an unhandled EventEmitter error.

## Summary

Keep open: current main mitigates parts of the old JSON-era auth-store problem, but it still does not provide a maintainer-approved env-key rotation sync, bulk auth update, or warning path for profile-shadowed API key rotation.

## What This Changes

The issue requests a user-facing way to sync, warn, or safely recover when rotated provider API keys are shadowed by per-agent auth profiles.

## Best Possible Solution

Add a maintainer-approved credential-rotation path, likely explicit auth-profile update or doctor/status repair guidance, while preserving profile precedence unless security review approves broader sync or fallback behavior.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw solve API-key rotation shadowing by explicitly updating auth profiles, warning/doctor-repairing profile shadows, or falling back from failed stored profiles to env/config keys?

Rationale: The source-backed issue is real, but each proposed solution changes credential propagation, auth precedence, or failure recovery semantics for provider credentials.

Likely owner: steipete

Owner reason: The decision sits on the auth-store, auth-order, and SQLite migration boundary where steipete has the strongest recent merged history.

Owner confidence: high

Options:

- **Prefer explicit repair/update path (recommended):** Add a user-invoked auth profile update or doctor/status repair flow that makes affected agents visible and updates only selected credentials with focused security tests.
- **Approve automatic sync:** Allow config/env key changes to propagate into agent auth stores automatically, accepting a larger secret-copy surface in exchange for less operator work.
- **Approve runtime fallback:** Let failed stored credentials fall back to env/config keys, accepting more dynamic auth behavior and requiring clear auth.order and audit semantics.

## Reproduction Assessment

Yes for the current behavior by source inspection: ordinary provider auth resolution checks stored profiles before env fallback, and the API-key paste command updates one selected agent store. I did not run a live multi-agent 401 scenario, so this is source-reproducible rather than live-reproduced.

## Solution Assessment

Unclear: explicit sync, warnings/doctor repair, and runtime fallback are all plausible, but the best fix depends on the desired credential propagation and precedence policy. A narrow explicit repair/update path is the safest default until maintainers approve automatic secret copying or fallback.

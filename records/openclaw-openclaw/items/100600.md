## Summary

Keep open: current main still turns empty-detail `response.failed` into `no_error_details` and lets that reason enter auth-profile cooldown/fallback handling, while no related merged or open item owns the Azure Foundry credential-cooldown cascade.

## What This Changes

The issue asks OpenClaw to treat Azure Foundry empty-detail `response.failed` as a transient upstream failure instead of cooling down a valid auth profile and cascading to misleading fallback errors.

## Best Possible Solution

Keep the diagnostic `no_error_details` classification, but prevent detail-less provider failures from poisoning shared auth-profile health unless a provider-specific probe proves an account or quota problem.

## Solution Assessment

Yes, the narrow core fix is the best path: keep the transport diagnostic and fallback state, but stop treating empty-detail upstream failures as shared auth-profile health evidence without affirmative auth/quota proof.

## Summary

Keep open: current main and v2026.6.11 still use a fixed cross-origin redirect safe-header allowlist with no operator config hook, and the existing security label means this needs maintainer security/product review rather than cleanup closure.

## What This Changes

The issue requests a configuration option that lets users opt in additional request headers to survive fetch-guard cross-origin redirects.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, implement a scoped operator policy that constrains both header names and destination origins with docs and regression tests.

## Solution Assessment

Unclear until maintainers choose the trust model. A global header-only allowlist is riskier than a scoped operator policy that also constrains redirect destinations.

## Summary

Keep open: current main and v2026.6.11 still use a fixed cross-origin redirect safe-header allowlist and tests assert that `x-api-key` is stripped, so the requested opt-in custom-header retention remains an unresolved security/config product decision.

## What This Changes

The issue requests an opt-in configuration surface that lets selected custom request headers survive fetch-guard cross-origin redirects.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, implement a narrowly scoped operator policy that validates header names and redirect destinations with focused tests and docs.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add an operator-controlled way to retain selected custom headers across cross-origin fetch-guard redirects, and should that policy be scoped by destination origin instead of a global safe-header list?

Rationale: This deliberately relaxes a credential-forwarding boundary and adds public config surface, so automation cannot choose the acceptable trust model or guardrails.

Likely owner: steipete

Owner confidence: high

Options:

- **Design a scoped operator policy (recommended):** Allow custom header retention only with strict defaults, header-name validation, redirect-destination scoping, docs, and regression coverage.
- **Keep strict stripping only:** Reject the new config surface and continue dropping credential-like custom headers on all cross-origin redirects.
- **Add the requested global list:** Implement `additionalSafeHeaders` directly, accepting that any allowed header may be replayed to any cross-origin redirect target.

## Reproduction Assessment

Yes, at source level: current main strips `x-api-key` on cross-origin redirects and the current config schema has no fetch-guard extension option. I did not run a live integration-specific reproduction.

## Solution Assessment

Unclear until maintainers choose the trust model. The requested global safe-header extension is riskier than a scoped operator policy that also constrains redirect targets.

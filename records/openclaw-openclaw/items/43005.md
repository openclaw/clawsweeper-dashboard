## Summary

Keep open: current main and v2026.6.11 still use a fixed cross-origin redirect safe-header allowlist with no custom-header config surface, and adding one would change a credential-forwarding security boundary.

## What This Changes

The issue requests an opt-in `security.fetchGuard.additionalSafeHeaders` config option so selected custom headers can survive fetch-guard cross-origin redirects.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, implement a scoped operator policy that constrains both header names and destination origins with docs and regression tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw allow operator-configured custom headers to survive cross-origin fetch-guard redirects, and if yes must the permission be scoped by redirect destination origin rather than a global header-name allowlist?

Rationale: The request changes a credential-forwarding boundary and adds public config surface, so automation cannot choose the acceptable trust model or guardrails.

Likely owner: steipete

Owner reason: The current strict custom-header behavior traces to steipete's security hardening commit, and the open question is whether to relax that trust boundary.

Owner confidence: high

Options:

- **Design scoped operator policy (recommended):** Add the capability only with header-name validation, destination-origin scoping, documentation, and tests proving the default remains strict.
- **Keep strict stripping only:** Reject the new config surface and keep custom credential-like headers blocked on all cross-origin redirects.
- **Add global header extension list:** Implement the proposed header-name-only config while accepting the higher risk that an allowed header can be replayed to any redirect origin.

## Reproduction Assessment

Yes, at source level: current main strips `X-Api-Key` on cross-origin redirects, and the config schema has no fetch-guard extension option. The issue does not include a live integration-specific reproduction.

## Solution Assessment

Unclear until maintainers choose the trust model. A global header-only allowlist is riskier than a scoped operator policy that also constrains redirect destinations.

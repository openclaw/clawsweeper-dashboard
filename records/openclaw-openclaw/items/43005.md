## Summary

Keep open: current main and the latest release still use a fixed cross-origin redirect safe-header allowlist, so the requested opt-in custom-header retention remains a security/config product decision rather than completed work.

## What This Changes

The issue asks for an opt-in configuration surface that would allow named custom request headers to survive fetch-guard cross-origin redirects.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, implement a narrowly scoped operator policy that constrains both header names and redirect destinations.

## Maintainer Decision

Required: true

Question: Should OpenClaw introduce an operator-controlled way to retain custom headers such as x-api-key across cross-origin fetch-guard redirects, and must that policy be scoped by destination origin instead of a global safe-header extension?

Rationale: The request intentionally changes a credential-forwarding boundary and adds public config surface, so automation cannot choose the trust model or acceptable guardrails.

Owner confidence: high

Options:

- **Design a scoped operator policy (recommended):** Allow the capability only with approved header-name validation, destination-origin scoping, docs, and tests that preserve strict defaults.
- **Keep strict stripping only:** Reject the new config surface and continue dropping credential-like custom headers on all cross-origin redirects.
- **Add a global header extension list:** Implement the requested shape directly, accepting the broader risk that an allowed header can be replayed to any redirect origin.

Yes, at source level: current code strips X-Api-Key on cross-origin redirects and the config schema has no fetch-guard extension option. I did not run a live integration-specific reproduction.

## Solution Assessment

Unclear until maintainers choose the trust model. The requested global header allowlist is riskier than a scoped operator policy that also constrains redirect targets or owner-specific usage.

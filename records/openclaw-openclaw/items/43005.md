## Summary

Keep open: current main and v2026.6.11 still strip custom headers such as x-api-key on cross-origin fetch-guard redirects, and relaxing that security boundary needs maintainer product/security direction before implementation.

## What This Changes

Request to add an opt-in configuration surface that lets operators retain selected custom headers across fetch-guard cross-origin redirects.

## Best Possible Solution

Keep strict stripping as the default; if approved, implement a scoped operator policy with header-name validation, HTTPS and destination-origin constraints, docs, and regression tests.

Options:

- **Design scoped operator policy (recommended):** Allow the capability only with maintainer-approved header validation, HTTPS and destination-origin scoping, docs, and tests that preserve strict defaults.
- **Keep strict stripping only:** Reject the new config surface and continue dropping non-standard headers on all cross-origin redirects.
- **Add global header extension list:** Implement the requested additionalSafeHeaders shape directly, accepting the higher risk that allowed headers can replay to any redirect origin.

Yes, at source level. Current source and tests show x-api-key is stripped on cross-origin redirects, and current config/schema has no fetch-guard extension option.

## Solution Assessment

Unclear until maintainers choose the trust model. A global header-only allowlist is riskier than a scoped operator policy that constrains both header names and redirect targets.

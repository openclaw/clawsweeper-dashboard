Keep open: current main and v2026.6.11 still use a fixed cross-origin redirect safe-header allowlist, and the requested opt-in custom-header retention remains a security/config product decision.

## What This Changes

Add configuration to extend fetch-guard's cross-origin redirect safe-header allowlist while keeping strict stripping as the default.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, implement a narrowly scoped operator policy that constrains both header names and redirect destinations.

- **Design a scoped operator policy (recommended):** Allow the capability only with strict defaults, header-name validation, destination-origin scoping, docs, and focused tests.

- **Add the requested global header list:** Implement additionalSafeHeaders directly, accepting that any allowed header may be replayed to any redirect origin.

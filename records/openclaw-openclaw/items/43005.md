## Summary

Keep open: current main and v2026.6.11 still use a fixed cross-origin redirect safe-header allowlist, and the requested opt-in custom-header policy would relax a credential-forwarding boundary that needs maintainer security/product direction.

## What This Changes

The issue asks for an opt-in configuration surface that allows selected custom headers to survive fetch-guard cross-origin redirects.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, implement a scoped operator policy with header-name validation, destination-origin scoping, documentation, and tests proving the default remains strict.

## Summary

Keep open: current main and the latest release still use a fixed cross-origin redirect safe-header allowlist, so the requested opt-in custom-header retention remains an unresolved security/config product decision rather than completed work.

## What This Changes

The issue requests an operator configuration option to retain selected custom headers, such as x-api-key, when fetch-guard follows cross-origin redirects.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, implement a narrowly scoped operator policy that constrains both header names and redirect destinations.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw introduce an operator-controlled way to retain custom headers such as x-api-key across cross-origin fetch-guard redirects, and must that policy be scoped by destination origin instead of a global safe-header extension?

Rationale: The request intentionally changes a credential-forwarding boundary and adds public config surface, so automation cannot choose the acceptable trust model or guardrails.

Likely owner: steipete

Owner reason: The current strict redirect-header boundary traces to steipete's security-hardening commits, and the open question is whether that boundary may be relaxed.

Owner confidence: high

Options:

- **Design a scoped operator policy (recommended):** Allow the capability only with strict defaults, header-name validation, destination-origin scoping, docs, and focused tests.
- **Keep strict stripping only:** Reject the new config surface and continue dropping credential-like custom headers on all cross-origin redirects.
- **Add the requested global header list:** Implement additionalSafeHeaders directly, accepting that any allowed header may be replayed to any redirect origin.

## Reproduction Assessment

Yes, at source level: current main strips x-api-key on cross-origin redirects and the config schema has no fetch-guard extension option. I did not run a live integration-specific reproduction.

## Solution Assessment

Unclear until maintainers choose the trust model. The requested global header allowlist is riskier than a scoped operator policy that also constrains redirect targets or owner-specific usage.

## Summary

Keep open: current main and v2026.6.11 still use a fixed cross-origin redirect safe-header allowlist, and the requested opt-in custom-header policy changes a credential-forwarding boundary that needs maintainer security/product direction.

## What This Changes

Request an opt-in config surface that lets selected custom headers survive fetch-guard cross-origin redirects while preserving strict defaults.

## Best Possible Solution

Keep strict stripping by default; if maintainers approve the capability, implement a scoped operator policy with header-name validation, destination-origin scoping, docs, and tests proving the default remains strict.

Question: Should OpenClaw allow operator-configured custom headers to survive cross-origin fetch-guard redirects, and if yes must that permission be scoped by destination origin instead of a global header-name allowlist?

Rationale: This changes a credential-forwarding boundary and adds public security/config surface, so automation cannot choose the trust model or acceptable guardrails.

Likely owner: steipete

Owner reason: The strict behavior traces to steipete's security hardening commit, and the remaining choice is whether to relax that boundary.

Owner confidence: high

Options:

- **Design scoped operator policy (recommended):** Add the capability only with header-name validation, destination-origin scoping, documentation, and tests that prove strict default behavior remains unchanged.
- **Keep strict stripping only:** Reject the new config surface and keep custom credential-like headers blocked on all cross-origin redirects.
- **Add global header extension list:** Implement the requested header-name-only config while accepting the higher risk that an allowed header can be replayed to any redirect origin.

## Reproduction Assessment

Yes, at source level: current main strips X-Api-Key on cross-origin redirects and the config type has no fetch-guard extension option. The issue does not include a live integration-specific reproduction.

## Solution Assessment

Unclear until maintainers choose the trust model. A global header-only allowlist is not the safest shape; a scoped operator policy that also constrains redirect destinations is the more maintainable direction if the capability is approved.

## Summary

Keep open: current main and v2026.6.11 still use a fixed cross-origin redirect header allowlist, and allowing x-api-key-style exceptions is a security/config product decision rather than an autonomous bug fix.

## What This Changes

Requests an opt-in fetch-guard configuration option so selected custom headers can survive cross-origin redirects.

## Best Possible Solution

Have maintainers choose a security-reviewed design; if accepted, keep the default stripping behavior and add a narrowly scoped, audited opt-in with schema, docs, and redirect tests.

Options:

- **Design scoped opt-in (recommended):** Add an explicit opt-in that is constrained by redirect target/origin and caller surface, with auditability and tests for secret-like headers.
- **Keep fixed core allowlist:** Leave core strict and document that integrations needing custom redirect auth must own redirect handling or avoid cross-origin redirects.
- **Defer to broader fetch-auth design:** Handle this together with the related auth-forwarding policy work so OpenClaw has one credential-forwarding model.

Yes for the current limitation: existing source and tests show X-Api-Key is stripped on cross-origin redirects. I did not run tests because this review is read-only.

## Solution Assessment

Unclear: the proposed global security.fetchGuard.additionalSafeHeaders shape is plausible but likely too broad for a credential boundary. A scoped per-origin or per-caller opt-in would be safer if maintainers accept the product direction.

## Summary

Keep open: current main and the latest release still use a fixed cross-origin redirect safe-header allowlist, so custom header retention remains an unresolved security and config product decision.

## What This Changes

The issue requests a config option to let selected custom request headers survive fetch-guard cross-origin redirects.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, implement a scoped operator policy that validates header names and constrains allowed redirect destinations.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw introduce an operator-controlled way to retain custom headers such as `x-api-key` across cross-origin fetch-guard redirects, and must it be scoped by redirect destination origin rather than a global safe-header extension?

Rationale: The request intentionally changes a credential-forwarding boundary and adds public security config, so automation cannot choose the trust model or acceptable guardrails.

Likely owner: steipete

Owner reason: The current strict behavior traces to this history and the decision changes that trust boundary.

Owner confidence: high

Options:

- **Design scoped operator policy (recommended):** Allow the capability only with header-name validation, destination-origin scoping, docs, and tests that keep the default strict.
- **Keep strict stripping only:** Reject the new config surface and continue dropping custom credential-like headers on all cross-origin redirects.
- **Add global header extension list:** Implement the requested shape directly, accepting the higher risk that any allowed header can be replayed to any redirect origin.

## Reproduction Assessment

Yes, at source level: current main strips `X-Api-Key` on cross-origin redirects and the strict config schema has no fetch-guard extension option. The issue does not include a live integration-specific reproduction.

## Solution Assessment

Unclear until maintainers choose the trust model. A header-only global allowlist is riskier than a narrowly scoped operator policy that also constrains redirect targets or owner-specific usage.

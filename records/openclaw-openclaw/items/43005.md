## Summary

Keep open: current main and v2026.6.11 still use a fixed cross-origin redirect safe-header allowlist and have no `security.fetchGuard` config surface, so the request remains an unresolved security/config product decision.

## What This Changes

Request to add opt-in configuration for retaining selected custom request headers across fetch-guard cross-origin redirects.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, implement a scoped operator policy with header-name validation, destination-origin constraints, docs, and regression tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw introduce an operator-controlled way to retain custom headers such as `x-api-key` across cross-origin fetch-guard redirects, and if yes must it be scoped by destination origin rather than a global header list?

Rationale: The requested behavior changes a credential-forwarding boundary and adds public security config, so automation cannot choose the trust model or acceptable guardrails.

Likely owner: steipete

Owner reason: The current strict behavior traces to this security-hardening work, and the open question is whether to loosen that trust boundary.

Owner confidence: high

Options:

- **Design a scoped operator policy (recommended):** Allow custom header retention only with explicit header validation, target-origin scoping, docs, and tests that prove the default remains strict.
- **Keep strict stripping only:** Reject the new config surface and continue dropping custom credential-like headers on all cross-origin redirects.
- **Add a global extension list:** Implement the requested header-only config shape, accepting the higher risk that any allowed header can be replayed to any redirect origin.

## Reproduction Assessment

Yes, at source level: current main strips `X-Api-Key` on cross-origin redirects, and the strict config schema has no fetch-guard extension option. The issue does not provide a live integration-specific reproduction.

## Solution Assessment

Unclear until maintainers choose the trust model. A header-only global allowlist is riskier than a scoped operator policy that also constrains redirect targets or owner-specific usage.

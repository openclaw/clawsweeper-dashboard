## Summary

Keep open: current main and the latest release still enforce a fixed cross-origin redirect safe-header allowlist and expose no custom safe-header config, so the requested opt-in capability remains an unresolved security/product decision.

## What This Changes

The issue requests a new `security.fetchGuard.additionalSafeHeaders` config option so custom headers can be retained across cross-origin guarded-fetch redirects.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, add a scoped operator policy with header-name validation, target-origin constraints, docs, and regression tests.

## Maintainer Decision

Question: Should OpenClaw introduce an operator-controlled way to retain custom headers such as `x-api-key` across cross-origin fetch-guard redirects, and if yes must it be scoped by destination origin rather than a global safe-header extension?

Rationale: The requested behavior intentionally changes a credential-forwarding boundary and adds public config surface, so automation cannot choose the trust model or acceptable guardrails.

Likely owner: steipete

Owner reason: The current strict behavior traces to steipete's security hardening commit, and the remaining choice is about changing that trust boundary.

Owner confidence: high

Options:

- **Design scoped operator policy (recommended):** Allow the capability only with header-name validation, destination-origin scoping, docs, and tests that keep default behavior strict.
- **Keep strict stripping only:** Reject the new config surface and keep custom credential-like headers blocked on all cross-origin redirects.
- **Add global header extension list:** Implement the requested shape directly, accepting the higher risk that any allowed header can be replayed to any redirect origin.

## Reproduction Assessment

Yes, at source level: current tests and code show `X-Api-Key` is stripped on cross-origin redirects, and the strict config schema has no extension option. The issue does not include a live integration-specific reproduction.

## Solution Assessment

Unclear until maintainers choose the trust model. A header-only global allowlist is riskier than a scoped operator policy that also constrains redirect targets or owner-specific usage.

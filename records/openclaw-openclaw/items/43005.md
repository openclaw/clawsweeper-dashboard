## Summary

Keep open: current main and v2026.6.11 still use a fixed cross-origin redirect safe-header allowlist, and the requested opt-in retention of credential-like custom headers needs maintainer security/product direction before implementation.

## What This Changes

Request an opt-in `security.fetchGuard.additionalSafeHeaders` config to retain selected custom headers across fetch-guard cross-origin redirects while keeping strict defaults.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, implement a narrowly scoped operator policy with header-name validation, HTTPS and destination-origin constraints, docs, and regression tests.

## Solution Assessment

Unclear until maintainers choose the trust model. A global header-only allowlist is riskier than a scoped operator policy that constrains both header names and redirect targets.

## Summary

Keep open: current main and the latest release still use a fixed cross-origin redirect safe-header allowlist, so the requested opt-in custom-header retention remains an unresolved security/config product decision.

## What This Changes

The issue requests an opt-in configuration option for preserving named custom headers across fetch-guard cross-origin redirects.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, implement a narrow operator policy with explicit header and target-origin guardrails plus regression tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw introduce an operator-controlled way to retain custom headers such as `x-api-key` across cross-origin fetch-guard redirects, and if yes must it be scoped by destination origin rather than a global safe-header extension?

Rationale: The requested behavior intentionally changes a credential-forwarding boundary and adds public config surface, so automation cannot choose the trust model or acceptable guardrails.

Likely owner: steipete

Owner reason: The current strict behavior traces to this security hardening commit, and the remaining decision is about changing that trust boundary.

Owner confidence: high

Options:

- **Design a scoped operator policy (recommended):** Allow the capability only with maintainer-approved header-name validation, destination-origin scoping, docs, and regression tests that keep the default strict.
- **Keep strict stripping only:** Reject the new config surface and keep custom credential-like headers blocked on all cross-origin redirects.
- **Add a global header extension list:** Implement the requested shape directly, accepting the higher risk that an allowed header can be replayed to any redirect origin.

## Reproduction Assessment

Yes, at source level: current code strips `X-Api-Key` on cross-origin redirects, and the strict config schema has no fetch-guard extension option. The issue does not provide a live integration-specific reproduction.

## Solution Assessment

Unclear until maintainers choose the trust model. A header-only global allowlist is riskier than a narrowly scoped operator policy that also constrains redirect targets or owner-specific usage.

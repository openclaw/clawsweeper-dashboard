## Summary

Keep open: current main and v2026.6.11 still use a fixed cross-origin redirect header allowlist with no config extension, and the requested opt-in custom-header retention is a security/product decision about forwarding credential-like headers across origins.

## What This Changes

The issue asks to add configuration that lets operators allow specified custom headers to survive fetch-guard cross-origin redirects.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve an exception, design a narrow operator policy with header-name validation, destination-origin scoping, docs, and regression tests for both default stripping and approved retention.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw introduce an operator-controlled way to retain custom headers such as `x-api-key` across cross-origin fetch-guard redirects, and if yes must it be scoped by destination origin rather than a global safe-header extension?

Rationale: The request intentionally changes a credential-forwarding boundary and adds public config surface, so automation cannot choose the trust model or acceptable guardrails.

Likely owner: steipete

Owner reason: The current strict custom-header redirect behavior traces to steipete's security hardening commit, and the decision changes that trust boundary.

Owner confidence: high

Options:

- **Design a scoped operator policy (recommended):** Allow the capability only with maintainer-approved header validation, destination-origin scoping, docs, and tests that keep the default strict.
- **Keep strict stripping only:** Reject the new config surface and keep custom credential-like headers blocked on all cross-origin redirects.
- **Add a global header extension list:** Implement the requested shape directly, accepting the higher risk that an allowed header can be replayed to any redirect origin.

## Reproduction Assessment

Yes, at source level: current main strips `X-Api-Key` on cross-origin redirects and the strict config schema has no fetch-guard extension option. The issue does not include a live integration-specific reproduction.

## Solution Assessment

Unclear until maintainers choose the trust model. A header-only global allowlist is riskier than a scoped operator policy that also constrains redirect targets or owner-specific usage.

## Summary

Keep open: current main and v2026.6.11 still use a fixed cross-origin redirect safe-header allowlist, so the requested opt-in custom-header retention remains an unresolved security/config product decision.

## What This Changes

The issue requests an opt-in fetch-guard configuration option that would let selected custom headers survive cross-origin redirects.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, implement a narrow operator policy with explicit header and target-origin guardrails plus tests for default stripping and approved retention.

## Reproduction Assessment

Yes, at source level: current code strips `X-Api-Key` on cross-origin redirects, and the strict config schema has no fetch-guard extension option. The issue does not provide a live integration-specific reproduction.

## Solution Assessment

Unclear until maintainers choose the trust model. A header-only global allowlist is riskier than a narrowly scoped operator policy that also constrains redirect targets or owner-specific usage.

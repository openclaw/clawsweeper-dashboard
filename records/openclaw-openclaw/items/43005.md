## Summary

Keep open: current main and v2026.6.11 still use a fixed cross-origin redirect safe-header allowlist, and allowing custom credential-like headers across origins needs maintainer security/product direction before implementation.

## What This Changes

The issue requests an opt-in configuration surface for allowing selected custom headers to survive fetch-guard cross-origin redirects.

## Best Possible Solution

Keep strict stripping as the default; if maintainers approve the capability, implement a narrowly scoped operator policy with header-name validation, destination-origin constraints, docs, and regression tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add an operator-controlled way to retain custom headers such as x-api-key across cross-origin fetch-guard redirects, and must that policy be scoped by destination origin rather than a global safe-header extension?

Rationale: The request intentionally changes a credential-forwarding boundary and adds public config surface, so automation cannot choose the acceptable trust model or guardrails.

Likely owner: steipete

Owner reason: The strict behavior traces to steipete's security hardening commit, and the remaining choice changes that trust boundary.

Owner confidence: high

Options:

- **Design scoped operator policy (recommended):** Allow the capability only with maintainer-approved header validation, HTTPS and destination-origin scoping, docs, and tests that preserve strict defaults.
- **Keep strict stripping only:** Reject the new config surface and continue dropping non-standard headers on all cross-origin redirects.
- **Add global header list:** Implement the requested additionalSafeHeaders shape directly, accepting the higher risk that allowed headers can replay to any redirect origin.

## Reproduction Assessment

Yes, at source level. Current source and tests show x-api-key is stripped on cross-origin redirects, and current config/schema has no fetch-guard extension option.

## Solution Assessment

Unclear until maintainers choose the trust model. A global header-only allowlist is riskier than a scoped operator policy that constrains both header names and redirect targets.

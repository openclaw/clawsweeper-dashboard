## Label Justifications

- `P2`: A valid no-timeout cron setting is blocked in the Control UI, but ordinary cron creation still works and the affected surface is limited to the timeout field.
- `impact:ux-friction`: Users configuring long-running cron jobs through the web UI hit an avoidable validation error and cannot use the backend-supported no-timeout sentinel there.

## Summary

Keep open: current `main` and the latest release still reject `timeoutSeconds: 0` in the Control UI cron form, while the backend schema and cron runtime already accept zero as the no-timeout sentinel. The linked open pull request is the active fix candidate, so the issue should stay open until that PR lands or is replaced.

## What This Changes

Accept `timeoutSeconds: 0` in the Control UI cron form as no-timeout mode and preserve it in the cron job payload.

## Best Possible Solution

Land a focused Control UI fix that accepts explicit zero in validation, preserves `timeoutSeconds: 0` in the cron payload, and updates the cron form regression test; replace the linked PR only if it cannot be repaired.

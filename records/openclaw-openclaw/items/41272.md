## Label Justifications

- `P2`: This is a normal-priority product bug with limited blast radius: the Control UI blocks a valid cron no-timeout value while the backend contract already supports it.
- `impact:ux-friction`: Users configuring long-running cron jobs through the UI hit avoidable validation friction and cannot express the established no-timeout sentinel there.

## Summary

Keep open: current main and the latest release still reject explicit `timeoutSeconds: 0` in the Control UI cron form even though the gateway cron contract and runtime accept zero as no-timeout. The open linked pull request is the active fix candidate and uses closing syntax, so this issue should stay open until that PR lands or is replaced.

## What This Changes

The issue requests accepting `timeoutSeconds: 0` in the cron job UI as a no-timeout mode instead of rejecting it during validation.

## Best Possible Solution

Land a focused UI cron fix through the linked PR or an equivalent replacement that updates validation, preserves explicit zero in the payload, rejects negative/non-finite values, and adds regression coverage.

Yes by source inspection. Current main rejects `timeoutSeconds: "0"` in `validateCronForm`, drops explicit zero in `buildCronPayload`, and the adjacent test still expects the invalid-timeout error.

## Solution Assessment

Yes, the best fix belongs at the Control UI form/payload boundary because the gateway schema, normalization, and runtime already support zero as no-timeout. The linked PR or a focused replacement should update both validation and payload preservation rather than creating a new backend behavior.

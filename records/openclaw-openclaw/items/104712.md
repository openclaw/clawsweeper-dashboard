## Label Justifications

- `P1`: Merging can cause duplicate agent executions for concurrent webhook retries, breaking an established idempotency workflow.
- `merge-risk: 🚨 message-delivery`: Concurrent same-key requests can dispatch duplicate agent work instead of replaying one accepted run.
- `merge-risk: 🚨 availability`: The new fixed admission timeout can abort slow startup and return 503 where current main responds immediately.

## Summary

The admission boundary is correct, but the new await creates an in-flight idempotency race: concurrent requests with the same key can launch duplicate agent runs before either result is cached. Real behavior proof is also still missing.

## What This Changes

The PR makes agent hook HTTP responses wait for runner admission, maps pre-start failures to 409/502/503, aborts startup after 15 seconds, and caches idempotency only after successful admission.

## Best Possible Solution

Track an in-flight dispatch per replay key so concurrent duplicates await the same admission result, cache only successful run ids, remove failed entries for retry, and prove the live HTTP behavior.

## Solution Assessment

No, not yet. Admission-gated acknowledgment is the correct boundary, but it must preserve the existing single-dispatch idempotency contract with an in-flight entry.

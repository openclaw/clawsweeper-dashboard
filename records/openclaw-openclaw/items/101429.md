## Summary

Keep open: the bounded-read mechanism is sound, but the current error handling introduces a merge-blocking compatibility regression by silently disabling oversized ignore sources and expanding the workspace scan.

## What This Changes

The PR resolves ignore-file symlink chains, bounds `.gitignore`, `.ignore`, and `.fdignore` reads at 4 MiB through `@openclaw/fs-safe`, and adds five focused regression tests.

## Best Possible Solution

Keep the race-safe bounded reader and symlink preservation, but return a distinct over-cap result to the skill loader and avoid silently scanning content that the ignore source may exclude; the affected scan should stop with an actionable diagnostic unless maintainers explicitly choose another policy.

Question: When a workspace ignore file exceeds the new 4 MiB limit, should skill scanning stop with a diagnostic, continue after warning, or silently scan without those ignore rules?

Rationale: The byte-bound implementation is mechanically correct, but each failure policy changes user-visible scan inclusion; current code and docs do not establish which tradeoff maintainers intend.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Stop with diagnostic (recommended):** Fail the affected workspace scan non-fatally with an actionable warning rather than silently scanning content the ignore file may exclude.
- **Warn and continue:** Continue without the oversized rules but identify the skipped file and explain that additional paths may be scanned.
- **Silently continue:** Accept the current patch behavior and treat oversized ignore files like unreadable sources with no user indication.

## Reproduction Assessment

Yes from source inspection: current main synchronously buffers each discovered ignore file without a byte limit, and the recursive skill-loader path reaches that helper. This read-only review did not intentionally create an OOM process.

## Solution Assessment

No, not as currently shaped: the race-safe bound is the correct mechanism, but collapsing the over-cap error into `null` silently reverses the effective inclusion policy; the loader should handle that condition explicitly.

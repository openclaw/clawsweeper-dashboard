## Summary

Keep open: this PR targets a real Windows update race, but the patch changes generic Scheduled Task stop/restart semantics, lacks after-fix real Windows proof, and the narrower maintainer PR is still draft/conflicting rather than a safe superseding close target.

## What This Changes

The PR adds `schtasks /Change /DISABLE` after Windows Scheduled Task stop and `schtasks /Change /ENABLE` before Scheduled Task restart.

## Best Possible Solution

Use an update-scoped suspend/resume guard that disables only enabled Windows Scheduled Task autostart during mutable package replacement and restores only tasks this invocation disabled.

## Reproduction Assessment

Yes, source-reproducible. Current main stops the managed service before mutable update work and the Windows Scheduled Task stop implementation uses `schtasks /End` without disabling repeated triggers; I did not run a native Windows update in this read-only review.

## Solution Assessment

No. This is a plausible mitigation, but it is broader than the bug because it changes generic stop/restart behavior instead of owning temporary suspension inside the update lifecycle.

  - body: The new `/DISABLE` call is inside `stopScheduledTask()`, and the Windows service registry routes ordinary `openclaw gateway stop` to this function. That turns a normal stop into persisted autostart suppression, so the suspend should live in the update lifecycle instead.
  - confidence: 0.91

  - body: The new `/ENABLE` in `restartScheduledTask()` runs for normal restarts too, even when this flow did not disable the task. That can re-enable an operator-disabled task; track update-scoped suspension state and restore only tasks this invocation disabled.
  - confidence: 0.87

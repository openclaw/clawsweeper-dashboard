## Summary

Keep open: current main and v2026.6.11 still have the Windows Scheduled Task update race, but this PR fixes it at the generic stop/restart layer, which would change normal Windows service semantics and still lacks after-fix real Windows proof.

## What This Changes

The branch adds `/DISABLE` after Windows Scheduled Task stop and `/ENABLE` before Scheduled Task restart in `src/daemon/schtasks.ts`.

## Best Possible Solution

Land or replace an update-scoped suspend/resume guard that disables only enabled Windows Scheduled Task autostart during package replacement and restores only tasks that invocation disabled.

## Reproduction Assessment

Yes, source-reproducible. Current main stops the managed service before mutable update work, and the Windows Scheduled Task stop implementation uses `/End` without disabling repeated triggers; I did not run a native Windows update in this read-only review.

## Solution Assessment

No. This PR is a plausible mitigation, but it is broader than the bug because it changes generic Windows stop/restart behavior instead of owning temporary suspension inside the update lifecycle.

- **[P1] Keep persistent disable out of generic stop:** `src/daemon/schtasks.ts:1334-1335`
  - body: The new `/DISABLE` call is inside `stopScheduledTask()`, and the Windows service registry routes ordinary `openclaw gateway stop` to this function. That turns a normal stop into persisted autostart suppression, so the suspend should live in the update lifecycle instead.
  - confidence: 0.91

  - body: The new `/ENABLE` in `restartScheduledTask()` runs for normal restarts too, even when this flow did not disable the task. That can re-enable an operator-disabled task; track update-scoped suspension state and restore only tasks this invocation disabled.
  - confidence: 0.88

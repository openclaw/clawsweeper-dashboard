## Summary

Keep open: the reported Windows update race is valid, but this PR is not the best fix because it changes generic Scheduled Task stop/restart semantics instead of limiting disable/enable to the update window. ## What This Changes

The branch adds `/DISABLE` in Windows `stopScheduledTask` and unconditional `/ENABLE` in `restartScheduledTask`.

## Best Possible Solution

Implement update-scoped suspension that disables only enabled Windows Scheduled Tasks during mutable package replacement, restores only tasks this invocation disabled, and leaves generic stop/restart semantics intact.

## Reproduction Assessment

Yes, source-reproducible. Current main stops the managed service before mutable update work and Windows Scheduled Task stop uses `/End` without disabling repeated legacy triggers; I did not run a native Windows update in this read-only review.

## Solution Assessment

No. This is a plausible mitigation, but it is broader than the bug because it changes generic stop/restart behavior instead of owning temporary suspension inside the update lifecycle.

  - body: The new `/DISABLE` call is inside `stopScheduledTask()`, and the Windows service registry routes ordinary gateway stop operations to this function. That turns a normal stop into persisted autostart suppression, so the suspend should live in the update lifecycle instead.

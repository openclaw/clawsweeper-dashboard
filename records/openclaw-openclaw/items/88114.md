## Summary

Keep open: the reported Windows update race is valid, but this PR changes generic Scheduled Task stop/restart semantics and still lacks real Windows after-fix proof; the narrower update-scoped fix is tracked in an open maintainer PR that is not yet mergeable enough to close this one as superseded.

## What This Changes

The PR adds a Windows `schtasks /Change /DISABLE` call after Scheduled Task stop and a matching `/ENABLE` call before Scheduled Task restart.

## Best Possible Solution

Land or replace the update-scoped suspend/resume design so only enabled Windows Scheduled Task autostart is disabled during mutable package replacement and only tasks this invocation disabled are restored.

## Reproduction Assessment

Yes, source-reproducible. Current main stops the managed service before mutable update work and `stopScheduledTask()` uses `/End` without disabling repeated triggers; I did not run a native Windows update in this read-only review.

## Solution Assessment

No. The proposed disable/enable calls are a plausible mitigation, but they are too broad because they change generic stop/restart behavior instead of owning temporary suspension inside the update lifecycle.

Full review comments:

- **[P1] Keep persistent disable out of generic stop:** `src/daemon/schtasks.ts:1335`
  - body: The new `/DISABLE` call is inside `stopScheduledTask()`, and the Windows service registry routes ordinary gateway stop operations to this function. That turns a normal stop into persisted autostart suppression, so the suspension needs to live in the update lifecycle instead.
  - confidence: 0.91
- **[P1] Restore only tasks this flow disabled:** `src/daemon/schtasks.ts:1358`
  - body: The new `/ENABLE` in `restartScheduledTask()` runs for normal restarts too, even when this flow did not disable the task. That can re-enable an operator-disabled task; track update-scoped suspension state and restore only tasks this invocation disabled.
  - confidence: 0.87

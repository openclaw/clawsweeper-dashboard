## Summary

Keep open: the Windows update race is still valid, but this branch is not merge-ready because it moves temporary autostart suspension into generic Scheduled Task stop/restart semantics and has no after-fix real Windows proof.

## What This Changes

The branch adds `schtasks /Change /DISABLE` after Windows Scheduled Task stop and `/ENABLE` before restart in `src/daemon/schtasks.ts`.

## Best Possible Solution

Use an update-scoped suspend/resume guard that disables only enabled Windows Scheduled Task autostart during mutable package replacement and restores only tasks this invocation disabled.

## Reproduction Assessment

Yes, source-reproducible: current main stops the managed service before mutable update work, and Windows Scheduled Task stop still uses `/End` without update-scoped disable. I did not run a native Windows update in this read-only review.

## Solution Assessment

No. This is a plausible mitigation, but it is broader than the bug because it changes generic stop/restart behavior instead of owning temporary suspension inside the update lifecycle.

- **[P1] Keep persistent disable out of generic stop:** `src/daemon/schtasks.ts:1334-1335`
  - body: The new `/DISABLE` call is inside `stopScheduledTask()`, and the Windows service registry routes ordinary gateway stop operations to this function. That turns a normal stop into durable autostart suppression, so the suspend should live in the update lifecycle instead.
  - confidence: 0.91
- **[P1] Restore only tasks this update suspended:** `src/daemon/schtasks.ts:1357-1358`
  - body: The new `/ENABLE` in `restartScheduledTask()` runs for normal restarts too, even when this flow did not disable the task. That can re-enable an operator-disabled task; track update-scoped suspension state and restore only tasks this invocation disabled.
  - confidence: 0.88

## Summary

Keep open, but this branch is not merge-ready: it addresses the real Windows update race in the wrong layer by changing generic Scheduled Task stop/restart semantics, while the canonical issue remains open and the better update-scoped PR has not merged.

## What This Changes

This PR adds `schtasks /Change /DISABLE` after Windows Scheduled Task stop and `/ENABLE` before Scheduled Task restart in `src/daemon/schtasks.ts`.

## Best Possible Solution

Land or replace the companion update-scoped design: suspend only enabled Windows Scheduled Task autostart during mutable package replacement, restore only tasks that invocation suspended, and prove the final Windows lifecycle.

## Reproduction Assessment

Yes, source-reproducible. Current main stops the managed service before update work and the Windows Scheduled Task stop implementation uses `/End` without update-scoped disable/re-enable handling; I did not run a native Windows update in this read-only review.

## Solution Assessment

No. The change is a plausible mitigation, but it is broader than the bug because it changes generic stop/restart behavior instead of owning temporary suspension inside the update lifecycle.

Full review comments:

- **[P1] Keep persistent disable out of generic stop:** `src/daemon/schtasks.ts:1334-1335`
  - body: The new `/DISABLE` call is inside `stopScheduledTask()`, and the Windows service registry routes ordinary `openclaw gateway stop` to this function. That turns a normal stop into persisted autostart suppression, so the suspend should live in the update lifecycle instead.
  - confidence: 0.91
- **[P1] Restore only tasks this flow disabled:** `src/daemon/schtasks.ts:1357-1358`
  - body: The new `/ENABLE` in `restartScheduledTask()` runs for normal restarts too, even when this flow did not disable the task. That can re-enable an operator-disabled task; track update-scoped suspension state and restore only tasks this invocation disabled.
  - confidence: 0.88

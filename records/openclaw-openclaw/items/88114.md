## Summary

Keep open: the reported Windows update race is valid, but this PR is not safe to merge as written because it changes generic Scheduled Task stop/restart semantics, lacks after-fix real Windows proof, and overlaps the still-open update-scoped candidate at https://github.com/openclaw/openclaw/pull/88292.

## What This Changes

The PR adds `/DISABLE` after Windows Scheduled Task `/End` and `/ENABLE` before Scheduled Task restart.

## Best Possible Solution

Use an update-scoped suspend/resume guard that disables only enabled Windows Scheduled Task autostart during package replacement and restores only tasks this invocation actually disabled.

## Reproduction Assessment

Yes, source-reproducible. Current main stops the managed Windows Scheduled Task with `/End` before mutable update replacement, while legacy repeated triggers can remain armed; I did not run a native Windows update in this read-only review.

## Solution Assessment

No. This is a plausible mitigation, but it is broader than the bug because it changes generic stop/restart behavior instead of owning temporary suspension inside the update lifecycle.

Overall correctness: patch is incorrect

Full review comments:

- **[P1] Keep persistent disable out of generic stop:** `src/daemon/schtasks.ts:1334-1335`
  - body: The new `/DISABLE` call is inside `stopScheduledTask()`, and the Windows service registry routes ordinary gateway stop operations to this function. That would turn a normal stop into persistent autostart suppression, so the suspend should live in the update lifecycle instead.
  - confidence: 0.91
- **[P1] Restore only tasks this flow disabled:** `src/daemon/schtasks.ts:1357-1358`
  - body: The new `/ENABLE` in `restartScheduledTask()` runs for normal restarts too, even when this flow did not disable the task. That can re-enable an operator-disabled task; track update-scoped suspension state and restore only tasks this invocation disabled.
  - confidence: 0.87

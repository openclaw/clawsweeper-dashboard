## Summary

Keep open for maintainer follow-up: current main and v2026.6.11 handle valid under-2 MB workspace-relative IDENTITY.md avatars and now expose machine-readable avatar failure reasons, but the remaining oversized-avatar/error-contract behavior touches authenticated local file serving and needs a product/security decision before cleanup closure.

## What This Changes

The issue reports broken webchat avatars from `/avatar/{agentId}` for workspace-relative `IDENTITY.md` avatar paths, with follow-up discussion narrowing part of the symptom to oversized local avatar files and unclear feedback.

## Best Possible Solution

Keep the secured local-avatar implementation, then have maintainers decide the public failure contract: either treat `?meta=1` plus Quick Settings diagnostics as sufficient and close the stale fork PR, or add a reviewed in-product diagnostic/HTTP-status path that does not leak local file details.

## Reproduction Assessment

Yes at source level for the remaining behavior: an oversized local avatar resolves to `none` with reason `too_large`, `?meta=1` returns `avatarUrl: null` plus that reason, and the direct image endpoint returns 404. I did not run a live Windows/browser reproduction; valid under-2 MB IDENTITY.md avatars are covered by current source and tests.

## Solution Assessment

No automatic code fix is best yet. Current main fixed the valid local-avatar path and added safer diagnostics, but choosing whether direct image failures should stay opaque or become more explicit is a security/product decision.

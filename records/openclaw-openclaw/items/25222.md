## Label Justifications

- `P2`: This is a normal-priority cross-channel session UX improvement with clear user impact but no outage, data loss emergency, or security boundary.
- `impact:session-state`: The issue is about how active session lock and queued follow-up state are surfaced to the user.
- `impact:message-loss`: A same-session message can be accepted into the queue while producing no immediate visible reply, making it appear lost until later processing.
- `impact:ux-friction`: Users can usually continue by waiting or starting a new session, but the missing busy/status reply creates avoidable confusion and support burden.

## Summary

Keep open: current main and the latest release still enqueue same-session active followups without a channel-visible scripted busy reply, cancel/new-session guidance, or stable busy reason payload; related work either closed into this issue or only added typing/status keepalive.

## What This Changes

The issue requests an immediate channel-visible busy acknowledgement, optional cancel/new-session actions, and busy reason/status handling when a message targets an already active session.

## Best Possible Solution

Settle a generic core busy-reply contract around queue policy, `runReplyAgent`, and dispatch, then implement it with channel-safe text/actions and tests that preserve existing steer, followup, collect, interrupt, `/stop`, and `/new` semantics.

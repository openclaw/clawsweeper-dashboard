## Label Justifications

- `P2`: This is a normal-priority cross-channel session UX improvement with clear source evidence but limited blast radius and no full setup blocker.
- `impact:session-state`: The request concerns active session locks, queued followups, busy reasons, and state visibility while a session run is in flight.
- `impact:message-loss`: The current silent enqueue path can make same-session user messages or status acknowledgements appear ignored or suppressed until later queue handling.
- `impact:ux-friction`: Users can proceed only by waiting, retrying, or guessing whether the bot is busy, stuck, or ignoring them.

## Summary

Keep open: current main and the latest release still enqueue active same-session followups without an immediate scripted busy/status reply, configurable cancel/new-session guidance, or stable busy reason payload, while the related implementation and duplicate work is closed rather than a viable replacement.

## What This Changes

Request a generic user-visible busy/status acknowledgement, optional cancel/new-session actions, and busy reason metadata when a channel message arrives while that session already has an active run.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, and dispatch, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused coverage for queue, runner, dispatch, and at least one channel path.

- **Channel-Local UX:** Keep core enqueue behavior unchanged and ask channel or plugin owners to implement local busy UX, accepting inconsistent behavior across channels.

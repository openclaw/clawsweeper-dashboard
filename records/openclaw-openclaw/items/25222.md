## Summary

Keep this issue open: current main still has the central UX gap because active same-session channel messages are steered or queued without returning a scripted busy/status reply, cancel/new-session guidance, or stable busy-reason payload.

## What This Changes

The issue requests an immediate channel-visible busy acknowledgement with optional wait/cancel/new-session actions when a user sends another message while the same session is already running.

## Best Possible Solution

Keep this issue as the canonical busy-session UX request and add a generic core contract for channel-safe busy text, optional non-destructive actions, stable busy metadata, and focused queue/dispatch/channel tests.

- **Opt-In Configurable Busy Ack:** Add busy acknowledgement only behind a new messages.queue option so existing deployments keep the current silent queue/typing behavior until operators enable it.
- **Typing-Only Status:** Keep the current typing/status-reaction approach and close the request only if maintainers decide visible busy text is too noisy for channel UX.

Yes. A source-level reproduction is clear: send a second same-session channel message while an active run is in followup/collect/steer fallback, and current main enqueues it then returns undefined, which dispatch turns into no scripted reply.

## Solution Assessment

Yes at the owner-boundary level, but the exact product shape still needs maintainer choice. The core reply queue/dispatch path is the right place because the behavior should be consistent across channels rather than patched per bridge.

## Label Justifications

- `P2`: This is a normal-priority cross-channel session UX improvement with clear source evidence but no emergency outage or full setup blocker.
- `impact:session-state`: The request concerns active session locks, queued followups, busy reasons, and state visibility while a session run is in flight.
- `impact:message-loss`: The silent enqueue path can make same-session user messages appear ignored or dropped until later queue handling.
- `impact:ux-friction`: Users can proceed only by waiting, retrying, or guessing whether the bot is busy, stuck, or ignoring them.

## Summary

Keep open: current main and v2026.6.11 still enqueue same-session followups without returning an immediate channel-visible busy acknowledgement, cancel/new-session guidance, or stable busy reason payload. The remaining gap is real, but the default behavior, config shape, and portable action semantics need maintainer product direction before implementation.

## What This Changes

The issue requests a generic session-busy reply, optional cancel/new-session actions, heartbeat/status behavior, and busy reason metadata when a message arrives while the same session is already running.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, dispatch, and channel presentation, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused queue/runner/dispatch/channel coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic busy-session acknowledgement by default, make it opt-in/configurable, and which portable cancel/new-session actions and busy reason fields should be part of that contract?

Rationale: The source gap is clear, but adding user-visible status text, configuration, and cross-channel actions changes UX and compatibility expectations across messaging surfaces.

Likely owner: steipete

Owner reason: Peter has the strongest history on the queue policy and queued-followup behavior this decision would change.

Owner confidence: high

Options:

- **Generic Conservative Default (recommended):** Add a short default busy acknowledgement with no destructive action by default, and expose typed optional cancel/new-session actions only where channels can render them safely.
- **Opt-In Configurable Acknowledgement:** Add the same core contract behind explicit messages.queue configuration so existing deployments preserve silent enqueue behavior unless operators enable it.
- **Defer To Local Surfaces:** Keep core enqueue behavior unchanged and let individual channels or clients implement busy UX, accepting inconsistent behavior across surfaces.

## Reproduction Assessment

Yes, at source level: active same-session followups resolve to enqueue-followup, runReplyAgent returns undefined, and dispatch converts undefined into no immediate channel-visible replies. I did not run a live chat reproduction in this read-only review.

## Solution Assessment

Mostly yes for the requested layer: this belongs in a generic core/channel busy-status contract rather than a Telegram-only bridge patch. The exact default, config, action, and reason-metadata contract remains a maintainer product decision.

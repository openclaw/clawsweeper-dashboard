## Label Justifications

- `P2`: This is a normal-priority cross-channel UX/session improvement with clear source evidence but no setup blocker, security emergency, or outage severity.
- `impact:session-state`: The request concerns active session locks, queued followups, busy reasons, and state visibility while a session run is in flight.
- `impact:message-loss`: The silent enqueue/steer path can make same-session user messages appear ignored or dropped until later queue handling.
- `impact:ux-friction`: Users can proceed only by waiting, retrying, or guessing whether the bot is busy, stuck, or ignoring them.

## Summary

Keep open: current main still steers or enqueues same-session busy messages without the requested immediate scripted busy acknowledgement, cancel/new-session guidance, or stable busy reason contract, and the remaining behavior needs maintainer product direction rather than cleanup closure.

## What This Changes

The issue requests an immediate channel-visible busy acknowledgement, optional cancel/new-session actions, heartbeat/status behavior, and stable busy reason metadata when a message arrives for a locked long-running session.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, dispatch, and channel presentation, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused queue/runner/dispatch/channel coverage.

## Maintainer Decision

Rationale: The source gap is clear, but adding visible status text, configuration, and cross-channel actions changes product UX and compatibility expectations across messaging surfaces.

Likely owner: steipete

Owner reason: The strongest current-main and feature-history signal for the shared queue/reply path points to steipete.

Owner confidence: high

Options:

- **Generic Conservative Default (recommended):** Add a short default busy acknowledgement with no destructive action by default, and expose typed optional cancel/new-session actions only where channels can render them safely.
- **Opt-In Configurable Acknowledgement:** Add the same core contract behind explicit messages.queue configuration so existing deployments preserve silent enqueue behavior unless operators enable it.
- **Defer To Channels:** Keep core enqueue behavior unchanged and let channel or plugin owners implement local busy UX, accepting inconsistent behavior across channels.

Yes, at source level: active same-session followups resolve to enqueue-followup or accepted steering, runReplyAgent returns undefined, and dispatch converts undefined into no channel-visible final reply. I did not run a live chat reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the UX and config contract. The maintainable direction is a generic core/channel busy-status contract, not a Telegram-only bridge patch or another isolated delivery workaround.

## Summary

Keep open: current main still lacks the requested immediate scripted busy/status reply, cancel/new-session guidance, and stable busy reason payload for same-session messages queued behind an active run. Existing current-main work partially improves typing/status cues, but the central cross-channel busy acknowledgement contract is still a product decision rather than an implemented behavior.

## What This Changes

Request an immediate channel-safe busy reply, optional cancel/new-session actions, ongoing status feedback, and busy reason metadata when a message arrives for an already locked session.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, and dispatch, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused coverage for queue, runner, dispatch, and one channel path.

## Maintainer Decision

Question: Should OpenClaw add a generic busy-session acknowledgement by default or behind configuration, and which portable cancel/new-session actions and busy reason fields should be part of that contract?

Rationale: The source gap is clear, but adding user-visible status text, configuration, and cross-channel actions changes product UX and compatibility expectations across messaging surfaces.

Likely owner: steipete

Owner reason: He has the strongest current history on the queue policy and queued-followup behavior that this decision would change.

Owner confidence: high

Options:

- **Generic conservative default (recommended):** Add a short default busy acknowledgement with no destructive action by default, and expose typed optional cancel/new-session actions only where channels can render them safely.
- **Opt-in configurable acknowledgement:** Add the same core contract behind explicit messages.queue configuration so existing deployments preserve silent enqueue behavior unless operators enable it.
- **Defer to channel plugins:** Keep core enqueue behavior unchanged and ask channel/plugin owners to implement local busy UX, accepting inconsistent behavior across channels.

Yes at source level: active same-session followups resolve to enqueue-followup, runReplyAgent returns undefined, and dispatch converts undefined into no channel-visible replies. I did not run a live chat reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the UX and config contract. The maintainable direction is a generic core/channel busy-status contract, not a Telegram-only bridge patch or another isolated delivery workaround.

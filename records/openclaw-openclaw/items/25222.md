## Summary

Keep open: current main and the latest release still queue busy same-session messages without the requested scripted busy reply, cancel/new-session guidance, or stable busy reason metadata. The source gap is clear, but the UX/default/config contract needs maintainer product direction before implementation.

## What This Changes

The issue requests a cross-channel busy-session acknowledgement with optional cancel/new-session actions and busy reason metadata when a user messages a locked session during a long-running response.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, dispatch, and channel presentation, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused queue/runner/dispatch/channel coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic busy-session acknowledgement by default or behind configuration, and which portable cancel/new-session actions plus busy reason fields belong in that contract?

Rationale: The source gap is clear, but visible status text, new configuration, and cross-channel action semantics change product UX and compatibility expectations across messaging surfaces.

Likely owner: steipete

Owner reason: The strongest history signal for queue policy and queued-followup behavior points to steipete, and the decision changes that shared reply path.

Owner confidence: high

Options:

- **Conservative Default (recommended):** Add a short default busy acknowledgement with no destructive action by default, and expose typed optional cancel/new-session actions only where channels can render them safely.
- **Opt-In Configuration:** Add the same core contract behind explicit messages.queue configuration so existing deployments preserve silent enqueue behavior unless operators enable it.
- **Channel-Local UX:** Keep core enqueue behavior unchanged and let channel/plugin owners implement local busy UX, accepting inconsistent behavior across channels.

## Reproduction Assessment

Yes, at source level: current main routes active same-session followups to enqueue-followup, returns undefined after enqueue, and dispatch maps that to no final channel reply. I did not run a live chat reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the UX and config contract. The maintainable direction is a generic core/channel busy-status contract, not a Telegram-only bridge patch or another isolated delivery workaround.

## Label Justifications

- `P2`: This is a normal-priority cross-channel UX/session improvement with clear source evidence but no setup blocker, security emergency, or outage severity.
- `impact:session-state`: The request concerns active session locks, queued followups, busy reasons, and state visibility while a session run is in flight.
- `impact:message-loss`: The silent enqueue path can make same-session user messages appear ignored or dropped until later queue handling.
- `impact:ux-friction`: Users can proceed only by waiting, retrying, or guessing whether the bot is busy, stuck, or ignoring them.

## Summary

Keep open: current main and the latest release still lack the requested channel-visible busy reply, cancel/new-session guidance, and stable busy reason payload for active same-session messages. Existing queue modes, status reactions, typing signals, `/stop`, and `/new` cover adjacent pieces, but they do not give the sender an immediate scripted acknowledgement on the enqueue-followup path.

## What This Changes

Request an immediate channel-safe busy/session status reply with optional cancel/new-session actions when a message arrives while the same session already has an active long-running run.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, dispatch, and channel presentation, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused coverage.

- **Channel-local UX only:** Keep core enqueue behavior unchanged and let channel/plugin owners implement local busy UX, accepting inconsistent behavior across channels.

## Label Justifications

- `P2`: This is a normal-priority cross-channel UX/session improvement with clear source evidence but no full setup blocker or emergency severity.

## Summary

Keep open: current main and the latest release still provide a queued-followup typing cue, but not the requested immediate scripted busy/status reply with cancel/new-session guidance or stable busy reason metadata. The remaining work is real and belongs in core, but it needs a maintainer product decision before implementation.

## What This Changes

Requests an immediate channel-visible busy/status acknowledgement, optional cancel/new-session actions, and busy reason metadata when a message arrives for a locked long-running session.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, dispatch, and channel presentation, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused queue/runner/dispatch/channel coverage.

## Maintainer Decision

Rationale: The source gap is clear, but adding user-visible status text, configuration, and cross-channel actions changes product UX and compatibility expectations across messaging surfaces.

Likely owner: steipete

Owner confidence: high

Options:

- **Generic Conservative Default (recommended):** Add a short default busy acknowledgement with no destructive action by default, and expose typed optional cancel/new-session actions only where channels can render them safely.
- **Opt-In Configurable Acknowledgement:** Add the same core contract behind explicit messages.queue configuration so existing deployments preserve silent enqueue behavior unless operators enable it.
- **Defer To Channels:** Keep core enqueue behavior unchanged and ask channel/plugin owners to implement local busy UX, accepting inconsistent behavior across channels.

## Label Justifications

- `P2`: This is a normal-priority cross-channel UX/session-state improvement for long-running turns with clear source evidence and bounded blast radius.
- `impact:session-state`: The request concerns active session locks, queued follow-ups, busy reasons, and clear state while a session run is in flight.
- `impact:message-loss`: The silent enqueue path can make same-session user messages appear ignored or dropped until a later queue drain.
- `impact:ux-friction`: The current behavior leaves users guessing whether the bot is waiting, stuck, retrying, or ignoring them during long-running responses.

## Summary

Keep open: current main and the latest release still enqueue active same-session follow-ups without an immediate channel-visible busy/status reply, cancel/new-session guidance, or stable busy-reason payload. The request remains a product/design item rather than a closeable implemented behavior.

## What This Changes

The issue requests a generic session-busy status reply with optional wait/cancel/new actions and busy-reason metadata when another message arrives during an active same-session response.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runner return payloads, and dispatch, with channel-safe text/actions, stable reason metadata, and focused coverage that proves queued follow-ups still drain after the active run.

## Reproduction Assessment

Yes, at source level: active same-session follow-ups resolve to `enqueue-followup`, `runReplyAgent` returns `undefined`, and dispatch converts that to no channel-visible replies. I did not run a live chat reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the UX and config contract. The maintainable direction is a generic cross-channel busy/status contract, not a Telegram-only bridge patch or another isolated delivery workaround.

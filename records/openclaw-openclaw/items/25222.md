- `P2`: This is a normal-priority cross-channel UX/session improvement with clear source evidence but no full setup blocker, security issue, or crash-loop severity.
- `impact:session-state`: The request concerns active session locks, queued followups, busy reasons, and state visibility while a session run is in flight.
- `impact:message-loss`: The silent enqueue path can make same-session user messages appear ignored or dropped until later queue handling.
- `impact:ux-friction`: Users can proceed only by waiting, retrying, or guessing whether the bot is busy, stuck, or ignoring them.

## Summary

Keep open: current main and the latest release still enqueue active same-session followups without an immediate busy/status reply, cancel/new-session guidance, or stable busy-reason payload. The remaining work is canonical, but it needs maintainer product direction before implementation.

## What This Changes

Request a channel-visible busy/status acknowledgement, optional cancel/new-session actions, typing continuity, and busy-reason metadata when a same-session message arrives during an active long-running run.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, dispatch, and channel presentation, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused queue/runner/dispatch/channel coverage.

## Maintainer Decision

Question: Should OpenClaw add a generic busy-session acknowledgement by default, make it opt-in/configurable, and which portable cancel/new-session actions and busy reason fields should be part of the contract?

Rationale: The source gap is clear, but adding user-visible status text, configuration, and cross-channel actions changes product UX and compatibility expectations across messaging surfaces.

Likely owner: steipete

Owner confidence: high

Options:

- **Conservative Default (recommended):** Add a short default busy acknowledgement with no destructive action by default, and expose typed optional cancel/new-session actions only where channels can render them safely.
- **Opt-In Configuration:** Add the same core contract behind explicit messages.queue configuration so existing deployments preserve silent enqueue behavior unless operators enable it.
- **Defer To Channels:** Keep core enqueue behavior unchanged and ask channel/plugin owners to implement local busy UX, accepting inconsistent behavior across channels.

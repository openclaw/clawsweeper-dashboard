## Label Justifications

- `P2`: This is a normal-priority cross-channel UX/session improvement for long-running turns with clear source evidence and bounded blast radius.
- `impact:session-state`: The request concerns active session locks, queued followups, busy reasons, and clear state while a session run is in flight.
- `impact:message-loss`: The silent enqueue path can make same-session user messages appear ignored or dropped until later queue handling.
- `impact:ux-friction`: Users can continue by waiting, retrying, or starting a new session, but the current silent busy state creates avoidable confusion and support burden.

## Summary

Keep open: current main and the latest release still enqueue active same-session followups without an immediate scripted busy/cancel reply, and the closed related items do not supersede this canonical UX request.

## What This Changes

The issue requests a fast channel-visible session-busy/status reply, optional cancel/new-session actions, and clearer busy reason metadata when a user sends another message to an already locked long-running session.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runner return payloads, and dispatch, with channel-safe text/actions, stable reason metadata, and focused queue/runner/dispatch/channel coverage.

## Reproduction Assessment

Yes, at source level: active same-session followups resolve to enqueue-followup, runReplyAgent returns undefined, and dispatch converts that to no channel-visible replies. I did not run a live chat reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the UX and config contract. The maintainable direction is a generic cross-channel busy/status contract, not a Telegram-only bridge patch or another isolated delivery workaround.

## Label Justifications

- `P2`: The issue is a normal-priority user-facing improvement to long-running session queue behavior, not an emergency outage.
- `impact:session-state`: The request concerns active session lock/queue state and how users perceive a locked session during long-running work.
- `impact:message-loss`: The reported UX makes queued or ignored channel messages look dropped even when the session may still be processing.
- `impact:ux-friction`: Users can continue but lack a clear in-channel explanation or low-friction recovery action during long model waits.

## Summary

Keep open: current main and v2026.6.11 still enqueue active-session followups without a scripted channel reply; typing/recovery improvements are adjacent, not the requested busy acknowledgement or cancel/new-session guidance.

## What This Changes

The issue requests an immediate channel-visible busy/status acknowledgement with cancel or new-session guidance when a user messages a locked long-running session.

## Best Possible Solution

Define one generic active-session busy acknowledgement contract in the shared queue/dispatch path, with conservative default text, stable reason metadata, optional typed actions, and tests proving the queued followup still drains exactly once.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What busy-acknowledgement contract should OpenClaw expose for messages that arrive while the target session already has an active run?

Rationale: The source gap is clear, but default-on behavior, config shape, reason vocabulary, and portable cancel/new-session actions affect channel UX and compatibility, so automation should not choose the policy alone.

Likely owner: steipete

Owner reason: The active-run queue policy, queued-followup typing behavior, and prior canonical issue review all route through this owner signal.

Owner confidence: high

Options:

- **Generic default with conservative actions (recommended):** Add a shared default busy reply with non-destructive wait guidance, stable reason metadata, and typed optional stop/new actions only where the channel safely supports them.
- **Config-gated busy acknowledgements:** Add disabled-by-default or per-channel busy-ack config first, accepting slower adoption to avoid changing existing channel noise and notification behavior.
- **Defer to durable status surface:** Keep this issue blocked behind the broader persistent channel-turn status design, avoiding a smaller interim busy reply contract.

## Reproduction Assessment

Yes at source level: active same-session followups enter enqueue-followup, the runner returns undefined, and dispatch converts that to no channel reply. I did not run a live channel repro in this read-only cleanup review.

## Solution Assessment

No automated fix should be queued yet; the source gap is clear, but the best solution needs maintainer direction for default text, config shape, reason metadata, and portable cancel/new-session semantics.

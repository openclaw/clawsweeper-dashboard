## Summary

Keep open: current main and v2026.6.11 still lack the requested scripted busy reply, cancel/new-session guidance, and stable busy reason payload; existing typing/status behavior only covers part of the user confusion.

## What This Changes

Issue requests a channel-visible busy/session-occupied reply with wait/cancel/new-session guidance and stable busy reason metadata for messages queued behind an active session run.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, dispatch, and channel presentation, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic busy-session acknowledgement by default, make it opt-in/configurable, and which portable cancel/new-session actions plus busy reason fields should be part of that contract?

Rationale: The source gap is clear, but visible status text, configuration/defaults, and cross-channel cancel/new actions change product UX and compatibility expectations across messaging surfaces.

Likely owner: steipete

Owner reason: The strongest history signal for queue policy and queued-followup behavior points to steipete, and this decision would change that shared reply path.

Owner confidence: high

Options:

- **Conservative default acknowledgement (recommended):** Add a short default busy acknowledgement with no destructive action by default, and expose typed optional cancel/new-session actions only where channels can render them safely.
- **Opt-in queue configuration:** Add the same core contract behind explicit messages.queue configuration so existing deployments preserve silent enqueue behavior unless operators enable it.
- **Channel-local UX only:** Keep core enqueue behavior unchanged and let channel/plugin owners implement local busy UX, accepting inconsistent behavior across channels.

## Reproduction Assessment

Yes, at source level: active same-session followups can resolve to enqueue-followup, runReplyAgent returns undefined after enqueue, and dispatch maps that to no final channel reply.

## Solution Assessment

Unclear until maintainers choose the UX and config contract; the maintainable direction is a generic core/channel busy-status contract rather than a Telegram-only bridge patch or isolated delivery workaround.

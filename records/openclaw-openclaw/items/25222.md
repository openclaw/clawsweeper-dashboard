- `P2`: This is a normal-priority cross-channel UX/session improvement with clear source evidence but no release-blocking setup, crash, security, or data-loss emergency.
- `impact:session-state`: The request concerns active session locks, queued followups, busy reasons, and state visibility while a session run is in flight.
- `impact:message-loss`: The silent enqueue path can make same-session user messages appear ignored or dropped until later queue handling.

## Summary

Keep open: current main still queues or steers same-session busy messages without the requested immediate scripted busy/status reply, cancel/new-session guidance, or stable busy reason metadata. The gap is source-reproducible, but the default UX, config shape, and portable action contract need maintainer product direction before implementation.

## What This Changes

Add an immediate channel-visible busy/status acknowledgement with optional wait, cancel, and new-session guidance when a message arrives for a session with an active long-running run.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, dispatch, and channel presentation, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused queue/runner/dispatch/channel coverage.

Options:

- **Generic Conservative Default (recommended):** Add a short default busy acknowledgement with no destructive action by default, and expose typed optional cancel/new-session actions only where channels can render them safely.
- **Opt-In Configurable Acknowledgement:** Add the same core contract behind explicit messages.queue configuration so existing deployments preserve silent enqueue behavior unless operators enable it.
- **Defer To Channels:** Keep core enqueue behavior unchanged and ask channel or plugin owners to implement local busy UX, accepting inconsistent behavior across channels.

## Reproduction Assessment

Yes, at source level. Active same-session followups resolve to enqueue-followup, runReplyAgent returns undefined, and dispatch converts undefined into no channel-visible final reply; I did not run a live chat reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the UX and config contract. The maintainable direction is a generic core/channel busy-status contract, not a Telegram-only bridge patch or another isolated delivery workaround.

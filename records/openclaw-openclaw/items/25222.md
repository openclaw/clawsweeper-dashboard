## Label Justifications

- `P2`: This is a normal-priority cross-channel UX/session improvement with clear source evidence but limited blast radius and no full setup blocker.
- `impact:session-state`: The request concerns active session locks, queued followups, busy reasons, and state visibility while a session run is in flight.
- `impact:message-loss`: The current silent enqueue path can make same-session user messages appear ignored or dropped until later queue handling.
- `impact:ux-friction`: Users can proceed only by waiting, retrying, or guessing whether the bot is busy, stuck, or ignoring them.

## Summary

Keep open: current main still queues active same-session followups without an immediate scripted busy/status reply, cancel/new-session guidance, or stable busy reason payload, and no merged/open replacement owns this exact UX contract.

## What This Changes

Request an immediate channel-visible busy/session status reply, optional cancel/new-session actions, and busy reason metadata when a message arrives during an active session run.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, and dispatch, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused coverage for queue, runner, dispatch, and at least one channel path.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic busy-session acknowledgement by default, make it opt-in/configurable, and which portable cancel/new-session actions and busy reason fields should be part of the contract?

Rationale: The source gap is clear, but adding user-visible status text, configuration, and cross-channel actions changes product UX and compatibility expectations across messaging surfaces.

Likely owner: steipete

Owner reason: Peter has the strongest history on the queue policy and queued-followup behavior that this product decision would change.

Owner confidence: high

Options:

- **Generic Conservative Default (recommended):** Add a short default busy acknowledgement with no destructive action by default, and expose typed optional cancel/new-session actions only where channels can render them safely.
- **Opt-In Configurable Acknowledgement:** Add the same core contract behind explicit messages.queue configuration so existing deployments preserve silent enqueue behavior unless operators enable it.
- **Defer To Channels:** Keep core enqueue behavior unchanged and ask channel/plugin owners to implement local busy UX, accepting inconsistent behavior across channels.

## Solution Assessment

Unclear until maintainers choose the UX and config contract. The maintainable direction is a generic core/channel busy-status contract, not a Telegram-only bridge patch or another isolated delivery workaround.

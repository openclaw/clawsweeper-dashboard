## Label Justifications

- `P2`: This is a normal-priority cross-channel UX/session improvement with clear source evidence but no setup blocker, security emergency, or outage severity.
- `impact:session-state`: The request concerns active session locks, queued followups, busy reasons, and state visibility while a session run is in flight.
- `impact:message-loss`: The silent enqueue path can make same-session user messages appear ignored or dropped until later queue handling.
- `impact:ux-friction`: Users can proceed only by waiting, retrying, or guessing whether the bot is busy, stuck, or ignoring them.

## Summary

Keep open: current main still has only steer/followup/collect/interrupt queue behavior plus typing/status cues, not the requested immediate scripted busy reply with portable cancel/new-session guidance and stable busy reason metadata.

## What This Changes

The issue requests a cross-channel busy-session acknowledgement when a message arrives while the same session is locked by a long-running model/tool turn.

## Best Possible Solution

Add one generic active-session busy/status contract across queue policy, runReplyAgent, dispatch, and channel presentation, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused regression coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic busy-session acknowledgement by default, make it opt-in/configurable, and which portable cancel/new-session actions plus busy reason fields should be part of that contract?

Rationale: The source gap is clear, but visible status text, configuration/defaults, and cross-channel cancel/new actions change product UX and compatibility expectations across messaging surfaces.

Likely owner: steipete

Owner reason: The strongest history signal for queue policy and queued-followup behavior points to steipete, and this decision would change that shared reply path.

Owner confidence: high

Options:

- **Conservative Default Acknowledgement (recommended):** Add a short default busy acknowledgement with no destructive action by default, and expose typed optional cancel/new-session actions only where channels can render them safely.
- **Opt-In Queue Configuration:** Add the same core contract behind explicit messages.queue configuration so existing deployments preserve silent enqueue behavior unless operators enable it.
- **Channel-Local UX Only:** Keep core enqueue behavior unchanged and let channel/plugin owners implement local busy UX, accepting inconsistent behavior across channels.

## Reproduction Assessment

Yes, at source level: active same-session followups can resolve to enqueue-followup, runReplyAgent returns undefined after enqueue, and dispatch maps that to no final channel reply. I did not run a live slow-model Telegram/webchat scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the UX and config contract; the maintainable direction is a generic core/channel busy-status contract rather than a Telegram-only bridge patch or isolated delivery workaround.

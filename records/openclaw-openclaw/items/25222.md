## Label Justifications

- `P2`: This is a normal-priority cross-channel UX/session improvement with clear source evidence but no setup blocker, security emergency, or outage severity.
- `impact:session-state`: The request concerns active session locks, queued followups, busy reasons, and state visibility while a session run is in flight.
- `impact:message-loss`: The silent enqueue path can make same-session user messages appear ignored or dropped until later queue handling.
- `impact:ux-friction`: Users can proceed only by waiting, retrying, or guessing whether the bot is busy, stuck, or ignoring them.

## Summary

Keep open: current main and v2026.6.11 still lack the requested scripted busy reply, cancel/new-session guidance, and stable busy reason payload. Existing queue typing/status cues cover part of the UX, but the remaining behavior needs a maintainer product/config decision before implementation.

## What This Changes

Add an immediate channel-visible busy/status reply with optional cancel/new-session actions and busy reason metadata when a user messages a locked session.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, dispatch, and channel presentation, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused queue/runner/dispatch/channel coverage.

Rationale: The source gap is clear, but visible status text, configuration/defaults, and cross-channel cancel/new actions change product UX and compatibility expectations across messaging surfaces.

Options:

- **Conservative Default (recommended):** Add a short default busy acknowledgement with no destructive action by default, and expose typed optional cancel/new-session actions only where channels can render them safely.
- **Opt-In Configuration:** Add the same core contract behind explicit messages.queue configuration so existing deployments preserve silent enqueue behavior unless operators enable it.
- **Channel-Local UX:** Keep core enqueue behavior unchanged and let channel/plugin owners implement local busy UX, accepting inconsistent behavior across channels.

Yes, at source level: active same-session followups can resolve to enqueue-followup, runReplyAgent returns undefined after enqueue, and dispatch maps that to no final channel reply. I did not run a live chat reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the UX and config contract. The maintainable direction is a generic core/channel busy-status contract rather than a Telegram-only bridge patch or another isolated delivery workaround.

## Summary

Keep open: current main and v2026.6.11 still enqueue active same-session followups without an immediate scripted busy/status reply, cancel/new-session guidance, or stable busy reason payload; related items are duplicate, closed unmerged, or adjacent rather than a shipped replacement.

## What This Changes

The issue requests a user-visible busy acknowledgement, optional cancel/new-session actions, typing heartbeat, and busy reason metadata when a same-session message arrives during an active long-running response.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, dispatch, and channel presentation, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused queue/runner/dispatch/channel coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic busy-session acknowledgement by default, make it opt-in/configurable, and which portable cancel/new-session actions and busy reason fields should be part of the contract?

Rationale: The source gap is clear, but user-visible status text, configuration, and cross-channel actions change product UX and compatibility expectations across messaging surfaces.

Likely owner: steipete

Owner reason: Peter has the strongest history on queue policy and queued-followup behavior that this product decision would change.

Owner confidence: high

Options:

- **Generic Conservative Default (recommended):** Add a short default busy acknowledgement with no destructive action by default, and expose typed optional cancel/new-session actions only where channels can render them safely.
- **Opt-In Configurable Acknowledgement:** Add the same core contract behind explicit messages.queue configuration so existing deployments preserve silent enqueue behavior unless operators enable it.
- **Defer To Channels:** Keep core enqueue behavior unchanged and ask channel/plugin owners to implement local busy UX, accepting inconsistent behavior across channels.

## Reproduction Assessment

Yes at source level: active same-session followups resolve to enqueue-followup, runReplyAgent returns undefined, and dispatch converts undefined into no channel-visible replies. I did not run a live chat reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the UX and config contract. The maintainable direction is a generic core/channel busy-status contract, not a Telegram-only bridge patch or another isolated delivery workaround.

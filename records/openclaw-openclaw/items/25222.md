## Summary

Keep open: current main still queues or steers same-session busy turns without the requested immediate scripted busy reply, cancel/new-session guidance, or stable busy reason payload, and the related implementation PR is closed unmerged.

## What This Changes

Add a generic busy-session status reply with optional wait/cancel/new-session actions when a user sends another message to a locked long-running session.

## Best Possible Solution

Implement one generic active-session busy/status contract across queue policy, runReplyAgent, dispatch, and channel presentation, with conservative channel-safe text, typed optional actions, stable reason metadata, and focused queue/runner/dispatch/channel coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic busy-session acknowledgement by default, make it opt-in/configurable, and which portable cancel/new-session actions plus busy reason fields belong in that contract?

Rationale: The missing source path is clear, but visible status text, configuration/defaults, and cross-channel cancel/new actions change product UX and compatibility expectations across messaging surfaces.

Likely owner: steipete

Owner reason: The strongest feature-history signal for queue policy and queued-followup behavior points to steipete, and this decision changes that shared reply path.

Owner confidence: high

Options:

- **Conservative shared default (recommended):** Add a short default busy acknowledgement with no destructive action by default, and expose typed optional cancel/new-session actions only where channels can render them safely.
- **Opt-in queue configuration:** Add the same core contract behind explicit messages.queue configuration so existing deployments preserve silent enqueue behavior unless operators enable it.
- **Channel-local UX only:** Keep core enqueue behavior unchanged and let channel/plugin owners implement local busy UX, accepting inconsistent behavior across channels.

## Reproduction Assessment

Yes, at source level: active same-session followups can resolve to enqueue-followup, runReplyAgent returns undefined after enqueue, and dispatch maps that to no final channel reply. I did not run a live chat reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the UX and config contract. The maintainable direction is a generic core/channel busy-status contract rather than a Telegram-only bridge patch or another isolated delivery workaround.

The issue requests billing-error cooldown/backoff for providers configured only with inline API keys in `models.providers`.

## Best Possible Solution

Review, rebase, or rebuild https://github.com/openclaw/openclaw/pull/88709 as the provider-level inline-key cooldown fix, preserving healthy stored-profile fallback and clear recovery behavior.

Rationale: The source-level bug is clear, but the fix changes existing inline-key auth-provider behavior and persistence semantics, which repository policy treats as compatibility-sensitive.

Likely owner: steipete

Owner confidence: high

Options:

- **Accept Provider-Level Cooldown (recommended):** Land or rebuild the linked fix so inline keys get billing/auth cooldown protection while healthy stored profiles remain usable fallback credentials.
- **Keep Profile-Only Cooldowns:** Document auth profiles as the supported cooldown boundary and keep inline keys outside cooldown tracking.
- **Request Narrower Design:** Pause the linked PR until maintainers define the exact inline credential identity, persistence, and recovery behavior.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: configure an inline `models.providers.<id>.apiKey`, trigger a billing/auth failure, and current main resolves the key without `profileId` while the runner failure marker returns when no profile id is present.

## Solution Assessment

Yes for the repair boundary, but not yet as a close condition. Provider-level inline-key cooldown state is the maintainable fix because profile cooldowns cannot cover credentials that intentionally have no profile, and the linked PR remains unmerged.

## Summary

Keep open for explicit maintainer product direction. This is a distinct, compatibility-sensitive Plugin SDK/channel contract: approval decision routing is already discussed separately, but external ownership of the user-facing approval presentation remains a new core boundary with real risks of duplicated or absent prompts.

## What This Changes

Add a generic approval capability through which a trusted channel or host can declare that an external runtime renders the approval UI while OpenClaw continues to authorize and resolve the approval.

## System Context

OpenClaw’s approval flow receives a tool or plugin approval request, determines whether the initiating channel can present it, and emits a structured pending result plus any native channel prompt. The proposed capability would alter only the presentation decision for trusted external hosts, while preserving pending state, authorization, and approval resolution.

## Architecture Diagram

flowchart LR
  A[Tool or plugin approval request] --> B[Approval routing]
  B --> C[Channel or host capability]
  C --> D{Presentation owner}
  D -->|Native channel| E[In-chat approval prompt]
  D -->|Trusted external runtime| F[External approval card or dialog]
  E --> G[Authorized approval decision]
  F --> G
  G --> H[Approval resolution and tool continuation]

## Best Possible Solution

Define one typed, opt-in presentation-ownership state at the existing approval capability boundary; preserve the current native path by default, retain structured pending events, and require contract plus authenticated end-to-end proof before accepting any external renderer.

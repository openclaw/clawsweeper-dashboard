## Label Justifications

- `P2`: The missing identity context creates a normal-priority approval-safety and usability gap for operators using concurrent sessions, without making the core runtime unusable.
- `impact:security`: The issue concerns whether an operator has enough trustworthy requester identity to make a sensitive exec-approval decision.
- `impact:session-state`: The popup cannot distinguish which active session originated the pending command.
- `impact:ux-friction`: Operators must infer the requester from command text or other indirect details when several sessions are active.

## Summary

Keep open. Current main still carries session identity into the native approval request without displaying it, while the related open PR expressly excludes the macOS popup and the prior maintainer-facing review leaves requester disclosure policy unresolved. citeturn3search6turn3search2

## What This Changes

Show session identity and safe requester context in the macOS exec-approval popup so operators can distinguish concurrent approval requests.

## Best Possible Solution

Define a sanitized approval-context display model that keeps routing identifiers internal, shows a concise session label plus optional channel/sender/thread details, omits unavailable values, and has focused decoding, redaction, truncation, and native prompt coverage.

## Maintainer Decision

Rationale: The code can mechanically render the existing field, but session keys and turn-source metadata may expose user, account, or conversation identifiers; repository behavior does not define the native popup's disclosure and redaction contract.

Owner confidence: medium

Options:

- **Sanitized Context (recommended):** Introduce display-safe session, channel, sender, and thread labels with explicit omission, redaction, and truncation rules while retaining raw identifiers only for routing.
- **Session Key Only:** Render the existing non-empty session key for parity with other approval surfaces and defer richer requester fields.
- **Keep Current Popup:** Leave requester identity out of the native popup and rely on command, agent, host, and other existing details.

## Reproduction Assessment

No live macOS popup reproduction was established, but the gap is source-reproducible with high confidence: the request carries `sessionKey` and the presenter does not render it or any turn-source fields.

## Solution Assessment

No, directly displaying raw session and requester identifiers is not yet the best complete solution. The maintainable path is a display-safe context contract with explicit privacy, omission, redaction, and truncation behavior.

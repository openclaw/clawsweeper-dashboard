## Summary

Keep this issue open. The linked approval-prompt PR explicitly improves channel-delivered prompts and excludes the macOS native popup, so it does not resolve this request; the minimal session row is a bounded parity improvement, while disclosing channel/sender context needs a maintainer-approved privacy and presentation contract.

## What This Changes

Show the originating session and, where safe, requester context in the macOS native exec-approval dialog so operators can distinguish concurrent approval requests.

## System Context

Exec approvals originate from gateway or node execution requests and are shown to an operator before a command can proceed. The macOS companion app decodes that request and presents a native approval dialog, while channel and web approval surfaces render related context separately.

## Architecture Diagram

flowchart LR
  A[Gateway or node exec request] --> B[Approval request payload]
  B --> C[macOS companion app]
  C --> D[Native approval dialog]
  B --> E[Web and channel prompts]
  D --> F[Operator approval decision]
  E --> F
  F --> G[Allow or deny command]

## Best Possible Solution

Add a non-empty Session row to the macOS approval accessory view for parity, then carry and display only a maintainer-approved, redacted requester-context subset with focused native-dialog coverage.

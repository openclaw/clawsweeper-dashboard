## Summary

Keep open: the linked security bug remains valid, but the current head still checks ownership on a pre-write snapshot rather than inside the authoritative persistence mutation, and it retains an unrelated doctor-health change. The supplied evidence is test-harness-only.

Likely related people: @Pick-cat is connected to the current accessor implementation with medium confidence; @steipete is a co-author and frequent contributor across the central session files with high confidence.

## What This Changes

The PR attempts to restrict `sessions.patch` to sessions owned by the calling plugin runtime, stamp ownership on newly created rows, reject ownerless legacy rows, and add regression coverage, while also changing doctor-health behavior.

## Best Possible Solution

Authorize the authoritative session row inside the same backend-neutral mutation that projects and persists it, preserve ownership stamping and focused race coverage, remove the doctor-health edit, and prove owned, foreign, concurrent, and ownerless behavior through a real plugin-runtime Gateway run.

No. Checking ownership while building a projection is insufficient when persistence occurs in a later mutation; the narrow maintainable fix is to authorize the authoritative write-time entry within the same backend-neutral mutation.

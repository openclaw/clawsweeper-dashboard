## Summary

The central bug remains valid, but this head still authorizes an earlier snapshot and can overwrite a row whose owner changed before the SQLite write queue runs. ## Best Possible Solution

Use the canonical SQLite target-patch boundary so the callback authorizes and projects from the same writer-queued row version that the transaction validates, stamp ownership only for genuinely new rows, split the doctor change, and add a tested migration or explicit operator recovery path for legacy ownerless rows.

- **[P1] Authorize the row version accepted by the SQLite write:** `src/config/sessions/session-accessor.ts:1810-1815`
  - body: `authorize` checks `existingEntry` before `applySessionEntryLifecycleMutation` enters the SQLite writer queue. If another queued writer replaces an owned row with a foreign-owned row between these phases, this request can overwrite it. Move authorization and projection into the writer-queued target update so they use the same prepared row the transaction validates.
  - confidence: 0.96

  - confidence: 0.99

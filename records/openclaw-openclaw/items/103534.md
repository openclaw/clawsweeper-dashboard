## Label Justifications

- `P1`: The PR closes an active cross-plugin session mutation boundary that can archive, unarchive, or rewrite another plugin's persisted session state.
- `merge-risk: 🚨 compatibility`: Plugin-runtime patches that previously succeeded against legacy ownerless rows will now fail and may require operator recovery.
- `merge-risk: 🚨 session-state`: The affected RPC mutates persisted archive, key, label, category, pinned, unread, and related session fields.
- `merge-risk: 🚨 security-boundary`: The patch determines which in-process plugin runtime may mutate a session and deliberately rejects mutations when ownership is unprovable.

## Summary

The branch is the strongest current candidate for the reported ownership gap: prior authorization-order defects are fixed, the atomic patch path is coherent, and no new line-level correctness defect remains. It should stay open for explicit maintainer approval of legacy ownerless-row behavior and after-fix proof from a deployed plugin-runtime setup.

## What This Changes

The PR adds plugin-runtime ownership authorization to `sessions.patch`, stamps ownership on patch-created session rows, and adds regression coverage for foreign, ownerless, concurrent, and own-session mutations.

## Best Possible Solution

Keep exact-owner authorization inside the locked projection before migration, retain ownership stamping for plugin-created rows, and land only after maintainers explicitly approve the legacy ownerless-row policy and deployed proof confirms the selected behavior.

Rationale: Ownerless rows provide no trustworthy plugin authority, but rejecting them changes an upgrade path that may have worked before ownership metadata existed; security isolation and compatibility cannot both be inferred safely from code alone.

Options:

- **Fail closed on ownerless rows (recommended):** Keep exact owner equality so a plugin runtime can patch only rows carrying its own `pluginOwnerId`, with operator recovery for legacy rows.
- **Add operator-owned migration:** Keep runtime fail-closed behavior but provide a narrow doctor or operator flow to assign or recreate legacy rows safely.
- **Preserve ownerless patching:** Allow plugin runtimes to patch ownerless rows for compatibility, accepting that the caller's authority over those rows cannot be established.

## Solution Assessment

Yes for the implementation shape: the authoritative check uses the transaction-selected freshest row before migration or persistence, and plugin-created rows receive stable ownership. The legacy ownerless-row policy and deployed proof remain merge gates rather than code-correctness findings.

## Summary

Current main still lets a BlueBubbles debounce flush fail terminally when dispatch throws a reply-session initialization conflict: the original batch is not retried or visibly recovered. The merged Signal repair covers only Signal, while the open shared self-healing PR may reduce the underlying conflict but does not yet establish BlueBubbles delivery recovery. This issue remains necessary as the BlueBubbles-specific reliability tracker.

## What This Changes

Retain and retry an inbound BlueBubbles message when reply-session initialization conflicts instead of logging the failed debounce flush and dropping the message.

## Best Possible Solution

Add a BlueBubbles-owned bounded retry around the retained ordered inbound batch, matching the Signal lifecycle guarantees: recognize nested conflict errors, reserve the conversation execution slot during jittered backoff, cancel on monitor shutdown, preserve message order, and log an observable terminal failure after exhaustion without changing shared session lifecycle policy.

No live current-main BlueBubbles reproduction was run, but the source path is high-confidence reproducible: a conflict thrown by `dispatchInboundMessage` reaches the debouncer error callback, which only logs and has no retention or retry path.

Yes. A bounded channel-owned retry is the narrowest maintainable repair because BlueBubbles still owns the original inbound payload and the merged Signal implementation already establishes the ordering, cancellation, and exhaustion pattern; shared session teardown should remain separate.

## Summary

Keep this issue open as the canonical product tracker: current main and v2026.6.11 still provide only per-session hard reset, while running chats intentionally retain their selected auth profile until individually reset; the narrower related issues do not replace the requested cross-session capability.

## What This Changes

Request an operator-triggered, context-preserving refresh of authentication state across all active sessions after credentials or providers change.

## Best Possible Solution

Add an admin-scoped auth-refresh operation that enumerates canonical session stores, preserves session IDs and transcripts, invalidates only automatically derived auth/runtime bindings by default, respects explicit pins, and defines deterministic handling for active runs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should a global auth switch refresh only automatically selected session credentials, or also replace explicit per-session auth-profile pins and interrupt active runs?

Rationale: Current main intentionally distinguishes explicit pins, automatic profile selection, CLI auth epochs, and hard session reset; repository behavior cannot determine the desired cross-session policy without maintainer intent.

Likely owner: steipete

Owner reason: This person has the strongest history across the Gateway reset lifecycle and previously retained the issue for this product decision.

Owner confidence: high

Options:

- **Refresh automatic selections (recommended):** Preserve explicit session pins and active conversation state while invalidating auto-selected auth and runtime bindings for subsequent turns.
- **Force every session:** Replace explicit pins as well, with operator.admin authorization and a defined cancellation policy for active runs.
- **Retain individual resets:** Keep the documented per-session /new or /reset workflow and decline a global refresh surface.

## Reproduction Assessment

Yes, at source level. Current main requires one session key for reset, performs one hard lifecycle reset, and documents that running sessions retain their auth selection until individually reset; no live multi-channel run is necessary to establish that the global capability is missing.

## Solution Assessment

No, a global hard reset is not the best implementation because it changes session lifecycle and may discard intentional per-session selections. A separate auth-only refresh with explicit pin and active-run semantics is the narrower maintainable solution.

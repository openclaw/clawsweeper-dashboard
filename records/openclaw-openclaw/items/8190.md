## Summary

Keep open: current main and v2026.6.11 still provide only per-session reset/auth invalidation, not the requested global, context-preserving auth refresh across active sessions. The issue remains useful as the canonical tracker because the remaining work crosses Gateway protocol scope, session context preservation, provider/auth ownership, and security semantics.

## What This Changes

The issue requests a global, context-preserving way to refresh or reset active sessions after auth/provider changes.

## Best Possible Solution

Design an additive, admin-scoped Gateway/session auth-refresh contract that enumerates active sessions, invalidates stale auth-backed runtime state, preserves intended context and explicit user selections, and adds protocol, Gateway, session-store, docs, and security coverage.

Rationale: The code gap is clear, but the safe behavior crosses credential ownership, explicit per-session pins, transcript continuity, Gateway protocol scope, and provider routing policy.

Likely owner: steipete

Owner confidence: high

Options:

- **Add admin auth refresh contract (recommended):** Define a sessions.refreshAuth-style API with all-sessions scope, stale-state ownership rules, and regression coverage for context preservation and credential invalidation.
- **Fold into provider-switch transaction:** Make provider/auth switching own session refresh as part of one transaction, reducing standalone API surface but tying the behavior to switch workflows.
- **Keep per-session reset only:** Leave current reset behavior unchanged and document per-session recovery, accepting continued multi-channel auth-switch friction.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 expose single-key sessions.reset plus per-session auth invalidation, but no global context-preserving auth refresh method. I did not run a live multi-channel auth-switch scenario in this read-only review.

## Solution Assessment

Unclear as a final implementation: a global Gateway action is plausible, but maintainers need to define admin scope, preservation rules, auth-epoch invalidation, and stale-auth versus intentional pin semantics before a safe fix lands.

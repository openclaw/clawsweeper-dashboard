## Summary

Current main narrows but does not eliminate the request: embedded provider turns resolve current credentials per run, while retained native/CLI runtime bindings still use auth epochs and lack a provider-targeted global refresh operation. Keep this open for a maintainer security/product decision rather than implementing the proposed blanket hard reset.

## What This Changes

Add a global, context-preserving way to refresh active sessions after provider or credential changes.

## Best Possible Solution

Integrate provider/profile-targeted native binding invalidation with authorized auth mutations, preserving OpenClaw session IDs and transcripts while applying a documented active-run policy.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: When credentials change for a provider/profile used by retained native or CLI sessions, should matching active runs be cancelled immediately or allowed to drain before their bindings are invalidated?

Rationale: Embedded provider turns already load current auth per run; the unresolved choice governs retired-credential lifetime and continuity for retained native runtime sessions.

Likely owner: steipete

Owner reason: This person has the strongest combined signal from direct issue discussion and repeated auth/session lifecycle history.

Owner confidence: high

Options:

- **Cancel and invalidate (recommended):** Cancel matching active runs, invalidate only affected native bindings, and preserve the OpenClaw transcript for the next turn.
- **Drain then invalidate:** Allow matching runs to finish with old credentials before invalidating bindings for subsequent turns.
- **Manual refresh RPC:** Keep auth mutation separate and require an admin-scoped provider/profile refresh action after credential changes.

## Reproduction Assessment

Yes, with a narrower scope. Current main has no global auth-refresh action, retained CLI bindings use auth epochs, and embedded provider attempts reload current auth rather than relying on session-lifetime cached keys.

## Solution Assessment

No. Bulk hard reset is not the best solution; provider/profile-targeted native binding invalidation is narrower, preserves context, and avoids disrupting unaffected sessions.

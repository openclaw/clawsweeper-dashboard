## Summary

Current main still lacks the requested global, context-preserving auth refresh. The existing operator-admin `sessions.reset` API addresses one session and performs a hard lifecycle rollover, while CLI credential changes are detected lazily during per-session reuse; maintainers must define the cross-agent scope and in-flight credential boundary before implementation.

## What This Changes

Add a global operation that refreshes provider authentication across active sessions while preserving each session’s conversation context.

## Best Possible Solution

Add an operator-admin Gateway auth-refresh operation that invalidates auth-backed runtime and CLI bindings across an explicitly chosen session scope, preserves durable session ids/transcripts/context, and defines deterministic behavior for in-flight runs.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should global auth refresh cover all persisted sessions across every agent store or only active sessions, and should in-flight runs finish, cancel, or be rejected during credential cutover?

Rationale: Current code establishes operator-admin authority for session reset but does not define the cross-agent target set or whether work already using the prior credential identity may continue safely.

Likely owner: steipete

Owner reason: The reset service extraction and densest current history across Gateway reset, protocol, and auth-epoch surfaces route this boundary decision here.

Owner confidence: high

Options:

- **All stores, future turns (recommended):** Refresh persisted auth bindings across agent stores while allowing already-started runs to finish with their captured credential identity.
- **Active sessions, cancel runs:** Refresh only active sessions and cancel their in-flight runs before accepting new work with current credentials.
- **Keep lazy invalidation:** Do not add a bulk operation; retain per-session next-use auth-epoch checks and improve provider-switch tooling and status feedback.

## Reproduction Assessment

Yes at source level. Current main exposes only an operator-admin, one-key hard reset, while credential epoch invalidation happens lazily when each CLI session is considered for reuse.

## Solution Assessment

No, globally invoking the existing reset is not the best solution because it rotates session and transcript lifecycle state. A dedicated bulk auth-refresh operation is the narrower and safer owner-boundary design.

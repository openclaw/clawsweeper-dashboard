## Summary

Keep open as the canonical product/API tracker. Current main and v2026.6.11 still expose only a keyed hard session reset, while credential refresh and binding invalidation remain runtime-specific; the narrower related issues do not supersede the requested cross-session coordination.

## What This Changes

Add a global, context-preserving way to refresh active sessions after provider credentials or auth accounts change.

## Best Possible Solution

Keep hard conversation reset separate; standardize next-turn credential refresh in runtime owners and add an admin-only cross-runtime invalidation coordinator only for persistent auth bindings, preserving session ids, transcripts, explicit pins, and deterministic in-flight behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add an admin-only cross-runtime auth-binding invalidation coordinator, or require all runtime owners to refresh credentials automatically without a global operator surface?

Rationale: Current main deliberately separates destructive session reset from runtime-specific auth refresh, and code evidence cannot determine the permanent coordination, authorization, explicit-pin, and active-run semantics.

Likely owner: steipete

Owner reason: Gateway and session lifecycle are the central coordination boundary, and Peter has the strongest recent and historical ownership signal.

Owner confidence: high

Options:

- **Add narrow coordinator (recommended):** Invalidate persistent runtime auth bindings across sessions while preserving canonical session state, explicit pins, and deterministic active-run behavior.
- **Runtime refresh only:** Require every runtime and provider owner to resolve current credentials on the next turn and add no global operator action.
- **Bulk hard reset:** Reuse the existing reset lifecycle across all sessions, accepting transcript rollover and lifecycle side effects.

## Reproduction Assessment

Yes. Current main and v2026.6.11 expose only a keyed administrative hard reset plus runtime-specific auth invalidation; no all-session, context-preserving auth coordinator exists.

## Solution Assessment

No, applying the existing reset globally is not the best solution because it rotates session identity and archives transcripts. A narrow auth-binding coordinator, or complete automatic runtime refresh, preserves the canonical session lifecycle and avoids a competing reset path.

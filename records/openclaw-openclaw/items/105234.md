## Summary

Current main and v2026.6.11 already protect shared schema repair and individual core imports with synchronous SQLite transactions, but plugin doctor migrations can compose multiple independently committed store writes. The Memory Core phase-signal migration is source-reproducible as a partial-state hazard because one write can persist, a later write can fail, and the retry path skips the retained source when any target namespace has rows; this remains necessary work, but it needs a maintainer decision on the plugin migration atomicity contract rather than a doctor-wide transaction.

## What This Changes

Ensure doctor-managed SQLite migrations cannot leave non-resumable partially migrated state when interrupted or when a later write fails.

## Best Possible Solution

Define an owner-scoped migration atomicity contract: prepare and parse asynchronously, then apply related SQLite rows in one synchronous transaction where feasible; otherwise use explicit per-item checkpoints and verify every required target before archiving or skipping the legacy source. Add failure-injection coverage for the Memory Core multi-namespace path and audit sibling plugin migrations for the same any-row-means-complete pattern.

## Solution Assessment

No, not as proposed: one transaction around all doctor migrations would cross asynchronous filesystem, session, and plugin boundaries. The best solution is an explicit owner-scoped atomic batch or checkpoint/resume contract, starting with regression coverage for the demonstrated multi-namespace migration.

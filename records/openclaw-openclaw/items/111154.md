## Summary

Keep this PR open for maintainer product direction and real after-fix Gateway evidence. The reattach-and-replay design addresses the duplicate-run problem, but it intentionally replaces the current automatic fresh-session fallback with a fail-closed default for ambiguous outcomes.

## What This Changes

The branch adds reconnect, wait, and cache-only idempotent replay for uncertain Gateway agent runs, with `--rerun-on-ambiguous` as an explicit embedded-rerun escape hatch.

## Best Possible Solution

Have the Gateway/CLI owner choose the disconnected-run contract first; if preserving current result availability is required, attempt reattach and replay first, then retain the isolated fallback by default while offering fail-closed behavior as an explicit mode.

Question: Should an unrecoverable disconnected `openclaw agent` run fail closed by default, or should the CLI preserve the current isolated embedded fallback after a bounded reattach-and-replay attempt?

Rationale: Both paths have material user consequences: fail-closed avoids duplicate side effects but can return no result, while fallback preserves result availability but can execute side effects twice.

Likely owner: steipete

Owner confidence: high

Options:

- **Preserve fallback compatibility (recommended):** Recover the original run first, then retain the existing isolated embedded fallback as the default when recovery cannot establish a terminal result; make fail-closed explicit.
- **Adopt fail-closed default:** Accept that ambiguous Gateway failures may return no result by default in exchange for preventing an automatic second execution, with the new flag as opt-in rerun consent.
- **Split by delivery mode:** Use reattach-first and fail-closed behavior for `--deliver` while retaining current fallback behavior for interactive stdout invocations.

## Label Justifications

- `P2`: The missing mode causes recurring Telegram formatting and client-compatibility friction, but current supported delivery paths and workarounds prevent a general channel outage.
- `impact:ux-friction`: Users must accept the selected Telegram formatting path or use presentation and client workarounds because no supported plain-text choice exists.

## Summary

Keep open. Current main and v2026.6.11 support an inherited `richMessages` switch between Telegram rich-message delivery and the standard HTML path, but neither provides the requested forced-plain or selectable formatting mode; recent discussion also confirms that this remains a real user-facing formatting need rather than a stale report.

## What This Changes

Request a configurable Telegram outbound formatting mode, optionally inheritable per account, instead of relying on the currently selected rich-message or HTML delivery path.

## Best Possible Solution

Define one plugin-owned, inherited safe text-output setting that preserves the current default, supports an explicit forced-plain mode, and excludes raw HTML or MarkdownV2 until separately approved, then apply it uniformly across sends, captions, edits, previews, schema, docs, and tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Telegram gain only a safe forced-plain opt-out alongside the current rich/HTML behavior, or a broader selectable renderer contract that also includes MarkdownV2 or raw HTML?

Rationale: The choice determines the permanent config contract, precedence with `richMessages`, escaping rules, and whether untrusted model text may reach Telegram formatting parsers without the existing renderer.

Likely owner: steipete

Owner confidence: high

Options:

- **Add safe plain mode (recommended):** Preserve current defaults, add an inherited forced-plain option, and keep MarkdownV2 and raw HTML outside the supported contract.
- **Define full renderer modes:** Design a broader enum covering plain, safe HTML, and MarkdownV2 with explicit escaping, precedence, migration, and end-to-end coverage.
- **Keep current controls:** Decline another config surface and address remaining presentation defects through the existing renderer and `richMessages` behavior.

## Reproduction Assessment

Not applicable as a bug reproduction; current source makes the missing capability high-confidence because Telegram configuration exposes `richMessages` but no forced-plain or general selectable formatting mode.

## Solution Assessment

No, the literal `none | Markdown | HTML` proposal is not yet the safest contract because it overlaps the rich-message architecture and leaves escaping semantics ambiguous; a narrow safe plain-mode decision is the clearest first step.

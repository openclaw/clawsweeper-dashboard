## Summary

Keep open: current main and v2026.6.11 expose `richMessages` plus internal HTML/plain fallback paths, but still no supported Telegram channel or account parse-mode config; the remaining work needs maintainer product direction.

## What This Changes

Request adding optional top-level and per-account Telegram parse-mode configuration for plain, Markdown, or HTML-style outbound rendering.

## Best Possible Solution

Define a maintainer-approved Telegram formatting policy in the bundled Telegram plugin, preserve current HTML compatibility by default, and expose only modes whose escaping, fallback, docs, and cross-funnel tests are specified.

Options:

- **Add Narrow Default-Preserving Selector (recommended):** Expose a typed Telegram text/parse-mode config that keeps current HTML behavior by default and initially supports only modes with well-defined escaping and fallback semantics.
- **Keep Only richMessages:** Close or defer parse-mode config and continue using `richMessages` plus internal HTML/plain fallbacks as the supported operator surface.
- **Design Broader Formatting Policy:** Pause implementation until maintainers define MarkdownV2, raw HTML/custom entities, rich messages, account inheritance, and security constraints together.

## Reproduction Assessment

Yes. Source inspection shows no top-level or per-account `parseMode` config in current main or v2026.6.11, while Telegram delivery chooses HTML, rich messages, or plain fallback internally.

## Solution Assessment

Unclear. The proposed `none | Markdown | HTML` shape is plausible, but the best solution needs maintainer-approved defaults, mode names, escaping rules, account inheritance, and `richMessages` interaction.

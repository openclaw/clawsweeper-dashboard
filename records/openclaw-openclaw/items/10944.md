## Summary

Current main and v2026.6.11 provide an account-inheritable `richMessages` switch for choosing standard HTML delivery instead of Telegram rich messages, but they still do not expose the requested forced-plain or selectable text mode. The feature remains useful, while its supported values, inheritance, defaults, and escaping boundary require maintainer product direction.

## What This Changes

Add an account-inheritable Telegram configuration for selecting plain or formatted outbound text delivery.

## Best Possible Solution

If maintainers sponsor the capability, add a plugin-owned, account-inheritable safe mode such as `auto | plain`, preserve current formatted behavior as the default, avoid implicit raw Markdown or HTML, and apply the resolved mode consistently across sends, edits, previews, captions, helpers, schema metadata, documentation, and tests.

## Maintainer Decision

Question: Should Telegram expose a forced-plain account setting, and should its public contract be limited to safe `auto | plain` behavior rather than Telegram API parse-mode dialects?

Rationale: Current delivery intentionally renders through OpenClaw-owned formatting and escaping. Source evidence cannot safely choose new raw-markup semantics, inheritance behavior, or defaults without maintainer intent.

Likely owner: steipete

Owner confidence: high

Options:

- **Add safe auto/plain mode (recommended):** Expose an account-inheritable `auto | plain` setting that preserves current behavior by default while allowing unformatted delivery without raw-markup semantics.
- **Keep automatic formatting:** Retain standard formatted delivery, plain fallback on formatting failure, and the existing rich-message switch without adding another setting.
- **Expose Telegram dialects:** Support Telegram-specific Markdown or HTML values only after defining trusted-content, escaping, fallback, and upgrade contracts for every delivery path.

## Reproduction Assessment

Yes, at source level: the current configuration and delivery paths expose standard formatted and rich-message behavior but no supported forced-plain or general parse-mode override. A live Telegram run is not required to establish that missing configuration surface.

## Solution Assessment

No, the proposed `none | Markdown | HTML` enum is not yet the best contract because it exposes transport parsing dialects without defining escaping and trust semantics. A narrower `auto | plain` setting is safer if maintainers approve the feature.

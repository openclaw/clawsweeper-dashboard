## Summary

Keep open: current main and v2026.6.11 still have `richMessages` plus internal HTML/rich/plain fallback behavior, but no supported top-level or per-account Telegram parse/text-mode config.

## What This Changes

The issue requests a Telegram parse/text-mode configuration option, possibly with per-account overrides, so users can choose plain text, Markdown, or HTML behavior.

## Best Possible Solution

Define a maintainer-approved Telegram formatting policy, preserve current HTML compatibility by default, and wire only explicitly supported modes through schema/types, docs, sends, edits, captions, previews, and tests.

## Reproduction Assessment

Yes. Source inspection shows `channels.telegram.parseMode` and account-level `parseMode` are absent from the strict Telegram schema/types on current main and v2026.6.11, while delivery paths choose HTML, rich messages, or plain fallback internally.

## Solution Assessment

Unclear whether the proposed `none | Markdown | HTML` shape is the best permanent API. The safer solution is a maintainer-approved formatting policy that preserves current defaults and defines escaping/security behavior for every supported mode.

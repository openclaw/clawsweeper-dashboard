## Summary

Keep open: current main and v2026.6.11 have `richMessages` plus internal HTML/plain fallback paths, but still no supported Telegram parse/text-mode config; adding that config surface needs product direction first.

## What This Changes

Request to add Telegram parse/text-mode configuration with top-level and per-account overrides for plain, Markdown, or HTML outbound rendering.

## Best Possible Solution

Define a maintainer-approved Telegram formatting policy in the bundled Telegram plugin, preserve current HTML compatibility by default, and expose only modes whose escaping, rich-message interaction, docs, and tests are specified.

- **Keep Only richMessages:** Close or defer parse-mode config and continue using `richMessages` plus internal HTML/plain fallbacks as the supported operator surface.
- **Design Broader Formatting Policy:** Pause implementation until maintainers define MarkdownV2, raw HTML/custom entities, rich messages, account inheritance, and security constraints together.

## Reproduction Assessment

Yes. Source inspection shows no top-level or per-account `parseMode` config in current main or v2026.6.11, while Telegram delivery chooses HTML, rich messages, or plain fallback internally.

## Solution Assessment

Unclear. The proposed `none | Markdown | HTML` shape is plausible, but the best solution needs maintainer-approved defaults, mode names, escaping rules, account inheritance, and `richMessages` interaction.

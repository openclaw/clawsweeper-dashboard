## Summary

Keep open. Current main and v2026.6.11 provide an inherited `richMessages` switch between standard HTML delivery and Telegram rich messages, but they still do not provide the requested forced-plain or selectable text mode; the remaining capability is useful but needs an explicit product and escaping-boundary decision.

## What This Changes

Requests configurable Telegram outbound text parsing at channel and account scope, including plain text, Markdown, and HTML modes.

## Best Possible Solution

Keep standard HTML as the compatibility default and `richMessages` as the existing opt-in, then add an inherited Telegram-owned forced-plain mode only if sponsored; exclude raw HTML or MarkdownV2 until their escaping and trusted-input contracts are explicitly designed.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Telegram support an inherited forced-plain outbound mode beyond the existing standard-HTML and `richMessages` paths, and should raw HTML or MarkdownV2 remain out of scope?

Rationale: The code can mechanically carry another mode, but maintainers must define the permanent config name, supported values, inheritance, default, and trust boundary rather than letting an implementation invent a public compatibility-sensitive contract.

Likely owner: steipete

Owner reason: The HTML transition, recent issue review, and repeated Telegram configuration history make this the strongest available product-routing signal.

Owner confidence: high

Options:

- **Add Safe Plain Mode (recommended):** Preserve standard HTML by default and add one inherited opt-in that sends escaped, unformatted plain text across all Telegram delivery paths.
- **Expose Multiple Parse Modes:** Support plain, HTML, and MarkdownV2 only after defining raw-input trust, escaping, fallback, captions, previews, and account inheritance as a documented public contract.
- **Keep Existing Modes:** Retain standard HTML plus the `richMessages` opt-in and close the request without adding another configuration surface.

## Reproduction Assessment

Yes at source-contract level: current Telegram docs, types, and delivery behavior expose standard HTML and `richMessages`, but no forced-plain or selectable parse mode. A live Telegram run is not needed to establish that the requested configuration capability is absent.

## Solution Assessment

No, the proposed unrestricted `none | Markdown | HTML` enum is not yet the best solution because it conflates safe plain delivery with raw formatting semantics. A narrower forced-plain option that preserves the current default is safer and easier to keep consistent.

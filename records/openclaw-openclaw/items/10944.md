## Summary

Keep open: current main and v2026.6.11 still do not expose `channels.telegram.parseMode` or a per-account equivalent; existing `richMessages` and `markdown.tables` cover different formatting choices, so the remaining work is a product/config decision.

## What This Changes

The issue requests a public Telegram `parseMode` setting at channel and per-account scope so users can choose plain text, HTML, or Markdown-style rendering.

## Best Possible Solution

Add a plugin-owned typed parse/text mode config only after maintainers decide supported modes and scope, then wire it through sends, captions, streaming previews, delivery helpers, schema/types/metadata/docs, and focused tests while preserving the current default unless a migration decision says otherwise.

Options:

- **Add a narrow plugin config (recommended):** Expose a typed Telegram-owned setting with current HTML as the default plus an explicit plain/no-parse option, and treat MarkdownV2/raw/custom-emoji support as separate decisions or follow-ups.
- **Keep existing knobs only:** Continue supporting `richMessages`, `markdown.tables`, and HTML/plain fallbacks without adding another public parse-mode surface.
- **Broaden to rich formatting policy:** Design a larger Telegram formatting policy that covers parse mode, rich messages, custom emoji, and raw trusted payloads together before implementation.

## Reproduction Assessment

Yes. Source inspection shows the Telegram schema/types do not accept a public `parseMode` key, while current send, caption, and preview paths still choose HTML/rich-message behavior internally.

## Solution Assessment

Unclear until maintainers choose the product surface. The requested direction is plausible, but the safest implementation is a narrow Telegram plugin config with explicit mode semantics rather than accepting every Telegram parse option at once.

## Summary

Keep open. Current main and the latest release still expose only the `richMessages` opt-in plus internal HTML/rich transport choices, not the requested Telegram `parseMode` configuration; this remains a valid feature/product-surface decision rather than a cleanup-close candidate.

## What This Changes

The issue requests a configurable Telegram parse mode at channel and optional per-account scope.

## Best Possible Solution

Adopt one maintainer-approved Telegram formatting policy in the bundled Telegram plugin that preserves current HTML compatibility by default and explicitly defines plain/no-parse, MarkdownV2 or raw-HTML support, account inheritance, and `richMessages` interaction.

## Reproduction Assessment

Yes, at source level: `channels.telegram.parseMode` and per-account `parseMode` are absent from the strict Telegram config/types while send, edit, media-caption, and preview paths still choose HTML or rich-message transport internally. I did not run a live Telegram rendering repro because the remaining item is a config/product surface gap.

## Solution Assessment

Unclear whether the exact proposed `none | Markdown | HTML` shape is the best permanent API. The safer solution is a maintainer-approved Telegram formatting policy that preserves current HTML defaults, keeps rich messages explicit, and only exposes modes whose escaping and client behavior are well defined.

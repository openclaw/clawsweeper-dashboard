## Summary

Keep open. Current main exposes `richMessages` to select rich-message delivery versus the standard HTML path, but it still does not provide the requested plain-text or selectable Telegram formatting mode; recent user reports confirm that formatting control remains useful. The remaining blocker is a maintainer product decision about supported modes, inheritance, escaping, and interaction with `richMessages`.

## What This Changes

Add configurable Telegram outbound formatting at channel and optionally account scope, allowing users to select HTML, plain text, or another supported parse mode.

## Best Possible Solution

Add a Telegram-plugin-owned formatting setting that initially supports `html` and `plain`, preserves HTML as the upgrade-safe default, supports normal account inheritance if desired, and is wired consistently through sends, captions, edits, previews, and fallbacks; defer MarkdownV2 and raw HTML until their escaping and trust contracts are explicitly approved and proven.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Telegram expose an inherited outbound formatting setting, and if so should the first supported contract be limited to upgrade-safe `html` and `plain` modes or also include MarkdownV2/raw formatting?

Rationale: The choice changes public configuration and message-rendering semantics, and source inspection cannot determine the intended mode set, precedence with `richMessages`, or acceptable escaping and trust boundary.

Likely owner: steipete

Owner reason: The strongest available history ties this person to the original HTML decision, recent Telegram configuration work, and prior product review of this issue.

Owner confidence: high

Options:

- **Ship HTML and plain modes (recommended):** Preserve HTML as the default, add an inherited plain-text opt-out, and defer MarkdownV2/raw formatting until a separate safe contract is designed.
- **Include MarkdownV2:** Add HTML, plain, and MarkdownV2 together only with end-to-end escaping, caption/edit/preview parity, compatibility documentation, and live Telegram proof.
- **Keep renderer-managed formatting:** Decline a user-selectable mode and instead fix individual HTML and rich-message rendering defects within the existing automatic delivery model.

## Reproduction Assessment

Yes at source level: the current documented and typed Telegram configuration lacks selectable plain/HTML/MarkdownV2 formatting, while the existing `richMessages` switch only selects the delivery mechanism. The discussion also supplies concrete user-visible examples, although no live reproduction was run during this read-only review.

## Solution Assessment

No, the literal proposed `parseMode: none | Markdown | HTML` contract is not yet the best safe design. A narrower semantic `html | plain` setting with the current default preserved is easier to maintain; MarkdownV2 or raw formatting should require a separately approved escaping contract.

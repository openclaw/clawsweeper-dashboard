## What This Changes

The issue asks OpenClaw to stop silently leaving intended legacy `MEDIA:` attachments undelivered when the token appears inside a markdown code fence.

## Best Possible Solution

Review and repair or close https://github.com/openclaw/openclaw/pull/80396; keep the no-extract default unless maintainers explicitly accept broader attachment parsing from code fences.

## Maintainer Decision

Question: Should fenced legacy `MEDIA:` directives stay non-extracting with a warning, be extracted as attachments, or remain documented as by-design only?

Rationale: The current parser intentionally preserves fenced examples as text, but the issue reports a real silent media-delivery failure; extraction versus diagnostics changes the product contract and false-positive behavior.

Likely owner: vincentkoc

Owner reason: This account provided the live member review that frames the warning-boundary contract and has adjacent reply-path history.

Owner confidence: high

Options:

- **Warn Only At Delivery Boundary (recommended):** Keep fenced tokens as text, emit one diagnostic warning in the actual outbound delivery path, and land the linked PR after the remaining warning-path repair.
- **Extract From Fences:** Treat standalone fenced `MEDIA:` lines as attachments, accepting the risk that code examples can become deliverable media unless a stricter policy is designed.
- **Docs Only:** Keep runtime behavior unchanged and rely on documentation that legacy `MEDIA:` lines must be standalone plain text.

## Reproduction Assessment

Yes. Source-level reproduction is high confidence: current main keeps fenced lines before the `MEDIA:` parsing branch, and the adjacent test expects the fenced token to remain visible text; I did not run a live channel repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the contract. The linked warn-only delivery-boundary path is the lowest-risk mitigation, while extracting fenced tokens could turn code examples into attachments.

## Label Justifications

- `P1`: A released version can abort active tool-heavy WebChat turns after tools have run, suppressing the final response and forcing manual side-effect verification.
- `impact:message-loss`: The affected turn can terminate without delivering the assistant’s final visible response.
- `impact:session-state`: The failure is driven by transcript changes during prompt-lock release and by incomplete continuation from recorded tool state.

## Summary

Keep this issue open: release-v2026.7.1 logs show a real user-visible turn abort, and the incomplete-turn path intentionally refuses automatic replay when tools may have produced side effects. The prompt-lock takeover and replay-unsafe incomplete `toolUse` cases overlap operationally but need separate regression coverage and an explicit recovery contract before implementation. ([github.com](https://github.com/openclaw/openclaw/issues/107873))

## What This Changes

Prevent embedded WebChat turns from aborting after prompt-lock takeover or incomplete tool-use races while preserving at-most-once handling of side-effecting tools.

## Best Possible Solution

Preserve the guarded transcript-ownership boundary, retry whole attempts only when replay metadata is safe, and otherwise continue from committed transcript and tool-result state without re-executing completed tools before producing a final reply.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What recovery contract should OpenClaw use when an embedded turn ends with terminal `toolUse` after potentially side-effecting tools have already committed results?

Rationale: Automatic whole-attempt replay risks duplicated side effects, while unconditional fail-closed behavior abandons a visible user turn; source inspection cannot choose the permanent at-most-once versus recovery semantics without maintainer intent.

Likely owner: jalehman

Owner reason: The recent prompt-fence work documents and tests the same transcript ownership boundary that constrains safe recovery.

Owner confidence: high

Options:

- **Continue From Committed State (recommended):** Resume with a continuation prompt from the authoritative transcript and recorded tool results, never replaying completed side-effecting calls; retry the whole attempt only when replay metadata is safe.
- **Keep Fail-Closed:** Retain the current manual-verification error for replay-unsafe turns and improve the in-product recovery guidance without automatic continuation.
- **Retry All Takeovers:** Boundedly rerun every takeover or incomplete-tool turn and accept the possibility of duplicated external side effects.

## Reproduction Assessment

No, there is not yet a high-confidence deterministic current-main reproduction. The v2026.7.1 logs and source establish both failure paths, but the reporter’s ordinary failing-tool probes did not reliably recreate the exact transcript-takeover plus replay-unsafe terminal state.

## Solution Assessment

No, unconditional outer-loop retries are not the best fix because they can repeat side-effecting tools. The safer direction is transcript-state continuation with full-attempt retry restricted to explicitly replay-safe attempts.

## Label Justifications

- `P1`: Cron can accept a scheduled Feishu announce job that later fails to deliver, breaking an active channel workflow for users.
- `impact:message-loss`: The reported behavior is scheduled announce output not reaching Feishu after an invalid no-target job is accepted.

## Summary

Keep open: current `main` and the latest release still validate only the announce channel shape and blank strings, not the Feishu/Lark missing-target case, while runtime outbound resolution still reports the Feishu missing-target failure. This issue remains the canonical report; the open fork PRs that close it are dirty and need maintainer adoption, refresh, or closure before starting replacement work.

## What This Changes

Create-time validation should reject Feishu/Lark announce cron jobs that omit `delivery.to` unless a deterministic target can be resolved.

## Best Possible Solution

Land one focused gateway/service create-and-update validation fix for Feishu/Lark announce delivery without a target, mirror it in CLI/UI feedback where useful, and track legacy audit or diagnostic wording as a separate follow-up if maintainers want it.

## Reproduction Assessment

Yes. Source inspection shows `cron add` can submit `delivery: { mode: "announce", channel: "feishu" }` without `to`, gateway validation does not reject that omission, and runtime outbound target resolution still has the Feishu missing-target error path.

## Solution Assessment

Yes. Gateway/service create and update validation is the narrowest maintainable fix because it prevents invalid stored jobs from every creation path; CLI/UI checks should only mirror that boundary for earlier feedback.

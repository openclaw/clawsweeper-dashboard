## Summary

This issue remains necessary: it describes a concrete destructive error path in standalone task maintenance when persisted cron state cannot be restored. The merged active-session admission work in https://github.com/openclaw/openclaw/pull/104137 addresses a different in-process race; it does not establish that a separate maintenance CLI process can safely treat failed persisted cron-state restoration as an empty running-job set.

## What This Changes

Prevent `tasks maintenance --apply` from pruning cron-run session registry entries when the persisted cron state needed to identify running jobs cannot be restored.

## Best Possible Solution

Make the persisted cron-state restore a fail-closed precondition for any session-registry pruning that relies on running cron-job identities, report the restore failure clearly, and add regression coverage proving the registry remains unchanged; retain only independently safe maintenance work if maintainers explicitly choose that split behavior.

- **Abort the whole apply pass (recommended):** Fail before any maintenance mutation when cron state cannot be restored, matching the conservative task-flow restore gate.
- **Skip only dependent pruning:** Continue task and task-flow maintenance only after proving those mutations do not depend on cron running-state restoration, while skipping session-registry pruning and reporting the partial result.

## Solution Assessment

Unclear until maintainers choose the partial-versus-total maintenance policy, but failing closed for session pruning is the narrowest safe invariant and is preferable to silently substituting an empty running-job set.

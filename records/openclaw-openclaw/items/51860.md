## Summary

Keep open. Current main and the latest release still manage macOS gateway install/status as a user LaunchAgent in the `gui/<uid>` launchd domain; `gateway status --deep` can discover system LaunchDaemons only as extra services, not as the managed install/status target. First-class LaunchDaemon support remains a maintainer product/security decision, with related lifecycle and duplicate-manager work still open.

## What This Changes

The issue requests macOS gateway LaunchDaemon install/status support so the gateway can start before user login and report system-domain service state accurately.

## Best Possible Solution

Define one explicit macOS launchd scope model across install, status, start/stop/restart/uninstall, doctor, docs, and tests: keep the user LaunchAgent as the safe default, and add only a maintainer-approved opt-in LaunchDaemon path or clear external-management guidance.

## Reproduction Assessment

Yes, source-level. Current main still installs and reads the managed macOS gateway service through a user LaunchAgent path and `gui/<uid>` launchd calls; I did not run a live boot-without-login macOS reproduction in this read-only review.

## Solution Assessment

No, not as a bare `--system` flag sketch. The maintainable fix needs a shared launchd scope model that handles privilege, execution user, coexistence, lifecycle commands, status, doctor repair, docs, and upgrade behavior together.

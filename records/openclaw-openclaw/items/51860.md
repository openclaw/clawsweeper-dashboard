## Summary

Keep open. Current main and v2026.6.11 still install/manage the macOS gateway as a user LaunchAgent; system LaunchDaemon discovery is diagnostic only, while first-class boot-without-login install/status remains a privileged-service product and security decision.

## What This Changes

The issue requests macOS gateway system LaunchDaemon install/status support so the gateway can start before user login and report system-domain service state correctly.

## Best Possible Solution

Define one explicit macOS user/system launchd contract across install, status, stop/uninstall, doctor, docs, and tests, keeping the user LaunchAgent as the safe default and adding only an audited opt-in LaunchDaemon mode or clear diagnostic guidance.

- **Keep diagnostic guidance only:** Do not manage LaunchDaemons yet; improve status/doctor/docs so operators can inspect and repair custom LaunchDaemons manually.
- **Defer LaunchDaemon support:** Leave boot-without-login unsupported until companion-app or installer ownership is ready to own the privileged service UX.

Yes, at source level. Current main still resolves Darwin gateway service management through a user LaunchAgent path and gui/<uid> launchctl domain; I did not run a live macOS LaunchDaemon boot scenario in this read-only review.

## Solution Assessment

No, not as a one-off --system flag sketch. The maintainable fix is a shared launchd user/system scope model that covers privileged install, status, lifecycle, doctor repair, docs, and regression proof together.

## Label Justifications

- `P2`: This is a real macOS always-on gateway gap with limited platform/setup blast radius and a required product/security decision before implementation.
- `impact:security`: First-class LaunchDaemon support would cross privileged macOS service ownership, root-owned plist metadata, execution-user selection, sudo flow, and durable environment handling.
- `impact:message-loss`: When the gateway does not start after reboot before login, channel traffic through the gateway can be missed until an operator logs in or repairs the service.
- `impact:ux-friction`: The current workaround requires manual plist creation, sudo launchctl commands, file ownership/mode changes, and TMPDIR edits rather than an in-product recovery path.
- `maturity:stable`: The affected macOS Gateway host surface is scored M4 Stable in `qa/maturity-scores.yaml`, including Gateway Service Lifecycle and Diagnostics categories.

## Summary

Keep open. Current main still treats macOS gateway service management as a user LaunchAgent path, while the requested boot-without-login LaunchDaemon install/status mode remains a privileged product/security decision.

## What This Changes

The issue requests first-class macOS LaunchDaemon support for gateway install/status so the gateway can start before user login and report system-domain service state accurately.

## Best Possible Solution

Define one audited macOS launchd scope model across install, status, stop, uninstall, doctor, docs, and tests, keeping LaunchAgent as the safe default while adding an explicit LaunchDaemon path or clear diagnostic-only guidance.

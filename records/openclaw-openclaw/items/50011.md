## Summary

Keep open: current main and v2026.6.11 still persist `gateway.nodes.denyCommands` as arbitrary strings during config writes, while unknown or pattern-like entries are only diagnosed later by the security audit path. Open linked fork PRs are implementation candidates, not merged fixes, and the remaining choice is security/product policy for warning-only versus fail-closed validation.

## What This Changes

Request write-time validation or warnings for invalid `gateway.nodes.denyCommands` values so typos are not silently persisted.

## Best Possible Solution

Add registry-aware `config set` warnings for direct and ancestor writes to `gateway.nodes.denyCommands`, reusing audit suggestions while preserving custom/plugin command IDs unless maintainers explicitly choose fail-closed behavior.

Question: Should `gateway.nodes.denyCommands` write-time validation warn only, fail closed, or remain audit-only when entries are unknown to the current command registry?

Rationale: This is a security-boundary and compatibility choice: warning-only reduces false confidence without blocking custom/plugin commands, while fail-closed behavior could break valid operator setups.

Options:

- **Warn on config write (recommended):** Emit actionable warnings for unknown or pattern-like entries during `config set` and keep audit-time findings for later checks.
- **Fail closed on unknowns:** Reject unknown deny entries at write time, but require explicit compatibility handling for plugin and custom command IDs.
- **Keep audit-only:** Leave config writes free-form and rely on `openclaw security audit` to catch ineffective entries after the fact.

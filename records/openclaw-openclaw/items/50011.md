## Summary

Keep open: current main and v2026.6.11 still accept arbitrary `gateway.nodes.denyCommands` strings at config-write time, while ineffective entries are only surfaced later by security audit. The remaining blocker is maintainer/security direction on warning-first versus fail-closed behavior for custom or plugin command IDs.

## What This Changes

The issue requests warning or validation when `gateway.nodes.denyCommands` is set to command names that are not in the known command registry.

## Best Possible Solution

Add maintainer-approved warning-first config mutation feedback for direct and ancestor `gateway.nodes.denyCommands` writes, reusing the audit/runtime command vocabulary while preserving custom and plugin command IDs unless maintainers explicitly choose fail-closed behavior.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `gateway.nodes.denyCommands` config writes warn and continue, fail closed, or remain audit-only when entries are unknown, pattern-like, or supplied by plugins/custom nodes?

Rationale: The source-level gap is clear, but the security contract is a human choice because fail-closed validation improves typo safety while warning-only behavior avoids blocking valid future or plugin-owned command IDs.

Likely owner: steipete

Owner reason: The decision affects security posture and gateway node command policy semantics, and recent history points to adjacent denyCommands/security policy work.

Owner confidence: high

Options:

- **Warn and continue (recommended):** Emit write-time warnings for unknown or pattern-like deny entries using the audit vocabulary, but keep the write valid so plugin/custom command IDs are not blocked.
- **Fail closed:** Reject unknown or pattern-like deny entries at config write time, accepting compatibility risk unless a plugin-aware exemption is designed first.
- **Stay audit-only:** Keep config writes permissive and rely on `openclaw security audit` to report ineffective deny entries after the fact.

Yes, at source level. Current main accepts arbitrary `gateway.nodes.denyCommands` strings through schema/config write code, runtime only applies exact deny matches, and audit reports ineffective entries later; I did not run the CLI because this cleanup review is read-only.

Unclear until maintainers choose warning versus failure semantics. A warning-first validator in the shared config mutation path looks safest because plugin and custom command IDs may be valid outside the built-in vocabulary.

## Summary

Keep open: current main and v2026.6.11 still accept arbitrary `gateway.nodes.denyCommands` strings at config-write time, while ineffective entries are only flagged later by security audit. The remaining blocker is a maintainer/security decision on warn-only versus fail-closed behavior for plugin or custom command IDs.

## What This Changes

The issue requests write-time feedback when `gateway.nodes.denyCommands` contains unknown or invalid command names.

## Best Possible Solution

Add maintainer-approved warning-first config mutation feedback for direct and ancestor `gateway.nodes.denyCommands` writes, reusing the audit/runtime command vocabulary while preserving plugin and custom command IDs unless maintainers explicitly choose fail-closed behavior.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `gateway.nodes.denyCommands` config writes warn and continue, fail closed, or stay audit-only when entries are unknown, pattern-like, or provided by plugins/custom nodes?

Rationale: The code path is clear, but the security/product contract is not: fail-closed validation improves safety for typos while warning-only behavior avoids blocking valid plugin or future node command IDs.

Likely owner: steipete

Owner reason: The decision affects security posture and gateway command policy semantics, and this history points to recent denyCommands/security policy ownership.

Owner confidence: high

Options:

- **Warn and continue (recommended):** Emit write-time warnings for unknown or pattern-like deny entries using the audit vocabulary, but keep the write valid so plugin/custom command IDs are not blocked.
- **Fail closed:** Reject unknown or pattern-like deny entries at config write time, accepting the compatibility risk for plugin/custom commands unless a registry-aware exemption is added first.
- **Stay audit-only:** Keep config writes permissive and rely on `openclaw security audit` to report ineffective deny entries after the fact.

## Reproduction Assessment

Yes at source level: current main accepts arbitrary `gateway.nodes.denyCommands` strings through schema/config write code, while runtime only applies exact deny matches and audit reports ineffective entries later. I did not run the CLI because this cleanup review is read-only.

## Solution Assessment

Unclear until maintainers choose warning versus failure semantics. A warning-first validator in the shared config mutation path looks safest because plugin and custom command IDs may be valid outside the built-in vocabulary.

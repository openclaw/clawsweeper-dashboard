## Summary

Keep open: current main and the latest release still accept arbitrary `gateway.nodes.denyCommands` strings through the config write path, with ineffective entries only surfaced later by security audit. The remaining blocker is a maintainer/security decision on warning-first versus fail-closed semantics for unknown, pattern-like, plugin, and custom command IDs.

## What This Changes

Warn or fail during `openclaw config set` when `gateway.nodes.denyCommands` contains invalid command names before audit-time detection.

## Best Possible Solution

Add maintainer-approved warning-first config mutation feedback for direct and ancestor `gateway.nodes.denyCommands` writes, reusing the audit/runtime command vocabulary while avoiding rejection of plausible plugin or custom command IDs.

## Maintainer Decision

Question: Should `gateway.nodes.denyCommands` config writes warn or fail for unknown and pattern-like entries, and how should plugin/custom command IDs be treated?

Rationale: The source-level bug is clear, but the permanent behavior changes a security-sensitive config boundary where fail-closed validation can break valid custom/plugin command policy.

Likely owner: steipete

Owner confidence: high

Options:

- **Warn first for unknown entries (recommended):** Emit a write-time warning with audit-style suggestions while still allowing custom and plugin command IDs to be stored.
- **Fail closed for invalid built-ins:** Reject unknown or pattern-like entries only after defining a plugin-aware known-command vocabulary and upgrade expectations.
- **Keep audit-only detection:** Leave config writes permissive and rely on `openclaw security audit` to report ineffective denylist entries later.

## Reproduction Assessment

Yes, at source level. Current main accepts arbitrary `gateway.nodes.denyCommands` strings through schema and config mutation, runtime only removes exact command IDs, and audit reports ineffective entries later.

## Solution Assessment

Unclear until maintainers choose warning versus fail-closed behavior. A warning-first validator in the shared config mutation path looks like the narrowest maintainable solution because plugin/custom command IDs may be valid outside the built-in vocabulary.

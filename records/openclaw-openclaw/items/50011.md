## Summary

Keep open: current main and latest release still accept `gateway.nodes.denyCommands` as plain strings at config-write time, while exact runtime matching makes typoed entries ineffective and security audit only reports them later. The issue is valid, but the fix needs maintainer direction because hard failure could reject valid plugin/custom command IDs; the open fork fix PRs are conflicting and not a safe canonical landing path.

## What This Changes

The issue requests config-write-time warning or failure when `gateway.nodes.denyCommands` contains command names that are not known to the node command registry.

## Best Possible Solution

Add a maintainer-approved warning-first validator in the shared config mutation path for direct and ancestor `gateway.nodes` writes, reusing the audit/runtime command vocabulary and preserving custom commands introduced through `allowCommands`.

## Reproduction Assessment

Yes, at source level: current main accepts arbitrary `gateway.nodes.denyCommands` strings, runtime only removes exact command IDs, and security audit reports unknown entries only after the config exists. I did not run the CLI because this review is read-only and avoids commands that can mutate local config.

## Solution Assessment

Unclear until maintainers choose warning versus failure semantics. A warning-first validator in `runConfigOperations` looks safer than a schema hard failure because plugin/custom command IDs may be valid even when absent from the built-in vocabulary.

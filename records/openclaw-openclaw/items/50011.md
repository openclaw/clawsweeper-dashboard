## Summary

Keep open: current `main` and latest release still accept arbitrary `gateway.nodes.denyCommands` strings through `openclaw config set` and only report ineffective entries during security audit. The remaining decision is warning-first versus fail-closed behavior for plugin/custom command IDs.

## What This Changes

`gateway.nodes.denyCommands` should warn or fail when `openclaw config set` writes command names that are unknown or likely ineffective.

## Best Possible Solution

Add maintainer-approved warning-first config mutation feedback for direct and ancestor `gateway.nodes.denyCommands` writes, reusing the audit/runtime command vocabulary without rejecting custom command IDs.

## Reproduction Assessment

Yes at source level: current `main` accepts arbitrary `gateway.nodes.denyCommands` strings through the schema and config write path, while the runtime only applies exact deny matches and audit reports ineffective entries later.

## Solution Assessment

Unclear until maintainers choose warning versus failure semantics. A warning-first validator in the shared config mutation path looks safest because plugin/custom command IDs may be valid outside the built-in vocabulary.

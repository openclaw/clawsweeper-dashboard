## Summary

Keep open: current main and the latest release still validate ineffective gateway.nodes.denyCommands only through security audit, not when config set writes the value. ## What This Changes

Warn or fail when gateway.nodes.denyCommands is set to unknown or ineffective command names instead of accepting them silently.

## Best Possible Solution

Add a maintainer-approved warning-first config mutation validator for direct and ancestor gateway.nodes writes that reuses the audit/runtime command vocabulary and preserves custom command flexibility.

## Reproduction Assessment

Yes at source level: current main accepts arbitrary denyCommands strings, runtime exact matching makes unknown entries ineffective, and security audit reports them only after the write. I did not run the CLI because this review is read-only and avoids commands that can mutate config files.

## Solution Assessment

Unclear until maintainers choose warning versus failure semantics. A warning-first validator in the shared config mutation path looks safest because plugin/custom commands may be valid even when absent from the built-in vocabulary.

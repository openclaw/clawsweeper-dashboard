## Summary

Keep open: current main and v2026.6.11 still accept arbitrary `gateway.nodes.denyCommands` strings at config-write time, while ineffective unknown or pattern-like entries are only reported later by security audit. The remaining blocker is maintainer/security direction on warning-first versus fail-closed behavior for plugin or custom command IDs.

## What This Changes

The issue asks for write-time warning or rejection when `gateway.nodes.denyCommands` contains ineffective unknown or pattern-like command names.

## Best Possible Solution

Add maintainer-approved warning-first config mutation feedback for direct and ancestor `gateway.nodes.denyCommands` writes, reusing the audit/runtime command vocabulary while preserving custom and plugin command IDs unless maintainers explicitly choose fail-closed behavior.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `gateway.nodes.denyCommands` config writes warn and continue, fail closed, or stay audit-only when entries are unknown or pattern-like and plugin/custom command IDs may exist?

Rationale: The source-level gap is clear, but the security contract is a human choice because fail-closed validation improves typo safety while warning-only behavior avoids blocking valid future or plugin-owned command IDs.

Likely owner: steipete

Owner reason: This choice affects security posture and Gateway command-policy semantics, and recent history points to adjacent denyCommands/security policy work.

Owner confidence: high

Options:

- **Warn and continue (recommended):** Emit write-time warnings for unknown or pattern-like deny entries using the audit vocabulary, but keep the write valid so plugin/custom command IDs are not blocked.
- **Fail closed:** Reject unknown or pattern-like deny entries at config write time, accepting compatibility risk unless a plugin-aware exemption is added first.
- **Stay audit-only:** Keep config writes permissive and rely on `openclaw security audit` to report ineffective deny entries after the fact.

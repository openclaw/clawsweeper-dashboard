## Summary

Keep open: current main still accepts arbitrary `gateway.nodes.denyCommands` strings through config writes and only reports ineffective entries during `openclaw security audit`. The remaining fix needs maintainer direction on warning versus failure semantics and custom/plugin command handling.

## What This Changes

The issue asks for `openclaw config set` or `security audit --fix` to warn or repair invalid `gateway.nodes.denyCommands` entries at write time instead of only reporting them during audit.

## Best Possible Solution

Add a maintainer-approved warning-first validator in the shared config mutation path for direct and ancestor `gateway.nodes` writes, reusing the audit command vocabulary without hard-rejecting custom/plugin ids by default.

## Reproduction Assessment

Yes, at source level: current main accepts arbitrary denyCommands strings, runtime matching only removes exact command ids, and security audit reports unknown entries later. I did not run the CLI because this review is read-only and avoids commands that can mutate config files.

## Solution Assessment

Unclear until maintainers choose warning versus failure semantics. A warning-first validator in the config mutation path looks safest because custom or plugin command ids may be legitimate even when absent from the built-in vocabulary.

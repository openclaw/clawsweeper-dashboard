## Summary

Keep open: current main and v2026.6.11 still accept `gateway.nodes.denyCommands` as arbitrary strings at config-write time, while ineffective entries are only diagnosed later by the security audit path. The remaining decision is security/product policy for warning-only versus fail-closed validation, especially for custom or plugin command IDs.

## What This Changes

Request write-time validation or warnings when `gateway.nodes.denyCommands` contains command names that are unknown to the node command registry.

## Best Possible Solution

Add registry-aware `config set` warnings for direct and ancestor writes to `gateway.nodes.denyCommands`, reusing the audit vocabulary and suggestions while preserving custom/plugin IDs unless maintainers explicitly choose fail-closed behavior.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `gateway.nodes.denyCommands` write-time validation warn only, fail closed, or remain audit-only when entries are unknown to the current command registry?

Rationale: This is a security boundary and compatibility choice: warning-only reduces false confidence without blocking custom/plugin commands, while fail-closed behavior could break valid operator setups.

Likely owner: steipete

Owner reason: The current schema, node command policy, and audit hardening history all point to this area ownership trail.

Owner confidence: high

Options:

- **Warn on config write (recommended):** Emit actionable warnings for unknown or pattern-like entries during `config set` and keep audit-time findings for later checks.
- **Fail closed on unknowns:** Reject unknown deny entries at write time, but require explicit compatibility handling for plugin and custom command IDs.
- **Keep audit-only:** Leave config writes free-form and rely on `openclaw security audit` to catch ineffective entries after the fact.

## Reproduction Assessment

Yes. Source inspection shows the current schema accepts any string array for `gateway.nodes.denyCommands`, the config write path has no custom deny-command warning, and the audit path later detects ineffective entries; I did not execute the CLI because this review is read-only.

## Solution Assessment

Unclear until maintainer/security direction is chosen. A warning-only write-time validator appears to be the narrowest maintainable fix, while fail-closed writes or `audit --fix` behavior are policy choices.

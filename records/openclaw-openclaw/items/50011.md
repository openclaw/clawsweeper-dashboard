## Summary

Keep open: current main still writes `gateway.nodes.denyCommands` through the normal config mutation path without a node-command registry warning, while the unknown/pattern detection remains in the later security audit path. The remaining blocker is a maintainer/security policy choice for warning-only versus fail-closed behavior with custom or plugin command IDs.

## What This Changes

The issue asks for config-write validation or warnings for invalid `gateway.nodes.denyCommands` entries before relying on `openclaw security audit`.

## Best Possible Solution

Add a maintainer-approved write-time warning that reuses the security audit command catalog and suggestions while preserving custom/plugin command IDs unless maintainers explicitly choose fail-closed behavior.

Question: Should config-write validation for `gateway.nodes.denyCommands` warn on unknown entries, fail closed, or remain audit-only for custom/plugin command compatibility?

Rationale: The source bug is clear, but changing a gateway security-control write path can affect custom or plugin command IDs and operator workflows, so automation should not choose the security policy unilaterally.

Likely owner: Peter Steinberger

Owner reason: Peter has the strongest combined history across security audit hardening, node command catalog behavior, and split audit tests around this surface.

Owner confidence: high

Options:

- **Warn on unknown entries (recommended):** Reuse the audit command catalog and suggestions during `openclaw config set/patch`, but still persist custom or plugin command IDs.
- **Fail closed on unknown entries:** Reject unknown denylist entries during config writes and require an explicit escape hatch or catalog registration story for custom commands.
- **Keep audit-only:** Leave config writes permissive and rely on `openclaw security audit` to diagnose ineffective entries after the fact.

## Reproduction Assessment

Yes. Source inspection shows config set/patch writes run schema and policy checks without invoking the node-command warning logic, while `denyCommands` accepts arbitrary strings in the schema and security audit catches unknown names later.

## Solution Assessment

Unclear until maintainer/security policy is chosen. Warning-only reuse of the audit catalog appears safest because it improves feedback without blocking custom/plugin command IDs.

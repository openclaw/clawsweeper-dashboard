## Summary

This issue remains necessary: current main still falls back from filtered sqlite-vec KNN results to a JavaScript scan that parses stored JSON embeddings, so a large filtered corpus can trade recall preservation for gateway liveness. The linked MMR issue and PR address a separate reranking hot path, not this fallback. Likely related person: christian-lallo (low-confidence routing candidate, based on the detailed live-corpus reproduction and proposed containment direction).

## What This Changes

Prevent memory-core vector search from silently scanning the full JSON-encoded embedding corpus when post-KNN filters exhaust sqlite-vec’s 4,096-result ceiling.

## System Context

Memory Core retrieves candidate chunks with sqlite-vec, then applies provider/model/source filters before returning memory-search results to the agent and gateway. When those filters leave too few KNN candidates, the current fallback reads stored embeddings and computes similarity in JavaScript, which can monopolize the gateway event loop on large corpora.

## Architecture Diagram

flowchart LR
  Query[Memory search query] --> KNN[sqlite-vec KNN candidates]
  KNN --> Filter[Provider, model, and source filters]
  Filter -->|Enough matches| Results[Search results]
  Filter -->|Starved result set| Scan[JSON embedding scan in JavaScript]
  Scan --> Results
  Scan --> Delay[Gateway event-loop delay]

## Best Possible Solution

Define an explicit bounded-retrieval contract that protects gateway liveness, reports clipped recall to the caller, adds regression coverage for filter-starvation behavior, and treats any embedding-storage migration as a separately designed upgrade path.

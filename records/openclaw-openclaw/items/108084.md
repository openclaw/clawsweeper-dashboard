## Summary

This PR should not merge as the canonical fix yet: its snapshot cloning protects objects already stored in the registry, but the production registration path mutates the active plugin record before that record is inserted. The newer competing implementation at https://github.com/openclaw/openclaw/pull/108143 addresses that owner-boundary gap and includes a before/after production-loader transcript, but it remains open, so this PR should stay open until maintainers select and land a viable canonical fix.

## What This Changes

The branch shallow-clones registration records, metadata arrays, map values, and dates in plugin transaction snapshots while retaining nested plugin-owned runtime objects by reference, with rollback regression tests.

## Best Possible Solution

Use one transaction-owner implementation that snapshots the active PluginRecord plus mutable registry envelopes across every loader caller, preserves callback and class-instance identity, and proves the before/after behavior through the production loader; then close the redundant competing branches.

## Reproduction Assessment

Yes from source: the active PluginRecord is mutated during registration before insertion into the registry, so a registry-only snapshot cannot restore that record after failure. This PR's tests reproduce manual registry mutations, while the competing PR supplies the production-loader before/after path.

## Solution Assessment

No. Cloning registry-contained records is a plausible isolation hardening, but the narrowest complete repair belongs at the transaction owner and must include the active record and all current loader callers without cloning opaque runtime objects.

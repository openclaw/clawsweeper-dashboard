## Summary

Keep open: current main and v2026.6.11 still fail closed when a trusted-proxy request lacks the configured identity header, and adding a fallback/default identity remains a security-sensitive Gateway auth policy decision.

## What This Changes

The issue requests a trusted-proxy fallback/default identity for cases where a trusted proxy reaches the Gateway without the configured identity header.

## Best Possible Solution

Keep this open for maintainer/security review and either approve a tightly constrained opt-in fallback identity or document no-identity Cloudflare WebSocket setups as unsupported for trusted-proxy auth.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should trusted-proxy auth support an explicit fallback identity when a configured trusted proxy reaches the Gateway without the identity header?

Rationale: The choice changes who OpenClaw authenticates as when the upstream proxy provides no per-user identity, affecting Gateway authorization, Control UI access, session scoping, and operator trust boundaries.

Likely owner: vincentkoc

Owner reason: They are assigned on the issue and provided the maintainer-side separation from related trusted-proxy fallback work.

Owner confidence: high

Options:

- **Keep fail-closed and document unsupported (recommended):** Reject missing identity headers in trusted-proxy mode and document Cloudflare IP-whitelist/no-identity WebSocket deployments as requiring password auth, Tailscale Serve, or a proxy path that reliably forwards identity.
- **Accept narrow opt-in fallback:** Add a named fallback identity only with explicit config, proxy-owned required evidence, allowUsers validation, security audit warnings, and regression coverage.
- **Defer to broader auth policy design:** Keep this issue as canonical input while maintainers design a more general identity-bearing proxy policy instead of adding a one-off fallback key.

Yes. Source inspection gives a high-confidence path: a trusted-proxy request that reaches `authorizeTrustedProxy` without the configured user header returns `trusted_proxy_user_missing`; I did not live-reproduce the Cloudflare Tunnel WebSocket header drop itself.

## Solution Assessment

Unclear pending maintainer intent. A simple `defaultUser` key would solve the reported setup, but it is not clearly the best fix unless maintainers accept the security tradeoff and define strict opt-in rules.

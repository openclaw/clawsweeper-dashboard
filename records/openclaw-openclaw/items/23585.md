## Summary

Keep open. Current main and the latest inspected release still reject trusted-proxy requests when the configured identity header is absent, and adding a fallback identity would change a security-sensitive auth boundary that needs maintainer approval.

## What This Changes

The issue requests a trusted-proxy `defaultUser` or `fallbackUser` option for trusted proxy requests that come from a configured proxy but lack the configured identity header.

## Best Possible Solution

Keep trusted-proxy identity validation fail-closed unless maintainers approve a narrow explicit single-principal fallback mode with source, loopback, allowlist, audit, docs, and regression-test rules.

## Reproduction Assessment

Yes for the OpenClaw source path: current main deterministically rejects a trusted-proxy request without the configured identity header, and a focused test asserts `trusted_proxy_user_missing`. I did not live-reproduce Cloudflare's WebSocket header stripping.

## Solution Assessment

Unclear pending security policy. The requested `defaultUser` or `fallbackUser` option is mechanically plausible, but it changes the trusted-proxy trust model; fail-closed identity headers or a documented alternate auth path may remain the safer product answer.

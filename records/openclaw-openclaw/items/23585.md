## Summary

Keep open: current main and v2026.6.11 still reject trusted-proxy requests when the configured identity header is absent, and adding a fallback identity would change a security-sensitive Gateway auth boundary that needs maintainer approval.

## What This Changes

The issue requests a trusted-proxy `defaultUser` or `fallbackUser` config option for trusted proxy requests whose configured identity header is absent, especially Cloudflare WebSocket upgrade paths.

## Best Possible Solution

Keep trusted-proxy identity validation fail-closed by default unless maintainers approve a narrow explicit single-principal fallback mode with config, schema, docs, audit guidance, loopback/source/header rules, allowlist semantics, and regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should trusted-proxy auth support an explicit fallback identity when the configured identity header is absent on a request from a trusted proxy source?

Rationale: The implementation path is mechanically clear, but it changes the auth boundary from per-request identity evidence to proxy-source plus configured principal, which automation should not decide.

Likely owner: vincentkoc

Owner reason: This person is assigned, already separated this report from the local-direct fallback cluster, and has recent commits on adjacent trusted-proxy auth boundary behavior.

Owner confidence: high

Options:

- **Approve narrow fallback mode (recommended):** Add an explicit single-principal fallback config with fail-closed defaults, audit/docs/schema updates, and tests for proxy source, loopback, required headers, origin, and allowlist semantics.
- **Keep fail-closed identity headers:** Reject headerless trusted-proxy identity and document Cloudflare Zero Trust IP-whitelist/no-identity WebSocket setups as unsupported for this auth mode.
- **Require live Cloudflare proof first:** Ask for reproducible Cloudflare Tunnel proof before deciding whether OpenClaw should add a fallback identity surface.

## Reproduction Assessment

Yes for the OpenClaw source path: current main deterministically rejects trusted-proxy requests without the configured identity header, and a focused test asserts `trusted_proxy_user_missing`. I did not live-reproduce Cloudflare's WebSocket header stripping.

## Solution Assessment

Unclear pending maintainer/security approval. The requested `defaultUser` or `fallbackUser` option is mechanically plausible, but it changes the trusted-proxy trust model; the safer baseline is fail-closed identity headers unless a narrow single-principal mode is explicitly accepted.

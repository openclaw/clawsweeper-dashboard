## Summary

Keep open. Current main still rejects trusted-proxy requests when the configured identity header is absent, and the only fallback on this path is the separate same-host local-direct password fallback. The requested default identity would add a security-sensitive auth/config surface, so it needs maintainer and security review rather than cleanup closure or autonomous repair.

## What This Changes

The issue requests a trusted-proxy `defaultUser` or `fallbackUser` option for deployments where a trusted proxy admits the request but does not forward an identity header on WebSocket upgrades.

## Best Possible Solution

Keep the issue open for maintainer/security review; if accepted, add an explicit trusted-proxy fallback identity contract across config types, schema, docs, audit guidance, and auth tests, and if rejected, document no-identity Cloudflare WebSocket setups as unsupported with safer alternatives.

## Reproduction Assessment

Yes from source inspection: current main deterministically returns `trusted_proxy_user_missing` when a trusted-proxy request lacks the configured identity header, and tests assert that behavior. I did not run a live Cloudflare Tunnel/WebSocket repro in this read-only review.

## Solution Assessment

Unclear as requested: a fallback user is a plausible operator escape hatch, but it is not automatically the best fix because it changes identity semantics; maintainers should choose between an explicit fallback contract, stronger required-header guidance, or documenting no-identity Cloudflare WebSocket paths as unsupported.

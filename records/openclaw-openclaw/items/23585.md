## Summary

Keep open: current main and the latest release still require a trusted-proxy identity header and reject headerless trusted-proxy requests; adding a fallback/default identity would create a new security-sensitive auth/config surface that needs maintainer approval.

## What This Changes

The issue requests a trusted-proxy fallback/default user identity for trusted proxy requests whose configured identity header is absent, especially Cloudflare WebSocket upgrades.

## Best Possible Solution

Maintainers should either keep trusted-proxy auth fail-closed and document no-identity Cloudflare/IP-whitelist WebSocket setups as unsupported, or explicitly approve a fallback identity option with schema, docs, audit warnings, and auth tests that define the security boundary.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should trusted-proxy auth accept a configured fallback/default identity when the request comes from a trusted proxy but the configured identity header is absent?

Rationale: The requested behavior changes the Gateway auth trust boundary from per-request proxy-provided identity to operator-configured identity for headerless traffic, and repository policy treats fallback and auth/config surfaces as compatibility- and security-sensitive.

Likely owner: vincentkoc

Owner reason: The live issue is assigned to vincentkoc and the recent trusted-proxy origin-check work is in this same security boundary.

Owner confidence: high

Options:

- **Keep fail-closed (recommended):** Continue requiring the proxy identity header and document Cloudflare Zero Trust paths that do not forward identity on WebSocket upgrades as unsupported for trusted-proxy identity auth.
- **Add explicit fallback identity:** Add a new trusted-proxy config field only with strict allowlist, required-header, origin/device-scope, audit, docs, and regression-test rules.
- **Use existing local password fallback only:** Keep fallback limited to same-host direct callers with gateway.auth.password and require external browser/WebSocket traffic to preserve proxy identity headers.

## Reproduction Assessment

Yes at source level: a trusted-proxy request that reaches authorizeTrustedProxy without the configured userHeader returns trusted_proxy_user_missing, and current config/schema expose no fallback identity option. I did not run a live Cloudflare Tunnel reproduction.

## Solution Assessment

Unclear until maintainer/security review decides the auth boundary; the safest current implementation is fail-closed, while the requested fallback would need an explicit, narrow config contract and audit guidance if accepted.

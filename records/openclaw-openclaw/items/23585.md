## Summary

Keep open: current main and the latest release still require a non-blank trusted-proxy identity header and only fall back to password for local-direct callers, not for real trusted-proxy WebSocket requests missing the user header. The requested fallback/default identity changes a security-sensitive auth boundary, so it needs maintainer/security approval before implementation.

## What This Changes

Request to add a trusted-proxy fallback/default user option when a request comes from a trusted proxy but the configured identity header is absent.

## Best Possible Solution

Keep this open for maintainer/security review; if accepted, implement an explicit opt-in fallback identity across config types, strict schema, docs, audit guidance, and auth tests, and if rejected, document Cloudflare Zero Trust no-identity WebSocket setups as unsupported for trusted-proxy auth.

Rationale: This is not a narrow bug fix: it changes who OpenClaw authenticates as when the upstream proxy provides no per-user identity, which affects Gateway authorization, Control UI access, session scoping, and operator trust boundaries.

Owner confidence: high

Options:

- **Keep fail-closed and document unsupported (recommended):** Reject missing identity headers in trusted-proxy mode and document Cloudflare IP-whitelist/no-identity WebSocket deployments as requiring password auth, Tailscale Serve, or a proxy path that forwards identity.
- **Accept a narrow opt-in fallback:** Add a named fallback identity only with explicit config, required proxy-owned headers or signed assertions, allowUsers validation, security audit warnings, and regression coverage.
- **Defer to a broader auth redesign:** Keep this issue open as canonical input while designing a more general identity-bearing proxy policy instead of adding a one-off fallback key.

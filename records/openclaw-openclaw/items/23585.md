## Summary

Keep open: current main and the latest release still require a non-blank trusted-proxy identity header, and the requested fallback/default identity would change a security-sensitive Gateway auth boundary.

## What This Changes

Request adding trusted-proxy default/fallback identity config so a trusted proxy request without the configured user header can authenticate as a configured user.

## Best Possible Solution

Keep trusted-proxy identity validation fail-closed by default unless maintainers approve a narrow explicit single-principal fallback mode with config, schema, docs, audit guidance, loopback/source/header rules, allowlist semantics, and regression coverage.

## Maintainer Decision

Kind: security_boundary

Question: Should trusted-proxy auth support an explicit fallback identity when a request from a trusted proxy source lacks the configured identity header?

Rationale: The implementation shape is mechanically clear, but it changes Gateway auth from requiring per-request proxy identity evidence to allowing proxy-source plus configured-principal trust.

Likely owner: vincentkoc

Owner reason: This person is assigned, distinguished this issue from adjacent trusted-proxy fallback work, and has recent commits in the trusted-proxy auth path.

Owner confidence: high

Options:

- **Approve narrow fallback mode (recommended):** Add an explicit single-principal fallback config with fail-closed defaults, audit/docs/schema updates, and tests for proxy source, loopback, required headers, origin policy, and allowlist semantics.
- **Keep fail-closed:** Document Cloudflare Zero Trust IP-whitelist or no-identity WebSocket setups as unsupported for trusted-proxy auth and point users to password auth, Tailscale Serve, or a proxy path that forwards identity headers.
- **Require live Cloudflare proof first:** Ask for a reproducible Cloudflare Tunnel/WebSocket proof before deciding whether OpenClaw should add this fallback identity surface.

## Reproduction Assessment

Yes for the OpenClaw source path: current main deterministically rejects trusted-proxy requests without the configured identity header, and a focused test asserts trusted_proxy_user_missing. I did not live-reproduce Cloudflare's WebSocket header stripping.

## Solution Assessment

Unclear pending maintainer/security approval. The requested defaultUser/fallbackUser option is mechanically plausible, but it changes the trusted-proxy trust model; the safer baseline is fail-closed identity headers unless a narrow single-principal mode is explicitly accepted.

## Summary

Keep open. Current main and v2026.6.11 still require a trusted-proxy identity header and reject headerless requests, while adding a fallback/default user would change a security-sensitive Gateway auth boundary that needs maintainer approval.

## What This Changes

The issue requests a `defaultUser` or `fallbackUser` trusted-proxy auth option for requests from trusted proxy sources when the configured identity header is absent.

## Best Possible Solution

Keep trusted-proxy identity validation fail-closed by default unless maintainers approve a narrow explicit single-principal fallback mode with schema, docs, audit guidance, loopback/source/header rules, allowlist semantics, and regression coverage.

Question: Should trusted-proxy auth support an explicit fallback identity when the configured identity header is absent on a request from a trusted proxy source?

Rationale: The implementation shape is mechanically clear, but it changes the Gateway auth trust boundary from per-request identity evidence to proxy-source plus configured principal, which automation should not decide.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Approve narrow fallback mode (recommended):** Add an explicit single-principal fallback config with fail-closed defaults, audit/docs/schema updates, and tests for proxy source, loopback, required headers, browser origin, and allowlist semantics.
- **Keep fail-closed:** Reject headerless trusted-proxy identity and document Cloudflare Zero Trust IP-whitelist or no-identity WebSocket setups as unsupported for trusted-proxy auth.
- **Require live Cloudflare proof first:** Ask for a reproducible Cloudflare Tunnel proof before deciding whether OpenClaw should add a fallback identity surface.

## Reproduction Assessment

Yes for the OpenClaw source path: current main deterministically rejects trusted-proxy requests without the configured identity header, and a focused test asserts `trusted_proxy_user_missing`. I did not live-reproduce Cloudflare's WebSocket header stripping.

## Solution Assessment

Unclear pending maintainer/security approval. The requested `defaultUser` or `fallbackUser` option is plausible, but it changes the trusted-proxy trust model; the safer baseline is fail-closed identity headers unless a narrow single-principal mode is explicitly accepted.

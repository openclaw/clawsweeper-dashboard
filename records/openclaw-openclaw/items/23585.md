## Summary

Keep open. Current main and the latest release still reject trusted-proxy requests when the configured identity header is absent, and adding a default identity would change a security-sensitive auth boundary rather than repair a broken existing contract.

## What This Changes

Request adding a trusted-proxy default or fallback user for trusted proxy requests that lack the configured identity header, especially Cloudflare Zero Trust WebSocket upgrade paths.

## Best Possible Solution

Keep this open for security/product review; if accepted, add one explicit trusted-proxy fallback identity contract across config types, zod/schema output, docs, audit guidance, and auth tests, and if rejected, document Cloudflare no-identity WebSocket setups as unsupported with safer proxy/password alternatives.

## Maintainer Decision

Kind: security_boundary

Question: Should trusted-proxy mode accept an explicitly configured fallback identity when a request comes from a configured trusted proxy but lacks the configured identity header?

Rationale: The requested option would deliberately change fail-closed proxy identity semantics and could authenticate a request that carries no user identity, which automation should not choose without maintainer security intent.

Likely owner: vincentkoc

Owner reason: This issue is assigned to vincentkoc and they already routed it as separate from the local-direct trusted-proxy fallback cluster.

Owner confidence: high

Options:

- **Approve a narrow fallback identity:** Add an explicit fallback/default identity option with strict trusted proxy source checks, allowlist interaction, security audit guidance, docs, and regression tests for missing-header proxy requests.
- **Reject fallback identity (recommended):** Keep trusted-proxy identity header presence mandatory and document Cloudflare IP-whitelist/no-identity WebSocket paths as unsupported unless the proxy forwards identity reliably or the deployment uses the local password path where appropriate.
- **Require a stronger proxy assertion first:** Allow fallback identity only when an additional proxy-owned required header or signed assertion proves the request passed the edge policy even though the user identity header is absent.

## Reproduction Assessment

Yes for the OpenClaw source path: current main deterministically returns `trusted_proxy_user_missing` when the configured user header is absent, and a focused auth test asserts that behavior. I did not live-reproduce Cloudflare's WebSocket header stripping.

## Solution Assessment

Unclear: a default user is a plausible operator feature, but it is not automatically the best fix because it changes a fail-closed auth boundary. A maintainer-approved security design or an explicit unsupported-deployment doc path is safer than an automated repair PR.

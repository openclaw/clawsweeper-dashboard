## Summary

Keep open: current main and latest release still fail closed when a trusted-proxy request lacks the configured identity header, and the requested fallback/default identity changes a security-sensitive Gateway auth boundary that needs maintainer approval.

## What This Changes

The issue requests an explicit trusted-proxy fallback/default user when the configured identity header is absent on proxied WebSocket requests.

## Best Possible Solution

Keep this open for maintainer/security review; if accepted, implement an explicit opt-in fallback identity across config types, strict schema, docs, audit guidance, and auth tests, and if rejected, document Cloudflare Zero Trust no-identity WebSocket setups as unsupported for trusted-proxy auth.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should trusted-proxy auth support an explicit fallback identity when a request comes from a configured trusted proxy but the configured identity header is absent?

Rationale: Current behavior deliberately fails closed without an identity header; accepting a fixed user would change Gateway authorization, Control UI access, session scoping, and operator trust boundaries.

Likely owner: vincentkoc

Owner reason: vincentkoc is assigned and already framed this issue as the distinct trusted-proxy missing-header policy case.

Owner confidence: high

Options:

- **Keep fail-closed and document unsupported (recommended):** Reject missing identity headers in trusted-proxy mode and document Cloudflare IP-whitelist/no-identity WebSocket deployments as requiring password auth, Tailscale Serve, or a proxy path that reliably forwards identity.
- **Accept a narrow opt-in fallback:** Add a named fallback identity only with explicit config, proxy-owned required evidence, allowUsers validation, security audit warnings, and regression coverage.
- **Defer to broader auth policy design:** Keep this issue as canonical input while maintainers design a more general identity-bearing proxy policy instead of adding a one-off fallback key.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence OpenClaw path: a trusted-proxy request that reaches `authorizeTrustedProxy` without the configured user header returns `trusted_proxy_user_missing`; I did not live-reproduce the Cloudflare Tunnel WebSocket header drop itself.

## Solution Assessment

Unclear pending maintainer intent. A simple `defaultUser` key would solve the reported setup, but it is not clearly the best fix unless maintainers accept the security tradeoff and define strict opt-in rules.

## Summary

Keep open: current main and the latest shipped release still reject trusted-proxy requests when the configured identity header is absent, while adding a fallback identity would change a security-sensitive Gateway auth boundary that needs maintainer approval.

## What This Changes

The issue requests a trusted-proxy default/fallback user for requests from a configured trusted proxy when the identity header is absent, especially on Cloudflare WebSocket upgrade traffic.

## Best Possible Solution

Keep trusted-proxy identity validation fail-closed by default unless maintainers approve a narrow explicit single-principal fallback mode with config, schema, docs, audit guidance, loopback/source/header rules, allowlist semantics, and regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should trusted-proxy auth support an explicit fallback identity when a request comes from a configured trusted proxy source but lacks the configured user identity header?

Rationale: The code change is mechanically clear, but it changes the Gateway auth trust boundary from per-request identity evidence to proxy-source plus configured principal, which automation should not decide.

Likely owner: vincentkoc

Owner reason: vincentkoc is assigned, has already routed this issue separately from the local-direct fallback cluster, and owns recent nearby trusted-proxy auth policy changes.

Owner confidence: high

Options:

- **Approve narrow fallback identity (recommended):** Add a default-off single-principal fallback config with strict source/header/loopback/allowlist semantics, audit/docs/schema updates, and focused auth/control-ui coverage.
- **Keep fail-closed identity headers:** Continue rejecting headerless trusted-proxy requests and document Cloudflare Zero Trust IP-whitelist or no-identity WebSocket setups as unsupported for trusted-proxy auth.
- **Require live Cloudflare proof first:** Ask for a reproducible Cloudflare Tunnel trace before deciding whether OpenClaw should add a fallback identity surface.

## Reproduction Assessment

Yes for the OpenClaw source path: current main deterministically rejects trusted-proxy requests without the configured identity header, and a focused test asserts trusted_proxy_user_missing. I did not live-reproduce Cloudflare's WebSocket header stripping.

## Solution Assessment

Unclear pending maintainer/security approval. The requested defaultUser or fallbackUser option is mechanically plausible, but it changes the trusted-proxy trust model; the safer baseline is fail-closed identity headers unless a narrow single-principal mode is explicitly accepted.

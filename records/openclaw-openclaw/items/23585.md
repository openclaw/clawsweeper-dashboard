## Summary

Keep open. Current main and v2026.6.11 still reject trusted-proxy requests when the configured identity header is absent; related merged work covers loopback admission and same-host password fallback, not a headerless default identity, and accepting one needs maintainer/security approval.

## What This Changes

The issue requests a trusted-proxy default or fallback user config that authenticates trusted-proxy requests when the configured identity header is absent.

## Best Possible Solution

Keep trusted-proxy identity validation fail-closed unless maintainers approve a narrow single-principal fallback mode with explicit config, source/loopback/header rules, allowlist semantics, audit/docs updates, and regression coverage.

## Reproduction Assessment

Yes for the OpenClaw source path: current auth tests and code still reject a trusted-proxy request when the configured identity header is absent. I have not live-reproduced the Cloudflare WebSocket header stripping.

## Solution Assessment

Unclear pending security policy. The requested defaultUser/fallbackUser is mechanically plausible, but it changes the trusted-proxy trust model; safer defaults are fail-closed identity headers, a documented alternate auth path, or a maintainer-approved single-principal mode.

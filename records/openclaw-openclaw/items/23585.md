## Summary

Keep open: current main still rejects trusted-proxy requests when the configured identity header is absent, and adding a default/fallback user would change a security-sensitive auth boundary that needs maintainer approval.

## What This Changes

Request adding a trusted-proxy default/fallback user so Cloudflare/WebSocket requests from a trusted proxy can authenticate when the configured identity header is absent.

## Best Possible Solution

Keep trusted-proxy identity validation fail-closed by default unless maintainers approve a narrow explicit single-principal fallback mode with config, schema, docs, audit guidance, loopback/source/header rules, allowlist semantics, and regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should trusted-proxy auth support an explicit fallback identity when the configured identity header is absent on a request from a trusted proxy source?

Rationale: The implementation path is mechanically clear, but it changes trusted-proxy auth from per-request identity evidence to proxy-source plus configured principal, which is a security and product boundary automation should not choose.

Likely owner: vincentkoc

Owner reason: This person is assigned on the live issue, separated this request from adjacent trusted-proxy issues, and has recent commits on the relevant auth boundary.

Owner confidence: high

Options:

- **Approve narrow fallback mode (recommended):** Add an explicit single-principal fallback config with fail-closed defaults, audit/docs/schema updates, and tests for proxy source, loopback, required headers, and allowlist semantics.
- **Keep fail-closed:** Reject headerless trusted-proxy identity and document Cloudflare Zero Trust IP-whitelist or no-identity WebSocket setups as unsupported for trusted-proxy auth.
- **Require live Cloudflare proof first:** Ask for a reproducible Cloudflare Tunnel proof before deciding whether OpenClaw should add a fallback identity surface.

## Reproduction Assessment

Yes for the OpenClaw source path: current main deterministically rejects trusted-proxy requests without the configured identity header, and a focused test asserts `trusted_proxy_user_missing`. I did not live-reproduce Cloudflare's WebSocket header stripping.

## Solution Assessment

Unclear pending maintainer/security approval. The requested `defaultUser` or `fallbackUser` option is mechanically plausible, but it changes the trusted-proxy trust model; the safer baseline is fail-closed identity headers unless a narrow single-principal mode is explicitly accepted.

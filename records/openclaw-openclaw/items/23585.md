## Summary

Keep open. Current `origin/main` and the latest release still require a trusted-proxy identity header and return `trusted_proxy_user_missing` when it is absent; adding a fallback/default identity is a security-sensitive new config surface that needs maintainer approval.

## What This Changes

The issue requests a trusted-proxy fallback/default user identity when the configured proxy identity header is absent on WebSocket requests.

## Best Possible Solution

Keep trusted-proxy identity validation fail-closed by default unless maintainers approve a narrow explicit single-principal fallback mode with config, schema, docs, audit guidance, source/loopback/header/allowlist rules, and regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should trusted-proxy auth support an explicit fallback identity when the configured identity header is absent on a request from a trusted proxy source?

Rationale: The code change is mechanically clear, but it changes the trusted-proxy trust boundary from per-request identity evidence to proxy-source plus configured principal, which automation should not decide.

Likely owner: vincentkoc

Owner reason: This person is assigned to the issue, already separated it from adjacent fallback bugs, and has recent work on the trusted-proxy auth boundary.

Owner confidence: high

Options:

- **Approve narrow fallback mode (recommended):** Add an explicit single-principal fallback config with fail-closed defaults, audit/docs/schema updates, and tests for proxy source, loopback, required headers, and allowlist semantics.
- **Keep fail-closed:** Reject headerless trusted-proxy identity and document Cloudflare Zero Trust IP-whitelist/no-identity WebSocket setups as unsupported for trusted-proxy auth.
- **Require live Cloudflare proof first:** Ask for a reproducible Cloudflare Tunnel proof before deciding whether OpenClaw should add a fallback identity surface.

## Reproduction Assessment

Yes for the OpenClaw source path: current `origin/main` deterministically rejects trusted-proxy requests without the configured identity header, and a focused test asserts `trusted_proxy_user_missing`. I did not live-reproduce Cloudflare's WebSocket header stripping.

## Solution Assessment

Unclear pending maintainer/security approval. The requested `defaultUser`/`fallbackUser` option is mechanically plausible, but it changes the trusted-proxy trust model; the safer baseline is fail-closed identity headers unless a narrow single-principal mode is explicitly accepted.

## Summary

Keep open. Current main and the latest release still reject trusted-proxy requests when the configured identity header is absent, and adding a default/fallback identity remains a security-sensitive Gateway auth product decision rather than a cleanup close.

## What This Changes

The issue requests an explicit trusted-proxy fallback/default user identity when the configured identity header is missing on WebSocket requests from a trusted proxy.

## Best Possible Solution

Keep trusted-proxy identity validation fail-closed by default unless maintainers approve a narrow explicit single-principal fallback mode with config, schema, docs, audit guidance, loopback/source/header rules, allowlist semantics, and regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should trusted-proxy auth support an explicit fallback identity when a request from a trusted proxy source lacks the configured identity header?

Rationale: The implementation shape is clear, but the choice changes the Gateway auth trust boundary from per-request identity evidence to proxy-source plus configured principal, which automation should not decide.

Likely owner: vincentkoc

Owner reason: vincentkoc is assigned, supplied the key related-issue distinction, and has recent commits on the adjacent trusted-proxy auth boundary.

Owner confidence: high

Options:

- **Approve narrow fallback mode (recommended):** Add an explicit single-principal fallback config with fail-closed defaults, audit/docs/schema updates, and tests for proxy source, loopback, required headers, and allowlist semantics.
- **Keep fail-closed identity headers:** Continue rejecting headerless trusted-proxy requests and document Cloudflare Zero Trust IP-whitelist/no-identity WebSocket setups as unsupported for trusted-proxy auth.
- **Require live Cloudflare proof first:** Ask for a reproducible Cloudflare Tunnel proof before deciding whether OpenClaw should add a fallback identity surface.

## Reproduction Assessment

Yes for the OpenClaw source path: current main deterministically rejects trusted-proxy requests without the configured identity header, and a focused test asserts trusted_proxy_user_missing. I did not live-reproduce Cloudflare's WebSocket header stripping.

## Solution Assessment

Unclear pending maintainer/security approval. The requested `defaultUser`/`fallbackUser` option is mechanically plausible, but it changes the trusted-proxy trust model; the safer baseline is fail-closed identity headers unless a narrow explicit mode is accepted.

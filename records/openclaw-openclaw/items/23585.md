## Summary

Keep open. Current main and the latest release still reject trusted-proxy requests when the configured identity header is absent, and adding a fallback identity would change a security-sensitive auth boundary.

## What This Changes

Add an explicit fallback/default user option for trusted-proxy auth when a trusted proxy request lacks the configured identity header.

## Best Possible Solution

Keep trusted-proxy identity validation fail-closed by default unless maintainers approve a narrow explicit single-principal fallback mode with schema, docs, audit guidance, loopback/source/header rules, allowlist semantics, and regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should trusted-proxy auth support an explicit fallback identity when the configured identity header is absent on a request from a trusted proxy source?

Rationale: The code change is mechanically bounded, but it changes the trusted-proxy auth boundary from per-request identity evidence to proxy-source plus configured principal.

Likely owner: vincentkoc

Owner reason: This person is assigned, has the issue discussion context, and authored recent trusted-proxy loopback policy work.

Owner confidence: high

Options:

- **Approve Narrow Fallback (recommended):** Add an explicit single-principal fallback config with fail-closed defaults, audit/docs/schema updates, and tests for proxy source, loopback, required headers, and allowlist semantics.
- **Keep Fail Closed:** Reject headerless trusted-proxy identity and document Cloudflare Zero Trust IP-whitelist/no-identity WebSocket setups as unsupported for trusted-proxy auth.
- **Require Live Cloudflare Proof:** Ask for a reproducible Cloudflare Tunnel proof before deciding whether OpenClaw should add a fallback identity surface.

## Reproduction Assessment

Yes for the OpenClaw source path: current main deterministically rejects trusted-proxy requests without the configured identity header, and a focused test asserts trusted_proxy_user_missing. I did not live-reproduce Cloudflare's WebSocket header stripping.

## Solution Assessment

Unclear pending maintainer/security approval. The requested `defaultUser` or `fallbackUser` option is mechanically plausible, but it changes the trusted-proxy trust model; the safer baseline is fail-closed identity headers unless a narrow single-principal mode is explicitly accepted.

## Summary

Keep open. Current main and v2026.6.11 still reject trusted-proxy requests when the configured identity header is absent, there is no default/fallback identity config or schema surface, and the merged related work only covers local-direct password fallback rather than real trusted-proxy requests missing identity headers.

## What This Changes

The issue requests a trusted-proxy fallback/default identity option for trusted proxy requests where the configured identity header is missing.

## Best Possible Solution

Keep trusted-proxy identity validation fail-closed unless maintainers approve a narrow single-principal fallback mode with explicit config, source/loopback/header rules, allowlist semantics, audit/docs updates, and regression coverage.

## Reproduction Assessment

Yes for the OpenClaw source path: current main deterministically rejects trusted-proxy requests without the configured identity header, and a focused test asserts trusted_proxy_user_missing. I did not live-reproduce Cloudflare's WebSocket header stripping.

## Solution Assessment

Unclear pending security policy. The requested defaultUser/fallbackUser is mechanically plausible, but it changes the trusted-proxy trust model; safer defaults are fail-closed identity headers, a documented alternate auth path, or a maintainer-approved single-principal mode.

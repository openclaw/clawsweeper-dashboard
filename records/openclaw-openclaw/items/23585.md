## Summary

Keep open. Current main and the latest release still reject trusted-proxy requests when the configured identity header is absent, and adding a fallback/default identity would change a security-sensitive Gateway auth boundary that needs maintainer approval.

## What This Changes

Requests a trusted-proxy default or fallback user config option for requests from a trusted proxy when the configured identity header is absent.

## Best Possible Solution

Keep trusted-proxy identity validation fail-closed by default unless maintainers approve a narrow explicit single-principal fallback mode with config, schema, docs, audit guidance, loopback/source/header rules, allowlist semantics, and regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should trusted-proxy auth support an explicit fallback identity when the configured identity header is absent on a request from a trusted proxy source?

Rationale: The implementation shape is mechanically clear, but it changes the trusted-proxy auth boundary from per-request identity evidence to proxy-source plus configured principal, which automation should not decide.

Likely owner: vincentkoc

Owner reason: This person is assigned, has discussion context, and has recent commits on the adjacent trusted-proxy fallback boundary.

Owner confidence: high

Options:

- **Approve narrow fallback mode (recommended):** Add an explicit single-principal fallback config with fail-closed defaults, audit/docs/schema updates, and tests for proxy source, loopback, required headers, and allowlist semantics.
- **Keep fail-closed identity headers:** Reject headerless trusted-proxy identity and document Cloudflare Zero Trust IP-whitelist or no-identity WebSocket setups as unsupported for trusted-proxy auth.
- **Require live Cloudflare proof first:** Ask for a reproducible Cloudflare Tunnel proof before deciding whether OpenClaw should add a fallback identity surface.

## Reproduction Assessment

Yes for the OpenClaw source path: current main deterministically rejects trusted-proxy requests without the configured identity header, and focused tests assert `trusted_proxy_user_missing`. I did not live-reproduce Cloudflare's WebSocket header stripping.

## Solution Assessment

Unclear pending maintainer/security approval. The requested `defaultUser` or `fallbackUser` option is mechanically plausible, but it changes the trusted-proxy trust model; the safer baseline is fail-closed identity headers unless a narrow single-principal mode is explicitly accepted.

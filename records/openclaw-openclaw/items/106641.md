## Label Justifications

- `P1`: Released HTTP-channel deployments consistently lose the `sessions_spawn` workflow with no configuration-level recovery.
- `impact:auth-provider`: The failure is an internal Gateway authorization-scope mismatch between the plugin-route runtime client and the `agent` RPC requirement.

## Summary

This remains necessary on current main: the subagent helper derives the `agent` method’s write scope but only forces a synthetic client for admin-scoped calls, allowing an HTTP plugin-route client with empty scopes to reach the `operator.write` gate. Existing tests verify in-process dispatch but do not verify the required synthetic write scope, and the related open PR addresses the WebSocket device-identity path rather than this scoped-client precedence path.

## What This Changes

Fix HTTP-webhook channel sessions so `sessions_spawn` can dispatch the internal `agent` RPC with its required `operator.write` authority.

## Best Possible Solution

At `callSubagentGateway`, force a synthetic client with the method-derived `operator.write` scope specifically for the internal in-process `agent` dispatch, retain admin scope for lifecycle cleanup, and add coverage proving an empty HTTP plugin-route client cannot override those scopes.

## Solution Assessment

The suggested chokepoint repair is the best general direction, but granting baseline scope to all HTTP plugin routes is too broad; force only the method-derived scope for the trusted internal subagent dispatch.

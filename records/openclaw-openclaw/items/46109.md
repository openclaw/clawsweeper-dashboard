## Summary

Keep open: current main supports SecretRefs, env-template shorthand, redaction/restore, write preflight, CLI workflows, and docs, but the requested first-class source-aware Control UI/config UX is still missing and needs a maintainer security/product decision before implementation.

## What This Changes

The issue requests source-aware `.env`/environment-backed secret configuration UX in Control UI and CLI so secret fields can show config/env/unset state without exposing raw secrets.

## Best Possible Solution

Define the safe metadata boundary first, then add a source-aware SecretInput renderer and metadata flow with masked source labels, resolved/unresolved state, config/env/unset editing, and aligned docs/tests.

Rationale: The requested UX improves secret hygiene, but showing env names, provider aliases, or resolution state can disclose operator setup details, so automation should not choose that boundary alone.

Owner confidence: high

Options:

- **Conservative source-aware UI (recommended):** Show masked source labels and safe resolved/unresolved state, reveal env variable names only where maintainers approve, and keep writes aligned with existing SecretRef configure/apply paths.
- **Minimal read-only badge:** Replace the generic structured placeholder with a safe `SecretRef configured` indicator while leaving editing in Raw/CLI until a fuller design is approved.
- **Defer UI disclosure:** Keep current Control UI behavior and improve docs/CLI guidance only, avoiding new metadata exposure until security review defines policy.

## Summary

Keep open: current main and the latest release still have SecretRef runtime, CLI, redaction, and docs foundations, but the requested source-aware Control UI/config UX is not implemented and needs maintainer security/product direction before an implementation lane is safe.

## What This Changes

The issue requests first-class Control UI and CLI affordances for environment-backed secrets so env-backed values are masked, source-aware, editable as config/env/unset, and not mistaken for missing values.

## Best Possible Solution

Define one safe SecretRef source-awareness contract, then add masked Control UI source badges, env-reference editing, resolved/unresolved diagnostics, and matching CLI/docs behavior on top of the existing SecretRef runtime.

Rationale: The requested UX improves secret hygiene, but exposing environment variable names, provider aliases, or resolution state can reveal operator setup details, so automation should not choose that disclosure boundary alone.

Owner confidence: medium

Options:

- **Conservative Source-Aware UI (recommended):** Show masked source labels and resolved/unresolved state, reveal env variable names only where maintainers approve, and keep writes aligned with existing SecretRef configure/apply paths.

- **Defer UI Disclosure:** Keep current UI behavior and improve docs/CLI guidance only until security review defines the metadata policy.

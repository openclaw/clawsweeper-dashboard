## Summary

Keep open. Current main and the latest release still hardcode deep short-term promotions to `MEMORY.md`; the merged budget/contamination fixes reduce growth and bad entries, but they do not add configurable target routing or the indexing/read semantics that alternate promotion files would need.

## What This Changes

Add memory-core configuration for where short-term promotions are written, instead of always appending promoted entries to `MEMORY.md`.

## Best Possible Solution

Define a product-approved promotion routing model, likely a canonical memory layout with constrained overrides by memory type/source, then update memory-core writing, memory indexing, memory reads, docs, and tests together.

## Reproduction Assessment

Yes. Source inspection shows the current promotion writer always resolves `MEMORY.md` under the workspace; no runtime reproduction was needed because the request is a missing configurable capability, not a failing command path.

## Solution Assessment

Unclear. The requested direction is valid, but a pure free-form file knob is not obviously the best permanent shape; maintainers should choose a constrained routing/layout contract that preserves indexing, read access, bootstrap behavior, and path safety.

## Summary

Keep open. Current main and the latest release still write deep short-term promotions to `MEMORY.md`; merged compaction and contamination fixes reduce symptoms but do not add configurable destination routing or settle the lifecycle/routing design raised in discussion.

## What This Changes

The issue requests a configurable memory-core promotion target so automated short-term promotions can write somewhere other than `MEMORY.md`, with searchable alternate destinations and optional date-based organization.

## Best Possible Solution

Maintainers should define one memory-core promotion routing contract, likely a canonical lane layout with guarded customization, then implement path validation, date tokens, docs/schema alignment, and `memory_search` coverage for every supported destination.

## Reproduction Assessment

Yes. Current source shows both automatic and manual deep promotion resolve the output to `workspaceDir/MEMORY.md`, and the memory-core manifest/docs expose no promotion destination config.

## Solution Assessment

Unclear. A configurable target would address the immediate report, but the June discussion makes the best solution a maintainer product decision around canonical lanes, routing rules, lifecycle metadata, and indexing semantics rather than a raw free-form path knob.

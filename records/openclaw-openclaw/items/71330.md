## Summary

Keep open. Current main and v2026.6.11 still write short-term promotions to root `MEMORY.md`; merged compaction and snippet-hardening work reduce growth but do not provide configurable destinations, routing rules, or the lifecycle semantics raised in the discussion.

## What This Changes

The issue asks for memory-core to let operators configure where short-term promotions are written instead of always appending them to `MEMORY.md`.

## Best Possible Solution

Define one memory-core promotion routing contract, likely with canonical lanes plus safe customization, then implement destination validation, date-token or type-based routing, frontmatter, docs/schema alignment, `memory_search` coverage, and lifecycle coordination.

## Reproduction Assessment

Yes. Source inspection shows current main and v2026.6.11 still write promotions to `workspaceDir/MEMORY.md`, and the docs describe `memory promote --apply` as appending selected candidates into `MEMORY.md`.

## Solution Assessment

Unclear. A configurable target addresses the immediate report, but the best maintainable solution needs maintainer decisions about canonical lanes, routing rules, path safety, indexing, metadata, and lifecycle semantics.

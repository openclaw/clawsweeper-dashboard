## Summary

Keep open: current main and v2026.6.11 still dispatch generic Discord component callbacks to the agent as text plus ordinary sender context, while richer interaction metadata exists only on the plugin interactive handler path. This remains a maintainer API and trust-boundary decision for a typed agent-visible Discord interaction metadata contract.

## What This Changes

The issue requests structured Discord component interaction metadata, including message id, custom id, button label, and clicker identity, in agent-visible button callback context.

## Best Possible Solution

Define and document a typed Discord interaction metadata contract for agent-dispatched component callbacks, populated from the component registry plus Discord interaction payload across buttons, selects, and modals.

Rationale: This changes the public agent inbound context and exposes Discord identifiers and callback data, so maintainers need to choose the schema, trust boundary, and compatibility shape before implementation.

Owner confidence: high

Options:

- **Add Typed Agent Metadata (recommended):** Expose a narrow documented metadata envelope with original message id, action kind, safe callback/custom data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields only in plugin interactive handlers and document that stateful Discord workflows should use plugin callbacks rather than generic agent fallback messages.
- **Start With Sender And Message:** Expose only clicker and originating message ids first, deferring callback payload semantics until a broader inbound metadata contract is settled.

## Solution Assessment

Unclear until maintainers choose the public contract; the requested direction is useful, but the durable fix should be a typed channel/inbound-context API rather than an ad hoc raw Discord payload leak.

## Summary

Keep open: current main and the latest release still route generic Discord component callbacks to agents as text-oriented inbound turns, while richer interaction data is only exposed to Discord plugin interactive handlers. The remaining work is a maintainer product/API decision for a typed agent-visible interaction metadata contract.

## What This Changes

The issue requests structured Discord interaction metadata in agent-visible button callback context, including source message, custom/button data, and clicker identity.

## Best Possible Solution

Define and document a typed Discord interaction metadata contract for generic agent-dispatched component callbacks, populated from the component registry plus sanitized Discord interaction fields across buttons, selects, and modals.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should generic Discord component clicks expose a new agent-visible structured interaction metadata envelope, and which fields should be public versus plugin-only?

Rationale: This changes the public agent inbound context and exposes transport identifiers/callback data, so maintainers need to choose schema shape, compatibility behavior, privacy/security boundary, and docs before implementation.

Likely owner: vincentkoc

Owner reason: The active current-main component callback and plugin-interactive paths are currently blamed to vincentkoc's Discord component refactor.

Owner confidence: high

Options:

- **Add Typed Agent Metadata (recommended):** Expose a narrow documented metadata envelope with source message id, action kind, safe callback/custom data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields only in plugin interactive handlers and document stateful Discord workflows as plugin-callback work rather than generic fallback messages.
- **Start With Message And Sender:** Expose only clicker and originating message ids first, deferring callback payload semantics until a broader inbound metadata contract is settled.

## Reproduction Assessment

Yes, source-based. Current main builds the generic Discord component callback as eventText and finalizes BodyForAgent/RawBody/CommandBody from that text, while custom data/message-id interaction fields remain plugin-handler-only.

## Solution Assessment

Unclear until maintainers choose the public contract. The maintainable path is a typed channel/inbound-context metadata API, not an ad hoc raw Discord payload leak.

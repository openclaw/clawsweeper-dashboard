## Summary

Keep open: current main and the latest release still route generic Discord component callbacks to the agent as formatted text plus ordinary sender context, while richer interaction details remain available only to plugin interactive handlers. This is still a product/API contract decision for agent-visible Discord interaction metadata.

## What This Changes

The issue requests structured Discord button interaction metadata, including original message id, custom/callback id, button label, and clicker identity, in agent callback context.

## Best Possible Solution

Define a typed, documented Discord interaction metadata contract for agent-dispatched component callbacks and populate it from the component registry plus Discord interaction payload across buttons, selects, and modals.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Discord component clicks expose a new agent-visible structured interaction metadata envelope, and which fields should be public versus plugin-only?

Rationale: This changes the public agent inbound context and exposes Discord identifiers/callback data, so maintainers need to choose the schema, trust boundary, and compatibility shape before implementation.

Likely owner: steipete

Owner reason: This issue needs a schema and trust-boundary decision, and steipete has the strongest recent history across the Discord component and plugin SDK contract surfaces.

Owner confidence: high

Options:

- **Add typed agent metadata (recommended):** Expose a narrow documented metadata envelope with message id, action kind, safe custom/callback data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep metadata plugin-only:** Leave rich interaction fields in the plugin interactive-handler API and document that stateful Discord workflows should use plugin callbacks rather than generic agent fallback messages.
- **Start with sender and message ids:** Expose only clicker and originating message identifiers first, deferring custom id and callback payload semantics until the broader inbound metadata contract is settled.

## Reproduction Assessment

Yes, at source level: the current Discord component fallback path builds the agent turn from eventText and ordinary sender/context fields, while original message id, custom id, and structured interaction details are not added to the agent context. I did not run a live Discord button click in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public contract; the requested direction is useful, but the durable fix should be a typed channel/inbound-context API rather than an ad hoc raw Discord payload leak.

## Summary

Keep open: current main and the latest release still expose generic Discord component callbacks to agents as formatted text plus ordinary sender context, while richer interaction details are available only to plugin interactive handlers. This remains a useful but maintainer-owned public API and trust-boundary decision for agent-visible Discord interaction metadata.

## What This Changes

The issue requests structured Discord button interaction metadata, including originating message ID, clicked component/custom ID, and clicker identity, in agent-visible callbacks.

## Best Possible Solution

Define and document a typed Discord interaction metadata contract for agent-dispatched component callbacks, populated from the component registry and Discord interaction payload across buttons, selects, and modals.

## Maintainer Decision

Question: Should generic Discord component clicks expose a new agent-visible structured interaction metadata envelope, and which fields are safe public agent context versus plugin-only callback data?

Rationale: This changes the public agent inbound context and exposes Discord message, user, and callback identifiers, so maintainers need to choose the schema and trust boundary before implementation.

Likely owner: steipete

Owner reason: The current Discord component callback boundary and plugin-interactive metadata path are most strongly tied to this person's recent commits.

Owner confidence: high

Options:

- **Add Typed Agent Metadata (recommended):** Expose a narrow documented envelope with original message id, interaction kind, component id/custom data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields only in plugin interactive handlers and document that stateful Discord workflows should use plugin callbacks rather than generic agent fallback messages.
- **Start With Sender And Message IDs:** Expose only clicker and originating message ids first, deferring callback payload semantics until a broader inbound metadata contract is settled.

Yes, at source level: current main builds generic Discord component callbacks from `eventText` and ordinary sender/context fields, while original message id, custom id, and structured interaction details are not added to the agent context. ## Solution Assessment

Unclear until maintainers choose the public contract; the requested direction is useful, but the durable fix should be a typed channel/inbound-context API rather than an ad hoc raw Discord payload leak.

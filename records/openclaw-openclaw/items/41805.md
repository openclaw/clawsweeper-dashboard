## Summary

Keep open: current main and v2026.6.11 still route generic Discord component callbacks to the agent as plain text plus ordinary sender fields, while richer interaction metadata exists only on the plugin interactive-handler path.

## What This Changes

The issue requests structured Discord button interaction metadata, including original message ID, clicked component identity, button label, and clicker identity, in the agent-visible callback context.

## Best Possible Solution

Define a typed, documented Discord interaction metadata contract for agent-dispatched component callbacks and populate it from the component registry plus Discord interaction payload across buttons, selects, and modals.

Options:

- **Add Typed Agent Metadata (recommended):** Expose a narrow documented metadata envelope with message id, action kind, safe callback/custom data, label/value details, and clicker identity, backed by Discord component tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields in the plugin interactive-handler API and document that stateful Discord workflows should use plugin callbacks rather than generic agent fallback messages.
- **Expose Sender And Message First:** Expose only clicker and originating message ids now, then defer custom id and callback payload semantics until the broader inbound metadata contract is settled.

Yes. Source inspection of origin/main shows the generic Discord component fallback builds an agent turn from eventText and ordinary sender fields, while tests assert plain BodyForAgent strings instead of structured interaction metadata.

## Solution Assessment

Unclear until maintainers choose the public contract. The maintainable fix should be a typed channel/inbound-context metadata API, not an ad hoc raw Discord payload leak or label-string workaround.

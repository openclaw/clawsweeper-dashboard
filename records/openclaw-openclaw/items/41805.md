## Summary

Keep open: current main and the latest release still route generic Discord component callbacks to agents as text-oriented inbound turns, while richer interaction data is available only to Discord plugin interactive handlers. The remaining work is a maintainer product/API decision for a typed agent-visible interaction metadata contract.

## What This Changes

Expose structured Discord button/select interaction metadata to agents when component callbacks are delivered as inbound messages.

## Best Possible Solution

Define and document a typed Discord interaction metadata contract for generic agent-dispatched component callbacks, populated from the component registry plus sanitized Discord interaction fields across buttons, selects, and modals.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should generic Discord component clicks expose a new agent-visible structured interaction metadata envelope, and which fields should be public versus plugin-only?

Rationale: This changes the public agent inbound context and exposes Discord identifiers/callback data, so maintainers need to choose schema shape, compatibility behavior, privacy/security boundary, and documentation before implementation.

Likely owner: thewilloftheshadow

Owner reason: Shadow introduced the Discord Components v2 surface and is the clearest history-backed owner for deciding whether generic agent callbacks should receive component metadata.

Owner confidence: high

Options:

- **Add Typed Agent Metadata (recommended):** Expose a narrow documented metadata envelope with originating message id, action kind, safe callback/custom data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields only in plugin interactive handlers and document that stateful Discord workflows should use plugin callbacks instead of generic fallback messages.
- **Start With Sender And Message:** Expose only clicker and originating message ids first, deferring callback payload semantics until a broader inbound metadata contract is settled.

## Reproduction Assessment

Yes. Source inspection shows the generic Discord component callback path dispatches eventText as BodyForAgent while existing tests assert text-only fallback behavior such as Clicked "Approve".

## Solution Assessment

Unclear until maintainers choose the public contract. The durable fix should be a typed channel/inbound-context metadata API that reuses existing sender context, not an ad hoc raw Discord payload leak.

## Summary

Keep open: current main and the latest release still turn generic Discord component callbacks into plain agent text plus ordinary sender context, while richer interaction fields are only available to plugin interactive handlers. This remains a maintainer product/API contract decision for agent-visible Discord interaction metadata.

## What This Changes

Request to expose structured Discord button interaction metadata such as original message id, custom/callback id, button label, and clicked-user identity to the agent callback path.

## Best Possible Solution

Define a narrow, documented Discord interaction metadata contract for agent-dispatched component callbacks and populate it from the component registry plus Discord interaction payload across buttons, selects, and modal submits.

Options:

- **Add Typed Agent Metadata (recommended):** Expose a documented metadata envelope with safe message id, action kind, custom/callback data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields in the plugin interactive-handler API and document that stateful Discord workflows should use plugin callbacks rather than generic fallback messages.
- **Narrow To Sender And Message IDs:** Expose only clicker and originating message ids first, deferring custom id and callback payload semantics until the broader inbound metadata contract is settled.

Yes, at source level: the current Discord component fallback path builds the agent turn from eventText and ordinary sender/context fields, while original message id, custom id, and structured interaction details are not added to the agent context. ## Solution Assessment

Unclear until maintainers choose the public contract; the requested direction is useful, but the durable fix should be a typed channel/inbound-context API rather than an ad hoc raw Discord payload leak.

## Summary

Keep open: current main and the latest release still send generic Discord component callbacks to agents as text plus ordinary sender context, while the richer interaction fields are only exposed to plugin interactive handlers. The remaining work is a maintainer API and trust-boundary decision for a typed agent-visible Discord interaction metadata contract.

## What This Changes

Request to expose structured Discord button interaction metadata, including originating message id, component/custom id, button label, and clicker identity, in agent callback context.

## Best Possible Solution

Define and document a typed Discord interaction metadata contract for agent-dispatched component callbacks, populated from the component registry plus Discord interaction payload across buttons, selects, and modals.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Discord component clicks expose a new agent-visible structured interaction metadata envelope, and which fields should be public versus plugin-only?

Rationale: This changes the public agent inbound context and exposes Discord identifiers and callback data, so maintainers need to choose the schema, trust boundary, and compatibility shape before implementation.

Likely owner: steipete

Owner reason: The decision is mainly a public plugin/channel API boundary choice, and this owner has recent relevant plugin-SDK and Discord boundary history.

Owner confidence: medium

Options:

- **Add Typed Agent Metadata (recommended):** Expose a narrow documented metadata envelope with original message id, action kind, safe callback/custom data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields only in plugin interactive handlers and document that stateful Discord workflows should use plugin callbacks instead of generic agent fallback messages.
- **Start With Sender And Message:** Expose only clicker and originating message ids first, deferring callback payload semantics until a broader inbound metadata contract is settled.

## Reproduction Assessment

Yes, at source level: current main builds generic Discord component callbacks from eventText and ordinary sender/context fields, while original message id, custom id, and structured interaction details are not added to agent context. ## Solution Assessment

Unclear until maintainers choose the public contract; the requested direction is useful, but the durable fix should be a typed channel/inbound-context API rather than an ad hoc raw Discord payload leak.

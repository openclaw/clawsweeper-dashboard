## Summary

Keep open: current main and latest release still route generic Discord component callbacks to the agent as plain text plus ordinary sender fields; richer interaction metadata exists only on the plugin interactive-handler path. This remains a product/API contract decision for agent-visible Discord interaction metadata.

## What This Changes

Request to expose structured Discord button interaction metadata, including originating message, component/custom id, label/value, and clicker identity, to agent callbacks.

## Best Possible Solution

Define a typed, documented Discord interaction metadata contract for agent-dispatched component callbacks and populate it from the component registry plus Discord interaction payload across buttons, selects, and modals.

Options:

- **Add Typed Agent Metadata (recommended):** Expose a narrow documented metadata envelope with message id, action kind, safe callback/custom data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields in plugin interactive handlers and document that stateful Discord workflows should use plugin callbacks rather than generic agent fallback messages.
- **Narrow To Sender And Message:** Expose only clicker and originating message ids first, deferring callback/custom id payload semantics until the broader inbound metadata contract is settled.

Yes, source-level: generic Discord component fallback builds BodyForAgent/RawBody/CommandBody from eventText and does not attach original message id, custom id, or button-label metadata. I did not run a live Discord click in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public contract; the durable fix should be a typed agent-visible inbound metadata seam, not a raw Discord payload leak or label-parsing workaround.

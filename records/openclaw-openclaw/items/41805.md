## Summary

Keep open: current main and v2026.6.11 still route generic Discord component callbacks to the agent as normal inbound text, while structured interaction fields remain internal or plugin-handler-only. This remains a public inbound-context and trust-boundary decision, not conservative cleanup.

## What This Changes

The issue requests structured Discord button/select interaction metadata, including message, callback/custom, and clicker identifiers, in agent-visible inbound context.

## Best Possible Solution

Define a narrow typed Discord interaction metadata contract for agent-dispatched component callbacks, document the field semantics, and populate it from the registry plus Discord interaction payload across buttons, selects, and modals.

Rationale: The request changes public agent inbound context and exposes Discord user identifiers plus callback data, so maintainers must choose the schema, compatibility shape, and trust boundary before implementation.

Likely owner: steipete

Owner confidence: high

Options:

- **Add Typed Agent Metadata (recommended):** Expose a documented envelope with action kind, originating message id, safe callback/custom data, selected values or label, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields on plugin interactive handlers and document that stateful Discord workflows should use plugin callbacks instead of generic agent fallback messages.
- **Expose Minimal Identity First:** Start with clicker and originating message ids only, deferring callback payload semantics until a broader inbound metadata contract is settled.

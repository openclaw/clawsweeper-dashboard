## Summary

Keep open: current main and v2026.6.11 still route generic Discord component callbacks to the agent as text plus ordinary sender context, while richer interaction fields are only exposed to plugin interactive handlers. This remains a product/API decision for a typed agent-visible Discord interaction metadata contract.

## What This Changes

Request structured Discord interaction metadata, such as original message id, control/custom id, button/select details, and clicker identity, in agent-visible Discord component callbacks.

## Best Possible Solution

Define and document a typed Discord interaction metadata contract for agent-dispatched component callbacks, populated from the component registry plus the Discord interaction payload across buttons, selects, and modals.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Discord component clicks expose a new agent-visible structured interaction metadata envelope, and which fields should be public versus plugin-only?

Rationale: This changes the public agent inbound context and exposes Discord identifiers/callback data, so maintainers need to choose the schema, trust boundary, and compatibility shape before implementation.

Likely owner: steipete

Owner reason: This person has the strongest recent history on the plugin/channel boundary and Discord component behavior that would define the public contract.

Owner confidence: high

Options:

- **Add Typed Agent Metadata (recommended):** Expose a narrow documented metadata envelope with original message id, action kind, safe callback/custom data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields only in plugin interactive handlers and document that stateful Discord workflows should use plugin callbacks rather than generic agent fallback messages.
- **Start With Sender And Message:** Expose only clicker and originating message ids first, deferring callback payload semantics until a broader inbound metadata contract is settled.

## Reproduction Assessment

Yes, at source level: generic Discord component callbacks are converted to eventText and ordinary sender/context fields, while original message id, custom id, and structured interaction details are not added to the agent context. I did not run a live Discord button click in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public contract; the requested direction is useful, but the durable fix should be a typed channel/inbound-context API rather than an ad hoc raw Discord payload leak.

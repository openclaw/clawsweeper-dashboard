## Summary

Keep open: current main and v2026.6.11 still route generic Discord component callbacks to the agent as text fallback, while richer interaction fields remain raw/internal or plugin-handler-only. This is still a public inbound-context and trust-boundary decision, not conservative cleanup.

## What This Changes

Expose structured Discord button/select interaction metadata such as originating message id, callback/custom data, label or values, and clicker identity to agent inbound context.

## Best Possible Solution

Define a narrow typed Discord interaction metadata contract for agent-dispatched component callbacks, document its field semantics, and populate it from the registry plus Discord interaction payload across buttons, selects, and modals.

Rationale: The request changes public agent inbound context and exposes Discord user identifiers plus callback data, so maintainers must choose the schema, compatibility shape, and trust boundary before implementation.

Likely owner: steipete

Owner reason: This decision most closely matches the typed presentation action and cross-channel interaction contract work in this area.

Owner confidence: high

Options:

- **Add Typed Agent Metadata (recommended):** Expose a documented envelope with action kind, originating message id, safe callback/custom data, selected values or label, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields on plugin interactive handlers and document that stateful Discord workflows should use plugin callbacks instead of generic agent fallback messages.
- **Expose Minimal Identity First:** Start with clicker and originating message ids only, deferring callback payload semantics until a broader inbound metadata contract is settled.

## Solution Assessment

Unclear until maintainers choose the public contract; the requested direction is useful, but the durable fix should be a typed channel/inbound-context API rather than an ad hoc raw Discord payload leak.

## Summary

Keep open: current main and the latest release still route generic Discord component callbacks to the agent as text plus ordinary sender context, while richer interaction data remains available only to plugin interactive handlers. The remaining work is a maintainer product/API decision for a typed agent-visible interaction metadata contract.

## What This Changes

The issue requests structured Discord interaction metadata for agent-visible button callbacks, including originating message, clicked component, and clicker identifiers.

## Best Possible Solution

Define and document a narrow typed Discord interaction metadata contract for generic agent-dispatched component callbacks, populated by the Discord plugin from the component registry and interaction payload across buttons, selects, and modals.

## Maintainer Decision

Rationale: This changes the public agent inbound context and exposes Discord identifiers/callback data, so maintainers need to choose schema, trust boundary, compatibility shape, and documentation before implementation.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Add Typed Agent Metadata (recommended):** Expose a documented metadata envelope with source message id, action kind, safe callback/custom data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields only in plugin interactive handlers and document that stateful Discord workflows should use plugin callbacks rather than generic agent fallback messages.
- **Start With Sender And Message:** Expose only clicker and originating message identifiers first, deferring callback payload semantics until a broader inbound metadata contract is settled.

## Reproduction Assessment

Yes. Current main source and tests show generic Discord component callbacks are dispatched as text plus ordinary sender context, while message/component/custom metadata is not exposed as a structured agent-visible interaction envelope.

## Solution Assessment

Unclear until maintainers choose the public contract. The requested direction is useful, but the maintainable fix should be a typed channel/inbound-context API rather than leaking a raw Discord payload into agent context.

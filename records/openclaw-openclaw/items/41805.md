## Summary

Keep open: current main and the latest release still expose Discord component clicks to the generic agent path as callback text plus ordinary sender fields, while the richer interaction id/message id/value fields are only available to plugin interactive handlers. This remains a public Discord inbound-context API and trust-boundary decision, not a cleanup close.

## What This Changes

Request structured Discord button/select interaction metadata, including originating message id, component/custom id, label/value, and clicker identity, in agent-visible callback context.

## Best Possible Solution

Define and document a typed Discord interaction metadata contract for agent-dispatched component callbacks, populated from the component registry and Discord interaction payload across buttons, selects, and modals.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should generic Discord component callbacks expose a new agent-visible structured interaction metadata envelope, and which fields are public versus plugin-only?

Rationale: This changes the public agent inbound context and exposes Discord identifiers and callback data, so automation should not choose the schema or trust boundary without maintainer intent.

Likely owner: huntharo

Owner reason: Recent merged work on the Discord component fallback and plugin interactive paths is the closest history signal for deciding this public callback contract.

Owner confidence: medium

Options:

- **Add typed agent metadata (recommended):** Expose a narrow documented envelope with originating message id, action kind, safe callback/custom data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep metadata plugin-only:** Leave rich interaction fields only in plugin interactive handlers and document that stateful Discord workflows should use plugin callbacks rather than generic fallback messages.
- **Start with ids only:** Expose only clicker and originating message ids first, deferring callback payload semantics until a broader inbound metadata contract is settled.

## Reproduction Assessment

Yes, at source level: current main builds generic Discord component callbacks from `eventText` and ordinary sender/context fields, while original message id, custom id, and structured interaction details are not added to agent context. I did not run a live Discord click in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public contract; the requested direction is useful, but the maintainable fix should be a typed channel/inbound-context API rather than an ad hoc raw Discord payload leak.

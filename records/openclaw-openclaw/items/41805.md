## Summary

Keep open: current main and the latest release still route generic Discord component callbacks to the agent as text plus ordinary sender context, while richer interaction data is only available to plugin interactive handlers. This remains a maintainer product/API decision for a typed agent-visible Discord interaction metadata contract.

## What This Changes

Requests structured Discord button interaction metadata, including message id, button/custom id, label, and clicker identity, in the agent inbound callback context.

## Best Possible Solution

Define and document a narrow typed Discord interaction metadata contract for generic agent-dispatched component callbacks, populated from the registry plus Discord interaction payload across buttons, selects, and modals without leaking raw transport payloads.

## Maintainer Decision

Question: Should generic Discord component clicks expose a new agent-visible structured interaction metadata envelope, and which fields should be public versus plugin-only?

Rationale: This changes the public agent inbound context and exposes Discord identifiers and callback data, so maintainers need to choose schema, trust boundary, and compatibility shape before implementation.

Likely owner: vincentkoc

Owner reason: The current source history most directly ties this person to the Discord component callback handler, dispatch context, and typed component boundary.

Owner confidence: high

Options:

- **Add Typed Agent Metadata (recommended):** Expose a documented metadata envelope with original message id, action kind, safe callback/custom data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields only in plugin interactive handlers and document that stateful Discord workflows should use plugin callbacks instead of generic agent fallback messages.
- **Start With Sender And Message:** Expose only clicker and originating message ids first, deferring callback payload semantics until a broader inbound metadata contract is settled.

## Reproduction Assessment

Yes. Source review shows current main builds generic Discord component callbacks from eventText plus ordinary sender/context fields, and tests assert the agent receives text such as Clicked "Approve"; I did not run a live Discord click in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public contract. The requested direction is useful, but the maintainable fix should be a typed channel/inbound-context API rather than an ad hoc raw Discord payload leak.

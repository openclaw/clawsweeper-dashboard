## Summary

Keep open: current main and the latest release still expose generic Discord component clicks to agents as text, not as structured interaction metadata, and the remaining change is a public agent/plugin API contract decision.

## What This Changes

The issue requests structured Discord button interaction metadata, including message, button, and user identifiers, in agent-visible callback context.

## Best Possible Solution

Define a typed, documented Discord interaction metadata contract for agent-dispatched component callbacks and populate it from the component registry plus Discord interaction payload across buttons, selects, and modals.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Discord component clicks expose a new agent-visible structured interaction metadata envelope, and which fields should be public versus plugin-only?

Rationale: This changes public agent inbound context and exposes Discord identifiers/callback data, so maintainers need to choose schema, trust boundary, and compatibility shape before implementation.

Likely owner: steipete

Owner reason: The recent path history for Discord component dispatch and plugin interactive boundaries points to this owner candidate for the schema decision.

Owner confidence: high

Options:

- **Add Typed Agent Metadata (recommended):** Expose a narrow documented envelope with message id, action kind, safe custom/callback data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields in the plugin interactive-handler API and document that stateful Discord workflows should use plugin callbacks rather than generic agent fallback messages.
- **Expose Sender And Message First:** Expose only clicker and originating message ids now, deferring custom id and callback payload semantics until the broader inbound metadata contract is settled.

## Reproduction Assessment

Yes, at source level: current Discord component fallback builds the agent turn from eventText and ordinary sender/context fields, while original message id, custom id, and a structured interaction object are not added to agent context. I did not run a live Discord button click in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public contract; the requested direction is useful, but the durable fix should be a typed channel/inbound-context API rather than an ad hoc raw Discord payload leak.

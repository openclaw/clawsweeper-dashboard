## Summary

Keep open: current main still sends generic Discord component callbacks to agents as text-only event turns, while richer interaction metadata exists only on the plugin interactive handler path. The remaining work is a public metadata-contract and trust-boundary decision, not conservative cleanup.

## What This Changes

Request structured agent-visible metadata for Discord button/select callbacks, including source message, component identity, and clicker identity.

## Best Possible Solution

Define a narrow documented Discord/channel interaction metadata contract populated from registry state and Discord interaction payload for buttons, selects, and modals, with focused tests and docs before exposing it to agents.

Rationale: The change would create a durable public inbound-context contract and expose Discord identifiers plus callback data, so maintainer intent is needed before implementation.

Likely owner: thewilloftheshadow

Owner confidence: high

Options:

- **Add Typed Agent Metadata (recommended):** Expose a documented bounded metadata envelope with source message id, component kind, safe callback/custom data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields on plugin interactive handlers and document that stateful Discord workflows should use plugin callbacks rather than generic fallback messages.
- **Start With Minimal IDs:** Expose only clicker and originating message ids first, deferring callback payload semantics until a broader inbound metadata contract is settled.

## Reproduction Assessment

Yes. Source inspection shows current main builds generic component callbacks as eventText and dispatches BodyForAgent, RawBody, and CommandBody without a typed interaction metadata object.

## Solution Assessment

Unclear until maintainers choose the public contract. The maintainable fix should be a typed channel/inbound interaction metadata contract, not an ad hoc raw Discord payload leak.

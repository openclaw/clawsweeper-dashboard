## Summary

Keep open: current main still sends generic Discord component callbacks to the agent as text-only inbound turns, while richer interaction fields are only available on the plugin interactive path. This remains a product/API decision about what structured Discord interaction metadata should be exposed to agents.

## What This Changes

Request exposing message, component/custom-id, and clicker metadata to agents when Discord buttons or selects are clicked.

## Best Possible Solution

Define a narrow, documented Discord interaction metadata contract for generic component callbacks, populated from the component registry and Discord interaction payload across buttons, selects, and modals.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should generic Discord component clicks expose a new agent-visible structured interaction metadata envelope, and which fields are public versus plugin-only?

Rationale: This changes public agent inbound context and exposes Discord identifiers/callback data, so maintainers need to choose schema, compatibility shape, and trust boundary before implementation.

Likely owner: thewilloftheshadow

Owner reason: The Discord Components v2 feature history makes this the clearest Discord-owner routing candidate for the public callback contract choice.

Owner confidence: medium

Options:

- **Add Typed Agent Metadata (recommended):** Expose a documented metadata envelope with originating message id, action kind, safe callback/custom data, label/value details, and clicker identity, backed by Discord plugin tests.
- **Keep Metadata Plugin-Only:** Leave rich interaction fields only in plugin interactive handlers and document plugin callbacks as the supported path for stateful Discord component workflows.
- **Start With Minimal IDs:** Expose only clicker and originating message ids first, deferring callback payload semantics until a broader inbound metadata contract is settled.

## Reproduction Assessment

Yes. Source inspection and existing tests show generic Discord component clicks are converted into eventText/BodyForAgent strings, while richer interaction fields remain on the plugin-only interactive path.

## Solution Assessment

Unclear until maintainers choose the public contract. The best implementation should be a typed channel/inbound metadata API, not an ad hoc leak of raw Discord interaction payloads.

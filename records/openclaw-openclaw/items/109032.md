## Label Justifications

- `P2`: Messages are delivered successfully, but the missing bubble-boundary control causes a limited, repeatable WhatsApp presentation problem.
- `impact:ux-friction`: Automatic replies lose the conversational multi-bubble structure users attempted to configure, without losing the underlying message text.

## Summary

Keep open for product direction: current main intentionally treats `newline` as a paragraph-boundary preference rather than a paragraph-per-bubble guarantee, so the report identifies a real missing delivery mode rather than a regression against the current documented contract. Likely related people: @tyler6204 (high confidence; introduced the earlier paragraph-flush behavior).

## What This Changes

Provide deterministic paragraph-per-bubble delivery for automatic WhatsApp replies instead of recombining short blank-line-separated paragraphs.

## Best Possible Solution

Preserve the current paragraph-preference default and, if maintainers want this UX, add one clearly named opt-in paragraph-per-bubble mode at the shared streaming boundary, with ordered delivery, WhatsApp live proof, focused regression tests, and aligned docs.

Question: Should OpenClaw add an explicit paragraph-per-bubble mode, restore that behavior globally for `streaming.chunkMode: "newline"`, or retain the current paragraph-preference semantics?

Rationale: Current source and documentation deliberately define `newline` as a preferred split boundary, while the requested behavior changes cross-channel message volume and may require a new public configuration contract.

Owner confidence: high

Options:

- **Add explicit opt-in mode (recommended):** Keep current `newline` compatibility and add a distinct paragraph-per-bubble policy whose boundaries survive chunking and coalescing.
- **Restore newline semantics globally:** Make every blank-line paragraph a separate outbound message across channels using `newline`, accepting increased bubble volume and a compatibility change.
- **Retain current behavior:** Keep paragraph-aware length chunking as documented and close the request as an unsupported presentation preference.

## Reproduction Assessment

Yes, with high confidence from source: a short two-paragraph automatic reply remains one chunk under the WhatsApp text limit, and the coalescer lacks forced boundary flushing. The reporter also supplies a concrete real-provider path, though this review did not rerun it.

## Solution Assessment

No, silently treating the current behavior as a bug and restoring old `newline` semantics is not clearly the best fix. A separate opt-in paragraph-per-bubble mode is safer, but maintainers must confirm that the extra configuration surface is justified.

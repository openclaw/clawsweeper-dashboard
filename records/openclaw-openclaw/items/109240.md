## Summary

Keep open for maintainer direction: current main still has one shared, hardcoded pairing reply with no config-backed override, while this fresh request proposes a bounded global customization surface rather than changing pairing access policy. The capability is still necessary, but a new security-adjacent global config key requires explicit product approval before implementation.

## What This Changes

Add an optional global `messages.pairingTemplate` setting with safe placeholders for pairing replies across pairing-capable channels.

## Best Possible Solution

Use one centralized, opt-in presentation contract at the shared pairing formatter, preserve the current reply byte-for-byte when unset, keep access control and challenge creation unchanged, define deterministic escaping/substitution behavior, and document the privacy and usability consequences of omitting each placeholder.

## Label Justifications

- `P1`: Legacy claims can block the normal Workboard release, reclaim, dispatch, and completion workflow, and the proposed repair currently may retain that block.
- `merge-risk: 🚨 compatibility`: The migration changes existing persisted claim records during an upgrade and needs a defined recovery outcome for users with legacy data.
- `merge-risk: 🚨 session-state`: Claim JSON and card assignment fields are Workboard session/ownership state, and the migration changes their meaning.
- `merge-risk: 🚨 security-boundary`: The new token participates in claim authorization, but the migration generates it without establishing who can validly present it.

## Summary

This PR targets a real Workboard recovery problem, but the current migration still persists a newly generated claim token that no existing claimant can know. That can leave the migrated card unable to satisfy strict token-based mutation checks, so the patch is not safe to merge until the recovery semantics are made explicit and demonstrated through the actual Doctor command and a subsequent Workboard operation.

## What This Changes

Adds a Doctor-only SQLite migration that detects legacy Workboard card claims lacking `ownerId` and rewrites or clears them so strict current claim handling can operate on canonical data.

## System Context

Workboard tools read card claim state from the Workboard SQLite database before allowing release, reclaim, dispatch, or completion actions. This PR adds a Doctor migration that rewrites older persisted claim JSON before those strict runtime authorization checks consume it.

## Best Possible Solution

Define legacy claims without a verifiable canonical token as unrecoverable by default and clear them into the normal dispatch path, unless maintainers explicitly choose and document a separate administrator-authorized recovery contract; then add focused coverage and live Doctor-to-Workboard proof.

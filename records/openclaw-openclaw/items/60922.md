## What This Changes

The PR adds an opt-in `agents.defaults.model.fallbacksFromModels` config key, schema/docs/tests, and fallback candidate logic to derive model failover candidates from `agents.defaults.models` when explicit fallbacks are omitted.

## Best Possible Solution

Use one effective fallback resolver shared by candidate construction, `hasConfiguredModelFallbacks`, `resolveEffectiveModelFallbacks`, gateway/status surfaces, and embedded-run failover tests, then document and prove the opt-in with redacted real runtime output.

## Reproduction Assessment

Yes, by source inspection. The PR can derive fallback candidates from the catalog, but current embedded-run availability still comes from explicit fallback arrays and the failover policy requires that flag before selecting `fallback_model`.

## Solution Assessment

No, not as-is. Candidate derivation is a plausible piece, but the best fix is a single effective fallback contract used by candidate construction, availability gates, effective fallback resolution, and embedded-run failover tests.

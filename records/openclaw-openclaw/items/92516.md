## Summary

Keep open: current main still requires bundled or trusted-official provenance before external channel plugins can use keyed state, and the issue’s remaining ask is a security/product decision for immutable self-hosted deployments rather than something already implemented.

## What This Changes

The issue requests a supported way for immutable/containerized self-hosted deployments to run externalized trusted channel plugins without losing official-install provenance behind a mounted state directory.

## Best Possible Solution

Keep the fail-closed keyed-state gate and add a maintainer-approved official-plugin install/provenance contract whose package root and trust record survive a mounted mutable state directory, with docs, doctor diagnostics, and Docker proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw support a separate immutable official-plugin package/provenance root for self-hosted containers, and what checks must it enforce before those external channel plugins receive trusted keyed-state access?

Rationale: The source failure is clear, but the fix decides which external code receives host-managed persistent state and channel ingress capabilities, so automation cannot choose the trust model safely.

Likely owner: hxy91819

Owner reason: They are the live assignee and already stated the relevant official-plugin provenance policy in the issue thread.

Owner confidence: high

Options:

- **Design immutable official-plugin provenance root (recommended):** Add a supported build-time/install-time path that preserves official catalog identity, package path, and install records outside the mutable runtime state mount while keeping raw load paths untrusted.
- **Document current installer/state-dir contract only:** Keep the existing fail-closed behavior and document that runtime containers must mount the same state directory created by the installer, accepting that common immutable-image layouts remain unsupported.
- **Allow explicit local trust override:** Add a config or flag that lets operators trust local/load-path plugins, trading deployment convenience for a broader security boundary that would need strong warnings and tests.

## Reproduction Assessment

Yes, at source level: an external Microsoft Teams plugin without matching trusted official-install metadata reaches openKeyedStore and current main throws before opening keyed state. I did not run the reporter’s ECS/Fargate container setup in this read-only review.

## Solution Assessment

No to raw trust allowlists or implicit load-path trust; the best fix is a provenance-preserving official plugin deployment contract. The narrow ClawHub npm-only PR is useful for a related issue but does not solve the mounted-state immutable-image case.

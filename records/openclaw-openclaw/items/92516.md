## Label Justifications

- `impact:security`: The requested fix determines which external plugin packages may access host-managed persistent keyed state and channel ingress APIs.

## Summary

Keep open: current main still fails closed for image-baked/load-path external channels without trusted official-install provenance, and the remaining ask is a security/product decision about a provenance-preserving immutable-container deployment path rather than a stale duplicate.

## What This Changes

The issue requests a supported way for self-hosted/container deployments to run official externalized channel plugins that need trusted keyed state when the mutable OpenClaw state directory is mounted separately.

## Best Possible Solution

Keep the fail-closed keyed-state gate, then design and document a provenance-preserving official plugin deployment path for containers where immutable package/provenance data survives a mutable state/config mount.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a provenance-preserving immutable/container official-plugin install path outside the mutable runtime state mount, and what package root plus trust-record storage should define that boundary?

Rationale: The source failure path is clear, but deciding how external channel plugins earn trusted state access changes a security boundary and likely a deployment/config contract.

Likely owner: hxy91819

Owner reason: They are assigned on the issue and already framed the fail-closed official-plugin provenance boundary in the discussion.

Owner confidence: high

Options:

- **Design Immutable Official Plugin Root (recommended):** Add or document an official install/provenance root that can be baked into an image while mutable runtime state and config remain mounted separately.
- **Keep Current Snapshot-State Contract:** Document that self-hosted images must ship and mount the same complete OpenClaw state directory, accepting that common immutable-container mounts remain unsupported.
- **Decline New Trust Path:** Close the request as not planned and keep trusted state limited to bundled plugins or installer-proven records in the active state directory.

## Reproduction Assessment

Yes at source level: a non-bundled external channel without matching trusted official-install metadata still throws when it opens keyed state, and Microsoft Teams opens keyed stores during runtime. I did not run the ECS/Fargate volume-mount reproduction in this read-only review.

## Solution Assessment

No to raw load-path trust or a simple trusted:true escape hatch; those are not the best fix because they weaken provenance. The best path is a maintainer-approved immutable official-plugin package and trust-record contract plus diagnostics for unsupported deployments.

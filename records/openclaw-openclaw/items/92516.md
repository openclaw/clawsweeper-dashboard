## Summary

Keep open: current main still gates keyed plugin state to bundled or trusted official installs, install provenance is stored under the active state directory that a container volume can mask, and the open related PR only addresses the narrower official ClawHub npmSpec case.

## What This Changes

The issue requests a supported container/self-hosted deployment path for official external channel plugins that need trusted keyed state without trusting arbitrary load-path packages.

## Best Possible Solution

Keep the fail-closed state gate and design a provenance-preserving official plugin package/install-record root that can live outside mutable runtime state mounts, with doctor/docs and Docker E2E proof.

Options:

- **Design a portable official install root (recommended):** Add a supported build-time official plugin install/provenance path outside mutable state mounts while keeping arbitrary load paths untrusted.
- **Keep current state-dir contract:** Declare that runtime containers must mount the same complete OpenClaw state directory used at install time and close the deployment model as unsupported.
- **Trust explicit load paths:** Allow operator-selected load paths or allowlists to access keyed state, accepting a broader spoofing/provenance risk.

## Reproduction Assessment

Yes at source level: a non-bundled external channel without matching trusted official-install metadata still throws when it opens keyed state, and Microsoft Teams opens keyed stores during runtime. I did not run the ECS/Fargate reproduction in this read-only review.

## Solution Assessment

Partly: the narrowed ask for a provenance-preserving immutable plugin root is the maintainable direction, but raw trust allowlists or implicit load-path trust are not the best fix for this security boundary.

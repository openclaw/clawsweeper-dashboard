## Label Justifications

## Summary

Keep open: current main still keeps trusted keyed state behind bundled or trusted-official provenance, and the remaining ask is a provenance-preserving immutable-container deployment contract rather than raw load-path trust.

## What This Changes

Provide a supported way for containerized self-hosted deployments to run official external channel plugins that need trusted keyed state while preserving source provenance.

## Best Possible Solution

Keep the fail-closed gate and design a supported official-plugin provenance path for immutable containers that separates image-baked package/provenance from mutable runtime state, with diagnostics, docs, and Docker proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a provenance-preserving immutable-container install/trust path for official external channel plugins, and which source of truth should confer trusted state access?

Rationale: The current supported installer ties package payload and install provenance to the active state directory, while the proposed deployment model needs that provenance to survive a mounted mutable state directory without turning raw load paths into trusted code.

Likely owner: hxy91819

Owner reason: They are assigned to this issue and already stated the intended trust boundary in the thread, making them the best available owner for the security/product choice.

Owner confidence: high

Options:

- **Approve immutable official plugin root (recommended):** Add a narrow official-plugin package/provenance root for image builds, verified against install records, resolved paths, and official catalog identity, while keeping raw load paths untrusted.
- **Keep mounted-state installer only:** Document that trusted external channel plugins must be installed into the mounted OpenClaw state directory and close this deployment model as unsupported.
- **Broaden allowlist or load-path trust:** Let operator-configured ids or load paths grant keyed-state access, accepting a weaker provenance boundary for self-hosted convenience.

## Reproduction Assessment

Yes, at source level: an external channel without bundled origin or trustedOfficialInstall still hits the openKeyedStore gate, and Microsoft Teams opens keyed stores during startup. I did not run the ECS/Fargate deployment path in this read-only review.

## Solution Assessment

Unclear until maintainers choose the security boundary. Raw trust allowlists are not the best fix; a provenance-preserving install/root contract is the maintainable direction.

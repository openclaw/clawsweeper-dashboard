## Summary

Keep open: current main still fails closed for copied/load-path external channel plugins without trusted official-install provenance, and the remaining ask is a provenance-preserving immutable-container deployment contract rather than raw trust bypass.

## What This Changes

Requested support for running externalized official channel plugins in immutable/self-hosted containers when the runtime state directory is mounted separately from image-baked plugin files.

## Best Possible Solution

Keep the fail-closed trust gate and add a maintainer-approved official-plugin provenance path for immutable images, where the plugin package and trust record remain verifiable even when mutable runtime state/config are mounted.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a provenance-preserving immutable/container install root for official external channel plugins, and which install sources may satisfy trustedOfficialInstall when the runtime state directory is mounted?

Rationale: The source failure is clear, but the fix decides which external plugin code receives trusted host-managed state and channel ingress capabilities, so automation should not choose the permanent trust boundary.

Likely owner: hxy91819

Owner reason: They are assigned to the live issue and already framed the trust-model tradeoff in the discussion.

Owner confidence: high

Options:

- **Design Immutable Official Install Root (recommended):** Add a supported build-time/install-time official plugin package and provenance root that survives a mounted runtime state directory while keeping raw load paths untrusted.
- **Document Same-State Snapshot Only:** Keep the current trust model and document that container images must ship and mount the same OpenClaw state directory containing the install record.
- **Broaden Operator Trust Allowlist:** Allow explicit operator config to trust load-path plugins, accepting a larger spoofing and provenance risk.

## Reproduction Assessment

Yes, at source level: a non-bundled/load-path external channel without matching trustedOfficialInstall still throws when it opens keyed state, and Microsoft Teams opens keyed stores during startup. I did not run the ECS/Fargate reproduction in this read-only review.

## Solution Assessment

No to raw trust allowlists or implicit load-path trust; the maintainable solution is a provenance-preserving install/deployment contract. The issue should stay open until maintainers choose that trust and storage shape.

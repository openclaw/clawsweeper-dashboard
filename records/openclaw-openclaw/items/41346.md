## Summary

Keep open: current main still has the reported cron path, and no merged/shipped fix covers consent, inherited expensive-model risk, provenance, and quota/circuit-breaker guardrails together. Related open items cover pieces of the problem, but they do not supersede this broader security/spend report.

## What This Changes

Request safe consent, model-cost, and quota guardrails for externally or plugin-registered recurring cron jobs that currently start enabled and inherit default models.

## Best Possible Solution

Define a provenance-aware cron scheduling policy that makes external/agent/plugin recurring jobs visibly consented, explicit about model/cost defaults, and protected by reason-aware quota/billing guardrails with an intentional upgrade path for existing jobs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should externally or plugin-registered recurring cron jobs become disabled/confirmation-gated by default, or should OpenClaw preserve enabled-by-default compatibility while adding explicit warnings, model defaults, and circuit breakers?

Rationale: Source inspection proves the gap, but choosing the permanent cron enablement, inherited-model, provider-spend, and plugin scheduling contract is a product/security compatibility decision.

Likely owner: Peter Steinberger

Owner reason: The current central implementation lines all blame to this recent area commit, and the decision spans cron, plugin scheduling, and model-selection behavior.

Owner confidence: high

Options:

- **Adopt provenance-gated consent (recommended):** External, agent, and plugin recurring jobs would require explicit operator activation or a doctor/update diff before becoming enabled, with migration handling for existing jobs.
- **Preserve enabled default with hard guardrails:** Keep existing jobs active by default but require explicit low-cost model/default selection, inherited-model warnings, and billing/auth circuit breakers before background polling runs.
- **Split immediate warnings from scheduler redesign:** Add doctor/update visibility and model-risk warnings now while leaving the non-forgeable scheduling API and budget enforcement to the related RFCs.

Yes, source-reproducible: current main still has plugin scheduled turns call cron.add with enabled: true and no payload model, cron creation defaults missing enabled to true, model selection falls through to agent/default model, and recurring failures only back off.

## Label Justifications

- `P1`: Enabled background cron jobs can repeatedly spend model quota without operator confirmation, affecting real provider-backed users but not making the core runtime unusable.
- `impact:security`: Persistent plugin/agent-created schedules are a security-sensitive control-plane surface that can continue running after the originating task ends.
- `impact:auth-provider`: The issue is tied to inherited provider/model selection and quota/cost exhaustion for authenticated model providers.
- `maturity:stable`: The affected cron.add gateway RPC belongs to Gateway runtime M4 Stable via Gateway RPC APIs and Events / Task and automation APIs.

## Summary

Keep open. Current main still defaults cron creates to enabled, plugin scheduled turns register enabled agent-turn jobs without model overrides, and no pre-run cost or usage circuit breaker exists; the related issues cover narrower slices rather than a complete fix.

## What This Changes

The issue requests safeguards for external/plugin-created cron jobs that auto-enable, inherit default models, and lack consent or spend circuit breakers.

## Best Possible Solution

Adopt a maintainer-approved cron safety design: operator cron remains explicit, plugin/agent/external recurring jobs get non-forgeable provenance, disabled-or-approval defaults, explicit model/cost policy, and upgrade/doctor proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What should the trust boundary and default activation policy be for plugin/agent/external recurring cron jobs that can spend model quota?

Rationale: A mechanical fix would change public cron behavior, plugin scheduling contracts, provider/model spend policy, and upgrade behavior, so maintainers need to choose the intended safety boundary before implementation.

Likely owner: Vincent Koc

Owner reason: Current blame and recent cron/model-selection refactors put the active implementation surface closest to Vincent Koc, while the decision should still involve security/product owners.

Owner confidence: medium

Options:

- **Provenance-gated scheduling API (recommended):** Create or harden a scheduling path that records non-forgeable origin, requires approval or disabled-by-default activation for recurring non-operator jobs, and requires explicit model/cost policy before execution.
- **Default external jobs disabled:** Make plugin/agent/external recurring cron registrations inactive until the operator enables them, accepting a compatibility migration and UX cost for existing automation.
- **Keep auto-enable with spend guards:** Preserve current activation behavior but add budget/quota/cost circuit breakers and warnings, leaving consent and provenance weaker than the issue requests.

## Reproduction Assessment

Yes at source level: cron create defaults missing enabled to true, plugin scheduled turns pass enabled true with a bare agentTurn payload, and model selection starts from configured defaults when payload.model is omitted; no live quota-burn repro was run in this read-only review.

## Solution Assessment

No narrow default flip is clearly best: the safer path is a maintainer-approved provenance, consent, model-cost, and upgrade policy that separates operator cron from plugin/agent scheduling.

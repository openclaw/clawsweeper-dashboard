## Summary

Keep open. Current main and v2026.6.11 still default omitted cron enablement to true, plugin scheduled turns still create enabled recurring agent-turn jobs without an explicit payload model, and the remaining consent, provenance, model-cost, and quota circuit-breaker behavior needs maintainer security/product direction.

## What This Changes

The issue requests safeguards so externally or plugin-registered cron jobs require approval or start disabled, avoid inheriting expensive default models silently, and gain dry-run/circuit-breaker cost controls.

## Best Possible Solution

Adopt a maintainer-approved cron scheduling safety design with explicit provenance and consent for plugin or agent-created recurring jobs, model/cost defaults or warnings, and gateway-level budget/circuit-breaker behavior with doctor/upgrade proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should externally, plugin, or agent-created recurring cron jobs remain auto-enabled, default disabled pending operator approval, or move behind a trusted scheduling API with provenance and explicit model/cost policy?

Rationale: This changes cron defaults, plugin scheduling contracts, provider/model spend policy, doctor/update behavior, and security posture for existing automation, so automation cannot choose the product boundary safely.

Likely owner: Vincent Koc

Owner reason: Vincent is the clearest current-code routing contact from the recent refactor across the affected cron and plugin scheduling files.

Owner confidence: medium

Options:

- **Provenance-based scheduling API (recommended):** Introduce a trusted scheduling path that records who created the job, requires operator approval or safe defaults for untrusted recurring jobs, and makes model/cost policy explicit.
- **Default external jobs disabled:** Keep the existing cron API but make externally registered recurring jobs inactive until the operator enables them, with migration and doctor messaging for existing jobs.
- **Keep enablement and add spend guards:** Preserve current auto-enable behavior but add model warnings, budget enforcement, and quota circuit breakers to reduce runaway-cost impact without changing scheduling consent.

## Reproduction Assessment

Yes at source level: creating a cron job without `enabled` still defaults it to true, and the plugin scheduled-turn helper explicitly registers enabled recurring `agentTurn` jobs without a payload model.

## Solution Assessment

The requested direction is valid, but the best fix is not a narrow cron default flip; it needs a maintainer-approved scheduling policy that separates operator-created jobs from plugin/agent-created jobs and handles model spend and quota enforcement consistently.

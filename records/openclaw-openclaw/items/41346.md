## What This Changes

The issue requests cron safety guardrails so externally registered polling jobs do not auto-enable without consent, silently inherit expensive default models, or run without quota/cost circuit breakers.

## Best Possible Solution

Define one maintainer-approved cron safety policy for external/plugin registration provenance, default activation, explicit model or cost warning behavior, doctor/update visibility, and quota-aware pause/notification semantics.

Yes, at source level: current cron creation defaults omitted `enabled` to true, plugin scheduled turns pass `enabled: true`, and cron model selection starts from configured defaults before payload/session overrides. I did not run a live provider scenario that burns quota.

## Summary

Keep open: current main and the latest checked release still allow newly created cron jobs to default enabled and allow model-backed isolated cron runs without an explicit per-job model, while the requested safeguards require maintainer security/product direction across cron provenance, activation, model defaults, and budget enforcement.

## What This Changes

The issue requests safeguards so externally registered or plugin-created recurring cron jobs do not silently start model-backed polling on expensive inherited defaults without operator confirmation or cost controls.

## Best Possible Solution

Keep the issue open for a maintainer-chosen cron safety design: provenance-aware external registration, explicit operator activation or update diff, model/default guardrails, and coordination with the open circuit-breaker and budget issues.

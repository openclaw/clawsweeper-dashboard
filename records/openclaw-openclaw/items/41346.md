## Label Justifications

- `P1`: The issue is source-reproducible and can trigger persistent background model calls with expensive inherited provider defaults, but it is not an immediate P0 crash, data-loss, or first-run blocker.

## Summary

Keep open. Current main and the latest v2026.6.11 release still allow recurring plugin/external cron jobs to be created enabled, plugin scheduled turns still omit an explicit model, cron model resolution can still inherit the configured default model, and the linked issues cover only sub-parts of the consent, provenance, model-cost, and circuit-breaker policy.

## What This Changes

The issue asks OpenClaw to prevent externally or plugin-registered polling cron jobs from silently enabling on expensive inherited models and to add confirmation, dry-run/cost visibility, and quota circuit breakers.

## Best Possible Solution

Define a maintainer-approved cron safety policy covering external/plugin registration provenance, operator activation consent, explicit per-job model or cost-warning behavior, doctor/update migration, and quota-aware pause/notification semantics.

Question: What default security policy should OpenClaw apply before externally or plugin-registered recurring agentTurn cron jobs can run on an inherited model?

Rationale: The source reproduction is clear, but the fix changes shipped cron defaults, plugin scheduling contracts, provider/model cost policy, quota thresholds, and upgrade behavior, so automation cannot safely choose the boundary.

Likely owner: openclaw/openclaw-secops

Owner confidence: high

Options:

- **Require explicit activation (recommended):** Recurring externally or plugin-registered agentTurn jobs should be created disabled or approval-pending unless an operator explicitly enables them with visible model/cost information and a doctor/update migration path.
- **Warn only on inherited expensive models:** Keep current activation semantics but warn or block only when a recurring agentTurn job inherits a high-cost default model without a job-specific model.
- **Split into narrower guardrails:** Resolve the consent, reason-aware backoff, cost-budget, and scheduling-provenance pieces independently through the linked issues, accepting that this combined behavior remains unresolved for now.

## Reproduction Assessment

Yes, source-level: omitted cron `enabled` defaults to true, plugin scheduled turns explicitly create enabled `agentTurn` jobs without a payload model, model selection begins from configured defaults, and recurring failures only back off. I did not run a live quota-burning reproduction.

## Solution Assessment

No, not as a single autonomous fix. The best path is a coordinated security/product design because activation defaults, inherited models, quota thresholds, provenance, and migration behavior all affect existing users.

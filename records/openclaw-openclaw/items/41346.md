## Label Justifications

- `P1`: Enabled recurring cron jobs can repeatedly spend provider quota without operator confirmation, affecting real users' background automation and model plans.
- `impact:security`: Persistent externally registered schedules are a security-sensitive control-plane surface that can keep running after the originating action ends.
- `impact:auth-provider`: The issue is tied to inherited provider/model selection and quota or cost exhaustion for authenticated model providers.
- `impact:other`: Unexpected recurring model spend and quota burn are concrete maintainer-visible impacts outside the more specific owned impact labels.
- `maturity:stable`: The affected Gateway cron RPC surface maps to Gateway runtime M4 Stable / Gateway RPC APIs and Events Stable in the maturity scorecard.

## Summary

Keep open: current main and v2026.6.11 still allow active plugin/external cron registrations, still inherit default model selection when no per-job model is set, and still lack a pre-dispatch spend/consent circuit breaker. The related issues cover narrower budget, retry, provenance, and cron-default slices rather than replacing this combined security/product decision.

## What This Changes

The issue requests consent, safe defaults, model-cost warnings, dry-run visibility, and usage circuit breakers for externally registered recurring cron jobs.

## Best Possible Solution

Adopt a maintainer-approved cron safety design where operator-created jobs remain explicit, plugin/agent/external recurring jobs carry non-forgeable provenance, activation requires approval or disabled-by-default policy, and model/cost guardrails run before dispatch.

- **Keep auto-enable with spend guards:** Preserve current activation behavior but add budget/quota warnings and circuit breakers, leaving consent and provenance weaker than the issue requests.

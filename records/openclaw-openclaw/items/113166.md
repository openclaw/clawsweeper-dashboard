## What This Changes

The issue requests that distinct agents using a shared Docker sandbox retain isolated persona and workspace files rather than all reading and writing the first agent’s mounted workspace.

## System Context

OpenClaw’s sandbox launcher resolves an agent workspace and creates or reuses a Docker container for tool execution. The resulting workspace mounts determine which persona, memory, skills, and editable files the agent can access while running tools.

## Architecture Diagram

flowchart LR

  B --> C[Shared container lookup]
  C --> D[Workspace mount planning]
  D --> E[Docker shared sandbox]

  F --> G[Persona memory and skills files]

## Best Possible Solution

Immediately prevent a shared container from exposing one agent’s writable workspace to another, preferably by refusing shared-scope execution when participating agents resolve to distinct workspaces; only add durable per-agent paths after the sandbox owner defines the compatibility contract and validates both rw and ro behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw treat an installed default Windows Scheduled Task as the trusted restart supervisor even when the running gateway lacks the injected service marker environment variables?

Rationale: Gateway restart fallback is compatibility- and availability-sensitive, and current code intentionally disables unmanaged detached Windows respawn to avoid orphaned children.

Likely owner: obviyus

Owner reason: They introduced the Windows Scheduled Task restart support and are also present in recent current-main history for the central restart files.

Owner confidence: high

Options:

- **Accept schtasks probing (recommended):** Review https://github.com/openclaw/openclaw/pull/95095 for a narrow probe that keeps unsafe unmanaged detached respawn disabled while recognizing an installed Scheduled Task.
- **Keep env-only detection:** Reject the probe path and keep this behavior explicit, leaving manually-started Windows gateways to use the documented Scheduled Task run workaround.
- **Fold into broader Windows restart work:** Defer this fix into the wider Windows restart reliability cluster if maintainers want one design to cover stderr surfacing, status truth, and SIGUSR1 handling together.

## Reproduction Assessment

Yes from source: on win32 with no Scheduled Task or service marker env vars, current main returns no supervisor and disables detached respawn, which drives the run loop into the in-process fallback. I did not run a live Windows Scheduled Task scenario in this read-only Linux checkout.

## Solution Assessment

Unclear until the linked PR is reviewed; direct schtasks probing is the plausible owner-boundary fix, but restart fallback behavior is compatibility-sensitive. The original detached-respawn proposal is not the best path because current code intentionally avoids orphaned Windows children.

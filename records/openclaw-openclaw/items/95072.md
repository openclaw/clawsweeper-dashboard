## Summary

Keep open: current main and the latest release still have the env-only Windows Scheduled Task detection and in-process fallback, while the linked open PR remains the active candidate fix for the env-missing Scheduled Task case.

## What This Changes

The issue requests that Windows `/restart` produce a real gateway process restart when a Scheduled Task exists but the running gateway lacks the expected supervisor environment markers.

## Best Possible Solution

Review and either land or reject https://github.com/openclaw/openclaw/pull/95095, preserving the safe Scheduled Task handoff and avoiding a return to unsafe unmanaged detached respawn.

Question: Should env-less native Windows gateway restarts probe Scheduled Tasks directly, and if so must the probe resolve the exact default/profile/custom task name before the gateway exits?

Rationale: The fix touches a compatibility-sensitive restart fallback where a false positive can stop the current gateway, while doing nothing leaves `/restart` as an in-process reload for the reported Windows setup.

Likely owner: obviyus

Owner confidence: high

Options:

- **Require Exact Scheduled Task Detection (recommended):** Proceed only if the linked PR probes the same task name the handoff will run and includes redacted Windows `/restart` plus `/status` proof.
- **Keep Env Markers As The Contract:** Reject direct probing and document that manually started Windows gateways without service markers use in-process restart unless launched through the Scheduled Task.
- **Accept Default-Task-Only Scope:** Allow probing only the default task and explicitly own the profile/custom-name false-negative or false-positive risk.

## Reproduction Assessment

Yes, source-reproducible: on win32 with no supervisor env markers, current main returns no `schtasks` supervisor and `restartGatewayProcessWithFreshPid()` returns `disabled`, which drives the run loop into the in-process fallback. I did not run a live Windows Scheduled Task scenario in this read-only review.

## Solution Assessment

Keeping this issue open is the right triage outcome because the linked fix PR is still open and current main/release are not fixed. The original detached-respawn direction is not the best fix; the safer path is exact Scheduled Task detection plus Windows proof.

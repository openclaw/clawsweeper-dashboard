## Summary

Keep open: current main and v2026.6.11 already make explicit session pins visible, provide `/model default`, and clear auto-created fallback pins on reset, but explicit and legacy user model pins are still intentionally preserved across `/new`, `/reset`, restarts, and rollovers. The remaining clear-all or precedence change is compatibility-sensitive product work, not conservative cleanup.

## What This Changes

Request to prevent or make recoverable persisted session `modelOverride` values that shadow changed config defaults after `/model`, gateway restart, and `/new`.

## Best Possible Solution

Keep the explicit user-vs-auto distinction, then add a maintainer-approved dry-run/explicit reset or reconcile path plus shared resolver visibility coordinated with #87957 and #28965.

Options:

- **Preserve pins, add opt-in recovery (recommended):** Keep explicit pins durable by default, but add a dry-run `sessions model-reset` or reconcile/doctor path with scoped opt-in clearing and status warnings.
- **Clear explicit pins on reset:** Make `/new` or `sessions.reset` drop explicit pins too, accepting a compatibility break for users who expect durable session model choices.
- **Document current behavior only:** Leave runtime semantics as-is and rely on `/model default`, status messaging, and docs without adding a bulk recovery surface.

## Reproduction Assessment

Yes at source level: seed a session with `modelOverrideSource: "user"` or a legacy `modelOverride`, then `/new` or `sessions.reset` preserves it and resolves from that pin; I did not run a live gateway restart path in this read-only review.

## Solution Assessment

Unclear as a strict bug fix: silently clearing explicit pins would break intentional per-session model choices, so the best fix is an opt-in clear/reconcile/visibility surface rather than changing precedence unilaterally.

## Summary

Keep open: current main and v2026.6.11 already make stale session pins visible, provide `/model default`, and clear auto-created fallback pins on reset, but explicit and legacy user `modelOverride` pins are still preserved by design. The remaining question is compatibility-sensitive product behavior, not an implemented-on-main cleanup close.

## What This Changes

Request to stop session-level model overrides from silently pinning stale provider/model state across gateway restarts and new sessions, with clearer visibility and reset support.

## Best Possible Solution

Keep the current visibility and `/model default` behavior, then have maintainers choose an explicit reset/reconcile policy for user and legacy session pins before any state-rewriting implementation.

Question: Should `/new`/`/reset` or config-default changes automatically clear explicit and legacy `modelOverride` pins, or should explicit pins remain strict with a separate bulk reset/reconcile tool?

Rationale: Current source, tests, and docs intentionally preserve user and legacy pins while clearing auto fallback pins, so changing the behavior affects persisted user state and upgrade expectations.

Likely owner: steipete

Owner reason: The remaining choice is product/documentation policy for model-selection semantics, and steipete authored the current docs that state the active contract.

Owner confidence: medium

Options:

- **Preserve pins, add explicit reset tooling (recommended):** Keep explicit session pins strict by default, and add a visible bulk reset or reconcile path with dry-run/reporting for users who want config defaults to take over.
- **Clear explicit pins on reset:** Make `/new` and `/reset` always inherit the configured primary, accepting that existing users who rely on persistent per-session model pins will see behavior change.
- **Make config outrank pins after restart:** Treat config-default changes as higher precedence than stored session pins after a gateway restart, which maximizes surprise-free defaults but weakens per-session pin semantics.

## Reproduction Assessment

Yes from source, not from a live gateway run: current reset code and regression tests show explicit or legacy user model overrides survive reset/restart semantics while auto fallback pins are cleared. The missing live repro does not block the review because the remaining behavior is directly asserted by source and tests.

## Solution Assessment

Unclear until maintainers choose the product policy: the current implementation is a conservative compatibility path, not the requested bulk-clear or precedence change. The safest next implementation would be an explicit reset/reconcile surface rather than silently changing precedence for existing session pins.

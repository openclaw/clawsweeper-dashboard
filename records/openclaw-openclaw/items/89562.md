## What This Changes

The issue reports that voice-call hangup aborts in-flight `sessions_spawn` work before spawned child sessions can initialize.

## Best Possible Solution

Define the hangup-versus-stop lifecycle contract, then add a bounded fix so an accepted or actively initializing `sessions_spawn` child can survive voice-call teardown while deliberate stop/reset paths still cascade, with focused regression coverage for the race.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should voice-call hangup be treated differently from explicit stop/reset once `sessions_spawn` has begun creating an independent child session?

Rationale: Current code makes the voice-call run cancellable through normal embedded-run abort paths, while the requested behavior preserves already-independent child work; that boundary changes lifecycle semantics for hangup, stop/reset, and subagent cleanup.

Likely owner: @steipete

Owner reason: Peter has the strongest recent cross-boundary history across voice-call session lifecycle and session helper work, which is where the product decision and likely fix boundary meet.

Owner confidence: medium

Options:

- **Decouple accepted spawn from hangup (recommended):** Define hangup as ending the voice transport only, then let an accepted or in-progress independent `sessions_spawn` child survive with regression coverage.
- **Keep hangup as cancellation:** Treat hangup as deliberate cancellation of all in-flight voice-turn work and document that background work must be queued outside the voice turn.
- **Add explicit operator mode:** Preserve current default and add a documented opt-in only if maintainers want a compatibility-preserving background-work mode.

## Reproduction Assessment

No high-confidence runnable reproduction yet. Source inspection shows the plausible voice-lane abort and child-spawn acceptance paths, but a live voice-call hangup or focused failing test is still missing for current main.

## Solution Assessment

Unclear until maintainers choose the lifecycle boundary. A gateway/tool-level accepted-spawn decoupling looks cleaner than a plugin-local grace timer if it preserves the documented non-blocking `sessions_spawn` contract without weakening deliberate stop/reset semantics.

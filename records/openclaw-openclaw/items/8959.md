## Summary

Keep open. Current main and v2026.7.1 still expose only scalar portable selects, while the closed unmerged dialog PR does not provide the requested cross-channel one-submit selection contract. The remaining work requires a maintainer decision on public SDK semantics, fallback behavior, and initial channel parity.

## What This Changes

Requests a portable message-tool multi-select interaction that batches several user choices into one callback and one agent turn across supported channels.

## Best Possible Solution

Extend the canonical presentation select block additively with explicit batch-selection semantics, bounded selected-value arrays, capability limits, and deterministic fallback; initially prove Discord and Slack end to end, then add Telegram only through an approved hosted-widget or web-app design rather than a provider-native field in the shared message tool.

## Risks / Open Questions

- Adding batch selection changes a shipped public presentation and plugin SDK contract, so scalar select compatibility and existing renderer behavior must remain intact.
- Telegram cannot match Discord or Slack with the same native primitive; a Mini App or hosted widget adds lifecycle, authorization, deployment, and callback-security decisions that should not be implied by a generic type alone.
- A cross-platform guarantee needs explicit degradation rules for channels that support only scalar selection or text fallback, otherwise the same presentation can produce materially different workflow behavior.

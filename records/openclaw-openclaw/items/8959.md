## Summary

Current main and v2026.7.1 still provide only scalar portable selects, so the requested one-submit multi-selection capability remains missing. This should stay open for a maintainer decision because it changes a public presentation/SDK contract and requires explicit fallback and channel-parity semantics.

## What This Changes

Add a portable message-tool multi-select control that batches selected values into one submitted callback across supported channels.

## Best Possible Solution

Extend `MessagePresentation` additively with a typed multi-select block and structured selected-values result, define generic capability limits and text fallback in core, then implement native render/callback handling in channel plugins according to an explicitly approved initial channel matrix.

Options:

- **Add a portable presentation block (recommended):** Define an additive typed multi-select contract with structured array results, ship Discord and Slack native implementations first, and require deterministic text fallback elsewhere.
- **Build a broader form/dialog API:** Treat multi-select as one field within a larger deterministic data-collection contract, accepting substantially greater scope and state-management complexity.
- **Keep channel-specific only:** Allow individual channel plugins to expose native selection workflows without promising a portable message-tool contract.

## Reproduction Assessment

Yes at source level: the current shared schema, SDK, docs, and provider mapping expose only scalar selects, so an array-valued one-submit selection cannot be expressed through the portable message surface.

## Solution Assessment

Yes, with one adjustment: the narrowest maintainable solution is an additive `MessagePresentation` block rather than a new provider-shaped top-level message parameter; maintainers must first approve its semantics and initial channel matrix.

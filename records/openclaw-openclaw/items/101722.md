## Label Justifications

- `P2`: This is a focused agent-harness parsing bug with plausible answer-mapping confusion but no evidence of broad outage, data loss, or blocked onboarding.
- `impact:ux-friction`: A user replying to an agent input prompt can get confusing or wrong answer mapping when answer text is mistaken for keyed syntax.

## Summary

Keep open. Current main still has the shared keyed-answer parser that treats delimiter-bearing lines as keyed entries; the broad URL/time examples only corrupt whole-helper output on key collision, but the shared Codex/Copilot answer bridge still lacks regression coverage for that edge.

## What This Changes

The issue reports that keyed-answer parsing in the agent user-input bridge can mistake delimiters inside URLs, paths, time strings, or config snippets for answer-key separators.

## Best Possible Solution

Keep the shared helper, but make keyed parsing question-aware or delimiter-aware so unkeyed answer text with URLs, times, Windows paths, or config snippets remains intact while supported keyed and numeric multi-question replies still map correctly.

## Maintainer Decision

Required: false

## Reproduction Assessment

No high-confidence end-to-end reproduction yet: source probes confirm the regex splits URLs, paths, and times into stray keyed entries, but the whole helper preserves common url/time fallback ids unless the stray key collides with a question key.

## Solution Assessment

Yes. A small shared-helper hardening with regression coverage is the best repair path; changing Codex or Copilot adapters separately would duplicate parsing policy across callers.

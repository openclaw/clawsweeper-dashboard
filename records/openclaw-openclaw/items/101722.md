## Summary

Keep open. Current main still has the same permissive shared parser, and a read-only source probe confirms delimiter-bearing lines can become stray keyed entries; the common URL/time fallback path is nuanced, but the shared parser still needs focused hardening and regression coverage.

## What This Changes

The issue asks OpenClaw to stop `parseKeyedAnswers()` from misclassifying unkeyed user-input answer lines that contain delimiters such as URLs, Windows paths, time strings, or config snippets.

## Best Possible Solution

Keep the shared helper, but make keyed parsing question-aware or delimiter-aware so unkeyed delimiter-bearing answer text remains intact while supported keyed and numeric multi-question replies still work.

No high-confidence end-to-end reproduction yet. Source inspection and a read-only regex probe reproduce the false keyed entries, but the full builder only corrupts these examples when the stray key collides with a supported question key or numeric index.

## Solution Assessment

Yes. A narrow shared-helper hardening with regression tests is the best repair path; changing only Codex or Copilot adapters would duplicate parsing policy and risk drift.

- `impact:ux-friction`: A user replying to an agent input prompt can get confusing or wrong answer mapping when answer text is mistaken for keyed syntax.

## Summary

Keep open. Current main still has the broad keyed-answer parser; the report overstates ordinary URL/time fallback corruption, but source inspection shows delimiter-bearing fallback lines can be misread when the accidental key matches a question id, header, question text, or index, and there is no regression coverage for that edge.

## What This Changes

The issue asks for the shared user-input answer parser to stop treating free-form delimiter text such as URLs, paths, times, or config snippets as keyed answer syntax.

## Best Possible Solution

Harden the shared helper so keyed parsing is question-aware or delimiter-aware, then add regression tests for unkeyed delimiter-bearing answers and existing keyed/numeric multi-question replies.

## Maintainer Decision

Required: false

## Reproduction Assessment

No high-confidence end-to-end reproduction yet. Source inspection shows the regex creates stray keyed entries and the builder prefers matching keyed entries over fallback lines, but the issue's broad examples only fail when the accidental key matches a question key or index.

## Solution Assessment

Yes, a small shared-helper hardening is the best fix. Changing Codex or Copilot adapters separately would duplicate parsing policy and risk drift across the plugin SDK surface.

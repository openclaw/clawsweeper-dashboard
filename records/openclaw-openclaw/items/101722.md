- `impact:ux-friction`: A user replying to an agent input prompt can get confusing or wrong answer mapping when delimiter-bearing text is mistaken for keyed syntax.

## Summary

Keep open. Current main still has the shared parser that treats delimiter-bearing lines as keyed answers, and no merged fix or canonical duplicate now owns this edge; the report overstates the common URL/time fallback case, but matching question keys can still corrupt answer values and coverage is missing.

## What This Changes

The issue reports that shared agent-harness keyed answer parsing can misclassify delimiter-bearing user replies such as URLs, Windows paths, times, or config snippets.

## Best Possible Solution

Keep the shared helper, but make keyed parsing question-aware or delimiter-aware so unkeyed answer text with URLs, times, Windows paths, or config snippets remains intact while supported keyed and numeric replies still map to question ids.

No high-confidence end-to-end reproduction yet. Source inspection and a regex probe show the parser still creates stray keyed entries for delimiter-bearing lines, but whole-builder corruption requires the accidental key to match a question id, header, question, or index.

## Solution Assessment

Yes. A small shared-helper hardening is the narrowest maintainable repair; changing only the Codex or Copilot adapters would duplicate parsing policy and risk drift from the shared plugin SDK surface.

## Summary

Keep open. Current main still has the permissive keyed-answer parser; the report overstates the ordinary URL/time/path fallback case, but source proof shows delimiter-bearing answers can be corrupted when the accidental left side matches a question key.

## What This Changes

The issue reports that multi-question user-input parsing can misclassify delimiter-bearing answers such as URLs, Windows paths, times, or config snippets as keyed replies.

## Best Possible Solution

Keep the shared helper, but make keyed parsing question-aware so only real question ids, headers, question text, or numeric indexes are treated as keyed replies while delimiter-bearing answer text stays in positional fallback.

No high-confidence end-to-end reproduction was run. Source inspection and a read-only exact-logic probe show false keyed entries for URLs, times, and Windows paths, with actual answer corruption when the accidental left side matches a question key.

## Solution Assessment

Yes. The best fix is a small shared-helper hardening rather than separate Codex or Copilot adapter changes, because Codex expects answer maps keyed by question id and OpenClaw owns the chat-reply convenience parser.

## Summary

Keep this PR open: the final resolver still silently prefers the new top-level selector when both it and the legacy OAuth-nested selector contain different profile ids. That can send a different stored bearer credential than an operator intended, so the existing P2 blocker remains until conflicting selectors are rejected or an explicitly approved precedence rule is documented and tested.

## What This Changes

This PR lets remote HTTP/SSE MCP servers inject bearer tokens from stored token or OAuth auth profiles through a new top-level `authProfileId`, while retaining legacy `oauth.authProfileId` configuration.

## System Context

MCP server definitions enter from OpenClaw configuration and are converted into CLI connection settings or embedded-client requests. The auth-profile resolver supplies the bearer credential at runtime so tokens are not serialized into MCP configuration.

## Architecture Diagram

flowchart LR

  Store[Auth profile secret store] --> Resolver[Bearer token resolver]
  Selector --> Resolver
  Resolver --> CLI[CLI MCP config and environment]
  Resolver --> Embedded[Embedded MCP request wrapper]
  CLI --> Remote[Remote MCP server]
  Embedded --> Remote

## Best Possible Solution

Make dual selector binding unambiguous: reject configurations where top-level `authProfileId` and legacy `oauth.authProfileId` differ, accept matching values and legacy-only configurations, and document that rule alongside focused regression coverage.

No: the bearer-neutral top-level field is a reasonable direction, but silently preferring it over a conflicting legacy field is not the narrowest safe compatibility behavior; conflict rejection is safer and mechanically testable.

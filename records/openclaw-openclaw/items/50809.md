## Summary

Keep open. Current main still lacks both requested Android-device pieces: no `sms.read` invoke command and no Android-node SMS ingress/reply channel; Android `sms.search` and the Twilio-backed SMS plugin are adjacent but do not satisfy this request.

## What This Changes

Add an Android-node `sms.read` command and a node-mediated SMS messaging channel with allowlisted inbound texts and outbound replies through a connected Android device.

## Best Possible Solution

Keep this as the canonical Android-device SMS tracker, split a narrow security-reviewed `sms.read` command from the inbound/reply channel decision, and preserve the Twilio SMS plugin as a separate provider-hosted channel unless maintainers choose a shared contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support Android-device SMS ingress/reply as a first-class channel, and should it reuse the existing `sms` channel/config surface or use a separate Android-device boundary?

Rationale: The remaining work crosses private Android SMS permissions, gateway node-event ingress, sender allowlists/pairing, outbound carrier-SMS authority, and the existing Twilio-owned `sms` channel namespace; automation cannot choose that product and security boundary safely.

Likely owner: steipete

Owner reason: The unresolved decision is primarily the `sms` channel/config ownership and product-security boundary created by the merged Twilio SMS channel.

Owner confidence: high

Options:

- **Split command and channel decisions (recommended):** Define a narrow dangerous/default-blocked Android `sms.read` command first, then separately design Android-device SMS ingress with fail-closed sender policy and a clear channel/config boundary.
- **Create a separate Android-device SMS channel:** Use a distinct channel or plugin identity for connected-device SMS so it does not conflict with the existing Twilio-backed `sms` channel semantics.
- **Decline Android-device SMS ingress:** Keep hosted Twilio SMS as the supported SMS channel and leave connected Android SMS limited to explicit node commands such as `sms.send` and `sms.search`.

Not applicable as a bug reproduction: this is a feature request. Source inspection gives a high-confidence current gap because Android exposes `sms.send` and `sms.search`, while `sms.read`, `sms.received`, and Android SMS receiver ingress are absent.

No, not as one combined automated change. The safer path is to split the Android read command from the Android-device channel/config/security decision and keep the existing Twilio SMS plugin separate unless maintainers choose a shared contract.

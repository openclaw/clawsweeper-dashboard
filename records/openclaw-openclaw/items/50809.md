## Summary

Keep open. Current main and v2026.6.11 still lack the requested Android `sms.read` command and Android-device SMS ingress/reply channel; the remaining work is real but security- and product-boundary-sensitive.

## What This Changes

Request to add an Android `sms.read` node invoke command and a node-mediated SMS messaging channel with allowlisted inbound texts and SMS replies.

## Best Possible Solution

Keep this issue open, split `sms.read` from Android-device channel design, and require a maintainer-approved SMS authority and channel ownership boundary before implementation.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Android-device SMS become an OpenClaw channel, and if so should it share the existing Twilio-backed `sms` channel surface or use a separate Android-node-specific boundary?

Rationale: The request would grant agents read/receive/send authority over carrier SMS while overlapping the existing `channels.sms.*` Twilio surface, so automation cannot safely choose the security, privacy, and channel ownership model.

Likely owner: steipete

Owner reason: He authored the current Twilio-backed SMS channel and is the official product lead, while the decision crosses channel naming and product/security boundaries.

Owner confidence: high

Options:

- **Split and design first (recommended):** Define a narrow dangerous-by-default Android `sms.read` command separately from any Android-device SMS channel, then implement channel behavior only after sender authorization, redaction, logging, and naming are approved.
- **Limit to read command:** Accept only a gateway-opt-in Android `sms.read` invoke command and defer inbound/reply channel behavior until a separate channel design is approved.
- **Keep device SMS out of the channel surface:** Leave the official `sms` channel as Twilio-backed and route Android-device SMS channel work to a future plugin/API design only if maintainers sponsor it.

## Reproduction Assessment

Not applicable; this is a feature request rather than a broken existing behavior report. Source and release inspection give a high-confidence current gap: Android exposes `sms.send` and `sms.search`, while `sms.read`, `sms.received`, and Android SMS receiver ingress are absent.

## Solution Assessment

No, not as one combined automated change. The safer path is to split the Android read command from the Android-device channel/config/security decision and keep the existing Twilio SMS plugin as a separate provider-hosted channel unless maintainers choose a shared contract.

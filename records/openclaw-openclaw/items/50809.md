## Summary

Keep open. Current main and v2026.6.11 still expose Android `sms.send`/`sms.search` and a separate Twilio-backed `sms` channel, but they do not implement the requested Android-node `sms.read` command or Android-device SMS ingress/reply channel.

## What This Changes

The issue requests an Android-node `sms.read` invoke command plus treating SMS as a first-class messaging channel through a connected Android node.

## Best Possible Solution

Keep this issue open as the Android-device SMS tracker, split `sms.read` from inbound/reply channel design, and require maintainer-approved security and channel ownership boundaries before implementation.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Android-device SMS become an OpenClaw channel, and if so should it reuse the existing `sms` channel surface or use a separate Android-node-specific boundary?

Rationale: The implementation would grant agents read/receive/send authority over carrier SMS while overlapping the existing Twilio-owned `channels.sms.*` surface, so automation cannot choose the security and product boundary safely.

Likely owner: steipete

Owner reason: He authored the current Twilio-backed `sms` channel and is the strongest history signal for the channel/config boundary decision.

Owner confidence: medium

Options:

- **Split and design first (recommended):** Define a narrow Android `sms.read` command contract separately from any Android-device SMS channel, then implement only after sender authorization, redaction, logging, and channel naming are approved.
- **Limit to read command:** Accept only a dangerous-by-default Android `sms.read` invoke command and defer inbound/reply channel behavior until a separate channel design is approved.
- **Keep SMS channel hosted-provider only:** Leave the official `sms` channel as Twilio-backed and close or redirect Android-device SMS channel work unless a new plugin/API seam is explicitly sponsored.

## Reproduction Assessment

Not applicable; this is a feature request rather than a broken existing behavior report. Source and release inspection give a high-confidence current gap: Android exposes `sms.send` and `sms.search`, while `sms.read`, `sms.received`, and Android SMS receiver ingress are absent.

## Solution Assessment

No, not as one combined automated change. The safer path is to split the Android read command from the Android-device channel/config/security decision and keep the existing Twilio SMS plugin as a separate provider-hosted channel unless maintainers choose a shared contract.

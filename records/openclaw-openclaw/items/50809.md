## Summary

Keep open. Current main still lacks both requested Android-device pieces: no `sms.read` invoke command and no Android-node SMS ingress/reply channel; the existing Android `sms.search` path and Twilio-backed SMS plugin are adjacent but do not satisfy this device-SMS request.

## What This Changes

The issue requests an Android-node `sms.read` invoke command plus a first-class SMS messaging channel routed through a connected Android device.

## Best Possible Solution

Keep this as the Android-device SMS tracker, split a narrow security-reviewed `sms.read` contract from the inbound/reply channel decision, and preserve the existing Twilio SMS plugin as a separate provider-hosted channel unless maintainers choose a shared contract.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw support Android-device SMS ingress/reply as a first-class channel, and if so should it reuse the existing `sms` channel/config surface or use a separate Android-device plugin/channel boundary?

Rationale: The request crosses private SMS read/receive/send authority, Android runtime permissions, gateway node-event ingress, and an existing Twilio-owned `sms` channel/config namespace; automation cannot choose that security and product boundary safely.

Likely owner: steipete

Owner reason: The most central unresolved product boundary is coexistence with the current Twilio-backed `sms` channel and OpenClaw's plugin/core scope policy, both tied to steipete's recent SMS channel work.

Owner confidence: medium

Options:

- **Split command and channel decisions (recommended):** Define a narrow, dangerous/default-blocked Android `sms.read` command first, then separately design Android-device SMS ingress with fail-closed sender policy and a clear channel/config boundary.
- **Create a separate Android-device SMS channel:** Use a distinct channel or plugin identity for connected-device SMS so it does not conflict with the existing Twilio-backed `sms` channel semantics.
- **Decline device SMS ingress:** Keep hosted Twilio SMS as the supported SMS channel and leave connected Android SMS limited to explicit node commands such as `sms.send` and `sms.search`.

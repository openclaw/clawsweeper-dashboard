## Summary

Keep open. Current main and v2026.6.11 still provide Android `sms.send`/`sms.search` and a separate Twilio-backed `sms` channel, but not the requested Android `sms.read` command or Android-node SMS ingress/reply channel.

## What This Changes

Requests Android `sms.read` for direct message/thread fetches and an Android-node-backed SMS channel with allowlisted inbound texts and outbound replies.

## Best Possible Solution

Split this into a security-reviewed Android `sms.read` command contract and a separately approved Android-device SMS channel/plugin boundary that coexists cleanly with the Twilio `sms` plugin.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Android-device SMS become an OpenClaw messaging channel, and should it reuse the existing `sms` channel surface or live behind a separate Android-node-specific channel/plugin boundary?

Rationale: The request grants read, receive, and send authority over carrier SMS while overlapping the current Twilio-owned `sms` channel and `channels.sms.*` config surface, so automation cannot safely choose the security and product boundary.

Likely owner: steipete

Owner reason: This account authored the current Twilio-backed `sms` channel and has the clearest history signal for the channel/config boundary decision.

Owner confidence: high

Options:

- **Split design first (recommended):** Define a narrow Android `sms.read` command separately from Android-device SMS ingress/reply, then implement only after sender authorization, redaction, logging, and channel naming are approved.
- **Limit to read command:** Accept only a dangerous-by-default Android `sms.read` invoke command and defer inbound/reply channel behavior until a separate channel design is approved.
- **Keep SMS hosted-provider only:** Leave the official `sms` channel as Twilio-backed and route Android-device SMS channel work outside core unless a missing plugin/API seam is explicitly sponsored.

## Reproduction Assessment

Not applicable; this is a feature request rather than a broken existing behavior report. Source and release inspection give a high-confidence current gap: Android exposes `sms.send` and `sms.search`, while `sms.read`, `sms.received`, and Android SMS receiver ingress are absent.

## Solution Assessment

No, not as one combined automated issue. The safer path is to split the Android read command from the Android-device channel/config/security decision and keep the existing Twilio SMS plugin as a separate provider-hosted channel unless maintainers choose a shared contract.

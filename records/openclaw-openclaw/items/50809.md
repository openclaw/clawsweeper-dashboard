## Summary

Keep open. Current main and the latest release still expose Android `sms.send`/`sms.search` plus a separate Twilio-backed `sms` channel, but they do not implement the requested Android `sms.read` command or Android-node SMS ingress/reply channel.

## What This Changes

The issue requests an Android-node `sms.read` command and a device-SMS messaging channel with allowlisted inbound texts and SMS replies through a connected Android node.

## Best Possible Solution

Keep this issue open as the Android-device SMS tracker, split `sms.read` from the inbound/reply channel design, and require maintainer-approved security and channel ownership boundaries before implementation.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Android-device SMS become an OpenClaw channel, and if so should it reuse the existing `sms` channel surface or use a separate Android-node-specific boundary?

Rationale: The work would grant agents read/receive/send authority over carrier SMS while overlapping the current Twilio-owned `channels.sms.*` surface, so automation cannot choose the security and product boundary safely.

Likely owner: steipete

Owner reason: He authored the current Twilio-backed `sms` channel and has the strongest current history signal for the channel/config boundary decision.

Owner confidence: high

Options:

- **Split and design first (recommended):** Define a narrow Android `sms.read` command contract separately from Android-device SMS channel ingress, then implement only after sender authorization, redaction, logging, and channel naming are approved.
- **Limit to read command:** Accept only a dangerous-by-default Android `sms.read` invoke command and defer inbound/reply channel behavior until a separate channel design is approved.
- **Keep SMS hosted-provider only:** Leave the official `sms` channel as Twilio-backed and redirect Android-device SMS channel work unless a new plugin/API seam is explicitly sponsored.

Not applicable; this is a feature request rather than a broken existing behavior report. Source and release inspection give a high-confidence current gap: Android exposes `sms.send` and `sms.search`, while `sms.read`, `sms.received`, and Android SMS receiver ingress are absent.

## Solution Assessment

No, not as one combined automated change. The safer path is to split the Android read command from the Android-device channel/config/security decision and keep the existing Twilio SMS plugin as a separate provider-hosted channel unless maintainers choose a shared contract.

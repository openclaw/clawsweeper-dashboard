## Summary

This remains a product request rather than a confirmed regression: it asks OpenClaw to define how an external event selects a particular live Control UI conversation. The supplied report shows that current session and injection mechanisms do not provide that workflow, but it does not establish a single safe routing policy for multiple tabs, clients, or simultaneously active dashboard sessions. A maintainer should choose the supported notification model before implementation.

## What This Changes

Add a supported way for an external notification source to deliver a notification to the appropriate active Control UI chat session without running an isolated agent turn.

## System Context

The Control UI creates dashboard-scoped chat sessions and sends user turns through the gateway into the agent runtime. External automations currently have session and cron-oriented paths, but this request needs a deliberate gateway-to-UI notification contract that decides whether to target a transcript, a connected client, or both.

## Architecture Diagram

flowchart LR
  A[External notification source] --> B[Gateway notification API]
  C[Control UI session activity] --> D[Active-client or session policy]
  B --> D
  D --> E[Target selection]
  E --> F[Control UI toast or chat entry]
  E --> G[Agent session transcript]

## Best Possible Solution

Define one supported gateway notification contract with explicit delivery semantics, target-selection rules, offline behavior, authorization, and Control UI rendering; avoid an implicit global “active session” shortcut until those user-facing policies are agreed.

Options:

- **Connected-client notifications (recommended):** Add a gateway event for authorized connected Control UI clients and render a toast or inbox item without silently writing into an agent transcript.
- **Explicit durable destination:** Allow a configured or caller-supplied session target for durable chat entries, with no automatic inference from dashboard activity.
- **Active-session registry:** Adopt a single active-session registry only after defining conflict resolution, expiry, authorization, and no-connected-client behavior.

## Evidence

- **Issue evidence:** The report describes dashboard sessions as distinct UUID-based sessions, says `sessions_send` does not propagate from the main session to dashboard children, and reports that `chat.inject` is persisted but filtered from the Control UI display.
- **Scope ambiguity:** The proposed registry names one active session per agent, but the issue does not define behavior when the same agent is open in multiple dashboard tabs or clients, when no dashboard is connected, or when a notification should become durable transcript content rather than transient UI state.
- **Related-item check:** The supplied related reports concern reply initialization failures, sidebar navigation, an incorrect agent label, and inherited model overrides. Their stated behaviors are adjacent Control UI/session concerns, not evidence of a canonical notification-routing implementation.

## Risks / Open Questions

- Implicitly selecting one “active” session can deliver a notification to the wrong user-visible conversation when an agent has multiple open dashboard sessions or clients.
- A Redis-backed registry would add an external-state dependency and conflicts with the repository policy favoring lifecycle-owned canonical state; the storage and expiry model need an explicit owner decision.
- Making an external notification a visible transcript message versus a transient UI notification has different retention, privacy, replay, and user-expectation consequences.

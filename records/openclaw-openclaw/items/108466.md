## Label Justifications

- `P1`: A shipped Telegram channel workflow consistently strips attribution from forwarded messages whenever inbound debounce batches multiple entries, causing agents to act on materially incorrect context.
- `impact:data-loss`: Per-message `forward_origin` metadata is silently discarded while the message text remains, making the loss difficult for users or agents to detect.
- `impact:session-state`: The resulting model turn records forwarded statements as though they came from the forwarding user, producing incorrect conversational context.

## Summary

Current main still joins debounced Telegram entries using only extracted text, so forwarded-message attribution is silently lost before the synthetic message reaches downstream context building. The report is recent, specific, and source-reproducible; it should remain open for a focused regression fix.

## What This Changes

Preserve each forwarded Telegram message's origin attribution when multiple inbound messages are coalesced by the configured debounce window.

## Best Possible Solution

Format every queued entry through one shared Telegram helper that preserves its own forward attribution before joining, with regression coverage for mixed ordinary messages and multiple forwarded messages from different origins; do not attach one origin to the entire synthetic batch.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes at source level: configure a nonzero Telegram inbound debounce and enqueue at least two forwarded messages; the current multi-entry flush deterministically reads only their text. A live Telegram run was not performed during this read-only review.

## Solution Assessment

No, not exactly as proposed: prefixing each entry is the right direction, but the maintainable fix should reuse a shared formatter and cover mixed and multi-origin batches rather than duplicating attribution formatting inside the coalescer.

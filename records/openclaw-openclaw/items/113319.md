## Label Justifications

- `P2`: A configured user-facing voice setting is ignored in the iOS native fallback, producing wrong or unintelligible speech for affected languages without affecting core Gateway availability.
- `impact:ux-friction`: The iOS Talk flow continues to run, but the configured Speech Language does not control native output and there is no reliable in-product recovery for the wrong pronunciation.

## Summary

Keep open. Current main has a concrete iOS fallback path, but it passes only a server Talk directive language into system synthesis while the configured Speech Language is separately used for recognition; a configured Turkish locale can therefore reach TTS as nil and default to the device voice. This is a bounded iOS bug rather than a duplicate of the fallback request in https://github.com/openclaw/openclaw/issues/113056.

## What This Changes

Make iOS native Talk/Wake system TTS honor the configured Speech Language when selecting its system voice.

## System Context

iOS Talk receives speech input, sends the transcript through the Gateway, then plays the assistant reply through ElevenLabs when available or the local system synthesizer when it is not. The Speech Language setting currently feeds speech recognition, while the native fallback needs that same resolved locale for output selection.

## Architecture Diagram

flowchart LR
  A[Speech Language setting] --> B[iOS Talk configuration]
  B --> C[Speech recognition locale]
  C --> D[Gateway chat reply]
  D --> E{Cloud TTS available?}
  E -->|Yes| F[Cloud voice playback]
  E -->|No| G[iOS system voice]
  B -. locale must also reach .-> G
  G --> H[Audible Talk reply]

## Best Possible Solution

Resolve the configured iOS Speech Language once, pass it to the native system-TTS fallback whenever no explicit reply language overrides it, select a matching installed AVSpeechSynthesisVoice gracefully, and cover both configured-locale and unavailable-voice fallback behavior.

No physical-device reproduction was run in this read-only review, but the current-main source gives a high-confidence code path: configured locale selects speech recognition, while fallback TTS receives only a reply directive language and can receive nil.

Yes. Reusing the already configured Speech Language is the narrowest fix because it restores the existing setting's expected output meaning; automatic language detection would add policy and ambiguity that this bug does not require.

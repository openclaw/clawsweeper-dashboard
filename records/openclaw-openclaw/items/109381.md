## Summary

The latest head improves the earlier retry placement, but a transient response body is still consumed before the retryable status is thrown. A dripping 503 can therefore exhaust the shared deadline and prevent a useful second request, so this PR still needs one narrow repair before merge.

Likely related people: @steipete (high confidence, recent provider-retry work) and @Pick-cat (medium confidence, prior merged bounded-response work).

## What This Changes

Adds a wall-clock deadline across generated-music response headers and body reads, moves non-2xx validation into the provider retry loop, and adds loopback timeout and retry coverage.

## Best Possible Solution

Classify 500/502/503/504 from the status immediately, cancel that response body, and throw into the retry loop before reading error details; retain deadline-bounded detail reads for non-retryable failures and add a slow-drip 503-to-200 regression.

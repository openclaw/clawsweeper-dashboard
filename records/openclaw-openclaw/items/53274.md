## Summary

Keep open: current main and the latest release still skip browser Control UI device identity when `crypto.subtle` is unavailable. The scope-preservation subissues are implemented, but the remaining request changes the documented Control UI auth/security boundary and needs maintainer security/product direction.

## What This Changes

The issue asks OpenClaw to generate browser Control UI device identity without depending on `crypto.subtle` so LAN HTTP reverse-proxy deployments are not forced into the device-auth bypass path.

## Best Possible Solution

Keep the implemented scope fixes, then have maintainers choose a documented remote-HTTP identity policy before changing the secure-context gate.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw allow persistent Control UI browser device identity to be generated and used in non-localhost plain-HTTP contexts?

Rationale: Current docs intentionally require HTTPS or localhost for browser device identity, and changing that behavior would alter the auth boundary for operator access in tamperable browser transports.

Likely owner: steipete

Owner reason: The current secure Control UI auth boundary and recent current-path ownership both trace most strongly to steipete/Peter Steinberger history.

Owner confidence: high

Options:

- **Keep secure-context default:** Continue rejecting remote plain-HTTP browser device identity and focus on clearer HTTPS, trusted-proxy, Tailscale, SSH tunnel, and break-glass guidance.
- **Design an explicit opt-in (recommended):** Add remote plain-HTTP device identity only behind a clear, audited operator opt-in with docs and tests for upgrade, warning, and threat-model behavior.
- **Allow by default:** Remove the WebCrypto/secure-context dependency and always attempt browser identity generation, accepting the plaintext transport threat-model change.

## Reproduction Assessment

Yes, source-level. Current main skips browser device identity when `crypto.subtle` is unavailable and docs still define non-localhost plain HTTP as blocked unless using trusted-proxy or break-glass exceptions.

## Solution Assessment

Unclear. Replacing the WebCrypto digest and always attempting identity generation is only the best fix if maintainers intentionally support persistent Control UI browser identity in remote plaintext HTTP contexts.

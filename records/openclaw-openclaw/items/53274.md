## Summary

Keep open: current main and v2026.6.11 still skip browser Control UI device identity when `crypto.subtle` is unavailable. The scope-preservation subissues are implemented, but the remaining change would alter a documented Control UI auth/security boundary and needs maintainer security/product direction.

## What This Changes

The issue requests browser Control UI device identity generation without depending on `crypto.subtle`/secure context for HTTP LAN or reverse-proxy deployments, plus related scope-preservation fixes.

## Best Possible Solution

Keep the implemented scope fixes, then have a maintainer/security decision choose whether remote plain-HTTP browser identity remains rejected, becomes an explicit opt-in policy, or is handled only through HTTPS, trusted-proxy, or Tailscale guidance.

## Reproduction Assessment

Yes. Source inspection shows current main skips browser device identity without `crypto.subtle`, and v2026.6.11 still ships the same secure-context gate; I did not run a live LAN reverse-proxy browser repro in this read-only review.

## Solution Assessment

Unclear. The pure-JS hash and always-attempt identity path is only the best solution if maintainers intentionally support persistent Control UI browser identity in plaintext remote browser contexts.

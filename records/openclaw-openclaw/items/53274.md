## Summary

Keep open: current main and the latest release still skip browser Control UI device identity when `crypto.subtle` is unavailable, while the bypass-scope and implied-scope subissues are already fixed. The remaining request would change the security boundary for browser operator identity over non-localhost plain HTTP, so it needs maintainer security/product direction rather than cleanup closure.

## What This Changes

The issue asks OpenClaw to generate Control UI browser device identity without depending on Secure Context/WebCrypto and includes related scope-preservation fixes for the device-auth bypass path.

## Best Possible Solution

Keep the shipped scope fixes, then have maintainers decide whether remote plain-HTTP browser identity stays rejected, becomes an explicit insecure opt-in, or is handled only through HTTPS, trusted-proxy, Tailscale, and diagnostics.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should browser Control UI device identity be allowed after the UI is delivered over non-localhost plain HTTP, and if yes should that be default behavior or an explicit insecure opt-in?

Rationale: The remaining change decides whether persistent operator browser identity can be trusted when the page itself may have been tampered with in transit, which is a maintainer security/product boundary rather than a mechanical SHA-256 helper fix.

Likely owner: steipete

Owner reason: The core decision traces to secure Control UI auth and device-bound connect challenge history that steipete introduced and recently carried forward.

Owner confidence: high

Options:

- **Keep Secure-Context Requirement (recommended):** Continue requiring HTTPS or localhost for browser device identity and rely on trusted-proxy, Tailscale, break-glass, docs, and warning mitigations for self-hosted deployments.
- **Add Explicit Insecure Opt-In:** Allow pure-JS browser identity only behind a clearly named insecure Control UI flag with audit warnings, docs, and tests for default-blocked and opt-in behavior.
- **Allow Plain HTTP By Default:** Remove the secure-context gate and WebCrypto digest dependency by default, accepting a broader remote-plaintext trust model for Control UI operators.

## Reproduction Assessment

Yes. Source inspection on current main shows that a non-secure browser lacks `crypto.subtle`, `buildConnectPlan` skips `loadOrCreateDeviceIdentity()`, and the Gateway still rejects remote device-less Control UI unless a documented exception applies.

## Solution Assessment

Unclear. Replacing the digest and always attempting identity is only the best solution if maintainers intentionally support persistent browser identity after remote plaintext page delivery; otherwise HTTPS/trusted-proxy guidance or an explicit insecure opt-in is safer.

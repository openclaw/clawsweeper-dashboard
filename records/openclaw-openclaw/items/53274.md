## Summary

Keep open: current main and v2026.6.11 still skip browser Control UI device identity when `crypto.subtle` is unavailable. The scope-preservation subissues are implemented, but the remaining behavior change would alter a documented Control UI auth/security boundary and needs maintainer security/product direction.

## What This Changes

The issue requests generating Control UI browser device identity in non-secure HTTP LAN/reverse-proxy deployments and preserving operator scopes when `dangerouslyDisableDeviceAuth` is used.

## Best Possible Solution

Keep this issue open for maintainer security/product direction on whether remote plain-HTTP browser identity remains rejected, becomes an explicit opt-in policy, or is handled only through HTTPS, trusted-proxy, Tailscale, localhost, or break-glass guidance.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw support persistent Control UI browser device identity when the UI is served over non-localhost plain HTTP?

Rationale: Current code and docs intentionally reject remote device-less Control UI sessions to preserve the secure-context/MitM boundary; removing the gate is a product/security policy choice, not a mechanical bug fix.

Likely owner: steipete

Owner reason: Current main blame and prior review context point to recent ownership of the Control UI/gateway identity boundary.

Owner confidence: medium

Options:

- **Keep remote HTTP rejected (recommended):** Retain the current secure-context requirement and focus on warnings, loopback/Tailscale guidance, and trusted-proxy/break-glass recovery paths.
- **Add explicit opt-in support:** Allow remote plaintext browser identity only behind a clearly named dangerous/operator-controlled policy with docs, audit warning, and focused upgrade/security tests.
- **Allow identity unconditionally:** Replace the WebCrypto digest dependency and always attempt browser identity, accepting the changed trust boundary for LAN HTTP deployments.

## Reproduction Assessment

Yes. Current source and tests show remote non-localhost Control UI without device identity is rejected, and the browser client skips identity generation when `crypto.subtle` is unavailable.

## Solution Assessment

Unclear. The pure-JS hash and always-attempt identity path is only the best solution if maintainers intentionally support persistent Control UI browser identity in plaintext remote browser contexts.

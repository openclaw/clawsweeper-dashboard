## Summary

Keep open: current main and v2026.6.11 still intentionally skip browser Control UI device identity when `crypto.subtle` is unavailable, while the reported scope-preservation subissues have already landed. The remaining change is a documented Control UI security-boundary/product decision, not a safe automatic cleanup close.

## What This Changes

The issue requests allowing browser Control UI device identity generation over HTTP reverse-proxy/LAN deployments instead of gating it on browser Secure Context/WebCrypto, plus related scope fixes.

## Best Possible Solution

Keep the implemented scope fixes and have maintainers decide whether remote plain-HTTP browser identity remains rejected, becomes an explicit insecure opt-in, or is handled only through HTTPS, trusted-proxy, Tailscale, and warning/docs guidance.

Question: Should OpenClaw allow browser Control UI device identity to be generated and used when the page is served over remote plain HTTP, and if yes should that be the default or an explicit insecure opt-in?

Rationale: The remaining request is not only a hash helper swap; it decides whether persistent operator browser identity can be trusted after the page was delivered over a tamperable transport.

Likely owner: steipete

Owner reason: The central boundary traces to the device-bound connect challenge and secure Control UI auth work authored by `steipete`.

Owner confidence: high

Options:

- **Keep Secure-Context Requirement (recommended):** Continue blocking remote plain-HTTP device identity and rely on HTTPS, localhost, trusted-proxy, break-glass, and warning/docs mitigations for self-hosted deployments.
- **Add Explicit Opt-In:** Permit pure-JS browser identity only behind a clearly named insecure Control UI policy flag with audit coverage, docs, and tests for default-blocked and opt-in behavior.
- **Allow By Default:** Remove the secure-context gate and WebCrypto digest dependency everywhere, accepting a broader remote-plaintext trust model for Control UI operators.

## Reproduction Assessment

Yes. Source inspection on current main and v2026.6.11 shows the browser client skips device identity without `crypto.subtle`, and current gateway/docs still reject non-localhost plain-HTTP Control UI identity by default.

## Solution Assessment

Unclear. Replacing WebCrypto with pure-JS hashing is mechanically plausible, but it is only the best fix if maintainers intentionally support persistent browser identity after remote plaintext page delivery; an explicit insecure opt-in or keeping the current default may be safer.

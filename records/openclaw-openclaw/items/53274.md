## Summary

Keep open: current main and v2026.6.11 still skip browser device identity when `crypto.subtle` is unavailable, so the central HTTP LAN/reverse-proxy request remains unresolved. The scope-preservation subissues are implemented, but changing the remaining secure-context boundary needs maintainer security/product direction.

## What This Changes

The issue asks OpenClaw to generate Control UI browser device identity in HTTP LAN/reverse-proxy deployments instead of depending on browser Secure Context/WebCrypto availability.

## Best Possible Solution

Keep the shipped scope fixes, then have maintainers decide whether remote plain-HTTP browser identity should remain rejected, become an explicit opt-in mode, or be handled through HTTPS, loopback, trusted-proxy, or Tailscale guidance.

## Reproduction Assessment

Yes, source-level. Current main skips browser device identity without `crypto.subtle`, the fingerprint still uses `crypto.subtle.digest`, and the Gateway rejects remote device-less Control UI unless a trusted-proxy or break-glass path is used.

## Solution Assessment

Unclear. The pure-JS hash and always-attempt identity path is mechanically plausible, but it is only the best solution if maintainers intentionally support persistent Control UI device identity in plaintext remote browser contexts.

## Summary

Keep open: current main still skips browser Control UI device identity when `crypto.subtle` is unavailable, while the bypass-scope and implied operator-scope subissues are already implemented. The remaining request changes a documented Control UI security boundary for remote plaintext HTTP, so it needs maintainer product/security direction rather than an automated fix.

## What This Changes

The issue requests allowing browser Control UI device identity generation over non-secure HTTP LAN/reverse-proxy deployments and includes related Control UI scope fixes.

## Best Possible Solution

Keep the implemented scope fixes, then make an explicit maintainer/security decision on whether remote plain-HTTP browser identity remains rejected, becomes a documented opt-in mode with audit/docs/tests, or is allowed by default.

## Maintainer Decision

Kind: security_boundary

Question: Should browser Control UI device identity be allowed to generate and authenticate after the UI is delivered over remote plain HTTP, and if so should that be an explicit opt-in policy instead of the default?

Rationale: The remaining change is not just replacing a hash helper; it decides whether persistent operator browser identity can be trusted when the page itself may have been modified in transit.

Likely owner: steipete

Owner reason: The central remaining decision traces to the secure Control UI auth boundary introduced in f76e3c141927 and to current Gateway/UI auth policy ownership.

Owner confidence: high

Options:

- **Keep secure-context requirement (recommended):** Continue blocking remote plain-HTTP device identity and rely on HTTPS, localhost, trusted-proxy, break-glass, and warning/docs mitigations for self-hosted deployments.
- **Add explicit opt-in:** Allow pure-JS browser identity only behind a clearly named insecure Control UI policy with security-audit coverage, docs, and tests for both default-blocked and opt-in behavior.
- **Allow by default:** Remove the secure-context gate and WebCrypto digest dependency everywhere, accepting a broader remote-plaintext trust model for Control UI operators.

Yes. Source inspection shows current main skips browser device identity whenever `crypto.subtle` is unavailable and the latest release still ships the same central secure-context gate; I did not run a live browser/reverse-proxy repro in this read-only review.

## Solution Assessment

Unclear. Replacing the digest and always attempting identity is only the best fix if maintainers intentionally support persistent Control UI browser identity after remote plaintext page delivery; otherwise keeping the secure-context block or adding an explicit opt-in is safer.

## Summary

Keep open: current main still skips browser Control UI device identity when `crypto.subtle` is unavailable, while the bypass scope and implied operator-scope subissues are already implemented. The remaining request would change a documented Control UI auth/security boundary for remote plaintext HTTP, so it needs maintainer security/product direction before implementation.

## What This Changes

The issue requests allowing Control UI browser device identity generation and authentication without depending on browser secure context, plus fixing related bypass scope handling.

## Best Possible Solution

Keep the implemented scope fixes, then make an explicit maintainer/security decision on whether remote plain-HTTP browser identity remains rejected, becomes a documented opt-in mode, or is handled only through HTTPS, trusted-proxy, Tailscale, and clearer diagnostics.

Question: Should browser Control UI device identity be allowed to generate and authenticate after the UI is delivered over remote plain HTTP, and if so should that be an explicit opt-in policy instead of the default?

Rationale: The remaining change is not just replacing a hash helper; it decides whether persistent operator browser identity can be trusted when the page itself may have been modified in transit.

Likely owner: steipete

Owner confidence: high

Options:

- **Keep Secure-Context Requirement (recommended):** Continue blocking remote plain-HTTP device identity and rely on HTTPS, localhost, trusted-proxy, break-glass, and warning/docs mitigations for self-hosted deployments.
- **Add Explicit Opt-In:** Allow pure-JS browser identity only behind a clearly named insecure Control UI config flag with security-audit coverage, docs, and tests for default-blocked and opt-in behavior.
- **Allow By Default:** Remove the secure-context gate and WebCrypto digest dependency everywhere, accepting a broader remote-plaintext trust model for Control UI operators.

## Summary

Keep open: current main and v2026.6.11 still gate browser Control UI device identity on `crypto.subtle`, while the scope-bypass subissues are already fixed. The remaining request changes the documented security boundary for remote plain-HTTP Control UI, so it needs maintainer security/product direction.

## What This Changes

Request to let browser Control UI generate device identity over non-secure HTTP by removing the secure-context guard and replacing WebCrypto fingerprinting, with related scope-bypass fixes now mostly landed.

## Best Possible Solution

Keep the shipped scope fixes and have maintainers choose the security policy: preserve HTTPS/localhost as the default, or add a clearly warned explicit opt-in with tests, docs, and audit coverage.

Question: Should browser Control UI device identity be allowed after the UI is delivered over non-localhost plain HTTP, and if yes should that be default behavior or an explicit insecure opt-in?

Rationale: The remaining change decides whether persistent operator browser identity can be trusted when the page itself may have been tampered with in transit, which is a maintainer security/product boundary rather than a mechanical hash-helper fix.

Likely owner: steipete

Owner confidence: high

Options:

- **Keep secure-context requirement (recommended):** Continue requiring HTTPS or localhost for browser device identity and rely on trusted-proxy, Tailscale, break-glass config, docs, and warnings for self-hosted deployments.
- **Add explicit insecure opt-in:** Allow pure-JS browser identity only behind a clearly named insecure Control UI setting with audit warnings, docs, and tests for both default-blocked and opt-in behavior.
- **Allow plain HTTP by default:** Remove the secure-context gate and WebCrypto digest dependency by default, accepting a broader remote-plaintext trust model for Control UI operators.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: in non-secure browser contexts `crypto.subtle` is unavailable, so current main skips browser device identity and the gateway rejects the default Control UI path. I did not run a live browser reverse-proxy scenario in this read-only review.

## Solution Assessment

Unclear. Replacing the digest and always attempting identity is only the best fix if maintainers intentionally support persistent browser identity after remote plaintext page delivery; otherwise the safer solution is to keep HTTPS/localhost as the default or add an explicit insecure opt-in.

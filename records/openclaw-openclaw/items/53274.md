## Summary

Keep open: current main and the latest release still skip browser Control UI device identity when `crypto.subtle` is unavailable. The scope-preservation subissues are implemented, but the remaining request would change the documented Control UI auth/security boundary and needs maintainer security/product direction.

## What This Changes

The issue requests allowing Control UI browser device identity generation over non-secure HTTP contexts and fixing related scope handling for `dangerouslyDisableDeviceAuth`.

## Best Possible Solution

Keep the implemented scope fixes, then have maintainers decide whether remote plain-HTTP browser identity remains rejected, becomes an explicit opt-in policy, or is handled only through HTTPS, trusted-proxy, Tailscale, and warning guidance.

Question: Should OpenClaw allow persistent Control UI browser device identity to be generated and used from non-localhost plain HTTP origins?

Rationale: The remaining change is not just a hash implementation swap; it decides whether a remote plaintext browser context may hold and present operator device identity after receiving UI code over an unauthenticated transport.

Likely owner: steipete

Owner confidence: high

Options:

- **Keep secure-context default (recommended):** Continue rejecting remote plain-HTTP browser device identity by default and focus on warnings, HTTPS/Tailscale guidance, and existing break-glass paths.
- **Add explicit plaintext opt-in:** Permit remote HTTP browser identity only behind a clearly named operator-selected policy with docs, audit warnings, and upgrade tests.
- **Remove the gate globally:** Always attempt browser identity generation without `crypto.subtle`, accepting the broader plaintext transport trust change as the default behavior.

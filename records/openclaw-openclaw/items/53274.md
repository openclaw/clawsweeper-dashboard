## Summary

Keep open: current main and v2026.6.11 still skip Control UI browser device identity when `crypto.subtle` is unavailable, so the central HTTP LAN/reverse-proxy request remains unresolved. The bypass scope-clearing and implied operator-scope subissues are implemented, but relaxing the remaining secure-context boundary needs maintainer security/product direction.

## What This Changes

The issue requests allowing Control UI browser device identity generation without depending on browser Secure Context or `crypto.subtle` for HTTP LAN and reverse-proxy deployments, plus related scope fixes.

## Best Possible Solution

Keep the shipped scope fixes, then have maintainers choose the Control UI remote-plaintext identity contract: keep rejection plus guidance, add an explicit opt-in, or intentionally support pure-JS device identity over LAN HTTP with matching docs and tests.

## Reproduction Assessment

Yes. Source inspection on current main shows the browser client skips device identity unless `crypto.subtle` exists, the device fingerprint still uses `crypto.subtle.digest`, and the gateway rejects remote device-less Control UI under the current policy.

## Solution Assessment

Unclear. The pure-JS hash and always-attempt identity path is mechanically plausible, but it is only the best solution if maintainers intentionally support persistent Control UI browser identity in plaintext remote browser contexts.

## Summary

Keep open: the scope-preservation subissues are fixed, but current main and v2026.6.11 still intentionally skip browser Control UI device identity when `crypto.subtle` is unavailable. The remaining request would change a documented Control UI auth/security boundary, so it needs maintainer security/product direction rather than an automatic cleanup close.

## What This Changes

Allow browser Control UI device identity to be generated without browser Secure Context/WebCrypto so HTTP LAN and reverse-proxy deployments do not have to disable device auth.

## Best Possible Solution

Maintainers should decide the remote plain-HTTP browser identity policy; if approved, implement a documented and tested UI identity path that avoids WebCrypto without loosening existing secure defaults by accident.

Options:

- **Keep Secure Context Default (recommended):** Maintain the current HTTPS/localhost requirement and resolve the remaining user pain through warnings, docs, Tailscale/trusted-proxy guidance, and the existing break-glass flag.
- **Allow Plain-HTTP Identity:** Permit pure-JS device identity on remote HTTP with explicit docs, dependency review, gateway/UI regression tests, and security copy that explains LAN MitM tradeoffs.
- **Add Explicit Policy Gate:** Keep the default secure but add a narrowly named operator opt-in for remote HTTP device identity if maintainers want a supported self-hosted LAN exception.

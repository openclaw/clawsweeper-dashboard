## Summary

Keep open: current main and v2026.6.11 still intentionally skip browser Control UI device identity when `crypto.subtle` is unavailable, while the scope-preservation subissues are already implemented. The remaining request would change a documented Control UI auth/security boundary, so it needs maintainer security/product direction rather than an automatic fix PR.

## What This Changes

Request allowing browser Control UI device identity generation over HTTP LAN or reverse-proxy deployments instead of skipping identity when `crypto.subtle` is unavailable.

## Best Possible Solution

Keep the implemented scope fixes, then make an explicit maintainer/security decision on whether remote plain-HTTP browser identity remains rejected, becomes a documented opt-in mode, or is handled only through HTTPS, trusted-proxy, or Tailscale guidance.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should browser Control UI device identity be allowed to generate and authenticate after the UI is delivered over remote plain HTTP, and if so should that be an explicit opt-in policy rather than the default?

Rationale: The remaining change is not just replacing a hash helper; it decides whether persistent operator browser identity can be trusted when the page itself may have been modified in transit.

Likely owner: steipete

Owner reason: The central boundary traces to the device-bound connect challenge and secure Control UI auth work, and current moved UI paths also route through recent steipete-owned commits.

Owner confidence: high

Options:

- **Keep Secure-Context Requirement (recommended):** Continue blocking remote plain-HTTP device identity and rely on HTTPS, localhost, trusted-proxy, break-glass, and warning/docs mitigations for self-hosted deployments.
- **Add Explicit Opt-In:** Allow pure-JS browser identity only behind a clearly named insecure Control UI config flag with security-audit coverage, docs, and tests for default-blocked and opt-in behavior.
- **Allow By Default:** Remove the secure-context gate and WebCrypto digest dependency everywhere, accepting a broader remote-plaintext trust model for Control UI operators.

## Reproduction Assessment

Yes. Source inspection on current main shows browser Control UI skips device identity when `crypto.subtle` is unavailable, and the latest release tag still ships the same central secure-context gate.

## Solution Assessment

Unclear. The pure-JS digest and always-attempt identity path is only the best solution if maintainers intentionally support persistent Control UI browser identity after remote plaintext page delivery; otherwise warning/docs, HTTPS, trusted-proxy, or an explicit opt-in are safer.

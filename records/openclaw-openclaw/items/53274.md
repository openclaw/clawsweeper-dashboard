## Summary

Keep open: current main and v2026.6.11 still skip browser Control UI device identity when `crypto.subtle` is unavailable, while the bypass-scope and implied-scope subissues are already fixed. The remaining request changes the documented Control UI security boundary for remote plaintext HTTP, so it needs maintainer security/product direction.

## What This Changes

Requests allowing Control UI browser device identity generation over non-secure HTTP reverse-proxy or LAN deployments, plus preserving bypass scopes and implied operator scopes.

## Best Possible Solution

Keep the shipped scope fixes, then have maintainers decide whether remote plain-HTTP browser identity stays rejected, becomes an explicit insecure opt-in, or is handled only through HTTPS, trusted-proxy, Tailscale, and diagnostics.

Question: Should browser Control UI device identity be allowed after the UI is delivered over non-localhost plain HTTP, and if yes should that be default behavior or an explicit insecure opt-in?

Rationale: The remaining change decides whether persistent operator browser identity can be trusted when the page itself may have been tampered with in transit, which is a maintainer security/product boundary rather than a mechanical hash-helper fix.

Likely owner: steipete

Owner confidence: high

Options:

- **Keep Secure-Context Requirement (recommended):** Continue requiring HTTPS or localhost for browser device identity and rely on trusted-proxy, Tailscale, break-glass, docs, and warning mitigations for self-hosted deployments.
- **Add Explicit Insecure Opt-In:** Allow pure-JS browser identity only behind a clearly named insecure Control UI flag with audit warnings, docs, and tests for default-blocked and opt-in behavior.
- **Allow Plain HTTP By Default:** Remove the secure-context gate and WebCrypto digest dependency by default, accepting a broader remote-plaintext trust model for Control UI operators.

## Reproduction Assessment

Yes. Source inspection on current main shows browser Control UI skips device identity when `crypto.subtle` is unavailable, and v2026.6.11 still ships the same central secure-context gate.

## Solution Assessment

Unclear. The pure-JS digest and always-attempt identity path is only the best solution if maintainers intentionally support persistent browser identity after remote plaintext page delivery; otherwise the safer shape is HTTPS/trusted-proxy guidance or an explicit insecure opt-in.

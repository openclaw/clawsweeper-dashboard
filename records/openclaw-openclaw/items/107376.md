## Summary

Keep open: current main still has the unbounded inbound buffer, and the patch is technically sound, but an IRC owner must confirm how a protocol-triggered disconnect should affect account status and recovery before merge.

## What This Changes

Adds a 512-byte inbound IRC record limit, closes the socket on oversized complete or pending records, and adds real TCP boundary, fragmentation, and UTF-8 coverage.

## Best Possible Solution

Keep byte-bounded inbound parsing, but define and test the full post-violation account lifecycle so status becomes accurate and reconnect-versus-manual-restart behavior is intentional.

Question: When a connected IRC server sends an oversized record, should the account stay down, reconnect, or discard the record and continue?

Rationale: The protocol permits closing, but the existing passive monitor does not establish how a deliberate post-ready close updates account status or recovers, and each option has different security and availability tradeoffs.

Likely owner: vignesh07

Owner reason: The repository explicitly assigns IRC ownership to vignesh07, making them the best available owner for the channel lifecycle tradeoff.

Owner confidence: high

Options:

- **Fail closed with explicit lifecycle (recommended):** Preserve the disconnect, propagate the terminal protocol error into account status, and make the chosen bounded recovery behavior explicit and tested.
- **Discard and resynchronize:** Bound memory by discarding bytes until the next line terminator, report the violation, and keep the connection alive.
- **Accept manual recovery:** Merge the current behavior with an acknowledged requirement that operators restart the IRC account or gateway after a violation.

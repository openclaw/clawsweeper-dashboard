## Summary

Keep open. The report describes a credible message-delivery failure with repeated token-burning retries, while current public Telegram documentation still treats locations as standalone sends rather than text/media companions. Current evidence does not prove that `main` handles this deterministic message-tool error or that the reported zombie-run behavior shares the same root cause.

Likely related people: `eleqtrizit` and `dutifulbob` are low-confidence routing candidates from recent agent tool-loop guard work.

## What This Changes

Fix message-tool sends that repeatedly fail when a model adds a placeholder Telegram location object to otherwise valid text or media output, and prevent the resulting run from retrying indefinitely.

## System Context

The agent model emits a `message` tool call, which is validated and converted into a channel-specific outbound payload before Telegram delivery. Invalid mixed location-and-text payloads return a tool error to the agent loop; without suitable error handling, the next model round can repeat the same invalid request instead of ending the run.

## Architecture Diagram

flowchart LR
  A[Agent model] --> B[Message tool call]
  B --> C[Outbound payload validation]
  C -->|valid standalone location or text/media| D[Telegram delivery]
  C -->|mixed location with text/media| E[Tool error result]
  E --> F[Agent retry loop]
  F --> A

## Best Possible Solution

Preserve standalone native-location sends, narrow the message-tool schema or action validation so ordinary sends do not invite a location payload, and classify repeated identical mixed-payload validation failures as terminal rather than repeatedly returning them to the model; cover both the valid location path and the failed mixed-payload path with regression tests.

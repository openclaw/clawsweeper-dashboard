## Summary

Keep open: current main and v2026.6.11 still model Slack as static bot/app/signing-secret credentials, while native token rotation would add Slack OAuth refresh storage, secret handling, and live runtime adoption that need maintainer product and security direction first.

## What This Changes

Add native Slack OAuth token rotation so OpenClaw can refresh expiring Slack bot tokens through the oauth.v2.access refresh-token flow without an external daemon.

## Best Possible Solution

Design a Slack-plugin-owned rotation lifecycle with secure persisted state, transactional refresh/update, status and doctor recovery, docs, and Socket/HTTP adoption proof while preserving static-token setups.

## Maintainer Decision

Question: Should the Slack plugin own native OAuth token rotation, and where should Slack client secrets, refresh tokens, expiry metadata, and refreshed bot tokens be stored and adopted at runtime?

Rationale: This changes credential persistence, OAuth secret custody, and live Slack auth behavior, so automation cannot safely choose the secret storage, redaction, migration, recovery, and operator UX model.

Likely owner: steipete

Owner reason: steipete is already visible in this issue's Slack OAuth discussion path and has recent Slack credential documentation history.

Owner confidence: high

Options:

- **Design plugin-owned rotation (recommended):** Build rotation inside the Slack plugin with secure storage, transactional refresh, status/doctor recovery, docs, and live Socket Mode plus HTTP Mode proof.
- **Create a generic refresh seam first:** Define a reusable credential-refresh contract before implementing Slack as one consumer if maintainers want token refresh to generalize beyond Slack.
- **Defer to external rotation:** Keep OpenClaw on static Slack token inputs for now and document external rotation or manual operational workarounds until maintainers want to own rotating Slack secrets.

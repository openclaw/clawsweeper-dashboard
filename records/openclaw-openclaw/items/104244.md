## Summary

This PR remains necessary because current main still reports UTF-16 string length as byte metadata for non-ASCII Code Mode API files. The updated real runtime output clears the prior proof blocker, and the focused implementation, regression coverage, dependency contract, and current-main comparison show no actionable correctness or security finding; it can proceed through ordinary maintainer review.

## What This Changes

The PR computes UTF-8 byte lengths for Code Mode virtual API files before QuickJS marshalling and exposes the canonical value through both `API.list()` and `API.read()`, with regression coverage.

## Best Possible Solution

Land the host-boundary UTF-8 calculation so every virtual file carries one canonical byte count that both guest APIs reuse, retaining the focused non-ASCII regression test.

## Maintainer Decision

## Reproduction Assessment

Yes, source-reproducible with high confidence. Current main uses JavaScript string length as the byte value, so any generated declaration containing non-ASCII characters deterministically underreports its UTF-8 size.

## Solution Assessment

Yes. Computing the value once at the Node host-to-guest boundary is the narrowest maintainable fix, matches the pinned QuickJS serializer contract, and avoids duplicate encoding logic or competing list/read calculations.

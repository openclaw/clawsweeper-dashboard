## Label Justifications

- `P1`: The issue is a source-proven sandbox isolation bug that can make co-hosted instances share an exec container and operate on the wrong workspace.
- `impact:data-loss`: The reported collision can make exec reads and writes land in another instance's mounted workspace.
- `impact:security`: The sandbox container identity gap weakens the isolation boundary between separate same-host OpenClaw instances.
- `impact:session-state`: Wrong-container reuse can associate agent/session work with another instance's sandbox state and files.

## Summary

Keep open. Current main and latest release still derive non-shared sandbox runtime names from scope keys without workspace or instance identity, while https://github.com/openclaw/openclaw/pull/96866 is the active unmerged candidate fix.

## What This Changes

Ensure Docker-backed agent and browser sandbox containers are unique per OpenClaw instance or workspace rather than only per agent/session scope key.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/96866, or an equivalent workspace-qualified non-shared sandbox identity fix, with explicit upgrade/reset and security sign-off.

## Reproduction Assessment

Yes, at source level. Current main resolves `scope: "agent"` to `agent:main` and derives Docker/browser names from that scope key, so two HOME-isolated instances using the default agent can collide without needing a live Docker run here.

## Solution Assessment

Yes, the active PR's workspace-qualified non-shared scope key is the right layer because Docker, browser, SSH, workspace, and recreate paths already consume the scope-key contract. The issue should stay open until that PR, or an equivalent maintainer-approved fix, merges.

## Label Justifications

- `P1`: The source-proven bug can make co-hosted OpenClaw instances share an exec sandbox container and operate on the wrong workspace.
- `impact:data-loss`: A shared sandbox container can route writes from one instance into another instance's mounted workspace.
- `impact:security`: The issue weakens the Docker sandbox isolation boundary between separately configured instances on the same host.
- `impact:session-state`: Wrong-container reuse can expose or mutate another instance's workspace, agent context, and session files.

## Summary

Keep open. Current main and the latest release still derive Docker and sandbox-browser runtime names from shared or agent scope keys before workspace or instance identity participates, while https://github.com/openclaw/openclaw/pull/96866 is an open candidate fix rather than a merged implementation.

## What This Changes

The issue asks OpenClaw to make Docker sandbox container identity unique across multiple HOME-isolated instances on the same host.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/96866 or an equivalent security-reviewed fix that scopes non-shared sandbox runtime identity by resolved workspace across Docker, browser, SSH, recreate commands, docs, and regression tests.

## Reproduction Assessment

Yes. Current main is source-reproducible: non-shared sandbox scope keys and Docker/browser container names are derived without workspace identity, and a running same-name container with mismatched hash can be kept as hot; I did not run a live two-HOME Docker repro in this read-only review.

## Solution Assessment

Yes on direction, with maintainer/security sign-off. Centralizing workspace identity in the non-shared sandbox scope key is better than a Docker-container-name-only patch because Docker, browser, SSH, skills workspace, and recreate paths already consume that scope contract.

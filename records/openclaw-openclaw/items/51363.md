## Label Justifications

- `P1`: The source-proven bug can make co-hosted OpenClaw instances share an exec sandbox container and operate on the wrong workspace.
- `impact:data-loss`: Wrong-container reuse can route file writes from one instance into another instance's mounted workspace.
- `impact:security`: The issue weakens the Docker sandbox isolation boundary between separately configured instances on the same host.
- `impact:session-state`: Wrong-container reuse can expose or mutate another instance's workspace, agent context, and session files.

## Summary

Keep open. Current main and the latest release still derive non-shared Docker and sandbox-browser runtime names from scope keys without workspace or instance identity, while https://github.com/openclaw/openclaw/pull/96866 is still an open candidate fix rather than merged code.

## What This Changes

The issue requests instance-unique Docker sandbox container names so multiple HOME-isolated OpenClaw instances on one host do not share one exec container.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/96866 or an equivalent security-reviewed fix that scopes non-shared sandbox runtime identity by resolved workspace across Docker, browser, SSH, recreate, docs, and regression tests.

## Reproduction Assessment

Yes. Current main is source-reproducible: non-shared sandbox scope keys and Docker/browser container names are derived without workspace identity, matching the co-hosted instance collision report; I did not run a live multi-Docker-instance repro.

## Solution Assessment

Yes on direction, but maintainer/security review is still needed. Workspace-scoping the sandbox lifetime key is better than a Docker-only name patch because Docker, browser, SSH, registry, skills workspace, and recreate paths all consume that scope contract.

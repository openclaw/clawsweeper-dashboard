## Summary

Keep open. Current main and v2026.6.11 still derive non-shared Docker and browser sandbox runtime names from scope keys without workspace identity, while the active fix remains an open PR that needs maintainer/security acceptance before this issue can close.

## What This Changes

The issue reports that co-hosted OpenClaw instances using the same default agent key can derive the same Docker sandbox container name and share the wrong workspace.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/96866 or an equivalent security-reviewed fix that scopes non-shared sandbox identity by resolved workspace across Docker, browser, SSH, recreate behavior, docs, and regression tests.

## Reproduction Assessment

Yes. Current main is source-reproducible: non-shared sandbox scope keys and container names are derived without workspace identity, matching the co-hosted instance collision report; I did not run a live Docker two-HOME repro in this read-only review.

## Solution Assessment

Yes on direction, with maintainer/security review. Workspace-scoping the non-shared sandbox lifetime key is more maintainable than changing only the Docker name because Docker, browser, SSH, skills workspace, and recreate paths already consume that scope contract.

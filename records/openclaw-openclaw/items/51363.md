## Summary

Keep open. Current main and v2026.6.11 still derive non-shared sandbox runtime names from scope keys without workspace or instance identity, and https://github.com/openclaw/openclaw/pull/96866 remains the active unmerged candidate fix for this security-sensitive bug.

## What This Changes

The issue reports that co-hosted HOME-isolated OpenClaw instances with Docker sandbox enabled can reuse the same agent-scoped container name and mount the wrong workspace.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/96866, or an equivalent security-reviewed fix that scopes non-shared sandbox runtime identity by resolved workspace across Docker, browser, SSH, recreate, docs, and regression tests.

## Reproduction Assessment

Yes at source level, though I did not run a live Docker repro in this read-only review. Current main still derives agent/shared sandbox names from scope keys without workspace identity, matching the reported co-hosted instance collision.

## Solution Assessment

Yes on direction, with maintainer acceptance of the upgrade reset. Centralizing workspace identity in the non-shared scope key is better than a Docker-only name patch because Docker, browser, SSH, skills workspace, registry, and recreate paths all consume that scope contract.

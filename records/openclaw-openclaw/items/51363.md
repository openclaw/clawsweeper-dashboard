## Label Justifications

- `P1`: The source-proven bug can make co-hosted OpenClaw instances share an exec sandbox container and operate on the wrong workspace.
- `impact:data-loss`: A shared sandbox container can route writes from one instance into another instance's workspace.
- `impact:security`: The issue weakens the Docker sandbox isolation boundary between separately configured instances on the same host.
- `impact:session-state`: Wrong-container reuse can expose or mutate another instance's workspace, agent context, and session files.

## Summary

Keep open. Current main and the latest release still derive non-shared Docker and sandbox-browser runtime names from scope keys that omit workspace or instance identity, while https://github.com/openclaw/openclaw/pull/96866 is an open candidate fix rather than merged code.

## What This Changes

The issue asks OpenClaw to make Docker sandbox runtime names unique per co-hosted instance so same-agent instances do not share one container.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/96866 or an equivalent security-reviewed fix that scopes non-shared sandbox runtime identity by resolved workspace across Docker, browser, registry, recreate, and sibling sandbox paths.

## Reproduction Assessment

Yes. Source inspection shows current main derives non-shared Docker and browser container names from scope keys without workspace identity, and the Docker hot-container path can keep a same-named running container with a mismatched config hash.

## Solution Assessment

Yes on direction, but it needs maintainer/security review. Workspace-scoping the sandbox lifetime key is more maintainable than a Docker-name-only patch because Docker, browser, registry, recreate, and sibling backend paths all consume that identity contract.

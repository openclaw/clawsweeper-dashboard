## Summary

Keep open. Current main and v2026.6.11 still derive non-shared sandbox runtime/container identity from scope keys without workspace or instance identity, while https://github.com/openclaw/openclaw/pull/96866 remains the open candidate fix path.

## What This Changes

The issue reports that co-hosted HOME-isolated OpenClaw instances with Docker sandboxing reuse the same agent-scope container name, causing exec operations to read or write another instance's workspace.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/96866 or an equivalent security-reviewed fix that scopes non-shared sandbox runtime identity by resolved workspace across Docker, browser, SSH, recreate, docs, and regression tests.

## Reproduction Assessment

Yes. Current main is source-reproducible: agent-scope and session-scope sandbox identities omit workspace identity, and Docker/browser container names are derived from those scope keys without a per-instance discriminator.

## Solution Assessment

Yes on direction, but maintainer/security review is still needed. Central workspace-scoped sandbox identity is a better fix than a Docker-only name patch because Docker, browser, SSH, registry, skills workspace, and recreate paths all consume the same scope contract.

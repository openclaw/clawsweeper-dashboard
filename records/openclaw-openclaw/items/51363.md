## Label Justifications

- `P1`: The source-proven bug can make co-hosted OpenClaw instances share an exec sandbox container and operate on the wrong workspace.
- `impact:data-loss`: Wrong-container reuse can route writes from one instance into another instance's mounted workspace.
- `impact:security`: The issue weakens the Docker sandbox isolation boundary between separately configured instances on the same host.
- `impact:session-state`: Wrong-container reuse can expose or mutate another instance's workspace, agent context, and session files.

## Summary

Keep open. Current main and v2026.6.11 still derive non-shared Docker and sandbox-browser runtime names from scope keys without workspace or instance identity, and the active candidate fix at https://github.com/openclaw/openclaw/pull/96866 is still open and currently conflicting.

## What This Changes

The issue requests instance-unique Docker sandbox container naming so HOME-isolated co-hosted OpenClaw instances cannot share a sandbox container and workspace.

## Best Possible Solution

Rebase and land https://github.com/openclaw/openclaw/pull/96866, or an equivalent security-reviewed fix that scopes non-shared sandbox runtime identity by resolved workspace across Docker, browser, SSH, recreate, docs, and regression tests.

## Reproduction Assessment

Yes at source level. Current main derives non-shared sandbox scope keys and Docker/browser container names without workspace identity, matching the reported two-HOME same-agent collision path.

## Solution Assessment

Yes on direction, but not as a new parallel fix. The best solution is the workspace-scoped non-shared sandbox identity path already represented by the active PR, with maintainer acceptance of the upgrade reset.

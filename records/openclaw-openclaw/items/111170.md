## Summary

Keep this PR open for normal merge review. The current `main` implementation accepts replacement-character-decoded claims from malformed JWT payload bytes, while this focused change makes that parsing fail closed and preserves the established opaque-grant fallback for identity-less OAuth credentials.

## What This Changes

The PR changes JWT payload decoding in execution auth-binding fingerprints to require valid UTF-8 and adds a regression test for malformed payload bytes.

## Best Possible Solution

Merge the narrow strict-decoding change after the normal PR checks finish, retaining the existing opaque-grant fallback when no valid JWT identity can be decoded.

## Reproduction Assessment

Yes from source: a base64url JWT payload containing invalid UTF-8 can reach the current lenient decode, parse as JSON with U+FFFD in an identity claim, and remain stable across access-token rotation. The PR supplies a focused real-function proof transcript and a matching regression test, although this read-only review did not independently execute it.

## Solution Assessment

Yes. Fatal UTF-8 decoding is the narrowest maintainable fix because malformed JSON already follows the same existing catch-and-no-identity path, while post-parse U+FFFD filtering would reject legitimate Unicode content.

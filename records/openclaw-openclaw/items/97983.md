## Summary

Keep open: current main still defines iOS/WebChat messages as Gateway `chat.send` requests with automatic WebChat final replies, while the issue has multiple shipped-release field reports where native iOS app messages append without `chat.send`, dispatch, run, or assistant-reply evidence; the closed package-parity conflict fix only covers an overlapping family, not this native transport failure.

## What This Changes

Fix the official iOS/WebChat path where native app messages append to `agent:main:main` but do not start a normal assistant turn or deliver the final reply.

## Best Possible Solution

Prove current-main native iOS send end to end against Gateway logs/history, then fix the layer that bypasses or loses `chat.send` while preserving internal WebChat automatic final replies.

## Reproduction Assessment

Partially. Multiple users reproduced the shipped iOS symptom and one A/B test shows browser WebChat replies on the same session, but no current-main live iOS run has isolated whether the break is in native WebSocket handshake, route lease, `chat.send` dispatch, or transcript projection.

## Solution Assessment

Current main and the closed package-parity issue are not sufficient by themselves; the best fix is a targeted native iOS/Gateway transport repair plus regression proof for `chat.send` ack, `dispatchInboundMessage`, transcript, and app-visible final reply.

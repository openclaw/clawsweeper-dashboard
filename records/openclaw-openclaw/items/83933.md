## Label Justifications

- `P1`: The PR addresses a real cron workflow where manual verification can destroy a future scheduled one-shot job and lose scheduled work.
- `merge-risk: 🚨 compatibility`: Manual `cron run` semantics and public cron state shape change for existing users and protocol clients.
- `merge-risk: 🚨 session-state`: The diff changes persisted cron job state, retry counters, backoff windows, and terminal status interpretation.
- `merge-risk: 🚨 message-delivery`: Cron state decides future scheduled agent/message fires, so a bad manual/scheduled split could suppress or duplicate scheduled delivery.

## Summary

Keep open: this PR is still necessary because current main still routes manual cron completion through the scheduled-run result path, while the branch provides the canonical candidate fix for the linked manual `deleteAfterRun` data-loss bug. I found no blocking code defect in the latest reviewed diff, but the change remains maintainer-review material because it changes compatibility-sensitive cron scheduling state and adds a public cron state field.

## What This Changes

Adds an `isManual` completion option for cron manual runs, records `lastRunWasManual`, preserves scheduled delete/retry/backoff/alert state for manual runs, and expands cron regression coverage.

## Best Possible Solution

Land the shared `applyJobResult` manual-run isolation after maintainer acceptance and current-head CI/cron validation, keeping failed-run cleanup policy in the separate related issue.

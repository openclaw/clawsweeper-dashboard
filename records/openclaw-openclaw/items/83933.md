## Summary

Keep this PR open, but it still needs changes before merge: the exact head is unchanged from the previous review and still misclassifies a user-invoked due trigger check as scheduler-owned work, allowing that request to mutate persistent retry, backoff, and catch-up state.

## What This Changes

The PR makes manual cron executions preserve delete-after-run jobs and scheduler-owned retry state, adds persisted last-run origin metadata, and expands regression coverage for manual and scheduled execution paths.

## Best Possible Solution

Carry a closed execution-origin value from the public-run and timer entry points through preparation and result application, keeping every explicit `cron run` request manual while reserving scheduled retry and catch-up mutation for timer-owned polling.

Yes. On the exact current head, invoke public `cron.run(jobId, "due")` for a trigger job whose evaluator throws or is unavailable; the changed path passes `isManual: false`, so scheduled counters, backoff, and origin state are mutated by a user request.

## Solution Assessment

No, not yet. Manual isolation is the correct policy, but deriving scheduler ownership from whether trigger evaluation fired is less safe than carrying explicit origin from the actual public-run or timer entry point.

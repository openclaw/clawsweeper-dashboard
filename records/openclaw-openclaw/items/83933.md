## Summary

Keep this PR open. Its explicit run-origin model is a plausible boundary for separating operator, scheduler, and on-exit behavior, but the final head changed manual-error accounting after the supplied live transcript and needs both final-head runtime proof and a maintainer decision on whether manual failures should affect error counters and failure alerts.

## What This Changes

The branch adds an internal cron run origin and persisted manual-run marker so manual runs preserve scheduled one-shots and timing while timer and gateway on-exit runs retain scheduler-consuming behavior.

## System Context

Cron jobs can be run manually through the CLI/RPC, by the scheduler timer, or after a watched process exits. Each run records an outcome in the cron store, which then determines deletion, retry/error accounting, and when the next scheduled fire occurs.

## Architecture Diagram

flowchart LR
  A[Operator CLI or RPC run] --> D[Identify cron run origin]
  B[Scheduler timer tick] --> D
  C[Gateway exit watcher] --> D
  D --> E[Run job and record outcome]
  E --> F[Update cron store state]
  F --> G[Delete one-shot or retain next scheduled fire]
  F --> H[Retry counters and failure alerts]

## Best Possible Solution

Keep run origin internal, preserve the scheduled slot and one-shot behavior for operator runs, and explicitly separate any operator-facing error observability from scheduler retry counters before merging; prove the agreed policy on the final head through a live gateway, CLI, and persisted-store transcript.

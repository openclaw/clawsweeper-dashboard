## Summary

Keep this PR open: it addresses the reported destructive manual-run behavior, but the final patch still persists manual error counts into scheduler state. A later timer failure can then inherit those counts for retry/backoff or disable decisions, which conflicts with the stated non-consuming operator-run contract. The supplied live transcript is also pinned to an earlier head and does not cover the later outcome-path changes.

## What This Changes

This PR distinguishes operator, timer, and gateway on-exit cron runs so manual runs retain scheduled one-shots while scheduler-owned runs continue to delete and reschedule jobs.

## System Context

The cron service accepts manual CLI/RPC runs, periodic timer ticks, and gateway on-exit watcher runs, then persists each job outcome. That persisted outcome determines one-shot deletion, retry and backoff counters, future run slots, alerts, and what gateway clients observe.

## Architecture Diagram

flowchart LR
  A[Manual CLI or RPC run] --> D[Cron service]
  B[Scheduled timer tick] --> D

  D --> E[Run-origin outcome handling]
  E --> F[Persisted cron job state]
  F --> G[Retry timing and counters]
  F --> H[One-shot deletion or retention]

## Best Possible Solution

Keep scheduler-owned counters, retry/backoff progression, disable thresholds, and future slots untouched by operator runs; if manual failures need observability, compute any alert or display result without persisting it into the scheduler counter sequence, then prove the final head through a live gateway, CLI, and restarted store.

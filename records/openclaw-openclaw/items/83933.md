Full review comments:

- **[P1] Preserve scheduled cron backoff across operator outcomes:** `src/cron/service/jobs.ts:95-99`
  - body: Late finding on the previously reviewed head: returning no backoff whenever `lastRunWasManual` is true loses the provenance of an earlier scheduled error. Manual finalization still runs `recomputeNextRunsForMaintenance`, so a cron job whose retry timestamp is not a natural cron slot can have that preserved retry immediately replaced after an operator success, skip, or error. Keep scheduler-owned last-error/backoff state separate from the latest operator outcome, and cover a full `cron.run` followed by maintenance/restart for a cron-schedule job.
  - late: true
  - confidence: 0.96
- **[P1] Keep watcher-terminal origin out of the public run contract:** `src/cron/service-contract.ts:26-32`
  - body: Late finding on the previously reviewed head: `CronServiceRunOptions` is part of the public facade shared with the plugin SDK, so adding `origin` lets any in-process caller request scheduler-consuming semantics even though the PR states only the Gateway watcher should do so. Public `run` should remain operator-only; expose a core-internal watcher method or capability so plugins cannot accidentally delete one-shots or mutate scheduler counters through this option.
  - late: true

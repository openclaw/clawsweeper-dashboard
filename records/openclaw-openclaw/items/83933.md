## Label Justifications

- `P1`: The PR addresses a destructive cron workflow where manual verification can consume or alter scheduled future execution state for real users.
- `merge-risk: 🚨 compatibility`: The branch changes manual `cron run` semantics and adds a persisted/gateway-protocol cron state field that existing cron tooling and upgrades will observe.
- `merge-risk: 🚨 session-state`: Manual runs now intentionally preserve or bypass cron retry counters, backoff windows, disable state, failure-alert cooldowns, and `nextRunAtMs` scheduler state.
- `merge-risk: 🚨 message-delivery`: Incorrect preservation or repair of cron schedule state can make scheduled cron deliveries fire too early, too late, or disappear for `deleteAfterRun` jobs.

## Summary

This PR remains necessary because current main still lacks the manual-run isolation being proposed, and the linked data-loss issue is still open. It is not merge-ready yet: the current head still has a cron-expression backoff regression where post-manual maintenance can treat the manual result as the latest scheduled state and clear or move a pending scheduled backoff window.

## What This Changes

The PR adds manual-run state to cron result handling, gateway cron state schemas, cron run completion paths, backoff resolution, and cron regression tests so `openclaw cron run` does not consume `deleteAfterRun` jobs or mutate scheduled retry state.

## Best Possible Solution

Preserve the non-consuming manual-run contract across both `every` and `cron` schedules, keep scheduled-run retry/delete/alert behavior unchanged, then have a cron owner accept the additive `lastRunWasManual` state contract before merge.

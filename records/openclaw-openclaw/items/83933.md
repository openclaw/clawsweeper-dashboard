## Summary

The latest head still misclassifies user-invoked `cron.run(..., "due")` trigger-evaluator failures as scheduled work, allowing a verification run to alter retry state and delay a later scheduled payload. Current main retains the original destructive manual-run behavior, so this PR remains necessary but is not merge-ready.

## What This Changes

The PR makes manual cron runs preserve scheduled deletion, retry, alert, backoff, and due-slot state, persists whether the last run was manual, and adds regression coverage across cron lifecycle paths.

## Best Possible Solution

Carry a closed, caller-owned execution origin through cron preparation and result application: every public `due` or `force` run remains manual, while only timer-owned trigger polling updates scheduled counters and backoff.

## Reproduction Assessment

Yes. The original destructive behavior has direct Gateway CLI evidence, and the remaining defect has a deterministic path through public `cron.run(id, "due")` when trigger evaluation errors or is unavailable.

## Solution Assessment

No. Manual-run isolation is the correct behavior, but inferring scheduler ownership from trigger-evaluation output is not the safest implementation; the invocation owner already knows the origin and should pass it explicitly.

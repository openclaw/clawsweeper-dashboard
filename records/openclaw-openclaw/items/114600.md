## Label Justifications

- `P1`: A released terminal-chat workflow becomes difficult to use during long streamed responses, affecting active users rather than a cosmetic-only surface.

## Summary

Keep open. This is a fresh, concrete TUI regression report against v2026.7.1, and the cited Control UI copy-scroll fix is a different surface. Current TUI code keeps a streaming run in one `ChatLog` component and updates its text in place, so the remaining investigation is the terminal renderer’s viewport-follow behavior during those renders rather than duplicate message insertion.

## What This Changes

Prevent `openclaw tui --local` from resetting a reader’s viewport while streamed assistant chunks update the active response.

## System Context

The TUI receives streamed agent events through its backend, updates the active assistant entry in the terminal chat log, and asks the Pi-based terminal renderer to repaint. The rendered chat log feeds the user’s terminal viewport, so repaint and follow-mode behavior determine whether manual scrolling remains stable.

## Architecture Diagram

flowchart LR
  A[Agent streaming chunks] --> B[TUI backend events]
  B --> C[Event handlers]
  C --> D[Active assistant chat entry]
  D --> E[Pi terminal renderer]
  E --> F[Terminal viewport]
  G[Reader scroll input] --> F

## Best Possible Solution

Add an explicit follow-mode invariant at the TUI/Pi-renderer boundary: preserve a manually scrolled viewport across stream updates, while advancing only when the reader was already at or near the live bottom; prove it in the local PTY smoke and any necessary upstream Pi contract coverage.

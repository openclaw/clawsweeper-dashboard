## Label Justifications

- `P0`: The reported current behavior is a plugin trust-policy bypass that can execute a native plugin despite an operator deny entry.
- `merge-risk: 🚨 compatibility`: Lowercasing only the manifest record can make existing mixed-case external plugins fail the loader's exact runtime-export ID check after upgrade.

## Summary

This PR is still necessary because current main remains vulnerable, but the current head should not merge: it lowercases the manifest record without updating the strict runtime-export identity check, so previously loadable mixed-case plugins can fail initialization. The refreshed Gateway tests strengthen regression coverage, but the PR body still lacks after-fix proof from a running Gateway.

## What This Changes

The PR lowercases manifest-declared plugin IDs and adds policy and Gateway-startup regression coverage for mixed-case denylist bypasses.

## Best Possible Solution

Use one lowercase, non-alias identity rule across manifest parsing and runtime-definition validation, retain mismatch errors for genuinely different IDs, add coverage for both denied non-import and successful allowed/default mixed-case loading, and provide redacted running-Gateway proof.

No. Canonicalizing at the manifest boundary is the right policy layer, but it is incomplete unless runtime definition validation applies the same canonical identity rule and proves allowed/default plugins still load.

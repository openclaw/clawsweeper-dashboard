## Summary

Keep open: current main has partial hook timeouts, session-lock watchdogs, gateway/channel crash-loop suppression, and a plugin-local Active Memory breaker, but it still lacks the requested framework-level plugin circuit breaker with plugin/hook attribution, persisted lifecycle state, operator controls, and per-plugin degradation policy.

## What This Changes

The issue requests a framework-level plugin circuit breaker with hook timing, plugin/session lock attribution, persisted breaker state, operator visibility/reset, and per-plugin degradation policy.

## Best Possible Solution

Define a maintainer-approved generic plugin-runtime degradation contract first, then phase hook timing/error/lock attribution before enabling any persisted open/half-open/forced-open behavior by default.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw core own a generic plugin circuit breaker with persisted state and operator reset controls, or should circuit breaking remain plugin/channel-specific with only smaller shared telemetry seams in core?

Rationale: The issue describes real stability impact, but the proposed fix changes plugin execution semantics, persistence, config, and operator workflow across all plugins.

Likely owner: Peter Steinberger

Owner reason: Recent history shows repeated ownership across plugin hook timeout, session-lock stability, and gateway architecture work adjacent to this product/API decision.

Owner confidence: high

Options:

- **Design core breaker contract (recommended):** Create a plugin runtime/API design for hook attribution, persisted state, status output, reset commands, fail modes, and upgrade behavior before implementation.
- **Keep breakers plugin-owned:** Narrow this to shared telemetry only, leaving active degradation policy inside each plugin or channel owner.
- **Phase only telemetry first:** Land timing/error/lock attribution without auto-disabling hooks until budgets and compatibility behavior are proven.

## Reproduction Assessment

Yes at the source-design level: current main has hook timeouts and fail-open/fail-closed policy, but no persisted plugin-scoped breaker that skips future hooks after rolling failures. No live multi-agent freeze reproduction was established in this review.

## Solution Assessment

Unclear as an implementation: a generic breaker may be the right end state, but the best first step is a maintainer-approved plugin API and persistence model, likely starting with timing/error/lock attribution before automatic quarantine.

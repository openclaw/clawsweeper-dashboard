## Summary

Keep open: the renderer-only fix targets a real misleading gateway diagnostic, but the branch treats `health.healthy` as ownership proof even though restart health can mark a reachable non-owned listener healthy, which can produce contradictory status guidance.

## What This Changes

The PR changes gateway status rendering so a failed RPC probe with healthy restart status prints credentials/config or restart guidance, and adds render tests for healthy, unhealthy, and unknown health cases.

## Best Possible Solution

Keep the renderer-only approach, but gate the new recovery text on explicit ownership/no-stale-PID proof or carry a separate ownership flag, then add a render regression for the healthy-plus-stale-PID case.

## Reproduction Assessment

Yes by source inspection: current main unconditionally prints the warm-up hint for a failed RPC probe while the loaded service runtime is running. The PR's introduced edge case is also source-reproducible because restart health can set `healthy` from reachability after ownership failed while retaining stale gateway PIDs.

## Solution Assessment

No. The renderer is the right narrow layer, but using `health.healthy` alone is not the best discriminator because it can mean reachable rather than owned; the fix should use explicit ownership or at least exclude stale gateway PIDs.

## Label Justifications

- `P1`: The issue can break Gemini 2.x provider turns that return images from tools by sending a request shape the model rejects and disabling the fallback turn.
- `impact:auth-provider`: The bug is in provider/model capability routing for Google Gemini ids and changes whether the Google transport sends a valid model-specific request shape.

## Summary

Keep open: current main still misclassifies provider-prefixed Gemini 2.x ids as supporting multimodal functionResponse, and no open or merged related item owns this exact remaining fix.

## What This Changes

This issue requests a Google transport fix so prefixed Gemini 2.x model ids use the same image tool-result fallback as bare Gemini 2.x ids.

## Best Possible Solution

Patch the Google transport capability detector to recognize prefixed Gemini ids, then add a regression test proving google/ and models/ Gemini 2.x image tool results keep media out of functionResponse and retain the separate image turn.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes from source: construct buildGoogleGenerativeAiParams with model id google/gemini-2.5-pro, image input, and an image toolResult; the current detector misses the prefixed id and emits functionResponse.parts instead of the fallback turn. I did not execute the harness or a live Google call in this read-only review.

## Solution Assessment

Yes: a narrow prefix-tolerant detector plus focused transport regression coverage is the maintainable fix, because sibling Gemini detectors already use that pattern and the provider prefix is intentionally preserved outside URL construction.

Full review comments:

- **[P1] Do not treat wildcard groups as unknown:** `extensions/telegram/src/unknown-group.ts:12`
  - body: `group-policy-allowlist-empty` is not always an unregistered chat: wildcard `groups["*"]` can intentionally admit the group while sender authorization still fails. Classifying that reason as unknown means `unknownGroupAction: "leave"` can eject the bot from a group the operator deliberately covered with wildcard group config.
  - confidence: 0.88
- **[P2] Use the Telegram thread helper for warnings:** `extensions/telegram/src/bot-handlers.runtime.ts:1660`
  - body: This warning send passes `resolvedThreadId` directly. For forum General topics, current `buildTelegramThreadParams()` intentionally omits `message_thread_id=1`; sending it here can make the warning fail before the bot leaves.
  - confidence: 0.9
- **[P2] Apply unknown-group actions before native commands:** `extensions/telegram/src/bot-handlers.runtime.ts:1644-1645`
  - body: The new action path only runs in the normal message handler, but Telegram native commands are registered first and resolve their own auth. If the first activity in an unknown group is `/help` or another native command, the bot uses the old auth reply path and never warns or leaves.
  - confidence: 0.84
- **[P2] Document the new Telegram config surface:** `src/config/types.telegram.ts:207-220`
  - body: These new operator-facing keys change group security behavior, but the PR only updates the type and Zod schema. Please align the public Telegram/groups docs and config help/metadata so users know how warn/leave interacts with `groups`, `groupAllowFrom`, wildcard groups, and forum topics.
  - confidence: 0.78

## Summary

Keep open: current main and the latest release still lack the requested Discord `trustedWebhooks` allowlist and optional identity-mapping contract. The remaining blocker is maintainer approval of the security model for letting Discord webhook possession trigger agent turns without enabling all bot-authored messages.

## What This Changes

The issue requests a guild-scoped Discord `trustedWebhooks` config that lets selected webhook-authored messages reach the agent and optionally map them to a configured user identity.

## Best Possible Solution

Define a Discord-owned trusted-webhook security contract first; if accepted, implement a strict webhook ID allowlist with focused preflight tests, docs, and either no user mapping or separately approved constrained mapping semantics.

Rationale: The request is narrower than `allowBots: true`, but it makes webhook possession a new authority to enter agent sessions and the proposed user mapping crosses authorization and session-identity boundaries.

Owner confidence: high

Options:

- **Approve allowlist only (recommended):** Add a default-off webhook ID allowlist that can pass the bot-message gate, while deferring or rejecting webhook-to-user mapping until its authorization semantics are defined.
- **Approve constrained user mapping:** Allow `mapToUser` only with strict validation against configured guild users, clear audit behavior, and tests proving it cannot bypass sender authorization or session isolation.
- **Decline Discord webhook ingress:** Keep Discord bot-message policy unchanged and direct external automations to an authenticated webhook plugin or other explicitly owned integration path.

## Solution Assessment

Unclear. A webhook ID allowlist is a plausible narrow solution, but the optional `mapToUser` behavior is not safe to approve without a maintainer-defined trust and authorization contract.

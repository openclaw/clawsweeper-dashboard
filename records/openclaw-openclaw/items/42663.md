## Summary

Keep open: current main and the latest release still only provide broad Discord `allowBots` modes and PluralKit handling, with no guild-scoped trusted webhook allowlist or webhook-to-user mapping contract. The remaining work is a product/security decision, not stale cleanup.

## What This Changes

Request to add guild-scoped Discord trusted webhook IDs and optional webhook-to-user mapping so selected webhook messages can trigger agent responses without broad `allowBots`.

## Best Possible Solution

Define the Discord trusted-webhook trust model first; if accepted, implement it inside the Discord plugin with strict schema validation, explicit identity-mapping rules, docs, and preflight tests while preserving the default bot-message safety policy.

Question: Should Discord support guild-scoped trusted inbound webhook IDs that bypass the default bot-message drop, and may those webhook messages map onto a configured Discord user identity?

Rationale: The allowlist idea is narrower than `allowBots: true`, but it creates a new inbound authority surface and the proposed `mapToUser` behavior crosses authorization and session-identity boundaries.

Likely owner: steipete

Owner confidence: medium

Options:

- **Approve allowlist without user mapping (recommended):** Allow selected Discord webhook IDs to pass the bot-message gate while keeping sender identity as the webhook/bot identity until a separate identity-mapping contract is approved.
- **Approve webhook-to-user mapping:** Permit user mapping only with strict validation against configured guild users or identity links, clear audit behavior, and tests proving it cannot bypass sender authorization or session isolation.
- **Decline Discord-specific trusted ingress:** Keep Discord bot-message policy unchanged and direct external automation to the generic webhook/plugin path or a separate plugin design.

## Reproduction Assessment

Yes, at source level. Current Discord preflight resolves a webhook id, then drops non-PluralKit bot-authored messages when `allowBots` is off; I did not run a live Discord webhook scenario in this read-only review.

## Solution Assessment

Unclear. A webhook-ID allowlist is plausible and narrower than `allowBots: true`, but `mapToUser` changes authorization and session identity semantics, so maintainers should approve the trust contract before implementation.

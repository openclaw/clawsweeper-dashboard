## Summary

Keep open: current main and the latest release still only support broad Discord `allowBots` modes, with no trusted webhook allowlist or webhook-to-user mapping contract. The remaining work is a security/product decision, not conservative cleanup.

## What This Changes

The issue requests a Discord trusted webhook allowlist, optionally mapping webhook messages to a configured user, so selected webhook-authored messages can trigger agent responses without enabling all bots.

## Best Possible Solution

Define the Discord trusted-webhook trust model first; if accepted, implement it inside the Discord plugin with strict schema validation, explicit identity-mapping rules, docs, and preflight tests while preserving the default bot-message safety policy.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Discord support guild-scoped trusted inbound webhook IDs that bypass the default bot-message drop, and may those webhook messages be mapped onto a configured Discord user identity?

Rationale: The request is narrower than `allowBots: true`, but it creates a new inbound authority surface and the proposed user mapping crosses authorization and session-identity boundaries.

Likely owner: steipete

Owner reason: The decision is mainly about inbound policy and security semantics, and steipete has recent merged history in the Discord inbound mention-policy path.

Owner confidence: medium

Options:

- **Approve allowlist without user mapping (recommended):** Allow selected Discord webhook IDs to pass the bot-message gate while keeping sender identity as the webhook/bot identity until a separate mapping contract is approved.
- **Approve webhook-to-user mapping:** Permit `mapToUser` only with strict validation against configured guild users, clear audit behavior, and tests proving it cannot bypass sender authorization or session isolation.
- **Decline Discord-specific trusted ingress:** Keep Discord bot-message policy unchanged and direct external automation to authenticated Gateway hooks or a separate plugin design.

## Reproduction Assessment

Yes. At source level, current Discord preflight resolves the webhook ID and then drops non-PluralKit bot-authored messages when `allowBots` is off; no live Discord webhook run was performed in this read-only review.

## Solution Assessment

Unclear. A webhook-ID allowlist is plausible and narrower than `allowBots: true`, but `mapToUser` changes authorization and session identity semantics, so maintainers should approve the trust contract before implementation.

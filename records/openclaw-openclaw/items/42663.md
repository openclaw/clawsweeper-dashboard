## Summary

Keep open: current main and the latest release still expose only broad Discord `allowBots` modes, with no guild-scoped trusted webhook allowlist or webhook-to-user mapping. The remaining work is a maintainer product/security decision, not stale cleanup or an already-implemented issue.

## What This Changes

Request to add Discord guild-scoped trusted webhook IDs with optional user mapping so selected webhook-authored messages can trigger agent responses without enabling all bot messages.

## Best Possible Solution

Define the Discord trusted-webhook trust model first; if accepted, implement it inside the Discord plugin with strict schema validation, explicit identity-mapping rules, docs, and preflight tests while preserving default bot-message safety.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Discord support guild-scoped trusted inbound webhook IDs that bypass the default bot-message drop, and may those webhook messages be mapped onto a configured Discord user identity?

Rationale: The request is narrower than global `allowBots: true`, but it creates a new inbound authority surface and the proposed user mapping crosses authorization and session-identity boundaries.

Likely owner: steipete

Owner reason: He has the strongest recent history on the Discord inbound preflight and mention-policy boundary that would own this trust decision.

Owner confidence: high

Options:

- **Approve allowlist without user mapping (recommended):** Allow selected Discord webhook IDs to pass the bot-message gate while keeping sender identity as the webhook or bot identity until a separate mapping contract is approved.
- **Approve webhook-to-user mapping:** Permit `mapToUser` only with strict validation against configured guild users, clear audit behavior, and tests proving it cannot bypass sender authorization or session isolation.
- **Decline Discord-specific trusted ingress:** Keep Discord bot-message policy unchanged and direct external automation to existing authenticated webhook/plugin surfaces or a separate plugin design.

## Reproduction Assessment

Yes, at source level: current Discord preflight resolves the webhook id and then drops non-PluralKit bot-authored messages when `allowBots` is off. I did not run a live Discord webhook scenario in this read-only review.

## Solution Assessment

Unclear. A webhook-ID allowlist is plausible and narrower than `allowBots: true`, but `mapToUser` changes authorization and session identity semantics, so maintainers should approve the trust contract before implementation.

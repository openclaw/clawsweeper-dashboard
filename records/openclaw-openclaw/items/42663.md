## Summary

Keep open: current main and v2026.6.11 still have no Discord `trustedWebhooks` or webhook-to-user mapping, and non-PluralKit Discord webhook/bot messages are dropped when `allowBots` is off. The remaining blocker is maintainer approval of the Discord inbound authority and identity-mapping contract.

## What This Changes

The issue requests a Discord guild-level `trustedWebhooks` allowlist so selected webhook-originated bot messages can trigger agent responses without enabling all bots.

## Best Possible Solution

Have maintainers define the Discord trusted-webhook contract first; if accepted, implement it inside the Discord plugin with strict schema validation, explicit identity-mapping rules, docs, and focused preflight/security tests while keeping the default bot-message policy conservative.

Options:

- **Approve Narrow Trusted Webhooks (recommended):** Allow a webhook-id allowlist to pass the bot-message gate, but keep user mapping disallowed or separately constrained until its authorization semantics are defined.
- **Approve Webhook-To-User Mapping:** Permit `mapToUser` only with strict validation against configured guild users, audit/logging behavior, and tests proving it cannot bypass sender authorization or session isolation.
- **Use Generic Hook Ingress:** Decline a Discord-specific config surface and direct external automation to authenticated Gateway hooks when same-channel Discord replies are not required.

Unclear. A webhook-id allowlist is plausible and narrower than `allowBots: true`, but `mapToUser` crosses authorization and session boundaries, so maintainers should approve the trust contract before implementation.

## Summary

Keep open: current main and the latest release still have no Discord `trustedWebhooks` config or webhook-to-user mapping, and the remaining work is a security/product decision rather than stale cleanup.

## What This Changes

Request a Discord guild-scoped `trustedWebhooks` allowlist that lets selected Discord webhook-authored messages trigger agent responses without enabling all bot messages.

## Best Possible Solution

Define the Discord trusted-webhook security model first; if accepted, implement it inside the Discord plugin with strict schema validation, docs, audit behavior, and preflight tests, preferably starting with an allowlist before user mapping.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Discord support guild-scoped trusted inbound webhook IDs that bypass the default bot-message drop, and may those webhook messages be mapped onto a configured Discord user identity?

Rationale: The request is narrower than `allowBots: true`, but it creates a new inbound authority surface and the proposed `mapToUser` behavior crosses authorization and session-identity boundaries.

Likely owner: steipete

Owner reason: Recent merged work on Discord webhook/PluralKit identity makes this the strongest available routing candidate for the security-boundary decision.

Owner confidence: high

Options:

- **Approve allowlist without user mapping (recommended):** Allow selected Discord webhook IDs to pass the bot-message gate while preserving webhook/bot sender identity until a separate mapping contract is approved.
- **Approve webhook-to-user mapping:** Permit `mapToUser` only with strict validation against configured guild users, explicit audit behavior, and tests proving it cannot bypass sender authorization or session isolation.
- **Decline Discord-specific trusted ingress:** Keep Discord bot-message policy unchanged and direct external automation to `allowBots: "mentions"`, the generic webhooks plugin, or a separate integration path.

## Reproduction Assessment

Yes, at source level: current Discord preflight resolves the webhook id, then drops non-PluralKit bot-authored messages when `allowBots` is off. I did not run a live Discord webhook scenario in this read-only review.

## Solution Assessment

Unclear. A webhook-id allowlist is a plausible narrower solution than `allowBots: true`, but `mapToUser` changes authorization and session identity semantics, so maintainers should approve the trust contract before implementation.

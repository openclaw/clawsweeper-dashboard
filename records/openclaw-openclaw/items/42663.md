## Summary

Keep open: current main and v2026.6.11 still only provide broad Discord `allowBots` modes, not a guild-scoped trusted webhook allowlist or webhook-to-user mapping. The request is useful, but it adds an inbound trust and identity surface that needs maintainer product/security direction before implementation.

## What This Changes

Request a guild-scoped Discord trusted webhook allowlist, optionally mapping webhook messages to a configured user, so selected webhook-authored messages can trigger agent replies without enabling all bot messages.

## Best Possible Solution

Define the Discord trusted-webhook trust model first; if accepted, implement it inside the Discord plugin with strict schema validation, identity-mapping limits, audit/logging behavior, docs, and preflight tests while preserving the default bot-message drop.

Options:

- **Approve allowlist without user mapping (recommended):** Allow selected Discord webhook IDs to pass the bot-message gate while keeping sender identity as the webhook/bot identity until a separate mapping contract is approved.
- **Approve webhook-to-user mapping:** Permit `mapToUser` only with strict validation against configured guild users, clear audit behavior, and tests proving it cannot bypass sender authorization or session isolation.
- **Decline Discord-specific trusted ingress:** Keep Discord bot-message policy unchanged and direct external automation to the authenticated Webhooks plugin or a separate plugin design when same-channel Discord replies are not required.

Unclear. A webhook-ID allowlist is plausible and narrower than `allowBots: true`, but `mapToUser` changes authorization and session identity semantics, so maintainers should approve the trust contract before implementation.

## Summary

Keep open: current main and the latest release still have no Discord trusted webhook allowlist or webhook-to-user mapping. This remains a feature/security-boundary decision, not stale cleanup or an already-implemented bug fix.

## What This Changes

The issue requests guild-scoped Discord `trustedWebhooks` config so selected webhook-authored messages can trigger agent responses without enabling all bot messages.

## Best Possible Solution

Define the Discord trusted-webhook trust model first; if accepted, implement it in the Discord plugin with strict schema validation, explicit identity-mapping rules, docs, and preflight tests while preserving the default bot-message safety policy.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Discord support guild-scoped trusted inbound webhook IDs, and may those webhook messages ever be mapped onto a configured Discord user identity?

Rationale: The request is narrower than `allowBots: true`, but it creates a new inbound authority surface and the proposed user mapping crosses authorization and session-identity boundaries.

Likely owner: steipete

Owner reason: steipete is tied to recent Discord inbound mention-policy and bot-message safety work, making him the best available routing candidate for this trust-boundary decision.

Owner confidence: high

Options:

- **Approve allowlist without user mapping (recommended):** Allow selected Discord webhook IDs to pass the bot-message gate while keeping sender identity as the webhook/bot identity until a separate mapping contract is approved.
- **Approve webhook-to-user mapping:** Permit `mapToUser` only with strict validation against configured guild users, clear audit behavior, and tests proving it cannot bypass sender authorization or session isolation.
- **Decline Discord-specific trusted ingress:** Keep Discord bot-message policy unchanged and direct external automation to existing `allowBots` modes or a separate hooks/plugin design.

## Reproduction Assessment

Yes at source level: current Discord preflight resolves a webhook ID and then drops non-PluralKit bot-authored messages when `allowBots` is off. I did not run a live Discord webhook scenario in this read-only review.

## Solution Assessment

Unclear. A webhook-ID allowlist is plausible and narrower than `allowBots: true`, but `mapToUser` changes authorization and session identity semantics, so maintainers should approve the trust contract before implementation.

## Summary

Keep open: current main and the latest release still drop ordinary Discord webhook messages when `allowBots` is off, and no `trustedWebhooks` or webhook-to-user mapping contract exists. The remaining blocker is a maintainer security/product decision for a new trusted Discord ingress authority surface.

## What This Changes

The issue requests a guild-level Discord trusted webhook allowlist so selected webhook messages can trigger agent responses without enabling all bot-authored messages.

## Best Possible Solution

Have maintainers define the Discord trusted-webhook security model first; if accepted, implement it inside the Discord plugin with strict schema validation, explicit mapping rules, docs, and focused preflight tests without broadening the default bot-message policy.

Rationale: The requested behavior is narrower than `allowBots: true`, but it turns possession of a Discord webhook URL into authority to enter agent sessions, and the proposed `mapToUser` crosses authorization and session-identity boundaries.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve narrow trusted webhook ingress (recommended):** Allow maintainers to design a webhook-ID allowlist that can pass the bot-message gate, while leaving webhook-to-user impersonation disallowed or separately constrained until its authorization rules are defined.
- **Approve webhook-to-user mapping too:** Permit `mapToUser` only with strict validation against configured guild users, clear audit behavior, and tests proving it cannot bypass sender authorization or session isolation.
- **Decline Discord-specific webhook ingress:** Keep Discord bot-message policy unchanged and direct external automation to the authenticated Webhooks plugin or a ClawHub integration instead of adding another Discord config surface.

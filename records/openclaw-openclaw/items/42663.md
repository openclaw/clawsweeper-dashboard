## Summary

Keep open: current main and v2026.6.11 still lack a Discord webhook-ID allowlist, and the remaining work is a security/product decision rather than stale cleanup.

## What This Changes

Request guild-scoped Discord `trustedWebhooks` config that lets selected webhook-authored messages trigger agent responses, optionally mapping a webhook to a Discord user identity.

## Best Possible Solution

Define the Discord trusted-webhook trust model first; if accepted, implement it in the Discord plugin with strict schema validation, explicit identity-mapping rules, docs, tests, and live Discord proof while preserving default bot-message safety.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Discord support guild-scoped trusted inbound webhook IDs that bypass the default bot-message drop, and may those webhook messages be mapped onto a configured Discord user identity?

Rationale: The request is narrower than `allowBots: true`, but it creates a new inbound authority surface and the proposed `mapToUser` option crosses authorization and session-identity boundaries.

Likely owner: steipete

Owner reason: They own the closest recent inbound mention-policy refactor across Discord and sibling channel gates, so they are the best available routing candidate for the trust-boundary decision.

Owner confidence: medium

Options:

- **Approve allowlist without user mapping (recommended):** Allow selected Discord webhook IDs to pass the bot-message gate while keeping sender identity as the webhook/bot identity until a separate mapping contract is approved.
- **Approve webhook-to-user mapping:** Permit `mapToUser` only with strict validation against configured guild users, clear audit behavior, and tests proving it cannot bypass sender authorization or session isolation.
- **Decline Discord-specific trusted ingress:** Keep Discord bot-message policy unchanged and direct external automation to authenticated webhooks, Gateway Protocol, or a separate plugin design.

## Reproduction Assessment

Yes. At source level, current Discord preflight resolves the webhook id and then drops non-PluralKit bot-authored messages when `allowBots` is off; I did not run a live Discord webhook scenario in this read-only review.

## Solution Assessment

Unclear. A webhook-ID allowlist is plausible and narrower than `allowBots: true`, but `mapToUser` changes authorization and session identity semantics, so maintainers should approve the trust contract before implementation.

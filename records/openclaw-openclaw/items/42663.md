## Summary

Keep open: current main and the latest stable release still drop ordinary Discord webhook messages when bot messages are not broadly enabled, and the requested trusted webhook/user-mapping surface is still absent. The next step is maintainer security/product approval, not an automated fix PR.

## What This Changes

Request to add guild-scoped Discord `trustedWebhooks` config so selected webhook-authored messages can trigger agent responses without enabling all bot messages.

## Best Possible Solution

Have maintainers approve the Discord trusted-webhook security contract first; if accepted, implement it inside the Discord plugin with strict schema validation, explicit mapping rules, docs, and preflight regression tests without broadening the default bot-message policy.

Rationale: The requested behavior is narrower than `allowBots: true`, but it turns possession of a Discord webhook URL into authority to enter agent sessions, and `mapToUser` crosses sender authorization and session-identity boundaries.

Owner confidence: high

Options:

- **Approve narrow webhook allowlist (recommended):** Allow maintainers to design an explicit webhook-id allowlist that can pass the bot-message gate, while keeping user impersonation/mapping disallowed or separately constrained until its authorization semantics are defined.
- **Approve mapped user authority:** Permit `mapToUser` only with strict validation against configured guild users, clear audit/logging behavior, and tests proving it cannot bypass sender authorization or session isolation.
- **Decline Discord-native webhook ingress:** Keep Discord bot-message policy unchanged and direct external automation to the authenticated Gateway/Webhooks plugin or a separate integration instead of adding another Discord config surface.

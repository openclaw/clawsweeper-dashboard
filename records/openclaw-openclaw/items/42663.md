## Summary

Keep open: current main and the latest release still drop ordinary Discord webhook-authored messages when `allowBots` is off, and there is no `trustedWebhooks` schema, docs, or webhook-to-user mapping contract. The remaining question is a maintainer security/product decision, not a stale cleanup close.

## What This Changes

The issue requests a guild-scoped Discord `trustedWebhooks` allowlist, optionally mapping webhook messages to a configured user identity so selected Discord webhooks can trigger agent replies without enabling all bot messages.

## Best Possible Solution

Define the Discord trusted-webhook security model first; if accepted, implement it inside the Discord plugin with strict schema validation, explicit identity-mapping rules, docs, and preflight tests while preserving the default bot-message safety policy.

Owner confidence: high

Options:

- **Approve webhook allowlist without user mapping (recommended):** Allow selected Discord webhook IDs to pass the bot-message gate while keeping sender identity as the webhook/bot identity until a separate mapping contract is approved.
- **Approve webhook-to-user mapping too:** Permit `mapToUser` only with strict validation against configured guild users, clear audit behavior, and tests proving it cannot bypass sender authorization or session isolation.
- **Decline Discord-specific trusted ingress:** Keep Discord bot-message policy unchanged and direct external automation to the authenticated webhooks plugin or a separate ClawHub integration.

Yes, at source level: current Discord preflight resolves the webhook id, then drops non-PluralKit bot-authored messages when `allowBots` is off. I did not run a live Discord webhook scenario in this read-only review.

## Solution Assessment

Unclear. A webhook-id allowlist is plausible and narrower than `allowBots: true`, but `mapToUser` changes authorization and session identity semantics, so maintainers should approve the trust contract before implementation.

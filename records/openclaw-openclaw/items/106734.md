## Label Justifications

- `P2`: The report describes substantial Discord response latency, but it targets an old release and current main already prevents the listener itself from awaiting the agent run.
- `impact:message-loss`: Incoming Discord messages can be effectively suppressed from the user's perspective while they wait behind a long active session run.
- `impact:ux-friction`: Users may perceive the bot as frozen because current ordered execution provides no immediate response to later same-session messages.

## Summary

Keep open, but reframe the report: current main does not synchronously block Node’s event loop, and Discord listeners now return immediately after queueing work. The remaining user-visible concern is that later messages for the same session intentionally wait behind the active agent run, which can still make Discord appear unresponsive during long foreground exec waits. This needs a current-version reproduction and a product decision about live steering, cancellation, or busy-state behavior.

Likely related people: steipete has high-confidence recent ownership of the exec implementation; openperf has medium-confidence history in adjacent exec lifecycle behavior.

## What This Changes

Prevent long foreground exec waits from making subsequent Discord messages appear unresponsive.

## Best Possible Solution

Keep immediate Discord listener handoff and ordered session execution, then add an explicit user-facing active-run path—such as busy status plus cancel or steering input—if maintainers want messages to affect a running turn; do not add worker threads or a Discord-specific yield cap for an event-loop blockage that current source disproves.

Question: While a Discord session has an active agent turn, should new text messages remain queued in order, or should selected messages be allowed to cancel or steer that run?

Rationale: Current main intentionally preserves per-session ordering, so making the bot responsive to later messages during an active turn changes conversation and session semantics rather than repairing a synchronous event-loop block.

Likely owner: steipete

Owner confidence: high

Options:

- **Preserve ordered execution (recommended):** Keep later messages queued, but expose a visible busy state and a clear cancellation path for long-running turns.
- **Support live steering:** Allow eligible new messages to steer, cancel, or otherwise affect the active run while preserving ordinary follow-up ordering.
- **Lower the global yield ceiling:** Force foreground exec calls to background sooner across all channels, accepting the compatibility change for existing tool behavior.

## Reproduction Assessment

No, not for the reported root cause: current source uses an asynchronous timer and a fire-and-forget Discord listener, so a synchronous event-loop blockage is not reproducible from current main. The narrower behavior that later same-session jobs wait behind an active run is directly supported by source and tests.

## Solution Assessment

No. A Discord gateway ceiling targets the wrong ownership layer, and worker-thread listener processing duplicates the immediate handoff already present; any remaining improvement should address shared active-run interaction semantics.

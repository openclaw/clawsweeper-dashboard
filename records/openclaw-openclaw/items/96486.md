## What This Changes

Review whether the Host-header origin fallback flag leaves a network-exposed Control UI gateway without adequate CSRF protection.

## Best Possible Solution

Security owners should choose a compatibility-aware hardening path: retire the fallback with a migration, or keep it only with stronger CSRF/DNS-rebinding defenses and explicit public-origin guidance.

Options:

- **Harden the break-glass path (recommended):** Keep the explicit flag but require a configured canonical public origin, CSRF token, or `Sec-Fetch-Site` style browser guard before exposed deployments can rely on it.
- **Remove the fallback:** Delete the flag and require explicit `gateway.controlUi.allowedOrigins`, with doctor/docs migration for existing exposed deployments.
- **Accept current policy:** Leave the flag as documented break-glass behavior and rely on the existing critical audit finding plus operator deployment guidance.

## Reproduction Assessment

Partly. Source inspection reproduces the dangerous fallback acceptance path when Origin host equals Host and the flag is enabled, but the exact arbitrary attacker-origin POST needs a live DNS/proxy scenario because mismatched Origins are rejected on current main.

## Solution Assessment

No, not as an autonomous change. Removing the flag may be the strongest security outcome, but current docs and types describe long-term support for intentional deployments, so the best fix needs a security-owner compatibility decision first.

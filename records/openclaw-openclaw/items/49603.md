## Summary

Keep open: current main has a useful partial self-owned lock cleanup, but field comments and source review show the remaining live current-PID/restart-recovery reclaim boundary is not safely resolved as implemented.

## What This Changes

The issue reports that session `.jsonl.lock` files owned by the current gateway PID can survive restart or recovery and block later session writes.

## Best Possible Solution

Keep this open until maintainers choose and land a safe liveness contract for live current-PID session locks, likely heartbeat or run-state based, while preserving the existing startup cleanup and doctor diagnostics.

- **Keep manual recovery only:** Preserve live current-PID locks by default and rely on doctor/status guidance for operator-driven cleanup until stronger proof arrives.

## Solution Assessment

No, not as a closure decision: the current startup/acquire cleanup is a useful mitigation, but the best complete fix needs a safe live-lock liveness policy before reclaiming current-PID locks during or after recovery.

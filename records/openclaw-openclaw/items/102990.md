## Summary

This PR is still necessary because current main leaves `chatUserCache` unbounded, but the latest head is not merge-ready: its capacity loop evicts another endpoint when refreshing an existing key at 100 entries, and Map insertion order does not implement the claimed least-recently-refreshed policy. The earlier same-NAS fallback finding was addressed in the new design, but this new-head defect can still remove recipient mappings used during Synology lookup failures.

## What This Changes

The PR caps the Synology Chat user-list cache at 100 entries and adds regression tests for oldest-entry eviction and preserving other webhook fallbacks.

## Best Possible Solution

Implement explicit refresh-recency eviction: overwrite an existing key without consuming capacity, move each successfully refreshed key to newest, evict only when adding a new key at capacity, and prove preserved cached users through a later failed lookup.

Yes, from the exact-head source. Fill the cache to 100 entries and refresh an already-cached non-oldest key to observe unrelated eviction; refreshing the insertion-oldest key also does not protect it from the next eviction.

## Solution Assessment

No. A bounded in-memory cache is the right layer, but this implementation neither distinguishes overwrite from growth nor implements its documented refresh-recency ordering.

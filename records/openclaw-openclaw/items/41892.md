## Review Findings

Overall correctness: patch is incorrect

Full review comments:

- **[P1] Preserve current cron.status fields on rebase:** `src/cron/service/ops.ts:220-228`
  - body: Current main's `cron.status` response includes `storage` and `sqlitePath`, and read-ops tests assert them. This PR head adds `gatewayTimezone` on a conflicting branch but returns only `enabled`, `storePath`, `jobs`, and `nextWakeAtMs`, so resolving the conflict by taking this shape would break existing status clients; keep the current fields and add the new one.
  - confidence: 0.9
- **[P2] Use real run state for past timeline markers:** `ui/src/ui/helpers/cron-timeline.ts:542`
  - body: `getTimelineMarkers` marks every scheduled slot at or before the current hour as `ok`, regardless of whether the relevant job actually succeeded, failed, was skipped, was not delivered, or never ran. The existing Cron UI already derives job status from `lastRunStatus`/`lastStatus`; the timeline should not present wall-clock-past as success.
  - confidence: 0.88
- **[P2] Use the scheduler's stable stagger offset:** `ui/src/ui/helpers/cron-timeline.ts:384-388`
  - body: Runtime scheduling offsets staggered cron jobs with a deterministic hash of the job id, but the timeline approximates every stagger as `staggerMs / 2`. That can place dots at times the scheduler will never use, so marker position and past/pending state can disagree with actual execution.
  - confidence: 0.86
- **[P3] Regenerate non-English timeline strings:** `ui/src/i18n/locales/de.ts:1241-1251`
  - body: The German locale metadata says it is fully translated, but the new timeline keys are still English. Since these non-English locale bundles are generated output, regenerate them through the Control UI i18n pipeline instead of landing stale or hand-filled strings.
  - confidence: 0.8

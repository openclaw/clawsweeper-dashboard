## Label Justifications

- `P2`: This is a real sandbox security hardening issue, but it is a bounded Docker default change rather than an active P0/P1 incident.
- `merge-risk: 🚨 compatibility`: Existing users who rely on Docker's current unlimited/default PID behavior can see behavior change after upgrade when no `pidsLimit` is configured.
- `merge-risk: 🚨 availability`: A hard default cap can cause high-process sandbox workloads to fail or stall if the cap is too low for an existing deployment.

## Summary

Keep open: current main and the latest release still leave Docker sandbox `pidsLimit` unset by default, so this PR is not obsolete. The patch should not merge as-is because it changes existing unset sandboxes to a hard 1024 PID cap without an aligned opt-out/schema/docs/test contract or real Docker behavior proof.

## What This Changes

The PR adds a `DEFAULT_SANDBOX_PIDS_LIMIT` constant and makes `resolveSandboxDockerConfig` default unset Docker `pidsLimit` to 1024.

## Best Possible Solution

Land a security-owner-approved PID default that preserves explicit overrides, defines documented unlimited/opt-out semantics, updates schema/type/docs/tests, and includes real Docker proof.

## Reproduction Assessment

Yes, source-level. On current main, resolving Docker sandbox config with no global or per-agent `pidsLimit` returns `undefined`, and Docker create args then omit `--pids-limit`; no live fork-bomb repro was run in this read-only review.

## Solution Assessment

No, not as submitted. The resolver fallback is a plausible narrow mitigation, but the best fix also needs an approved cap/opt-out contract, aligned schema/docs/tests, and real Docker proof.

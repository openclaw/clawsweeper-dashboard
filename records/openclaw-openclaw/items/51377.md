## Summary

Keep open: current main and the latest release still only partially address the request. `chat.send` can stage non-image attachments, but OpenResponses `input_file` remains a text/PDF extraction path with no default Excel MIME support and no durable binary workspace receipt for tools or skills.

## What This Changes

The issue requests first-class Excel and generic binary upload support in gateway/input_file flows, with allowlists, limits, workspace persistence, metadata, and documentation.

## Best Possible Solution

Define a Gateway media contract that stages approved binary `input_file` payloads as sanitized workspace artifacts with metadata receipts and explicit unsupported errors, while leaving provider-native forwarding and document parsing to their own approved follow-ups.

## Reproduction Assessment

Yes, at source level: `.xlsx` and generic binary MIME types are outside the default `input_file` allowlist, and allowed non-PDF files are decoded into prompt text rather than persisted as workspace artifacts. I did not run a live upload because this cleanup review is read-only.

## Solution Assessment

No, a simple allowlist expansion is not the best fix. The maintainable solution is a Gateway-level binary artifact/receipt contract with security policy, then separate parser or provider-native forwarding work where approved.

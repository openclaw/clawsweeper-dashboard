## Summary

Keep open: current main and v2026.6.11 still only partially cover the request. `chat.send` can now stage non-image files, but OpenResponses `input_file` still defaults to text/JSON/PDF extraction and does not provide durable Excel or generic binary workspace receipts.

## What This Changes

The issue requests first-class Excel and generic binary upload handling for Gateway/OpenResponses `input_file` paths, including persistence, metadata, limits, and documentation.

## Best Possible Solution

Define a maintainer-approved Gateway media contract that stages allowed binary `input_file` payloads as named workspace artifacts with metadata and explicit unsupported errors, while leaving richer parsing and provider-native forwarding to narrower follow-ups.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: an `.xlsx` `input_file` is outside the default allowlist, and allowed non-PDF files are decoded into prompt text rather than persisted as binary workspace artifacts.

## Solution Assessment

Yes for the workspace-receipt direction, but no for a narrow MIME-only fix. The maintainable solution needs a Gateway-level binary attachment contract with security policy rather than only adding `.xlsx` to `allowedMimes`.

## Summary

Keep open: current main and the latest release still reject Excel from the default `/v1/responses` `input_file` path and do not provide a durable generic-binary workspace receipt; the existing `chat.send` offload path is useful partial overlap, not completion.

## What This Changes

Request first-class Excel and generic binary upload support for Gateway/OpenResponses `input_file`, including MIME limits, persistence metadata, tool access, and docs.

## Best Possible Solution

Define a maintainer-approved Gateway `input_file` binary receipt contract that stages allowlisted binary payloads as sanitized workspace artifacts with metadata and explicit unsupported errors, while leaving provider-native forwarding and document parsing to their narrower tracks.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Gateway `/v1/responses` add a first-class binary `input_file` workspace receipt contract, and what default allowlist, persistence, redaction, and tool-access policy should it use?

Rationale: The source gap is clear, but implementing it changes public upload semantics and security boundaries beyond a mechanical bug fix.

Likely owner: steipete

Owner confidence: high

Options:

- **Add a scoped binary receipt contract (recommended):** Use the existing `files.allowedMimes` and byte limits to stage allowlisted binary payloads into a sanitized workspace attachment directory with metadata, redaction, and explicit unsupported errors.
- **Keep input_file text/PDF-only:** Leave `/v1/responses` limited to text/PDF extraction and direct Excel workflows to conversion, skills, or a future plugin surface.
- **Defer to provider-native file input:** Track this under the broader provider-native file/document abstraction before adding a local workspace receipt path.

## Reproduction Assessment

Yes. Source inspection shows `.xlsx` is outside the default `input_file` MIME allowlist, and accepted non-PDF files are decoded into prompt text rather than persisted as binary workspace artifacts.

## Solution Assessment

No as a simple allowlist change. The maintainable fix is a Gateway-level binary upload and workspace receipt contract with explicit security policy, not raw text decoding for more MIME types.

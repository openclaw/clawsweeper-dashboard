## Summary

Keep open: current main and v2026.6.11 still leave the central OpenResponses `input_file` / durable Excel and generic binary receipt request unresolved. The merged `chat.send` work is useful partial coverage, but it does not replace this issue because `input_file`, `agent.run`, and provider/native-document policy still need a product and security contract.

## What This Changes

The issue requests first-class Excel and generic binary upload support through gateway/input_file paths, with explicit allowlists, limits, persistence, metadata, and documentation.

## Best Possible Solution

Maintainers should define one explicit gateway file-ingest contract: either clearly reject unsupported Excel/generic binary `input_file` payloads, or persist allowlisted binary files to managed media/workspace receipts with MIME/size limits, redaction rules, docs, and a separate bridge to provider-native forwarding work.

## Reproduction Assessment

Yes, source-reproducible: current main’s OpenResponses `input_file` path has a narrow text/JSON/PDF allowlist and returns extracted prompt content, not a durable Excel/generic binary receipt. I did not run a live request because this review is read-only and the source/test contract is clear.

## Solution Assessment

Unclear as proposed, because adding Excel MIME types alone would run binary Office data through a text/PDF extraction path. The best fix is a maintainer-approved upload contract that separates allowlisting, persistence, tool-readable receipts, prompt injection/redaction, and provider-native forwarding.

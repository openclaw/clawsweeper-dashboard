## Summary

Keep open: current main and the latest release still show the Workboard dispatch path asking workers to call Workboard protocol tools without any allowlist path that would make those optional tools available.

## What This Changes

The issue reports that automated Workboard dispatch starts sub-agent runs without Workboard completion/block/heartbeat tools, leaving dispatched cards stuck in running state.

## Best Possible Solution

Add a narrow plugin subagent/Gateway `toolsAllow` path and have Workboard pass only its worker protocol tools, with regression coverage and live dispatch proof.

Rationale: The bug is source-proven, but the durable fix crosses the plugin runtime and Gateway request contract, so maintainer intent is needed before implementation.

Owner confidence: high

Options:

- **Add subagent toolsAllow (recommended):** Extend the plugin subagent/Gateway path to forward an explicit allowlist, then have Workboard grant only its heartbeat, completion, block, release, log, proof, and attachment tools to dispatched workers.
- **Make Workboard tools default:** Remove optional gating for some or all Workboard tools, accepting a broader default tool surface in normal sessions.
- **Use lifecycle fallback only:** Block or recover cards when a worker exits without protocol tools, which reduces stuck cards but does not give workers the documented completion path.

## Reproduction Assessment

Yes by source inspection: dispatch prompts workers to call Workboard tools, but those tools are optional and the plugin subagent/Gateway path has no allowlist field. I did not run a live Gateway/provider worker in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API seam. A narrow `toolsAllow` path for plugin subagents appears to be the best owner-boundary fix; broadening default Workboard tools is riskier, and lifecycle fallback alone only recovers after failure.

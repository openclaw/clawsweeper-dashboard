## Summary

Keep open: current main and the latest release still leave automated Workboard dispatch without a supported way to expose the Workboard worker protocol tools, and no merged or open canonical fix owns the gap.

## What This Changes

The issue reports that automated Workboard dispatch launches subagents without Workboard heartbeat, complete, and block tools, leaving cards stuck in `running` after worker completion.

## Best Possible Solution

Add a narrow plugin subagent/Gateway `toolsAllow` path and have Workboard pass only the worker protocol tools, with regression coverage and live dispatch proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Workboard fix dispatched workers by extending plugin `subagent.run` and the Gateway `agent` path with a narrow `toolsAllow` contract, by changing Workboard tool optionality, or by adding lifecycle fallback recovery?

Rationale: The bug is source-proven, but the durable repair crosses the plugin runtime/Gateway API boundary and changes how optional plugin tools are exposed to subagents.

Likely owner: steipete

Owner reason: He introduced the Workboard dispatch feature and is the strongest feature-history owner for the intended dispatch/tool contract.

Owner confidence: high

Options:

- **Add subagent toolsAllow (recommended):** Extend the plugin subagent/Gateway path to forward an explicit allowlist, then have Workboard grant only its heartbeat, completion, block, proof, log, attachment, and release tools to dispatched workers.
- **Make Workboard tools default:** Remove optional gating for some or all Workboard tools, accepting a broader default tool surface for normal sessions.
- **Use lifecycle fallback only:** Block or recover cards when a worker exits without protocol tools, which reduces stuck cards but does not give workers the documented completion path.

## Reproduction Assessment

Yes by source inspection: dispatch prompts workers to use Workboard protocol tools, but optional Workboard tools require allowlisting and the plugin subagent path has no allowlist field. I did not run a live Gateway/provider worker in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API seam. A narrow `toolsAllow` path for plugin subagents appears to be the best owner-boundary fix; broadening default Workboard tools is riskier, and lifecycle fallback alone only recovers after failure.

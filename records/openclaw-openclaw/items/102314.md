## Summary

Keep open: current main still has a source-backed Workboard dispatch gap where workers are instructed to use Workboard protocol tools, but the plugin subagent runtime cannot pass a tool allowlist and optional Workboard tools are filtered out unless explicitly allowed.

## What This Changes

The issue requests fixing automated Workboard dispatch so sub-agent workers can call Workboard heartbeat, completion, and blocking tools and avoid cards staying stuck in `running`.

## Best Possible Solution

Give Workboard-dispatched workers a narrow, explicit Workboard tool surface for heartbeat, completion, blocking, logs, proof, attachments, and release without making every optional Workboard tool globally default.

Options:

- **Add subagent `toolsAllow` (recommended):** Extend the plugin subagent runtime and Gateway `agent` path to forward an explicit allowlist, then have Workboard pass only the worker protocol tools it needs.
- **Make Workboard tools default:** Remove optional gating for some or all Workboard tools, accepting a broader default tool surface for normal sessions.
- **Add lifecycle fallback:** Use the existing protocol-violation path to block stranded cards when a worker exits without calling Workboard completion tools, without directly fixing worker tool access.

## Reproduction Assessment

Yes by source inspection: a Workboard dispatch worker is prompted to use Workboard tools, but optional Workboard tools are unavailable without an allowlist and the plugin subagent/Gateway path has no allowlist field. I did not run a live Gateway/provider worker in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API seam. A narrow `toolsAllow` path for plugin subagents looks like the best owner-boundary fix; removing `optional: true` from Workboard tools would be broader, and lifecycle fallback alone would only recover after failure.

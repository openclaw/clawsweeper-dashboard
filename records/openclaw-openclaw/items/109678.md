## Label Justifications

- `P1`: A documented browser lifecycle command consistently fails for an active agent workflow and leaves the managed browser unavailable for normal stop/restart cycling.
- `impact:crash-loop`: The surviving Chrome process retains the managed CDP port and prevents normal process-level browser recovery.
- `impact:ux-friction`: Recovery currently requires identifying and killing the Chrome process from a terminal rather than using the supported lifecycle command.

## Summary

Keep open: the release transcript establishes a repeatable lifecycle failure, and current main still makes `browser stop` depend on the launch owner's in-memory `RunningChrome` state even though agent or node dispatch can launch the same managed profile through another runtime context. The documented contract says a local managed profile must stop the spawned process.

## What This Changes

Fix `openclaw browser stop` so it terminates managed Chrome instances auto-launched through the agent browser tool, not only instances launched by the CLI lifecycle command.

## Best Possible Solution

Keep one lifecycle owner for agent, node-host, and CLI launches, and add an identity-verified recovery stop for an owned managed process when the original ChildProcess handle is unavailable; prove both CLI-launched and agent-launched paths without adding persistent file state or broad `pkill` behavior.

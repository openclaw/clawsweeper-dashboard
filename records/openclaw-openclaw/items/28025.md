## Summary

Keep open: current main supports static Slack reply-placement controls, including per-channel `replyToMode`, but still has no tool-use-sensitive policy for threading only tool-using replies.

## What This Changes

Request a default-off Slack reply-placement option that threads agent replies after tool use while keeping purely conversational replies top-level.

## Best Possible Solution

Define a maintainer-approved Slack-owned reply-placement policy, preferably by extending the existing `replyToMode` model with docs and regression coverage instead of adding a parallel routing path.

Options:

- **Extend Reply Mode (recommended):** Add an explicit Slack reply-placement mode or policy under the existing `replyToMode` family so account, chat-type, and per-channel precedence stay in one model.
- **Add Separate Flag:** Add the proposed default-off `thread.replyOnToolUse` flag and document exactly how it composes with static reply modes, DMs, streaming, and tool sends.
- **Decline Heuristic:** Keep static `replyToMode` and per-channel overrides as the supported way to reduce Slack clutter, and document that OpenClaw does not infer thread placement from tool use.

## Reproduction Assessment

Yes, at source level. Current Slack reply placement is selected from static `replyToMode` configuration before dispatch, and targeted search found no `replyOnToolUse` or equivalent tool-use-sensitive policy.

## Solution Assessment

Unclear until maintainers choose the product policy. If accepted, the maintainable implementation should live in the Slack reply-mode/config path with coverage for DMs, per-channel precedence, streaming, and tool callbacks.

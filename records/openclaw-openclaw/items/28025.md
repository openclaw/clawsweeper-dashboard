## Label Justifications

- `impact:ux-friction`: Users must currently predict deep Slack conversations and manually start threads to avoid clutter, which is avoidable channel workflow friction.

## Summary

Keep open: current main and v2026.6.11 still expose static Slack reply-threading controls only, while this request is specifically for tool-use-sensitive reply placement. The related Slack threading items overlap on channel clutter and reply-mode design, but none is a merged or safe canonical replacement for this exact behavior.

## What This Changes

Add Slack reply routing that sends tool-using agent responses into a thread while leaving purely conversational responses at top level.

## Best Possible Solution

Define one maintainer-approved Slack reply-policy contract for tool-sensitive threading, then update the Slack plugin schema, docs, routing/streaming behavior, and focused regression tests together.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 expose static Slack reply controls only and have no replyOnToolUse or equivalent routing branch. This is feature absence rather than a failing bug repro, so I did not run live Slack proof.

## Solution Assessment

Unclear for the proposed shape: a default-off boolean is plausible, but the best fix needs maintainer-approved precedence with existing Slack reply modes, DMs, existing threads, explicit top-level opt-outs, and streaming/status timing.

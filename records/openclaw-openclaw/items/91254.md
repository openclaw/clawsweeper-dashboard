## Summary

Keep open: current main still has the blind replacement primitive, and current main now explicitly applies output transforms to structured tool-call arguments before execution. The linked fork fix is useful context, but it is open, conflicting, and the permanent boundary needs maintainer direction.

## What This Changes

The issue reports silent filesystem-path misrouting from blind rebrand text substitutions applied to tool-call arguments and output.

## Best Possible Solution

Settle the text-transform boundary so cosmetic or plugin decode transforms cannot silently rewrite filesystem paths or other executable tool arguments, while preserving a supported plugin path for intentional argument decoding.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should plugin text transforms continue to apply to structured tool-call argument strings by default, or should OpenClaw add a path/tool-argument-safe boundary for filesystem and executable arguments?

Rationale: Current main intentionally restores transformed structured arguments before tool execution, while this issue shows the same blind replacement primitive can silently misroute path-bearing file operations; changing it affects public plugin/provider semantics.

Likely owner: steipete

Owner reason: The text-transform surface originated in steipete's commit and this decision is about that public plugin/provider boundary.

Owner confidence: high

Options:

- **Add a safe executable-argument boundary (recommended):** Keep prompt/display transforms but skip or narrowly gate replacements for path-like and executable tool arguments, with focused regression coverage and an upgrade note for plugin authors.
- **Keep current transform semantics:** Preserve structured argument transforms as a plugin contract and document that plugins needing path safety must implement their own `before_tool_call` policy.
- **Move argument transforms to explicit hooks:** Stop using `registerTextTransforms` for executable arguments and require plugins to opt into tool-specific decoding through `before_tool_call` or a new typed contract.

## Reproduction Assessment

Yes for the unsafe primitive and current-main tool-argument path by source inspection: a registered string replacement rewrites any matching path string, and current main applies output replacements to structured tool-call arguments. No full live reproduction of the reporter's macOS/Signal dual-directory deployment was run in this read-only review.

## Solution Assessment

Unclear pending maintainer direction. A path-aware fix is plausible, but the best permanent solution must balance executable path safety against the now-documented plugin behavior that restores transformed structured tool arguments before execution.

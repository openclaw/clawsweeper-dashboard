## What This Changes

The issue reports that plugin/rebrand text substitutions can rewrite legacy-name filesystem paths in tool-call text, silently routing file operations to the wrong directory.

## Best Possible Solution

Land a maintainer-sponsored fix that preserves cosmetic compatibility transforms while preventing filesystem or executable tool inputs from being silently rewritten, with focused regression tests and live dual-directory proof.

Question: What permanent boundary should plugin text transforms have for path-bearing prompts and executable tool-call arguments?

Rationale: Current behavior is documented and intentionally restores structured tool-call args, but the issue shows that the same broad string rewrite can misroute filesystem operations; automation cannot choose that compatibility boundary safely.

Likely owner: steipete

Owner reason: The feature-history evidence points to steipete as the introducer of the text-transform surface and the best available owner for the compatibility boundary decision.

Owner confidence: high

Options:

- **Path-safe transform boundary (recommended):** Keep text transforms for normal prompt/output compatibility, but skip or validate replacements in filesystem/tool-input contexts and add tests/docs for that boundary.
- **No tool-argument transforms:** Disable output transforms for executable tool-call arguments entirely, accepting that masking/normalization plugins must use before_tool_call for argument rewrites.
- **Keep broad transforms:** Preserve current broad semantics and document before_tool_call or deployment-specific configuration as the escape hatch, leaving this report as unsupported behavior.

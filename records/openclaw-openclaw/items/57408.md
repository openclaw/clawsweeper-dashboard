## Summary

Keep this issue open: current main and the latest release still block the reported workspace `.env` key, and the remaining behavior change needs maintainer/security direction rather than conservative cleanup closure.

## What This Changes

The issue asks OpenClaw to honor project-local `.env` values for `OPENCLAW_CONFIG_PATH` so CLI and gateway startup use the intended local config instead of falling back to the global config.

## Best Possible Solution

Maintainers should decide the workspace dotenv trust policy; if an exception is approved, implement only the approved `OPENCLAW_CONFIG_PATH` behavior with focused tests and docs while keeping state-dir, secrets, endpoint, and other runtime-control keys blocked.

## Reproduction Assessment

Yes, at source level. CLI startup loads workspace `.env` through `loadWorkspaceDotEnvFile`, and current tests explicitly prove `OPENCLAW_CONFIG_PATH` from that workspace file remains unset.

## Solution Assessment

Unclear. Allowing the key would restore the reported workflow, but current source, tests, docs, and repository policy treat workspace runtime controls as a security boundary, so the best fix needs maintainer/security direction first.

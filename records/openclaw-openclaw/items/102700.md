## Label Justifications

- `P2`: This is a normal Control UI behavior bug with limited blast radius: users can wait for reconnect, but cannot capture input while the mounted reconnect shell is visible.
- `impact:ux-friction`: The reconnecting chat UI creates avoidable user friction by disabling the composer even though the app can persist and retry queued sends.

## Summary

Keep open: current main still disables the Control UI composer whenever the Gateway snapshot is disconnected, even though the lower chat send path can already persist disconnected sends as waiting for reconnect. The protected `maintainer` label also prevents conservative cleanup closure or automatic work-lane routing.

## What This Changes

The issue asks for Control UI Chat to accept text and attachments while the Gateway is reconnecting, persist the pending send, show it as waiting for reconnect, and send it once connected again.

## Best Possible Solution

Decouple compose/queue eligibility from transport connectivity in the chat pane/view/composer, keep realtime-only actions and explicit queue retry connection-bound, and add browser E2E proof for offline submit, persistence, reconnect, and exactly-once send.

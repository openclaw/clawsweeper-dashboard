- `impact:ux-friction`: The mounted reconnect UI remains visible, but users cannot capture or queue new chat input until the connection returns.

## Summary

Keep open: current main still disables the Control UI chat composer when the Gateway is disconnected even though the mounted reconnect shell and waiting-reconnect queue path already exist. The protected `maintainer` label also prevents conservative cleanup from closing or auto-queueing this item.

## What This Changes

Allow Control UI Chat to accept and queue text and attachments while an established Gateway session is reconnecting.

## Best Possible Solution

Split chat compose/queue capability from transport connectivity in the Control UI, reuse the existing waiting-reconnect queue and persistence path, and keep realtime-only controls connection-bound.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, source-level: current main has a mounted reconnect shell and disconnected-send queue support, but the chat pane/view/composer still disable composition from `connected === false`. I did not run the browser harness in this read-only review.

## Solution Assessment

Yes, the narrow fix is to introduce a `canQueueInput`/`canCompose` capability for established reconnecting sessions and route it through the existing queue path. A separate component-local pending-message state, as sketched in the comment, would duplicate the existing queue machinery.

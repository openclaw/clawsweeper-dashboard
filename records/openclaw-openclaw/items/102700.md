## Label Justifications

- `P2`: The issue is a bounded Control UI behavior bug during recoverable Gateway disconnects, not a full setup blocker or core runtime outage.
- `impact:session-state`: The broken path prevents input from entering the existing persisted chat queue/session state while the Gateway reconnects.
- `impact:ux-friction`: Users must wait for reconnection before capturing a message or attachment even though the mounted dashboard remains available.

## Summary

Keep open: current main still routes the mounted reconnecting chat page through `connected`-based UI gates, so the textarea and Send path are disabled before the existing waiting-reconnect queue can be used. The merged reconnect/send work in related PRs is useful context, but it does not implement this issue's central compose-while-reconnecting behavior, and the protected `maintainer` label means this should stay in maintainer handling rather than cleanup-close or autonomous routing.

## What This Changes

The issue requests that Control UI allow chat text and attachments to be composed, persisted, queued, and flushed after reconnect while an established Gateway session is reconnecting.

## Best Possible Solution

Separate compose/queue capability from live transport connectivity in the Control UI chat path, reuse the existing composer persistence and waiting-reconnect queue, keep realtime-only and retry actions connection-bound, and add browser E2E coverage for offline submit, storage, reconnect flush, and exactly-once send.

## Summary

Keep open. Current main and v2026.6.11 still only order already-debounced WhatsApp entries by server timestamp; they do not batch delayed arrivals by `messageTimestamp`, and the remaining tolerance/default/config choice needs maintainer product direction.

## What This Changes

The issue requests WhatsApp inbound batching based on Baileys `messageTimestamp` rather than receive-time debounce so forward-plus-comment messages arrive as one user turn.

## Best Possible Solution

Choose a WhatsApp-owned, conservative timestamp coalescing contract, then implement it with focused tests and docs while preserving current media, location, quote, access-control, self-message, and control-command bypass behavior.

## Reproduction Assessment

Yes at source level: current main parses and forwards WhatsApp `messageTimestamp`, but the debounce key and timer path do not use it for coalescing. I did not run a live WhatsApp/Baileys delayed-delivery reproduction.

## Solution Assessment

Unclear until maintainers choose the product semantics: timestamp coalescing is plausible and belongs in the WhatsApp boundary, but the default, tolerance, and config shape need ownership review to avoid over-batching and compatibility surprises.

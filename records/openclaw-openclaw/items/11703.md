## Label Justifications

- `P2`: This is a bounded WhatsApp batching/context-quality issue with real user impact but no outage, data loss, or first-run blocker.
- `impact:session-state`: The reported behavior splits one intended WhatsApp interaction into separate agent turns, which can fragment or drift the agent context.

## Summary

The issue should stay open because current main and the latest release still use receive-time debounce for WhatsApp inbound batching; `messageTimestamp` is preserved and ordered but not used as a coalescing key. The remaining choice is product/config direction around opt-in versus default behavior, tolerance, and precedence.

## What This Changes

The issue requests batching WhatsApp inbound messages by WhatsApp server `messageTimestamp` instead of receive time so simultaneous forward/comment messages can reach the agent as one turn.

## Best Possible Solution

Add a WhatsApp-owned, preferably opt-in timestamp coalescing mode for text-only messages from the same account, conversation, and sender, with documented tolerance, schema/docs/tests, and unchanged media, quote, location, access-control, and control-command behavior.

- **Make coalescing default:** Treat same-server-timestamp WhatsApp text messages as one turn by default, accepting an upgrade-sensitive change in turn boundaries.
- **Defer to broader batching policy:** Keep this issue open until per-group debounce, media batching, and timestamp coalescing are resolved as one channel batching design.

## Reproduction Assessment

Yes, at source level: with a short WhatsApp debounce window, the first received message flushes by receive-time timer before a delayed same-`messageTimestamp` Baileys delivery can arrive. I did not run a live WhatsApp/Baileys scenario in this read-only review.

## Solution Assessment

Unclear as a final product choice: timestamp coalescing is the right implementation family for the reported WhatsApp behavior, but default behavior, tolerance, and config precedence need maintainer direction first.

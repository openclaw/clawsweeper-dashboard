## Summary

Current main still uses arrival-time debounce for WhatsApp; platform timestamps can order messages already sharing a buffer but cannot reunite matching messages delivered after that buffer flushes. The request remains necessary, while the batching default, timestamp tolerance, maximum hold, collision behavior, and configuration precedence need maintainer product judgment.

## What This Changes

Add WhatsApp-specific coalescing so delayed messages with the same or nearby platform timestamp can reach the agent as one ordered inbound turn.

## Best Possible Solution

Implement a disabled-by-default WhatsApp-owned coalescer keyed by account, conversation, sender, and a narrowly defined platform-timestamp bucket, with deterministic ordering, a hard hold cap, immediate control-command handling, preserved media and reply metadata, focused fake-timer coverage, and documented configuration precedence.

Options:

- **WhatsApp opt-in coalescing (recommended):** Add a disabled-by-default WhatsApp setting with a narrow timestamp tolerance and hard maximum hold, preserving current behavior for existing users.
- **Shared channel coalescing:** Design a cross-channel session-and-sender coalescer first, accepting broader architecture and configuration work before addressing WhatsApp.
- **Keep arrival-time debounce:** Retain current semantics and document that users must raise debounceMs when Baileys delivery skew exceeds the configured window.

## Reproduction Assessment

Yes at source level: equal-timestamp messages delivered after the configured receive-time timer flush cannot join the prior batch. A live current-main WhatsApp run was not performed.

## Solution Assessment

The timestamp-aware direction is appropriate, but the proposed 50–100 ms flush window cannot capture the reported five-to-ten-second delivery skew; the maintainable solution needs a bounded hold policy and explicit compatibility semantics.

## Summary

Keep open: the reported WhatsApp delivery pattern is not solved by receive-time debounce alone, but batching on second-resolution server timestamps needs an explicit product decision about added latency, collision handling, and whether any new setting is justified. The existing review correctly identifies this as a WhatsApp-owned behavior boundary rather than a generic shared-debouncer change.

## What This Changes

Request WhatsApp-specific inbound coalescing that can keep messages sharing a WhatsApp `messageTimestamp` together despite delayed Baileys delivery.

## Best Possible Solution

Keep the existing receive-time debounce as the default unless an owner approves a WhatsApp-local timestamp-coalescing contract with a narrow eligibility key, bounded hold, collision behavior, command/media flush rules, and focused fake-timer coverage.

## Risks / Open Questions

- WhatsApp `messageTimestamp` has second-level precision, so grouping solely by timestamp can merge unrelated messages from the same sender in a busy conversation.
- The reported Baileys delay can exceed the configured debounce interval; reliably waiting for a late matching message requires an explicit maximum hold and therefore adds latency to otherwise complete single-message turns.
- A new WhatsApp-specific switch or changed default would be compatibility-sensitive because existing users may depend on prompt reply timing and current debounce semantics.

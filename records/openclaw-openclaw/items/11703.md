## Summary

Keep open. Current main and v2026.6.11 still preserve WhatsApp `messageTimestamp` as metadata, but inbound batching remains receive-time debounce keyed by account, conversation, and sender; the remaining timestamp tolerance, default behavior, and config shape need maintainer product direction.

## What This Changes

The issue requests WhatsApp inbound batching based on Baileys `messageTimestamp` so simultaneously sent messages can reach the agent as one turn even when receive-time delivery is delayed.

## Best Possible Solution

Choose a WhatsApp-owned, conservative timestamp coalescing contract for text-only same account/conversation/sender messages, then implement it with focused regression tests and docs while preserving existing bypass behavior.

## Reproduction Assessment

Yes at source level: current main parses and forwards WhatsApp `messageTimestamp`, but the debounce key and timer path do not use it for coalescing. I did not run a live WhatsApp/Baileys delayed-delivery reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product semantics: timestamp coalescing is a plausible direction, but the default, tolerance, and config shape need ownership review to avoid over-batching and compatibility surprises.

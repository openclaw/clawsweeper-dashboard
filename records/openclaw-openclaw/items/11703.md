## Summary

The issue should stay open because current main still preserves WhatsApp server timestamps as message metadata but does not use them to coalesce delayed Baileys deliveries into one inbound turn. The remaining work is a product/config decision around timestamp tolerance and default behavior, not a safe automatic bug-fix lane.

## What This Changes

Request timestamp-based coalescing for WhatsApp inbound messages so simultaneously sent messages with the same or nearby WhatsApp `messageTimestamp` batch into one agent turn instead of separate receive-time debounce turns.

## Best Possible Solution

Add a WhatsApp-owned timestamp coalescing mode for same account, conversation, and sender with a small documented tolerance, preserving existing media/control-command flushing and making any new config/default behavior explicit.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: WhatsApp inbound messages use receive-time debounce keyed by account/conversation/sender while `messageTimestamp` is only stored on the message payload. I did not run a live Baileys scenario, but the reported delayed-delivery behavior would bypass the current debounce once the first timer flushes.

## Solution Assessment

Unclear as a final product choice: timestamp coalescing is the right implementation family for the reported WhatsApp behavior, but the default, tolerance, and config shape need maintainer direction before a fix PR.

## Summary

The current main branch still does not batch delayed WhatsApp messages by server timestamp: it preserves `messageTimestamp` as metadata and sorts buffered entries by it, but the buffer still opens and flushes on receive-time debounce. The issue remains useful and should stay open for a maintainer product decision on timestamp tolerance/default/config shape.

## What This Changes

The issue requests batching WhatsApp messages by WhatsApp server `messageTimestamp` rather than only by receive-time debounce, so forward-plus-comment and rapid same-timestamp messages arrive in one agent turn.

## Best Possible Solution

Add a WhatsApp-owned timestamp coalescing path only after maintainers choose the default and tolerance, preserving current media, command, access-control, durable-receive, read-receipt, reply-context, and shutdown-drain behavior.

## Reproduction Assessment

Yes, at source level. Current main uses receive-time debounce timers and a key of account, conversation, and sender, while `messageTimestamp` is only preserved as event metadata and ordering input inside an already-open buffer.

## Solution Assessment

Unclear until maintainers choose the product contract. The likely best shape is a narrow WhatsApp text-only coalescing rule using server timestamps with a small documented tolerance, not a broad shared debouncer rewrite or long global debounce default.

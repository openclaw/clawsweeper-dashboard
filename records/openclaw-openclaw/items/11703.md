## Summary

Keep open. Current main and v2026.6.11 still use WhatsApp inbound debouncing by account, conversation, sender, and receive-time timer; `messageTimestamp` is parsed and preserved, but it is not a coalescing key, timer input, or documented config contract. Related WhatsApp batching issues overlap but do not supersede this timestamp-specific product decision.

## What This Changes

The issue requests WhatsApp inbound batching that groups same account, conversation, and sender messages by WhatsApp server `messageTimestamp` instead of only by receive-time debounce.

## Best Possible Solution

Approve a WhatsApp-owned timestamp coalescing contract with conservative text-only scope, tolerance, and defaults, then implement it in the WhatsApp monitor using existing debounce seams with focused docs and tests.

## Reproduction Assessment

Yes at source level: current main parses and forwards WhatsApp `messageTimestamp`, but the debounce key and receive-time timer do not use it for coalescing. I did not run a live WhatsApp/Baileys delayed-delivery reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product semantics. Timestamp coalescing is plausible, but the safest shape is a WhatsApp-owned, conservative text-only mode rather than changing the shared debouncer or adding broad defaults without a tolerance/config decision.

## Summary

Keep open: current main still batches WhatsApp ingress by a receive-time sliding debounce keyed by account, conversation, and sender; it sorts a completed batch by event timestamp but never uses that timestamp to keep a late-arriving sibling in the batch. This remains a WhatsApp-owned feature decision because second-resolution timestamps can collide and the required late-arrival grace period changes response latency. Likely related people: steipete (high confidence) and vincentkoc (medium confidence).

## What This Changes

Add WhatsApp-specific inbound coalescing so messages from the same sender and conversation with the same WhatsApp server timestamp can reach the agent as one turn despite delayed Baileys delivery.

## Best Possible Solution

Have a WhatsApp owner define an opt-in, bounded timestamp-coalescing contract for same account, conversation, and sender, including collision behavior, command/media/reply handling, and live proof of the delayed-delivery case before adding any configuration keys.

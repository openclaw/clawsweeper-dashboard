## Summary

Current main and v2026.6.11 still capture WhatsApp text only within an arrival-time debounce window; the platform timestamp orders entries already in a buffer but cannot coalesce a related message delivered after that buffer flushes. No canonical issue or PR owns this exact behavior, so the request remains necessary, but the default, tolerance, maximum hold, and configuration precedence require maintainer product judgment.

## What This Changes

Add WhatsApp-specific timestamp-aware batching so related messages delivered seconds apart can reach the agent as one turn.

## Best Possible Solution

Define an opt-in, WhatsApp-owned coalescing mode that reuses the existing admitted/deduped delivery path, groups only text messages with the same account, conversation, sender, and narrowly bounded platform timestamp, enforces a hard maximum hold, and preserves immediate flushing for media, locations, control commands, reply-context boundaries, and shutdown.

## Risks / Open Questions

- WhatsApp timestamps have second-level granularity, so grouping without strict account, conversation, sender, tolerance, and maximum-hold rules could merge unrelated rapid messages.
- An opt-in config is the safest compatibility shape, but it adds another public setting whose account/channel precedence and upgrade behavior must be documented and tested.
- The inbound monitor also owns durable receive, dedupe, access control, read receipts, media, reply context, and keyed ordering; a parallel buffering path could regress those invariants.

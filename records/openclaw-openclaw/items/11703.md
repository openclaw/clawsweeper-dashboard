## Summary

Keep open. Current main and v2026.6.11 still preserve WhatsApp `messageTimestamp` as inbound metadata but batch WhatsApp text through a receive-time debounce window, so the requested server-timestamp coalescing remains unresolved and needs a maintainer product/config decision.

## What This Changes

The issue requests WhatsApp inbound batching based on WhatsApp server message timestamps rather than only local receive-time debounce.

## Best Possible Solution

Add a WhatsApp-owned, backwards-compatible timestamp coalescing mode for text-only messages from the same account, conversation, and sender, with a small documented tolerance and tests preserving media, location, quote, control-command, read-receipt, and shutdown-drain behavior.

Options:

- **Add opt-in WhatsApp coalescing (recommended):** Introduce a narrowly scoped WhatsApp timestamp coalescing option with focused tests and no default behavior change for existing users.
- **Make coalescing default:** Treat same-server-timestamp WhatsApp text messages as one turn by default, accepting an upgrade-sensitive behavior change.
- **Defer to broader batching design:** Keep this issue open until per-group debounce, media batching, and timestamp coalescing are resolved as one channel batching policy.

## Reproduction Assessment

Yes, at source level. Current WhatsApp inbound delivery uses a receive-time debouncer keyed by account, conversation, and sender while `messageTimestamp` is only stored on the emitted message, so delayed same-timestamp Baileys deliveries can miss the existing debounce window.

## Solution Assessment

Unclear as a final product choice. Timestamp coalescing is the right implementation family for the reported WhatsApp behavior, but maintainers still need to choose the default, tolerance, and config shape.

## Summary

Current main and v2026.6.11 still use arrival-time debounce for WhatsApp; platform timestamps can order messages already buffered but cannot reunite matching messages delivered after the buffer flushes. The request remains necessary, while the batching default, timestamp tolerance, maximum hold, and configuration precedence need maintainer product judgment.

## What This Changes

Coalesce WhatsApp messages from the same sender and conversation using their server timestamps so delayed forward-plus-comment bursts reach the agent as one turn.

## Best Possible Solution

Add an opt-in, WhatsApp-plugin-owned coalescer for text-only messages with the same account, conversation, sender, and exact server timestamp, bounded by a documented maximum hold and preserving immediate flush or bypass behavior for commands and non-text events.

Options:

- **Opt-in exact timestamp (recommended):** Add a WhatsApp-local disabled-by-default setting that groups only exact timestamp matches with a bounded maximum hold and explicit bypass rules.
- **Use the broad coalescing RFC:** Defer implementation until https://github.com/openclaw/openclaw/issues/51361 defines a shared cross-channel batching contract that can express the WhatsApp case.
- **Keep receive-time debounce:** Decline timestamp coalescing and document that users must increase debounceMs when Baileys delivers related messages several seconds apart.

## Reproduction Assessment

Yes at source level: same-sender WhatsApp text is flushed by an arrival-time timer, so a matching server-timestamp message delivered after that timer necessarily starts another turn. A fresh live Baileys reproduction was not performed during this read-only review.

## Solution Assessment

Unclear pending the product contract. The issue's broad global configuration proposal is not the narrowest path; a WhatsApp-local, opt-in, exact-timestamp rule with a hard hold cap is safer.

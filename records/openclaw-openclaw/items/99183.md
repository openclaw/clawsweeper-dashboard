## Summary

This issue is still necessary: current main still forks the local embedding worker without an explicit executable, so a running Gateway whose `process.execPath` points at a removed Homebrew Cellar Node can still hit the reported ENOENT path.

## What This Changes

Fix local llama.cpp embedding worker startup after Homebrew removes the Node binary recorded in a running Gateway process.

## Best Possible Solution

Reuse or promote the existing stable Homebrew Node path resolution for the local embedding worker fork, add a stale-Cellar regression test, and avoid new config or a doctor-only workaround.

## Reproduction Assessment

Yes at source level, but not with a live Homebrew upgrade run here. Current main omits `execPath` in the local worker `fork()`, and Node's `fork()` defaults that executable to `process.execPath`, which is exactly the deleted-Cellar path described in the report.

## Solution Assessment

Yes, the narrowest maintainable fix is to give the worker fork a stable Node executable or retry once after stale-execPath ENOENT. A health-check-only warning would still leave running gateways with broken new worker spawns.

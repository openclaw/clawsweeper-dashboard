## Label Justifications

- `P0`: A confidential-routing policy plugin cannot reliably enforce in-boundary model routing before all model submissions, which can send sensitive prompts to the wrong provider.
- `impact:security`: The report is about a failed confidentiality enforcement point before model submission.
- `impact:auth-provider`: The missing identity is the resolved provider/model routing data needed to distinguish local versus cloud serving.

## Summary

Keep open: current main only partially satisfies the report. Post-hoc model-call telemetry includes provider/model identity, and the embedded runner passes model identity through hook context, but the CLI before_agent_run path still builds hook context without resolved provider/model and the provider hook pair remains internal-only.

## What This Changes

Request that blocking-capable plugin hooks expose resolved provider/model identity before model submission, confirm post-hoc model-call telemetry, and eventually expose provider call attribution hooks.

## Best Possible Solution

A documented and tested blocking hook contract should expose the resolved provider/model before submission on every agent path, with provider-call hooks treated as a separate API design unless maintainers explicitly choose to fold them into this fix.

Options:

- **Standardize existing context contract (recommended):** Guarantee ctx.modelProviderId and ctx.modelId on before_agent_run across embedded and CLI agent paths, document it as read-only policy input, and add regression tests.
- **Add a new post-resolve blocking hook:** Introduce a dedicated pre-model-call hook, which is more explicit but broadens the plugin SDK and needs compatibility/API review.
- **Split provider hook exposure into design work:** Fix before_agent_run identity now and keep before_provider_request/after_provider_response exposure as a separate provider-hook design discussion.

## Reproduction Assessment

Yes from source inspection: a CLI before_agent_run hook can receive event/context without resolved provider/model because cli-runner.ts omits those fields before buildAgentHookContext. I did not execute a live plugin repro.

## Solution Assessment

No, closing as implemented would not be the best resolution because telemetry and embedded-runner context only cover part of the request. The best narrow path is to standardize the existing context fields across all blocking before_agent_run paths, then decide separately whether provider hooks should become public API.

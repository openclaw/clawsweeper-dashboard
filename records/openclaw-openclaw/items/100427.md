## Label Justifications

- `P0`: The issue reports a confidentiality policy guard failing open and a confidential turn being served by an external cloud provider.
- `impact:security`: The missing hook metadata affects enforcement of a confidentiality boundary before model serving.
- `impact:auth-provider`: The affected decision depends on resolved provider/model identity and provider routing visibility.

## Summary

Keep open: current main and the latest release still omit resolved provider/model from the blocking `before_agent_run` hook, while `model_call_ended` already carries observe-only attribution metadata; the remaining ask is a security-sensitive plugin API decision.

## What This Changes

Expose resolved provider/model identity to a blocking-capable plugin hook so policy plugins can block confidential turns before serving, and confirm post-hoc model-call attribution.

## Best Possible Solution

Add a documented, read-only resolved provider/model identity contract at a blocking-capable phase, preferably `before_agent_run`, with regression tests and docs; keep `model_call_*` as sanitized observe-only audit hooks.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose resolved provider/model identity on `before_agent_run`, add a dedicated post-resolve blocking hook, or keep model-bound policy enforcement outside plugin hooks?

Rationale: This changes a public plugin security boundary for policy enforcement, and the safe contract depends on maintainer intent around sanitized metadata, raw provider hooks, and backward-compatible hook semantics.

Likely owner: steipete

Owner reason: The decision crosses public plugin API and security posture, and this handle is the strongest current-main routing signal from recent merged hook/runtime history.

Owner confidence: medium

Options:

- **Add read-only identity to `before_agent_run` (recommended):** Expose resolved provider/model metadata on the existing fail-closed blocking hook so policy plugins can enforce before model input without a new raw provider-call surface.
- **Add a post-resolve blocking hook:** Create a new hook between model resolution and provider dispatch if maintainers want a cleaner phase boundary than extending `before_agent_run`.
- **Keep enforcement outside hooks:** Document config-derived agent-chain or provider-selection policy as the supported enforcement path and leave hook attribution observe-only.

## Reproduction Assessment

Yes for the source-level hook gap: current main resolves provider/model before attempt dispatch but does not include those fields in `before_agent_run`. The reported external-cloud confidentiality leak itself was not independently live-reproduced in this read-only review.

## Solution Assessment

Yes on direction but not yet on exact shape: exposing read-only resolved identity on an existing blocking hook looks like the narrowest maintainable path, while raw provider hook exposure needs a separate security/API decision.

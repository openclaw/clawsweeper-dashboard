## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.91

Full review comments:

- **[P1] Target the active SQLite auth-profile store:** `src/agents/auth-profiles/paths.ts:32`
  - body: This PR seals `auth-profiles.json`, but current main no longer reads or writes that file as the runtime auth-profile store: `saveAuthProfileStore()` persists secrets in `openclaw-agent.sqlite`, and tests assert legacy `auth-profiles.json` is ignored. As written, the new passphrase mode can appear to encrypt OpenClaw-owned auth stores while the active provider credentials remain in SQLite JSON rows.
  - confidence: 0.94
- **[P1] Block plaintext downgrade when the passphrase is missing:** `src/agents/auth-profiles/store.ts:438`
  - body: When a sealed auth file is loaded without `OPENCLAW_PASSPHRASE`, `loadProtectedAuthJson()` returns `undefined`; the later legacy/OAuth/CLI sync path can still set `shouldWrite` and call `saveSealedJsonFile()`. Because `saveSealedJsonFile()` writes plaintext with no passphrase, an operator who forgets the env var can replace sealed credentials with plaintext and potentially partial data.
  - confidence: 0.93
- **[P1] Write sealed credential files atomically and privately:** `src/infra/sealed-json-file.ts:113-114`
  - body: `saveSealedJsonFile()` writes directly to the destination and only then applies `chmod(0o600)`. Credential-bearing files need the existing fs-safe atomic/private replace pattern so there is no permissive creation window, truncation-on-failure exposure, or symlink/clobber path on this security boundary.
  - confidence: 0.9
- **[P2] Persist KDF parameters in the sealed envelope:** `src/infra/sealed-json-file.ts:39`
  - body: The sealed format derives its key with implicit `scryptSync()` parameters and stores no KDF metadata in the envelope. That makes the security posture and future tuning/migration behavior hard to audit because older files do not say which parameters were used to derive the key.
  - confidence: 0.86
- **[P2] Preserve long-running final-response requests:** `src/gateway/client.ts:520-530`
  - body: This branch schedules the default 30s timeout for every request without an explicit timeout, including `expectFinal` calls. Current main's packaged gateway client intentionally leaves `expectFinal` requests without an automatic default timeout, so carrying this forward would break long-running chat/agent responses unless callers explicitly opted in.
  - confidence: 0.88

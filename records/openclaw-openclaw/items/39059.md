## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.94

Full review comments:

- **[P1] Target the active SQLite auth-profile store:** `src/agents/auth-profiles/store.ts:526`
  - body: Current main no longer reads or writes `auth-profiles.json` as the runtime credential store: `saveAuthProfileStore` persists the secrets payload through `writePersistedAuthProfileStoreRaw`, and tests assert that `auth-profiles.json` is not created or read at runtime. Sealing this legacy JSON write path therefore misses the active credential store while presenting the PR as auth-store encryption.
  - confidence: 0.94
- **[P1] Block plaintext downgrade when the passphrase is missing:** `src/agents/auth-profiles/store.ts:438`
  - body: When a sealed auth store is loaded without `OPENCLAW_PASSPHRASE`, `loadProtectedAuthJson` returns `undefined`, so this path can treat the existing store as missing and then persist migration/OAuth/CLI data through `saveSealedJsonFile` without a passphrase. That writes plaintext over the sealed file instead of failing closed.
  - confidence: 0.96
- **[P1] Write sealed credential files atomically and privately:** `src/infra/sealed-json-file.ts:113-114`
  - body: `saveSealedJsonFile` writes credential material with `writeFileSync` and only then applies `chmod(0600)`. Credential writes need creation-time private mode plus atomic replacement, otherwise a local permission window, symlink/clobber behavior, or interrupted write can leak or corrupt the very store this hardening is meant to protect.
  - confidence: 0.9
- **[P2] Preserve long-running final-response requests:** `src/gateway/client.ts:520-524`
  - body: This applies the default 30s timeout even when callers set `expectFinal: true`. Current main deliberately leaves `expectFinal` requests without a default auto-timeout unless the caller supplies one, because agent/final-response RPCs can legitimately run longer than the ordinary per-RPC watchdog.
  - confidence: 0.9
- **[P2] Persist KDF parameters in the sealed envelope:** `src/infra/sealed-json-file.ts:38-39`
  - body: The sealed format derives keys with bare `scryptSync(passphrase, salt, 32)` but does not store KDF parameters in the envelope. Once files are written, changing cost factors or auditing the format becomes ambiguous, so the envelope should include explicit scrypt parameters and the reader should validate them.
  - confidence: 0.86
- **[P2] Read sealed main stores during subagent inheritance:** `src/agents/auth-profiles/store.ts:412-413`
  - body: Late discovery: the head is unchanged from the earlier reviewed SHA, but this inherited-store path was equally visible then. After this PR starts writing the main auth store in sealed form, subagents still read it with `loadJsonFile`, so a passphrase-enabled main store is parsed as non-JSON and inheritance silently fails.
  - late: true
  - confidence: 0.88

## Summary

Keep this issue open for an explicit maintainer product/API decision. Current OpenClaw remains an OS-hosted, Node-based orchestration product; the merged agent-core extraction improves internal ownership but does not provide the stable cross-language, bare-metal runtime protocol requested here. Likely related people: steipete is the strongest routing candidate from the merged runtime refactor and the existing issue discussion.

## What This Changes

Request a supported runtime-agnostic OpenClaw agent interface so embedded, bare-metal, or non-Node implementations such as an ESP32-class device can run an OpenClaw-compatible agent loop.

## System Context

OpenClaw receives channel and CLI inputs through its Gateway, then uses Node-hosted agent, provider, session, and tool runtime components to produce replies and actions. A portable embedded runtime would need a stable external contract for those inputs, policy decisions, state, events, and outputs rather than only reusing internal TypeScript modules.

## Architecture Diagram

flowchart LR
  A[Channel or CLI input] --> B[Gateway and policy]
  B --> C[Node-hosted agent runtime]
  C --> D[Providers tools and sessions]
  D --> E[Events replies and actions]
  F[Portable runtime contract] -. requested boundary .-> B
  F -. requested boundary .-> C

## Best Possible Solution

Start with a maintainer-sponsored design/RFC that defines the smallest supported external runtime contract, its security and state ownership, conformance tests, and one constrained reference host before committing to a full no-Node or bare-metal implementation.

## Maintainer Decision

Rationale: This is a large product and compatibility commitment: choosing the contract determines which session, tool, auth, streaming, persistence, and security semantics become supported outside the current process.

Likely owner: steipete

Owner reason: The merged agent-runtime ownership refactor and the existing issue response make this the clearest available routing candidate for the runtime-boundary decision.

Owner confidence: high

Options:

- **Sponsor a narrow portability RFC (recommended):** Define a minimal external runtime protocol and conformance scope before approving any language, WASM, or embedded implementation.
- **Keep Node as the supported runtime:** Treat external projects such as MimiClaw as independent implementations and retain only current Gateway/plugin extension seams.
- **Extend plugin IPC first:** Advance the language-agnostic plugin boundary in https://github.com/openclaw/openclaw/issues/98004, then reassess whether it exposes a genuine embedded-runtime gap.

## Summary

Keep open: current main and the latest release still lack the requested mobile custom-header path, and the work is now owned by two open platform PRs that need owner/security review rather than cleanup closure.

## What This Changes

The issue requests per-gateway custom HTTP headers in the iOS and Android apps so mobile clients can reach gateways behind authenticating reverse proxies.

## Best Possible Solution

Review and land or intentionally reject the linked iOS and Android PRs under one shared mobile proxy-credential contract with secure storage, redaction, gateway-only attachment, and real authenticated-proxy proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should native mobile gateway clients support arbitrary per-gateway custom headers, or should the first supported contract be a narrower typed proxy-auth surface such as Basic, Bearer, or fixed service-token headers?

Rationale: The source gap is clear, but this changes a credential-bearing pre-Gateway-auth boundary and determines how secrets are stored, redacted, scoped, and attached on both mobile platforms.

Likely owner: steipete

Owner reason: steipete is assigned to the issue, authored the active platform PRs, and has the strongest current signal across this mobile gateway security/product boundary.

Owner confidence: high

Options:

- **Approve a typed proxy-auth contract first (recommended):** Land platform work only after it narrows or documents the accepted credential shapes, TLS expectations, storage lifecycle, redaction, and gateway-only isolation.
- **Approve arbitrary per-gateway headers:** Accept the broader operator-defined header surface after owner/security review signs off on reserved-header filtering, secret storage, diagnostics, and non-gateway isolation.
- **Defer native proxy credentials:** Keep mobile reverse-proxy header injection unsupported for now and document VPN, Tailscale, or proxy-bypass alternatives while the security model remains unsettled.

## Reproduction Assessment

Yes, source-level: current main has no iOS or Android connection config field, secure-store slot, settings path, or WebSocket request-header hook for per-gateway custom headers. I did not run a live Cloudflare Access or reverse-proxy repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the credential contract. Per-gateway headers are plausible, but the safer final shape may be a narrower typed proxy-auth surface unless owner/security review approves arbitrary headers.

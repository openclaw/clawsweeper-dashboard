## Summary

Keep this issue open: current main and v2026.6.11 still leave stale `waiting` TaskFlows as non-terminal audit warnings only, and the direct fix attempt is closed unmerged after review found blanket timeout semantics unsafe. The report remains credible, but the exact busy-state owner still needs live diagnosis before a safe core fix can be scoped.

## What This Changes

The issue reports that orphaned TaskFlow rows stuck in `waiting` can keep a session busy and make heartbeat wakes repeatedly return `requests-in-flight`.

## Best Possible Solution

Define explicit controller-owned TaskFlow wait abandonment or deadline semantics, then wire startup/runtime recovery into the owner that actually holds the busy state and prove legitimate durable waits are preserved.

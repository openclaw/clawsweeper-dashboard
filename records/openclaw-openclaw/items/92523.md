## Summary

Keep open: current main and latest stable still leave `waiting` TaskFlows durable and non-terminal with audit-only stale detection, while the direct fix PR closed unmerged because blanket timeout semantics were unsafe.

## What This Changes

The issue reports orphaned TaskFlow `waiting` rows that may permanently block heartbeat dispatch with `requests-in-flight` skips.

## Best Possible Solution

Define explicit controller-owned wait abandonment or deadline semantics, then wire gateway/runtime recovery to the actual busy-state owner with proof that legitimate durable waits are preserved.

- **Manual repair only:** Keep stale waits as diagnostics and provide a documented operator repair path without changing the default runtime lifecycle.
- **Global default timeout:** Apply a uniform timeout to all waiting flows, accepting the compatibility risk for plugins with legitimate long waits.

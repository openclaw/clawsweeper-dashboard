## Summary

Keep this issue open: current main and v2026.6.11 still leave managed `waiting` TaskFlows as durable non-terminal state with audit-only stale warnings, and the closed direct fix attempt was unsafe because it added a blanket timeout without a wait-abandonment contract or live proof that it releases the heartbeat busy owner.

## What This Changes

The issue requests recovery for orphaned managed TaskFlows stuck in `waiting` so they cannot permanently block heartbeat dispatch as `requests-in-flight`.

## Best Possible Solution

Define explicit managed TaskFlow wait-abandonment or deadline semantics, then wire gateway/startup/runtime recovery to the proven busy-state owner with live proof that legitimate durable waits and pending-final delivery are preserved.

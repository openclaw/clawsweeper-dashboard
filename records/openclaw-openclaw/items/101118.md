## Summary

Keep open: the patch addresses the source-proven tight startup replay problem and includes useful terminal proof, but the new 250ms pacing is counted against the existing 60s recovery deadline, so large eligible backlogs can be left pending until another startup.

## What This Changes

This PR adds a shared 250ms startup recovery pacing helper and applies it to outbound and session delivery replay loops, with focused fake-timer tests.

## Best Possible Solution

Keep shared replay pacing, but make paced recovery eventually drain or explicitly reschedule eligible outbound and session backlogs instead of relying on another restart when the startup budget is reached.

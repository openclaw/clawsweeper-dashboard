## Summary

Keep open: current main and v2026.6.11 still do not make the state-dir `.env` authoritative over generated service-env values on plain gateway restart. The remaining work is a credential-source policy decision, not a stale cleanup candidate.

## What This Changes

Request to make `~/.openclaw/.env` the single management entry point for daemon environment variables, or otherwise sync, warn, or document conflicts with generated service-env files.

## Best Possible Solution

Maintainers should choose one managed-daemon environment contract, then align restart, install/reinstall, doctor, docs, and tests so stale generated service-env values are refreshed from `.env`, surfaced by a clear warning/repair path, or intentionally documented as higher precedence.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should state-dir `.env` become authoritative over generated service-env values on gateway restart, or should OpenClaw keep process/service env precedence and add conflict warnings, doctor repair, and clearer docs?

Rationale: Both paths affect credential precedence and upgrade behavior, so automation should not pick the permanent auth/source-of-truth contract without maintainer intent.

Likely owner: steipete

Owner reason: Recent work in the daemon install/service-env planning and provider setup area makes this the best available routing candidate for the product decision.

Owner confidence: medium

Options:

- **Keep precedence, add conflict repair (recommended):** Preserve existing process/service env precedence but add restart/install conflict warnings, doctor repair, and docs that explain how stale managed values are resolved.
- **Make `.env` authoritative:** Rebuild managed service env from state-dir `.env` on restart/reinstall with upgrade tests and a clear migration story for operator-managed values.
- **Document current behavior only:** Leave runtime behavior unchanged and document the priority chain, accepting that users may still need to inspect service-env files when keys drift.

## Reproduction Assessment

Yes at source level, not live: `gateway restart` passes `process.env` and macOS launchd restart restages `existing.environment`, so `.env` is not authoritative on plain restart. No live macOS LaunchAgent repro was run in this read-only pass.

## Solution Assessment

Unclear until maintainers choose the contract. Making `.env` the single entry point improves setup UX, but preserving current process/service env precedence with warnings and doctor repair is likely safer for upgrades.

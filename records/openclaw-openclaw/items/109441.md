## Summary

Keep open: the regression is real, but the proposed client-side resolver still diverges from canonical Gateway queue semantics, and the supplied validation is mock-only.

## What This Changes

The PR changes Control UI active-run follow-ups to inherit the Gateway webchat queue configuration unless the browser has an explicit local override.

## Best Possible Solution

Preserve explicit browser choices, but when no browser override exists, submit the active-run message through `chat.send` without forcing a mode so the Gateway applies session, webchat, global, and default precedence; add coverage for all canonical modes and session overrides.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes from source inspection: set a session queue override that differs from `messages.queue`, or use `interrupt` or `collect`, then submit a Control UI follow-up during an active run. The PR reads only configuration and maps every non-`steer` mode to the browser queue.

## Solution Assessment

No. The Gateway already owns effective queue resolution, so duplicating only part of that precedence in the browser is less correct and less maintainable than leaving inherited delivery policy to `chat.send`.

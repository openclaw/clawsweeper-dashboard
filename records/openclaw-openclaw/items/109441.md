## Summary

Keep this PR open. The Gateway-authoritative direction is sound and the current head addresses several earlier race and queue-semantics findings, but live `sessions.changed` updates can still leave the Control UI using stale queue policy; the available behavior evidence is also mock-Gateway-only rather than a live Gateway run.

## What This Changes

The PR makes Control UI active-run follow-ups inherit the Gateway’s effective webchat queue mode while retaining a visible, reversible browser-local override.

## Best Possible Solution

Keep the Gateway authoritative, but project normalized explicit and effective queue modes consistently through session list, history, describe, and `sessions.changed`; then prove with a live Gateway/browser run that changing the session mode during an active run immediately changes the next follow-up’s behavior.

## Solution Assessment

No, not yet. Making the Gateway authoritative is the narrowest maintainable fix, but the implementation must cover the live `sessions.changed` surface so policy cannot become stale between full refreshes.

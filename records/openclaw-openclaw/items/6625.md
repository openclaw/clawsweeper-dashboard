## Summary

Current main still lacks a child-visible pre-timeout warning or grace contract before `runTimeoutSeconds`; this remains a valid core sub-agent lifecycle feature that needs maintainer product/API direction rather than cleanup closure.

## What This Changes

The issue requests a configurable warning sent to a sub-agent shortly before the hard run timeout so the child can checkpoint unsaved work.

## Best Possible Solution

Define a core sub-agent lifecycle contract for a configurable pre-timeout warning, then implement it consistently across `sessions_spawn`, native spawn, ACP spawn, config schema, docs, and focused lifecycle tests while preserving existing post-timeout recovery.

## Maintainer Decision

Required: true

Rationale: The missing behavior is real, but adding a warning deadline changes public config/tool semantics and requires cross-runtime lifecycle choices that automation cannot safely choose.

Likely owner: steipete

Owner reason: Recent blame and prior review context place this account closest to sub-agent lifecycle, ACP spawn, and timeout/announce behavior.

Owner confidence: high

Options:

- **Add global and per-spawn warning controls (recommended):** Expose a documented default plus per-spawn override, schedule a child-visible warning before hard timeout, and test native plus ACP behavior.
- **Add only a global default:** Keep the tool API smaller by configuring the grace period only under sub-agent defaults, at the cost of less per-task control.
- **Defer in favor of post-timeout recovery:** Keep the current hard-timeout and recovery model and close or narrow this request if maintainers do not want child-visible timeout warnings.

## Solution Assessment

Unclear as proposed. A pre-timeout warning addresses the reported loss mode, but maintainers need to choose public config/API semantics and a delivery design that works across native and ACP runs.

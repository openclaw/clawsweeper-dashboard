## Summary

Keep open: current main still exposes a hard `runTimeoutSeconds` boundary without a native pre-timeout checkpoint warning, while the requested behavior requires a new cross-runtime lifecycle and configuration contract. Likely related people: steipete (high confidence) and vincentkoc/mitchmcalister (medium confidence) based on sub-agent timeout, ACP, and configuration history.

## What This Changes

The issue requests a warning before a sub-agent’s wall-clock timeout so it can persist progress before termination.

## Best Possible Solution

Define one owner-approved child-lifecycle policy that schedules a best-effort checkpoint warning before an absolute deadline, documents its delivery guarantees for native and ACP runs, and adds focused lifecycle tests without conflating it with inactivity-based stall recovery.

## Maintainer Decision

Question: Should OpenClaw add a supported absolute-deadline checkpoint-warning contract, and if so should it be a shared sub-agent default only or also a native per-spawn API despite ACP’s current timeout-override boundary?

Rationale: The request is a new lifecycle capability and potentially a new configuration/API surface; source and docs show native and ACP timeout controls are not currently symmetric, so implementation cannot safely choose the permanent public contract unilaterally.

Options:

- **Design one shared warning contract (recommended):** Specify a documented best-effort warning and its native/ACP guarantees before implementing a single coherent configuration surface.
- **Defer to stall recovery only:** Keep absolute wall-clock deadlines unchanged and treat inactivity-based nudge/kill work in https://github.com/openclaw/openclaw/issues/39305 as the supported recovery direction.
- **Adopt a native-only warning:** Expose a warning only for native sub-agent runs and explicitly document that ACP runs retain hard-timeout behavior.

## Reproduction Assessment

No live reproduction was performed, but source and current documentation provide a high-confidence path: configure a finite `runTimeoutSeconds`, run a child past that deadline, and observe that the supported contract has no pre-deadline child warning.

## Solution Assessment

Unclear: a pre-timeout warning is a plausible solution, but it is not yet proven to be the best permanent API because native and ACP runs have different timeout-override contracts and the related inactivity-recovery design overlaps only partially.

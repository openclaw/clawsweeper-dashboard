## Label Justifications

- `P2`: This is a meaningful reliability improvement for long-running delegated work, but it is a new lifecycle capability rather than an urgent regression.
- `impact:data-loss`: A hard timeout can discard useful work that the child has not yet persisted or returned.
- `impact:session-state`: The request concerns preserving and communicating child-session progress during a terminal lifecycle transition.

## Summary

Keep open: current main still enforces a hard sub-agent run deadline without warning the child first. The related stall-recovery request uses inactivity rather than an absolute wall-clock deadline, so it overlaps in lifecycle machinery but does not supersede this request.

## What This Changes

Add a configurable warning shortly before a sub-agent's hard run timeout so it can checkpoint or return partial progress.

## Best Possible Solution

Implement one race-safe internal child-intervention primitive, expose a config-owned warning before the absolute run deadline, support native and ACP only where the guarantee is real, and keep inactivity recovery separately parameterized.

Rationale: The requested behavior is new policy and configuration surface, and maintainers must choose its cross-runtime guarantee and relationship to the overlapping stall-recovery design before implementation.

Owner confidence: high

Options:

- **Unified primitive, distinct policies (recommended):** Build one internal intervention scheduler, add a config-only absolute-deadline warning, and let inactivity recovery use separate thresholds on the same control path.
- **Deadline-only implementation:** Add a narrow warning tied only to `runTimeoutSeconds`, accepting runtime-specific limitations and deferring inactivity recovery integration.
- **Keep hard timeout unchanged:** Retain post-timeout partial-progress recovery and require agents or prompts to checkpoint periodically without adding another lifecycle setting.

## Reproduction Assessment

Yes at source level: configure a short sub-agent run timeout, start a longer task, and inspect the child transcript; current code reaches the hard deadline without scheduling a warning. A live timed run was not performed during this read-only review.

## Solution Assessment

Unclear pending product direction. A per-spawn warning parameter is not the best default because current main deliberately rejects per-call timeout overrides; a config-owned policy using a shared internal intervention primitive is narrower and more maintainable.

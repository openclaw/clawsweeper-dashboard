## Summary

Current main and v2026.6.11 still enforce a hard sub-agent run deadline without warning the child first. Related work addresses inactivity recovery, idle handling, or post-timeout notification, so the requested absolute-deadline warning remains distinct and needs a maintainer-selected native/ACP contract.

## What This Changes

Requests a configurable warning shortly before a sub-agent hard timeout so the child can checkpoint work before termination.

## Best Possible Solution

Define one sub-agent intervention subsystem with distinct absolute-deadline and inactivity triggers, documented defaults, deterministic timer cancellation, and explicit native/ACP delivery guarantees before adding public configuration.

Options:

- **Unified lifecycle policy (recommended):** Implement one intervention subsystem with separate deadline and inactivity triggers, shared delivery semantics, and coordinated timer ownership.
- **Deadline warning only:** Add a narrowly scoped pre-timeout warning and explicitly document any weaker ACP behavior where equivalent steering is unavailable.
- **Keep hard deadlines:** Retain hard timeouts and post-timeout recovery without adding another runtime control or configuration surface.

## Reproduction Assessment

Yes at source level: a sub-agent whose work exceeds runTimeoutSeconds reaches a hard deadline, and current schema and spawn paths contain no preceding warning phase. A live timed run was not performed during this read-only review.

## Solution Assessment

No, the proposed standalone sessions.subAgentGracePeriodSeconds key is not the best final design. The behavior should live under the existing sub-agent lifecycle policy and reconcile the overlapping inactivity-nudge design across native and ACP runtimes.

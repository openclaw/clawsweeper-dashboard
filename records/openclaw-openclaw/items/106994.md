## Summary

Keep open: the current head still has four blocking upgrade-path defects, and the strong Windows/macOS proof was captured before later lifecycle changes, so it does not validate the exact merge candidate.

## What This Changes

The PR adds candidate-owned Node engine enforcement, explicit staged lifecycle execution, install-completion verification, and package-manager policy changes to preserve an existing installation when an update candidate cannot run.

## Best Possible Solution

Keep the candidate-owned preinstall guard, but accept the actual packed lifecycle contract, preserve validated legacy downgrade packages, prevent candidate postinstall from touching user state before activation, probe the Node used by the installed shim, and then rerun exact-head supported and unsupported real updates.

Full review comments:

- **[P1] Allow the packed prepare hook in the lifecycle contract:** `src/infra/package-update-lifecycle.ts:24`
  - body: The published package retains its declared `prepare` field, but this new contract requires `prepare: null`; consequently an ordinary npm candidate reaches staged validation and is rejected as an unsupported prepare contract. Match the actual packed manifest or strip and verify the field during packaging.
  - confidence: 0.98
- **[P1] Preserve validated legacy downgrade targets:** `src/infra/package-update-lifecycle.ts:132`
  - body: The unconditional install-guard requirement rejects shipped releases through 2026.7.1 even though the tarball checker recognizes them as legacy guardless packages and the CLI documents confirmed downgrades. Add a bounded legacy validation path using the older package metadata and dist inventory instead of making those targets uninstallable.
  - confidence: 0.96
- **[P1] Defer user-state migration until candidate activation:** `src/infra/package-update-steps.ts:789`
  - body: The staged lifecycle runs the candidate's full postinstall before final verification and swap, and that script can migrate the user's plugin registry. If verification or swap then fails, the old package remains but user state has already been rewritten by the rejected candidate; disable that migration while staging or split it into a post-activation step.
  - confidence: 0.97
- **[P1] Validate the Node used by the installed command shim:** `src/cli/update-cli/update-command.ts:304`
  - body: Normal package updates validate against `process.execPath` unless a managed-service node override is supplied, while the installed `openclaw` entrypoint later uses `/usr/bin/env node`. A user invoking the updater with a newer explicit Node but retaining an older Node first on PATH can therefore activate a package that ordinary CLI launches cannot run; probe the shim runtime before swap.
  - confidence: 0.95

## Summary

Keep this issue open: current main and v2026.6.11 still lack a browser-navigation userinfo rejection/redaction guard, while the linked browser PR is open and unmerged.

## What This Changes

The issue asks for browser open/navigate URLs containing embedded username/password credentials to be rejected early and redacted in surfaced errors/logs.

## Best Possible Solution

Keep this issue as the canonical tracker until https://github.com/openclaw/openclaw/pull/82490 or an equivalent maintainer-approved fix rejects credentialed browser navigation URLs before browser, proxy, Playwright, Chrome MCP, or Chromium dispatch and redacts diagnostics.

Required: true

Kind: security_boundary

Question: Should OpenClaw browser page navigation reject HTTP(S) URLs with embedded username/password userinfo before any browser or proxy dispatch?

Rationale: The guard would reduce credential exposure in runtime errors and logs, but it is a fail-fast behavior change for any existing Basic-auth URL workflow.

Likely owner: steipete

Owner reason: The current affected lines and recent browser-path history point most strongly to steipete for the browser security policy decision.

Owner confidence: high

Options:

- **Fail fast and redact (recommended):** Reject credentialed browser navigation URLs before dispatch, redact userinfo in surfaced diagnostics, and direct users to authenticated profiles, cookies, headers, or Playwright credentials.
- **Redact but preserve pass-through:** Keep URL-embedded Basic auth working while hardening log/error redaction, accepting that Chromium/Playwright still receives the credentialed URL.
- **Defer to browser auth design:** Leave the issue open until maintainers design a broader browser authentication policy and replacement workflow.

## Reproduction Assessment

Yes, source-level: current main forwards browser open/navigate URL input and the shared navigation guard does not inspect `URL.username` or `URL.password`. I did not run a live browser reproduction in this read-only cleanup review.

## Solution Assessment

Yes at the boundary level: the maintainable fix belongs in the browser plugin input/navigation guard before Chromium, Playwright, Chrome MCP, or proxy dispatch sees the URL. The exact fail-fast policy still needs maintainer acceptance because it can break Basic-auth URL workflows.

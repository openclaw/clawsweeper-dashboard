## Summary

Keep this issue open: current main and the latest release still do not reject browser open/navigate URLs with parsed username/password userinfo, and https://github.com/openclaw/openclaw/pull/82490 is the open candidate fix rather than merged implementation evidence.

## What This Changes

The issue requests failing early and redacting errors when the browser tool receives HTTP(S) navigation URLs with embedded credentials.

## Best Possible Solution

Keep this as the canonical tracker until the browser plugin rejects and redacts credentialed navigation URLs before proxy, Playwright, Chrome MCP, or Chromium dispatch, with maintainer acceptance of the fail-fast policy and supported alternatives such as browser credentials, headers, cookies, or an authenticated profile.

## Reproduction Assessment

Yes, source-level with high confidence: current main forwards browser open/navigate URL input toward local or proxy dispatch, and the shared navigation guard does not check parsed URL username/password. I did not run a live Chromium repro because this review is read-only.

## Solution Assessment

Yes at the direction level, but not complete yet. The maintainable fix belongs in the browser plugin input and navigation guard path before any browser/proxy dispatch, while the open candidate PR still needs maintainer review and policy acceptance before this issue can close.

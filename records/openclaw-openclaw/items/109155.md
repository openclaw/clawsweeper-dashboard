## Summary

Keep this PR open for revision: the underlying drip-hang bug is valid, but the unconditional one-hour cutoff can fail healthy large or slow model pulls, and the submitted proof is limited to Vitest-controlled loopback behavior.

## What This Changes

The PR adds a one-hour wall-clock deadline to Ollama setup model-pull streams, threads timeout overrides through the pull helper, and adds fake-timer and loopback HTTP regression tests.

## Best Possible Solution

Keep timeout ownership in `extensions/ollama/src/setup.ts`, but detect semantic no-progress—such as unchanged digest/completed values and status—rather than imposing a fixed total duration on healthy transfers, then prove the result through a real Ollama setup or daemon run.

## Reproduction Assessment

Yes, at source level: after headers, current main has only a per-chunk idle timer, so a server that emits any NDJSON chunk more often than every 300 seconds never times out. The supplied loopback test models that path, although it was not independently run in this review.

## Solution Assessment

No. A total one-hour cutoff bounds the hang but also bounds healthy progress; a semantic no-progress watchdog is the narrower fix because Ollama exposes status, digest, total, and completed fields.

## Summary

Keep open: the watchdog still treats `completed` as the only healthy-progress signal, but Ollama documents status-only verification and manifest-finalization phases after downloads complete. That can abort a healthy setup pull after the no-progress budget, so the prior P1 remains unresolved.

## What This Changes

The PR adds a no-progress timeout for Ollama setup model pulls, threads test-only timeout controls through the pull path, and adds focused fake-timer and local HTTP loopback regressions.

## Best Possible Solution

Keep one no-progress deadline, but reset it on meaningful documented pull-state transitions as well as increasing `completed`, while retaining the existing byte-idle timeout for silent bodies and adding a regression for a delayed status-only finalization phase.

## Reproduction Assessment

Yes, from source and Ollama’s documented protocol: emit increasing `completed` until download completion, then keep a documented status-only finalization phase open beyond a shortened no-progress budget. The current completed-only watchdog should cancel that otherwise healthy pull path.

## Solution Assessment

No. A completed-only reset is not the narrowest correct contract because Ollama defines healthy post-download status-only phases; resetting on meaningful status transitions plus increasing byte progress bounds duplicate drips without rejecting those phases.

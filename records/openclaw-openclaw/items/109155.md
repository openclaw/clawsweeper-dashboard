## Label Justifications

- `P0`: A non-technical first-time Ollama user can be blocked during onboarding with no in-product recovery when a pull stream never completes.
- `merge-risk: 🚨 compatibility`: The PR changes the timeout semantics of an existing automatic model-pull setup workflow and can newly fail valid-looking status-only pulls.
- `merge-risk: 🚨 availability`: The intended no-progress timeout can be bypassed by alternating status messages, leaving setup indefinitely stalled.

## Summary

The prior P1 blocker remains: the new watchdog treats every distinct status string as semantic progress, so a non-advancing stream can alternate status values forever and still avoid the timeout. The submitted loopback evidence is useful and the focused scope is otherwise sound, but this defeats the PR’s stated hang-prevention guarantee.

## What This Changes

The PR adds an Ollama setup-pull no-progress watchdog, test-only timeout overrides, and fake-timer plus native loopback regressions for dripping NDJSON pull streams.

## Best Possible Solution

Keep byte progress as the primary liveness signal and bound any status-only grace so repeated or cycling status text cannot postpone the timeout indefinitely; add a loopback regression for that adversarial stream while retaining the healthy finalization coverage.

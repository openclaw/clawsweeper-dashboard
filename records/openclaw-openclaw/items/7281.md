## Summary

Keep open. Current documented hook mappings still expose one delivery route, while the requested post-failure cross-channel delivery contract remains absent and needs maintainer direction before implementation.

## What This Changes

Add an ordered fallback channel or channels for hook-mapping delivery when the primary outbound channel fails.

## Best Possible Solution

Define a constrained, typed hook-delivery fallback contract first, then carry an ordered destination chain through hook mapping, dispatch, cron delivery, and outbound error handling with privacy, duplicate-delivery, and final-failure tests.

Options:

- **Design a constrained fallback chain (recommended):** Adopt ordered explicit destinations only after specifying opt-in routing, account ownership, retryable failure classes, and all-targets-failed reporting.
- **Keep one-target hook delivery:** Retain the current single-destination contract and document failure notifications or operator recovery as the supported behavior.
- **Expose a plugin seam first:** Add a generic post-send failure hook only if maintainers prefer extension-owned routing policy over a core hook-mapping option.

## Reproduction Assessment

Yes at the source-contract level: a mapping can configure one delivery channel and target, while current documentation provides no fallback-chain field. A live disconnected-channel scenario was not run in this read-only review.

## Solution Assessment

Unclear until maintainers choose the delivery contract. Reusing `channel: "last"` or `failureDestination` would not provide the requested post-failure resend semantics; a typed, explicit chain is the narrow maintainable path if the feature is accepted.

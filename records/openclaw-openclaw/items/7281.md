## Summary

Keep open: current main still models hook mapping delivery as a single target, and the related broad recovery PR is closed unmerged rather than a replacement for this focused fallback-chain request.

## What This Changes

The issue requests configurable hook mapping delivery fallback, such as `fallbackChannel` or `fallbackChannels`, when the primary hook delivery channel fails.

## Best Possible Solution

Define a shared ordered delivery-failover contract at the cron/outbound boundary, then expose typed hook-mapping config only after retry, idempotency, and reporting semantics are settled.

## Reproduction Assessment

Yes, source-reproducible: current config, schema, mapping, hook dispatch, and cron delivery carry one target and reject the proposed fallback keys. I did not run a live WhatsApp-to-webchat failure scenario in this read-only review.

## Solution Assessment

No, not as a hook-only field. The maintainable solution is a shared ordered delivery-failover contract that hook mappings can use after retry, idempotency, unknown-outcome, and reporting semantics are decided.

## Summary

Keep open: current main and v2026.6.11 still model hook delivery as a single channel/target, so the requested post-failure fallback chain remains unimplemented and needs a maintainer product decision.

## What This Changes

The issue requests a hook mapping fallback channel option so failed primary delivery can retry another channel.

## Best Possible Solution

Define a typed hook fallback delivery policy, then carry it through hook config/schema, mapping resolution, dispatch payloads, CronDelivery, outbound retry, docs, and regression tests after maintainers choose the public semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should hook mappings support automatic post-failure fallback delivery, and should the public shape be an ordered fallbackChannels chain, reuse cron failureDestination, or avoid cross-channel failover?

Rationale: This adds public config and cross-channel delivery semantics, and repository policy treats fallback/config additions as product- and compatibility-sensitive.

Likely owner: steipete

Owner reason: steipete has the strongest hook mapping provenance and prior review context on this exact request.

Owner confidence: high

Options:

- **Add ordered fallbackChannels (recommended):** Add a typed ordered fallback list for hook mappings and attempt alternates only after a real primary delivery failure, with docs and all-targets-failed tests.
- **Reuse failureDestination:** Route hook delivery through the existing cron failure-destination concept if maintainers want one shared failure-notification model instead of hook-specific failover.
- **Do not add failover:** Keep hook mappings single-target and document failureDestination, bestEffort, and channel health as the supported recovery paths.

## Reproduction Assessment

Yes. Source inspection confirms the proposed fallback keys are absent from hook config/schema and the hook dispatch path creates only one delivery target; I did not run a live disconnected-channel scenario.

## Solution Assessment

Unclear until maintainers choose the product contract. A fallback chain is plausible, but the best fix must settle ordering, failureDestination interaction, privacy/allowlist behavior, and failure reporting first.

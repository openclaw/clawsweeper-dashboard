## Summary

Keep open: current main and the latest release still model hook delivery as a single `channel`/`to` target, and the only related broad recovery PR is closed unmerged rather than a safe canonical implementation.

## What This Changes

The issue requests configurable hook mapping fallback delivery channels when the primary channel send fails.

## Best Possible Solution

Define a shared ordered delivery-failover contract at the cron/outbound boundary, then expose typed hook-mapping config that populates it with documented retry, idempotency, and failure-reporting semantics.

## Reproduction Assessment

Yes, source-reproducible: current hook config, strict schema, mapping pipeline, dispatch payload, and cron delivery path carry one target and reject or drop the proposed fallback keys. I did not run a live WhatsApp-to-webchat failure scenario in this read-only review.

## Solution Assessment

No, not as a hook-only field. The maintainable solution is a shared ordered delivery-failover contract that hook mappings can use after retry, idempotency, unknown-outcome, and reporting semantics are decided.

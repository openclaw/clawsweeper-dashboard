## Label Justifications

- `P2`: This is a valid delivery-reliability enhancement with limited blast radius, but it needs product semantics before implementation rather than urgent regression repair.
- `impact:message-loss`: When primary hook delivery fails after an agent response is generated, the requested notification can reach no user-visible channel.

## Summary

Keep open: current main and the latest release still model hook delivery as one target, while the related broad recovery PR was closed unmerged and does not replace this request.

## What This Changes

The issue requests a `fallbackChannel` or ordered `fallbackChannels` hook-mapping option that retries an alternate channel after primary hook delivery fails.

## Best Possible Solution

Define an ordered delivery-failover contract at the cron/outbound boundary, then expose typed hook-mapping config that populates it with documented retry, idempotency, and failure-reporting semantics.

## Reproduction Assessment

Yes, source-reproducible: current config, schema, mapping, hook dispatch, and cron delivery carry one target and reject the proposed fallback keys. I did not run a live WhatsApp-to-webchat failure scenario in this read-only review.

## Solution Assessment

No, not as a hook-only field. The maintainable solution is a shared ordered delivery-failover contract that hook mappings can use after retry, idempotency, unknown-outcome, and reporting semantics are decided.

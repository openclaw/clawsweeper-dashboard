## Summary

Keep open: current main and the latest release still model hook mapping delivery as one channel/target, while the requested post-failure fallback chain would add new config and delivery semantics that need maintainer product direction.

## What This Changes

The issue requests configurable hook delivery fallback channels so a hook response can retry a secondary channel after the primary delivery channel fails.

## Best Possible Solution

Define a shared ordered delivery-failover contract at the cron/outbound boundary, then expose typed hook-mapping config with docs and regression coverage for primary-fails/fallback-succeeds and all-targets-failed outcomes.

## Reproduction Assessment

Yes. Source inspection shows the current path carries a single delivery target from hook config/schema through mapping, hook dispatch, CronDelivery, and direct outbound delivery; I did not run a live WhatsApp-to-webchat failure scenario.

## Solution Assessment

No, not as a hook-only field. The maintainable fix is a shared ordered delivery-failover contract that hook mappings populate after maintainers settle retry, idempotency, unknown-outcome, and reporting semantics.

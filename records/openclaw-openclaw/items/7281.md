## Label Justifications

- `P2`: This is a normal-priority delivery-resilience feature with bounded but meaningful impact when a configured hook channel is unavailable.
- `impact:message-loss`: A failed primary delivery currently leaves the hook-generated notification undelivered because no alternate completion destination exists.

## Summary

Keep open: current main and the latest release still provide only one hook completion destination, while existing failure alerts and source-context fallbacks have different semantics; the remaining work requires a maintainer decision on safe cross-channel payload replay.

## What This Changes

Add configurable fallback delivery channels for hook mappings when the primary outbound delivery attempt fails.

## Best Possible Solution

Extend the shared cron/hook delivery plan with ordered explicit destination objects, validate every destination before sending, deduplicate equivalent targets, record each attempt in delivery traces, and keep failure notifications distinct from replaying the original payload.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw replay hook completion payloads across ordered explicit cross-channel destinations after the primary delivery attempt fails?

Rationale: Current contracts intentionally separate primary completion delivery, additional completion webhooks, failure notifications, and source-context selection; cross-channel payload replay adds new public configuration, privacy, retry, and accounting semantics that require maintainer intent.

Likely owner: steipete

Owner reason: The existing issue review already frames the unresolved product choice across hook mapping, cron delivery, outbound sending, and documentation.

Owner confidence: medium

Options:

- **Shared explicit alternates (recommended):** Add ordered explicit destination objects to the shared cron/hook delivery plan with validation, deduplication, attempt traces, and all-targets-failed reporting.
- **Failure notification only:** Keep a single completion destination and use the existing separate failure destination to report the failed send without replaying the original payload.
- **No automatic failover:** Retain explicit single-target delivery and require channel recovery or manual retry.

## Reproduction Assessment

Yes at source level, though no live failure was run: strict hook mapping config carries one destination into one outbound delivery attempt, with no post-failure alternate-channel loop.

## Solution Assessment

No, the proposed scalar `fallbackChannel` is underspecified because each alternate needs explicit target, account, and thread semantics; the shared delivery-plan contract is the safer maintainable owner.

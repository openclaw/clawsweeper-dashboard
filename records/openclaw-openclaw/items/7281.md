## Summary

Keep open: current main and the latest release still model hook-mapping delivery as a single primary channel/target, so configurable post-failure fallback delivery remains unimplemented and needs maintainer product direction.

## What This Changes

Request adding configurable hook delivery fallback channels so a hook mapping can retry another channel after the primary channel fails.

## Best Possible Solution

Settle a typed hook fallback delivery contract, then implement it through config/schema, hook mapping, dispatch, cron delivery, outbound retry, docs, and focused regression coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should hook mappings support automatic post-failure fallback delivery, and if so should the public config be an ordered fallbackChannels list, reuse cron failureDestination, or keep hooks single-target?

Rationale: This adds public configuration and cross-channel delivery semantics, and repository policy treats fallback/config additions as product- and compatibility-sensitive.

Likely owner: steipete

Owner reason: steipete has the strongest current hook-surface history signal and already reviewed this product question as open.

Owner confidence: high

Options:

- **Add ordered fallbackChannels (recommended):** Add a typed ordered fallback list for hook mappings and attempt alternates only after a real primary delivery failure, with docs and tests for all-targets-failed behavior.
- **Reuse failureDestination:** Model hook fallback through the existing cron failure-destination abstraction if maintainers want one shared failure-routing concept.
- **Keep single-target hooks:** Keep hook mappings single-target and document channel last, bestEffortDeliver, and failureDestination as the supported recovery paths.

## Reproduction Assessment

Yes, at source level. The requested fallback keys are absent from hook mapping types and rejected by strict schema, while dispatch and cron delivery carry only one target.

## Solution Assessment

Unclear until maintainers choose the public contract. An ordered fallback chain is plausible, but the best fix must settle failureDestination interaction, bestEffort behavior, privacy/allowlist rules, and all-targets-failed reporting first.

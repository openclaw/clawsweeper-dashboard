## Label Justifications

- `P2`: This is a valid delivery-reliability enhancement with clear source evidence, but it needs product semantics before implementation rather than urgent regression repair.
- `impact:message-loss`: When primary hook delivery fails after an agent response is generated, the requested notification can reach no user-visible channel.

## Summary

Keep open: current main and v2026.6.11 still model hook-triggered delivery as one target, while the requested ordered fallback chain would add new config and cross-channel failure semantics that need maintainer product review.

## What This Changes

Request adding `fallbackChannel` or ordered `fallbackChannels` to hook mappings so a hook delivery can try another channel after the primary send fails.

## Best Possible Solution

Define a shared ordered delivery-failover contract at the cron/outbound boundary, then expose typed hook-mapping config that populates it with documented retry, idempotency, and failure-reporting semantics.

## Reproduction Assessment

Yes, source-reproducible: current config, schema, mapping, hook dispatch, and cron delivery carry one target and reject or drop the proposed fallback keys. I did not run a live WhatsApp-to-webchat failure scenario in this read-only review.

## Solution Assessment

No, not as a hook-only field. The maintainable solution is a shared ordered delivery-failover contract that hook mappings can use after retry, idempotency, unknown-outcome, and reporting semantics are decided.

## Label Justifications

- `P2`: This is a valid hook delivery reliability enhancement with limited blast radius, but it needs product semantics before implementation rather than urgent regression repair.
- `impact:message-loss`: When primary hook delivery fails after an agent response is generated, the requested notification can reach no user-visible channel.
- `maturity:stable`: The affected Gateway HTTP hook ingress and delivery boundary overlaps `gateway-runtime`, which is scored M4 Stable in the checked-in maturity scorecard.

## Summary

Keep open: current main and the latest release still model hook delivery as one channel/target, so the requested post-failure fallback chain is not implemented and needs maintainer product direction.

## What This Changes

Requests a `fallbackChannel` or ordered `fallbackChannels` hook-mapping option so failed primary hook delivery can retry an alternate channel.

## Best Possible Solution

Define a shared ordered delivery-failover contract at the cron/outbound boundary, then expose typed hook-mapping config with docs and tests once retry, idempotency, and reporting semantics are settled.

## Reproduction Assessment

Yes, source-level. Current config types, strict schema, mapping transforms, hook dispatch, and cron delivery carry one target and reject the proposed fallback keys; I did not run a live WhatsApp-to-webchat failure scenario in this read-only review.

## Solution Assessment

No, not as a hook-only field. The maintainable solution is a shared delivery-failover contract that hook mappings can populate after retry, idempotency, unknown-outcome, and reporting semantics are decided.

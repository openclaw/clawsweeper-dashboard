## Summary

Current main and v2026.6.11 still expose one hook delivery destination; configurable post-failure failover remains missing and needs maintainer agreement on routing, deduplication, and cross-channel trust semantics before implementation.

## What This Changes

Requests configurable fallback destinations for hook-triggered delivery when the primary channel send fails.

## Best Possible Solution

Add an opt-in ordered list of fully qualified delivery routes, with explicit channel, recipient, account, and thread identity; attempt alternates only after a classified definitive failure, preserve idempotency, report the winning route and all failures, and keep failure notifications separate.

Options:

- **Failure notification only:** Keep one response destination and expose a separately configured route that receives only a delivery-failure notification.
- **No automatic failover:** Retain single-destination hook delivery and require operators or agents to implement alternate sends explicitly.

## Reproduction Assessment

Yes at source level: current main documents and carries only one hook delivery channel and target, so no configurable post-failure route can be selected. A live transport outage was not reproduced during this read-only review.

## Solution Assessment

No, not as a bare `fallbackChannel` string. The maintainable solution is a typed ordered route contract with explicit destination identity, security checks, definitive-failure rules, deduplication, and separate failure-notification semantics.

## Risks / Open Questions

- Automatic cross-channel failover can disclose hook-generated content to a different account, recipient, thread, or audience unless every fallback route is explicit and policy-validated.
- A primary send can fail ambiguously and later succeed, so naive failover could duplicate notifications without stable attempt identity and definitive-failure classification.
- The requested `webchat` example may not represent a normal outbound channel destination; the product contract must define which destination types are eligible rather than accepting arbitrary channel strings.
- Reusing `failureDestination` would conflate delivery of the original response with delivery of an error notification and produce misleading status semantics.

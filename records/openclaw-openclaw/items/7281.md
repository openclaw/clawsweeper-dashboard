## Summary

Keep open. Current main’s public hook contract still exposes one delivery route (`channel` and `to`), while cron’s `failureDestination` is a failure-notification route rather than a post-failure resend of the hook response. The requested behavior is a new, compatibility-sensitive cross-channel delivery contract that needs maintainer direction before implementation.

## What This Changes

Add ordered fallback delivery targets for hook mappings so an agent response can be delivered through another configured channel after primary delivery fails.

## Best Possible Solution

Define one typed, ordered hook-delivery fallback target contract with explicit channel, recipient, account, and thread identity; carry it through mapping resolution and cron delivery, retry only definitive transport failures, preserve dedupe/error reporting, and document the trust-boundary and `failureDestination` distinction.

## Risks / Open Questions

- A fallback that reuses inferred or `last` targets across channels could deliver hook-derived content into a different identity, account, thread, or trust boundary than the primary route.
- Retrying after an ambiguous transport outcome can duplicate a message; the contract needs definitive-failure classification, idempotency/dedupe behavior, and all-targets-failed reporting.
- Adding a bare `fallbackChannel` without an explicit target/account/thread model would create unclear semantics for channels that require recipient or account selection.

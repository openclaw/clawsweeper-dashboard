## Label Justifications

- `P2`: This is a valid hook delivery reliability enhancement with limited blast radius, but it needs product semantics before implementation rather than urgent regression repair.
- `impact:message-loss`: When primary hook delivery fails after an agent response is generated, the requested notification can reach no user-visible channel.
- `maturity:stable`: The affected Gateway runtime hook ingress and delivery fallback behavior sit under `gateway-runtime`, which is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main still models hook mapping delivery as a single channel/target, so the requested post-failure fallback chain is not implemented and needs maintainer product decisions before a safe fix.

## What This Changes

The issue requests a `fallbackChannel` or ordered `fallbackChannels` option for hook mappings so failed primary delivery can retry another channel.

## Best Possible Solution

Define a shared ordered delivery-failover contract at the cron/outbound boundary, then expose typed hook-mapping config once retry, idempotency, and failure-reporting semantics are settled.

## Reproduction Assessment

Yes, source-level: current config types, strict schema, mapping transforms, hook dispatch, and cron delivery carry one target and reject the proposed fallback keys. I did not run a live WhatsApp-to-webchat failure scenario in this read-only review.

## Solution Assessment

No, not as a hook-only field. The maintainable solution is a shared delivery-failover contract that hook mappings can populate after retry, idempotency, unknown-outcome, and reporting semantics are decided.

## Label Justifications

- `P2`: This is a valid delivery-reliability enhancement with limited blast radius, but it needs product semantics before implementation rather than urgent regression repair.
- `impact:message-loss`: When primary hook delivery fails after an agent response is generated, the requested notification can reach no user-visible channel.

## Summary

Keep open: current main and v2026.6.11 still model hook delivery as a single target, and the existing `fallbackChannel` helpers are pre-delivery channel-selection fallbacks, not post-failure hook delivery failover.

## What This Changes

Request to add configurable `fallbackChannel` or ordered `fallbackChannels` support for hook mapping deliveries when the primary channel send fails.

## Best Possible Solution

Define a shared ordered delivery-failover contract at the cron/outbound boundary, then expose typed hook-mapping config that uses it with documented retry, idempotency, and failure-reporting semantics.

## Reproduction Assessment

Yes, source-reproducible: current config types, strict schema, mapping transforms, hook dispatch, and cron delivery carry one target and reject the proposed fallback keys. I did not run a live WhatsApp-to-webchat failure scenario in this read-only review.

## Solution Assessment

No, not as a hook-only field. The maintainable solution is a shared ordered delivery-failover contract that hook mappings can populate after retry, idempotency, unknown-outcome, and reporting semantics are decided.

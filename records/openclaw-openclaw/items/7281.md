## Summary

Current main and v2026.6.11 still provide only one hook delivery destination; related work covers target safety, account routing, or failure notifications, not post-failure replay, so this remains a valid product-sensitive feature request.

## What This Changes

Add configurable ordered fallback destinations for hook mappings when delivery of the original response to the primary channel fails.

## Best Possible Solution

Extend the canonical hook/cron delivery plan with an ordered list of fully bound destinations, retry only replay-safe failures before partial delivery, preserve authorization checks, and return aggregate diagnostics when all destinations fail.

Rationale: This adds public configuration and cross-channel recipient, authorization, retry, and duplication policy that cannot be settled safely from implementation details alone.

Options:

- **Explicit destination chain (recommended):** Add ordered channel, target, account, and thread destinations with authorization checks, replay-safe failure classification, and duplicate prevention.
- **Failure notification only:** Keep the original response single-target and use failureDestination to notify an operator separately.
- **No automatic replay:** Require operators to configure independent hook workflows for each destination.

## Reproduction Assessment

Yes at the source level: current main carries one hook destination into one outbound delivery path and has no iteration over alternate destinations. This read-only review did not run a live disconnected-channel scenario.

## Solution Assessment

No, a bare `fallbackChannel` field is not the best complete solution; safe failover needs fully explicit destination identity plus rules for authorization, retryable failures, partial delivery, deduplication, and final error reporting.

## Summary

Current main and v2026.6.11 still support only one hook delivery destination; post-failure cross-channel retry remains unimplemented, but its public config, replay safety, and target-binding semantics require maintainer direction.

## What This Changes

Add configurable fallback delivery destinations for hook mappings when the primary outbound send fails.

## Best Possible Solution

Define one canonical ordered destination contract shared by hooks and cron, require explicit target bindings, retry only failures classified as safe to replay, deduplicate destinations, and report the aggregate terminal outcome.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should hook delivery support ordered automatic cross-channel retries after a primary send failure, with every alternate explicitly specifying channel, recipient, account, and optional thread?

Rationale: The request adds public configuration and changes privacy-sensitive routing, replay, and duplicate-delivery semantics that cannot be safely selected from source behavior alone.

Likely owner: steipete

Owner reason: The strongest current and historical trail across hook ingress, delivery contracts, and prior issue review points here for the product choice.

Owner confidence: high

Options:

- **Explicit destination chain (recommended):** Add ordered fully bound destinations to the canonical delivery contract and retry only failures classified as safe to replay.
- **Failure notification only:** Keep one content destination and notify a separate failure destination without replaying the hook output.
- **No automatic retry:** Keep single-target delivery and improve provider recovery and failure diagnostics instead.

## Reproduction Assessment

Yes at source level: current main accepts, persists, and executes one hook delivery destination and contains no ordered post-send fallback chain. This read-only review did not run a live disconnected-channel scenario.

## Solution Assessment

No, not as a lone fallbackChannel field; the narrowest maintainable solution needs a canonical explicit destination list, safe replay classification, target validation, deduplication, and terminal failure reporting.

## Label Justifications

- `P2`: This is a valid delivery-reliability enhancement with limited blast radius, but it needs product semantics before implementation rather than urgent regression repair.
- `impact:message-loss`: When primary hook delivery fails after an agent response is generated, the requested notification can reach no user-visible channel.

## Summary

Keep open: current main and the latest release still model hook delivery as a single target, while the requested ordered fallback channel behavior is a new config and delivery contract that needs maintainer product decisions.

## What This Changes

Request to add `fallbackChannel` or `fallbackChannels` to hook mappings so failed primary hook delivery can retry another channel.

## Best Possible Solution

Define a shared ordered delivery-failover contract at the cron/outbound boundary, then expose hook mapping config that populates it with docs and focused tests.

## Reproduction Assessment

Yes. Source inspection shows current hook type/schema/mapping/dispatch and `CronDelivery` all model one target and would reject `fallbackChannel` or `fallbackChannels`; I did not run a live WhatsApp-to-webchat failure scenario.

## Solution Assessment

No, not as a hook-only field. The maintainable solution is a shared cron/outbound failover contract that hook mappings can opt into after retry, idempotency, and reporting semantics are decided.

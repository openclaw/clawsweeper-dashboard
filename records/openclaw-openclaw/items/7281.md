## Label Justifications

- `impact:message-loss`: The reported outcome is that a successfully generated hook notification reaches no user when its single configured delivery channel is unavailable.

## Summary

Current main and v2026.6.11 still expose only one hook delivery destination, so the requested failover remains missing; the issue should stay open until maintainers define the public configuration and safe cross-channel retry contract. ([github.com](https://github.com/openclaw/openclaw/blob/main/docs/gateway/configuration-reference.md))

## What This Changes

Add configurable hook-mapping delivery fallback so a generated response can try an alternate destination after the primary channel fails.

## Best Possible Solution

Define ordered, fully typed fallback destinations containing channel, target, account, and thread identity; retry only after a definitive non-delivery result, preserve one canonical delivery outcome, and document how this differs from `channel: "last"`, `bestEffort`, and failure notifications.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should hook delivery support automatic cross-channel payload failover, and if so what canonical destination shape and retry boundary should it use?

Rationale: A bare fallback channel cannot safely represent recipient/account/thread identity, and retrying ambiguous failures can duplicate messages or disclose hook content across trust boundaries.

Likely owner: steipete

Owner reason: This issue already received product-oriented review from steipete, and the choice affects public configuration, delivery semantics, privacy, and operator expectations.

Owner confidence: medium

Options:

- **Typed ordered destinations (recommended):** Add ordered full destination objects and retry only after definitive non-delivery, with dedupe and all-targets-failed reporting.
- **Failure alert only:** Keep the generated payload single-destination and use a separate configured destination only to report that primary delivery failed.
- **No automatic failover:** Keep channel delivery explicit and require operators or workflows to handle alternate-channel routing themselves.

## Reproduction Assessment

No live failure reproduction was run, but yes, the missing capability is source-reproducible: current hook configuration and documentation carry only one delivery destination and define no post-failure alternate. ([github.com](https://github.com/openclaw/openclaw/blob/main/docs/gateway/configuration-reference.md))

## Solution Assessment

No, the proposed `fallbackChannel` string is not yet the best complete solution because it omits recipient, account, thread, dedupe, and ambiguous-failure semantics; a typed ordered destination contract is safer.

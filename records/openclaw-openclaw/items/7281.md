## Summary

Current main and v2026.6.11 still support only one hook delivery destination, and no related merged or viable open PR implements post-failure channel failover. The request remains useful, but it needs maintainer agreement on the public config and safe cross-channel retry semantics before implementation.

## What This Changes

Add configurable ordered fallback delivery destinations for hook mappings when the primary channel send fails.

## Best Possible Solution

Define one typed ordered destination list with explicit channel, target, and account per entry, retry only classified pre-delivery failures, preserve ambiguous-send safety, and record primary, fallback, and all-targets-failed outcomes in delivery traces.

Owner confidence: high

Options:

- **Add explicit destination list (recommended):** Add ordered destinations containing channel, target, and account, with failover limited to clearly pre-delivery failures and full delivery tracing.
- **Use failure notifications:** Keep original hook delivery single-target and send a separate failure alert through the existing failure-destination model.
- **Require caller routing:** Keep hooks single-target and require external orchestration to select a reachable destination before dispatch.

## Reproduction Assessment

Yes at source level: current main accepts and propagates only one hook delivery destination, so no post-failure alternate can be configured. This read-only review did not run a live disconnected-channel scenario.

## Solution Assessment

Unclear. Ordered fallback can solve the user problem, but the proposed channel-only field is not the safest final shape because fallback destinations also need explicit recipient/account binding and carefully bounded retry semantics.

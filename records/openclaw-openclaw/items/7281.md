## Summary

Keep open: current main and v2026.6.11 still lack a hook-mapping post-failure fallback chain, and the remaining work is a product/config decision rather than maintainer cleanup.

## What This Changes

The issue requests a `fallbackChannel`/`fallbackChannels` option for delivered hook mappings so failed primary channel sends can retry another channel.

## Best Possible Solution

Define a typed hook fallback delivery policy, then carry it through hook config/schema/help, mapping transforms, dispatch payloads, `CronDelivery`, outbound delivery, docs, and regression tests.

## Maintainer Decision

Question: Should hook mappings support automatic post-failure fallback delivery, and if so should the public config be an ordered `fallbackChannels` chain, reuse cron `failureDestination`, or keep hooks single-target?

Rationale: This adds public config and cross-channel delivery semantics, and repository policy treats fallback/config additions as product- and compatibility-sensitive.

Likely owner: steipete

Owner reason: steipete has the strongest current review and hook-surface provenance for this product/config decision.

Owner confidence: high

Options:

- **Add ordered fallbackChannels (recommended):** Add a typed ordered fallback list for hook mappings and attempt alternates only after a real primary delivery failure, with docs and tests for all-targets-failed behavior.
- **Reuse failureDestination:** Model hook fallback through the existing cron failure-destination concept if maintainers want one shared failure-routing abstraction.
- **Keep single-target hooks:** Keep hook mappings single-target and document `channel: "last"`, `bestEffortDeliver`, and `failureDestination` as the supported recovery paths.

## Reproduction Assessment

Yes. By source inspection, the proposed fallback keys are absent from hook mapping types and rejected by strict schema, while dispatch and cron delivery carry only one target.

## Solution Assessment

Unclear until maintainers choose the product contract. A fallback chain is plausible, but the best fix must settle ordered failover, `failureDestination` interaction, privacy/allowlist behavior, and failure reporting first.

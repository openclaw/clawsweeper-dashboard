## Summary

Keep open: current main and v2026.6.11 still model hook mapping delivery as a single target, and the related broad fallback/recovery PR closed unmerged. This remains a valid feature/product-direction item, not a cleanup close.

## What This Changes

The issue requests configurable fallback channels for hook mappings when primary delivery fails.

## Best Possible Solution

Define an ordered delivery-failover contract at the cron/outbound boundary, then expose typed hook-mapping config that populates it with documented retry, idempotency, authorization, and failure-reporting semantics.

## Reproduction Assessment

Yes. Source inspection shows current config, schema, mapping, hook dispatch, and cron delivery carry one target and reject the proposed fallback keys; I did not run a live WhatsApp-to-webchat failure scenario in this read-only review.

## Solution Assessment

No, not as a hook-only custom field. The safer solution is a shared ordered delivery-failover contract that hook mappings can use after retry, idempotency, unknown-outcome, authorization, and reporting semantics are decided.

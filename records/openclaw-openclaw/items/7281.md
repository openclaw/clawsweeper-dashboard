## Summary

Keep open: current main and the latest release still model hook mapping delivery as a single channel/target, so the requested post-failure fallback chain remains unimplemented and still needs maintainer product direction.

## What This Changes

The issue requests a `fallbackChannel` or ordered `fallbackChannels` hook mapping option so failed primary hook delivery can retry another channel.

## Best Possible Solution

Define a typed hook fallback delivery policy and carry it through hook config/schema/help, mapping transforms, dispatch payloads, `CronDelivery`, outbound delivery, docs, and focused failover tests.

## Maintainer Decision

Question: Should hook mappings support automatic post-failure fallback delivery, and if yes should the public config be an ordered `fallbackChannels` chain, reuse cron `failureDestination`, or keep hooks single-target?

Rationale: This adds public config and cross-channel delivery semantics, and repository policy treats fallback/config additions as product- and compatibility-sensitive.

Likely owner: steipete

Owner reason: steipete has the strongest current hook-surface review and ownership signal for this product/config decision.

Owner confidence: high

Options:

- **Add ordered fallbackChannels (recommended):** Add a typed ordered fallback list for hook mappings and attempt alternates only after a real primary delivery failure, with docs and tests for all-targets-failed behavior.
- **Reuse failureDestination:** Model hook fallback through the existing cron failure-destination abstraction if maintainers want one shared failure-routing concept.
- **Keep single-target hooks:** Keep hook mappings single-target and document `channel: "last"`, `bestEffortDeliver`, and `failureDestination` as the supported recovery paths.

## Reproduction Assessment

Yes. By source inspection, the requested fallback keys are absent from hook mapping types and rejected by strict schema, while dispatch and cron delivery carry one target.

## Solution Assessment

Unclear until maintainers choose the product contract. A fallback chain is plausible, but the best fix must settle ordered failover, `failureDestination` interaction, privacy/allowlist behavior, and failure reporting first.

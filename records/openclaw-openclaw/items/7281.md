## Label Justifications

- `P2`: This is a valid delivery-reliability enhancement with limited blast radius, but it needs product semantics before implementation rather than urgent regression repair.
- `impact:message-loss`: When primary hook delivery fails after an agent response is generated, the requested notification can reach no user-visible channel.

## Summary

Keep open: current main and the latest release still model hook mapping delivery as a single target, and the related broad recovery PR was closed unmerged rather than establishing a safe hook failover contract.

## What This Changes

Request to add `fallbackChannel` or ordered `fallbackChannels` to hook mappings so a failed primary delivery can retry an alternate channel.

## Best Possible Solution

Define a shared ordered delivery-failover contract at the cron/outbound boundary, then expose typed hook mapping config that populates it with documented retry, idempotency, and failure-reporting semantics.

## Reproduction Assessment

Yes. Source inspection shows current config, schema, mapping, hook dispatch, and cron delivery carry one target and reject the proposed fallback keys; I did not run a live WhatsApp-to-webchat failure scenario in this read-only review.

## Solution Assessment

No, not as a hook-only field. The maintainable path is a shared ordered delivery-failover contract that hook mappings can use after retry, idempotency, unknown-outcome, and reporting semantics are decided.

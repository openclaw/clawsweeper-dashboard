## Summary

Keep open: current main and the latest release still model hook mapping delivery as a single channel/target, so configurable post-failure hook delivery failover remains unimplemented and needs a maintainer product decision.

## What This Changes

The issue requests configurable hook delivery fallback channels so a hook-delivered agent response can retry another channel after the primary channel fails.

## Best Possible Solution

Define a typed ordered hook fallback delivery contract, then carry it through hook config/schema, mapping transforms, dispatch payloads, cron delivery, docs, and tests for primary-fails, fallback-succeeds, and all-targets-failed outcomes.

Options:

- **Add typed hook fallback chain (recommended):** Approve a narrow `fallbackChannels` contract for explicit user-configured alternates, with docs and tests for retry ordering, delivery status, and all-targets-failed reporting.
- **Keep failure notifications separate:** Do not add hook result failover now; document that `failureDestination` covers failed-run notifications, while hook result delivery remains single-target.
- **Fold into broad delivery contract:** Defer this request into the broader durable final delivery semantics work, accepting slower resolution for the Gmail-style hook fallback use case.

## Solution Assessment

Unclear until maintainers choose the public config shape. The maintainable path is a typed explicit fallback contract, not overloading current `failureDestination` or pre-delivery `fallbackChannel` helpers.

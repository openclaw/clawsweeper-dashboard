- `impact:message-loss`: The reported failure mode is a generated hook response that does not reach the user when the primary delivery channel is unavailable.

## Summary

Keep open: current main and the latest release still model mapped-hook delivery as a single target, and the related delivery-recovery items are adjacent or closed unmerged rather than an implementation of ordered post-failure hook failover.

## What This Changes

Request to add `fallbackChannel` or `fallbackChannels` to hook mappings so `deliver: true` hook output can try an alternate channel after the primary send fails.

## Best Possible Solution

Define a shared ordered delivery-failover contract at the cron/outbound boundary, then expose typed hook-mapping fallback config and docs only after retry, idempotency, target eligibility, and reporting semantics are settled.

## Reproduction Assessment

Yes, source-reproducible: current main rejects the proposed fallback keys and carries only one hook delivery target through mapping, dispatch, and cron delivery. I did not run a live WhatsApp-to-alternate-channel failure scenario in this read-only review.

## Solution Assessment

No, not as a hook-only field. The maintainable path is a shared ordered delivery-failover contract first, then hook config as one caller of that contract if maintainers approve the behavior.

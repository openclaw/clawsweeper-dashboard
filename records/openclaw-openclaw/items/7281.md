## Label Justifications

- `P2`: The request is a normal-priority reliability improvement for hook delivery with limited blast radius but real notification-loss impact.
- `impact:message-loss`: The reported failure mode is generated hook output not reaching the user when the primary delivery channel is unavailable.
- `maturity:stable`: The request touches Gateway hook ingress/HTTP API behavior under the M4 Gateway runtime surface, even though the narrower automation-hooks category is M3.

## Summary

Keep open: current main and v2026.6.11 still model hook mapping delivery as one channel/target, so configurable post-failure `fallbackChannel` or `fallbackChannels` remains unimplemented. Existing `channel: "last"`, cron `failureDestination`, and outbound `fallbackChannel` helpers solve different pre-delivery selection or failure-notification problems.

## What This Changes

Request to add an ordered fallback delivery channel option to hook mappings when the primary hook delivery target fails.

## Best Possible Solution

Define a typed hook fallback-delivery contract first, then carry it through hook config/schema, mapping transforms, dispatch payloads, cron delivery, direct outbound failure handling, docs, and regression tests without reusing failure-alert semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should hook mappings gain a public `fallbackChannel` or `fallbackChannels` config surface, and what exact authorization and retry semantics should apply after primary delivery fails?

Rationale: This changes public hook config and cross-channel delivery behavior, including where potentially private hook output may be sent after a failure; code inspection shows the shape is missing but does not settle the product/security contract.

Likely owner: steipete

Owner reason: Prior issue review and recent adjacent gateway/cron documentation history make this the clearest routing candidate for the product decision.

Owner confidence: medium

Options:

- **Design typed fallback chain (recommended):** Add an explicit ordered fallback config with authorization checks, clear primary-failure conditions, and tests for primary success, fallback success, and all-targets-failed reporting.
- **Use failure notifications only:** Keep completion delivery single-target and document `failureDestination` or cron alerts as the supported notification path when primary delivery fails.
- **Decline core fallback config:** Preserve single-target hook delivery and require operators to choose one reliable delivery channel or implement custom routing outside core.

## Reproduction Assessment

Not applicable as a strict bug reproduction, but the missing feature is source-reproducible: current config, schema, mapping, dispatch, and cron delivery paths carry one target and reject the proposed fallback keys.

## Solution Assessment

Unclear until maintainers choose the product/security contract; the maintainable path is a typed fallback chain, not reusing `channel: "last"` or cron failure notifications as implicit completion-delivery failover.

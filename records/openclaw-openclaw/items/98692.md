## Summary

Keep this PR open: the proof gap is now addressed with loopback terminal evidence, but the submitted Google streaming reader can still hard-fail after all requested embeddings have already been read because it keeps consuming extra or blank output rows instead of cancelling like the merged OpenAI sibling path.

## What This Changes

The PR replaces unbounded Gemini embedding batch upload/create error reads and completed output-file buffering with bounded diagnostics plus a streaming JSONL output reader and focused tests.

## Best Possible Solution

Repair the Google output reader to cancel once all requested IDs are satisfied while preserving per-record bounds, then let maintainers accept or tune the remaining fail-closed limits.

## Reproduction Assessment

Yes at source level: current main still uses `response.text()` for Google upload/create error bodies and completed output downloads, and the PR body includes loopback proof for the intended bounded path. The PR-introduced defect is also source-reproducible: one requested row followed by a blank or unknown row exceeds `maxLines` after the result is already complete.

## Solution Assessment

No as submitted: bounded error reads plus streaming JSONL is the right owner-local fix shape, but the Google reader should match the OpenAI sibling by stopping once all requested IDs are handled. Keeping the current extra-row hard failure is a maintainer compatibility decision, not the safest default repair.

## Label Justifications

- `P2`: The reported failure affects a normal inbound media-analysis workflow with bounded WhatsApp/media-store blast radius.
- `impact:message-loss`: The issue is about a delivered WhatsApp image becoming unreadable through its agent-visible media reference.

## Summary

Current main and v2026.6.11 already cover the reported failure: WhatsApp inbound media is saved once, the agent-visible URI is derived from that same media-store path, the RPC attachment normalizer does not re-save channel files, and media writes no longer prune inbound files.

## What This Changes

The issue asks OpenClaw to keep WhatsApp inbound image `media://inbound/*` references readable across repeated image-tool reads instead of losing the saved media file or ID.

## Best Possible Solution

Keep the current shipped single-save WhatsApp media path and timer-owned media retention; any future failure with configured `media.ttlHours` should come back as a new logs-backed cleanup/retention report.

## Reproduction Assessment

No high-confidence current-main failing reproduction remains. Source inspection on current main disproves the reported double-save path and the shipped media cleanup fix removes the disappearing-file cause.

## Solution Assessment

Yes. The best solution is the current single-save WhatsApp path plus timer-owned cleanup; adding broad path fallbacks or new retention shims would be a less maintainable media-store boundary change.

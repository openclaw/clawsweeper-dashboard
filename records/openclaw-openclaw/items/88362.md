## Summary

Current main and the latest release no longer have the reported WhatsApp double-save path or write-time media pruning that matched the missing-file symptom, so this issue can close as implemented while asking for a new report if a configured TTL sweep still causes a fresh failure.

## What This Changes

The issue reports that WhatsApp inbound images can be read once but fail on a later `media://inbound/<id>` read because the observed media ID no longer resolves to a stored file.

## Best Possible Solution

Keep the released single-save and write-time-prune-free implementation; if users still see second-read failures under `media.ttlHours`, track that as a new retention/pinning bug with logs and config.

## Reproduction Assessment

No current-main failing reproduction is available: source inspection and the latest issue comment both show the reported double-save path is absent on current main. The old v2026.5.27 commit was not present in this checkout, but v2026.6.11 contains the single-save and no-write-prune implementation.

## Solution Assessment

Yes. The best current solution is the shipped implementation that preserves one canonical media-store ID and removes write-time pruning; any remaining TTL sweep behavior should be handled as a focused retention issue with fresh logs.

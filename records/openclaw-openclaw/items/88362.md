## Summary

Current main and the latest shipped release no longer match the reported double-save or delete-after-read path: WhatsApp stores inbound media once, prompt refs point at that stored filename, RPC attachment normalization is a separate in-memory path, and media writes no longer prune inbound files.

## What This Changes

The issue reports WhatsApp inbound image media references failing on repeated `image` tool reads after an alleged double-save UUID mismatch.

## Best Possible Solution

Keep the shipped media cleanup behavior and ask for a fresh report with current-release logs only if repeated WhatsApp media reads still fail under v2026.6.11 or newer.

## Reproduction Assessment

No. The reported double-save path is absent on current main and the latest release source; reproducing any remaining failure would need new current-release WhatsApp logs or a concrete media.ttlHours cleanup trace.

## Solution Assessment

Yes. The best fix is the current owner-boundary behavior: WhatsApp persists inbound media once, prompt refs use the stored media filename, and cleanup is owned by the configured gateway maintenance timer rather than opportunistic media writes.

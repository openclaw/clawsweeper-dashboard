## Summary

Close as implemented on main. The reported double-save path is not present in current source, and the plausible shipped cause for missing second reads, write-time media pruning, was removed by the merged media cleanup fix now present in current main and shipped releases.

## What This Changes

The issue asks OpenClaw to keep WhatsApp inbound image `media://inbound` references readable across later image-tool reads instead of losing the file after first access.

## Best Possible Solution

Keep the shipped v2026.6.9+ behavior: WhatsApp emits the saved inbound media ID, RPC attachment normalization stays in-memory, and cleanup is controlled by the configured maintenance timer instead of media writes.

## Reproduction Assessment

Yes, source-level for the old shipped behavior: v2026.5.27 had write-time cleanup that could delete inbound media, while current main and v2026.6.9+ remove that cleanup path. I did not run a live WhatsApp replay in this read-only review.

## Solution Assessment

Yes. The current implementation solves this at the right boundary by keeping the channel save single-path, avoiding a gateway normalizer re-save, and moving media deletion to configured scheduled cleanup.

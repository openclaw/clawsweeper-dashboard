## Label Justifications

- `P2`: The issue affected a real inbound media analysis workflow in one channel, but it did not show a core crash, security bypass, or broad outage.
- `impact:data-loss`: The reported failure made an inbound user image unavailable through its persisted media reference after it had been saved.
- `impact:message-loss`: A delivered WhatsApp image could not be consumed by the image tool on a later read, effectively dropping the attachment from the agent workflow.
- `impact:session-state`: The symptom depended on the same `media://inbound` reference remaining valid across later turns or subagent context.

## Summary

Close as implemented: current main no longer has the reported WhatsApp double-save path, and the adjacent media deletion cause was fixed by the merged media cleanup PR and shipped in v2026.6.9.

## What This Changes

The issue asks OpenClaw to keep WhatsApp inbound image `media://inbound` IDs readable across later turns instead of losing the stored file or ID after first access.

## Best Possible Solution

Keep the current single-save WhatsApp path plus configured media cleanup behavior; if v2026.6.9 or newer still loses a referenced image, track that as a new retention/log-backed bug with `media.ttlHours` and gateway logs.

## Reproduction Assessment

No current-main failing reproduction remains. The historical disappearing-file behavior is source-reproducible through the removed write-time cleanup path and was supported by the merged PR's before/after host proof, but I did not run a live WhatsApp replay in this read-only review.

## Solution Assessment

Yes. The shipped fix removes the hidden write-time prune and keeps WhatsApp media IDs tied to the original managed inbound file path, which is narrower and safer than adding broad ID/path fallbacks.

## Label Justifications

- `P2`: This is a source-confirmed hook/session lifecycle gap with storage and UI impact, but it is a bounded enhancement rather than an emergency runtime outage.
- `impact:session-state`: Completed hook sessions remain in the session store and session list instead of having hook-specific lifecycle semantics.

## Summary

Keep open: current main and latest release still lack a hook/webhook-specific cleanup or archival policy; the merged cleanup work only covers cron `deleteAfterRun` sessions, and the remaining hook-session lifecycle behavior needs maintainer product direction.

## What This Changes

The issue requests configurable cleanup, archival, delayed retention, and transcript-retention behavior for completed webhook/hook-triggered sessions.

## Best Possible Solution

Add an explicit, default-safe hook-session lifecycle policy in core hooks config/schema/help/docs and hook-run finalization, with on-complete, delayed, and never modes plus clear transcript-retention semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What lifecycle policy should completed hook-agent sessions support, and how should it interact with generic session maintenance, cron retention, persistent hook sessions, and transcript retention?

Rationale: Source inspection proves the gap, but the public config API, default behavior, transcript deletion/archive semantics, and upgrade safety are product and data-retention decisions.

Likely owner: steipete

Owner reason: Peter already supplied the clearest product-direction review for this issue and is the strongest history signal for hook/config policy.

Owner confidence: high

Options:

- **Add Explicit Hook Cleanup Policy (recommended):** Introduce a default-safe `hooks.sessionCleanup` style policy with on-complete, delayed, and never modes plus transcript-retention behavior and focused hook/session tests.
- **Rely On Generic Maintenance:** Document that hook sessions are governed only by `session.maintenance` age/count/disk controls and close hook-specific cleanup as out of scope.
- **Defer Until Persistent Sessions Settle:** Wait for the persistent hook-session direction before designing cleanup so reuse and deletion semantics are not contradictory.

## Reproduction Assessment

Yes, by source inspection. Current main dispatches hook-agent work through isolated cron execution, stores non-cron `hook:*` keys as ordinary agent session rows, and only cleans up cron-key sessions when `deleteAfterRun` is true.

## Solution Assessment

Unclear until maintainers choose the policy. A dedicated hook lifecycle policy is more maintainable than silently reusing subagent or cron retention, but defaults and transcript semantics need product approval.

## Summary

Keep open: current main and the latest release still have no hook-specific cleanup/archive policy, and the merged cleanup work only covers cron-keyed delete-after-run sessions, not hook-created session rows or transcript-retention choices.

## What This Changes

The issue requests configurable cleanup, archival, delayed deletion, and transcript-retention behavior for completed webhook or hook-created sessions.

## Best Possible Solution

Define an explicit hook session lifecycle policy in core with conservative defaults, schema/docs alignment, runtime finalization for direct and mapped hooks, and tests covering on-complete, delayed cleanup, completed-session visibility, and transcript retention.

Rationale: The missing behavior is source-proven, but the fix adds public config and can delete or preserve user transcripts, so automation should not choose the default mode or retention semantics without maintainer intent.

Options:

- **Add Explicit Hook Cleanup Policy (recommended):** Add a `hooks.sessionCleanup`-style policy with conservative defaults, explicit transcript retention, and runtime handling for direct `/hooks/agent`, mapped hooks, and Gmail presets.
- **Use Existing Maintenance Only:** Decline a hook-specific lifecycle knob and document that operators should use global `session.maintenance` for eventual hook-session pruning.
- **Design Broader Ephemeral Sessions:** Fold hook cleanup into a wider cron/hook ephemeral-session model before adding public config surface.

## Reproduction Assessment

Yes. Source inspection shows hook-agent requests are dispatched as isolated jobs with non-cron session keys, while the cleanup helper only deletes cron-keyed `deleteAfterRun` sessions; I did not run a live Gmail webhook scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the lifecycle contract. A hook-specific policy is plausible, but the safest implementation should make cleanup and transcript retention explicit instead of reusing cron retention implicitly.

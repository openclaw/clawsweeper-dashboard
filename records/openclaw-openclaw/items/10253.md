## Label Justifications

- `P2`: This is a source-confirmed hook/session lifecycle gap with storage and UI impact, but it is a bounded enhancement rather than an emergency runtime outage.
- `impact:session-state`: Completed hook sessions remain in the session store and continue to affect session-list state instead of having hook-specific lifecycle semantics.
- `impact:data-loss`: The requested policy controls whether transcripts are retained, archived, or deleted, and current workarounds involve manual file or store deletion.

## Summary

Keep open: current main still lacks a hook/webhook-specific cleanup or archival policy, and the merged cleanup work only covers cron-keyed `deleteAfterRun` sessions, not non-cron `hook:*` rows.

## What This Changes

The issue requests configurable cleanup, archival, delayed retention, and transcript handling for completed webhook/hook-triggered sessions.

## Best Possible Solution

Add an explicit hook-session lifecycle policy in core hooks config, schema/help/docs, and hook-run finalization, preserving safe defaults while supporting on-complete or delayed cleanup with clear transcript-retention semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What hook-session lifecycle policy should OpenClaw support for completed webhook agent runs, and how should it interact with generic session maintenance, cron retention, and persistent hook sessions?

Rationale: The source gap is clear, but the permanent config API, default behavior, transcript deletion or archival semantics, and upgrade safety are product decisions with data-retention consequences.

Likely owner: steipete

Owner reason: Peter already framed the current open-review state for this issue and is the strongest history signal for the product/API decision.

Owner confidence: medium

Options:

- **Add explicit hook cleanup policy (recommended):** Introduce a default-safe `hooks.sessionCleanup` style policy with on-complete, delayed, and never modes plus transcript-retention behavior and focused hook/session tests.
- **Rely on generic maintenance:** Document that hook sessions are governed only by `session.maintenance` age/count/disk controls and close the request for hook-specific cleanup.
- **Defer until persistent mode settles:** Pause cleanup policy until the persistent hook-session direction is settled so cleanup and reuse semantics are designed together.

## Reproduction Assessment

Yes, by source inspection. Current main routes hook-agent runs through isolated cron execution, persists non-cron `hook:*` keys as ordinary agent session rows, and only cleans up cron-key sessions when `deleteAfterRun` is true.

## Solution Assessment

Unclear until maintainers choose the policy. A dedicated hook lifecycle policy is more maintainable than silently reusing subagent or cron retention, but the exact defaults and transcript semantics need product approval.

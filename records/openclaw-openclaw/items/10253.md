- `impact:session-state`: The issue concerns persisted hook session rows, completed lifecycle state, and whether they remain visible or reusable.
- `impact:data-loss`: The requested transcript-retention and delete-on-complete choices can intentionally remove audit and conversation data.

## Summary

Current main still lacks hook-specific lifecycle controls, and the merged cron cleanup remains deliberately restricted to cron keys. This issue remains necessary because generic session maintenance does not provide completion-based cleanup, hook-specific visibility, or transcript-retention semantics.

## What This Changes

Add configurable cleanup, archival timing, transcript retention, and completed-session visibility for hook-triggered sessions.

## Best Possible Solution

Define a closed hook session mode distinguishing backward-compatible retained isolation, explicit ephemeral disposal, and persistent stable-key conversations, with mode-owned visibility, delay, transcript retention, and maintenance precedence.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What lifecycle contract should stable and generated hook session keys use: backward-compatible retained isolation, explicit ephemeral disposal, or persistent multi-turn reuse, and under which modes may transcripts be deleted?

Rationale: Current main always creates a fresh isolated run but persists its row, while the cleanup request and the open persistent-reuse request require incompatible outcomes unless explicit modes and defaults are selected.

Likely owner: steipete

Owner reason: The prior detailed review and broad hook/session history provide the strongest available product-routing signal for choosing user-facing defaults.

Owner confidence: medium

Options:

- **Explicit hook session modes (recommended):** Keep current behavior as the compatibility default and add explicit ephemeral and persistent modes with mode-specific cleanup and transcript rules.
- **Retention-only policy:** Add only a hook TTL and leave completion disposal and stable-key persistence for later work.
- **Shared ephemeral primitive:** Design a generic core ephemeral-session contract first, then expose hooks as one caller alongside cron and other task-scoped runs.

## Reproduction Assessment

Yes at source level: current hook dispatch creates isolated runs, persists non-cron hook rows and transcript paths, and cannot enter the cron-only cleanup helper. A live hook run was not performed, so this is source-reproducible rather than runtime-reproduced.

## Solution Assessment

No, directly inheriting subagent archival or cron retention is not the best fix because hook keys can represent either one-shot events or persistent conversations. Explicit lifecycle modes at the hook/session boundary are narrower and safer.

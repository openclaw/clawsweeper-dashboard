## Summary

Keep open: current `main` still accepts `auth.mode: "none"` HTTP requests before consulting the browser-origin policy, while the WebSocket path rejects disallowed `Origin` headers. This is a real core gateway security-boundary issue, but the fix should get security/maintainer confirmation because it changes behavior for the explicit no-auth private-ingress mode.

## What This Changes

The issue reports that gateway HTTP state-changing routes accept cross-origin browser requests when `gateway.auth.mode` is `none`, unlike the WebSocket origin gate.

## Best Possible Solution

Enforce the existing browser-origin gate for any gateway HTTP request that carries an `Origin` header, including `auth.mode: "none"`, while preserving origin-less non-browser clients and adding focused regression coverage for state-changing HTTP routes.

- **Document None Mode As Fully Unguarded:** Leave runtime behavior unchanged and document that `auth.mode: "none"` has no browser-origin protection for HTTP APIs.
- **Require A Separate Design:** Pause implementation for a broader CSRF/private-ingress design if maintainers do not want the HTTP path to match WebSocket semantics.

Yes, conditionally: reusing `checkBrowserOrigin` for Origin-bearing HTTP requests is the narrowest maintainable fix and avoids a new config option. Maintainers still need to confirm the security-boundary choice for the explicit no-auth mode.

## Summary

Current evidence does not establish a privilege escalation: the named surface is test-only, ordinary test code can already mutate `process.env`, and the normal pull-request CI workflow uses `pull_request` with read-only repository permissions rather than a credential-bearing `pull_request_target` path. Keep this open only for an explicit security-owner determination of whether a separate trusted workflow runs untrusted tests with secrets.

## What This Changes

The issue requests restricting test environment overrides so test code cannot replace sensitive token variables during CI runs.

## Best Possible Solution

First identify a concrete workflow where untrusted code receives credentials; if one exists, isolate secrets and trust at the workflow/job boundary rather than treating a convenience test helper as the sandbox, and otherwise close the report under the test-only security policy.

## Summary

Keep open: current main and the latest release protect the WebChat UI from stale-history replacement, but the durable `chat.send` contract remains unresolved because the gateway still returns `started` before the user-turn recorder is created or persisted.

## What This Changes

The issue reports silent WebChat user-message loss when an optimistic local send is replaced by `chat.history` before the user turn is durably recorded or processed.

## Best Possible Solution

Define and implement the WebChat `chat.send` success contract so an accepted send is either durably persisted and progressing or visibly failed, ideally by resolving the open gateway candidate PR or replacing it with a narrower recorder-based fix.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should WebChat `chat.send` return `started` only after the user turn is durably recorded, or should it keep the faster ACK and add explicit visible recovery/failure semantics for unpersisted turns?

Rationale: Current source proves the ACK-before-recorder boundary remains, but the best product contract affects latency, duplicate suppression, and how session recovery reports failures.

Likely owner: shakkernerd

Owner reason: The remaining decision lives on the shared user-turn recorder and gateway fallback persistence contract introduced in the transcript centralization work.

Owner confidence: high

Options:

- **Persist Before ACK (recommended):** Make durable user-turn persistence part of a successful `chat.send` ACK and return a terminal failure when that cannot be established.
- **Fast ACK With Recovery:** Keep the low-latency ACK but add a durable pending/recovery state and a visible failure if persistence or dispatch never completes.
- **Close As UI Mitigated:** Treat the current pending-send and optimistic-history preservation as sufficient and leave the gateway ACK contract unchanged.

## Reproduction Assessment

Yes from source inspection, but not from a fresh live current-main run in this read-only review. Current main still returns `chat.send` `started` before recorder creation/persistence, while the UI now preserves optimistic messages across stale history.

## Solution Assessment

Unclear until maintainers choose the durable-send contract. A recorder-backed gateway fix is the narrowest complete solution for the durable-loss path; the current UI-only mitigation is necessary but not sufficient for the reported 'never processed' failure.

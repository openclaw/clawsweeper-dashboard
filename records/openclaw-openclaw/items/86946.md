## Summary

Keep open: current main and the latest release preserve WebChat optimistic/pending messages better, but the durable `chat.send` ACK/progress contract this issue asks about is still unresolved and the direct gateway-side candidate PR remains open and conflicting.

## What This Changes

The issue reports silent loss of accepted WebChat user messages when `chat.send` returns before the durable transcript and a later `chat.history` reconciliation drops the optimistic bubble.

## Best Possible Solution

Define the gateway contract so an accepted WebChat `chat.send` is either durably visible/progressing or fails visibly and auditably, while keeping the shipped UI pending-message protections.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw make `chat.send` ACK contingent on durable user-turn visibility/progress for WebChat, or keep the current faster ACK plus UI-side preservation and post-dispatch fallback model?

Rationale: Both choices are plausible product/runtime contracts, and the safer durable boundary may change latency and duplicate/session-rollover behavior beyond a mechanical bug fix.

Likely owner: shakkernerd

Owner reason: The decision centers on the user-turn transcript recorder and persistence contract introduced in their recent merged refactor.

Owner confidence: medium

Options:

- **Adopt durable progress contract (recommended):** Rework or replace the gateway candidate so accepted WebChat sends are durably visible or visibly failed, with tests for duplicate sends, session rollover, and runtime-owned persistence.
- **Keep fast ACK contract:** Document that `started` only means accepted for dispatch and rely on UI pending preservation plus follow-up fixes for remaining silent-failure modes.
- **Close as UI-fixed only:** Treat the current pending-send/history preservation as sufficient and close the durable transcript concern without changing gateway semantics.

## Summary

Keep open: current main and v2026.6.11 still eagerly resolve active SecretRefs and convert startup resolution failures into fatal startup errors, so the reported supervisor-amplified exec-provider loop is not fixed. The linked Varlock 1Password plugin is useful batching/caching workaround context, but it does not resolve OpenClaw core's startup failure policy.

## What This Changes

The issue asks OpenClaw to prevent exec SecretRef startup failures from crash-looping into external secret-provider rate-limit exhaustion through retry, backoff, circuit breaking, batching, or rate-limit-aware behavior.

## Best Possible Solution

Keep this as the canonical tracker and choose a generic core startup SecretRef failure policy that limits repeated exec-provider calls, preserves clear operator diagnostics, and leaves backend-specific batching/caching to plugin or ClawHub integrations when current provider seams are sufficient.

Rationale: Automation should not choose between fail-fast security posture, bounded retry/backoff, degraded startup, circuit breaking, or new config because those choices affect credential safety, availability, and operator recovery behavior.

Owner confidence: high

Options:

- **Bounded generic retry first (recommended):** Add a small core retry/backoff policy for startup SecretRef activation failures, with clear logs and tests, while avoiding provider-specific 1Password behavior and avoiding new config unless maintainers decide it is needed.
- **Keep fail-fast and document supervisor limits:** Preserve the current fail-closed startup contract and add stronger doctor/docs guidance for launchd/systemd restart throttling and external secret-provider wrappers.
- **Design degraded startup or circuit breaker:** Allow selected gateway surfaces to come up without unavailable secrets or stop retrying after repeated failures, but require a larger security and compatibility design before implementation.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 still throw a fatal startup error when required SecretRef preparation fails, and exec provider failures propagate into that path. I did not run a live 1Password plus launchd quota-exhaustion scenario.

## Solution Assessment

Unclear until maintainers choose the startup policy. A bounded generic startup retry/backoff looks like the narrowest first step, while provider-specific batching/caching is better handled by resolver plugins such as the Varlock 1Password plugin linked in discussion.

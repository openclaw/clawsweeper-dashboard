## Summary

Keep open: current main and v2026.6.11 still fail gateway startup when required SecretRef activation fails, and exec provider failures still propagate without startup backoff or rate-limit-aware handling. The Varlock 1Password plugin linked in discussion is useful batching/caching workaround context, but it does not resolve OpenClaw core's startup SecretRef failure policy.

## What This Changes

Request gateway SecretRef startup handling that avoids supervisor restart loops repeatedly executing 1Password exec providers and exhausting account-wide rate limits.

## Best Possible Solution

Adopt an owner-approved generic startup SecretRef failure policy that bounds repeated external provider calls, keeps fail-closed credential safety visible, and documents or delegates backend-specific batching/caching through resolvers or plugins.

- **Generic bounded startup policy (recommended):** Add a core-owned bounded retry/backoff or degraded-startup policy for required SecretRef activation failures, with tests and docs that avoid 1Password-specific behavior.
- **Resolver/plugin delegation plus docs:** Keep startup fail-fast in core and document supervisor restart limits plus external resolver batching/caching, such as Varlock, as the supported mitigation.
- **Configurable retry surface:** Add an explicit SecretRef retry policy or provider option, accepting the added config and upgrade-safety burden.

## Reproduction Assessment

Yes at source level: current main still throws a fatal startup error when required SecretRef preparation fails, and exec provider failures propagate into that path. I did not live-reproduce launchd plus 1Password quota exhaustion.

## Solution Assessment

Unclear until maintainers choose the startup policy. A bounded generic startup retry or degraded-startup strategy is plausible, while the requested retryPolicy config, circuit breaker, persistent cache, and provider-specific rate-limit awareness have different compatibility and security tradeoffs.

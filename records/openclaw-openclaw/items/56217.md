## Summary

Keep open: current main and v2026.6.11 still fail fast on startup SecretRef resolution errors, and exec provider failures still propagate without rate-limit-aware startup backoff. The Varlock 1Password plugin linked in discussion is useful external batching/caching context, and related duplicate reports now point back here, so this remains the canonical core policy tracker.

## What This Changes

The issue requests a safer generic SecretRef startup failure policy so exec-backed providers such as 1Password do not get hammered by supervisor restart loops.

## Best Possible Solution

Keep this as the canonical tracker for generic startup SecretRef failure policy, with backend-specific batching/caching delegated to plugin or resolver integrations when current seams are sufficient.

## Reproduction Assessment

Yes at source level: current main throws on startup SecretRef activation failure, tests assert the fatal wrapper, and v2026.6.11 has the same path. I did not live-run launchd plus 1Password quota exhaustion.

## Solution Assessment

Unclear until maintainers choose the startup policy. A generic bounded startup retry or degraded-startup strategy is plausible, but provider-specific 1Password handling or a new retryPolicy config knob should not be automatic without security/product approval.

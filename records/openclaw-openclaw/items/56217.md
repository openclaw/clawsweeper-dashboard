## Summary

Keep open: current main and v2026.6.11 still fail gateway startup when required SecretRef activation fails, and exec provider failures still propagate without startup backoff, circuit breaking, or rate-limit-aware behavior. The Varlock 1Password plugin linked in discussion is useful batching/caching workaround context, but it does not resolve OpenClaw core's startup failure policy.

## What This Changes

The issue requests startup backoff, circuit breaking, batching, or rate-limit-aware handling for exec-backed SecretRef provider failures that can be amplified by supervisor restarts.

## Best Possible Solution

Keep this as the canonical tracker for a generic startup SecretRef failure policy, while backend-specific batching or caching can remain external/plugin-owned when current seams are sufficient.

## Reproduction Assessment

Yes at source level for the fatal startup path: current main still resolves active SecretRefs during startup and throws on activation failure. No live launchd/systemd plus 1Password quota-exhaustion loop was reproduced here.

## Solution Assessment

Unclear until maintainers choose the startup policy. A bounded generic startup retry or degraded-startup strategy is plausible, but provider-specific `op` handling and a new retryPolicy config surface need security/product direction.

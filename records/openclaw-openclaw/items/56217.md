## Summary

Keep open: current main and v2026.6.11 still fail gateway startup when required SecretRef activation fails, and exec provider failures still propagate without startup backoff, circuit breaking, or rate-limit-aware behavior. The Varlock 1Password plugin linked in discussion is useful batching/caching workaround context, but it does not resolve OpenClaw core's startup failure policy.

## What This Changes

The issue requests safer gateway SecretRef startup behavior so failing 1Password-backed exec providers do not get repeatedly invoked under supervisor restarts until account-wide limits are exhausted.

## Best Possible Solution

Keep this as the canonical tracker while maintainers choose a generic startup SecretRef failure policy; backend-specific batching or caching should stay in resolver plugins or docs unless core APIs are missing.

## Reproduction Assessment

Yes at source level: current main still throws a fatal startup error when required SecretRef preparation fails, and exec provider failures propagate directly into that path. I did not live-reproduce the launchd plus 1Password quota exhaustion loop.

## Solution Assessment

Unclear until maintainer policy is chosen. A bounded generic startup retry or degraded-startup strategy is plausible, but retry policy, circuit breaker, batching, and rate-limit awareness carry different security and compatibility tradeoffs.

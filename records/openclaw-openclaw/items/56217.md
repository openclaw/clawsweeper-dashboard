## Summary

Keep open: current main and v2026.6.11 still eagerly resolve active SecretRefs and fail fast on startup when exec secret resolution fails, so the reported supervisor restart-loop/rate-limit amplification is not implemented away. The Varlock 1Password plugin and the existing exec batching/pluginIntegration path are useful workaround context, but they do not settle the generic OpenClaw startup failure policy; the open fork PR is conflicting and not a safe canonical fix.

## What This Changes

The issue asks OpenClaw to prevent exec-backed SecretRef startup failures from repeatedly invoking 1Password under launchd/systemd restart loops, using backoff, circuit breaking, batching, or rate-limit-aware behavior.

## Best Possible Solution

Adopt a maintainer-approved, provider-agnostic startup SecretRef failure policy in core, with backend-specific batching and caching left to resolver plugins or ClawHub integrations when current seams are sufficient.

Options:

- **Generic bounded startup protection (recommended):** Add a core-owned, provider-agnostic startup retry/backoff or supervisor-storm mitigation for active SecretRef resolution, with tests and docs that avoid 1Password-specific policy in core.
- **Document external resolver caching only:** Keep runtime fail-fast semantics and steer users to Varlock or a custom batched/caching exec resolver plus supervisor restart guidance.
- **Adopt provider-specific handling:** Special-case 1Password errors or `op` invocation behavior in core, accepting tighter coupling to a third-party credential tool.

## Reproduction Assessment

Yes at source level: startup errors from required SecretRef activation still throw a fatal startup error, and exec provider failures propagate into that path. I did not run a live launchd plus 1Password quota reproduction.

## Solution Assessment

Unclear until maintainers choose the startup failure policy; generic bounded retry or degraded-startup handling is plausible, while configurable retry policy, circuit breaking, batching, and provider-specific rate-limit handling have different security and compatibility tradeoffs.

## Summary

Keep open: current main and v2026.6.11 still eagerly resolve active SecretRefs during gateway startup and convert startup secret-resolution failures into fatal startup errors, while exec-provider timeout/nonzero-exit failures propagate without startup backoff, circuit breaking, or rate-limit-aware behavior. The Varlock 1Password plugin linked in discussion is useful batching/caching workaround context, and the open fork PR is a candidate implementation, but neither resolves the OpenClaw core startup failure policy yet.

## What This Changes

The issue asks OpenClaw to prevent exec/1Password secret-provider startup failures from turning supervised gateway restarts into rate-limit-exhausting crash loops.

## Best Possible Solution

Keep this issue as the canonical tracker for a generic OpenClaw startup SecretRef failure policy that prevents supervised restart amplification while preserving fail-closed credential semantics; backend-specific batching or caching can remain plugin/external-resolver owned when current seams are sufficient.

Question: What startup failure policy should OpenClaw own when active exec-backed SecretRefs fail under a supervised gateway service?

Rationale: Automation should not choose between fail-fast security, degraded/unready availability, retry timing, circuit breaking, provider-specific rate-limit detection, or new config surface without maintainer security intent.

Likely owner: joshavant

Owner reason: The provider-based external secrets and runtime SecretRef activation history most directly maps to the policy decision.

Owner confidence: high

Options:

- **Bounded generic startup guard (recommended):** Add a provider-agnostic startup guard that retries transient SecretRef failures with bounded backoff and then stops repeated external provider calls while surfacing a clear local recovery path.
- **Document supervisor limits only:** Keep runtime fail-fast semantics unchanged and document launchd/systemd restart-throttling plus external caching resolver guidance for quota-sensitive secret providers.
- **Provider/plugin-owned caching first:** Route 1Password batching/caching to ClawHub or external resolver plugins and only add core APIs if those implementations expose a missing OpenClaw seam.

## Solution Assessment

Unclear until maintainers choose the startup security policy. A generic startup SecretRef failure guard is the likely maintainable direction, while the requested retryPolicy config, circuit breaker, batching, and rate-limit awareness should not all be added as one unreviewed config surface.

## Summary

Keep open: current main and v2026.6.11 still eagerly resolve active SecretRefs and fail gateway startup on required secret-provider errors, so the reported supervisor restart-loop/rate-limit amplification is not implemented away. The Varlock 1Password plugin linked in discussion is useful batching/caching workaround context, but it does not resolve OpenClaw core's startup failure policy, and the issue remains the canonical tracker while linked backoff PR attempts are unmerged or not mergeable.

## What This Changes

The issue requests startup backoff, circuit breaking, batching, or rate-limit-aware handling so exec-backed 1Password SecretRef failures do not crash-loop the gateway and exhaust account-wide limits.

## Best Possible Solution

Ship an owner-approved generic startup SecretRef failure policy that limits supervisor restart-storm amplification while leaving backend-specific batching and caching to resolver plugins or external tools such as the linked Varlock 1Password plugin.

## Summary

Keep open: current main and v2026.6.11 still fail fast when required startup SecretRef resolution fails, and exec provider errors still propagate without retry/backoff or rate-limit-aware behavior; the Varlock 1Password plugin linked in discussion is useful external batching/caching workaround context, but it does not close the OpenClaw gateway startup policy gap.

## What This Changes

The issue asks OpenClaw to prevent exec/1Password SecretRef startup failures from crash-looping under process supervisors and exhausting provider rate limits.

## Best Possible Solution

Keep this as the canonical tracker while maintainers choose a generic startup SecretRef failure policy; backend-specific batching or caching should stay in plugins/ClawHub unless a core API gap is proven.

## Reproduction Assessment

Yes at source level: startup activation still throws a fatal startup error when required SecretRef resolution fails, and exec provider failures propagate from the resolver. I did not live-run launchd plus 1Password quota exhaustion.

## Solution Assessment

Unclear until maintainers choose the startup failure policy. A generic bounded retry/backoff or degraded-startup design is plausible, but retryPolicy, circuit breaker, batching, and rate-limit awareness each carry different security and compatibility tradeoffs.

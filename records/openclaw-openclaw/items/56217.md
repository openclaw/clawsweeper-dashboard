## Summary

Keep open: current main and v2026.6.11 still eagerly resolve active exec-backed SecretRefs during startup, and startup failures still become fatal errors that a supervisor can amplify into repeated provider calls. The Varlock 1Password plugin linked in discussion is useful batching/caching workaround context, but the OpenClaw startup failure policy remains unresolved.

## What This Changes

The issue requests startup retry/backoff, circuit-breaker, batching, and rate-limit mitigation for exec-backed SecretRef failures that can restart-loop under launchd or systemd.

## Best Possible Solution

Adopt a maintainer-approved generic startup SecretRef failure policy, likely bounded in-process retry/backoff before the existing fail-fast outcome, plus supervisor restart-storm docs and plugin/resolver guidance for backend-specific batching or caching.

Question: What startup policy should OpenClaw use when required exec-backed SecretRefs fail under a supervised gateway restart loop?

Rationale: Retrying credential providers protects availability but can increase side-effecting secret-provider traffic, while degraded startup or circuit breaking changes fail-closed security semantics for required credentials.

Likely owner: joshavant

Owner confidence: high

Options:

- **Bounded retry, then fail fast (recommended):** Add a small generic startup retry/backoff path with clear logs and keep required SecretRefs fail-closed after retries are exhausted.
- **Degraded startup mode:** Keep the gateway online with affected credential surfaces unavailable, accepting a larger security and compatibility decision around required secrets.
- **External resolver guidance only:** Do not change core startup behavior; document supervisor throttling and recommend batched/cached resolvers such as the linked Varlock 1Password plugin.

## Solution Assessment

Unclear until maintainers choose the startup policy. A bounded generic startup retry before the existing fail-fast outcome looks safer than a new retryPolicy config, persistent cache, or 1Password-specific core behavior, but that is still a security/product decision.

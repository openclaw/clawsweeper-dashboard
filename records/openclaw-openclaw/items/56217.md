## Summary

Keep open: current main and the latest release still eagerly resolve required SecretRefs, fail gateway startup on secret-provider errors, and have no startup retry, circuit breaker, or rate-limit-aware handling. The Varlock 1Password plugin linked in discussion is useful external workaround context, but it does not resolve OpenClaw core's supervised startup failure policy.

## What This Changes

The issue reports that exec-based SecretRef failures during supervised gateway startup can crash-loop and amplify 1Password service-account rate-limit exhaustion.

## Best Possible Solution

Keep this as the canonical tracker for a generic startup SecretRef failure policy in `src/gateway/server-startup-config.ts`; backend-specific batching/caching can remain in resolver plugins such as the linked Varlock 1Password plugin unless core API gaps are proven.

- **External resolver/plugin handoff:** Keep core startup fail-fast and steer rate-limit/caching behavior to ClawHub resolver plugins such as Varlock, accepting that supervised core startup can still amplify provider failures.

Unclear until maintainers choose the startup policy. A focused generic startup retry/degrade strategy is more maintainable than provider-specific `op` logic or reviving the stale old `server.impl.ts` PR as-is.

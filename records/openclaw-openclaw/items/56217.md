## Summary

Keep open: current main and v2026.6.11 still eagerly resolve active SecretRefs and fail gateway startup when exec-backed secret resolution fails. The closed upstream PR was superseded, the open fork PR is not an upstream landing path, and the linked Varlock 1Password plugin is useful workaround context but does not settle OpenClaw core's startup failure policy.

## What This Changes

The issue asks OpenClaw to prevent supervised gateway restart loops from repeatedly invoking exec-backed SecretRef providers and exhausting 1Password service-account rate limits.

## Best Possible Solution

Keep this as the canonical tracker for a maintainer-approved generic startup SecretRef retry/degrade/cooldown policy; keep backend-specific batching and caching in resolver plugins or ClawHub unless a missing core API is proven.

## Maintainer Decision

Kind: security_boundary

Question: What startup SecretRef failure policy should OpenClaw own for exec-backed external secrets under supervised gateway restarts?

Rationale: Changing fail-fast startup behavior can either reduce provider rate-limit amplification or weaken credential fail-closed guarantees, and adding retry/config/circuit-breaker behavior changes a security-sensitive startup contract.

Likely owner: joshavant

Owner reason: The feature-history trail ties joshavant most directly to the external secrets runtime and eager gateway activation design that this policy would change.

Owner confidence: high

Options:

- **Generic guarded startup policy (recommended):** Add a core-owned bounded startup retry/degrade/cooldown strategy with operator-visible diagnostics and focused live proof, while leaving backend batching and caching to resolver plugins.
- **Configurable retry policy:** Add `secrets.retryPolicy` or per-provider retry knobs, accepting the additional config, docs, migration, and upgrade-review surface.
- **Keep fail-fast plus docs:** Keep current fail-fast semantics and document launchd/systemd restart limits plus external caching resolver plugins as the supported mitigation.

## Reproduction Assessment

Yes at source level: current main eagerly resolves active SecretRefs during startup and throws on startup activation failure, which a supervisor can restart into repeatedly. I did not live-reproduce macOS launchd plus 1Password quota exhaustion.

## Solution Assessment

Unclear until maintainers choose the startup policy. A bounded generic startup retry/degrade policy is more maintainable than a 1Password-specific core workaround, while a new `secrets.retryPolicy` config surface needs explicit approval under the repo config bar.

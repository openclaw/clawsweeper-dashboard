## Summary

Keep open: current main and v2026.6.11 still eagerly resolve active SecretRefs during gateway startup and still fail startup on required secret activation errors, so the restart-loop/rate-limit problem remains. The Varlock 1Password plugin linked in discussion is useful external batching/caching workaround context, but it does not resolve OpenClaw core's startup failure policy.

## What This Changes

The issue requests that gateway SecretRef/exec-provider startup failures avoid crash-loop amplification into 1Password service-account rate-limit exhaustion.

## Best Possible Solution

Keep this as the canonical tracker for a generic startup SecretRef failure policy, while backend-specific batching or caching remains external/plugin-owned when current seams are sufficient.

## Reproduction Assessment

Yes at source level: current main eagerly resolves active SecretRefs during startup and throws on startup activation failure. I did not live-reproduce launchd plus 1Password quota exhaustion.

## Solution Assessment

Unclear until maintainers choose the startup policy. A bounded generic startup retry or degraded-startup strategy is plausible, but the requested retryPolicy config, circuit breaker, batching, and rate-limit awareness have different compatibility and security tradeoffs.

## Summary

Keep open: current main and the latest release still eagerly resolve active SecretRefs during gateway startup, fail startup on required secret resolution errors, and propagate exec-provider timeout/nonzero-exit failures without startup backoff, circuit breaking, or rate-limit-aware handling.

## What This Changes

Request to prevent exec-backed SecretRef startup failures from repeatedly invoking 1Password under process-manager restarts by adding backoff, circuit-breaker, batching, or rate-limit handling.

## Best Possible Solution

Keep this as the canonical tracker and define an owner-approved generic SecretRef startup failure policy that limits supervisor restart amplification without adding 1Password-specific core behavior; backend batching/caching should stay in resolver plugins when current pluginIntegration seams are sufficient.

Rationale: Changing this path affects credential-provider execution, gateway startup availability, fail-closed security behavior, and existing operator expectations; automation should not choose those tradeoffs from the issue text alone.

Likely owner: joshavant

Owner confidence: high

Options:

- **Generic bounded startup policy (recommended):** Add an owner-approved generic retry/backoff or circuit-breaker policy for startup SecretRef resolution, keep fail-closed semantics after the bound, and document supervisor restart guidance.
- **Degraded startup semantics:** Keep the gateway online when only non-required credential surfaces fail, but require a broader design for which SecretRefs are startup-critical and how operators see disabled providers.
- **Docs and plugin resolver path:** Keep runtime fail-fast behavior and direct users toward supervisor StartLimit settings plus ClawHub/plugin-backed caching resolvers for external vaults.

## Reproduction Assessment

Yes at source level: current main still eagerly resolves active SecretRefs and throws a fatal startup error when required secret preparation fails. I did not live-reproduce launchd plus 1Password quota exhaustion.

## Solution Assessment

Unclear until maintainers choose the startup policy. A simple retry-only patch is only a partial mitigation for supervisor restart storms, while persistent throttling, degraded startup, and provider-specific handling need explicit security/product direction.

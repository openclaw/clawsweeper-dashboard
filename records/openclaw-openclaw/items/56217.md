## Summary

Keep open: current main and the latest release still fail gateway startup when required SecretRef activation fails, and exec providers still have timeout/batching but no startup backoff, circuit breaker, or rate-limit-aware retry policy. The Varlock 1Password plugin linked in discussion is useful batching/caching workaround context, but it does not resolve OpenClaw core's startup restart-storm policy.

## What This Changes

Requests gateway startup protections against repeated exec/1Password SecretRef resolution failures so supervisor restarts do not exhaust provider rate limits.

## Best Possible Solution

Adopt a maintainer-approved core startup policy that reduces supervisor restart-storm provider calls, preferably with bounded internal backoff/circuit behavior plus docs and regression coverage, without adding broad config unless the policy decision requires it.

## Reproduction Assessment

Source-reproducible but not live-reproduced: current startup activation still throws on required SecretRef failure, which a supervisor can repeatedly restart. I did not run a live 1Password quota exhaustion scenario.

## Solution Assessment

Unclear as an implementation shape: bounded startup backoff is plausible, but the suggested retryPolicy/circuit/cache design needs maintainer security/product direction because current docs intentionally make startup fail-fast.

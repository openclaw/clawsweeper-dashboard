## Summary

Keep open: current main and v2026.6.11 still implement fail-fast startup SecretRef activation without generic startup backoff, circuit breaking, or rate-limit-aware behavior. The Varlock 1Password plugin linked in discussion is useful batching/caching workaround context, but it does not resolve OpenClaw core's supervised startup failure policy.

## What This Changes

The issue reports gateway startup crash loops from repeated exec-based SecretRef resolution failures exhausting 1Password service-account rate limits.

## Best Possible Solution

Keep this as the canonical tracker for a generic startup SecretRef failure policy; backend-specific batching/caching can stay in external resolvers or plugins when current exec/plugin seams are sufficient.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should gateway startup keep failing closed on required SecretRef resolution failures, add a bounded in-process retry/backoff policy, or introduce a degraded-startup/circuit-breaker mode for external exec secret providers?

Rationale: The source-level problem is clear, but the fix changes security and availability semantics for required credentials and could either reduce crash-loop amplification or mask credential failures too long.

Likely owner: joshavant

Owner reason: The strongest history trail for eager SecretRef activation and reload degradation behavior points to this contributor.

Owner confidence: high

Options:

- **Bounded generic startup retry (recommended):** Add a small default retry/backoff around startup SecretRef preparation, keep final failure fail-closed, and document that provider-specific caching belongs in resolvers/plugins.
- **Explicit degraded-startup policy:** Allow startup to remain online with unavailable SecretRefs only after a maintainer-approved policy defines which surfaces may degrade and how operators are alerted.
- **External resolver/plugin only:** Leave core fail-fast behavior unchanged and document resolver-level caching/batching such as Varlock for quota-sensitive providers.

## Reproduction Assessment

Yes, at source level: current main still throws a fatal startup error when required SecretRef preparation fails, and exec provider failures propagate into that path. I did not live-reproduce launchd plus 1Password quota exhaustion.

## Solution Assessment

Unclear until maintainers choose the startup policy. A bounded generic startup retry is the best default-looking direction, but the requested retryPolicy config, circuit breaker, batching, and rate-limit awareness have different compatibility and security tradeoffs.

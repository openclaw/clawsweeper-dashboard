## Summary

Keep open: current main and v2026.6.11 still fail gateway startup when required SecretRef activation fails, and exec provider failures still propagate without startup backoff, circuit breaking, or rate-limit-aware handling. The Varlock 1Password plugin linked in discussion is useful batching/caching workaround context, but it does not resolve OpenClaw core's startup failure policy.

## What This Changes

The issue requests safer gateway startup behavior when exec-based SecretRef provider failures can repeat under launchd/systemd and exhaust 1Password service-account rate limits.

## Best Possible Solution

Keep this as the canonical tracker for a generic startup SecretRef failure policy, while backend-specific batching/caching remains external or plugin-owned when current seams are sufficient.

Kind: product_direction

Question: What startup SecretRef failure policy should OpenClaw use when active exec-backed providers fail under a service supervisor?

Rationale: Current code intentionally fails closed for active SecretRefs at startup, but supervisor restarts can amplify side-effecting credential-provider calls; choosing retry, degraded boot, or circuit-break behavior changes security and operator semantics.

Likely owner: joshavant

Owner reason: The deepest concrete provenance for the SecretRef provider and eager runtime snapshot behavior points to this owner trail.

Owner confidence: high

Options:

- **Define generic guarded startup policy (recommended):** Adopt a bounded, provider-agnostic startup retry/degraded-mode policy with clear operator diagnostics and tests for exec failures without adding 1Password-specific behavior.
- **Document supervisor mitigation only:** Keep fail-fast startup semantics and document launchd/systemd restart limits plus batchable resolver patterns as the supported mitigation.
- **Add configurable retry surface:** Introduce a new `secrets` retry/circuit-breaker config, accepting the compatibility and schema surface cost with doctor/docs/tests.

## Reproduction Assessment

Yes at source level: current main still wraps required startup SecretRef activation failures as fatal startup errors, and exec provider failures propagate into that path. I did not live-reproduce launchd plus 1Password quota exhaustion.

## Solution Assessment

Unclear until maintainers choose the startup policy. A bounded generic startup retry/degraded-start strategy is plausible, but the requested retryPolicy config, circuit breaker, batching, and rate-limit awareness have different compatibility and security tradeoffs.

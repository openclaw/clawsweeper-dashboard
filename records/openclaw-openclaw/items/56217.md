## Summary

Keep open: current main and v2026.6.11 still eagerly resolve active exec SecretRefs during gateway startup and convert failures into fatal startup errors. Existing batching only helps within one configured provider, while the documented 1Password shape still models one provider per `op read`; the Varlock 1Password plugin is useful workaround context, not an OpenClaw startup-policy fix.

## What This Changes

The issue asks OpenClaw to prevent exec secret-provider startup failures from crash-looping and exhausting 1Password rate limits.

## Best Possible Solution

Keep this as the canonical core tracker for a generic startup SecretRef failure policy; backend-specific batching or caching can stay in ClawHub/plugin resolver work unless maintainers decide core needs a new API.

- **Define bounded core startup policy (recommended):** Add a generic bounded startup retry/backoff or circuit policy for active SecretRef failures, with operator-visible logs/docs and no 1Password-specific core behavior unless a generic contract requires it.
- **Keep fail-fast and document mitigation:** Preserve the current fail-closed startup contract and document supervisor start limits plus external caching/batching resolver plugins such as Varlock for rate-limit-sensitive deployments.

## Summary

Keep open: current main and v2026.6.11 still eagerly resolve active SecretRefs during startup and fail fast on provider errors; exec providers have timeout/no-output bounds and provider-level batching, but no startup backoff, circuit breaker, rate-limit-aware policy, or cross-restart protection for side-effecting secret providers.

## What This Changes

Requests a Gateway SecretRef startup policy that prevents supervisor-amplified exec provider retries from exhausting 1Password service-account rate limits.

## Best Possible Solution

Adopt an owner-approved generic SecretRef startup failure policy that bounds side-effecting exec retries under supervisor restarts, preserves clear fail-closed behavior for permanent credential failures, and documents external batching/caching resolvers such as Varlock as optional workarounds rather than the core fix.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What startup failure policy should OpenClaw own when active SecretRef exec providers fail under launchd/systemd restart loops?

Rationale: The current behavior is documented fail-fast startup, but the report shows side-effecting credential-provider retries can exhaust external account-wide secret access; changing this requires choosing the security boundary between fail-closed startup, bounded retry/degrade behavior, provider-specific rate-limit handling, and external resolver responsibility.

Likely owner: joshavant

Owner reason: The core behavior appears to originate in the SecretRef provider and eager runtime activation work authored by joshavant, so they are the best history-backed owner for the policy tradeoff.

Owner confidence: medium

Options:

- **Generic bounded startup policy (recommended):** Add a small generic startup retry/backoff or degrade-with-clear-diagnostic policy for active SecretRef provider failures, while keeping provider-specific batching and caching in resolver plugins or wrappers.
- **External resolver guidance only:** Keep core fail-fast semantics and document supervisor restart limits plus third-party batching/caching resolvers such as Varlock for 1Password-heavy deployments.
- **Configurable retry/circuit breaker:** Add a new `secrets` retry/circuit policy surface with upgrade-safe docs, defaults, and tests, accepting the added configuration and compatibility burden.

## Reproduction Assessment

Yes at source level: current main still resolves active SecretRefs eagerly and throws a fatal startup error when required resolution fails, and exec provider failures propagate immediately. A live launchd/systemd plus 1Password quota exhaustion reproduction has not been run here.

## Solution Assessment

Unclear until maintainers choose the policy. A bounded generic startup retry/degrade policy is the most maintainable direction I can support from the code, while provider-specific `op` hardcoding or a new retry config surface needs explicit product/security approval.

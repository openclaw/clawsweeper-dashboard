## Summary

Keep open: current main still renders a shared human-readable status card without a visibility policy, and the related multi-agent privacy report makes this a product/security-boundary decision rather than a routine clutter toggle. ([codefactor.io](https://www.codefactor.io/repository/github/openclaw/openclaw/source/main/src/status/status-message.ts))

## What This Changes

Requests a configuration option to suppress or replace the human-readable status card returned by chat `/status` and the `session_status` tool.

## Best Possible Solution

Define one shared per-agent status visibility policy, defaulting to today's output, that filters sensitive sections before both chat and tool serialization and includes schema, help, public docs, and focused command/tool tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What status-output contract should OpenClaw support for chat `/status` and `session_status`: whole-card suppression, per-agent section visibility, or no new customization?

Rationale: The choice determines whether an explicit command may return no visible reply, whether structured details remain visible to agents, and how provider usage or billing metadata is isolated in multi-agent deployments.

Likely owner: steipete

Owner reason: steipete is connected to both the relevant status-path commit and the issue's prior product-oriented review.

Owner confidence: medium

Options:

- **Per-agent section policy (recommended):** Add a shared allowlist or section-visibility policy applied before both rendered text and structured tool details, preserving current output by default.
- **Whole-card boolean:** Add the requested boolean and define whether disabled commands return no reply, a minimal acknowledgement, or structured output.
- **Keep current contract:** Reject new configuration and retain `/status` and `session_status` as explicitly requested diagnostic-card surfaces.

## Reproduction Assessment

Yes at source level: invoke chat `/status` or `session_status` on current main and the shared renderer constructs the full card without a visibility branch; no live runtime execution was performed. ([codefactor.io](https://www.codefactor.io/repository/github/openclaw/openclaw/source/main/src/status/status-message.ts))

## Solution Assessment

No, the proposed global boolean and JSON-only fallback are not yet the best solution because structured output may retain the privacy problem; a shared per-agent section policy is safer and more maintainable.

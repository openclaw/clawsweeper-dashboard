## Summary

Keep open: current main and v2026.6.11 still present `/status` and `session_status` as rendered status-card surfaces, with no documented visibility control. This remains the canonical request, but least-disclosure semantics and configuration ownership require maintainer judgment.

## What This Changes

Add a configuration control that suppresses the chat `/status` and `session_status` status card while preserving current rendering by default.

## Best Possible Solution

Define one canonical per-agent status-visibility policy that preserves current owner-facing defaults, supports least-disclosure for shared routes, and aligns schema, help, docs, command/tool behavior, and focused tests.

Options:

- **Per-Agent Least Disclosure (recommended):** Add a per-agent field allowlist or visibility policy, preserving the full owner-facing status card by default while suppressing selected details on configured shared agents.
- **Global Card Toggle:** Add one global boolean that replaces or suppresses the complete rendered card across both chat and tool surfaces, accepting reduced flexibility.
- **Keep Trusted-Operator Contract:** Reject a new visibility setting and document that status commands are intended only for authorized trusted operators, with channel allowlists as the supported control.

## Reproduction Assessment

Yes at source and documentation level: invoking authorized chat `/status` or `session_status` produces the documented rendered status output, and no supported suppression control is documented. A live invocation was not performed during this read-only review.

## Solution Assessment

Unclear: a blanket JSON-only toggle is not yet established as the best solution because it may preserve the same disclosure and clutter. A per-agent field-level visibility policy is the safer direction if maintainers accept shared-user least-disclosure as a supported boundary.

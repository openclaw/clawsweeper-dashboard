## Summary

Current main still has no supported way to suppress or redact the shared status card, and the request now represents the canonical product/security decision for both chat `/status` and `session_status`. It should remain open until maintainers choose the intended visibility granularity and configuration owner.

## What This Changes

Add a configuration-controlled way to hide or reduce the rendered session status card returned by chat `/status` and `session_status`.

## Best Possible Solution

Define one typed per-agent status-section visibility policy at the shared renderer boundary, preserve the current card by default, and keep structured tool details distinct from chat-visible text.

Rationale: The choice adds public configuration and determines how operator diagnostics and potentially sensitive provider/session information are exposed in shared-agent use.

Likely owner: steipete

Options:

- **Per-agent field policy (recommended):** Add a typed allowlist or suppression policy at the shared renderer so sensitive sections can be hidden without discarding all diagnostics.
- **Whole-card switch:** Add one inherited boolean that suppresses rendered status text while retaining current behavior as the default.
- **Keep current behavior:** Reject new configuration and explicitly document these status surfaces as operator-visible diagnostics.

## Reproduction Assessment

Yes, at source level. Current main deterministically routes authorized `/status` and `session_status` through the shared rendered-text card with no supported visibility control.

## Solution Assessment

No, the proposed boolean alone is not yet the best complete solution. A shared per-agent section policy better covers both clutter and the consolidated sensitive-field use case without splitting command and tool behavior.

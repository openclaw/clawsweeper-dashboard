## Summary

Current main still unconditionally renders the shared human-readable status card for both chat `/status` and `session_status`; no supported visibility control or structured-only equivalent exists, and the folded privacy use case makes the output scope a product and security-boundary decision rather than a routine configuration patch.

## What This Changes

Add a configurable way to hide or reduce the session status card returned by chat `/status` and the `session_status` tool.

## Best Possible Solution

Define one default-preserving, per-agent status visibility policy that can suppress sensitive sections for chat presentation while keeping a stable structured `session_status` details contract, then align schema, help, public docs, and focused tests across both callers.

Options:

- **Per-Agent Section Policy (recommended):** Add a default-preserving per-agent allowlist or denylist for status sections while retaining structured tool details and applying the same policy consistently to visible text.
- **Whole-Card Format Toggle:** Add a simpler global or agent-default text-versus-structured toggle, accepting less granular privacy control and broader presentation changes.
- **Keep Current Contract:** Reject additional configuration and continue treating the complete human-readable card as the required output of both status surfaces.

## Reproduction Assessment

Yes at source level: an authorized chat `/status` request and a normal `session_status` call both flow through `buildStatusText` and return its rendered text without a visibility branch. No live runtime execution was needed to establish the missing option.

## Solution Assessment

No, the proposed boolean and “JSON only” behavior are not yet the best-defined solution because they combine presentation, structured output, and privacy policy. A default-preserving per-agent section policy with stable structured details is narrower and safer.

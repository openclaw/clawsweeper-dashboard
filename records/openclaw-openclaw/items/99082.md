## Summary

Keep open: current main still has a source-visible path where explicit reset only clears queued/runtime side state, while active visible reply operations remain keyed by session key and can make the fresh post-reset visible turn wait for the stuck-session abort window. The latest release carries the same visible-recovery behavior, and the open related cleanup work does not clearly cover this archived-session visible-reply race.

## What This Changes

The issue reports that `/reset` in Slack multi-agent rooms can leave stale visible-reply work tied to an archived session id, delaying the fresh session acknowledgement and queued replies until stuck-session recovery.

## Best Possible Solution

Add a focused reset/recovery cleanup that releases or rejects visible reply work tied to the archived session id before the fresh session acknowledgement is admitted, with regression coverage for sibling multi-agent room traffic on the same session key.

## Reproduction Assessment

Yes, at source level. Current main rotates explicit reset sessions while only clearing queues/system events, and the active reply registry remains keyed by sessionKey with visible admission waiting on the stuck-session abort window; I did not run a live Slack room reproduction in this read-only pass.

## Solution Assessment

Yes, the best fix is a bounded core reset/recovery cleanup for archived-session reply work, not a channel-specific workaround or a new timeout/config knob. The repair should add regression coverage around reset rotation, reply-run registry state, and visible admission recovery.

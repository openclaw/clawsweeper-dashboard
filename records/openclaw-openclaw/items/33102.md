## Summary

Keep open: current main and the latest release still lack a config-backed TUI delivery default, and the remaining work is a product/config-surface decision rather than a safe automatic cleanup close.

## What This Changes

The issue requests a persistent config default for the TUI `--deliver` flag so users do not need to pass the flag on every invocation.

## Best Possible Solution

Maintainers should choose one canonical UX: approve a documented `tui.deliver`-style config/default path with override tests, or explicitly keep delivery as a per-launch/runtime opt-in and close the request as not planned.

## Reproduction Assessment

Yes, source-reproducible: current main still registers `--deliver` with a false default, forwards `Boolean(opts.deliver)`, and has no `tui.deliver` schema field. I did not run a live TUI session in this read-only review.

## Solution Assessment

Unclear as a final product choice: adding `tui.deliver` is plausible, but repository policy sets a high bar for new config surface and maintainers need to choose it over a default/runtime behavior change.

## Label Justifications

- `P2`: The issue is a normal-priority TUI/config improvement with a clear workaround, but it affects whether replies are delivered visibly by default.
- `impact:message-loss`: The requested setting controls TUI reply delivery, and the current default can suppress visible delivered output unless users remember the flag or toggle.
- `impact:ux-friction`: Users must repeatedly pass `--deliver`, use aliases, or toggle delivery in-product because no persistent default exists.

## Summary

Keep open: current main and the latest stable release still default TUI delivery off and do not expose a `tui.deliver` config default. The stuck-spinner/no-active-run sibling was fixed separately, but this issue remains the canonical product decision for whether TUI delivery should get a persistent config default.

## What This Changes

The issue requests an `openclaw.json` setting to make `openclaw tui --deliver` the default without passing the flag on every run.

## Best Possible Solution

Decide the product shape for a persistent TUI delivery preference, then implement it through the canonical config type, Zod schema, schema help/labels, docs, and CLI override tests.

## Reproduction Assessment

Yes, source-level: current main declares `--deliver` with default `false`, forwards only `Boolean(opts.deliver)`, and has no `tui.deliver` config key in the current config type/schema. I did not run a live TUI session in this read-only cleanup pass.

## Solution Assessment

Unclear until maintainers choose the config contract. The narrow implementation shape is plausible, but the best fix must first settle the public config key and CLI override semantics rather than only copying a closed unmerged PR.

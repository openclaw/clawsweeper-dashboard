## Summary

Keep open: current main and the latest release still default TUI delivery off and expose no persistent config key for that default. The adjacent stuck-spinner and abort behavior was addressed separately, while this issue remains a product-sensitive config/default decision.

## What This Changes

The issue requests a persistent OpenClaw config default for the TUI `--deliver` flag so users do not need to pass it on every `openclaw tui` invocation.

## Best Possible Solution

Make a maintainer decision on TUI delivery policy, then land one focused PR that aligns CLI parsing, config schema/help, docs, TUI settings behavior, and tests, or explicitly document that TUI delivery remains flag-only.

## Reproduction Assessment

Yes, at source level: current main registers `--deliver` with default `false`, passes the parsed boolean into `runTui`, sends chat with `deliverDefault`, and exposes no persistent `tui.deliver`-style config key. I did not run a live TUI session in this read-only cleanup review.

## Solution Assessment

Unclear: a config default is a plausible small solution, but the key shape, default policy, runtime Settings behavior, and `--deliver`/`--no-deliver` override semantics need maintainer agreement before implementation.

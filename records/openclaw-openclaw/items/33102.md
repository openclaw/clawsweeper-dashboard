## Label Justifications

- `P2`: The issue affects TUI reply visibility and default delivery ergonomics but is bounded to one CLI/TUI workflow.
- `impact:message-loss`: With delivery off by default, replies can be produced and stored without being shown in the TUI path the user expected.
- `impact:ux-friction`: Users currently need to remember a flag or in-TUI command rather than setting a persistent preference for this workflow.

## Summary

Keep open: current main and the latest release still default TUI delivery from the CLI flag only, and the existing `tui` config schema has no delivery default. The remaining work is concrete but needs maintainer product approval because it adds or changes a config/default surface.

## What This Changes

The issue requests a persistent OpenClaw config default for `openclaw tui --deliver` so users do not need to pass the flag on every run.

## Best Possible Solution

Make a maintainer decision on the TUI delivery default, then implement it through the existing `tui` config schema with docs and regression coverage for CLI override precedence.

## Reproduction Assessment

Yes. Source inspection shows the CLI still defaults `--deliver` to false, the TUI uses that value for message sends, and the config schema lacks a delivery default; I did not run an interactive TUI repro in this read-only review.

## Solution Assessment

Unclear. Adding a `tui.deliver` config key is a plausible narrow path, but OpenClaw policy treats config/default changes as product-sensitive and maintainers still need to choose the desired default behavior.

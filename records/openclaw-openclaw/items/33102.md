## Summary

Keep open: current main still has only a flag-level TUI delivery default, and the requested persistent `tui.deliver` config surface remains a product/config-contract decision. The later stuck-spinner/abort lifecycle problem was handled separately by a merged TUI fix, but that PR explicitly left this config-default request out of scope.

## What This Changes

The issue requests a persistent OpenClaw config default for `openclaw tui --deliver` so users do not need to pass the flag every launch.

## Best Possible Solution

Make one maintainer-approved canonical contract for persistent TUI delivery defaults, then align schema, CLI precedence, docs, and focused TUI/config tests around that contract.

Question: Should OpenClaw add an opt-in persistent `tui.deliver` config default for TUI launch delivery behavior?

Rationale: The missing capability is clear, but root policy sets a high bar for new config/default surfaces and delivery affects more than presentation, so automation should not choose the permanent product contract alone.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve narrow `tui.deliver` config (recommended):** Add an optional boolean config default with explicit CLI override precedence, schema/help/docs coverage, and tests for config default plus flag override behavior.
- **Keep delivery launch-only:** Close or defer the config request and keep `openclaw tui --deliver` as the explicit opt-in path documented for external delivery.
- **Design session preference instead:** Defer this issue into a broader TUI/session-preferences design if maintainers want persistent UI state without another top-level config default.

## Reproduction Assessment

Yes for the missing capability: source and docs show `--deliver` defaults off and only the launch option feeds TUI delivery, while the strict config schema has no `tui.deliver` field. I did not run a live TUI because the absence of a config path is directly source-verifiable.

## Solution Assessment

Unclear until maintainers choose the product contract. A narrow `tui.deliver` config field is plausible, but the safer end state must explicitly define precedence, docs, and whether persistent delivery belongs in OpenClaw config at all.

## Label Justifications

- `P2`: The remaining issue is a bounded TUI delivery-default improvement with real user friction but no current evidence of a core outage or security/data-loss emergency.
- `impact:message-loss`: Without a default delivery setting, expected provider/channel replies can remain suppressed unless the user remembers the launch flag.
- `impact:ux-friction`: Users must repeat `--deliver` or maintain shell aliases because the product has no persisted TUI delivery preference.

## Summary

Keep open: current main and the latest release still default TUI delivery off and the config schema still lacks a `tui.deliver` default, while the adjacent stuck-spinner bug has already been closed separately.

## What This Changes

The issue requests a persistent config default for TUI `--deliver` so users do not have to pass the flag on every launch.

## Best Possible Solution

Decide whether TUI delivery should be a persisted config default, an in-TUI/session setting, or remain explicit, then implement the chosen current-schema path with docs and focused tests.

## Reproduction Assessment

Yes, source-level. Current main registers `--deliver` with default `false`, passes only the launch option into TUI sends, and the config schema has no `tui.deliver` field.

## Solution Assessment

Unclear. Adding `tui.deliver` is plausible, but because it creates a new config/default surface for provider delivery, maintainers should choose the intended product shape before implementation.

## Label Justifications

- `P2`: The issue is a bounded TUI delivery/default improvement with real user confusion, but it needs product/config judgment rather than emergency handling.
- `impact:message-loss`: With the current default, assistant replies can be produced and stored without appearing in the TUI unless delivery is enabled.
- `impact:ux-friction`: Users must discover and repeat `--deliver` or use an alias because no in-product/config default exists today.

## Summary

Keep open: current main and the latest release still hard-code the TUI delivery default from the CLI flag and do not expose `tui.deliver` in config; the related stuck-spinner bug was closed separately, and the config/default ergonomics remain unresolved.

## What This Changes

The issue requests a persistent TUI config default for `--deliver` so users do not have to pass the flag on every TUI invocation.

## Best Possible Solution

Decide the TUI delivery policy first; if config is accepted, add `tui.deliver` through the canonical config schema/help/docs/tests and use tri-state CLI override behavior while keeping the shipped lifecycle fix separate.

## Reproduction Assessment

Yes, at source level. Current main registers `--deliver` with default `false`, passes only the CLI boolean into `runTui`, and the config schema rejects unknown TUI keys beyond `tui.footer.showRemoteHost`; I did not run a live TUI session.

## Solution Assessment

Unclear as an implementation direction. A `tui.deliver` key is plausible, but the best fix depends on maintainer choice between config default, default flip, settings-row behavior, and explicit `--no-deliver` override semantics.

## Summary

Current main still lacks a persisted TUI delivery default, but the older stuck-spinner/no-visible-reply failure was already fixed separately; this should stay open for maintainer product review because the remaining request adds a config/default surface.

## What This Changes

The issue asks for a configurable default for `openclaw tui --deliver` so users do not need to pass the flag on every TUI invocation.

## Best Possible Solution

Keep the already-shipped TUI-visible reply fix, and have maintainers decide whether explicit provider/channel delivery deserves a persisted TUI default; if accepted, implement the chosen config key with schema/types/docs and focused flag-precedence tests.

## Reproduction Assessment

Yes from source for the remaining request: current main still defaults `--deliver` to false and has no accepted `tui.deliver` or `cli.tui.deliver` config field. The older stuck-spinner/no-visible-reply symptom was separately closed as implemented in the related issue.

## Solution Assessment

Unclear: a persisted default is plausible, but it is not automatically the best fix because OpenClaw policy sets a high bar for new config/default surfaces. Maintainers should first decide whether this belongs under `tui`, `cli.tui`, or an existing preference/session surface and whether external delivery should remain explicit by design.

## Label Justifications

- `P2`: The issue affects TUI reply visibility and repeated user workflow friction, but it has a known `--deliver` workaround and needs product/config direction.
- `impact:message-loss`: The reported behavior is that assistant replies are produced and stored but not shown through the TUI unless delivery is enabled.
- `impact:ux-friction`: Users must repeatedly pass a flag or rely on workarounds, and current docs advertise delivery controls that current source does not expose.

## Summary

Keep open: current main and the latest release still default `openclaw tui --deliver` to off, and the checked config schema only exposes `tui.footer.showRemoteHost`, not a persistent TUI delivery default. The stuck-spinner failure reported in the discussion was closed separately as implemented, but the requested persistent delivery preference remains a config/product decision.

## What This Changes

Request to let `openclaw tui` read a persistent config default for the `--deliver` flag so users do not have to pass it on every run.

## Best Possible Solution

Make a maintainer-approved TUI delivery preference path: either add a canonical persistent default with tri-state CLI override, schema/help/docs/tests, or correct the docs and keep delivery explicitly per invocation/session.

## Reproduction Assessment

Yes, at source level: current main registers `--deliver` with default `false`, forwards only the parsed flag into `runTui`, and has no `tui.deliver` schema/type entry. I did not run a live TUI because this review was read-only.

## Solution Assessment

Unclear as a final implementation path: a config default is plausible, but the best fix needs maintainer choice because OpenClaw has a high config-surface bar and the docs already describe runtime delivery controls that the current TUI code does not implement.

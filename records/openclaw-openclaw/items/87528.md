## Best Possible Solution

Land one canonical fix that sets safe attachment filenames only for non-inline assistant media, keeps previewable media inline, and covers both gateway response headers and WebChat rendering with focused tests.

## Solution Assessment

No. The submitted route-wide attachment header is only a plausible symptom fix; the safer fix should gate disposition by MIME/media kind, use safe filename encoding, and preserve inline previews.

Overall correctness: patch is incorrect

Full review comments:

- **[P1] Keep preview media inline:** `src/gateway/control-ui.ts:606-610`
  - body: This shared endpoint also backs image, audio, and video `src` URLs in WebChat. Setting `attachment` for every successful response can make existing previews download instead of render, so gate the header to document/non-inline media or a dedicated download path.
  - confidence: 0.92
- **[P2] Encode filename* with RFC 5987-safe characters:** `src/gateway/control-ui.ts:610`
  - body: `encodeURIComponent` leaves delimiter-sensitive characters such as apostrophes unescaped after `UTF-8''`, and the quoted `filename` fallback should stay ASCII-safe. Use a small RFC 5987-safe encoder plus a clean fallback before interpolating the header.
  - confidence: 0.84

## Label Justifications

- `P2`: The report describes a real Telegram local Bot API workflow break with limited blast radius and no evidence of a global core outage.
- `impact:message-loss`: A stale offset can cause local Bot API inbound messages to be skipped before they reach agent session dispatch.
- `impact:crash-loop`: The reported `deleteWebhook` `400: Logged out` path still maps to a fatal non-network startup error that can restart the Telegram account loop.

## Summary

Keep open. Current main and v2026.6.11 still persist Telegram update offsets by account and bot token rather than by `apiRoot`, then pass that watermark into the configured local `getUpdates` endpoint. `deleteWebhook` now routes through the configured bot client, but a non-network `400: Logged out` remains fatal during startup, so the local Bot API migration problem is not fully implemented.

## What This Changes

The issue asks OpenClaw to make Telegram local Bot API `apiRoot` migration safe by dispatching inbound updates, resetting or partitioning offsets when endpoints change, and avoiding `deleteWebhook` crash loops during `logOut` cooldown.

## Best Possible Solution

Keep this as the canonical Telegram local Bot API migration bug until a maintainer-approved fix scopes or migrates update offsets by endpoint identity, handles the expected `logOut` cooldown startup state, and proves inbound dispatch against a live local Bot API server.

## Reproduction Assessment

Yes for the source-level offset and startup-failure paths, but not as a live local Bot API run. Current code reads an account/token-scoped persisted offset and passes it into the configured `apiRoot` worker, while non-network `deleteWebhook` failures still throw during startup.

## Solution Assessment

Unclear as an implementation path because the safest endpoint-switch behavior is a product policy choice. The best fix should be a narrow Telegram-owned migration/recovery path with live local Bot API proof, not a generic runtime fallback.

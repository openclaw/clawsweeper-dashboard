## Label Justifications

- `P2`: The issue affects a real Telegram local Bot API delivery/startup path, but the blast radius is limited to users configuring a custom Telegram API root.
- `impact:message-loss`: The report describes Telegram updates reaching raw polling/logging but not dispatching to agent sessions after an endpoint switch.
- `impact:crash-loop`: The report includes repeated Telegram channel restarts when `deleteWebhook` fails during local Bot API migration.

## Summary

Keep open. Current main and the latest release still store Telegram polling offsets by account/token rather than `apiRoot`, pass that stored watermark into the configured local `getUpdates` endpoint, and only continue past `deleteWebhook` failures when they look like recoverable network errors.

## What This Changes

Handle Telegram local Bot API `apiRoot` migrations so inbound updates dispatch, stale official-API offsets do not block local `getUpdates`, and `deleteWebhook` during migration does not crash-loop the channel.

## Best Possible Solution

Keep this as the canonical local Bot API migration tracker; define endpoint-switch offset/reset policy and narrow `400: Logged out` handling, then prove inbound dispatch and outbound replies against a live local Bot API server.

## Reproduction Assessment

No high-confidence live reproduction was established. Current source still shows the stale persisted-offset and non-network `deleteWebhook` paths, but a live self-hosted Bot API server migration is needed to prove the full raw-update-to-agent-dispatch failure end to end.

## Solution Assessment

Unclear. The likely fix belongs in Telegram polling state and startup cleanup, but maintainers need to choose endpoint-scoped offsets versus reset/doctor behavior and the exact safe scope for tolerating `400: Logged out`.

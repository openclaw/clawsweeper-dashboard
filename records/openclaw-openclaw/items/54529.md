## Summary

Keep open. Current main and the latest release still key Telegram update offsets by account/token rather than configured API root, pass that persisted watermark into local Bot API `getUpdates`, and only continue past `deleteWebhook` failures for recoverable network errors; the exact raw-update-to-agent-dispatch drop still needs live local Bot API proof.

## What This Changes

The issue reports that Telegram local Bot API `apiRoot` polling receives raw updates but drops inbound dispatch, keeps incompatible update offsets across endpoint switches, and crash-loops on `deleteWebhook` during logout cooldown.

## Best Possible Solution

Keep this as the canonical local Bot API migration tracker; define endpoint-switch offset/reset policy and narrow `400: Logged out` cleanup handling, then prove inbound dispatch and reply delivery against a live local Bot API server.

## Reproduction Assessment

No high-confidence live reproduction was established. The stale-offset and non-network `deleteWebhook` branches are source-reproducible on current main, but the full raw-update-to-agent-dispatch drop needs a live self-hosted Bot API run.

## Solution Assessment

Unclear. The likely fix belongs in Telegram polling state and startup cleanup, but maintainers need to choose endpoint-scoped offsets versus reset/doctor behavior and the exact safe scope for tolerating `400: Logged out`.

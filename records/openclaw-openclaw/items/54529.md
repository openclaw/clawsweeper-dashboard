## Summary

Keep open. Current main still leaves the central apiRoot migration problem unresolved: Telegram update offsets are scoped by account and token identity, not the configured Bot API root, and non-network deleteWebhook 400 failures still go through the retry/exit path. The issue is actionable, but persisted offset semantics and logOut-cooldown tolerance need maintainer direction and live local Bot API proof before a fix PR.

## What This Changes

The issue asks Telegram apiRoot local Bot API migrations to dispatch inbound updates, reset or scope update offsets on endpoint change, and avoid a deleteWebhook crash loop during Telegram logOut cooldown.

## Best Possible Solution

Add a Telegram-owned migration or doctor path that resets or scopes offsets when apiRoot changes and narrowly treats confirmed logOut-cooldown cleanup failures as non-fatal, with live local Bot API proof.

Options:

- **Endpoint-aware offset identity (recommended):** Store normalized apiRoot identity with the offset and reset or ignore stale offsets when account, token, or endpoint identity changes, with tests for official-to-local migration.
- **Doctor-only reset:** Keep runtime offset keys account/token-scoped but add a doctor/setup repair that detects apiRoot changes and clears the stale offset before polling.
- **Document manual reset only:** Leave runtime behavior unchanged and document that users must clear the Telegram offset when switching Bot API roots, accepting a higher support burden.

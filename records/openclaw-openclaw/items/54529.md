## Label Justifications

- `P2`: The report affects a real Telegram local Bot API delivery/startup path, but the blast radius is bounded to users configuring a custom Telegram API root.
- `impact:message-loss`: The issue describes Telegram updates being received by polling middleware but not dispatched to agent sessions.
- `impact:crash-loop`: The issue includes repeated Telegram channel restarts when `deleteWebhook` fails during local Bot API migration.

## Summary

Keep open. Current main and the latest release still carry Telegram polling offsets by account/token rather than API root, and startup cleanup still only continues past `deleteWebhook` failures that classify as recoverable network errors, so the local Bot API migration bug is not fully resolved.

## What This Changes

The issue requests reliable Telegram self-hosted Bot API (`apiRoot`) inbound dispatch, endpoint-aware update offset handling, and nonfatal startup behavior during the Bot API `logOut` cooldown.

## Best Possible Solution

Keep this as the canonical local Bot API migration bug; define endpoint-aware offset reset or migration plus a narrow logged-out cleanup policy, then prove inbound dispatch and outbound reply delivery against a live self-hosted Bot API server.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For Telegram local Bot API migrations, should OpenClaw reset or scope the persisted update offset when `apiRoot` changes, and should `400: Logged out` during the Telegram `logOut` cooldown be a narrow nonfatal startup state?

Rationale: This choice changes persisted polling-state semantics and Telegram 4xx startup handling; automation should not choose between runtime reset, doctor migration, manual documentation, or fail-closed auth behavior without maintainer intent and live proof.

Likely owner: vincentkoc

Owner reason: Recent merged work on Telegram isolated ingress spool recovery makes this the closest current owner path for polling-state behavior.

Owner confidence: medium

Options:

- **Endpoint-aware migration with narrow cooldown tolerance (recommended):** Reset or scope the offset when the API root changes and tolerate only the documented `400: Logged out` migration cooldown while preserving fail-closed behavior for other auth errors.
- **Document manual reset only:** Leave runtime state unchanged and document the exact offset cleanup steps required when moving a bot token from official Telegram API to a local Bot API server.
- **Keep current fail-closed behavior:** Preserve the account/token offset and `deleteWebhook` 4xx behavior, accepting that local Bot API migrations remain operator-managed and can require manual recovery.

No high-confidence live reproduction was run in this read-only review. Source inspection supports the stale-offset and non-network `deleteWebhook` paths, but a live self-hosted Bot API migration is still needed to prove the full raw-update-to-dispatch drop on current main.

## Solution Assessment

Unclear. The fix likely belongs in Telegram polling state and startup cleanup, but maintainers need to choose endpoint-scoped offsets versus runtime reset, doctor migration, or manual reset and the exact safe scope for tolerating `400: Logged out`.

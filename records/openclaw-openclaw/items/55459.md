## Summary

Keep open: current main and the latest release still document and execute the 1Password `op read` exec-provider shape without disabling the 1Password CLI cache, and the exact macOS/TCC cache-daemon workaround is not owned by another canonical item.

## What This Changes

The issue asks OpenClaw to prevent or document 1Password CLI cache-daemon hangs for exec SecretRef providers on macOS LaunchAgent setups.

## Best Possible Solution

Add 1Password docs guidance for `--cache=false` or `OP_CACHE=false` using existing exec provider fields, then only add generic runtime or plugin-owned behavior if maintainer/security review chooses that policy boundary.

## Reproduction Assessment

No live high-confidence reproduction was run. Source and docs make the current cache-enabled configuration path reproducible, but the macOS Tahoe/TCC daemon hang still needs live 1Password proof.

## Solution Assessment

Unclear for runtime behavior until maintainers choose the policy boundary. The narrowest maintainable first step is docs using existing `args` or `env`; core auto-detection of `op` is provider-specific and should not be automatic.

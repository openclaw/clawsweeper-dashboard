## Summary

Keep open: current main still documents the 1Password exec-provider example without disabling the 1Password CLI cache, and the runtime still only uses explicitly configured exec args/env, so the exact macOS LaunchAgent cache-daemon workaround remains unresolved.

## What This Changes

The issue asks OpenClaw to prevent or document 1Password CLI cache-daemon hangs for exec SecretRef providers on macOS LaunchAgent installs.

## Best Possible Solution

Document `--cache=false` or `OP_CACHE=false` in the 1Password SecretRef docs using the existing exec `args`/`env` surface, then separately decide whether a plugin/runtime policy should handle provider-specific cache defaults.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Partly: current source and docs reproduce the cache-enabled `op read` shape and fatal startup timeout path, but this review did not live-run macOS Tahoe plus 1Password CLI.

## Solution Assessment

Is this the best way to solve the issue? Unclear for runtime behavior: a docs update using existing `args` or `env` is the narrowest maintainable fix, while provider-specific core auto-detection needs maintainer/security approval.

## Summary

The report is related to the earlier bundle-replacement recovery work, but it identifies a distinct failure mode in the replacement handoff retry path.

## What This Changes

Bound macOS app replacement-handoff retries and add backoff/failure handling so a slow authenticated replacement cannot create an indefinite relaunch-and-kill loop under heavy machine load.

## System Context

The macOS app monitors a signed installed bundle for replacement and starts a trusted successor when the on-disk app changes. The successor reports authenticated readiness through a handoff channel; failure handling then determines whether the old process retries, remains active, or yields to its supervisor.

## Architecture Diagram

flowchart LR
  A[Installed signed macOS app] --> B[Replacement monitor]
  B --> C[Trusted replacement launch]
  C --> D[Authenticated readiness handoff]
  D -->|Ready| E[Old app exits]
  D -->|Timeout or failure| F[Bounded retry and backoff]
  F --> G[Actionable fault or supervisor recovery]

## Best Possible Solution

Make the replacement monitor use a bounded, delayed retry policy with an actionable terminal outcome; keep authentication verification intact and explicitly define whether a verified KeepAlive supervisor restarts the replacement after retry exhaustion.

- **Exit for verified supervisor (recommended):** After bounded retries, stop monitoring and exit only when the deployment contract confirms a KeepAlive supervisor will relaunch the installed replacement.
- **Keep old app running:** After bounded retries, retain the old trusted process and emit a single actionable fault until a later explicit replacement attempt.
- **Support both by deployment mode:** Use the verified supervisor state to choose exit versus retain-old behavior, with a documented fallback for unsupervised apps.

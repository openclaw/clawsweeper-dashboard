## Summary

Keep this issue open for product and channel-owner review. The requested operations are a new, mutable WhatsApp gateway API rather than a broken existing contract; current plugin infrastructure can register gateway methods, but the authenticated Baileys session remains owned by the WhatsApp channel, so a third-party skill/plugin cannot independently provide the same safe path. The proposal aligns with improved support for major messaging channels, but the public RPC scope and authorization contract need an explicit decision first.

Likely related people: `scoootscooob` is the strongest implementation-routing candidate from the WhatsApp channel-extension refactor history; `TurboTheTurtle` is a recent contributor on the channel surface; `steipete` is the best available scope-policy routing candidate. Confidence is medium because the decision concerns a new durable API rather than an established behavior defect.

## What This Changes

Add gateway RPCs to read WhatsApp group metadata, rename a group, and add or remove group participants through OpenClaw’s existing WhatsApp session.

## System Context

Gateway RPCs let authenticated clients request operations from OpenClaw’s running services. The WhatsApp channel plugin owns the paired Baileys connection, so any group-management request would pass from the gateway through that channel-owned session to WhatsApp and return structured results.

## Architecture Diagram

  E --> F[WhatsApp group state]
  F --> G[Structured RPC response]

## Best Possible Solution

Define a small WhatsApp-channel-owned Gateway API with stable request/result schemas, existing gateway authentication plus explicit write-operation safeguards, normalized group and participant identifiers, and focused live proof against an admin-controlled test group.

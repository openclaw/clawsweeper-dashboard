## Summary

Keep open: current main and v2026.6.11 still lack Discord glob-channel matching, and the remaining work is authorization-sensitive enough to need maintainer product/security direction.

## What This Changes

The issue requests glob or wildcard matching for Discord guild channel allowlist entries so dynamically named channels can be accepted without per-channel config edits and restarts.

## Best Possible Solution

Define one Discord-owned dynamic channel admission contract, then implement it with explicit precedence, schema/types/docs/status/audit updates, and regression coverage.

Rationale: Automation should not choose this because the new syntax changes a public Discord config surface and determines which guild messages can reach agents.

Options:

- **Approve Narrow Glob Contract (recommended):** Add Discord-owned glob matching with explicit precedence, schema/types/docs, audit/status visibility, and focused ingress tests while keeping category inheritance and access-list redesign separate.
- **Fold Into Existing Redesigns:** Keep this open but require maintainers to solve the dynamic-channel problem through the category tracker or broader access-control redesign instead of a separate glob syntax.
- **Reject Glob Syntax:** Keep exact entries plus the literal `*` model and document that dynamic workstreams should use the broad wildcard or the category/access-control trackers instead.

## Reproduction Assessment

Yes, at source level: a `ws-*` key is not evaluated as a pattern against an incoming `ws-task-1` channel, and a non-empty channel map without an exact, parent, or literal `*` match resolves to denied.

## Solution Assessment

Unclear until maintainers choose the public authorization contract. The implementation likely belongs in the Discord allowlist/config path, but automation should not choose glob syntax, matching order, or security semantics on its own.

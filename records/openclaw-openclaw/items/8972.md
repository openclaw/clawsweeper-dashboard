## Summary

Keep open: current main and the latest release still do not evaluate Discord guild channel keys such as `ws-*` as glob patterns, so the requested authorization-sensitive config feature remains unresolved.

## What This Changes

The issue requests glob-style Discord channel allowlist entries so dynamically created matching channels can be accepted without per-channel config edits and gateway restarts.

## Best Possible Solution

Keep this as the canonical Discord glob-pattern tracker and resolve it through a maintainer-approved allowlist contract covering syntax, precedence, schema/docs, audit/status behavior, and resolver/preflight tests.

Options:

- **Approve narrow glob contract (recommended):** Add Discord-owned glob matching with explicit precedence, schema/types/docs, audit/status visibility, and focused ingress tests while keeping category inheritance and access-list redesign separate.
- **Defer to adjacent redesigns:** Keep this open but require maintainers to fold the dynamic-channel problem into the category or access-control trackers before implementation.
- **Reject glob syntax:** Keep exact entries plus the literal `*` model and document that dynamic workstreams should use the broad wildcard or the category/access-control trackers instead.

## Reproduction Assessment

Yes, at source level. A guild channel key like `ws-*` is never compared as a pattern against an incoming `ws-task-1` channel, so a non-empty channel map without an exact, parent, or literal `*` match resolves to denied.

## Solution Assessment

Unclear until maintainers choose the public authorization contract. The implementation likely belongs in the Discord-owned allowlist/config path, but automation should not choose glob syntax, matching order, or security semantics on its own.

- `impact:security`: Pattern keys would decide which Discord guild messages cross the configured channel authorization boundary.

- `maturity:stable`: The issue affects the Discord channel surface, which `qa/maturity-scores.yaml` marks as M4 Stable.

## Summary

Keep open: current main and the latest release still resolve Discord guild channel allowlists through exact/normalized channel keys, thread-parent fallback, and the literal `*` fallback only, so a key like `ws-*` is not evaluated as a pattern.

## What This Changes

Request support for Discord guild channel allowlist entries that match channel-name patterns such as `ws-*` so dynamically created matching channels can be admitted without listing each one.

## Best Possible Solution

Approve one Discord-owned pattern contract, then update the resolver/preflight path, exported types, Zod schema, docs/status/audit behavior, and focused tests while keeping category inheritance and hot reload as separate scopes.

## Reproduction Assessment

Yes, at source level: with a nonempty Discord guild `channels` map containing `ws-*`, a channel named `ws-task-1` has no exact, normalized, parent, or literal `*` match and resolves denied. I did not run a live Discord repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the permanent pattern syntax and authorization precedence. If approved, the narrowest maintainable path is a Discord-owned pattern tier in the existing allowlist resolver, not bundling category inheritance, hot reload, or sender access-list redesign into the same change.

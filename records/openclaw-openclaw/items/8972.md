## Label Justifications

- `impact:security`: The requested pattern syntax would change which Discord guild channels are authorized to deliver messages to agents.
- `impact:message-loss`: Messages from intended dynamically created channels remain denied unless each channel is listed exactly or the broad literal wildcard is used.
- `maturity:stable`: The issue affects the Discord channel surface, which the checked-in maturity scorecard marks as M4 Stable.

## Summary

Keep open: current main and the latest release still treat Discord guild channel keys as exact id/name/slug entries, thread-parent fallbacks, or the literal `*`; adding glob keys such as `ws-*` remains an unresolved authorization-sensitive feature.

## What This Changes

The issue requests glob or wildcard-pattern support for Discord guild channel allowlist entries so dynamic channels can be admitted without per-channel config edits.

## Best Possible Solution

Keep this as the canonical Discord glob-pattern tracker and resolve it through a maintainer-approved allowlist contract covering syntax, precedence, schema/docs, audit/status behavior, and resolver/preflight tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Discord guild channel allowlists support glob-pattern keys such as `ws-*`, and what precedence should those patterns have relative to exact channel entries, disabled entries, thread-parent fallback, category inheritance, and the literal `*` entry?

Rationale: Automation should not choose this because the new syntax changes a public Discord config surface and determines which guild messages can reach agents.

Likely owner: steipete

Owner reason: steipete has the strongest recent history on the shared matcher and Discord allow-list surfaces affected by the decision.

Owner confidence: high

Options:

- **Approve narrow glob contract (recommended):** Add Discord-owned glob matching with explicit precedence, schema/types/docs, audit/status visibility, and focused ingress tests while keeping category inheritance and access-list redesign separate.
- **Defer to category or access redesign:** Keep this open but require maintainers to fold the dynamic-channel problem into https://github.com/openclaw/openclaw/issues/60582 or https://github.com/openclaw/openclaw/issues/69748 before implementation.
- **Reject glob syntax:** Keep exact entries plus the literal `*` model and document that dynamic workstreams should use the broad wildcard or the category/access-control trackers instead.

## Reproduction Assessment

Yes, at source level: a guild channel key like `ws-*` is not compared as a pattern against an incoming `ws-task-1` channel, so a non-empty channel map without an exact, parent, or literal `*` match resolves to denied. I did not run a live Discord repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public authorization contract. The implementation likely belongs in the Discord-owned allowlist/config path, but automation should not choose glob syntax, matching order, or security semantics on its own.

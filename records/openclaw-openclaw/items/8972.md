## Summary

Keep open: current main and v2026.6.11 still treat Discord guild channel keys as exact id/name/slug entries, thread-parent fallbacks, or the literal `*`; glob keys such as `ws-*` remain an unresolved authorization-sensitive feature.

## What This Changes

The issue requests Discord guild channel allowlist entries that can match dynamic channel names with glob or wildcard patterns.

## Best Possible Solution

Keep this as the canonical Discord glob-pattern tracker until maintainers approve one allowlist contract covering syntax, precedence, schema/types/docs/status/audit behavior, and resolver/preflight tests.

Options:

- **Approve narrow glob contract (recommended):** Add Discord-owned glob matching with explicit precedence, schema/types/docs, audit/status visibility, and focused ingress tests while keeping category inheritance and access-list redesign separate.
- **Defer to adjacent redesign:** Keep this open but require maintainers to fold the dynamic-channel problem into the category or broader access-control trackers before implementation.
- **Reject glob syntax:** Keep exact entries plus the literal `*` model and document that dynamic workstreams should use the broad wildcard or category/access-control design instead.

## Reproduction Assessment

Yes, at source level. A guild channel key like `ws-*` is never compared as a pattern against an incoming `ws-task-1` channel, so a non-empty channel map without an exact, parent, or literal `*` match resolves to denied.

## Solution Assessment

Unclear until maintainers choose the public authorization contract. The implementation likely belongs in the Discord-owned allowlist/config path, but automation should not choose glob syntax, matching order, or security semantics on its own.

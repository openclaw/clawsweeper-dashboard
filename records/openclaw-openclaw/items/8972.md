- `impact:security`: The requested pattern syntax would change which Discord guild channels are authorized to deliver messages to agents.
- `impact:message-loss`: Messages from intended dynamically created channels remain denied unless each channel is listed exactly or the broad literal wildcard is used.
- `maturity:stable`: The issue affects the Discord channel surface, which `qa/maturity-scores.yaml` marks as M4 Stable.

## Summary

Keep open: current main and v2026.6.11 still treat Discord guild channel allowlist keys as exact id/name/slug entries, thread-parent fallbacks, or the literal `*` entry only. Glob keys such as `ws-*` remain unsupported, and adding them would change a security-sensitive message-ingress boundary.

## What This Changes

Add glob or wildcard pattern matching to Discord guild channel allowlists so dynamically named channels can be admitted without per-channel config edits and restarts.

## Best Possible Solution

Keep this as the canonical Discord glob-pattern tracker and resolve it through a maintainer-approved allowlist contract covering syntax, precedence, schema/docs, audit/status behavior, and resolver/preflight tests.

- **Reject new glob syntax:** Keep the current exact-entry plus literal `*` model and document that dynamic workstreams should use the broad wildcard or the category/access-control trackers instead.

## Reproduction Assessment

Yes. At source level, a guild channel key like `ws-*` is never compared as a pattern against an incoming `ws-task-1` channel, so a non-empty channel map without an exact, parent, or literal `*` match resolves to denied.

## Solution Assessment

Unclear until maintainers choose the public authorization contract. The implementation likely belongs in the Discord-owned allowlist/config path, but automation should not choose glob syntax, matching order, or security semantics on its own.

## Summary

Keep this issue open. Current main still treats Discord guild channel keys as exact IDs/names/slugs plus the literal `*` fallback, so `ws-*` does not authorize dynamically named channels. Because this is an access-control grammar change, a maintainer needs to choose explicit matching and precedence semantics before implementation.

## What This Changes

Add a documented wildcard-pattern form for Discord guild channel allowlists so newly created matching channels can be authorized without adding each channel to configuration.

## System Context

Discord inbound messages resolve a guild and channel configuration before the plugin decides whether the message may enter an agent session. Channel entries currently match exact channel identifiers or names, with parent fallback for threads and a literal catch-all entry.

## Architecture Diagram

flowchart LR
  A[Discord inbound message] --> B[Guild configuration]
  B --> C[Channel and thread identifiers]
  C --> D[Channel entry matcher]
  D --> E[Allow or deny decision]
  E --> F[Agent session dispatch]

## Best Possible Solution

Adopt one Discord-owned, documented pattern grammar only after approving precedence such as exact direct match, normalized direct match, thread-parent match, most-specific pattern match, then literal `*`; update schema, docs, status/audit metadata, and regression coverage together.

Rationale: This changes the authorization boundary for inbound Discord messages, so an implementation cannot safely choose whether patterns are accepted, how overlaps resolve, or whether matching applies to IDs, names, and normalized slugs without maintainer intent.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve a narrow glob contract (recommended):** Support a restricted documented glob syntax for channel names/slugs, with exact and parent entries taking precedence and a deterministic most-specific pattern rule.
- **Prefer category configuration:** Decline name patterns and direct dynamic-channel workflows toward the separate category-level configuration proposal at https://github.com/openclaw/openclaw/issues/60582.
- **Keep explicit entries only:** Retain the current exact-entry and literal-wildcard authorization model to avoid adding another access-control grammar.

## Solution Assessment

Unclear: a restricted pattern form is a plausible solution, but it is not safe to implement until maintainers select the authorization grammar and precedence against exact, parent, and literal-wildcard entries.

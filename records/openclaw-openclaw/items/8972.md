## Summary

Keep open: current main and v2026.6.11 still treat Discord guild channel allowlist keys as exact entries plus the literal `*`, so glob keys like `ws-*` remain unimplemented and need a maintainer-approved authorization contract.

## What This Changes

Request adds glob/wildcard matching to Discord guild channel allowlist entries so dynamically named channels such as `ws-*` do not require per-channel config edits.

## Best Possible Solution

Keep this as the canonical Discord glob-pattern tracker until maintainers approve one narrow allowlist contract covering syntax, precedence, schema/docs, audit/status behavior, and resolver/preflight tests.

Rationale: The requested syntax changes a public Discord config surface and determines which guild messages can reach agents, so automation should not choose the authorization semantics on its own.

Options:

- **Approve narrow glob contract (recommended):** Add Discord-owned glob matching with explicit precedence, schema/types/docs, audit/status visibility, and focused ingress tests while keeping category inheritance and access-list redesign separate.
- **Fold into access-control redesign:** Keep this issue open but require maintainers to solve dynamic channels through the category or broader Discord access-control trackers before implementation.
- **Reject glob syntax:** Keep exact entries plus literal `*` and document that dynamic workflows should use wildcard, category inheritance, or another approved access-control design instead.

## Reproduction Assessment

Yes, at source level. A guild channel key like `ws-*` is never compared as a pattern against an incoming `ws-task-1` channel, so a non-empty channel map without an exact, parent, or literal `*` match resolves to denied.

## Solution Assessment

Unclear until maintainers choose the public authorization contract. The implementation likely belongs in the Discord-owned allowlist/config path, but automation should not choose glob syntax, matching order, or security semantics on its own.

## Summary

Keep open: current main and v2026.6.11 still lack Discord glob-pattern channel allowlist matching, and the remaining work is an authorization-sensitive config/product decision rather than cleanup-closeable stale work.

## What This Changes

Request support for Discord guild channel allowlist patterns such as `ws-*` so dynamically created matching channels do not need per-channel config edits and gateway restarts.

## Best Possible Solution

Keep this as the canonical Discord glob-pattern tracker until maintainers approve one allowlist contract covering syntax, precedence, schema/docs, audit/status behavior, and resolver/preflight tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Discord guild channel allowlists support glob-pattern keys such as `ws-*`, and what precedence should those patterns have relative to exact entries, disabled entries, thread-parent fallback, category inheritance, and the literal `*` entry?

Rationale: The new syntax changes a public Discord config surface and determines which guild messages can reach agents, so automation should not choose the authorization semantics on its own.

Likely owner: steipete

Owner reason: steipete has the strongest current and linked history on the shared matcher and Discord allowlist surfaces affected by this decision.

Owner confidence: high

Options:

- **Approve narrow glob contract (recommended):** Add Discord-owned glob matching with explicit precedence, schema/types/docs, audit/status visibility, and focused ingress tests while keeping category inheritance and broader access-list redesign separate.
- **Fold into Discord access-control redesign:** Keep this open but require maintainers to solve dynamic channels through the category or broader Discord access-control trackers before implementation.
- **Reject glob syntax:** Keep exact entries plus literal `*` and document that dynamic workflows should use wildcard, category inheritance, or another approved access-control design instead.

## Reproduction Assessment

Yes, at source level. A guild channel key like `ws-*` is never compared as a pattern against an incoming `ws-task-1` channel, so a non-empty channel map without an exact, parent, or literal `*` match resolves to denied.

## Solution Assessment

Unclear until maintainers choose the public authorization contract. The implementation likely belongs in the Discord-owned allowlist/config path, but automation should not choose glob syntax, matching order, or security semantics on its own.

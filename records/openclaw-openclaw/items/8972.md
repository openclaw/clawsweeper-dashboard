## Summary

Current main and v2026.6.11 still treat Discord guild channel keys as exact identifiers/names with parent and literal `*` fallback, so the requested pattern capability remains necessary; it should stay open because changing this authorization boundary requires an explicit maintainer decision on syntax and precedence.

## What This Changes

Add glob or wildcard matching for Discord guild channel allowlist entries so dynamically created matching channels work without per-channel config edits and gateway restarts.

## Best Possible Solution

Add a documented Discord-owned `patterns` map rather than reinterpreting existing channel keys, with deterministic precedence of exact ID/name/slug and thread-parent matches before ordered safe-glob matches and literal `*`, plus schema, audit/status warnings, docs, and authorization regression coverage.

Options:

- **Add explicit patterns map (recommended):** Introduce a dedicated Discord `patterns` config map with exact matches taking precedence, deterministic pattern ordering, safe glob semantics, and audit warnings for mutable-name authorization.
- **Interpret channel keys as globs:** Treat metacharacters in the existing `channels` map as patterns, accepting a smaller schema change but risking reinterpretation of previously literal keys and less explicit security posture.
- **Keep exact keys only:** Decline arbitrary patterns and direct dynamic workflows toward category inheritance or explicit channel management instead.

## Solution Assessment

## Risks / Open Questions

- Pattern matching broadens an inbound authorization boundary: ambiguous precedence or normalization could authorize more Discord channels than the operator intended.
- Name-based patterns are mutable and less trustworthy than stable Discord IDs, so status/security audit output should clearly warn when an allowlist depends on patterns.
- Overloading existing channel-map keys with glob syntax could silently reinterpret a previously literal channel name containing metacharacters; an explicit pattern namespace avoids that compatibility ambiguity.

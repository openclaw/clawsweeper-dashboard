## Summary

Keep open: current main and v2026.6.11 still lack behavioral capability descriptors on core tool types, plugin tool metadata, before_tool_call/trusted-policy payloads, effective tool inventory, and Gateway tool schemas. The related issues and Security Matrix PR are overlapping design work, not a merged replacement for this focused Plugin SDK/security-policy contract.

## What This Changes

The issue requests optional per-tool capability descriptors so policy, audit, and UI code can reason about tool behavior without brittle tool-name lists.

## Best Possible Solution

Define one additive, documented advisory tool-capability descriptor contract, project it through tool inventory, Gateway schemas, trusted policies, and before_tool_call, and keep declarations separate from explicit host authorization or grants.

- **Fold Into Permissions Work:** Keep this blocked behind the broader capability-permission/default-deny model so descriptors ship only as part of an enforceable grant system.
- **Limit To Security Matrix:** Use the Security Matrix audit model as the canonical consumer and avoid a general public descriptor field until that implementation lands and owners approve the vocabulary.

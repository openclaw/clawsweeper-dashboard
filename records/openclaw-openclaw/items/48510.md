## Summary

Keep open: current main and v2026.6.11 still lack the requested behavioral capability descriptors on core tool definitions, plugin tool metadata, before_tool_call/trusted-policy payloads, effective tool inventory, and Gateway tool schemas. Related open work overlaps with enforcement, provenance, and audit modeling, but it does not replace this focused public Plugin SDK/security-policy contract.

## What This Changes

Add optional behavioral capability descriptors to tool definitions so policy and audit plugins can reason about tool behavior without hardcoded tool-name lists.

## Best Possible Solution

Define one additive, documented advisory tool-capability descriptor contract and project it through tool definitions, plugin metadata, tool inventory, Gateway schemas, trusted policies, and before_tool_call without treating declarations as grants.

Options:

- **Approve unified descriptor contract (recommended):** Define additive optional descriptors with unknown-by-default semantics, thread them through tool definitions, plugin metadata, inventory, Gateway protocol, and hook events, and document that declarations do not bypass host policy.
- **Fold into permissions work:** Keep this blocked behind the broader capability-permission and default-deny model so descriptors ship only with an enforceable grant system.
- **Limit to Security Matrix:** Use the Security Matrix audit model as the first canonical consumer and avoid a general public descriptor field until that implementation lands and owners approve the vocabulary.

## Reproduction Assessment

## Solution Assessment

Unclear as a final implementation shape: optional descriptors are plausible and aligned, but the best fix needs maintainer-approved taxonomy, trust tiers, unknown semantics, and coordination with adjacent capability/provenance work.

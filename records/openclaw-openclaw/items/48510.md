## Summary

Keep open: current main still lacks optional behavioral capability descriptors on tool definitions, plugin tool metadata, before_tool_call/trusted-policy payloads, and Gateway tool inventory schemas. The related open work overlaps on enforcement, provenance, audit, or broader permissions, but none is a merged replacement for this focused public Plugin SDK/security-policy contract.

## What This Changes

The issue requests optional behavioral capability descriptors on tool definitions so policy and audit plugins can reason about tool behavior without brittle tool-name matching.

## Best Possible Solution

Define one additive advisory tool-capability descriptor contract with unknown-by-default semantics, project it through tool definitions, plugin metadata, inventories, Gateway schemas, trusted policies, and before_tool_call, and document that declarations are not grants.

Options:

- **Approve Unified Advisory Descriptor Contract (recommended):** Define additive optional descriptors with unknown-by-default semantics and thread them through tools, metadata, inventory, Gateway, trusted policies, and before_tool_call while stating that declarations do not bypass host policy.
- **Fold Into Capability Permissions:** Keep this blocked behind the broader default-deny capability-permission model so descriptors ship only with an enforceable grant system.
- **Limit To Security Matrix First:** Use the Security Matrix audit model as the first canonical consumer and avoid a general public descriptor field until that vocabulary and runtime-fact path lands.

Unclear until maintainer review: optional descriptors are plausible and aligned, but the best fix needs an owner-approved taxonomy, trust model, and coordination with adjacent capability/provenance work.

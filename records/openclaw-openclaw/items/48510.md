## Summary

Keep open: current main and the latest release still lack optional behavioral capability descriptors on core tool definitions, plugin tool metadata, before_tool_call/trusted-policy events, and Gateway tool projections. Related items are useful prior art or adjacent policy work, but none is a merged replacement for this focused Plugin SDK/security-policy contract.

## What This Changes

The issue requests optional self-declared tool capability descriptors so policy, permission, documentation, and audit code can reason about tool behavior without name matching.

## Best Possible Solution

Define one additive, documented advisory tool-capability descriptor contract, project it through tool inventory and hook policy surfaces, and keep declarations separate from host authorization or explicit grants.

- **Fold Into Permissions Work:** Keep this issue blocked behind the broader capability-permission/default-deny model so descriptors ship only as part of an enforceable grant system.
- **Limit To Security Matrix:** Use the Security Matrix audit model as the canonical consumer and avoid a general public descriptor field until that implementation and vocabulary are approved.

Yes. This is source-reproducible as an SDK/API gap: current main and v2026.6.11 can be inspected to show core tool types, plugin metadata, hook events, trusted-policy dispatch, docs, and Gateway schemas lack behavioral capability descriptors.

Unclear as a final implementation shape. Optional descriptors are plausible and aligned, but the best fix needs maintainer-approved taxonomy, trust tiers, unknown semantics, and coordination with adjacent capability/provenance work.

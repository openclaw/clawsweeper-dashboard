## Summary

Keep open: current main and v2026.6.11 still do not expose per-tool behavioral capability descriptors, and the related permission, provenance, audit, and Security Matrix work is adjacent rather than a merged replacement.

## What This Changes

The issue requests optional behavioral capability descriptors on built-in and plugin tool definitions so policy, onboarding, audit, and docs can reason about tool behavior without matching tool names.

## Best Possible Solution

Design one additive public SDK and Gateway protocol contract for behavioral tool capability descriptors, then project it through built-in/plugin tool metadata, tools.catalog/tools.effective, trusted policies, before_tool_call, docs, API baselines, and contract tests with conservative unknown semantics.

## Reproduction Assessment

Yes. This is source-reproducible as a feature/API gap: current main and v2026.6.11 expose tool names, params, identity hints, risk, tags, and derived paths, but not declared behavioral capability descriptors.

## Solution Assessment

Unclear as a final implementation shape. Optional descriptors are plausible, but the best fix needs maintainer-approved taxonomy, unknown/default semantics, and coordination with adjacent capability, provenance, and audit proposals.

## Summary

Keep this issue open. Current main still aborts device-code polling for any thrown error other than a timeout or caller cancellation, so a transient fetch/DNS/socket failure can end the interactive authorization window. The proposed unconditional retry is too broad because it would also hide local validation, SSRF-guard, and response-processing failures; a narrow retriable-error policy with the normal poll delay is the safer repair.

## What This Changes

Make OpenAI device-code authorization polling tolerate transient transport failures without forcing the user to restart the 15-minute login flow.

## System Context

The bundled OpenAI plugin obtains a device code, displays it to the user, polls OpenAI until authorization completes, and then exchanges the returned code for credentials. The polling result feeds the provider-auth flow used by headless or callback-hostile OpenAI/Codex sign-in.

## Architecture Diagram

flowchart TD
  A[User starts device-code login] --> B[OpenAI plugin requests user code]
  B --> C[User completes browser authorization]
  C --> D[Polling loop]
  D --> E{Poll result}
  E -->|Authorized| F[Exchange code for credentials]
  E -->|Pending or transient transport failure| D
  E -->|Terminal response or cancellation| G[Show actionable failure]
  F --> H[Save OAuth profile]

## Best Possible Solution

Keep explicit cancellation and terminal response errors fail-fast, but classify only well-understood transport failures and transient HTTP responses as retriable; wait using the existing deadline-aware poll delay and add regression coverage for both retry and terminal paths.

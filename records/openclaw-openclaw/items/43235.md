## Summary

Keep open: current main and v2026.6.11 still route ordinary foreground agent work through a per-session lane and then the shared `main` lane, and the prior implementation PR was closed unmerged rather than replacing this tracker.

## What This Changes

Issue requests per-agent command lanes so long-running work for one agent does not consume the shared foreground main lane for all agents in multi-agent deployments.

## Best Possible Solution

Keep this as the canonical foreground per-agent lane tracker, then design a server-owned lane/concurrency model that preserves a global cap, bounds lane names, updates schema/docs, and covers all foreground embedded-run entry points.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 still compose a per-session lane with a shared `main` global lane for foreground runs, and the issue/comment logs match that bottleneck. I did not run a live multi-agent Feishu deployment in this read-only review.

## Solution Assessment

Unclear as proposed: per-agent isolation is the right capability class, but maintainers still need to choose the server-owned config shape, global-cap semantics, lane-name validation, and relationship to adjacent lane proposals.

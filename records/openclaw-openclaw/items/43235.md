## Summary

Keep open: current main still routes ordinary embedded agent turns through a per-session lane and then the shared main lane, while the earlier implementation PR was closed unmerged and the remaining fix needs scheduler/config direction.

## What This Changes

The issue requests per-agent or per-agent-group command lanes so one busy agent cannot consume the shared main lane and delay other agents in multi-agent gateway deployments.

## Best Possible Solution

Define one scheduler-owned lane routing model that preserves shared-main as the default, adds trusted config-derived foreground isolation for agents or groups, keeps aggregate resource caps intact, and aligns with hook, browser/channel, and subagent lane proposals.

Options:

- **Design a unified lane-routing model (recommended):** Keep this issue as the foreground-agent scheduling case and design a trusted config model that can also accommodate hook, channel/browser, and subagent lane routing without request-controlled lane minting.
- **Ship a narrow per-agent option:** Add a default-off per-agent or per-agent-group foreground lane setting with explicit aggregate caps, docs, and upgrade-safe defaults while leaving other lane surfaces separate.
- **Document deployment partitioning only:** Decline new core lane configuration for now and document separate gateway processes as the supported isolation boundary for heavy agents.

## Reproduction Assessment

Yes, at source level: current main composes per-session lanes with the shared main global lane for ordinary embedded runs, and the issue/comment logs match that lane wait path. I did not run a live multi-agent Feishu deployment in this read-only review.

## Solution Assessment

Unclear: per-agent isolation is plausible, but the best fix should settle a trusted scheduler/config model with aggregate caps and adjacent lane surfaces instead of adding an ad hoc lane object.

## Summary

Keep open: current main and v2026.6.11 still route ordinary inbound agent turns through the shared `main` lane, while the closed broad implementation did not merge and the open hook-lane PR covers only a narrow adjacent surface.

## What This Changes

The issue requests opt-in per-agent or per-agent-group command lanes so heavy agents do not starve other agents on shared multi-agent gateways.

## Best Possible Solution

Define an opt-in core lane policy that preserves shared `main` as the default, supports per-agent or per-group foreground lane isolation with per-lane caps, keeps an aggregate safety cap, and ships with docs plus queue/security tests.

Options:

- **Design opt-in core lane policy (recommended):** Keep `main` as the default, add maintainer-approved per-agent or per-group foreground lane config, and require an aggregate safety cap plus docs/tests.
- **Defer to narrow lane surfaces:** Let hook, browser, channel, and subagent lane proposals proceed independently without a top-level per-agent foreground contract yet.
- **Document separate gateways:** Keep foreground replies on the shared `main` lane and recommend separate gateway deployments for heavy agent groups.

## Reproduction Assessment

Yes, at source level: ordinary foreground replies still pass through a per-session lane and then the shared `main` lane, with docs and tests preserving that behavior. I did not run a live 30-agent Feishu reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the scheduler contract; per-agent lanes are plausible, but the best fix should be a unified opt-in policy rather than a one-off config field that conflicts with adjacent lane proposals.

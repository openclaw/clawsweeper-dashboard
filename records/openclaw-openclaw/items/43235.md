## Summary

Keep open: current main and v2026.6.11 still route ordinary foreground agent turns through a per-session lane and then the shared `main` lane, while the requested per-agent foreground isolation adds public scheduler/config semantics that need maintainer direction.

## What This Changes

Request support for per-agent or per-agent-group foreground command lanes so one busy agent on a shared gateway does not starve unrelated agents.

## Best Possible Solution

Design a server-owned foreground lane model that derives lanes from trusted agent config, preserves a separate aggregate resource cap, documents upgrade/default behavior, and covers every embedded-agent entry point without accepting arbitrary request-minted lanes.

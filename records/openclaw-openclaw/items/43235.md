## Summary

Keep open: current main and v2026.6.11 still route ordinary inbound foreground agent turns through the shared `main` lane, while the broad implementation PR was closed unmerged and the open hook-lane PR covers only a narrow adjacent surface.

## What This Changes

The issue requests per-agent or per-agent-group command lanes so one heavy agent cannot starve other agents on a shared gateway.

## Best Possible Solution

Define an opt-in core scheduler policy that preserves shared `main` as the default, supports per-agent or per-group foreground lane isolation with aggregate caps, and ships docs plus queue/security regression tests.

Rationale: The source gap is clear, but the fix creates a public config and scheduler contract across agent, channel, hook, browser, and subagent surfaces; automation should not choose that product boundary.

Owner confidence: high

Options:

- **Design Opt-In Core Lane Policy (recommended):** Keep `main` as the default, add maintainer-approved per-agent or per-group foreground lane config, and require an aggregate safety cap plus docs/tests.
- **Defer To Narrow Lane Surfaces:** Let hook, browser, channel, and subagent lane proposals proceed independently without a top-level per-agent foreground contract yet.
- **Document Separate Gateways:** Keep foreground replies on the shared `main` lane and recommend separate gateway deployments for heavy agent groups.

## Reproduction Assessment

Yes, at source level: ordinary foreground replies still pass through a per-session lane and then the shared `main` lane, with docs and release-tag checks preserving that behavior. I did not run a live 30-agent Feishu reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the scheduler contract; per-agent lanes are plausible, but the best fix should be a coordinated opt-in policy rather than a one-off config field that conflicts with adjacent lane proposals.

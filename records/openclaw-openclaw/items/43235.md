## Summary

Keep open: current main and the latest release still route ordinary foreground agent turns through the shared `main` lane, while the remaining fix is a public scheduler/config decision rather than a cleanup close.

## What This Changes

The issue requests per-agent command lanes so one busy agent cannot starve unrelated agents on the shared foreground lane.

## Best Possible Solution

Define an opt-in core lane policy that preserves `main` as the default, supports per-agent or per-group foreground isolation with per-lane caps, keeps an aggregate safety cap, and documents upgrade behavior with focused queue tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a core opt-in scheduler/config surface for per-agent or per-group foreground command lanes, and what default plus aggregate-cap semantics should it use?

Rationale: Source inspection proves the missing behavior, but the fix creates public config and scheduler semantics across agent, channel, hook, browser, and subagent surfaces; automation should not choose that product contract.

Likely owner: Peter Steinberger

Owner reason: The strongest history signal runs through the central queue, embedded-runner, and gateway lane setup files that define this scheduler/config direction.

Owner confidence: high

Options:

- **Design opt-in core lane policy (recommended):** Keep `main` as the default, add maintainer-approved per-agent or per-group foreground lane config, and require aggregate caps plus docs and regression tests.
- **Defer to narrow lane surfaces:** Let hook, browser, channel, and subagent lane proposals land independently without adding a top-level per-agent foreground contract yet.
- **Document separate gateways:** Keep foreground replies on the shared `main` lane and recommend separate gateway deployments for heavy agent groups.

## Reproduction Assessment

Yes at source level: current main still sends ordinary foreground replies through the shared `main` lane and documents that lane as process-wide. I did not run a live 30-agent Feishu deployment in this read-only review.

## Solution Assessment

Unclear as an implementation direction: per-agent lanes are plausible, but the best fix should be a unified scheduler policy that composes with hook, browser, channel, and subagent lane proposals.

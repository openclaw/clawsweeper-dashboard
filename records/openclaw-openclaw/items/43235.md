## Summary

Keep open: current main and v2026.6.11 still route ordinary foreground agent turns through a per-session lane and then the shared main lane, while the remaining fix adds compatibility-sensitive scheduler/config semantics that need maintainer product direction.

## What This Changes

The issue requests per-agent command lanes so heavy agents in a shared gateway cannot starve unrelated agents on the shared main lane.

## Best Possible Solution

Define a server-owned foreground lane model that derives lanes from trusted agent config, preserves per-session serialization and an aggregate resource cap, and updates schema, docs, and upgrade expectations together.

Options:

- **Trusted per-agent lanes (recommended):** Add a validated agent/defaults config surface that maps agents or groups to server-owned lanes while keeping a separate aggregate safety cap.
- **Single scheduler model first:** Defer this until foreground, subagent, hook, and workload-specific lanes can share one coordinated scheduler contract.
- **Document process isolation:** Keep the current shared main lane and document separate gateway processes as the supported isolation pattern for heavy agents.

## Reproduction Assessment

Yes, at source level: current main composes a per-session lane with the shared main global lane for ordinary foreground turns, and the Feishu logs match that lane wait path. I did not run a live multi-agent Feishu deployment in this read-only review.

## Solution Assessment

Unclear as a final product shape: per-agent isolation is directionally plausible, but the public config shape, global-cap semantics, and trust boundary must be settled before implementation.

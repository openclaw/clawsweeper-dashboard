## Summary

Keep open: current main still routes ordinary foreground agent turns through the shared main lane and exposes no validated per-agent foreground lane config, while field logs show real multi-agent wait impact and the fix needs maintainer product direction.

## What This Changes

Request per-agent or grouped command lanes so heavy agents in a shared gateway do not starve other agents' foreground replies.

## Best Possible Solution

Design a default-preserving core scheduler config that routes foreground agent turns by server-owned agent or group lane with per-lane and aggregate caps, then update schema, docs, and upgrade tests alongside adjacent hook/subagent/channel lane work.

- **Fold Into Scheduler RFC:** Keep this open while maintainers design one coordinated lane/concurrency model for foreground agents, hooks, subagents, browser-heavy work, and channel routing.
- **Document Separate Gateways:** Decline core foreground lane config for now and document separate gateway instances as the supported isolation pattern for heavy agents.

## Reproduction Assessment

Yes, at source level: ordinary auto-reply sets `runLane` to `CommandLane.Main`, the embedded runner falls back missing lanes to `main`, and current config/schema has no per-agent foreground lane. I did not run the reported Feishu load test.

Unclear as an implementation shape: per-agent lanes are plausible, but the best fix needs maintainer-approved scheduler and config semantics, including trusted lane derivation and an aggregate safety cap.

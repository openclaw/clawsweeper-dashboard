## Label Justifications

- `P2`: The issue is a normal-priority multi-agent reliability and scalability improvement with a clear source gap but a bounded operator-facing blast radius.
- `impact:other`: A long-running agent can monopolize shared foreground capacity and delay unrelated agents on the same gateway, which is meaningful operator impact outside the narrower owned impact classes.

## Summary

Keep open: current main still sends ordinary foreground agent turns through per-session serialization and the shared global main lane, so the requested per-agent foreground command lane isolation remains unimplemented and needs maintainer product direction before a public config surface is added.

## What This Changes

Support per-agent or dedicated foreground command lanes so heavy agents on a shared gateway do not starve unrelated agents.

## Best Possible Solution

Define a server-owned foreground lane model from trusted agent config that preserves per-session serialization and an aggregate safety cap, then document and test fresh-install and upgrade behavior.

## Solution Assessment

Unclear as a final product shape: per-agent isolation is plausible, but maintainers need to choose lane ownership, aggregate caps, and config compatibility before implementation.

## Summary

Keep open: current main and v2026.6.11 still route ordinary foreground agent work through a per-session lane and then the shared main lane, while adding per-agent foreground lanes is a compatibility-sensitive scheduler/config product decision.

## What This Changes

The issue requests per-agent command-lane isolation so heavy work from one configured agent does not starve unrelated agents on the shared foreground lane.

## Best Possible Solution

Define a server-owned foreground lane model that derives lanes from trusted agent config, preserves per-session ordering and an aggregate resource cap, and updates schema, docs, and upgrade expectations together.

- **Trusted per-agent lanes (recommended):** Add a validated agent/defaults config surface that maps agents or groups to server-owned foreground lanes while keeping a separate aggregate safety cap.
- **Unified scheduler design first:** Defer this issue until foreground, subagent, hook, and workload-specific lanes can share one coordinated scheduler contract.
- **Document process isolation:** Keep the shared main lane and document separate gateway processes as the supported isolation pattern for heavy agents.

Unclear as a final product shape: per-agent isolation is directionally plausible, but the public config shape, aggregate cap semantics, and trust boundary must be settled before implementation.

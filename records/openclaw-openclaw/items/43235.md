- `impact:other`: The concrete impact is cross-agent queue starvation and high latency in shared deployments, which is meaningful but outside the narrower owned impact labels.

## Summary

Keep open: current main still sends ordinary inbound agent turns through a shared process-wide `main` lane, and the only open related PR covers hook-mapping lanes rather than per-agent foreground lane isolation.

## What This Changes

Request support for opt-in per-agent or per-agent-group command lanes so heavy agents in shared deployments do not starve other agents' inbound replies.

## Best Possible Solution

Define an opt-in core lane policy that keeps shared `main` as the default, supports per-agent or per-group foreground lane isolation with per-lane caps, preserves an aggregate safety cap, and ships with docs plus queue/security tests.

Options:

- **Design opt-in core lane policy (recommended):** Keep `main` as the default, add maintainer-approved per-agent or per-group foreground lane config, and require an aggregate safety cap plus docs/tests.
- **Defer to narrow lane surfaces:** Let hook, browser, channel, and subagent lane proposals proceed independently without a top-level per-agent foreground contract yet.
- **Document separate gateways:** Keep foreground replies on the shared `main` lane and recommend separate gateway deployments for heavy agent groups.

## Reproduction Assessment

Yes, at source level: ordinary foreground replies still pass through a per-session lane and then the shared `main` lane, with docs and release code preserving that behavior. I did not run a live 30-agent Feishu reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the scheduler contract; per-agent lanes are plausible, but the best fix should be a unified opt-in policy rather than a one-off config field that conflicts with adjacent lane proposals.

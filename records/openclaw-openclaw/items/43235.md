## Summary

Keep open: current main and v2026.6.11 still route ordinary foreground agent turns through the shared process-wide `main` lane, while per-agent or grouped foreground lane isolation remains an unresolved scheduler/config product decision.

## What This Changes

The issue requests per-agent or grouped foreground command lanes so long-running work from one agent does not starve other agents on a shared gateway.

## Best Possible Solution

Keep this as the canonical foreground scheduler design item and implement a default-preserving, server-controlled per-agent or grouped lane contract with aggregate safety caps, docs, and upgrade tests after maintainers settle the public config shape.

- **Fold Into Scheduler RFC:** Keep this issue open while maintainers design one lane/concurrency model covering foreground agents, hooks, subagents, browser-heavy work, and channel routing.
- **Document Gateway Isolation:** Decline core foreground lane config for now and document separate gateway instances as the supported isolation pattern.

Unclear as an implementation shape: per-agent lanes are plausible, but the best fix needs maintainer-approved scheduler and config semantics, including a trusted lane source and aggregate safety cap.

## Summary

Keep open: current main and v2026.6.11 still route ordinary foreground agent turns through the shared `main` lane, with only session serialization plus cron/subagent/nested special lanes. The broad per-agent implementation candidate was closed unmerged, and the newer hook-lane PR covers only a narrow adjacent hook surface.

## What This Changes

The issue requests per-agent command lanes so long-running work for one agent does not occupy the shared foreground `main` lane for every other agent.

## Best Possible Solution

Define an opt-in core lane policy that preserves the shared `main` default, supports per-agent or per-group foreground lane isolation with per-lane caps, keeps a global safety cap, and documents upgrade behavior with focused queue tests.

- **Design opt-in core lane policy (recommended):** Keep `main` as the default, add maintainer-approved per-agent or per-group lane config, and include a global safety cap plus docs/tests.
- **Defer to narrow lane surfaces:** Let hook, channel, browser, and subagent lane proposals land independently without adding a top-level per-agent foreground contract yet.
- **Document separate gateways only:** Keep foreground replies on the shared `main` lane and recommend separate gateway deployments for heavy agent groups.

## Reproduction Assessment

Yes at source level: ordinary foreground replies still pass `CommandLane.Main` into the embedded run path, and docs describe `main` as process-wide. I did not run a 30-agent Feishu live reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the lane contract; per-agent lanes are plausible, but the best fix should be a unified scheduler policy rather than a one-off config field that conflicts with hook, channel, or subagent lane proposals.

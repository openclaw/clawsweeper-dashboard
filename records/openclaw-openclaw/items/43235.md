## Summary

Keep open: current main and the latest release still route ordinary foreground agent turns through a per-session lane and then the shared process-wide `main` lane, so the requested per-agent foreground lane isolation remains unimplemented and needs maintainer product direction.

## What This Changes

Add per-agent command lanes so long-running work from one agent does not starve other agents sharing the foreground main lane.

## Best Possible Solution

Keep this issue as the canonical foreground scheduler design item and add server-controlled per-agent lane isolation only after maintainers settle the public config, aggregate cap, and safety semantics.

Yes, at source level: foreground auto-reply runs still pass `CommandLane.Main`, embedded runs enqueue through a per-session lane and then the shared global lane, and the config/docs expose only a global foreground `maxConcurrent`. I did not run the reported 30-agent Feishu load test.

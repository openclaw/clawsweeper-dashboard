## Summary

Keep open: current main and v2026.6.11 still route ordinary foreground agent turns through a per-session lane and then the shared global main lane, and the earlier implementation PR was closed unmerged after concrete security, compatibility, proof, and mergeability blockers.

## What This Changes

The issue requests per-agent command-lane isolation so slow work from one agent cannot consume the shared foreground main lane and delay other agents in large multi-agent deployments.

## Best Possible Solution

Design a trusted server-owned foreground lane model that derives lanes from validated agent config, preserves aggregate resource caps, updates schema/docs/doctor expectations as needed, and covers all embedded-run entry points.

- **Single Scheduler API:** Defer this issue until foreground, subagent, hook, and workload-specific lanes can share one coordinated scheduler model.
- **Document Gateway Isolation:** Keep the current shared main lane and document separate gateway processes as the supported isolation pattern for heavy agents.

## Reproduction Assessment

Yes, at source level: current main composes a per-session lane with the shared main global lane for ordinary foreground turns, and the Feishu logs match that lane wait path. I did not run a live multi-agent Feishu deployment in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public scheduler contract. Per-agent isolation is plausible, but the maintainable solution needs trusted config-derived lanes, aggregate caps, and coordination with adjacent lane proposals.

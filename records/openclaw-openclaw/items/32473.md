## Summary

Keep open: current main and v2026.6.11 still enforce the HTTPS-or-localhost Control UI device-identity boundary, so the Docker/VPS and homelab remote-HTTP access problem remains a security/product decision rather than implemented cleanup.

## What This Changes

The issue requests a way for Docker/VPS and homelab users to complete Control UI device authentication from non-localhost plain HTTP without being blocked by the secure-context requirement.

## Best Possible Solution

Keep the secure default while maintainers choose an explicit plaintext-LAN policy or a guided Doctor/setup recovery path that explains and launches HTTPS, localhost tunneling, or a clearly warned opt-in without hiding the security tradeoff.

## Reproduction Assessment

Yes, source-level. Current main skips browser device identity without WebCrypto, and the Gateway rejects remote device-less Control UI unless a trusted-proxy or break-glass path is used.

## Solution Assessment

Unclear. A simple bypass switch is not the best fix by default; the maintainable solution needs maintainer-approved security policy, in-product recovery guidance, and tests for both secure defaults and any explicit opt-in mode.

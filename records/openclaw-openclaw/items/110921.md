## Summary

Keep this PR open: its new retryable-media rethrow is still caught by LINE’s outer webhook handler, which commits the replay key on every error; the durable ingress retry therefore receives an event that the LINE replay cache suppresses. The latest branch does not change that outer commit path, so the intended second delivery cannot occur with the normal cache enabled.

## What This Changes

The branch converts LINE media-download failures into classified retryable errors and rethrows transient failures so durable ingress can retry media-only inbound events instead of degrading their attachment.

## Best Possible Solution

Keep transient LINE failures retryable only when the outer LINE replay lifecycle leaves the claimed key retryable, then prove two deliveries of the same event through the real replay cache with the second attempt persisting media.

## Reproduction Assessment

Yes at source level: a retryable throw from the changed media catch reaches the outer LINE webhook catch, whose replay-cache commit makes a redelivery of that same event skip. A focused two-delivery test with `createLineWebhookReplayCache()` can establish the failing runtime behavior directly.

## Solution Assessment

No. Retrying the ingress event is the right boundary, but rethrowing alone is incomplete because the outer replay cache commits errors; the retryable failure must leave that claim available before the error reaches durable ingress.

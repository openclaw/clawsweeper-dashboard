## Label Justifications

- `P2`: The issue describes real multi-channel reply delays and perceived delivery suppression, but the remaining work is scheduler/config design rather than an emergency outage.
- `impact:message-loss`: Fast inbound channel replies can sit behind long browser turns for minutes, making delivery effectively suppressed during contention.
- `maturity:stable`: The affected gateway lane/runtime surface maps to `gateway-runtime`, scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and v2026.6.11 still route ordinary non-cron embedded runs through a per-session lane and then the shared `main` global lane, with no browser/workload/per-channel lane routing config surface.

## What This Changes

The issue requests a dedicated browser lane or more general per-channel/workload lane routing so long browser automation does not consume all shared main-lane capacity for fast channel replies.

## Best Possible Solution

Design one server-owned scheduler/concurrency model that isolates slow workload classes or channel/agent groups while preserving a clear global resource cap, upgrade-safe defaults, schema/docs alignment, and tests for fresh-install and existing-config behavior.

## Label Justifications

- `P2`: The issue describes real multi-channel reply delays and perceived delivery suppression, but the remaining work is scheduler/config design rather than an emergency outage.
- `impact:message-loss`: Fast inbound channel replies can sit behind long browser turns for minutes, making delivery effectively suppressed during contention.
- `maturity:stable`: The affected gateway runtime surface is scored M4 Stable in `qa/maturity-scores.yaml`; Discord, one reported channel, is also M4 Stable.

## Summary

Keep open: current main and v2026.6.11 still route ordinary non-cron channel turns through a per-session lane and then the shared `main` global lane, with no browser/workload/per-channel routing config surface.

## What This Changes

The issue requests dedicated browser-workload lanes or configurable per-channel lane routing so slow browser automation cannot starve fast channel replies.

## Best Possible Solution

Design one server-owned scheduler/concurrency model that isolates slow workload classes or channel/agent groups while preserving a clear aggregate resource cap, upgrade-safe defaults, schema/docs alignment, and focused tests for fresh and existing configs.

## Label Justifications

- `P2`: The issue reports concrete multi-channel reply delays and perceived delivery loss, but the remaining work is scheduler/config design rather than an emergency outage.
- `impact:message-loss`: Fast inbound channel replies can sit behind long browser turns for minutes, making channel delivery effectively suppressed during contention.
- `maturity:stable`: The affected gateway runtime queue/scheduling surface maps to `gateway-runtime`, which is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and the latest release still route ordinary foreground embedded runs through a per-session lane and then the shared `main` global lane, while this issue asks for a browser/workload or per-channel lane-routing policy that remains unresolved and overlaps but is not fully owned by the per-agent or follow-up-drain issues.

## What This Changes

The issue requests dedicated browser/workload lanes or per-channel lane routing so slow browser automation does not consume all foreground `main` lane capacity for fast channel replies.

## Best Possible Solution

Design a server-owned foreground scheduling model that can isolate slow workload classes or channel/agent groups while preserving a global resource cap, session ordering, schema/docs consistency, and upgrade-safe defaults.

## Summary

Keep open: current main and the latest release still route normal foreground channel turns through the shared `main` lane, so the requested browser/workload/channel lane isolation remains a real scheduler/config product decision rather than conservative cleanup.

## What This Changes

The issue requests a dedicated browser lane or per-channel/workload lane routing so long browser automation does not starve fast messaging replies on the shared main lane.

## Best Possible Solution

Design one maintainer-owned opt-in scheduler model for slow workload, channel, or agent isolation with aggregate caps, stable defaults, schema/help/docs alignment, and focused fresh-config plus upgrade tests.

## Maintainer Decision

Rationale: The source gap is clear, but the solution adds public lane-routing semantics across core scheduler, config, channels, browser automation, and adjacent per-agent proposals, so automation should not choose that product contract.

Likely owner: Peter Steinberger

Owner reason: The strongest current-history signal for the central lane resolver, gateway lane setup, and foreground main-lane path points to Peter Steinberger-authored commits.

Owner confidence: high

Options:

- **Design unified scheduler lanes (recommended):** Add a maintainer-approved lane classification model that can cover browser, channel, agent-group, and priority use cases while keeping `main` as the default and preserving an aggregate safety cap.
- **Narrow to browser isolation:** Add a smaller browser-workload lane first, accepting that per-channel and per-agent starvation may remain separate follow-up decisions.
- **Fold into per-agent scheduler work:** Use https://github.com/openclaw/openclaw/issues/43235 as the broader design vehicle and keep this issue as browser/workload evidence rather than a separate implementation path.

Yes at source level: current foreground replies still pass `CommandLane.Main` into embedded runs, `resolveGlobalLane()` defaults to `main`, and the docs describe `main` as process-wide. I did not run a live browser-heavy multi-channel deployment.

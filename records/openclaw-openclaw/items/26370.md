## Summary

Keep open: current main has a merged agent-level cron scope mitigation, but the issue discussion reports same-agent/per-user leakage and the current cron caller scope still reduces trusted identity to agentId-only matching. The literal per-agent jobs.json proposal is obsolete because cron is SQLite-backed now, but the underlying security ownership problem still needs maintainer design.

## What This Changes

Request to isolate scheduled cron jobs so agent-originated cron management cannot expose, mutate, delete, or run another agent or user scope’s jobs in shared deployments.

## Best Possible Solution

Keep this issue open for a maintainer-approved SQLite-backed cron ownership model that uses trusted Gateway agent and session identity, enforces list/get/update/remove/run/runs by default, preserves an explicit operator/global path, and documents legacy unowned-job handling with focused tests.

## Reproduction Assessment

Yes, at source level. Current main carries a trusted sessionKey in the agent runtime identity, but cron caller matching retains only agentId, so two different sessions under the same agent can still satisfy the same ownership predicate.

## Solution Assessment

No for the literal per-agent jobs.json storage shape because cron now persists in SQLite. The maintainable solution is a server-side ownership boundary over the current store, with explicit operator behavior and migration handling.

## Summary

Keep open: current main has a useful agent-level cron scope mitigation, but the issue discussion includes same-agent/per-user leakage and current cron caller authorization still drops the trusted sessionKey before matching jobs.

## What This Changes

Request per-agent and per-session cron job isolation so agent tool callers cannot list, update, run, or remove scheduled jobs outside their trusted ownership scope.

## Best Possible Solution

Keep this as the canonical security/product item for a SQLite-backed cron ownership model that enforces trusted agent and session scope across list/get/add/update/remove/run/runs while preserving an explicit operator path.

## Reproduction Assessment

Yes, at source level. Current main carries a trusted sessionKey in the agent runtime identity, but the cron caller scope discards it and matches jobs only by effective agentId, so two different sessions under the same agent can still satisfy the same ownership check.

## Solution Assessment

No for the literal per-agent jobs.json storage shape because cron now persists in SQLite. The maintainable solution is a server-side ownership boundary over the current store, with explicit operator behavior and legacy-job handling.

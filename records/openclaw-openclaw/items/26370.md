## Summary

Keep open: current main has a merged agent-level cron caller-scope mitigation, but the production discussion also reports same-agent/per-user leakage, and the current source still reduces trusted caller identity to agentId for cron ownership checks. The requested per-agent jobs.json storage shape is obsolete because cron is now SQLite-backed, but the security ownership problem remains real.

## What This Changes

The issue requests isolated cron scheduled-job ownership so agent-originated cron list, mutation, run, and history paths cannot expose or modify another tenant's jobs.

## Best Possible Solution

Keep this issue open for a maintainer-approved SQLite-backed cron ownership model that uses trusted Gateway agent and session identity, enforces list/get/update/remove/run/runs by default, preserves an explicit operator/global path, and documents legacy unowned-job handling with focused tests.

## Reproduction Assessment

Yes, at source level. Current main carries a trusted sessionKey in the agent runtime identity, but cron caller scope discards it and matches jobs only by effective agentId, so two different sessions under the same agent can satisfy the same ownership check.

## Solution Assessment

No for the literal per-agent jobs.json storage shape because cron now persists in SQLite. The maintainable solution is a server-side ownership boundary over the current store, with explicit operator behavior and migration handling.

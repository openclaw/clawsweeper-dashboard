## Summary

Keep open. Current main has a strong partial mitigation from https://github.com/openclaw/openclaw/pull/96883 for cross-agent cron CRUD, but the richer production report still has an unresolved session/tenant-boundary decision: trusted Gateway identity carries `sessionKey`, while cron authorization reduces that identity to `agentId` and the list protocol/service still have no `sessionKey` filter.

## What This Changes

Request adds hard per-agent/per-session isolation for cron scheduled-job visibility and mutation in shared multi-user deployments.

## Best Possible Solution

Design one Gateway-enforced cron ownership model on the SQLite-backed store: derive trusted agent and session scope from caller identity, enforce default visibility/mutation by that scope, preserve explicit operator/admin global access, and coordinate with the broader scheduling-authority RFC.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: current trusted identity carries a session key, but cron caller scope and list filters reduce the boundary to agent id. I did not run a live multi-user Gateway scenario in this read-only review.

## Solution Assessment

No, the literal per-agent `jobs.json` proposal is not the best final shape because current cron runtime state is SQLite-backed. The maintainable fix is a Gateway-enforced agent/session ownership contract with explicit operator/admin escape hatches and migration/doctor handling where needed.

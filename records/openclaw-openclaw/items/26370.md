## Summary

Keep open: current main has the merged agent-level cron scoping from https://github.com/openclaw/openclaw/pull/96883, but the production comments report same-agent/per-user leakage and current caller-scope code still retains only agentId, not the trusted sessionKey. The literal per-agent jobs.json proposal is obsolete because cron is SQLite-backed now, but the security ownership problem remains.

## What This Changes

Requested per-agent cron scheduled-job isolation so agent-tool cron list, mutation, run, and history operations cannot expose or modify jobs across agents or users in multi-user deployments.

## Best Possible Solution

Keep this open for a maintainer-approved SQLite-backed cron ownership model that uses trusted Gateway agent and session identity, enforces list/get/update/remove/run/runs by default, and preserves an explicit operator/global path.

## Reproduction Assessment

Yes, at source level: current main carries trusted agent runtime identity through the Gateway, but cron caller scope retains only agentId and therefore cannot distinguish two sessionKeys under the same agent.

## Solution Assessment

No for the literal per-agent jobs.json shape because cron now uses SQLite-backed state. The best solution is server-side ownership enforcement over the canonical cron store with an explicit operator path and legacy handling.

## Summary

Keep open: current main has a merged agent-level cron scoping mitigation, but the issue discussion includes same-agent/per-user leakage and current cron ownership checks still collapse distinct sessions under the same agent.

## What This Changes

The issue requests isolated cron scheduled-job ownership so multi-user deployments cannot list, modify, run, or delete another agent or user's scheduled jobs.

## Best Possible Solution

Keep this open for a maintainer-approved SQLite-backed cron ownership model that uses trusted Gateway agent and session identity, enforces list/get/update/remove/run/runs by default, and preserves an explicit operator/global path.

## Reproduction Assessment

Yes, at source level. Current main carries a trusted sessionKey in the agent runtime identity, but the cron caller scope discards it and matches jobs by effective agentId, so two different sessions under the same agent can still satisfy the same ownership check.

## Solution Assessment

No for the literal per-agent jobs.json storage shape because cron now persists in SQLite. The maintainable solution is a server-side ownership boundary over the current store, with explicit operator behavior and legacy handling.

## Summary

Keep open: current main and v2026.7.1-beta.1 now enforce agent-scoped cron operations through the merged caller-identity work, but the production report includes same-agent multi-user sessions and the current trusted scope still reduces `sessionKey` to `agentId`, leaving exact session/peer isolation as an unresolved security/product decision.

## What This Changes

The issue requests isolated cron scheduled-job ownership so multi-user deployments cannot expose or mutate another user or agent's scheduled work.

## Best Possible Solution

Keep the merged agent-scoped caller-identity implementation, then define and implement the remaining session/peer ownership boundary for shared-agent deployments or explicitly document agent-only isolation as the supported contract.

## Reproduction Assessment

Yes, at source level: create two jobs with the same `agentId` but different session/peer `sessionKey` values, then call cron management from one session. Current Gateway cron authorization only compares parsed agent ids, so exact same-agent peer isolation is not enforced.

## Solution Assessment

No for the literal per-agent `jobs.json` shape because cron is now SQLite-backed and current main already has an agent-level fix. The best remaining solution is a maintainer-approved ownership model that uses the trusted `sessionKey` when shared-agent user isolation is intended.

## Summary

Keep open: current main has a merged agent-level cron scope mitigation, but the issue discussion includes same-agent/per-user leakage and current cron caller matching still drops the trusted sessionKey and matches only agentId. The literal per-agent jobs.json shape is obsolete because cron is SQLite-backed now, but the security ownership problem remains a maintainer design item.

## What This Changes

The issue requests isolated cron job storage and access control so multi-user deployments cannot see, edit, delete, or run other agents' or users' scheduled jobs.

## Best Possible Solution

Keep this issue open for a maintainer-approved SQLite-backed cron ownership model that uses trusted Gateway agent and session identity, enforces list/get/update/remove/run/runs by default, preserves an explicit operator/global path, and documents legacy unowned-job handling with focused tests.

## Reproduction Assessment

Yes, at source level. Current main carries a trusted sessionKey in the agent runtime identity, but the cron caller scope discards it and matches jobs only by effective agentId, so two different sessions under the same agent can still satisfy the same ownership check.

## Solution Assessment

No for the literal per-agent jobs.json storage shape because cron now persists in SQLite. The maintainable solution is a server-side ownership boundary over the current store, with explicit operator behavior and migration handling.

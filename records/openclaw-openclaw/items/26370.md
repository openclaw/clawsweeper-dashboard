## Summary

Keep open: current main has the merged agent-level mitigation from https://github.com/openclaw/openclaw/pull/96883, but the production same-agent/per-session leakage remains source-reproducible because cron caller matching still drops the trusted sessionKey and authorizes by agentId only.

## What This Changes

The issue requests isolated cron scheduled-job visibility and mutation ownership for multi-user or multi-agent deployments, originally suggesting per-agent jobs.json storage plus admin/global migration behavior.

## Best Possible Solution

Keep this issue open for a maintainer-approved, SQLite-backed cron ownership model that uses trusted Gateway agent and session identity for list/get/update/remove/run/runs while preserving an explicit operator/global path.

## Reproduction Assessment

Yes. Source inspection shows the agent runtime identity carries a sessionKey, but cron caller scope keeps only agentId and job matching only compares effective agent ownership, so two different sessions under one agent can remain in the same cron management scope.

## Solution Assessment

No for the literal per-agent jobs.json proposal because cron now persists in SQLite. The safer solution is server-side ownership enforcement over the canonical store, with explicit operator/admin behavior and migration handling.

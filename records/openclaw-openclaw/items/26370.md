## Summary

Keep open. Current main now enforces meaningful agent-level cron isolation, but the issue discussion includes production cases where multiple users share one agent, and current caller scope still carries only agentId rather than exact session/user ownership.

## What This Changes

The issue requests per-agent or per-session isolation for scheduled cron jobs so multi-user deployments cannot list, modify, run, or delete jobs owned by other agents or users.

## Best Possible Solution

Keep the existing agent-level scoping and add a maintainer-designed per-session/user cron ownership model with an explicit operator all-jobs path and migration/doctor guidance for existing global jobs.

## Reproduction Assessment

Yes, by source inspection for the remaining same-agent case: current main scopes cron tool operations to agentId, while the issue comments include users sharing one agent and current authorization does not carry exact sessionKey as caller scope.

## Solution Assessment

No final implementation is selected yet. Agent-level scoping is a useful partial fix, but the remaining best solution needs a maintainer-approved per-session/user ownership model and admin/operator path.

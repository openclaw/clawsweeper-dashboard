## Summary

Keep open: current main has a merged agent-level cron scope mitigation, but the production reports include same-agent per-user leakage, and current cron ownership checks still do not enforce exact trusted session/user ownership.

## What This Changes

Request cron scheduled-job isolation so agent/user-scoped callers cannot list, update, delete, run, or inspect other agents' or users' jobs.

## Best Possible Solution

Keep this as the canonical security/product tracker for a SQLite-backed cron ownership model that uses trusted Gateway agent and session identity, scopes list/get/update/remove/run/runs by default, and preserves an explicit operator/global path.

## Reproduction Assessment

Yes, at source level. Current main carries a trusted sessionKey in the agent runtime identity, but the cron caller scope and service filters use agentId only, so distinct sessions under the same agent are not proven isolated.

## Solution Assessment

No for the literal per-agent jobs.json storage shape because cron is now SQLite-backed. The best fix is a server-side trusted ownership boundary over the current store, with explicit operator behavior and legacy handling.

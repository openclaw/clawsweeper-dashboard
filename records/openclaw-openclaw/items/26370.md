## Summary

Keep open. Current main has a strong partial fix from the merged caller-scoped cron work, but it only scopes agent-tool cron operations to the calling agent; the production discussion also asks for session/user isolation within a shared agent and safe legacy/admin semantics, which remain a security-sensitive product boundary.

## What This Changes

The issue requests isolated cron scheduled-job ownership so multi-user deployments cannot list, edit, delete, run, or leak other agents' or users' scheduled tasks.

## Best Possible Solution

Define the supported cron ownership boundary first, then extend the trusted Gateway caller scope and cron visibility/mutation checks to cover the chosen agent/session/user model while preserving an explicit operator/admin path and SQLite-backed migration story.

## Reproduction Assessment

Yes. Source inspection shows current main's cron caller scope is agent-only and `cronJobMatchesCallerScope` does not require a full sessionKey match, so same-agent sessions remain a plausible current-main visibility/mutation gap without needing a live deployment to identify the path.

## Solution Assessment

No, not completely. PR 96883 is the right partial fix for cross-agent agent-tool access because it uses trusted Gateway identity, but the full issue needs a maintainer decision on same-agent session isolation, legacy jobs, and admin/operator access.

## Summary

Keep open: current main has the merged agent-level cron scope mitigation, but it still drops the trusted `sessionKey` and matches cron ownership only by `agentId`, so the same-agent per-user/session leakage reported in production is not fully solved. The literal per-agent `jobs.json` storage shape is obsolete because cron is now SQLite-backed, but the security ownership problem remains real.

## What This Changes

The issue requests isolated cron scheduled-job visibility and mutations so multi-user or multi-agent deployments cannot see, edit, delete, or misroute each other’s scheduled jobs.

## Best Possible Solution

Keep this issue open for a maintainer-approved SQLite-backed cron ownership model that uses trusted Gateway agent plus session or sender identity, enforces list/get/add/update/remove/run/runs by default, preserves an explicit operator/global path, and documents legacy unowned-job handling with focused tests.

## Reproduction Assessment

Yes, at source level. Current main carries trusted `sessionKey` in the Gateway runtime identity, but the cron caller scope discards it and compares jobs only by effective `agentId`, so distinct sessions under one agent can still satisfy the same ownership check.

## Solution Assessment

No for the literal per-agent `jobs.json` storage design because cron now persists in SQLite. The maintainable fix is a server-side ownership boundary over the canonical cron store, with explicit operator behavior and legacy-job handling.

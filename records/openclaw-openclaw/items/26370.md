## Summary

Keep open. Current main fixed cross-agent cron CRUD for agent-tool callers through PR #96883, but the issue discussion includes same-agent multi-user/session leakage, and current caller scope still discards the trusted sessionKey and matches jobs by agent identity rather than by same-session/peer ownership.

## What This Changes

Issue requests isolated cron scheduled-job visibility and mutations so agents or users cannot see, edit, run, or delete jobs outside their own ownership scope.

## Best Possible Solution

Keep the #96883 agent-scope mitigation, then design cron ownership over the shared SQLite store with default same-session/peer enforcement for agent-tool CRUD/history, an explicit operator all-jobs mode, legacy-job handling, and focused docs/tests.

## Reproduction Assessment

Yes at source level: current main carries trusted agent identity and blocks cross-agent jobs, but the cron caller scope drops sessionKey and the match helper only rejects foreign agent IDs, so same-agent peer/session isolation remains unproven and likely missing.

## Solution Assessment

Partially: PR #96883 is the best current mitigation for cross-agent CRUD/history, but it is not a complete solution for the same-agent multi-user session isolation and operator/migration semantics requested in this issue.

## Label Justifications

- `P2`: The issue is a bounded runtime/session-state bug in local embedded execution, with source evidence but no emergency crash, security, or broad outage signal.
- `impact:session-state`: Two session keys can drive one shared app-server lifecycle concurrently, risking stale or cross-pressured run/session state.

## Summary

Keep this open: current main still queues local embedded TUI runs by same session scope only, while Codex app-server attempts can share one leased backend across different session keys, so the reported cross-session concurrency hole remains source-reproducible.

## What This Changes

Embedded local agent runs are requested to serialize non-BTW executions globally across session keys when they share one app-server backend.

## Best Possible Solution

Add a focused queueing fix that serializes ordinary local embedded runs sharing the same Codex app-server backend, with regression coverage for different session keys plus preserved BTW, stop, and selected-agent behavior.

## Reproduction Assessment

Yes by source inspection, not live execution: different session keys do not match `isSameRunScope`, so a second non-BTW local run can bypass the current queue. A focused test can reproduce this by starting one unresolved local send, then sending another non-BTW prompt with a different session key and asserting the second backend call does not start until the first resolves.

## Solution Assessment

The requested direction is appropriate, but the best fix should serialize by shared embedded app-server/backend ownership rather than blindly making every local session global. The existing `waitForQueuedLocalRun` path can likely be reused once the predecessor selection is corrected.

- `P0`: The report describes first-time macOS users with a supported non-hardcoded provider being forced out of guided provider setup into a technical workaround.
- `impact:ux-release-blocker`: The affected path is first-run macOS onboarding, and unsupported catalog providers currently cannot complete the in-product manual-key setup flow.
- `impact:auth-provider`: The issue is specifically about provider auth choices, API-key setup, starter model validation, and credential persistence.
- `maturity:stable`: The issue affects `macos-gateway-host`, which the checked-in maturity scorecard marks as M4 Stable.

## Summary

The issue is still necessary: current main still hardcodes the macOS manual API-key picker and Gateway activation to Anthropic, OpenAI, and Google, while existing provider setup flows already have provider-owned catalog metadata. The protected `maintainer` label and the macOS/Gateway protocol boundary make this a maintainer-owned product/API decision, not an auto-close candidate.

## What This Changes

Request the macOS first-run API-key picker load supported text-inference API-key providers from the Gateway catalog instead of a three-provider app constant.

## Best Possible Solution

Add an additive Gateway/macOS setup contract that exposes provider-owned text-inference API-key choices, then render and validate those choices in the macOS first-run flow while keeping provider defaults and auth behavior owned by provider plugins.

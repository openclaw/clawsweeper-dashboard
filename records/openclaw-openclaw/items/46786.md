## What This Changes

The issue asks for enabled elevated exec to remain sandbox-by-default unless elevation is explicitly requested, including reconsidering the implicit elevated default and `/elevated ask` behavior.

## Maintainer Decision

Question: Should allowed elevated sessions with no explicit `agents.defaults.elevatedDefault` default to `off`, and should `/elevated ask` remain a host-with-approval alias or become sandbox-by-default per-call opt-in elevation?

Rationale: The narrow safer default changes upgrade behavior, while changing `/elevated ask` would redefine a documented sandbox escape contract; automation should not choose that security boundary alone.

Likely owner: steipete

Owner confidence: high

Options:

- **Default implicit elevation off (recommended):** Change only the no-explicit-default fallback to `off`, preserve `/elevated ask` as the documented host-with-approval alias, and update docs/tests for the safer default.
- **Redefine ask as opt-in:** Make `/elevated ask` keep normal exec in the sandbox and route only explicit elevated calls to host approval, accepting the broader behavior-contract change.
- **Keep current behavior:** Leave elevated enabled as session-level host exec by default and close this only after docs make that security posture unmistakable.

## Reproduction Assessment

Yes at source level. Current main resolves allowed sessions with no configured elevated default to `on`, omitted exec calls inherit that active mode, and elevated target resolution selects the gateway host.

## Solution Assessment

Unclear pending maintainer decision. Defaulting the implicit elevated level to `off` is the narrowest safety fix, while changing `/elevated ask` is a broader behavior-contract change.

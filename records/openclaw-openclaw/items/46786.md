## Summary

Keep this open: current main still resolves allowed elevated sessions with no explicit level to `on`, and active elevated routing still sends implicit sandboxed exec to the gateway host. The direct default-off fix attempts are closed unmerged, while related exec-policy work only partially overlaps.

## What This Changes

The issue requests that enabling `tools.elevated` preserve sandbox exec by default and make host elevation opt-in instead of routing ordinary exec calls to the gateway.

## Best Possible Solution

Make a maintainer-owned security/defaults decision, then align the elevated fallback, `/elevated ask` semantics, model-facing exec policy, system prompt text, public docs, and regression tests in one focused change.

## Reproduction Assessment

Yes, by source inspection. Current main still falls back to `"on"` for allowed elevated sessions, turns `on`/`ask` into active elevated mode, and resolves active elevated exec to gateway instead of the sandbox path; I did not run the full Docker plus Discord scenario.

## Solution Assessment

Unclear pending maintainer decision. Defaulting the fallback to `off` is the narrow fix for the silent sandbox bypass, but redefining `/elevated ask` conflicts with current docs and should be decided with the exec policy-boundary work.

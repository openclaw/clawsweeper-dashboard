## Summary

Keep open: current main and the latest release still implement the reported elevated-enabled routing behavior, and changing it requires a maintainer security/defaults decision rather than conservative cleanup.

## What This Changes

The issue asks OpenClaw to stop `tools.elevated.enabled` from making sandboxed `exec` route to the gateway by default and to support opt-in elevated host exec.

## Best Possible Solution

Maintainers should choose the elevated exec security contract, then align directive resolution, exec target routing, system prompts, tests, docs, and upgrade guidance around one explicit behavior.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should allowed elevated sessions with no explicit `elevatedDefault` keep sandbox exec as the default, or should the current elevated-by-default host exec contract remain supported?

Rationale: The requested change crosses the sandbox escape boundary and can alter existing operator workflows, so automation should not choose the default/security contract.

Likely owner: steipete

Owner reason: steipete has the strongest recent history across the exec runtime, auto-reply directive default, and elevated docs surfaces that need to be aligned.

Owner confidence: high

Options:

- **Default Elevated Off (recommended):** Unset `elevatedDefault` resolves to `off`, while `/elevated on|ask|full` and explicit elevated requests remain the deliberate ways to leave the sandbox.
- **Keep Current Contract:** Preserve current docs and runtime behavior where allowed elevated sessions default to host exec and `ask` is an approval-gated alias of `on`.
- **Add Separate Opt-In Mode:** Keep current `on` and `ask` semantics but add a distinct sandbox-by-default mode for per-call elevated host exec.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: allowed elevated sessions default to `on`, omitted per-call `elevated` uses that default, and elevated target resolution routes `auto` to `gateway` instead of `sandbox`. I did not run a live Docker scenario.

## Solution Assessment

Unclear. Default-off is security-aligned, but current docs and tests intentionally describe `ask`/`on` as active host exec, so the best fix depends on maintainer security/product intent.

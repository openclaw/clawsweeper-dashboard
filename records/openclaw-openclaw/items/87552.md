## Summary

Keep open: the recoverable-pending direction is useful and has real terminal proof, but the current head still has a blocking outbound recovery pacing bug that can let stale no-reconciler rows consume startup/reconnect replay pacing before newer deliverable rows are reached.

## What This Changes

The PR changes outbound recovery so ambiguous send-attempt and unknown-after-send entries without a reconciliation-capable adapter stay pending with backoff instead of being moved to failed, and updates focused tests plus Discord troubleshooting docs.

## Best Possible Solution

Keep the no-blind-replay and future-reconciliation behavior, but make unavailable-reconciler deferrals a cheap non-replay path and have a maintainer explicitly accept the pending-versus-failed queue policy before merge.

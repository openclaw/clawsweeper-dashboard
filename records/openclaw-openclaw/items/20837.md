## Summary

Keep open. Current main still exposes channel metadata in the normal inbound and embedded-runner prompt path, but slash-command prompt reconstruction still hardcodes unknown runtime host fields and omits channel, capabilities, shell, and channel actions; the related attempted fix is closed unmerged.

## What This Changes

The issue requests that agents receive the originating communication channel as context, with possible later selective reply routing by channel.

## Best Possible Solution

Implement prompt metadata parity only in `resolveCommandsSystemPromptBundle()`, using the embedded-runner pattern and account-aware channel capability/action resolution, while leaving selective delivery policy to existing visible-reply/message-tool settings or a separate routing decision such as https://github.com/openclaw/openclaw/issues/54531.

## Reproduction Assessment

Yes, source-level. Current main shows the command pipeline has channel/account metadata and the normal embedded runner passes channel runtime data into the system prompt, while `resolveCommandsSystemPromptBundle()` still omits it.

## Solution Assessment

Partly. The narrow command prompt metadata parity fix is the best implementation path for the confirmed gap, but selective reply routing should stay in existing visible-reply/message-tool policy or a separate maintainer-approved routing design.

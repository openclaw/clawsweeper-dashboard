## Summary

Keep open. Current main has useful Android notification-forwarding hardening, but the central cross-session security boundary is still unresolved: configured third-party packages can still enter the Gateway `notifications.changed` node-session heartbeat path, and the permanent outbound/session binding needs maintainer direction.

## What This Changes

The issue reports that Android notification forwarding can echo native WhatsApp notifications into node sessions, causing duplicate replies and replies to the wrong group.

## Best Possible Solution

Keep this as the canonical issue until maintainers choose and land a layered security-boundary fix that prevents native-channel notification echoes from creating node-session cross-channel sends, backed by live Android plus WhatsApp proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw enforce this primarily as outbound session/channel binding, Android native-package notification suppression, Gateway notification package filtering, or a layered combination?

Rationale: The remaining path crosses Android notification policy, Gateway node-session events, and heartbeat/message delivery authority, so automation should not choose the permanent security boundary or new default/config behavior without maintainer intent.

Likely owner: Ayaan Zaidi

Owner reason: The original feature history ties this person to both the Android notification event source and Gateway `notifications.changed` handling that need boundary direction.

Owner confidence: high

Options:

- **Harden outbound binding first (recommended):** Reject or constrain cross-channel sends from node notification or heartbeat sessions unless a verified source route binding exists, then use Android or Gateway filtering as defense in depth.
- **Suppress native packages in Android:** Default-block known native-channel package IDs in the Android app, reducing duplicate inputs but requiring maintained package ownership policy and upgrade proof.
- **Add Gateway package filtering:** Reject or filter notification packages server-side, which gives operators a central control but adds config/default surface and does not alone settle outbound authority.

## Reproduction Assessment

No live Android plus WhatsApp run was performed in this read-only review. Source inspection shows the necessary ingress path: an operator-allowed third-party Android notification can become a Gateway `notifications.changed` system event in a node session.

## Solution Assessment

Unclear. Android self-package filtering is useful but not the full fix, because native-channel package ownership and outbound route binding still need a maintainer-owned security boundary decision.

## Summary

Keep open. Current main has partial Android notification-forwarding hardening, but source still allows an operator-authorized third-party package such as WhatsApp to become a `notifications.changed` node-session event, and outbound message-tool binding is not proven to prevent the reported wrong-group send.

## What This Changes

The issue asks OpenClaw to prevent Android forwarded notifications from native channel apps from creating duplicate, cross-session WhatsApp replies, with proposed Android filtering, Gateway filtering, and session isolation.

## Best Possible Solution

Keep this as the canonical issue until maintainers choose and land a security-boundary fix that prevents native-channel notification echoes from creating node-session cross-channel sends, backed by live Android plus WhatsApp proof.

Rationale: The remaining source path crosses Android notification policy, Gateway node-session events, and message-tool sends; choosing the wrong owner could leave a cross-channel security gap or add brittle package/config policy.

Likely owner: Ayaan Zaidi

Owner confidence: medium

Options:

- **Harden outbound binding first (recommended):** Reject or constrain cross-channel `message.send` from node notification sessions unless an explicit verified route binding exists, then use Android or Gateway filtering as defense in depth.
- **Suppress native packages in Android:** Default-block known native-channel Android package IDs, reducing duplicate inputs but requiring maintained package ownership policy.
- **Add Gateway package filtering:** Add server-side package filtering for notification events, which helps operators but adds config surface and does not by itself close unbound outbound sends.

No live current-main Android plus WhatsApp reproduction was run. Source inspection does show the necessary path: an allowed third-party Android notification can become a Gateway `notifications.changed` system event in a node session.

## Solution Assessment

Unclear. Android filtering alone is not the best proven fix because the outbound message-tool route binding still needs a maintainer-owned security boundary decision.

## Summary

Keep this PR open. The narrow SQLite change follows the documented `journal_size_limit` mechanism and preserves the non-blocking `PASSIVE` maintenance direction introduced by the earlier merged work, but the submitted evidence is still test-only and does not demonstrate the reported long-running, blocked-reader recovery on a real database.

## What This Changes

This PR sets a 64 MiB SQLite WAL retention ceiling during database maintenance, adds contract coverage for the pragma, and clarifies task-registry WAL documentation.

## System Context

OpenClaw configures SQLite WAL maintenance for shared and agent-scoped runtime stores. Store writes and scheduled checkpoints feed SQLite’s WAL lifecycle, which affects gateway disk consumption and shutdown-time cleanup.

## Architecture Diagram

flowchart LR
  A[SQLite-backed runtime store] --> B[WAL maintenance setup]
  B --> C[Autocheckpoint and periodic PASSIVE checkpoint]
  C --> D[SQLite journal size limit]
  D --> E[Completed checkpoint or WAL reset]
  E --> F[Bounded retained WAL file]
  F --> G[Gateway disk and cache pressure]

## Best Possible Solution

Keep periodic checkpoints PASSIVE, retain the bounded journal-size default only after a live on-disk SQLite proof shows a blocked reader being released and later WAL reclamation, and document that active readers can defer reclamation.

## Summary

Keep open: the current node wake path still keys reconnect and throttle state only by node ID, while the PR provides credible real-gateway evidence that pairing removal can leave a stale three-second delay and let an old invocation observe a replacement session. The proposed lifecycle boundary appears coherent and well-tested, but the branch is behind current `main`, so the exact merge result needs refresh before landing.

Likely related people: `vincentkoc` is a high-confidence owner for adjacent pending-node delivery behavior; `ngutman` is a medium-confidence routing candidate for iOS background wake and reconnect behavior.

## What This Changes

The PR centralizes removed-node runtime cleanup and adds abortable wake lifecycles so direct and queued invocations cannot retain stale state or dispatch to a replacement pairing using the same node ID.

## Best Possible Solution

Rebase onto current `main`, preserve the single removal-owned lifecycle invalidation path, and rerun the real remove/re-pair scenario plus focused direct and pending invocation tests against the exact merge head before landing.

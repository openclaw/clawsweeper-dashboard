## Summary

Keep this open: current main and v2026.6.11 still contain the redaction-idempotency gate that can refuse to preserve credential-looking opaque provider signatures, and the Bedrock replay path still forwards any nonblank stored signature without a corruption-footprint guard.

## What This Changes

The issue reports that transcript secret redaction can mutate opaque Anthropic/Bedrock reasoning signatures when vendor-key patterns false-positive inside base64-like signature bytes, persist the corrupted signature, and cause repeated replay_invalid failures.

## Best Possible Solution

Preserve structurally valid provider-minted signed-thinking tokens only in recognized assistant signature fields, keep ordinary credential redaction intact elsewhere, and add Bedrock/Anthropic repair or drop coverage for already-poisoned signatures.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For provider-minted signed-thinking fields, should OpenClaw preserve structurally valid opaque replay tokens even when their bytes contain credential-shaped substrings, or keep the current redaction-idempotency gate and only harden individual secret patterns?

Rationale: The current tests intentionally redact credential-shaped provider signature fields, but the issue shows that policy can corrupt real opaque replay tokens; choosing the transcript redaction boundary is a maintainer/security decision.

Likely owner: steipete

Owner reason: PR 90682 history shows this person authored the final scoping and validation commits for the affected transcript-redaction boundary.

Owner confidence: high

Options:

- **Scoped Structural Preservation (recommended):** Preserve validated opaque signatures only in known provider signed-thinking fields while continuing to redact arbitrary text, missing-route fields, and malformed payloads.
- **Pattern-Only Hardening:** Make fixed-case vendor prefixes and boundaries stricter while keeping the current redaction-idempotency requirement for provider signatures.
- **Send-Side Recovery Only:** Drop visibly corrupted signatures on Bedrock/Anthropic send and rely on recovery without changing transcript-redaction preservation.

## Reproduction Assessment

Yes, at source level: current main still rejects opaque replay-token preservation when redactSensitiveText would change the value, then persists the redacted message. I did not run a live Bedrock request in this read-only pass.

## Solution Assessment

Unclear until the security boundary is chosen; the narrow direction appears to be scoped structural preservation plus replay hardening, while pattern-only hardening would not cover every opaque-token false positive.

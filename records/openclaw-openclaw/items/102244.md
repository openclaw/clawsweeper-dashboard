## Summary

Keep this open: current main and the latest release still have the transcript-redaction gate that can reject credential-looking opaque provider signatures, and Bedrock still replays any nonblank stored thinking signature without an ellipsis/corruption guard.

## What This Changes

The issue reports that transcript redaction can corrupt Anthropic/Bedrock opaque reasoning signatures when secret-pattern redaction matches credential-looking substrings inside those signatures.

## Best Possible Solution

Add a maintainer-approved route-scoped structural exemption for validated provider-owned opaque reasoning signature fields, keep credential redaction everywhere else, and add Bedrock/Anthropic guard or repair coverage for already-corrupted signatures.

## Maintainer Decision

Required: true

Question: Should provider-owned Anthropic/Bedrock reasoning signature fields bypass secret-pattern redaction based on route and opaque-token shape even when the byte string contains a credential-looking substring?

Rationale: The current tests intentionally redact credential-shaped values on provider signature fields, but the issue shows that this idempotency gate can corrupt real provider signatures; automation should not choose that security boundary alone.

Likely owner: steipete

Owner confidence: medium

Options:

- **Adopt route-scoped opaque-token preservation (recommended):** Preserve validated opaque signatures only in provider-owned assistant reasoning slots, and keep normal redaction for user text, nested payloads, route-missing data, malformed data, and ellipsis-marked values.
- **Prefer send-side recovery only:** Keep the current credential-first redaction boundary and add Bedrock/Anthropic replay guards to drop corrupted signatures, accepting that stored signatures may still be poisoned.
- **Defer as adjacent replay work:** Treat this as part of the broader invalid-signature replay cluster, but that leaves the source-level corruption mechanism open until a canonical owner takes it.

## Reproduction Assessment

Yes, source-level. Current main still compiles default redaction patterns case-insensitively, rejects opaque-token preservation when the redactor would change the value, then replays any nonblank Bedrock thinking signature.

Unclear without maintainer intent. The likely best fix is route-scoped opaque signature preservation plus Bedrock corruption guard/repair coverage, but the exact exemption boundary is a security decision.

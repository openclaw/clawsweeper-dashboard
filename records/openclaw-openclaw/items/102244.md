## Label Justifications

- `impact:session-state`: The corrupted signature is written into the on-disk session transcript and replayed on later turns.

- `impact:message-loss`: Affected follow-up turns can fail before a usable assistant response is delivered.

## Summary

Keep this open: current main and the latest release still have the redaction-idempotency gate that can reject preserving credential-looking opaque reasoning signatures, and Bedrock still forwards any nonblank stored thinking signature without a corruption-footprint guard.

## What This Changes

The issue reports transcript secret redaction corrupting Anthropic/Bedrock signed reasoning payloads when opaque signatures contain false-positive API-key substrings.

## Best Possible Solution

Preserve provider-minted opaque replay signatures only in tightly scoped signed-thinking fields, keep ordinary credential redaction intact elsewhere, and add Bedrock/Anthropic guard or repair coverage for already-poisoned signatures.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For provider-minted signed-thinking fields, should OpenClaw preserve structurally valid opaque replay tokens even when their bytes contain credential-shaped substrings?

Rationale: The current tests deliberately redact credential-shaped provider signature fields, but the report shows that policy can corrupt real opaque replay tokens; maintainers need to choose the transcript redaction boundary before an automated repair changes it.

Likely owner: steipete

Owner reason: The unresolved choice is a secret-redaction/security boundary, and the strongest history signal for that boundary is repeated ownership of src/logging/redact.ts hardening.

Owner confidence: medium

Options:

- **Scoped Structural Preservation (recommended):** Preserve validated opaque signatures only in known provider signed-thinking fields while leaving arbitrary text, missing-route fields, and malformed payloads redacted.
- **Pattern-Only Hardening:** Make fixed-case vendor prefixes and boundaries stricter but keep the current idempotent-redaction requirement for provider signatures.
- **Send-Side Recovery Only:** Drop visibly corrupted signatures on Bedrock/Anthropic send and rely on repair/recovery without changing transcript-redaction preservation.

## Reproduction Assessment

Yes, at source level: current main still rejects opaque replay-token preservation when redactSensitiveText would change the value, then persists the redacted message. I did not run a live Bedrock request in this read-only pass.

## Solution Assessment

Unclear until the security boundary is chosen; scoped structural preservation plus Bedrock/recovery hardening appears narrower than pattern-only hardening, which would not cover every opaque-token false positive.

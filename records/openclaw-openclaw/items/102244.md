## Summary

Keep this open: current main and v2026.6.11 still contain the source-level redaction false-negative where provider replay signatures are preserved only if the generic secret redactor leaves them unchanged, so credential-looking substrings can still poison Anthropic/Bedrock replay signatures.

## What This Changes

The issue asks OpenClaw to stop transcript redaction from corrupting Anthropic/Bedrock reasoning signatures when opaque base64 happens to match vendor credential patterns such as AIza or LTAI.

## Best Possible Solution

Preserve validated provider-owned opaque replay bytes only in known route and signature slots, keep normal credential redaction everywhere else, and add cleanup/send-side handling that drops the whole corrupted thinking block when a persisted signature is already poisoned.

Options:

- **Scoped structural preservation plus repair (recommended):** Preserve only validated route-and-field-specific opaque replay tokens, keep credential redaction elsewhere, and drop/repair already corrupted thinking blocks before Bedrock/Anthropic replay.
- **Only tighten vendor regexes:** Make case-sensitive and boundary-aware credential patterns to reduce false positives, but leave opaque signature preservation dependent on the generic redactor and risk other token-pattern false positives.
- **Rely on recovery only:** Keep current redaction behavior and depend on replay_invalid recovery, accepting persistent poisoned transcript entries and continued intermittent turn loss.

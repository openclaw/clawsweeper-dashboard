## Summary

Keep this issue open: current main and the latest release still have the reported redaction gate and Bedrock replay behavior, and the issue identifies a distinct upstream corruption source within the signed-thinking `replay_invalid` cluster.

## What This Changes

The issue reports that transcript secret redaction can corrupt Anthropic/Bedrock signed reasoning payload fields when opaque signatures contain case-insensitive vendor-key substrings, causing persisted `replay_invalid` failures.

## Best Possible Solution

Preserve provider-minted opaque replay signatures only in scoped signed-thinking fields, keep ordinary credential redaction intact elsewhere, and add Bedrock/Anthropic guard or repair coverage for already-poisoned signatures.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For provider-minted signed-thinking fields, should OpenClaw preserve structurally valid opaque replay tokens even when their bytes contain credential-shaped substrings, or keep the current redaction-idempotency gate and only harden individual secret patterns?

Rationale: The current tests deliberately redact credential-shaped provider signature fields, but the report shows that policy can corrupt real opaque replay tokens; maintainers should choose the redaction boundary before automation changes it.

Likely owner: vincentkoc

Owner reason: Current-main blame points to this recent area contributor for the active redaction and Bedrock replay surfaces.

Owner confidence: high

Options:

- **Scoped Structural Preservation (recommended):** Preserve validated opaque signatures only in known provider signed-thinking fields while leaving arbitrary text, missing-route fields, and malformed payloads redacted.
- **Pattern-Only Hardening:** Make case-sensitive vendor prefixes and boundaries stricter but keep the current idempotent-redaction requirement for provider signatures.
- **Send-Side Recovery Only:** Drop visibly corrupted signatures on Bedrock/Anthropic send and rely on recovery without changing transcript redaction preservation.

## Reproduction Assessment

Yes, at source level: current main still rejects opaque replay-token preservation when `redactSensitiveText` would change the value, then persists the redacted message. I did not run a live Bedrock request in this read-only pass.

## Solution Assessment

Yes on direction, but not as an automatic patch yet. The narrow maintainable solution is a scoped provider-signature preservation rule plus replay hardening, with maintainer approval for the redaction security boundary.

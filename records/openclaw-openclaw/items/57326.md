## Summary

Keep open: current main has fixed some slices of the CLI-backed helper dispatch problem, but source inspection still shows remaining divergence in auth probe execution, slug generation, status/profile discovery, and subagent/gateway runtime metadata; the open related PR and focused subagent issue cover only parts of the broader problem.

## What This Changes

The issue requests that CLI-backed helper paths use the same CLI execution-provider dispatch as normal agent runs instead of falling through to embedded/API helpers or raw canonical provider metadata.

## Best Possible Solution

Keep this issue as the broad canonical tracker until remaining helper paths share a single execution-provider boundary, status/diagnostic paths reflect CLI-backed auth correctly, and session metadata stays canonical while runtime dispatch uses CLI ids only at the execution handoff.

## Reproduction Assessment

Yes at source level: current main still has helper paths that call `runEmbeddedAgent` or persist/report raw canonical providers where the normal agent path resolves CLI execution providers. I did not run live CLI-backed provider proof in this read-only review.

## Solution Assessment

No, the issue is not solved on current main. The best fix should use a canonical execution-provider handoff and focused live proof, not store CLI runtime aliases as canonical session model providers.

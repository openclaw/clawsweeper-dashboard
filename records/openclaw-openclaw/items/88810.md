## Summary

Keep this PR open for changes. The final durable outbound funnel skips an empty rejected chunk with `continue`, but still uses the original chunk index to build reply/first-message metadata for later chunks; if the first attempted chunk is skipped and a later chunk delivers, that later message can lose first-delivery behavior such as the reply target. The earlier live proof is useful for the reply funnel, but the PR body still ties it to `f5807ad1` rather than the final `d47e0e3` head and does not show direct outbound behavior on that head.

**Likely related people:** hydro13 (medium confidence) introduced the earlier Telegram empty-reply guard; NianJiuZst (medium confidence) introduced the current standard-versus-rich delivery split that this PR preserves.

## What This Changes

This PR classifies Telegram empty-content failures centrally, treats rendered-empty reply and outbound sends as no-ops, and avoids recording skipped reply sends as delivered.

## System Context

Telegram has two text-delivery funnels: bot replies flow through reply-threading and delivery accounting, while direct outbound messages flow through the reusable text sender. Both end at Telegram Bot API sends and must only attach first-message reply metadata and delivery records after a message actually reaches Telegram.

  D -->|Delivered| F[First-delivery metadata]

## Best Possible Solution

Track first-delivered state in `createTelegramTextSender` and derive reply, first-only, and final-delivery parameters from delivered chunks rather than attempted indexes; add a mixed skipped-then-delivered outbound regression test and attach redacted exact-head live output for that funnel.

## Reproduction Assessment

Yes, from source: make the first direct-outbound chunk reject with a recognized empty-content error and let a later chunk deliver; the loop advances its source index after `continue`, so the later send is not treated as the first delivery attempt.

## Solution Assessment

No. The no-op policy is a reasonable fix for known empty-content errors, but the durable outbound loop must carry first-delivery semantics forward after a skip, as the reply-threading loop already does.

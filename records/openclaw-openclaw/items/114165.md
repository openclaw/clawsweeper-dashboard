## Summary

This issue is still necessary. Current main assigns the generic 128k/16k fallback after only a short Claude/MAI table, then persists those limits during Foundry deployment discovery; it also does not recognize Claude Opus 5 through the current capability checks. The report’s central bug is source-reproducible, although the requested fix should use Foundry-specific per-model limits rather than treating all GPT deployments as identical. Likely related people: attribution is unresolved from the available history evidence, so route initially through the Microsoft Foundry plugin area (low confidence).

## What This Changes

Repair Microsoft Foundry discovery so known GPT and Claude Opus 5 deployments receive their documented capabilities and do not send obsolete Claude thinking payloads.

## System Context

The bundled Microsoft Foundry provider turns selected Azure deployments into persisted OpenClaw model entries. Its capability resolver chooses the API family, reasoning support, context window, and output limit before onboarding writes the provider configuration used by agent runs.

## Best Possible Solution

Add a provider-local, tested Foundry capability table keyed by the resolved canonical model name, including Claude Opus 5 adaptive-thinking metadata and individually documented GPT limits; retain the conservative fallback only for unknown models.

## Summary

Keep open: current main partially addresses the lookup miss by returning an in-band gateway-tool result, but that result is still shaped as `ok: false` and the downstream tool-result classifier/payload policy can still treat it as a user-visible tool error in the no-reply path.

## What This Changes

The issue reports that a missing `config.schema.lookup` path returns the expected gateway error but also creates a visible channel warning.

## Best Possible Solution

Keep the in-band Gateway RPC miss, but make schema lookup misses non-warning-producing at the agent payload boundary or return a non-error tool-result shape with focused regression coverage for the channel payload path.

## Reproduction Assessment

Yes, by source inspection: `config.schema.lookup` misses are returned as `ok: false`, and the generic classifier treats `ok: false` as a tool error before payload warning policy runs. I did not run a live Telegram reproduction in this read-only review.

## Solution Assessment

No, the merged in-band result is a good partial fix but not clearly the best complete fix because the downstream payload classifier can still treat it as a tool error. The safer fix is to prove and suppress this exact read-only schema miss at the agent payload boundary or encode it as a non-error miss result.

## Summary

Keep open: the PR addresses a valid rate-limit bug, but the shared retry-count increase also makes every sustained 5xx or transport failure wait roughly nine times longer, including batch paths that may subsequently split and retry again. Real-provider after-fix proof is also still missing.

## What This Changes

The PR passes embedding errors into retry waits, raises the shared retry limit from 3 to 7, and applies a larger capped delay when an error message appears to indicate rate limiting.

## Best Possible Solution

Keep the existing transient-error attempt budget, add a rate-limit-specific schedule that honors structured Retry-After timing when available, retain a bounded fallback when it is absent, and prove both a successful live 429 recovery and unchanged sustained-5xx behavior.

## Solution Assessment

No. Differentiating rate limits is the right boundary, but globally increasing the shared retry count regresses every other retryable error; rate-limit-specific attempts or provider Retry-After timing are narrower and safer.

## Summary

Keep open: the 429 retry path is only partially fixed because retry-enabled provider POST helpers use a separate 5xx-only gate before the changed classifier can run; the new live proof is useful but does not exercise that caller boundary.

## What This Changes

The PR classifies structured and message-only HTTP 429 errors as transient provider-operation failures and adds two retry regression cases.

## Best Possible Solution

Use one canonical transient HTTP-status classifier across the retry loop and shared POST gate, retain the no-retry default for billable create operations, and cover a retry-enabled POST 429-to-200 flow.

## Solution Assessment

No, not yet: updating the generic classifier is necessary but leaves a parallel 5xx-only POST gate, so the narrow maintainable fix is to share one classifier and test the actual helper path.

Keep open. Current main does not implement the recovered-send replay guard, and the latest head is a focused fix with sufficient proof and no blocking line-level finding; because it changes outbound message recovery state ordering, it still needs maintainer review before merge.

## What This Changes

Adds recovery queue identifiers to outbound delivery params, marks recovered sends at platform-send start and `unknown_after_send` before ack, and adds regression tests for ack, marker, and commit-hook failure paths.

## Best Possible Solution

Land a focused recovery fix after maintainers accept the no-blind-replay state semantics and confirm the interaction with the broader ambiguous-row recovery policy.

## Reproduction Assessment

Yes at source level: current recovery sends an ordinary pending entry, then acks, then runs commit hooks without marking post-send ambiguity first; a thrown ack or bookkeeping failure goes through the retry path while the platform send may already have happened.

## Solution Assessment

Yes for the narrow bug: reusing the live-send platform-start marker and then marking `unknown_after_send` before ack is the right owner boundary. The remaining choice is maintainer acceptance of the exact recovery state used when the post-send marker write itself fails.

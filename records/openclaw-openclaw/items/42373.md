## Summary

Keep open: current main and the latest release still expose a USD-only model-cost/session-display contract with no `costCurrency` surface, but adding one is a new config and accounting/display product decision rather than a narrow bug fix.

## What This Changes

The issue requests a new `costCurrency` configuration option so model-cost displays can use non-USD currency symbols such as CNY or EUR.

## Best Possible Solution

Define one currency contract first, including scope, ISO-code versus symbol behavior, mixed-provider aggregation, and display-only versus accounting semantics, then update schema, types, docs, status, usage, UI, and persisted/API names together if maintainers accept the feature.

## Reproduction Assessment

Yes, source inspection is enough for the reported behavior: current main has no `costCurrency` implementation, model cost config is USD-only, and several cost display helpers hardcode `$`. This is not a runtime failure repro; it is a source-reproducible feature gap.

## Solution Assessment

No, not yet: a provider-level `costCurrency` option is plausible, but it is not proven best until maintainers decide currency scope and mixed-currency aggregation behavior. A safer implementation would update the config/accounting contract coherently rather than only swapping symbols in one formatter.

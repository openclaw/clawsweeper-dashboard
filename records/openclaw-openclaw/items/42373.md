## Summary

Keep open: current main and v2026.6.11 still lack a costCurrency config path, and the requested behavior changes public config plus local-cost accounting/display semantics that need maintainer product direction.

## What This Changes

The issue requests a costCurrency config option so configured model costs can display with non-USD currency symbols such as CNY or EUR.

## Best Possible Solution

Define one supported currency contract first: scope, ISO-code validation, mixed-currency behavior, display-only versus accounting semantics, persisted USD-field treatment, docs, and regression coverage.

Rationale: The source gap is clear, but choosing provider-level, model-level, or global currency semantics affects public config, status output, Control UI aggregation, telemetry names, docs, and provider-reported billing boundaries.

Options:

- **Design one currency contract first (recommended):** Choose scope, validation, mixed-currency aggregation, persisted-field semantics, and docs before implementation.
- **Keep configured estimates USD-only:** Leave models.providers.*.models[].cost as USD estimates and direct non-USD billing visibility to provider-reported usage surfaces.
- **Allow display-only override:** Permit a narrow symbol override while explicitly documenting that stored totals, telemetry, and aggregation remain local estimates rather than converted invoices.

## Reproduction Assessment

Yes, source-level: current main has no costCurrency key, strict config schemas reject that field, and local cost formatters still render dollar-prefixed estimates. This is a feature/config request rather than a broken existing behavior repro.

## Solution Assessment

Unclear until maintainers choose the contract. A provider-level costCurrency option is plausible, but a formatter-only fix would be too narrow because local estimates, provider billing, docs, UI aggregation, and telemetry currently have separate USD/unit semantics.

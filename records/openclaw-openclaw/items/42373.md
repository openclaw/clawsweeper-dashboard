- `maturity:stable`: The issue affects Gateway runtime status/operator cost display, and `gateway-runtime` is scored M4 Stable in the checked-in maturity scorecard.

## Summary

Keep open: current main and the latest release still encode configured model-cost estimates as USD, with no `costCurrency` config path; the remaining work is a public config and accounting-semantics product decision.

## What This Changes

Add a `costCurrency` option so configured model-cost estimates can display in a configured currency instead of always using USD.

## Best Possible Solution

Define one currency contract first: scope, ISO-code validation, mixed-currency behavior, display-only versus accounting semantics, persisted USD field treatment, docs, and regression coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw keep configured model costs USD-only, or define a non-USD currency contract for configured local/provider model pricing and cost display?

Rationale: The request changes public config and cost-accounting semantics across schema, status/chat output, Control UI, persisted USD-named fields, telemetry, and mixed-provider aggregation; automation should not choose that contract.

Likely owner: steipete

Owner reason: He has the strongest feature-history signal for usage-cost reporting and the provider-billing boundary this decision must coordinate with.

Owner confidence: high

Options:

- **Design one currency contract first (recommended):** Choose provider/model/global scope, ISO-code validation, mixed-currency behavior, persisted-field semantics, and docs before implementation.
- **Keep configured costs USD-only:** Leave `models.providers.*.models[].cost` as USD estimates and keep non-USD balances only in provider usage reporting.
- **Add display-only override:** Allow a narrow symbol/code override while documenting that stored totals and telemetry remain USD-like estimates.

## Reproduction Assessment

Yes, source-level: current main has no `costCurrency` config path, the strict model cost schema has no currency field, and cost display still uses USD formatters. This is a feature/config request rather than a broken existing behavior contract.

## Solution Assessment

Unclear until maintainers choose the contract. A provider-level `costCurrency` is plausible, but a formatter-only fix would be too narrow because stored fields, telemetry, docs, and mixed-provider totals currently encode USD semantics.

## Summary

Keep open: current main and the latest release still treat configured model costs as USD and have no `costCurrency` config surface, but adding one is a new cross-surface cost/accounting contract that needs maintainer product direction.

## What This Changes

Add a configuration option for choosing the currency used when displaying configured model costs.

## Best Possible Solution

Define one explicit model-cost currency contract first, including scope, ISO-code versus symbol behavior, mixed-currency aggregation, and display-only versus accounting semantics, then update schema, types, docs, status, usage, UI, and tests together.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support non-USD configured model costs, and if so should currency live per model, per provider, globally, or only as a display preference?

Rationale: The request adds a high-bar config surface and changes cost semantics across status output, usage aggregation, UI display, persisted USD fields, and provider billing concepts that code cannot safely infer.

Likely owner: steipete

Owner reason: They have the strongest current history across the USD model cost contract, cost summaries, status formatting, and provider usage surfaces.

Owner confidence: high

Options:

- **Define full currency contract (recommended):** Choose scope, units, aggregation behavior, and storage/display semantics before implementation so cost surfaces remain consistent.
- **Keep model costs USD-only:** Leave configured model pricing as USD estimates and rely on provider usage hooks for non-USD account balances until demand or design is stronger.
- **Add display-only preference:** Allow a narrow symbol preference while explicitly preserving `estimatedCostUsd` as USD-like estimate data and accepting mixed-currency ambiguity.

## Reproduction Assessment

Yes for source-level verification, not as a failing bug repro. Current main has no `costCurrency` match, strict model/provider schemas have no currency slot, and status/usage formatters still render USD-style costs.

## Solution Assessment

No, the proposed provider-level `costCurrency` knob is only one plausible shape. The best fix needs a maintainer decision on scope and mixed-currency semantics before a code change.

## Label Justifications

- `P2`: This is a meaningful protocol and performance improvement for large-file clients, but it does not regress existing inline attachment workflows or block ordinary first-run usage.
- `impact:other`: The issue concerns large-file transport efficiency and WebSocket payload exhaustion, which is maintainer-visible impact outside the more specific owned impact categories.

## Summary

Keep open: current main still carries `chat.send` attachment bytes inside JSON WebSocket frames, while media-store offloading occurs only after the Gateway receives the request, so already-uploaded large files can still exceed the negotiated payload limit. The feature direction is valid, but the authority, lifecycle, and security contract for references needs maintainer design approval.

## What This Changes

Add an additive `chat.send` attachment-reference form so clients can send an authenticated object handle instead of retransmitting file bytes as inline Base64.

## Best Possible Solution

Define an additive inline-or-reference attachment union where references are opaque, authenticated Gateway-owned asset handles created by a bounded upload/staging API, with size, MIME, hash, ownership, expiry, cleanup, and single-resolution semantics documented and tested.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw standardize Gateway-owned staged asset handles for `chat.send`, expose a namespaced plugin resolver contract for external object stores, or keep the protocol inline-only?

Rationale: The code can add a union mechanically, but only maintainers can choose the durable ownership and trust boundary shared by WebChat, native clients, third-party clients, plugins, and remote Gateways.

Likely owner: steipete

Owner reason: This choice spans the public Gateway contract, core storage ownership, security posture, and all first-party clients, matching the project-level gateway decision role.

Owner confidence: medium

Options:

- **Gateway-owned asset handles (recommended):** Add an authenticated upload or chunk-staging surface and let `chat.send` reference only opaque assets owned and validated by the receiving Gateway.
- **Namespaced resolver contract:** Let trusted plugins register reference namespaces and resolvers, accepting greater API and security complexity to support external object stores directly.
- **Retain inline transport:** Keep Base64 attachments as the only `chat.send` contract and document payload limits rather than expanding the protocol and storage lifecycle.

## Reproduction Assessment

No live 52 MB reproduction was run, but the source-level path is high-confidence: attachments are encoded into a JSON WebSocket request before Gateway media offloading, so a frame larger than the negotiated limit is rejected before `chat.send` processing.

## Solution Assessment

No, not as an unrestricted `objectId`: the additive reference direction is sound, but the narrowest maintainable design is an authenticated Gateway asset handle or an explicitly approved resolver namespace rather than an ambiguous external-store identifier.

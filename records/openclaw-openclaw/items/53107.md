## What This Changes

Request adds optional cron job tags/categories for organization, filtering, UI/CLI exposure, and possible bulk operations.

## Best Possible Solution

Define one additive cron classification/display metadata contract, then wire persistence, RPC/API filtering, CLI/UI presentation, accepted bulk operations, tests, and docs around that shared model.

Question: Should cron classification be modeled as freeform job tags, typed purpose/display metadata, or a plugin-owned classification seam?

Rationale: Current main lacks the requested capability, but the durable API shape affects persisted cron state, Gateway protocol, CLI/UI filters, reminders, and plugin scheduling behavior, so automation should not choose the product contract alone.

Likely owner: vincentkoc

Owner confidence: medium

Options:

- **Use typed metadata (recommended):** Design a narrow typed purpose/display metadata contract that can cover reminders and system/user/project jobs without creating opaque plugin-owned blobs.
- **Add freeform tags:** Add an optional normalized tags array to cron jobs and expose tag filtering consistently across storage, RPC/API, CLI, UI, tests, and docs.
- **Defer to plugin seam:** Keep core cron schema lean and first extend plugin hooks/API only if classification can be owned outside core without losing filtering support.

## Reproduction Assessment

Yes for the capability gap. Source inspection on current main shows no supported cron tag/category field, tag-aware cron.list filter, CLI list exposure, or Control UI tag filter.

## Solution Assessment

Unclear as proposed. Freeform tags are plausible, but maintainers should choose the shared cron classification/display metadata model first so reminders, plugin scheduling, CLI, API, and UI do not diverge.

## Summary

Keep open: current main and v2026.6.11 still lack a supported cron tags/categories contract, tag-aware cron listing, CLI exposure, and Control UI tag filters. The overlapping Reminders issue is narrower, and the prior opaque metadata PR was closed unmerged because cron metadata needs owner-reviewed API/protocol design.

## What This Changes

Request optional freeform tags/categories for cron jobs, with persistence, list/API/UI exposure, filtering, and possible tag-based bulk enable/disable.

## Best Possible Solution

Define one additive cron classification/display metadata contract, then wire persistence, RPC/API filtering, CLI/UI presentation, accepted bulk operations, tests, and docs around that shared model.

Owner confidence: high

Options:

- **Use typed classification metadata (recommended):** Design a narrow typed purpose/display metadata contract that can cover reminders and system/user/project jobs without creating opaque plugin-owned blobs.
- **Add freeform tags:** Add an optional normalized tags array to cron jobs and expose tag filtering consistently across storage, RPC/API, CLI, UI, tests, and docs.
- **Defer to plugin seam:** Keep core cron schema lean and first extend plugin hooks/API only if classification can be owned outside core without losing filtering support.

## Reproduction Assessment

Yes for the capability gap: current main has no supported cron tag/category field, tag-aware cron.list filter, CLI list exposure, or Control UI tag filter. This is a feature request rather than a failing-runtime bug reproduction.

## Solution Assessment

Unclear as proposed. Freeform tags are plausible, but maintainers should choose the shared cron classification/display metadata model first so reminders, plugin scheduling, CLI, API, and UI do not diverge.

## Summary

Keep open: this is useful CLI resource-exhaustion hardening and the PR body now includes real terminal proof, but the helper still delegates accepted input to `FileHandle.readFile`, so the actual read is not capped against a regular file that changes after the helper's size check.

## What This Changes

The PR adds `readFileWithBound` for `openclaw approvals set --file`, routes the set command through it, and adds tests for static oversized and non-regular file inputs.

## Best Possible Solution

Read at most `maxBytes + 1` bytes from the opened regular file handle, preserve the non-regular-file rejection, add a growth-after-stat regression, and have maintainers accept or adjust the new `--file` size cap before merge.

## Reproduction Assessment

Yes. Source inspection shows current main uses an unbounded `fs.readFile` for `--file`, and the PR head still calls `FileHandle.readFile` after the guard; I did not run tests because this review was read-only.

## Solution Assessment

No. Opening the fd before stat is a good partial fix for path swaps and non-regular files, but the best fix is a byte-limited read from the opened handle before JSON parsing.

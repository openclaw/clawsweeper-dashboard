## Summary

Keep open: current main and the latest release still read `approvals set --file` with an unbounded `fs.readFile`, while this PR adds a focused bounded reader with no blocking patch defects found. The remaining question is maintainer acceptance of the stricter public CLI input contract before merge.

## What This Changes

The PR replaces the approvals `set --file` read with an fd-based bounded regular-file reader and adds helper coverage for small, oversized, directory, and FIFO inputs.

## Best Possible Solution

Land the bounded reader once maintainers accept the regular-file-only, 1 MiB `--file` contract, or add docs/help before merge if that contract should be explicit.

## Reproduction Assessment

Yes from source inspection: current main and `v2026.6.11` read the `--file` path with unbounded `fs.readFile`, while the stdin sibling already enforces a byte cap. I did not run an OOM repro in the read-only checkout.

## Solution Assessment

Yes, with a compatibility caveat: reading through the opened fd with a `maxBytes + 1` loop is the narrow fix for the OOM path and prior non-regular-file bypasses. The remaining decision is whether maintainers accept or document the new regular-file-only, 1 MiB `--file` policy.

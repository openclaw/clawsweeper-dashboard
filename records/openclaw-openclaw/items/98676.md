## Summary

The latest PR head resolves the prior bounded-read correctness blocker by reading at most `maxBytes + 1` from the opened regular file handle. It should stay open for maintainer review because the new 1 MiB `--file` cap is a compatibility-sensitive CLI behavior change.

## What This Changes

The PR adds a byte-limited `readFileWithBound` helper for `openclaw approvals set --file`, uses it instead of `fs.readFile`, and adds focused file-bound tests.

## Best Possible Solution

Land after maintainers accept the stdin-aligned 1 MiB file-input cap as the intended compatibility and safety tradeoff, or adjust the cap/docs before merge.

## Reproduction Assessment

Yes, source-reproducible. Current main and the latest release read `--file` with unbounded `fs.readFile`, while the sibling stdin path already enforces a byte cap.

## Solution Assessment

Yes, with one maintainer decision. The helper is now placed at the narrow CLI ingestion boundary, preserves the parse/save path, and uses Node's bounded `FileHandle.read` primitive instead of a full-file read.

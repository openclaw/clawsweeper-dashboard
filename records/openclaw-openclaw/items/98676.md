## Summary

Keep this PR open: the resource-exhaustion fix is useful and well targeted, but the new single-read helper can parse a truncated file on short reads, and the new hard cap still needs maintainer acceptance as an upgrade-visible CLI behavior change.

## What This Changes

The PR adds a byte-limited file reader for `openclaw approvals set --file`, replaces the unbounded `fs.readFile` path, and adds focused tests for small, oversized, and non-regular file inputs.

## Best Possible Solution

Fix the bounded reader to loop until EOF or `maxBytes + 1` without exceeding the cap, then land only if maintainers accept the stdin-aligned 1 MiB `--file` limit or adjust the limit/docs first.

## Reproduction Assessment

Yes. Current main and `v2026.6.11` route `openclaw approvals set --file` through unbounded `fs.readFile`, while the sibling stdin path has a byte cap; the short-read issue is source-proven from Node's `FileHandle.read` contract.

## Solution Assessment

No, not quite. The CLI ingestion boundary is the right place for the fix, but the helper should loop until EOF or the cap instead of assuming one `FileHandle.read` returns the complete bounded file.

- **[P2] Read bounded files until EOF before parsing:** `src/cli/exec-approvals-cli.ts:94`
  - body: This returns after a single `fd.read(...)`, but Node treats `length` as the maximum attempt and reports the actual `bytesRead`; it can be lower than requested, so a valid approvals file can be parsed truncated on a slow or short-read filesystem.

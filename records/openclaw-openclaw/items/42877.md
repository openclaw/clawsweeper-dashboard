## Summary

Keep open. Current main and the latest release still expose memory recall/read plus narrower memory-flush and dreaming-promotion bounds, but not the requested first-class bounded memory CRUD/write contract; this remains a product, security, and API decision.

## What This Changes

The issue requests a built-in bounded memory write tool with hard per-store character limits, add/replace/remove operations, duplicate handling, snapshot injection, and optional credential-pattern blocking.

## Best Possible Solution

Define an approved memory-core bounded CRUD/write contract with explicit hard-limit behavior, target-store model, selection identity, duplicate/consolidation policy, secret handling, docs, and tests before implementation.

## Maintainer Decision

Required: true

Rationale: Source inspection shows the requested capability is still missing, but adding it would create public memory-write, config, persistence, and security behavior that cannot be safely chosen by automation.

Likely owner: steipete

Owner confidence: high

Options:

- **Define bounded memory-core CRUD (recommended):** Add an approved add/list/replace/remove or unified memory tool with hard per-store limits, usage feedback, stable identity, duplicate/consolidation behavior, secret policy, docs, and regression coverage.
- **Narrow to flush and visibility first:** Continue with existing memory-flush/dreaming bounds plus UI or startup warnings while leaving general CRUD writes out of the default memory tool surface for now.
- **Prototype the contract outside core first:** Use a memory plugin or operator-facing prototype to prove the write API and safety policy before promoting it into the default memory-core contract.

Unclear as an immediate implementation. A bounded memory tool is plausible, but the best fix needs maintainer choices on API shape, per-store limits, replacement identity, duplicate/consolidation, snapshots, and secret-safety behavior.

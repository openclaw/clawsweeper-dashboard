## Label Justifications

- `P1`: The report describes a post-upgrade sandbox startup failure that breaks real maker session command execution for affected Docker hosts.
- `impact:security`: The remaining fix choice is about whether and how to relax Docker `no-new-privileges`, a sandbox hardening boundary.

## Summary

Keep open: current main and the latest release still hard-code Docker `--security-opt no-new-privileges` for sandbox containers, there is no supported opt-out or targeted startup recovery path, and the direct fix PR was closed unmerged. The report remains actionable, but choosing an opt-out or fallback changes the sandbox security boundary and needs maintainer direction.

## What This Changes

The issue asks OpenClaw to recover from or clearly diagnose Docker sandbox startup failures when `--security-opt no-new-privileges` makes the sandbox `sleep infinity` process fail with EPERM.

## Best Possible Solution

Keep the secure default, then add a maintainer-approved dangerous recovery path with clear doctor/status diagnostics, security-audit reporting, docs, and Docker behavior proof for the incompatible-host case.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw allow Docker sandbox startup recovery by exposing an explicit dangerous `no-new-privileges` opt-out, by using diagnostic-only guidance, or by silently falling back after EPERM?

Rationale: The code fix is straightforward, but the policy choice changes sandbox hardening and cannot be safely chosen by cleanup automation.

Likely owner: Peter Steinberger

Owner reason: Recent commits show ownership of sandbox Docker create-args and dangerous override handling, which are the central decision surfaces here.

Owner confidence: high

Options:

- **Explicit dangerous opt-out with diagnostics (recommended):** Add a named opt-out that defaults to secure behavior, reports as dangerous in security/doctor output, and requires real Docker proof for both default and opt-out modes.
- **Diagnostic-only recovery:** Keep the hardening flag unconditional and improve status/session/doctor messages so affected operators can identify the host-level Docker incompatibility without weakening OpenClaw defaults.
- **Automatic fallback after EPERM:** Retry without the hardening flag on the specific startup failure, accepting that users may run with a weaker sandbox unless the fallback is made highly visible.

## Reproduction Assessment

Yes at source/report level: current main unconditionally creates Docker sandbox containers with `--security-opt no-new-privileges`, and the reporter's minimal Docker matrix isolates EPERM to that flag. I did not rerun the failing Docker host locally.

## Solution Assessment

Unclear until maintainers choose the security posture. The closed opt-out PR was a plausible narrow mitigation, but the best durable fix should make any hardening downgrade explicit, diagnosable, audited, documented, and proven on a real Docker host.

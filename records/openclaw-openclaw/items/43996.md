## Best Possible Solution

Add an explicit, well-labeled operator-controlled recovery path that keeps the secure default, surfaces the weaker sandbox posture in doctor/security reporting, and provides a clear diagnostic when Docker rejects `no-new-privileges`.

Question: Should OpenClaw allow Docker sandbox containers to start without `no-new-privileges` on hosts where that hardening flag prevents even `/usr/bin/sleep` from execing?

Rationale: The report is actionable, but the fix is a security-boundary product choice: a silent fallback improves availability but weakens hardening, while fail-closed preserves security but leaves affected sandboxes unusable.

Likely owner: steipete

Owner reason: They introduced the current Docker sandbox create-args path and have recent adjacent sandbox maintenance history.

Owner confidence: high

Options:

- **Explicit opt-out with warnings (recommended):** Keep `no-new-privileges` as the default, add a dangerous config opt-out, and report the weaker posture through doctor/security diagnostics.
- **Fail closed with better diagnostics:** Keep the hardening mandatory and improve status/session errors so affected operators can identify the Docker host incompatibility without patching dist output.
- **Automatic retry fallback:** Retry container startup without the flag only for the detected EPERM failure, accepting more availability risk and requiring careful audit visibility.

## Reproduction Assessment

Yes at source/report level: the issue includes a minimal Docker matrix where only `--security-opt no-new-privileges` fails, and current main still always emits that flag. I did not run the exact Docker 28/29 Ubuntu host live.

## Solution Assessment

Unclear until maintainers choose the security posture. The narrowest maintainable path appears to be a secure default plus explicit dangerous opt-out and diagnostics, while a silent fallback would be riskier.

## Summary

Keep open: current main and the latest release still always add Docker `--security-opt no-new-privileges` to sandbox containers, there is no supported opt-out or targeted recovery path, and the direct fix PR was closed unmerged. The report is actionable, but the recovery model changes a sandbox security boundary and needs maintainer direction.

## What This Changes

The issue asks for a Docker sandbox recovery path when OpenClaw's `no-new-privileges` container flag makes sandbox containers exit with EPERM.

## Best Possible Solution

Keep `no-new-privileges` enabled by default, then add a maintainer-approved recovery path with dangerous-config reporting, clear operator diagnostics, and real Docker proof on an affected host.

Question: Should OpenClaw support a Docker sandbox recovery path for hosts where `--security-opt no-new-privileges` prevents even `/usr/bin/sleep` from execing?

Rationale: The bug is well isolated, but removing or falling back from `no-new-privileges` changes the Docker sandbox boundary and repository policy requires explicit operator-controlled security tradeoffs rather than silent compatibility fallback.

Likely owner: Peter Steinberger

Owner reason: Peter has the strongest recent history on sandbox dangerous-override and Docker create-args patterns that this decision would extend.

Owner confidence: high

Options:

- **Add explicit dangerous opt-out (recommended):** Keep the secure default, add a clearly named `sandbox.docker` opt-out with dangerous-config reporting, docs, tests, and real Docker proof for the incompatible-host case.
- **Diagnostic-only recovery:** Keep the hardening unconditional and improve startup/session/doctor errors so affected hosts get a precise explanation and mitigation guidance without weakening the sandbox.
- **Unsupported host stance:** Treat Docker hosts that reject `no-new-privileges` as unsupported for Docker sandbox mode and direct users to another sandbox backend or host configuration.

## Reproduction Assessment

Yes at source/report level: the reporter’s Docker matrix shows the image failing only when `--security-opt no-new-privileges` is present, and current main always emits that flag. I did not rerun the affected host locally.

## Solution Assessment

Unclear until the security decision is made. The best narrow mitigation appears to be an explicit dangerous opt-out with secure default and reporting; a silent automatic fallback would be riskier because it weakens sandbox hardening without operator intent.

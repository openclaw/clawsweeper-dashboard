## Summary

Keep open: current main and the latest release still unconditionally add Docker `--security-opt no-new-privileges` when creating sandbox containers, the reported host-level Docker repro remains consistent with that source path, and the only direct fix PR is closed unmerged. The remaining choice is security-sensitive because any opt-out or fallback can weaken sandbox hardening.

## What This Changes

The issue asks for Docker sandbox sessions to recover on hosts where `--security-opt no-new-privileges` makes `/usr/bin/sleep` fail, via an opt-out, fallback, or clearer diagnostics.

## Best Possible Solution

Keep the secure default, then add a maintainer-approved audited path for incompatible Docker hosts, such as an explicit dangerous opt-out with reporting and real Docker proof, or choose diagnostic-only handling if weakening the boundary is unacceptable.

Options:

- **Add explicit dangerous opt-out (recommended):** Keep `no-new-privileges` default-on, add a clearly named opt-out with dangerous-config/status reporting, docs, tests, and real Docker proof on an affected or equivalent host.
- **Diagnostics only:** Keep the flag unconditional and improve startup/session/status errors so operators can identify the incompatible Docker host and choose a different runtime or version.
- **Reject weaker sandbox mode:** Do not add an opt-out or fallback, and close only after maintainers decide this host combination is outside the supported sandbox hardening envelope.

## Solution Assessment

Unclear: an explicit default-on dangerous opt-out is the narrowest mitigation if maintainers accept the security tradeoff, while a silent fallback would be riskier. Maintainers still need to choose between opt-out, image/runtime compatibility work, diagnostic-only behavior, or rejecting the weaker mode.

## Summary

Keep open: current `main` and `v2026.6.11` still create Docker sandbox containers with `--security-opt no-new-privileges`, there is no supported `noNewPrivileges` opt-out or targeted EPERM recovery path, and the direct fix PR is closed unmerged. The report is actionable, but the recovery model affects sandbox hardening and needs maintainer direction.

## What This Changes

The issue requests a supported recovery path for Docker sandbox containers that fail to start when `--security-opt no-new-privileges` triggers `exec /usr/bin/sleep: operation not permitted`.

## Best Possible Solution

Keep `no-new-privileges` enabled by default, then add a maintainer-approved recovery path with dangerous-config reporting, clear operator diagnostics, and real Docker proof on an affected host.

Rationale: The bug is well isolated, but disabling or falling back from `no-new-privileges` changes the Docker sandbox boundary, and repository policy requires explicit operator-controlled security tradeoffs rather than silent compatibility fallback.

Options:

- **Add explicit dangerous opt-out (recommended):** Keep the secure default, add a clearly named `sandbox.docker` opt-out with dangerous-config reporting, docs, focused tests, and real Docker proof for the incompatible-host case.
- **Improve diagnostics only:** Keep the hardening unconditional and surface a precise startup/session/doctor error for this EPERM mode without weakening the sandbox.
- **Document unsupported host stance:** Treat Docker hosts that reject `no-new-privileges` as unsupported for Docker sandbox mode and direct users to host repair or another sandbox backend.

## Reproduction Assessment

Yes at source/report level: the reporter’s Docker matrix shows the image failing only when `--security-opt no-new-privileges` is present, and current `main` always emits that flag. I did not rerun the affected Docker/kernel combination locally.

## Solution Assessment

Unclear until the security decision is made. The best narrow mitigation appears to be an explicit dangerous opt-out with secure default and reporting; a silent automatic fallback would be riskier because it weakens sandbox hardening without operator intent.

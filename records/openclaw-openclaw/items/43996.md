## Summary

Keep open: current main and the latest release still unconditionally pass Docker `--security-opt no-new-privileges` to sandbox containers, there is no supported opt-out or targeted fallback/diagnostic, and the direct fix PR was closed unmerged. The report is actionable, but recovery changes a sandbox security boundary and needs maintainer direction.

## What This Changes

The issue asks for a recovery path when Docker `no-new-privileges` makes sandbox containers exit with EPERM before basic commands can run.

## Best Possible Solution

Keep the secure default, then add a maintainer-approved recovery path with dangerous-config reporting, clear operator diagnostics, and real Docker proof on an affected host.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a Docker sandbox recovery path for hosts where `no-new-privileges` prevents even `/usr/bin/sleep` from execing, and should that path be an explicit dangerous opt-out, diagnostic-only guidance, or another security-reviewed fix?

Rationale: The observable bug is real, but disabling or falling back from `no-new-privileges` changes the Docker sandbox boundary and AGENTS/VISION policy requires explicit, operator-controlled security tradeoffs rather than silent compatibility fallbacks.

Likely owner: steipete

Owner reason: Peter Steinberger has the strongest recent history on sandbox security/config override patterns that this decision would extend.

Owner confidence: high

Options:

- **Add explicit dangerous opt-out (recommended):** Keep `no-new-privileges` enabled by default, add a clearly named config key with dangerous-config reporting, docs, tests, and real Docker proof for the incompatible-host case.
- **Diagnostic-only handling:** Keep the hardening unconditional and improve startup/session/doctor errors so affected hosts get a precise explanation and mitigation guidance without weakening the sandbox.
- **Reject opt-out:** Treat hosts where Docker rejects `no-new-privileges` as unsupported for Docker sandbox mode and direct users to another sandbox backend or host configuration.

## Reproduction Assessment

Yes at source/report level: the reporter’s Docker matrix shows `docker run --security-opt no-new-privileges openclaw-sandbox:bookworm-slim /usr/bin/sleep 1` failing while the same image works without that flag, and current main always emits the flag. I did not rerun the affected host locally.

## Solution Assessment

Unclear until the security decision is made. The best narrow fix appears to be an explicit dangerous opt-out with secure default and reporting; a silent automatic fallback would be riskier because it weakens sandbox hardening without operator intent.

## Label Justifications

- `P1`: A real user reports Docker sandbox sessions failing immediately after upgrade, which breaks an agent execution workflow and involves a security-sensitive sandbox default.
- `impact:security`: The issue centers on Docker sandbox hardening with `no-new-privileges`, and any opt-out or fallback may change the sandbox security boundary.
- `impact:crash-loop`: The sandbox container exits immediately with code 255, leaving session commands unable to run.

## Summary

Keep open: current main and the latest release still create Docker sandbox containers with `--security-opt no-new-privileges`, there is no supported config or fallback path to disable it, and the only direct fix PR is closed unmerged. The report remains actionable, but the fix needs maintainer security/product judgment because the obvious opt-out weakens sandbox hardening.

## What This Changes

The issue requests a fix for Docker sandbox containers exiting immediately on hosts where Docker `no-new-privileges` makes even `/usr/bin/sleep` fail with EPERM.

## Best Possible Solution

Keep the secure default, then add a maintainer-approved audited path for incompatible Docker hosts, such as an explicit dangerous opt-out with reporting, an image/runtime compatibility fix, or diagnostics that explain the host failure without silently weakening isolation.

## Reproduction Assessment

Yes, at source/report level: on the affected host, the reporter's Docker matrix shows `--security-opt no-new-privileges` is the minimal failing trigger, and current main still always passes that flag. I did not rerun the host-specific EPERM locally, so this is source-reproducible rather than locally reproduced.

## Solution Assessment

Unclear: a config opt-out is a plausible narrow mitigation, but it weakens sandbox hardening, and a silent fallback would be riskier. The best fix needs maintainer choice between image/runtime compatibility work, an explicit dangerous override with reporting, fallback behavior, or diagnostic-only handling.

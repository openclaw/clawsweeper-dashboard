## Summary

Keep open: current main and the latest release still unconditionally create Docker sandbox containers with `--security-opt no-new-privileges`, there is no supported opt-out or fallback path, and the direct fix PR is closed unmerged. The report remains actionable, but the fix needs maintainer security/product judgment because restoring the affected host can weaken sandbox hardening.

## What This Changes

The issue reports Docker sandbox startup failure when OpenClaw passes `--security-opt no-new-privileges` and asks for a supported opt-out, fallback retry, or clearer diagnostic path.

## Best Possible Solution

Keep the secure default, then add a maintainer-approved audited path for incompatible Docker hosts, such as an explicit dangerous opt-out with reporting, an image/runtime compatibility fix, or diagnostics that explain the host failure without silently weakening isolation.

## Reproduction Assessment

Yes, at source/report level: on the affected host, the reporter's Docker matrix shows `--security-opt no-new-privileges` is the minimal failing trigger, and current main still always passes that flag. I did not rerun the host-specific EPERM locally, so this is source-reproducible rather than locally reproduced.

## Solution Assessment

Unclear: a config opt-out is a plausible narrow mitigation, but it weakens sandbox hardening, and a silent fallback would be riskier. The best fix needs maintainer choice between image/runtime compatibility work, an explicit dangerous override with reporting, fallback behavior, or diagnostic-only handling.

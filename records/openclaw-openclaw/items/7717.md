## Summary

Keep open: current main still lacks configured Discord role-mention wake triggers, and this remains a distinct opt-in feature whose multi-agent fan-out semantics need maintainer approval.

## What This Changes

Add configurable Discord role IDs that count as wake signals for mention-gated agents at guild or channel scope.

## Best Possible Solution

Add a distinct opt-in role-ID trigger list at Discord guild and channel scope, preserving direct mentions, replies, sender authorization, other-mention filtering, routing, and bot-loop protection with aligned schema, docs, and tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should selected Discord role IDs be allowed to wake every eligible agent receiving that role mention, and should this policy be configurable at both guild and channel scope?

Rationale: The implementation boundary is clear, but multi-agent fan-out changes intentional trigger policy, operating cost, and loop exposure while adding a compatibility-sensitive configuration surface.

Likely owner: steipete

Owner reason: The prior review identifies this as a product-policy decision, and steipete is the strongest available history-backed routing candidate for that choice.

Owner confidence: high

Options:

- **Add opt-in role triggers (recommended):** Introduce a distinct guild/channel role-ID allowlist for wake targeting while retaining direct bot mentions as the default behavior.
- **Support managed bot roles only:** Treat only each bot's Discord-managed role as equivalent to its direct user mention, addressing autocomplete ambiguity without general role fan-out.
- **Keep direct mentions only:** Decline role-based wake fan-out and continue requiring direct bot mentions, replies, or configured textual mention patterns.

## Reproduction Assessment

Not applicable as a bug reproduction: current behavior intentionally recognizes other wake signals but does not define selected role mentions as supported wake targets.

## Solution Assessment

Yes, with refinement: a separate opt-in role-ID trigger list is the narrowest maintainable approach; automatic role fan-out or reusing sender roles would create policy and authorization ambiguity.

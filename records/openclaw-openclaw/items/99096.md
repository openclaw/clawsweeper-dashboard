## Best Possible Solution

Review and land the focused linked PR, or replace it with an equivalent source-level fix that reuses the existing leading-status parser without adding new config or broader retry policy.

Yes at source level: the reported `429 Provider returned error` lacks short-window wording and Retry-After, so the current gate returns null before the same-model retry path. I did not run a live provider repro, but the issue body includes matching live deployment logs.

## Solution Assessment

Yes: reusing `extractLeadingHttpStatus` inside the existing short-window gate after long-window filters is the narrowest maintainable fix. The best next action is to review and land the linked PR or an equivalent gate-only patch.

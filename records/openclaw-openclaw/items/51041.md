## Summary

Keep open: current main and the latest release still expose Discord plugin slash commands as a generic `PluginCommandContext` plus one returned `PluginCommandResult`; interaction-level `defer`, `reply`, `followUp`, and `editReply` primitives exist inside the Discord runtime but are not exposed to command handlers. This remains useful, but it changes the public plugin SDK and Discord command-routing contract, so it needs maintainer API direction rather than cleanup closure.

## What This Changes

Request to expose Discord interaction-level response controls to plugin command handlers for mixed ephemeral and visible slash-command flows.

## Best Possible Solution

Add a narrow, documented plugin-command responder or channel capability with a Discord implementation, while preserving current returned-payload behavior and command authorization/routing.

## Reproduction Assessment

Yes, at source level: current main still types plugin command handlers as `PluginCommandContext` plus one returned `PluginCommandResult`, and the Discord native command path only delivers that returned payload. I did not run live Discord because the missing public API is directly visible in the type and dispatch path.

## Solution Assessment

Unclear. A responder capability is the right class of solution, but maintainers should choose whether the permanent SDK surface is generic or Discord-specific before implementation.

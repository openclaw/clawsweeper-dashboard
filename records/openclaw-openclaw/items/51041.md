## Label Justifications

- `P2`: This is a bounded Discord/plugin SDK capability gap with source-level proof, but it is not an urgent production regression or setup blocker.
- `impact:message-loss`: Discord plugin commands cannot currently send a private slash acknowledgement plus a visible follow-up, so intended command output can be hidden from the conversation.
- `maturity:stable`: The issue affects the Discord channel surface, which `qa/maturity-scores.yaml` lists as M4 Stable.

## Summary

Keep open: current main and the latest release still route Discord plugin slash commands through a generic `PluginCommandContext` plus one returned `PluginCommandResult`, while Discord reply/follow-up/edit primitives remain internal to the Discord runtime and interactive-handler paths. The request is still valid, but it changes a public plugin SDK/channel contract and needs maintainer API direction rather than cleanup closure.

## What This Changes

Expose Discord interaction-level defer, reply, follow-up, and edit controls to plugin command handlers so handlers can mix private slash acknowledgements with visible follow-ups.

## Best Possible Solution

Add a narrow documented plugin-command responder or channel capability, preferably generic with a Discord implementation, while preserving returned-`ReplyPayload` compatibility and existing authorization/routing behavior.

- **Add generic responder capability (recommended):** Define a narrow documented command responder/capability that Discord implements first and other native-command channels can adopt later.
- **Add Discord-specific context:** Expose `ctx.discord.respond` for the immediate Discord use case, accepting a channel-specific public SDK surface.
- **Decline SDK expansion:** Keep plugin commands on returned `ReplyPayload` only and require plugin authors to build external Discord-specific workarounds.

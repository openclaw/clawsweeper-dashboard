## Summary

Keep open: current main and v2026.6.11 still route Discord plugin slash commands through the generic plugin command context and a single returned reply payload, while Discord interaction defer, follow-up, reply, and edit primitives remain internal to the Discord plugin runtime. The request is valid and aligned with the plugin API direction, but it needs maintainer API-shape approval before implementation.

## What This Changes

The issue requests Discord-specific responder controls on plugin command contexts so command handlers can defer, reply, follow up, and edit slash-command responses.

## Best Possible Solution

Choose a narrow plugin SDK responder contract that preserves command auth and routing, exposes Discord interaction primitives through a transport-scoped capability, and adds Discord native-command tests and docs for both the old return-payload path and mixed ephemeral/follow-up flow.

Question: Should OpenClaw add a Discord-specific command responder on PluginCommandContext, or design a generic channel responder capability for plugin commands?

Rationale: The missing capability is real, but either path expands the public Plugin SDK and channel boundary; automation cannot choose the permanent API shape or auth/routing constraints safely.

Likely owner: steipete

Owner reason: Recent blame and history put steipete on the current PluginCommandContext and Discord native-command implementation, and this choice is a public SDK boundary decision.

Owner confidence: high

Options:

- **Add a generic responder capability (recommended):** Expose a narrow capability-gated responder contract that Discord can implement for defer, reply, follow-up, and edit while preserving the existing returned ReplyPayload fallback for all plugins.
- **Add Discord-only ctx.discord.respond:** Ship the user-requested Discord-specific shape faster, accepting an owner-specific SDK surface that may need later generalization for Slack or other native command channels.
- **Keep the current return-payload model:** Decline per-interaction response controls for plugin commands, keeping the SDK smaller but leaving mixed visibility and edit flows unsupported for Discord plugins.

Yes. Source inspection shows PluginCommandContext and executePluginCommand do not expose responder methods, while the Discord interaction wrapper already has defer, reply, followUp, and editReply internally.

## Solution Assessment

Unclear until maintainer API direction is chosen. The proposed ctx.discord.respond shape is plausible, but a generic channel responder capability may be the more maintainable SDK boundary.

## Summary

Keep open: current main and the latest release still expose Discord plugin slash commands as a generic `PluginCommandContext` plus one returned `PluginCommandResult`, while Discord interaction reply/follow-up/edit primitives are only available inside Discord runtime and interactive-callback paths. This remains useful work, but it changes a public plugin SDK/channel contract and needs maintainer API direction rather than cleanup closure.

## What This Changes

The issue requests Discord-specific defer, reply, follow-up, and edit-reply controls in plugin command handlers so plugins can mix ephemeral and visible slash-command responses.

## Best Possible Solution

Add a narrow, documented plugin-command responder or channel capability with a Discord implementation, while preserving current returned-payload behavior and command authorization/routing.

## Reproduction Assessment

Yes, at source level: current main still types plugin command handlers as `PluginCommandContext` plus one returned `PluginCommandResult`, and the Discord native command path only delivers that returned payload. I did not run live Discord because the missing public API is directly visible in the type and dispatch path.

## Solution Assessment

Unclear. A responder capability is the right class of solution, but maintainers should choose whether the permanent SDK surface is generic or Discord-specific before implementation.

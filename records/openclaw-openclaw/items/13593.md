## Label Justifications

- `P2`: The issue is a normal-priority reliability/observability improvement for cron failures with limited blast radius but meaningful production impact.
- `impact:message-loss`: Silent cron execution failures can suppress scheduled agent/channel work without an operator-visible warning.
- `impact:session-state`: The related failure mode involves cron run state advancing or remaining healthy-looking while execution state does not match reality.

## Summary

Keep open: current `main` still only partially covers cron failure observability. It has cron state counters, durable run history, and generic health/readiness probes, but the requested cron-specific runtime outcome logs, cron-aware health/readiness decision, and unhealthy `openclaw cron list` warnings remain missing enough that this issue is still useful for maintainer coordination.

## What This Changes

Request adding cron execution logging, health reporting, and CLI warnings so failed, skipped, overdue, or apparently healthy-but-not-running cron jobs are visible.

## Best Possible Solution

Add coordinated cron observability that logs bounded structured outcomes for scheduled, catch-up, and manual runs, warns for skipped and non-throwing failure results, exposes cron health through the maintainer-chosen probe surface, and annotates cron list output for overdue or repeatedly failing/skipped jobs.

## Reproduction Assessment

Yes, from source inspection we have a high-confidence path showing the missing observability: current cron execution code can finish, skip, or return non-throwing failures without the requested runtime log and status warning surfaces. A live scheduler failure was not reproduced in this read-only review, so this remains source-reproducible rather than fully reproduced.

## Solution Assessment

Unclear as a complete implementation until maintainers choose the probe contract; the best fix is not only per-run logging, but a coordinated design across logs, run history, CLI status, and readiness/health semantics.

## Summary

Keep open: current main has durable cron run history, task records, failure counters and alerts, and canonical CLI status, but it still does not fully provide terminal-outcome runtime logging, cron-specific health signaling, or overdue and repeated-skip warnings in human cron-list output.

## What This Changes

Add structured cron execution-attempt logging, cron-aware health reporting, and CLI warnings for overdue, skipped, or repeatedly failing jobs.

## Best Possible Solution

Use one shared cron-health evaluator for CLI diagnostics and a minimal dedicated probe, log bounded and redacted terminal outcomes across scheduled, startup-catch-up, and manual paths, and leave generic liveness/readiness semantics unchanged by default.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should cron degradation use a dedicated minimal health route, affect the existing /readyz contract, or remain available only through authenticated diagnostics?

Rationale: Job failure is not equivalent to Gateway unavailability, and the chosen HTTP semantics affect orchestration behavior, information exposure, and compatibility for existing probe consumers.

Likely owner: steipete

Owner reason: This person has the strongest combined history across cron execution, skipped-run behavior, Gateway probes, and the issue discussion.

Owner confidence: high

Options:

- **Dedicated cron probe (recommended):** Add a minimal aggregate cron-health route without job metadata and keep /healthz and /readyz behavior unchanged.
- **Fold into readiness:** Make repeated cron failures or overdue jobs fail /readyz, accepting that infrastructure may remove a functioning Gateway from service.
- **Diagnostics only:** Keep cron health behind CLI, task audit, run history, and failure alerts without adding an HTTP component route.

## Reproduction Assessment

Yes at source level: scheduled, startup-catch-up, and manual terminal outcomes can be traced to paths that emit events and persist state without consistently writing runtime outcome logs. A live deployment reproduction was not performed during this read-only review.

## Solution Assessment

No, the literal proposal should not be landed wholesale because arbitrary job failures should not automatically redefine Gateway readiness. A shared evaluator plus bounded logging and a minimal dedicated probe is the narrower, safer design.

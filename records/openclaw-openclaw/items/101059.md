## Summary

Keep open: current main still lacks a refusal-to-provider-refusal path for OpenAI Responses streams, and the exact strict-tool refusal sequence needs a fixture or live capture before closing or auto-implementing with high confidence.

## What This Changes

Issue reports that OpenAI Responses streaming refusal payloads during tool-call output are handled as ordinary or empty tool-call output instead of a canonical model refusal.

## Best Possible Solution

Add a narrow OpenAI Responses refusal path in the shared parser and the agent transport sibling that maps confirmed refusal events to the canonical `provider_refusal` error/diagnostic shape without executing an empty tool call.

## Reproduction Assessment

No high-confidence live reproduction is available for the exact strict-tool sequence. Source inspection shows current main ignores refusal deltas outside message items, ignores `response.refusal.done`, and can still finalize a function call afterward if such a stream occurs.

## Solution Assessment

Yes, conditionally: the best fix is a small shared-parser plus sibling-transport repair using OpenClaw's existing `provider_refusal` diagnostic shape. The worker should first pin the OpenAI SDK/captured SSE event shape and avoid adding a new `ModelRefusalError` API unless maintainers explicitly want that contract.

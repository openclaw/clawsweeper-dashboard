## Summary

Keep this PR open for maintainer review. It addresses a real P1 Codex session-state regression caused by durable resets retaining the physical OpenClaw session ID, and the supplied live Telegram/Codex evidence plus focused regression coverage support the implementation; the remaining decision is whether the new optional reset correlation is an intentional shared harness and plugin-hook contract.

## What This Changes

The PR adds a one-shot runtime reset token through OpenClaw’s reset lifecycle so the Codex plugin can distinguish a successful same-session `/new` reset from stale or unrelated session-end events and allow the next turn to bind a fresh Codex thread.

## System Context

OpenClaw session reset paths first notify registered agent harnesses and later emit a `session_end` plugin event. The Codex plugin uses that lifecycle information to maintain the runtime binding between an OpenClaw session generation and its Codex app-server thread, which controls whether the next chat message can run.

## Architecture Diagram

flowchart LR
  A[User runs /new] --> B[OpenClaw session reset]
  B --> C[Registered agent harness reset]
  C --> D[Successful reset token]
  B --> E[Delayed session-end hook]
  D --> F[Codex binding lifecycle decision]
  E --> F
  F --> G[Next chat message]
  G --> H[Fresh Codex thread or safe retirement]

## Best Possible Solution

Accept the optional token as a documented generic lifecycle-correlation field only if shared harness and plugin-hook owners want that durable contract; otherwise keep the same exact-match safety property behind a Codex-owned boundary that does not extend shared lifecycle types.

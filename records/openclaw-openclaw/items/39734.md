## Summary

Keep open: current main and v2026.6.11 still do not expose a Bedrock config path for custom `anthropic_beta` or generic `additionalModelRequestFields`, and the remaining choice is the public Bedrock provider config contract.

## What This Changes

Request to let Amazon Bedrock model configuration pass custom `anthropic_beta` flags into Converse `additionalModelRequestFields`.

## Best Possible Solution

Add a Bedrock-plugin-owned, schema-backed request-field or beta merge contract with docs, focused merge/de-duplication tests, and redacted live Bedrock proof before landing.

Rationale: The source gap is clear, but adding any path creates a user-facing provider config contract and repository policy treats provider routing and config/default surfaces as compatibility-sensitive.

Owner confidence: medium

Options:

- **Add Bedrock-owned request fields (recommended):** Expose a Bedrock plugin or per-model params contract that validates and merges request fields, covering `anthropic_beta` without making core own generic Bedrock payload policy.
- **Add only typed beta support:** Support a narrow `anthropicBeta` or Bedrock `context1m` path for Claude long-context usage while avoiding a general Converse body passthrough.
- **Decline custom betas:** Keep Bedrock request shaping internal and require first-class provider support for each beta feature before OpenClaw sends it.

## Reproduction Assessment

Yes, source-level: current main's Bedrock provider constructs `additionalModelRequestFields` only internally and no config schema/options surface exists; the issue also includes a live Bedrock CLI transcript for the same failure mode.

## Solution Assessment

Unclear. A configurable Bedrock request-field path is plausible, but maintainers should choose the public config contract before implementation because it expands provider-owned request surface.

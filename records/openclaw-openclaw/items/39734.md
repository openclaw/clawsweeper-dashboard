## Summary

Keep open: current main and v2026.6.11 still lack a Bedrock config path for custom `anthropic_beta` or generic `additionalModelRequestFields`, and the remaining work is a provider config-contract decision rather than a cleanup-close candidate.

## What This Changes

Request to let Amazon Bedrock model config supply custom `anthropic_beta` or `additionalModelRequestFields` so Claude Bedrock beta features such as 1M context can be enabled without patching provider code.

## Best Possible Solution

Add a Bedrock-plugin-owned request-field merge contract with schema, docs, focused tests for `anthropic_beta` merge behavior, and redacted live Bedrock proof before landing.

Question: Should Bedrock expose a broad `additionalModelRequestFields` or `providerFields` passthrough, a narrower typed `anthropicBeta` or `context1m` option, or no user-configurable beta flags?

Rationale: This adds a user-facing provider config contract, and OpenClaw policy treats new config/default surfaces and provider request shaping as compatibility-sensitive product decisions.

Likely owner: steipete

Owner reason: The decision spans provider/plugin boundary and config-contract policy, and recent history shows provider SDK/config ownership work in the same area.

Owner confidence: high

Options:

- **Add Bedrock-owned request fields (recommended):** Expose a Bedrock plugin or per-model params contract that safely merges request fields, validates shape, documents upgrade behavior, and covers `anthropic_beta` without creating a core-wide generic passthrough.
- **Add only a narrow beta option:** Support a typed Bedrock `anthropicBeta` or `context1m` path for Claude long context while avoiding a general Converse body passthrough.
- **Decline custom betas:** Keep Bedrock request shaping internal and ask users to wait for first-class provider support for each beta feature.

Yes. Source inspection shows current main has no Bedrock config merge point for custom `anthropic_beta` or generic `additionalModelRequestFields`, and the issue includes a live Bedrock transcript for the same request-field gap.

## Solution Assessment

Unclear until maintainer direction is set. A Bedrock-owned request-field merge path is plausible, but maintainers should choose the public config contract before implementation because this expands provider-owned request surface.

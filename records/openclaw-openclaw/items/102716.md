## Label Justifications

- `P2`: This is a normal-priority feature with meaningful Apple Watch availability impact but the existing iPhone relay remains usable.
- `impact:auth-provider`: The request is centered on device-scoped Gateway credentials, setup-code handoff, revocation, and avoiding transfer of the iPhone's saved Gateway secret.
- `impact:ux-friction`: Apple Watch users lose supported watch actions when the iPhone is unavailable, even though they can still use the existing relay when the phone is reachable.

## Summary

Keep open: current main has an iOS node and a mature iPhone-relayed WatchConnectivity watch surface, but it does not let the Apple Watch pair or connect to the Gateway as its own direct node. The protected `maintainer` label plus new credential, setup, and capability-surface decisions require explicit maintainer direction before implementation.

## What This Changes

Requested an opt-in Apple Watch direct Gateway node mode over Wi-Fi or cellular while preserving the existing iPhone relay as the default fallback.

## Best Possible Solution

Keep the issue open for a maintainer-sponsored design that reuses existing setup-code/device-pairing and node-invoke contracts, adds a bounded watch-only credential/surface, and preserves the iPhone relay as the default fallback.

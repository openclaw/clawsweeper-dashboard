## What This Changes

Request a supported plugin development hot-reload or cache-clear workflow so TypeScript plugin code changes can apply without manually deleting Jiti cache and restarting containers.

## Best Possible Solution

A Gateway-owned development reload path should safely dispose plugin contributions, invalidate module/Jiti caches, replace active registries, restart affected channels when needed, and expose documented CLI/RPC behavior; if live source reload remains unsupported, docs and logs should state restart-only behavior clearly.

## Reproduction Assessment

Yes, at source level: current main has no public plugin reload/cache-clear command, keeps plugin source/install paths restart-backed, and documents Gateway restart after plugin code changes. I did not run a live container edit cycle in this read-only review.

## Solution Assessment

No, a manual /tmp/jiti deletion or cache-clear-only command is not the best durable solution. The maintainable path is a lifecycle-owned Gateway reload operation that safely tears down old plugin state, invalidates loader caches, replaces registries, and exposes clear CLI/RPC semantics.

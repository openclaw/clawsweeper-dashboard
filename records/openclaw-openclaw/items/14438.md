## Summary

Keep open: current main and the latest stable release still lack a supported plugin source/Jiti reload or cache-clear workflow, and the remaining work is a core Gateway/plugin-loader lifecycle design problem rather than conservative cleanup closure.

## What This Changes

Requests a supported plugin development reload or cache-clear workflow so TypeScript plugin changes can take effect without manually deleting Jiti cache files and restarting the container.

## Best Possible Solution

Design a Gateway-owned plugin development reload lifecycle that safely disposes old runtime state, invalidates loader/Jiti/module caches, rebuilds and swaps plugin registrations, and exposes a documented CLI/API command; if live reload stays unsupported, document restart-only behavior and supported cache diagnostics precisely.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 have no public plugin reload/cache-clear command, restart-back plugin source/install paths, and document Gateway restart after plugin code changes; I did not run a live container edit cycle in this read-only review.

## Solution Assessment

No, manually deleting dependency cache files is only a workaround. The maintainable path is an explicit Gateway lifecycle operation with teardown, cache invalidation, registry replacement, and documented CLI/API semantics.

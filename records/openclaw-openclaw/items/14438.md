## Summary

Keep open: current main and the latest release still have no supported plugin source/Jiti reload or cache-clear command, plugin code/install/load-path changes remain restart-backed, and the issue discussion includes maintainer design context plus later Windows evidence that hot-reload logging can precede actual runtime availability.

## What This Changes

Request a supported plugin development hot-reload or cache-clear workflow so TypeScript plugin edits and install changes do not require manual Jiti cache deletion plus Gateway/container restart.

## Best Possible Solution

Design a Gateway-owned plugin development reload lifecycle with explicit plugin teardown, loader/Jiti/module cache invalidation, registry replacement, and documented openclaw plugins reload or cache diagnostics; otherwise document restart-only behavior precisely.

## Reproduction Assessment

Yes, at source level: current main lacks a public plugin reload/cache-clear command, keeps plugin source/install/load-path changes restart-backed, and documents Gateway restart after plugin code changes. I did not run the Docker/Jiti edit cycle in this read-only review.

## Solution Assessment

No, a manual Jiti cache deletion or cache-clear-only command is not the best durable solution. The maintainable path is a lifecycle-owned Gateway reload operation that safely tears down old plugin state, invalidates loader caches, replaces registries, and exposes clear CLI/RPC semantics.

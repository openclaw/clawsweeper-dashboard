## Summary

Keep open: current main still has no public plugin reload or cache-clear command, plugin source/install changes remain restart-backed, and prior discussion plus current source show this needs a Gateway/plugin-loader lifecycle design rather than cleanup closure.

## What This Changes

Request a plugin development hot-reload workflow, such as a CLI reload/cache-clear command or watcher, so TypeScript plugin edits do not require manual Jiti cache cleanup and container restart.

## Best Possible Solution

Design a Gateway-owned plugin development reload lifecycle with explicit teardown, loader/Jiti/module cache invalidation, registry replacement, and a documented CLI/RPC command; if live source reload remains unsupported, document restart-only behavior and cache diagnostics precisely.

Question: Should OpenClaw support live plugin source/install reload as a first-class Gateway/CLI lifecycle, or keep plugin development restart-only with better diagnostics and docs?

Rationale: The useful fix crosses plugin loader cache invalidation, runtime teardown, registry replacement, Gateway reload behavior, CLI/RPC UX, and docs, and the repository policy explicitly treats plugin metadata changes as restart-required unless an owner-defined reload flow exists.

Owner confidence: high

Options:

- **Design first-class reload (recommended):** Specify and implement a Gateway-owned reload operation that safely disposes old plugin state, invalidates loader caches, replaces runtime registries, and exposes a documented CLI/RPC entrypoint.
- **Keep restart-only:** Leave source/install changes restart-backed and improve docs/logging so users know when a full Gateway restart is required and how to verify the active runtime.
- **Cache-clear only:** Add a narrow cache diagnostic or clear command without live registry replacement, accepting that users still need a restart for safe activation.

## Reproduction Assessment

Yes, source-level: current main has no public plugin reload/cache-clear command, keeps plugin source/install paths restart-backed, and documents Gateway restart after plugin code changes. I did not run a live container edit cycle in this read-only review.

## Solution Assessment

No for a cache-clear-only fix: clearing Jiti state alone would not safely replace live plugin registrations. The maintainable solution is an owner-defined Gateway reload lifecycle or an explicit restart-only product decision with clearer diagnostics.

## Summary

Keep open: current main supports config-driven plugin registry refreshes, but plugin source, load-path, and install changes still require a Gateway restart, with no public reload or cache-clear command. Recent user evidence confirms the gap remains observable, while safe restartless loading requires an explicit lifecycle contract rather than exposing Jiti internals.

## What This Changes

Request a supported way to reload plugin code or clear plugin loader/Jiti caches without restarting the OpenClaw process or container.

## Best Possible Solution

Define a Gateway-owned plugin reload transaction that quiesces and disposes the selected plugin, invalidates all relevant loader state, validates replacement registrations, atomically swaps the active registry, and rolls back on failure; then expose it as `openclaw plugins reload <id>` with runtime inspection and authoring documentation.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support in-process reload of plugin code, or keep plugin source process-stable and limit the product to managed Gateway restart plus clearer diagnostics?

Rationale: Both directions are technically viable, but in-process reload creates a durable plugin lifecycle and compatibility contract across many registration surfaces; automation cannot choose that product boundary safely.

Likely owner: vincentkoc

Owner reason: The strongest recent history is in the central loader, Jiti cache, and reload-planning surfaces that define the feasible product boundary.

Owner confidence: high

Options:

- **Design transactional plugin reload (recommended):** Add an explicit lifecycle and disposal contract plus an atomic Gateway reload operation before exposing a CLI command.
- **Keep restart-only semantics:** Preserve process-stable plugin code, improve restart automation and log wording, and clearly document the supported development loop.
- **Expose cache clearing only:** Add a cache command without runtime replacement, accepting that users must still restart and internal cache details become public surface.

## Reproduction Assessment

Yes, at source level: local plugin code, load-path, and install-record changes remain restart-classified, and a user report shows a newly installed provider stays absent until Gateway restart. A live current-main run was not performed in this read-only review.

## Solution Assessment

No, Jiti cache deletion alone is not the best solution because it does not safely remove and replace active registrations. The maintainable solution is a Gateway-owned transactional reload contract, or an explicit decision to retain restart-only behavior.

## Risks / Open Questions

- A restartless swap needs defined teardown for hooks, tools, services, providers, commands, channels, MCP runtimes, background tasks, and other plugin-owned resources or reloads can duplicate or strand behavior.

- Plugin source and install metadata are currently process-stable by policy; changing that boundary affects Gateway availability and plugin API expectations, not only developer convenience.

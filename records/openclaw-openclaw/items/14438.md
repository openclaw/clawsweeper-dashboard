## Summary

Keep open: current main and the latest release still lack a supported plugin reload/cache-clear workflow, and the remaining work is a Gateway/plugin-loader lifecycle design rather than a stale duplicate.

## What This Changes

The issue requests a supported plugin development reload or cache-clear path so TypeScript plugin changes can take effect without manually clearing Jiti cache and restarting the container.

## Best Possible Solution

Design a supported plugin development reload workflow that invalidates plugin/Jiti/module state, safely replaces runtime registrations and services, and exposes the result through CLI/RPC/docs; if live reload stays unsupported, document restart-only behavior and cache locations precisely.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes from source inspection: current main has no reload/cache-clear command and keeps plugin source/install/load-path changes restart-backed; the issue discussion also includes a Windows install/provider case that only resolves after Gateway restart.

## Solution Assessment

Is this the best way to solve the issue? No for a raw cache-delete command or watcher alone; the maintainable solution needs an explicit Gateway/plugin lifecycle reload path, or a deliberate restart-only product decision with accurate docs.

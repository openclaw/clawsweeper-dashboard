## Summary

Keep open: current main and v2026.6.11 still lack a supported plugin source/Jiti reload or cache-clear command. Adjacent plugin-management hot reload and Jiti cache scoping work improves the area, but it does not solve the developer workflow and a safe solution needs maintainer lifecycle design.

## What This Changes

Request a supported plugin development reload/cache invalidation workflow so TypeScript plugin edits can take effect without manual process/container restart and manual Jiti cache deletion.

## Best Possible Solution

Design a Gateway-owned plugin development reload lifecycle that invalidates loader/Jiti/module state, disposes old runtime registrations, swaps the active registry safely, and exposes a documented CLI/API path; if live source reload is rejected, document restart-only behavior and supported cache diagnostics precisely.

## Reproduction Assessment

Yes, at source level. Current main still has no public plugin reload/cache-clear command, plugin source/install changes remain restart-backed, and docs still tell users plugin code changes require a Gateway restart.

## Solution Assessment

No, deleting Jiti cache files manually is only a workaround. The maintainable solution needs a lifecycle-owned Gateway reload operation with explicit teardown, cache invalidation, registry replacement, and CLI/API semantics.

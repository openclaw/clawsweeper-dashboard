## Summary

Keep open: current main still documents plugin code/install-source changes as restart-backed and exposes no supported reload or cache-clear command, while the existing hot plugin reload path only covers config/management refreshes. The request is useful, but it needs maintainer design because safe source/Jiti reload crosses plugin cache invalidation, runtime teardown, registry replacement, Gateway lifecycle, CLI/RPC UX, and docs.

## What This Changes

The issue requests a supported plugin development reload workflow, such as `openclaw plugins reload`, cache clearing, or file watching, so TypeScript plugin changes can take effect without restarting the OpenClaw process or container.

## Best Possible Solution

Design a supported Gateway-owned plugin development reload operation that invalidates loader/Jiti/module state, disposes old plugin runtime resources, swaps registrations atomically, and exposes the workflow through CLI/RPC/docs; if live source reload remains unsupported, make the restart-only contract and cache guidance precise.

## Reproduction Assessment

Yes at source level: current main lacks `openclaw plugins reload` or cache-clear UX, docs still instruct Gateway restart for plugin code/source changes, and tests keep install/load-path changes restart-backed. I did not run a live Docker plugin edit cycle in this read-only review.

## Solution Assessment

No for a cache-clear-only shortcut: it would not safely replace live plugin registrations or dispose runtime resources. The maintainable fix needs a lifecycle-owned Gateway reload design, with CLI/RPC and docs layered on top.

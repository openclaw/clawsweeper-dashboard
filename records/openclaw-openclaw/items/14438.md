## Summary

Keep open: current main still documents plugin source/install changes as Gateway-restart-backed, has no `openclaw plugins reload` or cache-clear command, and the issue discussion includes maintainer/product-decision context plus later Windows install evidence that plugin changes are not live until restart.

## What This Changes

The issue requests a supported plugin-development reload workflow, such as a plugin reload or cache-clear CLI command or watcher-backed cache invalidation, so TypeScript plugin edits do not require a container/process restart.

## Best Possible Solution

Design a Gateway-owned plugin development reload lifecycle with explicit teardown, loader/Jiti/module cache invalidation, registry replacement, and a documented CLI/RPC command; if live source reload remains unsupported, document restart-only behavior and cache diagnostics precisely.

## Reproduction Assessment

Yes, at source level: current main has no public plugin reload/cache-clear command, keeps plugin source/install paths restart-backed, and documents Gateway restart after plugin code changes. I did not run a live container edit cycle in this read-only review.

## Solution Assessment

No, a manual `/tmp/jiti` deletion or cache-clear-only command is not the best durable solution. The maintainable path is a lifecycle-owned Gateway reload operation that safely tears down old plugin state, invalidates loader caches, replaces registries, and exposes clear CLI/RPC semantics.

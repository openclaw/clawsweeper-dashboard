## Summary

Keep open: current main still lacks a supported plugin reload or cache-clear workflow, and the remaining work crosses Gateway/plugin lifecycle design rather than stale cleanup.

## What This Changes

The issue requests a supported plugin hot-reload or cache-clear workflow so TypeScript plugin developers do not need manual Jiti cache cleanup plus container restart after code changes.

## Best Possible Solution

Design a Gateway-owned plugin development reload lifecycle with explicit teardown, loader/Jiti/module cache invalidation, registry replacement, and documented CLI/RPC semantics; if live source reload remains unsupported, document restart-only behavior and cache diagnostics precisely.

## Reproduction Assessment

Yes, source-level: current main has no public plugin reload/cache-clear command, keeps plugin source/install paths restart-backed, and documents Gateway restart after plugin code changes. I did not run a live container edit cycle in this read-only review.

## Solution Assessment

No, a cache-clear-only command is not the best durable solution. The maintainable path is a lifecycle-owned Gateway reload operation that safely tears down old plugin state, invalidates loader caches, replaces registries, and exposes clear CLI/RPC semantics.

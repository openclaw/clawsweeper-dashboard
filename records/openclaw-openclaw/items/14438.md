## What This Changes

Requests a supported plugin development reload or cache-clear workflow so TypeScript plugin changes can take effect without restarting the Gateway/container.

## Best Possible Solution

Design a Gateway-owned plugin development reload lifecycle with explicit teardown, loader/Jiti/module cache invalidation, registry replacement, and documented CLI/RPC UX; if live source reload remains unsupported, document restart-only behavior and cache diagnostics precisely.

Kind: product_direction

Question: Should OpenClaw support live plugin source/install reload as a first-class Gateway/CLI lifecycle, or keep plugin development restart-only with better diagnostics and docs?

Rationale: The useful fix crosses plugin loader caches, runtime teardown, registry replacement, Gateway reload semantics, CLI/RPC UX, and documentation; repository policy currently treats plugin metadata as process-stable unless an owner-defined reload flow exists.

Likely owner: steipete

Owner reason: steipete already provided the keep-open product/design note and has the strongest Gateway reload pipeline history among the traced owners.

Owner confidence: high

Options:

- **Design first-class reload (recommended):** Specify and implement a Gateway-owned reload operation that safely disposes old plugin state, invalidates loader caches, replaces runtime registries, and exposes a documented CLI/RPC entrypoint.
- **Keep restart-only:** Leave source/install changes restart-backed and improve docs/logging so users know when a full Gateway restart is required and how to verify the active runtime.
- **Add cache diagnostics only:** Expose a narrow cache diagnostic or clear command without live registry replacement, accepting that users still need a restart for safe activation.

## Reproduction Assessment

Yes. Source-level reproduction is high-confidence: current main has no public plugin reload/cache-clear command, keeps plugin source/install paths restart-backed, and documents Gateway restart after plugin code changes.

## Solution Assessment

No for a cache-clear-only fix. Clearing Jiti state alone would not safely replace live plugin registrations; the maintainable solution is an owner-defined Gateway reload lifecycle or an explicit restart-only product decision with clearer diagnostics.

## Summary

Keep open: current main and the latest release still do not provide a supported plugin source/Jiti reload or cache-clear command, and the existing hot-reload path deliberately leaves plugin install/source changes restart-backed. The issue remains a real plugin-development ergonomics gap, but it crosses loader cache invalidation, runtime registry replacement, Gateway lifecycle, CLI/RPC UX, and docs, so it needs maintainer design rather than an automatic cleanup close.

## What This Changes

The issue requests a supported plugin development reload or cache-clear workflow so TypeScript plugin changes can take effect without restarting the OpenClaw process/container.

## Best Possible Solution

Design an explicit plugin development reload contract through Gateway/plugin loader ownership that invalidates module and registry state, disposes old runtime registrations, and exposes a documented `openclaw plugins reload <id>` or cache diagnostic command; if that remains unsupported, document restart-only behavior with precise cache diagnostics.

## Reproduction Assessment

Yes, source inspection is enough to reproduce the feature gap: current main has no plugin reload/cache-clear CLI, plugin install/source changes are planned as Gateway restarts, and tests assert that restart behavior. I did not run the Docker workflow, but the code/docs/test path matches the report.

## Solution Assessment

No, deleting `/tmp/jiti` or adding a narrow cache-clear command is not the best standalone fix. The maintainable solution needs an owner-approved reload contract that handles Jiti/module cache invalidation plus safe runtime disposal and replacement, or else clearer restart-only documentation.

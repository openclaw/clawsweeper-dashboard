## Summary

Keep open: current main and the latest release still lack a supported plugin source/install reload or cache-clear command, while the existing hot-reload path only covers selected plugin config changes. The remaining work is a product and lifecycle design decision, not conservative cleanup.

## What This Changes

Request a supported plugin development reload or cache-clear workflow that invalidates Jiti/plugin loader state without requiring a full container or Gateway restart.

## Best Possible Solution

Design a Gateway-owned plugin development reload lifecycle with explicit teardown, loader/Jiti/module cache invalidation, registry replacement, and documented CLI/RPC UX; if live source reload remains unsupported, document restart-only behavior and cache diagnostics precisely.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support live plugin source/install reload as a first-class Gateway/CLI lifecycle, or keep plugin development restart-only with clearer diagnostics and docs?

Rationale: The useful fix crosses plugin loader caches, runtime teardown, registry replacement, Gateway reload semantics, CLI/RPC UX, and documentation; repository policy currently treats plugin metadata as process-stable unless an explicit owner reload/install/doctor flow exists.

Likely owner: steipete

Owner reason: steipete already provided the keep-open product/design note and has Gateway reload pipeline history.

Owner confidence: high

Options:

- **Design first-class reload (recommended):** Specify and implement a Gateway-owned reload operation that safely disposes old plugin state, invalidates loader caches, replaces runtime registries, and exposes a documented CLI/RPC entrypoint.
- **Keep restart-only:** Leave source/install changes restart-backed and improve docs/logging so users know when a full Gateway restart is required and how to verify the active runtime.
- **Add cache diagnostics only:** Expose a narrow cache diagnostic or clear command without live registry replacement, accepting that users still need a restart for safe activation.

## Reproduction Assessment

Yes, source-level: current main has no public plugin reload/cache-clear command, keeps plugin source/install paths restart-backed, and documents Gateway restart after plugin code changes. I did not run a live Docker plugin edit cycle in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product direction. A cache-clear-only fix is not the best solution by itself because it would not safely replace live plugin registrations and owned runtime resources.

## Summary

Keep open: current main and v2026.6.11 still keep plugin source/install/load-path changes restart-backed, and there is no public plugin reload or cache-clear command. The request remains a valid plugin developer lifecycle feature, but the safe fix needs maintainer direction across Gateway reload semantics, plugin teardown, loader/Jiti cache invalidation, registry replacement, CLI/RPC UX, and docs.

## What This Changes

Request support for plugin development hot reload or cache clearing so TypeScript plugin edits can take effect without manually clearing Jiti cache and restarting the container.

## Best Possible Solution

Design a Gateway-owned plugin development reload lifecycle with explicit teardown, loader/Jiti/module cache invalidation, registry replacement, and documented CLI/RPC UX; if live source reload remains unsupported, document restart-only behavior and cache diagnostics precisely.

Rationale: The requested behavior crosses plugin runtime ownership, process-stable metadata policy, Gateway reload behavior, and public CLI/docs contracts, so automation cannot safely choose the permanent lifecycle semantics.

Options:

- **Design first-class reload (recommended):** Add an owner-approved Gateway reload operation that disposes old plugin state, invalidates loader/Jiti/module caches, replaces runtime registries, and exposes a documented CLI/RPC path.
- **Keep restart-only:** Keep source/install/load-path changes restart-backed and improve docs, logs, runtime verification, and cache-location diagnostics so plugin authors know the supported path.
- **Expose cache diagnostics only:** Add a narrow supported cache-info or clear-cache tool for development troubleshooting while still requiring Gateway restart for live activation.

## Reproduction Assessment

Yes, source-level: current main has no public plugin reload/cache-clear command, keeps plugin source/install/load paths restart-backed, and documents Gateway restart after plugin code changes. I did not run a live Docker edit cycle in this read-only review.

## Solution Assessment

No for a cache-clear-only fix; clearing Jiti state alone would not safely replace runtime registrations. The maintainable path is either an owner-defined Gateway reload lifecycle or an explicit restart-only decision with better diagnostics.

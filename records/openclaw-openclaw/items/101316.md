## Summary

The current PR head fixes the earlier media-ordering blocker and I found no new line-level correctness finding, but this still needs maintainer acceptance because it intentionally changes default LINE rapid follow-up delivery from concurrent dispatch to busy-reply-and-skip.

## What This Changes

The PR adds a process-local LINE per-user in-flight guard, wires it into `createLineBot`, sends a busy reply for stable-sender concurrent events, bypasses senderless events, and expands handler tests.

## Best Possible Solution

Land the LINE plugin-local guard only if maintainers accept busy-skip semantics; otherwise replace it with a queue or active-turn feedback design that preserves follow-up messages.

## Solution Assessment

Yes if maintainers want busy-skip semantics for LINE; the plugin boundary, senderless bypass, and guard ordering are now sound. No if the product requirement is to preserve every follow-up message, in which case a queue or active-turn feedback path is the better direction.

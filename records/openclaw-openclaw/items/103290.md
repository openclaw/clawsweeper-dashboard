## Summary

The latest head does not resolve the previous P1: it assigns the result of writing the same stale pre-apply object, while bundled migration providers change configuration through the runtime mutation API. The PR remains useful and narrowly repairable, but merging it would trade the retry lockout for silent configuration loss on successful imports, and no after-fix real behavior proof is provided.

## What This Changes

The PR moves the onboarding migration config commit until after apply succeeds, but still commits the pre-apply config snapshot.

## Best Possible Solution

Stage provider config reads and mutations from the prepared wizard target without writing the real config file, then atomically commit the authoritative final staged config only after a conflict-free successful apply; leave the original disk config unchanged after errors or conflicts.

## Summary

Keep open: the prior blocking lifecycle finding remains on the current head. The guard prevents overlapping ticks only within one notifier instance, while the plugin’s registered service discards that instance on stop and creates another on restart, allowing the old pending poll and the new initial poll to overlap.

## What This Changes

Adds a service-instance in-flight guard to device-pair notifier polling and regression coverage for delayed polls across timer ticks and direct service restarts.

## Best Possible Solution

Make one lifecycle owner retain the in-flight state across the plugin’s registered stop/start sequence, and add regression coverage through the registered service callbacks before proving one real pairing notification flow.

## Solution Assessment

No. A per-instance guard is the right primitive but is owned below the production restart boundary; retaining the notifier instance or moving the guard into the registration wrapper is the narrower complete fix.

## Summary

Keep open. Current main and v2026.7.1 support outbound WhatsApp reactions and narrowly consume approval reactions, but the public action contract still has no WhatsApp reaction listing, historical query, or general reaction event/hook surface. The remaining work needs an explicit privacy, routing, retention, removal, and agent-turn contract before implementation. ([docs.openclaw.ai](https://docs.openclaw.ai/message?utm_source=openai))

## What This Changes

Add generic WhatsApp reaction listing, accessible inbound reaction events, and retrieval of historical reaction state.

## Best Possible Solution

Define one layered WhatsApp-plugin contract that normalizes authorized add/remove events, persists canonical observed reaction state in SQLite with explicit privacy and retention rules, exposes the generic `reactions` action, and remains passive by default while https://github.com/openclaw/openclaw/issues/17840 separately governs opt-in agent turns.

## Risks / Open Questions

- Persisting reaction state records personal identifiers, group identifiers, emoji feedback, and message correlations, so access scope and retention cannot be inferred safely from the outbound reaction API.
- A general event path must reuse WhatsApp sender authorization and conversation routing; otherwise reactions could be exposed to the wrong agent/session or unauthorized plugins.
- The existing approval-reaction consumer and any new generic listener need one canonical event-normalization path to avoid duplicate processing or conflicting removal semantics.
- Upstream live events do not by themselves guarantee historical completeness after disconnects or restarts, so the query contract must distinguish observed state from provider-authoritative history.

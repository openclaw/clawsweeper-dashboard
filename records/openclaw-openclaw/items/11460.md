## Summary

Keep open. Current main supports outbound WhatsApp reactions and narrowly registered approval reactions, but still excludes WhatsApp from the generic reaction-list action and provides no general historical reaction query. The closed implementation attempts do not supersede the request, and maintainers must choose the event, session, privacy, and persistence contract before implementation.

## What This Changes

Add WhatsApp support for listing message reactions, observing ordinary add/remove reaction events, and retrieving historical reaction state.

## Best Possible Solution

Define one WhatsApp-owned reaction contract: first emit access-controlled passive add/remove events without automatically starting agent turns, then add canonical SQLite-backed historical queries only if maintainers approve retention and upstream reconciliation semantics.

Options:

- **Stage passive events first (recommended):** Add access-controlled add/remove reaction events without agent turns, leaving historical persistence for a separately approved design.
- **Build the complete read path:** Implement passive events, optional agent-session delivery, and SQLite-backed historical queries together with documented retention semantics.
- **Retain narrow support:** Keep outbound and registered approval reactions only, declining ordinary reaction observation and history for now.

## Reproduction Assessment

Yes—at source and documented-contract level. Current main lists WhatsApp for outbound `react` but not for the generic `reactions` action, while only registered approval reactions have an inbound consumer; no live WhatsApp account was exercised in this read-only review.

## Solution Assessment

No single proposal in the issue is yet the best complete fix. A staged, plugin-owned passive event contract is safer than immediately creating agent turns or committing to historical storage without defined privacy and reconciliation rules.

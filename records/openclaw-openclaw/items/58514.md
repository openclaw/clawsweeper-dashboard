## Label Justifications

- `P1`: A real Google Chat Space workflow can accept a message but fail to create a session or agent reply, blocking group-channel use for affected users.
- `impact:message-loss`: The reported Space messages can be dropped before agent processing even though the webhook request succeeds.
- `impact:session-state`: The observable failure includes missing `googlechat:group` session creation for Space messages.

## Summary

Keep open: v2026.6.11 and current main include the modern Google Chat Space/DM classifier, but the reported Space path can still be accepted by the webhook and skipped before session/run creation when Google Chat mention activation is not recognized. The July 4 comment confirms Spaces can work after disabling `requireMention`, so the remaining issue is mention/session admission rather than basic webhook delivery.

## What This Changes

The issue asks for Google Chat Space/group @mention messages to create `googlechat:group` sessions and reach the agent instead of returning HTTP 200 with no reply.

## Best Possible Solution

Keep the classifier fix, then make the Google Chat Space admission path explicit: either robustly recognize current mention annotations with diagnostics or define an intentional implicit-mention rule for delivered app-url Space events, with focused Google Chat monitor/access tests and redacted live proof.

- **Treat Delivered Space Events As Mentions:** For service-account app-url Google Chat Spaces, bypass annotation-only mention detection because delivered events are already @mention-scoped by Google.
- **Consolidate With Broader Space Routing Work:** Fold this into the larger Google Chat Space/thread routing backlog and keep the current `requireMention:false` workaround documented until that design lands.

Yes at source level, but not with a fresh live run: current main can skip Google Chat group messages before the inbound run when annotation-based mention detection does not mark the app as mentioned. The latest user comment reports the same v2026.6.11 behavior and a `requireMention:false` workaround.

## Solution Assessment

Unclear until maintainers pick the activation boundary. A narrow parser/diagnostic fix is likely safest, while making all delivered Space events implicit mentions may be valid only if maintainers accept that product/security assumption.

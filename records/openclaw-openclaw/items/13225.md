## Label Justifications

- `P2`: This is a valid plugin/runtime API enhancement with meaningful routing and security implications, but it is not an urgent broken workflow.
- `impact:session-state`: Routing a pending tool call across models or sessions can affect transcript continuity, tool-call IDs, tool-result ownership, cancellation, and compaction state.

- `impact:auth-provider`: The requested redirect contract directly affects provider and model choice, auth profile selection, and fallback behavior.

## Summary

Keep open: current main and the latest release still expose `before_tool_call` as params/block/approval, not a pre-tool model/session routing contract. Related routing/context items are closed unmerged, duplicate back to this issue, or only partially overlap.

## What This Changes

Request a pre-tool-call hook or contract that can inspect pending assistant context and redirect a tool call to another model or session.

## Best Possible Solution

Keep this as the canonical maintainer design item for an additive pre-tool or continuation-routing plugin/runtime API with explicit security, audit, provider/auth, fallback, and session-state semantics.

Question: Should OpenClaw expose pre-tool model/session routing as an additive plugin/runtime API, and what authority and context boundary must that API enforce?

Rationale: The requested feature crosses plugin trust, model/provider auth, session ownership, transcript continuity, fallback, and audit boundaries, so code inspection can prove the gap but cannot choose the safe product contract.

Likely owner: steipete

Owner confidence: medium

Options:

- **Design a typed routing phase (recommended):** Add or extend a pre-tool routing contract only after defining allowed context, redirect targets, auth/fallback behavior, audit logs, and failure semantics.
- **Keep hooks params-only:** Leave `before_tool_call` limited to params/block/approval and require users to use `before_model_resolve`, capability-specific model config, or explicit subagents for routing.
- **Split context from routing:** First add narrowly gated assistant/tool context visibility, then revisit model/session redirection after security review.

## Reproduction Assessment

Yes, at the source-contract level: current `before_tool_call` event/result/runtime code has no redirect, provider, model, session target, or preceding-output contract. This is a feature gap rather than a broken-behavior runtime reproduction.

## Solution Assessment

No for the literal event sketch alone; the maintainable solution needs a typed routing phase or hook result that preserves provider/auth, fallback, audit, and session-state contracts. Existing `before_model_resolve` remains useful for prompt-time routing but does not solve pending tool-call delegation.

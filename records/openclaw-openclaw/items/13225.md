## Summary

Keep open: current main still limits pre-tool hooks to argument rewrite, blocking, and approval, while model/session redirection remains an unresolved plugin-runtime contract with significant authorization and transcript-state implications. The related implementation PRs closed unmerged, and no canonical open PR currently owns the requested behavior.

## What This Changes

Requests a pre-tool-call hook that can inspect preceding model output and redirect a pending tool call to a different model or session.

## Best Possible Solution

Add an additive, typed pre-tool routing seam that preserves the existing hook and explicitly defines visible context, target eligibility, authorization inheritance, tool-result ownership, transcript/audit behavior, cancellation, and fail-safe fallback before enabling provider or session transfer.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support transparent model or session transfer for a pending tool turn, and if so should that authority live in `before_tool_call` or a separate routing hook?

Rationale: The choice establishes a security-sensitive plugin API and determines ownership of provider credentials, session state, transcript continuity, permissions, failure handling, and audit records; source inspection cannot infer the intended product boundary.

Likely owner: steipete

Owner reason: He is the strongest available routing candidate from the central hook history and previously reviewed this exact product boundary.

Owner confidence: medium

Options:

- **Add a dedicated routing hook (recommended):** Define a separate, narrowly typed pre-tool routing contract while leaving argument-policy interception in `before_tool_call`; this provides the clearest security and lifecycle boundary.
- **Extend the existing hook:** Add context and redirect outcomes to `before_tool_call`, accepting a broader combined policy-and-orchestration API with stricter compatibility requirements.
- **Keep delegation explicit:** Decline transparent redirection and require plugins or agents to use explicit subagent/session APIs, documenting that pre-tool hooks remain policy-only.

## Reproduction Assessment

Not applicable as a failing bug, but the reported limitation is reproducible from current source with high confidence: the hook result has no model or session redirect outcome and the runtime has no transfer branch.

## Solution Assessment

Unclear pending product direction; transparent routing may be appropriate, but a separate routing hook is safer and more maintainable than adding orchestration semantics directly to the existing policy hook.

## Risks / Open Questions

- Allowing a plugin to inspect preceding assistant output could expose system, user, tool, or credential-adjacent context beyond the current hook payload and therefore needs an explicit data-access boundary.
- Redirecting a pending call across providers or sessions can change authorization, model availability, billing, fallback behavior, context-window accounting, and audit attribution.
- Mid-turn session transfer can mis-associate tool-call IDs, tool results, transcript ownership, compaction state, or cancellation unless the lifecycle is defined as one atomic runtime contract.
- Overloading `before_tool_call` with delegation could combine policy interception and agent orchestration into an ambiguous API; a separate typed routing hook may be safer.

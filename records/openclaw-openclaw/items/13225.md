## Label Justifications

- `P2`: This is a valid plugin/runtime API enhancement with meaningful routing and security implications, but it is not an urgent broken workflow.
- `impact:session-state`: Routing a pending tool call across models or sessions can affect transcript continuity, tool-call IDs, and tool-result ownership.
- `impact:security`: The requested hook would expose pre-execution context and grant routing authority at a sensitive plugin policy boundary.
- `impact:auth-provider`: The requested redirect contract directly affects provider and model choice, auth profile selection, and fallback behavior.

## Summary

Keep open: current `main` and the latest release still expose `before_tool_call` as params/block/approval, not the requested pre-tool model/session routing contract. Related routing PRs are closed unmerged or only partial context work, so this remains a canonical maintainer design item.

## What This Changes

Request an additive pre-tool-call hook capability that can inspect assistant context before a tool executes and redirect the pending call to another model or session.

## Best Possible Solution

Keep this as the canonical maintainer design item for an additive pre-tool or continuation-routing plugin/runtime API with explicit security, audit, provider/auth, fallback, and session-state semantics.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes for the source-level feature gap: current `before_tool_call` event/result/runtime code has no redirect, model, provider, session target, or preceding-output contract.

## Solution Assessment

Is this the best way to solve the issue? No for the literal event sketch alone; the maintainable solution needs a typed routing phase or hook result that preserves provider/auth, fallback, audit, and session-state contracts.

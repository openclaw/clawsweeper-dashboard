## Summary

Keep open: the PR targets a valid Docker E2E resource-cap failure, but the new cleanup parser can remove unrelated containers because it scans container command arguments after the image, and the posted proof is mocked Bash output rather than real Docker behavior.

## What This Changes

Adds retry-without-default-resource-limits behavior to Docker E2E container/package helpers with regression tests for resource-cap rejection.

## Best Possible Solution

Keep the retry approach in the Docker E2E helpers, but constrain cleanup parsing to Docker options before the image, apply the same fix to the package fallback, add a regression for command arguments containing --name/--cidfile, and include redacted real Docker proof.

## Reproduction Assessment

Source-reproducible: current main injects default Docker resource caps and has no retry path, matching the reported failure class. I did not reproduce it against a real constrained Docker daemon in this read-only review.

## Solution Assessment

No: the retry location is plausible, but the cleanup parser is too broad and real daemon proof is still missing. The safer fix is to parse only Docker options before the image and prove the retry on an affected host.

- **[P1] Stop cleanup parsing at the Docker image:** `scripts/lib/docker-e2e-container.sh:255-299`
  - body: `docker_e2e_docker_run_created_container_refs` scans the entire `docker run` argv for `--name` and `--cidfile`, including arguments that belong to the command after the image. Parse only Docker options before the image, and apply the same fix to the package fallback copy.

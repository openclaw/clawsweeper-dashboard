## Summary

Keep this PR open: it targets a real Docker E2E reliability bug, but the current patch still has a cleanup parser that can treat post-image command arguments as Docker options and remove an unrelated container, and the after-fix proof is mocked rather than from a real constrained Docker daemon.

## What This Changes

The PR adds retry-without-default-resource-limits behavior to Docker E2E container and package helpers, with mocked regression tests for resource-cap rejection.

## Best Possible Solution

Keep the retry approach, but stop cleanup parsing at the Docker image in both helper copies, add a regression for post-image --name/--cidfile arguments, and include redacted real constrained-Docker proof.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes from source: current main injects default Docker resource caps and has no retry path, matching the linked constrained-host failure class, though this read-only review did not run a real affected daemon.

## Solution Assessment

Is this the best way to solve the issue? Not yet: the retry location is plausible, but the cleanup parser must respect the Docker image boundary and the PR still needs real constrained-Docker proof.

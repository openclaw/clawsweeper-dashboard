## What This Changes

Make gateway startup and `doctor --fix` safely reconcile conflicts between legacy `plugins/installs.json` records and the authoritative shared SQLite plugin index.

## Best Possible Solution

Have doctor verify the canonical SQLite plugin record, preserve the conflicting legacy file as a diagnostic backup, archive or remove it so migration converges, and expose the same recovery through a visible Doctor/Fix flow rather than requiring manual file operations.

Question: When legacy plugin install metadata conflicts with an internally valid SQLite record, should doctor treat SQLite as authoritative and archive the legacy file, or require explicit operator selection between the two records?

Rationale: The migration must converge, but choosing either record can change an intentional plugin source, pin, integrity value, or install path; repository policy establishes SQLite as the runtime store without fully defining conflict arbitration.

Likely owner: Patrick-Erichsen

Owner confidence: medium

Options:

- **Verify SQLite, archive legacy (recommended):** Doctor validates the SQLite record and installed payload, preserves the legacy JSON as a backup, then archives it so startup can proceed.
- **Require operator selection:** Doctor presents both records and refuses destructive reconciliation until the operator chooses the authoritative install metadata.
- **Make conflict warning-only:** Gateway starts using SQLite while leaving the legacy conflict unresolved for later manual repair.

## Label Justifications

- `P0`: A released upgrade can leave the managed gateway permanently crash-looping with no working in-product repair path.
- `impact:crash-loop`: The fatal startup-migration result causes the supervised gateway process to exit and restart repeatedly.
- `impact:ux-release-blocker`: Recovery currently requires stopping the service and manually moving a machine-managed state file, blocking ordinary users without a technical workaround.

## Summary

The report describes a concrete released upgrade blocker. Current documentation still assigns legacy plugin-index migration to `doctor --fix`, while no linked fix or reviewed current-main provenance establishes that conflicting records now converge, so conservative cleanup should keep this issue open.

## What This Changes

Make startup and `openclaw doctor --fix` safely reconcile conflicting legacy `plugins/installs.json` metadata with the shared SQLite plugin index so the gateway can recover without manual file moves.

## Best Possible Solution

Add a doctor-owned migration that preserves verified canonical SQLite state, archives the legacy index only after successful verification, and otherwise presents both records through an explicit repair choice while keeping runtime SQLite-only.

Rationale: The recovery defect is clear, but choosing install-intent precedence can discard a deliberately selected source or path and therefore requires an explicit product rule.

Options:

- **Auto-reconcile verified SQLite (recommended):** When SQLite points to a present, integrity-matching installed artifact, preserve it, archive the legacy file, and require explicit repair only when verification fails.
- **Always require operator choice:** Show both records in doctor and require the operator to select the canonical install intent before archiving either source.
- **Relax readiness only:** Leave conflicting records untouched and downgrade this migration result to non-fatal, accepting persistent warnings and unresolved duplicate state.

## Reproduction Assessment

Yes at the state-shape level: create divergent records for one plugin in legacy `plugins/installs.json` and shared SQLite, start the gateway, and run `doctor --fix`. The released reports are detailed and mutually reinforcing, although this review did not execute the fixture against current main.

## Solution Assessment

No single suggested option is sufficient as written. The narrowest maintainable fix is doctor-owned verified reconciliation and archival, not a runtime fallback or blanket downgrade of all migration warnings.

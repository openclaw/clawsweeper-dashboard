- `P1`: The PR targets a real Telegram message-delivery and bot-token routing failure that can send through the wrong bot or fail group delivery for multi-bot users.

## Summary

Keep open: the patch appears to fix a source-reproducible Telegram default-account routing bug at the right resolver boundary, but it changes compatibility-sensitive bot/token precedence and still needs real Telegram proof before merge.

## What This Changes

The PR changes Telegram account and token resolution so omitted account IDs use the configured default account before the implicit default, with regression coverage for account, token, and action-runtime paths.

## Best Possible Solution

Land the resolver-level fix after real Telegram proof demonstrates omitted sends and actions use the configured default bot, while preserving the existing no-default and explicit-account compatibility cases.

## Reproduction Assessment

Yes from source inspection: current main normalizes omitted Telegram account IDs to the implicit default in both resolveTelegramAccount and resolveTelegramToken, so a credentialed stale default token shadows the configured default. I did not run tests in this read-only checkout, but the PR body reports focused before/after failures and passes.

## Solution Assessment

Yes, this is the best fix shape: resolving the configured default at the two canonical optional-account entry points avoids duplicating policy across action call sites. The remaining blocker is live Telegram proof and maintainer acceptance of the precedence change, not a different code location.

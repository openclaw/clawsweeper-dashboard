## Summary

Keep open. Current `main` still derives gateway memory readiness from embedding readiness and does not expose a separate live runtime-health signal, so the central false-negative class is not proven fixed; the linked closing fork PR is still open, unmerged, conflicting, and not maintainer-modifiable.

## What This Changes

The issue asks `openclaw status --deep` and related doctor/status surfaces to report a working live memory plugin as healthy instead of unavailable.

## Best Possible Solution

Land or replace a maintainer-approved live gateway memory status contract that separates runtime health from embedding readiness, with human status, JSON status, and `doctor.memory.status` proof against a working external memory plugin.

## Reproduction Assessment

No, not as a high-confidence live current-main reproduction. Source inspection gives medium-confidence reproduction of the decision path because current `main` still maps gateway memory readiness to `payload.embedding.ok` without a separate live runtime-health field.

## Solution Assessment

No. Current `main` is only a partial mitigation: it can avoid the old exact `unavailable` wording in some output, but it still does not encode the healthy-runtime-versus-skipped-embedding distinction that the reports need.

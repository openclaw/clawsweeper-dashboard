## Summary

Keep open. Current main no longer uses the old hard `unavailable` wording for skipped memory inspection, but it still does not prove live memory runtime health for `openclaw status --deep`, and the issue remains paired with an open conflicting fork PR that uses closing syntax.

## What This Changes

The issue reports that `openclaw status --deep` can mark a working live memory plugin such as Mem0, Honcho, or memory-qdrant as unavailable.

## Best Possible Solution

Define a maintainer-approved memory status contract where live gateway runtime health is separate from embedding readiness, then wire both human and JSON status surfaces to use that contract without reintroducing local plugin side effects.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw memory status truth come from the live gateway runtime, a passive local plugin status contract, or remain `not checked` unless an explicit full status scan runs?

Rationale: Current code partially mitigates the old wording but leaves a product/API boundary choice between live gateway truth and local plugin materialization, and an open conflicting closing PR is already attached to this issue.

Likely owner: steipete

Owner reason: The memory-runtime-through-plugin refactor and status memory surface history make this the strongest routing candidate for the product/API boundary decision.

Owner confidence: medium

Options:

- **Define live-gateway runtime health (recommended):** Expose runtime health separately from embedding readiness in `doctor.memory.status` and use it for human and JSON status when local memory materialization is inconclusive.
- **Define passive local plugin status:** Keep status local but require a passive plugin status API that cannot run heavyweight startup or mutate state, then update plugin/runtime contracts and tests.
- **Leave as not checked:** Keep the current conservative output and close or supersede the open fix PRs only after documenting that `status --deep` is not a live memory health check.

## Reproduction Assessment

No live current-main reproduction was established, but the remaining mismatch is source-reproducible: `status --deep` does not collect memory details unless `--all` is used, and gateway memory readiness still derives from `embedding.ok`. The exact old `unavailable` text has been softened to `not checked`, so this is not a high-confidence live repro of the original wording.

## Solution Assessment

No, current main is only a partial mitigation. The best fix needs a clear gateway doctor/status contract for runtime health versus embedding readiness, plus focused coverage for both human and JSON status output.

## Summary

Keep open: current main and the latest release still lack a supported visible coordinator-to-ACP-thread send or proxy-only Discord delivery contract; related fixes cover ACP replies and terminal task updates, not the initiating visible instruction path without main-session metadata creation.

## What This Changes

The issue requests a visible agent-to-agent delivery path for ACP thread-bound Discord sessions that avoids creating `agent:main:discord:channel:<thread_id>` session entries.

## Best Possible Solution

Add one explicit, authorized visible ACP-thread delivery contract that posts the coordinator instruction to the intended Discord thread, bypasses main-session metadata only for that call, preserves normal mirroring elsewhere, and includes focused source tests plus live Discord/ACP proof.

## Maintainer Decision

Kind: product_direction

Question: Which visible ACP-thread delivery contract should OpenClaw support for coordinator-to-worker instructions without creating main Discord session metadata?

Rationale: The code can support more than one narrow fix shape, but choosing between a sessions_send API extension, a message proxy-only path, or an ACP-bound-thread exclusion rule changes public API semantics, upgrade behavior, and security boundaries.

Likely owner: steipete

Owner reason: Most central current-main blame and shortlog history for the sessions_send, gateway schema, outbound metadata, and task delivery surfaces points to steipete as the strongest routing owner for the product/API choice.

Owner confidence: high

Options:

- **Define Narrow Visible ACP Send (recommended):** Add an explicit `sessions_send`-style visible delivery mode that is scoped to authorized ACP-bound sessions and proves no unintended main-session metadata is created.
- **Define Proxy-Only Message Send:** Add a `message`/gateway send bypass for authorized proxy delivery, preserving normal outbound mirroring for every other send path.
- **Keep This Plugin-Owned:** Decline a core API change and document a ClawHub/community relay path, accepting that current plugins cannot fully avoid the reported session-stub side effect.

## Reproduction Assessment

No live dual-account Discord ACP reproduction was run. Source inspection does give a high-confidence way to verify the central gap: the current schemas lack `visible`/`proxyOnly`, `sessions_send` sends the initiating prompt internally, and message sends still prepare outbound mirror metadata.

## Solution Assessment

No single proposed option is clearly best yet. A narrow explicit visible ACP delivery contract is likely safer than a broad ACP-bound-thread exclusion, but maintainers need to choose the public API and authorization boundary first.

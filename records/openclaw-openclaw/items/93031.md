## Summary

Keep open: current main still allows legacy/defaulted cron jobs to persist with NULL agent_id, while the direct fix candidates for this exact issue are closed unmerged. Current scheduler code has fallback behavior, so the original skip theory is not fully proven on main, but the persisted ownership gap remains real and compatibility-sensitive.

## What This Changes

The issue reports that legacy cron jobs migrated from jobs.json into SQLite can have a blank agent_id and then never dispatch for the intended agent.

## Best Possible Solution

Make the cron ownership contract explicit: either migrate blank legacy cron jobs to the configured default agent with upgrade proof, or deliberately codify blank ownership as default-agent-compatible across scheduler, delivery context, list, manual run, diagnostics, and docs.

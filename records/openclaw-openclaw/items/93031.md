## Summary

Keep open: current main still lets legacy/defaulted cron jobs persist with missing `agent_id`, while runtime fallbacks make the exact scheduler-skip mechanism less certain and all linked fix PRs are closed unmerged.

## What This Changes

The issue reports that v2026.5.28-to-v2026.6.6 cron migration can copy legacy `jobs.json` jobs into SQLite with blank `agent_id`, leaving scheduled work apparently healthy but not firing.

## Best Possible Solution

Make legacy cron migration canonical with maintainer-approved missing-agent semantics, then prove a v2026.5.28-to-current upgrade where legacy rows receive the intended owner and scheduled runs execute.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For legacy cron jobs with missing `agentId`/`agent_id`, should OpenClaw persist the configured default agent during doctor/startup migration, or intentionally keep NULL as dynamic default-agent inheritance?

Rationale: Both choices affect multi-agent upgrade compatibility and persisted session ownership, and current code already has runtime fallback behavior that makes this more than a mechanical one-line repair.

Likely owner: steipete

Owner reason: They are the strongest feature-history signal for the cron SQLite and doctor migration boundary that owns this compatibility choice.

Owner confidence: high

Options:

- **Persist Configured Default (recommended):** Doctor/startup migration rewrites missing legacy ownership to the configured default agent and adds upgrade proof for non-main default-agent setups.
- **Keep Dynamic Inheritance:** Maintain NULL `agent_id` as intentional default-agent inheritance, document it, and add tests proving migrated jobs run correctly without persisted ownership.
- **Require Manual Repair:** Leave existing behavior and direct affected operators to an explicit doctor/SQL repair, accepting the support burden for upgraded fleets.

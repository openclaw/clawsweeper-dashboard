## Label Justifications

- `P2`: The proposed cache limit can cause intermittent failures in agent database operations if a live handle is evicted, but the affected path is bounded to high-agent-count operation.
- `merge-risk: 🚨 availability`: Closing a handle that a caller still intends to use can turn a later SQLite operation into a runtime failure.
- `merge-risk: 🚨 session-state`: Per-agent SQLite handles back agent-scoped state, so a stale-handle failure can interrupt state reads or writes.

## Summary

Keep this protected maintainer PR open for manual review: the bounded-cache goal is sound, but the proposed eviction can close a returned agent database handle unless every caller’s lifetime is proven to stay within the synchronous protected section.

## What This Changes

Caps the process-local per-agent SQLite handle cache at 64 entries using LRU eviction and adds cache-eviction tests.

## Best Possible Solution

Bound only handles with an explicit idle/lease lifecycle, or prove and enforce that all returned handles are consumed entirely within a synchronous non-yielding section; add an interleaving regression test before merge.

## Summary

Close as implemented on current main: the reported split-UTF-8 corruption path is now fixed by stateful UTF-8 decoding for process output and raw-byte JSONL line assembly, with current-main regression coverage; the fix is not in v2026.6.11 yet.

## What This Changes

The issue reports random U+FFFD replacement characters in longer Chinese WebChat/group-chat agent responses, likely from multibyte UTF-8 being split across streaming chunks.

## Best Possible Solution

Keep the current-main streaming decoder and raw-byte JSONL line assembly, and let the next release ship this fix; adjacent Windows codepage/TUI/QMD work should stay on its separate maintainer PR path.

## Reproduction Assessment

Yes. Source inspection shows v2026.6.11 decoded default subprocess output chunks independently with `buffer.toString("utf8")`, and current main adds split-CJK/default decoder coverage for the fixed streaming decoder path.

## Solution Assessment

Yes. The current-main fix puts stateful UTF-8 decoding and raw-byte line assembly at the byte-stream boundaries, which is the narrow maintainable solution without adding feature, config, or product-policy surface.

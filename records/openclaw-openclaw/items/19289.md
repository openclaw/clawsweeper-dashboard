## Summary

Keep open: current main restored one built-in extension driver, but browser driver config, runtime routing, profile creation, and the public Plugin SDK still do not provide a third-party MCP/custom backend registration seam.

## What This Changes

Request to add a pluggable browser backend interface so external drivers can register profile driver ids and bind MCP/custom adapters without core forks.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend/adapter extension point that registers driver ids through core and the Plugin SDK, updates config/schema/CLI/control routes, and adds docs plus security and contract tests for MCP/custom adapters.

## Maintainer Decision

Kind: product_direction

Question: Should OpenClaw expose a generic browser backend Plugin SDK/registry seam for third-party MCP/custom drivers, or keep browser backends limited to first-party/profile-specific drivers for now?

Rationale: This is a public plugin API and browser-control security boundary, so automation should not choose the long-term contract by widening driver unions or landing a one-off adapter.

Likely owner: steipete

Owner confidence: high

Options:

- **Design generic SDK registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit to first-party drivers:** Handle Browserbase, My Browser, relay, and similar needs as individual built-in or bundled-plugin drivers without exposing a generic third-party contract yet.
- **Defer until demand PRs settle:** Keep this issue open while narrower Browserbase, My Browser, relay, and sandbox-backend work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, route validation, runtime resolution, and Plugin SDK browser types closed to built-in driver ids. No live runtime setup is needed because arbitrary drivers are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch.

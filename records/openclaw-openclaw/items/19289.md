## Summary

Keep open: current main restored a built-in Chrome extension driver, but browser profile drivers are still a closed set and there is no third-party browser backend registry or Plugin SDK contract for MCP/custom adapters.

## What This Changes

Add a browser backend Plugin SDK/registry so third-party MCP/custom browser drivers can be registered without modifying core.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend/adapter extension point that registers driver ids through core and the Plugin SDK, updates config/schema/CLI/control routing, and includes docs plus security and contract tests for MCP/custom adapters.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose a generic third-party browser backend Plugin SDK/registry seam, or keep browser backends limited to first-party/narrow drivers for now?

Rationale: The requested seam is both public API and a browser-control security boundary, so automation cannot safely choose the long-term contract by widening driver enums or landing one more built-in adapter.

Likely owner: steipete

Owner reason: steipete owns the newest first-party extension-driver implementation and has already scoped this issue as a browser backend Plugin SDK design gap.

Owner confidence: high

Options:

- **Design Generic SDK Registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Keep Narrow First-Party Drivers:** Continue handling Browserbase, extension relay, and My Browser needs as individual built-in or bundled-plugin drivers without exposing a generic third-party backend contract yet.
- **Defer Until Demand PRs Settle:** Keep this issue open while the Browserbase, My Browser, relay, and sandbox-backend work clarifies the smallest safe registration API.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, runtime resolution, public profile creation, and Plugin SDK browser types closed to built-in driver ids. No live runtime setup is needed because custom driver ids are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The eventual implementation should be a versioned backend registry and security-reviewed contract, not a quick enum-widening patch or one-off service driver.

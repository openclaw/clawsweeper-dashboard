## Summary

Keep open: current main and the latest release still expose a closed browser driver set with no browser-backend registration contract, so the requested third-party MCP/custom adapter seam remains a real core/Plugin SDK design gap.

## What This Changes

Requested a browser backend plugin interface so third-party MCP/custom browser drivers can register without OpenClaw core forks.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend registry in core and the Plugin SDK, then update browser profile config/schema/CLI/control routing, docs, and security/contract tests for third-party MCP/custom adapters.

## Reproduction Assessment

Yes, at source level: current main rejects arbitrary browser driver ids in config schema, profile creation, runtime resolution, CLI/client types, and Plugin SDK browser types. No live setup is needed because the public contracts reject custom drivers before backend dispatch.

## Solution Assessment

Yes for keeping this as a maintainer API-design issue; one-off built-in drivers or enum widening would be too narrow and risky. The best implementation needs a versioned registry contract with explicit browser-control security review.

## Summary

Keep open: current main still lacks a browser backend or driver registration interface for third-party MCP/custom adapters, and related Browserbase, My Browser, relay, and sandbox-backend work are narrower demand signals rather than replacements for this public Plugin SDK/API design issue.

## What This Changes

The issue requests a public browser backend registration interface so third-party MCP/custom adapters can provide profile drivers without patching core.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend/adapter extension point that registers driver ids through core and the Plugin SDK, updates config/schema/CLI/control routes, and adds docs plus security and contract tests for MCP/custom adapters.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic browser backend Plugin SDK/registry seam for third-party drivers, or keep browser backends limited to narrow first-party profile drivers for now?

Rationale: This would define public Plugin SDK, config, and browser-control security contracts, so automation cannot safely choose the long-term API by widening driver unions.

Likely owner: vincentkoc

Owner reason: The strongest current provenance is in browser driver migration and existing-session profile work.

Owner confidence: high

Options:

- **Design generic SDK registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit to first-party drivers:** Handle Browserbase, My Browser, relay, and similar needs as individual built-in or bundled-plugin drivers without exposing a generic third-party contract yet.
- **Defer until demand PRs settle:** Keep this issue open while narrower Browserbase, My Browser, relay, and sandbox-backend work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes, at source level: current main keeps driver config, schema, client, runtime resolution, route validation, SDK types, and tests closed to third-party driver ids. No live runtime setup is needed because arbitrary drivers are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as maintainer API-design work is the maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch.

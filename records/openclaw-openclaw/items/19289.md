## Label Justifications

- `P2`: This is a normal-priority feature/API gap for advanced browser automation workflows, not an immediate core outage.
- `impact:security`: A third-party browser backend interface would govern control over browser sessions, CDP endpoints, credentials, and private-network navigation.

## Summary

Keep open: current main still has a closed browser profile driver set and no Plugin SDK/browser backend registration contract, while the related Browserbase, My Browser, relay, and sandbox-backend items are narrower demand signals rather than a generic third-party adapter interface.

## What This Changes

Request a pluggable browser backend/driver interface so third-party MCP or custom adapters can register drivers without core forks.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend registry through core and the Plugin SDK, then update config/schema/CLI/control routes, docs, security review, and contract tests for MCP/custom adapters.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, route validation, runtime resolution, tests, and Plugin SDK browser types closed to third-party driver ids. No live runtime setup is needed because current public contracts reject arbitrary drivers before dispatch.

## Solution Assessment

Yes for keeping this as a maintainer API-design issue; one-off built-in drivers or enum widening are too narrow for the requested third-party backend seam. The maintainable path is a versioned registry with security and compatibility review.

## Summary

Keep open: current main restored first-party Chrome extension relay paths, but it still lacks a generic browser backend/driver registration seam for third-party MCP or custom adapters.

## What This Changes

Request to expose a pluggable browser backend interface so third-party plugins can register browser drivers without modifying OpenClaw core.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend registry that lets plugins declare driver ids, routes config/schema/CLI/control/runtime dispatch through that registry, and documents the security and compatibility contract.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose a versioned generic browser backend Plugin SDK/registry seam for third-party drivers, or keep browser drivers limited to first-party and whole-plugin replacement paths for now?

Rationale: The requested seam would become public API for browser-control authority, profile configuration, and third-party execution, so automation cannot safely choose the permanent driver contract, trust boundary, or upgrade policy.

Likely owner: steipete

Owner reason: steipete has the newest merged work on the same browser driver surface and already reviewed this item as a Plugin SDK design gap.

Owner confidence: high

Options:

- **Design Generic SDK Registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit To First-Party Drivers:** Keep solving Browserbase, extension relay, and My Browser needs as built-in or bundled-plugin drivers without exposing a general third-party contract yet.
- **Defer Until Narrow Work Settles:** Keep this issue open while narrower browser work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes. At source level, current main keeps browser driver config, schema, profile creation, runtime resolution, and Plugin SDK browser surfaces closed to built-in driver ids, so arbitrary adapters are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch or a ClawHub-only close.

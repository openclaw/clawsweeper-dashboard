## Summary

Keep open: current main restored first-party `extension` browser support and already has generic remote-CDP profiles, but it still does not expose a third-party browser backend registration contract for MCP/custom adapters.

## What This Changes

The issue requests a browser backend plugin interface so third-party MCP or custom browser drivers can register without core patches.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend registry that lets plugins declare driver ids, routes config/schema/CLI/control/runtime dispatch through that registry, and documents the security and compatibility contract.

Rationale: This would become public API for browser-control authority and profile configuration, so automation cannot safely choose the permanent driver contract, trust boundary, or upgrade policy.

Owner confidence: high

Options:

- **Design Generic SDK Registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit To First-Party Drivers:** Keep solving Browserbase, extension relay, and My Browser needs as built-in or bundled-plugin drivers without exposing a general third-party contract yet.
- **Defer Until Narrow PRs Settle:** Keep this issue open while narrower browser work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes. At source level, current main keeps browser driver config, schema, profile creation, runtime resolution, and Plugin SDK browser surfaces closed to built-in driver ids, so arbitrary adapters are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch or a ClawHub-only close.

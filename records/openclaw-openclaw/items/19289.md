## Summary

Keep open: current main still has a closed browser driver set and no Plugin SDK/browser backend registry for third-party MCP or custom adapters. The related Browserbase, My Browser, relay, and sandbox-backend items are narrower demand signals or candidate implementations, not a merged generic interface.

## What This Changes

Request a public browser backend registration interface so third-party MCP or custom adapters can provide browser profile drivers without forking core.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend/adapter extension point that registers driver ids through core and the Plugin SDK, updates config/schema/CLI/control routes, and adds docs plus security and contract tests for MCP/custom adapters.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, route validation, runtime resolution, CLI/client types, and Plugin SDK browser types closed to third-party driver ids. No live runtime setup is needed because arbitrary drivers are rejected before dispatch.

## Solution Assessment

Yes for keeping this as a maintainer API-design issue; one-off built-in drivers are too narrow for the requested third-party backend seam. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch.

## Summary

Keep open: current main restored a first-party `extension` browser driver, but browser profile config, route validation, runtime resolution, and Plugin SDK surfaces still do not expose a generic third-party backend/driver registration seam.

## What This Changes

Request to add a pluggable browser backend interface so third-party MCP/custom adapters can register driver ids without patching OpenClaw core.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend registry that lets plugins declare driver ids, route config/schema/CLI/control/runtime dispatch through that registry, and documents security and compatibility guarantees.

Rationale: The requested seam would become public API for browser-control authority and profile configuration, so automation cannot safely choose the permanent driver contract, trust boundary, or upgrade policy.

- **Limit To First-Party Drivers:** Keep solving Browserbase, extension relay, and My Browser needs as built-in or bundled-plugin drivers without exposing a general third-party contract yet.
- **Defer Until Narrow PRs Settle:** Keep this issue open while narrower browser work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes. At source level, current main keeps browser driver config, schema, profile creation, runtime resolution, and Plugin SDK browser surfaces closed to built-in driver ids, so arbitrary adapters are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch.

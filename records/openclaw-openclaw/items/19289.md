## Summary

Keep open: current main restores a built-in Chrome extension profile, but it still does not expose a third-party browser backend or driver registration interface through config, runtime dispatch, profile creation, or the Plugin SDK. The related Browserbase, My Browser, extension relay, and sandbox-backend items are narrower demand signals, not replacements for this public API design issue.

## What This Changes

Request a pluggable browser backend interface so third-party drivers, including MCP-backed adapters, can register without forking OpenClaw core.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend/adapter extension point that registers driver ids through core and the Plugin SDK, updates config/schema/CLI/control routes, and adds docs plus security and contract tests.

Rationale: This would become public API for browser-control authority and profile configuration, so automation cannot safely choose the permanent driver contract, trust boundary, or upgrade policy.

Owner confidence: high

Options:

- **Design Generic SDK Registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit To First-Party Drivers:** Keep solving Browserbase, extension relay, and My Browser needs as built-in or bundled-plugin drivers without exposing a general third-party contract yet.
- **Defer Until Narrow PRs Settle:** Keep this issue open while narrower browser work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, route validation, runtime resolution, and Plugin SDK browser surfaces closed to built-in driver ids. No live setup is needed because arbitrary driver ids are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch.

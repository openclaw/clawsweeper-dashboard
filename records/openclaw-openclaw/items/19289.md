## Summary

Keep open: current main and v2026.6.11 still expose a closed browser-driver set and no Plugin SDK browser-backend registration seam, while the related Browserbase, relay, sandbox, and My Browser items are narrower demand signals rather than replacements for this API design issue.

## What This Changes

The issue requests a pluggable browser backend interface so third-party MCP/custom browser drivers can register without core patches.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend/adapter extension point that registers driver ids through core and the Plugin SDK, updates config/schema/CLI/control routes, and adds docs plus security and contract tests for MCP/custom adapters.

- **Limit to narrow first-party drivers:** Handle Browserbase, My Browser, relay, and sandbox needs as individual built-in or bundled-plugin drivers without exposing a generic third-party contract yet.
- **Defer until demand PRs settle:** Keep this issue open while narrower Browserbase, My Browser, relay, and sandbox-backend work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, route validation, runtime resolution, tests, and Plugin SDK browser types closed to third-party driver ids. No live runtime setup is needed because current public contracts reject arbitrary drivers before backend dispatch.

## Solution Assessment

Yes for keeping this open as a maintainer API-design issue; one-off built-in drivers are too narrow for the requested third-party backend seam. The best implementation is a versioned registry/contract with security review, not an autonomous enum-widening patch.

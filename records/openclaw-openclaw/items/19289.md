## Summary

Keep open: current main restored a first-party Chrome extension driver, but it still lacks a generic third-party browser backend registration seam in config, schema, profile creation, runtime dispatch, and the Plugin SDK. The Browserbase, sandbox-browser, Cua MCP, My Browser, and extension-relay items are related demand signals or narrower implementations, not replacements for this API/design tracker.

## What This Changes

The issue requests a pluggable browser backend interface so third-party MCP/custom browser drivers can register without patching OpenClaw core.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend/adapter registry that lets plugins register driver ids while preserving config validation, security boundaries, docs, and compatibility tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose a generic browser backend Plugin SDK/registry seam for third-party drivers, or keep browser backends limited to first-party profile drivers for now?

Rationale: The requested seam would become public API for browser-control authority and profile configuration, so automation cannot safely choose the permanent driver contract, trust boundary, or upgrade policy.

Likely owner: steipete

Owner reason: steipete has the newest merged work on the same browser driver surface and already scoped this issue as a Plugin SDK design gap.

Owner confidence: high

Options:

- **Design Generic Backend Registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Keep First-Party Drivers Only:** Continue solving Browserbase, extension relay, and My Browser needs as built-in or bundled-plugin drivers without exposing a public third-party driver contract yet.
- **Defer Until Narrow PRs Settle:** Keep this issue open while narrower browser work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, route validation, runtime resolution, and Plugin SDK browser surfaces closed to built-in driver ids. No live setup is needed because arbitrary driver ids are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch.

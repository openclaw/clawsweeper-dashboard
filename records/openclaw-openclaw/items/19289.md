## Label Justifications

- `P2`: This is a normal-priority browser/plugin API feature gap for advanced automation workflows, not an immediate core outage.
- `impact:security`: A third-party browser backend seam would govern access to browser sessions, CDP endpoints, credentials, private-network reachability, and operator-equivalent browser control.

## Summary

Keep open: current main and v2026.6.11 still expose a closed browser driver set with no Plugin SDK browser-backend registration seam, and the related Browserbase, My Browser, relay, sandbox-backend, FSB, and browser-relay threads are narrower demand signals or external workarounds rather than a generic implementation.

## What This Changes

Request a browser backend/plugin interface that lets third-party MCP/custom adapters register profile driver IDs and bind runtime implementations without core forks.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend registration contract in core and the Plugin SDK, with config/schema/CLI/control-route support, docs, security review, and contract tests for third-party MCP/custom adapters.

## Reproduction Assessment

Yes, at source level: current main rejects arbitrary browser driver ids in config/schema, profile creation, runtime resolution, CLI/client types, and Plugin SDK browser types. No live runtime setup is needed because the public contracts reject custom drivers before dispatch.

## Solution Assessment

Yes for keeping this as a maintainer API-design issue; one-off built-in drivers or enum widening would be too narrow for the requested third-party backend seam. The implementation needs a versioned registry/contract plus browser-control security review before code work.

## Summary

Keep open: current main restored one built-in extension driver, but it still does not expose a third-party browser backend registration interface through config, runtime routing, or the Plugin SDK.

## What This Changes

The issue requests a pluggable browser backend interface so third-party MCP or custom browser drivers can register without core changes.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend/adapter extension point that registers driver ids through core and the Plugin SDK, updates config/schema/CLI/control routes, and adds docs plus security and contract tests for MCP/custom adapters.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose a generic browser backend Plugin SDK/registry seam for third-party drivers, or keep browser backends limited to first-party and narrow plugin-owned drivers for now?

Rationale: The requested seam is public API plus a browser-control security boundary, so automation cannot safely choose the long-term contract by widening enums or landing a one-off driver.

Likely owner: vincentkoc

Owner reason: vincentkoc has the strongest recent history on the browser driver migration, existing-session work, and browser SDK helper seam.

Owner confidence: high

Options:

- **Design generic SDK registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit to first-party drivers:** Handle Browserbase, My Browser, and relay needs as individual built-in or bundled-plugin drivers without exposing a generic third-party contract yet.
- **Defer until demand PRs settle:** Keep this issue open while narrower Browserbase, My Browser, relay, and sandbox-backend work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes. Current source still keeps browser driver config, schema, route validation, and Plugin SDK browser types closed to third-party driver ids, so no live runtime setup is needed to prove arbitrary drivers are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch or another one-off built-in driver.

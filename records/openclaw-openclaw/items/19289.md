## Label Justifications

- `P2`: This is a normal-priority browser/plugin API feature gap for advanced automation workflows, not an immediate core outage.
- `impact:security`: A browser backend extension point would govern third-party control over browser sessions, CDP endpoints, credentials, and private-network navigation.

## Summary

Keep open: current main and the latest release still keep browser driver selection closed to built-in modes, while the open related Browserbase, My Browser, relay, and sandbox-backend items are narrower demand signals rather than a generic third-party backend registry.

## What This Changes

Request a pluggable browser backend interface so third-party MCP/custom browser drivers can register without forking or patching core.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend/adapter extension point that registers driver ids through core and the Plugin SDK, updates config/schema/CLI/control routes, and adds docs plus security and contract tests for MCP/custom adapters.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, route validation, runtime resolution, tests, and Plugin SDK browser types closed to third-party driver ids. No live runtime setup is needed because current public contracts reject arbitrary drivers before backend dispatch.

## Solution Assessment

Yes for keeping this open as a maintainer API-design issue; one-off built-in drivers are too narrow for the requested third-party backend seam. The best implementation is a versioned registry/contract with security review, not an autonomous enum-widening patch.

## Summary

Keep open: current main restored a built-in Chrome extension driver, but it still does not provide the requested third-party browser backend registration interface through config, runtime dispatch, or the Plugin SDK.

## What This Changes

Allow browser plugins to register third-party backend driver ids, including MCP/custom adapters, without forking OpenClaw core.

## Best Possible Solution

Define a maintainer-approved, additive browser backend registry in the Plugin SDK with manifest-declared capabilities, explicit operator enablement, config/schema/doctor support, runtime dispatch through registered ids, security documentation, and contract tests; service-specific backends can then ship as plugins.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a public browser backend registration API for third-party drivers, and what permission/config/security contract should that API require?

Rationale: The code change would create a new public Plugin SDK and config surface for browser control, where a bad adapter can drive signed-in browser state or remote CDP endpoints; automation cannot choose that boundary safely without maintainer intent.

Likely owner: steipete

Owner reason: steipete has the strongest recent history across the browser driver restoration, browser plugin ownership, and plugin-boundary refactors relevant to this design choice.

Owner confidence: high

Options:

- **Add guarded backend registry (recommended):** Create a versioned Plugin SDK backend contract with manifest permissions, registered driver ids, config/schema/doctor integration, runtime dispatch, docs, and security tests.
- **Keep replacement-only plugins:** Document that third-party browser engines must disable the bundled browser plugin and provide a whole replacement browser tool, avoiding a new core driver registry.
- **Handle service drivers case by case:** Continue landing service- or topology-specific built-in drivers such as Browserbase or extension relay work without committing to a generic third-party adapter API.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: a non-built-in driver id is rejected by config/schema or profile creation, and runtime dispatch has no registered-backend lookup.

## Solution Assessment

No final solution is selected yet; the best maintainable path is an additive Plugin SDK backend contract rather than another one-off driver string or a full browser-tool replacement requirement.

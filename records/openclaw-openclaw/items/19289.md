## Summary

Keep open: current main has restored a built-in Chrome extension driver, but it still does not expose a third-party browser backend registry or Plugin SDK contract for MCP/custom drivers.

## What This Changes

The issue requests a browser backend plugin interface so third-party MCP or custom adapters can register profile drivers without forking core.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend registry in core and the Plugin SDK, with driver-id ownership, config/schema/CLI/control-route support, docs, and security/contract tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose a generic third-party browser backend Plugin SDK/registry seam, or keep browser drivers limited to first-party/bundled implementations for now?

Rationale: This would become public API for browser-control authority and profile configuration, so automation cannot choose the permanent trust boundary, driver contract, or upgrade policy safely.

Likely owner: steipete

Owner reason: steipete has the newest merged work on the same browser driver surface and already scoped this issue as a Plugin SDK design gap.

Owner confidence: high

Options:

- **Design Generic SDK Registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit To First-Party Drivers:** Continue solving Browserbase, extension relay, My Browser, and sandbox needs as built-in or bundled-plugin drivers without exposing a general third-party contract yet.
- **Defer Until Narrow PRs Settle:** Keep this issue open while narrower browser work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, route validation, runtime resolution, and Plugin SDK browser surfaces closed to built-in driver ids. No live setup is needed because arbitrary driver ids are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch.

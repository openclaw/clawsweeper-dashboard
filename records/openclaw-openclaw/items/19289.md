## Label Justifications

- `P2`: This is a normal-priority browser/plugin API feature gap for advanced automation workflows, not an immediate core outage.
- `impact:security`: A browser backend extension point would govern third-party control over browser sessions, CDP endpoints, credentials, and private-network navigation.

## Summary

Keep open: current main has first-party extension relay and direct remote-gateway pairing support, but it still does not expose a generic third-party browser backend registration seam in config, profile creation, runtime dispatch, or the Plugin SDK.

## What This Changes

Request a pluggable browser backend interface so third-party MCP/custom browser drivers can register without OpenClaw core patches.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend/adapter extension point that registers driver ids through core and the Plugin SDK, updates config/schema/CLI/control/runtime routing, and adds docs plus security and contract tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose a generic browser backend Plugin SDK/registry seam for third-party drivers, or keep browser backends limited to first-party profile drivers for now?

Rationale: The requested seam would become public API for browser-control authority and profile configuration, so automation cannot safely choose the permanent driver contract, trust boundary, or upgrade policy.

Likely owner: steipete

Owner reason: steipete has the newest merged work on the same browser driver surface and prior review context already scopes this as a Plugin SDK design gap.

Owner confidence: high

Options:

- **Design Generic SDK Registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit To First-Party Drivers:** Continue solving Browserbase, extension relay, and My Browser needs as built-in or bundled-plugin drivers without exposing a general third-party contract yet.
- **Defer Until Narrow PRs Settle:** Keep this issue open while narrower browser work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, route validation, runtime resolution, and Plugin SDK browser surfaces closed to built-in driver ids. No live setup is needed because arbitrary driver ids are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch.

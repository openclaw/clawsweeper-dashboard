## Summary

Keep open: current main and v2026.6.11 still keep browser profile drivers closed to built-ins, and the related Browserbase, My Browser, relay, and sandbox-backend items are narrower demand signals rather than a replacement for this public Plugin SDK/API design issue.

## What This Changes

The issue requests a browser backend plugin interface so third-party MCP or custom drivers can register without forking OpenClaw.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend/adapter extension point that registers driver ids through core and the Plugin SDK, updates config/schema/CLI/control routes, and adds docs plus security and contract tests for MCP/custom adapters.

## Maintainer Decision

Question: Should OpenClaw add a generic browser backend Plugin SDK/registry seam for third-party drivers, or keep browser backends limited to narrow first-party profile drivers for now?

Rationale: The requested seam is public API plus a browser-control security boundary, so automation cannot safely choose the long-term contract by widening enums or landing a one-off driver.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Design generic SDK registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit to first-party drivers:** Handle Browserbase, My Browser, and relay needs as individual built-in or bundled-plugin drivers without exposing a generic third-party contract yet.
- **Defer until demand PRs settle:** Keep this issue open while narrower Browserbase, My Browser, relay, and sandbox-backend work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, route validation, runtime resolution, tests, and Plugin SDK browser types closed to third-party driver ids. No live runtime setup is needed because current public contracts reject arbitrary drivers before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch.

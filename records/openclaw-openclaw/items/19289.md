## Summary

Keep open: current main restores a built-in `extension` browser driver, but it still does not provide a third-party browser backend registration interface through config, runtime dispatch, or the Plugin SDK.

## What This Changes

The issue requests a stable browser backend/plugin interface so third-party MCP or custom browser drivers can register without modifying OpenClaw core.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend/adapter extension point that registers driver ids through core and the Plugin SDK, updates config/schema/CLI/control routes, and adds docs plus security and contract tests for MCP/custom adapters.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic browser backend Plugin SDK/registry seam for third-party drivers, or keep browser backends limited to narrow first-party profile drivers for now?

Rationale: The requested seam is both public API and a browser-control security boundary, so automation cannot safely choose the long-term contract by widening driver enums or landing a one-off adapter.

Likely owner: vincentkoc

Owner reason: Vincent Koc has the strongest sampled history on the browser driver migration and profile-driver seam that this decision would change.

Owner confidence: high

Options:

- **Design Generic SDK Registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit To First-Party Drivers:** Handle Browserbase, My Browser, relay, and similar needs as individual built-in or bundled-plugin drivers without exposing a generic third-party contract yet.
- **Defer Until Demand PRs Settle:** Keep this issue open while narrower Browserbase, My Browser, relay, and sandbox-backend work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, route validation, runtime dispatch, and Plugin SDK API closed to named built-in drivers rather than externally registered adapters. No live runtime setup is needed because arbitrary driver ids are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this open for maintainer API design is the narrowest maintainable path. The eventual implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch.

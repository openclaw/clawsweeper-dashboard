## Label Justifications

- `P2`: This is a normal-priority browser/plugin API feature gap for advanced automation workflows, not an immediate core outage.
- `impact:security`: A browser backend extension point would govern third-party control over browser sessions, CDP/MCP endpoints, credentials, and private-network navigation.

## Summary

Keep open: current main has restored a built-in `extension` browser profile through the merged Chrome extension relay work, but it still does not provide a third-party browser backend driver registry or Plugin SDK contract; the latest release `v2026.6.11` predates the restored relay and does not solve the broader custom-adapter request.

## What This Changes

Add a browser backend Plugin SDK/registry seam so third-party MCP or custom adapter drivers can register browser profile implementations without modifying core.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend adapter contract that registers driver ids through core and the Plugin SDK, updates config/schema/CLI/control routes/runtime dispatch, and adds docs plus security and contract tests for MCP/custom adapters.

Rationale: This is a public API, config, runtime dispatch, and browser-control security boundary; automation can verify the missing seam but cannot safely choose the permanent extension contract.

Owner confidence: high

Options:

- **Design generic SDK registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Keep first-party drivers only:** Handle Browserbase, My Browser, relay, and similar needs as individual built-in or bundled-plugin drivers without exposing a generic third-party contract yet.
- **Defer until narrower work settles:** Keep this issue open while the narrower browser-driver PRs clarify the minimum safe registration API.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, route validation, runtime resolution, and Plugin SDK browser types closed to built-in driver ids. No live runtime setup is needed because arbitrary driver ids are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this open for maintainer API design is the narrowest maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch.

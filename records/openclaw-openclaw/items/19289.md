## Summary

Keep open: current main restored first-party browser drivers, including `extension`, but still lacks a generic third-party browser backend or driver registration seam, so this remains a maintainer-owned Plugin SDK/config/security design issue.

## What This Changes

The issue requests a pluggable browser backend interface so third-party MCP or custom adapters can register browser profile drivers without forking core.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend registry that lets plugins declare driver ids, route config/schema/CLI/control/runtime dispatch through that registry, and document security and compatibility guarantees.

Rationale: The requested seam would become public API for browser-control authority and profile configuration, so automation cannot safely choose the permanent driver contract, trust boundary, or upgrade policy.

Owner confidence: high

Options:

- **Design Generic SDK Registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit To First-Party Drivers:** Keep solving Browserbase, extension relay, and My Browser needs as built-in or bundled-plugin drivers without exposing a general third-party contract yet.
- **Defer Until Narrow PRs Settle:** Keep this issue open while narrower browser work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes. At source level, current main keeps browser profile driver config, schema, profile creation, runtime resolution, and SDK browser surfaces closed to built-in driver ids, so arbitrary adapters are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this open for maintainer API design is the narrowest maintainable path. The implementation should be a versioned registry and security contract, not an autonomous enum-widening patch.

## Label Justifications

- `P2`: This is a normal-priority browser/plugin API feature gap for advanced automation workflows, not an immediate core outage.
- `impact:security`: A third-party browser backend seam would govern plugin-mediated control over browser sessions, CDP endpoints, credentials, and private-network navigation.

## Summary

Keep open: current main restores one built-in `extension` browser driver, but it still does not provide a third-party browser backend registration interface or Plugin SDK contract for MCP/custom adapters.

## What This Changes

Request a pluggable browser backend interface so third-party drivers can register profile driver ids and bind custom or MCP-backed browser implementations without forking core.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend registry that lets plugins register driver ids through a narrow Plugin SDK contract, with config/schema/CLI/control routing, docs, security review, and contract tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic browser backend Plugin SDK/registry seam for third-party drivers, or keep browser backends limited to first-party profile drivers for now?

Rationale: The requested change is both public API and a browser-control security boundary, so automation cannot safely choose the permanent contract by widening driver literals or landing a one-off adapter.

Likely owner: steipete

Owner reason: steipete authored the latest first-party driver restoration and prior review scoping, so they are the best current router for the browser/plugin-boundary product decision.

Owner confidence: medium

Options:

- **Design Generic SDK Registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit To First-Party Drivers:** Handle Browserbase, My Browser, relay, and similar needs as individual built-in or bundled-plugin drivers without exposing a generic third-party contract yet.
- **Defer Until Demand PRs Settle:** Keep this issue open while narrower Browserbase, My Browser, relay, and sandbox-backend work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes, at source level: current main keeps browser driver config, schema, create-route validation, runtime resolution, docs, and Plugin SDK browser types closed to built-in driver ids. No live browser setup is needed because the public contracts reject arbitrary drivers before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch.

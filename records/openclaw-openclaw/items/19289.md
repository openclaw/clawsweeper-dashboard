## Summary

Keep open: current main restored narrower first-party browser driver work, but it still does not expose a generic browser backend or driver registration seam for third-party MCP/custom adapters.

## What This Changes

The issue requests a Plugin SDK, config, and runtime interface for third-party browser drivers such as MCP-backed or custom adapters.

## Best Possible Solution

Design a maintainer-approved, versioned browser backend registry that lets plugins declare driver ids, routes config/schema/CLI/control/runtime dispatch through that registry, and documents security and compatibility guarantees.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose a generic browser backend Plugin SDK and registry seam for third-party drivers, or keep browser backends limited to first-party profile drivers for now?

Rationale: The requested seam would become public API for browser-control authority and profile configuration, so automation cannot safely choose the permanent driver contract, trust boundary, or upgrade policy.

Likely owner: steipete

Owner confidence: high

Options:

- **Design Generic SDK Registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit To First-Party Drivers:** Continue solving Browserbase, extension relay, and My Browser needs as built-in or bundled-plugin drivers without exposing a general third-party contract yet.
- **Defer Until Narrow PRs Settle:** Keep this issue open while narrower browser work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes. At source level, current main keeps browser driver config, schema, profile creation, runtime resolution, and Plugin SDK browser surfaces closed to built-in driver ids, so arbitrary adapters are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The implementation should be a versioned registry and security-reviewed contract, not an autonomous enum-widening patch.

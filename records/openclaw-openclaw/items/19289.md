## Summary

Keep open: current main restored first-party `extension`/`chrome` browser paths, but browser drivers are still a closed built-in set and there is no Plugin SDK registry for third-party MCP/custom backend adapters.

## What This Changes

Requests a public browser backend/plugin registry so third-party MCP/custom drivers can be selected as browser profile drivers without core forks.

## Best Possible Solution

Design a maintainer-approved, versioned browser-backend registry that lets plugins declare driver ids, routes config/schema/CLI/control/runtime dispatch through that registry, and documents the security and compatibility contract.

- **Design Generic SDK Registry (recommended):** Add a versioned backend contract, registry-owned driver ids, config/schema/client/runtime routing, docs, and security tests before accepting third-party adapters.
- **Limit To First-Party Drivers:** Continue solving Browserbase, extension relay, and My Browser needs as built-in or bundled-plugin drivers without exposing a general third-party contract yet.
- **Defer Until Narrow PRs Settle:** Keep this issue open while narrower browser work clarifies the minimum safe registration API.

## Reproduction Assessment

Yes for the capability gap. Source inspection shows current main keeps browser driver config, schema, profile creation, runtime resolution, and Plugin SDK browser surfaces closed to built-in driver ids, so arbitrary adapters are rejected before backend dispatch.

## Solution Assessment

Yes for the review outcome: keeping this as a maintainer API-design issue is the narrowest maintainable path. The implementation should be a versioned registry/contract with security review, not an autonomous enum-widening patch or a ClawHub-only close.

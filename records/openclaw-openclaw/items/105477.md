## Summary

Keep this PR open: the allocation optimization is useful, but moving the size return ahead of the existing UTF-16 round-trip guard changes the response for content that is both oversized and malformed. The latest branch also has maintainer involvement through an assignment and a focused test commit, so it should receive a narrow repair rather than cleanup closure.

## What This Changes

The branch calculates UTF-8 byte length before creating a `Buffer` in `sessions.files.set` and updates the oversized-content regression test to cover multibyte input and allocation avoidance.

## Best Possible Solution

Preserve the unsafe-content validation before the size response using an allocation-free well-formed-UTF-16 check, retain exact UTF-8 byte accounting for valid input, and add coverage for content that is both malformed and oversized.

Yes, from source: submit `sessions.files.set` content containing a lone UTF-16 surrogate whose UTF-8 replacement-byte size exceeds 256 KiB. Current behavior validates the unsafe text before the size response, while this patch returns on size first.

## Solution Assessment

No. Computing byte length first is the right optimization, but the proposed ordering is not the best fix because it drops the existing malformed-text response precedence; validate well-formed UTF-16 without an encoded buffer before the size branch.

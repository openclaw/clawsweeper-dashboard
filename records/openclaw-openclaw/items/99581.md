## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P2] Fail closed when xargs can append protected paths:** `src/infra/exec-control-command-guard.ts:966`
  - body: `xargs` can append arguments from stdin or `-a` after the static initial argv. This unwraps only the static command, so `printf '%s\n' "$HOME/.codex/sessions" | xargs rg token` is treated as a harmless pathless piped `rg` even though xargs runs it against the protected session path.
  - confidence: 0.9
- **[P2] Parse nested shell payloads as shell scripts:** `src/infra/exec-control-command-guard.ts:901`
  - body: Shell payload text is re-split as one argv instead of being parsed as shell. A payload like `eval 'cd "$HOME"; rg token'` only exposes the `cd`, so the later protected-root `rg` is missed.
  - confidence: 0.88
- **[P2] Protect every configured sandbox workdir root:** `src/agents/bash-tools.exec.ts:1785`
  - body: Only `sandbox.containerWorkdir` is passed as an additional protected root, but backend workdir validation also accepts entries from `sandbox.workdirRoots`. A sandbox command under a non-container root such as `/agent/project` can search `/agent` without hitting the guard.
  - confidence: 0.9
- **[P2] Include sandbox env when expanding search paths:** `src/agents/bash-tools.exec.ts:1783`
  - body: The guard expands operands before `buildSandboxEnv()` adds `sandbox.env`. If a sandbox sets `OPENCLAW_STATE_DIR=/state`, `rg token "$OPENCLAW_STATE_DIR"` can be allowed by the guard but run against the configured state root inside the sandbox.
  - confidence: 0.88
- **[P2] Ignore function bodies until they are invoked:** `src/infra/exec-control-command-guard.ts:1217`
  - body: Parsed nested commands include function-definition bodies, and those payloads are classified immediately. A command that only defines `f(){ rg token ~/.codex/sessions; }; echo ok` would be rejected even though Bash never runs the search.
  - confidence: 0.86
- **[P2] Validate cd options before adopting cwd:** `src/infra/exec-control-command-guard.ts:341`
  - body: `resolveCdWorkdir()` skips every dash-prefixed token as if it were valid. Bash rejects invalid options like `cd -x /tmp`, leaving cwd unchanged, but the analyzer adopts `/tmp` and can allow a later broad search from the protected original cwd.
  - confidence: 0.9
- **[P2] Only adopt CDPATH targets that exist:** `src/infra/exec-control-command-guard.ts:369`
  - body: For CDPATH matches, this returns the unresolved candidate when `realpath` fails. Bash only changes cwd when the CDPATH target is an enterable directory, so missing targets can make the guard track a cwd the shell never entered.
  - confidence: 0.9
- **[P2] Update PWD after tracked cd changes:** `src/infra/exec-control-command-guard.ts:1290`
  - body: After adopting a successful `cd`, the guard updates only the tracked workdir, not the environment used for later `$PWD` expansion. A later `rg token "$PWD"` can be checked against the old cwd while the shell searches the new protected cwd.
  - confidence: 0.85
- **[P2] Fail closed on complex parameter expansions:** `src/infra/exec-control-command-guard.ts:1551`
  - body: Path expansion only handles simple `$VAR` and `${VAR}` forms. Shell expressions such as `${SESSION_ROOT:-$HOME/.codex/sessions}` can expand to protected roots at runtime while the guard resolves a literal unprotected path.
  - confidence: 0.88
- **[P2] Apply function cwd effects when arguments are used:** `src/infra/exec-control-command-guard.ts:838`
  - body: Function cwd tracking only considers zero-argument invocations. `f(){ cd "$1"; }; f "$HOME"; rg token` runs the search from home, but the analyzer ignores the invocation because `argv.length !== 1`.
  - confidence: 0.87

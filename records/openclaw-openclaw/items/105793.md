## Summary

Keep this PR open for maintainer review. The implementation appears technically sound and well-proven, but it deliberately changes upgrade behavior in an irrecoverably ambiguous state: preserving and warning avoids resurrecting deleted runs, while potentially withholding legitimate legacy runs. That compatibility contract and its operator recovery UX need explicit owner approval before merge.

## What This Changes

Moves legacy subagent registry import and cleanup out of runtime loading into automatic doctor migration with durable SQLite receipts, retryable source cleanup, and updated SQLite-first tests.

## Best Possible Solution

Keep runtime strictly SQLite-only and doctor as the sole legacy migration owner, while adopting a documented preserve-and-warn policy for ambiguous sources with a clear, non-destructive Doctor recovery action and focused fresh-upgrade plus interrupted-cleanup proof.

Question: When SQLite has no subagent rows, runs.json exists, and no trustworthy migration receipt establishes provenance, should Doctor preserve and warn rather than automatically importing the file?

Rationale: Source inspection cannot determine whether such a file contains legitimate unimported state or stale state whose rows were intentionally removed; either automatic choice can cause session-state harm.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Preserve and warn (recommended):** Keep the source untouched, avoid resurrection, and provide an explicit Doctor recovery action for operators who confirm the file is authoritative.
- **Automatically import:** Prioritize recovery of possible legacy-only runs, accepting that a stale source can recreate intentionally removed registry state.
- **Pause the migration:** Do not land the ownership change until a stronger provenance mechanism can distinguish legitimate legacy state from stale sources.

## Reproduction Assessment

Yes. The PR documents a current-main fault injection where SQLite import commits, JSON cleanup fails with EPERM, canonical rows are later cleared, and the stale JSON source is imported again.

## Solution Assessment

The SQLite-only runtime and doctor-owned transactional migration are the narrowest maintainable architecture. The preserve-and-warn edge policy is a reasonable fail-safe, but its recovery UX and compatibility tradeoff require maintainer confirmation.

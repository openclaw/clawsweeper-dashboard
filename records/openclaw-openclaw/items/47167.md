Question: Should OpenClaw expose mention-skipped, pre-session inbound content to installed plugins through a public read-only hook, and should that visibility require an explicit operator/plugin gate?

Rationale: This changes the plugin privacy boundary by allowing plugins to observe content before current mention/session dispatch gates expose it publicly.

Likely owner: obviyus

Owner confidence: high

Options:

- **Gate The Public Hook Before Landing (recommended):** Add an explicit operator/plugin permission or access gate, document the payload boundary, and land the hook only after that contract is visible.
- **Approve Installed-Plugin Trust:** Accept that any installed plugin registering the hook may observe skipped inbound content without an extra gate, and document that security model clearly.
- **Keep Internal Ingest Only:** Pause or reject the public hook and leave full-fidelity archive plugins dependent on internal or channel-specific integrations for now.

Yes, source inspection is enough to reproduce the gap: current main lacks the requested public hook, ignores unknown typed hooks, and representative mention-skip paths return before public message_received can run.

## Solution Assessment

Unclear until maintainer review. A separate read-only hook is a plausible owner-boundary solution that preserves message_received semantics, but the public API and privacy gate need maintainer approval.

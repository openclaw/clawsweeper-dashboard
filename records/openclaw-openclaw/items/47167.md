## Summary

Keep this open: current main and the latest release still do not expose a public early inbound Plugin SDK hook for mention-skipped messages, and the linked implementation PR remains the active API/privacy decision point.

## What This Changes

The issue requests a passive read-only inbound plugin hook so archive plugins can observe group messages skipped by mention gating without creating sessions or replies.

## Best Possible Solution

Resolve the linked implementation PR or a maintainer-approved successor by approving the skipped-message visibility contract, adding any required opt-in gate, and explicitly tracking non-Telegram rollout if it is not included.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should trusted installed plugins be allowed to observe mention-skipped inbound group messages through a public read-only hook, and does that hook require an explicit operator or plugin opt-in gate?

Rationale: The requested hook enables the plugin use case, but it deliberately exposes content that current public plugin hooks do not see because mention gating prevents dispatch/session entry.

Likely owner: obviyus

Owner reason: They authored the shipped partial internal-hook implementation and are closest in history to the current skipped-message visibility boundary.

Owner confidence: medium

Options:

- **Approve a gated public hook (recommended):** Add or require an explicit opt-in/access gate for `inbound_observed` so archive plugins can observe skipped messages only when the operator has enabled that visibility.
- **Approve installed-plugin trust as sufficient:** Land the public read-only hook without an additional gate and document that installed plugins may observe skipped inbound content.
- **Keep only internal ingest for now:** Decline the public hook until a broader plugin permission model or multi-channel design is ready.

## Reproduction Assessment

Yes. Source inspection shows the Telegram mention-skip branch returns before the downstream public `message_received` runner can fire, and current main only provides an opt-in internal hook path.

## Solution Assessment

Yes, conditionally. A separate read-only hook is cleaner than moving `message_received` earlier, but it needs maintainer approval or a gate for the plugin visibility boundary before it becomes the best final solution.

## What This Changes

The PR adds provider-aware web_search tool-parameter schema resolution from the active plugin registry, wires it into tool construction, updates tests, and revises the web tool docs.

## Best Possible Solution

Share the runtime candidate ordering and availability logic for a dry schema pass, preserve the no-cold-load active-registry constraint, and document the fallback count limit as fixed at 10.

## Reproduction Assessment

Yes by source inspection: current main advertises a fixed web_search schema, and existing runtime tests prove auto-detect fallback behavior that the new schema helper does not mirror. I did not run tests because this review was read-only and the checkout had to remain byte-clean.

## Solution Assessment

No as currently patched; provider-owned schema is the right layer, but the implementation needs to share execution's ordered-candidate fallback semantics rather than resolving a single target id. The docs also need to distinguish fallback max count from provider-specific schema limits.

- **[P2] Mirror execution fallback when choosing the schema:** `src/web-search/runtime.ts:496-502`

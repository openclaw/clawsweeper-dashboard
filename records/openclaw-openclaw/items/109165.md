## Label Justifications

- `P1`: The proposed fix targets an indefinite LINE inbound-media stall, but its current form can also break a real channel message workflow by rejecting valid media.
- `merge-risk: 🚨 compatibility`: Merging changes the existing 15-second readiness limit into a total transfer limit for LINE installations.
- `merge-risk: 🚨 message-delivery`: Valid inbound media can be suppressed when preparation and download exceed the newly shared 15-second budget.

## Summary

The hang is real, but the patch changes a readiness-only 15-second timer into a total transfer deadline. LINE serves potentially large media through this endpoint, so the proposed implementation can reject healthy downloads and is not ready to merge.

## What This Changes

The PR moves LINE inbound media’s 15-second timer above readiness polling and stream persistence, destroys the response stream on abort, and adds fake-stream and loopback deadline tests.

## Best Possible Solution

Keep the existing readiness budget, add a distinct body wall-clock sized for LINE’s large-media contract, abort and destroy the stream on that body deadline, and cover late-readiness plus slow-but-valid completion alongside the dripping-body regression.

## Reproduction Assessment

Yes from source and controlled loopback: current main clears the readiness timer after headers, so a continuously dripping body can keep `saveMediaStream` pending indefinitely. The branch’s loopback test exercises that failure shape, although it is not live LINE proof.

## Solution Assessment

No. Extending abort ownership through persistence is correct, but reusing the 15-second readiness budget for the entire potentially large media transfer is not the safest fix; readiness and body deadlines need separate contracts.

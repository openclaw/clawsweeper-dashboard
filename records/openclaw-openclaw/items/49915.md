## Summary

Keep open: current main and the latest release still have a source-reproducible Feishu text slash-command path where command authorization can resolve false and whole-message control commands can complete with no visible reply; related open PR work is only partial or still unmerged.

## What This Changes

The issue reports that Feishu group slash commands such as `/new`, `/status`, and `/model` do not execute and may be dropped as empty-content events.

## Best Possible Solution

Land a maintainer-approved Feishu text-command contract that covers group and DM `/new`, `/status`, `/model`, and adjacent control commands without unintentionally broadening other channels.

## Maintainer Decision

Kind: security_boundary

Question: Should Feishu text slash commands with no explicit command allowlist inherit already-admitted Feishu sender access, or should the shared command-gating helper treat all-unconfigured access-group authorizers as allowed across channels?

Rationale: Both shapes can fix the user symptom, but they define different command-authorization security boundaries and upgrade behavior for Feishu versus all channels using the shared helper.

Likely owner: steipete

Owner reason: The strongest history signal for both the shared command gate and current Feishu/channel context code is on steipete-authored commits.

Owner confidence: high

Options:

- **Prefer Feishu-scoped inheritance (recommended):** Authorize Feishu text slash commands for senders already admitted by Feishu DM/group policy when no Feishu command allowlist is configured, while preserving explicit allowlist denial and adding Feishu DM/group proof.
- **Approve shared helper change:** Change `resolveCommandAuthorizedFromAuthorizers` globally so all-unconfigured access-group command authorizers are allowed, with cross-channel security and compatibility tests.
- **Keep fail-closed default:** Require explicit command allowlists for Feishu control commands and document the operator action instead of changing runtime defaults.

Yes. Source inspection on current main shows Feishu supplies command text into the shared command-authorization path, an empty command allowlist resolves unauthorized under default access groups, and unauthorized whole-message control commands can return no reply; I did not run live Feishu.

## Solution Assessment

Unclear until maintainers choose the authorization boundary. A Feishu-scoped admitted-sender fix appears safer, while the linked shared-helper candidate could fix the symptom but changes command authorization semantics across other channels.

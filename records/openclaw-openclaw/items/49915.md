## Label Justifications

- `P1`: Feishu slash commands are a broken channel control workflow that can silently drop command-only messages for real users.
- `impact:message-loss`: The report and current source path show slash-command messages can produce no command action and no visible reply.
- `impact:session-state`: Commands such as `/new` and `/reset` affect session reset/state, so failure leaves users in the old session context.
- `impact:auth-provider`: The failure path is command authorization and includes `/model`, which affects model-selection control through the channel.

## Summary

Keep open: current main and the latest release still have the Feishu text-command authorization path where an unconfigured command allowlist denies slash commands under default access-groups mode, and the linked fixing PR has not landed.

## What This Changes

The issue reports Feishu group slash commands such as `/new`, `/status`, and `/model` failing or being swallowed instead of executing or reaching the agent as text.

## Best Possible Solution

Land a proof-backed fix that either narrowly authorizes Feishu text commands for already-admitted senders with no Feishu command allowlist, or explicitly changes the shared command-gating contract with cross-channel security coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Feishu slash commands with no explicit command allowlist inherit already-admitted Feishu sender access, or should `resolveCommandAuthorizedFromAuthorizers` change globally for every channel?

Rationale: Both choices can fix the user symptom, but the shared-helper approach changes the control-command authorization boundary across channels and was already flagged as security-sensitive in related PR review.

Likely owner: steipete

Owner reason: The strongest current-main history for the shared command gate and related security-boundary behavior points to this owner for the policy choice.

Owner confidence: high

Options:

- **Prefer Feishu-scoped inheritance (recommended):** Authorize Feishu text commands for senders already admitted by Feishu DM/group policy when no Feishu command allowlist is configured, while preserving explicit allowlist denial.
- **Approve shared helper change:** Change `resolveCommandAuthorizedFromAuthorizers` globally so an all-unconfigured command-authorizer set is allowed under access groups, with cross-channel security and upgrade tests.
- **Keep fail-closed default:** Require explicit command allowlists for Feishu control commands and document/configure the operator action instead of changing runtime defaults.

## Reproduction Assessment

Yes, at source level: current main still sends Feishu slash-command authorization through an empty command allowlist that resolves to `CommandAuthorized=false` under default access groups. I did not run a live Feishu workspace in this read-only review.

## Solution Assessment

Unclear until maintainer policy is chosen: a Feishu-scoped fix is the narrowest safer direction, while the open shared-helper PR fixes the symptom but broadens the command authorization boundary across channels.

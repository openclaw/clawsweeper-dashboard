## Label Justifications

- `P1`: The PR touches agent session compaction and cron watchdog timeout behavior that can wedge or delay real scheduled agent runs.
- `merge-risk: 🚨 compatibility`: The cron phase remap changes upgrade behavior for existing isolated cron jobs that previously received a pre-execution stall diagnostic at `context_engine`.
- `merge-risk: 🚨 session-state`: The provider bypass can disable the existing guard for GLM-style sessions and reintroduce unbounded context/session growth for some provider configurations.
- `merge-risk: 🚨 availability`: The watchdog remap can turn a setup stall into a full job-timeout wait, reducing timely failure and recovery for scheduled agent runs.

## Summary

Keep the PR open but do not merge this patch as-is: the cron watchdog half conflicts with the landed #74803 context-engine stall guard and overlaps the canonical #93912/#93914 watchdog work, while the provider half special-cases an unregistered `zhipu` provider id without current OpenClaw contract proof.

## What This Changes

The PR excludes `provider: "zhipu"` from silent-overflow auto-compaction guarding and remaps `model_resolution`, `auth`, and `context_engine` cron watchdog phases from pre-execution to execution with regression-test updates.

## Best Possible Solution

Keep the cron setup-progress decision in #93912/#93914 or an equivalent maintainer-approved fix that preserves the #74803 stall guard, and only add a Zhipu exemption if the provider contract is explicit and endpoint-backed rather than a bare provider-name bypass.

## Reproduction Assessment

Yes for the cron side: current main has a regression test that emits `context_engine` and expects the pre-execution watchdog to abort before the full job timeout. No live Zhipu-provider reproduction is established because current OpenClaw docs and manifest expose `zai`, not a `zhipu` provider contract.

## Solution Assessment

No; the cron change is a partial duplicate of open canonical watchdog work and the provider change relies on an unproven provider id. The safer path is to resolve the watchdog semantics in the canonical PR and make any provider exemption endpoint- or manifest-backed.

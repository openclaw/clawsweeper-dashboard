## Label Justifications

- `P2`: This is useful security hardening with a bounded but user-visible CLI fallback compatibility defect.
- `merge-risk: 🚨 compatibility`: The new fixed CLI fallback can reject images that existing configurations intentionally allow through a higher mediaMaxMb value.
- `merge-risk: 🚨 availability`: A valid image turn can fail specifically when execution reaches a CLI backend because the configured limit is not propagated.

## Summary

Keep this PR open: the final-head runtime proof now demonstrates the intended guard, and the provider-side implementation appears sound, but the CLI path introduces an unconditional 6 MiB ceiling when its caller omits the newly added limit, which can break configurations that intentionally accept larger images.

## What This Changes

The PR adds pre-decode base64 size estimates to CLI and generated-image paths and propagates configured image limits through Google, OpenAI, OpenRouter, and generic compatible providers.

## Best Possible Solution

Keep the pre-decode estimator, but resolve the active agent media byte limit at the CLI execution boundary and pass it through prepareCliPromptImagePayload to writeCliImages; add coverage showing that a configured limit above 6 MiB remains accepted while payloads above that configured limit are rejected before decoding.

Yes at source level: configure an agent media limit above 6 MiB and route an image between 6 MiB and that configured limit through a CLI backend; the execution caller omits maxBytes, so writeCliImages applies the lower constant.

## Solution Assessment

No, not yet. Reusing the shared estimator and propagating provider limits is the right design, but the CLI guard must preserve the existing configured media-limit contract rather than introduce an unrelated fixed ceiling.

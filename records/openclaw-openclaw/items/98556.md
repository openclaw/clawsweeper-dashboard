## Label Justifications

- `P1`: The report describes silent recurring model spend and eventual provider spend-cap failure on a default scheduled workflow, with a source-level path still present on current main.
- `impact:session-state`: The failure depends on heartbeat polling a stale main session whose `lastInteractionAt` is intentionally not refreshed by system-event turns.

## Summary

Keep open: current main still has a source-level path where scheduled heartbeats resolve and run against the main session without checking stale `lastInteractionAt` or session reset freshness, while heartbeat system events intentionally preserve that stale timestamp. https://github.com/openclaw/openclaw/issues/14051 covers broader activity-based idle timeout, but this report adds a concrete non-empty-HEARTBEAT.md runaway-spend case plus repeated provider auth-failure backoff that is not fully owned by the existing missing-file work.

## What This Changes

The issue asks OpenClaw to stop, cap, or back off scheduled heartbeat polling for long-idle main sessions so silent model spend and repeated provider auth failures do not continue indefinitely.

## Best Possible Solution

Add a maintainer-approved heartbeat preflight that skips scheduled non-event heartbeat runs when the resolved session is stale under existing session lifecycle freshness, while explicitly deciding whether cost caps and OK/auth-error backoff belong in this issue or follow-up work.

## Reproduction Assessment

Yes at source level: scheduled heartbeat preflight resolves the session and file/task gates but does not evaluate session freshness, while session tests show heartbeat turns intentionally reuse stale entries and preserve `lastInteractionAt`. No live provider-spend reproduction was run in this read-only review.

## Solution Assessment

Unclear as a complete fix until maintainers choose policy, but the narrowest maintainable first step appears to be a scheduled-heartbeat stale-session guard using existing session lifecycle freshness. New spend caps and OK/auth-error backoff would be useful defense-in-depth but need explicit product semantics.

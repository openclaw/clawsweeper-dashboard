## Label Justifications

- `P2`: This is a useful multi-device delivery improvement with source-backed impact, but it is not an emergency and needs product/security direction before implementation.
- `impact:message-loss`: Users relying on browser-to-mobile continuity can miss replies because WebChat-originated replies currently stay in WebChat.
- `impact:session-state`: The requested behavior depends on persisted last-channel and target delivery state surviving cross-surface WebChat interaction.
- `impact:security`: The feature would move Control UI output into a previous external chat, making privacy and authorization boundaries central.
- `maturity:stable`: The issue names Discord as affected, and Discord is scored M4 Stable with Conversation Routing and Delivery completeness Stable/LTS-supported.

## Summary

Keep open. Current main and v2026.6.11 still intentionally keep WebChat/Control UI replies internal unless an explicit delivery route is set, and the requested opt-in mirroring config remains a product and security-boundary decision.

## What This Changes

Request an optional session config flag that mirrors WebChat/Control UI-originated replies to the session's last established external channel.

## Best Possible Solution

Define one explicit, default-off cross-surface delivery policy with stale-route, authorization, duplicate-delivery, failure-handling, schema, docs, and live-channel proof, then implement WebChat-to-last-external mirroring only within that accepted policy.

- **Add Explicit Opt-In Mirroring (recommended):** Implement a default-off session policy with route freshness, authorization, duplicate-delivery, failure logging, schema/docs, and live Discord or Telegram proof.
- **Fold Into Origin-Delivery Policy:** Keep this issue as the WebChat scenario while https://github.com/openclaw/openclaw/issues/54531 defines a broader durable origin-channel delivery model.
- **Keep WebChat Isolated:** Document explicit sends or channel-docking workflows as the supported bridge and do not add automatic mirroring from WebChat to external channels.

## Reproduction Assessment

Yes, at source level. Current main's WebChat route guard returns internal WebChat without an explicit deliver route, reply routing suppresses origin delivery for internal WebChat turns, and tests assert that WebChat clients do not inherit external routes.

## Solution Assessment

Unclear until maintainers choose the policy. The proposed default-off flag is plausible, but the best solution must first define route freshness, authorization, duplicate-delivery, privacy, and failure handling.

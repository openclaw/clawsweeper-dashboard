## Summary

Keep open. Current main and v2026.6.11 still keep WebChat/Control UI replies internal unless an explicit delivery route exists, and adding mirroring is a product, security, and config-surface decision.

## What This Changes

The issue requests a default-off session config option that mirrors Control UI webchat replies to the session's last active external channel.

## Best Possible Solution

Define one explicit, default-off cross-surface delivery policy with route freshness, authorization, duplicate-delivery handling, failure logging, schema/docs, and live-channel proof before implementing WebChat-to-last-external mirroring.

Question: Should OpenClaw support default-off WebChat-to-last-external mirroring as its own session policy, fold it into the broader origin-channel delivery policy, or keep WebChat isolated from external routes?

Rationale: The requested behavior intentionally duplicates internal Control UI output into an external conversation selected from persisted session route state, so code inspection cannot safely choose the product and privacy boundary without maintainer intent.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Add Explicit Opt-In Mirroring (recommended):** Implement a default-off session policy with route freshness, authorization, duplicate-delivery protection, failure logging, schema/docs, and live Discord or Telegram proof.
- **Fold Into Origin Delivery Policy:** Keep this issue as the WebChat scenario while https://github.com/openclaw/openclaw/issues/54531 defines one durable origin-channel delivery model.
- **Keep WebChat Isolated:** Document explicit sends or channel-docking workflows as the supported bridge and avoid automatic mirroring from WebChat to external channels.

## Reproduction Assessment

Yes, at source level. Current main's WebChat route guard returns internal WebChat without an explicit deliver route, reply routing suppresses origin delivery for internal WebChat turns, and tests assert that WebChat clients do not inherit external routes.

## Solution Assessment

Unclear until maintainers choose the policy. The proposed default-off flag is plausible, but the best solution must first define route freshness, authorization, duplicate-delivery, privacy, and failure handling.

## Summary

Keep open: current main still has provider replay paths that classify media-typed tool-result blocks by type without validating payload, and the same-repo fix PR is still open. The originally suspected `sanitizeContentBlocksImages` path is already guarded, so the useful remaining work is provider replay/materialization, not closing this as implemented.

## What This Changes

The issue reports that OpenAI-compatible provider tool results can become payload-less image/media blocks in session history, making text tool outputs unreadable to the model over longer sessions.

## Best Possible Solution

Review and repair https://github.com/openclaw/openclaw/pull/99338 so payload-aware media validation covers the full OpenAI-compatible provider replay path, then close this issue after the fix merges while keeping broader leftover symptoms linked to https://github.com/openclaw/openclaw/issues/96857.

## Reproduction Assessment

Yes, at source level: current main still classifies media-typed tool-result blocks by type alone in shared provider replay helpers used by OpenAI-compatible conversion. I did not run a live Feishu/DeepSeek reproduction in this read-only cleanup review.

## Solution Assessment

Unclear as submitted: provider replay/materialization is the right repair layer, but the open PR may need to share the payload-aware guard with the earlier transform/downgrade boundary. A separate sanitizer-only fix would not be the best solution because that path is already guarded.

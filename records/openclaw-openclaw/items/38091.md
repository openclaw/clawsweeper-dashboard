## Summary

Keep open: current main has useful reconnect mitigations for queued sends and server-side in-flight run snapshots, but the WebChat UI still does not consume `chat.history`'s `inFlightRun` to re-adopt the active run after reconnect, and the overlapping recovery PR remains open and conflicting.

## What This Changes

Restore OpenClaw WebChat/Control UI reconnect behavior so WebSocket reconnects do not terminate or lose in-flight AI session state.

## Best Possible Solution

Define and land one current-main active-run reconnect contract that lets `chat.history` or session active-run data re-adopt UI run id, stream, and abort state after reconnect, then validate it with focused UI/gateway tests and real WebChat reconnect proof.

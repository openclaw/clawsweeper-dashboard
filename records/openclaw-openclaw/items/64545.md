## Label Justifications

- `P1`: A forgeable Mattermost interaction token can cross a channel authorization boundary and trigger agent action flows when the bot-token-derived signing root is exposed.
- `impact:security`: The issue is about credential-derived HMAC signing and the authorization boundary for Mattermost interaction callbacks.

## Summary

Keep open: current main and v2026.6.11 still derive Mattermost interaction signing from the bot token with a public HMAC key, while the same-repository candidate fix remains open and needs security/product direction before this issue can close.

## What This Changes

The issue asks OpenClaw to stop using a bot-token-derived Mattermost interaction signing secret that can be recomputed by anyone with the bot token.

## Best Possible Solution

Land a refreshed version of https://github.com/openclaw/openclaw/pull/64546, or a narrow replacement, that removes bot-token-derived signing and includes explicit setup, docs, upgrade, and old-forgery rejection coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What permanent Mattermost interaction-signing contract should replace the current bot-token-derived secret?

Rationale: Changing the signing root repairs a security boundary but also changes a documented integration contract and may require new SecretRef, generated credential, doctor, and upgrade behavior.

Likely owner: steipete

Owner reason: The decision is a security-boundary and channel authorization policy choice, and recent history ties steipete to shared channel security hardening.

Owner confidence: medium

Options:

- **Per-account stored secret (recommended):** Generate or configure a per-account interaction secret, persist it through the plugin-owned credential path, update docs, and reject old bot-token-derived forgeries after an explicit upgrade path.
- **Config-only explicit secret:** Require operators to set a new per-account interaction secret and fail closed when it is missing, accepting a sharper setup and upgrade burden.
- **Defer pending broader channel auth review:** Keep the issue open until maintainers decide whether Mattermost interactions need a shared channel callback-auth design instead of a Mattermost-only contract.

## Reproduction Assessment

Yes. Source inspection of current main shows the interaction secret is deterministically derived from the bot token with a public HMAC key, and that derived secret verifies callback _token values before dispatch.

## Solution Assessment

Yes on direction, but not yet as a completed repository state. The maintainable fix is to stop using the bot token as the signing root and provide a durable per-account interaction secret with explicit setup, docs, and upgrade behavior.

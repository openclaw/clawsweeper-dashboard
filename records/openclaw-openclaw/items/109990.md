## Label Justifications

- `P1`: The patch targets a real channel shutdown workflow but currently introduces a restart-time resource leak in an existing Zalo polling configuration.
- `merge-risk: 🚨 availability`: A pre-aborted polling startup can retain a plugin HTTP route because cleanup handlers added after `stop()` are skipped by the final idempotent cleanup call.

## Summary

Keep this PR open for revision: the new pre-aborted branch marks the monitor stopped before cleanup handlers exist, so a polling account with hosted-media routing can register a route afterward that the idempotent final `stop()` never unregisters.

Likely related people: @vincentkoc has recent Zalo integration-boundary history, and @romneyda has recent Zalo runtime and QA work; both are medium-confidence routing candidates.

## What This Changes

Calls the Zalo monitor's stop path synchronously when its `AbortSignal` is already aborted instead of only registering an abort listener.

## Best Possible Solution

Handle an already-aborted signal before acquiring any startup resources, or make cleanup registration immediately execute when the monitor is already stopped, then cover hosted-media cleanup and avoided polling startup work with a focused regression test.

Yes, from source: use a pre-aborted signal in polling mode with a configured hosted-media URL/path, then observe that the route unregister callback is appended after `stopped` becomes true and is skipped during final cleanup. This was not executed against a live account during this review.

## Solution Assessment

No. Calling `stop()` before resource acquisition creates an ordering bug; the narrower solution is to exit before startup work or make late cleanup registration safe, with focused coverage for the hosted-media path.

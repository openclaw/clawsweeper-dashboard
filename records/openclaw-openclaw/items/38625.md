Question: Should OpenClaw expose gateway update execution to HTTP-authenticated operator callers, and if so should it be a new `/admin/update` endpoint or an allowlisted Admin HTTP RPC wrapper around `update.run`?

Rationale: The request expands host package-update and restart authority from current CLI/WebSocket/control-plane paths to an HTTP surface and adds target-version semantics that current `update.run` does not define.

Likely owner: steipete

Owner reason: This is the best available decision owner from the history because the unresolved choice is the gateway update/admin security boundary rather than the shallow health serializer alone.

Owner confidence: medium

Options:

- **Split and design first (recommended):** Keep the version metadata half in the narrower open tracker and require a maintainer-owned security/API design before adding HTTP update execution.
- **Expose through Admin HTTP RPC:** Add `update.run` or a narrow wrapper to the opt-in Admin HTTP RPC plugin with explicit trusted-ingress, auth, audit, rate-limit, handoff, and target-version proof requirements.
- **Decline HTTP update execution:** Keep update execution limited to CLI/WebSocket/control-plane paths and document that fleet tools should use those or an external orchestrator.

## Reproduction Assessment

Yes, at source level: current `/health` and `/healthz` serialize only `{ ok: true, status }`, and tests assert that shallow body. The update surface exists as privileged gateway RPC, while Admin HTTP RPC allows only `update.status`, not `update.run`.

## Solution Assessment

No, not as one automatic combined endpoint. Version reporting is a narrow additive public contract, but HTTP-triggered updates should reuse or wrap `update.run` only after maintainers approve the security boundary, field set, and target-version semantics.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose update execution to gateway-authenticated HTTP callers, and if so should it be a new /admin/update endpoint or an intentional Admin HTTP RPC wrapper around update.run?

Rationale: The request expands host package-update and restart authority from existing CLI/WebSocket/control-plane paths to a network HTTP surface, so automation cannot safely choose the auth, audit, rate-limit, and failure-mode contract.

Likely owner: steipete

Owner reason: steipete has the strongest shared history across Admin HTTP RPC, gateway update flow, and adjacent version resolution.

Owner confidence: high

Options:

- **Split and design first (recommended):** Keep version metadata in the narrower tracker and require maintainer-owned security/API design before exposing update execution over HTTP.
- **Expose through Admin HTTP RPC:** Add update.run or a narrow wrapper to the default-off Admin HTTP RPC plugin with explicit trusted-ingress, auth, audit, rate-limit, and handoff proof requirements.
- **Reject HTTP update execution:** Keep update execution limited to existing CLI/WebSocket/control-plane surfaces and document that fleet tools should use those or an external orchestrator.

## Reproduction Assessment

Yes, for source-level verification of the missing feature. Current main’s /health and /healthz serializer still returns only { ok: true, status }, and Admin HTTP RPC allowlists update.status while omitting update.run.

## Solution Assessment

No, not as one automatic combined change. Version reporting is a narrow additive public contract, but HTTP-triggered updates should reuse or wrap update.run only after maintainers approve the security boundary and API shape.

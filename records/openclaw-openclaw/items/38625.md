## Summary

Keep open: current main still lacks version metadata on the shallow HTTP health probes, and there is still no dedicated `/admin/update` endpoint or Admin HTTP RPC exposure for `update.run`. The version-only half is already tracked by https://github.com/openclaw/openclaw/issues/91795, but the HTTP update-execution half remains a security-sensitive product decision.

## What This Changes

Request to add version metadata to the Gateway health response and an authenticated `POST /admin/update` endpoint for fleet-triggered package updates.

## Best Possible Solution

Split the concerns: let https://github.com/openclaw/openclaw/issues/91795 define the public version metadata contract, and expose update execution over HTTP only through a maintainer-approved trusted admin surface that reuses `update.run` safely.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose update execution over a gateway-authenticated HTTP surface for fleet tools, and if so should it be a dedicated `/admin/update` contract or an Admin HTTP RPC wrapper around `update.run`?

Rationale: The request changes who can trigger host package updates and Gateway restarts over the network, while current code deliberately keeps `update.run` as an operator-admin control-plane write and omits it from Admin HTTP RPC.

Likely owner: steipete

Owner reason: He has the strongest combined history across Admin HTTP RPC, Gateway update/restart flow, and adjacent version-resolution work.

Owner confidence: high

Options:

- **Split and defer HTTP update authority (recommended):** Keep version metadata in the narrower tracker and require a maintainer-owned security/API design before exposing update execution over HTTP.
- **Expose via Admin HTTP RPC:** Allow or wrap `update.run` only with explicit private-ingress, auth, audit, rate-limit, failure-mode, and upgrade-proof requirements.
- **Reject HTTP update execution:** Keep update execution limited to existing CLI/WebSocket/control-plane surfaces and document that fleet tools should use those or an external orchestrator.

## Reproduction Assessment

Yes, at source level. Current main serializes `/health` and `/healthz` with only `ok` and `status`, and Admin HTTP RPC allowlists `update.status` while omitting `update.run`.

## Solution Assessment

No, not as one automatic combined change. Version reporting is a narrow additive contract, but HTTP-triggered updates should reuse or wrap `update.run` only after maintainers approve the security boundary and API shape.

Question: Should OpenClaw expose host update execution to gateway-authenticated HTTP callers, and should that be a dedicated `/admin/update` contract or an allowlisted Admin HTTP RPC wrapper around `update.run`?

Rationale: The request would turn a privileged host package-update and restart operation into a network-reachable HTTP surface, while current code exposes only `update.status` over Admin HTTP RPC and keeps `update.run` as a control-plane write.

Likely owner: steipete

Owner confidence: high

Options:

- **Split and design first (recommended):** Keep version metadata in the narrower tracker and require a maintainer-owned security/API design before exposing update execution over HTTP.
- **Expose via Admin HTTP RPC:** Allow or wrap `update.run` only with explicit private-ingress, auth, audit, rate-limit, failure-mode, and upgrade-proof requirements.
- **Reject HTTP update execution:** Keep update execution limited to existing CLI/WebSocket/control-plane surfaces and document that fleet tools should use those or an external orchestrator.

No, not as one automatic combined change. Version reporting is a narrow additive public contract, but HTTP-triggered updates should reuse or wrap `update.run` only after maintainers approve the security boundary and API shape.

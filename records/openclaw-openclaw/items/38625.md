## Summary

Keep open: current main and v2026.6.11 still lack version metadata on `/health` and `/healthz`, and authenticated HTTP update execution is not exposed. The existing `update.run` Gateway RPC solves part of the update orchestration problem, but Admin HTTP RPC only allowlists `update.status` and the version-only half is already tracked by https://github.com/openclaw/openclaw/issues/91795.

## What This Changes

The issue requests adding runtime version metadata to gateway health responses and an authenticated HTTP update endpoint for fleet operators.

## Best Possible Solution

Split the concerns: keep the public version metadata decision in https://github.com/openclaw/openclaw/issues/91795, and expose update execution only through a maintainer-approved trusted admin HTTP surface that safely reuses or wraps `update.run`.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose update execution to gateway-authenticated HTTP callers, and if so should it be a dedicated endpoint or an Admin HTTP RPC wrapper around `update.run`?

Rationale: The request expands host package-update and restart authority from existing Gateway control-plane paths to an HTTP surface, so maintainer intent is needed for auth scope, private ingress, audit/rate-limit behavior, target-version support, and failure-mode guarantees.

Likely owner: steipete

Owner reason: steipete has the strongest shared history across Admin HTTP RPC, version resolution, and the current Gateway update surface.

Owner confidence: high

Options:

- **Split and design first (recommended):** Keep the version metadata contract on the narrower open issue and require a maintainer-owned security/API design before adding HTTP update execution.
- **Expose through Admin HTTP RPC:** Allow `update.run` or a narrow wrapper in the disabled-by-default Admin HTTP RPC plugin with explicit trusted-ingress, audit, rate-limit, handoff, and target-version proof requirements.
- **Reject HTTP update execution:** Keep update execution limited to existing CLI and WebSocket control-plane paths and document that fleet tools should use those or an external orchestrator.

## Reproduction Assessment

Yes, at source level. Current main’s `/health` and `/healthz` serializer still returns only `{ ok: true, status }`, and Admin HTTP RPC allowlists `update.status` while omitting `update.run`.

## Solution Assessment

No, not as one automatic combined change. Version reporting is a narrow additive public contract, but HTTP-triggered updates should reuse or wrap `update.run` only after maintainers approve the security boundary and API shape.

## Summary

Keep open: current main still serves shallow `/health` and `/healthz` responses without version metadata, and the existing HTTP admin RPC plugin is default-off and does not expose `update.run`. The issue is useful Crab/fleet-operator context, but the update endpoint is a security-boundary/product decision rather than conservative cleanup.

## What This Changes

Request adds version metadata to the Gateway health response and an authenticated HTTP admin update endpoint for fleet tooling.

## Best Possible Solution

Split the concerns: use https://github.com/openclaw/openclaw/issues/91795 for the public version metadata contract, and add HTTP-triggered update execution only after maintainers approve the admin API/security boundary.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose update execution to gateway-authenticated HTTP callers, and if so should that be a dedicated `/admin/update` contract or an allowlisted Admin HTTP RPC wrapper around `update.run`?

Rationale: The request would grant network callers host package-update and restart authority, while current code treats `update.run` as an operator-admin control-plane write and the existing Admin HTTP RPC plugin intentionally omits it.

Likely owner: steipete

Owner reason: steipete has the strongest combined history across Admin HTTP RPC, version resolution, and update-run stabilization.

Owner confidence: high

Options:

- **Split and design first (recommended):** Keep the version field in the narrower tracker and require a maintainer-owned API/security design before exposing update execution over HTTP.
- **Expose through Admin HTTP RPC:** Add `update.run` or a wrapper to the default-off Admin HTTP RPC plugin with explicit private-ingress, auth, audit, rate-limit, and handoff proof requirements.
- **Reject HTTP update execution:** Keep update execution limited to existing CLI/WebSocket/control-plane surfaces and tell fleet tools to use those or an external orchestrator.

## Reproduction Assessment

Yes for source-level verification: current main’s `/health` and `/healthz` serializer returns only `{ ok: true, status }`, and Admin HTTP RPC allowlists `update.status` while omitting `update.run`. I did not run a live gateway because this review is read-only.

## Solution Assessment

No, not as one automatic combined change. Version reporting is a narrow additive public contract, but HTTP-triggered updates should reuse or wrap `update.run` only after maintainers approve the security boundary and API shape.

## Summary

Keep open: current main still lacks the requested public health version field and an HTTP update trigger. The health-version portion overlaps the narrower open version-metadata issue, but the HTTP update endpoint and target-version pinning are a separate security-sensitive product decision.

## What This Changes

The issue requests adding running-version metadata to the Gateway health response and a token-authenticated HTTP endpoint that can trigger host package updates with optional version pinning.

## Best Possible Solution

Keep the version-only health metadata decision on https://github.com/openclaw/openclaw/issues/91795, and separately decide whether `update.run` should be exposed through an opt-in private admin HTTP surface with documented scopes, target-version semantics, tests, and security guidance.

Question: Should OpenClaw expose host package updates over HTTP for trusted fleet tooling, and if yes should that be a dedicated `/admin/update` route or an opt-in `admin-http-rpc` allowlist expansion for `update.run` with target-version support?

Rationale: The remaining work changes a host-level control-plane boundary, duplicates or extends existing update surfaces, and may allow remote package mutation by any Gateway operator-token holder; automation cannot choose that security/product contract safely.

Likely owner: steipete

Owner confidence: high

Options:

- **Extend existing admin HTTP RPC after review (recommended):** Expose `update.run` through the existing disabled-by-default `admin-http-rpc` plugin only after maintainers approve the method, params, docs, private-ingress guidance, and tests.
- **Add a dedicated endpoint:** Create `/admin/update` as a separate core HTTP route with its own schema and docs, accepting the extra surface area and duplication risk.
- **Do not expose HTTP updates:** Keep update execution on WebSocket/control-plane and CLI paths, and ask fleet tools to use those or an operator-side wrapper instead.

Track the public health version contract in https://github.com/openclaw/openclaw/issues/91795, then expose existing `update.run` through the default-off admin HTTP RPC plugin only if maintainers approve the HTTP update-execution boundary, request schema, docs, tests, and security proof.

## Maintainer Decision

Question: Should OpenClaw expose host update execution through an authenticated HTTP operator surface, and if so should that reuse the existing default-off admin HTTP RPC plugin instead of adding a bespoke `/admin/update` endpoint?

Rationale: Current main already has `update.run` as an admin-scoped Gateway RPC and has a default-off admin HTTP RPC plugin, but deciding whether host package-manager update execution may cross HTTP is a security and product boundary choice.

Likely owner: steipete

Owner reason: They authored the admin HTTP RPC plugin and the existing Gateway config/update restart flow that bound the decision.

Owner confidence: high

Options:

- **Reuse admin HTTP RPC after approval (recommended):** If maintainers approve HTTP update execution, add `update.run` to the default-off admin HTTP RPC plugin with explicit private-ingress docs, schema/tests, and upgrade proof.
- **Keep update execution WebSocket-only:** Leave `update.run` off HTTP and direct fleet tooling to WebSocket RPC or a local trusted helper until a stronger HTTP boundary is chosen.
- **Design a separate endpoint:** Add a bespoke authenticated update endpoint only if maintainers decide the existing RPC shape cannot support fleet tooling safely.

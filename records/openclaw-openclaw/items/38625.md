Kind: security_boundary

Question: Should OpenClaw expose `update.run` over a Gateway HTTP admin surface for external fleet tools, and if so should it be through the existing default-off `admin-http-rpc` plugin rather than a new `/admin/update` endpoint?

Rationale: The current code already has a guarded Gateway `update.run` method and a default-off admin HTTP RPC plugin, but that plugin deliberately exposes only an allowlisted set of methods and excludes update execution; changing that boundary affects host package updates, restart behavior, auditability, and shared-token operator risk.

Likely owner: steipete

Owner reason: The decision centers on the `update.run` control-plane boundary and restart hardening history that Peter Steinberger introduced and maintained.

Owner confidence: high

Options:

- **Approve default-off admin RPC update.run (recommended):** Add `update.run` to the existing `admin-http-rpc` allowlist with focused security docs, tests, and no new standalone route unless the existing RPC shape is insufficient.
- **Keep update execution off HTTP:** Document WebSocket RPC or Control UI as the supported update trigger and leave HTTP admin RPC limited to status and lower-risk methods.
- **Design a new update endpoint:** Create a new endpoint only after maintainers define target-version semantics, authorization, audit, idempotency, and rollback behavior as a separate product surface.

Question: Should OpenClaw expose update execution over a gateway-authenticated HTTP surface for fleet tools, and if so should it be a dedicated `/admin/update` contract or an allowlisted Admin HTTP RPC wrapper around `update.run`?

Rationale: The request would give network callers host package-update and restart authority, while current docs treat Admin HTTP RPC as a full trusted operator surface and current code intentionally omits `update.run` from that allowlist.

Likely owner: steipete

Owner confidence: high

Options:

- **Split and defer HTTP update authority (recommended):** Keep version metadata in the narrower tracker and require a maintainer-owned security/API design before exposing update execution over HTTP.
- **Expose via Admin HTTP RPC:** Allow or wrap `update.run` only with explicit private-ingress, auth, audit, rate-limit, failure-mode, and upgrade-proof requirements.
- **Reject HTTP update execution:** Keep update execution limited to existing CLI/WebSocket/control-plane surfaces and document that fleet tools should use those or an external orchestrator.

## Solution Assessment

No, not as one automatic combined change. Version reporting is a narrow additive public contract, but HTTP-triggered updates should reuse or wrap `update.run` only after maintainers approve the security boundary and API shape.

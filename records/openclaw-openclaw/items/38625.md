## What This Changes

The issue requests an additive version field on gateway health responses and a token-authenticated HTTP admin update surface for fleet tooling.

## Best Possible Solution

Track the health version contract in https://github.com/openclaw/openclaw/issues/91795, and expose existing `update.run` through the default-off Admin HTTP RPC plugin only if maintainers approve the HTTP update-execution boundary, schema, docs, tests, and security proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose host update execution through an authenticated HTTP operator surface, and if so should that reuse the existing default-off Admin HTTP RPC plugin instead of adding a bespoke `/admin/update` endpoint?

Rationale: Current main already has `update.run` as an admin-scoped Gateway RPC and a default-off Admin HTTP RPC plugin, but allowing host package-manager update execution over HTTP is a security and product boundary choice that automation should not make.

Likely owner: steipete

Owner reason: They authored both the Admin HTTP RPC plugin and the existing Gateway update/restart flow involved in the boundary decision.

Owner confidence: high

Options:

- **Reuse Admin HTTP RPC after approval (recommended):** If maintainers approve HTTP update execution, add `update.run` to the default-off Admin HTTP RPC plugin with explicit private-ingress docs, schema/tests, and upgrade proof.
- **Keep update execution WebSocket-only:** Leave `update.run` off HTTP and direct fleet tooling to WebSocket RPC or a local trusted helper until a stronger HTTP boundary is chosen.
- **Design a separate endpoint:** Add a bespoke authenticated update endpoint only if maintainers decide the existing RPC shape cannot support fleet tooling safely.

## Risks / Open Questions

- Exposing `update.run` over bearer-authenticated HTTP would let any holder of the Gateway operator secret orchestrate host package updates and restarts, so maintainers need to approve that boundary explicitly.
- The requested `target_version` body parameter is not part of the current `update.run` schema, and version pinning semantics would need product design across package, git, and managed-service update paths.
- The version metadata half is already tracked by https://github.com/openclaw/openclaw/issues/91795, so bundling it with HTTP update execution could slow the narrower observability decision.
- Public health version metadata is additive, but commit or build metadata can fingerprint deployments; the approved unauthenticated field set should be deliberate.

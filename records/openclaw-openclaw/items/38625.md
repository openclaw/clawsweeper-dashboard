Question: Should OpenClaw expose update execution over a gateway-authenticated HTTP surface for fleet tools, and if so should it be a dedicated `/admin/update` contract or an allowlisted Admin HTTP RPC wrapper around `update.run`?

Rationale: The requested HTTP update path crosses from operator API access into host package replacement and restart authority, while current code intentionally keeps `update.run` off the Admin HTTP RPC allowlist.

Likely owner: steipete

Owner confidence: high

Options:

- **Split and defer HTTP update authority (recommended):** Keep the version metadata decision in the narrower tracker and require maintainer-owned security/API design before exposing update execution over HTTP.
- **Expose through Admin HTTP RPC:** Allow or wrap `update.run` only with explicit private-ingress, auth, audit, rate-limit, target-version, failure-mode, and upgrade-proof requirements.
- **Reject HTTP update execution:** Keep update execution limited to existing CLI/WebSocket/control-plane surfaces and document that fleet tools should use those or an external orchestrator.

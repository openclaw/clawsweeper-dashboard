## Summary

Keep open: current main and v2026.6.11 still lack version metadata on `/health` or `/healthz`, and the authenticated HTTP update request is not superseded because `update.run` exists only as a Gateway control-plane method while the default-off admin HTTP RPC plugin intentionally exposes `update.status` but not `update.run`.

## What This Changes

The issue requests runtime version metadata in the gateway health response plus an authenticated HTTP endpoint that can trigger host package-manager updates.

## Best Possible Solution

Resolve version metadata in the canonical version-only issue, and if maintainers approve HTTP-triggered updates, expose the existing `update.run` through the default-off admin HTTP RPC contract with docs and focused auth/security/rate-limit tests instead of adding a bespoke endpoint.

Owner confidence: high

Options:

- **Expose through admin HTTP RPC (recommended):** Approve a narrow `update.run` allowlist expansion in the existing default-off plugin, with docs and security tests for trusted private ingress only.
- **Keep HTTP update blocked:** Leave update execution on CLI/WebSocket control-plane surfaces and keep HTTP admin RPC limited to status/observability methods.
- **Design a separate endpoint:** Sponsor a new HTTP endpoint only if maintainers want a response contract materially different from Gateway RPC.

## Solution Assessment

## Risks / Open Questions

- Exposing a host package-manager update trigger over HTTP changes the Gateway security boundary, even when authenticated by the existing gateway token.
- A bespoke `POST /admin/update` endpoint would duplicate the existing `update.run` and admin HTTP RPC architecture unless maintainers explicitly want a separate request/response contract.
- Publishing more than a version-only field, such as commit or build metadata, can increase deployment fingerprinting detail on unauthenticated health probes.
- Any health metadata change must preserve the current cheap, pre-config, non-blocking liveness behavior of `/healthz`.

## Summary

Keep open: current main and v2026.6.11 still lack version metadata on `/health` and `/healthz`, and the current Admin HTTP RPC plugin exposes `update.status` but not `update.run`. The version-only part is already covered by a narrower open issue, while HTTP-triggered updates remain a product and security-boundary decision.

## What This Changes

Request to add a `version` field to the Gateway health response and an authenticated HTTP update endpoint for fleet update orchestration.

## Best Possible Solution

Split the concerns: use https://github.com/openclaw/openclaw/issues/91795 for the public version metadata contract, and expose update execution over an opt-in trusted admin HTTP surface only after maintainers approve the security model and API shape.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose update execution to gateway-authenticated HTTP callers, and if so should it be a new `/admin/update` endpoint or an intentional Admin HTTP RPC wrapper around `update.run`?

Rationale: The request expands host package-update and restart authority from existing CLI/WebSocket/control-plane paths to an HTTP surface, so automation cannot safely choose the auth, audit, rate-limit, ingress, and failure-mode contract.

Likely owner: steipete

Owner reason: steipete has the strongest shared history across Admin HTTP RPC, gateway update flow, and adjacent version resolution.

Owner confidence: high

Options:

- **Split and design first (recommended):** Keep the version field decision in the narrower issue and require a maintainer-owned security/API design before exposing update execution over HTTP.
- **Expose through Admin HTTP RPC:** Add `update.run` or a narrow wrapper to the disabled-by-default Admin HTTP RPC plugin with explicit private-ingress, auth, audit, rate-limit, and handoff proof requirements.
- **Reject HTTP update execution:** Keep update execution limited to existing CLI/WebSocket/control-plane surfaces and document that fleet tools should use those or an external orchestrator.

## Reproduction Assessment

Yes, at source level. Current main’s `/health` and `/healthz` serializer still returns only `{ ok: true, status }`, and Admin HTTP RPC allowlists `update.status` while omitting `update.run`.

## Solution Assessment

No, not as one automatic combined change. Version reporting is a narrow additive public contract, but HTTP-triggered updates should reuse or wrap `update.run` only after maintainers approve the security boundary and API shape.

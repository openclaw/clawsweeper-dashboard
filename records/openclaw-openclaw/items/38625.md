## Summary

Keep open: current main and v2026.6.11 still return shallow `/health` and `/healthz` payloads without version metadata, and the existing HTTP admin surfaces do not intentionally expose `update.run`. The version-only half has a narrower open tracker, while HTTP-triggered host updates remain a product and security-boundary decision.

## What This Changes

The issue requests adding runtime version metadata to gateway health responses and an authenticated HTTP admin endpoint that can trigger host package updates.

## Best Possible Solution

Split the concerns: resolve the version field through the narrower health/version tracker, and separately decide whether remote update orchestration belongs in Admin HTTP RPC, a dedicated endpoint, or the external updater architecture.

Rationale: The requested endpoint would give network callers package-update and restart authority, while current HTTP admin surfaces are default-off, allowlisted, and currently expose update status but not update execution.

Options:

- **Split version metadata and defer update HTTP (recommended):** Keep the version field in the narrower public metadata discussion and require a maintainer-owned security/API design before exposing update execution over HTTP.

- **Reject HTTP update execution:** Keep update execution limited to existing CLI/WebSocket/control-plane paths and document that fleet tools should use those or an external orchestrator.

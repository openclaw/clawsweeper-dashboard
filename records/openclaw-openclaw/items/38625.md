## Summary

Keep open: current main and v2026.6.11 still expose shallow `/health` and `/healthz` payloads without runtime version metadata, and the opt-in Admin HTTP RPC surface still exposes `update.status` but not `update.run`. The version-only half is already tracked by https://github.com/openclaw/openclaw/issues/91795, while HTTP-triggered update execution remains a product and security-boundary decision.

## What This Changes

The issue requests version metadata in the gateway health response and an authenticated HTTP endpoint to trigger host package-manager updates.

## Best Possible Solution

Split the concerns: let https://github.com/openclaw/openclaw/issues/91795 own the public version metadata contract, and expose update execution over HTTP only through a maintainer-approved trusted admin surface with explicit security and upgrade proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose update execution to gateway-authenticated HTTP callers, and if so should it be a new `/admin/update` endpoint or an intentional Admin HTTP RPC wrapper around `update.run`?

Rationale: The requested endpoint would expand host package-update and restart authority from existing CLI/WebSocket/control-plane paths to an HTTP surface, which needs maintainer intent for auth scope, trusted ingress assumptions, auditability, rate limiting, and failure-mode guarantees.

Likely owner: steipete

Owner reason: steipete has the strongest shared history across Admin HTTP RPC, gateway update flow, and adjacent version resolution.

Owner confidence: high

Options:

- **Split and design first (recommended):** Keep version metadata in the narrower tracker and require a maintainer-owned security/API design before exposing update execution over HTTP.
- **Expose via Admin HTTP RPC:** Add `update.run` or a narrow wrapper to the disabled-by-default Admin HTTP RPC plugin with explicit private-ingress, auth, audit, rate-limit, and handoff proof requirements.
- **Reject HTTP update execution:** Keep update execution limited to existing CLI/WebSocket/control-plane surfaces and document that fleet tools should use those or an external orchestrator.

## Reproduction Assessment

Yes, at source level. Current main’s `/health` and `/healthz` serializer still returns only `{ ok: true, status }`, and Admin HTTP RPC allowlists `update.status` while omitting `update.run`.

## Solution Assessment

No, not as one automatic combined change. Version reporting is a narrow additive public contract, but HTTP-triggered updates should reuse or wrap `update.run` only after maintainers approve the security boundary and API shape.

## Summary

The updated branch fixes the earlier UTF-8 U+FFFD sentinel defect, but it now rejects valid declared non-UTF-8 response bodies containing U+FFFD and removes the existing `text()` fallback after an `arrayBuffer()` failure. Both are bounded compatibility regressions that need repair before merge.

## What This Changes

The PR reads raw response bytes when available, uses fatal UTF-8 decoding to distinguish malformed bytes from a legitimate U+FFFD character, and adds regression tests for that behavior.

## Best Possible Solution

Keep raw-byte validation, but perform fatal validation with the same resolved charset used for the response decode and preserve the existing `res.text()` fallback when byte acquisition fails.

## Reproduction Assessment

Yes, from source: a `charset=utf-16le` response whose raw bytes encode U+FFFD will decode successfully through the charset-aware path but fail the new hard-coded fatal UTF-8 validation; a Response-like object can also reject `arrayBuffer()` while resolving `text()`.

## Solution Assessment

No. Raw-byte validation is the right boundary, but a universal UTF-8 validator conflicts with the existing charset-aware decoder and the immediate empty return removes the former fallback behavior.

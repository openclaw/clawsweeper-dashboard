## Summary

This PR addresses a real decoding concern, but the proposed sentinel is not safe: it converts any legitimate U+FFFD character in a valid response into an empty web result. Keep it open for a narrow repair that distinguishes malformed bytes before decoding rather than interpreting the decoded text.

## What This Changes

The branch detects U+FFFD in `readResponseText()`’s non-streaming `Response.text()` fallback and returns an empty result, with regression tests for that behavior.

## Best Possible Solution

Preserve literal U+FFFD text and, if malformed UTF-8 must be rejected, retain raw bytes in the fallback, enforce the established response-size limit, and decode with a fatal UTF-8 decoder before returning text.

Yes, from source: a valid UTF-8 response containing a literal U+FFFD reaches the same new `includes()` condition as malformed bytes and is returned as an empty result.

## Solution Assessment

No. The proposed check is only a plausible mitigation because decoded text cannot reveal whether U+FFFD was originally present or inserted by forgiving decoding; raw-byte strict decoding is the maintainable fix if this behavior is required.

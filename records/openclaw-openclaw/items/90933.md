## Summary

Keep open: the previous timeout-abort blocker is fixed in the current PR head, and the lane-busy fix is still useful, but the branch now has a blocking mixed-version Gateway compatibility bug. The CLI sends a new strict `agent` parameter unconditionally while the Gateway protocol stays at v4, so a newly updated CLI can connect to an older released daemon and have every Gateway-backed `openclaw agent` request rejected before the busy-lane handling runs.

## What This Changes

The PR adds queue wait-detail/rejection plumbing, a CLI-only lane-busy path through the embedded runner and Gateway agent method, CLI stderr/JSON rendering, protocol model updates, and focused regression tests.

## Best Possible Solution

Keep the queue-to-Gateway-to-CLI busy-result behavior, but remove the ungated request-field dependency or add negotiated protocol/capability handling so upgraded CLIs remain compatible with older daemons.

## Reproduction Assessment

Yes, at source level: current main logs lane-wait diagnostics but has no structured Gateway/CLI lane-busy response path, and the linked issue plus PR terminal proof describe the same same-session CLI symptom. I did not rerun the live two-terminal CLI scenario in this read-only review.

## Solution Assessment

No, not as submitted: carrying queue wait facts through Gateway to the CLI is the right boundary, but the unconditional new protocol parameter is not the safest compatibility shape. The better repair is to derive the CLI-only opt-in from existing Gateway connection identity or negotiate/gate the new field.

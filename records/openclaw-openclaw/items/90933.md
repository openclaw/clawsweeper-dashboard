## Summary

Keep open: the PR targets the right CLI/Gateway lane-busy bug and has real behavior proof, but it still sends a new strict Gateway agent parameter unconditionally, which can break upgraded CLIs talking to older v4 daemons before the busy-lane handling path runs.

## What This Changes

The PR adds structured session-lane-busy wait details and rejection through the command queue, embedded runner, Gateway response, protocol/Swift models, CLI rendering, and regression tests.

## Best Possible Solution

Keep the queue-to-Gateway-to-CLI busy-result behavior, but remove or negotiate the new request-field dependency so upgraded CLIs remain compatible with older daemons and non-CLI Gateway calls stay unopted.

## Reproduction Assessment

Yes, at source level: current main logs lane-wait diagnostics but the Gateway/CLI response shape has no structured lane-busy result or renderer. I did not rerun the live two-terminal CLI scenario in this read-only review.

## Solution Assessment

No, not as submitted: carrying queue wait facts through Gateway to the CLI is the right boundary, but the unconditional new protocol parameter is not the safest compatibility shape. The better repair is to derive the CLI-only opt-in from existing Gateway connection identity or negotiate the field.

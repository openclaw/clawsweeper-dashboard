## Summary

Keep open: current main and v2026.6.11 still keep the read tool text/image-only, while the model/session contracts still lack a normalized native audio block for read-tool output. The request remains valid but needs maintainer product and security direction before implementation.

## What This Changes

Request read-tool support for audio files so supported models receive native audio attachments instead of raw binary decoded as text.

## Best Possible Solution

Define a shared, opt-in native-audio attachment contract for read results, provider serialization, capability checks, raw-media egress, payload limits, fallback behavior, and transcript/audit semantics before wiring audio into the read tool.

Options:

- **Fold into broader native-audio design:** Treat this read-tool request as a subcase of https://github.com/openclaw/openclaw/issues/51667 if maintainers want one product design thread for all native audio input.

## Reproduction Assessment

Yes, source-level. Current main only detects image MIME in the read tool before falling back to text decoding, and the normalized message/tool-result contracts support text/image blocks rather than audio.

## Solution Assessment

No for a simple read-tool extension-list patch. The maintainable path needs a shared native-audio content/provider contract plus security, fallback, payload-limit, and session/audit policy first.

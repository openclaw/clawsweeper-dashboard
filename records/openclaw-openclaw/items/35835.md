## Label Justifications

- `P2`: This is a clear multimodal feature gap with real user value, but it is not an urgent regression, outage, or data-loss event.
- `impact:session-state`: Native audio attachments would change what the session transcript, restore path, and audit trail can represent compared with current text/image outputs.
- `impact:security`: The requested behavior would forward original local audio bytes to model providers and needs explicit egress, retention, and audit boundaries.
- `impact:auth-provider`: The feature depends on provider/model capability routing and provider-specific native audio serialization.

## Summary

Keep open: current main and v2026.6.11 still make the read tool text/image-only, while native audio would require shared content, provider routing, session/audit, and raw-media egress decisions. The overlapping open native audio/video PR is not a landed or safe canonical fix for this read-tool request.

## What This Changes

Add native audio-file handling to the read tool so audio files are sent as multimodal model attachments instead of decoded as text.

## Best Possible Solution

Define a shared typed native-audio attachment contract for read results, provider serialization, model-capability checks, payload limits, unsupported-model behavior, explicit raw-media egress policy, and session/audit semantics before wiring audio into the read tool.

## Reproduction Assessment

Yes, source-level. Current main only detects image MIME in the read tool before falling back to text decoding, and normalized tool-result content supports text/image blocks only.

## Solution Assessment

No for a read-tool-only extension-list patch. The maintainable solution needs shared audio content/provider contracts plus security, fallback, and session/audit policy first.

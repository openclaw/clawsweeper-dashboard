## Label Justifications

- `P2`: This is a clear multimodal capability gap with real user value, but it is not an urgent regression, outage, crash loop, or data-loss event.
- `impact:session-state`: Native audio attachments would change what the session transcript, restore path, replay path, and audit trail can represent.
- `impact:security`: The requested behavior would forward original local audio bytes to model providers and needs explicit egress, retention, and audit boundaries.
- `impact:auth-provider`: The feature depends on model capability routing and provider-specific native audio serialization.

## Summary

Keep open: current main and v2026.6.11 still keep the read tool text/image-only, while native audio attachments require a product and security contract before implementation.

## What This Changes

Request to make the read tool send audio files as multimodal model attachments instead of decoding them as text.

## Best Possible Solution

Define an opt-in native-audio contract covering read results, provider serialization, capability checks, raw-media egress policy, payload limits, fallback behavior, and transcript/audit semantics before implementation.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add native audio attachments to the core read-tool contract, and what egress, fallback, provider-routing, and session/audit policy should govern that path?

Rationale: The source gap is clear, but the solution changes sensitive local media forwarding, provider capability routing, and session transcript semantics that automation cannot choose safely.

Likely owner: steipete

Owner reason: They have the strongest current history signal across the read, media-understanding, and product/security boundary this choice would change.

Owner confidence: high

Options:

- **Design native-audio contract first (recommended):** Settle typed audio blocks, provider transport, explicit raw-media egress, payload limits, unsupported-model behavior, and transcript/audit metadata before implementation.
- **Keep transcription-only for now:** Leave raw audio out of the read tool and direct users to existing STT/media-understanding paths until maintainers are ready to own native audio egress.
- **Fold into broader native-audio design:** Treat read-tool audio as a subcase of https://github.com/openclaw/openclaw/issues/51667 if maintainers want one product design thread.

## Reproduction Assessment

Yes, source-level: current main detects only image MIME in the read tool before text decoding, and normalized message/tool-result contracts support text/image blocks rather than audio.

## Solution Assessment

No for a simple read-tool extension-list patch. The maintainable fix needs a shared native-audio content/provider contract plus security, fallback, payload-limit, and session/audit policy first.

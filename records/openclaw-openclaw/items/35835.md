## Summary

Keep open: current main and the latest release still make the read tool text/image-only, and native audio needs a maintainer-approved content, provider, security, and session contract before implementation.

## What This Changes

Requests support for reading audio files as native multimodal model attachments instead of decoding them as text.

## Best Possible Solution

Define a shared typed native-audio attachment contract with capability checks, payload limits, unsupported-model behavior, raw-media egress policy, and session/audit semantics before wiring audio into read.

## Maintainer Decision

Rationale: The source gap is clear, but solving it changes core content types, provider serialization, sensitive media egress, and transcript/replay semantics that automation cannot safely choose.

Options:

- **Design the native-audio contract first (recommended):** Settle typed audio blocks, provider serialization, explicit raw-media egress, fallback behavior, payload limits, and transcript/audit metadata before implementation.

- **Fold into the broader native-audio tracker:** Treat this read-tool request as a subcase of https://github.com/openclaw/openclaw/issues/51667 if maintainers want one native-audio design thread.

## Solution Assessment

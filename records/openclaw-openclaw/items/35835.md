## Summary

Keep open: current main and v2026.6.11 still keep the read tool text/image-only, while native audio support needs a maintainer product/security decision on typed audio content, provider egress, fallback behavior, and session audit semantics before implementation.

## What This Changes

The issue requests native audio-file handling in the read tool so supported models receive audio as multimodal attachments instead of raw binary text.

## Best Possible Solution

Define a shared, explicit native-audio attachment contract for read results, provider serialization, capability checks, payload limits, fallback behavior, and transcript/audit semantics before wiring audio into the read tool.

Yes, source-level. Current main only detects image MIME in the read tool before falling back to text decoding, and normalized message/tool-result contracts support text/image blocks rather than audio.

## Solution Assessment

No for a simple read-tool extension-list patch. The maintainable path needs a shared native-audio content/provider contract plus security, fallback, payload-limit, and session/audit policy first.

## Label Justifications

- `P2`: This is a clear multimodal feature gap with real user value, but it is not an urgent regression, outage, crash loop, or data-loss event.
- `impact:session-state`: Native audio attachments would change what the session transcript, restore path, replay path, and audit trail can represent.
- `impact:security`: The requested behavior would forward original local audio bytes to model providers and needs explicit egress, retention, and audit boundaries.
- `impact:auth-provider`: The feature depends on model capability routing and provider-specific native audio serialization.

## Summary

Keep open: current main and the latest release still keep read-tool results text/image-only, while native audio support needs a maintainer-approved content, provider, security, and session-state contract before implementation.

## What This Changes

Add native audio-file handling to the read tool so supported models receive audio attachments instead of UTF-8-decoded binary text.

## Best Possible Solution

Define a typed, opt-in native-audio attachment contract for read results, provider serialization, capability checks, payload limits, unsupported-model fallback, and transcript/audit semantics before wiring audio into read.

Options:

- **Design the native-audio contract first (recommended):** Keep this issue open and require a maintainer-approved contract for typed audio blocks, provider transport, explicit raw-media egress, payload limits, unsupported-model behavior, and transcript/audit metadata before implementation.

Yes, source-level: current main detects only image MIME in the read tool before falling back to text decoding, and normalized message/tool-result contracts support text/image blocks rather than audio.

## Solution Assessment

No for a simple read-tool extension-list patch; the maintainable path needs a shared native-audio content/provider contract plus security, fallback, payload-limit, and session/audit policy first.

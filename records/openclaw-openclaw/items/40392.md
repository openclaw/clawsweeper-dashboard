## Review Findings

Full review comments:

- **[P1] Preserve legacy backups during timestamp migration:** `src/config/backup-rotation.ts:147`
  - body: The cleanup path now treats every non-datetime `.bak.*` as an orphan, so an existing user with `.bak.1` through `.bak.4` loses rollback points on the first config write after upgrade. The linked issue calls out preserving or converting those legacy files, and current main keeps them in the managed ring; migrate them into the timestamp set or retain them until capacity is safely filled.
  - confidence: 0.92
- **[P1] Harden legacy backups before best-effort cleanup:** `src/config/backup-rotation.ts:97-98`
  - body: `hardenBackupPermissions` only chmods datetime suffixes. During upgrade, permissive `.bak.1` files are no longer hardened and cleanup is best-effort, so an unlink failure can leave readable config backups that current main would chmod to `0600`. Either harden all legacy backup candidates before pruning or migrate them with owner-only mode.
  - confidence: 0.84
- **[P2] Avoid overwriting backups on timestamp collisions:** `src/config/backup-rotation.ts:53-56`
  - body: Using milliseconds reduces but does not eliminate collisions; two rotations with the same timestamp target the same destination, and POSIX `rename` replaces that file while the catch path hides Windows failures. Choose a unique suffix or no-clobber loop before rename so burst config writes do not silently reduce retention.
  - confidence: 0.82

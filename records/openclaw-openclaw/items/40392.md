## Summary

Keep open: current main still uses the numbered config backup ring, and this PR is the active implementation candidate for datetime suffixes, but the branch is not merge-ready because it can delete existing numeric recovery backups, can collide on same-millisecond writes, and lacks real behavior proof.

## What This Changes

The PR changes config backup rotation and tests from a numeric `.bak.N` ring to UTC datetime-suffixed backup files.

## Best Possible Solution

Keep the datetime naming idea, but make the migration preserve or convert existing numeric backups until replacement capacity exists, add collision-safe destination selection, and prove a real upgrade-style config write before merge.

Full review comments:

- **[P1] Preserve legacy backups during migration:** `src/config/backup-rotation.ts:145-147`
  - body: On upgrade, users can already have `.bak.1` through `.bak.4` recovery files from the current numeric ring. This branch classifies every non-datetime suffix as an orphan and unlinks it, so the first config write collapses recovery depth and can permanently remove rollback points the linked issue explicitly says to preserve or convert.
  - confidence: 0.96
- **[P2] Choose a unique timestamp backup path:** `src/config/backup-rotation.ts:53-56`
  - body: `formatBackupTimestamp` has millisecond precision, but `rotateConfigBackups` uses that value as the whole destination name and catches all rename errors. Two rotations in the same millisecond can overwrite the previous backup on POSIX or be skipped on Windows, reducing retained recovery points during burst config writes.
  - confidence: 0.88
- **[P2] Harden retained legacy backups before cleanup:** `src/config/backup-rotation.ts:96-100`
  - body: Current main chmods `.bak.1` through `.bak.4`, but this branch only chmods suffixes matching the new datetime regex. If legacy numeric backups are preserved for migration or if best-effort deletion fails, sensitive config backup files can remain without the hardening the shipped path applies today.
  - confidence: 0.78

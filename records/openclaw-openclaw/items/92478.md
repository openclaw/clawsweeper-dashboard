## Label Justifications

- `P2`: The issue affects an optional but user-facing Talk workflow with a confusing provider/auth failure, while normal text chat remains usable.
- `impact:auth-provider`: The behavior depends on whether OpenAI Realtime provider auth, API-key profiles, OAuth/Codex fallback, and realtime provider selection make Talk appear usable.
- `impact:ux-friction`: The UI can expose a Talk control that proceeds into microphone/WebRTC setup and then reports a provider failure instead of giving a clear readiness or setup state.

## Summary

Keep open: current main has better OpenAI Realtime auth handling, but it still leaves the Control UI Talk start path entering realtime/browser session creation without a clear preflight-disabled state for the reported local/non-Realtime setup, so the remaining blocker is a maintainer product decision rather than a safe cleanup close.

## What This Changes

The issue asks OpenClaw to stop the native/Control UI Talk button from attempting OpenAI Realtime WebRTC when Realtime is not configured or intended, and to show a clear disabled/error state or respect the non-Realtime Talk setup.

## Best Possible Solution

Gate the Start Talk flow on `talk.catalog` realtime readiness and the selected browser transport, then show an actionable setup/disabled state or route to the maintainer-approved non-Realtime Talk mode instead of letting the browser discover provider failure after microphone/WebRTC setup.

## Summary

Keep open: current main still exposes browser Talk, auto-enters the client-owned realtime path, and can reach the OpenAI SDP exchange before surfacing a generic setup error; related PRs settled narrower auth/provider behavior but not the product contract for when Control UI Talk should be enabled.

## What This Changes

The issue asks OpenClaw to prevent the native Control UI Talk button from starting OpenAI Realtime WebRTC and failing generically when the user expects local/non-Realtime Talk behavior.

## Best Possible Solution

Make Gateway-owned realtime readiness or preflight the single source for enabling Control UI Talk and for startup errors, after maintainers choose whether implicit OpenAI/Codex auth should count as browser Talk readiness.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Control UI browser Talk start from implicit OpenAI/Codex realtime credential availability, or only after an explicit talk.realtime readiness/preflight says the selected provider is usable?

Rationale: Current code and docs intentionally allow API-key/OAuth/Codex fallback, while this report expects a local/non-Realtime Talk setup not to start OpenAI Realtime; either choice changes setup semantics and compatibility.

Likely owner: steipete

Owner reason: steipete owns the most recent merged auth-policy change and documentation that define the current OpenAI Realtime fallback behavior.

Owner confidence: high

Options:

- **Gate On Gateway Readiness (recommended):** Disable or block browser Talk before microphone startup unless Gateway readiness reports a usable realtime provider, while preserving the chosen credential policy.
- **Keep Implicit Credential Activation:** Treat configured OpenAI/Codex realtime auth as enough to start Talk and limit follow-up work to clearer diagnostics for provider/API failures.
- **Require Explicit Realtime Config:** Only show or start browser Talk when talk.realtime is explicitly configured, accepting any migration or upgrade impact for existing users.

## Reproduction Assessment

Yes at source level: current main renders the Talk control, calls talk.client.create first, and the WebRTC transport posts SDP to OpenAI before surfacing a generic status error; I did not live-reproduce the external 500.

## Solution Assessment

Unclear until maintainers decide the enablement contract; a UI-only hide rule is too narrow because Gateway/provider readiness should keep UI, docs, and runtime routing aligned.

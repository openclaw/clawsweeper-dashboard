## Summary

Keep open: current main still exposes the Control UI Talk button independently of realtime readiness and can enter the browser WebRTC setup path before surfacing a generic provider failure; recent OpenAI auth changes affect the credential contract but do not settle the UI enablement/preflight behavior.

## What This Changes

The issue asks for the Control UI Talk microphone button to avoid starting an OpenAI Realtime WebRTC session when realtime voice is not intentionally configured or ready.

## Best Possible Solution

After maintainers choose the enablement contract, make Gateway-owned realtime readiness the single source for the Control UI Talk button and startup error, preserving an upgrade-safe credential policy for existing OpenAI realtime users.

Rationale: Current code and docs support realtime provider/auth resolution, while this report expects a local/non-Realtime Talk setup not to start OpenAI Realtime; either direction changes setup semantics and upgrade behavior.

Options:

- **Gate on Gateway readiness preflight (recommended):** Use `talk.catalog.realtime.ready` or an equivalent Gateway-owned preflight to disable or block Talk before microphone startup while preserving the chosen credential policy.

- **Require explicit realtime config:** Only show or start browser Talk when `talk.realtime` is explicitly configured, with migration or docs for users relying on implicit credentials.

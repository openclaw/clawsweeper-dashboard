## Label Justifications

- `P2`: This is a bounded Control UI Talk/provider-readiness issue with confusing optional-voice behavior, while normal text chat still works.
- `impact:auth-provider`: The issue turns on OpenAI Realtime auth, OAuth/Codex fallback, provider configured state, and explicit Talk realtime config.
- `impact:ux-friction`: The visible microphone control can activate the mic and fail with a generic Realtime provider error instead of a clear readiness or setup message.

## Summary

Keep open: current main still exposes the Control UI Talk entry point and can enter the OpenAI browser Realtime/WebRTC path before the browser posts SDP to OpenAI; recent merged auth work changes which credentials can make that path configured, but it does not settle whether browser Talk should be enabled only by explicit realtime readiness.

## What This Changes

The issue asks OpenClaw to avoid starting an OpenAI Realtime WebRTC call from the Talk button when Realtime is not configured or usable, and to show a clearer disabled or provider-readiness state.

## Best Possible Solution

Make Gateway realtime readiness the single source of truth for the Control UI Talk button and startup error, after maintainers choose whether implicit OpenAI/Codex auth should enable browser Talk.

Rationale: Current docs and code intentionally allow API-key/OAuth/Codex fallback, while this report expects a local/non-Realtime Talk setup not to start OpenAI Realtime; either direction changes user-facing setup semantics.

Options:

- **Gate On Gateway Readiness (recommended):** Disable or block browser Talk before microphone startup unless talk.catalog or an equivalent readiness result reports a usable realtime provider, while preserving the chosen credential policy.
- **Keep Implicit Credential Activation:** Treat configured OpenAI/Codex realtime auth as sufficient and narrow follow-up work to clearer diagnostics for provider/API failures.
- **Require Explicit Realtime Config:** Only show or start browser Talk when talk.realtime is explicitly configured, accepting any upgrade or migration impact for existing users.

Yes at source level: current main still renders the Talk control, calls `talk.client.create`, and the WebRTC transport posts SDP to OpenAI after acquiring microphone media. I did not live-reproduce the external OpenAI HTTP 500.

## Solution Assessment

Unclear until maintainers decide the enablement contract. A UI-only hide rule would be too narrow; the durable fix should use Gateway/provider readiness so UI, docs, and runtime routing stay aligned.

## Summary

Keep open: current main has improved OpenAI Realtime auth and live proof, but it still leaves the Control UI Talk activation contract unresolved for users with local/non-Realtime Talk expectations and implicit OpenAI credential availability.

## What This Changes

The issue asks for the Control UI native Talk button to avoid starting OpenAI Realtime WebRTC when Realtime is not configured or not intended.

## Best Possible Solution

Make Gateway-owned Talk realtime readiness the source of the Control UI button and startup error after maintainers choose the explicit-vs-implicit activation contract, while preserving supported OpenAI auth and local TTS fallback behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Control UI browser Talk require explicit realtime readiness before microphone/WebRTC startup, or should any resolved OpenAI Realtime-capable credential keep enabling Talk implicitly?

Rationale: Current main intentionally accepts API-key or OAuth/Codex auth for Realtime, while this report expects a local/non-Realtime Talk setup not to enter OpenAI WebRTC; either answer changes user-facing setup semantics and upgrade behavior.

Likely owner: steipete

Owner reason: The newest merged auth-provider policy and docs for OpenAI Realtime voice came from this owner trail, so they are the best routing candidate for the activation contract choice.

Owner confidence: high

Options:

- **Gate on Gateway readiness preflight (recommended):** Use talk.catalog or a dedicated Gateway readiness result to disable or block Talk before microphone startup unless the selected realtime provider is ready, and show a clear setup message.
- **Keep implicit credential activation:** Treat API-key or OAuth/Codex OpenAI auth as enough to enable browser Talk, and narrow the remaining work to clearer provider/API error text when OpenAI rejects setup.
- **Require explicit realtime config:** Only show or start browser Talk when talk.realtime is explicitly configured, accepting the upgrade impact for users who currently rely on auto-selected provider credentials.

## Reproduction Assessment

Yes at source level: current main still renders the Talk button, calls talk.client.create, opens microphone media after session metadata, and posts SDP to OpenAI with a generic status-only error on failure. I did not live-reproduce the external OpenAI 500.

## Solution Assessment

Unclear until maintainers decide the activation contract. A UI-only hide rule would be too narrow; the best fix should come from Gateway/provider readiness so UI, docs, and runtime behavior stay aligned.

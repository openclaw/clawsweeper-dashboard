## Summary

Keep open: current main still lets the Control UI Talk button enter the realtime session path before the browser posts SDP to OpenAI, and the merged OAuth/Codex auth work proves one supported credential path but does not settle whether browser Talk should require explicit realtime readiness or remain implicitly enabled by available OpenAI auth.

## What This Changes

The issue requests that Control UI Talk avoid starting an OpenAI Realtime WebRTC session, or show a clear readiness error, when the user's configured Talk path is local/non-Realtime.

## Best Possible Solution

Make Gateway-owned realtime readiness the single source for the Control UI Talk button and startup error after maintainers choose whether implicit OpenAI/Codex auth should enable browser Talk.

Question: Should Control UI browser Talk start from implicit OpenAI realtime credential availability, or only after an explicit Talk realtime readiness/configuration gate says the provider is usable for this session?

Rationale: Current code and docs intentionally allow API-key/OAuth/Codex fallback, while this report expects a local/non-Realtime Talk setup not to start OpenAI Realtime; either direction changes user-facing setup semantics.

Owner confidence: high

Options:

- **Gate On Gateway Readiness (recommended):** Disable or block browser Talk before microphone startup unless `talk.catalog` or an equivalent Gateway readiness result reports a usable realtime provider, while preserving the chosen credential policy.
- **Keep Implicit Credential Activation:** Treat configured OpenAI/Codex realtime auth as sufficient and narrow follow-up work to clearer diagnostics for provider/API failures.
- **Require Explicit Realtime Config:** Only show or start browser Talk when `talk.realtime` is explicitly configured, accepting any upgrade or migration impact for existing users.

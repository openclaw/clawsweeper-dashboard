## Summary

Keep open: current main has improved OpenAI Realtime auth behavior and docs, but the Control UI Talk button is still wired as a browser realtime entry point and the remaining choice is whether it should be gated by explicit realtime readiness before microphone/WebRTC startup.

## What This Changes

The issue asks for Control UI Talk to avoid starting an OpenAI Realtime WebRTC call when realtime voice is not configured or not usable, and to show a clearer disabled/error state instead.

## Best Possible Solution

Make Gateway-owned realtime readiness the single source for the Control UI Talk button and startup error, then apply the maintainer-chosen policy for implicit credentials versus explicit talk.realtime config without changing local TTS behavior unexpectedly.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Control UI browser Talk start from implicit realtime credential availability, or only after an explicit talk.catalog/talk.realtime readiness preflight says realtime voice is usable?

Rationale: Current code and docs treat browser Talk as a realtime surface that can be enabled by OpenAI API-key/OAuth/Codex auth, while this report expects local/non-Realtime Talk setup not to start OpenAI WebRTC; either direction changes user-facing setup semantics.

Likely owner: steipete

Owner reason: The most recent merged OpenAI Realtime auth/docs work and live proof came from steipete, making this the closest current owner trail for the enablement policy choice.

Owner confidence: high

Options:

- **Gate on Gateway readiness (recommended):** Use talk.catalog realtime.ready to disable or block Talk before microphone startup and show a specific setup message while preserving the chosen credential policy.
- **Keep implicit credential activation:** Accept that configured OpenAI realtime credentials enable browser Talk and narrow remaining work to clearer provider/API error messages.
- **Require explicit realtime config:** Only show or start browser Talk when talk.realtime is explicitly configured, with upgrade communication for users relying on implicit credentials.

## Reproduction Assessment

Yes at source level: current main still renders the Talk control, calls talk.client.create, and can reach the browser WebRTC SDP path that throws the reported generic status error. I did not live-reproduce the external OpenAI 500.

## Solution Assessment

Unclear until maintainers decide the enablement contract. A browser-only guard is not the best fix; Gateway/provider readiness should own the preflight so UI, docs, and runtime routing stay aligned.

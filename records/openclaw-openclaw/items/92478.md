## Summary

Keep open: current main still exposes the Control UI Talk/mic entry point and starts browser Realtime before a catalog/readiness gate, while the related merged auth fixes only changed which OpenAI credentials can satisfy Realtime and did not settle the desired UI/product behavior for non-Realtime Talk setups.

## What This Changes

The issue asks for the native Control UI Talk button to avoid starting an OpenAI Realtime WebRTC session that fails generically when the user's intended Talk setup is local TTS rather than configured Realtime voice.

## Best Possible Solution

Gate Control UI browser Talk startup on Gateway-owned realtime readiness and show a clear provider/setup action after maintainers decide the intended credential semantics.

- **Gate On Gateway Readiness (recommended):** Use talk.catalog or an equivalent Gateway preflight to disable or block browser Talk before microphone startup unless the selected Realtime provider is ready, with actionable setup copy.

- **Require Explicit Realtime Config:** Make browser Talk require explicit talk.realtime or provider configuration so local-TTS users never enter OpenAI Realtime accidentally.

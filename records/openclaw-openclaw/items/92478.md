## Summary

Keep open: current main still lets the Control UI Talk button start the client-owned Realtime path, requests microphone access, and posts SDP to OpenAI before surfacing a generic HTTP-status error; merged auth fixes and the open diagnostic PR cover narrower credential failures but do not settle when browser Talk should be enabled.

## What This Changes

The issue asks for Control UI Talk to respect non-Realtime/local Talk configuration by blocking or clearly explaining Realtime unavailability before starting an OpenAI WebRTC call.

## Best Possible Solution

Make Gateway-owned talk.catalog realtime readiness the source of truth for the Control UI Talk button and startup error after maintainers choose whether implicit OpenAI/Codex auth should count as ready.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Control UI browser Talk start from implicit OpenAI realtime credential availability, or only after an explicit Gateway readiness/preflight says a realtime provider is usable for this session?

Rationale: Current docs and provider code intentionally allow API-key/OAuth/Codex fallback, while the report expects a local/non-Realtime Talk setup not to start OpenAI Realtime; either choice changes user-facing setup semantics and possibly upgrade behavior.

Likely owner: steipete

Owner reason: steipete has the strongest recent current-main signal for the OpenAI Realtime auth/docs policy that defines this product boundary.

Owner confidence: high

Options:

- **Gate on Gateway readiness (recommended):** Disable or block browser Talk before microphone startup unless talk.catalog/readiness reports a usable realtime provider, while preserving the chosen credential policy.
- **Keep implicit credential activation:** Treat configured OpenAI/Codex realtime auth as sufficient and narrow follow-up work to clearer diagnostics for provider/API failures.
- **Require explicit realtime config:** Only show or start browser Talk when talk.realtime is explicitly configured, accepting any compatibility or migration impact for existing users.

## Reproduction Assessment

Yes at source level: current main still renders the Talk control, calls talk.client.create first, gets microphone media, and posts SDP to OpenAI before surfacing a generic status error. I did not live-reproduce the external OpenAI 500.

## Solution Assessment

Unclear until maintainers decide the enablement contract. A UI-only hide rule is too narrow; the durable fix should use Gateway/provider readiness so UI, docs, and runtime routing stay aligned.

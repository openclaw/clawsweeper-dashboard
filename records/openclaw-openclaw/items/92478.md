## Summary

Keep open: current main still has a Control UI browser Talk path that can auto-select a configured realtime provider and then post browser SDP to OpenAI after microphone access; the remaining question is the product contract for when that Talk button should be enabled, not an already-fixed issue.

## What This Changes

The issue asks for the Control UI Talk button to avoid starting an OpenAI Realtime WebRTC call and instead disable or show a clear message when Realtime is not configured or intended.

## Best Possible Solution

Make Gateway-owned realtime readiness the single source for the Control UI Talk button and startup error after maintainers choose whether OpenAI/Codex auth implicitly enables browser realtime Talk; keep local TTS Talk behavior separate from browser realtime sessions.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Control UI browser Talk start whenever OpenAI Realtime can be auto-selected from API-key/OAuth/Codex auth, or only after an explicit realtime readiness/preflight says the provider is intended and usable for this session?

Rationale: Current code and docs intentionally allow implicit OpenAI/Codex fallback, while this report expects a local/non-Realtime Talk setup not to start OpenAI Realtime; either choice changes user-facing setup and upgrade semantics.

Likely owner: steipete

Owner reason: The current OpenAI/Codex fallback and Control UI Talk docs are closest to steipete's recent merged work and current-main blame.

Owner confidence: high

Options:

- **Gate on Gateway readiness (recommended):** Disable or block the browser Talk start before microphone access unless talk.catalog/readiness reports a usable intended realtime provider, while preserving the chosen credential policy.
- **Keep implicit credential activation:** Treat configured OpenAI/Codex realtime auth as sufficient and limit follow-up work to clearer diagnostics for provider or API failures.
- **Require explicit realtime config:** Only show or start browser Talk when talk.realtime is explicitly configured, accepting any migration or upgrade impact for current users relying on auto-selection.

## Reproduction Assessment

Yes at source level: current main still renders the browser Talk control, starts a realtime Talk session, calls talk.client.create first, and the WebRTC transport posts SDP to OpenAI after microphone access when a browser session is returned. I did not live-reproduce the external HTTP 500.

## Solution Assessment

Unclear until maintainers decide the enablement contract. A UI-only hide rule would be too narrow; the durable fix should use Gateway/provider readiness so UI, docs, auth fallback, and runtime routing stay aligned.

- `P2`: This is a normal-priority Control UI Talk regression/UX issue with bounded blast radius because text chat still works and the affected voice path is optional.
- `impact:auth-provider`: The issue centers on whether provider/auth readiness is sufficient to start an OpenAI browser realtime session.

## Summary

Keep open: current main still exposes the Control UI Talk button and can enter the browser Realtime/WebRTC startup path, while the newer OpenAI/Codex auth merge changes credential policy but does not settle whether browser Talk should require explicit realtime readiness before microphone activation.

## What This Changes

The issue requests that the Control UI Talk button avoid starting OpenAI Realtime WebRTC when realtime voice is not explicitly configured or ready, and instead show a clear disabled/readiness state or respect local Talk/TTS configuration.

## Best Possible Solution

Use a Gateway-owned realtime readiness/preflight result as the single source for the Talk control and startup message, after maintainers choose whether implicit OpenAI/Codex auth should count as realtime-enabled.

Rationale: Current code starts the client-owned realtime path from the Talk button, while current docs and recent merges allow broader OpenAI/Codex auth availability; either policy affects user setup semantics and upgrade behavior.

Owner confidence: high

Options:

- **Gate on Gateway readiness (recommended):** Use talk.catalog/readiness or an equivalent Gateway preflight to disable or block Talk before microphone startup while preserving the chosen credential policy.
- **Keep implicit auth activation:** Accept that OpenAI/Codex realtime credential availability enables browser Talk and focus the remaining work on clearer provider/API error messages.
- **Require explicit realtime config:** Only start browser Talk when talk.realtime is explicitly configured, with upgrade proof for users who currently rely on implicit auth availability.

Yes at source level: current main renders the Talk button, calls talk.client.create, then the WebRTC transport can post SDP to OpenAI and surface a generic status error. I did not live-reproduce the external OpenAI 500.

## Solution Assessment

Unclear until maintainers decide the enablement contract. A browser-only guard is not the best fix; Gateway/provider readiness should own the preflight so UI, docs, and runtime routing stay aligned.

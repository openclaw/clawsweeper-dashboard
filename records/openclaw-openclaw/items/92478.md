## Summary

Keep open: current main still renders the Control UI Talk control and can enter the browser-owned realtime path that posts SDP to OpenAI before surfacing a generic `Realtime WebRTC setup failed (...)` error; adjacent OpenAI auth fixes do not settle whether browser Talk should require explicit realtime readiness or implicit OpenAI credential availability.

## What This Changes

Issue #92478 reports that the Dashboard Talk button starts an OpenAI Realtime WebRTC session and fails with a generic 500 when the user expected local TTS/non-Realtime configuration to be respected.

## Best Possible Solution

After a maintainer chooses the enablement contract, make Gateway-owned realtime availability/preflight the single source for the Control UI Talk button and startup error, with upgrade-safe behavior for existing OpenAI realtime users.

## Solution Assessment

Unclear until maintainers decide the enablement contract. A browser-only guard is not the best fix; Gateway/provider availability should own the preflight so UI, docs, and runtime routing stay aligned.

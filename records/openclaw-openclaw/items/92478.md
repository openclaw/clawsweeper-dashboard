- `impact:ux-friction`: The visible microphone button can lead users into microphone activation and a generic provider failure instead of a clear readiness or setup message.

## Summary

Keep open: current main still lets the Control UI Talk button start the client-owned OpenAI Realtime path before a definitive readiness gate, and the related auth/diagnostic work does not settle whether browser Talk should require explicit realtime configuration or implicit OpenAI/Codex auth availability.

## What This Changes

The issue asks for Control UI browser Talk to avoid starting OpenAI Realtime/WebRTC when Realtime is not configured or not usable, and to show a clear readiness/setup state instead.

## Best Possible Solution

Make Gateway Talk catalog/readiness the source of truth and have Control UI disable or block browser Talk before microphone startup with a clear setup error, after maintainers choose the intended OpenAI API-key/OAuth/Codex enablement policy.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Control UI browser Talk start from implicit OpenAI realtime credential availability, including OAuth/Codex fallback, or only after an explicit realtime readiness/preflight says the provider is usable for this user?

Rationale: Current code and docs intentionally support implicit OpenAI OAuth/Codex fallback, while the report expects a local/non-Realtime Talk setup not to activate OpenAI WebRTC or the microphone; either direction changes user-facing setup semantics.

Likely owner: steipete

Owner reason: steipete has the strongest current-main ownership signal for the OpenAI Realtime credential fallback and docs that define this behavior.

Owner confidence: high

Options:

- **Gate on Gateway readiness (recommended):** Disable or block browser Talk before microphone startup unless talk.catalog/readiness reports a usable realtime provider, while preserving whichever credential sources maintainers choose.
- **Keep implicit credential activation:** Treat configured OpenAI API-key/OAuth/Codex realtime auth as enough to show/start Talk, and narrow follow-up work to clearer diagnostics for provider or API failures.
- **Require explicit realtime config:** Only show or start browser Talk when talk.realtime is explicitly configured, accepting the upgrade and migration implications for existing implicit setups.

## Reproduction Assessment

Yes at source level: current main still renders the Talk control, calls talk.client.create first, and the WebRTC transport requests microphone media before posting SDP to OpenAI and surfacing a generic HTTP-status error. I did not live-reproduce the external OpenAI 500.

## Solution Assessment

Unclear until maintainers decide the enablement contract. A UI-only hide rule is not the best durable fix; the maintainable path should use Gateway/provider readiness so UI, docs, and runtime routing stay aligned.

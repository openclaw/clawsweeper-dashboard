## Summary

Keep open: current main still wires the Control UI Talk button into the browser realtime session path and can reach the OpenAI WebRTC SDP call based on realtime provider/auth selection, while the reporter's expected local/non-Realtime behavior needs an explicit maintainer policy choice.

## What This Changes

The issue asks that the Control UI/native Talk microphone not start an OpenAI Realtime WebRTC session when only local/non-Realtime Talk config is present or Realtime is not ready.

## Best Possible Solution

Make Gateway-owned talk.catalog readiness or an equivalent preflight the single source for the Control UI Talk button and startup error, after maintainers choose explicit realtime opt-in versus implicit credential-based activation.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Control UI browser Talk be enabled by implicit OpenAI realtime credential availability, or only after an explicit Gateway realtime readiness/preflight says the current Talk setup can start?

Rationale: Current code and docs make browser Talk a realtime-provider feature, while this report expects local/non-Realtime Talk configuration not to start OpenAI WebRTC; either answer changes user-facing setup semantics and upgrade behavior.

Likely owner: steipete

Owner confidence: high

Options:

- **Gate On Gateway Readiness (recommended):** Use Gateway realtime readiness/preflight to disable or block Talk before microphone/WebRTC startup while preserving whichever credential policy maintainers choose.
- **Keep Implicit Credential Activation:** Accept that configured OpenAI realtime credentials enable browser Talk and focus the remaining work on clearer provider/API error messages.
- **Require Explicit Realtime Config:** Only show or start browser Talk when talk.realtime is explicitly configured, with any needed upgrade note or migration for existing users.

## Reproduction Assessment

Yes at source level: current main renders the Talk button, calls talk.client.create, and the WebRTC transport posts SDP to OpenAI before throwing the generic status error. I did not live-reproduce the external OpenAI 500.

## Solution Assessment

Unclear until maintainers choose the browser Talk enablement contract. A UI-only hide rule is not the best fix; Gateway/provider readiness should own the preflight so UI, docs, and runtime routing stay aligned.

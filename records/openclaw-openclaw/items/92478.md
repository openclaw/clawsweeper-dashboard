## Summary

Keep open: current main improved OpenAI Realtime auth handling, but it still leaves the browser Talk button/startup path able to enter WebRTC setup and surface the generic SDP failure; the remaining question is the intended readiness rule, not an already-implemented fix.

## What This Changes

The issue reports that the Control UI Talk/microphone button starts an OpenAI Realtime WebRTC session and fails with a generic 500 when Realtime is not configured or not usable.

## Best Possible Solution

Add a maintainer-approved Talk readiness contract that keeps the browser mic button disabled or shows an actionable provider message before starting capture when realtime voice is unavailable or not intentionally configured.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should browser Talk treat any usable OpenAI API-key/OAuth/Codex auth as Realtime-ready, or require an explicit realtime readiness/preflight result before enabling the microphone button?

Rationale: Current main intentionally added OAuth/Codex fallback for OpenAI Realtime, while this issue asks for the UI to avoid starting the OpenAI WebRTC path when Realtime is not intentionally configured or available; both are plausible product rules and automation should not choose between them.

Likely owner: steipete

Owner reason: Available history shows the broadest ownership of Talk/gateway and OpenAI realtime provider boundaries, making this the best routed product/API decision owner among the likely owners.

Owner confidence: medium

Options:

- **Require explicit readiness before capture (recommended):** Use `talk.catalog` or provider preflight readiness to disable the Talk button or show a setup message before requesting microphone access.
- **Keep implicit auth readiness:** Document that OpenAI API-key/OAuth/Codex auth makes browser Talk available and improve only the provider error text after SDP/session failures.
- **Move browser Talk behind explicit config:** Require `talk.realtime.provider` or equivalent admin-configured defaults before the Control UI exposes the Talk start action.

## Reproduction Assessment

Yes from source for the current UI path, but not with live end-to-end proof in this review. The composer still starts browser Talk without a readiness gate, then the WebRTC transport obtains microphone media before the SDP POST can fail with the reported generic error.

## Solution Assessment

Unclear until maintainers decide the product rule for implicit OpenAI OAuth/API-key readiness versus explicit Realtime opt-in. The maintainable fix should use a Gateway/provider readiness result that the UI can consume before starting capture.

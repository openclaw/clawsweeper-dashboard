## Summary

Keep open: current main still lets Control UI browser Talk enter the OpenAI Realtime/WebRTC path before there is a maintainer-confirmed rule for explicit realtime readiness versus implicit OpenAI credential availability, so the remaining issue is not safely closeable as fixed.

## What This Changes

This issue asks Control UI Talk to avoid starting OpenAI Realtime/WebRTC unless realtime voice is explicitly available, and to show a clear disabled or actionable error state instead of a generic 500.

## Best Possible Solution

After a maintainer chooses the enablement contract, make Gateway-owned realtime readiness or preflight the single source for the Control UI Talk button and startup error, with upgrade-safe behavior for existing OpenAI realtime users.

Rationale: Current code and docs allow browser Talk through OpenAI realtime provider/auth resolution, while the report expects local/non-Realtime Talk setup not to start OpenAI Realtime; either answer changes visible setup semantics and possibly existing users.

Options:

- **Gate on Gateway realtime readiness (recommended):** Use a Gateway-owned readiness/preflight result to disable or block Talk before microphone/WebRTC startup while preserving whichever credential policy maintainers choose.
- **Keep implicit credential activation:** Accept that configured OpenAI realtime credentials enable browser Talk and limit the remaining fix to clearer provider/API error messaging.
- **Require explicit realtime config:** Only show or start browser Talk when `talk.realtime` is explicitly configured, with an upgrade note or migration for users relying on implicit auth.

## Solution Assessment

Unclear until maintainers decide the enablement contract. A browser-only guard is not the best fix; Gateway/provider availability should own the preflight so UI, docs, and runtime routing stay aligned.

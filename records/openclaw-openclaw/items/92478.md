## Summary

Keep open: current main still leaves the Control UI Talk affordance active and starts the client-owned realtime path before any readiness gate, while recent OpenAI auth fixes only settle narrower credential behavior and not the product contract for when browser Talk should be enabled.

## What This Changes

The issue requests that the Dashboard Talk button avoid starting OpenAI Realtime WebRTC when realtime voice is not explicitly configured or usable.

## Best Possible Solution

Make Gateway-owned realtime readiness the single source for the Control UI Talk button and startup error after maintainers choose whether implicit OpenAI/Codex auth should enable browser Talk.

Question: Should Control UI browser Talk start from implicit OpenAI realtime credential availability, or only after an explicit talk.realtime readiness/preflight says the provider is usable?

Rationale: Current docs and code intentionally allow API-key/OAuth/Codex fallback, while this report expects a local/non-Realtime Talk setup not to start OpenAI Realtime; either direction changes user-facing setup semantics.

Owner confidence: high

Options:

- **Gate On Gateway Readiness (recommended):** Disable or block browser Talk before microphone startup unless talk.catalog/readiness reports a usable realtime provider, while preserving the chosen credential policy.
- **Keep Implicit Credential Activation:** Treat configured OpenAI/Codex realtime auth as sufficient and narrow follow-up work to clearer diagnostics for provider/API failures.
- **Require Explicit Realtime Config:** Only show or start browser Talk when talk.realtime is explicitly configured, accepting any upgrade or migration impact for existing users.

## Solution Assessment

Unclear until maintainers decide the enablement contract. A UI-only hide rule is not enough; the durable fix should use Gateway/provider readiness so UI, docs, and runtime routing stay aligned.

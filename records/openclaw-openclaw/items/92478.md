## Label Justifications

- `P2`: The issue affects a bounded optional Control UI Talk workflow while normal text chat still works, but it creates a real user-facing provider/readiness failure.
- `impact:auth-provider`: The issue turns on whether OpenAI API-key/OAuth/Codex auth or explicit Talk realtime config should make the Realtime provider usable.
- `impact:ux-friction`: The UI can invite microphone activation and then show a generic provider failure instead of a clear readiness or setup message.

## Summary

Keep open: current main still exposes browser Talk from the Control UI composer and starts the client-owned realtime path before the browser posts SDP to OpenAI, while the remaining question is the intended enablement contract for implicit OpenAI/Codex realtime auth versus an explicit readiness gate.

## What This Changes

The issue asks for browser/native Talk to avoid starting an OpenAI Realtime WebRTC call when the user has configured local/non-Realtime Talk and Realtime voice is not explicitly usable.

## Best Possible Solution

Make Gateway realtime readiness the single source for the Control UI Talk button and startup error, then disable or block microphone startup with an actionable message once maintainers choose the implicit-auth versus explicit-config contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should browser Talk start when OpenAI Realtime is implicitly usable through OpenAI API-key/OAuth/Codex auth, or only when an explicit Talk realtime readiness/configuration says the provider is usable?

Rationale: The current docs and code intentionally support implicit OpenAI/Codex realtime activation, while the reporter expects local/non-Realtime Talk configuration not to start OpenAI WebRTC; either answer changes user-facing setup semantics and upgrade expectations.

Likely owner: steipete

Owner reason: steipete owns the most recent OpenAI Realtime auth fallback/docs change and the current UI path by git history, so they are the best available owner for the product contract.

Owner confidence: high

Options:

- **Gate On Gateway Readiness (recommended):** Use `talk.catalog` or an equivalent Gateway preflight to disable/block Talk before microphone startup unless a usable realtime provider is ready, while preserving the chosen credential policy.
- **Keep Implicit Credential Activation:** Treat configured OpenAI/Codex realtime auth as enough to show/start browser Talk and narrow the fix to better diagnostics for provider/API failures.
- **Require Explicit Realtime Config:** Only show or start browser Talk when `talk.realtime` is explicitly configured, accepting any migration or upgrade impact for existing implicit-auth users.

## Reproduction Assessment

Yes at source level: current main still renders the Talk control, starts a realtime session, requests microphone access, and posts SDP to OpenAI before surfacing a generic HTTP-status error. I did not live-reproduce the external OpenAI 500.

## Solution Assessment

Unclear until maintainers choose the enablement contract. The maintainable fix should be Gateway/provider-readiness backed rather than a standalone UI hide rule.

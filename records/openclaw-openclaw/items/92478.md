## Summary

Keep open: current main still exposes browser Talk and can enter the OpenAI Realtime WebRTC path before the browser SDP exchange, while the remaining question is the product contract for implicit OpenAI/Codex realtime readiness versus an explicit Gateway readiness gate.

## What This Changes

The issue asks Control UI Talk to avoid starting an OpenAI Realtime WebRTC call when realtime voice is not explicitly usable, and to show a clear disabled or setup state instead of a generic 500 error.

## Best Possible Solution

Make Gateway-owned realtime readiness the single source for the Control UI Talk button and startup error after maintainers choose whether implicit OpenAI/Codex auth should enable browser Talk.

Rationale: Current code and docs intentionally allow API-key, OAuth-profile, and external Codex auth to satisfy OpenAI Realtime, while this report expects a local/non-realtime Talk setup not to start OpenAI Realtime at all.

Owner confidence: high

Options:

- **Gate On Gateway Readiness (recommended):** Disable or block browser Talk before microphone startup unless talk.catalog or a preflight reports a usable realtime provider, while preserving the chosen credential policy.
- **Keep Implicit Credential Activation:** Treat configured OpenAI/Codex realtime auth as sufficient and narrow the issue to clearer diagnostics for provider or API failures.
- **Require Explicit Realtime Config:** Only show or start browser Talk when talk.realtime is explicitly configured, accepting the upgrade impact for users who currently rely on automatic OpenAI auth discovery.

Yes at source level: current main still renders the Talk control, calls talk.client.create first, and the WebRTC transport posts SDP to OpenAI before surfacing a generic status error; I did not live-reproduce the external 500.

## Solution Assessment

Unclear until maintainers decide the enablement contract; a UI-only hide rule is too narrow, and the durable fix should use Gateway/provider readiness so UI, docs, and runtime routing stay aligned.

- `P1`: The issue describes a real agent/channel workflow where Telegram messages queue for minutes while compaction occupies the processing lane.
- `impact:session-state`: The affected behavior is session memoryFlush/compaction scheduling, transcript state, and per-session lane serialization.

## Summary

Keep open: current main and the latest release still have only partial mitigations. The compaction timeout is now 180 seconds and memory-triggered runs are background priority, but active preflight compaction and memoryFlush can still occupy the session/global processing path rather than a dedicated or preemptible compaction lane.

## What This Changes

The issue requests that session memoryFlush and compaction stop occupying the main processing lane long enough to block inbound Telegram messages.

## Best Possible Solution

Land a maintainer-approved bounded or preemptible compaction/memory maintenance lane design that preserves session ordering while allowing foreground channel messages to be acknowledged or processed promptly.

- **Dedicated Maintenance Lane (recommended):** Create a bounded compaction/memory maintenance lane with explicit transcript/session handoff rules so foreground user turns can proceed or receive a quick busy response.
- **Preemptible In-Lane Compaction:** Keep compaction in the current lane but add a maintainer-approved cancellation/yield protocol and watchdog that can release the lane for foreground user messages.
- **Keep Current Mitigations:** Accept the 180-second timeout and background priority as sufficient for now, leaving active compaction able to block foreground work until timeout or completion.

## Reproduction Assessment

Yes, at source level: current main still awaits preflight compaction and runs memoryFlush through CommandLane.Main/session scheduling, so an active long-running compaction can block queued foreground work. I did not run a live Telegram timeout reproduction.

## Solution Assessment

No, current main is only a partial mitigation because a shorter timeout and queue priority do not preempt an already-active compaction or memoryFlush task. The best fix needs a maintainer-chosen scheduler design with session-ordering proof.

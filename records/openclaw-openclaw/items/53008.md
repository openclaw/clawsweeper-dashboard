- `P1`: The issue describes a real Telegram workflow becoming unresponsive for 10+ minutes while foreground messages wait behind compaction work.

## Summary

Keep open: current main and the latest release still serialize preflight compaction and memoryFlush through the active reply/session-lane path, so the reported foreground-message starvation is not implemented away. The issue remains the canonical tracker for deciding how compaction maintenance should stop blocking interactive channel work.

## What This Changes

The issue asks for session compaction and memoryFlush to stop blocking same-session Telegram message processing for minutes at a time.

## Best Possible Solution

Adopt a maintainer-approved maintenance-lane, preemption, or bounded recovery design that keeps session state consistent while preventing compaction and memoryFlush from starving foreground channel messages.

Kind: product_direction

Question: Should compaction and memoryFlush move to an isolated or preemptible maintenance path, or remain serialized with foreground session turns plus shorter recovery limits?

Rationale: The source-reproducible problem is real, but changing the lane boundary changes session ordering, transcript rotation, cancellation, and channel UX semantics; automation should not choose that architecture without maintainer intent.

Likely owner: Vincent Koc

Owner reason: Vincent Koc is the strongest current-history owner across the reply path, queued compaction wrapper, and diagnostic recovery code touched by any fix shape.

Owner confidence: high

Options:

- **Design maintenance isolation (recommended):** Move or preempt compaction and memoryFlush with explicit ordering, cancellation, and recovery semantics so foreground messages can be acknowledged or processed promptly.
- **Limit to recovery mitigation:** Keep compaction serialized but shorten timeouts/watchdog recovery, accepting that same-session messages still wait while maintenance is legitimately active.
- **Keep current serialization:** Treat the blocking behavior as the cost of strict per-session safety and close only after documenting that tradeoff clearly for operators.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainers choose the scheduling contract; queue priority and diagnostic recovery are mitigations, not a complete fix for active compaction occupying the reply/session path.

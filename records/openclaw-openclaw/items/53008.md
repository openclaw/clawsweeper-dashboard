## Summary

Keep open: current main and the latest release still route preflight compaction and memoryFlush through the active reply/session-lane path, so foreground same-session Telegram messages can still wait behind compaction work. The newer timeout and diagnostics reduce the outage window, but they do not implement the requested isolated or preemptible compaction lane.

## What This Changes

The issue asks OpenClaw to prevent memoryFlush/compaction from monopolizing the main/session processing lane so inbound Telegram messages keep processing during slow compaction.

## Best Possible Solution

Keep this as the canonical maintainer design thread and implement a session-safe isolated, bounded, or preemptible compaction/memoryFlush path with regression coverage for foreground same-session messages.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: current main still calls preflight compaction and memoryFlush inside the reply path, and queued compaction still uses the same session lane. I did not run a live Telegram hang repro.

## Solution Assessment

No, the current mitigations are not the best complete solution because shorter timeouts and stuck-session recovery still allow foreground messages to wait behind compaction. The maintainable fix needs a maintainer-approved isolation or preemption contract for compaction work.

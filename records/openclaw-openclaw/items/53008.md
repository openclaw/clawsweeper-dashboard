## Label Justifications

- `P1`: The issue describes a real user-facing Telegram workflow becoming unresponsive while foreground messages wait behind compaction work.
- `impact:session-state`: The affected behavior is session memoryFlush/compaction scheduling, transcript state, and per-session lane serialization.
- `impact:message-loss`: Inbound Telegram messages are reported as queued and not processed until manual recovery.
- `impact:crash-loop`: The observed recovery required a manual gateway restart after the session processing lane stayed wedged.

## Summary

Keep open: current main and the latest release still run preflight compaction and memoryFlush inside the foreground reply/session-lane path, so the central unresponsive-bot problem is not implemented away. The newer 180s compaction safety timeout reduces one worst case but does not give foreground messages an isolated or preemptive lane.

## What This Changes

The issue asks OpenClaw to prevent memory compaction and memoryFlush work from blocking foreground Telegram message processing for minutes.

## Best Possible Solution

Adopt a maintainer-approved bounded maintenance-lane, preemption, or recovery design that lets foreground channel messages be acknowledged or processed promptly while preserving session ordering and transcript safety.

## Reproduction Assessment

Yes: at source level, trigger preflight compaction or memoryFlush on a busy same-session channel path, then send another message; current main awaits those phases in the reply path and serializes embedded work through the same session lane. I did not run a live Telegram timeout replay.

## Solution Assessment

No current implementation fully solves it: timeout and watchdog changes reduce the worst hang duration but do not make compaction or memoryFlush out-of-band. The best fix needs maintainer agreement on scheduler and session-state semantics before implementation.

## Label Justifications

- `P1`: The issue describes a real Telegram workflow becoming unresponsive for minutes while foreground messages wait behind compaction work.
- `impact:session-state`: The affected behavior is session memoryFlush and compaction scheduling, transcript state, and per-session lane serialization.
- `impact:message-loss`: Inbound Telegram messages are reported as queued and not processed until manual gateway recovery.
- `impact:crash-loop`: The reported recovery required manually restarting the gateway after the session processing lane stayed wedged.

## Summary

Keep open: current main and v2026.6.11 still run preflight compaction and memoryFlush inside the active reply/session path, so the reported foreground-message starvation is not implemented away. The default compaction timeout is now 180 seconds instead of the reported 600 seconds, but the central nonblocking-lane behavior remains missing.

## What This Changes

The issue requests preventing memoryFlush and session compaction from blocking inbound Telegram/main-lane message processing during long compaction runs.

## Best Possible Solution

Land a maintainer-approved bounded or preemptible maintenance-lane design for compaction and memoryFlush that preserves transcript ordering while allowing foreground channel messages to be acknowledged or processed promptly.

Question: What scheduler contract should OpenClaw use when preflight compaction or memoryFlush is active and a foreground channel message arrives for the same session?

Rationale: The source path is clear, but the fix changes session ordering, transcript rotation safety, and channel acknowledgment behavior rather than a narrow local bug fix.

Likely owner: steipete

Owner reason: The memoryFlush feature and command-queue serialization history make this the strongest routing signal for the scheduler/session contract decision.

Owner confidence: medium

Options:

- **Dedicated maintenance lane (recommended):** Move compaction and memoryFlush to an isolated or preemptible maintenance lane with explicit transcript-lock and foreground-ack semantics.
- **Serialized with bounded recovery:** Keep compaction in the current session path but add shorter fail-open recovery and a visible busy/queued acknowledgment for foreground messages.
- **Keep current serialization:** Accept delayed foreground messages during compaction and rely on timeout/config tuning, preserving the current simple ordering contract.

## Reproduction Assessment

Yes, at source level: trigger preflight compaction or memoryFlush on a busy session, then send another same-session channel message. Current main awaits those phases and serializes embedded runs through the same session/main lanes; I did not run a live Telegram timeout replay.

## Solution Assessment

No current fix is in place. Timeout tuning is only a mitigation; the maintainable fix needs a scheduler/session-state design for foreground work during maintenance compaction.

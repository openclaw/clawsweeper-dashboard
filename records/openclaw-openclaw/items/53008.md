- `P1`: A real Telegram/agent workflow can become unresponsive for minutes while session maintenance occupies the foreground lane.
- `impact:session-state`: The reported failure is rooted in session compaction and memory-flush state occupying the active session lane.
- `impact:message-loss`: Inbound Telegram messages were queued and not processed until manual recovery, which is a channel message-delivery failure mode.

## Summary

Keep open: current main and the latest release have mitigations, but source still shows preflight compaction and memoryFlush occupying the foreground reply/session lane instead of an isolated or preemptible maintenance lane.

## What This Changes

The issue reports that memoryFlush/session compaction can occupy the main processing lane for the full compaction timeout, leaving Telegram messages queued and the bot unresponsive.

## Best Possible Solution

Move compaction and memory-flush maintenance out of the foreground message lane, or add a maintainer-approved preemptible/isolated compaction lane with explicit timeout and recovery semantics for queued user messages.

Options:

- **Isolate compaction lane (recommended):** Run compaction and memoryFlush in a dedicated low-concurrency lane or worker so foreground user messages can be admitted or acknowledged without waiting for the full maintenance timeout.
- **Preempt foreground maintenance:** Keep the lane model but make compaction/memoryFlush abortable and reschedulable when user messages arrive, preserving stricter ordering at the cost of scheduler complexity.
- **Accept timeout mitigation:** Treat the current 180-second timeout and stuck-session recovery as sufficient mitigation, leaving foreground turns blocked during active compaction windows.

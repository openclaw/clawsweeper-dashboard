## Summary

Keep open: current main and v2026.6.11 reduce the stall window and add recovery/priority mitigations, but preflight compaction and memoryFlush still run through the foreground reply/session operation rather than an isolated or preemptible maintenance lane.

## What This Changes

The issue requests that memoryFlush and session compaction stop blocking foreground Telegram/user message processing for minutes.

## Best Possible Solution

Define a core scheduler policy that isolates or preempts compaction and memoryFlush maintenance from foreground user turns while preserving one active transcript writer and explicit recovery semantics.

Options:

- **Isolate maintenance lane (recommended):** Run compaction and memoryFlush in a dedicated low-concurrency maintenance lane or worker so foreground user messages can be admitted, acknowledged, or scheduled without waiting for the full maintenance timeout.
- **Make maintenance preemptible:** Keep the current lane model but abort and reschedule compaction/memoryFlush when fresh user work arrives, trading simpler ownership for more abort/retry complexity.
- **Accept timeout mitigation:** Keep active compaction/memoryFlush in the foreground session lane and rely on the 180-second default timeout plus stuck-session diagnostics as the product behavior.

Yes at source level: current main still awaits preflight compaction and memoryFlush inside the reply/session path, and compaction is queued through the per-session lane. I did not run a live Telegram stall repro, and the default timeout is now 180 seconds rather than the original ten minutes.

## Solution Assessment

No final implementation is selected yet. Timeout and diagnostic mitigations help, but the best fix needs a maintainer scheduler decision about isolation or preemption rather than another one-sided timeout patch.

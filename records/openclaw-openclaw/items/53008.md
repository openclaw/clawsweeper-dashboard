## Label Justifications

- `P1`: The issue describes a real Telegram workflow becoming unresponsive for minutes while user messages queue behind compaction work.
- `impact:session-state`: The affected behavior is session memoryFlush/compaction scheduling, transcript state, and per-session lane serialization.
- `impact:message-loss`: Inbound Telegram messages are reported as queued and not processed while compaction occupies the active lane.
- `impact:crash-loop`: The reported recovery required manually restarting the gateway after the session processing lane stayed wedged.

## Summary

Keep open: current main and the latest checked release still run preflight compaction and memoryFlush in the active reply/session scheduling path. The timeout is now 180s and diagnostics can recover stale sessions, but the requested dedicated, bounded, or preemptible compaction path for foreground channel responsiveness is not implemented.

## What This Changes

The issue requests that memory compaction and memoryFlush stop blocking inbound Telegram/main-lane message processing for minutes.

## Best Possible Solution

Land a maintainer-approved bounded or preemptible maintenance-lane design for memoryFlush and compaction that preserves session ordering while allowing foreground channel messages to be acknowledged or processed promptly.

## Reproduction Assessment

Yes, at source level: current main still awaits preflight compaction, runs memoryFlush on CommandLane.Main, and queues compaction through the same session/global lane structure.

## Solution Assessment

No, current main is only partially mitigated by a shorter timeout and diagnostics; the durable fix needs maintainer agreement on scheduler and session-state semantics.

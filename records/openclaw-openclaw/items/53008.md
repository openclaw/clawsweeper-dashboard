## Summary

Keep open: current main and the latest release still await preflight compaction and memoryFlush in the foreground reply/session execution path, so the central Telegram unresponsiveness risk is mitigated but not implemented away. ## What This Changes

The issue reports that memoryFlush and preflight compaction can monopolize the interactive Telegram/session lane for minutes, queueing inbound messages until timeout or gateway restart.

## Best Possible Solution

Keep this as the canonical P1 lane-isolation tracker until compaction and memoryFlush have a foreground-safe scheduling design, bounded recovery behavior, and regression proof that queued Telegram/inbound messages drain while compaction is slow or stuck.

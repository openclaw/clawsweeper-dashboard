## Label Justifications

- `P1`: A real Telegram/agent workflow can become unresponsive for minutes while session maintenance occupies the foreground lane.
- `impact:session-state`: The failure is rooted in session compaction and memoryFlush state occupying the active session operation.
- `impact:message-loss`: Inbound Telegram messages were queued and not processed until timeout or manual recovery.
- `impact:crash-loop`: The bot became effectively unavailable for the affected session and required gateway restart in the report.

## Summary

Keep open: current main and v2026.6.11 still run preflight compaction and memoryFlush as foreground session maintenance, so the user-visible lane can still queue inbound Telegram messages during long maintenance work even though the default compaction timeout is now shorter.

## What This Changes

The issue asks for pre-compaction memory flush and compaction maintenance to stop monopolizing the foreground message lane during long timeouts.

## Best Possible Solution

Define a maintainer-approved compaction/memoryFlush scheduling contract that either isolates maintenance from foreground user turns or makes it preemptible with explicit timeout, recovery, and user-visible queued-message behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw isolate or preempt compaction and memoryFlush from the foreground session lane, or keep the current foreground-lane model with shorter timeouts and diagnostic recovery?

Rationale: The source-backed problem is real, but the durable fix changes session ordering, transcript consistency, and delivery guarantees for interactive turns versus context maintenance.

Likely owner: steipete

Owner reason: The feature history most directly ties steipete to memoryFlush ownership and current foreground maintenance code, making them the best available owner for the scheduling tradeoff.

Owner confidence: medium

Options:

- **Isolate maintenance lane (recommended):** Run compaction and memoryFlush in a dedicated low-concurrency maintenance lane or worker so foreground user messages can be admitted or acknowledged without waiting for the full maintenance timeout.
- **Preempt foreground maintenance:** Keep the current lane model but make compaction and memoryFlush abortable and reschedulable when user messages arrive, preserving stricter ordering at the cost of scheduler complexity.
- **Accept timeout mitigation:** Treat the current 180-second default timeout and stuck-session diagnostics as sufficient, leaving foreground turns blocked during active maintenance windows.

## Reproduction Assessment

Yes from source inspection, but not from a live current-main Telegram repro: current main still awaits preflight compaction and memoryFlush inside the foreground reply/session operation while later messages queue behind active work.

## Solution Assessment

Unclear until maintainers choose the scheduler contract; timeout-only mitigation reduces outage length but does not satisfy the requested foreground-lane isolation.

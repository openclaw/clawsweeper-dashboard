## Label Justifications

- `P1`: The issue describes a real Telegram workflow becoming unresponsive for minutes while foreground messages wait behind compaction work.
- `impact:session-state`: The affected behavior is session memoryFlush/compaction scheduling, transcript state, and per-session lane serialization.
- `impact:message-loss`: Inbound Telegram messages are reported as queued and never processed until manual gateway recovery.
- `impact:crash-loop`: The reported recovery required manually restarting the gateway after the session processing lane stayed wedged.

## Summary

Keep open: current main and v2026.6.11 still await preflight compaction and memoryFlush inside the foreground reply/session-lane path, so the reported Telegram unresponsiveness is only mitigated by shorter defaults and stuck-session recovery, not implemented away.

## What This Changes

The issue asks for memory compaction and memoryFlush work to stop blocking foreground Telegram/session-lane message processing for minutes.

## Best Possible Solution

Move compaction and memory-flush maintenance out of the foreground message lane, or add a maintainer-approved preemptible/isolated compaction lane with explicit timeout and recovery semantics for queued user messages.

Yes, at source level: trigger preflight compaction or memoryFlush on a busy same-session channel path, then send another same-session message; current main awaits those phases and serializes embedded work through the same session lane. I did not run a live Telegram replay in this read-only review.

## Solution Assessment

No current fix is in place. The 180-second default timeout and stuck-session recovery are useful mitigations, but the maintainable solution needs a maintainer-approved scheduler contract for foreground messages versus maintenance work.

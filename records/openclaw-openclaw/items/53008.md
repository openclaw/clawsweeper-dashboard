## Summary

Current main still serializes required preflight compaction and memory flush in the foreground reply path and queues compaction through the same session/global lanes, so the central request for foreground message processing not to be blocked by compaction remains unresolved despite shorter timeouts and stuck-session recovery.

## What This Changes

The issue requests that memory compaction stop blocking main agent message processing and provide faster recovery when compaction wedges a session lane.

## Best Possible Solution

Keep this open for an owner-approved scheduler and compaction design that isolates or preempts compaction/memory flush from foreground session message handling while preserving transcript ordering and recovery semantics.

## Reproduction Assessment

Yes from source inspection: current main still awaits required preflight compaction and memory flush in the reply path and queues compaction on the same session/global lanes; I did not run a live Telegram or Feishu repro.

## Solution Assessment

No, current main is not the complete fix because reduced timeouts and stale-session recovery bound the hang but do not provide a dedicated or preemptible compaction path for foreground messages.

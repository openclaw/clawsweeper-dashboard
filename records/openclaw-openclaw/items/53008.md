## Label Justifications

- `P1`: The issue describes a real Telegram workflow becoming unresponsive for minutes while foreground messages wait behind compaction work.
- `impact:session-state`: The affected behavior is session memoryFlush/compaction scheduling, transcript state, and per-session lane serialization.
- `impact:message-loss`: Inbound Telegram messages are reported as queued and not processed until manual gateway recovery.
- `impact:crash-loop`: The reported recovery required manually restarting the gateway after the session processing lane stayed wedged.

## Summary

Keep open: current main and the latest release still run preflight compaction and memoryFlush inside the foreground reply/session-lane path, so Telegram messages can still queue behind maintenance work. Related closed reports already route the remaining nonblocking-compaction work here, so this remains the canonical tracker.

## What This Changes

The issue asks for memoryFlush/session compaction to stop blocking foreground Telegram message processing for minutes when compaction hangs or times out.

## Best Possible Solution

Land a maintainer-approved bounded or preemptible maintenance-lane design for compaction and memoryFlush that preserves transcript ordering while allowing foreground channel messages to be acknowledged or processed promptly.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should compaction and memoryFlush move to a separate bounded or preemptible maintenance lane, or should OpenClaw keep strict same-session serialization and only shorten/recover the blocking path?

Rationale: The code path is clear, but the right behavior affects session ordering, transcript rotation, foreground message delivery, and recovery semantics, so automation should not choose the product contract alone.

Likely owner: steipete

Owner reason: The memoryFlush introduction and command-queue serialization history make steipete the strongest available owner for the product contract choice.

Owner confidence: medium

Options:

- **Bounded Maintenance Lane (recommended):** Move compaction and memoryFlush out of the foreground session lane with explicit transcript-locking, acknowledgment, timeout, and regression-test coverage.
- **Serialized With Recovery:** Keep the current serialization contract but add shorter bounded timeouts, visible busy/error behavior, and watchdog reset so the session cannot remain wedged silently.
- **Accept Current Blocking:** Keep the shipped in-band behavior and document timeout/model tuning as the supported mitigation, accepting delayed foreground messages during compaction.

## Reproduction Assessment

Yes, at source level: trigger preflight compaction or memoryFlush on a busy session, then send another same-session channel message; current main awaits those phases and serializes embedded runs through the same session lane. I did not run a live Telegram timeout replay.

## Solution Assessment

No current fix is in place. The best solution is not a config-only timeout tweak; it needs a maintainer-approved maintenance-lane or preemptible/bounded recovery design that preserves transcript and delivery semantics.

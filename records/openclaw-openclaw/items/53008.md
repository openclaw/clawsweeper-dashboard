## Label Justifications

- `P1`: The issue describes a real Telegram workflow becoming unresponsive for minutes while user messages queue behind compaction work.
- `impact:session-state`: The affected behavior is session memoryFlush/compaction scheduling, transcript state, and per-session lane serialization.
- `impact:message-loss`: Inbound Telegram messages are reported as queued and not processed while compaction occupies the active lane.
- `impact:crash-loop`: The reported recovery required manually restarting the gateway after the session processing lane stayed wedged.

## Summary

Keep open: current main still routes preflight compaction and memoryFlush through the active reply/session-lane path, so foreground channel messages can still wait behind active compaction work. Recent mitigations add priorities and recovery paths, but they do not provide the dedicated or preemptible compaction lane requested here.

## What This Changes

The issue asks for memory compaction to stop monopolizing the main processing lane so inbound Telegram messages are not queued behind long compaction runs.

## Best Possible Solution

Land a maintainer-approved bounded or preemptible maintenance-lane design for compaction and memoryFlush that preserves session ordering while allowing foreground channel messages to be acknowledged or processed promptly.

## Reproduction Assessment

Yes, at source level: current main still awaits preflight compaction, runs memoryFlush on `CommandLane.Main`, and queues compaction through the same `session:<key>` lane. I did not run a live Telegram timeout reproduction in this read-only pass.

## Solution Assessment

No, the current implementation is only partially mitigated by queue priority and recovery paths. The best fix needs maintainer agreement on scheduler and session-state semantics before implementation.

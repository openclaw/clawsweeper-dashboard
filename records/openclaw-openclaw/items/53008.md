- `P1`: A real Telegram/agent workflow can become unresponsive for minutes while session maintenance occupies the foreground lane.

- `impact:message-loss`: Inbound Telegram messages were queued and not processed until timeout or manual recovery.
- `impact:crash-loop`: The bot became effectively unavailable and required gateway restart recovery, which is a process-availability hang.

## Summary

Keep open: current main and v2026.6.11 reduce the worst timeout and add stuck-session recovery, but compaction and memoryFlush still occupy the foreground session/reply lane, so the central blocking problem remains.

## What This Changes

The issue asks for session compaction and memoryFlush work to stop starving inbound Telegram/user-message processing for minutes.

## Best Possible Solution

Adopt a maintainer-approved isolated or preemptible maintenance lane for compaction/memoryFlush, with explicit timeout, abort, recovery, and queued-message semantics.

Options:

- **Isolate maintenance lane (recommended):** Run compaction and memoryFlush in a dedicated low-concurrency lane or worker so new user messages can be admitted or acknowledged without waiting for maintenance to finish.
- **Preempt foreground maintenance:** Keep the existing lane model but make compaction and memoryFlush abortable and reschedulable when user-visible work arrives.
- **Accept recovery mitigation:** Treat the current 180-second compaction timeout and stuck-session recovery as sufficient, leaving active compaction windows foreground-blocking by design.

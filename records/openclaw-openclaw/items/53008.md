## Label Justifications

- `P1`: The issue reports a real Telegram workflow becoming unresponsive for minutes while user messages queue behind compaction work.
- `impact:session-state`: The affected behavior is session memory flush, compaction scheduling, transcript rotation, and per-session reply admission.
- `impact:message-loss`: Inbound Telegram messages are reported as queued and not processed while compaction occupies the active lane.
- `impact:crash-loop`: The reported recovery required manually restarting the gateway after the session processing lane stayed wedged.

## Summary

Keep open: current main and the latest stable release still run memory flush and preflight compaction through the foreground reply/session scheduling path, so the central request to keep Telegram messages from waiting behind compaction remains unresolved.

## What This Changes

The issue asks OpenClaw to prevent memory flush and session compaction from blocking the main Telegram message-processing lane.

## Best Possible Solution

Adopt a maintainer-approved isolation contract for memory flush and preflight compaction, such as a dedicated bounded maintenance lane or background compaction path, with tests proving foreground messages do not wait while transcript rotation remains safe.

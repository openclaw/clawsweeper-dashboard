## Summary

Keep open: current main and the latest release still route preflight compaction and memoryFlush through the session/main processing lanes. The 600s timeout has been reduced to 180s and stuck-session recovery exists, but the central request for foreground message processing not to wait behind compaction remains unresolved.

## What This Changes

The issue asks for memory compaction and memoryFlush work to stop monopolizing the main processing lane so Telegram messages are not queued behind a long compaction timeout.

## Best Possible Solution

Adopt a maintainer-approved scheduler design that prevents foreground user messages from waiting behind memoryFlush or preflight compaction, with focused coverage for ordering, cancellation, timeout, and recovery semantics.

## Label Justifications

- `P1`: The issue describes a real Telegram workflow becoming unresponsive for minutes while foreground messages wait behind compaction work.
- `impact:session-state`: The affected behavior is session memoryFlush/compaction scheduling, transcript state, and per-session lane serialization.
- `impact:message-loss`: Inbound Telegram messages are reported as queued and never processed until manual gateway recovery.
- `impact:crash-loop`: The reported recovery required manually restarting the gateway after the session processing lane stayed wedged.

## Summary

Keep open: current main and the latest release still run preflight compaction and memoryFlush in the foreground reply/session-lane path, so the reported Telegram unresponsiveness is not implemented away. The timeout default is now documented as 180 seconds, but explicit longer compaction timeouts are still allowed and the central lane-starvation behavior remains.

## What This Changes

The issue reports memoryFlush/session compaction blocking the main processing lane so inbound Telegram messages queue behind maintenance work until timeout or manual gateway restart.

## Best Possible Solution

Land a maintainer-approved bounded or preemptible maintenance-lane design for compaction and memoryFlush that preserves session ordering while allowing foreground channel messages to be acknowledged or processed promptly.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw isolate or preempt compaction and memoryFlush work from foreground same-session message handling, and what transcript-ordering contract should that design preserve?

Rationale: The bug is source-reproducible, but the fix is a scheduler/session-state design choice rather than a narrow line repair because it changes how compaction, memoryFlush, transcript rotation, active-run steering, and channel acknowledgments interact.

Likely owner: steipete

Owner reason: steipete is the strongest available routing signal from the memoryFlush feature history and current adjacent reply-path edits.

Owner confidence: medium

Options:

- **Design a bounded maintenance lane (recommended):** Move compaction and memoryFlush to a dedicated bounded/preemptible maintenance path with explicit ordering and recovery tests for foreground channel messages.
- **Keep serialization and add busy recovery:** Keep the current same-lane model but add a shorter bounded failure path plus visible busy/retry recovery so users are not silently blocked.
- **Preserve blocking behavior:** Treat compaction as intentionally foreground and close or defer nonblocking message handling as out of scope for now.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes, at source level: trigger preflight compaction or memoryFlush on a busy same-session channel path, then send another same-session message; current main awaits those phases and serializes embedded work through the same session lane.

## Solution Assessment

Is this the best way to solve the issue? No current fix is in place; reducing the default timeout is only a partial mitigation because active compaction and memoryFlush still occupy the foreground session path.

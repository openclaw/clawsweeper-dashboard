## Summary

Keep open: current main and v2026.6.11 still run preflight compaction and memoryFlush inside the active reply/session scheduling path. The default compaction timeout is now 180s instead of the reported 600s, but there is still no dedicated or preemptible compaction lane that would let foreground Telegram messages proceed promptly.

## What This Changes

The issue asks for memoryFlush/session compaction to stop blocking inbound Telegram and other user-message processing for minutes.

## Best Possible Solution

Adopt a maintainer-approved maintenance-lane or preemptible-background design for compaction and memoryFlush that preserves session-state ordering while allowing foreground channel messages to be acknowledged or processed promptly.

## Reproduction Assessment

Yes, at source level. Current main still awaits required preflight compaction, runs memoryFlush on CommandLane.Main, and queues compaction through the same session/global lane structure; I did not run a live Telegram timeout reproduction.

## Solution Assessment

No, current main is only a partial mitigation because the shorter timeout does not isolate background compaction from foreground messages. The best fix needs maintainer agreement on scheduler and session-state semantics before implementation.

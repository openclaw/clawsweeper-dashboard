## Label Justifications

- `P1`: A real Telegram/agent workflow can become unresponsive for minutes while session maintenance occupies the foreground lane.
- `impact:session-state`: The failure is rooted in session compaction and memory-flush state occupying the active session lane.
- `impact:message-loss`: Inbound Telegram messages were queued and not processed until recovery, which is a channel message-delivery failure mode.
- `impact:crash-loop`: The bot became effectively unavailable and required a gateway restart in the original field report.

## Summary

Keep open: current main and the latest stable release have shorter timeout and diagnostic-recovery mitigations, but compaction and memoryFlush still occupy the foreground reply/session lane rather than an isolated or preemptible maintenance path.

## What This Changes

Issue #53008 asks OpenClaw to prevent memory compaction and memoryFlush from blocking inbound Telegram/session messages for minutes.

## Best Possible Solution

Move compaction and memoryFlush out of the foreground message lane, or add a maintainer-approved preemptible maintenance lane with explicit transcript-ordering, timeout, and queued-message recovery semantics.

Rationale: The source-backed issue remains, but the durable fix changes scheduler and session-state ordering guarantees for interactive turns versus context maintenance.

Owner confidence: medium

Options:

- **Isolate maintenance lane (recommended):** Run compaction and memoryFlush in a dedicated low-concurrency or background lane so foreground user messages can be admitted or acknowledged without waiting for maintenance to finish.
- **Preempt foreground maintenance:** Keep the session-lane model but make compaction and memoryFlush abortable and reschedulable when user messages arrive.
- **Accept mitigation only:** Treat the 180-second timeout and stuck-session recovery as sufficient, leaving foreground turns blocked during active maintenance windows.

## Reproduction Assessment

Yes, source-reproducible: current main awaits preflight compaction and memoryFlush inside the foreground reply operation, and compaction itself is queued through the same per-session lane; no live Telegram repro was run.

## Solution Assessment

No final implementation is selected yet; timeout and stuck-recovery mitigations reduce the outage window but do not satisfy the requested isolated or preemptible foreground-lane behavior.

## Label Justifications

- `P1`: A real Telegram workflow can become unresponsive for minutes while foreground messages queue behind compaction work.
- `impact:message-loss`: Inbound Telegram messages are reported as queued and not processed while the active lane is occupied.
- `impact:session-state`: The affected path is session memoryFlush, compaction, transcript state, and per-session lane serialization.
- `impact:crash-loop`: The reported recovery required manually restarting the gateway after the processing lane stayed wedged.

## Summary

Keep open: current main and the latest release still run preflight compaction and memoryFlush inside the active reply/session scheduling path. The default compaction timeout is now 180 seconds instead of the reported 600 seconds, but there is still no dedicated or preemptible compaction lane that would let foreground Telegram messages proceed promptly; https://github.com/openclaw/openclaw/pull/81190 addresses a narrower tool-result overflow ordering case, not this lane-isolation problem.

## What This Changes

This issue reports that session memoryFlush/compaction can run in-band with interactive message processing, leaving Telegram messages queued behind a long compaction until timeout or manual gateway restart.

## Best Possible Solution

Land a maintainer-approved scheduler design that makes compaction and memoryFlush bounded, cancelable, and non-starving for foreground channel messages while preserving session transcript ordering.

## Reproduction Assessment

Yes, at source level: current main still awaits preflight compaction, runs memoryFlush on `CommandLane.Main`, and has no dedicated compaction lane. I did not run a live Telegram timeout reproduction.

## Solution Assessment

No, the current timeout reduction is only a mitigation because compaction can still occupy the interactive session lane. The best fix needs maintainer agreement on lane isolation or preemption semantics before implementation.

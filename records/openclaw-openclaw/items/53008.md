## Label Justifications

- `P1`: The issue describes a real Telegram workflow becoming unresponsive for 10+ minutes while foreground messages wait behind compaction work.
- `impact:session-state`: The affected behavior is session memoryFlush/compaction scheduling, transcript state, and per-session lane serialization.
- `impact:message-loss`: Inbound Telegram messages are reported as queued and never processed until manual gateway recovery.
- `impact:crash-loop`: The reported recovery required manually restarting the gateway after the session processing lane stayed wedged.

## Summary

Keep open: current main and the latest release still run preflight compaction and memoryFlush inside the active reply/session-lane path, so the central Telegram unresponsiveness problem is not implemented away. The report remains the canonical tracker for compaction and memoryFlush starving foreground message processing.

## What This Changes

The issue asks for memory compaction and memoryFlush to stop blocking inbound Telegram messages for minutes, likely through a separate, bounded, or preemptible maintenance lane.

## Best Possible Solution

Land a maintainer-approved bounded or preemptible maintenance-lane design for compaction and memoryFlush that preserves session ordering while allowing foreground channel messages to be acknowledged or processed promptly.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes, at source level: trigger preflight compaction or memoryFlush on a busy session, then send another same-session channel message; current main awaits those phases and serializes embedded runs through the same session lane. I did not run a live Telegram timeout replay.

## Solution Assessment

Is this the best way to solve the issue? No current fix is in place; queue priority and recovery mitigations are not enough because active compaction still occupies the reply/session path. The best fix needs maintainer agreement on scheduler and session-state semantics before implementation.

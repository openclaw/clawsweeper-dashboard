## Summary

Keep open: current main and the latest release still run preflight compaction and memoryFlush in the foreground reply/session path. The default compaction timeout is now 180s and stale-session recovery exists, but there is still no dedicated or preemptible compaction lane that guarantees new Telegram messages can proceed while maintenance work is active.

## What This Changes

The issue requests that session memory compaction and memoryFlush stop occupying the main processing lane so Telegram messages are not queued behind long maintenance work.

## Best Possible Solution

Make foreground user turns able to proceed or receive an immediate in-product recovery/deferral path while compaction and memoryFlush run in a bounded maintenance lane, preserving session ordering and transcript adoption invariants.

Options:

- **Dedicated maintenance lane (recommended):** Run compaction and memoryFlush in a bounded background lane with explicit session-state adoption rules and foreground user-message recovery behavior.
- **Watchdog-only recovery:** Keep current serial ordering but make diagnostics cancel or release stuck compaction faster and surface a user-visible recovery notice.
- **Keep current ordering:** Accept that compaction may block a session until timeout/recovery and document timeout tuning as the supported mitigation.

## Reproduction Assessment

Yes, from source and the reporter's logs: force a session into memoryFlush/preflight compaction and make that maintenance run slow or hang; current code awaits the maintenance path before the normal turn and serializes same-session work. I did not run a live Telegram repro.

## Solution Assessment

Unclear as implementation direction: a separate/preemptible maintenance lane is likely the right product shape, but it needs maintainer approval because it changes session ordering and recovery semantics.

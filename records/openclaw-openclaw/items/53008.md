## Summary

Keep open: current main and the latest release still run memoryFlush and preflight compaction in the foreground reply/session path, so the central Telegram unresponsiveness problem is not implemented on main. The timeout has been reduced to 180s, but there is still no dedicated or preemptible compaction lane.

## What This Changes

The issue requests that memoryFlush/session compaction stop blocking foreground Telegram message processing for minutes.

## Best Possible Solution

Land a maintainer-approved dedicated or preemptible maintenance-lane design for memoryFlush and compaction, preserving session ordering while keeping foreground channel messages responsive.

## Maintainer Decision

Question: Should OpenClaw move memoryFlush and preflight compaction into a dedicated/preemptible maintenance lane, or keep them in-band with shorter timeouts and watchdog recovery?

Rationale: The bug is source-reproducible and high impact, but the durable fix changes scheduler and session-state ordering semantics that automation should not choose alone.

Likely owner: Peter Steinberger

Owner confidence: high

Options:

- **Dedicated Maintenance Lane (recommended):** Move memoryFlush and compaction out of the foreground reply lane while preserving transcript rotation and active-run invariants.
- **In-Band With Watchdog:** Keep the current lane ownership but add faster abort, stuck-lane recovery, and user-visible diagnostics.
- **Timeout Mitigation Only:** Treat the 180s default timeout and current notices as sufficient and leave lane isolation out of scope for now.

## Reproduction Assessment

Yes, at source level: current main still awaits memoryFlush and preflight compaction in the active reply path, with memoryFlush on CommandLane.Main and queued compaction on the same session/global lane structure. I did not run a live Telegram timeout reproduction.

## Solution Assessment

Unclear without maintainer direction: the current 180s timeout is only a mitigation, not the requested lane isolation. A dedicated or preemptible maintenance lane is likely the cleanest end state, but it needs an explicit scheduler/session-ordering decision.

## Summary

Keep open: current main and the latest release cover Android call-log search, SMS search, installed-app/device metadata, and node-scoped Android chat sessions, but Android device control, ADB-style access, and dynamic Android code execution remain absent and need product/security direction.

## What This Changes

The issue requests broader Android node tools, including device control, ADB-style access, dynamic program execution, and Android session isolation improvements.

## Best Possible Solution

Keep the issue open, preserve the shipped call-log/SMS/session-isolation work, and split remaining Android authority into maintainer-approved, permission-gated device-control commands plus a separate decision on ADB or dynamic execution through the generic node-tool/plugin contract.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw accept Android device-control, ADB-style access, or dynamic code execution from connected Android nodes, and should that be Android-specific command work or part of the generic node-advertised tool contract?

Rationale: The remaining work changes phone authority, private-data access, and model-visible execution boundaries, so automation cannot choose the permanent product and security shape safely.

Likely owner: steipete

Owner reason: The strongest current routing signal for the generic node-to-model tool contract and security boundary is the open node-hosted plugin tools candidate plus recent Gateway/node/tool history.

Owner confidence: medium

Options:

- **Split and gate Android authority (recommended):** Implement only narrow Android device-control commands after explicit permission UX and policy review, while deferring ADB and dynamic execution until the generic node-tool trust model is accepted.
- **Route through node-hosted tools:** Use the generic node-registered tools thread and open candidate PR as the core contract, then let Android expose only approved descriptors through that model.
- **Keep high-power execution out of core:** Reject ADB and dynamic Android code execution in OpenClaw core for now and require an external plugin, ClawHub package, or app-specific fork for that authority.

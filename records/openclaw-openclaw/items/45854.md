## Summary

Keep open: current main and v2026.6.11 cover call-log search, SMS search, and per-device Android chat session keys, but the requested device-control, ADB-style access, and dynamic Android code execution remain missing and require maintainer security/product direction.

## What This Changes

Request to expand Android node tools with device control, ADB-style access, dynamic program execution, and isolated per-device Android chat sessions.

## Best Possible Solution

Keep the issue open, preserve the shipped call-log/SMS/session-isolation work, and split the remaining Android authority into permission-gated device-control design plus a separate maintainer decision for ADB or dynamic execution through the generic node-tool/plugin contract.

Kind: security_boundary

Question: Should OpenClaw accept Android device-control, ADB-style access, or dynamic code execution from connected Android nodes, and should that be Android-specific commands or part of a generic node-advertised tool contract?

Rationale: The unresolved work changes phone-control, private-data, and model-visible execution boundaries; automation cannot choose the permanent security and product shape safely.

Likely owner: steipete

Owner confidence: medium

Options:

- **Split and gate Android authority (recommended):** Implement only narrow Android device-control commands after explicit permission UX and policy review, while deferring ADB and dynamic execution until the generic node-tool trust model is accepted.
- **Route through node-hosted tools:** Use the node-registered-tools design thread as the core contract and let Android expose only approved descriptors through that model.
- **Keep high-power execution out of core:** Reject ADB and dynamic Android code execution in OpenClaw core for now and require external plugins or app-specific forks for that authority.

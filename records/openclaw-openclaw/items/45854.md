## Summary

Keep open: the shipped Android app now covers call-log search, SMS search, and per-device Android chat session isolation, but device control, ADB-style access, and dynamic Android code execution remain absent and need maintainer security/product direction.

## What This Changes

Request Android node enhancements for call logs, SMS, device control, ADB-style access, dynamic program execution, and per-device session isolation.

## Best Possible Solution

Keep this open, preserve the shipped call-log/SMS/session-isolation work, and split the remaining Android authority into maintainer-approved, permission-gated device-control commands plus a separate decision on ADB or dynamic execution through the generic node-tool/plugin contract.

Rationale: The remaining work is not a narrow bug fix; it changes phone authority, private-data access, and model-visible execution boundaries, so automation cannot choose the permanent security/product shape.

Options:

- **Split and gate Android authority (recommended):** Implement only narrow Android device-control commands after explicit permission UX and policy review, while deferring ADB and dynamic execution until the generic node-tool trust model is accepted.
- **Route through node-hosted tools:** Use https://github.com/openclaw/openclaw/issues/8287 and the candidate PR path as the core contract, then let Android expose only approved descriptors through that model.
- **Keep high-power execution out of core:** Reject ADB and dynamic Android code execution in OpenClaw core for now and require external plugins or app-specific forks for that authority.

## Summary

Keep open. Current main and the latest release contain the completed calllog.search, sms.search, and per-device session work, but the remaining Android device-control, ADB, and dynamic execution requests are still absent and need product/security direction before implementation.

## What This Changes

The issue requests a broader Android node roadmap: more phone tools, device control, ADB-style access, dynamic program execution, and isolated per-device chat sessions.

## Best Possible Solution

Keep the issue open as the Android roadmap, preserve the shipped calllog/search/session pieces, and split the remaining work into maintainer-approved opt-in command families with a clear security boundary before implementation.

Rationale: The remaining work changes what a connected phone can let the model read or execute, so automation cannot safely choose the trust model, sandbox, approval prompts, or core-versus-plugin boundary.

Options:

- **Split and gate narrow commands (recommended):** Define small device-control commands first, make privacy or control actions explicit opt-in through existing node command policy, and defer ADB/dynamic execution until the generic node-tool trust model is accepted.
- **Route through generic node tools:** Treat ADB and dynamic execution as dependent on https://github.com/openclaw/openclaw/issues/8287 so Android does not grow one-off model-visible execution paths.
- **Decline arbitrary execution:** Keep Android limited to reviewed native command handlers and reject arbitrary Kotlin/ADB execution unless a maintainer sponsors a hardened sandbox design.

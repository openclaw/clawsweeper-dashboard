## Summary

Keep open: current main intentionally retries only Telegram send failures with verified pre-connect provenance or recognized low-level codes; it still does not establish that every bare grammY `Network request for 'X' failed!` envelope is safe to replay. The merged v2026.7.1 retry improvement covers TCP/TLS connect-timeout codes, but the fresh production report on v2026.6.11 shows the broader message-loss problem and no current-main live proof establishes that it is fully resolved.

**Likely related people**
- `obviyus` — high-confidence owner of the strict Telegram safe-send retry boundary.
- `lzw112` — high-confidence recent contributor to Telegram pre-connect error classification.
- `chinar` — medium-confidence contributor to the earlier wrapped pre-connect retry path.

## What This Changes

Classify bare grammY network-failure envelopes safely enough to retry Telegram sends without silently losing completed replies or duplicating delivered messages.

## Best Possible Solution

Preserve the strict duplicate-safety boundary, carry verifiable pre-connect provenance or concrete transport codes through grammY and delivery wrappers, retry those cases once with bounded backoff, and keep ambiguous outcomes durably visible for reconciliation or user-facing recovery instead of silently ending the turn.

## Maintainer Decision

Kind: product_direction

Question: Should a bare grammY `Network request for 'X' failed!` message without verified nested pre-connect provenance be replayed for non-idempotent Telegram sends, or should OpenClaw keep it single-shot and improve durable visible recovery?

Rationale: Source inspection shows this is an intentional duplicate-delivery boundary rather than a mechanical regex omission; accepting the broad message trades message loss against possible duplicate sends and therefore needs an explicit owner decision.

Likely owner: obviyus

Owner reason: The strict classifier and duplicate-safety policy originate in this contributor's merged Telegram retry work.

Owner confidence: high

Options:

- **Require proven pre-connect provenance (recommended):** Keep ambiguous envelopes single-shot, propagate concrete low-level causes through wrappers, and add durable visible reconciliation for outcomes that cannot be classified safely.
- **Retry every bare envelope once:** Treat the grammY message itself as proof of a pre-connect failure, accepting the risk that a misclassified ambiguous send may produce a duplicate message.

## Reproduction Assessment

No current-main live reproduction is available, but the failure remains source-reproducible when a bare envelope has no recognized nested pre-connect code; the July 16 production report provides high-quality deployed evidence on v2026.6.11.

## Solution Assessment

No—the suggested optional-`after` regex is not the safest fix because it conflates verified pre-connect failures with potentially ambiguous delivery outcomes. Preserving concrete transport provenance plus durable recovery is the narrower maintainable solution.

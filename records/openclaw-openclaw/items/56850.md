Keep open: current main still only supports fixed cron/heartbeat scheduling primitives, while this request asks for a new state-aware scheduling contract. The June field report adds useful real-world motivation, but implementation needs maintainer product/API design for condition evaluation, state ownership, persistence, migration, and security boundaries.

## What This Changes

Request to let cron or heartbeat schedules choose shorter or longer intervals when declared state conditions are true.

## Best Possible Solution

Define one maintainer-approved scheduling contract first, then implement it consistently across cron schema/protocol, SQLite persistence, CLI, agent tool schema, heartbeat interactions, docs, and focused scheduler/security tests.

## Solution Assessment

Unclear. The proposed conditional_interval shape is plausible, but maintainers should first decide whether this belongs in first-class cron scheduling, heartbeat idle/per-task scheduling, plugin hooks, or a narrower activity-timeout contract.

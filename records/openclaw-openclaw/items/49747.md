## Label Justifications

- `P2`: This is a normal-priority channel/session routing bug with a limited but real blast radius for Slack A2A thread workflows.
- `impact:session-state`: The issue is about persisted session metadata drifting from the intended Slack thread route to webchat.
- `impact:message-loss`: Misrouted announce or reply delivery can send responses to the wrong session instead of the intended Slack thread.

## Summary

Keep open: current main and the latest release still do not extract the encoded Slack provider from `agent:<id>:slack:...` group/thread keys, so the central routing drift remains. The paired fix candidate is still open at https://github.com/openclaw/openclaw/pull/49750, but it is conflicting and still needs real behavior proof before it can close this issue.

## What This Changes

The issue reports Slack A2A thread routing drift where agent-prefixed Slack session keys can resolve as webchat and restart/announce fallback can route through a base session.

## Best Possible Solution

Review, rebase, and prove the paired Slack routing fix, or replace it with a narrow patch that parses `agent:<id>:<provider>:...` routes before context fallback and keeps target delivery context ahead of base-session fallback.

## Reproduction Assessment

Yes, by source inspection: current main still reads only `parts[0]` as the provider candidate in `resolveGroupSessionKey()`, so `agent:builder:slack:channel:...` can miss the encoded Slack provider and fall back to context such as webchat. I did not run a live Slack transport reproduction in this read-only review.

## Solution Assessment

Yes, the requested direction is the narrow maintainable fix: parse agent-prefixed session routes before contextual provider fallback, then keep explicit target delivery context ahead of base-session fallback. The best path is to get the paired PR rebased, proven, and reviewed rather than opening a duplicate repair lane now.

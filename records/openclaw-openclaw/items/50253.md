## Summary

Keep open: current main and the latest release still keep Gateway LAN/custom bind paths IPv4-only, and prior dual-stack PRs were closed unmerged. The remaining work is real, but it needs maintainer product/security direction before implementation because it changes non-loopback Gateway exposure.

## What This Changes

The issue requests native IPv6 or dual-stack support for Gateway bind/LAN mode so non-loopback Gateway listeners can accept IPv6 connections.

## Best Possible Solution

Define an explicit IPv6/dual-stack Gateway bind contract, then update bind resolution, listen host creation, custom host validation, CLI probes/status, docs, tests, and security guardrails together.

## Reproduction Assessment

Yes at source level: current main resolves lan to 0.0.0.0, does not expand non-loopback binds to IPv6, and rejects IPv6 customBindHost values. I did not run a live IPv6-only deployment.

## Solution Assessment

Unclear. Native IPv6 or dual-stack binding is plausible, but switching lan straight to :: is not clearly the best fix until maintainers choose the exposure, platform, and upgrade contract.

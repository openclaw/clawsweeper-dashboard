## Summary

Keep open: current main and the latest release still document and implement Gateway LAN/custom BYOH bind as IPv4-only, while prior dual-stack PRs were closed unmerged. The request is valid, but needs maintainer product/security direction before implementation because native IPv6 or dual-stack listening changes non-loopback Gateway exposure.

## What This Changes

The issue requests native IPv6 or dual-stack support for Gateway LAN/custom bind listening instead of the current IPv4-only BYOH path.

## Best Possible Solution

Define an explicit Gateway IPv6/dual-stack bind contract, then update bind resolution, listen-host creation, custom-host validation, CLI probes/status, docs, tests, and security guardrails together.

Question: Which Gateway IPv6 bind contract should OpenClaw expose for LAN/custom BYOH deployments?

Rationale: The implementation choice changes non-loopback Gateway reachability and upgrade semantics, and repository policy treats Gateway bind/config/security behavior as maintainer-owned rather than a safe automatic repair.

Likely owner: steipete

Owner reason: steipete has the strongest current-main history signal for the Gateway network resolver and related security-sensitive bind behavior.

Owner confidence: high

Options:

- **Add explicit opt-in dual-stack contract (recommended):** Introduce a documented IPv6 or dual-stack bind mode/path with security warnings, platform listener semantics, and fresh-install plus upgrade proof.
- **Change LAN/custom in place:** Make existing `lan` or `customBindHost` accept IPv6 directly, accepting the compatibility and global IPv6 exposure risk as the new behavior for those modes.
- **Keep IPv4-only core:** Leave core bind behavior IPv4-only and continue documenting reverse-proxy or sidecar workarounds for IPv6-only platforms.

## Reproduction Assessment

Yes, source-level. Current main resolves `lan` to `0.0.0.0`, leaves non-loopback bind hosts unexpanded, and rejects IPv6 `customBindHost` values; I did not run a live IPv6-only deployment.

## Solution Assessment

Unclear. Native IPv6 or dual-stack binding is plausible, but a direct `lan` swap to `::` is not clearly the best fix until maintainers choose the exposure, platform, and upgrade contract.

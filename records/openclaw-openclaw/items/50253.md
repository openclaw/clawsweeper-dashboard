## Summary

Keep open: current main and the latest release still keep Gateway LAN/custom bind paths IPv4-only, and the prior dual-stack PR attempts were closed unmerged; the remaining work needs maintainer product/security direction because it changes non-loopback Gateway exposure.

## What This Changes

The issue requests IPv6 or dual-stack listening support for Gateway LAN bind mode.

## Best Possible Solution

Define an explicit IPv6/dual-stack Gateway bind contract, then update bind resolution, listen-host creation, custom host validation, CLI probes/status, docs, tests, and security guardrails together.

Options:

- **Add explicit dual-stack opt-in (recommended):** Introduce a documented IPv6 or dual-stack bind mode/value with security warnings, platform-specific listener semantics, and fresh-install plus upgrade proof.
- **Change LAN/custom in place:** Make existing `lan` or `customBindHost` accept IPv6 directly, accepting the compatibility and global IPv6 exposure risk as the new default behavior for those modes.
- **Keep IPv4-only core:** Leave core bind behavior IPv4-only and document reverse-proxy or sidecar workarounds for IPv6-only platforms.

## Reproduction Assessment

Yes at source level. Current main resolves `lan` to `0.0.0.0`, leaves non-loopback listen hosts unexpanded, and rejects IPv6 `customBindHost` values; I did not run a live IPv6-only deployment.

## Solution Assessment

Unclear. Native IPv6 or dual-stack support is plausible, but switching `lan` directly to `::` is not clearly the best fix until maintainers choose the exposure, platform, and upgrade contract.

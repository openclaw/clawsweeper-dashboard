## Summary

Keep open: current main and v2026.6.11 still implement and document Gateway LAN/custom BYOH binds as IPv4-only, and the related dual-stack PRs were closed unmerged. The request is valid, but native IPv6 or dual-stack listening needs maintainer product/security direction before implementation.

## What This Changes

Request native IPv6 or dual-stack listening for Gateway LAN/custom bind mode instead of the current IPv4-only bind path.

## Best Possible Solution

Define an explicit Gateway IPv6/dual-stack bind contract, then update bind resolution, listen-host creation, custom-host validation, CLI probes/status, docs, tests, and security guardrails together.

Question: Which Gateway IPv6 bind contract should OpenClaw expose for LAN/custom BYOH deployments?

Rationale: The implementation choice changes non-loopback Gateway reachability and upgrade semantics, so automation cannot safely choose between default dual-stack behavior, explicit opt-in behavior, or keeping the IPv4-only core contract.

Likely owner: steipete

Owner confidence: high

Options:

- **Add explicit opt-in dual-stack contract (recommended):** Introduce a documented IPv6 or dual-stack bind mode/path with security warnings, platform listener semantics, and fresh-install plus upgrade proof.
- **Change LAN/custom in place:** Make existing `lan` or `customBindHost` accept IPv6 directly, accepting the compatibility and global IPv6 exposure risk as the new behavior for those modes.
- **Keep IPv4-only core:** Leave core bind behavior IPv4-only and continue documenting reverse-proxy or sidecar workarounds for IPv6-only platforms.

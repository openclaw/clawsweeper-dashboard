Keep open: current main and v2026.6.11 still implement and document Gateway LAN/custom bind paths as IPv4-only. The request is valid, but it needs maintainer product/security direction before changing Gateway exposure semantics.

Define an explicit IPv6/dual-stack Gateway bind contract, then update bind resolution, listen host creation, custom host validation, CLI probes/status, docs, auth/exposure guardrails, and cross-platform tests together.

Unclear. Native IPv6 or dual-stack binding is plausible, but switching lan directly to :: is not clearly the best fix until maintainers choose the exposure, platform, and upgrade contract.

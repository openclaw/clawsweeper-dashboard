## Summary

Keep open: the PR appears to address the Telegram webhook ACK-before-persistence loss window with the right shared-queue shape, but protected Telegram delivery semantics and the missing live Telegram proof keep it in maintainer-review state.

## What This Changes

The PR routes Telegram webhook updates through the shared SQLite ingress spool before acknowledging, adds a webhook spool drain/retry path, retries transient startup init failures, closes webhook/probe transports, and stops throttling authenticated webhook traffic by the failed-secret limiter.

## Best Possible Solution

Land a maintainer-reviewed version that persists authenticated webhook updates to the shared SQLite ingress queue before 200 ACK, with live Telegram proof for restart replay, dedupe, and high-throughput valid delivery.

## Reproduction Assessment

Yes for a source-level path: current main sends 200 before durable persistence or awaiting bot.handleUpdate, while the PR moves persistence before ACK. I did not run a live Telegram crash/restart reproduction in this read-only review.

## Solution Assessment

Yes, this appears to be the right implementation shape because it reuses the existing SQLite channel ingress queue instead of adding an ad hoc sidecar queue; the remaining blocker is maintainer approval and real Telegram proof for delivery semantics.

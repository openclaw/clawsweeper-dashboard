## Summary

Keep open for maintainer review: this is a plausible, well-scoped fix for Telegram webhook message loss, but it carries the protected maintainer label and lacks real Telegram behavior proof for the transport/restart path. I found no definite line-level correctness defect in the read-only review.

## What This Changes

The branch routes Telegram webhook updates through the existing SQLite ingress spool before acknowledging, adds a webhook spool drain/retry path, retries transient startup init failures, closes owned transports, and rate-limits only failed secret guesses.

## Best Possible Solution

Land a maintainer-reviewed version that persists authenticated webhook updates to the shared SQLite ingress queue before 200 ACK, with live Telegram proof for restart replay, dedupe, and high-throughput valid delivery.

## Reproduction Assessment

Yes for a source-level path: current main sends 200 before durable persistence or awaiting bot.handleUpdate, while the PR moves persistence before ACK. I did not run a live Telegram crash/restart reproduction in this read-only review.

## Solution Assessment

Yes, this appears to be the right implementation shape because it reuses the existing SQLite channel ingress queue instead of adding an ad hoc sidecar queue. The remaining blocker is not a known code defect, but maintainer approval and real Telegram proof for the delivery semantics.

## Label Justifications

- `P1`: A common proxy reconnect pattern can repeatedly invoke a costly gateway operation, degrading availability and causing watchdog restarts for an active deployment.
- `impact:crash-loop`: The report ties the repeated reconnect-triggered scans to sustained memory pressure and multiple watchdog restarts.
- `impact:message-loss`: Gateway restarts caused by the loop can terminate in-flight agent turns, producing observable message loss.

## Summary

Keep this issue open: current main still refreshes the active Control UI tab after every websocket reconnect, and the usage and overview tabs translate that refresh into new `sessions.usage` and `usage.cost` requests. The report identifies a concrete availability loop distinct from, but amplified by, the backend scan-cost problem tracked in https://github.com/openclaw/openclaw/issues/107916.

## What This Changes

Prevent websocket reconnects from repeatedly triggering full Control UI usage-data reloads while an idle or backgrounded tab remains open.

## Best Possible Solution

Keep initial usage loading intact, but make reconnect rehydration reuse already-loaded usage data and refresh it only when stale and visible or explicitly requested; cover first connect, repeated reconnect, tab visibility, and manual refresh while leaving backend scan optimization to the linked issue.

## Maintainer Decision

Required: false

## Reproduction Assessment

No live current-main proxy reproduction was run, but the failure is source-reproducible with high confidence: reconnect calls `refreshActiveTab`, and active usage or overview tabs immediately issue both usage RPCs.

## Solution Assessment

The proposed remedies are not interchangeable: keepalive alone cannot prevent every reconnect, while a reconnect-aware cached usage refresh directly removes the expensive lifecycle coupling without adding protocol or configuration surface.

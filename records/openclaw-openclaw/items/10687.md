## Summary

Keep open: current main has partial dynamic catalog infrastructure and OpenRouter dynamic execution mitigation, but the broad maintainer-labeled issue still owns unresolved provider catalog, allowlist, picker/list scope, cache/offline, and safety-control decisions.

## What This Changes

The issue requests fully dynamic model discovery for OpenRouter and other providers so current provider models can be listed and selected without static catalog updates.

## Best Possible Solution

Keep this as the maintainer-owned umbrella, choose the provider/plugin API and safety semantics, then land focused provider-owned implementations through the guarded live catalog SDK and existing visibility/picker paths.

Options:

- **Provider-owned live catalogs (recommended):** Use the guarded plugin SDK live catalog path per provider, with explicit wildcard, cache, and fallback rules; this preserves core/plugin ownership and builds on current infrastructure.
- **Generated catalog refresh:** Add a config or command-driven refresh that writes local catalog rows, which may help offline use but needs stricter migration and SecretRef-safe write policy.
- **Runtime fallback only:** Continue synthesizing unknown models at execution time and leave list/picker discovery incomplete, accepting weaker UX for fast-moving catalogs.

## Reproduction Assessment

Yes at source level: current OpenRouter catalog rows are static and models.list reuses snapshots, while dynamic hooks and wildcard visibility only partially address the requested live discovery behavior; no live OpenRouter credential path was run in this read-only review.

## Solution Assessment

Unclear as a final implementation: the issue identifies the right gap, but maintainers still need to choose provider-owned discovery versus generated refresh or runtime fallback, plus wildcard, cache, offline, picker, and safety-control semantics.

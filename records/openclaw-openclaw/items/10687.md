- `impact:auth-provider`: The remaining behavior concerns provider model resolution, metadata, and visibility for valid authenticated OpenRouter use.

## Summary

Current main and v2026.6.11 partially solve the original failures: OpenRouter can synthesize explicitly selected unknown model IDs and hydrate capabilities, and OpenClaw has a shared provider catalog pipeline. The central request remains necessary because OpenRouter’s authenticated text catalog still returns the same small static list, so current provider models are not dynamically discoverable in normal list/picker surfaces; protected maintainer and product-direction labels also require an explicit policy decision.

## What This Changes

Add runtime model discovery for fast-moving providers, beginning with OpenRouter, without losing usable model pickers or configured safety and cost controls.

## Best Possible Solution

Keep the shared core catalog pipeline and provider-owned dynamic execution, then make OpenRouter’s existing catalog hook fetch and normalize a bounded live catalog with SQLite-backed lifecycle ownership if persistence is needed; maintainers should define curated default visibility, explicit full selection, allowlist semantics, metadata trust, TTL/offline behavior, and safe fallback before implementation.

Question: What policy should live provider text catalogs use for default visibility, allowlists, capability metadata, cache/offline behavior, and unknown-model execution?

Rationale: The repository already has the necessary provider hooks, but switching from a small static catalog to a large mutable provider catalog changes safety, cost controls, UX, compatibility, and the public plugin contract.

Likely owner: steipete

Owner reason: The history connects this owner most directly to model-catalog unification and OpenRouter metadata and discovery behavior.

Owner confidence: high

Options:

- **Curated live catalogs (recommended):** Fetch through the existing provider catalog hook, cache with an owned bounded lifecycle, show a curated subset by default, and allow explicit full selection.
- **Full live catalogs:** Expose every fetched provider model in list and picker surfaces and rely on filters or user allowlists to control the result.
- **Dynamic execution only:** Keep arbitrary explicitly configured model execution but leave normal model discovery static and scan-oriented.

## Reproduction Assessment

Yes at source level: OpenRouter’s authenticated catalog returns its built-in provider definition rather than fetching current text models, while arbitrary configured IDs are synthesized only during runtime resolution. Partly: provider-owned catalog and dynamic-resolution hooks are the best boundary, but the proposed new core abstraction, disk cache, and `modelsMode` option are not the narrowest maintainable solution under current architecture and storage policy.

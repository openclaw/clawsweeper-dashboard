## Summary

Keep open for a maintainer product decision: current main has substantially improved dynamic-model resolution and provider-scoped picker visibility, but a provider-backed catalog refresh contract for OpenRouter and other configured endpoints remains active, overlapping work. The protected `maintainer` label also requires explicit human handling rather than automated cleanup.

## What This Changes

Request runtime discovery, safe listing, and selection of current provider model catalogs—especially OpenRouter—without stale static registries or exact-model allowlists.

## Best Possible Solution

Use https://github.com/openclaw/openclaw/issues/74481 to choose a provider-owned refresh contract with bounded cache, auth-context isolation, and safe fallback; retain exact allowlists and `provider/*` for visibility policy.

Question: Should OpenClaw standardize a shared provider catalog-refresh hook for configured `/v1/models` endpoints, starting with OpenRouter, or keep discovery entirely provider-specific through the existing runtime hooks?

Rationale: The current code already separates provider behavior from the generic loop, but cache lifetime, credential/tenant scope, failure behavior, and which catalog rows are safe to expose are durable product and API-contract choices.

Likely owner: steipete

Owner confidence: high

Options:

- **Sponsor the shared hook (recommended):** Define a narrow provider SDK catalog-refresh contract with bounded caching and make OpenRouter the first implementation.
- **Provider-owned only:** Document and implement OpenRouter discovery solely through existing dynamic-model and catalog-augmentation hooks without adding a new shared catalog API.
- **Defer live catalogs:** Keep the current forward-compatible resolution and wildcard visibility while relying on static or configured catalogs for listing.

## Summary

## What This Changes

The issue reports that installing and enabling a managed npm plugin causes existing workspace plugins from `plugins.load.paths` to be treated as missing and dropped from CLI/gateway plugin resolution.

## Best Possible Solution

Preserve the persisted plugin index fast path while ensuring current `plugins.load.paths` workspace plugins are included in metadata snapshots and config validation after managed npm installs.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Not live; source inspection shows the reported warning path and a plausible current-main registry path that drops `plugins.load.paths` entries when a persisted installed index is used.

## Solution Assessment

Is this the best way to solve the issue? Yes: the maintainable fix belongs in plugin metadata/installed-index registry construction, not in a config workaround, because workspace plugin discovery is already a documented part of the metadata scope.

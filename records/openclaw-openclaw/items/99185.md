## Summary

Keep open: current main still has a source-backed path where a persisted installed-plugin index can omit current `plugins.load.paths` workspace plugins from metadata/config validation, and the two linked fix PRs are open rather than merged.

## What This Changes

The issue reports that installing and enabling a managed npm plugin causes existing `plugins.load.paths` workspace plugins to disappear from CLI and Gateway plugin resolution with stale-config warnings.

## Best Possible Solution

Land one reviewed, proof-positive fix that includes configured load-path/workspace candidates in the installed-index metadata path without broadening shared discovery or losing plugin-id scoping.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: current main's installed-index branch passes only index candidates, those candidates skip `plugins.load.paths` discovery, and config validation emits the reported stale warning when `knownIds` lacks configured plugins; no live managed-install run was performed.

## Solution Assessment

Is this the best way to solve the issue? Yes: the fix belongs in installed-index manifest registry construction, not in a config workaround, and the issue should remain open while the linked fix PRs are reviewed or closed.

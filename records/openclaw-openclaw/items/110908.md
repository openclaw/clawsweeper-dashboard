## Summary

Keep this PR open for a narrow correction: its new 403 disambiguation can convert an ordinary per-path Vault ACL denial into a provider-wide outage when a valid token lacks permission for `auth/token/lookup-self`. The documented minimal Vault policy grants secret-path reads only, so this can disable otherwise usable owners and contradict the PR’s stated per-reference isolation guarantee.

## What This Changes

The PR classifies shared Vault failures as provider-scoped, aggregates Gateway diagnostics by provider and affected owner, and adds tests for outage fan-out and mixed failures.

## Best Possible Solution

Keep provider-wide classification for unambiguously shared bootstrap, authentication, transport, or availability failures, but preserve a Vault read 403 as ref-scoped unless the resolver has reliable evidence that the token itself is unusable; add a live or fixture proof for a read-capable token without `lookup-self` permission.

Yes, from source and the documented policy: configure a Vault token with read access to one secret path but no `auth/token/lookup-self` capability, then cause a 403 for another path in the same provider batch. ## Solution Assessment

No. Aggregating genuine shared provider outages is the right direction, but using a denied token self-lookup as proof of a shared authentication outage is not safe for the documented scoped-token contract.

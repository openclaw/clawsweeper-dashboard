## Summary

Keep open: current main and the latest shipped release still use the additive cache fallback for compaction context estimation, so the reported premature threshold trigger remains source-reproducible and narrow enough for a focused fix.

## What This Changes

The issue reports premature auto-compaction when context estimation falls back to summing turn-aggregated `cacheRead`/`cacheWrite` instead of using the latest real context token snapshot.

## Best Possible Solution

Make compaction estimation use the latest real context snapshot for threshold decisions and never use turn-aggregated cache buckets as a context-window fallback, while preserving aggregate usage for cost/reporting.

## Reproduction Assessment

Yes at source level: current main still has the additive cache fallback and threshold path that reproduce the inflated estimate when `totalTokens` is zero or absent on an aggregated usage object. I did not run a live Anthropic/container repro in this read-only review.

## Solution Assessment

Yes: the best fix is in the estimator or usage handoff, not a new config knob or reserve-token tuning. The repair should keep cost aggregation separate from context-window estimation.

## Repair Work Prompt

Fix https://github.com/openclaw/openclaw/issues/99843. The bug is that compaction threshold estimation can treat turn-aggregated cache buckets as current context size when `totalTokens` is zero or missing, causing premature auto-compaction. Keep the fix in the compaction estimator or usage handoff; do not add a config option or tune reserve defaults. Preserve aggregate usage/cost reporting, but make threshold decisions prefer the latest real context snapshot or otherwise avoid summing repeated cached context across multiple calls. Add regression coverage for a multi-call cached tool-loop usage shape where aggregate `cacheRead` is much larger than the final context, and for zero-usage error entries being skipped. Do not edit `CHANGELOG.md`.

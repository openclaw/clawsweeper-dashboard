## Summary

Keep open: current main still contains the fallback that can turn missing or zero `totalTokens` into an inflated context estimate, and the fresh 2026.6.11 report is not closed by older cached-token fixes or adjacent stale reports.

## What This Changes

Auto-compaction is reported to fire too early when context estimation falls back to summed turn-aggregated cache usage instead of the latest real context total.

## Best Possible Solution

Make compaction estimation prefer the latest real context snapshot and never use turn-aggregated cache buckets as a context-window fallback, with regression coverage for multi-call cached tool-loop turns and zero-usage error entries.

## Reproduction Assessment

Yes at source level: current main still has the additive fallback and threshold path that reproduce the inflated estimate when `totalTokens` is zero or absent on an aggregated usage object. A live Anthropic run was not executed in this read-only review.

## Solution Assessment

Yes, the best fix is in the estimator/usage handoff, not a new config knob or reserve-token tuning. The repair should preserve cost accounting while ensuring compaction uses current-context tokens only.

## Repair Work Prompt

Fix https://github.com/openclaw/openclaw/issues/99843. Auto-compaction must not use turn-aggregated `input/output/cacheRead/cacheWrite` as the context-window estimate when `totalTokens` is zero or absent. In the compaction estimator/session handoff, prefer a positive latest-call real context snapshot and make zero/missing aggregate totals fall back to a bounded current-context source, not summed turn cache buckets. Preserve skipping error/aborted assistant usage, keep billing/run usage aggregation intact, and do not add config options or changelog entries. Add focused regression coverage using the reported shape: aggregated cacheRead/cacheWrite with correct last-call/total context should not trip `shouldCompact` for a 300k window and 120k reserve, while true over-threshold latest context still compacts.

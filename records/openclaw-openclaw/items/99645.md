- `P1`: A declined native exec approval can leave Slack/email-style channel users with no answer and an apparently successful terminal turn, which is an urgent user-visible agent workflow failure.

- `impact:message-loss`: The reported failure drops the user-addressed channel reply after a blocked native exec tool result.

## Summary

Keep open: current main has partial user-visible warning behavior for declined Codex-native tools, but it still does not enforce the requested continuation or typed terminal-failure invariant, and `lastToolError` can count as terminal success evidence for an empty user-addressed turn.

## What This Changes

The issue asks OpenClaw to handle declined Codex native exec approvals as recoverable or visibly failed outcomes instead of allowing empty successful turns.

## Best Possible Solution

Define one native approval-denial contract at the Codex app-server bridge and attempt-finalization boundary: preserve blocked and completed sibling tool results, either grant one bounded model continuation or emit a typed user-visible failure, and never record an empty user-addressed turn as success solely because a declined native tool became `lastToolError`.

## Reproduction Assessment

Yes, at source level: current main maps declined Codex-native commands into `lastToolError`, then terminal classification can count that tool error as progress/success without guaranteeing Codex's documented continuation. I did not run the reporter's live Slack/email timing reproduction.

## Solution Assessment

No, the current `lastToolError` warning path is only a partial mitigation because it does not guarantee continuation, sibling-result preservation, or a non-success terminal invariant. The best fix needs a maintainer-approved native-denial contract at the Codex bridge/finalization boundary.

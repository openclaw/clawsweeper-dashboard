## Summary

Keep this open: current main still has the source-level gap where a declined Codex-native exec can become `lastToolError`, and that error is treated as terminal progress instead of enforcing the requested continuation or typed non-success invariant.

## What This Changes

The issue requests recoverable, user-visible handling for declined native exec approvals so user-addressed channel turns cannot finish with empty assistant text as success.

## Best Possible Solution

Define one native-approval-denial contract at the Codex bridge and attempt-finalization boundary: either run one bounded continuation with blocked and sibling tool results preserved, or emit a typed user-visible terminal failure that cannot close as success.

## Reproduction Assessment

Yes at source level: current main maps declined Codex-native commands into `lastToolError`, and the terminal-state helpers treat that as progress while suppressing incomplete-turn fallback. I did not rerun the reporter's Slack/email host timing scenario.

## Solution Assessment

No, the existing `lastToolError` warning path is only a partial mitigation because it does not guarantee model continuation, sibling-result preservation, or a no-empty-success terminal invariant. The best fix needs a maintainer-approved runtime contract before code changes.

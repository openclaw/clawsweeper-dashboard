## Summary

Keep open: current main mitigates declined Codex-native tools by recording a blocked `lastToolError` and sometimes surfacing a warning, but it still treats that error as terminal progress and skips the requested continuation or typed non-success terminal invariant for empty user-addressed turns.

## What This Changes

The issue requests a runtime contract so declined Codex-native exec approvals do not end user-addressed turns with empty assistant text and a successful terminal state.

## Best Possible Solution

Define one Codex-native denial contract at the bridge/finalization boundary: preserve sibling tool results, give one bounded continuation when allowed, or emit a typed user-visible terminal failure instead of treating `lastToolError` alone as success.

## Reproduction Assessment

Yes at source level: a declined native command maps to blocked `lastToolError`, `assistantTexts` can remain empty, and terminal classification treats `lastToolError` as progress; I did not rerun the reporter's Slack/email timing repro.

## Solution Assessment

Unclear pending product direction; a visible `lastToolError` warning is useful mitigation, but it is not the best complete solution because it does not preserve continuation semantics or enforce a non-success empty-turn invariant.

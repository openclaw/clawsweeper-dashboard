## Summary

Keep this open: current main and v2026.6.11 still have only partial safeguards for declined Codex-native exec approvals, because the declined item can become `lastToolError`, count as terminal progress, and still avoid the requested continuation or typed terminal-failure invariant.

## What This Changes

The issue requests a runtime contract so declined Codex-native exec approvals never silently finalize user-addressed turns with empty assistant text or discard completed sibling tool results.

## Best Possible Solution

Define one Codex-native approval-denial contract at the app-server projector and attempt-finalization boundary: preserve blocked and completed sibling results, then either run one bounded continuation or emit a typed user-visible terminal failure, never an empty successful user-addressed turn.

## Reproduction Assessment

Yes at source level: current main can project a declined Codex-native command as `lastToolError`, then treat that as terminal progress while leaving no guaranteed continuation or typed terminal failure. I did not run the reporter's Slack/email host reproduction.

## Solution Assessment

Unclear pending maintainer direction; the current `lastToolError` warning path is a partial mitigation, but it is not the best complete solution because it does not guarantee continuation, sibling-result preservation, or non-success finalization for empty user-addressed turns.

## Label Justifications

- `P1`: A declined native exec approval can leave Slack/email-style channel users with no answer and an apparently successful terminal turn, which is an urgent user-visible agent workflow failure.
- `impact:message-loss`: The reported failure drops the user-addressed channel reply after a blocked native exec tool result.
- `impact:session-state`: The trajectory/session terminal state can record `assistantTexts: []` with success or interruption while completed sibling tool results are not carried into a final answer.
- `maturity:stable`: The affected Gateway runtime approvals and remote-execution area is listed as M4 Stable in the maturity shortlist.

## Summary

Keep this open: current main and the latest release have partial safeguards for declined Codex-native tools, but the source path still allows a declined native exec to become `lastToolError`, which can count as terminal progress and suppress the incomplete-turn warning rather than enforcing the requested continuation or typed terminal-failure invariant.

## What This Changes

The issue asks OpenClaw to make declined Codex-native exec approvals recoverable or visibly terminal instead of letting user-addressed channel turns finish with empty assistant text and no answer.

## Best Possible Solution

Define a single native-approval-denial contract in the Codex app-server bridge and attempt finalizer: either give the model one bounded continuation with blocked and completed sibling tool results preserved, or emit a typed user-visible terminal failure, but never record an empty user-addressed turn as success solely because a declined native tool became `lastToolError`.

## Reproduction Assessment

Yes, at source level: current main can project a declined Codex-native command as `lastToolError`, then treat that as terminal progress while suppressing incomplete-turn fallback. I did not run the reporter's Slack/email host reproduction, so the live timing evidence remains from the issue body.

## Solution Assessment

No, relying on the existing `lastToolError` payload path is not the best complete solution because it does not guarantee model continuation, sibling-result preservation, or a non-success terminal invariant when user-visible payloads are suppressed. The best fix needs a maintainer-approved runtime contract at the Codex bridge/finalization boundary.

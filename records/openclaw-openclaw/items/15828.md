## Label Justifications

- `P2`: The request affects session-memory reliability and continuity, but it is a bounded feature/product design gap rather than an emergency outage.
- `impact:session-state`: The issue is about preserving session context across idle, shutdown, command, and long-running conversation boundaries.
- `impact:data-loss`: Without automatic checkpoints, useful transcript context can be discarded or require manual recovery when sessions rotate or the gateway stops.
- `impact:security`: Automatic transcript persistence and optional LLM summaries would process private conversation data outside the current explicit command boundary.

## Summary

Keep open. Current main and v2026.6.11 still keep the bundled session-memory hook scoped to explicit `command:new` and `command:reset`; adjacent shutdown and typed `session_end` infrastructure exists, but it does not implement idle, shutdown, message-count checkpoint, trigger config, or summary-output behavior for this bundled hook.

## What This Changes

The issue requests automatic session-memory checkpoints on idle, shutdown, message-count intervals, and richer summary output instead of relying only on explicit session commands.

## Best Possible Solution

Use this as the broad session-memory automation tracker while maintainers choose one lifecycle contract for automatic reset, shutdown, periodic checkpoints, and summary output with explicit privacy, timeout, dedupe, config, docs, and tests.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 show the bundled session-memory handler and metadata accept only command `new`/`reset`, while the requested trigger and summary config is absent.

## Solution Assessment

No single automated fix is the best path yet. The request crosses lifecycle, config, storage, and privacy boundaries, and maintainers should split or approve the lifecycle/plugin boundary before implementation.

## Summary

Keep open: the linked bug is real and neither current main nor v2026.6.11 has a cache bound, but this PR still has two cache-lifecycle defects and needs stronger real behavior proof before merge.

## What This Changes

The PR adds a 64-entry cap to the usage-bar template file cache and closes the oldest cached watcher before storing a newly loaded template.

## Best Possible Solution

Land a corrected bounded-cache implementation that evicts only before inserting a new key, frees an old watcher before opening the replacement, and proves eviction/closure with focused tests plus redacted real behavior proof.

## Reproduction Assessment

Yes. Source inspection on current main shows each distinct valid template path can allocate an fs.watch watcher and is stored in fileCache with no production eviction path.

## Solution Assessment

No. Bounding the cache in src/auto-reply/usage-bar/template.ts is the right layer, but this implementation should evict before watcher allocation and only when inserting a new key.

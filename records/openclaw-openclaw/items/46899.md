## Summary

Keep open: current main and v2026.6.11 still parse cron `delivery.channel` as a string-only field, delete unrecovered object-shaped channel values, and can fall back to `last`; the open linked PR remains the active fix candidate.

## What This Changes

The issue asks for cron jobs configured for Telegram delivery to honor that channel instead of falling back to Feishu or another enabled channel.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/91162 or an equivalent parser-boundary fix that keeps runtime `delivery.channel` canonical as a string and proves multi-channel cron delivery does not fall back to the wrong channel.

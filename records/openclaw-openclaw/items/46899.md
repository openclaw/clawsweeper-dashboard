## Summary

Keep open: current main and the latest release still parse cron `delivery.channel` as a string-only field, so object-shaped channel references can be dropped before delivery planning falls back to `last`; the linked open pull request remains the active fix path.

## What This Changes

The issue requests that cron jobs honor configured Telegram delivery instead of losing the configured channel and falling back to another enabled channel such as Feishu.

## Best Possible Solution

Review, refresh, prove, and land https://github.com/openclaw/openclaw/pull/91162 or a narrow replacement that recovers `{ id }` to the canonical string before cron delivery planning, with regression and real multi-channel delivery proof.

Yes for the fix direction: recovering `{ id }` at the cron delivery parsing boundary keeps runtime `delivery.channel` canonical as a string while preserving the intended explicit channel.

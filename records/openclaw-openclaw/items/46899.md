## Summary

Keep open: current main and the latest release still parse cron `delivery.channel` as a string-only field, so object-shaped persisted channel references can still be dropped before delivery planning falls back to `last`; the linked closing PR is open and should remain the active fix path.

## What This Changes

Cron jobs configured for Telegram delivery can lose the configured channel and fall back to Feishu or `last` routing, preventing scheduled messages from reaching the intended recipient.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/91162 or an equivalent focused parser-boundary fix that keeps runtime `delivery.channel` canonical as a string and proves Telegram-configured cron jobs deliver through Telegram when another channel is enabled.

## Reproduction Assessment

Yes for the source-level path: current main drops non-string `delivery.channel` values during cron normalization, and the delivery planner can then fall back to `last`. I did not establish a live Telegram/Feishu reproduction from the reporter's exact stored job.

## Solution Assessment

Yes for the likely fix shape, but the issue is not solved yet: normalizing recoverable `{ id }` channel references at the cron delivery parser boundary is the narrow maintainable path. The issue should remain open until the linked PR or an equivalent fix merges with live or upgrade-style proof.

## Summary

Keep open: current main and v2026.6.11 still parse cron `delivery.channel` as a string-only field, so object-shaped channel refs can be dropped before delivery planning falls back to `last`; the open linked pull request remains the active fix path.

## What This Changes

Cron jobs configured for Telegram delivery can lose the explicit channel during normalization and fall back to another enabled channel such as Feishu.

## Best Possible Solution

Review, refresh, prove, and land the linked parser-boundary fix or a narrow replacement that recovers `{ id }` to the canonical string before cron delivery planning.

## Solution Assessment

Yes: the narrow maintainable fix is to recover `{ id }` at the cron delivery parsing boundary while keeping runtime `delivery.channel` canonical as a string. The linked pull request is the active implementation candidate, but this issue should stay open until that path lands or is replaced.

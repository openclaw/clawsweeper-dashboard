## Summary

Keep open: current main and v2026.6.11 still parse cron `delivery.channel` as string-only, so an object-shaped channel reference can be dropped before delivery planning falls back to `last`; the linked open pull request remains the active fix candidate.

## What This Changes

Cron jobs with an explicit Telegram `delivery.channel` should keep that configured channel instead of falling back to another enabled channel such as Feishu.

## Best Possible Solution

Land or replace the linked parser-boundary fix so `{ id }` channel references normalize to the canonical string before cron delivery planning, with regression coverage and redacted multi-channel cron proof.

## Label Justifications

- `P1`: The issue reports a broken scheduled message-delivery workflow where cron output can route to the wrong enabled channel.
- `impact:message-loss`: Scheduled cron messages can miss the configured Telegram destination by being misrouted through another channel.

## Summary

Keep open: current main and v2026.6.11 still parse cron `delivery.channel` as a string-only field, so object-shaped persisted channel references can still be dropped before routing falls back to `last`; the open linked PR remains the active fix path.

## What This Changes

Cron jobs configured with `delivery.channel = "telegram"` should deliver through Telegram instead of falling back to a Feishu/`last` route with a stale recipient id.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/91162 or an equivalent parser-boundary fix that keeps runtime `delivery.channel` canonical as a string and proves a Telegram-configured cron job delivers through Telegram when another channel is enabled.

Yes, at source level: current main drops non-string `delivery.channel` values during cron normalization, and delivery planning can then fall back to `last`. I did not establish a live Telegram/Feishu reproduction from the reporter's exact stored job.

## Solution Assessment

Yes for the likely fix shape, but the issue is not solved yet: normalizing recoverable `{ id }` channel references at the cron delivery parser boundary is the narrow maintainable path. The issue should remain open until the linked PR or an equivalent fix merges with real or upgrade-style proof.

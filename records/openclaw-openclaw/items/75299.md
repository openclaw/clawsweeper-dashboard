## Summary

Keep this PR open for maintainer scheduler-policy review. The implementation and supplied production-module transcript support the foreground-preserving ordering it describes, but the one-tier cap means normal work can still wait indefinitely while foreground work continues; that conflicts with the linked issue’s stated starvation guarantee rather than resolving it completely.

## What This Changes

The PR changes command-lane dequeue selection so queued background work gains one priority tier after 30 seconds, while aged normal work remains below fresh foreground work.

## System Context

Command lanes serialize agent and maintenance work before it reaches the runtime. Callers label queue entries by priority, and the queue chooses the next waiting entry whenever lane capacity opens, affecting which session or background task runs next.

## Architecture Diagram

## Best Possible Solution

Choose and document the scheduler contract first, then implement it with tests that cover both continuous foreground traffic and the intended maximum wait for normal/background work without regressing interactive responsiveness.

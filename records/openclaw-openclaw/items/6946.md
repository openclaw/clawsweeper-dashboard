## Summary

Keep open: current main still lacks the requested standalone Telegram processing-message lifecycle, while the related presence work uses typing and reactions rather than sending, tracking, deleting, or editing a placeholder message. The remaining question is whether this additional feedback mode and configuration contract should exist.

## What This Changes

Add an opt-in Telegram placeholder message during processing, then delete it after successful delivery or update it when processing fails.

## Best Possible Solution

Choose one Telegram-owned, opt-in placeholder lifecycle with clear eligibility, success cleanup, failure behavior, schema/help/docs, and visible Telegram proof, or explicitly retain the existing feedback modes without adding parallel configuration.

## Summary

Keep open: current main still has only startup config/state preflight and warning/readiness checks, while version-stamped doctor/update repair remains explicit work outside direct container-image replacement. The new live Docker comment strengthens the source-level finding, and the protected maintainer/product-decision labels mean this should stay with maintainers rather than close or queue an automated fix.

## What This Changes

Detect direct container image version changes and run or block on pending OpenClaw upgrade migrations before gateway readiness.

## Best Possible Solution

Define a maintainer-owned container startup upgrade contract that records the last successfully migrated state/config version, then either runs the safe locked migration set before readiness or fails readiness with actionable doctor/update guidance and Docker image-swap coverage.

## Reproduction Assessment

Yes, with high confidence from source inspection and the new live Docker evidence, though I did not rerun current-main containers here. Current main still lacks a startup version-transition gate while the reported GHCR image swap shows readiness succeeding with `meta.lastTouchedVersion` unchanged.

## Solution Assessment

Unclear. The issue is valid, but maintainers need to choose the best contract: automatic locked startup migrations, fail-closed readiness with explicit operator repair, or a staged hybrid that preserves existing upgrade expectations.

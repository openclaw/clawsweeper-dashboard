## Label Justifications

- `P1`: The reported Docker upgrade path can leave a configured channel omitted while the gateway reports healthy, breaking real inbound/outbound channel workflows after upgrade.
- `impact:message-loss`: The central failure mode is that configured channel plugins can be skipped after container upgrade, causing inbound messages and replies to be missed.
- `impact:other`: The issue also concerns upgrade readiness and migration sequencing, which are maintainer-visible operational impacts outside the narrower message-loss taxonomy.
- `maturity:stable`: The issue affects M4 stable areas `gateway-runtime` and `cli-install-update-onboard-doctor` from the maturity shortlist.

## Summary

Keep open: current main has limited startup state preflight plus warning/update/doctor repair paths, but it does not detect direct container-image version jumps and run or block readiness on pending upgrade migrations before the gateway reports healthy.

## What This Changes

The issue requests gateway startup handling for container image upgrades so pending OpenClaw upgrade or doctor migrations run, or readiness is blocked, before the gateway starts serving.

## Best Possible Solution

Define a maintainer-owned startup upgrade contract that records the last successfully migrated state/config version and either runs pending idempotent migrations under a lock before readiness or fails readiness with actionable doctor guidance, with Docker image replacement coverage.

## Reproduction Assessment

Yes at source level, but not with a fresh live Docker run here: current main startup performs limited preflight and warning-only diagnostics while full configured-plugin/package repair remains explicit doctor/update work.

## Solution Assessment

Unclear: the problem is valid, but maintainers need to choose whether startup may run upgrade/package repair automatically or should fail readiness and require an explicit operator-run migration.

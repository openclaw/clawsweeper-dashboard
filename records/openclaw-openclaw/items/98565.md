- `P1`: The reported Docker upgrade path can leave configured channels or migrations skipped while the gateway reports healthy, breaking real post-upgrade channel workflows.

## Summary

Keep open: live issue evidence plus current source show the container default starts the gateway directly and gateway startup still runs limited state preflight or warning-only diagnostics rather than comparing `meta.lastTouchedVersion` and running or blocking on the full doctor/update migration set before readiness. The protected `maintainer` and product-decision labels make this human-owned rather than an automatic close or fix-PR candidate.

## What This Changes

The issue asks gateway/container startup to detect image-version changes, run or block on pending upgrade migrations before readiness, and cover the direct Docker image-swap path.

## Best Possible Solution

Define a maintainer-approved startup upgrade contract that records the last successfully migrated state/config version, runs idempotent startup-safe migrations under a lock before readiness, and fails readiness with actionable doctor guidance for unsafe package/plugin repairs.

## Reproduction Assessment

Yes, at source level and with a posted live Docker repro. The default image starts the gateway directly, current startup runs limited state migration preflight, and full doctor/update repair remains outside readiness.

## Solution Assessment

Unclear until maintainers choose the startup policy. The requested run-or-fail-readiness direction is the right boundary, but the best fix must separate startup-safe migrations from package-manager or operator-controlled doctor repairs.

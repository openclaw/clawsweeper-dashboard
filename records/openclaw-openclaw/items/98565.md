## Label Justifications

- `P1`: Direct container image upgrades can leave the gateway healthy while configured channels or migration-dependent state are not converged, breaking real post-upgrade workflows.
- `impact:message-loss`: The reported failure mode includes configured channel plugins being skipped after upgrade, which can drop inbound messages and replies while the gateway reports ready.
- `impact:session-state`: The issue is about mounted state/config volumes remaining on an older migration version while a newer gateway runtime starts against them.
- `impact:other`: The remaining impact also covers upgrade lifecycle and readiness semantics that do not fit only message loss or session-state labels.
- `maturity:stable`: The affected gateway runtime and CLI/doctor upgrade surfaces are both scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main still treats direct gateway startup as a limited state-migration and warning path, while full doctor/update repair remains explicit; the issue also has protected maintainer and product-decision labels, so the startup run-vs-fail contract needs human maintainer policy.

## What This Changes

Detect container image version changes on gateway startup and run or block on pending upgrade migrations before reporting the gateway ready.

## Best Possible Solution

Define a maintainer-owned container startup upgrade contract that compares mounted state/config migration version with the running binary, then either runs idempotent locked migrations before readiness or fails readiness with actionable doctor guidance and Docker image-swap coverage.

## Reproduction Assessment

Yes at source/live-evidence level, though I did not personally rerun a current-main Docker swap. The July 3 live repro shows the 2026.6.10 to 2026.6.11 image replacement reaching ready with stale `lastTouchedVersion`, and current main still keeps full repair work on explicit doctor/update paths.

## Solution Assessment

Unclear until maintainers choose the startup policy. The issue's requested direction is right, but the best implementation depends on whether gateway startup may run migrations/repairs automatically or should fail readiness with doctor guidance.

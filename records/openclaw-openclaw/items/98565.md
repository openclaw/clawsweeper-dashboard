## Summary

Keep open: current main still treats direct container image replacement as a gateway startup path, not as an update/finalize path, so the reported 2026.6.10 to 2026.6.11 migration gap remains a real upgrade/readiness problem despite adjacent Mattermost and config-health fixes.

## What This Changes

The issue requests that container-image upgrades run or gate required OpenClaw upgrade migrations before the gateway reports ready.

## Best Possible Solution

Define a maintainer-owned container upgrade contract that records the last successfully migrated OpenClaw version and either runs only safe idempotent pending migrations under a startup lock before readiness or fails readiness with an actionable in-product repair path.

## Reproduction Assessment

Yes: the issue discussion includes a live official-image 2026.6.10 to 2026.6.11 container swap where the default gateway command became healthy while version metadata and doctor output still showed pending migration work.

## Solution Assessment

Unclear until maintainers decide the startup policy: source evidence supports the bug, but the best fix must choose which migrations are safe before readiness versus which should hard-fail with a repair path.

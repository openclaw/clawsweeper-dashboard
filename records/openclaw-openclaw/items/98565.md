## Label Justifications

- `P1`: The issue affects real container upgrades where the gateway can report healthy while channel/plugin migrations remain pending and messages may be missed.
- `impact:message-loss`: Skipped upgrade migration can leave channel plugins unloaded after a healthy gateway start, so inbound channel messages may not be consumed.
- `impact:ux-friction`: Operators currently need logs, config metadata, or doctor output to discover that readiness did not mean upgrade repair completed.
- `impact:other`: The affected core contract is broader than one channel: version-transition detection, startup migration ownership, and readiness semantics are all involved.
- `maturity:stable`: Gateway runtime/lifecycle and CLI doctor/update surfaces match M4 Stable scorecard entries, even though the Docker hosting surface itself is M3 Beta.

## Summary

Keep open: current main still lets direct container image replacement enter gateway startup without a version-transition upgrade/finalize gate, so the gateway can become healthy while doctor/update migration work remains pending; the merged Mattermost and macOS fixes only cover narrower symptoms.

## What This Changes

Request gateway startup to detect container image version changes and run or block pending OpenClaw upgrade migrations before readiness.

## Best Possible Solution

Define a maintainer-owned startup upgrade contract: record the last successfully migrated OpenClaw version, run only safe idempotent migrations under a startup lock before readiness, and fail readiness with an actionable repair path for unsafe work.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should direct gateway startup for container image replacement run safe pending upgrade migrations before readiness, or fail readiness until an explicit repair/update command completes them?

Rationale: The decision changes startup-time mutation and readiness semantics for Docker/Kubernetes-style upgrades, so automation should not choose which doctor/update repairs are safe to run before the gateway reports ready.

Likely owner: openperf

Owner reason: openperf has the strongest recent history on the gateway startup migration guard surface where this policy would be enforced.

Owner confidence: high

Options:

- **Bounded startup migration gate (recommended):** Run a maintainer-approved safe migration set under startup coordination before readiness, and fail readiness with actionable guidance for repairs that cannot safely run automatically.
- **Explicit repair-only contract:** Keep gateway startup non-mutating and change readiness/status/docs so direct container replacement clearly reports pending upgrade work instead of appearing healthy.
- **Keep current startup behavior:** Leave image replacement as an operator-managed flow, accepting that health/readiness may not imply upgrade migration convergence.

## Reproduction Assessment

Yes: the issue discussion includes a live official-image 2026.6.10 to 2026.6.11 container swap, and current source still shows direct image startup only runs a limited preflight before gateway readiness.

## Solution Assessment

Unclear until maintainers choose the startup policy; source evidence supports the bug, but the best fix must separate safe pre-readiness migrations from repairs that should fail readiness with operator action.

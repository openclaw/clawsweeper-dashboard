## Repair Work Prompt

Fix the cron scheduler bug reported at https://github.com/openclaw/openclaw/issues/102238: a manual `cron.run(id, "force")` can leave a job active while an operator disables and re-enables it, clearing `runningAtMs`; the next `onTimer` then selects the same job again because `isRunnableJob` does not consult the active in-process registry. Implement the smallest scheduler-owned fix, likely in `src/cron/service/timer.ts` by treating `isCronJobActive(job.id)` as non-runnable, or an equally narrow `ops.ts` reservation-preservation fix if source review proves that is safer. Add a regression that fails on current main and drives the real cron service path: start an `at` isolated agent job with `cron.run(..., "force")`, keep it in flight, `cron.update(id, { enabled: false })`, `cron.update(id, { enabled: true })`, run one timer tick, and assert only one dispatch/max in-flight run. Preserve existing add/remove/update due-slot invariants from the related merged cron fixes, do not add config or product policy, and do not edit `CHANGELOG.md`; put release-note context in the PR body instead.

## Summary

The patch is focused, tested, and technically coherent, but it changes the accepted duration grammar only in the outer watchdog calculation. A Codex-area maintainer should confirm whether computer durations are canonically JSON numbers, whether decimal strings remain supported, and whether execution and deadline calculation must share one normalization boundary before merge.

## What This Changes

The PR replaces permissive `Number(...)` coercion for Codex computer wait deadlines with type-aware parsing and adds dedicated boundary tests for malformed strings, finite numeric fractions, and non-consuming actions.

## Best Possible Solution

Define one canonical computer-duration grammar at the computer-tool owner boundary, normalize or reject the argument there, and reuse that normalized value for both execution and outer-deadline calculation, with focused tests for numeric fractions and the chosen string-compatibility policy.

- **Land watchdog-only narrowing:** Accept that execution and watchdog parsing may have different grammars and document the resulting compatibility and premature-timeout risk.

## Reproduction Assessment

Yes, at source level: current main passes `args.duration` through JavaScript `Number(...)`, so inputs such as `"0x10"` and `"1e2"` deterministically alter the watchdog duration. The supplied terminal proof also demonstrates the old and proposed calculations, although this review did not independently run a live Codex app-server round trip.

## Solution Assessment

Not yet. The parser change fixes the local coercion problem, but the most maintainable solution is to define and enforce the duration grammar once at the computer-tool boundary so execution and watchdog accounting cannot diverge.

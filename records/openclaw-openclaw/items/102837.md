## Label Justifications

- `P0`: The issue reports an unauthenticated WebSocket path that can attach to an active voice-call media stream and inject call audio/transcripts, which is a security-boundary bypass.
- `impact:security`: The affected surface is authentication/session binding for externally reachable voice-call WebSocket media streams.

## Summary

Keep open: current main still has a source-visible non-Twilio media-stream authentication gap, because the `/voice/stream` start-frame validator only checks a per-call token for Twilio and otherwise accepts any active provider call id.

## What This Changes

Require authenticated, session-bound start frames for the voice-call media-stream WebSocket when Plivo or Telnyx calls are active.

## Best Possible Solution

Security-owned repair should make media streams fail closed unless every accepted start frame is bound to a provider-issued per-call credential; keep Twilio's current token flow and add equivalent Plivo/Telnyx validation or avoid exposing `/voice/stream` for providers that cannot authenticate it.

## Reproduction Assessment

Yes, at source level: current main routes `/voice/stream` upgrades into `MediaStreamHandler`, and `shouldAcceptStream` accepts non-Twilio active provider call ids without checking a token. I did not run a live carrier test in this read-only review.

## Solution Assessment

Unclear as an implementation detail, but the right end state is clear: fail closed for every provider unless a per-call stream credential validates. A config-only opt-in token like the closed unmerged PR is not the best default because it leaves the security boundary optional.

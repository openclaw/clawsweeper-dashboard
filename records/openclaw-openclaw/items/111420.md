## Label Justifications

- `P1`: Cron job completion can currently lose an on-exit payload and terminal history during an active edit or re-arm race.
- `merge-risk: 🚨 message-delivery`: The identified race makes `fireOnExit` ignore a `ran: false` result after the external command has already completed, suppressing its payload.
- `merge-risk: 🚨 session-state`: The patch changes durable active-run ownership and recovery state used to decide whether a completion may mutate the current cron job.

## Summary

Keep this PR open: the supplied review activity identifies a concrete remaining on-exit race where a valid predecessor completion can be dropped after the job is re-armed or edited. The final merge commit records conflicts only in run-admission and timer regression files, so the reviewer-identified `ops.ts` admission path was not changed afterward; the patch needs that completion path repaired before merge.

## What This Changes

This PR adds durable cron run-generation and ownership identities so an older active run cannot consume scheduling or trigger state belonging to a rescheduled, edited, or replacement job.

## Best Possible Solution

Finalize the exited predecessor against its captured execution snapshot in preserve mode while conditionally protecting the newer job's schedule and trigger state, then add a regression that edits or re-arms the job after completion persistence but before on-exit admission.

Yes. The supplied reviewer finding gives a concrete path: let an on-exit process finish, re-arm or edit its job after `persistCompletion` disables it but before `runOnExit` admission, then observe that the predecessor completion is rejected and dropped.

## Solution Assessment

No. The ownership guards correctly protect a replacement schedule, but rejecting the predecessor completion outright is not the narrowest solution because it also discards an already-completed command's history and payload.

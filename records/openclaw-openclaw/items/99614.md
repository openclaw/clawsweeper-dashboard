## Summary

Keep open: this PR is a useful partial mitigation, but it is not merge-ready because the new readiness guard still diverges from `run-node` rebuild decisions and can either stop a healthy gateway before a rebuild or defer a restart without a deterministic follow-up trigger.

## What This Changes

The PR adds `isBuildReadyForRestart()` to `scripts/watch-node.mjs`, checks it before watcher restarts and SIGTERM exit respawns, exposes the helper in declarations, and adds watch-node tests.

## Best Possible Solution

Prepare or validate the replacement build for the current checkout before signaling the healthy gateway child; if a smaller mitigation lands, it should share `run-node` readiness and schedule a deterministic pending restart.

## Reproduction Assessment

Yes. The canonical issue includes redacted production logs, and source inspection shows current watch-node can signal the child before `run-node` finishes a replacement build; I did not run the destructive systemd race in this read-only review.

## Solution Assessment

No. This is a plausible partial mitigation, but it is not the best fix unless it shares `run-node` readiness and deterministically restarts after deferral; a transactional prepare-then-signal boundary is safer.

- **[P1] Reject every run-node rebuild state before restart:** `scripts/watch-node.mjs:113-115`
  - body: `isBuildReadyForRestart()` returns true unless the build stamp has a mismatched `head`, but current `run-node` rebuilds for other states such as a missing stamp head, newer config, dirty watched tree, and missing bundled output. Those states can still pass this guard, stop the healthy gateway, and only then rebuild or clean `dist`.
  - confidence: 0.9
- **[P2] Trigger the deferred restart when output becomes ready:** `scripts/watch-node.mjs:560-566`
  - body: When this guard returns false, `requestRestart()` only logs and returns. Because `dist` is ignored by the watcher, the rebuild completing under `dist/` will not necessarily produce another watched event, so the old child can keep serving stale code indefinitely after a checkout update.
  - confidence: 0.86

## Summary

Keep open: this is a plausible partial mitigation, but the current head still lets the watcher treat several `run-node` rebuild/runtime-sync states as safe and drops a deferred restart until another watched source event arrives. The PR adds a `watch-node` build-readiness helper, checks it before watcher restarts and exit-handler restarts, updates the declaration file, and adds regression tests.

## Best Possible Solution

Prepare or validate the replacement build/runtime tree for the current checkout before signaling the healthy gateway child; if maintainers choose a smaller mitigation, share `run-node` readiness and schedule a deterministic pending restart.

Yes. The canonical issue provides concrete production logs and steps, and source inspection shows current main can stop the healthy child before `run-node` finishes preparing a replacement build; I did not run the destructive systemd/git-update race in this read-only review.

## Solution Assessment

No. This is a plausible partial mitigation, but it is not the best fix until it shares `run-node` readiness and deterministically restarts after deferral; a transactional prepare-then-signal boundary is safer.

## Summary

Keep open. Current main and the latest release still reject `mode="session"` without `thread: true` in both native subagent and ACP `sessions_spawn` paths, and the requested non-thread persistent-session behavior needs a maintainer-owned routing, lifecycle, cleanup, and ownership contract before implementation.

## What This Changes

Request to allow persistent native subagent and ACP `sessions_spawn` sessions without requiring channel thread binding.

## Best Possible Solution

Define a first-class non-thread persistent-session contract, then update native spawn, ACP spawn, tool schema exposure, follow-up routing, lifecycle cleanup, docs, and focused tests around that contract.

Question: Should OpenClaw make non-thread persistent `sessions_spawn` sessions a first-class native and ACP contract, or keep `mode="session"` reserved for bound thread/conversation sessions?

Rationale: The source repro is clear, but choosing the behavior changes session ownership, message delivery, lifecycle cleanup, and ACP security boundaries rather than fixing a narrow implementation bug.

Likely owner: steipete

Owner confidence: high

Options:

- **Define the new contract first (recommended):** Specify ownership, routing, cleanup, and safety semantics for non-thread persistent sessions, then implement native and ACP support with docs and tests.
- **Keep session mode thread-bound:** Leave `mode="session"` tied to thread/conversation binding and improve docs/errors around `mode="run"`, `sessions_send`, and `/acp spawn --bind here` alternatives.
- **Split ACP affinity separately:** Handle deterministic non-thread ACP reuse through the narrower affinity-key work while keeping native subagent session mode unchanged for now.

## Reproduction Assessment

Yes. Source inspection on current main and `v2026.6.11` shows both native and ACP `sessions_spawn` reject `mode="session"` unless `thread: true` is set, with tests and docs preserving that contract.

## Solution Assessment

Unclear. Decoupling persistence from thread binding is plausible, but direct guard removal is not the best fix until maintainers define non-thread ownership, delivery, targeting, cleanup, and ACP safety semantics.

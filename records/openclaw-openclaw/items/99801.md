## Summary

Keep open: current evidence is too thin to close, and current source/docs show sandbox path denials are an intentional security boundary while failed tools become model-visible error results rather than an automatic alternate-path retry.

## What This Changes

The issue requests that OpenClaw continue or recover when a sandbox/path-restricted tool call fails instead of freezing the task and requiring a manual restart.

## Best Possible Solution

First reproduce the freeze with logs, then add a narrow recovery or diagnostic path that keeps sandbox policy authoritative and reuses the existing path-policy and retry work instead of adding a blanket bypass.

## Reproduction Assessment

Unclear for the full freeze: the issue gives steps but no logs or current-main run. Source inspection does show the missing automatic alternate-path retry and confirms sandbox-denied tool failures are handled as error results/warnings, not as a self-correcting recovery path.

## Solution Assessment

Unclear. The best solution is not a generic retry after sandbox denial; maintainers should first decide the safe recovery contract and then implement diagnostics or bounded fallback without widening filesystem authority.

## Summary

Keep open: this is a focused fix for a real MCP mixed-transport bug that still exists on current main, but the PR is not merge-ready because it only rejects the shape at runtime, leaves config validation accepting the now-skipped config, and has no after-fix real behavior proof.

## What This Changes

The PR adds a guard in `resolveMcpTransportConfig` that returns `null` with a warning when an MCP server has both non-empty `command` and `url`, plus tests for mixed configs and log sanitization.

## Best Possible Solution

Land a narrow fix that rejects mixed `command` plus `url` consistently across resolver diagnostics and config validation, with focused tests and redacted real MCP runtime proof, then close the linked canonical issue.

## Reproduction Assessment

Yes, source-level: current main resolves a non-empty `command` before considering `url` or streamable-http, so the reported mixed config takes the stdio path. I did not run the external OpenSpace setup.

## Solution Assessment

No, not as-is: the resolver is the right layer to stop silent stdio precedence, but the best fix should also align config validation and include real behavior proof for the upgrade-visible rejection path.

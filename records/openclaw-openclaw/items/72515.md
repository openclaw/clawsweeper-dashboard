Keep open: this is a focused candidate fix for the linked MCP mixed-transport bug, but it is not merge-ready because the new runtime-only rejection leaves config validation accepting the same skipped shape and the external PR still lacks after-fix real behavior proof.

## What This Changes

The PR adds a guard and tests so `resolveMcpTransportConfig` rejects MCP server entries that set both a non-empty `command` and `url` instead of resolving stdio first.

## Best Possible Solution

Land a resolver-level mixed `command`+`url` rejection only after config validation/doctor coverage and real runtime proof agree on the user-visible failure mode.

## Reproduction Assessment

Yes, source-level: current main resolves a non-empty `command` before considering `url` or `transport`, so the reported mixed streamable-http config takes the stdio path and can hit the 30-second connect timeout. I did not run the external OpenSpace setup.

## Solution Assessment

No, not as currently proposed: the resolver is the right layer to stop silent stdio precedence, but the best fix should align config validation/doctor behavior and include real after-fix proof for the upgrade-visible rejection path.

## Summary

Keep open. Current main and v2026.6.11 still lack a restore/re-index utility and still lack a `chat.history` or `sessions_history` family/archive selector; the closest implementation path is the open, maintainer-review `includeFamily` PR at https://github.com/openclaw/openclaw/pull/90239, while the original mutation-style restore script still needs product and security direction.

## What This Changes

The issue requests a recovery path for session transcript archives created by reset behavior, originally as a restore/re-index script and later as broader archived-history access.

## Best Possible Solution

Land a maintainer-approved, bounded, read-only family-history path first, then decide whether already-affected users also need a separate doctor-style restore/re-index command instead of an ad hoc archive rename script.

Rationale: Current main only has active-missing fallback, while the remaining choices change model-facing history access, archived transcript exposure, and possibly persisted session metadata, so maintainer intent is needed before implementing or closing the broader recovery request.

Options:

- **Land Bounded Family History (recommended):** Use the open `includeFamily` PR as the canonical first fix and leave mutation-style restore for a later explicit recovery decision.
- **Add Doctor Recovery:** Sponsor a separate `openclaw doctor --fix` or recovery command that restores/re-indexes archives with metadata, backups, retention checks, and tests.
- **Reject Restore Mutation:** Keep archives read-only, document the supported retrieval/export path, and close restore/re-index script requests once read-only access has shipped.

Yes, at source level: current main has no restore/re-index command and no `chat.history` or `sessions_history` family/archive selector; the existing fallback only reads a reset archive when the active transcript is absent. I did not run a live multi-day reset scenario in this read-only review.

## Solution Assessment

Unclear as originally proposed. A script can help already affected users, but the safer maintainable path is a maintainer-approved read-only family-history API or doctor recovery command with source metadata, retention, and security semantics.

## Security Review

Status: needs_attention

Summary: No patch is under review, but archive recovery is security-sensitive because it can expose or mutate prior transcript content.

Concerns:

- **[medium] Define archived transcript exposure policy:**
  - body: Archived reset transcripts can contain sensitive prior context that current active history does not expose; model-facing or UI recovery should require bounded reads, lineage/header ownership checks, and clear operator-facing semantics.
  - confidence: 0.86
- **[medium] Avoid unsafe archive-to-active mutation:**
  - body: A restore script that renames `.reset.*` files back to active transcripts could corrupt session identity, retention expectations, or audit metadata unless it is owned by a deliberate doctor/recovery path.

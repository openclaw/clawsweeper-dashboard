## Label Justifications

- `P0`: Affected users can lose supported access to session history after reset archiving and currently need technical recovery before archives may be pruned.
- `impact:data-loss`: Archived transcript data disappears from supported product surfaces and may later be pruned, which users experience as lost history.
- `impact:session-state`: The issue centers on session continuity, transcript association, and archive access across reset boundaries.
- `impact:ux-release-blocker`: Recovering disappeared session history currently requires filesystem/manual re-index steps rather than an in-product restore or Doctor flow.

## Summary

Keep open: current main and v2026.6.11 still lack the requested restore/re-index path and only provide latest-reset-archive fallback when an active transcript is missing; open PRs cover candidate read-only family retrieval but remain unmerged and leave the product/security boundary unresolved.

## What This Changes

The issue requests a restore/re-index utility for `.jsonl.reset.<timestamp>` transcript archives and later broadens to supported archive/history recovery across reset families.

## Best Possible Solution

Land a bounded read-only reset-family history path first, then add Doctor-owned restore/re-index only if maintainers accept the mutation, lineage, retention, and audit semantics.

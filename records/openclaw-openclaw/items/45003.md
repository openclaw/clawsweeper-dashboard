## Summary

Keep open. Current main has fixed the over-aggressive daily-reset freshness check and added missing-active reset-archive fallback, but it still does not provide the requested restore/re-index flow and the broader read-only family-history API remains open in follow-up work.

## What This Changes

Request a restore/re-index utility for `.jsonl.reset.*` session archives so users can recover session history that disappeared from normal session history after daily reset.

## Best Possible Solution

Land a maintainer-approved bounded read-only family-history path first, then add a Doctor-owned restore/re-index command only if maintainers accept archive mutation semantics.

Options:

- **Ship read-only family history first (recommended):** Use the bounded `includeFamily`/history-retrieval path as the initial recovery surface and defer mutation or re-indexing until its data model is explicit.
- **Add Doctor restore/re-index:** Add a guided `openclaw doctor --fix` style recovery that backs up data, records archive provenance, and makes transcript mutation explicit to users.
- **Reject restore mutation:** Keep reset archives read-only through browsing/export APIs and avoid making old `.reset.*` files active sessions again.

## Reproduction Assessment

Yes from source inspection: main can read a reset archive only as a missing-active fallback, while there is no restore/re-index command and no current `includeFamily`/archived-history selector in the shipped protocol or agent tool.

## Solution Assessment

No single code fix is clearly best yet; a read-only family-history API is the safest first step, while restore/re-index needs maintainer approval for archive mutation and privacy semantics.

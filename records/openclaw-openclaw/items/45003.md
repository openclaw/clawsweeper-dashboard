- `P0`: Affected users can lose supported access to session history after reset archiving and have no in-product recovery path before archives may be pruned.
- `impact:ux-release-blocker`: Recovering disappeared session history currently requires filesystem/manual re-index steps rather than an in-product restore or Doctor flow.

## Summary

Keep open. Current main and v2026.6.11 still lack the requested restore/re-index recovery path, and the active read-only family-history work remains in open pull requests rather than merged on main.

## What This Changes

The issue requests a recovery path for archived `.reset.*` session transcripts so users can restore or re-index session history after daily reset archiving.

## Best Possible Solution

Land a maintainer-approved, bounded, read-only reset-family history path first, then add a Doctor-owned restore/re-index command only if maintainers accept the mutation and recovery semantics.

Unclear as originally proposed: a standalone rename script helps affected users, but the safer core solution is read-only family history or Doctor-owned recovery with lineage, retention, and security semantics.

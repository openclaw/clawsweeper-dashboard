## Label Justifications

- `P2`: The issue affects session-history recovery and perceived data loss, but the core runtime remains usable and active implementation candidates are already open.
- `impact:data-loss`: Reset archives can disappear from supported history surfaces and later be pruned, making user transcript data effectively unrecoverable through the product.
- `impact:session-state`: The central problem is session continuity across reset-created transcript fragments and `sessions.json` re-indexing.

## Summary

Keep open. Current main and v2026.6.11 still lack the requested restore/re-index utility and still lack a landed family/archive history selector; the active implementation path is the open, mergeable `includeFamily` PR at https://github.com/openclaw/openclaw/pull/90239, while the older `includeArchived` PR is conflicting and still needs proof.

## What This Changes

Request a core utility or recovery path to restore and re-index `.jsonl.reset.*` session archives after daily reset makes prior history disappear from normal session history surfaces.

## Best Possible Solution

Land one maintainer-approved, bounded, header-checked archive/family history contract, then add a narrow doctor or CLI recovery path only if mutable restore remains necessary.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should archive recovery for reset transcripts be solved as the open read-only `includeFamily` history API, as a mutable restore/re-index utility, or as both with separate safety gates?

Rationale: The code gap is clear, but the permanent contract changes model-facing history visibility, sensitive transcript access, and whether OpenClaw mutates archived session state.

Likely owner: vincentkoc

Owner reason: Recent commit and release history tie this person to the current reset-archive fallback and gateway session-history surface.

Owner confidence: high

Options:

- **Prefer read-only family history (recommended):** Review and land the bounded `includeFamily` path first, keeping restore/re-index mutation out of core unless users still need a doctor-style recovery tool.
- **Add a doctor restore tool:** Design a guarded `openclaw doctor --fix` or CLI repair that restores/re-indexes archives with backups, provenance, and dry-run output.
- **Keep manual recovery only:** Decline core restore tooling and leave archive access to docs or external tools while keeping existing latest-archive fallback behavior.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 expose no restore/re-index utility or archive/family selector, and current `chat.history` only falls back to one reset archive when the active transcript is missing. I did not run a live upgrade/reset scenario in this read-only review.

## Solution Assessment

No for the raw script as the primary fix: it is a useful stopgap, but the safer product path is an explicit read-only archive/family history API plus a guarded doctor/CLI recovery tool only if mutation is still needed.

## Label Justifications

- `P0`: Affected users can lose supported access to session history after reset archiving and currently need technical recovery before archives may be pruned.
- `impact:data-loss`: Archived transcript data disappears from supported product surfaces and may later be pruned, which users experience as lost history.
- `impact:session-state`: The issue centers on session continuity, transcript association, and archive access across reset boundaries.
- `impact:ux-release-blocker`: Recovering disappeared session history currently requires filesystem/manual re-index steps rather than an in-product restore or Doctor flow.

## Summary

Keep open. Current main and v2026.6.11 still provide only latest-reset-archive fallback when the active transcript is missing; they do not provide the requested restore/re-index flow, and the broader read-only reset-family history path is still in open PRs.

## What This Changes

The issue requests a script or product recovery path that restores `.jsonl.reset.*` session transcript archives back into supported session history and rebuilds the session index.

## Best Possible Solution

Land a maintainer-approved, bounded read-only reset-family history path first, then add a Doctor-owned restore/re-index command only if maintainers accept the mutation, identity, retention, and security semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should reset archive recovery be solved through read-only family history only, a Doctor-owned restore/re-index command, or both?

Rationale: The choice changes whether OpenClaw mutates archived transcripts and session indexes, how it exposes private prior context, and how retained/pruned reset archives are represented to users, so automation should not pick the permanent recovery boundary.

Likely owner: Pavan Kumar Gondhi

Owner reason: Current-main blame routes the central session-history and archive-discovery lines through this recent area commit, though product direction likely needs broader owner review.

Owner confidence: medium

Options:

- **Land read-only family history first (recommended):** Use an explicit, bounded family-history selector as the supported retrieval path before adding any archive-to-active mutation.
- **Add Doctor-owned restore/re-index:** Create a deliberate recovery command for affected users that preserves source metadata and explains retention and security consequences.
- **Reject mutation-style restore:** Keep reset archives read-only and track only discovery, export, and history-reading surfaces.

## Reproduction Assessment

Yes, at source level: current main has no restore/re-index command and no explicit archive-family selector, while the fallback only reads one latest archive when the active transcript is absent. I did not run a live multi-day reset scenario in this read-only review.

## Solution Assessment

Unclear as originally proposed: a standalone rename script helps affected users, but the safer core solution is read-only family history or Doctor-owned recovery with lineage, retention, and security semantics.

## Label Justifications

- `P0`: Affected users can see session history disappear after upgrade/reset and recovery currently requires filesystem/manual-script knowledge before archives are pruned.
- `impact:data-loss`: Reset archives are retained only for a configured window, so missing recovery can turn perceived loss into permanent transcript loss after cleanup.
- `impact:session-state`: The issue is about session history, context continuity, and agent recall becoming split across reset transcript files and the live session index.
- `impact:ux-release-blocker`: There is no in-product recovery path for a community user whose sidebar/history appears empty after reset; the workaround is manual file inspection or a community script.

## Summary

Keep open. Current main and v2026.6.11 have a narrow active-missing reset-archive fallback, but they still do not provide the requested restore/re-index recovery flow or a maintainer-approved family/archive history selector.

## What This Changes

Request a recovery utility or in-product path to restore and re-index `.jsonl.reset.*` session archives so reset history becomes visible again.

## Best Possible Solution

Approve one bounded in-product recovery contract: either a Doctor/restore flow that backs up and safely re-indexes archives, or an opt-in read-only family-history API with ownership/header checks, source metadata, retention warnings, and UI/tool discoverability.

## Reproduction Assessment

Yes, at source level. Current main archives reset transcripts and can fall back only when the active transcript is missing, while `chat.history` and `sessions_history` expose no restore, re-index, or family/archive selector.

## Solution Assessment

No, not as only a standalone script. The script is a useful stopgap, but the best durable fix is a maintainer-approved in-product recovery/read-only history path with bounded archive ownership checks and clear user-facing recovery affordances.

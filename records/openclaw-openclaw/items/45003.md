## Summary

Keep open. Current main and the latest release still do not provide the requested `.jsonl.reset.*` restore/re-index utility or an explicit reset-family history selector; the closest current implementation path is still open and conflicting, while a merged sibling only covers session-memory/session-log discovery.

## What This Changes

Request to provide a restore/re-index path for session transcript files archived as `.reset.<timestamp>` after daily or manual session reset behavior.

## Best Possible Solution

Land or narrow one maintainer-approved, bounded, header-checked reset-family history/recovery contract, then decide whether a separate doctor-style restore/re-index command is still needed for already affected users.

## Reproduction Assessment

Yes, at source level: current main has reset-archive fallback only when the active transcript is missing, and neither `chat.history` nor `sessions_history` can request reset-family or archived-history traversal. I did not run a live multi-day reset scenario in this read-only review.

## Solution Assessment

Unclear as originally proposed. A mutation-style restore script may help already affected users, but the safer maintainable path is a bounded read-only family-history API or an explicit doctor recovery command with metadata and retention semantics.

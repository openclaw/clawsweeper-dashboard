## Summary

Keep open: current main and the latest release still route normal `openai/*` agent turns through the Codex app-server path, and the source/dependency path still has a plausible `type: "custom"` tool emission route for the reporter's OpenAI 400. This is not the same proven root cause as the older Anthropic-bridge custom-tool issue.

## What This Changes

The issue reports that OpenAI model turns fail with an OpenAI 400 error because a `custom` tool value reaches the OpenAI tools parameter.

## Best Possible Solution

Keep `openai/*` agent turns supported, but gate or convert the Codex freeform/native code-mode tool path so OpenAI models that reject `type: "custom"` use a valid function-tool request shape, with live proof on `gpt-4o-mini` or `o3-mini`.

## Reproduction Assessment

Yes, from source and reporter evidence: `openai/*` currently routes through the Codex app-server, OpenClaw can enable Codex code mode, and upstream Codex serializes freeform code-mode tools as `type: "custom"`. I did not run a live OpenAI request with credentials in this read-only review.

## Solution Assessment

Unclear as an implementation path: the best fix is likely a narrow OpenAI/Codex request-shape or model-capability gate, but owner review should choose the boundary so OpenClaw does not accidentally remove useful Codex native tools for models that support them.

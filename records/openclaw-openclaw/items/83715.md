## Label Justifications

- `P2`: This is a bounded but compatibility-sensitive doctor downgrade repair whose incorrect ordering can mutate existing user configuration.
- `merge-risk: 🚨 compatibility`: The change alters how older binaries handle persisted configurations written by newer releases and must protect both default and intentional-downgrade behavior.

## Summary

Keep open: current main has the shared newer-config destructive-action guard, but it is not applied to doctor repairs; this branch attempts that missing protection but still permits two repair paths before the guard takes effect and has no real after-fix behavior proof.

## What This Changes

The PR blocks doctor repair, automatic confirmation, gateway-token generation, and later doctor write hints when config metadata was written by a newer OpenClaw binary.

## Best Possible Solution

Move future-config detection ahead of every doctor mutation-capable preflight and early repair, retain the existing explicit downgrade override, then add focused regressions and redacted terminal proof for blocked and override runs.

Yes at source level: invoke doctor repair against a newer-written config that is invalid to the older parser, and preflight recovery runs before this branch checks the guard; an early UI freshness issue similarly reaches the original repair-capable prompter first.

## Solution Assessment

No. Reusing the shared future-version guard is the right direction, but it must be resolved before every mutation-capable doctor phase rather than after config preflight and early UI repair.

Establish the future-config block before that early repair, or explicitly gate that path with it.

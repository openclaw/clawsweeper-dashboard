## Summary

Keep open: the Matrix E2EE bootstrap failure is real and current main does not contain this workaround, but the PR should not merge as written because the fetch-layer synthetic 200 can acknowledge an entire `/keys/upload` batch after the server rejected it, and inspectable real behavior proof is still missing.

## What This Changes

The PR adds a Matrix fetch-layer matcher that converts selected `/keys/upload` duplicate one-time-key 400 responses into synthetic 200 responses with empty `one_time_key_counts`, plus tests and a Matrix changelog entry.

## Best Possible Solution

Rework the mitigation at a Matrix crypto/outgoing-request boundary where the original upload body and account state are available, synthesize success only for a proven safe OTK-only collision case, preserve current main transport guards, and add redacted real Matrix proof.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Source and report evidence are strong but I did not run a live homeserver reproduction: the linked issue shows the `/keys/upload` 400, current main has no workaround, and matrix-js-sdk does not retry non-429 4xx responses.

## Solution Assessment

Is this the best way to solve the issue? No; the fetch boundary is too broad because upstream treats any successful `/keys/upload` response as success for the full key batch, so the safer fix belongs where the request payload and Matrix crypto state can be checked.

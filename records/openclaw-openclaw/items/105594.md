## Summary

The latest commit fixes the earlier last-good-chip regression, but the filesystem hardening remains incomplete: `lstat()` and path-based `readFile()` can operate on different objects, so the polling RPC can still block on a replacement FIFO, follow a replacement symlink, or read an oversized replacement file. Keep this PR open for a descriptor-based fix and real after-fix runtime proof.

## What This Changes

The PR replaces per-file git diff subprocesses with in-process untracked-file line counting and preserves degraded state-only pull-request chips as the last-known fallback during GitHub rate-limit failures.

## Best Possible Solution

Open each untracked candidate with nonblocking and no-follow protections where supported, validate size and regular-file type on that same descriptor, read only from that descriptor with an enforced byte cap, and retain the corrected degraded-chip `lastGood` behavior.

## Solution Assessment

No. Removing the per-file git subprocess loop is the right architectural direction, but the narrow maintainable fix must validate and read the same opened file object rather than validating one pathname object and reading another.

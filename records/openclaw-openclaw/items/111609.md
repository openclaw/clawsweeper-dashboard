## Label Justifications

- `P1`: A retained-prefix replay ledger can reaccept previously claimed receipts once their records fall beyond the read cap.
- `merge-risk: 🚨 compatibility`: Oversized existing replay stores change from complete reads to silently partial state without a migration or repair contract.
- `merge-risk: 🚨 message-delivery`: Missing replay records can cause a completed receipt to be claimed again and repeat channel-facing work.
- `merge-risk: 🚨 security-boundary`: The replay ledger is the receipt-reuse guard, and silently truncating it weakens that protection.

## Summary

The OOM boundary is useful, but the proposed truncated-prefix policy is unsafe for the replay ledger: once a valid replay record lies after 32 MiB, reopening the store can treat it as absent and allow the receipt to be processed again. The earlier replay-ledger blocker remains unresolved on the final head.

## What This Changes

The PR replaces unbounded Reef audit and replay JSONL reads with a 32 MiB chunked reader that returns complete prefix records and warns when it truncates an oversized file.

## Best Possible Solution

Keep bounded streaming reads, but give replay state a complete-ledger contract: fail closed with a clear recovery path when it exceeds the cap, or implement an explicitly approved durable compaction/migration path; audit-history prefix reads can remain best-effort if that distinction is intentional.

## Summary

Keep open. Current main still lets a mixed session/cache Telegram chat-window survive with duplicate visible assistant text when the session transcript and Telegram outbound cache use different timestamps, and no open narrower PR already owns this timestamp-drift fix.

## What This Changes

The issue asks OpenClaw to dedupe Telegram direct-message prompt context when the same visible assistant reply appears in both the session transcript and Telegram outbound prompt-context cache with different timestamps.

## Best Possible Solution

Preserve one canonical timestamp for a visible assistant reply across the session transcript and Telegram outbound prompt-context cache, with focused regression coverage, and avoid adding new IDs or config before the planned transcript storage work.

## Reproduction Assessment

Yes, source-level. Current main derives Telegram cache row timestamps from send/cache timing while deduping session and cache rows by exact timestamp_ms plus body, so identical visible assistant text can survive as two prompt-context rows when timestamps differ.

## Solution Assessment

Yes. The narrowest maintainable direction is to carry the assistant transcript timestamp into outbound prompt-context cache recording for the same visible reply, rather than adding a new context policy, config knob, or pre-SQLite message identity scheme.

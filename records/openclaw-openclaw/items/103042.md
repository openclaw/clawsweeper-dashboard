## Label Justifications

- `P0`: The PR concerns a command-injection hardening path for Azure CLI invocations in provider auth, which is a security-sensitive execution boundary.
- `merge-risk: 🚨 compatibility`: The patch changes how existing Windows Microsoft Foundry users launch Azure CLI during upgrade-sensitive auth and onboarding flows.
- `merge-risk: 🚨 auth-provider`: If `az.cmd` cannot be launched directly, Entra token refresh and device-code login fail for Microsoft Foundry auth on Windows.

## Summary

Keep this PR open, but it is not merge-ready: the earlier blocker remains at the same head because the new resolver can return `az.cmd` and then passes that `.cmd` path to Node child-process APIs without `shell`, which breaks the Windows Azure CLI auth path the PR is trying to harden.

## What This Changes

The PR adds a cached Azure CLI path resolver and removes the Windows `shell` option from Microsoft Foundry `execFileSync`, `execFile`, and `spawn` Azure CLI calls.

## Best Possible Solution

Keep the hardening goal, but route Azure CLI through a Node-supported injection-safe Windows invocation strategy and prove `az version`, token refresh, and device-code login on Windows.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, from source and dependency contract: on Windows this PR can return `az.cmd` and pass it to `execFileSync`, `execFile`, or `spawn` without `shell`, while Node documents that `.cmd` files cannot be launched with `execFile()`. I did not establish a live Windows repro.

## Solution Assessment

No. Removing shell parsing is the right security direction, but direct `az.cmd` execution is not a Node-supported Windows strategy; the safer path is a dedicated argument-safe Windows invocation helper plus Windows proof.

## Label Justifications

- `P1`: The issue affects real channel workflows now by leaking internal assistant/tool narration into user-facing messaging channels across several transports.
- `impact:security`: Reports include raw tool-call JSON, internal planning text, and potentially sensitive operational context becoming visible in external messaging channels.
- `impact:message-loss`: The affected delivery pipeline can duplicate, misroute, or incorrectly surface channel messages instead of delivering one intentional final reply.
- `impact:session-state`: Several reports show transcript-visible assistant text diverging from what the user actually saw, causing the agent to reason from stale or false delivery state.

## Summary

Keep open. Current main and latest release still preserve a source-reproducible fallback where phase-less or non-canonical assistant text collected during tool-using runs can become channel reply payloads, while the known direct-fix PRs for this issue were closed unmerged and the newest open PR targets an adjacent hidden-text replay problem rather than this leak.

## What This Changes

The issue asks OpenClaw to stop routing internal or intermediate assistant text between tool calls to user-facing messaging channels, while preserving intentional final replies or explicit message-tool sends.

## Best Possible Solution

Settle one central delivery contract for tool-using channel turns at the payload-construction/source-delivery boundary, then cover both interactive and cron delivery with regression tests and upgrade guidance.

Rationale: The secure UX fix conflicts with existing compatibility expectations for deployments that rely on automatic plain assistant replies, and repository policy treats channel delivery, fallback behavior, and config/default changes as compatibility-sensitive.

Likely owner: steipete

Owner confidence: medium

Options:

- **Adopt central final-only/tool-owned semantics (recommended):** Make the shared payload/source-delivery boundary suppress intermediate phase-less segments for tool-using channel turns, with tests for interactive and cron delivery plus documented upgrade behavior.
- **Add a narrow opt-in delivery flag:** Introduce a default-off final-only or last-segment-only channel/account setting for operators on phase-less transports, accepting that the unsafe default remains until a later migration.
- **Keep automatic delivery and document workarounds:** Leave current behavior in place and steer users to `message_tool_only`, prompts, or streaming settings, accepting continued leak risk for existing channel workflows.

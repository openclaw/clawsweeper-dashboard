## Label Justifications

- `P1`: The issue is a source-provable, cross-channel leak of internal assistant text into real user/customer messaging workflows.
- `impact:security`: Reported examples include internal reasoning, tool-call-like payloads, and operational/customer context becoming visible in external channels.
- `impact:message-loss`: The channel delivery pipeline can emit unintended standalone messages in addition to or instead of the intended final message-tool/final reply.
- `maturity:stable`: The issue includes Discord channel leakage, and Discord is scored M4 Stable in qa/maturity-scores.yaml.

## Summary

Keep open: current main has useful commentary/final-answer mitigations, but the central channel-leak problem is still source-provable in automatic delivery and cron announce paths, and open PRs still claim to fix this issue.

## What This Changes

The issue asks OpenClaw to stop routing assistant text produced before or between tool calls to user-facing messaging channels unless it is an intentional final reply or explicit message-tool send.

## Best Possible Solution

Keep this as the canonical product bug and have maintainers choose a channel-delivery policy that suppresses pre-tool, inter-tool, reasoning, and cron interim text by default while preserving an explicit compatibility path for intentional bare-text replies.

## Reproduction Assessment

Yes, source-reproducible: current tests still assert pre-tool block-reply flushing, source-reply defaults still permit automatic bare-text delivery, and cron delivery selection drops reasoning metadata. I did not run a live channel repro in this read-only review.

## Solution Assessment

No, closing is not the best outcome because current main only partially mitigates commentary/phased cases. The best fix needs a maintainer-approved delivery policy plus regression coverage across automatic source replies, message-tool-only replies, provider phases, and cron announce delivery.

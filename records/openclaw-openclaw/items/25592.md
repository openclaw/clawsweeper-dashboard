## Label Justifications

- `P1`: The issue describes a recurring real-user channel workflow where private interim agent text can be sent to external messaging channels.
- `impact:security`: Internal reasoning, tool-envelope text, and private operational context can become visible in Slack, Telegram, Discord, WhatsApp, and similar channels.
- `impact:message-loss`: The affected surface is channel delivery correctness: one assistant turn can emit extra or unintended visible messages.
- `impact:session-state`: Multiple reports show the leaked content can already be present in assistant turns or persisted session history before later delivery/projection exposes it.
- `maturity:stable`: The bug affects gateway-runtime delivery fallback behavior, which is scored M4 Stable in the checked-in maturity files.

## Summary

Keep open: current main and v2026.6.11 still allow automatic visible delivery for normal source replies and preserve at least one pre-tool block-reply delivery path, while newer comments and linked PRs show this remains a live cross-channel delivery-boundary bug.

## What This Changes

The issue asks OpenClaw to prevent assistant text produced before or between tool calls from being routed as visible messages to Slack, Telegram, iMessage, Discord, and similar channels.

## Best Possible Solution

Keep this as the canonical channel-delivery bug, preserve the existing commentary/final-answer hardening, and choose a backwards-compatible direct/group visible-reply policy before landing generic regression coverage for pre-tool, inter-tool, message-tool, cron, heartbeat, and yield/abort leak paths.

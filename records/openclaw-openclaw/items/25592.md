## Summary

Keep open: current main and v2026.6.11 have useful commentary/final-answer safeguards, but direct/source automatic delivery, unphased block-buffer flushes, and cron multi-payload delivery still leave source-provable paths for non-final assistant text to reach user-facing channels.

## What This Changes

The issue requests that intermediate assistant text produced before or between tool calls stay private instead of being routed as visible messaging-channel replies.

## Best Possible Solution

Keep this as the canonical product bug and choose a delivery policy that suppresses non-final/internal text across automatic, block/preview, and cron paths while preserving explicit progress lanes and a documented compatibility path for existing automatic replies.

## Reproduction Assessment

Yes, by source inspection: an automatic-delivery channel turn can emit unphased assistant text, buffer it, and flush it at tool_execution_start; existing tests also assert buffered pre-tool text delivery. I did not run a live Slack/Telegram/Discord scenario in this read-only review.

## Solution Assessment

Unclear as a single code change: explicit send semantics is robust, but making it the default has compatibility impact for existing automatic DM/source replies. The best fix needs maintainer policy on defaults plus targeted guards for unphased text, final-only delivery, and cron announce payloads.

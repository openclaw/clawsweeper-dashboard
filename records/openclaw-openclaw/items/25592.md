## Label Justifications

- `P1`: Multiple reporters describe real user-facing messaging leaks across Slack, Telegram, Discord, WhatsApp, Feishu, and webchat.
- `impact:message-loss`: The issue is about unintended, duplicated, or non-final channel messages reaching users.
- `impact:session-state`: Reports show incorrect assistant text blocks persisted in session history and replayed through delivery paths.
- `impact:security`: Leaked assistant commentary can expose internal tool payloads, debugging text, and private operational context to external chats.

## Summary

Keep open: current main still has source-reproducible automatic delivery paths for non-final assistant text, cron announce delivery can lose reasoning metadata before payload selection, and several related implementation PRs remain open rather than merged as a canonical fix.

## What This Changes

The issue requests that intermediate assistant text between tool calls stay internal so only final intentional replies or explicit message-tool sends reach messaging channels.

## Best Possible Solution

Keep this issue as the canonical cross-channel leakage tracker while maintainers choose an upgrade-safe visible-reply policy, land or close the active partial PRs, and add regression coverage for unphased, commentary, reasoning, NO_REPLY, cron announce, and message-tool-only turns.

## Reproduction Assessment

Yes from source: current tests still pin visible pre-tool/post-tool block replies on automatic delivery, and cron delivery drops reasoning metadata before selecting deliverable payloads. I did not run a live channel reproduction in this read-only review.

## Solution Assessment

No current implementation is a complete best fix yet; main has partial safeguards, but automatic delivery defaults and cron announce selection leave the core leak class open. The safer path needs maintainer policy on compatibility plus focused runtime and cron guards.

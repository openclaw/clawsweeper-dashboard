## Label Justifications

- `P1`: Multiple production channel reports show internal assistant text leaking into Slack, Telegram, Discord, WhatsApp, and other user-visible workflows.
- `impact:security`: The issue can expose private reasoning, tool payloads, and operational context to external messaging recipients.
- `impact:message-loss`: The affected delivery pipeline can send extra or wrongly scoped channel messages instead of only the intended final response.

## Summary

Keep open: current main has partial commentary-phase suppression, but automatic source replies, unphased block delivery, and cron deliverable selection still leave the reported internal-text leak class unresolved while related PRs remain open or partial.

## What This Changes

The issue asks OpenClaw to stop sending assistant narration, reasoning, or internal text emitted before or between tool calls as visible messaging-channel replies.

## Best Possible Solution

Keep #25592 as the canonical tracker, choose a compatibility-aware delivery policy, then land a generic fix with regressions for unphased pre/inter-tool text, NO_REPLY/message-tool turns, and cron announce delivery.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should external source-visible turns keep automatic bare-text delivery by default, switch to final/message-tool-only delivery, or move through an opt-in migration period?

Rationale: The safest leak fix changes documented channel delivery behavior and could break users who rely on automatic text replies, so automation cannot choose the permanent default alone.

Likely owner: @steipete

Owner reason: The decision spans documented visible-reply defaults, compatibility policy, and shared reply/channel delivery surfaces where @steipete has the strongest history signal.

Owner confidence: high

Options:

- **Compatibility-first migration (recommended):** Keep automatic delivery where explicitly configured, add a safe final/message-tool-only path for external channels, and ship doctor/docs/tests for the transition.
- **Strict explicit-send default:** Make external messaging delivery require final-safe or message-tool semantics by default, accepting a breaking change for setups that rely on bare text replies.
- **Keep automatic default with opt-in fixes:** Land only opt-in mitigations such as enforceFinalTag or verbose-off suppression, accepting that the central leak class remains possible by default.

## Reproduction Assessment

Yes, source-reproducible: current tests and delivery code show automatic visible source replies and pre-tool block flushing for unphased assistant text without requiring a live channel run.

## Solution Assessment

No single proposed path is proven best yet: explicit-send semantics are robust, but current docs/tests intentionally preserve automatic replies, so maintainers must choose the compatibility strategy.

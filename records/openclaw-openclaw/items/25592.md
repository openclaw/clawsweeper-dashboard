## Label Justifications

- `P1`: The issue has repeated current-production reports of internal assistant output leaking into real messaging channels, but it is not an unusable-core-runtime emergency.
- `impact:security`: Reports include internal reasoning, raw command/tool payloads, and operational context being exposed to external chat recipients.
- `impact:message-loss`: The channel delivery surface emits extra unintended messages and can make one intended final answer appear as multiple user-visible replies.
- `impact:session-state`: Several reports trace leaked text to assistant/session content blocks being persisted or replayed as deliverable output rather than internal state.

## Summary

Keep open: current main has important partial safeguards for commentary and message-tool-only paths, but source inspection still shows automatic visible reply defaults and generic unphased/block or cron delivery paths that can expose internal assistant output to external channels.

## What This Changes

The issue reports that assistant text produced before or between tool calls is delivered as visible messages in messaging channels instead of remaining internal until a final or explicit send.

## Best Possible Solution

Keep this issue as the canonical tracker and land a maintainer-approved generic delivery-boundary fix that preserves existing commentary/final safeguards, defines the compatibility policy for automatic direct/source replies, and adds regression coverage for unphased pre-tool/inter-tool text, message-tool turns, cron announce delivery, and thinking-placeholder variants.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For external channel sessions, should OpenClaw keep automatic bare-text source replies as the default while adding narrower final-only/internal-text guards, or should it move direct/group/channel source replies toward explicit message-tool-only delivery with a migration path?

Rationale: Current docs and tests make automatic visible replies a compatibility contract, while the production reports show that the same default can leak internal assistant output into customer or team channels; the tradeoff is product/security policy, not just a code location choice.

Likely owner: steipete

Owner reason: The recent visible-reply default history and docs tie this compatibility decision most closely to the current source-reply policy surface.

Owner confidence: medium

Options:

- **Generic guard with compatibility plan (recommended):** Preserve intentional automatic final replies where required, but suppress internal/pre-tool/inter-tool text through a generic delivery-boundary rule and document or migrate any changed defaults.
- **Explicit message-tool default:** Make external source replies message-tool-only or final-only by default, accepting that existing bare-text reply deployments need migration, docs, and upgrade proof.
- **Opt-in mitigations only:** Land only opt-in safeguards such as final-tag or verbose-off suppression, which reduces urgent pain for configured users but leaves the default leak class open.

## Reproduction Assessment

Yes at source level: current main still has automatic source-reply defaults and tests that flush generic buffered pre-tool text into block replies. I did not run a live Slack/Telegram/Discord reproduction in this read-only review.

## Solution Assessment

No, current main is not yet the best complete solution because it fixes some phased commentary paths but leaves automatic/unphased and cron delivery boundaries unresolved. The best fix is a generic delivery policy plus compatibility and security review, not a channel-specific filter.

## Label Justifications

- `P1`: The issue describes an active cross-channel workflow bug where internal assistant text can be delivered to real users in production messaging channels.
- `impact:security`: The reported leak can expose internal reasoning, tool traces, and workflow context to channel users who should only see intentional replies.
- `impact:message-loss`: The bug is a channel message-delivery failure: unintended intermediate messages are delivered alongside or instead of the intended final response.

## Summary

Keep open: current main has important commentary/final-answer mitigations, but source delivery still has automatic reply paths and cron/embedded payload selection paths that can surface non-final assistant text to channels.

## What This Changes

The issue asks OpenClaw to prevent intermediate assistant text between tool calls from being routed as visible Slack, iMessage, Telegram, Discord, or similar channel messages.

## Best Possible Solution

Keep this as the canonical bug and have maintainers choose a generic delivery policy that suppresses inter-tool/internal text across automatic, message-tool-only, and cron delivery paths while preserving intentional final replies and upgrade compatibility.

## Reproduction Assessment

Yes, source-level reproduction is high-confidence: current main still has automatic source-reply defaults and delivery paths that can emit non-final assistant text. I did not run a live Slack/Telegram/Discord repro in this read-only review.

## Solution Assessment

Unclear as an implementation, because the correct policy for direct chats and cron announce delivery needs maintainer choice. A narrow channel-specific filter would be too small; the best fix belongs at the generic source-reply and embedded/cron payload boundaries.

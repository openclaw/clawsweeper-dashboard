## Label Justifications

- `P1`: The issue reports active user-visible leakage of internal assistant text into real messaging channels, including production Slack, Telegram, WhatsApp, and Discord reports, but it is not a P0 crash loop or confirmed credential bypass.
- `impact:security`: Internal reasoning, tool traces, operational context, and customer-facing analysis can be exposed to external channel recipients.
- `impact:message-loss`: Channel recipients can receive extra or wrong visible messages instead of a single intended final or message-tool response.
- `impact:session-state`: Several reports show leaked commentary or duplicated text already persisted in assistant/session history before delivery, making transcript state part of the failure mode.

## Summary

Keep open: current main has several partial safeguards, but ordinary automatic visible-reply paths can still deliver unphased assistant text before or between tool calls, and cron announce delivery still selects deliverable text without a reasoning/commentary signal. The issue remains the canonical tracker for a security-sensitive channel-delivery boundary, with open/adjacent PRs not yet providing a merged, proven fix.

## What This Changes

The issue requests that intermediate assistant text produced before or between tool calls stay internal instead of being sent as visible Slack, Telegram, iMessage, WhatsApp, Discord, or other channel messages.

## Best Possible Solution

Keep this as the canonical product bug and implement a maintainer-approved generic delivery boundary that suppresses pre-tool, inter-tool, reasoning, commentary, NO_REPLY, yield/abort, and cron-announce leakage while preserving an explicit compatibility story for automatic direct replies.

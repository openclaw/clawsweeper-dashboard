## Label Justifications

- `P1`: The issue describes an active, cross-channel user-facing delivery regression with repeated production reports across messaging channels.
- `impact:security`: Internal reasoning, tool payloads, planning, and error context can be exposed to channel recipients who should only see intentional replies.
- `impact:message-loss`: The delivery pipeline can duplicate or misroute intermediate assistant text as standalone channel messages in the same user turn.

## Summary

Keep open: current main and the latest release still leave automatic source-reply paths where unphased assistant text can become visible, and the issue discussion has recent cross-channel production reports plus open candidate PRs rather than a merged fix.

## What This Changes

The issue requests that assistant text produced before or between tool calls stay internal instead of being delivered as visible Slack, Telegram, Discord, WhatsApp, iMessage, or similar channel messages.

## Best Possible Solution

Keep this as the canonical bug and land a generic delivery-boundary fix that suppresses internal reasoning/commentary/inter-tool text across interactive and cron paths while preserving an explicit, documented policy for automatic final replies versus message-tool-only delivery.

Question: What source-reply delivery policy should OpenClaw enforce for channel sessions when an assistant emits ordinary text before or between tool calls?

Rationale: Current behavior is partly product policy, partly security boundary: fixing the leak may require changing defaults or adding stricter guards that affect existing users who rely on automatic bare-text replies.

Likely owner: steipete

Owner reason: This is a compatibility-sensitive product/security boundary decision on the source-reply path, and steipete is the clearest recent reviewer/source-history routing signal from the current checkout and issue timeline.

Owner confidence: medium

Options:

- **Preserve automatic finals, suppress internals (recommended):** Keep automatic final replies as the default but add runtime guards so pre-tool, inter-tool, reasoning, commentary, and NO_REPLY-suppressed blocks cannot become channel-visible payloads.
- **Move channels to message-tool-only:** Require message(action=send) for more source/channel scopes by default, with migration, docs, and fallback handling for users whose agents only produce final text.
- **Only ship opt-in mitigations:** Keep defaults unchanged and land opt-in tools such as final-tag enforcement or message-tool mode, accepting that the default leak class remains possible.

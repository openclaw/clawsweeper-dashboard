## Label Justifications

- `P1`: The issue describes a recurring user-facing channel workflow failure that can expose internal assistant text in real Slack, Discord, Telegram, WhatsApp, and Feishu deployments.
- `impact:security`: Intermediate reasoning, raw tool-like payloads, and operational commentary can expose sensitive internal context to external messaging recipients.

- `maturity:stable`: The issue affects Discord conversation routing and delivery, and Discord is currently scored M4 Stable in qa/maturity-scores.yaml.

## Summary

Keep open: current main has important partial safeguards, but automatic visible-reply paths and unphased assistant text can still produce user-visible channel output, and two open implementation PRs still claim this issue with closing syntax.

## What This Changes

The issue asks OpenClaw to prevent intermediate assistant text between tool calls from being routed to messaging channels, leaving only intentional final replies or explicit message-tool sends visible.

## Best Possible Solution

Choose one source-reply policy for user-facing channel turns, then land a focused implementation that keeps inter-tool/unphased assistant text private by default while preserving an explicit compatibility path for automatic final replies and adding regression coverage across streaming, final payload assembly, cron/announce, and message-tool delivery.

Owner confidence: medium

Options:

- **Final-only source replies with compatibility escape (recommended):** Make inter-tool/unphased assistant text private unless it is explicit final-answer text or a message-tool send, while preserving or documenting an operator-controlled automatic-final compatibility mode.
- **Default everything to message-tool-only:** Require message(action=send) for user-visible source replies across direct, group, and channel conversations, accepting a higher upgrade break risk for existing bare-text workflows.
- **Land opt-in mitigations only:** Keep current automatic defaults and ship opt-in guards such as enforceFinalTag or verbose-off suppression, accepting that unconfigured deployments may still leak intermediate text.

## Reproduction Assessment

Yes, at source level. Current tests still assert pre/post-tool text snapshots become block replies and assistantTexts entries, and current source shows automatic delivery remains available for normal source replies.

## Solution Assessment

Unclear as a single implementation until maintainers choose the delivery policy. The best fix is not just one more sanitizer; it needs a consistent final-only/message-tool boundary with explicit compatibility handling for existing automatic reply users.

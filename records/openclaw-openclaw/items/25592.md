## Label Justifications

- `P1`: The issue describes a recurring real-user channel workflow failure where internal assistant output is delivered to external messaging channels.
- `impact:security`: Leaked reasoning, tool payloads, and internal planning can expose sensitive operational context to people in Slack, Telegram, Discord, WhatsApp, and similar channels.
- `impact:message-loss`: The failure mode is incorrect channel message delivery: extra standalone assistant messages are delivered when only one final or explicit message-tool send should appear.
- `maturity:stable`: The cross-channel delivery problem includes Discord, which is scored M4 Stable and has stable Conversation Routing and Delivery coverage in qa/maturity-scores.yaml.

## Summary

Keep open: current main has useful commentary-phase and reasoning-lane safeguards, but the central channel leak is still source-provable for unphased assistant text and cron/announce payload selection, and there are open related PRs rather than a merged fix.

## What This Changes

The issue reports that assistant text produced before or between tool calls is delivered as visible messages in user-facing channels instead of only delivering intentional final replies.

## Best Possible Solution

Keep this issue as the canonical product/security bug, choose the intended final-only or message-tool-only policy for channel sessions, then land a focused implementation with regression coverage for unphased inter-tool text, reasoning/commentary flags, explicit message-tool sends, and cron announce delivery.

## Reproduction Assessment

Yes at source level: current main still defaults ordinary source replies to automatic delivery and has tests that preserve visible post-tool assistant text. I did not run a live Slack/Telegram/Discord reproduction in this read-only review.

## Solution Assessment

No, current main is not yet the best end state: commentary-phase suppression is helpful, but unphased assistant text and cron announce payloads still have visible delivery paths. The best fix needs a maintainer policy decision because tightening defaults affects existing automatic bare-text reply setups.

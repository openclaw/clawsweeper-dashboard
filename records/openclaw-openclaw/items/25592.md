## Summary

Keep open. Current main has important phase-aware protections, but the broad leak is not fixed: no-canonical-final runs can still fall back to delivering every accumulated assistant text segment, and normal source replies still default to automatic delivery unless operators opt into message-tool-only mode.

## What This Changes

The issue asks OpenClaw to prevent intermediate assistant text between tool calls from being routed as visible messages in messaging channels.

## Best Possible Solution

Make the generic payload/delivery boundary distinguish intentional final/source replies from interim tool narration before any channel adapter sees it, with maintainer-approved compatibility behavior for automatic direct/group/channel replies.

Options:

- **Central final-only fallback with upgrade guard (recommended):** Trim or suppress interim accumulated text at `buildEmbeddedRunPayloads` or an equivalent shared boundary, keep explicit finals/message-tool sends visible, and add regression coverage for phase-less transports, cron delivery, and message-tool replies.
- **Default to explicit sends for channels:** Move more source-channel contexts to message-tool-only delivery, accepting a stronger safety posture but requiring a migration/documentation plan for deployments that rely on automatic bare text replies.
- **Opt-in only for now:** Add a per-channel or per-account final-only option and keep current automatic defaults, reducing compatibility risk but leaving the reported default-path leak open until operators opt in.

## Label Justifications

- `P1`: The issue reports an active cross-channel workflow failure where internal assistant text reaches real messaging users, including production customer-facing channels.
- `impact:message-loss`: The failure creates extra or misrouted visible channel messages instead of one intentional final reply or explicit message-tool send.
- `impact:session-state`: Reports show commentary/thinking text can be persisted in assistant turns and later reused or exposed through reply context/history paths.
- `impact:security`: Internal planning, tool traces, raw command envelopes, and customer-context reasoning can be exposed outside the intended agent/runtime boundary.

## Summary

Keep open: current main still has source-level paths where automatic visible replies, unphased assistant text, and cron delivery selection can expose internal assistant output to external channels, while the linked candidate PRs remain open or blocked rather than merged fixes.

## What This Changes

The issue asks OpenClaw to prevent assistant text produced before or between tool calls from being delivered as visible Slack, Telegram, iMessage, Discord, WhatsApp, or similar channel messages.

## Best Possible Solution

Keep this issue as the canonical core bug until maintainers choose the source-reply delivery policy and land a focused, proof-backed fix that suppresses internal text across automatic, message-tool-only, streaming/block, and cron announce paths without silently breaking existing channel setups.

Options:

- **Adopt safe external-channel default (recommended):** Make external channel output require explicit message-tool or final-only semantics by default, with migration/doctor/docs coverage and opt-out only where maintainers intentionally preserve legacy behavior.
- **Keep automatic default with targeted guards:** Preserve legacy bare-text replies and land narrower filters for commentary, reasoning, NO_REPLY, and cron paths, accepting that some model narration remains harder to classify.
- **Split by chat context:** Use message-tool-only for shared rooms and high-risk autonomous/cron paths while keeping DMs automatic until a later migration decision.

## Reproduction Assessment

Yes, at source level: current main documents automatic visible replies, resolves default source delivery to automatic in common paths, appends eligible unphased assistant text to block replies, and preserves cron deliverable text payloads. ## Solution Assessment

Unclear as a single code change: explicit send semantics is the strongest safety model, but it changes a documented compatibility contract. The best fix needs a maintainer-approved delivery policy plus focused regression coverage for direct chats, shared rooms, streaming/block replies, message-tool sends, NO_REPLY, reasoning/commentary phases, and cron announce delivery.

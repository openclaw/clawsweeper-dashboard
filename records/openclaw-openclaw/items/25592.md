## Label Justifications

- `P1`: The issue reports a recurring real-user messaging-channel leak of internal assistant text across Slack, Telegram, Discord, WhatsApp, Feishu, and webchat.
- `impact:message-loss`: The delivery pipeline can produce extra unintended channel messages during tool-heavy turns instead of a single intentional final reply.
- `impact:security`: The leaked content can expose internal planning, tool payloads, customer context, and raw command-like data to messaging-channel recipients.
- `impact:session-state`: Several reports show leaked or duplicated assistant text persisted in session history and replayed through channel delivery.
- `maturity:stable`: The issue includes Discord reproduction, and Discord is currently scored M4/Stable in the maturity scorecard.

## Summary

Keep open: current main and the latest release still preserve automatic source delivery paths and unphased assistant text can still enter the block-reply stream, so the central cross-channel leak class is not implemented away. The linked implementation PRs are open fork candidates, but both are unmerged and conflicting, so they are not a safe superseding target.

## What This Changes

The issue requests that intermediate assistant text produced before or between tool calls stay internal instead of being delivered as visible messaging-channel output.

## Best Possible Solution

Keep this issue open as the canonical cross-channel delivery bug while maintainers choose and land a compatibility-safe policy through the linked implementation PRs or a replacement design.

## Reproduction Assessment

No live high-confidence repro was run in this read-only review, but there is a clear source-level reproduction path: current main still permits automatic delivery for normal source chats and still buffers unphased assistant text before tool execution. The discussion also contains multiple recent real-channel reports, including Discord, Telegram, Slack, WhatsApp, Feishu, and webchat.

## Solution Assessment

Unclear as an implementation choice: the bug is real, but changing default direct/source delivery requires maintainer product and upgrade-policy judgment because existing users may rely on bare-text automatic replies. The best repair likely preserves explicit command/final-answer behavior while making inter-tool commentary private by default or through a maintained opt-in policy.

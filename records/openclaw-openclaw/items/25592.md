## Label Justifications

- `P1`: Internal reasoning and inter-tool text can still leak into real messaging channels across multiple reported deployments, making this an urgent user-facing channel workflow bug.
- `impact:security`: The issue crosses a sensitive information boundary by exposing internal reasoning, tool arguments, or operational context to external chat recipients.

## Summary

Keep open: current main has partial commentary-phase suppression, but documented automatic source delivery, unphased inter-tool buffering, and cron deliverable selection can still route internal assistant text to external channels; linked PRs are open candidates, not merged fixes.

## What This Changes

The issue asks OpenClaw to stop sending assistant text produced between tool calls to messaging channels, while still delivering intentional final or explicit message-tool replies.

## Best Possible Solution

Maintainers should choose the delivery policy, then land one generic fix that suppresses commentary, reasoning, unphased inter-tool text, and cron reasoning across automatic delivery while preserving or explicitly migrating intentional final replies.

## Maintainer Decision

Question: Should OpenClaw keep automatic final text as the channel default while suppressing only internal/inter-tool text, or move channel-visible output toward explicit message-tool sends by default?

Rationale: The security goal is clear, but the documented automatic reply default is a compatibility contract for existing channel users, so automation should not choose the new default policy alone.

Likely owner: Peter Steinberger

Owner confidence: medium

Options:

- **Preserve automatic finals, suppress internals (recommended):** Keep intentional final assistant text deliverable by default, but suppress commentary, reasoning, unphased pre-tool/inter-tool text, and cron reasoning payloads with focused source and channel regression tests.
- **Require explicit message sends:** Make channel-visible output require message(action=send) by default, accepting a larger compatibility break for a stronger security boundary.
- **Ship opt-in mitigations only:** Land the open opt-in or narrow PRs without changing defaults, leaving affected users protected only after configuration changes.

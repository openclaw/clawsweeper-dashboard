## Label Justifications

- `P1`: The issue affects real external messaging workflows with internal assistant text leaking to users, but it is not a total runtime outage or confirmed credential compromise.
- `impact:security`: Reports include internal planning, reasoning, and raw tool-call-like payloads becoming visible in Slack, Telegram, Discord, WhatsApp, and other external channels.
- `impact:message-loss`: The channel delivery path can emit extra unintended messages instead of only the intended final or explicit message-tool output.
- `impact:session-state`: The source-reproducible failure depends on assistant turn phase, buffered block reply state, and message-tool delivery state being interpreted incorrectly across a tool-using session.
- `maturity:stable`: Discord is scored M4 Stable in qa/maturity-scores.yaml, and this issue includes a current Discord production reproduction in the discussion.

## Summary

Keep open: current main and the latest release still preserve automatic source reply delivery for normal chats and still have a tested path that flushes buffered pre-tool text before tool execution. Several partial safeguards exist, but the remaining fix requires a maintainer policy decision about message-tool-only or final-only delivery defaults.

## What This Changes

The issue asks OpenClaw to stop routing intermediate assistant text between tool calls to external messaging channels and deliver only intentional final or explicit message-tool output.

## Best Possible Solution

Keep this issue as the canonical bug, choose an explicit source-reply delivery policy for normal chats, and land regression coverage that proves unphased assistant text before or between tool calls stays private unless the chosen policy intentionally delivers it.

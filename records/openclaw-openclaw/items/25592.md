## Summary

Keep open: current main has important partial safeguards, but the central channel delivery-boundary bug remains source-reproducible and still needs a maintainer policy/security decision before a safe fix can land.

## What This Changes

The issue asks OpenClaw to stop assistant text emitted before or between tool calls from being delivered as visible messages in Slack, Telegram, iMessage, WhatsApp, Discord, and similar channels.

## Best Possible Solution

Keep this as the canonical bug and make the source-reply pipeline record one delivery reality: private commentary/reasoning must not leak, and any suppressed text that remains in transcript context must be marked so the agent cannot treat it as user-visible.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For source-channel turns that emit assistant text before or between tool calls, should OpenClaw deliver classified user-facing text, keep it private with an agent-visible undelivered marker, or require message(action=send) for all channel-visible output?

Rationale: The source and related reports show both security/UX leakage and transcript-vs-delivery mismatch risks, and the safe default affects existing channel behavior, direct chats, cron delivery, and message-tool-only upgrade compatibility.

Likely owner: steipete

Owner reason: This is the strongest current-main routing signal from the sampled source-reply and embedded delivery history, and the decision spans product/security defaults rather than a narrow code defect.

Owner confidence: medium

Options:

- **Private plus delivery marker (recommended):** Keep internal/pre-tool text private by default, but inject or persist delivery-status context so later agent turns cannot assume suppressed text was seen by the user.
- **Deliver classified pre-tool text:** Flush text classified as user-facing before tool execution while preserving commentary/reasoning suppression and adding regression tests for leak variants.
- **Require message tool:** Move channel-visible output to explicit message(action=send) semantics with an upgrade path for existing automatic direct/source-chat deployments.

## Reproduction Assessment

Yes at source level: current main still has automatic visible reply paths, partial phase-based suppression, and a cron delivery selector that preserves multiple successful text payloads without carrying reasoning/commentary flags. I did not run a live Slack/Telegram/Discord replay in this read-only review.

## Solution Assessment

Unclear until maintainer direction: a narrow suppression patch is plausible but not necessarily the best fix because it can worsen transcript-vs-user delivery mismatch. The best fix should define one source-reply delivery policy and cover both leak and silent-drop variants.

## Summary

Keep open: current main still lacks a settled, default-preserving OpenAI Responses compatibility path for strict relays that reject prompt messages in `input`, and the proof-positive candidate PR is still open, draft, and product-gated.

## What This Changes

The issue asks OpenClaw to avoid sending `role: "system"` in OpenAI Responses `input` for configured reasoning models whose strict relay rejects system messages.

## Best Possible Solution

Land or replace the open candidate with a default-preserving Responses compatibility path, with tests/docs for strict relays and for providers that reject `developer`.

Question: For custom `openai-responses` providers that reject prompt messages in `input`, should OpenClaw support an explicit strict-relay compatibility mode, extend existing developer-role compat semantics, or decline core support for that relay class?

Rationale: The reported failure is real enough to keep open, but the request-shape default affects multiple incompatible OpenAI-compatible provider families and may create a public config contract.

Likely owner: vincentkoc

Owner reason: They own the most directly related merged developer-role compatibility change in the current Responses transport history.

Owner confidence: high

Options:

- **Sponsor default-preserving compat (recommended):** Keep current defaults and support a documented opt-in such as an instructions-placement switch or maintainer-approved extension of existing compat semantics.
- **Flip reasoning Responses to developer:** Make reasoning custom Responses models send `developer` by default, accepting the known regression risk for providers that reject developer role.
- **Decline this relay class:** Keep core behavior unchanged and direct affected operators to `openai-completions` or provider-specific external workarounds.

## Reproduction Assessment

No live current-main repro was run here; source inspection plus the reporter's tcpdump and 400 response strongly support the strict-relay failure. The exact path that made the configured reasoning model send `system` instead of `developer` still needs live or focused runtime proof.

## Solution Assessment

No, the requested global `developer` role for reasoning models is too broad by itself because current history proves the opposite provider class. A default-preserving opt-in compatibility path is the safer maintainable direction if maintainers accept the config surface.

## Summary

Keep open: this is a plausible fix for the linked crash-loop recovery bug, but it is not the best fix as written because it treats `openai-codex` as a bundled provider and omits the documented `openclaw doctor --fix` migration path for legacy `openai-codex` config/profile ids. The PR also still lacks real behavior proof for the exact no-auth `openai-codex/gpt-5.4` error path.

## What This Changes

The PR adds a legacy `openai-codex` branch to the embedded-agent missing-model hint and regression tests for legacy, built-in, and custom provider cases.

## Best Possible Solution

Update the legacy `openai-codex` hint to identify it as a legacy provider id, recommend `openclaw doctor --fix` plus `openclaw models status`, preserve the built-in/custom-provider hints, and add exact runtime proof for the no-auth error path.

## Reproduction Assessment

Yes, at source level: current main still emits the generic provider-registration hint for unresolved configured `openai-codex` refs, and current validation rejects the reported `models.providers.openai-codex` overlay without `baseUrl`. I did not run a live Docker crash-loop reproduction in this read-only review.

## Solution Assessment

No. The helper is the right owner boundary, but the best fix should call `openai-codex` a legacy provider id and recommend `openclaw doctor --fix` before or alongside auth checks; https://github.com/openclaw/openclaw/pull/100120 shows that better wording but is not a clean supersession target while its checks are failing.

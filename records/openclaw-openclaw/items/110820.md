## Summary

This PR improves cancellation of normally killable Git children, but it does not provide the claimed hard deadline for the stale-NFS/unresponsive-filesystem case: Node’s synchronous child-process timeout sends the signal and still waits for the child to close. The prior P2 concern remains on the unchanged head, and the submitted extracted-helper probe is not real end-to-end behavior proof for the owning script.

## What This Changes

The branch adds `SIGKILL` and a 120-second timeout to the `execFileSync` Git helper used by Testbox lease-freshness checks.

## Best Possible Solution

Choose and implement an execution model that lets the lease-freshness checker return after its deadline without waiting on an uninterruptibly blocked Git child, or deliberately scope the change and its documentation to killable child-process hangs only.

Question: Should the lease-freshness checker guarantee that its own process returns after the deadline even if Git is uninterruptibly blocked by filesystem I/O, or is best-effort cancellation of killable Git hangs the intended contract?

Rationale: A true return-time bound requires changing the synchronous execution/lifecycle model and deciding how to handle a child that cannot be killed immediately; that operator and cleanup tradeoff is not safely inferred from a two-line timeout addition.

- **Accept best-effort cancellation:** Keep the synchronous helper but narrow the PR claim and documentation to killable Git hangs rather than stale-NFS hard-bound behavior.

## Reproduction Assessment

No high-confidence reproduction of the stated stale-NFS case is provided. Source inspection establishes that the helper remains synchronously blocked until its child closes, and the supplied probe only covers a killable shimmed child.

## Solution Assessment

No; adding a synchronous child timeout is a useful best-effort mitigation, but it is not the best solution for the stated hard fail-fast requirement because Node still waits for a child blocked in uninterruptible I/O.

## Summary

Keep open. Current main and v2026.7.1 still lack an ordered fallback-chain diagnostic; the overlapping per-model probe request at https://github.com/openclaw/openclaw/issues/63145 does not settle whether OpenClaw should expose an independent health probe or exercise the canonical fallback ordering, so implementation needs a maintainer product choice first. ([raw.githubusercontent.com](https://raw.githubusercontent.com/openclaw/openclaw/main/src/cli/models-cli.ts))

## What This Changes

Add a command that proactively probes configured fallback models, optionally across the full ordered chain, without forcing a real primary-provider failure.

## Best Possible Solution

Provide one operator diagnostic that derives the effective ordered chain through the canonical fallback resolver, probes each candidate while pinning it to prevent later fallbacks from masking failure, and reports structured per-candidate results; add a slash wrapper only if maintainers explicitly want channel execution.

Question: Should proactive fallback validation be the ordered mode of the existing `models status --probe` diagnostic, a dedicated CLI fallback command, or a channel-visible `/models test-fallback` command?

Rationale: The existing auth probe, the broader per-model request, and this ordered-chain request overlap technically but have different safety, output, and user-surface contracts; implementing one without choosing the canonical interface would create competing diagnostics.

Likely owner: steipete

Owner reason: They supplied the prior item-specific product review and have extensive recent fallback-policy and probe history.

Owner confidence: high

Options:

- **Unify the CLI diagnostic (recommended):** Extend the existing model-status probe with an ordered fallback scope that reuses canonical candidate resolution, leaving `/models` focused on browsing and selection.
- **Create a fallback subcommand:** Add a dedicated `openclaw models fallbacks test` CLI command with first/all modes when maintainers want fallback semantics separated from auth status.
- **Ship the slash command:** Expose `/models test-fallback` only after defining channel authorization, token-cost warnings, timeouts, redaction, and its relationship to CLI probing.

## Reproduction Assessment

Not applicable as a bug reproduction: this is a new diagnostic capability, and current source plus v2026.7.1 documentation clearly confirm that no equivalent ordered fallback test exists.

## Solution Assessment

No, the proposed slash command is only one plausible interface; the narrower maintainable solution is to consolidate ordered fallback probing with the existing operator diagnostic and reuse the canonical resolver.

## Summary

Keep open. Current main and v2026.6.11 still lack a targeted fallback-chain test, the direct implementation PR closed for contributor queue limits rather than product rejection, and maintainers still need to choose how this overlaps the existing auth probe and broader configured-model health check.

## What This Changes

Add a live diagnostic command that deliberately skips the primary model, tests one or all configured fallbacks, and reports which candidates succeed.

## Best Possible Solution

Implement one isolated runtime-backed diagnostics service with explicit per-model and ordered-fallback scopes, no mutation of normal cooldown/session state, and shared presentation through the CLI and slash command where appropriate.

Question: Should fallback verification prove individual fallback-model reachability, the real ordered fallback runner, or both through one unified diagnostic surface?

Rationale: The semantics and public contract differ materially: independent probes are safer, while production-chain execution better represents real failover but introduces state and error-handling complexity.

Likely owner: steipete

Owner reason: He has the strongest combined history across fallback policy, model status probing, and the existing issue-level review.

Owner confidence: high

Options:

- **Unified isolated diagnostics (recommended):** Provide both configured-model and ordered-fallback scopes through one non-mutating probe service shared by the CLI and any slash-command presentation.
- **Reachability only:** Probe each configured fallback independently and document that this does not validate production fallback ordering.
- **Production chain only:** Exercise the real fallback runner in a dedicated diagnostic context and accept the additional state-isolation and reporting requirements.

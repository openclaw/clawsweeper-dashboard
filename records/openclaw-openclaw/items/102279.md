## Label Justifications

- `P1`: The default Telegram isolated-ingress workflow can silently consume an accepted user message during a long provider or handler timeout.
- `impact:message-loss`: The reported path leaves the inbound user message in a failed tombstone with no replay and no Telegram reply to the sender.
- `impact:session-state`: The failed user message can be absent from the normal transcript/session flow while only a retained ingress tombstone remains.

## Summary

Keep open: current `main` and the latest release still have Telegram isolated-ingress paths that fail timed-out or retry-exhausted spooled updates into durable tombstones while suppressing the normal user-facing failure fallback, and the adjacent merged fixes do not cover this failed-tombstone visibility/replay gap.

## What This Changes

The issue reports that Telegram isolated ingress can dead-letter timed-out or retry-exhausted spooled user messages without a reply, replay, or durable operator-facing surface.

## Best Possible Solution

Keep single-processing safety for failed tombstones, but make dead-lettered Telegram ingress entries actionable: surface retained failed rows in health/status/doctor and add a duplicate-safe user notice or maintainer-approved handler-timeout replay policy.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For Telegram isolated-ingress failed tombstones, should OpenClaw preserve terminal dead-letter semantics and add visibility, or should handler-timeout rows be replayed automatically?

Rationale: The current terminal tombstone behavior avoids duplicate side effects, but the user-visible and operator-visible recovery contract is a product reliability choice that affects retry policy, status/doctor surfaces, and Telegram user messaging.

Likely owner: joshavant

Owner reason: Josh authored the core timeout and spooled replay lifecycle fixes that best frame the single-processing versus replay tradeoff.

Owner confidence: medium

Options:

- **Surface And Notify Failed Tombstones (recommended):** Preserve terminal failed rows for unsafe timeout/retry-limit cases, add failed-ingress counts/details to operator surfaces, and send one duplicate-safe failure notice when a user message is dead-lettered.
- **Replay Handler-Timeout Tombstones Once:** Allow a guarded one-time replay for `handler-timeout` rows with zero attempts, but require proof that late original handlers cannot duplicate replies or session effects.
- **Operator Visibility Only:** Expose failed tombstones in status/doctor without user notices, accepting that senders may still see silence while operators get a repair path.

## Reproduction Assessment

Yes at source level: current `main` marks handler-timeout spooled updates failed, suppresses spooled replay fallback replies, and has regression tests expecting failed tombstones instead of replay. I did not run live Telegram fault injection in this read-only review.

## Solution Assessment

Unclear until maintainers choose the dead-letter policy. The report identifies a real gap, but the safest fix should preserve single-processing semantics while adding operator surfacing and a duplicate-safe user notice unless maintainers explicitly approve replay.

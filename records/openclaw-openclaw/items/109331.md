## Summary

The optimization is directionally sound because `openclaw/ci-gate` aggregates every selected CI lane, but the current gate-job lookup remains incomplete for workflows exceeding GitHub’s 100-job page limit, so the intended early-landing path can still fail on the repository’s large CI plans.

Likely related people: @steipete is the strongest routing candidate based on official repository stewardship and recent ownership of CI and maintainer landing tooling.

## What This Changes

The PR allows `scripts/pr` landing verification to accept an in-progress or queued CI workflow when that workflow run’s current-attempt `openclaw/ci-gate` job has already completed successfully.

## Best Possible Solution

Paginate and combine every `filter=latest` jobs page for the selected workflow run, add a regression with the successful gate after job 100, and retain exact-head/current-attempt plus gate-contract coverage before merging.

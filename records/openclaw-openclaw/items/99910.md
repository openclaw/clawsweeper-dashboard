## Summary

Keep open: current main has bounded and SQLite-backed memory-core state hardening, but there is still no proof that the reported 2026.6.9 missing/invalid short-term recall rebuild path cannot monopolize the gateway event loop, and the open related work covers pressure scheduling or interrupted-run observability rather than this exact outage loop.

## What This Changes

The issue reports that memory-core short-term promotion dreaming can monopolize the gateway event loop after the recall store is missing or invalid, preventing recall persistence and causing repeated watchdog restarts.

## Best Possible Solution

Identify the specific rebuild or state-store hot path, make memory-core dreaming bounded and yield-friendly without adding a new config knob, and coordinate interrupted-run lifecycle semantics with https://github.com/openclaw/openclaw/issues/97692.

## Reproduction Assessment

Yes at report level and partly at source level: the issue gives repeated timings and unmodified-release evidence, and current source shows the managed dreaming trigger still runs sweep, repair, rank, apply, report, and narrative work on the gateway path. I did not reproduce the 10-minute event-loop peg on current main.

## Solution Assessment

Unclear: capping or chunking is the right direction, but the best code change depends on whether the hot path is session ingestion, recall repair/writeback, plugin-state scanning, or narrative/report work. The interruption-recording work belongs with https://github.com/openclaw/openclaw/issues/97692 rather than replacing this performance fix.

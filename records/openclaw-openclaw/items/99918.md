## Summary

Keep this PR open for maintainer review: the terminal foundation is relevant to the linked feature request, but the current web panel does not pass the active agent into `terminal.open`, so multi-agent and fully sandboxed-agent cases can open the wrong default-agent host shell instead of using or refusing the target agent.

## What This Changes

Adds a gateway `terminal.*` PTY protocol, terminal config, CSP/bootstrap support, a dockable ghostty-web Control UI terminal, generated Swift protocol models, tests, and a new UI dependency.

## Best Possible Solution

Thread the active chat or selected agent id into the terminal panel, include it in `terminal.open`, add regression coverage for multi-agent and `sandbox.mode: "all"` cases, and keep the default-on shell/CSP decision explicit for maintainers before merge.

## Reproduction Assessment

Yes from source inspection: the app resolves an active workspace agent but renders the terminal panel without it, and the panel calls `terminal.open` with only rows and columns. I did not run the UI because this was a read-only review.

## Solution Assessment

No: the dedicated admin `terminal.*` gateway seam is the right general direction, but the web implementation must target the active agent before its sandbox and workspace guarantees are true. The default-enabled shell/CSP surface also needs explicit maintainer acceptance.

## Summary

Keep open: current main and v2026.6.11 still have local Content-Disposition filename parsers plus Feishu-specific recovery, not the requested shared multi-encoding decoder. The open shared-decoder PR is useful context, but it remains open, partial, and still needs a media-core/plugin-safe boundary decision.

## What This Changes

Request a centralized filename decoder for RFC 5987, mojibake recovery, and multi-charset Content-Disposition handling across media and channel adapters.

## Best Possible Solution

Choose one plugin-safe shared media filename decoder seam, then refresh and land https://github.com/openclaw/openclaw/pull/71517 or a narrower replacement that keeps Feishu fixes as consumers instead of duplicating decoder logic.

## Reproduction Assessment

Yes, at source level: current main still lacks a shared multi-encoding decoder and keeps separate remote-media and Feishu filename parsers. I did not run a live channel reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API boundary. A shared decoder is the right direction, but the maintainable solution should be one plugin-safe media seam rather than duplicated core and plugin helpers.

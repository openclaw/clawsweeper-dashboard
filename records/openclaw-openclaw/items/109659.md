## Label Justifications

- `P1`: A production channel can remain silently unavailable for hours while gateway and container health checks continue reporting healthy.
- `impact:message-loss`: Once the restart chain exits, channel messages are no longer received or delivered until an operator restarts the process.
- `impact:crash-loop`: The affected channel enters a persistent unavailable state with no automatic process-level recovery, despite the gateway remaining alive.

## Summary

Keep this issue open: the shared channel manager wraps both the abortable restart delay and the next startup attempt in an empty catch, creating an actionable silent-exit path, and none of the related reports owns this specific lifecycle defect. citeturn1search5turn3view0

## What This Changes

Prevent channel auto-restart from silently terminating when restart backoff is aborted or the subsequent startup fails, while reconciling restart state and diagnostics.

## Best Possible Solution

Give automatic restart an explicitly owned lifecycle, distinguish intentional shutdown from unexpected cancellation or startup failure, reconcile `restartPending` on every exit, retain bounded retries, and add diagnostics plus regression coverage for both the abort race and failed restart startup.

## Reproduction Assessment

Yes at source level: a fake channel can exit to schedule backoff, then trigger abort or make the next startup throw and assert that the current empty catch produces no further start, diagnostic, or state cleanup. That deterministic harness was not executed in this read-only review.

## Solution Assessment

The suggested direction is substantially right, but logging alone is not the best fix; the narrow maintainable solution must correct restart-signal ownership and terminal-state reconciliation while preserving intentional stops.

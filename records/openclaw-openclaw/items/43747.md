## Summary

Keep open: current main and the latest release still expose separate builtin/QMD backend config, a scalar memory plugin slot, and a separate compaction memory-flush writer, so the broader request for a coherent memory-management contract is not implemented.

## What This Changes

The issue asks OpenClaw to define one consistent memory-management contract so users do not see different SQLite, daily Markdown, or no-recall behavior across setups.

## Best Possible Solution

Settle one maintainer-approved memory contract covering backend selection, active memory plugin ownership, automatic flush/write behavior, and upgrade migration, then land it through the existing role-slot and Memory MVP tracks.

## Summary

Keep open: current main still exposes separate builtin/QMD backend selection, memory-search config, one active memory plugin slot, and an independent compaction memory-flush path, so the reported memory-management inconsistency is not resolved.

## What This Changes

The issue requests a strict, consistent memory-management definition/config so users do not see different SQLite, QMD Markdown, or disabled/no-memory behavior.

## Best Possible Solution

Decide the canonical memory architecture first, then land a migration-backed simplification that makes active backend, plugin role, flush behavior, and storage location predictable in docs, doctor, setup, and runtime.

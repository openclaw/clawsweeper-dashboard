## Summary

Keep open: current main and v2026.6.11 still expose separate builtin/QMD backend selection, memory-search settings, one active memory plugin slot, and an independent Markdown memory-flush path, so the reported memory-management inconsistency remains unresolved.

## What This Changes

The issue asks OpenClaw to define a strict, predictable memory-management model so SQLite memory, QMD Markdown memory, disabled memory, and mixed storage do not vary confusingly across users.

## Best Possible Solution

Decide the canonical memory architecture first, then land a migration-backed simplification that makes active backend, plugin role, flush behavior, and storage location predictable in docs, doctor, setup, and runtime.

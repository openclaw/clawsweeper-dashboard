- `P2`: This is a real memory consistency and product/API problem with multiple affected users, but it is not a crash, data-loss emergency, or unusable core runtime.
- `impact:session-state`: The issue concerns durable memory storage, recall behavior, per-agent/workspace scope, and future session context.
- `impact:ux-friction`: Users can continue with configuration workarounds, but the split between builtin memory, QMD, plugins, memorySearch, and memoryFlush is confusing and support-heavy.

## Summary

Keep open: current main has improved part of the report by moving builtin indexes to per-agent SQLite, but it still exposes separate memory backend, memory plugin slot, memorySearch, QMD, and compaction memory-flush surfaces rather than the unified memory-management contract requested here.

## What This Changes

The issue asks for one predictable memory-management contract so builtin SQLite memory, QMD Markdown memory, disabled memory, and workspace-specific storage do not diverge across users.

## Best Possible Solution

Settle a maintainer-approved memory contract that defines backend selection, plugin role ownership, storage scoping, migration/doctor behavior, and docs, then land or replace the open role-slot and storage-scope slices under that design.

## Reproduction Assessment

Yes, at source level. Current main still has separate `memory.backend`, `plugins.slots.memory`, `agents.defaults.memorySearch`, and `agents.defaults.compaction.memoryFlush` surfaces, and no `memory.type` or equivalent unified built-in/QMD/mixed contract; I did not run the reporter's three-user live setup.

## Solution Assessment

Unclear as proposed. A `memory.type` field is a plausible user-facing simplification, but the best fix likely needs a broader maintainer-approved contract covering memory role slots, storage scoping, QMD/builtin parity, doctor migration, and docs.

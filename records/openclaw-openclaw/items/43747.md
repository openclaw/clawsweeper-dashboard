## Summary

Keep open: current main still exposes separate builtin/QMD backend selection, memory-search provider config, one active memory plugin slot, and an independent compaction memory-flush path, so the reported memory-management inconsistency is not resolved.

## What This Changes

The issue asks for OpenClaw memory management to behave consistently across users by defining a single, clear memory backend/config model.

## Best Possible Solution

Decide the canonical memory architecture first, then land a migration-backed simplification that makes the active backend, plugin role, flush behavior, and storage location predictable in docs, doctor, and runtime.

## Summary

Keep open: current main and v2026.6.11 still use fixed delivery-recovery backoff with no jitter or pacing between eligible outbound recovery sends. The report's concurrency wording is not quite right because `recoverPendingDeliveries` awaits entries serially, but the central stability gap remains valid and is not owned by the related Feishu/Telegram rate-limit items.

## What This Changes

The issue requests jittered exponential backoff for outbound pending-delivery recovery so startup replay does not burst queued channel sends after an outage.

## Best Possible Solution

Add a bounded, testable jitter or pacing policy at the shared delivery recovery backoff boundary, with no new config surface, and keep related channel-specific rate limiters/readiness fixes separate.

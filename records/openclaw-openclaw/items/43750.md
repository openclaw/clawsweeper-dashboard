## Summary

Keep open: current main and the latest stable release still route `/new` and `/reset` through the resolved route/current session target, so explicit multi-agent target selection remains missing and needs a product/security contract.

## What This Changes

Request targeted `/new` and `/reset` behavior for multi-agent channels, including explicit agent targeting and safer behavior when no target is specified.

## Best Possible Solution

Define one shared destructive-command target contract, then implement explicit target parsing, ambiguous-target handling, authorization, and cross-channel regression coverage together.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For destructive session commands in shared multi-agent channels, should OpenClaw require an explicit agent target, prompt for a target, or preserve route-derived defaults when `/new` or `/reset` has no target?

Rationale: The remaining work changes command UX and the cross-agent session mutation boundary, so automation should not choose the permanent target syntax, ambiguity behavior, or authorization policy.

Likely owner: steipete

Owner reason: The shared native-command session target resolver and recent shallow blame point to this owner path for a cross-channel command contract decision.

Owner confidence: medium

Options:

- **Require explicit target in ambiguous channels (recommended):** Require `/new` and `/reset` to name a valid agent when multiple agents can receive the command, and fail closed or prompt when the target is ambiguous.
- **Prompt/select target on bare commands:** Allow bare `/new` and `/reset` but show an in-product target chooser such as agent buttons plus an explicit all-agents option.
- **Keep route-derived default:** Document current route-derived behavior and only add optional targeted syntax, accepting that bare commands can still affect the resolved route target.

## Reproduction Assessment

Yes at source level: reset command tails are not parsed as agent targets, and native command targets are route-derived; I did not run a live multi-agent Discord or Telegram replay.

## Solution Assessment

Unclear until maintainers choose the contract; explicit targeting is the right direction, but a one-channel patch would be too narrow without shared target and authorization semantics.

## Summary

Keep open: current main still has no explicit user-selected agent target for `/new` or `/reset`; source, docs, release-tag inspection, and user comments all point to a real multi-agent session-control gap that needs a maintainer product/security decision before implementation.

## What This Changes

The issue requests explicit `@agent` targeting, safe no-target behavior, and channel-gating parity for `/new` and `/reset` in multi-agent channels.

## Best Possible Solution

Define one cross-channel destructive-command targeting contract, then implement explicit target selection, safe ambiguous-target handling, authorization checks, and regression coverage for shared native and text command routing.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What should `/new` and `/reset` do when more than one agent is eligible in a channel and the user does not specify a target?

Rationale: The source gap is clear, but the safe default, target syntax, and authorization model affect session ownership across Discord, Telegram, Slack, text commands, and native slash commands.

Likely owner: steipete

Owner reason: They introduced the shared native command target resolver and earlier native target-session behavior that this contract would extend.

Owner confidence: high

Options:

- **Require explicit target in ambiguous rooms (recommended):** Require an explicit agent/account target when multiple agents are eligible, and return a chooser or refusal when no target is provided.
- **Choose active agent by heuristic:** Pick the active or highest-context agent for no-target commands, improving convenience but risking surprising destructive resets.
- **Reset active participants together:** Reset all agents participating in the current thread, preserving group-room semantics but making broad reset behavior intentional.

## Reproduction Assessment

Yes, source-reproducible: `/new` and `/reset` have no structured target argument, Discord native commands pass the effective route target, and reset handling never parses `@agent` as a target.

## Solution Assessment

Unclear until maintainers choose the contract; explicit targeting is the right direction, but the best fix should be shared target and authorization semantics rather than ad hoc one-channel parsing.

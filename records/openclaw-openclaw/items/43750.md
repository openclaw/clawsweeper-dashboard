## Summary

Keep open: current main and the latest published stable/prerelease builds still route `/new` and `/reset` through resolved native command sessions, but they do not expose explicit `@agent` or native `agent:` targeting, and the safe no-target behavior needs maintainer product/security direction.

## What This Changes

Request `/new` and `/reset` support explicit agent targeting and safer defaults in shared multi-agent channels.

## Best Possible Solution

Define one explicit target contract for destructive session commands, add text/native agent targeting, and no-op or prompt when a multi-agent room has no unambiguous target.

Question: What should `/new` and `/reset` do in a multi-agent channel when no explicit agent target is supplied?

Rationale: Current code can carry native command target sessions, but choosing `@agent` syntax, native `agent:` parameters, and ambiguous no-target behavior affects session-state safety and command authorization semantics.

Owner confidence: high

Options:

- **Require Explicit Target In Multi-Agent Rooms (recommended):** Add text and native-command agent targeting, and make ambiguous destructive commands prompt or no-op instead of resetting a guessed agent.
- **Route First, Target Optional:** Keep current route/binding behavior as the default and add explicit agent targeting only as an override.
- **Document Channel Isolation Only:** Leave runtime unchanged and document dedicated channels, bindings, or per-account command naming as the supported workaround.

## Reproduction Assessment

Yes, source-level: current command definitions and native dispatch paths accept only generic input/tail text and derive `CommandTargetSessionKey` from route/binding rather than an explicit agent selector; no live multi-agent channel repro was run.

## Solution Assessment

Unclear until maintainers choose the command contract; the safest direction is explicit agent targeting with prompt/no-op ambiguity handling, implemented on existing `CommandTargetSessionKey` plumbing.

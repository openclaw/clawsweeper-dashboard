## Label Justifications

## Summary

Keep open: the July 22 follow-up reports the same silent failure-alert behavior on v2026.7.1-2, so this is not confined to the original 2026.6.5 SQLite migration. The related run-status report identifies a plausible shared path, but it does not replace this issue’s concrete requirement that an error-classified cron run must attempt its configured alert.

## What This Changes

Fix cron failure alerts so an error-classified run that reaches its configured consecutive-error threshold attempts notification and records the resulting delivery outcome.

## System Context

Cron runs produce a final status and persist run/state records in the cron store; when that status is an error, the cron service should evaluate the job’s failure-alert policy and send a channel notification. The resulting delivery outcome feeds cron history and the operator’s visibility of failed scheduled work.

## Architecture Diagram

flowchart LR
  A[Cron schedule] --> B[Job execution]
  B --> C[Final run outcome]
  C --> D[Persist cron run and state]
  D --> E[Evaluate failure-alert threshold]
  E --> F[Channel notification attempt]
  F --> G[Delivery status for operators]

## Best Possible Solution

Make failure-alert evaluation an explicit post-outcome cron-service step that attempts delivery for a final error result, records attempted versus failed delivery distinctly, and adds regression coverage for timeout, pre-execution, and recovered-tool-error outcomes.

## Summary

Keep open. A July 22 report reproduces the silent-alert behavior on the current v2026.7.1 release line after the failure threshold is met, so the issue is not resolved by the earlier SQLite migration or default-preservation fixes. The linked reports show a related but broader run-outcome problem; maintainers should define the final-error boundary and then repair alert dispatch at the cron owner boundary.

## What This Changes

Repair cron failure alerts so a job that reaches its configured consecutive-error threshold attempts its configured notification after a genuine final run error.

## System Context

Cron scheduling executes a job, derives its final outcome, persists run and job state in the shared SQLite store, and sends normal delivery plus an optional failure alert. This issue sits between final-error classification and the failure-alert send, affecting whether operators receive an actionable message when scheduled work fails.

## Architecture Diagram

flowchart LR
  A[Cron job configuration] --> B[Scheduled job run]
  B --> C[Final run outcome]
  C --> D[SQLite run and job state]
  C --> E[Failure-alert threshold]

  F --> G[Operator channel]
  D --> H[Cron status and diagnostics]

## Best Possible Solution

Make the cron owner attempt failure-alert delivery after an authoritative final error once the configured threshold is reached, persist the attempted outcome separately from primary delivery, and add regression coverage for ordinary timeouts, pre-execution failures, and recovered tool errors.

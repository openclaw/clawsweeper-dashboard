## Summary

This is a valid product-direction discussion, not a duplicate of the landed shared-gateway identity work. Current main has a durable identity model for trusted gateway users and channel-specific sender identity, but it does not establish whether channel identities should become a unified cross-channel account, authorization, and session-membership authority; that boundary needs an explicit maintainer decision.

Likely related people: `steipete` is the high-confidence routing candidate because the current shared-gateway identity program and its merged implementation train originate from that feature history.

## What This Changes

The issue proposes making identities supplied by messaging channels first-class inputs to OpenClaw’s multi-user model, with the Control UI serving as an optional enhancement rather than the primary identity entry point.

## System Context

OpenClaw channels receive messages and sender metadata, while the gateway owns authenticated connections, durable profiles, session attribution, presence, and participation rules. This proposal would change how channel identities enter that shared identity and authorization layer before sessions and UI clients consume it.

## Architecture Diagram

flowchart LR
  A[Messaging platforms] --> B[Channel sender identity]
  C[Trusted gateway clients] --> D[Gateway authentication]
  B --> E[Identity mapping and trust policy]
  D --> E
  E --> F[Profiles and session membership]
  F --> G[Agent sessions and authorization]
  F --> H[Control UI presence and collaboration]

## Best Possible Solution

Define a maintainer-owned identity-source contract that keeps the gateway as the authorization authority, accepts channel identities as verified claims only where each channel can provide them safely, and specifies profile linking, revocation, consent, and fallback behavior before adding channel-specific mappings.

Question: Should OpenClaw extend its shared-gateway identity model so selected channel identities can be linked to durable profiles and participate in authorization, or should channels remain transport-level sender attribution while trusted gateway authentication remains the only shared-user authority?

Rationale: This choice sets a long-lived trust, privacy, and authorization boundary across all channels; source evidence shows the existing system intentionally centralizes session enforcement in the gateway, but it does not choose the proposed channel-first product direction.

Likely owner: steipete

Owner reason: The current shared-gateway identity architecture and related implementation train are directly connected to this decision.

Owner confidence: high

Options:

- **Keep gateway authentication primary (recommended):** Retain channels as transport and sender-attribution surfaces, while continuing to use trusted gateway authentication for shared-user profiles and session authorization.
- **Design opt-in channel identity claims:** Create a scoped design for verified channel claims, explicit profile linking, and per-channel permission semantics without treating platform roles as universal authority.
- **Adopt channel-first identity:** Make platform identities the primary multi-user entry point, accepting the larger cross-channel authorization and recovery design program this requires.

## Risks / Open Questions

- Channel platform IDs, roles, and group membership have different stability, verification, revocation, and administrator semantics; treating them as direct session authority without a defined trust model could weaken the server-enforced participation boundary.
- Cross-channel account linking can create impersonation, account-recovery, and privacy problems unless the mapping and consent model is explicitly designed.
- The current channel sender-attribution seam may cover much of the requested visibility value without requiring channels to become a universal authorization source.

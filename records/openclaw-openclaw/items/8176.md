## Summary

Keep open: current main and v2026.6.11 still lack user-prompt replacement in the public prompt-hook contract, and no related implementation PR merged; the capability remains a valid but security-sensitive plugin API decision requiring explicit maintainer semantics.

## What This Changes

Add an explicit plugin hook result that can replace the submitted user prompt before additive context is applied across supported agent runtimes.

## Best Possible Solution

Define one security-gated replacement field on `before_prompt_build`, inherit it through legacy `before_agent_start`, use the established higher-priority-first override rule, then apply prepend/append context around the replacement consistently across embedded, CLI, and shared harness runtimes with explicit original-input provenance and regression coverage.

Rationale: The capability is technically feasible and vision-aligned, but it expands a public plugin security boundary and cannot be implemented safely without intentional precedence, provenance, and audit semantics.

Options:

- **Add gated replacement (recommended):** Add one prompt replacement result to `before_prompt_build`, inherit it through the legacy hook, use higher-priority-first precedence, preserve original-input provenance separately, and enforce `allowPromptInjection`.
- **Keep additive hooks only:** Reject replacement and retain additive context plus `before_agent_run` blocking as the supported plugin boundary.

## Reproduction Assessment

Yes, at source level. Current public types, documentation, tests, and embedded, CLI, and Codex-backed consumers support additive prompt context but expose no user-prompt replacement result.

## Solution Assessment

No, an embedded-runner-only `promptOverride` is not the best complete solution. The narrow maintainable design is one security-gated `before_prompt_build` replacement contract inherited by legacy `before_agent_start`, with shared precedence, provenance, and all-runtime behavior.

## Risks / Open Questions

- A replacement hook could silently change or remove user input after submission, so transcript, audit, diagnostics, and user-visible provenance expectations must be explicit.
- Multiple modifying plugins need a deterministic winner and event-evolution rule; otherwise lower-priority plugins may inspect stale text or competing replacements may drift across runtimes.
- Current harness logic identifies the original prompt with `promptInputRange`; replacement must define whether that range tracks submitted text, original user text, or becomes unavailable.
- Empty replacements, attachments, prompt-local image discovery, retries, context-engine projections, and additive prepend/append ordering need parity across embedded, CLI, Copilot-style harness, and Codex paths.

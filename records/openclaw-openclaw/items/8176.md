## Summary

Keep open: current main still has no public result field that replaces the submitted user prompt, and the existing prompt-mutation gate makes this a security-sensitive plugin API decision rather than a narrow bug fix. Likely routing candidates are EVA for the shared hook contract and vincentkoc for Codex-harness parity.

## What This Changes

Add a supported plugin-hook result that can replace the effective user prompt before it is submitted to the model.

## Best Possible Solution

Approve or reject a single typed `prompt` replacement result on `before_prompt_build`; if approved, define first-wins precedence, retain the existing prompt-injection trust gate, document audit semantics, and implement the same behavior in every supported harness with regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should enabled prompt-mutating plugins be allowed to replace the current user prompt, and if so what precedence, transcript/audit, and cross-harness semantics are acceptable?

Rationale: Current hooks deliberately expose additive prompt mutation behind an operator-controlled gate, but replacing the user’s input changes the plugin authority and needs an explicit durable contract before implementation.

Likely owner: EVA

Owner reason: The shared plugin hook type and merger are the central contract boundary for the decision.

Owner confidence: medium

Options:

- **Adopt a controlled replacement contract (recommended):** Add an explicit `prompt` result to `before_prompt_build`, gated by existing prompt-injection policy, with documented first-wins precedence and equivalent PI, CLI, and Codex behavior.
- **Keep hooks additive and use blocking:** Retain the current additive contract and direct plugins to `before_agent_run` blocking or context injection rather than allowing user-prompt rewriting.

## Reproduction Assessment

No; this is a feature request rather than an established broken contract. Source inspection high-confidently confirms that current hooks expose additive mutations only and cannot replace the prompt.

## Solution Assessment

No; the original legacy-only `promptOverride` proposal is not the best final shape because new plugins should use `before_prompt_build` and the behavior must be defined across all harnesses, not only the embedded runner.

## Summary

Keep open: current main and latest release still expose additive prompt/context hook mutations only, so plugins cannot replace the submitted user prompt. The remaining work is a maintainer-owned plugin API and security-boundary decision, not conservative cleanup.

## What This Changes

The issue requests a plugin hook result field that can replace the effective user prompt before an agent model call.

## Best Possible Solution

Choose one documented prompt-replacement contract, then implement it consistently across prompt-build runners with precedence rules, allowPromptInjection behavior, docs, and regression coverage.

- **Use broader LLM interception:** Defer this issue to an llm_input-style modifying hook if maintainers want prompt rewriting at the provider-boundary rather than the prompt-build boundary.
- **Reject prompt replacement:** Keep plugin prompt hooks additive-only and direct oversized-prompt mitigation to context-engine or provider-side limits instead.

Yes at source level: current hook result types, merge logic, docs, and embedded/CLI/harness prompt paths expose no prompt replacement field or behavior. I did not run a live agent repro because the missing API is directly visible in source.

## Solution Assessment

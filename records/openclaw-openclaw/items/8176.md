## Summary

Keep open: current main and the latest release still expose only additive prompt context and system-prompt hook fields, so plugins still cannot replace the submitted user prompt. This remains a public plugin API and security-boundary decision rather than conservative cleanup.

## What This Changes

Request to let plugin prompt hooks replace the submitted user prompt, not only prepend or append context.

## Best Possible Solution

Keep this as the canonical tracker until maintainers approve and document a user-prompt replacement contract for prompt-build/start hooks or explicitly choose a different interception boundary such as modifying LLM input hooks.

## Reproduction Assessment

Yes, source-level: current hook result types, merge logic, embedded runner, CLI runner, release tag, and docs all show additive context/system-prompt support but no user-prompt replacement path. A live provider run is not needed to prove the API gap.

## Solution Assessment

Unclear until maintainers decide the API and trust boundary. A replacement field is plausible, but the best implementation must settle naming, precedence, allowPromptInjection behavior, observability, and whether broader LLM-input hooks should own this instead.

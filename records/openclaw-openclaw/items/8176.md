## Summary

Keep open: current main and v2026.6.11 still support additive prompt context and system-prompt mutation only, not replacement of the submitted user prompt. The remaining work is a public plugin API and security-boundary decision, with direct implementation attempts closed unmerged and the broader LLM interception PR still open and conflicting.

## What This Changes

The issue asks for plugin hook results to replace the current user prompt before model submission, especially through legacy `before_agent_start` and the newer prompt-build path.

## Best Possible Solution

Keep this as the canonical tracker until maintainers approve and document a user-prompt replacement contract, or explicitly choose a different interception boundary such as modifying `llm_input` hooks.

## Reproduction Assessment

Yes, source-level: current hook result types, merge logic, embedded runner, CLI runner, Codex bridge, release tag, and docs all show additive context/system-prompt support but no user-prompt replacement path. I did not run a live provider scenario because the missing public API is directly visible in source.

## Solution Assessment

Unclear until maintainers decide the permanent API and trust boundary. A replacement field is plausible, but the best solution must settle naming, multi-plugin precedence, later-hook input visibility, `allowPromptInjection` behavior, observability, and overlap with modifying LLM hooks.

## Summary

Keep open: current main still exposes additive prompt/context and system-prompt hook fields only, so plugins still cannot replace the submitted user prompt through `before_prompt_build` or legacy `before_agent_start`. The remaining work is a plugin API and security-boundary decision; the direct implementation PRs are closed unmerged, and the broader LLM-interception PR is still open and conflicting.

## What This Changes

The issue requests a plugin hook result field that can replace the effective user prompt before the agent model call.

## Best Possible Solution

Keep this as the canonical tracker until maintainers approve and document a prompt replacement API across shared hook surfaces, or explicitly reject that capability.

## Reproduction Assessment

Yes, source-level: current hook result types, merge logic, embedded runner, CLI runner, Codex harness, and docs all show additive context/system-prompt support but no user-prompt replacement path. I did not run a live provider scenario because the feature gap is directly visible in source.

## Solution Assessment

Unclear as an implementation direction until maintainers decide the API and trust boundary. A replacement field is plausible, but the best implementation must settle naming, precedence, `allowPromptInjection` behavior, observability, and whether the broader LLM-input hook boundary should own this instead.

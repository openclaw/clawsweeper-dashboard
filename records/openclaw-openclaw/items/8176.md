## Summary

Keep open. Current main and the latest checked release still expose additive prompt/context hook mutations only, so the requested plugin user-prompt replacement capability remains missing and needs an explicit plugin API and security-boundary decision before implementation.

## What This Changes

The issue requests a plugin hook result field that can replace the current user prompt before the model call.

## Best Possible Solution

Define one documented prompt replacement contract across embedded, CLI, and Codex harness paths, with explicit merge precedence, allowPromptInjection filtering, regression tests, and docs.

## Maintainer Decision

Required: true

Question: Should OpenClaw add user-prompt replacement to the canonical before_prompt_build contract with legacy before_agent_start compatibility, or should this be handled only through a broader llm_input interception API?

Rationale: The source gap is real, but the permanent API shape controls plugin compatibility and a security-sensitive prompt mutation boundary that automation should not choose alone.

Likely owner: vincentkoc

Owner reason: They have the strongest recent history across the hook contract split and Codex prompt-hook parity surfaces.

Owner confidence: high

Options:

- **Add prompt-build replacement contract (recommended):** Extend before_prompt_build as the canonical plugin API, bridge legacy before_agent_start if desired, and enforce allowPromptInjection plus precedence across all runners.
- **Use broader LLM interception:** Resolve this through the llm_input/llm_output modifying hook direction and keep before_prompt_build additive-only.
- **Reject prompt replacement:** Keep plugins limited to additive context/system prompt changes and document full user-prompt replacement as intentionally unsupported.

## Reproduction Assessment

Yes at source level: current hook types, merge logic, runner paths, and docs expose only additive context/system prompt fields, so a plugin cannot replace the submitted user prompt today. I did not run a live plugin because the missing public field and runner branch are directly visible in source.

## Solution Assessment

Unclear until maintainers choose the API direction: a legacy-only promptOverride would be too narrow, while the best fix needs a documented canonical hook contract and security filtering across all runner surfaces.

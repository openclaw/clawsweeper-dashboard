## Label Justifications

- `P2`: This is a normal-priority plugin API enhancement with clear source evidence but no urgent regression, outage, or data-loss impact.
- `impact:security`: User-prompt replacement would expand the trusted plugin prompt-mutation boundary by allowing plugins to silently change model input.

## Summary

Keep open: current main and latest release still expose additive prompt context and system-prompt hook fields only, so plugins cannot replace the submitted user prompt through `before_prompt_build` or legacy `before_agent_start`. The remaining work is a public plugin API and security-boundary decision, not conservative cleanup.

## What This Changes

The issue requests a plugin hook result that can replace the submitted user prompt before the model call.

## Best Possible Solution

Keep this as the canonical tracker until maintainers either approve and document a user-prompt replacement contract across shared hook surfaces, or explicitly reject the capability in favor of another interception boundary.

## Reproduction Assessment

Yes, source-level: current hook result types, merge logic, embedded runner, CLI runner, Codex bridge, and docs all show additive context/system-prompt support but no user-prompt replacement path. I did not run a live provider scenario because the feature gap is directly visible in source.

## Solution Assessment

Unclear as an implementation direction until maintainers decide the API and trust boundary. A prompt replacement field is plausible, but the best implementation must settle naming, precedence, `allowPromptInjection` behavior, observability, and whether broader LLM-input hooks should own this instead.

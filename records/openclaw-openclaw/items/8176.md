## Summary

Keep open. Current main and v2026.6.11 still expose only additive user-context and system-prompt mutations, while every direct prompt-replacement PR is closed unmerged. The request is a valid, vision-aligned plugin API extension, but prompt authority, precedence, transcript handling, and cross-harness parity require an explicit maintainer security decision.

## What This Changes

Allow trusted prompt-build hooks to replace the effective user prompt before model submission.

## Best Possible Solution

Add a phase-specific replacement field to before_prompt_build, inherit it only for legacy before_agent_start compatibility, gate it with allowPromptInjection, define deterministic priority and transcript semantics, and apply it consistently before image loading, context budgeting, and submission in every supported harness.

Question: Should trusted prompt-mutating plugins be allowed to replace user input, and should that replacement affect only model-visible input or also the persisted user message?

Rationale: Source inspection establishes the missing capability, but code cannot safely choose the plugin authority, audit semantics, and multi-plugin precedence without maintainer intent.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Approve bounded replacement API (recommended):** Add replacement to before_prompt_build under allowPromptInjection, use explicit priority semantics, preserve safe audit metadata, and implement parity across Pi, CLI, and Codex.
- **Keep prompts additive-only:** Reject direct replacement and direct context-management plugins toward a separately approved full-context transformation or context-engine API.
- **Allow model-only replacement:** Permit replacement only for the outbound model input while retaining the original transcript, clearly documenting that this is truncation rather than durable redaction.

## Reproduction Assessment

Yes at source level: current hook types, merge logic, runners, and docs provide no path for a plugin-returned replacement prompt to reach the model. A live provider call was not needed to establish that contract gap.

## Solution Assessment

No, the original legacy-only minimal patch is not the best complete solution. The maintainable path is a before_prompt_build contract shared with legacy compatibility and implemented consistently across all harnesses with explicit security, precedence, and persistence semantics.

## Risks / Open Questions

- A replacement hook could silently alter or redact user instructions, so its authority must remain gated by allowPromptInjection and be visible in safe diagnostics.

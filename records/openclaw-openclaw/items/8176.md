## Summary

Keep open. Current main exposes additive prompt-build mutations but no public result field or merged runtime path that replaces the outgoing user prompt; the earlier implementation PRs are closed unmerged. This needs a maintainer decision because installed plugins would gain authority to silently replace user-originated content across every agent harness.

## What This Changes

Add a documented plugin-hook result that can replace the effective user prompt before an agent sends its model request, while preserving defined ordering with context additions.

## System Context

Prompt-build hooks let installed plugins add system or user-context text before an agent run. The resulting prompt is assembled by the PI, CLI, and Codex harnesses before it is submitted to a model, so a replacement contract must be consistent across those runtimes.

## Architecture Diagram

flowchart LR
  A[Incoming user prompt] --> B[Prompt-build hooks]
  B --> C[Hook result merge]
  C --> D[Prompt assembly]
  D --> E[PI CLI and Codex harnesses]
  E --> F[Model request]
  B --> G[Existing injection policy]

## Best Possible Solution

Approve or reject one primary `before_prompt_build` replacement field—preferably `prompt` rather than a parallel legacy-only name—then implement one documented precedence rule, apply the existing prompt-injection policy, and add parity coverage for PI, CLI, and Codex before legacy `before_agent_start` inherits it.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should installed plugins be allowed to replace the user-authored prompt through the shared prompt-build API, and if so what precedence and audit boundary should govern that authority?

Rationale: Current code has a mature additive hook seam, but full prompt replacement changes the security and user-intent contract rather than repairing an established broken behavior.

Likely owner: vincentkoc

Owner reason: Recent merged work owns the Codex prompt-build bridge that must remain contract-compatible with the shared hook API.

Owner confidence: high

Options:

- **Approve a scoped shared replacement field (recommended):** Add a single `prompt` field to the primary prompt-build result, enforce the existing prompt-injection policy, define deterministic precedence, and require PI/CLI/Codex parity tests.
- **Keep hooks additive and blocking only:** Reject user-prompt replacement and direct context-limit mitigation toward blocking, compaction, or owner-controlled preprocessing paths.
- **Defer pending an audited transformation design:** Pause the API until maintainers define plugin provenance, user visibility, and logging expectations for rewritten prompts.

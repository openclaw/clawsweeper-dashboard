## Summary

Keep open: current main and v2026.6.11 still expose additive prompt/context and system-prompt hook fields only, so replacing the submitted user prompt remains an unresolved security-sensitive plugin API decision.

## What This Changes

The issue requests a plugin hook result field that can replace the effective user prompt before model submission, with prepend/append context applied around the replacement.

## Best Possible Solution

Choose one documented prompt-replacement contract and implement it consistently across prompt-build runners with precedence rules, allowPromptInjection behavior, docs, and regression coverage.

- **Keep hooks additive-only:** Reject prompt replacement and direct oversized-prompt mitigation to context-engine, memory, blocking, or provider-side controls.

## Reproduction Assessment

Yes, at source level: current hook result types, merge logic, docs, and embedded/CLI/harness prompt paths expose no prompt replacement field or behavior. I did not run a live agent repro because the missing API is directly visible in source.

## Solution Assessment

Unclear as originally phrased: adding promptOverride only to legacy before_agent_start is too narrow. The maintainable solution should define the before_prompt_build contract, legacy compatibility, security filtering, and cross-runner behavior together, or intentionally route the capability to modifying llm_input.

## Label Justifications

## Summary

Keep open. Current main and v2026.7.1 still expose additive prompt mutations but no supported way to replace the submitted user prompt; the capability is useful, while its silent user-intent and cross-runtime effects require an explicit maintainer security-boundary decision.

## What This Changes

Allow prompt-build plugins to replace the effective user prompt before model submission.

## Best Possible Solution

Define one shared prompt-replacement contract for before_prompt_build, inherited by legacy before_agent_start, gated by allowPromptInjection and applied consistently across embedded, CLI, and Codex paths with deterministic precedence, audit visibility, documentation, and regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should an installed plugin with prompt-injection permission be allowed to replace user-authored prompt text, and if so what precedence and audit semantics must every agent harness enforce?

Rationale: The change grants plugins authority to silently alter user intent and expands a shipped plugin API across several runtimes; source inspection cannot determine the intended trust and observability boundary.

Likely owner: vincentkoc

Owner reason: The merged Codex prompt-hook work makes this person the strongest available cross-harness contract owner in the feature history.

Owner confidence: high

Options:

- **Approve constrained replacement (recommended):** Add a shared replacement field gated by allowPromptInjection, use deterministic first-wins precedence with evolved effective state, expose the mutation in diagnostics, and implement parity across all harnesses.
- **Reject plugin replacement:** Keep hooks additive and solve oversized current prompts through core-owned overflow detection, blocking, or an explicit user-visible retry/truncation flow instead.

## Reproduction Assessment

Yes at source level: register a before_prompt_build or legacy before_agent_start hook that attempts to return replacement prompt text and observe that the public result type, merger, and runners have no supported replacement path. A live provider failure was not rerun during this read-only review.

## Solution Assessment

Unclear pending maintainer approval. A shared replacement contract is narrower and more maintainable than runner-specific patches, but it is only the best solution if maintainers accept the silent prompt-rewrite security boundary.

## Summary

Keep open: current main and v2026.6.11 still expose additive prompt/context hook mutations only, so plugins cannot replace the submitted user prompt. The remaining work is a plugin API and security-boundary decision rather than conservative cleanup.

## What This Changes

The issue requests a plugin hook result field that can replace the effective user prompt before model submission.

## Best Possible Solution

Choose one documented prompt-replacement contract, then implement it consistently across prompt-build runners with precedence rules, allowPromptInjection behavior, docs, and regression coverage.

## Maintainer Decision

Rationale: This is a new plugin API that lets enabled plugins rewrite model-bound user input, so automation should not choose the trust boundary, precedence, audit behavior, or hook layer without maintainer intent.

Options:

- **Add prompt-build replacement (recommended):** Add a documented replacement field to before_prompt_build, carry it through legacy before_agent_start, enforce prompt-injection policy filtering, and cover embedded, CLI, and harness runners.
- **Use LLM interception:** Defer this issue to an llm_input-style modifying hook if maintainers want prompt rewriting at the provider boundary instead of the prompt-build boundary.
- **Reject prompt replacement:** Keep plugin prompt hooks additive-only and direct oversized-prompt mitigation to context-engine, memory, or provider-side controls.

## Reproduction Assessment

Yes, at source level: current hook result types, merge logic, docs, and embedded/CLI/harness prompt paths expose no prompt replacement field or behavior. I did not run a live agent repro because the missing API is directly visible in source.

## Solution Assessment

Unclear as proposed: adding promptOverride only to legacy before_agent_start is too narrow. The maintainable solution should define the before_prompt_build contract, legacy compatibility, security filtering, and cross-runner behavior together.

## Summary

Keep open: current main and v2026.6.11 still only allow additive prompt/context hook mutations, so replacing the model-bound user prompt remains a new plugin API and security-boundary decision.

## What This Changes

The issue requests a plugin hook result field that can replace the submitted user prompt before model submission, with context prepended to the effective prompt afterward.

## Best Possible Solution

Choose one documented prompt-replacement contract, then implement it consistently across embedded, CLI, and Codex-style prompt paths with precedence rules, allowPromptInjection filtering, docs, and regression coverage.

Options:

- **Add prompt-build replacement (recommended):** Add a documented replacement field to before_prompt_build, carry it through legacy before_agent_start, enforce prompt-injection policy filtering, and cover embedded, CLI, and Codex-style runners.
- **Use LLM interception:** Defer this issue to an llm_input-style modifying hook if maintainers want prompt rewriting at the provider-boundary instead of the prompt-build boundary.
- **Reject prompt replacement:** Keep plugin prompt hooks additive-only and direct oversized-prompt mitigation to context-engine, memory, or provider-side controls.

## Reproduction Assessment

Yes, at source level: the hook result types, merger, embedded runner, CLI runner, harness helper, and docs expose additive prompt/context mutations only and no user-prompt replacement field. I did not run a live agent repro because the missing API is directly visible in current source and the latest release tag.

## Solution Assessment

Unclear as proposed: promptOverride only on legacy before_agent_start is too narrow for the current hook architecture. The maintainable solution should define the before_prompt_build contract, legacy compatibility, security filtering, and cross-runner behavior together.

## Summary

Current main still lacks inbound WhatsApp call-event handling, and the merged outbound MeowCaller work is explicitly adjacent rather than a fix for this request. Keep the issue open for a maintainer decision because exposing caller identity, timing, group context, and retained contact activity creates new privacy, configuration, state, and public API contracts.

## What This Changes

Add opt-in ingestion of Baileys WhatsApp voice and video call events and expose sanitized call activity for contact-aware agent workflows.

## Best Possible Solution

Keep ingestion inside the bundled WhatsApp plugin, normalize only authorized minimum fields, expose a typed opt-in event to approved consumers, and leave durable contact history to a clearly owned SQLite-backed feature or plugin rather than silently mutating conversation sessions.

Options:

- **Ephemeral typed event (recommended):** Add a default-off sanitized WhatsApp-plugin event with existing access-control gates and no built-in persistence, allowing approved plugins to own contact history.
- **First-party call history:** Define a SQLite-backed call-activity model, query surface, retention policy, migration behavior, and user controls before implementation.
- **Do not expose calls:** Leave Baileys call activity unconsumed because the privacy and product value do not justify a new agent-visible activity surface.

## Reproduction Assessment

Yes at source level: Baileys exposes call events while the WhatsApp plugin has no inbound call-consumption path. No live-device call was performed, so this is source-reproducible rather than runtime-reproduced.

## Solution Assessment

No, not as unrestricted session fields or a destination-capable calls tool. The narrowest maintainable starting point is a sanitized, default-off, access-controlled typed event without implicit persistence; maintainers must separately approve retained queryable history.

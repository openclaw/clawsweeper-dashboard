## Summary

Current main still ignores inbound Baileys call events; the merged MeowCaller feature is outbound-only, and implementation should wait for a maintainer decision on consent, privacy, retention, and agent exposure.

## What This Changes

Add WhatsApp/Baileys inbound call-event detection so agents can account for call activity as contact, not only messages.

## Best Possible Solution

Add a separate default-off, WhatsApp-owned transient call-activity event with minimum-data sanitization and existing account/access boundaries; defer persistent contact history to a separately approved SQLite data-model design.

Question: Should inbound WhatsApp call activity be exposed as a transient default-off event, persisted as contact history, or remain unsupported?

Rationale: Source and dependency proof establish the feature gap, but privacy, consent, retention, and agent visibility are product choices that automation must not invent.

Likely owner: steipete

Owner confidence: high

Options:

- **Transient opt-in event (recommended):** Emit minimal sanitized call activity without persistence and keep outbound call permissions separate.
- **Persist contact history:** Design a queryable SQLite-backed activity model with retention, deletion, migration, and user controls.
- **Keep unsupported:** Decline call-event collection until the product value outweighs the privacy and maintenance cost.

## Reproduction Assessment

Yes. Current main has no production Baileys `call` consumer or agent exposure surface, while the exact pinned dependency declares the event and payload; a live linked-device call is needed later to validate an implementation, not to establish the gap.

## Solution Assessment

No. A raw listener plus a generic `trackCalls` option is incomplete because it does not separate inbound collection from outbound permission or define consent, sanitization, access control, deduplication, retention, and deletion semantics.

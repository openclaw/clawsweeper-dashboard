## Summary

Current main and the latest release still do not consume inbound Baileys call events. The feature belongs in the official WhatsApp plugin, but maintainers must first choose whether OpenClaw exposes transient call activity or retains durable contact history, because those designs have materially different privacy, identity, storage, and API contracts.

## What This Changes

Add opt-in ingestion of WhatsApp voice and video call events and expose sanitized call activity to agents.

## Best Possible Solution

Keep the feature WhatsApp-plugin-owned: add a default-off, sanitized call-event path that reuses account and sender-policy boundaries, and add durable SQLite-backed contact history only if maintainers explicitly approve its identity, retention, deletion, and public API contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should the WhatsApp plugin expose only transient sanitized call lifecycle events, or also retain durable per-contact call history for queries such as “contacted today”?

Rationale: Transient events can remain a narrow channel capability, while durable history requires decisions about consent, identity resolution, retention, deletion, storage ownership, configuration, and the agent-facing API.

Likely owner: steipete

Owner reason: They supplied the existing scope guidance and recently implemented the adjacent WhatsApp outbound-call capability.

Owner confidence: high

Options:

- **Transient events first (recommended):** Add a default-off sanitized plugin event or typed hook without retaining call history, and consider durable contact tracking separately after its privacy contract is designed.
- **Durable contact history:** Store normalized call activity in plugin-owned SQLite with explicit retention, deletion, deduplication, access-control, and query contracts in the same feature design.
- **Do not ingest calls:** Leave Baileys call events unconsumed because their communications metadata is outside the desired WhatsApp channel scope.

## Reproduction Assessment

Yes at source level: current main lacks an inbound Baileys call listener and corresponding normalized state or API surface, while the dependency exposes call events. A live WhatsApp call is still needed to validate real event ordering and payload behavior.

## Solution Assessment

No, directly adding ad hoc session metadata or a message action is not yet the best fix. The narrow maintainable path is a plugin-owned sanitized event contract first, with durable SQLite history only after explicit privacy and retention approval.

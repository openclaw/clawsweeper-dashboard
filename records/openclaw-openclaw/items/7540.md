## Summary

Current main still does not consume Baileys inbound call updates, and the merged outbound MeowCaller capability does not solve that gap. This remains valid WhatsApp-plugin work, but implementation should pause for a maintainer decision because transient events and durable per-contact history have materially different privacy, storage, identity, deduplication, and API contracts.

## What This Changes

Add opt-in handling of Baileys inbound WhatsApp call events and expose sanitized call activity for contact-aware agent behavior.

## Best Possible Solution

Add a separate disabled-by-default WhatsApp inbound-call setting, normalize only the minimum event facts, apply existing account, self-chat, DM/group, allowlist, and privacy boundaries, and emit transient plugin-local events; pursue durable SQLite contact history only through a separately approved design.

## Risks / Open Questions

- The upstream event exposes sensitive contact, phone, group, timing, video, and call-state metadata; collection must be minimized and opt-in.
- Baileys emits multiple status updates for a call, so durable state would require stable-ID deduplication and explicit terminal-state semantics.
- Durable per-contact history needs a canonical SQLite owner, retention policy, identity normalization, access controls, and query contract.
- A new generic plugin hook would become a compatibility-sensitive API surface; a WhatsApp-local event is safer unless cross-plugin consumers are explicitly required.

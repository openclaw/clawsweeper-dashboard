## Summary

Current main and v2026.6.11 still do not consume inbound Baileys call events. The work belongs in the bundled WhatsApp plugin, but maintainers must choose a privacy-safe event, retention, identity, configuration, and public API contract before implementation.

## What This Changes

Add inbound Baileys voice/video call-event handling to the WhatsApp plugin and make sanitized call activity available to agents.

## Best Possible Solution

Implement a WhatsApp-plugin-owned, opt-in normalized call-activity event with strict account and access-control filtering; prefer transient delivery first, and add durable per-agent SQLite history only if maintainers explicitly approve retention semantics and a documented query API.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should inbound WhatsApp call activity be exposed only as transient opt-in events, or should OpenClaw retain durable per-contact call history for later agent queries?

Rationale: The two designs have materially different privacy, identity-resolution, storage, migration, configuration, and public API contracts, which automation should not choose.

Likely owner: steipete

Owner reason: The current history and issue discussion connect this person most directly to WhatsApp channel architecture, call capability, and the required privacy boundary.

Owner confidence: high

Options:

- **Transient event surface (recommended):** Expose sanitized opt-in call events through a documented WhatsApp-owned hook or session-event contract without retaining historical activity.
- **Durable contact history:** Store normalized call activity in the per-agent SQLite database and define identity, retention, migration, and query semantics before implementation.
- **Decline inbound tracking:** Keep the existing message-only inbound model and leave relationship-history tracking to an external integration.

## Reproduction Assessment

Yes at source level: current main has no Baileys `call` listener, normalization path, or exposed call-activity contract, while the pinned dependency defines the event. This is a feature omission rather than a failing existing behavior reproduction.

## Solution Assessment

No, the issue's alternatives are not yet specific enough to be the best fix. A transient, opt-in WhatsApp-owned event surface is the narrowest safe first step; durable contact history should require a separate explicit retention and SQLite design decision.

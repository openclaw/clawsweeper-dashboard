## Label Justifications

- `P2`: This is a valid WhatsApp channel enhancement with clear source evidence, but it is not an urgent regression or blocked first-run path.
- `impact:session-state`: The missing event path means contact-history/session activity can miss WhatsApp calls when users expect call activity to count as contact.
- `impact:security`: Adding the event would expose sensitive WhatsApp call/contact activity, so access control, opt-in, and sanitization are central to the issue.

## Summary

Keep open: current main and the latest release still lack inbound Baileys WhatsApp `call` event handling. The merged MeowCaller work is useful related outbound-call support, but it explicitly does not satisfy this inbound call-event/contact-history request, and the remaining work needs product and security review before implementation.

## What This Changes

Requested support for subscribing to Baileys WhatsApp call events so inbound WhatsApp voice/video call activity can count as contact history.

## Best Possible Solution

Keep this open and implement the feature inside the WhatsApp plugin with an explicit opt-in, shared inbound admission/access-control rules, sanitized call-event normalization, a documented event/session/tool surface, focused tests, docs, and live WhatsApp proof before release.

## Reproduction Assessment

Yes, at source level: current main subscribes to WhatsApp message/connection events but not Baileys `call`, while the pinned Baileys package exposes that event. I did not run a live WhatsApp call during this read-only review.

## Solution Assessment

No, the issue’s minimal `sock.ev.on("call")` sketch is only a starting point. The best solution needs plugin-owned opt-in, privacy filtering, access-control reuse, normalized event/session semantics, and live proof.

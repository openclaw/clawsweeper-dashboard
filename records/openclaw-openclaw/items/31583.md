## Label Justifications

- `P1`: This is a confirmed regression in a real skill/auth-to-exec workflow with multiple user confirmations and a fragile secret workaround.
- `impact:security`: The issue concerns whether credential-shaped per-skill env vars may cross into executable subprocess environments.
- `impact:auth-provider`: The reported failure blocks CLI-backed skills from receiving auth material such as keyring passwords, API tokens, or account selectors.

## Summary

Keep open: current main and v2026.6.11 still block credential-shaped `skills.entries.<skill>.env` keys unless the skill metadata declares them, and the linked open fix path needs a security-boundary maintainer decision before landing.

## What This Changes

The issue asks OpenClaw to pass per-skill configured environment variables through to host exec subprocesses so CLI-backed skills can authenticate non-interactively.

## Best Possible Solution

Allow operator-configured per-skill env keys to reach host exec only through a documented, tested boundary that preserves the hard dangerous-env denylist, active-skill scoping, restoration, and redaction behavior.

Options:

- **Allow explicit per-skill config keys (recommended):** Treat keys explicitly configured under a skill entry as operator intent, keep the hard dangerous-env denylist, and require regression/redaction tests for credential-shaped names.
- **Require skill metadata declarations:** Keep current blocking behavior unless the skill declares the env key in metadata, and update docs/error messaging so users know how to make a key eligible.
- **Defer to a broader secrets design:** Leave this issue blocked until a wider SecretRef or sandbox-env contract settles credential delivery to executable tools.

Yes, source-reproducible: `GOG_KEYRING_PASSWORD` matches the sanitizer's credential-name block pattern, and current main only re-allows blocked names declared by skill metadata. I did not run a live Gog flow in this read-only review.

## Solution Assessment

Unclear until maintainers decide the security boundary. The likely narrow fix is to treat explicit `skills.entries.<skill>.env` keys as allowed sensitive keys while preserving hard dangerous-name blocking and adding focused regression tests.

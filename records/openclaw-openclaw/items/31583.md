## Summary

Keep open: current main and v2026.6.11 still block credential-shaped `skills.entries.<skill>.env` keys unless the skill metadata declares them, and the bundled `gog` skill does not declare `GOG_KEYRING_PASSWORD`. The remaining fix needs maintainer security/product review because the obvious broad allow conflicts with the related generic-exec secret-leak boundary.

## What This Changes

The issue asks for `skills.entries.<skill>.env` values such as `GOG_KEYRING_PASSWORD` to reach subprocesses spawned by the exec tool.

## Best Possible Solution

Define and land a narrow credential boundary that lets intended skill-owned CLI execution receive configured env values while preventing unrelated generic exec children from inheriting skill secrets.

## Maintainer Decision

Required: true

Question: Should OpenClaw automatically allow credential-shaped keys from `skills.entries.<skill>.env` into host exec, or require a narrower skill-owned credential delivery contract first?

Rationale: The reported behavior is source-reproducible, but the direct fix changes which executable child processes can receive secrets and conflicts with the related generic-exec secret-leak report.

Likely owner: joshavant

Owner confidence: high

Options:

- **Design the skill-owned boundary (recommended):** Preserve the user-visible skill env contract while routing credentials only to intended skill/plugin execution paths and stripping them from unrelated generic exec children.
- **Allow explicit config env broadly:** Treat operator-configured `skills.entries.<skill>.env` as consent to pass sensitive names into all host exec during that run, while still blocking dangerous host env names.
- **Patch bundled gog metadata only:** Declare `GOG_ACCOUNT` and `GOG_KEYRING_PASSWORD` for the bundled `gog` skill as a narrow repair, leaving arbitrary sensitive config keys blocked.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 build `allowedSensitiveKeys` only from skill metadata, while the bundled `gog` skill does not declare `GOG_KEYRING_PASSWORD`, so that configured key is blocked before exec can inherit it. I did not run the full Ubuntu/Telegram/gog live flow in this read-only review.

## Solution Assessment

Unclear. Passing all user-configured sensitive skill env keys to generic host exec would fix this symptom, but the safer maintainable solution needs an explicit skill-owned credential boundary that also addresses the related secret-leak issue.

## Summary

Keep open: current main and v2026.6.11 still block credential-shaped keys such as `GOG_KEYRING_PASSWORD` from `skills.entries.<skill>.env` unless the skill metadata declares the same key, and the remaining fix needs one maintainer-owned security boundary decision with the inverse secret-leak work.

## What This Changes

The issue asks for per-skill environment variables from `skills.entries.<skill>.env` to reach host `exec` subprocesses so CLI-backed skills can authenticate non-interactively.

## Best Possible Solution

Define one credential boundary where intended skill-owned CLI execution can receive its configured secrets, unrelated generic exec children do not inherit them, and docs/tests cover both the availability and leak sides.

## Reproduction Assessment

Yes, source-backed: configure `skills.entries.gog.env.GOG_KEYRING_PASSWORD`, use the bundled `gog` skill, and current main blocks that credential-shaped key before host `exec` can inherit it. I did not run the real `gog` flow because it requires live credentials.

## Solution Assessment

Unclear as a product/security decision: simply allowing every configured credential-shaped skill env key would fix the reported `gog` case but conflicts with the inverse requirement to keep skill secrets out of unrelated generic exec children.

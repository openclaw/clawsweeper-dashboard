## Summary

Keep open: current main and v2026.6.11 still block credential-shaped keys configured only in `skills.entries.<skill>.env`, and the remaining repair needs maintainer security-boundary judgment because an overly broad fix can re-open unrelated exec secret leakage.

## What This Changes

The issue reports that environment variables configured in `skills.entries.<skill>.env` are not reaching commands spawned through the `exec` tool.

## Best Possible Solution

Land a maintainer-approved narrow fix that lets explicitly configured active-skill env keys reach intended host skill execution while preserving dangerous host-env blocking and stripping skill secrets from unrelated generic exec children.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should explicitly configured credential-shaped keys under `skills.entries.<skill>.env` bypass the generic sensitive-name block for the active skill's host run while dangerous host override names and unrelated generic exec inheritance remain blocked?

Rationale: The docs and current source support the user's expected host-run env injection, but the repair changes a credential-to-exec security boundary and overlaps the inverse leak tracked in https://github.com/openclaw/openclaw/issues/78528.

Likely owner: Vincent Koc

Owner reason: Vincent Koc has the strongest recent merged history in the overlapping skill env and SecretRef repair path.

Owner confidence: high

Options:

- **Allow configured skill env secrets (recommended):** Permit only keys explicitly configured for the active skill to bypass the sensitive-name block, with tests for dangerous-name rejection and unrelated exec isolation.
- **Keep metadata-only sensitive allowlist:** Require skills to declare every sensitive env name in metadata and update docs or doctor guidance so arbitrary credential-shaped config env keys are not expected to work.
- **Design a new secret contract:** Defer the bypass and define a plugin or SecretRef execution contract for CLI skills that need headless auth.

## Reproduction Assessment

Yes. Source inspection shows env-only keys matching `_PASSWORD` or `_TOKEN` enter `pendingOverrides`, are rejected by `sanitizeEnvVars`, and are not re-allowed unless declared in skill metadata.

## Solution Assessment

Unclear until maintainers choose the security boundary. The narrowest maintainable fix is likely to trust only keys explicitly configured for the active skill while preserving dangerous-host-env and unrelated-exec leak protections.

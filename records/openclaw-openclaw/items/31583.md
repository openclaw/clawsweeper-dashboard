## Label Justifications

- `P1`: This is a real regression blocking credential-backed skill use for multiple users and skills, but it needs security review rather than emergency closure or automatic repair.
- `impact:security`: The issue and fix both sit on the boundary for passing credential-shaped values into subprocess environments.
- `impact:auth-provider`: The reported failure prevents configured auth/keyring/API credential env vars from reaching tools such as `gog`, Tavily, and similar skills.
- `impact:ux-friction`: Users can sometimes work around it with system env vars or wrapper scripts, but those paths are fragile and defeat per-skill scoped configuration.

## Summary

Keep open: current main and v2026.6.11 still only allow sensitive-looking skill env keys when the skill metadata declares them, while bundled `gog` does not declare `GOG_KEYRING_PASSWORD`; the linked fix PR is open but conflicting and changes a credential-to-exec security boundary.

## What This Changes

The issue asks for `skills.entries.<skill>.env` variables to be available to host subprocesses spawned by the `exec` tool, including credential-shaped names such as `GOG_KEYRING_PASSWORD`.

## Best Possible Solution

Land or sponsor a focused security-reviewed fix that treats explicit `skills.entries.<skill>.env` keys as trusted for host-run skill env while still blocking dangerous host/sandbox override names, with regression coverage for password/token-shaped keys and unchanged sandbox semantics.

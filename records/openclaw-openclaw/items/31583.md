## Summary

Keep open: current main and v2026.6.11 still block undeclared credential-shaped values from `skills.entries.<skill>.env`, including the reported `GOG_KEYRING_PASSWORD`, before host `exec` can inherit them. The remaining fix is real but needs maintainer security-boundary direction because broad admission can conflict with the related generic-exec secret-leak work.

## What This Changes

The issue asks for per-skill `skills.entries.<skill>.env` values, including credential-shaped keys, to be available to `exec` subprocesses used by skills.

## Best Possible Solution

Define and land a maintainer-approved credential boundary that lets intended skill-owned CLI executions receive configured env while keeping skill secrets out of unrelated generic `exec` children.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should sensitive keys explicitly configured in `skills.entries.<skill>.env` be admitted into host exec broadly, or only through a scoped skill/plugin-owned execution path?

Rationale: The reported availability regression is source-backed, but the obvious broad allow changes which child processes can receive secrets and overlaps the open generic-exec secret-leak issue.

Likely owner: joshavant

Owner reason: This choice sits on the SecretRef and host exec env security boundary where this person has the strongest recent history.

Owner confidence: high

Options:

- **Design scoped credential delivery (recommended):** Preserve the skill env contract by delivering credentials only to intended skill-owned execution paths and stripping them from unrelated generic exec children.
- **Allow explicit env broadly:** Treat operator-configured `skills.entries.<skill>.env` as consent for all admitted sensitive names to reach host exec during that run, with dangerous host names still blocked.
- **Patch gog metadata narrowly:** Declare `GOG_ACCOUNT` and `GOG_KEYRING_PASSWORD` for the bundled gog skill while leaving arbitrary sensitive configured keys blocked.

## Reproduction Assessment

Yes, source-backed. `GOG_KEYRING_PASSWORD` matches the shared sensitive-name block pattern, current main admits blocked skill env keys only from metadata, and the bundled `gog` skill does not declare that password env.

## Solution Assessment

Unclear. Broadly allowlisting configured sensitive skill env keys would fix this symptom, but the safer solution needs scoped credential delivery that also addresses the related generic-exec secret-leak boundary.

## Summary

Keep open: current main and v2026.6.11 still block credential-shaped keys configured only in `skills.entries.<skill>.env`, and the remaining repair is a security-sensitive credential-to-exec boundary with an open but conflicting fix candidate.

## What This Changes

The issue reports that environment variables configured under `skills.entries.<skill>.env` are not available to exec-spawned subprocesses, breaking skill CLI authentication on headless systems.

## Best Possible Solution

Land a maintainer-approved narrow credential boundary that allows intended active-skill host-run credentials while blocking dangerous env names and preserving unrelated generic exec secret isolation.

## Maintainer Decision

Rationale: The source and docs support the regression, but the repair changes a credential-to-exec boundary and must be reconciled with the open inverse secret-leak issue before automation can safely choose semantics.

Owner confidence: high

Options:

- **Scoped allow plus isolation (recommended):** Permit explicit active-skill configured env keys for intended skill-owned execution, keep dangerous host override names blocked, and prove unrelated generic exec children do not inherit those secrets.
- **Metadata-only allowlist:** Require skills to declare sensitive env names in metadata and update docs or doctor guidance so arbitrary credential-shaped `env` keys are not expected to work.
- **Defer to credential contract:** Pause this bypass until maintainers define a broader SecretRef or plugin-owned credential delivery contract for CLI skills that need headless auth.

## Reproduction Assessment

Yes, source-level: an env-only key matching `_PASSWORD` or `_TOKEN` enters `pendingOverrides`, is rejected by `sanitizeEnvVars`, and is not re-allowed unless declared in skill metadata. I did not run a live gog/VPS repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the security boundary. The narrowest maintainable direction is likely to trust only explicit active-skill configured keys for intended host-run use while preserving dangerous-host-env and unrelated-exec leak protections.

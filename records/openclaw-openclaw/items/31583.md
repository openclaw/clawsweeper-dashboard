## Label Justifications

- `P1`: This is an urgent regression for auth-dependent skill workflows on headless hosts, with multiple user confirmations and no merged fix in current main or v2026.6.11.
- `impact:security`: The issue is about whether configured secret values such as keyring passwords may flow into executable subprocess environments without being exposed elsewhere.
- `impact:auth-provider`: The failure blocks CLI authentication for skills that depend on env-provided credentials or keyring passphrases.
- `impact:ux-friction`: Affected users can proceed only through fragile wrapper scripts, system-level env moves, or broader security workarounds.

## Summary

Keep open: current `main` and v2026.6.11 still block credential-shaped values from `skills.entries.<skill>.env` unless skill metadata declares that env name, and the remaining fix needs a maintainer security-boundary decision because it overlaps generic `exec` secret-leak hardening.

## What This Changes

The issue asks for `skills.entries.<skill>.env` values such as `GOG_KEYRING_PASSWORD` to be available to skill-invoked host `exec` subprocesses.

## Best Possible Solution

Define a narrow skill-scoped host-exec env contract: explicit per-skill config env keys may satisfy that skill's own CLI subprocess needs, dangerous host override keys remain blocked, and unrelated generic `exec` paths continue stripping active skill secrets.

## Maintainer Decision

Kind: security_boundary

Question: Should explicitly configured `skills.entries.<skill>.env` keys that look like credentials be allowed into skill-owned host `exec` subprocesses, and how should that interact with generic `exec` secret stripping?

Rationale: The current code violates the documented host skill-env behavior for real users, but a broad fix changes when credential values enter executable child processes and can conflict with active hardening against skill secret leakage into unrelated generic `exec`.

Likely owner: steipete

Owner confidence: medium

Options:

- **Allow only skill-scoped exec env (recommended):** Permit user-configured per-skill env keys for that skill's own host exec context while keeping dangerous env names blocked and stripping skill secrets from unrelated generic exec children.
- **Require metadata declarations:** Keep credential-shaped configured names blocked unless the skill manifest declares them, then update the `gog` skill or its ClawHub package metadata and docs accordingly.
- **Keep fail-closed behavior:** Document that credential-shaped `skills.entries.<skill>.env` names are intentionally blocked and require top-level/system env or sandbox-specific env configuration.

## Reproduction Assessment

Yes, source-reproducible: `GOG_KEYRING_PASSWORD` matches the sensitive-name sanitizer while the `gog` skill does not declare that env key, so current `main` blocks it before host exec can inherit it. I did not run a live `gog` auth flow in this read-only review.

## Solution Assessment

Unclear until the security boundary is decided. The narrow best fix is not just adding all configured env keys to the allow set; it must preserve dangerous-key blocking and the generic `exec` secret-stripping boundary.

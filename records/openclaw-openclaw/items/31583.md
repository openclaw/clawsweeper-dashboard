## Label Justifications

- `P1`: This is a user-visible regression in skill authentication through exec that affects real Telegram/VPS users and multiple credential-backed skills.
- `impact:security`: The issue is about whether credential-shaped env vars can safely cross from skill config into executable child-process environments.
- `impact:auth-provider`: The broken path prevents auth material such as `GOG_KEYRING_PASSWORD`, `GOG_ACCOUNT`, API tokens, or SecretRef-backed keys from reaching the CLI that needs them.
- `impact:ux-friction`: Affected users can proceed only with fragile wrapper scripts, system-level env exports, or broader-scoped secrets outside the intended per-skill config.

## Summary

Keep open: current main and v2026.6.11 still block credential-shaped `skills.entries.<skill>.env` keys such as `GOG_KEYRING_PASSWORD` unless the skill metadata declares them, and an open linked fix PR is conflicting and unmerged.

## What This Changes

The issue requests that `exec` subprocesses spawned during skill host runs receive per-skill env vars, including credential-shaped keys like `GOG_KEYRING_PASSWORD`.

## Best Possible Solution

Land the linked PR or a maintainer-approved replacement that treats explicit `skills.entries.<skill>.env` keys as allowed for that active host-run skill env, preserves dangerous host-var hard blocks, and coordinates with the generic exec secret-stripping work in `https://github.com/openclaw/openclaw/issues/78528`.

Rationale: The requested behavior matches current docs and user reports, but it deliberately moves credential-shaped values across a process/exec boundary that overlaps an open secret-leak issue.

Likely owner: joshavant

Owner confidence: high

Options:

- **Allow explicit skill env with leak guard (recommended):** Keep the documented host-run skill env contract by allowing configured per-skill keys while preserving hard-blocked host vars and adding/keeping tests that unrelated generic exec children do not inherit skill secrets.
- **Require manifest-declared sensitive keys:** Only allow credential-shaped keys when the skill declares them through metadata, which is stricter but would require updating bundled and external skills such as `gog`.
- **Reject credential-shaped skill env injection:** Document that password/token-shaped skill env keys are intentionally blocked and require users to use another secret path, accepting the current GOG/headless VPS breakage.

## Reproduction Assessment

Yes, source-level: current main blocks `*_PASSWORD`, `*_TOKEN`, and `*_API_KEY` names unless the key is declared by skill metadata, and the bundled `gog` skill does not declare `GOG_KEYRING_PASSWORD`. I did not run a live `gog` command in this read-only review.

## Solution Assessment

Unclear as a final security shape. Allowing explicit configured env keys is the narrowest fix for the documented host-run behavior, but the best solution must also preserve the separate boundary that keeps skill secrets out of unrelated generic exec children.

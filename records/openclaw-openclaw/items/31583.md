## Summary

Keep open: current main and v2026.6.11 still block credential-shaped `skills.entries.<skill>.env` keys such as `GOG_KEYRING_PASSWORD` unless the skill metadata declares them, and the remaining fix needs a narrow security-boundary decision rather than automatic cleanup.

## What This Changes

The issue asks for per-skill `skills.entries.<skill>.env` variables to reach `exec` subprocesses so CLI-backed skills can authenticate non-interactively.

## Best Possible Solution

Define a narrow skill-scoped host-exec env contract: explicit per-skill config env keys may satisfy that skill's own CLI subprocess needs, dangerous host override keys stay blocked, and unrelated generic exec paths keep stripping active skill secrets.

- **Keep current fail-closed behavior:** Document that credential-shaped per-skill env names are intentionally blocked and require top-level/system env or sandbox-specific env configuration.

## Solution Assessment

Unclear until the security boundary is confirmed. The best fix is not a broad allow-all change; it should preserve dangerous-key blocking and keep skill-injected secrets out of unrelated generic exec environments.

## Summary

Keep open: current main and v2026.6.11 still block credential-shaped values from `skills.entries.<skill>.env` unless the skill declares those env names, and the bundled `gog` skill does not declare `GOG_KEYRING_PASSWORD`. The remaining fix needs maintainer security/product review because the obvious availability fix conflicts with the related generic-exec secret-leak boundary.

## What This Changes

The issue asks for per-skill environment entries, especially credential-shaped keys like `GOG_KEYRING_PASSWORD`, to be available to `exec` subprocesses during skill runs.

## Best Possible Solution

Define a maintainer-approved credential boundary that lets intended skill-owned CLI executions receive configured env while preventing unrelated generic `exec` children from inheriting skill secrets.

- **Allow explicit config env broadly:** Treat operator-configured `skills.entries.<skill>.env` as consent to pass sensitive names into all host exec during that run, with dangerous host env names still blocked.
- **Patch bundled gog metadata only:** Add declared env metadata for `GOG_ACCOUNT` and `GOG_KEYRING_PASSWORD` as a narrow bundled-skill repair, leaving arbitrary sensitive config keys blocked.

## Reproduction Assessment

Yes. Current main and v2026.6.11 build `allowedSensitiveKeys` only from skill metadata, while the bundled `gog` skill does not declare `GOG_KEYRING_PASSWORD`, so that configured key is blocked before `exec` can inherit it.

## Solution Assessment

Unclear. Passing all user-configured sensitive skill env keys to generic host exec would fix the symptom, but the safer maintainable solution needs an explicit skill-owned credential boundary that also addresses the related secret-leak issue.

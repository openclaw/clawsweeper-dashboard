## Summary

Keep open: current main and the latest release still block credential-shaped `skills.entries.<skill>.env` keys unless the skill declares them in metadata, and the remaining fix crosses a credential-to-exec security boundary with an open but conflicting linked fix PR.

## What This Changes

The issue asks OpenClaw to pass `skills.entries.<skill>.env` values, including credential-shaped keys, into host `exec` subprocesses used by skills.

## Best Possible Solution

Define and land a narrow skill-scoped host-exec env contract: explicit per-skill config env keys may satisfy that skill's own CLI subprocess needs, dangerous host override keys stay blocked, and unrelated generic exec paths keep stripping active skill secrets.

Options:

- **Allow skill-scoped exec env (recommended):** Permit user-configured per-skill env keys for that skill's own host exec context while keeping dangerous env names blocked and stripping skill secrets from unrelated generic exec.
- **Require metadata declarations:** Keep credential-shaped names blocked unless the skill manifest declares them, then update the `gog` skill metadata or package docs for this credential path.
- **Keep fail-closed behavior:** Document that credential-shaped per-skill env names are intentionally blocked and require top-level, system, or sandbox-specific env configuration.

## Reproduction Assessment

Yes. Source inspection shows `GOG_KEYRING_PASSWORD` matches the credential-name sanitizer and the bundled `gog` skill does not declare that key, so the configured value is blocked before host `exec` can inherit it; I did not run a live `gog` auth flow in this read-only review.

## Solution Assessment

Unclear until the security boundary is confirmed. The best fix is not a broad allow-all change; it should preserve dangerous-key blocking and keep skill-injected secrets out of unrelated generic exec environments.

## Summary

Keep open: current main and the latest release still block credential-shaped keys configured only in `skills.entries.<skill>.env`, while the remaining repair crosses a credential-to-exec security boundary and has unmerged related PR work.

## What This Changes

The issue reports that per-skill env values configured in `openclaw.json` are not inherited by host `exec` subprocesses, blocking CLI skill authentication on headless systems.

## Best Possible Solution

Land a maintainer-approved scoped credential boundary that lets only the active skill's explicitly configured env keys reach intended skill-owned host execution while dangerous host/runtime env names stay blocked and unrelated generic exec children do not inherit skill secrets.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should explicitly configured `skills.entries.<skill>.env` credential-shaped names bypass the generic sensitive-name block for that active skill's intended host execution, and what boundary prevents unrelated generic exec leakage?

Rationale: The report is source-reproducible and matches the docs, but the repair intentionally moves credential-shaped values into executable subprocess environments and overlaps the inverse open secret-leak issue.

Likely owner: joshavant

Owner reason: The remaining choice is a host-exec credential boundary, and this handle has the strongest inspected history on host env hardening plus the assigned inverse security issue.

Owner confidence: high

Options:

- **Admit scoped active-skill env secrets (recommended):** Permit only keys explicitly configured for the active skill to pass the sensitive-name check, keep dangerous host-env names blocked, and add tests for selected-skill delivery plus unrelated exec isolation.
- **Keep metadata-only sensitive allowlist:** Require skills to declare every credential-shaped env name in metadata and update docs or doctor guidance so arbitrary `skills.entries.*.env` credential names are not promised.
- **Defer to a new credential contract:** Keep the current sanitizer until maintainers define a SecretRef or plugin-owned credential path for CLI skills that need headless auth.

## Reproduction Assessment

Yes. Source inspection shows an env-only key matching `_PASSWORD` or `_TOKEN` enters `pendingOverrides`, is rejected by `sanitizeEnvVars`, and is not re-allowed unless declared in skill metadata.

## Solution Assessment

Unclear until maintainers choose the security boundary. The narrowest maintainable fix is likely to trust only explicitly configured keys for the active skill while preserving dangerous-host-env and unrelated-exec leak protections.

## Summary

Keep open: current main and the latest release still block credential-shaped `skills.entries.<skill>.env` keys unless the skill declares those names in metadata, and `gog` still does not declare `GOG_KEYRING_PASSWORD`. The remaining work is a credential-to-exec security boundary decision, not a conservative cleanup close.

## What This Changes

Issue #31583 asks for `exec` subprocesses to inherit environment variables configured under `skills.entries.<skill>.env`, including `GOG_KEYRING_PASSWORD`, for skill CLI authentication.

## Best Possible Solution

Define a maintainer-approved credential boundary that lets intended skill-owned CLI execution receive configured env while preventing unrelated generic `exec` children from inheriting skill secrets.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw automatically allow credential-shaped keys from `skills.entries.<skill>.env` into host `exec`, or require a narrower skill-owned credential delivery contract first?

Rationale: The reported bug is real, but the obvious broad allow changes which executable child processes can receive secrets and conflicts with the open generic-exec secret-leak boundary in #78528.

Likely owner: joshavant

Owner reason: The unresolved choice spans SecretRef handling and host exec env hardening, both tied to this person's recent commit history.

Owner confidence: high

Options:

- **Design the skill-owned boundary (recommended):** Preserve the user-visible skill env contract while routing credentials only to intended skill/plugin execution paths and stripping them from unrelated generic exec children.
- **Allow explicit config env broadly:** Treat operator-configured `skills.entries.<skill>.env` as consent to pass sensitive names into all host exec during that run, while still blocking dangerous host env names.
- **Patch bundled gog metadata only:** Declare the needed `gog` env names as a narrow bundled-skill repair and leave arbitrary sensitive config keys blocked.

## Reproduction Assessment

Yes, source-reproducible: current main and `v2026.6.11` build `allowedSensitiveKeys` only from skill metadata, while bundled `gog` lacks `GOG_KEYRING_PASSWORD`, so that configured key is blocked before exec can inherit it.

## Solution Assessment

Unclear: passing all user-configured sensitive skill env keys to generic host exec would fix the symptom, but the safer maintainable fix needs an explicit skill-owned credential boundary that also addresses #78528.

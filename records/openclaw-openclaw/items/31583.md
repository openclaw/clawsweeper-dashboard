## Summary

Keep open: current main and v2026.6.11 still block credential-shaped keys configured only in `skills.entries.<skill>.env`, while the needed repair changes a credential-to-exec security boundary that overlaps the inverse secret-leak issue.

## What This Changes

The issue requests that env vars configured under `skills.entries.<skill>.env` be inherited by `exec` subprocesses for the active skill.

## Best Possible Solution

Land a maintainer-approved narrow fix that trusts only explicitly configured env keys for the active skill, keeps dangerous host/runtime override names blocked, and proves both intended skill auth delivery and unrelated exec secret isolation.

- **Redesign the secret contract:** Defer this bypass and define a SecretRef or plugin-owned credential path for CLI skills that need headless auth.

Yes. Source inspection shows an env-only key matching `_PASSWORD` or `_TOKEN` enters `pendingOverrides`, is rejected by `sanitizeEnvVars`, and is not re-allowed unless declared in skill metadata.

## Solution Assessment

Unclear until maintainers choose the security boundary. The narrowest maintainable fix is likely to trust only keys explicitly configured for the active skill while preserving dangerous-host-env and unrelated-exec leak protections.

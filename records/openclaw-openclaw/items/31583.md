## Summary

Keep open: current main and latest stable release v2026.6.11 still block credential-shaped `skills.entries.<skill>.env` keys unless the skill metadata declares them, so the reported headless `gog` auth path remains broken and needs a maintainer-approved credential-to-exec boundary.

## What This Changes

The issue requests that per-skill env values such as `GOG_KEYRING_PASSWORD` be available to host `exec` subprocesses for CLI-backed skills.

## Best Possible Solution

Adopt a scoped boundary that admits only the active skill's explicitly configured env keys for intended host skill execution, keeps dangerous host/runtime env names blocked, and prevents unrelated generic exec children from inheriting other skill secrets.

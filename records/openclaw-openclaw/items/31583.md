## Summary

Keep open: current main and the latest release still block credential-shaped per-skill env keys such as `GOG_KEYRING_PASSWORD` unless the skill metadata declares them, and the remaining fix needs maintainer review because it changes a credential-to-exec security boundary.

## What This Changes

The issue reports that `skills.entries.<skill>.env` variables are not available to commands spawned through the agent `exec` tool, breaking auth-dependent skills such as `gog` on headless hosts.

## Best Possible Solution

Define a narrow skill-scoped host-exec env contract: explicitly configured per-skill env keys may satisfy that skill's own CLI subprocess needs, dangerous host override keys stay blocked, and unrelated generic exec paths keep stripping active skill secrets.

Options:

- **Allow only skill-scoped exec env (recommended):** Permit user-configured per-skill env keys for that skill's own host exec context while keeping dangerous env names blocked and stripping skill secrets from unrelated generic exec.
- **Require skill metadata declarations:** Keep credential-shaped names blocked unless the skill metadata declares them, then update the `gog` skill metadata or package docs for this credential path.
- **Keep fail-closed behavior:** Document that credential-shaped per-skill env names are intentionally blocked and require top-level/system env or sandbox-specific env configuration.

## Reproduction Assessment

Yes. Source inspection shows `GOG_KEYRING_PASSWORD` matches the credential-name sanitizer and the bundled `gog` skill does not declare that key, so the configured value is blocked before host `exec` can inherit it; I did not run a live `gog` auth flow in this read-only review.

## Solution Assessment

Unclear until the security boundary is confirmed. The best fix is not a broad allow-all change; it should preserve dangerous-key blocking and keep skill-injected secrets out of unrelated generic exec environments.

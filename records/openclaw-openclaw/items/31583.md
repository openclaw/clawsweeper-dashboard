## Summary

Keep open: current main and v2026.6.11 still reject credential-shaped keys configured only in `skills.entries.<skill>.env` unless the key is declared in skill metadata, and the open fix candidate is conflicting while the adjacent skill-secret leak boundary remains unsettled.

## What This Changes

The issue reports that per-skill environment variables configured under `skills.entries.<skill>.env` are not inherited by subprocesses spawned through the `exec` tool.

## Best Possible Solution

Land a maintainer-approved narrow fix that trusts only explicitly configured env keys for the active skill's host run, preserves dangerous host-env blocking, and proves both gog-like credential delivery and unrelated exec isolation.

- **Allow configured skill env secrets (recommended):** Permit keys explicitly present in the active skill config to pass the sensitive-name check, with tests for dangerous-name rejection, gog-like credential delivery, and unrelated exec isolation.
- **Keep metadata-only sensitive allowlist:** Require skills to declare each sensitive env name in metadata, then update docs or doctor guidance so users do not expect arbitrary credential-shaped `env` keys to work.
- **Define a separate credential contract:** Defer this bypass and design a SecretRef or plugin-owned credential path for CLI skills that need headless auth.

## Reproduction Assessment

Yes. Source inspection shows an env-only key matching `_PASSWORD` or `_TOKEN` enters `pendingOverrides`, is rejected by `sanitizeEnvVars`, and is not re-allowed unless declared in skill metadata.

## Solution Assessment

Unclear until maintainers choose the security boundary. The narrowest maintainable fix is likely to trust only keys explicitly configured for the active skill while preserving dangerous-host-env and unrelated-exec leak protections.

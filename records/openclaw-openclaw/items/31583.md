## Summary

Keep open: current main and latest release still block configured-only credential-shaped `skills.entries.<skill>.env` keys such as `GOG_KEYRING_PASSWORD`, while the remaining fix overlaps with an open inverse secret-leak boundary that needs maintainer security/product judgment.

## What This Changes

The issue reports that per-skill environment variables configured under `skills.entries.<skill>.env` are not inherited by subprocesses spawned through `exec`.

## Best Possible Solution

Make one maintainer-owned security boundary decision, then land a focused fix that admits intended skill-owned configured credentials while stripping unrelated active skill secrets from generic exec children.

## Reproduction Assessment

Yes from source: configure a credential-shaped key such as `skills.entries.gog.env.GOG_KEYRING_PASSWORD`; the sanitizer blocks it unless metadata declares the key. I did not run the live gog flow because the review is read-only and would require credentials.

## Solution Assessment

Unclear as a product/security decision: allowing user-configured sensitive keys matches the docs and report, but maintainers need to confirm the intended boundary versus requiring explicit skill metadata declarations.

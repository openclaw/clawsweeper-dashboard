## Summary

Keep open: current main and v2026.6.11 still block credential-shaped keys configured only in `skills.entries.<skill>.env`, and the remaining fix crosses the skill-secret-to-exec security boundary rather than being safe cleanup.

## What This Changes

The issue reports that per-skill environment variables configured under `skills.entries.<skill>.env` are not inherited by subprocesses spawned through the `exec` tool.

## Best Possible Solution

Land a maintainer-approved scoped fix that lets only the active skill's explicitly configured env keys pass the sensitive-name filter while dangerous host/runtime env names stay blocked and unrelated exec children do not inherit other skill secrets.

## Maintainer Decision

Question: Should explicitly configured `skills.entries.<skill>.env` credential-shaped names bypass the generic sensitive-name block for that active skill's host run, and what isolation boundary prevents unrelated exec leakage?

Rationale: The issue is source-reproducible and affects documented behavior, but the repair intentionally moves credentials into executable subprocess environments and overlaps an inverse secret-leak concern.

Options:

- **Admit scoped active-skill env secrets (recommended):** Permit only keys explicitly configured for the active skill to pass the sensitive-name check, keep dangerous host-env names blocked, and add tests for selected-skill delivery plus unrelated exec isolation.
- **Keep metadata-only sensitive allowlist:** Require skills to declare every credential-shaped env name in metadata and update docs or doctor guidance so arbitrary `skills.entries.*.env` credential names are not promised.
- **Defer to a new secret contract:** Do not change the current sanitizer until maintainers define a SecretRef or plugin-owned credential path for CLI skills that need headless auth.

## Reproduction Assessment

Yes. Source inspection shows an env-only key matching `_PASSWORD` or `_TOKEN` enters `pendingOverrides`, is rejected by `sanitizeEnvVars`, and is not re-allowed unless declared in skill metadata.

## Solution Assessment

Unclear until maintainers choose the security boundary. The narrowest maintainable fix is likely to trust only explicitly configured keys for the active skill while preserving dangerous-host-env and unrelated-exec leak protections.

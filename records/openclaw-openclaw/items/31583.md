## Summary

Keep open: current main still blocks credential-shaped variables that exist only in `skills.entries.<skill>.env`, and the issue has a protected `security` label plus an open linked candidate PR that needs maintainer security/product review before the credential-to-exec boundary changes.

## What This Changes

The issue reports that per-skill environment variables configured under `skills.entries.<skill>.env` are not inherited by subprocesses launched through the `exec` tool.

## Best Possible Solution

Adopt a maintainer-approved credential boundary that lets explicitly configured per-skill env keys reach the intended host skill/CLI execution path while preventing unrelated generic exec or external runtime children from inheriting active skill secrets.

## Reproduction Assessment

Yes, source-backed: a key present only in `skills.entries.<skill>.env` and matching the sanitizer’s `_PASSWORD` or `_TOKEN` pattern is blocked unless declared by skill metadata. I did not run a live `gog` reproduction in this read-only review.

## Solution Assessment

Unclear as a final product choice. The linked PR’s approach fixes the reported blocking, but the safe long-term fix needs maintainer approval for how skill secrets are scoped away from unrelated exec and external runtime children.

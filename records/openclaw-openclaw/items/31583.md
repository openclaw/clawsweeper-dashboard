## Summary

Keep open: current main and v2026.6.11 still block credential-shaped `skills.entries.<skill>.env` values unless the skill declares those env names, and the bundled `gog` skill does not declare `GOG_KEYRING_PASSWORD`. The remaining fix needs maintainer security/product judgment because the obvious broad allow conflicts with the related generic-exec secret-leak boundary.

## What This Changes

The issue requests that `skills.entries.<skill>.env` values, including credential-like keys such as `GOG_KEYRING_PASSWORD`, reach subprocesses launched through the `exec` tool.

## Best Possible Solution

Define a maintainer-approved credential boundary that lets intended skill-owned CLI execution receive configured env while preventing unrelated generic exec children from inheriting skill secrets.

## Maintainer Decision

Question: Should OpenClaw automatically allow credential-shaped keys from `skills.entries.<skill>.env` into host exec, or require a narrower skill-owned credential delivery contract first?

Rationale: The reported bug is real, but the obvious fix changes which executable child processes can receive secrets and conflicts with the open generic-exec secret-leak boundary in https://github.com/openclaw/openclaw/issues/78528.

Likely owner: joshavant

Owner reason: This decision spans SecretRef handling and host exec env hardening, both areas tied to this person's recent commit history.

Owner confidence: high

Options:

- **Design the skill-owned boundary (recommended):** Preserve the user-visible skill env contract, but route credentials only to intended skill/plugin execution paths and strip them from unrelated generic exec children.
- **Allow explicit config env broadly:** Treat operator-configured `skills.entries.<skill>.env` as consent to pass sensitive names into all host exec during that run, while still blocking dangerous host env names.
- **Patch bundled gog metadata only:** Add declared env metadata for `GOG_ACCOUNT` and `GOG_KEYRING_PASSWORD` as a narrow bundled-skill repair, leaving arbitrary sensitive config keys blocked.

## Reproduction Assessment

Yes. Source inspection shows current main and v2026.6.11 block `GOG_KEYRING_PASSWORD` before exec can inherit it because the key matches the credential pattern and the `gog` skill does not declare it in metadata.

## Solution Assessment

Unclear. Passing all user-configured sensitive skill env keys to generic host exec would fix this symptom, but the safer maintainable solution needs an explicit skill-owned credential boundary that also addresses the related secret-leak issue.

## Summary

Keep open: current main still blocks credential-shaped keys that are configured only in `skills.entries.<skill>.env`, and an open linked fix PR plus an open inverse secret-leak issue mean this needs maintainer security/product review rather than cleanup closure.

## What This Changes

The issue requests that `exec` subprocesses receive per-skill environment variables from `skills.entries.<skill>.env`, including credential-shaped keys needed by skill CLIs on headless hosts.

## Best Possible Solution

Adopt a maintainer-approved credential boundary that lets explicitly configured per-skill env keys reach intended host skill/CLI execution while stripping or scoping active skill secrets away from unrelated generic exec children.

## Reproduction Assessment

Yes, source-backed: a key present only in `skills.entries.<skill>.env` and matching the sanitizer's `_PASSWORD` or `_TOKEN` pattern is blocked unless declared by skill metadata. I did not run a live `gog` reproduction in this read-only review.

## Solution Assessment

Unclear as a final product choice: the linked PR fixes the reported blocking, but the open inverse leak issue shows maintainers need to approve the durable env-scoping boundary before landing that shape unchanged.

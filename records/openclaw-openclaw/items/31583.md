## Label Justifications

## Summary

Keep open: current main and v2026.6.11 still block credential-shaped `skills.entries.<skill>.env` keys unless the skill metadata declares them, and the remaining fix is a security-boundary decision with an open linked fix candidate rather than conservative cleanup.

## What This Changes

The issue requests that environment variables configured in `skills.entries.<skill>.env` be available to `exec` subprocesses, including credential-shaped keys such as `GOG_KEYRING_PASSWORD`.

## Best Possible Solution

A maintainer should choose the credential-to-`exec` policy, then land one narrow security-reviewed fix with docs and regression tests, or close in favor of a deliberate agent-scoped/trusted-exec env path.

## Maintainer Decision

Question: Should user-configured credential-shaped `skills.entries.<skill>.env` keys be trusted to reach host `exec` subprocesses for active skills, or should only metadata-declared or agent-scoped env paths be allowed?

Rationale: The current docs and user reports support env injection, but allowing arbitrary credential-shaped keys into generic exec children is a secret-exposure boundary that automation should not settle without maintainer intent.

Likely owner: joshavant

Owner confidence: medium

Options:

- **Allow explicit per-skill env to exec (recommended):** Treat keys explicitly configured under `skills.entries.<skill>.env` as trusted for that active skill run while still hard-blocking loader, path, and host-pivot env names, with regression tests and docs.
- **Require skill metadata declarations:** Keep credential-shaped keys blocked unless the skill declares them in metadata, then fix affected skills such as `gog` by declaring the required env names.
- **Use agent-scoped trusted exec env instead:** Do not broaden skill env inheritance; direct users to a narrower agent-scoped or trusted-exec credential path and update docs accordingly.

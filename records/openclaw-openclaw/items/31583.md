## Summary

Keep open: current main and v2026.6.11 still block configured credential-shaped skill env keys unless the skill metadata declares the same key, and an open fix path needs maintainer security/product judgment because it intersects the inverse secret-leak boundary.

## What This Changes

The issue reports that per-skill environment variables configured under `skills.entries.<skill>.env` are not inherited by subprocesses spawned through the `exec` tool.

## Best Possible Solution

Land or sponsor a narrow credential-boundary fix that lets operator-explicit `skills.entries.<skill>.env` reach the intended host-run skill/CLI execution path while keeping active skill secrets out of unrelated generic exec children.

## Reproduction Assessment

Yes from source inspection, but not from a live gog run: `GOG_KEYRING_PASSWORD` matches the sanitizer's credential-name pattern and is not allowed unless the skill metadata declares it as primary or required env.

## Solution Assessment

Unclear as a final product/security decision: adding configured env keys to the sensitive allowlist is the narrow availability fix, but the best solution also needs an explicit boundary for unrelated generic exec children.

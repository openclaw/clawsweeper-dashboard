## Label Justifications

- `impact:security`: The issue concerns whether configured secret values such as keyring passwords may flow into executable child-process environments without leaking elsewhere.
- `impact:auth-provider`: The failure blocks CLI authentication for skills that depend on env-provided credentials or keyring passphrases.
- `impact:ux-friction`: Affected users can proceed only through fragile wrapper scripts, system-level env moves, or broader credential workarounds.

## Summary

Keep open: current main and v2026.6.11 still block credential-shaped keys such as `GOG_KEYRING_PASSWORD` from `skills.entries.<skill>.env` unless the skill metadata declares that exact env name. The issue has open/unmerged related fixes, and the remaining choice is a security boundary decision rather than conservative cleanup.

## What This Changes

The issue asks OpenClaw to pass per-skill configured environment variables through to `exec` subprocesses so auth-dependent skill CLIs work on headless hosts.

## Best Possible Solution

Define a narrow skill-scoped host-exec env contract: explicit per-skill config env keys can satisfy that skill's own CLI subprocess needs, dangerous host override keys remain blocked, and unrelated generic exec paths continue stripping active skill secrets.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should explicitly configured `skills.entries.<skill>.env` keys that look like credentials be allowed into skill-owned host `exec` subprocesses, and how should that interact with generic exec secret stripping?

Rationale: The current code violates documented host skill-env behavior for real users, but a broad fix changes when credential values enter executable child processes and overlaps active secret-leak hardening work.

Likely owner: steipete

Owner reason: This choice spans documented skill env behavior and security defaults, and steipete has strong history on both the env sanitizer and public skill docs.

Owner confidence: high

Options:

- **Allow only skill-scoped exec env (recommended):** Permit user-configured per-skill env keys for the intended skill-owned host exec context while keeping dangerous env names blocked and stripping skill secrets from unrelated generic exec.
- **Require metadata declarations:** Keep credential-shaped names blocked unless the skill manifest declares them, then update the `gog` skill or package metadata and docs for required credential names.
- **Keep fail-closed behavior:** Document that credential-shaped `skills.entries.<skill>.env` names are intentionally blocked and require top-level/system env or sandbox-specific env configuration.

## Reproduction Assessment

Yes, source-reproducible: `GOG_KEYRING_PASSWORD` matches the sanitizer's credential-name block, while the `gog` skill does not declare that env key and the allow set is metadata-only. I did not run a live `gog` auth flow in this read-only review.

## Solution Assessment

Unclear until the security boundary is decided. The narrow best fix is not just adding all configured env keys to the allow set; it must preserve dangerous-key blocking and keep unrelated generic exec from receiving skill secrets.

## Summary

Keep open: current main and v2026.6.11 still block credential-shaped values from `skills.entries.<skill>.env` unless the skill metadata declares that exact env key, so the reported `GOG_KEYRING_PASSWORD` path remains broken. The issue has an open linked fix PR, but the remaining decision is security-sensitive because it must preserve intended skill credential delivery without leaking skill secrets into unrelated generic `exec` children.

## What This Changes

The issue requests that env vars configured under `skills.entries.<skill>.env` be available to host `exec` subprocesses so skill CLI authentication works on headless systems.

## Best Possible Solution

Define a narrow skill-scoped host-exec env contract: explicit per-skill configured env keys may reach the intended skill CLI subprocess, dangerous host override keys remain blocked, and unrelated generic exec paths strip active skill secrets.

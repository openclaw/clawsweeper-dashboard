## Summary

Keep open: current main still blocks credential-shaped keys that are configured only in `skills.entries.<skill>.env`, and the open fix path overlaps an inverse secret-leak boundary that needs maintainer security/product review.

## What This Changes

The issue requests that `exec` subprocesses receive documented per-skill environment variables from `skills.entries.<skill>.env`, including credential-shaped keys such as passwords and tokens.

## Best Possible Solution

Define and land a scoped credential boundary that lets explicitly configured per-skill env keys reach the intended host skill/CLI execution path while preventing unrelated generic exec children from inheriting active skill secrets.

## Reproduction Assessment

Yes. Source inspection shows a configured-only `skills.entries.<skill>.env` key matching `_PASSWORD` or `_TOKEN` is blocked by the sanitizer unless it is also declared in skill metadata; the issue discussion provides matching real-world logs.

## Solution Assessment

Unclear as a final product choice. The linked PR's allowlist idea addresses the immediate bug, but the best fix must also settle the inverse secret-leak boundary for unrelated generic `exec` children.

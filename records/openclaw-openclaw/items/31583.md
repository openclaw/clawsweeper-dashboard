## Summary

Keep open: current main and v2026.6.11 still block credential-shaped keys configured only in `skills.entries.<skill>.env`, and the remaining fix is a security-sensitive credential-to-exec boundary with an open linked fix candidate that needs maintainer review.

## What This Changes

The issue asks for `exec` subprocesses to inherit environment variables configured under `skills.entries.<skill>.env`, especially credential-shaped values used by headless skill CLI authentication.

## Best Possible Solution

Land a maintainer-approved narrow credential boundary that admits explicitly configured active-skill host-run env values, blocks dangerous names, and proves both intended skill CLI auth and unrelated generic exec isolation.

Yes, source-level: an env-only key matching `_PASSWORD` or `_TOKEN` enters `pendingOverrides`, is rejected by `sanitizeEnvVars`, and is not re-allowed unless declared in skill metadata. I did not run a live gog/VPS repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the security boundary. The narrowest maintainable fix is likely to trust only explicitly configured active-skill env keys while preserving dangerous-host-env and unrelated-exec leak protections.

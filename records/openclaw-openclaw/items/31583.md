## Summary

Keep open: current main still blocks credential-shaped keys that are only user-configured in `skills.entries.<skill>.env`, and the remaining fix overlaps an open inverse secret-leak boundary plus an open conflicting candidate PR that needs maintainer security/product review.

## What This Changes

The issue reports that per-skill environment variables from `skills.entries.<skill>.env` do not reach `exec` subprocesses, breaking CLI-authenticated skills on headless systems.

## Best Possible Solution

Adopt a maintainer-approved credential boundary that allows explicitly configured per-skill env keys to reach the intended host skill/CLI execution path while stripping or scoping active skill secrets away from unrelated generic exec children.

## Reproduction Assessment

Yes, source-backed: a key present only in `skills.entries.<skill>.env` and matching the sanitizer’s `_PASSWORD`/`_TOKEN` pattern is blocked unless declared by skill metadata. I did not run a live `gog` reproduction in this read-only review.

## Solution Assessment

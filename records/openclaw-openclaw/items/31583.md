## Summary

Keep open: current main and v2026.6.11 still block credential-shaped `skills.entries.<skill>.env` keys such as `GOG_KEYRING_PASSWORD` unless skill metadata declares the key, and the remaining fix needs a maintainer security-boundary decision.

## What This Changes

The issue asks for `exec` subprocesses to inherit explicit per-skill environment variables configured under `skills.entries.<skill>.env`.

## Best Possible Solution

Adopt a narrow security-reviewed fix that treats operator-configured `skills.entries.<skill>.env` keys as approved soft-sensitive overrides while preserving hard blocks for dangerous host/runtime-control env keys.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should explicit `skills.entries.<skill>.env` keys bypass the soft credential-name block for host exec inheritance when hard dangerous-host env blocks still win?

Rationale: The source-level fix is small, but it defines which operator-configured secrets may enter subprocess environments and therefore needs maintainer security-boundary intent.

Likely owner: mcaxtr

Owner reason: Recent adjacent work on sensitive skill env allowlisting and sandbox env security makes this the strongest available routing signal.

Owner confidence: medium

Options:

- **Allow explicit skill env keys (recommended):** Treat keys explicitly listed in `skills.entries.<skill>.env` as operator-approved soft-sensitive overrides, while keeping `NODE_OPTIONS`, loader hooks, shell startup hooks, and similar hard blocks unbypassable.
- **Require skill metadata declarations:** Keep the current behavior and require skills to declare every credential-shaped env key in `primaryEnv` or `requires.env`, then update docs and diagnostics.
- **Move secrets outside skill env:** Declare per-skill credential env injection unsupported for credential-shaped keys and direct users to host process env, SecretRef-backed config, or plugin-owned auth flows.

## Reproduction Assessment

Yes from source, not from a live run: `GOG_KEYRING_PASSWORD` matches the credential-name filter and is dropped unless the skill metadata declares that key.

## Solution Assessment

Unclear until maintainer security intent is confirmed. The best narrow fix appears to be allowing explicit per-skill config env keys through the soft sensitive-name block while preserving hard dangerous-host env blocks and adding regression coverage.

## Summary

Keep open: current main and v2026.6.11 still block credential-shaped keys configured only in `skills.entries.<skill>.env`, and the remaining fix needs maintainer security/product direction because the inverse skill-secret leak boundary is also open.

## What This Changes

The issue asks for per-skill environment variables from `skills.entries.<skill>.env` to be inherited by `exec`-spawned subprocesses so CLI-backed skills can authenticate headlessly.

## Best Possible Solution

Land a maintainer-approved narrow fix that treats explicitly configured per-skill env keys as allowed for that active host run while blocking dangerous names and proving no unrelated exec or cross-skill leakage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should explicitly configured `skills.entries.<skill>.env` credential-shaped names bypass the generic sensitive-name block for that skill's host run while dangerous host override names and cross-skill isolation remain enforced?

Rationale: The documented host-run env behavior and user reports support delivery, but this is also the same credential boundary as open secret-leak work, so automation cannot safely choose the permanent semantics.

Likely owner: vincentkoc

Owner reason: This handle has the strongest recent history in the overlapping skill env, runtime snapshot, and SecretRef repair path.

Owner confidence: high

Options:

- **Allow configured skill env secrets (recommended):** Permit keys explicitly listed under the active skill's config to pass the sensitive-name check, with tests for dangerous-name rejection, snapshot behavior, and cross-skill isolation.
- **Keep metadata-only allowlist:** Require each skill to declare every sensitive env name in metadata and update docs or doctor diagnostics so users do not expect arbitrary credential-shaped `env` keys to work.
- **Move to a different secret contract:** Defer the env bypass and design a SecretRef or plugin-owned credential path for CLI skills that need headless auth.

## Reproduction Assessment

Yes. Source-level reproduction is high confidence: an env-only key matching `_PASSWORD` or `_TOKEN` enters `pendingOverrides`, is rejected by `sanitizeEnvVars`, and is not re-allowed unless declared in skill metadata.

## Solution Assessment

Unclear until maintainers choose the security boundary. The narrowest maintainable fix is likely to trust only keys explicitly configured for the active skill while preserving dangerous-host-env and cross-skill leak protections.

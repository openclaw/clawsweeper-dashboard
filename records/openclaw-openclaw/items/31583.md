## Label Justifications

- `P1`: This regression blocks authenticated CLI-backed skill workflows for real users on headless hosts until they apply fragile workarounds.
- `impact:security`: The issue is about whether configured secret values may flow into executable subprocess environments.
- `impact:auth-provider`: The failure prevents skill authentication variables such as keyring passwords, API tokens, and account selectors from reaching CLI tools.
- `impact:ux-friction`: Affected users can proceed only through wrapper scripts, system-level env moves, or broader secret exposure workarounds.

## Summary

Keep open: current main and v2026.6.11 still block credential-shaped `skills.entries.<skill>.env` keys unless the skill metadata declares them, so the reported host `exec` auth break remains a real security-boundary issue.

## What This Changes

The issue asks for per-skill `skills.entries.<skill>.env` variables to reach `exec` subprocesses so CLI-backed skills can authenticate without wrapper scripts.

## Best Possible Solution

Define a narrow skill-scoped host-exec env contract: explicit per-skill config env keys may satisfy that skill's CLI subprocess needs, dangerous host override keys stay blocked, and unrelated generic exec paths do not gain extra secret reach.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should explicitly configured `skills.entries.<skill>.env` keys that look like credentials be allowed into skill-owned host `exec` subprocesses without matching skill metadata?

Rationale: The current code conflicts with documented host skill-env behavior for real users, but the fix changes a credential-to-executable-process boundary.

Likely owner: steipete

Owner reason: This is primarily a security-boundary choice around the sanitizer and host exec credential behavior, where steipete has direct history.

Owner confidence: high

Options:

- **Allow explicit per-skill secrets (recommended):** Treat keys explicitly configured under `skills.entries.<skill>.env` as operator-approved for that skill, while continuing to block dangerous host env names and adding regression coverage.
- **Require metadata declaration:** Keep the current metadata-only allowlist and require skill packages to declare every credential-shaped env var they need.
- **Keep fail-closed and document it:** Document that credential-shaped per-skill env names are intentionally blocked unless declared, leaving wrapper or broader env setup as the supported path.

## Reproduction Assessment

Yes, source inspection gives a high-confidence path: a configured `GOG_KEYRING_PASSWORD` enters `pendingOverrides` but is blocked because it matches the credential-name sanitizer and is not in metadata `primaryEnv` / `requires.env`. I did not run a live `gog` auth flow in this read-only review.

## Solution Assessment

Unclear until maintainers decide the security boundary. The narrow maintainable fix should be skill-scoped and preserve dangerous-host-env blocking, not broadly allow every credential-shaped override into generic exec.

## Summary

Keep open for maintainer review: the patch is a narrow owner-local hardening change, but the 16 MiB fail-closed threshold intentionally changes existing OpenAI and Azure realtime voice behavior and needs explicit maintainer acceptance before merge.

## What This Changes

The PR adds a module-local 16 MiB `maxPayload` constant and passes it to the OpenAI realtime voice backend WebSocket constructor.

## Best Possible Solution

Merge this owner-local cap only after maintainers accept 16 MiB as the intended hard realtime voice threshold, or tune the constant before merge from representative vendor-frame evidence.

## Reproduction Assessment

Yes, source-level: current main constructs the OpenAI realtime voice backend WebSocket without `maxPayload`, and `ws` 8.21.0 defaults that client option to 100 MiB. The PR body supplies after-fix loopback output showing an oversized frame rejected with close status 1009; I did not run a live OpenAI or Azure oversized-frame session.

## Solution Assessment

Yes for the implementation shape: setting `maxPayload` at the owner-local OpenAI voice WebSocket constructor uses the dependency's built-in enforcement and avoids new config surface. The unresolved question is whether 16 MiB is the right maintained threshold for supported realtime voice sessions.

## Summary

This remains necessary: the report gives a concrete macOS reproduction against `imsg` 0.5.0, while the current iMessage guidance still treats `imsg status --json` as part of private-API probing without documenting a minimum compatible imsg version. The cited Full Disk Access report is a separate macOS permission-context problem, not a duplicate capability-negotiation failure.

## What This Changes

Make the bundled iMessage channel handle an imsg installation whose command surface does not include `status`, either through compatible capability detection or a clear supported-version diagnostic.

## System Context

The bundled iMessage plugin starts `imsg rpc` as a stdio bridge for normal messaging and uses a separate private-API probe to decide whether advanced iMessage actions are available. Channel status feeds that probe result to operators and determines which native actions the plugin can advertise.

## Architecture Diagram

flowchart LR
  A[iMessage channel config] --> B[imsg CLI path]
  B --> C[RPC bridge for messages]
  B --> D[Private API capability probe]
  D --> E[Channel status output]
  D --> F[Advertised advanced actions]
  C --> G[Inbound and outbound messages]

## Best Possible Solution

Keep normal iMessage RPC messaging independent of the advanced-action probe, then make the probe detect an unsupported `status` command and emit an actionable minimum-version/update message unless maintainers explicitly choose to support imsg 0.5.0 through another documented capability path.

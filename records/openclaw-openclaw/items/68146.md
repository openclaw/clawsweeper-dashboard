## Label Justifications

- `P2`: This is a normal-priority Gateway startup hardening PR with limited blast radius and no data-loss or security emergency signal.
- `merge-risk: 🚨 compatibility`: Existing clients and operators that expect immediate retryable startup errors for gated RPCs would instead observe a server-held wait or timeout.
- `merge-risk: 🚨 availability`: The PR intentionally keeps startup-gated requests pending on the server for up to 20 seconds, which can increase queued work if sidecars stall or clients reconnect in a burst.

## Summary

Keep open: current main still fail-fasts startup-gated RPCs, while this PR adds a distinct server-side wait that is not implemented on main and carries compatibility/availability tradeoffs that need maintainer acceptance and exact-head proof.

## What This Changes

The PR adds a Gateway StartupGateBarrier, threads it through request context and post-attach startup, and tests wait, timeout, non-gated, and no-barrier dispatch paths.

## Best Possible Solution

Refresh the branch, preserve current descriptor-derived gateway dispatch, add exact-head restart proof, and land only if maintainers choose the bounded server-side wait over relying on shipped client retries or the broader core-ready contract.

## Reproduction Assessment

Yes for the source-level server behavior: current main immediately returns retryable UNAVAILABLE while a method is in unavailableGatewayMethods. I did not reproduce the full cached Control UI restart flow on this exact PR head.

## Solution Assessment

Conditionally yes: a Gateway-owned barrier is the right layer for cached pre-retry clients, but shipped clients already retry the common symptom. The merge path still needs exact-head proof plus maintainer acceptance of the bounded server-side wait.

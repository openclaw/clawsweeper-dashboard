## Label Justifications

- `P2`: This is a normal-priority Gateway startup hardening PR with limited blast radius and no data-loss or security emergency signal.
- `merge-risk: 🚨 compatibility`: Existing clients and operators that expect immediate retryable startup errors for gated RPCs would instead observe a server-held wait or timeout.
- `merge-risk: 🚨 availability`: The PR intentionally keeps startup-gated requests pending on the server for up to 20 seconds, which can increase queued work if sidecars stall or clients reconnect in a burst.

## Summary

Keep open: current main does not implement this server-side startup wait, and the PR still contains a meaningful unique Gateway mitigation. It is not merge-ready until the dirty branch is refreshed, exact-head real behavior proof is supplied, and maintainers accept the startup timing tradeoff.

## What This Changes

The PR adds a Gateway startup barrier so startup-gated RPCs can wait for post-attach sidecar readiness before falling back to retryable startup unavailability.

## Best Possible Solution

Refresh the branch, preserve descriptor-derived startup gating, add exact-head restart proof, and land only if maintainers choose the bounded server-side wait over relying on shipped client retries or a broader core-ready contract.

## Reproduction Assessment

Yes for the source-level server behavior: current main immediately returns retryable UNAVAILABLE while a method is in unavailableGatewayMethods. I did not reproduce the full cached Control UI restart flow on this exact PR head.

## Solution Assessment

Conditionally yes: a Gateway-owned barrier is the right layer for cached pre-retry clients, but current clients already retry the common symptom. The best merge path needs exact-head proof plus maintainer acceptance of the bounded server-side wait.

## Label Justifications

- `P2`: This is a normal-priority Gateway startup race hardening PR with limited blast radius and no data-loss or security emergency signal.
- `merge-risk: 🚨 compatibility`: Existing clients that expect immediate retryable startup errors for gated RPCs would instead wait for the server-side barrier or timeout.

## Summary

Keep open for maintainer review: current main still fail-fasts startup-gated Gateway RPCs on the server, but shipped client retry paths already address the linked startup error, so this server-side wait is compatibility-sensitive hardening that needs branch refresh, exact-head proof, and maintainer acceptance.

## What This Changes

This PR adds a Gateway startup barrier that holds startup-gated RPCs for up to 20 seconds until post-attach sidecar readiness, threads it through request context, and adds focused unit tests.

## Best Possible Solution

Refresh the branch, preserve the descriptor-derived method set and current live-registry dispatch behavior, and land the bounded server-side wait only if maintainers accept the residual cached-client upgrade hardening after exact-head proof.

## Reproduction Assessment

Yes. Current-main source shows startup-gated RPCs return immediate retryable UNAVAILABLE while the unavailable set is populated, and the linked logs show the 0 ms chat.history failure during the post-ready sidecar window; this read-only review did not run a live restart repro.

## Solution Assessment

Conditionally yes. A Gateway-owned barrier is the right layer for cached pre-retry clients, but current releases already have client retries, so the remaining question is whether maintainers want the server-side timing tradeoff.

## Label Justifications

- `P2`: This is a normal-priority Gateway startup race hardening PR with limited blast radius and no data-loss or security emergency signal.
- `merge-risk: 🚨 compatibility`: Existing clients and operators that expect immediate retryable startup errors for gated RPCs would instead observe a server-held wait or timeout.
- `merge-risk: 🚨 availability`: The PR intentionally keeps startup-gated requests pending on the server for up to 20 seconds, which can increase queued work if sidecars stall or clients reconnect in a burst.

## Summary

This PR should stay open for maintainer review rather than cleanup-close: current main and the latest release still fail-fast startup-gated gateway RPCs, while the PR adds a distinct server-side wait that is not already implemented. It is not merge-ready because the branch is currently conflicting, the full restart-while-tab-open proof is not from this exact head, and the up-to-20-second server-held wait is a compatibility and availability tradeoff maintainers need to accept.

## What This Changes

The PR adds a Gateway startup barrier that holds startup-gated RPCs until post-attach sidecar readiness or a 20-second timeout, threads it through request context, and adds focused unit coverage.

## Best Possible Solution

Refresh the branch, preserve current descriptor-derived gateway dispatch semantics, and land the bounded server-side wait only if maintainers accept the startup timing tradeoff after exact-head real behavior proof.

## Reproduction Assessment

Yes for the current-main server behavior: source and tests show startup-gated RPCs return immediate retryable UNAVAILABLE while the unavailable set is populated. The full cached-Control-UI restart flow is not reproduced on this exact PR head, so live confidence is still limited.

## Solution Assessment

Conditionally yes: a gateway-owned barrier is the right layer for cached pre-retry clients, but current releases already have client retries. Maintainers still need to accept the server-side startup timing tradeoff and require exact-head proof.

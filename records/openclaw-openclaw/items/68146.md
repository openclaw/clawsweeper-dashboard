## Label Justifications

- `P2`: This is a normal-priority Gateway startup race hardening PR with limited blast radius and no data-loss or security emergency signal.
- `merge-risk: 🚨 compatibility`: Existing clients and operators that expect immediate retryable startup errors for gated RPCs would instead observe a server-held wait or timeout.
- `merge-risk: 🚨 availability`: The PR intentionally keeps startup-gated requests pending on the server for up to 20 seconds, which can increase queued work if sidecars stall or clients reconnect in a burst.

## Summary

Keep open: current main still returns immediate startup UNAVAILABLE from the Gateway server, so the PR’s server-side hold is not implemented on main. It is not merge-ready because the branch is currently conflicting, the exact-head real restart proof is insufficient, and maintainers need to accept the startup timing tradeoff now that shipped clients already retry the common symptom.

## What This Changes

The PR adds a Gateway startup barrier that holds startup-gated RPCs until post-attach sidecar readiness or a 20-second timeout, threads it through request context and post-attach startup, and adds focused unit coverage.

## Best Possible Solution

Refresh the branch, preserve current descriptor-derived Gateway dispatch semantics, and land the bounded server-side wait only if maintainers accept the startup timing tradeoff after exact-head real behavior proof.

## Reproduction Assessment

Yes for the source-level server behavior: current main immediately returns retryable UNAVAILABLE while a method is in unavailableGatewayMethods, and existing tests assert that fail-fast path. The full cached Control UI restart flow has not been reproduced on this exact PR head.

## Solution Assessment

Conditionally yes: a Gateway-owned barrier is the right layer for cached pre-retry clients, but current clients already retry the common symptom. The safer merge path is exact-head proof plus maintainer acceptance of the bounded server-side wait.

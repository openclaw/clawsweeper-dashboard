## Summary

Keep open: current main still has the reported Workboard dispatch cap and sequential start loop, and no duplicate or merged PR owns the maxStarts configurability request. The issue is valid, but the persistent config and parallel-spawn parts need maintainer scope/resource-policy review before an automated fix lane should take it.

## What This Changes

The issue requests making Workboard dispatch maxStarts configurable through CLI/RPC/config and parallelizing per-card worker starts.

## Best Possible Solution

Expose maxStarts through Workboard CLI/RPC with the default cap of 3 preserved, add focused dispatch concurrency and parameter-threading tests, and add persistent config only if maintainers approve that policy surface.

## Reproduction Assessment

Yes. Source inspection on current main shows dispatchAndStartWorkboardCards accepts maxStarts internally while the CLI and gateway entry point do not expose it, and the start loop awaits each selected card sequentially.

## Solution Assessment

Unclear. CLI/RPC threading with the default cap preserved looks like the narrowest safe first step, but persistent config and Promise.all-style spawning should be explicitly accepted because they change resource and operator-policy behavior.

## Summary

Keep this issue open. Current main still stores one leaf-certificate fingerprint per iOS gateway, and both initial trust and certificate-change recovery replace that single value; an anycast endpoint presenting another CA-valid leaf can therefore recreate the mismatch immediately. The report is credible, high impact, and needs an explicit endpoint-identity and migration decision rather than an automated patch.

## What This Changes

Fix the iOS Remote Domain connection loop where Cloudflare anycast leaf-certificate changes repeatedly invalidate the saved TLS pin after the user accepts the new certificate.

## Best Possible Solution

Use platform CA and hostname validation for CA-valid Remote Domain endpoints while retaining explicit fingerprint trust for self-signed or private discovery routes, with a narrow migration for existing saved leaf pins and tests covering alternating valid edge certificates.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What identity should the iOS app trust for a CA-valid Remote Domain endpoint whose reverse proxy or anycast service can present multiple legitimate leaf certificates?

Rationale: Choosing between platform PKI, leaf or SPKI pin sets, and strict single-leaf pinning changes the security boundary and determines how existing persisted pins must migrate; source inspection cannot safely infer that product policy.

Likely owner: ngutman

Owner reason: They introduced the current certificate-rotation recovery behavior and are the closest historical owner of this exact decision surface.

Owner confidence: high

Options:

- **Split Trust By Route (recommended):** Use platform CA and hostname validation for CA-valid Remote Domain endpoints, retain explicit pinning for self-signed or discovered private gateways, and migrate existing manual-domain pins after successful system validation.
- **Persist A Pin Set:** Keep explicit pinning but store a bounded set of accepted leaf or SPKI identities with an intentional rotation and expiry policy.
- **Keep Strict Leaf Pinning:** Continue requiring one exact leaf fingerprint and explicitly document Cloudflare anycast and rotating reverse proxies as unsupported.

## Reproduction Assessment

Yes at source level: current main persists and reconnects against one exact leaf fingerprint, so alternating valid edge certificates necessarily recreate the mismatch. A live latest-build Cloudflare reproduction has not yet been captured.

## Solution Assessment

No, unconditionally disabling pinning or repeatedly replacing one leaf pin is not the best fix. The maintainable solution is a route-aware trust contract that distinguishes publicly CA-valid domains from self-signed or private gateways and includes persisted-state migration coverage.

## Summary

Keep this issue open. Current main still binds an iOS manual TLS endpoint to one leaf-certificate fingerprint, and accepting a mismatch replaces that single value before reconnecting; an anycast hostname presenting another valid leaf can therefore recreate the blocking loop immediately. The remaining fix requires an explicit security-boundary decision rather than routine bug automation. citeturn7view0

## What This Changes

Fix the iOS Remote Domain connection loop caused by leaf-certificate pin changes across Cloudflare Tunnel/Access anycast edges.

## Best Possible Solution

Define separate TLS identity modes: preserve explicit leaf pinning for discovered or self-signed gateways, while manual public-DNS endpoints use system CA and hostname validation plus an authenticated gateway identity established during pairing; add regression coverage that alternates valid leaf certificates without accepting an untrusted certificate. citeturn7view0

Question: What identity contract should iOS Remote Domain mode use when a manually entered hostname has a valid system-trusted TLS chain but its leaf certificate changes between connections?

Rationale: The current fingerprint also helps classify the endpoint as trusted for credential fallback, so replacing leaf pinning cannot be decided safely as a mechanical certificate-handling fix.

Likely owner: mbelinky

Owner reason: The repository routes both iOS and security ownership to this person, matching the decision surface. citeturn2search4

Owner confidence: high

Options:

- **Separate public-CA trust mode (recommended):** Use CA and hostname validation for manually entered public domains, retain leaf pinning for discovered or self-signed endpoints, and bind gateway identity through authenticated pairing.
- **Retain strict leaf pinning:** Keep the current security model and explicitly document rotating or anycast TLS terminators as unsupported for Remote Domain mode.
- **Support managed pin rotation:** Keep pinning but introduce a narrowly defined multi-pin or rotation protocol, accepting the additional migration and lifecycle complexity.

## Reproduction Assessment

Yes at source level: when one hostname presents certificate A, then B, then A, the controller persistently stores only the most recently accepted fingerprint and rejects the next different leaf. A live Cloudflare/device run was not performed. citeturn7view0

## Solution Assessment

No—the report's blanket switch to CA-chain validation is not sufficient because the pin also participates in trusted-endpoint credential behavior. The safer solution is an explicit endpoint-specific identity model with fresh-install and upgrade tests. citeturn7view0

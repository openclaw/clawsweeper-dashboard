## Summary

Keep this issue open. Current main still treats one leaf-certificate fingerprint as the identity of every manual TLS endpoint, and accepting a rotation only replaces that single fingerprint, so a Cloudflare anycast hostname can immediately present another valid leaf and recreate the blocking loop. The report identifies a real security-sensitive iOS bug, but maintainers must choose the Remote Domain trust boundary before implementation.

## What This Changes

Fix the iOS Remote Domain connection loop where Cloudflare anycast leaf-certificate changes repeatedly invalidate the saved TLS pin.

## Best Possible Solution

Make Remote Domain use hostname verification plus the system CA trust chain while retaining explicit fingerprint pinning for discovered, direct, or self-signed gateway routes; migrate existing Remote Domain pins deliberately and provide an in-app recovery choice rather than requiring reinstall, config edits, or support intervention.

Question: Should iOS Remote Domain mode identify the gateway by its hostname and system-trusted certificate chain, while direct/discovered gateway modes continue using an explicitly approved certificate fingerprint?

Rationale: The current single-leaf identity cannot represent Cloudflare anycast, but globally disabling pinning would undo intentional security hardening and alter how trusted transport protects credential recovery.

Likely owner: ngutman

Owner reason: The most directly relevant merged history is the existing iOS rotated-certificate recovery implementation, with mbelinky and steipete providing broader iOS and security-boundary context.

Owner confidence: medium

Options:

- **Separate trust by connection mode (recommended):** Use system CA and hostname validation for Remote Domain, retain explicit fingerprint pinning for direct/discovered or self-signed gateways, and migrate stored Remote Domain trust state.
- **Add a trust-mode selector:** Keep fingerprint pinning as the default and let users explicitly choose system Web-PKI trust for reverse-proxy or anycast domains, at the cost of additional setup surface.
- **Keep leaf pinning only:** Document Cloudflare anycast and similar rotating-edge services as unsupported, preserving the current security boundary but leaving this remote-use path blocked.

Yes at source level: configure an iOS manual TLS endpoint whose hostname can return alternating system-trusted leaf certificates, accept the first replacement, and observe the next leaf fail against the newly stored single fingerprint. ## Solution Assessment

No, replacing pinning everywhere with generic CA-chain validation is too broad. The narrow maintainable fix is to define Remote Domain as a normal hostname-verified Web-PKI route while preserving explicit gateway pinning where it remains the intended identity boundary.

- Removing leaf pinning for every iOS connection would weaken the deliberate gateway-identity boundary and could expose stored credentials or device-token recovery to an endpoint trusted only by the public Web PKI.

- Changing the trust mode requires defined upgrade behavior for existing Remote Domain endpoints and stored pins so users are neither silently downgraded nor left in the same recovery loop.

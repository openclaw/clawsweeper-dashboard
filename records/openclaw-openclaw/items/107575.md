## Summary

Keep this issue open. Current main still binds each manual iOS TLS endpoint to one leaf-certificate fingerprint; trusting a replacement stores only the newly observed leaf, so a Cloudflare anycast hostname alternating between valid edge certificates can immediately recreate the blocking loop. Replacing that pin requires a security-owned endpoint-identity and migration decision rather than an automated patch. ([github.com](https://github.com/openclaw/openclaw/blob/main/apps/ios/Sources/Gateway/GatewayConnectionController.swift))

## What This Changes

Fix the iOS Remote Domain certificate-pin mismatch loop for Cloudflare Tunnel/Access anycast certificates.

## Best Possible Solution

Validate the system CA chain and requested hostname for public remote domains, then bind the paired connection to authenticated gateway identity rather than one rotating leaf certificate; migrate existing pins through an explicit in-app confirmation and include a visible Fix/Trust recovery flow with rotation and impersonation regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For CA-valid manual remote domains, should iOS replace single-leaf pinning with hostname validation plus authenticated gateway-identity binding, and how should existing stored pins migrate?

Rationale: The leaf pin is an intentional anti-impersonation boundary, but it is not a durable identity for an anycast TLS terminator; automation cannot safely choose its replacement or upgrade semantics.

Likely owner: ngutman

Owner reason: This contributor authored the current rotated-certificate recovery behavior and is the closest feature-history owner for the immediate decision.

Owner confidence: high

Options:

- **Bind domain and gateway identity (recommended):** Use system CA/hostname validation plus the authenticated paired gateway identity, with an explicit migration confirmation for existing pins.
- **Support a bounded pin set:** Allow several explicitly trusted leaf fingerprints per endpoint, accepting continued rotation-management complexity and weaker durability.
- **Keep single-leaf pinning:** Retain the current boundary and explicitly document Cloudflare Tunnel/Access anycast endpoints as unsupported for iOS Remote Domain mode.

## Reproduction Assessment

Yes from source: a manual hostname stores one leaf fingerprint, and trusting a mismatch replaces it with only the latest leaf, so alternating valid edge certificates recreate the mismatch. This read-only review did not perform a live Cloudflare/iPhone run.

## Solution Assessment

No, removing pinning without a replacement identity boundary is not the best fix. The narrow maintainable direction is CA/hostname validation combined with authenticated gateway-identity binding and an explicit stored-pin migration.

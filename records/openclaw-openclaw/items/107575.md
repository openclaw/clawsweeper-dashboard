## Summary

Keep this issue open. Current main still binds each manual iOS TLS endpoint to one leaf-certificate fingerprint; trusting a replacement stores only the newly observed leaf, so an anycast hostname alternating between valid edge certificates can immediately recreate the blocking loop. The remaining fix requires an explicit endpoint-identity decision because removing the pin without a replacement identity boundary could weaken the security hardening that introduced explicit TLS trust. ([github.com](https://github.com/openclaw/openclaw/blob/main/apps/ios/Sources/Gateway/GatewayConnectionController.swift))

## What This Changes

Make iOS Remote Domain connections work through Cloudflare Tunnel/Access when the hostname presents different system-trusted edge certificates.

## Best Possible Solution

Separate transport trust from gateway identity: use system hostname/CA validation for explicitly entered public domains while cryptographically binding the paired gateway identity at the protocol layer, retain leaf pinning for discovered or self-signed gateways, migrate existing pins visibly, and prove the result against alternating Cloudflare edge certificates.

Kind: security_boundary

Question: What identity boundary should iOS enforce for manually entered public WSS domains whose system-trusted leaf certificates legitimately vary across connections?

Rationale: The current leaf pin is incompatible with anycast certificate pools, but removing it without a replacement application-identity check changes the protection established by prior iOS TLS hardening.

Likely owner: mbelinky

Owner reason: The repository identifies this person with both iOS and security ownership, and their merged history covers the central connection and TLS enforcement path.

Owner confidence: high

Options:

- **Bind gateway identity (recommended):** Use normal system TLS for manual public hostnames and additionally verify the paired gateway's durable application identity across reconnects and certificate changes.
- **Allow multiple leaf pins:** Persist a bounded user-approved pin set, which reduces immediate loops but remains brittle across provider-wide certificate rotation and requires eviction policy.
- **Keep strict leaf pinning:** Document Cloudflare-style anycast TLS as unsupported and preserve the current security model at the cost of blocking this remote connection mode.

## Reproduction Assessment

Yes at source level: connect a manual TLS endpoint that alternates between two hostname-valid, system-trusted leaf certificates; each trust action replaces the sole stored pin, so the other leaf fails on the next connection. A live Cloudflare-backed run was not performed in this read-only review.

## Solution Assessment

No, repeatedly replacing one leaf fingerprint is not the best fix for an anycast certificate pool. The narrow maintainable solution is system TLS for the public hostname plus durable application-layer gateway identity, while preserving stronger pinning for self-signed and discovery paths.

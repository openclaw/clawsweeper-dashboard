## Summary

Keep this issue open. Current main persists one leaf-certificate fingerprint per gateway and rejects a different leaf even when iOS system trust succeeds; accepting the rotated certificate replaces that single value, so an endpoint alternating valid edge certificates can immediately re-enter the mismatch loop.

**Likely related people**
- `ngutman` — high confidence; introduced the existing rotated-certificate recovery path.
- `mbelinky` — medium confidence; authored adjacent iOS security and mandatory-TLS work.
- `steipete` — medium confidence; recent contributor across the iOS gateway controller and pairing architecture.

## What This Changes

Correct the iOS Remote Domain certificate-mismatch loop encountered when a Cloudflare anycast endpoint alternates between multiple valid TLS leaf certificates.

## Best Possible Solution

Separate transport trust from gateway identity: use normal iOS CA validation for public WSS transport while cryptographically verifying the paired gateway's stable application identity across reconnects; if that boundary is not yet available, adopt a bounded, user-reviewed multi-pin transition policy rather than repeatedly replacing one leaf pin.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For iOS Remote Domain connections through publicly trusted reverse proxies, should gateway identity move from one TLS leaf pin to the paired gateway's stable application identity, or should the app retain a bounded multi-pin TOFU policy?

Rationale: Both viable fixes alter the security contract: CA-only transport validation requires a separate authenticated gateway identity, while multi-pin TOFU expands and manages the set of certificates accepted for an endpoint.

Likely owner: mbelinky

Owner reason: Their history is most directly associated with the iOS security stack and mandatory TLS policy surrounding this choice.

Owner confidence: medium

Options:

- **Bind gateway identity (recommended):** Use platform CA validation for public WSS and verify the stable identity established during gateway pairing on every connection.
- **Bounded multi-pin TOFU:** Persist a small user-approved pin set with explicit replacement, expiry, and removal semantics for rotating or anycast endpoints.
- **Keep single-leaf pinning:** Preserve the current security boundary and explicitly document Cloudflare-style anycast Remote Domain endpoints as unsupported.

## Reproduction Assessment

Yes at source level with high confidence: alternate two system-trusted leaf certificates for one stable gateway ID; trusting either replaces the sole stored pin, and reaching the other deterministically produces another mismatch. A controlled live iOS reproduction would confirm the reported Cloudflare environment.

## Solution Assessment

No, CA-only validation by itself is not the best fix because it discards the existing TOFU identity check. The maintainable solution should verify a stable paired-gateway identity independently of rotating public TLS leaves, with bounded multi-pin trust as a possible interim design.

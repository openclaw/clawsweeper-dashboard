## Summary

Keep this issue open. Current main still uses one leaf-certificate fingerprint as the identity of a manually configured iOS gateway, so accepting one valid Cloudflare edge certificate does not prevent the next edge from presenting a different valid leaf and recreating the blocking loop.

## What This Changes

Make iOS Remote Domain connections remain usable when a Cloudflare Tunnel or Access hostname presents rotating valid edge certificates.

## Best Possible Solution

Define a security-reviewed endpoint-identity policy that uses system CA and hostname validation for manually entered public DNS endpoints, retains explicit pinning where self-signed or discovery-derived identity requires it, migrates existing stored pins safely, and provides an in-app recovery flow with tests covering alternating valid leaves and untrusted certificates.

Question: For manually configured public Remote Domain endpoints, should iOS authenticate the gateway through normal CA-plus-hostname validation instead of binding the endpoint to one TLS leaf fingerprint?

Rationale: The current behavior blocks valid anycast certificate rotation, but changing or removing the pin alters the identity boundary protecting a client that may execute gateway-directed actions; repository history does not establish the intended permanent policy.

Likely owner: ngutman

Owner reason: The most focused current-main ownership signal is the existing iOS certificate-rotation recovery implementation.

Owner confidence: high

Options:

- **Use public-PKI identity (recommended):** Use CA and hostname validation for manually entered public DNS endpoints while retaining pinning for self-signed, private, or discovery-derived endpoints, with a stored-pin migration.
- **Keep explicit pinning:** Retain strict leaf identity and document Cloudflare anycast endpoints as unsupported unless a stable origin certificate is exposed.
- **Introduce a selectable trust mode:** Add an explicit in-app endpoint trust choice, accepting the extra configuration and upgrade surface needed to distinguish PKI validation from pinning.

## Reproduction Assessment

Yes at source level: configure an iOS Remote Domain endpoint whose trusted public hostname alternates between valid leaf certificates, accept one mismatch, and observe that the next different leaf is compared against the newly stored single fingerprint. A live Cloudflare-backed device reproduction would strengthen implementation validation but is not needed to establish the current code path.

## Solution Assessment

No, globally removing certificate pinning as suggested in the report is not yet the safest complete fix. The narrow maintainable solution is to distinguish public-PKI endpoint identity from endpoints that require explicit pinning, then migrate persisted trust and test both rotation and impersonation cases.

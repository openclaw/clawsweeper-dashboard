## Summary

Keep this issue open. Current main still stores one leaf-certificate fingerprint per iOS gateway, and “Trust certificate” replaces it with one newly observed leaf, so an anycast endpoint can immediately alternate back into the mismatch state. The report is a credible P0 remote-connection blocker, but the safe repair requires an explicit endpoint-trust and persisted-state migration decision; the closed Android report only partially overlaps with ordinary certificate rotation.

## What This Changes

Fix the iOS Remote Domain connection loop caused by Cloudflare Tunnel/Access endpoints presenting different valid TLS leaf certificates.

## Best Possible Solution

Use system CA and hostname validation for manually configured public-PKI Remote Domain endpoints while retaining explicit pin trust for discovered, direct, or self-signed gateways; migrate existing saved state deliberately and provide an in-app recovery flow with focused anycast, rotation, fresh-install, and upgrade coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which durable TLS identity policy should the iOS app use for manually configured public-CA Remote Domain endpoints that can present multiple valid leaf certificates?

Rationale: Source proves the current single-leaf model cannot represent the reported endpoint, but choosing CA trust, a bounded pin set, or continued leaf pinning changes the gateway identity and upgrade contract and cannot be selected safely by automation.

Likely owner: mbelinky

Owner reason: The merged history shows the broadest ownership of the iOS gateway connection, pairing, TLS-requirement, and security paths affected by this decision.

Owner confidence: high

Options:

- **Split trust by endpoint type (recommended):** Use system CA/hostname trust for public-PKI manual domains and preserve explicit fingerprint trust for discovered, direct, or self-signed gateways, with a persisted-state migration.
- **Persist a bounded pin set:** Keep certificate pinning but store and manage multiple explicitly trusted leaves per endpoint, accepting added rotation, expiry, and eviction complexity.
- **Keep strict single-leaf pins:** Document Cloudflare anycast endpoints as unsupported and improve the UI so users receive a durable explanation rather than a repeated trust loop.

## Reproduction Assessment

Yes at source level: current main loads one saved fingerprint and replaces it with one observed fingerprint after trust, so alternating valid leaves deterministically recreate the mismatch. A live Cloudflare/iOS run was not established during this read-only review, so the status is source-reproducible rather than fully reproduced.

## Solution Assessment

No, not as a blanket switch from pinning to CA validation. The narrow maintainable solution is to distinguish public-PKI manual domains from direct or self-signed gateway connections, preserving stronger explicit pin trust where it remains necessary.

## Summary

Keep this issue open. Current main still requires one saved leaf-certificate fingerprint for iOS Remote Domain connections, so a Cloudflare anycast hostname presenting another valid leaf certificate can immediately recreate the mismatch after the user trusts the prior certificate. The fix must preserve gateway-identity security while supporting CA-trusted rotating edge certificates.

**Likely related people**
- `mbelinky` — medium confidence; substantial recent iOS gateway, pairing, and reconnect work.
- `steipete` — low confidence; release and Apple-platform integration history makes this a reasonable secondary routing candidate.

## What This Changes

Make iOS Remote Domain connections tolerate valid Cloudflare edge-certificate rotation without entering an unresolvable TLS pin mismatch loop.

## Best Possible Solution

For system-trusted Remote Domain endpoints, validate the CA chain and preserve continuity through the authenticated OpenClaw gateway identity, while retaining explicit certificate pinning for self-managed or self-signed endpoints; cover fresh pairing, upgrades, certificate rotation, alternating edge certificates, and trust-failure attacks on a real iOS device.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What identity should iOS treat as stable for a CA-trusted Remote Domain endpoint whose valid leaf certificate may vary between connections?

Rationale: Certificate leaf pinning, CA-chain trust, and authenticated gateway-identity continuity provide different security and compatibility guarantees; source inspection cannot choose that product security boundary safely.

Likely owner: mbelinky

Owner reason: The decision primarily affects the current iOS gateway connection, trust-prompt, and reconnect workflow where this contributor has substantial adjacent history.

Owner confidence: medium

Options:

- **CA trust plus gateway identity (recommended):** Use system CA validation and authenticated gateway-identity continuity for Remote Domain routes, retaining explicit leaf pins for self-signed or operator-pinned endpoints.
- **Support multiple certificate pins:** Retain certificate pinning but store and manage an approved pin set, which may still be fragile for externally managed anycast certificate fleets.
- **Keep strict leaf pinning:** Continue rejecting any changed leaf certificate and document Cloudflare-style rotating edge endpoints as unsupported.

## Reproduction Assessment

Yes at source level: save one leaf fingerprint, then reconnect to the same stable gateway ID while the endpoint presents a different system-trusted leaf certificate. A real Cloudflare/iOS run is still needed to capture final behavior proof.

## Solution Assessment

Unclear until maintainers choose the intended security boundary. Blindly removing pinning is not the best fix; the maintainable direction is CA validation combined with authenticated gateway-identity continuity for rotating public endpoints.

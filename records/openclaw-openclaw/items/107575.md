## Summary

Keep this issue open. Current main still associates each gateway with one expected leaf-certificate fingerprint; trusting a changed certificate replaces that single pin, so reconnecting through a Cloudflare anycast edge presenting another valid leaf can immediately trigger the mismatch again. The previously shipped certificate-rotation recovery handles sequential replacement, not multiple concurrently served certificates, and resolving that gap requires an explicit TLS trust-boundary decision. citeturn14view0turn16view0turn0view0

## What This Changes

Fix the iOS Remote Domain connection loop caused by alternating CA-valid Cloudflare edge certificates while preserving an intentional gateway identity boundary.

## Best Possible Solution

Make trust depend on route provenance: use platform CA and hostname validation for CA-valid Remote Domain endpoints, retain explicit fingerprint pinning for discovered, local, setup-code, or self-signed gateways, and add an in-product recovery path plus tests that alternate multiple valid leaf certificates for one hostname.

## Maintainer Decision

Kind: security_boundary

Question: What TLS identity policy should iOS Remote Domain mode use for a manually entered, CA-valid public hostname that may serve multiple rotating or anycast leaf certificates?

Rationale: The existing single-leaf TOFU model cannot reliably support Cloudflare anycast, but relaxing it globally could weaken protections intended for local, discovered, self-signed, or explicitly pinned gateways.

Likely owner: ngutman

Owner reason: The current certificate-rotation prompt and replacement behavior appears to originate in their merged iOS gateway work.

Owner confidence: high

Options:

- **Split trust by route provenance (recommended):** Use platform CA and hostname validation for CA-valid Remote Domain endpoints while preserving explicit pins for discovered, local, setup-code, and self-signed routes.
- **Support a bounded pin set:** Keep TOFU semantics but persist multiple user-approved fingerprints with explicit replacement, expiry, and pruning behavior.
- **Keep strict leaf pinning:** Retain the current security model and explicitly document rotating or anycast reverse-proxy TLS as unsupported for iOS Remote Domain mode.

## Reproduction Assessment

Yes, at source level: store edge fingerprint A, reconnect through an edge presenting B, trust B, then reconnect through an edge presenting A or C. Current main's single expected-fingerprint model deterministically repeats the mismatch, although a live iOS artifact was not supplied.

## Solution Assessment

No final implementation can be selected mechanically. The narrowest maintainable direction is provenance-aware trust rather than globally disabling pinning or repeatedly overwriting one leaf fingerprint.

## Summary

Keep this issue open. Current main still associates a gateway stable ID with one leaf-certificate fingerprint, and “Trust certificate” replaces that single value; an anycast endpoint alternating between multiple valid leaf certificates can therefore return immediately to the mismatch prompt. The prior Android report covered sequential certificate rotation, not concurrently served certificates.

**Likely related people**
- `ngutman` — high confidence; authored the existing iOS certificate-rotation recovery.
- `steipete` — high confidence; carried the security commits that established explicit TLS-pin trust.
- `mbelinky` — medium confidence; introduced and extensively developed the iOS gateway connection path.

## What This Changes

Make iOS Remote Domain connections usable through Cloudflare Tunnel/Access when an anycast hostname presents different device-trusted leaf certificates across connections.

## Best Possible Solution

Add an explicit per-endpoint trust policy to iOS Remote Domain setup: retain strict gateway pinning as the safe default, offer system-PKI plus hostname validation for public reverse-proxy/anycast domains, persist the selected policy, and cover fresh pairing, rotation, and alternating valid certificates.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What TLS identity policy should iOS Remote Domain mode use for public reverse-proxy and anycast hostnames that legitimately serve multiple leaf certificates?

Rationale: The current single-leaf pin is incompatible with the reported topology, but automatically accepting every device-trusted replacement changes the anti-impersonation guarantee established by the iOS security stack.

Likely owner: steipete

Owner reason: The relevant security contract appears to originate in security hardening commits they carried, making them the strongest available owner for the trust-boundary choice.

Owner confidence: high

Options:

- **Add explicit trust modes (recommended):** Keep strict pinning as the default and let users explicitly select system-PKI hostname validation for public reverse-proxy or anycast domains.
- **Allow multiple leaf pins:** Persist a bounded set of explicitly approved fingerprints per gateway, preserving pinning but potentially requiring repeated prompts as edge certificates change.
- **Use system PKI for Remote Domain:** Make all Remote Domain connections rely on device CA trust and hostname validation, simplifying Cloudflare use while intentionally removing the extra leaf-pin boundary.

## Reproduction Assessment

Yes at source level: alternate two device-trusted leaf fingerprints for the same Remote Domain stable ID, accept the first mismatch, and the next connection using the other leaf will fail because current main stores only the replacement fingerprint. A live Cloudflare/iOS run was not performed.

## Solution Assessment

No, repeatedly replacing one leaf pin is not the best fix for concurrent anycast certificates. The maintainable solution is an explicit endpoint trust policy that preserves strict pinning while providing a deliberate CA-and-hostname-validated mode for public domains.

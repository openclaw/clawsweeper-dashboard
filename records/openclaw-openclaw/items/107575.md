## Summary

Keep this issue open. Current main still treats one TLS leaf fingerprint as the saved gateway identity, so an anycast endpoint alternating valid certificates can re-enter the mismatch dialog immediately after the user accepts the new certificate; resolving that loop requires an explicit security-boundary decision.

## What This Changes

Fix the repeated iOS TLS certificate-pin mismatch loop when Remote Domain connections use Cloudflare Tunnel/Access endpoints that present different valid edge certificates.

## Best Possible Solution

After platform CA and hostname validation, authenticate a stable identity supplied by the paired gateway and provide an in-app identity-change recovery prompt; do not use a rotating edge leaf certificate as the gateway identity.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which stable identity should iOS Remote Domain mode authenticate after normal platform CA validation: the paired gateway identity, the TLS leaf certificate, or CA/hostname trust alone?

Rationale: Leaf pinning is incompatible with valid anycast rotation, but removing the additional identity check entirely could weaken the security assumptions around pairing and credential reuse; repository policy requires explicit owner judgment for this boundary.

Likely owner: mbelinky

Owner reason: Recent merged work covers the iOS gateway connection and pairing lifecycle closest to this decision surface.

Owner confidence: medium

Options:

- **Pin paired gateway identity (recommended):** Use CA and hostname validation for transport, then persist a stable gateway identity established during trusted pairing and prompt only when that identity changes.
- **Keep leaf pinning:** Retain the existing boundary and explicitly declare rotating reverse-proxy and anycast endpoints unsupported.
- **Use CA trust only:** Rely solely on platform CA and hostname validation for Remote Domain mode, accepting the reduced additional TOFU protection.

## Reproduction Assessment

Yes at source level: configure one hostname to alternate between two platform-trusted leaf certificates while the app persists only one fingerprint, then accept the mismatch and reconnect. A live iPhone and controlled Cloudflare or equivalent two-certificate endpoint should confirm the final fix.

## Solution Assessment

No, relying only on the CA chain is not yet the best proven fix because the current flow intentionally adds endpoint pinning. The safer narrow direction is normal CA validation plus a stable paired-gateway identity and an explicit in-app identity-change recovery path.

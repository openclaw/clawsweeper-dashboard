## Summary

Keep this issue open: the report gives a credible blocked iOS Remote Domain flow, current documentation still describes fingerprint trust for manual gateway connections, and no current-main or shipped fix was identified. The older Android report overlaps conceptually but does not resolve the iOS Cloudflare anycast case; changing the pinning policy also requires an explicit security-boundary decision.

## What This Changes

Make iOS Remote Domain connections tolerate legitimate Cloudflare Tunnel and Access edge-certificate variation without entering a repeated certificate-pin mismatch loop.

## Best Possible Solution

Define endpoint-scoped trust semantics: manually entered public WSS domains without an explicit fingerprint should rely on platform CA and hostname validation, while discovered, self-managed, or explicitly pinned endpoints retain strict fingerprint verification; the app should also provide a durable in-product recovery path that clearly identifies which trust mode is active.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should manually entered iOS Remote Domain endpoints without an explicitly supplied fingerprint use platform CA and hostname validation instead of automatic leaf-certificate TOFU pinning?

Rationale: Cloudflare anycast certificates make automatic leaf pinning unreliable, but removing it broadly would change the gateway identity security boundary; source inspection alone cannot determine the intended permanent trust policy.

Likely owner: ngutman

Owner reason: Their recent merged work is closely associated with iOS gateway connection and onboarding behavior.

Owner confidence: medium

Options:

- **CA validation for public domains (recommended):** Use platform CA and hostname validation for manually entered remote domains unless setup explicitly supplies a fingerprint, while retaining strict pinning for discovery and explicitly pinned endpoints.
- **Pin a stable identity:** Keep pinning but derive it from a stable gateway-controlled key or certificate identity that survives reverse-proxy leaf rotation, requiring a broader protocol and setup design.
- **Document unsupported topology:** Retain current leaf pinning and explicitly mark rotating or anycast TLS terminators as unsupported, leaving Cloudflare Tunnel and Access users without this connection path.

## Reproduction Assessment

No high-confidence current-main run has reproduced it yet, but the report provides a concrete Cloudflare Tunnel and Access sequence with exact expected and observed fingerprints. Confirmation should use an iOS device or simulator against an endpoint that presents different valid edge leaf certificates across connections.

## Solution Assessment

No, blanket removal of pinning is not yet the best proven fix because it could weaken explicitly pinned gateway connections. The narrower solution is to distinguish CA-validated manually entered domains from endpoints whose setup explicitly establishes a fingerprint.

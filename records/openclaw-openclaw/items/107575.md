## Summary

Keep this issue open. Current main still binds every iOS manual TLS endpoint to one leaf-certificate fingerprint, and accepting a mismatch only replaces that one value, so a Cloudflare anycast hostname can immediately present another system-trusted leaf and recreate the blocking loop. The bug is source-reproducible, but changing Remote Domain identity verification requires an explicit security-boundary decision.

## What This Changes

Fix the iOS Remote Domain connection loop where Cloudflare anycast edge certificates repeatedly fail a stored leaf-certificate pin after the user accepts the new certificate.

## Best Possible Solution

Use normal system certificate-chain and hostname validation for manual Remote Domain endpoints with publicly trusted certificates, retain explicit TOFU/pinning for discovered or non-publicly-trusted gateways, migrate obsolete Remote Domain leaf pins, and prove both modes on a real iOS device.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should iOS Remote Domain connections to system-trusted public hostnames use standard PKI and hostname verification instead of mandatory leaf-certificate pinning?

Rationale: The present pin protects against endpoint substitution but is incompatible with legitimate anycast and reverse-proxy certificate rotation; choosing which endpoint classes retain pinning changes the documented security boundary.

Likely owner: steipete

Owner reason: The choice changes the security model established by the explicit-trust and TLS-pin hardening commits.

Owner confidence: high

Options:

- **Use PKI for Remote Domain (recommended):** For manual public domains, trust the system-validated chain and hostname while retaining explicit pinning for discovered, self-signed, or explicitly pinned endpoints.
- **Keep pinning with a pin set:** Preserve mandatory pinning but support multiple bounded fingerprints or another operator-controlled identity set, which is more complex and may still be fragile with CDN-managed keys.
- **Keep current leaf pinning:** Retain the strongest existing endpoint pin but document Cloudflare anycast and rotating reverse proxies as unsupported for the native app.

## Reproduction Assessment

No live current-main device reproduction was run, but the failure is source-reproducible with high confidence: one leaf is required, and accepting rotation merely replaces it with another single leaf.

## Solution Assessment

No, repeatedly persisting a new leaf is not the best fix for an anycast hostname. The maintainable solution is an endpoint-class trust policy that uses system PKI for public Remote Domain hosts without weakening explicit pinning where it remains necessary.

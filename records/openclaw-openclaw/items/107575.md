## Summary

Keep this issue open. Current main still authenticates a manually configured iOS gateway with one saved leaf-certificate fingerprint, so accepting one Cloudflare edge certificate can be immediately invalidated when another valid anycast edge presents a different leaf certificate.

## What This Changes

Fix the iOS Remote Domain connection loop caused by leaf-certificate pinning when Cloudflare Tunnel/Access rotates among valid anycast edge certificates.

## Best Possible Solution

Use an explicit dual trust model: retain leaf pinning for direct or self-signed gateways, but for a user-selected system-trusted reverse-proxy endpoint validate hostname and CA while binding the session to the paired gateway's application-level identity; migrate existing pins and provide an in-app recovery flow with cross-platform tests.

## Maintainer Decision

Kind: security_boundary

Question: What durable identity should iOS authenticate when a manually configured gateway is reached through a system-trusted reverse proxy whose leaf certificate can change between connections?

Rationale: Source proves the current single-leaf model cannot support Cloudflare anycast, but choosing CA-only trust, gateway application identity, or continued strict pinning changes the remote-gateway security boundary and upgrade contract.

Likely owner: steipete

Owner reason: The relevant history ties this person to introducing the iOS TLS identity boundary that the decision would revise.

Owner confidence: high

Options:

- **Dual trust model (recommended):** Keep leaf pinning for direct or self-signed gateways and use system hostname/CA validation plus paired gateway identity for explicitly selected reverse-proxy endpoints.
- **Strict leaf pinning only:** Keep the existing security model and explicitly declare rotating anycast TLS termination unsupported, leaving Cloudflare Tunnel/Access remote use blocked.
- **System CA trust only:** Stop leaf pinning for manually configured public domains and rely solely on platform hostname and CA validation, accepting the loss of the current gateway-specific transport pin.

## Reproduction Assessment

Yes at source level: configure one gateway identifier and alternate between two system-trusted leaf certificates for the same hostname; the persisted single fingerprint necessarily mismatches every time the alternate edge is selected. A live Cloudflare/iOS run would strengthen proof but is not needed to establish the current-main defect path.

## Solution Assessment

No, removing pinning and relying only on the CA chain is not the best complete solution because it discards gateway-specific authentication. The narrower maintainable solution separates direct-gateway leaf trust from reverse-proxy transport trust and preserves a paired application-level gateway identity.

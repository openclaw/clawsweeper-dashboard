## Summary

Keep this issue open. Current main still authenticates each saved iOS gateway with one leaf-certificate fingerprint, and the shipped certificate-rotation recovery replaces that single value with the newly observed leaf. A valid anycast endpoint that alternates certificates can therefore re-enter the mismatch prompt immediately; resolving that without weakening gateway identity requires an explicit iOS/security decision.

## What This Changes

Fix the iOS remote-domain connection loop caused by Cloudflare anycast endpoints presenting different valid TLS leaf certificates.

## Best Possible Solution

For public WSS endpoints, retain normal platform CA and hostname validation while binding durable trust to the paired gateway identity rather than one rotating leaf; migrate legacy pins and make the in-app trust action atomically recover both connection roles, with alternating-certificate regression coverage and real-device proof.

- **Persist bounded pin sets:** Allow multiple approved leaf or public-key pins per gateway with explicit admission, rotation, eviction, and migration rules.
- **Keep strict leaf pinning:** Retain the existing security model and explicitly document rotating anycast remote domains as unsupported.

## Reproduction Assessment

Yes from source, with high confidence: current main persists one fingerprint per gateway and accepting rotation replaces it with one observed leaf, so alternating valid edge leaves can repeatedly mismatch. This review did not perform a live Cloudflare and iOS device reproduction.

## Solution Assessment

No, removing pinning and relying only on the CA chain is not yet the safest solution because the current protocol treats a pinned endpoint as trusted transport. The narrower maintainable direction is to separate public TLS transport validation from the already paired gateway's durable cryptographic identity.

## Summary

Keep this issue open. Current main still represents each iOS gateway with one saved leaf-certificate fingerprint, so the existing certificate-rotation recovery can loop when a valid anycast endpoint alternates among multiple trusted leaf certificates.

## What This Changes

Make iOS Remote Domain connections remain usable when a Cloudflare Tunnel or Access hostname presents different valid edge certificates across reconnects.

## Best Possible Solution

Separate transport trust from gateway identity: use normal iOS chain and hostname validation for manually entered public WSS domains, retain explicit TOFU pinning for discovery or self-signed gateways, migrate existing stored pins deliberately, and provide an inline recovery flow that explains and applies the selected trust mode without repeated prompts.

Options:

- **Adopt rotation-stable pins:** Keep mandatory application pinning but replace the single leaf fingerprint with a bounded SPKI, issuer, or multi-pin identity contract and explicit expiry semantics.
- **Keep leaf TOFU:** Continue pinning one leaf certificate and document CDN or anycast TLS termination as unsupported, leaving the reported remote path unusable.

## Reproduction Assessment

Yes at source level: current main stores and enforces one leaf fingerprint, and the trust action replaces it with one other fingerprint, so alternating valid edge certificates deterministically recreate the mismatch. A live Cloudflare capture was not run during this read-only review.

## Solution Assessment

No to blanket removal of pinning. The narrowest maintainable fix is mode-specific trust that uses system CA and hostname validation for manually configured public domains while preserving explicit identity pinning where system trust cannot establish the intended gateway.

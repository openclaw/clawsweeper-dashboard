## Summary

Keep this issue open. Current main still stores one leaf-certificate fingerprint for a manual iOS TLS endpoint; accepting a changed certificate replaces that single pin and reconnects, so an anycast hostname presenting another system-trusted leaf can immediately recreate the blocking loop. Choosing a replacement trust boundary requires explicit security ownership.

**Likely related people**
- `mbelinky` — medium confidence; explicitly routed into the iOS gateway/security discussion.
- `ngutman` — medium confidence; explicitly routed into the same discussion.
- `steipete` — low confidence; explicitly routed as an adjacent gateway/security decision owner.

## What This Changes

Fix the iOS Remote Domain certificate-pin mismatch loop for Cloudflare Tunnel/Access hostnames that may present different valid edge certificates.

## Best Possible Solution

Define separate native-client trust policies: retain explicit leaf pinning for gateway-managed or self-signed endpoints, while giving system-trusted Remote Domain endpoints a rotation-safe mode backed by hostname validation and, ideally, a stable cryptographic gateway identity; include a deliberate migration for existing manual pins and tests alternating valid leaf certificates.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For iOS Remote Domain endpoints with a system-trusted hostname, what stable identity should replace the current single-leaf certificate pin?

Rationale: Source establishes the blocking loop, but automation cannot decide whether public PKI, an application-level gateway identity, or continued strict leaf pinning is the intended authentication boundary without potentially weakening security.

Likely owner: mbelinky

Owner reason: The issue timeline most directly routes the iOS gateway trust-model decision to this person.

Owner confidence: medium

Options:

- **Public PKI plus gateway identity (recommended):** Use platform hostname and CA validation for rotating public certificates, then bind the paired connection to a stable gateway cryptographic identity when the protocol supports it.
- **Explicit public-PKI mode:** Add a clearly selected Remote Domain mode that relies on platform hostname and CA validation while preserving strict pinning for other endpoint types.
- **Keep strict leaf pinning:** Retain the current security boundary, document Cloudflare anycast and rotating reverse-proxy certificates as unsupported, and replace the looping prompt with a terminal explanation.

## Reproduction Assessment

Yes at source level: connect a manual system-trusted hostname that alternates between two valid leaf certificates; the app stores whichever leaf was most recently trusted and rejects the other on the next connection. A live Cloudflare reproduction was not run during this read-only review.

## Solution Assessment

No single proposal in the report is automatically the best fix: repeatedly replacing one leaf preserves the loop, while unconditional CA-only validation weakens the existing pin boundary. The narrow maintainable solution is an explicit endpoint trust policy with rotation-safe public-domain handling and retained strict pinning where appropriate.

## Summary

Keep this issue open. Current main still stores one leaf-certificate fingerprint for an iOS gateway and replaces it with only the currently observed leaf when the user accepts rotation; a Cloudflare anycast hostname can therefore present another valid leaf on the next attempt and recreate the blocking dialog. This is a valid security-sensitive bug, but the repair requires maintainer agreement on the Remote Domain identity boundary rather than a blanket removal of pinning.

## What This Changes

Fix the iOS Remote Domain certificate-mismatch loop that occurs when Cloudflare anycast edges present different valid TLS leaf certificates.

## Best Possible Solution

Use a mode-specific TLS identity policy: allow manually configured Remote Domain endpoints with a valid system-trusted hostname chain to rotate leaf certificates, bind the session to authenticated gateway identity after pairing, and retain explicit TOFU pinning for discovered or self-signed gateways; cover alternating valid leaves, invalid chains, hostname mismatch, and persisted trust in focused iOS tests.

Question: For a manually configured iOS Remote Domain endpoint with a system-trusted hostname certificate, what stable identity should replace the current single-leaf fingerprint boundary?

Rationale: Current pinning intentionally protects against gateway impersonation, but Cloudflare anycast makes a single mutable leaf fingerprint unusable; source inspection cannot choose the acceptable security tradeoff on maintainers' behalf.

Likely owner: @mbelinky

Owner reason: The ownership documentation and recent history connect this person to both the iOS app and its security-sensitive connection flow.

Owner confidence: high

Options:

- **Split policy by connection mode (recommended):** Use platform CA and hostname validation for public Remote Domain endpoints while retaining TOFU leaf pinning for discovered or self-signed gateways and binding paired sessions to gateway authentication identity.
- **Support multiple scoped pins:** Persist a bounded set of trusted leaf fingerprints per gateway, accepting operational complexity and continued churn whenever Cloudflare introduces an unseen certificate.
- **Retain strict single-leaf pinning:** Keep the present security model and document Cloudflare anycast TLS termination as unsupported for Remote Domain connections.

## Reproduction Assessment

Yes, from source with high confidence: the app saves exactly one observed leaf fingerprint, and accepting rotation replaces it with exactly one new leaf, so alternating valid anycast leaves necessarily recreate the mismatch. A live Cloudflare/iOS run would strengthen proof but is not required to establish this code-path failure.

## Solution Assessment

No, not as a blanket switch to CA-chain validation. The narrow maintainable solution is to distinguish public Remote Domain endpoints from discovered or self-signed gateways and preserve an authenticated gateway-identity boundary without pinning one rotating edge leaf.

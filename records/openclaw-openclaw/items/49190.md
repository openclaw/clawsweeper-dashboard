## Label Justifications

- `impact:message-loss`: The reported path involves successful cron work whose completion delivery fails or becomes ambiguous after execution.
- `impact:ux-friction`: Control UI can show a successful task as a failed run, creating avoidable investigation and alert fatigue.

## Summary

Keep open: current main and v2026.6.11 still lack a first-class cron warning status, and the linked implementation paths are open/unmerged with a product choice between `warning` and `ok` plus delivery fields still unresolved.

## What This Changes

Request a cron run status model that separates successful execution from failed post-run delivery so Control UI can show a warning instead of a failure.

## Best Possible Solution

Keep this issue as the canonical product/API decision, then land one chosen execution-versus-delivery contract with Gateway, CLI, Control UI, docs, and upgrade compatibility proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should successful cron execution followed by failed delivery become a first-class `warning` run status, or should cron keep `status=ok` and surface delivery failure through delivery-specific fields and warning UI?

Rationale: Both models are represented by open PRs and the choice changes persisted status, Gateway schema, Control UI rendering, backoff behavior, and external consumer semantics.

Likely owner: steipete

Owner reason: The current status/finalizer lines and recent cron outcome history point to this owner for the cross-surface cron semantics choice.

Owner confidence: high

Options:

- **Approve ok plus delivery fields (recommended):** Land the narrower contract where execution remains `ok` and operators use `deliveryStatus`, `lastDeliveryError`, and diagnostics for undelivered successful runs.
- **Adopt first-class warning:** Use the broader warning-status model only after updating storage, Gateway schema, CLI/UI filters, docs, and compatibility proof across repo-owned clients.
- **Keep delivery failures as errors:** Reject the split for now so post-run delivery failures continue to drive `status=error`, backoff, and failure alerts.

## Reproduction Assessment

Yes. Source inspection shows current main has no cron `warning` status and can still propagate an error-shaped delivery result into primary cron run status; I did not run a live cron delivery scenario in this read-only pass.

## Solution Assessment

Unclear until maintainers choose the product contract. Separating execution from delivery is the right boundary, but the durable model could be either a public `warning` state or `ok` plus delivery fields with warning UI.

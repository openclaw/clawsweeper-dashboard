## Summary

Keep open: current main and the latest release still do not have a first-class cron `warning` status, and the linked implementation candidates represent a real product/API choice rather than a cleanup-close case.

## What This Changes

Request a cron run status model that distinguishes successful execution from delivery failure so Control UI can show a warning instead of an execution error.

## Best Possible Solution

Choose one execution/delivery contract, then land it consistently across cron persistence, Gateway schema, CLI/UI rendering, docs, and regression tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should successful cron execution followed by failed delivery become a first-class `warning` run status, or should cron keep `status=ok` and have Control UI derive a warning presentation from delivery fields?

Rationale: Both approaches solve the false execution-failure signal, but the choice changes persisted status semantics, Gateway validation, UI filters, backoff behavior, and external consumer expectations.

Likely owner: YuzuruS

Owner reason: YuzuruS authored the merged adjacent delivery-status split and is the strongest history-linked owner for the status-versus-delivery contract tradeoff.

Owner confidence: medium

Options:

- **Use ok plus delivery fields (recommended):** Keep primary run status as execution-only `ok` and render warning UI from `deliveryStatus`, `lastDeliveryError`, and diagnostics so the protocol enum does not expand.
- **Add first-class warning:** Adopt `warning` as a persisted/API status after updating schema, storage readers, CLI/UI filters, plugin hooks, docs, and compatibility proof.
- **Keep delivery failures as errors:** Retain current error semantics so delivery-target failures continue to drive `status=error`, backoff, and failure alerts.

## Reproduction Assessment

Yes. Source inspection on current main shows no cron `warning` status and shows unresolved required delivery can still return an error-shaped result that the finalizer can propagate as the primary run status.

## Solution Assessment

Unclear until maintainers choose the product contract. Separating execution from delivery is the right boundary, but the durable model could be either a public `warning` state or `ok` plus delivery fields with warning UI.

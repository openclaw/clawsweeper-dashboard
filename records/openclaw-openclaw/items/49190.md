## Summary

Keep open: current main and v2026.6.11 still expose cron run status as `ok | error | skipped`, while linked open PRs represent competing choices for the requested partial-success semantics.

## What This Changes

The issue requests a cron status model that distinguishes successful execution from failed post-run delivery so Control UI can show a warning instead of an execution error.

## Best Possible Solution

Keep this issue as the canonical product decision, then land either a first-class `warning` contract or the narrower `ok` plus delivery-fields contract with explicit compatibility proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should cron runs with successful execution but failed post-run delivery become a first-class `warning` status, or should they remain `ok` with delivery failure recorded only in delivery fields?

Rationale: Current main and the latest release lack `warning`, while open PRs implement different public semantics; this changes persisted/API/UI behavior and cannot be chosen safely by cleanup automation.

Likely owner: steipete

Owner reason: The current cron status/delivery boundary history points to steipete, and the remaining question is a product/API compatibility choice across core and UI surfaces.

Owner confidence: medium

Options:

- **Adopt first-class warning (recommended):** Rework or land the broad warning-status path after resolving conflicts and proving Gateway, CLI, UI, docs, and external-client compatibility.
- **Keep ok plus delivery fields:** Use the narrower candidate semantics where execution remains `ok` and delivery failure is surfaced through `deliveryStatus` and diagnostics, accepting that Control UI will not have the requested yellow status unless it derives one locally.
- **Defer the contract change:** Leave the issue open as a product backlog item and close or pause implementation PRs until maintainers are ready to expand cron status semantics.

## Reproduction Assessment

Yes. Source inspection shows current main has no cron `warning` status and can still propagate delivery failure as a primary cron result, although I did not run a live cron delivery scenario in this read-only review.

## Solution Assessment

Unclear as final product direction. Separating execution and delivery is the right shape, but maintainers still need to choose between a public `warning` status and the narrower existing-status plus delivery-fields model.

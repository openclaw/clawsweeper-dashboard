## Label Justifications

- `P2`: This is a normal-priority cron/status semantics issue with real operator confusion but limited blast radius and open implementation candidates.
- `impact:message-loss`: The reported partial-success path is specifically a failed cron completion delivery after successful execution.
- `impact:ux-friction`: Control UI currently presents delivery-only failures as red execution failures, creating avoidable investigation and alert fatigue.

## Summary

Keep open: current main and the latest release still expose cron run status as `ok | error | skipped`, and the source path can still collapse non-fatal execution with delivery errors into the primary run status. The remaining work is already represented by open PR candidates, so this should stay with maintainer semantics review rather than a new repair job.

## What This Changes

Request a cron status model or equivalent execution/delivery split so successful cron execution with failed delivery appears as a warning instead of a hard execution error.

## Best Possible Solution

Maintainers should choose one canonical cron partial-success contract, preferably preserving execution status separately from delivery status and making Control UI display delivery-only failures as a warning without conflating them with execution errors.

Question: Should cron partial-success runs be persisted as a new `warning` CronRunStatus, or should execution remain `ok` while Control UI derives a warning presentation from `deliveryStatus=not-delivered`?

Rationale: Both approaches solve the reported operator confusion, but adding a new status value changes public protocol/client unions while deriving the warning from delivery fields preserves the existing execution-status contract.

Likely owner: Vincent Koc

Owner confidence: medium

Options:

- **Derive warning from delivery fields (recommended):** Keep `CronRunStatus` as execution-only and render `ok` plus failed delivery metadata as a warning in UI/API presentation where needed.
- **Add first-class warning status:** Land a broader additive protocol/UI change that records `warning` as a persisted cron run status and updates every repo-owned client surface.
- **Defer until linked bug PRs settle:** Pause this issue until the narrower delivery-failure PRs prove whether `ok + deliveryStatus` is sufficient for users.

Yes for source-level reproduction: current main still has only `ok | error | skipped`, and the non-fatal execution path can return the delivery dispatcher’s `status: "error"`. I did not run a live cron scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public contract: adding `warning` is plausible, but deriving warning presentation from existing delivery fields may be the narrower compatibility-safe solution.

## Summary

Keep open: current main and latest release still do not implement a cron `warning` run status, and open PRs now represent competing product contracts rather than a merged fix.

## What This Changes

The issue requests a cron run status model that separates successful execution from failed delivery so Control UI can show a warning instead of a full error.

## Best Possible Solution

Keep this issue as the canonical product decision, then land one chosen execution/delivery contract with Gateway, CLI, UI, docs, and upgrade compatibility proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should successful cron execution followed by failed delivery become a first-class `warning` run status, or should cron keep `status=ok` and surface delivery failure through delivery fields and UI presentation?

Rationale: Both open implementation paths solve the false execution-failure signal, but the choice changes persisted status semantics, Gateway validation, Control UI rendering, backoff, alerts, and external consumer compatibility.

Likely owner: Peter Steinberger

Owner reason: Peter has the strongest feature-history signal on the cron delivery-dispatch and run-outcome boundary that this product/API decision affects.

Owner confidence: high

Options:

- **Use ok plus delivery fields (recommended):** Land the narrower execution/delivery split and have UI/operators read `deliveryStatus`, `lastDeliveryError`, and diagnostics for undelivered successful runs.
- **Add first-class warning:** Adopt the broader `warning` status after updating storage, Gateway schema, CLI/UI filters, docs, and compatibility proof across clients.
- **Keep delivery failures as errors:** Reject the split for now so post-run delivery failures continue to drive primary `status=error`, backoff, and failure alerts.

## Reproduction Assessment

Yes. Source inspection on current main shows no cron `warning` status and shows unresolved required delivery can still produce an error-shaped primary run result without a live cron run.

## Solution Assessment

Unclear until maintainers choose the product contract. Separating execution from delivery is the right boundary, but the durable model could be a public `warning` state or `ok` plus delivery fields with warning UI.

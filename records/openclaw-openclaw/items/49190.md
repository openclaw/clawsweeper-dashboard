## Summary

Keep open: current main and the latest release still expose cron run status as `ok | error | skipped`, while the remaining work is a maintainer-visible choice between a first-class `warning` status and the existing `ok` plus delivery-status split.

## What This Changes

Request a cron execution/delivery status model so successful cron execution with failed result delivery is not shown as a hard execution error.

## Best Possible Solution

Keep this as the canonical product decision until maintainers choose the cron execution/delivery contract, then land one narrow implementation and close the linked overlaps from that decision.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should successful cron execution with failed post-run delivery become a first-class cron `warning` status, or should cron keep `status=ok` and surface the failure through `deliveryStatus` and `lastDeliveryError`?

Rationale: Both shapes are technically plausible, but they create different API, UI, backoff, and external-consumer semantics that automation should not choose silently.

Likely owner: steipete

Owner reason: Peter Steinberger has the strongest recent history across the isolated cron delivery and session-target surfaces involved in the product contract choice.

Owner confidence: high

Options:

- **Use ok plus delivery fields (recommended):** Keep `CronRunStatus` as execution-only and let Control UI render a warning from `deliveryStatus=not-delivered`; this matches the existing two-field model and the narrower proof-positive PR.
- **Add first-class warning status:** Expand cron status to include `warning` across storage, Gateway schema, CLI/UI filters, plugin/API consumers, docs, and compatibility proof.
- **Keep delivery failure as error:** Reject the split and continue treating required delivery failure as a cron error/backoff signal even when execution produced output.

## Reproduction Assessment

Yes, source-reproducible: current main has no cron `warning` status, unresolved required delivery can still produce an error-shaped result, and the scheduler persists primary status separately from delivery fields. I did not run a live cron delivery scenario in this read-only review.

## Solution Assessment

Unclear as final product direction: an execution/delivery split is the right boundary, but maintainers still need to choose first-class `warning` versus `ok` plus delivery fields.

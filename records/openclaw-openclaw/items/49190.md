## Label Justifications

- `P2`: This is a normal-priority cron correctness and operator-UX issue with bounded but meaningful impact on scheduled reporting workflows.
- `impact:message-loss`: The reported path involves successful cron work whose completion delivery fails or becomes ambiguous after execution.
- `impact:ux-friction`: Control UI can show a red failed run even when execution succeeded, creating avoidable investigation and alert fatigue.

## Summary

Keep open: current main and v2026.6.11 still lack a cron `warning` or partial-success status, delivery failures can still become the primary `error` run result, and the open closing PR is unmerged/conflicting while another open candidate uses different semantics.

## What This Changes

Add a cron run status model that separates successful execution from failed delivery so Control UI can render partial success as a warning.

## Best Possible Solution

Keep this issue as the canonical product decision, then land one chosen execution/delivery contract with storage, Gateway schema, CLI/UI filters, docs, and upgrade compatibility proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should successful cron execution followed by failed delivery become a first-class `warning` run status, or should cron keep `status=ok` and surface the delivery failure through delivery fields and UI presentation?

Rationale: Both models are represented by open PRs, and the choice changes persisted status, Gateway schema, Control UI rendering, backoff, and external consumer semantics.

Likely owner: steipete

Owner reason: Recent broad cron feature/status work makes this the strongest available owner for the cross-surface product/API choice.

Owner confidence: high

Options:

- **Use ok plus delivery fields (recommended):** Land the narrower execution/delivery split and make UI and operators read `deliveryStatus`, `lastDeliveryError`, and diagnostics for undelivered successful runs.
- **Add first-class warning:** Adopt the broader `warning` status only after updating storage, Gateway schema, CLI/UI filters, docs, and compatibility proof across clients.
- **Keep delivery failures as errors:** Reject the split for now so post-run delivery failures continue to drive `status=error`, backoff, and failure alerts.

## Reproduction Assessment

Yes. Source inspection shows current main has no cron `warning` status and can still persist an error-shaped delivery result as the primary cron run status; I did not run a live cron job in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product contract. Separating execution from delivery is the right boundary, but the durable model could be either a public `warning` state or `ok` plus delivery fields with warning UI.

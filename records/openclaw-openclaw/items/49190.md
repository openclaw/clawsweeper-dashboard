## Label Justifications

- `P2`: The issue affects cron status accuracy and operator trust for delivery failures, but it is a bounded cron/API/UI semantics decision rather than an emergency.
- `impact:message-loss`: The affected workflows involve cron completion delivery failing or being recorded as not delivered after successful execution.

## Summary

Keep open: current main and v2026.6.11 still expose cron run status as `ok | error | skipped`, while the broad linked implementation at https://github.com/openclaw/openclaw/pull/80139 remains open/conflicting and the newer https://github.com/openclaw/openclaw/pull/95419 is a narrower alternative that needs maintainer semantics approval.

## What This Changes

Request to distinguish successful cron execution with failed completion delivery from true execution failure, ideally by surfacing a warning state in Control UI and cron APIs.

## Best Possible Solution

Keep this issue as the canonical decision thread until maintainers either land a refreshed warning-status implementation or explicitly choose the narrower `ok` plus delivery-fields model and close the broader status request as intentionally not planned.

## Reproduction Assessment

Yes, source-reproducible: current main and v2026.6.11 have no `warning` cron status, and the current isolated finalizer can still propagate an error-shaped delivery result into the persisted run status. I did not run a live cron delivery scenario in this read-only review.

## Solution Assessment

Unclear as final product direction: an execution/delivery split is the right problem shape, but maintainers still need to choose between a first-class `warning` status and the narrower `ok` plus delivery-fields model before this can be considered solved.

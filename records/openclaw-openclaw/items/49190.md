## Summary

Keep open: current main and v2026.6.11 still lack a cron `warning` status, and open PRs represent competing execution-versus-delivery semantics rather than a merged fix.

## What This Changes

The issue requests a cron run status model that separates successful task execution from failed delivery so delivery-only failures surface as warnings rather than execution errors.

## Best Possible Solution

Keep this issue as the canonical product decision, then land one chosen execution/delivery contract with Gateway, CLI, UI, docs, and upgrade compatibility proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should successful cron execution followed by failed delivery become a first-class `warning` run status, or should cron keep `status=ok` and surface the delivery failure through delivery fields and UI presentation?

Rationale: Both models are plausible and already represented by open PRs, but the choice changes persisted status, Gateway schema, Control UI rendering, backoff, and external consumer semantics.

Likely owner: steipete

Owner reason: Recent cron feature/status history makes this the strongest available owner for the cross-surface product/API choice.

Owner confidence: high

Options:

- **Use ok plus delivery fields (recommended):** Land the narrower execution/delivery split and make UI and operators read `deliveryStatus`, `lastDeliveryError`, and diagnostics for undelivered successful runs.
- **Add first-class warning:** Adopt the broader `warning` status only after updating storage, Gateway schema, CLI/UI filters, docs, and compatibility proof across clients.
- **Keep delivery failures as errors:** Reject the split for now so post-run delivery failures continue to drive `status=error`, backoff, and failure alerts.

## Reproduction Assessment

Yes. Source inspection shows current main has no cron `warning` status and can still persist an error-shaped delivery result as the primary cron run status.

## Solution Assessment

Unclear until maintainers choose the product contract. Separating execution from delivery is the right boundary, but the durable model could be either a public `warning` state or `ok` plus delivery fields with warning UI.

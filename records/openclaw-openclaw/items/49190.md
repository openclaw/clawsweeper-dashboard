## Summary

Keep open: current main still has only `ok`, `error`, and `skipped` cron run statuses, and the remaining work is a maintainer choice between a first-class `warning` status and the narrower `ok` plus delivery-status model represented by open PRs.

## What This Changes

Request to distinguish successful cron execution from failed post-run delivery so isolated agentTurn runs with failed announce delivery do not appear as execution errors.

## Best Possible Solution

Keep this issue as the canonical product decision, then land one consistent execution/delivery contract across cron storage, Gateway, CLI, Control UI, docs, and compatibility guidance.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should successful cron execution followed by failed post-run delivery persist as a first-class `warning` run status, or as `status=ok` with delivery failure shown through delivery fields and UI presentation?

Rationale: Both open implementation paths can remove the false execution-failure signal, but the choice changes public status semantics, backoff/alert behavior, API schemas, UI filters, and external consumer expectations.

Likely owner: steipete

Owner reason: Recent broad cron status/schema work makes this the strongest available owner for the cross-surface status semantics decision.

Owner confidence: high

Options:

- **Approve ok plus delivery fields (recommended):** Land the narrower split so execution remains `ok` and operators detect delivery failure through `deliveryStatus`, `lastDeliveryError`, and diagnostics.
- **Adopt first-class warning:** Land a broader warning-state contract only after updating storage, Gateway schema, CLI/UI filters, docs, and compatibility proof.
- **Keep error semantics:** Reject the split for now so delivery-only failures continue to drive `status=error`, backoff, and failure alerts.

## Reproduction Assessment

Yes, source-level. Current main excludes `warning` from cron status types/schemas and still has a path where unresolved required delivery returns an error-shaped result that can become the primary cron run status.

## Solution Assessment

Unclear until maintainers choose the contract. Separating execution from delivery is the right boundary, but first-class `warning` versus `ok` plus delivery fields is a product/API decision.

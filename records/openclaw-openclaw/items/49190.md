## Summary

Keep open: current `main` and latest release still expose cron run status as `ok | error | skipped`, while open PRs now represent competing implementation choices for the requested execution-success versus delivery-failure semantics.

## What This Changes

Request a cron execution/delivery status split so successful cron execution with failed result delivery surfaces as a warning instead of an error.

## Best Possible Solution

Keep this issue as the canonical product decision until maintainers choose either a first-class `warning` status or a narrower `ok` plus delivery-fields contract.

## Reproduction Assessment

Yes, source-reproducible: current main has no cron `warning` status, unresolved delivery failures can still produce an error-shaped result, and the scheduler persists the primary run status separately from delivery fields. I did not run a live cron delivery scenario in this read-only review.

## Solution Assessment

Unclear as final product direction: an execution/delivery split is the right shape, but maintainers still need to choose a first-class `warning` contract versus the narrower delivery-fields model in the linked PRs.

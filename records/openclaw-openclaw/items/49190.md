## Summary

Keep open: current main and the latest release still have no cron `warning` status, and the remaining work is a product/API choice between a first-class warning state and the narrower `ok` plus delivery-status model.

## What This Changes

The issue requests a cron run status model that separates successful execution from failed delivery so Control UI can show a warning instead of an error.

## Best Possible Solution

Keep this issue as the canonical product decision, then land one chosen execution/delivery contract with Gateway, CLI, UI, docs, and upgrade compatibility proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should successful cron execution followed by failed delivery become a first-class `warning` run status, or should cron keep `status=ok` and surface the delivery failure through delivery fields and UI presentation?

Rationale: Both approaches are represented by open PRs and both solve the false execution-failure signal, but the choice changes persisted status, Gateway schema, Control UI rendering, backoff, and external consumer semantics.

Likely owner: steipete

Owner reason: Recent broad cron feature and schema/UI history makes this the strongest available owner for the cross-surface product/API choice.

Owner confidence: high

Options:

- **Use ok plus delivery fields (recommended):** Land the narrower execution/delivery split and make UI and operators read `deliveryStatus`, `lastDeliveryError`, and diagnostics for undelivered successful runs.
- **Add first-class warning:** Adopt the broader `warning` status only after updating storage, Gateway schema, CLI/UI filters, docs, and compatibility proof across clients.
- **Keep delivery failures as errors:** Reject the split for now so post-run delivery failures continue to drive `status=error`, backoff, and failure alerts.

## Reproduction Assessment

Yes. Source inspection on current main shows no cron `warning` status and shows an unresolved required delivery target can still produce an error-shaped result that becomes the primary cron run status.

## Solution Assessment

Unclear until maintainers choose the product contract. Separating execution from delivery is the right boundary, but the durable model could be either a public `warning` state or `ok` plus delivery fields with warning UI.

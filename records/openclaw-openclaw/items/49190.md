## Summary

Keep open: current main and v2026.6.11 still expose cron run status as `ok | error | skipped`, and the linked open PRs represent competing semantics for partial-success delivery failures.

## What This Changes

Request to add cron partial-success status semantics so successful execution with failed completion delivery can surface as `warning` instead of a primary execution `error`.

## Best Possible Solution

Keep this issue as the canonical product decision, then land one chosen execution/delivery contract with explicit Gateway, CLI, UI, docs, and upgrade compatibility proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should successful cron execution followed by failed delivery become a first-class `warning` run status, or remain `ok` with the delivery failure represented only by delivery fields and diagnostics?

Rationale: Both choices are plausible and already represented by open PRs, but the choice changes persisted/API/UI behavior and compatibility expectations for cron status consumers.

Likely owner: steipete

Owner reason: The current cron status/delivery boundary history points to steipete, and the remaining question is a product/API compatibility decision across core and UI surfaces.

Owner confidence: high

Options:

- **Adopt first-class warning (recommended):** Land a resolved version of the broad `warning` contract after proving cron storage, Gateway schema, CLI/UI filters, docs, and client compatibility.
- **Keep ok plus delivery fields:** Use the narrower semantics where execution remains `ok` and failed delivery is surfaced through `deliveryStatus`, diagnostics, and Control UI detail state.
- **Defer the contract change:** Leave the issue open and pause or close implementation PRs until maintainers are ready to commit to the public cron status model.

## Reproduction Assessment

Yes. Source inspection shows current main has no cron `warning` status and still has error-shaped delivery-target failure paths that can be persisted as the primary run status.

## Solution Assessment

Unclear as final product direction. Separating execution and delivery is the right shape, but maintainers still need to choose between a public `warning` status and the narrower `ok` plus delivery-fields model.

## Label Justifications

- `P2`: This is a normal-priority cron correctness and operator-UX issue for scheduled report workflows, without evidence of a release-blocking outage.
- `impact:message-loss`: The affected path is explicitly about cron completion delivery failing or becoming ambiguous after successful work.
- `impact:ux-friction`: Control UI can present successful execution as a red failed run, creating avoidable alert fatigue and investigation work.

## Summary

Keep open: current main and the latest release still expose cron run status as only `ok`, `error`, or `skipped`, and unresolved required delivery can still become the primary `error` run result even after execution succeeds. Open candidate PRs now cover different status-contract choices, so this needs maintainer product/API direction rather than another cleanup close.

## What This Changes

Request to distinguish successful cron execution from failed announcement delivery so API/state and Control UI can show a warning instead of an execution error.

## Best Possible Solution

Choose one cron execution-versus-delivery contract, then land it consistently across runtime persistence, Gateway protocol, CLI/UI rendering, docs, and upgrade compatibility tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should a successful cron execution with failed delivery become a first-class `warning` run status, or should cron keep execution `status=ok` and surface the delivery failure through delivery fields and warning UI?

Rationale: Both open implementation paths address the misleading red execution failure, but they create different public API and persisted-state contracts that automation should not choose without maintainer intent.

Likely owner: steipete

Owner reason: This is a cross-surface cron product/API decision involving runtime, protocol, UI, and compatibility behavior where steipete has the strongest recent ownership signal.

Owner confidence: high

Options:

- **Use `ok` plus delivery fields (recommended):** Land the narrower execution/delivery split, keep `CronRunStatus` stable, and make UI/operator surfaces render `lastDeliveryStatus=not-delivered` as a warning.
- **Adopt first-class `warning`:** Proceed with the broader protocol/status expansion only with full Gateway, UI, docs, backoff, and external-client compatibility proof.
- **Keep current error semantics:** Reject the split for now and continue treating failed required delivery as a primary cron run error.

## Reproduction Assessment

Yes. Source inspection on current main shows no cron `warning` status and a required delivery-target failure path that can still return an error-shaped primary cron result; I did not run a live cron scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the durable contract. Separating execution from delivery is the right boundary, but the best implementation could be either public `warning` status or stable `ok` status plus delivery fields and warning UI.

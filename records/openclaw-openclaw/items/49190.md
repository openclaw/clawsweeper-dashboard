## Label Justifications

- `P2`: The issue affects cron status accuracy and operator trust for delivery failures, but it is a bounded cron/API/UI improvement rather than an emergency.
- `impact:message-loss`: The affected workflows involve cron completion delivery failures or unclear `not-delivered` state after successful execution.
- `impact:ux-friction`: Control UI can show successful work as an error, causing avoidable investigation and alert fatigue for operators.

## Summary

Keep open: current main and the latest release still expose cron run status as `ok | error | skipped`, while the broad `warning` status implementation remains an open, conflicting PR and narrower overlapping PRs do not settle the requested public status model.

## What This Changes

Request a cron execution-vs-delivery status split so successful isolated cron execution with failed delivery can surface as a warning instead of an error.

## Best Possible Solution

Keep this issue as the canonical product thread until maintainers either land a retargeted warning-status implementation or explicitly choose the narrower `ok` plus delivery-status model.

## Reproduction Assessment

Yes. Source inspection shows current main has no `warning` cron status, unresolved delivery failures can still produce `status: "error"`, and the scheduler persists that status as the primary run outcome; I did not run a live cron delivery scenario in this read-only pass.

## Solution Assessment

Unclear as final product direction. An execution/delivery split is the right shape, but a first-class `warning` status changes public cron, Gateway, UI, and plugin-facing contracts and should land through the linked reviewed PR or an explicit maintainer-approved alternative.

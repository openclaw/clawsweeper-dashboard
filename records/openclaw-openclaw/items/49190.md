## Summary

Keep open: current `main` and latest release still do not have a cron `warning` run status, and the linked open PRs encode competing public semantics for successful execution with failed delivery.

## What This Changes

Request a cron run status model that separates execution success from post-run delivery failure so Control UI can show a warning instead of an execution error.

## Best Possible Solution

Keep this issue as the canonical product decision, then land one chosen execution/delivery contract with explicit Gateway, CLI, UI, docs, and upgrade compatibility proof.

## Maintainer Decision

Question: Should successful cron execution followed by failed post-run delivery become a first-class `warning` run status, or should execution remain `ok` while delivery failure is shown only through delivery fields and diagnostics?

Rationale: Both shapes are implemented by open candidate PRs, and the choice changes public persisted/API/UI behavior for cron status consumers.

Likely owner: steipete

Owner confidence: high

Options:

- **Adopt first-class warning (recommended):** Land a resolved version of the broad `warning` status contract after proving storage, Gateway schema, CLI/UI filters, docs, and external-client compatibility.
- **Keep ok plus delivery fields:** Use the narrower model where execution remains `ok` and Control UI highlights `deliveryStatus=not-delivered` without adding a new run status.
- **Defer the status contract:** Leave this issue open and pause or close implementation PRs until maintainers are ready to commit to the public cron status model.

## Reproduction Assessment

Yes, source-level. Current `main` has no `warning` cron status and still has delivery-target failure paths that can be propagated into the primary cron run status.

## Solution Assessment

Unclear as final product direction. Separating execution and delivery is the right shape, but maintainers still need to choose whether the public status model should add `warning` or keep execution `ok` with delivery fields.

## Summary

Keep open: current main still does not recognize top-level string `detail` API error payloads, and the unconfigured-provider/Codex suppression behavior remains a product decision rather than an implemented fix.

## What This Changes

The issue reports raw OpenAI Codex provider errors being forwarded into user chat when the user has not configured Codex/OpenAI.

## Best Possible Solution

Land a maintainer-approved fix that recognizes `detail` payloads, adds focused regression coverage, and defines the provider-routing policy for unconfigured Codex/OpenAI failures before changing chat delivery behavior.

## Maintainer Decision

Rationale: The source-backed parser gap is narrow, but the issue's expected behavior asks for a delivery policy that affects provider routing, channel replies, and user visibility.

Options:

- **Safe generic error plus parser fix (recommended):** Recognize `detail` payloads and replace unconfigured-provider leaks with generic, non-raw user copy while keeping actionable configured-provider errors visible.
- **Silent suppression:** Discard errors proven to come from providers the user did not configure, which reduces noise but may hide setup or runtime drift.
- **Parser-only fix:** Only normalize FastAPI-style `detail` payloads and defer provider-discovery gating to a separate issue or PR.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: a top-level `{"detail":"..."}` string is not accepted by `parseApiErrorPayload`, then `formatAssistantErrorText` can fall through to raw text. I did not run a live Telegram/Codex repro in this read-only review.

## Solution Assessment

Unclear as a complete solution: adding `detail` parsing is the narrow parser fix, but the issue also asks for a provider-routing policy for unconfigured Codex/OpenAI failures. The best fix should cover both the parser regression and the maintainer-approved delivery behavior.

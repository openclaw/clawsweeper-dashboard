## Label Justifications

- `P2`: A bundled provider advertises model ids that the upstream API has retired, producing a normal-priority setup and runtime failure for DeepSeek users.
- `impact:auth-provider`: The issue concerns DeepSeek credential resolution and selectable provider model ids.
- `impact:ux-friction`: Users can configure a catalog-advertised model or an intuitive inline key path and receive an opaque request failure instead of a guided recovery path.

## Summary

This issue remains necessary: current main still advertises the retired `deepseek-chat` and `deepseek-reasoner` ids in the bundled DeepSeek catalog, while DeepSeek’s official API documentation says they became inaccessible after July 24, 2026. The API-key portion needs a clearer unsupported-config diagnostic or doctor path rather than silently treating a plugin-owned provider like a generic custom provider.

## What This Changes

Update the bundled DeepSeek provider so its supported model catalog and upgrade guidance match DeepSeek V4, and make unsupported inline API-key configuration actionable.

## System Context

The DeepSeek plugin supplies OpenClaw’s provider catalog, setup/auth choices, and request compatibility metadata. Users select a `deepseek/*` model through config or onboarding; the plugin then supplies the model definition and resolves credentials before the generic inference runtime sends requests.

  B --> D[Bundled model catalog]
  C --> E[Generic inference runtime]

  F --> G[Agent response or actionable error]

## Best Possible Solution

Keep DeepSeek authentication on the documented plugin-owned credential path, add a clear validation or doctor diagnostic for ignored inline credentials, and migrate supported legacy model refs to explicit V4 Flash settings only where their runtime semantics can be preserved.

## What This Changes

The issue reports that adding `acp.enabled=true` with `backend: "acpx"` while the gateway is running can trigger repeated gateway restarts where acpx is not loaded after the self-triggered restart.

## Best Possible Solution

Make the ACP setup auto-enable and in-process restart lifecycle converge on one stable plugin activation path so adding ACP config while the gateway is running causes at most one restart and then loads a healthy acpx backend.

## Repair Work Prompt

Fix the ACP/acpx gateway restart loop reported in https://github.com/openclaw/openclaw/issues/102205. When `acp.enabled=true` and `acp.backend="acpx"` are added while the gateway is already running, OpenClaw should schedule at most one required restart, then the next in-process gateway lifecycle must include and start the acpx plugin service so the ACP backend is loaded and the config watcher does not repeatedly detect the same ACP auto-enable gap. Investigate the interaction between ACP setup auto-enable, `acp.*` reload planning, in-process SIGUSR1 restart startup config assembly, plugin activation source config, and `extensions/acpx/register.runtime.ts` service registration. Keep core plugin-agnostic, do not add a new config/env surface, and do not change unrelated ACP auth or session behavior from https://github.com/openclaw/openclaw/issues/83508. Add focused regression coverage for the add-ACP-config-while-running path or the closest unit seam proving that the restart lifecycle sees the auto-enabled acpx plugin and starts its service after restart. No CHANGELOG edit; include release-note context in the PR body if user-visible.

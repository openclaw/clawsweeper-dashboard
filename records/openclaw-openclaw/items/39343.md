## Summary

Keep open: current main and the latest release still lack the LINE rapid-media batching behavior, while Telegram album buffering is already implemented and WhatsApp-specific media loss is tracked separately.

## What This Changes

The issue requests gateway-layer buffering/coalescing for rapid image or media messages so multiple channel updates reach the agent as one turn.

## Best Possible Solution

Keep this open as the broad LINE media batching tracker, implement the remaining behavior inside the LINE plugin boundary, leave Telegram album buffering unchanged, and keep WhatsApp-specific media loss on https://github.com/openclaw/openclaw/issues/79949.

## Reproduction Assessment

Yes, at source level: current LINE still creates one media-bearing inbound context per message event and shared inbound debounce explicitly leaves media outside the generic text debounce path. I did not run a live LINE webhook test in this read-only review.

## Solution Assessment

No for the proposed generic gateway layer as written; the maintainable solution is a LINE-plugin-owned media batching contract with explicit defaults and reply-token semantics. Telegram's existing media_group_id buffering should remain channel-owned, and WhatsApp should stay on its narrower tracker.

## Summary

Keep open. Telegram album buffering is implemented on current main and in v2026.6.11, but the LINE part of the request still processes each downloadable media webhook event as its own agent turn and needs a maintainer product/config decision before repair automation should choose the buffering semantics.

## What This Changes

The issue requests an optional media batching buffer for rapid image/media messages, using Telegram media group metadata when available and heuristic same-sender batching for channels like LINE.

## Best Possible Solution

Choose the product boundary first, then implement any accepted remaining behavior inside the LINE plugin as opt-in same-sender media batching; keep Telegram's current mediaGroupFlushMs path and avoid a gateway-global batcher unless maintainers approve a shared SDK contract.

Options:

- **LINE opt-in batching (recommended):** Add a conservative LINE plugin config key and buffer same-account, same-conversation, same-sender downloadable media with documented latency and reply-token tradeoffs.
- **Shared channel contract:** Design a media-aware channel SDK/core contract first, accepting broader architecture and compatibility review before changing LINE.
- **Keep unsupported:** Keep native Telegram media-group handling only and document that channels without reliable grouping metadata dispatch media events individually.

## Reproduction Assessment

Yes, at source level: current main handles each downloadable LINE media event with a fresh allMedia array and immediate processMessage call, with no same-sender media buffer. I did not run a live LINE webhook burst.

## Solution Assessment

Unclear until maintainers choose the product boundary. A LINE-owned opt-in buffer is the narrowest likely implementation, while a gateway-global media batcher would cut across plugin ownership and config policy.

## Summary

Keep open. Current main and the latest release cover Telegram albums with `mediaGroupFlushMs`, but LINE still handles each downloadable media webhook event as its own agent turn and has no media batching config/docs surface, so the remaining work is a product/config decision rather than stale cleanup.

## What This Changes

The issue requests an optional gateway-layer media batching buffer so rapid images, Telegram albums, and LINE media bursts can flush as one agent turn.

## Best Possible Solution

Keep Telegram's existing `mediaGroupFlushMs` path, then choose either an opt-in LINE plugin media buffer or a broader SDK contract before implementing heuristic batching outside Telegram.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should the remaining rapid-media batching behavior be accepted as a LINE-owned opt-in config surface, designed as a broader shared channel/plugin contract, or intentionally left unsupported for channels without native grouping metadata?

Rationale: LINE lacks native grouping metadata and the request adds delayed delivery plus new configuration, so automation should not choose the product boundary, default, or heuristic semantics.

Likely owner: steipete

Owner reason: This decision crosses LINE config/docs, shared channel debounce semantics, and plugin-boundary policy where recent path history shows repeated work.

Owner confidence: medium

Options:

- **Plugin-owned LINE opt-in batching (recommended):** Add a LINE plugin config key with default-off or conservative timing, buffer same account/conversation/sender downloadable media, and document reply-token and latency tradeoffs.
- **Shared media batching contract:** Design a channel SDK/core contract for media-aware aggregation before changing LINE, accepting broader architecture and compatibility review.
- **Keep heuristic batching unsupported:** Keep Telegram's native media-group handling only and document that LINE users should send combined media/text when no reliable grouping metadata exists.

## Reproduction Assessment

Yes, at source level for the remaining LINE behavior: current main handles each downloadable LINE media event with a fresh `allMedia` array and immediate `processMessage`, with no batching key or delay. I did not run a live LINE webhook burst.

## Solution Assessment

Unclear until maintainers choose the product boundary. A LINE-owned opt-in buffer is the narrowest likely implementation, while a gateway-global media batcher would cut across plugin ownership and config policy.

## Summary

Keep open. Current main implements the Telegram media-group half, but LINE still handles downloadable media events one at a time and has no batching config/docs surface; the remaining LINE behavior needs a maintainer product decision before automation chooses defaults or heuristics.

## What This Changes

Request to buffer rapid inbound media, especially Telegram albums and LINE image bursts, so related images reach the agent as one turn.

## Best Possible Solution

Keep the current Telegram mediaGroupFlushMs implementation, then decide a LINE plugin-owned imageSet-first batching design with any time-proximity fallback explicitly opt-in and documented; avoid a gateway-global media batcher unless maintainers approve a shared channel SDK contract.

Options:

- **LINE imageSet-first batching (recommended):** Implement LINE-owned batching keyed by account, conversation, sender, and imageSet id when present, with any time-proximity fallback disabled or narrowly opt-in.
- **Shared channel contract:** Design a media-aware channel/plugin SDK contract first, accepting broader compatibility and architecture review before changing LINE behavior.
- **Keep unsupported:** Keep Telegram album buffering and text-only inbound debounce as the supported behavior, and document that LINE media without usable grouping dispatches as separate turns.

Yes, at source level for the remaining behavior: current main handles each downloadable LINE media event with a fresh allMedia array and immediate processMessage call, with no LINE media batch buffer. I did not run a live LINE webhook burst, and this is a feature gap rather than a broken current contract.

## Solution Assessment

Unclear until maintainers choose the product boundary. A LINE plugin imageSet-first buffer is the narrowest likely implementation, while a gateway-global batcher would cut across plugin ownership and config policy.

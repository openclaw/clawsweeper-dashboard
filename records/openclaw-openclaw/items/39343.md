## Summary

Keep open. Current main and v2026.6.11 cover the Telegram album half with `mediaGroupFlushMs`, but LINE still dispatches each downloadable media webhook event as its own agent turn with no same-sender media buffer or LINE config surface.

## What This Changes

The issue requests gateway-layer batching for rapid image/media messages so related attachments are delivered as one agent turn instead of separate replies.

## Best Possible Solution

Maintainers should choose the product boundary first; the likely narrow end state is an opt-in LINE plugin media buffer keyed by account, conversation, and sender, while keeping Telegram's existing `mediaGroupFlushMs` path and shared text debounce semantics unchanged.

- **LINE opt-in media batching (recommended):** Add a conservative LINE plugin config key and buffer same-account, same-conversation, same-sender downloadable media while documenting latency and reply-token tradeoffs.
- **Shared channel contract first:** Design a media-aware channel SDK/core coalescing contract before changing LINE, accepting a broader architecture and compatibility review.
- **Keep unsupported:** Keep Telegram's native media-group handling only and document that LINE-style independent media events dispatch individually unless a channel exposes reliable grouping metadata.

## Reproduction Assessment

Yes, source-level. Current main handles each downloadable LINE media event with a fresh `allMedia` array and immediate `processMessage`, with no same-sender media buffer; I did not run a live LINE webhook burst.

## Solution Assessment

Unclear until maintainers choose the product boundary. A LINE-owned opt-in buffer is the narrowest likely implementation, while a gateway-global batcher would cut across plugin ownership and config policy.

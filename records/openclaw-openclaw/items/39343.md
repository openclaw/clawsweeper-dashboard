## Label Justifications

- `P2`: The request targets a real multi-message UX problem with limited channel blast radius, but it is not an outage, data-loss emergency, or hard onboarding blocker.
- `impact:session-state`: Batching changes how separate inbound messages are grouped into one session and agent turn.
- `impact:ux-friction`: Users can still send media, but rapid multi-image or image-plus-text workflows can produce fragmented replies or force awkward workarounds.

## Summary

Keep open: current main and v2026.6.11 cover Telegram albums and text-only inbound debounce, but the broader media-aware batching contract remains unresolved for channels whose media arrives as independent events.

## What This Changes

Request to add optional gateway/channel media batching so rapid images from the same chat/user can be delivered as one agent turn instead of separate turns.

## Best Possible Solution

Define a maintainer-approved media-aware inbound batching contract or explicit channel/plugin ownership plan, keep Telegram album buffering as the existing channel-specific solution, and let narrower channel bugs such as WhatsApp media loss land through their own PRs.

Rationale: The remaining request changes public config/API surface, latency defaults, session grouping, and media attachment semantics across channel boundaries; repository policy requires maintainer direction before adding that kind of product surface.

Owner confidence: medium

Options:

- **Design generic media batching contract (recommended):** Define a typed channel/gateway batching seam with explicit keys, media preservation, flush semantics, command bypass rules, defaults, docs, and upgrade tests before implementation.
- **Keep channel-specific fixes only:** Treat Telegram as already solved and handle WhatsApp/LINE-style cases in each plugin without creating a new shared gateway contract.
- **Defer for more live evidence:** Keep the issue open but require concrete non-Telegram reproduction and target UX proof before choosing a core API.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 explicitly keep shared inbound debounce text-only, and WhatsApp still opts media-bearing messages out of debounce. Telegram albums are the exception because they have a dedicated media_group_id buffer.

## Solution Assessment

Unclear as an implementation path: the requested gateway layer is plausible, but the best fix needs maintainer agreement on whether media batching belongs in a shared contract or stays channel/plugin-specific.

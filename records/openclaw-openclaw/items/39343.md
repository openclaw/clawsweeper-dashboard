## Summary

Keep open: current main covers Telegram album buffering and text-only inbound debounce, but LINE rapid media events still dispatch as separate turns, so the remaining behavior needs maintainer product/config direction rather than cleanup closure.

## What This Changes

The issue requests optional media batching for rapid image/media messages, using Telegram media-group metadata where available and same-sender timing heuristics for channels like LINE.

## Best Possible Solution

If maintainers accept the behavior, implement it as an opt-in LINE/channel-plugin media buffer keyed by account, conversation, and sender while preserving Telegram's existing media-group path and avoiding a gateway-global batcher without a broader design decision.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should the remaining rapid-media batching behavior be accepted as a LINE-owned opt-in config surface, designed as a broader shared channel/plugin contract, or intentionally left unsupported for channels without native grouping metadata?

Rationale: LINE has no native grouping metadata and the request adds delayed webhook handling plus a new configuration surface, so automation should not choose the product boundary, defaults, or heuristic semantics on its own.

Likely owner: steipete

Owner reason: This choice crosses config policy, shared debounce semantics, and channel plugin boundaries where recent history shows direct involvement.

Owner confidence: medium

Options:

- **Plugin-owned LINE opt-in batching (recommended):** Add a default-off LINE media batching option that buffers only same account, conversation, and sender downloadable media, with docs covering latency and reply-token tradeoffs.
- **Shared media batching contract:** Design a channel SDK or gateway contract for media-aware aggregation before adding LINE behavior, accepting broader architecture and compatibility review.
- **Keep heuristic batching unsupported:** Keep native Telegram media-group handling only and document that channels without reliable grouping metadata may dispatch separate media turns.

## Reproduction Assessment

Yes, at source level: LINE currently handles each downloadable media webhook event with a fresh `allMedia` array and immediate `processMessage`, while shared inbound debounce explicitly excludes media. I did not run a live LINE webhook burst.

## Solution Assessment

Unclear until maintainers choose the product boundary. A LINE-owned opt-in buffer is the narrowest likely implementation, while a gateway-global media batcher would cut across plugin ownership and config policy.

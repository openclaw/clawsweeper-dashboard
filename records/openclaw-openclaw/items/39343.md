## Summary

Keep open: current main and v2026.6.11 cover text-only inbound debounce and Telegram album buffering, but they still do not implement LINE-style independent media batching; the remaining work changes channel latency, config, and plugin/core ownership, so it needs maintainer product direction.

## What This Changes

Request optional media batching so rapid same-user image/media messages are flushed as one agent turn, with Telegram keyed by media_group_id and LINE using sender/chat/time proximity.

## Best Possible Solution

Choose an opt-in plugin-owned media batching contract for LINE-like independent media events, preserving Telegram album buffering and text-only debounce unless maintainers explicitly approve a shared SDK/gateway seam.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should the remaining independent-media batching be implemented as a LINE/plugin-owned opt-in buffer, a shared channel SDK/gateway coalescer, or deferred to narrow per-channel bugs?

Rationale: The remaining behavior changes public config, latency, session/turn boundaries, webhook semantics, and the plugin-versus-core owner boundary, so automation should not choose the permanent product/API direction.

Likely owner: steipete

Owner reason: This choice spans shared debounce policy, plugin/core ownership, and config compatibility, and history ties this owner to those surfaces.

Owner confidence: high

Options:

- **Approve plugin-owned media batching (recommended):** Implement an opt-in same-account/conversation/sender media buffer in the affected channel plugin first, adding shared SDK helpers only if duplication appears across channels.
- **Design a shared coalescer:** Create a broader channel SDK or gateway media coalescing contract before implementation, accepting larger API, config, and compatibility review.
- **Defer broad batching:** Keep text debounce and Telegram album support as the supported behavior for now, and handle only narrower channel bugs such as WhatsApp steer media loss through their own trackers.

## Reproduction Assessment

Yes, at source level. Current main excludes media-bearing messages from shared inbound debounce, and LINE still builds a one-message media context and immediately dispatches it; no live LINE webhook reproduction was run.

## Solution Assessment

Unclear as proposed. The gateway-layer request may be too broad for OpenClaw’s plugin boundary, while a plugin-owned opt-in media buffer looks safer but still needs maintainer approval for config and latency semantics.

## Summary

Keep open: current main and v2026.6.11 still model token mode as one shared Gateway bearer credential, while this issue asks for a new per-token identity/session-isolation contract that remains unsolved and security-sensitive.

## What This Changes

Request support for multiple Gateway bearer tokens with per-token labels/scopes so shared Control UI/WebChat access can isolate sessions by user.

## Best Possible Solution

Choose a Gateway principal model that preserves existing single-token deployments while adding maintainer-approved multi-token identity/scoping, session attribution semantics, docs, doctor/migration handling if needed, and targeted auth/session tests.

## Reproduction Assessment

Yes, as a source-level capability check rather than a runtime bug repro. Current main and v2026.6.11 support singular shared token/password auth plus identity-bearing trusted-proxy/Tailscale paths, with no gateway.auth.tokens map/list or token-derived user session identity.

## Solution Assessment

Unclear as proposed. Gateway auth is a plausible owner boundary, but token object shape, scope semantics, session binding, device/trusted-proxy interaction, and author-attribution behavior need maintainer security/product direction first.

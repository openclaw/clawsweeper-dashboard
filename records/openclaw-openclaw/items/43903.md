## Summary

Keep open: current main still treats Gateway token/password auth as one shared operator credential, while this issue asks for native per-token identity and session isolation. The Pinchy front-layer workaround, trusted-proxy auth, scoped-token follow-up, and author-attribution issue are useful related paths, but none replaces this focused Control UI/WebChat token-identity request.

## What This Changes

The issue requests native multiple Gateway bearer tokens with per-token identity and scope mapping so WebChat/Control UI users can have isolated sessions without trusted-proxy setup.

## Best Possible Solution

Define one Gateway principal model that composes token identity, scoped credentials, trusted-proxy identity, device pairing, session-key routing, and author attribution before adding config or protocol surface.

## Reproduction Assessment

Yes, as a source-level capability check rather than a runtime bug repro. Current main and the latest release still support singular shared token/password auth plus identity-bearing trusted-proxy and device-token paths, with no gateway.auth.tokens map/list or token-derived user session identity.

## Solution Assessment

Unclear as proposed. Gateway auth is a plausible owner boundary, but the token object shape, scope semantics, session binding, device/trusted-proxy interaction, and author-attribution model need maintainer security/product direction first.

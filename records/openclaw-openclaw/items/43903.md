## Summary

Keep open: current main and v2026.6.11 still model Gateway token/password auth as a single shared operator credential, while this issue asks for native per-token user identity and session isolation. Pinchy-style front layers, trusted-proxy auth, and related scoped-token and author-attribution threads are useful context, but none replaces this focused Control UI/webchat token-identity request.

## What This Changes

Request support for multiple Gateway bearer tokens with per-token labels/scopes so team users can share one OpenClaw instance while keeping Control UI/webchat sessions isolated.

## Best Possible Solution

Define one Gateway principal model that composes token identity, scoped credentials, trusted-proxy identity, device pairing, session-key routing, and author attribution before adding the config/API surface.

## Reproduction Assessment

Yes, as a source-level capability check rather than a runtime bug repro. Current main and the latest release still support singular shared token/password auth plus identity-bearing trusted-proxy and device-token paths, with no gateway.auth.tokens map/list or token-derived user session identity.

## Solution Assessment

Unclear as proposed. Gateway auth is a plausible owner boundary, but the token object shape, scope semantics, session binding, device/trusted-proxy interaction, and author-attribution model need maintainer security/product direction first.

## Summary

Keep open: current main and the latest release still model Gateway token/password auth as one shared operator credential, while this issue asks for a new per-token identity and session-isolation contract. The Pinchy/front-layer workaround and trusted-proxy/device-token paths are useful today, but they do not replace native token-mode per-user identity.

## What This Changes

The issue requests multiple Gateway bearer tokens with per-token identity mapping so Control UI/webchat users can have isolated sessions.

## Best Possible Solution

Keep this focused design item open until maintainers choose a Gateway principal model that composes token identity, scoped credentials, trusted-proxy, device pairing, session keys, and author attribution.

## Reproduction Assessment

Yes, as a source-level capability check rather than a runtime bug repro. Current main and v2026.6.11 support singular shared token/password auth plus identity-bearing trusted-proxy and device-token paths, with no gateway.auth.tokens map/list or token-derived user session identity.

## Solution Assessment

Unclear as proposed. Gateway auth is a plausible owner boundary, but the token object shape, scope semantics, session binding, device/trusted-proxy interaction, and author-attribution model need maintainer security/product direction first.

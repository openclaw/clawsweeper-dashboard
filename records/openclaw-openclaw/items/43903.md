## Summary

Keep open: current main and the latest release still treat Gateway token/password auth as a single shared operator credential, while this issue asks for native per-token identity and session isolation. The linked Pinchy front-layer pattern, trusted-proxy auth, scoped-token issue, and chat-author issue are useful context but do not replace this focused Control UI/webchat token-identity request.

## What This Changes

The issue requests multiple gateway tokens with per-token identity mapping so shared Control UI/webchat deployments can isolate sessions by user.

## Best Possible Solution

Define a single Gateway principal model that composes token identity, scoped credentials, trusted-proxy identity, device pairing, session-key routing, and author attribution before adding the config/API surface.

## Reproduction Assessment

Yes, as a source-level capability check rather than a runtime bug repro. Current main and v2026.6.11 still support singular shared token/password auth plus identity-bearing trusted-proxy, Tailscale, and device-token paths, with no gateway.auth.tokens map/list or token-derived user session identity.

## Solution Assessment

Unclear as proposed. Gateway auth is a plausible owner boundary, but the token object shape, scope semantics, session binding, device/trusted-proxy interaction, and author-attribution model need maintainer security/product direction first.

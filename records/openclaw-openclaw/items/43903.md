## Summary

Keep open: current main and v2026.6.11 still implement token/password Gateway auth as one shared operator credential, while this issue asks for native per-token identity and session isolation for Control UI/webchat users. Pinchy-style front layers and trusted-proxy auth are useful production workarounds, but they do not replace the requested native token-mode principal model.

## What This Changes

Request support for multiple Gateway bearer tokens with per-token labels/scopes so shared Control UI users can get isolated sessions and attributable user identity.

## Best Possible Solution

Define one Gateway principal model that composes token identity, scoped credentials, trusted-proxy identity, device pairing, session-key routing, and author attribution before adding the config/API surface.

## Reproduction Assessment

Yes, as a source-level capability check rather than a runtime bug repro. Current main and v2026.6.11 support singular shared token/password auth plus identity-bearing trusted-proxy and device-token paths, with no gateway.auth.tokens map/list or token-derived user session identity.

## Solution Assessment

Unclear as proposed. Gateway auth is a plausible owner boundary, but the token object shape, scope semantics, session binding, device/trusted-proxy interaction, and author-attribution model need maintainer security/product direction first.

## Summary

Keep open: current main and the latest release still model Gateway token/password auth as one shared operator credential, while this issue asks for a new per-token user identity and session-isolation contract. The Pinchy front-layer workaround and related scoped-token/author-attribution issues are useful context, but they do not replace this focused Gateway token-mode request.

## What This Changes

Request support for multiple Gateway auth tokens with per-token labels/scopes so multi-user Control UI/webchat sessions can be isolated without switching to trusted-proxy mode.

## Best Possible Solution

Define one Gateway principal model that composes token identity, scoped credentials, trusted-proxy identity, device pairing, session routing, and author attribution before adding config/API surface.

## Reproduction Assessment

Yes, as a source-level capability check rather than a runtime bug repro. Current main and v2026.6.11 still support singular shared token/password auth plus identity-bearing trusted-proxy and device-token paths, with no gateway.auth.tokens map/list or token-derived user session identity.

## Solution Assessment

Unclear as proposed. Gateway auth is a plausible owner boundary, but the token object shape, scope semantics, session binding, device/trusted-proxy interaction, and author-attribution model need maintainer security/product direction first.

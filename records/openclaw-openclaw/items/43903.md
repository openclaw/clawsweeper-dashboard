## Summary

Keep open: current main and v2026.6.11 still model Gateway token/password auth as one shared operator credential, while this issue asks for native per-token identity and session isolation. The Pinchy front-layer pattern is useful production context, but it is a workaround rather than a core Gateway token-identity implementation.

## What This Changes

Request native multiple Gateway bearer tokens with per-token labels/scopes so shared Control UI or webchat users can get isolated session identity without switching to trusted-proxy auth.

## Best Possible Solution

Define one Gateway principal model that composes token identity, scoped credentials, trusted-proxy identity, device pairing, session routing, and author attribution before adding config/API surface.

## Reproduction Assessment

Yes, as a source-level capability check rather than a runtime bug repro. Current main and v2026.6.11 support singular shared token/password auth plus identity-bearing trusted-proxy/device paths, with no gateway.auth.tokens registry or token-derived user session identity.

## Solution Assessment

Unclear as proposed. Gateway auth is a plausible owner boundary, but the token shape, scope semantics, session binding, device/trusted-proxy interaction, and author-attribution model need maintainer security/product direction first.

- `maturity:stable`: The issue affects the M4 Stable gateway-runtime surface, including shared-secret login, trusted-proxy auth, device tokens, and operator permissions.

## Summary

Keep open: current main and v2026.6.11 still model Gateway token/password auth as one shared operator credential, while this issue asks for a new native per-token identity and session-isolation contract that needs maintainer security/product direction.

## What This Changes

Request support for multiple Gateway bearer tokens with per-token labels/scopes so shared Control UI or webchat users can map to isolated sessions.

## Best Possible Solution

Define one Gateway-owned principal model that covers per-token identity, scoped credentials, session binding, SecretRef/rotation semantics, trusted-proxy/device-token interaction, docs, and regression tests.

Options:

- **Design Unified Principals (recommended):** Define one Gateway-owned principal contract that covers per-user tokens, scoped service tokens, SecretRefs, rotation/revocation, docs, and tests before implementation.
- **Narrow To User Labels:** Implement only token-to-user labels and session identity for Control UI/webchat now, accepting possible later migration into a broader scoped-token model.
- **Keep External Front Layers:** Decline native multi-token auth for now and document trusted-proxy or Pinchy-style front layers as the supported team-deployment path.

## Reproduction Assessment

Yes, as a source-level capability check rather than a runtime bug repro: current main and v2026.6.11 support singular shared token/password auth plus identity-bearing trusted-proxy/device-token paths, with no gateway.auth.tokens map/list or token-derived user session identity.

## Solution Assessment

Unclear as proposed. Gateway auth is a plausible owner boundary, but the token object shape, scope semantics, session binding, device/trusted-proxy interaction, and author-attribution model need maintainer security/product direction first.

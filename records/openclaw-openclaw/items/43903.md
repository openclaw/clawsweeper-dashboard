## Summary

Keep open: current main and the latest release still model Gateway token/password auth as one shared operator credential, while this asks for a new per-token Gateway identity and session-isolation contract that needs maintainer security/product design.

## What This Changes

Add native support for multiple Gateway bearer tokens mapped to per-user labels/scopes so shared Control UI/WebChat deployments can isolate user sessions without trusted-proxy setup.

## Best Possible Solution

Keep this as the canonical per-user Gateway token identity design item until maintainers define one Gateway principal model that composes token identity, scoped credentials, trusted-proxy identity, device pairing, session keys, and author attribution.

Options:

- **Design unified principals (recommended):** Define one Gateway-owned principal model covering per-user token identity, scoped service tokens, SecretRefs, rotation, docs, and tests before implementation.
- **Narrow to user labels:** Implement only token-to-user labels and session identity for Control UI/WebChat first, accepting possible later migration into a broader scoped-token model.
- **Keep external front layers:** Decline native multi-token auth for now and document trusted-proxy or Pinchy-style front layers as the supported team-deployment path.

Yes, as a source-level capability check rather than a runtime bug repro. Current main and v2026.6.11 support singular shared token/password auth plus identity-bearing trusted-proxy and device-token paths, with no gateway.auth.tokens map/list or token-derived user session identity.

## Solution Assessment

Unclear as proposed. Gateway auth is a plausible owner boundary, but the token object shape, scope semantics, session binding, device/trusted-proxy interaction, and author-attribution model need maintainer security/product direction first.

## Summary

Keep open: current main still has a single shared Gateway token/password credential path, while trusted-proxy and the linked Pinchy front-layer workaround do not provide native per-token identity or session isolation for Control UI/webchat users.

## What This Changes

The issue requests native support for multiple Gateway tokens so separate users sharing an OpenClaw instance can be identified and isolated without sharing one operator credential.

## Best Possible Solution

Define a Gateway principal model that supports multiple bearer tokens with explicit identity and scope semantics, preserves single-token compatibility, and documents or doctors any config migration path.

## Reproduction Assessment

Yes, source-level: current config, schema, auth resolution, and Control UI chat send paths expose only one shared token and no per-token or per-message user identity.

## Solution Assessment

The request is a plausible core primitive, but the exact token shape, scope model, and session mapping need maintainer security/product design; Pinchy and trusted-proxy are useful alternatives, not substitutes.

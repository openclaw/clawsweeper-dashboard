## Summary

Keep open: current main still treats Gateway token/password auth as a single shared operator credential, while this issue asks for new native per-token user identity and session isolation. Related threads are useful context, but none supersede the focused Control UI/webchat token-mode request.

## What This Changes

Request support for multiple Gateway bearer tokens with per-token labels/scopes so Control UI and webchat users can have isolated session identity.

## Best Possible Solution

Define one Gateway-owned principal model that composes per-token user identity, scopes, SecretRefs, device pairing, trusted-proxy behavior, session keys, and author attribution before implementation.

Rationale: The request changes public auth config, credential matching, caller identity, authorization scopes, session isolation, and security docs, so automation should not choose the permanent trust model.

Owner confidence: high

Options:

- **Design unified Gateway principals (recommended):** Define a single security model covering per-user tokens, scoped service tokens, SecretRefs, rotation, docs, and upgrade behavior before implementation.
- **Narrow to user labels first:** Implement only token-to-user labels and session identity for Control UI/webchat now, accepting a likely later migration into broader scoped principals.
- **Keep external front layers:** Decline native multi-token auth for now and document trusted-proxy or Pinchy-style front layers as the supported team-deployment path.

## Reproduction Assessment

Yes, as a source-level capability check rather than a runtime bug repro. Current main supports one shared token/password plus trusted-proxy and device-token paths, with no gateway.auth.tokens map/list or token-derived user session identity.

## Solution Assessment

Unclear as proposed. Gateway auth is a plausible owner boundary, but the token object shape, scope semantics, session binding, device/trusted-proxy interaction, and author-attribution model need maintainer security/product direction first.

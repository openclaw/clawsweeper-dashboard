## Summary

Keep open: current main still treats token/password Gateway auth as one shared operator credential, while this issue asks for native per-token identity and session isolation. The Pinchy front-layer pattern, trusted-proxy auth, and related scoped-token and author-attribution issues are useful context, but they do not replace this focused Control UI/webchat token-identity request.

## What This Changes

Add multi-token Gateway auth with per-token identity/scope metadata so multiple Control UI or webchat users can keep isolated sessions while retaining token-mode local CLI and device-pairing behavior.

## Best Possible Solution

Define a single Gateway principal model that composes token identity, scoped credentials, trusted-proxy identity, device pairing, session-key routing, and author attribution before adding the config/API surface.

## Reproduction Assessment

Yes, as a source-level capability check rather than a runtime bug repro. Current main and the latest release still support singular shared token/password auth plus identity-bearing trusted-proxy and device-token paths, with no gateway.auth.tokens map/list or token-derived user session identity.

## Solution Assessment

Unclear as proposed. Gateway auth is a plausible owner boundary, but the token object shape, scope semantics, session binding, device/trusted-proxy interaction, and author-attribution model need maintainer security/product direction first.

## Summary

Keep open: the PR is focused, but the header-only guard does not actually bound untrusted CDP bodies when the endpoint omits or understates Content-Length, so the central OOM risk remains. It also has a changed-line lint failure and only mock/unit proof.

## What This Changes

The PR adds a Content-Length precheck before `readChromeVersion` parses the browser CDP `/json/version` response and adds six browser Chrome helper boundary tests.

## Best Possible Solution

Use the existing byte-bounded response reader through the plugin SDK to read and parse `/json/version` under a hard cap, cancel overflow, preserve cleanup and diagnostics, and cover no-header plus lying-header overflow cases before merge.

## Reproduction Assessment

Yes, from source inspection rather than a live run: current main calls `response.json()`, and Node/Undici fully reads and concatenates the body before JSON parsing. A synthetic no-Content-Length stream over the cap is the high-confidence reproduction path that should be added as a regression test.

## Solution Assessment

No. The PR is a plausible partial mitigation, but the best fix is to bound the actual response stream before JSON parsing rather than trusting the declared Content-Length header.

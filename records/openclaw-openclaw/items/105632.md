## Label Justifications

- `P2`: The deterministic Control UI race silently loses draft edits during session creation but has limited scope and is not present in the latest stable release.
- `impact:data-loss`: The UI accepts late message or target changes that are discarded when the original session creation succeeds.
- `impact:ux-friction`: The pending screen misleadingly remains interactive, causing avoidable confusion during normal session startup.

## Summary

Keep open: current main still accepts message and target-control edits after the New Session request has captured its draft, then discards those accepted edits on navigation. The report is well reproduced, no duplicate or fixing PR was found, and the protected `maintainer` label requires explicit maintainer handling.

## What This Changes

Lock the Control UI New Session message and target controls while `sessions.create` is pending so late accepted edits are not silently discarded.

## Best Possible Solution

Use `submitting` as the single page-level lock: prevent target menus from opening, disable their mutable fields and the textarea, restore interactivity after failure, and cover the pending interval with deferred-Gateway browser proof.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes. The reported live Playwright run is corroborated by current main: draft values are captured before an awaited `sessions.create`, while the textarea and target selectors remain interactive during `submitting`.

## Solution Assessment

Yes. Applying one atomic lock through the existing page-level pending state is the narrowest maintainable fix; maintaining a second mutable draft would introduce unnecessary reconciliation and navigation complexity.

- `P1`: The PR changes an active browser security boundary and remote Gateway workflow that can affect real Control UI users before merge.
- `merge-risk: 🚨 compatibility`: Existing remote `gatewayUrl` users would move from localStorage-only state to a cookie-plus-reload handoff during upgrade.

## Summary

Keep this PR open, but the current patch is not merge-ready: it usefully removes the blanket `ws:`/`wss:` sources, yet the new query/cookie origin authority keeps the CSP egress boundary client-controlled and the current PR body still lacks visible raw proof for the live external Gateway/provider paths it says were not tested.

## What This Changes

The PR tightens the Gateway-served Control UI CSP `connect-src`, adds explicit provider endpoints, and adds query/cookie/UI reload handling plus tests for remote `gatewayUrl` origins.

## Best Possible Solution

Land a server-owned or explicitly maintainer-approved dynamic `connect-src` model that preserves the documented remote `gatewayUrl` flow and includes redacted browser/network proof for default, live remote Gateway, in-page edit, and provider endpoint paths.

## Reproduction Assessment

Yes, source-reproducible: current `main` and `v2026.6.11` serve `connect-src` with bare `ws:` and `wss:`, and the CSP/WebSocket standards make that a WebSocket egress concern. I did not run an exploit browser path in this read-only review.

## Solution Assessment

No, not as currently proposed: removing blanket WebSocket schemes and listing provider endpoints is the right direction, but making `connect-src` depend on client-writable query/cookie state is not the best security-boundary fix without maintainer acceptance or a server-owned origin contract.

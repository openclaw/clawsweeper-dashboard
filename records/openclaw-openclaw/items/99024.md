## Label Justifications

- `P2`: This is a meaningful Control UI security hardening with limited blast radius, but it has merge-blocking compatibility and security-boundary concerns.
- `merge-risk: 🚨 compatibility`: The tightened CSP can block existing or first-time remote Gateway UI connect flows unless every connect entry point gets the remote origin into the served CSP before the WebSocket opens.
- `merge-risk: 🚨 security-boundary`: The PR changes the browser CSP boundary and currently lets a script-writable cookie expand `connect-src`.

## Summary

Keep open: the CSP hardening is useful and now has strong browser/terminal proof, but the branch is not merge-ready because the remote Gateway CSP handoff misses direct UI connect paths and the dynamic origin model trusts a script-writable cookie that undercuts the stated XSS WebSocket-exfiltration boundary.

## What This Changes

The PR tightens the Control UI `connect-src` CSP by replacing bare `ws:`/`wss:` with explicit endpoints and adding dynamic remote Gateway origins via `gatewayUrl` query/cookie handling plus UI handoffs and tests.

## Best Possible Solution

Land a version that removes broad WebSocket scheme sources while deriving remote Gateway CSP origins from a maintainer-approved server-owned trust boundary and centralizing the pre-connect CSP handoff for every UI connect path.

## Reproduction Assessment

Yes from source for the review findings: the login/overview direct connect paths bypass the new `handleGatewayUrlConfirm()` cookie handoff, and the server reads a script-writable cookie into `connect-src`. I did not run a browser repro in this read-only review.

## Solution Assessment

No. Tightening `connect-src` is the right direction, but this implementation is not the best fix until the remote-origin trust boundary is server-owned or explicitly approved and the remote-connect preflight is centralized.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.87

Full review comments:

- **[P1] Run the CSP handoff on every remote Gateway connect:** `ui/src/ui/app.ts:1489-1490`
  - body: This guard only runs after confirming a `pendingGatewayUrl`. The login gate and overview access controls can write `settings.gatewayUrl` and call `state.connect()` directly, so a first-time remote Gateway typed there still opens a cross-origin WebSocket under the tightened CSP before any `gateway-url` cookie/reload exists. Move the cookie/reload decision into `connect()`, `connectGateway()`, or another single path used by every remote connect.
  - confidence: 0.88
- **[P1] Keep CSP origins out of script-controlled cookies:** `src/gateway/control-ui.ts:981-987`
  - body: The server now reads `gateway-url` and appends its origin to `connect-src`, while the UI writes that cookie from JavaScript. For the stated XSS WebSocket-exfiltration threat model, injected script can set this cookie and reload to regain arbitrary WebSocket egress, so the extra origin needs to come from a server-owned allowlist/signed state or an explicitly approved trust model.
  - confidence: 0.84

## Summary

Keep open. The PR is on the right Android cache/auth lifecycle surface and has useful focused proof, but current head still leaves a stale connect window across auth reset, so it should not merge until `beginConnect` is claimed or generation-checked as part of the reset lifecycle.

## What This Changes

The PR hardens Android offline chat cache cleanup, credential replacement, Gateway socket teardown, Room cache deletion, queued command purge, and related Android tests/license inventory.

## Best Possible Solution

Claim the entire `beginConnect` path in the auth-reset lifecycle, or generation-check it before any stale auth reaches `connectWithAuth`, with a regression test for connect-start-before-reset.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes from source inspection: a `beginConnect` call can pass the reset flag sample before reset begins, remain uncounted by `gatewayConnectOperationsInFlight`, and then call `connectWithAuth` after reset clears the flag; I did not run a device-level race repro in this read-only review.

## Solution Assessment

Is this the best way to solve the issue? Not yet: bounding cache cleanup and credential reset in `NodeRuntime` is the right layer, but the current patch claims only `connectWithAuth`, leaving `beginConnect` outside the lifecycle boundary.

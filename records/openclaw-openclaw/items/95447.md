## Summary

No blocking correctness or security finding remains. Current main still overestimates CJK-heavy tool-result payloads on the built-in precheck path, and the clean merge result applies a focused estimator fix with regression coverage; the remaining question is maintainer acceptance of the availability-calibration risk.

## What This Changes

The PR adds CJK-ratio-aware tool-result token-pressure estimation and regression tests for CJK, mixed, Latin-only, JSON, and non-serializable payloads.

## Best Possible Solution

Land the focused estimator change after maintainers accept the CJK calibration; keep the already-merged context-engine skip as a separate partial fix.

## Reproduction Assessment

Yes, source-reproducible: current main estimates tool-result content with the 2 chars/token path after CJK inflation, so a CJK-heavy toolResult can be overestimated enough to route to precheck overflow. I did not run tests because this review is read-only, but the PR body includes terminal output from production helpers showing the after-fix route change.

## Solution Assessment

Yes. The direct estimator change is the best bounded fix for the remaining built-in and mid-turn precheck paths because it changes the owner calculator, preserves non-CJK conservatism, and covers structured and fallback payloads; the merged context-engine skip only addresses a narrower subset.

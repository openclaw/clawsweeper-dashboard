## Summary

Keep open. Current main still uses the fixed `/2` tool-result estimator after CJK char inflation, while this PR adds CJK-ratio-aware routing and focused regression coverage; I found no blocking correctness or security finding, but maintainers should explicitly accept the availability calibration before merge.

## What This Changes

The PR makes preemptive compaction estimate CJK-heavy tool results with the normal CJK-aware ratio while keeping conservative estimates for non-CJK-heavy tool results.

## Best Possible Solution

Land the focused estimator fix with its structured/fallback regressions once maintainers accept the CJK calibration risk; keep the merged context-engine skip as a complementary partial fix.

## Reproduction Assessment

Yes. Source inspection shows current main applies estimateStringChars CJK inflation and then divides tool-result content by the fixed `/2` ratio; a CJK-heavy toolResult passed to estimateLlmBoundaryTokenPressure or shouldPreemptivelyCompactBeforePrompt exercises the false-overflow path.

## Solution Assessment

Yes. This is the best bounded fix for the remaining built-in and mid-turn estimator path because it changes the owner calculator directly, preserves non-CJK conservatism, and covers structured plus non-serializable payloads; the already-merged context-engine skip only fixes a narrower subset.

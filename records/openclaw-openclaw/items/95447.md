## Summary

Keep open for normal maintainer review: current main still uses a fixed 2 chars/token tool-result estimate, this PR targets a real CJK false-overflow path with focused tests and terminal proof, and I found no blocking patch defect.

## What This Changes

The PR adds CJK-ratio-aware tool-result token estimation in the preemptive compaction helper and regression coverage for CJK, mixed, JSON, and non-serializable tool-result payloads.

## Best Possible Solution

Land a focused estimator fix that keeps non-CJK conservatism while aligning CJK-heavy tool-result precheck estimates with estimateStringChars, with maintainer acceptance of the provider-tokenizer heuristic.

## Reproduction Assessment

Yes. Source inspection on current main shows toolResult content always uses estimateStringChars(...)/2, which double-counts CJK-heavy payloads; the PR body's production-helper output demonstrates the before/after route change.

## Solution Assessment

Yes. This is a narrower owner-boundary fix than the earlier context-engine-only workaround because it changes the shared precheck estimator used by pre-prompt and mid-turn calls while preserving the conservative non-CJK path.

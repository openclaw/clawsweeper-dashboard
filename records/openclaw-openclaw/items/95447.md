Keep this PR open: current main still overestimates CJK-heavy tool-result payloads on the built-in precheck path, and the PR is a focused fix with sufficient helper-level terminal proof. The remaining blocker is maintainer acceptance of the availability-routing calibration, not an automated repair.

## What This Changes

The PR makes preemptive-compaction token estimation use a CJK-aware ratio for CJK-heavy tool-result payloads while preserving the conservative tool-result ratio for non-CJK payloads.

## Best Possible Solution

Land the focused estimator fix with its structured/fallback regressions once maintainers accept the availability calibration; keep the merged context-engine skip as a separate partial fix.

## Reproduction Assessment

Yes. Current main routes CJK-heavy tool-result content through `estimateStringChars(...)/2`, so CJK characters inflated for the normal `/4` estimate are effectively double-counted on the tool-result path; I did not run tests because this review is read-only.

## Solution Assessment

Yes. The direct estimator change is the best bounded fix for the remaining built-in and mid-turn precheck path because it updates the owner calculator, preserves non-CJK conservatism, and covers structured and non-serializable payloads; the merged context-engine skip only covers a narrower subset.

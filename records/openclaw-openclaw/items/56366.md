## Summary

Keep open: current main and v2026.6.11 still load and watch `~/.agents/skills` as a built-in personal skill source with no source-level opt-out, and the duplicate source-disable report was closed in favor of this issue. The remaining work is a maintainer product/config decision rather than conservative cleanup.

## What This Changes

Request add a `skills.load` opt-out for automatic `~/.agents/skills` discovery to avoid Claude Code skill conflicts and prompt bloat.

## Best Possible Solution

Choose a backward-compatible skill-source opt-out contract, then implement it consistently across discovery, watcher registration, config schema/help, docs, status behavior, and focused regression tests while preserving current defaults when unset.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a public `skills.load` source opt-out for `agents-skills-personal`, and should that API be a typed source-disable list or a narrower personal-source toggle?

Rationale: The source-level behavior is currently a built-in cross-agent convention, and adding an opt-out expands public config surface that repository policy treats as compatibility-sensitive.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve typed source-disable list (recommended):** Add a documented `skills.load.disableSources`-style enum list and apply it before discovery, watcher registration, status, and prompt snapshot generation.
- **Approve personal-source toggle only:** Add the narrowest possible boolean for the home `.agents/skills` root, reducing API breadth but likely requiring another design pass if project-agent sources need the same treatment later.
- **Decline source opt-out:** Keep the current agentskills convention as always-on and direct users to per-skill disables, prompt limits, or moving Claude Code skills out of the shared directory.

## Reproduction Assessment

Yes. Source inspection on current main shows `loadWorkspaceSkillEntries` always loads `~/.agents/skills` as `agents-skills-personal` and `resolveWatchTargets` watches it, while the strict `skills.load` schema has no disable or ignore field.

## Solution Assessment

Unclear until maintainers choose the public API shape. A source-level opt-out likely belongs in core because the built-in scan is core-owned, but the exact config contract must satisfy the repository's high bar for new config surface.

## Summary

Keep open. Current main and v2026.6.11 have the core SessionBindingService path and Telegram conversation-binding adapter, but Telegram still declares current-conversation placement and does not expose model-visible child-topic subagent session spawning; the remaining work is a maintainer product/API decision with active candidate PRs.

## What This Changes

Request Telegram support for persistent `sessions_spawn(thread:true, mode:"session")` subagent sessions bound to Telegram conversations or forum topics.

## Best Possible Solution

Land or replace the active Telegram candidate with a maintainer-approved SessionBindingService capability that keeps normal Telegram placement current, makes child-topic subagent spawning explicit, updates docs/tests, and refreshes live Telegram proof on the final head.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Telegram expose explicit child-topic session spawning for native `sessions_spawn(thread:true, mode:"session")` while keeping ordinary Telegram top-level binding placement as `current`?

Rationale: Current main has the lower-level binding primitives, but exposing child-topic spawning changes Telegram-visible topic creation, routing, session persistence, and plugin capability semantics.

Likely owner: steipete

Owner reason: The decision extends the core thread-binding architecture introduced in PR 88416 and affects the channel/plugin API boundary.

Owner confidence: high

Options:

- **Review active Telegram implementation (recommended):** Use https://github.com/openclaw/openclaw/pull/82023 as the main design input, rebase or replace it against current core binding policy, and require final-head live Telegram proof.
- **Defer child-topic spawning:** Keep current-conversation Telegram binding only until visible-topic defaults and broader automatic spawn policy are settled.
- **Reject child-topic spawning:** Close this request and associated candidates if maintainers decide internal subagent work should not create Telegram topics.

## Reproduction Assessment

Yes, at source level: current main keeps Telegram top-level placement as `current` while the model-visible `sessions_spawn` thread/session fields are exposed only for automatic child-thread channels. I did not run a live Telegram forum reproduction in this read-only review.

## Solution Assessment

No, not as originally proposed: adding new primary routing through `subagent_spawning` is stale because core now owns thread-bound subagent binding. The better path is an explicit, maintainer-approved SessionBindingService capability for Telegram child-topic spawning.

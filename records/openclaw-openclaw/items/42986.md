## Summary

Keep open. Current main and v2026.6.11 have Telegram conversation-binding primitives and a core SessionBindingService path for explicit thread-bound subagent spawns, but Telegram still defaults to current-conversation placement and the model-visible child-topic session-spawn behavior remains an unresolved product/API decision with open candidate work.

## What This Changes

Request support for Telegram `sessions_spawn(thread: true, mode: "session")` so persistent subagent sessions can bind to Telegram conversations or topics.

## Best Possible Solution

Land or replace the active Telegram candidate with a maintainer-approved core session-binding capability that preserves Telegram's current-topic default, makes child-topic subagent spawning explicit, updates docs/tests, and refreshes live Telegram proof on the final head.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Telegram expose native child-topic session spawning for explicit `sessions_spawn(thread:true, mode:"session")` now, and should that use the current core SessionBindingService capability path while normal Telegram placement stays `current`?

Rationale: Current main has the lower-level binding primitives, but exposing child-topic spawning changes Telegram-visible topic creation, routing, session persistence, and plugin capability/API behavior.

Likely owner: steipete

Owner reason: The open decision extends the core thread-binding architecture introduced in PR 88416.

Owner confidence: high

Options:

- **Review active Telegram implementation (recommended):** Use https://github.com/openclaw/openclaw/pull/82023 as the main design input, rebase or replace it against current core binding policy, and require final-head live Telegram proof.
- **Defer child-topic spawning:** Keep current-conversation Telegram binding only until visible-topic defaults and broader automatic spawn policy are settled.
- **Reject child-topic spawning:** Close this request and associated candidates if maintainers decide internal subagent work should not create Telegram topics.

## Reproduction Assessment

Yes, at source level: current main keeps Telegram top-level placement as `current` while `sessions_spawn` only exposes thread/session fields when automatic child-thread spawn is supported. I did not run a live Telegram forum reproduction in this read-only review.

## Solution Assessment

No, not as originally proposed: adding new primary routing through `subagent_spawning` is stale because core now owns thread-bound subagent binding. The better path is an explicit, maintainer-approved core/session-binding capability for Telegram child-topic spawning.

## Label Justifications

- `P1`: The PR can weaken an explicit filesystem-root restriction in a security-sensitive outbound media path.
- `merge-risk: 🚨 compatibility`: Existing or newly documented root policies could behave differently than operators expect because explicit roots are silently widened by workspace fallback.
- `merge-risk: 🚨 security-boundary`: A deny-all or narrow `tools.fs.roots` policy can still allow workspace-local media reads after `resolvedWorkspaceDir` is appended.
- `merge-risk: 🚨 message-delivery`: The changed media root policy directly controls which local files can be attached or rejected by outbound channel delivery.

## Summary

The PR is a useful and well-evidenced direction, but it still has a merge-blocking security-boundary regression: explicit `tools.fs.roots` are widened by appending the agent workspace after root resolution, so even a deny-all roots policy can still allow workspace-local outbound media reads.

## What This Changes

The PR adds a per-agent `tools.fs.roots` filesystem-root policy with read/write/media modes and threads it through agent tools, outbound media loading, Telegram/Discord delivery, config schema, plugin SDK exports, docs, and tests.

## Best Possible Solution

Configured `tools.fs.roots` should be terminal for host/outbound media access; workspace/default roots should apply only for the legacy default path or when sandbox policy intentionally ignores configured roots.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: configure explicit `tools.fs.roots`, pass a workspace directory, and `resolveAgentScopedOutboundMediaAccess` still appends that workspace to outbound media roots.

## Solution Assessment

No, the direction is plausible but not the best merge shape until explicit roots are treated as the complete allowlist instead of being widened later by workspace fallback.

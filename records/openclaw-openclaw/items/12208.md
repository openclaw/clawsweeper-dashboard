## Summary

Keep open for a maintainer product decision. Current native chat code still renders each message body directly inside the transcript and has no bounded, independently scrollable body path; deciding that every “large” bubble should nest scrolling is a distinct mobile interaction contract, not an established regression fix.

## What This Changes

Add a consistent inner reader for large native chat bubbles so their body can scroll even when content is not otherwise truncated.

## System Context

Native iOS/macOS and Android chat views receive persisted messages and streaming output from the chat view model, render them as bubbles, and place those bubbles inside a transcript-level scroller. This request would change how an individual bubble body handles long content without changing message delivery or stored transcripts.

## Architecture Diagram

flowchart TD
  A[Chat messages and live output] --> B[Native chat transcript]
  B --> C[iOS and macOS bubble renderer]
  B --> D[Android bubble renderer]
  C --> E[Bubble body content]
  D --> E
  E --> F[Maintainer-selected long-content interaction]
  F --> G[Readable mobile chat transcript]

## Best Possible Solution

Define a single native long-content interaction contract—prefer a bounded reader only for selected tall content classes or an explicit expand/read-full affordance—then implement the same rule for persisted and streaming bubbles on SwiftUI and Android with device-level verification.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should native chat use an always-scrollable bounded body for every large/tall bubble, or preserve transcript scrolling and expose a bounded reader only for selected content or an explicit expand action?

Rationale: Current code has no shared `.large` abstraction or established inner-scroll contract, and the choice changes touch, accessibility, and streaming behavior across two mobile UI frameworks.

Likely owner: Chris Zhang

Owner reason: The available path history most directly connects this person to the current native chat renderer surface where the contract would be implemented.

Owner confidence: medium

Options:

- **Define a selective bounded reader (recommended):** Specify height and content-type criteria plus an accessible expansion path, then implement the same contract in SwiftUI and Compose.
- **Always scroll large bodies:** Adopt nested scrolling for every maintainer-defined large bubble and accept the cross-platform gesture and accessibility tradeoffs.
- **Keep transcript-only scrolling:** Decline nested bubble scrolling unless a concrete mobile reproduction demonstrates a blocked reading flow.

## Reproduction Assessment

## Solution Assessment

Unclear. The request identifies a real missing capability, but making every large bubble independently scrollable is not yet shown to be the best interaction model; a maintainer should first choose the bounded-reader versus explicit-expand contract.

## Summary

Keep open: current main still only protects Telegram truncation at UTF-16 surrogate boundaries, so the grapheme-boundary direction is useful, but this PR should not merge as-is because progress clipping now treats 300 graphemes as within the cap even when the payload is more than 300 UTF-16 units, and the PR has no real Telegram proof.

## What This Changes

The PR replaces Telegram progress and draft chunk slicing with Intl.Segmenter-based grapheme-boundary slicing and updates truncation tests.

## Best Possible Solution

Use grapheme-boundary cuts while preserving the existing Telegram progress payload cap, and keep the draft chunk payload-length checks intact.

## Reproduction Assessment

Yes, source inspection gives a high-confidence path: 296 ASCII characters plus a ZWJ family emoji plus xyz is 300 graphemes but 310 UTF-16 units, and the PR head returns it unchanged under the new segments.length guard. I did not run the PR tests locally because this was a read-only review.

## Solution Assessment

No, the PR is a plausible Unicode-boundary fix but not the best shape because it replaces the existing length cap with grapheme-count semantics. The narrow maintainable fix is to cut only at grapheme boundaries while still enforcing the existing code-unit payload cap.

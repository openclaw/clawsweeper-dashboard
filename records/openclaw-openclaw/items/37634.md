- `P1`: The reported regression blocks write-heavy sandboxed skills and workspace operations for users who enabled isolated sandboxing.
- `impact:security`: The issue is about the sandbox filesystem write boundary between an unmounted real workspace and an isolated sandbox workspace.

## Summary

Keep open: current `main` and latest release still make the isolated `workspaceAccess: "none"` sandbox workspace read-only. The source repro is strong, but changing this mode to isolated-writable affects the sandbox security boundary and conflicts with current tests/docs, so it needs maintainer product/security approval.

## What This Changes

The issue requests that `workspaceAccess: "none"` keep the real agent workspace unmounted while making the isolated sandbox `/workspace` writable.

## Best Possible Solution

Clarify the sandbox contract, then either document `none` as intentionally read-only or implement isolated-writable `none` consistently across Docker/browser mounts, local and remote filesystem bridges, write-tool exposure, docs, and regression proof.

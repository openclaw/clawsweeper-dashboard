## Summary

Keep open: current main and v2026.6.11 still make the isolated `workspaceAccess: "none"` sandbox workspace read-only at the mount and filesystem-bridge layers. The exact writable-`none` fix attempts are closed unmerged, and the remaining decision is a sandbox security/product contract rather than conservative cleanup.

## What This Changes

Request to keep the real agent workspace hidden under `workspaceAccess: "none"` while making the isolated sandbox `/workspace` writable.

## Best Possible Solution

Settle the sandbox policy, then make mounts, local and remote bridges, tool exposure, docs, and tests express one consistent `workspaceAccess: "none"` contract.

## Reproduction Assessment

Yes. Source inspection shows `none` selects the isolated sandbox workspace, then current mounts and filesystem bridges mark that workspace read-only unless access is `"rw"`; no live Docker sandbox was run in this read-only review.

## Solution Assessment

Unclear until maintainers choose the sandbox write policy. The requested isolated-but-writable behavior is coherent, but current docs and tests also treat `none` as read-only/no-write, so the best fix must first resolve that contract.

## Summary

Keep open: current main and the latest release still make `workspaceAccess: "none"` read-only for both Docker mounts and filesystem bridge writes, while the discussion shows multiple users are blocked by that behavior. The remaining decision is not whether the report is real, but whether OpenClaw wants `none` to mean isolated-but-writable or a read-only/no-write profile.

## What This Changes

The issue asks for `workspaceAccess: "none"` to keep the real agent workspace hidden while leaving the isolated sandbox workspace writable.

## Best Possible Solution

Have the sandbox/security owner decide the `none` contract; if accepted, restore writes only to the isolated sandbox workspace while keeping the real agent workspace omitted, protected skill roots read-only, docs aligned, and Docker/browser/fs-bridge coverage updated.

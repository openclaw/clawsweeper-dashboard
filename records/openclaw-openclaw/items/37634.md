## Label Justifications

- `P1`: The report describes an upgrade-visible sandbox regression that breaks write-heavy skills and workspace operations for users relying on isolated sandboxing.
- `impact:security`: The issue is about sandbox filesystem write boundaries and whether an isolated workspace may be writable under `workspaceAccess: "none"`.
- `impact:session-state`: The affected workspace is the per-agent or per-session sandbox state area under `~/.openclaw/sandboxes`, where tools, skill materialization, and session-local files operate.

## Summary

Keep open: current main and the latest release still make the isolated `workspaceAccess: "none"` sandbox workspace read-only in mounts and filesystem bridges. The source reproduction is strong, but changing `none` to isolated-writable changes sandbox write-boundary semantics that current docs/tests partly encode as read-restricted, so this needs maintainer security/product approval before implementation.

## What This Changes

The issue requests that `workspaceAccess: "none"` keep the real agent workspace unmounted while making the isolated sandbox `/workspace` writable.

## Best Possible Solution

Decide the sandbox contract, then either document `none` as intentionally read-only or implement isolated-writable `none` consistently across Docker/browser mounts, local and remote filesystem bridges, write-tool behavior, docs, and regression tests while preserving real-workspace isolation and read-only skill protection.

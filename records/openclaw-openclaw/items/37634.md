- `P1`: The issue blocks write-heavy sandboxed skills and file operations for users who enabled isolated sandboxing, and the latest maintainer signal confirms the current behavior is a regression to fix.
- `impact:security`: The issue is about sandbox filesystem write boundaries and must preserve the isolation between the real agent workspace and the sandbox-owned workspace.
- `impact:session-state`: The affected path is the per-session or per-agent sandbox workspace under `~/.openclaw/sandboxes`, which carries isolated run files and materialized skill state.

## Summary

Keep open: current main and v2026.6.11 still make the isolated `workspaceAccess: "none"` sandbox workspace read-only, while a recent maintainer comment on the closed strict-gating PR confirms the intended direction is to keep the real workspace unmounted but make the sandbox-owned `/workspace` writable.

## What This Changes

The issue requests that `workspaceAccess: "none"` keep the real agent workspace hidden while leaving the per-session sandbox `/workspace` writable.

## Best Possible Solution

Implement the maintainer-confirmed isolated-writable `workspaceAccess: "none"` contract across Docker/browser mounts, local and remote filesystem bridges, tool exposure, docs, and regression tests while preserving `ro` and protected-skill read-only behavior.

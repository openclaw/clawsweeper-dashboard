## Label Justifications

- `P1`: This is a source-reproducible sandbox regression affecting real write-heavy agent and skill workflows, but it needs security/product review before implementation.
- `impact:security`: The issue is about sandbox filesystem write boundaries and whether `none` may write inside an isolated workspace.
- `impact:session-state`: The read-only isolated workspace can break per-session temp state, outputs, caches, memory-related writes, and intermediate files inside sandboxed runs.

## Summary

Keep open: current `main` and latest release still make the isolated `workspaceAccess: "none"` `/workspace` read-only in mounts and filesystem bridges, while recent maintainer discussion says the deeper contract should be fixed here rather than hidden by stricter tool gating.

## What This Changes

Make `workspaceAccess: "none"` keep the real agent workspace unmounted while allowing writes inside the isolated sandbox `/workspace`.

## Best Possible Solution

Settle and implement one sandbox contract: `none` keeps the real agent workspace hidden but makes only the isolated sandbox workspace writable, with bridge/tool/docs/tests and live sandbox proof all aligned.

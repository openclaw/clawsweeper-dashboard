## Label Justifications

- `P1`: The report describes a regression that blocks write-heavy sandboxed skills and workspace operations for users who enabled isolated sandboxing.
- `impact:security`: The requested behavior changes sandbox write semantics while preserving host-workspace isolation and protected skill paths.
- `impact:session-state`: The affected path is the per-session or per-agent sandbox workspace under `~/.openclaw/sandboxes`, which carries isolated session files and materialized skills.

## Summary

Keep open: current `main` and the latest release still treat the isolated `workspaceAccess: "none"` sandbox workspace as read-only in Docker/browser mounts plus local and remote filesystem bridges. The source reproduction is clear and prior comments/closed PRs confirm the user impact, but changing `none` to isolated-writable changes a sandbox security boundary that current docs and tests still encode as read-restricted.

## What This Changes

The issue requests that `workspaceAccess: "none"` keep the host workspace hidden while making the isolated per-session sandbox `/workspace` writable.

## Best Possible Solution

Clarify the sandbox contract, then either document `none` as intentionally read-only or implement isolated-writable `none` consistently across Docker, browser, local bridge, remote bridge, write-tool exposure, docs, and protected skill paths.

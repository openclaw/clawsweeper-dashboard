## Label Justifications

- `impact:security`: The requested behavior changes sandbox filesystem read/write boundaries and must preserve host workspace isolation.
- `impact:session-state`: The affected path is the per-session sandbox workspace used for temporary outputs, caches, and session-local files.

## Summary

Keep open: current main and the latest release still make the isolated `workspaceAccess: "none"` sandbox workspace read-only at Docker/browser mount, local fs-bridge, and remote fs-bridge layers. Exact writable-`none` fix attempts are closed unmerged, and the remaining choice changes sandbox security/product semantics rather than being cleanup-closeable.

## What This Changes

The issue requests that `workspaceAccess: "none"` keep the main agent workspace hidden while leaving the per-session sandbox `/workspace` writable.

## Best Possible Solution

Settle the sandbox policy, then implement one consistent `workspaceAccess: "none"` contract across mounts, bridges, tool exposure, docs, and tests while preserving real workspace isolation and protected read-only paths.

## Reproduction Assessment

Yes. Source inspection shows `none` selects an isolated sandbox workspace, but current mount and filesystem bridge code marks that workspace writable only for `"rw"`; no live Docker sandbox was run in this read-only review.

## Solution Assessment

Unclear until maintainers choose the sandbox write policy. The requested isolated-but-writable behavior is coherent, but current docs/tests also encode `none` as write-restricted, so the best fix must first resolve that contract.

## Label Justifications

- `P1`: The reported regression blocks write-heavy sandboxed skills and workspace operations for users who enabled isolated sandboxing.
- `impact:security`: The issue changes sandbox write semantics and the boundary between an unmounted real workspace and an isolated writable sandbox workspace.
- `impact:session-state`: The affected path is the per-session or per-agent sandbox workspace under `~/.openclaw/sandboxes`, which carries isolated session files and materialized skills.

## Summary

Keep open: current `main` and the latest release still treat the isolated `workspaceAccess: "none"` sandbox workspace as read-only in Docker/browser mounts plus local and remote filesystem bridges. The source repro is clear, but changing `none` to isolated-writable conflicts with current docs/tests and should be a deliberate sandbox security/product decision rather than conservative cleanup.

## What This Changes

The issue asks for `workspaceAccess: "none"` to hide the real agent workspace while keeping the per-session isolated sandbox `/workspace` writable.

## Best Possible Solution

Clarify the sandbox contract, then either document `none` as intentionally read-only or implement isolated-writable `none` consistently across Docker, browser, local bridge, remote bridge, write-tool exposure, and docs while preserving read-only skill protection.

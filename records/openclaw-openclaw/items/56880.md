## Summary

Keep open: current main and v2026.6.11 still intentionally serialize one active run per session, so the fast-lane or parallel-turn request remains unimplemented and needs a maintainer scheduler/safety decision.

## What This Changes

The issue requests same-session concurrent or fast-lane message handling so short follow-ups can run while a long agent turn is active.

## Best Possible Solution

Settle a maintainer-approved session responsiveness contract that preserves session-state safety, then implement either bounded steer/yield/interrupt admission or an opt-in fast lane with docs, schema, tests, and real channel proof.

## Summary

Keep open: current main still serializes each session lane and only provides steering, followup, collect, and interrupt mitigations rather than true same-session parallel turns. The linked fast-lane PRs are either closed or conflicting, and the remaining behavior needs a maintainer product/safety decision.

## What This Changes

The issue requests concurrent or fast-lane handling for new messages in an already-active session so short followups are not blocked behind long agent turns.

## Best Possible Solution

Define the supported concurrency model first, then land a focused target-repo PR with session-state/tool-safety tests and real Discord or channel proof; the existing steering PR can cover only the active-run steering subset.

## Reproduction Assessment

Yes, from source inspection: same-session work enters `session:<key>` lanes with `maxConcurrent: 1`, and active followup/collect messages enqueue instead of spawning parallel turns. I did not run a live Discord reproduction in this read-only review.

## Solution Assessment

No current solution is complete: steering and interrupt modes mitigate some cases, but they do not provide the requested independent same-session fast-lane or parallel-turn behavior. The best fix needs a maintainer-approved concurrency contract rather than another unreviewed fork fast-lane patch.

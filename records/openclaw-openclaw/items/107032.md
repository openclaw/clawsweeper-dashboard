## Summary

Keep this issue open for concrete current-version evidence, but do not queue a repair. Current main has no cited `message-relayer.ts` or Discord `api-client.ts`; outbound Discord sends are awaited through plugin-owned retry code that explicitly handles HTTP 429, and existing coverage verifies a rejected 429 is retried successfully. The report still lacks an affected version, rejection stack, sanitized logs, rate-limit headers, or repeatable scenario showing a promise escaping this path.

## What This Changes

Prevent Discord rate-limit failures during streamed outbound delivery from surfacing as unhandled promise rejections that terminate the gateway.

## Best Possible Solution

Preserve the awaited, plugin-owned Discord retry boundary; if a current-main reproduction identifies another streaming caller, route that caller through the same retry helper and add a regression test proving the 429 is awaited, retried, and never reaches `unhandledRejection`.

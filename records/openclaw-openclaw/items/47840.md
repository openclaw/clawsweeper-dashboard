## Summary

Keep open. Current main still has source-reproducible raw provider display/filter/export/aggregate paths in the Control UI usage surface, and the only linked implementation PR for this issue is closed unmerged; the remaining blocker is the maintainer product contract for canonical-only display versus canonical display with alias context.

## What This Changes

The issue asks for Control UI provider labels and related model/provider views to display canonical provider ids instead of raw configured aliases.

## Best Possible Solution

Define one provider-display/canonicalization contract for Control UI usage surfaces, then apply it consistently across server aggregates, client aggregates, filters, CSV export, and visible badges, with alias context in the UI if maintainers want users to see what they configured.

Rationale: The source fix is clear, but the product contract affects visible labels, query/filter values, CSV output, aggregate keys, and how users reconcile UI labels with their openclaw.json aliases.

Owner confidence: medium

Options:

- **Canonical primary plus alias context (recommended):** Use canonical ids for keys, filtering, exports, and primary labels while optionally showing the configured alias as a tooltip or secondary detail where visible.
- **Canonical only everywhere:** Normalize all display, query, export, and aggregate provider values to canonical ids and do not surface the configured alias in the Control UI.
- **Preserve raw configured labels:** Keep raw configured provider ids in display/export paths and treat internal canonical ids as implementation-only behavior.

## Reproduction Assessment

Yes. Source inspection on current main shows provider values are still lowercased or rendered directly in usage filters, CSV export, UI badges, and server/client aggregate keys instead of being canonicalized through plugin alias metadata.

## Solution Assessment

No, the issue's render-only sketch is too narrow for the current code. The best fix should centralize provider alias canonicalization for the usage data path and apply it before display, query/export, and aggregate boundaries rather than patching one table cell.

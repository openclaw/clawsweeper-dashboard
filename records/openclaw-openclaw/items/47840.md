## Summary

Keep open. Current main and v2026.6.11 still route the affected Control UI Sessions/Usage display, filters, CSV, and aggregate keys through raw provider strings, while the direct implementation attempt is closed unmerged and the exact provider alias display contract still needs maintainer confirmation.

## What This Changes

The issue asks for Control UI provider displays to show canonical normalized provider ids, such as `zai`, instead of raw alias config values such as `bailian`.

## Best Possible Solution

Define the supported provider-display canonicalization contract, then normalize derived Usage/Sessions display, filters, query suggestions, CSV, and aggregate keys while preserving raw stored config and session fields.

## Reproduction Assessment

Yes. Current main still has multiple Usage/Sessions paths that render or group `modelProvider`, `providerOverride`, or usage `entry.provider` directly, so raw provider strings can remain visible from source inspection.

## Solution Assessment

No, not exactly as proposed. Applying a generic `Jp()`-style helper to every display path is not currently the best fix because the current generic provider normalizer is lowercase-only and raw config/session data should remain intact; the safer path is a maintainer-approved display contract for derived UI and usage surfaces.

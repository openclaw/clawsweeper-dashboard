## Summary

Keep open. Current main and the latest release still lack the requested end-to-end channel creation path: Discord has partial provider/runtime support, but the CLI/docs expose only channel info/list and Slack still has no channel-create discovery, dispatch, scope, or gate.

## What This Changes

Request to add a native message-tool or CLI channel creation action for Slack, Discord, and similar messaging providers.

## Best Possible Solution

Approve a provider-owned, default-off channel-creation design, then implement Slack discovery/runtime/setup/docs/tests and land or replace the narrower Discord CLI wiring without moving provider-specific admin policy into core.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose provider channel creation through the message tool/CLI, and what explicit admin gate or requester authorization must protect Slack and Discord workspace/server mutations?

Rationale: Channel creation lets agents mutate provider-side workspace/server structure, and current message.action is an operator.write method; automation cannot safely choose the permanent authority boundary.

Likely owner: steipete

Owner reason: steipete already reviewed this issue’s exact surfaces and current history points to Peter Steinberger on the affected current-main files.

Owner confidence: high

Options:

- **Approve explicit admin-gated provider implementation (recommended):** Add provider-owned channel creation behind default-off admin/channel gates, with Slack setup/docs/scopes, Discord CLI/tool wiring, and tests for both allowed and denied paths.
- **Limit scope to Discord CLI for now:** Land or replace the focused Discord CLI subcommand work while keeping Slack channel creation and broader admin actions blocked until a separate Slack security design is approved.
- **Decline native channel creation for now:** Keep channel creation as an external provider/API workflow and document that OpenClaw message actions do not manage workspace/server structure yet.

Yes, source-level. Current main and v2026.6.11 show the shared action name and partial Discord provider support, while the CLI/docs and Slack paths still lack an end-to-end channel creation surface.

## Solution Assessment

Unclear until maintainers decide the authority model. The maintainable direction is provider-owned channel creation behind explicit default-off gates, not a generic core-only command that bypasses provider policy.

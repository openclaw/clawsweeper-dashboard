## Summary

Keep open: current main still exposes only service-account Google Chat credentials and does not provide delegated user-auth routing for reactions, attachment uploads, or email-alias direct-message lookup. The official Google Chat API requires user authentication for the requested reaction and upload operations, so the central capability remains missing. ([developers.google.com](https://developers.google.com/workspace/chat/upload-media-attachments?utm_source=openai))

## What This Changes

Add optional delegated Google Chat user authentication for reactions, media uploads, reaction-based typing, and proactive direct messages while retaining service-account webhook and bot operations.

## Best Possible Solution

The bundled Google Chat plugin should own an explicit delegated-auth setup flow with minimal scopes, SecretRef-aware credential handling, refresh and revocation support, clear sender attribution, operation-specific client selection, and documented app-auth fallbacks.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which delegated Google Chat identity model should the bundled plugin support for user-auth-only operations, and how should that identity be selected and stored?

Rationale: Per-user OAuth and domain-wide delegation differ in consent, administrator control, sender attribution, token lifecycle, and blast radius; implementing either without an explicit contract could expose long-lived credentials or send messages as an unexpected user.

Likely owner: steipete

Owner reason: They have the strongest available combination of relevant commit provenance and prior review involvement on this exact product and security decision.

Owner confidence: high

Options:

- **Scoped user OAuth flow (recommended):** Add a plugin-owned login flow that obtains only the required Chat scopes, stores refresh credentials through approved secret/token surfaces, and explicitly binds each account to the consenting sender identity.
- **Domain-wide delegation only:** Require Workspace administrators to configure service-account impersonation and a delegated subject, trading consumer usability for centralized organizational control.
- **Retain app authentication:** Keep service-account-only behavior and pursue graceful reaction/media fallbacks without enabling user-attributed Google Chat actions.

## Reproduction Assessment

Yes at the source and upstream-contract level: configure service-account app authentication, then invoke reaction creation, attachment upload, or email-alias user lookup; the current credential path supplies `chat.bot`, while Google requires user authentication for the requested reaction and upload methods. A live current-main Workspace run was not established in this review.

## Solution Assessment

No, the raw `userOAuth` config sketch is not yet the best complete solution because it bypasses decisions about consent, token storage, refresh rotation, sender identity, revocation, and domain-wide delegation. A plugin-owned setup and credential lifecycle with operation-specific routing is safer and more maintainable.

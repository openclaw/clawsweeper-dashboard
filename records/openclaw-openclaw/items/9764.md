## Summary

Keep open. Current main and the latest release still use only service-account Google Chat auth with the `chat.bot` scope, while the requested user OAuth model would add new secret-bearing auth/config behavior that needs maintainer product and security direction.

## What This Changes

Request optional user OAuth credentials for the Google Chat plugin so reactions, attachment uploads, and proactive DMs can use user-scoped Google Chat APIs while service-account auth remains for webhooks and bot operations.

## Best Possible Solution

Add optional, secret-aware user OAuth support inside the Google Chat plugin, route only user-scoped operations through it, keep service-account auth for webhook/app operations, and document the fallback when user OAuth is absent.

## Reproduction Assessment

Yes at source level: current main accepts only service-account Google Chat credentials, builds only a `chat.bot` scoped auth client, and routes reaction/upload/DM APIs through that token. I did not run a live Google Workspace OAuth repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the OAuth product shape. The requested direction is the right capability class, but the best implementation must be secret-aware, scoped per operation, and explicitly preserve service-account webhook behavior.

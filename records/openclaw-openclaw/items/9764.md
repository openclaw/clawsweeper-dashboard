## Label Justifications

- `P2`: This is a meaningful Google Chat capability gap with real channel impact, but it requires auth/config design rather than emergency core-runtime handling.
- `impact:security`: The requested solution would introduce OAuth client secrets, refresh tokens, user scopes, and credential routing to the Google Chat plugin.
- `impact:message-loss`: Without user-auth routing or a fallback, Google Chat reactions, native attachment uploads, and some proactive DM paths can fail before the expected user-visible result is delivered.
- `impact:auth-provider`: The issue is specifically about choosing service-account versus user OAuth credentials and scopes for Google Chat operations.

## Summary

Keep open. Current main and v2026.6.11 still use service-account Google Chat auth with the single `chat.bot` scope, while the requested user OAuth credential model and scoped routing for reactions, uploads, and email-alias DMs is still missing; the linked media-fallback PRs only mitigate one symptom.

## What This Changes

The issue requests optional Google Chat user OAuth so reactions, attachment uploads, and proactive DMs can use user-level Google Chat scopes alongside existing service-account app auth.

## Best Possible Solution

Add a plugin-owned, secret-aware Google user OAuth credential model and scoped OAuth client routing for only the operations that require user auth, while keeping service-account auth for webhook verification and existing bot-level sends.

## Reproduction Assessment

Yes, at source level. Current main only accepts service-account Google Chat credentials and always requests `chat.bot`, while the strict config schema has no user OAuth credential branch.

## Solution Assessment

No, not as the issue's config sketch alone. User OAuth is the plausible product direction, but the best fix needs a maintainer-approved SecretRef/redaction, scope, fallback, documentation, and live-proof design.

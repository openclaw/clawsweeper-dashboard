## Summary

Keep open. Current main and v2026.6.11 still document and implement Google Chat as service-account/app-auth only; media-link fallback work mitigates one delivery failure but does not provide the requested reactions, native uploads, or email-alias direct messages. The remaining work requires a maintainer and security decision on the supported user-credential model.

## What This Changes

Add optional Google Chat user authentication for reactions, native media uploads, and proactive direct messages while retaining service-account auth for webhook and bot operations.

## Best Possible Solution

Keep service-account auth as the compatible default, use the maintained Google authentication library plus existing SecretRef patterns for an explicitly configured user identity, and route only documented user-auth-required operations through that identity with clear unavailable-operation diagnostics when it is absent.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which user-authentication contract should the bundled Google Chat plugin support for reactions, uploads, and email-alias direct messages?

Rationale: Source and API contracts prove that app authentication cannot supply the requested operations, but they cannot choose between end-user OAuth, Workspace domain-wide delegation, or intentionally retaining app-only behavior; each option has different security and product consequences.

Likely owner: steipete

Owner reason: They are the strongest available routing candidate because they committed the imported surface and already reviewed the exact product boundary in this issue.

Owner confidence: medium

Options:

- **Explicit user OAuth identity (recommended):** Add a SecretRef-aware, per-account user credential with narrowly scoped operation routing while preserving service-account auth as the default.
- **Workspace delegation only:** Support service-account domain-wide delegation and user impersonation, accepting administrator setup and organization-only applicability.
- **Remain app-auth only:** Do not add user credentials; instead make every unsupported operation degrade predictably through links, warnings, or unavailable capabilities.

## Reproduction Assessment

Yes for the reported limitation: configure the documented service-account Google Chat channel and invoke reaction creation, attachment upload, or email-alias DM lookup; current source, docs, and Google API contracts show those paths lack the required user identity. This establishes the missing capability rather than a regression in an existing user-OAuth contract.

## Solution Assessment

Unclear pending product direction. Optional dual authentication is plausible, but the proposed raw refresh-token config is not the safest final interface; it should use existing secret-resolution patterns, maintained Google auth primitives, explicit identity routing, and compatibility proof.

## Label Justifications

- `P2`: This is a normal-priority Google Chat channel improvement with clear user impact but a bounded plugin surface and no evidence of an unusable core runtime.
- `impact:security`: The requested fix would introduce Google OAuth refresh-token/client-secret handling and scoped user credentials.
- `impact:message-loss`: Media uploads and reaction/action paths can fail or be skipped under service-account auth, preventing expected channel output.
- `impact:auth-provider`: The central missing behavior is auth-provider routing between service-account `chat.bot` auth and user OAuth scopes.

## Summary

Keep open: current main and v2026.6.11 still have Google Chat wired to service-account credentials and the `chat.bot` scope only, with no user OAuth config, refresh-token credential model, or OAuth-aware routing for reactions, attachment upload, reaction typing, or email-alias direct messages.

## What This Changes

The issue requests optional Google Chat user OAuth support for reactions, media uploads, and proactive direct messages while preserving service-account auth for existing bot/webhook behavior.

## Best Possible Solution

Keep the issue open and design a Google Chat plugin-owned, secret-aware user OAuth credential model that routes only the operations requiring user scopes through user auth while retaining service-account auth for webhook verification and bot-level sends.

## Reproduction Assessment

Yes, at source level: current main has only service-account credential resolution and `chat.bot` auth, while the affected API methods are wired through that same token path. I did not perform a live Google Chat workspace run in this read-only review.

## Solution Assessment

Unclear as proposed: user OAuth is the right capability gap, but the exact credential/config surface, SecretRef or auth-profile storage model, and fallback behavior need maintainer security/product review before an implementation PR.

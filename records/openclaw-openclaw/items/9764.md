## Label Justifications

- `impact:security`: The requested fix would add refresh-token credentials and broader Google user OAuth scopes.

- `impact:auth-provider`: The issue is fundamentally about credential mode, OAuth scopes, SecretRef-style resolution, and routing operations to the right Google Chat auth client.

## Summary

Keep open. Current main and the latest release still use Google Chat service-account credentials with the `chat.bot` scope only; the open media-fallback work covers one delivery-loss symptom, not the requested user OAuth credential model for reactions, uploads, and user-scoped DM lookup.

## What This Changes

Request optional Google Chat user OAuth support alongside service-account auth for reactions, media uploads, reaction typing, and proactive DMs.

## Best Possible Solution

Implement a Google Chat plugin-owned, secret-aware user OAuth credential model and route only user-scope operations through that client while preserving service-account webhook verification and bot-level sends.

## Reproduction Assessment

Yes. Source inspection shows current main has service-account credential resolution, a single `chat.bot` auth path, and upload/reaction/direct-message helpers that all reuse that token path; I did not run a live Google Chat workspace in this read-only review.

## Solution Assessment

Unclear as proposed. A plugin-owned user OAuth path is the right boundary, but the exact config, SecretRef, refresh-token, fallback, and scope model needs maintainer product/security approval before implementation.

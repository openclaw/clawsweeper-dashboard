- `impact:security`: The requested design would store and refresh delegated Google Workspace credentials with authority beyond the current app identity.

## Summary

Current main still lacks Google Chat user OAuth routing: outbound access tokens use service-account credentials with the `chat.bot` scope, account resolution has no user-OAuth credential branch, and current docs explicitly withhold reactions and outbound attachments under service-account auth. The request remains useful, but delegated credentials, sender identity, consent, storage, and fallback semantics require maintainer and security direction.

## What This Changes

Add optional user OAuth credentials and route Google Chat reactions, attachment uploads, reaction typing, and proactive email-address DMs through user-authenticated clients while retaining service-account webhook and bot operations.

## Best Possible Solution

Define one plugin-owned delegated-auth contract with SecretRef-backed credentials, explicit consent and scope documentation, per-operation auth selection, stable sender attribution, safe refresh and revocation, and tested service-account-only fallbacks before enabling each capability incrementally.

## Risks / Open Questions

- User OAuth introduces long-lived refresh tokens and delegated Google Workspace authority, so SecretRef support, redaction, revocation, scope minimization, and cache invalidation must be designed first.
- Routing some operations as a user and others as the Chat app can change sender attribution, authorization, audit trails, and space or DM visibility.
- Reactions, native uploads, typing reactions, and proactive email-alias DMs may require different scopes or domain-wide delegation constraints, making one shared fallback rule unsafe.
- Runtime code currently advertises reaction and upload actions while current docs say they are unavailable under service-account auth, leaving a contract inconsistency to resolve alongside OAuth design.

## Label Justifications

- `P2`: This is a meaningful bundled-channel enhancement with confirmed capability gaps, but it is not an emergency or current regression in documented service-account behavior.
- `impact:security`: The request introduces delegated user credentials, consent, token refresh, and possible impersonation with access to Workspace user data and actions.
- `impact:message-loss`: Google Chat users cannot deliver native outbound files under the supported app-auth identity, and media-bearing workflows can therefore fail or require degraded delivery.
- `impact:auth-provider`: The central request is a new credential type and operation-specific routing between app and delegated-user authentication.

## Summary

Keep open: current main deliberately remains service-account-only and explicitly disables reactions and outbound attachments, while Google requires user authentication for those operations. The requested capability is valid but needs maintainer product and security decisions for delegated identity, consent, credential storage, and fallback behavior before implementation.

## What This Changes

Add optional Google Chat user authentication for reactions, attachment uploads, reaction typing indicators, and proactive direct-message lookup while retaining service-account authentication for app operations and webhook verification.

## Best Possible Solution

Add a plugin-owned dual-auth design that keeps service-account authentication as the compatible default, stores delegated credentials through existing SecretRef/auth-profile facilities, routes only explicitly approved user-only operations through a scoped user client, and exposes clear setup, consent, revocation, attribution, and unavailable-capability diagnostics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which delegated Google Chat identity model should the bundled plugin support for user-only operations, and how should users provision and select that identity?

Rationale: Per-user OAuth, administrator-approved domain-wide delegation, and remaining app-auth-only have materially different consent, storage, impersonation, attribution, and setup consequences that cannot be selected safely from implementation evidence alone.

Likely owner: steipete

Owner reason: They committed the original channel, have substantial subsequent area history, and already provided maintainer-side review context for this exact product decision.

Owner confidence: high

Options:

- **Scoped user OAuth profiles (recommended):** Add plugin-owned OAuth setup and SecretRef-backed credentials, preserve service-account defaults, and route only approved reaction, upload, and user-DM operations through the selected user profile.
- **Domain-wide delegation only:** Support administrator-configured service-account impersonation for managed Workspace deployments, accepting a higher enterprise setup and privilege burden.
- **Keep app authentication only:** Do not add delegated identity; retain explicit unsupported-operation diagnostics and improve graceful text-link or message-mode fallbacks instead.

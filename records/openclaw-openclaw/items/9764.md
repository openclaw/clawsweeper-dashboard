## Label Justifications

- `P2`: This is a normal-priority Google Chat capability gap with real channel impact, but it requires new auth/config design rather than an urgent core-runtime outage.
- `impact:security`: The requested fix would add OAuth client secrets, refresh tokens, and scope routing to the Google Chat credential surface.
- `impact:message-loss`: Current service-account auth can fail or skip media uploads and reaction-style feedback that users expect to be delivered.
- `impact:auth-provider`: The issue is specifically about selecting service-account versus user OAuth credentials and scopes for Google Chat operations.

## Summary

Keep open. Current main and the latest release still use Google Chat service-account auth with the `chat.bot` scope only; the open media-fallback work covers one symptom but does not add the requested user OAuth credential model.

## What This Changes

The issue requests optional Google Chat user OAuth support for reactions, attachment uploads, reaction typing, and proactive DM lookup while keeping service-account auth for existing bot/webhook operations.

## Best Possible Solution

Add a plugin-owned, secret-aware Google user OAuth credential model and scoped OAuth client routing for only the operations that require user auth, while keeping service-account auth for webhook verification and existing bot sends.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? No live Google Workspace repro was run, but source inspection gives a high-confidence source reproduction: current main only accepts service-account credentials and always requests `chat.bot` for Google Chat API calls.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainer/security direction is set; user OAuth is the plausible product path, but the durable fix needs the right SecretRef, scope, fallback, docs, and live-proof shape.

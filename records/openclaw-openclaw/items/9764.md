## Label Justifications

- `P2`: This is a meaningful Google Chat channel capability gap with clear user-visible delivery/auth impact, but it needs product and security design rather than emergency handling.
- `impact:security`: The requested solution would add client secrets, refresh tokens, broader Google Chat scopes, and credential routing decisions.
- `impact:message-loss`: Without user OAuth or a defined fallback, media uploads and reaction/proactive-DM operations can fail before the user receives the intended result.
- `impact:auth-provider`: The issue is fundamentally about Google Chat auth mode, scope routing, credential resolution, and SecretRef-compatible token handling.

## Summary

Keep open: current main and v2026.6.11 still wire Google Chat to service-account credentials and the `chat.bot` scope only, with no user OAuth config, refresh-token credential path, or scoped client routing for reactions, attachment upload, reaction typing, or email-alias DM lookup. The related media-upload PRs are useful fallback work for app-auth 403s, but they do not implement the broader user OAuth request.

## What This Changes

Requests optional Google Chat user OAuth credentials so reactions, media uploads, reaction typing, and proactive DM/email-alias lookup can use user-level scopes while service-account auth remains for webhook and bot operations.

## Best Possible Solution

Keep this as the canonical Google Chat user OAuth design item and implement a plugin-owned, secret-aware OAuth credential model with scoped user clients for reactions, attachment uploads, reaction typing, and proactive DM lookup while preserving service-account webhook verification and documenting absent-OAuth fallback behavior.

## Reproduction Assessment

Yes at source level. Current main has service-account-only config, credential resolution, and chat.bot auth while the reported reaction, upload, typing-reaction, and DM lookup helpers all route through that same account path; I did not run a live Google Chat workspace repro in this read-only review.

## Solution Assessment

Unclear as a final implementation. The plugin-owned optional user OAuth direction fits the problem, but maintainers still need to approve the exact secret storage, scope model, fallback behavior, and docs before an implementation PR is safe.

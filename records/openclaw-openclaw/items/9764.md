## Summary

Keep open. Current main still deliberately supports Google Chat service-account authentication only; the related media-fallback work mitigates one delivery symptom but does not add user-auth credentials, reactions, native uploads, or user-scoped direct-message lookup. The feature is vision-aligned, but maintainers must first choose the security and product boundary for user OAuth versus delegated impersonation.

## What This Changes

Add optional Google Chat user authentication and route reactions, native media uploads, and proactive direct-message lookup through user-scoped credentials while retaining service-account behavior.

## Best Possible Solution

Define one plugin-owned, SecretRef-aware Google Chat user-auth contract; route only APIs that require user authentication through it, retain service-account webhook verification and bot sends, expose clear behavior when user auth is absent, and require live fresh-setup plus existing-service-account upgrade proof.

Owner confidence: high

Options:

- **Scoped user OAuth (recommended):** Add client credentials and refresh-token SecretRefs, using the user client only for operations whose Google contract requires user authentication.
- **Domain-wide delegation:** Support service-account impersonation of a configured Workspace user, accepting the broader administrator setup and privilege boundary.
- **Keep app auth only:** Retain service-account-only operation and rely on explicit unsupported errors or safe text-link fallbacks instead of native user-auth features.

## Reproduction Assessment

Yes at source level: current main has only service-account credential resolution, fixes access-token acquisition to `chat.bot`, and explicitly rejects outbound attachments because user OAuth is unsupported. This review did not exercise a live Google Workspace.

## Solution Assessment

Unclear until maintainers choose end-user OAuth versus domain-wide delegation and the exact supported operations. Dual authentication is a reasonable boundary, but inline client secrets and refresh tokens should not be the preferred canonical configuration; SecretRefs and narrowly scoped routing are safer.

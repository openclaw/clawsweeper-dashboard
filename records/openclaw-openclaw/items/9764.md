## Summary

Keep open. Current main and v2026.6.11 still expose Google Chat through service-account `chat.bot` auth only, while adding user OAuth would introduce secret-bearing config and scoped credential routing that needs maintainer product and security direction.

## What This Changes

The issue requests optional Google Chat user OAuth support for reactions, media uploads, reaction typing, and proactive DM/email-alias operations while keeping service-account auth for webhook and bot operations.

## Best Possible Solution

Add a plugin-owned, secret-aware Google user OAuth credential model with scoped client routing for only user-auth-required operations, while preserving service-account auth for webhook verification and existing bot sends.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Source-level yes: current main accepts only service-account credentials and always requests `chat.bot` for Google Chat API calls, so the proposed `userOAuth` config and scoped operation routing are absent. I did not run a live Google Workspace OAuth repro in this read-only review.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainer and security direction is set; user OAuth is the plausible product path, but the durable fix needs the right SecretRef, scope, fallback, and documentation shape rather than the issue's config sketch alone.

## Summary

Keep open. Current main and the latest release still use service-account Google Chat credentials with the `chat.bot` scope only, and the open media-fallback PRs address one upload-loss symptom rather than the requested user OAuth credential model.

## What This Changes

The issue requests optional user OAuth support for the bundled Google Chat channel so reactions, attachment uploads, reaction typing, and proactive DM/email-alias operations can use user-level scopes while service-account auth remains available for bot/webhook behavior.

## Best Possible Solution

Add a maintainer-approved, secret-aware Google Chat user OAuth credential model inside the bundled plugin, route only user-scope-required operations through that client, keep service-account auth for webhook and bot-level behavior, and document fallback behavior when user OAuth is absent.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence reproduction path: current main accepts only service-account Google Chat credentials and uses the `chat.bot` scope, so the requested user OAuth operations cannot be configured through the shipped plugin.

## Solution Assessment

Unclear until maintainers choose the permanent auth/config shape. The direction is valid, but the best fix must use existing SecretRef/redaction patterns and a deliberate split between service-account and user OAuth clients rather than an ad hoc config block.

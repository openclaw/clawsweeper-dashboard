## Label Justifications

- `P2`: This is a normal-priority Google Chat capability gap with real channel impact, but it is a new auth/config feature rather than an urgent core-runtime outage.
- `impact:security`: The requested fix would add OAuth client secrets, refresh tokens, and sensitive Google scopes to the Google Chat credential surface.
- `impact:message-loss`: Without user-auth-aware routing, reactions and native media uploads can fail or be skipped instead of reaching Google Chat users.
- `impact:auth-provider`: The issue is about selecting service-account versus user OAuth credentials and scopes for Google Chat operations.

## Summary

Keep open. Current main and the latest release still lack a Google Chat user OAuth credential model, and the related media-fallback work only mitigates one service-account failure path rather than adding scoped user-auth routing.

## What This Changes

Add optional Google Chat user OAuth support for reactions, attachment uploads, reaction typing, and proactive direct-message lookup while preserving service-account webhook and bot operations.

## Best Possible Solution

Add a plugin-owned, secret-aware Google Chat user OAuth credential model and route only user-auth-required operations through scoped user OAuth clients, while keeping service-account auth for webhook verification and existing bot-level sends.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes by source inspection: current main accepts only service-account credentials for Google Chat and always requests `chat.bot` for API calls, so user-OAuth-only operations have no configured route.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainer/security direction is set; user OAuth is the right capability family, but the durable solution needs a reviewed SecretRef, scope, fallback, and documentation shape rather than only the issue's config sketch.

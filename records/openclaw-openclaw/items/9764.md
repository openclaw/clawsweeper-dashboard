## Label Justifications

- `P2`: This is a normal-priority Google Chat capability gap with real channel impact, but it is a new auth/config feature rather than an emergency core-runtime outage.
- `impact:security`: The requested fix would add OAuth client secrets, refresh tokens, and scoped Google credentials to the Google Chat surface.
- `impact:message-loss`: Without user-auth routing or fallback, Google Chat reactions and native media uploads can fail or be unavailable for expected outbound delivery.
- `impact:auth-provider`: The issue centers on selecting service-account versus user OAuth credentials and scopes for Google Chat operations.

## Summary

Keep open. Current main and v2026.6.11 still route Google Chat through service-account credentials and the `chat.bot` scope only; the related media-fallback PRs address one app-auth upload symptom but do not add the requested user OAuth credential model, scoped routing, or fallback behavior for reactions, native uploads, and proactive DM lookup.

## What This Changes

Add optional Google Chat user OAuth credentials and scoped routing for reactions, media uploads, reaction typing, and proactive direct-message lookup while keeping service-account auth for webhook/bot operations.

## Best Possible Solution

Add a plugin-owned, secret-aware Google user OAuth credential model and scoped OAuth client routing for only operations that require user auth, while keeping service-account auth for webhook verification and existing bot sends.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: current main only accepts Google Chat service-account credentials and always requests the `chat.bot` scope for affected Google Chat API calls; no live Google Workspace repro was run in this read-only review.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainer/security direction is set; plugin-owned user OAuth is the plausible product path, but the config sketch needs a durable SecretRef, scope, fallback, docs, and live-proof design before implementation.

## Label Justifications

- `P2`: This is a bounded Google Chat capability gap with real channel impact, but it requires a new auth/config feature rather than an urgent core-runtime repair.
- `impact:security`: The requested fix would add OAuth client secrets, refresh tokens, scopes, and credential routing to the Google Chat channel.
- `impact:message-loss`: Without user-auth-aware handling, media upload and reaction-style feedback paths can fail or be skipped for Google Chat users.
- `impact:auth-provider`: The core issue is choosing and routing Google Chat service-account versus user OAuth credentials and scopes.

## Summary

Keep open. Current main and the latest release still have Google Chat wired to service-account credentials and the `chat.bot` scope only; the open media-fallback PRs address one delivery symptom but do not add the requested user OAuth credential model.

## What This Changes

Request optional Google Chat user OAuth alongside service-account auth for reactions, native media uploads, reaction typing, and proactive DM lookup.

## Best Possible Solution

Add a plugin-owned, secret-aware Google Chat user OAuth credential model and route only user-scope operations through it, while keeping service-account auth for webhook verification and existing bot-level sends.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes by source inspection: current main only accepts service-account credentials and always requests the `chat.bot` scope for Google Chat API calls, so no user OAuth path can be selected for the reported operations.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainer/security direction is set; user OAuth is the plausible product path, but the durable fix needs a vetted SecretRef, scope, fallback, docs, and live-smoke shape rather than only the sketched config block.

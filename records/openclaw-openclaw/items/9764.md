## Label Justifications

- `P2`: This is a meaningful Google Chat channel capability gap with limited blast radius, but it is a new auth/config feature rather than an urgent core outage.
- `impact:security`: The requested fix would add OAuth client secrets, refresh tokens, user scopes, and credential routing to the Google Chat channel.
- `impact:message-loss`: Current service-account auth can leave media uploads and reaction-style feedback undelivered when Google requires user-scoped credentials.
- `impact:auth-provider`: The issue is specifically about selecting service-account versus user OAuth credentials and scopes for Google Chat operations.

## Summary

Keep open. Current main and the latest release still only model Google Chat credentials as service-account auth with the `chat.bot` scope, so the requested user OAuth path for outbound reactions, media upload, reaction typing, and email-alias DM lookup remains unimplemented.

## What This Changes

Request adding optional Google Chat user OAuth credentials alongside service-account auth for user-scoped reactions, media uploads, and proactive DM lookup.

## Best Possible Solution

Add a plugin-owned, secret-aware Google Chat user OAuth credential model and scoped user-auth client routing only for operations that require user auth, while preserving service-account auth for webhook verification and existing bot sends.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: current main only accepts service-account credentials and always requests the `chat.bot` scope for Google Chat API calls, while the requested user OAuth config path is absent.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainers decide the permanent credential shape; user OAuth is the right capability direction, but the maintainable implementation needs explicit SecretRef, scope, fallback, docs, and live-proof design rather than only the sketched config object.

## Label Justifications

- `P2`: This is a meaningful Google Chat channel capability and delivery/auth gap, but it is an optional-channel feature requiring product and security design rather than an emergency runtime outage.
- `impact:security`: The requested solution would add user OAuth credentials, refresh-token handling, and new Google scopes to the Google Chat channel.
- `impact:message-loss`: Without a user-auth path or fallback, media upload and reaction-related operations can fail instead of delivering the intended channel action.
- `impact:auth-provider`: The issue is fundamentally about Google Chat auth mode selection, scopes, credential resolution, and SecretRef-compatible token handling.

## Summary

Keep this issue open: current main and the latest release still use Google Chat service-account auth with the `chat.bot` scope only, so the requested user OAuth path for outbound reactions, attachment upload, and email-alias DM lookup remains missing. The external Google Drive workaround is useful prior art, but it is not an OpenClaw implementation of this OAuth feature.

## What This Changes

Request to add optional Google Chat user OAuth credentials and route reaction, media upload, and proactive DM operations through user-scoped auth while preserving service-account webhook behavior.

## Best Possible Solution

Implement this inside the Google Chat plugin as a strict, secret-aware user OAuth credential model with scoped user clients for reactions, attachment upload, reaction typing, and email-alias DM lookup, while keeping service-account auth for webhook verification and bot-level sends.

## Reproduction Assessment

Yes for a source-level reproduction: current main has service-account-only Google Chat credentials, a hardcoded `chat.bot` auth scope, and no accepted `userOAuth` schema. I did not run a live Google Chat workspace repro in this read-only review.

## Solution Assessment

Unclear as proposed because adding `userOAuth` directly is plausible but security- and compatibility-sensitive. The maintainable path is a plugin-owned credential design that uses existing SecretRef/redaction patterns, scoped clients, docs, and fallback semantics rather than a narrow runtime patch.

## Label Justifications

- `P2`: This is a concrete Google Chat capability gap with user-visible delivery/auth impact, but text messaging still works and it is not an emergency core-runtime failure.
- `impact:security`: The requested solution introduces OAuth client secrets, refresh tokens, scopes, redaction, and storage decisions.

- `impact:auth-provider`: The issue is primarily about adding a second Google Chat authentication mode and routing operations to the correct credential type.

## Summary

Keep open. Current main and the latest release still use service-account Google Chat auth with the `chat.bot` scope only, while the requested user OAuth credential model for reactions, media upload, and user-scoped DM lookup is not implemented; related media-fallback PRs cover only one symptom.

## What This Changes

Issue requests optional user OAuth support for the bundled Google Chat plugin so reactions, attachment uploads, and proactive direct messages can use user-level scopes while service-account auth remains for app/webhook behavior.

## Best Possible Solution

Keep this issue open for a maintainer-approved Google Chat plugin design that adds secret-aware user OAuth credentials, scoped user-auth clients for user-only operations, service-account retention for webhook/app flows, explicit fallback behavior, docs, and live Workspace proof.

## Reproduction Assessment

Yes from source inspection: the current config schema and Google Chat auth helper still expose service-account credentials and the chat.bot scope only, so the requested user OAuth configuration cannot be accepted or used.

## Solution Assessment

Unclear: adding user OAuth in the Google Chat plugin is the right owner boundary, but the exact credential model, SecretRef handling, fallback behavior, and doctor/docs migration plan need maintainer security and product direction.

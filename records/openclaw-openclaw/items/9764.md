## Summary

Keep open. Current main and v2026.6.11 remain service-account-only for Google Chat, and no related pull request implements the requested user-auth credential model or operation routing.

## What This Changes

Add optional Google Chat user authentication for reactions, attachment uploads, reaction-based typing indicators, and proactive direct-message lookup by email alias.

## Best Possible Solution

Add one explicit plugin-owned user-auth mode with SecretRefs, minimum required scopes, operation-specific client routing, unchanged service-account webhook and bot behavior, graceful fallback when absent, setup documentation, and redacted live Google Workspace proof.

Rationale: The capability gap is established, but the two viable user-auth models have materially different administrator, consent, impersonation, secret-storage, revocation, and blast-radius implications that require maintainer intent.

Likely owner: steipete

Owner confidence: high

Options:

- **Domain-wide delegation (recommended):** Use the existing service-account credential with a required impersonated user subject and narrowly configured Google Chat scopes as an explicit administrator-controlled mode.
- **Refresh-token OAuth:** Add OAuth client and refresh-token SecretRefs with a documented authorization, refresh, rotation, and revocation workflow.
- **Keep app authentication only:** Decline user credentials and instead improve unsupported-operation warnings and app-auth media fallbacks.

## Reproduction Assessment

Yes at source level. Current configuration, the fixed `chat.bot` scope, proactive-DM client routing, public documentation, and the latest release all establish that the requested user-auth capability is absent.

## Solution Assessment

No, not exactly as sketched. The Google Chat plugin is the correct owner, but maintainers should first choose the permanent secure Workspace authentication model rather than committing directly to raw client-secret and refresh-token fields.

## Summary

Keep this PR open; it is a useful direction but not merge-ready because the latest head still buffers unknown-length Playwright responses, silently loses the truncation signal for known-large responses, has stale real-behavior proof, and currently fails lint.

## What This Changes

The branch changes browser `responseBodyViaPlaywright` to prefer `body()+subarray()` with a `content-length` pre-check and adds response-body regression tests.

## Best Possible Solution

Use a response-body strategy that either proves a truly bounded read for all relevant response shapes or explicitly narrows the behavior to a content-length-only guard while preserving API signals for capped bodies.

## Reproduction Assessment

Yes. Source and dependency inspection show current main reads the full Playwright response before trimming, and the PR still does that for chunked or missing-content-length responses.

## Solution Assessment

No. The content-length pre-check is a useful partial mitigation, but it is not the best complete fix for the stated OOM issue because unknown-length responses still buffer fully and known-large responses lose the truncation signal.

Full review comments:

- **[P1] Avoid buffering unknown-length Playwright responses:** `extensions/browser/src/browser/pw-tools-core.responses.ts:115-116`
  - body: For responses without a usable oversized `content-length`, this still awaits `resp.body()` before slicing. In Playwright 1.60.0, `Response.body()` returns the full Buffer and `text()` is built on top of it, so a large chunked or omitted-length response can still allocate the full body and the stated OOM fix remains incomplete.
  - confidence: 0.93
- **[P1] Preserve the capped-body signal:** `extensions/browser/src/browser/pw-tools-core.responses.ts:111`
  - body: When `oversized` is true, the function skips reading the body but then falls through with `bodyText === ""`, so the returned object has an empty body and no `truncated` flag. That silently changes existing callers from a truncated prefix with an explicit signal to a real-looking empty response; return `truncated: true`, an explicit capped result, or a clear error for this path.
  - confidence: 0.91
- **[P3] Use Number.NaN for the fallback value:** `extensions/browser/src/browser/pw-tools-core.responses.ts:110`
  - body: The latest CI lint log fails on this line with `unicorn(prefer-number-properties)`: use `Number.NaN` instead of the global `NaN` so the PR can pass the repo lint gate.

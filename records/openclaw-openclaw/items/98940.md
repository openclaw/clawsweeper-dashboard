## Summary

Keep open: the PR addresses a real source-visible browser response-capture OOM path, but the latest head still awaits Playwright's full `Response.body()` before applying the byte slice, so it is only a decode-memory mitigation and not the claimed bounded body read. It also still needs contributor real behavior proof beyond mocked/unit validation.

## What This Changes

The PR changes browser Playwright response capture to prefer `Response.body()`, decode only a capped byte prefix, and add regression tests for small and oversized responses.

## Best Possible Solution

Use a response capture path that limits bytes before Playwright materializes the body, or explicitly narrow this branch to a partial decode-memory mitigation with maintainer-accepted semantics, focused coverage, and real proof.

## Reproduction Assessment

Yes by source and dependency inspection: current main reads the full Playwright response text before final truncation, and Playwright 1.60 `Response.body()` returns the full binary body. I did not run a live large-response browser repro in this read-only review.

## Solution Assessment

No. The latest patch reduces full-string decoding but is not the best OOM fix because it still waits for Playwright to buffer the whole response before slicing.

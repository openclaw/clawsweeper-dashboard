## Label Justifications

- `P1`: The PR targets an OOM-prone browser responsebody path that can affect active browser-agent workflows, and the current head still leaves the known-large response path unbounded.

## Summary

Keep open: this is a useful decode-only mitigation, but the current head still fully reads known oversized Playwright response bodies before truncating, so the prior P1 blocker remains.

## What This Changes

The PR replaces Playwright response text decoding with `body()+subarray()` prefix decoding and adds a unit test for large response prefix preservation.

## Best Possible Solution

Restore a current-head content-length pre-reject before `resp.body()`, keep the passive `body()+subarray()` decode path for unknown lengths, align the CLI/proof claims with the actual diff, and add a regression proving `body()` is not called for known oversized responses.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, source-reproducible: current main uses full `resp.text()`/`resp.body()` before truncation, and the PR head still calls `resp.body()` before any size guard. A Playwright response with `content-length` above `maxBytes` follows that path and can fully buffer before truncation.

## Solution Assessment

No; the current patch is only a partial decode-allocation mitigation. The better fix is the narrower pre-read content-length rejection for known oversized responses plus bounded decode for unknown-length responses.

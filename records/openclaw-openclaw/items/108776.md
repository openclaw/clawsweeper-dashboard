## Summary

The current head still contains the previously reported authorization defect: `approval.history` reads terminal approvals allowed by the coarse `operator.approvals` scope without applying the per-record reviewer-device checks used by lookup and resolution. This PR should remain open for that security-boundary repair and direct after-fix Control UI proof.

## What This Changes

Adds a pending-approval sidebar chip and paginated Control UI approval-history page through a new gateway RPC over the durable operator approval ledger, with additive attribution fields and generated clients and translations.

## Best Possible Solution

Keep the history feature, but make pagination access-aware by applying the same client/device record policy as `approval.get` and `approval.resolve`, add cross-device and device-less regression coverage, then provide redacted real-browser proof of the chip-to-overlay and history-page flows.

No, not at the current head. Reusing the durable ledger and an additive RPC is maintainable, but the read path must preserve the canonical per-record approval authorization invariant and its pagination semantics.

## Summary

Keep open: current main already forwards non-consult realtime tool calls to the owning Gateway Talk client and accepts submitted results, but it does not establish the requested client-scoped declaration contract. This is a new config/protocol capability whose trust model and permanent API shape need maintainer direction before implementation.

## What This Changes

Add an optional `talk.realtime.clientTools` declaration so Gateway-relay Talk clients can expose client-executed realtime tools to the selected provider.

## Best Possible Solution

Define a session- or owner-scoped client-tool declaration contract at the Gateway protocol boundary, preserve the existing owner-only dispatch/result path, and add schema validation, collision handling, docs, and focused relay round-trip coverage after maintainers choose the trust model.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Gateway-relay Talk expose client-executed realtime tools through a globally configured `talk.realtime.clientTools` list, or should declarations be supplied and scoped by the owning client/session during session creation?

Rationale: Both shapes can reuse the existing relay result path, but they have materially different multi-client, reconnect, capability-discovery, and compatibility semantics; source evidence does not establish an approved permanent contract.

Likely owner: Jackten

Owner reason: The author has supplied the clearest concrete protocol proposal, while current-main history ownership could not be verified in the available read-only environment.

Owner confidence: low

Options:

- **Use client/session declarations (recommended):** Add a typed owner-scoped declaration at session creation so provider-visible tools exactly match the client that can execute them.
- **Use global configuration:** Add `talk.realtime.clientTools` only if maintainers intend one operator-defined capability set shared by all eligible relay clients.
- **Defer the surface:** Keep the current built-in tool set until an explicit generic client-capability protocol is designed.

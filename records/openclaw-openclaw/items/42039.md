## Summary

Keep open: current main and the latest release still keep the restart catch-up limit and stagger as internal CronService dependencies only, while public cron config, strict validation, docs, and Gateway construction do not expose or wire the requested settings. This issue remains the canonical product/config decision for public cron missed-run controls.

## What This Changes

Expose cron restart catch-up limit and stagger controls through public cron configuration so users can reduce or disable startup missed-job replay.

## Best Possible Solution

Maintainers should choose one supported missed-run policy, then wire it through config types, strict schema, config help, docs, Gateway CronService construction, and restart-catch-up tests while preserving the current default unless an explicit migration is approved.

- **Keep Controls Internal:** Decline new public config and document the current restart catch-up behavior plus safer cron authoring patterns.

Yes. Source inspection shows the internal deps exist and startup catch-up consumes them, while CronConfig, the strict schema, docs, and Gateway construction do not expose them; I did not run the reporter's live 13-job restart scenario.

## Solution Assessment

Unclear until maintainers choose the public policy. The existing internal max/stagger path is the narrowest implementation base, but exposing it as config is compatibility-sensitive and a skip/freshness policy may be the better product API.

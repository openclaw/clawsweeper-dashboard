Options:

- **Design Explicit Missed-Run Policy (recommended):** Add a named global and/or per-job skip/freshness policy and only expose max/stagger as advanced tuning if maintainers want those raw knobs too.
- **Expose Existing Internal Knobs:** Make `maxMissedJobsPerRestart` and `missedJobStaggerMs` public with schema, docs, tests, and a documented `0` behavior for disabling immediate catch-up.
- **Keep Policy Internal:** Leave restart catch-up semantics as product-owned defaults and close or retitle this request to track only narrower duplicate-message bugs.

Yes, at source level: the internal cron service deps contain the requested controls, while current public `CronConfig`, strict zod schema, docs, and latest release do not expose or accept them.

## Solution Assessment

No, not as a purely mechanical field exposure. The best fix needs a maintainer-chosen public missed-run policy so operators get clear skip/freshness behavior instead of only raw internal throttle knobs.

## Summary

Keep open: current main and v2026.6.11 still keep the requested cron restart catch-up controls internal. The source gap is clear, but raw exposure needs maintainer direction because `maxMissedJobsPerRestart: 0` would currently defer missed jobs rather than skip catch-up, and new cron config is compatibility-sensitive.

## What This Changes

The issue asks to expose cron restart catch-up limit and stagger controls in `openclaw.json` so overdue jobs can be skipped or slowed after gateway restarts.

## Best Possible Solution

Approve an explicit restart catch-up policy with current defaults preserved, then wire it through `CronConfig`, the strict schema, config help/docs, Gateway construction, and focused tests for skip/disable, stagger, default, and upgrade behavior.

Rationale: The code gap is clear, but this adds public config and changes scheduler restart semantics; the existing internal knobs do not directly implement the reporter's zero-means-skip expectation.

Owner confidence: medium

Options:

- **Define explicit catch-up policy (recommended):** Add a documented global policy, and possibly a later per-job override, where current catch-up remains the default and skip/disable/stagger semantics are explicit and tested.
- **Expose raw internal knobs:** Expose `maxMissedJobsPerRestart` and `missedJobStaggerMs` directly, but document that zero defers all missed jobs or intentionally special-case zero to skip with tests.
- **Keep controls internal:** Keep the fixed internal restart catch-up defaults and document the current behavior/workarounds instead of expanding public cron config.

## Reproduction Assessment

Yes, source-level: current main keeps the max/stagger controls as internal `CronServiceDeps` and consumes them in startup catch-up, while `CronConfig`, the strict schema, docs, and Gateway config mapping do not expose them. I did not run the reporter's live 13-job restart scenario.

## Solution Assessment

No, not as proposed without a policy decision: raw exposure alone is not the best fix because `maxMissedJobsPerRestart: 0` currently means defer every missed job, not skip catch-up. Maintainers should choose explicit restart catch-up semantics before implementation.

## What This Changes

Expose restart missed-job catch-up limit and stagger controls through public cron configuration, with optional skip-style policy for jobs where replay is harmful.

## Best Possible Solution

Maintainers should choose one supported restart missed-run policy, preserve current defaults for upgrade safety, and then wire it through CronConfig, schema/help/docs, Gateway CronService construction, and focused restart-catch-up tests.

- **Expose narrow global controls (recommended):** Approve documented global cron keys based on the existing internal max/stagger behavior, including explicit default-preserving and zero-limit semantics.
- **Design skip policy first:** Prefer a global or per-job skip/freshness policy before implementation so user-facing announcement jobs can opt out without changing catch-up defaults globally.
- **Keep controls internal:** Decline new public config for now and document current restart catch-up behavior plus operational workarounds.

## Reproduction Assessment

Yes, at source level: the internal deps exist and startup catch-up consumes them, while CronConfig, the strict schema, Gateway construction, and latest release do not expose them. I did not rerun the reporter's live 13-job restart scenario.

## Solution Assessment

Unclear until maintainers choose the public policy. The existing internal max/stagger path is the narrowest implementation base, but exposing it as config is compatibility-sensitive and a skip/freshness policy may better fit user-facing announcements.

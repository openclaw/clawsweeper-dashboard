## Summary

Keep this issue open: current main and v2026.6.11 still use growing full-content Feishu CardKit updates, the open linked PR is not merged, and the latest live comment says the PR's coalescing approach did not materially fix the long-reply tail latency.

## What This Changes

The issue requests a fix for Feishu streaming-card long-reply latency after the plugin switched from append/suffix CardKit updates to full accumulated text updates.

## Best Possible Solution

Resolve the Feishu streaming-card latency in the plugin by preserving the default full-content CardKit contract while adding only a maintainer-approved, live-proven opt-in fallback or alternative transport for tenants where full-content updates are too slow.

## Maintainer Decision

Rationale: The current default was added to prevent truncation and matches the prior CardKit full-content contract, but the latest live repro says cadence coalescing is insufficient for some deployments, so automation cannot choose the permanent compatibility policy.

Options:

- **Proofed opt-in append mode (recommended):** Keep full-content updates as the default, but accept a narrowly documented append/delta mode only with live Feishu proof that it fixes latency without truncation in the affected setup.
- **Full-content only:** Reject append mode as an unsupported CardKit contract split and document streaming:false or renderMode:raw as the supported workaround for slow tenants.
- **Cadence-only PR:** Continue with the linked coalescing PR despite the latest report, accepting that it may reduce calls without solving the core long-reply tail latency.

## Reproduction Assessment

Yes for a source-backed and live-reported path: Feishu DM with renderMode:card, streaming:true, and a long reply still sends repeated full accumulated CardKit payloads. I did not independently run a credentialed Feishu tenant reproduction in this read-only review.

## Solution Assessment

Unclear as currently proposed: coalescing full-content updates is narrower than adding a config mode, but the latest live repro says that approach did not noticeably fix the latency. The best path needs a maintainer choice between a proven opt-in append mode and keeping full-content-only behavior with documented fallback.

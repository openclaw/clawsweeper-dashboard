## Label Justifications

- `P2`: This is a normal-priority session persistence improvement with meaningful but bounded impact and partial workarounds.
- `impact:data-loss`: Automatic rollover can discard conversation context that was never persisted by session-memory or another memory path.
- `impact:session-state`: The missing lifecycle notification breaks transcript and memory continuity across daily and idle session boundaries.

## Summary

Keep open. Current main still archives prior daily/idle session state without invoking the reset persistence surfaces used by bundled session-memory; the secondary config-schema mismatch is fixed, while the active implementation and durable hook contract still need maintainer review.

## What This Changes

Requests an automatic daily/idle session reset hook that lets session-memory persist the previous session before rollover, plus hook-specific config schema support.

## Best Possible Solution

Use one canonical rollover helper that preserves the archived prior transcript, exposes explicit daily/idle reasons through an owner-approved typed lifecycle contract, adapts bundled session-memory without synthetic command ambiguity, and tests daily, idle, and manual no-double-fire behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which lifecycle contract should automatic daily and idle rollover expose to persistence consumers?

Rationale: Current main separates internal command hooks from typed plugin lifecycle hooks, so selecting whether to extend before_reset, add a reset event, or synthesize command events is a compatibility-sensitive API decision.

Likely owner: vincentkoc

Owner reason: The active hooks/plugins candidate and issue history most directly route this contract decision to vincentkoc.

Owner confidence: medium

Options:

- **Extend typed reset lifecycle (recommended):** Route every rollover reason through a canonical typed reset helper and adapt bundled session-memory at its owning boundary without presenting automatic rollover as a user command.
- **Reuse command reset events:** Emit synthetic command events with daily or idle metadata, reducing implementation work but conflating command and lifecycle semantics.
- **Add a session reset event:** Create a distinct internal session reset event while retaining separate typed plugin behavior, accepting another public hook surface.

## Reproduction Assessment

Yes at source level: configure daily or idle reset, let a session become stale, then send the next message; current main archives the old session and emits typed lifecycle hooks but not the reset surfaces consumed by session-memory. This read-only review did not run a live Gateway reproduction.

## Solution Assessment

No, the exact new session:reset event proposed is not yet proven to be the best contract; a canonical typed reset lifecycle helper with an owner-boundary adapter for bundled session-memory is narrower and avoids synthetic command semantics.

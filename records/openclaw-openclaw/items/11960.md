## Summary

Keep open. Current main still captures and archives daily/idle rollover state but does not expose that rollover to the internal `session-memory` hook surface; the secondary per-hook `messages` configuration problem is already resolved. The overlapping open implementation at https://github.com/openclaw/openclaw/pull/61675 makes this a maintainer lifecycle-contract decision rather than a candidate for another competing fix PR.

## What This Changes

Add a reset-time hook/persistence surface so automatic daily and idle session rollovers can preserve session memory, while allowing per-hook configuration such as `session-memory.messages`.

## Best Possible Solution

Define one typed reset lifecycle contract for manual, daily, and idle rollovers; make `session-memory` consume that contract with prior-session context, preserve current archive semantics, and add daily/idle plus no-double-dispatch regression coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should automatic daily and idle rollovers extend the existing reset contract through a dedicated typed session-reset event, or should they reuse command-style reset events for internal hooks?

Rationale: The primary behavior requires a stable shared lifecycle API affecting bundled and custom hooks; current code provides only command events for session-memory while the open implementation uses a different event shape.

Likely owner: vincentkoc

Owner reason: The relevant code and the overlapping proposal both converge on the hooks/plugins boundary.

Owner confidence: medium

Options:

- **Add a typed reset lifecycle event (recommended):** Expose a reasoned reset event with prior-session context for automatic and manual resets, then migrate bundled session-memory to it while preserving existing command compatibility.
- **Reuse command-style reset events:** Dispatch the existing internal command surface for automatic daily and idle rollover, minimizing new event types but coupling lifecycle transitions to command semantics.
- **Limit the change to plugin hooks:** Extend `before_reset` for automatic rollovers but leave managed and workspace internal hooks unchanged, which does not fully meet the bundled session-memory use case.

## Reproduction Assessment

Yes, source-reproducible: current main creates a `previousSessionEntry` for stale daily/idle rollover while the documented `session-memory` internal hook listens only to `command:new` and `command:reset`. A live configured daily/idle session would be the final runtime confirmation.

## Solution Assessment

No, a one-off session-memory special case is not the best long-term fix; the maintainable solution is a maintainer-approved, typed reset lifecycle contract shared by bundled and custom hooks.

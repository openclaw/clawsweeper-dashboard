## Summary

Keep open. Current main still has the central daily/idle reset persistence gap: stale rollovers capture and lifecycle-notify the prior session, but bundled session-memory remains command-only and the remaining fix needs a maintainer choice on the durable reset hook contract.

## What This Changes

The issue requests a reset hook surface so automatic daily and idle session rollovers can persist memory before old session context is cleared.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/61675 or a maintainer-approved replacement that persists session-memory on daily/idle rollover, keeps manual resets single-fired, documents the chosen hook contract, and covers daily plus idle regressions.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which automatic reset hook contract should OpenClaw support for daily and idle rollover memory persistence?

Rationale: The source-level gap is clear, but the permanent API shape affects internal hooks, typed plugin hooks, session lifecycle ordering, and transcript-bearing privacy expectations, so automation should not pick the contract alone.

Likely owner: steipete

Owner reason: steipete authored the prior detailed review and has the strongest current history across internal hooks, daily reset policy, and this issue's contract question.

Owner confidence: high

Options:

- **Refine the active reset PR (recommended):** Accept command-style daily/idle reset events plus lazy before_reset dispatch as the narrow fix path, then require rollover proof and docs alignment before merge.
- **Define a typed session reset event:** Pause the active implementation and design a new session:reset or session:before-reset surface before wiring bundled session-memory to it.
- **Use lifecycle hooks only:** Keep automatic rollover on existing session_end/before_reset-style lifecycle hooks and adapt memory persistence around that surface instead of adding command-style actions.

## Reproduction Assessment

Yes. Source-level reproduction is high confidence: daily/idle stale rollover can create a new session while bundled session-memory only handles command:new and command:reset; I did not run a live filesystem rollover in this read-only review.

## Solution Assessment

Unclear as a final design. Persisting before automatic reset is the right end state, but maintainers still need to choose the stable hook/API contract before a fix should land.

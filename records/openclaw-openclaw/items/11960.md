## Label Justifications

- `P2`: Automatic reset persistence is a normal-priority core improvement with meaningful but bounded impact and an available transcript archive fallback.
- `impact:data-loss`: Unsaved conversational context can be silently omitted from durable memory when daily or idle rollover replaces the active session.
- `impact:session-state`: The missing lifecycle signal occurs specifically while replacing session identity and preserving prior-session context.

## Summary

Current main still rolls daily and idle-stale sessions without exposing that boundary to the bundled session-memory internal hook; the secondary hook-config schema mismatch is resolved, but the primary persistence gap remains and the existing implementation needs lifecycle-contract selection plus real behavior proof.

## What This Changes

Add a reset lifecycle hook so automatic daily and idle session rollovers can preserve prior-session memory, and permit hook-specific configuration fields such as session-memory message count.

## Best Possible Solution

Route every session replacement through one canonical lifecycle coordinator that emits a typed reset reason and previous-session context before archival, adapts that fact to a documented session:reset internal event and the existing plugin before_reset hook, and regression-tests daily, idle, and explicit reset ordering without duplicate persistence.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should automatic daily and idle rollover establish a new documented session:reset internal-hook contract while also invoking the existing typed before_reset plugin hook, or should one existing surface exclusively own reset persistence?

Rationale: Both hook systems intentionally serve different users, and selecting the permanent event name, context, ordering, and ownership is a compatibility-sensitive API decision that should not be inferred from an unmerged contributor implementation.

Likely owner: vincentkoc

Owner reason: The related PR identifies vincentkoc as the hooks/plugins CODEOWNER, making this the strongest available owner signal for the lifecycle API choice.

Owner confidence: high

Options:

- **Canonical reset lifecycle event (recommended):** Create one internal reset lifecycle fact and adapt it to session:reset plus the existing typed before_reset hook before transcript archival.
- **Typed plugin hook only:** Make before_reset the sole runtime contract and move bundled persistence behind a plugin-owned path rather than adding another internal event.
- **Reuse command events:** Emit synthetic command events for daily and idle rollover, minimizing new API surface but permanently mixing command and lifecycle semantics.

## Reproduction Assessment

Yes at source level: configure a daily or idle reset, create prior conversation history, then send the first message after the stale boundary; current code rotates the session while the documented session-memory hook still accepts only manual command events. A live current-main run was not performed in this read-only review.

## Solution Assessment

Unclear until maintainers select the permanent lifecycle contract; adding reset visibility is appropriate, but synthetic command events are less maintainable than a canonical reset event shared by the internal and typed-plugin adapters.

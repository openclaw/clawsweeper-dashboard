## Label Justifications

- `impact:ux-friction`: The floating indicator can obstruct long responses and distract users, but they can continue using WebChat and scroll manually.

## Summary

Current main preserves backscroll and provides persisted auto-scroll modes, but the New messages recovery action is still driven directly by scroll state without a visibility or presentation preference. This issue remains the canonical request for that distinct WebChat ergonomics choice, and prior maintainer discussion explicitly kept it open after the related auto-scroll work landed.

## What This Changes

Add a user preference to hide, dismiss, or otherwise reduce the WebChat New messages indicator.

## Best Possible Solution

Add a browser-local persisted indicator presentation setting through the existing Control UI settings path, preserve the current button by default, and ensure every mode retains an obvious manual way to reach unread content.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should WebChat support hiding the New messages recovery action, and if so what manual catch-up affordance must remain available when automatic scrolling is disabled?

Rationale: The indicator is both notification UI and the recovery control for persisted auto-scroll Off mode, so implementation cannot safely choose hide, dismiss, or redesign semantics without product intent.

Likely owner: steipete

Owner reason: He is the clearest product decision owner and has prior review and current-history involvement in this WebChat surface.

Owner confidence: high

Options:

- **Add Local Visibility Setting (recommended):** Add a browser-local persisted visible/hidden preference while retaining a compact manual scroll-to-latest control whenever auto-scroll is Off.
- **Redesign Without A Toggle:** Keep the recovery action universally available but make it smaller, dismissible, or less obstructive instead of allowing full removal.
- **Keep Current Behavior:** Retain the current indicator as the required manual catch-up affordance and close the feature request as not planned.

## Reproduction Assessment

Yes from source inspection: new content received while the user is away from the bottom sets chatNewMessagesBelow, and the render path displays the New messages action without a visibility preference. A fresh live browser reproduction was not performed.

## Solution Assessment

No, a new gateway-level openclaw.json option is not the best first solution because this is browser presentation state. The narrowest maintainable direction is a persisted local UI setting integrated with the existing auto-scroll controls while preserving a manual catch-up path.

## Summary

Keep this open: current main and the latest release still omit the `file` alias from the central Read/Write/Edit display path resolver and read-start diagnostics, and the same-repository PR that uses closing syntax remains open but unmerged and dirty.

## What This Changes

The issue requests that Read/Write/Edit tool summaries show the file path when tool args use the `file` alias instead of canonical `path` or other historical path aliases.

## Best Possible Solution

Settle the alias contract, then either land a refreshed https://github.com/openclaw/openclaw/pull/77312 or a replacement that aligns display, diagnostics, validation, metadata, and tests, or deliberately document/enforce canonical `path` everywhere.

## Reproduction Assessment

Yes, source-level. Current main still omits `record.file` from `resolvePathArg()` and from the read-start guard, so a display call with `{ file: ... }` cannot resolve the path through the central display path.

## Solution Assessment

Unclear as a display-only change. The narrow alias addition is plausible, but the best fix needs a maintainer decision on whether legacy aliases remain supported despite current canonical `path` validation.

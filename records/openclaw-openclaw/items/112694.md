## Summary

Keep this PR open for repair and owner review. It addresses a credible memory-dreaming gap, but the new `memory_get` tracker uses the top-level workspace instead of the resolved agent workspace and records inaccurate source ranges; lowering two promotion defaults also changes what existing opted-in deployments persist into `MEMORY.md` without an established upgrade policy. The PR body reports compilation only, not after-fix behavior in a real workspace.

## What This Changes

The PR lowers default dreaming promotion scores and adds best-effort recall tracking after successful `memory_get` reads so daily-memory reads can contribute to long-term promotion.

## System Context

The bundled memory-core plugin reads daily memory files through `memory_get` and records recall evidence for its dreaming pipeline. That pipeline ranks recalled daily-note snippets and, when configured gates pass, promotes durable material into the agent workspace’s `MEMORY.md`.

## Best Possible Solution

Full review comments:

- **[P1] Use the resolved agent workspace for recall tracking:** `extensions/memory-core/src/tools.ts:921`
  - body: `memory_get` has already resolved its backend for `agentId`, but this new path uses the top-level `cfg.workspace`.   - confidence: 0.94
- **[P2] Record the actual read range before queuing promotion evidence:** `extensions/memory-core/src/tools.ts:434-447`
  - body: The tracker invents an end line as `from + lines`, which includes one extra line, and writes `0` for an unbounded read. It also does not carry the returned slice into the recall result. Dreaming later relies on accurate source identity to rehydrate a live snippet, so this can produce invalid candidates or fail to promote the content that was actually read. Build tracking data from the successful read result and use an inclusive `from + lines - 1` range when a bounded slice is returned.
  - confidence: 0.88

## Summary

Keep open. Current main fixes the gateway reset lifecycle, but source still shows a direct-chat `/new`/`/reset` initialization path can publish a new session id and family lineage without creating a transcript header, and there is no live current-main Feishu proof that the reported generic failure loop is gone.

## What This Changes

Feishu direct `/reset` or `/new` should recover to a durable transcript instead of leaving family ids without transcript artifacts and falling into the generic external-run fallback.

## Best Possible Solution

Make every direct-chat reset/new rotation transactional across the store entry, family lineage, and transcript header, with doctor or repair fallback only for already-broken state.

Options:

- **Require transactional rotation (recommended):** Every reset/new path creates or verifies the target transcript header before committing the new id and lineage, and failures keep or remap to the prior valid transcript.
- **Add repair-only recovery:** Leave runtime rotation mostly as-is but add doctor or startup repair that detects missing transcript family members and remaps them to the newest valid transcript.
- **Fold into broader Feishu UX work:** Defer the durability fix until the broader Feishu failure-translation issue owns reset recovery and user-facing fallback copy together.

Closing is not the best solution yet; the remaining work is to unify reset/new lifecycle ownership so all paths publish a new session id only with a durable transcript or explicit remap failure.

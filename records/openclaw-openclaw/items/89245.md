## Summary

Keep open. Current main has partial session-lifecycle hardening and Feishu doctor repair, but I did not find proof that the Feishu direct text-command /reset and /new path now publishes a rotated session id only after the transcript is durable or repairs orphaned usage-family ids; the adjacent compaction issue was closed while explicitly leaving this reset/new case here.

## What This Changes

The issue requests a fix for Feishu direct sessions that can remain stuck after user /reset or /new when session-family metadata references transcript ids that do not exist on disk.

## Best Possible Solution

Define one durable reset/new contract for direct chat sessions, then make the Feishu text-command path either prewarm the new transcript before publishing the family id or keep the prior valid entry authoritative and expose a specific recovery message.

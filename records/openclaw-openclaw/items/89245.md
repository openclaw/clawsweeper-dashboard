## Summary

Keep open. Current main has newer session-lifecycle guards and cleanup repair code, but I did not find source or test proof that the Feishu/direct `/reset` and `/new` reply path publishes a newly rotated session id only after its transcript is durable; the closed related compaction issue covers an adjacent path and leaves this reset/new durability case here.

## What This Changes

The issue requests transactional `/reset` and `/new` session recovery so Feishu direct sessions cannot advance lineage to missing transcripts and then fall into generic failure loops.

## Best Possible Solution

Make reply-session reset/new rotation transactional: publish the new session id only after a durable transcript exists, otherwise keep the previous valid transcript active and surface a session-repair recovery path instead of the generic fallback.

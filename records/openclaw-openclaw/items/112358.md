## Summary

The central bug remains on current `main`: `test-speech` does not forward or apply the already-modeled per-request timeout, while the sibling listen probe does. The proposed wiring is a bounded, consistent fix with focused coverage, but it still needs real after-fix behavior proof on an audio-capable Google Meet setup before merge.

## What This Changes

This PR adds an optional per-request timeout to the Google Meet `test-speech` probe, passes it through CLI, Gateway, and tool paths, and reports manual browser blockers without also calling them speech timeouts.

## System Context

The Google Meet plugin exposes CLI commands and an agent tool that call Gateway handlers, which create or inspect a Meet session and poll Chrome audio-bridge health. The speech probe turns those health observations into a verification or blocker result for the operator.

## Best Possible Solution

Keep the existing default fast probe window, land the bounded explicit-timeout wiring only after a redacted real Meet run shows a valid request crossing the Gateway and producing the longer-wait or manual-blocker result on a supported audio-capable host.

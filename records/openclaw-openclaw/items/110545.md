## Label Justifications

- `P0`: A first-run Windows Companion setup path deterministically loses its hosting Gateway before onboarding can complete.
- `impact:crash-loop`: The embedded wizard can invoke the normal runtime exit path and terminate the shared Gateway process.
- `impact:ux-release-blocker`: Affected companion users cannot complete fresh setup or recovery through the client’s expected wizard flow.

## Summary

Keep this issue open as the canonical report: current `main` still passes the process-exiting CLI runtime into both Gateway wizard flows, and the two linked open pull requests are complementary candidate fixes rather than merged resolution.

## What This Changes

Fix Gateway-hosted setup and channel wizard sessions so they cannot exit their shared Gateway process, while allowing RPC callers to pass the existing onboarding `installDaemon` option.

## Best Possible Solution

Consolidate the two complementary fixes into one bounded Gateway change: run both RPC wizard flows with a non-exiting runtime, translate only `ExitError(0)` to normal completion, surface nonzero exits as session errors, and forward optional `installDaemon` unchanged.

## Reproduction Assessment

Yes in source: `wizard.start` supplies `defaultRuntime` to runners whose setup path calls `runtime.exit()`, which reaches `process.exit`; a focused live Gateway RPC run is still needed as regression proof after the fix.

## Solution Assessment

Yes, if handled as one Gateway owner-boundary repair: reuse the existing non-exiting runtime and forward the already-defined onboarding option rather than adding Companion-specific behavior or changing CLI lifecycle semantics.

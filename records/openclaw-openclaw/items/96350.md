## Summary

Keep open: current main and the latest release still build Android `system.notify` notifications without a deeplink/contentIntent path, and the safe implementation requires a maintainer security/product decision rather than a cleanup close.

## What This Changes

The issue requests Android `system.notify` notification taps to carry a deeplink/contentIntent instead of doing nothing when tapped.

## Best Possible Solution

Define one narrow Android notification-tap contract, either sharing the allowlisted deeplink policy from https://github.com/openclaw/openclaw/issues/88293 or limiting taps to OpenClaw-owned deep links, then implement it across Android parser/poster, command policy, tests, and docs.

Question: Should Android `system.notify` support notification-tap deeplinks, and if so should the targets use the broader allowlisted Android URL-launch policy or only OpenClaw-owned app routes?

Rationale: The current source proves the feature is missing, but wiring a caller-supplied deeplink directly into a `PendingIntent` would cross a native Android app-launch security boundary and likely add a new settings/policy surface.

Likely owner: steipete

Owner reason: steipete is the live assignee for this issue and the unresolved choice is product/security policy rather than a narrow code repair.

Owner confidence: medium

Options:

- **Share an allowlisted deeplink policy (recommended):** Use the same explicit allowlist/settings model being discussed for Android URL launch, and let `system.notify` reference that policy for notification taps.
- **Limit taps to OpenClaw-owned routes:** Support notification taps only for internal OpenClaw app routes and leave arbitrary companion-app deeplinks to a separate command.
- **Reject notification deeplinks:** Document that `system.notify` is display-only and keep Android deeplink launching behind a separate command design.

## Reproduction Assessment

Yes. Current source shows Android `system.notify` parses only title/body/sound/priority and posts without `setContentIntent`; I did not run a live Pixel repro in this read-only review.

## Solution Assessment

Unclear as proposed. Directly setting a `PendingIntent` from a raw deeplink parameter is not the safest final shape; a shared allowlist or OpenClaw-only route contract is the more maintainable path.

## Summary

Keep open: current main still posts Android `system.notify` notifications without any deeplink/contentIntent tap target, and the remaining work needs maintainer product/security direction rather than conservative cleanup.

## What This Changes

The issue asks for Android `system.notify` to honor a deeplink/contentIntent parameter so tapping the posted notification can open an intended action surface.

## Best Possible Solution

Settle one Android deeplink policy first, then implement notification taps either through the shared allowlisted URL-launch contract or a narrower OpenClaw-owned deep-link contract with Android tests and docs.

Options:

- **Share Allowlisted URL Policy (recommended):** Implement notification tap targets only after defining the same explicit scheme/host allowlist and rejection semantics used for the broader Android URL-launch capability.
- **Restrict To OpenClaw Deep Links:** Allow notification taps only for OpenClaw-owned app screens or actions, reducing launch risk but not satisfying arbitrary companion-app deeplinks.
- **Defer Tap Targets:** Keep Android `system.notify` notifications non-actionable until maintainers decide the broader native deeplink/app-launch policy.

## Reproduction Assessment

Yes, source-level: current Android parsing carries only title/body/sound/priority and the notification builder has no `setContentIntent` path. I did not run a Pixel live repro in this read-only review.

## Solution Assessment

Unclear: wiring a raw `deeplink` parameter directly into `system.notify` is only a plausible implementation, not the proven best one. The safer end state is a maintainer-approved allowlist or first-party deep-link contract before adding `PendingIntent` support.

## Summary

Keep open: current main and v2026.6.11 still build Android `system.notify` notifications without carrying a deeplink/contentIntent, and the safe implementation shape needs maintainer product/security direction.

## What This Changes

Request Android `system.notify` to accept a deeplink/contentIntent so tapping a posted notification can open an intended target instead of doing nothing.

## Best Possible Solution

Define a narrow Android notification-tap contract, preferably sharing the allowlisted deeplink policy from the broader Android URL-launch discussion or limiting taps to OpenClaw-owned routes, then implement it with Android unit coverage, gateway policy coverage, and user-facing docs.

Options:

- **Share one allowlisted deeplink policy (recommended):** Define one Android URL/deeplink allowlist and let both a future open-url command and notification contentIntent use that policy.
- **Restrict to OpenClaw routes only:** Allow notification taps only to open OpenClaw-owned app routes or in-app action screens, leaving arbitrary companion-app deeplinks out of `system.notify`.
- **Keep notification taps passive:** Leave `system.notify` without deeplinks and pursue local app launch only through the separate allowlisted command discussion.

Yes, source-reproducible for the missing behavior: current Android source parses only title/body/sound/priority and builds the notification without `setContentIntent`. I did not run a live Pixel tap repro in this read-only review.

## Solution Assessment

Unclear: directly wiring a raw `deeplink` parameter into a `PendingIntent` is plausible but not the safest final shape. The better solution should first settle allowlisted targets or OpenClaw-owned routes and then implement that contract consistently.

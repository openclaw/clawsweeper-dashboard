## Summary

Keep open: current main and the latest release still build Android `system.notify` notifications without a deeplink/contentIntent path, and the safe implementation needs maintainer security/product direction before repair work starts.

## What This Changes

Issue requests Android `system.notify` notifications to attach a deeplink/contentIntent so tapping the notification can open an Android route.

## Best Possible Solution

Define one narrow Android notification-tap contract, preferably sharing any allowlisted deeplink policy chosen for the broader Android URL-launch request or restricting taps to OpenClaw-owned deep links, then implement it with Android and gateway coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Android `system.notify` accept a notification-tap deeplink/contentIntent, and if so must it share an allowlisted URL-launch policy or be limited to OpenClaw-owned destinations?

Rationale: The implementation can be small, but the behavior crosses a native Android app-launch boundary and overlaps the broader deeplink-launch issue, so automation should not choose the security policy.

Likely owner: steipete

Owner reason: He is the current issue assignee for this maintainer decision, while @obviyus is the strongest Android code owner candidate.

Owner confidence: medium

Options:

- **Allowlisted Notification Deeplinks (recommended):** Permit notification taps only through a maintainer-approved scheme/host allowlist shared with the Android URL/deeplink launch policy.
- **OpenClaw-Only Notification Taps:** Support only OpenClaw-owned app routes from notifications and leave arbitrary companion-app deeplinks to a separate command.
- **No Native Tap Launch:** Keep Android `system.notify` display-only until a broader Android deeplink command is designed.

## Reproduction Assessment

Yes. Current Android source parses only title/body/sound/priority and builds the notification without `setContentIntent`; I did not run a live Pixel repro in this read-only review.

## Solution Assessment

Unclear as a final implementation. Directly wiring a raw `deeplink` parameter into `system.notify` would be too broad without maintainer-approved target policy; the safer path is to define this alongside the Android deeplink-launch design.

## Summary

Keep open: current main and the latest release still build Android `system.notify` notifications without a deeplink/contentIntent path, and adding one safely needs maintainer security/product direction rather than automatic cleanup.

## What This Changes

The issue asks for Android `system.notify` notifications to attach a deeplink/contentIntent so tapping the notification can open the intended Android route.

## Best Possible Solution

Define one Android tap-target policy first, preferably by sharing a narrow allowlisted deeplink policy with the broader Android URL-launch work or by limiting `system.notify` taps to OpenClaw-owned app routes, then implement Android handler, gateway policy, tests, and docs together.

Likely owner: steipete

Owner confidence: medium

Options:

- **Share allowlisted deeplink policy (recommended):** Route notification tap targets through the same explicit allowlist/config and structured-error policy as the broader Android URL/deeplink launcher work.
- **Limit to OpenClaw-owned routes:** Add contentIntent support only for OpenClaw app-owned navigation or approval routes and reject arbitrary external app deeplinks.
- **Keep notify passive:** Leave `system.notify` as display-only and put all Android URL launching behind a separate explicit command if maintainers sponsor that capability.

## Reproduction Assessment

Yes. Source inspection on current main shows Android `system.notify` parses only title/body/sound/priority and posts a notification without `setContentIntent`; I did not run a Pixel live repro in this read-only review.

## Solution Assessment

Unclear. Wiring a raw `deeplink` parameter directly into `system.notify` is not the best safe fix until maintainers choose the allowed target model; an allowlisted shared policy or OpenClaw-owned route-only contract is safer.

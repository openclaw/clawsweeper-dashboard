## What This Changes

The PR changes `src/mcp/channel-bridge.ts` so the MCP gateway `onEvent` callback attaches an empty `.catch(() => {})` to `handleGatewayEvent(event)`.

## Best Possible Solution

Catch MCP gateway event handler rejections at the async callback boundary, emit one low-noise diagnostic with verbose detail when useful, and add focused proof that the process no longer leaks an unhandled rejection.

## Reproduction Assessment

Source-reproducible for the async boundary: `GatewayClient` calls `onEvent` synchronously while the bridge starts an async handler. I do not have high-confidence live reproduction of a current MCP event path that forces `handleGatewayEvent` to reject.

## Solution Assessment

No: observing the handler promise is the right boundary, but an empty catch is not the best fix because it turns event-processing failures into silent lost MCP events.

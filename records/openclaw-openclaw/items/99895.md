## What This Changes

The PR changes `src/mcp/channel-bridge.ts` so the async MCP channel bridge gateway event handler has a no-op rejection handler.

## Best Possible Solution

Catch MCP gateway event handler rejections at the async callback boundary, but emit a low-noise diagnostic for handler failure and add focused proof that the process no longer leaks an unhandled rejection.

## Reproduction Assessment

Source-reproducible: current `GatewayClient` calls `onEvent` synchronously, while the bridge starts an async handler without observing its promise on current `main`. I did not run a live MCP bridge scenario that forces a rejected handler promise.

## Solution Assessment

No: observing the handler promise is the right fix boundary, but an empty catch is not the best implementation because it turns event-processing failures into silent lost MCP events.

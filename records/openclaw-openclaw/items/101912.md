## Summary

Keep open. The PR adds a useful Android model-management path, but the proposed UI reads the configured catalog while the new writes mutate only provider model config, so allowlist-backed setups can save or remove models without the screen reflecting the change; the PR also lacks after-fix real behavior proof from Android against a real Gateway.

## What This Changes

Adds Android Providers & Models management UI/state plus `models.configure` and `models.remove` Gateway admin RPCs for provider model config writes, with tests and native i18n updates.

## Best Possible Solution

Make Android model management source-aware before merge: expose provider-authored model rows or row source metadata, hide or scope Remove to rows the RPC can actually remove, and deliberately handle `agents.defaults.models` as a separate allowlist surface if maintainers want Android to edit it.

Rationale: The current PR mixes a visibility API with a provider-config write API; choosing the permanent source-of-truth contract affects Gateway protocol shape, Android UX, and upgrade behavior for existing allowlist users.

Likely owner: Shakker

Owner confidence: high

Options:

- **Provider-model source only (recommended):** Expose provider-authored row source metadata or a provider-config view, and keep `agents.defaults.models` out of this PR except for clear disabled/noop messaging.
- **Manage allowlist too:** Update `agents.defaults.models` intentionally when it controls the visible catalog, with compatibility tests for provider models, exact allowlist entries, and provider wildcards.
- **Pause for a split design:** Land neither write path until model-provider editing and model-allowlist editing are separated into reviewed product surfaces.

## Reproduction Assessment

## Solution Assessment

No; the PR is a plausible feature direction, but the current implementation is not the best fix because the displayed model source and edited config source can diverge. A source-aware provider-model view or an explicit allowlist-management contract is safer.

## Label Justifications

- `P1`: A normal operator-approved plugin update can silently activate an older plugin than the loaded copy and undermine real upgrade verification.
- `impact:ux-friction`: The safe plugin update flow currently requires a manual exact install workaround and clearer duplicate-source diagnostics to avoid testing the wrong plugin version.
- `maturity:stable`: The affected `openclaw plugins update` workflow maps to the `cli-install-update-onboard-doctor` CLI surface scored M4 Stable.

## Summary

Keep open: current main still lets targeted plugin-id updates reuse a stale recorded npm spec and compare against the recorded install path, so it can propose or install an older copy without checking the newer active duplicate plugin.

## What This Changes

The issue asks `openclaw plugins update <id>` to avoid stale tracked-plugin downgrades, resolve the intended latest/default target safely, and print clearer active-source/version diagnostics.

## Best Possible Solution

Add a downgrade-safe targeted update path that compares the proposed target with the active loaded plugin version, recorded install version, and registry default, then refuses implicit downgrades and prints explicit package-spec plus duplicate-source diagnostics.

Question: For targeted plugin id updates with a stale exact npm install record and a newer active plugin copy, should OpenClaw preserve exact-pin semantics with a downgrade guard, or automatically move the plugin to the registry default/latest line?

Rationale: Current docs and recent merged work intentionally keep targeted id updates pinned, while this issue's acceptance criteria ask the id form to resolve latest in at least this stale-record scenario.

Likely owner: steipete

Owner confidence: high

Options:

- **Guard Downgrades, Keep Pins (recommended):** Preserve documented exact-pin behavior, but fail or skip when the recorded target would downgrade the active plugin and show the explicit package-spec command to move to latest.
- **Follow Registry Default:** Change targeted id updates to choose the latest/default registry target when the active plugin is newer than the tracked record, accepting a broader behavior change.
- **Keep Current Behavior:** Leave tracked exact specs fully authoritative even when they reactivate an older copy, relying on manual exact package specs for recovery.

## Reproduction Assessment

Yes at source level. Current main preserves the tracked exact npm spec for targeted id updates, reads the current version from the recorded install path, and does not compare against the active duplicate plugin version before proposing or applying the update.

## Solution Assessment

Unclear until maintainers choose the targeted-update policy. The safest narrow fix is a downgrade guard and duplicate-source diagnostics while keeping explicit npm package specs as the documented way to unpin or follow latest.

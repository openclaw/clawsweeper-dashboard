## Label Justifications

- `P1`: A normal operator-approved plugin update can silently activate an older plugin than the loaded copy and undermine real upgrade verification.
- `impact:ux-friction`: The safe plugin update flow requires a manual exact install workaround and clearer duplicate-source diagnostics to avoid testing the wrong plugin version.
- `maturity:stable`: The affected `openclaw plugins update` workflow maps to `cli-install-update-onboard-doctor`, scored M4 Stable in the maturity shortlist.

## Summary

Keep open: current main still reuses a targeted plugin's tracked npm spec and compares against the recorded install path, so a stale exact install record can be selected without considering a newer active plugin copy or the registry default line.

## What This Changes

The issue asks for `openclaw plugins update <id>` to avoid stale tracked-version downgrades, report active/recorded/latest versions, and warn clearly when duplicate plugin copies affect the active source.

## Best Possible Solution

Add a downgrade-safe plugin update path that compares the proposed target with the active loaded plugin version, recorded install version, and registry default, then refuses implicit downgrades and prints an explicit package-spec command plus duplicate-source diagnostics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For targeted plugin id updates with a stale exact npm install record and a newer active plugin copy, should OpenClaw preserve exact-pin semantics and only block/warn on downgrades, or automatically move the plugin to the registry default/latest line?

Rationale: Current docs and recent merged PRs intentionally preserve exact pins for `plugins update <id>`, while this issue's acceptance criteria ask the id form to resolve latest in at least this stale-record scenario.

Likely owner: steipete

Owner reason: The decision crosses plugin updater semantics, update-channel policy, and current docs that recent history ties to this owner area.

Owner confidence: medium

Options:

- **Guard downgrades, keep pins (recommended):** Preserve the documented exact-pin contract, but make `plugins update <id>` fail or skip when the recorded target would downgrade the active plugin and show the explicit `package@latest` or exact-version command to proceed.
- **Follow registry default:** Change targeted id updates to choose the latest/default registry target when the active plugin is newer than the tracked record, accepting a broader behavior change from current docs.
- **Keep current behavior:** Leave exact pins fully authoritative even when they reactivate an older copy, relying on explicit package specs and manual verification for recovery.

## Reproduction Assessment

Yes at source level. Current main preserves the tracked exact npm spec for targeted id updates, reads the current version from the recorded install path, and does not compare against the active duplicate plugin version before proposing or applying the update.

## Solution Assessment

Unclear until maintainers choose the targeted-update policy. The safest narrow fix is to prevent implicit downgrades and improve diagnostics while keeping explicit npm specs as the way to unpin or follow latest.

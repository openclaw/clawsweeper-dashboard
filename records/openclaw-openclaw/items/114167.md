## Summary

Keep this PR open, but it is not ready to merge. Its new `status_changed` contract claims durable replay while deriving events from a capped recent-event ring and the card’s current run/session metadata; that can lose old transitions and mis-scope retained transitions after a card is relinked. The latest head only adds an unrelated auth-test adjustment after the prior review, so the previously identified Workboard blockers remain.

## What This Changes

This PR adds an opt-in Workboard `status_changed` notification kind, documents it, and projects status transitions from each card’s stored `moved` events when subscribers read notifications.

## System Context

Workboard records card lifecycle activity, then its notification reader filters stored and synthesized events for a subscriber’s board, card, session, run, and event-kind selection. The proposed event would feed downstream consumers that need to react to non-terminal card status changes.

## Architecture Diagram

## Best Possible Solution

Store an immutable, transition-time-scoped status-change record independently of the capped recent-event history, expose the kind consistently through the subscription schema and docs, and add redacted live proof for opt-in delivery and replay across a retained-history boundary.

  - confidence: 0.98
- **[P1] Capture run and session scope at transition time:** `extensions/workboard/src/store-card-helpers.ts:773-774`
  - body: The synthesized event falls back to the card’s current session/run identifiers. When a card is relinked or reused, retained transitions from an earlier run can be delivered to the new run’s subscriber; write scope onto the move/transition record when the status changes.
  - confidence: 0.97
- **[P2] Use an immutable transition identifier:** `extensions/workboard/src/store-card-helpers.ts:776`
  - body: The public revision starts at zero and is recalculated from retained history. Once older events are trimmed, remaining revisions change and new transitions can reuse an earlier consumer key; derive the id from immutable persisted transition data instead.
  - confidence: 0.97

  - body: The new documentation says a subscription without `eventKinds` receives all kinds, but the runtime only adds this event when the filter explicitly includes `status_changed`. Correct the docs or change the runtime semantics so readers get the behavior they were told to expect.

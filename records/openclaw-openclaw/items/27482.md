## Label Justifications

- `P2`: This is a source-proven multimodal feature gap with meaningful user friction, but it is not an urgent regression, outage, data-loss event, or active security incident.
- `impact:security`: Direct video upload would send original user video bytes through managed storage or provider egress, so limits, retention, and policy are security-relevant.
- `impact:auth-provider`: The requested behavior depends on provider/model capability routing and native LLM media payload support.
- `impact:ux-friction`: Users who want direct LLM video analysis must leave the chat flow and use frame extraction, external tools, or separate media-understanding paths.

## Summary

Keep open: current main still blocks WebChat video uploads and lacks a typed native video content/capability path to provider chat models; the direct implementation PRs are closed unmerged and the remaining work needs product, provider, and security direction.

## What This Changes

The issue requests direct video upload from WebChat/message tools to video-capable LLMs, including validation, preview, provider payload routing, and MP4/WebM/MOV-style format support.

## Best Possible Solution

Keep this as the canonical tracker until maintainers approve one coherent video-aware contract across WebChat, Gateway parsing/staging, model catalog metadata, provider delivery, fallback/security policy, docs, and tests.

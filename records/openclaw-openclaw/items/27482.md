## Summary

Keep open: current main and v2026.6.11 still do not provide direct video upload to a video-capable LLM chat/model path; existing video.description media-understanding support is adjacent but not the requested WebChat/message-tool native video input contract.

## What This Changes

Add direct MP4/WebM/MOV-style video upload, preview, validation, and provider-native delivery for LLMs that support video input.

## Best Possible Solution

Keep this as the canonical tracker until maintainers approve and land one coherent video-aware contract across WebChat, Gateway validation/staging, model catalog metadata, provider delivery, fallback/security policy, docs, and tests.

Rationale: The source gap is clear, but the fix crosses product API shape, provider routing, model capability metadata, raw-media egress, retention, and fallback behavior that automation should not choose alone.

Options:

- **Approve first-class video input (recommended):** Define a WebChat/Gateway/model-catalog/provider contract with security limits and then land or replace the implementation accordingly.
- **Keep video in media-understanding only:** Defer direct chat/model video uploads and document the supported video.description tool-style path instead.
- **Prove providers first:** Let provider-specific implementations such as MiniMax or Google validate native video behavior behind provider-owned seams before adding a generic core chat-video content contract.

Yes, at source level: current main filters MP4/WebM/MOV/M4V before WebChat send, and the chat/model contracts only provide native image content plus generic offloaded media. I did not run a live browser upload in this read-only review.

## Solution Assessment

No for immediate automation. Existing video.description media-understanding plumbing is useful but distinct, so the best path is a maintainer-approved product/API/security design or a repaired implementation PR rather than a duplicate fix branch.

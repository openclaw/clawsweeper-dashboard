## Label Justifications

- `P2`: This is a source-proven multimodal feature gap with meaningful user friction, but it is not an urgent regression, outage, data-loss event, or active security incident.
- `impact:security`: Direct video upload would forward original user video bytes through managed storage or provider egress, so limits, retention, and policy are security-relevant.
- `impact:auth-provider`: The requested behavior depends on provider/model capability metadata, model choice, auth-preserving transport, and provider-native media payload support.
- `impact:ux-friction`: Users who want direct LLM video analysis must leave the chat upload flow and use media-understanding commands, frame extraction, or external tools.

## Summary

Keep open: current main and v2026.6.11 still lack direct video upload as native LLM chat/model input; existing video media-understanding support is adjacent, and the direct/overlapping implementation PRs are closed unmerged.

## What This Changes

Request direct video file upload support for video-capable LLMs, including file validation, native/fallback delivery, and chat preview behavior.

## Best Possible Solution

Keep this as the canonical tracker and land a maintainer-approved video-aware contract across WebChat, Gateway validation/staging, model capability metadata, provider delivery, fallback/security policy, docs, and regression tests.

## Maintainer Decision

Kind: product_direction

Question: Should OpenClaw add provider-native video as a first-class chat/model input, and if so what core/plugin contract, security limits, and fallback behavior should own it?

Rationale: The source gap is clear, but the permanent API shape crosses product UX, provider routing, raw-media egress, plugin/core ownership, and fallback policy that automation should not choose alone.

Likely owner: steipete

Owner reason: steipete has the strongest visible routing context plus broad adjacent media/provider history among the likely owners.

Owner confidence: medium

Options:

- **Approve first-class video input (recommended):** Define a coherent WebChat/Gateway/model-catalog/provider contract with size, retention, egress, and fallback rules before landing an implementation.
- **Keep video in media-understanding:** Defer direct chat/model video uploads and document the supported video.description media-understanding path instead.
- **Prove provider-specific plugins first:** Let provider-owned video behavior mature behind existing media-understanding/plugin seams before adding generic chat-video content types.

## Reproduction Assessment

Yes, at source level: current main filters video files before WebChat send, and the chat/model contracts only expose native image content plus generic managed media. I did not run a live browser upload in this read-only review.

## Solution Assessment

No for immediate automation. Existing video.description media-understanding is useful but distinct, so the best path is a maintainer-approved product/API/security design or a repaired implementation PR, not a duplicate fix branch.

## Summary

Keep open: this PR is a useful candidate, but it is not merge-ready because it strips volatile output only for `status: "failed"` exec results while OpenClaw maps ordinary non-zero process exits to `status: "completed"`. That leaves common Docker/SSH-style failures with exit codes such as 1 or 255 on the completed-output hash path, so their varying stderr can still reset the no-progress streak.

## What This Changes

The PR splits `exec` result hashing so completed exec output remains in the hash, failed exec output is omitted, and failed hashes include `failureKind` plus normalized `exitSignal`, with focused loop-detection tests.

## Best Possible Solution

Fix the no-progress fingerprint for real foreground exec outcomes, including normal non-zero `completed` results, while preserving exit-code-zero completed output as progress and keeping session-global breaker work in its separate canonical PR.

## Reproduction Assessment

Yes at source level. In the potential merge ref, an exec with `reason: "exit"` and exit code 1 remains `status: "completed"`, and the completed hash still includes output, so repeated same-command non-zero exits with varying stderr can still reset `noProgressStreak`.

## Solution Assessment

No. The PR is a plausible partial fix, but the best fix must cover the actual foreground exec result contract rather than only synthetic `status: "failed"` details.

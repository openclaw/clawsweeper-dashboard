## Summary

Keep open: current main still treats memory embeddings as a separate provider surface and defaults an unset or legacy-auto selection to OpenAI, while the May 31 reproduction confirms that non-OpenAI onboarding can still leave memory unavailable. The original message-blocking impact appears mitigated, but the embedding-auth and setup problem remains unresolved.

Likely related people: `steipete` has high-confidence historical ties to the memory system; Vincent Voyer and Blair Axford have medium-confidence ties through later memory-provider work.

## What This Changes

Address a regression where memory embeddings select OpenAI credentials instead of an appropriate explicitly configured embedding provider for agents using a non-OpenAI chat model.

## Best Possible Solution

Keep embeddings explicitly provider-configured, prevent memory-auth failures from blocking agent turns, and add an in-product onboarding or Doctor flow that selects and validates a supported embedding provider while clearly surfacing degraded memory status.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should memory embeddings remain an explicitly configured independent provider, or should OpenClaw inherit the active chat provider only when it advertises a supported embedding capability?

Rationale: Source establishes the current independent-provider behavior, but choosing automatic inheritance, mandatory setup, defaults, and upgrade handling changes provider and onboarding policy rather than repairing one mechanical defect.

Likely owner: steipete

Owner reason: The memory architecture traces to this person's feature history, and the remaining choice affects core provider and onboarding policy.

Owner confidence: high

Options:

- **Explicit setup and validation (recommended):** Keep memory embeddings independent, require or strongly prompt provider selection during setup, validate credentials, and degrade visibly without blocking chat.
- **Capability-based inheritance:** Inherit the chat provider only when its adapter explicitly declares embedding support, otherwise require an independent embedding provider.
- **Retain current behavior:** Continue defaulting memory embeddings to OpenAI and address the problem through clearer documentation and diagnostics only.

## Reproduction Assessment

Partly yes: source inspection and the May 31 reproduction establish the independent OpenAI embedding-auth failure on non-OpenAI onboarding. There is not a high-confidence current-main reproduction of the original claim that this still blocks all agent messages.

## Solution Assessment

No—the requested unconditional use of DeepSeek chat credentials is not generally safe because chat support does not prove embedding capability. The narrow maintainable solution is explicit or capability-gated embedding selection, validated setup, and graceful failure isolation.

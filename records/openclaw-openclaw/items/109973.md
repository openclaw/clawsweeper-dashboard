## What This Changes

The PR changes ACP new-session and resume-session handlers to launch session snapshot and available-command notifications without awaiting them before returning their results.

## Best Possible Solution

Schedule the complete notification sequence through a transport-owned post-response hook, or an explicit post-handler macrotask if no hook exists, catch failures from both notifications, and verify the exact wire sequence for new and resumed sessions with a focused transport test plus redacted live client logs.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.97

Full review comments:

- **[P1] Defer starting notifications past the response boundary:** `src/acp/translator.ts:394`
  - body: Calling an async function starts executing it immediately; `void` only discards its promise. This therefore depends on an internal `await` happening before any transport write and does not guarantee that the JSON-RPC result is serialized first, especially across both record modes. Use a transport-owned post-response hook or explicitly schedule the whole notification operation after handler completion, then test the wire sequence.
  - confidence: 0.96
- **[P1] Handle rejection from the available-command notification:** `src/acp/translator.ts:398`
  - body: The rejection callback only handles failure of `sendSessionSnapshotUpdate`. If `sendAvailableCommands` rejects, the promise returned by `then()` rejects with no terminal handler because the chain is discarded, potentially producing an unhandled rejection. Add a catch covering the complete sequence.
  - confidence: 0.99

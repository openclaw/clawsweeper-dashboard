## Summary

Keep open: current main and v2026.6.11 only partially address the reported session-artifact disk bloat. Deleted/reset archive retention, stale store temp cleanup, and old unreferenced transcript cleanup exist, but `.bak.*` retention, proactive startup/timer cleanup, and the broader durable archive lifecycle still need maintainer direction; the open cleanup PR only covers the narrower deleted/reset reporting path.

## What This Changes

The issue requests automatic cleanup of stale session artifacts such as `.reset.*`, `.deleted.*`, `.tmp`, and `.bak.*` files that accumulate under agent session directories.

## Best Possible Solution

Land or replace the targeted deleted/reset cleanup reporting PR, then make one explicit session-artifact lifecycle decision for `.bak.*`, stale temps, orphan transcripts/checkpoints, and startup/timer versus operator-command cleanup.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What durable lifecycle should OpenClaw enforce for session archive artifacts beyond the deleted/reset cleanup already covered by https://github.com/openclaw/openclaw/pull/97103?

Rationale: Current code intentionally preserves `.bak.*` archives in normal retention while other open reports argue both for more cleanup and for never deleting archived transcripts, so automation should not pick the data-retention policy.

Likely owner: steipete

Owner reason: Recent current-main history and adjacent cleanup/source-seam changes make this the strongest available routing signal for the product decision.

Owner confidence: medium

Options:

- **Narrow cleanup plus explicit archive policy (recommended):** Review or replace the deleted/reset reporting PR first, then specify a single retention policy for `.bak.*`, orphan transcripts/checkpoints, and proactive sweeps before queuing another fix.
- **Keep cleanup operator-driven:** Keep startup reads cheap and require `openclaw sessions cleanup --enforce` or a future explicit command for physical artifact cleanup.
- **Adopt proactive cleanup:** Make gateway startup or a timer run a bounded artifact sweep, accepting the need for stronger upgrade and data-retention proof.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: current code and tests show deleted/reset cleanup is partial, `.bak.*` archives are preserved, and startup reads do not run full pruning, but I did not perform a live multi-day filesystem repro.

## Solution Assessment

Is this the best way to solve the issue? Unclear for the full issue: the existing archive-retention helper is the right narrow path for deleted/reset cleanup, but `.bak.*` deletion and proactive sweeping need a maintainer-approved lifecycle policy.

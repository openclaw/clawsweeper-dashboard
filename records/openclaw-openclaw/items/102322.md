## Summary

Keep open: current main and the latest release still have the ACP bridge slicing cumulative Gateway snapshots by emitted length while Gateway explicitly marks non-prefix replacements, so the reported corruption remains real and unresolved.

## What This Changes

Fix the ACP bridge so Gateway non-append replacement deltas update assistant and thinking text without corrupting or leaving stale ACP client output.

## Best Possible Solution

Define an ACP-compatible replacement strategy, then update the translator to consume Gateway deltaText/replace for assistant text and thinking with divergent and shorter-revision regressions.

Options:

- **Choose a conservative ACP mapping (recommended):** Buffer or otherwise avoid unretractable provisional output when Gateway replacement semantics are possible, then add text and thinking regression tests.
- **Use a new-message fallback:** Emit replacement snapshots under a new ACP message identity, accepting that some clients may show both stale and corrected messages instead of one corrected answer.
- **Define a client extension:** Depend on ACP metadata or a known client capability only if maintainers are willing to document behavior for clients that ignore it.

Yes. Source inspection shows Gateway emits replace=true/deltaText for non-prefix revisions while ACP slices the cumulative message snapshot by sent length; I did not run a fresh failing executable test in this read-only review.

## Solution Assessment

Unclear. Fixing the slice is necessary, but the best repair depends on maintainer-selected ACP replacement semantics because plain agent_message_chunk output is append-oriented in common clients.

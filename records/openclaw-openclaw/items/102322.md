## Summary

Keep open: current main still has the ACP translator append-slicing Gateway snapshots, while Gateway explicitly emits replacement deltas for non-prefix revisions; the remaining blocker is a maintainer choice for ACP-compatible replacement semantics.

## What This Changes

The issue reports ACP assistant/thought chunk corruption when Gateway sends non-append in-progress text revisions and the ACP translator slices snapshots as append-only text.

## Best Possible Solution

Maintainers should choose an ACP-compatible replacement strategy, then update the translator and focused tests so divergent and shorter Gateway revisions cannot leave stale assistant or thinking text in ACP clients.

Options:

- **Choose conservative ACP mapping (recommended):** Buffer or otherwise avoid unretractable provisional output when replacement semantics are possible, then add text and thinking regression tests.
- **Adopt a client-specific replace extension:** Use ACP metadata or a known client capability only if maintainers accept non-standard behavior and document fallback semantics.
- **Accept corrected follow-up message:** Emit replacements as a new visible message/messageId and accept that some clients may show both stale and corrected text.

## Reproduction Assessment

Yes. Source inspection shows Gateway emits replace=true/deltaText for non-prefix revisions while ACP still slices cumulative snapshots by sent length; I did not execute a fresh live ACP client in this read-only review.

## Solution Assessment

Unclear. Fixing the bad slice is necessary, but the proposed full-text replacement emission is not obviously sufficient for append-only ACP clients, so maintainers should choose the replacement mapping first.

## Summary

Keep open: current main still has the ACP translator append-slicing Gateway snapshots, while Gateway now explicitly marks non-prefix replacements; the remaining blocker is choosing an ACP-compatible way to represent replacements because standard ACP message chunks appear append-only.

## What This Changes

The issue requests that ACP clients receive the Gateway-authoritative assistant text when in-progress output is revised instead of appended.

## Best Possible Solution

Define an ACP-compatible replacement strategy first, then update the ACP translator and focused tests so divergent and shorter Gateway revisions cannot leave stale assistant or thinking text in ACP clients.

Question: How should the ACP bridge represent Gateway replace=true revisions when standard ACP message chunks cannot retract already-emitted text?

Rationale: The source bug is clear, but the dependency contract means the obvious fix of emitting the full replacement text can still leave stale text in append-only ACP clients.

Likely owner: steipete

Owner confidence: high

Options:

- **Choose a conservative ACP mapping (recommended):** Preserve final-text correctness by buffering or otherwise avoiding unretractable provisional output when Gateway replacement semantics are possible, then add text and thinking regression tests.
- **Adopt a client-specific replace extension:** Use ACP metadata or a known client capability only if maintainers are willing to depend on non-standard behavior and document fallback behavior for clients that ignore it.
- **Accept new-message fallback:** Emit replacement snapshots as a new ACP message/messageId, accepting that some clients may show both stale and corrected text instead of one corrected answer.

## Reproduction Assessment

Yes. Source inspection shows Gateway emits replace=true/deltaText for non-prefix revisions while ACP still slices cumulative snapshots by sent length; I did not execute a fresh failing test in this read-only review.

## Solution Assessment

Unclear. Fixing the bad slice is necessary, but the proposed full-text replacement emission is not obviously sufficient for append-only ACP clients, so maintainers should choose the replacement mapping first.

## Summary

Keep open: current main still has the ACP translator append-slicing cumulative Gateway snapshots, while Gateway already marks non-prefix revisions with `replace=true` and `deltaText`; the remaining blocker is choosing an ACP-safe replacement mapping before changing streaming behavior.

## What This Changes

Fix the ACP bridge so revised Gateway assistant snapshots cannot leave ACP clients rendering corrupted or stale assistant or thinking text.

## Best Possible Solution

Define an ACP-compatible replacement strategy, then update the ACP translator for both visible text and thinking snapshots so Gateway `replace`/`deltaText` revisions cannot leave stale output, with focused translator and Gateway bridge tests.

Question: How should the ACP bridge represent Gateway `replace=true` revisions when standard ACP chunks are append-oriented and already-emitted text may not be retractable?

Rationale: The source bug is clear, but the durable fix depends on the product/protocol choice for replacement rendering across ACP clients rather than only on changing the slice arithmetic.

Likely owner: steipete

Owner confidence: high

Options:

- **Choose final-correct conservative mapping (recommended):** Buffer, restart message identity, or otherwise avoid unretractable provisional output so the final ACP-visible answer is correct across standard clients; this is the recommended direction before automation fixes code.
- **Adopt a client-specific replace extension:** Use ACP metadata or client capability behavior only if maintainers are willing to document fallback behavior for clients that ignore it.
- **Accept new-message fallback:** Emit replacement snapshots as a new ACP message/messageId and accept that some clients may show both stale and corrected text.

## Reproduction Assessment

Yes at source level. Gateway producer tests and docs show replacement deltas, while current ACP translator code still slices cumulative snapshots by sent length; I did not run a fresh executable ACP client repro in this read-only review.

## Solution Assessment

Unclear. Fixing the bad slice is necessary, but the best durable fix needs a maintainer-chosen ACP replacement mapping because standard ACP chunks and OpenClaw's ACP client append text rather than replacing prior output.

## Summary

Keep open: current main and the latest release still slice ACP assistant/thinking snapshots as append-only text while Gateway explicitly emits non-prefix replacements, and no newer issue or PR owns this exact ACP replacement-delta problem.

## What This Changes

The issue reports ACP assistant output corruption when Gateway sends non-append in-progress revisions that the translator slices as append-only deltas.

## Best Possible Solution

Define an ACP-compatible replacement strategy first, then update the ACP translator and focused text/thinking regression tests so divergent and shorter Gateway revisions cannot leave stale assistant output in ACP clients.

## Maintainer Decision

Question: How should the ACP bridge represent Gateway `replace=true` revisions when standard ACP message and thought chunks cannot retract already-emitted text?

Rationale: The source bug is clear, but the externally consumed ACP contract makes the repair shape a product/protocol choice rather than a safe mechanical slice replacement.

Likely owner: steipete

Owner reason: They introduced the ACP bridge and are the strongest history signal for choosing cross-protocol ACP behavior.

Owner confidence: high

Options:

- **Choose conservative ACP buffering (recommended):** Delay or buffer provisional ACP text when Gateway replacement semantics are possible so clients end the turn with the authoritative final text without relying on a non-standard retract operation.
- **Use a documented extension:** Emit replacement metadata or a client-specific capability only if maintainers are willing to document fallback behavior for clients that ignore it.
- **Accept new-message fallback:** Emit replacement snapshots under a new `messageId`, accepting that some clients may show both stale and corrected text instead of one corrected answer.

## Reproduction Assessment

Yes at source level. Gateway emits `replace=true`/`deltaText` for non-prefix revisions, while the ACP translator still ignores those fields and slices cumulative text/thinking snapshots by previously sent length.

## Solution Assessment

Unclear. Fixing the bad slice is necessary, but emitting full replacement text directly is not obviously the best fix for append-only ACP clients, so maintainers should choose the replacement semantics first.

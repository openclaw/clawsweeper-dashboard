## Summary

Keep open: current main and the latest release still have the ACP translator consuming Gateway chat snapshots as append-only text, while Gateway explicitly emits non-prefix replacements with `replace: true` and `deltaText`; the remaining decision is the ACP-compatible replacement strategy.

## What This Changes

The issue requests fixing ACP assistant and thought streaming so non-append Gateway revisions render the authoritative final text instead of stale or corrupted chunks.

## Best Possible Solution

Define an ACP-compatible replacement strategy first, then update the ACP translator and focused tests so divergent and shorter Gateway revisions cannot corrupt assistant or thinking text.

## Maintainer Decision

Required: true

Kind: product_direction

Question: How should the ACP bridge represent Gateway `replace: true` revisions when standard ACP message chunks cannot retract already-emitted text?

Rationale: The source bug is clear, but the durable behavior depends on whether maintainers prefer buffering, a client-specific replace extension, or a fallback that may show corrected text separately.

Likely owner: steipete

Owner reason: ACP support traces to this owner and the choice crosses the ACP/Gateway protocol boundary rather than being a purely mechanical slice fix.

Owner confidence: high

Options:

- **Choose conservative buffering (recommended):** Buffer or delay unretractable provisional ACP output where Gateway replacement revisions are possible, then emit a final append-only sequence that matches the authoritative text.
- **Use a replace extension:** Adopt an ACP metadata or capability extension for clients that understand replacement semantics and document fallback behavior for clients that ignore it.
- **Accept fallback duplication:** Emit corrected replacement snapshots as new ACP output even if some clients may show both stale and corrected text.

Yes. Source inspection shows Gateway emits `replace: true`/`deltaText` for non-prefix revisions while ACP still slices cumulative snapshots by sent length; I did not run a fresh failing test in this read-only review.

## Solution Assessment

Unclear. Fixing the bad slice is necessary, but maintainers should choose the ACP replacement mapping before an automated fix changes streaming behavior for append-only ACP clients.

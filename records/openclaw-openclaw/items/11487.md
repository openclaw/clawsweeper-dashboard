## Summary

Keep open: current main and the latest release still omit an ignored descriptive metadata field from strict channel group-entry schemas, typed config surfaces, generated config metadata, and docs. The related WhatsApp issue and PR overlap on readability, but they target runtime matching by mutable group name and do not solve this cross-channel metadata-only config request.

## What This Changes

The issue requests an optional human-readable metadata field on channel group config entries so numeric group IDs can be labeled without affecting runtime behavior.

## Best Possible Solution

Approve one canonical descriptive string field and apply it consistently across relevant group-entry types, strict schemas, generated metadata, docs, and validation coverage while preserving it through config load/write and ignoring it at runtime.

## Reproduction Assessment

Yes, at source level. Current strict representative group-entry schemas, typed config surfaces, and generated config metadata omit the requested descriptive field, so unrecognized metadata remains invalid without needing a live channel run.

## Solution Assessment

Unclear until maintainers choose the public contract. The maintainable shape is one canonical metadata field across schemas, types, generated metadata, docs, and tests rather than per-channel labels or multiple aliases.

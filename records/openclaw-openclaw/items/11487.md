## Summary

Keep open: current main still rejects the requested optional human-readable metadata field on representative strict group/channel config entries, and the open WhatsApp name-matching work addresses a narrower runtime lookup problem rather than this cross-channel config-label contract.

## What This Changes

Request an optional ignored string metadata field such as `name`, `label`, or `description` on channel group config entries so numeric or opaque group IDs can carry human-readable labels.

## Best Possible Solution

Choose one canonical optional string metadata key, add it consistently to relevant group/channel entry types, strict schemas, generated metadata, docs, and validation tests, then preserve it through config load/write while ignoring it at runtime.

## Reproduction Assessment

Yes. Source inspection on current main shows representative strict group/channel schemas and Telegram types do not accept `name`, `label`, or `description`, so a config entry with that metadata would remain invalid.

## Solution Assessment

Unclear pending maintainer choice. The proposed direction is plausible, but the best implementation needs a canonical field name and cross-channel scope decision; the related WhatsApp name-matching PR is a different functional feature, not the metadata-only fix.

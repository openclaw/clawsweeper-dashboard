## Summary

Keep open: current main and v2026.6.11 still do not accept an ignored human-readable `name`/`label`/`description` field on representative strict group-entry config schemas, and the linked WhatsApp work only partially overlaps by solving a different runtime matching problem.

## What This Changes

The issue requests a new optional string metadata field for channel group config entries so numeric group IDs in `openclaw.json` can carry a human-readable label without changing runtime behavior.

## Best Possible Solution

Choose one canonical optional string metadata field and apply it consistently across relevant group-entry types, strict schemas, generated metadata, docs, and validation coverage while preserving it through config load/write and ignoring it at runtime.

## Reproduction Assessment

Yes, at source level. Current strict representative group-entry schemas and typed config surfaces omit the requested descriptive field, so unrecognized metadata remains invalid without needing a live channel run.

## Solution Assessment

Unclear until maintainers choose the public contract. The maintainable shape is one canonical metadata field across schemas, types, generated metadata, docs, and tests rather than per-channel labels or multiple aliases.

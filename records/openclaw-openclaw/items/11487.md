## Summary

Keep open: current main and v2026.6.11 still reject the requested ignored human-readable group-entry metadata, and the related WhatsApp issue/PR only covers functional WhatsApp group-name matching rather than cross-channel config metadata.

## What This Changes

The issue requests an optional ignored string metadata field such as `name`, `label`, or `description` on channel group config entries.

## Best Possible Solution

Choose one canonical optional string metadata field and apply it consistently across relevant group-entry schemas, types, generated metadata, docs, and validation coverage while ignoring it at runtime.

## Reproduction Assessment

Yes, at source level: representative strict group-entry schemas and the Telegram type surface still omit `name`, `label`, and `description`, so the proposed config shape remains unsupported on current main and v2026.6.11.

## Solution Assessment

Unclear until maintainers choose the public config contract. The best shape is one canonical metadata field across schemas, types, generated metadata, docs, and tests rather than multiple aliases or a per-channel-only field.

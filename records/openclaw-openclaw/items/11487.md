## Summary

Keep open: both current main and the latest release still reject descriptive metadata on strict group-entry schemas, and the adjacent WhatsApp work solves functional name matching rather than this cross-channel config-readability problem. The remaining blocker is a maintainer product decision on the canonical field name and scope.

## What This Changes

Add one optional inert human-readable metadata field to channel group configuration entries.

## Best Possible Solution

Adopt one explicitly inert `label` field for opaque-ID group and channel entries, preserve it through validation and config writes without runtime semantics, and keep name-to-ID discovery or authorization matching as a separate capability.

## Maintainer Decision

Question: Should OpenClaw add a canonical inert metadata field to opaque-ID group/channel entries, and should that field be named `label` rather than `name` or `description`?

Rationale: The source proves the capability is absent but cannot establish the intended public config vocabulary or whether readable-key channel entries should receive the same field.

Likely owner: steipete

Owner confidence: high

Options:

- **Adopt `label` for opaque IDs (recommended):** Add an optional inert `label` string only to group/channel entries whose keys are stable opaque identifiers, with schema, metadata, docs, and round-trip coverage.
- **Apply one field everywhere:** Add the chosen metadata property uniformly to every group and channel entry schema for maximum consistency.
- **Use discovery tooling only:** Keep behavior-only schemas and instead improve directory or config tooling that maps stable IDs to live display names.

## Reproduction Assessment

Yes at source level: current and released strict schemas reject unrecognized descriptive fields, while the corresponding exported config types omit them. No artifact-producing runtime test was run during this read-only review.

## Solution Assessment

The inert-metadata approach is the narrowest durable solution if one canonical field is limited to opaque-ID entries; applying it indiscriminately across all channels would be broader than the demonstrated problem.

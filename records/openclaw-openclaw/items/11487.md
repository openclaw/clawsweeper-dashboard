## Summary

Keep this issue open: current main still rejects a display-only field on strict group-entry schemas, while the permanent field name and cross-channel contract need a maintainer decision. Likely related people: steipete (high confidence) and vincentkoc (medium confidence).

## What This Changes

Add one optional, runtime-ignored human-readable metadata field to channel group configuration entries keyed by opaque IDs.

## Best Possible Solution

Adopt one explicitly display-only field—preferably `label`—for the supported group-entry shapes, validate and preserve it consistently, ignore it in runtime matching and authorization, then update generated metadata, documentation, and parity tests together.

- **Use `name` as display metadata:** Adopt an optional string `name`, while documenting that it is operator-maintained metadata rather than the provider’s current group name.
- **Keep opaque keys only:** Decline a new public metadata field and retain IDs as the sole in-config group identifier.

## Reproduction Assessment

Yes, from source: adding `name` or `label` to a Telegram group entry is rejected because the current `TelegramGroupSchema` is strict and omits those fields. The same ID-keyed, functional-only contract is documented for group configuration.

## Solution Assessment

No, not as a per-channel one-line schema addition. The maintainable path is one maintainer-approved display-only field applied consistently to supported group entry types and their config metadata, docs, and tests.

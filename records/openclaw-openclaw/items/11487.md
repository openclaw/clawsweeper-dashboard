Keep open: current main and the latest release still omit the requested ignored descriptive group-entry metadata from representative strict schemas, typed config surfaces, generated metadata, and docs; the related WhatsApp work only partially overlaps because it targets runtime name matching.

## What This Changes

The issue requests an optional human-readable `name`, `label`, or `description` string on channel group config entries.

## Best Possible Solution

Approve one canonical descriptive string field and implement it consistently across relevant group-entry types, strict schemas, generated metadata, docs, and validation coverage while preserving it through config load/write and ignoring it at runtime.

## Reproduction Assessment

Yes, at source level: representative strict group-entry schemas and typed config surfaces still omit the requested descriptive field, and generated metadata keeps extra group-entry fields invalid.

## Solution Assessment

Unclear until maintainers choose the public contract. The maintainable path is one canonical metadata field across schemas, types, generated metadata, docs, and tests rather than multiple aliases or per-channel labels.

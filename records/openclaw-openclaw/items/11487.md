## What This Changes

The issue requests an optional human-readable string metadata field such as `name` or `label` on channel group config entries.

## Best Possible Solution

Approve one canonical optional string metadata field and apply it consistently across relevant group-entry types, strict schemas, generated metadata, docs, and validation coverage while preserving it through config load/write and ignoring it at runtime.

## Reproduction Assessment

Yes, at source level: representative strict group-entry schemas and typed config surfaces still omit the requested descriptive field, so unrecognized metadata remains invalid without a live channel run.

## Solution Assessment

Unclear until maintainers choose the public contract. The maintainable path is one canonical metadata field across schemas, types, generated metadata, docs, and tests rather than multiple aliases or per-channel labels.

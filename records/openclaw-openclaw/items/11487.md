## Summary

Current main still lacks persistent schema-visible metadata for opaque channel group entries. JSON5 comments and channel-resolution tooling do not provide a validated identifier that programmatic config edits reliably preserve, while the linked WhatsApp work addresses distinct runtime name matching.

## What This Changes

Add an optional human-readable metadata string to channel group configuration entries without changing runtime behavior.

## Best Possible Solution

Define one explicitly metadata-only field for opaque identifier-keyed entries, preserve it through config parsing and writing without runtime semantics, and update all in-scope types, strict schemas, generated metadata, documentation, and validation coverage together.

Options:

- **Add scoped `label` metadata (recommended):** Add an optional `label` string only to opaque identifier-keyed group or channel entries, preserve it in config tooling, and ignore it at runtime.
- **Add universal metadata:** Add a canonical field to every group, topic, guild, and channel entry for uniformity, accepting a broader public configuration surface.
- **Keep external annotations:** Decline new config surface and rely on JSON5 comments plus channel-specific lookup and resolution workflows.

## Reproduction Assessment

Yes at source level: current strict group-entry schemas reject unknown metadata and the corresponding configuration types omit it, although this is a feature gap rather than a runtime bug.

## Solution Assessment

No, not as a mechanical addition of `name` across every channel entry; a maintainer-approved metadata-only field scoped to opaque identifiers is the narrower and less ambiguous design.

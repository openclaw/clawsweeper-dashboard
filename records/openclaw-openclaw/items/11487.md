## Summary

Keep this open: current main still rejects human-readable group-entry metadata in the strict channel config schemas, types, generated metadata, and docs; the remaining work is a product/config-contract decision, not cleanup-close material.

## What This Changes

The issue requests an optional human-readable metadata field on channel group config entries so opaque group IDs can be identified in `openclaw.json`.

## Best Possible Solution

Adopt one canonical optional string metadata key across the relevant group/channel entry types, strict schemas, generated metadata, docs, and validation tests while keeping runtime behavior unchanged.

## Reproduction Assessment

Yes, from source inspection: current strict group-entry schemas and config types do not include `name`, `label`, or `description`, so such metadata would be rejected by config validation. I did not run parser tests because this review is read-only.

## Solution Assessment

Partly: a single cross-channel optional metadata field is the right shape if maintainers want this capability, but the field name and exact config-contract scope need maintainer choice before implementation.

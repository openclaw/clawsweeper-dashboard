## Summary

Keep open: current main and v2026.6.11 still reject descriptive metadata on representative strict group-entry config schemas, and the related WhatsApp work solves a different runtime name-matching problem rather than this cross-channel metadata contract.

## What This Changes

The issue requests one optional ignored string field such as `name` or `label` on channel group config entries so humans and agents can identify numeric group IDs.

## Best Possible Solution

Choose one canonical optional string metadata field and add it consistently across relevant group-entry types, strict schemas, generated config metadata, docs, and validation coverage while preserving it through config load/write and ignoring it at runtime.

## Reproduction Assessment

Yes, at source level. Current strict representative group-entry schemas and typed config surfaces omit the requested descriptive field, so unrecognized metadata remains invalid without needing a live channel run.

## Solution Assessment

Unclear until maintainers choose the public contract. The maintainable shape is one canonical metadata field across schemas, types, generated metadata, docs, and tests rather than per-channel labels or multiple aliases.

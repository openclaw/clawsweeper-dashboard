## Summary

Keep open: current main and v2026.6.11 still omit the requested ignored descriptive field from representative strict group-entry schemas, typed config surfaces, generated config metadata, and group docs; the related WhatsApp work only partially overlaps on runtime name matching.

## What This Changes

Requested addition of an optional human-readable metadata field, such as `name` or `label`, to channel group config entries in `openclaw.json`.

## Best Possible Solution

Approve one canonical descriptive string field and apply it consistently across relevant group-entry types, strict schemas, generated metadata, docs, and validation coverage while preserving it through config load/write and ignoring it at runtime.

## Reproduction Assessment

Yes, at source level. Current strict representative group-entry schemas and typed config surfaces omit the requested descriptive field, so unrecognized metadata remains invalid without needing a live channel run.

## Solution Assessment

Unclear until maintainers choose the public contract. The maintainable shape is one canonical metadata field across schemas, types, generated metadata, docs, and tests rather than per-channel labels or multiple aliases.

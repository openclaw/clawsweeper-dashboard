## Summary

Keep open: current main and v2026.6.11 still reject ignored descriptive metadata on representative strict group-entry schemas, and the related WhatsApp issue/PR only covers runtime matching by mutable group name rather than this cross-channel metadata contract.

## What This Changes

The issue requests one optional human-readable string field such as `name`, `label`, or `description` on channel group config entries.

## Best Possible Solution

Approve one canonical optional string metadata field and apply it consistently across relevant group-entry types, strict schemas, generated metadata, docs, and validation coverage while preserving it through config load/write and ignoring it at runtime.

## Reproduction Assessment

Yes, at source level. Current strict representative group-entry schemas, typed config surfaces, generated metadata, and docs omit the requested descriptive field, so unrecognized metadata remains invalid without a live channel run.

## Solution Assessment

Unclear until maintainer product review: adding one optional string field is a plausible narrow implementation, but the best fix depends on the canonical field name and whether all relevant channel group-entry surfaces should accept it together.

Keep open: current main and the latest release still omit the requested ignored human-readable group-entry metadata from strict channel group schemas, typed config surfaces, generated metadata, and docs; the related WhatsApp work only partially overlaps by adding runtime name matching for one channel.

## What This Changes

The issue requests an optional string metadata field such as `name`, `label`, or `description` on group config entries across channel configs.

## Best Possible Solution

Choose one canonical optional string metadata field, add it consistently to relevant group-entry types, strict schemas, generated metadata, docs, and validation coverage, preserve it through config load/write, and ignore it at runtime.

## Reproduction Assessment

Yes, at source level: representative strict group-entry schemas and typed config surfaces still omit the requested descriptive field, so unrecognized metadata remains invalid without needing a live channel run.

## Solution Assessment

Unclear until maintainers choose the public config contract. The maintainable path is one canonical metadata field across schemas, types, generated metadata, docs, and tests rather than multiple aliases or per-channel labels.

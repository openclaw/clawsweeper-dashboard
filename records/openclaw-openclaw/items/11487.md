## What This Changes

The issue requests an optional human-readable `name`, `label`, or `description` string on channel group config entries in `openclaw.json`.

## Best Possible Solution

Approve one canonical descriptive string field and apply it consistently across relevant group-entry types, strict schemas, generated metadata, docs, and validation coverage while preserving it through config load/write and ignoring it at runtime.

## Reproduction Assessment

Yes, at source level: representative strict group-entry schemas and typed config surfaces still omit the requested descriptive field, so unrecognized metadata remains invalid without needing a live channel run.

## Solution Assessment

Unclear until maintainers choose the public contract. The maintainable path is one canonical metadata field across schemas, types, generated metadata, docs, and tests rather than multiple aliases or per-channel labels.

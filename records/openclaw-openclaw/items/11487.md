## Summary

Current main still lacks schema-visible metadata for opaque channel group entries. JSON5 comments and limited name-resolution commands are not equivalent to a validated identifier preserved by config tooling, while the linked WhatsApp work changes runtime matching and does not supersede this cross-channel request. 

## What This Changes

Add an optional human-readable metadata string to applicable channel group configuration entries without changing runtime behavior.

## Best Possible Solution

Standardize an inert optional `label` field only on applicable opaque-ID group, guild, channel, and topic entries, preserve it through schema-aware config writes, expose it in generated metadata and documentation, and keep routing and authorization based on stable native IDs.

## Reproduction Assessment

Yes at source level: current strict group-entry schemas and public examples lack a schema-visible metadata field, so the proposed properties remain unsupported. No failing runtime scenario is needed because this is a feature request rather than a regression.

## Solution Assessment

Not fully yet: inert metadata is maintainable, but applying it to every channel type is too broad until maintainers choose the canonical name and eligible opaque-ID entry shapes. `label` is the safest default because it does not imply runtime native-name matching.

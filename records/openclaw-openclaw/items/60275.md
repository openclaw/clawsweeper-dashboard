## Summary

Keep open: current main and the latest release still expose one effective heartbeat schedule/config per agent, with only a single optional session override; cron can target explicit sessions, but that is an adjacent scheduler rather than native persisted heartbeat entries.

## What This Changes

The issue requests native session-scoped heartbeat entries so one agent can own multiple restart-safe schedules with explicit session binding, routing, observability, and operator controls.

## Best Possible Solution

A maintainer-owned design should either add one canonical persisted heartbeat-entry store/control API or explicitly document cron/plugin-owned scheduling as the supported multi-session path, with migration rules that avoid duplicate truth.

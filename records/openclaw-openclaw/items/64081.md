## Summary

Keep open: current main and v2026.6.11 still lack a config-level default task notify policy, while ACP, subagent, and Task Flow paths continue to fall back to hardcoded notify defaults unless each caller passes `notifyPolicy`. This is valid but needs maintainer product direction because it adds a public config/default surface and overlaps narrower channel visibility issues.

## What This Changes

The issue requests a user-configurable default task notification policy for ACP/subagent/background task records so users can suppress raw completion messages without racing a per-task `openclaw tasks notify` override.

## Best Possible Solution

Add a maintainer-approved, backward-compatible task notify default resolver that preserves current behavior when unset, lets explicit task/flow policies win, keeps cron/CLI/media silent defaults intact, and updates config schema, help, docs, and focused regression tests together.

Options:

- **Adopt per-runtime defaults (recommended):** Add an additive `agents.defaults.tasks.notifyPolicy` map that keeps current defaults when unset and lets ACP, subagent, cron, CLI, and media behavior be configured independently.
- **Adopt one global default:** Add a simpler global default while preserving explicit task policies and carve-outs for current silent runtime classes, accepting less granular operator control.
- **Defer config surface:** Keep this issue open but solve only the narrower Discord/Codex visibility bugs until maintainers choose a broader task notification policy model.

## Reproduction Assessment

Yes. Source inspection shows deliverable tasks without explicit `notifyPolicy` still resolve to `done_only`, ACP/subagent callers omit the field, and the strict config schema has no default task notify policy key.

## Solution Assessment

Unclear. A config-level default is plausible, but maintainers still need to choose the public config path and semantics before implementation; the safe direction must preserve explicit per-task policies and current silent defaults.

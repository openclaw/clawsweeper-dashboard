## Summary

Keep open: current main and the latest release still lack a config-backed default task notify policy, while ACP, subagent, and Task Flow paths continue to fall back to hardcoded task notification defaults. This remains a real feature/product decision rather than a stale cleanup close.

## What This Changes

Request a config-level default task notify policy so ACP and subagent background completions can be silenced or adjusted without a per-task race.

## Best Possible Solution

Add a maintainer-approved task notify default resolver that preserves current behavior when unset, lets explicit task/flow policies win, keeps cron/CLI/media silent defaults intact, and updates schema, docs, and tests together.

## Maintainer Decision

Question: Should OpenClaw add a config-backed default task notify policy, and should that surface be one global default or a per-runtime policy map?

Rationale: The source gap is clear, but choosing a public config key and default semantics affects existing channel notification volume and cannot be safely inferred by automation.

Likely owner: vincentkoc

Owner reason: Vincent has the strongest recent history on task delivery policy, task registry defaults, and ACP/subagent task routing.

Owner confidence: high

Options:

- **Add per-runtime defaults (recommended):** Introduce an agents.defaults.tasks.notifyPolicy map so ACP/subagent behavior can be tuned while cron, CLI, and media defaults remain explicit.
- **Add one global default:** Use a simpler agents.defaults.tasks.defaultNotifyPolicy key, accepting that callers must override more paths to preserve today’s runtime differences.
- **Decline new config:** Keep the existing per-task CLI override and address only narrower runtime/channel issues such as Discord visibility or ACP runaway loops.

## Reproduction Assessment

Yes. Source inspection shows deliverable tasks without explicit notifyPolicy still resolve to done_only, ACP/subagent callers omit that field, and docs expose only a per-task notify override.

## Solution Assessment

Unclear. A config-level default is plausible, but maintainers still need to choose the public config shape and compatibility semantics before implementation.

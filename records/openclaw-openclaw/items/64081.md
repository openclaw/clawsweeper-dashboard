## Summary

Keep open: current main and v2026.6.11 still lack a schema-backed config default for task notify policy, and ACP, subagent, and Task Flow creation still fall back to hardcoded notify defaults when callers omit `notifyPolicy`. The source gap is clear, but adding a public config/default surface needs maintainer product direction before implementation.

## What This Changes

Request to add a config-level default task notification policy for ACP, subagent, and related task records so users can suppress raw background completion messages before task creation.

## Best Possible Solution

Add a maintainer-approved, backward-compatible task notify default resolver that preserves current behavior when unset, lets explicit task or flow policies win, keeps cron/CLI/media silent defaults intact, and updates schema, docs, and tests together.

Owner confidence: high

Options:

- **Add per-runtime defaults (recommended):** Add an additive `agents.defaults.tasks` policy map that defaults to current behavior and lets maintainers preserve cron/CLI/media silence while users tune ACP and subagent notifications.
- **Add one global default:** Expose a smaller single default that is easier to document but risks flattening today’s runtime-specific behavior unless exceptions are hardcoded.
- **Defer to narrower policies:** Keep this issue open while maintainers resolve Discord/Codex/ACP-specific visibility and flood-control issues before adding a cross-runtime config surface.

## Reproduction Assessment

Yes, from source inspection. Deliverable tasks without an explicit `notifyPolicy` still resolve to `done_only`, ACP/subagent callers omit the field, and current config has no default policy key.

## Solution Assessment

Unclear until maintainers choose the public API shape. A config-level default is plausible, but the maintainable fix should be additive, preserve explicit policies, and avoid conflicting with narrower channel/runtime visibility issues.

## Summary

Keep open: current main and v2026.6.11 still lack a schema-backed config default for task notify policy, and ACP/subagent/Task Flow paths still fall back to hardcoded defaults unless a caller passes `notifyPolicy`.

## What This Changes

The issue requests a config-level default notify policy for background task completion messages across subagent and ACP task creation.

## Best Possible Solution

Add a maintainer-approved, backward-compatible resolver under the current config model that preserves existing behavior when unset, lets explicit task and flow policies win, keeps cron/CLI/media silent defaults intact, and updates schema, docs, and tests together.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What public config shape should OpenClaw support for default task notify policy: one global default or per-runtime defaults for ACP, subagent, cron, CLI, and media-like tasks?

Rationale: The code path is clear, but AGENTS.md and VISION.md treat config/default additions as compatibility-sensitive product surface; automation should not choose the permanent schema and default semantics.

Likely owner: vincentkoc

Owner reason: Vincent Koc owns the clearest recent task delivery and ACP/subagent executor-routing history for the affected defaulting path.

Owner confidence: high

Options:

- **Per-runtime defaults (recommended):** Add a strict `agents.defaults.tasks.notifyPolicy` map so operators can silence ACP/subagent completions without changing cron/CLI/media behavior.
- **Single global default:** Add one `agents.defaults.tasks.defaultNotifyPolicy` value, accepting simpler configuration at the cost of broader message-volume impact.
- **No new config:** Keep per-task `openclaw tasks notify` and solve only the narrower channel/runtime visibility issues separately.

## Reproduction Assessment

Yes for source inspection: deliverable tasks without explicit `notifyPolicy` still resolve to `done_only`, and the ACP/subagent callers omit that field. I did not run a live Telegram repro because the source path directly proves the reported default behavior.

## Solution Assessment

Unclear until maintainers choose the config contract. A config-level default is plausible, but the safest implementation should preserve current defaults when unset and avoid creating overlapping channel/runtime policy surfaces.

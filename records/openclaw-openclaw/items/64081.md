## Summary

Keep open: current main and the latest release still lack a config-level default task notify policy, while ACP, subagent, and Task Flow paths continue to fall back to hardcoded notification defaults. This is valid, but it adds a public config/default surface and needs maintainer product direction before implementation.

## What This Changes

The issue requests a config-level default task notification policy so users can make ACP/subagent task completion notifications silent or more granular without racing per-task CLI overrides.

## Best Possible Solution

Add a maintainer-approved, backward-compatible task notify default resolver that preserves current behavior when unset, lets explicit task or flow policies win, keeps cron/CLI/media silent defaults intact, and updates schema, docs, and tests together.

Question: Should OpenClaw expose a public config-level default task notify policy, and should that config be a single global default or a per-runtime policy map?

Rationale: The source gap is clear, but choosing the config contract changes defaults and channel delivery semantics for existing users, which automation should not decide without maintainer intent.

Likely owner: steipete

Owner reason: Recent adjacent work touched requester attribution, task docs, and subagent delivery paths, making this the best available routing candidate for the public config/default decision.

Owner confidence: medium

Options:

- **Per-runtime default map (recommended):** Add a strict config surface such as agents.defaults.tasks.notifyPolicy with per-runtime entries so ACP/subagent can be changed without disturbing cron, CLI, and media defaults.
- **Single global default:** Add one defaultNotifyPolicy with explicit code exceptions for runtimes that must remain silent, accepting a simpler user model but more special-case logic.
- **No new config surface:** Keep per-task CLI overrides and address narrower Discord/Codex/ACP visibility issues individually instead of adding another global config knob.

## Solution Assessment

Unclear as a final product choice: a config-level default is plausible, but maintainers still need to choose the public config shape and compatibility semantics before implementation.

## Summary

Current main still emits tool emoji and decorative Unicode throughout the built-in TUI, and the exact prior implementation closed unmerged after deprioritization rather than resolution. The issue remains necessary, but maintainers must choose the durable activation contract and fallback vocabulary before implementation because current main now has a dedicated terminal-only `tui` config boundary and the pinned selector dependency hard-codes one Unicode marker.

## What This Changes

Add a user-selectable plain-text TUI rendering mode that replaces emoji and decorative Unicode with screen-reader-friendly text or ASCII.

## Best Possible Solution

Define one typed TUI rendering policy under the current terminal owner boundary, resolve it once in `runTui()`, apply it to every visible glyph path, and add or upstream a configurable pi-tui selection marker; validate the chosen text with real screen-reader users and focused config, component, and PTY tests.

## Label Justifications

- `impact:ux-friction`: Decorative emoji and Unicode produce verbose, confusing screen-reader output and make the available TUI workflow materially harder to navigate.

## Summary

Keep open: current main still lacks a TUI-wide ASCII presentation mode, the only implementation PR closed unmerged, and maintainers still need to approve the durable startup contract and selector ownership.

## What This Changes

Add a TUI accessibility option that replaces emoji and decorative Unicode symbols with screen-reader-friendly ASCII or plain text.

## Best Possible Solution

Add a documented `tui.accessibility.plainText` startup setting, keep its presentation effects explicitly TUI-scoped, define one canonical ASCII symbol set, obtain or own a configurable selector-prefix seam, and validate the complete first-render workflow with a blind screen-reader user.

- **Defer the presentation contract:** Keep the issue open without implementation until a broader terminal presentation-profile system is designed.

## Reproduction Assessment

Yes at source level: current main and the pinned pi-tui dependency emit the reported decorative emoji and Unicode without an ASCII alternative. Final acceptance still needs a real terminal and screen-reader run covering the first render, selectors, statuses, and tool cards.

## Solution Assessment

Not yet: the accessibility mode is the right direction, but the original `ui.accessibility.plainText` shape should move under the dedicated `tui` namespace, remain TUI-scoped, and include a real solution for the dependency-owned selector arrow.

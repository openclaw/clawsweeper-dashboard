## Label Justifications

## Summary

Keep open: current main still lacks a TUI plain-text accessibility mode, the prior implementation closed unmerged, and multiple screen-reader users confirm that decorative glyph output remains a usability problem requiring a maintainer product decision.

## What This Changes

Add a TUI accessibility mode that replaces emoji, box-drawing characters, arrows, and other decorative Unicode symbols with screen-reader-friendly ASCII text.

## Best Possible Solution

Add one documented persisted plain-text mode, load it once at TUI startup, thread it through every TUI renderer and pi-tui theme seam, standardize tested ASCII alternatives, and validate the completed flow with a real screen reader.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw standardize a persisted `ui.accessibility.plainText` contract, and what ASCII vocabulary should it use for tools, status indicators, selectors, and separators?

Rationale: The problem is established, but repository policy sets a high bar for new config and the choice determines a lasting user-visible presentation contract across OpenClaw and pi-tui-owned rendering.

Likely owner: vignesh07

Owner reason: The repository explicitly routes TUI ownership to this person, making them the strongest available owner for the presentation and activation contract.

Owner confidence: high

Options:

- **Persisted plain-text mode (recommended):** Add `ui.accessibility.plainText`, use explicit ASCII forms such as `[ok]`, `[err]`, `>`, and `-`, and cover all TUI presentation paths consistently.
- **Runtime-only flag:** Add an `openclaw tui --plain` flag without persistent config, reducing config surface but requiring accessibility users to remember the flag on every launch.
- **Wait for upstream defaults:** Defer the feature until pi-tui provides a complete accessibility theme, leaving OpenClaw-owned emoji and glyph output unchanged meanwhile.

## Reproduction Assessment

Yes at source level: current configuration exposes no plain-text setting and the identified presentation paths still emit decorative glyphs unconditionally. A fresh live screen-reader session was not run during this read-only review.

## Solution Assessment

Unclear until maintainers choose the activation contract and canonical ASCII vocabulary; once chosen, a single mode threaded through all render paths is preferable to isolated character substitutions.

## Summary

Current main still lacks a plain-text TUI mode, and the exact prior implementation closed unmerged after deprioritization rather than because the problem was solved. The accessibility need is supported by source and two screen-reader users, but maintainers still need to choose the durable activation contract before implementation.

## What This Changes

Add a TUI accessibility mode that substitutes ASCII text for emoji, arrows, spinners, separators, and other decorative Unicode symbols.

## Best Possible Solution

Create one startup-resolved TUI presentation policy with explicit ASCII alternatives for every decorative glyph, route all OpenClaw and pi-tui wrapper rendering through it, document the chosen activation mechanism, and validate it with a real screen reader plus PTY coverage.

Question: Should plain-text TUI rendering be activated by a persisted config key, automatic terminal detection, or an explicit TUI/CLI flag?

Rationale: The prior PR selected a config key but was closed after deprioritization, while repository policy sets a high bar for new config and environment detection is imperfect; maintainer intent is needed for the durable public contract.

Likely owner: steipete

Owner confidence: high

Options:

- **Explicit TUI flag (recommended):** Add a documented `openclaw tui`/`openclaw chat` flag that avoids persistent config growth and provides a reliable user-controlled mode.
- **Persisted TUI setting:** Add a strict `tui.accessibility` setting that persists across launches but enlarges config, schema, help, docs, and upgrade-sensitive surfaces.
- **Automatic detection:** Infer the mode from terminal or accessibility environment signals, accepting false positives and negatives unless an explicit override is also added.

## Reproduction Assessment

Yes at source level: current main unconditionally emits emoji, arrows, box drawing, ellipses, and dependency spinner symbols, and two users report the screen-reader impact. This review did not perform a live NVDA or VoiceOver terminal run.

## Solution Assessment

No, the proposed persisted `ui.accessibility.plainText` key is not yet proven to be the best activation mechanism. The best implementation shape is a centralized TUI presentation policy, preferably first exposed by an explicit TUI flag unless maintainers intentionally choose persistence.

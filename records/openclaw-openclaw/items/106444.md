## Summary

Keep this issue open for a maintainer-defined Telegram delivery contract and a redacted current-main trace. Current releases already fixed the two concrete mechanisms named in the report—same-chat tool sends falling through to a silent fallback, and replay of accumulated pre-tool text—but the broader retry/resume assertion is not reproduced here and a turn-wide receipt could suppress intentional follow-ups.

## What This Changes

Ensure a single logical Telegram assistant result is not visibly emitted again through a message tool, final reply, delivery-mirror, retry, or resumed-turn path.

## System Context

An inbound Telegram turn invokes an agent that may explicitly send a message and may later produce a final reply or recovery output. The delivery layer decides which of those outputs becomes visible in the Telegram chat and records related session state.

## Best Possible Solution

Keep the existing path-specific suppression rules, obtain a redacted current-main trace that identifies the second outbound path, and extend deduplication only at the delivery owner that can prove the outputs are equivalent.

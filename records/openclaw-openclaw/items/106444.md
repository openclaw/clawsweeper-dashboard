## Summary

Keep this issue open, but do not implement the proposed global receipt system yet. Current main already performs route-aware suppression of exact same-target message-tool duplicates and tracks several explicit delivery-evidence states; the report provides no logs, transcript, payload pair, or current-main reproduction identifying which remaining path bypasses those guards. The open queue-recovery report covers one concrete subset, while suppressing every distinct final after a tool send could hide intentional follow-ups.

## What This Changes

Ensure one logical Telegram result is not visibly delivered more than once across explicit message-tool sends, final replies, delivery mirrors, retries, and resumed turns.

## Best Possible Solution

First capture one current-main Telegram trace showing the successful outbound path and the later duplicate, then repair the narrow owner boundary that lost or ignored delivery evidence; keep exact route-aware dedupe and preserve explicitly distinct follow-ups rather than adding a global semantic-content ledger by default.

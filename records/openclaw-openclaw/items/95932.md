## Label Justifications

- `P3`: This is local developer hook hardening with limited blast radius and no runtime product impact.
- `merge-risk: 🚨 compatibility`: Existing contributors with relative or same-file global hooksPath values can have their local commit workflow broken by the new hook chain.
- `merge-risk: 🚨 availability`: The same-file hook case can recurse repeatedly and stall local pre-commit execution before the repo formatter flow runs.

## Summary

Keep open: the hardening idea is useful, but the patch is not merge-ready because the configured global hook can resolve to this same repo hook and recurse before the existing formatter flow runs.

## What This Changes

The branch makes `git-hooks/pre-commit` read global `core.hooksPath` and invoke an executable global `pre-commit` before the repo-local formatter hook.

## Best Possible Solution

Keep the global-hook chaining only after resolving the candidate global hook and the current repo hook, skipping the global call when they point to the same executable, with focused coverage for the relative `hooksPath=git-hooks` case.

Yes. Source inspection against the merge result plus Git's hook-path contract shows that a global relative `core.hooksPath=git-hooks` can resolve to this repo's `git-hooks/pre-commit` and invoke itself.

## Solution Assessment

No. The hook is the right layer for this local hardening, but the current implementation needs a same-file recursion guard before it is the narrow maintainable fix.

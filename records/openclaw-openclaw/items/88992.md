## Summary

Keep open: the recovery direction and proof are useful, but current head still uses user-controlled `summaryLine` as the one-shot retry marker, so an ordinary queued turn can be mistaken for an already retried recovery and suppress the only retry. Maintainers also still need to choose between this opt-in config branch and the related default-on successor at https://github.com/openclaw/openclaw/pull/99536, which is open but currently conflicting.

## What This Changes

The PR adds opt-in `messages.strandedReplyRecovery` behavior that detects substantive `message_tool_only` finals without a message tool call, enqueues a single message-tool retry, updates prompt/docs/config schema, and adds QA/unit coverage.

## Best Possible Solution

Use private queued-run metadata for retry identity, then have maintainers choose the opt-in config surface versus the default-on guarded recovery path before merging.

## Reproduction Assessment

Yes. Source inspection and the linked QA scenario show the high-confidence path: `messages.visibleReplies=message_tool`, a substantive final without `message(action=send)`, and no current-main recovery beyond the warning.

## Solution Assessment

No for the current patch shape. A bounded message-tool retry is plausible, but using `summaryLine` as retry state is not robust, and the opt-in versus default-on policy still needs maintainer choice.

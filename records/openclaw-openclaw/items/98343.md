## Summary

Keep open: the PR still gates shipped direct `google-gemini-cli` runtime provider/backend registration behind a new env opt-in, and the body proof is stale for the current `b0d3566` head. ## What This Changes

The branch gates direct bundled Google Gemini CLI provider/backend registration behind `OPENCLAW_ENABLE_GOOGLE_GEMINI_CLI_HARNESS`, preserves setup-registry backend resolution, updates runtime-alias logic and Google docs/metadata, and adds tests.

## Best Possible Solution

Either preserve shipped Gemini CLI runtime registration by default, or land an explicitly approved opt-in migration with setup-flow docs, upgrade behavior proof, and current-head real behavior proof.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 register `google-gemini-cli` directly by default, while the PR head only registers it when `OPENCLAW_ENABLE_GOOGLE_GEMINI_CLI_HARNESS` is enabled. I did not run tests because this was a read-only review.

## Solution Assessment

No, not as-is: the env gate is a plausible product direction, but the best fix needs maintainer-approved compatibility policy, setup docs, upgrade proof, and current-head proof. Preserving default registration is the safer implementation unless maintainers explicitly choose the opt-in migration.

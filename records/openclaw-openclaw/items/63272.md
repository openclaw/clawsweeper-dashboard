## Summary

Keep open: current main and v2026.6.11 still lack a `skills uninstall` CLI command, while ClawHub skill install/update still use workspace lockfile state that manual deletion cannot clean. Closed related PRs are unmerged, so this remains the canonical tracker pending maintainer product direction for the destructive command semantics.

## What This Changes

Add `openclaw skills uninstall <slug>` to remove a ClawHub-installed skill directory and its `.clawhub/lock.json` entry from the selected skills workspace.

## Best Possible Solution

Keep this as the canonical CLI uninstall design tracker, settle the destructive behavior contract, then land one narrow CLI/lifecycle/docs/test implementation using the existing safe skill-dir resolver and lockfile helpers.

Question: Should OpenClaw add a destructive `openclaw skills uninstall <slug>` command for ClawHub-tracked workspace/global skills, and what should it do for manual or non-ClawHub skill directories?

Rationale: The missing command is real, but deletion behavior and non-ClawHub handling are product/security choices that should not be inferred by automation after several unmerged attempts chose different surfaces.

Likely owner: steipete

Owner reason: The native ClawHub install/update code and current skills lifecycle ownership history point here for the product-boundary decision.

Owner confidence: high

Options:

- **Approve narrow CLI uninstall (recommended):** Land a focused CLI/lifecycle implementation that removes the safe-resolved ClawHub skill directory and lockfile entry, with prompt, dry-run, JSON, and explicit manual-skill behavior.
- **Gateway-first lifecycle:** Defer the CLI command until maintainers define a shared Gateway or lifecycle API that both CLI and dashboard surfaces can reuse.
- **Do not add core uninstall yet:** Keep manual removal and docs as the supported path until ClawHub skill lifecycle ownership is redesigned more broadly.

## Reproduction Assessment

Yes. Source inspection shows ClawHub install writes origin and lockfile metadata, `skills update --all` consumes tracked lockfile slugs, and the current CLI/docs expose no uninstall command to remove both pieces of state.

## Solution Assessment

Unclear until maintainers decide the destructive command contract. A narrow CLI command built on existing lifecycle helpers is the best apparent implementation shape, but manual-skill and workspace/global semantics need owner approval first.

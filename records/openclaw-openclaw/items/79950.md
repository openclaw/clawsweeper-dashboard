## What This Changes

Ensure asynchronous `sessions_send` completions reach a Telegram-bound requester exactly once without exposing internal wrappers or changing the requester’s delivery route.

## Best Possible Solution

Create one canonical exactly-once completion path keyed by the delegated run: carry the requester’s prepared Telegram delivery facts from dispatch, keep inter-session envelopes internal, prevent reverse `sessions_send` during the routed turn, and deduplicate the final announce before external delivery.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For `sessions_send(..., timeoutSeconds: 0)`, should OpenClaw automatically deliver exactly one final completion to the requester’s bound external channel, or should fire-and-forget results remain internal unless the caller explicitly relays them?

Rationale: The current reply-back and announce lifecycle intentionally supports agent coordination, but the reported duplicate/lost Telegram behavior shows that the external-delivery ownership is ambiguous; code alone cannot safely choose which path owns the user-visible completion.

Likely owner: vincentkoc

Owner reason: Recent history most strongly connects this contributor to the shared session-routing and channel-delivery boundary where the contract must be enforced.

Owner confidence: medium

Options:

- **Exactly-once automatic announce (recommended):** Make the A2A lifecycle own one deduplicated final delivery to the requester’s preserved channel/thread while keeping internal wrappers transcript-only.
- **Internal fire-and-forget only:** Treat timeout-zero sends as internal dispatch and require the requester agent or an explicit message action to produce any user-visible result.
- **Separate explicit mode:** Preserve current behavior temporarily and add a clearly named delivery mode after defining compatibility and migration semantics.

No, not yet with high confidence on current main. The issue supplies a focused timeout-zero Telegram path and a recent matching report, but a controlled current-main run with delivery and transcript evidence is still missing.

## Solution Assessment

No, disabling the ping-pong loop alone is not the best complete fix. The maintainable solution must define one owner for external completion delivery and jointly cover route preservation, wrapper suppression, reverse-call prevention, and run-level deduplication.

## Summary

Keep open: current main and the latest release still lack the requested model-facing browser Network/CDP interception action. Existing code provides passive request listing and bounded response-body capture through lower browser-control/CLI routes, but adding active request interception is a new security-sensitive browser capability that needs maintainer product and security design.

## What This Changes

Request to expose CDP Network-domain request capture and interception through the browser tool so agents can discover SPA API requests beyond page-side fetch hooks.

## Best Possible Solution

Design this as a browser-plugin network inspection capability with explicit sensitive-data policy, profile capability rules, and wrapped/redacted model-facing output, reusing `/requests` and `/response/body` where they fit.

## Reproduction Assessment

Yes. Source inspection reproduces the gap: the model-facing browser schema and act-kind union do not expose network, requests, responsebody, or intercept actions, while lower control routes only provide passive request listing and bounded response-body capture.

## Solution Assessment

No, not as proposed yet. A raw browser act kind=network surface should wait for a maintainer-designed security boundary and profile capability matrix rather than directly exposing CDP Network interception to agents.

## Risks / Open Questions

- A model-facing Network interception API can expose cookies, authorization headers, tokens, private API endpoints, and response bodies unless redaction, permissions, profile restrictions, and output wrapping are designed first.

## Summary

Keep open: current main and v2026.6.11 still lack a model-facing browser Network/CDP interception action. Lower browser-control routes can list observed requests and fetch bounded response bodies, but exposing that to models, especially active interception, remains a security-sensitive product decision.

## What This Changes

Request to add browser-tool access to CDP Network request inspection and interception for SPA/API debugging.

## Best Possible Solution

Design this in the browser plugin as an explicit network diagnostics capability: start with redacted passive request listing and bounded response-body access for the model-facing tool, then decide active interception or mutation only after a maintainer-approved security policy.

Options:

- **Ship passive redacted diagnostics first (recommended):** Expose request listing and bounded response-body retrieval through the browser tool with redaction, profile support, output wrapping, and focused tests before considering active interception.
- **Allow active interception with explicit policy:** Add request interception or mutation only after maintainers define permissions, opt-in behavior, profile limits, and security review requirements.
- **Keep network inspection off model tools:** Leave network inspection on CLI/control/API or external workflows if model-facing access is judged too risky.

## Reproduction Assessment

Yes for the requested-capability gap, not as a runtime bug. Source inspection shows the model-facing browser schema and act dispatcher lack network/intercept actions while lower routes only expose passive request listing and bounded response-body capture.

## Solution Assessment

No, not as the raw proposed `browser act kind=network` API yet. The better path is a browser-plugin capability with explicit redaction, permission, profile-support, and security-boundary design before active interception is considered.

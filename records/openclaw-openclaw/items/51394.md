## Summary

Keep open: current main and v2026.6.11 still do not expose a model-facing browser Network/CDP interception action. The lower browser control server has passive request listing and bounded response-body routes, but the requested model-facing API and active interception capability remain a security-sensitive product decision.

## What This Changes

Request to expose CDP Network-domain request capture and interception through the browser tool for SPA API discovery and debugging.

## Best Possible Solution

Design this inside the browser plugin as an explicit network diagnostics capability, starting with redacted passive request listing and bounded response-body access, and gate any active interception or mutation behind maintainer-approved security policy and profile support.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose model-facing browser network inspection/interception, and if so should the first supported contract be passive redacted diagnostics or active request interception?

Rationale: The source gap is clear, but the permanent contract controls sensitive authenticated browser traffic and cannot be safely chosen by automation.

Likely owner: steipete

Owner reason: He has the clearest history on the browser plugin schema, runtime ownership split, and model-facing browser tool surface.

Owner confidence: high

Options:

- **Ship passive redacted diagnostics first (recommended):** Expose request listing and bounded response-body retrieval through the browser tool with redaction, profile support, output wrapping, and tests before considering active interception.
- **Allow active interception with explicit policy:** Add request interception or mutation only after maintainers define permissions, opt-in behavior, profile limits, and security review requirements.
- **Do not expose this to models:** Keep network inspection on lower control/CLI surfaces or external workflows if model-facing access is judged too risky.

## Reproduction Assessment

Yes for the requested-capability gap, not as a runtime bug. Source inspection shows the current model-facing browser tool schema and dispatcher lack a network/intercept action while lower routes only expose passive request listing and bounded response-body capture.

## Solution Assessment

No, not as the raw proposed `browser act kind=network` API yet. The safer path is a maintainer-designed browser-plugin capability with explicit redaction, permissions, profile support, and security boundaries.

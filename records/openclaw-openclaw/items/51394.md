## Summary

Keep open: current main and v2026.6.11 still lack a model-facing browser action for CDP Network request interception, while existing browser control and CLI paths only expose passive request listing and bounded response-body capture. This remains a new security-sensitive browser capability that needs maintainer product and security design before implementation.

## What This Changes

Expose browser-tool CDP Network capabilities so agents can capture, inspect, and potentially intercept request/response traffic during browser automation.

## Best Possible Solution

Design this as a browser-plugin network inspection capability with an explicit sensitive-data policy, profile capability matrix, permission/redaction rules, wrapped model-facing output, and reuse of the existing /requests and /response/body paths where they fit.

## Reproduction Assessment

Yes. Source inspection reproduces the gap: the model-facing browser tool schema and act-kind union do not expose network, requests, responsebody, or intercept actions, while lower control routes only expose passive request listing and bounded response-body capture.

## Solution Assessment

No, not as proposed yet. A raw browser act kind=network surface should wait for a maintainer-designed security boundary and profile capability matrix rather than directly exposing CDP Network interception to agents.

## Risks / Open Questions

- A model-facing network interception API can expose cookies, authorization headers, tokens, private endpoints, request bodies, and response bodies unless redaction, permissions, profile restrictions, and output wrapping are designed first.
- Active interception or request mutation is stronger than the existing passive request listing and bounded response-body capture paths, so it changes the browser tool security boundary.
- Managed, raw/remote CDP, sandbox, node-hosted, and existing-session profiles may need different support levels; a single action shape could overexpose data or fail inconsistently.

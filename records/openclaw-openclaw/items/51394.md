## Summary

Keep open: current main and v2026.6.11 still lack a model-facing browser Network/CDP interception action, and the overlapping Chrome MCP diagnostics PR is broad, unmerged, and only partially covers passive request listing rather than the full request-interception capability.

## What This Changes

The issue requests browser tool actions for CDP Network enablement, captured-request listing, and URL-pattern request interception during browser automation.

## Best Possible Solution

Design this as a browser-plugin network inspection capability with explicit sensitive-data policy, profile capability matrix, permission/redaction rules, wrapped model-facing output, and reuse of existing `/requests` and `/response/body` paths where they fit.

## Reproduction Assessment

Yes for the requested-capability gap, not as a runtime bug. Source inspection shows the current model-facing browser tool schema and dispatcher lack the requested network/intercept action while lower browser routes only expose passive request listing and bounded response-body capture.

## Solution Assessment

No, not as the proposed raw `browser act kind=network` surface yet. The safer direction is a maintainer-designed browser plugin capability with explicit redaction, permissions, profile support, and security boundaries.

## Risks / Open Questions

- A model-facing network interception API can expose cookies, authorization headers, tokens, private endpoints, request bodies, and response bodies unless redaction, permissions, profile restrictions, and output wrapping are designed first.

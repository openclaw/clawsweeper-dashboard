## Summary

Keep open: current main and the latest release still lack a model-facing browser-tool action for CDP Network request interception. Existing browser control and CLI paths provide passive request listing and bounded response-body capture, but exposing interception to agents is a new security-sensitive browser capability that needs maintainer product and security design.

## What This Changes

The issue requests a browser-tool API that exposes CDP Network-domain capabilities for request interception, captured request listing, and SPA endpoint discovery.

## Best Possible Solution

Design this as a browser-plugin network inspection capability with explicit sensitive-data policy, profile capability rules, and wrapped/redacted model-facing output, reusing the existing `/requests` and `/response/body` paths where they fit.

## Reproduction Assessment

Yes. Source inspection reproduces the capability gap: the model-facing browser tool schema and dispatcher do not include network/request/intercept actions, while lower CLI/control routes only expose read-only request listing and response-body capture.

## Solution Assessment

No, not as proposed yet. A `browser act kind=network` API should wait for a maintainer-designed security boundary and profile capability matrix rather than directly exposing CDP Network interception to agents.

## Risks / Open Questions

- A model-facing Network interception API can expose cookies, authorization headers, tokens, private endpoints, and response bodies unless redaction, permissions, profile restrictions, and output wrapping are designed first.
- Active interception or request mutation is stronger than the current read-only request listing and response-body capture paths, so it changes the browser tool security boundary.
- Managed, raw/remote CDP, sandbox, node-hosted, and existing-session profiles may need different support levels; a single action shape could overexpose data or fail inconsistently.

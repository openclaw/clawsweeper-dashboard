## Summary

Keep open: current main and v2026.6.11 still do not expose the requested model-facing browser Network/CDP interception API. Existing lower-level browser routes can passively list recent requests and wait for a bounded response body, and https://github.com/openclaw/openclaw/pull/85993 partially overlaps by adding a `requests` action, but that PR is open, conflicting, and still does not settle active interception or the security boundary.

## What This Changes

The issue requests a model-facing browser/CDP Network domain API for enabling, listing, and intercepting network requests during browser automation.

## Best Possible Solution

Design this as a browser-plugin network inspection capability with explicit sensitive-data policy, profile capability matrix, permission/redaction rules, wrapped model-facing output, and a clear decision on whether active interception is in scope beyond passive request diagnostics.

- **Defer behind related Browser work:** Wait for https://github.com/openclaw/openclaw/pull/85993 to be resolved or split, then decide what remaining Network-domain capability still belongs in the Browser plugin.

## Solution Assessment

Unclear as proposed: a raw `browser act kind=network` API is only a possible shape. The safer solution is a maintainer-designed Browser plugin capability that reuses existing request/response infrastructure while defining redaction, permissions, profile support, and whether active interception is allowed.

## Summary

Keep open: current main and v2026.6.11 still do not expose a model-facing browser action for CDP Network request interception. The existing browser stack has passive request listing and bounded response-body capture, but active interception would be a new security-sensitive browser-plugin capability that needs maintainer product/security design.

## What This Changes

Request to expose CDP Network/request-interception actions in the browser tool so agents can capture and inspect SPA request/response traffic.

## Best Possible Solution

Design this inside the browser plugin as an explicit network inspection/interception capability with a maintainer-approved sensitive-data policy, profile capability matrix, redaction rules, wrapped outputs, and reuse of existing /requests and /response/body paths where appropriate.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes: source inspection shows BrowserToolSchema and BrowserActRequest do not accept the requested network/intercept actions, while lower-level routes only provide passive listing and bounded response-body capture.

## Solution Assessment

Is this the best way to solve the issue? Not as proposed yet: exposing raw CDP Network interception directly to agents should wait for a maintainer-designed browser-plugin security boundary and profile support matrix.

## Risks / Open Questions

- A model-facing network interception API could expose cookies, authorization headers, tokens, private endpoints, request bodies, and response bodies unless permissions, redaction, profile restrictions, and output wrapping are designed first.
- Active request interception or mutation is stronger than the existing passive /requests and bounded /response/body paths, so it changes the browser tool security boundary.
- Managed, raw/remote CDP, sandbox, node-hosted, and existing-session profiles may need different support levels; a single action shape could overexpose data or fail inconsistently.

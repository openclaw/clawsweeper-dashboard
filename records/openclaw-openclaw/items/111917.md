## Summary

Keep this PR open: the clearing behavior is well-scoped, but the shared agent-tool payload schema also permits `timeoutSeconds: null` for cron creation, contradicting the intended update-only contract and producing a late validation failure for an accepted tool call. Real end-to-end behavior proof is also still needed before merge.

## What This Changes

The PR adds `openclaw cron edit --clear-timeout-seconds`, nullable timeout patch support, and merge logic that removes an existing per-job payload timeout override.

## Best Possible Solution

Keep `null` as an update-only clear marker by parameterizing or splitting the agent-tool payload schemas, then show a redacted real cron create → clear-timeout edit → get/readback transcript against a running Gateway.

Yes, from source: submit a cron-tool `add` request with `job.payload.timeoutSeconds: null`; the changed shared tool schema accepts it even though the add validator is intended to reject null. A live Gateway run was not provided.

## Solution Assessment

No. The CLI and Gateway update path are a maintainable way to clear the override, but the agent tool must use a separate non-nullable create schema so it does not advertise or accept an invalid add payload.

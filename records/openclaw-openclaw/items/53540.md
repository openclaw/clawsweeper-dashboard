## Label Justifications

- `P1`: The report describes a broken agent/subagent workflow where real model turns repeatedly fail before producing the requested tool call or final response.
- `impact:message-loss`: The failed turn produces no `Write` tool call, output file, or final assistant response, so the user-visible result is lost.
- `impact:session-state`: The failure happens after embedded agent/subagent work has accumulated context, leaving progress uncommitted and the run in an error state.

## Summary

Keep this open: current main still has a positive embedded-runner idle watchdog for cloud provider streams, and OpenRouter’s Anthropic route remains OpenAI-compatible rather than native Anthropic fine-grained tool streaming. Main has useful mitigations, especially explicit provider `timeoutSeconds`, but I did not find source, test, merged-PR, or live-provider proof that the reported large OpenRouter Anthropic tool-argument path now succeeds by default.

## What This Changes

The issue asks OpenClaw to stop losing embedded runner turns when a slow provider takes longer than the underlying request timeout to generate large tool-call parameters.

## Best Possible Solution

Keep this as the canonical tracker until maintainers choose and prove a provider-safe fix: either supported OpenRouter tool-argument streaming, a deliberate timeout policy for silent large arguments, or a tool-loop strategy that avoids single huge `Write` arguments.

## Reproduction Assessment

Yes at source level, but not as a fresh live current-main repro: the embedded runner still aborts provider silence between chunks, and OpenRouter’s OpenAI-compatible path only advances when upstream chunks arrive. A high-confidence live repro still needs OpenRouter Anthropic credentials and the large `Write` scenario from the report.

## Solution Assessment

Unclear: the issue is valid, but the best permanent fix is a maintainer policy choice between timeout behavior, provider-specific tool-argument streaming, or changing how agents create large files. The current `timeoutSeconds` knob is a mitigation, not enough evidence to close this as solved.

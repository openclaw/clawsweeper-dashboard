## Summary

Keep open: the availability-hardening goal is valid, but the patch is not merge-ready because the non-streaming fallback still allocates through `arrayBuffer()` when `content-length` is missing or understated, and current main already has the public declared-length fast path before this helper is called.

## What This Changes

The PR exports `readCapturedResponseBodyBounded`, adds a Content-Length precheck in its non-streaming fallback, and adds focused proxy-capture runtime tests.

## Best Possible Solution

Keep the existing `captureHttpExchange` public fast path, and if the helper needs its own bounded contract, make the non-streaming fallback fail closed without whole-body allocation and prove that exact branch with a Response-like clone.

## Solution Assessment

No. The patch is a plausible partial mitigation, but the best fix is to avoid whole-body allocation whenever the fallback cannot stream under the cap, aligned with the existing fail-closed bounded-reader pattern.

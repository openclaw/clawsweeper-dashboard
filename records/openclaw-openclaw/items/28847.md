## Summary

Keep open: current main covers flat API-key rotation and same-provider auth-profile cooldowns, but it still does not model shared Gemini project/quota buckets that can be cooled as a group. The linked sidecar and related provider-pool issues are useful evidence, but the remaining work is a compatibility-sensitive provider/auth product decision.

## What This Changes

Add provider API-key pools with bucket/quota-group-aware cooldown and backoff for Gemini project-scoped 429s so OpenClaw avoids retrying keys that share the same quota.

## Best Possible Solution

Design an opt-in provider/auth pool model that groups credentials by quota bucket or project, applies bucket-wide cooldowns for new requests without changing single-key defaults, and ships with docs, focused tests, and any needed doctor/config migration.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: current main has flat key/profile cooldown paths but no bucket metadata or bucket-wide cooldown, though I did not replay a live exhausted Gemini project.

## Solution Assessment

Is this the best way to solve the issue? Unclear as proposed: the sidecar is useful evidence, but the maintainable fix should be a maintainer-approved core/provider-auth design rather than log tailing plus auth-state rewrites.

## Summary

Keep open: current main now implements flat Gemini API-key rotation for official Google LLM requests, but neither current source nor docs define the requested Gemini project/quota-bucket identity or bucket-wide cooldown. The reporter's Keymanager sidecar and the linked fork are useful workaround evidence, while the open provider-pool, quota-circuit-breaker, and same-provider rotation items only partially overlap this narrower bucket-aware key-pool request.

## What This Changes

The issue requests provider key pools with quota-bucket-aware cooldown/backoff for 429 and RESOURCE_EXHAUSTED errors, especially Gemini project-level quota buckets.

## Best Possible Solution

Define an additive provider-owned quota-scope identity on key/auth candidates, route 429 cooldown through that scope, preserve current defaults, and reconcile the API shape with broader provider-profile routing before implementation.

## Reproduction Assessment

Yes at source level: current main exposes flat key rotation and per-profile/model cooldowns but has no shared quota-bucket identity. I did not run a live exhausted Gemini project in this read-only review.

## Solution Assessment

Partly: native bucket-aware behavior targets the right gap, but the sidecar log-watcher/auth-file rewrite should remain a workaround rather than the core design. The best fix needs a typed provider/auth quota identity and maintainer-approved config or plugin API shape.

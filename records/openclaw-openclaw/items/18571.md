## Label Justifications

- `P2`: The request affects plugin guardrail and session correlation correctness, but it is an additive public API/product improvement rather than an active core outage.
- `impact:session-state`: The requested hook data is needed to correlate outbound messages with the correct same-turn run/session state under concurrent or multi-path delivery.
- `impact:security`: The requested pre-send verification evidence is security-sensitive because it would let plugins inspect or block outbound claims before users act on them.

## Summary

Keep open: current main and the latest release still only partially cover the request. `message_sending` can rewrite/cancel and now receives `sessionKey`, and `reply_payload_sending` has `runId` plus usage state, but no outbound pre-send hook exposes outbound `runId` together with bounded same-turn transcript/tool-call/result evidence for deterministic verification.

## What This Changes

Request an outbound pre-send plugin hook/context that can read outbound text, correlate it to session/run state, inspect tool-call/result history, and annotate or block delivery for deterministic verification.

## Best Possible Solution

Define a maintainer-approved additive hook contract for outbound run identity plus redacted, bounded same-turn verification evidence, then wire shared outbound and direct-reply paths with docs and focused regression tests.

Rationale: The remaining work changes public plugin API semantics and can expose sensitive session/tool data before delivery, so automation cannot safely choose field shape, redaction, permissions, or hook ownership without maintainer intent.

Owner confidence: high

Options:

- **Add bounded evidence contract (recommended):** Expose run identity plus capped, redacted same-turn verification evidence on the chosen pre-send hook and document the permission/security model.
- **Land identity only first:** Add outbound runId/message identity now but leave deterministic evidence for a later plugin API design.
- **Treat payload hook as sufficient:** Declare `reply_payload_sending` the supported path, accepting that plugins still lack first-class tool/result evidence.

## Reproduction Assessment

Yes, at source level: current `message_sending` has sessionKey but no outbound runId or bounded same-turn verification evidence, while `reply_payload_sending` has runId but only exposes payload and usage state.

## Solution Assessment

Unclear until product/security review. Adding run identity is plausible, but transcript/tool-call evidence needs a bounded, redacted, permission-aware plugin SDK contract rather than an ad hoc metadata dump.

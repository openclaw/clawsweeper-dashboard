## Summary

Keep open: current main partially covers this with outbound `sessionKey` and `reply_payload_sending` runId/usage state, but no pre-send hook exposes outbound runId together with bounded same-turn transcript/tool-call/result evidence for deterministic verification.

## What This Changes

Request to add a pre-send outbound hook context that exposes outbound content, session/run identity, and bounded tool-call/result evidence so plugins can annotate or block messages deterministically.

## Best Possible Solution

Define a maintainer-approved additive hook contract for outbound run identity plus redacted, bounded same-turn verification evidence, then wire shared outbound and direct-reply paths with docs and focused regression tests.

Rationale: The remaining work changes public plugin API semantics and can expose sensitive session/tool data before delivery, so automation cannot safely choose field shape, redaction, permissions, or hook ownership without maintainer intent.

Owner confidence: high

Options:

- **Add bounded evidence contract (recommended):** Expose run identity plus capped, redacted same-turn verification evidence on the chosen pre-send hook and document the permission/security model.
- **Land identity only first:** Add outbound runId/message identity now while leaving deterministic evidence for a later plugin API design.
- **Treat payload hook as sufficient:** Close the request as covered by `reply_payload_sending`, accepting that plugins still lack first-class tool/result evidence.

## Reproduction Assessment

Yes, source-reproducible: current main's `message_sending` hook has sessionKey but no outbound runId or bounded same-turn verification evidence, while `reply_payload_sending` has runId but only exposes payload and usage state.

## Solution Assessment

Unclear until product/security review. Adding run identity is plausible, but transcript/tool-call evidence needs a bounded, redacted, permission-aware plugin SDK contract rather than an ad hoc metadata dump.

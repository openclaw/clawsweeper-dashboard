## Label Justifications

- `P2`: The request affects plugin guardrail and session correlation correctness, but it is an additive public API/product improvement rather than an active core outage.
- `impact:session-state`: The requested hook data is needed to correlate outbound messages with the correct same-turn run/session state under concurrent or multi-path delivery.
- `impact:security`: The requested verification evidence is used for pre-send policy enforcement and could expose sensitive transcript or tool-result data if designed incorrectly.

## Summary

Keep open: current main and v2026.6.11 still only partially cover the request. `message_sending` can rewrite/cancel and receives `sessionKey` on shared outbound delivery, while `reply_payload_sending` has `runId` plus usage state on live dispatcher paths, but no outbound pre-send hook exposes outbound `runId` together with bounded transcript/tool-call/result evidence for deterministic verification.

## What This Changes

Request an outbound pre-send hook contract that can inspect outbound text, correlate session/run identity, access bounded tool-call evidence, and block or annotate delivery before send.

## Best Possible Solution

Define a maintainer-approved additive hook contract for outbound run identity plus redacted, bounded same-turn verification evidence, then wire shared outbound and direct-reply paths with docs and focused regression tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose same-turn transcript/tool-call/result evidence to outbound pre-send plugin hooks, and what bounded, permissioned public SDK shape should own it?

Rationale: The remaining work changes public plugin API semantics and can expose sensitive session/tool data before delivery, so automation cannot safely choose field shape, redaction, permissions, or hook ownership without maintainer intent.

Likely owner: steipete

Owner reason: They are closest to the current hook contract wording, prior issue review, and product/security decision boundary for this surface.

Owner confidence: high

Options:

- **Add a bounded evidence contract (recommended):** Expose run identity plus capped, redacted same-turn verification evidence on the chosen pre-send hook and document the permission/security model.
- **Land identity only first:** Add outbound runId/message identity now but leave deterministic evidence for a later plugin API design.
- **Treat payload hook as sufficient:** Declare `reply_payload_sending` the supported surface and accept that plugins still lack first-class tool/result evidence on `message_sending`.

## Reproduction Assessment

Yes, at source level: current main's `message_sending` hook has sessionKey but no outbound runId or bounded same-turn verification evidence, while `reply_payload_sending` has runId but only exposes payload and usage state.

## Solution Assessment

Unclear until product/security review. Adding run identity is plausible, but the best fix for transcript/tool-call evidence needs a bounded, redacted, permission-aware Plugin SDK contract rather than an ad hoc metadata dump.

## Label Justifications

- `P2`: This is an additive plugin guardrail and correlation API request with bounded blast radius, not an active core outage.
- `impact:session-state`: The request is about correlating outbound messages with the correct same-turn run/session state under concurrent or multi-path delivery.
- `impact:security`: The requested pre-send evidence supports policy enforcement but could expose sensitive transcript or tool-result data if designed incorrectly.

## Summary

Keep open: current main and v2026.6.11 still only partially satisfy the request. `message_sending` can rewrite/cancel and receives `sessionKey`, and `reply_payload_sending` carries `runId` plus usage state, but no outbound pre-send hook exposes outbound `runId` together with bounded same-turn transcript/tool-call/result evidence for deterministic verification.

## What This Changes

The issue requests a pre-send outbound hook that can read outbound text, correlate to session/run identity, inspect same-turn tool evidence, and annotate or block delivery.

## Best Possible Solution

Define a maintainer-approved additive plugin hook contract for outbound run identity plus redacted, bounded same-turn verification evidence, then wire shared outbound and direct-reply paths with docs and focused regression tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose same-turn transcript/tool-call/result evidence to outbound pre-send plugin hooks, and what bounded, permissioned public SDK shape should own it?

Rationale: The remaining work changes public plugin API semantics and can expose sensitive session/tool data before delivery, so automation cannot safely choose field shape, redaction, permissions, or hook ownership without maintainer intent.

Likely owner: steipete

Owner reason: steipete is closest to the prior issue review, adjacent hook contract work, and product/security boundary for this surface.

Owner confidence: high

Options:

- **Add bounded evidence contract (recommended):** Expose run identity plus capped, redacted same-turn verification evidence on the chosen pre-send hook and document the permission/security model.
- **Land identity only first:** Add outbound runId/message identity now and leave deterministic evidence for a later plugin API design.
- **Treat current hooks as sufficient:** Close the direction as covered by `reply_payload_sending`, accepting that plugins still lack first-class tool/result evidence.

## Reproduction Assessment

Yes, at source level: current main's `message_sending` hook has `sessionKey` but no outbound `runId` or bounded same-turn verification evidence, while `reply_payload_sending` has `runId` but only exposes payload and usage state.

## Solution Assessment

Unclear until product/security review. Adding run identity is plausible, but transcript/tool-call evidence needs a bounded, redacted, permission-aware plugin SDK contract rather than an ad hoc metadata dump.

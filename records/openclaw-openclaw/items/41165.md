## Label Justifications

- `P1`: The issue affects real Telegram plus heartbeat users with session contamination, misrouted wake handling, and reported swallowed heartbeat delivery.
- `impact:session-state`: The central failure is cross-contamination between heartbeat/main sessions and Telegram direct-message sessions.
- `impact:message-loss`: A confirming report says heartbeat delivery to Telegram was silently swallowed until session state was manually cleared.

## Summary

Keep open: current main still resolves forced wake/session keys before `heartbeat.session`, and Telegram DMs still default to the main session unless `session.dmScope` is configured. The linked fork PR is open but conflicting, and the same-repo Telegram isolation PR was closed unmerged, so there is no landed canonical fix to close against.

## What This Changes

The issue reports Telegram DM and heartbeat/session routing cross-contamination where direct-message traffic or event-triggered heartbeat work can reuse the wrong session.

## Best Possible Solution

Land a maintainer-approved fix that makes explicit `heartbeat.session` win over event-origin sessions for wake-triggered runs, then decide whether Telegram DMs should default to isolated sessions or remain controlled by `session.dmScope`, with regression coverage for both paths.

## Reproduction Assessment

Yes, source inspection gives a high-confidence path: event wakes pass a session key into `runHeartbeatOnce`, and `resolveHeartbeatSession()` resolves that forced key before `heartbeat.session`. I did not run a live Telegram/heartbeat repro in this read-only review.

## Solution Assessment

No, closing now is not the best way to solve the issue. The open fork PR is conflicting and the Telegram default routing part needs an explicit maintainer compatibility decision because current docs intentionally default DMs to the main session unless `session.dmScope` is changed.

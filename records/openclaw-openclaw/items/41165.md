## Label Justifications

- `P1`: The issue affects real Telegram plus heartbeat users with session contamination, token waste, and reported swallowed heartbeat delivery.
- `impact:session-state`: The central failure is cross-contamination between heartbeat/main sessions and Telegram direct-message sessions.

## Summary

Keep open: current main still resolves event-provided heartbeat wake session keys before an explicit `heartbeat.session`, and Telegram DMs still intentionally default to the main session unless `session.dmScope` isolates them. A linked implementation candidate exists, but it is an open conflicting fork PR, so there is no landed canonical fix to close against.

## What This Changes

The issue requests stricter isolation between Telegram DMs, heartbeat sessions, and event-triggered heartbeats to prevent session pollution and missed or misrouted heartbeat replies.

## Best Possible Solution

Land a maintainer-approved fix that makes explicit `heartbeat.session` win for event-triggered wakes and handles pending system events without cross-session pollution, then decide Telegram DM default isolation separately with docs and regression coverage.

- **Defer to heartbeat entries:** Hold this behind native per-session heartbeat scheduling, which may be cleaner long term but leaves the current forced-session contamination path unresolved longer.

## Reproduction Assessment

Yes for a source-level repro: exec and node event wakes carry a session key into the heartbeat runner, and current `resolveHeartbeatSession()` resolves that forced key before `heartbeat.session`. I did not run a live Telegram heartbeat repro in this read-only review.

## Solution Assessment

No, closing now is not the best solution because current main still preserves the implicated heartbeat precedence and documented default DM behavior. The maintainable path is a heartbeat precedence fix plus a separate compatibility decision for Telegram DM defaults.

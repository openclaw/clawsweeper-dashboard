## Summary

Keep open: current main still routes native macOS Push-to-Talk through Apple Speech, while `tools.media.audio` is a separate Gateway/media-understanding path. The request remains a useful, narrower native PTT slice of https://github.com/openclaw/openclaw/issues/46661, but it needs maintainer product and security direction before implementation.

## What This Changes

Request to add a configurable speech-to-text backend boundary for native macOS Push-to-Talk while preserving Apple Speech as the default.

## Best Possible Solution

Design a narrow native PTT STT boundary that preserves Apple Speech as the default, starts with final-text batch mode, and reuses Gateway media/provider security contracts if maintainers choose that owner boundary.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should native macOS Push-to-Talk gain a batch STT backend seam, and should the first implementation bridge to Gateway `tools.media.audio` instead of adding a separate native HTTP or command backend?

Rationale: The missing capability is clear, but maintainers must choose product ownership, credential handling, private-network policy, fallback semantics, and overlay UX before a safe implementation can be scoped.

Likely owner: steipete

Owner confidence: high

Options:

- **Design Gateway-backed batch PTT seam (recommended):** Keep Apple Speech as the default and add a final-text batch backend that reuses existing media/provider request controls and explicit fallback policy.
- **Fold into broader native ASR design:** Track this as the macOS PTT slice of https://github.com/openclaw/openclaw/issues/46661 until maintainers choose a shared native/provider contract.
- **Defer native backend selection:** Keep native PTT on Apple Speech until a broader voice-input plan across PTT, Talk, wake-word, and mobile surfaces is ready.

## Reproduction Assessment

Yes for the current behavior by source inspection, though this is not a bug reproduction. Native macOS PTT constructs Apple Speech recognizer/request objects directly, and the settings/runtime paths show no configurable STT backend selector.

## Solution Assessment

Unclear until maintainers choose the product and security shape. A Gateway-backed batch bridge looks like the narrowest maintainable first slice, while a raw native HTTP or command setting would duplicate existing provider contracts.

- `impact:security`: The requested feature would route microphone audio and possibly authorization material to configurable local, LAN, command, or cloud STT infrastructure.

## Summary

Keep open: current main and v2026.6.11 still run native macOS Push-to-Talk through Apple Speech, while existing `tools.media.audio` and Talk transcription paths are separate Gateway/provider surfaces. The request remains useful, but it needs maintainer product and security design before implementation.

## What This Changes

The issue requests a configurable speech-to-text backend boundary for native macOS Push-to-Talk instead of always using Apple Speech.

## Best Possible Solution

Design a narrow native PTT STT boundary that preserves Apple Speech as the default, starts with final-text batch mode, and reuses existing Gateway media/provider security contracts where maintainers choose that owner boundary.

Yes for the current behavior by source inspection, though this is not a bug reproduction. Native macOS PTT constructs Apple Speech objects directly, and the settings/runtime paths show no configurable backend selector.

## Solution Assessment

Unclear until maintainers choose the product and security shape. A Gateway-backed batch bridge looks like the narrowest maintainable first slice, but a raw native HTTP or command setting would risk duplicating existing provider contracts.

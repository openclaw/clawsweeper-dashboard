## Summary

Keep open: current main and v2026.6.11 still route native macOS Push-to-Talk through Apple Speech before forwarding text, while `tools.media.audio` remains a separate media-understanding path. The request is valid, but it needs maintainer product/security/API direction before implementation.

## What This Changes

Request to let native macOS Push-to-Talk choose an STT backend such as Gateway `tools.media.audio` or a private/local ASR service instead of always using Apple Speech.

## Best Possible Solution

Add a maintainer-approved native PTT STT backend boundary that keeps Apple Speech as the default, reuses `tools.media.audio`/media-understanding for batch final-text transcription where appropriate, and defines credential, private-network, error, and fallback UX before implementation.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should macOS Push-to-Talk get a native batch STT backend seam now, and should that seam reuse Gateway `tools.media.audio` rather than adding a separate native custom-ASR endpoint setting?

Rationale: The source-level gap is real, but the implementation changes provider routing, credentials, microphone-audio egress, fallback behavior, and native/Gateway ownership, which require maintainer product and security intent.

Likely owner: steipete

Owner reason: He has the strongest native macOS voice feature-history signal and is already timeline-mentioned for this issue family.

Owner confidence: high

Options:

- **Design batch PTT seam first (recommended):** Add a macOS PTT-only batch backend boundary, preserve Apple Speech as default, and route opted-in final audio through the existing media-audio/provider contract with explicit security policy.
- **Fold into broader custom-ASR design:** Treat this as a narrow slice of https://github.com/openclaw/openclaw/issues/46661 and wait for a shared native ASR provider contract across native voice flows.
- **Defer native backend selection:** Keep native PTT on Apple Speech for now and rely on sidecars or media-understanding plugins until the security and UX requirements are clearer.

## Risks / Open Questions

- Fallback behavior is product-sensitive: silent fallback from local/private STT to Apple or cloud transcription could violate user privacy expectations, while fail-closed behavior could break the existing PTT flow.

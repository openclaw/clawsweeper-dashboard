## Summary

Keep this PR open, but it is not merge-ready: the new settlement callback consumes a global receipt-order FIFO even though QQ Bot processes different peers concurrently and can merge several source events into one turn, so a fast later completion can settle an older in-flight sequence and recreate the reconnect message-loss bug. The prior direct-slash-command finding was addressed, but the PR still needs a message-bound settlement design and real after-fix gateway proof.

## What This Changes

The branch introduces a QQ Bot RESUME sequence watermark and hooks queue completion into it so reconnects replay queued or in-flight inbound events.

## Best Possible Solution

Bind every registered gateway sequence to the exact queued event or source-event set, settle that binding on every terminal path (normal queue, merged group turn, urgent execution, eviction, and queue clear), then provide redacted live reconnect evidence showing the withheld sequence is replayed.

Yes, from source: deliver sequence 2 to a blocked peer, then sequence 3 to a different fast peer; completion of sequence 3 reaches the shared FIFO first and settles sequence 2. No. The watermark idea is viable, but a global receipt-order FIFO is not the best fix because current QQ Bot queue drains run concurrently per peer and group messages can merge; sequence ownership must travel with the dispatched message(s).

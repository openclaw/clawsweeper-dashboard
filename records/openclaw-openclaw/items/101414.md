## Summary

Keep this PR open: the reported fallback gap remains on current `main`, and the contributor supplied convincing runtime proof, but the new `isSchemaErrorMessage` exclusion incorrectly treats failover reason and runtime diagnostic kind as mutually exclusive. Preserve `providerRuntimeFailureKind: "schema"` while independently returning failover reason `format`, then obtain shared fallback-owner confirmation for the intentionally broader provider-routing behavior.

## What This Changes

The PR classifies structured provider `invalid_request_error` payloads as format failures, admits returned format-error payloads into model fallback, and adds classifier, formatter, result-level, and fallback integration coverage.

## Best Possible Solution

Keep dual classification: structured invalid-request bodies should yield failover reason `format` while retaining `schema` or `replay_invalid` runtime diagnostics as applicable, with focused tests proving raw-message, structured-signal, returned-payload, and fallback-chain behavior.

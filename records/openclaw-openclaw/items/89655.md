## Summary

Keep open: current main and the latest release still carry the macOS service `NODE_USE_SYSTEM_CA=1` default and reachable Codex keychain/auth paths. Provider-scoped auth list/probe code now avoids keychain prompting in some read-only paths, but no merged fix or live macOS proof shows the reported `SecItemCopyMatching failed -50` and fresh-launch failure are resolved.

## What This Changes

The issue reports a macOS regression where `NODE_USE_SYSTEM_CA=1` makes legacy `openai-codex`/Codex keychain-backed auth reads fail and can destabilize fresh runtime launch.

## Best Possible Solution

Reproduce the failure on macOS, then implement a scoped auth/startup boundary so Codex keychain/status/runtime launch reads do not inherit the problematic CA mode while preserving the launchd TLS default.

Options:

- **Scope the auth/keychain boundary (recommended):** Keep the macOS service TLS default, prevent keychain/status/fresh launch auth reads from inheriting the problematic CA mode, and require live macOS proof.
- **Change the macOS service default:** Remove or narrow the global system-CA default, accepting the risk of re-opening launchd TLS failures unless separate TLS proof covers them.
- **Treat as legacy-provider migration only:** Close the `openai-codex` surface in favor of doctor migration to canonical `openai`, but only if maintainers decide fresh Codex keychain launch failures are outside current support.

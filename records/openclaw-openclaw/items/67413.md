## Label Justifications

- `P2`: This is a real multi-agent memory-core resource and configuration gap with bounded surface area and active candidate fixes, not an emergency core outage.
- `impact:session-state`: Dreaming writes memory and narrative artifacts across configured agent workspaces without an agent-level scope or opt-out boundary.
- `impact:crash-loop`: The reporter describes gateway OOM kills under a 6GB MemoryMax limit when all configured agents run the scheduled Dreaming sweep.

## Summary

Keep open. Current main and the latest release still expose only global memory-core Dreaming configuration, still resolve every configured agent workspace for a scheduled sweep, and the linked implementation paths are open rather than merged.

## What This Changes

The issue requests schema-backed per-agent Dreaming enablement and scheduling controls so multi-agent memory-core sweeps can be scoped or staggered instead of running every configured workspace on one global schedule.

## Best Possible Solution

Choose a durable, schema-backed Dreaming scoping API, land a reviewed implementation that aligns type/schema/docs/runtime/tests, and split per-agent schedule or stagger policy into a narrower follow-up if it is not part of the first accepted contract.

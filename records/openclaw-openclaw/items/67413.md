## Label Justifications

- `P2`: The request addresses real multi-agent memory-core resource pressure and operator control, but it is a bounded feature/config decision rather than an emergency outage.
- `impact:session-state`: Dreaming writes and reports memory/session-derived artifacts across agent workspaces, so scoping changes affect agent memory state generation.
- `impact:crash-loop`: The reporter describes gateway OOM kills under a 6GB MemoryMax limit when all configured agents run the scheduled dreaming sweep.

## Summary

Keep open. Current main and the latest release still expose global-only memory-core dreaming config and still resolve every configured agent workspace for scheduled dreaming, while the two implementation candidates remain open rather than merged.

## What This Changes

Request per-agent memory-core dreaming controls so operators can disable, scope, or stagger dreaming instead of running one global sweep across every configured agent workspace.

## Best Possible Solution

Keep this issue open while maintainers choose the durable memory-core scoping API, then land the viable candidate or successor and split per-agent schedule/stagger/backoff behavior if it is not part of the first accepted contract.

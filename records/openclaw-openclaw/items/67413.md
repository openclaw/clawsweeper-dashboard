## Label Justifications

- `P2`: This is a normal-priority memory-core operator-control improvement with real multi-agent resource impact but a bounded affected surface.
- `impact:session-state`: Dreaming reads and writes per-agent memory and narrative artifacts, and the missing scope control affects which agent workspaces receive that state.
- `impact:crash-loop`: The reporter describes gateway OOM kills under a 6GB MemoryMax limit when all configured agents are swept by the scheduled dreaming job.

## Summary

Keep open. Current main and latest release still expose only global memory-core dreaming configuration, while the open candidate PRs are unmerged and the discussion now needs a maintainer choice between per-agent overrides, an agent allowlist, and scheduling/backoff scope.

## What This Changes

The issue requests per-agent memory-core dreaming controls so operators can disable or reschedule dreaming instead of running one global sweep over every configured agent workspace.

## Best Possible Solution

Land a documented, schema-backed scoped dreaming contract for memory-core, preferably the narrow allowlist or enabled/disabled control first, and split per-agent cron schedules or stagger/backoff policy into explicit follow-ups if maintainers do not want them in the first API.

## Label Justifications

- `P1`: Completed heavyweight relay processes can remain resident during a real Codex workflow, with reported process waves and host-level availability failures.
- `impact:crash-loop`: The issue concerns lingering CLI processes causing process-level resource exhaustion and reported macOS userspace-watchdog panics.

## Summary

Keep open. Current main still runs the hidden relay command through an ordinary action wrapper that only assigns `process.exitCode`; the earlier relay-deadline fix bounds unfinished work but does not guarantee termination after a handler has completed. The protected `maintainer` label also requires explicit maintainer handling.

## What This Changes

Make completed `openclaw hooks relay` one-shot processes exit after stdout and stderr drain, while preserving the relay handler’s exit status.

## Best Possible Solution

Run the relay action through the existing shared one-shot shutdown path after capturing its status, preserve stdout/stderr draining and non-zero error codes, and add a real child-process regression that injects a referenced handle for success, malformed-input, and timeout-result cases.

Required: false

## Reproduction Assessment

Yes at high confidence from the bounded published-release reproduction and current-main source path: a referenced Node handle can keep the process alive after the relay handler returns because only `process.exitCode` is assigned. This review did not execute the child-process reproduction against current main.

## Solution Assessment

Yes. Reusing the existing one-shot exit mechanism is narrower and more maintainable than adding another relay deadline or special-case forced exit, provided regression coverage verifies stream draining and exit-code preservation.

## Summary

This PR addresses a real Vydra configuration gap, but it still applies the configured request policy only to the initial submission; status polling continues without the resolved dispatcher policy. The previously raised blocker remains, and the PR body has no after-fix real behavior proof.

## What This Changes

The PR sanitizes `models.providers.vydra.request` and passes it to Vydra’s shared provider HTTP configuration resolver.

## Best Possible Solution

Carry the resolved request policy through Vydra’s same-origin job-status polling path, add a controlled regression proving submission and polling observe it, and keep generated-asset downloads separate unless their header and destination contract is explicitly approved.

## Summary

Keep open: current main deliberately rejects the local runtime-identity mechanism for remote clients, so the requested capability remains missing. The protected `maintainer` label and cross-machine authorization contract require explicit human ownership; likely related person: steipete, high confidence.

## What This Changes

Define device- or connection-bound authenticated agent, session, and turn provenance for remote Gateway calls so approvals can route using verified origin context.

## Best Possible Solution

Add one closed Gateway-authenticated caller context scoped to authorized device and agent/session state, derive routing facts server-side, ignore request-supplied identity, and validate forged targets, replay, reconnect, cross-device access, fail-closed delivery, and client version skew.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should remote agent-turn provenance be negotiated as server-authorized connection context or carried by a short-lived delegation credential bound to the authenticated device connection?

Rationale: Current device authentication proves device identity but does not define delegated authority for a particular agent, session, turn, or delivery route; replay and rollout semantics require explicit maintainer intent.

Likely owner: steipete

Owner reason: He introduced and recently maintained the local identity boundary, authored the linked security review, and currently owns the issue.

Owner confidence: high

Options:

- **Server-authorized connection context (recommended):** Negotiate allowed agent and session provenance on the authenticated connection and attach a normalized read-only context server-side to every request.
- **Connection-bound delegation credential:** Issue short-lived signed turn credentials with explicit audience, authority, expiry, nonce, replay, and reconnect rules.
- **Keep remote fail-closed:** Retain denial and no-route behavior until a broader remote identity design is approved while local and plugin SDK work proceeds separately.

## Reproduction Assessment

Yes from current source and regression tests: the agent helper refuses trusted caller identity for remote targets, and the Gateway explicitly rejects the local runtime identity token from remote clients. A live multi-host invocation should still be captured during implementation.

## Solution Assessment

Yes at the architectural level: server-derived authenticated caller context is the narrowest maintainable direction and avoids forgeable raw fields, silent session lookup, or sharing the host-local HMAC secret across machines. The precise delegation and rollout contract still requires maintainer approval.

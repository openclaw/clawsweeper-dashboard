## Label Justifications

- `P2`: The issue affects agent context correctness and operator ergonomics, but the remaining work is a bounded product/API design rather than an urgent outage.
- `impact:session-state`: Overly broad, stale, or unfiltered bootstrap context can make subagent, heartbeat, cron, and main sessions carry the wrong instructions or state.

## Summary

Keep open: current main still only has fixed bootstrap allowlists, hook-based extra files, heartbeat/subagent lightweight modes, and cache-stable timezone guidance; the requested public session-type selector, bootstrap command expansion, and general dynamic context contract remain unresolved.

## What This Changes

The issue requests deterministic dynamic bootstrap/context injection, configurable session-type filtering, and built-in current-time context for agent sessions.

## Best Possible Solution

Define one maintainer-approved bootstrap context contract that preserves cache and security defaults, supports deterministic session-scoped filtering, and either defers or explicitly sandboxes command expansion.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose a first-class bootstrap selector/session filtering contract, and should bootstrap command expansion be deferred, plugin-owned, or included behind a reviewed security boundary?

Rationale: The remaining work changes public config/API behavior and command-execution authority in session prompt context, so cleanup automation cannot safely choose the long-term product and security boundary.

Likely owner: steipete

Owner confidence: high

Options:

- **Narrow selector first (recommended):** Add a small maintained bootstrap selector or tier contract for session-scoped filtering and defer command expansion until a separate sandbox design is approved.
- **Plugin hook contract only:** Document and extend hook/plugin seams for dynamic context while keeping core bootstrap loading limited to safe built-in files.
- **Full dynamic command expansion:** Pursue bootstrap command expansion only with explicit sandboxing, provenance, opt-in behavior, docs, and focused security tests.

## Reproduction Assessment

Yes. Current source shows fixed allowlists and narrow lightweight modes but no public selector or bootstrap command expansion, and the issue discussion gives a concrete HEARTBEAT_OK subagent failure pattern.

## Solution Assessment

Unclear as filed. The direction is useful, but it bundles selector policy, command execution, and built-in time context; a smaller maintainer-approved selector contract is the safer first step.

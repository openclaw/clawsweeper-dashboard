## Summary

Keep open: current main and the latest release still do not infer the only enabled account when the message tool omits `accountId`, and https://github.com/openclaw/openclaw/pull/85671 remains open, conflicting, and unmerged as the active candidate fix.

## What This Changes

Request auto-selecting the sole enabled channel account for message-tool sends when `accountId` is omitted instead of falling back to a disabled default account.

## Best Possible Solution

Review, rebase, prove, and land or replace https://github.com/openclaw/openclaw/pull/85671 with a shared outbound account resolver after channel selection that preserves explicit/default/bound precedence, uses plugin config adapter hooks, documents zero/one/multiple enabled-account behavior, and includes real behavior proof.

- **Require Channel-Owned Fallback:** Ask for channel-owned behavior if maintainers do not want core to own this fallback policy across message channels.

## Reproduction Assessment

Yes, at source level: current main leaves `accountId` unset unless it is explicit, defaulted by the caller, or target-bound, and WhatsApp omitted-account sends then ask the default-account helper. I did not run a live WhatsApp or CLI send in this read-only review.

## Solution Assessment

Yes for the owner boundary if maintainers accept the behavior: a shared resolver after channel selection is more maintainable than a WhatsApp-only fallback. The remaining question is product policy for omitted-account fallback semantics.

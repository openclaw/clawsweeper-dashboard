## Summary

Keep open: current main and v2026.6.11 still do not infer the single enabled account when message-tool accountId is omitted, and the linked implementation PR is open, conflicting, and unmerged.

## What This Changes

The issue requests that outbound message sends without accountId choose the only enabled configured account instead of falling back to a disabled default account.

## Best Possible Solution

Review, land, or replace https://github.com/openclaw/openclaw/pull/85671 with a shared outbound account resolver that preserves explicit/default/bound precedence and documents zero, one, and multiple enabled-account behavior.

- **Require channel-owned fallback:** Ask for channel-owned behavior if maintainers do not want core to own this fallback policy across message channels.

Yes for the owner boundary, but it needs product acceptance: a shared resolver after channel selection is more maintainable than a WhatsApp-only fallback, while the compatibility policy belongs in maintainer review of the linked PR.

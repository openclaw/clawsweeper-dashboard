## Label Justifications

- `P2`: The request affects real multi-account proactive message delivery, but the blast radius is bounded to omitted-account outbound sends.
- `impact:message-loss`: The reported path can make outbound messages target a disabled default account or fail instead of reaching the only enabled account.

## Summary

Current main and the latest release still use the default-account path when the message tool omits `accountId`; the requested single-enabled-account inference remains unmerged, and https://github.com/openclaw/openclaw/pull/85671 is the active open implementation candidate.

## What This Changes

The issue asks the message tool to select the only enabled channel account when `accountId` is omitted instead of falling back to a disabled `default` account.

## Best Possible Solution

Land or replace a maintainer-approved shared outbound account resolver that preserves explicit/default/bound account precedence, selects exactly one enabled configured account when safe, and gives clear zero-or-multiple-account errors.

## Reproduction Assessment

Yes, at source level: current main leaves `accountId` unset unless it is explicit/default/bound, and the WhatsApp omitted-account path then asks the default-account helper. I did not run a live WhatsApp send in this read-only review.

## Solution Assessment

Yes for the owner boundary, but it still needs product approval: a shared resolver after channel selection uses existing channel adapter hooks and is safer than a WhatsApp-only fallback. The exact ambiguous-account and zero-account behavior should be settled in the linked PR before closing this issue.

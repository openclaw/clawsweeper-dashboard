## Label Justifications

- `P2`: The issue affects real multi-account proactive sends but is bounded to omitted account selection rather than a core outage.
- `impact:message-loss`: A proactive message can target a disabled or wrong account when `accountId` is omitted, so delivery may fail or be misrouted.

## Summary

Keep open: current main and the latest release still do not infer the only enabled account for omitted message-tool `accountId`, and the open linked implementation candidate is not merged yet.

## What This Changes

The issue requests that outbound message sends infer the only enabled configured account for the selected channel when `accountId` is omitted instead of falling back to a disabled `default` account.

## Best Possible Solution

Review, rebase, prove, and land or replace https://github.com/openclaw/openclaw/pull/85671 as a shared outbound account resolver that preserves explicit/default/bound account precedence and uses plugin config adapter hooks for enabled/configured account selection.

## Reproduction Assessment

Yes at source level: with a selected channel and no `accountId`, current main leaves the account unset unless it is explicit/default/bound, and WhatsApp then falls back to the default-account helper. I did not run a live WhatsApp send in this read-only review.

## Solution Assessment

Yes for the owner boundary, but it needs maintainer policy approval: a shared resolver after channel selection is narrower and cleaner than WhatsApp-only logic, while explicit/default/bound account precedence must remain first.

## Label Justifications

- `P2`: The issue affects real proactive sends in multi-account channel setups, but the affected surface is bounded and already has an open implementation candidate.
- `impact:message-loss`: The reported omitted-account path can target a disabled default account, causing proactive messages not to reach the intended enabled account.
- `impact:ux-friction`: Users must know and pass an internal account ID even when only one account is enabled for the selected channel.

## Summary

Keep open: current main and the latest release still leave omitted `accountId` unresolved before WhatsApp falls back to the default-account helper, and https://github.com/openclaw/openclaw/pull/85671 is the open closing PR for this work.

## What This Changes

Request that the outbound message tool infer the only enabled account for the selected channel when `accountId` is omitted instead of falling back to a disabled `default` account.

## Best Possible Solution

Land or replace the open implementation with a shared outbound account resolver after channel selection that preserves explicit/default/bound precedence, infers exactly one enabled configured account, and documents/tests ambiguous or missing account failures.

## Reproduction Assessment

Yes, at source level: current main leaves `accountId` unset unless it is explicit/default/bound, and the WhatsApp send path then falls back to the default-account helper. I did not run a live WhatsApp send in this read-only review.

## Solution Assessment

Yes for the owner boundary: a shared outbound resolver after channel selection is the maintainable fix, while a WhatsApp-only fallback would be too narrow. The exact fallback policy still needs maintainer acceptance through the linked PR review.

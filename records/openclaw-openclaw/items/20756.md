## Summary

Keep open: current main and v2026.6.11 still do not infer the only enabled account when the message tool omits `accountId`, and https://github.com/openclaw/openclaw/pull/85671 is the open, unmerged candidate fix.

## What This Changes

Request auto-selecting the single enabled channel account for message-tool sends when `accountId` is omitted instead of falling back to a disabled or unsuitable default account.

## Best Possible Solution

Review, land, or replace https://github.com/openclaw/openclaw/pull/85671 with a shared outbound account resolver after channel selection that preserves explicit/default/bound precedence, uses plugin config adapter hooks, documents zero/one/multiple enabled-account behavior, and includes real behavior proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should omitted message-tool `accountId` infer a single enabled configured account after explicit/default/bound precedence, or should OpenClaw continue requiring explicit `accountId` or `defaultAccount` when the configured default is disabled?

Rationale: The code boundary is clear, but the behavior changes fallback semantics for existing multi-account setups and can change whether sends auto-select an account or fail closed.

Likely owner: steipete

Owner reason: steipete already supplied the prior shared-resolver direction and has the strongest feature-history signal for the fallback policy decision.

Owner confidence: high

Options:

- **Accept Shared Resolver Policy (recommended):** Land or replace the linked PR with a shared resolver that preserves explicit/default/bound account IDs first, then selects an enabled configured default or exactly one enabled configured account with clear zero-or-multiple errors.
- **Keep Explicit Account Selection:** Keep current semantics and document that users must set `accountId` or `defaultAccount` when a multi-account channel's default account is disabled.
- **Require Channel-Owned Fallback:** Ask for channel-owned fallback behavior if maintainers do not want core to own this policy across message channels.

## Reproduction Assessment

Yes, at source level: current main leaves `accountId` unset unless it is explicit, caller-defaulted, or target-bound, and WhatsApp omitted-account sends then ask the default-account helper. I did not run a live WhatsApp or CLI send in this read-only review.

## Solution Assessment

Yes if maintainers accept the behavior: a shared resolver after channel selection is more maintainable than a WhatsApp-only fallback. The remaining blocker is product policy for omitted-account fallback semantics.

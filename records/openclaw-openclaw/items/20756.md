## Summary

Keep open: current main and the latest release still do not infer the only enabled account when `accountId` is omitted, and the open linked implementation PR is the active fix candidate with closing syntax.

## What This Changes

The issue requests that outbound message sends infer the only enabled account when `accountId` is omitted instead of falling back to a disabled `default` account.

## Best Possible Solution

Review and land or replace https://github.com/openclaw/openclaw/pull/85671 with a shared resolver that preserves explicit/default/bound precedence, infers exactly one enabled configured account, and documents/tests ambiguous or missing account failures.

## Reproduction Assessment

Yes, at source level: current main leaves `accountId` unset unless it is explicit/default/bound, and the WhatsApp send path then falls back to the default-account helper. I did not run a live WhatsApp send in this read-only review.

## Solution Assessment

Yes for the likely owner boundary, but it still needs maintainer product acceptance: a shared resolver after channel selection is better than a WhatsApp-only fallback because the plugin config adapter already exposes enabled/configured/default account state.

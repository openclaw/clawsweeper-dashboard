## Summary

Keep open: current main and the latest release still use explicit, configured-default, or bound account IDs only, while the linked implementation at https://github.com/openclaw/openclaw/pull/85671 is open, unmerged, and not a completed fix.

## What This Changes

The issue asks the message tool to infer the enabled default account, or the only enabled configured account, when `accountId` is omitted instead of falling through to a disabled `default` account.

## Best Possible Solution

Review, land, or replace https://github.com/openclaw/openclaw/pull/85671 with a shared outbound account resolver after channel selection that preserves explicit/default/bound precedence, uses plugin config adapter hooks, and documents zero, one, and multiple enabled-account behavior.

- **Keep explicit account selection:** Keep current semantics and document that users must set `accountId` or `defaultAccount` when the configured default account is disabled.
- **Require channel-owned fallback:** Ask for channel-owned behavior if maintainers do not want core to own this fallback policy across message channels.

## Reproduction Assessment

Yes, at source level: current main leaves `accountId` unset unless it is explicit, defaulted by the caller, or target-bound, and WhatsApp omitted-account sends then ask the default-account helper. I did not run a live WhatsApp or CLI send in this read-only review.

## Solution Assessment

Yes for the owner boundary if maintainers accept the behavior: a shared resolver after channel selection is more maintainable than a WhatsApp-only fallback. The remaining question is product policy for omitted-account fallback semantics.

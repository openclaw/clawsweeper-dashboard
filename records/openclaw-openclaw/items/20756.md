## Label Justifications

- `P2`: The issue affects bounded multi-account outbound sends and can cause proactive messages to miss the intended enabled account.
- `impact:message-loss`: The reported failure mode is an omitted-account send using a disabled default account so the intended proactive message is not delivered.

## Summary

Keep open: current main and the latest release still fall back to explicit/default/bound account IDs rather than auto-selecting the only enabled account, and the open closing PR is still the active implementation candidate rather than a merged fix.

## What This Changes

The issue requests that outbound message sends infer the only enabled configured account when `accountId` is omitted instead of falling back to a disabled `default` account.

## Best Possible Solution

Review, rebase, prove, and either land or replace https://github.com/openclaw/openclaw/pull/85671 as the canonical shared outbound resolver, with maintainer-approved behavior for zero or multiple enabled accounts.

## Reproduction Assessment

Yes at source level: current main only preserves explicit/default/bound account IDs, and WhatsApp omitted-account sends then resolve through the default helper. I did not run a live WhatsApp or CLI send in this read-only review.

## Solution Assessment

Yes for the likely owner boundary, but not yet finished: a shared resolver after channel selection using the plugin config adapter is the maintainable shape. The remaining decision is the compatibility policy for omitted-account ambiguity and the linked PR still needs proof/conflict resolution.

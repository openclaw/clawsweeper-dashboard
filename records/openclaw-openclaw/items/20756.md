- `impact:message-loss`: The reported omitted-account path can route through a disabled default account and leave proactive messages undelivered.

## Summary

Keep open: current main still lacks enabled-account inference for omitted message-tool `accountId`, and the open linked PR is the active candidate fix rather than a reason to close this issue before merge.

## What This Changes

The issue asks the outbound message tool to infer the sole enabled channel account when `accountId` is omitted instead of falling back to a disabled `default` account.

## Best Possible Solution

Land or replace the linked PR with a shared outbound account resolver after channel selection that preserves explicit/default/bound account precedence, uses plugin config adapter hooks, and documents zero, one, and multiple enabled-account behavior.

## Reproduction Assessment

Yes, at source level: current main leaves `accountId` unset unless it is explicit/default/bound, and WhatsApp omitted-account sends then resolve the default helper. I did not run a live WhatsApp or CLI send in this read-only review.

## Solution Assessment

Yes for the proposed owner boundary: a shared resolver after channel selection is narrower and more maintainable than a WhatsApp-only fallback. The exact fallback policy still needs maintainer acceptance through the linked PR before this issue closes.

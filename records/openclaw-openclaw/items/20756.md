## Label Justifications

- `impact:message-loss`: The reported failure mode is an omitted-account send targeting a disabled default account, so the intended message is not delivered.

## Summary

Keep open: current main and the latest release still leave omitted message-tool `accountId` unresolved, and the active linked implementation candidate at https://github.com/openclaw/openclaw/pull/85671 has not merged.

## What This Changes

The issue requests outbound message-account inference so an omitted `accountId` uses the only enabled configured account instead of falling back to a disabled `default` account.

## Best Possible Solution

Review, rebase, and land or replace https://github.com/openclaw/openclaw/pull/85671 with a shared resolver that preserves explicit/default/bound precedence, infers exactly one enabled configured account, and documents/tests ambiguous or missing account failures.

## Reproduction Assessment

Yes at source level: current main leaves `accountId` unset unless it is explicit/default/bound, and WhatsApp omitted-account sends then use the default helper. I did not run a live WhatsApp or CLI send in this read-only review.

## Solution Assessment

Yes for the owner boundary: a shared outbound resolver after channel selection is more maintainable than a WhatsApp-only fallback. The remaining question is product acceptance of the changed fallback semantics, which is why the linked PR needs maintainer review.

## Summary

Keep open: current main and v2026.6.11 still do not infer the only enabled account when the message tool omits `accountId`, and the linked implementation PR is open, conflicting, and unmerged.

## What This Changes

The issue asks the message tool to infer the only enabled configured channel account when `accountId` is omitted instead of falling back to a disabled `default` account.

## Best Possible Solution

Review, land, or replace https://github.com/openclaw/openclaw/pull/85671 with a shared outbound account resolver after channel selection that preserves explicit/default/bound precedence, uses plugin config adapter hooks, documents zero/one/multiple enabled-account behavior, and includes real behavior proof.

Yes, at source level: current main leaves `accountId` unset unless it is explicit, defaulted by the caller, or target-bound, and WhatsApp omitted-account sends then ask the default-account helper. I did not run a live WhatsApp or CLI send in this read-only review.

Yes for the owner boundary if maintainers accept the behavior: a shared resolver after channel selection is more maintainable than a WhatsApp-only fallback. The remaining question is product policy for omitted-account fallback semantics.

## Label Justifications

- `P2`: This is a bounded multi-account outbound message routing bug affecting proactive sends rather than a broad runtime outage.
- `impact:message-loss`: The reported fallback can route through a disabled default account and make proactive messages fail while the caller believes delivery succeeded.

## Summary

Keep open: current main and the latest release still do not infer the only enabled account for omitted message-tool accountId, and the open linked implementation candidate at https://github.com/openclaw/openclaw/pull/85671 should be reviewed before this issue closes.

## What This Changes

The issue requests that the outbound message tool infer the single enabled channel account when accountId is omitted instead of falling back to a disabled default account.

## Best Possible Solution

Review, repair if needed, and land or close https://github.com/openclaw/openclaw/pull/85671; the end state should be a shared post-channel-selection account resolver that preserves explicit/default/bound account precedence and handles zero, one, and multiple enabled accounts clearly.

## Reproduction Assessment

Yes, at source level: current main still carries no accountId unless it was explicit/default/bound, then WhatsApp omitted sends resolve the default account and can error on a disabled default listener. I did not run a live WhatsApp multi-account send.

## Solution Assessment

Yes in direction, but not complete yet: the maintainable solution is a generic resolver after channel selection using plugin config adapter hooks, and the linked PR is the current candidate. Maintainers still need to review compatibility and proof before the issue can close.

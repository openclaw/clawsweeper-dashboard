## Label Justifications

- `P2`: The issue affects proactive outbound message delivery in multi-account channel setups but is bounded to account selection behavior.
- `impact:message-loss`: The report describes omitted-account sends targeting a disabled default account, so messages can fail to reach the only enabled account.

## Summary

Keep open: current main and the latest release still do not infer the only enabled account when the message tool omits `accountId`, and https://github.com/openclaw/openclaw/pull/85671 is the active unmerged implementation candidate for this issue.

## What This Changes

The issue asks the message tool to infer the only enabled account when `accountId` is omitted instead of falling back to a disabled `default` account.

## Best Possible Solution

Review, repair, or replace https://github.com/openclaw/openclaw/pull/85671 with a shared outbound resolver that preserves explicit/default/bound precedence, infers exactly one enabled configured account, and documents/tests ambiguous or missing account failures.

## Reproduction Assessment

Yes, at source level: current main leaves `accountId` unset unless it is explicit/default/bound, and the WhatsApp send path then falls back to the default-account helper. I did not run a live WhatsApp send in this read-only review.

## Solution Assessment

Yes for the likely owner boundary, but not yet resolved: a shared outbound account resolver after channel selection is better than a WhatsApp-only fallback. The behavior still needs maintainer acceptance because it changes default fallback semantics, and the active PR has not merged.

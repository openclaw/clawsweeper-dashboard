## Summary

Keep open: current main and the latest release still do not infer the only enabled account when the message tool omits `accountId`, and https://github.com/openclaw/openclaw/pull/85671 is the open implementation candidate that uses closing syntax.

## What This Changes

Request that the message tool infer the only enabled configured account when `accountId` is omitted instead of falling through to a disabled default account.

## Best Possible Solution

Review, rebase, and land or replace https://github.com/openclaw/openclaw/pull/85671 with a shared outbound account resolver that preserves explicit/default/bound precedence, infers exactly one enabled configured account, and documents/tests ambiguous or missing account failures.

## Reproduction Assessment

Yes, at source level: current main leaves `accountId` unset unless it is explicit/default/bound, and WhatsApp omitted-account sends then use the default helper. I did not run a live WhatsApp send in this read-only review.

## Solution Assessment

Yes for the owner boundary, but it still needs maintainer acceptance: a shared resolver after channel selection is more maintainable than a WhatsApp-only fallback. The open implementation candidate must be rebased, proven, and reviewed before this issue can close.

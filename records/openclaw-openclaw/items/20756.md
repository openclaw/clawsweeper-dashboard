## Summary

Keep open: current main and latest release still do not infer the only enabled account when the message tool omits `accountId`, and https://github.com/openclaw/openclaw/pull/85671 is the active open implementation candidate with closing syntax.

## What This Changes

The issue requests that outbound message sending infer the single enabled configured account for a selected channel when `accountId` is omitted.

## Best Possible Solution

Review, rebase, and land or replace https://github.com/openclaw/openclaw/pull/85671 with a shared resolver that preserves explicit/default/bound precedence, infers exactly one enabled configured account, and documents/tests ambiguous or missing account failures.

## Reproduction Assessment

Yes, at source level: current main leaves `accountId` unset unless it is explicit/default/bound, and the WhatsApp send path then falls back to the default-account helper. I did not run a live WhatsApp send in this read-only review.

## Solution Assessment

Yes for the likely owner boundary: the best fix is a shared outbound account resolver after channel selection, not a WhatsApp-only fallback. The behavior still needs maintainer acceptance because it changes default fallback semantics.

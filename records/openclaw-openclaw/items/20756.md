## Label Justifications

- `P2`: The issue is a normal-priority outbound message-account selection improvement with a clear source path and limited channel/account blast radius.
- `impact:message-loss`: When omitted account selection falls through to a disabled default listener, proactive outbound messages can fail to reach the intended channel account.

## Summary

Keep open. Current `main` and the latest release still use explicit/default/bound account selection only; omitted WhatsApp account sends still fall through to the default-account helper, and the open implementation candidate is not merged yet.

## What This Changes

The issue requests that the outbound message tool infer the only enabled account for the selected channel when `accountId` is omitted instead of falling back to a disabled `default` account.

## Best Possible Solution

Land a mergeable, proven version of https://github.com/openclaw/openclaw/pull/85671 or an equivalent shared resolver that preserves explicit/default/bound accounts, then infers exactly one enabled configured account and documents the behavior.

## Reproduction Assessment

Yes, at source level. Current main leaves `accountId` unset unless it is explicit/default/bound, and WhatsApp omitted-account sends then use the default-account helper, so the reported disabled-default path is traceable without a live send.

## Solution Assessment

Yes, the right implementation shape is a shared resolver after channel selection rather than a WhatsApp-only fallback. The issue should stay open until the linked PR or an equivalent patch is mergeable, proven, and accepted with the compatibility semantics documented.

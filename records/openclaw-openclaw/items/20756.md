## Summary

Keep open: current main and the latest release still leave omitted message-tool `accountId` unresolved unless it is explicit, defaulted, or bound, and the active implementation candidate at https://github.com/openclaw/openclaw/pull/85671 is open, conflicting, and unmerged.

## What This Changes

The issue requests that omitted message-tool `accountId` select the only enabled configured account instead of falling through to a disabled default account.

## Best Possible Solution

Land or replace a narrow shared outbound resolver that preserves explicit/default/bound account precedence, infers exactly one enabled configured account, and documents/tests clear zero-or-multiple-account failures.

## Reproduction Assessment

Yes at source level: current main leaves `accountId` unset unless explicit/default/bound, and the WhatsApp send path then falls back to the default-account helper. I did not run a live WhatsApp send in this read-only review.

## Solution Assessment

Yes for the likely owner boundary: a shared resolver after channel selection is preferable to a WhatsApp-only fallback. It still needs maintainer acceptance because the requested behavior changes omitted-account fallback semantics.

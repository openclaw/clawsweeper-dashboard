## Summary

Keep this PR open: the Slack helper redirect SSRF gap is real on current main, the patch applies the existing manual-redirect/revalidate pattern locally, and I found no blocking code-review or security finding; the remaining blocker is ordinary merge readiness because one CI shard failed and QA Smoke was still pending on the current head.

## What This Changes

The PR rewrites `fetchWithSlackAuth` in the Slack plugin to follow redirects manually, reject non-HTTPS or non-Slack redirect targets, strip Authorization on cross-origin Slack redirects, and add regression tests for the new guard.

## Best Possible Solution

Land the Slack helper redirect hardening after the remaining CI failure and pending QA settle, while keeping the production `resolveSlackMedia`/`saveRemoteMedia` guarded path unchanged.

## Reproduction Assessment

Yes. Source inspection on current main shows the first Slack URL is hostname-validated, then the redirected HTTPS URL is handed to `fetch` with automatic redirect following and no Slack hostname recheck for later hops; I did not run a failing current-main network repro.

## Solution Assessment

Yes. This is the narrow owner-local fix: it keeps redirects manual inside the Slack helper, reuses the existing Slack hostname allowlist, preserves same-origin auth, and strips auth after cross-origin Slack redirects; the safer alternative would be deleting the unused helper, but the tests still treat it as a supported local contract.

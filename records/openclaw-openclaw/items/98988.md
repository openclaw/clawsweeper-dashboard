The PR replaces tools-manager tar/unzip/PowerShell extraction with the shared `extractArchive` facade, adds a 100 MB download/archive cap plus extraction limits, and updates tools-manager tests.

## Best Possible Solution

Use the shared `extractArchive` path with a Transform-style download limiter that rejects before forwarding overflow chunks, clean up failed downloads, and add redacted real fd or rg extraction proof.

## Reproduction Assessment

Yes. Source inspection shows current main downloads release archives directly to disk and extracts them with unbounded `tar`/`unzip` subprocesses; I did not run a live decompression-bomb payload.

## Solution Assessment

No, not yet. Reusing `extractArchive` is the right extraction boundary, but the PR should reject overflow chunks before writing them, remove partial downloads on failure, and provide real fd/rg extraction proof.

Full review comments:

- **[P2] Enforce the byte cap before forwarding overflow chunks:** `src/agents/utils/tools-manager.ts:210-218`
  - body: The limiter increments bytes from a `PassThrough` `data` listener, but that listener runs after the chunk has been emitted toward the file pipeline, and `downloadTool` does not remove `archivePath` when `downloadFile` rejects before extraction cleanup starts.

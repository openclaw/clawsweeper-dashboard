## Summary

Keep open: current main and v2026.6.11 still hardcode read-based Skills guidance, and the related items cover adjacent skill-loading problems rather than replacing this narrow Skill-loader prompt contract decision.

## What This Changes

The issue requests that the native Skills prompt prefer invoking a registered Skill loader tool over read-based SKILL.md loading when such a tool is available.

## Best Possible Solution

Define an explicit trusted Skill-loader capability or plugin contract, then update the native Skills prompt, focused prompt tests, and public docs while preserving the read fallback when no trusted loader is available.

## Maintainer Decision

Question: Should OpenClaw support a plugin-provided Skill loader in the native Skills prompt by raw tool name, by an explicit trusted capability or manifest contract, or defer this until broader skill-contract parity is decided?

Rationale: The source gap is clear, but deciding how plugin tool output becomes higher-authority skill-loading context changes the plugin trust boundary and model-facing prompt contract.

Likely owner: steipete

Owner confidence: high

Options:

- **Require Explicit Skill-Loader Contract (recommended):** Add a named trusted capability or manifest/SDK contract before changing prompt wording, so only intentionally declared loader tools receive stronger loading guidance.
- **Use Normalized Tool Name Detection:** Treat any available tool named Skill as the loader and update the prompt now, accepting collision and trust-boundary risk for a smaller change.
- **Defer To Broader Skill Contract Work:** Keep the read-based prompt until native/Codex parity and slash-invocation skill-loading semantics are decided together.

## Reproduction Assessment

Yes. Source inspection on current main shows buildSkillsSection always emits read-based SKILL.md guidance and receives no available-tool set, while tool names are normalized before the section is built.

## Solution Assessment

Unclear as proposed. Preferring a loader tool is plausible, but a raw availableTools.has("Skill") check is not clearly the best fix without a supported capability, namespace, or trust contract.

## Summary

Keep open: current main and v2026.6.11 still hardcode read-based skill loading, and the safe fix needs a maintainer decision about a trusted Skill-loader contract rather than a raw prompt-name check.

## What This Changes

The issue requests changing the native Skills system prompt so a registered Skill loader tool is preferred over direct SKILL.md reads when available.

## Best Possible Solution

Define an explicit trusted Skill-loader capability or plugin contract, then update the native Skills prompt, focused prompt tests, and public docs while preserving the read fallback when no trusted loader is available.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw support a plugin-provided Skill loader in the native Skills prompt by raw tool name, by an explicit trusted capability or manifest contract, or defer this until broader skill-contract parity work is settled?

Rationale: The source gap is clear, but deciding how plugin tool output becomes higher-authority skill-loading context changes the plugin trust boundary and prompt contract, which automation should not settle.

Likely owner: steipete

Owner reason: steipete has the strongest current history on the system prompt surface and adjacent prompt/plugin-boundary changes.

Owner confidence: high

Options:

- **Require Explicit Skill-Loader Contract (recommended):** Add a named trusted capability or manifest/SDK contract before changing prompt wording, so only intentionally declared loader tools receive the stronger loading instruction.
- **Use Normalized Tool Name Detection:** Treat any available tool named Skill as the loader and update the prompt now, accepting collision and trust-boundary risk for a smaller change.
- **Defer To Broader Skill Contract Work:** Keep the read-based prompt until native/Codex parity and slash-invocation skill-loading semantics are decided together.

## Reproduction Assessment

Yes. Source inspection on current main shows buildSkillsSection always emits read-based SKILL.md guidance and receives no available-tool set, while tool names are normalized before the section is built.

## Solution Assessment

Unclear as proposed. Preferring a loader tool is plausible, but a raw availableTools.has("Skill") check is not clearly the best fix without a supported capability, namespace, or trust contract.

- `impact:security`: Automatically granting skill-loading authority based on a plugin-controlled tool name could cross an instruction-provenance and trust boundary.

## Summary

Keep open for a maintainer-owned security and product decision. Current main still directs native OpenClaw agents to read SKILL.md directly, but automatically trusting any plugin tool named `Skill` would create a name-collision authority boundary; the broader cross-harness contract remains active in https://github.com/openclaw/openclaw/issues/95058.

## What This Changes

Define whether native OpenClaw should prefer a registered skill-loading tool over direct SKILL.md reads when constructing its skills prompt.

## Best Possible Solution

Introduce an explicit trusted skill-loader capability owned by the generic plugin or harness contract, pass its verified tool identity and current skill snapshot into prompt construction, use it when present, preserve direct `read` as the default fallback, and cover native and Codex sibling behavior plus security collisions in tests and docs.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add an explicit trusted skill-loader capability, and which runtime or plugin contract is allowed to claim it for the current skill snapshot?

Rationale: Tool names are generic plugin-controlled identifiers, while selecting a loader changes the authority and provenance of instructions delivered to the model; source inspection cannot safely choose that security and cross-harness product contract.

Likely owner: steipete

Owner reason: Recent history places this person across the central prompt and runtime integration surface where the product and security boundary must be selected.

Owner confidence: medium

Options:

- **Add trusted loader capability (recommended):** Define a typed capability with verified skill identity, snapshot provenance, and fallback behavior, then make prompt construction prefer the resolved loader.
- **Keep direct-read loading:** Retain `read` as the only native implicit-loading mechanism and document that plugins must supply their own non-conflicting prompt guidance.
- **Recognize the tool name:** Prefer a case-insensitive `Skill` tool by convention, accepting collision and compatibility risks for simpler plugin integration.

## Reproduction Assessment

Yes at source level: provide a skills snapshot and an active tool named `Skill`; current prompt construction still emits direct-read guidance because `buildSkillsSection` never receives available-tool capability data. A live model-compliance run was not established.

## Solution Assessment

No, the proposed tool-name check is not the best fix because names do not prove loader semantics or trust. A typed, provenance-aware capability coordinated across harnesses is the narrower durable solution.

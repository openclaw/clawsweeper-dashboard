## Summary

Keep open for a maintainer security/product decision. Current main and v2026.6.11 still emit unconditional direct-read skill guidance even when registered tool names are available, so the requested behavior is not implemented. However, a case-insensitive `Skill` name check is not a safe contract: Pi tools are generic and can supply their own prompt guidance, Codex uses a typed harness-owned skill protocol, and OpenClaw documents third-party skills as untrusted code. The durable fix is an explicit trusted loader capability coordinated with the broader cross-harness contract work, not automatic authority for any same-named plugin tool.

## What This Changes

Allow the native system prompt to prefer an available skill-loading tool over direct SKILL.md reads.

## Best Possible Solution

Define a typed, trusted skill-loader capability shared across harnesses, let the owning loader provide exact prompt guidance, and preserve direct SKILL.md reads when that capability is absent.

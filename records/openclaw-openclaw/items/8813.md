## Summary

Keep open: current main and v2026.6.11 still prescribe direct SKILL.md reads, and the broader harness-contract issue does not fully resolve this distinct plugin-provided loader case.

## What This Changes

Request that native prompt guidance prefer an available Skill loader tool over directly reading SKILL.md.

## Best Possible Solution

Define a typed, harness-owned skill-loader capability with explicit authority and invocation semantics, then apply it consistently across native and Codex paths while retaining direct reads as the native fallback.

Question: What trusted skill-loader contract, if any, should plugins be allowed to provide across OpenClaw harnesses?

Rationale: Current Codex behavior is typed and harness-owned; an ordinary plugin tool name cannot establish equivalent authority, schema, source validation, or injection semantics.

Likely owner: steipete

Owner reason: He introduced and recently maintained the central prompt behavior and has already reviewed this issue and its adjacent design direction.

Owner confidence: high

Options:

- **Typed cross-harness loader (recommended):** Add an explicit loader capability with authority, schema, and injection semantics shared by native and Codex integrations.
- **Native named-tool convention:** Recognize a tool named `Skill` only in the native prompt and document its weaker convention, trust assumptions, and collision behavior.
- **Retain direct reads:** Keep direct SKILL.md reads as the sole native loading contract and reject authoritative plugin loaders.

## Reproduction Assessment

Yes, at source level. Current main always directs native agents to read SKILL.md even though tool availability is known, and tests plus public docs preserve that contract.

## Solution Assessment

No. A conditional based only on the name `Skill` is not equivalent to Codex’s typed, harness-owned loading and injection contract; loader capability and authority must be defined first.

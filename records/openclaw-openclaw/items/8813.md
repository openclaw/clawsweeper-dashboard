## Summary

The current source and latest release still hardcode read-based skill loading, so the issue remains valid; it should stay open because the actual fix requires a maintainer decision about the trusted plugin Skill-loader contract rather than a blind prompt edit.

## What This Changes

Request the native Skills system prompt to prefer an available plugin-provided Skill loader tool over read-based SKILL.md loading.

## Best Possible Solution

Define an explicit trusted Skill-loader capability or plugin contract, then update the native Skills prompt, focused prompt tests, and public system-prompt docs while preserving the read fallback when no trusted loader is available.

Options:

- **Require Explicit Skill-Loader Contract (recommended):** Add a named trusted capability or manifest/SDK contract before changing prompt wording, so only intentionally declared loader tools receive the stronger loading instruction.
- **Use Normalized Tool Name Detection:** Treat any available tool named Skill as the loader and update the prompt now, accepting collision and trust-boundary risk for a smaller change.
- **Defer To Broader Skill Contract Work:** Keep the read-based prompt until native/Codex parity and slash-invocation skill-loading semantics are decided together.

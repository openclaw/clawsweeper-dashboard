## Summary

Keep open: current main and the latest release still hardcode read-based Skills guidance, no merged related PR implements the registered Skill-tool preference, and the remaining work needs a maintainer decision on the plugin Skill-loader trust contract.

## What This Changes

Request to make the native Skills prompt prefer a registered Skill loader tool over the read tool when that loader is available.

## Best Possible Solution

Define an explicit trusted Skill-loader contract or capability, then update src/agents/system-prompt.ts, focused prompt tests, and public docs while preserving the read fallback when no loader is available.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw support a plugin-provided Skill loader in the native Skills prompt by raw tool name, by an explicit trusted capability/contract, or defer this until broader skill-contract work is settled?

Rationale: The source gap is clear, but choosing how plugin tool output becomes higher-authority skill-loading context changes the prompt and plugin trust boundary in a way automation should not decide.

Likely owner: steipete

Owner reason: steipete has the strongest history on the current Skills prompt list and adjacent prompt-rule changes.

Owner confidence: high

Options:

- **Require Explicit Skill-Loader Capability (recommended):** Add a named trusted capability or manifest/SDK contract before changing prompt wording, so only intentionally declared loader tools receive the stronger loading instruction.
- **Use Normalized Tool Name Detection:** Treat any available tool named Skill as the loader and update the prompt now, accepting the collision and trust-boundary risk for a smaller change.
- **Defer To Broader Skill Contract Work:** Keep the read-based prompt until native/Codex parity and slash-invocation skill-loading semantics are decided together.

## Reproduction Assessment

Yes. Source inspection on current main shows buildSkillsSection always emits read-based SKILL.md guidance and receives no available-tool set, while tool names are normalized before the section is built.

## Solution Assessment

Unclear as proposed. Preferring a loader tool is plausible, but a raw availableTools.has("Skill") check is not clearly the best fix without a supported capability, namespace, or trust contract.

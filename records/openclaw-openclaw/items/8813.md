## Summary

Keep open: current main and v2026.6.11 still hardcode read-based skill loading, and the remaining work needs a maintainer decision about the trusted Skill-loader plugin contract rather than conservative cleanup closure.

## What This Changes

The issue requests changing the Skills system-prompt instruction to prefer a registered `Skill` tool over reading `SKILL.md` directly.

## Best Possible Solution

Define an explicit trusted Skill-loader or skill-router capability, then update `src/agents/system-prompt.ts`, focused prompt tests, and public docs while preserving the read fallback when no trusted loader is available.

## Maintainer Decision

Question: Should native OpenClaw prompt guidance prefer a plugin-provided `Skill` tool by raw tool name, or only prefer a loader that advertises an explicit trusted skill-loading capability?

Rationale: The requested behavior changes instruction authority from direct file reads to plugin tool responses, which is a product/security boundary rather than a mechanical prompt edit.

Options:

- **Require Explicit Loader Capability (recommended):** Add or reuse a generic plugin capability/manifest/runtime marker and have prompt guidance prefer only that approved loader, preserving read fallback for other tools named Skill.
- **Adopt Tool-Name Convention:** Treat normalized `Skill`/`skill` tool availability as the supported contract and document that convention for plugin authors.
- **Wait For Router Direction:** Leave this issue open until maintainers decide whether the `local_skill_route` design should replace direct Skill-tool preference.

## Reproduction Assessment

Yes. Source inspection on current main shows `buildSkillsSection` always emits read-based `SKILL.md` guidance and receives no available-tool set, while tool names are normalized before the section is built.

## Solution Assessment

Unclear as proposed. Preferring a loader tool is plausible, but a raw `availableTools.has("Skill")` check is not clearly the best fix without a supported capability, namespace, or trust contract.

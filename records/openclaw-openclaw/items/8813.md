## Summary

Keep open: current main and v2026.6.11 still hardcode read-based Skills guidance, while the existing Claude CLI skills-plugin path does not cover a generic plugin-provided Skill loader tool. The remaining decision is the supported trusted-loader contract, not whether the source gap exists.

## What This Changes

The issue requests changing the native Skills system prompt to prefer a registered Skill-loader tool over read-based SKILL.md loading when that tool is available.

## Best Possible Solution

Define an explicit trusted Skill-loader capability or manifest/SDK contract, then update src/agents/system-prompt.ts, focused prompt tests, and public docs while preserving the read fallback when no trusted loader is available.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw support a plugin-provided Skill loader in the native Skills prompt by raw tool name, by an explicit trusted capability/contract, or defer it until broader skill-contract work is settled?

Rationale: Choosing how plugin tool output becomes higher-authority skill-loading context changes prompt precedence and the native plugin trust boundary, so automation should not choose the permanent contract.

Likely owner: steipete

Owner reason: steipete has the strongest current history on buildSkillsSection and adjacent Skills prompt rule changes.

Owner confidence: high

Options:

- **Require Explicit Skill-Loader Capability (recommended):** Add a named trusted capability or manifest/SDK contract before changing prompt wording, so only intentionally declared loader tools receive the stronger loading instruction.
- **Use Normalized Tool Name Detection:** Treat any available tool named Skill as the loader and update the prompt now, accepting the collision and trust-boundary risk for a smaller change.
- **Defer To Broader Skill Contract Work:** Keep the read-based prompt until native/Codex parity, slash invocation, and instruction-isolation semantics are decided together.

## Reproduction Assessment

Yes. Source inspection on current main shows buildSkillsSection always emits read-based SKILL.md guidance and receives no available-tool set, while tool names are normalized before that section is built.

## Solution Assessment

Unclear as proposed. Preferring a loader tool is plausible, but a raw availableTools.has("Skill") check is not clearly the best fix without a supported capability, namespace, or trust contract.

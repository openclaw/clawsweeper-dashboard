## Summary

Keep open: current main and v2026.6.11 still hardcode read-based Skills guidance even though plugin tool names can reach prompt construction, and the remaining change needs a maintainer decision about the trusted Skill-loader contract.

## What This Changes

The issue requests that the native Skills system prompt prefer invoking a registered Skill loader tool over read-based SKILL.md loading when such a tool is available.

## Best Possible Solution

Define an explicit trusted Skill-loader capability or contract, then update src/agents/system-prompt.ts, focused prompt tests, and public docs while preserving the read fallback when no loader is available.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw support a plugin-provided Skill loader in the native Skills prompt by raw tool name, by an explicit trusted capability or contract, or defer this until the broader skill-contract work is settled?

Rationale: The source gap is clear, but choosing how plugin tool output becomes stronger skill-loading authority changes the prompt and plugin trust boundary in a way automation should not decide alone.

Likely owner: steipete

Owner reason: steipete has the strongest history on the current skills prompt list and adjacent prompt-rule changes.

Owner confidence: high

Options:

- **Require explicit Skill-loader capability (recommended):** Add a named trusted capability or manifest/SDK contract before changing prompt wording, so only intentionally declared loader tools receive higher prompt authority.
- **Use normalized name-based detection:** Treat any available tool named Skill as the loader and update the prompt now, accepting the collision and trust-boundary risk for a smaller change.
- **Defer to broader skill parity work:** Keep the read-based prompt until the broader native/Codex and slash-invocation skill-loading contract is decided together.

## Reproduction Assessment

Yes. Source inspection on current main shows buildSkillsSection always emits read-based SKILL.md guidance and receives no available-tool set, while plugin tool names are forwarded into prompt construction.

## Solution Assessment

Unclear as proposed. Preferring a loader tool is plausible, but a raw availableTools.has("Skill") check is not clearly the best fix without a supported capability, namespace, or trust contract.

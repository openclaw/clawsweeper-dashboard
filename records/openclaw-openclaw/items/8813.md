## Summary

Keep open: current main and v2026.6.11 still hardcode read-based skill loading, while the requested Skill-loader preference needs a maintainer decision about plugin trust and instruction authority before implementation.

## What This Changes

The issue asks OpenClaw to prefer invoking a registered Skill-loader tool in the Skills system prompt instead of always telling the model to read SKILL.md files directly.

## Best Possible Solution

Define an explicit trusted Skill-loader or skill-router capability, then update src/agents/system-prompt.ts, focused prompt tests, and public docs while preserving the read fallback when no trusted loader is available.

Question: Should native OpenClaw prompt guidance prefer a plugin-provided Skill loader by raw tool name, or only prefer a loader that advertises an explicit trusted skill-loading capability?

Rationale: The requested behavior changes skill instructions from direct file reads to plugin tool responses, which affects prompt authority, plugin trust, and user upgrade expectations beyond a mechanical wording edit.

Options:

- **Require Explicit Loader Capability (recommended):** Add or reuse a generic plugin capability or manifest/runtime marker and have prompt guidance prefer only that approved loader while preserving read fallback for other tools named Skill.
- **Adopt Tool-Name Convention:** Treat a normalized Skill tool name as the supported contract and document that convention for plugin authors, accepting the collision and trust-boundary risk.
- **Wait For Router Direction:** Keep this issue open until maintainers decide whether the local_skill_route design or a broader skill-router API should replace direct Skill-tool preference.

## Reproduction Assessment

Yes. Source inspection on current main shows buildSkillsSection always emits read-based SKILL.md guidance and receives no available-tool set, while runtime tool names are normalized before prompt sections are built.

## Solution Assessment

Unclear as proposed. Preferring a loader tool is plausible, but a raw availableTools.has("Skill") check is not the best maintainable fix until OpenClaw defines a trusted loader capability or namespace contract.

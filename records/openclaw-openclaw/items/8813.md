## Summary

Keep open: current main and v2026.6.11 still emit read-based skill-loading guidance, and no merged related PR now implements the requested registered Skill-loader preference. The remaining work is a product/API contract decision because a name-only Skill tool check would change prompt authority for plugin-provided tools.

## What This Changes

The issue requests that the Skills system prompt prefer invoking a registered Skill loader tool over reading SKILL.md directly when that tool is available.

## Best Possible Solution

Define the supported Skill-loader contract, then update src/agents/system-prompt.ts, focused prompt tests, and public system-prompt docs while preserving the current read fallback when no loader tool is available.

## Reproduction Assessment

Yes. Source inspection on current main shows buildSkillsSection always emits read-based SKILL.md guidance and receives no available-tool set, while tool names are normalized before the section is built.

## Solution Assessment

Unclear as proposed. Preferring a registered loader tool is plausible, but maintainers should first choose whether the supported contract is name-based, namespaced, or an explicit skill-loader capability.

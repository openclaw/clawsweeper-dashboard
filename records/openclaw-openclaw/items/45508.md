## Label Justifications

- `P2`: Provider-backed WebChat voice is a meaningful improvement with real user friction, but current default WebChat and Talk flows are not globally broken.
- `impact:auth-provider`: The request depends on routing WebChat voice through configured TTS/STT providers, models, endpoints, and credentials.

- `impact:ux-friction`: Users can proceed by recording and uploading audio or using realtime Talk, but those workarounds do not provide one-button editable provider-backed dictation/read-aloud.

## Summary

Keep open: current main and the latest release expose useful backend TTS and media-audio pieces, but WebChat still lacks a landed provider-backed read-aloud action and a gateway-backed editable mic/STT flow. The open related PRs are partial candidates and still need maintainer review, proof, or security-boundary decisions before they can resolve the broad request.

## What This Changes

The issue requests routing WebChat read-aloud and microphone input through OpenClaw gateway-backed TTS/STT providers instead of browser speech APIs.

## Best Possible Solution

Land split, current-main implementations: WebChat read-aloud should use the existing TTS RPC plus scoped assistant-media tickets, and microphone input should be an explicit batch dictation flow through `tools.media.audio` with no browser-exposed provider credentials.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should WebChat provider-backed voice proceed as two core Gateway-owned slices: TTS read-aloud through existing TTS RPCs and batch editable STT through `tools.media.audio`, with no new `messages.stt` config surface?

Rationale: The source shows the backend pieces exist, but accepting browser microphone audio through Gateway and deciding fallback/config ownership are product and security-boundary choices that review automation should not settle.

Likely owner: steipete

Owner reason: steipete has the strongest sampled history on prior WebChat dictation and core TTS decisions, and is connected to the open TTS candidate PR.

Owner confidence: high

Options:

- **Split and accept Gateway-owned voice (recommended):** Proceed with TTS read-aloud first, then a batch dictation flow that reuses `tools.media.audio`, requires scoped credentials, and proves no provider secrets reach the browser.
- **TTS-only for now:** Land only a safe TTS/read-aloud implementation and keep STT tracked behind the narrower dictation/custom-ASR issues until the microphone security boundary is approved.
- **Defer core STT:** Keep WebChat realtime Talk and attachment upload as the supported voice paths and route provider-specific STT experiments to plugins or future API design.

## Reproduction Assessment

Not applicable as a failing-bug repro, but yes at source level: current WebChat has realtime Talk and attachment audio playback, while targeted searches and tests show no provider-backed Read aloud action or editable Gateway STT dictation path.

## Solution Assessment

No current implementation fully solves it. The maintainable direction is to reuse existing TTS RPCs and `tools.media.audio` rather than adding a parallel `messages.stt` provider stack or exposing provider calls directly from the browser.

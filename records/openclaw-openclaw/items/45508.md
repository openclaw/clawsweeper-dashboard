## Summary

Keep open: current main still lacks a completed provider-backed WebChat voice flow. Gateway TTS, Talk relay, and media-audio transcription primitives exist, but WebChat has no per-message Gateway-backed Read aloud action and no one-click provider-backed editable mic capture path; related items cover partial or conflicting slices rather than a landed solution.

## What This Changes

The issue requests provider-backed WebChat voice support so Read aloud uses configured Gateway TTS and microphone input can use configured server-side STT instead of browser speech APIs.

## Best Possible Solution

Keep this broad issue open as the provider-backed WebChat voice umbrella, land a secure scoped TTS Read aloud slice, and route editable mic dictation through the existing media-audio/Gateway path rather than adding a parallel `messages.stt` config stack.

## Reproduction Assessment

Yes, at source level: current main still asserts the Read aloud action and Voice input button are absent, while Gateway/provider primitives exist separately. I did not run a live browser session because the read-only cleanup question is already proven by current source and tests.

## Solution Assessment

No current implementation solves the whole issue. Reusing existing `tts.convert` and media-audio transcription plumbing is the right direction, but the recorder UX, media-ticket/auth handling, and provider/privacy boundaries need maintainer-approved PR review.

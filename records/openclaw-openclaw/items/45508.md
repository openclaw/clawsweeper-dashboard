## Summary

Keep open: current main still lacks a completed provider-backed WebChat voice flow. Gateway TTS, Talk transcription, and media-audio primitives exist, but WebChat has no per-message Read aloud action and no one-click provider-backed mic capture path; related open PRs cover partial or conflicting slices rather than a landed solution.

## What This Changes

The issue requests routing WebChat voice input/output through configured gateway-backed STT/TTS instead of browser speech APIs.

## Best Possible Solution

Keep this as the canonical WebChat provider-backed voice thread; land or replace the TTS slice using existing `messages.tts`/`tts.convert`, and settle a Gateway-backed editable STT UX that reuses `tools.media.audio` or Talk transcription rather than adding a parallel `messages.stt` config surface by default.

## Reproduction Assessment

Yes, at source level: current main lacks a provider-backed WebChat Read aloud action and one-click editable mic-capture/transcribe path, while tests assert the old `Voice input` and `Read aloud` controls are absent. This is not a strict bug repro because the remaining request is a feature/product gap.

## Solution Assessment

No final implementation is present. The issue should not be solved by a new `messages.stt` block by default because existing `tools.media.audio`, Talk transcription, and `messages.tts` surfaces already define the likely provider boundaries.

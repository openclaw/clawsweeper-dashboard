## Summary

Keep open: current main still lacks a completed provider-backed WebChat voice flow. The old browser speech controls are gone, but WebChat still has no Read aloud action backed by `messages.tts` and no one-click mic capture path that feeds configured `tools.media.audio` STT into the agent composer.

## What This Changes

Request provider-backed WebChat STT/TTS support so self-hosted or configured audio providers are used instead of browser-only speech paths.

## Best Possible Solution

Keep this as the canonical WebChat provider-backed voice thread; land or replace the TTS slice using existing `messages.tts`/`tts.convert`, and decide a Gateway-backed mic UX that reuses `tools.media.audio` or transcription-only Talk without adding a parallel `messages.stt` surface by default.

## Reproduction Assessment

Yes, at source level: current main has file upload and Talk controls but no Read aloud action, no provider-backed Voice input, and no `chat.transcribeAudio` method. This is a feature/product gap rather than a strict broken-contract bug.

## Solution Assessment

No final implementation is present. The best path should reuse `messages.tts`, `tools.media.audio`, and existing Talk transcription primitives where possible; adding a new `messages.stt` config surface is not the narrowest default solution.

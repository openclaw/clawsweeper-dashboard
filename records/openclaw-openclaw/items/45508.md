## Summary

Keep open: current main still lacks a merged provider-backed WebChat Read aloud action and a merged editable mic capture path that reuses the configured audio transcription pipeline. The request is now split across open partial PRs, so this issue remains useful as the canonical tracker.

## What This Changes

Request routes WebChat read-aloud and voice input through configured Gateway TTS/STT providers instead of browser speech APIs.

## Best Possible Solution

Keep this issue as the canonical WebChat provider-backed voice tracker, land or replace the TTS slice through existing Gateway TTS methods, and scope STT as editable batch push-to-talk using `tools.media.audio` with credentials kept server-side.

Options:

- **Narrow to TTS only:** Make this issue only the provider-backed read-aloud tracker and let the editable dictation issue own the STT product surface.
- **Pause for unified voice design:** Defer both slices until maintainers define one WebChat voice model across Talk, dictation, TTS settings, and fallback behavior.

## Reproduction Assessment

Yes, by source inspection: current WebChat lacks a provider-backed Read aloud action and has no merged editable batch mic capture flow, while existing audio upload and Talk paths are separate. This is a feature-gap reproduction rather than a strict bug reproduction.

## Solution Assessment

No, not exactly as proposed: routing through the Gateway is the right direction, but adding `messages.stt` would duplicate `tools.media.audio`. The narrower maintainable shape is existing Gateway TTS for read-aloud and editable batch dictation backed by the existing media audio pipeline.

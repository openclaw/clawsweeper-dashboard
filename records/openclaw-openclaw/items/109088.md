## Label Justifications

- `P2`: This is a normal reliability fix for a bounded provider-response hang found by source audit, without evidence of a widespread active regression.
- `merge-risk: 🚨 availability`: The new global idle cutoff can fail existing provider operations that pause more than 30 seconds between response chunks.
- `merge-risk: 🚨 compatibility`: Existing JSON/text helper callers silently acquire new timeout semantics without caller enumeration or upgrade proof.

## Summary

The timeout wiring is directionally sound, but the same stalled-body failure remains in the shared non-2xx provider error reader, and the PR supplies only a synthetic unit-stream test rather than after-fix real behavior proof. The new 30-second default also changes every JSON/text helper caller, so merge readiness needs caller-wide compatibility evidence.

## What This Changes

The PR adds idle and total timeout options to provider JSON, text, and binary response helpers, defaults JSON/text idle reads to 30 seconds, and adds a stalled JSON stream unit test.

## Best Possible Solution

Use one shared provider-body policy for JSON, text, and bounded error previews: default finite idle timeouts for control responses and error bodies, keep large binary reads explicitly caller-budgeted, and prove both stalled-success and stalled-error socket paths without changing unrelated provider behavior.

## Reproduction Assessment

Yes at source level: a response stream can emit a byte and leave the next `reader.read()` pending forever, and current main passes no chunk timeout in these helpers. The PR’s synthetic stream demonstrates that mechanism, but no real socket or provider reproduction is supplied.

## Solution Assessment

No, not yet. Wiring the existing idle-timeout primitive is the right layer, but the fix is one-sided because the shared non-2xx error-body reader retains the same indefinite read and the global default is not caller-audited.

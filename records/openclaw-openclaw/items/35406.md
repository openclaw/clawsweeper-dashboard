## Summary

Keep open: current main still decodes non-image `read` inputs as text, so PDF/Office bytes can still enter the tool result. The direct same-repo guard PRs are closed unmerged, and the only open implementation candidate is a conflicting fork PR that needs maintainer review or replacement rather than closing this issue.

## What This Changes

The issue requests safer `read` tool behavior for binary document formats so Office/PDF bytes do not enter model context as garbled text.

## Best Possible Solution

Land or close the linked implementation candidate after deciding the narrow contract, with a bounded `read` guard that prevents raw binary document bytes from entering context and leaves richer parsing to approved document/PDF tooling.

## Reproduction Assessment

Yes, at source level: current main only detects images before non-image files are decoded as text, so PDF/Office bytes can become `read` tool text output. I did not run a live binary read in this read-only review.

## Solution Assessment

Unclear: a safe fallback is likely the narrowest first fix, but automatic document parsing and PDF routing need maintainer decisions about ownership, security limits, and shared extractor boundaries.

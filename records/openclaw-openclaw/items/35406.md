## Summary

Keep open: current main and the latest release still route non-image reads through text decoding, while an open linked PR is the active but conflicted candidate for the safe-fallback guard.

## What This Changes

Request that the read tool stop returning raw binary document bytes for .docx, .pdf, .pptx, and .xlsx files, either by returning a safe fallback message or extracting text.

## Best Possible Solution

Add a narrow core read-tool guard that detects common binary document formats and returns an actionable fallback, pointing PDFs to the existing pdf tool and leaving full Office parsing to the broader document-input/plugin path.

## Maintainer Decision

Question: Should the read tool get a narrow core safe-fallback guard for binary document formats now, or should this wait for broader document parsing/provider-native file input work?

Rationale: The source-proven problem is narrow, but automatic parsing and provider-native forwarding overlap with larger open document-input issues and plugin/ClawHub scope decisions.

Likely owner: vincentkoc

Owner confidence: medium

Options:

- **Add narrow read fallback (recommended):** Keep the fix small: detect PDF/Office-style binary documents before text decoding and return a clear instruction to use pdf or a document parser.
- **Fold into broader document input:** Defer this issue to the provider-native file/document and attachment ingestion design so read behavior changes only once.
- **Implement parsing in core:** Add native extraction for selected formats in the read path, accepting the larger dependency, security, and maintenance surface.

## Reproduction Assessment

Yes from source inspection: the read tool only distinguishes images from everything else, then decodes all non-image buffers as text. I did not run a live tool call, so this is source-reproducible rather than live reproduced.

## Solution Assessment

Unclear as a full product direction, but the narrow safe-fallback option is the best bounded first step. Automatic parsing/provider-native forwarding should stay with the broader document-input issues unless maintainers explicitly choose that larger scope.

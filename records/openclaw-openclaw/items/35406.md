## Summary

Keep open: current main and the latest release still route non-image document reads through the text-decoding path, and the only linked closing PR is unmerged and conflicting rather than an implemented fix.

## What This Changes

The issue requests preventing the read tool from returning raw binary output for document formats such as DOCX, PDF, PPTX, and XLSX, either by warning or by extracting text.

## Best Possible Solution

Review or port a narrow safe-fallback guard in the current read-tool path for known binary document formats, while leaving full document extraction to the existing PDF/document/plugin surfaces.

## Maintainer Decision

Rationale: Source inspection confirms the current token-waste path, but the durable product choice is whether read should fail helpfully for binary documents or grow inline parsing behavior.

Options:

- **Add narrow read fallback (recommended):** Port or review the linked guard so read returns an actionable message for known binary Office/PDF formats and leaves parsing to dedicated tools.
- **Limit this to tool guidance:** Keep read as a text/image tool and update descriptions/docs to steer agents toward pdf or document tools, accepting that unsupported binary reads can still happen.
- **Fold into broader document ingestion:** Treat this as part of the broader provider-native file/document and attachment extraction work, with security and dependency review before implementation.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: non-image PDF/Office files miss the image branch and are decoded as UTF-8 text in the read tool, including the sandbox path where MIME detection only returns image types.

## Solution Assessment

Unclear until maintainers choose the scope. A narrow safe fallback is the smallest maintainable first step; automatic parsing belongs in the existing PDF/document extraction surfaces or broader document-ingest work.

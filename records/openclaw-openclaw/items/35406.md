## Summary

Keep open: current main still treats non-image read targets as text after image-only detection, so Office/PDF files can still produce raw binary-looking output; the open linked closing PR is an implementation candidate, not merged evidence.

## What This Changes

The issue asks OpenClaw to stop the `read` tool from returning raw binary output for document formats such as `.docx`, `.pdf`, `.pptx`, and `.xlsx`, either by returning a safe fallback or by extracting text.

## Best Possible Solution

Adopt or rebase a narrow current-main `read` guard for known binary document formats that returns a structured fallback and points users to dedicated document tools; keep broader parser/provider-native document support in the related product tracks.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should the filesystem `read` tool add a generic binary-document fallback for Office/PDF files, or should document handling be left entirely to dedicated parser/provider/file-input surfaces?

Rationale: The source gap is real, but the permanent shape affects core tool semantics, existing PDF/document-extract surfaces, and whether OpenClaw adds only a safe default or parser-backed document handling in core.

Likely owner: Peter Steinberger

Owner reason: Recent read-tool ownership and core/product-boundary history make this the best available routing candidate for the read semantics decision.

Owner confidence: medium

Options:

- **Adopt a narrow read guard (recommended):** Add a focused MIME/extension guard for known binary document formats that returns a helpful fallback and routes users to `pdf` or document-extraction tools without parsing documents in `read`.
- **Add parser-backed read support:** Teach `read` to extract text for selected document formats, accepting the added security, dependency, and maintenance surface after explicit design review.
- **Defer to dedicated tools only:** Leave `read` text/image-only and rely on tool descriptions plus PDF/document/file-input surfaces, accepting that the reported binary-read token waste may continue when the model chooses `read`.

## Reproduction Assessment

Yes. Source inspection shows the current read path only special-cases detected images; non-image document bytes are decoded as text, so a `.docx`/`.xlsx`/`.pptx`/`.pdf` read can still produce binary-looking output.

## Solution Assessment

Yes for the safe-fallback direction, but not for automatic parsing as the default core `read` behavior without maintainer approval; the narrow maintainable fix is a binary-document guard that points to dedicated document tools.

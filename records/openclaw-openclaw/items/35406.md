## Summary

Keep open: current main and the latest release still send non-image PDF and Office-format reads through the generic text-decoding path, and an open conflicting fork PR specifically targets this issue, so this remains the canonical maintainer decision point.

## What This Changes

The issue asks OpenClaw to stop the read tool from returning raw binary-looking output for PDF and Office documents, either by warning or by extracting readable text.

## Best Possible Solution

Approve a narrow read-tool fallback that blocks raw PDF/Office binary bytes from transcript context and points users to the PDF/document extraction path, while leaving richer parsing or provider-native forwarding to the broader document-input issues.

- **Defer To File-Input Work:** Keep read unchanged for now and link this issue to the broader document extraction and provider-native file-input architecture trackers.

Yes. Source inspection gives a high-confidence path: non-image PDF/Office bytes bypass image MIME handling and are decoded as text by the read tool; I did not run a live read because this review is read-only.

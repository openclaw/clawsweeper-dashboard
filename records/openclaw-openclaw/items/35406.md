## Summary

Keep open: current main and the latest release still let non-image `read` inputs fall through to text decoding, so the direct PDF/Office token-waste path remains. Separate PDF/media-understanding paths help adjacent workflows, but the open linked fork PR is conflicting and the remaining choice needs maintainer product direction.

## What This Changes

The issue asks OpenClaw to stop returning raw binary-looking output when the agent `read` tool is pointed at PDF or Office documents, either by returning a clear fallback message or by extracting document text.

## Best Possible Solution

Add a narrow core `read` guard for known binary document MIME types/extensions that returns a concise fallback and points PDFs to the existing `pdf` tool, while leaving richer Office parsing and provider-native file forwarding to the broader document work.

Yes, source-reproducible. Current `read` checks only for image MIME and otherwise decodes the file buffer as text, so a DOCX/PDF buffer can become model-visible UTF-8 output; no live run was executed in this read-only review.

Unclear until maintainer direction is set. A narrow fallback is the safest first fix, while automatic parsing and provider-native forwarding need explicit security and ownership decisions.

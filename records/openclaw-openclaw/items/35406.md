## Summary

Keep open: current main and the latest release still decode non-image `read` inputs as text, so PDF/Office bytes can still enter the tool result. An open cross-repo closing PR exists at https://github.com/BingqingLyu/openclaw/pull/1676, but it is unmerged and conflicting, so it is an implementation candidate rather than a reason to close this issue.

## What This Changes

Prevent the `read` tool from returning garbled raw bytes for PDF and Office document files, either by safe fallback messaging or approved text extraction.

## Best Possible Solution

Decide the narrow core contract, then land or replace the linked implementation with a bounded `read` guard that prevents raw binary document bytes from entering context while leaving richer parsing to approved document/PDF tooling.

Owner confidence: medium

Options:

- **Narrow fallback guard (recommended):** Return a clear structured message for known binary document formats in host and sandbox read paths, with regression tests for text/image passthrough and document blocking.
- **Parser-backed read:** Add extraction for selected formats only after choosing archive/XML/parser dependencies, size limits, and security boundaries.
- **Route to separate tooling:** Keep `read` text/image-only and make the model-facing description plus existing document/PDF tools handle supported formats explicitly.

Yes, at source level: current `read` detects only image MIME types before falling through to text decoding for every non-image buffer. I did not run a live binary read in this read-only review.

## Solution Assessment

Unclear: the narrow safe fallback is likely the best first step, but parser-backed extraction needs a maintainer decision about ownership, dependency limits, and security boundaries.

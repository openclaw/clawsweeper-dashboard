## Summary

Keep open: current main deliberately disables configured fallbacks for `modelOverrideSource: "user"`, and its regression tests lock that behavior in. The July 22 beta reproduction confirms the user impact remains, while the open opt-in policy PR provides a possible direction but does not settle the product contract for an exact user-selected model.

## What This Changes

Change fallback handling so a manually selected session model can recover through the configured model fallback chain during provider failure.

## Best Possible Solution

Keep strict behavior until the assigned owner selects an explicit user-override fallback contract; if resilience is approved, land one narrow, documented opt-in policy with resolver and real provider-failover coverage rather than an unconditional substitution.

Yes at source level: current main deterministically returns an empty list for a user override, and its regression test asserts that result. The July 22, 2026 beta report corroborates the runtime symptom, though this read-only review did not run a live provider-outage scenario.

## Solution Assessment

No for the proposed unconditional change: current code treats an exact user selection as a strict contract, so silently substituting another model needs explicit product approval. A documented, narrowly scoped opt-in is the safer maintainable path if maintainers choose resilience.

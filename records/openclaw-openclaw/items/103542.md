## Summary

Current main and release v2026.6.11 retain the reported time-of-check/time-of-use race: prune selects an old registry row, later removes by runtime name, and unconditionally deletes that name even if another context refreshed or recreated it. The related open PR explicitly leaves cross-process pruning as follow-up, and the protected `maintainer` label requires explicit handling.

## What This Changes

Prevent graceful sandbox pruning from removing or deregistering a same-name runtime that was refreshed after prune selected a stale snapshot.

## Best Possible Solution

Make graceful prune a canonical lifecycle mutation that acquires the selected cross-process owner, re-reads eligibility, validates the concrete runtime identity, and conditionally deletes the exact registry version; preserve confirmed explicit recreate as a separate immediate operator action.

Options:

- **Gateway-owned pruning (recommended):** Route graceful prune through the owning Gateway so one lifecycle process drains work and performs fresh runtime and registry checks.
- **Recoverable shared lease:** Implement a process-shared lease with stale-owner recovery plus runtime-identity and registry-version compare-and-swap checks.

## Reproduction Assessment

Yes, at high confidence from source: defer `removeRuntime` after the initial prune snapshot, refresh or recreate the same registry name, then resume prune and observe name-only runtime removal followed by unconditional row deletion. Current tests do not yet encode this interleaving.

## Solution Assessment

The requested fresh eligibility check, runtime-identity validation, and version-coupled deletion are the correct invariants; the permanent cross-process ownership mechanism still requires maintainer security-boundary judgment.

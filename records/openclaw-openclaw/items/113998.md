## Label Justifications

- `merge-risk: 🚨 compatibility`: Existing cron webhook receivers lose bearer authentication until operators add trusted destination hosts or explicitly select `*`.

## Summary

Keep this PR open for maintainer review. The branch provides a focused defense against a real bearer-token disclosure path and the author addressed the earlier hostname-normalization and invalid-entry findings, but the deliberate fail-closed rollout changes authentication for existing `cron.webhookToken` users and needs an explicit security/product decision before merge.

## What This Changes

The PR adds `cron.webhookTokenHosts`, withholds cron webhook bearer tokens from destinations outside that hostname allowlist, and adds validation, Doctor guidance, documentation, and delivery-path coverage.

## System Context

Cron jobs store webhook destinations and the Gateway posts run results to those destinations. This change sits between stored job delivery settings and the outbound webhook request, deciding whether the operator-owned bearer token is attached while leaving the webhook delivery itself intact.

## Architecture Diagram

## Best Possible Solution

Have the security and cron owners explicitly choose the fail-closed upgrade policy; if approved, retain the central host gate and Doctor-only advisory, with clear release communication that existing authenticated receivers need an allowlist entry or the explicit `*` opt-out.

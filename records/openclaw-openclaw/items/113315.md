## Summary

Keep open for targeted maintainer investigation. Current main’s isolated-polling parent handler writes the Telegram update to the durable ingress spool before it sends the worker a successful acknowledgment, so the reported persisted-offset-with-no-spool signature is not established from that handler alone; the worker’s offset-persistence path and the reporter’s beta build need to be traced together.

Likely related people: obviyus is the strongest routing candidate from recent Telegram ingress and durable-drain work; joshavant is also closely connected through the earlier isolated-spool recovery work.

## What This Changes

The issue requests that Telegram polling never persist or acknowledge an inbound update until a durable spool or equivalent recoverable dispatch handoff succeeds, with visible diagnostics when it does not.

## System Context

Telegram’s isolated polling worker receives Bot API updates and hands them to the Telegram plugin’s durable ingress spool. The spool drain later adopts each update into OpenClaw’s channel and agent-dispatch pipeline, while the polling offset controls whether Telegram will redeliver it.

## Architecture Diagram

flowchart LR
  A[Telegram Bot API updates] --> B[Isolated polling worker]
  B --> C[Parent ingress handoff]
  C --> D[Durable Telegram ingress spool]
  D --> E[Ingress drain]
  E --> F[Channel and agent dispatch]
  C --> G[Polling offset acknowledgement]
  G --> A

## Best Possible Solution

Trace the worker’s acknowledgment-to-offset-persistence implementation, add structured polling-batch/spool-write/offset diagnostics, and add a fault-injection regression that proves a failed or absent durable handoff leaves the Telegram update eligible for recovery without creating duplicate dispatch.

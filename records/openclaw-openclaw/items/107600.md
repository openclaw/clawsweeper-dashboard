## Summary

This PR should stay open, but the current patch is not safe to merge: it converts an indeterminate Funnel-status probe into “no route,” which can defeat `preserveFunnel` and replace an externally managed route.

**Likely related people:** @RenzoMXD introduced the route-preservation behavior, and @steipete committed that work and has extensive history in this Tailscale infrastructure area.

## What This Changes

The PR changes Tailscale Funnel status handling to return false instead of propagating a JSON parse error when command stdout is malformed.

## Best Possible Solution

Represent probe failure separately from confirmed absence—by preserving the rejection or returning an explicit indeterminate outcome—and ensure the caller never applies Serve when Funnel status cannot be established.

Rationale: The root policy treats fallback behavior as a product decision, and either choice trades external-route preservation against best-effort Serve availability.

Options:

- **Preserve on unknown (recommended):** Keep parse failure distinct from false and skip Serve reconfiguration unless status positively proves no matching Funnel route exists.
- **Apply Serve best-effort:** Intentionally map malformed status to false, accepting possible replacement of an external route and documenting that limitation.

## Solution Assessment

No. Returning false is not the safest fix because it conflates malformed status with confirmed absence; an explicit indeterminate outcome or preserved rejection protects the route-preservation invariant.

## Summary

The prior blocker remains: the new fallback converts an unknown Funnel status into a definitive “no route” result, which conflicts with the documented `preserveFunnel` safety contract and can cause startup to replace an externally managed route. The PR also still lacks after-fix proof from a real Tailscale setup.

## What This Changes

The PR changes Tailscale Funnel status parsing so malformed command output returns `false` instead of throwing, and updates the focused unit test.

## Best Possible Solution

Represent malformed Funnel status as an unknown/error outcome and make the startup caller preserve the existing external route by skipping Serve; add caller-level regression coverage and redacted live Tailscale proof.

## Reproduction Assessment

Yes at source level: malformed stdout makes the parser throw on current main, while this patch catches it and returns `false`; the downstream preservation risk follows from the documented `preserveFunnel` caller contract. A real Tailscale reproduction has not been supplied.

## Solution Assessment

No. Preventing the uncaught parse error is reasonable, but returning `false` is not the safest fix because it conflates an unreadable status with confirmed route absence; an explicit unknown outcome that preserves the route is narrower and safer.

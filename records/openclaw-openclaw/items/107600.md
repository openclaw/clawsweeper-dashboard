## Label Justifications

- `P1`: Merging the current patch can break an active externally configured Funnel workflow during gateway startup.
- `merge-risk: 🚨 compatibility`: The new failure behavior changes `preserveFunnel` from conservative preservation to treating malformed status as permission to replace routing.
- `merge-risk: 🚨 availability`: Applying Serve after an unknown status can disable the public Funnel endpoint that an existing setup relies on.

## Summary

Keep this PR open: the new `false` result conflates an unknown Funnel status with a confirmed absent route, so the gateway can proceed to apply Serve and replace a Funnel configuration that the existing preservation path was designed to retain.

## What This Changes

The PR catches malformed `tailscale funnel status --json` output in `hasTailscaleFunnelRouteForPort`, returns `false`, and changes the focused unit-test expectation accordingly.

## Best Possible Solution

Represent Funnel inspection as covered, not covered, or unknown—preferably with the repository’s `Result` convention—and have gateway startup skip Serve on unknown status while logging the inspection failure.

## Solution Assessment

No. Catching the parse error is reasonable, but converting an unknown status to `false` is unsafe because the caller interprets false as authorization to apply Serve; an explicit failure or tri-state result is the narrower maintainable fix.

## Review Findings

Full review comments:

- **[P1] Move durable ACP state out of JSON sidecar storage:** `src/acp/store/store.ts:112`
  - body: This adds `state/acp/gateway-node-runtime-store.json` and persists sessions, runs, worker events, leases, checkpoints, delivery targets, and idempotency through JSON reads/writes. OpenClaw-owned runtime state under state dirs is required to use SQLite/shared state DB or an explicitly designed DB schema, so this bypasses migration/doctor handling and creates recovery/upgrade debt for the core durability path.
  - confidence: 0.93
- **[P1] Propagate ACP worker event send failures:** `src/node-host/invoke.ts:426`
  - body: The new ACP invoke path passes worker events through `sendNodeEvent`, but that helper catches and ignores `client.request("node.event", ...)` failures. A node can therefore report an ACP turn as accepted or completed locally while the gateway never records the event or terminal, leaving the durable run stuck in recovery and replay state inconsistent.
  - confidence: 0.9
- **[P1] Do not restart an active projection runner:** `src/auto-reply/reply/dispatch-acp-replay.ts:456`
  - body: When a target already has an active runner, `ensureProjection` calls `existing.start()`, and `start()` always launches another `run()` loop. A second ensure for the same target can race the first loop on the same events/checkpoints and duplicate outward delivery instead of deduplicating projection work.
  - confidence: 0.91
- **[P2] Stop the runner when turn start never creates a run:** `src/auto-reply/reply/dispatch-acp.ts:396`
  - body: The durable dispatch path starts a projection runner with `waitForRunStart`, then rethrows `turnError` when no durable run exists. That branch never stops the runner, so the background loop keeps polling for a run that will never appear after each early `runTurn` failure.
  - confidence: 0.88
- **[P1] Serialize reconnect reconcile before accepting worker traffic:** `src/gateway/server/ws-connection/message-handler.ts:1024`
  - body: Node connect starts `handleNodeConnected` as fire-and-forget while the same connection can immediately send `acp.worker.event` or `acp.worker.terminal`. During that window the store still sees the lease as `suspect`, rejects progress as not active, and the node-host ACP path does not emit periodic heartbeats that would reliably replay the dropped terminal/event.
  - confidence: 0.86
- **[P1] Validate run idempotency by session and request:** `src/acp/store/store.ts:533-534`
  - body: `startRun` returns any existing `store.runs[runId]` before checking that it belongs to the same `sessionKey` and `requestId`. If two ACP sessions reuse a provider/request-derived run id, the second session aliases the first run record and later worker traffic fails session/lease validation, corrupting recovery and delivery bookkeeping.
  - confidence: 0.9

## Label Justifications

- `P1`: A completed multi-tool user request is surfaced as a failure, prompting unnecessary retries and materially degrading active channel workflows.
- `impact:message-loss`: The user receives no usable final response for an otherwise completed request, so the completion result is effectively suppressed.

## Summary

This issue remains necessary. Current main detects empty visible assistant responses and has a one-shot retry path, but it explicitly skips that retry after potential side effects, which is the reported successful-tool-work case; it then retains the generic failure text. The merged terminal-fallback work improves delivery of the failure payload, not a tool-disabled final summary after successful work.

Likely related people: `dolphinsboy` is the recent terminal-delivery contributor, with high confidence from the merged fallback work.

## What This Changes

Add a guarded, tool-disabled final-response recovery for whitespace-only `stop` completions after successful tool work, with a truthful degraded reply if recovery also yields no visible answer.

## Best Possible Solution

Extend the existing bounded empty-response recovery with a separate post-tool finalization lane: only after a normal `stop`, blank visible output, successful settled tool outcomes, and no current-request delivery; run once with tools unavailable, then emit a conservative artifact-oriented fallback when no summary is produced.

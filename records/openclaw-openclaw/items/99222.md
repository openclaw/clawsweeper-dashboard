Full review comments:

- **[P1] Allow retry for stale Cellar node paths:** `packages/memory-host-sdk/src/host/embeddings-worker.ts:277-279`
  - body: The reported stale Homebrew executable is shaped like `/opt/homebrew/Cellar/node/<version>/bin/node`, so this `includes("/bin/node")` guard makes `doRetry` false for the exact failure this PR is meant to recover. The error then falls through to the old process-error path with no retry.
  - confidence: 0.97
- **[P1] Resolve an executable instead of a module:** `packages/memory-host-sdk/src/host/embeddings-worker.ts:240-247`
  - body: `require.resolve("node")` is module resolution, not PATH executable lookup; in the inspected Node runtime it throws `MODULE_NOT_FOUND`, so the catch returns the same stale `process.execPath`. Even after the retry predicate is fixed, the retry can spawn the deleted binary again.
  - confidence: 0.95
- **[P1] Use the stable executable for worker forks:** `packages/memory-host-sdk/src/host/embeddings-worker.ts:256-258`
  - body: The branch initializes and updates `stableNodePathPromise`, but `ensureChild()` never reads it and still passes `execPath: process.execPath`. Normal launches and later launches after a retry child exits can keep using the stale Cellar path.
  - confidence: 0.94
- **[P1] Replay the request after starting the retry child:** `packages/memory-host-sdk/src/host/embeddings-worker.ts:313-320`
  - body: The ENOENT branch starts a retry child and then immediately rejects every pending request. The initialize or embed request that triggered recovery is never sent to the retry child, so caller-visible recovery still fails even if the second fork succeeds.
  - confidence: 0.93
- **[P1] Keep local worker error codes in sync:** `packages/memory-host-sdk/src/host/embedding-worker-errors.ts:8`
  - body: Adding `staleNodePath` only to the SDK list leaves memory-core's worker-failure detector unaware of the new code, so local-provider degradation and cache clearing can skip this exact failure shape.
  - confidence: 0.89

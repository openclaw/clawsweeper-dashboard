Full review comments:

- **[P1] Resolve a Node executable, not a module name:** `packages/memory-host-sdk/src/host/embeddings-worker.ts:244-246`
  - body: `require.resolve("node")` performs module resolution, not executable discovery; on the supported Node runtime here it throws `MODULE_NOT_FOUND`, so the catch returns the same stale `process.execPath` and the retry can spawn the deleted binary again.
  - confidence: 0.94
- **[P1] Replay the worker request after retry:** `packages/memory-host-sdk/src/host/embeddings-worker.ts:313-320`
  - body: The ENOENT handler starts a retry child, then immediately rejects every pending request. The initialize or embed request that triggered recovery is never resent to the retry child, so callers still see failure even if the second fork succeeds.
  - confidence: 0.93
- **[P1] Use the resolved stable path for fork calls:** `packages/memory-host-sdk/src/host/embeddings-worker.ts:258`
  - body: The branch initializes and updates `stableNodePathPromise`, but `ensureChild()` never reads it and still passes `execPath: process.execPath`. Normal launches and later launches after a retry child exits can keep using the stale Cellar path.
  - confidence: 0.9
- **[P1] Keep local worker error codes in sync:** `packages/memory-host-sdk/src/host/embedding-worker-errors.ts:8`
  - body: Adding `staleNodePath` only to the SDK list leaves memory-core's worker-failure detector unaware of the new code, so the local-provider degradation/cache-clearing path can skip this exact failure.
  - confidence: 0.88
- **[P2] Make the mocked worker answer initialize:** `packages/memory-host-sdk/src/host/embeddings-worker-stale-node.test.ts:83-88`
  - body: These tests await `createLocalEmbeddingWorkerProvider()`, which waits for an initialize response. The mocked child only calls the `send` callback and never emits a matching message, so the tests can hang before proving the retry behavior.
  - confidence: 0.86

## Summary

Keep open. Current main and v2026.6.11 still make ordinary Gateway startup reject invalid config or emit manual `openclaw doctor --fix` guidance rather than auto-applying doctor repairs, and the issue discussion shows broad unattended doctor repair can affect sandbox and Telegram availability, so this remains a maintainer product/security policy item rather than cleanup-close material.

## What This Changes

The issue requests automatic or configurable application of safe doctor fixes during Gateway startup so repeated startup warnings and config drift do not require a manual doctor fix command.

## Best Possible Solution

Define a narrow startup repair contract first: classify unattended-safe doctor mutations, exclude security/sandbox/channel-availability/plugin/provider/auth changes unless explicitly opted in, log every redacted changed path with backup details, and keep broad repair behind manual `openclaw doctor --fix`.

## Reproduction Assessment

Yes, at source level: current startup validates and rejects invalid snapshots with manual `openclaw doctor --fix` guidance, while the doctor repair sequence only runs from explicit repair/yes options. I did not run a live Gateway because this review is read-only.

## Solution Assessment

No for the broad suggested shape: auto-running the whole doctor repair sequence at every Gateway start is not the safest solution because the repair sequence can touch security, channel, plugin, provider, and auth state. A narrower safe-startup repair contract or explicit opt-in with audit logging is the maintainable path.

## Summary

Keep open. Current main and v2026.6.11 still keep ordinary Gateway startup repair manual: startup validates the config snapshot and emits doctor guidance instead of running repair, while the explicit doctor repair sequence is broad enough to affect channel, plugin, auth, and security-adjacent config. The issue discussion adds useful safety context because a startup `doctor --fix` workaround reportedly changed intentional sandbox posture and disabled Telegram, so this remains a product/security policy item rather than cleanup closure.

## What This Changes

The issue asks OpenClaw to auto-apply safe doctor repairs at Gateway startup, or add an audited `doctor.autoFix`-style option, so config drift does not keep warning across restarts.

## Best Possible Solution

Define a narrow startup repair contract first: classify unattended-safe doctor mutations, exclude security/sandbox/channel/provider/plugin/auth changes unless explicitly opted in, log every redacted changed path with backup details, and keep broad repair behind manual `openclaw doctor --fix`.

## Reproduction Assessment

Yes, at source level: current Gateway startup validates the snapshot and emits manual `openclaw doctor --fix` guidance instead of invoking the doctor repair sequence. I did not run a live Gateway because this review is read-only.

## Solution Assessment

No, auto-running the whole existing doctor repair sequence during every startup is not the best fix. A bounded safe-repair subset or explicit opt-in with redacted audit logs and no-clobber boundaries is the safer maintainable direction.

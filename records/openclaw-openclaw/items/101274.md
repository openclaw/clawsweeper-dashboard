## Summary

Keep open: the patch is a useful hardening step, but it is not merge-ready because the new cap runs after `processStream` has already accumulated the SSE event, so oversized or no-boundary stream data can still grow memory before the guard, and the PR lacks real production-path proof.

## What This Changes

The PR adds a 16 MiB byte-length check before Tlon Urbit SSE `JSON.parse` and adds two direct `processEvent` boundary tests.

## Best Possible Solution

Add the limit at the Tlon SSE stream/pending-event accumulation layer, keep the parse guard as defense in depth if desired, and prove normal, oversized, and no-boundary SSE data through the production stream path.

## Reproduction Assessment

Yes, from source inspection: current main calls `JSON.parse(data)` without a size check and accumulates SSE stream chunks until an event boundary with no pending-buffer cap. I did not run a live Urbit stream reproduction.

## Solution Assessment

No. The proposed guard is useful but too late in the production path; the best fix is to bound `processStream` pending/event data before `processEvent` and then prove that path.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.88

Full review comments:

- **[P1] Move the cap before stream buffering can grow unbounded:** `extensions/tlon/src/urbit/sse-client.ts:32-34`
  - body: This check runs only inside `processEvent`, after `processStream` has already appended chunks into `buffer` until `\n\n` and sliced out `eventData`. A hostile ship can still send an oversized event or omit the boundary and grow memory before this guard runs, and the new tests call `processEvent` directly, bypassing that production path. Put the byte cap in the stream/pending-event accumulation path and cover it through `processStream` or `openStream`.
  - confidence: 0.9

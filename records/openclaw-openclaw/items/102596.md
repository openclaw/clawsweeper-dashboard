## Label Justifications

- `P2`: This is a deterministic cron CLI validation bug with limited blast radius rather than a core runtime outage.
- `impact:message-loss`: Persisting a channel id as a channel type can make cron delivery or failure alerts miss the intended chat later.
- `impact:ux-friction`: The current flag help and delayed `channel_not_found` failure make a natural Slack channel-id mistake hard to diagnose.

## Summary

Keep this open: current main still accepts and stores channel-id-looking values in cron channel-type fields without a clear add/edit-time hint, and the linked closing PR is still open.

## What This Changes

The issue asks cron add/edit to warn when a channel id is passed to `--channel` or `--failure-alert-channel`, and to make the help text describe a channel type instead.

## Best Possible Solution

Land or revise the linked PR so cron add/edit emit a non-blocking channel-type hint and corrected help while leaving Gateway routing authoritative for external channels.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes. Source inspection on current main shows cron add/edit still store the channel fields without known-channel-type validation, and the help fallback still says `last|<channel-id>`; no live CLI run was needed for this read-only source repro.

## Solution Assessment

Yes on direction. The narrow maintainable fix belongs in the cron CLI add/edit layer as a non-blocking hint and help correction, while preserving the Gateway as the authoritative router for valid external channels.

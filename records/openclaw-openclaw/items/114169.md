## Summary

Keep this issue open. The reported path is a plausible channel-health regression: a busy channel with an old run-activity timestamp is classified as stuck after a fixed 25-minute window, while the existing configurable threshold covers stale inbound events rather than busy-run activity. The requested new configuration surface is not yet the clearly best fix because the health monitor must still recover genuinely stalled runs.

Likely related people: `vincentkoc` is the strongest routing candidate from the original channel-health/readiness implementation; `Takhoffman` is a recent adjacent contributor to the policy tests and stale-socket recovery path.

## What This Changes

The issue requests that long-running healthy channel turns not be restarted by the health monitor after a fixed 25-minute busy-activity timeout, potentially through a configurable threshold.

## System Context

The gateway health monitor reads channel runtime snapshots and decides whether a channel is healthy, stale, or stuck. A stuck result causes the channel lifecycle manager to restart the account, which can interrupt an active agent turn and its user-facing reply path.

## Architecture Diagram

## Best Possible Solution

Preserve recovery for genuinely wedged channel runs while preventing false restarts of turns that are demonstrably progressing; first correct or prove the active-run activity signal, and add an operator-facing threshold only if maintainers decide that different deployment policies cannot be represented safely by the canonical behavior.

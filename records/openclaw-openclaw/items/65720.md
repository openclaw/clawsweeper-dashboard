## Summary

Keep open: current main and v2026.6.11 still serve Control UI only from the in-process Gateway HTTP listener, with no crash-survivor static fallback or public config contract, so this remains a product and security architecture decision.

## What This Changes

The issue requests an opt-in Gateway crash fallback that keeps a static WebUI maintenance page available on port 18789 after the Gateway process exits.

## Best Possible Solution

Maintain this as a product/security design item and choose either a supervised rescue/static sidecar or an explicitly documented operator-supervisor contract with auth, origin, TLS, port handoff, configuration, docs, and upgrade proof.

## Maintainer Decision

Required: true

Question: Should OpenClaw core own a crash-survivor Control UI static fallback on the Gateway port, or should this remain an operator-supervisor/reverse-proxy responsibility?

Rationale: Current code can only serve Control UI while the Gateway process is alive, and adding a same-port fallback changes availability architecture plus security/auth semantics that automation cannot choose safely.

Options:

- **Document supervisor pattern:** Core would keep the Gateway lean and document systemd, launchd, container, or reverse-proxy supervision as the supported crash-recovery path.
- **Defer request:** Leave the feature open without implementation until enterprise deployment demand or a concrete proposal justifies the core surface.

## Reproduction Assessment

Yes for the missing capability from source inspection: current main has no crash-survivor Control UI fallback or config knob. I did not run a live crash scenario because this is a feature request, not a broken documented behavior report.

## Solution Assessment

No for the exact proposed simple toggle: once the Gateway process exits, in-process code cannot continue serving a page. The better solution needs a maintained supervisor or rescue-sidecar design with explicit security and upgrade semantics.

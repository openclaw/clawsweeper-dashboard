## Summary

Keep open: current main and the latest release still serve the Control UI from the Gateway process itself with no crash-survivor static fallback or public crash-fallback config, so this remains a product and security architecture decision rather than a cleanup close.

## What This Changes

The issue requests an opt-in Gateway/WebUI resilience feature so a static maintenance-style Control UI remains reachable after the Gateway process crashes.

## Best Possible Solution

Define the supported resilience boundary first; if core owns it, implement a supervised rescue/static sidecar or documented supervisor contract with explicit port handoff, auth/origin/TLS semantics, config schema, docs, and upgrade proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw core own a crash-survivor same-port Control UI fallback after the Gateway process exits, or should this remain a deployment supervisor/reverse-proxy pattern?

Rationale: The requested behavior crosses process supervision, public config, and Control UI security boundaries; code inspection shows it cannot be satisfied by a simple in-process Gateway toggle.

Likely owner: steipete

Owner reason: The decision sits on the Gateway/Control UI architecture and feature history that steipete originally introduced and has most heavily maintained.

Owner confidence: high

Options:

- **Document supervisor pattern (recommended):** Keep core lean and document systemd/reverse-proxy recovery as the supported enterprise deployment pattern unless a concrete core API gap is identified.
- **Sponsor core rescue sidecar:** Accept the new core availability surface and design a narrow supervised static sidecar with explicit auth, TLS, origin, port handoff, and upgrade tests.
- **Decline native fallback:** Close the direction as out of scope for OpenClaw core and ask operators to use existing process supervisors or infrastructure tooling.

## Reproduction Assessment

Not applicable: this is an enhancement request, not a broken documented behavior. Source inspection gives high confidence that current main still lacks the requested crash-survivor WebUI mode.

## Solution Assessment

No, not as a simple in-process toggle: once the Gateway process exits, it cannot serve HTTP. The maintainable solution needs a supervisor or rescue-sidecar design with explicit security and upgrade semantics.

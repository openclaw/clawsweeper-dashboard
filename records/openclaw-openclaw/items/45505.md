## Summary

Keep open: current main and the latest release contain the narrow successful-compaction count reconciler, but the requested authoritative reconciliation boundary for broader compaction-derived session state is still not implemented and needs maintainer direction.

## What This Changes

The issue requests a generalized post-timeout compaction completion reconciliation model for session counters, token/status snapshots, and downstream session state after compaction finishes late.

## Best Possible Solution

Define a maintainer-approved compaction-completion reconciliation boundary, then deliberately enroll only compaction-derived session fields with monotonic/idempotent semantics and focused regression coverage.

Kind: product_direction

Question: Should OpenClaw promote successful compaction completion into an authoritative reconciliation boundary for session-derived state beyond compactionCount?

Rationale: Current main has a narrow count repair, but deciding whether token snapshots, status freshness, memory-flush state, auth-profile markers, or channel recovery signals should converge through the same event is an ownership and session-state semantics choice rather than a mechanical bug fix.

Likely owner: jalehman

Owner reason: jalehman reviewed and co-authored the merged narrow fix, so they are the strongest available routing candidate for deciding whether that boundary should expand.

Owner confidence: high

Options:

- **Design a bounded reconciliation layer (recommended):** Define one helper or event for monotonic compaction-derived state and enroll only fields whose truth is successful compaction completion.
- **Keep the count-only repair:** Leave compactionCount as the only late-success reconciliation target and narrow or close the broader follow-up if more state should stay on existing paths.
- **Split by state surface:** Track token/status snapshots, memory flush gating, and channel recovery as separate follow-ups instead of one shared boundary.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainers choose the boundary; promoting the existing count repair into an authoritative compaction-completion reconciliation layer is plausible, but enrolling status, memory-flush, auth-profile, and channel recovery state needs product/owner judgment first.

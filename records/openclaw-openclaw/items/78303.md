## Summary

## What This Changes

Adds a bundle-MCP consent-envelope path that detects approval-required MCP tool results, routes them through plugin approvals and `/approve`, re-calls with `confirmation_token`, and documents/configures `mcp.approvals`.

## Best Possible Solution

Land this or a replacement only after maintainers settle the MCP consent protocol/defaults, bind approvals to full origin and exact call metadata, close the first-call token gap, and attach current-head real behavior proof.

## Solution Assessment

No. The bundle-MCP materializer is a plausible enforcement layer, but this diff is not the best merge-ready solution until the default, token-redemption, exact-call binding, and protocol-direction decisions are resolved.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.86

Full review comments:

- **[P1] Make MCP approvals opt-in or prove upgrade safety:** `src/agents/agent-bundle-mcp-materialize.ts:87-89`
  - body: This resolves the new consent gate as enabled unless users explicitly set `mcp.approvals.enabled: false`. Existing MCP servers that already return this envelope will stop returning a model-visible result and instead wait on plugin approval routing after upgrade, so this needs either opt-in behavior or maintainer-approved upgrade proof for default-on semantics.
  - confidence: 0.87
- **[P1] Reserve confirmation_token before the first consent call:** `src/agents/agent-bundle-mcp-materialize.ts:130-138`
  - body: The first MCP call still sends `params.input` unchanged, so a model-supplied `confirmation_token` reaches the MCP server before OpenClaw has detected an envelope or issued channel approval. That contradicts the advertised trust boundary for consent-capable tools.
  - confidence: 0.89
- **[P1] Bind approvals to full origin and exact call metadata:** `src/agents/agent-bundle-mcp-consent.ts:213-216`
  - body: The approval request carries agent/session/channel/target but not account/thread origin fields, and it has no canonical digest tying approval to the exact server/tool/arguments being retried. Side-effecting MCP approvals need at least the same origin binding as existing plugin approvals plus exact-call binding so a changed retry or different surface cannot authorize the wrong call.
  - confidence: 0.84

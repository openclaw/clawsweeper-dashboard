## Label Justifications

- `impact:other`: The observable impact is a third-party channel-plugin action-discovery failure, which does not match the more specific owned impact categories.

## Summary

This is a third-party Zulip plugin integration defect rather than a missing OpenClaw core capability. Current main intentionally limits `getChatChannelMeta` to bundled channel metadata, while the channel-plugin base explicitly supports external channel IDs by taking their metadata from the plugin’s own `meta` parameters.

## What This Changes

The issue requests that message-action discovery work for a Zulip channel supplied by an installed third-party plugin.

## System Context

Channel plugins register their own identity, metadata, capabilities, and optional message-action discovery with OpenClaw. The shared `message` tool asks the active plugin for its supported actions; bundled-channel metadata is only a helper for OpenClaw-owned channel catalog entries.

## Architecture Diagram

flowchart LR
  A[Installed Zulip plugin] --> B[Channel plugin registration]
  B --> C[Plugin metadata and action adapter]
  C --> D[Shared message tool discovery]
  E[Bundled channel catalog] --> F[Bundled metadata helper]
  F --> G[Known bundled channel metadata]
  F --> H[Unknown external ID error]
  C --> I[Agent-visible message actions]

## Best Possible Solution

Update the Zulip plugin to provide its own complete channel metadata and avoid calling the bundled-only metadata helper for `zulip`; add a plugin-level regression test that loads the installed channel and exercises its `describeMessageTool` path.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, from source: an external `zulip` id passed to the bundled-only metadata helper reaches the defined unknown-channel error path, while external plugins are expected to supply their own metadata.

## Solution Assessment

No, changing OpenClaw’s bundled metadata catalog is not the best fix. The supported plugin contract already gives external channels an owner-local metadata path, so the narrow durable repair belongs in the Zulip package.

## Evidence

- **Current SDK contract:** `getChatChannelMeta` resolves metadata from the bundled channel catalog and deliberately rejects an unknown id. The adjacent comment states that `createChannelPluginBase` serves external plugin ids through `params.meta`, so an installed plugin should not use the bundled-only lookup for `zulip`.
  - file: [src/plugin-sdk/core.ts:2606](https://github.com/openclaw/openclaw/blob/97d3d60b5120a59e8cb9ccbdfca12455acaf909e/src/plugin-sdk/core.ts#L2606)
  - sha: [97d3d60b5120](https://github.com/openclaw/openclaw/commit/97d3d60b5120a59e8cb9ccbdfca12455acaf909e)
- **External-channel capability boundary:** The channel plugin contract requires each plugin to provide `id`, `meta`, `capabilities`, and `config`; message actions are an optional plugin-owned adapter. This supports fixing the metadata/action setup in the Zulip package without changing OpenClaw core.
  - file: [src/channels/plugins/types.plugin.ts:591](https://github.com/openclaw/openclaw/blob/97d3d60b5120a59e8cb9ccbdfca12455acaf909e/src/channels/plugins/types.plugin.ts#L591)

- **Message-action ownership:** `describeMessageTool` is defined as a channel-owned action adapter and receives the active channel context, so action discovery is supplied by the channel plugin rather than the bundled metadata catalog.
  - file: [src/channels/plugins/types.core.ts:3203](https://github.com/openclaw/openclaw/blob/97d3d60b5120a59e8cb9ccbdfca12455acaf909e/src/channels/plugins/types.core.ts#L3203)

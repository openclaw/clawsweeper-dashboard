## Summary

Keep open: current main and v2026.6.11 provide targeted wake, sessionKey, delivery-context, hook, cron, and small in-process event-bus primitives, but they still do not provide the requested first-class async route registry with external-event matching, lifecycle, ambiguity handling, dedupe policy, privacy policy, and safe action routing.

## What This Changes

Request a framework-level async result routing layer that maps later external events back to the originating topic session and optionally posts a summary plus wakes that session.

## Best Possible Solution

Define a narrow plugin/API-friendly async callback route contract that composes existing hooks, targeted wake, delivery context, dedupe, and approval policy, then decide whether any core-owned registry is warranted.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw create a core-owned async callback route registry, expose missing plugin/API primitives so this lives outside core, or defer the feature behind existing wake/hooks/cron building blocks?

Rationale: The remaining work is not a localized bug fix; it requires product ownership over storage, privacy, safety policy, event-source matching, ambiguity handling, and core-versus-plugin boundaries.

Likely owner: Peter Steinberger

Owner reason: The question is primarily product/API scope, and Peter Steinberger appears in current main and adjacent wake-routing history while VISION.md provides the relevant boundary guidance.

Owner confidence: medium

Options:

- **Design plugin/API contract first (recommended):** Keep core lean by identifying any missing extension points, then let route registries and source watchers live as plugins or ClawHub packages unless a small core primitive is clearly required.
- **Build a minimal core registry:** Accept core ownership of a local single-gateway route ledger, matcher, dedupe state, and safe action runner with migration and privacy policy tests.
- **Defer to existing primitives:** Document current targeted wake, hooks, cron, delivery-context, and approval building blocks and leave higher-level callback routing to workspace-specific implementations for now.

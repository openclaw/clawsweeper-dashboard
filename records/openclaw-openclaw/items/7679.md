## Summary

Current main still uses pairing for Telegram DMs and lacks verified owner capture during onboarding. The request remains necessary and vision-aligned, but maintainers must choose between verified onboarding capture and a post-approval policy transition before implementation.

## What This Changes

Make fresh Telegram onboarding securely establish the intended owner and configure direct messages as an owner-only allowlist instead of leaving pairing as the default.

## Best Possible Solution

Keep installed configurations unchanged, but make fresh Telegram setup run a visible one-time token challenge, capture only the matching numeric sender ID, and persist a complete owner-only channel policy in the Telegram plugin.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Telegram establish the first owner with a verified challenge during onboarding, or keep pairing for bootstrap and auto-flip the channel policy only after approval?

Rationale: The alternatives have different first-run UX, authorization timing, multi-account mapping, and compatibility behavior, so implementation should not choose between them implicitly.

Likely owner: steipete

Owner reason: They have the strongest cross-surface history and already participated in this issue's product-level review.

Owner confidence: high

Options:

- **Verified onboarding allowlist (recommended):** Display a one-time token, capture only the matching sender ID, and write an explicit Telegram allowlist during fresh setup.
- **Post-approval auto-flip:** Keep pairing for first-owner bootstrap, then safely derive an explicit channel allowlist as proposed in https://github.com/openclaw/openclaw/issues/81876.
- **Keep pairing default:** Retain the current trust flow and limit changes to warnings and documentation.

## Reproduction Assessment

Yes at source level: omitted Telegram DM policy resolves to pairing, an unknown sender receives a pairing challenge, and setup has no verified owner-capture flow. Current source and focused tests establish this without a live bot run.

## Solution Assessment

No, blindly capturing the first message is not the best solution because it creates an owner-race window. A token-bound onboarding handshake is the narrowest safe design unless maintainers intentionally select the post-approval auto-flip model.

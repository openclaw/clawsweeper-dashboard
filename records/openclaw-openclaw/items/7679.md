## Summary

Keep open: current main and v2026.6.11 still default Telegram DMs to pairing and require manual numeric owner enrollment. The requested safer first-owner default remains useful, but token-verified identity capture and upgrade compatibility are security/product choices that require maintainer direction. ([github.com](https://github.com/openclaw/openclaw/blob/main/docs/channels/telegram.md?utm_source=openai))

## What This Changes

Make fresh Telegram setup enroll a verified owner ID and use an owner-only DM allowlist instead of pairing by default.

## Best Possible Solution

Add a Telegram-owned, challenge-token enrollment step for fresh setup that captures the matching numeric sender ID, writes `dmPolicy: "allowlist"` plus `allowFrom`, preserves all existing explicit and upgraded configurations, and covers first-install, timeout, wrong-token, race, multi-account, and manual-fallback behavior.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should fresh Telegram onboarding replace initial DM pairing with token-verified owner capture, or retain pairing and harden only the post-approval state?

Rationale: Both approaches change the first-owner authorization boundary, and the repository does not currently define whether compatibility, zero-config pairing, or fail-closed owner enrollment should take precedence.

Likely owner: steipete

Owner reason: They have the strongest combined history across Telegram runtime, onboarding, docs, and the prior security/product review of this exact request.

Owner confidence: high

Options:

- **Verified owner capture (recommended):** For fresh interactive setup, require an exact random challenge token, capture that sender's numeric ID, and persist an owner-only allowlist while leaving existing configs unchanged.
- **Post-pairing auto-lock:** Keep first-run pairing, then convert an omitted policy to a durable owner allowlist after the first explicitly approved owner, aligning with the broader post-bootstrap proposal.
- **Keep pairing default:** Retain current behavior and improve setup warnings, owner-ID assistance, and documentation without changing admission defaults.

## Reproduction Assessment

Yes for the current-state gap: current schema and docs clearly show pairing remains the default and owner allowlisting remains manual. This is a feature request rather than a failing-runtime reproduction. ([github.com](https://github.com/openclaw/openclaw/blob/main/docs/channels/telegram.md?utm_source=openai))

## Solution Assessment

Unclear until maintainers choose the authorization model. Token-verified fresh-install capture is the safest narrow implementation; unverified first-message capture is not acceptable, and silently changing existing omitted-policy configurations would be upgrade-unsafe.

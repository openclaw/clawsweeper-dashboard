## Summary

Keep open: current main and v2026.6.11 still use pairing for unset Telegram DM policy, require manual numeric owner-ID entry for allowlist setup, and issue pairing challenges to unknown senders. The broader owner-bootstrap reports overlap but do not replace this narrow Telegram trust-boundary decision.

## What This Changes

Default fresh Telegram DM setup to an allowlist populated through verified capture of the intended owner's numeric Telegram ID.

## Best Possible Solution

Add a Telegram-owned, one-time-token owner bootstrap that atomically records the matching numeric sender ID and selects allowlist for fresh setup, while preserving existing explicit pairing configurations and documenting the transition.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should fresh Telegram onboarding establish the first owner through a token-verified allowlist flow, or retain initial pairing and harden the policy only after owner approval?

Rationale: Both choices change the first-run trust boundary and failure mode; repository behavior cannot determine the intended tradeoff between zero-config pairing and fail-closed verified owner capture.

Likely owner: steipete

Owner reason: The live discussion and repeated Telegram onboarding history make this the strongest available owner for the trust-boundary decision.

Owner confidence: high

Options:

- **Verified allowlist bootstrap (recommended):** Generate a one-time challenge, accept only the matching sender, and write that numeric ID with dmPolicy allowlist for fresh setup.
- **Pair then auto-harden:** Keep initial pairing, then switch an otherwise unset policy to the approved owner's allowlist after first-owner establishment.
- **Keep pairing default:** Retain current pairing behavior and limit the change to warnings or separate abuse mitigations.

## Reproduction Assessment

Yes. Current source and tests establish pairing as the omitted-policy default, manual numeric allowlist setup, and pairing challenges for unauthorized senders; a live Telegram account is unnecessary to reproduce that configured behavior.

## Solution Assessment

No, not exactly as originally proposed: the security goal is sound, but first-message owner capture is unsafe. The maintainable solution needs a one-time verification challenge or an explicit post-pairing hardening transition.

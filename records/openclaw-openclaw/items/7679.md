## Summary

Keep this issue open. Current public Telegram documentation still makes pairing the default, requires an explicit numeric allowlist for allowlist mode, and describes manual owner-ID discovery; no evidence establishes the requested token-verified owner capture or a merged canonical replacement. The related bootstrap and post-pairing-default proposals overlap but make distinct product-policy choices, so a maintainer should choose the intended first-owner and upgrade model before implementation.

## What This Changes

Make fresh Telegram setup securely identify the intended owner and configure direct messages as an explicit allowlist rather than the current pairing default.

## System Context

Telegram is an OpenClaw channel plugin: setup writes its account and access-policy configuration, then inbound direct messages are gated by the configured DM policy before an agent processes them. Pairing supports first-contact approval, while allowlist mode requires durable numeric sender IDs in configuration.

## Architecture Diagram

## Best Possible Solution

Add a Telegram-owned, token-verified first-owner setup step that writes an explicit numeric allowlist and allowlist DM policy only for a fresh verified setup, preserves existing explicit policies, and provides a clear recovery path when verification cannot complete.

## Risks / Open Questions

- Changing a fresh-install default from pairing to allowlist can make a newly configured bot unreachable unless setup atomically verifies and persists the intended sender ID.
- Capturing the first inbound sender without a user-visible challenge token creates a race in which another Telegram user could become the configured owner.
- The maintainer must define upgrade behavior: existing explicit pairing configurations must remain unchanged, and any migration of prior pairing approvals into config must be deliberate and recoverable.

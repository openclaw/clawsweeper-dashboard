## Label Justifications

- `P2`: This is a meaningful Telegram security-default and setup improvement with bounded channel authorization impact, not an active bypass or outage.
- `impact:security`: The issue concerns whether unknown Telegram users can receive pairing challenges instead of being blocked after owner setup, and any owner capture must preserve the authorization boundary.

## Summary

Keep open: current main and v2026.6.11 still default omitted Telegram DM policy to pairing, still issue pairing challenges to unknown DM senders, and still rely on manual numeric allowFrom setup; related open items overlap but do not implement token-verified Telegram owner capture.

## What This Changes

Requests that Telegram fresh setup/defaults use dmPolicy="allowlist" with the owner's numeric Telegram ID captured during onboarding instead of leaving DMs in pairing mode.

## Best Possible Solution

Choose the Telegram trust model, then implement a token-verified owner capture or maintainer-approved owner-derived default with explicit-pairing compatibility, docs, schema, setup/runtime tests, and live Telegram proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Telegram first-run setup replace default pairing with token-verified owner allowlist capture, use a post-bootstrap owner-derived default flip, or preserve pairing as the default with stronger manual allowlist guidance?

Rationale: The request changes who becomes authorized to command a Telegram bot during first-run setup and changes upgrade/default behavior for existing omitted dmPolicy configs, so automation cannot safely choose the trust model.

Likely owner: steipete

Owner reason: steipete has the strongest current history signal across Telegram config defaults, runtime fallback, setup, docs, and prior review routing for this trust-boundary decision.

Owner confidence: high

Options:

- **Token-Verified Owner Capture (recommended):** Generate a short setup token, require the intended owner to send that token to the bot, then write dmPolicy="allowlist" and allowFrom for that numeric Telegram ID while preserving explicit pairing configs.
- **Post-Bootstrap Default Flip:** Keep first-run pairing unchanged and derive owner allowlist behavior from commands.ownerAllowFrom after the first approved owner, aligning this issue with the broader cross-channel default-flip design.
- **Keep Pairing Default:** Leave runtime/setup defaults as pairing and improve warning, doctor, and docs guidance for users who want owner-only allowlist mode.

## Reproduction Assessment

Yes, by source inspection: omitted Telegram dmPolicy still resolves to pairing, unknown DMs still enter the pairing challenge path, and setup still requires manual numeric allowFrom entry rather than token-verified owner capture.

## Solution Assessment

Unclear. Token-verified owner capture is a plausible safest direction, but maintainers need to choose between that, a post-bootstrap owner-derived default flip, or preserving pairing before implementation.

## Summary

Current main still uses pairing when Telegram DM policy is omitted, issues pairing challenges to unknown direct senders, and requires manual numeric owner-ID entry for allowlist setup. No merged replacement owns this narrow onboarding-verification request, but its first-owner trust and recovery contract requires maintainer security and product judgment.

## What This Changes

Verify the intended Telegram owner during onboarding and persist that numeric sender ID with allowlist DM policy for fresh setups.

## Best Possible Solution

Implement one Telegram-owned, challenge-verified owner-bootstrap flow that atomically writes canonical dmPolicy and allowFrom state, preserves explicit existing configurations, and offers an in-product retry or recovery path.

## Maintainer Decision

Question: Should fresh Telegram onboarding establish the owner through a one-time verification challenge and immediately persist allowlist state, or bootstrap through pairing and transition only after explicit owner approval?

Rationale: Both designs address unsolicited pairing exposure, but they define different initial trust, failure recovery, and alignment with the cross-channel post-bootstrap proposal; repository evidence cannot choose that contract safely.

Owner confidence: high

Options:

- **Challenge-verified onboarding (recommended):** Require the intended owner to return a one-time token, then atomically persist the numeric sender ID and allowlist policy.
- **Post-pairing transition:** Keep pairing for first access and explicitly convert the approved owner into allowlist state afterward, coordinating with the cross-channel proposal.
- **Retain pairing default:** Leave authorization behavior unchanged and improve warnings plus manual numeric-ID setup only.

## Reproduction Assessment

Yes, at high confidence from current source: omitted Telegram DM policy remains pairing, unknown senders still reach the pairing-challenge path, and setup still relies on manually entered numeric IDs. This is a source reproduction of a feature gap rather than a failing established behavior contract.

## Solution Assessment

No, a bare default flip is not the best solution. The maintainable path must verify the intended owner, atomically persist canonical authorization state, and include non-technical retry or recovery while preserving explicit existing configs.

## Summary

Keep open: current main and v2026.6.11 still use Telegram pairing by default and require manual numeric owner enrollment. The safer owner-only outcome remains useful, but token-verified identity capture and existing-install compatibility require an explicit maintainer security decision.

Likely related people: `steipete` and `obviyus` are the strongest routing candidates from recent Telegram setup, access-control, runtime, and documentation history; `ernestodeoliveira` and `sumukhj1219` have adjacent setup-warning and pairing-path history.

## What This Changes

Add token-verified first-owner enrollment during Telegram onboarding and persist an owner-only DM allowlist instead of leaving new setups on pairing.

## Best Possible Solution

For newly completed Telegram onboarding, authenticate the intended owner with a short one-time challenge, then persist account-scoped `dmPolicy: "allowlist"`, numeric `allowFrom`, and matching command-owner identity; preserve existing implicit-pairing installations unless maintainers approve a doctor-backed migration.

Options:

- **Verified fresh onboarding (recommended):** Generate a one-time token, capture only the Telegram sender who returns it, and write explicit owner allowlists for new setup while leaving existing installations unchanged.
- **Verified post-pairing transition:** Keep pairing for initial bootstrap, then persist the first explicitly approved account as owner and stop future pairing challenges unless pairing was explicitly configured.
- **Global default migration:** Change omitted `dmPolicy` to allowlist for all installations and provide a doctor migration and recovery path for configurations without a resolvable owner.

## Reproduction Assessment

Yes at source level: the current schema and runtime default to pairing, the DM path issues challenges to unknown senders, and setup accepts only manually entered numeric IDs. A live onboarding run was not needed to establish that verified owner capture is absent.

## Solution Assessment

No, not exactly as originally phrased. Owner-only allowlisting is the right end state, but setup must authenticate the sender with a one-time challenge and preserve account and upgrade compatibility rather than trusting the first inbound message or globally changing the implicit default.

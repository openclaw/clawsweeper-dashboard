## Best Possible Solution

No: the shared header seam is a plausible core piece, but the best solution must also cover sibling iOS gateway consumers and prevent cleartext Basic credential transport. The current PR is too narrow for the advertised user path.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.86

Full review comments:

- **[P2] Carry proxy auth into share relay sends:** `apps/ios/Sources/Model/NodeAppModel.swift:2614`
  - body: This wires proxy headers into the main node session, but the iOS share extension later opens its own `GatewayNodeSession` from `ShareGatewayRelayConfig`, which currently saves only the URL, token, and password. A user connected through a Basic-auth reverse proxy will still hit proxy 401s when sending via the share extension; persist/pass the proxy auth material through that relay config with backward-compatible decode behavior.
  - confidence: 0.88
- **[P2] Block Basic proxy auth on cleartext WebSockets:** `apps/ios/Sources/Gateway/GatewayConnectionController.swift:821-823`
  - body: The new proxy header is built regardless of the gateway URL scheme, while manual gateways can still be configured with `Use TLS` off. That would send a decodable Basic credential over `ws://`; require `wss://` for proxy credentials or drop the header with a clear Settings/preflight error before connecting.
  - confidence: 0.82

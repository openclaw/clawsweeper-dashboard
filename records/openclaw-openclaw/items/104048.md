## Summary

The cross-boundary design is sensible, but the exact head is not merge-ready: it can pass a non-original event to AppKit’s drag API and exceeds the repository’s enforced Swift type-length limit. The protected `maintainer` label also requires explicit human handling rather than cleanup closure.

## What This Changes

The PR adds a guarded WKWebView-to-AppKit bridge so passive split-view pane headers can drag the macOS window, disables header title selection, and adds focused Swift and TypeScript tests.

## Best Possible Solution

Keep the cross-boundary design, but move the drag-message parsing and handling out of the oversized controller, ensure `performDrag(with:)` receives only the initiating left-mouse-down event, and prove the actual app can drag from title and empty header space without stealing any header button.

## Solution Assessment

No as written. A WebKit-to-AppKit bridge is the narrowest ownership-correct approach, but it must preserve the original mouse-down event and avoid growing the controller past the enforced limit.

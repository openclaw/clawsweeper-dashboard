## Summary

Current main and v2026.6.11 use a fixed two-check cooldown plus a rolling hourly restart cap, so adaptive backoff remains unimplemented. The request fits OpenClaw’s stability direction, but maintainers should define the maximum delay and healthy-reset condition before implementation.

## What This Changes

Adopt progressively increasing restart delays for unhealthy channel accounts instead of relying on a fixed health-check cooldown.

## Best Possible Solution

Implement gateway-owned, per-account bounded backoff that advances only after consecutive unhealthy recovery attempts, resets after a confirmed healthy monitor observation, preserves immediate continuation of an already-pending recovery, and retains the rolling hourly cap.

## Reproduction Assessment

Yes at source level: keeping an account unhealthy causes retries after the same fixed cooldown until the rolling hourly cap applies, and focused fake-timer tests encode this behavior. This read-only review did not run a live provider-outage scenario.

## Solution Assessment

The adaptive-backoff direction is likely better for sustained outages, but the request is not yet a complete best fix because it omits the maximum delay and healthy-reset semantics; the bounded gateway-owned policy described above is the safer shape.

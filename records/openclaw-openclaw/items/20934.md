## Summary

Keep open. Current main and the latest release still lack REST-native session reset/status/compact/model/reasoning endpoints for HTTP API integrations, and the remaining work is a product/security decision about exposing mutating session controls over bearer-authenticated HTTP.

## What This Changes

The issue requests authenticated REST endpoints for HTTP clients to reset, query, compact, and update session state without re-enabling slash-command dispatch over `/v1/chat/completions`.

## Best Possible Solution

Define a maintainer-approved authenticated Gateway HTTP session-management surface that reuses existing session RPC semantics, preserves default-deny slash commands, documents the security model, and adds focused route/auth/request/response tests.

Options:

- **Approve narrow `/v1/sessions/*` API (recommended):** Implement reset/status/compact/model/reasoning endpoints with explicit scope mapping, strict schemas, tests, docs, and no slash-command re-enablement.
- **Limit HTTP to reset/status first:** Ship only the most common reset/status workflow while deferring compaction and model/reasoning mutations until the security model is proven.
- **Keep controls off `/v1`:** Document WebSocket/native clients or an intentionally enabled admin surface as the supported control plane for trusted automation.

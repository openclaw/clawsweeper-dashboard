## Summary

Keep open: current main and v2026.6.11 still lack REST-native session-management endpoints for HTTP integrations, and the related plugin/reset/read-only HTTP work does not cover the requested mutating Gateway HTTP API surface.

## What This Changes

Request authenticated REST endpoints for HTTP API clients to reset, inspect, compact, and update model/reasoning settings for sessions by key.

## Best Possible Solution

Approve one narrow authenticated Gateway HTTP session-management contract that reuses existing session handlers, preserves default-deny slash-command behavior, documents the security boundary, and covers reset/status/compact/model/reasoning with route/auth/request/response tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose dedicated `/v1/sessions/*` REST management endpoints for HTTP integrations, route this through the default-off admin HTTP RPC plugin, or keep session control limited to WebSocket/plugin surfaces for now?

Rationale: The source gap is clear, but adding mutating session controls to HTTP creates a public API and security-boundary choice that automation should not make on its own.

Likely owner: steipete

Owner reason: This account has the strongest combined history on the OpenAI-compatible HTTP surface and the shared-secret HTTP security boundary.

Owner confidence: high

Options:

- **Approve dedicated REST session management (recommended):** Implement reset/status/compact/model/reasoning routes as a focused Gateway HTTP layer over existing session handlers with explicit operator-scope, reserved-key, rate-limit, docs, and tests coverage.
- **Use admin HTTP RPC instead:** Expand and document the default-off admin HTTP RPC plugin as the intended HTTP control-plane path, avoiding a second dedicated `/v1/sessions/*` API.
- **Defer mutating HTTP controls:** Keep HTTP integrations on chat completions plus WebSocket/plugin surfaces until maintainers are ready to own a broader REST control-plane contract.

Yes, for the API gap at source level: current main has no `/v1/sessions/reset`, `/status`, `/compact`, `/model`, or `/reasoning` route while the underlying Gateway session RPCs already exist. I did not run a live Open WebUI setup in this read-only review.

## Solution Assessment

Unclear until maintainers approve the API and security shape. The maintainable direction is a focused authenticated HTTP route layer over existing session RPC/shared helpers, not re-enabling slash-command interpretation in `/v1/chat/completions`.

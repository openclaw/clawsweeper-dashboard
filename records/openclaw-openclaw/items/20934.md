## Summary

Keep open. Current main still lacks REST-native session reset/status/compact/model/reasoning endpoints for HTTP API integrations, while the existing Gateway session RPCs and adjacent HTTP helpers show the missing piece is an authenticated HTTP control-plane mapping rather than solved behavior.

## What This Changes

Request a REST session-management surface for `/v1/chat/completions` clients to reset, inspect, compact, and update session-level model or reasoning settings by session key.

## Best Possible Solution

Add a focused authenticated Gateway HTTP session-management adapter over existing session RPC/shared semantics, keep `/v1/chat/completions` slash commands default-deny, and document/test auth, route, request, and response behavior.

## Reproduction Assessment

Yes, at source level: current HTTP routing and docs lack the requested REST session-management endpoints, while the underlying session RPC methods and schemas exist and `/v1/chat/completions` remains command-default-deny.

## Solution Assessment

Mostly yes: the right shape is a thin authenticated HTTP adapter over existing Gateway session handlers, not text slash-command interception or duplicated session business logic; maintainers still need to approve the exact route and security contract.

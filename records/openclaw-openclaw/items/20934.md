## Summary

Keep open. Current main still lacks REST-native `/v1/sessions/*` management endpoints for HTTP API integrations, while the existing session operations remain available through Gateway RPC/WebSocket and adjacent session history/kill HTTP helpers only.

## What This Changes

The issue requests authenticated REST endpoints for HTTP clients to reset, inspect, compact, and update session settings without routing slash commands through chat completions.

## Best Possible Solution

Keep this issue as the focused tracker for an authenticated Gateway HTTP session-management API that reuses existing session RPC/helper semantics, preserves default-deny slash-command handling, and lands with route/auth/request/response tests plus public HTTP docs.

## Reproduction Assessment

Yes at source level: the current HTTP router and docs do not expose `/v1/sessions/reset`, `/v1/sessions/status`, `/v1/sessions/compact`, `/v1/sessions/model`, or `/v1/sessions/reasoning`, while `/v1/chat/completions` still enters the agent path without `CommandAuthorized`. I did not run a live curl because this review is read-only, but the route table makes the missing surface clear.

## Solution Assessment

Yes, the maintainable direction is to map authenticated HTTP endpoints onto the existing Gateway session RPC/helper contracts rather than re-enabling command interception in chat completions. The exact route shape and scope model still need maintainer product/security approval before implementation.

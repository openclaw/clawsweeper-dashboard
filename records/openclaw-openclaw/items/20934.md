## Summary

Keep open: current main still lacks REST-native `/v1/sessions/*` reset/status/compact/model/reasoning endpoints for OpenAI-compatible HTTP integrations, while the existing session control logic remains available only through Gateway RPC/WebSocket, adjacent history/kill HTTP helpers, plugins, or admin HTTP RPC surfaces that do not expose the requested methods.

## What This Changes

The issue requests authenticated REST endpoints for HTTP API integrations to reset, inspect, compact, and update model/reasoning state for a session without re-enabling slash-command handling in `/v1/chat/completions`.

## Best Possible Solution

Define a focused authenticated Gateway HTTP session-management surface that reuses existing `sessions.*` handlers and scopes reset/compact/model/reasoning as operator-admin mutations, documents the `/v1/chat/completions` command-deny boundary, and keeps this tracker distinct from broader read-only REST query work.

## Reproduction Assessment

Yes, at source level: current main registers no requested `/v1/sessions/*` management routes, while the existing session reset/patch/compact/list behavior is only available through Gateway methods or adjacent non-equivalent HTTP helpers. I did not run a live HTTP curl because the route table, docs, and schemas define the current behavior clearly.

## Solution Assessment

Unclear until maintainers confirm the HTTP route and security contract. The narrow maintainable path is a thin authenticated adapter over existing session RPC/shared helpers, not re-enabling slash-command interpretation in `/v1/chat/completions` or duplicating session logic.

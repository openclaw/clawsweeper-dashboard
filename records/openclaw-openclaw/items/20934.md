## Summary

Keep open. Current main and the latest release still expose session reset/status/compact/model/reasoning through Gateway RPC and adjacent HTTP helpers, but not the requested REST-native `/v1/sessions/*` management surface for HTTP API integrations; the closed REST attempt and open plugin reset PR do not resolve this core HTTP API request.

## What This Changes

Request authenticated REST endpoints that let `/v1/chat/completions` HTTP integrations reset, inspect, compact, and update session model/reasoning state without re-enabling slash-command interpretation.

## Best Possible Solution

Define a focused authenticated Gateway HTTP session-management API that reuses existing session RPC/helper semantics, preserves default-deny slash-command behavior, documents the operator security boundary, and adds route/auth/request/response tests.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: current main has no requested `/v1/sessions/*` HTTP route while the underlying `sessions.*` RPC operations and schemas exist.

## Solution Assessment

Yes for keeping this open; unclear for implementation until maintainers confirm the HTTP control-plane contract. The narrow maintainable direction is a thin authenticated REST mapping over existing session semantics, not slash-command re-enablement or a separate plugin-only reset API.

## Summary

Keep open. Current main and the latest release still lack the requested REST-native session management endpoints; existing Gateway RPC methods, adjacent session history/kill HTTP helpers, the open plugin reset PR, and the broader read-only REST tracker only cover adjacent pieces, while exposing reset/compact/model/reasoning over HTTP needs maintainer product and security approval.

## What This Changes

The issue requests authenticated REST session-management endpoints for HTTP API clients using `/v1/chat/completions`, covering reset, status, compact, model, and reasoning controls.

## Best Possible Solution

Define a maintainer-approved authenticated Gateway HTTP session-management surface that reuses existing `sessions.*` handlers, preserves default-deny slash-command handling, documents the bearer-token security model, and coordinates with broader read-only REST work without collapsing this tracker.

## Reproduction Assessment

Yes, at source level. Current main and `v2026.6.11` expose OpenAI-compatible HTTP routes and adjacent session kill/history helpers, while the requested `/v1/sessions/*` management routes are absent and `/v1/chat/completions` still treats slash commands as chat input.

## Solution Assessment

Unclear until maintainers approve the API and security contract. The narrow maintainable path is a thin authenticated HTTP adapter over existing Gateway session handlers, not re-enabling command interception in chat completions or duplicating session business logic.

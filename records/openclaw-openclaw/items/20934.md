## Summary

Keep open. Current main and v2026.6.11 still do not expose REST-native session reset/status/compact/model/reasoning routes for HTTP API integrations; existing Gateway session RPCs, session history/kill HTTP helpers, the default-off admin HTTP RPC plugin, and the open plugin reset PR only cover adjacent or partial surfaces.

## What This Changes

The issue requests authenticated REST endpoints for session reset, status, compaction, model selection, and reasoning controls for clients using the OpenAI-compatible HTTP API.

## Best Possible Solution

Implement a focused authenticated Gateway HTTP session-management surface that reuses existing `sessions.*` handler semantics, preserves default-deny slash-command handling for `/v1/chat/completions`, documents the operator security contract, and coordinates with the broader read-only REST tracker without collapsing this specific mutation/control request into it.

## Reproduction Assessment

Yes, at source level. Current main exposes the underlying `sessions.*` RPC methods but the HTTP router, docs, and admin RPC allowlist do not expose the requested REST session-management endpoints.

## Solution Assessment

Yes on direction, not yet on exact product shape. The maintainable fix is a thin authenticated HTTP adapter over existing Gateway session operations, not re-enabling slash-command interpretation or duplicating session business logic.

## Summary

Keep this PR open: it targets a real current-main TUI startup loader gap, but the current patch can newly clear a user-owned `sending`/`waiting` status to `idle` during post-connect initialization, and the branch is also conflicting with current main with the slow real-runtime proof still unresolved.

## What This Changes

The PR adds a TUI `starting up` busy activity state during post-connect initialization and changes history/startup cleanup so reconnect or adopted in-flight runs keep active status.

## Best Possible Solution

Tighten the idle clear to release only a still-owned `starting up` claim, resolve the TUI conflict against current main, rerun the focused TUI checks, and have maintainers either accept the split proof or capture a real slow Terminal Hatch/local-runtime artifact before merge.

## Reproduction Assessment

Yes. Current main is source-reproducible: `client.onConnected` marks the TUI ready before awaited post-connect work, and the renderer only shows a loader for statuses in `TUI_BUSY_ACTIVITY_STATUSES`, which lacks a startup/init state.

## Solution Assessment

No, not yet. Reusing the existing busy-status renderer is the right narrow direction, but the current idle-clear guard is too broad because it can overwrite `sending` or `waiting`; the safer fix is to clear only when the status is still `starting up`.

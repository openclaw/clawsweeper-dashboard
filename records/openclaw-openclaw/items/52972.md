- `impact:session-state`: The failure is tied to per-turn `successfulCronAdds` state not reflecting an actual scheduled cron side effect.

## Summary

Keep open: current main and v2026.6.11 still count only structured `cron` tool adds for `successfulCronAdds`, while the shell-driven `openclaw cron add` path is owned by the open linked fix candidate at https://github.com/openclaw/openclaw/pull/86064.

## What This Changes

The issue reports that successful cron reminder scheduling through shell/cron paths can still be followed by the contradictory unscheduled-reminder note.

## Best Possible Solution

Land or replace the linked fix with a narrow telemetry-producer change that counts successful shell-driven `openclaw cron add` results before the reply guard runs, with focused regression coverage and real behavior proof when practical.

## Reproduction Assessment

Yes, at source level: current main can create a cron through a shell command without incrementing `successfulCronAdds`, and the reply guard appends the note whenever reminder text has zero successful cron adds. I did not run a live Telegram or cron scenario in this read-only review.

## Solution Assessment

Yes, the best fix shape is to count successful shell-driven cron adds at the telemetry producer before the reply guard runs, rather than hiding the note only in Telegram delivery. The current linked PR targets that ownership boundary but remains open and unmerged.

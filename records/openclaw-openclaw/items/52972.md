## Summary

Keep open: current main and v2026.6.11 still count only structured cron-tool additions as successful reminder scheduling, so a shell-driven `openclaw cron add --at ...` can leave the reply guard with `successfulCronAdds === 0` and append the contradictory note.

## What This Changes

The issue asks OpenClaw to suppress the unscheduled-reminder note when a reminder was successfully scheduled through a cron command path.

## Best Possible Solution

Land a narrow producer-side fix that counts successful exec/bash `openclaw cron add` results before the reply guard runs, without adding a Telegram-only sanitizer or new config surface.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, at source level: current main counts structured `cron` add results but not exec/bash `openclaw cron add`, while the reply guard appends the note whenever reminder text has zero successful cron adds. I did not run a live Telegram scenario in this read-only review.

## Solution Assessment

Yes: the maintainable fix belongs at the telemetry producer that sets `successfulCronAdds`, not in a downstream channel sanitizer. The patch should narrowly parse the shell command and success result, then add regression coverage for successful, failed, and unrelated exec commands.

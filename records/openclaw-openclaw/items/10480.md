## Summary

Keep open: current main still hardcodes the Cloudflare AI Gateway onboarding path to Anthropic Messages and one Claude default, and the broader Cloudflare bridge issue overlaps but does not fully replace this specific Workers AI non-interactive onboarding request.

## What This Changes

Support Workers AI model selection during Cloudflare AI Gateway non-interactive onboarding.

## Best Possible Solution

Keep the Cloudflare provider plugin as the owner of the final behavior, either by adding a Workers AI endpoint/model selector with docs and tests or by explicitly documenting the generic custom-provider route as the supported Cloudflare Workers AI setup path.

Kind: product_direction

Question: Should Cloudflare Workers AI support be added to the bundled Cloudflare AI Gateway provider onboarding flow, or should OpenClaw document the generic custom-provider path as the supported Workers AI setup?

Rationale: Current code can support manual OpenAI-compatible provider config, but changing the provider plugin auth-choice/onboard behavior would add provider-facing setup and model-selection surface that maintainers have already labeled as needing product direction.

Likely owner: Vincent Koc

Owner reason: Current blame and recent docs/provider work put this person closest to the checked-in Cloudflare onboarding surface.

Owner confidence: high

Options:

- **Add provider-owned Workers AI mode (recommended):** Extend the Cloudflare AI Gateway plugin to write the Workers AI base URL, OpenAI-compatible API adapter, model list, and default model during onboarding.
- **Document custom-provider setup:** Keep the bundled Cloudflare AI Gateway provider Anthropic-only and publish a precise Workers AI custom-provider onboarding command and config example.
- **Fold into broader AIG bridge:** Track this only through the broader Cloudflare AI Gateway bridge design so onboarding lands together with REST/model-catalog semantics.

## Summary

Keep open: current main and v2026.6.11 still configure the Cloudflare auth choice as an Anthropic-only provider with one Claude default, while the existing generic custom-provider workflow is an undocumented workaround rather than equivalent Workers AI onboarding. The related REST and multi-provider requests remain open and only partially overlap this concrete setup requirement.

## What This Changes

Support selecting and configuring Cloudflare Workers AI models during non-interactive onboarding.

## Best Possible Solution

Preserve the shipped Anthropic mode and, if maintainers approve first-class support, add an explicit plugin-owned Workers AI mode whose endpoint, API type, model definition, auth semantics, catalog output, onboarding options, tests, and public documentation all share one canonical contract.

Rationale: The missing onboarding capability is proven, but the shipped provider is intentionally Anthropic-specific and the open REST and bridge proposals leave the permanent Cloudflare endpoint, auth, provider-identity, and model-ID contract unresolved.

Options:

- **Add compatible plugin mode (recommended):** Preserve existing Anthropic setups and add an explicitly selected Workers AI mode owned end-to-end by the Cloudflare plugin.
- **Document the generic workflow:** Keep the bundled provider Anthropic-only and publish an exact supported non-interactive custom-provider recipe for Workers AI.
- **Wait for the bridge contract:** Defer implementation until the broader multi-provider Cloudflare design chooses the endpoint, auth, and model-routing contract.

## Reproduction Assessment

Yes, at source level. Both current main and v2026.6.11 show that the Cloudflare non-interactive auth choice accepts only credentials and gateway metadata, then writes the fixed Anthropic/Claude configuration without a Workers AI model or endpoint selector.

## Solution Assessment

Unclear as proposed: the plugin boundary is the correct ownership layer, but a generic `--model` flag alone is insufficient because endpoint, API type, authentication, provider identity, and catalog metadata must change together. A backward-compatible explicit plugin mode is the best first-class shape; exact generic-provider documentation is the safer alternative if maintainers do not want to expand the bundled contract.

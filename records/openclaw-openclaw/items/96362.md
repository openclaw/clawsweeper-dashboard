## Summary

Keep open: this draft PR still changes a native hook execution path by default on Linux, lacks real Linux/systemd behavior proof, and has a concrete fail-open risk if the wrapper starts but the constrained scope cannot run the relay correctly.

## What This Changes

The PR wraps native hook relay commands in `systemd-run --user --scope` on Linux when `XDG_RUNTIME_DIR` and a `systemd-run` path are present, adds an environment override, and adds one command-builder test.

## Best Possible Solution

Make systemd scoping opt-in or viability-checked and fail-safe, preserve hook stdio behavior, and keep the canonical relay fan-out decision tied to the open relay-pressure issue and stronger open fix candidates.

## Reproduction Assessment

Yes for the PR-introduced defect: source inspection shows the wrapper is selected by path presence, and upstream Codex treats nonzero PreToolUse hook exits as failed hook runs without blocking. I did not run a live systemd user-scope failure reproduction.

## Solution Assessment

No as submitted: a systemd scope may be a plausible mitigation, but the default path needs viability checks, fail-safe fallback, stdio proof, and real Linux behavior proof before it is the best fix.

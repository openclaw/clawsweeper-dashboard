## Label Justifications

- `P1`: The PR targets real Codex native hook relay process pressure that can stall gateway RPCs and break agent workflows under user load.
- `merge-risk: 🚨 compatibility`: The default Linux native hook command shape changes whenever `systemd-run` is present and a user runtime is detected.

- `merge-risk: 🚨 availability`: If the user scope or fixed resource properties fail, Linux hook relay commands that previously ran plainly can fail across upgraded setups.

## Summary

Keep open: this focused bug-fix PR is not implemented on current main, but the patch still has a P1 fail-safe blocker because it selects `systemd-run` by path presence and can fail before the OpenClaw native relay policy code runs.

## What This Changes

The branch wraps Linux native hook relay commands in a user `systemd-run --scope` with fixed CPU, memory, and task limits when a user runtime and `systemd-run` path are present, plus a command-builder test.

## Best Possible Solution

Keep the original relay command as the safe default unless the exact scoped wrapper is viability-checked and proven, and treat systemd resource scoping as a maintainer-approved mitigation alongside the canonical relay fan-out work.

## Reproduction Assessment

Yes for the PR-introduced defect: source inspection shows the wrapper is selected by `systemd-run` path presence, while Codex treats nonzero PreToolUse exits as failed hook runs without blocking. I did not run a live systemd user-scope failure reproduction.

## Solution Assessment

No as submitted: a systemd scope is a plausible mitigation, but the default path needs viability checks, fail-safe fallback or opt-in behavior, and real Linux proof before it is the best fix.

## Label Justifications

- `P1`: The PR targets Codex native hook relay pressure that can stall gateway RPCs and availability, while the current patch can also skip relay policy on wrapper failure.
- `merge-risk: 🚨 compatibility`: The default Linux relay command shape changes whenever a user runtime and `systemd-run` path are detected, and an env override is added.

- `merge-risk: 🚨 availability`: The wrapper can make native hook relay commands fail on Linux setups where the plain relay command worked before.

## Summary

Keep open: the PR is a focused attempt to reduce native hook relay process contention, but the submitted default systemd wrapper can fail before the OpenClaw relay CLI runs, which bypasses the existing fail-closed/no-op relay responses and still lacks real Linux behavior proof.

## What This Changes

The PR wraps Linux native hook relay commands in `systemd-run --user --scope` with fixed CPU, memory, and task limits when a user runtime is detected, plus a command-builder unit test.

## Best Possible Solution

Make scoped execution fail-safe and viability-checked before any default use, or keep the plain relay as default while maintainers choose the broader relay fan-out direction in the canonical issue cluster.

## Reproduction Assessment

Yes for the PR-introduced defect: source inspection shows the wrapper is selected by path presence, while Codex treats nonzero PreToolUse exits as failed hook runs without blocking. I did not run a live systemd user-scope failure reproduction.

## Solution Assessment

No as submitted: a systemd scope is a plausible mitigation, but the default path needs viability checks, fail-safe fallback, and real Linux proof before it is the best fix.

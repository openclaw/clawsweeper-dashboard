## Summary

Current main and v2026.6.11 retain one queued-writer closure per distinct diagnostic path, but the named callers normally resolve process-level configured paths, the pinned append implementation closes each file handle, and no real current-main workload demonstrates growing path cardinality or material heap retention. Keep this issue open for focused evidence that a production caller changes these paths repeatedly within one gateway process; the linked exec-output report and broader Matrix heap report do not establish the same root cause.

## What This Changes

Investigate and bound retention of queued diagnostic file writers when distinct log paths accumulate.

## Best Possible Solution

Narrow the investigation to retained JavaScript registry entries, measure distinct paths and post-GC heap on a real current-main gateway, and if growth is confirmed let the path-owning diagnostic subsystem remove only idle, fully flushed writers while preserving one active serialization queue per path.

## Reproduction Assessment

Partly yes: source inspection gives a high-confidence path to demonstrate one retained writer closure per distinct path. It does not reproduce persistent file handles or material unbounded growth in a real current-main gateway because the named paths are process-level settings and each append closes its descriptor.

## Solution Assessment

No, the proposed generic WeakRef or LRU eviction is not the best demonstrated fix because it can split the per-path serialization queue. A lifecycle-owned idle release is safer, but only after a production dynamic-path source and measurable retained-memory growth are established.

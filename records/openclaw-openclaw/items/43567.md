## Summary

Keep open: the concrete pre-compaction memory-flush transcript leak was fixed by the merged memory PR and is present in the latest release, but current main still lacks a shared runtime/system audience policy and a dedicated Control UI/WebChat diagnostic presentation path for visible system-originated messages.

## What This Changes

The issue asks for runtime/system-originated messages to render as distinct system or diagnostic UI blocks instead of ordinary user or assistant chat bubbles.

## Best Possible Solution

Define one shared audience/provenance contract: agent-only internals stay hidden, while deliberately visible runtime notices render through a dedicated diagnostic/system treatment across Control UI/WebChat and TUI.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should visible runtime/system-originated messages be hidden by default, rendered as dedicated diagnostic/system blocks, or continue through ordinary chat grouping for some system rows?

Rationale: The source supports multiple implementation shapes, but the choice affects transcript projection, Control UI/WebChat rendering, TUI parity, and restart-continuation behavior, so automation should not pick the product policy by itself.

Likely owner: steipete

Owner reason: The strongest recent history is on Gateway display projection and system-event handling, which are central to the policy decision.

Owner confidence: medium

Options:

- **Define shared audience contract (recommended):** Choose a core hidden-vs-diagnostic audience model first, then implement Gateway projection and UI/TUI rendering from that contract.
- **Hide runtime internals:** Treat system/runtime-originated prompts as agent-only unless a source explicitly opts into user-visible diagnostics.
- **Style current system rows only:** Add a distinct system block for role `system` rows without changing visibility semantics, accepting that some agent-only text may still be exposed.

## Reproduction Assessment

Yes, at source level: Control UI can build and normalize system-role rows, but system roles fall through the generic `other` chat group rather than a dedicated system block. I did not run a live Control UI or TUI reproduction in this read-only review.

## Solution Assessment

No, a display-only colored block is not the best standalone fix. The maintainable path is to decide the runtime audience/provenance contract first, then wire Gateway projection and surface-specific rendering to that contract.

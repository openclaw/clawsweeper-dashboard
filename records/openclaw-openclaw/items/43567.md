## Summary

Keep open: the concrete pre-compaction memory-flush leak was fixed by the merged memory PR, but current main and the latest release still lack a shared runtime/system audience policy and a dedicated Control UI/WebChat diagnostic presentation for deliberately visible system-originated messages.

## What This Changes

The issue requests that internal system/runtime messages shown in Control UI or TUI be visually separated from normal user and assistant chat bubbles.

## Best Possible Solution

Define one shared audience/provenance contract: agent-only internals stay hidden, while deliberately visible runtime notices render through a dedicated diagnostic/system treatment across Control UI/WebChat and TUI.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should visible runtime/system-originated messages be hidden by default, rendered as dedicated diagnostic/system blocks, or continue through ordinary chat grouping for some system rows?

Rationale: The source supports several implementation shapes, but the choice affects transcript projection, Control UI/WebChat rendering, TUI parity, and restart-continuation behavior, so automation should not choose the product policy by itself.

Likely owner: steipete

Owner reason: The strongest product-boundary history is in Gateway display projection and system-event handling, which are central to the policy decision.

Owner confidence: medium

Options:

- **Define Shared Audience Contract (recommended):** Choose a core hidden-vs-diagnostic audience model first, then implement Gateway projection and UI/TUI rendering from that contract.
- **Hide Runtime Internals:** Treat system/runtime-originated prompts as agent-only unless a source explicitly opts into user-visible diagnostics.
- **Style Current System Rows Only:** Add a distinct system block for role `system` rows without changing visibility semantics, accepting that some agent-only text may still be exposed.

## Reproduction Assessment

Yes, at source level: Control UI preserves role `system` but renders it through the generic `other` chat-group path, while Gateway projection lacks a shared visible diagnostic/system audience branch. I did not run a live Control UI or TUI reproduction in this read-only review.

## Solution Assessment

No, a display-only colored block is not the best standalone fix. The maintainable path is to decide the runtime audience/provenance contract first, then wire Gateway projection and surface-specific rendering to that contract.

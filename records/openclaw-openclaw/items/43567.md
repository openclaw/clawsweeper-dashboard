## Summary

Keep open: current main fixes the concrete pre-compaction memory-flush leak, but the broader request remains because generic visible system/runtime rows still render through normal chat grouping instead of a first-class diagnostic/system block.

## What This Changes

Request to render internal system/runtime messages in a visually distinct UI treatment instead of ordinary user or assistant chat bubbles.

## Best Possible Solution

Define one shared audience/provenance contract: agent-only internals stay hidden, while deliberately visible runtime notices render through a dedicated diagnostic/system treatment across Control UI/WebChat and TUI.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should intentionally visible runtime/system-originated rows be hidden by default, rendered as a dedicated diagnostic block, or left as ordinary transcript messages with lighter styling?

Rationale: The source has enough provenance and UI seams to implement several behaviors, but choosing hidden versus visible diagnostic semantics affects transcript projection, WebChat/Control UI rendering, TUI parity, and restart-continuation behavior.

Likely owner: steipete

Owner reason: This decision primarily affects the display projection and Control UI grouping surfaces where recent history points to this owner signal.

Owner confidence: medium

Options:

- **Define Shared Audience Contract (recommended):** Choose a core hidden-vs-diagnostic audience model first, then implement Gateway projection and UI/TUI rendering from that contract.
- **Hide Runtime Internals:** Treat system/runtime-originated user-role rows as agent-only unless explicitly whitelisted for user-visible diagnostics.
- **Style Visible System Rows Only:** Add a distinct visual block for role system rows without changing which runtime messages are visible, accepting the risk that agent-only prompts may still be exposed.

## Reproduction Assessment

Yes, at source level for the remaining gap: generic system-role rows can still be built as normal message items and rendered through the generic other chat group path. I did not run a live Control UI/TUI reproduction in this read-only review.

## Solution Assessment

No, a display-only colored block is not the best standalone fix. The maintainable solution is to choose the runtime audience/provenance contract first, then wire projection and surface-specific rendering to that contract.

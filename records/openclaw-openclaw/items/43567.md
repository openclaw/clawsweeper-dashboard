## Summary

Keep open: current main fixed the concrete pre-compaction memory-flush leak, but the broader runtime/system-message presentation request remains because system-role rows still flow through generic chat grouping rather than a first-class diagnostic block.

## What This Changes

Render internal system/runtime messages in a distinct UI treatment instead of normal user or assistant chat bubbles.

## Best Possible Solution

Define one shared audience/provenance contract: agent-only internals stay hidden, while deliberately visible runtime notices render through a dedicated diagnostic/system treatment across Control UI/WebChat and TUI.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should visible runtime/system-originated messages be hidden by default, rendered as a dedicated diagnostic block, or continue through ordinary chat grouping?

Rationale: The source supports several implementation shapes, but the choice affects transcript projection, Control UI/WebChat rendering, TUI parity, and restart-continuation behavior.

Likely owner: steipete

Owner reason: The most relevant recent history is on Gateway display projection and Control UI chat rendering, which are central to this product decision.

Owner confidence: medium

Options:

- **Define Shared Audience Contract (recommended):** Choose a core hidden-vs-diagnostic audience model first, then implement projection and rendering from that contract.
- **Hide Runtime Internals:** Treat system/runtime-originated prompts as agent-only unless a source explicitly opts into user-visible diagnostics.
- **Style Current System Rows:** Add a distinct block for role system rows without changing visibility semantics, accepting the risk that agent-only text may still be exposed.

## Reproduction Assessment

Yes, at source level: current Control UI can create and normalize system-role rows, but renders them through the generic `other` chat group instead of a dedicated system block. I did not run a live Control UI/TUI reproduction in this read-only review.

## Solution Assessment

No, a display-only colored block is not the best standalone fix. The maintainable path is to decide the runtime audience/provenance contract first, then wire Gateway projection and surface-specific rendering to that contract.

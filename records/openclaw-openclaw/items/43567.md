## Summary

Keep open: current main fixes the concrete pre-compaction memory-flush leak, but the broader UI/product request remains because system/runtime rows can still enter normal chat item grouping instead of a first-class diagnostic block.

## What This Changes

Request to render internal system/runtime messages in a distinct UI treatment instead of normal user/assistant chat bubbles.

## Best Possible Solution

Define a shared audience/provenance contract first: hide agent-only internals, and render deliberately visible runtime notices through a dedicated diagnostic/system block across Control UI/WebChat and TUI.

Question: Should OpenClaw hide internal/runtime-originated messages by default, or expose selected runtime notices in a dedicated diagnostic/system UI block?

Rationale: Current source can still render system-shaped rows through normal chat grouping, but deciding which runtime messages are visible is a product/API boundary choice rather than a mechanical UI-only fix.

Likely owner: steipete

Owner reason: The current UI and Gateway display-projection history points to steipete as the strongest available routing candidate for the cross-surface product decision.

Owner confidence: medium

Options:

- **Audience contract first (recommended):** Define agent-only versus visible-diagnostic provenance, hide agent-only internals, then render only intentional runtime notices in a distinct system block.
- **Hide all internals from chat:** Treat system/runtime messages as logs or diagnostics only and keep the main transcript strictly user/assistant visible.
- **Style current system rows only:** Add a visual system treatment for existing system-role rows without changing upstream audience/provenance semantics.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: current main still normalizes system-role rows into message groups and inserts a system history notice as a normal message item, while Gateway projection only hides selected internals; no live UI run was performed in this read-only review.

## Solution Assessment

No. A display-only colored block is not the best standalone fix; the maintainable solution is to choose the runtime audience/provenance contract first, then wire projection and surface-specific rendering to that contract.

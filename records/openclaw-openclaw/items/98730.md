## What This Changes

The PR adds a live session-state block to `/mcp show` using existing MCP runtime peek APIs and expands command tests for connected, diagnostic, stale, disabled, cold-catalog, and no-runtime cases.

## Best Possible Solution

Compute session MCP config staleness for any existing runtime, surface stale state before per-server disabled/pending/connected labels, then add redacted real `/mcp show` proof from an actual warm session.

## Reproduction Assessment

Yes, source-level: existing session runtimes retain their creation-time MCP config and the PR skips fingerprint comparison when `peekCatalog()` is null, so config changes before cataloging are reported as pending/disabled instead of stale.

## Solution Assessment

No as-is; the maintainable shape is to mirror the existing `tools.effective` order by checking fingerprint staleness before catalog-specific rendering.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.86

Full review comments:

- **[P2] Report stale runtimes before cold or disabled state:** `src/auto-reply/reply/commands-mcp.ts:78-82`
  - body: Here `stale` is only computed when a catalog is already warm, and `renderMcpServerLiveLine` lets current-config `enabled:false` win before stale. Existing session runtimes keep the MCP config captured at creation, while `/mcp set|unset` writes config without retiring them, so after a user edits or disables a server before the runtime catalogs tools, `/mcp show` can say it is pending or disabled even though the next tool use will still use the stale runtime config. Compute the fingerprint for any existing runtime and let stale state outrank these per-server labels.
  - confidence: 0.88

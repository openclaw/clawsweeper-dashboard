Keep open: the branch still has a source-proven stale-session reporting bug and the external real behavior proof gate is not satisfied. The code can report a stale MCP runtime as disabled or not yet discovered because it only computes staleness after a catalog is warm.

## What This Changes

The PR adds a read-only live MCP session-state block to `/mcp show` and extends MCP command tests for connected, diagnostic, stale, disabled, cold-catalog, sandboxed workspace, and no-runtime cases.

## Best Possible Solution

Compute session MCP staleness for any existing runtime before rendering per-server labels, then require redacted real warm-session command proof before merge.

## Reproduction Assessment

Yes, source-level: the PR skips fingerprint comparison when `peekCatalog()` is null, so an existing runtime whose config changed before cataloging is rendered as pending or disabled instead of stale.

## Solution Assessment

No as-is; the maintainable shape is to mirror the existing `tools.effective` order by checking runtime fingerprint staleness before catalog-specific rendering.

Full review comments:

- **[P2] Report stale runtimes before cold or disabled state:** `src/auto-reply/reply/commands-mcp.ts:78-82`
  - body: Here `stale` is only computed when a catalog is already warm, while `renderMcpServerLiveLine` can return disabled or pending before stale. Existing session runtimes keep the MCP config captured at creation, and `/mcp set|unset` writes config without retiring them, so after a user edits or disables a server before cataloging, `/mcp show` can say the runtime is pending/disabled even though the next tool use will use stale runtime config. Compute the fingerprint for any existing runtime and let stale outrank these per-server labels.

## Label Justifications

- `P1`: A source-confirmed queue-progress defect can block real Android chat submissions after reconnect.
- `merge-risk: 🚨 compatibility`: The PR changes the persistent Room schema and upgrade path for queued user input.
- `merge-risk: 🚨 message-delivery`: The patch rewrites dispatch, retry, FIFO blocking, and retirement behavior for every Android chat send.
- `merge-risk: 🚨 session-state`: Queue progress depends on associating accepted rows, run completion, and canonical history with the correct session.

## Summary

The history-proof durability model is well motivated and the primary offline/reboot flow has credible real proof, but the current head can indefinitely block a background session's queue because flushed sends are only adopted when their session is visible.

## What This Changes

The PR journals every Android chat submission and its attachments in Room, retires rows only after canonical-history proof, adds non-destructive migrations and bounded attachment storage, pins routing, and parks ambiguous or reconnect-crossing commands for explicit action.

## Best Possible Solution

Keep journal-all submission and canonical-history retirement, but give every dispatched row a session-independent completion/reconciliation owner until it is proven delivered or visibly parked, with v1/v2 migration coverage preserved on the rebased tree.

## Reproduction Assessment

Yes. Queue two messages for a session that is not currently visible, allow the first run to remain in flight beyond the two immediate history reads, and observe that its accepted row lacks local ownership and blocks the second row.

## Solution Assessment

No in the current head. Canonical-history proof is the right retirement invariant, but queue completion must be owned independently of which session the UI currently displays.

## Label Justifications

- `P1`: The PR targets an urgent cron workflow regression where successful isolated cron work can be reported as a delivery-target failure in no-channel setups.
- `merge-risk: 🚨 compatibility`: The patch changes existing cron run status/error semantics for implicit no-channel delivery from `error` to `ok`/not-delivered.
- `merge-risk: 🚨 message-delivery`: The patch changes when cron delivery failures are treated as visible failed delivery versus silent not-delivery, which affects operator alerts and retry expectations.

## Summary

Keep open: current main still has the no-channel implicit cron delivery failure path, and this PR is a useful candidate fix, but it is not merge-ready until contributor real behavior proof and maintainer acceptance of the status-semantic change are present.

## What This Changes

The branch adds an explicit-target dispatch predicate, downgrades unresolved implicit `last` delivery with no channel to ok/not-delivered, aligns preview text, preserves delivered=false during run finalization, and adds focused cron tests.

## Best Possible Solution

Land the narrow no-channel cron delivery fix only after redacted real behavior proof, a small CLI docs alignment, and maintainer acceptance of the compatibility-sensitive status change.

## Reproduction Assessment

Yes from source inspection: default detached cron output jobs request `announce` to `last`, no previous channel returns `ok:false`, and dispatch currently hard-fails unresolved non-best-effort delivery. I did not run a live local no-channel cron scenario in this read-only review.

## Solution Assessment

Yes for a bounded mitigation of the no-channel implicit route: it keeps explicit and channel-resolved failures fail-closed while preserving output as ok/not-delivered. It still needs real behavior proof, docs alignment, and maintainer acceptance because broader warning/default policy remains a separate product decision.

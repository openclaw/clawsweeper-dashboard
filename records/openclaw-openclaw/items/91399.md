## Label Justifications

- `P1`: The PR targets a user-facing cron regression where successful isolated cron work can be reported as a delivery-target failure in no-channel setups.
- `merge-risk: 🚨 compatibility`: The patch changes existing cron run status and error semantics for implicit no-channel delivery from error to ok/not-delivered.
- `merge-risk: 🚨 message-delivery`: The patch changes when cron delivery failures are treated as visible failed delivery versus silent not-delivery, affecting operator alerts and retry expectations.

## Summary

Keep open: current main and v2026.6.11 still have the unresolved no-channel cron delivery hard-fail path, and this PR is the active candidate fix, but it still needs contributor real-behavior proof and maintainer acceptance of the compatibility-sensitive ok/not-delivered semantics before merge.

## What This Changes

The PR changes isolated cron delivery dispatch, final run metadata, preview formatting, and regression tests so unresolved implicit announce-to-last with no channel becomes ok/not-delivered while explicit or channel-resolved target failures stay fail-closed.

## Best Possible Solution

Land the narrow no-channel cron delivery fix only after redacted real behavior proof, docs alignment, and explicit maintainer acceptance of the compatibility-sensitive status change; keep the broader warning/default policy work separate.

## Reproduction Assessment

Yes. Source inspection on current main shows detached cron output defaults to announce/last, no-channel target resolution can return ok:false, and non-best-effort dispatch hard-fails that unresolved target; I did not run the live local Control UI scenario in this read-only review.

## Solution Assessment

Yes for a bounded mitigation of the no-channel implicit route: the PR keeps explicit and channel-resolved failures fail-closed while preserving output as ok/not-delivered. It still needs real behavior proof, docs alignment, and maintainer acceptance because broader warning/default policy remains separate.

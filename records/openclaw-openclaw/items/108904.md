## Label Justifications

- `P1`: The PR addresses an observed reconnect loop that repeatedly invokes an expensive RPC and has caused real gateway memory pressure and watchdog restarts, but the current patch leaves a common window-focus path unresolved.

## Summary

Keep this PR open: the shared refresh-policy direction is sound, but the implementation does not actually require window focus, so a stale reconnect in a visible tab belonging to an unfocused browser window can still trigger the expensive usage requests the PR is meant to suppress. The protected `maintainer` label and current merge conflict also require explicit maintainer handling.

## What This Changes

Adds a shared five-minute usage refresh policy for the Control UI Usage and Profile pages, with reconnect, visibility, focus, manual-refresh, request-coalescing, and regression-test changes.

## Best Possible Solution

Extend the shared policy to require both document visibility and window focus for automatic reconnect, poll, and activation refreshes; keep manual refresh unconditional, cover visible-but-unfocused reconnects on both pages, rerun the Control UI browser scenario, and then rebase onto current main.

Yes, from source: use a stale payload in a selected tab whose browser window is unfocused but whose document remains visible, then reconnect the websocket; the helper receives `visible: true` and returns `fetch` because focus is not represented.

## Solution Assessment

No, not yet. A single shared policy is the right ownership boundary, but it must model both visibility and actual window focus to implement the stated behavior and close the reported reconnect-loop path.

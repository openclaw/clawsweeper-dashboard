## Summary

Keep this issue open, narrowed to documentation and product direction. Current main already delegates multiline editing to `pi-tui`, whose default behavior supports Shift+Enter newline with terminal-specific limitations, but OpenClaw’s TUI docs and help surface still advertise only Enter-to-send and expose no send/newline preference.

Likely related people:
- `steipete` — high confidence; introduced and repeatedly maintained the TUI editor wrapper and recently maintained its documentation.
- `vincentkoc` — medium confidence; recently changed the editor wrapper and other TUI behavior.

## What This Changes

Document reliable multiline composition in the TUI and decide whether to expose configurable send/newline keybindings while preserving Enter-to-send by default.

## Best Possible Solution

Document Shift+Enter, fallback behavior, and terminal limitations in the TUI guide and in-product help; only add one canonical TUI send-key preference if maintainers explicitly sponsor the additional config surface, preserving Enter-to-send as the default.

- **Document Existing Behavior (recommended):** Add TUI docs and in-product help for Shift+Enter, terminal support, and fallback behavior without adding another OpenClaw setting.
- **Add One TUI Preference:** Define and persist a canonical send-key mode, wire it through the editor dependency, and cover fresh and upgraded behavior with focused tests.

## Reproduction Assessment

Yes, at source level: the upstream editor owns newline handling, while current OpenClaw docs/help omit it and `TuiOptions` has no configurable send-key bridge. A live runtime failure is not established because Shift+Enter support depends on the terminal’s modified-key protocol.

## Solution Assessment

No single implementation path is established yet. Documentation of the existing behavior is the narrowest maintainable first step; a persistent preference is appropriate only after maintainers accept the extra configuration contract.

## Summary

Keep this PR open: it fixes the error-payload case, but it also changes every non-string successful `canvas.eval` value into `{ ok: false }`, which can falsely report a successful evaluation as a failure. The PR body currently provides test output rather than an after-fix Canvas/node invocation, so real behavior proof is still required before merge.

## What This Changes

The branch widens Canvas `eval` payload handling and returns an error response for non-string results or gateway error payloads instead of falling through to generic success.

## Best Possible Solution

Separate gateway error detection from result typing: return failure only for an explicit error envelope, preserve successful non-string results under the existing successful response contract, and prove both paths with a real Canvas/node invocation.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes from source: any `canvas.eval` response with a non-string `payload.result` and no `payload.error` reaches the changed fallback and is returned as `ok: false`; a live node run is still needed to establish which non-string values occur in practice.

## Solution Assessment

No. Surfacing explicit gateway errors is the right direction, but using result type as the failure discriminator conflates successful values with errors; the narrower solution is to branch on the explicit error envelope first.

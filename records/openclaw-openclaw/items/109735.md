## Summary

Keep this PR open: the reliability goal is reasonable, but applying one 30-second deadline to every shared `gh` invocation has not been validated against long-running callers or demonstrated in a real setup.

## What This Changes

The PR adds a 30-second default timeout to `execPlainGh`, `execGhApiRead`, and `spawnPlainGh`, while allowing callers to override it through `options.timeout`.

## Best Possible Solution

Use operation-aware deadlines: keep a finite short default for one-shot API reads, explicitly classify longer or waiting commands, and lock both behaviors down with focused tests and redacted live terminal proof.

Rationale: The correct timeout is an operational policy choice because this shared helper serves both quick API reads and potentially longer maintainer automation, and the PR does not establish that one deadline is safe for all callers.

Options:

- **Classify callers first (recommended):** Audit callers, retain a bounded default for short API operations, and set explicit longer or disabled deadlines for commands designed to wait.
- **Accept one global deadline:** Adopt 30 seconds for all helpers after adding tests and real proof that representative PR, release, and inherited-stdio operations remain usable.
- **Keep caller-owned timeouts:** Do not add a shared default; add deadlines only to specific network operations whose expected duration and failure handling are known.

## Reproduction Assessment

Yes at source level: current `main` passes no timeout to these synchronous subprocess calls, so a non-returning `gh` process can block its caller. The PR does not provide a live stalled-network reproduction or after-fix observation.

## Solution Assessment

Unclear: bounding network-backed subprocesses is appropriate, but a single default across every caller is not yet shown to be the narrowest safe fix; operation-specific deadlines may better preserve long-running workflows.

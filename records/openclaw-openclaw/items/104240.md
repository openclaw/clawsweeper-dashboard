## Summary

The LINE behavior is correct and convincingly proven, but the previous exact-head blocker remains: this PR adds independently indexed `results` and `kinds` arrays to a documented plugin SDK helper, allowing invalid ID-kind associations to type-check and silently produce misleading receipts.

## What This Changes

The PR captures every ordered LINE push and reply message ID, maps each ID to its outbound message kind, and adds optional per-result kinds to the shared receipt normalizer.

## Best Possible Solution

Keep the unified, live-proven LINE push/reply path, but make invalid ID-kind alignment unrepresentable by carrying each optional kind on its corresponding flat receipt input result; nested receipts and the existing aggregate-kind fallback should remain unchanged.

## Reproduction Assessment

Yes. Current main directly returns literal `push` and `reply` receipt IDs and discards the successful SDK response IDs; the contributor's exact-head credential-backed output demonstrates the corrected two-message provider paths.

## Solution Assessment

No, not in its current public API shape. Capturing all ordered LINE IDs is the correct behavioral fix, but each kind should travel with its receipt result rather than through a separately ordered array.

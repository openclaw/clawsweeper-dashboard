## Summary

Keep open. The PR targets a real iOS PTT race, but the current patch holds the new FIFO for the full one-shot capture, so `talk.ptt.cancel` and `talk.ptt.stop` queue behind an active one-shot instead of interrupting it; it also still lacks real iOS behavior proof.

## What This Changes

The branch wraps iOS Talk invokes in a cancellation-aware FIFO, adds cancellation cleanup for one-shot push-to-talk, and refreshes native i18n source locations.

## Best Possible Solution

Keep one canonical iOS PTT ownership path, but narrow the critical section so queued starts/one-shots are cancellation-aware while stop/cancel can interrupt an active one-shot; add focused regression coverage or equivalent Swift proof plus redacted device/simulator evidence.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, source-reproducible: on the PR head `talk.ptt.once` acquires the FIFO before it awaits `runPushToTalkOnce`, so a separate `talk.ptt.cancel` or `talk.ptt.stop` must wait for that one-shot to finish before it can call the cleanup path. I did not run an iOS simulator or device.

## Solution Assessment

No. The safer fix is to serialize capture preparation and queued starts/one-shots while preserving stop/cancel as interrupt paths, matching the Android sibling invariant rather than holding one FIFO across the full capture.

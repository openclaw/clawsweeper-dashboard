## Label Justifications

- `P2`: This is a normal-priority data integrity bug in the usage log path with limited blast radius and a clear narrow fix.
- `impact:data-loss`: Invalid transcript timestamps can be returned as non-finite or serialized-null usage log data, corrupting the reported session usage record.
- `maturity:stable`: The affected gateway usage API surface belongs to Gateway runtime, which is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and the latest release still have the unguarded `loadSessionLogs` string timestamp parse, and two open PRs already reference this issue as candidate fixes.

## What This Changes

Guard `loadSessionLogs` transcript string timestamp parsing so invalid date strings cannot propagate non-finite timestamps into usage log responses.

## Best Possible Solution

Review and land one canonical linked PR that guards the parse and adds focused `loadSessionLogs` regression coverage, then close the duplicate candidate PR.

## Reproduction Assessment

Yes at source level: current main directly assigns `new Date(parsed.timestamp).getTime()` in `loadSessionLogs`, and Node confirms an unparseable string produces `NaN` that serializes as `null`. I did not run a full session-file gateway repro in this read-only review.

## Solution Assessment

Yes, a finite/NaN guard in `loadSessionLogs` is the narrow maintainable fix; the best version should reuse or mirror the existing guarded `parseTimestamp` behavior and add a regression test. Because open closing PRs already exist, the next action is review and land one of them rather than queue another fix.

## Summary

Keep open: current main still returns a non-finite timestamp from `loadSessionLogs` when the top-level transcript timestamp is an unparseable string, and the adjacent merged date-validation PRs do not touch this log parser path.

## What This Changes

The issue requests a finite/NaN guard for string timestamp parsing in session cost usage log loading.

## Best Possible Solution

Normalize `loadSessionLogs` timestamps through the existing guarded timestamp parser, or an equivalent finite-number helper, and add regression coverage that invalid top-level strings fall back without returning `NaN` or JSON `null`.

## Reproduction Assessment

Yes at source level: current main directly assigns `new Date(parsed.timestamp).getTime()` in `loadSessionLogs`, and Node confirms an unparseable string produces `NaN` that serializes as `null`. A full runtime repro was not run because this review is read-only.

## Solution Assessment

The requested NaN guard is a valid narrow fix, but the best implementation is to reuse or mirror the existing guarded `parseTimestamp` helper so invalid strings, numeric message timestamps, and date-valid ranges follow one rule.

Do not broaden this into usage RPC date-range validation, cron timestamp validation, UI refactors, or `CHANGELOG.md` edits; those adjacent paths are already covered by https://github.com/openclaw/openclaw/pull/94096, https://github.com/openclaw/openclaw/pull/93903, and https://github.com/openclaw/openclaw/pull/93745.

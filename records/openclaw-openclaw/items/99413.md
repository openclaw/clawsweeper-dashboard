## Summary

Keep open: current main and the latest release still have the unguarded session log timestamp parse, and two open linked PRs already claim the narrow fix, so this issue should stay open until one fix lands.

## What This Changes

The issue requests a `Number.isNaN` guard after parsing string timestamps in session cost/usage log handling so invalid strings fall back instead of returning `NaN`.

## Best Possible Solution

Land one narrow fix that reuses or mirrors the existing guarded timestamp parser and adds a focused `loadSessionLogs` regression test for invalid string timestamps.

## Reproduction Assessment

Yes, at source level: current main directly assigns `new Date(parsed.timestamp).getTime()` in `loadSessionLogs`, and a bad date string produces `NaN` that serializes as JSON `null`. I did not run a full gateway repro because this review is read-only.

## Solution Assessment

Yes, the narrow timestamp finite-value guard is the right repair shape; the best implementation should reuse or mirror the existing guarded `parseTimestamp` behavior and add regression coverage rather than adding a broader product change.

- `impact:auth-provider`: The reported failure is an authentication and operator-scope transition from a loopback token path to a paired-device identity.

## Summary

Keep this issue open. The report gives a concrete, repeatable idle-reconnect symptom in the exec-approval path, and current documentation confirms that direct loopback clients may use the shared gateway token while approval resolution requires `operator.approvals`; no merged fix or linked implementation PR establishes that current main preserves that authentication mode across reconnects.

## What This Changes

Repair the exec-approval runtime so an idle WebSocket reconnect to a loopback token-authenticated gateway uses the same approval-runtime token authentication as the initial connection instead of failing the first exec request with a pairing error.

## System Context

Exec approval registration connects a local runtime to the Gateway so pending command approvals can be presented and resolved. The Gateway authenticates that connection, checks its operator scopes, and then delivers the approval workflow back to the requesting exec call.

## Architecture Diagram

flowchart LR
  A[Exec request needs approval] --> B[Approval runtime]
  B --> C[Loopback WebSocket connection]
  C --> D[Gateway authentication]
  D --> E[Operator approvals scope check]
  E --> F[Approval request or pairing error]
  F --> G[Exec call result]

## Best Possible Solution

Keep the loopback approval-runtime authentication decision stable for the lifetime of the runtime or deterministically recompute it from the persisted local socket configuration on every reconnect; add focused coverage for both initial connection and post-idle reconnect, while retaining device pairing for non-loopback clients.

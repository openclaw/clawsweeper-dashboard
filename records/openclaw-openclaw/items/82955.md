## Summary

Current main still downloads and executes the Homebrew installer without a content gate, so this PR remains necessary. The rebased patch has convincing proof and no discrete correctness defect, but its new fail-closed shebang contract needs explicit installer/security ownership before merge.

## What This Changes

The PR adds download-failure guards and a shared nonempty/shebang validator before four remotely downloaded Homebrew and NodeSource scripts execute, with a shell proof harness and updated installer test mocks.

## Best Possible Solution

Keep one centralized download-success and content-validation gate for all remote Bash execution, then land it after owners explicitly accept either the strict shebang invariant or a more semantic Bash-validation contract, with the installer suite retaining the regression cases.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw permanently require every remotely downloaded Homebrew and NodeSource setup script to begin with `#!`, failing installation if an upstream serves otherwise-valid Bash in another format?

Rationale: The patch is technically coherent and improves rejection of error bodies, but the byte-level shebang requirement creates a new fail-closed compatibility contract with third-party installer endpoints that code review and CI cannot authorize on behalf of installer/security owners.

Likely owner: steipete

Owner reason: The repository identifies this handle as the overall product owner, and this choice changes the supported installer trust and failure boundary.

Owner confidence: medium

Options:

- **Approve the strict shebang gate (recommended):** Land the current validator and accept that any non-shebang upstream response stops installation until OpenClaw or the upstream adjusts.
- **Use semantic Bash validation:** Keep the explicit download guards and nonempty check, but replace the byte-level requirement with an owner-approved Bash syntax/content validation rule that permits valid shebang-less scripts.
- **Limit hardening to download failures:** Merge only mandatory download-status checks and defer content validation, preserving maximum upstream compatibility but leaving HTTP-200 error bodies unguarded.

## Reproduction Assessment

Yes. Current main visibly downloads and executes the remote file without a content gate, and the supplied production-function harness demonstrates the bad-response and failed-download paths on Bash 3.2.

## Solution Assessment

Unclear pending owner intent. A centralized guard is the right boundary, but requiring `#!` is stricter than `/bin/bash file` itself and therefore needs an explicit compatibility/security decision rather than reviewer inference.

## Summary

Keep open: current main and v2026.6.11 still model trajectory rows as timestamped events rather than measured spans, and current OTel still exports `openclaw.context.assembled` with duration 0. The linked OTel latency work overlaps but is still open and conflicting, so it is not an implemented or superseding fix.

## What This Changes

The issue requests duration/start-end instrumentation for trajectory and telemetry rows such as `context.compiled`, `prompt.submitted`, `tool.call`, `tool.result`, and `session.started`.

## Best Possible Solution

Define a bounded trajectory timing contract, add measured duration data only for operations with a real lifecycle, and document any rows that intentionally remain point-in-time events.

## Reproduction Assessment

Yes, source-reproducible: current main writes trajectory runtime and transcript rows with one timestamp and no duration/start/end fields, and OTel context assembly still uses a hard-coded zero duration. I did not run a live agent trace in this read-only review.

## Solution Assessment

Unclear until maintainers choose the schema direction. Adding measured durations is the right end state for real lifecycle operations, but forcing synthetic nonzero durations onto point-in-time events would likely be the wrong model.

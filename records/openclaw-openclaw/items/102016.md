## Summary

Keep open: current main and v2026.6.11 still model trajectory rows as timestamped events, and the OTel context-assembled span is still emitted with zero duration, so the observability gap remains. A maintainer should decide the trajectory event-versus-span contract before a fix changes exported diagnostic data.

## What This Changes

The issue requests measured duration/start-end instrumentation for trajectory and telemetry events such as context.compiled, prompt.submitted, tool.call, tool.result, and session.started.

## Best Possible Solution

Define a bounded trajectory timing contract, add real measured duration data only for lifecycle operations, and document which rows intentionally remain point-in-time events.

- **Add a trajectory timing contract (recommended):** Keep this issue open and require a focused design/fix that adds durationMs or start/end fields for real lifecycle operations with tests and docs.
- **Keep trajectory event-only:** Leave trajectory JSONL as event-only and document that OTel spans, not trajectory rows, own duration analysis.
- **Split by event family:** Track runtime lifecycle timing separately from transcript-derived tool call/result reconstruction so each event family gets the right schema.

## Reproduction Assessment

Yes. Source inspection shows trajectory runtime/Codex records use one timestamp and no duration/start/end fields, while OTel context.assembled is still exported with duration 0.

## Solution Assessment

Unclear until maintainers choose the schema direction. Measured durations are the right end state for real lifecycle operations, but synthesizing nonzero durations for point-in-time events may be the wrong model.

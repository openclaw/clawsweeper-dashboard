## Summary

Keep open: current main and the latest release still model trajectory bundle rows as single-timestamp events, and the OTel context assembly span still uses a hard-coded zero duration. The related latency-decomposition PR partially overlaps but is open, conflicting, and does not settle the trajectory JSONL event-versus-span schema.

## What This Changes

The issue asks OpenClaw to add measured duration instrumentation to trajectory/telemetry events such as context compilation, prompt submission, tool calls/results, and session startup.

## Best Possible Solution

Define a bounded trajectory timing contract, then add measured duration data only for lifecycle operations while documenting any rows that intentionally remain point-in-time events.

Options:

- **Define measured trajectory spans (recommended):** Keep this issue open and approve a focused design that adds `durationMs` or start/end fields for real lifecycle operations with tests and docs.
- **Keep trajectory event-only:** Leave trajectory JSONL as a point-event support bundle and route latency measurement to OTel diagnostics, with docs clarifying that distinction.
- **Split runtime and transcript timing:** Measure runtime lifecycle events first and track transcript-derived tool call/result timing as a separate schema decision.

## Reproduction Assessment

Yes. Source inspection on current main shows trajectory runtime and transcript rows have one timestamp and no duration/start/end fields, including the reported context, prompt, session, and tool event paths; I did not run a live agent trace in this read-only review.

## Solution Assessment

Unclear until maintainers choose the schema direction. Adding measured durations is the right end state for lifecycle operations, but synthetic nonzero durations for truly point-in-time events would be a weaker model.

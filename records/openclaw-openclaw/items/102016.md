## Summary

Keep open: current main and v2026.6.11 still expose trajectory rows as single-timestamp events, so the reported duration gap remains real and needs a maintainer decision on trajectory event-versus-span semantics before implementation.

## What This Changes

The issue asks for duration instrumentation on trajectory telemetry rows such as context, prompt, tool, and session events that currently appear as zero-duration spans downstream.

## Best Possible Solution

Define a bounded trajectory timing contract, then add measured duration data only for operations with a real lifecycle while documenting event-only rows that intentionally remain point-in-time.

Options:

- **Add measured trajectory durations (recommended):** Implement duration or start/end fields for real lifecycle operations such as context compilation, prompt submission, model completion, and session lifecycle with docs and tests.
- **Keep trajectory event-only:** Leave trajectory JSONL as point events and update docs to make duration analysis live only in OTel and related latency diagnostics.
- **Split by event family:** Track runtime lifecycle timing separately from transcript-derived tool call/result reconstruction so each schema gets the right semantics.

## Reproduction Assessment

Yes. Source inspection shows current main writes trajectory runtime and transcript rows with one `ts` timestamp and no start/end or duration field, including the reported context, prompt, tool, and session event paths.

## Solution Assessment

Unclear until maintainers choose the trajectory schema direction. Measured durations are the right end state for lifecycle operations, but synthetic nonzero durations for transcript point events may be the wrong model.

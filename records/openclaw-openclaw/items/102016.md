## Summary

Keep open: current main and the latest release still export trajectory rows as timestamped events with no duration contract, so the reported observability gap remains. This should stay in maintainer review because turning trajectory rows into duration-bearing spans changes the diagnostic schema and overlaps with narrower open timing work.

## What This Changes

The issue requests duration instrumentation for trajectory rows such as `context.compiled`, `prompt.submitted`, `tool.call`, `tool.result`, and `session.started`.

## Best Possible Solution

Define a bounded trajectory timing contract, then add measured duration data only for operations with a real lifecycle while documenting event-only rows that intentionally remain point-in-time.

## Reproduction Assessment

Yes, source-reproducible: current main writes trajectory runtime and transcript rows with a single timestamp and no duration fields, including the reported context, prompt, session, and tool event paths. I did not run a live trajectory export in this read-only review.

## Solution Assessment

Unclear until maintainers choose the trajectory schema direction. Adding measured durations is the right end state for lifecycle operations, but forcing synthetic nonzero durations onto truly point-in-time events may be the wrong model.

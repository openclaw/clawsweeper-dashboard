## Summary

Keep open: current main and v2026.6.11 still model trajectory JSONL rows as timestamped point events without start/end/duration fields. The remaining work is real, but it needs a maintainer decision on trajectory event-versus-span semantics before a fix changes exported diagnostic data.

## What This Changes

The issue requests duration-bearing trajectory instrumentation for events such as `context.compiled`, `prompt.submitted`, `tool.call`, `tool.result`, and `session.started`.

## Best Possible Solution

Define a bounded trajectory timing contract, add measured duration data only for operations with real lifecycles, and document any rows that intentionally remain point-in-time events.

- **Add trajectory timing contract (recommended):** Keep this issue open and require a focused design/fix that adds duration or start/end fields for real lifecycle operations with tests and docs.
- **Keep trajectory event-only:** Leave trajectory JSONL as point events and document that duration analysis belongs to OTel or a separate latency report path.
- **Split runtime and transcript semantics:** Track runtime lifecycle spans separately from transcript-derived tool call/result reconstruction so each can get the right schema.

## Reproduction Assessment

Yes, source-reproducible: current main writes trajectory runtime and transcript rows with one timestamp and no duration/start/end fields, including the reported context, prompt, and tool-event paths. I did not run a live agent trace in this read-only review.

## Solution Assessment

Unclear until maintainers choose the trajectory schema direction. Adding measured durations is likely right for lifecycle operations, but synthetic nonzero durations for truly point-in-time transcript events would be the wrong model.

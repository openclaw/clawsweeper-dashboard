## Summary

Keep open: current main and v2026.6.11 still expose trajectory rows as timestamped events, and diagnostics-otel still emits `openclaw.context.assembled` as a zero-duration span. The remaining work needs a maintainer telemetry-schema decision because the request changes exported event/span semantics and only partially overlaps the open OTel latency PR.

## What This Changes

The issue asks OpenClaw to add real duration instrumentation or explicit non-instant event semantics for trajectory and telemetry rows such as `context.compiled`, `prompt.submitted`, tool events, and session lifecycle events.

## Best Possible Solution

Define a bounded trajectory timing contract, add measured duration data for real lifecycle operations, document event-only rows that intentionally remain point events, and coordinate the OTel context/reply timing overlap with the existing latency-decomposition work.

Question: Should trajectory JSONL rows gain an explicit measured duration/start-end contract, and which reported row types should become lifecycle spans versus remain point events?

Rationale: The current public shape is an event timeline with one timestamp, so adding durations changes exported diagnostic schema semantics and synthetic nonzero durations for point events could make telemetry misleading.

Likely owner: joshavant

Owner confidence: medium

Options:

- **Add a trajectory timing contract (recommended):** Approve additive `durationMs` or start/end fields for operations with real lifecycle timing, with docs and tests for the supported event families.
- **Keep trajectory event-only:** Leave trajectory JSONL as point events, clarify the docs, and let the separate OTel latency work own measured spans and metrics.
- **Split by event family:** Handle runtime lifecycle rows such as context and prompt timing separately from transcript-derived tool call/result reconstruction.

## Reproduction Assessment

Yes, source-reproducible: current main writes trajectory runtime and transcript rows with a single timestamp and no duration/start/end fields, and diagnostics-otel still hard-codes `openclaw.context.assembled` to duration 0. I did not run a live agent trace in this read-only review.

## Solution Assessment

Unclear until maintainers choose the telemetry schema direction. Adding measured durations is the right end state for real lifecycle operations, but forcing synthetic nonzero durations onto event-only rows would be a weaker model.

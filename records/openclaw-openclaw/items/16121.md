## Summary

Keep open: current main and v2026.6.11 only partially cover raw Telegram custom emoji HTML/rich-message paths; the shared message tool and Telegram action/send/caption/edit surfaces still lack first-class custom emoji entity support.

## What This Changes

The issue requests first-class Telegram custom emoji support for message text, captions, and replies, including custom emoji identifiers and sending/displaying them wherever standard emoji are supported.

## Best Possible Solution

Choose the public custom emoji representation first, then wire validated Telegram custom emoji support through message.send, Telegram actions, captions, edits, reply delivery, docs, and focused regression tests while preserving current HTML/rich fallbacks.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose Telegram custom emoji through raw/rich HTML only, through Telegram entity arrays, or through a shared Markdown/IR custom-emoji span that the Telegram plugin turns into Telegram payloads?

Rationale: The source gap is clear, but solving it expands a public message-tool/plugin contract and affects delivery fallback behavior across several Telegram funnels.

Likely owner: steipete

Owner reason: steipete has the strongest signal from the prior review on this exact issue and relevant Telegram formatting/API history.

Owner confidence: high

Options:

- **Design typed entity/IR contract (recommended):** Pick a typed representation that can round-trip custom emoji IDs through sends, edits, captions, and replies while preserving the current HTML fallback behavior.
- **Keep raw/rich HTML only:** Document the current `<tg-emoji>` and `richMessages` path as the supported surface and explicitly decline first-class entity arrays for now.
- **Add Telegram-only entity fields:** Expose `entities` and `caption_entities` only through Telegram-owned action/channelData surfaces without changing shared Markdown IR yet.

## Reproduction Assessment

Yes for a source-level reproduction path: current main's shared message tool and Telegram action/send paths do not accept or forward entity arrays, while comments report direct Bot API calls with the same entities working. I did not run a live Premium Telegram custom emoji probe in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public contract. Raw `<tg-emoji>`/rich-message support is only a partial path; a maintainable fix needs a typed Telegram/entity or shared IR representation that covers sends, captions, edits, replies, and fallbacks consistently.

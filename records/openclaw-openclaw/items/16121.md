## Summary

Keep open: current main and v2026.6.11 only partially cover the request by allowing raw Telegram `<tg-emoji>` HTML, while first-class `entities` / `caption_entities` custom emoji metadata still cannot be requested through the shared message tool or Telegram send/edit/caption paths.

## What This Changes

The issue requests first-class Telegram custom emoji support for messages, captions, and replies.

## Best Possible Solution

Choose the product/API representation first, then implement validated Telegram custom emoji support through the message tool and Telegram send/edit/caption/delivery paths while preserving safe raw HTML fallback behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What supported OpenClaw API should represent Telegram custom emoji: a shared Markdown/IR custom-emoji span, Telegram-specific `entities` / `caption_entities` in channel data, or raw `<tg-emoji>` HTML only?

Rationale: Current source can preserve raw HTML but cannot carry first-class entity metadata through the shared message tool; adding that surface changes public message-tool/plugin contracts and needs maintainer intent.

Likely owner: steipete

Owner reason: steipete authored the most concrete maintainer-facing review of the API-shape blocker and has adjacent Telegram command-runtime history.

Owner confidence: high

Options:

- **Add typed entity support (recommended):** Expose a narrow, validated Telegram entity/caption-entity payload through the message tool and Telegram plugin, with UTF-16 offset validation and delivery tests.
- **Design shared IR first:** Add a cross-channel custom emoji span to the Markdown/message presentation model before Telegram-specific send wiring, trading broader architecture for a cleaner long-term abstraction.
- **Keep raw HTML only:** Document `<tg-emoji>` as the supported escape hatch and close first-class entity support as out of scope, leaving plugin slash-command entity arrays unsupported.

## Reproduction Assessment

Yes, source-reproducible: current message-tool schema, Telegram action payloads, and send/caption paths have no `entities` or `caption_entities` parameter path, while Telegram's API requires entity metadata for first-class custom emoji. I did not run a live Telegram bot probe in this read-only cleanup review.

## Solution Assessment

Unclear until maintainers choose the API shape. The safest end state is not a one-off raw HTML bypass; it needs a typed representation with validation across message, caption, edit, reply, chunking, and fallback paths.

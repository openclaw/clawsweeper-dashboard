## Summary

Keep open: current main and v2026.6.11 partially support raw Telegram `<tg-emoji>` and opt-in rich messages, but they still do not expose first-class `entities` or `caption_entities` through the shared message tool and Telegram send/edit/caption surfaces.

## What This Changes

Requests first-class Telegram custom emoji support for messages, captions, replies, and shared message-tool delivery.

## Best Possible Solution

Choose one canonical entity representation, then implement validated Telegram custom emoji delivery across the shared message tool and Telegram send, edit, caption, reply, and streaming paths while preserving current raw HTML and rich-message fallbacks.

Options:

- **Define entity-bearing message API (recommended):** Add a maintainer-approved entity representation and implement it consistently across message-tool, Telegram send/edit/caption/reply delivery, docs, and regression tests.
- **Keep rich HTML and richMessages only:** Treat `<tg-emoji>` HTML and opt-in Bot API rich messages as the supported path while leaving user-supplied entity arrays unsupported.
- **Split API design first:** Create or designate a narrower API-design item before implementation so the eventual PR does not guess the permanent plugin contract.

## Reproduction Assessment

Yes for source-level reproduction, but not via a live Telegram run in this read-only review. The issue discussion gives a concrete message-tool path, and current source shows entity inputs are absent from the shared schema and Telegram send/edit/caption surfaces.

## Solution Assessment

Unclear until maintainers choose the public API shape. Raw `<tg-emoji>` preservation and `richMessages` cover part of the request, but they are not the full entity-based message/caption/reply solution reported by users.

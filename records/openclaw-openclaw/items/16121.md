## Summary

Keep open: current main has partial raw `<tg-emoji>` and rich-message handling, but it still lacks a first-class Telegram `entities`/`caption_entities` path through the shared message tool, Telegram action runtime, captions, edits, and replies.

## What This Changes

Request support for Telegram custom emoji in messages, captions, and replies, including custom emoji identifiers and entity-based delivery through OpenClaw's Telegram paths.

## Best Possible Solution

Choose one canonical Telegram custom emoji representation, then wire it through the shared message tool and Telegram send/edit/caption/reply paths while preserving current HTML and rich-message fallback behavior.

## Reproduction Assessment

Yes. Source inspection shows the current message-tool, Telegram action runtime, outbound payload, and send option surfaces have no first-class entity-array path, while issue comments provide a production path where `custom_emoji` entities are dropped.

## Solution Assessment

Unclear until maintainers choose the API shape. Raw `<tg-emoji>` preservation and `richMessages` are useful partial support, but they do not satisfy the requested shared message/caption/reply entity contract.

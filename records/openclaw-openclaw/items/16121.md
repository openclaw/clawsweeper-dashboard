## Summary

Keep open: current main and the latest release partially support raw `<tg-emoji>` HTML and opt-in rich messages, but the requested first-class custom emoji/entity path through the shared message tool, Telegram send/edit/caption delivery, and durable reply surfaces is still missing.

## What This Changes

The issue requests Telegram custom emoji support for outgoing messages, captions, and replies, including custom emoji identifiers and formatting support through OpenClaw’s Telegram bot path.

## Best Possible Solution

Define the custom emoji representation first, then implement validated Telegram entity/custom-emoji support through the Telegram plugin send/edit/caption/reply paths and shared message tool while preserving current HTML fallback behavior.

## Reproduction Assessment

Yes, source inspection is enough to reproduce the missing capability: the message tool and Telegram send/action paths do not expose or forward `entities`/`caption_entities`, while Telegram documents those fields for custom emoji. I did not run a live Telegram bot because this read-only review has no bot credential path.

## Solution Assessment

No, the current shipped raw `<tg-emoji>` allowlist and rich-message support are only partial solutions. The maintainable fix is a deliberate Telegram/message-tool entity contract with tests across sends, captions, edits, replies, chunking, and fallback behavior.

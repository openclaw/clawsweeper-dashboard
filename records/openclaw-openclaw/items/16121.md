## Summary

Keep open: current main and the latest release only partially support Telegram custom emoji through allowed `<tg-emoji emoji-id="...">` HTML, while the shared message tool and Telegram send/edit/caption paths still cannot carry `entities` or `caption_entities`. The production report about entity arrays being dropped remains source-reproducible and needs maintainer API-shape judgment, not conservative cleanup closure.

## What This Changes

Request first-class Telegram custom emoji support for messages, captions, replies, and shared message-tool delivery.

## Best Possible Solution

Choose the shared API representation first, then add validated Telegram custom emoji support through the message tool and Telegram send/edit/caption/durable/streaming paths while preserving the existing HTML passthrough behavior.

Required: true

Question: What permanent API shape should OpenClaw expose for Telegram custom emoji delivery: raw Telegram `entities` and `caption_entities`, a portable rich-text/custom-emoji IR, or Telegram-only channel data?

Rationale: The source gap is clear, but exposing entity arrays changes shared message-tool and plugin API shape, while the current formatter already supports a partial HTML passthrough path.

Likely owner: steipete

Owner reason: Prior review and local history make steipete the strongest API-shape routing candidate for this shared message-tool and Telegram plugin boundary.

Owner confidence: high

Options:

- **Design Shared Rich-Text Entity API (recommended):** Add a typed representation that can carry custom emoji IDs through the shared message tool and let Telegram map it to Bot API entities or safe HTML.
- **Expose Telegram-Only Entities:** Add a narrow `channelData.telegram.entities` and `caption_entities` path with Telegram-specific validation and tests.
- **Keep HTML-Only Support:** Declare `<tg-emoji>` HTML passthrough the supported path and keep raw entity-array requests out of scope for now.

## Reproduction Assessment

Yes for the remaining source-level gap: current main has no schema, payload, or Telegram send option that preserves `entities` or `caption_entities` through the shared message tool. I did not perform a live Telegram Bot API send in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API shape. Raw Telegram entities are a plausible repair path, but a shared typed rich-text/custom-emoji representation may be more maintainable than adding a Telegram-only parameter directly to the generic tool.

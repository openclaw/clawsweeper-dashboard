## Summary

Keep open: current main and the latest release only cover the raw HTML `<tg-emoji>` path, while first-class custom-emoji entities still cannot flow through the shared message tool or the Telegram send/caption surfaces.

## What This Changes

The issue requests first-class Telegram custom emoji support for Telegram messages, captions, and replies.

## Best Possible Solution

Choose a Telegram-owned entity/custom-emoji contract, then implement it through the shared message tool and Telegram send/edit/caption/streaming paths while preserving current HTML fallback behavior.

## Reproduction Assessment

Yes for the source-level gap: current main has raw `<tg-emoji>` HTML allowlisting, but the message tool, Telegram action runtime, and send/caption paths still have no `entities` or `caption_entities` flow. I did not run live Telegram proof because the blocker is the missing public API/delivery surface, not an intermittent runtime failure.

## Solution Assessment

Unclear until maintainers choose the public API shape. A Telegram-owned entity contract is the narrowest visible path, but a shared Markdown/rich-message representation may be better if maintainers want this to be portable rather than Telegram-specific.

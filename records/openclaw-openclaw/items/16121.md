## Summary

Keep open: current main has partial raw `<tg-emoji>` HTML allowlisting and Bot API 10.1 rich-message plumbing, but it still lacks the requested first-class custom emoji entity path through the shared message tool, Telegram send/edit/media-caption delivery, and agent/plugin command surfaces.

## What This Changes

The issue requests Telegram custom emoji support for outgoing messages, captions, and replies, including custom emoji identifiers and rendering parity with standard emoji.

## Best Possible Solution

Pick the public representation first, then implement validated Telegram custom emoji support through the shared message tool and Telegram send/edit/media/delivery/streaming paths with focused regression tests and preserved fallback behavior.

## Reproduction Assessment

Yes, at source level: current main has no shared message-tool `entities`/`caption_entities` schema, the Telegram action runtime does not forward entity arrays, and `TelegramSendOpts` has no entity-bearing option. I did not run a live Telegram probe in this read-only review.

## Solution Assessment

No, this should not be closed or solved by only allowing raw HTML. The maintainable fix is a deliberate entity/rich-text contract across the message tool and Telegram-owned send/delivery paths.

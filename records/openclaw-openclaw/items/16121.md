## Summary

Keep open: current main and v2026.6.11 only partially support Telegram custom emoji via allowed `<tg-emoji emoji-id="...">` HTML, while the shared message tool, Telegram action payload, send options, text sends, and caption sends still have no `entities` or `caption_entities` path for the production-reported case.

## What This Changes

Request support for Telegram custom emoji in messages, captions, replies, and message-tool delivery according to the Telegram Bot API.

## Best Possible Solution

Choose the shared API representation first, then add validated Telegram custom emoji support through the message tool and Telegram send/edit/caption/durable/streaming paths while preserving existing HTML passthrough behavior.

Rationale: The source gap is clear, but the fix expands shared message-tool or Telegram channel-data API shape and affects plugin contracts rather than repairing one private implementation branch.

Owner confidence: high

Options:

- **Design Shared Rich-Text Entity API (recommended):** Add a typed representation that can carry custom emoji IDs through the shared message tool, with Telegram mapping it to Bot API entities or safe HTML.
- **Expose Telegram-Only Entities:** Add a narrow Telegram-specific `entities` and `caption_entities` path with validation and focused delivery tests.
- **Keep HTML-Only Support:** Declare `<tg-emoji>` HTML passthrough the supported custom emoji path for now and keep raw entity arrays out of the generic message tool.

## Reproduction Assessment

Yes for the remaining source-level gap: current main has no schema, payload, or Telegram send option that preserves `entities` or `caption_entities` through the shared message tool. I did not perform a live Telegram Bot API send in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API shape. Raw Telegram entities are plausible, but a shared typed rich-text/custom-emoji representation may be more maintainable than adding a Telegram-only parameter directly to the generic tool.

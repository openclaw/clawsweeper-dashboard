## Summary

Keep open: current main and v2026.6.11 now cover part of the request by allowing raw `<tg-emoji emoji-id="...">` HTML through the Telegram renderer, but first-class outgoing `entities` / `caption_entities` still cannot flow through the shared message tool, Telegram send/edit/caption surfaces, or shared Markdown IR.

## What This Changes

The issue requests Telegram custom emoji support for messages, captions, and replies, including recognition of custom emoji identifiers and rendering/sending where normal emoji are supported.

## Best Possible Solution

Choose the public custom-emoji/entity representation first, then implement validated Telegram entity support through the bundled Telegram plugin send/edit/caption/reply paths and shared message tool while preserving current raw HTML fallback behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What public representation should OpenClaw support for outgoing Telegram custom emoji: raw `<tg-emoji>` HTML only, typed Telegram `entities` / `caption_entities` on the message tool, or a shared Markdown/IR custom-emoji span?

Rationale: Current code partially supports raw HTML tags, but the remaining gap changes the shared message-tool/plugin API and Telegram send-funnel semantics, so automation should not pick the permanent public contract.

Likely owner: steipete

Owner reason: steipete has the clearest issue-review and API-shape history on this exact tracker and appears in the current local blame for the affected snapshot.

Owner confidence: high

Options:

- **Add Typed Entity Contract (recommended):** Define a validated entity representation for the message tool and Telegram plugin, forward it through send/edit/caption/reply paths, and keep current HTML/plain fallback behavior for ordinary sends.
- **Treat Raw HTML as Sufficient:** Document the existing `<tg-emoji>` passthrough as the supported path and close or narrow the remaining entity-array work to cases with concrete product approval.
- **Fold Into Formatting Policy:** Defer implementation until the broader Telegram parse-mode/rich-message policy in https://github.com/openclaw/openclaw/issues/10944 decides how raw HTML, MarkdownV2, rich messages, and entities should coexist.

## Reproduction Assessment

Yes. Source inspection shows the shared message tool and Telegram send/action paths still have no entity-array send surface, and the issue comments include a concrete plugin slash-command path where those entities are lost before reaching Telegram.

## Solution Assessment

Unclear. Raw `<tg-emoji>` passthrough is already partly solved, but the remaining first-class entity support needs maintainer approval for the narrowest durable API shape before implementation.

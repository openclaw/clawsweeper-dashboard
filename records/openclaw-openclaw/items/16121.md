## Summary

Keep open. Current main has partial raw `<tg-emoji emoji-id="...">` HTML passthrough, but the issue discussion still has a meaningful unresolved request for first-class outgoing Telegram custom emoji entities through messages, captions, replies, and the shared message tool; the related implementation PRs are closed unmerged and do not supersede this issue.

## What This Changes

The issue requests Telegram custom emoji support for outgoing messages, captions, and replies, including custom emoji identifiers and rendering wherever normal emoji-style formatting is supported.

## Best Possible Solution

Choose a maintainer-approved custom emoji representation, then wire validated Telegram entity or raw-HTML support through the Telegram plugin send, caption, edit, streaming, durable outbound, and shared message-tool paths with focused UTF-16 offset and fallback tests.

Options:

- **Adopt a first-class entity contract (recommended):** Add a validated custom emoji representation through the message tool or Telegram-owned channelData and wire it to `entities`/`caption_entities` while preserving current HTML fallback behavior.
- **Narrow to raw HTML passthrough:** Document and test `<tg-emoji emoji-id="...">` as the supported path, and explicitly leave entity-array support out of scope for now.
- **Defer behind parse-mode work:** Let https://github.com/openclaw/openclaw/issues/10944 settle the broader Telegram formatting mode before adding any custom emoji-specific public surface.

## Reproduction Assessment

Yes from source inspection, not from a live Telegram run: current main has no shared message-tool `entities` field, no Telegram action payload slot, and no `TelegramSendOpts` entity/caption-entity path. A message-tool call that supplies Telegram custom emoji entities therefore has no supported path to survive to the Bot API.

## Solution Assessment

No for maintainer cleanup closure: raw `<tg-emoji>` HTML passthrough is useful partial support, but it is not the best complete solution for the broader issue because it leaves entity arrays, captions, and plugin slash-command message-tool delivery unresolved. The safer next step is a maintainer-approved API shape before implementation.

## Summary

Keep open: current main has partial Telegram custom emoji support via allowed `<tg-emoji emoji-id="...">` HTML/rich text, but the shared message tool still cannot carry `entities` or `caption_entities`, so the production entity-round-trip gap remains.

## What This Changes

The issue requests first-class Telegram custom emoji support in messages, captions, and replies, including custom emoji identifiers and rendering according to Telegram formatting/entity rules.

## Best Possible Solution

Choose the shared API representation first, then add validated Telegram entity/caption-entity support through the message tool and durable/streaming send paths while preserving existing HTML/rich-text custom emoji support.

Owner confidence: high

Options:

- **Design Shared Rich-Text Entity API (recommended):** Add a typed representation that can carry custom emoji IDs through the shared message tool and let Telegram map it to Bot API entities or rich HTML.
- **Expose Telegram-Only Entities:** Add a narrow Telegram-owned `channelData.telegram.entities` or `caption_entities` path with validation and tests, accepting that it is not portable across channels.
- **Document HTML-Only Support:** Keep current `<tg-emoji>` HTML/rich-text support as the supported path and close narrower entity-array requests as out of scope.

## Reproduction Assessment

Yes for the remaining entity round-trip gap: current-main source shows no schema, payload, or Telegram send option that preserves `entities` or `caption_entities` through the shared message tool.

## Solution Assessment

Unclear until maintainers choose the API shape; raw Telegram entities are a plausible repair path, but a shared rich-text/entity representation may be the more maintainable long-term solution.

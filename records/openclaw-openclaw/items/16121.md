## Summary

Keep open: current main partially supports raw Telegram `<tg-emoji>` HTML and rich-message sends, but it still lacks first-class custom-emoji `entities` / `caption_entities` support through the shared message tool and Telegram message/caption/reply delivery surfaces.

## What This Changes

The issue requests Telegram custom emoji support for messages, captions, and replies, including custom emoji identifiers and send/display behavior.

## Best Possible Solution

Choose one canonical Telegram custom-emoji representation, then implement validated entity support through the shared message tool and Telegram send/edit/caption/reply paths while preserving current raw HTML and rich-message fallback behavior.

## Reproduction Assessment

Yes. Source inspection shows the raw HTML path exists, but the shared message-tool and Telegram send option surfaces still do not expose first-class `entities` or `caption_entities`; the June 12 production comment reports the same entity array loss through plugin slash-command sends.

## Solution Assessment

Unclear until maintainers choose the public API shape. Raw `<tg-emoji>` preservation is useful, but it is not the full shared message/caption/reply entity solution requested.

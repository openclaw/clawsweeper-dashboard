## Label Justifications

- `P1`: A shipped update path can make a configured Linux gateway inaccessible by switching to a different HOME/config root.
- `impact:data-loss`: The central symptom is silently abandoning a populated user config and replacing it with a sparse config under another HOME.
- `impact:auth-provider`: The abandoned config includes gateway auth, provider/model, and channel credential routing state.
- `impact:crash-loop`: The report includes gateway downtime, startup blockage from missing gateway.mode, and competing gateway processes after update.
- `maturity:stable`: The affected CLI install/update/doctor and Linux gateway host surfaces are both scored M4 Stable in qa/maturity-scores.yaml.

## Summary

Keep open: current main and the latest release still leave the reported cross-HOME update path unresolved. The update/service code still starts discovery from the updater environment, systemd user-unit lookup is HOME-keyed, and forced reinstall still drops prior HOME and OPENCLAW_* roots instead of preserving, migrating, warning, or blocking when they changed.

## What This Changes

The issue asks OpenClaw update/service refresh to stop silently abandoning existing config and state when a systemd service HOME changes between users.

## Best Possible Solution

Add a Linux update/service-refresh guard that identifies the previously installed gateway service root before rewriting, compares HOME, OPENCLAW_HOME, OPENCLAW_STATE_DIR, and OPENCLAW_CONFIG_PATH against the updater environment, then preserves the prior root only when safe or emits a clear blocking migration warning.

## Reproduction Assessment

Yes at source level: the report gives concrete upgrade steps, and current code still has HOME/env-keyed service discovery plus forced reinstall behavior that drops prior service roots. I did not run a live cross-user systemd upgrade in this read-only review.

## Solution Assessment

Unclear until maintainers choose the compatibility and privacy policy. The requested warning or migration direction is right, but the durable fix must avoid broadly reusing stale service env or exposing sibling-user state.

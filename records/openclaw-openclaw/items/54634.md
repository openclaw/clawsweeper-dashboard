- `impact:data-loss`: The central symptom is silently abandoning a populated user config and replacing it with a sparse config under another HOME.
- `impact:auth-provider`: The abandoned config includes gateway auth, provider/model routing, and channel credential configuration.
- `impact:crash-loop`: The report includes gateway downtime, startup blockage, and competing gateway processes after the update.
- `maturity:stable`: The issue affects M4 Stable CLI install/update/doctor and Linux gateway host service-management surfaces.

## Summary

Keep open: current main still leaves the reported cross-HOME Linux update path unresolved; the source now has adjacent service-env and doctor hardening, but no merged guard that preserves, migrates, warns, or blocks when an update changes the service HOME/config root.

## What This Changes

The issue requests update/service safeguards so a Linux systemd upgrade cannot switch HOME from a dedicated OpenClaw user to root and silently abandon config/state.

## Best Possible Solution

Add a Linux update/service-refresh guard that records or discovers the previously installed gateway service root, compares HOME, OPENCLAW_HOME, OPENCLAW_STATE_DIR, and OPENCLAW_CONFIG_PATH against the updater environment, and then either preserves the prior root when policy-safe or blocks with an explicit migration warning.

## Reproduction Assessment

Yes at source level: the report gives concrete upgrade steps and current main still has HOME/env-keyed service discovery plus forced reinstall behavior that drops prior service roots. I did not run a live cross-user systemd upgrade in this read-only review.

## Solution Assessment

Unclear until maintainers choose the compatibility and privacy policy. The best fix should prevent cross-HOME config abandonment without broadly reusing stale service env or leaking sibling-user state.

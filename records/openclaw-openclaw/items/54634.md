## Summary

Keep open: current main has fixed an adjacent unreadable-config overwrite path, but it still does not solve the reported Linux update case where changing the service HOME/config root causes the updater to miss the prior systemd unit and generate a new sparse root config.

## What This Changes

The issue reports an update from 2026.3.23-2 to 2026.3.24 changing the systemd service HOME from a dedicated OpenClaw user to root, abandoning the existing config/state and breaking the gateway.

## Best Possible Solution

Add a Linux update/service-refresh guard that identifies the previously installed gateway service root before rewriting, compares HOME, OPENCLAW_HOME, OPENCLAW_STATE_DIR, and OPENCLAW_CONFIG_PATH against the updater environment, and then preserves, blocks, or clearly prompts for migration according to an explicit maintainer-approved security policy.

## Reproduction Assessment

Yes, at source level: the report gives concrete upgrade steps, and current main still has HOME-keyed systemd lookup plus updater-env-based service discovery. I did not run a live cross-user systemd upgrade in this read-only review.

## Solution Assessment

No current implementation is sufficient yet. The best fix needs maintainer security/product direction on whether to preserve the old service root, block the update, or require an explicit migration when HOME/config roots change.

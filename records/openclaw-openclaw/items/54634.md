## Summary

Keep open: current main still does not safely handle the reported Linux update path where the updater runs under a different HOME from the installed systemd user service, and the linked PRs cover adjacent migration slices rather than a landed fix for this cross-HOME service-root split.

## What This Changes

The issue asks OpenClaw update/doctor to preserve, migrate, warn, or block when a systemd service HOME change would abandon an existing config and state root.

## Best Possible Solution

Add a Linux update/service-refresh guard that identifies the previously installed gateway service root before rewriting, compares HOME, OPENCLAW_HOME, OPENCLAW_STATE_DIR, and OPENCLAW_CONFIG_PATH against the updater environment, and either safely preserves the intended root or blocks with a clear migration warning.

## Reproduction Assessment

Yes, at source level. Current main still uses the updater environment for service discovery, resolves systemd user-unit paths from HOME, and deliberately drops prior HOME/OPENCLAW_* service roots during forced reinstall; I did not run a live cross-user systemd upgrade.

## Solution Assessment

Unclear until maintainers choose the compatibility and privacy policy. The durable fix should prevent cross-HOME config abandonment without broadly reusing stale service env or exposing sibling-user state.

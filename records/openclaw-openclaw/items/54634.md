## Summary

Keep open: current main and v2026.6.11 still have the HOME/env-keyed update and service-regeneration behavior implicated by the report, and the related open items cover adjacent roots rather than a merged fix for this cross-HOME update path.

## What This Changes

The issue asks for update/service migration safeguards so changing HOME during a Linux gateway update does not abandon existing config/state or silently create a sparse replacement config.

## Best Possible Solution

Add a Linux update/service-refresh guard that identifies the existing managed gateway service root before rewrite, compares HOME/OPENCLAW_HOME/OPENCLAW_STATE_DIR/OPENCLAW_CONFIG_PATH to the updater environment, and either preserves the intended root when safe or blocks with a clear migration warning.

## Reproduction Assessment

Yes at source level: the report gives concrete update steps and current main still has HOME-keyed service discovery plus forced reinstall behavior that drops prior control roots. I did not run a live cross-user systemd upgrade in this read-only review.

## Solution Assessment

Unclear until maintainers choose the compatibility and privacy policy; the fix should prevent cross-HOME config abandonment without broadly reusing stale service env or leaking sibling-user state.

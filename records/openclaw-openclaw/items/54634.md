## Label Justifications

- `P1`: A shipped update path can make an existing configured Linux gateway inaccessible by switching to a different HOME/config root.
- `impact:data-loss`: The reported failure silently abandons a populated user config and starts from a sparse replacement config.
- `impact:auth-provider`: The abandoned config includes gateway auth token state, provider/model routing, and channel credential settings.
- `impact:crash-loop`: The report includes gateway downtime, startup blockage, and competing gateway processes after the update.
- `maturity:stable`: The issue affects M4 Stable CLI install/update/doctor and Linux Gateway host service-management surfaces.

## Summary

Keep open: current main still has source-level evidence for the reported cross-HOME update failure, and the open related PRs cover adjacent service-env or legacy-config cases rather than this exact HOME/root migration gap.

## What This Changes

The issue asks OpenClaw update/service repair to preserve, migrate, or clearly warn when a Linux systemd update changes HOME and would abandon the existing config, state, auth, and channel settings.

## Best Possible Solution

Add a Linux update/service guard that detects a prior managed service root before rewrite, compares HOME and `OPENCLAW_*` config/state roots, and either blocks with clear recovery guidance or performs an explicit backed-up migration chosen by maintainers.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: When an updater runs with a different HOME than the installed Linux systemd gateway service, should OpenClaw block, preserve the prior service root, or migrate config/state automatically?

Rationale: The code can detect the mismatch, but the permanent behavior controls cross-user credential-bearing config access and could conflict with existing stale-service-env hardening.

Likely owner: steipete

Owner reason: The central update/service restart path and recent related history point to steipete as the best available routing owner for the security/product choice.

Owner confidence: high

Options:

- **Block and require explicit migration (recommended):** Detect the mismatch, stop before rewriting service/config roots, and print a Doctor/setup command that the operator must run in the intended user context.
- **Preserve matching prior root:** Reuse the prior service HOME/config roots only when ownership and service identity match a strict safe policy.
- **Automatic backed-up migration:** Move or copy the old config/state into the new root with backups, audit output, and strict ownership checks.

Yes, at source level: the issue gives concrete upgrade steps and current main still has HOME-keyed systemd discovery plus service refresh paths that can start from the updater environment. I did not run a live cross-user systemd update in this read-only review.

## Solution Assessment

Unclear until maintainers choose the cross-HOME security policy. The narrowest maintainable fix is a guarded update/service repair path, not reintroducing broad runtime config fallback or silently reusing all old service env.

## Label Justifications

- `P1`: A shipped update path can make an existing configured Linux gateway inaccessible by switching to a different HOME/config root.
- `impact:data-loss`: The central symptom is silently abandoning a populated user config and using a sparse replacement under another HOME.
- `impact:auth-provider`: The abandoned config includes gateway auth, provider/model, channel credential, and routing settings.
- `impact:crash-loop`: The report includes gateway downtime, startup blockage from missing `gateway.mode`, and competing gateway processes after update.
- `maturity:stable`: The issue affects the M4 Stable `cli-install-update-onboard-doctor` surface, including update, doctor, and gateway service-management behavior.

## Summary

Keep open: current main and v2026.6.11 still use HOME-keyed service/config discovery and do not guard the reported update-time switch from the dedicated OpenClaw user to root; related items cover adjacent service-env, moltbot, and EACCES clobber paths, but not this cross-HOME update path.

## What This Changes

The issue reports that a 2026.3.24 update changed the Linux systemd service HOME from a dedicated OpenClaw user to root, abandoning the existing config/state and starting from a sparse root config.

## Best Possible Solution

Add a Linux update/service-refresh guard that identifies the previously installed gateway service root before rewriting, compares HOME and OpenClaw path env against the updater context, and either preserves the safe prior root or blocks with an explicit migration warning.

## Reproduction Assessment

Yes, source-level: current main still keys Linux user-systemd discovery and config defaults to the updater HOME/env, while forced reinstall intentionally drops prior HOME and `OPENCLAW_*` service roots. I did not run a live cross-user systemd upgrade in this read-only review.

## Solution Assessment

Unclear until maintainers choose the cross-HOME compatibility and privacy policy. The best fix should prevent config-root abandonment without broadly reusing stale service env or exposing sibling-user state.

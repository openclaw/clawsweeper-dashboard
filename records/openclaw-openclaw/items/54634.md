## Summary

Keep open: current main has adjacent service-root and config-write hardening, but it still does not prove preserve, migrate, or block behavior for the reported HOME-only update split where an installed service rooted in one Unix home is refreshed from another.

## What This Changes

The issue asks OpenClaw update/doctor to prevent or recover config/state loss when an update changes the service HOME from the existing OpenClaw home to another Unix home.

## Best Possible Solution

Add a Linux update/service-refresh guard that detects an installed service HOME/config-root mismatch before rewrite, then blocks with a clear doctor migration path or performs an explicit backed-up migration under maintainer-approved policy.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: When the updater HOME differs from the installed gateway service HOME and no explicit `OPENCLAW_CONFIG_PATH` is present, should OpenClaw preserve the service HOME, block until explicit migration, or add a guarded doctor migration?

Rationale: The repair crosses credential-bearing config, service identity, and Unix-user boundaries, and preserving old service env blindly can conflict with stale-env hardening.

Likely owner: steipete

Owner reason: The recent package-update restart path is closest to the policy decision and implementation boundary.

Owner confidence: high

Options:

- **Block and require explicit migration (recommended):** Detect the HOME/root mismatch before service rewrite and point the operator at a doctor migration that shows source and destination roots with backups.
- **Preserve authenticated service HOME:** Carry the previous service HOME into update doctor/restart paths only when the installed service can be verified as OpenClaw-owned.
- **Document manual recovery only:** Keep runtime behavior unchanged and document the wrong-HOME update class as an operator-managed recovery path.

## Reproduction Assessment

Yes, source-reproducible: current main still derives default config/state from HOME and post-install doctor does not carry service HOME when explicit config/state env is absent. I did not run a live cross-user systemd upgrade in this read-only review.

## Solution Assessment

No, current main is not the complete solution: package-root matching and stale-env hardening reduce adjacent risks but do not prove preserve/migrate/block behavior for the HOME-only config-root split. The best fix needs a maintainer-approved cross-HOME credential boundary policy.

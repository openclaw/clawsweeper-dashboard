## Label Justifications

- `P1`: A shipped update path can make a configured Linux gateway inaccessible by switching to a different HOME/config root.
- `impact:data-loss`: The central symptom is silently abandoning a populated user config and using a sparse replacement under another HOME.
- `impact:auth-provider`: The abandoned config includes gateway auth, provider/model routing, and channel credential state.
- `impact:crash-loop`: The report includes gateway downtime, startup blockage from missing gateway.mode, and competing gateway processes.
- `maturity:stable`: The issue affects the M4 Stable CLI install/update/doctor surface and the M4 Stable Linux Gateway host service-management path.

## Summary

Keep open: current main and v2026.6.11 still leave the reported cross-HOME Linux update path without a guard, migration, or blocking warning when the updater environment points at a different HOME than the installed user service.

## What This Changes

The issue asks OpenClaw update/service refresh to detect, preserve, migrate, or warn before abandoning a populated config/state root when HOME changes during an upgrade.

## Best Possible Solution

Add a Linux update/service-refresh guard that identifies the previously installed gateway service root before rewriting, compares HOME and OPENCLAW path roots against the updater environment, and either preserves the intended root, runs an explicit doctor migration, or blocks with a clear warning.

## Reproduction Assessment

Yes at source level: the report gives concrete upgrade steps, and current code still has current-env service discovery plus HOME-keyed systemd unit lookup. I did not run a live cross-user systemd upgrade in this read-only review.

## Solution Assessment

Unclear until maintainers choose the cross-HOME compatibility and security policy. The requested detect/migrate/warn outcome is right, but the best implementation must avoid broad stale-env reuse or sibling-user credential leakage.

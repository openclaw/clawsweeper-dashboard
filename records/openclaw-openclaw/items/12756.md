## Label Justifications

- `P2`: This is a useful, bounded Telegram capability request, but it is not a regression or emergency and needs deliberate product design before implementation.
- `impact:security`: The feature would retain and expose inbound group-message content, creating privacy, authorization, and data-retention concerns.
- `impact:session-state`: The requested behavior introduces queryable historical conversation state that agents could use for monitoring and later context.

## Summary

Keep open: current main and v2026.6.11 still reject Telegram `message read`; the request remains useful, but storing and exposing observed group messages requires an explicit retention, authorization, and privacy decision.

## What This Changes

Add Telegram support for the shared `message read` action so agents can retrieve recently observed chat messages.

## Best Possible Solution

Implement an explicitly enabled, Telegram-owned observed-message read path backed by bounded SQLite or plugin KV storage, with authorization and retention controls, no secondary `getUpdates` polling, clear observed-only semantics, and end-to-end action, CLI, documentation, and test coverage.

## Maintainer Decision

Question: Should the bundled Telegram plugin expose observed-only message reads, and if so what retention, default enablement, and authorization contract should govern the stored chat content?

Rationale: Source inspection establishes the implementation gap, but repository policy cannot choose whether bundled Telegram should retain group content or how broadly agents may query it; those choices alter privacy and security behavior.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve bounded observed-only reads (recommended):** Add an explicit action gate and bounded SQLite-backed store containing only messages the running bot observed, with documented retention and access semantics.
- **Provide a generic hook only:** Prioritize the passive inbound hook represented by https://github.com/openclaw/openclaw/pull/83101 and leave archival and history querying to separately installed plugins.
- **Decline retained history:** Keep Telegram transport stateless beyond existing operational context and document that the Bot API cannot provide arbitrary chat-history reads.

## Reproduction Assessment

Yes, from source: the shared action accepts `read`, but Telegram does not advertise, map, gate, or dispatch it, so the provider reaches its unsupported-action path. This review did not execute the live CLI command.

## Solution Assessment

No, parity with Slack and Discord parameters alone is not sufficient because Telegram lacks an arbitrary bot history endpoint. The maintainable path is a bounded, authorized, observed-only store if maintainers approve retaining this content.

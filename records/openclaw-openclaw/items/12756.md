## Summary

Keep open: current main and the latest release still do not implement Telegram `message read`; the shared action exists, but the Telegram plugin does not advertise, map, gate, dispatch, test, or document a read/history action. The remaining work is a product/security decision because Telegram reads would expose retained chat content and likely need an observed-only bounded store rather than arbitrary history fetches.

## What This Changes

Request support for `openclaw message read --channel telegram` so agents can inspect recent Telegram group messages similarly to Slack and Discord.

## Best Possible Solution

Implement Telegram `message read` in the Telegram plugin as an observed-only, bounded, explicitly gated read path with target/topic authorization, retention semantics, docs, and focused tests, without adding a secondary `getUpdates` poller.

Owner confidence: medium

Options:

- **Observed-only, explicit read gate (recommended):** Add a bounded observed-message read path behind an explicit Telegram action/config gate and document that it cannot fetch arbitrary historical Telegram messages.
- **Defer behind passive hook work:** Keep this open until the passive history/plugin hook direction lands, then design `message read` on top of that contract.
- **Reject core read surface:** Leave Telegram history retrieval to user-installed archive plugins if maintainers decide retained chat content should not be exposed through the built-in message tool.

Yes. Source inspection on current main shows the shared `read` action exists, while Telegram discovery, action mapping, runtime aliases, config gates, tests, and docs still omit Telegram read, so the unsupported-action path is clear without live Telegram proof.

## Solution Assessment

Unclear until maintainers choose the retained-message contract. The correct layer is the Telegram plugin, but a safe implementation must settle privacy, retention, observed-history semantics, and the default action gate first.

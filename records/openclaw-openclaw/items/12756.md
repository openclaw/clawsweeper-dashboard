## Summary

Keep open: current main and v2026.6.11 still do not expose Telegram `message read`; this remains the canonical general request and needs product/security direction before implementation.

## What This Changes

The issue requests Telegram support for `openclaw message read` so agents can read recent Telegram group messages like Slack or Discord.

## Best Possible Solution

Define Telegram `message read` in the Telegram plugin with an observed-message contract, explicit action gate, bounded retention, target/topic authorization, docs, focused tests, and no secondary `getUpdates` poller.

Options:

- **Observed-only, default-off read (recommended):** Add a bounded observed-message read path behind an explicit Telegram action gate and document that it cannot fetch arbitrary historical Telegram messages.
- **Observed-only, default-on read:** Expose observed reads for already-configured Telegram chats by default, accepting a broader upgrade-time privacy change.
- **Defer to archive hook direction:** Keep the issue open until the passive history/plugin hook design lands, then build `message read` on that contract.

## Reproduction Assessment

Yes. Source inspection is enough for the unsupported-action symptom: shared `read` exists, but Telegram discovery, mapping, runtime aliases, config gating, tests, and docs still omit it on current main and v2026.6.11.

## Solution Assessment

Unclear until maintainers choose the retained-message contract. The correct layer is the Telegram plugin, but the safe implementation depends on privacy, retention, observed-history semantics, and the default action gate.

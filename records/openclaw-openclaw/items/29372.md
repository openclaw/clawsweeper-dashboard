## Summary

Keep open: current main and v2026.6.11 still do not support `agents.list[].subagents.workspace`; existing shipped mitigations are explicit child agent profiles, `subagents.requireAgentId`, sandbox workspace policy, and per-call `cwd`, so this remains a maintainer product/security-boundary decision.

## What This Changes

Request to add a per-agent `subagents.workspace` config option so default child subagents can use a separate workspace without creating explicit child agent profiles.

## Best Possible Solution

Maintainers should choose the supported isolation model first: keep explicit child profiles plus `requireAgentId`, or approve a narrow opt-in `subagents.workspace` contract with schema, docs, doctor/security review, and regression coverage across same-agent, cross-agent, `cwd`, and sandbox paths.

## Reproduction Assessment

Yes, at source level: omit `agentId` and current main resolves the child target to the requester, then uses the requester workspace as the inherited spawned workspace. I did not run a live spawn, but current tests assert same-agent children preserve the inherited requester workspace.

## Solution Assessment

Unclear: the proposed config directly solves the no-`agentId` isolation request, but the existing supported path is explicit child profiles with `requireAgentId` plus optional `cwd`. Maintainers need to decide whether the extra public config surface is worth the security-boundary complexity.

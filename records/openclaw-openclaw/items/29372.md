## Summary

Keep open: current main and v2026.6.11 still do not support `agents.list[].subagents.workspace`; the remaining question is whether OpenClaw should add a new public, security-sensitive workspace config surface or continue relying on explicit child agent profiles, `requireAgentId`, sandbox policy, and per-call `cwd`.

## What This Changes

Request to add an `agents.list[].subagents.workspace` option so default child subagents can use a workspace different from the parent agent without creating separate agent profiles.

## Best Possible Solution

Maintainers should choose the supported isolation model first: keep explicit child profiles plus `requireAgentId`, or approve a narrow opt-in `subagents.workspace` contract with schema, docs, doctor/security review, and regression coverage across same-agent, cross-agent, `cwd`, and sandbox paths.

- **Defer to workspace policy design:** Hold this until subagent workspace, task `cwd`, sandbox policy, and skill workdir isolation are designed together with https://github.com/openclaw/openclaw/issues/87253.

## Reproduction Assessment

Yes, at source level: omit `agentId` and current main resolves the child target to the requester, then uses the requester workspace as the inherited spawned workspace. I did not run a live spawn, but current tests also assert same-agent children preserve inherited requester workspace.

## Solution Assessment

Unclear: the proposed config directly solves the no-`agentId` isolation request, but the existing supported path is explicit child profiles with `requireAgentId` plus optional `cwd`. Maintainers need to decide whether the extra public config surface is worth the security-boundary complexity.

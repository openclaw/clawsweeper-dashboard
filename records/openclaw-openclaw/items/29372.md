## Summary

Keep open: current main and v2026.6.11 still do not support `agents.list[].subagents.workspace`; the available mitigations are explicit child agent profiles, `subagents.requireAgentId`, sandbox workspace policy, and per-call `cwd`, so this remains a maintainer security/product decision.

## What This Changes

Request to add a per-agent `agents.list[].subagents.workspace` config option so default child subagents spawned without `agentId` can use a separate workspace from the parent agent.

## Best Possible Solution

Maintainers should choose the supported isolation model first: either keep explicit child profiles plus `requireAgentId`, or approve a narrow opt-in `subagents.workspace` contract with schema, docs, doctor/security review, and regression coverage across same-agent, cross-agent, `cwd`, and sandbox paths.

Options:

- **Add Narrow Opt-In Config:** Implement `subagents.workspace` only for same-agent default child spawns, with strict schema, docs, doctor/security review, and focused workspace regression coverage.
- **Defer To Broader Workdir Design:** Hold this until subagent workspace, task `cwd`, sandbox policy, and skill workdir isolation are designed together with https://github.com/openclaw/openclaw/issues/87253.

## Reproduction Assessment

Yes, at source level: omit `agentId` and current main resolves the child target to the requester, then uses the requester workspace as the inherited spawned workspace. I did not run a live spawn, but current tests also assert same-agent children preserve inherited requester workspace unless `requireAgentId` blocks them.

## Solution Assessment

Unclear: the proposed config directly solves the no-`agentId` isolation request, but the existing supported path is explicit child profiles with `requireAgentId` plus optional `cwd`. Maintainers need to decide whether the extra public config surface is worth the security-boundary complexity.

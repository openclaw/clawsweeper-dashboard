## Label Justifications

- `P2`: The issue affected log-debugging accuracy for non-UTC users, but it had workarounds and is now implemented.
- `impact:ux-friction`: UTC log output made a user-facing troubleshooting workflow confusing without fully blocking OpenClaw use.

## Summary

Current main and the latest stable release already solve the reported log timestamp problem: `openclaw logs` renders local time by default, keeps UTC as an explicit opt-in, and parses the top-level `time` field before `_meta.date`.

## What This Changes

The issue asks for `openclaw logs` to display local-time log timestamps by default instead of UTC timestamps from the `date` field.

## Best Possible Solution

Keep the shipped local-time default with `--utc` as the explicit opt-in and close the older duplicate/attempted-fix thread as implemented.

## Reproduction Assessment

No, not against current main: the current source and tests show `openclaw logs` renders local timestamps by default and only emits UTC with `--utc`. The original report is credible for older releases such as v2026.3.13, but the failing behavior is now covered by source-level regression tests.

## Solution Assessment

Yes. The current solution is the narrow maintainable shape: parse the log record's top-level `time`, use the shared timestamp formatter in local mode by default, and keep UTC available as an explicit CLI option.

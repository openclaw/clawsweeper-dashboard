## Summary

Keep open: this is a focused candidate fix for the linked QQBot reconnect outbound-delivery regression, and I do not see a concrete patch defect after source review. ## What This Changes

The PR adds operation-aware outbound delivery resolution for text and poll sends, routes direct delivery and gateway polls through it, and drains QQBot pending deliveries on ready/resumed reconnect callbacks.

## Best Possible Solution

Land this PR, or a maintainer-approved equivalent, after explicit maintainer acceptance of the resolver-ordering and QQBot reconnect replay behavior.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: the linked issue has live 2026.5.28 QQBot 4009 logs followed by outbound-not-configured failures, and current main still has the capability-blind direct adapter path that can select a setup shell before throwing.

## Solution Assessment

Is this the best way to solve the issue? Yes, with maintainer acceptance: splitting shared lookup from delivery-gated lookup preserves action/read callers while aligning sendMessage, sendPoll, direct delivery, and gateway poll. Gating the shared resolver would be a worse fit because action-only plugins still need to resolve.

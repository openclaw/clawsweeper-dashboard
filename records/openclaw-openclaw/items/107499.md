## Summary

Current main still has the architectural gap: feature-specific TypeBox validators exist, but the request envelope and shared server-handler contract erase method-specific payload types. Keep this open, but narrow it to built-in RPC typing with an explicit plugin-method extension boundary rather than a closed union of every runtime method. ([github.com](https://github.com/openclaw/openclaw/blob/main/src/gateway/server-methods/shared-types.ts))

## What This Changes

Add method-specific static types for Gateway command payloads and consume them in server request handlers instead of generic records and repeated assertions.

## Best Possible Solution

Introduce a schema-derived built-in method-to-params map and generic handler type, retain an explicit typed fallback or augmentation seam for plugin RPCs, and migrate handlers incrementally with compile-time and validator-contract tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Gateway request typing cover built-in RPCs only with a plugin fallback, or establish a public type-augmentation contract for plugin-registered RPC methods?

Rationale: The built-in payload schemas can support strict typing, but the runtime registry intentionally accepts plugin-defined method names, so the permanent extension boundary needs maintainer intent before a broad migration.

Likely owner: steipete

Owner reason: The recent method registry architecture and most of the protocol history route through this contributor.

Owner confidence: high

Options:

- **Built-ins plus plugin fallback (recommended):** Type built-in RPCs exhaustively while preserving a documented generic handler path for plugin-registered methods.
- **Public plugin augmentation:** Add a supported declaration-merging or registry-generic contract so plugins can contribute method-specific payload types.
- **Internal handlers only:** Keep RequestFrame generic and add local generic handler helpers without creating a central method map.

## Reproduction Assessment

Yes at source level: current main clearly exposes unknown request params at the envelope and Record<string, unknown> at the handler boundary. No user-visible runtime failure is claimed or needed for this cleanup request.

## Solution Assessment

No, not exactly as proposed. Strict built-in payload typing is appropriate, but defining concrete types for all runtime commands as one closed contract is unsafe because plugin methods are dynamically registered.

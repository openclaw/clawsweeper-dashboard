## Summary

Keep open: current main and v2026.6.11 still handle accepted Telegram reactions as passive standard-emoji system events, while wake behavior, custom-emoji normalization, and product-level semantics remain unmerged product/API work with live Telegram proof still needed.

## What This Changes

Requests first-class Telegram reaction triggers so standard and custom emoji reactions can wake or drive agent workflows with configurable semantics and observability.

## Best Possible Solution

Land or close a maintainer-approved opt-in notification-wake design that preserves queue-only defaults, normalizes standard/custom reaction keys, documents the semantics boundary, and includes live Telegram proof.

## Reproduction Assessment

Yes at source level: current main accepts standard emoji Telegram reactions and enqueues system events without a wake request, and comments include repeated live Telegram DM reports across released versions. I did not run a live Telegram account in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public API. A shared default-queue policy with explicit wake/off modes and reaction-key normalization is safer than unconditional wake or hardcoded per-emoji behavior.

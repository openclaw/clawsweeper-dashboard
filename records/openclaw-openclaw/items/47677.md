## Summary

Keep open: current main and the latest release still treat accepted Telegram reactions as passive standard-emoji system events, while wake behavior, custom-emoji normalization, and product-level semantics remain unmerged product/API work with open implementation candidates.

## What This Changes

Requested first-class Telegram reaction handling so configured reactions can wake an agent, support standard and custom emoji semantics, and provide observable operator workflow signals.

## Best Possible Solution

Land or close a maintainer-approved opt-in notification-wake design that preserves passive queue defaults, normalizes standard/custom reaction keys, and documents the semantics boundary with live Telegram proof.

## Reproduction Assessment

Yes at source level: current main and v2026.6.11 accept and enqueue Telegram reaction events without a wake path, and comments include repeated live Telegram DM reports across released versions. I did not run a live Telegram account in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public API. A shared default-queue policy with explicit wake/off modes plus reaction-key normalization is safer than unconditional wake or a one-off local repair.

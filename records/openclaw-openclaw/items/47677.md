## Label Justifications

- `P2`: This is a normal-priority Telegram channel workflow improvement with clear operator friction but no outage, security bypass, crash loop, or first-run blocker.

## Summary

Keep open: current main and the latest release still treat accepted Telegram reactions as queued system events, while reaction wake, custom-emoji normalization, and product-level semantics remain unresolved with open implementation candidates.

## What This Changes

The issue requests first-class Telegram reaction input so configured reactions can wake the agent, carry stable reaction keys, support operator semantics, and provide useful observability.

## Best Possible Solution

Choose one default-safe opt-in reaction wake contract, preferably the shared queue/wake/off policy, then track per-emoji semantics, custom-emoji metadata, prompt guidance, and durable feedback as explicitly scoped follow-ups or implementation requirements.

Yes, source-reproducible: current main accepts standard-emoji Telegram reactions and enqueues them as system events without requesting a heartbeat wake. I did not run a live Telegram account in this read-only cleanup review.

## Solution Assessment

Unclear until maintainers choose the public contract. A shared opt-in queue/wake/off policy looks safer than unconditional wake or Telegram-only drift, but the active candidates still need maintainer direction and live proof.

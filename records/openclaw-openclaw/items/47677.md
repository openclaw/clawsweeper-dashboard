## Label Justifications

- `P2`: This is a normal-priority channel improvement with real operator workflow impact, but it is not a first-run blocker, crash loop, security bypass, or urgent regression.
- `impact:message-loss`: Reaction-only Telegram inputs are received but remain passive until another turn, so the user-visible channel signal is effectively delayed or suppressed for wake-driven workflows.

## Summary

Keep open: current main and latest release still treat accepted Telegram reactions as passive queued system events, while reliable reaction-only wakes, custom-emoji reaction keys, and first-class reaction semantics remain unresolved and are currently represented by open implementation/product-direction work.

## What This Changes

The issue requests first-class Telegram reaction inputs that can wake an agent, normalize standard and custom emoji, support operator semantics, and expose enough observability for debugging.

## Best Possible Solution

Land or narrow a shared opt-in reaction wake policy with stable reaction keys, keep default queue-only compatibility, document the operator semantics boundary, and require focused tests plus live Telegram proof before closing this issue.

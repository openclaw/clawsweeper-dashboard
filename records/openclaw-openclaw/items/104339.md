## Summary

This PR should remain open because the increasing wait occurs after the next connection has already started, so it does not achieve the stated throttling goal and can delay recovery; the defect is narrow enough to repair, but real Discord runtime proof is also still required.

## What This Changes

The PR replaces the Discord gateway READY supervisor’s fixed two-second retry delay with an exponential two-to-thirty-second schedule.

## Best Possible Solution

If the READY supervisor needs throttling beyond the internal gateway policy, wait before initiating the next restart, then poll READY immediately; add exact fake-timer coverage for reconnect timing, prompt success recognition, and abort behavior.

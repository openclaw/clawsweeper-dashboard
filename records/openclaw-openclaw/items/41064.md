## Label Justifications

- `P1`: The issue affects active Dashboard chat runs where reconnect or tab switching can misrepresent a running session as idle and disrupt the operator workflow.
- `impact:session-state`: The reported failure loses or misrepresents active session run state after returning to chat or reconnecting.
- `impact:message-loss`: A stale idle state can route a new send instead of queueing behind an in-flight response, risking interrupted or replaced chat output.

## Summary

Keep open: current main and the latest release still clear local Dashboard chat run state on reconnect, and send/queue decisions still rely on local `chatRunId` rather than the recovered session-row active-run state. The open linked PR is the candidate fix, but it remains unmerged, conflicting, and proof-gated.

## What This Changes

The issue reports that Gateway Dashboard chat should preserve Stop/Queue busy state after tab or reconnect restoration so an active run is not treated as idle.

## Best Possible Solution

Review, repair, or replace https://github.com/openclaw/openclaw/pull/41067 so one authoritative active-run state drives rendering, send/queue, abort, stream ownership, and cleanup, then prove the Dashboard tab-return/reconnect flow in a real setup.

## Reproduction Assessment

Yes, at source level: current main clears local run state during reconnect hello while `sessionsResult` can still report an active run, and send/queue logic only treats local `chatRunId` as busy. I did not run a live Dashboard tab-switch scenario.

## Solution Assessment

No merged solution fully solves this yet. The current partial Stop recovery is not authoritative for send/queue behavior, and the linked PR must be reviewed, repaired, or replaced before this issue can close.

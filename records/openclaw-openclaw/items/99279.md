## Summary

Keep open. Current main and the latest release still lack Mattermost inbound bot-identity facts, Mattermost `allowBots`, and Mattermost bot-loop facts, so bot-authored Mattermost posts that pass sender policy can still reach dispatch as ordinary senders.

## What This Changes

The issue asks for Mattermost inbound bot identity handling so shared bot-loop protection or an explicit bot-admission policy can guard bot-authored Mattermost messages.

## Best Possible Solution

Add a Mattermost plugin-owned design that derives reliable inbound bot facts, keeps existing default admission compatible, and wires accepted bot-authored turns into the shared bot-loop guard with focused tests and docs.

## Reproduction Assessment

Yes from source inspection, but not from a live Mattermost deployment in this review. Current main clearly admits non-self Mattermost senders through ordinary access gates and never supplies bot-loop facts or `SenderIsBot`; a live two-bot Mattermost loop would still be useful proof for the final design.

## Solution Assessment

Unclear as an implementation direction because this is a policy/config/security decision, not a narrow strict bug fix. The likely best path is to populate reliable Mattermost bot identity in the plugin and then decide whether an explicit `allowBots` mode is required before enabling bot-authored admission semantics.

## Summary

Keep open. Current main and the latest release still lack a Mattermost inbound bot-identity or bot-admission path, so Mattermost posts from other bots or webhooks that pass ordinary sender and mention/thread gates can reach dispatch without the shared bot-pair loop guard; the remaining decision is product/security policy for Mattermost defaults and webhook handling.

## What This Changes

The issue requests Mattermost inbound bot identity handling so bot-loop protection or an explicit bot-admission policy can guard multi-bot and webhook-authored Mattermost messages.

## Best Possible Solution

Add a Mattermost-owned bot identity and admission design that validates user/webhook identity, wires accepted bot-authored turns into the shared bot-pair guard, and documents/tests upgrade-safe defaults for DMs, channels, groups, and participated threads.

## Reproduction Assessment

Yes, at source level: Mattermost filters self/system posts, then admits allowed senders and participated-thread follow-ups without bot identity facts, and the strict config schema has no allowBots or Mattermost botLoopProtection surface. I did not run a live two-bot Mattermost deployment, so this is source-reproducible rather than runtime-reproduced.

## Solution Assessment

Unclear as a final product shape: wiring reliable Mattermost bot facts into the existing shared pair-loop guard is the right owner boundary, but maintainers still need to choose allowBots/default semantics and webhook handling before implementation.

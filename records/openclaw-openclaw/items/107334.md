- `P2`: This is a meaningful but non-regression UX and provider-management improvement with broad scope and existing supported setup paths.
- `impact:auth-provider`: The proposal directly concerns provider credentials, model availability, default-model selection, and routing between providers.
- `impact:ux-friction`: Users can configure providers through onboarding, CLI, or schema-driven settings, but the fragmented workflow creates avoidable confusion and manual support burden.

## Summary

Keep this issue open for product scoping: current main already provides model pickers, schema-driven configuration, provider usage cards, quotas, spend, and budgets, but it does not yet provide the requested guided provider onboarding and unified routing-policy experience.

## What This Changes

Add a purpose-built Control UI experience for connecting LLM providers, managing credentials and discovered models, selecting defaults, viewing usage, and defining model-routing rules.

## Best Possible Solution

Ship a phased, provider-neutral Control UI manager that reuses plugin auth/catalog/usage contracts and existing `models.list` and config APIs for connect, test, browse, default, and fallback flows; evaluate automatic task routing separately as an explicit, auditable plugin/API or product RFC.

## Risks / Open Questions

- The request combines provider onboarding, credential management, model catalog discovery, billing display, default/fallback selection, and automatic task routing; treating it as one implementation risks multiple competing sources of truth.
- Provider keys, OAuth profiles, connection tests, and endpoint details cross security and plugin-ownership boundaries and must remain on the Gateway rather than being exposed or persisted in the browser.
- Automatic task- or cost-based routing can silently change the selected provider, price, capabilities, tool policy, or data destination, so it needs explicit policy semantics and auditability rather than UI-only heuristics.

## Summary

Keep open: current main has not shown a fix for the reported iOS Limited Photos failure, and the relevant source still depends on the iOS app's permission snapshot matching `PHPhotoLibrary.authorizationStatus(for: .readWrite)` while the reporter has a concrete device repro where that snapshot reaches the gateway as `photos: false`.

## What This Changes

The issue reports that iOS Photos Limited Access is reported to the gateway as `photos: false`, causing `photos.latest` to fail with `PHOTOS_PERMISSION_REQUIRED`.

## Best Possible Solution

Use one canonical iOS Photos permission helper for request, settings/status display, gateway `device.permissions`, and `photos.latest`, treating `.limited` as allowed and proving the limited-access flow on a real iOS setup.

## Reproduction Assessment

Yes, source-reproducible with reporter-provided device steps: current main shows the gateway trusts the iOS node's Photos permission boolean, and the iOS node computes that boolean from the same Photos authorization status path that the report says fails under Limited Access. I did not run a real iOS Limited Access reproduction.

## Solution Assessment

Yes, the best fix is narrow: align iOS Photos permission request/status/reporting and `photos.latest` behind one helper, then validate Limited Access live. A gateway-only workaround would be the wrong layer because the gateway cannot infer the native Photos grant.

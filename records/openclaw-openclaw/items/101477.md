## Summary

This PR addresses a still-live unbounded cron quarantine-sidecar read on current main, but its new five-file pruning policy silently deletes persistent recovery records without maintainer approval. The branch also needs a current-main rebase and inspectable after-fix runtime evidence before merge.

## What This Changes

The branch replaces unbounded cron quarantine-sidecar reads with an 8 MiB cap, rotates oversized sidecars so writes can continue, and retains only the five newest recovery archives.

## Best Possible Solution

Keep the bounded read and write-cap goal, but have the cron persistence owner choose a documented recovery-record lifecycle—preferably preserving archives until a doctor-owned or explicit cleanup path exists—then rebase and demonstrate the accepted behavior with redacted live output.

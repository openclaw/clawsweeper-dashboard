## Summary

The bounded read is sound hardening, but the added write cap is unsafe: the quarantine is append-only, and once it exceeds 8 MiB the throw leaves pending quarantine work uncleared so `persist()` refuses subsequent durable cron writes. The previous P1 remains unresolved on this rebased head.

## What This Changes

The PR replaces an unbounded cron quarantine sidecar read with the shared bounded-file reader, rejects serialized quarantine writes above 8 MiB, and adds oversized read/write regression tests.

## Best Possible Solution

Keep the bounded `readRegularFile` load, but serialize a deterministic byte-bounded set of quarantine records—retaining the newest useful repair evidence—so reaching the limit cannot prevent normal cron persistence; cover accumulated entries at both store and service levels.

## Reproduction Assessment

Yes. Accumulate enough unique invalid cron rows for the merged quarantine JSON to exceed 8 MiB, then perform a cron mutation requiring persistence; the new throw makes the quarantine flush fail and `persist()` returns false before the durable store write.

## Solution Assessment

No. Reusing the shared bounded reader is the narrowest maintainable read-side fix, but the write side must bound retained history rather than make append-only diagnostics a prerequisite for future cron persistence.

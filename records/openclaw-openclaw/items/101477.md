## Summary

The bounded read/write and archive-recovery direction is useful and has credible real-runtime proof, but this PR still changes recovery-record retention by silently deleting the oldest archives after five overflows. That data-lifecycle choice needs explicit owner approval before merge; the GitHub merge result is also currently dirty and must be refreshed after the decision.

## What This Changes

The branch caps cron quarantine sidecar reads and writes at 8 MiB, archives an oversized sidecar so cron writes can continue, and retains only the five newest archive files.

## Best Possible Solution

Keep the bounded read/write and archive-recovery work, but have the cron persistence owner explicitly choose the archive lifecycle; the safer default is a doctor-owned, inspectable cleanup or recovery path rather than unconditional runtime deletion.

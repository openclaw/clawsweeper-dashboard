## Summary

Keep open: current main and v2026.6.11 still use in-process command lanes, Gateway-owned cron execution, process-local cron locks/active markers, local SQLite task ledgers, and no Redis/BullMQ-style distributed worker queue or shared job-claiming contract.

## What This Changes

The issue requests Redis/BullMQ-style horizontal scaling with distributed job orchestration, worker processes, retries/backoff, dead-letter handling, scheduled jobs, and queue observability.

## Best Possible Solution

Define a backend-neutral distributed scheduler/job ownership contract or plugin API first, then decide whether Redis/BullMQ is one implementation and coordinate the narrower cron HA, session storage, runtime, and worker-auth trackers.

Options:

- **Design Backend-Neutral Contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron support, observability, and security review requirements before any Redis/BullMQ-specific implementation lands.
- **Document External Orchestration:** Keep OpenClaw core single-process for now and document ScalyClaw/BullMQ-style orchestration as an external deployment or plugin pattern without adding core runtime surfaces.
- **Defer To Narrow Trackers:** Let cron HA, external session storage, distributed runtime, and worker-auth issues establish core boundaries first, then revisit whether a broad distributed worker layer is still needed.

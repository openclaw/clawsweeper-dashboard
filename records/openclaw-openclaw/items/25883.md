## Summary

Keep open. Current main still has process-local command lanes, Gateway-local cron execution, process-local active cron/job ownership, SQLite-backed local ledgers, and no Redis/BullMQ-style distributed worker queue or shared worker claiming; related open issues cover narrower slices without replacing this broader architecture proposal.

## What This Changes

The issue proposes Redis/BullMQ-style distributed job orchestration with separate workers, shared queue state, retries/backoff, cron/delayed jobs, and observability for horizontally scaled OpenClaw deployments.

## Best Possible Solution

Keep this as the broad horizontal job-orchestration architecture tracker until maintainers decide whether to add a backend-neutral distributed scheduler/job seam, split pieces into narrower cron/session/runtime trackers, or document the ScalyClaw-style Redis/BullMQ approach as an external/plugin pattern.

## Reproduction Assessment

Yes for source confirmation, not as a bug reproduction: current main uses in-process command lanes, Gateway-local cron execution, process-local active cron markers, and SQLite-backed local ledgers, so the missing distributed Redis/BullMQ-style worker queue is directly visible in code and docs.

## Solution Assessment

Unclear as a direct implementation: Redis/BullMQ is useful prior art, but the best OpenClaw path needs maintainer direction on backend-neutral API shape, core versus plugin ownership, config surface, credentials, failure semantics, and upgrade behavior.

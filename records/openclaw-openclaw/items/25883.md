## Summary

Keep open: current main and v2026.6.11 still lack the requested Redis/BullMQ-style distributed job orchestration, shared worker claiming, dead-lettered worker backend, and horizontal coordination; the ScalyClaw prototype is useful prior art, but this remains a broad architecture/product decision.

## What This Changes

The issue requests a Redis/BullMQ-style distributed scheduler and job orchestration layer for background, delayed, cron, retry, and worker-scaled OpenClaw work.

## Best Possible Solution

Keep this open for maintainer architecture review and define a backend-neutral distributed scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as the implementation detail.

Rationale: The source gap is clear, but backend boundary, config shape, worker failure semantics, credential model, observability, and core-versus-plugin ownership require maintainer architecture intent.

Owner confidence: high

Options:

- **Design Backend-Neutral Contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron support, and observability before any Redis/BullMQ-specific code lands.
- **Document External Pattern:** Keep core single-process for now and document ScalyClaw/BullMQ-style orchestration as an external deployment or plugin pattern.
- **Defer To Narrower Trackers:** Let cron HA, external session storage, distributed runtime, and federation decisions settle first, then revisit whether a broader distributed worker layer is still needed.

## Reproduction Assessment

Yes, source-level only: current main still has process-local command lanes, Gateway-local cron execution, process-local cron locks, and no Redis/BullMQ-style worker backend or distributed job-claiming contract.

## Solution Assessment

No, not as a direct Redis/BullMQ core integration yet. The maintainable path is a maintainer-approved backend-neutral scheduler/job ownership contract with a clear core-or-plugin boundary.

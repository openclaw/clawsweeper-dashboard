## Summary

Keep open: current main and v2026.6.11 still lack the requested Redis/BullMQ-style distributed job orchestration layer, shared worker claiming, external queue backend, dead-letter semantics, or horizontal worker coordination. The issue remains useful architecture input rather than a cleanup-close candidate.

## What This Changes

The issue proposes a Redis/BullMQ-backed distributed job orchestration layer for background work, delayed jobs, scheduled jobs, retries, observability, and horizontal worker scaling.

## Best Possible Solution

Keep this as the broad architecture tracker while maintainers define a backend-neutral scheduler/job ownership contract and decide which pieces belong in core, plugin APIs, ClawHub, or narrower cron/session/runtime issues.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw define a backend-neutral distributed scheduler/job ownership contract in core or plugin APIs, route Redis/BullMQ orchestration to a ClawHub plugin on current seams, or defer the broad layer to narrower cron/session/runtime trackers?

Rationale: The source gap is clear, but backend boundary, worker failure semantics, config/credential shape, observability, cron ownership, and core-versus-plugin policy are architecture and product choices automation cannot safely choose.

Likely owner: steipete

Owner reason: steipete has the strongest live issue signal and current queue/cron/task architecture history for the product boundary decision.

Owner confidence: high

Options:

- **Design Backend-Neutral Contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron support, observability, and security review before backend-specific code lands.
- **Route Queue Backend To Plugin:** Keep core Tasks/TaskFlow canonical and ask Redis/BullMQ durable executor work to ship through ClawHub unless a plugin proves a narrow missing core API.
- **Defer To Narrower Trackers:** Let cron HA, external session storage, distributed runtime, Kubernetes worker auth, and execution-backend issues settle first, then revisit whether a broader queue layer remains necessary.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 still use in-process queue lanes, Gateway-local cron execution, process-local cron locks/active markers, and no Redis/BullMQ-style distributed worker backend. I did not run a live multi-Gateway load test in this read-only review.

## Solution Assessment

No, not as a direct Redis/BullMQ core integration yet. The maintainable path is a maintainer-approved backend-neutral scheduler/job ownership contract, with plugin/ClawHub implementation preferred for optional queue backends unless cron or task APIs are missing.

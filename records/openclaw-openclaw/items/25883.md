## Summary

Keep open: current main and the latest release still use in-process command lanes, Gateway-local cron ownership, process-local cron locks, local SQLite task ledgers, and no Redis/BullMQ-style distributed worker queue or shared job-claiming contract. This remains a broad architecture/product decision, with the linked ScalyClaw prototype useful as prior art rather than a drop-in core fix.

## What This Changes

The issue proposes a Redis/BullMQ-style distributed job orchestration layer for background work, delayed tasks, scheduled jobs, retries, dead-lettering, observability, and horizontal worker scaling.

## Best Possible Solution

Keep this open for maintainer architecture review and define a backend-neutral distributed scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as the implementation detail; preserve ScalyClaw as useful prior art and coordinate narrower slices with the cron HA, external session storage, and distributed runtime trackers.

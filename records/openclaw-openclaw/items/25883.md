## Label Justifications

- `P2`: The proposal targets meaningful production scalability and reliability but remains a broad architecture feature rather than an urgent confirmed regression.
- `impact:session-state`: Multi-instance worker ownership and task/session coordination can drift without shared state or distributed claiming.
- `impact:message-loss`: The described job orchestration gap can delay, miss, duplicate, or fail scheduled/background deliveries under load or multi-instance deployment.

## Summary

Keep open: current main and the latest release still use in-process command lanes, Gateway-local cron ownership, process-local cron locks/active-job guards, and local task indexes rather than the requested Redis/BullMQ-style distributed job orchestration layer. The linked ScalyClaw prototype is useful prior art, but the remaining work is a broad architecture/product decision, not conservative cleanup-closeable work.

## What This Changes

Request to add Redis/BullMQ-style distributed job orchestration, worker processes, retries/backoff, dead-letter handling, scheduled jobs, and observability for horizontal scaling.

## Best Possible Solution

Keep this open for maintainer architecture review and define a backend-neutral distributed scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as an implementation detail.

Rationale: The source gap is clear, but the backend boundary, config shape, worker failure semantics, credential model, observability surface, and core-versus-plugin ownership require maintainer architecture intent.

Owner confidence: high

Options:

- **Design Backend-Neutral Contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron support, observability, and plugin/core ownership before any Redis/BullMQ-specific code lands.
- **Document External Pattern:** Keep OpenClaw's built-in runtime single-process for now and document ScalyClaw/BullMQ-style orchestration as an external deployment or plugin pattern.
- **Defer To Narrow Trackers:** Let the cron HA, external session storage, and distributed runtime issues settle first, then revisit whether a broader distributed worker layer is still needed.

Yes. Source inspection on current main shows process-local command lanes, Gateway-local cron execution, process-local cron locks/active-job guards, and local task indexes with no Redis/BullMQ-style distributed job claiming; I did not run a live multi-Gateway load test in this read-only review.

## Solution Assessment

No, not as a direct Redis/BullMQ core integration yet. The maintainable path is a maintainer-approved backend-neutral scheduler/job ownership contract with a clear core-or-plugin boundary.

- `P2`: The proposal targets meaningful production scalability and reliability, but it is a broad architecture feature rather than an urgent confirmed regression.

## Summary

Keep open: current main and the latest release still use in-process command lanes, Gateway-local cron scheduling, process-local cron locks, and local SQLite-backed task/flow ledgers rather than a Redis/BullMQ-style distributed worker/job orchestration layer. The ScalyClaw prototype is useful prior art, but integrating this requires maintainer architecture direction rather than cleanup closure.

## What This Changes

The issue proposes Redis/BullMQ-style distributed job orchestration, workers, retries, delayed/cron jobs, and observability for horizontally scaled OpenClaw deployments.

## Best Possible Solution

Define a maintainer-approved backend-neutral distributed scheduler/job ownership contract or plugin API first, then decide whether ScalyClaw/BullMQ-style Redis orchestration belongs in core, a plugin, or external deployment docs.

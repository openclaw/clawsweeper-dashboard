## Summary

Keep open: current main and v2026.6.11 still use in-process command lanes, Gateway-local cron execution, process-local cron locks/active-job markers, and SQLite-backed local task/cron ledgers rather than the requested Redis/BullMQ-style distributed job orchestration layer. The related cron HA, session storage, and distributed runtime issues are useful slices, but none replaces this broader architecture decision.

## What This Changes

The issue proposes adding a Redis/BullMQ-style distributed job orchestration layer, using the ScalyClaw prototype as prior art for horizontally scaled background jobs, delayed jobs, cron, retries, worker processes, and observability.

## Best Possible Solution

Keep this open for maintainer architecture review and define a backend-neutral distributed scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as the implementation detail.

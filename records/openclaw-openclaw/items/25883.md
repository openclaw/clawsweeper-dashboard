## Label Justifications

- `P2`: The proposal targets meaningful production scalability and reliability, but it is a broad feature/design item rather than an urgent confirmed regression.
- `impact:session-state`: The requested distributed ownership layer would prevent local task, run, and worker state from drifting across horizontally scaled instances.

## Summary

Keep open: current main and v2026.6.11 still use process-local command queues, Gateway-local cron execution, process-local cron locks, and local SQLite-backed task/cron ledgers rather than Redis/BullMQ-style distributed job and worker coordination. The linked ScalyClaw prototype is useful prior art, but integrating this needs maintainer architecture direction.

## What This Changes

The issue proposes a Redis/BullMQ-backed job orchestration layer with dedicated workers, delayed and scheduled jobs, retries/backoff, dead-letter handling, and queue observability for horizontally scaled OpenClaw deployments.

## Best Possible Solution

Define a maintainer-approved backend-neutral distributed scheduler/job ownership contract or plugin API first, then decide whether ScalyClaw/BullMQ-style Redis orchestration belongs in core, a plugin, or external deployment docs.

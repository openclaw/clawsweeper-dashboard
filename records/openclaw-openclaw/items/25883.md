## Label Justifications

- `P2`: The proposal targets meaningful production scalability and reliability, but it is a broad feature/design item rather than an urgent confirmed regression.
- `impact:session-state`: The requested horizontal scaling model would change where session, task, and worker ownership state lives and how it is coordinated across instances.
- `impact:message-loss`: The issue and related cron HA reports describe delayed, duplicated, or missed background/channel deliveries in multi-instance deployments.

## Summary

Keep open: current main and v2026.6.11 still use in-process command lanes, Gateway-local cron ownership, process-local cron locks, and local task/flow registries, with no Redis/BullMQ-style distributed worker queue or shared job-claiming contract. This remains a broad architecture/product decision, and the related open issues cover narrower cron, session, runtime, or federation slices rather than replacing this tracker.

## What This Changes

The issue proposes Redis/BullMQ-style distributed job orchestration, worker processes, retries/backoff, dead-letter handling, cron support, and observability for horizontally scaled OpenClaw deployments.

## Best Possible Solution

Keep this issue open as the broad horizontal-scaling/job-orchestration tracker, then have maintainers define a backend-neutral scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as an implementation detail; preserve ScalyClaw as prior art and coordinate narrower slices with the cron HA, external session storage, distributed runtime, and federation trackers.

- **Defer to narrower trackers:** Let cron HA, external session storage, and distributed runtime issues establish boundaries first, then revisit whether a broad distributed worker layer is still needed.

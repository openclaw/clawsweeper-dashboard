## Summary

Keep open: current main and v2026.6.11 still lack the requested Redis/BullMQ-style distributed job orchestration layer, and the open cron HA, session storage, and distributed runtime issues are narrower overlaps rather than replacements.

## What This Changes

The issue proposes horizontal scaling through Redis/BullMQ-style job queues, independent workers, retries/backoff, scheduled jobs, dead-letter handling, and queue observability.

## Best Possible Solution

Keep this open for maintainer architecture review and define a backend-neutral scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as an implementation detail.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a backend-neutral distributed scheduler/job ownership contract in core or plugin APIs, document Redis/BullMQ-style orchestration as external only, or defer the broad job layer to narrower cron/session/runtime trackers?

Rationale: The source gap is clear, but backend boundary, config shape, credential model, failure semantics, observability surface, and core-versus-plugin ownership are product and architecture decisions automation cannot safely choose.

Likely owner: steipete

Owner reason: steipete has the strongest live issue signal and current queue/cron architecture history for this decision.

Owner confidence: high

Options:

- **Design Backend-Neutral Contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron support, observability, and security review before backend-specific code lands.
- **Document External Pattern:** Keep core single-process for now and document ScalyClaw/BullMQ-style orchestration as an external deployment or plugin pattern.
- **Defer To Narrower Trackers:** Let cron HA, external session storage, distributed runtime, and federation issues settle first, then revisit whether a broader distributed worker layer is still needed.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 still have in-process queue lanes, Gateway-local cron execution, process-local locks/active-job markers, local SQLite task ledgers, and no Redis/BullMQ-style worker backend or distributed claiming contract. I did not run a live multi-Gateway load test in this read-only review.

## Solution Assessment

No, not as a direct Redis/BullMQ core integration yet. The maintainable path is a maintainer-approved backend-neutral scheduler/job ownership contract with a clear core-or-plugin boundary.

## Summary

Keep open. Current main and the latest release still use in-process queues, Gateway-local cron execution, process-local locks, and local SQLite task ledgers rather than Redis/BullMQ-style distributed job orchestration; the ScalyClaw prototype is useful prior art, but integration needs maintainer architecture direction.

## What This Changes

The issue proposes Redis/BullMQ-style horizontal scaling for background work, delayed jobs, cron jobs, worker coordination, retries, dead-letter handling, and job observability.

## Best Possible Solution

Keep this open for maintainer architecture review and define a backend-neutral distributed scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as the implementation detail.

Question: Should OpenClaw add a backend-neutral distributed scheduler/job ownership contract in core or plugin APIs, document Redis/BullMQ-style orchestration as external only, or defer the work to narrower cron/session/runtime trackers?

Rationale: The source gap is clear, but the backend boundary, config shape, worker failure semantics, credential model, observability surface, and core-versus-plugin ownership are product and architecture decisions.

Likely owner: steipete

Owner confidence: high

Options:

- **Design Backend-Neutral Contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron ownership, and observability before any Redis/BullMQ-specific implementation lands.
- **Document External Pattern:** Keep core single-process for now and document ScalyClaw/BullMQ-style orchestration as an external deployment or plugin pattern without adding core surfaces yet.
- **Defer To Narrower Trackers:** Use the cron HA, external session storage, distributed runtime, and cross-gateway issues to settle individual boundaries before revisiting a broader job orchestration layer.

## Reproduction Assessment

Yes. Source inspection shows current main still uses process-local command lanes, Gateway-local cron execution, process-local cron locks, and local SQLite task ledgers with no Redis/BullMQ-style worker backend or distributed job-claiming contract.

## Solution Assessment

No, not as a direct Redis/BullMQ core integration yet. The maintainable path is a maintainer-approved backend-neutral scheduler/job ownership contract with a clear core-or-plugin boundary.

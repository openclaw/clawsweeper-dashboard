## Summary

Current main and the latest release still use local/process-scoped queue, cron, active-job, and task-state surfaces, so the requested distributed job orchestration remains a real architecture/product decision rather than cleanup-closeable work.

## What This Changes

The issue proposes a Redis/BullMQ-style distributed job orchestration layer with separate workers, retries/backoff, delayed and cron jobs, dead-letter handling, state visibility, and horizontal worker coordination.

## Best Possible Solution

Define a maintainer-approved backend-neutral distributed scheduler/job ownership contract or plugin API first, then decide whether ScalyClaw/BullMQ-style Redis orchestration belongs in core, a plugin, or external deployment docs.

- **Defer To Narrower Trackers:** Use the cron HA, external session storage, and distributed runtime issues to settle individual boundaries before revisiting a broader job orchestration layer.

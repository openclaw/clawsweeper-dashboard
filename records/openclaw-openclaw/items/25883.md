## Summary

Keep open: current main and v2026.6.11 still use process-local command lanes and Gateway-local cron/task coordination, so the Redis/BullMQ-style distributed job orchestration request remains a broad architecture/product decision rather than cleanup-close material.

## What This Changes

The issue proposes a Redis/BullMQ-backed distributed job orchestration layer with separate workers, retries/backoff, delayed and scheduled jobs, dead-letter behavior, and queue observability.

## Best Possible Solution

Keep this open for maintainer architecture review and define a backend-neutral distributed scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as the implementation detail.

## Summary

Keep open. Current main and v2026.6.11 still use process-local command lanes, Gateway-owned cron execution, local/process-owned task runtime indexes, and no Redis/BullMQ-style distributed job backend; this remains broad architecture input that needs maintainer product direction rather than cleanup closure.

## What This Changes

The issue proposes adding a Redis/BullMQ-style distributed job orchestration layer for horizontal scaling, including separate workers, delayed and scheduled jobs, retries, dead-letter handling, and queue observability.

## Best Possible Solution

Keep this open for maintainer architecture review, decide whether OpenClaw should expose a generic distributed scheduler/job backend or plugin seam, and coordinate the narrower cron and session-storage slices through the linked open issues.

## Reproduction Assessment

Yes for the architectural gap: source and docs show no distributed Redis/BullMQ-style queue, worker claiming, coordination backend, or dead-letter system on current main. I did not run a live high-load or multi-host reproduction because this is a feature proposal, not a narrow bug report.

## Solution Assessment

Unclear as an implementation. Redis/BullMQ and the ScalyClaw prototype are useful prior art, but maintainers first need to choose the core/plugin boundary, failure semantics, security posture, and upgrade/config path.

## Summary

Keep open. Current main and v2026.6.11 still use process-local command lanes, Gateway-owned cron scheduling, local active-job ownership, and SQLite-backed task/cron ledgers rather than a Redis/BullMQ-style distributed worker queue; the ScalyClaw prototype is useful prior art, but this needs maintainer architecture/product review instead of cleanup closure.

## What This Changes

The issue proposes a Redis/BullMQ-backed horizontal scaling architecture with distributed job queues, worker processes, retries/backoff, delayed and scheduled jobs, failure handling, and job-state observability.

## Best Possible Solution

Keep this as broad architecture input, then decide whether OpenClaw should define a backend-neutral distributed scheduler/job API or document Redis/BullMQ-style orchestration as an external/plugin pattern while coordinating the narrower cron and session slices.

## Reproduction Assessment

Yes, as source confirmation rather than a bug repro: current main visibly lacks distributed queue ownership, external worker claiming, leader leasing, or Redis/BullMQ config/API. I did not run a multi-host load test in this read-only review.

## Solution Assessment

Unclear as the literal Redis/BullMQ core change. Redis/BullMQ is plausible prior art, but the maintainable OpenClaw solution first needs a maintainer decision on core versus plugin/API seam, backend neutrality, failure semantics, credentials, and upgrade behavior.

## Label Justifications

- `P2`: The issue targets meaningful production scalability and reliability, but it is a broad architecture feature rather than an urgent confirmed regression.
- `impact:session-state`: Distributed job ownership and worker coordination would affect how multi-instance task, runtime, cron, and session state stay associated.
- `impact:message-loss`: The described orchestration gap can delay, miss, duplicate, or fail scheduled/background deliveries under load or multi-instance deployment.

## Summary

Keep open: current main and the latest release still use in-process queue lanes, Gateway-local cron execution, process-local cron locks, and local process indexes for task state; the requested Redis/BullMQ-style distributed worker orchestration is a real feature gap that needs maintainer architecture direction rather than cleanup closure.

## What This Changes

The issue proposes a Redis/BullMQ-style distributed job orchestration layer for background tasks, delayed jobs, cron jobs, workers, retries, failure handling, and queue observability.

## Best Possible Solution

Keep this open for maintainer architecture review and define a backend-neutral scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as an implementation detail, while coordinating the narrower cron HA, session storage, and distributed-runtime trackers.

Options:

- **Defer To Narrower Trackers:** Let cron HA, external session storage, distributed runtime, and federation issues settle first, then revisit whether a broader distributed worker layer is still needed.

## Summary

Keep open. Current main and v2026.6.11 still use in-process command lanes, Gateway-local cron execution, SQLite task ledgers, and process-local active-job indexes, so the requested distributed job orchestration layer remains a real architecture/product decision rather than cleanup-close material.

## What This Changes

The issue proposes Redis/BullMQ-style horizontal orchestration for background tasks, delayed jobs, scheduled jobs, retries, dead-letter handling, observability, and multi-instance worker coordination.

## Best Possible Solution

Keep this as maintainer architecture input until OpenClaw decides whether distributed job orchestration belongs in core, a new plugin/API seam, or documented external deployment guidance that preserves the ScalyClaw prototype as prior art.

## Reproduction Assessment

Yes, at the source level. Current code and docs show process-local queue/cron coordination plus SQLite task ledgers, while the requested distributed job backend, worker claiming, dead-letter queue, and shared observability layer are absent.

## Solution Assessment

Unclear as a direct implementation. Redis/BullMQ may be useful prototype evidence, but the best OpenClaw solution needs a maintainer decision on core versus plugin/API ownership, backend neutrality, failure semantics, and upgrade-safe config first.

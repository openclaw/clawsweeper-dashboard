- `P2`: The proposal targets meaningful production scalability and reliability, but it is a broad feature/design item rather than an urgent confirmed regression.
- `impact:session-state`: The requested horizontal scaling model would change where session, task, and worker ownership state lives and how it is coordinated across instances.

## Summary

Keep open: current main and the latest release still use in-process command lanes, Gateway-owned cron scheduling, process-local cron locks, and local SQLite task/flow ledgers, so the Redis/BullMQ-style distributed worker queue and shared job-claiming contract remain unimplemented.

## What This Changes

Request to add a Redis/BullMQ-style distributed job orchestration layer for background, delayed, scheduled, retried, and observable work across horizontally scaled OpenClaw instances.

## Best Possible Solution

Keep this open for maintainer architecture review and first define a backend-neutral distributed scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as the implementation detail.

Owner confidence: high

Options:

- **Design backend-neutral contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron support, observability, and security review requirements before any Redis/BullMQ-specific implementation lands.
- **Document external orchestration:** Keep OpenClaw core single-process for now and document ScalyClaw/BullMQ-style orchestration as an external deployment or plugin pattern without adding core runtime surfaces.
- **Defer to narrower trackers:** Let cron HA, external session storage, and distributed runtime issues establish the core boundaries first, then revisit whether a broad distributed worker layer is still needed.

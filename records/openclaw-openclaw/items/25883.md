## Summary

Keep open: current main still lacks the requested Redis/BullMQ-style distributed job orchestration, shared worker claiming, dead-letter handling, and horizontal worker coordination; the ScalyClaw prototype is useful prior art, but this remains architecture/product work.

## What This Changes

Request to add a Redis/BullMQ-style distributed job orchestration layer for background, delayed, scheduled, and long-running OpenClaw work.

## Best Possible Solution

Keep this as the broad architecture tracker and design a backend-neutral scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as an implementation detail.

Options:

- **Design Backend-Neutral Contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron support, and observability before any Redis/BullMQ-specific code lands.
- **Document External Pattern:** Keep core single-process for now and document ScalyClaw/BullMQ-style orchestration as an external deployment or plugin pattern.
- **Defer To Narrower Trackers:** Let cron HA, external session storage, distributed runtime, and subagent placement decisions settle first, then revisit whether a broader distributed worker layer is still needed.

## Reproduction Assessment

Yes, source-level only: current main still has process-local command lanes, Gateway-local cron execution, process-local cron locks, and local SQLite-backed ledgers with no Redis/BullMQ-style worker backend or distributed job-claiming contract.

## Solution Assessment

No, not as a direct Redis/BullMQ core integration yet; the maintainable path is a maintainer-approved backend-neutral scheduler/job ownership contract with a clear core-or-plugin boundary.

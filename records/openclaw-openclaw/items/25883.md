## Summary

Keep open. Current main and v2026.6.11 still use in-process command lanes, Gateway-local cron execution, and SQLite-backed task records rather than a Redis/BullMQ-style distributed queue with worker claiming, dead-letter handling, or horizontal worker coordination; however, the requested direction is broad architecture/product work, not a cleanup-close or autonomous fix-PR candidate.

## What This Changes

The issue proposes adding a Redis/BullMQ-style distributed job orchestration layer for background, delayed, scheduled, and horizontally scaled OpenClaw work.

## Best Possible Solution

Keep this issue open as broad maintainer architecture input, decide the supported distributed work-ownership boundary first, and coordinate narrower implementation slices through the cron coordination, external session storage, distributed runtime, worker placement, and post-response continuation trackers.

## Reproduction Assessment

Yes, at source level: current main still uses in-process queue lanes and Gateway-local cron execution with no Redis/BullMQ or distributed worker-claiming contract. I did not run a multi-instance load reproduction in this read-only review.

## Solution Assessment

No, not as a direct Redis/BullMQ core addition yet. The maintainable path needs maintainer approval for the ownership boundary, backend contract, security model, failure semantics, migration path, and whether this belongs in core or a plugin/API seam.

## Label Justifications

- `P2`: The proposal targets meaningful production scalability and reliability, but it is a broad feature/design item rather than an urgent confirmed regression.
- `impact:session-state`: The requested horizontal scaling model would change where task, worker, and agent ownership state lives and how it is coordinated across instances.
- `impact:message-loss`: The reported orchestration gap can delay, miss, duplicate, or fail scheduled/background deliveries under load or multi-instance deployment.

## Summary

Keep open: current main and the latest release still use in-process command lanes, Gateway-owned cron execution, process-local cron guards, and local SQLite task ledgers; the Redis/BullMQ-style distributed worker queue and shared job-claiming layer requested here is still a broad architecture decision rather than implemented or superseded work.

## What This Changes

The issue proposes adding a Redis-backed distributed job orchestration layer for scalable background jobs, delayed work, cron scheduling, retries, observability, and horizontal worker coordination.

## Best Possible Solution

Keep this open for maintainer architecture review and define a backend-neutral distributed scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as the implementation detail; preserve ScalyClaw as prior art and coordinate narrower slices with the cron HA, external session storage, and distributed runtime trackers.

Options:

- **Design backend-neutral contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron support, observability, and security review requirements before any Redis/BullMQ-specific implementation lands.

- **Defer to narrower trackers:** Let cron HA, external session storage, and distributed runtime issues establish the core boundaries first, then revisit whether a broad distributed worker layer is still needed.

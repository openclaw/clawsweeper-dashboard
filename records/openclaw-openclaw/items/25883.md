## Summary

Keep open: current main still lacks the requested Redis/BullMQ-style distributed job orchestration, shared worker claiming, dead-letter handling, and horizontal worker coordination, and the remaining question is a broad architecture/product decision rather than cleanup-close material.

## What This Changes

Requests Redis/BullMQ-style distributed job orchestration with dedicated workers, delayed and scheduled jobs, retries, failure handling, and observability for horizontal OpenClaw scaling.

## Best Possible Solution

Keep this as the broad architecture tracker and define a backend-neutral distributed scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as an implementation detail.

Options:

- **Design Backend-Neutral Contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron support, and observability before any Redis/BullMQ-specific code lands.
- **Document External Pattern:** Keep core single-process for now and document ScalyClaw/BullMQ-style orchestration as an external deployment or plugin pattern.
- **Defer To Narrower Trackers:** Let the cron HA, external session storage, and distributed runtime issues settle first, then revisit whether a broader distributed worker layer is still needed.

Yes, source-level only: current main still has process-local command lanes, Gateway-local cron execution, process-local cron locks, and local SQLite-backed ledgers with no Redis/BullMQ-style worker backend or distributed job-claiming contract. ## Solution Assessment

No, not as a direct Redis/BullMQ core integration yet. The maintainable path is a maintainer-approved backend-neutral scheduler/job ownership contract with a clear core-or-plugin boundary.

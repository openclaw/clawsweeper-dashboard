## Summary

Keep open: current main and the latest release still lack the requested Redis/BullMQ-style distributed worker queue, shared job claiming, dead-letter semantics, and horizontal worker coordination. The ScalyClaw prototype is useful prior art, but integrating this into OpenClaw needs maintainer architecture direction rather than a cleanup close.

## What This Changes

The issue proposes adding a Redis-backed distributed job orchestration layer with separate workers, retries/backoff, delayed and cron jobs, dead-letter handling, and observability for horizontally scaled OpenClaw deployments.

## Best Possible Solution

Keep this open for maintainer architecture review and define a backend-neutral distributed scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as an implementation detail.

Options:

- **Design backend-neutral contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron support, observability, and security review requirements before any Redis/BullMQ-specific implementation lands.
- **Document external orchestration:** Keep OpenClaw core single-process for now and document ScalyClaw/BullMQ-style orchestration as an external deployment or plugin pattern without adding core runtime surfaces.
- **Defer to narrower trackers:** Let the cron HA, external session storage, and distributed runtime issues establish the core boundaries first, then revisit whether a broad distributed worker layer is still needed.

## Solution Assessment

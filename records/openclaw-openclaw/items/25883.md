## Summary

Keep open: current main and v2026.6.11 still use local/in-process queue, cron, active-job, and task-ledger ownership rather than the requested Redis/BullMQ-style distributed worker orchestration, so this remains a maintainer architecture decision.

## What This Changes

The issue proposes Redis/BullMQ-style horizontal scaling with distributed background-job orchestration, separate workers, retries/backoff, dead-letter handling, scheduling, and queue observability.

## Best Possible Solution

Keep this issue open for maintainer architecture review and define a backend-neutral distributed scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as an implementation detail.

Options:

- **Design Backend-Neutral Contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron support, and observability before any Redis/BullMQ-specific code lands.

- **Defer To Narrower Trackers:** Let cron HA, external session storage, distributed runtime, and federation issues settle first, then revisit whether a broader distributed worker layer is still needed.

## Summary

Keep open: current main and v2026.6.11 still do not implement the requested Redis/BullMQ-style distributed job orchestration layer, and the related cron HA, session storage, runtime split, and federation issues are narrower overlaps rather than replacements.

## What This Changes

The issue proposes Redis/BullMQ-backed horizontal scaling for background jobs, delayed/cron work, separate workers, retries/backoff, dead-letter handling, and queue observability.

## Best Possible Solution

Keep this open for maintainer architecture review and define a backend-neutral scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as an implementation detail.

Rationale: The source gap is clear, but backend boundary, config shape, worker failure semantics, credential model, observability surface, and core-versus-plugin ownership are product and architecture decisions that automation cannot safely choose.

Options:

- **Design Backend-Neutral Contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron support, observability, and security review before backend-specific code lands.
- **Document External Pattern:** Keep core single-process for now and document ScalyClaw/BullMQ-style orchestration as an external deployment or plugin pattern.
- **Defer To Narrower Trackers:** Let cron HA, external session storage, distributed runtime, and federation issues settle first, then revisit whether a broader distributed worker layer is still needed.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 still have in-process queue lanes, Gateway-local cron execution, process-local locks/active-job markers, and no Redis/BullMQ-style worker backend or distributed job-claiming contract. ## Solution Assessment

No, not as a direct Redis/BullMQ core integration yet. The maintainable path is a maintainer-approved backend-neutral scheduler/job ownership contract with a clear core-or-plugin boundary.

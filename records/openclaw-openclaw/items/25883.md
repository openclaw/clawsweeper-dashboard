## Summary

Keep open: current main and v2026.6.11 still use in-process queues, Gateway-local cron execution, process-local cron locks, and local task ledgers rather than the requested Redis/BullMQ-style distributed job orchestration layer. The related cron/session/runtime items are useful slices, but none supersedes this broader architecture decision.

## What This Changes

The issue proposes horizontal scaling through a distributed Redis/BullMQ-style job orchestration layer with separate workers, retries/backoff, delayed and scheduled jobs, dead-letter handling, and observability.

## Best Possible Solution

Keep this open for maintainer architecture review: define a backend-neutral distributed scheduler/job ownership contract or plugin API before choosing Redis/BullMQ as an implementation detail, and preserve ScalyClaw as prior art while coordinating cron HA, external session storage, and distributed runtime design.

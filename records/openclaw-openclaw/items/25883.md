## Summary

Keep open: current `main` still does not implement the requested Redis/BullMQ-style distributed job orchestration layer, and the remaining work is a broad architecture/product decision rather than conservative cleanup.

## What This Changes

The issue proposes Redis/BullMQ-backed distributed job orchestration with dedicated workers, retries/backoff, delayed and cron jobs, dead-letter handling, and queue observability for horizontally scaled OpenClaw deployments.

## Best Possible Solution

Keep this as the broad architecture tracker while maintainers define a backend-neutral scheduler/job ownership contract and decide which pieces belong in core, plugin APIs, ClawHub, or narrower cron/session/runtime issues.

## Maintainer Decision

Question: Should OpenClaw define a backend-neutral distributed scheduler/job ownership contract in core or plugin APIs, route Redis/BullMQ-style orchestration to a ClawHub plugin on current seams, or defer the broad layer to narrower cron/session/runtime trackers?

Rationale: The source gap is clear, but backend boundary, worker failure semantics, config/credential shape, observability, cron ownership, and core-versus-plugin policy are maintainer architecture choices.

Likely owner: steipete

Owner reason: steipete has the strongest live issue signal plus the clearest queue/cron architecture history for choosing the boundary.

Owner confidence: high

Options:

- **Design backend-neutral contract (recommended):** Define shared queue/state, worker claiming, retries/backoff, dead-letter semantics, cron support, observability, and security review before backend-specific code lands.
- **Route queue backend to plugin:** Keep core Tasks/TaskFlow canonical and ask Redis/BullMQ durable executor work to ship through ClawHub unless a plugin proves a narrow missing core API.
- **Defer to narrower trackers:** Let cron HA, external session storage, distributed runtime, K8s worker auth, and execution-backend issues settle first, then revisit whether a broader queue layer remains necessary.

## Reproduction Assessment

Yes, source-level: current `main` and `v2026.6.11` still use in-process queue lanes, Gateway-local cron execution, process-local cron locks/active-job markers, and no Redis/BullMQ-style distributed worker backend. I did not run a live multi-Gateway load test in this read-only review.

## Solution Assessment

No, not as a direct Redis/BullMQ core integration yet. The maintainable path is a maintainer-approved backend-neutral scheduler/job ownership contract, with plugin or ClawHub implementation preferred for optional queue backends unless core cron/task APIs are missing.

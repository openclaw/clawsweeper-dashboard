## Summary

Keep open: the structured tool is a better boundary than visible-text parsing, but a reported failure is not terminal because a later `completed` report overwrites it and can suppress the cron error state and failure alert.

## What This Changes

This PR adds a cron-only `cron_report_outcome` agent tool and carries its structured outcome through the embedded-agent runner so cron runs can become errors without parsing final assistant text.

## System Context

Isolated cron jobs run an embedded agent and then translate its result metadata into a cron status, persisted counters, and optional failure alerts. This PR adds a model-to-runner outcome signal before that terminal status resolution.

## Architecture Diagram

  C --> D[Embedded run result]
  D --> E[Cron outcome resolver]
  E --> F[Run status]
  F --> G[Failure alert and counters]

## Best Possible Solution

Make a failed cron outcome write-once or failure-sticky, reject or ignore later outcome reports, add ordering coverage, and attach redacted proof of a real cron run reaching persisted `error` plus its configured failure alert.

## Reproduction Assessment

Yes. A cron agent can call `cron_report_outcome` with `failed` and then with `completed`; the handler stores only the latter report, and terminal resolution then lacks the fatal report needed for cron error classification.

## Solution Assessment

No. A typed tool is the right boundary, but the current mutable last-report-wins state does not implement a terminal failure outcome; latching fatal failure is the narrower maintainable repair.

## Summary

Keep open: current main and v2026.6.11 still ignore the Teams removal lifecycle that should bound session history, and two linked fix PRs are open rather than merged.

## What This Changes

The issue asks OpenClaw to stop silently reusing prior Microsoft Teams DM session history after a true Teams app removal and re-add lifecycle boundary.

## Best Possible Solution

Implement plugin-owned Teams lifecycle handling for true app-management removal that routes installationUpdate and bot membersRemoved, stales the exact routed session, removes or tombstones the cached conversation reference, preserves transcripts unless a separate retention policy says otherwise, and lands with redacted live Teams proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For true Microsoft Teams app-management removal, should OpenClaw stale the routed session and remove the cached proactive conversation reference, stale only the session, or delete retained Teams transcript/session data?

Rationale: The source gap is clear, but the durable behavior controls personal-chat history and proactive reachability after app removal, so automation should not choose the privacy-retention boundary alone.

Likely owner: steipete

Owner reason: Recent Teams conversation-store and security-sensitive state history makes this the best available owner for the retention-boundary choice.

Owner confidence: high

Options:

- **Stale session and clear cached reference (recommended):** Use the existing non-destructive stale-session pattern while removing or tombstoning the stored Teams conversation reference so proactive sends cannot keep a removed app chat alive.
- **Stale only the routed session:** Limit the fix to transcript-context isolation and accept cached proactive references as a separate follow-up risk.
- **Delete retained Teams data:** Treat removal as a destructive retention boundary, which needs explicit data-loss policy, migration behavior, and stronger security review.

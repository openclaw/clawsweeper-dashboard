## Summary

Keep open: current main and v2026.6.11 still lack Teams app-removal lifecycle handling, and the open linked PR is a candidate fix but has not merged or cleared review.

## What This Changes

The issue asks OpenClaw to stop silently reusing prior Microsoft Teams personal-DM session history after true app removal and re-add.

## Best Possible Solution

Handle true Teams app removal in the Teams plugin by staling the matched DM session and tombstoning stale proactive conversation refs, while documenting that Teams 'Remove chat history' is not server-visible.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For true Microsoft Teams app removal/uninstall events, what retention boundary should OpenClaw enforce for the affected personal DM?

Rationale: This decides a privacy boundary for retained user conversation history, and automation should not choose between non-destructive staling, proactive-reference tombstoning, or hard deletion without maintainer intent.

Likely owner: steipete

Owner reason: Recent Teams state-store and security-sensitive history makes this the best available routing owner for the retention-boundary choice.

Owner confidence: medium

Options:

- **Stale session and tombstone conversation ref (recommended):** Use the existing non-destructive session-boundary pattern, remove stale proactive conversation references, and leave transcript deletion to a separate retention policy.
- **Only stale the active session:** This is the narrowest fix but may leave stored proactive conversation references valid after uninstall.
- **Hard-delete retained Teams DM data:** This is strongest for privacy but needs explicit data-loss policy, migration, and stronger security review.

## Reproduction Assessment

Yes at source level and from the reporter's redacted live capture. Current main lacks installationUpdate and membersRemoved handling while Teams DMs reuse the routed session key; this review did not run a fresh Teams tenant.

## Solution Assessment

The best direction is plugin-owned lifecycle handling, not core session-key derivation or transcript deletion. The current linked PR is only a candidate because it still needs repair, retention-policy confirmation, and live proof.

## Summary

Keep open. Current main has queue recovery, normalized channel receipts, and transcript mirror markers, but it still lacks the requested durable transcript-entry to provider-message receipt ledger, per-entry delivery state, and transcript-vs-origin-channel reconciler.

## What This Changes

The issue requests durable delivery receipts and reconciliation between channel-scoped session transcripts and client-visible channel messages.

## Best Possible Solution

Design one generic SQLite-backed delivery ledger keyed by transcript entry and expected channel target, feed it from outbound send/recovery receipts, expose it through session/Gateway APIs and Control UI, and let adapters add reconciliation capability without duplicating queue state.

Options:

- **Design Generic Ledger First (recommended):** Add a SQLite-backed transcript delivery ledger tied to outbound receipts and adapter reconciliation, then surface per-entry status in session APIs and Control UI.
- **Limit To Queue Mitigations:** Keep accepting narrow recovery fixes while deferring the broader transcript/client delivery-state surface until maintainers are ready to commit to it.
- **Split Runtime And UI Work:** Create separate runtime-ledger and Control UI follow-up tracks if the full design is too large for one implementation lane.

No live Discord reproduction was run in this review. Source inspection does give a high-confidence way to verify the remaining gap: current main lacks a transcript-entry to provider-message ledger and per-entry delivery-state surface.

## Solution Assessment

Unclear until maintainers choose the durable contract. The requested direction is appropriate, but the best fix should extend the existing SQLite/outbound recovery lifecycle instead of adding a sidecar that can drift.

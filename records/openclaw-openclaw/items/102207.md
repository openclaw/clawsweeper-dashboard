## Summary

Keep open: this targets a real source-reproducible XML payload limit gap, but the patch is not merge-ready because it makes the shared `maxPayloadBytes` option byte-based for XML while the JSON parser path still counts UTF-16 code-unit offsets, and the external PR currently has only unit-test/autoreview proof.

## What This Changes

The PR changes the plain-text tool-call repair parser to measure XML-ish parameter blocks and cumulative XML payloads with UTF-8 byte length, and adds a plugin-SDK regression test for multibyte parameter text.

## Best Possible Solution

Land a version that enforces or explicitly scopes byte-based `maxPayloadBytes` semantics consistently across the public parser formats, with direct redacted terminal/live-output proof of the multibyte XML rejection before merge.

## Solution Assessment

No: the XML change is in the right parser layer, but the best fix should not leave the same public `maxPayloadBytes` option using byte accounting for XML and code-unit accounting for JSON.

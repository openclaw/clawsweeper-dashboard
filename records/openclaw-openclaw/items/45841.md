## Summary

Keep open: current main and v2026.6.11 still intentionally block ACP spawning from sandboxed requester sessions, and the remaining work is a security-boundary/product decision rather than conservative cleanup.

## What This Changes

The issue requests a sandbox-aware way for sandboxed OpenClaw sessions to spawn ACP sessions without giving up the sandbox boundary.

## Best Possible Solution

Choose a core sandbox-aware ACP execution design that keeps spawn, steer, and cancel narrowly authorized and auditable, then implement docs and tests for sandboxed requester behavior and sandbox="require" semantics.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw support sandboxed requester sessions spawning ACP by running ACP inside a sandbox, by adding a narrow host-side bridge/proxy, or by folding this into the execution-backend placement contract?

Rationale: Changing the current block defines a sandbox-to-host trust boundary plus likely public config and model-facing tool semantics, so automation cannot safely choose the permanent security design.

Likely owner: steipete

Owner reason: steipete has the strongest combined signal across ACP docs, sandboxed ACP blocking, and architecture review context.

Owner confidence: high

Options:

- **Design Sandbox-Aware ACP Boundary (recommended):** Define a narrow bridge or placement contract for ACP spawn, steer, and cancel with explicit auth, audit, workspace, secret, rate-limit, and cleanup rules before implementation.
- **Require Harnesses Inside Sandbox:** Keep the host-side ACP block and document running Claude Code, Codex, or Gemini inside the OpenClaw sandbox container as the supported workflow for now.
- **Defer To Execution Backends:** Keep this issue as an acceptance case while the broader execution-backend placement design settles remote-worker and sandbox semantics.

## Reproduction Assessment

Yes, at source level: current main returns a forbidden runtime-policy error for sandboxed ACP spawns and for sandbox="require" with runtime="acp". I did not run a live Docker ACP scenario because the source, tests, and docs describe the behavior explicitly.

## Solution Assessment

Unclear as a final implementation: the requested direction is valid, but the safest fix is not a bare allow flag. Maintainers should first choose whether this belongs in an ACP proxy, sandboxed harness execution, or the broader execution-backend placement contract.

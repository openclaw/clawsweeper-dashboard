## Summary

Keep open: current main and the latest release still intentionally block sandboxed requester sessions from ACP spawns, and the related execution-backend work is broader, partial, and unmerged rather than a direct fix for this security-boundary decision.

## What This Changes

Request sandboxed OpenClaw sessions to spawn ACP sessions through an opt-in secure bridge, sidecar, or isolated worker model instead of the current hard block.

## Best Possible Solution

Keep the current fail-closed behavior until maintainers approve a narrow opt-in ACP bridge or isolated execution-backend contract covering authentication, audit, workspace and secret scoping, rate limits, cancellation, and cleanup.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw allow sandboxed sessions to request ACP host or worker spawns, and which security boundary should own that capability?

Rationale: The code can implement several shapes, but the deciding factor is whether OpenClaw should preserve a strict sandbox boundary, add an audited host bridge, or route ACP into isolated workers; automation should not choose that trust model.

Likely owner: osolmaz

Owner reason: The decision is closest to the ACP runtime and sandbox-inheritance security boundary that osolmaz merged and has adjacent runtime context for.

Owner confidence: medium

Options:

- **Prefer Isolated ACP Workers (recommended):** Extend the execution-backend/profile or sidecar-worker design so ACP runs in a sandboxed worker with explicit auth, workspace, secret, rate-limit, cancellation, and cleanup boundaries before enabling sandboxed requesters.
- **Approve Audited Host Bridge:** Add an opt-in host-side ACP proxy with narrow spawn/steer/cancel APIs, allowlisting, rate limits, and durable audit logs for operators who accept controlled privilege escalation.
- **Keep Current Block:** Continue documenting that sandboxed sessions must use `runtime="subagent"` or install the harness inside the container until a stronger security design is sponsored.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 explicitly reject sandboxed ACP spawns in code, tests, and docs. I did not run a live Docker plus ACP harness scenario because the existing source path already proves the documented hard block.

## Solution Assessment

Unclear as a final implementation: a bridge/proxy or worker-backed ACP path could solve the workflow, but a simple config bypass is not the best fix without a maintainer-approved trust model. The safer end state is an explicit opt-in bridge or isolated execution backend with security and lifecycle proof.

## Summary

Keep open: current main and the latest release still intentionally block ACP spawns from sandboxed requester sessions, and the remaining work is a security-sensitive product decision about how ACP should cross or share the sandbox boundary.

## What This Changes

Request to let sandboxed OpenClaw sessions spawn ACP sessions through a safe sandbox, sidecar, bridge, or execution-placement model.

## Best Possible Solution

Choose a core sandbox-aware ACP execution design that keeps spawn/steer/cancel narrowly authorized and auditable, then implement it with docs and tests for sandboxed requester behavior, sandbox="require", slash-command ACP spawns, and upgrade-safe config semantics.

Options:

- **Design A Sandbox-Aware ACP Boundary (recommended):** Define a narrow bridge or placement contract for ACP spawn/steer/cancel with explicit auth, audit, workspace, secret, rate-limit, and cleanup rules before implementation.
- **Require Harnesses Inside The Sandbox:** Keep the current host-side ACP block and document running Claude Code/Codex/Gemini inside the OpenClaw sandbox container as the supported path for this workflow.
- **Defer To Broader Execution Backends:** Keep this issue open as an acceptance case while https://github.com/openclaw/openclaw/issues/82017 settles backend/profile placement and remote-worker security semantics.

## Reproduction Assessment

Yes, at source level: current main returns a forbidden runtime-policy error for sandboxed ACP spawns and for sandbox="require" with runtime="acp". I did not run a live Docker ACP scenario because the documented/source behavior is explicit and the requested work is a feature/security design change.

## Solution Assessment

Unclear as a final implementation: the requested direction is valid, but the safest fix is not a bare allow flag. Maintainers should first choose whether this belongs in an ACP proxy, sandboxed harness execution, or the broader execution-backend placement contract.

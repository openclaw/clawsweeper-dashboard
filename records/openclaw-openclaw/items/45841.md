## Summary

Keep open: current main and v2026.6.11 still intentionally block sandboxed requester sessions from ACP spawns, and the related execution-backend work is broader, partial, open, and not a direct fix for this sandbox-to-ACP security-boundary decision.

## What This Changes

Request a safe way for sandboxed OpenClaw sessions to spawn or control ACP sessions without giving up the sandbox boundary.

## Best Possible Solution

Keep the current fail-closed behavior until maintainers approve a narrow opt-in ACP bridge or isolated ACP worker contract with explicit auth, audit, workspace, secret, rate-limit, cancellation, and cleanup guarantees.

Rationale: The implementation could take several shapes, but automation should not choose whether sandboxed sessions may cross into host-side ACP execution or whether ACP must move into isolated workers.

Likely owner: osolmaz

Owner confidence: medium

Options:

- **Prefer Isolated ACP Workers (recommended):** Extend the execution-backend/profile design so ACP runs in a sandboxed worker or sidecar with explicit auth, workspace, secret, and lifecycle boundaries before enabling sandboxed requesters.
- **Approve Audited Host Bridge:** Add an opt-in host-side ACP proxy with narrow spawn, steer, and cancel APIs, allowlisting, rate limits, and durable audit logs for operators who accept controlled privilege escalation.
- **Keep Current Block:** Continue documenting that sandboxed sessions should use `runtime="subagent"` or run ACP-capable harnesses inside the container until a stronger security design is sponsored.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 explicitly reject sandboxed ACP spawns in code, tests, and docs. I did not run a live Docker plus ACP harness scenario because the shipped source path proves the documented hard block.

## Solution Assessment

Unclear as a final implementation: a bridge/proxy or worker-backed ACP path could solve the workflow, but a simple config bypass is not the best fix without a maintainer-approved trust model. The safer end state is an explicit opt-in bridge or isolated execution backend with security and lifecycle proof.

## Summary

Keep open: current main and v2026.6.11 still intentionally block ACP spawns from sandboxed requester sessions, and the remaining work is a security-sensitive product decision about the sandbox-to-host ACP boundary.

## What This Changes

Request to let sandboxed OpenClaw sessions spawn ACP sessions through an in-sandbox, separately sandboxed, or controlled host-bridge execution path.

## Best Possible Solution

Choose a core sandbox-aware ACP execution design that keeps spawn, steer, and cancel narrowly authorized and auditable, then implement it with docs and regression coverage for sandboxed requesters and sandbox="require" behavior.

## Maintainer Decision

Kind: security_boundary

Question: Should OpenClaw support sandboxed requesters spawning ACP sessions by running ACP inside a sandbox, by adding a host-side bridge/proxy, or by folding the behavior into a broader execution-backend placement contract?

Rationale: The next step defines a sandbox-to-host trust boundary plus public config and model-facing tool semantics, so automation cannot safely choose the permanent security design.

Likely owner: steipete

Owner reason: steipete has the strongest combined history on sessions_spawn, ACP sandbox docs, and the current ACP spawn policy surface.

Owner confidence: high

Options:

- **Design A Sandbox-Aware ACP Boundary (recommended):** Define a narrow bridge or placement contract for ACP spawn, steer, and cancel with explicit auth, audit, workspace, secret, rate-limit, and cleanup rules before implementation.
- **Require Harnesses Inside The Sandbox:** Keep the current host-side ACP block and document running external harnesses inside the OpenClaw sandbox container as the supported secure path.
- **Defer To Execution Backends:** Keep this issue open as an acceptance case while https://github.com/openclaw/openclaw/issues/82017 settles backend/profile placement and remote-worker security semantics.

## Reproduction Assessment

Yes, at source level: current main returns a runtime-policy error for sandboxed ACP spawns and for sandbox="require" with runtime="acp". I did not run a live Docker ACP scenario because the source, docs, and tests explicitly encode the current limitation.

## Solution Assessment

Unclear as a final implementation: the requested direction is valid, but the safest fix is not a bare allow flag. Maintainers should first choose whether this belongs in an ACP proxy, in-sandbox ACP execution, or the broader execution-backend placement contract.

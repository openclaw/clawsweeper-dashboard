## Summary

Keep open: current main and v2026.6.11 still intentionally block ACP spawns from sandboxed requester sessions, and the open execution-backend PR is only adjacent contract work, not a sandbox-to-ACP bridge. The issue has useful bridge, sidecar, and nested-sandbox design context, but this needs maintainer product and security agreement before implementation.

## What This Changes

Allow sandboxed OpenClaw sessions to spawn or control ACP sessions through a safe bridge, nested sandbox, or execution-placement contract.

## Best Possible Solution

Keep the fail-closed guard until maintainers define an explicit opt-in sandbox-to-ACP bridge or execution-placement contract with allowlisting, audit controls, docs, tests, and live Docker/acpx proof.

## Reproduction Assessment

Yes, at source level: sandboxed requesters calling sessions_spawn with runtime="acp" are denied before ACP dispatch, and /acp spawn calls the same fail-closed policy path. I did not run a live Docker/acpx repro in this read-only review.

## Solution Assessment

Unclear as an implementation: bridge, sidecar, nested-sandbox, and broader execution-placement designs are plausible. The best next step is maintainer product and security design before an autonomous patch.

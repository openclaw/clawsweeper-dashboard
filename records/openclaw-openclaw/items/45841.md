## Summary

Keep open: current main and the latest release still intentionally block ACP spawns from sandboxed requesters, and the remaining work is a security/product architecture decision rather than a stale or already-implemented feature.

## What This Changes

Allow sandboxed OpenClaw sessions to spawn and control ACP sessions through a safe bridge, sidecar, nested sandbox, or execution-placement design.

## Best Possible Solution

Keep the fail-closed guard until maintainers define an explicit opt-in sandbox-to-ACP bridge or execution-placement contract with allowlisting, audit controls, docs, tests, and live Docker/acpx proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add an opt-in sandbox-to-ACP bridge now, fold sandboxed ACP into the broader execution-backend/runtime design, or keep ACP blocked from sandboxed sessions?

Rationale: The request crosses from container-isolated agent execution into host-side process execution and would define public security, config, and tool contracts that automation should not choose.

Likely owner: steipete

Owner reason: steipete has the strongest combined history across sessions_spawn, ACP sandbox docs, slash-command policy, and the security/product boundary language.

Owner confidence: high

Options:

- **Design Narrow Bridge (recommended):** Define an explicit opt-in host bridge with requester allowlisting, spawn/steer/cancel verbs, audit logs, rate limits, docs, and live Docker/acpx proof.
- **Fold Into Execution Backends:** Use the broader backend/profile or ACP-runtime work as the design home and keep this issue as the sandboxed ACP acceptance case.
- **Keep Blocked:** Preserve the current fail-closed behavior and document that ACP must run from non-sandboxed sessions or inside a separately sandboxed harness setup.

## Reproduction Assessment

Yes, at source level: sandboxed requesters calling sessions_spawn with runtime="acp" are denied before ACP dispatch, and /acp spawn uses the same fail-closed policy path. I did not run a live Docker/acpx repro in this read-only review.

## Solution Assessment

Unclear as an implementation: bridge, sidecar, nested sandbox, execution-backend placement, and ACP-runtime consolidation are all plausible. The best next step is maintainer product and security design before an autonomous patch.

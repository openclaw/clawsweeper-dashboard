## Summary

Keep open: current main and v2026.6.11 still intentionally block sandboxed requester sessions from ACP spawns, and the remaining work is a sandbox-to-ACP trust model rather than a narrow code repair.

## What This Changes

The issue requests a safe way for sandboxed OpenClaw sessions to spawn or control ACP sessions without giving up sandbox isolation.

## Best Possible Solution

Keep the current fail-closed behavior until maintainers approve either an isolated ACP worker/backend contract or a narrow opt-in host bridge with explicit auth, audit, workspace, secret, quota, cancellation, and cleanup guarantees.

Options:

- **Prefer Isolated ACP Workers (recommended):** Extend the execution-backend/profile design so ACP can run in a sandboxed worker or sidecar with explicit auth, workspace, secret, lifecycle, and audit boundaries before enabling sandboxed requesters.
- **Approve Audited Host Bridge:** Add an opt-in host-side ACP proxy with narrow spawn/steer/cancel APIs, allowlists, rate limits, durable audit logs, and clear operator warnings for controlled privilege crossing.
- **Keep Current Block:** Continue documenting that sandboxed sessions must use `runtime="subagent"` or run ACP-capable harnesses inside the sandbox until a stronger design is sponsored.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 explicitly reject sandboxed ACP spawns in code, tests, and docs. I did not run a live Docker plus ACP harness scenario because the checked source path already proves the documented hard block.

## Solution Assessment

Unclear as a final implementation: a bridge, sidecar, or worker-backed ACP path could solve the workflow, but a simple config bypass is not the best fix without a maintainer-approved trust model. The safer direction is an explicit isolated-worker or audited-bridge design with security and lifecycle proof.

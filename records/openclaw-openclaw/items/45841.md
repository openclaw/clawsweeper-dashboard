## Summary

Keep open: current main and the latest release still intentionally block ACP spawns from sandboxed requester sessions, and the remaining work is a security-sensitive product decision about how ACP should cross or share the sandbox boundary.

## What This Changes

Requested support for spawning ACP-backed coding-harness sessions from sandboxed OpenClaw/Docker sessions without giving up sandbox isolation.

## Best Possible Solution

Choose a core sandbox-aware ACP execution design that keeps spawn, steer, cancel, workspace, secrets, audit, rate limits, and cleanup boundaries explicit before enabling sandboxed requesters.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw support sandboxed requesters spawning ACP sessions by running harnesses in a sandbox, by adding a host-side bridge/proxy, or by folding the behavior into the broader execution-backend placement contract?

Rationale: The next step defines a sandbox/host trust boundary plus public config and model-facing tool semantics, so automation cannot safely choose the permanent security design.

Likely owner: steipete

Owner reason: steipete has the strongest direct history on sessions_spawn and ACP sandbox policy, including the original tool, limitation docs, and slash-command block.

Owner confidence: high

Options:

- **Design sandbox-aware ACP boundary (recommended):** Define a narrow bridge or placement contract for ACP spawn/steer/cancel with explicit auth, audit, workspace, secret, rate-limit, and cleanup rules before implementation.
- **Require harnesses inside sandbox:** Keep the current host-side ACP block and document running the harness inside the sandbox container as the supported path for this workflow.
- **Defer to execution backends:** Keep this issue open as an acceptance case while the broader execution-backend placement design settles remote-worker security semantics.

## Reproduction Assessment

Yes, at source level: current main returns a forbidden runtime-policy error for sandboxed ACP spawns and for sandbox="require" with runtime="acp" before ACP initialization. I did not run a live Docker ACP scenario because the documented/source behavior is explicit and this is a feature/security design request.

## Solution Assessment

No current implementation solves the issue. The safest fix is not a bare allow flag; maintainers should first choose whether this belongs in an ACP proxy, sandboxed harness execution, or the broader execution-backend placement contract.

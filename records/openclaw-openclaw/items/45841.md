## Summary

Keep open: current main and v2026.6.11 still intentionally block sandboxed requester sessions from ACP spawns, and the remaining work is a security-boundary/product decision rather than a conservative cleanup close.

## What This Changes

Allow sandboxed OpenClaw sessions to spawn ACP sessions through a safe bridge, sidecar, nested sandbox, or execution-backend design.

## Best Possible Solution

Keep the current fail-closed behavior until maintainers approve a narrow opt-in ACP bridge or isolated execution-backend contract with explicit auth, audit, workspace, secret, rate-limit, cancellation, and cleanup boundaries.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw allow sandboxed requester sessions to start ACP host or worker sessions, and which trust boundary should own that capability?

Rationale: The code can implement several shapes, but choosing between a host bridge, isolated ACP workers, nested sandboxing, or keeping the block is a security/product decision that automation should not make.

Likely owner: osolmaz

Owner reason: This choice is closest to the ACP runtime and sandbox-inheritance security boundary that osolmaz merged and co-authored in the current implementation history.

Owner confidence: high

Options:

- **Prefer Isolated ACP Workers (recommended):** Extend the execution-backend/profile design so ACP runs in a sandboxed worker or sidecar with explicit auth, workspace, secret, lifecycle, and cleanup rules before enabling sandboxed requesters.
- **Approve Audited Host Bridge:** Add an opt-in host-side ACP proxy with narrow spawn/steer/cancel APIs, allowlisting, rate limits, and durable audit logs for operators who accept controlled privilege escalation.
- **Keep Current Block:** Continue documenting that sandboxed sessions must use runtime="subagent" or run ACP-capable harnesses inside the container until a stronger design is sponsored.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 explicitly reject sandboxed ACP spawns in code, tests, and docs. I did not run a live Docker plus ACP harness scenario because the documented hard block is already proven by the current source path.

## Solution Assessment

Unclear as a final implementation: a bridge/proxy or worker-backed ACP path could solve the workflow, but a simple config bypass is not the best fix without a maintainer-approved trust model. The safer end state is an explicit opt-in bridge or isolated execution backend with security and lifecycle proof.

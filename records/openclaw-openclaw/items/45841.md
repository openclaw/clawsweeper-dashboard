## Summary

Keep open: current main and v2026.6.11 still intentionally block ACP spawns from sandboxed requester sessions, and the remaining work is a security-boundary/product decision rather than a conservative cleanup close.

## What This Changes

Request to let sandboxed OpenClaw sessions spawn or control ACP harness sessions through an opt-in bridge, sidecar, or isolated backend instead of the current fail-closed block.

## Best Possible Solution

Keep the current fail-closed behavior until maintainers approve a narrow opt-in ACP bridge or isolated execution-backend contract with explicit auth, audit, workspace, secret, rate-limit, cancellation, and cleanup semantics.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw allow sandboxed sessions to request ACP host or worker spawns, and which security boundary should own that capability?

Rationale: The code can implement a host bridge, sidecar, or isolated worker path, but automation should not choose whether sandboxed sessions may cross into host-side ACP execution or what trust model makes that acceptable.

Likely owner: osolmaz

Owner reason: osolmaz has the strongest current history on the ACP sandbox inheritance merge and adjacent ACP/acpx runtime boundary.

Owner confidence: high

Options:

- **Prefer Isolated ACP Workers (recommended):** Extend the execution-backend/profile design so ACP runs in sandboxed workers or sidecars with explicit auth, workspace, secret, lifecycle, and audit boundaries before enabling sandboxed requesters.
- **Approve Audited Host Bridge:** Add an opt-in host-side ACP proxy with narrow spawn/steer/cancel APIs, allowlists, rate limits, durable audit logs, and operator warnings for controlled privilege escalation.
- **Keep The Current Block:** Continue documenting that sandboxed sessions must use runtime="subagent" or run ACP-capable harnesses inside the container until a stronger design is sponsored.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 explicitly reject sandboxed ACP spawns in source, tests, and docs. I did not run a live Docker plus ACP harness scenario because the existing code path proves the documented hard block.

## Solution Assessment

Unclear as a final implementation: a bridge/proxy or worker-backed ACP path could solve the workflow, but a simple config bypass is not the best fix without a maintainer-approved trust model. The safer end state is an explicit opt-in bridge or isolated execution backend with security and lifecycle proof.

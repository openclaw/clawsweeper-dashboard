## Label Justifications

- `P2`: This is a normal-priority fix for a concrete local-memory reliability bug with limited blast radius to local embedding workers after a Homebrew Node upgrade.
- `merge-risk: 🚨 availability`: The changed worker spawn path can still fail to start new local embedding workers in the reported stale-Cellar environment if PATH lookup is unavailable or wrong.

## Summary

Keep this PR open, but the patch is not ready: it relies on `process.argv[0]` as the original launch symlink even though Node rewrites that value to `process.execPath`, so the intended Homebrew symlink fallback is skipped in the stale-Cellar case.

## What This Changes

The PR adds a local embedding worker `execPath` resolver that checks `process.execPath`, `process.argv[0]`, and PATH before passing the result to `child_process.fork`.

## Best Possible Solution

Use `process.argv0` or a package-local stable Homebrew Node resolver before PATH fallback, add a focused stale-Cellar regression test, and include redacted real macOS/Gateway proof for the fresh worker fork path.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, at source level. Current main omits `execPath` on the worker `fork()`, Node defaults that to `process.execPath`, and the PR's `process.argv[0]` fallback is contradicted by Node's own runtime values.

## Solution Assessment

No. Passing an explicit worker `execPath` is the right layer, but this implementation should use `process.argv0` or the existing stable-node resolver before PATH fallback and should include stale-Cellar coverage.

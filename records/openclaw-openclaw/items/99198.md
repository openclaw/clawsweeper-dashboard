## Label Justifications

- `P1`: The report describes repeated user-visible heartbeat turns executing follow-up work from inferred consent, which is an urgent agent workflow safety bug even without a crash.
- `impact:security`: The central concern is side-effecting work proceeding without fresh user authorization from a real persisted user message.
- `impact:session-state`: The failure depends on stale main-session transcript context being treated as current turn state.
- `impact:message-loss`: The user-visible channel output can make it appear that phantom inbound replies were received and acted on.

## Summary

Keep open: current main and v2026.6.11 still run ordinary non-isolated heartbeat polls in the resolved main session with prompt/filter guardrails, but no source-level boundary that makes stale conversation context non-authorizing for side-effecting follow-up work.

## What This Changes

Request that main-session heartbeat polls stop inferring fresh user replies or consent from stale context and avoid follow-up side effects unless an auditable source authorizes them.

## Best Possible Solution

Add a maintainer-approved heartbeat authorization boundary so main-session heartbeat can observe state but cannot turn stale assistant questions into fresh user consent, with focused regression coverage for ordinary polls, explicit heartbeat tasks, cron/events, and tool gating.

## Reproduction Assessment

Yes at source level, but not as a live current-main repro. Current main still routes unset or main heartbeat sessions through the main session with isHeartbeat set, and the issue supplies a sanitized audit showing persisted user rows contained only the heartbeat poll marker.

## Solution Assessment

Unclear as an exact implementation. A blanket default-isolation change would be too broad; the better fix is a narrow non-authorizing heartbeat context/tool policy that preserves intentional main-session monitoring.

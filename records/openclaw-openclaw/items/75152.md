## Summary

Keep open: current main forwards edit-tool argument preparation, but its normalizer still does not handle the reported XML-RPC-style `{ item: { oldText, newText } }` entries, and every linked fix PR closed without merging. The remaining uncertainty is whether that envelope is a current provider contract and whether normalization belongs at the transport boundary rather than specifically in the edit tool.

## What This Changes

Fix the edit tool rejecting otherwise valid edit arrays when a provider transport wraps each edit entry in an extra `item` object.

## Best Possible Solution

Capture a redacted current-version provider tool call, confirm the upstream transport contract, then normalize the envelope once at the provider/tool-call decoding boundary when generic; use `prepareEditArguments` only if the shape is explicitly edit-specific, with canonical, string, wrapped, mixed, and negative regression coverage.

## Summary

Keep open: the reporter supplied a fresh recurrence on OpenClaw v2026.7.1, and current main still requires a resolved planned delivery target before a message-tool send can satisfy cron/hook delivery verification. The remaining choice is intentional delivery policy, not stale reporter evidence.

## What This Changes

Correct hook-run delivery accounting when an agent successfully sends an explicit Telegram message but the hook mapping has no resolved runner-owned recipient to compare against.

## System Context

Workspace Gmail hooks create an isolated agent/cron-style run with optional announce delivery. The run can use the message tool for a direct channel send, while the cron delivery layer separately verifies and records whether the planned delivery route completed.

## Architecture Diagram

flowchart LR
  A[Gmail inbound event] --> B[Hook mapping]
  B --> C[Isolated agent run]
  C --> D[Message tool Telegram send]
  B --> E[Planned announce target]
  D --> F[Delivery verification]
  E --> F
  F --> G[Hook run status and diagnostics]

## Best Possible Solution

Keep the no-implicit-recipient safety rule, then define one explicit hook policy: either direct agent sends own delivery when runner delivery is disabled, or targetless announce hooks fail with a diagnostic that tells operators to configure a recipient or disable runner delivery.

- **Accept explicit direct sends:** Treat a successful direct message-tool send as delivery for targetless hook runs, with a narrowly scoped test that preserves the keyless `last` refusal.

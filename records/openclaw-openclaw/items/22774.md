## Summary

Keep open: current main and the latest release have partial provenance and sender-label display paths, but they still do not provide the requested durable human/main-agent/sub-agent sender identity contract across protocol schemas, transcripts, live/history events, subagent announcements, and Control UI avatars.

## What This Changes

Request durable multi-role Chat UI attribution so human, main-agent, and sub-agent messages remain distinguishable in multi-agent workflows.

## Best Possible Solution

Define one additive sender identity contract for chat/session messages, persist and expose it through history and live events, carry it through inter-session and subagent delivery, then render Control UI labels/avatars/colors from that single contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a durable per-message sender identity contract for multi-agent chat, and what canonical fields and trust rules should flow through Gateway schemas, transcripts, live/history events, and Control UI rendering?

Rationale: The missing behavior is real, but the permanent fix defines a cross-surface protocol and persistence contract rather than a narrow renderer bug; automation should not choose field names, trust semantics, or compatibility behavior alone.

Likely owner: steipete

Owner reason: The strongest history signal is around inter-session provenance, protocol-adjacent session work, and prior review of this exact product/API boundary.

Owner confidence: medium

Options:

- **Add Durable Sender Identity (recommended):** Adopt an additive sender object with id, kind, display name, source session or agent, and render metadata, then migrate the affected protocol, transcript, event, and UI paths together.
- **Keep SenderLabel Projection Only:** Treat current senderLabel/provenance display as the intended scope and leave only narrower requester-name or blank-label bugs to separate issues.
- **Fold Into Broader Multi-Agent UI:** Defer this focused contract until a broader multi-agent chat/group-chat product design owns participants, permissions, and sender rendering together.

## Reproduction Assessment

Yes, at source level: current schemas, provenance, subagent announce delivery, and Control UI rendering expose role plus senderLabel/provenance hints rather than a durable per-message human/main-agent/sub-agent identity object. I did not run a live five-agent WebChat scenario in this read-only review.

## Solution Assessment

Unclear until maintainer product/API direction is set: a durable sender identity contract is the right end state, while the current senderLabel projection is only a partial mitigation for specific sessions_send display cases.

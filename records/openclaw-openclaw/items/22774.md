## Label Justifications

- `P2`: Missing durable sender attribution materially impairs multi-agent auditability and debugging, but it does not make the core runtime unusable.
- `impact:session-state`: The requested sender identity must stay associated with messages across session handoffs, transcripts, history, live events, and Control UI state.
- `maturity:stable`: The issue affects stable Gateway RPC/API event surfaces in `gateway-runtime` M4 even though the WebChat UI surface remains beta.

## Summary

Keep open. Current main and the latest v2026.6.11 release have inter-session provenance, browser-local identity, and a derived `senderLabel` path for some `sessions_send` display cases, but they still do not provide the requested durable human/main-agent/sub-agent sender identity contract across protocol input, transcripts, subagent announcements, history/live payloads, and per-message Control UI avatars.

## What This Changes

Add durable multi-role sender identity in Chat UI so human, main-agent, and sub-agent messages retain distinct attribution, avatars, and audit metadata in multi-agent workflows.

## Best Possible Solution

Define one additive trusted per-message sender metadata contract, persist it where appropriate, propagate it through chat/session/subagent delivery and history/live events, and render stable names, avatars, and colors without changing provider-facing roles.

## Reproduction Assessment

Yes, at source level. Current schemas, provenance types, subagent delivery, history projection, and Control UI rendering provide trace fields or derived labels rather than a durable human/main-agent/sub-agent sender identity contract.

## Solution Assessment

Yes in direction, but not as a UI-only avatar patch or new provider message roles. The maintainable solution is additive trusted sender metadata that preserves canonical transcript roles while giving history and UI consumers durable renderable identity.

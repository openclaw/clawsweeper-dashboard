## Summary

Keep open: current main and v2026.6.11 still have provenance and senderLabel display hints, but not the requested durable human/main-agent/sub-agent sender identity contract across protocol input, transcripts, live/history payloads, and Control UI rendering.

## What This Changes

Request durable multi-role sender attribution in Chat UI so human, main-agent, and sub-agent messages are distinguishable in multi-agent workflows.

## Best Possible Solution

Define an additive per-message sender identity contract and carry it through protocol input, persisted transcripts, history/live events, and Control UI rendering without relying on UI-only senderLabel inference.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a durable per-message sender identity contract for multi-agent conversations, and which metadata should be canonical across protocol, transcripts, events, and Control UI rendering?

Rationale: This is not a narrow bug fix: it changes public gateway payloads, stored message semantics, and UI rendering while current code already has several partial attribution mechanisms that need one source of truth.

Likely owner: steipete

Owner reason: The decision spans protocol, session provenance, transcript, and product direction, and steipete has the strongest recent history on the central provenance/API surfaces.

Owner confidence: high

Options:

- **Design additive sender metadata (recommended):** Add a durable sender identity object with sender id, kind, display name, source session/agent, and renderable avatar/color metadata, then migrate UI and session surfaces to consume it.
- **Keep narrow partial fixes:** Continue landing scoped senderLabel and sessions_send prompt fixes while leaving the broader durable identity contract unimplemented for now.
- **Defer multi-agent identity:** Leave this as roadmap work until a larger multi-agent/session model design is prioritized.

## Reproduction Assessment

Yes, at source level: current main has no durable sender identity fields in chat.send or sessions.send, InputProvenance only carries source trace metadata, and Control UI rendering consumes role plus senderLabel. I did not run the reported live five-agent workflow in this read-only review.

## Solution Assessment

Unclear until maintainers define the product/API contract. The maintainable direction is an additive per-message sender metadata contract; more role-only avatar or senderLabel inference would remain a partial workaround.

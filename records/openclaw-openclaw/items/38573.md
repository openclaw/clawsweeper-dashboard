## Summary

Keep open. Current main and the latest release still force text-only thread/topic isolated cron completions through direct outbound delivery and do not expose a public opt-in route for main-agent processing, so this remains a product/API decision rather than cleanup-closeable work.

## What This Changes

The issue requests an opt-in config or per-cron option that lets topic/forum cron completions use the main-session announce/agent-turn flow instead of the current forced direct delivery path.

## Best Possible Solution

Define a narrow, backward-compatible job-level text-completion route enum for thread/topic cron delivery, keep current direct delivery as the default, keep structured payloads direct-only, and specify delivery status plus fallback semantics before coding it.

## Maintainer Decision

Kind: product_direction

Question: Should text-only isolated cron completions for thread/topic targets support an opt-in main-agent processing route, and which public API plus fallback behavior should own it?

Rationale: The source-level gap is clear, but adding this route changes cron's public config/protocol and delivery failure behavior, and repository policy treats config/default/fallback surfaces as compatibility-sensitive product decisions.

Likely owner: steipete

Owner reason: steipete introduced the direct-deliver thread/topic cron behavior and extracted the current dispatch boundary, making him the strongest history-backed owner for the route decision.

Owner confidence: high

Options:

- **Add Job-Level Route Enum (recommended):** Add a narrow per-job text-completion route selector that defaults to direct delivery, applies only to text-only thread/topic completions, and has explicit fail-closed or direct-fallback semantics.
- **Add Global Default Plus Override:** Add a global cron default with per-job override for operators who want consistent topic behavior across many jobs, accepting a wider config surface.
- **Keep Direct Delivery Only:** Preserve current thread/topic direct-send behavior and document target-awareness or message-tool patterns as the supported alternatives.

## Reproduction Assessment

Yes. Source inspection on current main shows thread/topic cron targets still force direct outbound delivery, while the type, protocol, config, and docs expose no opt-in main-agent route selector; no live Telegram cron flow was run in this read-only review.

## Solution Assessment

Unclear until maintainers choose the surface. A job-level opt-in route looks like the narrowest plausible shape, but the API, fallback, timeout, duplicate-delivery, and delivery-status semantics need product direction first.

## What This Changes

Ensure ACP binding sessions recover across gateway restarts without orphaning transcript identity or presenting a misleading model error.

## Best Possible Solution

Preserve the persisted backend session identity during restart recovery; if the backend explicitly reports that the transcript is missing, atomically invalidate the stale mapping, create and persist a fresh session, report the session-recovery cause accurately, and offer an in-product ACP Fix/Doctor action instead of requiring process kills or manual file deletion.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When a persistent ACP binding cannot resume its stored backend transcript after restart, should OpenClaw preserve-first then automatically recreate, always fail for explicit recovery, or always start fresh?

Rationale: The choice determines whether OpenClaw favors transcript continuity, automatic availability, or explicit operator control, and it must remain consistent across restart, `/reset`, and `/acp close`.

Likely owner: osolmaz

Owner reason: They merged the persistent binding and adjacent Telegram ACP lifecycle implementations, providing the strongest available ownership signal.

Owner confidence: high

Options:

- **Preserve, then recover (recommended):** Reuse the persisted identity first, but atomically recreate and clearly notify the user when the backend confirms that the transcript is missing.
- **Fail explicitly:** Preserve transcript continuity strictly and require an in-product Fix/Doctor action before creating a replacement session.
- **Always start fresh:** Discard persisted backend identity after every gateway restart, accepting conversation-history loss for simpler recovery.

## Reproduction Assessment

No, not yet with high confidence: current source supports the stale persisted-session failure class, and a related report describes the restart path, but no live current-main run establishes the exact new-ID and missing-transcript sequence.

## Solution Assessment

No, the three alternatives in the report should not be implemented independently; the narrow maintainable solution is one canonical preserve-first recovery transaction with an explicit missing-transcript fallback, accurate error mapping, and consistent reset/close semantics.

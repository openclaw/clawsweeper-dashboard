## Summary

Keep this issue open: current main and the latest release still do not provide a captureFilter or default EXTERNAL_UNTRUSTED_CONTENT rejection in memory-lancedb autoCapture, and the remaining choice is a security/product boundary decision.

## What This Changes

The issue requests source-based filtering for memory-lancedb autoCapture so wrapped untrusted external content is not stored as long-term memory.

## Best Possible Solution

Define the host-owned autoCapture trust boundary first; prefer default rejection of OpenClaw external-content wrappers before trigger matching unless maintainers explicitly approve a captureFilter config surface.

## Maintainer Decision

Required: true

Question: Should memory-lancedb autoCapture reject OpenClaw-authored external-content wrappers by default, or should this be exposed as a new captureFilter configuration option?

Rationale: The source-level gap is real, but the permanent security boundary determines whether trust is enforced by the framework by default or delegated to operator configuration.

Likely owner: vincentkoc

Owner reason: This crosses the external-content security boundary and memory persistence behavior, and vincentkoc is tied to the wrapper hardening path.

Owner confidence: medium

Options:

- **Reject wrappers by default (recommended):** Treat EXTERNAL_UNTRUSTED_CONTENT as a host-owned capture boundary before trigger matching and add regression coverage for wrapped web, browser, and tool content.
- **Add captureFilter config:** Introduce a documented operator-controlled excludeWrapped option with schema, manifest, docs, and upgrade-safe default tests.
- **Defer to provenance architecture:** Leave this narrow filter open until the broader memory trust/provenance model defines the canonical source-authority contract.

## Reproduction Assessment

Yes, at source level. Current main can take user-role text through memory-lancedb autoCapture, sanitize it, match trigger words such as always, and store it without a wrapper/provenance gate when the wrapped text remains under the configured capture limit.

## Solution Assessment

Unclear as proposed. Source-based filtering is the right mitigation area, but maintainers should decide whether the best fix is default host-owned wrapper rejection or a new captureFilter config surface.

## Summary

Keep this issue open: current main and v2026.6.11 still lack the requested `captureFilter` or a default host-owned skip for `EXTERNAL_UNTRUSTED_CONTENT`-wrapped content, while the autoCapture path still reaches trigger-based storage after sanitization. The remaining decision is security/product policy, especially whether this should be a default trust boundary or an operator-configured memory plugin option.

## What This Changes

The issue requests a memory-lancedb `autoCapture` source filter that skips `EXTERNAL_UNTRUSTED_CONTENT`-wrapped content before trigger-based memory storage.

## Best Possible Solution

Define the host-owned autoCapture trust boundary first: reject host-wrapped external content before trigger matching by default, or add `captureFilter` only if maintainers intentionally accept an operator-configured policy with docs and regression tests.

## Reproduction Assessment

Yes, at source level: current main has host-authored external-content wrappers and memory-lancedb autoCapture still runs trigger matching/storage without a captureFilter or explicit wrapper boundary. I did not run a live exploit, so this is source-reproducible rather than live-reproduced.

## Solution Assessment

Unclear as proposed: source-based exclusion is the right mitigation area, but a user-configured `captureFilter` may be weaker than a host-owned default rejection of external-content wrappers. Maintainers should choose the trust policy and config shape before implementation.

## Summary

Keep this issue open: current main and latest release still route memory-lancedb autoCapture through sanitization plus trigger matching with no captureFilter and no default rejection for EXTERNAL_UNTRUSTED_CONTENT wrappers. The source-level gap is clear, but the remaining work needs maintainer security/product direction on default host-owned rejection versus a new config surface.

## What This Changes

Request source-based filtering for memory-lancedb autoCapture so host-wrapped external content is not stored as long-term memory.

## Best Possible Solution

Define the host-owned autoCapture trust boundary first, then either reject external-content wrappers by default before trigger matching or approve a narrow documented captureFilter config with regression coverage.

## Reproduction Assessment

Yes, at source level: current main has host-authored EXTERNAL_UNTRUSTED_CONTENT wrappers, while memory-lancedb autoCapture still sanitizes, runs shouldCapture, and stores trigger-matching user text without rejecting that wrapper boundary. I did not run a live exploit.

## Solution Assessment

Unclear as proposed: source-based exclusion is the right mitigation area, but a user-configured captureFilter may be weaker than default host-owned rejection of external-content wrappers. Maintainers should decide the security policy and config shape before implementation.

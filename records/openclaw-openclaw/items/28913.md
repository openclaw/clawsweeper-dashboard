## Label Justifications

- `P2`: This is meaningful persistent-memory security hardening with bounded scope, but it needs product/security design rather than emergency runtime repair.
- `impact:session-state`: Automatically captured untrusted text can become durable memory that affects later sessions after the original external context is gone.
- `impact:security`: The issue targets prompt-injection and memory-poisoning content crossing a trust boundary into long-term memory.

## Summary

Keep open: current main and v2026.6.11 still lack a source/provenance gate before `memory-lancedb` auto-capture stores trigger-matching text. The broader trust/provenance issues are useful context, but they do not replace this narrower capture-time memory-poisoning gap.

## What This Changes

Request adds source-based filtering for `memory-lancedb` auto-capture so `EXTERNAL_UNTRUSTED_CONTENT`-wrapped text is not stored as memory.

## Best Possible Solution

Define a host-authored auto-capture trust/provenance gate that excludes untrusted external content by secure default, with any override explicit and aligned with broader memory trust design.

## Reproduction Assessment

Yes, at source level: current main extracts user text, sanitizes it, runs `shouldCapture`, and stores trigger-matching content without a source/provenance gate. I did not run a live poisoning scenario because this read-only review could establish the gap from source.

## Solution Assessment

No, not exactly as proposed. Excluding untrusted auto-capture is the right goal, but a wrapper-name config is weaker than a typed host-authored provenance/trust signal with a secure default chosen by maintainers.

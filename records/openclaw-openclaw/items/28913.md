- `impact:security`: The issue targets prompt-injection and memory-poisoning content crossing an external-content trust boundary into long-term memory.
- `impact:session-state`: Automatically captured untrusted text can become durable memory that affects later sessions after the original external context is gone.

## Summary

Keep open: current main and v2026.6.11 still lack a source/provenance gate before memory-lancedb autoCapture stores trigger-matching text, and the related memory-trust issues overlap but do not replace this narrower capture-time hardening request.

## What This Changes

The issue requests source-based filtering for memory autoCapture so wrapped untrusted external content is not stored as long-term memory.

## Best Possible Solution

Define a host-authored source/provenance trust signal for autoCapture and make untrusted external content ineligible for durable memory by secure default, with any override explicitly operator-controlled.

## Reproduction Assessment

Yes, at source level: current main extracts user text, sanitizes it, runs shouldCapture, and stores trigger-matching content without a source/provenance gate. I did not run a live poisoning scenario because this read-only review already shows the missing security boundary in source.

## Solution Assessment

No, not exactly as proposed. Excluding untrusted auto-capture is the right goal, but a wrapper-name config is weaker than a typed host-authored provenance/trust signal with a secure default chosen by maintainers.

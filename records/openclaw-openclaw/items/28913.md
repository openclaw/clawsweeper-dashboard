## Summary

Keep open: current main still has memory-lancedb auto-capture sanitization and external-content wrapping, but it does not provide the requested `captureFilter` option or a default capture-time skip for `EXTERNAL_UNTRUSTED_CONTENT`-wrapped content. The remaining work is security-sensitive product/config policy rather than conservative cleanup, and the related open issues cover broader provenance/trust architectures without superseding this narrower autoCapture gap.

## What This Changes

Request source-aware filtering for memory-lancedb autoCapture so host-wrapped untrusted external content is not persisted as long-term memory.

## Best Possible Solution

Decide the host-owned autoCapture trust boundary first, then implement capture-time rejection of host-wrapped external content before trigger matching, adding config/docs/tests only if maintainers intentionally choose an operator-controlled filter.

## Reproduction Assessment

Yes, at source level: current main has host-authored `EXTERNAL_UNTRUSTED_CONTENT` wrappers, and memory-lancedb autoCapture still sanitizes text and runs `shouldCapture` without rejecting that wrapper boundary before trigger matching. I did not run a live exploit because the source path is clear and this is a security-sensitive policy gap.

## Solution Assessment

Unclear as proposed: source-based autoCapture exclusion is the right mitigation area, but a user-configured `captureFilter` may be weaker and noisier than a host-owned default rejection of external-content wrappers. Maintainers should choose the security policy and config shape before implementation.

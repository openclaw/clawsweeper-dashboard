## Label Justifications

- `P2`: The issue describes meaningful persistent-memory security hardening with bounded scope, but it needs product/security design rather than emergency runtime repair.
- `impact:session-state`: Automatically captured untrusted text can become durable memory that affects later sessions after the original external context is gone.

## Summary

Keep open: current main and v2026.6.11 still lack a source/provenance gate before `memory-lancedb` auto-capture stores trigger-matching text. The related provenance and trust-tagging issues are useful context, but they do not replace this narrower capture-time memory poisoning gap.

## What This Changes

The issue requests a source-aware memory auto-capture filter that excludes externally wrapped untrusted content from automatic durable memory storage.

## Best Possible Solution

Make untrusted external content ineligible for memory auto-capture by secure default using a host-authored provenance or trust fact, then document any explicit override alongside the broader memory trust design.

## Reproduction Assessment

Yes, at source level: current main extracts user text, sanitizes it, runs `shouldCapture`, and stores trigger-matching content without a source/provenance gate. I did not run a live poisoning scenario because this is a read-only review and the remaining blocker is security/product policy.

## Solution Assessment

No, not exactly as proposed. Excluding untrusted auto-capture is the right goal, but a wrapper-name config is weaker than a typed host-authored provenance/trust signal with a secure default chosen by maintainers.

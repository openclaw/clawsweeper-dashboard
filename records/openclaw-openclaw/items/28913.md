## Label Justifications

- `P2`: This is meaningful persistent-memory security hardening with source-level evidence, but it needs product/security design rather than emergency runtime repair.
- `impact:security`: The issue targets prompt-injection and memory-poisoning content crossing an untrusted external-content boundary into durable memory.
- `impact:session-state`: Automatically captured untrusted text can become long-term memory that affects later sessions after the original context is gone.

## Summary

Keep open: current main and v2026.6.11 still allow `memory-lancedb` auto-capture to decide from sanitized text triggers without a host-authored source/provenance gate, and the narrower capture-time memory-poisoning gap is not replaced by the broader trust/provenance issues.

## What This Changes

The issue requests a `memory-lancedb` auto-capture filter that excludes externally wrapped untrusted content from long-term memory storage.

## Best Possible Solution

Define a host-authored provenance or trust fact for memory auto-capture, make untrusted external content ineligible by secure default, and align any override with the broader memory trust design.

## Reproduction Assessment

Yes, at source level: current main extracts user-role text, sanitizes it, runs `shouldCapture`, and stores trigger-matching content without a source/provenance gate. I did not run a live poisoning scenario because the checkout is read-only and the remaining blocker is product/security policy.

## Solution Assessment

No, not exactly as proposed. Excluding untrusted auto-capture is the right goal, but a wrapper-name config is weaker than a typed host-authored provenance/trust signal with a secure default chosen by maintainers.

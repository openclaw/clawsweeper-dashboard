## Label Justifications

- `P2`: This is meaningful persistent-memory security hardening with source-level evidence, but it needs product/security design rather than emergency runtime repair.
- `impact:session-state`: Automatically captured untrusted text can become durable memory that affects later sessions after the original external context is gone.
- `impact:security`: The issue targets prompt-injection and memory-poisoning content crossing a trust boundary into long-term memory.

## Summary

Keep open: current main and v2026.6.11 still lack a source/provenance gate before `memory-lancedb` auto-capture stores trigger-matching text. The broader provenance/security issues are useful context, but none replaces this focused capture-time memory-poisoning gap.

## What This Changes

Add a memory-lancedb autoCapture source filter so externally wrapped untrusted content is not automatically stored as durable memory.

## Best Possible Solution

Define a host-authored provenance/trust fact for memory auto-capture, make untrusted external content ineligible by secure default, and allow any override only through an explicit reviewed policy surface.

## Reproduction Assessment

Yes, at source level: current main extracts user text, sanitizes it, runs `shouldCapture`, and stores trigger-matching content without a source/provenance gate. I did not run a live poisoning scenario because this review is read-only and the remaining blocker is policy design.

## Solution Assessment

No, not exactly as proposed. Excluding untrusted auto-capture is the right goal, but a wrapper-name config is weaker than a typed host-authored provenance/trust signal with a secure default chosen by maintainers.

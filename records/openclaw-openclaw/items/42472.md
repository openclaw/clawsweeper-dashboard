## Summary

Keep open: current main and v2026.6.11 still preserve generic mixed trailing `NO_REPLY` text on the shared normal reply path, while merged work only covers narrower quoted, punctuation, reasoning-prefixed, cron, or streaming-prefix cases. The remaining behavior is a security-sensitive message-delivery policy decision, and an open conflicting fork PR still targets the issue.

## What This Changes

The issue requests suppressing an entire auto-reply payload when model output contains or ends with `NO_REPLY` so partial internal text does not leak to channels.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed `NO_REPLY` payloads, preserve legitimate substantive replies, and apply that contract consistently across reply normalization, outbound delivery, cron, and streaming or turn-level paths with focused regression proof.

Options:

- **Adopt classifier-based suppression (recommended):** Define and reuse a shared classifier that suppresses internal or silent-intent mixed payloads while preserving legitimate substantive replies.
- **Use blanket own-line suppression:** Suppress any reply ending with a trailing or own-line `NO_REPLY` token and accept that some currently visible substantive replies may be dropped.
- **Keep the narrow policy:** Document that only token-only, punctuation-only, reasoning-prefixed, and scoped cron cases are suppressed, then retarget broad suppression requests.

## Reproduction Assessment

Yes, source-reproducible: current `normalizeReplyPayload` strips a trailing `NO_REPLY` token from generic mixed content and returns the remaining text, and tests assert that behavior. I did not run a live channel repro because this is a read-only review.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer solution is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

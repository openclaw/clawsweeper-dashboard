## Label Justifications

- `P2`: The issue describes a real shared delivery/security hardening gap with limited scope and no evidence of a core-runtime outage.
- `impact:security`: Mixed `NO_REPLY` output can expose internal model summaries or reasoning that were intended to be suppressed.
- `impact:message-loss`: The requested policy directly changes whether generated channel replies are delivered or suppressed.

## Summary

Keep open: current main and the latest release still preserve some generic mixed trailing `NO_REPLY` payloads, while only narrower token-only, punctuation-wrapped, reasoning-prefixed, and cron-specific cases are covered. Broad suppression remains a shared message-delivery and security-boundary decision, and the linked implementation candidates are unmerged or not ready.

## What This Changes

The issue asks OpenClaw to suppress the entire reply whenever a model emits text followed by `NO_REPLY`, instead of stripping the token and delivering the preceding text.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed `NO_REPLY` payloads, preserve legitimate substantive replies, and apply that contract consistently across reply normalization, outbound delivery, cron, and streaming paths with focused regression proof.

Question: Should OpenClaw broaden `NO_REPLY` suppression for mixed trailing or own-line payloads, and what boundary should separate silent-intent/internal text from legitimate substantive replies that mention or append the token?

Rationale: Current main intentionally preserves some substantive trailing-token replies, while the issue asks for broader suppression to prevent internal text leaks; that is a shared message-delivery and security-boundary choice rather than a mechanical cleanup close.

Likely owner: steipete

Owner confidence: medium

Options:

- **Adopt classifier-based suppression (recommended):** Define and test a shared classifier that suppresses internal or silent-intent mixed payloads while preserving legitimate substantive replies across delivery paths.
- **Use blanket trailing or own-line suppression:** Suppress any reply ending with a trailing or own-line `NO_REPLY` token, accepting that some currently visible substantive replies may be dropped.
- **Keep the current narrow policy:** Document that only token-only, punctuation-wrapped, JSON, and reasoning-prefixed silent payloads are suppressed, then retarget broad suppression requests.

## Reproduction Assessment

Yes. The issue is source-reproducible: `normalizeReplyPayload` strips a trailing `NO_REPLY` token from generic mixed content and returns the remaining text, and current tests assert that behavior.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The maintainable solution is a maintainer-approved silent-intent classifier that prevents internal leaks without silently dropping legitimate substantive replies.

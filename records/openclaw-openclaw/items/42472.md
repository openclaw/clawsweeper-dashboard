- `impact:security`: The reported behavior can expose internal model summaries or reasoning-like text to end-user channels when the model intended silence.

## Summary

Keep open: current main and the latest release still preserve generic substantive-looking text before a trailing `NO_REPLY` on the shared final-reply path, while narrower reasoning-prefixed, punctuation-wrapped token-only, and cron synthesized cases are already partially handled. The remaining change is a shared message-delivery/security policy decision, not a cleanup close.

## What This Changes

The issue asks OpenClaw to suppress the entire outbound reply when model output includes a trailing or contained `NO_REPLY` sentinel instead of delivering text before the token.

## Best Possible Solution

Maintainers should choose and document the shared silent-reply contract, then update the shared classifier/normalizer and focused tests while preserving the existing cron, reasoning-prefixed, and punctuation token-only fixes.

Question: Should the shared reply pipeline suppress the whole message for generic prefix text followed by `NO_REPLY`, or keep delivering substantive-looking prefixes except for narrower reasoning/cron/token-only cases?

Rationale: Current source and tests deliberately preserve some substantive trailing-token replies, while this issue asks to turn that same shape into full suppression for security and noise reduction; automation cannot safely choose that policy boundary.

Owner confidence: medium

Options:

- **Define A Narrow Shared Silence Rule (recommended):** Suppress whole messages only for an explicit final-line or silent-intent boundary that maintainers document, and add tests for both suppression and preserved substantive replies.
- **Adopt Broad Contains Suppression:** Treat any `NO_REPLY` occurrence as a whole-message suppressor, accepting the message-loss risk for text that previously delivered after token stripping.
- **Preserve Current Split Behavior:** Keep the current reasoning-prefixed, punctuation token-only, and cron-specific fixes, then close or re-scope this issue as not planned for generic mixed content.

Yes. Source inspection and existing tests show the current shared normalizer strips `NO_REPLY` from a substantive-looking trailing-token reply and returns the remaining prefix; I did not run tests in this read-only review.

## Solution Assessment

Unclear. The requested suppress-if-present rule would solve the leak class but is broader than the current tested contract; the maintainable path is an explicit maintainer-approved silence-intent boundary with regression tests for preserved substantive replies.

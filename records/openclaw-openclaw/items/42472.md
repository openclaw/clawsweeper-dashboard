## Summary

Keep open: current main and the latest release still preserve general mixed trailing `NO_REPLY` payloads by stripping the token and delivering the preceding text, while narrower token-only, punctuation-wrapped, reasoning-prefixed, and cron-specific cases are covered separately. The remaining work is a shared reply-delivery security/product boundary decision, and the open fork PR is only an unmerged implementation candidate.

## What This Changes

The issue requests suppressing the entire auto-reply payload when a model emits visible text followed by `NO_REPLY`, instead of stripping only the sentinel and delivering the preceding text.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed `NO_REPLY` payloads, preserve legitimate substantive replies, then apply that contract consistently across shared delivery paths with focused regression proof.

Rationale: Current source and tests intentionally preserve some mixed trailing-token replies, while the report asks for broader suppression to prevent internal text leaks; choosing that boundary changes shared reply-delivery semantics.

Likely owner: steipete

Owner confidence: high

Options:

- **Adopt classifier-based suppression (recommended):** Define a shared silent-intent classifier that suppresses internal/status preambles while preserving legitimate substantive replies, then use it across delivery paths.
- **Use blanket trailing-token suppression:** Suppress any reply ending with a trailing or own-line `NO_REPLY` token and accept that some currently visible replies may be dropped.
- **Keep the narrow policy:** Document that only token-only, punctuation-only, reasoning-prefixed, and scoped path cases are suppressed, leaving broad mixed-content suppression out of scope.

## Reproduction Assessment

Yes, source-reproducible: `normalizeReplyPayload` strips a trailing `NO_REPLY` token from mixed content and returns the remaining text, and current tests assert that behavior. I did not run a live channel repro because this is a read-only review.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer path is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

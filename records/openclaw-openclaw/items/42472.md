## Summary

Keep open: current main and v2026.6.11 still preserve generic mixed trailing NO_REPLY text on the shared normal reply path, while adjacent fixes only cover narrower token-only, punctuation-wrapped, reasoning-prefixed, cron-specific, or streaming-prefix cases. The remaining request changes shared message-delivery and security semantics, and an open conflicting fork PR still references this issue as its closing target.

## What This Changes

The issue requests broader post-processing so a model reply containing or ending with NO_REPLY suppresses the whole reply instead of exposing preceding internal text.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed NO_REPLY payloads, preserve legitimate substantive replies, and apply that contract consistently across reply normalization, outbound delivery, cron, and streaming/turn-level paths with focused regression proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw broaden NO_REPLY suppression for generic mixed trailing or contained payloads, and where should the boundary sit between silent-intent text and legitimate substantive replies that mention or append the token?

Rationale: Current main deliberately preserves some substantive trailing-token replies while the issue asks for broader suppression to avoid internal text leaks; that is a shared message-delivery and security contract decision rather than a mechanical cleanup.

Likely owner: steipete

Owner reason: This choice spans shared reply delivery and security/product policy, and steipete is tied to recent classifier and central-file landing history.

Owner confidence: medium

Options:

- **Adopt classifier-based suppression (recommended):** Define a shared classifier that suppresses internal or silent-intent mixed payloads while preserving legitimate substantive replies, then reuse it across delivery paths.
- **Use blanket trailing/own-line suppression:** Suppress any reply ending with a trailing or own-line NO_REPLY token and accept that some currently visible substantive replies may be dropped.
- **Keep the current narrow policy:** Document that only token-only, punctuation-only, reasoning-prefixed, and selected scoped cases are suppressed, then close or retarget broad suppression requests.

## Reproduction Assessment

Yes, source-reproducible: current normalizeReplyPayload strips a trailing NO_REPLY token from generic mixed content and returns the remaining text, and tests assert that behavior. I did not run a live channel repro because this is a read-only review.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer solution is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

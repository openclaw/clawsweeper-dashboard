## Summary

Keep open: current main and v2026.6.11 still preserve and deliver generic mixed trailing `NO_REPLY` text on the shared normal reply path, while narrower token-only, punctuation-wrapped, reasoning-prefixed, and cron-specific cases are covered. The remaining request changes a shared security and message-delivery contract, so it needs maintainer direction rather than cleanup closure.

## What This Changes

The issue requests suppressing the entire auto-reply payload when a model emits text followed by `NO_REPLY`, instead of stripping only the token and delivering the prefix text.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed `NO_REPLY` payloads, preserve legitimate substantive replies, and apply that contract consistently across reply normalization, outbound delivery, cron, and streaming paths with focused regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw broaden mixed trailing or own-line `NO_REPLY` suppression, and what boundary should separate internal silent-intent text from legitimate substantive replies that mention or append the token?

Rationale: Current main deliberately preserves some substantive trailing-token replies, while the issue asks for broader suppression to prevent internal text leaks; that is a shared security and message-delivery contract choice.

Likely owner: steipete

Owner reason: The decision spans the shared reply contract introduced by the PR 31080 landing and needs a maintainer-level security/product boundary call.

Owner confidence: medium

Options:

- **Adopt classifier-based suppression (recommended):** Define shared silent-intent detection that suppresses internal or silent-intent mixed payloads while preserving legitimate substantive replies across delivery paths.
- **Use blanket trailing suppression:** Suppress any reply ending with a trailing or own-line `NO_REPLY`, accepting that some currently visible substantive replies may be dropped.
- **Keep the narrow policy:** Document that only token-only, punctuation-wrapped, JSON, and reasoning-prefixed silent payloads are suppressed, then retarget or close broad suppression requests.

## Reproduction Assessment

Yes, source-reproducible: current `normalizeReplyPayload` strips a trailing `NO_REPLY` from mixed content and returns the remaining text, and current tests assert that behavior. I did not run a live channel repro because this review is read-only.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer solution is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

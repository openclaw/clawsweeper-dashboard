## Label Justifications

- `P2`: The issue describes a real shared delivery/security hardening gap with limited scope and no evidence of a core-runtime outage.
- `impact:security`: Mixed NO_REPLY output can expose internal model summaries or reasoning that were intended to be suppressed.

## Summary

Keep open: current main still preserves some mixed trailing NO_REPLY payloads by stripping the token and delivering the remaining text. Adjacent token-only, punctuation-wrapped, JSON, reasoning-prefixed, and cron-specific cases are covered, but the broader suppress-entire-payload request still needs a maintainer security/message-delivery decision.

## What This Changes

Request broader NO_REPLY post-processing so mixed model outputs containing or ending with NO_REPLY suppress the entire visible reply.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed NO_REPLY payloads, preserve legitimate substantive replies, and apply that contract consistently across reply normalization, outbound delivery, cron, and streaming/turn-level paths with focused regression and real channel proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw broaden NO_REPLY suppression for mixed trailing or own-line payloads, and where should it draw the boundary between silent-intent text and legitimate substantive replies that mention or append the token?

Rationale: Current main intentionally preserves some substantive trailing-token replies while this issue asks for broader suppression to prevent internal text leaks, so the right boundary is a maintainer security and message-delivery policy choice.

Likely owner: steipete

Owner reason: The choice spans shared reply delivery, security policy, and the current central-file history where steipete is the strongest routing candidate.

Owner confidence: high

Options:

- **Adopt classifier-based suppression (recommended):** Define a shared classifier that suppresses internal or silent-intent mixed payloads, preserves legitimate substantive replies, and applies consistently across delivery paths.
- **Suppress any trailing or own-line token:** Treat every reply ending with a trailing or own-line NO_REPLY token as silent, accepting that some currently visible substantive replies may be dropped.
- **Keep the current narrow policy:** Document that only token-only, punctuation-only, JSON, reasoning-prefixed, and selected cron silent payloads are suppressed, then close or retarget broad suppression requests.

## Reproduction Assessment

Yes, source-reproducible: current normalizeReplyPayload strips a trailing NO_REPLY token from mixed content and returns the remaining text, while adjacent tests assert that substantive trailing-token payloads stay non-silent. I did not run live channel proof because this review is read-only.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer solution is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

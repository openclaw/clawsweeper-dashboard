## Summary

Keep open: current main and v2026.6.11 still preserve some mixed trailing `NO_REPLY` payloads by stripping the token and delivering the remaining text, while narrower token-only, punctuation-wrapped, reasoning-prefixed, and cron-specific cases are already covered. The remaining change is a shared reply-delivery/security policy decision, not a cleanup close.

## What This Changes

The issue requests suppressing the entire outgoing reply when a model emits visible text followed by the `NO_REPLY` silent-reply sentinel.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed `NO_REPLY` payloads, preserve legitimate substantive replies, then apply that contract consistently across reply normalization, outbound delivery, cron, and streaming/turn-level paths with focused regression and real channel proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw broaden NO_REPLY suppression for mixed trailing or own-line payloads, and where should the boundary sit between silent-intent internal text and legitimate substantive replies that append or mention the token?

Rationale: Current code and tests intentionally preserve some substantive trailing-token replies, while the issue asks for broader suppression to prevent internal text leaks; changing that shared delivery contract requires product/security intent.

Likely owner: steipete

Owner reason: This is a shared reply-delivery and security/product policy choice, and history shows steipete carried recent classifier follow-up work in the central files.

Owner confidence: medium

Options:

- **Adopt classifier-based suppression (recommended):** Define one shared silent-intent classifier that suppresses internal or status preambles but preserves legitimate substantive replies, then apply it across reply normalization, outbound delivery, cron, and streaming paths.
- **Use blanket trailing or own-line suppression:** Suppress any reply ending with a trailing or own-line NO_REPLY token, accepting that some currently visible substantive replies may be dropped.
- **Keep the narrow policy:** Document that only token-only, punctuation-only, and reasoning-prefixed silent payloads are suppressed, then close broad suppression requests as out of scope.

## Reproduction Assessment

Yes, source-reproducible: `normalizeReplyPayload` strips a trailing NO_REPLY token from mixed content and returns the remaining text, and tests currently assert that behavior. I did not run a live channel repro because this review is read-only.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer solution is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

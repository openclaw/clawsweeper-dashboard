- `P2`: This is a real shared delivery/security hardening issue with source-level evidence, but it has limited blast radius and no current core-runtime outage.
- `impact:security`: Mixed `NO_REPLY` output can expose internal model summaries or reasoning that the model attempted to suppress.
- `impact:message-loss`: The requested policy changes whether generated channel replies are delivered or suppressed.

## Summary

Keep open: current main and latest release still deliver generic mixed text before a trailing `NO_REPLY`, while narrower token-only punctuation, reasoning-prefixed, and cron-specific cases are only partially covered. The remaining work is a shared reply-delivery/security policy decision because blanket suppression would also drop replies that current tests intentionally preserve.

## What This Changes

The issue requests broad post-processing so any model output containing or ending with `NO_REPLY` suppresses the entire user-visible reply instead of stripping only the sentinel.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed `NO_REPLY` payloads, preserve legitimate substantive replies, and apply it consistently across reply normalization, outbound delivery, cron, and streaming paths with focused channel proof.

Question: Should OpenClaw broaden `NO_REPLY` suppression for mixed trailing or own-line payloads, and what boundary should separate silent-intent internal text from legitimate substantive replies that append or mention the token?

Rationale: Current source and tests intentionally preserve some trailing-token replies, while the issue asks for broader suppression to prevent internal text leaks; changing that shared delivery contract requires maintainer product and security intent.

Likely owner: steipete

Owner confidence: high

Options:

- **Adopt a shared classifier (recommended):** Define a single silent-intent classifier that suppresses internal/status preambles while preserving legitimate substantive replies, then apply it across the delivery surfaces.
- **Use blanket trailing suppression:** Suppress any reply ending with an own-line or trailing `NO_REPLY`, accepting that some currently visible substantive replies may be dropped.
- **Keep the narrow contract:** Document that only token-only, punctuation-wrapped token-only, and reasoning-prefixed silent payloads are suppressed, and close broad mixed-content suppression as out of scope.

## Reproduction Assessment

Yes. Source inspection shows `normalizeReplyPayload` strips a trailing `NO_REPLY` from mixed content and returns the remaining text, and current tests assert that behavior for substantive text before the token.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer solution is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

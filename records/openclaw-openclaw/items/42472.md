## Summary

Keep open: current main and v2026.6.11 still preserve and deliver generic mixed trailing `NO_REPLY` text on the shared reply path, while current fixes only cover token-only, punctuation-wrapped, reasoning-prefixed, and cron-specific cases. The remaining request changes shared message-delivery/security semantics and needs maintainer product/security direction before a new fix path is safe.

## What This Changes

Request to suppress the entire reply when model output appends or contains `NO_REPLY`, instead of stripping only the token and delivering preceding text.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed `NO_REPLY` payloads, preserve legitimate substantive replies, and apply it consistently across reply normalization, outbound delivery, cron, and streaming/turn-level paths with focused regression proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw broaden `NO_REPLY` suppression for mixed trailing or own-line payloads, and where is the boundary between silent-intent internal text and legitimate substantive replies that append or mention the token?

Rationale: Current main intentionally preserves some mixed trailing-token replies, while the issue asks for broader suppression to prevent internal text leaks; that is a shared message-delivery and security contract choice rather than a mechanical cleanup close.

Likely owner: steipete

Owner reason: This decision spans shared reply delivery and security/product policy, and steipete is the clearest routing candidate from the central behavior's commit history.

Owner confidence: medium

Options:

- **Adopt classifier-based suppression (recommended):** Define a shared classifier that suppresses internal or silent-intent mixed payloads, preserves legitimate substantive replies, and is reused by every delivery path.
- **Use blanket trailing or own-line suppression:** Suppress any reply ending with a trailing or own-line `NO_REPLY` token, accepting that some currently visible substantive replies may be dropped.
- **Keep the narrow current policy:** Document that only token-only, punctuation-only, and reasoning-prefixed silent payloads are suppressed, then retarget broad suppression requests.

## Reproduction Assessment

Yes. Source inspection shows `normalizeReplyPayload` strips a trailing `NO_REPLY` token from mixed content and returns the remaining text, and current tests assert that behavior.

## Solution Assessment

No, not as the suggested blanket suppress-if-contains rule. The safer path is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

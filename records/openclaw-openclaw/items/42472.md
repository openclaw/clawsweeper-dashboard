## Summary

Keep open: current main and v2026.6.11 still strip and deliver some mixed trailing NO_REPLY payloads on the shared normal reply path, while only narrower token-only, punctuation-wrapped, reasoning-prefixed, and cron-specific cases are covered. The remaining request changes shared message-delivery/security semantics and should stay with maintainer product/security review, especially because a linked fork PR is open but conflicting and unmerged.

## What This Changes

The issue asks OpenClaw to suppress an entire reply when model output contains a trailing or own-line NO_REPLY token after other text, instead of stripping only the token and delivering the preceding content.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed NO_REPLY payloads, preserve legitimate substantive replies, then apply that contract consistently across reply normalization, outbound delivery, cron, and streaming/turn-level paths with focused regression and real channel proof.

Question: Should OpenClaw broaden NO_REPLY suppression for mixed trailing or own-line payloads, and if so where is the boundary between silent-intent text and legitimate substantive replies that mention or append the token?

Rationale: Current main intentionally preserves some substantive trailing-token replies, while the issue asks for broader suppression to prevent internal text leaks; that is a shared message-delivery and security contract choice rather than a mechanical cleanup close.

Likely owner: steipete

Owner reason: The decision spans shared reply delivery and security/product policy; steipete is the best available routing candidate from recent classifier commit and current central-file history.

Owner confidence: medium

Options:

- **Adopt classifier-based suppression (recommended):** Define a shared classifier that suppresses internal or silent-intent mixed payloads, preserves legitimate substantive replies, and applies consistently across delivery paths.
- **Use blanket trailing/own-line suppression:** Suppress any reply ending with a trailing or own-line NO_REPLY token, accepting that some currently visible substantive replies may be dropped.
- **Keep the current narrow policy:** Document that only token-only, punctuation-only, and reasoning-prefixed silent payloads are suppressed, then close or retarget broad suppression requests.

## Reproduction Assessment

Yes, source-reproducible: normalizeReplyPayload strips a trailing NO_REPLY token from mixed content and returns the remaining text, and tests currently assert that behavior. I did not run a live channel repro because this review is read-only.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer solution is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

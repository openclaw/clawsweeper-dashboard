## Summary

Keep open: current main and latest release still strip and deliver generic mixed trailing `NO_REPLY` text on the shared final-reply path, while only narrower reasoning-prefixed, punctuation-wrapped token-only, and cron synthesized cases are covered. The remaining behavior needs maintainer product/security direction because current tests intentionally preserve substantive-looking text before a trailing sentinel.

## What This Changes

The issue requests post-processing so a reply containing `NO_REPLY`, especially text followed by the sentinel, suppresses the whole reply instead of leaking the prefix text.

## Best Possible Solution

Maintainers should choose and document the shared silent-reply contract, then update the shared classifier/normalizer and focused tests while preserving the existing cron, reasoning-prefixed, and punctuation token-only fixes.

Rationale: Current source and tests deliberately preserve some substantive trailing-token replies, while the issue asks to turn that same shape into full suppression for security and noise reduction; automation cannot choose that policy boundary safely.

Options:

- **Define A Narrow Shared Silence Rule (recommended):** Suppress whole messages only for an explicit final-line or silent-intent boundary that maintainers document, and add tests for both suppression and preserved substantive replies.
- **Adopt Broad Contains Suppression:** Treat any `NO_REPLY` occurrence as a whole-message suppressor, accepting the message-loss risk for text that previously delivered after token stripping.
- **Preserve Current Split Behavior:** Keep the current reasoning-prefixed, punctuation token-only, and cron-specific fixes, and close or re-scope this issue as not planned for generic mixed content.

Yes: source inspection and existing tests show the current shared normalizer strips `NO_REPLY` from a substantive-looking trailing-token reply and returns the remaining prefix. I did not run tests in this read-only review, and cron synthesized delivery is already covered by a separate suppression path.

## Solution Assessment

Unclear: the requested `/NO_REPLY/` suppress-if-present rule would solve the leak class but is broader than the current tested contract. The more maintainable path is an explicit maintainer-approved silence-intent boundary with regression tests for preserved substantive replies.

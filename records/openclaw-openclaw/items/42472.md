## Label Justifications

- `P2`: The issue describes a real shared reply-delivery hardening gap with limited scope and no evidence of a core runtime outage.
- `impact:security`: Mixed `NO_REPLY` output can expose internal model summaries or reasoning that were intended to be suppressed.

## Summary

Keep open: current main still preserves general mixed `NO_REPLY` replies by stripping the token and delivering the remaining text, while narrower token-only, punctuation-wrapped, reasoning-prefixed, and cron-specific cases are already covered. The remaining work is a maintainer security/product boundary decision, and the open fork PR that claims the closing relationship is unmerged and conflicting.

## What This Changes

The issue requests a broader reply post-processing rule that suppresses an entire model reply when mixed text contains or ends with `NO_REPLY`.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed `NO_REPLY` payloads, preserve legitimate substantive replies, then apply that contract consistently across shared reply normalization, outbound delivery, cron, streaming, and history paths with focused regression proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw broaden mixed trailing or own-line `NO_REPLY` suppression, and what boundary should separate silent-intent internal text from legitimate substantive replies that append or mention the token?

Rationale: Current source and tests intentionally preserve some mixed trailing-token replies, while the issue asks for broader suppression to prevent internal text leaks; choosing that boundary affects both security and message-loss behavior.

Likely owner: steipete

Owner reason: He is the strongest history-backed routing candidate for the existing mixed-token normalizer behavior and tests.

Owner confidence: high

Options:

- **Adopt classifier-based suppression (recommended):** Define a shared classifier that suppresses internal/status preambles and reasoning-like silent intent while preserving legitimate substantive replies, then update all delivery paths to use it.
- **Use blanket trailing-token suppression:** Suppress any reply ending with a trailing or own-line `NO_REPLY` token and accept that some currently visible replies may be dropped.
- **Keep the narrow policy:** Document that only token-only, punctuation-only, reasoning-prefixed, and scoped cron cases are suppressed, and close broader mixed-content suppression as out of scope.

## Reproduction Assessment

Yes, source-reproducible: current shared normalization strips a trailing `NO_REPLY` token from generic mixed content and returns the remaining text, and current tests assert mixed-token preservation. I did not run a live channel repro because this review was read-only.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer path is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

## Summary

Keep open: current main still strips a generic trailing NO_REPLY from mixed text and delivers the preceding text, with tests pinning that behavior; the linked fork PR targets this issue but is open, unmerged, and conflicting, so maintainers still need to choose the suppression contract.

## What This Changes

The issue requests suppressing the entire auto-reply payload when a model emits visible text before a trailing or contained NO_REPLY sentinel.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed NO_REPLY payloads, preserve legitimate substantive replies, and apply that contract consistently across reply normalization, outbound delivery, cron, and streaming or turn-level paths with focused regression proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw broaden NO_REPLY suppression for generic mixed trailing or contained payloads, and where should the boundary sit between silent-intent text and legitimate substantive replies that mention or append the token?

Rationale: Current main deliberately preserves some substantive trailing-token replies while the issue asks for broader suppression to avoid internal text leaks, so this is a shared message-delivery and security contract decision rather than mechanical cleanup.

Likely owner: vincentkoc

Owner reason: Recent current-main ownership is strongest on the classifier and normalizer files that would need the final policy encoded.

Owner confidence: high

Options:

- **Adopt classifier-based suppression (recommended):** Define and reuse a shared classifier that suppresses internal or silent-intent mixed payloads while preserving legitimate substantive replies.
- **Use blanket own-line suppression:** Suppress any reply ending with a trailing or own-line NO_REPLY token and accept that some currently visible substantive replies may be dropped.
- **Keep the narrow policy:** Document that only token-only, punctuation-only, reasoning-prefixed, and scoped cron cases are suppressed, then retarget broad suppression requests.

## Reproduction Assessment

Yes, source-reproducible: current normalizeReplyPayload strips a trailing NO_REPLY token from generic mixed content and returns the remaining text, and current tests assert that behavior. I did not run a live channel repro because this is a read-only cleanup review.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer solution is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

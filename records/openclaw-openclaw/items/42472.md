## Label Justifications

- `P2`: The issue describes a real shared reply-delivery hardening gap with limited scope and no evidence of a core runtime outage.
- `impact:security`: Mixed `NO_REPLY` output can expose internal model summaries or reasoning that were intended to be suppressed.
- `impact:message-loss`: The requested policy directly controls whether generated channel replies are delivered or suppressed.

## Summary

Keep open: current `main` and the latest release still preserve general mixed trailing `NO_REPLY` payloads by stripping the token and delivering the preceding text, while narrower punctuation-only, reasoning-prefixed, and cron-specific cases are already covered. The remaining work is a shared reply-delivery security/product boundary decision, and an open fork PR still claims the closing relationship but is unmerged.

## What This Changes

Issue requests suppressing the entire model reply whenever a mixed response contains `NO_REPLY`, so preceding internal summaries are not delivered to users.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed `NO_REPLY` payloads, preserve legitimate substantive replies, then apply that contract consistently across reply normalization, outbound delivery, cron, and streaming/history paths with focused regression proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw broaden mixed trailing or own-line `NO_REPLY` suppression, and what boundary should separate silent-intent internal text from legitimate substantive replies that append or mention the token?

Rationale: Current source and tests intentionally preserve some mixed trailing-token replies, while this report asks for broader suppression to prevent internal text leaks; choosing that boundary changes the shared security/product delivery contract.

Likely owner: steipete

Owner reason: The earliest inspected mixed-token strip-and-deliver behavior was landed by this owner, and the remaining choice changes that shared contract.

Owner confidence: high

Options:

- **Adopt classifier-based suppression (recommended):** Define and share a silent-intent classifier that suppresses internal/status preambles while preserving legitimate substantive replies, then update all delivery paths to use it.
- **Use blanket trailing-token suppression:** Suppress any reply ending with a trailing or own-line `NO_REPLY` token and accept that some currently visible replies may be dropped.
- **Keep the narrow policy:** Document that only token-only, punctuation-only, reasoning-prefixed, and scoped cron cases are suppressed, and close broader mixed-content suppression as out of scope.

## Reproduction Assessment

Yes, source-reproducible: current `normalizeReplyPayload` strips a trailing `NO_REPLY` token from mixed content and returns the remaining text, and current tests assert that behavior. I did not run a live channel repro because this is a read-only review.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer path is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

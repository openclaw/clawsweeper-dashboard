## Label Justifications

- `P2`: Silent-reply leakage is a normal-priority user-visible reliability/security issue with limited but real message-delivery blast radius.
- `impact:security`: The report is about internal summaries or reasoning leaking to users when `NO_REPLY` is intended to suppress output.
- `impact:message-loss`: The requested behavior changes whether generated channel replies are delivered or suppressed when `NO_REPLY` appears with other text.

## Summary

Keep open: current main and the latest release still preserve some mixed trailing `NO_REPLY` payloads, while only narrower reasoning-prefixed, punctuation-only, and cron-specific cases have landed. The broad requested suppression policy changes shared message-delivery semantics and should stay with maintainer security/product review, especially because the linked fork PR is open, conflicting, and unmerged.

## What This Changes

The issue requests suppressing an entire auto-reply payload when model output includes `NO_REPLY` after preceding text, instead of stripping only the token and delivering the prefix.

## Best Possible Solution

Define a shared, maintainer-approved silent-token classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies, then apply it consistently across reply normalization and outbound delivery.

## Reproduction Assessment

Yes. Source inspection shows current main still strips a mixed trailing `NO_REPLY` and returns the non-empty prefix in the shared normalizer, and adjacent tests pin that behavior.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer path is a maintainer-approved classifier that distinguishes internal or silent-intent payloads from legitimate substantive replies before changing shared delivery semantics.

## Summary

Keep open: current main and v2026.6.11 still preserve some mixed trailing NO_REPLY payloads by stripping the token and delivering the remaining text. Narrower token-only, punctuation-wrapped, JSON, reasoning-prefixed, and cron-specific cases are covered, but the broader suppress-entire-payload request is a shared message-delivery/security policy decision, not a cleanup close.

## What This Changes

The issue requests a gateway/reply post-processing rule that suppresses the entire response when a model emits visible text followed by a NO_REPLY sentinel.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed NO_REPLY payloads, preserve legitimate substantive replies, and apply that contract consistently across reply normalization, outbound delivery, cron, and streaming/turn-level paths with focused regression and real channel proof.

Rationale: Current main intentionally preserves some substantive trailing-token replies, while this issue asks for broader suppression to prevent internal text leaks; that is a shared message-delivery and security contract choice rather than a mechanical fix.

Options:

- **Adopt classifier-based suppression (recommended):** Define a shared classifier that suppresses internal or silent-intent mixed payloads, preserves legitimate substantive replies, and applies consistently across delivery paths.
- **Suppress any trailing or own-line token:** Treat every reply ending with a trailing or own-line NO_REPLY token as silent, accepting that some currently visible substantive replies may be dropped.
- **Keep the current narrow policy:** Document that only token-only, punctuation-only, JSON, and reasoning-prefixed silent payloads are suppressed, then close or retarget broad suppression requests.

## Reproduction Assessment

Yes, source-reproducible: current normalizeReplyPayload strips a trailing NO_REPLY token from mixed content and returns the remaining text, and adjacent tests assert that substantive trailing-token payloads stay non-silent. I did not run live channel proof because this review is read-only.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer solution is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

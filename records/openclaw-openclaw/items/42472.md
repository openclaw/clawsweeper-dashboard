## Label Justifications

- `P2`: The issue describes a real shared reply-delivery hardening gap with limited scope and no evidence of a core runtime outage.
- `impact:security`: Mixed `NO_REPLY` output can expose internal model summaries or reasoning that were intended to be suppressed.
- `impact:message-loss`: The requested policy directly controls whether generated channel replies are delivered or suppressed.

## Summary

Keep open: current main and the latest release still preserve generic mixed trailing `NO_REPLY` payloads by stripping the token and delivering the preceding text. Narrower token-only, punctuation-wrapped, reasoning-prefixed, and cron-specific cases are covered, but the broad shared reply-delivery policy still needs maintainer security/product direction.

## What This Changes

The issue requests suppressing an entire auto-reply payload when model output contains a trailing or own-line `NO_REPLY` sentinel after visible text.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed `NO_REPLY` payloads, preserve legitimate substantive replies, and apply that contract consistently across reply normalization, outbound delivery, cron, and streaming/history paths with focused regression proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw broaden mixed trailing or own-line `NO_REPLY` suppression, and what boundary should separate silent-intent internal text from legitimate substantive replies that append or mention the token?

Rationale: Current source and tests intentionally preserve some mixed trailing-token replies, while the report asks for broader suppression to prevent internal text leaks; choosing that boundary is a shared security/product contract, not a mechanical cleanup.

Likely owner: steipete

Owner reason: He is the strongest current-history routing candidate for the shared auto-reply policy and tests touched by this issue.

Owner confidence: high

Options:

- **Adopt classifier-based suppression (recommended):** Define and share a silent-intent classifier that suppresses internal/status preambles while preserving legitimate substantive replies, then update all delivery paths to use it.
- **Use blanket trailing-token suppression:** Suppress any reply ending with a trailing or own-line `NO_REPLY` token and accept that some currently visible replies may be dropped.
- **Keep the narrow policy:** Document that only token-only, punctuation-only, reasoning-prefixed, and scoped cron cases are suppressed, and close broader mixed-content suppression as out of scope.

## Reproduction Assessment

Yes, source-reproducible: `normalizeReplyPayload` strips a trailing `NO_REPLY` token from mixed content and returns the remaining text, and current tests assert that behavior. I did not run a live channel repro because this is a read-only review.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer path is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

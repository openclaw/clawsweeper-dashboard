## Summary

Keep open: current main and v2026.6.11 still preserve generic mixed trailing NO_REPLY text, while merged fixes cover narrower reasoning-prefixed, punctuation-wrapped, and cron-specific cases. The remaining broad suppression request changes the shared message-delivery/security contract and needs maintainer product review, especially with an open but conflicting fork PR linked as a candidate.

## What This Changes

Request to broaden NO_REPLY post-processing so mixed responses containing or ending with NO_REPLY suppress the whole reply instead of stripping the token and delivering the prefix.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed NO_REPLY payloads, preserve legitimate substantive replies, and apply that contract consistently across reply normalization, outbound delivery, cron, and streaming/turn-level paths with focused regression and real channel proof.

Question: Should OpenClaw broaden NO_REPLY suppression for mixed trailing or own-line payloads, and where is the boundary between silent-intent text and legitimate substantive replies that append or mention the token?

Rationale: Current main intentionally preserves some substantive trailing-token replies, while the issue asks for broader suppression to prevent internal text leaks; that is a shared delivery and security policy choice rather than a mechanical cleanup.

Likely owner: steipete

Owner confidence: medium

Options:

- **Adopt classifier-based suppression (recommended):** Define a shared classifier that suppresses internal or silent-intent mixed payloads, preserves legitimate substantive replies, and applies consistently across delivery paths.
- **Use blanket trailing/own-line suppression:** Suppress any reply ending with a trailing or own-line NO_REPLY token, accepting that some currently visible substantive replies may be dropped.
- **Keep the current narrow policy:** Document that only token-only, punctuation-only, and reasoning-prefixed silent payloads are suppressed, then close or retarget broad suppression requests.

## Reproduction Assessment

Yes, source-reproducible: normalizeReplyPayload strips a trailing NO_REPLY token from mixed content and returns the remaining text, and tests currently assert that behavior. I did not run a live channel repro because this review is read-only.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer solution is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

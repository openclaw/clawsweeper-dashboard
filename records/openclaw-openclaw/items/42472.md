## Summary

Keep open: current main and v2026.6.11 still preserve generic mixed trailing NO_REPLY payloads after stripping the token, while only narrower token-only, punctuation-wrapped, reasoning-prefixed, and cron-specific cases are covered. A linked fork PR is open but conflicting, so the remaining broad suppression policy needs maintainer security/product review rather than cleanup close.

## What This Changes

The issue requests suppressing an entire reply when model output contains or ends with NO_REPLY after other text, instead of stripping only the token and delivering the prefix.

## Best Possible Solution

Define one maintainer-approved silent-intent classifier for mixed NO_REPLY payloads, preserve legitimate substantive replies, then apply that contract consistently across reply normalization, outbound delivery, cron, and streaming/turn-level paths with focused regression and real channel proof.

- **Use blanket trailing or own-line suppression:** Suppress any reply ending with a trailing or own-line NO_REPLY token, accepting that some currently visible substantive replies may be dropped.
- **Keep the current narrow policy:** Document that only token-only, punctuation-only, and reasoning-prefixed silent payloads are suppressed, then close or retarget broad suppression requests.

## Reproduction Assessment

Yes, source-reproducible: normalizeReplyPayload strips a trailing NO_REPLY token from mixed content and returns the remaining text, and current tests assert that behavior. I did not run live channel proof because this review is read-only.

## Solution Assessment

No, not as a blanket suppress-if-contains rule. The safer solution is a maintainer-approved classifier that suppresses internal or silent-intent payloads while preserving legitimate substantive replies before changing shared delivery semantics.

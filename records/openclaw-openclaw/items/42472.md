## Summary

Keep open: current main has narrowed NO_REPLY hardening for token-only, punctuation-wrapped, reasoning-prefixed, and cron-delivery cases, but it still deliberately preserves generic substantive mixed-content replies that end in NO_REPLY. The remaining broad suppress-if-present behavior is a message-delivery/security product decision, not conservative cleanup.

## What This Changes

The issue requests changing NO_REPLY post-processing so replies that contain or end with the silent token suppress the entire user-visible message instead of delivering text before the token.

## Best Possible Solution

Define one maintainer-approved mixed-NO_REPLY classifier, preserve legitimate substantive replies, and apply that contract consistently across reply normalization, directive parsing, cron, streaming, and dispatcher paths with focused channel proof.

## Reproduction Assessment

Yes, source-reproducible: current tests explicitly keep generic substantive replies ending in NO_REPLY as non-silent, while reasoning-prefixed and cron-specific cases are handled separately. I did not run live channel proof because this was a read-only cleanup review.

## Solution Assessment

No for a blanket suppress-if-contains rule. The better path is a maintainer-approved classifier that suppresses internal or silent-intent payloads without erasing legitimate substantive replies that current tests preserve.

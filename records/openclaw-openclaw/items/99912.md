## Label Justifications

- `P1`: A shipped multi-agent heartbeat workflow can run under the wrong agent identity and workspace for real users using global session scope.
- `impact:session-state`: The report is about heartbeat turns being associated with the default agent session/identity instead of the configured secondary agent.
- `impact:message-loss`: Wrong-agent heartbeat routing can suppress or misdirect the expected heartbeat output for the configured agent.

## Summary

Keep open: current main and the latest release still construct heartbeat reply context with `SessionKey: "global"` but no explicit agent identity, so secondary-agent heartbeats can resolve as the default agent. The open fix candidate at https://github.com/openclaw/openclaw/pull/102307 now owns the narrow remaining work.

## What This Changes

The issue reports secondary-agent heartbeats under global session scope running as the default agent and reading the default agent's `HEARTBEAT.md` instead of the configured agent's workspace.

## Best Possible Solution

Land a narrow fix that passes the configured heartbeat agent id into reply context while preserving the global session key contract, with regression coverage and live multi-agent heartbeat proof, then close this issue.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes for a source-level reproduction: `session.scope: "global"` produces `SessionKey: "global"`, current heartbeat context does not set `AgentId`, and reply resolution falls back to the default agent. I did not run a live Docker/WSL heartbeat turn in this read-only review.

## Solution Assessment

Yes, the current candidate shape is the narrowest maintainable fix: keep the global session key but pass the heartbeat's agent id through the existing `MsgContext.AgentId` fallback. Re-keying global sessions per agent would conflict with the global-scope contract.

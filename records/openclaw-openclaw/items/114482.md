## Summary

This is still a live developer-experience feature request: it proposes a new core CLI scaffold rather than repairing broken documented behavior. The request has a credible implementation direction, but repository policy makes the scope choice consequential—maintainers should first decide whether channel scaffolding belongs in the core authoring command or should remain a documented/plugin-owned starter pattern.

## What This Changes

Add a `openclaw plugins init --type channel` option that creates and validates a minimal channel-plugin package with manifest, setup entry, configuration schema, adapter stubs, tests, and authoring documentation.

## System Context

`openclaw plugins init` is the CLI entry point that creates starter packages for extension authors. A channel scaffold would feed generated package metadata and source stubs into the plugin SDK, after which an external channel plugin can be built, validated, installed, and loaded by OpenClaw.

## Architecture Diagram

flowchart LR
  Author[Plugin author] --> CLI[Plugin init command]
  CLI --> Choice[Scaffold type selection]
  Choice --> Generator[Channel starter generator]
  Generator --> Package[Generated plugin package]
  Package --> SDK[Plugin SDK contracts]
  SDK --> Loader[OpenClaw plugin loader]
  Loader --> Channel[External channel integration]

## Best Possible Solution

Choose a supported minimum channel-plugin starter contract first, then either add that narrowly to `openclaw plugins init` with generated-scaffold validation or publish a maintained external starter package if core CLI ownership is not warranted.

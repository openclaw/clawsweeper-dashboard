## Summary

Keep this issue open. The supplied report identifies a concrete model-fallback failure: a Google invalid-key response is a credential failure, but the shared matcher apparently leaves it unclassified, allowing retry bookkeeping to end a failed candidate as successful and prevent later configured providers from running. No merged fix or canonical replacement is established in the related-item context.

## What This Changes

Classify Google Generative AI invalid-API-key HTTP 400 responses as authentication failures so a failed Google candidate advances to the next configured model fallback.

## System Context

Model failover selects an ordered model/provider candidate, classifies failures, and either retries credentials or advances through later candidates. Google provider errors feed the shared classifier, whose result controls agent-run fallback decisions and the final response returned to the user.

## Best Possible Solution

Add a narrowly scoped Google invalid-key matcher in the shared failover classification path, cover the exact HTTP 400 payload and its structured `API_KEY_INVALID` variant, and prove that a subsequent healthy fallback is attempted while unrelated Google 400 validation errors remain non-auth.

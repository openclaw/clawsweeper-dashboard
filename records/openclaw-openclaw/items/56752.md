## Summary

Keep open: current main and v2026.6.11 still do not provide independent macOS desktop WebChat windows. The remaining work is a real feature/product decision, not conservative cleanup, because macOS still has one normal WebChat window owner, no macOS `sessions.create` transport, and `/new` still falls back to resetting the current session when create-session support is unavailable.

## What This Changes

The issue requests multi-window desktop sessions so opening a new conversation window does not pause or interrupt an existing active session.

## Best Possible Solution

Define the desktop session/window ownership model, then implement macOS WebChat windows keyed by session with `sessions.create` support and coverage proving one active run survives opening another chat window.

## Reproduction Assessment

Yes, at source level: current main has one normal macOS WebChat window owner, macOS inherits the unsupported `createSession` default, and `/new` falls back to reset. I did not run a live macOS desktop smoke in this read-only cleanup review.

## Solution Assessment

No current implementation solves the request. The best path is a maintainer-approved desktop session/window model that reuses the existing gateway `sessions.create` RPC instead of adding another session API.

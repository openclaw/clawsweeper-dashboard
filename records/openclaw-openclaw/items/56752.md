## Summary

Keep open: current main still does not provide the requested parallel desktop chat-window behavior. The browser Control UI has shipped flat multi-session creation, but the native macOS WebChat path still owns one normal window, inherits the unsupported create-session transport default, and both current main and the latest stable release still block or reset instead of opening an independent active conversation while another run is in progress.

## What This Changes

The issue requests multiple parallel desktop conversation windows that can run independently without pausing, resetting, or interrupting existing active sessions.

## Best Possible Solution

Define the desktop session/window ownership model, then wire macOS WebChat to the existing sessions.create flow so independent windows can run concurrently while preserving active-run subscriptions and session isolation.

Rationale: The backend create-session primitive exists, but choosing the desktop window model, active-run visibility, native /new behavior, and whether concurrent session creation is allowed while another run is active changes user-facing product semantics beyond a narrow bug fix.

Owner confidence: high

Options:

- **Design Native Multi-Window Sessions (recommended):** Keep this issue open and have macOS/session owners define the window registry, session subscription, and /new/create behavior before implementation.
- **Limit To Browser Flat Sessions:** Treat the shipped Control UI create/switch flow as the current product boundary and explicitly defer native multi-window desktop behavior.
- **Split Browser And macOS Follow-Ups:** Keep this issue for macOS desktop windows and open a separate narrower product question for the Control UI active-run creation guard if maintainers want that changed.

## Reproduction Assessment

Yes, at source level: WebChatManager owns one normal macOS window and closes it for a different session, MacGatewayChatTransport inherits unsupported createSession, and Control UI refuses New Chat while the current session has active or queued work. I did not run a live macOS desktop smoke in this read-only pass.

## Solution Assessment

Unclear until maintainers choose the product contract. The narrow maintainable direction is to reuse the existing sessions.create RPC, but the desktop window registry, active-run subscription behavior, and active-run creation guard need product approval first.

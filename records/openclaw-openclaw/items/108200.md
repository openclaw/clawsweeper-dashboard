## Summary

This PR should remain open but must not merge as written: `@google/genai` applies `httpOptions.timeout` to fetch-based HTTP requests, while `live.connect()` creates a WebSocket and waits for open/setup without consuming that timeout. The regression test verifies configuration rather than the reported behavior, and the terminal proof exercises the wrong transport. ([raw.githubusercontent.com](https://raw.githubusercontent.com/googleapis/js-genai/main/src/_api_client.ts))

## What This Changes

Adds a 30-second timeout to the Google GenAI client used for realtime live sessions and a test asserting that client configuration.

## Best Possible Solution

Enforce a finite deadline in the actual WebSocket open/setup lifecycle, close or invalidate the pending connection on timeout, and prove that a stalled production bridge rejects without later callbacks or reconnect leakage.

Yes at source level: the production bridge awaits the SDK's WebSocket-open and setup-complete promises without a deadline, and the SDK timeout only wraps fetch requests. A stalled WebSocket endpoint can exercise this path, although this read-only review did not run that reproduction. ([raw.githubusercontent.com](https://raw.githubusercontent.com/googleapis/js-genai/main/src/_api_client.ts))

## Solution Assessment

No. The proposed option affects the SDK's HTTP transport rather than the WebSocket transport used by `live.connect()`, so it is not the narrowest effective fix for the reported hang. ([raw.githubusercontent.com](https://raw.githubusercontent.com/googleapis/js-genai/main/src/_api_client.ts))

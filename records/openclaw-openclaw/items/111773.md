## Summary

Keep this PR open, but it is not safe to merge as written: making every fetched response fatal UTF-8 turns valid non-UTF-8 web pages into silently skipped link-understanding results. The current fetch path deliberately accepts broad `text/*` and JSON responses, so decoding must account for the response’s declared character encoding before rejecting malformed bytes.

## What This Changes

The PR changes `fetchLinkContent` to use a fatal UTF-8 `TextDecoder`, causing malformed byte sequences to throw instead of being replaced with U+FFFD.

## Best Possible Solution

Decode according to the response’s declared supported charset and reject malformed sequences for that encoding; retain a deliberate, tested fallback policy for absent or unsupported charset declarations.

## Reproduction Assessment

Yes, source inspection gives a high-confidence path: serve a successful `text/*` response with a valid declared non-UTF-8 charset and bytes invalid under UTF-8; this patch throws during decoding and the surrounding URL loop skips it.

## Solution Assessment

No. Rejecting malformed UTF-8 is a plausible safety goal, but applying it before considering the response charset is not the narrowest compatible solution for a fetcher that accepts broad text responses.

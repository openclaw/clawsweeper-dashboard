## Label Justifications

- `P1`: A reachable user-facing TUI run can appear hung for the full 30-minute approval timeout, breaking the interactive agent workflow until abort or expiry.
- `impact:security`: The bug sits in the exec-approval availability and fallback boundary, where any repair must remain fail-closed.
- `impact:message-loss`: Completed sibling tool results can remain suppressed behind the unresolved approval and may never reach the user when the run is aborted.
- `impact:ux-friction`: The TUI provides no visible approval or pending explanation, forcing users to infer a hang and discover a configuration workaround.

## Summary

Keep this issue open: current main still treats TUI/webchat as approval-capable before checking whether an approval can actually be displayed, while the documented contract says unavailable approval UI should resolve through the configured fallback. The report identifies a credible current behavior bug rather than a completed or duplicate request. 

## What This Changes

Make exec approvals fail visibly and promptly when the initiating TUI or headless surface cannot display an approval, without withholding completed sibling-tool progress for 30 minutes.

## Best Possible Solution

Make approval availability capability-based rather than channel-name-based: if no connected client, native approver route, or actual initiating-surface UI can resolve the request, immediately apply `askFallback` and emit a visible explanation; track incremental parallel-tool progress separately if upstream ordering permits it.

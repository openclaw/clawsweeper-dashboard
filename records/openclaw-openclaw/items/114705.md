## Label Justifications

- `P2`: The proposed optimization has a bounded but real compatibility question for subagent registry state in custom task-runtime deployments.
- `merge-risk: 🚨 session-state`: Removing the post-task save can make registry-owned metadata mutations fail to reach durable subagent state until an unrelated later lifecycle write.

## Summary

Keep this PR open for a narrow compatibility decision before merge. The retained throwing save still protects accepted-registration durability, and the supplied SQLite measurement is useful, but the patch removes the only post-task-creation persistence point while a plugin-replaceable task runtime receives registry-owned request metadata by reference; that can leave a synchronous runtime mutation durable only in memory.

## What This Changes

The PR removes the second best-effort subagent-registry save after task and listener setup, and adds queued and running regression tests that assert one registry persistence call per registration.

## System Context

Subagent registration inserts a run into the durable registry, then creates task-runtime work, attaches lifecycle observation, and starts cleanup/completion handling. The registry snapshot is later read by wait and lifecycle paths, while each persistence call also wakes registry-persistence subscribers.

## Architecture Diagram

flowchart LR

  C --> D[Task runtime creation]
  D --> E[Event listener setup]
  E --> F[Sweeper and completion wait]
  C --> G[Registry persistence subscribers]
  F --> H[Later lifecycle persistence]

## Best Possible Solution

Keep the single authoritative pre-task durability save, but make the task-runtime boundary explicit: pass an isolated request-metadata value if registry state must remain canonical, or document and test an immutability contract before deleting the trailing persistence point.

## Label Justifications

- `P2`: This is a plausible runtime performance bug with limited trigger conditions, affecting large bundle-MCP configurations rather than ordinary setup.
- `impact:crash-loop`: The affected synchronous work can hang the Node event loop long enough to affect Gateway availability and heartbeat-sensitive agent runs.

## Summary

Keep open: current main still synchronously serializes and hashes the bundle-MCP config during CLI backend preparation, and a focused Node probe confirms large SHA-256 input stalls the event loop; the fix should cover the whole fingerprinting path, not only one hash call.

## What This Changes

The issue requests preventing synchronous SHA-256 fingerprinting of generated bundle-MCP CLI config from blocking the Gateway event loop for very large MCP configurations.

## Best Possible Solution

Make bundle-MCP config fingerprinting nonblocking or bounded across serialization and hashing while preserving deterministic `mcpConfigHash`/`mcpResumeHash` values and CLI session invalidation semantics.

## Maintainer Decision

Required: false

## Reproduction Assessment

Partial yes: current source executes synchronous `JSON.stringify` and `crypto.createHash` in the bundle-MCP prepare path, and a 50 MiB hash probe delayed the event loop by 47.9 ms. I did not reproduce the full Gateway heartbeat-disconnect symptom against a live Gateway.

## Solution Assessment

Unclear as stated: replacing only the line-116 hash would be too narrow because the surrounding serialization and resume canonicalization are also synchronous. The maintainable fix should preserve the existing fingerprints while moving or bounding the whole large-config fingerprinting cost.

## Summary

Keep open: current main and v2026.6.11 still reject explicit no-auth Gateway mode on non-loopback binds, and allowing it would weaken a reachable Gateway auth boundary that needs maintainer security/product approval.

## What This Changes

The issue requests an explicit `gateway.auth.mode: "none"` mode for trusted internal deployments without the current trusted-proxy workaround.

## Best Possible Solution

Keep the fail-closed token/password/trusted-proxy requirement by default; if maintainers sponsor private-ingress no-auth, implement it as a named high-risk policy with explicit acknowledgement, audit warnings, docs, and focused runtime/CLI tests.

- **Keep Fail-Closed Boundary (recommended):** Preserve the current token/password/trusted-proxy requirement for reachable Gateway binds and point private deployments at the supported delegated-auth path.
- **Sponsor Guarded Private Ingress:** Allow reachable no-auth only behind a deliberately named high-risk policy with startup warnings, audit findings, documentation, and tests.
- **Reject Reachable No-Auth Core Mode:** Close the direction as not planned after documenting why OpenClaw core will not support unauthenticated reachable Gateway binds.

Yes. Source inspection gives a high-confidence reproduction path: configure `gateway.bind` as `lan` with `gateway.auth.mode` as `none`, and current runtime/CLI guards reject startup before the Gateway runs.

## Solution Assessment

No for the exact proposed shape. Auth mode `none` without validations is not the safest maintainable solution; a maintainer-approved private-ingress policy with explicit warnings and tests is the safer alternative if this direction is accepted.

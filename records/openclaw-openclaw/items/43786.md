## Summary

Keep open for maintainer security/product review: current main and v2026.6.11 still reject explicit no-auth Gateway mode on non-loopback binds, and accepting the request would move the reachable Gateway auth boundary to external infrastructure.

## What This Changes

The issue asks OpenClaw to allow `gateway.auth.mode: "none"` for trusted internal or Kubernetes deployments without the current non-loopback auth validations.

## Best Possible Solution

Keep the fail-closed token/password/trusted-proxy requirement by default; if maintainers sponsor private-ingress no-auth, implement it as a named high-risk policy with explicit acknowledgement, audit warnings, docs, and focused runtime/CLI tests.

No for the exact proposed shape. Auth mode `none` without validations is not the safest maintainable solution; a maintainer-approved private-ingress policy with explicit warnings and tests is the safer alternative if this direction is accepted.

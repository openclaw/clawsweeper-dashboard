## Summary

Keep open: current main and v2026.6.11 still reject explicit no-auth Gateway mode on non-loopback binds, and allowing it would weaken a reachable Gateway auth boundary that needs maintainer security/product approval.

## What This Changes

Request support for intentionally disabling Gateway authentication in trusted internal or private-ingress deployments without requiring a trusted-proxy workaround.

## Best Possible Solution

Keep fail-closed token/password/trusted-proxy as the default; if maintainers sponsor no-auth private ingress, implement a named high-risk policy with explicit acknowledgement, warnings, audit coverage, docs, and runtime/CLI regression tests.

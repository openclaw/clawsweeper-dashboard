## Summary

Keep open for maintainer security/product review: current main and the latest release still reject explicit no-auth Gateway mode on non-loopback binds, and accepting the request would deliberately move a reachable Gateway auth boundary to external infrastructure.

## What This Changes

Request support for intentionally disabling Gateway auth in trusted internal Docker/Kubernetes or other non-loopback deployments without requiring trusted-proxy headers.

## Best Possible Solution

Keep the fail-closed token/password/trusted-proxy requirement by default; if maintainers sponsor private-ingress no-auth, implement it as a named high-risk policy with explicit acknowledgement, audit warnings, docs, and focused runtime/CLI tests.

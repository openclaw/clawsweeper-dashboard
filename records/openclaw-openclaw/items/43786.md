## Summary

Keep open: current main and v2026.6.11 still reject explicit no-auth Gateway startup on non-loopback binds, and the requested relaxation would intentionally change a stable Gateway auth/security boundary that needs maintainer product and security approval.

## What This Changes

Request support for disabling OpenClaw Gateway auth in trusted internal, Docker, or Kubernetes deployments without requiring a trusted-proxy workaround.

## Best Possible Solution

Maintainers should either retain token/password/trusted-proxy for non-loopback binds, or sponsor a named private-ingress no-auth opt-in with explicit warnings, startup and audit behavior, docs, and regression coverage.

## Reproduction Assessment

Yes. Source and tests show the requested behavior is missing: explicit auth.mode="none" works at the auth layer but is rejected for bind: lan and other non-loopback startup paths.

## Solution Assessment

No for the exact proposed shape. Disabling auth without validations is not the safest maintainable solution; an accepted version needs an explicit private-ingress policy, warnings, audit behavior, docs, and regression coverage.

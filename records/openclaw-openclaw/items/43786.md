## Summary

Keep open: current main and v2026.6.11 still reject explicit no-auth Gateway mode on non-loopback binds, and changing that reachable auth boundary needs maintainer security/product approval rather than cleanup closure.

## What This Changes

The issue requests allowing trusted internal deployments to run the Gateway with `gateway.auth.mode: "none"` on non-loopback/private-ingress binds instead of using trusted-proxy auth.

## Best Possible Solution

Keep the fail-closed token/password/trusted-proxy requirement unless maintainers explicitly approve a named private-ingress no-auth policy with warnings, audit coverage, docs, and regression tests.

- **Keep fail-closed by default (recommended):** Preserve the current token/password/trusted-proxy requirement for reachable Gateway binds and direct trusted-network deployments to the existing delegated-auth path.
- **Sponsor private-ingress opt-in:** Allow no-auth reachable binds only behind a deliberately named high-risk policy with startup warnings, audit findings, documentation, and focused tests.
- **Close as not planned:** Reject this trust model in core after explaining the supported token/password and trusted-proxy alternatives.

Yes. Source inspection gives a high-confidence reproduction path: configure `gateway.bind="lan"` or container auto-bind with `gateway.auth.mode="none"`, and current runtime/CLI guards reject startup before the Gateway runs.

## Solution Assessment

No for the exact proposed shape. `auth mode = none without any validations` is not the safest maintainable solution; a maintainer-approved private-ingress policy with explicit warnings and tests is the safer alternative if this direction is accepted.

## Summary

Keep open: current main and the latest release still reject explicit no-auth Gateway mode on non-loopback binds, and allowing that would change a reachable Gateway auth boundary that needs maintainer security/product approval.

## What This Changes

The issue requests an explicit no-auth Gateway mode for trusted internal deployments without requiring the current trusted-proxy workaround.

## Best Possible Solution

Keep fail-closed token/password/trusted-proxy as the default; if maintainers sponsor this direction, implement a named private-ingress no-auth policy with explicit acknowledgement, warnings, audit coverage, docs, and runtime/CLI regression tests.

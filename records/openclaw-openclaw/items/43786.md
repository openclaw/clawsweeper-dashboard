## Summary

Keep open: current main and v2026.6.11 still intentionally reject explicit no-auth Gateway mode on non-loopback binds, and accepting the request would move a reachable Gateway auth boundary to external infrastructure, so it needs maintainer security/product direction.

## What This Changes

Request support for running Gateway with `gateway.auth.mode: "none"` on trusted internal or non-loopback deployments without the trusted-proxy workaround.

## Best Possible Solution

Keep token/password/trusted-proxy required for non-loopback Gateway by default; if maintainers sponsor private-ingress no-auth, add a deliberately named high-risk policy with startup warnings, audit/docs, and focused runtime/CLI tests.

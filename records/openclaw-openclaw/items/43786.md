## Summary

Keep open: current main and v2026.6.11 still reject explicit no-auth Gateway mode on non-loopback binds, and accepting the requested behavior would intentionally move a reachable Gateway auth boundary to external network controls.

## What This Changes

The issue requests allowing `gateway.auth.mode: "none"` for trusted internal non-loopback Gateway deployments without requiring the existing trusted-proxy workaround.

## Best Possible Solution

Keep the fail-closed token/password/trusted-proxy requirement by default; if maintainers sponsor private-ingress no-auth, implement it as a named high-risk policy with explicit acknowledgement, audit warnings, docs, and focused runtime/CLI tests.

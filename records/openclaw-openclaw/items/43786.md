## Summary

Keep open: current main and the latest release still reject explicit no-auth Gateway startup on non-loopback/container binds, and relaxing that boundary needs a maintainer security/product decision.

## What This Changes

Request to allow intentionally unauthenticated Gateway operation for trusted internal deployments without requiring trusted-proxy headers.

## Best Possible Solution

Maintainers should either keep the token/password/trusted-proxy requirement or explicitly design a named private-ingress no-auth opt-in with startup guards, security audit behavior, docs, and regression coverage.

Rationale: The requested behavior intentionally weakens a stable Gateway auth/security boundary, so code inspection cannot decide whether trusted external infrastructure should be accepted as the product contract.

Likely owner: steipete

Owner confidence: high

Options:

- **Guarded private-ingress opt-in (recommended):** Approve a deliberately named unsafe/private-ingress mode or flag with warnings, audit coverage, docs, and tests for both CLI and runtime startup.
- **Keep fail-closed boundary:** Continue requiring token/password or trusted-proxy auth for non-loopback binds and close this direction as not planned after maintainer confirmation.
- **Raw auth.mode none exemption:** Allow existing auth.mode="none" to bypass non-loopback startup guards without a separate acknowledgement, accepting the unauthenticated exposure risk.

## Reproduction Assessment

Yes, by source and tests rather than a live run: explicit auth.mode="none" reaches the no-auth authorization branch, but current startup guards reject it for bind="lan" and container auto-bind paths.

## Solution Assessment

No, not as proposed. "Auth mode none without any validations" is not the safest maintainable shape; if accepted, it should be a deliberate private-ingress policy with warnings, audit behavior, docs, and coverage.

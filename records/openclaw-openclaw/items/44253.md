## Summary

Keep open: current main still lacks a parent-self-only tool denial policy, and existing source/docs still make inherited subagent policy monotonic; the July 5 peer-mesh comment adds a second concrete use case, so this needs maintainer product and security design rather than cleanup closure.

## What This Changes

Add a per-agent policy such as `tools.selfDeny` so selected tools can be hidden from the requester model while remaining available to spawned subagents.

## Best Possible Solution

Design a first-class delegate-only/self-deny policy that keeps ordinary `deny` absolute, hides selected tools from the requester model, persists and audits child access, and documents native/ACP/Gateway behavior.

Options:

- **Design explicit delegate-only policy (recommended):** Adopt a first-class `selfDeny` or `delegateOnly` policy with ordinary `deny` remaining absolute, plus audit diagnostics, docs, and native/ACP/Gateway coverage before implementation.
- **Keep monotonic inheritance:** Keep the current rule that child sessions cannot regain tools removed from the requester, accepting separate agent profiles or prompt guidance as the supported pattern.
- **Fold into delegated permissions:** Defer this into a unified spawned-session permission model so parent-self-only delegation and per-spawn child narrowing share one API.

## Reproduction Assessment

Yes, at source level: strict config schemas have no self-only deny field, and child sessions still inherit the requester’s final allow/deny policy through stored `inheritedToolAllow` and `inheritedToolDeny`.

## Solution Assessment

Unclear; `selfDeny` is plausible, but the best permanent fix needs maintainer approval for syntax, deny-wins behavior, auditability, and native/ACP/Gateway semantics.

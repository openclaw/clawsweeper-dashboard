## Summary

Keep open: current main still has no `selfDeny`, `delegateOnly`, or equivalent parent-self-only tool denial policy, and the July 5 peer-mesh comment adds a concrete second use case. This remains a security/product decision because it would let child sessions receive selected command/file tools that the requester model cannot use directly.

## What This Changes

Request adds a per-agent tool policy such as `tools.selfDeny` so an agent can delegate tools to subagents without seeing or calling those tools itself.

## Best Possible Solution

Design a maintainer-approved delegate-only policy that keeps ordinary `deny` absolute, hides selected tools from the requester model surface, and explicitly audits child access across native, ACP, Gateway, docs, and tests.

Options:

- **Design explicit delegate-only policy (recommended):** Adopt a first-class `selfDeny` or `delegateOnly` policy with ordinary `deny` remaining absolute, plus audit diagnostics, docs, and native/ACP/Gateway coverage before implementation.
- **Keep monotonic inheritance:** Keep the current rule that child sessions cannot regain tools removed from the requester, accepting separate agent profiles or prompt guidance as the supported pattern.
- **Fold into delegated permissions:** Defer this into a unified spawned-session permission model so parent-self-only delegation and per-spawn child narrowing share one API.

## Reproduction Assessment

Yes, at source level. Current main has no parent-self-only deny key, and ordinary requester allow/deny policy is still captured into inherited child policy.

## Solution Assessment

Unclear. `selfDeny` is a plausible shape, but the best permanent solution needs maintainer approval for syntax, deny-wins semantics, audit behavior, and coverage across native, ACP, and Gateway paths.

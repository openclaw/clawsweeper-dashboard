## Summary

Keep open: current main and the latest release still do not implement native outbound Telegram album sending. OpenClaw now preserves multiple media URLs, but the Telegram paths deliver them sequentially without a `sendMediaGroup` branch, and an open external draft with closing syntax remains the implementation candidate for maintainers to review or supersede.

## What This Changes

The issue requests Telegram `message` tool support for native media groups/albums by accepting multiple media paths and one shared caption.

## Best Possible Solution

Implement native Telegram album delivery inside the bundled Telegram plugin for eligible 2-10 groupable media items across `message.send`, reply delivery, and outbound payload delivery, while preserving sequential fallback for single or non-groupable media and adding focused tests, docs, and live Telegram proof.

Question: Which permanent Telegram album API should OpenClaw support for this issue: album semantics on the existing `mediaUrls` send paths, the external draft's new `send-media-group`/`filePaths` action, or no native album feature for now?

Rationale: The source gap is clear, but choosing the model-facing action shape and cross-path delivery semantics changes a public channel/tool contract and should not be guessed by cleanup automation while an external draft with closing syntax is still open.

Likely owner: steipete

Owner reason: This decision crosses the shared reply-payload helper/API shape and bundled Telegram plugin boundary, both connected to steipete's issue context and recent helper history.

Owner confidence: medium

Options:

- **Port album semantics onto `mediaUrls` (recommended):** Use existing structured media payloads and add `sendMediaGroup` only as an eligible Telegram delivery optimization with sequential fallback.
- **Adopt the external draft action:** Review and reshape the external draft's `send-media-group`/`filePaths` API as the supported model-facing action surface, accepting a new action contract.
- **Defer native albums:** Keep current sequential fanout as supported behavior and document that Telegram albums are not a current OpenClaw guarantee.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Not as a bug reproduction, but yes at source level: current main preserves multiple media URLs and then sends them sequentially, with no outbound `sendMediaGroup` branch on current main or v2026.6.11.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainers choose the public API shape; the narrowest maintainable direction appears to be adding album semantics to existing structured `mediaUrls` paths rather than a parallel action unless maintainers prefer the external draft contract.

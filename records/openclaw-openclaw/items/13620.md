## Summary

Keep open: current main and the latest release still do not implement outbound Telegram album delivery through `sendMediaGroup`; they preserve multiple `mediaUrls` but send them as separate Telegram media messages. The remaining work is a maintainer API-shape decision because the open cross-repository draft with closing syntax proposes a new `send-media-group`/`filePaths` surface beside the existing `sendMessage`/`mediaUrls` path.

## What This Changes

Support Telegram album/media-group sending from the message tool so multiple related media items can be sent as one grouped Telegram album with a shared caption.

## Best Possible Solution

Add album behavior inside the bundled Telegram plugin's existing outbound send pipeline, using `sendMediaGroup` for eligible multi-media groups while preserving sequential fallbacks, documenting the chosen message-tool API, and proving it with focused tests plus live Telegram evidence.

Rationale: Current main already carries multiple media URLs through the normal send path, while the open draft introduces a parallel action and parameter name; choosing the contract affects tool prompting, docs, fallback behavior, and plugin API stability.

Owner confidence: high

Options:

- **Use existing mediaUrls (recommended):** Implement automatic `sendMediaGroup` for eligible multi-media `sendMessage`/`mediaUrls` payloads and fall back to existing sequential sends for non-groupable cases.
- **Accept explicit album action:** Sponsor a separate `send-media-group` action only if maintainers want album sending to be opt-in and separately documented from normal sends.
- **Defer API shape:** Keep the issue open and ask the draft PR author to pause until maintainers choose the permanent message-tool contract.

## Reproduction Assessment

Yes. Source inspection shows multi-media Telegram payloads are preserved as `mediaUrls`, but current outbound paths iterate and send one media item per Telegram API call rather than using an album send.

## Solution Assessment

No. The linked draft is only a plausible implementation direction because it adds a new action and `filePaths` surface beside existing `sendMessage`/`mediaUrls`; maintainers should choose the stable message-tool contract first.

## Summary

Keep open: current main and the latest release still have the same source-level asymmetry where normal timer due-job collection does not apply the completed one-shot guard, and the direct candidate fix remains open but conflicting rather than merged.

## What This Changes

The issue asks for `kind: "at"` cron jobs with `deleteAfterRun: true` to stop re-triggering after a successful one-shot run and be removed as intended.

## Best Possible Solution

Land or replace a current-base fix that makes normal timer due-job collection honor the same terminal one-shot guard as startup catch-up, with regression coverage for a successful past-due `deleteAfterRun` `at` job that remains in persisted state.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, at source level. A persisted enabled `kind: "at"` job with terminal status and a past `nextRunAtMs` is skipped on startup catch-up but remains runnable through the normal timer path because that call omits `skipAtIfAlreadyRan`.

## Solution Assessment

No, current main is not the best end state because the normal timer path still lacks the completed one-shot guard. The narrow fix should align timer collection with startup catch-up while preserving explicit retry cases where `nextRunAtMs` is intentionally after the last run.

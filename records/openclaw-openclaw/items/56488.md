## Summary

Keep open: current main and the latest release still have the normal timer path collecting due jobs without the completed one-shot guard, so a persisted terminal `at` job with a past `nextRunAtMs` remains source-reproducible. The direct same-repo PR was closed unmerged and the currently open closing candidate is still conflicting, so this is not conservative cleanup yet.

## What This Changes

The issue asks for successful one-shot cron `at` jobs with `deleteAfterRun` to be deleted after their first scheduled run instead of becoming due again.

## Best Possible Solution

Land or replace a current-base cron-only fix that applies the terminal one-shot guard to normal timer collection while preserving explicit retry cases and adding regression coverage.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, at source level. A persisted enabled `kind: "at"` job with terminal status and a past `nextRunAtMs` is skipped on startup catch-up but remains runnable through the normal timer path because that call omits `skipAtIfAlreadyRan`.

## Solution Assessment

No, current main is not the best end state because the normal timer path still lacks the completed one-shot guard. The narrow fix should align normal timer collection with startup catch-up while preserving explicit retry cases where `nextRunAtMs` is intentionally after the last run.

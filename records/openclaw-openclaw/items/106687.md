## Label Justifications

- `P2`: The report raises a plausible process-availability concern, but current main already blocks the claimed oversized state insertion and plugins are trusted in-process code.
- `impact:crash-loop`: The reported impact is Node process termination through excessive memory use, even though the described queue path is currently bounded.

## Summary

Current main already rejects each next-turn plugin injection above 32,768 UTF-16 code units before it enters session state, so the reported 500 MB queue injection does not pass the canonical enqueue boundary. Because plugins execute in-process as trusted code, a malicious plugin can allocate memory directly; changing this guard to a byte-count check would not create a security boundary.

## What This Changes

Add a hard byte-size limit for plugin-provided next-turn hook injection payloads before they enter session state.

## Best Possible Solution

Keep the existing 32 Ki-code-unit queue limit; if real accidental oversized plugin output is demonstrated, add a cheap raw-length rejection before trimming and retain the post-normalization check rather than introducing a new configurable limit.

## Reproduction Assessment

No. On current main, the canonical enqueue function rejects normalized injection text above 32,768 code units before storing it, so the described 500 MB state-queue insertion does not reproduce from source.

## Solution Assessment

Yes for the reported state-queue problem: the existing fixed guard is narrower and stricter than the suggested 1 MB byte cap. A pre-trim raw-length check would only be optional defense in depth for accidental oversized values, not protection from a malicious in-process plugin.

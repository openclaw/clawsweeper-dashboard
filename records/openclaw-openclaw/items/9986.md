## Summary

Keep open: current main still defines exhausted context overflow as a compaction/recovery failure rather than a guarded switch to a larger-context fallback, and the remaining cross-model replay policy requires maintainer intent.

## What This Changes

Trigger the configured model fallback chain when the active model exceeds its context window, selecting a candidate with sufficient context headroom.

## Best Possible Solution

After same-model compaction and oversized-tool-result recovery are exhausted, temporarily retry only a configured candidate whose resolved context window safely fits the rebuilt prompt, provided replay metadata proves no irreversible side effect occurred; log the decision and preserve the configured primary for later turns.

Options:

- **Guarded temporary fallback (recommended):** After compaction and truncation fail, retry a headroom-qualified fallback only when replay is safe, and keep the configured primary unchanged for future turns.
- **Keep compaction-only policy:** Do not cross models automatically; improve the blocked-state recovery UI and document manual model switching or session reset.
- **Adopt preflight model routing:** Select a sufficiently large model before submission based on estimated context size, accepting a broader routing-policy and observability change.

## Reproduction Assessment

Yes at source level: current documentation and the embedded-result classifier show that exhausted overflow remains a blocked recovery outcome rather than a headroom-aware fallback transition. A live oversized-session run was not performed in this read-only review.

## Solution Assessment

Yes, with safeguards: reusing the existing fallback chain after local recovery is narrower than adding a new routing configuration, but it must filter by context headroom and prohibit unsafe replay rather than treating every overflow as an ordinary retryable error.

## Risks / Open Questions

- Replaying an overflowing turn on another model after tool calls or outbound actions may duplicate side effects unless the fallback is gated by authoritative replay metadata.
- Provider or custom-model context-window metadata may be missing or inaccurate, so candidate headroom must fail safely instead of blindly cycling through smaller models.
- Persisting the successful fallback model could silently alter later session routing; making it temporary could instead repeat the same overflow on every subsequent turn.

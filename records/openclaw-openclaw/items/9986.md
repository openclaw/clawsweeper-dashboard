## Summary

Current main still treats context overflow as compaction/retry territory and explicitly excludes it from advancing the configured model fallback chain. The requested larger-context fallback remains missing and needs a maintainer decision on replay safety, candidate headroom, and session-state persistence.

## What This Changes

Request automatic selection of a configured larger-context fallback model when the active model exhausts its context window.

## Best Possible Solution

After normal compaction and oversized-tool-result recovery are exhausted, allow fallback only from a replay-safe boundary, select candidates whose effective prompt budget exceeds the measured request with reserve headroom, persist and announce the selected auto fallback consistently, and cover recovery, side effects, and return-to-primary behavior in focused tests and docs.

## Maintainer Decision

Kind: product_direction

Question: Should exhausted context overflow automatically change the conversation's active model, and if so must the retry occur only before side-effecting tool work and persist as the session's auto fallback?

Rationale: Current behavior intentionally keeps overflow inside compaction to avoid unsafe replay and smaller-window candidates; changing it affects user-visible model selection, tool side effects, and persisted session state.

Likely owner: steipete

Owner reason: The prior issue review and recent central fallback/runtime history make steipete the strongest available owner for this cross-model session contract decision.

Owner confidence: high

Options:

- **Guarded persistent fallback (recommended):** Retry only from a replay-safe boundary on a candidate with verified effective headroom, then persist it through the existing auto-fallback session contract.
- **Temporary overflow retry:** Use a larger candidate only for the failed turn without changing the stored active model, accepting additional runtime and session-state complexity.
- **Keep compaction-only:** Retain the current policy and improve terminal overflow messaging and recovery actions instead of automatically changing models.

## Reproduction Assessment

Yes at source level: current main explicitly documents and classifies context overflow as compaction/retry behavior rather than a model-fallback trigger. This read-only review did not perform a live 200k-to-256k provider run.

## Solution Assessment

Unclear until maintainers choose the replay and persistence contract. Unconditional fallback on every overflow is not the best fix because it could replay side effects or select a candidate without sufficient effective headroom.

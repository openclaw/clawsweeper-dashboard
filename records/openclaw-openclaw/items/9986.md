## Summary

Keep open: current main and v2026.6.11 still keep context overflow on the active-model compaction/truncation path and then return or rethrow context overflow instead of selecting a configured larger-context fallback. The direct implementation PR closed unmerged, so the remaining work is a maintainer product-policy decision.

## What This Changes

Request automatic model fallback to a configured larger-context model when the active model exceeds its context limit.

## Best Possible Solution

Maintainers should either document overflow as compaction-only behavior, or implement guarded larger-context fallback only after compaction and truncation are exhausted, with candidate context-window filtering, replay-safety gates, fallback logs, docs, and regression coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw allow model fallback after context overflow recovery is exhausted, and under what replay-safety and context-window constraints?

Rationale: Both choices are product-valid: current docs and code intentionally keep overflow inside compaction/retry, while this issue reports a real long-session recovery gap that crosses provider routing, replay safety, and context-window semantics.

Likely owner: steipete

Owner reason: Peter Steinberger has recent current-main history on the affected fallback/classifier paths and previously framed this issue as a policy choice.

Owner confidence: high

Options:

- **Implement guarded larger-window fallback (recommended):** Allow fallback only after compaction and truncation fail, only to candidates with known sufficient effective context, and preserve replay-safety and delivery guards.
- **Keep compaction-only behavior:** Document that context overflow is not a model-fallback trigger and improve user-facing recovery guidance instead.
- **Defer to narrower UX work:** Prioritize diagnostics and model-switch recovery issues while leaving larger-context fallback as an explicit future policy decision.

## Reproduction Assessment

Yes, by source inspection. Current main rethrows escaped context-overflow errors and returns blocked embedded context_overflow results instead of trying a configured larger fallback model; I did not run a live provider repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the policy. A guarded post-recovery larger-window fallback is plausible, but unconditional fallback is unsafe without context-window filtering, replay-safety gates, and docs alignment.

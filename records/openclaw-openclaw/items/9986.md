## Summary

Keep open: current main and v2026.6.11 still intentionally keep context overflow inside same-model compaction and recovery, then return or rethrow overflow instead of trying a configured larger-context fallback. The direct implementation attempt closed unmerged, and the remaining change needs maintainer direction on replay safety, trustworthy context-window metadata, and session fallback persistence.

## What This Changes

Request automatic selection of a configured larger-context fallback model after the active model exhausts context recovery.

## Best Possible Solution

After same-model compaction and oversized-result recovery are exhausted, emit a replay-safe overflow outcome that tries only configured candidates with verified sufficient context headroom; otherwise preserve the actionable blocked result.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should exhausted context overflow become eligible for configured model fallback when a candidate has a larger verified context window?

Rationale: Current source and documentation deliberately make overflow compaction-only, so changing it requires explicit policy for replay safety, context-window metadata, and session fallback persistence.

Likely owner: steipete

Owner reason: He has recent merged history across failover classification and embedded overflow handling and previously reviewed this specific policy boundary.

Owner confidence: high

Options:

- **Guarded larger-model fallback (recommended):** Retry only after same-model recovery is exhausted, no delivery or side effects committed, and a configured candidate has verified headroom.
- **Keep compaction-only:** Preserve the blocked overflow result and document manual model or session recovery as the intended contract.

## Reproduction Assessment

Yes from source: escaped overflow exceptions are immediately rethrown by the fallback runner, and exhausted compaction tests end with a terminal context_overflow result rather than another model attempt. This read-only review did not run a live provider boundary scenario.

## Solution Assessment

No existing path solves the request, and unconditional fallback at the first overflow would not be the safest fix. The narrowest maintainable direction is a guarded extension of the canonical fallback and embedded-result boundary after existing recovery is exhausted.

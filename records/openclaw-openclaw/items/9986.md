## Summary

Keep open: current main still ends exhausted context-overflow recovery as a blocked session result rather than selecting a configured larger-context model, and the required cross-model replay and session-persistence semantics remain an explicit product decision.

## What This Changes

Request automatic selection of a configured larger-context fallback model after the primary model exhausts context-overflow recovery.

## Best Possible Solution

After ordinary compaction and oversized-tool-result recovery are exhausted, retry only on configured candidates proven to have sufficient effective context, block unsafe side-effect replay, and apply a documented temporary-or-persisted session model policy with observable fallback logging.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should exhausted context overflow automatically replay the turn on a larger configured fallback model, and should that switch be temporary for the recovery attempt or persisted for the session?

Rationale: Current main deliberately treats overflow as compaction and session recovery, while cross-model replay changes side-effect safety, context-headroom calculation, and persisted model semantics that cannot be chosen safely from implementation evidence alone.

Likely owner: steipete

Owner reason: They have recent history across both decision surfaces and authored the latest substantive review of this issue.

Owner confidence: high

Options:

- **Guarded temporary fallback (recommended):** After compaction and truncation fail, retry once on a sufficiently large configured fallback without changing the persisted session model, and prohibit replay after delivery or side effects.
- **Persist the larger model:** Switch the session to the first sufficiently large fallback after overflow recovery fails so later turns remain on that model.
- **Keep compaction-only recovery:** Document overflow as ineligible for model fallback and improve the blocked-session recovery experience instead.

## Reproduction Assessment

Yes at source level: current main compacts and retries the active model, then returns blocked overflow recovery, while the embedded result classifier has no overflow-to-fallback branch. This read-only review did not perform a live 200K-primary to 256K-fallback provider run.

## Solution Assessment

Not yet as written: automatic fallback is plausible, but the best implementation must run only after existing recovery, filter by effective context headroom, prevent unsafe turn replay, and define whether the model switch persists.

## Summary

Keep open: current main and the latest release still treat context overflow as active-model compaction/truncation recovery followed by a blocked overflow result or rethrow, not as a trigger to select a configured larger-context fallback model. The direct implementation PR was closed unmerged, so the remaining work is a maintainer product-policy decision.

## What This Changes

The issue requests automatic routing to a configured larger-context fallback model when the primary model exceeds its context limit.

## Best Possible Solution

Maintainers should either document overflow as compaction-only, or implement guarded larger-context fallback only after compaction and truncation recovery are exhausted, with context-window filtering, replay-safety gates, fallback logs, docs, and regression coverage.

- **Implement Guarded Larger-Window Fallback (recommended):** Allow fallback only after compaction and truncation fail, only to candidates with known sufficient effective context, while preserving replay-safety and delivery guards.
- **Keep Compaction-Only Behavior:** Document that context overflow is not a model-fallback trigger and improve user-facing recovery guidance instead.
- **Defer To Narrower UX Work:** Prioritize diagnostics and model-switch recovery items while leaving larger-context fallback as a future policy decision.

Yes, source inspection gives a high-confidence reproduction path: current main rethrows escaped context-overflow errors and returns blocked embedded context_overflow results instead of trying a larger configured fallback model. I did not run a live provider repro in this read-only sweep.

## Solution Assessment

Unclear until maintainers choose the policy. A guarded post-recovery larger-window fallback is plausible, but unconditional fallback is not the best solution without context-window filtering, replay-safety gates, and docs alignment.

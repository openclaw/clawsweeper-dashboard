## Summary

Keep open: current main still has adjacent tool and transcript hooks, but no generic durable-state pre-write hook for memory, file, cron, config, or preference writes; this remains the canonical Plugin SDK and security-boundary design item.

## What This Changes

Request an additive `before_persistence_write` Plugin SDK hook before durable state writes such as memory, file, cron, config, and preference persistence.

## Best Possible Solution

Settle one public durable-write policy contract with minimal payloads, explicit block/mutate/failure semantics, docs, and representative writer coverage.

## Maintainer Decision

Kind: security_boundary

Question: Should OpenClaw add a dedicated `before_persistence_write` hook for durable state changes, or represent durable-write policy through enriched `before_tool_call` and provenance contracts instead?

Rationale: This choice defines a public Plugin SDK security boundary over persisted user and agent state, including what plugins can see, whether writes can be blocked or mutated, and how failures affect durable state.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Design a dedicated durable-write hook (recommended):** Add a narrow additive hook with redacted targets, explicit block or mutation rules, bounded failure policy, docs, and coverage across representative writer paths.
- **Fold durable context into existing hooks:** Extend `before_tool_call` and related provenance APIs instead of adding a hook family, reducing hook count but requiring broader taxonomy work first.
- **Defer to persistent-state provenance design:** Keep this issue open as a dependency of the broader provenance/read-time trust model before implementing a write-only seam.

## Reproduction Assessment

Yes. Source inspection on current main shows adjacent hooks but no `before_persistence_write` or equivalent durable-state pre-write hook across representative file, cron, config, and transcript paths.

## Solution Assessment

Unclear pending maintainer design. A dedicated hook is plausible and vision-aligned, but the best shape depends on taxonomy, redaction, block versus mutate semantics, failure policy, and relation to provenance/read hooks.

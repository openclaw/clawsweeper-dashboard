## Summary

Keep open: current main still has adjacent tool, transcript, message-write, and cron lifecycle hooks, but no generic pre-write hook for durable state changes; the remaining work is a public Plugin SDK security-boundary design decision.

## What This Changes

Request to add a `before_persistence_write` plugin hook for memory, file, cron, config, and preference writes that cross session boundaries.

## Best Possible Solution

Settle one minimal public durable-write policy contract with explicit payload redaction, block versus mutate semantics, failure behavior, docs, and representative coverage across the writer paths maintainers choose to support.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a dedicated `before_persistence_write` hook for durable state changes, or represent durable-write policy through enriched existing hook and provenance contracts instead?

Rationale: This choice defines a public Plugin SDK security boundary over persisted user and agent state, including what plugins can see, whether writes can be blocked or modified, and how failures affect durable state.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Design a dedicated durable-write hook (recommended):** Add a narrow additive hook with redacted targets, explicit block or mutation rules, bounded failure policy, docs, and coverage across representative writer paths.
- **Extend existing hook context:** Fold durable-write classification into `before_tool_call` and related provenance APIs, reducing hook count but requiring broader taxonomy and coverage work first.
- **Defer to provenance design:** Keep this as a dependency of the broader persistent-state provenance/read-time trust model before implementing a write-only seam.

## Reproduction Assessment

Yes. Source inspection on current main shows adjacent hook surfaces but no `before_persistence_write` or equivalent durable-state pre-write hook in hook types, docs, or runner dispatch.

## Solution Assessment

Unclear pending maintainer design. A dedicated hook is plausible and vision-aligned, but the best shape depends on taxonomy, redaction, block versus mutate semantics, failure policy, and relation to provenance/read hooks.

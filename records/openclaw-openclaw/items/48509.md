## Summary

Keep open: current main still has adjacent tool, transcript, message, session, and cron hooks, but no dedicated pre-write hook for durable state changes across memory, files, cron, config, or preferences. This remains a coherent Plugin SDK and security-boundary design request, not a cleanup-close candidate.

## What This Changes

The issue requests a new `before_persistence_write` Plugin SDK hook for blocking or auditing durable state writes before they cross session boundaries.

## Best Possible Solution

Define one additive durable-write Plugin SDK contract with minimal redacted payloads, explicit block/mutate semantics, ordering after `before_tool_call`, bounded failure behavior, and focused writer coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a dedicated `before_persistence_write` Plugin SDK hook for durable state writes, or should this capability be modeled through existing tool/policy/provenance hooks?

Rationale: This is a public Plugin SDK enforcement boundary over persisted user and agent state, so automation cannot safely choose the taxonomy, payload exposure, block/mutate semantics, or failure policy without maintainer security and product intent.

Likely owner: jalehman

Owner reason: They are the clearest maintainer-routing signal from the generic host-hook foundation history and are better positioned than feature contributors to decide a public Plugin SDK/security boundary.

Owner confidence: medium

Options:

- **Design a dedicated hook (recommended):** Add a narrowly scoped `before_persistence_write` contract with redacted payloads, explicit write-target taxonomy, bounded execution, and tests for representative memory/file/cron/config writers.
- **Extend existing tool hooks:** Keep a single tool-policy surface by enriching `before_tool_call` with durable-write metadata, accepting that non-tool persistence writes may still need separate coverage.
- **Defer into provenance work:** Keep this thread open but require the broader persistent-state provenance design to decide write and read semantics together before implementation.

## Reproduction Assessment

Yes, at source level: current hook types, runner dispatch, docs, and representative tool-hook construction do not expose `before_persistence_write` or equivalent durable-write context.

## Solution Assessment

Unclear pending maintainer design: a dedicated hook is plausible and aligned with plugin extensibility, but maintainers still need to decide taxonomy, block versus mutate semantics, redaction, failure policy, and relation to provenance/read hooks.

## Summary

Keep open: current main and the latest release still use the x11vnc/Xvfb noVNC stack, upstream noVNC/x11vnc behavior supports the UTF-8 clipboard corruption report, and the only linked TigerVNC fix PR is closed unmerged after security-default concerns.

## What This Changes

The issue asks OpenClaw to stop corrupting non-Latin-1 text pasted through the sandbox-browser noVNC clipboard, likely by replacing x11vnc with a VNC server that supports Extended Clipboard.

## Best Possible Solution

Keep this canonical issue open until a maintainer-approved sandbox-browser VNC replacement preserves existing observer auth/binding contracts and proves CJK/Cyrillic paste in a real Docker/noVNC flow.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 still run x11vnc behind noVNC, while upstream noVNC falls back to a Latin-1/Uint8 path when Extended Clipboard is unavailable. I did not run the live Docker/noVNC user flow in this read-only review.

## Solution Assessment

Unclear as a final implementation: replacing x11vnc with TigerVNC is the plausible dependency-layer fix, but the previous candidate shows the best solution must also preserve existing password, token, localhost binding, and upgrade contracts.

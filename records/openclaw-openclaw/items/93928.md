## Summary

Keep open: current main fixed the Feishu Drive `list` continuation half via https://github.com/openclaw/openclaw/pull/101572, but `feishu_drive info` still performs one `drive.file.list` call, has no folder/cursor schema, and can still falsely miss files outside that first page.

## What This Changes

The issue requests pagination support for Feishu Drive `list` and `info` so files beyond the first Lark API page remain accessible.

## Best Possible Solution

Keep this issue open for a Feishu-plugin-local `info` fix that uses a folder-aware lookup contract, follows `has_more` and `next_page_token` within that scope, and preserves the current manual list continuation behavior.

Options:

- **Add scoped info pagination (recommended):** Expose or accept an explicit folder-scoped lookup for `info`, paginate only within that concrete folder, and require focused regression plus Feishu or SDK-boundary proof.
- **Keep info root-only:** Document `info` as root-only and require agents to use `list` continuation to browse shared folders before selecting files.
- **Use direct metadata lookup:** If Lark provides a reliable bot-compatible metadata endpoint by token and type, switch `info` away from folder enumeration instead of adding folder pagination.

## Reproduction Assessment

Yes, source-reproducible: current main's `info` action dispatches `getFileInfo(client, p.file_token)`, and `getFileInfo` calls `drive.file.list` once before throwing `File not found`. I did not run a live Feishu tenant test.

## Solution Assessment

Unclear until the maintainer chooses the remaining `info` contract; the merged `list` fix is the right narrow shape, but `info` should be folder-scoped or direct-token based rather than automatic root draining.

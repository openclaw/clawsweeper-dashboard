## Summary

Keep open: current main and the latest release do not implement the dashboard binding substrate or the requested stream, command, and computed binding kinds. This remains an active feature under https://github.com/openclaw/openclaw/issues/101136, and the command-binding part crosses a command-execution security boundary that needs maintainer direction before implementation.

## What This Changes

The issue requests new dashboard data-binding sources for push streams, allowlisted periodic command output, and computed values derived from other bindings.

## Best Possible Solution

Settle the Wave 1 dashboard substrate first, then design stream and computed bindings separately from any command-execution binding unless maintainers approve the command security model.

Rationale: Automation cannot choose the product and security boundary for a feature that turns dashboard data resolution into recurring command execution, especially before the dashboard substrate is accepted.

Owner confidence: high

Options:

- **Split Command Security Design (recommended):** Proceed with stream and computed binding design only after the substrate lands, and require a separate maintainer-approved proposal for command execution.
- **Approve All Binding Kinds Together:** Accept stream, computed, and command bindings as one roadmap feature with full allowlist, permission, and proof requirements.
- **Defer Apps-Layer Bindings:** Keep the issue open but pause implementation until maintainers decide whether this dashboard apps layer belongs in bundled OpenClaw.

## Reproduction Assessment

Not applicable; this is a new dashboard data-binding capability request rather than broken existing behavior. Source inspection confirms the requested binding kinds are absent from current main and from the open dashboard substrate candidates.

## Solution Assessment

No; the direction is plausible, but combining stream, command, and computed bindings is not the safest first implementation path. The maintainable path is to land or reject the dashboard substrate first and split command execution behind a separate reviewed allowlist/security design.

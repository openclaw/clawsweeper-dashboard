## Label Justifications

- `P2`: This fixes incorrect memory-cache reuse for configured custom embedding endpoints, with a bounded blast radius to affected Mistral and DeepInfra users.
- `merge-risk: 🚨 compatibility`: Existing custom-endpoint or routing-header setups intentionally receive a different cache identity after upgrade.
- `merge-risk: 🚨 session-state`: The cache identity feeds persisted memory index metadata, so endpoint changes alter which stored embedding rows are selected or rebuilt.

## Summary

This PR remains necessary: it closes the endpoint-identity gap left after the analogous Ollama fix, and its updated body now includes an after-fix production CLI/SQLite transcript showing a changed provider key, a second cache row, and a request to the newly selected endpoint. The implementation appears correct, but its compatibility-sensitive cache rebuild behavior should be confirmed against the current merge result before landing.

## What This Changes

The branch makes Mistral and DeepInfra memory embeddings distinguish custom endpoints and non-secret routing headers in their cache identity while preserving the existing identity for shipped default endpoints.

## System Context

Memory embedding adapters obtain a resolved remote client from provider configuration, then supply cache identity data to Memory Core's index and embedding cache. That identity determines whether a changed endpoint reuses old vectors or triggers a separate index/cache entry before memory search consumes the embeddings.

## Architecture Diagram

flowchart LR

  B --> C[Mistral or DeepInfra adapter]
  C --> D[Endpoint-aware cache identity]
  D --> E[Memory index metadata]
  D --> F[Embedding cache]
  E --> G[Memory search results]
  F --> G

## Best Possible Solution

Land the shared endpoint-identity rule after refreshing the branch against current main and confirming that default Mistral and DeepInfra installations retain their existing cache key while custom endpoint/header users rebuild through the normal memory indexing flow.

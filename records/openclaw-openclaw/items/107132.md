## What This Changes

The PR makes the Gateway delegate warmed plugin HTTP requests directly to the already-loaded plugin handler, avoiding one redundant active-route-registry lookup per request while retaining lazy initialization.

## System Context

Gateway HTTP dispatch routes incoming requests to built-in Gateway handlers and then to plugin HTTP routes. The first plugin request lazily loads the plugin handler only when routes exist; afterward, the loaded handler continues to read the active route registry so runtime route changes take effect on the next request.

## Architecture Diagram

flowchart LR
  A[Incoming HTTP request] --> B[Gateway dispatch]
  B --> C{Plugin handler loaded?}
  C -->|No| D[Check active plugin routes]
  D -->|Routes exist| E[Load plugin HTTP handler]
  D -->|No routes| H[Continue Gateway routing]
  C -->|Yes| E
  E --> F[Read active route registry]
  F --> G[Plugin route response]

## Best Possible Solution

Merge the direct warmed-handler delegation while retaining the cold-path empty-registry guard and the loaded handler’s per-request active-registry resolution.

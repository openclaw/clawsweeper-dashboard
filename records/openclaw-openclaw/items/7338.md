## Summary

Current main still lacks a general, opt-in attestation contract for arbitrary outbound requests, while recent provider-attribution work remains limited to provider transports. Keep this protected issue open because a client-generated header or JWT cannot itself prove that a human did not control the client, and the discussion still requires explicit product and security direction.

## What This Changes

Add opt-in, domain-scoped identity or cryptographic attestation metadata to external requests made by OpenClaw agents.

## Best Possible Solution

Define a narrow identity contract that distinguishes self-identification from verifiable platform attestation, uses an external or hardware-backed trust anchor whenever proof is claimed, scopes disclosure to explicit audiences, and exposes only the smallest generic plugin or core seam needed for approved request paths without claiming that OpenClaw can prove autonomous rather than human-controlled use.

Options:

- **Scoped self-identification (recommended):** Expose opt-in, audience-scoped metadata through a generic plugin or runtime seam while explicitly documenting that it is not proof that a request was autonomous or human-free.
- **Platform-backed attestation:** Design a verifier protocol around a hardware, hosted, or third-party trust anchor with key lifecycle, replay protection, privacy, and covered-path guarantees before adding headers.
- **No general core contract:** Keep provider-specific attribution only and require agent-only services to use their own authenticated plugin, API-key, OAuth, wallet, or trusted-execution integration.

## Risks / Open Questions

- A self-signed header or JWT could create false assurance because the same operator or human caller controlling OpenClaw can usually reproduce the credential and request.
- Stable agent identifiers, skill names, versions, audiences, or keys can become cross-service tracking signals or leak deployment topology unless disclosure and scope are narrowly defined.
- A shared signing authority introduces key generation, storage, rotation, revocation, verifier discovery, replay prevention, and compromise-recovery obligations.
- The requested scope is ambiguous across built-in web fetch, provider transports, browser automation, exec-launched clients, plugin tools, MCP, and skill-owned code, so partial injection would create inconsistent security semantics.

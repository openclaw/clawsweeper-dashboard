## Summary

Keep open. Current main and v2026.6.11 provide ordinary web-fetch headers and provider-specific attribution, but not general opt-in, domain-scoped external-request attestation; this canonical tracker still needs an explicit product and security decision about what identity is asserted and where.

## What This Changes

Add optional, domain-scoped metadata or cryptographic attestation to OpenClaw-originated external HTTP requests.

## Best Possible Solution

Define a truthful, audience-bound installation or agent-profile assertion with explicit non-goals and complete key-lifecycle, privacy, replay, redirect, and request-scope rules, or keep service-specific authentication inside plugin-owned tools.

- **Define truthful signed identity (recommended):** Specify an audience-bound installation or agent-profile assertion with explicit limitations and complete security semantics before implementation.
- **Use plugin-specific authentication:** Keep service credentials and request signing in plugin-owned tools unless a concrete missing generic plugin API is demonstrated.
- **Decline general attestation:** Retain provider attribution and document that OpenClaw cannot prove autonomous-agent initiation.

## Reproduction Assessment

Not applicable: this issue requests a new security and identity capability rather than reporting broken documented behavior. Current-main source inspection confirms the requested general attestation surface is absent.

## Solution Assessment

No, not as currently proposed: static headers are spoofable, and a signed token should attest a precise installation or profile rather than claim to distinguish human from agent initiation. A plugin-owned service integration is safer unless maintainers approve a generic core contract.

## Summary

Keep this protected issue open. Current main provides provider-specific attribution but no general attestation contract, and the proposed guarantee requires explicit product and security direction before implementation.

## What This Changes

The issue requests opt-in, domain-scoped static or cryptographic agent-attestation metadata for external HTTP requests, optionally declared by skills.

## Best Possible Solution

Separate descriptive attribution from verifiable attestation: expose a generic plugin integration only after defining the guarantee, and require any strong identity claim to be signed at a trusted egress, hardware, or managed-service boundary outside the user-controlled agent process.

Rationale: These choices have materially different security meaning, privacy impact, key ownership, enforceability, and core-versus-plugin architecture, so repository inspection cannot safely choose the policy.

Likely owner: steipete

Owner confidence: high

Options:

- **Design verified egress identity (recommended):** Specify a protected signing authority, audience and replay rules, key lifecycle, privacy limits, and enforceable outbound-path coverage before adding a generic integration seam.
- **Add attribution only:** Permit opt-in domain-scoped headers while documenting that they identify an OpenClaw client configuration and do not prove autonomous-agent origin.
- **Keep trust service-specific:** Use API credentials, OAuth, mTLS, gateways, or plugin-owned handshakes instead of defining a universal OpenClaw attestation claim.

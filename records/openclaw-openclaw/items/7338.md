## Summary

Keep open. Current main and v2026.6.11 still lack opt-in, domain-scoped agent-origin attestation for arbitrary external HTTP requests; related provider-header, skill-trust, and native identity work is narrower or adjacent and does not close the product/security design question.

## What This Changes

The issue requests optional OpenClaw agent attestation headers or signed tokens for outbound HTTP requests, with domain allowlists, skill metadata, and privacy-preserving configuration.

## Best Possible Solution

Keep this open for maintainer product/security design, then implement a privacy-preserving opt-in attestation contract with explicit outbound scope, domain allowlists, signed/static semantics, non-leakage tests, docs, and any required plugin/config API changes.

## Reproduction Assessment

Not applicable: this is a feature request rather than a broken existing behavior report. Source and release inspection show the requested attestation surface is absent in current main and v2026.6.11.

## Solution Assessment

Unclear: adding headers directly is not yet proven to be the best solution because the trust model, signing authority, privacy defaults, and exact outbound paths are unsettled. The safer path is design approval first, then a narrow opt-in implementation with allowlist and non-leakage proof.

## Summary

Keep open: current main and v2026.6.11 still lack a general opt-in, domain-scoped agent attestation mechanism for arbitrary outbound HTTP requests. The adjacent provider-attribution and plugin-hook work is useful context, but it does not provide signed/static agent-origin attestations, skill-declared audiences, or allowlisted header injection.

## What This Changes

The issue requests optional OpenClaw agent attestation headers or signed attestations for outbound external HTTP requests, with domain allowlists and possible skill metadata controls.

## Best Possible Solution

Define the attestation trust model and outbound scope first, then add an opt-in, domain-scoped API/config surface with privacy-preserving defaults, clear static-versus-cryptographic semantics, docs, and tests for allowlisted injection plus non-leakage.

## Reproduction Assessment

Yes, as a source-level feature gap: current main and v2026.6.11 lack opt-in, domain-scoped OpenClaw agent attestation for external HTTP requests, skill metadata, or accepted config. No runtime failure reproduction is applicable because this is a new capability request.

## Solution Assessment

Unclear as a final implementation path. The tracker is well motivated, but maintainers still need to choose the trust model, signing authority, privacy defaults, outbound surfaces, and whether this belongs in core config, plugin APIs, skill metadata, or a combination.

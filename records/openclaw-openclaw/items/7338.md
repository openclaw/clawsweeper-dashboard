## Summary

Keep open for an explicit product and security decision. Current main offers ordinary web-fetch headers and provider-specific request attribution, but no general, domain-scoped attestation contract; more importantly, a client-generated header or JWT cannot by itself prove that a human did not control the client.

## What This Changes

Requests optional, domain-scoped headers or cryptographic attestations that let external services identify requests as originating from an OpenClaw agent.

## Best Possible Solution

Define the attainable identity claim first, then prefer service-issued, audience-bound credentials in an owner plugin; add a minimal core or plugin-SDK seam only if existing request and SecretRef APIs cannot support that model safely.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What claim should OpenClaw support and which outbound paths may emit it: service-credential possession, a locally generated installation identity, or centrally or hardware-attested runtime identity?

Rationale: These choices provide materially different guarantees, privacy properties, key-distribution requirements, and core-versus-plugin boundaries; implementation cannot safely choose among them.

Likely owner: steipete

Owner reason: Peter already framed this as a product/security decision and owns the most relevant adjacent attribution history.

Owner confidence: high

Options:

- **Service-specific credential proof (recommended):** Let each service or plugin issue audience-bound credentials and signed requests, without claiming that credential possession proves the absence of human control.
- **Local installation identity:** Add an opt-in locally generated key and domain allowlist, explicitly documenting that it identifies a key-holding installation rather than an autonomous agent.
- **Central or hardware attestation:** Defer implementation until OpenClaw has an authority, provisioning, revocation, hardware-root, replay, and privacy model capable of supporting the stronger claim.

## Reproduction Assessment

Not applicable: this issue requests a new identity and attestation capability rather than reporting broken behavior under an existing contract. Current source and docs confirm that the capability is absent.

## Solution Assessment

No, not as currently proposed: static headers are trivially impersonable, while a shared OpenClaw signing identity or self-issued JWT does not prove autonomous origin. The narrowest safe starting point is an audience-bound, service-issued credential flow owned by the relevant plugin or integration.

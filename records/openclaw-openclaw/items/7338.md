## Summary

Keep open. The requested capability remains a distinct product and security design question: ordinary request headers and provider-specific attribution do not establish general, domain-scoped agent attestation, and the discussion explicitly preserves this issue as the canonical tracker for defining that trust model.

## What This Changes

Add opt-in, domain-scoped identity or cryptographic attestation to external HTTP requests made by OpenClaw agents.

## Best Possible Solution

Define a threat model and issuer/root-of-trust contract first, then implement the narrowest opt-in capability at the correct owner boundary with audience-bound short-lived credentials, strict destination enforcement, privacy-preserving identifiers, redirect non-leakage, rotation/revocation, documentation, and fresh-install plus upgrade tests.

Options:

- **Design platform attestation (recommended):** Define a core security protocol with an issuer or hardware-backed trust model, audience binding, rotation, revocation, and explicit supported request paths before implementation.
- **Expose a generic plugin seam:** Provide only a narrowly reviewed outbound-request signing or credential-injection API so service-specific plugins own identity semantics and keys.
- **Decline agent-personhood claims:** Document that OpenClaw cannot prove a human is absent and direct services to standard service credentials or OAuth-style client authentication instead.

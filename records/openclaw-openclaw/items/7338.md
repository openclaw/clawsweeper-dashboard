## Summary

Keep open. Current main still has no general, opt-in agent-attestation contract, and the existing provider attribution is deliberately endpoint-specific rather than proof that an arbitrary external request came from an autonomous agent; the recent discussion also preserves this as the product/security design tracker.

## What This Changes

Add opt-in, domain-scoped identity or cryptographic attestation metadata to outbound requests made by OpenClaw agents.

## Best Possible Solution

Define a maintainer-approved threat model that states the attainable claim, then use a standards-based, short-lived, audience-bound proof behind a generic plugin/request-policy seam with explicit domain and redirect controls, per-installation keys, no stable agent identifier by default, and tests proving both injection and non-leakage.

Options:

- **Approve a narrow attestation RFC (recommended):** Define an audience-bound proof of possession for a configured OpenClaw installation, reuse an established request-signing standard, and add only the generic plugin/request seam required by approved paths.
- **Keep attestation service-specific:** Treat each external service as a plugin-owned authentication integration using its own API keys, OAuth, DPoP, or message-signature contract without a universal OpenClaw identity claim.
- **Decline agent-origin claims:** Document that an open local client cannot reliably distinguish autonomous agent intent from a human controlling the same installation and do not add a general attestation surface.

## Risks / Open Questions

- A locally generated signature can prove possession of a configured installation key, but it cannot by itself prove that a request was autonomously chosen by an AI rather than initiated or replayed by a human controlling that installation.
- The signing authority, key enrollment and rotation, verifier trust distribution, revocation, nonce or replay handling, issuer and audience semantics, and behavior after key compromise are undefined.
- Stable agent or installation identifiers could enable cross-service tracking, while applying headers across web_fetch, plugin tools, skills, browser automation, exec-based clients, and provider transports could leak identity inconsistently across redirects or unapproved domains.

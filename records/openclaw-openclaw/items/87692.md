Rationale: The remaining behavior is not purely mechanical: retrying can recover message delivery, but current replay metadata shows fallback can repeat side effects if tools or outbound actions already happened.

Owner confidence: medium

Options:

- **Prove first, fallback narrowly (recommended):** Run live current-main Copilot cron proof and allow fallback only when no tool, message, spawn, or cron side-effect evidence exists.
- **Fallback on no-output aborts:** Classify aborted or no-output Copilot results as fallback-worthy whenever a fallback model is configured, accepting the replay risk.
- **Do not expand fallback:** Keep current-main cron error surfacing and the 60-second idle cap without adding a new aborted-result fallback path.

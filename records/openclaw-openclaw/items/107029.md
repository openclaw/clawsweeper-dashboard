## Summary

Keep this issue open for a maintainer product and security-boundary decision. Current main already has SQLite-backed plugin state and agent cache primitives, but the public Plugin SDK does not establish the proposed third-party, agent-scoped cache contract; the remaining question is API ownership and isolation rather than a demonstrated missing table. Likely related people: steipete for recent plugin-state storage work and vincentkoc for shared state-migration work, both with medium confidence.

## What This Changes

Add an agent-scoped, TTL-capable SQLite cache facade to the Plugin SDK and discourage in-memory inter-turn plugin state.

## Best Possible Solution

Inventory concrete plugin use cases first, then define one canonical Plugin SDK storage contract with explicit plugin and agent scoping, trust, quotas, TTL, cleanup, migration, and compatibility semantics; implement it through the existing Kysely-backed databases rather than adding an underspecified parallel cache facade.

## Risks / Open Questions

- A generic third-party cache API needs an explicit security model for plugin identity, cross-plugin isolation, agent access, sensitive values, quotas, deletion, and uninstall cleanup.
- Agent-scoped storage may be wrong for plugin-global or account-scoped data, while the existing shared plugin store may be wrong for agent-private data; choosing one implicit scope could create a lasting compatibility problem.
- No concrete external plugin or lost-state reproduction demonstrates which data needs persistence, whether it is disposable cache or user state, or whether a new SDK surface is preferable to existing plugin-owned storage.
- Adding context.cache alongside existing plugin state mechanisms could create parallel sources of truth and ambiguous migration responsibilities.

## Summary

Keep this issue open for maintainer product and security-boundary review. Current main already provides SQLite-backed plugin state, but the request introduces a distinct agent-scoped public SDK contract whose ownership and isolation semantics remain undecided.

## What This Changes

Add a Plugin SDK cache facade backed by agent-local SQLite storage and discourage process-memory retention across turns.

## Best Possible Solution

Extend the existing versioned plugin-state abstraction with an explicit, host-enforced scope contract—global or agent-local—then reuse the canonical SQLite stores with documented TTL, cleanup, migration, quota, and sensitive-data rules.

Question: Should third-party plugin state remain globally plugin-scoped, become agent-scoped for cache use, or support an explicit choice between those scopes?

Rationale: Current main deliberately places arbitrary plugin state in the shared database while reserving agent databases for agent-owned data; changing that boundary creates a permanent Plugin SDK and isolation contract that automation cannot choose safely.

Likely owner: steipete

Owner confidence: medium

Options:

- **Add explicit scopes (recommended):** Extend the existing plugin-state API with explicit global and agent scopes and define lifecycle, isolation, quota, backup, and migration behavior for both.
- **Keep global namespaces:** Retain shared plugin-state storage and require plugins to include agent identity in keys when agent separation is needed.
- **Require agent-local caches:** Introduce an agent-only cache facade and prohibit cross-agent sharing through that API.

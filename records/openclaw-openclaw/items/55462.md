## Summary

Keep open: current main and v2026.6.11 still route generic Telegram callback clicks as agent-visible `callback_data` text while using the opaque callback query id as the inbound `MessageSid`, so generic agent turns still lack the source chat/message id needed to edit the clicked inline-button message. Plugin interactive callbacks already receive source-message metadata, but the ordinary agent callback path remains unresolved and the same-repo implementation attempt is closed unmerged.

## What This Changes

The issue requests that Telegram inline-button callback turns expose the originating Telegram message id, and likely chat id, so agents can call `editMessage` on the clicked message.

## Best Possible Solution

Add a Telegram-owned callback metadata/current-message contract that preserves `callback.id` for answering and dedupe while exposing the source chat/message ids to generic agent turns and message actions, with focused tests and live Telegram proof.

## Reproduction Assessment

Yes, source-level: a Telegram `callback_query` with distinct `callback.id` and `callback.message.message_id` reaches current callback paths that pass `callback.id` into `MessageSid`, while the generic agent payload only contains `callback_data`. I did not run a live Telegram scenario in this read-only review.

## Solution Assessment

No final solution has landed. The requested direction is useful, but the best fix is a deliberate callback source-message metadata/current-message contract rather than a one-line id swap that could break dedupe or callback answering.

- **[P1] Preserve plugin ids as lifecycle lookup keys:** `src/plugins/installs.ts:58`
  - body: This is still the earlier lifecycle blocker: writing agent-scoped installs under `pluginId:agentId` makes the map key stop being the runtime plugin id, but current inspect/update/index callers still look up records by `installRecords[plugin.id]` or iterate keys as plugin ids.   - body: The branch adds `plugins install --agent` but leaves `plugins uninstall` without an `--agent` option and never passes an agent id into `runPluginUninstallCommand`. Users can create `pluginId:agentId` records through the new install path, but the public CLI cannot target those records for removal.
  - confidence: 0.94
- **[P1] Keep shared plugin config during scoped uninstall:** `src/plugins/uninstall.ts:393`
  - body: This is still the earlier shared-config blocker: even after adding `agentId` to `removePluginFromConfig`, the body removes `plugins.entries`, allow/deny lists, slots, load paths, and owned channel config by bare plugin id. A future `uninstall --agent coding demo` would still disable or reset shared/global `demo` config needed by other installs of the same plugin id.
  - confidence: 0.88
- **[P2] Validate the agent before resolving its workspace:** `src/cli/plugins-install-command.ts:1011`
  - body: `resolveAgentWorkspaceDir` is a fallback resolver, not an existence check: for a non-default unknown id it can synthesize a state-dir workspace path. Calling it directly for `--agent` means a typo like `--agent codnig` can install plugin code into a new implied workspace instead of failing closed against `agents.list`.
  - confidence: 0.86

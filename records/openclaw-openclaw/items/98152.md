Full review comments:

- **[P1] Keep scoped records compatible with the plugin lifecycle:** `src/plugins/installs.ts:90-93`
  - body: This writes agent-scoped installs under `pluginId:agentId`, but registry, update, inspect, and trust/precedence code still use `installRecords[manifest.id]` while discovery scans all record paths into the shared registry. A scoped install will not be treated as the managed record for the plugin id, and multiple same-id scoped installs still collapse into normal duplicate plugin resolution instead of staying independent.
  - confidence: 0.91
- **[P2] Add scoped uninstall before writing scoped installs:** `src/cli/plugins-cli.ts:191`
  - body: The PR exposes `plugins install --agent`, but `plugins uninstall` still has no `--agent` option and `runPluginUninstallCommand` has no agent option. Users can create an agent-scoped record and managed directory, but the CLI cannot target that same scope to remove it.
  - confidence: 0.94
- **[P1] Preserve shared config during scoped uninstall:** `src/plugins/uninstall.ts:393-399`
  - body: When `agentId` is passed, this helper still removes shared `plugins.entries`, allow/deny lists, slots, and channel config for `pluginId`. A scoped uninstall must remove only that agent's install record/files unless no other global or agent install still owns the shared plugin config.
  - confidence: 0.9
- **[P2] Validate the requested agent before choosing the install root:** `src/cli/plugins-install-command.ts:1010-1012`
  - body: `resolveAgentWorkspaceDir` returns a fallback workspace path for arbitrary ids, so a typo in `--agent` silently installs executable plugin code into a phantom workspace and persists that `agentId`. The install command should first prove the agent exists or fail before selecting the scoped extensions directory.
  - confidence: 0.87

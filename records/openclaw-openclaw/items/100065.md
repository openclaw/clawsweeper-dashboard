## Summary

Keep open: current main and the latest release still treat `yieldDetected` as terminal progress by itself, so the reported direct-session dead end remains possible when no accepted spawn, message-tool delivery, cron add, async task, or other continuation source exists. Related open issues and PRs cover adjacent empty-output, top-level fan-out, cron, and announce-give-up failures, but none clearly owns this exact no-fresh-continuation-source guard.

## What This Changes

The issue requests a runtime guard or visible fallback so `sessions_yield` cannot silently park an interactive direct session before a viable continuation source exists.

## Best Possible Solution

Define a yield-continuation invariant for interactive direct turns: a yielded turn should either have a known continuation source or produce a visible failed/unsafe fallback instead of silently parking.

## Reproduction Assessment

Yes at source level: `sessions_yield` sets `yieldDetected`, and current terminal-state/fallback logic treats that flag as sufficient even when no accepted spawn, message-tool delivery, cron add, async activity, or visible payload was recorded. I did not run the full Telegram incident live.

## Solution Assessment

Unclear until maintainers define what counts as a valid continuation source. The best technical shape is a runtime guard or visible fallback, but it must preserve valid waits on already-active child work and coordinate with adjacent yielded-session wake PRs.

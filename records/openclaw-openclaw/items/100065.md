## Label Justifications

- `P1`: The issue describes a real direct interactive session that can finish as a successful yielded turn while the user sees the bot stop responding.
- `impact:session-state`: The yielded lane can remain parked until a later inbound message because no fresh wake source was established.

- `maturity:stable`: The direct interactive delivery fallback surface maps to the M4 Stable `gateway-runtime` taxonomy entry, including delivery fallback behavior.

## Summary

Keep open: current main still accepts `sessions_yield` as a successful terminal turn even when the attempt has no accepted spawn or other fresh continuation/delivery evidence, and the related open fallback PR may cover the visible symptom but does not settle the lower-level yield contract or diagnostics.

## What This Changes

The issue reports that `sessions_yield` can end a direct interactive turn without any fresh continuation source, leaving the user-visible session parked until another inbound message arrives.

## Best Possible Solution

Land or adapt the broad empty-interactive fallback if it is the chosen user-visible repair, then ensure the yield terminal-state path records `sessions_yield` without a fresh continuation source as unsafe or diagnosable rather than successful silent progress.

## Reproduction Assessment

Yes, at source level: current main treats `yieldDetected` itself as terminal delivery and terminal state even when `acceptedSessionSpawns`, message-tool delivery, cron side effects, and other continuation evidence are absent. I did not run a live Telegram reproduction in this read-only pass.

## Solution Assessment

Unclear as an implementation choice: a final reply fallback is likely the safest user-visible repair, but the lower-level yield classifier still needs maintainer direction on whether to reject, fail visibly, or only diagnose no-wake yields.

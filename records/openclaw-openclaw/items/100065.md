## Summary

Keep open: current main still treats `yieldDetected` as terminal progress by itself, so the reported direct-session dead end remains possible when `sessions_yield` fires before a fresh wake source exists. Related issues cover adjacent empty-output, cron, subagent wake, and delivery failures, but none clearly owns this exact continuation-source guard.

## What This Changes

The issue requests a runtime guard or visible fallback when `sessions_yield` is called in a direct interactive session before any viable continuation source exists.

## Best Possible Solution

Define the valid continuation invariant for interactive direct yields, then enforce it in the runner/tool boundary with visible fallback diagnostics and regression coverage.

## Reproduction Assessment

Yes at source level: current main treats `yieldDetected` as terminal progress and suppresses incomplete-turn fallback even when no accepted spawn, message-tool delivery, cron add, heartbeat, or async task evidence is present. I did not run the full Telegram incident live.

## Solution Assessment

Unclear until maintainers choose the exact semantics for valid continuation sources. A runtime guard or visible fallback is the maintainable direction, but it must preserve legitimate re-yields for already-active child work.

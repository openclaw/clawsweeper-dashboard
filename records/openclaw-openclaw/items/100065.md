## Label Justifications

- `P1`: A direct interactive session can appear to stop responding after a successful yielded turn, which is a broken agent/channel workflow affecting real users.
- `impact:session-state`: The yielded session is recorded as paused/end_turn without a proven wake source, leaving session liveness state ahead of user-visible progress.
- `impact:message-loss`: The reported user-visible failure is no reply after the accepted direct turn, making the channel look hung until a later human message arrives.
- `maturity:stable`: The affected Gateway runtime agent/session surface is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main still lets `sessions_yield` become a successful paused/end-turn outcome without requiring an accepted spawn, message-tool delivery, cron add, or other fresh continuation source. Related open issues cover adjacent wake and empty-output failures, but none clearly owns this exact no-fresh-wake-source contract gap.

## What This Changes

Report that `sessions_yield` can be accepted in an interactive direct session before any fresh wake source exists, leaving the direct session parked silently.

## Best Possible Solution

Add a runtime-level safety contract for interactive direct `sessions_yield`: require a tracked continuation source or emit a visible fallback/failure diagnostic instead of treating yield intent alone as successful terminal progress.

## Reproduction Assessment

Yes at source level: current main can mark a `yieldDetected` attempt as paused/end_turn and return no payload without accepted session-spawn, message delivery, or cron-add evidence. I did not run a live Telegram reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers decide the yield contract. The best fix is likely a guarded runtime contract that accepts existing durable wake evidence but rejects or visibly fails yields with none, rather than a blanket same-turn-spawn-only check.

## Summary

Keep open: current main still lacks stdout/stderr stream-error handling for the local CLI TTS provider, and this PR targets the right bug, but the stdout failure path should terminate the unusable child process and the proof should exercise the provider path before merge.

## What This Changes

The PR adds separate stdout and stderr stream error handlers to `extensions/tts-local-cli/speech-provider.ts`.

## Best Possible Solution

Make stdout stream errors a terminal provider failure that also terminates the child process, keep stderr diagnostic stream errors handled without affecting audio output, and add provider-path proof that emits the stream errors.

## Maintainer Decision

Required: false

## Reproduction Assessment

Source-reproducible, but not live reproduced here: current main pipes stdout/stderr in `runCli` without stream error listeners, so a pipe `error` event on those streams is not handled by the provider. The PR body includes copied terminal output for a standalone child-pipe simulation, but not a current-main failing provider run.

## Solution Assessment

No, not as-is. The stdout/stderr split is the right owner-local direction, but stdout stream failure should also tear down the failed child process and the PR should prove the provider path, not only standalone stream mechanics.

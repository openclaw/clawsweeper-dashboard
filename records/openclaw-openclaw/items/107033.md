## Label Justifications

- `P0`: A first-time headless-node setup can appear successful and then become unreachable immediately after SSH logout, with recovery potentially requiring terminal expertise or physical access.
- `impact:crash-loop`: The missing persistence setup causes process-level node availability failure and can lead users into conflicting service configurations and restart loops while attempting recovery.
- `impact:ux-release-blocker`: The documented setup path gives no in-product warning or recovery action before a non-technical user loses remote access after logout.

## Summary

Keep this issue open as the canonical Linux node-service persistence bug: current main still leaves node installs vulnerable when systemd user lingering is disabled, while two open closing pull requests propose competing warning-only and automatic-enable approaches.

## What This Changes

Ensure Linux node services installed under user-level systemd remain available after logout, with clear setup and recovery guidance.

## Best Possible Solution

Reuse the existing systemd linger flow after successful Linux node installation, attempt safe non-interactive enablement, preserve an exact `loginctl enable-linger <user>` warning in text and JSON when enablement is unavailable, document the requirement, and prove persistence through an actual SSH logout cycle before landing one candidate.

Yes at source level: install a Linux node as the generated user-level systemd service with `Linger=no`, verify it while logged in, then end the final login session; current main has no node-install linger handling. A real current-main logout-cycle run was not independently captured in this review.

## Solution Assessment

The best fix is to reuse the existing gateway-oriented systemd linger flow rather than add a node-only implementation; warning-only documentation is useful but weaker than safe enablement with a structured fallback warning.

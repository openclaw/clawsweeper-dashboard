## Summary

Keep open: current main verifies a trusted-proxy user but discards that identity before constructing authenticated connection state, leaving session, chat, event, and pairing surfaces unable to enforce per-user authorization. This is a real missing gateway primitive, but the requested tenancy model, ownership rules, shared-session policy, privacy behavior, and compatibility default require a maintainer security/product decision; related open items overlap without superseding it.

## What This Changes

Retain trusted-proxy verified identity in server-owned gateway connection state, optionally scope sessions and session-bound RPCs per user, and expose the verified identity on device-pairing requests.

## Best Possible Solution

Sponsor one generic gateway-principal design: retain server-verified identity outside client `connect` input, centralize session visibility and mutation authorization across every RPC and event projection, define ownership/shared-session/admin semantics, preserve current access by default, and expose only a minimal pairing principal projection with explicit privacy rules.

## Risks / Open Questions

- A trusted-proxy-specific field would fragment identity semantics across trusted-proxy, token, device-token, Tailscale, and future service-principal modes.

- Exposing a user identifier in persisted pairing records and events introduces normalization, privacy, retention, and audit requirements.

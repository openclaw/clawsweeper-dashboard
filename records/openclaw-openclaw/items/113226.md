## Summary

Needs changes before merge: the two added `contents: read` grants in the event-driven responder workflow are broader than its stated API needs, while the labeler’s separate repository-configuration read path can retain its explicit scope.

## What This Changes

The PR adds explicit `contents: read` permissions to the primary and fallback GitHub App tokens used by the auto-response and labeler workflows so Workflow Sanity can audit their declared token scopes.

## System Context

Incoming GitHub issue and pull-request events start the repository’s response and labeling workflows. Each workflow mints a scoped GitHub App token, then uses that token to read repository configuration or write comments and labels through the GitHub API.

## Architecture Diagram

flowchart LR
  A[Issue or pull request event] --> B[Response or label workflow]
  B --> C[GitHub App token]
  C --> D[Declared API permissions]
  D --> E[Repository reads]
  D --> F[Comments and labels]
  E --> G[Workflow sanity audit]

## Best Possible Solution

Keep `contents: read` only on the labeler tokens if their repository configuration load requires it, and remove it from both auto-response token definitions so the audit passes without broadening responder credentials.

## Summary

Keep this PR open for a narrow security correction before merge. The labeler token needs `contents: read` because the action fetches its configuration through the API, but the auto-response workflow checks out and imports its trusted-base script using the job token and the inspected script has no repository-content API call; granting the app token that extra scope there is not justified by the current path.

## What This Changes

This PR adds explicit `contents: read` permission to the primary and fallback GitHub App installation tokens used by automated response and PR-labeling workflows.

## System Context

These `pull_request_target` workflows mint short-lived GitHub App tokens to label pull requests and post deterministic responses. The labeler passes its app token to `actions/labeler`, while auto-response checks out trusted base code and passes its app token to a local GitHub API script.

## Architecture Diagram

flowchart LR
  Event[Issue or pull request event] --> Auto[Auto-response workflow]
  Event --> Label[Labeler workflow]
  Auto --> Checkout[Trusted base checkout]
  Checkout --> Script[Local response script]
  Label --> Token[GitHub App token]
  Token --> LabelAction[Labeler reads config and applies labels]
  Script --> Responses[Issue and PR responses]
  LabelAction --> Labels[Repository labels]

## Best Possible Solution

Keep `contents: read` on both primary and fallback labeler-token requests, remove it from auto-response unless a concrete repository-content API call is introduced and documented, then rerun Workflow Sanity on the refreshed head.

## Summary

This PR remains necessary: current `main` gives the labeler job’s `GITHUB_TOKEN` contents access but passes a separately scoped GitHub App token to `actions/labeler`, which reads `.github/labeler.yml`. The two explicit `contents: read` grants are the narrow repair and prior responder-token over-grants have been removed; keep it open for a security-boundary owner to accept that both primary and fallback App tokens need this read scope before merge.

## What This Changes

The PR adds `contents: read` to the primary and fallback GitHub App tokens used by the labeler workflow so the token passed to `actions/labeler` can read its repository configuration.

## System Context

The labeler workflow reacts to issue and pull-request events, creates a scoped GitHub App token, loads repository label-routing configuration, and applies labels through GitHub APIs. Workflow Sanity audits the declared token permissions, so its result depends on the token scope matching that runtime path.

## Best Possible Solution

Retain the explicit `contents: read` scope on both labeler token paths, merge after the workflow/security owner confirms that both remain responsible for reading `.github/labeler.yml`, and remove the scope if either path stops serving `actions/labeler`.

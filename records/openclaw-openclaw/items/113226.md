## Summary

This PR should remain open. It makes a narrowly scoped permission change, but the supplied green workflow runs do not prove the conditional recovery path in which the primary GitHub App token fails and the fallback token must read repository configuration before applying labels.

## What This Changes

The branch adds `contents: read` to the primary and fallback GitHub App token requests used by the repository labeler workflow.

## System Context

The labeler workflow responds to repository events by minting a GitHub App token, loading label-routing configuration from the repository, and applying labels through GitHub APIs. Its fallback token is used only when the primary App token cannot be minted or used, so both token paths must have the same required read capability.

## Best Possible Solution

Retain the explicit, least-privilege permission only if a controlled fallback run proves that the fallback token reads the label-routing configuration and applies labels; otherwise narrow or remove the fallback grant according to the action and workflow contract.

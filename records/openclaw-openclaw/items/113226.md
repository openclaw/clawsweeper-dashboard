## Summary

This PR remains necessary if Workflow Sanity currently rejects the Labeler token configuration, but it should not merge until the fallback App’s new `contents: read` request is proven against the actual fallback installation. The current hosted runs show ordinary workflow success, not the recovery case where the primary App cannot mint a token; the action’s contract says requesting a permission absent from an App installation errors, so this is both an availability and permission-boundary concern. ([raw.githubusercontent.com](https://raw.githubusercontent.com/actions/create-github-app-token/v1/README.md))

## What This Changes

The PR adds `contents: read` to the primary and fallback GitHub App token requests in the Labeler workflow so its token can read repository label-routing configuration.

## System Context

The Labeler GitHub Actions workflow reacts to repository events, mints a scoped GitHub App token, loads label-routing configuration, and applies labels through GitHub APIs. A fallback App token keeps labeling available if the primary App cannot create a token.

## Architecture Diagram

flowchart LR
  A[Repository event] --> B[Labeler workflow]
  B --> C[Primary App token]
  B --> D[Fallback App token]
  C --> E[Read label routing configuration]
  D --> E
  E --> F[Apply labels through GitHub API]

## Best Possible Solution

Keep the primary and fallback requests aligned only after an owner confirms the fallback installation grants read-only Contents access and a redacted controlled run proves that a forced primary-token failure still loads the routing configuration and applies labels through the fallback token.

## Summary

Keep open: current main now applies static and identity `messages.responsePrefix` values to message-tool sends, but current source and tests intentionally skip provider/model/thinking template prefixes that the issue discussion explicitly asks to support, so a meaningful product-contract decision remains.

## What This Changes

The issue requests consistent application of `messages.responsePrefix` to visible outbound sends made through `message(action="send")`, including provenance-style template prefixes.

## Best Possible Solution

Define one canonical contract for selected provider/model/thinking prefix variables on message-tool sends, then either carry the current agent attempt context into the outbound send path when available or document those variables as unsupported for this path without leaking raw placeholders.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `message(action="send")` inherit the current agent attempt's provider/model/thinking context for `messages.responsePrefix` templates, and what should happen when no live attempt context exists?

Rationale: Current main deliberately skips unresolved model/provider/thinking templates to avoid sending raw placeholders, but the remaining requested behavior requires deciding whether cross-target tool sends should use the current source run context, target-session context, or no selected-model context.

Likely owner: ZengWen-DT

Owner reason: They authored the merged partial implementation and documented the unresolved model/provider/thinking scope boundary in the fix history.

Owner confidence: medium

Options:

- **Use current-attempt context (recommended):** Pass the selected provider/model/thinking from the active agent run into message-tool sends so visible tool delivery matches direct replies when a live attempt exists, with a documented no-context fallback.
- **Keep static and identity only:** Document that message-tool sends support static and identity prefixes but do not support selected-model variables because the send path does not perform model selection.
- **Move to broader attribution design:** Track provider/model/thinking visibility under the broader model-attribution work at https://github.com/openclaw/openclaw/issues/33975 and keep this issue limited to the already-merged static prefix behavior.

## Reproduction Assessment

Yes, at source level: current main has a focused test where `messages.responsePrefix: "[{provider}/{model}]"` on a message-tool send delivers `hello world` without the prefix. I did not run the test in this read-only review.

## Solution Assessment

No: current main is a useful partial fix because it avoids raw placeholder leaks, but it is not the complete requested parity for selected provider/model/thinking templates. The maintainable next step is a maintainer-approved context contract before implementation.

## Summary

Keep open: current main fixed the static and identity-token `messages.responsePrefix` omission for message-tool sends, but the issue was explicitly kept as the canonical tracker for provider/model/full-model/thinking template parity on those sends.

## What This Changes

The issue requests that configured `messages.responsePrefix` be applied consistently to visible outbound sends made through the `message(action="send")` tool, not only to normal replies.

## Best Possible Solution

Keep this as the canonical product/architecture decision for selected-model responsePrefix template parity on message-tool sends: either thread actual attempt context into the send path, or explicitly document and accept the current skip semantics.

## Reproduction Assessment

Yes, at source level. Current tests intentionally show `messages.responsePrefix: "[{provider}/{model}]"` is skipped on `message(action="send")`, while normal replies have model-selected prefix context.

## Solution Assessment

Unclear for the remaining scope. Current main is the right partial fix for static and identity prefixes, but full provider/model/thinking parity needs a maintainer decision about passing selected-model context into message-tool sends.

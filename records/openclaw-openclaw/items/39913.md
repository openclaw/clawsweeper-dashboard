## Summary

Keep open: current main implements static and identity `responsePrefix` for message-tool sends, but the provider/model/full-model/thinking template parity requested in the discussion is still intentionally skipped and needs a product-boundary decision.

## What This Changes

The issue requests that configured `messages.responsePrefix` be applied consistently to outbound sends made through the `message` tool.

## Best Possible Solution

Define the message-tool prefix contract, then carry actual selected provider/model/full-model/thinking context into agent-originated visible sends while keeping the unresolved-template guard for CLI or out-of-run sends.

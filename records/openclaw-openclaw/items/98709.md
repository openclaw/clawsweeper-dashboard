## Summary

Keep open: current `main` still has the Google OAuth token call-site `response.text()`/`response.json()` path, and this PR is a focused, likely-correct fix, but the external-contributor proof is still mock-based and should be strengthened before merge.

## What This Changes

The PR caps Google OAuth token error body text at 8 KiB, parses successful token responses through the provider JSON helper, and adds loopback regression tests for oversized OAuth error streams.

## Best Possible Solution

Keep the narrow Google token call-site cap, but require redacted current-head terminal or live-output proof that exercises the real fetch wrapper path before merge.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Source inspection shows current `main` still embeds the Google OAuth token error body via `response.text()`, but I did not run a failing current-main repro in this read-only review.

## Solution Assessment

Is this the best way to solve the issue? Yes for the call-site diagnostic cap: it reuses the public provider HTTP SDK helper inside the Google plugin boundary and complements the already-merged shared fetch cap.

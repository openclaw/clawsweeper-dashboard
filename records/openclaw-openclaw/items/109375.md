## Label Justifications

- `P1`: A normal mid-run correction can terminate an active agent workflow instead of reaching the next model boundary, affecting a documented default queue mode.
- `impact:message-loss`: The incoming steering message is not safely admitted or deferred and can be lost when the active turn errors.
- `impact:session-state`: The race occurs at the active-run streaming/tool state boundary and interrupts the session's current turn.

## Summary

Close as a duplicate of the open canonical issue at https://github.com/openclaw/openclaw/issues/48003, which already tracks the same failure to admit steering while an active run is between model streaming and tool completion and explicitly identifies the same `isStreaming()` versus active-run checks. This report contributes useful WebChat, Z.AI/GLM, WSL2, and v2026.7.1 reproduction context, but the remaining fix should stay consolidated. ([github.com](https://github.com/openclaw/openclaw/issues/48003))

## What This Changes

Ensure a steer message arriving while an active model run awaits a tool result is queued for the next model boundary instead of erroring and terminating the run.

## Best Possible Solution

Keep one central fix in https://github.com/openclaw/openclaw/issues/48003: admit steering for any compatible active run, defer it to the next model boundary without interrupting the in-flight tool, and add regression coverage for the tool-pending window across normal channel ingress rather than special-casing WebChat. ([github.com](https://github.com/openclaw/openclaw/issues/48003))

## Summary

The hardening is focused and the submitted tempfile proof is credible, but the new 1 MiB cutoff deliberately makes otherwise valid existing auth-profile JSON look absent to provider-source checks. That can change auth routing or doctor/status results for existing installations, so this needs an explicit auth-storage compatibility decision before merge.

## What This Changes

The PR caps JSON reads in `hasAuthProfileStoreSourceForProvider` at 1 MiB using `readRegularFileSync` and adds a regression test for an oversized valid-looking auth profile store.

## Best Possible Solution

Keep the bounded-read hardening, but preserve a supported eligibility path for valid existing stores or explicitly define and migrate the auth-profile storage-size contract before making oversized stores fail closed.

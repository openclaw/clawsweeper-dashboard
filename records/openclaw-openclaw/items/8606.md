## Summary

Keep open: current main and the latest release still lack a context/session pruning lifecycle hook, and the linked implementation candidate remains open, conflicting, and unmerged.

## What This Changes

The issue requests a hook event after context pruning so external memory/indexing code can observe what was trimmed from active context.

## Best Possible Solution

Review and land the linked PR or a maintainer-approved replacement that emits bounded, sanitized pruning metadata from the active agent-hooks path after successful pruning, with focused tests and public docs.

Options:

- **Metadata-only session prune hook (recommended):** Emit session:prune with counts, timestamp, session identity when available, and sanitized bounded tool metadata only.
- **Trusted raw-content opt-in:** Allow raw pruned content only behind an explicit trusted hook or plugin permission with privacy, timeout, and size documentation.
- **Defer core hook surface:** Keep scheduled indexing as the workaround until a broader memory or hook API design covers pruning, reset, and compaction together.

## Reproduction Assessment

Yes, at source level. Current main prunes through the active context extension and pruner without emitting a pruning hook or returning hook metadata, and the hook catalogs and docs omit a pruning event.

## Solution Assessment

Unclear until maintainers choose the hook contract. A bounded metadata-only session:prune event in the active agent-hooks path appears to be the narrowest maintainable direction; raw pruned-content access needs explicit privacy, trust, timeout, and size-limit decisions.

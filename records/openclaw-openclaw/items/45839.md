## Label Justifications

- `P0`: The discussion describes a first-run/recovery lockout where a user who lost browser sessions must use SSH/CLI or an already-paired device to approve a new browser/Control UI pairing.
- `impact:security`: The requested buttons would resolve pairing decisions, which are a trust and authorization boundary for device/browser access.
- `impact:auth-provider`: The issue turns on operator scopes, paired-device authorization, and whether Telegram-originated approval can satisfy pairing/admin requirements.
- `impact:ux-release-blocker`: Without an in-product Telegram approval path, the reported recovery path can block non-technical users unless they use terminal commands or support-level access.

## Summary

Keep open: current main and the latest release still present pairing approval as text commands, while Telegram inline callback support exists only for generic/message-tool and exec/plugin approval surfaces. The remaining work is security-sensitive because a Telegram-originated tap could approve device/browser access, including requests that may require operator.admin.

## What This Changes

The issue requests Telegram inline approve/deny buttons for pairing requests so operators do not need to copy CLI approval commands.

## Best Possible Solution

Add a device-pair-owned, typed approval card/action path that Telegram can render as Approve/Deny buttons, validates the clicking user and requested scopes before resolving, updates or disables the buttons after resolution, and preserves a text fallback command when native callbacks are unavailable.

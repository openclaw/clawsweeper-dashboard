## Summary

Keep open: current main and v2026.6.11 still send Telegram/device pairing approvals as text commands, while the one-tap approval path needs a maintainer security/product decision around sender binding and operator scope checks.

## What This Changes

Request to add Telegram inline Approve/Deny buttons to pairing notifications so operators do not have to paste CLI approval commands.

## Best Possible Solution

Add a device-pair-owned Telegram approval card using typed callback actions, keep the durable pairing store and Gateway scope checks as the source of truth, and coordinate it with the broader channel-aware device approval design.

- **Design guarded pairing callbacks first (recommended):** Define a typed device-pair callback contract that preserves current scope checks, request binding, expiry, idempotency, and denial behavior before implementing Telegram buttons.
- **Limit to low-scope DM pairing only:** Ship buttons only for pairing requests that need `operator.pairing`, while leaving admin/browser scope upgrades on the existing CLI or Control UI path.
- **Fold into broader approval cards:** Pause this issue until https://github.com/openclaw/openclaw/issues/92666 defines the shared channel-aware device approval card contract.

## Reproduction Assessment

Yes, at source level: current main builds pairing notifications as text with `/pair approve <requestId>` and sends them through `sendText` without buttons. I did not run a live Telegram setup because this read-only review can prove the missing path from source and release code.

## Solution Assessment

Unclear as filed: Telegram buttons are a plausible UX, but the best fix is a typed, device-pair-owned callback contract that preserves Gateway scope checks rather than raw callback strings or a shortcut around `/pair approve` authorization.

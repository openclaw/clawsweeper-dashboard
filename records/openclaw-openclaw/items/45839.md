## Label Justifications

- `P0`: The issue discussion includes first-run/recovery pairing paths where a non-technical user can be blocked from Control UI/browser recovery without an in-product approval path.
- `impact:security`: Pairing approval determines whether a Telegram or device/browser identity gains trusted access, so the requested callback path affects an authorization boundary.
- `impact:auth-provider`: The affected behavior is pairing, approval scopes, and trusted Telegram/browser identity authorization rather than ordinary message rendering.
- `impact:ux-release-blocker`: The reported workflow can leave users needing SSH or CLI approval to recover a browser/device pairing path, which is not an in-product path for a first-time or community user.

## Summary

Keep open: current main and the latest checked release still send Telegram pairing requests as plain CLI/text approval commands, while existing inline-button/callback support covers adjacent surfaces such as exec approvals or generic outbound messages, not pairing approve/deny. The remaining work changes an auth-sensitive Telegram approval path and needs maintainer security/product direction before implementation.

## What This Changes

The issue requests Telegram inline approve/deny buttons for pairing requests instead of requiring CLI/text approval commands.

## Best Possible Solution

Define a typed, replay-safe Telegram pairing approval action that preserves existing durable pairing records and scope checks, then split broader `operator.admin` device/browser approval cards to #92666 unless maintainers explicitly choose to combine them.

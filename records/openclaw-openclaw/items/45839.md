## Label Justifications

- `P0`: A later user report describes a Telegram plus Control UI recovery path where losing browser sessions leaves no in-product approval path and requires SSH or CLI access.
- `impact:security`: The requested buttons would approve or deny access-changing pairing requests and must preserve authorization boundaries.
- `impact:auth-provider`: The affected surface is pairing, operator scopes, and trusted device/browser authorization rather than ordinary message rendering.
- `impact:ux-release-blocker`: A community user can be blocked from Control UI/browser recovery unless they use terminal/SSH or an already-paired device.

## Summary

Keep open: current `main` and v2026.6.11 still render Telegram/channel pairing approval as copyable command text, while Telegram callback handling covers other interactive surfaces but not pairing approve/deny. The remaining work is useful, security-sensitive, and needs maintainer direction before implementation.

## What This Changes

The issue requests Telegram inline Approve/Deny buttons on pairing notifications so operators can approve or deny pairing requests without pasting CLI commands.

## Best Possible Solution

Define a typed, replay-safe pairing/device approval action that keeps the durable pairing store and existing approval-time scope checks authoritative, renders Telegram Approve/Deny buttons, and provides an in-product recovery path for browser/device pairing that does not require SSH.

## Label Justifications

- `P0`: A later user report describes a Telegram-plus-Web-UI recovery path where losing browser sessions leaves no in-product approval path and requires SSH/CLI to approve a new browser device.
- `impact:security`: The requested buttons would approve or deny access-changing pairing requests and must preserve authorization boundaries.
- `impact:auth-provider`: The affected surface is pairing, operator scopes, and trusted device/browser authorization rather than ordinary message rendering.
- `impact:ux-release-blocker`: A community user can be blocked from Control UI/browser recovery unless they use terminal/SSH or an already-paired device.

## Summary

Keep open: current main and the latest release still render Telegram/channel pairing approval as text commands, while Telegram callback handling covers generic/plugin/exec callbacks but not pairing approve/deny. The remaining work is useful, but it needs a maintainer security/product decision before implementation.

## What This Changes

Request Telegram pairing notifications to render Approve/Deny inline buttons that approve or deny pairing requests instead of requiring copied CLI commands.

## Best Possible Solution

Add a typed, replay-safe pairing/device approval action that renders as Telegram buttons while keeping the durable pairing store and existing approval-time scope checks authoritative, plus an in-product recovery path for browser/device pairing that does not require SSH.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Telegram chat callbacks be allowed to approve or deny pairing/device requests, and which operator scopes must a button press prove for DM pairing versus `operator.admin` browser/device approval?

Rationale: The requested UX moves access-changing approval from explicit CLI or scoped gateway clients into Telegram callback handling, and current source intentionally gives Telegram command owners only `operator.pairing` for device-pair approvals.

Likely owner: steipete

Owner reason: The relevant history spans shared pairing formatting, native approval UX, and recent pairing work, making this the clearest routing candidate for the security/product decision.

Owner confidence: high

Options:

- **Design typed pairing approval actions (recommended):** Define reusable approval actions with request id, action, expiry, single-use semantics, caller identity, audit, and existing scope enforcement before Telegram renders Approve/Deny buttons.
- **Limit first pass to DM pairing:** Add buttons only for low-scope channel DM pairing and keep `operator.admin` browser/device approvals on CLI or Control UI until a separate step-up model lands.
- **Defer chat-originated approvals:** Keep the command-copy workflow until the broader channel-aware device approval and step-up authorization direction is settled.

## Reproduction Assessment

Yes, source-level: current main sends Telegram/channel pairing and device-pair notifications as text commands, and the Telegram callback handler has no pairing approve/deny branch. I did not run a live Telegram pairing flow in this read-only review.

## Solution Assessment

Unclear as proposed: inline buttons are the right UX target, but the maintainable fix should use typed approval-action semantics with existing scope enforcement rather than a pairing-specific raw callback shortcut.

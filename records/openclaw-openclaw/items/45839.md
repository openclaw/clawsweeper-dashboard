## Summary

Keep open: current main and v2026.6.11 still render Telegram/device-pair pairing approvals as command text, while Telegram native callback handling covers generic/plugin/select/exec approval paths but not pairing approve/deny. The requested button flow remains security-sensitive because it would approve chat/device access and must preserve owner, scope, expiry, replay, deny, and first-owner bootstrap semantics.

## What This Changes

Request Telegram inline Approve/Deny buttons for pairing notifications so operators can resolve pairing requests without copying CLI commands.

## Best Possible Solution

Define a typed, request-bound pairing approval callback contract for Telegram that renders Approve/Deny buttons while the existing pairing stores and approval-time scope checks remain authoritative.

## Reproduction Assessment

Yes, source-level: device-pair notifications and DM pairing replies still emit `/pair approve` or `openclaw pairing approve` text, and the Telegram callback handler has no pairing approval branch.

## Solution Assessment

Unclear until maintainer decision: inline buttons are plausible, but the best fix must use typed callbacks with owner/scope checks, request binding, expiry, idempotency, deny cleanup, and first-owner bootstrap semantics.

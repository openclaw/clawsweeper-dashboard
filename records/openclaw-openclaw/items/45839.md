## Label Justifications

- `P0`: A community user described losing browser sessions and having no in-product approval path without SSH/CLI or an already-paired device.
- `impact:security`: The requested buttons would approve or deny access-changing pairing requests and must preserve authorization boundaries.
- `impact:auth-provider`: The affected surface is pairing, operator scopes, and trusted device/browser authorization rather than ordinary message rendering.
- `impact:ux-release-blocker`: The reported Control UI recovery path can block non-technical users unless they use terminal, SSH, or an already-approved device.

## Summary

Keep open: current main and v2026.6.11 still render Telegram and device-pair approval as copyable command text, and the Telegram callback handler has no pairing approve/deny branch. The request is useful but trust-changing, so it needs maintainer security/product direction before implementation.

## What This Changes

Request to add Telegram Approve/Deny inline buttons for pairing notifications so operators can approve or deny pairing requests without copying CLI commands.

## Best Possible Solution

Define a typed, request-bound, single-use pairing/device approval action that renders Telegram Approve/Deny buttons, preserves existing operator scope checks, clears stale buttons, records audit/resolution state, and offers an in-product recovery path for browser/device pairing.

Options:

- **Design typed approval actions (recommended):** Define reusable approval actions with request id, action, expiry, single-use semantics, caller identity, audit, and existing scope enforcement before rendering Telegram buttons.
- **Limit first pass to DM pairing:** Add buttons only for low-scope channel DM pairing and keep `operator.admin` browser/device approvals on CLI or Control UI until a separate step-up model lands.
- **Defer chat-originated approvals:** Keep the command-copy workflow until the broader channel-aware device approval and step-up authorization direction is settled.

## Reproduction Assessment

Yes, source-level: current main formats pairing approval as command text, Telegram sends the pairing reply without `reply_markup`, device-pair notifications say `/pair approve`, and the callback handler has no pairing approve/deny branch. I did not run a live Telegram pairing flow in this read-only review.

## Solution Assessment

Unclear as proposed: inline buttons are the right UX target, but the maintainable fix should use typed approval-action semantics with existing scope enforcement rather than a pairing-specific raw callback shortcut.

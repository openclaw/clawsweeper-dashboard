## Label Justifications

## Summary

Keep open: current main and v2026.6.11 still deliver Slack file attachments through placeholders and media path/type fields, not a structured per-file metadata object with id, name, MIME type, and size. The remaining work is a channel-to-agent context contract decision, not a stale or already-implemented issue.

## What This Changes

The issue requests Slack inbound file attachments to expose structured metadata such as file id, name, MIME type, and size to agents.

## Best Possible Solution

Define a shared inbound attachment metadata contract, map Slack file id/name/MIME/size into it, and preserve the existing placeholders, MediaPath(s), and download-file workflow for compatibility.

Yes, source-reproducible: Slack file messages flow through resolveSlackMedia into placeholders and media facts, while the shared inbound media contract has no structured id/name/MIME/size fields. I did not run a live Slack workspace repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API shape. A shared inbound attachment metadata contract is safer than adding Slack-only fields because the same invariant applies to multiple channel plugins.

## Summary

Keep open: current main and v2026.6.11 mitigate Slack files with placeholders, fileId text, downloads, and media paths, but they still do not expose the requested structured per-file metadata contract to agents.

## What This Changes

Request to expose Slack inbound file attachment metadata such as id, name, MIME type, and size to agents instead of only text/placeholders/media path fields.

## Best Possible Solution

Define a shared inbound attachment metadata contract in the channel/plugin API, populate Slack id, filename, MIME type, and size first, and keep existing placeholders and media fields intact.

Options:

- **Add shared attachment metadata (recommended):** Introduce a channel-agnostic metadata block and populate Slack file id, name, MIME type, and size without replacing existing media fields.
- **Keep current Slack surfaces:** Continue relying on placeholders, media paths/types, and download-file, then close or defer structured metadata.
- **Add Slack-only metadata:** Ship a narrow Slack-only field now, accepting future cross-channel cleanup risk if other transports need the same contract.

## Reproduction Assessment

Yes at source level: Slack receives file id/name/MIME/size fields, but current normalization projects only placeholders and media path/type facts into agent context. No live Slack workspace run was performed in this read-only review.

## Solution Assessment

The structured metadata option is the right direction, but the best implementation is shared channel metadata rather than a Slack-only inline text field.

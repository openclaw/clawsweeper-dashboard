## Summary

Keep open: current main and v2026.6.11 still do not provide the requested structured Slack file metadata to agents; related fixes cover placeholders, file IDs in text, and media downloads, but the remaining work is a shared channel/plugin context contract decision.

## What This Changes

Requested behavior: deliver Slack inbound file attachment metadata such as file ID, name, MIME type, and size to agents.

## Best Possible Solution

Define a shared inbound attachment metadata contract in the channel/plugin API, populate Slack file ID, filename, MIME type, and size first, and keep existing placeholders and media fields intact.

Rationale: The source-level gap is real, but the durable fix changes the agent-facing channel/plugin context API rather than only Slack internals.

- **Add shared attachment metadata (recommended):** Introduce a channel-agnostic metadata block and populate Slack file ID, name, MIME type, and size without replacing existing media fields.
- **Keep current Slack surfaces:** Continue relying on placeholders, media paths/types, and download-file, then close or defer structured metadata.
- **Add Slack-only metadata:** Ship a narrow Slack-only field now, accepting future cross-channel cleanup risk if other transports need the same contract.

## Reproduction Assessment

Yes, at source level: Slack receives file ID, name, MIME, and size fields, but current normalization projects only placeholders and media path/type facts into agent context. I did not run a live Slack workspace in this read-only review.

## Solution Assessment

No for a narrow Slack-only field; the maintainable path is a shared inbound attachment metadata contract that preserves the current Slack placeholder and media fields.

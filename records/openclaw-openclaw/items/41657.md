## Summary

Keep open: current main and the latest release expose Slack files through downloaded media plus filename/fileId placeholders, but they still do not provide the requested structured per-file metadata contract for agents.

## What This Changes

The issue requests Slack inbound messages to deliver file attachment metadata such as file id, filename, MIME type, and size to agents.

## Best Possible Solution

Define a shared InboundAttachments-style channel/plugin SDK contract that preserves existing placeholder and Media* fields while mapping provider file IDs, filenames, MIME types, sizes, local paths, and download status across Slack and sibling channels.

## Maintainer Decision

Kind: product_direction

Rationale: The missing data is clear in source, but field shape, privacy boundaries, and cross-channel semantics change the agent-facing channel/plugin contract and should be chosen by maintainers.

Likely owner: vincentkoc

Owner confidence: medium

Options:

- **Add Shared Attachment Metadata (recommended):** Introduce a cross-channel structured attachment field covering provider ids, filenames, MIME types, sizes, local paths, and download status while preserving legacy fields.
- **Keep Current Contract:** Document that Slack fileId is available through placeholders and defer structured metadata until more channels require it.
- **Prototype Slack Only:** Add a Slack-only metadata field first, accepting possible migration risk if the shared contract differs later.

## Reproduction Assessment

Yes, at source level: current main reads Slack files and exposes placeholders plus MediaPath/MediaTypes, but no structured field carries filename, MIME type, size, and provider file id together. I did not run a live Slack event.

## Solution Assessment

Unclear until maintainers choose the contract. A shared inbound attachment model looks more maintainable than adding another Slack-only field because Discord and Telegram have similar attachment metadata surfaces.

## Summary

Keep open: current main and v2026.6.11 still expose Slack files through placeholders, media paths, content types, and download-file guidance, but not as structured per-file id/name/MIME/size metadata. The issue discussion usefully narrowed this from “files are stripped” to a shared inbound attachment contract decision across channel plugins.

## What This Changes

The issue requests structured Slack file attachment metadata in inbound agent context, including file id, name, MIME type, and size.

## Best Possible Solution

Define a shared inbound attachment metadata contract, map Slack file id/name/MIME/size into it, and preserve the existing placeholders, MediaPath(s), and download-file workflow for compatibility.

## Reproduction Assessment

Yes, source-reproducible: Slack file messages flow through resolveSlackMedia into placeholders/media facts, while the shared inbound media contract has no file id/name/MIME/size metadata field. I did not run a live Slack workspace repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API shape. A shared inbound attachment metadata contract is safer than adding Slack-only context fields because the same invariant applies to multiple channel plugins.

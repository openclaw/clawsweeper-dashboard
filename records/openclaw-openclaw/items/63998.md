## Summary

Keep open: current main and v2026.6.11 still allow oversized active session JSONL to reach whole-file repair and `SessionManager.open()`, while the only open bootstrap-marker PR is a partial candidate and does not cover the full crash-restart recovery boundary.

## What This Changes

The issue requests recovery guards for gateway OOM restart loops caused by oversized session transcripts, repeated bootstrap markers, and duplicated media payloads.

## Best Possible Solution

Keep this as the canonical core recovery tracker and land a maintainer-approved default pre-open oversized-transcript policy, with the bootstrap-marker cap coordinated as a partial mitigation rather than the closing fix.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What default recovery policy should OpenClaw apply when an active session transcript is too large or repeatedly poisons gateway startup?

Rationale: The bug is source-reproducible, but the fix must choose between preserving data, truncating or rotating history, skipping a bad session, marking it degraded, and adding media dedupe; automation should not choose that user-data policy alone.

Likely owner: vincentkoc

Owner reason: They have recent history across the active runner, bootstrap helper, and session repair paths implicated by the policy choice.

Owner confidence: medium

Options:

- **Default Safe Quarantine (recommended):** Before whole-file repair/open, detect oversized or repeatedly failing active transcripts, move them out of the hot path, expose a clear recovery/doctor path, and preserve data for manual inspection.
- **Default Tail Rotation:** Automatically compact or rotate oversized active transcripts into a bounded successor before the next run, accepting a more invasive rewrite path.
- **Partial Marker Cap Only:** Land only the bootstrap-marker circuit breaker and leave transcript-size and bad-session recovery to later work, accepting that crash loops can still recur from other oversized transcript causes.

## Reproduction Assessment

Yes at source level: current main still routes active transcripts through whole-file repair and `SessionManager.open()` before any default oversized-file recovery boundary, and related field reports provide concrete OOM evidence. I did not run a live long-duration crash loop.

## Solution Assessment

No current implementation is sufficient yet: the opt-in compaction byte threshold is not a default recovery boundary, and the open bootstrap PR only addresses one amplifier. The best fix needs a maintainer-approved default pre-open recovery policy.

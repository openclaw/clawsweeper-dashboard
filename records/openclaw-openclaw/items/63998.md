Question: What default recovery should OpenClaw apply when an active session transcript is too large to safely repair/open during gateway startup or restart?

Rationale: The source-level bug is clear, but the permanent behavior affects persisted user transcripts and recovery semantics, so automation should not choose quarantine, truncation, skip, or doctor-only repair without maintainer intent.

Likely owner: vincentkoc

Owner reason: He is the strongest current-main history signal for the implicated embedded runner/session paths in this shallow checkout.

Owner confidence: medium

Options:

- **Default Degraded Quarantine (recommended):** Mark the session degraded before full open, skip automatic replay, expose doctor or in-product recovery, and stop the gateway crash loop without silently truncating user history.
- **Default Truncate Or Rotate:** Automatically compact, truncate, or rotate oversized active transcripts before replay, accepting more automatic mutation of persisted session history.
- **Bootstrap Cap Only:** Land only the bootstrap-marker circuit breaker now and keep the larger transcript-size and degraded-reload policy for a separate follow-up.

## Reproduction Assessment

Yes at source level: current main still routes oversized active transcripts through whole-file repair and SessionManager.open, and related user reports provide concrete OOM/restart evidence. I did not perform a live long-duration crash-loop reproduction.

## Solution Assessment

No current implementation is sufficient yet: the opt-in byte guard is not a default recovery boundary and the open bootstrap PR covers only one amplifier. The best fix needs a maintainer-approved default recovery policy before implementation.

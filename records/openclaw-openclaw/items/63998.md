## What This Changes

The issue asks for default recovery controls that prevent oversized session transcripts and repeated bootstrap entries from driving the gateway into an OOM restart loop.

Keep this as the canonical recovery tracker and land a maintainer-approved default pre-open oversized-transcript policy, with bootstrap-marker capping as one component rather than the whole fix.

## Maintainer Decision

Kind: product_direction

Question: What default recovery behavior should OpenClaw use when an active session transcript is too large or repeatedly crashes during gateway restart?

Rationale: Automation can identify the unsafe whole-file load path, but choosing between quarantine/skip, truncation/reset, media dedupe, and doctor-guided recovery changes user-data preservation and upgrade behavior.

Likely owner: vincentkoc

Owner reason: They have recent, directly relevant embedded-runner/bootstrap/session history and are a plausible routing owner for the recovery-policy decision.

Owner confidence: high

Options:

- **Pre-open quarantine with recovery (recommended):** Detect oversized or repeatedly failing transcripts before whole-file repair/open, mark the session degraded, skip the crash loop, and expose a doctor/fix recovery path.
- **Automatic truncation or reset:** Keep the gateway running by rewriting the active transcript automatically, accepting a higher risk of surprising transcript loss.
- **Bootstrap cap only:** Land only the marker append circuit breaker as a partial mitigation while leaving the oversized transcript loader and recovery policy unresolved.

## Reproduction Assessment

Yes at source level: current main still repairs and opens the active transcript through whole-file reads, and the discussion includes macOS and Linux OOM restart-loop field reports. I did not execute a live long-running 31 MB crash loop.

## Solution Assessment

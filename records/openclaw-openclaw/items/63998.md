## Summary

Keep open: current main and v2026.6.11 still let an oversized active session transcript reach whole-file repair and cold `SessionManager.open()` before any default quarantine, skip, or truncate policy, and the only linked PR is a partial bootstrap-marker mitigation that has not landed.

## What This Changes

The issue asks for default recovery safeguards so large session transcripts and repeated bootstrap entries cannot drive a gateway crash-restart OOM loop.

## Best Possible Solution

Keep this issue as the canonical recovery tracker and choose a default pre-open oversized-transcript policy that prevents restart loops without silently destroying user history.

Question: What default recovery policy should OpenClaw apply before repairing or opening an active session transcript that is large enough to crash the gateway on restart?

Rationale: Source proof shows the failure boundary is real, but the safe product behavior depends on a maintainer choice between preserving history, quarantining/skipping dangerous sessions, truncating old entries, or requiring a doctor-mediated recovery.

Likely owner: vincentkoc

Owner reason: They are the clearest recent owner across the active embedded runner, bootstrap, repair, and session manager paths that would carry the policy.

Owner confidence: high

Options:

- **Quarantine Then Doctor Recovery (recommended):** Move oversized crash-prone active transcripts out of the hot startup/open path by default, mark the session degraded, and provide a doctor or visible recovery flow for inspection and restoration.
- **Bounded Tail Load:** Load only a bounded tail or compacted summary for oversized transcripts, accepting more automatic history loss in exchange for fewer manual recovery steps.
- **Marker Cap Only:** Land only the bootstrap-entry circuit breaker first, accepting that full-transcript OOM recovery remains open as a separate later decision.

## Reproduction Assessment

Yes, at source level: current main still routes oversized active transcripts through whole-file repair and `SessionManager.open()`, and the issue plus related reports provide concrete OOM/restart evidence. I did not run a live long-duration crash loop.

## Solution Assessment

No current implementation is sufficient yet: the cache cap avoids retaining some warm entries, and the open bootstrap PR only addresses one growth amplifier. The best fix needs a default pre-open recovery policy before repair/open.

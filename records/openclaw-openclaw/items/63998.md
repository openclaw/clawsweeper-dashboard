Question: Which default recovery policy should OpenClaw apply when an active session transcript is already oversized or poison-restarts the gateway on reload?

Options:

- **Default bounded recovery (recommended):** Add a default pre-open guard that moves oversized or repeatedly crashing transcripts into an explicit degraded recovery path before whole-file repair/open, with doctor or CLI recovery guidance.
- **Opt-in only:** Keep maxActiveTranscriptBytes as an operator opt-in and document manual recovery, accepting that default installs can still hit this crash-restart boundary.
- **Split narrow fixes:** Land the bootstrap-marker cap separately and split media dedupe or loader streaming into focused follow-ups while this issue remains open as the umbrella.

Yes at source level: current main still routes oversized active transcripts through whole-file repair and SessionManager.open, and related field reports show the OOM loop. I did not run a live long-duration crash loop.

## Solution Assessment

No current implementation is sufficient: the byte guard is opt-in and the open PR only addresses bootstrap-marker growth. The best fix needs a default pre-open recovery policy for oversized active transcripts.

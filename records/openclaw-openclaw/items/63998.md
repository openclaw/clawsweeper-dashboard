## Summary

Keep open: current main and the latest release still allow oversized active session transcripts to reach whole-file repair/open paths, and the linked bootstrap-marker PR only covers one growth amplifier rather than the full crash-restart recovery boundary.

## What This Changes

The issue requests gateway/session recovery guards for oversized active transcripts so crash-restart cycles stop loading and growing the same JSONL until OOM.

## Best Possible Solution

Keep this issue open as the canonical recovery work: add a default oversized-active-transcript boundary before repair/open, stop repeated bootstrap marker appends, and expose doctor/user recovery without requiring manual file surgery.

Kind: product_direction

Question: What default recovery policy should OpenClaw use when the active session transcript is too large to safely repair/open on gateway restart?

Rationale: The source-level bug is clear, but the durable fix changes user-visible recovery semantics: quarantine/skip, truncate/compact, or opt-in-only behavior each has data retention and upgrade tradeoffs.

Likely owner: vincentkoc

Owner reason: Recent session/transcript merge history makes this the best available routing owner for the recovery-policy decision.

Owner confidence: medium

Options:

- **Default quarantine and doctor recovery (recommended):** Before whole-file repair/open, detect oversized active transcripts, mark the session degraded, skip the crash loop, and surface a doctor/fix path that preserves the original file for operator recovery.
- **Bootstrap circuit breaker only:** Land only the open bootstrap-marker cap and accept that oversized transcripts can still OOM until a later recovery design lands.
- **Opt-in compaction guard only:** Rely on `maxActiveTranscriptBytes` and transcript rotation configuration, which avoids a default data-policy change but leaves existing default installs exposed.

## Reproduction Assessment

Yes at source level: large active transcripts still flow through whole-file repair and `SessionManager.open()` before any default quarantine/skip boundary, and bootstrap completion markers are still appended on main. I did not run a live OOM loop in this read-only review.

## Solution Assessment

No: the linked bootstrap PR is only a partial mitigation because it removes one append amplifier but leaves whole-file transcript load and recovery policy unresolved. The safer fix is a default recovery boundary before repair/open plus the bootstrap circuit breaker.

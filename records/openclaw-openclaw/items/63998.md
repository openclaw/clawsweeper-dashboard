## Summary

Keep open: current main and v2026.6.11 still allow active session transcripts to reach whole-file repair/open before any default quarantine, skip, or truncate boundary; the open bootstrap-marker PR only addresses one amplifier.

## What This Changes

This issue asks for recovery guards around oversized session transcripts so crash restarts do not keep loading and appending to the same JSONL until the gateway OOMs.

## Best Possible Solution

Add a default crash-recovery boundary for oversized active transcript load, with doctor-visible quarantine or compact-to-successor recovery, and treat bootstrap-marker limiting as a separate amplifier fix.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What default recovery policy should OpenClaw use when an active session transcript is too large or repeatedly crashes the gateway on reload?

Rationale: The code can prove the current unbounded load boundary, but choosing between skip/quarantine, automatic compaction, destructive truncation, or opt-in-only behavior determines data preservation and upgrade semantics.

Likely owner: vincentkoc

Owner reason: Recent session serialization, repair, and compaction-adjacent history makes this the strongest routing candidate for the recovery-policy decision.

Owner confidence: medium

Options:

- **Default quarantine or successor recovery (recommended):** Mark the session degraded before full replay and move future turns to a safe successor or quarantine path with doctor-visible recovery guidance.
- **Bootstrap amplifier only:** Land only the bootstrap marker circuit breaker and leave oversized transcript recovery to manual operator cleanup or existing opt-in compaction settings.
- **Config-gated strict mode:** Keep current default behavior and add an explicit strict recovery option, accepting that existing users can still hit the crash loop until they opt in.

## Reproduction Assessment

Yes, source-reproducible rather than live-reproduced: the issue gives concrete crash-loop logs, a second Linux confirmation, and current source still materializes active JSONL in the SessionManager and repair paths. I did not run a 31 MB gateway crash loop locally.

## Solution Assessment

No: the current opt-in byte compaction and the open bootstrap-marker circuit breaker are useful partial mitigations, but the best fix needs a default recovery boundary before oversized transcripts can repeatedly crash reload.

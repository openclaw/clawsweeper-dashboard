## Summary

Keep this PR open for QQBot owner approval: the transport hardening is correctly placed and well proven, but the permanent 1 MiB receive-size contract is not established by QQ protocol documentation or a live QQ gateway run, so merging can reject legitimate events.

## What This Changes

The PR sets a 1 MiB inbound `maxPayload` on the QQBot gateway WebSocket factory and updates direct and proxy-path constructor tests to require that option.

## Best Possible Solution

Adopt an owner-approved and documented QQBot gateway receive limit—prefer a conservative 16 MiB cap absent stronger platform evidence—while retaining shared direct/proxy wiring tests and oversized-frame loopback proof.

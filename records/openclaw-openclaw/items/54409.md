## Summary

Keep open: current main and the latest release still route ordinary Feishu same-chat messages through the full sequential handler before shared active-run queue admission, and the direct fixing PR is open, unmerged, and currently conflicting.

## What This Changes

The issue reports that Feishu same-chat serialization prevents `messages.queue.mode = "collect"` follow-up messages from reaching the shared active-run queue while the first run is still active.

## Best Possible Solution

Land or replace https://github.com/openclaw/openclaw/pull/92962 so ordinary Feishu same-chat follow-ups reach shared active-run queue admission while preserving control and `/btw` lane ordering.

Yes. Source inspection shows Feishu still awaits the same-key sequential task around the full message handler, and the shared queue only batches followups when they arrive while `isActive` is true; I did not run a live Feishu tenant reproduction.

## Solution Assessment

Yes. The best remaining path is the linked Feishu-boundary repair or an equivalent replacement; the shared queue policy already handles collect once messages reach it while the run is active.

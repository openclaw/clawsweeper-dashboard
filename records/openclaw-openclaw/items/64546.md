## Label Justifications

- `P1`: The PR addresses a high-impact Mattermost callback-token forgery path but may also break button callbacks if the replacement secret is not durable.
- `merge-risk: 🚨 compatibility`: Existing deployments without a configured interaction secret can change behavior during upgrade because the PR replaces the shipped bot-token-derived fallback.
- `merge-risk: 🚨 message-delivery`: Mattermost button callbacks can be rejected if sender and verifier do not share the same generated fallback secret.
- `merge-risk: 🚨 security-boundary`: The PR changes the HMAC credential boundary that authorizes Mattermost interactive button callbacks.

## Summary

Keep open: the PR addresses a real Mattermost interaction-token security flaw, but the current patch can break legitimate callbacks when no configured interaction secret is present and does not wire the new credential through supported setup, docs, or SecretRef target surfaces.

## What This Changes

The PR changes Mattermost interactive callback token signing to use configured or generated per-account interaction secrets instead of deriving a stable secret from the bot token.

## Best Possible Solution

Choose an upgrade-safe Mattermost interaction-secret model, then wire setup, SecretRef/secret-target docs, Mattermost docs, restart or split-process coverage, and a clean branch refresh before merge.

## Reproduction Assessment

Yes. Source inspection shows current main derives the Mattermost interaction HMAC secret from the bot token with a public key and uses it for callback `_token` verification; I did not run a live Mattermost server in this read-only review.

## Solution Assessment

No. Removing bot-token-derived signing is the right direction, but an in-memory random fallback plus hidden config surface is not the best upgrade-safe solution for a credential shared by sender and callback verifier.

## Label Justifications

- `P1`: The PR addresses a Mattermost callback authorization weakness but can also break real button-click workflows if merged without durable credential handling.
- `merge-risk: 🚨 compatibility`: Merging the PR can change existing Mattermost button behavior for deployments that do not configure the new interaction secret.
- `merge-risk: 🚨 message-delivery`: A mismatched generated secret can cause legitimate Mattermost button callbacks to be rejected as invalid tokens.
- `merge-risk: 🚨 security-boundary`: The diff changes the credential used as the authorization boundary for Mattermost interaction callbacks.

## Summary

Keep open: the security direction is still needed, but this patch is not merge-ready because the new fallback secret is process-local, the new credential is not wired through supported setup/SecretRef/docs surfaces, and the branch is currently dirty against base.

## What This Changes

The branch adds a Mattermost `interactions.secret` credential and replaces bot-token-derived callback HMAC secrets with configured or generated per-account interaction secrets plus tests.

## Best Possible Solution

Land a refreshed or replacement fix that removes bot-token-derived signing while making the Mattermost interaction secret durable or explicitly fail-closed, with setup, SecretRef metadata, docs, restart/split-process proof, and old-forgery rejection coverage.

## Reproduction Assessment

Yes. Source inspection of current main and v2026.6.11 shows the interaction secret is deterministically derived from the bot token with a public HMAC key and then used for `_token` verification; I did not run a live Mattermost server in this read-only review.

## Solution Assessment

No. Removing bot-token-derived signing is the right direction, but the current in-memory fallback plus hidden credential surface is not the narrowest upgrade-safe solution for a secret shared by sender and callback verifier.

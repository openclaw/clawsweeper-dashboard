## Label Justifications

- `P1`: The PR addresses a security-sensitive Mattermost callback signing weakness that can affect interaction authorization and real button workflows.
- `merge-risk: 🚨 compatibility`: Changing the signing secret fallback can break existing Mattermost button callbacks across restarts or split sender/verifier processes unless a durable secret is provisioned.
- `merge-risk: 🚨 message-delivery`: Valid Mattermost button clicks can be rejected as `Invalid token` when the signer and verifier do not share the generated in-memory secret.
- `merge-risk: 🚨 security-boundary`: The diff changes the credential and HMAC authorization boundary for Mattermost interaction callbacks without fully wiring the new secret through supported credential handling.

## Summary

Keep open: this PR addresses a real Mattermost interaction-signing security bug that is still present on current main and v2026.6.11, but the branch is not merge-ready because the replacement secret can be per-process only, the new credential surface is not wired through supported setup/SecretRef/docs surfaces, and GitHub reports the PR as dirty.

## What This Changes

This PR replaces Mattermost interaction signing's bot-token-derived secret with configured or generated per-account secrets, adds an `interactions.secret` config field, and updates related Mattermost send, monitor, account, and test paths.

## Best Possible Solution

Land a refreshed security fix, or a narrow replacement, that removes bot-token-derived Mattermost interaction signing while making the replacement secret durable or explicitly fail-closed through supported setup, SecretRef, docs, tests, and restart or split-process proof.

## Reproduction Assessment

Yes. Source inspection of current main and v2026.6.11 shows the deterministic bot-token-derived HMAC secret used for Mattermost `_token` verification; I did not run a live Mattermost server in this read-only review.

## Solution Assessment

No. Removing bot-token-derived signing is the right direction, but the current in-memory fallback plus hidden credential surface is not the narrowest upgrade-safe solution for a secret shared by sender and callback verifier.

## Label Justifications

- `P1`: The PR addresses a high-impact Mattermost callback-token forgery path but can also break live button workflows if the replacement secret is not durable.
- `merge-risk: 🚨 compatibility`: The replacement signing secret changes existing Mattermost interaction upgrade behavior when no configured secret exists.
- `merge-risk: 🚨 message-delivery`: If sender and verifier do not share the generated secret, legitimate Mattermost button callbacks can be rejected.
- `merge-risk: 🚨 security-boundary`: The patch changes the credential and HMAC boundary that authorizes Mattermost interaction callbacks.

## Summary

Keep open: current main and v2026.6.11 still contain the Mattermost bot-token-derived HMAC signing root, so this security fix remains needed, but this PR is not merge-ready because the replacement unset-secret path is process-local, the new credential is not wired through supported setup/docs/SecretRef surfaces, and the branch currently conflicts with base.

## What This Changes

The branch adds a SecretRef-capable Mattermost `interactions.secret`, replaces bot-token-derived interaction HMAC secrets with configured or generated per-account secrets, and updates Mattermost interaction/account tests.

## Best Possible Solution

Choose a durable or explicit fail-closed Mattermost interaction-secret model, wire the supported setup/docs/SecretRef surfaces, refresh the branch, and prove old-forgery rejection plus restart or split-process callback validation.

## Reproduction Assessment

Yes. Source inspection shows current main derives the Mattermost interaction signing secret from the bot token with a public HMAC key, and the PR's unset-secret regression is source-reproducible because generated secrets are process-local.

## Solution Assessment

No. Removing bot-token-derived signing is the right direction, but an in-memory random fallback plus hidden config is not the best upgrade-safe solution for a credential shared by sender and callback verifier.

## Label Justifications

- `P1`: This PR addresses a security-sensitive Mattermost interaction-token boundary and can affect real button callback delivery.
- `merge-risk: 🚨 compatibility`: Existing deployments without a configured interaction secret may need a new operator action or migration before callbacks remain stable.
- `merge-risk: 🚨 message-delivery`: A process-local generated secret can cause legitimate Mattermost button clicks to be rejected as Invalid token.
- `merge-risk: 🚨 security-boundary`: The PR changes the credential that protects the plugin-auth Mattermost interaction endpoint from forged callbacks.

## Summary

Keep open: the security direction is valid, but this PR still has merge-blocking upgrade and delivery issues because the unset-secret fallback is random and process-local, while the new credential is not wired through supported setup, SecretRef, or docs surfaces.

## What This Changes

The PR changes Mattermost interaction token signing from bot-token-derived HMAC secrets to configured or generated per-account interaction secrets, with schema/types and focused tests.

## Best Possible Solution

Choose an upgrade-safe Mattermost interaction-secret model, then wire setup, SecretRef registry/reference docs, Mattermost docs, restart or split-process coverage, and a clean branch refresh before merge.

## Reproduction Assessment

Yes. Source inspection of current main and v2026.6.11 shows the Mattermost interaction HMAC secret is derived from the bot token with a public key, and source inspection of the PR shows unset secrets become random process-local values.

## Solution Assessment

No. Removing bot-token-derived signing is the right direction, but an in-memory random fallback plus a schema-only credential is not the best upgrade-safe solution for a secret shared by the sender and callback verifier.

## Summary

Keep open: current main and the latest release still delete only the cron job record, while base cron session rows remain outside both `cron.remove` and the current `:run:` retention sweep. The issue is already tied to open cleanup work, but the remaining choice is a cron/session lifecycle decision rather than something safe to auto-close or queue as a new independent fix.

## What This Changes

The issue asks for cron job deletion to remove associated session-store records and run artifacts so deleted jobs no longer appear as ghost sessions in the Control UI.

## Best Possible Solution

Land one maintainer-approved cron session lifecycle policy that removes deleted-job ghost sessions without deleting live cron base rows that carry user preferences.

Options:

- **Guarded retention cleanup (recommended):** Use the ownership-aware orphan-retention path so deleted-job base rows are cleaned after the retention window while live job-owned rows stay protected.
- **Immediate delete cleanup:** Clean the deleted job's base and run session rows during `cron.remove`, with tests proving active-run, per-agent store, and carried-preference behavior are safe.
- **Split the scopes:** Land guarded retention first and track immediate Control UI ghost-session cleanup as a narrower follow-up if delayed cleanup is not acceptable.

## Reproduction Assessment

Yes. Source inspection shows `cron.remove` removes only the cron job row, isolated cron can use base `agent:<agentId>:cron:<jobId>` keys, and the current reaper/test boundary skips those base rows.

## Solution Assessment

Unclear. Direct delete-time cleanup matches the report, but guarded ownership-aware retention is safer for live base rows that preserve model/auth/label choices, so maintainers should choose the lifecycle boundary.

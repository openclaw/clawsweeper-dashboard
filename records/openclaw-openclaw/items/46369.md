## Label Justifications

- `P2`: This is a bounded cron/session cleanup bug with visible stale UI state but no emergency outage, data loss, or security bypass shown for this issue.
- `impact:session-state`: The reported failure leaves cron session metadata in the session store after the owning cron job is deleted.

## Summary

Keep open: current main and v2026.6.11 still leave base cron session rows outside both `cron.remove` and the `:run:`-only reaper, so the reported ghost-session path remains source-reproducible. The remaining blocker is choosing the cron/session lifecycle policy, not proving that the report is obsolete.

## What This Changes

The issue requests that deleting a cron job also remove its related run artifacts and persisted cron session row so the Control UI does not show deleted-job ghost sessions.

## Best Possible Solution

Land one maintainer-approved cron session lifecycle policy that removes deleted-job ghost sessions while preserving live cron base rows that carry user preferences.

Options:

- **Split Delete And Retention Scopes (recommended):** Land or revise the guarded retention work for stale orphan rows, then add narrow immediate `cron.remove` cleanup only if maintainers require deleted jobs to disappear from session UI immediately.
- **Immediate Delete Cleanup:** Make `cron.remove` purge the deleted job's base and run session rows with tests for active runs, per-agent stores, and carried preferences.
- **Retention-Only Cleanup:** Accept that deleted-job base rows are removed after `cron.sessionRetention` and document that immediate Control UI disappearance is not guaranteed.

## Reproduction Assessment

Yes. Source inspection on current main shows `cron.remove` removes only the job record, isolated cron can use base `agent:<agentId>:cron:<jobId>` keys, and the current reaper/test boundary skips those base rows; I did not run a live mutating gateway repro in this read-only review.

## Solution Assessment

Unclear. Direct delete-time cleanup best matches the ghost-session report, but guarded ownership-aware retention is safer for broad base-row pruning, so maintainers should choose the lifecycle boundary before implementation.

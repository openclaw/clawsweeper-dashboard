## Summary

Keep open: current main has provider usage visibility and reactive rate-limit/cooldown handling, but it still lacks response-header pace capture, projected pace tiers, durable pace/admission state, `agents.defaults.pace`, autonomous throttling, and structured `session_status` pace data.

## What This Changes

Requested built-in pace-aware rate limiting for autonomous agents based on Anthropic usage windows, with status/tool visibility and optional throttling config.

## Best Possible Solution

Define a visibility-first core design that reuses provider usage/status surfaces, then add opt-in autonomous admission only with durable SQLite state, explicit defaults, and upgrade-safe config semantics.

Options:

- **Phase Observability First (recommended):** Capture and expose pace context in status and session_status without blocking work until the data model and provider semantics prove reliable.
- **Add Opt-In Enforcement:** Introduce disabled-by-default pace thresholds that can throttle subagents, with explicit config, tests, and operator recovery guidance.
- **Plugin/API First:** Keep core lean by first designing provider and agent hooks so a plugin can own pace policy without hardcoding Anthropic behavior in core.

Not applicable as a bug reproduction: this is a feature request. Source inspection gives a high-confidence current-main gap because existing usage windows are display-only and reactive cooldowns happen after failures, while no pace-tier/config/throttling surface exists.

## Solution Assessment

No, not as a one-off config knob; the best fix needs maintainer-scoped visibility, API, persistence, and opt-in throttling semantics coordinated with related rate-limit, budget, and provider-routing work.

## Summary

Keep open: current main has Anthropic usage-window visibility and reactive cooldown/failover, but it still lacks Anthropic response-header capture, pace projection tiers, structured `session_status` pace data, and autonomous admission controls. This remains a product/API/config design item, not conservative cleanup.

## What This Changes

The issue requests built-in pace-aware rate limiting that captures Anthropic quota signals, projects usage pace, surfaces pace in status/session_status, and optionally throttles autonomous agents.

## Best Possible Solution

Approve a visibility-first design that captures provider quota/usage at the right provider seam and exposes projected pace in status/session_status, then add opt-in admission controls only after config, persistence, and provider-contract semantics are decided.

Rationale: The request adds public config/defaults, provider usage state, status/tool output, persistence, and autonomous run-throttling semantics that automation cannot choose safely under the repo's compatibility and core-boundary rules.

Likely owner: Peter Steinberger

Owner confidence: medium

Options:

- **Visibility-first provider pace (recommended):** Expose provider quota windows and projected pace in status/session_status without blocking agent work until the UX and state model are validated.
- **Opt-in admission gates:** Add disabled-by-default pace config for subagent or noninteractive admission, with explicit tests for both disabled and enabled modes.
- **Plugin/API boundary first:** Expose any missing provider usage APIs and let a plugin or skill own policy until core maintainers choose default product behavior.

## Solution Assessment

No for an immediate all-phases implementation; the safer path is maintainer-scoped visibility and API design first, followed by opt-in throttling once config, persistence, and upgrade behavior are agreed.

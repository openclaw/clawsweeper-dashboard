## Summary

Keep open: current main still has the reported unconditional shared MCP loopback teardown path, but this PR is conflict-dirty and the creator-only ownership model can still close the shared server while another cleanup-enabled run is active.

## What This Changes

The branch changes the MCP loopback ensure API to return creation ownership, threads that through CLI run preparation, and gates run-end loopback cleanup on that ownership while adding lifecycle tests.

## Best Possible Solution

Use a per-run lease or refcount release API for the shared loopback server, close only on last release, preserve unconditional gateway shutdown, rebase, and add live A2A proof or a maintainer override.

## Reproduction Assessment

Yes at source level: current main has a global MCP loopback singleton and cleanup-enabled CLI runs close it unconditionally, while subagent and one-shot paths pass the cleanup flag. I did not run a live gateway A2A reproduction in this read-only review.

## Solution Assessment

No. Creator ownership is a plausible mitigation for the parent-created child-reuse case, but the best fix is active-user lifecycle tracking so any run still using the shared loopback server is protected.

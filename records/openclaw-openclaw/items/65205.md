Full review comments:

- **[P1] Move Activity config under Canvas plugin ownership:** `src/config/zod-schema.ts:654-660`
  - body: Current main has moved Canvas host config and routing into `extensions/canvas`, with root `canvasHost` kept only as legacy migration input. Adding `canvasHost.activity` here creates a second runtime config surface that doctor can migrate away from the same root object, so fresh installs and upgrades can diverge unless the Activity settings live under the Canvas plugin config and migration/docs path.
  - confidence: 0.93
- **[P1] Require a credential before allowing Activity access:** `src/gateway/a2ui-activity.ts:150-154`
  - body: `authorizeCanvasRequest` accepts this helper before the normal bearer/capability checks, but the helper returns true when no Activity token is configured after only checking spoofable query/cookie/referer launch markers. A public caller can append an Activity-looking marker and reach Canvas/A2UI without the existing Gateway auth boundary.
  - confidence: 0.95
- **[P1] Bundle or pin the Discord SDK before injecting it:** `src/canvas-host/a2ui.ts:173-175`
  - body: The injected Canvas helper executes `@discord/embedded-app-sdk` from jsDelivr or esm.sh at runtime in the Canvas origin. That puts a third-party CDN response on the trusted execution path for hosted Canvas pages; this should use a pinned local dependency or an explicitly approved integrity/CSP boundary before merge.
  - confidence: 0.9
- **[P2] Stop carrying Activity tokens in WebSocket URLs:** `src/canvas-host/a2ui/index.html:325-329`
  - body: The A2UI bridge copies `activityToken`/`a2uiToken` from the page URL into the WebSocket query string and downgrades to `ws://` on HTTP pages. That leaks the Activity credential through URLs, logs, browser history, intermediaries, and cleartext transport; use a secure cookie or explicit authenticated exchange and fail closed for non-TLS Activity auth.
  - confidence: 0.88
- **[P1] Bound Activity broadcasts and slow clients:** `src/gateway/a2ui-activity.ts:240-243`
  - body: `broadcastPush` retains the full last JSONL payload and sends it to every connected WebSocket without a size cap or `bufferedAmount`/slow-client handling. A large A2UI push or stalled clients can grow memory and event-loop work on the Gateway, so this needs payload limits and backpressure behavior before exposing the hub.
  - confidence: 0.9

## Risks / Open Questions

- The branch is currently conflicting/dirty and still edits old root Canvas/Gateway paths while current main has Canvas config and HTTP routing under the bundled Canvas plugin.
- Adding canvasHost.activity resurrects root Canvas runtime config after current main made root canvasHost a legacy migration input, so upgrades and docs could point operators at a config surface doctor later migrates away.
- Activity mode can authorize public Canvas/A2UI before existing Gateway bearer or plugin node-capability auth when no real Activity credential is configured and spoofable launch markers are present.
- Activity tokens are accepted from URLs/referers and appended to WebSocket URLs, including ws:// when the page is served over HTTP, which can leak credentials through logs, history, intermediaries, or cleartext transport.
- The injected Canvas helper executes Discord SDK code from third-party CDNs at runtime instead of a pinned local package/integrity boundary.
- The Activity WebSocket hub retains and broadcasts arbitrary payloads without size limits or slow-client/backpressure handling, so a large A2UI payload or many slow clients can create availability risk.
- The overlapping Discord canvas branch at https://github.com/openclaw/openclaw/pull/18778 remains open, draft, and dirty, so maintainers need to choose one hardened path rather than keep both as parallel landing candidates.

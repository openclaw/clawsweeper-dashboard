## Summary

Keep open: current main and the latest release have durable SQLite cron run history with status, delivery, run-id, query, paging, UI/API filters, and row-count pruning, but the requested timestamp filters, `openclaw cron logs` or `cron history` CLI surface, follow/export behavior, success-rate aggregates, and explicit prune/vacuum or day-retention workflow are still missing.

## What This Changes

The issue requests persistent cron execution history with filtering, export, aggregates, and retention management.

## Best Possible Solution

Define a narrow core cron-history contract on top of the existing SQLite run-log path: add accepted timestamp filtering and CLI/docs/export/follow/summary behavior, while explicitly scoping retention and security before adding new config or prune commands.

## Reproduction Assessment

Not applicable as a bug reproduction: this is a feature request. Source and docs inspection give high confidence that only the existing SQLite `cron.runs` subset is present today.

## Solution Assessment

No for an automated one-shot fix: the request spans CLI, protocol, UI, docs, config/retention, and security policy. The maintainable path is to extend the existing SQLite run-log path rather than adding a parallel history store or accepting the issue's legacy `cron-history.db`/JSONL paths as written.

## Summary

Keep open: current main implements durable SQLite cron run history with paging, status, delivery, query, run-id, and UI filters, but the central requested timestamp filters, `openclaw cron logs`/`cron history` CLI surface, follow/export behavior, success-rate aggregates, and explicit prune/vacuum or day-retention workflow remain missing.

## What This Changes

The issue requests persistent cron execution history with status/time filtering, CLI log/history commands, summary aggregates, export/follow behavior, and retention maintenance controls.

## Best Possible Solution

Define a narrow core cron-history contract on the existing SQLite `cron.runs` path: add accepted timestamp filters and CLI/docs behavior, choose whether export/follow/summary/prune belong in core, and explicitly scope redaction, access control, and retention before adding config.

## Reproduction Assessment

Not applicable as a bug reproduction: this is a feature request. Source and docs inspection gives high confidence that the existing SQLite `cron.runs` subset is present but the requested CLI/API/time-filter/export/maintenance surface is not.

## Solution Assessment

No, not as an automated one-shot fix. The best path is a maintainer-scoped product and security decision that extends the existing SQLite run-log path rather than adding a parallel history store or ad hoc JSON log export.

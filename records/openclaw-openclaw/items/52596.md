## Summary

Keep open. Current main and v2026.6.11 still have the before-tool-call choke point, session reset lifecycle, and session metadata surfaces, but they do not implement a `session.auth.pin` config, a framework-owned authenticated-session bit, or a trusted non-model verifier; this remains a security-sensitive product/design decision rather than cleanup closure.

## What This Changes

The issue requests a core session authentication PIN gate that blocks tool calls until each new or reset session is verified outside the model context.

## Best Possible Solution

Design an approved core primitive or plugin/API extension with SecretRef-backed secret material, framework-owned authenticated session state cleared on `/new` and `/reset`, a trusted native verification path, and regression coverage for tool blocking plus no PIN transcript leakage.

Rationale: The request crosses config shape, secret handling, session state, reset semantics, transcript redaction, and fail-closed tool execution, so automation should not choose the permanent security boundary or default behavior.

Options:

- **Design a core SecretRef-backed gate (recommended):** Add a core primitive only after specifying secret storage, trusted verification, reset behavior, transcript redaction, compatibility, and recovery UX.
- **Keep it plugin-owned:** Treat the current hook surface as the enforcement seam and document or extend plugin APIs so deployments can opt into session gates outside core.
- **Defer the PIN gate:** Leave existing sandboxing, approvals, allowlists, and external-content wrapping as the supported mitigation until a stronger step-up-auth design is chosen.

## Reproduction Assessment

Yes, at source level. Current main exposes the before-tool-call hook and reset lifecycle, but source inspection shows no `session.auth.pin` config, authenticated session bit, or trusted verifier; this is feature absence rather than a failing existing contract.

## Solution Assessment

Unclear until maintainers choose the security boundary. The before-tool-call and reset layers are plausible, but a raw PIN in config is probably not the best permanent secret shape; a SecretRef-backed verifier or explicit plugin API design is safer than prompt-space comparison.

## Summary

Keep open: current `main` still reduces each payload’s delivery results to one `messageId` before firing `message_sent`, while the normalized receipt and durable queue identity remain internal; the request fits OpenClaw’s plugin-extension direction, but maintainers must define queue-scoped versus universal delivery identity before implementation.

**Likely related people**
- @Drickon — medium confidence; prior work added richer outbound `message:sent` correlation.
- @zqchris — medium confidence; recent work maintained `message_sending`/`message_sent` payload behavior.

## What This Changes

Expose normalized delivery receipts, logical delivery identity, retry attempts, and originating run correlation through the `message_sent` plugin hook.

## Best Possible Solution

Add an explicitly documented, additive delivery-observation contract that exposes a stable receipt projection and available run correlation, keeps existing `messageId` semantics unchanged, and initially treats delivery ID and attempt number as optional queue-owned fields unless maintainers choose a universal dispatch identity.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `message_sent` expose queue identity only when a durable queued delivery exists, or should OpenClaw mint a logical delivery ID and attempt number for every outbound dispatch?

Rationale: Both choices are implementable, but they create different permanent Plugin SDK semantics for direct sends, retries, recovery, and idempotency; repository behavior does not currently establish one as the public contract.

Likely owner: @Drickon

Owner reason: Their prior outbound `message:sent` correlation work is the strongest available feature-history signal for this API choice.

Owner confidence: medium

Options:

- **Queue-scoped identity (recommended):** Expose a hook-safe receipt and available run correlation now, with optional `deliveryId` and clearly defined `attemptNumber` only for durable queued deliveries.
- **Universal delivery identity:** Mint and propagate a logical identity for every outbound dispatch, accepting the broader delivery-lifecycle and persistence design work.
- **Receipt first:** Expose the receipt and available run correlation now while deferring all queue identity fields to a separate lifecycle API design.

## Reproduction Assessment

Yes for the capability gap: current source shows complete delivery results and queue identity exist internally while `message_sent` receives only one message ID and the existing canonical context. This is source-reproducible rather than a failing end-user runtime path.

## Solution Assessment

Partly: reusing the existing normalized receipt is the narrowest maintainable direction, but blindly renaming `retryCount` to `attemptNumber` or minting universal identities would establish semantics that current code does not define.

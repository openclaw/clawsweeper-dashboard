## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.87

Full review comments:

- **[P1] Preserve delayed channel stop around QR takeover:** `src/gateway/server-methods/web.ts:109`
  - body: This branch always stops the channel before `loginWithQrStart` once the new existing/preflight hooks return no result. Current main deliberately delays that stop for a non-forced running channel until the plugin actually returns a QR, so non-QR unstable/already-linked failures do not bounce a live WhatsApp runtime; the rebase needs to keep that behavior.
  - confidence: 0.9
- **[P1] Do not reuse terminal QR login state:** `extensions/whatsapp/src/login-qr.ts:84-90`
  - body: `readActiveQrResult` returns any fresh cached `qrDataUrl` without checking whether the waiter has already connected or failed, and the new gateway hook calls it before the auth/preflight checks. A second start request after the scan or an error can therefore show a stale consumed QR instead of the real linked/failed state.
  - confidence: 0.86
- **[P2] Keep auth-stabilizing status warnings:** `extensions/whatsapp/src/status-issues.ts:61`
  - body: The status collector now ignores the old `statusState === "unstable"` path while suppressing the not-linked warning for unknown linked state. That makes a snapshot with auth still stabilizing and no runtime health return no issue, losing the current-main warning operators use to know they should retry later.
  - confidence: 0.84
- **[P1] Avoid parallel QR gateway hooks without API approval:** `src/channels/plugins/types.adapters.ts:342-348`
  - body: Adding `loginWithQrStartExisting` and `loginWithQrStartPreflight` creates a second plugin-facing QR start lifecycle beside `loginWithQrStart`. Because current main already centralizes start/wait behavior through the existing adapter contract, this needs either removal in favor of one canonical path or explicit maintainer-approved SDK direction and compatibility coverage.
  - confidence: 0.8

## Summary

Keep open: current main and v2026.6.11 still expose Telegram forum topic names only after a numeric topic/thread id is already known; they do not provide the requested name-to-topic_id resolver, topic list action, or catalog surface for agent routing.

## What This Changes

The issue requests first-class Telegram forum topic name to topic_id resolution for routing messages by human-readable topic names.

## Best Possible Solution

Keep this as the canonical tracker and design a Telegram-owned observed-topic catalog, list action, or resolver that maps known topic names to IDs with explicit stale, duplicate, renamed, and closed-topic behavior.

Rationale: The existing cache provides observed id-to-name data, but exposing reverse routing requires maintainer intent for stale data, duplicate titles, permissions, and whether the contract belongs in message actions or session context.

Owner confidence: high

Options:

- **Expose Observed Topic Catalog (recommended):** Add a Telegram-owned list/catalog action that returns known topic ids, names, closed state, and freshness so agents can choose or ask when ambiguous.
- **Add Resolver-Only Helper:** Add a direct name-to-id helper that returns structured ambiguity instead of silently routing when duplicate or stale names exist.
- **Keep Manual IDs For Now:** Leave numeric topic ids as the only supported routing contract and document the workaround until a stronger Telegram product surface is chosen.

## Reproduction Assessment

Yes, at source level: current main still routes Telegram forum sends through numeric messageThreadId or chatId:topic:id, while the existing cache only returns a name after the numeric id is known. I did not run a live Telegram forum group.

## Solution Assessment

Unclear which proposed surface is best. The existing topic-name cache is the likely data source, but the maintainable fix needs a maintainer-selected resolver, list, or catalog contract rather than relying on current-topic metadata.

## Summary

Keep open: current main and the latest release still provide reverse/current-topic name metadata and numeric topic routing, but not the requested forward topic-name to topic_id catalog or resolver.

## What This Changes

The issue asks for first-class Telegram forum topic-name to topic_id resolution so agents can route messages by human-readable topic title.

## Best Possible Solution

Keep this as the canonical tracker and design a Telegram-owned observed-topic catalog, list action, or resolver that maps known topic names to IDs with explicit stale, duplicate, renamed, and closed-topic behavior.

Options:

- **Expose Observed Topic Catalog (recommended):** Add a Telegram-owned list/catalog action or metadata endpoint that returns known topic ids, names, closed state, and freshness so agents can choose or ask when ambiguous.
- **Add Resolver-Only Helper:** Add a direct name-to-id helper, returning structured ambiguity or stale-data errors instead of silently routing when names collide or cache data is old.
- **Keep Numeric-Only Routing:** Leave topic names as display/context metadata and document numeric topic ids or `chatId:topic:<threadId>` as the only supported routing contract.

Yes, source-level: current main still routes Telegram forum sends through numeric `messageThreadId` or `chatId:topic:id`, while the existing cache only returns a name after the numeric id is known. I did not run a live Telegram forum group.

## Solution Assessment

Unclear which proposed surface is best. The existing topic-name cache is the likely data source, but the maintainable fix needs a maintainer-selected resolver, list, or catalog contract rather than relying on current-topic metadata.

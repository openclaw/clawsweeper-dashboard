## Summary

Keep open: current main still exposes Telegram forum topic names only after a numeric thread id is known, and it does not provide the requested topic-name-to-topic_id resolver, topic-list action, or catalog surface for routing.

## What This Changes

The issue requests first-class Telegram forum topic name-to-topic_id resolution so agents can route messages to named topics without manual numeric IDs.

## Best Possible Solution

Keep this as the canonical tracker and design a Telegram-owned observed-topic catalog or resolver that returns topic ids, names, closed state, freshness, and structured ambiguity before any name-based routing is allowed.

- **Add Resolver-Only Helper:** Add a direct name-to-id resolver that returns structured ambiguity or not-found results instead of silently choosing a stale or duplicate topic.
- **Keep Numeric IDs Only:** Document numeric topic ids as the only supported routing contract until Telegram topic catalogs have stronger product direction.

Yes, at source level: current main routes Telegram forum sends through numeric messageThreadId/threadId or chatId:topic:id, while the topic-name cache only returns a name after the numeric id is known. I did not run a live Telegram forum group.

Unclear which proposed surface is best. The existing topic-name cache is the likely data source, but maintainers need to choose a catalog, resolver, or context contract before implementation.

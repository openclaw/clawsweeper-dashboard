## Label Justifications

- `impact:session-state`: Repeated or unnecessary compaction can shrink persisted conversational context and destabilize continuation of large sessions.

## Summary

Keep this issue open. Current fallback orchestration carries provider/model identity into each attempt but has no candidate context-window eligibility check, while OpenClaw documents context windows as hard per-model limits handled through compaction; the related reports cover adjacent transition and metadata problems rather than this automatic-failover gap. ([github.com](https://github.com/openclaw/openclaw/blob/main/src/agents/model-fallback.ts))

## What This Changes

Make mid-turn model failover context-window-aware by skipping candidates that cannot fit or compacting before dispatch.

## Best Possible Solution

Add a deterministic candidate preflight that resolves each candidate's catalog window, compares it with the assembled prompt estimate plus output reserve, skips only candidates proven too small when a later candidate fits, and otherwise performs at most one logged compaction targeted to the selected candidate before retrying.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When a known fallback candidate cannot fit the current assembled prompt, should OpenClaw skip it, compact to preserve configured order, or use a bounded hybrid policy?

Rationale: Skipping changes explicit fallback ordering, while compaction persistently changes session state; source inspection cannot determine the intended compatibility tradeoff.

Likely owner: steipete

Owner reason: The central file history shows the broadest recent involvement in fallback semantics, model-chain preservation, runtime behavior, and tests.

Owner confidence: high

Options:

- **Bounded hybrid preflight (recommended):** Skip definitively undersized candidates when a later candidate fits, otherwise compact once for the best eligible configured candidate and fail clearly if it still cannot fit.
- **Preserve order by compacting:** Always attempt to compact for each configured candidate, preserving operator order but accepting latency and persistent context-loss risk.
- **Skip undersized candidates only:** Never compact during failover selection and advance past candidates that cannot fit, favoring session preservation over strict fallback order.

## Reproduction Assessment

We do not have a live current-main reproduction in this read-only review, but the source-level path is high confidence: fallback candidates and attempts carry no context-window or prompt-size eligibility data, and tests do not cover that transition.

## Solution Assessment

Unclear until maintainers choose the compatibility policy. Candidate-aware preflight is the correct boundary, but unconditional skipping and unconditional compaction each create avoidable behavioral risks; a bounded hybrid is the safest default.

## Risks / Open Questions

- Skipping a candidate changes the semantics of an explicitly ordered fallback chain and could bypass a model the operator expected to receive a compacted prompt.
- Preemptive compaction mutates persistent session context; choosing an unnecessarily small candidate could cause avoidable information loss or repeated summaries. ([github.com](https://github.com/openclaw/openclaw/blob/main/docs/concepts/compaction.md?utm_source=openai))
- Candidate-window metadata can be absent or incorrect, particularly for self-hosted discovery, so a hard skip must fail safely when capacity is unknown.
- Prompt token estimation is approximate; the policy needs headroom and loop bounds so estimation error cannot create another retry or compaction storm.

## Label Justifications

- `P1`: A paired Windows node cannot reconnect unattended after each application or computer restart, breaking a normal companion workflow.
- `impact:other`: The concrete impact is repeated device-pairing approval for an already authorized Windows node, which does not fit the more specific owned impact classes.

## Summary

This is a credible Windows Companion regression, but the supplied logs identify a client-side reconnect contract failure rather than a change needed in the OpenClaw core repository. Core Gateway intentionally treats a missing value for a previously pinned device family as a metadata change requiring approval; the Windows companion should persistently send its device family on every signed reconnect.

## What This Changes

Repair the Windows Companion so a previously paired node reconnects with the same device-family metadata and does not request pairing approval after each restart.

## System Context

The Windows Companion connects to the OpenClaw Gateway over the device-pairing WebSocket protocol. The Gateway compares signed client metadata against the approved pairing record before it authorizes a node connection, then issues or reuses the device token for that approved role.

## Architecture Diagram

flowchart LR
  A[Windows Companion restart] --> B[Signed Gateway connect]
  B --> C[Gateway pairing check]
  C --> D{Metadata matches approved device?}
  D -->|Yes| E[Authorize node connection]
  D -->|No or missing| F[Create repair approval]
  F --> G[Operator approval required]

## Best Possible Solution

File a focused bug in the external Windows Companion repository at https://github.com/openclaw/openclaw-windows-node: preserve and send the stable Windows device-family value for every reconnect, add a restart regression test, and prove one approved node reconnects without a repair request.

## Summary

Keep open: current main and latest release still use one static memory-lancedb database/table with unscoped store and vector search, while https://github.com/openclaw/openclaw/pull/47277 remains open, conflicting, and proof/product/security blocked.

## What This Changes

The issue requests partition-aware memory isolation so memory writes and search results do not leak across users or deployment partitions.

## Best Possible Solution

Keep this as the canonical tracker until a maintainer-approved design enforces gateway-owned user or partition identity across memory-lancedb and memory-core reads, writes, search, legacy handling, docs, and two-user proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What memory isolation contract should OpenClaw support for multi-user deployments: gateway-owned user/partition identity, per-agent/workspace-only isolation, or no supported multi-tenant memory boundary for now?

Rationale: The source-level bug is clear, but choosing the identity boundary, default behavior, and migration/legacy policy affects privacy guarantees, persisted memory data, config compatibility, and plugin API contracts.

Likely owner: steipete

Owner reason: The decision spans memory plugin boundaries, security defaults, and config/migration policy, and steipete has the strongest current history on those surfaces.

Owner confidence: medium

Options:

- **Approve structural partition isolation (recommended):** Define a gateway-owned partition identity and require all memory store/search/get/auto-recall paths to enforce it with explicit legacy-row and migration policy.
- **Narrow to agent/workspace isolation:** Treat user-level tenancy as out of scope for now and only support agent/workspace-scoped memory isolation where current architecture already has stronger ownership signals.
- **Defer multi-user memory support:** Document that shared memory plugins are not safe for multi-tenant deployments until a future design is sponsored.

## Reproduction Assessment

Yes, source-level: current memory-lancedb stores rows without partition identity and searches the shared table without a metadata filter. I did not run a live two-user LanceDB setup in this read-only review.

## Solution Assessment

Unclear: the issue’s proposed options are plausible, but the maintainable fix likely needs a gateway-owned partition identity plus explicit upgrade and legacy-memory policy rather than only dbPath templating or plugin-local filtering.

## Summary

Keep open: current main and v2026.6.11 still lack the requested natural-language inbound reply-in-thread suffix, and the remaining blocker is maintainer product direction for global trigger vocabulary and cross-channel reply-routing semantics.

## What This Changes

The issue requests a built-in inbound suffix directive that strips phrases like `reply in thread` or `rit` from user text and forces the agent response to reply to the inbound message.

## Best Possible Solution

Define a maintainer-approved per-message reply override contract, then implement either a narrow shared inbound directive or a plugin/API seam with prompt stripping, reply-mode semantics, docs, and regression coverage.

Rationale: Source inspection shows the feature is absent, but adding global natural-language parsing can silently change message routing and may introduce public config behavior.

Owner confidence: medium

Options:

- **Approve narrow core directive (recommended):** Adopt only unambiguous suffixes, likely excluding bare `thread`, and require stripping from all model-facing and command-facing inbound bodies with defined reply-mode override behavior.
- **Keep it prompt or plugin owned:** Leave natural-language phrasing to agent instructions or a future plugin/API seam and keep core limited to explicit reply tags plus configured reply modes.
- **Require default-off config first:** Allow the behavior only behind documented schema/config with focused upgrade-safe tests and no default routing change for existing installs.

## Reproduction Assessment

Not applicable as a bug reproduction: this is a feature request. Source and release inspection confirm current OpenClaw supports explicit reply tags and reply modes, but not the requested natural-language inbound suffix parser.

## Solution Assessment

Unclear until product direction is set. A shared inbound parser is plausible, but trigger vocabulary, prompt-stripping coverage, and `replyToMode` override semantics need maintainer approval first.

## Summary

Keep open: current main and the latest release still do not implement a built-in natural-language inbound reply-in-thread suffix, and the remaining decision is cross-channel product behavior rather than a missing bug fix.

## What This Changes

Request a built-in inbound message suffix directive that strips phrases like `reply in thread` or `rit` and forces the outbound reply to target the inbound message.

## Best Possible Solution

Define a maintainer-approved per-message reply override contract, then implement a narrow shared inbound directive or plugin/API seam with prompt stripping, reply-mode semantics, docs, and regression coverage.

Rationale: The source-level feature absence is clear, but this would add new global natural-language parsing that can silently reroute messages and may add public config surface.

Likely owner: steipete

Owner confidence: medium

Options:

- **Approve a narrow core directive (recommended):** Adopt only unambiguous suffixes, likely excluding bare `thread`, and require the implementation to strip all model-facing and command-facing inbound bodies while defining reply-mode override behavior.
- **Keep it prompt or plugin owned:** Leave natural-language phrasing to agent instructions or a plugin/API seam and keep core limited to explicit reply tags plus configured reply modes.
- **Require explicit config first:** Allow the behavior only behind a documented default-off config key with schema, docs, and upgrade-safe tests.

## Reproduction Assessment

Not applicable as a bug reproduction: this is a feature request. Source inspection shows current main and v2026.6.11 support explicit reply tags and reply modes, but not the requested natural-language suffix parser.

## Solution Assessment

Unclear until product direction is set. A shared inbound parser is plausible, but trigger vocabulary, prompt-stripping coverage, and `replyToMode` override semantics need maintainer approval first.

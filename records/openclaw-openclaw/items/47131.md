## Summary

Keep open: current main and v2026.6.11 still support reply threading through reply tags and reply modes, but not the requested inbound natural-language suffix directive. The only direct implementation attempt was closed unmerged, and the remaining work needs maintainer product direction before automation.

## What This Changes

Request to add a built-in inbound `reply in thread`/`rit`-style suffix directive that strips the trigger from the prompt and forces the next reply into the triggering message's thread.

## Best Possible Solution

Define a maintainer-approved per-message reply override contract, then implement one narrow shared inbound directive or plugin/API seam with regression coverage for prompt stripping and supported threaded channels.

- **Defer to broader reply-policy design:** Hold this issue until maintainers design a cross-channel reply-placement policy that can cover user suffixes, tool-use heuristics, and channel-specific thread behavior together.

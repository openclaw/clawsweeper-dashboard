## Summary

Keep open: current main and the latest release still do not implement a built-in natural-language inbound reply-in-thread suffix directive, and the linked implementation attempt is closed unmerged with unresolved product/behavior questions.

## What This Changes

Add a built-in inbound message directive that strips suffixes like `reply in thread` or `rit` and forces threaded replies across thread-capable channels.

## Best Possible Solution

Define a maintainer-approved per-message reply override contract, then implement a narrow shared inbound parser or SDK/plugin seam with prompt stripping, reply-mode semantics, docs, and channel coverage.

Options:

- **Approve a narrow core directive (recommended):** Adopt a small explicit suffix contract, likely excluding ambiguous bare `thread`, and require implementation to strip all model-facing and command-facing inbound body fields with threaded-channel coverage.
- **Keep it prompt or plugin owned:** Leave natural-language phrasing to agent prompts or a plugin/API seam and keep core limited to explicit reply tags plus configured reply modes.
- **Require explicit config first:** Allow the feature only behind a documented config key with schema, docs, and tests, accepting the extra configuration surface intentionally.

## Label Justifications

- `P1`: Automatic background model calls can repeatedly fail for live users despite the same session succeeding through profile-aware interactive resolution.
- `impact:auth-provider`: The defect selects the wrong provider credential and ignores the established auth-profile routing and expiry contract.
- `impact:session-state`: The reported failure blocks automatic compaction and can pin an unusable auth profile onto active sessions.

## Summary

Keep open: current main still builds the PI discovery credential map by taking the first convertible profile for each provider in raw store insertion order. That bypasses the documented profile-order and OAuth-preference resolver, and OAuth conversion accepts any positive expiry timestamp rather than rejecting expired credentials; the report therefore describes a live provider-auth regression, not an obsolete setup issue.

## What This Changes

Honor canonical auth-profile ordering, OAuth preference, expiry eligibility, and session-specific profile selection when background paths resolve provider credentials.

## Best Possible Solution

Make PI discovery consume a canonical, eligibility-filtered ordered profile selection, then pass session-specific overrides through background model-auth callers rather than retaining a raw one-profile-per-provider map as a competing authority.

## Reproduction Assessment

Yes, at source level: create same-provider API-key and OAuth profiles with the API key first in store insertion order, then invoke PI discovery. The current map selects that first profile without consulting `auth.order`, OAuth ranking, or OAuth expiry eligibility.

## Solution Assessment

Yes, with one refinement: reuse the canonical profile-order/eligibility logic rather than duplicating preference rules in PI discovery, and pass `authProfileOverride` from session-aware background callers instead of trying to infer it from a provider-only map.

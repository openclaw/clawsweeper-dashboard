## Summary

Keep open. Current main and v2026.6.11 still use one coarse Discord message-action gate, so deployments cannot independently deny destructive edit/delete operations while retaining message read/send access; the capability remains useful but needs an explicit security and compatibility decision before implementation.

## What This Changes

Add separate Discord send, read, edit, and delete permission gates while defining the upgrade behavior of the existing boolean message gate.

## Best Possible Solution

Adopt one canonical Discord message-permission resolver owned by the Discord plugin, with explicitly approved legacy-boolean semantics and per-operation send/read/edit/delete decisions reused by schema metadata, discovery, and runtime checks.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Discord message permissions become a boolean-or-object configuration contract, and what exact defaults and inheritance rules should apply to legacy booleans, omitted sub-gates, and account overrides?

Rationale: This changes a mature security boundary and public configuration surface; source inspection can establish the missing capability but cannot choose whether upgrades preserve every existing permission or tighten destructive operations by default.

Likely owner: steipete

Owner reason: This person performed the prior detailed review and is the strongest available routing signal for obtaining the Discord security/config decision.

Owner confidence: medium

Options:

- **Compatible granular gates (recommended):** Retain `messages: boolean` as shorthand and add optional send/read/edit/delete overrides whose omitted values inherit the legacy gate, preserving all existing deployments.
- **Explicit separate gates:** Replace the coarse behavior through a doctor migration to four canonical booleans, avoiding a union contract but requiring a defined shipped-config migration.
- **Keep coarse gate:** Decline additional configuration complexity and document that Discord message operations intentionally share one trust boundary.

## Reproduction Assessment

Yes at source level: the current type, strict schema, discovery code, and runtime dispatcher all expose or enforce one shared `messages` boolean for the relevant operations. A live Discord run is unnecessary to establish that the requested configuration capability is absent.

## Solution Assessment

Unclear until maintainers select the security and upgrade contract. A shared resolver with backward-compatible granular overrides is the narrowest likely implementation, but silently choosing inheritance or safer defaults would be a product and security decision.

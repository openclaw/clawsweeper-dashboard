## Summary

Keep this open: current main and v2026.6.11 still lack a Telegram TTS selector for full-width text plus a separate voice note, and the open captioned-final TTS PR targets single voice-with-caption delivery rather than this requested mode.

## What This Changes

The issue requests a configurable Telegram TTS delivery mode that sends readable text as a normal message and the voice note as a separate message instead of using a voice caption.

## Best Possible Solution

Define a backward-compatible TTS text/voice delivery policy, choose whether it lives globally or under Telegram channel/account TTS config, document it, and require tests plus live Telegram proof for both captioned and separate modes.

Options:

- **Approve a narrow delivery policy (recommended):** Define captioned/bundled versus separate behavior, keep existing captioned behavior as the default, and require docs, focused tests, and live Telegram proof.
- **Keep captioned delivery standard:** Document tagged/manual splitting and overflow fallback as the supported path instead of adding another TTS delivery mode.
- **Defer until captioned-final settles:** Wait for https://github.com/openclaw/openclaw/pull/83988 or its replacement to land before deciding whether separate delivery should become first-class.

## Reproduction Assessment

Yes, at source level: current main has no messages.tts.delivery or equivalent selector, successful TTS still creates one audio-bearing payload, and Telegram keeps short text as a voice caption while splitting only overflow. No live Telegram repro was run in this read-only review.

## Solution Assessment

Unclear pending product direction. A delivery-mode option is plausible, but maintainers should first choose the public contract and reconcile it with captioned-final and voice-only TTS proposals.

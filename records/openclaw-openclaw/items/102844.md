- `impact:ux-friction`: The user-facing setup flow succeeds underneath but presents a transport error and requires an avoidable in-product recovery click.
- `maturity:stable`: The issue affects macOS local Gateway setup integration, and `macOS Gateway host` is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main still reports a dropped `crestodian.chat` RPC as a hard error, while the sibling structured setup path already reconciles the same outcome-unknown Gateway restart case; no open or merged PR currently owns this specific chat-path fix.

## What This Changes

The issue requests that macOS Crestodian conversational onboarding recover after a successful setup restarts the Gateway and drops the in-flight chat RPC.

## Best Possible Solution

Add a narrow macOS Crestodian chat recovery path that polls `crestodian.setup.detect` after a setup-time transport drop, confirms persisted setup, and shows a success/continue state without retrying the mutating chat command.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, source-reproducible with high confidence: approve first-run Crestodian setup in the macOS chat while the Gateway restarts, and the current chat model will catch the dropped RPC as `errorMessage` instead of reconciling setup state. I did not run a live macOS packaged repro in this read-only sweep.

## Solution Assessment

Yes, the best fix is a bounded chat-side outcome reconciliation modeled on `OnboardingAISetupModel.reconcileActivationAfterTransportDrop`. Blindly retrying `crestodian.chat` would risk duplicating an approved mutation, and a Gateway-wide change is broader than needed because `crestodian.setup.detect` already exposes the safe state check.

## Summary

Keep this maintainer-labeled feature open: current main exposes the persisted config snapshot hash but not a runtime-applied revision, so the Control UI cannot reliably distinguish saved state from the configuration accepted by the running Gateway. The additive direction is aligned, but the canonical hash semantics and runtime ownership need maintainer confirmation before implementation. ([github.com](https://github.com/openclaw/openclaw/blob/main/docs/gateway/protocol.md))

## What This Changes

Expose resolved saved and actively applied config revision hashes through the Gateway protocol so clients can distinguish persisted config from running state.

## Best Possible Solution

Add one canonical Gateway-owned resolved revision function, retain the raw root-file `hash` solely for optimistic writes, expose optional saved-resolved and applied revision hashes additively, update the applied value only after successful runtime acceptance, and cover startup, `$include`, hot apply, no-op, rejection, restart, reconnect, and page-reload behavior.

Owner confidence: high

Options:

- **Approve canonical dual revisions (recommended):** Define one resolved revision algorithm, expose saved and applied hashes in both protocol surfaces, and keep the existing raw hash as the write guard.
- **Expose through config.get only:** Keep the handshake smaller and require clients to call `config.get` after connecting or reconnecting to reconstruct applied state.
- **Defer runtime revision tracking:** Keep browser-local pending state and accept that out-of-band restarts cannot be reconstructed truthfully.

## Reproduction Assessment

Yes at source level: save a restart-required config change, reload the page or restart the Gateway out of band, and the client receives only the persisted snapshot hash with no authoritative applied-runtime revision. A live run would strengthen UX proof but is not needed to establish the protocol gap.

## Solution Assessment

Yes in direction, but the permanent field names and hash inputs need maintainer confirmation. A single Gateway-owned revision algorithm is safer than browser-local state or separate ad hoc hashes in the UI and reload paths.

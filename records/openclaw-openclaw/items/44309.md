## Summary

Keep open: current main still implements `sessions_send` as an A2A conversation lifecycle with requester reply-back and target announce behavior, while the requested one-way dispatch/handoff semantic remains missing and needs a maintainer API decision.

## What This Changes

The issue requests an explicit one-way A2A dispatch mode for `sessions_send` that persists work into the target session without requester reply-back ping-pong or target announce.

## Best Possible Solution

Add a maintainer-approved explicit dispatch/delivery semantic at the core `sessions_send` boundary, preserving today’s conversation default while allowing one-way handoff with focused tests, docs, and live multi-agent proof.

- **Add Separate Delivery Primitive:** Introduce a new one-way delivery tool or primitive and keep `sessions_send` as the conversation-oriented API, accepting a larger public surface.
- **Defer To Narrow Guard Fixes:** Keep this issue as design context while landing reverse-call and acknowledgement fixes separately without adding a dispatch mode yet.

## Reproduction Assessment

Yes at source level: current main has no dispatch parameter and still schedules the A2A reply/announce lifecycle for ordinary `sessions_send` calls. I did not run a live webchat multi-agent replay in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API shape. A first-class dispatch semantic is the right solution class, while the existing global `maxPingPongTurns=0` knob is not a complete per-call no-announce handoff solution.

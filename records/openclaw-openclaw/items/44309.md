## Summary

Keep open: current main and the latest release still expose `sessions_send` as conversation-style A2A delivery with reply-back and announce behavior, while this issue asks for first-class one-way dispatch semantics. The open reverse-call PR at https://github.com/openclaw/openclaw/pull/91161 overlaps one duplicate-message symptom but does not replace the broader product/API decision.

## What This Changes

The issue requests a one-way A2A dispatch or handoff mode that persists a task into the target session without reply-back ping-pong or requester announce.

## Best Possible Solution

Add an additive per-send dispatch contract that defaults existing `sessions_send` calls to conversation mode, persists the target-session message, optionally returns delivery acknowledgement, and skips reply-back plus announce only when the caller explicitly requests dispatch.

## Maintainer Decision

Kind: product_direction

Question: Should OpenClaw add one-way A2A handoff as an explicit `sessions_send` mode, as a separate delivery primitive, or defer it while only fixing narrower reverse-call and announce bugs?

Rationale: The source gap is clear, but the fix changes model-facing A2A/session semantics and can affect existing coordination workflows, so automation should not choose the permanent public API shape.

Likely owner: steipete

Owner reason: He has the strongest combined signal from current sessions_send history, adjacent handoff comments, and product/API ownership of this surface.

Owner confidence: high

Options:

- **Add explicit dispatch mode (recommended):** Extend `sessions_send` with a clearly named one-way mode while preserving current conversation behavior as the default, with docs and tests for both modes.
- **Create a separate primitive:** Add a `sessions_deliver` or `sessions_enqueue` style tool so one-way delivery cannot be confused with conversational `sessions_send`, accepting a larger model-facing tool surface.
- **Defer dispatch semantics:** Keep only the current conversation lifecycle for now and handle narrower reverse-call or announce bugs through their existing canonical issues and PRs.

## Reproduction Assessment

Yes at source level: current `sessions_send` has no dispatch parameter and still starts the A2A reply/announce flow for ordinary peer sends. I did not run a live multi-agent replay in this read-only pass.

## Solution Assessment

Unclear as an implementation until maintainers choose the API shape. First-class framework semantics are the right boundary, but `mode`, a separate primitive, and flag-based designs carry different compatibility tradeoffs.

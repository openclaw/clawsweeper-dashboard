## Summary

Keep open: current main and the latest release still implement ordinary peer `sessions_send` as conversation-style A2A delivery with reply-back turns plus announce, while this issue asks for a first-class one-way dispatch/handoff contract. The open reverse-call fix overlaps the duplicate-message symptom but does not cover the broader dispatch-mode API decision.

## What This Changes

The issue requests a one-way A2A dispatch mode for `sessions_send` so task handoffs can be delivered into a target session without reply-back or announce behavior.

## Best Possible Solution

Define a first-class per-send dispatch contract that persists the target-session message and returns optional delivery acknowledgement without starting reply-back or announce, while preserving the existing conversation mode as its own explicit behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should one-way A2A handoff be added as an explicit `sessions_send` mode, a separate one-way primitive, or left outside core while preserving only the current conversation lifecycle?

Rationale: The missing behavior is real in source, but the fix changes model-facing session semantics and could affect existing peer A2A workflows, so automation should not pick the permanent API shape.

Likely owner: steipete

Owner reason: The history points to steipete as the strongest available owner for session docs, inter-session provenance, and A2A lifecycle decisions.

Owner confidence: high

Options:

- **Add explicit dispatch mode (recommended):** Extend the existing `sessions_send` contract with an explicit one-way mode that preserves current conversation behavior as the default and adds focused docs/tests for both modes.
- **Create separate delivery primitive:** Add a new `sessions_deliver` or `sessions_enqueue` style tool so dispatch cannot be confused with conversational `sessions_send`, at the cost of another model-facing tool surface.
- **Keep current lifecycle only:** Treat reverse-call and announce issues as narrower bugs and decline a new one-way core API until a broader A2A design is accepted.

## Reproduction Assessment

Yes at source level: current peer `sessions_send` still has no dispatch parameter and still starts the A2A reply/announce flow for ordinary peer sends. I did not run a live multi-agent replay in this read-only cleanup pass.

## Solution Assessment

Unclear as an implementation until maintainers choose the API shape. First-class framework semantics are the right boundary, but `mode`, separate primitive, and flag-based designs have different compatibility tradeoffs.

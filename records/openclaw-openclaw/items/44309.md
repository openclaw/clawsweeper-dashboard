## Summary

Keep open: current main and the latest release still expose `sessions_send` as conversation-style A2A delivery with reply-back and announce behavior, while this issue asks for a distinct one-way dispatch semantic. The linked reverse-call and duplicate-message PRs are useful adjacent work, but they do not replace the product/API decision for dispatch mode.

## What This Changes

Requested one-way dispatch semantics for A2A `sessions_send` handoffs so a task can be delivered into a target session without reply-back reinjection or announce behavior.

## Best Possible Solution

Define a first-class per-send dispatch contract that persists the target-session message and can return an optional delivery acknowledgement without starting reply-back or announce, while preserving existing conversation mode as the default behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should one-way A2A handoff be added as an explicit `sessions_send` mode, as a separate one-way primitive, or deferred while only fixing narrower reverse-call and duplicate-delivery bugs?

Rationale: Source inspection shows the requested behavior is missing, but the fix changes model-facing session semantics and compatibility for existing A2A workflows, so automation should not choose the permanent API shape.

Likely owner: steipete

Owner reason: The strongest available history signal for session docs and A2A lifecycle decisions points to steipete-authored work in the central files.

Owner confidence: high

Options:

- **Add explicit dispatch mode (recommended):** Extend `sessions_send` with a clearly named one-way mode that keeps current conversation behavior as the default and adds docs/tests for both modes.
- **Create separate primitive:** Add a `sessions_deliver` or `sessions_enqueue` style tool so dispatch cannot be confused with conversational `sessions_send`, accepting the cost of another model-facing tool.
- **Defer dispatch semantics:** Keep only the current conversation lifecycle for now and handle narrower duplicate-delivery bugs such as the open reverse-call and mirror-dedupe PRs separately.

## Reproduction Assessment

Yes, at source level: current `sessions_send` has no dispatch parameter and still starts the A2A reply/announce flow for ordinary peer sends. I did not run a live multi-agent replay in this read-only pass.

## Solution Assessment

Unclear until maintainers choose the API shape; the requested separation between conversation and dispatch is the right product boundary, but implementation should be opt-in and preserve current default behavior.

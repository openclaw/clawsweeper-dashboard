## Summary

Keep open: current main and the latest release still implement ordinary peer `sessions_send` as conversation-style A2A delivery, while this issue asks for an explicit one-way dispatch contract. The open reverse-call guard at https://github.com/openclaw/openclaw/pull/91161 overlaps the echo symptom but does not replace the broader product/API decision.

## What This Changes

The issue requests a first-class one-way A2A dispatch mode that persists a task into the target session without reply-back reinjection or announce behavior.

## Best Possible Solution

Define an explicit per-send dispatch contract that persists the message into the target session and can return a minimal delivery acknowledgement without starting reply-back or announce, while preserving current conversation mode as the default.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should one-way A2A handoff be added as an explicit `sessions_send` mode, as a separate one-way tool, or deferred while narrower A2A duplicate-delivery bugs are fixed first?

Rationale: Source inspection proves the requested behavior is missing, but choosing the model-facing API shape changes session semantics and compatibility for existing A2A workflows.

Likely owner: steipete

Owner reason: The strongest history signal for session-tool semantics and A2A lifecycle decisions points to steipete-authored work across the core files and docs.

Owner confidence: high

Options:

- **Add explicit dispatch mode (recommended):** Extend `sessions_send` with a clearly named one-way mode, keep conversation behavior as the default, and document/test both modes.
- **Create separate delivery primitive:** Add a `sessions_deliver` or `sessions_enqueue` style tool so one-way dispatch cannot be confused with conversational `sessions_send`.
- **Defer dispatch semantics:** Keep current conversation semantics and handle narrower bugs such as reverse-call suppression through focused fixes only.

## Reproduction Assessment

Yes at source level: current `sessions_send` has no dispatch parameter and still starts reply/announce follow-up for ordinary peer sends. I did not run a live multi-agent replay in this read-only review.

## Solution Assessment

Unclear as an implementation until maintainers choose the API shape. First-class framework semantics are the right boundary, but a mode, separate primitive, and flag-based design have different compatibility tradeoffs.

## Summary

Keep open: current main and v2026.6.11 still expose `sessions_send` as conversation-style A2A delivery, while this issue asks for a distinct one-way dispatch contract. The open reverse-call fix is related but explicitly leaves result delivery unchanged, so it does not supersede this request.

## What This Changes

Add a first-class one-way A2A dispatch or handoff mode for `sessions_send` or a sibling primitive that persists into the target session without requester reinjection or announce.

## Best Possible Solution

Define an explicit per-send dispatch contract that persists the target-session message and returns optional delivery acknowledgement without starting reply-back or announce, while preserving the existing conversation mode as the default.

Options:

- **Add explicit dispatch mode (recommended):** Extend `sessions_send` with an explicit one-way mode while preserving current conversation behavior as the default and covering both modes in docs/tests.
- **Create a separate primitive:** Add a `sessions_deliver` or `sessions_enqueue` style tool so dispatch cannot be confused with conversational `sessions_send`, at the cost of another tool surface.
- **Keep current lifecycle only:** Treat reverse-call and announce issues as narrower bugs and defer or decline a new one-way core API until a broader A2A design is accepted.

## Reproduction Assessment

Yes at source level: current peer `sessions_send` has no dispatch parameter and still starts the A2A reply/announce flow for ordinary peer sends. I did not run a live multi-agent replay in this read-only cleanup pass.

## Solution Assessment

Unclear as an implementation until maintainers choose the API shape. First-class framework semantics are the right boundary, but `mode`, separate primitive, and flag-based designs carry different compatibility tradeoffs.

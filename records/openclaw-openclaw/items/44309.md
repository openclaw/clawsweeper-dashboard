## Summary

Keep open: current main still implements normal peer `sessions_send` as conversation-style A2A delivery with optional reply-back turns and a target-side announce step, while this issue asks for a distinct one-way dispatch contract. Recent and open related work narrows isolated-cron feedback and reverse-call duplicates, but it does not provide a general per-send mode that avoids requester reinjection and announce behavior.

## What This Changes

The issue requests an explicit one-way A2A dispatch mode for `sessions_send` handoffs so target-session work does not reply back, re-inject the first target reply, or run announce behavior in the requester session.

## Best Possible Solution

Define a maintainer-approved per-send dispatch contract in core: persist or enqueue the message into the target session, optionally return a small delivery acknowledgement, and skip requester reply-back plus target announce while leaving today’s conversation mode as the default.

## Reproduction Assessment

Yes, at source level: current main has no dispatch parameter and ordinary peer `sessions_send` still starts the A2A reply/announce flow. I did not run a live multi-agent replay, but the missing contract is clear from the schema, docs, helper code, and related comments.

## Solution Assessment

Yes at the product level, but the exact API shape is unresolved. A first-class dispatch mode or primitive is more maintainable than prompt conventions or global `maxPingPongTurns=0`, but maintainers should choose the permanent model-facing contract before implementation.

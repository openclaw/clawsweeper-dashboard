## Summary

Keep open: current main and the latest release still lack an explicit one-way A2A dispatch mode, and the related open PRs address narrower reverse-call, acknowledgement, or duplicate-delivery symptoms rather than the requested no-reply/no-announce handoff semantic.

## What This Changes

Request to add an explicit one-way dispatch mode for A2A handoffs so `sessions_send` can deliver into a target session without reply-back reinjection or announce behavior.

## Best Possible Solution

Add a maintainer-approved per-call dispatch/delivery semantic in the core session tool boundary, preserving today’s conversation/announce default while allowing explicit one-way handoff with focused tests and live multi-agent proof.

Options:

- **Add per-call dispatch mode (recommended):** Add a narrow explicit `sessions_send` delivery mode that skips requester ping-pong and target announce unless requested while keeping the current default unchanged.
- **Add a separate primitive:** Introduce a new one-way delivery tool or primitive and keep `sessions_send` as the conversation-oriented API, accepting a larger new surface.
- **Defer to narrower fixes:** Keep this open as design context while landing reverse-call, cycle, acknowledgement, and channel-specific fixes without adding dispatch semantics yet.

## Reproduction Assessment

Yes, at source level: current main always models `sessions_send` as inter-session delivery followed by the A2A reply/announce lifecycle unless a narrow parent-owned child skip applies. I did not run a live webchat multi-agent replay in this read-only review.

## Solution Assessment

No, the existing `maxPingPongTurns=0` knob is not a complete solution because it is global and still leaves target announce behavior. The maintainable path is an explicit per-call dispatch semantic or separate primitive chosen by maintainers.

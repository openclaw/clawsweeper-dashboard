## Summary

Keep open: current main and the latest release still expose ordinary peer `sessions_send` as conversation-style A2A delivery with reply-back turns plus announce, while this issue asks for a first-class one-way dispatch/handoff contract. The open reverse-call PR overlaps duplicate-message symptoms but does not add dispatch-only semantics.

## What This Changes

The issue requests a first-class one-way dispatch mode for A2A `sessions_send` handoffs that persists the target message without reply-back reinjection or requester announce behavior.

## Best Possible Solution

Keep the existing conversation semantics as the default, then add an explicit dispatch/handoff path that persists the target-session message and optional delivery acknowledgement without starting reply-back or announce.

Options:

- **Add explicit dispatch mode (recommended):** Add a named dispatch/handoff mode to the current session tool contract, keep conversation mode as the default, and cover both source-level and user-facing delivery behavior.
- **Add a separate primitive:** Introduce a new `sessions_deliver` or `sessions_enqueue` style tool for one-way delivery, accepting the extra model-facing surface and docs burden.
- **Limit work to reverse-call guard:** Land only the narrower reverse-call fix and leave dispatch-only handoffs without a first-class contract.

## Reproduction Assessment

Yes at source level: current main still has no dispatch-only `sessions_send` parameter and still starts the A2A reply/announce lifecycle for ordinary peer sends. I did not run a live multi-agent replay in this read-only cleanup pass.

## Solution Assessment

Unclear as an implementation until maintainers choose the API shape. A first-class framework semantic is more maintainable than prompt conventions or `timeoutSeconds: 0`, but the permanent surface needs product/API review.

## Label Justifications

- `P2`: The issue describes a medium-impact multi-agent workflow gap with transcript/routing noise but requires product/API design before implementation.
- `impact:session-state`: The requested dispatch mode changes how inter-session messages are persisted and whether requester transcripts receive worker replies.

## Summary

Keep open: current main and the latest release still expose `sessions_send` without a dispatch-only parameter, and ordinary peer sends still enter the A2A reply/announce lifecycle. The open reverse-call PR only covers one duplicate-message path and explicitly leaves result delivery unchanged, so it does not supersede this product/API request.

## What This Changes

The issue requests a first-class one-way A2A dispatch/handoff mode for `sessions_send` or a sibling primitive that delivers into the target session without reply-back or announce behavior.

## Best Possible Solution

Add a maintainer-approved core A2A delivery contract that cleanly distinguishes conversation mode from dispatch mode while preserving existing `sessions_send` behavior for current callers.

## Reproduction Assessment

Yes at source level: current `sessions_send` starts the target run as `inter_session` data and then `runSessionsSendA2AFlow` can run requester ping-pong plus target announce, with no dispatch-only parameter in the tool schema. I did not run a live multi-agent replay in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public API shape. A typed dispatch mode or sibling primitive is the maintainable alternative to prompt conventions or `timeoutSeconds: 0`, but that is a product/API decision.

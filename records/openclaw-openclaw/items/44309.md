- `impact:session-state`: The reported problem is requester transcript pollution and unintended requester/target session turn ownership during A2A handoffs.

- `maturity:stable`: The affected session/Gateway runtime behavior maps to the M4 Stable Gateway runtime surface and Session APIs category in the maturity scorecard.

## Summary

Keep open: current main and the latest release still expose conversation-style `sessions_send` with reply-back and announce behavior, while this issue asks for a separate one-way dispatch semantic. The related open PRs address narrower duplicate-delivery or acknowledgement pieces but do not settle the product/API shape for dispatch-only A2A handoffs.

## What This Changes

Request an explicit one-way A2A dispatch mode or primitive that delivers work into the target session without requester reinjection, reply-back ping-pong, or announce unless explicitly requested.

## Best Possible Solution

Add an explicit opt-in dispatch-only A2A contract that preserves current conversation behavior by default, persists the task into the target session, suppresses requester reinjection/ping-pong/announce unless requested, documents the API, and proves the behavior with focused tests plus a real multi-agent run.

Rationale: Current main only has conversation-style A2A delivery; changing model-facing session delivery semantics affects compatibility, transcript state, message delivery, and several overlapping open PRs, so automation should not choose the permanent API shape alone.

Owner confidence: high

Options:

- **Add Opt-In `sessions_send` Mode (recommended):** Keep current behavior as the default and add an explicit dispatch mode that disables reply-back, requester reinjection, and announce unless acknowledgement is requested.
- **Create Separate Delivery Primitive:** Add a new `sessions_deliver` or enqueue-style tool if maintainers want dispatch to be visually and semantically distinct from conversational `sessions_send`.
- **Defer To Broader A2A Design:** Keep this issue open until structured callbacks, handoff acknowledgements, and cron/session output routing are designed together.

Yes at source level: current main exposes only the existing `sessions_send` parameters and still runs the A2A reply-back/announce flow. I did not run a live multi-agent reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API shape; the requested separation between conversation and dispatch is the right product boundary, but implementation should be opt-in and preserve current default behavior.

## Summary

Keep open: current main still treats normal `sessions_send` as a conversation-style A2A lifecycle with requester reply-back and target announce, while the requested one-way dispatch/handoff mode remains missing and needs a maintainer API decision.

## What This Changes

The issue requests an explicit one-way A2A dispatch mode or primitive for `sessions_send` handoffs that persists work in the target session without requester reply-back ping-pong or target announce.

## Best Possible Solution

Add a maintainer-approved explicit dispatch/delivery semantic at the core `sessions_send` boundary, preserving today’s conversation default while allowing one-way handoff with focused tests, docs, and live multi-agent proof.

Rationale: The source gap is clear, but choosing the permanent API affects model-facing tool semantics, session-state behavior, docs, tests, and compatibility with existing A2A conversation workflows.

Options:

- **Add Per-Call Dispatch Mode (recommended):** Add an additive `sessions_send` mode that skips requester ping-pong and target announce unless explicitly requested, while leaving the current default unchanged.
- **Add Separate Delivery Primitive:** Introduce a new one-way delivery tool or primitive and keep `sessions_send` as the conversation-oriented API, accepting a larger public surface.
- **Defer To Narrow Guard Fixes:** Keep this issue as design context while landing reverse-call, cycle-guard, and acknowledgement fixes separately without adding a dispatch mode yet.

## Reproduction Assessment

Yes, at source level: current main exposes no dispatch parameter and ordinary `sessions_send` still starts the A2A reply-back/announce lifecycle. I did not run a live webchat multi-agent replay in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API shape. A first-class dispatch semantic is the right solution class, while the existing global `maxPingPongTurns=0` knob is not a complete per-call no-announce handoff solution.

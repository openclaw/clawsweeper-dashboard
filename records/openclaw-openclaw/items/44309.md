## Summary

Keep open: current `main` and the latest release still expose `sessions_send` as conversation-style A2A delivery, while this issue asks for a new one-way dispatch semantic that is not implemented and needs maintainer API direction.

## What This Changes

The issue requests a first-class one-way A2A dispatch mode for `sessions_send` or a sibling primitive that delivers into the target session without reply-back reinjection or final announce behavior.

## Best Possible Solution

Define an explicit per-send dispatch contract that persists the target-session message and can return an optional delivery acknowledgement without starting reply-back or announce, while preserving current conversation mode as the default.

Options:

- **Add explicit dispatch mode (recommended):** Extend `sessions_send` with a clearly named one-way mode that keeps current conversation behavior as the default and adds docs/tests for both modes.
- **Create a separate primitive:** Add a `sessions_deliver` or `sessions_enqueue` style tool so one-way dispatch cannot be confused with conversational `sessions_send`.
- **Defer dispatch semantics:** Keep the current conversation lifecycle and handle narrower duplicate-delivery bugs such as the open reverse-call fix separately.

Yes, source-level: current `main` has no dispatch parameter and still starts the A2A reply/announce flow for ordinary peer sends. I did not run a live multi-agent replay in this read-only cleanup pass.

## Solution Assessment

Unclear as an implementation until maintainers choose the API shape. First-class framework semantics are the right boundary, but `mode`, separate primitive, and flag-based designs carry different compatibility tradeoffs.

## Summary

Keep open: current main and the latest release still treat ordinary peer `sessions_send` as conversation-style A2A delivery with reply-back turns plus announce, while this issue asks for a separate one-way dispatch contract. The open reverse-call PR is relevant but only covers the narrower duplicate reverse-call bug, not the requested dispatch-mode API.

## What This Changes

Request an explicit one-way A2A dispatch/handoff mode for `sessions_send` or a sibling primitive that writes to the target session without reply-back or announce.

## Best Possible Solution

Define a first-class per-call dispatch contract that persists the target-session message and returns optional delivery acknowledgement without starting reply-back or announce, while preserving the existing conversation mode as the default or as an explicit mode.

Question: Should one-way A2A handoff be added as an explicit `sessions_send` mode, as a separate one-way primitive, or declined in favor of the existing conversation lifecycle plus narrower duplicate-message fixes?

Rationale: The missing behavior is source-backed, but the fix changes model-facing session semantics and compatibility for existing A2A workflows, so automation should not choose the permanent API shape.

Likely owner: steipete

Owner reason: The history points to this handle as the strongest available owner for session docs, inter-session provenance, and A2A lifecycle design.

Owner confidence: high

Options:

- **Add explicit dispatch mode (recommended):** Extend `sessions_send` with a clear one-way mode that preserves current conversation behavior by default and adds focused docs/tests for both modes.
- **Create separate delivery primitive:** Add a `sessions_deliver` or `sessions_enqueue` style tool so one-way handoff cannot be confused with conversational `sessions_send`, at the cost of another model-facing tool.
- **Keep current lifecycle only:** Treat reverse-call, announce, and presentation issues as narrower bugs and decline a new one-way core API until a larger A2A design is accepted.

## Reproduction Assessment

Yes at source level: current peer `sessions_send` still has no dispatch parameter and still starts the A2A reply/announce flow for ordinary peer sends. I did not run a live multi-agent replay in this read-only cleanup pass.

## Solution Assessment

Unclear until maintainers choose the API shape. First-class framework semantics are the right boundary, but `mode`, separate primitive, and flag-based designs have different compatibility tradeoffs.

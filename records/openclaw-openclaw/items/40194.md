## Label Justifications

- `P1`: The reported Feishu multi-bot group workflow can route all mentions through one durable bot session/account boundary for real users.
- `impact:session-state`: Multiple Feishu bot applications in one group can share or collide on one persisted group session identity.
- `impact:security`: Replies and state can cross configured Feishu bot application/account boundaries and appear under the wrong identity.
- `impact:message-loss`: Messages addressed to one bot can be handled by the wrong bot session, producing misrouted or suppressed replies.

## Summary

Keep open: current main and the latest release still build Feishu group session identity from group/topic/sender data without a bot account or app discriminator, so the reported multi-bot group session/account collision remains possible and is not owned by a merged fix.

## What This Changes

The issue asks for Feishu group sessions to distinguish multiple bot applications or accounts in the same group so the mentioned bot replies from the correct identity and session.

## Best Possible Solution

Adopt a maintainer-approved Feishu group session identity that includes a stable bot/account boundary, with upgrade-safe doctor or migration handling, focused regression tests, and redacted live multi-bot Feishu proof.

Yes, at source level. Current main still builds Feishu group peer ids from chat/topic/sender only, and the generic non-direct session key builder omits accountId/appId; no live Feishu tenant was exercised.

## Solution Assessment

Unclear. The requested group-plus-app discriminator is the right class of fix, but the best implementation needs a maintainer-approved discriminator and migration or doctor plan before changing durable session keys.

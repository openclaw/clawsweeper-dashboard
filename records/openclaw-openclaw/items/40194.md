## Label Justifications

- `P1`: Multi-bot Feishu group routing can mis-associate active bot identity and session state for real channel users, which is an urgent channel workflow bug.
- `impact:session-state`: The same durable group session key can be reused across Feishu bot accounts, mixing context and last-route state.
- `impact:security`: Wrong account/session association crosses bot identity and authorization boundaries in a shared enterprise chat.
- `impact:message-loss`: Replies can be sent through the wrong bot identity or account, which is message misrouting from the user's perspective.

## Summary

Keep open: current main and v2026.6.11 still let Feishu group sessions collapse by group peer without an account/app discriminator, so multiple Feishu bot accounts in the same group can share session state and overwrite last-route account metadata.

## What This Changes

The issue reports Feishu multi-bot group chats reusing one durable group session and replying under the wrong bot account/persona.

## Best Possible Solution

Make Feishu group session identity account/app-aware by default, with focused tests and an explicit doctor/migration plan for existing shared group sessions and last-route metadata.

## Maintainer Decision

Rationale: The source-level bug is clear, but changing durable session identity affects transcript continuity, last-route account metadata, and cross-bot authorization boundaries, so automation should not choose the compatibility/security policy alone.

Options:

- **Account-scope with migration (recommended):** Update Feishu group peer/session identity to include account or app identity and provide tested migration or doctor handling for existing shared group sessions.
- **Opt-in account-scoped mode:** Add an explicit compatibility-preserving mode first, keeping current shared group sessions as default until maintainers are ready to migrate users.
- **Document unsupported multi-bot grouping:** Keep shared group sessions and document that multiple Feishu apps in one group are not isolated, accepting the current safety and UX limitations.

## Reproduction Assessment

Yes, at source level: two Feishu accounts in the same group with the same agent/default group scope resolve to the same group session key while last-route metadata stores the per-account accountId. I did not run a live multi-bot Feishu tenant.

## Solution Assessment

Unclear until maintainers choose the migration boundary. The likely best fix is account/app-scoped Feishu group identity plus regression tests, but the durable-key migration behavior needs an explicit maintainer decision.

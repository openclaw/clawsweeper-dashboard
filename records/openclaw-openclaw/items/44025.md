## Summary

Keep open: current main and the latest release still expose only explicit flat model fallback lists, while provider-family wildcard/auto selection and the commenter-proposed `fallbackFamilies` contract remain absent. The overlapping catalog-derived fallback PR is open, conflicting, and only partially overlaps this broader design request, so it cannot close or supersede this issue.

## What This Changes

Request provider-family wildcard or auto model fallback selection so configured runs can stay within an intended provider/model pool before crossing to generic routers.

## Best Possible Solution

Keep this open for a maintainer to choose one public fallback contract, likely by extending the existing explicit fallback resolver to derive provider-family candidates from configured catalogs only under an intentional opt-in or documented provider/plugin capability.

## Reproduction Assessment

Yes by source inspection: current main only accepts explicit flat fallback arrays and builds the runtime candidate chain from those arrays. This is a feature/config request, not a broken existing contract reproduction.

## Solution Assessment

Unclear as proposed: wildcard/auto expansion, catalog-derived fallback, and explicit fallback families are different public contracts. The best fix needs maintainer selection of one predictable provider-routing model before implementation.

## Summary

Keep open: current main and v2026.6.11 still support only explicit flat model fallback lists, while provider-family wildcard/auto selection and grouped fallback-family semantics remain absent. The related catalog-derived fallback PR is narrower, open, and not a safe superseding implementation for this broader config contract.

## What This Changes

Requests provider-family wildcard or auto model fallback selection, with optional ordered provider/model priority lists before cross-provider fallback.

## Best Possible Solution

Have a maintainer choose one public provider-family fallback contract using canonical openai/* model refs, then align schema, normalization, runtime fallback resolution, embedded-run fallback gates, docs, and any needed doctor behavior around that single contract.

Rationale: This changes public config and provider-routing behavior, and repository policy treats fallback and config surface additions as product-sensitive rather than a routine repair.

Owner confidence: high

Options:

- **Choose one core fallback contract (recommended):** Pick one canonical config/runtime shape and require implementation across schema, resolver, embedded fallback gates, docs, and migration/doctor expectations.
- **Use plugin routing only:** Keep core fallbacks flat and direct provider-family policies to before_model_resolve plugins, accepting that this will not express ordered failure-chain semantics natively.
- **Defer the surface:** Leave explicit fallbacks as the only supported contract until stronger user evidence or a maintainer-sponsored design narrows the behavior.

## Reproduction Assessment

Source-reproducible rather than a failing bug: current schema, helper, runtime resolver, embedded gate, and docs all show only explicit flat fallbacks. No live provider failover was run because the requested public contract is absent in source.

## Solution Assessment

Unclear as proposed: wildcard/auto refs, fallbackFamilies, and catalog-derived fallbacks are different public contracts. The best fix needs a maintainer-selected provider-routing model before implementation.

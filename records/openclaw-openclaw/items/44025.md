## Summary

Keep open: current main and the latest release still only support explicit flat model fallback lists, while provider-family wildcard/auto selection and the commenter-proposed grouped fallback contract remain absent. The related catalog-derived fallback PR is open, conflicting, proof-blocked, and narrower than this issue, so it is not a safe superseding implementation.

## What This Changes

Requested provider-family wildcard or auto model fallback so users can stay within an intended provider/subscription tier before cross-provider fallback.

## Best Possible Solution

Choose one explicit provider-family fallback contract, then align schema, runtime candidate construction, fallback availability gates, tests, docs, and any doctor/config migration behavior around that contract.

## Reproduction Assessment

Yes, by source inspection: current main accepts only string or `{ primary, fallbacks }` model config and fallback resolution only iterates that flat list. This is a feature/config request rather than a failing current contract reproduction.

## Solution Assessment

Unclear as proposed: wildcard/auto refs, explicit fallbackFamilies, and catalog-derived fallbacks are competing public contracts. The best fix needs maintainer selection of one predictable provider-family fallback model before implementation.

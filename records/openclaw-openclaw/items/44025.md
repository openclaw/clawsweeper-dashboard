## Summary

Keep open: current main and the latest release still only support explicit flat model fallback lists, while provider-family wildcard/auto selection and the commenter-proposed grouped fallback contract remain absent. The related catalog-derived fallback PR is open and narrower, so it is not a merged or safe superseding implementation.

## What This Changes

Request provider-family model fallback selection via wildcard/auto model refs and optional ordered fallback groups so failover stays within the intended provider or subscription tier before crossing providers.

## Best Possible Solution

Keep this open for maintainers to choose one public provider-family fallback contract, then align schema, docs, runtime fallback resolution, embedded-run fallback availability, and any needed doctor/config behavior around that single contract.

## Reproduction Assessment

Yes, by source inspection: current main accepts only string or { primary, fallbacks } model config and fallback resolution only iterates that flat list. This is a feature/config request rather than a failing current contract reproduction.

## Solution Assessment

Unclear as proposed: wildcard/auto refs, catalog-derived fallback, and explicit fallbackFamilies are different public contracts. The best fix needs maintainer selection of one predictable provider-routing model before implementation.

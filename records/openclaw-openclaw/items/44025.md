## Summary

Keep open: current main and the latest release still only support explicit flat model fallback lists, while the requested provider-family wildcard/auto behavior and the commenter-proposed `fallbackFamilies` contract remain absent. The related catalog-derived fallback PR is only a partial, conflicting candidate and cannot safely supersede this broader design item.

## What This Changes

Request provider-family wildcard/auto or grouped model fallback so OpenClaw can stay within an intended provider/model pool before crossing to router or other-provider fallbacks.

## Best Possible Solution

Keep this open for maintainers to choose one predictable public fallback contract, likely an explicit opt-in that derives provider-family candidates from configured catalogs while preserving canonical `openai/*` routing and existing flat `fallbacks`.

## Reproduction Assessment

Yes for the missing capability by source inspection: current main and `v2026.6.11` only accept/read flat explicit fallback arrays, and the strict schema rejects the proposed fields. This is a feature/config contract request rather than a broken existing behavior reproduction.

## Solution Assessment

Unclear as proposed: wildcard/auto expansion, catalog-derived fallback, and explicit `fallbackFamilies` are separate public contracts. The best fix should be selected by maintainers before implementation so provider cost, auth rotation, legacy `openai-codex` migration, and upgrade behavior stay predictable.

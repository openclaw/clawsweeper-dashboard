## Summary

Keep open: current main and the latest release still only support explicit flat model fallback lists; provider-family wildcard/auto selection and `fallbackFamilies` remain absent. The open catalog-derived fallback PR partially overlaps, but it is conflicting and proof-blocked, so it is not a safe superseding implementation.

## What This Changes

The issue requests provider-family-aware model fallback using wildcard or auto model refs, with optional ordered provider-family fallback lists.

## Best Possible Solution

Keep this open until maintainers choose one provider-family fallback contract, then align schema, docs, fallback candidate construction, fallback-availability gates, and doctor/config behavior around that contract.

## Reproduction Assessment

Yes by source inspection: current main accepts explicit flat fallback arrays and does not expand provider wildcard, auto suffix, or grouped family fallback candidates. This is a feature/config request rather than a failing existing contract.

## Solution Assessment

Unclear: wildcard/auto refs, catalog-derived fallback, and explicit fallback families are different public contracts with different provider, quota, and cost behavior. The best solution needs maintainer selection of one predictable routing model before implementation.

## Summary

Keep open: current main still only supports explicit flat model fallback lists, while provider-family wildcard/auto selection and the commenter-proposed grouped fallback contract remain unimplemented. The related catalog-derived fallback PR is open, conflicting, proof-blocked, and narrower than this issue, so it is not a safe canonical replacement.

## What This Changes

Request provider-family-aware model fallback selection, such as `provider/auto`, `provider/*`, or grouped fallback lists, so failover stays within the intended provider/subscription family before crossing to generic routers.

## Best Possible Solution

Choose one canonical provider-family fallback contract, then implement it consistently across schema, docs, candidate construction, fallback availability gates, config write/doctor behavior, and focused failover tests.

## Reproduction Assessment

Yes by source inspection: current main accepts only string or `{ primary, fallbacks }` model config, and fallback resolution only iterates that flat list. This is a feature/config gap rather than a broken existing-contract bug reproduction.

## Solution Assessment

Unclear as proposed: wildcard/auto refs, catalog-derived fallback, and explicit fallbackFamilies are different public contracts. The best fix needs maintainer selection of one predictable provider-routing model before implementation.

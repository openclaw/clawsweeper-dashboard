## Summary

Keep open: current main and v2026.6.11 still only support explicit flat model fallback lists, while this issue asks for a broader provider-family wildcard/auto or grouped fallback contract. The related catalog-derived fallback PR is narrower, open, and conflicting, so it is not a safe canonical replacement for the broader product/config decision.

## What This Changes

Request provider-family model fallback selection through wildcard/auto model refs, optional per-provider priority lists, or grouped fallback families before crossing to generic router fallbacks.

## Best Possible Solution

Have a maintainer choose one canonical provider-family fallback contract, then implement schema, config normalization, runtime fallback candidate construction, fallback availability gates, docs, and regression tests consistently.

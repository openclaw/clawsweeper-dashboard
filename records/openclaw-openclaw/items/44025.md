## Summary

Keep open: current main and v2026.6.11 still support only explicit flat model fallback lists, while provider-family wildcard/auto selection and the commenter-proposed fallbackFamilies contract remain absent. The open overlapping implementation PR covers only a narrower catalog-derived fallback idea and is currently conflicting and unproven, so it cannot close or supersede this design tracker.

## What This Changes

Requests provider-family wildcard or auto model fallback selection so configured models can stay within an intended provider/subscription family when a specific model name changes or fails.

## Best Possible Solution

Keep the issue open for maintainers to choose one predictable fallback contract, then implement it consistently across schema, config normalization, candidate construction, fallback-availability gates, docs, and regression tests while preserving existing explicit fallbacks.

## Reproduction Assessment

Yes by source inspection: current main and v2026.6.11 only read explicit flat fallback arrays and reject the proposed grouped or wildcard fields. This is a feature/config contract gap, not a broken existing behavior reproduction.

## Solution Assessment

Unclear as proposed: wildcard/auto expansion, catalog-derived fallback, and fallbackFamilies are different public contracts. The best fix needs maintainer selection of a predictable provider-routing model before implementation.

## Summary

Keep open: current main and v2026.6.11 still implement only explicit flat model fallback lists, while provider-family wildcard/auto selection and the commented `fallbackFamilies` contract remain absent. The overlapping catalog-derived fallback PR is open, conflicting, proof-blocked, and only partially overlaps this broader fallback-contract request.

## What This Changes

Requests provider-family wildcard or auto model fallback selection, plus optional ordered provider-family fallback lists, so model retries stay within an intended provider/subscription family before crossing providers.

## Best Possible Solution

Keep the issue open until maintainers choose one provider-family fallback contract, then align schema, docs, runtime fallback resolution, embedded-run availability checks, and any needed doctor/config migration behavior around that contract.

## Reproduction Assessment

Yes, at source level: current main only accepts and resolves explicit flat fallback arrays, so wildcard/auto provider-family selection and `fallbackFamilies` are absent. This is a feature/config contract gap rather than a failing existing contract reproduction.

## Solution Assessment

Unclear as proposed: wildcard/auto refs, catalog-derived fallbacks, and explicit fallback families are different public contracts. The best solution needs maintainer selection of one predictable provider-routing model before implementation.

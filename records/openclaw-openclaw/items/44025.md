## Summary

Keep open: current `main` and `v2026.6.11` still only support explicit flat model fallback lists, while provider-family wildcard/auto selection and the related `fallbackFamilies` idea remain absent. The overlapping https://github.com/openclaw/openclaw/pull/60922 covers only catalog-derived fallbacks and is currently conflicting/not merge-ready, so it should not close this broader design tracker.

## What This Changes

The issue requests provider-family wildcard or auto model fallback so OpenClaw can stay within the intended provider/model pool when configured models become unavailable.

## Best Possible Solution

Maintain one explicit public fallback contract that preserves existing `fallbacks` behavior, then update schema/types, config docs, candidate construction, fallback availability gates, and upgrade/doctor handling together.

## Reproduction Assessment

Yes by source inspection: current `main` only accepts flat `fallbacks`, builds text fallback candidates from that array, and reports fallback availability from the same explicit list. This is a feature/config reproduction rather than a failing existing-contract bug reproduction.

## Solution Assessment

Unclear as proposed: wildcard/auto expansion, catalog-derived fallback, and explicit `fallbackFamilies` are competing public contracts. The best fix needs maintainer selection of one predictable provider-routing model before implementation.

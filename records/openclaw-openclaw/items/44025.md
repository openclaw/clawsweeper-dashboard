## Summary

Keep open: current main and the latest release still support only explicit flat fallback lists; provider-family wildcard/auto fallback and the related grouped fallback contract are still absent. The open catalog-derived fallback PR is narrower, conflicting, and not a safe canonical replacement for this broader config/product decision.

## What This Changes

Request provider-family model fallback selection such as wildcard or auto model refs, plus optional priority lists that stay within an intended provider family before crossing to generic routers.

## Best Possible Solution

Choose one canonical provider-family fallback contract, then update schema, config docs/help, fallback candidate construction, embedded-run fallback availability, and focused tests around that single design.

## Reproduction Assessment

Yes, by source inspection: current main accepts only string or { primary, fallbacks } model config and fallback resolution only iterates that flat list. This is a feature/config request rather than a failing current contract reproduction.

## Solution Assessment

Unclear as proposed: wildcard/auto refs, explicit fallbackFamilies, and catalog-derived fallback are separate public contracts. The best fix needs a maintainer-selected contract before implementation so fallback behavior stays predictable.

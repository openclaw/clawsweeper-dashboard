## Summary

Keep open: current main and the latest release still support explicit flat fallback lists, while provider-family wildcard/auto selection and the later `fallbackFamilies` proposal remain absent. The overlapping catalog-derived fallback PR is open but conflicting and only covers a subset, so it is not a safe superseding target.

## What This Changes

Request provider-family wildcard/auto model fallback selection, with optional ordered provider-family fallback groups, so failover stays within the intended provider or subscription tier before crossing to generic routers.

## Best Possible Solution

Keep this as the maintainer design tracker until one public fallback contract is chosen, then implement it across schema, write normalization, candidate resolution, docs, and focused fallback tests with upgrade-safety proof.

## Reproduction Assessment

Yes by source inspection: current main and `v2026.6.11` only accept and execute explicit flat fallback arrays. This is a feature/config request rather than a broken existing contract reproduction.

## Solution Assessment

Unclear as proposed: wildcard/auto expansion, catalog-derived fallback, and explicit fallback-family groups are different public contracts. The best fix needs maintainer selection of one predictable provider-routing model before implementation.

## Summary

Keep open: current main and v2026.6.11 still support explicit flat model fallback lists only, while provider-family wildcard/auto selection and grouped fallback semantics remain absent. The related catalog-derived fallback PR is open, conflicting, and narrower than this issue, so it should not be treated as a safe superseding implementation.

## What This Changes

Request provider-family model fallback selection, such as wildcard/auto model refs or ordered fallback groups, so failover stays within the intended provider or subscription tier before crossing to generic routers.

## Best Possible Solution

Land one maintainer-selected provider-family fallback contract and align schema, config normalization, runtime candidate construction, embedded fallback availability checks, docs, and upgrade behavior around that single contract.

Options:

- **Design explicit family fallback contract (recommended):** Adopt an explicit ordered family/group contract, such as fallbackFamilies or equivalent, so users control provider and subscription-tier order without relying on ambiguous provider auto-selection.
- **Narrow to catalog-derived fallback:** Use the related fallbacksFromModels direction as the canonical implementation, accepting that it reduces duplication but does not fully solve wildcard/auto provider-family semantics.
- **Keep flat fallbacks only:** Decline new fallback config for now and document explicit fallbacks as the supported way to preserve provider and cost control.

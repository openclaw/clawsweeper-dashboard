## Summary

Keep open: current main and v2026.6.11 still support only explicit flat model fallback lists, while this issue requests a new provider-family wildcard/auto or grouped fallback contract. The related catalog-derived fallback PR is narrower and not a safe canonical replacement, so this remains a maintainer product/config decision.

## What This Changes

Request provider-family wildcard or auto model fallback so configured provider preferences survive model rotation without falling through to unrelated router models.

## Best Possible Solution

Have a maintainer choose one canonical provider-family fallback contract, then implement it consistently across schema, config normalization, runtime fallback candidate construction, fallback availability gates, docs, and regression tests.

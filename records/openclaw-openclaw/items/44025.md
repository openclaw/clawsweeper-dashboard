## Summary

Keep open: current main and the latest release still support only explicit flat model fallback lists, while provider-family wildcard/auto selection and the related `fallbackFamilies` idea remain absent. The overlapping catalog-derived fallback PR is still open, conflicting, and proof-blocked, so it is not a safe superseding implementation.

## What This Changes

Request provider-family model fallback via wildcard/auto model refs or ordered fallback groups so unavailable or renamed models stay within the intended provider before cross-provider fallback.

## Best Possible Solution

Choose one maintainer-approved provider-family fallback contract, then align schema, config help, docs, runtime candidate construction, tests, and any doctor/upgrade behavior around that single contract.

## Reproduction Assessment

Yes by source inspection: current main accepts only string or `{ primary, fallbacks }` model config and resolves only explicit fallback lists. This is a feature/config gap rather than a failing existing-behavior repro.

## Solution Assessment

Unclear as proposed: wildcard/auto refs, catalog-derived fallbacks, and explicit fallback families are different public contracts. The best fix needs a maintainer product choice before implementation.

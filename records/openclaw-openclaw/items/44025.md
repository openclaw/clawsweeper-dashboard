## Summary

Keep open: current main and the latest release still expose only explicit flat model fallbacks, not provider-family wildcard/auto fallback or grouped fallback-family semantics. The related catalog-derived fallback PR is open, conflicting, and only partially overlaps this broader product contract.

## What This Changes

Request provider-family wildcard/auto model fallback selection, with optional ordered provider/model priority, so failures stay inside the intended provider family before crossing to generic router fallbacks.

## Best Possible Solution

Keep one core issue open for maintainers to choose a single provider-family fallback contract, then align schema, runtime fallback resolution, availability gates, docs, tests, and any doctor/config migration behavior around that contract.

## Reproduction Assessment

Not applicable as a strict bug reproduction; this is a feature/config request. Source inspection gives a high-confidence reproduction of the gap: current main only accepts and resolves explicit flat fallback arrays, while docs describe the same flat behavior.

## Solution Assessment

Unclear as proposed: wildcard/auto refs, `fallbackFamilies`, and catalog-derived fallbacks are different public contracts. The maintainable path is to choose one predictable provider-family fallback model before code changes.

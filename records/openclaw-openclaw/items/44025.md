## Summary

Keep open: current main and v2026.6.11 still support explicit flat model fallbacks, but not provider-family wildcard/auto refs or grouped fallback families. The open catalog-derived fallback PR is narrower, conflicting, and not a safe canonical implementation for this broader config contract.

## What This Changes

Request provider-family wildcard or auto model fallback selection so failover stays within the intended provider/subscription family before crossing to generic router fallbacks.

## Best Possible Solution

Keep this issue open until maintainers choose one canonical provider-family fallback contract, then align schema, docs, runtime candidate construction, embedded-run fallback availability, config normalization, and focused upgrade tests around that contract.

## Reproduction Assessment

Yes by source inspection: current main accepts only string or { primary, fallbacks } model config and fallback resolution only iterates that flat list. This is a feature/config request rather than a failing current contract reproduction.

## Solution Assessment

Unclear as proposed: wildcard/auto refs, catalog-derived fallback, and fallbackFamilies are different public contracts. The best fix needs maintainer selection of one predictable provider-routing model before implementation.

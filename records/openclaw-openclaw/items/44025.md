## Summary

Keep open: current main and the latest release still only support explicit flat model fallback lists, while provider-family wildcard/auto selection and the related `fallbackFamilies` contract remain unimplemented. The open catalog-derived fallback PR is a narrower, conflicting, proof-blocked partial overlap, so it is not a safe superseding implementation.

## What This Changes

Request provider-family wildcard/auto model fallback, with optional ordered fallback groups, so failover can stay within an intended provider or subscription family before crossing to router models.

## Best Possible Solution

A maintainer should choose one public provider-family fallback contract, then align schema, runtime candidate construction, embedded-run fallback availability, docs, and any needed doctor/config behavior around that contract.

## Reproduction Assessment

Yes, by source inspection: current main accepts only string or `{ primary, fallbacks }` model config and fallback resolution only iterates that flat list. This is a feature/config request rather than a broken current behavior contract.

## Solution Assessment

Unclear as proposed: wildcard/auto refs, catalog-derived fallback, and explicit `fallbackFamilies` are different public contracts. The best path is a maintainer-selected canonical fallback model before implementation.

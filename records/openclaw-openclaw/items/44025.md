## Summary

Keep open: current main and the latest release still support explicit flat fallback lists, but not provider-family wildcard/auto fallback selection or the commenter-proposed fallback family contract. ## What This Changes

The issue requests provider-family model fallback behavior through wildcard or auto model refs, with related interest in ordered fallback families.

## Best Possible Solution

Keep this issue open for maintainers to choose one public provider-family fallback contract, then align schema, docs, runtime candidate construction, model visibility, and any needed doctor/config migration behavior around that contract.

## Reproduction Assessment

Yes by source inspection: current main only accepts and consumes explicit flat fallback arrays, while provider/* is limited to model visibility/catalog policy. This is a feature/config request rather than a failing existing contract.

## Solution Assessment

Unclear as proposed: wildcard/auto refs, fallbackFamilies, and catalog-derived fallback are competing public contracts. The best fix needs maintainer selection of one predictable provider-routing model before implementation.

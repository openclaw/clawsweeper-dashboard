## Summary

Keep open: current main and v2026.6.11 still provide only partial parent/depth lineage, and no merged or viable related item supplies the requested durable root and chain identity. The existing W3C diagnostic `traceId` contract makes the remaining identifier semantics a genuine product/API decision.

## What This Changes

Add canonical parent, root, chain identifier, and depth metadata for spawned sessions and expose it through session APIs.

## Best Possible Solution

Use an explicitly named durable chain identifier distinct from diagnostic tracing, derive root and depth consistently in every native and ACP spawn path, and expose normalized lineage only through authorized session views.

## Maintainer Decision

Rationale: The identifier lifetime, naming, persistence, and public exposure change the session API contract and cannot safely be selected from implementation evidence alone.

Likely owner: steipete

Owner confidence: high

Options:

- **Dedicated chain ID (recommended):** Add a clearly named persisted chain identifier with root, parent, and depth fields on authorized lineage projections.
- **Parent and depth only:** Persist parent and depth, derive roots when needed, and avoid introducing another durable identifier.
- **Reuse diagnostic tracing:** Persist W3C trace IDs across session lifetimes, intentionally coupling request observability to session lineage.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 both lack root and durable chain identity in persisted sessions and Gateway rows, while the conflicting diagnostic `traceId` contract is directly inspectable.

## Solution Assessment

No, not exactly as proposed. The literal `traceId` field is not the safest contract because that name already represents W3C diagnostic tracing; a dedicated durable chain identifier is the narrower maintainable design.

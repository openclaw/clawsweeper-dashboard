## Summary

Current main and the latest release still expose only partial spawned-session lineage; the requested durable root/trace contract remains absent, and adding it requires a maintainer decision about canonical identity rather than another uncoordinated implementation attempt.

## What This Changes

Add canonical parent, root, trace, and depth metadata for spawned session chains and expose it through session listing APIs.

## Best Possible Solution

Standardize one canonical parent edge, derive root and depth where practical, and add a durable chain identifier only if maintainers define a lifecycle distinct from diagnostic traces and task IDs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should spawned-session lineage standardize on the existing parent edge with derived root/depth, or add persisted `rootSessionKey` and a new durable session-chain `traceId`?

Rationale: Either choice becomes persisted session state and a public Gateway/tool contract; source inspection cannot determine the intended identity lifetime or whether diagnostic/task identifiers should be reused.

Likely owner: steipete

Owner reason: This person supplied the existing item-specific API review and has recent adjacent history on the subagent runtime.

Owner confidence: high

Options:

- **Canonical parent, derived lineage (recommended):** Normalize spawnedBy and parentSessionKey into one authoritative parent relationship, derive root/depth for reads, and avoid a new trace identifier unless a separate lifetime is proven.
- **Persist all four fields:** Add parent, root, depth, and chain trace fields with explicit creation, reset, adoption, access-control, and migration semantics.
- **Defer new contract:** Keep current parent/depth metadata and postpone broader chain APIs and visualization until a durable identity model is selected.

## Reproduction Assessment

Yes, at the source-contract level: current main deterministically shows parent/depth lineage without persisted root or chain-trace fields. This is a missing capability rather than a failing runtime behavior.

## Solution Assessment

No, the four-field proposal is not yet the safest final design because it duplicates derivable lineage and leaves trace lifetime ambiguous; a single canonical parent contract should be chosen first.

## Summary

Keep open: current main provides direct parent/depth lineage and child discovery, but it still lacks a durable root-session and chain-identity contract across multi-hop spawning. The related implementation PR is closed and unmerged, while the merged ACP work exposes only the lineage fields already available from Gateway rows.

## What This Changes

Add canonical parent, root, trace, and depth metadata for spawned sessions and expose it through Gateway and agent-facing session listings.

## Best Possible Solution

Define one immutable canonical lineage model in the session store—direct parent, root session, depth, and a chain-specific identifier distinct from transient diagnostic tracing—derive it consistently in every spawn path, expose it through existing Gateway/tool projections, and cover mixed old/new sessions plus multi-hop spawning.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw persist an immutable root and dedicated chain identifier on each spawned session, or derive lineage from direct parent links and reuse an existing tracing concept?

Rationale: Both approaches can support traversal, but they create different persistence, upgrade, protocol, and diagnostic semantics that cannot be safely selected from implementation details alone.

Likely owner: steipete

Owner reason: They reviewed the exact unresolved contract and have the strongest recent history across the affected session and Gateway boundaries.

Owner confidence: high

Options:

- **Persist dedicated lineage (recommended):** Store immutable rootSessionKey and a session-chain identifier separate from diagnostic trace context, with optional fields for existing sessions.
- **Derive from parent links:** Keep only direct parent and depth metadata, deriving roots and chains during traversal without introducing another persisted identifier.
- **Reuse diagnostic tracing:** Bridge session lineage to an existing trace identifier, accepting tighter coupling between durable orchestration identity and transient observability.

## Reproduction Assessment

Not applicable as a runtime failure; source inspection provides a high-confidence demonstration that direct parent/depth metadata exists while root and stable chain identity remain absent.

## Solution Assessment

Unclear until maintainers choose the authoritative identity semantics. Additive optional fields are plausible, but a dedicated durable chain identifier is safer than overloading transient diagnostic trace context.

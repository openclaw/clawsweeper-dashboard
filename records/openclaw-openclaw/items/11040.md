## Summary

Keep open: current main still has only partial spawned-session lineage and does not implement the requested persisted root session key or durable session-chain trace contract.

## What This Changes

Add first-class spawned-session chain metadata so parent, root, trace, and depth can be reconstructed from session APIs and `sessions_list`.

## Best Possible Solution

Decide the public spawn-chain contract, then land a focused additive implementation that persists root/trace metadata, derives it in native and ACP spawn paths, exposes it in Gateway and agent projections, and documents/tests multi-hop reconstruction.

## Maintainer Decision

Question: Should OpenClaw add public persisted rootSessionKey and session-chain traceId fields for spawned sessions, and should traceId be a new chain id or bridge existing diagnostic trace context?

Rationale: The code change is bounded, but rootSessionKey and traceId would become persisted session and Gateway API contract fields, so automation should not choose the permanent API semantics.

Likely owner: steipete

Owner confidence: high

Options:

- **Add Minimal Spawn-Chain Contract (recommended):** Add optional parent/root/trace/depth semantics for spawned sessions only, with additive schema, projections, docs, and focused tests while leaving traversal APIs for later.
- **Defer To Resolver Lineage Direction:** Keep this open until sessions.resolve lineage semantics are settled, then align spawned-session metadata with that broader contract.
- **Reject Durable Root/Trace Fields:** Keep the current parent/depth behavior and narrow future work to docs or tooling if maintainers do not want a durable chain identifier.

## Reproduction Assessment

Yes, at source level. Current main defines and projects spawnedBy, parentSessionKey, spawnDepth, and childSessions in some paths, but the persistent model, Gateway schema/list rows, agent-facing sessions_list rows, and spawn write paths do not define rootSessionKey or a session-chain traceId.

## Solution Assessment

Unclear until maintainer API direction is set. The requested additive metadata is a plausible bounded solution, but trace semantics and overlap with resolver lineage need a product decision first.

## Summary

Keep open: current main still has only partial direct session lineage, while durable root/trace identity remains absent and TaskFlow now creates a real ownership choice that requires maintainer direction.

## What This Changes

Add durable parent, root, trace, and depth metadata for spawned session chains and expose it through session listing APIs.

## Best Possible Solution

Use one canonical durable orchestration-lineage contract, with explicit mappings between sessions and TaskFlow tasks, then project that identity consistently through gateway, ACP, and agent-facing listing surfaces.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should durable multi-hop lineage be owned by SessionEntry/session APIs, by TaskFlow task records, or by an explicit shared bridge between them?

Rationale: Current main has two partial ownership models—direct session parent/depth metadata and TaskFlow flow/task identity—and repository behavior does not establish which should become the permanent root and trace contract.

Likely owner: steipete

Owner reason: This person has the strongest combined issue-review and central session-boundary history in the available evidence.

Owner confidence: high

Options:

- **Bridge Sessions And TaskFlow (recommended):** Define one shared lineage identity and project it through both session and task APIs without creating independent roots or traces.
- **Session-Owned Lineage:** Persist root and trace identifiers directly on spawned sessions and treat TaskFlow as an optional higher-level consumer.
- **TaskFlow-Owned Lineage:** Keep sessions limited to direct parent/depth metadata and direct durable DAG reconstruction to TaskFlow task APIs.

## Reproduction Assessment

Yes at source level: current main’s persistent session model, gateway projection, and agent-facing listing visibly lack the requested durable root and trace fields. This is a feature gap rather than a failure of an established contract.

## Solution Assessment

No, not without refinement: adding four independent SessionEntry fields is plausible, but it is not clearly the best solution now that TaskFlow owns adjacent durable orchestration identity.

## Label Justifications

- `P2`: This is a normal-priority macOS startup/profile bug with clear source evidence and limited blast radius to users who enable Launch at login from a custom profile env.
- `impact:session-state`: A login-launched app can bind to the default config/state instead of the profile the user enabled autostart from, causing profile and session-state drift.
- `maturity:stable`: The issue affects `macos-gateway-host` Profiles and Isolation / LaunchAgent behavior, and that surface is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and the latest release still emit the macOS app LaunchAgent plist with only `PATH`, while the app profile resolver depends on `OPENCLAW_CONFIG_PATH` and `OPENCLAW_STATE_DIR`. The issue now has open fix candidates, especially https://github.com/openclaw/openclaw/pull/99739 with closing syntax, so this should remain open until one candidate lands or maintainers choose a canonical replacement.

## What This Changes

Preserve the active macOS app profile environment when enabling Launch at login so login-launched OpenClaw uses the same config and state directory.

## Best Possible Solution

Review and land one narrow macOS app LaunchAgent fix that carries the existing non-empty profile env vars, safely serializes plist values, and adds focused Swift plist coverage without changing the separate gateway service env policy.

## Reproduction Assessment

Yes from source inspection, though not from a live login cycle: `LaunchAgentManager.plistContents` emits only `PATH`, while `OpenClawPaths` uses `OPENCLAW_CONFIG_PATH` and `OPENCLAW_STATE_DIR` to select the app profile.

## Solution Assessment

Yes: preserving already-supported env override keys in the app LaunchAgent is the narrow maintainable fix, while the open linked PRs need review and macOS proof before the issue can close.

## Summary

Keep open. The PR targets a real outbound message-ordering bug and has convincing Telegram proof, but it is not merge-ready because the proposed lane key is derived from raw pre-adapter values and the new per-destination mutex is unbounded and abort-unaware.

## What This Changes

Adds an in-memory DeliverySerializer around outbound delivery plus tests for FIFO ordering, cross-target concurrency, error isolation, synchronous throws, and cleanup.

## Best Possible Solution

Land a target-aware serializer that derives lanes from canonical channel/account/thread/recipient identity and cannot hold a lane indefinitely on aborts or stalled adapter sends.

## Reproduction Assessment

Yes, source-backed and proof-backed: current main has no per-destination serializer, and inspected Mantis Telegram screenshots show the baseline inversion and candidate improvement. I did not run a fresh live Telegram repro in this read-only pass.

## Solution Assessment

No as proposed. An in-memory serializer is an acceptable mitigation, but the best fix must derive lanes from canonical delivery targets and bound waits on aborts or stalled adapter sends.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.88

Full review comments:

- **[P1] Derive lanes from canonical delivery targets:** `src/infra/outbound/deliver.ts:1274`
  - body: The lane is built from raw `params.accountId` and `params.to` before adapters resolve the real destination. Discord rewrites threaded sends to `channel:${threadId}`, Discord and account helpers normalize account IDs, and Signal strips a leading `signal:` prefix, so equivalent real recipients can still bypass the mutex while unrelated threads can block each other. Please derive the serializer key from the canonical delivery target, including normalized account and thread/topic identity where it changes the destination.
  - confidence: 0.91
- **[P2] Bound same-target waits on aborts and stalls:** `src/infra/outbound/deliver.ts:1277`
  - body: This wraps the platform send in an unbounded per-lane promise chain. If a send never settles, every later delivery for that lane waits forever; current Discord webhook sends use bare `fetch` without a signal or timeout, and the serializer itself does not release on abort while waiting. Add abort/stall handling and regression coverage before putting all same-target sends behind this lock.
  - confidence: 0.86

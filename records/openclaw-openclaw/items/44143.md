## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.88

Full review comments:

- **[P1] Reuse the existing keyed queue primitive:** `src/infra/outbound/delivery-serializer.ts:9-13`
  - body: `DeliverySerializer` reimplements the same per-key promise-tail queue that already exists as `enqueueKeyedTask`/`KeyedAsyncQueue` in `src/plugin-sdk/keyed-async-queue.ts`. Keeping a second queue implementation here creates drift in cleanup, rejection, and lifecycle behavior for a hot delivery path; use the shared primitive or move any needed bounded-lane behavior into that owner instead.
  - confidence: 0.91
- **[P1] Derive lanes before enqueue from canonical targets:** `src/infra/outbound/deliver.ts:1278-1295`
  - body: This serializer is entered only after `enqueueDelivery(...)` has already completed, so two same-target sends can still invert if the earlier call has a slower queue write and the later call reaches this line first. The key also uses raw `accountId`/`to` instead of the normalized channel target, so equivalent aliases can bypass the lane and distinct thread/topic destinations can be over-serialized; compute the canonical lane before the write-ahead enqueue and include the full routed destination.
  - confidence: 0.9
- **[P2] Bound waits on stalled or aborted deliveries:** `src/infra/outbound/delivery-serializer.ts:39-41`
  - body: Once a task is the tail for a key, every later same-target delivery waits for it to settle. Some transport paths can wait on network work without a propagated abort/timeout, so this can turn one stalled send into a permanent head-of-line block; the lane needs abort-aware waiting and a bounded release/failure path before serializing user-visible replies.
  - confidence: 0.83

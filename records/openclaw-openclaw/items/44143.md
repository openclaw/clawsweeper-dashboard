## Summary

Keep open; the ordering bug is real and the Telegram proof is useful, but this branch is not merge-ready because the serializer does not cover queue enqueue order, keys lanes from raw pre-adapter fields, and can wedge later sends behind stalled or aborted platform sends.

## What This Changes

The PR adds an in-memory DeliverySerializer around outbound delivery plus tests for same-key ordering, cross-key concurrency, error propagation, synchronous throws, and cleanup.

## Best Possible Solution

Land a rebased serializer that orders the entire durable-send path by canonical target, includes thread identity where it changes the real destination, and bounds or cancels waits without dropping current queue recovery behavior.

## Solution Assessment

No. The serializer is a plausible direction, but the best fix needs to cover the full durable-send ordering boundary, use canonical target identity, and avoid unbounded head-of-line blocking.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P1] Acquire the lane before enqueueing delivery:** `src/infra/outbound/deliver.ts:1278`
  - body: The serializer is entered only after `enqueueDelivery(...)` has finished. If two same-recipient sends start together and the earlier send has a slower queue write, the later send can reach this line first and deliver first, so the PR still does not guarantee FIFO by delivery initiation.
  - confidence: 0.92
- **[P1] Derive lanes from canonical delivery targets:** `src/infra/outbound/deliver.ts:1274`
  - body: This key uses raw `accountId` and `to` before adapter normalization and omits `threadId`. Equivalent destinations such as Signal `signal:+...` versus `+...` can bypass serialization, while distinct Discord/Telegram threads can be forced into one lane and block each other.
  - confidence: 0.91
- **[P2] Bound same-target waits on aborts and stalled sends:** `src/infra/outbound/deliver.ts:1278`
  - body: Serializing the whole platform send means one stalled request holds the lane forever; for example Discord webhook sends use `fetch` without a timeout or signal. The serializer needs abort/stall handling so later messages are not wedged behind a cancelled or hung delivery.
  - confidence: 0.85

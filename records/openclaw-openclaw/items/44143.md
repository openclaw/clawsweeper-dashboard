## Summary

Keep open: the outbound ordering bug and Telegram proof are convincing, but this branch is not merge-ready because it duplicates the existing keyed queue primitive, acquires its lane after durable enqueue, and can block later same-recipient sends behind stalled platform work.

## What This Changes

Adds an in-memory outbound `DeliverySerializer` singleton and unit tests for same-key FIFO ordering, cross-target concurrency, failures, synchronous throws, and cleanup.

## Best Possible Solution

Implement outbound ordering through the existing keyed queue primitive at the durable delivery boundary, derive a collision-safe canonical lane before write-ahead enqueue, and make abort or stall behavior explicit for queued waits.

Full review comments:

- **[P1] Reuse the existing keyed queue primitive:** `src/infra/outbound/delivery-serializer.ts:8-14`
  - body: Current main already exports `enqueueKeyedTask`/`KeyedAsyncQueue` with the same per-key serialization, failure isolation, and cleanup semantics. Adding another Promise-tail queue in outbound creates a second source of truth for the same behavior; wire the outbound lane through the existing primitive or extend that primitive if it is missing a required hook.
  - confidence: 0.9
- **[P1] Derive lanes before enqueue from canonical targets:** `src/infra/outbound/deliver.ts:1274-1278`
  - body: The serializer key is built and acquired only inside `deliverOutboundPayloadsWithQueueCleanup`, after `enqueueDelivery(...)` has already awaited. If an earlier same-target send has slower queue I/O than a later send, the later call reaches this mutex first and can still deliver first; derive a canonical lane before queue admission and run both enqueue and send under that lane.
  - confidence: 0.9
- **[P2] Bound serialized waits on aborts and stalls:** `src/infra/outbound/deliver.ts:1278`
  - body: This queue waits for the previous same-lane send without any abort or timeout path. A Discord webhook send currently awaits `fetch` without a signal, so one stalled platform request can wedge every later reply to that recipient until restart; add bounded wait/abort handling or avoid serializing behind work that can no longer make progress.
  - confidence: 0.86

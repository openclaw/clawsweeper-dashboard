## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P1] Reuse the existing keyed queue primitive:** `src/infra/outbound/delivery-serializer.ts:9-13`
  - body: This adds a second per-key Promise-tail queue even though current main already has `enqueueKeyedTask` and `KeyedAsyncQueue` for the same serialization contract. Keeping a parallel serializer will make cleanup, rejection, cancellation, and future queue semantics drift; reuse the existing helper and keep only outbound-specific lane derivation here.
  - confidence: 0.86
- **[P1] Derive lanes before enqueue from canonical targets:** `src/infra/outbound/deliver.ts:1274`
  - body: The mutex key is built from raw `channel`, `accountId`, and `to`, and the lock is acquired only after `enqueueDelivery`. An earlier same-target send can lose the queue-write race to a later send, and adapters later canonicalize account, recipient, and thread identity, so equal chats can still race while unrelated threads can block each other. Derive and acquire the lane from canonical account, recipient, and thread identity before queue I/O or platform send.
  - confidence: 0.9
- **[P2] Bound serialized waits on aborts and stalls:** `src/infra/outbound/deliver.ts:1278-1279`
  - body: The serializer releases the key only after `deliverOutboundPayloadsCore` settles. A hung Discord webhook fetch or an already-aborted send waiting behind a long same-target send can now hold the lane and block every later reply to that chat; before this patch those later sends could still proceed independently. Add abort-aware waiting and a bounded stall policy before serializing production traffic.
  - confidence: 0.86

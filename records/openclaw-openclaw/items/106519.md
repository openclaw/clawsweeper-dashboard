## Label Justifications

- `P1`: The current failure mode can leave a live Codex app-server workflow waiting indefinitely with no transport exit or retry path.
- `merge-risk: 🚨 compatibility`: A fixed 30-second upgrade cutoff can break existing slow remote app-server connections that previously remained pending and could eventually connect.
- `merge-risk: 🚨 availability`: If the fixed deadline is too short for a deployment's proxy or network, Codex runs can repeatedly fail to establish their transport.

## Summary

The patch is coherent and strongly proven, but this PR should remain open until the Codex transport owner confirms that every WebSocket and Unix-socket connection should gain an unconditional, non-configurable 30-second establishment deadline; that new policy can reject slow but previously viable remote app-server connections.

## What This Changes

The PR adds a shared 30-second WebSocket upgrade timeout for Codex app-server TCP and Unix transports, guards optional transport error forwarding, and adds stalled-peer regression and real-socket proof coverage.

## Best Possible Solution

Use one owner-approved connection-establishment deadline for both TCP and Unix WebSocket paths, retain the stalled-peer and healthy-roundtrip coverage, and document the deadline semantics if operators are expected to rely on remote app-server connections.

Question: Should Codex app-server WebSocket and Unix connection establishment use an unconditional 30-second deadline, or should that deadline derive from an existing owner-approved timeout budget?

Rationale: Current behavior has no connection-establishment deadline, while the documented 60-second `requestTimeoutMs` applies to control-plane calls after connection; choosing a fixed 30-second cutoff therefore changes compatibility and operator expectations rather than merely correcting an implementation detail.

Owner confidence: high

Options:

- **Approve the fixed 30 seconds (recommended):** Keep the bounded shared constant because it avoids new config, matches established handshake floors, and gives stalled connections a deterministic failure path.
- **Reuse the request budget:** Pass the resolved app-server request timeout into transport creation so operators retain one timeout budget, while explicitly documenting that it now also bounds connection establishment.
- **Add a connection-specific setting:** Introduce a dedicated plugin-owned connection timeout only if remote deployments demonstrably require independent tuning and the added config surface is accepted.

## Reproduction Assessment

Yes. A real TCP peer that accepts the socket but never returns a WebSocket upgrade leaves raw `ws` in `CONNECTING`, while the patched production transport exits near the injected short deadline and causes `initialize()` to reject.

## Solution Assessment

Yes for the mechanism, but maintainer confirmation is still required for the policy. Using `ws`'s native handshake timeout at the shared TCP/Unix constructor is the narrowest implementation, while the exact fixed deadline remains an owner decision.

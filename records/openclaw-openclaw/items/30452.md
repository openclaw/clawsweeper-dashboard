## Summary

Keep open: current main and v2026.6.11 already cover the compaction and memory-flush model override parts, but the requested flush-then-reset mode is still absent and needs maintainer product/security direction.

## What This Changes

Request configurable model overrides for compaction and memory flush plus an optional flush-then-reset mode that skips compaction after durable memory flush.

## Best Possible Solution

Keep the shipped override behavior, then define one maintainer-approved compaction-threshold reset policy aligned with reset-memory lifecycle work before adding a default-off config surface.

Options:

- **Design Unified Reset-Memory Policy First (recommended):** Keep this issue open and align compaction-threshold reset mode with #45608 so explicit, daily, idle, and compaction-pressure resets share one bounded policy.
- **Add Default-Off resetAfterFlush:** Approve a narrow default-off memoryFlush.resetAfterFlush mode with explicit provider, timeout, notification, and regression proof requirements.
- **Reject Automatic Reset After Flush:** Keep compaction as the canonical context-preservation path and rely on model overrides, memory flush, and manual reset flows for cost control.

## Reproduction Assessment

Yes, at source level: current main has the two model override knobs but the strict schema and runtime have no resetAfterFlush or successful-flush reset path; this is a feature gap, not a broken existing behavior repro.

## Solution Assessment

Unclear: the model override pieces are already solved, but flush-then-reset is only a plausible solution until maintainers choose reset timing, durable-memory sufficiency, provider/auth policy, and user-visible recovery semantics.

## Summary

Keep open: this quality-of-life feature is still necessary on current main, where URL-bearing tool output remains text in both Control UI tool cards and native WebChat. The two linked Control UI attempts were closed unmerged, and maintainers need to set the delivery boundary—especially whether native WebChat must match—before a replacement implementation proceeds. Likely related people: Chris Zhang and steipete, both with medium-confidence history signals.

## What This Changes

Render safe, clickable HTTP(S) URLs embedded in tool-result cards in the Control UI and, if in scope, native WebChat while preserving the visible raw output.

## System Context

Tool calls produce structured or plain-text results that are routed into chat tool cards rather than ordinary assistant-message Markdown. Those cards currently preserve output as text for Control UI and SwiftUI WebChat, so URL values do not become interactive links for users reviewing web and browser results.

## Architecture Diagram

flowchart LR
  A[Tool result text] --> B[Tool output card data]
  B --> C{Safe URL presentation}
  C --> D[Control UI cards]
  C --> E[Native WebChat cards]
  D --> F[Clickable browser links]
  E --> F

## Best Possible Solution

Confirm whether native WebChat parity is required, then implement one safe URL-token presentation contract per client that preserves raw text and copy behavior, allows only HTTP(S) targets, handles punctuation correctly, and covers every tool-output presentation path.

## Solution Assessment

No—the proposed field-name regex plus HTML-string injection is not the best general solution. A safe URL-token renderer with an explicit client-parity decision is narrower, avoids trusting arbitrary tool text as markup, and covers URLs outside a small list of JSON keys.

## Summary

Keep open: current main and the latest release still intentionally flatten remote Markdown image URLs and block remote browser image fetches, so changing this behavior needs a Control UI remote-media security/product decision rather than conservative cleanup.

## What This Changes

Request to render remote http/https Markdown image URLs inline in Control UI chat instead of flattening them to alt text.

## Best Possible Solution

Define the approved Control UI remote-media policy first, then either keep the current no-remote-fetch behavior or update renderer, CSP, docs, tests, and browser proof together.

Question: Should Control UI render remote http/https Markdown image URLs from chat content, and if so should that be direct browser fetch, proxy-mediated, or operator opt-in?

Rationale: Current code, tests, docs, and merged hardening intentionally prevent remote browser image fetches, while the request improves UX by changing that security boundary.

Likely owner: drobison00

Owner confidence: high

Options:

- **Keep no-remote-fetch default (recommended):** Preserve same-origin, data, and blob image rendering until an explicit proxy or opt-in design is approved.
- **Approve direct remote images:** Accept the privacy/read-receipt tradeoff and require coordinated renderer, CSP, docs, tests, and browser proof updates.
- **Design mediated media path:** Treat remote images as structured media that can be proxied, consent-gated, or opened explicitly rather than fetched silently on render.

## Reproduction Assessment

Yes, at source level: current main routes Markdown images through a renderer that flattens non-data image URLs, and tests assert that behavior. I did not run live browser proof in this read-only review.

## Solution Assessment

No for the suggested renderer-only fix. The maintainable path needs an explicit remote-media trust policy and coordinated renderer, sanitizer, CSP, docs, tests, and browser proof rather than only allowing http(s) image src values.

## Label Justifications

- `P2`: This is a normal-priority Control UI UX and security-policy issue with no outage, data loss, or crash evidence.
- `impact:security`: The requested behavior changes whether untrusted chat content can cause an operator browser to fetch arbitrary remote image URLs.
- `impact:ux-friction`: Users expecting inline remote images see alt text instead and must use another viewing path.

## Summary

Keep open: current main, docs, tests, and the latest release still intentionally flatten remote Markdown image URLs and block remote Control UI image fetches, so this is a product/security policy decision rather than conservative cleanup.

## What This Changes

The issue asks for Control UI chat Markdown image syntax using remote `http` or `https` URLs to render inline instead of being flattened to alt text.

## Best Possible Solution

Define the approved Control UI remote-media policy first, then either keep the current no-remote-fetch behavior or implement a coordinated renderer, CSP, docs, tests, and browser-proof update.

- **Design click-to-load or proxy media:** Support inline media without automatic third-party browser fetches by adding a controlled proxy or user action first.

Yes. Source inspection reproduces the behavior: the active renderer returns alt text for non-`data:image` sources, and tests assert that remote `https://` image Markdown does not produce `<img>`; I did not run live browser proof in this read-only review.

## Solution Assessment

No for the suggested renderer-only fix. The maintainable path needs an explicit remote-media trust policy and coordinated renderer, CSP, docs, tests, and browser proof rather than only allowing `http(s)` image src values.

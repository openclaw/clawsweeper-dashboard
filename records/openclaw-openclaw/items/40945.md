## Summary

Keep open: current main and the latest release still intentionally flatten remote Markdown image URLs and enforce a Control UI no-remote-image-fetch policy, so this is a security/product decision rather than conservative cleanup.

## What This Changes

The issue requests rendering remote `http/https` image URLs inline in Control UI chat Markdown instead of flattening them to alt text.

## Best Possible Solution

Define the approved Control UI remote-media policy first, then either keep the no-remote-fetch default or land a coordinated renderer, sanitizer/CSP, docs, tests, and browser-proof change together.

Options:

- **Keep no-remote-fetch default (recommended):** Preserve the current default and require same-origin media, local blob/data images, or an explicitly approved proxy/opt-in design before rendering remote images.
- **Allow direct remote images:** Accept the privacy and tracking tradeoff, then update the renderer, sanitizer attributes, CSP, docs, tests, and browser proof together.
- **Fold into inline media policy:** Let the broader inline-media work at https://github.com/openclaw/openclaw/issues/64607 explicitly accept or reject remote Markdown images before this focused behavior changes.

Yes, at source level: current main routes Markdown images through a renderer that flattens non-data image URLs, and tests assert that behavior. I did not run a live browser session in this read-only review.

## Solution Assessment

No for the suggested renderer-only fix. The maintainable path needs an explicit remote-media trust policy and coordinated renderer, sanitizer, CSP, docs, tests, and browser proof rather than only allowing `http(s)` image `src` values.

## Label Justifications

- `P2`: The issue is a real Control UI product/security tradeoff with limited blast radius, not a release-blocking setup failure.
- `impact:security`: The requested behavior would allow untrusted chat content to cause remote browser image fetches from the operator's Control UI session.
- `impact:ux-friction`: Users who expect Markdown image URLs to preview inline currently see only alt text or fallback text.

## Summary

Keep open: current main and the latest release intentionally flatten remote Markdown images and enforce a Control UI CSP that blocks remote image loads. Satisfying this request would change a documented no-remote-browser-fetch security boundary, so it needs maintainer product/security direction rather than conservative cleanup.

## What This Changes

Allow Control UI/WebChat Markdown image syntax with remote http/https sources to render inline instead of flattening to alt text.

## Best Possible Solution

Decide the remote image policy first; if accepted, implement an explicit operator-controlled path such as an allowlist, proxy, or setting while preserving the default no-remote-fetch behavior and updating renderer, CSP, docs, and tests together.

Rationale: Current code, tests, and docs intentionally prevent remote image fetches; reversing that default changes the operator-browser privacy boundary and cannot be decided by cleanup automation.

Likely owner: drobison00

Owner confidence: high

Options:

- **Keep Default Deny:** Keep flattening remote Markdown images and close or redirect this request to the broader inline media policy discussion if maintainers do not want browser remote fetches.
- **Add Controlled Opt-In (recommended):** Preserve the default block but add a maintainer-approved allowlist, proxy, or setting with tests and docs for both blocked and enabled modes.
- **Allow Direct http/https Images:** Render remote images directly and relax CSP, accepting that assistant text can make the operator browser contact arbitrary image hosts.

## Reproduction Assessment

Yes, source inspection and current tests provide a high-confidence reproduction path: remote `https://` Markdown image sources are converted to alt text while `data:image/...` sources render inline. I did not run a live browser session in this read-only cleanup review.

## Solution Assessment

No, the suggested direct http/https renderer pass-through is not the best fix by itself because current CSP/docs intentionally block remote image fetches. The maintainable solution needs an explicit security/product policy, likely default-deny with an opt-in allowlist or proxy if maintainers accept the feature.

## Summary

Keep open: current main and the latest release still intentionally flatten remote Markdown image URLs and block remote Control UI image fetches, so the requested behavior remains missing and needs maintainer product/security direction rather than cleanup.

## What This Changes

The issue asks for Control UI chat markdown to render remote http/https image URLs inline instead of flattening them to alt text.

## Best Possible Solution

First decide the approved Control UI remote-media policy, then either keep the current no-remote-fetch behavior or rework the linked implementation path into a coordinated renderer, CSP, docs, tests, and browser-proof change.

Owner confidence: high

Options:

- **Keep no-remote-fetch default (recommended):** Preserve the current secure default and require same-origin, data/blob, explicit open/download, or a future approved media surface for remote content.
- **Add opt-in remote image rendering:** Approve an operator-controlled setting or allowlist and update renderer, CSP, docs, tests, and browser proof together so the fetch behavior is explicit.
- **Design click-to-load or proxy media:** Support inline media without automatic third-party browser fetches by adding a controlled proxy or user action first.

Yes. Source inspection gives a high-confidence reproduction path: the active renderer returns alt text for non-data image sources, adjacent tests assert that behavior, and chat rendering uses that shared renderer.

## Solution Assessment

No for the suggested renderer-only fix. The maintainable path needs an explicit remote-media trust policy and coordinated renderer, CSP, docs, tests, and browser proof rather than only allowing http(s) image src values.

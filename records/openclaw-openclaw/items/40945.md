## Summary

Keep open: current main and the latest release still intentionally flatten remote Markdown images and block remote Control UI image fetches, so this needs a maintainer product/security decision rather than cleanup.

## What This Changes

The issue requests that Control UI chat render Markdown image syntax with remote `http/https` URLs inline instead of degrading it to alt text.

## Best Possible Solution

Define the approved Control UI remote-media policy first, then either keep the current no-remote-fetch behavior or implement an approved renderer, CSP, docs, tests, and browser-proof update together.

Options:

- **Keep no-remote-fetch default (recommended):** Preserve the current default and require same-origin media, data/blob URLs, or an explicit proxy/opt-in design before rendering remote images.
- **Allow direct remote images:** Accept the privacy/tracking tradeoff and update the renderer, sanitizer attributes, CSP, docs, tests, and browser proof together.
- **Fold into inline-media policy:** Resolve this focused case through the broader inline-media issue only after that issue explicitly accepts or rejects remote Markdown images.

## Reproduction Assessment

Yes, at source level: current main routes Markdown images through a renderer that flattens non-data image URLs, and tests assert that behavior. I did not run live browser proof in this read-only review.

## Solution Assessment

No for the suggested renderer-only fix. The maintainable path needs an explicit remote-media trust policy and coordinated renderer, sanitizer, CSP, docs, tests, and browser proof rather than only allowing http(s) image src values.

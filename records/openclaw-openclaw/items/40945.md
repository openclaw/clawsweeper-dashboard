## Summary

Keep open: current main and the latest stable release still intentionally flatten remote Markdown images and the Gateway CSP blocks remote image loads, so this is a real remaining feature request that needs a product/security decision rather than cleanup closure.

## What This Changes

The issue requests that Control UI chat markdown render remote HTTP/HTTPS image URLs inline instead of flattening them to alt text.

## Best Possible Solution

Keep the current no-remote-fetch default unless maintainers approve an operator-controlled inline-media design, preferably capability-gated or proxied rather than raw remote Markdown image loads.

## Maintainer Decision

Kind: product_direction

Question: Should Control UI chat support remote Markdown images, and if yes should that be direct browser http(s) loading or an explicit/proxied opt-in media path?

Rationale: Current shipped code and tests intentionally block the requested behavior for security/privacy reasons, so automation should not reverse that policy without maintainer intent.

Likely owner: steipete

Owner confidence: medium

Options:

- **Keep safe default and design an explicit media path (recommended):** Leave remote Markdown images flattened by default and pursue inline media through a capability-gated, proxied, allowlisted, or opt-in design that names the browser-fetch risk.
- **Allow direct remote Markdown images:** Accept that model-provided markdown can cause browser requests to arbitrary image hosts and update the renderer, CSP, tests, and docs accordingly.
- **Close as not planned:** Decide that arbitrary remote Markdown images should remain unsupported and point users to managed media attachments or future inline-widget work instead.

## Reproduction Assessment

Yes, at source level: current main routes Markdown images through a renderer that flattens non-data image URLs, and adjacent tests assert that behavior. I did not run a live browser session in this read-only review.

## Solution Assessment

Unclear as requested: allowing remote http(s) images directly is a plausible UX fix but not clearly the best solution because it conflicts with current security hardening and CSP. The safer solution needs maintainer-approved policy for explicit, proxied, allowlisted, or opt-in inline media.

## What This Changes

The PR adds `api.runtime.talk.watch`, a Plugin SDK observer that sends plugins anonymous Talk lifecycle, state, and speech-pulse events for ambient voice UI.

## System Context

Talk clients and relays send canonical events through the shared Talk session controller. This PR records those events in a process-wide activity registry and exposes them through the Plugin SDK to ambient UI plugins.

## Best Possible Solution

Define and approve the observation trust boundary first, then expose Talk activity only through a declared capability or an owner/session-scoped subscription with tests proving unauthorized plugins receive no cross-owner events.

Owner confidence: medium

Options:

- **Require scoped observation (recommended):** Expose activity only to a plugin with an explicit reviewed capability and bind events to the session or route it owns.
- **Approve global observation:** Document that all loaded plugins may observe anonymous process-wide Talk activity and accept this as a permanent Plugin SDK privacy contract.
- **Defer the SDK surface:** Keep the activity recorder internal until a supported plugin trust model and consumer need are approved.

## Reproduction Assessment

Yes, from source: register a plugin watcher, start Talk from a different plugin or client, and the process-global watcher registry forwards that other session’s anonymous events. The branch tests establish event delivery and redaction but do not establish cross-plugin isolation.

## Solution Assessment

No. The payload is appropriately narrow, but a global unscoped listener is not the narrowest safe solution because it still exposes cross-plugin behavioral metadata; a declared capability or owner/session-scoped API is safer.

## Summary

Keep open. Current main has route-preservation substrate, but it still lacks the requested force-origin/fallback policy and keeps internal WebChat/dashboard routes gated unless an explicit delivery route is present; the linked persisted-origin PR is closed unmerged and multiple comments report continuing channel-visible reply loss.

## What This Changes

Request to force final agent replies from messaging-channel turns back to the originating Telegram, Discord, WhatsApp, or similar channel, with fallback behavior when origin is unclear.

## Best Possible Solution

Define a durable turn-origin delivery invariant that carries channel, target, account, and thread through agent, tool, ACP, and queued follow-up paths, then add fallback or mirroring only behind an explicit maintainer-approved security policy.

## Reproduction Assessment

Yes, source-level. Current main still gates origin routing on non-internal WebChat, a present routable target, and origin differing from current surface, while Gateway WebChat clients do not inherit external routes; I did not run a live channel reproduction.

## Solution Assessment

No, the proposed unconditional force/fallback config is not yet the best fix. The safer solution is a sticky turn-origin route plus explicit, security-reviewed fallback policy rather than a broad default that can leak to stale external chats.

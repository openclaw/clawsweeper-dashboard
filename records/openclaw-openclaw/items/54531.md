## Summary

Keep open. Current main has partial origin-route preservation for explicit delivery, session-send handoffs, and channel-scoped UI delivery, but it still intentionally blocks some webchat/internal inheritance paths, has no force-origin/fallback policy, and related open reports show the delivery-loss class is still active.

## What This Changes

The issue requests reliable delivery of generated agent replies back to the originating Telegram, Discord, WhatsApp, or similar channel, with a proposed force-origin/fallback routing configuration.

## Best Possible Solution

Define a maintainer-approved origin-delivery invariant that preserves an explicit per-turn target and delivery receipt without reintroducing unsafe cross-surface mirroring; add config only if the policy cannot be expressed safely by current route metadata and send-policy controls.

## Reproduction Assessment

Yes for source-level reproduction: current main still has explicit routing gates that can keep internal/webchat turns from inheriting external routes, and tests assert several blocked inheritance cases. I did not perform a fresh live channel run in this read-only review.

## Solution Assessment

No: the requested force-origin config is a plausible workaround, but not proven to be the best fix because it overlaps with security-sensitive cross-context delivery and delivery-receipt policy. A sticky per-turn route plus explicit delivery status/reconciliation is the safer product direction to settle first.

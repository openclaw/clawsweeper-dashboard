## Summary

Keep open. Current main and v2026.6.11 still have the internal-WebChat and same-surface routing gates, the requested force/fallback reply policy is not implemented, and related reports show this remains a live channel-delivery policy and security-boundary decision.

## What This Changes

The issue requests a force-originating-channel reply behavior, with optional fallback routing, so generated agent replies reliably return to the messaging channel that originated the turn.

## Best Possible Solution

Define a safe turn-origin delivery invariant that preserves the captured channel, target, account, and thread through agent, ACP, tool, and queued follow-up paths; make fallback or mirroring an explicit maintainer-approved policy with security coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw automatically deliver final replies to a captured originating external route across internal/dashboard contexts, and should any fallback channel be allowed when the origin is missing or stale?

Rationale: This is not just a mechanical routing bug: the chosen default can intentionally publish internal replies to external chats selected from stored or inferred state, so maintainer intent is needed before changing the boundary.

Likely owner: Peter Steinberger

Owner reason: The central reply-dispatch, outbound message policy, and security-boundary history most strongly route this decision to Peter Steinberger among the identified owners.

Owner confidence: medium

Options:

- **Define a sticky turn-origin invariant (recommended):** Capture the inbound route at turn start and deliver ordinary final replies to that route unless an explicit policy suppresses or redirects delivery, with tests and live channel proof.
- **Add default-off force/fallback config:** Expose explicit operator-controlled force-origin and fallback settings, but keep current defaults until route freshness, authorization, and failure semantics are documented.
- **Keep explicit delivery only:** Leave internal WebChat/dashboard replies isolated from external routes unless callers set ExplicitDeliverRoute or use the message tool, and document that boundary.

## Reproduction Assessment

Yes, source-reproducible. Current routing code and tests show internal WebChat/dashboard turns do not route to an external origin without ExplicitDeliverRoute, while the issue discussion includes repeated Telegram, Discord, and Tlon reports.

## Solution Assessment

No, the raw force/fallback config is not clearly the best solution yet. The safer fix is a durable turn-origin route invariant plus an explicit maintainer-approved fallback or mirroring policy.

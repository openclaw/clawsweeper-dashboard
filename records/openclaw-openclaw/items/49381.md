## Summary

Keep open: current main still leaves the reported Feishu failover/final-delivery coordination problem unresolved, and the related candidate fixes are closed unmerged rather than canonical landing paths.

## What This Changes

The issue asks for Feishu failover final-reply coordination so one inbound DM cannot produce duplicate final assistant replies after a rate-limited primary model falls back.

## Best Possible Solution

Define the owner-level invariant for failover recovery first, then land a focused fix that suppresses failed-attempt finals in Feishu streaming and shared non-streaming final dispatch without dropping legitimate distinct replies.

## Reproduction Assessment

Yes, source-level: the current Feishu dispatcher still closes streaming state on final delivery errors, and shared final dispatch still sends every reply entry without a per-turn final-dedupe guard. I did not run a live Feishu rate-limit failover in this read-only review.

## Solution Assessment

Unclear until maintainer direction is set: a Feishu-only streaming change would cover the visible card case, while the streaming-disabled logs point to a shared final-dispatch invariant too. The best fix should define that invariant before choosing the exact owner boundary.

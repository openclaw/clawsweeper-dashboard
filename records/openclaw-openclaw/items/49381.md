## Summary

Keep open: current main and the latest release still allow the Feishu failover/error-recovery path to expose more than one visible final reply, while the direct candidate PR is closed unmerged and the broader related issues do not fully own this failover duplicate-final variant.

## What This Changes

The issue reports that a single Feishu DM can produce duplicate final assistant replies when a rate-limited primary model fails over to a secondary model.

## Best Possible Solution

Land one focused Feishu/final-delivery coordination fix that suppresses failed-attempt visible finals once a recovered fallback final is delivered, while preserving intentional distinct finals and proving the behavior with regression tests plus redacted live Feishu failover evidence.

## Reproduction Assessment

Yes at source level, but not as a live replay: the issue includes sanitized one-inbound-message Feishu failover logs, and current main tests still preserve visible later finals after error closeout. I did not run a credentialed Feishu plus provider-failover reproduction in this read-only review.

## Solution Assessment

Unclear on the exact owner boundary: a cooldown/config knob is not the best fix, and maintainers need to choose a Feishu-local versus shared final-dispatch repair that preserves intentional distinct finals. The closed candidate PR shows a useful direction but is not a safe landing path as submitted.

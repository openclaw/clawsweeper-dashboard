## Summary

Keep open: current main and v2026.6.11 still allow the Feishu error/failover closeout shape to expose more than one visible final reply, while the direct candidate PR is closed unmerged and related issues only partially overlap.

## What This Changes

The issue asks OpenClaw to prevent one Feishu DM from producing duplicate final assistant replies when a rate-limited primary model falls back to a secondary model.

## Best Possible Solution

Land or adopt one focused Feishu/final-delivery coordination fix that treats failed-primary plus recovered-fallback output as one user-visible turn while preserving intentional distinct diagnostics, with regression tests and redacted live Feishu failover proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw treat an errored primary attempt plus recovered fallback as one user-visible Feishu final, and should the guard live in Feishu streaming closeout, shared final-dispatch identity, or the broader durable delivery contract?

Rationale: Current code intentionally preserves some later finals after errors, so an automated fix could either suppress useful diagnostics or leave the duplicate-failover path unresolved without maintainer intent.

Likely owner: steipete

Owner reason: They have the strongest recent merged history in the Feishu error-final dispatcher surface and adjacent review context.

Owner confidence: high

Options:

- **Narrow Feishu recovery guard (recommended):** Make Feishu keep or replace the errored-attempt card during transient failure and deliver only the recovered fallback final for the user turn, with explicit exceptions for distinct diagnostics.
- **Shared final identity contract:** Define a dispatcher-level same-turn final identity so all channels collapse failed-attempt/recovered-fallback duplicates while preserving intentionally distinct finals.
- **Fold into durable delivery roadmap:** Track this only under the broader durable final-delivery contract and defer a Feishu-local fix until that contract is designed.

Yes at source level, but not as a live replay. The issue includes sanitized one-inbound-message Feishu failover logs, and current main tests still preserve later visible finals after error closeout.

## Solution Assessment

Unclear on the exact owner boundary. A cooldown or config knob is not the best fix; maintainers should choose a Feishu-local versus shared final-dispatch repair that preserves intentional distinct finals.

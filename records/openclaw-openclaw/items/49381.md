## Summary

Keep open: current main has partial Feishu duplicate suppression, but the reported failover/error-recovery class is still not fully settled, especially for non-streaming distinct finals and Feishu error-closeout recovery paths. Related PRs for this exact symptom are closed unmerged, while broader delivery-contract issues only partially overlap.

## What This Changes

The issue reports duplicate Feishu final replies after a rate-limited primary model falls back to a secondary model.

## Best Possible Solution

Define a Feishu/shared final-delivery coordination rule that exposes only the accepted recovered final for one inbound failover turn while preserving explicit partial-failed or recovery outcomes, then prove it with focused tests and redacted live Feishu failover evidence.

## Reproduction Assessment

Yes at source level: the issue has sanitized one-inbound-message failover logs, and current tests/source still permit multiple visible finals in Feishu error-closeout and non-streaming distinct-final paths. No live Feishu provider-failover replay was run in this read-only review.

## Solution Assessment

Unclear on exact owner: cooldown knobs or a broad unconditional one-final guard are not the best fix by themselves. Maintainers need to choose the shared final-delivery contract versus a Feishu-local guard so recovered finals stay visible without leaking failed-attempt finals.

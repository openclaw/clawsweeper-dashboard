## Summary

Keep open: current main still preserves the Feishu error-closeout shape where an errored final and a later recovered final can both become visible, and the direct candidate PRs are closed unmerged while related issues only partially cover the failover-specific duplicate-final path.

## What This Changes

The issue reports that one Feishu direct message can produce duplicate final assistant replies when a rate-limited primary model fails and a fallback model succeeds.

## Best Possible Solution

Land or adopt a focused Feishu/final-delivery coordination fix that treats failed-primary plus recovered-fallback output as one user-visible turn while preserving intentional distinct diagnostics, with regression tests and redacted live Feishu failover proof.

Options:

- **Narrow Feishu Recovery Guard (recommended):** Make Feishu keep or replace the errored-attempt card during transient failure and deliver only the recovered fallback final for that user turn, with explicit exceptions for distinct diagnostics.
- **Shared Final Identity Contract:** Define dispatcher-level same-turn final identity so all channels collapse failed-attempt/recovered-fallback duplicates while preserving intentionally distinct finals.
- **Fold Into Durable Delivery Roadmap:** Track this only under the broader durable final-delivery contract and defer a Feishu-local fix until that cross-channel contract is designed.

Yes at source level, but not as a live replay. The issue includes sanitized one-inbound-message Feishu failover logs, and current main still has tests and code paths that preserve a later visible final after error closeout.

Unclear on the exact owner boundary. A cooldown or config knob is not the best fix; maintainers should choose a Feishu-local versus shared final-dispatch repair that preserves intentional distinct finals.

## Summary

Keep open. Current main and v2026.6.11 still do not accept or enforce binding-scoped tool policy, and the remaining question is a real security/product contract decision rather than stale cleanup.

## What This Changes

The issue requests declarative per-binding `tools.allow`/`tools.deny` restrictions for route/ACP bindings so selected channels or groups can deny tools such as `sessions_spawn`.

## Best Possible Solution

Define one maintainer-approved scoped tool-policy contract that either implements binding policy end to end across schema, types, routing/ACP propagation, enforcement, docs, and tests, or documents existing group/sender/session policy as the supported boundary.

Rationale: This adds a new public security-control config surface and precedence model across route matching, ACP bindings, Gateway tool resolution, embedded-agent tool construction, and existing policy layers; automation cannot safely choose that contract.

Options:

- **Design binding-scoped policy (recommended):** Keep this issue open and approve an end-to-end binding policy contract with precedence, enforcement, docs, and regression proof before implementation.
- **Use existing policy surfaces:** Decline the new binding key and document group/channel, sender, session, and per-agent policy as the supported way to restrict tools.
- **Defer to identity/session work:** Block this on the broader scoped session or conversation identity design if maintainers want one authorization model instead of a binding-specific slice.

## Reproduction Assessment

Yes. Source inspection on current main and v2026.6.11 shows strict route and ACP binding schemas reject the requested `tools` field; no live Gateway startup was run in this read-only cleanup review.

## Solution Assessment

Unclear for the proposed shape. A schema-only change is not the best fix; the maintainable solution needs either complete enforcement through the tool-policy pipeline or clear documentation that existing group/sender/session policy is the supported boundary.

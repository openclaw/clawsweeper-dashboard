## Summary

Keep open: current main and v2026.6.11 still lack a native `registerMcpServer` Plugin SDK API, and the only direct implementation PR is closed unmerged. The external `kevinslin/openai-apps` motivation is credible, but this remains a maintainer product and security decision because it would add a public plugin-managed MCP process-launching surface.

## What This Changes

Add a native Plugin SDK API for plugins to register managed MCP servers that OpenClaw can inject into embedded OpenAI-backed runs.

## Best Possible Solution

A maintainer-sponsored design should either define a narrow, additive, validated Plugin SDK MCP registration contract or explicitly keep dynamic MCP exposure outside core until the security model is settled.

## Reproduction Assessment

Not applicable; this is a feature request, not a report of broken existing behavior. Source inspection confirms the requested SDK method is absent while current MCP support is bundle/config based.

## Solution Assessment

Unclear until maintainer product and security review. A native Plugin SDK seam may be the right direction for dynamic account-state inventories, but the execution boundary and public API shape need explicit approval.

## Risks / Open Questions

- A native MCP registration API would let plugin code ask OpenClaw to manage stdio MCP process launches, expanding command execution and tool exposure boundaries.
- The product decision is still open: dynamic native plugin MCP registration may be justified for account-state inventories, but static bundle/config MCP remains the safer supported route when it can express the capability.
- A future implementation must preserve manifest-first discovery, operator visibility, validation, workspace scoping, user/operator MCP precedence, and clear security review for launched processes.

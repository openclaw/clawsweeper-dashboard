## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded Slack config/product decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native command names can route a command to the wrong Slack app, so commands may not reach the intended agent.
- `impact:session-state`: The affected commands include reset, compact, and stop, which directly alter agent/session state when routed to the wrong agent.

## Summary

Keep open: current main and v2026.6.11 still have only provider-scoped Slack native command names and no account-level native command naming contract, so the reported multi-app Slack slash-command collision remains. The prior prefix and nativeNames implementation PRs are closed unmerged, and the remaining blocker is the supported config/API shape.

## What This Changes

Request account-level Slack native slash-command naming so multiple Slack apps or agents in one workspace can register distinct commands without collisions.

## Best Possible Solution

Adopt one validated account-level Slack native command naming contract, preferably explicit nativeNames mapping unless maintainers deliberately choose prefix sugar, and cover registration, dispatch, arg-menu callbacks, schema, docs, and tests in one Slack plugin change.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack multi-account native slash commands be solved with validated account-level nativeNames mapping, constrained nativePrefix sugar, or documented as unsupported for duplicate native command names?

Rationale: Current main has no account-level naming contract, and the two prior unmerged PRs show a real design fork between prefix convenience and explicit mappings; either implementation adds user-visible Slack config/API surface.

Likely owner: steipete

Owner reason: steipete has the strongest history signal on the shared native command registry and Slack provider override behavior that this product contract would change.

Owner confidence: high

Options:

- **Implement Validated nativeNames (recommended):** Add explicit per-account native command mapping with duplicate and Slack-format validation, registration, reverse lookup, arg-menu callback support, docs, and focused tests.
- **Implement Constrained nativePrefix:** Add prefix sugar only with strict lowercase slug validation and no broad dash-stripping fallback, accepting a simpler UX but a second naming abstraction.
- **Document Unsupported Duplicate Names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names, preserving the current config surface at the cost of this workflow.

## Reproduction Assessment

Yes, at source level: current main has no account-level Slack native command naming field, and registration/lookup are provider-scoped. I did not run a live multi-app Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but a validated explicit nativeNames mapping appears safer than implicit prefix aliases under the repository's config-surface policy and prior PR direction.

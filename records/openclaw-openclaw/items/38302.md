## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native slash command names can route a command to the wrong app, so the intended agent may never receive it.
- `impact:session-state`: The ambiguous commands include reset, compact, and stop, which directly affect agent/session state.

## Summary

Keep open: current main still has provider-scoped Slack native command names, no account-level `nativePrefix` or `nativeNames` field in the strict Slack slash-command config, and both implementation attempts are closed unmerged. The remaining blocker is maintainer product/API direction for the supported Slack account-level native naming contract.

## What This Changes

The issue requests account-level native slash-command naming so separate Slack apps can avoid command-name collisions in multi-agent Slack workspaces.

## Best Possible Solution

Keep this issue as the canonical Slack multi-app native command naming item, then implement one validated account-level contract, likely explicit `nativeNames` mapping, with schema validation, duplicate/format checks, registration, reverse lookup, arg-menu roundtrip coverage, and docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack multi-account native slash commands be solved with validated account-level `nativeNames` mapping, constrained `nativePrefix` sugar, or documented as unsupported for duplicate native command names?

Rationale: Current main lacks the account-level naming contract, and the two closed implementation attempts show a real design fork for a compatibility-sensitive Slack config/API surface.

Likely owner: steipete

Owner reason: The strongest current and historical route points to recent Slack native-command and shared command-registry work by Peter Steinberger.

Owner confidence: high

Options:

- **Implement explicit nativeNames (recommended):** Add validated per-account command-key to native-name mapping with duplicate/format checks, registration, dispatch, docs, and tests for the Slack native command path.
- **Implement constrained nativePrefix:** Add prefix sugar only with strict lowercase/slug validation and no broad fallback stripping if maintainers prefer the simpler operator UX.
- **Document unsupported duplicates:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes for source reproduction: current main has no account-level Slack native naming field, its strict schema rejects the proposed config, and registration/lookup are provider-scoped. I did not run a live Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but a validated explicit `nativeNames` mapping appears safer because it avoids implicit alias behavior and matches the later unmerged PR direction.

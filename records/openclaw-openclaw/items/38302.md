## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native command names can route commands to the wrong Slack app, so commands may not reach the intended agent.

## Summary

Keep open: current main and the latest release still lack an account-level Slack native-command naming contract, so the reported multi-app Slack slash-command collision remains. The prior implementation PRs were closed unmerged, and the remaining blocker is choosing the supported config/API shape.

## What This Changes

The issue requests account-level Slack native slash-command naming so multiple Slack apps can register targetable commands without command-name collisions.

## Best Possible Solution

Adopt one validated account-level Slack native-command naming contract in the Slack plugin and docs, covering schema, registration, dispatch, arg-menu callbacks, duplicate validation, and upgrade expectations.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack multi-account native slash commands be solved with explicit account-level nativeNames mapping, constrained nativePrefix sugar, or documented as unsupported for duplicate native command names?

Rationale: The remaining fix adds user-visible Slack config/API surface, and the two prior unmerged PRs show a real design fork that automation should not choose without maintainer intent.

Likely owner: steipete

Owner reason: steipete has the strongest history signal on Slack native command naming and the shared command-registry behavior involved in this product choice.

Owner confidence: high

Options:

- **Implement validated nativeNames (recommended):** Add one explicit per-account mapping surface with format and duplicate validation, registration and reverse-lookup support, docs, and focused Slack tests.
- **Implement constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document unsupported duplicate names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes. Source inspection shows current main and v2026.6.11 lack nativePrefix/nativeNames in strict Slack config, while Slack native registration and lookup remain provider-scoped; I did not run a live multi-app Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but the prior PR discussion and config-surface policy make a validated explicit nativeNames mapping the safer default direction.

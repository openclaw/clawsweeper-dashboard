## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native command names can route a slash command to the wrong app, so the intended agent may never receive the command.

## Summary

Keep open: current main and the latest release still lack an account-level Slack native-command naming contract, and both linked implementation PRs were closed unmerged. The remaining blocker is a maintainer product/API decision, not stale cleanup.

## What This Changes

The issue requests account-level Slack native slash-command names so multi-agent deployments can register distinct commands such as `/oz-reset` and `/dross-reset`.

## Best Possible Solution

Adopt one validated Slack account-level native naming contract, preferably explicit nativeNames mapping, and implement schema validation, registration, dispatch, argument-menu roundtrips, docs, and focused tests together.

Question: Should Slack multi-account native slash commands be solved with validated account-level nativeNames mapping, constrained nativePrefix sugar, or documented as unsupported for duplicate native command names?

Rationale: Current main has no account-level naming contract, and the two closed implementation attempts show a real design fork that expands Slack account config and native command behavior.

Likely owner: steipete

Owner confidence: high

Options:

- **Implement validated nativeNames (recommended):** Add an explicit per-account mapping surface with Slack-name format validation, duplicate checks, registration and reverse lookup support, docs, and tests.
- **Implement constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document unsupported duplicates:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes. Source inspection shows current main has no account-level Slack native command naming field, and Slack native registration plus lookup are provider-scoped rather than account-scoped.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but the later PR discussion and validation concerns make a validated explicit nativeNames mapping the safer default direction.

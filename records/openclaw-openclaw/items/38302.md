## Summary

Keep open: current main still has provider-scoped Slack native command names and no account-level naming contract, so the reported multi-app Slack slash-command collision remains. The prior prefix and nativeNames implementation PRs were closed unmerged, and the remaining decision is which config/API shape maintainers want.

## What This Changes

The issue requests an account-level Slack native slash-command naming option so multiple Slack apps/agents can register distinct commands instead of colliding on the same native names.

## Best Possible Solution

Adopt one validated account-level Slack native command naming contract, likely explicit nativeNames mapping unless maintainers deliberately choose prefix sugar, and cover registration, dispatch, arg-menu callbacks, docs, and schema validation in one focused Slack plugin change.

Rationale: Current main has no account-level naming contract, and the two prior unmerged PRs show a real design fork between prefix convenience and explicit mappings; adding either path expands Slack config/API surface.

Likely owner: steipete

Owner confidence: high

Options:

- **Implement validated nativeNames (recommended):** Add one explicit per-account mapping surface with duplicate/format validation, registration and reverse lookup support, docs, and tests; this matches the later PR direction and avoids implicit prefix aliases.
- **Implement constrained nativePrefix:** Add prefix sugar only with strict lowercase/slug validation and no broad dash-stripping fallback, accepting a simpler UX but a second naming abstraction.
- **Document unsupported duplicate names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names, preserving current config surface at the cost of the reported multi-agent workflow.

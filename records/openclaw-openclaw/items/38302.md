## Summary

Keep open: current main and v2026.6.11 still lack an account-level Slack native-command naming contract, so duplicate Slack app slash-command names remain unresolved. The two linked implementation attempts are closed unmerged, and the remaining blocker is the maintainer choice of supported config/API shape.

## What This Changes

Request account-level Slack native command prefixes or mappings so each Slack app in a multi-agent workspace can register unique slash command names.

## Best Possible Solution

Adopt one validated account-level Slack native-command naming contract in the Slack plugin and docs, covering schema, registration, dispatch, arg-menu callbacks, duplicate validation, and upgrade expectations.

Options:

- **Implement Validated nativeNames (recommended):** Add one explicit per-account mapping surface with format and duplicate validation, registration and reverse-lookup support, docs, and focused Slack tests.
- **Implement Constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document Unsupported Duplicate Names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 lack nativePrefix/nativeNames in strict Slack config and Slack native registration/lookup is provider-scoped. I did not run a live multi-app Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but the prior PR discussion and config-surface policy make a validated explicit nativeNames mapping the safer default direction.

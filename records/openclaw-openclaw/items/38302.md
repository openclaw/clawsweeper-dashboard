## Summary

Keep open: current main and v2026.6.11 still lack an account-level Slack native-command naming contract, so multi-app Slack slash-command collisions remain. The linked implementation PRs are closed unmerged, and the remaining blocker is choosing the supported config/API shape.

## What This Changes

Add an account-level Slack native slash-command naming option so separate Slack apps in the same workspace can register distinct commands for each agent.

## Best Possible Solution

Adopt one validated account-level Slack native-command naming contract in the Slack plugin and docs, covering schema, registration, reverse lookup, arg-menu callbacks, duplicate validation, and setup guidance.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack multi-account native slash commands be solved with explicit account-level nativeNames mapping, constrained nativePrefix sugar, or documented as unsupported for duplicate native command names?

Rationale: The missing behavior is source-proven, but either implementation adds Slack account-level config/API surface and the two closed PRs show a design fork that automation should not choose alone.

Likely owner: steipete

Owner reason: This person has the strongest history signal on Slack native command naming and shared command-registry behavior.

Owner confidence: high

Options:

- **Implement Validated nativeNames (recommended):** Add one explicit per-account mapping surface with format and duplicate validation, registration and reverse-lookup support, docs, and focused Slack tests.
- **Implement Constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document Unsupported Duplicate Names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 lack nativePrefix or nativeNames in strict Slack config, and Slack native registration/lookup is provider-scoped. I did not run a live multi-app Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. A validated nativeNames mapping is likely safer than prefix-only because it avoids implicit dash-stripping and handles per-command collisions explicitly.

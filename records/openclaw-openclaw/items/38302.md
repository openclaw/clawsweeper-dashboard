## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native command names can route commands to the wrong Slack app, so commands may not reach the intended agent.

## Summary

Keep open: current main and v2026.6.11 still lack a supported Slack account-level native command naming contract, so multi-app Slack slash-command collisions remain. The two linked implementation attempts are closed unmerged, and the remaining blocker is maintainer choice of the supported config/API shape.

## What This Changes

The issue requests account-scoped Slack native slash command names so multiple Slack app identities can target separate agents without command-name collisions.

## Best Possible Solution

Adopt one validated account-level Slack native-command naming contract in the Slack plugin and docs, covering schema, registration, dispatch, arg-menu callbacks, duplicate validation, and upgrade expectations.

Question: Should Slack multi-account native slash commands be solved with explicit account-level `nativeNames` mapping, constrained `nativePrefix` sugar, or documented as unsupported for duplicate native command names?

Rationale: The source gap is clear, but either implementation adds Slack account-level config/API surface and the two closed PRs show a real design fork that automation should not choose alone.

Likely owner: steipete

Owner confidence: high

Options:

- **Implement validated nativeNames (recommended):** Add one explicit per-account mapping surface with format and duplicate validation, registration and reverse-lookup support, docs, and focused Slack tests.
- **Implement constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document unsupported duplicates:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 lack `nativePrefix` or `nativeNames` in strict Slack config, and Slack native registration/lookup is provider-scoped. I did not run a live multi-app Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but the prior PR discussion and config-surface policy make a validated explicit `nativeNames` mapping the safer default direction.

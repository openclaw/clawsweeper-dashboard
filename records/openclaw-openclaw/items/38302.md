- `impact:message-loss`: Duplicate Slack native command names can route a slash command to the wrong app, so the intended agent may never receive the command.

## Summary

Keep open: current main and v2026.6.11 still lack any account-level Slack native-command naming contract, and the linked implementation PRs are closed unmerged. The remaining blocker is a maintainer product/API choice, not stale cleanup.

## What This Changes

Requested account-level Slack native slash-command naming so multiple Slack apps can register distinct commands for multi-agent deployments.

## Best Possible Solution

Choose one supported account-level Slack native-command naming contract, then implement schema validation, registration, dispatch lookup, docs, and focused regression tests together.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack multi-account native slash commands use explicit per-account nativeNames mapping, constrained nativePrefix sugar, or remain unsupported for duplicate native command names?

Rationale: Current main has no account-level naming contract, and the closed implementation attempts show a real design fork that expands Slack account config and native command routing behavior.

Likely owner: steipete

Owner reason: This account has the clearest recent history on Slack native command aliases, the shared command registry, and the current ClawSweeper decision comment.

Owner confidence: high

Options:

- **Implement validated nativeNames mapping (recommended):** Add an explicit per-account map from internal command keys to Slack native names with strict Slack-name validation, duplicate checks, registration, reverse lookup, docs, and tests.
- **Implement constrained nativePrefix:** Add prefix sugar for all native command names with strict lowercase slug validation, accepting a simpler operator setup but a second naming abstraction.
- **Document duplicate names as unsupported:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes. Source inspection shows current main and v2026.6.11 have no account-level Slack native command naming field, and Slack native registration plus lookup are provider-scoped rather than account-scoped.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but an explicit validated nativeNames mapping looks safer because it avoids implicit alias stripping and can validate every Slack command name independently.

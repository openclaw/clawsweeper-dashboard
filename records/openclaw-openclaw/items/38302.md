## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native command names can route a slash command to the wrong app, so the intended agent may never receive the command.
- `impact:session-state`: The ambiguous commands include reset, compact, and stop, which directly affect agent/session state.

## Summary

Keep open: current main still has Slack native command names scoped only by provider, with no account-level prefix or native-name mapping contract. The two implementation attempts linked from the issue were closed unmerged, and the remaining blocker is a maintainer product/API decision for Slack account-level native command naming.

## What This Changes

Request account-level Slack native slash-command naming so multiple Slack app accounts can register distinct commands like `/oz-reset` and `/dross-reset` without collisions.

## Best Possible Solution

Choose one validated Slack account-level native command naming contract, preferably explicit `nativeNames` mapping, and implement schema validation, registration, dispatch, argument-menu roundtrips, docs, and focused tests together.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack multi-account native slash commands be solved with validated account-level `nativeNames` mapping, constrained `nativePrefix` sugar, or documented as unsupported for duplicate native command names?

Rationale: Current main has no account-level naming contract, and the two prior unmerged PRs show a real design fork; either implementation expands Slack account config and native command behavior.

Likely owner: steipete

Owner reason: This owner has the clearest history across Slack native command aliases and the shared command registry surface.

Owner confidence: high

Options:

- **Implement validated `nativeNames` (recommended):** Add an explicit per-account mapping surface with duplicate and Slack-name validation, registration and reverse lookup support, docs, and tests.
- **Implement constrained `nativePrefix`:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting a simpler UX but a second naming abstraction.
- **Document duplicate names unsupported:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes, source-level: current main has no account-level Slack native command naming field, and the registration and lookup path is provider-scoped. I did not run a live multi-app Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but the later PR discussion makes a validated explicit `nativeNames` mapping the safer default direction.

## Summary

Keep open: current main and v2026.6.11 still lack an account-level Slack native-command naming contract, so the multi-app Slack slash-command collision remains. The linked implementation PRs were closed unmerged, and the remaining blocker is a maintainer product/API decision about the supported config shape.

## What This Changes

The issue requests an account-level Slack native slash-command naming option so multiple Slack apps can register unique commands for different agents.

## Best Possible Solution

Adopt one validated account-level Slack native-command naming contract in the Slack plugin and docs, covering schema, registration, dispatch, arg-menu callbacks, duplicate validation, and upgrade expectations.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack multi-account native slash commands be solved with explicit account-level nativeNames mapping, constrained nativePrefix sugar, or documented as unsupported for duplicate native command names?

Rationale: Current main has no account-level naming contract, and the two prior unmerged PRs show a real design fork; either implementation adds Slack config/API surface that repository policy reserves for maintainer product judgment.

Likely owner: Peter Steinberger

Owner reason: He has the strongest history signal on the shared native command registry and Slack provider-specific command naming behavior.

Owner confidence: high

Options:

- **Implement Validated nativeNames (recommended):** Add one explicit per-account mapping surface with format and duplicate validation, registration and reverse-lookup support, docs, and focused Slack tests.
- **Implement Constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document Unsupported Duplicate Names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 lack nativePrefix/nativeNames in strict Slack config, and Slack native registration/lookup is provider-scoped. I did not run a live multi-app Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but the prior PR discussion and config-surface policy make a validated explicit nativeNames mapping the safer default direction.

## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native command names can route a slash command to the wrong app, so the intended agent may never receive the command.

## Summary

Keep open: current main and latest release still lack an account-level Slack native command naming contract, while the linked implementation attempts were closed unmerged. The remaining blocker is a maintainer product/API choice for how Slack multi-account native slash command names should be represented.

## What This Changes

The issue requests account-level Slack slash command native naming so multi-agent Slack apps can register distinct commands such as `/oz-reset` and `/dross-reset`.

## Best Possible Solution

Adopt one validated Slack account-level native command naming contract, preferably explicit `nativeNames` mapping, and implement schema validation, registration, dispatch, argument-menu roundtrips, docs, and focused tests together.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack multi-account native slash commands be solved with validated account-level `nativeNames` mapping, constrained `nativePrefix` sugar, or documented as unsupported for duplicate native command names?

Rationale: Current main has no account-level naming contract, and the two unmerged PRs show a real design fork that would expand Slack account config and native command behavior.

Likely owner: steipete

Owner reason: This person has the clearest history across Slack native command aliases and the shared command registry surface.

Owner confidence: high

Options:

- **Implement validated `nativeNames` (recommended):** Add an explicit per-account mapping surface with Slack-name format validation, duplicate checks, registration and reverse lookup support, docs, and tests.
- **Implement constrained `nativePrefix`:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document duplicate names unsupported:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes, source-level: current main has no account-level Slack native command naming field, and the registration and lookup path is provider-scoped. Slack's own docs also require unique slash command names to avoid app conflicts. ([docs.slack.dev](https://docs.slack.dev/interactivity/implementing-slash-commands?utm_source=openai))

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but the later PR discussion makes a validated explicit `nativeNames` mapping the safer default direction.

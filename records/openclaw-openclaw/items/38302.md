## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native command names can route a slash command to the wrong app, so the intended agent may never receive the command.

## Summary

Keep open: current main and the latest release still lack an account-level Slack native command naming contract, while both linked implementation PRs are closed unmerged. The remaining blocker is a maintainer product/API decision, not stale issue cleanup.

## What This Changes

Request account-level Slack native slash-command naming support so multiple Slack apps in one workspace can register distinct OpenClaw commands for different agents.

## Best Possible Solution

Adopt one validated Slack account-level native command naming contract, preferably explicit nativeNames mapping, with schema validation, collision checks, registration, dispatch, argument-menu roundtrips, docs, and focused tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack multi-account native slash commands be solved with explicit per-account nativeNames mapping, constrained nativePrefix sugar, or documented as unsupported for duplicate Slack native command names?

Rationale: Current main has no account-level naming contract, and the two closed unmerged PRs show a real design fork that would expand Slack account config and native command behavior.

Likely owner: steipete

Owner reason: steipete has the clearest history across the Slack-specific native-name override and the shared command registry surface.

Owner confidence: high

Options:

- **Implement validated nativeNames (recommended):** Add an explicit per-account mapping surface with Slack-name format validation, duplicate checks, registration and reverse lookup support, docs, and tests.
- **Implement constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document duplicate names unsupported:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 have no account-level Slack native command naming field, and registration plus lookup are provider-scoped. I did not run a live multi-app Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. The safest apparent direction is a validated explicit nativeNames mapping rather than implicit prefix stripping, but that is a product/API choice.

## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native slash command names can route a command to the wrong Slack app, so the intended agent may never receive it.
- `impact:session-state`: The ambiguous commands include reset, compact, and stop, which directly affect agent/session state.

## Summary

Keep open: current main still has provider-scoped Slack native command names, no account-level `nativePrefix` or `nativeNames` config, and both implementation attempts are closed unmerged. The remaining blocker is maintainer product/API direction for the supported Slack account-level native naming contract.

## What This Changes

The issue requests account-level Slack native slash command naming so multiple Slack apps in one workspace can register distinct commands for different agents.

## Best Possible Solution

Keep this as the canonical Slack multi-app native naming issue and implement one validated account-level contract, likely explicit `nativeNames`, with schema validation, duplicate/format checks, registration, reverse lookup, arg-menu roundtrip coverage, and docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack multi-account native slash commands be solved with validated account-level `nativeNames`, constrained `nativePrefix` sugar, or documented as unsupported for duplicate native command names?

Rationale: Current main lacks the account-level naming contract, and the two closed implementation attempts show a real design fork for a compatibility-sensitive Slack config/API surface.

Likely owner: steipete

Owner reason: The strongest current and historical route points to shared command-registry, Slack config, and Slack native-command work by steipete.

Owner confidence: high

Options:

- **Implement explicit nativeNames (recommended):** Add a validated per-account command-key to native-name mapping with duplicate and format checks, registration, dispatch, docs, and Slack native-command tests.
- **Implement constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation if maintainers prefer the simpler operator UX over per-command mapping flexibility.
- **Document unsupported duplicates:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes. Current main has no account-level Slack native naming field, its strict schema rejects the proposed config, and registration/lookup are provider-scoped; I did not run a live Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but a validated explicit `nativeNames` mapping appears safer because it avoids implicit fallback aliases and matches the later unmerged PR direction.

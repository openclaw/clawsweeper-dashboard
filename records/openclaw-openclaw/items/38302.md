## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an urgent core outage.
- `impact:message-loss`: Duplicate Slack native command names can route a slash command to the wrong app, so the intended agent may never receive the command.

## Summary

Keep open: current main still lacks account-level Slack native command naming, so the multi-app Slack slash-command collision remains. The prior prefix and nativeNames implementation attempts are both closed unmerged, leaving a maintainer product/config decision rather than a safe cleanup close.

## What This Changes

Requests account-level Slack native slash-command naming so separate Slack apps in one multi-agent deployment can register distinct commands such as `/oz-reset` and `/dross-reset`.

## Best Possible Solution

Adopt one validated account-level Slack native naming contract, likely explicit nativeNames mapping unless maintainers choose constrained prefix sugar, and cover schema, registration, dispatch, arg-menu callbacks, docs, and tests in one Slack plugin change.

Rationale: Current main has no account-level naming contract, the two prior unmerged PRs show a design fork, and either implementation expands Slack config/API surface that AGENTS.md treats as compatibility-sensitive.

Owner confidence: high

Options:

- **Implement validated nativeNames (recommended):** Add one explicit per-account mapping surface with duplicate/format validation, registration and reverse lookup support, arg-menu roundtrip coverage, docs, and schema tests.
- **Implement constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting a simpler UX but a second naming abstraction.
- **Document unsupported duplicate names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

Yes for source-level reproduction: current main has no account-level Slack native naming field, strict config accepts only the existing slashCommand fields, and Slack native registration/lookup is provider-scoped. I did not run a live Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but the later unmerged work and the repository's config-surface policy make validated explicit nativeNames mapping the safer default direction.

## Summary

Keep open: current main and v2026.6.11 still lack an account-level Slack native-command naming contract, so the multi-app slash-command collision remains. The related implementation PRs were closed unmerged, and the remaining blocker is choosing the supported Slack config/API shape.

## What This Changes

The issue requests per-account Slack native slash-command naming so multiple Slack apps can avoid command-name collisions in multi-agent channels.

## Best Possible Solution

Adopt one validated account-level Slack native-command naming contract in the Slack plugin and docs, covering schema, registration, dispatch, arg-menu callbacks, duplicate validation, and upgrade expectations.

Rationale: Current main has no account-level naming contract, and the two prior unmerged PRs show a real design fork; either implementation adds Slack config/API surface that repository policy reserves for maintainer product judgment.

Owner confidence: high

Options:

- **Implement validated nativeNames (recommended):** Add one explicit per-account mapping surface with format and duplicate validation, registration and reverse-lookup support, docs, and focused Slack tests.
- **Implement constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document unsupported duplicate names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 lack nativePrefix/nativeNames in strict Slack config and Slack native registration/lookup is provider-scoped. I did not run a live multi-app Slack workspace reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but the prior PR history and config-surface policy make a validated explicit nativeNames mapping the safer default direction.

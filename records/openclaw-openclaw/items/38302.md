- `P2`: This affects real multi-agent Slack deployments but remains a bounded feature/config decision rather than an emergency outage.

## Summary

Keep open: current main and the latest release still have provider-scoped Slack native command names with no account-level naming contract, while the two implementation attempts were closed unmerged and the remaining choice is product/API shape.

## What This Changes

The issue requests account-level Slack native slash command names so multi-agent Slack apps can register distinct commands such as prefixed reset, compact, and stop commands.

## Best Possible Solution

Adopt one validated account-level Slack native-command naming contract, likely explicit `nativeNames` unless maintainers choose prefix sugar, and cover config/schema, spec generation, reverse lookup, arg-menu callbacks, docs, and focused tests together.

Rationale: The current code lacks the account naming boundary, and the two closed implementation attempts show a real design fork that expands Slack config/API surface either way.

Likely owner: steipete

Owner reason: The strongest current-code and history evidence for the Slack native-command registry and config surface points to steipete.

Owner confidence: high

Options:

- **Implement validated nativeNames (recommended):** Add explicit per-account native-name mapping with format/collision validation, registration and reverse lookup support, arg-menu roundtrip coverage, docs, and tests.
- **Implement constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup at the cost of another naming abstraction.
- **Document unsupported duplicate names:** Keep runtime unchanged and document that multiple Slack apps in one workspace must not register identical native slash command names.

Yes for source reproduction: current main has no account-level Slack native naming field, and the registration/lookup path is provider-scoped. I did not run a live Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but the prior PR discussion and OpenClaw's config-surface policy make a validated explicit mapping the safer default direction.

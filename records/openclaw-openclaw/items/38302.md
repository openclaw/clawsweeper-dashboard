## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:message-loss`: Duplicate native Slack command names can route a slash command to the wrong app, so the intended agent may never receive it.
- `impact:session-state`: The ambiguous commands named in the report include reset, compact, and stop, which directly affect agent session state.

## Summary

Keep open: current main and v2026.6.11 still have provider-scoped Slack native command names with no account-level prefix or nativeNames contract, and both linked implementation PRs were closed unmerged. The remaining blocker is a maintainer product/config decision, not evidence that the issue is obsolete.

## What This Changes

Request account-level Slack native slash-command naming so multiple Slack app accounts can register non-colliding commands such as `/oz-reset` and `/dross-reset`.

## Best Possible Solution

Adopt one validated account-level Slack native command naming contract, likely explicit nativeNames mapping unless maintainers choose constrained prefix sugar, and wire schema, docs, registration, dispatch, arg-menu callbacks, and collision validation together.

## Maintainer Decision

Kind: product_direction

Question: Should Slack multi-account native slash commands use explicit per-account nativeNames mapping, constrained nativePrefix sugar, or remain unsupported for duplicate Slack native command names?

Rationale: Current main has no account-level naming contract, the prior PRs show a real design fork, and either implementation expands Slack account config surface.

Likely owner: steipete

Owner reason: steipete has the strongest current and historical signal on the shared native command registry and Slack native alias behavior this decision would change.

Owner confidence: high

Options:

- **Implement validated nativeNames (recommended):** Add explicit per-account command-name mapping with strict Slack-name validation, duplicate checks, registration, reverse lookup, docs, and tests.
- **Implement constrained nativePrefix:** Add prefix sugar with narrow slug validation and no broad dash-stripping fallback, accepting a simpler UX but another naming abstraction.
- **Document unsupported duplicates:** Keep runtime unchanged and document that multiple Slack apps in one workspace must not register the same native slash command names.

## Reproduction Assessment

Yes, at source level: current main has no account-level Slack native naming field, and registration/lookup are provider-scoped. I did not run a live multi-app Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. The safest likely direction is a validated explicit nativeNames mapping, but constrained prefix sugar is also plausible if maintainers want that UX.

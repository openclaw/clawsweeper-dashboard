## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments, but it is a bounded feature/config decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native command names can route commands to the wrong app, so messages may not reach the intended agent.
- `impact:session-state`: The ambiguous commands include reset, compact, stop, and status flows that directly affect or inspect agent session state.

## Summary

Keep open: current main and the latest release still have provider-scoped Slack native command names with no account-level naming contract, while both linked implementation attempts are closed unmerged. The remaining blocker is maintainer product direction on the supported Slack account-level naming API.

## What This Changes

Request account-level Slack native slash command naming so multiple Slack apps or agents can register distinct `/reset`, `/compact`, `/stop`-style commands without collisions.

## Best Possible Solution

Choose one supported account-level Slack native naming contract, preferably explicit `nativeNames` mapping with strict validation, and implement it across schema/types, native spec generation, Slack registration/lookup/arg menus, docs, and tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack multi-account native slash commands be solved with validated account-level `nativeNames` mapping, constrained `nativePrefix` sugar, or documented as unsupported for duplicate native command names?

Rationale: Current main has no account-level naming contract, and the two closed implementation PRs show a real design fork; adding either path expands a user-visible Slack config/API surface that repository policy treats as product-sensitive.

Likely owner: steipete

Owner reason: The most relevant historical commits for Slack native names and shared command registry behavior point to steipete.

Owner confidence: high

Options:

- **Implement validated nativeNames (recommended):** Add one explicit per-account mapping surface with duplicate and Slack-name validation, registration and reverse lookup support, docs, and tests.
- **Implement constrained nativePrefix:** Add prefix sugar only with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but another naming abstraction.
- **Document unsupported duplicate names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes for source-level reproduction: current main has no account-level Slack native naming field and the registration/lookup path is provider-scoped. I did not run a live Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. A validated explicit `nativeNames` mapping looks safer than implicit prefix stripping, but the final API shape is a maintainer decision.

## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native slash command names can route a command to the wrong app, so the intended agent may never receive it.

## Summary

Keep open: current main and the latest release still expose only provider-scoped Slack native command names, while both linked implementation PRs are closed unmerged. The remaining blocker is maintainer product/API direction for the account-level Slack native naming contract.

## What This Changes

The issue requests account-level Slack native slash-command naming so multiple Slack apps in one workspace can register distinct commands for different agents.

## Best Possible Solution

Keep this as the canonical Slack multi-app native command naming item, then implement one validated per-account contract with schema validation, duplicate/format checks, registration, reverse lookup, arg-menu roundtrip coverage, docs, and Slack setup proof.

Rationale: Current main lacks the account-level naming contract, and the two closed implementation attempts show a real design fork for a compatibility-sensitive Slack config/API surface.

Owner confidence: high

Options:

- **Implement Explicit nativeNames (recommended):** Add validated per-account command-key to native-name mapping with duplicate/format checks, registration, dispatch, docs, and tests for the Slack native command path.
- **Implement Constrained nativePrefix:** Add prefix sugar only with strict lowercase/slug validation and no broad fallback stripping if maintainers prefer the simpler operator UX.
- **Document Unsupported Duplicate Names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes for source reproduction: current main has no account-level Slack native naming field, its strict schema rejects the proposed config, and registration/lookup are provider-scoped. I did not run a live Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. A validated explicit `nativeNames` mapping appears safer than implicit prefix stripping, but `nativePrefix` may be acceptable if maintainers prefer constrained sugar.

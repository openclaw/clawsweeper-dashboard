## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native command names can route commands to the wrong Slack app, so commands may not reach the intended agent.

## Summary

Keep open: current main and v2026.6.11 still lack any account-level Slack native command naming contract, so the multi-app Slack slash-command collision remains. The prior implementation PRs are closed unmerged, and the remaining blocker is choosing the supported config/API shape.

## What This Changes

Request account-level Slack native slash-command names or prefixes so multiple Slack apps/agents can register unique commands without collisions.

## Best Possible Solution

Adopt one validated account-level Slack native-command naming contract in the Slack plugin and docs, with schema validation, registration, dispatch, arg-menu callbacks, duplicate handling, and release-note context.

Options:

- **Implement Validated nativeNames (recommended):** Add one explicit per-account mapping surface with format and duplicate validation, registration and reverse-lookup support, docs, and focused Slack tests.
- **Implement Constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document Unsupported Duplicate Names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Solution Assessment

Unclear until maintainers choose the contract. Prefixing is plausible, but the prior PR discussion and config-surface policy make a validated explicit nativeNames mapping the safer default direction.

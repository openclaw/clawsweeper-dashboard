## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an outage or release blocker.
- `impact:message-loss`: Duplicate Slack native command names can route commands to the wrong Slack app, so commands may not reach the intended agent.

## Summary

Keep open: current main and v2026.6.11 still lack an account-level Slack native-command naming contract, so the multi-app Slack slash-command collision remains. The two linked implementation attempts are closed unmerged, and the remaining blocker is choosing the supported config/API shape rather than proving the source gap exists.

## What This Changes

The issue requests per-account Slack native slash-command naming so multiple Slack apps can register unique commands for different agents in the same workspace.

## Best Possible Solution

Adopt one validated Slack-plugin account-level native-command naming contract, preferably explicit nativeNames mapping unless maintainers choose constrained prefix sugar, and document the supported setup and unsupported collision cases.

Owner confidence: high

Options:

- **Implement validated nativeNames (recommended):** Add one explicit per-account mapping surface with format and duplicate validation, registration and reverse-lookup support, docs, and focused Slack tests.
- **Implement constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document unsupported duplicate names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 lack nativePrefix/nativeNames in strict Slack config, and Slack native registration/lookup is provider-scoped. I did not run a live multi-app Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but the prior PR discussion and config-surface policy make a validated explicit nativeNames mapping the safer default direction.

## Summary

Keep open: current main and v2026.6.11 still lack any account-level Slack native-command naming contract, and the two linked implementation PRs were closed unmerged. The remaining blocker is choosing the supported config/API shape, not proving whether the Slack multi-app collision can happen.

## What This Changes

The issue requests account-level Slack native slash-command names or prefixes so multiple Slack apps can register distinct commands for separate agents.

## Best Possible Solution

Adopt one validated account-level Slack native-command naming contract in the Slack plugin and docs, covering schema, registration, dispatch, arg-menu callbacks, duplicate validation, and upgrade expectations.

## Maintainer Decision

Kind: product_direction

Question: Should Slack multi-account native slash commands be solved with explicit account-level `slashCommand.nativeNames`, constrained `slashCommand.nativePrefix` sugar, or documented as unsupported for duplicate native command names?

Rationale: Current main has no account-level naming contract, and the two prior unmerged PRs show a real design fork that adds Slack config/API surface requiring maintainer product judgment.

Likely owner: steipete

Owner reason: steipete has the strongest history signal on Slack native command naming and the shared command-registry behavior this decision would change.

Owner confidence: high

Options:

- **Implement validated nativeNames (recommended):** Add one explicit per-account mapping surface with format and duplicate validation, registration and reverse-lookup support, docs, and focused Slack tests.
- **Implement constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document unsupported duplicate names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 lack `nativePrefix` or `nativeNames` in strict Slack config, and Slack native registration/lookup is provider-scoped. I did not run a live multi-app Slack workspace reproduction in this read-only cleanup pass.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but the prior PR discussion and config-surface policy make a validated explicit nativeNames mapping the safer default direction.

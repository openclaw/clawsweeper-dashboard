## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded channel/config product decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native command names can route slash commands to the wrong Slack app, so commands may not reach the intended agent.
- `impact:session-state`: The ambiguous commands include reset, compact, and stop, which directly affect agent/session state.

## Summary

Keep open: current main and the latest release still lack an account-level Slack native slash-command naming contract, so multi-app Slack command collisions remain. The two implementation attempts linked from the issue are closed unmerged, and the remaining blocker is the maintainer product/API choice between explicit mappings, prefix sugar, or documented unsupported duplicate native names.

## What This Changes

Request account-level Slack native slash-command names or prefixes so multiple Slack apps in one workspace can register distinct commands for separate agents.

## Best Possible Solution

Adopt one validated account-level Slack native command naming contract, likely explicit nativeNames mapping unless maintainers deliberately choose prefix sugar, and cover schema, registration, dispatch, arg-menu callbacks, docs, and focused Slack tests together.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack multi-account native slash commands be solved with explicit account-level nativeNames mapping, constrained nativePrefix sugar, or documented as unsupported for duplicate native command names?

Rationale: Current main has no account-level naming contract, the two unmerged PRs show a real design fork, and adding either option expands Slack config and setup behavior.

Likely owner: steipete

Owner reason: The clearest current and historical code trail for Slack native names and the shared command registry points to steipete.

Owner confidence: high

Options:

- **Implement validated nativeNames (recommended):** Add one explicit per-account mapping surface with Slack command-name validation, collision checks, registration/reverse lookup support, docs, and tests.
- **Implement constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document duplicate native names as unsupported:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical OpenClaw native command names.

## Reproduction Assessment

Yes, source-level: current main has no account-level Slack native command naming field, and the registration/lookup path is provider-scoped. I did not run a live multi-app Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. The proposed prefix is plausible, but the later nativeNames direction is safer unless maintainers explicitly want prefix sugar.

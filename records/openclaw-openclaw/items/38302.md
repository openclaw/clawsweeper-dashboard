## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:message-loss`: Duplicate Slack native command names can route a slash command to the wrong app, so the intended agent may never receive the command.
- `impact:session-state`: The ambiguous commands include reset, compact, and stop, which directly affect agent/session state.

## Summary

Keep open: current main and the latest release still lack an account-level Slack native-command naming contract, and the two linked implementation PRs were closed unmerged. The remaining blocker is choosing the supported config/API shape, not stale cleanup.

## What This Changes

The issue requests per-Slack-account native slash command prefixes or mappings so multiple Slack apps can register non-colliding commands for different agents.

## Best Possible Solution

Define one validated Slack account-level native command naming contract, preferably explicit nativeNames mapping, and implement schema validation, registration, reverse lookup, docs, and focused tests together.

## Maintainer Decision

Question: Should Slack multi-account native slash commands be solved with explicit account-level nativeNames mapping, constrained nativePrefix sugar, or documented as unsupported for duplicate native command names?

Rationale: Current main has no account-level naming contract, and the two closed implementation attempts show a real design fork that expands Slack account config and native command behavior.

Likely owner: Peter Steinberger

Owner reason: Peter has the clearest observed history on Slack native-name aliasing and the shared command registry boundary.

Owner confidence: medium

Options:

- **Implement validated nativeNames (recommended):** Add an explicit per-account mapping surface with Slack-name format validation, duplicate checks, registration, reverse lookup, argument-menu roundtrip support, docs, and tests.
- **Implement constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting simpler setup but a second naming abstraction.
- **Document unsupported duplicates:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes, source-level. Current main has no account-level Slack native command naming field, and Slack native registration plus lookup are provider-scoped rather than account-scoped.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but the later PR discussion and validation concerns make a validated explicit nativeNames mapping the safer default direction.

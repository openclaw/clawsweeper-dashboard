## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:session-state`: The ambiguous native commands include reset, compact, and stop, which can affect the wrong agent or session state in multi-agent Slack setups.
- `impact:message-loss`: Duplicate Slack native command names can route a slash command to the wrong app, so the intended agent may never receive the command.

## Summary

Keep open: current main still lacks an account-level Slack native command naming contract, and the closed implementation attempts are unmerged. The remaining blocker is maintainer product/API direction for the supported Slack account-level native naming shape.

## What This Changes

The issue requests account-level native Slack slash command prefixes so multiple OpenClaw Slack apps can register distinct command names for multi-agent deployments.

## Best Possible Solution

Keep this as the canonical Slack multi-app native command naming item, then implement one validated account-level contract with schema, duplicate/format checks, registration, reverse lookup, arg-menu roundtrip coverage, and docs.

## Maintainer Decision

Kind: product_direction

Question: Should Slack multi-account native slash commands use explicit account-level `nativeNames` mapping, constrained `nativePrefix` sugar, or remain documented as unsupported for duplicate native command names?

Rationale: Current main lacks the account-level naming contract, and the two closed implementation attempts show a real API/config design fork for a compatibility-sensitive Slack account surface.

Likely owner: steipete

Owner confidence: high

Options:

- **Implement Explicit Native Names (recommended):** Add validated per-account command-key to native-name mapping with duplicate and Slack format checks, registration, dispatch, docs, and tests.
- **Implement Constrained Prefix Sugar:** Add a single validated lowercase prefix option if maintainers prefer simpler operator setup over per-command naming control.
- **Document Unsupported Duplicates:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes, source-level: current main has no account-level Slack native naming field, its strict schema rejects the proposed config, and registration/lookup are provider-scoped. I did not run a live multi-app Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. Prefixing is plausible, but explicit validated `nativeNames` mapping appears safer because it avoids implicit alias behavior and matches the later unmerged PR direction.

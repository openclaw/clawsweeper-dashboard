## Label Justifications

- `P2`: The issue affects real multi-agent Slack deployments but is a bounded feature/config decision rather than an emergency outage.
- `impact:session-state`: The affected commands include reset, compact, and stop, which directly control agent session state in multi-agent Slack deployments.

## Summary

Keep open: current main and v2026.6.11 still lack a Slack account-level native-command naming contract, so the multi-app slash-command collision remains. Prior implementation attempts were closed unmerged, and the remaining decision is the supported config/API shape rather than whether the issue is real.

## What This Changes

The issue requests account-level Slack native slash-command naming so multiple Slack apps in one workspace can register distinct commands for separate agents.

## Best Possible Solution

Adopt one validated account-level Slack native-command naming contract in the Slack plugin and docs, covering schema, registration, dispatch, arg-menu callbacks, duplicate validation, and upgrade expectations.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Slack multi-account native slash commands use explicit account-level nativeNames mapping, constrained nativePrefix sugar, or remain unsupported for duplicate native command names?

Rationale: The current code has no account-level native naming contract, and prior unmerged PRs show a real design fork that adds user-visible Slack config/API surface.

Likely owner: steipete

Owner reason: steipete has the strongest history signal on the Slack native alias and shared command-registry behavior that this decision would change.

Owner confidence: high

Options:

- **Implement Validated nativeNames (recommended):** Add explicit per-account native name mapping with Slack-safe format validation, duplicate/default collision checks, registration and reverse lookup support, docs, and focused tests.
- **Implement Constrained nativePrefix:** Add prefix sugar with strict lowercase slug validation and no broad dash-stripping fallback, accepting a simpler setup at the cost of a second naming abstraction.
- **Document Unsupported Duplicate Names:** Leave runtime unchanged and document that multiple Slack apps in one workspace must not register identical native command names.

## Reproduction Assessment

Yes, source-level: current main and v2026.6.11 lack account-level Slack native command names, and Slack native registration/lookup remains provider-scoped. I did not run a live multi-app Slack workspace reproduction.

## Solution Assessment

Unclear until maintainers choose the product contract. A validated explicit nativeNames mapping looks safer than prefix stripping because it avoids implicit aliases and can validate exact Slack command names.

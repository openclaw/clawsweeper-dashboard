## Summary

Keep open: current main and the latest release still route Feishu Markdown-table replies through interactive-card sends without a table-count guard or fallback, and the active fix candidate remains open and conflicting rather than merged.

## What This Changes

The issue requests Feishu delivery to avoid dropping replies when interactive cards exceed the table limit, preferably by falling back to post/plain text or rendering tables safely.

## Best Possible Solution

Land or replace the narrow Feishu static-card table-limit fallback against current main, with focused outbound and reply-dispatcher tests; track CardKit streaming separately unless the same limit is proven there.

## Reproduction Assessment

Yes, source-reproducible: current main routes Markdown-table replies through Feishu card paths without a table-count guard, and the issue plus linked PR proof include 230099/11310 failure logs. I did not run a live Feishu tenant reproduction in this read-only review.

## Solution Assessment

Yes for the static-card path: preflight/fallback to the existing post sender is the narrow maintainable fix because sendMessageFeishu already converts Markdown tables. Rendering tables as images would add a broader media-rendering surface and should not be the first repair.

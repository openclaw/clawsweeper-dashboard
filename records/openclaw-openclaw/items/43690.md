## Summary

Keep open: current main and v2026.6.11 still route Feishu Markdown-table replies through interactive-card paths without a five-table guard or table-limit fallback, while the active fix candidate is open but still conflicting.

## What This Changes

The issue requests a Feishu delivery fallback when Markdown-table-heavy replies exceed the interactive-card table limit and otherwise disappear from chat.

## Best Possible Solution

Land or replace the narrow Feishu static-card table-limit fallback against current main with focused outbound and reply-dispatcher tests; track streaming CardKit separately unless the same limit is proven there.

## Reproduction Assessment

Yes, source-reproducible: current main routes Markdown-table replies through Feishu card paths without a table-count guard, and the issue plus linked PR proof include 230099/11310 failure logs. I did not run a live Feishu tenant reproduction in this read-only review.

## Solution Assessment

Yes for the static-card path: preflight/fallback to the existing post sender is the narrow maintainable fix because sendMessageFeishu already converts Markdown tables. Rendering tables as images would add a broader media-rendering surface and should not be the first repair.

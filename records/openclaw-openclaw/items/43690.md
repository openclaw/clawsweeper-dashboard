## Summary

Keep open: current main and the latest release still route Feishu markdown-table replies through interactive-card sends without a five-table guard or table-limit fallback, and the same-repo fix candidate remains open and conflicting rather than merged.

## What This Changes

The issue requests graceful Feishu delivery when markdown-table card rendering exceeds Feishu's interactive-card table limit.

## Best Possible Solution

Land or replace the narrow Feishu static-card table-limit fallback against current main, with focused outbound and reply-dispatcher tests; track streaming CardKit separately unless the same limit is proven there.

## Reproduction Assessment

Yes, source-reproducible: current main routes renderMode=card and auto-detected markdown-table text through Feishu interactive-card sends without a table-count guard. The issue and linked PR include Feishu 230099/11310 failure logs, but I did not run a live Feishu tenant in this read-only review.

## Solution Assessment

Yes for the static-card path. A narrow preflight fallback to the existing post sender is the maintainable fix because sendMessageFeishu already converts markdown tables; rendering tables as images would add a broader media-rendering surface.

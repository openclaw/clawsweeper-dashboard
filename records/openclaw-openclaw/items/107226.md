## Label Justifications

- `P0`: A routine stable update can leave an existing user's configured agents unable to complete any turn, with recovery requiring manual config edits, plugin installation, and gateway restart.
- `impact:data-loss`: Doctor reportedly deletes the user's persisted plugins.allow entry during upgrade rather than preserving or migrating it.
- `impact:auth-provider`: The deleted plugin policy prevents the selected Codex agent runtime from registering, breaking provider/runtime routing for every affected turn.
- `impact:ux-release-blocker`: The update reports a healthy gateway while the user's agents are unusable, and the available recovery path requires terminal commands and internal plugin knowledge.

## Summary

Keep open: the released upgrade path can delete a working Codex runtime allowlist entry and leave affected agents unable to run, while the linked open repair PR addresses only the pruning path and does not resolve or define the reported readiness gap. ([github.com](https://github.com/openclaw/openclaw/issues/107226))

## What This Changes

Preserve Codex runtime plugin configuration across upgrades and report degraded readiness when a configured agent's required harness is unavailable.

## Best Possible Solution

Make upgrade reconciliation transactional for version-bound runtime plugins: preserve the user's activation intent, install the host-cohort plugin or emit a blocking actionable failure, then mark readiness degraded only when an agent's effective required runtime has no registered owner or valid fallback; prove both upgrade and agent-turn behavior.

Options:

- **Degrade required runtimes (recommended):** Mark readiness unhealthy only when an agent's effective selected runtime is unavailable and no configured valid fallback can execute the turn.
- **Warn outside readiness:** Keep readiness process-oriented and surface the missing harness prominently through doctor, status, diagnostics, and update completion instead.
- **Fail any missing harness:** Mark readiness unhealthy whenever any configured agent names an unregistered harness, regardless of fallback availability.

## Summary

Keep open: release v2026.7.1 can turn a working Codex-backed agent into a fail-every-turn state during routine update. The linked open repair at https://github.com/openclaw/openclaw/pull/107285 addresses allowlist pruning, but current readiness semantics still do not detect a configured harness that never registered.

## What This Changes

Prevent upgrades from silently pruning allowlisted externalized runtime plugins and expose a degraded state when configured agent harnesses are unavailable.

## Best Possible Solution

Preserve and install version-bound externalized runtime plugins during upgrade, then make `/readyz` or an equally prominent startup diagnostic report configured-but-unregistered harnesses while keeping `/healthz` limited to process liveness.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should a configured agent harness that fails to register make Gateway `/readyz` and status degraded, or should readiness remain limited to Gateway startup infrastructure with doctor/update as the sole enforcement point?

Rationale: Both policies are technically viable, but they define a public operational contract for orchestrators and users; source inspection cannot determine the intended readiness boundary.

Likely owner: steipete

Owner reason: This person merged and refined the existing configured-runtime diagnostics and has recent involvement in Gateway status semantics.

Owner confidence: high

Options:

- **Degrade readiness (recommended):** Keep `/healthz` as liveness, but make `/readyz` and status degraded with actionable plugin-install guidance whenever a configured harness owner is unavailable.
- **Keep readiness narrow:** Leave Gateway readiness unchanged and instead make update/doctor fail loudly or block completion until every explicitly configured harness owner is installed and enabled.

## Reproduction Assessment

Yes at source level: upgrade a pre-v2026.7.1 configuration containing `plugins.allow: ["codex"]`, run doctor repair, restart, and make a Codex-bound agent turn. The report provides a shipped-version reproduction and the current repair sequence explains the allowlist loss, although this review did not execute the live upgrade.

## Solution Assessment

No, preserving the allowlist alone is not the complete best fix. It should be combined with verified upgrade installation or loud failure and a maintainer-chosen readiness signal for configured harnesses that remain unavailable.

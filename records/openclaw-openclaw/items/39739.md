## Summary

Keep open: current main and the latest release still only support exact parsed origins or the global `*` allow-all entry, while this issue asks for a new scheme-level wildcard policy on a Gateway browser-origin security boundary.

## What This Changes

The issue asks for `gateway.controlUi.allowedOrigins` to accept scheme-level wildcard origins such as `chrome-extension://*` so changing Chrome extension IDs do not require config edits.

## Best Possible Solution

Decide the allowed wildcard grammar for Gateway browser origins first, then implement the narrowest accepted matcher with unit, WebSocket handshake, trusted-proxy HTTP, docs, and negative security coverage.

Options:

- **Approve constrained scheme wildcards (recommended):** Define a small grammar, implement it in the shared origin helper, and document allowed/rejected cases before accepting the feature.
- **Keep exact origins only:** Reject scheme wildcards and rely on exact opaque-origin fixes plus the existing global `*` for intentionally broad local testing.
- **Fold into broader origin-pattern design:** Wait for the loopback pattern work to settle, then decide whether extension scheme wildcards belong in that same contract.

## Solution Assessment

No, the issue body's prefix-match sketch is only a plausible starting point. The best fix needs maintainer-approved wildcard semantics and coverage for allowed, rejected, exact, global wildcard, WebSocket, and trusted-proxy HTTP cases.

## Summary

Keep open: current main and v2026.6.11 still only accept exact parsed origins or the global `*`, while `chrome-extension://*` remains a security-sensitive Gateway origin-policy feature that related open PRs do not cover.

## What This Changes

The issue requests scheme-level wildcard support in `gateway.controlUi.allowedOrigins` so Chrome extension clients can survive changing extension IDs without using the global wildcard.

## Best Possible Solution

Define a maintainer-approved constrained origin-pattern policy for extension/browser origins, then implement it across schema/help, runtime WebSocket and HTTP origin checks, security audit, docs, and focused negative tests; otherwise document that Chrome extension clients must use exact origins or the existing global wildcard knowingly.

- **Keep exact origins only:** Leave scheme wildcards unsupported and focus related PRs on exact non-standard-origin matching, accepting that extension ID churn remains an operator burden.
- **Reject extension-wide trust:** Close this direction after documenting that trusting all Chrome extension origins is too broad for Gateway origin authorization.

## Solution Assessment

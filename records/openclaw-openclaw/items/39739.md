## Summary

Keep open: current main and v2026.6.11 still only accept exact parsed origins or the global `*`, while this issue asks for a new scheme-level wildcard policy on a Gateway browser-origin security boundary.

## What This Changes

Request support for scheme-level wildcard entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins` so Chrome extension origins do not require per-ID config updates.

## Best Possible Solution

Decide the Gateway browser-origin wildcard contract first, then implement the narrowest accepted matcher with WebSocket, trusted-proxy HTTP, docs, and negative security coverage.

Question: Should `gateway.controlUi.allowedOrigins` accept scheme-level wildcard entries such as `chrome-extension://*`, and what exact wildcard grammar is acceptable for the Gateway browser-origin authorization boundary?

Rationale: This changes which browser origins may reach Gateway HTTP/WebSocket handling, and current docs intentionally describe full-origin allowlisting plus the global `*` as the only wildcard policy.

Likely owner: steipete

Owner reason: He introduced and repeatedly hardened the Gateway origin-check boundary, so he is the strongest routing candidate for this security/product choice.

Owner confidence: high

Options:

- **Approve constrained scheme wildcards (recommended):** Define a small, explicit grammar such as vetted scheme-only extension patterns, implement it in the shared origin helper, and document allow/reject cases before accepting the feature.
- **Keep exact origins only:** Reject scheme wildcards and rely on exact opaque-origin support plus the existing global `*` escape hatch for intentionally broad local testing.
- **Fold into origin-pattern design:** Wait for the broader allowed-origin-pattern contract to settle, then decide whether Chrome extension scheme wildcards belong in that same config surface.

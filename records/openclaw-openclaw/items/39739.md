## Summary

Keep open: current main and the latest release still only allow exact parsed origins or the global `*`, while this issue requests a new scheme-level wildcard policy for a Gateway browser-origin security boundary.

## What This Changes

Request support for scheme-level wildcard entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins` so Chrome extension origins can remain allowed across ID changes.

## Best Possible Solution

Define the accepted wildcard grammar and scheme limits first, then implement the narrowest matcher in the shared origin helper with WebSocket, trusted-proxy HTTP, docs, and negative security coverage.

Question: Should `gateway.controlUi.allowedOrigins` allow scheme-level wildcard entries such as `chrome-extension://*`, and what grammar and scheme limits are acceptable for Gateway browser-origin authorization?

Rationale: This changes which browser origins may reach Gateway HTTP/WebSocket handling, and current docs intentionally describe full-origin allowlisting plus the global `*` as the only wildcard policy.

Likely owner: steipete

Owner reason: He introduced the Gateway origin boundary and merged the existing wildcard allowlist behavior, so this security policy decision is closest to his feature history.

Owner confidence: high

Options:

- **Approve constrained extension wildcard grammar (recommended):** Define a small explicit grammar for extension-scheme wildcards, implement it in the shared helper, and document allow/reject cases before accepting the feature.
- **Keep exact origins only:** Reject scheme wildcards and rely on exact opaque-origin fixes plus the existing global `*` escape hatch for intentionally broad local testing.
- **Fold into broader origin-pattern contract:** Wait for the loopback pattern work to settle and decide whether Chrome extension scheme wildcards belong in the same public config contract or a separate one.

Yes, as a source-level reproduction. Current `checkBrowserOrigin` only accepts exact parsed origins or the global `*`, and a Node URL probe shows Chrome-extension origins serialize to `origin === "null"`; I did not run a live Gateway handshake.

## Solution Assessment

No, not as sketched. The prefix-loop proposal is only a starting point; the maintainable fix needs maintainer-approved wildcard semantics plus regression coverage for allowed, rejected, exact, global wildcard, WebSocket, and trusted-proxy HTTP cases.

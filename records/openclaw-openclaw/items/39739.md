## Summary

Keep open: current main and v2026.6.11 still only support exact `gateway.controlUi.allowedOrigins` matches plus the global `*`, and the open related PRs cover exact custom-scheme origins or loopback-port patterns rather than `chrome-extension://*`. The remaining work is a Gateway origin-policy security/product decision.

## What This Changes

Request support for scheme-level wildcard entries such as `chrome-extension://*` in Gateway Control UI browser-origin allowlisting so changing Chrome extension IDs do not require exact config updates.

## Best Possible Solution

Adopt a maintainer-approved constrained origin-pattern contract, then wire it through runtime checks, schema/help, security audit, docs, UI guidance, and focused allow/reject tests; otherwise document exact origins or the existing global wildcard as the supported choices.

Rationale: This changes the Gateway browser-origin authorization boundary and the current config contract treats `allowedOrigins` as full origins except for the global `*`, so automation should not choose the permanent wildcard grammar or trust model.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve constrained extension pattern policy (recommended):** Add a narrow, documented, audited pattern rule for extension origins with explicit negative tests and no generic prefix matching beyond the approved grammar.
- **Keep exact origins only:** Advance exact custom-scheme origin fixes and accept that changing Chrome extension IDs remain an operator config task.
- **Reject extension-wide trust:** Document that trusting every Chrome extension origin is too broad for Gateway origin authorization and keep `chrome-extension://*` unsupported.

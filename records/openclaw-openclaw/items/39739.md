## Summary

Keep open: current main and the latest release still only support full-origin exact matches or the global `*` allow-all entry for `gateway.controlUi.allowedOrigins`; the merged Chrome-extension relay route solves the official extension workflow, but not this generic scheme-level wildcard policy request.

## What This Changes

The issue requests scheme-level wildcard support in `gateway.controlUi.allowedOrigins`, especially entries such as `chrome-extension://*` for Chrome-extension-origin WebSocket clients.

## Best Possible Solution

Keep the paired official `/browser/extension` path for OpenClaw’s Chrome extension, and only add generic extension-origin wildcard support if maintainers approve a constrained, documented grammar with WebSocket, trusted-proxy HTTP, audit, and negative security coverage.

Question: Should OpenClaw support generic scheme-level browser-origin wildcards such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins`, now that the official Chrome extension has a paired `/browser/extension` route?

Rationale: This changes a Gateway browser-origin authorization boundary, and the current code/docs intentionally expose only exact full origins plus the global allow-all `*`; current related PRs do not settle the security semantics.

Likely owner: steipete

Owner reason: He owns the strongest history across the original Gateway origin hardening and the newly merged official Chrome-extension route.

Owner confidence: high

Options:

- **Keep exact origins plus paired route (recommended):** Reject generic scheme wildcards for now and direct official Chrome-extension users to the paired `/browser/extension` route while exact-origin fixes continue separately.
- **Approve a constrained wildcard grammar:** Allow a narrowly specified `chrome-extension://*` policy with explicit tests, docs, audit handling, and clear limits on which schemes can be wildcarded.
- **Fold into broader origin patterns:** Wait for the `allowedOriginPatterns` design to settle and decide whether Chrome-extension scheme wildcards belong in that separate contract instead of overloading `allowedOrigins`.

## Solution Assessment

No, the issue body's prefix-loop sketch is only a plausible starting point. The best solution needs a maintainer-approved wildcard contract, not an arbitrary `endsWith("*")` prefix match on a security boundary.

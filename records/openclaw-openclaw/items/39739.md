## Summary

Keep open: current main and the latest release still only support exact normalized origins plus the global `*`, while this issue asks for a new scheme-level wildcard policy on a Gateway browser-origin authorization boundary.

## What This Changes

The issue requests support for entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins` so Chrome extension Gateway clients do not need a changing exact extension id in config.

## Best Possible Solution

Decide the allowed wildcard grammar for Gateway browser origins first, then implement the narrowest accepted matcher in the shared origin helper with unit, WebSocket handshake, trusted-proxy HTTP, docs, and negative security coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `gateway.controlUi.allowedOrigins` allow scheme-level wildcard entries such as `chrome-extension://*`, and if so what exact wildcard grammar and scheme limits are acceptable for Gateway browser-origin authorization?

Rationale: The requested behavior changes which browser origins may reach Gateway HTTP/WebSocket handling, and current docs intentionally describe full-origin allowlisting plus the global `*` as the only wildcard policy.

Likely owner: steipete

Owner reason: He authored the key Gateway origin hardening commits and is the strongest history signal for this security-boundary decision.

Owner confidence: high

Options:

- **Approve constrained extension wildcard grammar (recommended):** Define a small explicit grammar for extension-scheme wildcards, implement it in the shared helper, and document allow/reject cases before accepting the feature.
- **Keep exact origins only:** Reject scheme wildcards and rely on exact opaque-origin fixes plus the existing global `*` escape hatch for intentionally broad local testing.
- **Fold into a broader pattern contract:** Wait for the loopback origin-pattern work to settle and decide whether Chrome extension scheme wildcards belong in the same public config contract or a separate one.

## Reproduction Assessment

Yes. Source inspection shows current `checkBrowserOrigin` only accepts exact parsed origins or the global `*`, and a Node URL probe shows Chrome extension origins serialize to `origin === "null"`; I did not run a live Gateway handshake.

## Solution Assessment

No. The issue body's prefix-loop sketch is only a plausible starting point; the best fix needs maintainer-approved wildcard semantics plus regression coverage for allowed, rejected, exact, global wildcard, WebSocket, and trusted-proxy HTTP cases.

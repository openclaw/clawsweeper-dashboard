## Summary

Keep open: current main and the latest release still only support exact parsed origins or the global `*` allow-all entry, while this issue asks for a new scheme-level wildcard policy on a Gateway browser-origin security boundary.

## What This Changes

The issue requests support for scheme-level wildcard entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins`.

## Best Possible Solution

Decide the allowed wildcard grammar for Gateway browser origins first, then implement the narrowest accepted matcher with unit and handshake coverage plus docs for exact, wildcard, and negative cases.

## Reproduction Assessment

Yes for source-level reproduction: current `checkBrowserOrigin` only accepts the global `*` or an exact parsed origin, and Node serializes `chrome-extension://...` origins as `"null"`. No live Gateway run was performed.

## Solution Assessment

No, the proposed prefix loop is only a plausible sketch; the best fix needs an explicit security policy for permitted wildcard patterns and regression coverage for allowed and rejected origins.

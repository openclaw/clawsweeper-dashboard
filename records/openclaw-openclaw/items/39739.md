## Summary

Keep open: current main and v2026.6.11 still support only exact parsed origins or the global `*` allow-all entry, and no related open PR settles the requested scheme-level wildcard security policy.

## What This Changes

The issue requests `gateway.controlUi.allowedOrigins` support for scheme-level wildcard entries such as `chrome-extension://*`.

## Best Possible Solution

Maintainers should approve or reject a constrained Gateway browser-origin wildcard grammar; if approved, implement it in the shared origin checker with docs plus WebSocket, trusted-proxy HTTP, exact-match, global-wildcard, and negative security coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `gateway.controlUi.allowedOrigins` accept scheme-level wildcard entries such as `chrome-extension://*`, and what exact wildcard grammar is acceptable for Gateway browser-origin authorization?

Rationale: The requested behavior changes which browser origins can reach Gateway HTTP/WebSocket handling, and the current documented contract intentionally limits wildcard behavior to the global `*`.

Likely owner: steipete

Owner reason: He introduced and repeatedly hardened the relevant Gateway origin-check boundary, making him the strongest routing candidate for the security/product decision.

Owner confidence: high

Options:

- **Approve constrained wildcard grammar (recommended):** Define a narrow list of allowed scheme-pattern forms, implement it once in `checkBrowserOrigin`, and document positive and negative cases before accepting the feature.
- **Keep exact origins only:** Reject scheme wildcards and rely on exact opaque-origin fixes plus the existing global `*` escape hatch for intentionally broad local testing.
- **Defer to broader pattern design:** Wait for loopback-origin pattern work to settle, then decide whether Chrome extension scheme wildcards belong in the same contract or a separate one.

## Reproduction Assessment

Yes, source-level. Current main parses browser origins with `new URL`, then accepts only exact `parsedOrigin.origin` matches or the global `*`, and Node serializes Chrome extension origins to the opaque `null` origin.

## Solution Assessment

No. The issue body's prefix-loop sketch is only a plausible starting point; the best fix needs maintainer-approved wildcard semantics and regression coverage across WebSocket, trusted-proxy HTTP, exact, global-wildcard, and negative cases.

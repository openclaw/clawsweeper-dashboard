## Summary

Keep open: current main and v2026.6.11 still only support exact parsed origins or the global `*`, while related open PRs cover exact custom origins or loopback-port patterns rather than `chrome-extension://*`; the remaining change needs a Gateway origin-policy security decision.

## What This Changes

Request support for scheme-level wildcard values like `chrome-extension://*` in `gateway.controlUi.allowedOrigins` so Chrome extension ID churn does not require repeated config updates.

## Best Possible Solution

Define a maintainer-approved constrained origin-pattern policy for extension origins, then implement it consistently in schema/help, WebSocket and HTTP origin checks, security audit, docs, and focused allow/reject tests; otherwise document that Chrome extension clients must use exact origins or the existing global wildcard knowingly.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Gateway origin policy allow `chrome-extension://*`, and if yes should that live inside `allowedOrigins` or a separate constrained pattern surface?

Rationale: This changes a Gateway browser-origin authorization boundary and the current config contract treats `allowedOrigins` as exact full origins except for global `*`; automation should not choose the permanent wildcard grammar or extension-origin trust model.

Likely owner: steipete

Owner reason: He introduced and hardened the Gateway browser-origin policy surface, making him the strongest history-backed owner for this security-boundary choice.

Owner confidence: high

Options:

- **Approve constrained extension pattern policy (recommended):** Add a narrow, documented, audited pattern rule for extension origins with explicit negative tests and no generic prefix matching beyond the approved grammar.
- **Keep exact origins only:** Land or sponsor exact custom-scheme origin fixes and accept that changing Chrome extension IDs remain an operator config task.
- **Reject extension-wide trust:** Document that trusting every Chrome extension origin is too broad for Gateway origin authorization and keep `chrome-extension://*` unsupported.

## Reproduction Assessment

Yes. Source inspection plus a Node URL probe show current main compares configured entries against `URL.origin`, while `chrome-extension://<id>` serializes that origin as `null`; I did not run a live Gateway handshake.

## Solution Assessment

No for the proposed minimal prefix match. The capability may be useful, but the maintainable fix is a constrained, audited origin-pattern policy rather than silently expanding a field documented as full-origin-only.

## Summary

Keep open: current main and v2026.6.11 still support only exact parsed origins or the global `*`, while this issue asks for a new scheme-level wildcard policy on a Gateway browser-origin authorization boundary.

## What This Changes

Support scheme-level wildcard entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins`.

## Best Possible Solution

Define the narrow accepted Gateway browser-origin wildcard grammar first, then implement it in the shared origin helper with WebSocket, trusted-proxy HTTP, docs, and negative security coverage.

Rationale: This changes which browser origins can reach Gateway HTTP/WebSocket authorization paths, and current docs intentionally expose only full-origin matches plus the global allow-all wildcard.

Options:

- **Approve constrained scheme wildcards (recommended):** Define a small allowlisted grammar such as hosted opaque schemes only, reject broad regex/hostless patterns, and require source plus handshake coverage before implementation.
- **Keep exact origins only:** Reject scheme wildcards for now and rely on exact opaque-origin fixes plus the existing global `*` escape hatch for intentionally broad local testing.
- **Defer to pattern design:** Wait for the loopback `allowedOriginPatterns` work to settle, then decide whether extension scheme wildcards belong in the same contract or a separate one.

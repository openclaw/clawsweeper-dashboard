## Summary

Keep open: current main and v2026.6.11 still only accept exact parsed origins or the global `*`; scheme-level origin wildcards would widen a Gateway browser-origin authorization boundary and need maintainer security/product approval before implementation.

## What This Changes

Request scheme-level wildcard support such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins` so Chrome extension origins can remain allowlisted across extension ID changes.

## Best Possible Solution

Define a constrained, security-reviewed origin-pattern contract for extension/custom-scheme origins with parser rules, docs, audit behavior, and negative Gateway tests, or explicitly keep exact-origin matching only.

Rationale: This changes which browser-origin WebSocket and trusted-proxy HTTP requests may pass Gateway authorization, so automation should not choose the wildcard grammar or security posture on its own.

Options:

- **Define constrained pattern contract (recommended):** Add a reviewed pattern grammar, docs, audit handling, and allow/reject tests for approved extension/custom-scheme cases before implementation.
- **Keep exact origins only:** Land an exact opaque-origin fix separately and defer changing-extension-ID wildcard support as outside current Gateway policy.
- **Allow only Chrome extension scheme wildcard:** Support `chrome-extension://*` narrowly with scheme-specific matching and negative security tests rather than generic prefix wildcards.

## Reproduction Assessment

Yes, source-level reproduction is high-confidence. Current main compares configured entries against `URL.origin`, and a Node probe shows `chrome-extension://...` serializes to `null`, so `chrome-extension://*` has no matching path today.

## Solution Assessment

No. The proposed minimal prefix match is not the safest maintainable fix for this security boundary; a constrained pattern parser with docs, audit handling, and negative tests is the better shape.

## Summary

Keep open: current `main` and the latest release still support exact `gateway.controlUi.allowedOrigins` entries plus the global `*`, but not scheme-level extension wildcards. The remaining work is a Gateway origin-policy security and product decision, not a conservative cleanup close.

## What This Changes

The issue requests support for scheme-level wildcard origins such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins` so Chrome extension clients do not need a stable extension ID.

## Best Possible Solution

Define a maintainer-approved constrained origin-pattern policy for extension origins, then implement it consistently across schema/help, WebSocket and HTTP origin checks, security audit, docs, and focused allow/reject tests; otherwise document exact origins or the existing global wildcard as the supported choices.

- **Reject extension-wide trust:** Document that trusting every Chrome extension origin is too broad for Gateway origin authorization and keep `chrome-extension://*` unsupported.

## Summary

Keep open: current main and the latest release still only support exact parsed origins or the global `*`, while `chrome-extension://*` remains an unresolved Gateway origin-authorization product and security decision.

## What This Changes

The issue requests scheme-level wildcard support such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins`.

## Best Possible Solution

Define a constrained, security-reviewed origin pattern contract for extension or custom-scheme origins with parser rules, docs, audit behavior, and negative Gateway tests instead of accepting arbitrary prefix wildcards.

Rationale: The requested behavior broadens an origin authorization boundary beyond exact matches and the existing global wildcard, so automation should not choose the permanent security grammar.

Options:

- **Approve constrained scheme patterns (recommended):** Define a narrow grammar for specific schemes, update `checkBrowserOrigin`, docs, config help, and security tests around that contract.
- **Prefer exact custom-scheme origins only:** Keep scheme-wide wildcards rejected and steer fixes toward exact non-standard origin matching such as the linked custom-scheme PRs.
- **Reject core support:** Keep the current exact/global-only contract and require extension relay operators to manage exact origins or use a plugin-owned gateway surface.

No. The proposed generic prefix match is not the best fix for this security boundary; a constrained pattern parser with docs, audit handling, and negative tests is the safer maintainable shape.

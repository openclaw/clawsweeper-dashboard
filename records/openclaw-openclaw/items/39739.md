## Summary

Keep open: current main and the latest release still lack scheme-level wildcard matching for `gateway.controlUi.allowedOrigins`, and the requested `chrome-extension://*` policy changes a Gateway browser-origin security boundary.

## What This Changes

Support scheme-level wildcard entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins` for Chrome extension Gateway clients.

## Best Possible Solution

Define the accepted Gateway browser-origin wildcard grammar first, then implement the narrowest approved matcher in the shared origin helper with WebSocket, trusted-proxy HTTP, docs, and negative security coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `gateway.controlUi.allowedOrigins` accept scheme-level wildcard entries such as `chrome-extension://*`, and what exact grammar and scheme limits are safe for Gateway browser-origin authorization?

Rationale: This would broaden a browser-origin authorization boundary for Gateway WebSocket and trusted-proxy HTTP paths, and current docs intentionally expose only full-origin entries plus the global `*`.

Likely owner: steipete

Owner reason: He has the strongest history on the Gateway origin-check boundary and related security hardening decisions.

Owner confidence: high

Options:

- **Approve constrained extension wildcard grammar (recommended):** Define a small explicit grammar for extension-scheme wildcards, implement it in `checkBrowserOrigin`, and document allow/reject cases before accepting the feature.
- **Keep exact origins only:** Reject scheme wildcards and rely on exact opaque-origin fixes plus the existing global `*` escape hatch for intentionally broad local testing.
- **Fold into broader origin patterns:** Wait for the loopback pattern work to settle and decide whether Chrome extension scheme wildcards belong in the same public config contract or a separate one.

## Reproduction Assessment

Yes, source-level. Current `checkBrowserOrigin` only accepts exact parsed origins or the global `*`, and a Node URL probe shows Chrome extension origins serialize to `origin === "null"`; I did not run a live Gateway handshake.

## Solution Assessment

No, not as sketched. The prefix-loop proposal is only a starting point; the best fix needs maintainer-approved wildcard semantics plus regression coverage for allowed, rejected, exact, global wildcard, WebSocket, and trusted-proxy HTTP cases.

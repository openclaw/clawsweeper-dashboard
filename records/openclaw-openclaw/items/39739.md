## Summary

Keep open: current main and v2026.6.11 still only support exact parsed origins or global `*`, while the requested scheme-level wildcard changes the Gateway browser-origin authorization boundary and needs maintainer security/product direction.

## What This Changes

Request support for scheme-level wildcard entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins`.

## Best Possible Solution

Adopt a maintainer-approved, constrained origin-pattern contract for this security boundary, with parser limits, negative tests, docs, and audit behavior before implementation.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Gateway allow scheme-level browser-origin wildcards such as `chrome-extension://*`, and should that grammar live inside `allowedOrigins` or a constrained pattern field?

Rationale: The source failure is clear, but this changes browser-origin authorization semantics for Gateway clients and current related PRs do not establish the permanent wildcard grammar or security posture.

Likely owner: steipete

Owner reason: He introduced the current Gateway browser-origin hardening and is the strongest history-backed owner for the security-boundary decision.

Owner confidence: high

Options:

- **Define constrained pattern contract (recommended):** Add a reviewed, narrow pattern grammar with tests, docs, and audit handling instead of accepting arbitrary trailing-prefix wildcards.
- **Keep exact origins only:** Continue with exact opaque-origin fixes and reject changing-extension-ID wildcards as outside the current Gateway origin policy.
- **Allow Chrome extension wildcard only:** Permit `chrome-extension://*` in the existing allowlist with scheme-specific matching and negative security tests.

## Reproduction Assessment

Yes. Source-level reproduction is high confidence: current `checkBrowserOrigin` only checks exact parsed origins or global `*`, and Node parses `chrome-extension://...` to opaque `origin=null`.

## Solution Assessment

No, not as proposed. The one-line trailing-`*` prefix match is not proven as the best security-boundary fix; a constrained parser or pattern surface with docs, audit behavior, and negative tests is safer.

## Summary

Keep open: current main and the latest release still only support exact parsed origins or global `*`, while this asks for new scheme-level wildcard semantics on a Gateway browser-origin security boundary.

## What This Changes

Support scheme-level wildcard entries such as `chrome-extension://*` for `gateway.controlUi.allowedOrigins`.

## Best Possible Solution

Define and document a constrained Gateway browser-origin wildcard contract first, then implement the narrowest approved matcher with WebSocket, trusted-proxy HTTP, docs, and negative security coverage.

Options:

- **Approve constrained wildcard grammar (recommended):** Define a small allowed pattern set, implement it in the shared origin helper, and document positive and negative cases before accepting the feature.

- **Defer to broader pattern design:** Wait for loopback origin-pattern work to settle and decide whether Chrome extension scheme wildcards belong in the same contract or a separate one.

## Summary

Keep open: current main and the latest release still only accept exact parsed origins or the global `*`, and the requested scheme-level wildcard changes a Gateway browser-origin authorization boundary that needs maintainer security/product approval.

## What This Changes

Requests `gateway.controlUi.allowedOrigins` support scheme-level wildcard patterns such as `chrome-extension://*` so changing extension IDs do not require repeated exact-origin config edits.

## Best Possible Solution

Define a constrained, security-reviewed origin pattern contract for extension/custom-scheme origins with parser rules, docs, audit behavior, and negative Gateway tests instead of accepting arbitrary prefix wildcards.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Gateway support scheme-level browser-origin wildcards such as `chrome-extension://*`, and if yes should that live inside `allowedOrigins` or in a dedicated constrained pattern setting?

Rationale: This changes which browser-origin WebSocket and trusted-proxy HTTP requests can pass Gateway authorization, so automation should not choose the wildcard grammar or security posture on its own.

Likely owner: steipete

Owner reason: He introduced and continues to review the Gateway origin-security boundary most directly affected by this decision.

Owner confidence: high

Options:

- **Define constrained pattern contract (recommended):** Add a reviewed pattern grammar, docs, audit handling, and allow/reject tests for approved extension/custom-scheme cases before implementation.
- **Keep exact origins only:** Land an exact opaque-origin fix separately and close or defer the changing-extension-ID wildcard request as outside current Gateway policy.
- **Allow only Chrome extension wildcard:** Accept `chrome-extension://*` narrowly, but require scheme-specific matching and negative security tests rather than generic trailing-prefix matching.

## Reproduction Assessment

Yes, source-reproducible. Current main compares configured entries against `URL.origin`, and a Node probe shows `chrome-extension://...` serializes to `null`, so the requested `chrome-extension://*` pattern has no matching path today.

## Solution Assessment

No. The proposed minimal prefix match is not the best fix for this security boundary; a constrained pattern parser with docs, audit handling, and negative tests is the safer maintainable shape.

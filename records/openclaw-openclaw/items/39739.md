## Summary

Keep open: current main and the latest release still only accept exact parsed origins or the global `*`, while this issue asks for a new scheme-level wildcard policy on a Gateway browser-origin security boundary.

## What This Changes

Request support for scheme-level wildcard entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins`.

## Best Possible Solution

Decide the allowed Gateway browser-origin wildcard grammar first, then implement the narrowest accepted matcher with WebSocket, trusted-proxy HTTP, docs, audit, and negative security coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `gateway.controlUi.allowedOrigins` allow scheme-level wildcard entries such as `chrome-extension://*`, and what exact wildcard grammar is acceptable for Gateway browser-origin authorization?

Rationale: The requested behavior broadens which browser origins can reach Gateway HTTP/WebSocket handling, and current docs intentionally limit this config to full origins plus the global `*` allow-all policy.

Likely owner: steipete

Owner reason: He has the strongest history on the current Gateway origin-check boundary and its security hardening.

Owner confidence: high

Options:

- **Approve constrained scheme wildcards (recommended):** Define a small explicit wildcard grammar, implement it in the shared origin helper, and document allow/reject cases before accepting the feature.
- **Keep exact origins only:** Reject scheme wildcards and rely on exact opaque-origin fixes plus the existing global `*` escape hatch for intentionally broad testing.
- **Defer to broader origin-pattern design:** Wait for loopback origin-pattern work to settle, then decide whether extension scheme wildcards belong in that same contract or a separate one.

## Reproduction Assessment

Yes. Source inspection plus a Node URL probe show `chrome-extension://...` serializes to `origin = null`, while current main only checks exact `parsedOrigin.origin` or the global `*`; I did not run a live Gateway reproduction.

## Solution Assessment

No. The issue body's prefix-match sketch is only a plausible starting point; the best fix needs maintainer-approved wildcard semantics and regression coverage for allowed, rejected, exact, global wildcard, WebSocket, and trusted-proxy HTTP cases.

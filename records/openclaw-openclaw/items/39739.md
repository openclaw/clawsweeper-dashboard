## Summary

Keep open: current main and `v2026.6.11` still only allow exact normalized origins or the global `*`, while this issue asks for a new scheme-level wildcard policy on a Gateway browser-origin security boundary.

## What This Changes

Support scheme-level wildcard entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins` so Chrome extension clients with changing IDs can connect without using the global wildcard.

## Best Possible Solution

Have a maintainer choose the allowed wildcard grammar, then implement the narrowest accepted matcher in the shared Gateway origin policy with docs and negative coverage for WebSocket and trusted-proxy HTTP.

Options:

- **Approve constrained extension wildcard grammar (recommended):** Define an explicit extension-scheme-only grammar, add shared matcher coverage, and document the allow/reject cases before implementation.
- **Keep exact origins only:** Reject scheme wildcards and rely on exact opaque-origin fixes plus the existing global `*` escape hatch for deliberately broad local testing.
- **Fold into broader pattern contract:** Wait for the loopback pattern work to settle and decide whether Chrome extension wildcards belong in the same public config contract or a separate one.

## Summary

Keep open: current main and v2026.6.11 still only support exact parsed origins or the global `*`, and scheme-level origin wildcards remain a security-sensitive Gateway config/product decision rather than a cleanup-close candidate.

## What This Changes

Request support for scheme-level wildcard entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins`.

## Best Possible Solution

Define a constrained, security-reviewed origin pattern contract for extension/custom-scheme origins with parser rules, docs, audit behavior, and negative Gateway tests instead of accepting arbitrary prefix wildcards.

## Maintainer Decision

Rationale: This changes which browser-origin WebSocket and trusted-proxy HTTP requests can pass Gateway authorization, so automation should not choose the wildcard grammar or security posture.

Likely owner: steipete

Owner confidence: high

Options:

- **Define constrained pattern contract (recommended):** Add a reviewed pattern grammar, docs, audit handling, and allow/reject tests for approved extension or custom-scheme cases before implementation.
- **Keep exact origins only:** Land exact opaque-origin matching separately and defer the changing-extension-ID wildcard request as outside current Gateway policy.
- **Allow only extension scheme wildcard:** Support a narrow `chrome-extension://*` case with scheme-specific matching and negative security tests, without generic trailing-prefix matching.

## Reproduction Assessment

Yes. Source inspection plus a Node URL probe show `chrome-extension://...` serializes to `origin = null`, while current main only checks exact `parsedOrigin.origin` or the global `*`; I did not run a live Gateway reproduction.

## Solution Assessment

No. The proposed generic prefix match is not the best fix for this security boundary; a constrained pattern parser with docs, audit handling, and negative tests is the safer maintainable shape.

## Summary

Keep open: current main and the latest release still only support exact parsed origins or the global `*` allow-all entry, while this issue asks for a new scheme-level wildcard policy on a Gateway browser-origin security boundary.

## What This Changes

Add support for scheme-level wildcard entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins`.

## Best Possible Solution

Decide the allowed wildcard grammar for Gateway browser origins first, then implement the narrowest accepted matcher with unit, WebSocket handshake, trusted-proxy HTTP, docs, and negative security coverage.

Question: Should `gateway.controlUi.allowedOrigins` allow scheme-level wildcard entries such as `chrome-extension://*`, and if so what exact wildcard grammar is acceptable for the Gateway browser-origin authorization boundary?

Rationale: The request changes which browser origins may reach Gateway HTTP/WebSocket handling, and current repository docs intentionally describe full-origin allowlisting plus the global `*` as the only wildcard policy.

Likely owner: steipete

Owner reason: He introduced and repeatedly hardened this Gateway origin-check boundary, making him the strongest routing candidate for the security/product decision.

Owner confidence: high

Options:

- **Approve a constrained wildcard grammar (recommended):** Define a small set of allowed patterns, implement them in the shared origin helper, and document allow/reject cases before accepting the feature.
- **Keep exact origins only:** Reject scheme wildcards and rely on exact opaque-origin fixes plus the existing global `*` escape hatch for intentionally broad local testing.
- **Defer to broader origin-pattern design:** Wait for the loopback pattern work to settle and then decide whether Chrome extension scheme wildcards belong in the same contract or a separate one.

Yes. Source inspection shows current `checkBrowserOrigin` only accepts exact parsed origins or the global `*`, and a Node URL probe shows `chrome-extension://...` serializes to `origin === "null"`; no live Gateway run was performed.

## Solution Assessment

No, the issue body's prefix-loop sketch is only a plausible starting point. The best fix needs maintainer-approved wildcard semantics and regression coverage for allowed, rejected, exact, global wildcard, WebSocket, and trusted-proxy HTTP cases.

## Summary

Keep open: current main and the latest release still only support exact parsed origins or the global `*` allow-all entry, while this issue asks for a new scheme-level wildcard policy on a Gateway browser-origin security boundary.

## What This Changes

Support scheme-level wildcard entries like `chrome-extension://*` in `gateway.controlUi.allowedOrigins` so Chrome extension origins do not require per-extension-ID allowlist updates.

## Best Possible Solution

Decide the allowed wildcard grammar for Gateway browser origins first, then implement the narrowest accepted matcher with unit, WebSocket handshake, trusted-proxy HTTP, docs, and negative security coverage.

Options:

- **Approve constrained scheme wildcards (recommended):** Define a small allowed pattern grammar, implement it in the shared origin helper, and document positive and negative cases before accepting the feature.
- **Keep exact origins only:** Reject scheme wildcards and rely on exact opaque-origin fixes plus the existing global `*` escape hatch for intentionally broad local testing.
- **Fold into broader origin-pattern design:** Wait for the loopback origin-pattern work to settle and then decide whether extension scheme wildcards belong in that contract or a separate one.

## Summary

Keep open: current main and the latest release still only accept exact parsed origins or the global `*`; supporting `chrome-extension://*` would change Gateway browser-origin authorization policy and needs maintainer security/product review.

## What This Changes

Request support for scheme-level wildcard entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins`.

## Best Possible Solution

Define a constrained, documented origin-pattern contract for Gateway browser-origin checks, or explicitly decide that this boundary remains exact-origin-only except for the existing global `*`.

Unclear. The proposed one-line prefix match is plausible but not yet the best security-boundary design; a constrained parser or dedicated pattern surface with docs, audit behavior, and negative tests is safer.

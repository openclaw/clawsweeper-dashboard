## Summary

Keep open: current main and v2026.6.11 still only accept exact parsed origins or the global `*`, while `chrome-extension://*` would change Gateway browser-origin authorization and needs maintainer security/product approval. Related open PRs cover exact opaque-origin matching or constrained loopback port patterns, but none settles this scheme-level wildcard policy.

## What This Changes

The issue requests scheme-level wildcard support in `gateway.controlUi.allowedOrigins`, such as `chrome-extension://*`, for Chrome extension Gateway WebSocket origins.

## Best Possible Solution

Define a constrained, security-reviewed origin pattern contract for extension/custom-scheme origins with parser rules, docs, audit behavior, and negative Gateway tests instead of accepting arbitrary prefix wildcards.

## Maintainer Decision

Kind: security_boundary

Question: Should Gateway support scheme-level browser-origin wildcards such as `chrome-extension://*`, and if yes should that live inside `allowedOrigins` or in a dedicated constrained pattern setting?

Rationale: This changes which browser-origin WebSocket and trusted-proxy HTTP requests can pass Gateway authorization, so automation should not choose the wildcard grammar or security posture on its own.

Likely owner: steipete

Owner reason: He introduced the origin checker and the non-loopback origin hardening that this wildcard policy would modify.

Owner confidence: high

Options:

- **Define constrained pattern contract (recommended):** Add a reviewed pattern grammar, docs, audit handling, and allow/reject tests for approved extension/custom-scheme cases before implementation.
- **Keep exact origins only:** Land exact opaque-origin matching separately and defer or reject changing-extension-ID wildcards as outside current Gateway policy.
- **Allow only Chrome extension wildcard:** Accept `chrome-extension://*` narrowly inside the existing setting with scheme-specific matching and negative security tests, not generic prefix matching.

## Reproduction Assessment

Yes, at source level. Current main compares allowlist entries to `URL.origin`, and a Node probe shows Chrome extension origins serialize to `null`, leaving no path for `chrome-extension://*` to match today.

## Solution Assessment

No. The proposed minimal prefix match is not the best fix for this security boundary; a constrained pattern contract with docs, audit handling, and negative tests is the safer maintainable shape.

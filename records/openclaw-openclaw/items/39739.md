## Summary

Keep open: current main and the latest release still only accept exact parsed origins or the global `*`; the requested scheme-level wildcard changes Gateway browser-origin security policy, and related open PRs only cover exact opaque origins or constrained loopback patterns.

## What This Changes

The issue requests scheme-level wildcard support such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins` so Chrome extension ID churn does not require config edits.

## Best Possible Solution

Adopt a constrained, security-reviewed origin pattern contract for this boundary, preferably a narrow parser or dedicated pattern surface rather than arbitrary prefix matching, while exact opaque-origin bugs continue through their linked PRs.

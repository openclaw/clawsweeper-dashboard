## Summary

Keep open: current main and the latest release still only accept exact parsed origins or the global `*`, and the requested `chrome-extension://*` behavior remains a Gateway security/product decision not covered by the related exact-origin or loopback-pattern PRs.

## What This Changes

Support scheme-level wildcard entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins` so Chrome extension clients with changing IDs do not need per-ID config updates.

## Best Possible Solution

Define a maintainer-approved constrained origin-pattern policy for extension origins, with schema/help/docs/security-audit alignment plus positive and negative Gateway WebSocket proof; otherwise explicitly reject scheme-level wildcards and keep exact-origin allowlisting as the supported path.

## Summary

Keep open: current `main` and v2026.6.11 still only accept exact `gateway.controlUi.allowedOrigins` entries plus the global `*`, and the related open PRs cover exact custom-scheme origins or loopback-port patterns rather than `chrome-extension://*`. The remaining work is a Gateway origin-policy security/product decision.

## What This Changes

The issue requests opt-in scheme-level wildcard support in `gateway.controlUi.allowedOrigins`, especially `chrome-extension://*` for changing Chrome extension IDs.

## Best Possible Solution

Define a maintainer-approved constrained origin-pattern policy for extension origins, then implement it consistently in schema/help, WebSocket and HTTP origin checks, security audit, docs, and focused allow/reject tests; otherwise document exact origins or the existing global wildcard as the supported choices.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Gateway origin policy allow `chrome-extension://*`, and if yes should it live inside `allowedOrigins` or a separate constrained pattern surface?

Rationale: This changes the Gateway browser-origin authorization boundary, and the current config contract treats `allowedOrigins` as exact full origins except for the global `*`, so automation should not choose the permanent wildcard grammar or trust model.

Likely owner: steipete

Owner reason: He introduced and hardened the Gateway browser-origin policy surface, making him the strongest history-backed owner for this security-boundary choice.

Owner confidence: high

Options:

- **Approve constrained extension pattern policy (recommended):** Add a narrow, documented, audited pattern rule for extension origins with explicit negative tests and no generic prefix matching beyond the approved grammar.
- **Keep exact origins only:** Advance exact custom-scheme origin fixes and accept that changing Chrome extension IDs remain an operator config task.
- **Reject extension-wide trust:** Document that trusting every Chrome extension origin is too broad for Gateway origin authorization and keep `chrome-extension://*` unsupported.

## Reproduction Assessment

Yes. Source inspection plus the Node URL probe give a high-confidence reproduction path: `chrome-extension://<id>` serializes `URL.origin` as `"null"`, while current `checkBrowserOrigin` only compares exact `parsedOrigin.origin` or the global `*`; I did not run a live Gateway handshake.

## Solution Assessment

No for the proposed minimal prefix match. The capability may be useful, but the maintainable solution is a constrained, audited origin-pattern policy rather than silently expanding a field documented as full-origin-only.

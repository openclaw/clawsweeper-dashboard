## Summary

Keep open: current main and the latest release still only allow exact normalized origins or the global `*`, while this issue asks for a new scheme-level wildcard policy on a Gateway browser-origin security boundary.

## What This Changes

The issue asks for `gateway.controlUi.allowedOrigins` to accept scheme-level wildcard entries such as `chrome-extension://*` so Chrome extension origins remain valid across changing extension IDs.

## Best Possible Solution

Decide the allowed wildcard grammar for Gateway browser origins first, then implement the narrowest accepted matcher in the shared origin helper with unit, WebSocket handshake, trusted-proxy HTTP, docs, and negative security coverage.

Rationale: This changes which browser origins may reach Gateway HTTP/WebSocket handling, and current docs intentionally describe full-origin allowlisting plus the global `*` as the only wildcard policy.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve constrained extension wildcard grammar (recommended):** Define a small explicit grammar for extension-scheme wildcards, implement it in the shared helper, and document allow/reject cases before accepting the feature.
- **Keep exact origins only:** Reject scheme wildcards and rely on exact opaque-origin fixes plus the existing global `*` escape hatch for intentionally broad local testing.
- **Fold into broader pattern contract:** Wait for the loopback pattern work to settle and decide whether Chrome extension scheme wildcards belong in the same public config contract or a separate one.

No. The issue body's prefix-loop sketch is only a plausible starting point; the best fix needs maintainer-approved wildcard semantics plus regression coverage for allowed, rejected, exact, global wildcard, WebSocket, and trusted-proxy HTTP cases.

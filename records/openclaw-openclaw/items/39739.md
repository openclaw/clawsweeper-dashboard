## Summary

Keep open: current `main` and the latest release still do not support scheme-level `allowedOrigins` patterns, and the related open PRs deliberately target exact opaque-origin matching rather than the broader wildcard policy this issue requests.

## What This Changes

The issue requests support for scheme-level `gateway.controlUi.allowedOrigins` entries such as `chrome-extension://*` so Chrome extension clients do not need a new exact allowlist entry when their extension ID changes.

## Best Possible Solution

Decide the Gateway origin policy first; if scheme wildcards are approved, implement a restricted hosted-scheme matcher with negative tests, docs, and security-audit wording rather than a generic prefix match.

## Reproduction Assessment

Yes at the source level: current `main` compares only `parsedOrigin.origin` or global `*`, and Node serializes `chrome-extension://abcdefghijklmnop` as origin `null`. I did not run a live Gateway WebSocket repro.

## Solution Assessment

No, not as sketched in the issue. A generic prefix loop is only a plausible implementation; the best fix needs an explicit security policy for allowed wildcard forms plus focused allow/reject coverage.

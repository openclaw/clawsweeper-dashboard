## Summary

Keep open: current main and v2026.6.11 still support only exact parsed origins or the global `*`, while scheme-level wildcard origins would change Gateway browser-origin authorization and need maintainer security/product approval.

## What This Changes

Request to let `gateway.controlUi.allowedOrigins` match scheme-level wildcard entries such as `chrome-extension://*` so Chrome extension clients do not need per-install origin IDs.

## Best Possible Solution

Define a constrained, security-reviewed origin pattern contract for extension/custom-scheme origins, with parser rules, docs, audit behavior, and Gateway allow/reject tests; keep exact custom-scheme fixes separate.

## Maintainer Decision

Question: Should Gateway support scheme-level browser-origin wildcards such as `chrome-extension://*`, and if yes should that live inside `allowedOrigins` or in a dedicated constrained pattern setting?

Rationale: This changes which browser-origin WebSocket and trusted-proxy HTTP requests can pass Gateway authorization, so automation should not choose the wildcard grammar or security posture on its own.

Likely owner: steipete

Owner confidence: high

Options:

- **Define Constrained Pattern Contract (recommended):** Add a reviewed pattern grammar, docs, audit handling, and allow/reject tests for approved extension/custom-scheme cases before implementation.
- **Keep Exact Origins Only:** Land exact opaque-origin fixes separately and defer or close the changing-extension-ID wildcard request as outside current Gateway policy.
- **Allow Chrome Extension Wildcard Only:** Accept `chrome-extension://*` narrowly inside `allowedOrigins`, but require scheme-specific matching and negative security tests rather than generic trailing-prefix matching.

## Reproduction Assessment

Yes. Current main compares configured entries against `URL.origin`, and a Node probe shows `chrome-extension://...` serializes to `null`, so the requested `chrome-extension://*` pattern has no matching path today.

## Solution Assessment

No. The proposed minimal prefix match is not the best fix for this security boundary; a constrained pattern parser with docs, audit handling, and negative tests is the safer maintainable shape.

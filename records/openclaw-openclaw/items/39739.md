## Summary

Keep open: current main and the latest release still support only exact parsed origins or the global `*` allow-all entry, while this issue asks for a new scheme-level wildcard policy on a Gateway browser-origin authorization boundary.

## What This Changes

The issue requests scheme-level wildcard support in `gateway.controlUi.allowedOrigins`, especially `chrome-extension://*`.

## Best Possible Solution

Decide and document the constrained Gateway origin wildcard grammar, then implement the shared matcher with unit, WebSocket handshake, trusted-proxy HTTP, docs, and negative security coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `gateway.controlUi.allowedOrigins` allow scheme-level wildcard entries such as `chrome-extension://*`, and if so what exact wildcard grammar is acceptable for Gateway browser-origin authorization?

Rationale: The request changes which browser origins can reach Gateway HTTP/WebSocket handling, and current docs intentionally describe full-origin allowlisting plus the global `*` as the only wildcard policy.

Likely owner: steipete

Owner reason: He introduced and repeatedly hardened this Gateway origin-check boundary, making him the strongest routing candidate for the security/product decision.

Owner confidence: high

Options:

- **Approve constrained scheme wildcards (recommended):** Define a small allowed grammar, implement it in the shared origin helper, and document allowed and rejected cases before accepting the feature.
- **Keep exact origins only:** Reject scheme wildcards and rely on exact opaque-origin fixes plus the existing global `*` escape hatch for deliberately broad local testing.
- **Defer to broader pattern design:** Wait for the loopback origin-pattern work to settle and then decide whether Chrome extension wildcards belong in the same contract or a separate one.

## Reproduction Assessment

Yes for source-level behavior: current `checkBrowserOrigin` only accepts exact parsed origins or the global `*`, and a Node URL probe shows Chrome extension origins serialize as `origin=null`. No live Gateway run was performed in this read-only review.

## Solution Assessment

No, the issue body's prefix-loop sketch is only a plausible starting point. The best fix needs maintainer-approved wildcard semantics and regression coverage for allowed, rejected, exact, global wildcard, WebSocket, and trusted-proxy HTTP cases.

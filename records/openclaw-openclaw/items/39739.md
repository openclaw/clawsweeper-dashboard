## Summary

Keep open: current main and the latest release still keep `gateway.controlUi.allowedOrigins` to exact parsed origins or the global `*`; the new Chrome extension relay covers the official extension path separately, but it does not implement generic scheme-level wildcard semantics for Control UI/WebChat origins.

## What This Changes

Request support for opt-in scheme-level wildcard entries such as `chrome-extension://*` in `gateway.controlUi.allowedOrigins`.

## Best Possible Solution

Decide the generic browser-origin wildcard policy first; if accepted, implement the narrowest approved matcher in the shared origin helper with WebSocket, trusted-proxy HTTP, docs, and negative security coverage while keeping the dedicated Chrome extension relay separate.

Owner confidence: high

Options:

- **Keep Control UI full-origin only (recommended):** Use the dedicated Chrome extension relay for the official extension and require a clearer generic-extension need before adding scheme wildcards to Control UI origins.
- **Approve a constrained extension wildcard:** Allow only a tightly scoped `chrome-extension://*` grammar with explicit positive and negative Gateway tests and docs.
- **Fold into broader origin patterns:** Wait for the loopback `allowedOriginPatterns` design and decide whether extension schemes belong in that same contract or a separate one.

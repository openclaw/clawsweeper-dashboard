## Label Justifications

- `impact:message-loss`: The gateway removes a queued node request before confirming the paired node received it.
- `maturity:stable`: The affected Gateway runtime and RPC surface is scored M4 Stable in the maturity shortlist.

## Summary

Current main still deletes explicit pending node work inside `drainNodePendingWork` before the gateway attempts to send the RPC response, so a dropped reconnect response permanently loses the request. The report is valid, no open or linked fix PR owns it, and the existing `node.pending.ack` method applies to a separate pending-actions queue.

## What This Changes

Make queued node pending work survive a lost reconnect-time drain response until the node confirms receipt.

## Best Possible Solution

Make pending-work retrieval non-destructive, add a queue-specific acknowledgement operation for returned work IDs, and have every node consumer process idempotently before acknowledging; cover lost response, lost acknowledgement, successful acknowledgement, paging, expiry, and baseline-status behavior.

Yes, at source level with high confidence: enqueue explicit work, invoke the real drain helper or handler, discard its response, and the next drain cannot return the deleted item. The issue also supplies handler-seam observed output; this read-only review did not execute tests.

## Solution Assessment

Yes in direction: a read-then-ack contract is the narrow durable fix. The acknowledgement must be specific to `NodePendingWork` rather than silently reusing the separate `PendingNodeAction` pull/ack queue.

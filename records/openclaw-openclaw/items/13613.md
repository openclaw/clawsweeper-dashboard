## Summary

Keep open: current main and v2026.6.11 still run cron inside each Gateway without a shared cron lease, leader election, coordination backend, or cron leader/status surface. The broader horizontal-scaling and distributed-runtime issues, including the ScalyClaw Redis/BullMQ prototype linked from related discussion, are useful architecture context but do not replace this narrower cron HA request.

## What This Changes

The issue requests distributed coordination for cron jobs so high-availability or blue/green Gateway deployments do not execute the same scheduled work multiple times.

## Best Possible Solution

Define a supported distributed cron ownership contract first, then implement backend-neutral fenced claiming or leader leasing with upgrade-safe config or plugin API, health/CLI visibility, docs, and separate-process tests.

## Reproduction Assessment

Yes, at source level: current main has no shared cron lease, leader check, conditional cross-process claim, or accepted cron coordination config/API. I did not run a live multi-host reproduction in this read-only review.

## Solution Assessment

No, the issue's backend-specific config proposal is not yet the best fix. Redis, etcd, DynamoDB, state_leases, and queue-backed workers are plausible options, but maintainers first need to choose the ownership boundary, failure semantics, and core-versus-plugin API shape.

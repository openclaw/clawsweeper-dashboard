- `impact:message-loss`: Multiple Gateways can independently execute and deliver the same scheduled output, producing duplicate channel messages.

## Summary

Current main and v2026.6.11 still lack cross-Gateway cron ownership: scheduling remains Gateway-process-owned with process-local serialization and no distributed lease, leader election, coordination backend, or operator status surface. Broader scaling RFCs overlap but do not replace this cron-specific request, and recent maintainer-side review explicitly kept the architecture decision open.

## What This Changes

Requests distributed coordination so cron jobs execute once across multiple Gateway instances in high-availability deployments.

## Best Possible Solution

Define a backend-neutral cron ownership and fencing contract, preserve current single-Gateway behavior by default, and require explicit HA health/status visibility plus separate-process integration proof before selecting a bundled backend or plugin seam.

- **Bundle one backend:** Choose and support a core backend such as Redis, accepting its dependency, secrets, health, and upgrade obligations.
- **Require one cron Gateway:** Document and enforce that HA deployments designate exactly one cron-enabled Gateway while other Gateway instances disable cron.

## Reproduction Assessment

Yes at source level: current main has a Gateway-owned timer and process-local lock with no external lease or leader check, so independent Gateways have no shared execution owner. A live multi-process run is not required to establish the missing coordination boundary.

## Solution Assessment

No, directly adding Redis, etcd, and DynamoDB configuration is a useful sketch but not yet the narrowest maintainable solution. Maintainers should first define ownership, fencing, outage behavior, and the core-versus-plugin boundary.

## Risks / Open Questions

- Fail-open behavior during coordination outages can preserve duplicate execution and duplicate delivery, while fail-closed behavior can silently stop scheduled automation; that policy needs an explicit product decision.
- Bundling Redis, etcd, or DynamoDB directly into core would add dependencies, credentials, health checks, configuration, and upgrade obligations that may conflict with OpenClaw's lean, plugin-agnostic architecture.
- Lease expiry, clock skew, long-running jobs, Gateway restarts, and delivery retries require fencing and idempotency semantics; a simple TTL lock can still permit concurrent side effects.

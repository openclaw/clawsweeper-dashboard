## Label Justifications

- `P2`: Production HA duplicate cron execution is a real reliability gap, but the remaining work is an architectural enhancement rather than an urgent confirmed regression or emergency.
- `impact:message-loss`: The issue is about scheduled channel deliveries being duplicated or incorrectly emitted when multiple Gateways can fire the same cron job.

## Summary

Keep open: current main and the latest release still use Gateway-local cron scheduling with local SQLite state and process-local locks only, so the HA coordination request remains unresolved and needs maintainer architecture direction before implementation.

## What This Changes

Request distributed coordination for cron jobs so multiple Gateway instances do not execute the same scheduled job concurrently in HA deployments.

## Best Possible Solution

Define a backend-neutral cron ownership contract first, then implement leased claiming or leader election with upgrade-safe config or plugin API, health/CLI visibility, docs, and separate-process tests.

## Reproduction Assessment

Yes, source-level only: independent Gateways still have no shared lease, leader election, or accepted coordination config/API; a live multi-host repro was not run in this read-only review.

## Solution Assessment

No, not as proposed yet: Redis, etcd, and DynamoDB locks are plausible implementations, but maintainers first need to choose core-versus-plugin ownership, failure semantics, fencing/TTL behavior, and upgrade path.

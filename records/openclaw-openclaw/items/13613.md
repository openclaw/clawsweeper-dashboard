## Label Justifications

- `P2`: This is a real production HA reliability gap with limited blast radius to multi-Gateway cron deployments, but it requires architecture direction before implementation.
- `impact:message-loss`: The issue is about duplicate scheduled deliveries to channels when multiple Gateways execute the same cron job.

## Summary

Keep open. Current main and the latest release still implement cron as a Gateway-local scheduler with process-local duplicate suppression and no distributed lease, leader election, coordination backend, HA health/status, or leader CLI surface; this remains a valid architecture/product follow-up rather than cleanup-close material.

## What This Changes

Request to add distributed cron job ownership or locking so multiple Gateway instances do not execute the same scheduled jobs in HA deployments.

## Best Possible Solution

Define a supported distributed cron ownership model first, then implement it with a versioned config or plugin API boundary, health/status visibility, CLI inspection, docs, and multi-process tests sharing scheduled jobs.

## Reproduction Assessment

Not applicable as a traditional bug repro, but the gap is high-confidence from source: current cron has only process-local locks and no distributed lease or leader path. A real HA repro would run two Gateway processes with the same due job and observe that no external ownership check exists before execution.

## Solution Assessment

Unclear until maintainers choose the architecture. Distributed cron ownership belongs near the Gateway cron scheduler, but Redis/etcd/DynamoDB backends, fail-open behavior, CLI/status shape, and config compatibility need product and owner decisions first.

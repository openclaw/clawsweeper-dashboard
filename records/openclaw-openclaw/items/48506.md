## Summary

Keep open: current main and v2026.6.11 still do not expose resolved target, externality, or cross-context facts on the public `message_sending` hook, and the remaining work needs a maintainer/security decision on the Plugin SDK disclosure boundary.

## What This Changes

Requests optional resolved outbound target context on `PluginHookMessageSendingEvent` so policy plugins can make DLP, allowlisting, compliance, and cross-context decisions without reimplementing target resolution.

## Best Possible Solution

Approve a narrow optional `message_sending` target-context contract populated from canonical outbound resolver and policy facts, then update SDK docs and focused hook/delivery tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What resolved outbound target facts may ordinary loaded plugins receive on `message_sending`, and should that contract be nested as `targetContext` or exposed through a different Plugin SDK shape?

Rationale: The source gap is clear, but the next step defines a public Plugin SDK contract and a security disclosure boundary for channel, account, target, and cross-context information.

Likely owner: steipete

Owner reason: The current history ties steipete to the hook/delivery files, target resolver, outbound policy, and the Plugin SDK/product boundary needing a decision.

Owner confidence: high

Options:

- **Approve narrow target context (recommended):** Expose only stable, policy-useful facts such as target kind, channel id, and cross-context/external booleans, populated from existing outbound resolver and policy state.
- **Keep hook raw for now:** Leave `message_sending` unchanged until a broader plugin policy/trust model decides what target-resolution details plugins may observe.
- **Use an explicit resolver helper:** Document a supported plugin-side resolver path, accepting that plugins may need to opt into lookup cost and may not see the exact runtime-resolved destination for every send.

## Reproduction Assessment

Yes, for the source-level capability gap: current main and v2026.6.11 show no `targetContext` or resolved target facts on `PluginHookMessageSendingEvent`. This is not a runtime bug reproduction; it is a missing public API capability.

## Solution Assessment

Unclear until maintainer/security review chooses the public contract. Optional nested fields are plausible, but the safest implementation is a narrow approved target-context shape that reuses existing resolver and cross-context policy facts.

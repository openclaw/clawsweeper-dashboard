## Summary

Keep open: current main still lacks a channel-level `/agent <id>` command that temporarily switches a direct conversation to another configured agent. Existing support covers configured bindings, thread-bound subagent/session controls, TUI-local agent selection, and one channel-specific dynamic-agent creation path, so this still needs product and security design before implementation.

## What This Changes

The issue requests `/agents` and `/agent <name>` chat commands to temporarily switch the active channel conversation to another configured agent without restarting Gateway or mutating global bindings.

## Best Possible Solution

Design an additive, opt-in conversation-level routing contract that reuses configured agent ids, preserves per-agent session and memory isolation, defines authorization and sandbox rules, and avoids hot-editing global bindings for normal command use.

## Reproduction Assessment

Yes, at source level: `/agents` is implemented for thread-bound subagent/session listings, `/agent` only exists in the TUI, and route resolution still uses configured bindings plus session-key conversation bindings rather than a configured-agent switch.

## Solution Assessment

Unclear as proposed; `/agent <id>` may be the right UX, but the best implementation should be an authorization-aware conversation routing contract instead of hot reloading bindings or ad hoc state files.

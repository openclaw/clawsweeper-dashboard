## Summary

Keep open: current main still has thread/subagent binding controls and TUI-local agent selection, but no channel-level `/agent <id>` command that temporarily reroutes a direct conversation to another configured agent. The remaining work needs a maintainer product/security decision around target authorization, routing authority, and durable conversation state ownership.

## What This Changes

Request a channel/chat command to list configured agents and temporarily switch the current conversation's active agent without editing bindings or restarting Gateway.

## Best Possible Solution

Add an opt-in conversation-level routing contract that reuses configured agent ids, enforces explicit target authorization, preserves per-agent session and memory isolation, and avoids hot-editing global bindings as the command path.

## Reproduction Assessment

Yes, at source level: `/agents` is implemented for thread-bound subagent/session listings, `/agent` only exists in the TUI, and route resolution still uses configured bindings plus session-key conversation bindings rather than a configured-agent switch.

## Solution Assessment

Unclear as proposed; `/agent <id>` may be the right UX, but the best implementation should be an authorization-aware conversation routing contract instead of hot reloading bindings or ad hoc state files.

## Summary

Keep open: current main and v2026.6.11 still provide transcript/cache-backed usage summaries plus run-level `model.usage` diagnostics, but not the requested durable per-call usage ledger with event IDs, source/run/job attribution, idempotency, backfill, or ledger-first readers.

## What This Changes

Request native per-model usage logging for cost tracking, model-mix analysis, and source/session attribution across user, cron, heartbeat, and background model calls.

## Best Possible Solution

Define one canonical completed-model-call accounting contract, likely SQLite-backed, written at the normalized usage/cost seam with safe metadata only, durable event IDs, source/run/job attribution, backfill, and readers for CLI, UI, and plugin summaries.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw make a core durable completed-call usage ledger the canonical accounting source, or keep spend accounting on transcript summaries, diagnostics, and plugin/external seams for now?

Rationale: The evidence shows a real user need, but the boundary affects core storage policy, privacy, gateway/API contracts, plugin capability design, and future UI/CLI readers, so automation should not choose it unilaterally.

Likely owner: steipete

Owner reason: He has the strongest history on current usage-cost summaries, token-use docs, and the prior ledger-scope review.

Owner confidence: high

Options:

- **Design the core ledger first (recommended):** Create a maintainer-owned first phase for a canonical SQLite-backed ledger plus transcript backfill and ledger-first readers, then let plugins consume that stable seam.
- **Expose a plugin seam first:** Prioritize provider-scoped model-usage plugin delivery and leave durable spend ledgers to ClawHub or external plugins until native accounting requirements are clearer.
- **Defer native accounting:** Keep transcript summaries, diagnostics, and documented external tools as the supported path while adjacent usage and auth-profile issues settle.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 can be inspected to show transcript/cache-derived usage summaries and `model.usage` diagnostics exist, but no durable per-call ledger type, writer, idempotency key, backfill, or ledger-first reader exists.

## Solution Assessment

No current implementation fully solves the issue. The maintainable path is a single canonical completed-call accounting contract, not a transcript-only cache, diagnostics-only hook, or standalone plugin ledger that can diverge from OpenClaw summaries.

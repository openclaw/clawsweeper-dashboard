## Summary

Keep open: current main and the latest release still have harness-registry clear paths that can leave gateway/channel dispatch without a required harness, and the linked candidate PR is unmerged and blocked on the intended plugin lifecycle semantics.

## What This Changes

Fix MissingAgentHarnessError failures caused by plugin cache or reload paths clearing the process-wide agent harness registry during Discord, cron, or gateway agent turns.

## Best Possible Solution

Land an ownership-aware harness lifecycle fix that prevents active gateway dispatch from observing a missing required harness while still clearing disabled or unscoped plugin-owned harnesses according to a maintainer-approved contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For empty plugin scopes and plugin cache reloads, which agent harness entries should remain selectable in the process-global registry while the active plugin registry is empty or being rebuilt?

Rationale: Current source still exposes clear-and-empty registry windows, but the candidate fix changes plugin disablement and activation semantics by restoring every prior harness; automation cannot choose that ownership contract safely.

Likely owner: steipete

Owner reason: This handle introduced the pluggable agent harness registry and is the strongest history signal for deciding the registry ownership contract.

Owner confidence: high

Options:

- **Preserve Approved Always-On Harnesses (recommended):** Preserve only maintainer-approved built-in or provider-owned harnesses during empty-scope reloads, and explicitly clear disabled or unscoped plugin-owned harnesses.
- **Accept Restore-All Semantics:** Allow all previously registered harnesses to survive empty-scope reloads and document that plugin disablement does not immediately remove process-global harnesses.
- **Use Readiness or Retry Instead:** Keep empty-scope clearing strict and queue or retry channel dispatch until plugin runtime readiness is restored.

## Reproduction Assessment

No for a high-confidence live current-main race reproduction in this read-only pass; yes at source level, because current main still has paths that clear the process-global harness registry while selection reads from that registry.

## Solution Assessment

No final fix is on main yet. The best fix is not a blanket retry or restore-all patch; it needs an ownership-aware lifecycle contract plus proof that affected Discord, cron, or gateway paths recover without leaving disabled plugin harnesses callable.

## Summary

Keep open: current main still has the process-global harness clear paths and empty-plugin-scope branches that can leave required harnesses unavailable, and the related repair remains an open candidate rather than a merged fix.

## What This Changes

The issue reports intermittent MissingAgentHarnessError failures when plugin/cache reloads clear or empty the agent harness registry, causing Discord, cron, or gateway agent turns to fail before model execution.

## Best Possible Solution

Land an ownership-aware harness lifecycle fix that preserves only maintainer-approved always-on harnesses, clears disabled or unscoped plugin-owned harnesses, covers loader and gateway empty-scope paths, and proves the affected gateway/channel path after patching.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should empty-plugin-scope reloads preserve all previously registered agent harnesses, preserve only core or bundled provider harnesses, or intentionally clear everything and make callers wait or retry?

Rationale: All three repair shapes are implementable, but the durable behavior changes plugin lifecycle and disablement semantics for third-party harnesses.

Likely owner: steipete

Owner reason: This person introduced the pluggable harness registry and is the best available routing candidate for the harness ownership contract.

Owner confidence: high

Options:

- **Preserve only approved harnesses (recommended):** Keeps configured built-in runtimes available across empty-scope reloads while still respecting plugin disablement for third-party harnesses.
- **Preserve all harnesses:** Matches the simpler open-PR approach but may leave third-party plugin harnesses selectable after an explicit empty active registry.
- **Clear and add readiness or retry:** Keeps empty-scope semantics strict but requires dispatch paths to wait or retry so channel and cron messages do not fail visibly.

## Reproduction Assessment

No for a high-confidence live reproduction of the exact current-main timing race; yes at source level for the remaining lifecycle hazard. Current main and the latest release still clear harness state in loader and gateway empty-scope paths and still select from the process-global harness registry.

## Solution Assessment

Unclear as a final implementation path: retrying can mask real missing-runtime states, atomic restore alone does not settle empty-scope semantics, and the open restore-all approach is too broad without maintainer-approved ownership rules.

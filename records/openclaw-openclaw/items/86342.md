## Maintainer Decision

Required: true

Kind: product_direction

Question: What harness lifecycle contract should OpenClaw enforce when plugin reload or gateway startup resolves to an empty active plugin scope?

Rationale: Current code can clear process-global harness state, but preserving every prior harness may keep disabled or unscoped plugin-owned code callable; the correct boundary is an ownership/product decision, not a mechanical retry choice.

Likely owner: steipete

Owner reason: The registry was introduced by steipete and the decision crosses agent harness, plugin lifecycle, and provider-routing ownership boundaries.

Owner confidence: medium

Options:

- **Preserve Only Approved Always-On Harnesses (recommended):** Filter preservation to maintainer-approved provider or always-on harnesses and clear plugin-owned harnesses that are disabled or outside the active scope.
- **Accept Restore-All Semantics:** Allow previous harnesses to survive an empty active registry, but document and test that plugin disablement does not revoke those harnesses until a broader lifecycle reset.
- **Clear And Gate Dispatch:** Keep empty scopes fail-closed and add readiness/retry behavior so channel or cron dispatch waits instead of surfacing a transient MissingAgentHarnessError.

## Reproduction Assessment

No live current-main reproduction of the exact timing race was established, but yes at source level: current main still clears process-global harness state in loader and gateway empty-scope paths and selection still reads that global registry.

## Solution Assessment

Unclear as a final implementation path: retrying can mask real missing-runtime states, atomic restore alone does not settle empty-scope clearing, and the open restore-all PR is too broad without ownership rules.

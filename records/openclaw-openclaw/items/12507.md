## Summary

Keep open: current main has advisory ClawHub verification and provenance metadata, but the runtime loader still accepts SKILL.md without trusted signature enforcement or unsigned-skill capability policy.

## What This Changes

Requested native SKILL.md integrity verification, signing, loader checks, and degraded or restricted behavior for unsigned skills.

## Best Possible Solution

Keep this as the canonical native SKILL.md trust-boundary issue and define a staged design binding ClawHub verification, persisted expected integrity, loader-time signature checks, unsigned capability policy, and migration.

Rationale: This decides the permanent trust root, signature envelope, revocation behavior, unsigned defaults, and upgrade compatibility for third-party instructions loaded into agent context.

Owner confidence: high

Options:

- **Adopt staged runtime trust model (recommended):** Define a versioned digest/signature contract, persist trusted metadata at install/update, then add loader-time warn/strict enforcement and unsigned capability restrictions with migration guidance.
- **Keep verification advisory:** Keep ClawHub verify output and install provenance as user-visible trust signals without runtime blocking until maintainers define stronger enforcement.
- **Split design first:** Track issuer/signature format, ClawHub metadata, loader checks, capability policy, and migration as separate owner-reviewed design tasks before implementation.

## Solution Assessment

Unclear until maintainers choose the security contract. A hash-only patch is not the best solution because the durable fix needs trusted metadata, runtime verification, unsigned compatibility policy, and migration semantics.

## Summary

Keep open: current main and v2026.6.11 have advisory ClawHub verification/provenance groundwork, but still do not enforce trusted SKILL.md signatures or digests before runtime prompt use; unsigned-skill capability policy remains product/security design.

## What This Changes

The issue requests cryptographic integrity or signature verification for SKILL.md files and restricted behavior for unsigned skills.

## Best Possible Solution

Define one canonical native skill trust model that binds ClawHub or publisher signatures to exact loaded skill contents, persists and reverifies expected state, exposes status, and specifies unsigned or revoked capability policy with migration.

Rationale: The remaining work chooses security boundaries, trust roots, revocation behavior, unsigned compatibility, and likely config/profile semantics that automation should not invent.

Likely owner: steipete

Owner confidence: high

Options:

- **Design canonical signed-skill trust model (recommended):** Define publisher keys, signed digests, revocation, lock/origin binding, status surfaces, and unsigned compatibility before runtime enforcement lands.
- **Ship advisory verification first:** Keep signatures and hashes informational for now, reducing upgrade breakage but leaving this runtime trust boundary open.
- **Require verified skills for full capability:** Fail closed or degrade unsigned skills by default, improving security while requiring a migration and override plan for existing installations.

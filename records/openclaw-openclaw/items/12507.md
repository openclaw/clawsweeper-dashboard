## Summary

Keep open: current main and v2026.6.11 still do not enforce trusted SKILL.md signatures or unsigned-skill capability policy at runtime, even though main now has partial ClawHub install provenance and advisory verification surfaces.

## What This Changes

The issue requests cryptographic verification/signing for SKILL.md skill content, trusted distribution metadata, and capability restrictions for unsigned skills.

## Best Possible Solution

Keep this as the canonical native skill integrity/signature tracker and design one trust contract that spans ClawHub metadata, install/update provenance, runtime SKILL.md loading, user-visible status, and unsigned capability policy; treat existing projects like @ellistevo/openclaw-secure and the SkillSandbox/APort discussion as design input, not a reason to close OpenClaw’s core trust gap.

## Reproduction Assessment

Yes, source-level. Current main loads SKILL.md into Skill records and runtime snapshots without comparing a trusted signature, persisted digest, revocation state, or unsigned capability tier.

## Solution Assessment

No, not as a direct automatic fix. The requested direction is valid, but maintainers still need to choose trust roots, signature authority, revocation behavior, compatibility defaults, and operator overrides before code is safe to land.

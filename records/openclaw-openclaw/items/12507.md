## Summary

Keep open: current main and v2026.6.11 have ClawHub skill verification/provenance metadata, but they still do not enforce trusted SKILL.md signatures or unsigned-skill capability policy at runtime. This remains the canonical security/product design issue rather than a cleanup-close candidate.

## What This Changes

The issue requests cryptographic integrity verification, code signing, and unsigned-skill restrictions for SKILL.md-based skills.

## Best Possible Solution

Keep this as the canonical native skill trust-boundary issue and settle a staged design that binds ClawHub verification, persisted expected integrity, loader-time signature checks, unsigned policy, and migration before enforcement.

Rationale: The remaining work defines trust roots, issuer/signature semantics, revocation, unsigned defaults, and upgrade behavior for third-party instructions, which automation cannot choose safely.

Likely owner: steipete

Owner confidence: high

Options:

- **Adopt staged runtime trust model (recommended):** Define a versioned digest/signature contract, persist trusted metadata at install/update, then add loader-time warn/strict enforcement and unsigned capability restrictions with migration guidance.
- **Keep verification advisory:** Keep ClawHub verify output and install provenance as user-visible trust signals without runtime blocking until maintainers define a stronger enforcement API.
- **Split design first:** Track issuer/signature format, ClawHub metadata, loader checks, capability policy, and migration as separate owner-reviewed design tasks before code work.

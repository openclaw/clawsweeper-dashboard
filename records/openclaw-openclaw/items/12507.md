## Summary

Keep open: current main and v2026.6.11 still load SKILL.md into skill records and runtime snapshots without trusted signature/digest enforcement or an unsigned-skill capability policy; the merged ClawHub provenance work is useful groundwork but not runtime verification.

## What This Changes

The issue requests signed or otherwise trusted integrity verification for SKILL.md skill content before runtime use.

## Best Possible Solution

Keep this as the canonical native skill signature work and define trust roots, revocation, persisted provenance, runtime load enforcement, status surfaces, and unsigned capability policy before implementation.

## Reproduction Assessment

Yes, source inspection gives a high-confidence current-main and v2026.6.11 proof: SKILL.md is read into Skill records and runtime snapshots without comparing a trusted signature, persisted digest, revocation state, or unsigned capability tier. This is a feature/security design gap rather than a failing user-flow bug.

## Solution Assessment

No as a one-shot Ed25519 or hash patch. The maintainable solution needs maintainer-approved trust roots, revocation, compatibility defaults, ClawHub metadata, and operator override behavior before runtime enforcement lands.

## Summary

Keep open: current main has ClawHub verification, provenance, and lock metadata, but native skill runtime loading still accepts local SKILL.md bytes without trusted signature, digest, revocation, or unsigned capability enforcement.

## What This Changes

The issue requests cryptographic integrity and signature verification for skills, with unsigned skills restricted or degraded by policy.

## Best Possible Solution

Keep this as the canonical native skill signature/integrity tracker and define one ClawHub-backed trust contract with persisted expected integrity, runtime load verification, revocation, visible status, unsigned/degraded capability policy, and operator override/migration semantics.

## Reproduction Assessment

Yes, as a source-level feature gap: current main reads SKILL.md into Skill records and runtime snapshots without comparing trusted signature, persisted digest, revocation state, or unsigned capability tier.

## Solution Assessment

Unclear as a final implementation path: signature verification is the right problem area, but maintainers still need to choose trust roots, revocation, compatibility defaults, and operator override behavior before implementation.

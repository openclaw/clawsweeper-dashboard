## Summary

Keep open: current main has advisory ClawHub verification and install provenance, but it still does not enforce trusted SKILL.md signatures, loader-time integrity checks, or unsigned-skill capability policy. This remains the canonical security/product trust-boundary item rather than a cleanup-close candidate.

## What This Changes

The issue requests cryptographic integrity and signature verification for SKILL.md skills, including ClawHub signing metadata and restricted behavior for unsigned skills.

## Best Possible Solution

Keep this as the canonical native SKILL.md trust-boundary issue and define a staged design that binds ClawHub verification, persisted expected integrity, loader-time signature checks, unsigned policy, and migration before enforcement.

Question: What native SKILL.md trust model should OpenClaw adopt for third-party skills: advisory verification only, runtime signature enforcement, or staged enforcement tied to capability policy?

Rationale: The remaining work defines trust roots, issuer/signature semantics, revocation, unsigned defaults, and upgrade behavior for third-party instructions, which automation cannot choose safely.

Likely owner: steipete

Owner reason: steipete has the strongest visible review and history signal across skill loading, ClawHub lifecycle, and security hardening for this trust boundary.

Owner confidence: high

Options:

- **Adopt staged runtime trust model (recommended):** Define a versioned digest/signature contract, persist trusted metadata at install/update, then add loader-time warn/strict enforcement and unsigned capability restrictions with migration guidance.
- **Keep verification advisory:** Keep ClawHub verify output and install provenance as user-visible trust signals without runtime blocking until maintainers define a stronger enforcement API.
- **Split the design first:** Track issuer/signature format, ClawHub metadata, loader checks, capability policy, and migration as separate owner-reviewed design tasks before code work.

Yes for the feature gap: source inspection shows current main records some ClawHub provenance metadata but the loader still returns SKILL.md skills without trusted signature or unsigned-policy state. This is not a broken existing behavior repro; it is a verified missing security capability.

## Solution Assessment

Unclear until maintainers choose the security contract. A hash-only patch is not the best solution because the durable fix needs trusted metadata, runtime verification, unsigned compatibility policy, and migration semantics.

## Summary

Keep open: current main records some ClawHub skill provenance and exposes verification status, but runtime skill loading still accepts SKILL.md without trusted signature enforcement or an unsigned-skill capability policy. This remains canonical security/product design work rather than a conservative cleanup close.

## What This Changes

The issue requests cryptographic integrity/signature verification for native SKILL.md skills, ClawHub signing infrastructure, and degraded capability policy for unsigned skills.

## Best Possible Solution

Keep this as the canonical skill-signature trust-model item and define one maintainer-approved end state covering ClawHub signed metadata, install verification, persisted expected integrity, runtime loader enforcement, user-visible status, and unsigned compatibility policy.

## Reproduction Assessment

Yes, source-reproducible: current loader and snapshot code load SKILL.md without a signature gate, while ClawHub install provenance is recorded but not enforced during runtime loading.

## Solution Assessment

Unclear until maintainers choose the trust model; a local hash-only repair or informational verify command would not authenticate publishers or bind runtime loading to trusted state.

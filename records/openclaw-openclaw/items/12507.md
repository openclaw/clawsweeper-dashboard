## Summary

Keep open: current main has useful ClawHub verification, security-verdict, Skill Card, and local provenance metadata, but it still does not enforce trusted SKILL.md signatures at runtime or define unsigned-skill capability policy.

## What This Changes

The issue requests cryptographic signature and integrity verification for SKILL.md skills, including ClawHub signing metadata and degraded capability policy for unsigned skills.

## Best Possible Solution

Keep this as the canonical native SKILL.md trust-boundary item and define a staged model that binds ClawHub verification, persisted expected integrity, loader-time signature checks, unsigned capability policy, CLI/UI status, and migration.

Options:

- **Adopt Staged Runtime Trust Model (recommended):** Define a versioned digest/signature contract, persist trusted metadata at install/update, then add loader-time warn/strict enforcement and unsigned capability restrictions with migration guidance.
- **Keep Verification Advisory:** Keep ClawHub verify output and install provenance as user-visible trust signals without runtime blocking until maintainers define a stronger enforcement API.
- **Split Design First:** Track issuer/signature format, ClawHub metadata, loader checks, capability policy, and migration as separate owner-reviewed tasks before code work.

## Reproduction Assessment

Yes for the feature gap: source inspection shows current main records some ClawHub provenance and verification metadata, but the loader still returns SKILL.md skills without trusted signature or unsigned-policy state.

## Solution Assessment

Unclear until maintainers choose the security contract. A hash-only or advisory-only patch is not the best solution because durable protection needs trusted metadata, runtime verification, unsigned compatibility policy, and migration semantics.

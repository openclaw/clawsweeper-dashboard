## Summary

Keep open: current main has useful ClawHub skill provenance and verification metadata, but the central request remains unresolved because native skills are still loaded without runtime signature enforcement or a maintainer-approved unsigned-skill capability policy.

## What This Changes

The issue requests cryptographic code verification and signatures for installed skills, including trusted `SKILL.md` integrity and unsigned-skill handling.

## Best Possible Solution

Adopt a maintainer-approved staged native skill trust model that persists trusted registry metadata, verifies `SKILL.md` at load time, defines unsigned/degraded capability behavior, and documents the upgrade path.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What native skill trust model should OpenClaw adopt for signed, unsigned, and unverifiable `SKILL.md` content?

Rationale: The remaining work sets a security boundary and could intentionally block or degrade existing installed skills, so automation cannot choose the trust root, signature format, revocation behavior, or compatibility policy alone.

Likely owner: steipete

Owner reason: The prior review and discussion route this as canonical product/security trust-boundary work rather than a narrow implementation patch.

Owner confidence: medium

Options:

- **Staged signed-skill enforcement (recommended):** Define a signed trust envelope and loader-time verification now, start unsigned skills in an explicit warning/degraded mode, and reserve strict blocking for a documented policy milestone.
- **Advisory verification only:** Keep install and `skills verify` metadata informational, which preserves compatibility but leaves runtime prompt loading without an enforceable trust boundary.
- **Strict signed-only loading:** Require valid signatures before loading ClawHub skills, which gives the clearest boundary but risks breaking existing users without a migration window.

## Reproduction Assessment

Yes for the source-level gap: current main persists some ClawHub provenance but still loads skills without runtime signature enforcement or trust-policy fields.

## Solution Assessment

Unclear until maintainers choose the trust contract; advisory hashes alone are not enough to solve trusted `SKILL.md` loading, while strict blocking needs an upgrade policy.

## Summary

Current main still has provider cooldown and session-suspension behavior, but it does not provide the durable capacity-wait prompt queue requested here, so the item remains necessary. The work should stay open as a core runtime/storage design item rather than being closed by the partial followup-restart or provider-cooldown PRs.

## What This Changes

Request durable queuing of prompts when API/provider limits prevent an immediate response, with visible waiting state and automatic resume once capacity is available.

## Best Possible Solution

Design a maintainer-approved SQLite-backed capacity-wait queue that stores the pending prompt/run intent, integrates with provider cooldown and retry timing, exposes a clear waiting state, and replays exactly once after capacity returns.

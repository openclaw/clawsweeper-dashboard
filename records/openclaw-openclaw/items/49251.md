## Summary

Keep open: current main still has process-local followup queues, rate-limit cooldown/error copy, and quota suspension metadata, but not the requested durable capacity-wait prompt queue with visible waiting state and automatic replay; the related PRs are open partial slices rather than merged fixes.

## What This Changes

The issue requests that prompts blocked by API/provider limits remain queued, visible to the user, and automatically resumed when capacity returns.

## Best Possible Solution

Keep this as the canonical design tracker for a SQLite-backed capacity-wait queue integrated with provider cooldowns, user-visible waiting state, and exactly-once replay; review the related PRs as partial implementation candidates.

## Reproduction Assessment

No high-confidence live reproduction was run. Source inspection does show the missing current-main behavior: followup queues are process-local and provider exhaustion becomes cooldown/suspension metadata or a user-facing failure, not a durable queued prompt with automatic replay.

## Solution Assessment

Unclear pending maintainer design. A durable queue is the right direction, but the JSONL sidecar sketch conflicts with the repo's SQLite-first runtime-state policy; the best path is a maintained SQLite-backed capacity-wait design tied to provider retry semantics.

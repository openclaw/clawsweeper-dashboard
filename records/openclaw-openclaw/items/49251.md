## Summary

Keep open: current main and the latest release still have process-local followup queues plus provider cooldown/session suspension, but they do not provide a durable capacity-wait prompt queue with visible waiting state and automatic replay after all usable models are API-limited.

## What This Changes

The issue requests preserving prompts when provider API limits prevent any current or fallback model from responding, showing that work is waiting, and resuming automatically when capacity returns.

## Best Possible Solution

Define and land a maintainer-approved SQLite-backed capacity-wait queue that stores prompt payloads, provider cooldown metadata, visible wait status, and exactly-once replay semantics.

## Reproduction Assessment

No high-confidence live reproduction was run. Source inspection shows that all-model fallback exhaustion leads to cooldown copy/session suspension rather than a durable queued prompt, which is enough to keep the issue open but not enough for strict bug automation.

## Solution Assessment

Unclear pending maintainer design. A durable queue is the right direction, but it should be SQLite-backed and integrated with provider cooldown/status semantics rather than a JSONL sidecar or isolated cooldown tweak.

## Summary

Keep open: current main still records provider cooldown/session suspension and visible rate-limit copy, but it does not persist the blocked prompt itself as a durable capacity-wait queue or replay it automatically; overlapping PRs remain open and partial.

## What This Changes

Request to durably queue prompts that cannot run because the current and fallback models are API-limited, show the waiting state, and resume automatically.

## Best Possible Solution

Define and land a core SQLite-backed capacity-wait queue that stores prompt payloads, provider cooldown metadata, visible waiting status, and exactly-once replay semantics while reconciling the open followup and cooldown PR slices.

## Solution Assessment

Unclear pending maintainer design. A durable queue is likely the right direction, but it should be SQLite-backed and integrated with provider cooldown/status semantics rather than a JSONL sidecar or isolated cooldown tweak.

## Summary

Keep this open: current main has in-process followup queues, short-window provider retry/fallback, and quota suspension metadata, but it still does not provide the requested durable capacity-wait prompt queue with visible waiting state and automatic replay after provider capacity returns.

## What This Changes

The issue requests preserving prompts that cannot run because all current and fallback models are API-limited, showing them as waiting, and resuming them automatically when capacity returns.

## Best Possible Solution

Design one core-owned SQLite-backed capacity-wait queue that coordinates provider cooldown/session suspension, visible waiting status, restart recovery, and exactly-once replay, then converge or close the partial PRs against that design.

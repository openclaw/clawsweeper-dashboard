## Summary

Current main still does not provide the requested durable provider-limit prompt queue: it has in-memory follow-up queues, provider cooldown/suspension metadata, and adjacent durable delivery queues, but not a persisted prompt/run-intent queue that visibly waits and replays after capacity returns. Keep this open for maintainer product and storage design, especially now that the broader run-lifecycle design issue overlaps but does not fully replace this narrower provider-capacity request.

## What This Changes

The issue asks OpenClaw to keep provider-rate-limited prompts visibly queued and automatically resume them once model capacity returns.

## Best Possible Solution

Adopt a maintainer-approved SQLite-backed capacity-wait queue that stores pending prompt/run intent, integrates with provider cooldown timing, exposes a waiting state, and replays exactly once after capacity returns.

## Summary

Keep open: current main has in-process followup queues and provider cooldown/session suspension metadata, but it still does not implement a durable capacity-wait prompt queue with visible waiting state and automatic replay. The directly related retry issue was already closed as duplicate of this issue, while the open PRs are partial slices rather than merged canonical fixes.

## What This Changes

Request to preserve prompts blocked by provider/API limits, show the user they are waiting, and resume processing automatically when capacity returns.

## Best Possible Solution

Keep this as the canonical design tracker for a SQLite-backed capacity-wait queue integrated with provider cooldowns, user-visible waiting state, and exactly-once replay.

## Reproduction Assessment

No live provider-limit reproduction was run. Source inspection gives a medium-confidence reproduction of the missing behavior: current main has process-local followup queues and provider suspension metadata, but no durable prompt replay queue for capacity waits.

## Solution Assessment

No, the JSONL sidecar sketch in discussion is not the best final solution under current repo policy. The maintainable path is a maintainer-approved SQLite-backed queue/retry design that reuses provider cooldown and wake primitives without adding a parallel runtime-state store.

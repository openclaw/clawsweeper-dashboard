## Summary

Issue #49251 should stay open because current main has in-process followup queueing, bounded provider retry/fallback, and session quota suspension, but it still lacks the requested durable capacity-wait prompt queue that survives restarts and automatically resumes queued work after provider capacity returns.

## What This Changes

The issue requests a durable prompt queue that holds user prompts while all provider/API-limit options are exhausted, waits for capacity, then resumes delivery without requiring the user to re-prompt.

## Best Possible Solution

Design one core-owned SQLite-backed capacity-wait queue that coordinates provider cooldown/session suspension, visible waiting status, restart recovery, and exactly-once replay, then either merge or close the overlapping partial PRs against that design.

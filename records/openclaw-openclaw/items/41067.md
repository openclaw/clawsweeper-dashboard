## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.88

Full review comments:

- **[P1] Gate restart abort notices to restart closes:** `src/gateway/server-close.ts:137-147`
  - body: `createGatewayCloseHandler` runs this block for every close, but it aborts active chat runs with `stopReason: "shutdown"` and injects a gateway restart transcript notice before checking whether this is actually a restart. A normal shutdown can therefore write a false restart notice and interrupt active chat state; keep this path under the explicit restart close flow.
  - confidence: 0.9
- **[P1] Use the filtered active-run projection:** `src/gateway/server/ws-connection/message-handler.ts:104-110`
  - body: `listActiveChatRuns` exposes every abort-controller entry in the hello snapshot, while current session state filters out hidden, inactive, and agent-owned entries before marking a session busy. A reconnect can recover a run that the UI should not treat as abortable, leaving the composer stuck or cross-scoped.
  - confidence: 0.86
- **[P1] Move the snapshot field to the live protocol schema:** `src/gateway/protocol/schema/snapshot.ts:64`
  - body: `activeChatRuns` is added under the old `src/gateway/protocol` schema, but current main's hello schema is owned by `packages/gateway-protocol/src/schema/snapshot.ts` and generated clients read from that package. As-is, a rebase would either conflict or leave native/browser protocol contracts out of sync.
  - confidence: 0.88
- **[P2] Return false when transcript setup fails:** `src/gateway/server-restart-sentinel.ts:32`
  - body: `injectRestartNoticeIntoSession` can throw from session loading, path resolution, or `ensureGatewayTranscriptFile`; callers only enqueue the fallback when the helper returns `false`. Because the sentinel has already been consumed, an exception drops the restart notice entirely instead of falling back to a system event.
  - confidence: 0.84
- **[P2] Choose recovered runs deterministically:** `ui/src/ui/app-gateway.ts:126-137`
  - body: `resolveActiveChatRunForSession` returns the first matching array entry, but the server can expose multiple run IDs for one session. If an older entry wins, later deltas/finals for the newest run are ignored by runId checks and the chat can stay busy or stale; select the current/newest matching run deterministically.
  - confidence: 0.82

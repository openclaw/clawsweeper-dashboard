## Label Justifications

- `impact:message-loss`: The reported dead reconnect loop can leave an IRC account unable to receive or send messages while status still appears healthy.
- `impact:ux-friction`: The status surface can mislead operators into seeing the IRC account as healthy, increasing troubleshooting burden without an in-product failure signal.

## Summary

Keep this open: current main still has the IRC post-ready reconnect loop with a fixed one-second retry and no disconnected/error status signal, and no merged duplicate or current implementation solves the fatal-login path.

## What This Changes

The issue requests that IRC post-ready reconnect failures stop looking healthy and stop retrying forever at a fixed one-second cadence after fatal login errors.

## Best Possible Solution

Keep the fix plugin-local where possible: publish honest IRC `connected: false` and `lastError` status on disconnect/reconnect failure, replace the fixed one-second retry with bounded backoff, and only mark terminal if maintainers choose that policy.

- **Capped retry with honest status (recommended):** Keep retrying with bounded backoff and clear disconnected/error status so operators see the outage while server-side fixes can recover without process restart.
- **Terminal fatal disconnect:** Treat 432/464/465 on reconnect as a terminal account failure, stop reconnecting, and require operator action before the account runs again.
- **Status-only first slice:** First land disconnected/error status for the current loop, then decide the retry/backoff policy in a follow-up.

## Reproduction Assessment

Yes at source level, but not by a live run in this read-only review. A loopback IRC server that accepts the first `001`, drops the ready socket, then returns 432/464/465 on reconnect follows the current `onDisconnect` to fixed-delay `scheduleReconnect()` path.

## Solution Assessment

Unclear until maintainers decide the fatal-login policy. The narrowest maintainable direction appears to be honest disconnected/error status plus capped backoff, with permanent terminal failure only if maintainers explicitly choose it.

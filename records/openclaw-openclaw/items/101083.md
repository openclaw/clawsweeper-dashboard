## Label Justifications

- `P2`: This is a normal-priority channel reliability bug with limited blast radius to IRC accounts that become non-recoverable after a successful connection.
- `impact:message-loss`: A dead IRC monitor can miss inbound and outbound channel traffic while the account still appears healthy.
- `impact:ux-friction`: Operators are sent to status surfaces that can remain green while the IRC account is actually stuck retrying and logging failures.

## Summary

Keep open: current main still has the reported IRC reconnect/status gap, with a fixed 1-second retry loop after reconnect failures and no IRC transport status patch that would make gateway health report the account as disconnected.

## What This Changes

The issue asks for IRC post-success reconnect failures to stop or back off on fatal login errors and surface disconnected/error status instead of healthy running status.

## Best Possible Solution

IRC should publish transport connected:false and lastError on disconnect/reconnect failure, then apply a bounded fatal-login retry policy that preserves normal transient reconnect recovery.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For IRC reconnects after a successful session, should fatal login numerics permanently stop the account, or should the monitor keep retrying with capped backoff while reporting connected:false/lastError?

Rationale: Both choices can be technically correct, but they create different operator recovery behavior after bans, K-lines, or rotated server passwords; automation should not pick fail-closed versus repairable retry policy without maintainer intent.

Likely owner: RomneyDa

Owner reason: The current gateway health and IRC monitor lines are blamed to the #99707 current-main merge, so this is the best available routing owner for the policy choice.

Owner confidence: medium

Options:

- **Capped Backoff With Honest Status (recommended):** Keep retrying in case the operator fixes the server-side condition, but publish connected:false/lastError and use capped backoff instead of a 1-second loop.
- **Terminal Fatal Failure:** Treat 432/464/465 after reconnect as terminal, stop the monitor task, and surface a terminal failure until the operator restarts or reconfigures the account.
- **Status-Only First Slice:** First publish connected:false/lastError on disconnects while leaving retry policy for a narrower follow-up decision.

## Reproduction Assessment

Yes, by source inspection: a loopback IRC server can accept the first session through 001, close it, then return 464/465/432 on the next login so monitor.ts retries every 1000 ms. I did not run that live repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the fatal-login policy. The narrowest maintainable first slice is status honesty plus capped backoff, because it fixes the false-healthy surface without removing transient reconnect recovery.

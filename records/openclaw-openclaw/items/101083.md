## Summary

Keep this open: current main still has the IRC post-ready reconnect path retrying every second after reconnect login failures without publishing disconnected/error status, and no merged duplicate or current implementation owns the remaining fatal-login policy decision.

## What This Changes

The issue requests IRC reconnect/status handling for fatal post-ready login failures so the channel stops or backs off and reports disconnected/error state instead of healthy.

## Best Possible Solution

Keep the fix plugin-local where possible: publish IRC connected:false and lastError on disconnect/reconnect failure, replace the fixed one-second retry with bounded backoff, and only mark terminal if maintainers choose that policy.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For IRC post-ready reconnect failures caused by fatal login replies 432, 464, or 465, should the monitor mark the account terminally failed, or keep retrying with capped backoff while publishing connected:false and lastError?

Rationale: Both choices are plausible: terminal failure is clearer for truly fatal login errors, while capped retry lets an operator fix a server-side password, ban, or nick issue without restarting OpenClaw.

Likely owner: vincentkoc

Owner reason: He validated and merged the adjacent IRC lifecycle PR and is the clearest history-backed owner for the remaining policy choice.

Owner confidence: high

Options:

- **Capped retry with honest status (recommended):** Keep retrying with bounded backoff and publish disconnected/error status so operators see the outage while recoverable server-side fixes can take effect.
- **Terminal fatal disconnect:** Treat 432/464/465 on reconnect as a terminal account failure, stop reconnecting, and require operator action before the account runs again.
- **Status-only first slice:** First land disconnected/error status for the current loop, then decide the retry/backoff policy in a follow-up.

## Reproduction Assessment

Yes at source level, but not by a live run in this read-only review. A loopback IRC server that accepts the first 001, drops the ready socket, then returns 432/464/465 on reconnect follows the current onDisconnect to fixed-delay scheduleReconnect path.

## Solution Assessment

Unclear until maintainers decide the fatal-login policy. The narrowest maintainable direction appears to be honest disconnected/error status plus capped backoff, with permanent terminal failure only if maintainers explicitly choose it.

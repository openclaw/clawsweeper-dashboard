## Label Justifications

- `P2`: This is a normal-priority channel reliability bug with limited blast radius to IRC accounts that become unable to reauthenticate after an established connection drops.
- `impact:message-loss`: A dead IRC account can miss inbound and outbound channel traffic while the monitor keeps retrying internally.
- `impact:ux-friction`: The operator-facing status can continue to look healthy while IRC is permanently failing reconnects, creating avoidable diagnosis burden.

## Summary

Keep open: current main still has the IRC post-ready reconnect path retrying every 1000 ms after reconnect failures, and IRC does not publish `connected: false` or `lastError`, so the linked QQBot and Twitch status work does not supersede this IRC-specific bug.

## What This Changes

The issue requests honest IRC channel health reporting and bounded handling for non-recoverable IRC login errors after an established connection drops.

## Best Possible Solution

IRC should publish disconnected/error status for post-ready disconnects and failed reconnects, then use a maintainer-approved bounded backoff or terminal-disconnect policy that fits the shared channel health model.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For IRC post-ready reconnects that fail with fatal login codes `432`, `464`, or `465`, should OpenClaw mark the account terminally failed, or keep retrying with capped backoff while publishing `connected: false` and `lastError`?

Rationale: The source-backed bug is real, but the permanent-fail versus capped-retry behavior determines operator recovery semantics and should not be guessed by automation.

Likely owner: steipete

Owner reason: This choice spans IRC plugin behavior and shared gateway health policy, and this handle appears in recent history for both implicated surfaces.

Owner confidence: medium

Options:

- **Capped Retry With Honest Status (recommended):** Publish `connected: false` plus the reconnect error immediately, use bounded exponential backoff, and allow recovery if the server-side IRC condition is fixed.
- **Terminal Fatal Failure:** Treat these reconnect login codes as terminal for the account, stop retrying, and require an explicit operator restart after fixing credentials or bans.
- **Status-Only First Slice:** Land only the disconnected/error status propagation first, leaving retry policy unchanged until a later explicit channel-health decision.

## Reproduction Assessment

Yes, source inspection gives a high-confidence path: after an established IRC connection closes, `onDisconnect` schedules reconnect, and a subsequent `432`/`464`/`465` login rejection falls into an unbounded 1000 ms retry loop. I did not run a live IRC server capture in this read-only review.

## Solution Assessment

Unclear until maintainers choose the fatal-reconnect policy. The safest first slice appears to be status honesty plus capped backoff, because it fixes the false-healthy state without permanently requiring operator intervention.

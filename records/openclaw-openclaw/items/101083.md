## Label Justifications

- `P2`: This is a bounded IRC channel availability/status bug with missed messages and misleading health reporting, but the blast radius is limited to IRC accounts that hit fatal reconnect login errors.
- `impact:message-loss`: A fatally disconnected IRC account can miss inbound and outbound channel traffic while the monitor keeps retrying unsuccessfully.
- `impact:ux-friction`: Operators can see a healthy/running status while the account is permanently failing, forcing log inspection or guesswork to diagnose the outage.

## Summary

Keep open: current main still has the IRC post-ready reconnect path that retries every 1000 ms after fatal login rejection and does not publish a disconnected/error status, so the reported health mismatch remains valid.

## What This Changes

The issue asks for IRC post-ready fatal reconnect failures to stop being reported as healthy and to use capped or terminal reconnect behavior instead of a fixed 1s loop.

## Best Possible Solution

Adopt a plugin-local IRC fix that publishes connected:false and lastError on post-ready disconnect/reconnect failure, then applies the maintainer-chosen bounded backoff or terminal-disconnect policy with loopback IRC regression proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For IRC post-ready reconnects that hit fatal login codes 432, 464, or 465, should OpenClaw mark the account terminally disconnected or keep retrying with capped backoff while reporting connected:false and lastError?

Rationale: The source bug is clear, but the permanent-stop versus retry-after-operator-fix behavior is an operator policy choice that code should not guess.

Likely owner: vincentkoc

Owner reason: They validated and landed the adjacent IRC reconnect behavior, so they are the best available routing owner for the policy choice.

Owner confidence: medium

Options:

- **Capped retry with honest status (recommended):** Report connected:false and lastError immediately, retry with bounded backoff, and let operators repair server-side credentials or bans without restarting OpenClaw.
- **Terminal fatal disconnect:** Treat 432, 464, and 465 after reconnect as terminal, stop the IRC monitor, and require explicit operator restart after fixing configuration or server-side state.
- **Defer to shared channel policy:** Pause the IRC-specific fix until maintainers decide a common fatal transport policy for all channel plugins.

## Reproduction Assessment

Yes, source-reproducible: after a ready IRC socket closes, the monitor schedules reconnect, and a subsequent 432/464/465 rejection falls into the catch path that reschedules every 1000 ms. I did not run a live IRC server capture in this read-only review.

## Solution Assessment

Unclear until maintainers choose the retry policy; the narrowest maintainable fix is plugin-local status reporting plus bounded retry or terminal disconnect, leaving the existing gateway health policy to consume connected:false.

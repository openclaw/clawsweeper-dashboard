## Summary

Keep open. Current main still sends Signal media-only audio attachments with a synthesized `<media:audio>` body, while the requested strict `messages` suppression option is still absent; the iMessage sibling was fixed, but the remaining Signal/config request still needs maintainer product judgment.

## What This Changes

Add an opt-in messages configuration surface to suppress visible `<media:audio>` or other synthetic media placeholder text for media-only channel sends.

## Best Possible Solution

Resolve the remaining Signal media-only placeholder visibility with a transport-valid hidden-body or attachment-only path, and add a documented default-off `messages` setting only if maintainers confirm cross-channel policy control is needed.

## Reproduction Assessment

Yes, at source level: a blank Signal media send with an `audio/*` attachment maps to `audio` and then sends `<media:audio>` as the Signal RPC body. I did not run a live Signal client in this read-only review.

## Solution Assessment

Unclear. The requested global config option is plausible, but current main has already fixed iMessage channel-locally, so maintainers should decide whether the remaining solution is Signal-specific delivery behavior or a cross-channel messages policy.

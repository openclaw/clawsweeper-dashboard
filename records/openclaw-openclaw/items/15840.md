## Summary

Keep open. Current main still sends a visible `<media:audio>`-style body for blank Signal audio/media sends, the latest release has the same Signal path, and the requested strict `messages` suppression option is still absent; iMessage was fixed separately, so the remaining work is a Signal/global product decision rather than cleanup close material.

## What This Changes

Request to add an opt-in configuration or channel policy to suppress visible `<media:audio>` fallback text for media-only voice/audio sends while preserving default fallback behavior.

## Best Possible Solution

Keep this as the canonical product decision and choose either a documented default-off `messages` option or a narrower Signal hidden-body policy, preserving default fallback behavior and adding focused Signal media-only regression proof.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes, at source level: a blank Signal media send with an `audio/*` attachment maps to `audio` and then sends `<media:audio>` as the RPC body; no live Signal client was exercised in this read-only review.

## Solution Assessment

Is this the best way to solve the issue? Unclear: the requested global config option is plausible, but a Signal-specific hidden-body policy may be narrower now that iMessage was fixed channel-locally.

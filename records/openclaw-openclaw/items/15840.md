## Summary

Keep open. Current main and the latest release still synthesize visible Signal media placeholder text for blank audio/media sends, the requested strict `messages` suppression option is still absent, and the related config PRs are closed unmerged; iMessage is now fixed separately, so the remaining work is a Signal/config product decision rather than an implemented cleanup close.

## What This Changes

Request an opt-in `messages` configuration setting to suppress synthetic `<media:audio>` or related media-placeholder text for media-only audio/voice sends, especially Signal TTS voice notes.

## Best Possible Solution

Keep this as the canonical Signal/media-placeholder product request until maintainers choose a default-off `messages` policy or Signal-specific hidden-body policy, then update config/schema/docs and focused Signal media-only tests without disturbing the iMessage fix.

## Reproduction Assessment

Yes, at source level: a blank Signal media send with an `audio/*` attachment flows from Signal reply delivery into `sendMessageSignal`, maps to `audio`, and sends `<media:audio>` as the RPC body. I did not run a live Signal client in this read-only review.

## Solution Assessment

Unclear: the requested global config option is plausible, but current policy makes new config surface high-bar and Signal may need a hidden non-empty body. The best next step is a maintainer product decision on global `messages` config versus a Signal-owned transport policy.

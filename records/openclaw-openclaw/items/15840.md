## Summary

Keep open. Current main still sends a synthesized Signal media placeholder for blank media-only sends, the requested strict `messages` suppression option is absent, and the remaining choice is a maintainer product/config decision rather than conservative cleanup.

## What This Changes

The issue requests an opt-in setting to suppress visible `<media:audio>` or related media-placeholder text on outbound voice/audio media messages.

## Best Possible Solution

Maintain the iMessage local fix, have maintainers choose the Signal/global policy, then implement the approved default-preserving suppression path with schema/help/docs and focused Signal media-only proof.

## Reproduction Assessment

Yes, at source level: a blank Signal media send with an `audio/*` attachment flows into `sendMessageSignal`, maps to `audio`, and sends `<media:audio>` as the RPC body. No live Signal client was run in this read-only review.

## Solution Assessment

Unclear: the requested global config option is plausible, but it adds a new strict `messages` surface and the iMessage sibling was solved channel-locally. Maintainers should choose between a Signal-local hidden-body policy and a default-off global suppression option before implementation.

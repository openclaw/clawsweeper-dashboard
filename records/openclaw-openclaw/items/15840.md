## Summary

Keep open. Current main still sends a generated Signal media placeholder for blank media-only audio sends, and the requested strict `messages` suppression option is still absent; the iMessage sibling was fixed separately, but the central Signal/config request remains unresolved.

## What This Changes

The issue requests a default-off configuration option to suppress generated `<media:audio>` media placeholder text for voice/audio-only messages while preserving existing fallback behavior by default.

## Best Possible Solution

Keep this open as the canonical product/config request: after maintainer approval, add a documented default-off media-placeholder suppression option or narrower Signal hidden-body policy, wire it through the remaining Signal media-only send path, and preserve current fallback behavior for users who do not opt in.

## Reproduction Assessment

Yes, at source level: blank Signal media sends pass empty text plus a media URL into `sendMessageSignal`, where audio MIME types map to `<media:audio>` before dispatch. I did not run a live Signal client in this read-only review.

## Solution Assessment

Unclear until maintainers approve the product surface. A default-off config option is plausible, but current main already fixed iMessage channel-locally, so maintainers should decide whether the remaining solution is Signal-specific delivery behavior or cross-channel `messages` policy.

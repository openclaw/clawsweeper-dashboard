## Summary

Keep open. Current main and latest release still synthesize visible Signal media-placeholder text for blank audio/media sends, while the requested strict `messages` suppression option is absent; the iMessage sibling was fixed separately, but the central Signal/config request remains.

## What This Changes

Add an opt-in way to suppress automatically generated `<media:audio>` or other media placeholder text for media-only outbound messages.

## Best Possible Solution

Keep this as the canonical product/config request and choose either a documented default-off `messages` option or a narrower Signal hidden-body policy, preserving default fallback behavior and adding focused Signal media-only regression proof.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes, at source level: a blank Signal media send with an `audio/*` attachment maps to `audio` and then sends `<media:audio>` as the RPC body; no live Signal client was exercised in this read-only review.

## Solution Assessment

Is this the best way to solve the issue? Unclear: the requested global config option is plausible, but iMessage is already fixed channel-locally, so maintainers should decide between a Signal-specific transport fix and a broader `messages` policy.

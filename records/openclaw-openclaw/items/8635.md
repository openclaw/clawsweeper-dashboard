## Summary

Keep open: current main and the latest release still expose `session_status` as rendered status text with small route/model details, while the requested raw session, last-turn, cost, quota-window, source, and freshness metadata are not available through a stable agent-facing tool contract.

## What This Changes

Expose structured per-session and last-turn token, cost, and budget usage data through the `session_status` tool so agents can budget their own work without parsing transcript files.

## Best Possible Solution

Define a maintainer-approved structured agent-facing usage contract, then implement it through existing `session_status` visibility checks or a separate supported usage tool that reuses gateway/transcript usage sources.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose raw token, cost, quota-window, and freshness/source metadata through `session_status.details.usage`, or should this become a separate agent-facing usage tool/API?

Rationale: The source gap is clear, but the response shape, privacy boundary, freshness semantics, and whether this belongs on `session_status` are public API/product choices rather than a narrow bug repair.

Likely owner: steipete

Owner reason: He has the strongest visible ownership signal for the current tool/status surfaces and has already framed the unresolved API contract decision in the prior review.

Owner confidence: high

Options:

- **Extend session_status details (recommended):** Add a stable `details.usage` contract to the existing tool while preserving rendered status text and current visibility checks.
- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query surface backed by existing gateway/transcript usage code.
- **Keep status display-only:** Leave raw usage behind gateway/UI/CLI surfaces and document that agents should not consume it through `session_status`.

## Reproduction Assessment

Yes, at source level: current main still accepts only `sessionKey` and `model`, returns rendered status text plus minimal details, and documents status-card behavior rather than a raw usage API.

## Solution Assessment

Unclear until maintainers choose the API shape. Extending `session_status.details` is likely the narrowest maintainable path if it reuses the existing visibility boundary and gateway/transcript usage sources.

## Summary

Keep open: current main still exposes `session_status` as status-card text with limited details, while raw token, cost, last-turn, budget, source, and freshness data remains outside the agent-facing tool contract.

## What This Changes

The issue requests structured per-session and last-turn token, cost, and budget usage data through the `session_status` tool.

## Best Possible Solution

Ship a documented, visibility-aware structured usage contract for agent callers, either in `session_status.details` or a dedicated usage tool, reusing existing transcript and gateway usage parsers with explicit source, freshness, availability, cost, and quota metadata.

- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower visibility-scoped agent-facing usage query tool backed by `sessions.usage`.
- **Keep usage operator-only:** Leave raw usage on Gateway/operator surfaces until broader usage-ledger and freshness designs settle.

Yes. Source inspection on current main and `v2026.6.11` shows `session_status` lacks structured usage fields while the requested data exists only as rendered text, transcript state, or separate Gateway usage RPCs.

## Solution Assessment

Unclear until maintainers choose the API boundary. Extending `session_status.details` is plausible, but a separate agent-facing usage tool may be cleaner if raw usage queries should stay separate from status-card rendering.

## Summary

Keep open: current main and the latest release still expose `session_status` as a rendered status-card tool with minimal structured details, while raw session token, cost, quota-window, source, and freshness data remain on gateway/status/transcript surfaces rather than a stable agent-facing usage API.

## What This Changes

Request to expose raw per-session and last-turn token, cost, and budget data through the agent-facing `session_status` tool.

## Best Possible Solution

Define a maintainer-approved structured agent-facing usage contract, then implement it through the existing `session_status` visibility checks or an equivalent supported tool that reuses gateway/transcript usage sources.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose raw token, cost, quota-window, and freshness/source metadata through `session_status.details.usage`, or should this become a separate agent-facing usage tool/API?

Rationale: The source gap is clear, but the stable response shape, privacy boundary, and quota/freshness semantics are product-owned API decisions.

Likely owner: steipete

Owner reason: He introduced `session_status`, has related usage/status history, and authored the prior detailed review framing the API decision.

Owner confidence: medium

Options:

- **Extend session_status details (recommended):** Add a stable `details.usage` contract to the existing tool while preserving the rendered status card and current visibility checks.
- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query surface backed by the existing gateway/transcript usage code.
- **Keep status display-only:** Leave raw usage behind gateway, UI, and CLI surfaces and document that agents should not consume it through `session_status`.

## Reproduction Assessment

Yes, at source level: current `session_status` still accepts only `sessionKey` and `model`, returns rendered status text plus minimal structured details, and documents status-card behavior rather than a raw usage API.

## Solution Assessment

Unclear until maintainers choose the API shape. Extending `session_status.details` is likely the narrowest maintainable path if it reuses the existing visibility boundary and gateway/transcript usage sources.

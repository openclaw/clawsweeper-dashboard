## Summary

Keep open: this remains a product/API-contract request for stable, agent-readable session usage rather than a narrow defect. The latest supplied review found `session_status` still centered on rendered status output while structured totals and quota data live on adjacent gateway surfaces; the merged context-budget work improves a related fallback but does not establish the requested session/last-turn usage contract.

## What This Changes

Add a documented structured usage result to the `session_status` tool so agents can read per-session and last-turn token, cost, and provider-budget information without parsing transcript files.

## System Context

`session_status` is the agent-facing status tool: it resolves an accessible session and produces the status information that agents and users consume next. Transcript usage and provider quota data originate in session records and provider/gateway usage paths, then need a stable privacy-aware contract before they can safely reach the tool response.

## Architecture Diagram

flowchart LR
  A[Session transcript and runtime data] --> B[Usage aggregation]
  C[Provider quota windows] --> D[Availability and privacy checks]
  B --> D
  E[Agent calls session status] --> F[Session access resolution]
  F --> D
  D --> G[Stable structured usage response]
  G --> H[Agent budgeting and status decisions]

## Best Possible Solution

Define one additive, documented `session_status.details.usage` contract that separates transcript-derived session and last-turn totals from provider-window data, carries source/freshness/availability metadata, and reuses existing access controls and gateway aggregation rather than adding a parallel tracker.

## Summary

Keep open: current main and v2026.6.11 still expose `session_status` as rendered status text with minimal structured details, while raw session, last-turn, cost, quota-window, source, and freshness metadata remain outside a stable agent-facing tool contract.

## What This Changes

The issue requests optional structured `usage` fields on `session_status` for per-session and last-turn token, cost, and budget/window data.

## Best Possible Solution

Define a maintainer-approved structured agent-facing usage contract, then implement it through existing `session_status` visibility checks or a separate supported usage tool that reuses gateway/transcript usage sources.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose raw token, cost, quota-window, and freshness/source metadata through `session_status.details.usage`, or should this become a separate agent-facing usage tool/API?

Rationale: The missing source surface is clear, but the stable response shape, privacy boundary, and quota/freshness semantics are public API and product choices rather than a narrow bug repair.

Likely owner: steipete

Owner reason: He introduced the tool and has already framed the unresolved API/product decision in prior review context.

Owner confidence: high

Options:

- **Extend session_status details (recommended):** Add a stable optional `details.usage` contract to the existing tool while preserving rendered status text and current visibility checks.
- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query surface backed by the existing gateway/transcript usage code.
- **Keep raw usage out of agent tools:** Document that agents should use existing status display and gateway/operator surfaces while raw usage remains unavailable through `session_status`.

## Reproduction Assessment

Yes, at source level: current main still accepts only `sessionKey` and `model`, returns rendered status text plus minimal details, and documents status-card behavior rather than a raw usage API.

## Solution Assessment

Unclear until maintainers choose the API shape. Extending `session_status.details` is likely the narrowest maintainable path if it reuses existing visibility checks and gateway/transcript usage sources.

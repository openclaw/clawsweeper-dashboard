## Summary

Keep open: current main and the latest checked release still expose `session_status` primarily as a rendered status card with minimal details, while structured token/cost/session usage remains in separate gateway/operator RPC surfaces rather than an agent-facing `session_status` usage contract.

## What This Changes

The issue requests structured token, cost, quota, last-turn, and budget usage data through `session_status` or an equivalent agent-facing tool API.

## Best Possible Solution

Define a documented additive structured usage contract on `session_status.details.usage` or a dedicated usage tool, reusing existing gateway/transcript readers while preserving session visibility, source, and freshness metadata.

## Risks / Open Questions

- Future implementation needs a privacy and visibility decision because exposing costs, provider quota, transcript totals, and cross-session usage through an agent tool could leak session or provider-account metadata.
- Provider-reported quota and transcript-derived estimates have different freshness and source semantics, so the API should include availability/source metadata instead of flattening them into one ambiguous number.
- Changing `session_status.details` creates a public tool response contract that should be additive and documented to avoid breaking existing agent/tool consumers.

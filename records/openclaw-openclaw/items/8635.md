## Summary

Keep open: current main and the latest release still expose `session_status` as a rendered status-card tool, while the requested raw session, last-turn, cost, quota-window, source, and freshness fields remain outside a stable agent-facing contract.

## What This Changes

Expose raw per-session and last-turn token, cost, and budget usage data through `session_status` or an equivalent agent-facing usage surface.

## Best Possible Solution

Define a maintainer-approved structured agent-facing usage contract, then implement it through existing `session_status` visibility checks or an equivalent supported tool that reuses gateway/transcript usage sources.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose raw token, cost, quota-window, and freshness/source metadata through `session_status.details.usage`, or should this become a separate agent-facing usage tool/API?

Rationale: The source gap is clear, but the stable response shape, privacy boundary, and quota/freshness semantics are public API/product choices rather than a narrow bug repair.

Likely owner: steipete

Owner reason: He already framed the unresolved API/product decision in the prior review and has the strongest visible ownership signal for deciding the public tool contract.

Owner confidence: medium

Options:

- **Extend session_status details (recommended):** Add a stable `details.usage` contract to the existing tool while preserving rendered status text and current visibility checks.
- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query surface backed by existing gateway/transcript usage code.
- **Keep status display-only:** Leave raw usage behind gateway, UI, and CLI surfaces and document that agents should not consume it through `session_status`.

## Reproduction Assessment

Yes, at source level: current main still accepts only `sessionKey` and `model`, returns rendered status text plus minimal details, and documents status-card behavior rather than a raw usage API.

## Solution Assessment

Unclear until maintainers choose the API shape. Extending `session_status.details` is likely the narrowest maintainable path if it reuses existing visibility checks and gateway/transcript usage sources.

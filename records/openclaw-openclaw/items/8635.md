## Summary

Keep open: current main still exposes `session_status` as a `/status`-style text result with route/model details, while structured token, cost, session, and last-turn usage remains on Gateway usage RPCs and transcript readers instead of a documented agent-facing tool contract.

## What This Changes

Request to add raw per-session, last-turn, cost, and budget usage data to the agent-facing `session_status` tool.

## Best Possible Solution

Add a documented additive agent-facing usage contract on `session_status` or an equivalent supported tool that reuses `sessions.usage` and transcript readers while preserving current visibility checks.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw define a structured agent-facing usage contract on `session_status`, or keep raw usage data limited to Gateway usage RPCs/UI surfaces?

Rationale: This changes the stable tool response surface and requires product decisions about privacy boundaries, availability/source metadata, cost semantics, and whether `session_status` is the right API owner.

Likely owner: steipete

Owner reason: He introduced and recently maintained the `session_status` behavior and already provided prior maintainer-side review context on this issue.

Owner confidence: high

Options:

- **Define narrow usage fields (recommended):** Add a small additive `usage` object with session, last-turn, cost, budget/window availability, and source metadata while reusing existing Gateway/transcript usage code.
- **Keep usage in Gateway RPCs:** Leave `session_status` as a rendered status card and document `sessions.usage` as the structured API for operator clients instead of agents.
- **Fold into broader metadata RFC:** Defer this to the tool freshness/usage metadata design so `session_status` gets the same envelope as other cached tools.

## Reproduction Assessment

Yes. Source inspection on current main shows `session_status` has no structured usage fields and returns rendered status text plus minimal details, while structured usage is available only through separate Gateway usage RPCs.

## Solution Assessment

Unclear. Extending `session_status.details` is a plausible narrow path, but the best fix needs maintainer-owned API shape and privacy/source metadata decisions before implementation.

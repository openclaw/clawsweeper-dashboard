## Summary

Keep open: current main and v2026.6.11 still expose `session_status` as rendered status text with minimal details, while raw session, last-turn, cost, quota-window, source, and freshness metadata remain outside a stable agent-facing tool contract.

## What This Changes

Request to expose structured per-session and last-turn token, cost, and budget usage data through `session_status` so agents can budget their own capacity.

## Best Possible Solution

Define a maintainer-approved structured agent-facing usage contract, then implement it through existing `session_status` visibility checks or an equivalent supported tool that reuses gateway/transcript usage sources.

Owner confidence: medium

Options:

- **Extend session_status details (recommended):** Add a stable `details.usage` contract to the existing tool while preserving rendered status text and current visibility checks.
- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query surface backed by existing gateway/transcript usage code.
- **Keep status display-only:** Leave raw usage behind gateway/UI/CLI surfaces and document that agents should not consume it through `session_status`.

## Reproduction Assessment

Yes, at source level: current main still accepts only `sessionKey` and `model`, returns rendered status text plus minimal details, and documents status-card behavior rather than a raw usage API.

## Solution Assessment

Unclear until maintainers choose the API shape. Extending `session_status.details` is likely the narrowest maintainable path if it reuses the existing visibility boundary and gateway/transcript usage sources.

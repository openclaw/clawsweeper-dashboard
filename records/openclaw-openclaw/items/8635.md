## Summary

Keep open: current main and v2026.6.11 still expose `session_status` as a rendered status-card tool, while structured token/cost/session usage exists on gateway usage surfaces rather than a stable agent-facing `session_status` usage API.

## What This Changes

Request structured per-session and last-turn token, cost, and quota usage fields from the `session_status` tool.

## Best Possible Solution

Define a maintainer-approved structured agent-facing usage contract, then implement it through `session_status.details.usage` or an equivalent tool that reuses existing gateway/transcript usage sources and visibility checks.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should raw token, cost, quota-window, and freshness/source metadata be exposed through `session_status.details.usage`, or through a separate agent-facing usage tool/API?

Rationale: The source gap is clear, but the stable response shape, privacy boundary, and quota/freshness semantics are product-owned API decisions.

Likely owner: steipete

Owner reason: They introduced `session_status` and have recent history across status, docs, and usage/cost surfaces.

Owner confidence: medium

Options:

- **Extend session_status details (recommended):** Add a stable additive `details.usage` contract to the existing tool while preserving the rendered status card and current visibility checks.
- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query surface backed by existing gateway/transcript usage code.
- **Keep status display-only:** Leave raw usage behind gateway, UI, CLI, and `/usage` surfaces and document that agents should not consume raw usage through `session_status`.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 show `session_status` still accepts only `sessionKey` and `model`, returns rendered status text plus minimal details, and documents status-card behavior rather than a raw usage API.

## Solution Assessment

Unclear until maintainers choose the API shape. Extending `session_status.details` is likely the narrowest maintainable path if it reuses the existing visibility boundary and gateway/transcript usage sources.

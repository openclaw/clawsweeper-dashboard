## Summary

Keep open: current main still exposes `session_status` as rendered status text plus route/model details, while raw session, last-turn, cost, budget, source, and freshness usage data remain in transcript/status helpers or separate Gateway usage RPCs rather than a documented agent-facing tool contract.

## What This Changes

The issue requests structured per-session and last-turn token, cost, and budget usage data through the agent-facing `session_status` tool.

## Best Possible Solution

Ship a documented, visibility-aware structured usage contract for agent callers, either in `session_status.details.usage` or a dedicated usage tool, reusing existing transcript and Gateway usage parsers with explicit source, freshness, availability, cost, and quota metadata.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should raw token, cost, and quota usage become part of `session_status.details`, move into a separate agent-facing usage tool, or remain only on Gateway/operator usage surfaces for now?

Rationale: The missing behavior is source-confirmed, but the public API boundary affects privacy, session visibility, source/freshness semantics, provider cost metadata, and compatibility for agent tools.

Likely owner: steipete

Owner confidence: high

Options:

- **Add structured session_status usage (recommended):** Extend `session_status.details` with stable session, last-turn, budget/window, source, freshness, and unavailable metadata while preserving the rendered status card.
- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query tool that reuses Gateway and transcript parsers under the same visibility guards.
- **Keep raw usage operator-only:** Leave raw usage on Gateway and operator surfaces until the broader usage-ledger and freshness-metadata designs settle.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 show `session_status` lacks structured usage fields while the requested data exists only as rendered text, transcript state, or separate Gateway usage RPCs.

## Solution Assessment

Unclear until maintainers choose the stable API boundary. Extending `session_status.details` is plausible, but a separate agent-facing usage tool may be cleaner if raw usage queries should stay separate from status-card rendering.

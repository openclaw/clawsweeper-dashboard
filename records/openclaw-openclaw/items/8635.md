## Summary

Keep open: current main and the latest release still expose `session_status` as rendered status text plus minimal structured details, while the requested raw session, last-turn, cost, quota-window, source, and freshness usage contract is still missing. The source gap is clear, but the public API shape and privacy boundary need maintainer product direction.

## What This Changes

The issue requests structured per-session and per-turn token, cost, and budget usage data through the `session_status` tool so agents can budget their own work.

## Best Possible Solution

Define a maintainer-approved structured agent-facing usage contract, then implement it through existing `session_status` visibility checks or an equivalent supported tool that reuses gateway and transcript usage sources.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose raw token, cost, quota-window, and freshness/source metadata through `session_status.details.usage`, or should this become a separate agent-facing usage tool/API?

Rationale: The missing source surface is clear, but the stable response shape, privacy boundary, quota availability semantics, and freshness contract are public API/product choices rather than a narrow bug repair.

Likely owner: steipete

Owner reason: He introduced the tool and already framed the unresolved public API and privacy decisions in the prior review.

Owner confidence: medium

Options:

- **Extend session_status details (recommended):** Add a stable `details.usage` contract to the existing tool while preserving rendered status text and current visibility checks.
- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query backed by existing gateway/transcript usage code.
- **Keep status display-only:** Leave raw usage behind gateway/UI/CLI surfaces and document that agents should not consume it through `session_status`.

## Reproduction Assessment

Yes, at source level: current main still accepts only `sessionKey` and `model`, returns rendered status text plus minimal details, and documents status-card behavior rather than a raw usage API.

## Solution Assessment

Unclear until maintainers choose the public API shape. Extending `session_status.details` is likely the narrowest maintainable path if it reuses existing visibility checks and gateway/transcript usage sources.

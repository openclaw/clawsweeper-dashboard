## Summary

Keep open: current main and v2026.6.11 still expose `session_status` as a rendered status-card tool with minimal structured details, while the requested raw session, last-turn, cost, quota-window, source, and freshness data remain outside a stable agent-facing tool contract.

## What This Changes

Expose structured per-session and last-turn token, cost, and budget usage data through the `session_status` tool so agents can budget their own capacity.

## Best Possible Solution

Define a maintainer-approved structured agent-facing usage contract, then implement it through the existing `session_status` visibility checks or an equivalent supported tool that reuses gateway/transcript usage sources.

## Maintainer Decision

Question: Should OpenClaw expose raw token, cost, quota-window, and freshness/source metadata through `session_status.details.usage`, or should this become a separate agent-facing usage tool/API?

Rationale: The source gap is clear, but the stable response shape, privacy boundary, and quota/freshness semantics are public API and product choices rather than a narrow bug repair.

Likely owner: steipete

Owner reason: He introduced the tool and already framed the unresolved public contract and privacy/freshness decision in the prior review.

Owner confidence: high

Options:

- **Extend session_status details (recommended):** Add a stable `details.usage` contract to the existing tool while preserving rendered status text and current visibility checks.
- **Create separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query surface backed by existing gateway/transcript usage code.
- **Keep status display-only:** Leave raw usage behind gateway/UI/CLI surfaces and document that agents should not consume it through `session_status`.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 still accept only `sessionKey` and `model`, return rendered status text plus minimal details, and document status-card behavior rather than a raw usage API.

## Solution Assessment

Unclear until maintainers choose the API shape. Extending `session_status.details` is likely the narrowest maintainable path if it reuses the existing visibility boundary and gateway/transcript usage sources.

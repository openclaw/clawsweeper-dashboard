## Summary

Keep open: current main and the latest release still do not expose a structured agent-facing usage payload on `session_status`; the remaining work is an API/product contract decision, not conservative cleanup.

## What This Changes

Requested behavior: expose structured per-session and last-turn token, cost, and budget usage through the agent-facing `session_status` tool.

## Best Possible Solution

Define a maintainer-approved structured agent-facing usage contract, then implement it through the existing `session_status` visibility boundary or a separate supported usage tool backed by gateway/transcript usage sources.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should raw token, cost, quota-window, and freshness/source metadata be exposed through `session_status.details.usage`, or through a separate agent-facing usage tool/API?

Rationale: The source gap is clear, but the stable response shape, privacy boundary, and quota/freshness semantics are product-owned API decisions.

Likely owner: steipete

Owner reason: He introduced `session_status`, has recent provider usage history, and already engaged on this issue's prior review.

Owner confidence: high

Options:

- **Extend session_status details (recommended):** Add a stable `details.usage` contract to the existing tool while preserving the rendered status card and current visibility checks.
- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query backed by the existing gateway/transcript usage code.
- **Keep status display-only:** Leave raw usage behind gateway, UI, and CLI surfaces and document that agents should not consume it through `session_status`.

## Reproduction Assessment

Yes, at source level: `session_status` still accepts only `sessionKey` and `model`, returns rendered status text plus minimal details, and documents status-card behavior rather than a raw usage API.

## Solution Assessment

Unclear until maintainers choose the public API shape; extending `session_status.details` is likely the narrowest path if it reuses the existing visibility boundary.

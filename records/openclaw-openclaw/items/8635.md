## Summary

Keep open: current main and v2026.6.11 still expose `session_status` as rendered status text plus minimal details, while structured session, last-turn, cost, quota-window, source, and freshness metadata remain outside the agent-facing tool contract.

## What This Changes

The issue requests a structured agent-facing token usage API on `session_status`, including session totals, last-turn counts, costs, and budget/window metadata.

## Best Possible Solution

Define a maintainer-approved structured agent-facing usage contract, then implement it through existing `session_status` visibility checks or an equivalent supported tool that reuses gateway/transcript usage sources.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose raw token, cost, quota-window, and freshness/source metadata through `session_status.details.usage`, or should this become a separate agent-facing usage tool/API?

Rationale: The source gap is clear, but the stable response shape, privacy boundary, quota-window semantics, and freshness/source model are public API and product choices rather than a narrow bug repair.

Likely owner: steipete

Owner reason: He introduced the tool, maintained adjacent usage/status behavior, and already framed the unresolved API/product decision in the prior review.

Owner confidence: high

Options:

- **Extend `session_status.details` (recommended):** Add a stable `details.usage` object while preserving current rendered status text and session visibility checks.
- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query surface backed by existing gateway/transcript usage code.
- **Keep raw usage out of tools:** Document that agents should use existing display/gateway/UI surfaces and not consume raw usage through `session_status`.

## Reproduction Assessment

Yes, at source level: current main still accepts only `sessionKey` and `model`, returns rendered status text plus minimal details, and documents status-card behavior rather than a raw usage API.

## Solution Assessment

Unclear until maintainers choose the API shape. Extending `session_status.details` is likely the narrowest maintainable path if it reuses existing visibility checks and gateway/transcript usage sources.

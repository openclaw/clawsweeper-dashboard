## Summary

Keep open: current main and the latest release still expose `session_status` as a rendered status-card tool, while raw per-session, last-turn token/cost, quota-window, source, and freshness data remain outside a stable agent-facing usage contract.

## What This Changes

Request to expose raw token usage, cost, and budget/window data through `session_status` so agents can programmatically track session capacity and spending.

## Best Possible Solution

Define a maintainer-approved structured agent-facing usage contract, then implement it through `session_status.details.usage` or an equivalent supported tool that reuses existing gateway/transcript usage sources and visibility checks.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw expose raw token, cost, quota-window, and freshness/source metadata through `session_status.details.usage`, or should this become a separate agent-facing usage tool/API?

Rationale: The source gap is clear, but the stable response shape, privacy boundary, and quota/freshness semantics are product-owned API decisions on a stable gateway/session surface.

Likely owner: steipete

Owner reason: He introduced `session_status` and has the strongest combined history on status, provider usage, and the prior review context for this issue.

Owner confidence: high

Options:

- **Extend session_status details (recommended):** Add a stable `details.usage` contract to the existing tool while preserving the rendered status card and current visibility checks.
- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query surface backed by existing gateway/transcript usage code.
- **Keep status display-only:** Leave raw usage behind gateway/UI/CLI surfaces and document that agents should not consume it through `session_status`.

## Reproduction Assessment

Yes, at source level: `session_status` still accepts only `sessionKey` and `model`, returns rendered status text plus minimal structured details, and the docs describe status-card behavior rather than a raw usage API.

## Solution Assessment

Unclear until maintainers choose the stable API shape; extending `session_status.details` is likely the narrowest path if the existing visibility boundary is reused.

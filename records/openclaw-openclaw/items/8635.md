## Summary

Keep open: current main and v2026.6.11 still expose `session_status` as rendered status text plus route/model details, while raw session/last-turn token, cost, and budget data remain in transcript/status helpers or separate Gateway usage RPCs rather than a documented agent-facing usage contract.

## What This Changes

Request to expose structured per-session, last-turn, token/cost, and quota/budget usage through `session_status` or an equivalent agent-facing API.

## Best Possible Solution

Ship a documented, visibility-aware structured usage contract for agent callers, either in `session_status.details.usage` or a dedicated usage tool, reusing existing transcript/Gateway usage parsers with explicit source, freshness, availability, cost, and quota metadata.

- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query tool that reuses Gateway/transcript parsers under the same visibility guards.
- **Keep raw usage operator-only:** Leave raw usage on Gateway/operator surfaces until the broader usage-ledger and freshness-metadata designs settle.

Yes. Source inspection on current main and v2026.6.11 shows `session_status` lacks structured usage fields while the requested data exists only as rendered text, transcript state, or separate Gateway usage RPCs.

## Solution Assessment

Unclear until maintainers choose the stable API boundary. Extending `session_status.details` is plausible, but a separate agent-facing usage tool may be cleaner if raw usage queries should stay separate from status-card rendering.

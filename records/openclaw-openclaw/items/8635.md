## Summary

Keep open: current main and v2026.6.11 still expose session_status as status-card text plus limited details, not as the requested structured token, cost, budget, source, and freshness API.

## What This Changes

Expose structured per-session and per-turn token, cost, and budget data through the agent-facing session_status tool.

## Best Possible Solution

Ship a documented, visibility-aware structured usage contract for agent callers, either in session_status details or a dedicated usage tool, reusing existing transcript and Gateway usage parsers with explicit source, freshness, availability, cost, and quota metadata.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should raw token, cost, and quota usage become part of session_status details, move into a separate agent-facing usage tool, or remain only on Gateway/operator usage surfaces for now?

Rationale: The gap is source-confirmed, but choosing the stable agent-facing API requires maintainer intent around transcripts, provider quota windows, cost authority, visibility, privacy, and freshness semantics.

Likely owner: steipete

Owner reason: They introduced session_status and have the strongest current-history signal on the exact tool/details contract.

Owner confidence: high

Options:

- **Add session_status usage details (recommended):** Extend session_status details with stable session, last-turn, budget/window, source, freshness, and unavailable metadata while preserving the rendered status card.
- **Create a separate usage tool:** Keep session_status display-oriented and add a narrower agent-facing usage query tool under the same visibility guards.
- **Keep usage operator-only:** Leave raw usage on Gateway/operator surfaces until broader usage-ledger and freshness designs settle.

## Reproduction Assessment

Yes. Source inspection on current main and v2026.6.11 shows session_status lacks structured usage fields while the requested data exists only as rendered text, transcript state, per-turn footer data, or separate Gateway usage RPCs.

## Solution Assessment

Unclear until maintainers choose the stable API boundary. Extending session_status details is plausible, but a separate agent-facing usage tool may be cleaner if raw usage queries should stay separate from status-card rendering.

## Summary

Keep open: current main and v2026.6.11 still expose `session_status` as a rendered `/status`-style result with limited structured details, while raw token/cost/session usage remains on separate gateway RPCs or rendered status lines rather than an agent-facing `session_status.details.usage` contract.

## What This Changes

Expose structured per-session and last-turn token, cost, and budget usage data through the agent-facing `session_status` tool.

## Best Possible Solution

Define a documented structured usage contract for `session_status` or an equivalent agent-facing tool that reuses existing gateway usage and transcript parsers while preserving current visibility checks and explicit source/availability metadata.

Question: Should OpenClaw extend `session_status.details` with structured `usage.session`, `usage.lastTurn`, cost, and budget/window metadata, or create a separate agent-facing usage tool that reuses the existing gateway usage pipeline?

Rationale: The source gap is clear, but the fix chooses a public agent tool contract, privacy/visibility boundaries, provider cost and quota semantics, and compatibility with existing rendered status output.

Likely owner: steipete

Owner confidence: medium

Options:

- **Extend session_status details (recommended):** Add an optional structured `details.usage` payload while keeping the existing rendered text/status card behavior for current callers.
- **Add a separate usage tool:** Create a dedicated read-only agent usage tool and leave `session_status` focused on the `/status`-style card and route/model state.
- **Keep usage gateway-only:** Treat programmatic usage as an operator/gateway API surface and do not expose raw totals or costs directly to agents for now.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 show `session_status` lacks a structured usage payload while structured usage exists only on gateway RPCs and rendered status lines.

## Solution Assessment

Unclear until maintainers choose the API shape; extending `session_status.details` is the narrowest user-visible path, but a separate usage tool may be cleaner if raw usage/cost semantics should stay distinct from the status card.

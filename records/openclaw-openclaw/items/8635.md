## Summary

Keep open: current main and v2026.6.11 still expose token, cache, cost, and provider quota usage through rendered status text or separate Gateway usage RPCs, not as a stable agent-facing `session_status` structured usage contract.

## What This Changes

Expose raw per-session, last-turn, token, cost, and budget usage data through the `session_status` tool so agents can budget their own work without parsing transcript files.

## Best Possible Solution

Ship a documented, visibility-aware structured usage contract for agent callers, either in `session_status.details.usage` or a dedicated usage tool, reusing existing transcript and Gateway usage parsers with explicit source, freshness, availability, cost, and quota metadata.

Rationale: The source-confirmed gap requires choosing a stable agent-facing API boundary over transcripts, cost data, provider quota windows, visibility rules, and freshness semantics; automation should not decide that contract alone.

Options:

- **Add structured session_status usage (recommended):** Extend `session_status.details` with stable session, last-turn, budget/window, source, freshness, and unavailable metadata while preserving the rendered status card.
- **Create a separate usage tool:** Keep `session_status` display-oriented and add a narrower agent-facing usage query tool under the same visibility guards.
- **Keep raw usage operator-only:** Leave raw usage on Gateway/operator surfaces until broader usage-ledger and freshness-metadata designs settle.

## Reproduction Assessment

Yes. Source inspection on current main and v2026.6.11 shows `session_status` lacks structured usage fields while the requested data exists only as rendered text, transcript state, or separate Gateway usage RPCs.

## Solution Assessment

Unclear until maintainers choose the stable API boundary. Extending `session_status.details` is plausible, but a separate agent-facing usage tool may be cleaner if raw usage queries should stay separate from status-card rendering.

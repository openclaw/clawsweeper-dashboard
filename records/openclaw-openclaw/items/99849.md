## Summary

Keep open: this PR is not merge-ready because the new own-property check only guards the legacy-key flag, while `raw.jobId` is still read before that guard and can still copy an inherited string into `raw.id`; the submitted proof also does not exercise the claimed inherited-`jobId` failure.

## What This Changes

The PR changes cron legacy job identity normalization to use `Object.hasOwn(raw, "jobId")` for the legacy key presence flag and adds a prototype-key regression test.

## Best Possible Solution

Gate both presence and value reads on own `jobId`, add a regression where inherited `jobId` with no own `id` does not mutate the row, and refresh before/after terminal proof.

## Reproduction Assessment

Yes from source inspection: with no own `id` and an inherited string `jobId`, `normalizeOptionalString(raw.jobId)` can still produce `normalizedId` before the own-property check is used.

## Solution Assessment

No. `Object.hasOwn` is the right primitive, but the patch must also use it to control the `jobId` value read; the added test covers unrelated inherited keys rather than inherited `jobId`.

- `P2`: This is a focused web-tool response-size hardening bug with limited blast radius but a concrete remaining merge blocker.
- `merge-risk: 🚨 availability`: A response-like fallback can still buffer an unbounded body under a claimed byte cap, which can create memory pressure or stalls in web-tool paths.
- `merge-risk: 🚨 security-boundary`: `maxBytes` is the boundary for untrusted web response bodies, and this PR enforces it only after the untrusted body has already been read.

## Summary

Keep open: the live head now changes the shared web-tool response reader rather than the config-provider validation described in the PR body, and the patch still buffers the entire text fallback before enforcing `maxBytes`. That leaves a concrete merge blocker despite the useful direction of making byte counts accurate.

## What This Changes

The branch updates `readResponseText` so its `.text()` fallback reports UTF-8 byte counts, truncates returned text after reading when `maxBytes` is set, and adds a focused fallback truncation test.

## Best Possible Solution

Make `readResponseText` fail closed or use a genuinely bounded byte source whenever `maxBytes` is set and no readable stream is available, then update the PR title/body/proof and tests to match the web-shared change.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: use a Response-like object with no `body.getReader()` and a `.text()` method returning a large string, then call `readResponseText(response, { maxBytes })`. I did not run Vitest because this review was required to keep the checkout read-only.

## Solution Assessment

No. Byte-level reporting is useful, but the best fix for a byte cap must avoid unbounded fallback reads before applying the cap, not truncate only after `.text()` has completed.

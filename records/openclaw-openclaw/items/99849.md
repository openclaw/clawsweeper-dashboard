## Label Justifications

- `P2`: This is a focused web-tool response-size hardening bug with limited blast radius but a concrete merge blocker.
- `merge-risk: 🚨 security-boundary`: `maxBytes` is the boundary for untrusted web response bodies, and the patch enforces it only after the text fallback body is read.
- `merge-risk: 🚨 availability`: A text-only fallback can still buffer an unbounded body under a claimed byte cap, creating memory-pressure or stall risk in web-tool paths.

## Summary

Keep open: the current branch still applies the byte cap only after `response.text()` has fully read the fallback body, and the PR body/proof still describe an obsolete config-provider change rather than this web response-reader patch.

## What This Changes

The branch changes `readResponseText` to UTF-8 byte-count and post-read truncate the text-only fallback when `maxBytes` is set, with a focused fallback truncation test.

## Best Possible Solution

Define and implement the text-only fallback policy for capped response reads, preferably fail-closed or otherwise use a genuinely bounded byte source when `maxBytes` is set, then align the PR body and proof with that behavior.

## Reproduction Assessment

Yes. Source inspection shows that a Response-like object with no readable body or `arrayBuffer()` and a large `.text()` result reaches `await res.text()` before the cap is applied; I did not run tests because this review is read-only.

## Solution Assessment

No. The patch improves byte accounting for returned text, but the best bounded-read fix must avoid the unbounded fallback read or get maintainer approval to define it as best-effort output truncation.

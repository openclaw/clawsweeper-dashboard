## Label Justifications

- `P0`: A normal long-lived-install upgrade can leave the supervised Gateway unusable, while recovery currently requires manual service control, file operations, or direct SQLite intervention.
- `impact:crash-loop`: The fatal readiness gate causes launchd or systemd to repeatedly restart a Gateway that cannot complete its startup migration.
- `impact:ux-release-blocker`: Affected users cannot complete the upgrade or recover through the advertised Doctor path without terminal-level internal state repair.

## Summary

Keep open: three current-release upgrade reports show a real recovery dead end, and recent source history confirms that genuine legacy-versus-SQLite conflicts are intentionally preserved while Doctor invokes the same migration without offering a resolution. The fatal readiness gate therefore turns a compatibility safeguard into an upgrade-blocking crash loop.

## What This Changes

Make startup-migration conflicts recoverable through Doctor or equally explicit in-product guidance instead of leaving upgraded gateways in a fatal restart loop.

## Best Possible Solution

Provide a Doctor-owned recovery transaction that backs up every conflicting legacy artifact, presents an explicit authoritative-side choice or narrowly safe default, verifies the resulting SQLite state, and only then enables service restart; expose the same Fix action in status/app recovery so users never need manual file moves, SQL, or launchctl/systemctl knowledge.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When legacy plugin or health metadata genuinely conflicts with shared SQLite during startup, should Doctor require an explicit authoritative-side choice, or may it automatically back up and retire regenerable legacy sources?

Rationale: The existing fail-safe policy preserves true conflicts to avoid silently discarding meaningful metadata, but the new fatal readiness gate makes leaving them unresolved an unusable upgrade path; code evidence cannot choose the intended compatibility policy.

Likely owner: steipete

Owner reason: Recent merged history covers both the shared migration ownership boundary and the startup lease/readiness recovery behavior that created this policy intersection.

Owner confidence: high

Options:

- **Guided Doctor Resolution (recommended):** Add a backed-up Doctor repair flow that displays each conflict, recommends the safe side when provable, and requires confirmation for ambiguous records before restarting the service.
- **SQLite Wins Automatically:** Treat shared SQLite as authoritative for these legacy sources, archive all conflicting files, and document the compatibility tradeoff with focused upgrade tests.
- **Keep Fail-Closed:** Retain unresolved conflicts as fatal but replace the no-op Doctor hint with exact supported backup and recovery commands plus visible app/status guidance.

## Reproduction Assessment

Yes at source and shipped-behavior level: seed conflicting legacy plugin/update/config-health state beside differing shared SQLite rows, then run startup and Doctor repeatedly. Three v2026.7.1 reports supply matching real-world outcomes, though this review did not execute the destructive upgrade scenario itself.

## Solution Assessment

No, leaving true conflicts active while making incomplete migration fatal and directing users to the same non-reconciling Doctor path is not a complete solution. The best fix is a backed-up, explicit Doctor resolution workflow with service restart deferred until migration verification succeeds.

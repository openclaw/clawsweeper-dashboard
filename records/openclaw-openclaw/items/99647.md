## Summary

Keep open: the intended Slack conflict retry is useful, but the branch breaks the relay delivery contract by scheduling an untracked local retry while rejecting the original awaited dispatch, which can leave the relay unacked and duplicate the Slack reply on redelivery.

## What This Changes

The PR treats wrapped Slack reply-session initialization conflicts as retryable, skips inbound delivery persistence for those failures, schedules bounded delayed re-enqueues, and adds focused handler coverage.

## Best Possible Solution

Preserve the relay awaitDispatch/ack contract through bounded retries, or rely on relay redelivery for awaited deliveries, with tests proving one dispatch and one ack for the session-conflict path.

## Reproduction Assessment

Yes, from source inspection: the PR drops dispatchCompletion on retry while current relay-source.ts sends its ack only after an awaited handler resolves. The scheduled retry also bypasses the handler's persisted inbound-delivery precheck.

## Solution Assessment

No. Recognizing the wrapped session-init conflict is the right layer, but the retry implementation must keep relay acknowledgement tied to the retry outcome or let the relay own the retry.

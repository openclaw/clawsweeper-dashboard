## Summary

Keep open for maintainer review: the PR targets a real gateway/plugin routing gap, but the current branch is not merge-ready because scoped route loading happens from the HTTP request path, uses active plugin loading, and splits auth from the registry used for dispatch.

## What This Changes

The PR adds manifest `activation.onRoutes` route hints, bundled plugin manifest updates, route-owner planning, docs, and a gateway plugin HTTP fallback that loads a scoped route registry after startup-registry misses.

## Best Possible Solution

Integrate manifest-planned route ownership into the current server-local route registry lifecycle with non-activating, gateway-owned caching so auth and dispatch share one registry snapshot before any route handler runs.

## Reproduction Assessment

Source-reproducible: the PR head shows scoped route loading happens after startup-route matching misses, while the gateway auth stage decides gateway-auth enforcement before that scoped registry exists. I did not run a live gateway repro or PR test suite because this review is read-only.

## Solution Assessment

No; this is a plausible direction but not the best merge shape because request misses should not activate global plugin registries or split auth and dispatch registry snapshots. The safer design is a non-activating gateway-owned scoped route registry prepared before auth and dispatch decisions.

## Review Findings

Full review comments:

- **[P1] Avoid activating plugin registries from request misses:** `src/plugins/runtime/http-route-registry-loader.ts:30-38`
  - body: `loadOpenClawPlugins` defaults to an active load, so this request-path fallback can clear/restore global plugin state and replace the active registry while serving an unmatched HTTP request. Build this scoped registry as a non-activating gateway-owned snapshot/cache before using it for route dispatch.
  - confidence: 0.9
- **[P2] Authenticate against the scoped route registry before dispatch:** `src/gateway/server/plugins-http.ts:84-90`
  - body: The gateway auth stage only sees the startup route registry; scoped routes are loaded later inside plugin dispatch. A scoped-only `auth: "gateway"` route on an unprotected path will be found after auth was skipped, so even valid gateway credentials cannot satisfy it consistently.
  - confidence: 0.85
- **[P2] Isolate failed scoped owners from healthy route owners:** `src/plugins/runtime/http-route-registry-loader.ts:32-33`
  - body: With `throwOnLoadError: true`, any failed plugin in the scoped owner set throws the whole scoped load. Because plugin HTTP is a continue-on-error stage, one broken route owner can make unrelated healthy scoped routes unreachable for that request.
  - confidence: 0.87

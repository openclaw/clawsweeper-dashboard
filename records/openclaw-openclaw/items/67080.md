## Label Justifications

- `P1`: The PR touches gateway plugin HTTP dispatch and can introduce security-boundary and availability regressions in a user-facing route path.
- `merge-risk: 🚨 compatibility`: The branch changes gateway plugin route activation and registry fallback behavior that existing plugins and startup/runtime registry invariants depend on.

## Summary

Keep open: this maintainer-labeled PR still targets a useful missing route-activation consumer, but the current branch is conflicting and not merge-ready because the scoped fallback can activate plugin runtime from HTTP requests, misses the existing auth decision point for scoped gateway routes, and lets one failed route owner block healthy scoped routes.

## What This Changes

The branch adds manifest-driven `gateway-plugin-http` route activation planning, route-owner trust filtering, scoped fallback route registry loading, bundled manifest hints, docs, and tests.

## Best Possible Solution

Move scoped route-owner resolution into a gateway-owned, non-activating, cached lifecycle that feeds auth and dispatch from the same stable registry, isolates owner failures, and is reconciled with the broader deferred runtime attachment work.

## Reproduction Assessment

Yes, at source level: current main has `activation.onRoutes` metadata/planning but no gateway `gateway-plugin-http` live consumer, and the PR adds a scoped fallback consumer. I did not run a live gateway/plugin traffic reproduction in this read-only review.

## Solution Assessment

No. The requested behavior is useful, but request-time activating loads are not the best fix; the route-owner registry should be prepared under gateway lifecycle ownership before auth and dispatch decisions.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P1] Avoid activating plugin registries from requests:** `src/plugins/runtime/http-route-registry-loader.ts:30-38`
  - body: This scoped route loader is called from the HTTP request path after a startup-registry miss, but it calls `loadOpenClawPlugins` without `activate:false`. The loader activates registries by default, so a network request can replace process-global plugin runtime state and rerun plugin initialization instead of using a gateway-owned stable route snapshot.
  - confidence: 0.91
- **[P2] Run auth before dispatching scoped gateway routes:** `src/gateway/server/plugins-http.ts:83-90`
  - body: Scoped routes are matched only after `plugin-auth` has already decided whether gateway auth is required from the startup registry. A scoped route with `auth: "gateway"` on a non-protected path will then be blocked without `gatewayAuthSatisfied`, making that route class unreachable even when the caller sends valid credentials.
  - confidence: 0.86
- **[P2] Keep one bad route owner from blocking scoped routes:** `src/plugins/runtime/http-route-registry-loader.ts:32`
  - body: The scoped loader uses `throwOnLoadError: true` for the whole planned owner set. If one route-owner plugin is broken or unconfigured, the exception skips the plugin-http stage for this request, so healthy scoped routes do not get a chance to match.
  - confidence: 0.84

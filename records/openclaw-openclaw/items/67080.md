## Summary

Keep open: this maintainer PR is useful direction, but it is not merge-ready because the gateway HTTP miss path can still trigger activating plugin runtime loads, and the design needs rebase-level integration with current main's server-local route-registry lifecycle.

## Best Possible Solution

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P1] Avoid activating plugin registries from request misses:** `src/plugins/runtime/http-route-registry-loader.ts:30-38`
  - body: This loader is reached from the plugin HTTP route miss path and calls `loadOpenClawPlugins` without `activate:false`. The loader activates by default on current main, so an unmatched network request can execute plugin runtime and replace process-global plugin state instead of using a gateway-owned snapshot.
  - confidence: 0.9
- **[P2] Run auth against the same route set used for dispatch:** `src/gateway/server/plugins-http.ts:85-90`
  - body: Scoped route matching happens inside plugin dispatch after the earlier `plugin-auth` stage has already decided whether gateway auth is needed from the pre-scoped route registry. A scoped `auth: "gateway"` route outside the default protected paths can therefore be rejected even when the caller provided valid gateway credentials.
  - confidence: 0.84
- **[P2] Keep one bad route owner from blocking scoped routes:** `src/plugins/runtime/http-route-registry-loader.ts:31-33`
  - body: Using `throwOnLoadError:true` makes one failing plugin in the planned route-owner set throw the whole scoped registry load. Because plugin HTTP is a continue-on-error stage, that skips healthy scoped routes that could have handled the request.
  - confidence: 0.86

## Label Justifications

- `P1`: The PR changes gateway plugin HTTP dispatch in a way that can introduce security-boundary and availability regressions on user-facing route handling.
- `merge-risk: 🚨 compatibility`: The branch changes plugin route activation and fallback registry behavior that existing gateway/plugin runtime invariants depend on.
- `merge-risk: 🚨 security-boundary`: The diff lets network-triggered HTTP misses load plugin runtime and potentially mutate process-global plugin state.
- `merge-risk: 🚨 availability`: Repeated request-time loading or one failing scoped route owner can skip healthy plugin routes or destabilize the gateway route stage.

## Summary

Keep open: this maintainer-labeled PR is still useful but not merge-ready because the scoped route fallback can activate plugin runtime from HTTP request handling, scoped gateway-auth routes are matched after the auth stage, and the branch conflicts with current main's newer gateway route-registry lifecycle.

## What This Changes

The PR adds manifest-driven scoped gateway plugin HTTP route loading from `activation.onRoutes`, shared route-id normalization, bundled plugin route hints, docs, and seam tests.

## Best Possible Solution

Move scoped route-owner loading into a gateway-owned, non-activating stable lifecycle, include scoped routes in auth decisions, isolate failed route owners, and reconcile the route-manifest work with the broader deferred runtime attachment path.

## Reproduction Assessment

Yes at source level: current main has manifest `activation.onRoutes` planning metadata, and the PR adds a scoped route consumer from the HTTP request path. I did not run a live gateway/plugin traffic reproduction in this read-only review.

## Solution Assessment

No. The route-owner planning idea is useful, but request-time activating plugin loads are the wrong layer; the safer solution is a gateway-owned non-activating lifecycle integrated with auth and failure isolation.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P1] Avoid activating plugin registries from requests:** `src/plugins/runtime/http-route-registry-loader.ts:30-38`
  - body: This scoped route loader is called after an HTTP route miss, but it calls `loadOpenClawPlugins` without `activate:false`. The loader activates registries by default on current main, so network traffic can execute plugin runtime and replace process-global plugin state instead of using a gateway-owned stable route snapshot.
  - confidence: 0.91
- **[P2] Run auth before dispatching scoped gateway routes:** `src/gateway/server/plugins-http.ts:83-90`
  - body: Scoped routes are matched only after the `plugin-auth` stage has already decided whether gateway auth is required from the startup registry. A scoped route with `auth: "gateway"` on a non-protected path can therefore be blocked without `gatewayAuthSatisfied`, even when the caller sends valid credentials.
  - confidence: 0.86
- **[P2] Keep one bad route owner from blocking scoped routes:** `src/plugins/runtime/http-route-registry-loader.ts:32`
  - body: The scoped loader uses `throwOnLoadError: true` for the full planned owner set. If one route-owner plugin is broken or unconfigured, the exception skips the plugin-http stage for this request, so healthy scoped routes do not get a chance to match.
  - confidence: 0.84

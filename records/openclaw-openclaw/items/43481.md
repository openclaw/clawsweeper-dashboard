## Summary

Keep open: current main still has no provider media trust-policy surface, the agent fallback paths still replay or load prompt-local images, and the linked implementation candidate remains open and unmerged.

## What This Changes

Request provider-level media trust controls so cross-provider fallback can restrict images and attachments separately from text fallback.

## Best Possible Solution

Keep this issue as the canonical tracker until maintainers land a privacy-preserving provider media trust policy, or explicitly document configured fallback as consent to send media across providers.

Likely owner: vincentkoc

Options:

- **Add explicit media trust policy (recommended):** Preserve the current default for compatibility, then add a documented config surface and tests so users can restrict cross-provider images and attachments.
- **Fail closed on cross-provider media:** Strip images and prompt-detected media whenever fallback crosses providers, accepting that existing multimodal fallback setups may lose context after upgrade.
- **Document configured fallback as consent:** Leave runtime behavior unchanged and make docs state that configured fallback providers may receive the same media payloads as the primary provider.

Yes, source-level. Current main forwards explicit images into CLI fallback and loads prompt-local images in the embedded runner, while the model config schema has no provider media trust policy.

## Solution Assessment

Unclear until maintainer security/product review. A trust-policy surface is a plausible solution, but the permanent default and upgrade behavior need an explicit decision before implementation is settled.

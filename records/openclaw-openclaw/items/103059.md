## Summary

Keep open: current main and the latest release still have an unguarded migration config merge path reachable from Hermes migration-import data, while sibling config writers already block prototype-bearing keys.

## What This Changes

The issue requests guarding migration config patch merge/write helpers against `__proto__`, `constructor`, and `prototype` keys imported from Hermes provider, MCP, or skill config.

## Best Possible Solution

Add shared blocked-key handling to the migration config patch merge/write helpers, cover direct helper behavior plus Hermes provider/MCP/skill imports, and preserve normal safe config merges.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should the public migration config patch helper drop blocked object keys, reject the affected migration item, or use another explicit failure mode when imported config contains `__proto__`, `constructor`, or `prototype`?

Rationale: The bug is clear, but the permanent security contract for a public plugin SDK helper affects bundled and third-party migration providers and should be set by a maintainer before automation changes behavior.

Likely owner: steipete

Owner reason: Peter introduced the migration provider/onboarding helper path and is the clearest routing owner for the SDK helper boundary decision.

Owner confidence: high

Options:

- **Guard the shared SDK helper (recommended):** Block prototype-bearing keys in `mergeMigrationConfigValue`/`writeMigrationConfigPath` and add regression coverage for direct helper and Hermes-imported provider/MCP/skill keys.
- **Sanitize only Hermes imports:** Filter Hermes provider/MCP/skill keys locally, which fixes this reported path but leaves the SDK helper unsafe for other migration providers.
- **Defer as trusted import input:** Leave migration imports unchanged and document that tampered prior-tool configs are out of scope, accepting the current prototype-write primitive.

## Reproduction Assessment

Yes, source-level: a Hermes config key named `__proto__` can flow into a migration patch value and then through `writeMigrationConfigPath`, where the recursive merge assigns it by bracket notation. I did not independently run the full interactive onboarding UI in this read-only review.

## Solution Assessment

Yes, the best fix is a narrow shared migration-helper guard using the existing `isBlockedObjectKey` pattern, with the maintainer deciding whether the SDK contract should drop or reject blocked keys.

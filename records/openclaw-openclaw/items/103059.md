## Summary

Keep open: current main and the latest release still have an unguarded migration config merge path reachable from imported Hermes config data, while sibling config writers already block prototype-bearing keys.

## What This Changes

The issue requests a prototype-pollution guard for migration-import config patch merging in the public plugin SDK helper path.

## Best Possible Solution

Add shared blocked-key handling to the migration config patch merge/write helpers, cover direct helper behavior plus Hermes provider/MCP/skill imports, and preserve normal safe config merges.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should the public migration config patch helper drop blocked object keys, reject the affected migration item, or use another explicit failure mode when imported config contains `__proto__`, `constructor`, or `prototype`?

Rationale: The vulnerability is clear, but the public SDK helper contract affects bundled and third-party migration providers, so the security boundary and user-facing failure mode need maintainer intent.

Likely owner: steipete

Owner reason: Peter introduced the migration provider/onboarding helper path and is the clearest routing owner for the SDK helper boundary decision.

Owner confidence: high

Options:

- **Guard shared SDK helper (recommended):** Block prototype-bearing keys in `mergeMigrationConfigValue` and `writeMigrationConfigPath`, with regression coverage for direct helper behavior and Hermes-imported provider, MCP, and skill keys.
- **Sanitize only Hermes imports:** Filter Hermes provider, MCP, and skill keys locally, fixing the reported bundled path while leaving the shared SDK helper behavior unchanged for other providers.
- **Document trusted import input:** Leave migration imports unchanged and treat tampered prior-tool configs as out of scope, accepting the current prototype-write primitive.

## Reproduction Assessment

Yes, source-level: a Hermes config key named `__proto__` can flow into a migration patch value and then through `writeMigrationConfigPath`, where the recursive merge assigns it by bracket notation. I did not independently run the full interactive onboarding UI in this read-only review.

## Solution Assessment

Yes, the best fix is a narrow shared migration-helper guard using the existing `isBlockedObjectKey` pattern, with the maintainer deciding whether the SDK contract should drop or reject blocked keys.

## Summary

Keep open: current `main` and the latest release still expose only global/per-agent sub-agent tool policy, while `sessions_spawn` has no public per-call tool restriction; the open implementation candidate must be reviewed rather than closing its canonical issue.

## What This Changes

Requests an additive per-spawn tool policy for `sessions_spawn` so each child agent can receive a narrower enforced tool set.

## Best Possible Solution

Land a narrow allow-only `sessions_spawn` restriction for supported native sub-agents, intersect it with every existing policy layer, bind it immutably to the child capability envelope, reject unsupported runtimes explicitly, and document/test empty, inherited, nested, restored, and plugin-tool cases.

## Risks / Open Questions

- The API must only narrow the already-effective parent, agent, profile, group, sandbox, and global policies; override semantics that can grant tools back would create a privilege-escalation path.
- The policy must remain attached to the child capability/session identity across restoration, follow-up turns, nesting, and context forks so later runs cannot silently regain tools.
- Native, ACP, CLI-backed, and plugin-launched sub-agent paths need an explicit support matrix; silently ignoring a restriction would give operators a false security guarantee.
- An allowlist is safer than a deny-only interface because newly added tools would otherwise become available automatically.

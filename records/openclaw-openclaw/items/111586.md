## Label Justifications

- `P1`: The patch can break existing Gateway TLS configurations at runtime when their valid CA bundle exceeds the newly imposed shared cap.
- `merge-risk: 🚨 compatibility`: An existing configured `caPath` that previously loaded can now be rejected solely because its bundle is larger than 64 KiB.
- `merge-risk: 🚨 availability`: Rejecting a configured CA bundle causes Gateway TLS setup to fail closed and can prevent the configured listener from starting.

## Summary

Needs changes before merge: the revised head still routes the optional CA bundle through the new 64 KiB cap, so existing valid TLS configurations with larger CA chains can now fail closed. The prior ClawSweeper P1 remains unfixed on the same head.

## What This Changes

The PR replaces unbounded Gateway TLS certificate, key, and CA file reads with a 64 KiB descriptor-based bounded reader and adds oversized-file and symlink coverage.

## Best Possible Solution

Keep the bounded-read hardening, but give CA bundles a separately justified bounded limit that preserves supported chain deployments and add a regression test for a valid CA bundle above 64 KiB.

Yes, from source: configure a valid CA bundle larger than 64 KiB and call `loadGatewayTlsRuntime`; the new shared helper rejects it before TLS initialization. The supplied proof confirms the same bounded-read failure mode for an oversized certificate, but not the CA path.

## Solution Assessment

No: applying one certificate-sized cap to all three TLS materials is not the best fix because CA bundles have a distinct supported size profile. A dedicated bounded CA limit with a regression test preserves both the hardening goal and existing configuration compatibility.

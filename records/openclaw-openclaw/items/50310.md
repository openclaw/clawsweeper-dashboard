## Summary

Keep open: current main and the latest release still mark archived Discord thread sessions stale rather than deleting or pruning their session-store rows, and the remaining cleanup path is destructive session lifecycle work that needs maintainer product direction.

## What This Changes

## Best Possible Solution

Define a maintainer-approved Discord orphan-session lifecycle with plugin-owned reachability checks, previewable cleanup candidates, explicit retention rules, and clear operator or agent permissions before destructive pruning runs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which product shape should OpenClaw support for stale Discord thread session cleanup: preview-first prune, agent/operator delete, automatic TTL cleanup, or no automatic cleanup for now?

Rationale: All viable fixes can delete persisted session state or hide conversation history, so automation should not choose the permission model, false-positive policy, or retention behavior without maintainer intent.

Likely owner: steipete

Owner reason: Session maintenance and durable-conversation preservation history makes this the strongest product-policy owner for destructive cleanup behavior.

Owner confidence: medium

Options:

- **Approve preview-first prune (recommended):** Add plugin-owned Discord reachability and revalidation behind a preview/apply cleanup flow before exposing automatic or agent-initiated deletion.
- **Expose controlled delete:** Add an explicit admin-scoped agent/operator deletion path for selected stale sessions while leaving automatic orphan discovery for a later design.
- **Defer destructive cleanup:** Keep the current reset-only behavior and rely on manual selected-session deletion until false-positive and retention policy are settled.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: archived Discord thread updates reset matching rows to `updatedAt: 0`, `sessions_list` reads persisted rows, and generic maintenance protects external channel/thread rows from pruning.

## Solution Assessment

Unclear. The need is valid, but unconditional startup GC, an agent-facing delete tool, and TTL auto-expiry each carry different safety and retention tradeoffs; a preview-first prune flow with plugin-owned revalidation looks safer.

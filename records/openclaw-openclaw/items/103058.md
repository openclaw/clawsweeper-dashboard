## Summary

Keep open: current main still shows the reported owner-boundary gap across `/learn`, `skill_workshop`, and `/approve`, and no merged or open PR specifically owns this issue yet. This is a security-boundary report, not stale cleanup.

## What This Changes

The issue reports that non-owner authorized senders can use `/learn`, `skill_workshop`, and `/approve` to create and apply workspace skills without the owner-tier gate used by plugin install commands.

## Best Possible Solution

Make live Skill Workshop writes from chat require owner/admin identity before applying workspace skills, and explicitly decide whether non-owner authorized senders may create pending proposals at all.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Skill Workshop chat authoring and lifecycle approval require owner/admin identity, and if so should the owner gate cover proposal creation as well as apply/reject/quarantine approval?

Rationale: The current implementation crosses a workspace-write security boundary, but the durable product choice is whether drafting pending proposals remains a normal authorized-user capability or becomes owner-only like live skill/plugin mutation.

Likely owner: steipete

Owner reason: He introduced `/learn` and has the clearest recent history across this command and Skill Workshop policy surface.

Owner confidence: high

Options:

- **Gate live writes and approvals (recommended):** Require owner or `operator.admin` for `skill_workshop` lifecycle actions and `/approve` decisions that resolve Skill Workshop plugin approvals, while separately evaluating whether pending proposal creation stays available to authorized senders.
- **Gate all Skill Workshop chat authoring:** Require owner or `operator.admin` for `/learn` and all `skill_workshop` mutating actions, making chat Skill Workshop match the Gateway admin proposal API boundary.
- **Keep same-chat approval:** Document and accept that authorized non-owner chat participants may create and apply workspace skills through approval prompts, which preserves current behavior but leaves the reported boundary open.

## Reproduction Assessment

Yes. Source inspection on current main shows the same missing owner identity checks described in the report, and the issue includes direct production-function proof; I did not execute the write path because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the exact security boundary. Owner/admin gating for live Skill Workshop apply/approval matches the existing Gateway admin scope and plugin-write precedent; proposal creation may need a separate product call.

- `P0`: The report describes a current-main owner/approval bypass that lets an authorized non-owner apply persistent workspace skill behavior.
- `impact:security`: The affected surface is an authorization boundary for who may approve and write live workspace skills.

## Summary

Keep open: current main still has a source-reproducible owner/approval bypass for Skill Workshop lifecycle writes. The affected code appears to be current-main-only relative to v2026.6.11, but it remains a security-boundary issue before the next release.

## What This Changes

Require owner-tier authorization for the `/learn` and `skill_workshop` apply/approval path so authorized non-owners cannot self-approve workspace skill writes.

## Best Possible Solution

Enforce an owner/operator-admin or explicit configured-approver boundary at the Skill Workshop lifecycle approval/apply path, while preserving the proposal-first workflow and adding focused non-owner regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Where should the owner boundary be enforced for Skill Workshop lifecycle writes and same-chat approval resolution?

Rationale: The safest fix must close the privilege path without accidentally breaking unrelated plugin approval flows that intentionally use same-chat fallback.

Likely owner: steipete

Owner reason: The current affected lines across the command, tool, and approval surfaces blame to the same commit authored as Peter Steinberger.

Owner confidence: high

Options:

- **Gate Skill Workshop lifecycle writes (recommended):** Require owner/operator.admin or an explicit configured approver for `/learn`-driven Skill Workshop lifecycle approval and direct `skill_workshop` apply/reject/quarantine paths, with regression tests for authorized non-owners.
- **Gate only `/learn` entry:** Block non-owner `/learn` requests but leave direct tool lifecycle calls and generic `/approve` same-chat behavior unchanged, which is narrower but likely incomplete.
- **Harden all same-chat approvals:** Change the generic empty-approver fallback for plugin and exec approvals, which may be safer globally but has broader compatibility impact.

## Reproduction Assessment

Yes. Current-main source inspection shows the `/learn` gate, tool apply path, and `/approve` authorization chain can be followed without owner status; the issue also includes direct production-function proof from the filing commit, though I did not run a live channel E2E in this read-only review.

## Solution Assessment

The requested owner-tier direction is the right fix shape, but it should cover the lifecycle approval/apply boundary rather than only the `/learn` entry point. The exact scope of generic same-chat approval hardening should be a maintainer security-boundary choice.

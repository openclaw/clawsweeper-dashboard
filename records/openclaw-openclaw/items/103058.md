- `impact:security`: The issue concerns owner authorization and approval authority for writing trusted skill content into the shared workspace.

## Summary

Keep open: current main still shows a concrete owner-authorization gap across `/learn`, `skill_workshop apply`, and `/approve`, and the broader Skill Workshop lifecycle approval issue is related but does not fully cover this permissive owner-bypass report.

## What This Changes

The issue reports that an authorized non-owner sender can use `/learn`, `skill_workshop apply`, and `/approve` to create, apply, and self-approve a live workspace skill without owner participation.

## Best Possible Solution

Add owner-tier authorization for live Skill Workshop lifecycle mutation and its approval-resolution path, with regression tests proving non-owner authorized senders cannot create, apply, or self-approve live workspace skills while owner paths still work.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Skill Workshop lifecycle writes require owner-tier authorization at the `/learn` entry point, the dynamic tool/service mutation path, the `/approve` resolution path, or all of those layers?

Rationale: The bug is concrete, but the durable boundary must be chosen by maintainers because callers can reach Skill Workshop lifecycle mutation through command routing, dynamic tool execution, and approval resolution separately.

Likely owner: steipete

Owner reason: They authored the current `/learn` command and the recent Skill Workshop lifecycle approval changes, which are the central decision surfaces.

Owner confidence: high

Options:

- **Enforce owner at every mutation boundary (recommended):** Require owner-tier authorization before `/learn` can start Skill Workshop authoring, before lifecycle apply/reject/quarantine can execute, and before `/approve` can resolve those lifecycle approvals.
- **Gate only chat entry points:** Block non-owner `/learn` and `/approve` while leaving lower-level tool/service calls governed by existing approval policy, which is smaller but trusts every non-chat caller.
- **Fold into broader approval-evidence design:** Treat this as part of https://github.com/openclaw/openclaw/issues/93278, accepting that the concrete bypass remains unresolved until the larger approval model is settled.

## Reproduction Assessment

Yes. Current-main source inspection reproduces the path: `/learn` uses the authorized-sender gate, `skill_workshop apply` has no sender identity to enforce, and `/approve` authorization does not receive `senderIsOwner`.

## Solution Assessment

Unclear pending maintainer security-boundary direction. The narrow maintainable fix is owner-tier enforcement around Skill Workshop lifecycle writes, but maintainers should choose whether that boundary lives at each entry point, the shared mutation service, approval resolution, or all of them.

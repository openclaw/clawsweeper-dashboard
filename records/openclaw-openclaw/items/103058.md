- `impact:security`: The affected behavior is authorization and approval enforcement for writing trusted Skill Workshop content into the workspace.

## Summary

Keep open: current main still allows the reported non-owner Skill Workshop path by source inspection, and the affected approval/owner boundary is security-sensitive enough to need maintainer handling before a fix is routed.

## What This Changes

The issue reports that `/learn`, the `skill_workshop` lifecycle apply path, and `/approve` can let a command-authorized non-owner create, apply, and approve a live workspace skill without owner participation.

## Best Possible Solution

Land a security-boundary fix that owner/admin-gates Skill Workshop authoring and lifecycle application, prevents same-chat approval from being the only authorization for live skill writes, and adds regression coverage for `/learn`, direct `skill_workshop` apply, and `/approve`.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Skill Workshop creation/application and its approval resolution require owner or `operator.admin`, and should the implicit same-chat plugin approval fallback be narrowed globally or only for `skill_workshop`?

Rationale: The source path is clear, but the permanent boundary affects non-owner chat users, plugin approval semantics, and potentially shipped direct Skill Workshop behavior.

Likely owner: steipete

Owner reason: The current feature-history evidence points to this owner boundary and Skill Workshop implementation work.

Owner confidence: high

Options:

- **Gate Skill Workshop writes (recommended):** Require owner or `operator.admin` for `/learn`, `skill_workshop` lifecycle writes, and approval of those writes, then audit the shared implicit approval fallback separately.
- **Gate only apply:** Allow non-owner users to draft proposals but require owner or `operator.admin` for apply/reject/quarantine and approval resolution.
- **Document shared-agent trust:** Keep same-chat behavior and document that command-authorized non-owner users can participate in Skill Workshop writes on a shared agent.

## Reproduction Assessment

Yes, source inspection on current main gives a high-confidence reproduction path: authorized non-owner `/learn` is not owner-gated, `skill_workshop` apply lacks caller identity, and `/approve` can rely on implicit authorization. I did not run a live chat E2E because this review is read-only.

## Solution Assessment

Unclear until the security boundary is chosen: owner/admin-gating the Skill Workshop write path is the narrow maintainable fix, but maintainers should decide whether to change the shared implicit plugin-approval fallback globally or only for this tool.

## Summary

Keep open: current main still shows a concrete owner-authorization gap across `/learn`, `skill_workshop apply`, and `/approve`, and the older Skill Workshop approval issue is related but not a full duplicate of this permissive bypass report.

## What This Changes

The issue reports that a non-owner authorized sender can use `/learn`, `skill_workshop apply`, and `/approve` to author, apply, and self-approve a live workspace skill without the owner gate used by plugin installs.

## Best Possible Solution

Add owner-tier authorization for live Skill Workshop lifecycle mutation and its approval-resolution path, with regression tests showing a non-owner authorized sender cannot create, apply, or self-approve a live workspace skill while the owner path still works.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Skill Workshop lifecycle writes require owner-tier authorization at the command, tool/service, approval-resolution path, or all of those layers?

Rationale: The report is a concrete authorization bypass, but the durable security boundary should be chosen by maintainers because `/learn`, dynamic tool execution, and `/approve` can each be entered through different runtime surfaces.

Likely owner: steipete

Owner reason: Recent history ties this handle to same-chat approval routing and Skill Workshop lifecycle approval fixes, which are the central decision surfaces here.

Owner confidence: high

Options:

- **Enforce owner at every mutation boundary (recommended):** Require owner-tier authorization before `/learn` can start Skill Workshop authoring, before lifecycle apply/reject/quarantine can execute, and before `/approve` can resolve the plugin approval for those lifecycle calls.
- **Gate only the chat entry points:** Block non-owner `/learn` and `/approve` use while leaving lower-level service/tool calls governed by existing approval policy, which is smaller but leaves more trust in callers.
- **Fold into broader approval-evidence design:** Treat this as part of https://github.com/openclaw/openclaw/issues/93278, accepting that the concrete bypass remains open until that larger model is settled.

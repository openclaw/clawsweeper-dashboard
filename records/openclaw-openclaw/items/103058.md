## Summary

Keep open: current main still contains the reported owner-authorization gap across `/learn`, `skill_workshop apply`, and `/approve`, and the related Skill Workshop approval issue is broader rather than a duplicate of this concrete bypass.

## What This Changes

The issue asks OpenClaw to owner-gate `/learn` Skill Workshop authoring, lifecycle apply, and approval submission so authorized non-owners cannot write live workspace skills.

## Best Possible Solution

Add owner-tier authorization for Skill Workshop live lifecycle mutation and its approval-resolution path, with regression coverage proving non-owner authorized senders cannot create, apply, or self-approve live workspace skills while owner paths still work.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Where should OpenClaw enforce owner-tier authorization for Skill Workshop authoring and lifecycle approval: `/learn`, `skill_workshop` lifecycle execution, `/approve` plugin approval resolution, or all of those layers?

Rationale: The source-level bypass is concrete, but choosing only one enforcement layer could leave another entry point open, while enforcing every layer changes a security boundary across chat commands, agent tools, and approval routing.

Likely owner: steipete

Owner reason: The decision is centered on same-chat approval routing and owner authorization semantics, where this history is strongest.

Owner confidence: high

Options:

- **Enforce owner at every mutation boundary (recommended):** Require owner-tier authority before `/learn` starts Skill Workshop authoring, before lifecycle apply/reject/quarantine executes, and before `/approve` resolves those plugin approval decisions.
- **Gate only chat entry points:** Block non-owner `/learn` and `/approve` use while leaving lower-level service/tool calls governed by existing approval policy, which is smaller but trusts callers more heavily.
- **Fold into the broader approval-evidence design:** Handle this with https://github.com/openclaw/openclaw/issues/93278, accepting that the concrete bypass remains open until the broader model is decided.

## Reproduction Assessment

Yes. The current source still routes `/learn` through an authorized-sender gate, applies Skill Workshop proposals without sender identity, and resolves approvals through helpers that do not receive `senderIsOwner`; the implicated files are unchanged from the filing commit.

## Solution Assessment

Unclear until maintainers choose the enforcement layer. The best direction is a narrow owner-boundary repair with tests, but the durable security boundary should be selected before queuing automation.

## Label Justifications

- `P1`: The issue describes a source-backed broken multi-account hook delivery workflow where callers can receive success while no channel message is delivered.
- `impact:message-loss`: The reported failure mode is silently lost outbound delivery from `/hooks/agent` in multi-account channel setups.
- `impact:auth-provider`: The dropped `accountId` affects account/provider routing for channels that need a specific configured account.

## Summary

Keep open: current main and v2026.6.11 still drop `accountId` before `/hooks/agent` becomes cron delivery, and the linked fix candidate at https://github.com/openclaw/openclaw/pull/43951 is still open rather than merged.

## What This Changes

Preserve `accountId` from `/hooks/agent` payloads through hook dispatch into cron delivery so multi-account channel deliveries route to the intended account.

## Best Possible Solution

Land a reviewed version of https://github.com/openclaw/openclaw/pull/43951 or an equivalent narrow repair that carries hook `accountId` into `CronDelivery` and covers the hook dispatch path with focused tests.

## Reproduction Assessment

Yes from source inspection: `normalizeAgentPayload()` ignores `accountId`, and `dispatchAgentHook()` builds cron delivery without it. I did not run a live WhatsApp multi-account setup, so this is source-reproducible rather than locally reproduced.

## Solution Assessment

Yes: routing the hook through the existing cron delivery normalization/account path is the maintainable fix boundary. A fallback-channel feature or new config surface would not address the specific dropped-field bug.

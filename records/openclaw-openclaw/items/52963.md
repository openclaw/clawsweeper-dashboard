## Summary

Keep open: current main and the latest release still treat Slack inbound routing as bot/app-account traffic and do not implement per-envelope user authorization routing or reply-as-user semantics for user-level DM events.

## What This Changes

Support Slack user-level Socket Mode `message.im` events and route replies through a configured Slack user token when user-token writes are enabled.

## Best Possible Solution

Keep this as a maintainer-owned Slack identity feature: design an explicit opt-in path that routes on Slack event authorizations, preserves bot-token defaults, documents scopes and consent, and proves the full user-level DM flow in a real Slack workspace.

Owner confidence: medium

Options:

- **Add explicit user-identity mode (recommended):** Keep bot-token behavior as default and add a clearly documented, live-proven opt-in that routes by Slack authorizations and sends with the selected user token only inside that mode.
- **Decline bundled support:** Keep OpenClaw’s bundled Slack plugin bot/app-authored and ask users who need full user impersonation to build or run a dedicated custom Slack integration outside core.
- **Broaden existing userToken behavior:** Treat `userTokenReadOnly: false` as permission to receive and send user-authorized DMs, accepting the larger upgrade and security blast radius.

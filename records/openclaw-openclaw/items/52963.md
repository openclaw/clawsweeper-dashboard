## Label Justifications

- `P2`: The issue affects a real Slack DM workflow but is an opt-in user-token capability requiring maintainer security/product review rather than an urgent core outage.
- `impact:message-loss`: The reported failure is that Slack DMs to the configured user identity are silently dropped before OpenClaw handles them.
- `impact:auth-provider`: The requested fix changes which Slack authorization identity and token route inbound events and outbound replies.
- `impact:security`: Receiving and responding as a regular Slack user crosses an identity and authorization boundary that can expose broader workspace authority.

## Summary

Keep open: current main and v2026.6.11 still treat Slack Socket Mode monitor startup and normal reply delivery as bot-token centered, while `userToken` is documented and tested as a read-helper/write-fallback surface rather than user-authorized DM ingress. The request is valid but security- and product-sensitive because it would receive and respond as a regular Slack user identity.

## What This Changes

Request support for Slack user-authorized `message.im` events and matching user-token replies so a dedicated Slack user account can act as the OpenClaw DM surface.

## Best Possible Solution

Design this as an explicit Slack plugin capability: route inbound events by the Slack authorization/user identity, select the matching send token for replies, document required user-event scopes, and prove the flow in a real Slack workspace before closing.

## Reproduction Assessment

No live high-confidence reproduction was established in this review. Source inspection does show the requested user-authorized ingress and user-token reply path is absent from current main and the latest release.

## Solution Assessment

Unclear as final product direction. The request is plausible, but the best fix needs maintainer-approved Slack identity semantics, scope guidance, and live proof rather than a narrow automatic patch.

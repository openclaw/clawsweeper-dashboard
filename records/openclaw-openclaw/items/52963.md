- `impact:security`: The request would let OpenClaw receive and send as a regular Slack user identity using a user token, which affects a sensitive identity boundary.

- `impact:auth-provider`: The requested fix depends on Slack token selection, user-token authorization, and inbound identity routing.

## Summary

Keep open: current main and v2026.6.11 still build Slack Socket Mode around the bot/app token pair and send normal monitor replies with the bot token, so user-authorized DM routing is not implemented. The request is meaningful but product/security-sensitive because it would receive and respond as a regular Slack user identity, so it needs maintainer review and live Slack proof rather than cleanup close.

## What This Changes

Support Slack user-level `message.im` events and route replies through the configured Slack user token for a dedicated regular Slack user account.

## Best Possible Solution

Add a maintainer-approved Slack user-identity mode in the Slack plugin that routes inbound envelopes by authorizing user/team, selects the send token from that inbound authorization, preserves the existing bot-token default, and includes security docs plus live Slack proof.

## Reproduction Assessment

No live current-main reproduction was run. Source inspection does confirm the requested user-level event routing is absent: the monitor is bot-token based and normal replies post through `ctx.botToken`, but Slack delivery of user-authorized events still needs live verification.

## Solution Assessment

Unclear as implementation. The requested direction matches the likely missing surface, but the best fix needs maintainer product/security approval for the identity model before choosing whether existing `userTokenReadOnly: false` is sufficient or a more explicit operator control is required.

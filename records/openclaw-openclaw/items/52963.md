## Label Justifications

- `P2`: This is a real Slack workflow gap with a bot-DM workaround and limited blast radius, but it is not an emergency core-runtime outage.
- `impact:message-loss`: DMs sent to the regular Slack user are reported as never reaching OpenClaw, which is a channel message-delivery loss.
- `impact:auth-provider`: The requested behavior depends on Slack token choice and authorizing-user routing, not just message formatting.
- `impact:security`: Replying as a human Slack user through an xoxp token changes the channel authorization and impersonation boundary.

## Summary

Keep open. Current main and v2026.6.11 still model Slack Socket Mode around bot/app tokens and bot-level event subscriptions; the Slack handler does not inspect event `authorizations` or choose an inbound/reply token from the authorizing user, while docs still say bot-token writes are preferred. This is a useful but security-sensitive Slack feature/product decision, not a conservative cleanup close.

## What This Changes

The issue requests Slack user-level `message.im` event support so OpenClaw can route DMs sent to a dedicated Slack user and reply with the configured user token.

## Best Possible Solution

Add an explicit opt-in Slack user-event mode in the Slack plugin that validates scopes/settings, routes inbound events by Slack envelope authorization, selects the matching user token only for that mode, preserves allowlist/audit boundaries, and ships docs plus focused source and live Slack proof.

## Reproduction Assessment

No high-confidence live reproduction was established. Source inspection does show the requested reply-as-user path is unsupported because Socket Mode requires a bot token and current writes prefer the bot token whenever it exists, but live Slack user-event delivery and scopes still need verification.

## Solution Assessment

No. Making `userTokenReadOnly: false` automatically process and reply as a human Slack user would be too implicit for the security boundary; a named opt-in Slack user-event mode with explicit docs, scopes, allowlists, and live proof is the safer solution.

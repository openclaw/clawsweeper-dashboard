## Summary

Keep open: current main still treats Slack Socket Mode, inbound message handling, and normal replies as bot-token-centered, with no user-event authorization mapping or user-token reply selection for Slack DMs. This remains a useful feature request, but it changes Slack identity, authorization, and impersonation boundaries, so it needs maintainer product and security review before implementation.

## What This Changes

Request Slack plugin support for user-authorized `message.im` DM events and replying via the matching configured user token so a dedicated Slack user account can act as the agent identity.

## Best Possible Solution

Design an explicit Slack-plugin-owned user-identity DM mode that maps inbound Slack authorizations to configured user tokens, selects the matching send token, documents scopes and audit tradeoffs, and keeps bot/app behavior as the default.

## Reproduction Assessment

No live high-confidence reproduction was run. Source inspection supports the missing capability because current main uses bot-token Socket Mode startup, bot-token normal replies, bot-events setup, and no authorizations-based user-token routing path.

## Solution Assessment

No, overloading `userTokenReadOnly: false` alone is not the best way to solve this issue. The safer route is an explicit Slack user-account DM mode with authorization mapping, token selection, tests, docs, and security guardrails.

## Summary

Keep open: current main and the latest release still build Slack Socket Mode around the bot/app identity and normal inbound replies use the bot token, so user-authorized DM routing and replies-as-user are not implemented. The remaining work changes Slack identity and token-routing semantics, so it needs maintainer product and security approval before implementation.

## What This Changes

The request is to let Slack DMs delivered on behalf of a configured regular user route inbound and reply through the matching xoxp user token.

## Best Possible Solution

Add an explicitly opt-in Slack plugin user-identity DM mode that maps inbound Slack authorizations to configured user tokens, selects the reply token from that authorization, documents required scopes and audit tradeoffs, and keeps bot/app identity as the default.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Slack support an explicit user-identity DM mode that accepts user-authorized message.im events and replies with xoxp tokens, or should OpenClaw keep bot/app identity as the only supported inbound DM path?

Rationale: The requested behavior would let OpenClaw act as a regular Slack user, while current docs and tests treat userToken as read-oriented and keep bot-token writes preferred when a bot token exists.

Likely owner: kevinlin-openai

Owner reason: They most recently worked on Slack per-event scope handling, which is the closest current-main decision surface for this authorization model.

Owner confidence: medium

Options:

- **Add explicit user-identity mode (recommended):** Design a named opt-in mode with authorization-scoped inbound routing, matching xoxp reply-token selection, docs, tests, and live Slack proof.
- **Keep bot-only DMs:** Document that user-level Slack event subscriptions are unsupported and keep DMs routed through the Slack app/bot identity.
- **Verify read-only first:** Add diagnostics for user-token scopes and delivered authorizations while deferring send-as-user behavior until the security model is approved.

## Reproduction Assessment

No live high-confidence reproduction was run. Source inspection supports the missing capability because current main constructs the Slack listener and normal replies around the bot token and has no user-authorizations-to-xoxp routing path.

## Solution Assessment

No, treating userTokenReadOnly:false as an implicit takeover mode is not the best solution. The safer maintainable path is an explicit user-identity mode with authorization mapping, token selection, tests, docs, and security guardrails.

## Summary

Keep open: current main and v2026.6.11 still treat Slack Socket Mode and normal replies as bot-token paths, while this request asks for a new user-authorized Slack DM identity mode with security-sensitive token routing.

## What This Changes

Request support for Slack user-authorized `message.im` DM events and replies sent through the matching configured xoxp user token so OpenClaw can operate as a dedicated Slack user.

## Best Possible Solution

Design an explicit Slack-plugin-owned user-account DM mode that maps inbound Slack authorizations to configured user tokens, selects the matching reply token, documents scopes and audit tradeoffs, and keeps bot/app behavior as the default.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw support an explicit Slack user-account DM mode that receives user-authorized events and replies with the matching xoxp user token, or keep user tokens read-oriented?

Rationale: The implementation is not just a routing fix; it changes Slack identity, token use, consent, and audit semantics for messages sent as a human user.

Likely owner: steipete

Owner confidence: high

Options:

- **Design explicit opt-in mode (recommended):** Add a named Slack user-account DM mode with authorization mapping, per-event send-token selection, docs, tests, and clear security warnings while preserving bot defaults.
- **Keep user tokens read-oriented:** Document that OpenClaw intentionally does not operate as a regular Slack user and close or defer this request as unsupported.
- **Prototype behind maintainer gate:** Allow a maintainer-sponsored experiment first, but do not ship it as general behavior until the security model is reviewed.

## Reproduction Assessment

No live high-confidence reproduction was run. Source inspection does show current main lacks the requested user-authorized Slack DM mode and still routes Socket Mode and normal replies through bot-token paths.

## Solution Assessment

No, overloading `userTokenReadOnly: false` is not the best way to solve this. The safer solution is an explicit opt-in user-account DM mode with authorization mapping, token selection, tests, docs, and security guardrails.

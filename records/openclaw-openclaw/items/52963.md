## Summary

Keep open: current main still treats Slack Socket Mode startup and monitor replies as bot-token based, while the requested user-authorized `message.im` routing and user-token replies are not implemented. The feature needs maintainer product and security review because it would let OpenClaw receive and respond as a regular Slack user identity.

## What This Changes

The issue requests Slack user-authorized `message.im` event handling and user-token replies so DMs to a regular Slack user account can be routed through OpenClaw.

## Best Possible Solution

Define a Slack-plugin-owned, explicit user-identity mode that routes inbound user-authorized envelopes by Slack authorization and chooses reply credentials safely, with docs, focused tests, and live Slack proof.

## Reproduction Assessment

Yes from source for the current-main gap: Socket Mode startup and monitor replies are bot-token based, while the requested user-authorized event route is not modeled. No live Slack workspace repro was run.

## Solution Assessment

Unclear until product and security approval; authorizing-user routing plus per-inbound token selection is plausible, but acting as a regular Slack user needs an explicit operator-controlled mode rather than implicit behavior from `userTokenReadOnly: false`.

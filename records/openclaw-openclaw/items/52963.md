## Label Justifications

- `P2`: This is a meaningful Slack channel improvement with message-loss impact for dedicated user-account agents, but the existing bot DM workaround keeps core Slack usage available.
- `impact:security`: The request would let OpenClaw receive and send as a regular Slack user identity using a user token, which affects identity and authorization boundaries.
- `impact:message-loss`: The reported symptom is that DMs sent to the configured regular Slack user are not processed by OpenClaw.
- `impact:auth-provider`: The requested behavior depends on Slack credential selection, user-token authorization, and inbound identity routing.

## Summary

Keep open: current main and the latest release still run Slack inbound Socket Mode through the bot/app-token path and normal monitor replies through the bot token, so user-authorized DM routing and reply-as-user behavior remain unimplemented. The request is useful, but it changes Slack identity, authorization, and token-selection semantics and needs maintainer product/security approval plus live Slack proof.

## What This Changes

Support Slack DMs delivered on behalf of a configured user token and route replies through that user token so a dedicated Slack user account can be controlled without the app badge.

## Best Possible Solution

Add an explicit Slack user-identity opt-in mode in the Slack plugin that preserves bot-token behavior by default, routes inbound events by authorizing Slack user/team, sends replies with the matching user token only under operator opt-in, and includes docs, tests, and live Slack proof.

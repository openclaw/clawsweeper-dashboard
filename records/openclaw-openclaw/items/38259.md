## Summary

Keep open: current main and the latest release still load allowed dotenv values literally, and the merged service-env change only skips whole-value unresolved references instead of implementing general `$VAR` or `${VAR}` expansion. The remaining choice is security-sensitive because it changes which credentials may propagate across workspace, global, config, runtime, and durable service-env boundaries.

## What This Changes

The issue requests expanding `$VAR` and `${VAR}` references in loaded workspace/global `.env` values while preserving existing process-env precedence.

## Best Possible Solution

Define one maintainer-approved dotenv expansion policy across workspace, global/state-dir, legacy gateway, config substitution, and service-env paths, then either implement it with focused security/precedence tests and docs or document dotenv values as intentionally literal.

## Label Justifications

- `P2`: The issue breaks plugin observability for Codex-native exec/bash failures with limited blast radius, but it is not a crash loop, security bypass, or first-run blocker.
- `impact:session-state`: Plugins receive incorrect per-tool outcome state for agent runs, causing hook consumers to misclassify command failures as successes.

## Summary

Keep open: current main still leaves Codex-native shell/apply_patch `after_tool_call` observers with the raw native `tool_response` string while suppressing the app-server path that has structured status and exit-code data.

## What This Changes

The issue requests structured Codex-native `after_tool_call` results so plugins can distinguish successful and failed exec/bash-family tool calls.

## Best Possible Solution

Define one canonical Codex-native `after_tool_call` payload that exposes status, exitCode, duration, and text output/error semantics, then add focused regression coverage for successful, nonzero, timeout/abort, and no-duplicate cases.

Options:

- **Canonical structured OpenClaw payload (recommended):** Use app-server commandExecution/fileChange completion data as the plugin-visible `after_tool_call` result for Codex-native shell/apply_patch and suppress the raw string relay for those tools.
- **Wait for upstream Codex shape:** Keep OpenClaw relaying Codex `tool_response` unchanged and coordinate an upstream Codex `PostToolUse` payload that includes status and exit-code fields.
- **Document raw-string contract:** Treat the current raw string as intentional compatibility and direct plugins needing exit codes to another surface, accepting weaker observability for this hook.

## Reproduction Assessment

Yes at source level: current main forwards Codex shell `tool_response` strings through the native relay and suppresses the structured app-server commandExecution observation when that relay is enabled. I did not run a live plugin repro in this read-only pass.

## Solution Assessment

Unclear until maintainers choose the hook contract, but the strongest direction is one structured `after_tool_call` observation for Codex-native tools with a stable text/output field for display-only consumers.

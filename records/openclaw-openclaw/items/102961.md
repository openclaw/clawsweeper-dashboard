## Label Justifications

- `P2`: This is a normal-priority plugin hook fidelity bug with real observability impact but no evidence of a crash loop, security bypass, or first-run blocker.
- `impact:session-state`: Plugins can record or react to the wrong per-tool outcome state because command failures and successes may be indistinguishable in the hook payload.
- `impact:other`: The issue affects public plugin observability/API usefulness, which is maintainer-visible but outside the more specific impact categories.

## Summary

Keep open: current main still has the reported Codex-native exec/bash payload gap because the native `PostToolUse` relay forwards Codex's string `tool_response` unchanged and suppresses the structured app-server fallback for command items.

## What This Changes

Fix `after_tool_call` for Codex-native exec/bash so plugins receive structured outcome fields instead of only flattened command output text.

## Best Possible Solution

Define one compatibility-aware `after_tool_call` outcome envelope for Codex-native exec/bash/apply_patch across native relay and app-server projection, preserving raw output while consistently exposing status, exitCode, error, and duration with tests and docs.

Required: true

Kind: product_direction

Question: Should OpenClaw normalize Codex-native `after_tool_call` results into an OpenClaw-owned structured envelope even when Codex native PostToolUse supplies shell output as a flat string, and where should raw output remain available?

Rationale: The bug is clear, but the repair changes the public plugin hook payload/timing boundary and must choose between native-relay immediacy, app-server structured fidelity, and duplicate-event avoidance.

Likely owner: steipete

Owner confidence: medium

Options:

- **Canonical structured OpenClaw payload (recommended):** Use app-server commandExecution/fileChange completion data as the plugin-visible `after_tool_call` result for Codex-native shell/apply_patch and suppress the raw string relay for those tools.
- **Ask Codex to change native payloads:** Keep OpenClaw relay behavior stable and require upstream Codex to emit structured shell/exec `tool_response`, accepting that the OpenClaw issue remains blocked until that ships.
- **Document raw-string compatibility:** Treat native Codex `PostToolUse` strings as the intended contract and document that plugins must use another surface for exit-code observability.

## Reproduction Assessment

Yes from source for the native relay path: Codex shell PostToolUse currently exposes `tool_response` as a string, OpenClaw forwards it as `event.result`, and the structured app-server observation is skipped when native PostToolUse relay is active; I did not run a live current-main plugin repro.

## Solution Assessment

The current main-only fallback is not a complete fix because it leaves the native relay path Codex-shaped; the best fix is a documented, compatibility-aware outcome envelope shared by both paths rather than a new mutating hook.

## Label Justifications

- `P2`: The issue breaks plugin observability for Codex-native exec/bash outcomes with limited blast radius and no crash, security bypass, or first-run blocker.
- `impact:session-state`: Plugin hook consumers receive incorrect per-tool outcome state and can misclassify command failures as successes.

## Summary

Keep open: current main still forwards Codex-native shell `PostToolUse` results as raw `tool_response` strings and suppresses the structured app-server observation path, so plugins still cannot reliably classify exec/bash failures from `after_tool_call`.

## What This Changes

The issue asks for `after_tool_call` plugin hooks to receive structured exec/bash tool result data instead of a flattened string so plugins can detect command failures.

## Best Possible Solution

Make one canonical `after_tool_call` observation for Codex-native shell/apply_patch that exposes structured status, exitCode, duration, and output/error semantics without emitting a duplicate raw-string event.

- **Wait for Codex upstream:** Keep OpenClaw relay behavior stable and require upstream Codex to emit structured shell/exec `tool_response`, leaving this issue blocked until that ships.
- **Document raw string contract:** Treat native Codex `PostToolUse` strings as the supported contract and document that plugins must use another surface for exit-code observability.

## Reproduction Assessment

Yes, at source level: current main forwards Codex shell `tool_response` strings through the native relay and suppresses the structured app-server commandExecution observation when that relay is enabled. I did not run a live plugin repro because this review is read-only.

## Solution Assessment

No complete fix exists yet; the best fix is to define one structured Codex-native `after_tool_call` payload path and add regression coverage that a failing exec exposes exitCode/status instead of only output text.

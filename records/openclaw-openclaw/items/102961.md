## Summary

Keep open. Current main added a structured app-server observation path for Codex-native command completions, but the native Codex PostToolUse relay still forwards Codex's `tool_response` as `event.result`; for shell commands Codex currently supplies that value as a flat string, and OpenClaw suppresses the structured app-server fallback when the native relay is active.

## What This Changes

The issue asks for `after_tool_call` on exec/bash-family tools to expose structured outcome data such as status, exitCode, error, and duration instead of only raw output text.

## Best Possible Solution

Define one compatibility-aware `after_tool_call` outcome envelope for Codex-native exec/bash/apply_patch across native relay and app-server projection, preserving raw output while consistently exposing status, exitCode, error, and duration with tests and docs.

Options:

- **Normalize with raw-output preservation (recommended):** Expose a consistent structured outcome for Codex-native tools while keeping the original text in an additive field so existing string consumers have a migration path.
- **Preserve Codex payload verbatim:** Keep forwarding Codex `tool_response` unchanged and document that native shell `after_tool_call.result` may be a flat string without exit status.
- **Add a parallel details field:** Leave `event.result` untouched but add a documented `resultDetails` or equivalent field for status, exitCode, error, and duration.

## Reproduction Assessment

Yes from source for the native relay path: Codex shell PostToolUse currently exposes `tool_response` as a string, OpenClaw forwards it as `event.result`, and the structured app-server observation is skipped when native PostToolUse relay is active; I did not run a live current-main plugin repro.

## Solution Assessment

The current main-only fallback is not a complete fix because it leaves the native relay path Codex-shaped; the best fix is a documented, compatibility-aware outcome envelope shared by both paths rather than a new mutating hook.

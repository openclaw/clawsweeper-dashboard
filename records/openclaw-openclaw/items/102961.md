## Label Justifications

- `P2`: This is a real plugin observability bug for Codex-native tool outcomes, but it has bounded blast radius and is not a release-blocking outage.
- `impact:session-state`: Plugins observing session/tool state cannot reliably distinguish successful and failed Codex-native tool calls from the current flattened payload.

## Summary

Keep open: current main still forwards Codex-native `PostToolUse` `tool_response` as the plugin `after_tool_call.result`, and the dependency contract/source shows that shell response is a JSON string, not structured status or exit-code data.

## What This Changes

The issue asks OpenClaw to expose a structured `after_tool_call` result for Codex-native exec/bash/apply_patch tools so plugins can distinguish successful commands from nonzero, timed-out, aborted, or failed tool calls.

## Best Possible Solution

Define one canonical structured Codex-native `after_tool_call` observation that includes text output plus status, exitCode, timeout/abort/error metadata, and fires once per tool call.

- **Add Parallel Structured Field:** Keep `result` as the raw text for compatibility and add a new documented field such as `outcome` or `details` for status and exit-code data.
- **Keep Raw String Contract:** Document that Codex-native `after_tool_call` is raw text only and leave plugins to use separate aggregate or trace surfaces for outcome data.

Yes from source, though I did not rerun the live plugin probe in this read-only review. Current main forwards Codex native `tool_response` directly as `after_tool_call.result`, upstream Codex supplies that shell response as a string, and OpenClaw suppresses the structured app-server fallback for native relay items.

## Solution Assessment

Unclear until maintainers choose the public plugin payload contract. The best repair is not plugin-side parsing; it should establish one canonical structured observation and keep text output available for existing display-only consumers.

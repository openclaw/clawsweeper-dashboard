## Label Justifications

- `P2`: The request is a bounded plugin API improvement with real lifecycle impact but no current core outage or urgent regression.
- `impact:session-state`: The issue concerns cancelling stale in-progress agent runs so plugin-managed session state does not drift after context changes.
- `impact:security`: The requested API would grant plugins authority to abort agent runs, which is a security and authorization boundary.

## Summary

Keep open: current main still lacks the requested injected `api.runtime.agent.abort({ runId })` plugin runtime API. Existing Gateway cancellation paths and partial-overlap PRs do not settle the plugin authority/security model or provide the exact plugin runtime contract.

## What This Changes

Requested addition of `api.runtime.agent.abort({ runId })` so plugins can cancel in-progress agent runs by run id.

## Best Possible Solution

Maintainers should first decide the plugin abort authority model, then either add a narrow scoped runtime method with SDK docs, API baseline coverage, and Gateway/plugin runtime tests, or document Gateway/session cancellation as the intended boundary.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose a supported plugin runtime abort API, and if so what ownership, session, and permission boundary must it enforce?

Rationale: The source gap is clear, but granting plugin code authority to abort arbitrary run ids is a product and security-boundary choice that automation cannot safely infer.

Likely owner: steipete

Owner reason: This is a Plugin SDK/Gateway product and security-boundary decision, and this handle is the strongest available routing candidate from adjacent runtime history and prior review context.

Owner confidence: medium

Options:

- **Design a scoped plugin abort API (recommended):** Approve a narrow `api.runtime.agent.abort` contract only after defining session/run ownership checks, trusted-plugin access, docs, and focused Gateway/plugin runtime tests.
- **Use existing Gateway cancellation only:** Decline a new runtime method and document `chat.abort` or session cancellation as the supported path for trusted in-process plugins or operator clients.
- **Defer for broader lifecycle design:** Keep this open but block implementation until plugin lifecycle permissions and run-management APIs are designed together.

## Reproduction Assessment

Yes. Source inspection reproduces the API gap: the current plugin runtime type, implementation, test, and docs do not expose `api.runtime.agent.abort`, while Gateway cancellation exists separately.

## Solution Assessment

Unclear. The requested shape is plausible, but the best permanent fix needs maintainer judgment around plugin authority, run ownership, session scoping, and whether existing Gateway/session-run cancellation is the intended contract.

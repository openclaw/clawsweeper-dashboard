## Summary

Keep open: current main still builds the CLI loopback MCP tool surface without the auth-profile store that xAI OAuth-only tool registration needs, but the exact fix must be reconciled with the open xAI billed-tool provider-boundary discussion before automation changes behavior.

## What This Changes

The issue requests that OAuth-only xAI `x_search` and `code_execution` register consistently for CLI-backend loopback MCP sessions and their xAI subagents.

## Best Possible Solution

Preserve a safe provider-billed tool boundary while making OAuth-backed xAI tools available to the sessions that actually run xAI, including subagents spawned from CLI-backed parents.

- **Add explicit cross-provider opt-in:** Allow `claude-cli` parent sessions to use xAI-billed tools only through an explicit allowlist or opt-in that makes billing ownership visible.
- **Restore credential-only CLI parity:** Thread the auth store into loopback so OAuth credentials make xAI tools visible to any CLI parent session, accepting the cross-provider billing exposure.

Yes, source-level reproduction is high confidence: current main's loopback resolver does not carry `authProfileStore`, while xAI OAuth-only tool registration requires the auth helper created from that store. I did not run a live `claude-cli`/xAI OAuth gateway session.

## Solution Assessment

Unclear until the provider-billing boundary is decided. Threading the auth store matches the native path, but the best fix should avoid making xAI-billed tools silently visible to non-xAI CLI parent sessions.

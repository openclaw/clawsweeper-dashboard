## Summary

Keep open: current main and the latest release still expose only the narrower `tools.fs.workspaceOnly` boolean, while the requested allow/deny filesystem policy and exec strategy remain unmerged, security-sensitive product work.

## What This Changes

The issue requests a configurable filesystem sandbox policy with mode, allowed paths, and deny paths for file and exec tools.

## Best Possible Solution

Keep this issue as the canonical tracker until maintainers choose a versioned `tools.fs` policy contract, explicitly decide the exec scope, and require normalization, symlink, media, apply_patch, subagent, docs, and upgrade proof before landing an implementation.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which host filesystem policy contract should OpenClaw standardize for this issue, and should the first version cover arbitrary shell/exec access or explicitly split that into a separate contract?

Rationale: Current main has only `tools.fs.workspaceOnly`, while open implementation candidates propose different public config shapes and leave different security boundaries around exec; automation cannot safely choose that product and security contract.

Likely owner: steipete

Owner reason: He has the strongest recent source, history, and discussion signal around the current filesystem policy contract.

Owner confidence: high

Options:

- **Standardize a `tools.fs` PathGuard contract and split exec (recommended):** Define the file/media/apply_patch boundary under `tools.fs` with canonical deny-wins path semantics, document exec as out of scope for v1, and keep the exec-specific work on https://github.com/openclaw/openclaw/issues/74379.
- **Adopt a typed roots model instead:** Use a `tools.fs.roots` style contract if maintainers prefer explicit `file`/`dir` and `ro`/`rw` roots over broad allow/deny path globs.
- **Defer to OS or sandbox backends:** Keep the current `workspaceOnly` model and recommend Docker, SSH, or local-user isolation for stronger host boundaries, accepting that native host allow/deny remains unavailable.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: the strict schema accepts only `tools.fs.workspaceOnly`, so the reported `tools.fileAccess` config is outside the current contract. Current tests also preserve outside-workspace host access when `workspaceOnly` is false or unset.

## Solution Assessment

No, the exact requested `tools.fileAccess` shape is not yet proven to be the best solution. The maintainable path is a maintainer-approved `tools.fs` or roots-style contract with explicit exec semantics and security proof.

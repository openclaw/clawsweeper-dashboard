## Summary

Keep open: current main and the latest release still expose only the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while the requested allow/deny path policy and explicit exec strategy remain unimplemented security/product work.

## What This Changes

Request to add a filesystem sandboxing config surface with allow/deny path rules and enforcement across file and exec tools.

## Best Possible Solution

Keep this issue open until maintainers choose and land one canonical filesystem policy design, likely under `tools.fs` or a successor permission policy, with normalized deny-wins path rules, clear symlink/nonexistent-path semantics, media/plugin propagation, and an explicit exec coverage decision or linked exec follow-up.

## Reproduction Assessment

Yes. Source inspection provides a high-confidence reproduction of the config gap: `tools.fs` is strict and only accepts `workspaceOnly`, while the requested allow/deny keys have no current runtime policy path.

## Solution Assessment

No for the exact `tools.fileAccess` shape as-is; the better solution is a maintainer-approved canonical `tools.fs` or permission-policy contract that avoids duplicated partial config surfaces and is honest about exec coverage.

## Summary

Keep open: current `main` and `v2026.6.11` still only expose the narrower `tools.fs.workspaceOnly` boolean, while this issue asks for configurable allow/deny filesystem policy and an explicit `exec` boundary. The open PathGuard PR is useful context, but it is unmerged and explicitly leaves arbitrary shell execution out of scope.

## What This Changes

Request to add configurable filesystem access restrictions with allowed and denied paths for OpenClaw tools, including a defined behavior for read, write, edit, apply_patch, and exec access.

## Best Possible Solution

Design a versioned core `tools.fs` filesystem policy with normalized deny-wins path rules for file/media/apply_patch paths, plus an explicit `exec` strategy or separately tracked exec limitation, and document the boundary honestly.

Options:

- **Adopt versioned tools.fs path policy (recommended):** Define `allowedPaths`/`denyPaths` semantics under `tools.fs`, require normalization/symlink tests, and make PRs state whether exec is included or linked to a separate canonical item.
- **Split file tools and exec:** Allow a file/media/apply_patch PathGuard direction only if the docs and issue cluster clearly preserve exec coverage as separate work.
- **Keep workspaceOnly only:** Decline path-level core config for now and direct operators to Docker, OS-user isolation, `tools.fs.workspaceOnly`, and current exec approval hardening.

Yes, source inspection reproduces the reported config gap: the strict schema and public type accept only `tools.fs.workspaceOnly`, so `tools.fileAccess.allowedPaths` and `denyPaths` remain invalid on current main.

## Solution Assessment

Unclear as an implementation path: the exact `tools.fileAccess` shape should not be accepted blindly; the maintainable solution likely belongs in a versioned `tools.fs` policy with explicit exec scope and compatibility handling.

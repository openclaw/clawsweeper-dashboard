## Summary

Keep open: current main and v2026.6.11 still only expose the narrower `tools.fs.workspaceOnly` filesystem guard, while this issue asks for a configurable path-rule security boundary with allow/deny paths and an explicit exec strategy.

## What This Changes

The issue requests a filesystem access policy config, originally shaped as `tools.fileAccess`, with sandbox/full mode plus `allowedPaths` and `denyPaths` for agent file and exec access.

## Best Possible Solution

Keep this as the canonical tracker until maintainers choose one versioned `tools.fs` filesystem policy contract, deny-wins normalization semantics, and an explicit exec-scope boundary, then land one reviewed implementation with docs and security-focused tests.

Owner confidence: high

Options:

- **Settle one `tools.fs` path-policy contract (recommended):** Choose a canonical config shape, require normalization/symlink/deny precedence coverage, and make exec coverage explicit before merging either implementation path.
- **Split exec into a separate boundary:** Land a file-tool-only policy only if docs and tracking state clearly say shell-mediated file access remains a separate security boundary.
- **Defer to OS/container isolation:** Reject or defer host filesystem ACLs if maintainers decide OpenClaw should only own workspaceOnly, tool-name policy, and sandbox backends for now.

## Reproduction Assessment

Yes for the reported schema gap: source inspection shows the strict `ToolFsSchema` and public `FsToolsConfig` only accept `workspaceOnly`. The broader allow/deny filesystem boundary is a feature/security design gap rather than a failing current contract.

## Solution Assessment

Unclear: the requested enforcement boundary is aligned, but `tools.fileAccess` itself is not yet the confirmed best API. A canonical `tools.fs` successor with explicit exec semantics is safer than adding a parallel config key.

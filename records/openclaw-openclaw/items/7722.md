## Summary

Keep open: current main and v2026.6.11 still expose only the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while the requested allow/deny filesystem policy and explicit exec strategy remain unmerged security/product work.

## What This Changes

The issue requests a configurable filesystem sandbox policy for OpenClaw tools, including allowed paths, denied paths, sandbox/full modes, and explicit behavior for file and exec access.

## Best Possible Solution

Keep this issue open as the canonical filesystem policy tracker until maintainers choose and land a versioned `tools.fs` or successor contract that covers file tools, media/apply_patch, canonicalization, deny precedence, and an explicitly documented exec strategy.

## Reproduction Assessment

Yes. Source inspection shows the strict tools schema has no `tools.fileAccess` key and `tools.fs` only accepts `workspaceOnly`, matching the reported unrecognized-key behavior without needing to mutate the checkout.

## Solution Assessment

No, not as the exact proposed `tools.fileAccess` shape. The best fix needs a maintainer-approved security/config contract under `tools.fs` or a successor, with explicit decisions for canonicalization, deny precedence, media/apply_patch, and exec scope.

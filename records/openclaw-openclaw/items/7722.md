## Summary

Keep open: current main and the latest release still provide only the narrower `tools.fs.workspaceOnly` / `tools.exec.applyPatch.workspaceOnly` controls, while the requested allow/deny filesystem policy and exec strategy remain unresolved security/product work.

## What This Changes

The issue requests a configurable filesystem access policy such as `tools.fileAccess` with allow and deny path rules enforced across file and exec tools.

## Best Possible Solution

Keep one maintainer-owned core design path for a canonical `tools.fs` filesystem policy that explicitly defines allow/deny semantics, path normalization and symlink behavior, migration/docs, and whether exec is covered in v1 or tracked separately.

## Reproduction Assessment

Yes. Source inspection shows the current strict schema only accepts `tools.fs.workspaceOnly`, so the reported `tools.fileAccess` and allow/deny keys would be rejected as unrecognized config.

## Solution Assessment

No, not as a drop-in autonomous fix. The desired security boundary is valid, but the exact public config shape and exec enforcement scope need maintainer security/product review before implementation.

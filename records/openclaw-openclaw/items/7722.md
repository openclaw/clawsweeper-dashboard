## Summary

Keep open: current main still only supports the narrower `tools.fs.workspaceOnly` boolean, while this issue asks for configurable allow/deny filesystem policy and an explicit exec/tool-layer security boundary. Related open PRs and issues are useful implementation/design paths, but none is merged or shipped as the canonical solution.

## What This Changes

Request a filesystem sandboxing configuration surface with allow/deny paths, deny precedence, and coverage across file and exec tool behavior.

## Best Possible Solution

Keep this issue as the canonical design tracker until maintainers choose one versioned `tools.fs` or successor policy contract with explicit allow/deny semantics, normalization and symlink rules, media/helper coverage, upgrade behavior, and a documented exec scope or separate exec policy follow-up.

## Summary

Keep this issue open as the canonical security-boundary decision: current main still exposes only binary workspace confinement, while the two open candidate PRs propose different granular policy contracts and neither constrains arbitrary shell-mediated filesystem access.

## What This Changes

Requests configurable allow/deny filesystem path restrictions across native file tools and exec.

## Best Possible Solution

Adopt one versioned policy under tools.fs with canonical deny-wins rules for every native filesystem and local-media path, while treating exec as a separate boundary enforced by real sandboxing or disabled runtime tools rather than best-effort shell parsing.

Options:

- **Canonical file-tool policy (recommended):** Choose one tools.fs path-policy contract for native file/media tools and document that exec requires sandboxing or denial.
- **Full process boundary:** Design the feature around an OS or container sandbox that constrains both native file tools and arbitrary child processes.
- **Keep workspace-only model:** Decline granular host-path policy and continue directing operators to workspaceOnly, dedicated OS users, VMs, or containers.

## Summary

Keep open: current main and v2026.6.11 still expose only the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while the requested allow/deny filesystem policy and explicit exec strategy remain unmerged security/product work.

## What This Changes

The issue requests a configurable filesystem access policy such as `tools.fileAccess` or an equivalent allow/deny path policy enforced across file and exec tools.

## Best Possible Solution

Keep this issue open until maintainers choose a versioned filesystem policy contract, likely under `tools.fs` or a successor, and enforce it consistently across file tools, media helpers, apply_patch, and an explicitly documented exec scope.

## Reproduction Assessment

Yes. Source inspection shows the strict tools schema does not include `tools.fileAccess`, and `tools.fs` only accepts `workspaceOnly`, which explains the reported unrecognized-key failure without mutating the checkout.

## Solution Assessment

No. Adding the exact proposed `tools.fileAccess` shape would be only a plausible implementation; the best fix needs a maintainer-approved contract for canonicalization, deny precedence, symlink/hardlink behavior, media helpers, apply_patch, and whether exec is covered or split into a separate tracked control.

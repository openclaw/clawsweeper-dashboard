## Summary

Keep open: current main and the latest release still expose only the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while the requested allow/deny filesystem policy and explicit exec strategy remain unmerged security/product work.

## What This Changes

The issue requests a filesystem sandboxing config surface with allowed and denied paths, covering file tools and exec-mediated filesystem access.

## Best Possible Solution

Keep this as the canonical filesystem allow/deny security-policy tracker until maintainers choose a versioned `tools.fs` or successor contract and define enforcement across file tools, media helpers, apply_patch, and the documented exec scope.

## Reproduction Assessment

Yes. Source inspection shows the strict tools schema does not include `tools.fileAccess`, and `tools.fs` only accepts `workspaceOnly`, which explains the reported unrecognized-key failure without mutating the checkout.

## Solution Assessment

No, not as the exact proposed `tools.fileAccess` shape. The best fix needs a maintainer-approved policy contract for canonicalization, deny precedence, symlink behavior, media helpers, apply_patch, and whether exec is covered or split into a separate tracked control.

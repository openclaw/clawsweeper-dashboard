## Summary

Keep open: current main and the latest release still expose only the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while the requested allow/deny path policy and explicit exec strategy remain unmerged security/product work.

## What This Changes

The issue requests a configurable filesystem sandbox policy, originally proposed as `tools.fileAccess`, with allowed paths, denied paths, and coverage for read, write, and exec tools.

## Best Possible Solution

Keep this issue open until maintainers choose a versioned filesystem policy contract, likely under `tools.fs` or a successor, with explicit canonicalization, deny precedence, symlink/hardlink behavior, media/apply_patch coverage, and a documented exec scope or separate exec follow-up.

## Reproduction Assessment

Yes. Source inspection shows current main's strict tools schema does not include `tools.fileAccess`, and `tools.fs` only accepts `workspaceOnly`, which explains the reported unrecognized-key failure without mutating the checkout.

## Solution Assessment

No. Adding the exact proposed `tools.fileAccess` shape is only a plausible implementation; the best fix needs maintainer approval for the canonical config surface, path normalization semantics, denial precedence, media/apply_patch behavior, and whether exec is covered in v1.

## Summary

Keep open: current main and v2026.6.11 still provide only the binary `tools.fs.workspaceOnly` guard, while the requested granular policy remains unresolved and the open candidate PRs use competing contracts that intentionally leave arbitrary shell execution outside the boundary.

## What This Changes

Requests a configurable filesystem access policy with allow/deny paths and enforcement across file and exec tools.

## Best Possible Solution

Define one canonical, versioned `tools.fs` policy with deny-wins semantics and explicit read/write capabilities, then enforce it consistently across file tools, apply_patch, local media, generated-file delivery, and subagents while either integrating exec with a real OS/container boundary or clearly documenting exec as outside the guarantee.

## Risks / Open Questions

- The open candidates define different permanent configuration models—allow/deny globs versus typed read/write roots—so implementation without a maintainer decision could create an unstable or duplicated security contract.
- A file-tool-only policy can give operators false assurance if arbitrary `exec` commands can still read or mutate the same denied host paths.
- A dependable boundary must specify normalization, nonexistent parents, symlink and hardlink behavior, case-insensitive filesystems, rename/copy source and destination checks, and race-resistant access rather than relying on lexical path matching.
- Changing the unrestricted default could break existing trusted host workflows and requires explicit upgrade behavior; retaining it means the new policy must be opt-in and accurately documented.

## Summary

Keep open: current main and v2026.6.11 still only expose the narrower `tools.fs.workspaceOnly` boolean, while this issue asks for a configurable allow/deny filesystem policy with an explicit exec boundary. Related PRs are useful implementation candidates or partial overlaps, but none is merged and broad enough to make the core security/config design complete.

## What This Changes

Requests a configurable filesystem access policy such as `allowedPaths` and `denyPaths` to restrict read/write/exec tool access beyond OS-user permissions.

## Best Possible Solution

Keep this as the canonical tracker until maintainers choose and land one versioned `tools.fs` path-policy contract with deny precedence, normalization/symlink semantics, explicit exec scope, docs, and security-focused tests.

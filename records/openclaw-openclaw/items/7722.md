## Summary

Keep open. Current main provides the narrower `tools.fs.workspaceOnly` guard and sandbox controls, but it does not provide the requested per-path allow/deny filesystem policy; its own security docs also state that tool policy does not inspect side effects inside allowed `exec`. The open PathGuard PR is relevant partial work, but it expressly excludes arbitrary shell execution, so it cannot complete this issue’s requested boundary without a maintainer decision on the security contract.

## What This Changes

Request a configuration-defined filesystem access boundary for agent tools, including normalized allow/deny paths and an explicit scope for shell execution.

## System Context

OpenClaw creates an agent tool set from configuration and may run it either on the host or in a sandbox. The filesystem policy governs file-oriented tools and local media paths, while `exec` is a separate runtime surface whose containment must be made explicit to operators.

## Architecture Diagram

flowchart LR
  A[Operator configuration] --> B[Tool and filesystem policy]
  B --> C[File and media tools]
  B --> D[Exec runtime]
  E[Sandbox mode and mounts] --> C
  E --> D
  C --> F[Host or sandbox filesystem]
  D --> G[Shell process]
  F --> H[Agent result]
  G --> H

## Best Possible Solution

Adopt one versioned `tools.fs` policy for normalized, deny-wins file and local-media access, document it as file-tool containment rather than shell containment, and direct operators needing `exec` isolation to a sandboxed or OS-isolated execution path until a separately designed shell contract exists.

Options:

- **Ship an explicit file-tool policy (recommended):** Define canonical `tools.fs.allowedPaths` and `tools.fs.denyPaths` with normalization and deny precedence, while documenting sandbox or OS isolation as required for arbitrary `exec`.

- **Keep the current guardrails:** Retain `workspaceOnly`, tool allow/deny, and sandbox guidance without adding a broader per-path host policy.

## Summary

Keep open: current main and the latest release still expose only the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while the requested allow/deny filesystem policy and explicit exec strategy remain unmerged security/product work.

## What This Changes

The issue requests a configurable filesystem access policy for OpenClaw tools with sandbox/full modes plus allow and deny path rules enforced across file and exec-style operations.

## Best Possible Solution

Keep this issue open as the canonical product/security tracker until maintainers choose and implement a versioned filesystem policy contract with explicit coverage for file tools, apply_patch, media helpers, normalization, and exec scope.

## Reproduction Assessment

Yes. Source inspection shows the strict tools schema does not include tools.fileAccess, and tools.fs only accepts workspaceOnly, which matches the reported unrecognized-key failure.

## Solution Assessment

No, not as a direct tools.fileAccess drop-in. The best solution needs a maintainer-approved policy contract under tools.fs or a successor surface, plus explicit decisions on deny precedence, canonicalization, symlinks, media helpers, apply_patch, and exec coverage.

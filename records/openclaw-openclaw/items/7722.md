## Summary

Keep open: current main and v2026.6.11 still expose only the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while the requested configurable allow/deny filesystem policy and explicit exec strategy remain unmerged security/product work.

## What This Changes

Request a filesystem access policy config that can restrict agent read, write, and exec path access with allowed and denied paths.

## Best Possible Solution

Keep this as the canonical tracker until maintainers approve a versioned filesystem policy contract, likely under `tools.fs` or a successor, with normalized deny-wins path enforcement across file tools, media helpers, apply_patch, and an explicitly documented exec scope.

## Reproduction Assessment

Yes. Source inspection shows the strict tools schema does not include `tools.fileAccess`, and `tools.fs` only accepts `workspaceOnly`, which explains the reported unrecognized-key failure without modifying the checkout.

## Solution Assessment

No. Adding exactly the proposed `tools.fileAccess` shape is only a plausible implementation; the best fix needs maintainer-approved semantics for canonicalization, deny precedence, symlinks, media helpers, apply_patch, and whether exec is covered or split into a separate control.

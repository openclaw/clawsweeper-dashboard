## Summary

Keep open: current main and v2026.6.11 still expose only the narrower `tools.fs.workspaceOnly` / `tools.exec.applyPatch.workspaceOnly` controls, while the requested allow/deny filesystem policy and exec strategy remain unmerged security/product work.

## What This Changes

The issue requests a configurable filesystem sandbox policy with allowed and denied paths, including explicit coverage for file tools and exec.

## Best Possible Solution

Keep this issue open until maintainers choose a versioned filesystem policy contract, likely under `tools.fs` or a successor, and enforce it consistently across file tools, media helpers, apply_patch, and an explicitly documented exec scope.

## Reproduction Assessment

Yes. Source inspection shows the strict tools schema accepts `tools.fs.workspaceOnly` only and the runtime policy carries only that boolean, so the reported `tools.fileAccess` / allow/deny config remains rejected on current main.

## Solution Assessment

No. Adding exactly the proposed `tools.fileAccess` shape would be only a plausible implementation; the best fix needs a maintainer-approved contract for canonicalization, deny precedence, symlink behavior, media/apply_patch coverage, and whether exec is covered or split into a separate tracked control.

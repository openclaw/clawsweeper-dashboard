## Summary

Keep open: current main and the latest release still expose only the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while the requested allow/deny filesystem policy and explicit exec strategy remain unmerged security/product work.

## What This Changes

Request filesystem sandboxing config that restricts file and exec access to declared allow/deny paths instead of relying only on OS permissions or the existing workspace-only boolean.

## Best Possible Solution

Maintain this as the canonical filesystem access-policy tracker until maintainers choose a versioned config contract and land one implementation that covers file tools, media helpers, apply_patch, and a clearly documented exec scope.

## Reproduction Assessment

Yes. Source inspection shows the strict tools schema does not include `tools.fileAccess`, and `tools.fs` only accepts `workspaceOnly`, which explains the reported unrecognized-key failure.

## Solution Assessment

No. Adding exactly the proposed `tools.fileAccess` shape is only one plausible implementation; the best fix needs a maintainer-approved contract for canonicalization, deny precedence, symlink behavior, media helpers, apply_patch, and exec scope.

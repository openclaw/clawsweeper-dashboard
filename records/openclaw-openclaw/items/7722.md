## Summary

Keep open: current main and v2026.6.11 still only expose the narrower `tools.fs.workspaceOnly` boolean, while the requested allow/deny path policy and exec scope remain unmerged security-sensitive product work.

## What This Changes

The issue requests a first-class filesystem sandboxing configuration surface such as `tools.fileAccess` with deny-wins allow/deny path rules across file and exec tools.

## Best Possible Solution

Keep this as the canonical filesystem policy tracker until maintainers choose a versioned `tools.fs` or successor contract that defines allow/deny semantics, path normalization, media/apply_patch coverage, and explicit exec scope.

## Reproduction Assessment

Yes by source inspection: the strict schema still rejects the requested `tools.fileAccess`/`allowedPaths`/`denyPaths` shape, and the runtime filesystem policy only carries `workspaceOnly`. I did not run a live config parse because this review is read-only.

## Solution Assessment

Unclear: a path policy belongs at the tool execution layer, but the exact `tools.fileAccess` versus `tools.fs` contract and the exec enforcement story need maintainer security/product agreement before implementation.

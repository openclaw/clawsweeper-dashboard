## Summary

Keep open as the canonical decision for configurable host filesystem policy. Current OpenClaw supports the narrower `tools.fs.workspaceOnly` guard, while the requested normalized allow/deny policy and an honest enforcement boundary for arbitrary `exec` remain unresolved; the open PathGuard PR is useful partial work, not completion.

## What This Changes

Request a configurable filesystem policy with allow/deny paths and a sandbox/full mode across file tools and shell execution.

## Best Possible Solution

Adopt one versioned `tools.fs` policy contract for file and local-media tools only, with deny-wins canonical path evaluation and explicit subagent ceilings; document that shell access requires an existing sandbox or a separately approved OS-level execution boundary, then narrow or replace the open PathGuard work around that decision.

Rationale: Path parsing cannot reliably make unrestricted shell execution equivalent to a filesystem authorization boundary, while a new public config contract affects existing tool behavior, setup guidance, and operator threat assumptions.

Likely owner: steipete

Owner confidence: high

Options:

- **Define file-tool scope first (recommended):** Adopt a clearly named `tools.fs` normalized allow/deny contract for file and local-media tools, state that it does not authorize or sandbox arbitrary shell commands, and direct stronger isolation to sandbox backends.
- **Require an end-to-end boundary:** Defer the configuration surface until OpenClaw can pair it with a supported OS/container/account execution boundary that also contains shell-mediated access.
- **Keep workspace-only only:** Retain the current workspace-only guard and close the broader policy direction only if maintainers intentionally reject granular host-path configuration.

## Solution Assessment

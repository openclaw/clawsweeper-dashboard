## Summary

Keep this issue open as the canonical filesystem-security decision. Current main still provides only binary workspace confinement, while two open candidate PRs propose different granular policy contracts and both leave arbitrary shell-mediated filesystem access outside their guarantees.

## What This Changes

Add configurable filesystem allow/deny enforcement for file operations and command execution.

## Best Possible Solution

Choose one canonical `tools.fs` policy, enforce deny-wins rules after canonical path resolution across every file and media operation with monotonic per-agent inheritance, and either add real exec containment or state prominently that shell access is outside the guarantee.

- **Canonical file policy with explicit exec boundary (recommended):** Select one `tools.fs` contract, land complete file and media enforcement, and clearly name arbitrary exec as outside the guarantee until separately contained.
- **Require exec containment in v1:** Do not ship granular filesystem controls until shell-mediated reads and writes are constrained by an enforceable OS or runtime mechanism.
- **Keep OS isolation authoritative:** Reject a granular core policy and continue directing strong isolation requirements to sandboxing, containers, virtual machines, or separate OS users.

## Reproduction Assessment

Yes at source level: current main’s strict schema rejects the requested granular keys, its effective policy carries only `workspaceOnly`, and exec uses a separate security model. This reproduces a missing capability rather than a regression against an existing contract.

## Solution Assessment

No, the proposed `tools.fileAccess` shape is not yet established as the best solution. The maintainable direction is a canonical `tools.fs` contract with complete path normalization, inheritance rules, and an explicit decision about exec.

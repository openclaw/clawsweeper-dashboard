## Summary

Keep open: current main and v2026.6.11 still only support the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while configurable allow/deny filesystem policy and exec-scope design remain unmerged security/product work.

## What This Changes

The issue requests a configurable filesystem access policy such as `tools.fileAccess` or an equivalent allow/deny path sandbox for file and exec tools.

## Best Possible Solution

Keep this issue open as the canonical filesystem access policy tracker until maintainers choose and implement a versioned `tools.fs` or successor contract with explicit normalization, deny precedence, media/apply_patch coverage, and exec scope.

## Reproduction Assessment

Yes. Source inspection shows the strict schema rejects the requested `tools.fileAccess`/allow/deny keys and current runtime policy only models `workspaceOnly`.

## Solution Assessment

No. The exact proposed `tools.fileAccess` shape is only one possible fix; the best solution needs a maintainer-approved config contract and explicit enforcement story across file tools, media helpers, apply_patch, and exec.

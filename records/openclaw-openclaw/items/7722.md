## Summary

Keep open: current main and v2026.6.11 still provide only `tools.fs.workspaceOnly` plus `tools.exec.applyPatch.workspaceOnly`, while the requested allow/deny filesystem policy and explicit exec boundary remain unresolved.

## What This Changes

The issue requests a configurable filesystem sandboxing policy such as `tools.fileAccess` with allowed paths, denied paths, deny precedence, and coverage for file operations and exec.

## Best Possible Solution

Keep this as the canonical filesystem policy tracker until maintainers choose the config contract and exec boundary, then land one implementation with schema/types/docs, regression tests, and upgrade or doctor guidance as needed.

## Reproduction Assessment

Yes. Source inspection shows the strict config schema rejects the requested keys, the runtime filesystem policy only carries `workspaceOnly`, and current tests preserve unrestricted host access when that boolean is false or unset.

## Solution Assessment

Unclear as an exact implementation. The existing `tools.fs.workspaceOnly` boolean is too narrow, and the best fix needs a maintainer-approved contract for normalization, deny precedence, symlink/media/apply_patch semantics, and whether exec is in scope or separately tracked.

## Summary

Keep open: current main still exposes only the narrower `tools.fs.workspaceOnly` boolean, and the latest stable release `v2026.6.11` has the same boolean-only filesystem policy while this issue asks for configurable allow/deny paths plus an explicit exec strategy.

## What This Changes

Issue #7722 requests a configurable filesystem sandboxing policy with allow/deny paths, deny-wins behavior, and coverage for file and exec tools.

## Best Possible Solution

Keep #7722 as the canonical tracker until maintainers choose a versioned `tools.fs` path-policy contract, deny-wins normalization semantics, and an explicit exec-scope plan.

Rationale: This defines a public config surface and security boundary, and the open implementation candidates make different compatibility, enforcement, and false-security tradeoffs.

Likely owner: steipete

Owner reason: steipete has the strongest current schema/tool-policy history and previously framed this issue as the canonical security-boundary decision.

Owner confidence: high

Options:

- **Settle one `tools.fs` path-policy contract (recommended):** Choose one canonical config shape, require normalization/symlink/deny precedence tests, and make exec coverage explicit before merging an implementation path.
- **Split exec into a separate tracker:** Allow a file-tool-only policy only if docs and labels clearly state that shell-mediated file access remains a separate boundary.
- **Defer host path ACLs:** Keep only `workspaceOnly` and sandbox backends if maintainers decide OpenClaw should not own host filesystem path policy beyond those existing controls.

Yes. Source inspection gives a high-confidence reproduction path for the reported config rejection: the strict filesystem schema only accepts `workspaceOnly`, and runtime policy carries only that boolean.

## Solution Assessment

Unclear as the final implementation shape: the security goal is aligned, but adding `tools.fileAccess` as a parallel key is not clearly better than a canonical `tools.fs` successor with explicit exec semantics.

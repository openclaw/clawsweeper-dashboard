## Summary

Keep open: current main and v2026.6.11 still only expose the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while the requested allow/deny filesystem policy and explicit exec strategy remain unmerged security/product work.

## What This Changes

The issue requests a configurable filesystem sandbox policy with allow/deny paths and exec-aware enforcement for agent file access.

## Best Possible Solution

Keep this issue open until maintainers choose a canonical `tools.fs` or successor filesystem policy contract, enforce it consistently across file tools, apply_patch, media helpers, and a documented exec scope, then land docs and upgrade-proof coverage.

## Reproduction Assessment

Yes. Source inspection is enough to reproduce the reported config rejection: the strict tools schema accepts `tools.fs.workspaceOnly` only and has no `tools.fileAccess`, `allowedPaths`, or `denyPaths` fields.

## Solution Assessment

No, not exactly as proposed. The best solution should be a maintainer-approved filesystem policy contract, likely under `tools.fs` or a successor, with explicit normalization, symlink, deny precedence, media/apply_patch, and exec-scope semantics rather than only adding the literal `tools.fileAccess` shape.

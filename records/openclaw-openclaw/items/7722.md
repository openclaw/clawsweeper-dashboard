## Summary

Keep open: current main and v2026.6.11 still only expose the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while the requested allow/deny filesystem policy and exec strategy remain unresolved security/product work with open partial implementation candidates.

## What This Changes

The issue requests configurable filesystem sandboxing, such as `tools.fileAccess`, with sandbox/full modes plus allow and deny path rules enforced across file and exec tools.

## Best Possible Solution

Keep this issue as the canonical filesystem policy tracker until maintainers choose and land a versioned policy surface, likely under `tools.fs` or a successor contract, with deny-wins path rules, normalization/symlink semantics, docs, regression coverage, and an explicit exec strategy or linked exec follow-up.

## Solution Assessment

Unclear as specified: a filesystem policy is the right product area, but the exact `tools.fileAccess` shape is not proven to be the best contract. The safer solution is a maintainer-approved `tools.fs` or successor policy with explicit normalization, deny precedence, exec scope, and upgrade semantics.

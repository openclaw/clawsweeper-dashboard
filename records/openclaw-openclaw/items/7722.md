## Summary

Keep open: current main and v2026.6.11 still expose only the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while the requested allow/deny filesystem policy and explicit exec strategy remain unmerged security/product work.

## What This Changes

Request to add configurable filesystem access restrictions with allowed and denied paths enforced across file operations and exec.

## Best Possible Solution

Adopt a maintainer-approved, versioned filesystem policy contract under `tools.fs` or a successor, enforce deny-wins path rules across file/media/apply_patch surfaces, and explicitly document or implement the exec strategy.

## Reproduction Assessment

Yes. Source inspection shows the strict tools schema does not include `tools.fileAccess`, and `tools.fs` only accepts `workspaceOnly`, which explains the reported unrecognized-key failure without mutating the checkout.

## Solution Assessment

No, not as the exact proposed `tools.fileAccess` shape. The maintainable fix needs a canonical policy contract, denial precedence, path normalization rules, media/apply_patch coverage, and an explicit decision on whether exec is covered or tracked separately.

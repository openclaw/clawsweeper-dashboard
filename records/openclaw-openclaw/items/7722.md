## Summary

Keep open: current main and v2026.6.11 still only expose the narrower `tools.fs.workspaceOnly` boolean, while this issue asks for configurable allow/deny path policy and an explicit exec strategy.

## What This Changes

Request a configurable filesystem access policy for agent tools with sandbox/full mode, allowed paths, denied paths, and read/write/exec enforcement.

## Best Possible Solution

Keep this as the canonical tracker until maintainers choose one versioned `tools.fs` path-policy contract with normalization, deny precedence, coverage tests, and explicit exec scope.

Question: What host filesystem boundary should OpenClaw expose: deny-wins `tools.fs` allow/deny paths, `tools.fs.roots` access modes, or workspace-only plus a separate exec path policy?

Rationale: The choice defines a public config surface and security boundary, and open candidate PRs show incompatible designs with different false-security and compatibility tradeoffs.

Likely owner: steipete

Owner confidence: high

Options:

- **Settle one tools.fs path-policy contract (recommended):** Choose the canonical config shape, require normalization/symlink/deny-precedence tests, and make exec coverage explicit before merging an implementation.
- **Split exec from file-tool policy:** Allow a file-tool-only policy only if docs and issue tracking clearly state shell-mediated filesystem access remains a separate boundary.
- **Stay with workspace/sandbox isolation:** Reject host path ACLs beyond `workspaceOnly` and sandbox backends if maintainers decide OpenClaw should not own that boundary.

## Solution Assessment

Unclear. The requested enforcement boundary is aligned, but `tools.fileAccess` is not yet proven to be the best API; a canonical `tools.fs` successor with explicit exec semantics is safer.

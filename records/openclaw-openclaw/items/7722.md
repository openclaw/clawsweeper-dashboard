## Summary

Keep open: current main and v2026.6.11 still only expose `tools.fs.workspaceOnly`, while this issue asks for configurable allow/deny path rules and an explicit exec/filesystem security boundary.

## What This Changes

The issue requests a new filesystem sandboxing config surface for path allowlists/denylists, with denied paths enforced across file tools and exec.

## Best Possible Solution

Keep this as the canonical tracker until maintainers choose a versioned `tools.fs` path-policy contract with deny-wins normalization semantics, explicit exec scope, docs, and security-focused tests.

Question: What filesystem boundary should OpenClaw expose for host-mode agents: a `tools.fs` allow/deny PathGuard policy, a `tools.fs.roots` access-mode policy, a narrower workspace-only/exec-split design, or no core host path ACL beyond sandboxing?

Rationale: This defines a public config and security boundary, affects existing operator workflows, and has competing open implementation designs with different compatibility and false-security tradeoffs.

Likely owner: steipete

Owner reason: steipete introduced and refactored the current workspace-only guard and already framed the prior maintainer-side review for this canonical issue.

Owner confidence: high

Options:

- **Settle one `tools.fs` path-policy contract (recommended):** Choose a canonical config shape, require normalization/symlink/deny precedence tests, and make exec coverage explicit before merging either implementation path.
- **Split exec into a separate security tracker:** Allow a file-tool-only policy only if docs, labels, and follow-up tracking clearly state shell-mediated filesystem access remains outside that boundary.
- **Defer to OS or container isolation:** Reject core host path ACLs if maintainers decide workspaceOnly plus sandbox backends are the intended boundary, then close related implementation PRs with that policy.

Unclear. The requested security boundary is aligned, but the exact `tools.fileAccess` API is not yet the confirmed best shape; a canonical `tools.fs` successor with explicit exec semantics is safer than adding a parallel key.

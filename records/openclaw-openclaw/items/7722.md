## Summary

Keep open: current main and the latest release still expose only the narrower `tools.fs.workspaceOnly` boolean, while the requested allow/deny filesystem policy and exec coverage remain security-sensitive product work with open, unmerged candidate PRs.

## What This Changes

Request a configurable filesystem sandbox policy with sandbox/full mode, allowed paths, denied paths, and enforcement across read, write, edit, and exec tools.

## Best Possible Solution

Keep this issue as the canonical maintainer design/security item until OpenClaw chooses a versioned filesystem policy contract, lands normalized deny-wins enforcement for filesystem tools, and either covers exec or explicitly tracks exec path policy separately.

## Reproduction Assessment

Yes for the config gap: current source shows the strict `tools.fs` schema only accepts `workspaceOnly`, so the reported `tools.fileAccess` shape would be rejected. This is not a strict bug reproduction because the request is for a new filesystem policy capability.

No final solution is present yet. The maintainable path is likely a maintainer-approved `tools.fs` or successor contract with explicit migration/docs and a clear exec boundary, not accepting the exact proposed `tools.fileAccess` shape by default.

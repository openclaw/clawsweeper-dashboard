## Summary

Keep this issue open as the canonical security-boundary decision. Current main provides binary workspace confinement, but normalized granular path rules and a truthful strategy for shell-mediated filesystem access remain unresolved; recent operator feedback and open candidate implementations make this active work rather than cleanup.

## What This Changes

Add configurable, deny-wins filesystem path restrictions for file and execution tools, with sandbox/full modes and explicit allowed and denied paths.

## Best Possible Solution

Define one versioned policy under the existing `tools.fs` contract with normalized deny-wins path rules, enforce it across every file and media helper, and either provide an OS-backed exec boundary or explicitly separate and document exec as outside the file-tool guarantee.

Options:

- **OS-backed complete boundary (recommended):** Specify path policy plus an OS-level sandbox backend so file tools and arbitrary exec share one enforceable filesystem boundary.
- **File-tool ACL v1:** Ship normalized deny-wins ACLs for file and media tools while explicitly documenting that unrestricted exec bypasses them.
- **Keep workspace-only model:** Decline granular in-process ACLs and direct users to Docker, VM, or per-user isolation for a complete boundary.

## Reproduction Assessment

Yes for the reported configuration gap: current source accepts only `tools.fs.workspaceOnly`, so the proposed granular keys are rejected and no equivalent cross-tool path policy exists. This is source-reproducible rather than a broken established contract.

## Solution Assessment

Unclear until maintainers choose the security boundary. A normalized deny-wins policy under `tools.fs` is the narrowest config design, but calling it sandboxing is unsafe unless shell-mediated access is constrained or explicitly excluded.

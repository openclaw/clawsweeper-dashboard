## Summary

Keep open: current main and v2026.6.11 still expose only the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while configurable allow/deny path policy and the exec-scope decision remain unmerged security/product work.

## What This Changes

The issue requests a configurable filesystem sandbox policy with mode, allowed paths, denied paths, and enforcement across file and exec tools.

## Best Possible Solution

Keep this issue as the canonical filesystem access policy tracker until maintainers either land a complete file-policy implementation and split exec to a linked follow-up, or choose a single policy contract covering both file tools and shell-mediated access.

Yes. Source inspection reproduces the config gap: current main rejects the requested keys because the strict `tools.fs` schema only accepts `workspaceOnly`; I did not run the CLI because this is a read-only cleanup review.

## Solution Assessment

No. Adding exactly the proposed `tools.fileAccess` shape is only a plausible path; the best fix needs a maintainer-approved `tools.fs` or successor contract with canonicalization, deny precedence, media/apply_patch coverage, and explicit exec scope.

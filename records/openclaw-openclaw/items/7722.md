## Summary

Keep this issue open as the canonical maintainer decision point: current main and v2026.6.11 still provide only binary `tools.fs.workspaceOnly`, while two open, conflicting candidate PRs propose incompatible granular policy contracts and neither constrains arbitrary exec-mediated filesystem access.

## What This Changes

Requests configurable allow/deny filesystem access restrictions across file and execution tools.

## Best Possible Solution

Select one canonical `tools.fs` policy with explicit read/write semantics across every file and media source and destination, enforce it after canonical path resolution, and treat arbitrary exec as a separately named boundary unless an OS-enforced sandbox can constrain it.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should the permanent core policy use allow/deny patterns or typed read/write roots, and may its first version explicitly exclude arbitrary exec-mediated filesystem access?

Rationale: The two open candidates encode materially different public configuration and security guarantees, and automation cannot safely choose which permanent contract OpenClaw should support.

Likely owner: steipete

Owner reason: The original workspace-only contract and prior maintainer-side review make steipete the strongest available owner for selecting its successor.

Owner confidence: high

Options:

- **Typed roots, file tools first (recommended):** Use explicit file/directory roots with read-only/read-write permissions across all host file and media paths, while documenting arbitrary exec as outside the guarantee.
- **Allow and deny patterns:** Use deny-wins path patterns with rigorous normalization, symlink, and operation semantics, while still treating arbitrary exec separately.
- **Require OS enforcement:** Defer granular core policy until a sandbox backend can enforce the same boundary for shell-mediated filesystem access.

## Reproduction Assessment

Yes. Current main and v2026.6.11 expose only binary `tools.fs.workspaceOnly`, intentionally preserve unrestricted host access when it is false, and construct exec through a separate enforcement path.

## Solution Assessment

No, not exactly as proposed. A new `tools.fileAccess` namespace would compete with the existing `tools.fs` owner boundary; the narrower maintainable solution is one canonical `tools.fs` contract with explicit operation, normalization, symlink, and exec-scope semantics.

## Summary

Keep open: current main and v2026.6.11 still expose only the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while the requested allow/deny filesystem policy and exec boundary remain unmerged security/product work.

## What This Changes

The issue requests configurable filesystem access restrictions with allow/deny paths, sandbox/full mode semantics, and coverage for read, write, edit, and exec tools.

## Best Possible Solution

Keep this as the canonical core security design issue until maintainers choose and land a versioned `tools.fs` or successor policy with path normalization, symlink coverage, deny precedence, media/helper propagation, docs, upgrade handling, and an explicit exec scope or linked exec follow-up.

## Reproduction Assessment

Yes for the reported config rejection: source inspection shows the strict filesystem schema accepts only `tools.fs.workspaceOnly`, so `tools.fileAccess` and path-rule keys would be rejected. This is a feature/security gap rather than a broken existing contract.

## Solution Assessment

No for the exact `tools.fileAccess` shape as-is; the maintainable solution should likely extend the existing `tools.fs` contract or a deliberate successor, with exec behavior explicitly covered or split into a canonical follow-up.

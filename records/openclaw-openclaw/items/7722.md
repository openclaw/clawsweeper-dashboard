## Summary

Keep open: current main and v2026.6.11 still expose only the narrower `tools.fs.workspaceOnly` boolean, while configurable allow/deny filesystem policy and exec scope remain unmerged security-sensitive product work.

## What This Changes

Request a configurable filesystem sandbox policy such as `tools.fileAccess` or an equivalent `tools.fs` allow/deny path contract for read, write, edit, and exec behavior.

## Best Possible Solution

Keep this as the canonical security/config issue until maintainers choose and land a versioned `tools.fs` policy shape with normalized deny-wins path checks, file/media/apply_patch coverage, and an explicit exec strategy or linked exec follow-up.

Rationale: Current main only has the boolean `tools.fs.workspaceOnly`, while open PRs propose incompatible public config surfaces and leave different parts of the security boundary out of scope.

Likely owner: steipete

Owner confidence: high

Options:

- **Land a file-tool policy first (recommended):** Choose a `tools.fs` allow/deny or roots contract for file/media/apply_patch tools, document that exec remains outside v1, and keep a separate exec boundary item open.
- **Require unified RWX policy:** Pause file-tool-only PRs until maintainers design one policy model spanning read/write/edit/apply_patch and exec path effects.
- **Stay with workspaceOnly and Docker:** Decline granular policy work and recommend Docker, VM, OS-user isolation, and `tools.fs.workspaceOnly` as the supported hardening path.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence reproduction path: strict `tools.fs` accepts only `workspaceOnly`, and tests preserve unrestricted host read/write/edit when that flag is false or unset.

## Solution Assessment

No, the literal `tools.fileAccess` shape is not yet the confirmed best solution. The best path is a maintainer-chosen `tools.fs` or successor contract that covers normalization, symlinks, deny precedence, upgrade behavior, and exec scope explicitly.

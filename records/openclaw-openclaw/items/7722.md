## Summary

Keep open: current main and the latest release still expose only the narrower `tools.fs.workspaceOnly` boolean guard, while the requested path allow/deny policy and explicit exec strategy remain unmerged security/product work. The open candidate PRs at https://github.com/openclaw/openclaw/pull/60981 and https://github.com/openclaw/openclaw/pull/52951 are useful context, but neither is merged and both leave shell-mediated filesystem access as a separate policy question.

## What This Changes

Request a config-enforced filesystem access policy for agent tools, with allow/deny paths covering file operations and an explicit strategy for exec-mediated filesystem access.

## Best Possible Solution

Design a versioned `tools.fs` or successor policy with normalized deny-wins path rules across file tools, apply_patch, local media, and plugin contexts, plus an explicit documented exec boundary or separate exec path policy.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: the strict config schema accepts only `tools.fs.workspaceOnly`, so the requested `tools.fileAccess` and allow/deny keys would be rejected. Current tests also preserve unrestricted host file access when `workspaceOnly` is false or unset.

## Solution Assessment

No final solution is selected yet. The literal `tools.fileAccess` shape is only one plausible API; a maintainable fix should likely live under `tools.fs` or a successor config contract and must settle exec coverage, upgrade behavior, and path-normalization semantics.

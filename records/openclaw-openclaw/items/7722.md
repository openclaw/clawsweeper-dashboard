## Summary

Keep open: current main still has only the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while the requested configurable allow/deny filesystem policy and exec strategy remain unresolved security/product work with active related implementation candidates.

## What This Changes

The issue requests a filesystem sandboxing config surface with `mode`, `allowedPaths`, and `denyPaths` that enforces path restrictions across file and exec tools.

## Best Possible Solution

Keep this open until maintainers choose and land a versioned filesystem access policy, likely under `tools.fs` or a successor config contract, with explicit deny precedence, normalization/symlink behavior, upgrade compatibility, and a documented exec strategy.

## Reproduction Assessment

Yes, from source inspection: the current strict config schema only accepts `tools.fs.workspaceOnly`, so the reported `tools.fileAccess` shape is rejected and the requested allow/deny policy cannot be expressed on current main.

## Solution Assessment

Unclear as a final design: an allow/deny filesystem policy is a plausible direction, but the best fix needs maintainer security/product review for config shape, upgrade behavior, path normalization, symlink handling, and whether exec is covered in v1.

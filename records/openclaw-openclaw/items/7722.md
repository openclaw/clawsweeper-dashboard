## Summary

Keep open. The requested configurable filesystem boundary remains a security-sensitive product decision: the previously reviewed current-main implementation had only the narrower `tools.fs.workspaceOnly` guard, while this request requires a durable policy contract for normalized allow/deny paths and an honest scope for shell-mediated access. The open PathGuard work is useful context, but an unmerged related PR is not completion. Likely related people: steipete (medium confidence, recent reviewer and adjacent contributor); SaucePackets (medium confidence, related default-policy contributor); Chris Zhang (medium confidence, current-path history signal).

## What This Changes

Add a configurable filesystem-access policy for agent tools, with normalized allow/deny paths, deny precedence, and an explicit enforcement boundary for arbitrary shell commands.

## System Context

OpenClaw builds agent file and execution tools from user and agent configuration. The filesystem policy determines which local paths file-oriented tools may reach, while the execution path can independently invoke shell commands that may also access the host filesystem.

## Architecture Diagram

flowchart LR

  Agent[Agent tool requests] --> FileTools[Read write edit media tools]
  Policy --> FileTools

  Exec --> HostFiles
  Policy --> Decision[Allow or deny decision]

## Best Possible Solution

Define one versioned `tools.fs` policy contract with deny-wins normalized path rules, explicit coverage for every file and media tool, and a separately documented decision for shell containment; preserve or migrate the existing workspace-only behavior deliberately rather than adding a competing config surface.

## Maintainer Decision

Kind: security_boundary

Question: Should OpenClaw’s first-class filesystem policy be a file-tool boundary only, or must it also provide an enforceable containment strategy for arbitrary shell execution before it is presented as sandboxing?

Rationale: The answer determines the security claim, configuration shape, upgrade behavior, test matrix, and whether the related implementation is sufficient; source inspection cannot safely choose that product and security boundary.

Likely owner: steipete

Owner reason: The supplied issue discussion shows this person framing the unresolved policy and execution boundary in the prior maintainer-side review.

Owner confidence: medium

Options:

- **File tools with explicit scope (recommended):** Ship normalized deny-wins rules for file-oriented tools while documenting that arbitrary exec is outside this boundary and remains governed by the existing execution/sandbox controls.
- **Require shell containment:** Do not expose the policy as filesystem sandboxing until the selected execution runtime can enforce the same host-path boundary for shell-mediated access.
- **Adopt sandbox isolation instead:** Keep host filesystem policy narrow and direct security-sensitive deployments toward OS, container, or per-agent-account isolation rather than extending host tool permissions.

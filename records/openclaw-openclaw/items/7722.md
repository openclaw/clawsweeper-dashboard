## Summary

Keep open: current main and v2026.6.11 still expose only the narrower workspace-only filesystem guard, while the requested configurable allow/deny filesystem policy and explicit exec scope remain unmerged security/product work.

## What This Changes

Request a filesystem sandboxing configuration surface that can allow and deny paths for read, write, edit, apply_patch, media, and exec-related access.

## Best Possible Solution

Keep this issue open until maintainers choose a versioned filesystem policy contract under `tools.fs` or a successor, enforce it consistently across file tools, media, apply_patch, and an explicitly documented exec scope, then land the chosen path with focused regression coverage.

## Reproduction Assessment

Yes. Source inspection shows the strict tools schema does not include `tools.fileAccess`, and `tools.fs` only accepts `workspaceOnly`, which explains the reported unrecognized-key failure without mutating the checkout.

## Solution Assessment

No. Adding exactly the proposed `tools.fileAccess` shape would be only one plausible implementation; the best fix needs maintainer approval for canonicalization, deny precedence, symlink behavior, media/apply_patch propagation, and whether exec is covered or split into a separate control.

## Summary

Keep open: current main and v2026.6.11 still expose only the narrower `tools.fs.workspaceOnly` and `tools.exec.applyPatch.workspaceOnly` controls, while allow/deny path policy and exec coverage remain unresolved. The related PRs are useful implementation candidates but are open and partial, so this issue remains the canonical tracker.

## What This Changes

The issue requests configurable filesystem sandboxing, including allow and deny path rules, under a config surface like `tools.fileAccess` and enforced across file and exec tools.

## Best Possible Solution

Keep this issue open as the canonical filesystem policy tracker, then choose a versioned `tools.fs` or successor config contract with explicit path normalization, deny precedence, exec scope, docs, and upgrade guidance.

## Reproduction Assessment

Yes. Source inspection shows current main rejects the requested config shape because `ToolFsSchema` is strict and only accepts `workspaceOnly`, while runtime policy and tests preserve the unrestricted default when that boolean is false or unset.

## Solution Assessment

No for closing or treating the literal `tools.fileAccess` shape as settled. The best path is a maintainer-approved `tools.fs` or successor policy design that reconciles allow/deny rules, `roots`/RWX alternatives, and exec coverage before implementation.

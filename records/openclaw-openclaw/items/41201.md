## Summary

Keep open: current main still accepts remote avatar values through CLI/config and exposes them as avatar metadata, while the Control UI deliberately refuses remote image rendering under its render gate and CSP, so the remaining problem is a real Control UI contract and security-policy mismatch.

## What This Changes

The issue reports Control UI avatars configured with `openclaw agents set-identity --avatar <url/path>` rendering as broken or missing images for remote URLs and local workspace paths.

## Best Possible Solution

Choose one Control UI avatar contract: keep local/data-only rendering and align CLI/docs/validation/diagnostics, or add a same-origin remote-avatar proxy/cache with strict MIME, size, auth, caching, privacy, and failure-feedback controls.

- **Keep Control UI local/data-only (recommended):** Preserve the current CSP posture and align CLI help, docs, validation, and UI diagnostics so remote avatars are not presented as renderable in Control UI.
- **Add same-origin remote proxy:** Support remote avatars only through a gateway-owned fetch/proxy/cache with strict MIME, size, auth, caching, privacy, and failure-feedback rules.
- **Allow direct remote image loads:** Let the browser load configured remote avatar URLs directly, accepting the weaker CSP and operator-browser privacy tradeoff.

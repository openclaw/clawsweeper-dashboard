## Summary

Keep open: current main and the latest release still accept remote avatar values through CLI/config, but the Control UI blocks remote image rendering by design, so this remains a real avatar contract mismatch that needs maintainer direction.

## What This Changes

The issue asks for Control UI avatars set via agent identity, especially `http(s)` URLs and workspace paths, to render instead of appearing as broken images.

## Best Possible Solution

Maintainers should choose one Control UI avatar contract: either a controlled same-origin remote-avatar proxy/cache, or an explicit local/data-only policy with aligned CLI/docs/validation and clear diagnostics.

Rationale: The remaining fix changes browser network-fetch behavior, CSP, privacy expectations, and the public avatar configuration contract, so automation should not pick the policy silently.

Likely owner: steipete

Owner confidence: high

Options:

- **Keep local/data-only Control UI avatars (recommended):** Preserve the current CSP posture and update CLI docs, validation, and UI diagnostics so remote avatars are not presented as renderable in Control UI.
- **Build a same-origin remote-avatar proxy:** Support remote avatars through a gateway-owned proxy/cache with explicit MIME, size, auth, caching, privacy, and failure-feedback behavior.
- **Allow direct remote image fetches:** Let the browser load arbitrary remote avatar URLs directly, accepting the CSP and operator-browser privacy tradeoff.

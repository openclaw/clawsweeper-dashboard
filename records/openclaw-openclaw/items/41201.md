## Summary

Keep open: current main still accepts remote avatar values through CLI/config, but Control UI deliberately rejects remote image rendering through its render gate, tests, and CSP, so the remaining fix needs maintainer product/security direction rather than cleanup closure.

## What This Changes

The issue asks for Control UI avatars configured through `openclaw agents set-identity --avatar` to render instead of appearing as broken images.

## Best Possible Solution

Maintainers should choose one Control UI avatar contract: either support remote avatars through a same-origin proxy/cache with explicit MIME, size, auth, caching, privacy, and diagnostics, or make Control UI local/data-only and align CLI/docs/validation with that policy.

Options:

- **Keep local/data-only rendering (recommended):** Preserve the current CSP posture and update CLI/docs/validation/UI diagnostics so remote avatars are not presented as renderable in Control UI.
- **Add a same-origin proxy/cache:** Support remote avatars only through a gateway-owned fetch/proxy/cache with strict MIME, size, auth, caching, privacy, and failure-feedback behavior.
- **Allow direct remote loads:** Let the browser load configured remote avatar URLs directly and accept the CSP and operator-browser privacy tradeoff.

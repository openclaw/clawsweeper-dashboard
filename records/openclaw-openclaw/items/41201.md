## Summary

Keep open: current main and v2026.6.11 still accept `http(s)` avatar values in CLI/config, but Control UI intentionally rejects remote image rendering, so the broken-avatar report remains a real contract mismatch that needs maintainer product/security direction.

## What This Changes

The issue requests that agent avatars configured via `openclaw agents set-identity --avatar <url/path>` render correctly in Control UI instead of showing broken images.

## Best Possible Solution

Maintainers should choose one Control UI avatar contract: either a controlled same-origin remote-avatar proxy/cache, or an explicit local/data-only Control UI policy with aligned CLI/docs/validation and clear diagnostics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Control UI support remote `http(s)` avatars, or should remote avatar inputs remain blocked and be documented/validated as unsupported for Control UI rendering?

Rationale: The remaining fix changes browser network-fetch behavior, CSP, privacy expectations, and the public avatar configuration contract, so automation should not choose the policy silently.

Likely owner: Peter Steinberger

Owner reason: This is the strongest history signal for the avatar route, resolver, and security-hardening decisions touched by either option.

Owner confidence: high

Options:

- **Keep Local/Data-Only Control UI Avatars (recommended):** Preserve the current CSP posture and update CLI/docs/validation/UI diagnostics so remote avatars are not presented as renderable in Control UI.
- **Build Same-Origin Remote-Avatar Proxy:** Support remote avatars through a gateway-owned proxy/cache with explicit MIME, size, auth, caching, privacy, and failure-feedback behavior.
- **Allow Direct Remote Image Fetches:** Let the browser load arbitrary remote avatar URLs directly, accepting the CSP and operator-browser privacy tradeoff.

Yes, at source level: configure an `http(s)` avatar, the gateway resolves it as remote metadata, and the Control UI renderability gate rejects that URL and clears the avatar. I did not run a live Railway/browser reproduction.

Unclear: the report is valid, but the best fix depends on a maintainer security/product choice between remote-avatar support and explicitly local/data-only Control UI behavior.

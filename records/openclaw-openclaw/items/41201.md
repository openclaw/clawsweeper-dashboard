## Summary

Keep open: local workspace avatars are now mostly covered by same-origin authenticated serving, but remote avatar values are still accepted by identity/config surfaces and then intentionally blocked by Control UI rendering/CSP, so the remaining issue is a real product/security contract mismatch.

## What This Changes

The issue requests that Control UI display avatars configured through `openclaw agents set-identity --avatar`, including remote URLs and local workspace paths, instead of showing broken images.

## Best Possible Solution

Maintainers should choose one explicit Control UI avatar contract: either keep local/data/same-origin avatars and add clear validation/diagnostics for remote values, or implement remote avatar support through a gateway-owned same-origin proxy/cache with strict size, MIME, redirect, privacy, and auth controls.

Options:

- **Keep CSP and diagnose remote avatars (recommended):** Preserve local/data/blob-only rendering and update CLI/config/docs/UI feedback so users know remote avatars do not render in Control UI.
- **Proxy remote avatars through Gateway:** Support remote avatars only by fetching and bounding them server-side, then exposing same-origin or data/blob URLs to the browser.
- **Allow direct remote image loads:** Relax `img-src` to let the browser fetch remote avatar URLs, accepting the weaker CSP and operator privacy tradeoff.

Yes from source inspection: configure an `http(s)` avatar and the resolver/metadata path still treats it as remote, while the frontend render gate and CSP allow only same-origin, data, or blob avatar URLs. I did not run a live browser/Railway reproduction during this read-only cleanup review.

## Solution Assessment

Unclear until maintainers choose the product/security boundary. The safest maintainable path appears to be keeping the tight CSP and adding explicit diagnostics, unless maintainers want a bounded gateway proxy for remote avatars.

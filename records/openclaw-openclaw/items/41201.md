## Label Justifications

- `P2`: Broken or inconsistent Control UI avatar display is a visible regression with limited blast radius, not a core runtime outage.
- `impact:security`: The remaining decision affects CSP, authenticated avatar routes, local workspace file serving, and whether operator browsers may fetch externally hosted images.
- `impact:ux-friction`: Users can configure documented avatar values that Control UI will not render, producing broken-image behavior and unclear diagnostics.

## Summary

Keep open: current main has improved local/data avatar handling, but the central remote http(s) avatar case is still a contract mismatch because CLI/config accept remote avatar values while Control UI blocks remote image rendering for CSP/privacy reasons.

## What This Changes

Fix broken Control UI agent avatar rendering after `openclaw agents set-identity --avatar`, especially for remote http(s) URLs and workspace-relative avatar paths.

## Best Possible Solution

Choose one avatar contract: either support remote avatars through a controlled same-origin proxy/cache with explicit CSP, privacy, MIME, size, auth, caching, and diagnostics, or make Control UI local/data-only by tightening CLI/config/docs and UI feedback.

## Reproduction Assessment

Yes, at source level: configure an http(s) avatar, the gateway can resolve remote metadata, and the Control UI renderability gate rejects the remote URL and clears the avatar. I did not run a live Railway/browser reproduction.

## Solution Assessment

No automatic small fix is best yet. The maintainable fix needs a maintainer security/product choice between controlled remote-avatar support and explicitly local/data-only Control UI behavior.

## Summary

Keep open: current main and v2026.6.11 still accept `http(s)` avatar values through CLI/config, while Control UI intentionally blocks remote image rendering for CSP/privacy reasons, so the issue remains a real contract mismatch that needs maintainer direction.

## What This Changes

The issue reports that Control UI agent avatars configured via `openclaw agents set-identity --avatar` render as broken images for remote URLs and local workspace paths.

## Best Possible Solution

Resolve the avatar contract deliberately: either add bounded same-origin remote-avatar proxying, or make Control UI local/data-only support explicit across CLI help, config validation/docs, UI diagnostics, and tests.

## Maintainer Decision

Kind: product_direction

Question: Should Control UI support remote `http(s)` avatars accepted by `set-identity`, or should remote avatar inputs remain blocked and be documented/validated as unsupported for Control UI rendering?

Rationale: The remaining fix changes CSP, privacy expectations, browser network-fetch behavior, and the public CLI/config avatar contract, so automation should not choose the policy silently.

Likely owner: steipete

Owner reason: This handle is the strongest history signal for the avatar route, resolver, and security-hardening decisions touched by either option.

Owner confidence: high

Options:

- **Keep local/data-only Control UI avatars (recommended):** Preserve the current CSP posture and update CLI/docs/validation/UI diagnostics so remote avatars are not presented as renderable in Control UI.
- **Build a same-origin remote-avatar proxy:** Support remote avatars through a gateway-owned proxy/cache with explicit MIME, size, auth, caching, privacy, and failure-feedback behavior.
- **Allow direct remote image fetches:** Let the browser load arbitrary remote avatar URLs directly, accepting the CSP and operator-browser privacy tradeoff.

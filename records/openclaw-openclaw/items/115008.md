## Summary

Keep this issue open. The supplied reproduction shows a real diagnostic gap around intentionally fail-closed SQLite schema protection: two builds can report the same release-style version while supporting different schemas, so the error does not identify the stale executable. The `maintainer` label also requires explicit human handling rather than automated cleanup.

## What This Changes

Make newer-schema errors identify the actual stale OpenClaw build and its supported versus observed schema versions instead of attributing the condition to a user downgrade.

## System Context

OpenClaw’s shared state database is opened by the runtime and by maintenance commands such as `doctor --fix`. A schema-version gate compares the database against the executing build’s supported schema and refuses unsafe downgrades before any state repair can run.

## Architecture Diagram

flowchart LR
  A[Installed OpenClaw build] --> B[State database]
  B --> C[Schema version check]
  A --> C
  C -->|database is newer| D[Fail-closed diagnostic]
  D --> E[Operator chooses compatible build or state directory]
  E --> F[Doctor repair path]

## Best Possible Solution

Preserve the fail-closed schema gate, but make its diagnostic name the executing build’s actionable identity and schema ceiling, state the database schema found, and direct the operator to the compatible installation or separate state directory without asserting an unobserved downgrade.

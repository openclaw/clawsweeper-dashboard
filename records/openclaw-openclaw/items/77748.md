## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.91

Full review comments:

- **[P1] Make WhatsApp history opt in before advertising it:** `extensions/whatsapp/src/channel-actions.ts:83-84`
  - body: `createActionGate` defaults missing action keys to enabled, and this PR adds `history` as an optional WhatsApp action. Existing configs would advertise recent-history access to agents unless users explicitly disable it, so this needs an explicit opt-in/default-false policy before exposure.
  - confidence: 0.94
- **[P2] Correlate history replies with Baileys request ids:** `extensions/whatsapp/src/inbound/monitor.ts:679-701`
  - body: Baileys `fetchMessageHistory` returns a request id and `messaging-history.set` carries `peerDataRequestSessionId`, but this code stores one pending request per chat JID. Concurrent requests or unrelated sync chunks for the same chat can resolve the wrong caller; key pending history by the returned request id and match the event id before resolving.
  - confidence: 0.9
- **[P2] Use the canonical OpenAI provider in the helper:** `scripts/docker/openai-codex-auth.sh:8`
  - body: Current main treats `openai-codex` as legacy migration input, while new ChatGPT/Codex OAuth belongs under `openai`. A new Docker helper should not create fresh legacy-profile or auth-order state; route through `--provider openai` and the current method flag needed for the intended OAuth flow.
  - confidence: 0.91
- **[P2] Prove or redesign the Docker OAuth callback path:** `docker-compose.yml:32`
  - body: Codex binds the OAuth callback listener to `127.0.0.1` and uses a localhost redirect with a 1457 fallback, so publishing host port 1455 alone is not proven to make a host browser reach the container listener. Add redacted Docker proof for the callback path or document/use the existing manual/device flow instead.
  - confidence: 0.83

## Label Justifications

- `P2`: This is a normal-priority multi-agent routing improvement with real workflow impact but no urgent shipped regression.
- `impact:message-loss`: Without content-based routing, shared-chat messages can be handled by the default or statically bound agent instead of the intended specialist agent.
- `impact:session-state`: Wrong-agent routing can attach conversation context to the wrong agent or session in multi-agent setups.

## Summary

Keep open: current main and v2026.6.11 still only support static binding selectors, and the related pre-routing hook work is an open partial API path rather than a merged replacement for binding-level content matching or `stripMatch`.

## What This Changes

Requests an optional binding content matcher, with regex or prefix matching and optional `stripMatch`, so messages in one channel or group can route to different agents by text pattern.

## Best Possible Solution

Choose one maintainer-approved routing surface: a validated binding content matcher with deterministic precedence, cache, and body-rewrite semantics, or a documented plugin hook path that explicitly replaces this config request.

## Reproduction Assessment

Yes, by source inspection. Adding `match.content` would be rejected by the strict binding schema, and the route resolver has no message text input or stripped-body output.

## Solution Assessment

Unclear until maintainers choose the API shape. A binding matcher is plausible, but the adjacent pre-routing plugin-hook design may be the cleaner long-term owner for content-driven routing.

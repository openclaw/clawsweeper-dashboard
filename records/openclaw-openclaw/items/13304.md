## Label Justifications

- `P2`: This is a normal-priority routing/config feature with real multi-agent workflow impact but no urgent shipped regression.
- `impact:message-loss`: Without content-sensitive routing, shared-chat messages can be handled by the default or statically bound agent instead of the intended specialist agent.
- `impact:session-state`: Routing content to the wrong agent can attach conversation context to the wrong agent/session in multi-agent setups.

## Summary

Keep open: current main and v2026.6.11 still lack binding-level content matching, message-text-aware route resolution, and `stripMatch`; the open pre-routing hook work overlaps but does not replace the requested declarative binding API.

## What This Changes

Request content or prefix/regex matchers in agent bindings so inbound messages can route to different agents by message text, optionally stripping the matched prefix before dispatch.

## Best Possible Solution

Define one maintainer-approved routing surface: either a validated binding content matcher with deterministic precedence, cache, safety, and body-rewrite semantics, or a documented plugin hook path that explicitly supersedes this config request.

## Maintainer Decision

Kind: product_direction

Question: Should OpenClaw add a declarative `bindings.match.content` routing contract, or should content-driven routing be owned by a pre-routing plugin hook instead?

Rationale: Both paths affect config/API surface, route precedence, message delivery, session state, and regex/security behavior; the current code does not make that product/API choice for automation.

Owner confidence: high

Options:

- **Resolve API Direction First (recommended):** Keep this issue open while maintainers choose whether declarative binding config or a plugin hook is the canonical routing surface before implementation.
- **Approve Binding Matcher:** Add validated `match.content` config with explicit precedence, safe matching rules, cache behavior, docs, generated schema updates, and `stripMatch` semantics.
- **Supersede With Plugin Hook:** Close or narrow this issue only after a reviewed pre-routing hook lands and documentation explains how it replaces binding-level content routing.

## Reproduction Assessment

Yes, source-level: current main rejects `match.content` through the strict binding schema, `resolveAgentRoute` has no message-text input or stripped-body output, and representative channel callers pass only static metadata. This is a missing feature/API surface rather than a broken existing behavior contract.

## Solution Assessment

Unclear until maintainers choose the API shape. A declarative binding matcher fits the reported workflow, but the adjacent pre-routing plugin-hook design may be the better long-term owner for content-driven routing.

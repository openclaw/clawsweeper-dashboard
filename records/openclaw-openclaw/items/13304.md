## Label Justifications

- `P2`: This is a normal-priority routing/config feature with real multi-agent workflow impact but no urgent shipped regression.
- `impact:message-loss`: Without content-sensitive routing, shared-chat messages can be handled by the default or statically bound agent instead of the intended specialist agent.
- `impact:session-state`: Routing content to the wrong agent can attach conversation context to the wrong agent or session in multi-agent setups.

## Summary

Keep open: current main and the latest release still only support static binding selectors, and the related pre-routing hook and mention-routing items do not implement declarative `bindings[].match.content` plus `stripMatch` behavior.

## What This Changes

Request to add a declarative binding content matcher, with regex or prefix matching and optional `stripMatch`, so inbound message text can choose the target agent.

## Best Possible Solution

Choose one maintainer-approved content-routing surface: either a validated binding content matcher with deterministic precedence, cache, safety, docs, and body-rewrite semantics, or a documented plugin hook path that explicitly supersedes the config request.

Yes, source-level: current main rejects `match.content` through strict binding schema, `resolveAgentRoute` has no message-text input or stripped-body output, and representative channel callers pass only static metadata. This is a missing feature/API surface rather than a broken existing behavior contract.

## Solution Assessment

Unclear until maintainers choose the API shape. A declarative binding matcher fits the reported workflow, but the adjacent pre-routing plugin-hook design may be the better long-term owner for content-driven routing.

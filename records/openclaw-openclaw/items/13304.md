## Label Justifications

- `P2`: This is a normal-priority multi-agent routing improvement with real workflow impact but no urgent shipped regression.
- `impact:message-loss`: Without content-based routing, messages in shared chats can be handled by the default or statically bound agent instead of the intended specialist agent.
- `impact:session-state`: Routing content to the wrong agent can attach the turn and follow-up context to the wrong agent/session in multi-agent setups.

## Summary

Keep open: current main still has only static binding selectors, strict config validation still rejects a `match.content` object, and the related pre-routing hook work is only a partial overlapping path rather than a merged replacement for declarative binding content matching and `stripMatch`.

## What This Changes

Request to add `bindings[].match.content` with prefix or regex matching and optional `stripMatch` so messages in a shared channel can route directly to specialist agents.

## Best Possible Solution

Define one maintainer-approved routing surface: either a validated binding content matcher with deterministic precedence/cache/body-rewrite semantics, or a documented plugin hook path that explicitly replaces this config request.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence current-main reproduction: adding `match.content` would be rejected by the strict binding schema, and the resolver has no message text input or stripped-body output.

## Solution Assessment

Unclear until maintainers choose the API shape. A binding matcher is plausible, but the adjacent pre-routing plugin-hook design may be the better long-term owner for content-driven routing.

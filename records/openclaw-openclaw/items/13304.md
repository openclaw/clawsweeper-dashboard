## Label Justifications

- `P2`: This is a normal-priority routing enhancement with real multi-agent workflow impact but it needs product/API direction before implementation.
- `impact:message-loss`: Without content-based routing, shared-chat messages can be handled by the default or statically bound agent instead of the intended specialist agent.
- `impact:session-state`: Routing content to the wrong agent can attach conversation context to the wrong agent/session in multi-agent setups.

## Summary

Keep open: current main still rejects the requested binding-level content matcher, resolves routes from static metadata only, and has no contract for stripping matched text before the agent sees the message. The adjacent pre-routing hook work is useful context, but it is open/unmerged and does not settle the requested declarative binding API.

## What This Changes

Request to add optional `bindings[].match.content` pattern matching and `stripMatch` support so inbound messages can route to different agents by message text.

## Best Possible Solution

Define one maintainer-approved routing surface: either a validated binding content matcher with deterministic precedence/cache/body-rewrite semantics, or a documented plugin hook path that explicitly replaces this config request.

## Reproduction Assessment

Yes, from source inspection: current main rejects `match.content` through the strict binding schema, and `resolveAgentRoute` has no message text input or stripped-body output. This is a missing feature rather than a failing existing contract.

## Solution Assessment

Unclear until maintainers choose the API shape. A binding matcher is plausible, but the adjacent pre-routing plugin-hook design may be the better long-term owner for content-driven routing.

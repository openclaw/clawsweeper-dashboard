## Label Justifications

- `P2`: This is a normal-priority multi-agent routing improvement with concrete workflow impact but no urgent shipped regression.
- `impact:message-loss`: Without content-based routing, shared-chat messages can be handled by the default or statically bound agent instead of the intended specialist agent.
- `impact:session-state`: Routing content to the wrong agent can attach conversation context to the wrong agent/session in multi-agent setups.

## Summary

Keep open: current main and the latest release still do not support binding-level message-content matching or `stripMatch`, and the open pre-routing hook work is only a partial alternate path rather than a merged replacement for declarative binding config.

## What This Changes

The issue requests a new `bindings[].match.content` matcher, with regex or prefix matching and optional prefix stripping, so shared-chat messages can route directly to different agents by message text.

## Best Possible Solution

Choose one maintainer-approved routing surface: either a validated binding content matcher with deterministic precedence, cache, regex-safety, and body-rewrite semantics, or a documented plugin hook path that explicitly replaces this config request.

## Reproduction Assessment

Yes, by source inspection: adding `match.content` is rejected by the strict binding schema, and the resolver has no message text input or stripped-body output. This is a missing feature rather than a broken existing contract.

## Solution Assessment

Unclear until maintainers choose the API shape. A binding matcher is plausible, but the adjacent pre-routing plugin-hook design may be the better long-term owner for content-driven routing.

## Label Justifications

- `P2`: This is a normal-priority routing/config feature with real multi-agent workflow impact but no urgent shipped regression.
- `impact:session-state`: Routing by the wrong static binding can attach shared-chat context to the wrong agent or session in multi-agent setups.
- `impact:message-loss`: Messages intended for a specialist agent can be handled by the default or statically bound agent instead.

## Summary

Keep open: current main and the latest release still support only static binding selectors, while the related pre-routing hook work is open and does not replace the requested declarative content matcher plus `stripMatch` behavior.

## What This Changes

Requests an optional binding content matcher with regex or prefix matching and optional prefix stripping so shared-chat messages can route to different agents by message text.

## Best Possible Solution

Define one maintainer-approved content-routing surface: either a validated binding content matcher with deterministic precedence, cache, safety, docs, and body-rewrite semantics, or a documented plugin hook path that explicitly supersedes this config request.

## Maintainer Decision

Question: Should OpenClaw add declarative `bindings[].match.content` routing with `stripMatch`, or should content-driven routing be owned by a pre-routing plugin hook instead?

Rationale: Both directions add public routing/API surface and affect session ownership, message delivery, route caching, regex safety, and plugin trust boundaries; current source, docs, and related open PRs do not settle that product choice.

Owner confidence: high

Options:

- **Resolve API Direction First (recommended):** Keep this issue open while maintainers choose whether declarative binding config or a plugin hook is the canonical content-routing surface.
- **Approve Binding Matcher:** Add validated `match.content` config with explicit precedence, safe matching rules, cache behavior, docs, generated schema updates, and `stripMatch` semantics.
- **Supersede With Plugin Hook:** Close or narrow this issue only after a reviewed pre-routing hook lands and documentation explains how plugins replace binding-level content routing.

## Reproduction Assessment

Yes, source-level: current main rejects `match.content` through strict binding schema, `resolveAgentRoute` has no message-text input or stripped-body output, and representative channel callers pass only static metadata. This is a missing feature/API surface rather than a broken existing behavior contract.

## Solution Assessment

Unclear until maintainers choose the API shape. A declarative binding matcher fits the reported workflow, but the adjacent pre-routing plugin-hook design may be the better long-term owner for content-driven routing.

## Label Justifications

- `P2`: This is a normal-priority routing/config feature with real multi-agent workflow impact but no urgent shipped regression.
- `impact:message-loss`: Without content-sensitive routing, shared-chat messages can be handled by the default or statically bound agent instead of the intended specialist agent.
- `impact:session-state`: Routing content to the wrong agent can attach conversation context to the wrong agent/session in multi-agent setups.

## Summary

Keep open: current main and v2026.6.11 still lack binding-level content matching and `stripMatch`, while the related pre-routing hook work is overlapping, unmerged, and not a replacement for this declarative binding API request.

## What This Changes

Requested a binding `content` matcher so inbound messages can route to different agents by prefix or regex and optionally strip the matched text before dispatch.

## Best Possible Solution

Define one maintainer-approved routing surface: either a validated binding content matcher with deterministic precedence, cache, safety, and body-rewrite semantics, or a documented plugin hook path that explicitly replaces this config request.

## Reproduction Assessment

Yes, from source inspection: current main rejects `match.content` through the strict binding schema, `resolveAgentRoute` has no message-text input or stripped-body output, and representative channel callers pass only static metadata. This is a missing feature/API surface rather than broken existing behavior.

## Solution Assessment

Unclear until maintainers choose the API shape. A declarative binding matcher is plausible for the reported workflow, but the adjacent pre-routing plugin-hook design may be the better long-term owner for content-driven routing.

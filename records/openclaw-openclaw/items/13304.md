## Label Justifications

- `P2`: This is a useful multi-agent routing improvement with bounded but cross-cutting design impact, not an urgent regression.
- `impact:message-loss`: The requested selector determines which agent receives an inbound message, so an incorrect contract can suppress or misroute delivery.
- `impact:session-state`: Choosing a different agent changes the owning session and context, making routing semantics directly relevant to session association.

## Summary

Current main still lacks content-aware binding selection or agent-facing body rewriting, while the open generic pre-routing hook work only partially overlaps and has not landed. Keep this issue open for a maintainer product decision on whether content routing belongs in core bindings or behind a plugin extension seam.

## What This Changes

Add regex or prefix content matchers to agent bindings, with optional removal of the matched text before agent dispatch.

## Best Possible Solution

Provide a narrowly specified pre-route plugin API that can atomically choose the target agent/session and return the agent-facing normalized body, then implement regex or prefix routing as an external plugin unless maintainers explicitly choose a small safe core matcher.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should content-based routing become a built-in bindings config contract, or should core expose a generic pre-route route/body override for a plugin to implement it?

Rationale: Current plugin hooks can inspect content but cannot reroute or rewrite the inbound agent body, while adding regex and stripping semantics directly to bindings creates public config, precedence, performance, and cross-channel commitments.

Likely owner: steipete

Owner reason: The existing issue discussion and routing/config history make steipete the strongest available product-routing decision owner.

Owner confidence: high

Options:

- **Add generic plugin seam (recommended):** Extend the pre-route plugin contract with validated agent/session selection and agent-facing body replacement, then publish content routing as a plugin.
- **Add bounded core matcher:** Add a deliberately limited prefix or safe-regex matcher to bindings with explicit precedence, cache bypass, normalization, and stripping contracts.
- **Keep dispatcher pattern:** Decline new routing surface and continue using a default agent or custom middleware as the dispatcher.

## Reproduction Assessment

Yes at source level: current binding types, documented config, and dispatch hook results provide no path for content-based agent selection or matched-prefix stripping. This verifies a capability gap rather than a broken existing contract.

## Solution Assessment

No, the proposed direct regex field is not yet proven to be the best boundary. A generic pre-route plugin seam with atomic route and agent-body override better matches the plugin-first architecture unless maintainers intentionally sponsor a bounded core matcher.

## Label Justifications

- `P2`: This is a normal-priority routing/config feature with real multi-agent workflow impact but no urgent shipped regression.
- `impact:session-state`: Content-based routing would decide which agent/session owns an inbound group message in multi-agent setups.
- `impact:message-loss`: Without this routing surface, shared-chat messages can be handled by the default or statically bound agent instead of the intended specialist agent.

## Summary

Keep open: current main and v2026.6.11 still only support static binding selectors, and the open pre-routing hook work is a partial overlap rather than a merged replacement for declarative binding content matchers and `stripMatch`.

## What This Changes

The issue requests optional content pattern matching in `bindings[]` so inbound messages can route directly to different agents based on prefixes or regexes.

## Best Possible Solution

Define one maintainer-approved routing surface: a validated binding content matcher with deterministic precedence, cache, safety, and body-rewrite semantics, or a documented plugin hook path that explicitly replaces this config request.

## Reproduction Assessment

Yes, at source level: current main rejects `match.content` through the strict binding schema, and `resolveAgentRoute` has no message text input or stripped-body output. This is a missing feature/API surface rather than a failing existing behavior contract.

## Solution Assessment

Unclear until maintainers choose the API shape. A declarative binding matcher is plausible for simple prefixes, but the adjacent pre-routing plugin-hook design may be the better long-term owner for arbitrary content-driven routing.

## Risks / Open Questions

- The requested matcher needs maintainer decisions on precedence against static bindings, native mention/reply routing, focus or thread bindings, ACP bindings, and plugin-owned pre-routing hooks.
- `stripMatch` needs an explicit contract for whether it rewrites only the agent-facing body or also command text, raw body, reply context, grouped history context, and channel metadata.
- Regex or prefix matching across channel inputs needs normalization, size limits, and safe-regex rules to avoid accidentally broad or expensive routing.
- Content-sensitive routing conflicts with the current static route cache unless the cache key includes normalized content, content rules bypass caching, or route caching is split by matcher type.

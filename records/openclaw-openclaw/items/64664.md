## Summary

Keep open: current main and the latest release still keep in-flight exec/plugin approval requests in fresh process-local managers, so a gateway restart drops pending IDs. The Telegram infinite-retry symptom and part of the stale-callback UX have been handled, but the remaining restart-persistence versus explicit fail-closed invalidation policy is still a security/product decision.

## What This Changes

The issue asks OpenClaw to handle approval callbacks after gateway restart by either preserving pending approvals or giving clearer stale-approval recovery, especially for Telegram approval buttons.

## Best Possible Solution

Choose and document one approval restart policy: either fail closed on restart with consistent channel-visible recovery and button invalidation, or add SQLite-backed pending approvals with expiry, requester/reviewer binding, replay protection, and restart tests.

Options:

- **Fail closed with explicit recovery (recommended):** Keep restart invalidation as the default, but make all channel surfaces clearly consume or replace stale approval UI and tell the user to re-request the action.
- **Persist pending approvals securely:** Store pending approvals in SQLite with strict expiry, requester/reviewer binding, replay protection, and restart/live proof before accepting stale buttons after restart.
- **Split by approval kind:** Persist only lower-risk plugin approvals while continuing to invalidate exec approvals on restart, with docs/tests explaining the security boundary.

Yes, source inspection gives a high-confidence reproduction path: create an approval, restart the gateway so fresh approval managers are constructed, then resolve the old ID and hit the missing/expired approval path. I did not run a live restart test in this read-only review.

## Solution Assessment

Unclear until maintainers choose the policy: current main has a partial UX/retry mitigation, but durable cross-restart approvals are not automatically the best fix because they change approval security semantics. The safer default appears to be fail-closed restart invalidation with clearer channel recovery unless maintainers explicitly sponsor persistence.

## Label Justifications

- `P0`: Applying a malformed update can replace user-authored skill content without a guaranteed user-accessible recovery path.
- `impact:data-loss`: The report concerns destructive replacement of an existing SKILL.md with unrelated proposal text.

## Summary

Current main still allows update proposals to carry arbitrary body text through scanning and into the active SKILL.md; rollback metadata limits irreversibility but does not prevent the destructive replacement, and the paired prompt issue does not provide an apply-time safety boundary.

## What This Changes

Prevent Skill Workshop apply from replacing an existing SKILL.md with plan or other non-skill proposal text.

## Best Possible Solution

Keep the documented full-content proposal contract, but harden generation prompts, validate the exact would-be active SKILL.md centrally, show a bounded before/after diff before destructive updates, and expose a supported restore path for the recorded previous content.

Yes at source level: create an update proposal whose body is plan text and apply it; current main carries that body through proposal scanning and writes it as the active SKILL.md. A live failing run was not executed during this read-only review.

## Solution Assessment

Partly: strengthening the generation prompt in https://github.com/openclaw/openclaw/issues/107708 is appropriate but insufficient by itself; the best fix also places a central pre-write safety check and visible diff at the destructive apply boundary.

## Review Findings

Full review comments:

- **[P2] Preserve numeric record keys when formatting issue paths:** `src/config/issue-location.ts:553-554`
  - body: `parseConfigIssuePath(..., { numericDotSegments: true })` converts every numeric dotted segment into an array index. Config paths can traverse records keyed by numeric strings, so a path such as `models.providers.123.api` is reformatted and traversed as an array path even when `123` is an object key. Carry the original typed Zod segments or resolve numeric segments against the actual container before adding brackets.
  - confidence: 0.97
- **[P2] Attribute included values to their owning source file:** `src/cli/config-cli.ts:2636-2639`
  - body: This decorator receives only the root snapshot's `raw`, `parsed`, and path, while `ConfigFileSnapshot.sourceConfig` is the post-`$include` value that validation covers. An error under an included value therefore cannot be located in the root text or correctly labeled with the included filename. Carry per-source provenance/raw text through include resolution or omit a location when ownership is unavailable.
  - confidence: 0.99
- **[P1] Use authoritative sensitivity metadata before showing values:** `src/config/issue-location.ts:484-498`
  - body: The fixed suffix regex is narrower than the repository's canonical sensitivity rules and schema hints, including wildcard environment/header fields and plugin-declared sensitive fields. Invalid scalar values at those paths can be appended to stderr. Gate received-value output through the same sensitivity classifier/schema metadata used by config redaction, defaulting to omission when sensitivity is unknown.
  - confidence: 0.99

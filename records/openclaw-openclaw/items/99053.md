Full review comments:

- **[P1] Keep the fallback reachable after media loading:** `extensions/discord/src/send.outbound.ts:61`
  - body: Lowering `DEFAULT_DISCORD_MEDIA_MAX_MB` to 10 means the default path calls `loadWebMedia(..., { maxBytes: 10MB })`. For non-image media like the reported MP3, `loadWebMedia` throws when the buffer exceeds that cap before `sendDiscordMedia` reaches the new text fallback, so the real 10.7MB case still fails instead of sending text-only. The new test mocks an 11MB return despite the 10MB cap, so it misses this path.
  - confidence: 0.95
- **[P1] Respect configured Discord media limits:** `extensions/discord/src/send.shared.ts:399`
  - body: This hard-coded 10MB check ignores `channels.discord.mediaMaxMb`, even though the docs and existing tests preserve higher configured Discord media caps. Existing setups that intentionally set a higher cap for targets that accept larger uploads would now have attachments stripped before Discord is tried. Use a separate effective Discord upload decision that preserves explicit config semantics or update the config contract deliberately.
  - confidence: 0.86

  - body: The lint job is failing on the newly added nested template expressions in the fallback text. Replace the unnecessary `${`...`}` wrappers so `check-lint` can pass after the behavior fix.

## Summary

Keep this PR open for revision: the pre-read hardening is useful, but the patch introduces an undocumented file-only 1 MiB compatibility limit, leaves the equivalent stdin path unlimited, and does not provide convincing real CLI behavior proof.

## What This Changes

The PR adds a pre-read regular-file and 1 MiB size check for `config patch --file`, plus oversized and normal-input tests.

## Best Possible Solution

Use one shared bounded UTF-8 input path for both `--file` and `--stdin`, with a documented and maintainer-approved config-patch byte limit, race-resistant file handling, and boundary tests that prove oversized content is stopped before unbounded buffering.

Rationale: Current behavior has no documented 1 MiB ceiling, so selecting that threshold and applying it to only one public input mode is a product and upgrade-compatibility choice rather than a mechanical bug fix.

- **Keep file-only limit:** Intentionally accept and document that file patches above 1 MiB fail while equivalent stdin patches remain accepted.
- **Avoid a new cap:** Pause this PR until a resource-bound solution can be designed without changing the accepted config-patch size contract.

## Reproduction Assessment

Yes at source level: the current file path reads the complete patch with `readFileSync` before parsing, so an arbitrarily large local file is buffered; no live current-main reproduction was run in this read-only review.

## Solution Assessment

No. A pre-read bound is appropriate, but an arbitrary file-only threshold is not the narrowest maintainable fix; the limit and bounded reader should be shared with stdin and treated as a public CLI contract.

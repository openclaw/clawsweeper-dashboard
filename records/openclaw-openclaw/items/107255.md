## Label Justifications

- `P2`: A shipped optional plugin UI workflow is broken for token-authenticated gateways, but the failure is limited to external Control UI tabs rather than the core runtime.
- `impact:security`: The issue concerns securely transferring bounded authenticated authority into a sandboxed plugin iframe without exposing gateway credentials or weakening direct route authentication.

## Summary

Current main still renders the documented external plugin tab as a plain iframe, so gateway-authenticated routes can return 401 under token auth; keep this issue open while the focused closing PR is reviewed.

## What This Changes

Fix external Control UI plugin tabs so an already authenticated dashboard can securely render gateway-authenticated plugin HTTP routes without exposing the shared gateway credential.

## Best Possible Solution

Review and land a narrow secure fix through https://github.com/openclaw/openclaw/pull/107323 that grants only short-lived, path-confined plugin-route access from an authenticated Control UI, preserves direct unauthenticated 401 responses, and proves token, password, Tailscale-served, cross-plugin, and expiry behavior.

Yes from source inspection: current main places the descriptor path directly in the iframe src while gateway-authenticated plugin HTTP routes require HTTP authentication, yielding the reported unauthenticated request path. ## Solution Assessment

The proposed gateway-side short-lived HttpOnly session is a plausible narrow fix and preferable to URL credentials or public routes, but it needs security and architecture comparison against the broader launch/session design before landing.

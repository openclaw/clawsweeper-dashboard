## Label Justifications

- `merge-risk: 🚨 compatibility`: Existing operators may rely on the documented HTTP 429 response, Twilio error reporting, or a configured fallback URL for rejected callbacks.

## Summary

Keep this PR open but do not merge it as written: it turns a documented fail-closed rejection into a successful Twilio acknowledgment while still discarding the callback, suppressing failure and fallback signals without solving message loss.

## What This Changes

Changes signature-validated Twilio SMS callbacks above the dispatch quota from HTTP 429 to HTTP 200 with empty TwiML, logs the dropped message SID, skips dispatch and replay-cache insertion, and adds focused tests and documentation.

## Best Possible Solution

Acknowledge a callback only after dispatch or durable bounded acceptance; otherwise preserve a non-2xx failure that keeps Twilio fallback and operator-visible failure semantics available.

## Maintainer Decision

Kind: product_direction

Question: Should the SMS plugin report HTTP 200 for a signature-validated callback that it intentionally discards, or reserve success for callbacks that were dispatched or durably accepted?

Rationale: Both choices are implementable, but they define externally visible delivery, fallback, and monitoring semantics that automation cannot choose safely.

Likely owner: pgondhi987

Owner reason: The current accepted-callback quota and its HTTP response contract originate from their merged SMS webhook work.

Owner confidence: medium

Options:

- **Preserve acceptance semantics (recommended):** Keep a non-2xx response for discarded callbacks and pursue durable bounded queuing separately if lossless burst handling is required.
- **Adopt ack-and-drop explicitly:** Accept HTTP 200 for discarded callbacks, document that fallback and failure monitoring are bypassed, and require live Twilio proof plus dedicated drop metrics.

## Reproduction Assessment

Yes at source level: the thirty-first valid signed callback for one quota key receives HTTP 429 and is not dispatched on current main, and the PR tests plus an independent A/B report exercise that boundary. An exact live Twilio run was not supplied.

## Solution Assessment

No. Returning success for an event that was neither dispatched nor durably accepted hides the same message loss from Twilio; durable acceptance or preserved failure/fallback semantics is safer.

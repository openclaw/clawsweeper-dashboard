## What This Changes

Changes signature-validated Twilio SMS callbacks above the dispatch quota from HTTP 429 to HTTP 200 with empty TwiML, logs the dropped message SID, skips dispatch and replay-cache insertion, and adds focused tests and documentation.

## Best Possible Solution

Return 2xx only after a callback is durably accepted for processing; otherwise retain an observable non-2xx rejection so Twilio fallback, retry, and monitoring can react, with exact-head Twilio proof of the chosen behavior.

Question: Should a validated SMS callback above OpenClaw's dispatch quota remain an observable failure eligible for Twilio fallback or retry, or may OpenClaw return 200 while intentionally discarding it?

Rationale: Current documentation and provider semantics treat non-2xx as the recovery signal, while this PR redefines 200 as successful receipt without processing; automation cannot choose that message-delivery contract.

Likely owner: steipete

Owner reason: The original SMS channel and webhook contract appear to originate from their merged feature work.

Owner confidence: high

Options:

- **Require admission before success (recommended):** Keep HTTP 429 unless the callback is durably queued or otherwise guaranteed eventual processing before returning 2xx.
- **Accept intentional discard:** Return 200 without dispatch only if maintainers explicitly accept irreversible overflow loss and document that fallback and retries will not run.
- **Pause this change:** Leave the existing rejection behavior in place until a bounded durable-overflow design is available.

## Reproduction Assessment

Yes at source level: fill the signed callback quota, submit the next validated callback, and observe HTTP 200 while the dispatch count remains unchanged. This review did not execute a live Twilio request.

## Solution Assessment

No. Acknowledging a callback that was not admitted hides the loss; preserving non-2xx failure semantics or durably queueing before 2xx is safer and consistent with the existing contract.

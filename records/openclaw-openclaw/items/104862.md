## Label Justifications

- `P1`: The item concerns active inbound SMS message loss, and the proposed fix would conceal overload drops as successful webhook deliveries.
- `merge-risk: 🚨 message-delivery`: Merging changes an unaccepted inbound callback from an explicit failure into HTTP success, which can prevent retry or fallback recovery.

## Summary

Keep open: rebasing onto the merged quota hardening resolves the prior pre-validation abuse-budget concern, but the branch still returns success for authenticated callbacks it deliberately discards, leaving the earlier delivery-loss P1 unresolved; exact-head live Twilio proof is also still absent.

## What This Changes

The PR changes the SMS webhook so signature-validated Twilio callbacks above the dispatch quota receive HTTP 200 with empty TwiML, are warning-logged, and are neither dispatched nor replay-cached.

## Best Possible Solution

Only return 2xx after the validated callback has been durably accepted into a bounded queue; until that exists, preserve an explicit non-2xx overload response and document Twilio retry-policy and fallback configuration rather than marking discarded messages successful.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What delivery contract should the SMS webhook use when a signature-validated callback exceeds the accepted-callback quota: reject it for retry/fallback, durably queue it before acknowledging, or deliberately acknowledge and discard it?

Rationale: All three policies have different message-loss, overload, and operator-observability consequences, and current repository behavior does not establish that a callback may be reported successful without being accepted.

Likely owner: pgondhi987

Owner reason: Their merged work most recently defined the quota boundary and makes them the strongest available technical routing candidate, although final product approval still requires repository maintainers.

Owner confidence: medium

Options:

- **Preserve failure semantics (recommended):** Keep HTTP 429 for unaccepted callbacks and document Twilio `rp=4xx` or fallback configuration until OpenClaw has durable admission.
- **Queue before acknowledging:** Add a bounded durable callback queue and return HTTP 200 only after the message has been accepted for later dispatch.
- **Own ack-and-drop:** Explicitly adopt intentional loss under overload with clear documentation, metrics, logs, and maintainer acceptance that Twilio will record success.

## Reproduction Assessment

Yes at the source and A/B-test level: current main returns 429 after the validated-callback quota trips, while this head returns 200 and skips dispatch. A real exact-head Twilio webhook reproduction has not been supplied.

## Solution Assessment

No. Moving quota enforcement after authentication is correct, but acknowledging a callback that was neither dispatched nor durably queued is not the safest maintainable fix; 2xx should follow acceptance, not intentional discard.

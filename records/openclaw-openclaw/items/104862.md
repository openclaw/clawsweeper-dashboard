## Label Justifications

- `P1`: The patch changes an active inbound channel workflow in a way that can hide and finalize message loss during ordinary quota trips.
- `merge-risk: 🚨 message-delivery`: Returning HTTP 200 for a callback that is neither dispatched nor persisted can suppress retry and fallback handling while losing the inbound message.

## Summary

Keep this PR open for an SMS owner decision, but do not merge the current patch: it changes a documented fail-closed rejection into HTTP success while deliberately discarding the validated message, hiding rather than preventing message loss.

## What This Changes

The PR changes SMS webhook overload handling so signature-validated Twilio callbacks above the dispatch quota receive HTTP 200 with empty TwiML, are warning-logged, and are neither dispatched nor replay-cached.

## Best Possible Solution

Return HTTP 200 only after the validated callback has been durably accepted into a bounded plugin-owned queue for later dispatch; until that exists, preserve the documented HTTP 429 rejection and Twilio retry/fallback signal.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When a signature-validated SMS callback exceeds the dispatch quota, should OpenClaw explicitly reject it with HTTP 429, or durably accept it for deferred delivery before returning HTTP 200?

Rationale: HTTP success versus rejection defines the externally visible message-acceptance contract; code inspection cannot decide whether maintainers intend durable backpressure, explicit loss signaling, or intentional acknowledgement-and-drop behavior.

Likely owner: pgondhi987

Owner reason: This is the strongest available routing candidate because their merged work established the current quota and response contract being changed.

Owner confidence: medium

Options:

- **Preserve explicit rejection (recommended):** Keep HTTP 429 and the existing retry/fallback signal until OpenClaw has a durable acceptance path for overloaded callbacks.
- **Add durable overload delivery:** Persist validated callbacks in a bounded plugin-owned SQLite queue, acknowledge only after commit, and drain them with deduplication and recovery coverage.
- **Own acknowledgement-and-drop:** Explicitly adopt HTTP 200 with intentional message loss and update operator documentation and telemetry to make that contract unmistakable.

## Reproduction Assessment

Yes at source level: send more than 30 valid signed callbacks for the same account, route, and client-address key within one minute; current main returns HTTP 429 for the over-quota callback, and Twilio does not retry that status without opt-in retry policy. No live current-main reproduction was performed in this review.

## Solution Assessment

No. Acknowledging a callback without dispatching or durably retaining it is not the safest fix; either preserve explicit rejection or add bounded durable acceptance before returning success.

## Label Justifications

- `P1`: The patch can silently suppress validated inbound SMS callbacks and Twilio failure handling during quota bursts.
- `merge-risk: 🚨 message-delivery`: Returning success while skipping dispatch can make inbound messages permanently disappear without provider redelivery or fallback.
- `merge-risk: 🚨 compatibility`: Existing operators may rely on Twilio error reporting or a configured fallback URL that the new HTTP 200 response prevents from running.

## Summary

Keep open: the patch has a blocking delivery-semantics defect because it reports success for a callback it deliberately discards, suppressing Twilio failure and fallback handling. Exact-head SMS proof is also missing, and the overload admission policy needs explicit owner direction.

## What This Changes

Changes validated Twilio SMS callbacks above the dispatch quota from HTTP 429 rejection to HTTP 200 with empty TwiML while logging and skipping dispatch and replay-cache insertion.

## Best Possible Solution

Keep a non-2xx response until OpenClaw durably accepts the callback; if lossless overload handling is desired, add a bounded durable queue and return HTTP 200 only after successful enqueue, with retry/fallback documentation and focused tests.

Question: Should SMS overload preserve a truthful failure response, or should OpenClaw durably queue validated callbacks before acknowledging them, instead of returning HTTP 200 while discarding them?

Rationale: HTTP success is a provider-level acceptance signal, so changing that signal while dropping the message is a delivery-policy choice automation cannot safely resolve.

Likely owner: pgondhi987

Owner confidence: high

Options:

- **Keep truthful rejection (recommended):** Retain HTTP 429 for callbacks not accepted for processing and leave durable overload handling for a separate bounded design.
- **Queue before acknowledging:** Persist validated callbacks in a bounded queue and return HTTP 200 only after acceptance for later dispatch.
- **Approve acknowledgment-and-drop:** Explicitly accept provider-level success for discarded messages and document the resulting loss and disabled fallback behavior.

## Reproduction Assessment

Yes at source level: fill the 30-callback quota and current main returns HTTP 429 for the next validated callback, while Twilio's documented default does not retry HTTP 4xx. No inspectable exact-head live SMS reproduction was supplied.

## Solution Assessment

No. The patch changes the provider's success signal without accepting the message; truthful rejection or acknowledgment only after durable enqueue is the maintainable solution.

## Label Justifications

- `P2`: The issue affects macOS managed Gateway stability for Volta users after Node upgrades, but the scope is bounded to daemon runtime path selection.
- `impact:crash-loop`: A LaunchAgent pinned to a removed Volta tools/image Node binary can leave the managed gateway unable to start after upgrades.
- `maturity:stable`: The affected macOS Gateway host surface is M4 Stable and includes shell PATH and version-manager drift for the host Gateway.

## Summary

Keep open: current main still only canonicalizes Homebrew Cellar Node paths, so a supported Volta tools/image executable can remain pinned in the generated service command when no supported system Node wins first; the related implementation candidates are not merged and the remaining question is a daemon runtime policy decision.

## What This Changes

Request that macOS gateway LaunchAgent generation prefer the stable Volta shim path over a version-pinned Volta tools/image Node path when Volta is the chosen runtime and no better system Node is available.

## Best Possible Solution

Settle the daemon runtime policy first, then either land a narrow resolver-level Volta tools/image-to-shim fix with focused tests and live launchd proof, or route users to an explicit runtime pin contract instead of changing the default fallback.

## Reproduction Assessment

No live high-confidence reproduction was run in this read-only review. The source path is clear: a supported Volta tools/image `process.execPath` falls through `resolveStableNodePath` unchanged when no supported system Node is selected first.

## Solution Assessment

Unclear. Extending the stable-node resolver is the narrowest code boundary, but maintainers need to accept Volta shim fallback versus the current documented system-Node preference or an explicit runtime-path contract.

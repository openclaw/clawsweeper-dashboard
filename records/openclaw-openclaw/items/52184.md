## Label Justifications

- `P2`: The issue affects macOS gateway LaunchAgent stability for Volta-managed Node installs, but the blast radius is bounded to service runtime path selection.
- `impact:crash-loop`: A LaunchAgent pinned to a removed Volta image Node executable can leave the managed gateway unable to start after Node upgrades.
- `maturity:stable`: The affected macOS Gateway host surface is `macos-gateway-host`, scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and the latest release still leave Volta `tools/image/node/<version>/bin/node` paths unchanged when no supported system Node is selected, and an open cross-repository candidate PR is not merged into OpenClaw main.

## What This Changes

The issue requests preferring a stable Volta shim path over a version-pinned Volta Node path when generating macOS gateway LaunchAgent command arguments.

## Best Possible Solution

Decide the Volta fallback policy, then either land a helper-level Volta `tools/image` normalization with focused tests and live macOS LaunchAgent proof, or document that system Node remains the supported managed-service path.

Options:

- **Support Volta shim fallback (recommended):** Keep the existing system-Node preference, normalize accessible Volta `tools/image` paths to the stable shim, and require focused tests plus live macOS LaunchAgent proof before landing.
- **Require system Node for services:** Reject the Volta shim fallback, document system Node as the supported managed-service runtime, and close the linked implementation attempts as not planned.
- **Defer for live proof:** Keep the issue open until a maintainer or contributor proves a real LaunchAgent install and Volta upgrade/reinstall flow with the shim path.

No live high-confidence reproduction was run in this read-only review. Source inspection gives a clear path: a supported Volta `tools/image` `process.execPath` falls through unchanged when no supported system Node is selected first.

## Solution Assessment

## Label Justifications

- `P2`: The issue affects macOS gateway LaunchAgent stability for Volta-managed Node installs, but the blast radius is bounded to service runtime path selection.
- `impact:crash-loop`: A LaunchAgent pinned to a removed Volta tools/image Node executable can leave the managed gateway unable to start after Node upgrades.
- `maturity:stable`: The affected macOS Gateway host surface is scored M4 Stable, and the Gateway Service Lifecycle category covers LaunchAgent install, restart, and status.

## Summary

Keep open: current main and v2026.6.11 still leave Volta tools/image Node paths unchanged, and the remaining work is a gateway runtime policy decision rather than conservative cleanup.

## What This Changes

The issue requests that macOS gateway LaunchAgent generation prefer a stable Volta shim path over a version-pinned Volta Node image path when Volta is the selected Node manager.

## Best Possible Solution

Decide the Volta fallback policy, then either land a helper-level Volta tools/image normalization with focused tests and live macOS LaunchAgent proof, or document that system/Homebrew Node remains the supported managed-service path.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should macOS gateway service generation treat the Volta shim as an acceptable stable absolute Node path when no supported system/Homebrew Node is available?

Rationale: The code boundary is small, but accepting the shim changes the managed-service runtime policy for version-manager users and conflicts with the current warning-first posture.

Likely owner: steipete

Owner reason: They landed the resolver precedent and authored the current system-Node preference logic, so they are the clearest owner for the policy tradeoff.

Owner confidence: high

Options:

- **Support Volta shim fallback (recommended):** Allow ~/.volta/bin/node as the stable fallback for Volta tools/image Node paths when the shim is executable and no supported system Node is selected.
- **Keep system Node policy:** Reject Volta shim fallback and keep version-manager service runtimes warning-only, with docs pointing users to system/Homebrew Node for managed services.
- **Defer to broader version-manager policy:** Fold this into the wider version-manager service-runtime discussion covering NVM, fnm, asdf, Volta, and configurable Node paths.

## Reproduction Assessment

Yes, source-level with high confidence: a supported Volta tools/image process.execPath is passed through resolveStableNodePath unchanged when no supported system Node is selected first. I did not run a live macOS launchd repro in this read-only review.

## Solution Assessment

Unclear until the policy decision is made. Extending resolveStableNodePath is the narrowest implementation boundary if Volta shim fallback is accepted, but current docs and audit still prefer system Node for managed services.

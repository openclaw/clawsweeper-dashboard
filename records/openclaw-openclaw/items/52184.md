## Label Justifications

- `P2`: The issue affects macOS LaunchAgent runtime path stability for Volta-managed installs, but the blast radius is bounded to service-generation fallback policy.
- `impact:crash-loop`: A LaunchAgent pinned to a removed Volta tools/image Node executable can leave the managed gateway unable to start after Node upgrades.
- `maturity:stable`: The affected macOS Gateway host LaunchAgent lifecycle maps to `macos-gateway-host`, scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and v2026.6.11 still leave Volta tools/image Node paths unchanged, and the issue is paired with an open cross-repository candidate PR plus a maintainer policy decision about version-manager service runtimes.

## What This Changes

Issue requests that macOS gateway LaunchAgent generation prefer a stable Volta shim path over version-pinned Volta Node image paths when Volta is the selected Node manager.

## Best Possible Solution

Decide the Volta fallback policy, then either land helper-level Volta tools/image normalization with focused tests and live macOS LaunchAgent proof, or document that system Node remains the only supported managed-service path.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support a Volta shim fallback for managed gateway services when no supported system Node is available?

Rationale: Current docs intentionally warn on version-manager service runtimes and prefer system Node, while the reporter requests a stable Volta shim fallback as the least-brittle version-manager path.

Likely owner: steipete

Owner reason: steipete merged the original Homebrew stable-node precedent and authored the current system-Node preference behavior, making this the best available routing owner for the policy choice.

Owner confidence: high

Options:

- **Support Volta shim fallback (recommended):** Accept resolver-level normalization from Volta tools/image paths to the accessible Volta shim, with focused tests and live macOS LaunchAgent proof before merge.
- **Keep system Node policy only:** Reject Volta shim fallback for managed services and update docs or issue comments to say version-manager service runtimes remain warned or unsupported beyond explicit wrappers.
- **Route through wrapper guidance:** Require users who need Volta-managed runtime behavior to install with a stable wrapper path instead of adding Volta-specific normalization to core path selection.

## Reproduction Assessment

No, not with a high-confidence live path in this read-only review. Source inspection shows a medium-confidence path: a supported Volta tools/image `process.execPath` falls through unchanged when no supported system Node is selected first.

## Solution Assessment

Unclear. Extending `resolveStableNodePath` is the narrowest technical boundary, but maintainers still need to accept or reject Volta shim fallback versus the documented system-Node preference for managed services.

## Summary

Current main and v2026.6.11 accept per-agent descriptions, but the observable discovery behavior remains incomplete because `agents_list` does not return them. The linked open pull request is the canonical, proof-backed implementation candidate, so this issue should remain open until that PR is refreshed and landed or maintainers reject the exposure contract.

## What This Changes

Expose optional per-agent descriptions through `agents_list` so orchestrators can select specialized sub-agents dynamically.

## Best Possible Solution

Land a refreshed implementation that returns only normalized, nonblank, length-bounded descriptions for agents already visible under the existing `agents_list` allowlist, with focused output, omission, authorization, docs, and prompt-size coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `agents_list` expose operator-authored agent descriptions to every requester already authorized to discover and spawn that agent, and what normalization and length limit should form the permanent contract?

Rationale: The config field already exists, but exposing arbitrary authored text in model-visible discovery output affects prompt size and the trust boundary; code inspection alone cannot choose that permanent policy.

Likely owner: steipete

Owner reason: The history ties this person most directly to the original discovery tool and multi-agent config/routing contract, and repository documentation identifies them as the project lead.

Owner confidence: high

Options:

- **Expose bounded descriptions (recommended):** Return trimmed, nonblank descriptions only for already-authorized agents, enforce a documented maximum length, and cover authorization and omission behavior.
- **Keep descriptions config-only:** Do not expose the field through `agents_list`, and close the linked implementation PR after documenting that descriptions are administrative metadata only.
- **Use a privileged metadata surface:** Keep `agents_list` minimal and expose descriptive metadata through a separate explicitly privileged discovery API or tool.

## Reproduction Assessment

Not applicable as a bug reproduction: this is a feature request, and current source plus the linked PR clearly establish that the config field exists while `agents_list` still omits it.

## Solution Assessment

Yes, with a bounded metadata contract. Extending the existing allowlist-filtered `agents_list` path is narrower and more maintainable than injecting every sibling into the system prompt or building a parallel discovery mechanism.

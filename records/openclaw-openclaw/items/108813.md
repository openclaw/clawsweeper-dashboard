## Label Justifications

- `P0`: The reported behavior can grant owner-only capabilities to a Discord voice participant who was configured only for transport access, meeting the security-bypass priority rubric.
- `merge-risk: 🚨 security-boundary`: The patch changes how Discord voice participants receive owner authority, so a faulty merge or rebase could either restore privilege escalation or revoke intended owner access.

## Summary

This PR remains necessary: the current Discord voice path can conflate transport admission with owner authority, while the proposed separation preserves ordinary voice access without exposing owner-only tools. The patch is focused, security-positive, and has no blocking correctness finding. Likely related people are Shadow for Discord subsystem ownership and steipete for the voice feature history.

## What This Changes

Separates Discord voice-access allowlists from owner-authority allowlists across `/vc`, transcript ingress, participant resolution, documentation, and regression tests.

## Best Possible Solution

Rebase onto current `main` and land the two-source authorization model after exact-head security checks and focused Discord voice proof confirm ordinary allowlisted speakers remain non-owner while explicit command owners retain authority.

## Reproduction Assessment

Yes. With no Discord-scoped command owner list and a speaker present only in the selected account allowlist, the pre-patch production resolver feeds that admission list into owner resolution; the manager regression case and isolated Gateway proof exercise this path.

## Solution Assessment

Yes. Separating access and owner sources at the voice owner resolver, then carrying both through `/vc` and transcript ingress, is narrower and safer than adding configuration or special-casing agent tools downstream.

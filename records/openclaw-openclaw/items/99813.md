## Label Justifications

- `P1`: The report describes a real Telegram heartbeat workflow flooding a user channel, hitting platform rate limits, and stranding delivery recovery.
- `impact:message-loss`: The central failure is channel delivery corruption: raw output is over-delivered and then delivery recovery can strand the queued state.

## Summary

Keep open: current main still has a plausible source path where heartbeat delivery normalizes only the selected final reply while embedded terminal/tool-output delivery and Telegram chunking can send large text separately, and no merged fix or canonical issue fully covers the aborted heartbeat raw-output flood.

## What This Changes

The issue reports that aborted heartbeat runs can flush raw tool output into Telegram delivery without applying the heartbeat ackMaxChars cap, causing message flooding and a stuck delivery entry after rate limiting.

## Best Possible Solution

Keep this issue open and fix the heartbeat/embedded-run delivery boundary so aborted heartbeat runs cannot flush deferred tool-output or block-reply payloads to the channel; handle any broader flood guard as an explicit follow-up policy.

## Reproduction Assessment

No, not as a high-confidence end-to-end reproduction from this checkout. The reporter’s logs plus current source make the abort/deferred-output and Telegram chunking path source-reproducible, but the exact 91-message flood still needs trajectory logs or a targeted regression harness.

## Solution Assessment

Unclear as a complete fix shape. The narrowest first fix is likely to suppress or summarize aborted heartbeat terminal tool/block payloads before channel delivery, while a generic per-chat flood guard needs separate maintainer policy approval.

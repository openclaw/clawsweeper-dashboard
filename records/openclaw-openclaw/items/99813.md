## Label Justifications

- `P1`: The report describes a real Telegram heartbeat workflow flooding a user channel, hitting platform rate limits, and leaving delivery recovery stuck.
- `impact:message-loss`: The central failure is message-delivery corruption: raw output is over-delivered, then subsequent delivery recovery can strand queued message state.
- `impact:ux-friction`: The user-facing failure produced dozens of unwanted Telegram messages and required manual queue quarantine rather than an in-product recovery path.

## Summary

Keep open: current main still has a plausible source path for aborted heartbeat or embedded-run terminal payloads to reach durable Telegram delivery, and the post-report commits/searches do not show a merged fix for the raw tool-output flood.

## What This Changes

The issue reports that an aborted heartbeat run can deliver accumulated raw tool output to Telegram in many chunks, ignoring the heartbeat ack cap and leaving delivery recovery wedged after rate limits.

## Best Possible Solution

Keep this open and fix the heartbeat/embedded-run delivery boundary so aborted heartbeat runs cannot flush deferred partial or tool-output payloads to the channel, with any broader flood guard handled as a maintainer-approved follow-up.

## Reproduction Assessment

No, not as a high-confidence live reproduction from this checkout. The reporter's logs plus current source make the abort/deferred-output and outbound-chunking path source-reproducible, but the exact 91-message Telegram flood still needs the trajectory or a targeted regression harness.

## Solution Assessment

Unclear as a complete fix shape. The best first fix appears to be suppressing or summarizing aborted heartbeat terminal payloads at the heartbeat/embedded-run boundary, while a generic per-chat flood guard should be a separate maintainer-approved recovery policy.

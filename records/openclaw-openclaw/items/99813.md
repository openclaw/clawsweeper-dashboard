## Label Justifications

- `P1`: The report describes a real Telegram heartbeat workflow flooding a user channel, hitting platform rate limits, and leaving delivery recovery stuck.
- `impact:message-loss`: The central failure is message-delivery corruption: raw output is over-delivered, then subsequent delivery recovery can strand the queued message state.
- `impact:ux-friction`: The user-facing failure produced dozens of unwanted Telegram messages and required manual queue quarantine rather than an in-product recovery path.

## Summary

Keep open: current main still has a plausible source path where aborted heartbeat/embedded-run terminal delivery can flush deferred payloads into durable channel delivery, and no merged fix or canonical PR currently covers the raw aborted heartbeat tool-output flood.

## What This Changes

The issue reports that an aborted Telegram heartbeat run can flush raw accumulated tool output as many outbound messages, bypassing heartbeat `ackMaxChars` and wedging delivery after rate limiting.

## Best Possible Solution

Keep this issue open and fix the heartbeat/embedded-run delivery boundary so aborted heartbeat runs cannot flush deferred partial or tool-output payloads to the channel, with any broader flood guard handled only after the core abort behavior is covered by regression tests.

## Reproduction Assessment

No, not as an end-to-end live reproduction from this checkout. The reporter’s logs plus current source make the abort/deferred-output and outbound-chunking path source-reproducible, but the exact 91-message Telegram flood still needs the trajectory or a targeted regression harness.

## Solution Assessment

Unclear as a complete fix shape. The best first fix appears to be suppressing or summarizing aborted heartbeat terminal payloads at the heartbeat/embedded-run boundary, while a generic per-chat flood guard should be a separate maintainer-approved recovery policy.

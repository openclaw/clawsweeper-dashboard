## Label Justifications

- `P1`: A persistent store error can repeatedly trigger background session I/O on successive cron ticks and destabilize affected systems.

## Summary

This is a valid current-main reliability bug: caught session-store failures bypass the intended reaper cooldown, and no duplicate report or open fix PR currently owns the work.

## What This Changes

Make cron session cleanup observe its existing five-minute per-store cooldown after persistence failures as well as successful sweeps.

## Best Possible Solution

Record a non-forced sweep attempt at the existing throttle boundary before fallible store work, then test that failures suppress immediate retries and become eligible again after five minutes.

## Reproduction Assessment

Yes from source inspection: make session-store listing or lifecycle mutation throw, then invoke a normal sweep again within five minutes; the first catch returns before recording the throttle timestamp, so persistence is retried. This read-only review did not execute the failure injection.

## Solution Assessment

Yes. Extending the already-defined per-store cooldown to failed attempts is the narrowest maintainable fix and avoids adding another retry policy, configuration option, or fallback store.

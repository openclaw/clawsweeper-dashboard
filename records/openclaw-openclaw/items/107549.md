## Summary

Keep this protected security issue open for explicit security-owner disposition. Current main does not expose the reported client-defined recursive filter or AST-to-SQL path; ACP replay accepts only session identifiers and executes fixed parameterized queries. A narrower availability question remains because an authenticated client can repeatedly reload an existing session and replay bounded ledger history without a dedicated replay throttle.

## What This Changes

Assess whether ACP historical-session replay needs query-complexity limits, execution timeouts, or request rate limiting to prevent denial of service.

## Best Possible Solution

Have the security owners decide the authenticated ACP replay threat boundary; if defense-in-depth is warranted, add a narrow replay-specific per-client/session throttle or concurrency budget around the existing identifier-based path rather than an AST-complexity analyzer for a filter API that does not exist.

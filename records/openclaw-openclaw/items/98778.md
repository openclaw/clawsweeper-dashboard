## Label Justifications

- `P1`: Recoverable Telegram API errors can drop the user-visible final reply, which is a broken channel workflow for affected Telegram users.
- `impact:message-loss`: The reported failure mode loses final Telegram replies or message-tool sends after the agent has produced the response.

## Summary

Keep open: current main still shows durable Telegram send paths without the same generic fallbacks as the streaming bot-reply path, and the protected `maintainer` label independently prevents conservative cleanup closure.

## What This Changes

The issue reports that Telegram durable final and message-tool sends miss fallback behavior already present in the streaming bot-reply path for rich entity rejection, media caption parse errors, native quote rejection, and longer flood waits.

## Best Possible Solution

Implement Telegram-owned durable send fallback parity in the plugin: reuse or extract the bot-path quote/rich fallback behavior for durable text and media sends, add caption parse fallback coverage, and use a Telegram-specific flood-wait retry cap with focused regression tests.

## Reproduction Assessment

Yes, source-level: current main still routes durable final/message-tool sends through `sendMessageTelegram`, where rich validation, media caption parse, native quote, and retry-after cap behavior can fail without the sibling streaming fallbacks. I did not run a live Telegram repro in this read-only pass.

## Solution Assessment

Yes, with one boundary constraint: the best fix is Telegram-plugin fallback parity around the durable send helpers, not a broad core channel rewrite. The retry-after piece should be implemented as Telegram-specific policy unless maintainers choose to change shared channel retry defaults.

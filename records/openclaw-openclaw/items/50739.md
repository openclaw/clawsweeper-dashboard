## Label Justifications

- `P2`: The issue describes a real alert-reliability gap during provider incidents, but the remaining work is a bounded product and security design rather than an emergency outage.
- `impact:message-loss`: A delayed incident alert can be effectively missed when it surfaces after the provider incident has already self-reset or been handled elsewhere.
- `impact:session-state`: Any queue-bypassing prompt-visible system event must preserve active session ordering, transcript state, and system-event drain semantics.
- `impact:security`: A direct trusted `System:` injection path crosses prompt-spoofing, authorization, and prompt-ordering boundaries.
- `maturity:stable`: The affected Gateway RPC/API system-event surface maps to `gateway-runtime`, which is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open. Current main has implemented the adjacent session-targeting work for `system event`, but it still has no priority or queue-bypass contract; `--mode now` enqueues a prompt-visible event and asks heartbeat to run, and heartbeat still skips active or queued same-session work.

## What This Changes

Requested behavior is a high-priority or queue-bypass mode for `openclaw system event --mode now` so in-session alerts surface immediately during congested or failing session lanes.

## Best Possible Solution

Define a trusted urgent-alert contract that separates immediate operator-visible notification from ordered prompt/transcript injection, then add typed CLI, protocol, gateway, TUI, and regression-test support around that contract.

- **Defer to scheduler fairness:** Keep `system event` best-effort for now and solve foreground/background ordering through the broader session-lane policy tracked at https://github.com/openclaw/openclaw/issues/54488.

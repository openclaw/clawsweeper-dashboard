## Label Justifications

- `P2`: This is a normal-priority PDF tool input bug with misleading output risk but a narrow blast radius and clear repair path.
- `impact:data-loss`: Fractional `pages` values can cause the user-selected PDF page content to be silently dropped before extraction.

## Summary

Keep open: current main still accepts fractional PDF page tokens at the parser boundary, and the fallback extractor then drops those non-integer pages before extraction. The related merged PDF range fix only rejects empty out-of-range selections, so this narrower integer-validation bug remains actionable.

## What This Changes

The issue asks the PDF tool to reject fractional `pages` values instead of letting fallback extraction silently select no PDF pages.

## Best Possible Solution

Reject non-integer single-page tokens in `parsePageRange`, preserve existing range/clamp behavior, and add focused helper plus tool-boundary regression coverage.

## Reproduction Assessment

Yes at source level: current `parsePageRange("1.5", 20)` follows the single-token `Number(part)` branch, and fallback extraction filters the resulting non-integer page out. I did not run a live PDF execution because this review was constrained to read-only inspection.

## Solution Assessment

Yes, the best fix is at the parser boundary because `parsePageRange` is the source of truth for converting the public `pages` string into the `pageNumbers` contract. Changing the extractor would leave invalid tool input accepted and would not protect native-routing checks consistently.

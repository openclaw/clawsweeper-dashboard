- `P2`: This is a normal-priority PDF tool input bug with misleading output risk but a narrow blast radius.
- `impact:data-loss`: Fractional page selections can silently drop the user-selected PDF page content before fallback extraction.

## Summary

Keep open: current main still accepts fractional PDF page tokens at the parser boundary, and fallback extraction then drops those non-integer pages before extraction. The merged empty-selection PDF range fix is adjacent but does not add integer validation for accepted single-page tokens.

## What This Changes

The issue reports that fractional PDF `pages` values are accepted by the parser and later dropped by fallback extraction instead of being rejected as invalid input.

## Best Possible Solution

Reject non-integer single-page tokens in `parsePageRange`, preserve existing integer/range/clamp behavior, and add focused helper plus tool-boundary regression coverage.

## Reproduction Assessment

Yes, at source level: `parsePageRange("1.5", 20)` follows the single-token `Number(part)` path, and fallback extraction later filters that value out with `Number.isInteger`. I did not run a live PDF tool execution because this review is read-only.

## Solution Assessment

Yes, the parser boundary is the best fix location because `parsePageRange` is the source of truth for converting the public `pages` string into `pageNumbers`. Fixing only the extractor would keep invalid tool input accepted and would not protect native-routing checks consistently.

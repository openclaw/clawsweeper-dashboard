## Label Justifications

- `P2`: This is a valuable core Gateway performance improvement, but it is not yet affecting released users and has a bounded pre-merge repair.
- `merge-risk: 🚨 compatibility`: The deferred cleanup can invalidate an existing managed-plugin generation still used by the running Gateway during an install-triggered restart.
- `merge-risk: 🚨 availability`: Deleting an in-use plugin tree can make lazy imports, hooks, or plugin operations fail before the old Gateway exits.

## Summary

Keep open: the earlier durable-provider reload finding is fixed on the latest head, but deferred retained-plugin cleanup can still delete the generation used by the running Gateway after an install advances the index. That P1 lifecycle race blocks merge despite otherwise strong proof.

## What This Changes

The PR defers retained-plugin cleanup until after readiness, lazily loads worker-environment startup/runtime modules, and adjusts startup benchmarking and dead-export baselines.

## Best Possible Solution

Capture the startup generation paths, union them with the live installed-plugin paths when cleanup executes, and add a regression test that advances install records before the idle task runs so only a later Gateway can remove the old generation.

## Reproduction Assessment

Yes at source level: start with generation A loaded, commit generation B while the idle cleanup remains pending, then let cleanup run before the old Gateway closes and exercise a lazy import or hook from A. The PR does not yet include this exact regression scenario.

## Solution Assessment

No in its current form. Deferring optional work and lazy-loading worker modules are appropriate, but cleanup must preserve both the running Gateway's startup generation and any generation installed during the delay.

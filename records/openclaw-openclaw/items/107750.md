## Label Justifications

- `P1`: A busy real-world channel workflow repeatedly runs futile session maintenance during live writes and has reported user-visible turn failure and session contention symptoms.
- `impact:session-state`: The issue concerns persistent conversation pointers, session-cap eviction behavior, compaction interaction, and session-file concurrency.

## Summary

Keep open: current main still protects durable thread, group, and channel pointers from all entry maintenance while triggering cap maintenance from the total row count, so a protected population above `maxEntries` remains unsatisfiable and repeatedly evicts transient rows. The no-churn defect is clear, but durable-pointer expiration is a separate continuity policy requiring maintainer direction.

## What This Changes

Prevent futile repeated session-cap enforcement when durable conversation pointers exceed `maxEntries`, and define whether inactive durable pointers should eventually expire.

## Best Possible Solution

Split the outcomes: make runtime maintenance removable-capacity-aware so an unsatisfiable protected population produces no repeated destructive pass and at most a deduplicated operator warning, then separately choose and document an explicit inactivity lifecycle for durable conversation pointers with focused fresh/upgrade behavior tests.

Options:

- **Split repair and policy (recommended):** Land a bounded no-churn fix now, then decide durable-pointer retention separately with explicit inactivity and re-entry semantics.
- **Retain indefinitely:** Keep durable pointers permanently exempt and treat `maxEntries` as a cap only on removable synthetic rows, with clear diagnostics when protected rows exceed it.
- **Add durable retention:** Define a documented age or inactivity policy that can retire durable pointers while preserving safe conversation restart and routing behavior.

## Reproduction Assessment

Yes at source level: create more protected thread/group/channel rows than `maxEntries`, then add or update a removable transient row; total-count triggering runs while the cap grants zero removable slots and deletes the transient row. A fresh live current-main run was not performed in this read-only review.

## Solution Assessment

No, one combined retention change is not the safest fix. The narrow no-churn defect should be repaired independently, while durable-pointer expiration needs an explicit continuity policy and separate validation.

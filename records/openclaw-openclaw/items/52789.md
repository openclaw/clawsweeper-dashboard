## Label Justifications

- `P2`: This is a normal-priority multi-agent cron reliability feature with real user impact, but it requires product and security direction before implementation.
- `impact:message-loss`: The report says cron results can be silently dropped when smaller models fail to call `sessions_send` correctly.
- `impact:session-state`: The requested mode would write cron output into another agent session and affect transcript and context routing semantics.

## Summary

Keep open: current main and v2026.6.11 still only support cron delivery as `none`, `announce`, or `webhook`; adding invisible cron-to-session delivery is a real feature request that needs maintainer product and security direction.

## What This Changes

Requested a new cron `delivery.mode="session"` that sends completed cron output internally to a target session via `sessions_send`.

## Best Possible Solution

Keep this open for maintainer design of a cron-to-session delivery contract that aligns schema, protocol, authorization, A2A dispatch semantics, docs, and tests.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 both expose only `none`, `announce`, and `webhook` cron completion delivery, so the requested `session` mode is absent without needing a live run.

## Solution Assessment

Unclear. Framework-owned session delivery is plausible, but maintainers still need to choose the cron output API shape, A2A relationship, authorization rules, and transcript semantics before this should become code.

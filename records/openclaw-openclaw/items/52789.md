## Label Justifications

- `P2`: This is a meaningful multi-agent cron reliability feature with limited blast radius, but it is not an emergency runtime outage.
- `impact:session-state`: The requested mode would write cron output into another agent session and affect transcript/context routing semantics.
- `impact:security`: Invisible framework-owned cross-session delivery requires explicit authorization, visibility, and provenance decisions.
- `impact:message-loss`: The report says cron results can be silently dropped when smaller models fail to call `sessions_send` correctly.

## Summary

Keep open: current main and v2026.6.11 still expose cron completion delivery only as `none`, `announce`, or `webhook`, while the requested internal cron-to-session mode remains a new product and security-sensitive contract.

## What This Changes

Request adds a cron `delivery.mode: "session"` path that sends completed cron output internally to a target session via `sessions_send` instead of relying on visible chat, webhook delivery, or model tool calls.

## Best Possible Solution

Define one maintainer-approved cron output/session delivery contract that aligns schema, runtime delivery, A2A dispatch semantics, authorization, audit/provenance, docs, and focused tests before implementation.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 both expose only `none`, `announce`, and `webhook` cron completion delivery, so `delivery.mode="session"` is absent without a live run.

## Solution Assessment

Unclear. Framework-owned session delivery is plausible, but maintainers still need to choose the cron output API shape, A2A relationship, authorization rules, and transcript semantics before this should become code.

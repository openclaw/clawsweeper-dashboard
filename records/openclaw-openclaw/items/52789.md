## Label Justifications

- `P2`: This is a normal-priority multi-agent cron reliability feature with real power-user impact but no core runtime outage and unresolved product direction.
- `impact:session-state`: The request would write cron output into another agent session and affect transcript/context routing semantics.
- `impact:security`: Invisible scheduler-owned cross-session delivery needs authorization, provenance, and audit decisions before implementation.
- `impact:message-loss`: The report says cron results can be silently dropped when lower-capability models fail to call `sessions_send` correctly.

## Summary

Keep open: current main and the latest release still lack a cron `delivery.mode="session"` contract, and the remaining work is a public cron/session delivery API with security and product decisions rather than conservative cleanup.

## What This Changes

Add a cron delivery mode that sends completed job output internally to a target session instead of a visible chat channel or webhook.

## Best Possible Solution

Choose a maintainer-approved cron-to-session output contract that composes with the broader cron output-routing and A2A dispatch designs, then update schema, protocol, runtime delivery, docs, and regression tests together.

## Reproduction Assessment

Yes. Current main source, protocol schema, runtime planning, docs, and the latest release all show cron delivery is limited to `none`, `announce`, and `webhook`, so the missing `session` contract is source-reproducible without a live run.

## Solution Assessment

Unclear. Framework-owned session delivery is plausible, but maintainers need to choose the cron output API, A2A dispatch relationship, authorization, and transcript semantics before implementation.

- `impact:session-state`: The requested mode would write cron output into another agent session and affect transcript/context routing semantics.

- `impact:message-loss`: The report says cron results can be silently dropped when models fail to call `sessions_send` correctly.

## Summary

Keep open: current main and the latest release still expose cron completion delivery as `none`, `announce`, or `webhook`, while this request adds a new framework-owned cron-to-session delivery contract that needs maintainer product and security direction.

## What This Changes

Add a cron `delivery.mode: "session"` option that routes a completed cron job's output into a target session internally instead of posting to a visible channel or relying on the model to call `sessions_send`.

## Best Possible Solution

Design one maintainer-approved cron-to-session output contract that composes with A2A dispatch, defines authorization and provenance, and then updates schema, runtime delivery, docs, UI/protocol surfaces, and focused tests together.

## Reproduction Assessment

Yes, at source level: current main exposes cron completion delivery as `none`, `announce`, or `webhook` only across types, parser/planner, protocol schema, and docs. A live run is not needed to prove the requested public contract is absent.

## Solution Assessment

Unclear. Framework-owned session delivery is plausible, but maintainers still need to choose the permanent cron output API shape, A2A relationship, authorization model, and transcript semantics before implementation.

## Label Justifications

- `P1`: The PR targets a regression where recurring silent cron jobs are marked as errors and can trigger false failure handling on every scheduled run.
- `merge-risk: 🚨 compatibility`: The diff changes the default status semantics for existing cron jobs that currently treat empty assistant output as `empty_response` failure.
- `merge-risk: 🚨 message-delivery`: For delivery-requested cron jobs, an empty model response would now suppress delivery and record success, which can hide a message that operators expected to be sent or flagged as failed.

## Summary

Keep this PR open for maintainer review rather than cleanup close: current main and v2026.6.11 still lack the cron executor opt-in, while this branch fixes both runner handoffs and has sufficient real behavior proof. The remaining blocker is maintainer acceptance of the all-cron silent-empty policy, because the change intentionally turns empty cron output into `ok` for delivery-requested jobs too.

## What This Changes

Adds `allowEmptyAssistantReplyAsSilent: true` to the isolated cron executor's CLI and embedded runner calls and adds regression tests for both handoffs.

## Best Possible Solution

Have a maintainer accept or narrow the all-cron silent-empty policy, then land this canonical executor-boundary fix and close or supersede the overlapping PRs.

## Summary

Keep this canonical feature request open. Current main and v2026.6.11 expose Telegram forum-topic creation and editing but not close, reopen, or delete; deletion permanently removes the topic and its messages, so its authorization and default gate need maintainer direction before implementation.

## What This Changes

Add Telegram forum-topic create, edit, close, reopen, and delete operations to the message tool.

## Best Possible Solution

Implement close and reopen as explicit Telegram-owned topic actions, and expose permanent deletion as a distinct default-off action with its own authorization gate, clear destructive semantics, documentation, and focused contract/runtime tests rather than overloading ordinary message deletion.

## Maintainer Decision

Question: Should permanent Telegram forum-topic deletion be exposed, and if so must it use a distinct default-off action and configuration gate rather than the existing message-delete path?

Rationale: Close and reopen are reversible topic-management operations, but deleteForumTopic permanently removes the topic and its messages under a different Telegram permission; automation cannot choose that product and safety boundary.

Options:

- **Distinct default-off delete (recommended):** Add close/reopen normally and add topic-delete as a separate, explicitly enabled destructive action with its own gate and documentation.
- **Lifecycle without deletion:** Add close and reopen now, leaving permanent deletion unsupported until a broader destructive-action policy is approved.
- **Enable full lifecycle by default:** Expose close, reopen, and delete without a separate deletion opt-in, accepting the larger destructive blast radius.

## Solution Assessment

No, the original all-actions proposal needs a safer boundary: reversible close/reopen can follow the existing topic-action pattern, while permanent deletion should be separately named, authorized, and default-off.

## Summary

This remains necessary and should stay the canonical lifecycle tracker: current main and v2026.6.11 support Telegram forum-topic creation and editing, but not closing, reopening, or deletion. Maintainers still need to choose the public action names, defaults, and destructive-operation gates.

## What This Changes

Add Telegram forum-topic close, reopen, and delete operations to the message tool’s existing create/edit support.

## Best Possible Solution

Add separate Telegram-plugin-owned `topic-close`, `topic-reopen`, and `topic-delete` actions using grammY primitives, explicit operation gates, focused contract/runtime/docs coverage, and live Telegram proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Telegram forum close, reopen, and delete be separate message actions with independent configuration gates?

Rationale: Current create/edit support and the closed prior proposals do not establish approved public names, default enablement, or safety gates for destructive lifecycle operations.

Likely owner: obviyus

Owner reason: They introduced the adjacent current `topic-edit` capability and have the strongest direct feature-history signal.

Owner confidence: high

Options:

- **Separate gated actions (recommended):** Add `topic-close`, `topic-reopen`, and `topic-delete` with explicit Telegram-owned gates, documentation, tests, and live proof.
- **Overload edit and delete:** Infer topic lifecycle behavior from topic identifiers on existing actions, reducing action count but introducing dual semantics and compatibility risk.
- **Defer destructive lifecycle:** Keep create/edit only until maintainers explicitly sponsor broader agent-controlled topic administration.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 consistently stop at create/edit across action registration, Telegram discovery, runtime dispatch, configuration, and documentation.

## Solution Assessment

Yes on the Telegram-plugin owner boundary, but the proposed public interface is not fully settled. Separate gated actions avoid ambiguous message/topic deletion semantics and are the cleanest option if maintainers approve the capability.

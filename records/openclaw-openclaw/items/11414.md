## Summary

Keep open. Current main and v2026.6.11 still implement only Telegram forum-topic creation and editing; close, reopen, and delete remain missing, and the deletion-only prior PR closed unmerged. Maintainer direction is required because permanent deletion has different permissions and consequences from the other lifecycle operations.

## What This Changes

Add Telegram forum-topic create, edit, close, reopen, and delete operations to the message plugin.

## Best Possible Solution

Implement distinct Telegram-owned topic-close, topic-reopen, and topic-delete actions after owner approval, with permission-specific failures, explicit configuration/default behavior, clear destructive-delete documentation, and focused contract, runtime, transport, config, and live Telegram proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Telegram topic close, reopen, and permanent delete become distinct public message actions with permission-specific configuration gates and defaults?

Rationale: Current contracts expose none of these operations, and Telegram deletion has materially different permissions and destructive consequences from close and reopen.

Likely owner: obviyus

Owner reason: Their merged history introduced topic-edit and normalized the Telegram action contract that this decision would extend.

Owner confidence: high

Options:

- **Distinct lifecycle actions (recommended):** Add topic-close, topic-reopen, and topic-delete with explicit Telegram-owned gates, permission-specific errors, and prominent destructive-delete documentation.
- **Reuse existing actions:** Overload edit and delete based on topic identifiers, reducing action names but creating ambiguous public semantics and permission handling.
- **Defer permanent deletion:** Add close and reopen first while leaving deletion unsupported until its irreversible message removal is separately approved.

## Reproduction Assessment

Yes at source level: current main and v2026.6.11 expose create and edit but omit close, reopen, and delete across action discovery, dispatch, transport, configuration, documentation, and tests. No live Telegram run was needed to establish the missing public surface.

## Solution Assessment

Yes on owner boundary, but not yet on final API shape: one coherent Telegram-plugin implementation is the narrowest maintainable solution, while distinct lifecycle actions are safer than overloading message edit/delete because permissions and destructive effects differ.

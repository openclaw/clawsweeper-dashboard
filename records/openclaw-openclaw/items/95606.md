## Summary

Keep open: current main and the latest release still leave the model-visible recall-to-forget handoff broken, while broader replacement/deprecation semantics remain a memory product/API decision.

## What This Changes

The issue asks for stale or conflicting long-term memories to be deletable or superseded after a corrected fact is stored.

## Best Possible Solution

Choose a memory-lancedb cleanup contract that makes exact deletion selectors model-visible for recall, while leaving automatic replacement, tombstone, and conflict-resolution semantics to the broader Memory MVP design.

## Maintainer Decision

Options:

- **Expose recall UUIDs narrowly (recommended):** Add full UUIDs to memory_recall content with regression and live plugin proof, while explicitly leaving replacement and tombstone semantics to the broader Memory MVP trackers.
- **Design lifecycle contract first:** Keep this issue open until maintainers settle the canonical memory schema, supersede/tombstone states, and conflict-resolution flows before changing recall output.
- **Use a non-UUID deletion handle:** Define an opaque model-visible deletion selector instead of raw UUIDs, accepting extra API design work before implementation.

## Reproduction Assessment

Yes for the narrow recall-to-forget handoff: current main exposes UUIDs only in details.memories, docs say details are not model-visible, and delete rejects numeric indexes. A July 6 live repro on v2026.6.11 confirmed the same behavior against memory-lancedb.

## Solution Assessment

Unclear until maintainers choose the contract. Exposing UUIDs in recall content is the narrowest plausible fix for exact deletion, but automatic replacement, tombstoning, or index-based deletion require product/API direction.

## Summary

Keep open: current main still does not persist followup queues across restart, and this branch remains useful context, but the PR is not landable because it uses a JSON runtime-state sidecar, replays user text through trusted system-event prompt lines, has a fixed stale-drop window, lacks real behavior proof, and is stale against the current startup surface.

## What This Changes

The PR adds JSON sidecar persistence for in-memory followup queues during gateway shutdown and replays the saved messages as startup system events after restart.

## Best Possible Solution

Land a rebased SQLite/doctor-backed followup recovery design that restores through normal or explicitly untrusted replay semantics, proves exactly-once delivery in a real channel restart, and keeps the canonical issue open until that fix merges.

No. Persisting queued followups is the right bug boundary, but this branch uses a JSON sidecar and trusted system-event replay; the maintainable fix should be SQLite-backed recovery with normal or explicitly untrusted replay semantics.

Full review comments:

- **[P1] Move queue persistence into SQLite state:** `src/auto-reply/reply/queue/persist.ts:67`
  - body: This writes OpenClaw-owned runtime queue state to `state/pending-messages.json`. The repository state contract keeps runtime queues and caches in SQLite-backed stores, with sidecars handled only by doctor or migration code, so this creates a parallel source of truth with no upgrade owner.
  - confidence: 0.91
- **[P1] Keep replayed prompts out of trusted system events:** `src/gateway/server-pending-messages.ts:32-44`
  - body: `item.prompt` comes from user or channel messages, but this path embeds it in a recovery summary and queues that summary as a system event. Current main renders system events as `System:` prompt lines, so crafted queued text can be elevated after restart instead of being replayed through normal untrusted/user-message handling.
  - confidence: 0.9
- **[P2] Remove the fixed five-minute recovery drop:** `src/auto-reply/reply/queue/persist.ts:110-116`
  - body: The loader drops all persisted queue entries older than five minutes, which means a slow update, manual downtime, or repeated restart failure still silently loses exactly the messages this PR is meant to preserve. Durable queue recovery should either restore until consumed or use an explicit product policy with visible handling.
  - confidence: 0.78

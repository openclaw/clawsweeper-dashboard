## Summary

Keep open: current main has implemented `openclaw config validate`, write-time config validation, SecretRef builder/dry-run flows, non-TTY fail-closed handling, and `${ENV}` preservation for existing placeholders, but interactive bare `openclaw config` is still a documented wizard entrypoint and literal value-mode secret-write policy remains unsettled.

## What This Changes

The issue requests safer `openclaw config` behavior: avoid surprising wizard entry, add config validation, and prevent resolved environment secrets from being written into config files.

## Best Possible Solution

Keep the implemented validation, SecretRef builder/dry-run, non-TTY guard, and env-placeholder restoration; have maintainers decide the documented root-command UX and whether new literal secret writes need a warning, refusal, or clearer SecretRef-first flow.

## Solution Assessment

Unclear pending maintainer direction: the implemented validation and env-preserve pieces are good mitigations, but switching bare `openclaw config` to help/status would change a documented setup entrypoint. The safer path is an explicit maintainer decision on root-command UX and secret-source policy rather than an automatic fix PR.

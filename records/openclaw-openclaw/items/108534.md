## Label Justifications

- `P1`: A reproduced real-user Feishu workflow loses deterministic access to a successfully downloaded document, forcing unreliable recovery and affecting later agent turns.
- `impact:session-state`: The persisted conversation loses the attachment provenance needed to associate a later turn with the original downloaded file.
- `impact:security`: Recovery by scanning the shared inbound directory can expose attachments belonging to other agents or users.

## Summary

Keep open: current main downloads the Feishu attachment and carries its path as transient inbound-media facts, but constructs the persisted agent-facing message body separately; no current source or test evidence shows that a later turn retains a durable per-message attachment reference. The related shared-directory report increases the security impact but does not own this narrower provenance-loss bug. ([github.com](https://github.com/openclaw/openclaw/blob/main/extensions/feishu/src/bot.ts))

## What This Changes

Persist a trusted durable reference for downloaded Feishu document attachments so later turns can retrieve the complete file after inline content is truncated.

## Best Possible Solution

Persist an opaque managed media reference plus filename, content type, and message provenance in the canonical inbound/session record, with Feishu supplying the downloaded attachment facts and later turns resolving the same reference without directory scanning.

## Maintainer Decision

Question: Should durable inbound attachment provenance become a shared managed-media/session contract, or may Feishu append a plugin-local attachment record to the persisted message body?

Rationale: The representation controls filesystem disclosure, media lifetime, cross-agent isolation, and whether other channels inherit the same durable-reference guarantee; source inspection cannot determine that security boundary without owner intent.

Options:

- **Shared managed reference (recommended):** Add an opaque durable media reference to the shared inbound/session contract and migrate Feishu to it, avoiding raw host paths and channel-specific semantics.
- **Feishu-local record:** Append a structured Feishu-only attachment record to the persisted body, accepting a narrower fix and future cross-channel contract divergence.
- **Defer to storage isolation:** Wait for https://github.com/openclaw/openclaw/issues/19330, although per-agent storage alone would not preserve the message-to-file mapping required here.

Yes at source level: current main downloads the attachment and supplies transient media facts separately from the constructed agent message body, matching the reported provenance-loss path. A live current-main Feishu replay is still needed to capture the serialized session and follow-up failure.

## Solution Assessment

No, appending an absolute local path directly to Feishu text is not the best long-term fix; the safer solution is a shared opaque managed-media reference persisted with the session, with focused Feishu coverage.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.91

Full review comments:

- **[P1] Keep timed-out OAuth work from writing after lock release:** `src/agents/auth-profiles/oauth-manager.ts:491-493`
  - body: The new in-lock timeout rejects the callback passed to `withFileLock`, so the lock is released, but the abandoned async body is not cancelled. If it later resumes, it can still persist and mirror refreshed credentials while another process or queued refresh now owns the same OAuth key, which breaks the lock invariant this path relies on.
  - confidence: 0.94
- **[P1] Block timed-out auth work from mutating runtime state:** `src/agents/embedded-agent-runner/run/auth-controller.ts:148-149`
  - body: `withAuthDeadline(...)` only rejects the caller; it does not cancel the underlying refresh or cold-start auth operation. A timed-out operation can later resume and run the existing `setRuntimeApiKey`, request override, or `setRuntimeAuthState` writes after later turns have already proceeded.
  - confidence: 0.91
- **[P2] Give the outer auth deadline real contention headroom:** `src/agents/runtime-auth-refresh.ts:26`
  - body: The hard deadline is 300s, while OAuth can spend 150s in the old owner's in-lock section and another 150s in the new owner's in-lock section, before accounting for scheduling or queued work. That means legitimate serialized refreshes can hit the outer hard deadline even though each inner deadline is still within its configured budget.
  - confidence: 0.84

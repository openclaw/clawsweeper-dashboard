## Summary

Keep this PR open for an auth-area maintainer decision rather than cleanup: it has strong focused regression coverage and real-timer recovery evidence, but it deliberately changes the runtime contract from indefinite waiting to deadline-abandon-and-retry across provider, keychain, and file-lock work. The remaining question is whether that 150s/360s failure-and-recovery policy is the intended upgrade behavior for all supported auth providers, not a narrow mechanical defect.

## What This Changes

This PR adds hard deadlines to embedded runtime-auth refresh, cold-start preparation, and OAuth lock-held credential work so a hung provider hook, keychain operation, or lock wait releases the agent lane instead of waiting forever.

## System Context

Embedded agent runs obtain provider credentials through a runtime-auth controller; it refreshes credentials in the background and delegates OAuth token refresh to a cross-process lock-protected manager. These credentials feed subsequent model turns, so a stuck refresh can otherwise leave a healthy gateway process unable to produce replies.

## Architecture Diagram

  C --> D[OAuth refresh manager]
  D --> E[Cross-agent file lock]
  E --> F[Credential store and provider hook]
  F --> G[Updated runtime credentials]
  B --> H[Agent lane continues or receives timeout error]

## Best Possible Solution

Adopt one documented, owner-approved deadline-and-retry contract for runtime OAuth work, with the existing stale-write guards retained and focused tests covering both recovery after abandonment and a legitimate slow-lock contention path.

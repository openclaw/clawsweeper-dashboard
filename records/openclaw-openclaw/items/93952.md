- **[P1] Prevent timed-out OAuth work from writing after lock release:** `src/agents/auth-profiles/oauth-manager.ts:491-494`
  - body: The new in-lock timeout rejects the callback passed to `withFileLock`, so the global refresh lock can be released while the abandoned async body is still running. If it later resumes, it can persist or mirror credentials after another process or queued refresh owns the same OAuth key.
  - confidence: 0.94

  - body: `withAuthDeadline(refreshOperation, ...)` clears the single-flight handle on timeout, but the underlying refresh operation can still finish later and write the runtime API key, request overrides, and auth state when generation/profile/source still match. A retry using the same generation can therefore be overwritten after later turns were unblocked.
  - confidence: 0.91
- **[P2] Give the hard auth deadline real contention headroom:** `src/agents/runtime-auth-refresh.ts:26`
  - body: `RUNTIME_AUTH_REFRESH_HARD_TIMEOUT_MS` is 300s, while a legitimate cross-process path can spend up to the 150s in-lock budget behind an old owner and then up to 150s in its own in-lock work, before timer jitter or queue delay. That can report a hard runtime-auth timeout for work still inside the inner budgets.
  - confidence: 0.84

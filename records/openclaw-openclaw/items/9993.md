## Summary

## What This Changes

Add a synchronous, rejectable pre-persistence hook for gateway configuration mutations so validators can inspect and block an invalid pending configuration.

## Best Possible Solution

Settle a narrow, documented Plugin SDK contract for a synchronous config-write policy hook at the shared pre-persistence boundary, with typed rejection, redacted actor/context data, deterministic ordering, and tests that rejection leaves both disk and active configuration unchanged.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a config-only, rejectable Plugin SDK hook at the canonical pre-persistence boundary, and what trust, ordering, timeout, redaction, and recovery contract should govern it?

Rationale: Existing validation prevents many malformed writes, but the requested mandatory external policy point changes plugin authority over persisted configuration and cannot be safely selected by an implementation worker.

Likely owner: steipete

Owner reason: The recorded maintainer review already identified this as a config validation/mutation design-direction decision.

Owner confidence: medium

Options:

- **Approve a scoped config policy hook (recommended):** Define a config-only synchronous reject hook after built-in validation/preflight and before the canonical write, with an explicit Plugin SDK security contract.
- **Design a broader persistence policy first:** Fold config into a general durable-write interception model so hook semantics are shared across config, state, and other persistent writes.
- **Keep validation built-in only:** Decline third-party veto authority and continue relying on schema validation, preflight, tool allowlists, and external advisory tooling.

## Solution Assessment

## Summary

Keep open: current main validates pending configuration, preflights SecretRefs, guards concurrent writes, and restricts agent config tools, but still has no mandatory plugin-facing veto between validation and persistence. The remaining work requires an explicit Plugin SDK and security-boundary contract rather than an autonomous mechanical fix.

## What This Changes

Add a synchronous plugin-facing pre-apply hook that can inspect and reject pending gateway configuration mutations before persistence.

## Best Possible Solution

Define one typed synchronous interception point in the canonical configuration-write pipeline, after pending-config validation and SecretRef preflight but before persistence, with redacted payload rules, deterministic ordering, bounded execution, typed rejection, recursion protection, and tests proving every supported writer leaves disk and active runtime state unchanged when rejected.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should trusted plugins be allowed to synchronously inspect and veto every canonical configuration write, and under what redaction, failure, timeout, and recovery contract?

Rationale: This changes the Plugin SDK and makes plugin execution part of a security- and availability-sensitive persistence boundary; source inspection cannot determine the intended trust and fail-open/fail-closed policy.

Likely owner: steipete

Owner reason: The existing issue review already routes this gap into configuration mutation product direction and distinguishes it from current built-in safeguards.

Owner confidence: medium

Options:

- **Add a bounded trusted-plugin veto (recommended):** Expose a typed, redacted pre-persistence event from the canonical writer with strict timeout, rejection, recursion, and operator-recovery semantics.
- **Keep validation core-owned:** Do not expose a veto hook; instead extend built-in validation and doctor rules for configuration invariants that OpenClaw officially supports.
- **Offer advisory validation only:** Let plugins report diagnostics before writes while core validation remains the only blocking authority.

## Reproduction Assessment

Yes at the source level: current main's hook catalog and canonical config-write paths contain no synchronous plugin-facing veto between pending-config validation and persistence. The original provider failure incident was not rerun, but reproducing that incident is unnecessary to establish the requested API gap.

## Solution Assessment

Unclear until maintainers choose the security contract. A config-specific hook in the canonical mutation pipeline is narrower and safer than relying on before_tool_call or introducing a broad generic persistence hook, but its trust, redaction, timeout, and failure semantics need explicit approval.

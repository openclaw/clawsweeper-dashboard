## Summary

Keep open: current main has built-in validation, SecretRef preflight, base-hash guarded writes, and agent-tool restrictions, but it still lacks the requested synchronous plugin/API-level veto point before config persistence.

## What This Changes

The issue requests a synchronous config pre-apply hook that can validate and reject gateway config writes before they are persisted.

## Best Possible Solution

Define a documented synchronous config-write interception API that runs after pending config computation and built-in validation/preflight but before persistence, covers all config write paths, and returns a typed reject result without mutating disk or runtime state on rejection.

Options:

- **Design guarded config-write hook (recommended):** Add a narrow, documented pre-persistence hook covering config.set, config.patch, config.apply, and shared mutation helpers with explicit redaction, timeout, recursion, ordering, and rejection semantics.
- **Limit to built-in validation:** Keep config validation, SecretRef preflight, and agent-write allowlists in core, and document external validators as optional helpers that cannot enforce mandatory pre-apply policy.
- **Fold into broader preflight design:** Defer this specific hook until the related preflight/config validation direction chooses one shared validation contract across startup and config mutation.

## Reproduction Assessment

Yes, at source level: current main exposes config write RPCs and plugin hooks, but there is no rejectable config pre-apply hook between validation/preflight and persistence. This is a feature/API gap rather than a failing runtime repro.

## Solution Assessment

Unclear until maintainer design review. A config-write interception seam is the maintainable direction, but the exact hook contract, ordering, and security semantics need a product/security decision first.

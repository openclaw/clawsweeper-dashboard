## Summary

Keep open: current main and v2026.6.11 have strong built-in config validation and an internal final commit guard, but plugins still cannot register a mandatory pre-persistence veto; the linked config-guard project remains an opt-in workaround rather than a solution to that API gap.

## What This Changes

Requests a synchronous plugin-facing veto hook before gateway configuration changes are persisted.

## Best Possible Solution

Expose a typed trusted-plugin config-write decision contract through the existing final pre-commit guard, covering all canonical writers and providing current and pending config, operation, changed paths, actor context, and typed rejection without creating a gateway-tool-only path.

Rationale: The repository already has the correct internal commit seam, but source evidence cannot decide which plugins may block writes, which sensitive fields they receive, how timeouts and hook errors behave, or how operators recover when a validator itself blocks repair.

Likely owner: steipete

Owner confidence: high

Options:

- **Trusted synchronous veto (recommended):** Expose a typed hook for explicitly trusted code plugins, composed after built-in validation and SecretRef preflight with bounded execution, redacted context, and an operator recovery bypass.
- **Core validators only:** Keep the final veto internal to core and offer plugins only non-blocking post-validation observation, avoiding third-party denial-of-service authority.
- **Unified persistence contract:** Fold config writes into the broader durable-state hook design at https://github.com/openclaw/openclaw/issues/48509 before adding any config-specific public API.

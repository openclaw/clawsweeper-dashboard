## Summary

Keep open: current main and v2026.6.11 validate configuration, preflight SecretRefs, and guard writes with a base hash, but neither exposes a mandatory plugin-facing decision point before configuration persistence. The remaining work is a real Plugin SDK and security-boundary design choice, not an obsolete request.

## What This Changes

Add a synchronous plugin-facing pre-apply hook that receives current and pending configuration and can reject config mutations before they are written.

## Best Possible Solution

Define a trusted, typed, timeout-bounded hook at the canonical config commit boundary, with redacted payload rules, explicit caller and action metadata, recursion and recovery semantics, and tests proving rejection leaves disk and active runtime unchanged for every writer.

- **Trusted typed veto (recommended):** Add a trusted-plugin-only, timeout-bounded hook at the canonical commit boundary with redacted payloads and a documented recovery bypass.
- **Advisory validation event:** Expose pending-change context to plugins but reserve rejection authority for core validation.
- **Core-only hardening:** Keep persistence exclusively core-owned and expand built-in provider, schema, preflight, and doctor validation instead.

## Reproduction Assessment

Yes at source level: config.set, config.patch, and config.apply proceed from built-in validation and SecretRef preflight to persistence, while the public typed plugin hook catalog has no config-write veto.

## Solution Assessment

The capability is justified, but the exact tool-scoped sketch is not the best implementation; the maintainable solution is one canonical commit-boundary contract covering gateway and internal writers.

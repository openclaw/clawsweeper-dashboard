## Summary

Keep open: current main has built-in config validation, SecretRef preflight, base-hash checks, and tool-side restrictions, but it still does not expose the requested synchronous plugin/API config-write veto before persistence.

## What This Changes

Requests a synchronous `config:pre-apply` hook that lets plugins validate and block Gateway config writes before `config.patch` or `config.apply` persists them.

## Best Possible Solution

Define a documented synchronous config-write interception API that runs after pending config computation and built-in validation/preflight but before persistence, covers all config write paths, and returns a typed reject result without mutating disk or runtime state on rejection.

Options:

- **Design guarded config-write hook (recommended):** Add a narrow, documented pre-persistence hook covering `config.set`, `config.patch`, `config.apply`, and shared mutation helpers with explicit redaction, timeout, recursion, and rejection semantics.
- **Limit to built-in validation:** Keep config validation and agent-write allowlists in core only, and document external validators as optional helpers that cannot enforce mandatory pre-apply policy.
- **Fold into broader preflight RFC:** Defer this specific hook until the broader config validation/preflight direction chooses one shared validation contract.

Yes at source level: current main exposes config write RPCs and plugin hooks, but there is no rejectable config pre-apply hook between validation and persistence. This is a feature/API gap rather than a failing runtime repro.

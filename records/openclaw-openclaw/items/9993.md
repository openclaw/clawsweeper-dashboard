## Summary

Current main substantially mitigates the reported agent incident through canonical validation, SecretRef preflight, conflict guards, and a narrow fail-closed agent allowlist, but it still provides no mandatory plugin-facing veto between pending config computation and persistence. No canonical replacement issue or PR owns that remaining API gap, and recent discussion explicitly keeps it open for a maintainer security and product decision.

## What This Changes

Add a synchronous plugin-facing pre-apply interception point that can inspect and reject pending gateway config writes before persistence.

## Best Possible Solution

Keep canonical schema, SecretRef, conflict, and agent-path protections non-bypassable, then add a documented typed control-plane veto only for explicitly approved config writers, with bounded execution, actor and changed-path context, recursion protection, and tests proving rejection leaves disk and active runtime state unchanged.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should third-party plugins be allowed to synchronously veto persisted config writes, and if so which writers and failure policy are in scope?

Rationale: The missing interception seam is source-proven, but plugin authority over operator configuration, recovery paths, timeout behavior, and fail-open or fail-closed handling cannot be safely selected without maintainer intent.

Likely owner: steipete

Owner reason: The strongest current-main feature-history signal spans the central config-write, hook, SDK, and agent-guard surfaces involved in this decision.

Owner confidence: high

Options:

- **Narrow control-plane veto (recommended):** Add a bounded typed veto for gateway config.set, config.patch, and config.apply after canonical validation and SecretRef preflight but before persistence.
- **Core validation only:** Keep veto authority in core and extend schemas, plugin-owned validation contracts, and agent mutation policy for newly identified unsafe changes.
- **Universal shared-write hook:** Intercept gateway, CLI, install, doctor, and SDK mutation helpers through one contract, accepting much higher recursion and recovery-path complexity.

## Reproduction Assessment

Yes, at the source level. Current plugins cannot register a mandatory decision between pending config validation and persistence, although the original agent-triggered write path is now narrowly allowlisted and core-validated.

## Solution Assessment

Unclear pending maintainer intent. A narrow gateway control-plane veto is safer and more maintainable than the proposed broad universal hook, while retaining core-only validation is also a legitimate product and security choice.

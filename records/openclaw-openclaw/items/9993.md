## Summary

Keep open. Current main has built-in config validation, SecretRef preflight, base-hash/destructive-array guards, and an agent-tool allowlist, but it still lacks the requested mandatory synchronous plugin/API-level veto before config mutations are persisted.

## What This Changes

The issue requests a synchronous config pre-apply hook that can validate and reject gateway config mutations before persistence.

## Best Possible Solution

Define a maintainer-approved synchronous config-write interception seam invoked by config.set, config.patch, config.apply, and shared mutation helpers after pending config computation plus built-in validation/preflight, but before persistence.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose a public synchronous config-write veto hook, and what trust, ordering, and failure contract should it use?

Rationale: The source gap is clear, but the hook would let plugins block persistent config writes across auth, provider, SecretRef, startup, and reload surfaces; automation cannot safely choose that public security boundary.

Likely owner: steipete

Owner reason: The issue discussion already includes steipete's review keeping this open and the current central source lines trace to the same recent area history.

Owner confidence: medium

Options:

- **Design narrow config-write hook (recommended):** Define a config-specific plugin/API contract with current and pending config, action, changed paths, actor metadata, base hash, typed rejection, timeouts, recursion protection, and regression tests.
- **Fold into durable-write hook:** Make this a config-specific case of the broader before-persistence-write design, accepting a larger cross-state API discussion before this issue is implemented.
- **Reject plugin veto:** Keep config safety in built-in validation, doctor, rollback, and allowlists only, and document that plugins cannot synchronously block core config writes.

## Reproduction Assessment

Yes, at source level: the hook catalog and public hook docs lack a config pre-apply hook, and config.set/config.patch/config.apply validate/preflight before calling the shared write path without a plugin veto. I did not run a live crash repro because this is a missing API boundary rather than a narrow runtime bug.

## Solution Assessment

Unclear until maintainer design review. A config-write interception point is plausible, but the best solution must choose between a config-specific hook and a broader durable-write hook while defining ordering, security, and rollback semantics.

## Summary

Keep open. Current main has stronger built-in config validation, SecretRef preflight, base-hash/destructive-array guards, and agent-tool write allowlists, but it still lacks the requested mandatory synchronous plugin/API-level veto before config mutations are persisted.

## What This Changes

Requests a synchronous config pre-apply hook that lets plugins or validators inspect and reject pending Gateway config changes before they are written.

## Best Possible Solution

Define a maintainer-approved config mutation interception contract invoked by config.set, config.patch, config.apply, and shared mutation helpers after pending-config computation plus built-in validation/preflight but before persistence, with typed rejection and regression tests proving disk and runtime config remain unchanged on rejection.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose a synchronous public plugin/API veto point for persistent config writes, and what trust/failure semantics should it use?

Rationale: This cannot be safely resolved by code shape alone because the hook can inspect or block sensitive auth/provider config, can affect Gateway availability, and would become a plugin API compatibility contract.

Likely owner: steipete

Owner reason: steipete already provided the prior keep-open/product-routing review and has adjacent config safety history.

Owner confidence: medium

Options:

- **Design the config-write veto API (recommended):** Define a typed pre-persistence hook with explicit ordering, timeouts, SecretRef/redaction rules, actor metadata, fail-closed behavior, and coverage across config.set, config.patch, config.apply, and shared mutation helpers.
- **Keep validation built in only:** Reject the public hook direction and continue improving core validation/doctor rules, leaving external config guards as advisory tools that agents must call explicitly.
- **Fold into broader preflight RFC:** Defer this hook until the broader config validation/preflight framework chooses one boundary for boot-time checks, config writes, and plugin-owned validators.

## Reproduction Assessment

Yes, at source level. The current hook catalog and config write paths show built-in validation/preflight but no mandatory plugin/API-level pre-persistence config veto.

## Solution Assessment

Yes as a direction, but not as an automatic fix. A synchronous config-write interception point is the right seam if external validators must be impossible to bypass, while wrapper scripts and before_tool_call remain too narrow.

## Summary

Keep open: current main has strong built-in schema, clobber, SecretRef, concurrency, and agent-write safeguards, but it still lacks a mandatory plugin-facing veto between pending-config validation and persistence. The remaining work is an intentional Plugin SDK and security-boundary decision, not an obsolete request or a safe autonomous repair.

## What This Changes

Add a synchronous plugin-facing interception point that can inspect and reject pending configuration changes before persistence.

## Best Possible Solution

Define one trusted, typed, inspect-and-reject config-write gate at the shared transactional commit boundary, after canonical merge/schema/SecretRef checks but before persistence, with sanitized payloads, bounded deterministic execution, explicit recovery bypass rules, actor metadata, and tests proving rejection leaves disk and active runtime state unchanged.

## Security Review

Status: needs_attention

Summary: The requested API is security-sensitive because it combines plugin access to potentially credential-bearing configuration with authority to block persistent control-plane writes.

Concerns:

- **[high] Constrain sensitive configuration exposure:**
  - body: A pre-write hook must not automatically disclose resolved secrets, tokens, or unrelated credential-bearing subtrees to every installed handler; define redaction, capability declaration, and least-privilege payload rules.
  - confidence: 0.94
- **[high] Preserve an operator recovery path:**
  - body: A broken, timed-out, or malicious trusted plugin must not permanently block doctor repairs, plugin disablement, or emergency configuration recovery; define bounded execution and an auditable bypass or safe-mode path.
  - confidence: 0.93
- **[medium] Avoid recursion and competing mutation ownership:**
  - body: If handlers can write config or modify the pending value during the veto, they can recurse or create conflicting normalization rules; prefer an inspect-and-reject initial contract.

## Risks / Open Questions

- A hook receiving full current and pending configuration could expose resolved credentials, tokens, or sensitive channel and auth material to every registered handler unless the payload and permissions are deliberately constrained.
- Fail-closed hook errors, timeouts, or plugin startup failures could block operator repair, doctor migrations, disabling the broken plugin, or other recovery writes and create an availability loop.
- Hooking only config.patch and config.apply would leave config.set, CLI writers, doctor migrations, plugin mutation helpers, and other shared write paths with inconsistent policy enforcement.
- Allowing plugins to mutate the pending payload as well as veto it would create competing config normalization and migration ownership; the safest initial contract is likely inspect-and-reject only.

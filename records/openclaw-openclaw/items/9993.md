## Summary

Keep open. Current main and the latest release have stronger built-in validation, SecretRef preflight, base-hash/destructive-array guards, and an agent-tool allowlist, but the linked config-guard workaround still cannot enforce the requested mandatory synchronous plugin/API-level veto before config writes persist.

## What This Changes

Requests a mandatory synchronous config pre-apply hook that lets validators inspect and reject config.set, config.patch, and config.apply changes before persistence.

## Best Possible Solution

Define a maintainer-approved config mutation interception contract invoked by config.set, config.patch, config.apply, and shared mutation helpers after pending-config computation plus built-in validation/preflight but before persistence, with typed rejection and tests proving disk and runtime config remain unchanged on rejection.

Kind: security_boundary

Question: Should OpenClaw expose a synchronous public plugin/API veto point for persistent config writes, and what trust, redaction, timeout, and failure semantics should it use?

Rationale: Automation can prove the source gap, but it cannot safely choose a plugin API contract that can observe or block sensitive auth/provider config and affect Gateway availability.

Likely owner: steipete

Owner reason: steipete provided the prior keep-open product-routing review and has recent adjacent config-write safety history.

Owner confidence: high

Options:

- **Design the config-write veto API (recommended):** Define a typed pre-persistence hook with explicit ordering, timeouts, redaction/SecretRef rules, actor metadata, fail-closed behavior, and coverage across config.set, config.patch, config.apply, and shared mutation helpers.
- **Keep validation built in only:** Reject the public hook direction and continue improving core validation, doctor, and gateway-tool guards while leaving external validators as advisory tools agents must call explicitly.
- **Fold into broader preflight RFC:** Defer this hook until the broader validation/preflight framework chooses one boundary for boot-time checks, config writes, and plugin-owned validators.

## Reproduction Assessment

Yes, at source level. Current main's hook catalog and config write paths show built-in validation/preflight but no mandatory plugin/API-level pre-persistence config veto.

## Solution Assessment

Yes as a direction, but not as an automatic fix. A synchronous config-write interception point is the right seam if external validators must be impossible to bypass, while wrapper scripts and before_tool_call remain too narrow.

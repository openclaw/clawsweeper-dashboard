## Summary

Keep open: current main has validated, SecretRef-preflighted, base-hash-guarded configuration writes, but still has no mandatory plugin-facing decision point before persistence, and no related merged PR owns that remaining capability.

## What This Changes

Add a synchronous plugin-facing interception point that can validate and reject pending gateway configuration changes before they are persisted.

## Best Possible Solution

Define an opt-in trusted configuration-mutation policy for config.set, config.patch, and config.apply that runs after built-in validation and SecretRef preflight but before persistence, receives redacted structured context and changed paths, has bounded timeout and recursion behavior, and cannot block doctor, recovery, setup, or host-owned security writes.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which host-owned configuration mutations, if any, may installed plugins synchronously veto?

Rationale: The answer determines recovery availability, secret exposure, compatibility guarantees, and whether the API can honestly promise that relevant writes cannot bypass validation.

Likely owner: steipete

Owner reason: The live discussion shows the clearest product-routing engagement and an explicit keep-open assessment of the remaining public API gap.

Owner confidence: medium

Options:

- **Gateway RPC Policy (recommended):** Expose a trusted typed veto for config.set, config.patch, and config.apply while excluding doctor, recovery, setup, and host-owned security writes.
- **Global Write Policy:** Invoke plugins from the shared configuration mutation layer and accept that plugin failures can block every host configuration and recovery path.
- **No Mandatory Veto:** Keep built-in validation authoritative and retain optional before_tool_call policies or explicit plugin-owned mutation APIs without a new interceptor.

## Reproduction Assessment

Yes at source level: current gateway configuration RPCs and shared write paths can be traced through validation to persistence, and no plugin pre-commit decision call exists. A live gateway crash reproduction was not necessary to establish this API gap.

## Solution Assessment

No, not exactly as proposed: the capability remains useful, but an unrestricted global hook would give plugin code control over recovery and security-sensitive host writes. A trusted, RPC-scoped policy with redacted context is the safer maintainable direction.

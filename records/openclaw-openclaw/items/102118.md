## Summary

Keep open: the same merge blocker remains at the current head. The patch still starts from a registry helper that clones and sorts every task before the new top-K selection runs, and the PR still lacks real large-registry behavior proof.

## What This Changes

The branch adds quickselect-based partial sorting to Gateway `tasks.list` so it sorts only the requested page window after filtering.

## Best Possible Solution

Implement a bounded task-registry or Gateway listing path that filters and selects the requested `tasks.list` page without calling a helper that pre-sorts every task, while preserving the current response shape and cursor/order semantics.

## Reproduction Assessment

Yes, at source level: the PR still calls `listTaskRecords()` inside `tasks.list`, and current `listTaskRecords()` clones and sorts every task before returning. I did not run a live 10k-record benchmark in this read-only review.

## Solution Assessment

No, this is only a partial mitigation: it avoids the second full sort but leaves the registry helper's full sort in the polling path. The better fix is to expose or use an unsorted or bounded registry traversal for this listing path, then apply top-K selection before paging.

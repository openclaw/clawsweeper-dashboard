## Summary

Keep this PR open for gateway-owner review: it still applies the Control UI browser-origin policy to every Origin-bearing WebSocket before the handshake, while the established post-handshake path is client-aware. The updated raw-socket transcript proves the basic 101/403 behavior at the current head, but it does not prove that non-Control-UI Origin-bearing clients or trusted-proxy requests preserve their existing behavior.

## What This Changes

The PR adds a `WebSocketServer.verifyClient` hook that reuses `checkBrowserOrigin` to reject disallowed Origin headers before the HTTP 101 upgrade, with focused tests and gateway-security documentation.

## Best Possible Solution

Retain pre-handshake rejection only after a gateway owner confirms and encodes the intended client scope; otherwise keep the existing client-aware policy boundary and add pre-upgrade coverage only where that boundary can be identified safely.

## Summary

Keep open. Current main still lets `reserveTokensFloor + softThresholdTokens` make the memory-flush/preflight token gate non-positive, and no same-repository fix has merged yet; related open PRs touch adjacent reserve/threshold policy but do not make this issue obsolete.

## What This Changes

The issue asks for memory flush and related preflight compaction gates to still trigger when `reserveTokensFloor` is equal to the context window instead of producing a non-positive threshold.

## Best Possible Solution

Land a maintainer-approved fix that centralizes a context-window-aware positive threshold or effective reserve for memory flush and token-based preflight compaction, with regression coverage for `reserveTokensFloor >= contextWindowTokens` and explicit compatibility behavior.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence reproduction path: with positive token usage and `reserveTokensFloor + softThresholdTokens >= contextWindowTokens`, the shared gate returns null and token-based memory flush/preflight compaction skips.

## Solution Assessment

Unclear as final policy. A shared context-window-aware effective threshold is the narrow technical layer, but maintainers still need to choose clamp, warning, validation, or doctor behavior for existing oversized reserve configs.

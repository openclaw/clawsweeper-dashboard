## Summary

Current main still has the reported non-positive memory-flush threshold path, so this is not safe to close as implemented. The remaining work is a maintainer policy choice because the fix affects existing reserve-floor and memory-flush timing semantics.

## What This Changes

The issue reports that token-based memory flush can fail when `reserveTokensFloor` is configured equal to the active context window.

## Best Possible Solution

Use one canonical effective-reserve calculation for compaction and memory-flush gates, then add focused regression coverage for `reserveTokensFloor >= contextWindowTokens` without changing unrelated memory defaults.

Options:

- **Reuse effective reserve budget (recommended):** Route memory flush and preflight gates through the same capped reserve calculation used by embedded compaction, with tests for oversized floors and normal large-window behavior.
- **Doctor-repair invalid floors:** Keep runtime strict and add a doctor/config repair path that rewrites `reserveTokensFloor >= contextWindowTokens` before runtime gates consume it.
- **Defer to adaptive threshold work:** Let https://github.com/openclaw/openclaw/pull/81417 or a successor settle broader memory-flush threshold policy before fixing this narrow edge case.

## Reproduction Assessment

Yes, at source level: passing `reserveTokensFloor` equal to `contextWindowTokens` makes the computed memory-flush threshold non-positive, and current main returns false from the flush gate. I did not run a live long-session reproduction in this read-only cleanup pass.

## Solution Assessment

No single proposed fix is proven best yet. The maintainable direction is to share the existing effective-reserve/cap policy across compaction and memory-flush gates, or explicitly choose a doctor/config repair path for invalid floors.

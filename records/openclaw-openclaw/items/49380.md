## Label Justifications

- `P2`: This is a normal-priority status/session-state accuracy bug for plugin context engines; sessions continue, but the operator-visible compaction counter is wrong.
- `impact:session-state`: The displayed session compaction state can drift from actual context-engine compaction activity.

## Summary

Keep open: current main and the latest release still lack a plugin-facing way for context engines that own compaction to report successful after-turn or maintenance compactions into the session counter that `/status` renders. The related items are duplicates, broader design follow-ups, or adjacent observability changes rather than a completed fix for this count path.

## What This Changes

Add a plugin-facing way for context engines that own compaction to report successful after-turn or proactive compactions so `/status` and `session_status` compaction counts reflect them.

## Best Possible Solution

Add one narrow, additive plugin lifecycle reporting contract that lets context engines report successful owned compactions to the canonical session store, then keep `/status` and `session_status` rendering from that counter.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which plugin-facing compaction reporting contract should OpenClaw support for context engines that own compaction: an `afterTurn` notification callback, an `afterTurn` result shape, or a status/stats query surface?

Rationale: The bug is source-reproducible, but the fix changes the public context-engine/plugin lifecycle contract and needs maintainer intent before implementation.

Likely owner: jalehman

Owner reason: They introduced and extended the context-engine plugin API that would need the new lifecycle reporting contract.

Owner confidence: high

Options:

- **Add an afterTurn callback (recommended):** Pass a narrow callback in `afterTurn` and maintenance params so engines can increment the canonical session counter only after successful owned compactions.
- **Return compaction metadata:** Allow `afterTurn` or maintenance to return a small result object, but this broadens existing lifecycle signatures for plugin implementations.
- **Query engine stats:** Let status query optional engine stats, but reconcile carefully so it does not create a second source of truth beside session state.

## Reproduction Assessment

Yes, source-level. `afterTurn` and turn maintenance can run plugin-owned background compactions but currently have no compaction notification path, while `/status` renders only `SessionEntry.compactionCount`.

## Solution Assessment

Unclear until maintainers choose the plugin API shape. A callback is the narrowest likely repair because it keeps the session store canonical and lets plugins report only successful owned compactions.

- `impact:session-state`: The report is about drift between plugin-owned context compaction state and the persisted session status counter.

## Summary

Keep open: current main still has the source-level gap the issue describes, because plugin-owned context-engine lifecycle work can compact in `afterTurn` or maintenance while `/status` still renders only the persisted session-store counter. Recent Codex logging and `/status` outcome work are adjacent, but they do not add a plugin compaction reporting contract or make plugin-private leaf compactions update `SessionEntry.compactionCount`.

## What This Changes

The issue requests that `/status` reflect compactions performed by plugin-owned context engines instead of showing the session-store compaction count as zero.

## Best Possible Solution

Define an additive context-engine reporting contract, persist confirmed plugin-owned compaction deltas into the canonical session counter, and cover the built-in, manual, overflow, Codex app-server, and plugin lifecycle paths without double-counting.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence reproduction path: an `ownsCompaction` engine can compact in `afterTurn`, but that hook returns `Promise<void>` and status reads only `SessionEntry.compactionCount`; I did not run a live third-party engine session in this read-only review.

## Solution Assessment

No final implementation shape is proven best yet. The reported gap is valid, but maintainers still need to choose the stable plugin API/reporting contract before this should become a code-only repair.

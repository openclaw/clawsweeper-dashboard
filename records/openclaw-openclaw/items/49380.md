## Summary

Keep open: current main and v2026.6.11 still lack a plugin-facing way for context engines that own compaction to report successful after-turn or maintenance compactions into the session counter rendered by `/status`. The source-level gap is clear, but choosing the plugin lifecycle/API shape needs maintainer intent.

## What This Changes

Report that plugin context engines with `ownsCompaction` cannot report successful after-turn or maintenance compactions into `/status`'s persisted compaction counter.

## Best Possible Solution

Add one narrow plugin lifecycle reporting contract that lets context engines report successful owned compactions to the canonical session store, then keep `/status` and `session_status` rendering from that counter.

Rationale: The source gap is clear, but the fix changes the public context-engine/plugin lifecycle contract and needs maintainer intent before implementation.

Likely owner: jalehman

Owner confidence: high

Options:

- **Add an afterTurn callback (recommended):** Pass a narrow callback in `afterTurn` and maintenance params so engines can increment the canonical session counter only after successful owned compactions.
- **Return compaction metadata:** Allow `afterTurn` or maintenance to return a small result object, accepting a broader lifecycle signature change for plugin implementations.
- **Query engine stats:** Let status query optional engine stats, but reconcile carefully so it does not create a second source of truth beside session state.

## Reproduction Assessment

Yes, source-level. `afterTurn` and turn maintenance can run plugin-owned background compactions but currently have no compaction notification path, while `/status` renders only `SessionEntry.compactionCount`.

## Solution Assessment

Unclear until maintainers choose the plugin API shape. A callback is the narrowest likely repair because it keeps the session store canonical and lets plugins report only successful owned compactions.

## Label Justifications

- `P2`: The reported drift makes status inaccurate for plugin context-engine sessions, but it does not stop sessions from running.
- `impact:session-state`: The displayed session compaction counter can diverge from the context engine's actual compaction activity.

## Summary

Keep open: current main and v2026.6.11 still lack a way for plugin-owned `afterTurn` or maintenance compactions to update the session compaction counter rendered by `/status`. The source-level gap remains real, but the fix changes the plugin lifecycle/API contract and needs maintainer direction.

## What This Changes

Plugin context engines that own compaction should be able to report successful compactions so `/status` does not keep showing `Compactions: 0`.

## Best Possible Solution

Add one narrow plugin lifecycle reporting contract that lets context engines report successful owned compactions to the canonical session store, then keep `/status` and `session_status` rendering from that counter.

Question: Which plugin-facing compaction reporting contract should OpenClaw support for context engines that own compaction: an `afterTurn`/maintenance callback, a lifecycle return value, or a status/stats query surface?

Rationale: The source-level bug is clear, but the fix changes the public context-engine/plugin lifecycle contract and needs maintainer intent before implementation.

Likely owner: jalehman

Owner reason: jalehman authored the context-engine API and transcript maintenance contract that would need the new reporting shape.

Owner confidence: high

Options:

- **Add a lifecycle callback (recommended):** Pass a narrow host callback through `afterTurn` and maintenance params so engines can increment the canonical session counter only after successful owned compactions.
- **Return compaction metadata:** Allow `afterTurn` or maintenance to return a small result object, but this broadens existing lifecycle signatures for plugin implementations.
- **Query engine stats:** Let status query an optional engine stats method, but reconcile carefully so it does not create a second source of truth beside session state.

## Reproduction Assessment

Yes. Source inspection shows `afterTurn` has no result/callback, maintenance returns only transcript rewrite state, and `/status` formats only `SessionEntry.compactionCount`; I did not run a live third-party context engine in this read-only review.

## Solution Assessment

Unclear until maintainers choose the plugin API shape. A narrow callback is the best-looking option because it keeps the session store canonical and avoids making `/status` query plugin-private state.

## Label Justifications

- `P2`: This is a normal-priority status accuracy bug for plugin context engines; sessions continue, but the operator-visible counter is wrong.
- `impact:session-state`: The displayed session compaction state can drift from actual plugin context-engine compaction activity.

## Summary

Keep open: current main still has no plugin-facing path for owned context-engine compactions that happen in `afterTurn` or maintenance to update the canonical session compaction counter, and the related open status-outcome PR explicitly does not fix this count accuracy gap.

## What This Changes

The issue requests a way for plugin-owned context-engine compactions performed after turns to increment the session compaction counter shown by `/status`.

## Best Possible Solution

Add one narrow plugin lifecycle reporting contract that lets owning context engines report successful compactions into the canonical session store, then keep `/status` and `session_status` rendering from that canonical counter.

Question: Which plugin-facing compaction reporting contract should OpenClaw support for context engines that own compaction: an `afterTurn` notification callback, an `afterTurn` result shape, or a status/stats query surface?

Rationale: The bug is source-reproducible, but the fix changes the context-engine/plugin lifecycle contract and needs owner intent before implementation.

Likely owner: jalehman

Owner reason: They authored the context-engine plugin API and maintenance lifecycle where this reporting contract would live.

Owner confidence: high

Options:

- **Add a notification callback (recommended):** Pass a narrow `notifyCompaction(count?)` callback in post-turn and maintenance params so engines can increment the canonical session counter only after successful owned compactions.
- **Return compaction metadata:** Allow `afterTurn` to return a small result object, trading a broader signature change for direct host reconciliation.
- **Query engine stats:** Add an optional stats surface for status rendering, but it must avoid creating a second source of truth beside session state.

## Reproduction Assessment

Yes, source-level: plugin-owned `afterTurn` and maintenance can perform compactions but have no channel to update `SessionEntry.compactionCount`, while `/status` renders only that field.

## Solution Assessment

Unclear until maintainers choose the plugin API shape; a callback is the narrowest likely repair because it preserves the session store as the canonical counter while letting plugins report only successful owned compactions.

## What This Changes

The issue requests that post-core plugin payload validation use the same `openclaw.extensions` entrypoint semantics as the plugin loader, so a stale unrelated npm `main` field cannot block gateway readiness.

## System Context

OpenClaw discovers a plugin’s extension entrypoint from package metadata, activates it in the gateway, and runs post-update payload checks before reporting startup ready. If the loader and the readiness check resolve different metadata fields, a functioning plugin can become a startup blocker.

## Architecture Diagram

flowchart LR
  A[Plugin package metadata] --> B[Plugin loader]
  A --> C[Post-update payload smoke check]
  B --> D[Loaded extension]
  C --> E[Startup migration gate]
  D --> F[Gateway readiness]
  E --> F

## Best Possible Solution

Make the payload smoke check validate the extension entrypoint through the same canonical resolution path as the loader, with a focused regression test covering a valid `openclaw.extensions` entry plus a stale unrelated npm `main`; preserve fatal readiness failures only for payloads the loader itself cannot resolve.

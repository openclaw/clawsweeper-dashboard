## Summary

Keep open: the configuration-reference gap is real, but this wording overstates current Gateway behavior because current main intentionally allows the reserved direct-loopback `gateway-client` backend path under `gateway.auth.mode: "none"` while rejecting browser-origin or otherwise non-exempt backend claims.

## What This Changes

Updates `docs/gateway/configuration-reference.md` to warn that `gateway.auth.mode: "none"` does not generate a shared token and recommends token mode for backend clients.

## Best Possible Solution

Merge a narrower configuration-reference note that says auth-none does not generate a shared token while preserving the reserved direct-loopback `gateway-client` backend exception and naming custom, remote, browser-origin, or otherwise non-exempt clients as the cases that need token/password auth.

## Reproduction Assessment

Yes. Current source and tests show auth-none local reserved backend clients can connect without device identity, while browser-origin backend claims still fail with `device identity required`.

## Solution Assessment

No as written. The maintainable fix is a narrower docs note that distinguishes the absence of a generated shared token from the supported direct-local backend exception.

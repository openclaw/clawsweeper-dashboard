## Summary

Keep open. The configuration-reference docs gap is real because `auth.mode: "none"` does not expose a shared token, but the PR wording overgeneralizes by saying backend clients will fail when current Gateway still supports the reserved direct-local `gateway-client` backend path under auth-none.

## What This Changes

The PR expands the `gateway.auth.mode: "none"` entry in the Gateway configuration reference to warn that no shared token is generated and to recommend token mode for backend clients.

## Best Possible Solution

Merge a narrower docs note that says auth-none does not provide a shared token while preserving the direct-local reserved `gateway-client` backend exception and warning only about custom, remote, browser-origin, or otherwise non-exempt clients.

## Reproduction Assessment

Yes. Source and compatibility tests show auth-none does not provide shared token/password auth, while direct-local reserved `gateway-client` backend connects can still skip device identity and browser-origin backend connects still fail with `device identity required`.

## Solution Assessment

No as written. The best fix is a narrower configuration-reference note that distinguishes the absence of a shared token from the supported local backend exception.

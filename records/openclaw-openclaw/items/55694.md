## Summary

Keep open: current main and latest release still leave the reported default-path failed-tool loop possible because rolling loop detection is opt-in, validation errors become model-visible tool errors, and channel-visible status/output policy still needs maintainer-approved defaults.

## What This Changes

The issue requests retry limits, deterministic tool-error classification, loop breaking, and quieter channel reporting when failed tool calls repeat.

## Best Possible Solution

Keep this open until core has a maintainer-approved default policy that classifies deterministic tool failures, blocks runaway repeated failures, and emits at most one structured channel-visible failure message.

## Reproduction Assessment

Yes, at source level: invalid tool arguments are converted into model-visible error tool results, and the rolling loop detector still does not block by default. I did not run a live Feishu or Telegram replay in this read-only pass.

## Solution Assessment

Unclear as a direct implementation request: extending existing loop-detection, terminal-error, and channel-visible failure surfaces is likely right, but default thresholds and user-facing stop behavior need maintainer policy first.

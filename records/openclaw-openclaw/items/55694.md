## Label Justifications

- `P1`: The issue describes an active agent/channel loop that can require manual intervention and repeatedly spend runtime after tool failures.
- `impact:message-loss`: The reported failure mode includes repeated channel-visible messages after tool or validation failures, which can spam or misrepresent delivery state.
- `impact:crash-loop`: The underlying repeated tool-call loop can continue until the session is manually stopped or resource limits are hit.

## Summary

Keep open: current main has partial loop-safety work, but the reported default-path failure mode remains credible because rolling tool-loop detection is still disabled by default and deterministic validation/tool failures are returned to the model as ordinary tool-result content that can be retried and repeated into channel messages.

## What This Changes

Request to prevent agents from repeatedly retrying failed tool calls and sending repeated channel messages after validation or tool failures.

## Best Possible Solution

Define a maintainer-approved default failure-loop policy in core that classifies deterministic validation/tool errors, caps repeated no-progress failures, and emits one structured user-visible failure message without breaking legitimate polling or recovery.

Unclear: the right fix should extend the existing loop-detection and message-suppression surfaces, but default blocking semantics, thresholds, and channel-visible failure behavior require maintainer product judgment.

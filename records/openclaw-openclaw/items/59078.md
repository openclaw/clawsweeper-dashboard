## Summary

Keep open: current main still treats skill `requires.env` readiness as satisfied only by process env, `skills.entries.<skill>.env`, or a matching `primaryEnv` API key, so file-backed skill credentials can still be reported as missing. The broader setup-hook issue overlaps but does not settle this credential-readiness/status contract.

## What This Changes

Skill readiness/status should not mark a skill as needing setup when its credentials are available through skill-owned config files rather than declared environment variables.

## Best Possible Solution

Define a security-reviewed declarative skill credential-readiness contract and wire it consistently through status, runtime eligibility, CLI/UI, doctor, docs, and tests without arbitrary status-time skill code execution.

Options:

- **Add declarative readiness sources (recommended):** Define a manifest/SDK contract for env-or-file credential readiness with path/source limits, redacted diagnostics, and shared status/runtime/doctor behavior.
- **Allow skill-owned status/setup hooks:** Let skills report or prepare setup with a reviewed consent, timeout, logging, sanitizer, and execution model, accepting the larger host-code execution surface.
- **Keep env-only readiness:** Document that `requires.env` means env/config-apiKey only and ask skills with file fallbacks to model that differently or move to an external plugin flow.

Yes at source level. A skill with `requires.env` remains ineligible unless the required key is present in process env, per-skill config env, or the matching `primaryEnv` API-key slot; I did not run a live UI reproduction in this read-only pass.

## Solution Assessment

Unclear until maintainers choose the credential-readiness contract. A declarative env-or-file credential source appears safer than executing arbitrary skill code during routine status checks.

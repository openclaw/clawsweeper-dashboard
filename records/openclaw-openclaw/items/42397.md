## Summary

Keep open: current main and the latest stable release still support only a run-level `heartbeat.model`; `HEARTBEAT.md` tasks are parsed as `name`/`interval`/`prompt` and batched into one heartbeat prompt, so per-task model selection remains a real product/API gap rather than cleanup.

## What This Changes

Request to let individual `HEARTBEAT.md` task blocks select or escalate to a different model than the run-level `heartbeat.model` setting.

## Best Possible Solution

Define a narrow heartbeat task model-selection contract, then implement it across task parsing, due-task grouping or run splitting, provider/model validation, session-state isolation, docs, and regression proof without letting a task-specific model bleed into later main-session turns.

- **Fold cost control into cron:** Keep HEARTBEAT.md tasks model-agnostic and direct model-specific scheduled work toward the cron model-override design tracked in https://github.com/openclaw/openclaw/issues/42631.

## Reproduction Assessment

Yes, source-level for the missing feature: current main and `v2026.6.11` parse only `name`/`interval`/`prompt` and apply one `heartbeat.model` to the whole heartbeat run. This is not a broken existing-behavior bug reproduction.

## Solution Assessment

Unclear until maintainers choose the public contract. A HEARTBEAT task-level model hint is plausible for the reported use case, but plugin per-turn routing and cron-level overrides are adjacent alternatives with different ownership and compatibility tradeoffs.

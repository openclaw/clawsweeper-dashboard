## Summary

Keep open for a maintainer product/API decision: current main still parses heartbeat tasks as only name/interval/prompt, batches due tasks into one model call, and supports only one heartbeat model override per heartbeat run; the existing plugin hook can route a whole turn but does not provide the requested per-task execution boundary.

## What This Changes

Request to add HEARTBEAT.md task-level model hints or escalation so selected heartbeat tasks can use a different model than the run-level heartbeat model.

## Best Possible Solution

Maintainers should choose a single contract first: document plugin/per-turn routing for whole heartbeat ticks, or add a narrow native HEARTBEAT.md task model field that splits due tasks by effective model while preserving shared session state.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw core support native per-task model hints in HEARTBEAT.md, or should heartbeat model routing remain per-turn and plugin-owned unless a missing generic seam is proven?

Rationale: Current main lacks the requested task-level boundary, but adding it would create public HEARTBEAT.md syntax and model/session precedence rules; the existing before_model_resolve hook covers whole-turn routing but not exact per-task escalation.

Likely owner: steipete

Owner reason: The decision is primarily about product boundary between core HEARTBEAT.md syntax and plugin-owned model routing, and steipete introduced the current model-resolution hook seam.

Owner confidence: medium

Options:

- **Keep routing plugin-owned for now (recommended):** Document that heartbeat ticks are routed as one model-selected turn and use before_model_resolve or ClawHub plugins for routing policy unless maintainers approve native task splitting.
- **Add native task model hints:** Define model/provider task fields, split or group due tasks by effective model, and add docs/tests for precedence, timestamps, and shared-session restoration.
- **Fold into scheduled-job routing:** Use https://github.com/openclaw/openclaw/issues/42631 as the canonical scheduled model-override track and avoid a separate heartbeat-specific routing syntax until cron and heartbeat semantics converge.

Yes, source-level. Current main parses only name/interval/prompt tasks, batches due HEARTBEAT.md tasks into one prompt, and passes one heartbeatModelOverride for the whole run.

## Solution Assessment

Unclear until maintainers choose the product contract. Native HEARTBEAT.md syntax is one plausible way to solve exact per-task escalation, while plugin/per-turn routing is the leaner existing path for whole heartbeat ticks.

## Summary

Keep open for maintainer product/API decision: current main still parses HEARTBEAT.md tasks as name/interval/prompt, batches due tasks into one heartbeat turn, and applies only one heartbeat model override for the whole run.

## What This Changes

Request per-task model/provider hints in HEARTBEAT.md so selected heartbeat tasks can use a different model than the heartbeat run default.

## Best Possible Solution

Define one explicit scheduled model-routing contract: either document that HEARTBEAT.md tasks share one heartbeat model and route finer control through plugins/cron, or add a narrow task model field with tested session and timestamp semantics.

Options:

- **Keep routing plugin- or job-owned (recommended):** Document that HEARTBEAT.md due tasks share one heartbeat model today and route finer-grained scheduled model choices through before_model_resolve plugins or the open cron/job-level override track.

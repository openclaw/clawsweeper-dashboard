## Summary

Keep open for maintainer product/API decision: current main supports only a heartbeat-wide model and whole-turn plugin overrides, while exact per-task HEARTBEAT.md model selection would add public task syntax and session/model precedence.

## What This Changes

Requested support for choosing a different model for individual HEARTBEAT.md tasks instead of using one heartbeat-wide model.

## Best Possible Solution

Maintainers should choose one durable contract: keep heartbeat routing whole-turn and plugin-owned, fold scheduled model control into the cron/job override track, or add native HEARTBEAT.md task model/provider fields that preserve task timestamps and session state.

Rationale: Current main lacks the requested per-task heartbeat boundary, but adding it changes public task-file syntax, model precedence, and shared-session behavior; automation should not choose that product contract.

Owner confidence: medium

Options:

- **Fold into scheduled-job routing (recommended):** Use the open cron/job-level model override track as the canonical way to run different scheduled work on different models, avoiding another heartbeat-specific routing syntax.
- **Add native HEARTBEAT.md task hints:** Define task-level model/provider fields, group or split due tasks by effective model, and cover precedence, validation, timestamps, and session restoration in docs and tests.
- **Keep whole-turn plugin routing only:** Document that before_model_resolve can route an entire heartbeat turn and close the exact per-task split unless a missing generic plugin seam is approved.

## Summary

Keep open for maintainer product/API decision: current main and the latest release still support only one heartbeat model per heartbeat run, while HEARTBEAT.md tasks are parsed as name/interval/prompt and batched into one prompt; the existing plugin hook can route a whole turn but does not provide the requested native per-task heartbeat execution boundary.

## What This Changes

Request to let individual HEARTBEAT.md task blocks choose or escalate the model instead of applying one heartbeat.model to the whole heartbeat run.

## Best Possible Solution

Maintainers should choose one contract: document plugin/per-turn routing as the supported path, fold this into a scheduled-job model override design, or add native HEARTBEAT.md task model/provider fields with explicit grouping, validation, and session-state restoration.

Options:

- **Fold into scheduled routing first (recommended):** Use the open cron/job-level model override design as the canonical scheduled-model-routing contract before adding another HEARTBEAT.md-specific syntax.
- **Add native HEARTBEAT.md hints:** Define model/provider fields on task blocks, group or split due tasks by effective model, and add docs/tests for validation, timestamps, and session restoration.
- **Keep routing plugin-owned:** Document that heartbeat ticks are one model-routed turn today and steer task-dependent routing to before_model_resolve or ClawHub plugins unless a missing core seam is proven.

Yes, source-level. Current main parses HEARTBEAT.md tasks as name/interval/prompt only, batches due tasks into one prompt, and resolves one heartbeat model override for the whole run.

## Solution Assessment

Unclear until maintainers choose the product contract. A one-off HEARTBEAT.md model field is plausible for this issue, but the safer maintainable path may be a generic scheduled-routing contract or documented plugin-owned whole-turn routing.

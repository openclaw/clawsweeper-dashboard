## Summary

Keep open for maintainer product/API decision: current main supports one heartbeat model override per heartbeat turn, but HEARTBEAT.md tasks still have no model/provider field and due tasks are batched into one model call.

## What This Changes

The issue requests per-task HEARTBEAT.md model hints or escalation so selected periodic heartbeat tasks can run on a different model than the rest of the heartbeat run.

## Best Possible Solution

Maintainers should choose the permanent contract first; if native support is accepted, add task-level model/provider parsing, model-scoped due-task execution, session-state isolation, docs, and focused heartbeat runner tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw core support native per-task model hints in HEARTBEAT.md, or should heartbeat model routing remain per-turn and plugin-owned?

Rationale: Current main lacks the requested native task boundary, while the existing before_model_resolve hook and ClawHub plugin path cover only whole-run routing; choosing native syntax affects public HEARTBEAT.md semantics, model precedence, and session-state behavior.

Likely owner: steipete

Owner reason: steipete has the clearest history on the model-routing product boundary and plugin-owned hook seam used to compare against a native HEARTBEAT.md contract.

Owner confidence: high

Options:

- **Keep routing per-turn/plugin-owned (recommended):** Document that heartbeat ticks currently route as one model-resolved turn and use before_model_resolve or ClawHub plugins for routing policy unless maintainers approve a native task split.
- **Add native HEARTBEAT.md task hints:** Define model/provider task fields, split or group due tasks by effective model, and add docs/tests for precedence, timestamps, and session restoration.
- **Fold into scheduled-job routing:** Make https://github.com/openclaw/openclaw/issues/42631 the canonical scheduled model override design and avoid a separate heartbeat-specific routing syntax until cron and heartbeat semantics converge.

## Reproduction Assessment

Yes, source-level: current main parses only name/interval/prompt tasks, batches due HEARTBEAT.md tasks into one prompt, and passes a single heartbeatModelOverride for the entire run. This is a missing feature rather than a broken existing behavior.

## Solution Assessment

Unclear until maintainers choose the product contract. Plugin per-turn routing is the lean existing path, while exact per-task heartbeat escalation requires a native task execution boundary or a broader scheduled-work routing design.

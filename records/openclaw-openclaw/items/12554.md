## Summary

Keep open: current main and v2026.6.11 still lack a public session-scoped Gateway/RPC/CLI surface to list and terminate child exec processes, while the remaining work is product and security-boundary design rather than stale cleanup.

## What This Changes

Request to add a session-scoped operator surface that lists and terminates child exec processes spawned by a session.

## Best Possible Solution

Define an additive, authorization-checked Gateway and CLI session exec-control contract that resolves canonical session scope, lists supervisor-owned active exec runs, cancels matching scopes with per-run outcomes and fallback behavior, and documents isolation without changing sessions.abort/delete defaults silently.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What public session exec-control contract and authorization boundary should OpenClaw expose for listing and terminating child exec processes spawned by a stored session?

Rationale: The missing behavior is source-proven, but exposing process visibility and termination by session can cross agent/session/sandbox boundaries and needs an owner-approved product and security model before implementation.

Likely owner: vincentkoc

Owner reason: Vincent is already connected to this issue timeline and has recent gateway security/session-boundary history.

Owner confidence: medium

Options:

- **Add guarded session exec control (recommended):** Add new Gateway and CLI methods for session exec list and kill with explicit operator scope, canonical session resolution, per-run outcomes, and tests for child, PTY, sandbox, and fallback behavior.
- **Extend existing abort/delete explicitly:** Add opt-in kill-exec flags to existing session maintenance methods while preserving current defaults and documenting upgrade behavior.
- **Defer public process control:** Keep the existing agent-scoped process tool only and track orphan/restart cleanup in narrower lifecycle issues until a broader process-control design is ready.

## Reproduction Assessment

Yes, source-level: current main exposes sessions.abort/delete and internal process-control primitives, but no public session-wide exec process list/kill operation. I did not run a live orphan-process scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public API shape and authorization model. An additive Gateway/CLI contract using supervisor scope cancellation and explicit per-run outcomes is safer than silently changing sessions.abort or sessions.delete defaults.

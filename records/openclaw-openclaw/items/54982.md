## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.88

Full review comments:

- **[P1] Drop every preserved chunk for suppressed finals:** `src/tui/components/chat-log.ts:100-102`
  - body: In preserve mode, each displayable delta appends a component, but `streamingRuns` only remembers the latest one. Current final-event handling calls `dropAssistant` when a final has no message or when `(no output)` is suppressed, so this would remove only the newest chunk and leave older partial text visible as a phantom assistant reply.
  - confidence: 0.91
- **[P2] Avoid duplicating unchanged final snapshots:** `src/tui/components/chat-log.ts:116-117`
  - body: `finalizeAssistant` always appends another preserved component, even when the final text is identical to the latest streamed display text. Normal streams often repeat the terminal snapshot, so this can show duplicate assistant output and consume the fixed chat-log budget faster.
  - confidence: 0.84
- **[P2] Bound preserved snapshots per run:** `src/tui/components/chat-log.ts:100-102`
  - body: Every changed display text from the stream assembler becomes a full chat-log component under this flag. A verbose response can spend the shared 180-component cap on one run and evict earlier conversation rows, so preserve mode needs a per-run cap or coalescing policy plus coverage for that tradeoff.
  - confidence: 0.84
- **[P2] Document the flag in option references:** `docs/cli/tui.md:27-28`
  - body: The PR adds the new flag only as an example, but the CLI options table and web TUI options/history sections would still omit or contradict the new mode. Users reading the reference docs would not see the supported option or its retention tradeoff.
  - confidence: 0.82

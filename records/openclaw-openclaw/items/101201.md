## Summary

Keep open: current main and the latest release still contain a `repairJson()` path that can turn a real newline escape after a false Windows-path prefix into literal backslash-n output, and this issue is paired with an open same-author PR that should be reviewed rather than closing one half of the pair. ## What This Changes

The issue reports that `write()` and other file-write paths produce literal backslash-n bytes instead of real newline bytes, attributing the behavior to `repairJson()`.

## Best Possible Solution

Keep this issue open while maintainers review the canonical parser fix path, then close or consolidate it after a merged fix proves real newlines after code block openers are preserved without regressing Windows-path repair.

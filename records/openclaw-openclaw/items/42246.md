## Summary

Keep open: current main still lacks configurable timed outbound Telegram notification digest aggregation, and the related items cover adjacent throttling, single-turn coalescing, inbound aggregation, or opposite immediate-delivery policy rather than this remaining product/config decision.

## What This Changes

The issue requests configurable outbound Telegram notification batching so bursts of short events can be emitted as digest messages.

## Best Possible Solution

Define an opt-in Telegram-owned or shared outbound digest policy that keeps immediate delivery as the default, persists pending digest state when durability is required, and routes flushed digest payloads through existing durable delivery and Telegram throttling.

- **Require external plugin or hook extension:** Keep core lean and extend or document plugin hooks only if durable delayed aggregation cannot be built safely with current surfaces.
- **Keep immediate delivery semantics:** Treat current streaming coalescing, throttling, and error cooldowns as the supported anti-spam mechanisms and narrow or close the request later.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes, at source level: current main sends rendered payloads directly through durable delivery and Telegram send functions, while config and docs expose no timed outbound digest batching surface.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainers choose the product boundary; a Telegram-local ring buffer alone is too narrow unless it preserves durability, bypass, media, thread, and retry semantics.

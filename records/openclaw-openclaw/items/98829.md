## Summary

Keep open: current main and the latest release still buffer SSH command stdout/stderr without a bound, and this PR is a focused fix with sufficient terminal proof and no blocking code findings. The remaining maintainer decision is whether the hard 16 MiB fail-closed SSH/OpenShell output contract is the intended upgrade behavior.

## What This Changes

The PR adds a 16 MiB combined stdout/stderr cap to `runSshSandboxCommand` and adds focused regression tests for normal, over-cap, partial-output, and post-cap data behavior.

## Best Possible Solution

Land this bounded SSH command-result path after maintainers accept the 16 MiB fail-closed contract, or revise oversized-output handling to an approved truncate/stream policy if larger buffered results must remain supported.

## Reproduction Assessment

Yes from source inspection and PR proof: current main appends every SSH stdout/stderr chunk into arrays until close, and the PR body shows a real child-process negative control buffering 20 MiB on main. I did not run a live SSH OOM scenario in this read-only review.

## Solution Assessment

Mostly yes: `runSshSandboxCommand` is the right chokepoint for backend-managed SSH helper commands, and the tests cover the new cap. The one remaining solution question is policy, not mechanics: maintainers need to accept the hard fail-closed limit or choose truncation/streaming instead.

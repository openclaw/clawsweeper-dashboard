## Summary

Keep open: current main and v2026.6.11 still lack the requested assistant text-stream repetition guard, and the direct implementation PR closed unmerged. The remaining work is product-sensitive because thresholds, alerting, resume/cancel semantics, buffered-output discard, and session cleanup need maintainer direction.

## What This Changes

Request a core streaming safeguard that detects repeated assistant text, halts or pauses the stream, alerts the user, and requires resume or cancel confirmation.

## Best Possible Solution

Define a core stream-content repetition circuit breaker with maintainer-approved thresholds, alert/recovery semantics, buffered-output discard, and session cleanup while keeping timeout and broad session-health breaker work separate.

Rationale: The source boundary is clear, but default strictness, false-positive tolerance, whether confirmation can safely resume suspect output, and how to sanitize session history are product and compatibility decisions automation should not invent.

Options:

- **Define A Core Stream Guard (recommended):** Specify thresholds, alert copy, abort/retry/resume behavior, and session cleanup before implementing the detector in the embedded-agent stream path.
- **Defer To Timeout And Session Breaker Work:** Keep this issue open but wait for generation-timeout and broader session-health decisions before adding semantic stream detection.
- **Reject Resume Semantics:** Allow a detector only to abort and quarantine the turn, avoiding a manual resume path that might continue looped output.

## Solution Assessment

Unclear until maintainers choose the product contract. A core stream guard is plausible, but halt-and-confirm, retry, abort-only, and session-cleanup semantics have different compatibility and safety tradeoffs.

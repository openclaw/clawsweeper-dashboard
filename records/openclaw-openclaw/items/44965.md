## Summary

Keep open: current main and v2026.6.11 still lack a semantic repeated-text stream circuit breaker, and the requested halt/confirm behavior needs maintainer direction before a safe implementation.

## What This Changes

Request stream-level detection of repeated assistant output that halts generation, alerts the user, and requires confirmation before continuing.

## Best Possible Solution

Design a core stream-content repetition circuit breaker in the embedded-agent stream path with approved thresholds, buffer discard, user alerting, and session cleanup semantics; keep timeout configuration tracked separately.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What should OpenClaw do when assistant text or thinking output becomes semantically repetitive during an active stream?

Rationale: The missing code path is clear, but default abort behavior, false-positive tolerance, confirmation/resume semantics, and session-history cleanup are product and compatibility decisions that automation should not invent.

Likely owner: steipete

Owner reason: steipete is the strongest current routing candidate from stream-handler blame and the existing maintainer review context for this issue.

Owner confidence: high

Options:

- **Add guarded abort with cleanup (recommended):** Implement a core repeated-text detector that aborts the active stream, suppresses buffered repetitive output, records a recoverable terminal state, and asks the user to cancel, retry, or reset rather than blindly resume the same stream.
- **Detector only, no confirmation:** Add a lower-friction guard that aborts and reports the turn without a manual resume flow, reducing product surface but leaving recovery policy simpler.
- **Defer to timeout work:** Leave semantic repetition unimplemented for now and rely on generation timeout work in https://github.com/openclaw/openclaw/issues/8724, accepting that repeated active streams may continue until a timeout or token cap.

## Solution Assessment

## Summary

Keep open: current main still lacks a stream-level text/thinking repetition guard, and related duplicate reports were explicitly centralized on this issue. The remaining work is product-sensitive because halt/confirm behavior affects session state, buffered message delivery, and false-positive handling.

## What This Changes

Request a core streaming-output repetition circuit breaker that halts repeated LLM text, alerts the user, and requires approval or cancel before continuing.

## Best Possible Solution

Define a maintainer-approved core guard that detects repeated assistant text/thinking, suppresses buffered spam, aborts or quarantines the bad turn, notifies the user, and explicitly documents whether resume, fallback, or cancel is supported.

Rationale: The detector can be implemented, but the requested halt-and-confirm UX affects delivery, transcript/session state, false-positive policy, and recovery semantics that cleanup automation should not choose alone.

Options:

- **Ship Conservative Abort And Notify (recommended):** Add a default core guard that stops repeated-output turns, drops buffered repeated text, notifies the user, and quarantines/sanitizes the turn without trying to resume the same corrupted stream.
- **Design Full Halt And Resume:** Specify pause, approve, cancel, resume, and fallback semantics before implementation, accepting a larger state-machine and channel-delivery design.
- **Keep To Existing Timeout Work:** Decline semantic repetition detection for now and rely on https://github.com/openclaw/openclaw/issues/8724 plus provider/run timeout work, leaving pure text loops partially uncovered.

## Solution Assessment

Unclear until maintainers choose the recovery policy. A semantic detector is plausible, but the safest first implementation is likely abort-and-notify with buffer suppression and turn quarantine rather than resuming a corrupted stream.

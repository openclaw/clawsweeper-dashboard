## Summary

Keep open. Current main and the latest release still contain the shared strict-mode fallback that can return all text after an unclosed thinking tag once final-tag boundaries have been stripped, so the remaining security-sensitive leak is not fully fixed even though the direct Gemini tagged-mode trigger is mitigated.

## What This Changes

The issue reports Gemini `<think>/<final>` reasoning text leaking through WhatsApp and later identifies a shared unclosed-tag sanitizer fallback affecting sibling channel delivery.

## Best Possible Solution

Keep the direct-Gemini native reasoning mitigation, then make a maintainer-approved shared sanitizer or stream-parser decision for unclosed `<think>` plus `<final>` leakage with WhatsApp and sibling-channel regression coverage.

Question: What should strict-mode sanitization do when a user-delivery payload contains an unclosed `<think>` opener and a `<final>` body whose tags are stripped before the thinking fallback runs?

Rationale: This choice controls whether OpenClaw may recover malformed answers or must fail closed to avoid exposing hidden reasoning, and the right default is a security/product boundary decision rather than a safe autonomous patch.

Likely owner: Peter Steinberger

Owner confidence: high

Options:

- **Define shared safe fallback (recommended):** Adopt a shared sanitizer or stream-parser rule that preserves only a confidently identified final answer and otherwise suppresses unclosed reasoning, then cover WhatsApp and Telegram delivery paths.
- **Fail closed on unclosed thinking:** Always drop text after an unclosed thinking opener in strict delivery paths, accepting possible empty replies to minimize hidden-reasoning exposure.
- **Use channel-specific splitters:** Add WhatsApp-style stream coordinators per channel, accepting duplicated policy and drift risk while leaving the shared fallback mostly unchanged.

## Reproduction Assessment

Yes at source level, but not as a fresh live channel run. Current main still strips `<final>` markers before returning all text after an unclosed `<think>` opener when strict-mode output would otherwise be empty.

## Solution Assessment

No, a WhatsApp-only splitter is too narrow while the shared fallback remains. The maintainable fix belongs in the shared sanitizer or stream parser, with channel coverage proving the visible delivery behavior.

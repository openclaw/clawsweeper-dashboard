## Summary

Keep open. Current main and the latest release reduce the original direct-Gemini trigger by using native reasoning for the Google provider, but the shared strict sanitizer still removes `<final>` markers before its unclosed-`<think>` recovery path returns all post-opener text, so the cross-channel hidden-reasoning leak remains source-reproducible and needs maintainer direction.

## What This Changes

The issue asks OpenClaw to stop Gemini `<think>/<final>` reasoning tags from leaking into WhatsApp replies after the Telegram-only fix, especially for unclosed `<think>` output mixed with `<final>` answer text.

## Best Possible Solution

Keep the Google native-reasoning mitigation, then make a maintainer-approved shared sanitizer or stream-parser change that preserves the answer from original `<final>` boundaries without exposing unclosed `<think>` content, with WhatsApp and at least one sibling-channel regression case.

Rationale: The current fallback recovers otherwise-empty replies but can expose hidden reasoning after final markers are stripped; choosing the replacement semantics is a security boundary and product behavior decision rather than a purely mechanical WhatsApp fix.

Likely owner: steipete

Owner confidence: high

Options:

- **Recover only the final answer (recommended):** When an original `<final>` boundary is present, return only that final body and suppress the unclosed `<think>` region, then add shared and WhatsApp/Telegram coverage.
- **Fail closed on malformed reasoning:** Suppress the entire malformed unclosed reasoning payload unless a structured final-answer block is already known, favoring secrecy over answer recovery.
- **Keep current fallback:** Accept the risk that malformed tagged output can expose reasoning in exchange for preserving more malformed local-model replies.

## Reproduction Assessment

Yes, at source level but not as a live current-main WhatsApp run. Current strict sanitization still strips `<final>` markers before recovering all text after an unclosed `<think>` opener when the visible result would otherwise be empty.

## Solution Assessment

No, a WhatsApp-only splitter is too narrow while the shared strict fallback remains. The maintainable fix belongs in the shared sanitizer or stream parser, with WhatsApp and sibling-channel coverage proving the visible delivery behavior.

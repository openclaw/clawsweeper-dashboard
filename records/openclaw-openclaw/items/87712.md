## Summary

Keep open: current main and v2026.6.11 mitigate the direct Gemini tagged-mode trigger, but the shared strict sanitizer fallback still can expose reasoning text when an unclosed `<think>` is followed by `<final>` content before WhatsApp/Telegram delivery.

## What This Changes

The issue asks OpenClaw to stop Gemini `<think>/<final>` reasoning tags and malformed unclosed tagged reasoning text from leaking through WhatsApp and sibling channel delivery after the earlier Telegram-only fix.

## Best Possible Solution

Keep the direct Google native-reasoning behavior, then land a shared sanitizer fix that treats `<final>` as the visible boundary for unclosed reasoning recovery, with WhatsApp, Telegram, and WebChat regression coverage rather than a WhatsApp-only splitter.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For strict delivery sanitization when a model emits `<think>private<final>answer</final>` without `</think>`, should OpenClaw recover only the final body, drop the payload, or keep the current post-`<think>` recovery?

Rationale: This decides a security boundary between avoiding blank replies and preventing hidden reasoning from reaching external channel recipients; automation should not choose the permanent fallback semantics alone.

Likely owner: steipete

Owner reason: The decision is centered on the shared reasoning/final-tag sanitizer behavior that steipete most directly shaped in recent merged history.

Owner confidence: high

Options:

- **Recover final body only (recommended):** Treat a valid `<final>` opener as the visible-answer boundary before unclosed reasoning fallback, preserving the answer while dropping private reasoning.
- **Fail closed on malformed reasoning:** Drop the whole malformed payload when strict mode cannot prove a safe visible boundary, prioritizing privacy over answer recovery.
- **Keep current fallback:** Continue recovering all text after the unclosed reasoning opener, accepting the hidden-reasoning leak risk for malformed providers.

## Reproduction Assessment

Yes at source level, but not as a live current-main WhatsApp or Telegram run. The current strict sanitizer still removes `<final>` markers before returning all text after an unclosed `<think>` opener when the visible result is otherwise empty.

## Solution Assessment

No for the originally suggested WhatsApp-only splitter; the maintainable fix belongs in the shared sanitizer or stream parser. The best current path is a maintainer-approved final-boundary recovery decision with channel regression coverage.

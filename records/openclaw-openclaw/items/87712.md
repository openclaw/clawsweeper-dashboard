## Summary

Keep open. Current main fixes the direct-Gemini tagged-mode trigger and the Google baseUrl transport footgun, but the shared strict sanitizer fallback still returns all text after an unclosed reasoning opener after `<final>` markers have been removed, so the WhatsApp and sibling-channel leak class is not fully implemented away.

## What This Changes

The issue asks OpenClaw to stop WhatsApp and sibling channels from exposing Gemini `<think>/<final>` reasoning text after the earlier Telegram-only fix.

## Best Possible Solution

Keep the direct Gemini native-reasoning behavior, then make a maintainer-approved shared sanitizer or stream-parser decision for unclosed `<think>` plus `<final>` text, with WhatsApp, Telegram, and WebChat regression coverage.

Required: true

Kind: security_boundary

Question: What should strict sanitizer recovery do when a reply has an unclosed reasoning tag followed by a `<final>` boundary: return only the final body, suppress the malformed payload, or keep the current post-opener recovery fallback?

Rationale: This is a security boundary choice because one behavior can leak hidden reasoning while the other can drop or truncate the user's answer; code alone cannot choose the intended product tradeoff safely.

Likely owner: steipete

Owner reason: The decision is centered on shared final/reasoning sanitizer semantics where this owner has the strongest sampled feature history.

Owner confidence: high

Options:

- **Recover only final answer text (recommended):** Change shared strict recovery to use a valid `<final>` body when present, drop preceding reasoning, and add WhatsApp/Telegram/WebChat coverage for malformed tag turns.
- **Fail closed on malformed reasoning:** Suppress the entire malformed payload when reasoning is unclosed, accepting possible message loss to avoid private reasoning exposure.
- **Keep current recovery behavior:** Leave the answer-recovery fallback in place and rely on native Gemini mode/provider fixes to reduce the malformed tagged input source.

## Reproduction Assessment

Yes at source level, but not as a live current-main WhatsApp run. The current strict sanitizer still strips `<final>` markers before returning all text after an unclosed reasoning opener when the visible result is otherwise empty.

## Solution Assessment

No, the WhatsApp-only splitter proposed in the issue is too narrow while the shared strict fallback remains. The better fix is shared sanitizer or stream-parser semantics with channel-specific regression proof.

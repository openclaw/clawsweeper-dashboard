## Label Justifications

- `P2`: Telegram media ingestion can lose the usable video attachment while the impact is bounded to one channel/media path.
- `impact:message-loss`: The reported Telegram video payload can reach the agent/session without the actual media attachment.
- `impact:session-state`: The session transcript can imply media context exists when no attachment path is available, causing agent context drift.

## Summary

Keep open: current main and v2026.6.11 still have the source-proven Telegram path where `getFile()` failures return `null`, no attachment is saved, and placeholder/file_id context can still reach the agent without a user-visible unavailable-media state.

## What This Changes

The issue asks OpenClaw to handle Telegram inbound video `getFile()` failures by attaching the media or surfacing a clear failure instead of sending placeholder-only media context.

## Best Possible Solution

Consolidate Telegram unavailable-media handling so failed `getFile()` or download paths produce a typed unavailable attachment state, preserve useful file_id metadata, cover single messages and media groups, and emit rate-limited user-visible warnings.

## Reproduction Assessment

Yes, at source level: make Telegram `ctx.getFile()` fail for a video and current main returns `null`, proceeds with no saved media, and can render placeholder/file_id context without an attachment. I did not run a live Telegram bot reproduction in this read-only review.

## Solution Assessment

No, current main is not the best solution because it still lacks a typed unavailable-media state for the null path. The safer fix should cover warnings, throttling, metadata preservation, and media groups together.

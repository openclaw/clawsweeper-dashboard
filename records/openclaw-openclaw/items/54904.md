## Summary

This PR is still needed because current main and v2026.6.11 do not enforce the configured Feishu webhook path, but the current head still has the prior blocking compatibility defect: it normalizes the configured path while comparing the incoming safe origin-form pathname raw, so valid trailing-slash callback URLs can be rejected before dispatch.

## What This Changes

The PR adds Feishu webhook request-path validation, normalizes the configured webhookPath, rejects malformed or mismatched request targets before signature verification, and adds Feishu transport tests.

## Best Possible Solution

Keep the strict malformed-target, network-path, and dot-segment protections, then normalize the remaining safe origin-form incoming pathname with the shared webhook helper before comparing it to the normalized configured Feishu webhook path.

## Reproduction Assessment

Yes from source: with a configured path that normalizes to `/expected-feishu-hook`, the current PR head compares that to a raw incoming `/expected-feishu-hook/` pathname and returns 404 before dispatch. I did not run tests because this review is read-only and the failing path is direct in source.

## Solution Assessment

No. The Feishu-owned early route gate is the right layer, but the current patch should normalize accepted safe origin-form incoming paths before comparing them with the configured path.

## Summary

Keep open: current main and the latest release still omit structured progress metrics from the relevant public plugin hook payloads, and adding them is a Plugin SDK semantics decision rather than stale cleanup.

## What This Changes

The issue requests optional structured progress metrics such as step counts, percent, and ETA on existing plugin hook events for live progress-card rendering.

## Best Possible Solution

Define optional producer-owned progress metrics in the Plugin SDK, wire them through the hook producers with docs and tests, and omit unknown values instead of fabricating percentages.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a producer-owned structured progress metrics contract to plugin hook events, and which runtime source owns step totals, percent, ETA, and terminal metrics across embedded, CLI, and Codex-facing paths?

Rationale: The missing fields are source-reproducible, but the correct semantics are a public Plugin SDK/API decision that automation should not invent from tool-call counts alone.

Likely owner: vincentkoc

Owner reason: The current history ties vincentkoc to the closest public hook payload contract work and current hook runtime ownership trail.

Owner confidence: high

Options:

- **Define a narrow metrics contract (recommended):** Add optional metrics only where the runtime can produce authoritative values, document unknown fields as absent, and cover the main hook producers with focused tests.
- **Keep hooks unchanged:** Leave plugins to derive progress from existing lifecycle, text progress, and tool events, accepting text-only live cards until a stronger source exists.
- **Design a separate progress event:** Create a dedicated progress event or agent-event projection instead of attaching percentages to tool and terminal hooks.

## Reproduction Assessment

Yes, at source-contract level: current hook event types, producers, docs, and the latest release omit the requested structured progress metric fields. A live Feishu card run is not needed to verify the missing public API field.

## Solution Assessment

Unclear as proposed: enriching hook payloads is plausible, but step totals, percent, ETA, and terminal success/failure semantics need maintainer agreement. The safer shape is producer-owned metrics with absent values when progress is unknown.

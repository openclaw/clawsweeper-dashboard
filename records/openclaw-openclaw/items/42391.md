## Summary

Keep open: current main and the latest release still omit structured progress metrics from the relevant plugin hook payloads, and adding them is a public Plugin SDK semantics decision rather than stale cleanup.

## What This Changes

Request to add optional structured progress metrics to existing plugin hook events so plugin live progress cards can render numeric completion.

## Best Possible Solution

Define optional producer-owned progress metrics in the Plugin SDK, wire only authoritative values through each hook producer, document absent fields as unknown, and cover embedded/CLI/Codex-facing paths with focused tests.

Rationale: The code change is feasible, but progress semantics become public Plugin SDK behavior and automation should not invent misleading completion percentages or cross-runtime ownership rules.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Define a narrow metrics contract (recommended):** Add optional metrics only where the runtime can produce authoritative values, document unknown fields as absent, and test each producer path that emits them.
- **Keep hooks unchanged:** Leave plugins to derive progress from existing lifecycle and tool events, accepting text-only cards until a stronger progress source exists.
- **Create a dedicated progress event:** Design a separate progress hook or agent-event projection instead of attaching percentages to tool and terminal hooks.

## Reproduction Assessment

Yes. At source-contract level, current hook event types, producers, docs, and the latest release omit the requested structured progress metric fields; a live Feishu card run is not needed to verify the missing public API field.

## Solution Assessment

Unclear as proposed. Enriching hook payloads is plausible, but step totals, percent, ETA, and terminal success/failure semantics need maintainer agreement before a maintainable implementation can be called best.

## Summary

Keep open: current main and the latest release still omit structured progress metrics from the relevant plugin hook payloads, and this is a public Plugin SDK semantics decision rather than stale cleanup.

## What This Changes

The issue asks OpenClaw to add optional structured progress metrics (`stepIndex`, `stepTotal`, `percent`, `etaSec`) to existing plugin hook payloads so live progress-card plugins can render numeric progress.

## Best Possible Solution

Define optional producer-owned progress metrics in the Plugin SDK, wire them through all hook producers with tests/docs, and omit unknown values rather than fabricating percentages.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a producer-owned structured progress metrics contract to plugin hook events, and which runtime source owns `stepTotal`, `percent`, ETA, and terminal metrics across embedded, CLI, and Codex paths?

Rationale: The code change is feasible, but the public Plugin SDK semantics and progress source of truth are product/API decisions that automation should not invent.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Define a narrow metrics contract (recommended):** Add optional metrics only where the runtime can produce authoritative values, document unknown fields as absent, and cover embedded/CLI/Codex-facing producers with focused tests.
- **Keep hooks unchanged:** Leave plugins to derive progress from existing lifecycle and tool events, accepting text-only live cards until a stronger progress source exists.
- **Create a separate progress event:** Design a dedicated progress event or agent-event projection instead of attaching percentages to tool and terminal hooks.

## Reproduction Assessment

Yes, at source-contract level: current hook event types, producers, docs, and the latest release omit the requested structured progress metric fields. A live Feishu card run is not needed to verify the missing public API field.

## Solution Assessment

Unclear as proposed: enriching hook payloads is plausible, but step totals, percent, ETA, and terminal success/failure semantics need maintainer agreement. The safer shape is producer-owned metrics with absent values when progress is unknown.

## Summary

Keep open: current main and the latest release still do not expose the requested structured progress metrics on plugin hook payloads, and the remaining work is a public Plugin SDK/product semantics decision rather than stale cleanup.

## What This Changes

The issue requests optional structured progress metrics on `before_tool_call`, `after_tool_call`, and `agent_end` hook payloads for plugin-rendered live progress cards.

## Best Possible Solution

Define optional producer-owned progress metrics in the Plugin SDK, wire them only from authoritative runtime state with tests/docs, and omit unknown values rather than fabricating percentages.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a producer-owned structured progress metrics contract to plugin hook events, and which runtime source owns `stepTotal`, `percent`, ETA, and terminal metrics across supported run paths?

Rationale: The implementation shape is feasible, but these fields become public Plugin SDK semantics and automation should not invent progress source-of-truth rules.

Likely owner: vincentkoc

Owner reason: The strongest current history signal for public hook contract ownership points to vincentkoc's hook type and registry work.

Owner confidence: high

Options:

- **Define a narrow metrics contract (recommended):** Add optional metrics only where the runtime can produce authoritative values, document unknown fields as absent, and cover active producers with focused tests.
- **Keep hooks event-based:** Leave plugins to derive progress from existing lifecycle and tool events, accepting text-only live cards until a stronger progress source exists.
- **Design a separate progress surface:** Create a dedicated progress event or agent-event projection instead of attaching percentages to tool and terminal hooks.

Yes. Source inspection against current main reproduces the gap: the requested hook event types, producers, docs, and latest release omit structured progress metric fields.

## Solution Assessment

Unclear as proposed. Enriching hook payloads is plausible, but the best fix depends on maintainer-approved semantics for authoritative step totals, percentages, ETA, and terminal-state handling.

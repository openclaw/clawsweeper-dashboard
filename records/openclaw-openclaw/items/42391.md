## Summary

Keep open: current main still lacks the requested structured progress metrics on the public plugin hook payloads, and adding them is a Plugin SDK/API semantics decision rather than stale cleanup.

## What This Changes

The issue requests optional structured progress metrics on existing hook payloads so plugin-rendered progress cards can show step counts or percent complete.

## Best Possible Solution

Define optional producer-owned progress metrics in the Plugin SDK, wire them only where the runtime has authoritative values, document absent unknowns, and cover terminal success/failure semantics with focused tests.

Owner confidence: high

Options:

- **Define a narrow metrics contract (recommended):** Add optional metrics only where the runtime can produce authoritative values, document unknown fields as absent, and cover core producers with tests.
- **Keep hooks unchanged:** Leave plugins to derive progress from lifecycle and tool events, accepting text-only live cards until a stronger progress model exists.
- **Create a separate progress event:** Design a dedicated progress event or task-flow projection instead of attaching percentages to existing hook payloads.

## Reproduction Assessment

Yes, at source-contract level: current hook event types, producers, docs, and the latest release omit the requested structured progress metric fields. A live Feishu card run is not needed to verify the missing public API field.

## Solution Assessment

Unclear as proposed: enriching hook payloads is plausible, but step totals, percent, ETA, and terminal success/failure semantics need maintainer agreement. The safer shape is producer-owned metrics with absent values when progress is unknown.

## Summary

Keep open: current main and v2026.6.11 still omit structured progress metrics from the requested plugin hook payloads, and the external Feishu progress plugin context shows a real UX gap. The remaining work is an additive public Plugin SDK semantics decision, not stale cleanup.

## What This Changes

Expose optional structured progress metrics on existing plugin hook payloads so live progress-card plugins can render numeric step or percent progress.

## Best Possible Solution

Define an optional producer-owned progress metrics contract in the Plugin SDK, emit only authoritative values, document absent unknowns, and cover embedded, CLI, and hook producer paths with focused tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add structured progress metrics to public plugin hook events, and which runtime source owns step totals, percent, ETA, and terminal success/failure semantics across producers?

Rationale: This would be an additive public Plugin SDK contract, and naive tool-call counting could mislead plugin UIs for dynamic, retried, cancelled, failed, or branched runs.

Likely owner: vincentkoc

Owner reason: The strongest current-history trail for public hook contract changes points to this owner path, and the decision affects Plugin SDK semantics.

Owner confidence: high

Options:

- **Define a narrow metrics contract (recommended):** Add optional metrics only where producers can supply authoritative values, leave unknowns absent, and document/test the hook semantics across producers.
- **Keep current hook payloads:** Leave plugins to derive phase or text progress from existing events until OpenClaw has a stronger progress source of truth.
- **Design a dedicated progress event:** Create a separate progress event or agent-event projection instead of attaching percentages to tool and terminal hooks.

## Reproduction Assessment

Yes at source level: the current hook event types and emitters for before_tool_call, after_tool_call, and agent_end do not include metrics or the requested step/percent fields. This is an additive feature gap, not a broken existing contract.

## Solution Assessment

Unclear as proposed: enriching existing hooks is plausible, but the best maintainable shape needs maintainer-approved semantics for totals, percent, ETA, cancellation, and failed terminal states.

## Summary

Keep open: current main and v2026.6.11 still lack the requested structured progress metrics in plugin hook payloads, and adding them is a public Plugin SDK progress-semantics decision rather than stale cleanup.

## What This Changes

The issue requests optional `metrics` fields such as step index, total, percent, and ETA on existing plugin hook events for live progress-card plugins.

## Best Possible Solution

Define optional producer-owned progress metrics in the Plugin SDK only where OpenClaw can provide authoritative values, document unknown fields as absent, and cover hook producers with tests/docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a producer-owned structured progress metrics contract to plugin hook events, and which runtime source owns `stepTotal`, `percent`, ETA, and terminal metrics across embedded, CLI, and Codex paths?

Rationale: The source gap is clear, but the field names, semantics, terminal behavior, and source of truth become a public Plugin SDK API decision that automation should not invent.

Likely owner: vincentkoc

Owner reason: The prior run/tool hook correlation work is the closest current-main ownership trail for this public hook contract choice.

Owner confidence: high

Options:

- **Define a narrow metrics contract (recommended):** Add optional metrics only when the runtime can produce authoritative values, omit unknown fields, and document/test semantics across relevant producers.
- **Use agent/process events instead:** Keep tool and terminal hooks unchanged and make live-card plugins consume a separate structured event surface for progress state.
- **Keep hooks text-only:** Leave plugins to derive progress from existing lifecycle/tool events and accept phase-only live cards until a stronger progress source exists.

## Reproduction Assessment

Yes, at source-contract level: current hook event types, producers, docs, and v2026.6.11 omit the requested structured progress metric fields. A live Feishu card run is not needed to verify the missing public API field.

## Solution Assessment

Unclear as proposed: enriching hook payloads is plausible, but step totals, percent, ETA, and terminal success/failure semantics need maintainer agreement. A safer solution would publish only producer-owned metrics and omit unknown values.

## Risks / Open Questions

- Generic tool-call counts are not an authoritative progress model for dynamic, retried, cancelled, failed, or branched runs, so naive percentages could mislead plugin UIs.
- Adding `metrics` to hook payloads creates a public Plugin SDK contract that needs consistent semantics across embedded, CLI, Codex relay, and channel-backed paths.
- Existing agent event subscriptions are an adjacent possible source of truth, so maintainers should choose whether progress belongs on hook payloads, agent events, or a separate process/step contract.

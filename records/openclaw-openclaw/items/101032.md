## Summary

Keep open: this is a real Docker sandbox reliability gap, but the proposed stdin error handler can leave `execDockerRaw` waiting for child close after input delivery fails, so a wedged `docker exec -i` can hang instead of rejecting; contributor proof is also only mock/check evidence so far.

## What This Changes

The PR adds a stdin `error` listener to `execDockerRaw`, a new regression test, and a standalone proof script for Docker sandbox stdin stream errors.

## Best Possible Solution

Keep the fix at `execDockerRaw`, but handle stdin errors through the same first-error, terminate-child, reject-on-close lifecycle as stdout/stderr and add proof where the child stays alive until killed.

## Reproduction Assessment

Yes, from source inspection rather than a live repro: current main closes `child.stdin` without an `error` listener, and the PR regression demonstrates the intended stdin error path. I did not run a live Docker failure scenario in this read-only review.

## Solution Assessment

No. The shared `execDockerRaw` boundary is the right place, but the implementation should terminate the child on stdin stream errors like stdout/stderr so the command cannot hang waiting for close.

## Summary

Keep this PR open: the bounded admission approach is a useful response to repeated catalog scans and the supplied loopback Gateway RPC proof is meaningful, but coalescing currently appears to retain only the first request’s progress sink. A concurrent caller with its own `progressId` can receive the final catalog response without the streamed catalog updates it previously received, which is a compatibility regression.

## What This Changes

The branch adds a process-local Gateway coordinator that coalesces identical `sessions.catalog.list` provider scans, briefly caches results, and bounds concurrent and queued distinct catalog loads.

## System Context

The Control UI and other Gateway clients call `sessions.catalog.list` to discover sessions from registered catalog providers. The handler turns provider scans into streamed and final catalog responses, so admission and coalescing behavior directly affects both Gateway load and RPC caller-visible progress.

## Architecture Diagram

flowchart LR
  Client[Control UI or Gateway client] --> Request[Catalog RPC request]
  Request --> Key[Normalized request key]
  Key --> Coordinator[Coalescing and admission]
  Coordinator --> Providers[Catalog provider scans]
  Providers --> Progress[Streamed catalog updates]
  Providers --> Result[Final catalog response]
  Progress --> Client
  Result --> Client

## Best Possible Solution

Keep one shared provider scan per normalized request, but register each coalesced caller as a progress subscriber and emit every streamed catalog update using that caller’s own `progressId`; add coverage for leader and follower progress plus final responses.

## Reproduction Assessment

Yes, source-reproducible: issue two identical catalog RPCs concurrently with different `progressId` values while the provider emits streamed catalog rows. The coordinator’s single shared load closure has no mechanism to relay those updates to the follower’s identifier.

## Solution Assessment

No. Provider-load coalescing is the right bounded repair, but the current implementation coalesces only the final promise rather than the complete RPC contract; progress delivery must be multiplexed per waiting caller.

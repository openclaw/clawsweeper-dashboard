## Summary

This issue remains necessary: current ACP follow-up dispatch can start a run-mode child without its persisted backend resume identity and does not reliably reject active, non-steerable one-shots. The report supplies a concrete two-provider reproduction, and no merged fix or canonical replacement was found.

## What This Changes

Resume completed ACP run-mode backend sessions on follow-up sends while rejecting active or identity-less one-shots.

## Best Possible Solution

At the canonical ACP dispatch boundary, pass the persisted stable backend session identity when a completed run-mode child receives a new turn, reject active or identity-less one-shots with actionable guidance, and preserve existing persistent-session behavior with focused lifecycle coverage.

Yes, at source-reproducible confidence: spawn a run-mode ACP child, wait for its stable backend identity and completion, then send to its session key and observe that the new ACP initialization omits that resume identity. ## Solution Assessment

Yes in direction: reuse the canonical persisted ACP identity after completion and reject unsupported active steering rather than adding another session type, fallback, or configuration surface. Direct Codex-source verification remains required before implementation approval.

## Label Justifications

- `impact:session-state`: The requested selector determines which agent owns the initial session and workspace context.
- `impact:auth-provider`: Selecting the wrong startup agent also selects the wrong configured model and provider routing.
- `impact:ux-friction`: Users currently need a full agent-scoped session key, a dedicated workspace launch, or post-launch interaction to reach a non-default agent.

## Summary

Keep open: current main and the latest release still lack a native TUI startup agent selector, and the merged workspace-inference workaround does not cover launches from arbitrary directories. This remains the canonical request, but adding a public CLI flag requires maintainer-approved precedence semantics.

## What This Changes

Add `openclaw tui --agent <id>` to start the TUI with a selected configured agent’s session, model, workspace, and context.

## Best Possible Solution

Add a validated startup agent field at the existing TUI CLI boundary, feed it into the canonical session resolver, reject conflicting explicit agent selectors, and cover direct launch, relaunch, local/Gateway modes, docs, and precedence tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `openclaw tui --agent <id>` become the canonical explicit startup selector, overriding cwd inference and rejecting a conflicting agent-scoped `--session`?

Rationale: The capability is demonstrably missing, but the durable behavior of two public selectors and existing inferred/remembered state cannot be chosen safely without maintainer intent.

Likely owner: steipete

Owner reason: Peter introduced the TUI and its current agent-selection surface and has already reviewed this exact behavior gap.

Owner confidence: high

Options:

- **Add explicit selector (recommended):** Validate configured agent ids, let `--agent` override cwd inference, and return a clear error when it conflicts with an agent-scoped session key.
- **Keep current selection paths:** Continue supporting canonical session keys, workspace inference, the picker, and `/agent` without adding another public option.

## Reproduction Assessment

Yes, at source level with high confidence: current main and `v2026.6.11` expose no startup agent option, and the resolver accepts only session, cwd, and default-agent inputs. No live runtime reproduction was needed to establish the missing CLI capability.

## Solution Assessment

Yes, subject to maintainer approval: a thin validated option that reuses canonical agent/session routing is the narrowest maintainable solution. Extending session-key shorthand would blur the existing distinction between selecting an agent and naming a session.

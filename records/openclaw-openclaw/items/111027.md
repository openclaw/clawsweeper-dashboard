## Summary

Keep this PR open: the documentation fills a useful operational gap, but it currently describes constrained-memory sizing as though it evaluates the managed service’s own limit. The installer instead derives that value in its CLI process, so a systemd `MemoryMax=` applied only to the target unit can still leave the documented guidance overstating protection.

## What This Changes

The PR documents managed Gateway heap sizing, status and doctor reporting, metadata repair, and the distinction between managed and custom supervisors.

## Best Possible Solution

Document the actual boundary: sizing uses the installer process’s visible memory constraint, while a managed unit with its own resource limit needs an explicit heap setting or future unit-aware sizing support.

Yes, source-reproducible: run the installer from an unconstrained shell, then apply a lower `MemoryMax=` only to the managed systemd unit; the installer-side `process.constrainedMemory()` calculation does not observe that unit-only limit.

## Solution Assessment

No. The PR’s documentation path is the right solution, but the current wording crosses the installer-process and target-service boundary; qualifying that boundary is narrower and more accurate than promising unit-aware sizing that is not implemented.

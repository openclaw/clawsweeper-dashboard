## Summary

Keep open. Current main and latest release still send main-session `systemEvent` cron reminders through the heartbeat cron-event prompt and `getReplyFromConfig`; command cron is now a no-model path for explicit scripts, but it does not replace the watcher/reminder behavior reported here.

## What This Changes

The issue requests a deterministic no-model delivery path for simple scheduled reminder text because the current cron/heartbeat path can use OpenAI/ChatGPT as a formatter and drive high API usage.

## Best Possible Solution

Define a narrow literal-notification or simple-reminder main-session cron contract, while keeping `systemEvent` on the model-backed heartbeat path for reasoning-dependent events and directing scripted jobs to command cron.

## Maintainer Decision

Kind: product_direction

Question: Should main-session cron `systemEvent` reminders get a new literal/simple-reminder no-model delivery mode, or should deterministic users be expected to move this class of work to command cron?

Rationale: Both outcomes are plausible: a no-model reminder path reduces cost for simple watcher messages, but changing `systemEvent` semantics can break cron events that rely on model reasoning, tools, summarization, or internal-only handling.

Likely owner: steipete

Owner reason: Peter is the clearest routing candidate from the current issue discussion and recent heartbeat event-filter history.

Owner confidence: high

Options:

- **Add narrow literal reminder mode (recommended):** Add an explicit cron payload, flag, or conservative simple-reminder boundary for trusted text that should be delivered without a model call, and document that `systemEvent` remains model-backed.
- **Keep command cron as the no-model path:** Close the direction by telling users to emit literal stdout from command cron jobs when they need zero-token scheduled delivery.
- **Auto-detect simple systemEvents:** Bypass the model when an event looks simple, accepting more ambiguity and higher regression risk around reminders that need reasoning or internal handling.

## Reproduction Assessment

Yes, at source level. A main-session cron job with non-empty `systemEvent` text is enqueued with a `cron:` context key, selected as a cron event by heartbeat, and sent through `getReplyFromConfig`; I did not repeat the reporter's live OpenAI logging.

## Solution Assessment

No, not as a blanket string-formatting bypass. The maintainable solution is a narrow explicit literal-notification mode or conservative simple-reminder boundary, with command cron remaining the supported model-free path for scripted jobs.

## Summary

Keep open. Current main and latest release v2026.6.11 still route main-session cron `systemEvent` reminders through the heartbeat cron-event prompt and `getReplyFromConfig`; command cron gives explicit scripts a no-model path, but it does not replace the watcher/reminder behavior reported here.

## What This Changes

Request to reduce repeated model calls for main-session cron `systemEvent` reminders by formatting or delivering simple reminders deterministically instead of using ChatGPT as a formatter.

## Best Possible Solution

Define a narrow literal-notification or simple-reminder main-session cron contract, while keeping `systemEvent` on the model-backed heartbeat path for reasoning-dependent events and directing scripted jobs to command cron.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should main-session cron `systemEvent` reminders get a new literal/simple-reminder bypass, or should deterministic users be expected to move this class of work to command cron?

Rationale: Both directions are plausible: bypassing the model reduces cost for simple reminders, but changing `systemEvent` semantics can break cron events that intentionally rely on model reasoning, tools, summarization, or internal-only handling.

Likely owner: steipete

Owner reason: Peter posted the prior keep-open review and has the strongest history signal for the heartbeat event-filter/product-boundary decision.

Owner confidence: high

Options:

- **Add a narrow literal reminder mode (recommended):** Add an explicit cron payload, flag, or conservative simple-reminder boundary for trusted text that should be delivered without a model call, and document that `systemEvent` remains model-backed.
- **Keep command cron as the only no-model path:** Close the product direction by telling users to emit literal stdout from command cron jobs when they need zero-token scheduled delivery.
- **Auto-detect simple systemEvents:** Bypass the model when an event looks simple, accepting more ambiguity and higher regression risk around reminders that need reasoning or internal handling.

## Reproduction Assessment

Yes, at source level. A main-session cron job with non-empty `systemEvent` text is enqueued with a cron context key, selected as a cron event by heartbeat, and sent through `getReplyFromConfig`; I did not repeat the reporter's live OpenAI logging.

## Solution Assessment

No, not as a blanket string-formatting bypass. The maintainable solution is a narrow explicit literal-notification mode or conservative simple-reminder boundary, with command cron remaining the supported model-free path for scripted jobs.

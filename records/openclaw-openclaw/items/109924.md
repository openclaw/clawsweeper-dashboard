## Summary

Keep this PR open. The updated patch has useful live Upgrade evidence, but the proposed `verifyClient` hook sits after Gateway plugin-upgrade routing and captures a startup config object, so its broad `gateway.security.*` contract does not match the existing shared upgrade boundary or current-config behavior. A Gateway security owner needs to choose the intended scope before a narrow refactor and final-head raw-header proof can make this landable.

## What This Changes

Adds three opt-in `gateway.security.*` settings and a `WebSocketServer.verifyClient` gate to reject selected WebSocket upgrades before the HTTP 101 response.

## Best Possible Solution

Define one explicit pre-upgrade admission boundary in the shared Gateway upgrade handler, pass its current config snapshot into the policy, scope any intentional plugin exemption in the setting/docs, and publish final-head raw-wire proof for both rejection and permitted proxy-chain cases.

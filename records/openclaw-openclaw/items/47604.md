Full review comments:

- **[P1] Exclude Wear identity files from backup:** `apps/android/wear/src/main/res/xml/data_extraction_rules.xml:4`
  - body: `GatewayDeviceIdentityStore` persists the direct-auth private key under `context.filesDir/openclaw/identity/device.json`, but these data extraction rules include the entire file domain for cloud backup and device transfer. That can carry device private key material into backup/transfer, so exclude the identity path or disable Wear backup before this direct-auth client ships.
  - confidence: 0.87
- **[P1] Wire the Wear module into Android gates:** `apps/android/settings.gradle.kts:21`
  - body: Adding `:wear` creates a new shippable Android app module, but current Android CI and Android CodeQL still build only `:app`, and the release artifact helper also packages only `:app`. Green checks would not directly compile, test, analyze, or ship the Wear app, so add Wear build/test/CodeQL/release coverage or mark it explicitly non-shipping before merge.
  - confidence: 0.85
- **[P2] Clear bootstrap auth when password changes:** `apps/android/wear/src/main/java/ai/openclaw/wear/ui/ConnectionSettingsScreen.kt:51`
  - body: The password editor saves only `password`, while `buildWearConnectParams` prefers any stored `bootstrapToken` over password when token is blank. If fallback sync previously stored a bootstrap token, switching to password auth can keep sending stale bootstrap auth until another reset clears it.
  - confidence: 0.8
- **[P2] Use shared Android versioning for Wear:** `apps/android/wear/build.gradle.kts:17-18`
  - body: The phone app reads generated Android version metadata from `Config/Version.properties`, but the new Wear module hard-codes `versionCode` and `versionName`. Future Android releases could ship stale Wear metadata or break update ordering unless Wear uses the same version source and release checks.
  - confidence: 0.78

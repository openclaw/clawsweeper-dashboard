## Label Justifications

- `P1`: A routine Control UI save can otherwise silently attach a retained or newly created config row to another row’s value-backed credential.
- `merge-risk: 🚨 compatibility`: The new identity algorithm changes restore semantics for existing ID-keyed arrays and leaves an upgrade-sensitive reuse case undefined.
- `merge-risk: 🚨 auth-provider`: The affected redacted fields include provider/API-key configuration, so ID reuse can route a row to the wrong stored credential.

## Summary

This PR fixes the demonstrated delete/reorder corruption, but it still treats a newly created row that reuses a removed row’s visible `id` as the old row and restores its redacted value. That is a P1 configuration/authentication boundary decision rather than a safe implicit default; likely related people: `masatohoshino` (current implementation author, low-confidence routing signal).

## What This Changes

The branch changes redacted config-array restoration from positional matching to matching original object rows by client-visible unique `id`, with regression tests for deletion, reordering, insertion, and ambiguous IDs.

## Best Possible Solution

Keep identity matching for stable retained rows, but reject any ambiguous ID-reuse restore while a placeholder remains unless maintainers explicitly define and document ID reuse as deliberate credential/state adoption.

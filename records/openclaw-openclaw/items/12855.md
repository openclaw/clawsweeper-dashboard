## Summary

Keep open. Current main provides a default-off package auto-updater and a supervised restart-continuation/status path, but the requested scheduling, approval modes, notification targeting, and automatic post-update report remain missing; adjacent updater issues do not replace this canonical workflow request.

## What This Changes

Add a first-class scheduled auto-update workflow with confirm, notify-only, and silent modes plus channel-targeted post-restart update reporting.

## Best Possible Solution

Build a bounded core workflow on the existing auto-update policy, managed-service `update.run` handoff, restart sentinel, continuation queue, `update.status`, and generic channel delivery seams; keep unattended updates explicitly opt-in, make approval the default for agent-initiated updates, and add only the minimum configuration that cannot be expressed through existing automation and destination contracts.

## Risks / Open Questions

- Silent auto-update grants unattended code-install and service-restart authority, so install provenance, operator consent, kill-switch behavior, and safe failure handling require explicit security review.
- Confirmation and notification delivery must bind to an authorized session, channel, account, and target without leaking update details or accepting approval from the wrong conversation.
- A separate scheduling implementation would duplicate existing cron/timezone behavior and create conflicting timing semantics, missed-run policy, and daylight-saving edge cases.
- Post-restart reporting must wait for verified running-version and health results; reporting success from the pre-update process can hide split-brain or failed-restart states.
- Adding every proposed field directly to `update.auto` would expand an already large compatibility-sensitive config surface before the permanent ownership split is settled.

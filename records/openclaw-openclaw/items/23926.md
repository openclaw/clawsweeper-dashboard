## Label Justifications

- `P1`: Third-party skill installation is a live supply-chain security workflow, and scanner/audit integrations still lack the requested completion lifecycle contract even though blocking pre-install policy now exists.
- `impact:security`: The issue is about scanning, blocking, and auditing untrusted skills before or after they are accepted onto a user's machine.

## Summary

Keep open: current main now covers the blocking pre-install side with `security.installPolicy` and plugin `before_install`, but it still has no plugin-visible skill install/update completion observer for audit, outcome, and post-install metadata. The remaining work is a public, security-sensitive plugin lifecycle contract that needs maintainer direction rather than cleanup closure.

## What This Changes

The issue requests skill install lifecycle hook events: a blocking pre-install hook and an observational post-install hook for skill scanning, blocking, warnings, and audit logging.

## Best Possible Solution

Keep `security.installPolicy` and `before_install` as the blocking path, then design a minimal redacted non-blocking skill install/update completion observer for OpenClaw-managed CLI, Gateway, and UI install paths.

Rationale: Automation can prove the missing lifecycle surface, but choosing what install metadata plugins may see and whether observer failures can affect an already-written install is a security and product boundary decision.

Likely owner: steipete

Options:

- **Add Minimal Observer (recommended):** Add a non-blocking completion hook with redacted source, target, provenance, outcome, and timestamp metadata plus documented fail-open logging semantics.
- **Keep Pre-Install Only:** Declare `security.installPolicy` and `before_install` sufficient for install security, then narrow or reject the audit-observer request separately.
- **Defer To ClawHub Trust Design:** Hold the observer until maintainers define a broader ClawHub trust/provenance API that can supply the same audit events safely.

## Reproduction Assessment

Yes, at source level. Current main exposes `security.installPolicy` and `before_install` for blocking install decisions, but the hook registry and ClawHub success path show no post-install/update completion observer.

## Solution Assessment

Partly. Reusing `security.installPolicy` and `before_install` is the right blocking path, but the remaining audit capability should be specified as a redacted non-blocking completion hook rather than accepting the original event names and payload unchanged.

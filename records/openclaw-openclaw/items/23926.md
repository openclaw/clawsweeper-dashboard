## Label Justifications

- `P1`: Third-party skill installation is a live supply-chain security workflow, and scanner/audit integrations still lack the requested completion hook contract.
- `impact:security`: The issue is about scanning, blocking, and auditing untrusted skills before or after they are accepted onto a user's machine.

## Summary

Keep open: current main covers the blocking install-policy side through `security.installPolicy` and `before_install`, but it still lacks the requested plugin-visible post-install/update observer, and that remaining lifecycle API needs maintainer security/product direction.

## What This Changes

The issue requests blocking `skill:pre-install` and observational `skill:post-install` hook events for skill install scanning, blocking, and audit integrations.

## Best Possible Solution

Keep `security.installPolicy` and `before_install` as the blocking path, then decide a minimal redacted, non-blocking skill install/update completion observer for OpenClaw-managed CLI, Gateway, and UI install paths, or explicitly reject that observer as out of scope.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose a plugin-visible skill install/update completion observer, and what redacted payload plus observer-failure semantics should it use?

Rationale: Automation can prove the missing lifecycle surface, but deciding what install metadata plugins may see and whether observer failures affect an already-written install is a security and product boundary choice.

Likely owner: steipete

Owner reason: This choice crosses ClawHub skill install behavior and public plugin lifecycle API shape, and steipete is the strongest product-routing signal from discussion and file history.

Owner confidence: medium

Options:

- **Add Minimal Observer (recommended):** Add a non-blocking completion hook with redacted source, target, provenance, outcome, and timestamp metadata plus documented fail-open logging semantics.
- **Keep Pre-Install Only:** Declare `security.installPolicy` and `before_install` sufficient for install security, then narrow or reject the audit-observer portion explicitly.
- **Defer To ClawHub Trust Design:** Hold the observer until maintainers define a broader ClawHub trust/provenance API that can supply the same audit events.

## Reproduction Assessment

Yes, at source level. Current main exposes blocking install policy through `security.installPolicy` and `before_install`, but the hook registry and ClawHub success path show no post-install/update completion observer.

## Solution Assessment

Partly. Reusing `security.installPolicy` and `before_install` is the right blocking path, but the remaining audit capability should be specified as a redacted non-blocking completion hook rather than accepting the original event names and payload unchanged.

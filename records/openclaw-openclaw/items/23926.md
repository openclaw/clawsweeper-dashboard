## Label Justifications

- `P1`: Third-party skill installation is a live supply-chain security workflow, and scanner/audit integrations still lack the requested completion hook contract.
- `impact:security`: The issue is about scanning, blocking, and auditing untrusted skills before or after they are accepted onto a user's machine.

## Summary

Keep open: current main and v2026.6.11 cover the blocking side through `security.installPolicy` plus `before_install`, but they still do not expose the requested plugin-visible post-install/update observer for audit and compliance metadata.

## What This Changes

Add plugin-visible skill install lifecycle hooks so security or audit tooling can block installs before copy and observe installs after completion.

## Best Possible Solution

Keep the current blocking install policy path, then either add a minimal redacted non-blocking skill install/update completion observer for OpenClaw-managed installs or explicitly reject that observer as out of scope.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose a plugin-visible skill install/update completion observer, and what redacted payload plus observer-failure semantics should it use?

Rationale: Automation can prove the missing lifecycle surface, but deciding what install metadata plugins may see and whether observer failures affect an already-written install is a security and product boundary choice.

Likely owner: steipete

Owner reason: This choice crosses native ClawHub skill install behavior and public plugin lifecycle API shape, where steipete has the strongest product-routing and file-history signal.

Owner confidence: medium

Options:

- **Add Minimal Completion Observer (recommended):** Add a non-blocking completion hook with redacted source, target, provenance, outcome, and timestamp metadata plus documented fail-open logging semantics.
- **Keep Pre-Install Only:** Declare `security.installPolicy` and `before_install` sufficient for install security and explicitly narrow or reject the audit-observer portion.
- **Defer To ClawHub Trust Design:** Hold the observer until maintainers define a broader ClawHub trust/provenance API that can supply the same audit events.

## Reproduction Assessment

Yes, at source level: the hook registry lists only `before_install`, and the ClawHub success path returns after metadata and telemetry without a post-install/update observer. A runtime repro is not required to prove this feature gap.

## Solution Assessment

Partly. Reusing `security.installPolicy` and `before_install` is the right blocking path, but the remaining audit capability should be specified as a redacted non-blocking completion hook rather than accepting the original event names and payload unchanged.

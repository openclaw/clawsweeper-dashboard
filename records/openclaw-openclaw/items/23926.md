## Label Justifications

- `P1`: Third-party skill installation is a live supply-chain security workflow, and scanner/audit integrations still lack the requested completion hook contract.
- `impact:security`: The issue is about scanning, blocking, warning, and auditing untrusted skills before or after they are accepted onto a user's machine.

## Summary

Keep open: current main now covers the blocking install-policy side for OpenClaw-managed skill installs, but it still lacks the requested plugin-visible post-install/update observer and the remaining API is security-sensitive.

## What This Changes

Request adds blocking skill pre-install and observational post-install hook events so security plugins can scan, block, warn, or audit skill installs across ClawHub, UI, sync, and plugin-shipped flows.

## Best Possible Solution

Keep `security.installPolicy` and `before_install` as the blocking path, then design a minimal redacted non-blocking skill install/update completion observer for OpenClaw-managed CLI, Gateway, and UI install paths.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a plugin-visible skill install/update completion observer now, and what redacted payload plus observer-failure semantics should it expose?

Rationale: Automation can prove the missing lifecycle surface, but choosing what install metadata plugins may see and whether observer failures affect an already-written install is a public plugin API and security-boundary decision.

Likely owner: steipete

Owner reason: This crosses ClawHub skill install behavior and public plugin lifecycle API shape, and steipete is the strongest product-routing signal from issue discussion plus adjacent path history.

Owner confidence: medium

Options:

- **Add Minimal Observer (recommended):** Add a non-blocking completion hook with redacted source, target, provenance, outcome, and timestamp metadata plus documented fail-open logging semantics.
- **Keep Pre-Install Only:** Declare `security.installPolicy` and `before_install` sufficient for install security, then narrow or close the audit-observer part separately.
- **Defer To ClawHub Trust Design:** Hold the observer until maintainers define a broader ClawHub trust/provenance API that can supply the same audit events.

## Reproduction Assessment

Yes, at source level. Current main exposes blocking install policy through `security.installPolicy` and `before_install`, but the hook registry and ClawHub success path show no post-install/update completion observer.

## Solution Assessment

Partly. Reusing `security.installPolicy` and `before_install` is the right blocking path, but the remaining audit capability should be specified as a redacted non-blocking completion hook rather than accepting the original event names and payload unchanged.

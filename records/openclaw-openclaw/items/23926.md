## Label Justifications

- `P1`: Third-party skill installation is a live supply-chain security workflow, and scanner/audit integrations still lack the requested completion hook contract.
- `impact:security`: The issue is about scanning, blocking, and auditing untrusted skills before or after they are accepted onto a user's machine.

## Summary

Keep open: current main covers the blocking side through `security.installPolicy` plus plugin `before_install`, but it still lacks the requested plugin-visible skill install/update completion observer for audit and compliance metadata.

## What This Changes

The issue requests blocking pre-install and observational post-install hook events for skill installation flows so security tools can scan, block, warn, or audit skill installs.

## Best Possible Solution

Keep `security.installPolicy` and `before_install` as the blocking path, then decide a minimal redacted, non-blocking skill install/update completion observer for OpenClaw-managed CLI, Gateway, and UI install paths, or explicitly reject that observer as out of scope.

Options:

- **Add Minimal Completion Observer (recommended):** Add a non-blocking completion hook with redacted source, target, provenance, outcome, and timestamp metadata plus documented fail-open logging semantics.
- **Keep Pre-Install Only:** Declare `security.installPolicy` and `before_install` sufficient for install security, then explicitly narrow or reject the audit-observer portion of this request.
- **Defer To ClawHub Trust Design:** Hold the observer until maintainers define a broader ClawHub trust and provenance API that can supply the same audit events.

## Reproduction Assessment

Yes, at source level: current main exposes blocking install policy through `security.installPolicy` and `before_install`, but the hook registry and ClawHub success path show no post-install/update completion observer.

## Solution Assessment

Partly. Reusing `security.installPolicy` and `before_install` is the right blocking path, but the remaining audit capability should be specified as a redacted non-blocking completion hook rather than accepting the original event names and payload unchanged.

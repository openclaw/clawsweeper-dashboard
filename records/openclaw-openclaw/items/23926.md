## Label Justifications

## Summary

Keep open: current main covers much of the blocking pre-copy side through `security.installPolicy` and plugin `before_install`, but it still lacks a plugin-visible post-install/update observer with audit/outcome metadata, and the public security lifecycle API needs maintainer direction.

## What This Changes

The issue requests blocking `skill:pre-install` and observational `skill:post-install` hook events for skill installation and update paths.

## Best Possible Solution

Keep `security.installPolicy` and `before_install` as the blocking path, then decide a minimal redacted, non-blocking skill install/update completion observer for OpenClaw-managed CLI, Gateway, and UI install paths.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose a plugin-visible skill install/update completion observer, and what redacted payload plus observer-failure semantics should it use?

Rationale: Automation can prove the missing lifecycle surface, but deciding what install metadata plugins may see and whether observer failures affect an already-written install is a public security and product boundary choice.

Likely owner: steipete

Owner reason: This choice crosses native ClawHub skill install behavior and public plugin lifecycle API shape, where the discussion and file history point most strongly to steipete for routing.

Owner confidence: high

Options:

- **Add Minimal Completion Observer (recommended):** Add a non-blocking completion hook with redacted source, target, provenance, outcome, and timestamp metadata plus documented fail-open logging semantics.
- **Keep Pre-Install Only:** Declare `security.installPolicy` and `before_install` sufficient for install security, then explicitly reject or narrow the audit-observer portion.
- **Defer To ClawHub Trust Design:** Hold the observer until maintainers define a broader ClawHub trust/provenance API that can supply the same audit events.

## Reproduction Assessment

Yes, at source level. Current main exposes blocking install policy through `security.installPolicy` and `before_install`, but the hook registry and ClawHub success path show no post-install/update completion observer.

## Solution Assessment

Partly. Reusing `security.installPolicy` and `before_install` is the right blocking path, but the remaining audit capability should be specified as a redacted non-blocking completion hook rather than accepting the original event names and payload unchanged.

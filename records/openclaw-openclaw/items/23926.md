## Label Justifications

- `impact:security`: The issue is about scanning, blocking, and auditing untrusted skills before or after they are accepted onto a user's machine.

## Summary

Keep open: current main and the latest release cover the blocking install decision through `security.installPolicy` and plugin `before_install`, but they still do not expose the requested plugin-visible skill install/update completion observer for audit and compliance metadata.

## What This Changes

The issue requests blocking `skill:pre-install` and observational `skill:post-install` hook events for skill installation security policy and audit workflows.

## Best Possible Solution

Keep `security.installPolicy` and `before_install` as the blocking path, then either define a minimal redacted non-blocking skill install/update completion observer for OpenClaw-managed install paths or explicitly reject that observer as out of scope.

Rationale: Source inspection proves the missing lifecycle surface, but deciding which install metadata plugins may see and whether observer failures affect an already-written install is a security and product boundary choice.

Likely owner: steipete

Owner reason: This decision crosses ClawHub skill install behavior and public plugin lifecycle API shape, and steipete is the strongest routing signal from discussion and file history.

Owner confidence: high

Options:

- **Add Minimal Completion Observer (recommended):** Add a non-blocking completion hook with redacted source, target, provenance, outcome, and timestamp metadata plus documented fail-open logging semantics.
- **Keep Pre-Install Only:** Declare `security.installPolicy` and `before_install` sufficient for install security, then narrow or reject the audit-observer portion explicitly.
- **Defer To ClawHub Trust Design:** Hold the observer until maintainers define a broader ClawHub trust/provenance API that can supply the same audit events.

## Reproduction Assessment

Yes, at source level: current main exposes blocking install policy through `security.installPolicy` and `before_install`, but the hook registry and ClawHub success path show no post-install/update completion observer.

## Solution Assessment

Partly. Reusing `security.installPolicy` and `before_install` is the right blocking path, but the remaining audit capability should be specified as a redacted non-blocking completion hook rather than accepting the original event names and payload unchanged.

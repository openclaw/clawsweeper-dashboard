## Label Justifications

- `P1`: Third-party skill installation is a live supply-chain security workflow, and the remaining lifecycle API gap blocks scanner/audit integrations even though part of the blocking path exists.
- `impact:security`: The issue is about scanning, blocking, and auditing untrusted skills before or after they are accepted onto a user's machine.

## Summary

Keep open: current main has the blocking install-policy foundation, but the requested skill install lifecycle surface is still incomplete because there is no plugin-visible post-install/update observer and the direct CLI ClawHub install path appears not to pass runtime config into policy evaluation.

## What This Changes

Requests blocking pre-install and observational post-install hook events for skill installs so trusted scanners or audit plugins can inspect, block, warn, or log untrusted skill installation.

## Best Possible Solution

Keep the existing `security.installPolicy` and `before_install` blocking seams, add a minimal redacted non-blocking skill install/update completion observer for OpenClaw-managed paths, and align direct CLI install with documented policy coverage.

Options:

- **Add minimal observer (recommended):** Add a non-blocking completion hook with redacted source/provenance/outcome metadata, documented fail-open logging semantics, and tests across CLI/Gateway/UI install and update paths.
- **Keep blocking only:** Declare `security.installPolicy` and `before_install` sufficient for install security, then close or split the audit-observer request as not planned.
- **Defer to ClawHub trust design:** Hold the observer until maintainers define a broader ClawHub trust/provenance API that can provide the same audit events safely.

## Reproduction Assessment

Yes, at source level. Current main exposes `security.installPolicy` and `before_install` for blocking install decisions, but the hook registry and ClawHub success path show no post-install/update completion observer; direct CLI install also appears not to pass config into the policy path.

## Solution Assessment

Partly. Reusing `security.installPolicy` and `before_install` is the right blocking path, but the remaining audit capability should be specified as a redacted completion observer rather than accepting the original event names and payload unchanged.

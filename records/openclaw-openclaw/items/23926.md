## Label Justifications

- `P1`: Third-party skill installation is a live supply-chain security workflow, and the missing completion observer blocks scanner/audit integrations even though the blocking pre-install path now exists.
- `impact:security`: The issue is about scanning, blocking, and auditing untrusted skills before or after they are accepted onto a user's machine.

## Summary

Keep open: current main now covers the blocking pre-install side through `security.installPolicy` and plugin `before_install`, including ClawHub-backed skill installs, but it still has no plugin-visible post-install/update completion observer with audit metadata.

## What This Changes

Request adds skill install lifecycle hook events so trusted scanners can block staged skill installs before copy and observe completed installs for audit/compliance.

## Best Possible Solution

Keep the existing blocking `security.installPolicy` and `before_install` seams, then design a minimal redacted non-blocking skill install/update completion observer with explicit ordering, failure semantics, docs, and coverage for ClawHub, upload, git/local, Gateway, UI, and update paths.

## Maintainer Decision

Rationale: Automation can identify the missing lifecycle surface, but choosing what install metadata plugins may see and whether observer failures can affect an already-written install is a security/product boundary decision.

Likely owner: steipete

Owner confidence: medium

Options:

- **Add minimal observer (recommended):** Add a non-blocking completion hook with redacted source/provenance/outcome metadata and documented fail-open logging semantics.
- **Keep pre-install only:** Declare `security.installPolicy` and `before_install` sufficient for install security and close or narrow the audit-observer request.
- **Defer to ClawHub trust design:** Hold the observer until maintainers define a broader ClawHub trust/provenance API that can supply the same audit events.

## Reproduction Assessment

Yes, at source level. Current main exposes `security.installPolicy` and `before_install` for blocking install decisions, but the hook registry and ClawHub success path show no post-install/update completion observer.

## Solution Assessment

Partly. Reusing `security.installPolicy` and `before_install` is the best blocking path, but the remaining audit capability should be specified as a redacted non-blocking completion hook rather than accepting the original event names and payload unchanged.

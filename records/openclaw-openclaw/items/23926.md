## Label Justifications

- `P1`: Third-party skill installation is a live supply-chain security workflow, and the missing completion observer blocks scanner and audit integrations even though the blocking pre-install path now exists.
- `impact:security`: The issue is about scanning, blocking, and auditing untrusted skills before or after they are accepted onto a user's machine.

## Summary

Keep open: current main covers the blocking install-policy side through `security.installPolicy` and plugin `before_install`, but it still lacks a plugin-visible post-install/update completion observer, and the remaining public security lifecycle contract needs maintainer direction.

## What This Changes

Request to add blocking `skill:pre-install` and observational `skill:post-install` hook events around OpenClaw-managed skill installs and updates for security scanning and audit integrations.

## Best Possible Solution

Keep the existing blocking `security.installPolicy` and `before_install` seams, then design a minimal redacted non-blocking skill install/update completion observer for OpenClaw-managed ClawHub, upload, git/local, Gateway, UI, and update paths.

Rationale: Automation can prove the missing lifecycle surface, but choosing what install metadata plugins may see and whether observer failures affect an already-written install is a public plugin API and security boundary decision.

Likely owner: steipete

Options:

- **Add minimal observer (recommended):** Add a non-blocking completion hook with redacted source, provenance, outcome, and target metadata plus documented fail-open logging semantics.
- **Keep pre-install only:** Declare `security.installPolicy` and `before_install` sufficient for install security, then close or split the audit-observer part separately.
- **Defer to ClawHub trust design:** Hold the observer until maintainers define a broader ClawHub trust and provenance API that supplies the same audit events.

## Reproduction Assessment

Yes, at source level. Current main exposes `security.installPolicy` and `before_install` for blocking install decisions, but the hook registry and ClawHub success/update path show no post-install/update completion observer.

## Solution Assessment

Partly. Reusing `security.installPolicy` and `before_install` is the right blocking path, but the remaining audit capability should be specified as a redacted non-blocking completion hook rather than accepting the original event names and payload unchanged.

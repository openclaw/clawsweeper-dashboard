## Summary

Keep open: current main and the latest release have the blocking install-policy foundation, but they still do not provide the requested plugin-visible post-install/update audit observer, and source inspection shows at least one direct CLI ClawHub install path still lacks config propagation into that policy evaluator.

## What This Changes

Request to add blocking pre-install and observational post-install lifecycle hooks around skill installation so policy plugins can scan, block, warn, and audit third-party skills.

## Best Possible Solution

Keep security.installPolicy and before_install as the blocking path, fix any remaining OpenClaw-managed coverage gaps, and design a minimal redacted non-blocking skill install/update completion observer only after maintainer security review.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a plugin-visible skill install/update completion observer now, and what redacted payload plus fail-open/fail-closed semantics should it expose after files or metadata are written?

Rationale: Automation can prove the missing lifecycle surface and the CLI config propagation gap, but choosing which install metadata plugins may see and whether observer failures can affect an already-written install is a security and product boundary decision.

Likely owner: steipete

Owner reason: The decision crosses native ClawHub install behavior and public plugin lifecycle API shape, where steipete is the strongest history and product-routing signal.

Owner confidence: high

Options:

- **Add minimal observer and close coverage gaps (recommended):** Add a non-blocking completion hook with redacted source, target, provenance, outcome, and timestamp metadata, and make sure every OpenClaw-managed install path passes config into the existing blocking policy evaluator.
- **Keep blocking policy only:** Declare security.installPolicy and before_install sufficient for install security, fix the CLI config propagation gap if confirmed, and close or narrow the audit-observer request separately.
- **Defer to broader ClawHub trust design:** Hold the observer until maintainers define a larger ClawHub trust/provenance API that can supply the same audit events without exposing unsafe local metadata.

## Reproduction Assessment

Yes, at source level. Current main exposes security.installPolicy and before_install for blocking decisions on covered paths, but the hook registry and ClawHub success path show no post-install/update completion observer, and direct CLI install does not pass config into the policy evaluator.

## Solution Assessment

Partly. Reusing security.installPolicy and before_install is the best blocking path, but the remaining audit capability should be specified as a redacted non-blocking completion hook rather than accepting the original event names and payload unchanged.

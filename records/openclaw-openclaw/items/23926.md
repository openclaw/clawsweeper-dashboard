## Label Justifications

- `impact:security`: The issue is about scanning, blocking, and auditing untrusted skills before or after they are accepted onto a user's machine.

## Summary

Keep open: current main and the latest release cover the blocking pre-install side through `security.installPolicy` and plugin `before_install`, but they still lack the requested plugin-visible post-install/update observer for skill install audit workflows.

## What This Changes

The issue requests blocking pre-install and observational post-install skill lifecycle hook events for ClawHub, UI, sync/update, and plugin-shipped skill installs.

## Best Possible Solution

Keep `security.installPolicy` and `before_install` as the blocking gate, then design a minimal redacted non-blocking skill install/update completion observer for OpenClaw-managed CLI, Gateway, and UI install paths.

Rationale: Automation can prove the missing lifecycle surface, but deciding what install metadata plugins may see and whether observer failures affect an already-written install is a security and product boundary choice.

Options:

- **Add Minimal Redacted Observer (recommended):** Add a non-blocking completion hook with redacted source, target, provenance, outcome, and timestamp metadata plus documented fail-open logging semantics.
- **Keep Pre-Install Only:** Declare `security.installPolicy` and `before_install` sufficient for install security, then explicitly narrow or reject the audit-observer portion.
- **Defer To ClawHub Trust Design:** Hold the observer until maintainers define a broader ClawHub trust/provenance API that can supply the same audit events.

## Solution Assessment

Partly. Reusing `security.installPolicy` and `before_install` is the right blocking path, but the remaining audit capability should be specified as a redacted non-blocking completion hook rather than accepting the original event names and payload unchanged.

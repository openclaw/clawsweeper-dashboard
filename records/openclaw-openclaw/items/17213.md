## Summary

Keep open: current main and the latest release still expose adjacent liveness and no-fake-progress safeguards, but they do not define the requested atomic run.begin/run.exec/run.commit-or-abort contract with structured abort blockers.

## What This Changes

The issue requests a transaction-style run lifecycle that guarantees intent notices are followed by execution evidence and a mandatory commit or abort with blocker details.

## Best Possible Solution

Define one additive lifecycle/process contract for intent, execution evidence, mandatory commit or abort, blocker details, ordering, and compatibility, then wire it through runtime, gateway protocol, session projection, clients, plugin-visible surfaces, docs, and regression tests.

- **Unify With Process Events (recommended):** Make begin, execution evidence, commit, abort, and blocker semantics part of one structured lifecycle/process-events design so clients get a single progress source of truth.
- **Create Separate Run Transaction API:** Add a distinct run.begin/run.exec/run.commit/run.abort contract and document how it composes with existing lifecycle, item, plan, and process streams.
- **Keep Adjacent Safeguards Only:** Treat strict-agentic retries, liveness states, and no-fake-progress tests as sufficient, then narrow this issue to documentation or telemetry follow-up.

## Reproduction Assessment

Yes for the source-level contract gap: current main lacks typed transaction lifecycle phases in event, protocol, runtime, session, and wait paths. The intermittent orphan-notice symptom itself was not live-reproduced from a deterministic trace.

## Solution Assessment

Unclear until maintainers choose the public lifecycle contract. A transaction-style flow is the right problem framing, but it should compose with structured process-event and anti-drift work rather than add a competing state machine.

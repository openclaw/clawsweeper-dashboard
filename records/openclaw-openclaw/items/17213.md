## Summary

Keep open: current main and the latest shipped release have narrower strict-agentic, liveness, retry, and no-fake-progress safeguards, but they still do not define the requested begin, execution, commit-or-abort lifecycle contract with structured abort blockers.

## What This Changes

The issue requests a transaction-style agent run lifecycle that guarantees announced intent is followed by execution evidence and an explicit commit or abort status.

## Best Possible Solution

Define one additive lifecycle/process contract for begin intent, execution evidence, mandatory commit or abort, structured blockers, ordering, compatibility, and client behavior, then wire it through runtime, gateway protocol, session projection, plugin-visible surfaces, docs, and regression tests.

- **Unify With Process Events (recommended):** Make begin, execution evidence, commit, abort, and blocker semantics acceptance criteria for one structured process/events contract so clients have a single source of lifecycle truth.
- **Create Separate Run Transaction API:** Add a distinct run.begin/run.exec/run.commit/run.abort contract and document how it composes with current lifecycle, item, plan, tool, and process streams.
- **Keep Existing Safeguards Only:** Treat strict-agentic retries, liveness states, and no-fake-progress coverage as sufficient, then narrow this issue to documentation or telemetry follow-up.

Yes for the source-level contract gap: current main lacks typed transaction lifecycle phases in event, protocol, runtime, session, and wait paths. The intermittent orphan-notice symptom itself was not live-reproduced from a deterministic trace.

## Solution Assessment

Unclear until maintainers choose the public lifecycle contract. A transaction-style flow is the right problem framing, but it should compose with structured process/event work rather than add a competing state machine.

## Summary

Keep this PR open. The hard process-boundary recovery is well motivated and strongly proven, but the current implementation knowingly requests an ineffective whole-gateway in-process restart on unmanaged installations, disrupting unrelated channels without releasing the guarded Telegram lane; after that is corrected, an owner still needs to approve the permanent generic channel snapshot contract.

## What This Changes

The PR detects Telegram spool handlers that remain wedged after abort, reports a generic process-restart-required channel status, routes health recovery through gateway restart scheduling, and persists per-account escalation budgets in SQLite.

## Best Possible Solution

Keep the hard-boundary design, but only initiate automatic recovery when the restart path can guarantee process replacement—or add an explicit hard-restart capability/result that suppresses ineffective in-process fallback—then land the generic snapshot signal only after its cross-channel contract is owner-approved.

## Summary

Keep open: current main and the latest release still deliver exec approval requests through the existing immediate request/forward/resolve path, and there is no hold window or agent-accessible retraction action. This is useful approval UX work, but it needs maintainer design because it adds config, Gateway protocol/RPC surface, forwarding timing semantics, and Codex/native approval contract changes.

## What This Changes

Request an opt-in `approvals.exec.holdMs` buffering window plus an agent-accessible retraction action so self-corrected exec approval prompts can be cancelled before forwarded delivery.

## Best Possible Solution

Define the opt-in approval hold/retract design first, then implement it across config schema/help, Gateway approval methods/events, forwarding delivery, audit logging, Codex/native approval contracts, docs, and regression tests with default `0` preserving instant delivery.

## Reproduction Assessment

Yes for the current behavior: source inspection shows an exec approval request is registered, broadcast, and forwarded immediately, with only resolve/expiry paths afterward. I did not run live channel proof because the remaining work is an opt-in feature design rather than a reported runtime regression.

## Solution Assessment

Unclear until maintainer design is settled: a hold-and-retract window plausibly targets the abandoned-versus-intended signal better than a denylist, but it is not a narrow bug fix and must be designed across config, Gateway, forwarding, and Codex/native approval contracts.

## What This Changes

Request to add an explicit Slack outbound DM recipient allowlist, such as `dmAllowTo` or `allowTo`, for `openclaw message send` targets.

## Best Possible Solution

Approve one explicit outbound recipient policy shape, keep inbound `allowFrom` semantics unchanged, and then implement Slack enforcement with schema, docs, logging, and focused send-path coverage.

- **Route Through Plugin Hooks:** Defer Slack config and instead use or extend `message_sending` target context so a ClawHub or npm plugin owns recipient policy.
- **Decline First-Class ACL:** Keep explicit operator sends unrestricted under the trusted-operator model and document prompt/tool/plugin workarounds for deployments that want extra hardening.

## Reproduction Assessment

Yes for the source-level capability gap: current main and v2026.6.11 support Slack `user:<id>` DM targets but have no outbound recipient allowlist to enforce. This is not a bug reproduction because documented `allowFrom` is inbound sender authorization.

## Solution Assessment

Unclear until maintainers choose the policy boundary. A new explicit outbound policy is plausible; overloading inbound `allowFrom` would be the wrong contract, and a plugin-hook path may be preferable if maintainers want core to stay lean.

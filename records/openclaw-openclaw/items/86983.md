## Summary

Keep open: current main and v2026.6.11 still lack a Slack outbound DM recipient allowlist, and the remaining work is a security-sensitive feature/config decision rather than an implemented fix or a documented `dmPolicy` bug.

## What This Changes

The issue requests an outbound Slack DM recipient allowlist such as `allowTo`/`dmAllowTo` to block `openclaw message send` from DMing non-approved users.

## Best Possible Solution

Design a canonical outbound target policy that preserves current behavior when unset and enforces recipient allowlists at the shared message-action/channel boundary before Slack delivery.

Options:

- **Add explicit outbound target policy (recommended):** Add a documented allowTo-style recipient policy with schema, docs, tests, and enforcement before Slack delivery while keeping `allowFrom` inbound-only.
- **Fold into broader guardrails:** Track Slack recipient allowlisting as one acceptance case under the broader outbound guardrails work at https://github.com/openclaw/openclaw/issues/87870.
- **Decline core allowTo for now:** Keep the trusted-operator model unchanged and document that `dmPolicy` and `allowFrom` do not constrain explicit operator sends.

## Reproduction Assessment

Yes, at source level: current main sends explicit Slack user targets through the CLI/outbound/Slack path without any `dmAllowTo` or `allowTo` check. It is not reproduced as a bug against a documented contract because docs define `dmPolicy` and `allowFrom` as inbound sender access.

## Solution Assessment

Unclear until maintainers choose the product boundary. The requested allowTo direction is plausible, but the maintainable fix should be an explicit outbound target policy with schema/docs/tests rather than overloading inbound `allowFrom`.

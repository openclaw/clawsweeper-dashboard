## Summary

Keep open. Current main and the latest release partially solve the runtime gap with global transient retry/backoff for recurring cron failures, but the requested per-job `cron add` / `cron edit` retry controls and retrying status semantics are still absent and product/API-sensitive.

## What This Changes

Request per-cron-job retry count, retry delay, and optional backoff controls for failed recurring cron jobs before the next natural schedule.

## Best Possible Solution

Keep this as the canonical per-job cron retry design issue and land an additive, backward-compatible cron contract only after maintainers settle flags, defaults, storage, and status semantics.

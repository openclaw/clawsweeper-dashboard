## Summary

Keep open. Current main and `v2026.6.11` already have global transient retry/backoff for recurring cron failures, but the requested per-job `cron add` / `cron edit` retry controls and retrying status semantics are still missing and require a public API/product decision.

## What This Changes

The issue requests configurable per-job retry count, retry delay, and optional backoff controls for failed cron jobs.

## Best Possible Solution

Keep the shipped global retry behavior, then either add a job-level retry policy with CLI, storage, docs, list/show status, and focused upgrade tests, or document that `cron.retry` is intentionally deployment-wide only.

Options:

- **Add Per-Job Retry Policy (recommended):** Add stored job-level retry settings, wire them through cron add/edit/show/list/docs, and let global `cron.retry` remain the default when a job does not override it.
- **Keep Global Retry Only:** Keep `cron.retry.maxAttempts` and `cron.retry.backoffMs` as the supported surface and close or narrow this issue to documentation/status wording.
- **Fold Into Guardrails Work:** Defer per-job controls and make the broader reason-aware cron guardrail issue own retry policy, retry reasons, and circuit-breaker semantics together.

## Summary

Keep open. Current main and v2026.6.11 already have global transient retry/backoff for recurring cron failures, but the requested per-job `cron add` / `cron edit` retry count, delay, and backoff controls are still absent and need maintainer-approved CLI, Gateway, storage, and scheduler semantics.

## What This Changes

Request per-job retry count, retry delay, and optional backoff controls for cron jobs so failed recurring jobs can retry before their next natural schedule.

## Best Possible Solution

Keep this issue as the canonical request and land an additive, maintainer-approved per-job retry design that preserves global retry/backoff safeguards and documents CLI, Gateway, storage, scheduler, and alert semantics.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 expose global cron retry/backoff, while the requested per-job CLI flags, Gateway fields, and persisted job retry policy are absent.

## Solution Assessment

Unclear until maintainers choose the public contract. Per-job retry controls are plausible, but the best fix must define precedence with global `cron.retry`, side-effecting retry defaults, edit/clear semantics, and user-visible retry state.

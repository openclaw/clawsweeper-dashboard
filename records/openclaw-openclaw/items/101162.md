## Label Justifications

- `P1`: The issue affects the public Gateway stop path for external clients and can leave an active tool subprocess running after the UI reports an abort.
- `impact:session-state`: The reported state diverges between the aborted chat/API stream and the still-running embedded agent/tool process.
- `impact:ux-friction`: External UI users can click Stop and believe the run stopped while the workaround is injecting `/stop` into the chat session.
- `maturity:stable`: The affected Gateway Chat RPC surface maps to Gateway RPC APIs and Events under `gateway-runtime`, which is scored M4 Stable.

## Summary

Keep open: current main and the latest release still keep `chat.abort` on the Gateway abort-controller/queued-run path, while `/stop` reaches embedded-run, queue, and subagent cleanup; the reported false-abort result remains source-reproducible and is not owned by a merged fix.

## What This Changes

The issue asks for Gateway `chat.abort` to stop the same active embedded agent/tool subprocesses, queues, and requester subagents that `/stop` stops, or to expose an equivalent RPC for external clients.

## Best Possible Solution

Implement a shared, authorization-preserving session stop path so `chat.abort` can stop the target active embedded run/tool process and requester-owned subagents/queues without broadening multi-owner session cleanup.

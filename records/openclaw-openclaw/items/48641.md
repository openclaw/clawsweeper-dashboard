## Summary

Keep open: current main and v2026.6.11 still preserve Discord account-scoped allowFrom precedence, and the direct union-style repair was closed because it changes authorization semantics.

## What This Changes

The issue asks OpenClaw to stop silently dropping inbound Discord DMs from an allowlisted user in a multi-account allowlist setup.

## Best Possible Solution

Have maintainers define the Discord DM account-inheritance and multi-account ownership contract, then implement it in the Discord plugin with focused precedence tests, docs updates, diagnostics for denied DMs, and live DM proof.

Question: Should Discord account-scoped allowFrom replace the root allowlist as the current docs/tests say, or should root and account allowFrom be unioned for inbound DMs?

Rationale: The obvious fix changes who is authorized to start Discord DM agent sessions, so code inspection alone cannot choose the intended security contract.

Likely owner: steipete

Owner reason: The decision centers on shared account config and Discord DM access semantics where this owner has the strongest recent history.

Owner confidence: high

Options:

- **Preserve account narrowing by default (recommended):** Keep account-scoped allowFrom as a narrowing boundary unless maintainers add a documented migration or explicit opt-in broader behavior.
- **Union root and account allowFrom:** Allow root-listed users through account DMs too, which addresses the proposed root-cause path but broadens access for accounts that were intentionally narrower.
- **Require explicit per-account DM allowlists:** Treat the issue as diagnostics/docs plus setup validation and require users to put every allowed DM sender on the receiving account.

## Reproduction Assessment

Partly. Current source proves account-level allowFrom takes precedence over root allowFrom and denied DMs can return null before routing, but the exact live multi-account Discord DM drop was not reproduced here.

## Solution Assessment

No. The closed union PR was plausible, but it is not clearly the best fix because it widens account authorization; maintainers should choose the security contract before a repair branch changes behavior.

## Summary

Keep open: current main and v2026.6.11 still preserve Discord account-scoped `allowFrom` precedence, the direct union PR was closed unmerged because the semantics need design review, and the remaining fix changes an authorization boundary.

## What This Changes

Discord inbound DMs from an allowlisted user are reported as silently dropped while outbound DMs and guild messages work.

## Best Possible Solution

Have maintainers define the Discord root-versus-account DM authorization contract, then implement that contract with focused precedence tests, docs updates, denied-DM diagnostics, and live multi-account DM proof.

Question: Should Discord account-scoped `allowFrom` keep narrowing/replacing the root allowlist, or should root and account `allowFrom` be unioned for inbound DMs?

Rationale: The apparent repair can broaden who may start Discord DM agent sessions on narrowed accounts, so code inspection alone should not choose the security contract.

Likely owner: steipete

Owner reason: This decision crosses Discord account config, shared DM access, and security-sensitive sender admission, where history and live timeline point most strongly to steipete.

Owner confidence: high

Options:

- **Preserve Account Narrowing (recommended):** Keep account-scoped `allowFrom` as the default narrowing boundary and address this issue through explicit account configuration, diagnostics, or a separately approved migration.
- **Union Root And Account Lists:** Allow root-listed users through account DMs too, which addresses the reported root-cause hypothesis but broadens access for accounts that were intentionally narrowed.
- **Add Explicit Inheritance Policy:** Introduce a documented opt-in inheritance mode only if maintainers want both root convenience and account-specific narrowing.

## Reproduction Assessment

Partly: source inspection shows account-level `allowFrom` takes precedence over root `allowFrom` and denied DMs return before routing. I did not establish a live multi-account Discord DM reproduction for the exact silent-drop scenario.

## Solution Assessment

No for a direct union fix: it is plausible but not clearly best because it widens account authorization. The safer next step is a maintainer decision on the root-versus-account contract before implementation.

## Summary

Keep open: current main still has a source-reproducible path where a C-prefixed Slack MPIM event with missing `channel_type` and unresolved channel info falls back to `channel`, while explicit MPIM events route as `group`, so the reported session split remains a real narrow Slack bug.

## What This Changes

The issue reports that Slack MPIM inbound messages without `channel_type` can classify the same room as `channel` instead of `group`, splitting per-agent sessions.

## Best Possible Solution

Fix the Slack monitor path so known MPIM channel type is carried forward from explicit events or channel info and missing-type bot-authored events cannot create a second `slack:channel:<channelId>` session for the same group DM.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, from source inspection: a C-prefixed Slack MPIM event with missing `channel_type` and unresolved channel info normalizes to `channel`, then routing uses the channel session key family. I did not run a live Slack workspace reproduction in this read-only review.

## Solution Assessment

Yes, the best narrow fix is in the Slack plugin's monitor type-resolution path: cache or reuse authoritative MPIM type from explicit events or channel info before routing, with regression tests for bot-authored missing-type MPIM messages. A broader fail-closed change for all unknown C-prefixed rooms should be avoided unless maintainers choose it explicitly.

## Summary

Keep open: this is a focused Mattermost thread-context fix, but the current patch still leaves a blocking inbound availability issue because large server threads can trigger unbounded sequential user lookups before the history is trimmed.

## What This Changes

Adds a Mattermost thread-history fetch/backfill path that seeds channel thread history from `GET /posts/{id}/thread` once per agent session, with unit coverage for seed, skip, rotation, and error behavior.

## Best Possible Solution

Keep the session-gated backfill design, but bound the recovered post set before any username lookups and prove long-thread recovery only does O(historyLimit) work.

## Reproduction Assessment

Yes at source level: current main builds Mattermost thread context from a process-local `channelHistories` map and has no server-side thread fetch when that window is empty. I did not run a live Mattermost repro in this read-only review, but the PR supplies live Mattermost proof for the central recovery behavior.

## Solution Assessment

No as submitted: session-id gating and a bounded thread fetch are the right direction, but the best fix must cap the server-thread posts before username resolution so recovery cannot stall on large threads.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.86

Full review comments:

- **[P1] Cap backfill before resolving users:** `extensions/mattermost/src/mattermost/monitor.ts:544-552`
  - body: The new timeout only bounds the `/posts/{id}/thread` request. Once that returns, this loop still walks every post in the server thread and awaits `resolveUserInfo` before trimming to `historyLimit`, so a large cold thread can issue many sequential Mattermost user lookups in the inbound reply path and stall recovery well beyond the intended bound. Please cap to the last eligible `historyLimit` posts before username resolution, or otherwise make the per-post lookups bounded.
  - confidence: 0.86

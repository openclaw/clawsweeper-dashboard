## Summary

Keep open: current main and v2026.6.11 still lack a per-binding Discord nickname or ordinary routed-reply identity override, and the remaining work needs maintainer product/security direction before implementation.

## What This Changes

Request to add an optional Discord binding-level identity override so one bot token can show distinct agent names in different bound channels.

## Best Possible Solution

Have maintainers choose one Discord plugin-owned visible-identity model, likely webhook persona delivery if approved, with explicit schema, credential handling, docs, tests, and live Discord proof.

Question: Should OpenClaw support ordinary Discord routed-reply visible identity overrides for bindings, and should that be implemented as webhook persona delivery, bot self-profile mutation, a binding nickname field, or deferred?

Rationale: The current code lacks this surface, and implementing it would create a public config/API plus credential-backed Discord identity behavior that automation should not choose without maintainer product and security intent.

Likely owner: onutc

Owner confidence: high

Options:

- **Approve webhook persona delivery (recommended):** Add a Discord plugin-owned routed-reply identity path that reuses webhook username/avatar delivery with explicit secret handling, fallback behavior, docs, tests, and live Discord proof.
- **Coordinate with self-profile work:** Treat this as part of the Discord self-profile decision and add nickname/avatar mutation only if maintainers accept the identity semantics and security boundary.
- **Defer per-binding identity:** Keep current bot-account replies plus thread-bound webhook persona behavior and ask users to use multiple bot accounts or existing thread-bound flows for now.

## Solution Assessment

Unclear as proposed: setting a bot nickname per response is probably not the narrowest maintainable contract, while webhook persona delivery better matches the existing Discord outbound primitive. Maintainers still need to choose the public contract and security boundary first.

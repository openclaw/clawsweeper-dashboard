## What This Changes

The issue reports that a systemd-managed Gateway can fail Kimi auth and fall back to Ollama even though `models status --agent` reports `env: KIMI_API_KEY` as usable.

## Best Possible Solution

Define the managed-Gateway credential contract, then align systemd service-env rendering or runtime env application, `models status --agent` wording/JSON, Kimi docs, and a focused systemd-style regression test around that contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For systemd-managed Gateway turns, should config `env.KIMI_API_KEY` be treated as an effective runtime credential, or should durable provider credentials be required in the per-agent auth profile store with `models status` labeling config env as CLI/config-only?

Rationale: Both choices touch auth-provider behavior, daemon secret materialization, status semantics, and docs; the repo policy treats auth/config/default changes as compatibility-sensitive, so automation should not pick the credential contract alone.

Likely owner: Vincent Koc

Owner reason: The current blame and recent review history point to Vincent across the active config, gateway startup, service-env marker, daemon install, and status surfaces.

Owner confidence: medium

Options:

- **Support config env in managed Gateway (recommended):** Materialize or apply config env in the managed Gateway runtime path, then prove systemd Kimi turns and status agree without writing secrets into unsafe surfaces.
- **Require auth profiles for daemon turns:** Keep systemd service env minimal, update docs and `models status --agent` to distinguish config-only env from managed-runtime auth, and steer users to per-agent API-key profiles.
- **Split status and runtime semantics:** Keep current runtime behavior but change status output to warn when an env credential is visible only to the CLI process and not proven in the managed Gateway runtime.

## Reproduction Assessment

Yes at source level, but not as a live systemd Kimi run in this review. Current code and tests show config env keys can be omitted from service env while status resolves env-backed auth from the CLI process, and the reporter provided sanitized Gateway failover logs.

## Solution Assessment

Unclear until maintainers choose the intended daemon credential contract. The linked PR's duplicate startup `applyConfigEnvVars` call is not the best fix; a coordinated service-env/runtime/status/docs/test change is safer.

Keep open: current main does not provide enough live proof to close this Kimi/systemd auth report, and the remaining question is the managed-service credential contract rather than a small Kimi-only code patch.

## What This Changes

The issue reports that Kimi Coding configured through `env.KIMI_API_KEY` can look available in `models status` while a systemd-managed Gateway turn treats Kimi auth as unavailable and fails over.

## Best Possible Solution

Define the daemon credential contract once, then align systemd service-env rendering, Gateway startup env application, `models status --agent` output, Kimi docs, and a live or Crabbox regression proof around that contract.

Question: For managed systemd Gateways, should provider API keys from the config `env` block be a supported runtime credential source, or should daemon users be steered to `.env`, SecretRef, or per-agent auth profiles instead?

Rationale: Both options affect credential persistence and status semantics; automation should not choose whether OpenClaw should materialize config secrets into supervisor env files or change the documented Kimi setup path.

Likely owner: vincentkoc

Owner confidence: medium

Options:

- **Support config env in daemons (recommended):** Keep the documented Kimi config path supported and add focused service-env/runtime/status tests plus live proof that systemd Gateway turns use it consistently.
- **Make daemon auth profile or dotenv only:** Update docs and `models status` so config-env credentials are not presented as effective daemon runtime auth unless they are in `.env`, SecretRef, or the per-agent auth store.
- **Fold into broader env unification:** Defer this specific Kimi/systemd case to the broader env-source precedence issue, accepting that this report remains unresolved until that contract lands.

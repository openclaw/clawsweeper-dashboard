## What This Changes

The issue reports Kimi Coding env-based auth appearing available in CLI status but failing in systemd-managed Gateway turns, causing auth-class failover to the configured Ollama fallback.

## Best Possible Solution

Define the managed-Gateway credential contract, then align systemd service-env rendering, Gateway startup env application, `models status --agent` output, Kimi docs, and focused regression or live systemd proof around that contract.

Rationale: The code already applies config env during config snapshot reads, but service generation intentionally avoids embedding plain config-env values; choosing the fix requires a maintainer decision about credential persistence, diagnostics truthfulness, and docs guidance.

Owner confidence: medium

Options:

- **Keep config env supported process-locally (recommended):** Preserve the documented Kimi config example, prove systemd Gateway startup applies it for real turns, and update status/docs/tests without writing plaintext secrets into generated service files.
- **Move managed services to auth profiles or SecretRef:** Change Kimi docs and `models status` wording so config env is not presented as durable managed-service auth unless backed by an auth profile or SecretRef service env path.
- **Materialize plain config env into service files:** Render literal config-env values into systemd/LaunchAgent service env files, accepting the broader credential-persistence and upgrade implications.

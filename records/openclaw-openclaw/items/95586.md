## Summary

Keep open: the report is still a valid auth/provider contract problem for managed Gateway runs, and the linked fix PR is closed unmerged. Current source shows overlapping config-env, service-env marker, runtime auth, and `models status` paths, but not a settled maintainer decision for whether config `env.KIMI_API_KEY` is a durable systemd Gateway credential source.

## What This Changes

Configured Kimi Coding models can fail over as unauthenticated in a systemd-managed Gateway when `KIMI_API_KEY` is visible to config/status diagnostics but not to the daemon runtime auth path.

## Best Possible Solution

Define the managed-Gateway credential contract, then align service-env rendering, Gateway startup env application, `models status --agent`, Kimi docs, and focused regression proof around that contract.

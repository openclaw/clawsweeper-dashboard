## What This Changes

The issue asks OpenClaw to make Kimi API keys declared in config env resolve consistently for systemd-managed Gateway turns and CLI status.

## Best Possible Solution

Define one managed-Gateway credential contract, then align Gateway startup env application, systemd/service-env rendering, `models status --agent` semantics, Kimi docs, and focused regression or live proof around that contract.

Required: true

Kind: product_direction

Question: For systemd-managed Gateway turns, should root config env provider keys be treated as durable runtime credentials, service-managed environment entries, or CLI/status-only diagnostics?

Rationale: The code already applies config env during config snapshot reads, while the generated service environment intentionally avoids embedding literal config env values; choosing the wrong fix can either leave Kimi turns failing or change credential storage semantics for existing services.

Likely owner: steipete

Owner reason: This decision spans config compatibility, service credential storage, docs/status semantics, and setup UX, which matches Peter's recent config/env and policy history.

Owner confidence: medium

Options:

- **Keep config-env runtime support (recommended):** Confirm config env is supported for managed Gateway turns, add live/systemd proof plus tests, and make `models status` reflect the same runtime context.
- **Move users to auth profiles:** Declare config env as setup/config-only for managed services, update Kimi docs/status wording, and steer non-default agents toward per-agent auth profiles.
- **Persist service-managed env values:** Materialize config env through a protected service env file or SecretRef path, accepting the upgrade and credential-storage review burden.

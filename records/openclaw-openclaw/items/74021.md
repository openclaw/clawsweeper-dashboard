## Label Justifications

- `P2`: The issue describes meaningful provider compatibility and empty-answer failures, but current main has partial mitigations and the remaining work is broad product design rather than an urgent universal regression.
- `impact:security`: Using or displaying raw reasoning requires an explicit privacy and redaction boundary because reasoning may contain internal context or sensitive data.
- `impact:message-loss`: Affected models can produce useful answers only in reasoning fields while visible content is empty, leaving users with missing or fallback replies.
- `impact:auth-provider`: The behavior depends on provider-specific reasoning request formats, model capabilities, and response normalization.

## Summary

Keep open: current main now ingests several native reasoning fields and has provider-specific visible-output controls and empty-turn recovery, but the requested privacy-safe extraction policy, compatibility reporting, and clear contract for reasoning-only final answers remain unresolved product work.

## What This Changes

Requests reasoning-field ingestion, visible-final-answer policy, and benchmark/reporting distinctions for native reasoning model outputs.

## Best Possible Solution

Keep reasoning private and structurally separate in core, let provider plugins enforce or normalize visible final output for known model contracts, and add privacy-safe aggregate compatibility instrumentation that records extraction source without persisting raw reasoning by default.

Owner confidence: medium

Options:

- **Provider-owned normalization (recommended):** Keep core reasoning private, add provider hooks for visible-output enforcement or narrowly approved final promotion, and expose only aggregate compatibility diagnostics by default.
- **Generic opt-in extraction:** Add a core model/profile mode that may promote reasoning into final output, with explicit redaction, persistence, channel, tool, and JSON-task restrictions.
- **Reporting-only scope:** Implement compatibility counters and extraction-source reporting first, leaving runtime reasoning-only answers unsupported until a later policy decision.

## Solution Assessment

No, not as one generic core implementation. The safer maintainable direction is provider-owned visible-output normalization plus privacy-safe reporting, with any generic reasoning promotion requiring an explicit maintainer-approved security contract.

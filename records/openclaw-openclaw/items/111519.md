## Summary

Keep this open as a concrete P1 delivery regression. A source-level reproduction isolates the failure before Telegram transport: Codex intentionally supplies separate sandbox and live-run session keys, but the message tool still receives the sandbox key for terminal source-reply receipt handling, so it can read the wrong recovery claim and reject the normal reply path. This is distinct from the Telegram reasoning-stream/reconnect scenario in https://github.com/openclaw/openclaw/issues/101839, which includes transport failures and an ambiguous-send recovery state.

## What This Changes

Repair Codex-run message delivery so terminal source-reply ownership looks up the live run session rather than a sandbox-only session while preserving the sandbox key for tool capability and authorization checks.

## System Context

A Telegram DM starts an agent run through the Codex app-server plugin, which builds OpenClaw tools with both sandbox and live-run session context. The message tool records and completes source-reply delivery against session state; choosing the wrong key makes the normal reply receipt appear stale and pushes delivery into a delayed fallback.

## Architecture Diagram

flowchart LR
  A[Telegram DM] --> B[Gateway agent turn]
  B --> C[Codex app-server]

  D --> E[Message tool]

  F --> G[Telegram normal reply]

## Best Possible Solution

Add an explicit live run-session key to the message-tool receipt/session-routing inputs, use it only where delivery ownership and transcript/session state require the live run, retain the sandbox key for capability and policy checks, and cover both split-key and equal-key runs with focused regression tests.

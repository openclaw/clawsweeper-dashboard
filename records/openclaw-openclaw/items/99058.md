## Summary

## What This Changes

## Best Possible Solution

Use the existing strict content-length parser or an equivalent digit-only safe-integer check before any no-body read, add malformed-header regression coverage, and keep the intentional no-length fail-closed policy visible in proof.

## Reproduction Assessment

Yes, source-reproducible: the PR head parses `Content-Length` with `Number(header)`, so malformed values such as `1e3` pass as finite non-negative lengths. Existing repository parsers and tests treat that header shape as invalid.

## Solution Assessment

No: the pre-read guard is the right layer for this no-body branch, but the best fix needs strict digit-only safe-integer parsing before trusting the header. Reusing `parseMediaContentLength` or matching its contract would keep the patch narrow.

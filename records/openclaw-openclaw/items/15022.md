## Summary

Keep open: current main and latest release still lack the requested opt-in coalescing or final-only delivery policy for tool-interleaved assistant text, and the remaining work needs maintainer choice on delivery semantics and config shape.

## What This Changes

Request a config option or delivery policy that merges text blocks from one tool-interleaved agent turn into a single outbound channel message.

## Best Possible Solution

Keep this as the canonical core reply-pipeline policy issue, choose opt-in coalescing versus final-only semantics, then implement the chosen mode across final payload assembly and block-streamed tool boundaries with schema, docs, and regression coverage.

## Maintainer Decision

Question: Should OpenClaw add an opt-in core delivery mode for tool-interleaved assistant text, and if so should it merge all text blocks, deliver only the final block, or rely on the existing message-tool-only visible reply mode instead?

Rationale: The source path is clear, but the user-visible contract conflicts with existing block-boundary preservation, Discord ordering work, and OpenClaw's high bar for new config/default surfaces.

Likely owner: Peter Steinberger

Owner confidence: high

Options:

- **Define an opt-in coalesce/final-only mode (recommended):** Choose the semantics and config shape first, then implement the policy across final payload and block-streamed tool-boundary delivery.
- **Rely on message-tool-only visible replies:** Treat existing `messages.visibleReplies: "message_tool"` as the supported suppression path and narrow this issue to any concrete gap that mode cannot cover.
- **Keep current automatic delivery:** Preserve current block/message boundaries and document prompt/message-tool workarounds instead of adding a new core delivery mode.

## Reproduction Assessment

Yes, at source level: current main preserves multiple assistant text payloads, sends reply items separately, flushes block replies before tool execution, and has no requested turn-level coalescing/final-only config. I did not run live Telegram or BlueBubbles proof in this read-only review.

## Solution Assessment

Unclear until maintainers choose the delivery contract. A hold/defer or final-only mode is plausible, but it should be opt-in and must cover both final payload assembly and streamed tool-boundary flushing without breaking existing message-boundary behavior.

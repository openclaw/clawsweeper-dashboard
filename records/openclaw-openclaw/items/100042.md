## Summary

Keep open: the protected `maintainer` label alone prevents cleanup closure, and current main still has the core mismatch between absolute aggregate tool-result truncation and window-relative compaction routing. Recent main appears to partially protect fresh trailing tool results, but repeated aggregate truncation is still not itself a compaction/diagnostic trigger.

## What This Changes

The issue requests a fix for long large-context sessions where aggregate live tool-result truncation can hide fresh tool output without triggering compaction or an operator-visible warning.

## Best Possible Solution

Keep this maintainer-owned issue open and fix the core runtime so repeated aggregate truncation participates in context-pressure handling, fresh tool output remains visible, and operators get a clear diagnostic without adding a broad new config surface.

## Reproduction Assessment

Yes at source level, but not by live run in this read-only review. Current main still combines an absolute aggregate prompt-history cap with window-relative compaction routing, while existing tests only prove part of the fresh-trailing-output protection.

## Solution Assessment

Unclear: the requested direction is valid, but maintainers should choose the exact policy. Raising caps or adding another knob would be too narrow; the better fix is a bounded runtime policy connecting aggregate truncation pressure to compaction and diagnostics.

## Summary

This is a valid Feishu bug fix at the correct plugin boundary, but the implementation only classifies errors delivered through the dispatcher’s direct `onError` path. Feishu streaming cards are enabled by default, and their CardKit update/close methods absorb failed writes and return a visibility result, so a 230028 rejection there still reaches the generic no-visible-content fallback. The linked issue should remain open until that default path is covered.

## What This Changes

Adds Feishu error-code 230028 classification and queues one neutral content-policy rejection notice, with tests for wrapped errors, non-streaming delivery, partial delivery, duplicate suppression, and notice-send failure.

## Best Possible Solution

Propagate a structured Feishu audit-rejection signal from both SDK message sends and CardKit streaming writes into the dispatcher, then queue exactly one neutral notice without modifying, retrying, or bypassing the rejected content.

## Reproduction Assessment

Yes, at source level with high confidence: Feishu streaming is the documented default, CardKit write errors are reduced to false/logging, and Feishu documents 230028 on those write APIs. The related closed PR also provides a real tenant reproduction of the misleading fallback.

## Solution Assessment

No. Classifying 230028 in the plugin-owned dispatcher is the right direction, but handling only direct dispatcher delivery errors misses deferred CardKit writes on the default streaming path; the narrowest complete fix is to preserve and classify that streaming failure signal too.

## Summary

This remains a useful, well-proven fix for the linked startup race, but the unchanged catch-all retry policy still delays permanent Tailscale failures and should be narrowed before merge.

## What This Changes

The PR adds up to three 500 ms-spaced attempts for each Tailscale status JSON read used by hostname discovery and adds regression coverage for a first-call failure followed by success.

## Best Possible Solution

Keep retrying at the hostname status-read boundary, but restrict retries to recognized transient daemon-readiness execution failures and immediately propagate permanent execution, parsing, and semantic failures.

## Maintainer Decision

## Reproduction Assessment

Yes. The exact PR head was exercised through three real macOS/Homebrew Serve cycles with a deterministic first-call daemon-socket failure, and each cycle recovered the actual tailnet hostname on its second attempt.

## Solution Assessment

No, not as written. Retrying the status read is narrower and more maintainable than an unconditional post-Serve sleep or new binary-path configuration, but retry eligibility must exclude failures that cannot recover with time.

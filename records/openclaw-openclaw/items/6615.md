## Summary

Keep this issue open. Current main and v2026.6.11 still expose allowlist-only exec policy, while the linked open implementation PR is the active candidate and must be resolved before the issue can close; the remaining questions are security-policy semantics, cross-host parity, and upgrade-safe persisted configuration.

## What This Changes

Add deny-over-allow command and argument patterns to exec approvals so selected dangerous commands require human approval under otherwise permissive policies.

## Best Possible Solution

Adopt one additive deny-over-allow overlay, rather than parallel `security: denylist` and `ask: on-match` modes, that evaluates command and parsed-argument patterns before permissive or durable allow decisions on both gateway and node hosts, preserves rules through all config/protocol writes, and clearly documents the guardrail’s limits.

## Risks / Open Questions

- A denylist is necessarily incomplete, so documentation and UI must not present it as a comprehensive security boundary or substitute for sandboxing and restrictive allowlists.
- Deny-over-allow precedence must remain identical across gateway-host exec, node-host `system.run`, persisted approvals files, global configuration, and per-agent configuration; one-sided enforcement would create bypass-like policy drift.
- Adding persisted deny rules is upgrade-sensitive: schema validation, normalization, save round-trips, protocol writes, and older UI/CLI clients must not silently drop or weaken configured rules.
- Maintainers still need to choose whether matches always force human approval, may hard-deny, and whether `allow-once` can override a match without permitting durable `allow-always` trust.

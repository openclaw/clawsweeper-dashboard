## Summary

Current main still lacks a native deny-over-allow exec policy, while the linked open pull request is the active implementation candidate; keep this issue open until maintainers settle the security semantics and that candidate lands or is replaced. citeturn14view0turn14view1turn14view2

## What This Changes

Add native exec-approval deny patterns that force a prompt or block selected command and argument combinations while otherwise permitting broad execution.

## Best Possible Solution

Adopt one additive deny-over-allow rule layer, shared across gateway and node execution, that reuses established command/argv analysis, forces human-only approval before permissive policy or durable trust, round-trips through both configuration stores and protocol schemas, and documents any intentional host asymmetry.

## Maintainer Decision

Rationale: Current main has no such policy, external plugins do not own built-in host enforcement, and the open candidate necessarily chooses security precedence, durable-trust, fallback, and cross-host semantics that automation cannot authorize.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve additive approval override (recommended):** Treat every deny-pattern hit as human-only approval before broad allow or durable trust, require documented gateway/node parity for supported configuration sources, and land the linked candidate after proof.
- **Allow fail-closed host asymmetry:** Accept the linked design with documented cases where node-local-only rules hard-deny because the gateway cannot prepare a prompt.
- **Reject native deny patterns:** Keep core on allowlist and strict modes and direct advanced deny policies to external policy plugins, acknowledging they do not replace all built-in host enforcement paths.

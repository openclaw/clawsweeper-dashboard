## Summary

Keep open: current main has fixed the newly marked post-send recovery path, but source inspection still leaves a real upgrade/product question for legacy Telegram queue rows imported without `recoveryState`; those rows can still flow through the recovery replay path instead of the unknown-send guard.

## What This Changes

The issue asks OpenClaw to prevent Telegram delivery-queue recovery from replaying ambiguous `sendMessage` replies and duplicating `delivery-mirror` transcript entries after network failures.

## Best Possible Solution

Land or revise the existing ambiguous-delivery recovery policy so markerless legacy Telegram rows are classified through an explicit migration/quarantine path while preserving current no-blind-replay behavior for marked post-send rows.

## Reproduction Assessment

Yes, at source level: a markerless legacy outbound row imported from `delivery-queue/*.json` can bypass the `recoveryState` guard and reach the replay path. I did not establish a live Telegram failure replay on current main.

## Solution Assessment

Unclear as a direct repair: refusing all ambiguous `sendMessage` replays is directionally right, but the best fix needs a maintainer-approved upgrade policy for markerless legacy rows so genuinely unsent pre-marker entries are not silently lost.

## Summary

Keep open: current main protects newly marked ambiguous outbound sends, but the reported v2026.3-era legacy Telegram queue shape can still migrate without recovery-state metadata and remain eligible for recovery replay.

## What This Changes

Prevent Telegram delivery queue recovery from replaying ambiguous sendMessage failures and duplicating delivery-mirror transcript entries.

## Best Possible Solution

Add a maintainer-approved upgrade/recovery policy for legacy ambiguous Telegram queue rows, then regression-test both the new-state recovery path and migrated legacy queue shape.

## Reproduction Assessment

Yes from source inspection: a legacy pending Telegram queue row with a network sendMessage error but no recoveryState migrates with null recovery_state, inflates without recoveryState, bypasses the guarded recovery branch, and remains eligible for replay.

## Solution Assessment

No complete fix is present yet; current main is the right direction for newly-created entries, but the reported legacy upgrade state still needs a recovery or migration policy before this issue can close.

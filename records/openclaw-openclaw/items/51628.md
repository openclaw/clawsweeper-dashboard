## Summary

Keep open: current main protects newly marked post-send recovery rows and has idempotent channel-final transcript mirror appends, but legacy migrated Telegram queue rows without `recoveryState` can still load unmarked and bypass the replay guard.

## What This Changes

The issue asks OpenClaw to prevent Telegram recovery from replaying uncertain old `sendMessage` replies and duplicating `delivery-mirror` transcript entries.

## Best Possible Solution

Add a maintainer-approved migration/recovery policy that classifies legacy unmarked Telegram queue rows before replay, then prove no duplicate Telegram send or delivery-mirror append on restart.

Rationale: The code can implement several narrow policies, but the correct default chooses between possible dropped unsent messages and possible duplicate delivered messages for existing users upgrading from shipped queue files.

Owner confidence: high

Options:

- **Quarantine ambiguous legacy Telegram rows (recommended):** Treat legacy unmarked Telegram rows with ambiguous network send errors as unsafe to replay, move or keep them out of blind recovery, and document/operator-surface the skipped delivery.
- **Infer `unknown_after_send` during migration:** Migrate matching legacy Telegram rows into the existing marked unknown-send path so future reconciliation or no-blind-replay behavior handles them consistently.
- **Keep current replay behavior:** Accept duplicate-send risk for legacy unmarked rows to avoid dropping any possibly unsent queued reply.

## Reproduction Assessment

Yes, at source level: a legacy Telegram queued delivery with a network `lastError` and no `recoveryState` can migrate with null `recovery_state`, inflate without `recoveryState`, and bypass the guard that protects marked post-send rows. I did not run a live Telegram restart reproduction in this read-only review.

## Solution Assessment

No for closing: current main fixes newly marked post-send entries and idempotent channel-final mirrors, but the legacy unmarked queue-row upgrade path still needs a maintainer policy. The narrow maintainable fix should live in migration/recovery policy plus restart-replay regression proof, not as an unconditional replay or disabled mirror workaround.

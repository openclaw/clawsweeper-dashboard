## Label Justifications

- `P2`: This is a concrete Telegram duplicate-delivery and transcript-state bug with limited channel scope, not a core runtime outage.
- `impact:message-loss`: The reported recovery path can duplicate outbound Telegram replies after ambiguous `sendMessage` failures.
- `impact:session-state`: The replay can append duplicate `delivery-mirror` assistant entries into the source session transcript.

## Summary

Keep open: current main protects newly marked post-send recovery rows and now gives Telegram delivery mirrors stable idempotency keys, but legacy queue rows can still migrate with null `recovery_state`, inflate without `recoveryState`, and bypass the replay guard. The remaining work is the upgrade policy for ambiguous legacy Telegram queue entries.

## What This Changes

The issue requests safer Telegram outbound recovery so ambiguous old `sendMessage` queue entries are not blindly replayed and delivery-mirror transcript appends remain deduped.

## Best Possible Solution

Classify, quarantine, or migrate legacy Telegram delivery-queue rows with missing `recoveryState`, then add restart-replay coverage proving no blind Telegram send replay and no duplicate delivery-mirror append.

## Reproduction Assessment

Yes at source level: a legacy Telegram queued delivery with network `lastError` and no `recoveryState` can migrate with null `recovery_state`, inflate without `recoveryState`, and bypass the marked-row replay guard. I did not run a live Telegram restart reproduction in this read-only review.

## Solution Assessment

No for closing: current main fixes newly marked post-send rows and mirror idempotency, but the legacy unmarked queue-row upgrade path still needs a maintainer policy decision. The best fix should live in migration/recovery policy plus regression proof, not as unconditional replay or disabling transcript mirrors.

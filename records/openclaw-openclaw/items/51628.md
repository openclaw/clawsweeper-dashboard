## Summary

Keep open: current main protects newly marked post-send recovery rows, but legacy Telegram delivery-queue rows imported without `recoveryState` still bypass that guard and can reach recovery replay.

## What This Changes

The issue reports that Telegram recovery can replay old queued `sendMessage` replies and append duplicate `delivery-mirror` transcript entries.

## Best Possible Solution

Keep this issue open until legacy Telegram queue rows are classified, quarantined, or migrated into a safe recovery state with regression coverage for no blind replay and mirror dedupe.

## Reproduction Assessment

Yes at source level: a legacy Telegram queued delivery with network `lastError` and no `recoveryState` can migrate with null `recovery_state`, inflate without `recoveryState`, bypass the guard, and reach recovery replay.

## Solution Assessment

No for closing: current main fixes newly marked post-send recovery entries, but the legacy unmarked queue-row migration path reported here remains open.

## Label Justifications

- `P2`: The issue is a concrete Telegram duplicate-delivery and transcript-state bug with limited channel/legacy recovery scope rather than a core runtime outage.
- `impact:message-loss`: The reported recovery path can duplicate outbound Telegram replies after an ambiguous `sendMessage` failure.
- `impact:session-state`: The same replay can append duplicate `delivery-mirror` assistant entries into the source session transcript.

## Summary

Keep open: current main prevents blind replay for newly marked ambiguous sends, but legacy or migrated Telegram queue rows with missing `recoveryState` can still bypass that guard and replay, so the reported duplicate-delivery and transcript-mirror problem is not fully resolved.

## What This Changes

Prevent Telegram outbound recovery from replaying ambiguous old `sendMessage` queue entries and duplicating `delivery-mirror` transcript entries.

## Best Possible Solution

Adopt a maintainer-approved migration/recovery policy for legacy ambiguous Telegram rows, then add restart-replay coverage proving no blind platform resend and no duplicate mirror append.

## Maintainer Decision

Question: How should OpenClaw treat legacy or migrated Telegram outbound queue rows whose previous `sendMessage` outcome is ambiguous but no `recoveryState` was recorded?

Rationale: The code fix depends on an upgrade-policy choice: preserving delivery by replaying old rows risks duplicate visible Telegram messages, while quarantining or failing them may drop an unsent legacy message.

Likely owner: steipete

Owner reason: steipete authored the recovery split and merged the recent recovery-policy PRs, making this the strongest available owner for the upgrade semantics decision.

Owner confidence: high

Options:

- **Quarantine Ambiguous Legacy Rows (recommended):** Mark or move legacy Telegram rows with ambiguous network/timeout send evidence out of blind replay, preserving enough operator/doctor detail to inspect them later.
- **Require Exact Reconciliation Before Replay:** Keep rows pending until a Telegram-capable reconciliation contract can prove whether the platform send landed, accepting that old entries may remain unresolved.
- **Accept Legacy Replay Risk:** Leave legacy null-marker rows replayable and document the duplicate-delivery risk as an accepted upgrade tradeoff.

## Reproduction Assessment

Yes, at source level: a legacy Telegram queue row with network `lastError` and no `recoveryState` can migrate with null `recovery_state`, inflate without `recoveryState`, skip the ambiguous-send guard, and reach the replay call.

## Solution Assessment

No for closing: current main fixes newly marked post-send rows and improves mirror idempotency when keys exist, but the legacy unmarked queue-row upgrade path still needs a maintainer-approved recovery policy.

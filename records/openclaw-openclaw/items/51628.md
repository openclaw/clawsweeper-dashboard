## Summary

Keep open: current main fixes new post-send recovery rows and stable Telegram mirror idempotency, but it still does not encode a clear upgrade policy for legacy Telegram queue rows that lack `recoveryState`; those rows can bypass the replay guard and reach normal recovery replay.

## What This Changes

The issue asks OpenClaw to avoid replaying ambiguous Telegram `sendMessage` queue entries and to keep delivery-mirror transcript appends idempotent across recovery.

## Best Possible Solution

Apply one documented no-blind-replay policy to legacy and current Telegram queue rows, preferably by mapping ambiguous legacy rows into the same unknown-send recovery path and adding focused migration/recovery coverage.

Owner confidence: medium

Options:

- **Map legacy rows to unknown-send policy (recommended):** Backfill or classify ambiguous legacy Telegram rows so they cannot be blindly replayed and can follow the same reconciliation/quarantine behavior as newly marked rows.
- **Quarantine ambiguous legacy rows:** Move old Telegram rows with network/timeout send errors and no recovery state to failed diagnostics to minimize duplicate delivery risk.
- **Keep legacy rows replayable:** Accept duplicate-send risk for old rows to maximize recovery of messages that may not have reached Telegram.

Yes for the remaining source-level path: legacy rows can migrate with null `recovery_state`, inflate without `recoveryState`, and bypass the current replay guard. I did not run a live Telegram replay in this read-only review.

## Solution Assessment

No, current main is not yet the complete solution for this issue: new rows and mirror idempotency are improved, but legacy ambiguous rows still need an explicit upgrade policy and regression coverage.

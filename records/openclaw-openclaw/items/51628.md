## Label Justifications

- `P2`: The issue affects Telegram delivery reliability and transcript correctness, but the remaining confirmed gap is a bounded upgrade edge case for legacy queue rows.
- `impact:message-loss`: Ambiguous replay policy can either duplicate an already-delivered Telegram message or strand a message that did not land.
- `impact:session-state`: Duplicate delivery-mirror appends can corrupt session transcript state and later model context.

## Summary

Keep open: current main protects new ambiguous queued sends and adds Telegram transcript mirror idempotency, but the legacy delivery-queue migration still imports old pending Telegram queue JSON without a replay-safe recovery state, leaving the original upgrade/restart replay edge case unresolved.

## What This Changes

Request to prevent Telegram delivery queue recovery from replaying ambiguous old `sendMessage` replies and duplicating `delivery-mirror` transcript entries.

## Best Possible Solution

Choose an upgrade policy for legacy ambiguous Telegram queue rows, then migrate or quarantine them so recovery never blindly replays non-idempotent sends while preserving current idempotent mirror behavior.

Options:

- **Quarantine ambiguous legacy rows (recommended):** Move legacy Telegram rows without `recoveryState` to failed or a reviewable quarantine during migration so startup never blindly resends them.
- **Keep ambiguous rows pending:** Mark legacy rows as `unknown_after_send` and leave them pending until a Telegram reconciliation path can prove whether the send landed.
- **Allow legacy blind replay:** Preserve current replay behavior for old rows and accept the duplicate-message risk for pre-migration queues.

## Solution Assessment

Not solved yet. Current main has the right new-row recovery markers and mirror idempotency, but the legacy migration path still needs an explicit policy and test coverage.

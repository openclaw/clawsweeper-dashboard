## Summary

Keep open: current main partially protects marked post-send recovery rows and improves delivery-mirror idempotency, but legacy Telegram delivery-queue JSON rows without `recoveryState` can still migrate and load as unmarked rows, bypassing the replay guard. This remains a real recovery-policy bug, not conservative cleanup.

## What This Changes

Requests preventing Telegram delivery-queue recovery from replaying ambiguous `sendMessage` replies and duplicating `delivery-mirror` transcript entries.

## Best Possible Solution

Add a migration or recovery policy for legacy unmarked Telegram queue rows, then prove restart recovery cannot blindly replay the send or append a duplicate mirror entry.

## Maintainer Decision

Required: true

Kind: product_direction

Question: How should OpenClaw handle legacy Telegram outbound delivery-queue rows that have ambiguous network-send evidence but no `recoveryState` marker?

Rationale: Automation cannot safely choose between preserving possibly-unsent legacy replies and avoiding user-visible duplicate Telegram sends without maintainer intent for this upgrade edge case.

Likely owner: zhangguiping-xydt

Owner reason: They authored the most recent merged recovery hardening in the same queue lifecycle and are best positioned to judge the remaining upgrade-policy fit.

Owner confidence: medium

Options:

- **Quarantine ambiguous legacy Telegram rows (recommended):** Classify matching legacy rows as unsafe to replay, move or fail them with an operator-visible diagnostic, and add restart-replay regression coverage.
- **Keep them pending until reconciliation exists:** Avoid duplicate sends by refusing replay while preserving the row for a future Telegram reconciliation capability or manual operator action.
- **Continue replaying unmarked rows:** Maximize delivery of possibly unsent legacy messages but accept that some users may receive duplicate Telegram replies and mirrored transcript entries.

## Reproduction Assessment

Yes at source level: a legacy Telegram queued delivery without `recoveryState` migrates with null `recovery_state`, loads without `recoveryState`, and bypasses the guard that protects marked post-send rows. I did not run a live Telegram restart reproduction in this read-only review.

## Solution Assessment

No for closing: current main is a partial fix for marked rows and mirror dedupe, but it does not settle legacy unmarked queue imports. The best fix should live in migration or recovery policy with restart-replay coverage, not in a broad transcript-mirror disable workaround.

- `impact:session-state`: The reported failure appends duplicate `delivery-mirror` assistant entries into the source session transcript.
- `impact:message-loss`: The affected delivery path can duplicate or wrongly replay channel messages during recovery.

## Summary

Keep open: current main prevents blind replay only when a queue row already carries `send_attempt_started` or `unknown_after_send`, but legacy Telegram `delivery-queue/*.json` rows from the reported shipped path can migrate with no `recoveryState` and still fall through to normal recovery replay.

## What This Changes

The issue asks OpenClaw to stop Telegram recovery from replaying ambiguous `sendMessage` queue entries and duplicating delivery-mirror transcript entries.

## Best Possible Solution

Adopt a maintainer-approved legacy queue migration/recovery policy for Telegram network-failure rows without `recoveryState`, then cover migration plus restart/reconnect recovery so ambiguous sends cannot duplicate user-visible replies or mirror entries.

## Reproduction Assessment

Yes, source inspection gives a high-confidence path: a legacy Telegram queue row with `lastError` but no `recoveryState` migrates with null `recovery_state`, loads without `recoveryState`, and bypasses the current blind-replay guard. I did not run a live Telegram replay because this review is read-only.

## Solution Assessment

No, current main is only a partial fix: it protects newly marked ambiguous rows but not the shipped legacy row shape described in the report. The safer solution needs an explicit upgrade policy for ambiguous legacy Telegram queue entries plus regression coverage.

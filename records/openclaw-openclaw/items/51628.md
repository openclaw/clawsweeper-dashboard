## Label Justifications

- `P2`: The issue is a normal-priority Telegram delivery reliability bug with real duplicate-message and transcript-state impact, but it needs product/upgrade policy rather than emergency handling.
- `impact:message-loss`: The reported failure can duplicate Telegram outbound replies through recovery replay of an ambiguous `sendMessage` result.
- `impact:session-state`: The same replay path can append duplicate `delivery-mirror` assistant entries and make the session transcript diverge from actual channel history.

## Summary

Keep open: current main protects newly marked post-send recovery rows and improves transcript-mirror dedupe, but legacy delivery-queue rows imported without `recoveryState` can still be treated as first-replay eligible, so the central upgrade/recovery bug is not fully closed.

## What This Changes

The issue asks for Telegram outbound recovery to avoid blindly replaying ambiguous `sendMessage` failures and to keep `delivery-mirror` transcript appends idempotent across recovery.

## Best Possible Solution

Keep this issue open until maintainers choose and implement the upgrade policy for legacy or ambiguous Telegram delivery entries, ideally by quarantining or safely reconciling old rows before startup recovery can replay them.

## Reproduction Assessment

Yes, source-level: a legacy queue row imported without `recoveryState` remains first-replay eligible, while the current no-blind-replay guard only applies to marked post-send states. I did not run a live Telegram replay in this read-only review.

## Solution Assessment

No, current main is only a partial fix. The maintainable solution needs an explicit migration/quarantine/reconciliation policy for legacy or otherwise unmarked ambiguous sends, plus regression coverage for recovery and transcript mirror behavior.

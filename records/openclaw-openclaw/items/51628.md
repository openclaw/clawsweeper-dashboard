## Label Justifications

- `P2`: This is a concrete Telegram duplicate-delivery and transcript-state bug with limited blast radius, not a core runtime outage.
- `impact:message-loss`: The reported recovery path can replay an old Telegram reply after an ambiguous sendMessage failure.
- `impact:session-state`: The same replay can append duplicate delivery-mirror assistant entries into the source session transcript.

## Summary

Keep open: current main prevents blind replay for newly marked post-send recovery rows, but legacy Telegram queue rows imported without recoveryState can still inflate without the guard and reach the recovery replay path.

## What This Changes

The issue requests preventing Telegram recovery from replaying ambiguous sendMessage deliveries and duplicating delivery-mirror transcript entries.

## Best Possible Solution

Keep this open until legacy Telegram delivery-queue rows with ambiguous sendMessage failures are classified or migrated into a safe recovery state, with regression coverage for no blind replay and no duplicate delivery-mirror append.

## Reproduction Assessment

Yes at source level: a legacy Telegram queued delivery with network lastError and no recoveryState can migrate with null recovery_state, inflate without recoveryState, bypass the guard, and reach recovery replay. I did not run a live Telegram restart scenario in this read-only review.

## Solution Assessment

No for closing: current main is the right direction for newly marked post-send entries, but it does not yet settle the legacy unmarked-row upgrade policy. The best fix should handle that migration/quarantine decision explicitly rather than relying on the current state-gated guard.

## Summary

Keep open: current main protects newly marked post-send recovery rows and now uses stable Telegram mirror idempotency, but legacy delivery-queue JSON rows can still migrate with null `recovery_state`, inflate without `recoveryState`, and bypass the replay guard. That remaining upgrade-policy gap keeps the issue necessary.

## What This Changes

The issue reports Telegram delivery-queue recovery replaying ambiguous `sendMessage` replies, causing duplicate visible Telegram delivery and duplicate `delivery-mirror` transcript entries.

## Best Possible Solution

Classify, quarantine, or migrate legacy Telegram delivery-queue rows with missing `recoveryState`, then add restart-replay coverage proving no blind Telegram send replay and no duplicate delivery-mirror append.

## Reproduction Assessment

Yes, at source level: a legacy Telegram queued delivery with network `lastError` and no `recoveryState` can migrate with null `recovery_state`, inflate without `recoveryState`, and bypass the guard that protects marked post-send rows. I did not run a live Telegram restart reproduction in this read-only review.

## Solution Assessment

No for closing: current main fixes newly marked post-send recovery entries and mirror idempotency, but the legacy unmarked queue-row upgrade path still needs a maintainer policy decision. The best fix should live in migration/recovery policy plus regression proof, not as an unconditional replay or a disabled mirror workaround.

## Label Justifications

- `P2`: This is a concrete Telegram duplicate-delivery and transcript-state bug with limited blast radius, not a core runtime outage.
- `impact:message-loss`: The reported recovery path can replay old Telegram replies after ambiguous sendMessage failures, duplicating channel delivery.
- `impact:session-state`: The same replay can append duplicate delivery-mirror assistant entries into the source session transcript.

## Summary

Keep open: current main hardens newly marked post-send recovery rows, but legacy Telegram delivery-queue rows imported without recoveryState can still bypass that guard and reach recovery replay.

## What This Changes

The issue asks OpenClaw to stop Telegram delivery-queue recovery from replaying uncertain old sendMessage replies and duplicating delivery-mirror transcript entries.

## Best Possible Solution

Add a maintainer-approved migration and recovery policy for ambiguous legacy Telegram sendMessage rows, with no blind replay unless a real Telegram-safe reconciliation signal proves the send did not land.

## Reproduction Assessment

Yes at source level: a legacy Telegram queued delivery with network lastError and no recoveryState can migrate with null recovery_state, inflate without recoveryState, bypass the recovery guard, and reach replay.

## Solution Assessment

No for closing: current main fixes newly marked post-send recovery entries, but the legacy unmarked queue-row migration path reported here remains open and needs a policy decision.

## Summary

Keep open: current main protects newly marked post-send queue entries, but legacy/imported Telegram queue rows without `recoveryState` can still bypass that guard; the merged related PRs are partial fixes and the open adjacent PR does not settle the legacy-upgrade policy.

## What This Changes

The issue reports unsafe Telegram delivery-queue recovery after ambiguous `sendMessage` failures, causing duplicate visible replies and duplicate `delivery-mirror` transcript entries.

## Best Possible Solution

Keep this open until legacy Telegram queue rows are classified, quarantined, or migrated into a no-blind-replay recovery state with regression coverage.

## Reproduction Assessment

Yes at source level: a legacy Telegram queued delivery with network `lastError` and no `recoveryState` can migrate/backfill with null `recovery_state`, inflate without `recoveryState`, skip the marked-send recovery guard, and reach replay.

## Solution Assessment

No for closing: current main is a strong partial fix for newly marked post-send entries, but the legacy unmarked queue-row policy remains unresolved and has an upgrade tradeoff.

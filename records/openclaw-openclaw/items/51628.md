## Summary

Keep open: current main and v2026.6.11 protect new queued sends that carry recovery state, but legacy Telegram queue JSON without that state can still import as pending and reach replay recovery. The remaining question is a maintainer policy choice for ambiguous legacy rows, not a cleanup close.

## What This Changes

The issue reports duplicate Telegram reply recovery and duplicate delivery-mirror transcript entries after ambiguous sendMessage failures.

## Best Possible Solution

Maintain current protections for new sends and add doctor or migration handling for legacy ambiguous Telegram queue rows once maintainers choose the recovery policy.

Rationale: Source inspection shows current main can distinguish new ambiguous rows, but older JSON entries predate that state; choosing quarantine, pending deferral, or replay requires a human tradeoff between duplicate delivery and dropping unsent messages.

Options:

- **Quarantine Ambiguous Legacy Telegram Rows (recommended):** Doctor or migration would move old Telegram rows with ambiguous network/sendMessage errors out of pending recovery and preserve diagnostics, avoiding duplicate delivery at the cost of possible unsent replies.
- **Keep Recoverable Pending Semantics:** Legacy rows would remain pending for future reconciliation or operator tooling, but maintainers must accept that some old rows may stay stranded until a surfaced repair path exists.
- **Replay Legacy Rows:** OpenClaw would continue recovering old rows as send intents, preserving delivery attempts but accepting the duplicate-send risk this issue reports.

## Reproduction Assessment

Yes from source inspection for the legacy-upgrade edge: a pending legacy Telegram queue JSON with network `lastError` and no recovery state imports as pending, and recovery will replay rows that lack recovery state. I did not run a live Telegram reproduction in this read-only review.

## Solution Assessment

No final code path is selected yet; the best fix depends on maintainer policy for ambiguous legacy Telegram rows. A narrow migration/doctor policy plus regression coverage is safer than changing steady-state recovery to guess from old queue contents at runtime.

## Label Justifications

- `P2`: The issue is a concrete Telegram duplicate-delivery and transcript-state bug with limited channel-specific blast radius, not a core runtime outage.
- `impact:message-loss`: The reported recovery path can replay old Telegram replies after ambiguous `sendMessage` failures.
- `impact:session-state`: The replay can append duplicate `delivery-mirror` assistant entries into the source session transcript.

## Summary

Keep open: current main hardens new marked post-send recovery entries, but the reported legacy Telegram queue shape can still migrate without `recoveryState`, inflate as unmarked, and bypass the no-blind-replay guard into recovery replay.

## What This Changes

Issue requests preventing Telegram delivery queue recovery from replaying old `sendMessage` replies and duplicating `delivery-mirror` transcript entries.

## Best Possible Solution

Keep this issue open until legacy Telegram queue rows are classified, quarantined, or migrated into a non-replayable recovery state with regression coverage for recovery and transcript mirror dedupe.

## Reproduction Assessment

Yes at source level: a legacy Telegram queued delivery with network `lastError` and no `recoveryState` can migrate with null recovery state, inflate without `recoveryState`, bypass the guard, and reach recovery replay.

## Solution Assessment

No for closing: current main fixes new marked post-send recovery entries, but not the legacy unmarked queue-row migration path reported here.

## Label Justifications

- `P2`: This is a concrete Telegram duplicate-delivery and transcript-state bug with limited blast radius, not a core runtime outage.
- `impact:message-loss`: The reported recovery path can replay old Telegram replies after ambiguous `sendMessage` failures.
- `impact:session-state`: The same replay can append duplicate `delivery-mirror` assistant entries into the source session transcript.

## Summary

Keep open: current main protects newly marked post-send recovery rows, but legacy imported Telegram queue rows with a network `lastError` and no `recoveryState` still inflate unmarked and can reach recovery replay. The related duplicate-message issues and PRs only partially overlap this legacy-row policy gap.

## What This Changes

The issue requests safe Telegram delivery-queue recovery so ambiguous old `sendMessage` entries are not blindly replayed and delivery-mirror transcript appends stay deduped.

## Best Possible Solution

Keep this issue open until legacy Telegram queue rows are classified, quarantined, or migrated into a safe recovery state with regression coverage for no blind replay and mirror dedupe.

## Reproduction Assessment

Yes at source level: a legacy queued delivery with network `lastError` and no `recoveryState` can migrate with null `recovery_state`, inflate without `recoveryState`, bypass the guard, and reach recovery replay. I did not run a live Telegram reproduction in this read-only review.

## Solution Assessment

No for closing: current main fixes newly marked post-send recovery entries, but the legacy unmarked queue-row migration path reported here remains open. The maintainable fix needs a maintainer decision on how to classify old ambiguous rows without losing genuinely unsent crash-before-send deliveries.

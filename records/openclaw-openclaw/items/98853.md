## Summary

Keep open: the resource-leak target is source-reproducible and the paired issue is still open, but this PR is not merge-ready because the eviction runs after watcher creation, can evict on same-key reloads, and the screenshot does not prove the changed eviction path.

## What This Changes

The PR adds a 32-entry cap to the usage-bar template file cache and closes the oldest cached watcher before storing a new entry.

## Best Possible Solution

Land a corrected cache-bound implementation that evicts only before adding a new key, frees a watcher before opening the replacement, and proves eviction/closure with focused tests plus real behavior proof.

## Reproduction Assessment

Yes. Source inspection on current main shows distinct valid template paths are stored in a module-level cache and can open fs.watch watchers with no size bound; I did not run a live 33-template repro in this read-only review.

## Solution Assessment

No. The cache boundary is the right layer, but this PR should evict before watcher allocation and only for new keys, with focused tests and real behavior proof.

## Review Findings

Full review comments:

- **[P2] Evict before opening the replacement watcher:** `src/auto-reply/usage-bar/template.ts:149-156`
  - body: The new eviction block runs after `watch(path, ...)` has already tried to allocate the replacement watcher. With a full cache and watcher/file-descriptor pressure, allocation can fail before this frees an old watcher, leaving the new template cached without live refresh even though evicting first could have preserved it.
  - confidence: 0.88
- **[P2] Gate eviction to new cache entries:** `src/auto-reply/usage-bar/template.ts:149`
  - body: `cacheTemplateFile` is also used for paths already cached without a watcher after an earlier miss or invalid file. In that overwrite case `fileCache.set(path, entry)` does not grow the Map, but this condition can still delete an unrelated oldest entry and close its live watcher.
  - confidence: 0.84

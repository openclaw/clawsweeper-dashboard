## Summary

Keep this PR open, but do not merge it as-is: it targets a real source-reproducible watcher/cache leak, yet the proposed eviction runs after the replacement watcher is opened and can evict an unrelated entry when retrying an already-cached path.

## What This Changes

The PR adds a 32-entry cap to the usage-bar template file cache and closes the oldest cached watcher when the cache is full.

## Best Possible Solution

Evict only when adding a new cache key, do it before opening the replacement watcher, add focused template-cache coverage, and require redacted real-run proof for more than 32 template paths.

## Reproduction Assessment

Yes by source inspection: current main stores a cache entry per distinct configured template path and opens watchers for valid templates without a size bound. I did not run a live more-than-32-path repro in this read-only review.

## Solution Assessment

No. The cache boundary is the right place to fix this, but the patch should evict before watch creation, skip eviction when overwriting an existing key, and prove the behavior with a focused test and real-run evidence.

- **[P2] Evict before opening the replacement watcher:** `src/auto-reply/usage-bar/template.ts:149-156`
  - body: This block runs after `watch(path, ...)` has already tried to allocate the replacement watcher.   - confidence: 0.86

  - body: `cacheTemplateFile` is also used to retry paths that are already cached without a watcher. In that case `fileCache.set(path, entry)` overwrites an existing key and does not grow the cache, but this condition can still delete the oldest unrelated entry and close its live watcher.
  - confidence: 0.82

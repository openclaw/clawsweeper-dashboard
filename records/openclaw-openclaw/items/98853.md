## Summary

Keep open. The resource-leak concern is valid, but the patch allocates the next watcher before evicting an old one, so it can still fail in the full-cache/resource-pressure case, and the PR body only provides unit-test evidence rather than real behavior proof.

## What This Changes

The branch adds a 32-entry cap to the usage-bar template file cache and closes the watcher on an evicted cache entry.

## Best Possible Solution

Land a small version that evicts and closes the oldest cache entry before opening the replacement watcher, with focused regression coverage for the full-cache path.

## Reproduction Assessment

Yes by source inspection, though not by a live run here: current main keeps a module-level cache entry and watcher per distinct valid template path with no size bound. A focused reproduction would load more than 32 valid template paths and assert watcher close/eviction behavior.

## Solution Assessment

No. The cache is the right fix boundary, but the implementation should evict before calling fs.watch and add regression coverage for that ordering.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.82

Full review comments:

- **[P2] Move eviction before opening the next watcher:** `src/auto-reply/usage-bar/template.ts:149`
  - body: This eviction block runs after `watch(path, ...)` has already tried to allocate the new watcher. When the cache is full and the process is near the OS watcher/file-descriptor limit, the 33rd watcher can fail before this PR closes an old watcher, leaving the newly loaded valid template cached without live refresh even though freeing one existing watcher first would have worked. Evict and close the oldest entry before creating the new watcher, and cover that ordering.
  - confidence: 0.82

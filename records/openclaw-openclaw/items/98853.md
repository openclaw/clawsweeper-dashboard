## Summary

Keep open: the PR is a useful candidate for the usage-template watcher leak, but it is not merge-ready because eviction happens after watcher allocation, fires on same-key reloads, and the screenshot proof does not demonstrate the real overflow/eviction path.

## What This Changes

The branch adds a 32-entry cap to `src/auto-reply/usage-bar/template.ts` and deletes the oldest `fileCache` entry before storing the newly read template.

## Best Possible Solution

Land a corrected bounded-cache implementation that evicts only before inserting a new key, frees an old watcher before opening the replacement, and proves eviction/closure with focused tests plus real behavior proof.

## Reproduction Assessment

Yes. Source inspection on current main shows each distinct valid template path can allocate an `fs.watch` watcher and is stored in `fileCache` with no production size bound; I did not run a live many-template exhaustion repro in this read-only review.

## Solution Assessment

No. Bounding the cache in `src/auto-reply/usage-bar/template.ts` is the right layer, but this PR should evict before watcher allocation and only for newly inserted keys, with focused regression coverage.

## Summary

Keep open: current main and v2026.6.11 still do not provide a trusted parent-scoped mid-run send path for native sub-agents. Related work covers completion announce routing or direct message-tool opt-ins, but this issue remains the focused security-sensitive API/design decision for child-to-direct-parent communication.

## What This Changes

Request a native parent-only mechanism, such as `sessions_send_parent` or a trusted `sessionKey:"parent"`, so sub-agents can send mid-run updates or questions only to their direct parent session.

## Best Possible Solution

Define one narrow parent-only send contract derived from canonical active sub-agent metadata, then update tool policy, resolution, delivery, docs, and security regression tests together.

Rationale: The source gap is clear, but the permanent API changes child-to-parent session authorization and model-facing tool semantics in a security-sensitive boundary.

Likely owner: steipete

Owner confidence: high

Options:

- **Add dedicated parent-only contract (recommended):** Implement a dedicated tool or trusted parent selector that derives the direct parent from active spawn metadata and rejects missing, stale, sibling, ancestor, cross-agent, and auto-forwarded targets.
- **Reserve `sessionKey:"parent"`:** Keep one `sessions_send` surface but make `parent` a trusted resolver token rather than a literal user-supplied key.
- **Decline native mid-run sends:** Keep child-originated mid-run sends unsupported and document completion handoff, `sessions_yield`, or explicit trusted operator opt-ins as the supported paths.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 still deny `sessions_send` to sub-agents by default and do not expose a parent-only selector or tool.

## Solution Assessment

Yes in direction, but not as a broad opt-in to ordinary `sessions_send`. The maintainable solution is a dedicated parent-only operation or trusted parent selector backed by active run metadata and security tests.

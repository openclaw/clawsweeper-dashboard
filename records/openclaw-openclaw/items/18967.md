## Summary

Keep open: current main and v2026.6.11 still lack a trusted parent-scoped mid-run send path for native sub-agents, and the remaining work is a security-sensitive model-facing API decision.

## What This Changes

Request a parent-scoped sub-agent send mechanism for mid-run progress updates and clarifying questions to the direct parent session only.

## Best Possible Solution

Define one narrow parent-only send contract derived from canonical active sub-agent metadata, then update policy, resolver, delivery, docs, and security regression tests together.

Rationale: The source gap is clear, but the final shape changes session authorization and model-facing tool semantics across parent/child agent boundaries.

Options:

- **Add a dedicated parent-only contract (recommended):** Implement a dedicated tool or trusted parent selector that derives the direct parent from active spawn metadata and rejects missing, stale, sibling, ancestor, cross-agent, and forwarded targets.
- **Reserve sessionKey:"parent":** Keep one sessions_send tool but make parent a trusted selector resolved from sub-agent metadata rather than a literal user-supplied session key.
- **Decline native mid-run sends:** Keep child-originated mid-run sends unsupported and document completion handoff, sessions_yield, or explicit trusted operator opt-ins as the supported paths.

Yes, at source level. Current main and v2026.6.11 still deny sessions_send to sub-agents by default and do not expose a parent-only selector or dedicated tool.

## Solution Assessment

Yes in direction, but not as a broad opt-in to ordinary sessions_send. The maintainable path is a dedicated parent-only operation or trusted parent selector backed by active run metadata and security tests.

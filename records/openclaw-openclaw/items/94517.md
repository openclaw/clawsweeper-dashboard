## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P2] Preserve labels across pairing rebuilds:** `src/infra/device-pairing.ts:115`
  - body: Adding `operatorLabel` to the record and patch path is not enough because `buildApprovedPairedDevice` still rebuilds an existing paired-device record without copying `params.existing?.operatorLabel`. Reapproving or bootstrap-repairing the same device will silently drop the rename, so carry the field through and cover that path.
  - confidence: 0.93
- **[P2] Mirror renamed labels in the Control UI:** `src/cli/devices-cli.runtime.ts:942`
  - body: This changes only the CLI table to prefer `operatorLabel`; the same `device.pair.list` response also feeds the Control UI, whose paired-device type and renderer still use `displayName` or `deviceId`. After a successful rename, the CLI and Control UI can show different names for the same paired device.
  - confidence: 0.91
- **[P2] Sanitize labels before gateway logging:** `src/gateway/server-methods/devices.ts:562`
  - body: `displayName` is only validated as a non-empty string, then `label=${trimmed}` is written directly to Gateway logs. A label containing newlines or ANSI/control sequences can forge or obscure log output; sanitize the label with the existing log-safe sanitizer or omit the raw label from the log line.
  - confidence: 0.88
- **[P3] Document the devices rename command:** `src/cli/devices-cli.ts:98-101`
  - body: This adds a new public `openclaw devices rename` command, but `docs/cli/devices.md` still documents the older devices command set. Add the command syntax, scope behavior, and label precedence so the shipped CLI surface is discoverable.
  - confidence: 0.84

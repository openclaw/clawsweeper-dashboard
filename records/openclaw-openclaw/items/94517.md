Full review comments:

- **[P2] Preserve labels when rebuilding approved devices:** `src/infra/device-pairing.ts:1094-1095`
  - body: `operatorLabel` is now persisted via `updatePairedDeviceMetadata`, but `approveDevicePairing` and `approveBootstrapDevicePairing` rebuild the `PairedDevice` through `buildApprovedPairedDevice` without copying `existing.operatorLabel`. Any later reapproval or bootstrap approval for the same device will silently drop the friendly name the operator just set.
  - confidence: 0.91
- **[P2] Mirror operator labels in the Control UI:** `src/cli/devices-cli.runtime.ts:942`
  - body: The CLI now prefers `operatorLabel`, but the Control UI's paired-device type/render path still uses only `displayName || deviceId`. A renamed device will therefore show the friendly name in `openclaw devices list` but keep the old hash-like label on the Devices page, leaving the linked web UI request only partially fixed.
  - confidence: 0.89
- **[P2] Sanitize the rename label before gateway logging:** `src/gateway/server-methods/devices.ts:562`
  - body: `displayName` is operator-controlled input, and this log line interpolates the trimmed value directly. A label with control characters or sensitive-looking text can forge or pollute Gateway logs; route the label through the existing Gateway log formatter/sanitizer before logging it.
  - confidence: 0.87
- **[P3] Document the devices rename command:** `src/cli/devices-cli.ts:98-101`
  - body: This adds a public CLI command and Gateway method, but the Gateway protocol/admin HTTP docs still list only list/approve/reject/remove for device pairing. Please document `openclaw devices rename` and the `device.pair.rename` method so operators and integrators can discover the new surface.
  - confidence: 0.82

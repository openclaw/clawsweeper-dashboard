## What This Changes

The PR adds `browser.profiles` as a hot browser-plugin reload prefix, changes config reload matching to choose the most-specific prefix, and adds gateway/browser regression coverage for profile-only `config.patch` writes.

## Best Possible Solution

Land this after updating user docs and maintainer acceptance of most-specific reload matching, keeping `browser.profiles.*` hot while `browser.enabled`, `browser.defaultProfile`, and service-level browser config remain restart-scoped.

## Reproduction Assessment

## Solution Assessment

Mostly yes. Moving the profile-specific hot rule into browser plugin reload metadata is the right ownership boundary and is better than hard-coding `browser.profiles` in core, but docs need the same carve-out and maintainers should accept the global longest-prefix semantics.

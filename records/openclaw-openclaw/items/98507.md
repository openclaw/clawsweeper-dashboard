## Summary

Keep open: the raw response cap is useful, but the current gzip guard can reject valid compressed token responses under Node fetch and still relies on an unbounded `gunzipSync` path for wrapped gzip sizes.

## What This Changes

The PR changes Google Vertex ADC token response parsing to use a shared byte-limited reader, adds gzip decoded-size checks and unit tests, and adds a standalone proof script under `scripts/`.

## Best Possible Solution

Use the shared raw-body reader plus `gunzipSync(bytes, { maxOutputLength })` with `ERR_BUFFER_TOO_LARGE` mapping, preserve the auto-decompressed gzip-header fallback, and provide terminal proof through the production token-refresh/parser path.

## Reproduction Assessment

Yes for the patch defects: source inspection plus a local Node 24 loopback fetch show that Node can expose `content-encoding: gzip` with already-decompressed JSON bytes, and the PR head would read those JSON tail bytes as ISIZE before falling back. Current main's raw `arrayBuffer()` OOM risk is source-reproducible from the existing token response path.

## Solution Assessment

No. The raw-body cap is the right direction, but the best fix should replace the ISIZE pre-check with zlib `maxOutputLength`, preserve the header-only gzip fallback, and prove the actual production parser or token-refresh path.

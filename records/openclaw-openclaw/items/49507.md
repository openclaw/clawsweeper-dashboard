## Label Justifications

- `P2`: Wrong-account cron delivery is a bounded but real multi-account bug with security and delivery impact.
- `impact:security`: Scheduled content can cross a channel-account or tenant trust boundary when session state selects a different account.
- `impact:message-loss`: Cron messages can be delivered through the wrong outbound account or recipient context.
- `impact:session-state`: Stored session `lastAccountId` currently overrides the intended agent/channel account when `accountId` is omitted.

## Summary

Keep open: current main and the latest release still allow session-derived `lastAccountId` to win before the agent/channel binding when cron delivery omits `accountId`, and the related open PRs cover adjacent channel or message-tool behavior rather than this cron delivery precedence bug.

## What This Changes

Cron jobs that specify an agent but omit `delivery.accountId` can send through a session/default account instead of the intended bound Feishu or Telegram account.

## Best Possible Solution

Define a maintainer-approved cron account precedence rule: explicit `delivery.accountId` first, then the correct agent/channel binding or fail closed when ambiguous, with focused regression coverage and upgrade guidance.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: When cron delivery omits `delivery.accountId`, should OpenClaw prefer the agent/channel binding over session-derived `lastAccountId`, or preserve the current session-account precedence?

Rationale: Both choices affect credential and tenant boundaries: binding-first prevents stale session account drift, while session-first may preserve workflows that intentionally inherit recent account context.

Likely owner: steipete

Owner reason: This person merged the existing binding-fallback behavior and is the clearest owner signal for deciding the security/compatibility precedence rule.

Owner confidence: medium

Options:

- **Prefer Binding After Explicit Account (recommended):** Keep explicit `delivery.accountId` first, then resolve the agent/channel binding before session-derived account state, failing closed when binding resolution is ambiguous.
- **Preserve Session Precedence:** Keep current behavior and document that multi-account cron jobs must set `delivery.accountId` explicitly when session account inheritance is unsafe.
- **Add Explicit Policy Surface:** Require an opt-in cron delivery account policy or migration before changing existing account precedence.

## Reproduction Assessment

Yes, at source level: current main still lets session `lastAccountId` win before the agent/channel binding, and a current test asserts that behavior. I did not run a live Feishu or Telegram multi-account cron reproduction.

## Solution Assessment

No: direct `agentId` to `accountId` inference is not the best fix because those identifiers are separate contracts. The maintainable solution is a binding-aware precedence rule with explicit compatibility and security behavior.

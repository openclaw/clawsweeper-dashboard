## Summary

Keep open: current main and the latest release still let a same-channel session-derived `lastAccountId` outrank the configured agent/channel binding for cron delivery. The issue is source-reproducible, but changing account precedence is a security and compatibility decision that needs maintainer direction.

## What This Changes

Cron jobs with `agentId` but no `accountId` can send through the wrong Feishu or Telegram account, and the report asks for safer account inference instead of stale/default account selection.

## Best Possible Solution

Define a binding-aware cron account precedence contract: keep explicit `delivery.accountId` first, prefer a unique configured agent/channel binding over stale session account state where safe, fail closed on ambiguity, and avoid naive `agentId === accountId` fallback unless maintainers explicitly approve it.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For cron delivery without `delivery.accountId`, should a configured agent/channel binding outrank a same-channel session `lastAccountId`, or should session-first behavior remain the compatibility default?

Rationale: Current source and tests preserve session-first behavior, but the reported multi-account cases show that this can cross account and credential boundaries during scheduled non-interactive delivery.

Likely owner: nxmxbbd

Owner reason: They most recently changed the cron delivery resolver and tests that govern implicit delivery safety.

Owner confidence: medium

Options:

- **Adopt binding-aware precedence (recommended):** Use explicit cron account first, then a unique configured agent/channel binding, then only safe session/default fallbacks, with fail-closed tests for ambiguity.
- **Keep session-first compatibility:** Leave `lastAccountId` precedence intact and document that multi-account cron jobs must set `--account` or stored delivery context explicitly.
- **Fail closed on disagreement:** When a cron delivery binding and session-derived account disagree, refuse delivery with a clear diagnostic instead of choosing either account.

## Reproduction Assessment

Yes, at source level: current main derives cron delivery account from session `lastAccountId` before configured agent/channel bindings, and the test suite asserts that precedence. I did not run a live Feishu or Telegram cron, so this is source-reproducible rather than live-reproduced.

## Solution Assessment

No for the proposed naive `agentId` to `accountId` fallback: the maintainable fix should use explicit account and configured binding contracts, with fail-closed behavior for ambiguous multi-account state. The exact precedence needs maintainer approval because current tests encode the opposite ordering.

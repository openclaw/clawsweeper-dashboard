## Label Justifications

- `P2`: Wrong-account cron delivery is a normal-priority bug with bounded but real multi-account security and delivery impact.
- `impact:security`: The issue describes scheduled content being sent through a different trusted account in multi-account channel setups.
- `impact:message-loss`: Cron messages can be misrouted through the wrong outbound account or recipient context.
- `impact:session-state`: Stored session account state can override the intended agent/channel account when `accountId` is omitted.

## Summary

Keep open: current main still lets a cron session-derived `lastAccountId` win before the agent/channel binding when `accountId` is omitted. The newer keyless implicit cron guard mitigates one wrong-target path, but it does not resolve this account-precedence bug, and the latest release snapshot still has the same precedence.

## What This Changes

Cron jobs should resolve the correct outbound account for the job's agent when `accountId` is omitted instead of sending through the default or last-active Feishu/Telegram account.

## Best Possible Solution

Define a maintainer-approved cron account precedence rule that keeps explicit `delivery.accountId` first, then uses the correct agent/channel binding or fails closed when ambiguous, with focused regression coverage and operator-facing upgrade guidance.

## Reproduction Assessment

Yes, at source level: current main still lets session `lastAccountId` win before the agent/channel binding, and the current test suite asserts that behavior. I did not run a live Feishu or Telegram multi-account cron reproduction.

## Solution Assessment

No: naive `agentId` to `accountId` inference is not the best fix because those identifiers are separate contracts. The maintainable fix is a binding-aware precedence rule with explicit compatibility and security behavior.

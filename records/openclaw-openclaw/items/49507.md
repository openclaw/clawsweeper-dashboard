## Label Justifications

- `P2`: Wrong-account cron delivery is a bounded but real multi-account bug with security and delivery impact.
- `impact:security`: Scheduled content can cross a channel-account or tenant trust boundary when session state selects a different account.
- `impact:message-loss`: Cron messages can be delivered through the wrong outbound account or recipient context.
- `impact:session-state`: Stored session `lastAccountId` currently overrides the intended agent/channel account when `accountId` is omitted.

## Summary

Keep open: current `main` still lets cron delivery use a session-derived `lastAccountId` before the agent/channel binding when `accountId` is omitted, and the latest release has the same precedence. The related items cover adjacent channel, message-tool, or Feishu tool-call surfaces rather than closing this cron message-delivery account bug.

## What This Changes

The issue requests binding-aware `accountId` resolution for cron delivery when a job has an `agentId` but no explicit `accountId`, so scheduled messages do not send under the wrong Feishu or other channel account.

## Best Possible Solution

Define a maintainer-approved cron account precedence rule: explicit `delivery.accountId` first, then the correct agent/channel binding or a clear fail-closed path when ambiguous, with regression coverage and upgrade guidance.

Question: When cron delivery omits `delivery.accountId`, should the resolver prefer the agent/channel binding over session-derived `lastAccountId`, or preserve current session-account precedence?

Rationale: Both choices affect credential and tenant boundaries: binding-first prevents stale session account drift, while session-first preserves behavior introduced by the existing binding-fallback PR.

Likely owner: steipete

Owner reason: This is the best available decision owner from history because steipete merged the existing precedence-bearing binding fallback PR.

Owner confidence: medium

Options:

- **Prefer binding after explicit account (recommended):** Keep explicit `delivery.accountId` first, then use the agent/channel binding before session-derived account state, failing closed when binding resolution is ambiguous.
- **Preserve session precedence:** Keep current behavior and document that multi-account cron jobs must set `delivery.accountId` explicitly when session account inheritance is unsafe.
- **Add explicit policy surface:** Require an opt-in cron delivery account policy or migration before changing existing account precedence.

## Reproduction Assessment

Yes, at source level: current `main` still lets session `lastAccountId` win before the agent/channel binding, and a current test asserts that behavior. I did not run a live Feishu or Telegram multi-account cron reproduction.

## Solution Assessment

No for the reporter's direct `agentId` to `accountId` inference, because agent ids and channel account ids are separate routing contracts. The maintainable fix is a binding-aware precedence rule with explicit compatibility and security behavior.

## Label Justifications

- `P2`: Wrong-account cron delivery is a bounded but real multi-account bug with security and delivery impact.
- `impact:security`: Scheduled content can cross a channel-account trust boundary when session state selects a different account.
- `impact:message-loss`: Cron messages can be delivered through the wrong outbound account or recipient context.
- `impact:session-state`: Stored session `lastAccountId` currently overrides the intended agent/channel account when `accountId` is omitted.

## Summary

Keep open: current main and v2026.6.11 still let session-derived `lastAccountId` win before the agent/channel binding when cron delivery omits `accountId`, so the wrong-account delivery risk remains and needs a maintainer precedence decision.

## What This Changes

The issue asks cron delivery to use the correct per-agent Feishu/channel account when `agentId` is set and `accountId` is omitted.

## Best Possible Solution

Define a maintainer-approved cron account precedence rule: explicit `delivery.accountId` first, then the correct agent/channel binding or fail closed when ambiguous, with focused regression coverage and upgrade guidance.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: When cron delivery omits `delivery.accountId`, should the resolver prefer the agent/channel binding over session-derived `lastAccountId`, or preserve current session-account precedence?

Rationale: Both choices affect a credential and tenant boundary: binding-first prevents stale session account drift, while session-first may preserve workflows intentionally inheriting the most recent account context.

Likely owner: steipete

Owner reason: steipete is the strongest current-history owner for the cron/outbound precedence lines and the security-sensitive routing choice.

Owner confidence: high

Options:

- **Prefer Binding After Explicit Account (recommended):** Keep explicit `delivery.accountId` first, then use the agent/channel binding before session-derived account state, failing closed when binding resolution is ambiguous.
- **Preserve Session Precedence:** Keep current behavior and document that multi-account cron jobs must set `delivery.accountId` explicitly when session account inheritance is unsafe.
- **Add Explicit Policy Surface:** Require a new opt-in cron delivery account policy or migration before changing existing account precedence.

## Reproduction Assessment

Yes, at source level: current main still lets session `lastAccountId` win before the agent/channel binding, and the current test suite asserts that behavior. I did not run a live Feishu or Telegram multi-account cron reproduction.

## Solution Assessment

No: direct `agentId` to `accountId` inference is not the best fix because those identifiers are separate contracts. The maintainable solution is a binding-aware precedence rule with explicit compatibility and security behavior.

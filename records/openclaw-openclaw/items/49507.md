## Label Justifications

- `P2`: Wrong-account cron delivery is a bounded but real multi-account bug with security and delivery impact.
- `impact:security`: Scheduled content can cross a channel-account or tenant trust boundary when session state selects a different account.
- `impact:message-loss`: Cron messages can be delivered through the wrong outbound account or recipient context.
- `impact:session-state`: Stored session `lastAccountId` currently overrides the intended agent/channel account when `accountId` is omitted.

## Summary

Keep open: current main still prefers session-derived `lastAccountId` before the agent/channel binding when cron delivery omits `accountId`, and the current test suite asserts that precedence. The latest release has the same resolver ordering, and related PRs cover Feishu tools, chat, channel normalization, or generic message-tool account selection rather than this cron delivery precedence bug.

## What This Changes

The issue reports cron delivery using the wrong Feishu or message-channel account when `agentId` is set but `accountId` is omitted.

## Best Possible Solution

Define a maintainer-approved cron account precedence rule: explicit `delivery.accountId` first, then the correct agent/channel binding or fail closed when ambiguous, with focused regression coverage and upgrade guidance.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: When cron delivery omits `delivery.accountId`, should the resolver prefer the agent/channel binding over session-derived `lastAccountId`, or preserve current session-account precedence?

Rationale: Both choices affect credential and tenant boundaries: binding-first prevents stale session account drift, while session-first may preserve workflows intentionally inheriting the most recent account context.

Likely owner: steipete

Owner reason: The relevant merged binding-fallback PR was merged by steipete, and prior review context already identified this as a maintainer-level security/compatibility precedence decision.

Owner confidence: medium

Options:

- **Prefer Binding After Explicit Account (recommended):** Keep explicit `delivery.accountId` first, then use the agent/channel binding before session-derived account state, failing closed when binding resolution is ambiguous.
- **Preserve Session Precedence:** Keep current behavior and document that multi-account cron jobs must set `delivery.accountId` explicitly when session account inheritance is unsafe.
- **Add Explicit Policy Surface:** Require an opt-in cron delivery account policy or migration before changing existing account precedence.

## Reproduction Assessment

Yes, at source level: current main still lets session `lastAccountId` win before the agent/channel binding, and a current test asserts that behavior. I did not run a live Feishu or Telegram multi-account cron reproduction.

## Solution Assessment

No: direct `agentId` to `accountId` inference is not the best fix because those identifiers are separate contracts. The maintainable solution is a binding-aware precedence rule with explicit compatibility and security behavior.

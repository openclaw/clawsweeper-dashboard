## Summary

Keep open: current main still lets a same-channel session-derived `lastAccountId` win over the agent/channel binding for cron delivery, and the latest release contains the same precedence. The report is source-reproducible, but the correct repair needs maintainer product/security judgment because changing account precedence can affect existing multi-account cron behavior.

## What This Changes

The issue requests that cron delivery choose the correct outbound account when a job has an `agentId` but omits `delivery.accountId`, instead of falling back to a default or stale session account.

## Best Possible Solution

Define a binding-aware cron account precedence contract: keep explicit `delivery.accountId` first, prefer a unique configured agent/channel binding over stale session account state where safe, fail closed on ambiguity, and avoid naive `agentId === accountId` fallback unless maintainers explicitly approve it.

Rationale: The current code and tests intentionally preserve session-first behavior, but the report shows that behavior can cross account/security boundaries in scheduled non-interactive delivery.

Owner confidence: medium

Options:

- **Adopt binding-aware precedence (recommended):** Use explicit cron account first, then a unique configured agent/channel binding, then only safe session/default fallbacks, with fail-closed tests for ambiguous bindings.
- **Keep session-first compatibility:** Leave `lastAccountId` precedence intact and document that multi-account cron jobs must set `--account` or a stored delivery context explicitly.
- **Fail closed on disagreement:** When a cron delivery binding and session-derived account disagree, refuse delivery and surface a clear diagnostic instead of choosing either account.

## Reproduction Assessment

Yes, from source inspection: current main derives cron delivery account from session `lastAccountId` before agent/channel bindings, and the current test suite asserts that precedence. I did not run a live Feishu or Telegram cron, so this is source-reproducible rather than live-reproduced.

## Solution Assessment

No for the proposed naive `agentId` to `accountId` fallback: the maintainable fix should use explicit account and configured binding contracts, with fail-closed behavior for ambiguous multi-account state. The exact precedence needs maintainer approval because current tests encode the opposite ordering.

## Label Justifications

- `P2`: Wrong-account cron delivery is a bounded but real multi-account bug with security and delivery impact.
- `impact:security`: Scheduled content can cross a channel-account or tenant trust boundary when session state selects a different account.
- `impact:message-loss`: Cron messages can be delivered through the wrong outbound account or recipient context.
- `impact:session-state`: Stored session `lastAccountId` currently overrides the intended agent/channel account when `accountId` is omitted.

## Summary

Keep open: current main still lets session-derived `lastAccountId` win before the configured agent/channel binding when cron delivery omits `accountId`, and the latest release has the same resolver ordering. Related open items cover channel normalization, generic message-tool omitted-account selection, or Feishu tool execution, but none has landed the cron message-delivery account-precedence fix.

## What This Changes

The issue requests that cron message delivery infer the correct channel account from the job's agent when `accountId` is omitted, instead of sending through a stale or default account.

## Best Possible Solution

Define a maintainer-approved cron account precedence rule: explicit `delivery.accountId` first, then the correct agent/channel binding or fail closed when ambiguous, with focused regression coverage and upgrade guidance.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: When cron delivery omits `delivery.accountId`, should account resolution prefer the agent/channel binding over session-derived `lastAccountId`, or preserve the current session-account precedence?

Rationale: Both choices affect credential and tenant boundaries: binding-first reduces stale session account drift, while session-first may preserve existing workflows that intentionally inherit the most recent account context.

Likely owner: steipete

Owner reason: This choice is a maintainer-level security and compatibility decision, and steipete committed the merged binding-fallback behavior this decision would revise.

Owner confidence: medium

Options:

- **Prefer Binding After Explicit Account (recommended):** Keep explicit `delivery.accountId` first, then use a single unambiguous agent/channel binding before session-derived account state, failing closed when binding resolution is ambiguous.
- **Preserve Session Precedence:** Keep current behavior and document that multi-account cron jobs must set `delivery.accountId` explicitly when session account inheritance is unsafe.
- **Add Explicit Policy Surface:** Require a dedicated cron delivery account policy or migration before changing existing account precedence.

## Reproduction Assessment

Yes at source level: current main still lets session `lastAccountId` win before the agent/channel binding, and a current test asserts that behavior. I did not run a live Feishu or Telegram multi-account cron reproduction.

## Solution Assessment

No: direct `agentId` to `accountId` inference is not the best fix because those identifiers are separate contracts. The maintainable solution is a binding-aware precedence rule with explicit compatibility and security behavior.

## Summary

Keep open: current main still allows a same-channel session-derived `lastAccountId` to beat the agent/channel binding for cron announce delivery, and the latest release has the same precedence. The report is source-reproducible, but the repair needs maintainer security/product direction because changing account precedence can alter existing multi-account cron behavior.

## What This Changes

The issue asks cron announce delivery to avoid using the wrong Feishu or Telegram account when `agentId` is set but `delivery.accountId` is omitted.

## Best Possible Solution

Define a binding-aware cron account precedence contract: keep explicit `delivery.accountId` first, prefer a unique configured agent/channel binding over stale session account state where safe, fail closed on ambiguity or disagreement, and avoid naive `agentId === accountId` inference unless maintainers explicitly approve it.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For cron announce delivery without explicit `delivery.accountId`, should a configured agent/channel binding outrank a same-channel session `lastAccountId`, should disagreement fail closed, or should current session-first compatibility remain?

Rationale: The current source and tests intentionally preserve session-first account behavior, but the issue reports wrong-account scheduled delivery across multi-account trust boundaries; automation should not choose that security/compatibility policy alone.

Likely owner: steipete

Owner reason: They have the strongest visible history across cron delivery, session routing, and binding helper surfaces involved in the policy decision.

Owner confidence: high

Options:

- **Adopt binding-aware precedence (recommended):** Use explicit cron account first, then a unique configured agent/channel binding, then safe session/default fallbacks, with tests for wrong-account and ambiguous-binding cases.
- **Fail closed on disagreement:** Refuse delivery when session-derived and binding-derived accounts disagree, surfacing a diagnostic instead of silently choosing an account.
- **Keep session-first compatibility:** Leave `lastAccountId` precedence intact and document that multi-account cron jobs must set `--account` or stored delivery context explicitly.

## Reproduction Assessment

Yes, at source level: current main uses session `lastAccountId` before the agent/channel binding, and the current test suite asserts that ordering. I did not run a live Feishu or Telegram cron job, so this is source-reproducible rather than live-reproduced.

## Solution Assessment

No for the proposed naive `agentId` to `accountId` fallback: OpenClaw docs and routing contracts treat agent ids and account ids as separate identifiers. The best fix is a maintainer-approved binding-aware precedence rule with fail-closed handling for ambiguous multi-account state.

## Summary

Keep open: current main and v2026.6.11 still let same-channel session `lastAccountId` outrank the configured agent/channel binding for cron delivery, so the reported wrong-account path remains source-reproducible and needs maintainer precedence direction.

## What This Changes

The issue reports that cron jobs with `agentId` but no `delivery.accountId` can send through a stale or default Feishu/Telegram account and asks for account inference from agent context.

## Best Possible Solution

Define a binding-aware cron account precedence contract: keep explicit `delivery.accountId` first, prefer a unique configured agent/channel binding over stale same-channel session state where safe, fail closed on ambiguity, and avoid naive `agentId === accountId` fallback unless maintainers explicitly approve it.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For cron delivery without `delivery.accountId`, should a configured agent/channel binding outrank a same-channel session `lastAccountId`, or should session-first behavior remain the compatibility default?

Rationale: Current source and tests intentionally preserve session-first behavior, but the reported multi-account cases show that this can cross account and credential boundaries during scheduled non-interactive delivery.

Likely owner: steipete

Owner reason: The decision is product/security precedence rather than a purely mechanical patch, and steipete has adjacent cron routing/account history plus merger history in this surface.

Owner confidence: medium

Options:

- **Adopt binding-aware precedence (recommended):** Use explicit cron account first, then a unique configured agent/channel binding, then only safe session/default fallbacks, with fail-closed tests for ambiguity.
- **Keep session-first compatibility:** Leave `lastAccountId` precedence intact and document that multi-account cron jobs must set `--account` or stored delivery context explicitly.
- **Fail closed on disagreement:** When cron delivery has both a binding-derived account and a different session-derived account, refuse delivery with a clear diagnostic.

## Reproduction Assessment

Yes, at source level: current main derives cron delivery account from session `lastAccountId` before configured agent/channel bindings, and the test suite asserts that precedence. I did not run a live Feishu or Telegram cron, so this is source-reproducible rather than live-reproduced.

## Solution Assessment

No for the proposed naive `agentId` to `accountId` fallback: the maintainable fix should use explicit account and configured binding contracts, with fail-closed behavior for ambiguous multi-account state. The exact precedence needs maintainer approval because current tests encode the opposite ordering.

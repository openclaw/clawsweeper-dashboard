## Summary

Keep open: current main and the latest release still let a same-channel session-derived `lastAccountId` outrank an agent/channel binding for cron delivery. The issue is source-reproducible, but the repair needs maintainer security and compatibility direction because changing account precedence can affect existing multi-account cron setups.

## What This Changes

The issue asks cron delivery to resolve the correct channel account when `agentId` is set but `delivery.accountId` is omitted, instead of using stale or default account state.

## Best Possible Solution

Define a binding-aware cron account precedence contract: keep explicit `delivery.accountId` first, prefer a unique configured agent/channel binding over stale session account state where safe, fail closed on ambiguity, and avoid `agentId === accountId` fallback unless maintainers explicitly approve it.

- **Keep session-first compatibility:** Leave `lastAccountId` precedence intact and document that multi-account cron jobs must set `--account` or a stored delivery context explicitly.
- **Fail closed on disagreement:** When a cron delivery binding and session-derived account disagree, refuse delivery with a clear diagnostic instead of choosing either account.

## Reproduction Assessment

Yes, at source level: current main derives cron delivery account from session `lastAccountId` before agent/channel bindings, and the current test suite asserts that precedence. I did not run a live Feishu or Telegram cron, so this is source-reproducible rather than live-reproduced.

## Solution Assessment

No for the proposed naive `agentId` to `accountId` fallback. The maintainable fix should use explicit account and configured binding contracts, with fail-closed behavior for ambiguous multi-account state.

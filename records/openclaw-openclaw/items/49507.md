## Summary

Keep open: current main and v2026.6.11 still let a same-channel session-derived account outrank the configured agent/channel binding for cron delivery, and no merged or open PR currently owns this exact account-precedence fix.

## What This Changes

The issue reports that cron delivery without an explicit accountId can send through the wrong Feishu or Telegram account instead of the intended agent-bound identity.

## Best Possible Solution

Define a binding-aware cron account precedence contract: keep explicit delivery.accountId first, prefer a unique configured agent/channel binding over stale session account state where safe, fail closed on ambiguity, and avoid naive agentId-to-accountId mapping unless maintainers explicitly approve it.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For cron delivery without delivery.accountId, should a configured agent/channel binding outrank a same-channel session lastAccountId, or should session-first behavior remain the compatibility default?

Rationale: Current source and tests preserve session-first behavior, but the reported multi-account cases show that stale session account state can cross account, credential, and tenant boundaries during scheduled non-interactive delivery.

Likely owner: steipete

Owner reason: They are the strongest available routing-decision owner from the current cron/outbound history and the merged binding-fallback provenance.

Owner confidence: medium

Options:

- **Adopt Binding-Aware Precedence (recommended):** Use explicit cron account first, then a unique configured agent/channel binding, then only safe session/default fallbacks, with fail-closed handling for ambiguity.
- **Keep Session-First Compatibility:** Leave lastAccountId precedence intact and document that multi-account cron jobs must set delivery.accountId explicitly.
- **Fail Closed On Disagreement:** Refuse delivery when configured binding and session-derived account disagree instead of choosing either account silently.

## Reproduction Assessment

Yes, at source level: current main derives cron delivery account from session lastAccountId before configured agent/channel bindings, and the focused test suite asserts that precedence. I did not run a live Feishu or Telegram cron, so this is not live-reproduced.

## Solution Assessment

No for the proposed naive agentId-to-accountId fallback: the maintainable fix should use explicit account and configured binding contracts, with fail-closed behavior for ambiguous multi-account state. The exact precedence needs maintainer approval because current tests encode the opposite ordering.

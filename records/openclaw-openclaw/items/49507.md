## Summary

Keep open: current main and v2026.6.11 still let a same-channel stored session `lastAccountId` beat the agent/channel binding; the remaining account-precedence change is security- and compatibility-sensitive and needs maintainer direction.

## What This Changes

The issue asks cron delivery to avoid sending from the wrong Feishu or messaging account when a job has `agentId` but omits `accountId`.

## Best Possible Solution

Define one explicit cron account precedence contract: `delivery.accountId` wins, proven same-route session account is allowed only when it cannot cross accounts, and ambiguous or conflicting session-vs-binding accounts fail closed with a diagnostic plus cron/channel regression tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For cron announce delivery with `agentId` and no `delivery.accountId`, should OpenClaw prefer a same-channel session `lastAccountId`, the agent/channel binding, or fail closed when those can disagree?

Rationale: This changes account identity selection for scheduled sends, so automation cannot safely choose between compatibility with current session-first behavior and the security goal of preventing cross-account delivery.

Likely owner: steipete

Owner reason: He merged the original binding-fallback work and is the clearest available owner signal for a security/product routing decision.

Owner confidence: medium

Options:

- **Fail closed on ambiguity (recommended):** Keep explicit `delivery.accountId` highest, use a binding only when no conflicting session account is present or the route proves the same account, and otherwise refuse with a clear cron diagnostic.
- **Prefer agent binding:** Make the bound agent/channel account outrank session history for cron delivery, accepting that existing jobs relying on session account drift may change behavior.
- **Keep session-first:** Preserve current compatibility and document that multi-account cron jobs must set `delivery.accountId` explicitly to avoid wrong-account sends.

## Reproduction Assessment

Yes. Source inspection and current tests show that a cron delivery with a same-channel `lastAccountId` uses that session account even when the agent has a different bound account; I did not run a live Feishu or Telegram cron.

## Solution Assessment

No. The suggested naive `agentId` to `accountId` fallback is too broad because account IDs need not equal agent IDs; a binding-aware and ambiguity-safe precedence contract is the maintainable fix.

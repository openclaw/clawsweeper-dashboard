## Label Justifications

- `P2`: Wrong-account cron delivery is a bounded but real multi-account security and message-routing bug.
- `impact:security`: The issue describes scheduled content being sent through the wrong trusted account boundary.
- `impact:message-loss`: Cron delivery can route scheduled messages through the wrong account or recipient context.
- `impact:session-state`: Stored session `lastAccountId` can override the intended agent/channel account when `accountId` is omitted.

## Summary

Keep open: current main and the latest release still let session-derived `lastAccountId` win before the agent/channel binding when cron delivery omits `accountId`, so the wrong-account cron delivery problem remains real and security-sensitive.

## What This Changes

The issue reports cron delivery selecting the wrong Feishu or Telegram account when `accountId` is omitted, and asks for safer account inference tied to the job/agent instead of stale/default account fallback.

## Best Possible Solution

Define and implement a maintainer-approved cron account precedence rule that keeps explicit `delivery.accountId` first, then resolves binding/session context deliberately with regression coverage.

## Reproduction Assessment

Yes, at source level: current main still lets session-derived `lastAccountId` win before the agent/channel binding, and the current test suite asserts that behavior. I did not run a live Feishu or Telegram multi-account cron reproduction.

## Solution Assessment

No: naive `agentId` to `accountId` inference is not the best fix because those identifiers are separate contracts. The maintainable fix is a binding-aware precedence rule with explicit upgrade/security behavior.

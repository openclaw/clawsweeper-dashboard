- `impact:security`: The issue describes scheduled content being sent through a different trusted account in multi-account channel setups.
- `impact:message-loss`: Cron messages can be misrouted through the wrong outbound account or recipient context.

## Summary

Keep open: current main still lets a cron session-derived `lastAccountId` win before the agent/channel binding when `accountId` is omitted, so the reported wrong-account cron delivery problem is not implemented away.

## What This Changes

The issue asks cron delivery to avoid wrong-account sends when `agentId` is set but `delivery.accountId` is omitted.

## Best Possible Solution

Define a maintainer-approved cron account precedence rule that keeps explicit `delivery.accountId` first, then uses the correct agent/channel binding or fails closed when ambiguous, with regression coverage and upgrade guidance.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should omitted cron delivery account IDs prefer a configured agent/channel binding over session-derived `lastAccountId`, and should ambiguous binding/session cases fail closed?

Rationale: This changes credential and tenant routing behavior for scheduled messages, so automation should not choose the permanent compatibility/security rule without maintainer intent.

Likely owner: steipete

Owner reason: steipete merged the binding-fallback behavior and is the strongest available owner for the account-precedence security choice.

Owner confidence: high

Options:

- **Prefer binding after explicit account (recommended):** Change cron delivery so explicit `delivery.accountId` wins, then a safe agent/channel binding wins over stale session account state, with ambiguity failing closed.
- **Keep session precedence:** Document that cron delivery inherits session `lastAccountId` unless users set `--account`, preserving compatibility but leaving this wrong-account class to operator configuration.
- **Require explicit account in risky cases:** Keep existing precedence for simple cases but make multi-account cron delivery without explicit account fail with an actionable error.

## Reproduction Assessment

Yes, at source level: current main still lets session `lastAccountId` win before the agent/channel binding, and the current test suite asserts that behavior. I did not run a live Feishu or Telegram multi-account cron reproduction.

## Solution Assessment

No: naive `agentId` to `accountId` inference is not the best fix because those identifiers are separate contracts. The maintainable fix is a binding-aware precedence rule with explicit compatibility and security behavior.

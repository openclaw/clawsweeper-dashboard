## Label Justifications

- `P2`: Wrong-account cron delivery is a normal-priority multi-account bug with bounded but real security and delivery impact.
- `impact:security`: Scheduled content can be sent through a different trusted channel account boundary in multi-account setups.
- `impact:message-loss`: Cron messages can be misrouted through the wrong outbound account or recipient context.
- `impact:session-state`: Stored session account state can override the intended agent/channel account when `accountId` is omitted.

## Summary

Keep open: current main and the latest release still let cron session-derived `lastAccountId` win before the agent/channel binding when `accountId` is omitted, so the wrong-account delivery risk remains and needs maintainer precedence direction.

## What This Changes

The issue reports cron delivery choosing the wrong Feishu or message-channel account when `agentId` is set but `accountId` is omitted.

## Best Possible Solution

Define a maintainer-approved cron account precedence rule that keeps explicit `delivery.accountId` first, then uses the correct agent/channel binding or fails closed when ambiguous, with focused regression coverage and operator-facing upgrade guidance.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When a cron job omits `delivery.accountId`, should cron delivery prefer the agent/channel binding over session-derived `lastAccountId`, or preserve the current session-account precedence?

Rationale: Both choices affect security and compatibility: binding-first prevents stale session account drift, while session-first may preserve workflows that intentionally inherit the most recent account context.

Likely owner: steipete

Owner reason: steipete is the strongest routing candidate from current blame and prior review context for this security-sensitive cron account precedence decision.

Owner confidence: high

Options:

- **Prefer binding after explicit account (recommended):** Keep explicit `delivery.accountId` first, then use the agent/channel binding before any session-derived account, and fail closed when the binding is ambiguous.
- **Preserve session precedence:** Keep current behavior and document that multi-account cron jobs must set `delivery.accountId` explicitly when session account inheritance is not desired.
- **Add an explicit policy surface:** Require a new opt-in cron delivery account policy or migration before changing existing account precedence.

## Reproduction Assessment

Yes, at source level: current main still lets session `lastAccountId` win before the agent/channel binding, and the current test suite asserts that behavior. I did not run a live Feishu or Telegram multi-account cron reproduction.

## Solution Assessment

No: direct `agentId` to `accountId` inference is not the best fix because those identifiers are separate contracts. The maintainable fix is a binding-aware precedence rule with explicit compatibility and security behavior.

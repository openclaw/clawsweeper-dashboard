## Label Justifications

- `P2`: Wrong-account cron delivery is a normal-priority bug with bounded but real multi-account security and delivery impact.
- `impact:security`: The issue describes scheduled content being sent through a different trusted account in multi-account channel setups.
- `impact:message-loss`: Cron messages can be misrouted through the wrong outbound account or recipient context.

## Summary

Keep open: current main still lets a cron session-derived `lastAccountId` win before the agent/channel binding when `accountId` is omitted, and the latest release has the same precedence. Related open work covers adjacent channel normalization or generic omitted-account selection, but not this exact cron account-precedence bug.

## What This Changes

The issue reports cron/proactive delivery selecting the wrong message account when `accountId` is omitted in multi-account channel setups.

## Best Possible Solution

Define a maintainer-approved cron account precedence rule that keeps explicit `delivery.accountId` first, then uses the correct agent/channel binding or fails closed when ambiguous, with focused regression coverage and operator-facing upgrade guidance.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For cron/proactive message delivery with no explicit `delivery.accountId`, should the resolver prefer the agent/channel binding over session `lastAccountId`, keep the current session-first behavior, or fail closed when both are plausible?

Rationale: The source-level bug is clear, but changing this precedence is a compatibility- and security-sensitive behavior choice for existing multi-account cron setups.

Likely owner: steipete

Owner reason: steipete committed the binding-fallback change and is a strong routing candidate for a security-sensitive precedence decision.

Owner confidence: medium

Options:

- **Prefer binding before session account (recommended):** Keep explicit job `accountId` first, then use the unique agent/channel binding, and only use session account when it cannot conflict with that binding.
- **Fail closed on ambiguity:** When a session account and bound account differ, refuse delivery and ask the operator to set `delivery.accountId` explicitly.
- **Keep session-first behavior:** Preserve compatibility but document that cron jobs must set `accountId` explicitly to avoid wrong-account delivery.

## Reproduction Assessment

Yes at source level: current main still lets session `lastAccountId` win before the agent/channel binding, and a current test asserts that behavior. I did not run a live Feishu or Telegram multi-account cron reproduction.

## Solution Assessment

No: naive `agentId` to `accountId` inference is not the best fix because agent ids and channel account ids are separate contracts. The maintainable fix is a binding-aware precedence rule or fail-closed ambiguity handling chosen by maintainers.

## Summary

Keep open: current main and the latest release still allow a same-channel session-derived `lastAccountId` to outrank the configured agent/channel binding for cron delivery. The report is source-reproducible, but changing account precedence is a security and compatibility decision that should be made by maintainers first.

## What This Changes

Cron delivery without an explicit `accountId` should use the intended agent/channel account instead of a stale default or last-active messaging account.

## Best Possible Solution

Define a binding-aware cron account precedence contract: keep explicit `delivery.accountId` first, prefer a unique configured agent/channel binding over stale session account state where safe, fail closed on ambiguity, and avoid naive `agentId === accountId` fallback unless maintainers explicitly approve it.

Options:

- **Adopt binding-aware precedence (recommended):** Use explicit cron account first, then a unique configured agent/channel binding, then only safe session/default fallbacks, with fail-closed tests for ambiguity.
- **Keep session-first compatibility:** Leave `lastAccountId` precedence intact and document that multi-account cron jobs must set `--account` or a stored delivery context explicitly.
- **Fail closed on disagreement:** When a cron delivery binding and session-derived account disagree, refuse delivery with a clear diagnostic instead of choosing either account.

## Reproduction Assessment

Yes, at source level: current main derives cron delivery account from session `lastAccountId` before configured agent/channel bindings, and the test suite asserts that precedence. I did not run a live Feishu or Telegram cron, so this is source-reproducible rather than live-reproduced.

## Solution Assessment

No for the proposed naive `agentId` to `accountId` fallback: the maintainable fix should use explicit account and configured binding contracts, with fail-closed behavior for ambiguous multi-account state. The exact precedence needs maintainer approval because current tests encode the opposite ordering.

Keep open: current main and the latest release still preserve automatic TTS fallback from the configured provider to another configured provider, while the merged related work only made fallback visible and fixed adjacent registration/config issues.

## What This Changes

The issue requests that configured ElevenLabs TTS audio be played instead of falling through to OpenAI after ElevenLabs is selected or called.

## Best Possible Solution

Make a maintainer-owned TTS fallback policy decision, then align speech-core behavior, status output, docs, and regression tests around the chosen behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should messages.tts keep automatic fallback across configured providers by default, or should a configured provider be sticky/fail-closed for auto-TTS when it fails or is skipped?

Rationale: Current source, docs, and tests intentionally preserve fallback behavior, but this report shows that the behavior can surprise users and make ElevenLabs look ignored after configuration.

Likely owner: joshavant

Owner reason: joshavant authored the related diagnostics PRs and already framed provider stickiness as the remaining decision in the issue discussion.

Owner confidence: high

Options:

- **Keep fallback default, design explicit stickiness (recommended):** Preserve the documented fallback chain and add or document an explicit strict/sticky provider path only if maintainers want users to opt into fail-closed provider selection.
- **Make configured provider sticky by default:** Change messages.tts synthesis so the configured provider fails visibly instead of trying other configured providers, then update docs and tests for the compatibility change.
- **Close as expected fallback behavior:** Treat fallback-to-OpenAI as intended when ElevenLabs fails or is skipped, and leave only diagnostics/education work for future reports.

## Reproduction Assessment

No high-confidence live reproduction exists for the reporter's Ubuntu and ElevenLabs setup. Source inspection confirms current main can still fall through from a configured primary TTS provider to another provider when the primary attempt fails or is skipped.

## Solution Assessment

Unclear until maintainers decide the policy. The existing diagnostics and registration fixes are useful partial fixes, but a narrow code change would either fight the documented fallback contract or intentionally change it.

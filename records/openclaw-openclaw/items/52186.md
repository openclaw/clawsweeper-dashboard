## What This Changes

## Best Possible Solution

Make an explicit TTS fallback-versus-stickiness decision, then update speech-core behavior, status output, docs, and regression tests together.

## Maintainer Decision

Kind: product_direction

Question: Should auto TTS keep the documented multi-provider fallback default when the configured provider fails or is skipped, or should a configured provider be sticky and fail loudly instead of playing a fallback voice?

Rationale: Both behaviors are plausible: fallback preserves availability and matches current docs/tests, while stickiness avoids surprising provider changes and possible paid-provider confusion.

Likely owner: steipete

Owner reason: steipete has the strongest history across core TTS, fallback provider behavior, and speech provider registration, so this product-policy call routes there best.

Owner confidence: medium

Options:

- **Keep fallback default, add strict path (recommended):** Preserve current documented fallback behavior for upgrades, but add or reuse a clear strict-provider path for users who require ElevenLabs-only playback.
- **Make configured provider sticky by default:** Change auto TTS so messages.tts.provider failure stops playback instead of using another provider, with release notes and regression coverage for the behavior change.
- **Keep diagnostics-only behavior:** Leave fallback semantics unchanged and close future requests as expected behavior once docs/status messaging are judged sufficient.

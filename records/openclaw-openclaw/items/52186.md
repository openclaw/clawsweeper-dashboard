## Summary

Keep open: current main and the latest release still allow a configured TTS provider to fall through to another configured provider after skip/error cases, while the merged related PRs only fixed registration, compatibility, and diagnostics. The remaining question is whether OpenClaw should keep documented fallback semantics or add stricter provider stickiness for configured voices.

## What This Changes

The issue asks OpenClaw to stop playing an OpenAI TTS voice when ElevenLabs is configured and has processed the TTS request.

## Best Possible Solution

Define the intended TTS provider policy, then make configured-provider fallback explicit: either keep fallback with stronger user-visible warnings and controls, or add a maintainable sticky/fail-closed path for selected voice providers with matching tests and docs.

## Reproduction Assessment

No live high-confidence reproduction was run for the reporter's exact Ubuntu/ElevenLabs/OpenAI playback setup. Source inspection does reproduce the remaining policy path: selected TTS providers can still fall through to later configured providers on skip/error cases.

## Solution Assessment

Unclear as an implementation choice: strict provider stickiness would address the reported surprise, but it changes documented fallback semantics. The best next step is a maintainer decision on fallback policy before a fix PR changes runtime behavior.

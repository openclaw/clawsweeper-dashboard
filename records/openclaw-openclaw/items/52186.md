Required: true

Kind: product_direction

Question: Should configured TTS providers stay best-effort with automatic fallback, or should OpenClaw add a strict provider-stickiness/fail-closed mode for users who never want fallback speech?

Rationale: Current source and docs intentionally treat other configured TTS providers as fallbacks, while the remaining request would change user-visible provider-routing semantics and likely add config surface.

Likely owner: steipete

Owner reason: The current fallback loop and recent TTS/provider routing work point to steipete as the best available owner for the product-direction choice.

Owner confidence: high

Options:

- **Preserve automatic fallback by default (recommended):** Keep the current default behavior, require live proof for any successful-audio-discard bug, and improve only diagnostics or targeted provider failures as needed.
- **Add opt-in strict TTS mode:** Expose a narrow documented setting so users can choose no fallback without breaking existing fallback users by default.
- **Make stickiness unconditional:** Stop on configured-provider failure instead of falling back, accepting an upgrade-sensitive behavior change for users who currently depend on fallback speech.

## Summary

Keep open: current main and the latest release still intentionally try fallback speech providers after a configured TTS provider is skipped or fails, while the exact claim that successful ElevenLabs audio is discarded still needs live proof.

## What This Changes

The issue asks OpenClaw to respect a configured ElevenLabs TTS provider instead of playing an OpenAI voice after ElevenLabs appears to process the request.

## Best Possible Solution

Decide and document the TTS fallback policy; if provider stickiness is desired, add an explicit strict or disable-fallback path with focused speech-core tests and status diagnostics while preserving the existing default unless maintainers approve a breaking change.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Auto-TTS keep using other configured speech providers as fallbacks when the selected provider is skipped or fails, or should OpenClaw expose/enable provider stickiness for configured providers?

Rationale: Current docs and tests make fallback deliberate, but this report shows the fallback can surprise users and obscure billing/provider expectations; automation should not choose that policy without maintainer intent.

Likely owner: Peter Steinberger

Owner reason: Peter has the most recent current-main ownership signal on the speech-core TTS surface, while the remaining decision is cross-cutting fallback policy.

Owner confidence: medium

Options:

- **Add opt-in provider stickiness (recommended):** Keep fallback as the compatibility default, but expose a documented strict mode that fails visibly instead of playing another provider when the selected provider cannot be used.
- **Keep fallback-only behavior:** Close the remaining behavior as expected after improving docs/status messaging enough that users understand why OpenAI may play.
- **Fail closed by default:** Make configured providers sticky by default and require an upgrade note because existing fallback setups may stop producing audio.

## Reproduction Assessment

No high-confidence live reproduction of the exact successful-ElevenLabs-then-OpenAI playback path is available. Source inspection does show the remaining fallback path: if the selected provider is skipped or fails, OpenClaw can synthesize with another configured provider and record fallbackFrom.

## Solution Assessment

Unclear: forcing provider stickiness is not automatically the best fix because current docs describe fallback as intentional. The safer path is a maintainer-approved fallback policy, likely preserving fallback by default and adding an explicit strict mode if needed.

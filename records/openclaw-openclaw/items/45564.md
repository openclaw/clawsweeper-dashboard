## Summary

Keep open. Current main still leaves explicitly typed `/new` and hard `/reset` unconfirmed in the Control UI, TUI, and channel/Gateway reset paths; the merged button-confirmation work only covers an adjacent UI affordance, so the remaining change needs maintainer UX/config policy.

## What This Changes

The issue asks for a confirmation step, optionally configurable, before destructive `/new` and `/reset` session-wipe commands.

## Best Possible Solution

Define one maintainer-approved destructive-command confirmation contract across Control UI, TUI, and channel/Gateway paths, avoiding a new config knob unless maintainers explicitly accept that surface.

Rationale: Current main already protects the button-triggered New Session path, but typed commands remain immediate across multiple surfaces; changing that behavior or adding a config option is a UX/config contract decision.

Options:

- **Confirm typed destructive commands (recommended):** Add one short-lived repeat-to-confirm or equivalent confirmation for typed `/new` and hard `/reset`, while preserving `/reset soft` and non-destructive commands.
- **Keep typed commands immediate:** Treat explicitly typed `/new` and hard `/reset` as intentional expert commands and leave only click/tap affordances guarded.
- **Make confirmation configurable:** Add an opt-out or step-count policy, accepting the extra config, docs, tests, and upgrade proof burden.

Yes, at source level. Current main and the latest release both show typed `/new` and hard `/reset` bypass confirmation in Control UI, while TUI and channel/Gateway handlers execute the same destructive command family immediately.

## Solution Assessment

Unclear until maintainers choose the UX contract. A single repeat-within-timeout confirmation looks narrower than the requested 2-3 clicks or new config, but the surface coverage and opt-out policy need product approval first.

## Summary

Keep open. Current main and the latest release still leave typed `/new` and destructive typed `/reset` unconfirmed in the Control UI and TUI, while the merged confirmation work only covers button/override paths; the remaining change needs maintainer UX and config-contract direction.

## What This Changes

The issue asks for confirmation before destructive typed `/new` and `/reset` commands wipe or reset session context, with an optional configurable confirmation depth.

## Best Possible Solution

Define one maintainer-approved confirmation contract for destructive explicit session commands across Control UI, TUI, and relevant channel/Gateway paths, with a safe default and no new config knob unless maintainers explicitly accept that surface.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 show typed `/new` and `/reset` bypass confirmation in Control UI tests and handlers, and the TUI handler resets or rotates sessions immediately.

## Solution Assessment

Unclear as an implementation request. A single confirmation step is likely narrower than 2-3 clicks or a new config tree, but maintainers still need to choose the command-surface and config policy before implementation.

## Summary

Keep open. Current main still leaves explicit typed `/new` and hard `/reset` unconfirmed across Control UI, TUI, and Gateway command paths; the merged button work only covered the older button-triggered New Session affordance, so the remaining command-confirmation and config policy needs maintainer direction.

## What This Changes

Request a confirmation step, and optionally a configurable confirmation count, before `/new` or hard `/reset` can wipe or replace session context.

## Best Possible Solution

Adopt one maintainer-approved hard-reset confirmation policy across explicit command surfaces, likely a single confirmation for `/new` and hard `/reset` with `/reset soft` exempt, and avoid a new config knob unless maintainers explicitly choose an opt-out.

Unclear pending maintainer policy. A one-step confirmation for `/new` and hard `/reset` is more maintainable than 2-3 confirmations, but config and cross-client parity need owner direction before implementation.

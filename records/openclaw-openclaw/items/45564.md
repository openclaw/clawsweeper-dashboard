## Summary

Keep open. Current main and v2026.6.11 still preserve unconfirmed typed `/new` and hard `/reset` behavior in Control UI, TUI, and channel/Gateway reset handling; the remaining work is a real session-state UX request but needs maintainer product/config direction before implementation.

## What This Changes

The issue requests a confirmation step before destructive `/new` and `/reset` session wipes, with an optional configurable confirmation count.

## Best Possible Solution

Define one maintainer-approved hard-reset confirmation contract for explicit commands across Control UI, TUI, and channel/Gateway paths, and avoid adding config unless maintainers explicitly accept that compatibility cost.

## Reproduction Assessment

Yes, at source level: current tests and handlers show typed `/new` and hard `/reset` bypass confirmation in Control UI, while TUI and channel/Gateway reset paths act immediately.

## Solution Assessment

Unclear as a direct implementation request. A single confirmation step may be right, but confirmation depth, timeout behavior, config shape, and cross-surface scope need maintainer approval first.

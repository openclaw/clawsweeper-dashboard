## Summary

Keep open. Current main and v2026.6.11 still leave typed `/new` and destructive `/reset` unconfirmed, while the merged button-confirmation work only covers adjacent Control UI affordance cases; the remaining command policy needs maintainer UX/config direction.

## What This Changes

Request adds a confirmation step, and optionally configurable confirmation depth, before `/new` or `/reset` can wipe or rotate a session.

## Best Possible Solution

Define one maintainer-approved hard-reset confirmation contract for explicit commands across Control UI, TUI, and channel/Gateway paths, with no new config knob unless maintainers explicitly accept the compatibility cost.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 handlers and tests show typed `/new` and destructive `/reset` bypass confirmation in Control UI and the TUI command handler resets or rotates sessions immediately.

## Solution Assessment

Unclear as an implementation request. A single confirmation step may be right, but confirmation depth, config shape, timeout behavior, and which command surfaces change need maintainer approval first.

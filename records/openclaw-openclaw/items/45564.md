## Summary

Keep open. Current main and v2026.6.11 still confirm only button-triggered Control UI new-session resets; typed `/new`, typed hard `/reset`, TUI reset commands, and Gateway bare reset handling remain immediate, so the remaining behavior needs maintainer product direction.

## What This Changes

The issue requests a confirmation step, and optionally a config knob, before `/new` and `/reset` wipe session state.

## Best Possible Solution

Adopt one maintainer-approved destructive-command policy across command surfaces, likely a single confirmation for `/new` and hard `/reset` with `/reset soft` exempt, and add config only if maintainers accept that public surface.

Options:

- **Confirm hard resets by default (recommended):** Add a one-step confirmation for typed `/new` and hard `/reset`, keep `/reset soft` immediate, and defer config until user evidence proves an opt-out is needed.
- **Add configurable confirmation:** Add confirmation plus a documented opt-out or step-count setting, accepting the extra schema, docs, and upgrade-policy burden.
- **Preserve explicit command behavior:** Keep typed reset commands immediate and limit confirmation to visible UI affordances such as buttons.

## Reproduction Assessment

Yes at source level. Current main tests explicitly assert typed `/new` and typed `/reset` bypass confirmation, and current source only runs the confirmation guard for override sends with `confirmReset`.

## Solution Assessment

Unclear pending maintainer policy. A one-step hard-reset confirmation appears more maintainable than the requested two or three steps, and the config knob should not be added unless maintainers choose that public surface.

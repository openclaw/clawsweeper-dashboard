## Summary

Keep open for maintainer product and security review: current main and v2026.6.11 still lack declarative scheduled/event SKILL.md trigger metadata, cron registration from skill frontmatter, skill-level last-triggered output, and a settled trust boundary for autonomous skill execution.

## What This Changes

Request declarative scheduled/event trigger metadata in SKILL.md frontmatter so skills can self-describe autonomous cron or lifecycle triggers and expose trigger audit status.

## Best Possible Solution

Define the permissioned automation contract first, then implement one coordinated path for metadata parsing, scheduler/event registration, audit state, CLI/docs output, and regression coverage.

Options:

- **Define Permissioned Trigger Contract (recommended):** Keep this issue open while maintainers specify a guarded SKILL.md trigger contract covering trusted sources, operator approval, scheduler registration, event names, last-triggered state, and revocation.
- **Route To Explicit Cron/Plugin APIs:** Reject SKILL.md-owned autonomous triggers and require skills or plugins to document explicit operator-created cron jobs or maintainer-approved plugin hooks instead.
- **Metadata-Only First:** Allow a non-executing documentation field such as trigger_description for audits while deferring automatic cron/event registration to a later security review.

## Reproduction Assessment

Yes for the source-level feature gap, not as a bug reproduction. Current main and v2026.6.11 omit trigger metadata from skill parsing, prompt rendering, cron registration, and skills list output.

## Solution Assessment

Unclear until maintainers choose the product and security boundary. A SKILL.md field is plausible, but the safest path must decide whether autonomous scheduling belongs in skill metadata, explicit cron jobs, or a permissioned plugin API first.

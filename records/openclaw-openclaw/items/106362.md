## Label Justifications

- `P1`: A real multi-tab workflow silently loses a successfully created user catalog entry with no conflict or recovery signal.
- `impact:data-loss`: A later stale writer deletes an independently created persisted custom group without warning.
- `impact:ux-friction`: Both tabs converge on the winning state without explaining that one user's successful creation was discarded.

## Summary

This is a current, concrete concurrency bug in the custom session-group catalog: two independent clients can both succeed while the later full-catalog replacement silently discards the earlier addition. The protected `maintainer` label also requires explicit maintainer handling, and the related issue covers rejected-write error presentation rather than the lost-update root cause.

## What This Changes

Make custom session-group mutations preserve concurrent additions or return an explicit stale-write conflict instead of silently replacing a newer catalog.

## Best Possible Solution

Define a Gateway-owned atomic mutation contract that preserves concurrent additions and ordering, or returns a typed revision conflict that clients visibly refresh and retry, with coverage for two stale clients and both Control UI creation entry points.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should the session-group API move to semantic atomic mutations, or retain full-catalog replacement with revision-based compare-and-set conflicts?

Rationale: Both designs can prevent lost updates, but the durable Gateway protocol, ordering semantics, and client retry behavior require an explicit owner decision rather than an automated narrow patch.

Likely owner: steipete

Owner reason: The available evidence identifies the reporter as the only person concretely connected to the current behavior, though git-history ownership could not be established.

Owner confidence: low

Options:

- **Atomic semantic mutations (recommended):** Add Gateway operations for add/remove/reorder that transact against authoritative rows and preserve concurrent additions.
- **Revisioned catalog replacement:** Return a catalog revision from reads and reject stale full replacements so clients can refresh, rebase, and retry visibly.

## Reproduction Assessment

Yes. Two authenticated Control UI tabs can start from the same empty custom-group snapshot, concurrently add different names, and observe the later full replacement leave only one persisted group.

## Solution Assessment

The issue's Gateway-boundary direction is correct, but the exact best API is not yet settled; an atomic semantic mutation is preferable to a client-only queue because it closes cross-client races at the authoritative store.

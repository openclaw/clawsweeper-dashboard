## Summary

Keep open. The report describes a direct user-request message being silently lost, and the documented `NO_REPLY` contract says that silent suppression is for true background/no-delivery turns rather than ordinary actionable requests. Current evidence does not establish that `main` already preserves an earlier completed assistant response when the terminal projection is bare `NO_REPLY`.

**Likely related people:** `dom521` can validate the reported current-release sequence; `rbutera` is a lower-confidence routing candidate from related embedded-runner/reply-pipeline investigation.

## What This Changes

Prevent a direct user-request turn from discarding an earlier completed assistant response when the terminal output is only `NO_REPLY`.

## System Context

Inbound messages enter the agent-run and reply-projection pipeline, which converts a completed turn into channel payloads. The silent-reply policy suppresses true background output, but a direct user-request turn should not lose a completed user-facing answer during that final projection.

## Architecture Diagram

flowchart LR
  A[Direct user request] --> B[Agent turn]
  B --> C[Completed assistant drafts]
  B --> D[Terminal result]
  C --> E[Reply projection]
  D --> E
  E --> F{Bare silent token?}
  F -->|Background turn| G[Suppress delivery]
  F -->|Direct user request| H[Deliver eligible completed answer]
  H --> I[Channel response]

## Best Possible Solution

At terminal reply projection, retain the last eligible completed non-silent assistant payload for the same direct `user_request` turn and deliver it only when the terminal result is bare `NO_REPLY` and nothing has already been delivered; keep true background silence unchanged.

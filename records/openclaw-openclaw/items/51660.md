## Summary

Keep open: current main and v2026.6.11 still lack a configurable permission policy for agent-created user-facing files, and the requested fix needs maintainer product/security direction because it changes filesystem access semantics across tool write paths.

## What This Changes

The issue requests configurable umask or explicit file/directory modes for user-facing files created by agent tools in shared Docker/NAS deployments.

## Best Possible Solution

Define a scoped opt-in user-output permission policy, keep private OpenClaw state/config/credential/session paths restrictive, and cover host Write/Edit, apply_patch, sandbox bridge, exec-created output boundaries, docs, and regression proof together.

Rationale: The request adds config surface and changes security-sensitive filesystem semantics across several tool write paths, so automation should not choose the permanent permission boundary.

Options:

- **Approve scoped output policy (recommended):** Add an opt-in policy for user-facing outputs while explicitly excluding private OpenClaw state, config, credentials, auth, and session files.
- **Use fixed per-path defaults:** Adjust only selected write paths such as managed media or sandbox-created files without adding a general permission config knob.
- **Document external management:** Keep OpenClaw defaults unchanged and document OS/container ACL, user, group, or umask setup as the supported workaround.

## Reproduction Assessment

Yes, at source level for the missing capability: current schema only supports tools.fs.workspaceOnly, and the central host, apply_patch, and sandbox write paths do not accept or apply a configurable file mode. I did not run a live Docker/NAS repro in this read-only review.

## Solution Assessment

Unclear as a final implementation: a configurable policy is plausible, but maintainers need to choose the permission model and exact user-output boundary before a safe fix can land.

## Summary

Keep open: current main and v2026.6.11 still lack an operator-controlled permission policy for agent-created user-facing files, and the remaining work is a security-sensitive product/config decision rather than conservative cleanup.

## What This Changes

Add an operator-controlled umask or file-mode policy for agent-created user-facing files so Docker/NAS shared-host deployments can choose group-writable outputs without changing sensitive internal file modes.

## Best Possible Solution

Land a maintainer-approved tools.fs permission policy that defaults secure, applies only to user-facing workspace/tool outputs, documents exec limitations, and keeps internal config, credentials, media trust boundaries, sessions, and state on their existing private-mode paths.

## Reproduction Assessment

Yes for the current limitation: source inspection shows current main has no tools.fs permission key and the write/edit paths do not take an operator-selected mode. This is a feature/config request rather than a broken existing contract with a failing runtime reproduction.

## Solution Assessment

Unclear as proposed: a raw global tools umask could overreach into sensitive surfaces. The safer solution is a narrow user-facing-output policy with explicit exclusions, docs, and tests for write/edit/sandbox/exec behavior.

## Risks / Open Questions

- A broad umask or mode knob could accidentally loosen config, credential, session, or state files unless the product boundary is explicitly limited to user-facing outputs.
- Exec-created files may need a different implementation shape than write/edit tool files because child processes inherit process umask rather than OpenClaw's fs helper options.
- Cross-platform behavior needs maintainer direction because POSIX modes, Docker bind mounts, NAS conventions, default ACLs, and Windows ACLs do not share one simple permission model.

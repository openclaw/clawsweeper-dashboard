## Summary

Keep open. Current main and v2026.6.11 still lack a caller-readable progress/event surface for long-running peer `sessions_send` runs; only the delivery-timeout reporting has been partially improved, while streaming/subscription API design remains unresolved.

## What This Changes

Request adds inter-session progress visibility for `sessions_send`, likely via `sessions_subscribe`, `agent.events`, or a maintainer-approved progress option.

## Best Possible Solution

Add an additive, permission-checked run-progress observation contract with bounded replay and redaction, then expose it through `sessions_subscribe` or a maintainer-approved `sessions_send` progress option.

## Reproduction Assessment

Yes, at source level: current main lacks `sessions_subscribe`, `agent.events`, or another caller-readable buffered run-event API for a `sessions_send` caller; no live Telegram/ACP scenario was run in this read-only review.

## Solution Assessment

Unclear final API shape: a separate `sessions_subscribe` tool is plausible, but maintainers still need to decide event API, authorization, redaction, buffering, retention, replay, and channel delivery semantics.

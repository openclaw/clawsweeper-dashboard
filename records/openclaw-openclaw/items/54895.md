## Label Justifications

- `P2`: This is a normal-priority feature gap in a stable session/gateway surface: long-running peer runs remain usable but lack real-time progress visibility.
- `impact:session-state`: The request is about preserving and exposing run/session progress state across peer sessions rather than only a final announce.
- `impact:security`: Any cross-session progress stream would expose potentially sensitive tool, command, assistant, and artifact data unless explicitly authorized and redacted.

- `maturity:stable`: The affected Gateway runtime and Gateway RPC APIs/Events category are scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open. Current main still lacks a caller-readable progress/event surface for long-running peer `sessions_send` runs; the timeout result is partly improved to `accepted` for nonterminal waits, but subscription/streaming semantics remain unresolved and security-sensitive.

## What This Changes

Request an inter-session progress/event stream for long-running `sessions_send` runs, likely through `sessions_subscribe`, `agent.events`, or an approved `sessions_send` progress option.

## Best Possible Solution

Design an additive, permission-checked run-progress observation contract with bounded buffering/replay, redaction, and channel delivery rules, then expose it through a maintainer-approved session tool/RPC.

## Reproduction Assessment

Yes at source level: current main lacks `sessions_subscribe`, `agent.events`, or a caller-readable buffered event API, and `sessions_send`/A2A still waits for completion or final announce. I did not run a live Telegram/ACP scenario.

## Solution Assessment

Unclear final API shape. A separate `sessions_subscribe` or `agent.events` read API is plausible, but maintainers must choose authorization, redaction, retention, replay, and channel-routing semantics before implementation.

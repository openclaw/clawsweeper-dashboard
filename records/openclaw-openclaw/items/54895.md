## Summary

Keep open. Current main partially improved the misleading wait-timeout result by returning `accepted` for nonterminal waits, but it still lacks a caller-readable progress/event surface for long-running peer `sessions_send` runs, and the remaining work is security-sensitive API design rather than conservative cleanup.

## What This Changes

The issue requests inter-session progress streaming or subscription support for long-running `sessions_send` runs, especially ACP/Codex sessions.

## Best Possible Solution

Design an additive, permission-checked run-progress observation contract with bounded replay/redaction, then expose it through `sessions_subscribe` or a maintainer-approved `sessions_send` progress option.

## Reproduction Assessment

Yes at source level: current main has no `sessions_subscribe`, `agent.events`, or other caller-readable buffered run-event API for a `sessions_send` caller. I did not run a live Telegram/ACP scenario in this read-only review.

## Solution Assessment

Unclear final API shape: a separate `sessions_subscribe` tool is plausible, but maintainers still need to choose event API, authorization, redaction, buffering, retention, replay, and channel delivery semantics.

## Summary

Keep open. Current main and the latest release still lack caller-visible progress streaming, `sessions_subscribe`, `agent.events`, or another buffered run-event read API for long-running peer `sessions_send` runs; related open items only cover adjacent process, node-host, timeout, or handoff slices.

## What This Changes

The issue requests caller-visible progress streaming or subscription support for long-running `sessions_send` peer-session runs.

## Best Possible Solution

Define an additive, permission-checked run-progress observation contract with bounded replay and redaction, then expose it through `sessions_subscribe` or a maintainer-approved `sessions_send` progress option.

- **Add Permission-Checked Subscription Contract (recommended):** Create a bounded run-event observation API and tool that derives observer rights from session visibility/A2A policy and sanitizes event payloads before replay or delivery.
- **Land Only Timeout/Ack Slices:** Keep progress streaming out of scope while reviewing separate timeout-compensation or handoff-acknowledgement PRs on their own narrower contracts.
- **Defer Core Progress API:** Document the current fire-and-forget, wait, history, and final-announce behavior while leaving real-time inter-session progress unsupported for now.

Yes, at source level: current main lacks `sessions_subscribe`, `agent.events`, or another caller-readable buffered run-event API for a `sessions_send` caller. I did not run a live Telegram/ACP scenario in this read-only review.

## Solution Assessment

Unclear final API shape: `sessions_subscribe` over a bounded `agent.events` read API is plausible, but existing ACP `streamTo="parent"` only covers spawn-time ACP streaming and maintainers still need to define authorization, redaction, retention, replay, and channel delivery semantics.

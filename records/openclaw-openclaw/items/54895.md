## Summary

Keep open. Current main still lacks caller-visible progress streaming for long-running `sessions_send` runs: the tool can return `accepted` after nonterminal wait expiry, but there is no `sessions_subscribe`, `agent.events`, or equivalent buffered run-event read API, and the remaining authorization/redaction/API shape needs maintainer design.

## What This Changes

Requests an inter-session run-progress observation surface for long-running `sessions_send` calls, such as `sessions_subscribe` or a progress-stream option.

## Best Possible Solution

Define an additive, permission-checked and redacted run-progress observation contract with bounded replay, then expose it through `sessions_subscribe` or a maintainer-approved `sessions_send` progress option.

## Reproduction Assessment

Yes, at source level: current main lacks `sessions_subscribe`, `agent.events`, or another caller-readable buffered run-event API for a `sessions_send` caller. I did not run a live Telegram/ACP scenario in this read-only review.

## Solution Assessment

Unclear final API shape. A separate `sessions_subscribe` tool is plausible, but maintainers still need to decide event authorization, redaction, buffering, retention, replay, and channel delivery semantics.

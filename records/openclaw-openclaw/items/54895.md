## Summary

Keep open: current main and v2026.6.11 still lack a caller-readable run-event/progress contract for peer sessions_send runs, and the remaining work is a product/security API decision rather than stale or duplicate cleanup.

## What This Changes

Request a core inter-session progress stream or subscription surface so sessions_send callers can observe long-running target session runs before the final announce.

## Best Possible Solution

Define an additive permission-checked run-progress observation contract with bounded replay and redaction, then expose it through sessions_subscribe or a maintainer-approved sessions_send progress option.

## Maintainer Decision

Required: true

Question: Should OpenClaw add a caller-visible run-progress observation surface for peer sessions_send runs, and should the permanent API be sessions_subscribe/agent.events or a sessions_send progress option?

Rationale: The missing capability is real, but API shape, authorization, redaction, replay retention, and channel delivery semantics are product/security choices that source inspection cannot safely decide.

Likely owner: steipete

Owner reason: The strongest history signal is repeated work on sessions_send, A2A behavior, ACP/session handling, and run-wait helpers that this API would touch.

Owner confidence: high

Options:

- **Add sessions_subscribe plus agent.events (recommended):** Create a separate read-only progress observation path with explicit permission checks, bounded per-run replay, event filters, and focused tests for session isolation.
- **Add an opt-in sessions_send progress mode:** Keep a single tool surface but require a clear request/response contract for progress chunks and compatibility with ordinary sessions_send callers.
- **Defer to structured process events:** Fold this into the broader process-event design in #52826, accepting that sessions_send progress remains unavailable until that architecture lands.

## Reproduction Assessment

Yes, source-reproducible: current main only offers sessions_send fire-and-forget or wait/final-announce behavior and has no caller-readable buffered run-event API.

## Solution Assessment

Unclear final API shape: sessions_subscribe plus agent.events is plausible, but maintainers still need to choose authorization, redaction, replay retention, and channel delivery semantics.

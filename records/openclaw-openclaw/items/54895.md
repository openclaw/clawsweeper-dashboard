## Summary

Keep open. Current main and the latest release address only part of the delivery-status problem by treating ordinary active-run wait expiry as accepted, but they still lack caller-visible progress streaming, `sessions_subscribe`, `agent.events`, or another buffered run-event read API for long-running inter-session `sessions_send` runs; the remaining API and security shape needs maintainer design.

## What This Changes

The issue requests caller-visible progress streaming or subscription support for long-running inter-session `sessions_send` runs.

## Best Possible Solution

Design an additive, permission-checked run-progress observation contract with bounded replay, ordering, retention, and redaction, then expose it through a maintainer-approved `sessions_subscribe` tool or explicit `sessions_send` progress option with focused session/gateway/channel tests.

## Reproduction Assessment

Yes, at source level: current main lacks `sessions_subscribe`, `agent.events`, a `sessions_send` progress option, or another caller-readable buffered run-event API. I did not run a live Telegram/ACP scenario in this read-only review.

## Solution Assessment

Unclear final API shape. A separate `sessions_subscribe` tool is plausible, but maintainers still need to decide authorization, redaction, buffering, retention, replay, and channel delivery semantics before this is the best implementation path.

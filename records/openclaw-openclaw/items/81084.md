## Summary

Keep open: current main and the latest release still hard-code Microsoft Teams channel-thread replies onto thread-suffixed sessions, and the latest human follow-up frames this as the canonical remaining Teams session-policy decision rather than stale fallout from the earlier thread-isolation fixes.

## What This Changes

The issue requests an explicit Microsoft Teams channel session-routing policy so selected channel-bound agents can keep canonical channel memory instead of always forking replies into per-thread sessions.

## Best Possible Solution

Preserve per-thread Teams isolation as the default, then add a Teams-owned explicit channel-vs-thread session policy with focused default/opt-out tests and docs for the memory-boundary tradeoff.

## Reproduction Assessment

Yes, at source level: current main always sends Teams channel thread ids into `resolveMSTeamsRouteSessionKey`, which appends a thread suffix when a thread id exists. I did not run a live Teams room reproduction in this read-only review.

## Solution Assessment

Yes to an explicit opt-in Teams-owned policy that keeps per-thread routing as the default; no to the local hotfix as a final solution because it would globally undo thread isolation. The exact config scope still needs maintainer product approval.

## Summary

Keep open: current main and v2026.6.11 still route Microsoft Teams channel-thread replies onto thread-suffixed sessions and expose no supported channel-memory opt-out; the latest human follow-up also confirms this is the canonical remaining policy/config decision.

## What This Changes

The issue requests an explicit Microsoft Teams channel session policy so channel-bound agents can opt out from per-thread sessions and retain channel-level memory.

## Best Possible Solution

Maintain per-thread isolation as the default, then add a Teams-owned explicit channel-vs-thread session policy with maintainer-approved scope, regression tests, and docs for the session-state tradeoff.

## Reproduction Assessment

Yes, at source level: current Teams channel replies pass the extracted `conversationMessageId` or `replyToId` into a helper that appends a `:thread:` suffix. I did not run a live Teams room reproduction in this read-only review.

## Solution Assessment

Yes to an opt-in Teams-owned policy with per-thread behavior preserved as the default; no to the local hotfix as a final solution because it would globally undo isolation. Maintainers still need to choose the exact schema scope before implementation.

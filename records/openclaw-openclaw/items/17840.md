## Summary

Keep open: current main and v2026.6.11 still treat accepted reactions as passive queued system events, while the requested opt-in wake/config contract remains unmerged product/API work with overlapping open PR candidates.

## What This Changes

Request an opt-in policy that lets accepted channel reaction events wake an agent turn.

## Best Possible Solution

Land one maintainer-approved, queue-by-default reaction wake policy across the relevant bundled plugins, preserving existing filters and documenting config, defaults, upgrade behavior, and focused tests.

## Reproduction Assessment

Yes at source level: current Discord, Telegram, and Slack reaction handlers enqueue accepted reaction system events without calling requestHeartbeat, and docs describe passive system-event delivery. I did not run a live channel repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public contract. A shared queue-by-default notificationWake.reactions policy looks safer than unconditional wake or per-channel drift, but it remains unmerged and overlaps with a narrower Discord candidate.

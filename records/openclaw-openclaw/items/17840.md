## Summary

Keep open: current main and v2026.6.11 still expose accepted reactions as passive queued system events, while the open implementation PRs are unmerged candidates and the remaining wake/config contract needs maintainer product/API direction.

## What This Changes

Request an opt-in reaction wake contract so accepted reaction notifications can trigger agent turns for low-friction channel workflows.

## Best Possible Solution

Keep this as the canonical cross-channel request, have maintainers choose a default-safe opt-in wake contract, then land it through shared policy/config/docs/tests after existing channel filters pass.

## Reproduction Assessment

Yes, at source level. Current main shows accepted Discord, Telegram, and Slack reaction paths enqueue system events without any documented wake contract or `requestHeartbeat` call; I did not run a live channel repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public API. A shared default-queue policy with explicit wake/off modes after existing authorization and reaction-notification filters is safer than unconditional wake or a one-channel-only config surface.

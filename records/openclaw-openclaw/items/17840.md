## Summary

Keep open: current main and the latest release still expose reaction notifications as passive queued system events, with no merged opt-in wake/turn policy; the open shared and Discord-specific PRs are candidate implementations, not completed fixes.

## What This Changes

The issue requests an opt-in mechanism so accepted reaction events can wake the agent for reaction-driven workflows such as quick confirmations and emoji-choice polling.

## Best Possible Solution

Keep this as the canonical cross-channel product/API request, land one maintainer-approved opt-in wake contract that preserves queued-only behavior by default, then close or split narrower channel follow-ups after the chosen implementation merges.

## Reproduction Assessment

Yes, at source level. Current main shows accepted Discord, Telegram, Signal, Matrix, and iMessage reactions enqueue system events, while targeted search found no merged opt-in reaction wake policy.

## Solution Assessment

Unclear until maintainers choose the product/API contract. A default-safe shared queue/wake/off policy after existing channel gates looks safer than unconditional wake or a drifting one-channel config, but the direction needs maintainer approval.

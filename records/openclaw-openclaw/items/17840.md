## Summary

Keep open: current main and v2026.6.11 still expose accepted reactions as passive queued system events, while the opt-in wake/config contract remains unmerged product/API work. The open shared-policy and Discord-specific PRs are implementation candidates, not a reason to close this issue before maintainers choose and land the contract.

## What This Changes

Request an opt-in config or per-message mechanism so accepted channel reaction events can trigger agent turns instead of only queuing passive system events.

## Best Possible Solution

Land a maintainer-approved opt-in notification-wake contract that keeps queued-only behavior as the default, makes wake/off explicit, runs only after existing reaction filters pass, and updates schemas, docs, generated metadata, and focused channel tests.

## Reproduction Assessment

Yes, at source level. Current Discord, Telegram, and Slack reaction handlers enqueue routed system events, and targeted current-main search found no reaction wake/config surface; I did not run a live channel repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public contract. A default-safe shared notification-wake policy after existing reaction filters is the narrowest maintainable direction I found, while unconditional per-channel wake would be too risky.

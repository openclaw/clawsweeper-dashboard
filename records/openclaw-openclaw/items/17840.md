## Label Justifications

- `P2`: This is a normal-priority feature/product gap with real operator workflow friction but no evidence of a blocked first-run or core outage.
- `impact:message-loss`: Reaction-only inputs can be accepted and queued as system events without promptly reaching an agent turn, so the user's intended channel signal is effectively missed until another wake occurs.
- `maturity:stable`: The issue affects Discord reaction behavior, and the Discord channel is currently scored M4 Stable in qa/maturity-scores.yaml.

## Summary

Keep open: current main still treats accepted reaction notifications as passive queued system events, and the requested opt-in wake/turn contract remains a cross-channel product/API decision with overlapping but unmerged PR candidates.

## What This Changes

The issue requests an opt-in mechanism for accepted reaction events to wake the routed agent turn instead of waiting for a later text message or heartbeat.

## Best Possible Solution

Adopt one default-safe notification-wake contract, likely queue by default with explicit wake/off, then wire accepted reactions after existing channel access filters and update schemas, docs, and focused tests across the chosen bundled plugins.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should reaction-triggered turns use one shared cross-channel notification-wake policy, land as channel-specific opt-in settings first, or remain passive system events for now?

Rationale: The issue asks for new public wake/config semantics across multiple channels, and current open PRs demonstrate competing scope choices that automation should not pick unilaterally.

Likely owner: steipete

Owner reason: He authored the open shared policy PR and has recent history on both heartbeat/runtime and channel system-event surfaces.

Owner confidence: high

Options:

- **Shared opt-in wake policy (recommended):** Define one queue/wake/off-style contract and apply it consistently after existing reaction notification and access filters; this best matches the cross-channel request and avoids drift.
- **Channel-specific first:** Land a focused Discord or Telegram path first and keep this broader issue open until the remaining channels and naming are settled.
- **Defer core wake semantics:** Keep reactions as passive system events and route richer behavior to hooks/plugins until maintainers are ready to own a core config surface.

## Reproduction Assessment

Yes at source level: current main shows accepted reactions in Discord, Telegram, Slack, and Matrix enqueue system events, while targeted search found no opt-in reaction wake/turn contract. I did not run a live channel repro in this read-only cleanup review.

## Solution Assessment

Unclear until maintainers choose the public contract. A shared, default-safe notification-wake policy is the strongest fit for this broad issue; a one-channel fix should either be explicitly scoped or leave this issue open.

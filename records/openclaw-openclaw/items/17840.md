## Summary

Keep open: current main still treats accepted reaction notifications as passive queued system events, and the open implementation PRs are candidates that need maintainer product/API direction before this broader cross-channel request can close.

## What This Changes

Request an opt-in mechanism for reaction events to wake the agent, either per message or through channel/config-scoped reaction-trigger policy.

## Best Possible Solution

Land one maintainer-approved opt-in notification-wake contract that preserves passive queue behavior by default, wakes only after accepted reaction enqueue succeeds, documents precedence, and proves the chosen Discord/Telegram paths before expanding to other reaction-capable channels.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 enqueue accepted Discord and Telegram reactions as system events, and targeted search found no opt-in reaction wake contract or heartbeat request in those reaction paths.

## Solution Assessment

Unclear until maintainers choose the public contract. A default-safe shared queue/wake/off policy after existing channel gates looks more maintainable than unconditional wake or one-off per-channel semantics, but that direction still needs approval and proof.

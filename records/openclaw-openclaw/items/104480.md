## Summary

Keep open. Current main still routes Telegram CLI sends through a 10-second Gateway message-action deadline while Telegram video uploads may legitimately run for 30 seconds or longer, so the shipped false-negative and duplicate-retry failure remains source-reproducible.

## What This Changes

Prevent large Telegram media sends from returning a 10-second Gateway timeout failure when the upload later succeeds.

## Best Possible Solution

Give long-running send actions an idempotent accepted-to-terminal delivery contract with reconciliation, while keeping short message control actions on bounded deadlines and adding focused Telegram large-media regression proof.

Rationale: A longer deadline is a bounded mitigation but cannot cover configured or reconnect-driven delays; an accepted/reconciled outcome changes public CLI result semantics and requires maintainer intent.

Options:

- **Track Send Completion (recommended):** Return an idempotent accepted or unknown result with reconciliation so callers do not retry a send that remains in progress.
- **Raise Send Deadline:** Use a longer timeout only for send actions as a near-term mitigation while retaining synchronous semantics.

## Solution Assessment

No. A generic timeout flag or environment variable adds public surface and leaves ambiguous delivery semantics; the narrower maintainable solution is a send-specific acknowledgement and reconciliation contract.

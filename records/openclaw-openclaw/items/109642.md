## Summary

Keep this PR open for revision: the bounded-cache idea is appropriate, but eviction currently happens before duplicate detection, so a saturated cache can emit a supposedly one-time warning again; the PR also lacks after-fix real behavior proof.

## What This Changes

The PR adds fixed-size FIFO eviction to the process-local iMessage startup and per-chat group-allowlist warning caches.

## Best Possible Solution

Preserve the bounded sets, but check for an existing key first and evict only when inserting a novel key; cover both caches at their exact capacity boundaries and provide redacted runtime or terminal proof.

## Reproduction Assessment

Yes, at source level: fill either set to its limit with distinct keys, invoke the function with the oldest key again, and the patch deletes that key before membership testing and returns true to warn again.

## Solution Assessment

No. FIFO bounding is suitable, but duplicate detection must precede eviction so only insertion of a new key changes the cache.

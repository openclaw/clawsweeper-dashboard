## Summary

Keep open. Current main still reserves `/workspace` for sandbox containers while gateway and CLI containers use `/home/node/.openclaw/workspace`; the earlier direct-symlink PR closed unmerged, so maintainers still need to decide whether a shared runtime-container alias is an intentional supported contract.

## What This Changes

Add a `/workspace` alias in OpenClaw runtime containers that resolves to `/home/node/.openclaw/workspace`.

## Best Possible Solution

Establish one documented container workspace-path contract: either provide a collision-safe `/workspace` alias across supported runtime images with Docker and Podman smoke coverage, or keep `/workspace` sandbox-only and remove any first-party guidance that implies runtime containers provide it.

## Risks / Open Questions

- An unconditional `/workspace` alias would make the same absolute path mean the runtime workspace in gateway/CLI containers but an isolated workspace in sandbox containers, which may confuse documentation and agent assumptions.
- The implementation must confirm behavior when `/workspace` already exists in downstream images and under rootless Docker or Podman rather than assuming an image-build symlink is universally safe.
- A Dockerfile-only change may cover images shared by Compose and Podman, but maintainers should explicitly define whether custom images and non-image launch paths are part of the supported contract.

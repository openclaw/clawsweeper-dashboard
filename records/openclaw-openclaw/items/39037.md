## Summary

Keep open. Current main and the latest release still drop the CTWA click identifier, and the remaining work needs a maintainer decision about prompt, plugin-hook, and session-retention boundaries for attribution data.

## What This Changes

Expose WhatsApp Click-to-WhatsApp ad referral fields, especially `ctwa_clid`, from inbound messages to agent/plugin/session context for conversion attribution.

## Best Possible Solution

Define a WhatsApp-owned CTWA attribution payload, expose it through the approved untrusted context or plugin-hook boundary, and persist it only if maintainers approve an explicit retention and redaction contract.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should WhatsApp CTWA attribution data be exposed only as per-turn untrusted context, also passed to plugin hooks, or durably stored on session metadata for later Conversions API use?

Rationale: The extraction is technically clear, but `ctwa_clid` is an ad attribution identifier and the issue requests prompt/session visibility, so automation should not choose the privacy and retention boundary.

Likely owner: steipete

Owner reason: The remaining decision spans prompt visibility, security posture, and session metadata, all areas in recent adjacent history.

Owner confidence: medium

Options:

- **Per-turn untrusted context (recommended):** Extract the CTWA fields in the WhatsApp plugin and expose them only through the existing fenced untrusted structured-context prompt path.
- **Plugin-hook attribution payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume it without putting the identifier into every agent prompt.
- **Persist session attribution:** Store the first CTWA payload on session state only after defining retention, redaction, and access rules.

## Reproduction Assessment

Yes, source-level: a Baileys inbound message carrying `contextInfo.externalAdReply.ctwaClid` would pass through the current extractor without that field. I did not run a live Click-to-WhatsApp webhook reproduction.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right extraction owner, but broad prompt/session exposure is not automatically the safest contract. The best likely direction is a typed CTWA attribution payload with persistence only after a retention decision.

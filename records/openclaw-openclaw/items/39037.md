## What This Changes

Expose Click-to-WhatsApp ad attribution fields from WhatsApp inbound context into agent-accessible metadata or session context.

## Best Possible Solution

Define a WhatsApp-owned CTWA attribution payload, expose it through an approved untrusted prompt or plugin-hook boundary, and persist it only with an explicit retention and redaction contract.

## Maintainer Decision

Required: true

Question: Should WhatsApp CTWA attribution data be exposed only as per-turn untrusted structured context, also made available to plugin hooks, or persisted as session metadata for later Conversions API use?

Rationale: The extraction is source-clear, but ctwaClid is ad attribution data and the issue asks for prompt/session visibility, so automation should not choose the exposure and retention boundary.

Likely owner: steipete

Owner confidence: high

Options:

- **Per-turn untrusted context (recommended):** Extract CTWA fields in the WhatsApp plugin and expose them only through the existing fenced untrusted structured-context prompt path without durable persistence.
- **Plugin-hook attribution payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume it without putting the identifier into every agent prompt.
- **Persist session attribution:** Store the first CTWA payload on session state only after maintainers approve a retention, redaction, and access policy.

## Reproduction Assessment

Yes, source-level: current main extracts only title/sourceUrl/body from WhatsApp externalAdReply and does not project ctwaClid, sourceType, sourceId, or referral-style data. I did not run a live Meta CTWA webhook reproduction.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right extraction owner, but broad session metadata or preamble exposure is not automatically the safest contract. A typed CTWA payload behind the existing untrusted context or plugin-hook boundary is the safer direction, with persistence only after explicit approval.

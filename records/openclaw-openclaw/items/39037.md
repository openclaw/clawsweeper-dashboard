Options:

- **Per-turn untrusted payload (recommended):** Extract CTWA fields in the WhatsApp plugin and expose them only through the existing fenced untrusted structured-context path, without durable persistence.
- **Opted-in plugin hook payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume it without putting the identifier into every prompt.
- **Persist session attribution:** Store the first CTWA payload on session state only after maintainers define retention, redaction, export, and deletion behavior.

## Reproduction Assessment

Yes, source-level: the pinned Baileys type exposes ctwaClid and source id/type fields, but current WhatsApp extraction and forwarding only carry title, sourceUrl, and body. I did not run a live Click-to-WhatsApp webhook reproduction in this read-only review.

## Solution Assessment

Unclear as proposed: WhatsApp is the right extraction owner, but broad prompt/session exposure is not automatically the safest contract. The best direction is a typed CTWA attribution payload behind the existing untrusted context or plugin-hook boundary, with persistence only after an explicit retention decision.

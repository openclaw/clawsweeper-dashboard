## Summary

Keep open. Current main and the latest stable release still expose only partial WhatsApp external-ad-reply metadata, while the requested CTWA click identifier needs a maintainer decision on prompt, plugin-hook, and session-retention boundaries.

## What This Changes

Expose Click-to-WhatsApp `ctwa_clid` and related referral metadata from inbound WhatsApp messages to agents or session metadata for Meta Conversions API attribution.

## Best Possible Solution

Keep the WhatsApp plugin as the extraction owner, add a typed CTWA attribution payload after maintainers choose the visibility boundary, and persist it only with an explicit retention/redaction contract.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should WhatsApp CTWA attribution data be exposed only as per-turn untrusted structured context, exposed through plugin hook metadata, or persisted as session metadata for later Conversions API use?

Rationale: The extraction itself is bounded, but `ctwa_clid` is an advertising click identifier and the issue asks for prompt/session exposure, so automation should not choose the retention and visibility policy.

Likely owner: steipete

Owner reason: The decision crosses the structured prompt and sensitive metadata boundary that recent prompt-hardening work touched.

Owner confidence: medium

Options:

- **Per-turn untrusted context (recommended):** Extract CTWA fields in the WhatsApp plugin and expose them only through the existing fenced untrusted structured-context prompt path without durable persistence.
- **Plugin-hook attribution payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume it without putting the identifier into every agent prompt.
- **Persist session attribution:** Store the first CTWA payload on session state only after defining retention, redaction, and access policy.

## Reproduction Assessment

Yes, source-level: current WhatsApp extraction and forwarding paths omit CTWA/referral fields while preserving only partial external-ad-reply metadata. I did not run a live Click-to-WhatsApp webhook reproduction.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right owner for extraction, but broad prompt/session exposure is not automatically the safest contract. The best likely direction is typed attribution data behind an approved untrusted-context or plugin-hook boundary.

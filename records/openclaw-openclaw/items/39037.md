## Best Possible Solution

Define a WhatsApp-owned CTWA attribution payload and expose it through fenced untrusted context or a typed plugin hook; persist it only after maintainers define retention and redaction.

Question: Should WhatsApp CTWA attribution data be exposed only as per-turn untrusted structured context, exposed to plugin hooks for attribution plugins, or persisted as session metadata for later Conversions API use?

Rationale: The extraction is technically bounded, but the requested value is an advertising click identifier and the issue asks for prompt/session exposure, so automation should not choose the visibility and retention boundary.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Per-Turn Untrusted Context (recommended):** Extract `ctwaClid` and related ad fields in the WhatsApp plugin and expose them only through the existing fenced untrusted structured-context prompt path without durable persistence.
- **Plugin-Hook Attribution Payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume it without putting the identifier into every agent prompt.
- **Persist Session Attribution:** Store the first CTWA payload on session state only with an explicit retention, redaction, and access policy.

## Reproduction Assessment

Yes, source-level: current WhatsApp extraction reads only `externalAdReply.title`, `sourceUrl`, and `body`, while `ctwaClid`, `sourceType`, `sourceId`, `headline`, and Cloud-API-style referral data are not projected. I did not run a live Click-to-WhatsApp webhook reproduction.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right owner for extraction, but broad prompt/session exposure is not automatically the safest contract. The best likely direction is typed CTWA attribution data behind the existing untrusted context or plugin-hook boundary, with persistence only after an explicit retention decision.

## Summary

Keep open. Current main and the latest release still expose only partial WhatsApp `externalAdReply` metadata; the requested CTWA click id, field shape, prompt visibility, plugin-hook access, and session-retention boundary remain unresolved.

## What This Changes

Expose Click-to-WhatsApp ad referral fields, especially `ctwaClid`, from inbound WhatsApp messages into agent-accessible metadata or session context.

## Best Possible Solution

Define a WhatsApp-owned CTWA attribution payload, expose it through the approved untrusted prompt or plugin-hook boundary, and persist it only if maintainers approve a clear retention and redaction contract.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should WhatsApp CTWA attribution data be exposed only as per-turn untrusted structured context, exposed to opted-in plugin hooks, or persisted as session metadata for later Conversions API use?

Rationale: The extraction is bounded, but `ctwaClid` is an advertising click identifier and the issue explicitly asks for prompt/session exposure, so automation should not choose visibility, plugin access, or retention policy.

Likely owner: steipete

Owner reason: He has the strongest recent history across the prompt metadata, plugin-boundary, and session-adjacent surfaces that need the security/product decision.

Owner confidence: high

Options:

- **Per-turn untrusted context only (recommended):** Extract CTWA fields in the WhatsApp plugin and expose them only through the existing fenced untrusted structured-context prompt path, without durable persistence.
- **Plugin-hook attribution payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume it without putting the identifier into every prompt.
- **Persist session attribution:** Store the first CTWA payload on session state only after maintainers define retention, redaction, export, and deletion behavior.

## Reproduction Assessment

Yes, source-level: the pinned Baileys type exposes `ctwaClid`, but current WhatsApp extraction and forwarding only carry `title`, `sourceUrl`, and `body`. I did not run a live Click-to-WhatsApp webhook reproduction in this read-only review.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right owner for extraction, but broad prompt/session exposure is not automatically the safest contract. The best likely direction is typed CTWA attribution data behind the existing untrusted context or plugin-hook boundary, with persistence only after an explicit retention decision.

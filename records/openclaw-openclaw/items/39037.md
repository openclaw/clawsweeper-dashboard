## Summary

Keep open. Current main only carries partial WhatsApp `externalAdReply` context and still does not expose CTWA click identifiers or define their prompt, plugin-hook, or session-retention boundary.

## What This Changes

Expose Click-to-WhatsApp attribution metadata from inbound WhatsApp messages so agents or integrations can use `ctwa_clid` for Meta Conversions API attribution.

## Best Possible Solution

Define a WhatsApp-owned CTWA attribution payload, expose it through an approved untrusted-context or plugin-hook boundary, and persist it only if maintainers set explicit retention and redaction rules.

Rationale: The extraction is bounded, but the requested value is an advertising click identifier and the issue asks for agent/session exposure, so automation should not choose the visibility and retention boundary.

Options:

- **Per-Turn Untrusted Context (recommended):** Extract CTWA fields in the WhatsApp plugin and expose them only through the existing fenced untrusted structured-context path without durable persistence.
- **Plugin-Hook Attribution Payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume it without putting the identifier in every prompt.
- **Persist Session Attribution:** Store the first CTWA payload on session state only after maintainers define retention, redaction, and access rules.

## Reproduction Assessment

Yes, source-level: current main extracts only partial `externalAdReply` data and does not project CTWA click/referral fields even though the pinned Baileys proto exposes them. I did not establish a live Click-to-WhatsApp webhook reproduction.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right extraction owner, but broad prompt/session exposure is not automatically the safest contract. The best likely direction is typed CTWA attribution behind the existing untrusted-context or plugin-hook boundary, with persistence only after an explicit retention decision.

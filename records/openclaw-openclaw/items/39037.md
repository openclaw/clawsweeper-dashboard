## Summary

Keep open. Current main and v2026.6.11 still expose only partial WhatsApp `externalAdReply` context and have no `ctwaClid`, referral, plugin-hook attribution, or session-retention path; the remaining blocker is the product/security boundary for ad click identifiers.

## What This Changes

Request to extract Click-to-WhatsApp referral/click-id metadata from WhatsApp inbound messages and expose it through session or agent-facing metadata.

## Best Possible Solution

Define a WhatsApp-owned CTWA attribution payload, expose it first through an approved plugin-hook boundary for Conversions API integrations, and add prompt visibility or session persistence only if maintainers explicitly approve retention and redaction rules.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should WhatsApp CTWA attribution data be exposed through plugin-hook metadata only, untrusted per-turn prompt context, or persisted session metadata?

Rationale: The extraction itself is bounded, but the requested click id is ad-attribution data and the issue asks for model/session visibility, so automation should not choose the exposure and retention boundary.

Likely owner: steipete

Owner reason: The strongest current history signal is ownership of the session metadata path and adjacent product/security boundary work.

Owner confidence: high

Options:

- **Plugin-Hook Attribution Payload (recommended):** Expose CTWA fields to opted-in WhatsApp/plugin hook metadata so a Conversions API plugin can consume them without putting click ids in the model prompt by default.
- **Untrusted Prompt Context:** Expose selected CTWA fields as untrusted structured context and accept that the model can see them during that turn.
- **Persist Session Attribution:** Store first-touch CTWA attribution on session state after defining retention, redaction, and access rules.

## Reproduction Assessment

Yes, source-level: a Baileys inbound message with `contextInfo.externalAdReply.ctwaClid` reaches a WhatsApp extractor that keeps only `title`, `sourceUrl`, and `body`, and downstream hook/session metadata has no CTWA field. I did not run a live Click-to-WhatsApp webhook.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right extraction owner, but broad session metadata or preamble exposure is not automatically the safest contract. A typed plugin-hook attribution payload looks like the safest default, with prompt visibility and persistence only after maintainer approval.

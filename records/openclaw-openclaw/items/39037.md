## Summary

Keep open. Current main and the latest release still expose only partial WhatsApp `externalAdReply` metadata; the requested CTWA click identifier, prompt/plugin visibility, and session retention boundary remain unresolved.

## What This Changes

Expose WhatsApp Click-to-WhatsApp ad attribution fields such as `ctwaClid` or referral data to agents, plugin hooks, or session metadata.

## Best Possible Solution

Define a WhatsApp-owned CTWA attribution payload, expose it through an approved untrusted prompt or plugin-hook boundary, and persist it only if maintainers approve a clear retention and redaction contract.

Question: Should WhatsApp CTWA attribution data be exposed only as per-turn untrusted structured context, also included in plugin hook metadata, or persisted as session metadata for later Conversions API use?

Rationale: The extraction is bounded, but the requested click identifier is ad attribution data and the issue explicitly asks for prompt/session exposure, so automation should not choose the visibility and retention boundary.

Owner confidence: high

Options:

- **Per-turn untrusted context only (recommended):** Extract `ctwaClid` and related ad fields in the WhatsApp plugin and expose them only through the existing fenced untrusted structured-context prompt path without durable persistence.
- **Plugin-hook attribution payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume it without putting the identifier into every agent prompt.
- **Persist session attribution:** Store the first CTWA payload on session state only after defining explicit retention, redaction, and access rules.

## Reproduction Assessment

Yes, source-level: current WhatsApp extraction reads only `externalAdReply.title`, `sourceUrl`, and `body`, while `ctwaClid`, `sourceType`, `sourceId`, and referral-style data are not projected. I did not run a live Click-to-WhatsApp webhook reproduction.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right owner for extraction, but broad prompt/session exposure is not automatically the safest contract. The better direction is typed CTWA attribution behind an approved untrusted context or plugin-hook boundary, with persistence only after an explicit retention decision.

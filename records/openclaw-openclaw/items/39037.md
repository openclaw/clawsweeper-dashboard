## Summary

Keep open. Current main and the latest release only expose partial WhatsApp external-ad metadata, while the requested CTWA click identifier and its prompt/plugin/session retention boundary remain unresolved.

## What This Changes

Expose WhatsApp Click-to-WhatsApp ad referral fields, especially `ctwa_clid`, through session metadata or another agent-visible attribution surface.

## Best Possible Solution

Define a WhatsApp-owned CTWA attribution payload, expose it through the approved untrusted prompt or plugin-hook boundary, and persist it only if maintainers approve a clear retention and redaction contract.

Rationale: The extraction is bounded, but the requested value is an advertising click identifier and the issue explicitly asks for agent/session exposure, so automation should not choose the visibility and retention boundary.

Owner confidence: high

Options:

- **Per-turn untrusted context only (recommended):** Extract `ctwaClid` and related non-secret ad fields in the WhatsApp plugin and expose them only through the existing fenced untrusted structured-context prompt path without durable persistence.
- **Plugin-hook attribution payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume the click ID without putting it into every agent prompt.
- **Persist session attribution:** Store the first CTWA payload on session state only after maintainers define explicit retention, redaction, and access rules.

## Reproduction Assessment

Yes, source-level: current WhatsApp extraction and forwarding read only partial external-ad metadata and omit CTWA/referral identifiers. I did not run a live Click-to-WhatsApp webhook reproduction.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right owner for extraction, but broad prompt/session exposure is not automatically the safest contract. A typed CTWA attribution payload behind the existing untrusted context or plugin-hook boundary is the safer likely direction.

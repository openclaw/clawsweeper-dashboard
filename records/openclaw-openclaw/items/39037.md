## Summary

Keep open. Current main and the latest release still expose only partial WhatsApp external-ad-reply context, while CTWA click/referral exposure remains a product and security-boundary decision.

## What This Changes

The issue requests extracting WhatsApp Click-to-WhatsApp ad referral fields, especially `ctwaClid`, and exposing them through agent/session metadata for conversion attribution.

## Best Possible Solution

Define a WhatsApp-owned CTWA attribution payload, expose it through an approved untrusted-context or plugin-hook boundary, and persist it only if maintainers set explicit retention and redaction rules.

Question: Should WhatsApp CTWA attribution data be exposed only as per-turn untrusted context, through plugin-hook metadata, or persisted on session metadata for later Conversions API use?

Rationale: The extraction is bounded, but the requested value is an advertising click identifier and the issue asks for agent/session exposure, so automation should not choose the visibility and retention boundary.

Owner confidence: medium

Options:

- **Per-turn untrusted context (recommended):** Extract CTWA fields in the WhatsApp plugin and expose them only through the existing untrusted structured-context prompt path without durable persistence.
- **Plugin-hook attribution payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume it without putting the identifier in every prompt.
- **Persist session attribution:** Store the first CTWA payload on session state only after maintainers define retention, redaction, and access rules.

## Reproduction Assessment

Yes, source-level: current main extracts only partial `externalAdReply` data and does not project CTWA click/referral fields even though the pinned Baileys proto exposes them. I did not establish a live Click-to-WhatsApp webhook reproduction.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right extraction owner, but broad prompt/session exposure is not automatically the safest contract. The likely best direction is typed CTWA attribution behind the existing untrusted-context or plugin-hook boundary, with persistence only after an explicit retention decision.

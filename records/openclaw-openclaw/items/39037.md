## Summary

Keep open. Current main and the latest release still expose only partial WhatsApp `externalAdReply` data; the requested CTWA click identifier/referral payload and its prompt, plugin, or session-retention boundary remain unresolved.

## What This Changes

Request to expose WhatsApp CTWA ad referral and click identifiers from inbound messages to agent or session metadata for attribution workflows.

## Best Possible Solution

Define a WhatsApp-owned CTWA attribution payload, expose it through an approved untrusted context or plugin-hook boundary, and persist it only with an explicit retention/redaction policy.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should WhatsApp CTWA attribution data be exposed only as per-turn untrusted structured context, through plugin hook metadata, or persisted as session metadata for later Conversions API use?

Rationale: The extraction is bounded, but the requested value is an advertising click identifier and the issue explicitly asks for agent/session exposure, so automation should not choose the visibility and retention boundary.

Likely owner: steipete

Owner reason: The unresolved choice is the prompt/plugin/session visibility and retention boundary, and history points to adjacent structured-context and session-metadata work.

Owner confidence: medium

Options:

- **Per-turn untrusted context (recommended):** Extract CTWA fields in the WhatsApp plugin and expose them only through the existing untrusted structured-context prompt path without durable persistence.
- **Plugin-hook attribution payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume it without putting the identifier into every prompt.
- **Persist session attribution:** Store the first CTWA payload on session state only after maintainers define retention, redaction, and access rules.

## Reproduction Assessment

Yes, source-level: current WhatsApp extraction reads only `title`, `sourceUrl`, and `body` from `externalAdReply` and does not project CTWA click fields or a referral object. I did not run a live Click-to-WhatsApp webhook reproduction.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right owner for extraction, but broad prompt/session exposure is not automatically the safest contract. The best likely direction is typed CTWA attribution data behind the existing untrusted context or plugin-hook boundary, with persistence only after an explicit retention decision.

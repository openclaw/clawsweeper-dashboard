## Summary

Keep open. Current main and v2026.6.11 expose only partial WhatsApp `externalAdReply` context and still do not carry `ctwaClid`, source type/id, a Cloud-API-style referral payload, or a decided prompt/plugin/session retention boundary.

## What This Changes

Request to expose WhatsApp Click-to-WhatsApp `ctwa_clid` and referral metadata from inbound messages to agents, plugins, or session metadata.

## Best Possible Solution

Define a WhatsApp-owned CTWA attribution payload, expose it through an approved plugin-hook or tightly scoped untrusted-context boundary, and persist it only if maintainers set explicit retention and redaction rules.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should WhatsApp CTWA attribution data be exposed per-turn in untrusted prompt context, surfaced only to plugin hooks, or persisted on session metadata for later Conversions API reporting?

Rationale: The extraction itself is bounded, but `ctwa_clid` is a personal advertising click identifier and the issue asks for prompt/session visibility, so automation should not choose the exposure and retention boundary.

Likely owner: steipete

Owner reason: Their recent structured-context and session-metadata work is the closest match for deciding prompt visibility, plugin access, and persistence policy.

Owner confidence: high

Options:

- **Plugin-Hook Attribution Payload (recommended):** Expose CTWA fields to opted-in WhatsApp/plugin hook metadata so a Conversions API plugin can consume them without putting the click id in every model prompt.
- **Per-Turn Untrusted Context:** Expose selected CTWA/referral fields through the existing untrusted structured-context path and accept that the model can see them for that turn.
- **Persist Session Attribution:** Store the first CTWA payload on session state only after defining retention, redaction, and access rules.

## Reproduction Assessment

Yes, source-level: a Baileys inbound message with `contextInfo.externalAdReply.ctwaClid` would reach an extractor that keeps only `title`, `sourceUrl`, and `body`, and downstream hook/session metadata has no CTWA field. I did not run a live Click-to-WhatsApp webhook.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right extraction owner, but broad session metadata or preamble exposure is not automatically the safest contract. The safer likely direction is a typed plugin-hook attribution payload, with prompt visibility and persistence only after maintainer approval.

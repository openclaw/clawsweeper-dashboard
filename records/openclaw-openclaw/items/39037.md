## Best Possible Solution

Define a WhatsApp-owned CTWA attribution payload, expose it through the approved untrusted prompt or plugin-hook boundary, and persist it only if maintainers approve a clear retention and redaction contract.

Options:

- **Per-turn untrusted context only (recommended):** Extract `ctwaClid` and related ad fields in the WhatsApp plugin and expose them only through the existing fenced untrusted structured-context prompt path without durable persistence.
- **Plugin-hook attribution payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume it without putting the identifier into every agent prompt.
- **Persist session attribution:** Store the first CTWA payload on session state with an explicit retention and redaction policy before implementation.

## Reproduction Assessment

Yes, source-level: current WhatsApp extraction reads only `externalAdReply.title`, `sourceUrl`, and `body`, while `ctwaClid`, `sourceType`, `sourceId`, `headline`, and Cloud-API-style referral data are not projected. I did not run a live Click-to-WhatsApp webhook reproduction.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right owner for extraction, but broad prompt/session exposure is not automatically the safest contract. The best likely direction is typed CTWA attribution data behind the existing untrusted context or plugin-hook boundary, with persistence only after an explicit retention decision.

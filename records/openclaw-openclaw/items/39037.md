Keep open. Current main and v2026.6.11 still expose only partial WhatsApp `externalAdReply` data; the requested CTWA click identifier/referral payload and its prompt, plugin-hook, or session-retention boundary remain unresolved.

## What This Changes

Expose WhatsApp Click-to-WhatsApp ad referral fields, especially `ctwa_clid`, through agent-visible session or metadata context.

## Best Possible Solution

Define a WhatsApp-owned CTWA attribution payload, expose it through an approved untrusted context or plugin-hook boundary, and persist it only with explicit retention and redaction rules.

Rationale: The extraction is bounded, but the requested value is an advertising click identifier and the issue asks for agent/session exposure, so automation should not choose the visibility and retention boundary.

Options:

- **Per-turn Untrusted Context (recommended):** Extract the CTWA fields in the WhatsApp plugin and expose them only through the existing untrusted structured-context prompt path without durable persistence.
- **Plugin-Hook Attribution Payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume it without putting the identifier in every prompt.
- **Persist Session Attribution:** Store the first CTWA payload on session state only after maintainers define retention, redaction, and access rules.

## Reproduction Assessment

Yes, source-level: current main extracts only partial `externalAdReply` data and does not project CTWA click/referral fields even though the bundled Baileys proto type exposes them. I did not run a live Click-to-WhatsApp webhook reproduction.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right owner for extraction, but broad prompt/session exposure is not automatically the safest contract. The best likely direction is typed CTWA attribution behind the existing untrusted context or plugin-hook boundary, with persistence only after an explicit retention decision.

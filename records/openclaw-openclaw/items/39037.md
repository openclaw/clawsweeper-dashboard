Keep open. Current main and v2026.6.11 still expose only partial WhatsApp `externalAdReply` data; the requested CTWA click identifier/referral payload remains missing and needs a maintainer-approved security/product boundary before implementation.

## What This Changes

Request to expose WhatsApp Click-to-WhatsApp ad `ctwa_clid` and referral fields from inbound messages to agent or session metadata for conversion attribution.

## Best Possible Solution

Add a WhatsApp-owned CTWA attribution payload that maps Baileys and referral-style fields into an approved untrusted-context or plugin-hook boundary, with persistence only after explicit retention and redaction rules.

Question: Should WhatsApp CTWA attribution data be exposed only as per-turn untrusted context, through plugin-hook metadata, or persisted on session metadata for later Conversions API use?

Rationale: The extraction is bounded, but `ctwa_clid` is an advertising click identifier and the issue asks for agent/session exposure, so automation should not choose the visibility and retention boundary.

Options:

- **Per-Turn Untrusted Context (recommended):** Extract CTWA fields in the WhatsApp plugin and expose them only through the existing untrusted structured-context prompt path without durable persistence.
- **Plugin-Hook Attribution Payload:** Define a typed WhatsApp attribution payload for opted-in plugin hooks so a Conversions API plugin can consume it without putting the identifier in every prompt.
- **Persist Session Attribution:** Store the first CTWA payload on session state only after maintainers define retention, redaction, and access rules.

## Reproduction Assessment

Yes, source-level: current main extracts only partial `externalAdReply` data and does not project CTWA click/referral fields even though the bundled Baileys proto type exposes them. I did not run a live Click-to-WhatsApp webhook reproduction.

## Solution Assessment

Unclear as proposed: the WhatsApp plugin is the right owner for extraction, but broad prompt/session exposure is not automatically the safest contract. The best likely direction is typed CTWA attribution behind the existing untrusted context or plugin-hook boundary, with persistence only after an explicit retention decision.

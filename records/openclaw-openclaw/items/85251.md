## Summary

Keep open: the central failure remains a shared embedded-run reliability problem, not only a Codex app-server timeout. The discussion contains live incidents through July 11, 2026 across Codex, Claude, WhatsApp, Telegram, Slack, and webchat; newer open reports also describe distinct remaining Codex liveness gaps. Closed design and implementation work improved recovery, but it does not safely establish that every silent-turn, abort-to-release, and channel-visible recovery path is fixed.

## What This Changes

The issue requests bounded recovery for embedded agent turns that start but stop making observable progress, so the originating channel receives a clear retryable outcome instead of a multi-minute silent wedge.

## System Context

Channel messages enter a per-session lane, which starts an embedded agent runtime such as Codex and records progress for diagnostics. When progress stops, session recovery may abort the run; the recovery result must release lane state and communicate a safe outcome to the original channel without losing queued work.

## Architecture Diagram

  C --> D[Codex or other runtime events]
  D --> E[Progress and liveness tracking]
  E --> F{Progress or terminal outcome?}
  F -->|No| G[Bounded recovery]
  G --> H[Lane release and channel-visible result]
  F -->|Yes| H

## Best Possible Solution

Define one cross-runtime recovery contract: progress-aware timeout classification, safe abort-to-release cleanup, preservation or explicit disposition of queued work, and one visible retryable failure outcome on the originating channel; then prove it against a deliberately silent Codex turn and an active resumed native turn.

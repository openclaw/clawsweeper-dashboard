## Summary

Keep open. Recent field evidence reports the same user-visible silent, wedged channel turn on `2026.7.1-beta.5`, after the referenced Codex liveness work, while the discussion also establishes equivalent failures outside Codex. The remaining decision is a shared embedded-run recovery contract—bounded detection, abort cleanup, and channel-visible handling of the interrupted message—not a narrow Codex-only timeout patch.

## What This Changes

Fix channel-triggered embedded agent runs that stop making progress after starting so they recover promptly without silently stranding queued user messages.

## System Context

Incoming channel messages enter a session lane, which starts an embedded agent run through a provider runtime such as Codex app-server. Progress events drive reply delivery and liveness diagnostics; when progress stops, session recovery must clean up the run and leave the lane able to process or visibly resolve the user’s message.

## Architecture Diagram

flowchart LR
  A[Inbound channel message] --> B[Session lane]
  B --> C[Embedded agent run]
  C --> D[Codex or other runtime]
  D --> E[Progress and completion events]
  E --> F[Reply delivery]
  C --> G[Stall detection and recovery]
  G --> B

## Best Possible Solution

Define and implement one shared embedded-run lifecycle contract: detect genuinely stale progress with prepared run facts, atomically release run and reply-operation state on abort, and send or schedule one deterministic channel-visible outcome before the next queued message is processed.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When a visible channel turn is aborted for missing progress, should OpenClaw retry/resume it automatically, emit a retryable failure and release the lane, or use a bounded hybrid policy by failure class?

Rationale: The reports show that aborting alone can lose the accepted message or leave stale lane state; choosing delivery/retry semantics changes user-visible behavior and cannot be safely inferred from a timeout implementation.

Likely owner: obviyus

Owner reason: The linked reliability-design and Codex liveness work make this the strongest available routing signal for the recovery-policy decision.

Owner confidence: medium

Options:

- **Release and notify (recommended):** Abort the stale run, atomically clear its ownership state, send one retryable failure through the originating channel, and let the next inbound message start cleanly.
- **Bounded automatic retry:** Retry only classes with a demonstrably safe idempotency boundary, then fall back to a visible failure and lane release.
- **Resume-only recovery:** Preserve and resume interrupted work where the runtime supports it, accepting greater implementation and state-consistency complexity.

The safer path is shared lifecycle cleanup plus an explicit channel outcome policy, with runtime-specific liveness inputs where needed.

## Label Justifications

- `P1`: The linked failure is a real source-channel message-loss workflow where generated replies can remain private and never reach the user.
- `merge-risk: 🚨 compatibility`: The PR changes default behavior for existing `message_tool_only` setups that currently treat no message-tool call as no source reply.
- `merge-risk: 🚨 message-delivery`: The new retry and diagnostic paths can change whether, when, and what a source-channel user receives after a missed message-tool call.
- `merge-risk: 🚨 security-boundary`: The PR replays private final text into a synthetic prompt and may cause it to be published through the message tool, which is privacy-sensitive.

## Summary

Keep open: the PR targets a real silent message-loss report, but the default-on retry path changes the current `message_tool_only` privacy/delivery contract and conflicts with prior maintainer direction unless a stronger required-visible-reply signal or explicit maintainer approval is added.

## What This Changes

The PR makes substantive `message_tool_only` private finals enqueue a one-shot message-tool recovery retry by default, adds a sanitized retry-failure diagnostic, updates prompt/docs text, and adds QA/mock-provider coverage.

## Best Possible Solution

Gate recovery on a maintainer-approved required-visible-reply signal or make it an explicit opt-in; otherwise retain warning-only diagnostics for private finals.

## Reproduction Assessment

Yes. Current main has source-level reproduction through the checked-in QA scenario and warning-only code path, and the linked issue includes recent Telegram DM reports showing successful turns with no message-tool outbound.

## Solution Assessment

No, not yet. The retry shape is safer than direct auto-publication, but using the warning heuristic as the default recovery trigger is broader than prior maintainer direction; the maintainable fix needs a required-visible-reply signal or explicit opt-in/approval.

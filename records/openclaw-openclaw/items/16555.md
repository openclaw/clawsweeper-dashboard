## Summary

Keep open: current main and the latest release still lack an outbound delivery-queue TTL/expiry policy, and the remaining work needs maintainer direction on public config, default behavior, and expired-entry handling.

## What This Changes

The issue requests configurable expiry for stale outbound delivery queue entries so restart recovery does not replay old channel messages.

## Best Possible Solution

Keep this as the canonical outbound delivery expiry issue, then implement a narrow startup-recovery and reconnect-drain policy after maintainers choose the config, default, and expired-entry semantics.

Options:

- **Opt-in messages.delivery TTL (recommended):** Add optional `messages.delivery.maxAgeMs` with a failed/quarantine-style expired action, preserving the current no-TTL default while covering startup and reconnect drains.
- **Finite default TTL:** Ship a default max age to prevent stale floods without user setup, accepting a compatibility-sensitive change to existing recovery behavior.
- **Broader freshness design:** Pause the outbound-only fix and design outbound plus inbound stale-message policy together, reducing drift but delaying the known outbound repair.

## Reproduction Assessment

Yes, at source level: seed an old pending outbound entry with `retryCount: 0` and no `lastAttemptAt`, then call `recoverPendingDeliveries`; current main checks retry/backoff but not queued age. No live restart reproduction was run in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public config/default/action. The narrow maintainable path is outbound expiry in recovery and reconnect drains; bundling inbound freshness would be a broader product decision.

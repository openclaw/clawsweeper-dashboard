## Summary

Keep open: current main and the latest checked release still replay outbound pending deliveries without a queued-age expiry policy, and the remaining work needs a maintainer choice for the public config key, default behavior, and expired-entry handling.

## What This Changes

The issue requests configurable TTL/expiry for outbound delivery queue recovery so stale queued messages are not replayed after gateway restarts.

## Best Possible Solution

Keep #16555 as the canonical outbound delivery expiry issue, then implement a narrow startup-recovery and reconnect-drain policy after maintainers choose the config, default, and expired-entry semantics.

Rationale: The missing source-level policy is clear, but adding a strict config surface and changing whether old queued messages replay after upgrade requires product and compatibility intent.

Options:

- **Opt-in messages.delivery TTL (recommended):** Add optional messages.delivery.maxAgeMs with a failed or quarantine-style expired action, preserving the current no-TTL default while covering startup recovery and reconnect drains.
- **Finite Default TTL:** Ship a default max age to prevent stale floods without user setup, accepting a compatibility-sensitive change to existing recovery behavior.
- **Broader Freshness Design:** Pause the outbound-only fix and design outbound plus inbound stale-message policy together, reducing policy drift but delaying the known outbound repair.

Unclear until maintainers choose the public config/default/action; the narrow maintainable path is outbound expiry in recovery and reconnect drains, while bundling inbound freshness would be a broader product decision.

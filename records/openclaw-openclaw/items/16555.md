## Summary

Keep open: current main and the latest release still replay eligible outbound delivery queue entries without a queued-age expiry policy, and the remaining work needs maintainer agreement on the public config key, default behavior, and expired-entry handling.

## What This Changes

The issue requests configurable TTL/expiry behavior for stale outbound delivery queue messages so gateway restart recovery does not flood channels with old replies.

## Best Possible Solution

Add a narrow, backward-compatible outbound expiry policy that uses the existing SQLite-backed delivery queue metadata, preserves default no-TTL behavior unless maintainers choose otherwise, applies consistently to startup recovery and reconnect drains, logs expired counts, and covers config/schema plus recovery tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which outbound delivery expiry contract should OpenClaw expose for stale queued messages: an opt-in messages.delivery-style config that preserves current default replay behavior, a new default TTL that expires stale entries automatically, or no core TTL for now?

Rationale: The code fix is clear, but the product contract is not: default expiry can drop delayed legitimate recovery messages, while opt-in config adds a new public config surface that AGENTS.md says should have a high bar.

Likely owner: steipete

Owner reason: steipete provided the latest maintainer-facing direction on this issue and has strong recent history in the delivery queue files.

Owner confidence: high

Options:

- **Opt-in expiry config (recommended):** Add a strict, documented messages.delivery-style TTL and expire action while preserving current replay behavior by default for upgrade compatibility.
- **Default bounded expiry:** Ship a conservative default TTL and migration/docs proof, accepting that some existing delayed-recovery setups will stop replaying old queued replies.
- **Do not add core TTL now:** Keep recovery unchanged and close or defer stale-replay mitigation to operator cleanup or a broader lifecycle redesign.

## Reproduction Assessment

Yes, at source level: seed an old pending outbound delivery with retryCount 0 and no lastAttemptAt, then run recoverPendingDeliveries; current main treats it as eligible after only max-retry/backoff checks. I did not run tests because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the product contract. The best technical shape appears to be a narrow expiry policy in the existing delivery queue recovery/storage path, but the default and public config surface need maintainer direction first.

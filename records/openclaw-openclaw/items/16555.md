## Summary

Keep open: stale outbound replay remains a concrete, source-reproducible reliability problem, but the public config shape, default expiry policy, and treatment of expired persisted messages require maintainer product direction; the related implementation PRs were closed unmerged and do not own the remaining work.

## What This Changes

Requests configurable expiry handling for stale outbound delivery-queue messages before startup or reconnect replay.

## Best Possible Solution

Define one bounded outbound-only expiry contract at the delivery-queue owner boundary, preserve existing behavior by default unless maintainers intentionally choose a new default, terminalize expired entries with observable diagnostics, and apply the same policy consistently to startup recovery and reconnect draining with fresh-install and upgrade coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should outbound delivery expiry be opt-in or enabled by default, and should an expired entry be terminalized as failed, deleted, or remain pending?

Rationale: Each choice changes the reliability contract and persisted-state behavior: replaying favors at-least-once delivery, while expiration prevents stale or duplicate channel floods but can suppress legitimate delayed messages.

Likely owner: steipete

Owner reason: This person has the strongest combined current-code history and issue-level product-direction signal for the delivery recovery surface.

Owner confidence: high

Options:

- **Opt-in terminal expiry (recommended):** Add an optional maximum age and move expired entries to the existing failed/quarantine path with clear logs, preserving current replay behavior for existing configurations.
- **Default bounded expiry:** Enable a maintained default maximum age for all users and document the intentional upgrade-time change from indefinite replay to terminal expiration.
- **No TTL surface:** Keep indefinite recovery and instead pursue stronger acknowledgement or idempotency tracking so already-delivered messages are not replayed.

## Reproduction Assessment

Yes at source level: persisted entries carry enqueuedAt, and both startup recovery and reconnect draining can process old pending entries without the requested configurable expiry check; production comments provide matching restart logs. A controlled current-main live restart reproduction was not performed in this read-only review.

## Solution Assessment

Unclear until maintainers choose the delivery contract. A narrow outbound policy shared by startup and reconnect recovery is preferable to the proposed three-action menu or bundling the separate inbound freshness problem.

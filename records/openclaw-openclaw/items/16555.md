- `impact:message-loss`: The recovery behavior can replay duplicate or stale channel messages after restart, polluting outbound message delivery.

## Summary

Keep open: current main and v2026.6.11 still lack an outbound delivery-queue TTL/expiry policy, and the remaining work needs a maintainer decision on the public config key, default behavior, and expired-entry action.

## What This Changes

Add configurable TTL/expiry behavior for outbound delivery queue recovery so stale queued messages are not replayed after gateway restarts.

## Best Possible Solution

Keep this as the canonical outbound delivery expiry issue, then implement a narrow startup-recovery and reconnect-drain policy after maintainers choose the config, default, and expired-entry semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What outbound delivery expiry policy should OpenClaw expose for queued delivery recovery: which config key, default TTL/no-TTL behavior, and expired-entry action?

Rationale: The source-level stale replay problem is clear, but the fix adds public config/default behavior in a strict core schema and changes whether existing queued messages replay after upgrade.

Likely owner: steipete

Owner reason: steipete has the strongest recent history on the delivery queue recovery/storage and config-adjacent code and already gave direction on this issue.

Owner confidence: high

Options:

- **Opt-in messages.delivery TTL (recommended):** Add optional messages.delivery.maxAgeMs plus a closed failed/quarantine-style expired action, preserving current no-TTL default while covering startup recovery and reconnect drains.
- **Finite default TTL:** Ship a default max age to prevent stale floods without user setup, accepting a compatibility-sensitive change to existing recovery behavior.
- **Design outbound and inbound freshness together:** Pause the outbound-only fix and design outbound plus inbound stale-message handling together, reducing drift but delaying the known outbound repair.

## Reproduction Assessment

Yes, at source level: seed an old pending outbound entry with retryCount 0 and no lastAttemptAt, then call recoverPendingDeliveries; current main checks retry/backoff but not queued age. No live restart reproduction was run in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public config/default/action. The narrow maintainable path is outbound expiry in recovery and reconnect drains; bundling inbound freshness would be a broader product decision.

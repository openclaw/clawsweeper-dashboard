## Label Justifications

- `P2`: The issue reports stale outbound messages being replayed after restarts, which is a normal-priority reliability improvement with limited blast radius but real channel impact.
- `impact:message-loss`: The affected surface is outbound message delivery recovery, where stale or duplicate channel messages can be replayed after restart.
- `maturity:stable`: The restart recovery path is part of the Gateway runtime surface, which is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and v2026.6.11 still recover outbound delivery queue entries by pending status, retry count, and backoff only, with no accepted `messages.delivery` TTL or expiry action; the related implementation attempts are closed unmerged rather than canonical fixes.

## What This Changes

Add an operator-configurable TTL or expiry policy for outbound delivery queue messages so stale queued replies are not replayed after gateway restart.

## Best Possible Solution

Add a narrow opt-in outbound delivery expiry policy to the existing SQLite-backed delivery queue recovery and reconnect-drain paths, keep default no-TTL behavior unless maintainers choose otherwise, and cover config/schema/docs plus focused recovery tests.

## Reproduction Assessment

Yes, at source level: seed an old pending outbound delivery row and current startup recovery or reconnect drain will consider it based on pending status, max retries, and backoff, not queued age. I did not run a live gateway replay in this read-only review.

## Solution Assessment

Unclear until maintainers choose the policy: an opt-in TTL on the existing outbound queue is the narrowest maintainable shape, but the proposed config names, defaults, and `expireAction` vocabulary need product direction before implementation.

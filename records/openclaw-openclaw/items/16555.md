## Label Justifications

- `P2`: This is a normal-priority reliability improvement for stale outbound replay with limited blast radius and no core-runtime outage.
- `impact:message-loss`: The reported recovery behavior can replay duplicate or stale channel messages after restart, polluting outbound message delivery.
- `maturity:stable`: The issue affects Gateway runtime delivery/recovery, and `qa/maturity-scores.yaml` lists `gateway-runtime` as M4 Stable.

## Summary

Keep open: current main and the latest release still lack an outbound delivery-queue TTL/expiry policy, the strict messages config has no requested `messages.delivery.*` surface, and the related implementation attempts are closed unmerged rather than canonical fixes.

## What This Changes

Add configurable TTL/expiry for outbound delivery queue messages so gateway recovery and reconnect drains do not replay stale or orphaned messages indefinitely.

## Best Possible Solution

Keep this as the canonical outbound delivery expiry issue, then implement a narrow current-main policy covering startup recovery and reconnect drains after maintainers choose the config/default/action semantics.

Question: What outbound delivery expiry policy should OpenClaw expose for queued delivery recovery: which config key, default behavior, and expired-entry action?

Rationale: The source bug is clear, but the fix adds public config/default behavior in a strict core schema and changes whether existing queued messages replay after upgrade, so automation should not choose that product contract alone.

Likely owner: steipete

Owner reason: steipete has the strongest recent history on the delivery queue/config area and already gave maintainer-facing direction on this issue.

Owner confidence: high

Options:

- **Opt-in messages.delivery TTL (recommended):** Add an optional `messages.delivery.maxAgeMs` with a closed `expireAction` such as failed/quarantine, preserve current no-TTL default, and cover startup plus reconnect drains.
- **Finite default TTL:** Ship a default max age to prevent stale floods without user setup, accepting a compatibility-sensitive change to existing recovery behavior.
- **Broader freshness design:** Pause the outbound-only fix and design outbound plus inbound message freshness together, which may reduce drift but broadens the scope and delays the known outbound repair.

## Reproduction Assessment

Yes, at source level: seed an old pending outbound entry with `retryCount: 0` and no `lastAttemptAt`, then call `recoverPendingDeliveries`; current main checks max retries/backoff but not queued age.

## Solution Assessment

Unclear until maintainer policy is chosen. The maintainable implementation is a narrow expiry policy for startup recovery and reconnect drain; bundling inbound freshness would be a broader product decision.

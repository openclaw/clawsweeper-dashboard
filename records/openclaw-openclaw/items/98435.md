## Summary

Keep open: current main still has a credible gap where restart recovery can report a resumed main session while the external Claude CLI MCP bridge has not been proven reloaded or reconnected, and neither the latest release nor the open related PR closes this exact post-restart loopback readiness problem.

## What This Changes

The issue asks OpenClaw to make MCP loopback capability reconnect automatically, or report partial recovery, after a gateway restart instead of marking the session recovered while Claude CLI tool calls fail.

## Best Possible Solution

Preserve Claude CLI conversation reuse while adding a maintainer-approved post-restart MCP readiness contract, such as an explicit reconnect/nudge path or a partial-recovery status that tells the user when MCP capability is not restored.

## Reproduction Assessment

Yes at source and field-report level, but not by an independently replayed destructive gateway restart in this read-only pass. Current code can report `recovered=1` after scheduling an agent resume while the stable Claude CLI MCP resume path intentionally preserves session reuse across loopback port churn.

## Solution Assessment

Unclear: the suggested reconnect supervisor is plausible, but the best fix needs a maintainer choice about where to own reconnects, readiness status, and safe retry semantics without regressing Claude CLI memory preservation.

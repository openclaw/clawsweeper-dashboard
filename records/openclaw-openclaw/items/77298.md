## Summary

Keep open for a maintainer product decision. The issue has recent live reports on the current stable release that restart recovery is visible as an ordinary cron error, while the proposed remedies change the public meaning of cron terminal status, counters, delivery state, and alerting rather than repairing an already-defined contract.

## What This Changes

Request that cron runs interrupted by a gateway restart remain diagnostically visible without being counted or surfaced as ordinary agent-job failures.

## System Context

Cron persists a running marker while scheduled work is executing; gateway startup recovery converts a leftover marker into a stored cron result. That stored result feeds cron health views, error counters, delivery handling, and operator alerting.

## Architecture Diagram

flowchart LR
  A[Scheduled cron job] --> B[Persisted running marker]
  B --> C[Gateway restart]
  C --> D[Startup recovery]
  D --> E[Stored cron outcome]
  E --> F[Health counters]
  E --> G[Delivery and alerts]
  F --> H[Operator monitoring]

## Best Possible Solution

Define gateway-restart interruption as one documented cron terminal contract—preferably reuse `skipped` with the restart diagnostic, neutral error/skipped counters, and no failure delivery if that matches existing skipped semantics—then update restart recovery, health aggregation, delivery behavior, and regression coverage together.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should gateway-restart recovery reuse the existing `skipped` cron status with neutral counters and delivery, or should OpenClaw add a distinct public `interrupted` terminal status and associated counter semantics?

Rationale: Both options alter persisted status vocabulary and the operator-facing meaning of cron health, retries, notifications, and integrations; code review alone cannot choose the permanent product contract.

Likely owner: markoub

Owner reason: Their current related recovery work is closest to the durable cron restart boundary, though final status semantics need broader maintainer sponsorship.

Owner confidence: low

Options:

- **Reuse `skipped` for restart interruption (recommended):** Persist the restart diagnostic as a skipped run, leave failure counters unchanged, and avoid a failure-delivery attempt; this is the smaller API surface.
- **Add `interrupted` as a terminal status:** Expose a separate public status and interruption counter so operators can distinguish planned gateway interruption from both skipped work and agent failure.

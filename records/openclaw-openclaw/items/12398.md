## Label Justifications

- `P2`: This is a meaningful reliability and safety improvement for scheduled agent work, but it is an additive design item rather than an urgent shipped regression or first-run blocker.
- `impact:session-state`: Cron can currently persist a clean isolated session termination without a scheduler-owned check that the intended task outcome was achieved.
- `impact:security`: The proposed verifier would execute configured commands and expose run/session context to those commands.

## Summary

Keep open: current main and v2026.6.11 still lack a scheduler-owned cron postcondition verifier for successful-but-incomplete isolated agent jobs, and the related cron hook/plugin paths remain partial or closed unmerged rather than a safe replacement.

## What This Changes

The issue requests an optional cron `postconditions` contract that runs deterministic checks after isolated agent jobs and can retry or escalate failed outcomes.

## Best Possible Solution

Define a maintainer-approved additive cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin seam for optional verifiers.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should cron post-run verification be implemented as a scheduler-owned bounded verifier contract, a fail-capable plugin hook, or deferred until a broader agent outcome-verification API exists?

Rationale: The source gap is clear, but the proposed shell-based verifier changes command execution, retry, persisted state, protocol, plugin API, and security boundaries that automation should not choose by itself.

Likely owner: steipete

Owner reason: He already reviewed this exact issue and has the strongest recent history on the cron schema/runtime surfaces involved in the product decision.

Owner confidence: high

Options:

- **Approve bounded scheduler contract (recommended):** Define typed cron post-run verification owned by the scheduler, with explicit command/plugin adapters, timeouts, output caps, redaction, persisted status, retry limits, and failure-alert integration.
- **Add plugin seam first:** Expose a fail-capable cron post-run hook that can return pass, fail, retry, or escalate decisions while keeping verifier implementations outside core.
- **Defer verifier API:** Keep this issue as the specific design tracker until maintainers settle a broader outcome-verification architecture across cron and outbound hooks.

## Reproduction Assessment

Yes, at source level: current main lacks cron postcondition fields, public schema support, and a verifier branch between isolated agent completion and state application. The specific production 18-of-50 incident was not replayed in this read-only review.

## Solution Assessment

Unclear until product and security review. Deterministic post-run verification is the right capability, but the proposed raw shell-string field should become a typed, bounded scheduler contract or fail-capable plugin seam rather than an ad hoc command hook.

## Label Justifications

- `P2`: This is a meaningful reliability improvement for scheduled agent work, but it is an additive design item rather than an urgent shipped regression.
- `impact:session-state`: Cron can currently record a clean isolated session termination without scheduler-owned proof that the intended task outcome was achieved.

## Summary

Keep open: current main still lacks a cron postcondition contract or equivalent scheduler-owned verifier for successful-but-incomplete isolated agent turns, and the remaining work is a product/security design item rather than conservative cleanup.

## What This Changes

The issue requests an optional cron `postconditions` field that runs deterministic verification after agent-driven cron jobs, persists verifier state, and drives retry or escalation when checks fail.

## Best Possible Solution

Add a maintainer-approved additive cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin adapter.

## Reproduction Assessment

Yes, at source-contract level: current main has no cron postcondition fields, public schema support, verifier environment contract, or verifier branch between isolated agent completion and state application. The specific 18-of-50 production incident was not replayed in this read-only review.

## Solution Assessment

No, not as the raw shell-string field alone. Deterministic post-run verification is the right capability, but the maintainable solution needs a typed, bounded, permission-aware scheduler or plugin contract with explicit retry, idempotency, and redaction semantics.

## Label Justifications

- `P2`: This is a meaningful reliability improvement for scheduled agent work, but it is an additive design item rather than an urgent shipped regression.
- `impact:session-state`: Cron can currently record a clean isolated session outcome without scheduler-owned verification that the intended task result was achieved.

## Summary

Keep open: current main still lacks a cron postcondition contract or equivalent scheduler-owned verifier for successful-but-incomplete isolated agent turns, and the remaining work needs product and security design rather than cleanup closure.

## What This Changes

The issue requests an optional cron job postcondition verifier that deterministically checks isolated agent outcomes and drives retry or escalation after a run.

## Best Possible Solution

Add a maintainer-approved additive cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin adapter for optional verifiers.

## Reproduction Assessment

Yes, at the source-contract level: current main has no cron postcondition fields, public schema support, or verifier branch between isolated agent completion and state application. The specific production 18-of-50 incident was not replayed in this read-only review.

## Solution Assessment

Unclear as proposed: deterministic post-run verification is the right capability, but a raw shell-string field is not yet proven to be the best permanent API because execution boundaries, retries, redaction, and plugin ownership need design.

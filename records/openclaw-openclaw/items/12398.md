## Summary

Keep open: current main still lacks a cron postcondition contract or equivalent scheduler-owned verifier for successful-but-incomplete isolated agent cron runs, and the remaining design crosses cron runtime, protocol, UI/CLI, retry semantics, and command-execution security.

## What This Changes

Request to add deterministic post-run verification for cron agent jobs, including postcondition checks, retry context injection, persisted state, and escalation.

## Best Possible Solution

Add a maintainer-approved cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin seam.

## Maintainer Decision

Question: Should cron post-run verification be a scheduler-owned bounded verifier contract, a plugin-owned fail-capable hook, or deferred to a broader agent outcome-verification design?

Rationale: The source proves the capability is missing, but adding it directly changes core cron semantics and introduces command-execution/security and retry-policy choices that automation should not decide.

Owner confidence: high

Options:

- **Add bounded scheduler verifier (recommended):** Define an additive cron postcondition contract in core with typed state, strict execution limits, retry/escalation behavior, and security review before implementation.
- **Add fail-capable plugin hook:** Keep core lean by first adding a supported post-run hook that can fail a cron run and request scheduler-owned retry or escalation.
- **Defer to broader verification design:** Leave this issue open but pause implementation until maintainers settle a shared verification model across cron, channel delivery, and agent finalization.

## Label Justifications

- `P2`: The issue is a significant cron reliability and trust improvement, but it is a broad opt-in feature/design item rather than an active outage or first-run blocker.
- `impact:session-state`: The requested verifier would decide whether an agent cron session's terminal state represents real task completion or an incomplete/hallucinated outcome.
- `impact:security`: The proposed design executes deterministic shell checks and may expose session summaries or tool outcomes to verifier code, so it crosses a security-sensitive boundary.

## Summary

Keep open: current main and the latest release still lack a cron postcondition contract or equivalent scheduler-owned verifier for successful-but-incomplete isolated agent cron runs, and the remaining work is a product/security design item rather than cleanup closure.

## What This Changes

The issue requests optional CronJob postconditions that run deterministic shell verification after agent cron jobs and drive retry, escalation, and state reporting.

## Best Possible Solution

Define a reviewed additive cron post-run verification contract, either as a scheduler-owned postcondition field or a fail-capable plugin hook, with typed state/protocol/CLI/UI/docs, bounded command execution, retry context, and failure-alert integration.

- **Defer native verification:** Keep command cron and external monitors as the supported path for now, accepting that successful-but-incomplete agent cron runs remain hard to detect automatically.

Unclear until maintainer product/security review. A postconditions field is a plausible solution, but the best shape must bound command execution and decide whether core cron or a fail-capable plugin hook owns verification and retry semantics.

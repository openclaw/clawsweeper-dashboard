## Label Justifications

- `P2`: This is a meaningful reliability improvement for scheduled agent work, but it is an additive design item rather than an urgent shipped regression.
- `impact:session-state`: The issue is about cron run/session state treating clean isolated session termination as success without verifying the intended task outcome.
- `impact:security`: The proposed verifier would execute configured commands and expose run/session context to those commands.

## Summary

Keep open: current main and v2026.6.11 still lack a cron postcondition contract or equivalent fail-capable scheduler-owned verifier for successful-but-incomplete isolated agent turns, and the remaining work needs product and security design rather than cleanup closure.

## What This Changes

Request an optional cron `postconditions` field that runs deterministic post-run verification with retry and escalation after isolated agent jobs.

## Best Possible Solution

Add a maintainer-approved additive cron verifier contract with bounded execution, persisted verifier results, retry/escalation semantics, and public API/UI/docs support before implementation.

## Reproduction Assessment

Yes at the source-contract level: current main has no cron postcondition fields, public schema support, or verifier branch between isolated agent completion and state application. The specific production 18-of-50 incident was not replayed in this read-only review.

## Solution Assessment

No, not exactly as a raw shell-string field. Deterministic post-run verification is the right capability, but the maintainable path needs a typed, bounded verifier or fail-capable plugin seam with explicit retry, idempotency, and security semantics.

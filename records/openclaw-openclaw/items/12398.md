## Summary

Keep open: current main and v2026.6.11 still lack a scheduler-owned cron postcondition verifier, and existing command-cron plus observation/plugin hooks do not verify successful-but-incomplete isolated agent turns or drive retry/escalation.

## What This Changes

The issue requests deterministic post-run verification for isolated cron agent jobs, including a postconditions contract, bounded check execution, retry context injection, escalation, and persisted verifier state.

## Best Possible Solution

Define a maintainer-approved additive cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin seam for optional verifiers.

- **Approve bounded scheduler contract (recommended):** Define typed post-run verification owned by cron, with explicit command/plugin adapters, timeout/output/redaction rules, persisted status, retry limits, and failure-alert integration.
- **Add plugin seam first:** Expose a fail-capable cron post-run hook that can return pass, fail, retry, or escalate decisions while verifier implementation remains outside core.
- **Defer verifier API:** Keep this issue as the specific design tracker until maintainers settle broader outcome-verification semantics across cron and outbound hooks.

## Reproduction Assessment

Yes, at source level: current main lacks cron postcondition fields, public schema support, and a verifier branch between isolated agent completion and state application. The specific production 18-of-50 incident was not replayed in this read-only review.

## Solution Assessment

Unclear until product and security review. Deterministic post-run verification is the right capability, but the proposed raw shell-string field should become a bounded typed scheduler contract or fail-capable plugin seam rather than an ad hoc command hook.

## Label Justifications

- `P2`: This is a meaningful reliability and safety improvement for scheduled agent work, but it is an additive design item rather than an urgent shipped regression.
- `impact:session-state`: Cron can currently record a clean isolated session termination without a scheduler-owned check that the intended task outcome was achieved.
- `impact:security`: The proposed verifier would execute configured commands and expose run/session context to those commands.

## Summary

Keep open: current main still lacks a scheduler-owned cron postcondition/verifier contract, and the remaining work is a product and security design item rather than conservative cleanup.

## What This Changes

Add optional cron job postconditions that deterministically verify isolated agent-turn outcomes, persist verifier state, retry with failure context, and escalate on repeated failure.

## Best Possible Solution

Define a maintainer-approved additive cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin seam.

## Reproduction Assessment

Yes, at source level: current main lacks cron postcondition fields, public schema support, and a verifier branch between isolated agent completion and state application. The specific production 18-of-50 incident was not replayed in this read-only review.

## Solution Assessment

Unclear until product and security review. Deterministic post-run verification is the right capability, but the proposed raw shell-string field should become a typed, bounded scheduler contract or fail-capable plugin seam rather than an ad hoc command hook.

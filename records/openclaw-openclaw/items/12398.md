## Label Justifications

- `P2`: This is a meaningful reliability improvement for scheduled agent work, but it is an additive design item rather than an urgent shipped regression or first-run blocker.
- `impact:session-state`: Cron can currently record a clean isolated session termination without a scheduler-owned check that the intended task outcome was achieved.
- `impact:security`: The proposed verifier would execute configured commands and expose run/session context to those commands.

## Summary

Keep open: current main and v2026.6.11 still lack a scheduler-owned postcondition verifier for successful-but-incomplete isolated cron runs, and the related hook/plugin paths are partial, closed, or still unsettled product/security work.

## What This Changes

Requests an optional cron `postconditions` verifier that deterministically checks isolated agent-turn outcomes and can retry or escalate after semantic failure.

## Best Possible Solution

Define a maintainer-approved additive cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin seam for optional verifiers.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should cron post-run verification be implemented as a scheduler-owned bounded verifier contract, a fail-capable plugin hook, or deferred until a broader agent outcome-verification API exists?

Rationale: The source gap is clear, but the proposed shell-based verifier changes command execution, retry, plugin API, persisted state, protocol, and security boundaries that automation should not choose by itself.

Likely owner: steipete

Owner reason: steipete already reviewed this exact issue and has the strongest routing signal across cron runtime, protocol, docs, and the security/product decision boundary.

Owner confidence: high

Options:

- **Approve Bounded Scheduler Contract (recommended):** Define a typed post-run verifier owned by cron, with explicit command/plugin adapters, timeouts, output caps, redaction, persisted status, retry limits, and failure-alert integration.
- **Add Plugin Seam First:** Add a fail-capable cron post-run hook that can return pass/fail/retry/escalate decisions while keeping verifier implementation outside core.
- **Defer Verification API:** Keep the issue open as a design tracker until maintainers settle a broader agent outcome-verification architecture across cron and outbound hooks.

## Reproduction Assessment

Yes, at source level: current main lacks cron postcondition fields, public schema support, and a verifier branch between isolated agent completion and state application. The specific production 18-of-50 incident was not replayed in this read-only review.

## Solution Assessment

Unclear until product and security review. Deterministic post-run verification is the right capability, but the proposed raw shell-string field should become a typed, bounded scheduler contract or fail-capable plugin seam rather than an ad hoc command hook.

## Risks / Open Questions

- A partial implementation could diverge across cron runtime, run logs, Gateway protocol, CLI, Control UI, docs, plugin hooks, and existing failure-alert delivery semantics.

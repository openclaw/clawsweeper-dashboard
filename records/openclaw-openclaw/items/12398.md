## Label Justifications

- `P2`: This is a meaningful reliability improvement for scheduled agent work, but it is an additive design item rather than an urgent shipped regression.
- `impact:session-state`: The issue is about cron run/session state treating clean isolated session termination as success without verifying the intended task outcome.
- `impact:security`: The proposed verifier would execute configured commands and expose run/session context to those commands.

## Summary

Keep open: current main and v2026.6.11 still lack a cron postcondition contract or equivalent scheduler-owned verifier for successful-but-incomplete isolated agent turns, and the remaining work needs maintainer product/security design rather than cleanup closure.

## What This Changes

Request adding optional deterministic postcondition checks for isolated cron agent jobs, including persisted verifier results, retry context, and escalation on failed checks.

## Best Possible Solution

Define a maintainer-approved additive cron verifier contract with bounded deterministic execution, durable result projection, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin seam for optional verifiers.

## Reproduction Assessment

Yes at the source-contract level: current main has no cron postcondition fields, public schema support, or verifier branch between isolated agent completion and state application. The specific production 18-of-50 incident was not replayed in this read-only review.

## Solution Assessment

Unclear. Deterministic post-run verification is the right capability, but the raw shell-string proposal should become a typed, bounded verifier or plugin seam with explicit retry, idempotency, and security semantics before implementation.

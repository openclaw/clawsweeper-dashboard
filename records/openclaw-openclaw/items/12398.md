- `impact:session-state`: The issue is about cron run/session state treating clean isolated session termination as success without verifying the intended task outcome.

## Summary

Keep open: current main and the latest release still lack a scheduler-owned cron postcondition contract or equivalent fail-capable verifier for successful-but-incomplete isolated agent turns, and the remaining work needs product and security design rather than cleanup closure.

## What This Changes

The issue requests an optional cron postcondition verifier that runs deterministic checks after isolated agent-turn cron jobs and can retry or escalate when the intended outcome was not achieved.

## Best Possible Solution

Add a maintainer-approved additive cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin adapter.

## Reproduction Assessment

Yes at the source-contract level: current main has no cron postcondition fields, public schema support, or verifier branch between isolated agent completion and state application. The specific production 18-of-50 incident was not replayed in this read-only review.

## Solution Assessment

No, not exactly as a raw shell-string field. Deterministic post-run verification is the right capability, but the maintainable path needs a typed, bounded verifier or fail-capable plugin seam with explicit retry, idempotency, and security semantics.

## Label Justifications

- `P2`: This is a meaningful reliability and safety improvement for scheduled agent work, but it is an additive design item rather than an urgent shipped regression or first-run blocker.
- `impact:session-state`: Cron can currently persist a clean isolated session termination without a scheduler-owned check that the intended task outcome was achieved.
- `impact:security`: The proposed verifier would execute configured commands and expose run/session context to those commands.

## Summary

Keep open: current main and v2026.6.11 still lack a scheduler-owned cron postcondition verifier, and the remaining design crosses cron protocol/state, retries, unattended command execution, and security boundaries.

## What This Changes

The issue requests deterministic postcondition checks for cron jobs so framework-owned verification can convert successful-but-incomplete isolated agent runs into retry or escalation outcomes.

## Best Possible Solution

Define a maintainer-approved additive cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin seam.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should cron post-run verification be implemented as a scheduler-owned bounded verifier contract, a fail-capable plugin hook, or deferred until a broader agent outcome-verification API exists?

Rationale: The source gap is clear, but the solution adds public cron config/protocol/state, retry behavior, and unattended command execution semantics that require maintainer product and security intent.

Likely owner: steipete

Owner reason: steipete already reviewed this exact issue and has the strongest recent history on the cron schema/runtime/doc surfaces.

Owner confidence: high

Options:

- **Approve bounded scheduler contract (recommended):** Define typed post-run verification owned by cron, with command or plugin adapters, timeout and output caps, redaction, persisted status, retry limits, and failure-alert integration.
- **Add plugin seam first:** Expose a fail-capable cron post-run hook that can return pass, fail, retry, or escalation decisions while keeping verifier implementation outside core.
- **Defer verifier API:** Keep this issue as the specific design tracker until maintainers settle a broader outcome-verification architecture across cron and outbound hooks.

## Reproduction Assessment

Yes, at source level: current main lacks cron postcondition fields, public schema support, and a verifier branch between isolated agent completion and state application. The specific production 18-of-50 incident was not replayed in this read-only review.

## Solution Assessment

Unclear until product and security review. Deterministic post-run verification is the right capability, but the proposed raw shell-string field should become a typed, bounded scheduler contract or fail-capable plugin seam rather than an ad hoc command hook.

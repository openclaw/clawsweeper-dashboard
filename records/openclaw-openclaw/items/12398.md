## Summary

Keep open: current main and v2026.6.11 still lack a scheduler-owned cron postcondition verifier; existing command cron, retries, failure alerts, and observe-only cron plugin hooks cover adjacent cases but do not verify successful-looking isolated agent outcomes or inject retry context.

## What This Changes

The issue requests an optional cron `postconditions` contract that runs deterministic checks after an agent cron run, records verifier state, retries with failure context, and escalates when verification fails.

## Best Possible Solution

Settle a maintainer-approved additive cron post-run verification contract: either a narrow core CronJob postcondition API or a fail-capable scheduler hook, with typed state/protocol/docs, bounded command execution, retry/escalation semantics, and coverage across scheduled, startup, and manual run paths.

## Maintainer Decision

Kind: security_boundary

Question: Should OpenClaw support scheduler-owned cron post-run verification for agentTurn jobs, and should that live as a core CronJob postconditions field or as a fail-capable plugin hook with scheduler retry/escalation authority?

Rationale: The remaining work adds public cron schema/state and can execute unattended shell checks after model work, so automation cannot safely choose the core-vs-plugin API or command-execution trust boundary.

Likely owner: steipete

Owner reason: They have the strongest recent history on the cron schema/runtime/docs surfaces and prior routing comments for this exact product/security boundary.

Owner confidence: high

Options:

- **Design Scheduler-Owned Verifier (recommended):** Define a narrow additive verifier contract with explicit permissions, timeout/cancellation/redaction rules, durable state, retry context injection, and failure-alert integration before implementation.
- **Expose Fail-Capable Plugin Hook:** Keep CronJob schema smaller and first add a plugin hook that can turn a completed cron run into a scheduler-owned retry or escalation decision.
- **Defer Native Verification:** Document command cron and external monitoring as the current workaround and leave native postcondition verification unimplemented until maintainers are ready to own the security model.

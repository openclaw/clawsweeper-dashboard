## Summary

Keep open: current main still treats a clean agent-turn termination as a successful cron run without a scheduler-owned mechanism to verify the intended outcome, while the remaining design needs explicit product and security decisions.

## What This Changes

Add deterministic post-run verification for agent-driven cron jobs, with persisted results, bounded retries, retry context, and escalation on failed checks.

## Best Possible Solution

Define a generic scheduler-owned verifier contract that reuses the bounded command runner, records verification state in canonical SQLite run history, and can request tightly limited retry or escalation under explicit operator-admin policy; then expose the approved contract consistently through protocol, CLI, UI, and docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should deterministic cron outcome verification be a first-class core job contract, or a generic fail-capable plugin hook that can request scheduler-owned retry and escalation?

Rationale: Both approaches require new public semantics and security boundaries, and source inspection cannot determine whether maintainers want permanent per-job verifier configuration in core or a reusable plugin extension point.

Likely owner: steipete

Owner reason: The existing discussion and recent cron runtime, schema, and documentation history make this person the best available owner for the product-boundary decision.

Owner confidence: high

Options:

- **Generic verifier contract (recommended):** Add a narrow scheduler-owned verifier abstraction with a bounded command implementation and a plugin-capable extension seam, keeping retry, state, and escalation semantics canonical.
- **Core postconditions field:** Adopt the proposed per-job postconditions surface directly in cron and own its command security, protocol, UI, migration, and retry behavior in core.
- **Plugin hook only:** Add only a fail-capable post-run plugin hook and require external plugins to provide verifier configuration and execution.

## Reproduction Assessment

No live failure was reproduced in this review, but the missing capability is high-confidence from the current contract: an isolated agent turn can return `ok`, and cron has no configured post-run verifier that can reject that result based on external state.

## Solution Assessment

No, not yet: the proposed shell field demonstrates the needed behavior, but the safer maintainable design should reuse existing bounded command execution and first resolve whether the public contract belongs in core or behind a generic fail-capable plugin seam.

## Security Review

Status: needs_attention

Summary: The requested feature is security-sensitive because it adds unattended command execution, context transfer, and automated retry behavior to scheduled jobs.

## Risks / Open Questions

- A direct per-job shell field would add unattended Gateway-host command execution and must reuse the bounded command runner, operator-admin authorization, timeout, output-cap, environment, and audit controls rather than creating a parallel execution path.
- Passing verifier output or agent summaries into retries can expose sensitive context and turn untrusted script output into prompt instructions unless output is capped, clearly delimited, and treated as untrusted data.
- Automatic retries can repeat non-idempotent external actions and increase model cost; the design needs strict attempt limits, run identity, cancellation behavior, and visible duplicate-action semantics.
- The permanent ownership boundary remains unresolved: a core cron contract offers consistent retry/state behavior, while a generic fail-capable plugin hook better preserves a lean core but requires a new supported API.

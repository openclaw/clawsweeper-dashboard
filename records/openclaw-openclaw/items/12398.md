## Label Justifications

- `P2`: This is a meaningful reliability and security-sensitive enhancement for scheduled agent work, but it is additive and needs design review rather than emergency handling.
- `impact:session-state`: Cron can currently persist a clean isolated session termination without a scheduler-owned check that the intended task outcome was achieved.
- `impact:security`: The proposed verifier would execute configured commands and expose run/session context to those commands.

## Summary

Keep open: current main and the latest release still lack a cron postcondition contract or equivalent scheduler-owned verifier for successful-but-incomplete isolated agent cron runs, and the remaining work needs product and security design rather than cleanup closure.

## What This Changes

The issue requests an opt-in cron job postcondition contract that deterministically verifies isolated agent cron outcomes and can retry or escalate when a cleanly terminated agent run did not actually finish its task.

## Best Possible Solution

Add a maintainer-approved additive cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin seam.

## Reproduction Assessment

Yes, at source level: current main lacks cron postcondition fields, public schema support, and a verifier branch between isolated agent completion and state application. The specific production 18-of-50 incident was not replayed in this read-only review.

## Solution Assessment

Unclear until product and security review. Deterministic post-run verification is the right capability class, but current hooks appear observational for cron completion, so maintainers need to choose a bounded scheduler contract or a new fail-capable plugin seam.

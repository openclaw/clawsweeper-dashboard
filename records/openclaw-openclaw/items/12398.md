## Label Justifications

- `P2`: This is a meaningful reliability improvement for scheduled agent work, but it is an additive design item rather than an urgent shipped regression.
- `impact:session-state`: Cron can currently record a clean isolated session termination without a scheduler-owned check that the intended task outcome was achieved.
- `impact:security`: The proposed verifier would execute configured commands and expose run/session context to those commands.

## Summary

Keep open: current main still lacks a cron postcondition contract or equivalent scheduler-owned verifier for successful-but-incomplete isolated agent cron runs, and the remaining work needs product and security design rather than cleanup closure.

## What This Changes

Request an additive cron post-run verification contract so isolated agent cron jobs can deterministically check outcomes, retry with context, and escalate when semantic completion fails.

## Best Possible Solution

Add a maintainer-approved additive cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin seam for optional verifiers.

## Reproduction Assessment

Yes at source level: current main lacks cron postcondition fields, public schema support, and a verifier branch between isolated agent completion and state application. The specific 18-of-50 production incident was not replayed in this read-only review.

## Solution Assessment

Unclear until product and security review. Deterministic post-run verification is the right capability, but the proposed raw shell-string field should become a typed, bounded scheduler contract or fail-capable plugin seam rather than an ad hoc command hook.

- The core-contract versus plugin-hook boundary remains unresolved because current command jobs and cron_changed hooks are useful but do not let a verifier fail an already-completed agentTurn run and request scheduler-owned retry/escalation.

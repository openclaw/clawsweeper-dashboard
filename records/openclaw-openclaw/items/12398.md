- `P2`: This is a meaningful reliability improvement for scheduled agent work, but it is an additive design item rather than an urgent shipped regression.

## Summary

Keep open: current main and v2026.6.11 still lack a cron postcondition contract or equivalent scheduler-owned verifier for successful-but-incomplete isolated agent cron runs, and the remaining work needs product and security design rather than cleanup closure.

## What This Changes

Request adds optional cron postconditions that deterministically verify isolated agentTurn jobs after completion and drive retry or escalation.

## Best Possible Solution

Add a maintainer-approved cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin seam for optional verifiers.

## Maintainer Decision

Question: Should cron post-run verification be implemented as a scheduler-owned bounded verifier contract, a plugin-owned fail-capable hook, or deferred until a broader agent-verification API exists?

Rationale: The source gap is clear, but the proposed verifier changes command execution, retry semantics, persisted state, protocol, UI/CLI, plugin hooks, and security boundaries that automation should not choose by itself.

Owner confidence: high

Options:

- **Approve bounded scheduler contract (recommended):** Define a typed post-run verifier owned by cron, with explicit command or plugin adapters, timeouts, output caps, redaction, persisted status, retry limits, and failure-alert integration.
- **Add plugin seam first:** Add a fail-capable cron post-run hook that can return pass, fail, retry, or escalate decisions while keeping verifier implementation outside core.
- **Defer verification API:** Keep this issue as a design tracker until maintainers settle a broader agent outcome-verification architecture across cron and outbound hooks.

## Reproduction Assessment

Yes, at source level: current main lacks cron postcondition fields, public schema support, and a verifier branch between isolated agent completion and state application. The specific production 18-of-50 incident was not replayed in this read-only review.

## Solution Assessment

Unclear until product and security review. Deterministic post-run verification is the right capability, but the proposed raw shell-string field should become a typed, bounded scheduler contract or fail-capable plugin seam rather than an ad hoc command hook.

## Label Justifications

- `P2`: This is a meaningful reliability improvement for scheduled agent work, but it is an additive design item rather than an urgent shipped regression.
- `impact:session-state`: The issue is about cron run/session state treating clean isolated session termination as success without verifying the intended task outcome.
- `impact:security`: The proposed verifier would execute configured commands and expose run/session context to those commands.

## Summary

Keep open: current main and the latest release still lack a cron postcondition contract or equivalent scheduler-owned verifier for successful-but-incomplete isolated agent turns, and the remaining work is a security-sensitive product/API design rather than conservative cleanup.

## What This Changes

Add optional cron postconditions that run deterministic verification after agent-turn cron jobs and can drive retry or escalation when the agent completed cleanly but did not meet the intended outcome.

## Best Possible Solution

Add a maintainer-approved additive cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin adapter for optional verifiers.

## Reproduction Assessment

Yes at the source-contract level: current main has no cron postcondition fields, public schema support, or verifier branch between isolated agent completion and state application. The specific production 18-of-50 incident was not replayed in this read-only review.

## Solution Assessment

No, not exactly as a raw shell-string field. Deterministic post-run verification is the right capability, but the maintainable path needs a typed, bounded verifier or plugin seam with explicit retry, idempotency, and security semantics.

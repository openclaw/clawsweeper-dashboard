## Summary

Keep open: current main and v2026.6.11 still lack a scheduler-owned postcondition verifier for successful-but-incomplete isolated cron runs, and the related hook/plugin paths are partial, closed, or still unsettled product/security work.

## What This Changes

The issue requests deterministic post-run verification for isolated cron agent jobs, including postcondition command execution, retry context injection, persisted verifier state, and escalation when a clean agent run did not complete the intended work.

## Best Possible Solution

Define a maintainer-approved additive cron verifier contract with typed persisted results, bounded execution, retry/escalation semantics, and either a safe scheduler-owned runner or a fail-capable plugin seam for optional verifiers.

## Maintainer Decision

Required: true

Question: Should cron post-run verification be implemented as a scheduler-owned bounded verifier contract, a fail-capable plugin hook, or deferred until a broader agent outcome-verification API exists?

Rationale: The source gap is clear, but the proposed shell-based verifier changes command execution, retry, plugin API, persisted state, protocol, and security boundaries that automation should not choose by itself.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve bounded scheduler contract (recommended):** Define typed post-run verification owned by cron, with explicit command/plugin adapters, timeouts, output caps, redaction, persisted status, retry limits, and failure-alert integration.
- **Add plugin seam first:** Add a fail-capable cron post-run hook that can return pass, fail, retry, or escalate decisions while keeping verifier implementation outside core.
- **Defer verifier API:** Keep this issue as the specific design tracker until maintainers settle a broader outcome-verification architecture across cron and outbound hooks.

## Reproduction Assessment

Yes, at source level: current main lacks cron postcondition fields, public schema support, and a verifier branch between isolated agent completion and state application. The specific production 18-of-50 incident was not replayed in this read-only review.

## Solution Assessment

Unclear until product and security review. Deterministic post-run verification is the right capability, but the proposed raw shell-string field should become a typed, bounded scheduler contract or fail-capable plugin seam rather than an ad hoc command hook.

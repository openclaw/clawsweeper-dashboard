- `impact:session-state`: The central request is about fallback attempts reusing the primary agent's workspace, context, session file, and skills state.

## Summary

Keep open: current main and the latest release still model fallback as provider/model retry while preserving the same agent, session, workspace, auth scope, and bootstrap context; the requested fallback-agent/workspace behavior remains a product/API design change.

## What This Changes

The issue requests a fallback mode where a failed primary model can retry under a different agent or model-specific context/workspace profile instead of reusing the primary agent's full context.

## Best Possible Solution

Keep this open for a maintainer-selected fallback context contract, then implement that chosen agent-switch, workspace override, or model-context-profile path through config schemas, docs, fallback metadata, runner/session plumbing, and regression tests.

## Reproduction Assessment

Yes, at source level: current main still exposes only provider/model fallback refs and runs fallback candidates with the same agent/session/workspace context. I did not run a live outage because the missing config and runtime surface is directly visible in source.

## Solution Assessment

Unclear. The reported gap is real, but maintainers still need to choose whether the best long-term API is fallbackAgent, fallbackWorkspace, or a narrower model-context-profile/budget mechanism.

## Label Justifications

- `P2`: The request affects multi-model fallback quality and session/context correctness for configured fallback users without being an immediate core outage.
- `impact:session-state`: Fallback attempts currently retain the primary agent's workspace, session file, skills snapshot, and context identity.
- `impact:auth-provider`: The behavior is rooted in provider/model fallback candidate routing, and any fix would change model fallback scoping.

## Summary

Keep open: current main and v2026.6.11 still treat fallback as provider/model retry, with no supported way for a fallback attempt to switch agent identity, workspace, session file, agentDir, skills snapshot, or context profile. Existing hooks and docs expose bootstrap customization and model failover, but they do not solve the requested fallback-agent/workspace contract, so this remains a maintainer product/design item rather than cleanup.

## What This Changes

Request an agent-level fallback/context mechanism so a model fallback can use a different agent, workspace, or smaller context profile instead of reusing the primary agent context.

## Best Possible Solution

Keep this open for a maintainer-selected fallback context contract, then implement the chosen agent-switch, workspace override, or model-context-profile semantics through config schemas, docs, fallback candidate metadata, reply-runner/session plumbing, and regression tests proving fallback retries use alternate context without corrupting the original session.

## Reproduction Assessment

Yes, at source level: current main exposes only primary/fallback model refs and runs fallback candidates with the same agent/session/workspace context. I did not run a live provider outage because the missing config/runtime surface is directly visible in source.

## Solution Assessment

Unclear. The reported gap is real, but maintainers still need to choose whether the best long-term API is fallbackAgent, fallbackWorkspace, or a narrower model-context-profile/budget mechanism.

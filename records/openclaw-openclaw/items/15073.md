## Label Justifications

- `P2`: The request affects fallback quality and session integrity for multi-model users, but it is a bounded feature/design issue rather than an urgent outage.
- `impact:session-state`: The central problem is fallback attempts reusing the primary agent workspace, prompt context, and session state instead of a fallback-specific context.
- `impact:auth-provider`: The behavior is triggered by provider/model fallback routing and any fix would change how fallback candidates are selected and scoped.

## Summary

Keep open: current main and the latest release still implement fallback as provider/model candidate retry inside the same agent run context, while the requested alternate fallback agent/workspace/context contract remains unimplemented and needs maintainer product design.

## What This Changes

The issue requests per-agent fallback context so a failed primary model can retry through another agent, workspace, or reduced context profile instead of reusing the original full prompt context.

## Best Possible Solution

Keep this open for a maintainer-chosen fallback context contract, then implement the selected agent-switch, workspace override, or model-context-profile semantics through config schemas, docs, fallback candidate metadata, runner/session plumbing, and regression tests.

## Reproduction Assessment

Yes, at source level: current main exposes only primary/fallback model refs and runs each fallback candidate with the same agent/session/workspace context. I did not run a live provider outage because the missing config/runtime surface is directly visible in source.

## Solution Assessment

Unclear. The reported gap is real, but maintainers still need to choose whether the best long-term API is fallbackAgent, fallbackWorkspace, or a narrower model-context-profile/budget mechanism.

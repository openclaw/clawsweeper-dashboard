- `impact:session-state`: The central problem is fallback attempts reusing the primary agent's workspace, session, and skills context instead of fallback-specific context.
- `impact:auth-provider`: The behavior is triggered by provider/model fallback routing and any fix would change fallback candidate scoping.

## Summary

Keep open: current main still implements model fallback as provider/model retry while retaining the original agent, workspace, session file, config, and skills context, so the requested fallback-agent/workspace/context behavior remains a real product/API design issue.

## What This Changes

The issue requests a fallback path that can switch to another agent or context/workspace when the primary model falls back to a smaller or local model.

## Best Possible Solution

Keep this open for a maintainer-selected fallback context contract, then implement the chosen agent-switch, workspace override, or model-context-profile semantics through config schemas, docs, runner/session plumbing, and regression tests.

## Reproduction Assessment

Yes, at source level: current main exposes only primary/fallback model refs and runs fallback candidates with the same agent/session/workspace context. I did not run a live provider outage because the missing config/runtime surface is directly visible in source.

## Solution Assessment

Unclear. The reported gap is real, but maintainers still need to choose whether the durable API is fallbackAgent, fallbackWorkspace, or a narrower model-context-profile/budget mechanism.

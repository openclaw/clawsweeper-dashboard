## Label Justifications

- `P2`: The request affects fallback quality and session integrity for multi-model users, but it is a bounded feature/design issue rather than an urgent outage.
- `impact:session-state`: The central problem is fallback attempts reusing the primary agent's workspace, context, session, and skills state instead of fallback-specific context.
- `impact:auth-provider`: The behavior is triggered by provider/model fallback routing and any fix would change fallback candidate scoping.

## Summary

Keep open: current main still treats fallback as provider/model retry while reusing the same agent, session, workspace, and skills context, so the requested fallback agent/workspace/context contract remains real and needs maintainer product direction.

## What This Changes

The issue requests a way for model fallback to switch to a different agent, workspace, or model-specific context profile instead of sending the primary agent's full context to a smaller fallback model.

## Best Possible Solution

Keep this open for a maintainer-selected core fallback-context contract, then implement the chosen agent-switch, workspace override, or model-context-profile semantics through config schemas, docs, runner/session plumbing, and regression tests.

## Reproduction Assessment

Yes, at source level: current main still exposes only primary/fallback model refs and runs each fallback candidate with the same agent/session/workspace context. I did not run a live provider outage because the missing config/runtime surface is directly visible in source.

## Solution Assessment

Unclear. The reported gap is real, but maintainers still need to choose whether the best long-term API is fallbackAgent, fallbackWorkspace, or a narrower model-context-profile/budget mechanism.

## Label Justifications

- `P2`: The issue affects multi-model fallback quality and operator reliability, but it is a bounded feature/design request rather than an urgent regression or outage.
- `impact:session-state`: The central problem is fallback attempts reusing the primary agent's workspace, context, session, and skills state instead of fallback-specific context.
- `impact:auth-provider`: The behavior is triggered by provider/model fallback routing and any fix would change fallback candidate scoping.

## Summary

Keep open: current main and the latest release still model fallback as provider/model retry, with no fallback-agent, fallback-workspace, or model-context-profile contract, so the requested behavior remains real and needs maintainer product direction.

## What This Changes

The issue requests a way for model fallback to use a different agent/workspace/context, or a narrower per-model context budget/profile, instead of reusing the primary agent context.

## Best Possible Solution

Keep this issue as the canonical core design thread, choose the fallback context contract first, then implement schema, docs, runner/session plumbing, and regression coverage around that contract.

Rationale: The missing behavior is visible in source, but the permanent public API affects config schema, session identity, agentDir/workspace ownership, auth routing, skills snapshots, and upgrade behavior.

Owner confidence: high

Options:

- **Define fallback context profiles (recommended):** Add a first-class model or fallback context profile that controls bootstrap budget/files, skills visibility, and session-safe context without changing agent identity by default.
- **Add fallback agent/workspace switching:** Allow fallback attempts to select another configured agent or workspace, but require explicit session, auth, state, and migration semantics before implementation.
- **Defer to narrower threads:** Keep fallback model selection unchanged for now and solve only notification, re-injection, model-key, or auth-propagation subproblems in their own issues.

Unclear: the reported gap is real, but maintainers still need to choose whether the best solution is fallbackAgent, fallbackWorkspace, or a narrower model-context-profile/budget mechanism.

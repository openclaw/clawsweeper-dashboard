## Label Justifications

- `P2`: The request affects fallback quality and session integrity for multi-model users, but it is a bounded feature/design issue rather than an urgent outage.
- `impact:session-state`: The central problem is fallback attempts reusing the primary agent's workspace/context/session state instead of a smaller fallback-specific context.
- `impact:auth-provider`: The behavior is triggered by provider/model fallback routing and would change how fallback candidates are selected and scoped.

## Summary

Keep open: current main and v2026.6.11 still treat fallback as provider/model candidate retry inside the same agent run context, while the requested alternate fallback agent/workspace/context contract remains a product-design change.

## What This Changes

The issue requests a way for model fallback to switch to an agent-specific workspace or context profile instead of reusing the primary agent's large bootstrap context.

## Best Possible Solution

Keep this open for a maintainer-chosen fallback context contract, then implement the chosen agent-switch, workspace override, or model-context-profile semantics through config schemas, docs, fallback candidate metadata, runner/session plumbing, and regression tests.

## Reproduction Assessment

Yes, at source level: current main still exposes only primary/fallback model refs and runs each fallback candidate with the same agent/session/workspace context. I did not run a live provider outage because the missing config/runtime surface is directly visible in source.

## Solution Assessment

Unclear. The reported gap is real, but maintainers still need to choose whether the best long-term API is fallbackAgent, fallbackWorkspace, or a narrower model-context-profile/budget mechanism.

- `impact:session-state`: The central problem is fallback attempts reusing the primary agent's workspace, context, session, and skills state instead of fallback-specific context.

## Summary

Keep open: current main still treats fallback as provider/model retry under the same agent/session/workspace context, while the requested alternate agent/workspace/context behavior remains a public config and runtime design decision.

## What This Changes

The issue requests an agent-level fallback context/workspace mechanism so a fallback model can use a smaller separate agent identity and workspace instead of the primary agent context.

## Best Possible Solution

Keep this open for a maintainer-selected fallback context contract, then implement the chosen agent-switch, workspace override, or model-context-profile semantics through config schemas, docs, runner/session plumbing, and regression tests.

## Reproduction Assessment

Yes, at source level: current main exposes only primary/fallback model refs and runs fallback candidates with the same agent/session/workspace context. I did not run a live provider outage because the missing config/runtime surface is directly visible in source.

## Solution Assessment

Unclear. The reported gap is real, but maintainers still need to choose whether the best long-term API is fallbackAgent, fallbackWorkspace, or a narrower model-context-profile/budget mechanism.

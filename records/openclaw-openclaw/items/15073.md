## Label Justifications

- `P2`: This is a valid fallback-quality improvement with meaningful but limited blast radius, not an emergency or current core-runtime outage.
- `impact:session-state`: The requested fallback context can change workspace prompt, memory, transcript association, skills, and agent identity during an active session.
- `impact:auth-provider`: The behavior is triggered by provider/model failover and any alternate-agent design would also affect per-agent credential ownership.

## Summary

Keep open: current main still performs fallback as provider/model candidate retry within the existing agent and session. The newer per-agent `localModelLean` mode reduces tool exposure for small local models, but it neither selects a different fallback workspace nor changes bootstrap context, so it does not resolve the central request. ([github.com](https://github.com/openclaw/openclaw/blob/main/src/config/types.agents-shared.ts))

## What This Changes

Add fallback behavior that can use a different agent workspace or a model-specific context profile when the primary model fails.

## Best Possible Solution

Keep agent, session, transcript, and auth identity stable while allowing fallback candidates to select one bounded context profile controlling bootstrap limits/files, skills, and tool exposure; carry that profile explicitly through candidate metadata and prove fresh-session, mid-session, and fallback-recovery behavior.

## Maintainer Decision

Kind: product_direction

Question: Should fallback retain the current agent/session and select a model-specific context profile, or transfer execution to a separately configured agent and workspace?

Rationale: The alternatives define materially different ownership for transcripts, authentication, workspace files, skills, tools, and reply delivery, so implementation cannot safely choose the public contract without maintainer intent.

Likely owner: steipete

Owner reason: This person supplied the recent maintainer-facing design assessment and has the strongest available connection to the fallback/config runtime boundary.

Owner confidence: high

Options:

- **Model context profile (recommended):** Keep agent and session identity fixed while each fallback candidate selects a bounded bootstrap, skills, and tool-context profile.
- **Fallback agent transfer:** Switch to another configured agent only after defining explicit auth, transcript, workspace, and delivery handoff semantics.
- **Keep model-only fallback:** Retain current fallback behavior and document separate agents plus manual routing as the supported small-model workflow.

## Reproduction Assessment

Yes, at source level: configure a model fallback and inspect the candidate path, which varies only provider/model while retaining the caller's agent/session context. No live rate-limit or timeout run was performed in this read-only review.

## Solution Assessment

No final API shape is proven yet. A model-specific context profile is narrower and safer than switching agent identity because it addresses prompt overload without introducing transcript, auth, workspace, and delivery handoff semantics.

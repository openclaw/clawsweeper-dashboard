## Label Justifications

- `P2`: Fallback quality and graceful degradation matter, but this remains a bounded feature/design issue rather than an urgent production regression.
- `impact:session-state`: The requested behavior would intentionally change workspace/context and possibly agent/session identity during fallback retries.
- `impact:auth-provider`: The trigger is provider/model fallback routing and model choice, with auth/provider semantics involved in choosing fallback attempts.

## Summary

Keep open. Current main and the latest release still treat fallback as provider/model candidate retry inside the original agent/session/workspace context, while the requested fallback agent/workspace/context-profile behavior remains a compatibility-sensitive product design decision.

## What This Changes

The issue requests a way for model fallback to switch to a different agent, workspace, or context profile instead of reusing the primary agent's full context.

## Best Possible Solution

Define one maintainer-approved fallback context contract, then update config schemas, docs, candidate metadata, runner/session plumbing, and regression tests together.

## Reproduction Assessment

Yes, at source level. Current-main types, strict schemas, fallback candidate metadata, docs, and fallback execution show retries vary provider/model while reusing the original run context.

## Solution Assessment

No implementation is under review yet. The issue is valid, but the best path needs maintainer product design before an automated repair picks fallbackAgent, fallbackWorkspace, or context-profile semantics.

## Label Justifications

- `P2`: The issue affects fallback quality and session integrity in multi-model setups, but it is a bounded feature/design request rather than an active outage.
- `impact:session-state`: The requested behavior is about keeping fallback attempts from inheriting the wrong prompt, workspace, skills, and session context.
- `impact:auth-provider`: The problem is triggered by provider/model fallback routing and would change how fallback model attempts are selected and scoped.

## Summary

Keep open: current main still treats model fallback as provider/model retry, not as a fallback agent, fallback workspace, or model-specific context profile, and related cleanup already treats this issue as the canonical remaining design thread.

## What This Changes

Request a first-class way for fallback attempts to use a different agent/workspace/context profile instead of reusing the primary agent prompt and workspace context.

## Best Possible Solution

Choose one core fallback-context contract, then update config types, strict schemas, docs, fallback candidate metadata, reply-runner/session plumbing, and regression tests so fallback attempts use the intended context without corrupting the original session.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which public fallback-context contract should OpenClaw support for this issue: switching to another agent, overriding only workspace/context, or defining model-specific context profiles?

Rationale: The implementation changes public config and session/auth semantics, and automation should not choose whether fallback changes agent identity or only prompt/context assembly.

Likely owner: steipete

Owner reason: steipete already kept this issue open for design and is the clearest product-direction routing candidate in the current discussion.

Owner confidence: medium

Options:

- **Model context profile first (recommended):** Add an explicit model/fallback context profile that can control bootstrap/context budgets and possibly tools/skills while preserving the original agent/session identity.
- **Fallback agent switch:** Allow fallback attempts to run as another configured agent, accepting the larger migration and safety work around agentDir, auth, skills, and transcript identity.
- **Narrow workspace/runbook override:** Add a smaller fallback workspace or runbook override for graceful degradation, leaving full per-model profile identity for a later design.

## Reproduction Assessment

Yes, at source level for the missing capability: current schemas and fallback selection only support provider/model fallbacks, while run parameters keep the original agent/workspace/session context. I did not run a live provider outage reproduction in this read-only review.

## Solution Assessment

Unclear as proposed: fallbackAgent is plausible but not necessarily the best permanent shape. A maintainer should first choose between agent switching, workspace/runbook override, and model-context-profile semantics.

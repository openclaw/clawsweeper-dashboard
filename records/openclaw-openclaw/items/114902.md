## Summary

The watchdog addresses a real source-level QQBot liveness gap, but the new counter is connection-independent and is not reset when a socket is replaced. A previous socket’s unanswered heartbeat can therefore make a fresh socket terminate after only one missed ACK, producing avoidable reconnect churn; keep this PR open for that narrow repair and for real QQBot behavior proof.

## What This Changes

This PR adds a QQBot gateway heartbeat-ACK watchdog that terminates a WebSocket after two unanswered heartbeats and adds regression tests for ACK, no-ACK, blocked-ingress, and malformed-frame paths.

## System Context

The QQBot extension maintains a gateway WebSocket that receives gateway events, serializes normal inbound events into durable ingress, and reconnects after socket closure. The proposed watchdog observes heartbeat ACKs before that serialized ingress path and terminates an unhealthy connection so the existing reconnect flow can resume message delivery.

## Best Possible Solution

Reset heartbeat-liveness state whenever a gateway socket is discarded or before a replacement socket begins its heartbeat cycle, add a reconnect-boundary regression test, and provide redacted runtime evidence from a QQBot session before merge.

Yes, from source: let one socket send a heartbeat without an ACK, replace that socket, then withhold one ACK on the replacement; the retained counter makes the new connection reach the threshold one heartbeat earlier than intended. ## Solution Assessment

No. Synchronous ACK handling before durable ingress is a sound direction, but the state must be scoped to one WebSocket lifetime; resetting it on cleanup or replacement is narrower and preserves the stated two-unanswered-send policy.

## Summary

Keep open. Current main and v2026.6.11 still keep managed HOOK.md hooks on the void-returning internal hook registry, while enforceable before/after tool-call policy remains in typed plugin hooks; this remains a security-sensitive API/product decision, not a cleanup close.

## What This Changes

Request to expose before_tool_call and after_tool_call through managed/internal HOOK.md hooks so operators can inspect, block, rewrite, and audit tool calls without packaging a full plugin.

## Best Possible Solution

Keep this as the canonical design tracker until maintainers either add a typed managed HOOK.md tool-call contract with block/rewrite/observe semantics, validation, docs, and tests, or explicitly keep tool-call policy plugin-only and reject or warn on unsupported managed hook event names.

- **Keep plugin-only policy:** Reject or warn on before_tool_call and after_tool_call in HOOK.md metadata and point users to typed plugin hooks or ClawHub-packaged code plugins for enforceable tool policy.
- **Expose telemetry only:** Expose non-blocking after-call observation for managed hooks while keeping pre-tool blocking and parameter rewrites in the typed plugin contract.

Yes, at source level. A managed HOOK.md handler can register event strings, but current internal hooks return void and current before/after tool paths consult plugin hooks rather than managed internal hooks.

## Solution Assessment

Unclear as an implementation shape. The requested capability is valid, but the best fix depends on whether maintainers want managed hooks to gain policy semantics or want unsupported tool-call event names rejected with plugin-hook guidance.

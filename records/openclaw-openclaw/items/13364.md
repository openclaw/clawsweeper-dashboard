## Summary

Keep open: current main and v2026.6.11 still keep enforceable tool-call interception on the plugin hook surface, while managed HOOK.md/internal hooks have no tool-call event family, no blocking or parameter-rewrite return contract, and no complete merged canonical fix.

## What This Changes

Request to expose before_tool_call and after_tool_call interception through managed HOOK.md/internal hooks so hooks can observe, rewrite, or block tool operations without a full plugin.

## Best Possible Solution

Keep this as the canonical maintainer API/security design item: either add typed managed before/after tool-call events with explicit blocking/rewrite semantics across active tool paths, or explicitly keep enforcement plugin-only and reject or document unsupported HOOK.md event names.

## Reproduction Assessment

Yes, at source level: managed HOOK.md handlers register only with the internal void-returning hook registry, while the actual before/after tool paths consult the plugin hook runner. I did not run a live gateway reproduction because the current source and shipped tag already show the missing dispatch and return contract.

## Solution Assessment

Unclear as a product direction, not as a source gap. A direct internal-hook bridge is plausible, but plugin hooks already own enforceable middleware today, so the best fix needs maintainer agreement on whether managed hooks should become a second policy gate or should fail clearly when tool-call events are declared.

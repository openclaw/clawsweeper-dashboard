## Summary

Keep open: current main and v2026.6.11 still expose enforceable before/after tool-call policy only through typed plugin hooks, while managed HOOK.md internal hooks remain void-returning command/lifecycle handlers with no tool-call event or blocking/parameter-rewrite bridge.

## What This Changes

Request exposing existing before_tool_call and after_tool_call tool interception semantics through the managed internal HOOK.md hook system.

## Best Possible Solution

Keep this as the canonical design tracker: either add typed managed/internal before and after tool-call events with block, parameter rewrite, after-call observation, unsupported-event validation, docs, and focused tests, or explicitly keep tool-call policy plugin-only and surface unsupported HOOK.md event names.

## Reproduction Assessment

Yes, at source level. A managed HOOK.md handler can register an event string, but current internal hooks return void and the before/after tool paths consult typed plugin hooks rather than managed internal hooks.

## Solution Assessment

Unclear as an implementation shape. The issue should stay open until maintainers choose the managed-hook API, trust model, event names, return semantics, timeout behavior, and unsupported-event diagnostics.

## Summary

Keep open. Current main and the latest release still keep enforceable before/after tool-call policy in typed plugin hooks, while managed HOOK.md internal hooks remain a void-returning event system with no tool-call event type, no blocking or parameter-rewrite return contract, and no bridge from tool execution; related closed items are duplicates or partial unmerged attempts, and the open lifecycle PR does not own this full request.

## What This Changes

Request to expose before_tool_call and after_tool_call through managed internal HOOK.md hooks so simpler hook handlers can observe, rewrite, and block tool operations.

## Best Possible Solution

Keep this issue as the canonical maintainer design tracker for managed/internal hook tool-call interception; a complete solution should either define safe typed before/after managed tool events with blocking and params-rewrite semantics, ordering, failure policy, tests, and docs, or explicitly reject unsupported HOOK.md tool events and keep enforcement plugin-only.

## Reproduction Assessment

Yes. Source inspection shows a high-confidence path: managed HOOK.md events register only into the internal hook registry, whose handler type returns void and whose dispatcher is not called by before_tool_call or after_tool_call tool execution paths.

## Solution Assessment

No, this is not a safe automatic bug-fix lane. The maintainable solution needs a maintainer API/security decision about whether managed hooks should gain plugin-like pre-execution authority, and if so how ordering, blocking, failure policy, docs, and tests line up with the existing plugin hook contract.

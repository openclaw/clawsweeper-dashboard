## Summary

Keep open. Current main and v2026.6.11 still keep enforceable tool-call policy in typed plugin hooks, while managed/internal HOOK.md hooks have no tool-call event type, no blocking or parameter-rewrite return contract, and no tool execution bridge.

## What This Changes

The issue requests exposing before_tool_call and after_tool_call semantics through managed/internal HOOK.md hooks so they can block, rewrite, and observe tool calls without building a full plugin.

## Best Possible Solution

Keep this as the canonical design tracker: either add typed managed/internal before and after tool-call events with block, parameter rewrite, after-call observation, unsupported-event validation, docs, and focused tests, or explicitly keep tool-call policy plugin-only and surface unsupported HOOK.md event names.

## Reproduction Assessment

Yes, at source level. A managed HOOK.md before_tool_call handler would register in the internal hook registry, while current before/after tool execution consults the plugin hook runner and the internal dispatcher cannot return block or parameter decisions.

## Solution Assessment

Unclear as a direct bridge. The maintainable solution needs a typed contract or an explicit plugin-only boundary, because the requested behavior changes a security-sensitive tool policy surface.

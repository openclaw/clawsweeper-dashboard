## Summary

Keep open. Current main and v2026.6.11 still expose enforceable before/after tool-call interception through typed plugin hooks only; managed HOOK.md internal hooks remain void-returning events with no tool-call dispatch, blocking contract, or parameter-rewrite contract.

## What This Changes

Request to expose before_tool_call and after_tool_call behavior through the managed internal HOOK.md hooks system.

## Best Possible Solution

Keep this as the canonical design tracker: either add typed managed/internal before and after tool-call events with blocking, parameter rewrite, after-call observation, unsupported-event validation, docs, and focused tests, or explicitly keep tool-call policy plugin-only and surface unsupported HOOK.md event names.

## Reproduction Assessment

Yes, at source level. A HOOK.md before_tool_call handler would register into the internal hook registry, while current before/after tool execution consults the plugin hook runner and the internal dispatcher cannot return block or parameter decisions.

## Solution Assessment

Unclear as an implementation shape, but keeping this issue open is the right triage outcome. The best fix needs maintainer decisions about event names, trust model, return semantics, unsupported-event validation, and double-firing avoidance.

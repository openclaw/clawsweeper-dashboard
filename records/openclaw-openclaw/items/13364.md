## Summary

Keep open. Current main and v2026.6.11 still keep enforceable before/after tool-call behavior in typed plugin hooks, while managed HOOK.md internal hooks have no tool-call event type, no blocking or parameter-rewrite return contract, and no bridge from tool execution.

## What This Changes

Expose existing plugin before_tool_call and after_tool_call behavior to managed internal HOOK.md handlers so they can observe, rewrite, or block tool calls.

## Best Possible Solution

Keep this as the canonical design tracker: either add typed managed/internal before and after tool-call events with block, parameter rewrite, after-call observation, unsupported-event validation, docs, and focused tests, or explicitly keep tool-call policy plugin-only and surface unsupported HOOK.md event names.

## Reproduction Assessment

Yes, at source level. A managed HOOK.md handler can register an event string, but the current internal dispatcher returns void and the before/after tool paths consult plugin hooks rather than managed internal hooks.

## Solution Assessment

Unclear as an implementation shape; the issue should stay open until maintainers choose the managed-hook API, trust model, event names, return semantics, and unsupported-event behavior.

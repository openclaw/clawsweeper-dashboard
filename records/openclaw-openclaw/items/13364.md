## Summary

Keep open. Current main still keeps enforceable before/after tool-call interception in typed plugin hooks, while managed HOOK.md internal hooks remain a void-returning command/session/agent/gateway/message automation surface; the remaining work is a security-sensitive API/product decision, not an already-implemented cleanup item.

## What This Changes

Request to expose existing plugin before_tool_call and after_tool_call hooks through managed internal HOOK.md hooks with blocking and parameter rewrite semantics.

## Best Possible Solution

Decide the managed-hook contract first: either add typed before/after internal tool-call events with explicit block/rewrite, timeout, validation, docs, and cross-tool-path coverage, or document and enforce that runtime tool policy remains plugin-only.

- **Expose observe-only internal events:** Allow after-tool or telemetry-style HOOK.md events while leaving pre-execution blocking and parameter rewriting in plugin hooks.

## Reproduction Assessment

Yes, at source level: current main has no internal tool-call event type or non-void return contract, and tool execution calls plugin hook runners rather than triggerInternalHook. A live HOOK.md repro was not needed for this read-only review because the source contract directly shows the gap.

## Solution Assessment

Unclear as a final product direction. Bridging the existing plugin hooks is plausible, but the best fix depends on whether maintainers want HOOK.md hooks to become a synchronous security policy surface or remain operator automation only.

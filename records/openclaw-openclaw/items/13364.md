## Summary

Keep open. Current main and v2026.6.11 still route enforceable before/after tool-call policy through typed plugin hooks, while managed HOOK.md internal hooks remain a void-returning command/session/agent/gateway/message event system with no tool-call bridge.

## What This Changes

Requests exposing before_tool_call and after_tool_call through managed/internal HOOK.md hooks so handlers can observe, block, or rewrite tool calls without full plugin packaging.

## Best Possible Solution

Keep this as the canonical design tracker: either add typed managed/internal before and after tool-call events with blocking, parameter rewrite, after-call observation, unsupported-event validation, docs, and focused tests, or explicitly keep tool-call policy plugin-only and surface unsupported HOOK.md event names.

## Reproduction Assessment

Yes, at source level. A HOOK.md event string can be registered into the internal hook map, but current tool execution consults the plugin hook runner and the internal dispatcher returns void.

## Solution Assessment

Unclear as a literal implementation sketch. The issue is the right canonical tracker, but maintainers still need to choose event names, return semantics, trust/failure policy, and whether this should remain plugin-only.

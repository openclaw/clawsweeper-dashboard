## Summary

Keep open. Current main and the latest release still keep managed HOOK.md hooks on the void-returning internal hook registry, while enforceable before/after tool-call policy remains in typed plugin hooks; the merged local-extension registry fix at https://github.com/openclaw/openclaw/pull/92016 does not add the managed HOOK.md tool-call contract requested here.

## What This Changes

Expose before_tool_call and after_tool_call tool lifecycle events through managed/internal HOOK.md hooks with before-call blocking or parameter rewrite support.

## Best Possible Solution

Keep this as the canonical design tracker until maintainers either add typed managed HOOK.md before/after tool-call events with block, rewrite, observation, validation, docs, and focused tests, or explicitly keep enforceable tool policy plugin-only and warn or reject unsupported managed event names.

Rationale: The source gap is clear, but granting managed hooks pre-tool execution authority changes OpenClaw's trusted local-code, plugin API, ordering, timeout, failure, and compatibility boundaries.

Likely owner: steipete

Owner confidence: high

Options:

- **Design managed tool-call hooks (recommended):** Add typed managed/internal before and after tool-call events that compose with plugin hooks, trusted policies, and all supported tool execution paths, with focused tests and public docs.
- **Keep policy plugin-only:** Reject or warn on before_tool_call and after_tool_call in HOOK.md metadata and point users to typed plugin hooks or ClawHub-packaged code plugins for enforceable tool policy.
- **Expose telemetry only:** Expose non-blocking after-call observation for managed hooks while keeping pre-tool blocking and parameter rewrites in the typed plugin contract.

## Reproduction Assessment

Yes, at source level. HOOK.md events register as internal hook strings, InternalHookHandler returns void, and the before/after tool execution paths consult typed plugin hooks rather than managed internal hooks.

## Solution Assessment

Unclear as an implementation shape. The requested capability is valid, but the best fix depends on whether maintainers want managed hooks to gain policy semantics or want unsupported tool-call event names rejected with plugin-hook guidance.

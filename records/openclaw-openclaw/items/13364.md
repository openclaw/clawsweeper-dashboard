## Summary

Keep open. Current main and the latest release still keep managed HOOK.md hooks on the void-returning internal hook registry, while enforceable before/after tool-call policy remains in typed plugin hooks; this remains the canonical security-sensitive API/product decision rather than a cleanup close.

## What This Changes

The issue requests exposing before/after tool-call interception through managed internal HOOK.md hooks so handlers can block, rewrite, or audit tool operations without packaging a full plugin.

## Best Possible Solution

Keep this issue as the canonical design tracker until maintainers either add a typed managed HOOK.md tool-call contract with block/rewrite/observe semantics, validation, docs, and tests, or explicitly keep tool-call policy plugin-only and reject or warn on unsupported managed hook event names.

## Maintainer Decision

Required: true

Question: Should managed HOOK.md hooks be allowed to block or rewrite tool calls, or should enforceable tool-call policy remain typed-plugin-only with clear validation for unsupported HOOK.md event names?

Rationale: The source gap is clear, but granting managed hooks pre-tool execution authority changes OpenClaw's trusted local-code, plugin API, ordering, timeout, failure, and compatibility boundaries.

Likely owner: steipete

Owner reason: steipete is tied to the original internal hook surface and already provided canonical-tracker signal in the issue discussion.

Owner confidence: high

Options:

- **Design managed tool-call hooks (recommended):** Add typed managed/internal before and after tool-call events that compose with plugin hooks, trusted policies, and all supported tool execution paths, with focused tests and public docs.
- **Keep plugin-only policy:** Reject or warn on before_tool_call and after_tool_call in HOOK.md metadata and point users to typed plugin hooks or ClawHub-packaged code plugins for enforceable tool policy.
- **Expose telemetry only:** Expose non-blocking after-call observation for managed hooks while keeping pre-tool blocking and parameter rewrites in the typed plugin contract.

## Reproduction Assessment

Yes, source-level. HOOK.md events are registered as internal hook strings, but InternalHookHandler returns void and the before/after tool execution paths consult plugin hooks rather than managed internal hooks.

## Solution Assessment

Unclear as an implementation shape. The requested capability is valid, but the best fix depends on whether maintainers want managed hooks to gain policy semantics or want unsupported tool-call event names rejected with plugin-hook guidance.

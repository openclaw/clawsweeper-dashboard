## Summary

Keep open. Current main and v2026.6.11 still keep enforceable before/after tool-call policy in typed plugin hooks, while managed HOOK.md/internal hooks remain a void-returning command/lifecycle automation surface; the existing maintainer discussion also keeps this as the canonical tracker.

## What This Changes

The issue requests exposing before_tool_call and after_tool_call through managed/internal HOOK.md hooks so simpler hook handlers can observe, rewrite, or block tool operations without packaging a full plugin.

## Best Possible Solution

Keep this as the canonical design tracker until maintainers either add a typed managed HOOK.md tool-call contract with block/rewrite/observe semantics, validation, docs, and tests, or explicitly keep tool-call policy plugin-only and reject or warn on unsupported managed hook event names.

Options:

- **Design managed tool-call hooks (recommended):** Add a typed managed/internal before and after tool-call API that composes with plugin hooks, trusted policies, and all tool execution surfaces, with focused tests and public docs.
- **Keep policy plugin-only:** Reject or warn on before_tool_call and after_tool_call in HOOK.md metadata, and point users to typed plugin hooks or ClawHub-packaged code plugins for enforceable tool policy.
- **Expose telemetry only:** Expose non-blocking after-call or observation-only tool events to managed hooks while keeping pre-tool blocking and parameter rewrites in the typed plugin contract.

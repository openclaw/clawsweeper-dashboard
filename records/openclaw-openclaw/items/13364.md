## Summary

Keep open. Current main and v2026.6.11 still keep enforceable before/after tool-call behavior in typed plugin hooks, while managed/internal HOOK.md hooks lack a tool-call event type, blocking or parameter-rewrite return contract, and a tool execution bridge.

## What This Changes

Expose existing plugin before_tool_call/after_tool_call behavior through managed/internal HOOK.md hooks so operators can block, rewrite, and audit tool calls without packaging a plugin.

## Best Possible Solution

Keep this as the canonical design tracker: either add typed managed/internal before and after tool-call events with block, parameter rewrite, after-call observation, unsupported-event validation, docs, and focused tests, or explicitly keep tool-call policy plugin-only and surface unsupported HOOK.md event names clearly.

## Reproduction Assessment

Yes, at source level. A managed HOOK.md before_tool_call handler would register in the internal hook registry, while current before/after tool execution consults the plugin hook runner and the internal dispatcher cannot return block or parameter decisions.

## Solution Assessment

Unclear as a direct bridge. The maintainable solution needs a typed, security-reviewed managed hook contract or an explicit plugin-only boundary, because the requested behavior changes a sensitive tool policy surface.

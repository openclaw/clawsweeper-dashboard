## Summary

Keep open. Current main and v2026.6.11 still route enforceable tool-call interception through typed plugin hooks, while managed HOOK.md internal hooks remain void-returning command/lifecycle events with no before/after tool-call bridge; the related closed PRs cover only partial or unmerged attempts.

## What This Changes

Expose before_tool_call and after_tool_call behavior through managed HOOK.md internal hooks so simple hooks can observe, rewrite, or block tool operations.

## Best Possible Solution

Keep this as the canonical design tracker: either add typed managed/internal before and after tool-call events with block, parameter rewrite, after-call observation, unsupported-event validation, docs, and focused tests, or explicitly keep tool-call policy plugin-only and surface unsupported HOOK.md event names.

## Reproduction Assessment

Yes, at source level. A managed HOOK.md handler can register an event string, but the current internal dispatcher returns void and the before/after tool paths consult plugin hooks rather than managed internal hooks.

## Solution Assessment

Unclear as an implementation shape, but keeping this issue open is the right triage result. The best fix needs maintainer decisions about event names, trust model, return semantics, unsupported-event validation, and double-firing avoidance.

## Summary

Keep open. Current main and v2026.6.11 still keep enforceable before/after tool-call behavior in typed plugin hooks, while managed HOOK.md internal hooks have no tool-call event type, no blocking or parameter-rewrite return contract, and no bridge from tool execution.

## What This Changes

The issue requests exposing before_tool_call and after_tool_call behavior through managed internal HOOK.md hooks so local hook handlers can block, rewrite, and observe tool calls without a full plugin.

## Best Possible Solution

Keep this as the canonical design tracker: either add typed managed/internal before and after tool-call events with block, parameter rewrite, after-call observation, unsupported-event validation, docs, and focused tests, or explicitly keep tool-call policy plugin-only and reject unsupported HOOK.md event names.

## Reproduction Assessment

Yes, at source level. A HOOK.md before_tool_call handler registers into the internal hook registry, while current before/after tool execution consults the plugin hook runner and the internal dispatcher cannot return block or parameter decisions.

## Solution Assessment

Unclear as an implementation shape; the issue should stay open until maintainers choose the managed-hook API, trust model, event names, return semantics, and unsupported-event behavior.

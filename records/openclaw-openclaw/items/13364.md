## Summary

Keep open. Current main and the latest release still route enforceable before/after tool-call behavior through typed plugin hooks, while managed/internal HOOK.md hooks remain a void-returning command/lifecycle system with no tool-call event, no block or parameter-rewrite contract, and no bridge from tool execution. Related reports and an open maintainer PR overlap, but no merged current-main path implements the requested managed-hook policy surface.

## What This Changes

The issue requests exposing before_tool_call and after_tool_call interception through managed internal HOOK.md hooks so handlers can observe, rewrite, or block tool operations without packaging a full plugin.

## Best Possible Solution

Keep this as the canonical design tracker: either add typed managed/internal before and after tool-call events with block, parameter rewrite, after-call observation, unsupported-event validation, docs, and focused tests, or explicitly keep tool-call policy plugin-only and surface unsupported HOOK.md event names clearly.

## Reproduction Assessment

Yes, at source level. A managed HOOK.md before_tool_call handler registers into the internal hook registry, while current before/after tool execution consults the plugin hook runner and the internal dispatcher cannot return block or parameter decisions.

## Solution Assessment

Unclear as a final implementation shape, but keeping this issue open is the right triage outcome. The best fix needs maintainer decisions about event names, trust model, return semantics, unsupported-event validation, and double-firing avoidance.

## Summary

Keep open. Current main and v2026.6.11 still do not expose enforceable before/after tool-call events through managed HOOK.md hooks; typed plugin hooks remain the supported policy surface, and this needs maintainer API/security direction.

## What This Changes

Request to expose existing before_tool_call and after_tool_call plugin hook behavior through managed/internal HOOK.md hooks so hooks can block, rewrite, and observe tool execution.

## Best Possible Solution

Keep this as the canonical design tracker until maintainers either add a typed managed HOOK.md tool-call contract with block/rewrite/observe semantics, validation, docs, and tests, or explicitly keep tool-call policy plugin-only and surface unsupported managed hook event names.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should managed HOOK.md hooks be allowed to block or rewrite tool calls, or should tool-call policy remain typed-plugin-only with clear validation for unsupported HOOK.md event names?

Rationale: The source gap is clear, but exposing pre-tool execution to managed hooks changes OpenClaw's security and plugin API boundary; automation cannot choose trust, ordering, timeout, failure, and compatibility semantics safely.

Likely owner: steipete

Owner reason: steipete is tied to the original internal hook surface and already provided maintainer signal on this canonical tracker.

Owner confidence: high

Options:

- **Design managed tool-call hooks (recommended):** Add a typed managed/internal before and after tool-call API that composes with plugin hooks, trusted policies, and all tool execution surfaces, with focused tests and public docs.
- **Keep plugin-only policy:** Reject or warn on before_tool_call and after_tool_call in HOOK.md metadata, and point users to typed plugin hooks or ClawHub-packaged code plugins for enforceable tool policy.
- **Expose telemetry only:** Expose non-blocking after-call or observation-only tool events to managed hooks while keeping pre-tool blocking and parameter rewrites in the typed plugin contract.

## Reproduction Assessment

Yes, at source level. A managed HOOK.md handler can register an event string, but current internal hooks return void and current before/after tool paths consult plugin hooks rather than managed internal hooks.

## Solution Assessment

Unclear as an implementation shape. The requested capability is valid, but the best fix depends on whether maintainers want managed hooks to gain policy semantics or want unsupported tool-call event names rejected with plugin-hook guidance.

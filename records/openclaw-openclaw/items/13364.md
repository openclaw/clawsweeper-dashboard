## Summary

Keep open. Current main and the latest release still keep managed HOOK.md handlers on the void-returning internal hook registry, while enforceable before/after tool-call policy remains in typed plugin hooks; this is still the canonical security-sensitive API/product decision.

## What This Changes

Request to expose existing before_tool_call and after_tool_call plugin-hook behavior through managed internal HOOK.md hooks so handlers can block, rewrite, or audit tool execution.

## Best Possible Solution

Keep this as the canonical design tracker until maintainers either add a typed managed HOOK.md before/after tool-call contract with block, rewrite, observe, validation, docs, and tests, or explicitly keep tool-call policy plugin-only and reject or warn on unsupported managed hook event names.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should managed HOOK.md hooks be allowed to block or rewrite tool calls, or should enforceable tool-call policy remain typed-plugin-only with clear validation for unsupported managed hook event names?

Rationale: Source inspection proves the gap, but granting managed hooks pre-tool execution authority changes OpenClaw's local-code trust, plugin API, ordering, timeout, failure, and compatibility boundaries.

Likely owner: steipete

Owner reason: steipete is tied to the original internal hook surface and already provided canonical-tracker signal in the issue discussion.

Owner confidence: high

Options:

- **Design managed tool-call hooks (recommended):** Add typed managed/internal before and after tool-call events that compose with plugin hooks, trusted policies, and supported tool execution paths, with focused tests and public docs.
- **Keep plugin-only policy:** Reject or warn on before_tool_call and after_tool_call in HOOK.md metadata and point users to typed plugin hooks or ClawHub-packaged code plugins for enforceable tool policy.
- **Expose telemetry only:** Expose non-blocking after-call observation for managed hooks while keeping pre-tool blocking and parameter rewrites in the typed plugin contract.

## Reproduction Assessment

Yes, source-level. HOOK.md events are registered as internal hook strings, but InternalHookHandler returns void and the before/after tool execution paths consult plugin hooks rather than managed internal hooks.

## Solution Assessment

Unclear as an implementation shape. The capability is valid, but the best fix depends on whether maintainers want managed hooks to gain policy semantics or want unsupported tool-call event names rejected with plugin-hook guidance.

## Summary

Keep open for an explicit maintainer product decision. Current main deliberately separates coarse, side-effect-oriented managed hooks from typed plugin middleware with blocking and mutation semantics; the existing plugin path supports the reported policies, but it does not provide the requested `HOOK.md` ergonomics, and the discussion has substantial independent demand plus prior maintainer signal to retain this as the canonical tracker.

## What This Changes

Expose blocking and observational tool-call lifecycle events to managed `HOOK.md` internal hooks.

## Best Possible Solution

Choose one canonical policy surface: preferably retain typed plugin hooks for blocking and mutation, keep managed hooks side-effect-only with strict event validation, and support reusable file-gate or command-policy implementations as installable ClawHub plugins; only add a managed bridge if maintainers explicitly define identical ordering, approval, timeout, mutation, and failure semantics.

Rationale: Both directions are technically possible, but the choice changes a security-sensitive extension boundary and cannot be safely inferred from community demand alone; current documentation favors typed plugins while prior discussion retained this issue for an explicit decision.

Options:

- **Preserve the typed-plugin boundary (recommended):** Keep managed hooks side-effect-only, reject unsupported tool-policy event declarations clearly, and direct reusable enforcement policies to installable ClawHub plugins.
- **Design a managed policy bridge:** Specify and implement managed before/after tool events with plugin-equivalent ordering, blocking, parameter mutation, approval, timeout, failure, and cross-runtime coverage guarantees.

## Reproduction Assessment

Not applicable as a runtime bug, but the capability gap is source-reproducible with high confidence: managed hooks lack tool-call events and decision-return semantics while typed plugin hooks provide them.

## Solution Assessment

Unclear pending product direction. A direct bridge is plausible but is not automatically the best fix because it duplicates a security-sensitive typed plugin contract; preserving one policy surface plus better validation and ClawHub packaging is the safer default.

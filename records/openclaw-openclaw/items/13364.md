## Summary

Current main and v2026.6.11 still keep enforceable before/after tool-call behavior in typed plugin hooks, while managed HOOK.md internal hooks have no tool-call event family, no blocking or parameter-rewrite return contract, and no bridge from tool execution. Keep this open as the canonical maintainer design item because the source gap is clear but the fix changes a security-sensitive hook/API boundary.

## What This Changes

Request exposing before_tool_call and after_tool_call through the managed/internal HOOK.md hooks system so internal hooks can observe, block, or rewrite tool calls without packaging a full plugin.

## Best Possible Solution

Keep this as the canonical design tracker: either add typed managed/internal before and after tool-call events with block, parameter rewrite, after-call observation, unsupported-event validation, docs, and focused tests, or explicitly keep tool-call policy plugin-only and surface unsupported HOOK.md event names clearly.

## Reproduction Assessment

Yes, at source level. A managed HOOK.md before_tool_call handler would register into the internal hook registry, while current before/after tool execution consults the plugin hook runner and the internal dispatcher cannot return block or parameter decisions.

## Solution Assessment

Unclear as an implementation shape, but keeping this issue open is the right triage outcome. The best fix needs maintainer decisions about event names, trust model, return semantics, unsupported-event validation, and double-firing avoidance.

## Summary

Keep open. Current main still leaves managed HOOK.md hooks as a non-blocking internal automation surface while enforceable before/after tool-call interception remains in typed plugin and session-extension paths, so this canonical security-sensitive API decision is still unresolved.

## What This Changes

The issue requests exposing enforceable before/after tool-call events through managed internal HOOK.md hooks instead of requiring a full plugin.

## Best Possible Solution

Decide the managed-hook contract first: either add typed before/after tool-call internal events with explicit block, rewrite, timeout, validation, docs, and focused coverage across tool paths, or document that runtime tool policy remains plugin-only.

## Maintainer Decision

Rationale: The source gap is clear, but the requested fix changes the trusted-code boundary around shell, file, and plugin tool execution and could create a second policy API with different semantics from plugin hooks.

Likely owner: steipete

Owner confidence: high

Options:

- **Design managed tool-call hooks (recommended):** Add a typed managed before/after tool-call contract with explicit fail-open/fail-closed, timeout, block, rewrite, audit, docs, and test coverage before implementation.
- **Keep policy plugin-only:** Document that HOOK.md hooks are operator automation only, keep enforcement in typed plugin hooks, and surface unsupported tool lifecycle event names clearly in hooks info/loading.
- **Expose observe-only hooks:** Allow after-tool or telemetry-style HOOK.md observation while leaving pre-execution blocking and parameter rewriting in the plugin hook API.

Unclear as final product direction. Bridging the existing plugin hook semantics into managed hooks is plausible, but the best fix depends on whether maintainers want HOOK.md hooks to be a synchronous security policy surface or to stay as operator automation only.

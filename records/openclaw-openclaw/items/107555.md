## What This Changes

Fix QQ Bot direct-chat approval callbacks so a legitimate Allow click resolves the pending skill workshop approval instead of being rejected and timing out.

## Best Possible Solution

Authorize QQ approval callbacks by binding the actor, account, and conversation to the original approval delivery or configured owner, then add direct-public-DM, explicit-allowlist, wildcard, multi-actor, and group regressions plus redacted live QQ callback proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For QQ Bot C2C approval buttons, must authorization bind the callback actor to the original approval recipient or configured owner, or may direct-chat type alone grant approval authority?

Rationale: OpenClaw's documented open-DM mode permits any sender, so the linked PR's assumption that every C2C conversation is inherently owner-only cannot be accepted safely without an explicit authorization decision.

Likely owner: vincentkoc

Owner reason: Recent QQ Bot authorization hardening makes this the strongest available routing candidate for the security-boundary choice.

Owner confidence: medium

Options:

- **Bind callback identity (recommended):** Require the callback actor, QQ account, and C2C target to match the original approval recipient or configured owner before resolving the approval.
- **Require explicit approvers:** Keep command-style explicit authorization for all approval callbacks and improve setup or diagnostics for direct-chat users without an owner entry.
- **Trust direct chat type:** Allow every C2C callback to resolve approvals, accepting that public-DM configurations may grant approval authority to non-owner senders.

## Reproduction Assessment

Yes—source inspection and the release logs provide a high-confidence reproduction path: use a QQ C2C approval with no explicit non-wildcard command approver, click Allow, and observe command authorization reject the callback before the plugin approval expires. This review did not execute a live QQ callback.

## Solution Assessment

No—the linked PR's unconditional direct-chat bypass is not the safest fix because direct chat can be public. The narrow maintainable solution is request-recipient or owner identity binding with explicit group and public-DM coverage.

## Summary

Keep open with the linked PR: current main intentionally rejects implicit QQ approval callbacks unless the actor is explicitly command-authorized, so the reported rejection is source-reproducible but not yet an established button-mapping bug. Maintainers must decide whether C2C identity safely implies approval authority before relaxing this security boundary.

## What This Changes

Allow authorized QQ Bot direct-chat users to resolve skill_workshop approval prompts instead of having Allow actions rejected and expire.

## Best Possible Solution

Keep explicit authorization as the default and make direct-chat approvals work by binding the callback actor to a configured QQ approver or owner identity; add live redacted QQ callback proof plus tests for explicit allowlists, pairing, wildcard-open DMs, access groups, account defaults, and group chats.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should a QQ C2C approval callback grant authority solely because it came from a direct conversation, or must the callback actor still match an explicit approver or owner identity?

Rationale: Current behavior deliberately separates permission to DM the bot from permission to approve sensitive operations, while the linked PR would collapse those boundaries for every direct conversation.

Likely owner: steipete

Owner reason: They reviewed and merged the current authorization contract and carried the latest substantive fixups on this exact QQ approval path.

Owner confidence: high

Options:

- **Require explicit approval identity (recommended):** Keep the current fail-closed default and resolve C2C approvals only when the callback actor matches configured approvers, owner identity, or canonical command authorization.
- **Trust every C2C sender:** Accept all direct-conversation approval callbacks, including senders admitted by an open wildcard DM policy, and explicitly own the broader authorization boundary.
- **Add an opt-in C2C policy:** Preserve explicit authorization by default but introduce a documented QQ-specific setting for operators who intentionally trust all direct-message senders.

## Reproduction Assessment

Yes, at source level: an implicit QQ fallback callback with no explicit actor allowlist, or only a wildcard open-DM entry, reaches the command-authorization gate and is rejected. A live QQ run is still needed to validate callback identity and distinguish intentional authorization failure from a platform mapping defect.

## Solution Assessment

No. The linked PR is a plausible usability mitigation, but trusting every direct-conversation sender is not the best fix without proof that QQ C2C identity represents the configured owner; explicit approver or owner binding is safer and consistent with sibling approval surfaces.

## Summary

Keep this issue open while its paired pull request remains open. Current QQ Bot documentation shows that this rejection is the intended authorization behavior for wildcard or absent approver configuration, so the remaining question is whether direct-chat approvals should gain a narrower trusted-owner exception rather than whether the Allow button is decoded incorrectly. ([docs.openclaw.ai](https://docs.openclaw.ai/channels/qqbot))

## What This Changes

Change QQ Bot direct-chat approval handling so an intended Allow click can resolve a Skill Workshop approval instead of being rejected and timing out.

## Best Possible Solution

Keep explicit approver identity enforcement, acknowledge unauthorized button clicks with an in-chat explanation instead of a silent timeout, and provide a guided path to add the sender to `execApprovals.approvers`; if implicit C2C approval is desired, bind it to a verified owner identity rather than every direct sender.

## Solution Assessment

No. Unconditionally trusting every direct-chat sender is not the safest maintainable solution; preserve explicit approver identity or define a narrower verified-owner exception with positive and negative live proof.

## Summary

Keep this issue open with its paired pull request. The observed rejection is source-reproducible, but current QQ Bot behavior deliberately requires explicit actor authorization for fallback approval clicks; making every direct-conversation sender an implicit approver would change a security boundary and needs maintainer review rather than a second automated fix.

## What This Changes

Allow QQ Bot users in direct conversations to approve `skill_workshop` requests when their DM policy uses no explicit allowlist or a wildcard allowlist.

## Best Possible Solution

Preserve explicit approval authorization, then make QQ Bot direct approvals either bind to a verified configured or paired owner identity or fail fast with actionable in-product guidance instead of presenting an unusable button followed by a timeout.

- **Keep explicit approval authority (recommended):** Retain the current gate and improve the prompt, setup flow, or diagnostics so operators can configure an explicit approver without waiting for a timeout.
- **Bind verified owner identity:** Permit direct approvals only when the callback actor is proven to match a configured or paired owner identity, with focused security tests and live QQ proof.
- **Trust every C2C sender:** Accept the linked pull request's blanket direct-conversation bypass and explicitly own the resulting behavior under open DM policies.

Yes at source level: an open or wildcard QQ DM configuration produces no explicit approval actor, so the current fallback authorization branch rejects the callback and leaves the request to expire. A live QQ reproduction is still needed to validate platform identity assumptions.

## Solution Assessment

No. Unconditionally trusting every direct-conversation sender is broader than necessary and weakens an intentional authorization boundary; verified owner binding or clearer explicit-approver setup is safer.

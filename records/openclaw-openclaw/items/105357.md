## Summary

Keep this issue open. Current main still activates every direct-CDP screenshot target, which the official protocol defines as foregrounding the tab; this behavior was intentionally added on July 6, 2026, and is not in the latest stable release v2026.6.11. The adjacent open tab-creation PR does not address screenshots, while the remaining fix requires an explicit reliability-versus-focus decision for remote browsers whose actual headless mode is unknown.

## What This Changes

Avoid implicit tab activation during direct-CDP screenshots on headed browsers while retaining reliable capture for affected headless background tabs.

## Best Possible Solution

At the direct-CDP screenshot owner, use prepared profile mode for local managed browsers, define a deliberate default for unknown remote mode, and add dual-mode real-browser proof plus focused tests; never retry a timed-out capture on the same socket.

Rationale: Known local managed mode can be handled deterministically, but current configuration cannot establish the actual mode of remote CDP or existing-session browsers; either default has a user-visible tradeoff.

Likely owner: steipete

Owner confidence: high

Options:

- **Preserve focus by default (recommended):** Activate only for known-headless local managed sessions, and capture without activation for unknown remote mode unless capability metadata later proves activation is needed.
- **Preserve reliability by default:** Skip activation only for known-headed local managed sessions while retaining activation-first capture for unknown remote mode.
- **Capture-first recovery:** Capture without activation everywhere, then reconnect, activate, and retry only after the exact screenshot timeout within a defined total timeout budget.

## Reproduction Assessment

Yes, source-reproducible with high confidence: current main always calls the official CDP tab-activation command before direct-CDP capture. A headed two-tab run is the concrete live path; platform-specific window raising still needs behavioral proof.

## Solution Assessment

The issue targets the correct owner boundary, but its same-socket retry suggestion is unsafe because timeout closes the connection. The best fix uses prepared mode facts where authoritative and requires a maintainer choice for unknown remote mode.

## Summary

Keep open: this is a focused bug-fix PR, but it is not merge-ready because the new persistence path can still drop offline watch replies when no current gateway ID is held, native i18n/format checks fail, and the PR has no real iOS/watch behavior proof.

## What This Changes

The PR persists iOS watch quick replies in a UserDefaults-backed queue scoped by gateway stable ID, changes agent request forwarding to confirmed `node.event` requests, and adds Swift coverage for queue restore behavior.

## Best Possible Solution

Persist replies with a durable gateway owner that survives the offline window, preserve stale-gateway protection, refresh native i18n/SwiftFormat output, and require redacted real iOS/watch offline-restart proof before merge.

## Reproduction Assessment

Yes from source inspection: current main stores queued replies only in memory, and the PR path can still be source-reproduced by delivering a quick reply while `gatewayConnected` is false and `connectedGatewayID` has been cleared. I did not run a real iOS/watch device scenario.

## Solution Assessment

No: the persisted queue direction is reasonable, but using `connectedGatewayID` alone is too narrow for the offline/cold-start states the PR is meant to fix. The safer fix is to carry or recover a durable gateway owner before dropping the reply.

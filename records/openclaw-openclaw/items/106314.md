## Summary

The bind-error buffering and close-based stderr drain are well supported, but the previously reported spawn-error regression remains on the unchanged reviewed head: failed spawns also emit `close`, so they now enter the five-second restart path.

## What This Changes

Buffers Gmail watcher stderr across chunks, classifies bind errors before tail truncation, and moves restart decisions from child `exit` to `close`.

## Best Possible Solution

Retain close-based classification for successfully spawned children, but track spawn success or spawn failure and prevent the restart handler from scheduling retries after a failed spawn; cover the `error` followed by `close` sequence with a focused regression test.

Yes. The PR provides a real occupied-port run through `startGmailWatcher` and deterministic child-process sequencing for split and post-exit stderr; the remaining spawn-error regression is source-reproducible from Node's documented `error` then `close` ordering.

## Solution Assessment

No, not yet. Waiting for `close` is the correct way to see drained stderr, but the restart policy must distinguish a successfully spawned child from process-creation failure before this is the best fix.

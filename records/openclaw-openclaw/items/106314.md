## Label Justifications

- `P2`: This is a valid, limited-blast-radius reliability bug in the optional Gmail watcher, but the proposed fix remains incomplete and lacks live proof.

## Summary

The reported bug remains worth fixing, but this patch does not fully establish that the bind diagnostic is consumed before restart policy runs: Node permits `exit` to fire while stderr is still open, so a final marker chunk can still arrive after the watcher schedules another spawn. The external PR also provides mocked emitter coverage only and explicitly leaves the real occupied-port path unverified.

## What This Changes

The PR carries a bounded stderr tail across Gmail watcher chunks so split address-in-use errors stop respawns, with two regression tests.

## Best Possible Solution

Keep the bounded stderr classification, but make the restart decision only after child stdio has closed, add a regression case where `exit` precedes the final stderr fragment and `close`, and show a redacted live occupied-port run that stops without respawning.

Required: false

## Reproduction Assessment

Yes at source level: current behavior classifies stderr chunks independently, and splitting the bind marker leaves `addressInUse` false before restart scheduling. The PR's test demonstrates that path, though no live `gog` run was performed.

## Solution Assessment

No. Carrying a bounded tail fixes adjacent chunk matching, but restart policy should run on `close` or another stderr-drained boundary because `exit` does not guarantee all stderr data has arrived.

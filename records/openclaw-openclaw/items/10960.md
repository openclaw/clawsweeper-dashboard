## Summary

Keep this issue open: current main and v2026.7.1 intentionally provide capability-dependent steering at safe boundaries, not the requested transparent abort, immediate context injection, and context-aware continuation lifecycle; the linked implementation work addresses only part of that gap and still requires maintainer product direction.

## What This Changes

Add true mid-generation soft steering that interrupts an active generation, incorporates new user input, and continues with preserved context.

## Best Possible Solution

Define one capability-aware runtime contract that uses native same-turn steering where supported, preserves safe tool-boundary steering elsewhere, and exposes a separate explicit interrupt-and-restart path only after transcript, partial-output, tool-cancellation, fallback, and delivery semantics are documented and tested.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw promise transparent abort, message injection, and continuation for harnesses that lack native same-turn steering, or keep steering capability-dependent and expose interruption as a separate operation?

Rationale: Source and upstream contracts establish multiple technically valid semantics, but choosing whether OpenClaw should emulate transparent continuation changes user expectations, transcript meaning, tool-side-effect handling, and shared runtime policy.

Likely owner: steipete

Owner reason: They introduced the current user-facing steering command and documentation and have already reviewed the distinction between boundary steering and transparent continuation.

Owner confidence: high

Options:

- **Capability-aware steering (recommended):** Use native same-turn steering where a harness supports it, retain boundary steering for Pi-style runtimes, and design explicit interruption separately with defined state semantics.
- **Emulate soft continuation:** Abort unsupported active generations, persist partial output and tool state, append the new user message, and restart under a cross-runtime continuation contract.
- **Keep boundary semantics:** Retain the current documented behavior and close this feature direction without adding transparent abort-and-resume emulation.

## Reproduction Assessment

Yes at the source-contract level: current documentation states that Pi steering is consumed between tool calls and does not interrupt a tool already in flight, so sending corrective input during that phase demonstrates the requested capability gap. This is an intentional feature boundary rather than a reproduced bug.

## Solution Assessment

No, the issue's hypothesized generic abort, partial-output capture, and resume mechanism is not yet the safest shared solution. A capability-aware contract separating native steering from explicit interruption avoids pretending that every harness can provide equivalent continuation semantics.

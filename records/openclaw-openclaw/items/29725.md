## Summary

Keep open: current main and v2026.6.11 still lack the requested `api.runtime.channel.discord.updatePresence` plugin runtime API. Existing Discord support covers static config, auto-presence, and a gated `setPresence` message action, but exposing presence mutation to plugins remains a public API and bot-credential security-boundary decision.

## What This Changes

The issue requests a plugin runtime method that lets Discord plugins update bot presence dynamically without a restart.

## Best Possible Solution

Approve or reject a narrow Discord-owned plugin-runtime presence contract that reuses the existing gateway presence path through an explicit gate, account scope, docs, tests, and precedence rules.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose Discord bot presence mutation to plugins as a public runtime API, and what gate, account scoping, and precedence model should it use?

Rationale: The internal gateway path exists, but promoting it to plugin runtime changes the public plugin contract and exposes a Discord bot-credential-backed mutation boundary to plugin code.

Likely owner: Peter Steinberger

Owner reason: The unresolved choice is primarily a public plugin-runtime API and security-boundary decision, and the plugin runtime contract history points to this boundary.

Owner confidence: medium

Options:

- **Design a gated runtime API (recommended):** Add a narrow Discord-owned `updatePresence`-style runtime seam with explicit gating, account selection, docs, tests, and precedence rules.
- **Keep presence as message action only:** Leave dynamic presence mutation on the existing default-off `setPresence` message action and document that plugins should not mutate Discord presence directly.
- **Fold into self-profile direction:** Defer this request behind https://github.com/openclaw/openclaw/issues/34004 if maintainers want one Discord identity/profile API instead of a separate presence-only runtime API.

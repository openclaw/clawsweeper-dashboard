## Summary

Keep open: current main and the latest release still load Dashboard history through the stored session row, while the shipped orphan-key migration only canonicalizes key names and does not prove or repair a Dashboard key whose stored `sessionId` points at the wrong preserved transcript. The related transcript-header identity issue is useful adjacent work, but it is not a duplicate fix for this already-corrupted mapping case.

## What This Changes

The issue reports that after upgrade, some Dashboard history keys in `sessions.json` can point to the wrong sessionId, so opening an old Dashboard entry loads the wrong preserved conversation.

## Best Possible Solution

Add a maintainer-approved doctor or migration repair that can prove a Dashboard key belongs to a preserved transcript before rewriting `sessions.json`, using explicit transcript identity metadata when available and otherwise surfacing candidates without guessing.

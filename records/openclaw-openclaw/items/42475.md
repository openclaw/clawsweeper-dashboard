## Summary

Keep open: current main and the latest stable release still provide cost reporting, provider usage visibility, and plugin run-block hooks, but not native per-agent spend caps, durable budget reservations, or synchronous gateway model-call admission enforcement.

## What This Changes

The issue requests optional per-agent daily/monthly spend caps enforced before gateway model dispatch.

## Best Possible Solution

Maintainers should define the boundary first: either a core gateway budget/reservation feature with SQLite-backed per-agent counters and status/doctor UX, or a blocking plugin/API seam with enough pre-call estimate and receipt data.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should per-agent spend limits be a native core gateway feature, a new blocking plugin/API seam, or deferred to external/provider budget controls?

Rationale: The fix adds config/defaults, provider dispatch admission policy, durable accounting semantics, and operator UX; automation cannot safely choose the product boundary or upgrade contract.

Likely owner: steipete

Owner reason: They have the strongest recent history on cost/usage visibility and related product-scoping discussions for outbound governance.

Owner confidence: medium

Options:

- **Design native gateway budgets (recommended):** Define a default-unlimited core budget contract with reservations, receipts, status/doctor output, and upgrade-safe config before implementation.
- **Expose blocking plugin/API admission:** Keep budget policy outside core but add the missing synchronous pre-model-call estimate/reservation hook needed for reliable external enforcement.
- **Defer to external/provider controls:** Document provider dashboards, proxies, and per-account approaches as the supported path and close or narrow this issue to missing extension APIs only.

## Reproduction Assessment

Yes, at source level: current config schemas have no spend-budget field, usage.cost is reporting-only, and the model_call_started hook is observation-only rather than a blocking admission point.

## Solution Assessment

Unclear until maintainers choose the product boundary; gateway admission is plausible, but the proposed daily/monthly block/warn/pause shape needs design for reservations, unknown pricing, concurrency, and plugin/core ownership.

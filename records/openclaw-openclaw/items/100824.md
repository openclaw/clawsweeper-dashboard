## Summary

Keep open: the report is fresh, plausible, and overlaps known fallback visibility work, but current main still lacks live or source-level proof that cross-provider fallback attempts preserve the same user-visible long-task progress as primary attempts.

## What This Changes

The issue reports missing or unreliable intermediate progress messages when a long task runs on a secondary fallback model after the primary model becomes unavailable.

## Best Possible Solution

Define the shared fallback-attempt progress contract, then add regression and live proof for a primary failure followed by a successful fallback that emits channel-visible execution, tool, item, commentary, heartbeat, and subagent progress.

Question: Should OpenClaw guarantee channel-visible intermediate progress parity across model fallback candidates, including cross-provider fallbacks with different streaming and tool-progress behavior?

Rationale: The code has multiple progress surfaces and related fallback visibility reports point in different directions, so automation should not choose the user-visible audience or parity contract on its own.

Owner confidence: high

Options:

- **Guarantee parity in core (recommended):** Treat fallback attempts as the same user-visible progress contract as primary attempts and fix the shared progress plumbing with source and live proof.
- **Document degraded fallback progress:** Guarantee only final delivery and explicit fallback notices when a provider or runtime cannot support equivalent intermediate progress.
- **Fold into durable status work:** Keep this as a symptom under broader durable channel status and fallback delivery semantics instead of adding a narrower progress repair now.

## Label Justifications

- `P0`: The affected updater path can fetch, execute, build, and install code controlled by an untrusted directory, which is a security-boundary bypass in a core update workflow.
- `merge-risk: 🚨 compatibility`: The new all-remotes rule deliberately makes package-to-dev conversion fail when the default Git path contains a personal fork or any additional noncanonical remote.
- `merge-risk: 🚨 security-boundary`: The patch codifies canonical remote URLs as an acceptance condition even though hostile Git config, refs, refspecs, objects, and local commits can still control execution and the selected build.

## Summary

Keep this PR open but do not merge it in its current form: the URL check is thoughtful and well-proven for foreign remotes, but a canonical remote URL does not establish that the checkout will fetch, resolve, or build canonical code. Maintainer direction is required on whether package-to-dev conversion may adopt any pre-existing checkout at all.

## What This Changes

The PR adds validation of every effective Git remote before reusing an existing checkout for a package installation switching to the dev update channel, with focused real-Git regression tests.

## Best Possible Solution

For package-to-dev conversion, build from a fresh OpenClaw-owned clone or fetch the canonical repository and exact ref into a clean repository using sanitized Git configuration; treat reuse of an arbitrary existing checkout as an explicit developer workflow rather than a security-validated path.

## Summary

This PR addresses a real current-main hang, but it is not ready to merge: it adds a second remote-media timeout lifecycle beside the canonical guarded fetch/save path, and its failure settlement can remove a partial file before the destination stream closes. The local-server regression is valuable, while standalone after-fix runtime proof is still required for this external contribution.

## What This Changes

The PR adds 30-second response-header and idle-body timeouts to `saveMediaSource()` remote downloads and adds real-socket Vitest coverage for header stalls, body stalls, successful completion, and temporary-file cleanup.

## Best Possible Solution

Consolidate remote URL persistence behind one guarded media-download lifecycle, preserving `saveMediaSource()` compatibility while sharing response-header bounds, idle reads, redirects, SSRF pinning, size enforcement, stream shutdown, and post-close partial-file cleanup.

- **[P1] Reuse the canonical guarded media download lifecycle:** `src/media/store.ts:34-37`
  - body: This adds a second implementation of response-header deadlines, idle reads, redirects, SSRF-pinned requests, errors, and cleanup even though `src/media/fetch.ts` already owns the guarded URL-to-store lifecycle through `saveRemoteMedia()`. Keeping both paths will drift in timeout and cleanup behavior; extract/share that lifecycle or route this caller through it while preserving the existing `saveMediaSource()` contract.
  - confidence: 0.9
- **[P2] Wait for the pipeline before removing the partial file:** `src/media/store.ts:301-309`
  - body: On timeout or request error, `settleReject` removes `dest` before `pipeline(res, out)` has necessarily closed the write stream, and the later pipeline rejection is ignored because `settled` is already true. Platforms with open-file unlink restrictions can therefore retain the partial file; abort the streams, await pipeline shutdown, and only then remove the destination.
  - confidence: 0.93

## Summary

Keep open: current main and latest stable still send the selected Bedrock runtime model id as the AWS `ConverseStreamCommand.modelId`; `params.modelId` remains ordinary provider params, and the supported Bedrock inference-profile identity contract is still unresolved.

## What This Changes

Support Amazon Bedrock Haiku 4.5 inference-profile identity by honoring a `params.modelId` override, full ARN model refs, or a provider alias instead of falling back away from Bedrock.

## Best Possible Solution

Choose one plugin-owned Bedrock wire-identity contract, implement it in the Bedrock provider path, document it, and verify with focused runtime/discovery/cron tests plus one live Bedrock Haiku 4.5 profile request.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Amazon Bedrock treat `agents.defaults.models[...].params.modelId` as the AWS `ConverseStreamCommand.modelId`, require discovered or explicitly configured model ids/ARNs as the canonical model id, or add a Bedrock-named wire-id parameter instead?

Rationale: The choice affects provider identity semantics, config compatibility, discovery/catalog rows, full ARN model refs, and the shape of live verification; automation should not invent that contract.

Likely owner: wirjo

Owner reason: wirjo authored the closest merged inference-profile discovery work, making them the best initial owner for the Bedrock identity contract choice.

Owner confidence: medium

Options:

- **Honor `params.modelId` (recommended):** Use the existing per-model params value as the Bedrock wire model id, then add docs, unit coverage, cron-model coverage, and live Bedrock proof for this contract.
- **Require canonical model ids:** Do not make generic params an identity override; instead require discovered inference-profile ids or explicit model rows, and document how ARN-like refs must be registered.
- **Add Bedrock-named wire id:** Introduce a provider-owned `bedrockModelId` or `wireModelId` parameter if maintainers think generic `modelId` is too ambiguous for request identity.

## Reproduction Assessment

Yes at source level: configure per-model `params.modelId`, resolve the Bedrock model, and current source still constructs the AWS command with `model.id`; I did not rerun a live AWS cron request.

## Solution Assessment

Unclear: `params.modelId` is the simplest proposed repair, but maintainers need to choose whether that generic params key should become the Bedrock wire-identity contract or whether discovery/explicit model rows should own identity.

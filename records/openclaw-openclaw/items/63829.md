## Label Justifications

- `P1`: Real multi-agent users report disabling memory-wiki or risking cross-agent knowledge bleed because one gateway currently shares a single wiki vault.
- `impact:session-state`: The issue is about memory-wiki vault contents, indexes, prompt context, and search results crossing agent boundaries that operators expect to keep isolated.
- `impact:security`: A shared wiki vault can expose private or tenant-specific knowledge across agents unless OpenClaw defines and enforces isolation semantics.

## Summary

Keep open: current main and v2026.6.11 still resolve memory-wiki from one global plugin config and one vault path, while the issue discussion gives source-level and operator evidence that this can cross intended multi-agent memory/security boundaries.

## What This Changes

Request per-agent memory-wiki vault configuration so agents on one gateway can keep wiki files, indexes, search, and write paths isolated instead of sharing one global vault.

## Best Possible Solution

Define one maintainer-approved agent-scoped memory-wiki isolation contract, then implement vault routing, schema/config precedence, security/upgrade behavior, docs, and focused two-agent regression coverage around that contract.

Likely owner: steipete

Owner confidence: high

Options:

- **Design generic agent-scoped plugin config (recommended):** Add a shared per-agent plugin config contract with explicit precedence, schema validation, SecretRef handling, lifecycle/restart semantics, doctor/upgrade behavior, and memory-wiki coverage.
- **Keep plugin config global and scope memory-wiki only:** Leave plugins.entries global and add memory-wiki-owned per-agent vault mapping or routing, reducing core surface but creating plugin-specific semantics.
- **Use ctx-aware vault path templating:** Allow vault.path to expand from invocation context, but require fail-closed behavior for no-agent CLI/gateway/background surfaces and migration docs for existing shared vaults.

## Solution Assessment

Unclear: the requested isolation is valid, but the best fix depends on a maintainer choice between generic per-agent plugin config, memory-wiki-owned vault routing, ctx-aware path templating, or shared/private layer semantics. A one-off config patch would be too risky without that contract.

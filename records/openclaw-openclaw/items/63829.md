## Summary

Keep open: current main and the latest release still give memory-wiki one gateway-level vault config, while multiple commenters report real multi-agent memory isolation and sensitive-boundary impact; the remaining work needs maintainer product/security direction rather than cleanup closure.

## What This Changes

Request per-agent memory-wiki vault configuration so agents on one gateway can keep isolated wiki vaults and search results instead of sharing one global vault.

## Best Possible Solution

Define one maintainer-approved isolation contract, preferably a generic per-agent plugin config or context-aware plugin runtime seam, then implement memory-wiki vault/read/write/search/prompt behavior with upgrade and security proof against existing global-vault installs.

Question: What isolation contract should OpenClaw support for memory-wiki and other plugin-owned memory config on a shared multi-agent gateway?

Rationale: The fix can add a broad per-agent plugin config API, a memory-wiki-specific context-aware vault resolver, or an explicit unsupported stance; each choice changes config compatibility, plugin API expectations, and sensitive memory isolation guarantees.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Generic per-agent plugin config (recommended):** Add a typed agents.list[].plugins.entries override contract, make memory-wiki consume it, and require docs, schema, upgrade, and isolation tests for fresh and existing installs.
- **Memory-wiki-only context vault:** Keep the general plugin API unchanged and resolve memory-wiki vault paths from trusted agent/workspace context at each operation, accepting that other plugins remain separately tracked.
- **Document separate-gateway isolation only:** Do not add a new config surface now; document that memory-wiki is gateway-global and that sensitive tenant boundaries require separate gateways.

Yes, source-reproducible: current main shows memory-wiki resolving one plugin config and AgentEntrySchema rejecting any per-agent plugins field. I did not run a live two-agent gateway repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose the contract: per-agent vault isolation is the right end state, but the best layer could be generic per-agent plugin config or a narrower memory-wiki context-aware resolver.

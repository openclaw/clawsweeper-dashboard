## Label Justifications

- `P1`: Multiple users report production multi-agent setups cannot safely enable memory-wiki because one shared vault can expose or mix agent-specific knowledge domains.
- `impact:session-state`: The issue is about durable wiki memory and search state being shared across agents that operators expect to remain isolated.

## Summary

Keep open: current main and v2026.6.11 still resolve memory-wiki through one global plugin config and one vault path, while the discussion shows real multi-agent isolation and sensitive-memory boundary impact that no merged or viable PR now owns.

## What This Changes

The issue requests per-agent memory-wiki vault configuration so multi-agent setups can keep wiki memory isolated instead of sharing one global vault.

## Best Possible Solution

Define one maintainer-approved memory isolation contract that preserves the current global default, supports per-agent vault separation, and covers tools, prompt/corpus supplements, gateway methods, CLI/admin flows, docs, upgrade/doctor behavior, and focused two-agent regression proof.

Rationale: The request changes configuration/API surface and sensitive memory isolation semantics, so automation cannot safely choose precedence, SecretRef, validation, lifecycle, and upgrade behavior without maintainer intent.

Options:

- **Design generic agent-scoped plugin config (recommended):** Add a shared agents.list[].plugins contract with explicit merge precedence, SecretRef handling, validation, restart semantics, doctor coverage, and memory-wiki tests/docs using that contract.
- **Add memory-wiki-owned vault routing:** Keep plugin config global and add a memory-wiki-specific per-agent or ctx-aware vault resolver with fail-closed no-context behavior and docs for CLI/gateway limitations.
- **Defer first-class isolation:** Document shared-gateway memory-wiki vault isolation as unsupported for now and point operators to separate gateway processes until the broader plugin config contract is designed.

Yes, at source level: current main resolves memory-wiki config once from global plugin config, the strict agent schema has no plugins override field, and wiki corpus reads use that captured vault path. I did not run a live two-agent gateway because this read-only review had enough source proof.

Unclear: the requested per-agent plugin config shape is plausible, but the best fix needs maintainer direction on whether the permanent contract is generic plugin config, memory-wiki-specific vault routing, or ctx-aware path templating with strict no-context behavior.

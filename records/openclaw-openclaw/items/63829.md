## Label Justifications

- `P1`: The issue blocks real multi-agent users from enabling memory-wiki safely on one gateway because wiki state and search can cross intended agent boundaries.
- `impact:session-state`: The reported behavior mixes memory-wiki vault content, prompt context, indexes, and search results across agents that operators expect to keep isolated.

## Summary

Keep open: current main and v2026.6.11 still use one global memory-wiki config and vault path, while the issue discussion shows real multi-agent memory isolation and security impact that no merged or viable PR now owns.

## What This Changes

The issue requests per-agent memory-wiki vault isolation so separate agents on one gateway can keep wiki pages, indexes, and search results separated.

## Best Possible Solution

Define one maintainer-approved memory-wiki isolation contract with schema precedence, vault routing, no-context behavior, security/upgrade guidance, docs, and a two-agent regression proving isolated writes and searches.

Unclear: the requested direction is valid, but maintainers still need to choose between a plugin-owned per-agent vault contract, a generic per-agent plugin config contract, or documented unsupported shared-gateway isolation.

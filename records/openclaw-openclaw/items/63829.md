## Label Justifications

- `P1`: The issue blocks real multi-agent users from enabling memory-wiki safely on one gateway because wiki state and search can cross intended agent boundaries.
- `impact:session-state`: The reported behavior mixes memory-wiki vault content, indexes, prompt context, and search results across agents that operators expect to keep isolated.
- `impact:security`: A shared memory-wiki vault can expose private, tenant-specific, or organization-specific knowledge across agent boundaries unless isolation semantics are defined.

## Summary

Keep open: current main, latest stable v2026.6.11, and latest beta v2026.7.1-beta.2 still resolve memory-wiki from one global plugin config and one vault path, while the issue discussion shows real multi-agent isolation and security impact with no merged or viable open PR owning the fix.

## What This Changes

Request per-agent memory-wiki vault configuration so multi-agent setups can isolate wiki roots, indexes, searches, and writes instead of sharing one global vault.

## Best Possible Solution

Define one maintainer-approved agent-scoped memory-wiki isolation contract, then cover config precedence, vault routing, no-context behavior, security/upgrade handling, docs, and two-agent regression proof across tools, gateway methods, CLI, and prompt/corpus supplements.

## Label Justifications

- `P1`: The issue blocks real multi-agent users from safely enabling memory-wiki on one gateway because wiki state and search can cross intended agent boundaries.
- `impact:session-state`: The reported behavior can mix memory-wiki vault content, indexes, prompt context, and search results across agents that operators expect to keep isolated.
- `impact:security`: A shared memory-wiki vault can expose private or tenant-specific knowledge across agent boundaries unless isolation semantics are defined.

## Summary

Keep open: current main and v2026.6.11 still resolve memory-wiki from one global plugin config and one vault path, while the discussion shows real multi-agent memory isolation and security impact that needs maintainer-owned product/security design.

## What This Changes

Request per-agent memory-wiki vault configuration so agents on one gateway can use isolated wiki roots instead of one shared global vault.

## Best Possible Solution

Define one maintainer-approved agent-scoped memory-wiki isolation contract with schema/config precedence, vault routing, security and upgrade behavior, docs, and focused two-agent regression coverage.

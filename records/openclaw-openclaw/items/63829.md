## Label Justifications

- `P1`: Multi-agent users report disabling memory-wiki or risking cross-agent knowledge contamination on one gateway, which is an urgent broken memory workflow but not an unusable core runtime.

## Summary

Keep open: current main and v2026.6.11 still use one process-wide memory-wiki config and vault, while the discussion shows real multi-agent sensitive-memory contamination and the remaining fix needs a maintainer-chosen per-agent plugin/vault contract.

## What This Changes

The issue requests per-agent memory-wiki vault configuration so agents on one gateway can keep wiki content, search results, and writes isolated instead of sharing one global vault.

## Best Possible Solution

Define a maintainer-approved per-agent plugin/memory contract, then make memory-wiki resolve vault, prompt, bridge, CLI, and repair behavior from the active agent while preserving the existing global default and documenting upgrade/security behavior.

Options:

- **Approve generic per-agent plugin config (recommended):** Add a documented `agents.list[].plugins.entries` override/merge contract and implement memory-wiki on top of that shared plugin API direction.
- **Approve memory-wiki-only vault scoping:** Add a narrower agent-aware vault mode or path-template mechanism inside memory-wiki and explicitly defer the broader plugin-config issue.
- **Document separate gateways only:** Decline shared-gateway vault isolation for now and document separate gateway processes as the supported isolation boundary.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: configure two agents that need different memory-wiki vaults and the current strict agent schema has no per-agent plugin config while memory-wiki closes over one global vault config. I did not run a live two-agent gateway scenario, so this is source-reproducible rather than live-reproduced.

## Solution Assessment

Unclear until maintainer direction is set: the request is valid, but a direct `agents.list[].plugins.entries` patch is only one possible contract. The safer solution should choose one durable per-agent plugin/vault model and test prompt, tool, bridge, CLI, and upgrade behavior together.

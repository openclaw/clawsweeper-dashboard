## Label Justifications

- `P1`: The issue blocks real multi-agent users from enabling memory-wiki safely on one gateway because wiki state and search can cross intended agent boundaries.
- `impact:session-state`: The reported behavior mixes memory-wiki vault content, prompt context, indexes, and search results across agents that operators expect to keep isolated.
- `impact:security`: A shared memory-wiki vault can expose private or tenant-specific knowledge across agent boundaries unless isolation semantics are defined.

## Summary

Keep open: current main and v2026.6.11 still resolve memory-wiki from one global plugin config and one vault path, while the discussion shows real multi-agent isolation and sensitive-memory boundary impact that no merged or viable PR now owns.

## What This Changes

Request per-agent memory-wiki vault configuration so multi-agent gateways can isolate wiki writes and searches instead of sharing one global vault.

## Best Possible Solution

Define one maintainer-approved memory-wiki isolation contract with schema precedence, vault routing, no-context behavior, security/upgrade guidance, docs, and a two-agent regression proving isolated writes and searches.

- **Document unsupported shared-gateway isolation:** Leave memory-wiki global for now and document separate gateways or separate installs as the only supported hard isolation boundary.

## Solution Assessment

Unclear: the requested direction is valid, but maintainers still need to choose between a plugin-owned per-agent vault contract, a generic per-agent plugin config contract, or documented unsupported shared-gateway isolation. A narrow memory-wiki-owned contract appears safer than a one-off deep merge unless the generic contract is deliberately chosen.

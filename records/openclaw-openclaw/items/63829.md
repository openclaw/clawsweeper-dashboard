## Label Justifications

- `P1`: Real multi-agent users report that shared memory-wiki vaults block safe use on one gateway because wiki state and search can cross intended agent boundaries.
- `impact:session-state`: The issue is about memory-wiki vault content, indexes, prompt context, and search results being shared across agents that operators expect to isolate.
- `impact:security`: A shared vault can expose private or tenant-specific knowledge across agent boundaries unless isolation semantics are defined.

## Summary

Keep open: current main and v2026.6.11 still resolve memory-wiki through one global plugin config and one vault path, while the issue has recent source-level and production-user evidence that shared vaults break multi-agent memory isolation. The broader generic tracker #55401 overlaps, but this issue remains the canonical memory-wiki vault-isolation slice because duplicates point here and the prior implementation PR is closed unmerged.

## What This Changes

The issue requests per-agent memory-wiki vault configuration so agents on one gateway can use isolated wiki roots instead of a shared global vault.

## Best Possible Solution

Define a maintainer-approved agent-scoped memory-wiki isolation contract, preferably coordinated with the generic per-agent plugin-config design, then cover vault routing, no-context behavior, docs, doctor/upgrade semantics, and two-agent regression proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should memory-wiki vault isolation be solved through generic `agents.list[].plugins` overrides, a memory-wiki-owned per-agent/workspace vault resolver, or an explicit unsupported/shared-gateway limitation?

Rationale: Automation cannot safely choose the permanent config, SecretRef, lifecycle, CLI/gateway, and upgrade semantics for a security-sensitive cross-agent memory boundary.

Likely owner: steipete

Owner reason: This choice spans plugin config runtime, SDK/config compatibility, security semantics, and recent memory-wiki state work where steipete has the strongest current boundary history.

Owner confidence: high

Options:

- **Design generic agent-scoped plugin config (recommended):** Add a shared per-agent plugin config contract with precedence, SecretRef/redaction, schema validation, restart semantics, docs, and memory-wiki coverage built on that contract.
- **Add memory-wiki-owned vault scoping only:** Keep global plugin config but give memory-wiki an explicit per-agent/workspace vault mapping or resolver, reducing generic core surface while creating plugin-specific semantics.
- **Document shared-vault limitation for now:** State that memory-wiki is not isolated across agents on one gateway and require separate gateways or disabled memory-wiki until a broader design lands.

## Reproduction Assessment

Yes, source-level: current main captures one memory-wiki config at plugin registration, rejects `agents.list[].plugins` through the strict agent schema, and routes read/write/prompt/corpus paths through the captured `vault.path`; I did not run a live two-agent gateway repro in this read-only pass.

## Solution Assessment

Unclear: the requested isolation is valid, but the best fix requires maintainer choice between a generic per-agent plugin config contract, a memory-wiki-specific vault resolver, templated paths, or documented unsupported behavior.

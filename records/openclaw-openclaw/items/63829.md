## Label Justifications

- `P1`: Multiple users report real multi-agent deployments where memory-wiki is unsafe or disabled because one shared vault can commingle sensitive agent knowledge.
- `impact:session-state`: The issue is about agent memory/wiki state and search results crossing boundaries between agents that operators expect to keep separate.
- `impact:security`: A shared memory-wiki vault can expose sensitive per-agent or per-tenant knowledge across intended isolation boundaries.

## Summary

Keep open: current main and v2026.6.11 still resolve memory-wiki from one global plugin config and one vault path, while the issue discussion shows real multi-agent memory isolation and security-boundary impact with no safe merged or open PR owning the fix.

## What This Changes

Request per-agent memory-wiki vault configuration so agents in one gateway can use isolated wiki vaults instead of a shared global vault.

## Best Possible Solution

Choose a maintainer-approved agent-scoped memory-wiki/plugin config contract, then implement it with schema/docs, migration or doctor behavior if needed, and two-agent regression proof for read, write, prompt, corpus, gateway, and CLI paths.

Rationale: The issue affects sensitive memory boundaries and persistent plugin state, so automation cannot safely choose the long-term config/API, SecretRef, validation, lifecycle, and upgrade semantics.

Owner confidence: medium

Options:

- **Design a generic agent-scoped plugin config contract (recommended):** Add a shared `agents.list[].plugins` or equivalent contract with explicit merge precedence, SecretRef/redaction, schema validation, restart semantics, doctor behavior, and memory-wiki coverage.
- **Keep plugin config global and add memory-wiki vault routing:** Leave `plugins.entries` global and give memory-wiki its own per-agent vault map or safe path-template contract, reducing generic core surface but making this a plugin-specific pattern.
- **Defer behind broader plugin isolation work:** Treat per-agent plugin install/config/lifecycle as one larger design and keep this issue open as the memory-wiki security/use-case evidence for that design.

## Reproduction Assessment

Yes, at source level: current main resolves one memory-wiki config and one `vault.path` at plugin registration, and the strict agent schema has no `agents.list[].plugins` override. I did not run a live two-agent gateway because this review is read-only and the source path is sufficient to verify the missing surface.

## Solution Assessment

Unclear. Per-agent plugin config is plausible, but the best fix needs a maintainer choice between generic plugin overrides, memory-wiki-owned vault routing, ctx-aware templates, and CLI/admin selectors, with security and upgrade semantics defined first.

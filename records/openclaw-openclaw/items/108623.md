## Label Justifications

- `P0`: The proposed deletion path can move unrelated user directories and files to Trash, creating a concrete data-loss hazard.
- `merge-risk: 🚨 compatibility`: Existing installations using supported custom `agentDir` paths can have a different and much broader directory removed during agent deletion.
- `merge-risk: 🚨 security-boundary`: The patch weakens filesystem target ownership by deriving a destructive operation from the parent of a configurable path without a canonical-root or emptiness check.

## Summary

Keep open: the cleanup goal is valid, but the proposed parent deletion is unsafe because `agentDir` is configurable and both trash implementations move an entire directory rather than requiring it to be empty. A custom agent directory can therefore make deletion target an unrelated parent such as the user's home directory. ([docs.openclaw.ai](https://docs.openclaw.ai/start/wizard?utm_source=openai))

## What This Changes

The PR adds best-effort cleanup of the per-agent parent state directory after CLI or Gateway agent deletion, with focused regression tests.

## Best Possible Solution

Add one shared helper that derives the canonical `agents/<agentId>` state container independently of configurable `agentDir`, verifies the known child relationship, and removes the container only with empty-directory semantics after known state cleanup.

Yes from source inspection: configure an agent with a custom `agentDir`, then delete it through either path; the new code passes that directory's parent to a whole-directory trash operation. The PR's terminal transcript also demonstrates the original empty-folder behavior on the default layout.

## Solution Assessment

No. Removing the canonical container only when empty is the narrow fix; recursively trashing `path.dirname(agentDir)` changes the deletion boundary and can remove unrelated data.

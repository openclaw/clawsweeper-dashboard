## Summary

Keep open: current main and the latest release cover much of the model-attribution request through `messages.responsePrefix` templates, but there is still no fallback-approval config field or approval hook before executing the next model candidate. The remaining behavior is a product/config decision, not a stale or implemented item.

## What This Changes

Request adds an opt-in approval gate before model fallback and optional visible provider/model attribution on messages.

## Best Possible Solution

Keep the existing response-prefix attribution path, then have maintainers define whether fallback approval belongs as a default-off core model-routing option, an approval/channel event contract, or an extension hook before implementation.

Owner confidence: high

Options:

- **Design a core opt-in fallback gate (recommended):** Define a per-agent or per-run approval contract with timeout behavior, channel delivery, docs, and tests before implementing the runtime pause.
- **Keep fallback automatic:** Treat response-prefix attribution and fallback notices/logs as the supported visibility model and close the approval-gate direction as not planned.
- **Route through extension/API design:** Design a generic approval or fallback-decision extension hook first instead of adding a one-off model config key.

## Reproduction Assessment

Yes for the source-level gap: the current schema and fallback loop have no approval field or approval callback before running the next fallback candidate. This is a feature request, not a broken existing behavior bug.

## Solution Assessment

Unclear until maintainers choose the contract. The attribution half is best served by existing `messages.responsePrefix` templates, while fallback approval needs a deliberate core or extension-point design rather than a narrow bug-fix PR.

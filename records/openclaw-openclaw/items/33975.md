## Summary

Keep open: current main covers the model-attribution half through `messages.responsePrefix` and fallback notices, but the requested opt-in approval gate before executing configured model fallbacks is still missing and needs a maintainer product decision.

## What This Changes

The issue requests two opt-in capabilities: confirmation before model fallback and visible model/provider attribution in outbound messages.

## Best Possible Solution

Keep the existing response-prefix and fallback-notice visibility paths, then decide a default-off fallback approval contract with timeout, denial, channel delivery, docs, and tests before implementation.

Question: Should OpenClaw add a core opt-in approval gate before executing configured model fallbacks, and if so what config scope, timeout behavior, and delivery surface should own it?

Rationale: The remaining request changes fallback runtime behavior and adds operator-facing config; OpenClaw policy treats fallback behavior and config surface as compatibility- and product-sensitive.

Likely owner: steipete

Owner confidence: high

Options:

- **Design A Core Default-Off Gate (recommended):** Define a per-agent or per-session approval contract with timeout behavior, denial semantics, same-channel delivery, and upgrade-safe config before implementation.
- **Keep Fallback Automatic:** Treat response-prefix attribution, fallback notices, strict user-selected models, and explicit empty fallback lists as the supported control model and close this direction as not planned.
- **Route Through Extension Design First:** Define a plugin or approval-event hook for fallback decisions before adding a one-off core model config key.

## Reproduction Assessment

Yes for the source-level gap: current config schema and the fallback loop have no approval field or approval callback before running the next fallback candidate. This is a feature request, not a broken existing behavior bug.

## Solution Assessment

Unclear until maintainers choose the product contract. The attribution half is already best served by `messages.responsePrefix`, while fallback approval needs deliberate core or extension-point design rather than a narrow bug-fix PR.

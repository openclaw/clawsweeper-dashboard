## Summary

Keep open: current main covers much of the model-attribution request through `messages.responsePrefix` templates and fallback notices, but it still lacks an opt-in approval gate before executing configured model fallbacks.

## What This Changes

The issue requests opt-in fallback confirmation before model failover plus visible model attribution on responses.

## Best Possible Solution

Keep the existing response-prefix and fallback-notice visibility paths, and have maintainers decide whether a default-off fallback approval gate belongs in core model routing, an approval/channel event surface, or a plugin/API extension.

## Maintainer Decision

Rationale: The remaining request changes fallback runtime behavior and adds config surface; repository policy treats fallback behavior and config additions as compatibility- and product-sensitive.

Likely owner: steipete

Owner confidence: high

Options:

- **Design a default-off core gate (recommended):** Define a per-agent or per-session approval contract with timeout behavior, channel delivery semantics, docs, and tests before implementation.
- **Keep fallback automatic:** Treat current fallback notices plus response-prefix attribution as the supported visibility/control model and close the approval direction as not planned.
- **Route through extension design:** Add or refine a plugin/API hook for approval decisions instead of adding a one-off model config key in core.

## Reproduction Assessment

Yes, at source level: current schema and runtime fallback code have no approval field or approval callback before executing the next fallback candidate. This is a feature gap rather than a broken existing behavior bug.

## Solution Assessment

Unclear until maintainers choose the product contract. The attribution half is best served by existing `messages.responsePrefix` templates, while fallback approval needs a deliberate core or extension-point design.

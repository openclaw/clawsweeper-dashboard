## Summary

Keep open: current main covers the model-attribution half through `messages.responsePrefix` templates, but the requested opt-in approval gate before fallback execution is still absent and remains a core product/config decision.

## What This Changes

Requests an opt-in mode that asks before switching to a fallback model, plus visible model attribution in responses.

## Best Possible Solution

Keep this as the canonical tracker until maintainers decide the fallback approval product shape; then implement one canonical per-agent/default config path with cross-channel approval routing, timeout semantics, docs, and focused fallback tests while keeping `messages.responsePrefix` as the attribution path.

## Reproduction Assessment

Yes for the remaining gap by source inspection: current main’s config schema accepts only `primary` and `fallbacks`, and the fallback loop calls the next candidate without an approval hook. This is a feature request rather than a broken existing behavior reproduction.

## Solution Assessment

Unclear until a maintainer confirms the product direction. The attribution side is best handled by the existing `messages.responsePrefix` template path, while fallback approval needs an explicit core approval/config design before implementation.

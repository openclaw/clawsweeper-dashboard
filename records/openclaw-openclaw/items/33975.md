## Summary

Keep open: current main covers most model-attribution visibility through response-prefix templates, model metadata, and fallback notices, but the requested opt-in approval gate before executing configured model fallbacks is still missing and needs maintainer product direction.

## What This Changes

Requests a default-off fallback approval mode before model failover plus visible model/provider attribution in outbound messages.

## Best Possible Solution

Keep the existing response-prefix and fallback-notice visibility paths, then have maintainers define a default-off fallback approval contract with timeout, denial, and approval-route behavior before implementation.

- **Design a core opt-in fallback gate (recommended):** Define a default-off per-agent or per-session approval contract that uses existing approval delivery where possible and specifies timeout and deny behavior before coding.
- **Keep automatic fallback with visibility only:** Treat responsePrefix model attribution and fallback notices as the supported transparency model, leaving fallback execution automatic.
- **Route through plugin/API design first:** Add or extend an approval/fallback hook surface so plugins can own policy before adding a core config key.

## Reproduction Assessment

Yes, at source level: current config/schema and the fallback loop have no approval field or approval callback before running the next fallback candidate. This is a feature request rather than a broken existing behavior bug.

## Solution Assessment

Unclear until maintainers choose the product contract. The attribution half is best served by existing `messages.responsePrefix` templates, while fallback approval needs a deliberate core or extension-point design.

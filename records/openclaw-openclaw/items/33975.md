## Summary

Keep open: current main covers the model-attribution part through `messages.responsePrefix` template variables and chat metadata, but it still has no opt-in approval gate before trying the next fallback model. The closed fallback-confirmation duplicate points back to this issue, so this remains the canonical tracker for the remaining product decision.

## What This Changes

Requests opt-in confirmation before model fallback plus optional model attribution in user-visible replies.

## Best Possible Solution

Keep model disclosure on `messages.responsePrefix`, and define a per-agent opt-in fallback approval policy only after maintainers choose the approval route, timeout, resume, and docs/test contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw core add an opt-in per-agent approval gate before automatic model fallback, and if so what approval route and timeout policy should it use?

Rationale: The missing behavior is not a strict bug; it adds new config and changes fallback reliability, provider-routing, and channel approval semantics that need maintainer product intent.

Likely owner: steipete

Owner reason: The decision spans agent model config and fallback policy, and steipete has the strongest history on both surfaces.

Owner confidence: high

Options:

- **Design a core approval gate (recommended):** Add a default-off per-agent fallback approval policy after specifying approval delivery, timeout, fail/proceed behavior, and regression coverage.
- **Keep automatic fallback only:** Reject approval gating and rely on existing fallback notices plus `messages.responsePrefix` for transparency.
- **Defer to external orchestration:** Leave core unchanged and document that users needing approval before provider changes should orchestrate model selection outside the fallback loop.

## Solution Assessment

Unclear until maintainers decide the product shape. The attribution half is already best handled by `messages.responsePrefix`; the fallback approval half needs a deliberate core design rather than an automatic one-file fix.

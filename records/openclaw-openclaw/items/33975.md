## Summary

Keep open: current main covers much of the model-attribution request through response-prefix templates and chat metadata, but it still has no opt-in approval gate before executing the next configured model fallback. That remaining behavior is compatibility- and product-sensitive because it adds config surface and changes fallback routing semantics.

## What This Changes

Request an opt-in fallback approval mode before switching configured models, plus visible model attribution in outbound messages.

## Best Possible Solution

Keep the existing response-prefix/model metadata attribution path, and have maintainers decide whether OpenClaw should add a per-agent, default-off fallback approval policy integrated with the existing approval routing and timeout semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a default-off per-agent approval gate before executing configured model fallbacks, and what timeout/fail/proceed behavior should it use?

Rationale: The missing behavior is real in current source, but solving it adds config surface and changes the reliability-versus-control contract for provider fallback routing.

Likely owner: steipete

Owner reason: The relevant fallback and config schema history points most strongly to steipete for product-level model fallback contract decisions.

Owner confidence: high

Options:

- **Define the per-agent approval contract (recommended):** Adopt a narrow default-off schema such as `agents.list[].model.requireApprovalBeforeFallback` with explicit timeout and fail/proceed semantics, then implement it with docs and upgrade-safe tests.
- **Keep automatic fallback only:** Reject fallback approval as too much runtime friction and close this tracker after documenting that model visibility should use response prefixes and logs instead.
- **Defer to a broader approval-routing RFC:** Leave this open but block implementation until approval routing, channel UX, and model fallback policy are designed together.

## Reproduction Assessment

Yes for the source-level gap, though this is a feature request rather than a failing bug repro: the schema and runtime fallback loop show no approval field or pause before trying the next candidate. Model attribution is already partly covered by response-prefix templates and chat metadata.

## Solution Assessment

No implementation should be queued yet. The best fix depends on a maintainer-approved fallback approval contract; a narrow per-agent, default-off gate would be the most maintainable shape if the product direction is accepted.

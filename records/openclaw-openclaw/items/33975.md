## Summary

Keep open: current main covers much of the model-attribution request through `messages.responsePrefix` templates and fallback notices, but the opt-in approval gate before executing configured model fallbacks is still missing and needs maintainer product direction.

## What This Changes

The issue requests a default-off fallback approval mode plus visible model/provider attribution in outbound responses.

## Best Possible Solution

Keep the current response-prefix and fallback-notice visibility paths, then define a default-off fallback approval contract or extension hook with clear timeout, denial, channel-delivery, and upgrade semantics before implementation.

- **Keep Automatic Failover:** Treat fallback notices, status, logs, and response-prefix attribution as the supported control/visibility model and close this direction as not planned.
- **Design Extension Hook First:** Add or reuse an approval/event seam so plugins or operators can own fallback approval policy without a one-off model config key.

## Reproduction Assessment

Yes, at source level: current schema and runtime types have no fallback approval field, and the fallback loop runs the next candidate without an approval callback. This is a missing feature path rather than a broken existing behavior bug.

## Solution Assessment

Unclear until maintainers choose the product contract. The attribution half is best handled by existing `messages.responsePrefix` templates, while fallback approval needs an explicit core or extension-point design before a fix PR is safe.

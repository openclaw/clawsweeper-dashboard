Implement the Azure Foundry Realtime path in the OpenAI provider and Talk Gateway Relay with constrained server-side API-key/Entra handling, Azure-specific diagnostics, docs, focused regression tests, and live Azure proof once a deployable resource is available.

Question: Should OpenClaw support Azure Foundry GPT Realtime Talk now as first-class OpenAI provider Gateway Relay config, and which Azure credential/endpoint contract should be accepted for the first implementation?

Rationale: The remaining work crosses provider routing, new or formalized config surface, server-side credential handling, redirect safety, and external Azure availability; automation should not choose the permanent auth/security contract alone.

Likely owner: Peter Steinberger

Owner reason: Peter has the strongest recent history on the OpenAI realtime provider, GA bridge, docs, and current realtime auth behavior that this decision would extend.

Owner confidence: high

Options:

- **API-key relay first (recommended):** Ship a narrow Gateway Relay path for Azure API-key deployments using the current Azure GA endpoint contract, with constrained redirect/host handling, SecretRef docs, diagnostics, tests, and live proof before considering Entra support.
- **Wait for Entra-first design:** Pause implementation until maintainers can validate Microsoft Entra or managed identity end to end, accepting a slower path for stronger production security posture.
- **Route out of core:** Decline first-class core support and require an external plugin/provider integration, which avoids core scope but likely leaves current Talk/Gateway Relay users without the needed server-side credential path.

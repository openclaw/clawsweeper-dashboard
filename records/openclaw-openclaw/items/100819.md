## Summary

Keep open: current main and v2026.6.11 still carry the reported browser/CDP SSRF policy mismatch, and the failure remains source-reproducible. The repair should wait for maintainer/security direction because it changes how browser SSRF policy distinguishes page navigation from CDP control-plane traffic.

## What This Changes

The issue reports that `navigate` can fail with `browser endpoint blocked by policy` when `browser.ssrfPolicy.hostnameAllowlist` is non-empty because `withAllowedHostname` only updates `allowedHostnames`.

## Best Possible Solution

Route Playwright connection and target lookup through a scoped CDP-control policy, while keeping the original browser navigation policy for requested URLs, redirects, and final-page checks.

Options:

- **Scope the fix to CDP control policy (recommended):** Keep page navigation checks strict, but ensure Playwright/CDP connection and target lookup use the selected profile's CDP control policy so local control traffic does not self-block.
- **Make the helper update both fields:** Teach `withAllowedHostname` to also extend `hostnameAllowlist`, accepting the risk that any caller using the adjusted policy outside CDP control may broaden hostname matching.
- **Keep current strict behavior:** Require users with `hostnameAllowlist` to include the local CDP host explicitly, and update docs/tests to make that operator burden intentional.

Yes. The source path is high-confidence: current main passes browser navigation policy into Playwright target lookup, `withAllowedHostname` only updates `allowedHostnames`, and the low-level resolver rejects non-matching `hostnameAllowlist` before that exact-host grant helps.

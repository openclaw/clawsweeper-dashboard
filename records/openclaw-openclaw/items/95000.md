## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.91

Full review comments:

- **[P1] Avoid provider-owned writes in the read RPC:** `src/gateway/server-methods/image.ts:89-90`
  - body: `image.providers` is an `operator.read` metadata call, but this still invokes each provider's `isConfigured` hook before the local read-only fallback. Current image providers route that hook through `isProviderApiKeyConfigured`, which calls `ensureAuthProfileStore` without forcing `readOnly`, so a Console inventory refresh can touch auth profile state instead of remaining read-only. Derive `configured` through a read-only env/profile/config projection here, or add a provider contract that accepts and enforces read-only auth lookup.
  - confidence: 0.9
- **[P2] Require non-empty config before reporting configured:** `src/gateway/server-methods/image.ts:44-47`
  - body: This fallback marks any matching provider key as configured, including `models.providers.<id>: {}` and an empty plugin config object. The existing CLI inventory path only treats non-empty config objects as a signal, so custom providers without an `isConfigured` hook can be shown as configured even when no credential or usable config exists. Reuse a `hasOwnKeys`-style check and cover the empty-object case in tests.
  - confidence: 0.86
- **[P2] Include all SDK geometry capability fields in the protocol:** `packages/gateway-protocol/src/schema/image-generation.ts:18-22`
  - body: The handler returns provider `capabilities.geometry` directly, but the new protocol type omits `aspectRatiosByModel` and `resolutionsByModel`, which are part of the current image-provider SDK contract and are consumed by normalization. That under-types valid plugin capability payloads for the first shipped Gateway contract. Add those fields to the schema, exported type, and protocol tests before merge.
  - confidence: 0.82

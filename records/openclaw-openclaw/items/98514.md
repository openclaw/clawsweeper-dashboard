## Summary

Keep open. This is a useful partial mitigation for mid-transcript `[cron:]` text, but it still allows a first-message human `[cron:]` in reset/deleted archives to mark the archive cron-generated and skip later remembered content while closing the canonical issue.

## What This Changes

The PR adds a `collected.length === 0` guard to archive cron text classification in `buildSessionEntry` and adds a regression test for a later `[cron:]` user message in a reset archive.

## Best Possible Solution

Land one canonical fix for https://github.com/openclaw/openclaw/issues/98241 that distinguishes trusted cron provenance from human text and covers both first-turn and mid-transcript reset/deleted archives while preserving or explicitly redefining metadata-less cron opacity.

## Reproduction Assessment

Yes at source level: current `buildSessionEntry` clears archive content and skips later messages after a user-role `[cron:]` prefix on usage-counted archive paths. I did not run tests because this is a read-only review.

## Solution Assessment

No. The patch is a plausible mid-transcript mitigation, but `collected.length` is only a position proxy and does not solve the first-turn human `[cron:]` archive case from the linked issue.

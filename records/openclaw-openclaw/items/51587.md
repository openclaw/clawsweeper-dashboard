## Summary

Keep open: current main and the latest shipped tag still require the cron minute field to be the literal `0`, so step/list/range expressions that fire at minute zero still miss the default stagger. Same-repository fix attempts are closed unmerged, and the only open closing candidate is a fork PR that is unmerged and not maintainer-modifiable, so this needs maintainer adoption, replacement, or closure rather than cleanup close.

## What This Changes

The issue asks OpenClaw to recognize cron minute fields such as `*/15`, `0,30`, and `0-30` as minute-zero schedules for the default top-of-hour stagger.

## Best Possible Solution

Land or adopt one narrow core fix in the cron stagger helper that detects minute-zero inclusion, preserves explicit `staggerMs: 0`, and adds focused coverage for helper, runtime defaulting, and doctor migration behavior.

## Reproduction Assessment

Yes. Source inspection on current main is enough: `isRecurringTopOfHourCronExpr("*/15 * * * *")` cannot return true because the minute field must equal `"0"`; no test was run because this review is read-only.

## Solution Assessment

Yes. The narrow maintainable fix belongs in `src/cron/stagger.ts`, with regression coverage on the helper and the runtime/default-migration callers rather than a broad scheduler rewrite or new config surface.

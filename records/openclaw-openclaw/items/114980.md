## Label Justifications

- `P2`: Least-privilege operators can still inspect Cron state, but every visible management action fails predictably, making this a normal-priority user-facing authorization UX defect.
- `impact:ux-friction`: The Cron page presents actions that the connected operator cannot perform and only explains the mismatch after a Gateway scope failure.

## Summary

This issue remains necessary: current Control UI rendering exposes Cron mutation controls while the Gateway classifies `cron.add`, `cron.update`, `cron.remove`, and `cron.run` as `operator.admin`. The Gateway still rejects the action, but read/write operators encounter visible controls that deterministically fail instead of a read-only Cron experience.

## What This Changes

Hide or disable Cron create, edit, run, clone, pause/resume, and delete actions for Control UI operators without `operator.admin`, while preserving job status, selection, history, and filtering.

## System Context

The Control UI reads Cron jobs and runs through Gateway methods, then renders management controls in the Cron page. Gateway descriptors enforce operator scopes at dispatch; the UI should use the same capability boundary before offering mutation actions.

## Architecture Diagram

## Best Possible Solution

Apply the existing operator-admin capability helper consistently across Cron creation, row actions, detail actions, editor submission, and starter suggestions; add focused read-only and admin rendering regressions without weakening Gateway scope enforcement.

## Summary

The UTF-16-safe direction is appropriate, but the new wrapper can still return a window shorter than `MIN_ECHO_CHARS` when a safe end trim reaches the input boundary; both matching paths then accept that shorter window. This remains a narrow mechanical repair before merge.

## What This Changes

The PR replaces raw fixed-width UTF-16 slices in the gateway boot-echo guard with a wrapper around the shared UTF-16-safe slicing utility.

## Best Possible Solution

Make safe-window generation reject any result shorter than the requested minimum, then add a focused regression for a terminal unpaired high-surrogate boundary on both boot-prompt chunking and haystack probing.

No. Extending the end offset handles ordinary surrogate-pair boundaries, but the correct invariant is to discard any safe slice that remains shorter than the required minimum rather than compare it.

## Summary

Keep open. Current main partially fixed the old input-schema complaint by accepting audio/video inputs, but it still lacks a configured chat-model output-modality contract; media generation remains routed through separate image/video tool/provider settings, so the Poe media-output failure or misleading fallback path is not implemented or safely superseded.

## What This Changes

The issue asks OpenClaw to explicitly reject or correctly support Poe image/video-output models that are accepted in custom provider config but fail or fall back in chat/session runtime.

## Best Possible Solution

Define a text-output-only chat model contract with clear unsupported media-output diagnostics, and keep supported image/video generation on the existing image/video provider tool contracts unless maintainers explicitly design output-modality config and channel delivery support.

## Reproduction Assessment

No for the exact live Poe failure; this review did not exercise Poe credentials or Telegram. Yes at source level for the remaining contract gap: current configured chat models carry input metadata but no output modality, while media generation routes through separate tools.

## Solution Assessment

Unclear. Explicit unsupported-media rejection is the narrowest short-term path, but maintainers need to decide whether output modality belongs in config/catalog, media-generation provider contracts, or both before implementation.

## Summary

Keep open. Current main partially addressed the original input-modality schema concern, but it still does not define an output-modality contract for configured Poe media-output chat models; image and video generation are routed through separate provider-tool capabilities, so the reported runtime confusion remains.

## What This Changes

The issue asks OpenClaw to either clearly reject unsupported Poe image/video-output models in chat runtime or implement first-class media-output model routing and capability metadata.

## Best Possible Solution

Define the session-runtime contract for non-text-output provider models, then either reject or hide them with a clear unsupported-media-output diagnostic, or extend the existing media-generation provider-tool architecture into first-class image/video-output model routing with docs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should configured Poe image/video-output models be explicitly rejected as unsupported session chat models for now, or should OpenClaw add first-class media-output model routing?

Rationale: The short-term rejection path and the full media-output runtime path are both plausible, but they create different public config, provider capability, fallback, and channel-rendering contracts.

Likely owner: steipete

Owner reason: The strongest history ties this boundary to the image_generate/media-tool and current model/config surfaces that must change for either direction.

Owner confidence: high

Options:

- **Reject media-output chat models for now (recommended):** Add validation and runtime diagnostics that make text-output session support explicit while leaving image/video generation on provider-tool paths until a fuller design exists.
- **Add media-output runtime support:** Extend schema, model selection, response handling, and channel rendering so configured image/video-output models can produce media directly in sessions.
- **Track in broader provider capability design:** Keep this as product-design input while a larger model modality and provider capability contract is planned.

## Reproduction Assessment

Yes at source level for the structural gap: configured chat models and catalogs still expose input metadata only, while generated media goes through separate image_generate/video_generate provider capabilities. I did not run a live Poe + Telegram repro for the exact HTTP 400 or fallback behavior.

## Solution Assessment

Unclear until maintainers choose the product contract. Explicit rejection/diagnostics is the narrowest near-term mitigation; first-class image/video-output chat runtime support would be larger and touches channel rendering and provider capability semantics.

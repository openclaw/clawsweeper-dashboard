## Summary

Keep open. Current main and v2026.6.11 still have no chat/session output-modality contract for configured Poe image/video-output models; media generation is routed through separate `image_generate` and `video_generate` capabilities, so the reported misleading selection/fallback behavior still needs a maintainer product/API decision.

## What This Changes

The issue asks OpenClaw to handle Poe media-output models registered as chat models by either rejecting unsupported image/video output clearly or adding first-class media-output support.

## Best Possible Solution

Define a generic media-output contract: either fail chat/session selection of image/video-output models with a clear unsupported-output diagnostic that points to generation tools, or add output-modality metadata with runtime and channel rendering support.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw reject non-text-output models when configured as chat/session models, or add first-class output-modality metadata and runtime support for image/video outputs?

Rationale: Both paths are plausible, but the choice changes public config semantics, provider ownership, model selection, and channel delivery behavior, so automation should not choose it from source inspection alone.

Likely owner: steipete

Owner reason: The decision crosses provider/model config, docs, and media-generation direction where current and recent history show repeated ownership.

Owner confidence: high

Options:

- **Reject Unsupported Chat Output (recommended):** Add a clear diagnostic for image/video-output models selected as chat/session models and direct users to `image_generate` or `video_generate` until first-class support exists.
- **Add Output-Modality Support:** Extend config/catalog metadata plus runtime/channel rendering so selected models can intentionally produce image/video outputs in session flow.
- **Docs-Only Clarification:** Document that media generation must use generation tools while leaving current custom-provider behavior unchanged and accepting continued runtime confusion.

## Reproduction Assessment

Source-level yes, live no. Current main shows the structural gap in chat model metadata and separate media-generation tooling, but the exact Poe HTTP 400 and Telegram fallback path still needs live Poe credentials to reproduce end to end.

## Solution Assessment

Unclear until maintainers choose the contract. Explicit rejection is the safest short-term mitigation; full support needs output-modality metadata and channel/runtime rendering work.

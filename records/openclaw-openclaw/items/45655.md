## Summary

Keep open. Current main and the latest release still have input-only chat model metadata and separate media-generation tool routing, so Poe/custom-provider image- or video-output chat models still need a maintainer product decision rather than cleanup closure.

## What This Changes

The issue asks OpenClaw to either reject or support Poe/custom-provider image/video-output models instead of accepting chat-model config that later fails or falls back.

## Best Possible Solution

Define the generic media-output contract: short term, fail unsupported chat selections with a clear diagnostic that points to image_generate/video_generate; longer term, add output-modality metadata and runtime/channel rendering only if maintainers want first-class media-output chat models.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw reject non-text-output models when configured as chat/session models, or add first-class output-modality metadata and runtime support for image/video chat outputs?

Rationale: Both paths are plausible, but the choice changes public config semantics, provider ownership, and media-generation routing, so automation should not choose it from source inspection alone.

Likely owner: steipete

Owner reason: This decision spans provider/model config, fallback policy, and media-generation direction where recent history shows relevant ownership.

Owner confidence: medium

Options:

- **Reject unsupported chat output now (recommended):** Add a clear unsupported-output diagnostic for image/video-output models selected as chat/session models and direct users to image_generate or video_generate until first-class support exists.
- **Add output-modality support:** Extend config/catalog metadata plus runtime and channel rendering so selected models can intentionally produce image/video outputs in session flow.
- **Docs-only clarification:** Document that media generation must use generation tools while accepting the current custom-provider runtime behavior and its support burden.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainers choose the product contract; explicit rejection is the safest short-term path, while full support needs output-modality metadata and channel/runtime rendering work.

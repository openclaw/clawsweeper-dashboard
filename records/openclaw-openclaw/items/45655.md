## Summary

Keep open. Current main still lacks a configured chat-model output-modality contract; media generation is handled through separate generation-tool/provider capability paths, so the Poe image/video-output confusion is not resolved by the newer input-modality schema work.

## What This Changes

The issue asks OpenClaw to either clearly reject unsupported Poe image/video-output chat models or add first-class media-output support instead of sending malformed requests or silently falling back.

## Best Possible Solution

Define one product contract: either reject configured chat models that are known or declared as non-text-output with clear diagnostics and docs, or add output-modality/generation-provider metadata that routes image/video generation through the supported media capability path.

## Reproduction Assessment

No for the exact live Poe HTTP 400 and Telegram fallback path; this review did not run a Poe setup. Source inspection does reproduce the structural gap: configured chat models carry input metadata only, while media output is routed through separate generation tools.

## Solution Assessment

Unclear. Explicit rejection is a reasonable short-term mitigation, but the best fix depends on maintainer direction for whether output modality belongs in model config/catalog metadata or only in generation-provider capabilities.

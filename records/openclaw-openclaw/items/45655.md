## Summary

Keep open. Current main has partially fixed audio/video input metadata handling, but it still has no output-modality contract for chat/session models, so Poe-style image/video-output models need maintainer product direction rather than cleanup closure.

## What This Changes

The issue requests clear handling for Poe/custom-provider image- and video-output models that can be registered as chat models but fail or fall back at runtime.

## Best Possible Solution

Define the generic media-output contract: short term, reject unsupported image/video-output chat selections with a clear diagnostic that points to image_generate or video_generate; longer term, add output-modality metadata and runtime/channel rendering only if maintainers want first-class media-output chat models.

## Maintainer Decision

Question: Should OpenClaw reject non-text-output models when configured as chat/session models, or add first-class output-modality metadata and runtime support for image/video chat outputs?

Rationale: Both paths are plausible, but the choice changes public config semantics, provider ownership, fallback behavior, and media-generation routing, so automation should not pick it from source inspection alone.

Likely owner: steipete

Owner reason: They merged the latest adjacent model metadata fix and have the strongest current routing signal across provider/config/fallback policy.

Owner confidence: high

Options:

- **Reject unsupported chat output now (recommended):** Add a clear unsupported-output diagnostic for image/video-output models selected as chat/session models and direct users to image_generate or video_generate until first-class support exists.
- **Add output-modality support:** Extend config/catalog metadata plus runtime and channel rendering so selected models can intentionally produce image/video outputs in session flow.
- **Docs-only clarification:** Document that media generation must use generation tools while accepting the current custom-provider runtime behavior and its support burden.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainers choose the product contract; explicit rejection is the safest short-term direction, while full support needs new output metadata plus runtime and channel rendering work.

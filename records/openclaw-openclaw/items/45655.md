## Summary

Keep open: current main only partially addresses the input-modality side, while custom chat/session model refs still have no output-modality contract or explicit unsupported-media-output diagnostic for Poe-style image/video models.

## What This Changes

The issue asks OpenClaw to make Poe image/video-output model refs either work through media-generation routing or fail clearly instead of producing malformed requests or silent fallback.

## Best Possible Solution

Define a generic output-modality contract, with diagnostic-first behavior for chat/session models unless maintainers explicitly choose to route media-output refs through image_generate and video_generate.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw treat image/video-output provider model refs as unsupported chat/session models with clear diagnostics, or add a first-class output-modality contract that routes those refs through media generation?

Rationale: Both choices change public provider/model semantics: diagnostics need a way to identify output-only models, while first-class support crosses provider contracts, media tools, response handling, and channel delivery.

Likely owner: steipete

Owner reason: This is a product/API boundary choice across provider model semantics and media-generation routing rather than a narrow code repair.

Owner confidence: medium

Options:

- **Diagnostic-first contract (recommended):** Add or derive output-modality metadata only far enough to reject media-output chat/session selections clearly while keeping generation on image_generate and video_generate.
- **First-class media-output routing:** Add output modality metadata and route selected image/video-output model refs through media-generation runtime with channel delivery support.
- **Wait for plugin proof:** Keep core unchanged until a Poe or generic media provider plugin proves the missing API surface and desired workflow.

## Reproduction Assessment

Yes, at source level: current main has input-only model metadata, no output modality field, a text/image-only LLM runtime model interface, and separate media-generation tool routing. I did not establish a live Poe run against Nano Banana, Veo, or Sora.

## Solution Assessment

No, a schema-only rejection is not clearly the best fix because current main intentionally widened some input modality paths. The maintainable solution is a maintainer-chosen output-modality contract with diagnostics, docs, and regression coverage.

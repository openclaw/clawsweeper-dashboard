## Summary

Keep open: current main fixed part of the input-modality schema story, but custom chat/session provider models still have no output-modality contract, while image/video generation is routed through separate tool configs.

## What This Changes

The issue asks OpenClaw to reject or support Poe image/video-output models instead of letting them be configured as chat models that fail or fall back at runtime.

## Best Possible Solution

Define a generic output-modality contract: keep chat/session models text-output-only with explicit unsupported-media-output diagnostics unless maintainers choose broader media-output routing through shared generation tools and channel delivery.

## Maintainer Decision

Rationale: Both paths change public provider/model semantics: diagnostics require a way to identify output-only models, while first-class support requires broader provider, tool, response, and channel contracts.

Options:

- **Diagnostic-first contract (recommended):** Add or derive enough output-modality metadata to fail fast for media-output chat/session selections while keeping generation on image_generate and video_generate.
- **First-class media-output models:** Add output modality metadata and route image/video-output model refs through media-generation runtime with channel delivery support.
- **Wait for plugin proof:** Keep core unchanged until a Poe or generic media provider plugin proves the missing API surface and desired user workflow.

No, a schema-only rejection is not clearly the best fix because current main now accepts wider input metadata. The safer path is a maintainer-chosen output-modality contract with diagnostics, docs, and focused regression coverage.

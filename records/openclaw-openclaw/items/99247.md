## Summary

Keep open: the latest head introduces a blocking consent regression by promoting OpenClaw Location Off back to While Using or Always when iOS already has a positive grant, and the background-location posture still needs explicit privacy approval and final-head proof.

## What This Changes

The PR adds an iOS Location permission summary, updates Settings reconciliation for OS grants, gates background/significant-location behavior on Always authorization, declares the iOS background location mode, refreshes native i18n inventory, and adds Swift tests.

## Best Possible Solution

Keep the desired OpenClaw mode as the canonical app preference: show positive iOS grants while Location is Off without mutating `location.enabledMode`, and merge only after iOS/privacy approval plus final-head proof.

## Reproduction Assessment

Yes, source-level: current PR head maps Off plus a positive iOS location grant to an enabled app mode and writes it back through `locationModeRaw` during Settings refresh. I did not run a signed-device repro in this read-only review.

## Solution Assessment

No for the latest reconciliation path: the permission summary and background gates are a reasonable shape, but automatically promoting Location Off from OS authorization is not the best consent model. The safer fix is to display the OS grant while preserving the app-level Off preference.

## Summary

Keep open: current main and v2026.6.11 still drop structured ACP image content from tool-call updates, and this branch is a focused fix with the earlier empty/whitespace validation findings addressed; it still needs real ACP-client behavior proof before merge.

## What This Changes

The PR extends ACP tool-call content extraction to forward valid `image` blocks with `data` and `mimeType`, and adds focused mapper tests for text, image, mixed, malformed, empty, whitespace-only, and fallback cases.

## Best Possible Solution

Land this focused mapper change after the contributor adds redacted real ACP-client proof that a read-tool PNG/JPG result displays in the client, while leaving broader media rendering issues to their existing canonical items.

## Reproduction Assessment

Yes, at source level: current main routes tool update/result payloads through `extractToolCallContent()`, which only emits text blocks despite ACP and OpenClaw tool results supporting images. I did not run a live ACP client reproduction in this read-only review.

## Solution Assessment

Yes for the code shape: the mapper is the narrow owner boundary, and the branch now validates non-empty image fields consistently with the text path. It is not merge-ready until real ACP-client proof shows the user-visible behavior works.

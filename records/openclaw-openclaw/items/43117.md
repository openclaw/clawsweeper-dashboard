## Label Justifications

- `P2`: This is a normal-priority memory-search feature with bounded but non-trivial product and security scope, not an urgent active regression.
- `impact:session-state`: The request changes what conversation memory indexes and retrieves across sessions, including remembered media and attachments.
- `impact:security`: The requested behavior would upload and retain user media or attachment-derived embeddings through remote provider contracts.

## Summary

Keep open: current main covers the Gemini Embedding 2 preview model, output dimensionality, and opt-in image/audio file embeddings, but the requested PDF/video modalities and remembered chat-attachment indexing still remain product- and security-sensitive work.

## What This Changes

The issue requests multimodal memory search for Gemini Embedding 2, including media/attachment embeddings, configurable output dimensions, and cross-modal retrieval.

## Best Possible Solution

Define a gated media-memory contract first, then implement only maintainer-approved attachment/PDF/video modalities in memory-core and the Google provider with reindexing, docs, provider-contract tests, and live Gemini proof.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expand multimodal memory beyond the shipped opt-in image/audio file path into PDF/video files and remembered session attachments, and what consent, retention, deletion, provider-upload, and reindexing contract should gate it?

Rationale: The missing behavior is technically feasible, but it changes what user media is uploaded to remote embedding providers and retained in searchable memory, so automation should not choose the product/security boundary.

Likely owner: gumadeiras

Owner reason: This choice is closest to the shipped multimodal memory boundary introduced in PR https://github.com/openclaw/openclaw/pull/43460.

Owner confidence: high

Options:

- **Design Gated Media Memory First (recommended):** Define supported modalities, explicit opt-in consent, retention/deletion behavior, provider limits, result presentation, and reindex behavior before implementation.
- **Keep Core To Shipped Subset:** Leave core at Gemini image/audio file indexing and close or defer attachment/PDF/video memory until a stronger maintainer-sponsored direction appears.
- **Expand ExtraPaths Only:** Allow a narrower follow-up for PDF/video files under configured memory paths while explicitly excluding remembered chat-attachment retention for now.

## Reproduction Assessment

Yes, at source level. Current main only normalizes image/audio in multimodal memory settings, the config schema rejects video/PDF modality names, and session memory extracts text rather than embedding media paths or bytes.

## Solution Assessment

Unclear without maintainer direction. The existing Gemini image/audio path is a plausible foundation, but the best fix must first define media retention, provider-upload consent, supported formats/model IDs, and reindex behavior.

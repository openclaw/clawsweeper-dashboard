## Summary

Keep open: current main still carries delivery/session metadata through cron and subagent runs, but it does not provide a plugin-visible requester/user-context contract for OAuth-dependent tools. The remaining work is a security-sensitive Plugin SDK/runtime design decision, not conservative cleanup.

## What This Changes

Request a generic user-context mechanism for cron jobs and spawned subagent sessions so plugin OAuth tools can identify the requesting user outside inbound message turns.

## Best Possible Solution

Design one typed requester-context contract across cron payload/protocol, sessions_spawn/subagent runtime, Plugin SDK access, audit/security docs, and tests, avoiding env-var fallbacks or plugin-specific shims.

Question: What requester identity contract should cron and subagent runs expose to plugin OAuth tools?

Rationale: This would let unattended or delegated execution act under a user OAuth identity, so automation cannot safely choose the API shape, authority boundary, consent model, or audit semantics.

Likely owner: steipete

Owner confidence: high

Options:

- **Typed Gateway/Plugin SDK Requester Context (recommended):** Add a runtime-owned requester identity seam propagated only from approved schedule/spawn authority, with consent, audit, revocation, and privacy rules.
- **Plugin-Local Default Identity Only:** Keep core unchanged and let affected plugins define explicit scheduled identities where their owners can enforce plugin-specific OAuth policy.
- **No User-Scoped OAuth For Unattended Runs:** Keep cron and spawned sessions headless for user OAuth tools unless they are triggered by an active inbound user message.

## Reproduction Assessment

Yes for source-level gap proof: inbound message paths pass senderId into tool policy, while cron payloads and sessions_spawn/subagent calls only carry session/delivery metadata. No live OAuth plugin repro was run in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API and security shape. A typed runtime/Plugin SDK requester-context seam is safer than process.env or fixed sender config fallbacks.

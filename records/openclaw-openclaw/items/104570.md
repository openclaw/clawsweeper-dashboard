## Summary

The main pagination behavior is well-designed and strongly proven, and all earlier findings are fixed, but one session-lifecycle defect remains: if the first history load fails after switching chats, the prior chat’s pagination cursor remains active and can be used for the newly selected session.

## What This Changes

The branch makes Control UI consume `chat.history` pagination metadata, load older pages on top-scroll, preserve the viewport after asynchronous prepends, and move a bounded 2,000-message render window through long transcripts.

## Best Possible Solution

Reset all pagination metadata atomically when route-session state changes, then add a regression test covering session A with a cursor, a switch to session B, B’s failed initial load, rejection of any stale-offset older request, and later successful establishment of B’s cursor.

## Reproduction Assessment

Yes. The original bug is directly source-reproducible because current main loads one history page and only expands locally; the patch defect is also deterministic by switching chats, failing the new initial history request, and then top-scrolling.

## Solution Assessment

No, not yet. Consuming the existing gateway pagination contract with a bounded UI window is the right solution, but the cursor must be reset or scoped with the selected session before the implementation is safe to merge.

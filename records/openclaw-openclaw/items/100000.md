## Summary

Keep open: current main has a normal Telegram `file_path` download-and-save path, but it still has a source-proven unavailable-media path where `getFile()` failures return `null`, no attachment is saved, and placeholder-only context can reach the agent. The reporter's all-format zero-save regression is broader than any single existing related issue, so it should not be closed as implemented or as a clean duplicate yet.

## What This Changes

The issue reports that Telegram DM images, documents, audio, and video on OpenClaw 2026.4.23 reach the agent only as media placeholders and never create files under `media/inbound/`.

## Best Possible Solution

Reproduce the reported Telegram DM flow on the latest release or current main, then consolidate the unavailable-media behavior so successful media always materializes and failed media surfaces a clear unavailable-attachment state rather than placeholder-only context.

## Reproduction Assessment

Yes for the source-level unavailable-media path: make Telegram `ctx.getFile()` fail and current main returns `null`, proceeds with no saved media, and can emit placeholder-only context. No for the reporter's full all-format zero-save claim against current main, because no live credentialed Telegram reproduction was run.

## Solution Assessment

Unclear. Current main is not the complete solution for `getFile()` failure handling, but the all-format regression needs live triage before maintainers decide whether it is the same unavailable-media contract as the existing open issues or a separate runtime problem.

## Summary

Keep open: current main and v2026.6.11 still have a source-proven Telegram media path where `getFile()` failures return `null`, no attachment is saved, and placeholder context can still reach the agent. Successful `getFile().file_path` downloads are implemented, so this should be consolidated with the related unavailable-media and local Bot API work rather than closed as already fixed.

## What This Changes

The issue reports Telegram DM media of multiple formats arriving only as placeholders, with nothing saved under `media/inbound` and no gateway error on OpenClaw 2026.4.23.

## Best Possible Solution

Define one Telegram unavailable-media contract: successful `file_path` media saves to inbound storage, null or failed resolution surfaces a clear throttled unavailable-attachment state, and local Bot API path materialization is coordinated with the open trusted-root PR.

## Reproduction Assessment

Yes for the source-level null path: make Telegram `ctx.getFile()` fail and current main returns `null`, saves no media, and can still construct placeholder context. No live reproduction was run for the reporter's exact all-format Ubuntu setup.

## Solution Assessment

Unclear as a single fix: current main correctly handles successful `file_path` downloads, but the null/unavailable-media path still needs a consolidated Telegram contract across single messages, media groups, warnings, and local Bot API materialization.

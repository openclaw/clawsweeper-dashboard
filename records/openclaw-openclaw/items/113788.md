## Summary

Keep open. The report identifies a plausible P1 duplicate-delivery failure in the core model-fallback path: a completed attempt may be reclassified as retryable after visible output was already sent, allowing a second model attempt for the same user turn. The prior review reached the same open conclusion, and no merged fix or canonical replacement is evidenced in the supplied context.

## What This Changes

Prevent model fallback from delivering a second reply when an earlier model attempt has already delivered output but is subsequently classified as retryable.

## System Context

OpenClaw’s agent runner executes a model attempt, records delivery and terminal outcomes, and may select another configured model when classification marks the result retryable. The fallback decision feeds the same outbound channel flow, so retrying after committed delivery can send a duplicate response to the user.

## Architecture Diagram

flowchart LR

  B --> C[Primary model attempt]
  C --> D[Delivery evidence]
  C --> E[Result classifier]
  D --> E
  E --> F{Retry fallback?}
  F -->|No| G[Finish one user reply]
  F -->|Yes| H[Fallback model attempt]
  H --> G

## Best Possible Solution

Define one authoritative committed-visible-delivery signal for an attempt, pass it into every fallback classifier path before retry selection, and add regression coverage proving a post-delivery billing or transient classification cannot start another visible reply for the same turn.

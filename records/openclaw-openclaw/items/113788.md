## Label Justifications

- `P1`: A single user prompt can produce multiple independently generated channel replies after a retryable model failure, which breaks an active messaging workflow.
- `impact:message-loss`: The affected delivery path can duplicate user-visible messages for one turn, a form of incorrect channel message delivery.

## Summary

Keep open. The report describes a concrete duplicate-message failure within one agent run: a delivered messaging-tool reply is followed by a retryable failure, then failover starts without prior delivery evidence and produces another answer. Existing delivery-terminal work appears to classify an individual attempt, not carry delivery state across attempts, so there is no evidence that current `main` already resolves the central problem.

## What This Changes

Preserve confirmed messaging delivery evidence across retryable model-failover attempts so fallback models do not re-answer a turn that has already reached the user.

## System Context

The embedded agent runner executes one incoming channel turn and may retry it with a fallback model after a retryable failure. Its messaging-tool stream handler records committed outbound delivery, while the failover loop decides whether another model attempt should run and the channel layer ultimately delivers the resulting messages.

## Architecture Diagram

flowchart LR
  A[Incoming channel turn] --> B[Embedded agent attempt]
  B --> C[Messaging tool delivery evidence]
  B --> D{Attempt outcome}
  D -->|Retryable failure| E[Fallback model attempt]
  C --> E
  E --> F[Terminal delivery decision]
  F --> G[User-visible channel messages]

## Best Possible Solution

Carry a narrowly scoped committed-delivery fact through retryable failover within the same run, make terminal/fallback policy consume that fact, and add regression coverage for both delivered-then-failed and never-delivered attempts.

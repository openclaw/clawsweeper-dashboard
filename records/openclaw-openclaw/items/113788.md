## Summary

Keep open for a focused owner decision. The report identifies a plausible source-level path where a thrown primary attempt bypasses result classification and can advance fallback after a visible reply, but the guard must distinguish a completed final reply from an interim outbound side effect before a repair is safe.

Likely related people: `osolmaz` is a low-confidence routing candidate because they authored the related durable-delivery contract issue.

## What This Changes

Prevent model fallback from re-running a turn and sending a duplicate visible reply after the primary model has already delivered the turn’s final response.

## System Context

Model fallback runs a configured sequence of model candidates for one agent turn. The embedded runner records delivery evidence while producing replies, and the fallback controller must use that evidence to decide whether another candidate may safely retry the same turn.

## Architecture Diagram

flowchart LR
  A[Inbound user turn] --> B[Primary model attempt]
  B --> C[Reply delivery evidence]
  B --> D{Returned result or thrown error}
  D --> E[Fallback safety decision]
  C --> E
  E -->|safe to retry| F[Fallback model attempt]
  E -->|reply already completed| G[Finish one user-visible turn]

## Best Possible Solution

Define one owner-approved predicate for “this interactive turn has completed final delivery,” then use it consistently for both returned-result classification and thrown-attempt fallback decisions, with regression coverage for final reply, interim progress-only, and no-delivery failures.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For fallback after a thrown model attempt, should OpenClaw suppress retry only after completed terminal delivery, or after any committed outbound side effect?

Rationale: The existing delivery helpers encode different valid semantics: one protects user-turn completion and the other protects recovery after any external side effect. Choosing between them changes whether an interim status message may recover through a fallback model.

Likely owner: osolmaz

Owner reason: Their related issue already owns the broader durable final-delivery contract that this fallback decision depends on.

Owner confidence: low

Options:

- **Use terminal-delivery semantics (recommended):** Allow fallback after progress-only output, but stop it once the source turn has a completed final reply; this is recommended because it prevents duplicate answers without sacrificing recovery after interim status.
- **Use any-side-effect semantics:** Stop fallback after any committed outbound action, prioritizing avoidance of repeated external effects at the cost of leaving progress-only failed turns unrecovered.
- **Specify a new explicit fallback-delivery contract:** Define a dedicated turn-scoped signal if neither existing predicate exactly captures the intended retry boundary.

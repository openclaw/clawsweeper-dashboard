Full review comments:

- **[P2] Check the WAL checkpoint result before trusting durability:** `extensions/memory-core/src/memory/manager-sync-ops.ts:2802`
  - body: `PRAGMA wal_checkpoint(TRUNCATE)` returns a row: SQLite reports a blocked FULL/RESTART/TRUNCATE checkpoint with the first column set to 1 and frame counts in the next columns. `exec()` discards that row, so an incomplete checkpoint can look successful and the code can still continue with the newly published meta only in the WAL if the process dies before close. Use `prepare(...).get()` or an equivalent row-returning helper and handle busy/incomplete results explicitly.
  - confidence: 0.88
- **[P2] Make the checkpoint test prove the live DB checkpoint:** `extensions/memory-core/src/memory/manager.wal-checkpoint.test.ts:132-139`
  - body: This spy watches every SQLite `exec`, then only asserts that some TRUNCATE checkpoint happened during sync. Current main already closes the shadow DB during sync, and that close path can issue a TRUNCATE checkpoint, so this test can pass without proving the new post-publish checkpoint ran on `originalDb` or made the live main file durable before close.

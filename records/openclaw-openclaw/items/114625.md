## Summary

Keep this PR open for a narrow repair: its durable-spool path is well proven, but the newly introduced retry error is a different class from the replay guard’s retry marker, so a no-lifecycle replay path would commit the message instead of releasing it for retry. Likely related people: sunlit-deng (current repair author; low-confidence routing signal).

## What This Changes

The PR changes Nextcloud Talk room-kind lookup failures from a cached group-room fallback into deferred durable webhook retries, caching only successful direct or group classifications.

## System Context

Nextcloud Talk receives signed Activity Streams webhook events, persists them in its ingress queue, determines whether the target is a direct message or room through the room-info API, then applies channel access policy and dispatches an agent reply. The proposed retry result is consumed by the durable ingress monitor so temporary room-info outages should not misclassify or lose direct messages.

## Architecture Diagram

flowchart LR
  A[Nextcloud Talk webhook] --> B[Durable ingress queue]
  B --> C[Inbound message handler]
  C --> D[Room-info lookup]
  D -->|direct or group| E[Access and routing policy]
  E --> F[Agent reply dispatch]
  D -->|temporary failure| G[Deferred retry outcome]
  G --> B

## Best Possible Solution

Use one monitor-owned retry error contract for both durable lifecycle deferral and replay-guard release, then add a focused no-lifecycle replay regression test proving the claim is released and a later attempt is processed once.

## Summary

This PR has strong focused tests and real Telegram before/after evidence for a genuine reply-delivery failure, but merging changes the freshness contract: after 20 seconds an older completed reply may arrive while a newer turn is still running. Keep it open for an auto-reply owner to approve or reject that deliberate ordering tradeoff.

## What This Changes

The branch bounds foreground reply-fence waits at 20 seconds, lets non-stale tool-status payloads bypass the wait, and extracts the fence into a dedicated module with regression tests.

## Best Possible Solution

Adopt one explicit foreground-freshness contract across visible channels: retain stale-winner suppression, but only merge the bounded 20-second fallback if owners accept old→new delivery when the newer turn remains silent.

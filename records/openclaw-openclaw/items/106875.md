## Label Justifications

- `P1`: The reported regression prevents active cron and hook workflows from starting and permanently disables retryable one-shot jobs for affected users.
- `impact:session-state`: Maintenance changes or removes active cron/hook session identity before lifecycle admission, causing session-state drift and failed work.

## Summary

Keep this issue open: the v2026.7.1 incident provides strong evidence of a real cron/hook session-state regression, and current main has substantially changed persistence but does not yet prove that lifecycle claim failures receive bounded retries or that the full upgrade scenario is covered.

## What This Changes

Prevent session maintenance from evicting active cron/hook sessions, handle legacy migrated sidecars consistently, and retry lifecycle claim conflicts instead of permanently disabling one-shot jobs.

## Best Possible Solution

Make cron/hook lifecycle admission and persistence atomic through the canonical session accessor, migrate or exclude legacy sidecars through Doctor, and classify typed lifecycle claim conflicts as bounded transient retries with fresh-install and v2026.7.1 upgrade coverage.

Yes for v2026.7.1: the logs, affected-job counts, over-budget directory state, and successful one-line protection patch form a high-confidence reproduction. A current-main live reproduction is not yet established because persistence has moved to the session accessor and SQLite.

## Solution Assessment

Mostly yes: typed transient retry classification and active-session-safe persistence are the right boundaries, but current main should use its canonical accessor rather than restoring a legacy file-store-only argument patch. Legacy sidecars should be handled by Doctor migration, not a steady-state runtime compatibility branch.

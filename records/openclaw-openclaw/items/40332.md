## Summary

Keep open: current main and v2026.6.11 still lack static per-binding or per-agent ACP permission defaults, while the issue has concrete source and user evidence that global ACPX `permissionMode` over-grants mixed-trust ACP sessions.

## What This Changes

Request scoped ACP permission defaults on `bindings[].acp` and `agents.list[].runtime.acp` so different ACP sessions can use different approval policies instead of the global ACPX `permissionMode`.

## Best Possible Solution

Approve a generic scoped ACP permission-profile contract, then implement schema, binding materialization, runtime option propagation, docs, and security-focused regression coverage together.

Rationale: The source gap is clear, but the durable public config shape controls security boundaries and could either align with current generic runtime options or duplicate ACPX-specific plugin config.

Owner confidence: high

Options:

- **Use generic permissionProfile defaults (recommended):** Add scoped `permissionProfile` defaults that map through the existing ACP runtime option alias layer, keeping ACPX-specific names at the plugin-global layer.
- **Add ACPX-specific scoped keys:** Implement the requested `permissionMode` and optional `nonInteractivePermissions` precedence directly for ACPX sessions, accepting a backend-specific config surface.
- **Keep global config only:** Document `/acp permissions` and global ACPX config as the supported paths and leave static scoped permission defaults out for now.

## Reproduction Assessment

Yes. Source inspection is enough to reproduce the gap: strict schemas reject the requested scoped keys, and ACPX permission mode is still consumed from plugin-global config only.

## Solution Assessment

Unclear. The proposed precedence is plausible, but maintainers should decide whether the durable public surface is generic `permissionProfile` defaults or ACPX-specific `permissionMode` keys.

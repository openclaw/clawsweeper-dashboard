## Summary

Keep open: current main still rejects static scoped ACP permission defaults at both `bindings[].acp` and `agents.list[].runtime.acp`, while ACPX permission policy remains plugin-global and security-sensitive.

## What This Changes

The issue requests per-binding and per-agent ACP permission overrides instead of only `plugins.entries.acpx.config.permissionMode`.

## Best Possible Solution

Define one scoped ACP permission-default contract, preferably aligned with generic runtime permission profiles, then add schema, binding materialization, runtime propagation, docs, and security-focused tests together.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose scoped ACP permission defaults as generic `permissionProfile` values, ACPX-specific `permissionMode` and `nonInteractivePermissions` values, or no static scoped permission defaults?

Rationale: The source gap is clear, but the requested behavior changes which channel-bound headless sessions receive write and shell authority and could create a parallel public config surface.

Likely owner: osolmaz

Owner reason: He owns the ACP runtime option shape and ACPX integration history most directly tied to the durable permission contract.

Owner confidence: high

Options:

- **Use generic scoped permission profiles (recommended):** Add per-agent and per-binding `permissionProfile` defaults that flow through the existing ACP runtime option layer while keeping ACPX `permissionMode` plugin-global.
- **Add ACPX-specific scoped keys:** Implement the requested `permissionMode` and possible `nonInteractivePermissions` precedence directly for ACPX sessions, accepting a backend-specific public config contract.
- **Keep global-only permissions:** Document global ACPX permissions plus live `/acp permissions` controls as the supported paths and leave static scoped defaults out for now.

## Reproduction Assessment

Yes. Source inspection is enough: strict schemas reject the requested scoped keys, binding materialization does not carry permission policy, and ACPX permissions still come from plugin-global config.

## Solution Assessment

Unclear. The requested precedence is plausible, but current main also has generic `permissionProfile` runtime options, so maintainers should choose the durable public config shape before implementation.

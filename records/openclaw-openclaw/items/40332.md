## Summary

Keep open: current main and latest stable release still only support ACPX permission defaults through global plugin config, while scoped per-binding and per-agent ACP permission defaults remain absent and security-sensitive.

## What This Changes

Request adding per-binding and per-agent ACP permission defaults so different ACP sessions do not share one global acpx permissionMode.

## Best Possible Solution

Approve a generic scoped ACP permission-profile contract, then implement schema, binding materialization, runtime option propagation, docs, and security-focused regression coverage without changing the global defaults.

Kind: security_boundary

Question: Should OpenClaw expose static scoped ACP permission defaults on `bindings[].acp` and `agents.list[].runtime.acp`, and should that public surface be generic `permissionProfile` or ACPX-specific `permissionMode` plus `nonInteractivePermissions`?

Rationale: The source gap is clear, but this config controls write and shell authority for channel-bound ACP sessions and could either align with current generic runtime options or create a parallel ACPX-specific permission contract.

Likely owner: osolmaz

Owner reason: He owns both the ACP runtime option/control-plane shape and the ACPX runtime integration most likely to define the durable permission contract.

Owner confidence: high

Options:

- **Use generic permissionProfile defaults (recommended):** Add scoped `permissionProfile` defaults that map through the existing ACP runtime option alias layer, leaving ACPX-specific names at the plugin-global layer.
- **Add ACPX-specific scoped keys:** Implement the requested `permissionMode` and optional `nonInteractivePermissions` precedence directly for ACPX sessions, accepting a backend-specific config surface.
- **Keep global config only:** Document `/acp permissions` and global ACPX config as the supported paths and leave static scoped permission defaults out for now.

## Reproduction Assessment

Yes. Source inspection is enough: current strict schemas reject the requested scoped keys, binding materialization omits permission policy, and ACPX runtime construction consumes only plugin-global permission config.

## Solution Assessment

Unclear. The proposed precedence is plausible, but maintainers should decide whether the durable public surface is generic `permissionProfile` defaults or ACPX-specific `permissionMode` keys.

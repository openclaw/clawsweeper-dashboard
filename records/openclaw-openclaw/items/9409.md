## Summary

Keep open. The central request remains useful: current overflow handling has rich budget facts in diagnostics and session metadata, but the user-facing recovery path still needs a deliberately designed, redacted diagnostic contract rather than another generic string. The closed implementation attempt did not land, while fresh production reports show that opaque overflow recovery continues to create avoidable operator confusion.

## What This Changes

Add safe, actionable context-overflow diagnostics that identify the affected session and explain the model/context limit, estimated pressure, and recovery actions.

## System Context

Agent runs assemble a session transcript and prompt, then compare its estimated size with the selected model's context budget before sending it to the provider. When compaction or truncation cannot recover, the runner and channel reply paths emit a user-visible failure message to the affected conversation.

## Architecture Diagram

flowchart LR
  A[Inbound channel message] --> B[Agent session and transcript]
  B --> C[Prompt and token-budget check]
  C --> D{Compaction or truncation recovers?}
  D -->|Yes| E[Continue model run]
  D -->|No| F[Safe overflow diagnostic]
  F --> G[Channel reply and operator logs]

## Best Possible Solution

Define one shared, redaction-aware overflow-diagnostic result that receives only prepared run facts, labels estimates honestly, renders a portable recovery message, and is used consistently by terminal runner, precheck, sanitizer, and auto-reply fallbacks; keep detailed file-size inspection in operator diagnostics unless maintainers explicitly approve a user-visible contract.

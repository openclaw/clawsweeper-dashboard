## Summary

The centralized implementation is the best fix, and no blocking correctness or security findings remain. ([raw.githubusercontent.com](https://raw.githubusercontent.com/openclaw/openclaw/main/scripts/lib/docker-e2e-container.sh))

## What This Changes

Centralizes Docker E2E resource-limit error recognition, preserves the original Docker failure and single-run behavior, and adds regression coverage for container and package helper paths.

## Best Possible Solution

Land the shared fail-closed diagnostic so incompatible runtimes retain the original error and status while receiving a deliberate repair-or-opt-out path, without automatic weaker retry behavior.

Yes. A constrained or rootless Docker daemon that accepts plain runs but rejects the injected CPU, memory, or PID controls reproduces the current-main status-125 failure, and the linked issue includes a real daemon transcript. ([github.com](https://github.com/openclaw/openclaw/issues/98601))

## Solution Assessment

Yes. A shared diagnostic wrapper is narrower and safer than automatically retrying with weaker resource controls, and it keeps the container and package-backed paths aligned while reusing the existing explicit opt-out.

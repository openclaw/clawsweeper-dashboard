- `merge-risk: 🚨 compatibility`: The patch changes the meaning of an explicit empty plugin scope by retaining registrations that current lifecycle code clears.

## Summary

Keep this PR open for a maintainer decision: the reported harness-loss class remains relevant, but restoring every previously registered harness after an explicit empty scope can retain plugin-owned runtime behavior that the scoped reload intentionally excluded.

## What This Changes

The branch snapshots and restores agent harness registrations around empty plugin-scope activation in the plugin loader and gateway startup path, and adds a loader regression test.

## Best Possible Solution

Define scoped-reload ownership once, then preserve active plugin surfaces by loading and merging only missing requested plugins, or explicitly retain only a documented always-on core harness class rather than restoring all prior plugin-owned entries.

Options:

- **Preserve active registry ownership (recommended):** Adopt the scoped-load merge approach so only missing requested plugins are registered and unrelated active plugin lifecycles are not torn down.
- **Keep only explicit always-on harnesses:** Introduce a narrowly defined ownership class for core provider harnesses and retain only that class across an empty scope.
- **Treat empty scope as authoritative teardown:** Keep empty scope as a full removal and pursue the upstream cause of unexpected empty-scope reloads instead.

The issue requests structured installer error handling with npm error classification, clearer remediation messages, and retry behavior for transient failures.

## Best Possible Solution

Define one conservative installer error policy first, then apply shared diagnostics across POSIX, Windows, install-cli, and Docker setup: retry only clearly transient network errors and provide explicit remediation for permission, disk, engine, package, and TLS failures.

Options:

- **Conservative diagnostics plus transient retries (recommended):** Retry only clearly transient network errors, keep security and local-system failures fail-fast with actionable remediation, and avoid changing best-effort probes without explicit cases.
- **Broader automatic remediation:** Attempt permission and cleanup repairs automatically after classification, accepting more installer-side mutation and a larger compatibility/security review burden.
- **Diagnostics only:** Standardize structured error messages without adding retry or auto-repair behavior, leaving recovery to the user or doctor flows.

## Solution Assessment

Unclear until maintainers choose the policy. Conservative structured diagnostics plus transient-only retries looks like the narrowest maintainable direction, while automatic permission repair and fail-closed probe changes need explicit approval.

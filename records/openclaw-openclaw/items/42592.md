## Summary

Keep open: current main and the latest release still provide partial installer diagnostics and a few targeted retries, but they do not implement the requested cross-platform structured npm error policy, retry classification, or remediation behavior.

## What This Changes

The issue requests structured installer error handling, clearer npm error guidance, and retry/remediation behavior for transient network, permission, disk, package, and engine failures.

## Best Possible Solution

Define a conservative cross-platform installer error policy, then implement shared diagnostics that retry only clearly transient network failures, give explicit remediation for permission/disk/engine/package errors, and preserve security-sensitive failures as explicit operator decisions.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What cross-platform npm installer failure policy should OpenClaw ship for retries, auto-repair, and fail-closed behavior?

Rationale: The requested behavior spans installer UX, npm/network retries, platform-specific permission repair, and security-sensitive failure classes, so automation should not choose retry or remediation semantics without maintainer intent.

Likely owner: steipete

Owner reason: The broad policy crosses POSIX installer diagnostics and Docker setup behavior where steipete has recent path-specific history.

Owner confidence: high

Options:

- **Conservative structured policy (recommended):** Add structured extraction and user-facing remediation while retrying only clearly transient network failures and keeping certificate/security and persistent local failures explicit.
- **Broader automatic repair:** Attempt safe permission or prefix repairs after EACCES-style failures and retry only when the repair succeeds, with platform-specific tests and rollback behavior.
- **Diagnostics-only first:** Keep install execution mostly unchanged while improving error messages and docs, then revisit retries after more live failures are confirmed.

## Reproduction Assessment

Yes, source-level: current main shows generic and targeted installer failure handling rather than a structured npm error-code retry/remediation policy. A live failing npm scenario would still be needed before proving platform-specific repair behavior.

## Solution Assessment

Unclear until maintainers choose the policy boundary: structured diagnostics plus conservative transient retries appears safest, while automatic EACCES repair and any fail-closed behavior need explicit product/security direction.

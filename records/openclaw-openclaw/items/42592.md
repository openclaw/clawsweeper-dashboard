## Summary

Keep open: current main and v2026.6.11 have partial installer diagnostics and ad hoc retries, but they still do not implement the requested cross-platform structured npm error policy; the remaining behavior needs maintainer product/security direction before a fix PR.

## What This Changes

The issue requests structured installer error classification, clearer npm failure guidance, transient retry handling, and safer replacement of broad best-effort error masking.

## Best Possible Solution

Define a maintainer-approved installer error policy, then implement shared POSIX, PowerShell, and install-cli classification that retries only clearly transient network failures and gives explicit remediation for permission, disk, engine, package, and TLS failures.

Rationale: The request spans first-run UX, platform-specific permission repair, optional setup probes, and security-sensitive npm TLS failures, so automation should not choose retry or remediation semantics without maintainer intent.

Options:

- **Conservative diagnostics and transient retries (recommended):** Add structured error extraction and remediation text while retrying only clearly transient network failures and leaving certificate/security and persistent local failures explicit.
- **Broader automatic repair:** Attempt safe permission or prefix repairs after EACCES-style failures and retry when the repair succeeds, with platform-specific tests and rollback behavior.
- **Diagnostics-only first:** Keep install execution behavior mostly unchanged while improving error messages and docs, then revisit retries after specific failures are confirmed.

## Solution Assessment

Unclear until maintainers choose the policy boundary. Structured diagnostics plus conservative transient retries appears safest, while automatic EACCES repair and TLS recovery need explicit product/security direction.

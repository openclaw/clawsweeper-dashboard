## Summary

Keep open: current main and v2026.6.11 still only partially diagnose installer npm failures, while the requested cross-platform retry/remediation policy remains a product and security decision rather than a completed implementation.

## What This Changes

The issue requests structured installer error classification, clearer npm failure guidance, and retry/remediation behavior for transient or fixable install failures.

## Best Possible Solution

Define a conservative installer error policy first, then implement shared POSIX, PowerShell, local-prefix, and Docker-setup diagnostics that retry only clearly transient failures and give explicit remediation for permissions, disk, engine, package, and TLS errors.

## Maintainer Decision

Question: What cross-platform npm installer failure policy should OpenClaw ship for retries, automatic repair, and fail-closed behavior?

Rationale: The request spans first-run UX, retry behavior, optional setup probes, permission repair, and TLS/security-sensitive npm failures, so automation should not choose retry or remediation semantics without maintainer intent.

Likely owner: vincentkoc

Owner reason: Recent history points to vincentkoc as the strongest owner for installer/setup behavior across POSIX, Windows, and local-prefix paths.

Owner confidence: high

Options:

- **Conservative diagnostics and transient retries (recommended):** Add structured error extraction and remediation text while retrying only clearly transient network errors and leaving certificate/security and persistent local failures explicit.
- **Broader automatic repair:** Attempt safe permission or prefix repairs after EACCES-style failures and retry only when the platform-specific repair succeeds with tests and rollback behavior.
- **Diagnostics-only first:** Keep install execution behavior mostly unchanged while improving error messages and docs, then revisit retries after more live failures are confirmed.

## Reproduction Assessment

Yes, source-level: current main shows partial diagnostics and ad hoc retries rather than the requested structured npm error-code retry/remediation policy. A live failing npm scenario would still be useful before implementing platform-specific repair behavior.

## Solution Assessment

Unclear until maintainers choose the policy boundary. Structured diagnostics plus conservative transient retries appears safest, while automatic EACCES repair and fail-closed setup behavior need explicit product/security direction.

## Summary

Keep open: current main and latest release v2026.6.11 still lack a Telegram trusted-owner approval-bypass mode, and adding one would be a security-sensitive product/config decision rather than conservative cleanup.

## What This Changes

The issue requests an opt-in Telegram trusted-owner mode that can bypass approval prompts for configured owner/group/tool-class combinations.

## Best Possible Solution

Design a disabled-by-default shared trusted-owner approval policy that composes with Telegram group authorization, existing elevated and approval policy, action-class and destructive-operation rules, audit records, docs, and live Telegram proof.

Options:

- **Design shared trusted-owner policy (recommended):** Add a disabled-by-default policy with explicit sender, allowlisted group, action-class, destructive-operation, audit, docs, and regression-test semantics across the existing approval stack.
- **Keep existing approval model:** Decline the bypass and document that operators who want no prompts should deliberately use existing elevated full plus permissive host approval policy.
- **Add Telegram-only shortcut:** Implement the proposed Telegram config directly, accepting a smaller patch but higher risk of policy drift from shared approvals and elevated execution.

No live group reproduction was run; at source level, current main has no Telegram trusted-owner approval-bypass config/schema or execution path. The observable behavior is expected under today’s separate group authorization, elevated, and approval gates.

## Solution Assessment

No, not as a bare Telegram boolean. The safer path is a shared approval/elevated policy design that preserves explicit security boundaries and avoids a one-off channel shortcut.

## Summary

Keep this protected security issue open for security-owner validation, but do not implement the proposed ACP changes. Current main has no `src/acp/control-plane/server.ts`, and `src/acp/server.ts` is a stdio-to-authenticated-Gateway-WebSocket bridge rather than an HTTP control plane. A potentially relevant boundary instead exists in the default-off, gateway-authenticated `admin-http-rpc` plugin, which accepts raw JSON POST bodies and exposes configuration mutations; whether browser cross-origin requests can authenticate depends on the configured HTTP auth and deployment mode.

**Likely related people:** @osolmaz for the current ACP control-plane architecture, @steipete for the original ACP bridge and later auth hardening, and @joshavant for gateway credential-resolution work.

## What This Changes

Investigate and prevent cross-origin browser requests from performing configuration-changing control-plane operations.

## Best Possible Solution

Test the actual `admin-http-rpc` endpoint across token, password, trusted-proxy, and explicit no-auth deployments, then enforce a non-forgeable request boundary—such as strict JSON Content-Type plus origin validation or a CSRF token for ambient-auth modes—without changing the non-HTTP ACP bridge.

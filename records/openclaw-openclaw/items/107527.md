## Summary

Keep this protected security issue open for explicit security-owner review. The named ACP files do not establish the reported HTTP path: the ACP bridge is stdio/NDJSON, while the relevant browser-reachable mutation surface is the separate, default-off `admin-http-rpc` plugin; that route requires Gateway HTTP authentication in normal modes, but the documented `auth.mode="none"` and origin-less automation behavior leave an unresolved CSRF boundary that needs a targeted private reproduction. ([github.com](https://github.com/openclaw/openclaw/blob/main/docs.acp.md?utm_source=openai))

Likely related people: `vincentkoc` (high confidence) for the shared Gateway HTTP origin-auth work, and `steipete` (medium confidence) for adjacent Gateway configuration/security ownership.

## What This Changes

Determine whether browser cross-site requests can invoke configuration-changing local Gateway HTTP control-plane methods without an adequate Origin or anti-CSRF check.

## Best Possible Solution

Privately reproduce the admin HTTP RPC route under token, trusted-proxy, and explicit no-auth modes, then enforce the narrowest browser-request protection—Origin validation and strict JSON/content-type handling or a dedicated CSRF mechanism—while preserving authenticated origin-less host automation.

Options:

- **Require private reproduction first (recommended):** Test cross-origin browser requests against the real admin route in each auth mode, then add only the protection demonstrated necessary while retaining origin-less authenticated automation.

- **Confirm private-ingress trust contract:** Treat explicit no-auth private ingress as operator-trusted and close only after a security owner confirms that browsers on the same host/network are intentionally inside that boundary.

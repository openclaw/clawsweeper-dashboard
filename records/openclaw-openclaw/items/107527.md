## Summary

Keep this protected security issue open for security-owner validation, but do not patch the named ACP files: ACP is a stdio-to-authenticated-Gateway-WebSocket bridge, while the relevant configuration-mutation surface is the separate, default-off `admin-http-rpc` plugin. The unresolved question is whether cross-site browser requests can pass that route’s shared HTTP authentication in `trusted-proxy` or explicit `none` deployments. ([github.com](https://github.com/openclaw/openclaw/blob/main/docs.acp.md))

## What This Changes

Determine whether browser-origin requests can execute state-changing Gateway admin HTTP RPC methods without adequate origin or anti-CSRF enforcement.

## Best Possible Solution

Validate a real cross-site request against `POST /api/v1/admin/rpc`, then enforce any confirmed protection in the shared authenticated plugin HTTP-route boundary—preserving non-browser clients without `Origin` while explicitly defining trusted-proxy and no-auth behavior.

Rationale: The current documentation treats the route as trusted host automation, but it also permits identity-proxy and no-auth ingress modes; deciding whether browser-origin access is supported determines whether the correct fix is shared origin enforcement, an explicit opt-in, or documentation/audit hardening.

Options:

- **Require Trusted Browser Origins (recommended):** Reproduce the route first, then reject cross-site browser requests at the shared authenticated HTTP-route boundary while continuing to allow non-browser clients without an `Origin` header.
- **Preserve Trusted-Ingress Contract:** Treat trusted-proxy and explicit no-auth deployments as operator-owned boundaries, adding stronger security-audit and documentation warnings rather than mandatory origin enforcement.
- **Add Explicit Browser Opt-In:** Keep browser-origin admin HTTP requests disabled by default and permit them only through a narrowly documented origin allowlist or plugin setting.

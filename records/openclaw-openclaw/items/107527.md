## Summary

Keep this protected security issue open for a focused Gateway HTTP boundary audit. The named ACP files do not describe current architecture—ACP uses stdio and forwards through the authenticated Gateway WebSocket—and current documentation says browser-origin HTTP requests are origin-checked, but the report has not identified a concrete state-changing HTTP route, request, auth mode, or observed mutation that proves or disproves complete route coverage.

Likely related people
- @joshavant — high-confidence recent contributor to Gateway security-boundary hardening and explicitly routed into this issue.
- @eleqtrizit — high-confidence contributor who added the adjacent MCP loopback browser-origin guard.

## What This Changes

Audit whether local control-plane HTTP routes permit cross-site state-changing requests without origin or anti-CSRF enforcement.

## Best Possible Solution

Have a security owner enumerate every current state-changing Gateway HTTP entry point, verify browser-origin rejection under each supported auth mode, add one shared pre-dispatch origin/CSRF gate where feasible, and cover both allowed same-origin and rejected cross-origin requests with focused tests; move any confirmed exploit details into a private GitHub Security Advisory.

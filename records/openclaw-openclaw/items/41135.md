## Summary

Keep open: current main and v2026.6.11 have auth profiles, order, cooldowns, session pinning, and bounded failure-driven same-provider rotation, but they still do not provide the requested opt-in provider-profile pool routing API with explicit strategies, per-profile in-flight/concurrency state, task/no-stickiness modes, quota/bucket scoring, or pool observability. This remains a product/API design item, not a conservative cleanup close.

## What This Changes

The issue requests an opt-in provider-profile routing layer for multi-account OAuth/API pools with explicit selection policies, concurrency limits, cooldown/failure awareness, and observability.

## Best Possible Solution

Keep this as the canonical design tracker for an opt-in core provider-profile pool API that preserves current session-sticky defaults, reuses auth order/cooldown state where appropriate, and explicitly consolidates narrower key-pool, rotation, and rate-limit follow-ups before implementation.

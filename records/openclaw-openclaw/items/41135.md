## Label Justifications

- `P2`: This is a meaningful provider/auth routing improvement for batch and multi-account users, but it is not a core outage, data-loss event, or security emergency.
- `impact:auth-provider`: The request directly affects provider auth profile selection, OAuth/API-key routing, cooldowns, quota-aware provider choice, and fallback behavior.
- `impact:session-state`: The requested task/no-stickiness modes and pool selection state would change how auth profile choices are pinned or rotated across sessions and worker tasks.

## Summary

Keep open: current main and v2026.6.11 still provide provider-wide auth ordering, session-pinned profile selection, cooldowns, bounded same-provider retries, and status usage snapshots, but not the requested opt-in provider-profile pool routing contract with explicit strategies, per-profile concurrency/in-flight state, quota/bucket/weight metadata, or task/no-stickiness modes.

## What This Changes

Request an opt-in provider-profile pool routing layer for distributing batch or worker requests across multiple OAuth/API-key profiles and endpoints for the same provider.

## Best Possible Solution

Define an additive generic provider/auth-profile routing contract that preserves session-sticky defaults, exposes one minimal observable pool strategy first, and leaves provider-specific quota signals and richer scheduling behind explicit follow-up design.

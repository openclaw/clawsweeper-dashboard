## Summary

Keep open: current main and v2026.6.11 have auth profile order, cooldown, session pinning, and bounded same-provider retry behavior, but they still do not provide the requested opt-in provider-profile pool router with explicit strategies, in-flight/concurrency limits, quota/bucket state, weights, or task/no-stickiness modes.

## What This Changes

The issue requests opt-in provider-profile pool routing policies for multi-account OAuth/API-key/endpoints, including routing strategies, concurrency/in-flight state, cooldown/failure awareness, and observability.

## Best Possible Solution

Define an additive generic provider/auth-profile pool routing contract that preserves current session-sticky and explicit-order defaults, starts with one observable opt-in strategy, and leaves provider-specific quota/bucket semantics to explicit follow-up acceptance criteria.

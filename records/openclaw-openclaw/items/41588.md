## Summary

Keep open: current main and v2026.6.11 mitigate the old 600-second default by raising the default run budget to 48 hours, but configured chat/agent run timeouts still use one wall-clock deadline and the activity-aware idle-vs-hard-cap contract remains a product decision.

## What This Changes

Request activity-aware timeout semantics so productive multi-tool runs are not killed solely by elapsed wall-clock budget.

## Best Possible Solution

Define the core timeout contract first, then land one coordinated implementation that separates activity/idle liveness from a hard safety cap and preserves user-visible timeout notices.

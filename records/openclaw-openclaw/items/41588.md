## Summary

Keep open: current main and v2026.6.11 still enforce agent turns with a fixed run deadline, while related open PRs cover narrower timeout notice, Telegram progress, or subagent idle-watchdog slices rather than the core activity-aware timeout contract.

## What This Changes

Request activity-aware agent run timeout semantics so active multi-tool turns are not killed solely by a flat wall-clock deadline.

## Best Possible Solution

Define a core timeout contract that separates an activity/idle budget from a hard maximum run budget, preserves `timeoutSeconds` upgrade behavior, and aligns the existing notice, Telegram progress, and subagent heartbeat PRs to that contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw keep `timeoutSeconds` as the hard maximum run budget and add a separate activity/idle timeout, or should `timeoutSeconds` itself become activity-aware?

Rationale: Both directions are technically possible, but the choice changes core runtime semantics, config schema, resource ceilings, upgrade behavior, and how the open partial timeout PRs should be reviewed.

Likely owner: steipete

Owner reason: The decision spans the shared agent timeout resolver and gateway abort semantics that Peter Steinberger introduced and previously refactored.

Owner confidence: medium

Options:

- **Add idle timeout plus hard cap (recommended):** Keep `timeoutSeconds` or a successor as the hard ceiling while adding an explicit liveness/idle budget so productive tool-heavy runs can continue without removing runaway protection.
- **Keep wall-clock semantics:** Leave the existing hard timeout contract intact and focus on user-visible timeout notices, progress previews, and per-surface mitigations.
- **Narrow to existing PR slices:** Review the open timeout-notice, Telegram-progress, and subagent-heartbeat PRs separately and defer the broader core timeout contract.

## Reproduction Assessment

Yes. Source inspection on current main shows one resolved run timeout, one gateway `expiresAtMs`, and one maintenance abort path with no reset on LLM or tool progress; I did not run a live 600-second multi-tool turn in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product contract. The safest direction appears to be an idle/liveness timeout plus a hard cap, not reset-only progress or unlimited timeouts.

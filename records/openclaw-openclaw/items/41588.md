## Summary

Keep open: current main and the latest release still use a fixed wall-clock run deadline, while the related open PRs only cover narrower timeout-notice, subagent idle-watchdog, or channel-progress slices.

## What This Changes

Request activity-aware agent run timeout behavior so productive multi-tool turns are not killed solely by total wall-clock time.

## Best Possible Solution

Define a core timeout contract that separates idle or liveness budget from a hard maximum run budget, preserves upgrade behavior for `timeoutSeconds`, and aligns the narrower timeout-notice, subagent-heartbeat, and channel-progress work with that contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw keep `timeoutSeconds` as the hard wall-clock cap and add a separate activity/idle timeout, or should `timeoutSeconds` itself become activity-aware?

Rationale: Both designs are technically plausible, but the choice changes core runtime semantics, config schema, resource ceilings, docs, and how the currently open partial timeout PRs should be reviewed.

Likely owner: steipete

Owner reason: This decision spans gateway abort tracking, agent runtime liveness, and config compatibility, all areas with recent direct history from this owner candidate.

Owner confidence: high

Options:

- **Add idle plus hard cap (recommended):** Introduce an explicit idle/liveness budget while preserving a hard maximum run ceiling so productive turns can continue without removing runaway protection.
- **Only improve timeout visibility:** Keep wall-clock timeout semantics and land only user-visible timeout notices or progress indicators so users understand why long turns stopped.
- **Limit fixes to narrow slices:** Treat subagent idle watchdogs, channel progress previews, and timeout notices as separate fixes and leave the core run-timeout contract unchanged for now.

## Reproduction Assessment

Yes, source-reproducible: current main resolves one timeout budget, registers one fixed `expiresAtMs`, and the maintenance sweep aborts on that deadline; I did not run a live 600-second multi-tool turn.

## Solution Assessment

Unclear until maintainers choose the product contract; the safest direction appears to be idle/liveness timeout plus a hard cap, not reset-only progress or unlimited runtime.

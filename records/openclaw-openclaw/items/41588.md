Kind: product_direction

Question: Should OpenClaw keep `timeoutSeconds` as the hard wall-clock cap and add a separate activity/idle timeout, or should `timeoutSeconds` itself become activity-aware?

Rationale: Both shapes are technically plausible, but the choice changes core runtime semantics, config schema, resource ceilings, and how the existing partial timeout PRs should be reviewed.

Likely owner: steipete

Owner reason: The decision spans gateway abort tracking, agent runtime timeouts, and config compatibility, all areas with recent direct history from this owner candidate.

Owner confidence: medium

Options:

- **Add idle plus hard cap (recommended):** Introduce an explicit idle/liveness budget while keeping a hard maximum run ceiling so productive runs can continue without removing runaway protection.
- **Only improve timeout messaging:** Keep wall-clock timeout semantics and land only user-visible notices/progress so users understand why long turns stopped.
- **Limit fixes to narrow slices:** Treat subagent idle watchdogs, Telegram progress previews, and timeout notices as separate fixes and leave the core run timeout contract unchanged for now.

No, not as a separate tracker anymore. The focused request is valid, but the maintainable path is to fold it into the maintainer-owned bounded-liveness and run-lifecycle contract in https://github.com/openclaw/openclaw/issues/101863.

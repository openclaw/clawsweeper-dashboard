## Summary

Keep open: current main and v2026.6.11 still have a single fixed run deadline, while the remaining request is a core timeout semantics decision rather than a landed implementation.

## What This Changes

Request an activity-aware agent run timeout so active multi-tool runs are not killed solely by the original wall-clock deadline.

## Best Possible Solution

Define a core idle/liveness timeout plus hard maximum run ceiling, preserve upgrade behavior for existing `timeoutSeconds`, and align the narrower notice, Telegram, and subagent PRs to that contract.

Rationale: Both approaches are technically plausible, but the choice changes core runtime semantics, config schema, resource ceilings, and how the open partial timeout PRs should be reviewed.

Owner confidence: medium

Options:

- **Add idle plus hard cap (recommended):** Introduce an explicit idle/liveness budget while keeping a hard maximum run ceiling so productive runs can continue without removing runaway protection.
- **Only improve timeout messaging:** Keep wall-clock timeout semantics and land only user-visible notices or progress so users understand why long turns stopped.
- **Limit fixes to narrow slices:** Treat subagent idle watchdogs, Telegram progress previews, and timeout notices as separate fixes while leaving the core run timeout contract unchanged for now.

## Reproduction Assessment

Yes, by source inspection: current main resolves one timeout budget, registers one `expiresAtMs`, and the maintenance sweep aborts on that fixed deadline. I did not run a live long multi-tool turn in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product contract. The safest direction appears to be an idle/liveness timeout plus a hard cap, not reset-only progress or unlimited timeouts.

## Summary

Keep open: current main and v2026.6.11 still use one wall-clock run deadline, while the related open PRs cover narrower timeout notice, Telegram progress, or subagent idle-watchdog slices rather than the core activity-aware timeout contract.

## What This Changes

Request an activity-aware agent run timeout so active multi-tool turns are not aborted only because the original wall-clock budget elapsed.

## Best Possible Solution

Define a core timeout contract that separates liveness or idle budget from a hard maximum run budget, preserves upgrade behavior for `timeoutSeconds`, and lets narrower notice/channel/subagent PRs align with that contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw keep `timeoutSeconds` as the hard wall-clock cap and add a separate activity/idle timeout, or should `timeoutSeconds` itself become activity-aware?

Rationale: Both shapes are technically plausible, but the choice changes core runtime semantics, config schema, resource ceilings, and how the existing partial timeout PRs should be reviewed.

Likely owner: steipete

Owner reason: The decision spans gateway abort tracking, agent runtime timeouts, and config compatibility, all areas with recent direct history from this owner candidate.

Owner confidence: medium

Options:

- **Add idle plus hard cap (recommended):** Introduce an explicit idle/liveness budget while keeping a hard maximum run ceiling so productive runs can continue without removing runaway protection.
- **Only improve timeout messaging:** Keep wall-clock timeout semantics and land only user-visible notices/progress so users understand why long turns stopped.
- **Limit fixes to narrow slices:** Treat subagent idle watchdogs, Telegram progress previews, and timeout notices as separate fixes and leave the core run timeout contract unchanged for now.

## Reproduction Assessment

Yes, by source inspection: current main resolves one timeout budget, registers one `expiresAtMs`, and the maintenance sweep aborts on that fixed deadline. I did not run a live 600-second multi-tool turn in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product contract. The safest direction appears to be an idle/liveness timeout plus a hard cap, not reset-only progress or unlimited timeouts.

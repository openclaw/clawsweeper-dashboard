## Summary

Keep open: current main and v2026.6.11 mitigate the original 600-second default by using a 48-hour default and supporting explicit zero-timeout overrides, but configured runs still use one wall-clock deadline. The activity-aware idle-vs-hard-cap behavior remains unimplemented and needs a maintainer product/config decision.

## What This Changes

Request activity-aware run timeout semantics so active multi-tool agent runs are not killed by a single wall-clock `agents.defaults.timeoutSeconds` deadline.

## Best Possible Solution

Define one core timeout contract that separates activity/liveness from an absolute safety cap, preserves shipped defaults or adds a doctor-backed migration if config changes, and lets narrower PRs land only as pieces of that contract.

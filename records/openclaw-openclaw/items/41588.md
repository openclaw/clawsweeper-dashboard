## Summary

Keep open: current main still enforces the central run budget as fixed wall-clock deadlines, while the related open PRs address narrower timeout-notice, Telegram progress, or subagent idle-watchdog slices rather than the requested activity-aware core timeout contract.

## What This Changes

Request an activity-aware agent/gateway run timeout so active multi-tool turns are not killed only because the original wall-clock budget elapsed.

## Best Possible Solution

Define a core timeout contract that separates an activity or idle budget from a hard maximum run budget, preserves upgrade behavior for `timeoutSeconds`, and aligns the narrower notice, Telegram progress, and subagent heartbeat PRs under that contract.

## Maintainer Decision

Question: Should OpenClaw keep `timeoutSeconds` as the hard wall-clock ceiling and add a separate activity/idle timeout, or should `timeoutSeconds` itself become activity-aware?

Rationale: Both shapes are technically plausible, but the choice changes core runtime semantics, config schema, runaway-resource protection, and how the open partial timeout PRs should be reviewed.

Owner confidence: high

Options:

- **Add idle budget plus hard cap (recommended):** Introduce an explicit liveness/idle budget while preserving a hard maximum run ceiling and a compatibility plan for existing `timeoutSeconds` users.
- **Keep wall-clock semantics and improve UX:** Leave the current hard wall-clock budget unchanged and land only notices/progress improvements so users understand long-turn failures.
- **Limit work to narrow slices:** Treat subagent idle watchdogs, Telegram progress previews, and timeout notices as independent fixes and defer the core timeout contract.

## Reproduction Assessment

Yes, by source inspection: current main resolves one run timeout, stores one `expiresAtMs`, and aborts when that fixed deadline expires. I did not run a live 600-second multi-tool turn in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product contract. The safest direction appears to be an explicit idle/liveness timeout plus a hard cap, not reset-only progress or unlimited timeouts.

## Summary

Keep open: current main and shipped releases have mitigated the original 600-second default by raising the default agent runtime budget to 48 hours, but the remaining request is still real because core chat/agent runs are still governed by one wall-clock deadline rather than an activity-aware idle timeout plus hard cap.

## What This Changes

The issue requests activity-aware agent run timeout semantics so active multi-tool runs are not killed solely because a flat wall-clock budget expires.

## Best Possible Solution

Define a core timeout contract that keeps a hard wall-clock safety cap while adding or explicitly rejecting activity-based idle semantics, then land the narrow related PRs that match that decision with docs and regression proof.

Yes, source inspection gives a high-confidence reproduction path without executing a long live run: configure a lower agents.defaults.timeoutSeconds and run an active tool-heavy turn longer than that deadline.

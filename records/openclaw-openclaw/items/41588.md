## Summary

Keep open: current main still has a single run timeout deadline, while the open related PRs address narrower timeout notices, Telegram progress, or subagent idle-watchdog behavior rather than the core activity-aware run timeout contract.

## What This Changes

The issue requests timeout semantics that do not kill active multi-tool agent runs solely because a fixed wall-clock deadline elapsed.

## Best Possible Solution

Define a core timeout contract that separates an idle or liveness budget from a hard maximum run budget, preserves upgrade behavior for `timeoutSeconds`, and then align the narrower notice, Telegram, and subagent PRs with that contract.

Rationale: Both shapes are technically plausible, but the choice changes core runtime semantics, config schema, resource ceilings, and how the existing partial timeout PRs should be reviewed.

Owner confidence: medium

Options:

- **Add idle plus hard cap (recommended):** Introduce an explicit idle/liveness budget while keeping a hard maximum run ceiling so productive runs can continue without removing runaway protection.
- **Only improve timeout messaging:** Keep wall-clock timeout semantics and land user-visible timeout notices or progress previews so users understand why long turns stopped.
- **Limit fixes to narrow slices:** Treat subagent idle watchdogs, Telegram progress previews, and timeout notices as separate fixes while leaving the core run timeout contract unchanged for now.

## Reproduction Assessment

Yes, by source inspection: current main resolves one timeout budget, registers one `expiresAtMs`, and the maintenance sweep aborts on that fixed deadline. I did not run a live 600-second multi-tool turn in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product contract. The safest direction appears to be an idle/liveness timeout plus a hard cap, not reset-only progress or unlimited timeouts.

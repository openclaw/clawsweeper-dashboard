## Summary

Keep open: current main and the latest release still use one fixed run deadline, while the open related PRs cover narrower timeout-notice, Telegram-progress, or subagent-idle symptoms. The remaining work is a core timeout-semantics and compatibility decision, not an already-implemented cleanup item.

## What This Changes

The issue requests activity-aware agent run timeout behavior so productive multi-tool runs are not killed only because the configured wall-clock budget elapsed.

## Best Possible Solution

Define a core run-timeout contract with an activity or idle budget plus a hard maximum ceiling, then align chat.send, agent RPC, embedded runner activity boundaries, timeout notices, docs, and any upgrade-safe config/default behavior to that contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw keep timeoutSeconds as the hard maximum run cap and add a separate activity/idle timeout, or should timeoutSeconds itself become activity-aware?

Rationale: Both designs are technically plausible, but the choice changes core runtime semantics, config schema, resource ceilings, and the review direction for the open partial timeout PRs.

Likely owner: steipete

Owner reason: The decision spans the timeout resolver, gateway abort tracking, and gateway maintenance paths that his commits introduced or refactored.

Owner confidence: high

Options:

- **Add idle plus hard cap (recommended):** Introduce an explicit idle/liveness budget while keeping a hard maximum run ceiling so productive runs can continue without removing runaway protection.
- **Only improve timeout messaging:** Keep wall-clock timeout semantics and land only user-visible notices or progress so users understand why long turns stopped.
- **Limit fixes to narrow slices:** Treat subagent idle watchdogs, Telegram progress previews, and timeout notices as separate fixes while leaving the core run timeout contract unchanged for now.

## Reproduction Assessment

Yes, by source inspection: current main resolves one timeout budget, registers one expiresAtMs, and the maintenance sweep aborts on that fixed deadline. I did not run a live long multi-tool turn in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product contract. The safest direction appears to be an idle/liveness timeout plus a hard cap, not reset-only progress or unlimited timeouts.

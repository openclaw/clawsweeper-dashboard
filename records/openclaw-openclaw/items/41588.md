- `impact:message-loss`: The report describes completed tool work being followed by no assistant response when the run deadline aborts the turn.

## Summary

Keep open: current main and v2026.6.11 still use a fixed gateway run deadline, so active tool/model progress does not reset the outer run timeout. The old 600s default has been mitigated by a 48h default and per-run no-timeout override handling, but the broad activity-aware timeout contract is not implemented and the linked open PRs cover narrower slices.

## What This Changes

Request activity-aware agent run timeout semantics so active multi-tool runs are not killed solely by the original wall-clock `agents.defaults.timeoutSeconds` deadline.

## Best Possible Solution

Keep this issue open as the canonical product/design decision for core activity-aware run budgets, then land a narrow implementation that preserves an absolute safety cap and makes timeout termination user-visible.

- **Notice-only mitigation:** Keep the wall-clock deadline but prioritize the open timeout-notice work so users get a clear failure instead of silence.

## Reproduction Assessment

Yes, from source inspection: current main still registers one fixed `expiresAtMs` for chat/agent runs and the maintenance sweep aborts when that wall-clock timestamp expires, without resetting on tool or model progress. I did not run a live long-turn reproduction in this read-only review.

## Solution Assessment

Unclear until maintainers choose the product contract. The safest shape appears to be idle/activity timeout plus an absolute max-run cap and user-visible timeout notices, not an unlimited timeout or a tool-progress-only reset with no cap.

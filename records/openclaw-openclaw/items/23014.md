Keep open. Current main still does not classify `.m2a` as audio across the shared media and UI fallback paths, and https://github.com/openclaw/openclaw/pull/92167 is the active open implementation candidate that uses closing syntax for this issue.

## What This Changes

Request to classify `.m2a` audio attachments as audio across Telegram and shared media handling so agents can accept and process them like other supported audio formats.

## Best Possible Solution

Review and land a focused implementation that maps `.m2a` to the correct audio MIME in shared media helpers and updates the sibling filename-based audio surfaces, then close this issue after the fix merges.

## Reproduction Assessment

Yes, at source level. Current main omits `.m2a` from shared audio classifiers, voice compatibility, UI transcript fallback, and memory audio extension lists, so filename-only `.m2a` attachments cannot consistently enter existing audio paths.

## Solution Assessment

Yes, the best direction is a focused shared media classification update plus sibling fallback coverage, not a Telegram-only workaround. The active linked PR is the right ownership path to review before closing this issue.

## Summary

Keep this PR open for maintainer review. The cache-boundary review concern was addressed in the latest head, and the supplied real-install timing evidence plus focused tests support the CLI responsiveness fix; however, the patch deliberately changes automatic preflight from full-database detection to a scoped check, so a maintainer must explicitly accept the resulting integrity-reporting boundary before merge.

## What This Changes

This PR lets ordinary CLI and TUI startup use a scoped integrity preflight for an already-current shared SQLite state database, while retaining full checks for Doctor, schema migrations, quarantined databases, and gateway checkpoint paths.

## System Context

Before many CLI commands start, OpenClaw runs configuration and state-migration preflight against the shared SQLite state database. The proposed change selects a lightweight current-schema gate for ordinary commands, while explicit repair and migration-owner paths continue to use full verification.

## Architecture Diagram

flowchart LR
  Command[CLI or TUI command] --> Bootstrap[Configuration preflight]
  Bootstrap --> Migration[Legacy state migration check]
  Migration --> Schema[State schema preflight]
  Schema --> Scoped[Scoped current-schema check]
  Schema --> Full[Full integrity and repair path]
  Scoped --> Run[Requested command runs]
  Full --> Run
  Doctor[Explicit Doctor or migration owner] --> Full

## Best Possible Solution

Accept the scoped CLI gate only if maintainers explicitly want ordinary commands to prioritize startup responsiveness while retaining a clear, reliable full-verification route for integrity diagnosis and repair; otherwise keep automatic CLI preflight full or add a user-visible escalation/reporting path.

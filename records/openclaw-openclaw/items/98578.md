## Summary

Keep this PR open, but do not merge it as-is. The V2 patch fixes the destructive archive wipe for human `[cron:]` text, but its new opacity flag is not honored by the `memory_search` indexing path, so no-metadata cron archives can still return non-empty content that gets indexed.

## What This Changes

The PR changes `buildSessionEntry` so usage-counted archives no longer wipe or skip content when a user-role message matches `[cron:]`, adds an `archiveOpaqueByCronPromptText` flag, and updates memory-host-sdk tests.

## Best Possible Solution

Land one canonical fix that keeps ordinary human `[cron:]` archive content searchable while preserving, or explicitly changing with maintainer approval, the no-metadata cron archive privacy boundary in the actual memory indexing path.

## Reproduction Assessment

Yes, at source level. Current main clears archive content after a user-role `[cron:]` prefix, and PR head can return `generatedByCronRun: true` with non-empty content that the session memory indexer still chunks.

## Solution Assessment

No. The PR fixes the destructive wipe, but using `generatedByCronRun` as a returned opacity marker is not the best solution because the `memory_search` indexing path does not honor that marker.

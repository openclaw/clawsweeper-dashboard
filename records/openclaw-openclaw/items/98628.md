## Summary

Keep open: the code now appears to preserve the prior empty/malformed-body fallback while adding a bounded read, but the contributor proof is still helper-level rather than changed-path proof through the exported Discord webhook sender.

## What This Changes

The PR changes Discord webhook success-response parsing from unbounded `response.json()` to a 1 MiB `readResponseWithLimit` read with tolerant JSON fallback, and adds a loopback proof script.

## Best Possible Solution

Keep the bounded read and tolerant parse, but require redacted changed-path proof through `sendWebhookMessageDiscord` before merge and have maintainers explicitly accept the 1 MiB success-response cap.

## Reproduction Assessment

Yes. Current main has a source-level reproduction for the unbounded success-response read because `sendWebhookMessageDiscord` calls native `response.json()` after `response.ok`.

## Solution Assessment

Mostly yes for the code path: the cap belongs at the webhook success read site and the PR now preserves the existing tolerant fallback. The proof path is not the best way to prove the fix because it bypasses the exported webhook sender and duplicates the parse logic.

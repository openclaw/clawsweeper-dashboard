## Summary

Keep open: current main and the latest release still perform one ordinary OAuth refresh attempt before fallback/error handling, and the remaining work needs auth-owner policy review rather than cleanup close.

## What This Changes

The issue requests bounded retry behavior for transient OAuth token refresh failures so agents do not fail on a single temporary provider/API error.

## Best Possible Solution

Add bounded retry at the centralized OAuth manager boundary using retryAsync, an auth-owner-approved transient classifier, and focused tests that preserve locking, adoption/fallback, plugin hooks, and refresh-token-reuse recovery.

## Reproduction Assessment

Yes, by source inspection rather than a live transient-provider failure. An expired or forced OAuth refresh invokes one provider refresh call, and current tests show HTTP 500 and network timeout do not enter the only specialized recovery branch.

## Solution Assessment

No, the issue body's local withRetry wrapper around getOAuthApiKey is not the best final shape. The safer solution belongs at the centralized OAuth manager boundary with retryAsync, a transient-error classifier, and auth-owner timing semantics.

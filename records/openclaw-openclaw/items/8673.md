## Summary

Keep open: current main and the latest release still perform one ordinary OAuth refresh attempt for transient provider/API failures, while existing recovery only retries the special refresh-token-reuse race and adjacent MCP/Codex work does not cover this generic auth-profile retry gap.

## What This Changes

Add bounded retry behavior for OAuth token refresh so transient network or provider/API failures do not immediately fail agent runs.

## Best Possible Solution

Add a bounded transient-error retry policy in the shared OAuth refresh owner path, preserving the existing lock, timeout, external-credential adoption, fallback, and refresh-token-reuse recovery behavior.

## Reproduction Assessment

Yes, by source inspection: current main has a single ordinary refresh call, and tests keep HTTP 500/network timeout outside the existing refresh-token-reuse recovery. I did not run a live upstream transient-provider failure because that would require real OAuth credentials and induced provider/network failure.

## Solution Assessment

No for the literal proposed local helper; the maintainable direction is to reuse the existing shared retry utility with a provider-safe transient-error classifier. The requested outcome is still valid, but the retry budget and classifier need auth-owner review before implementation.

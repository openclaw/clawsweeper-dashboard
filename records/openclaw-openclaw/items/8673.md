## Summary

Keep this issue open: current main and v2026.6.11 still make one ordinary OAuth provider refresh attempt, so a transient network or server failure can terminate an otherwise recoverable agent run; implementation should wait for an auth owner to approve the cross-provider retry classifier and total latency budget.

## What This Changes

Add bounded retry and backoff for transient OAuth token refresh failures without retrying terminal authentication errors.

## Best Possible Solution

Use the shared retry primitive at the canonical refresh owner boundary, retry only typed network, timeout, 408, 429, and retryable 5xx failures within a fixed total budget, and preserve current locking, credential adoption, token-reuse recovery, persistence, and fallback semantics.

Options:

- **Adopt classified shared retries (recommended):** Retry only typed transient network, timeout, 408, 429, and retryable 5xx failures with jitter and a strict total latency cap.
- **Keep retries provider-owned:** Require each provider refresh adapter to define its own retry policy and leave the shared manager single-shot.
- **Keep single-shot refresh:** Decline refresh retries and rely on credential adoption, profile fallback, clearer diagnostics, and reauthentication recovery.

## Reproduction Assessment

No live current-main failure was reproduced, but there is a high-confidence source reproduction: ordinary provider refresh errors receive one attempt, while the only second-attempt branch is limited to refresh_token_reused credential adoption.

## Solution Assessment

No, the proposed unconditional local withRetry wrapper is not the best fix because it can retry terminal OAuth failures and duplicate repository infrastructure; the narrow maintainable solution is a shared, typed, bounded retry policy integrated with the existing manager lifecycle.

## Risks / Open Questions

- Retrying every thrown refresh error could repeat terminal failures such as invalid_grant, revoked credentials, malformed requests, or rotating-token errors instead of failing promptly.
- Backoff occurs inside a serialized refresh lifecycle, so the attempt count and delays must remain within the refresh timeout and lock-staleness budgets to avoid increasing contention or agent latency.
- Some upstream or provider wrappers may discard HTTP status and cause details, making a reliable cross-provider transient-error classifier incomplete without preserving typed error metadata.

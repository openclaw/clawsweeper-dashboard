- `impact:auth-provider`: The issue directly concerns OAuth token refresh and continued provider authentication.

## Summary

Keep open: current main and v2026.6.11 still perform a single ordinary auth-profile OAuth refresh attempt for transient provider/API failures; current recovery covers timeouts, credential adoption, refresh-token-reuse recovery, and adjacent MCP/session cases, but not the generic retry requested here.

## What This Changes

The issue asks OpenClaw to retry transient OAuth token refresh API failures so agents do not fail on a single network blip or provider timeout.

## Best Possible Solution

Add bounded retry at the centralized OAuth manager refresh boundary using retryAsync, an auth-owner-approved transient classifier, and tests that preserve locking, adoption/fallback, plugin hooks, and refresh-token-reuse recovery.

## Reproduction Assessment

Yes, by source inspection rather than a live transient-provider failure. An expired or forced OAuth refresh invokes one provider refresh call, and current tests show HTTP 500 and network timeout do not enter the only specialized recovery branch.

## Solution Assessment

No, the issue's local withRetry wrapper around getOAuthApiKey is not the best final shape. The safer solution belongs at the centralized OAuth manager boundary with retryAsync, a transient-error classifier, and auth-owner timing semantics.

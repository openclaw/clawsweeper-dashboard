## Summary

Keep open: current main and the latest release still perform one ordinary OAuth refresh attempt, with only refresh-token-reuse recovery providing a second attempt. The remaining work is real, but it needs maintainer direction for retryable-error classification, retry budget, and provider/plugin semantics before implementation.

## What This Changes

The issue requests bounded retry logic for OAuth token refresh so transient provider or network failures do not immediately fail agents.

## Best Possible Solution

Implement bounded retry at the centralized OAuth manager boundary using retryAsync and an auth-owner-approved transient-error classifier, while preserving locks, adoption/fallback, plugin hooks, and refresh-token-reuse recovery.

## Reproduction Assessment

Yes, by source inspection rather than a live transient-provider failure. An expired or forced OAuth refresh invokes one provider refresh call, and current tests show HTTP 500 and network timeout do not enter the only specialized recovery branch.

## Solution Assessment

No, the issue's proposed local withRetry wrapper around getOAuthApiKey is only a plausible fix shape. The safer solution belongs at the centralized OAuth manager boundary with retryAsync, an explicit transient-error classifier, and owner-approved timing semantics.

## Risks / Open Questions

- Retrying every OAuth refresh failure could repeat terminal failures such as invalid_grant, revoked credentials, malformed token responses, or provider-specific permanent errors.
- Retry count and backoff need to fit the existing hard refresh-call timeout and global refresh-lock budget so other waiting agents are not stalled unexpectedly.
- Provider plugin refresh hooks may already retry internally, so the shared contract should avoid surprising double-retry behavior.

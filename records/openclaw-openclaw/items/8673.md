## Label Justifications

- `P2`: Transient OAuth refresh failures can interrupt OAuth-backed provider calls, but the blast radius is limited to affected auth/provider workflows and has restart or later-retry workarounds.
- `impact:auth-provider`: The issue directly concerns OAuth token refresh and continued provider authentication.

## Summary

Keep open: current main and v2026.6.11 still perform a single ordinary OAuth refresh attempt for transient provider/API failures; existing recovery only covers changed stored credentials and the specialized refresh-token-reuse path, while the direct retry PRs are closed unmerged.

## What This Changes

Add bounded retry handling for transient OAuth token refresh failures so temporary network or API errors do not immediately fail OAuth-backed agents.

## Best Possible Solution

Add bounded retry at the centralized OAuth manager boundary using retryAsync, an auth-owner-approved transient classifier, and tests that preserve locking, adoption/fallback, plugin hooks, and refresh-token-reuse recovery.

## Reproduction Assessment

Yes, by source inspection rather than a live transient-provider failure. An expired or forced OAuth refresh invokes one provider refresh call, and current tests show HTTP 500 and network timeout do not enter the only specialized recovery branch.

## Solution Assessment

No, the issue's local withRetry wrapper around getOAuthApiKey is not the best final shape. The safer solution belongs at the centralized OAuth manager boundary with retryAsync, a transient-error classifier, and auth-owner timing semantics.

## Risks / Open Questions

- A retry policy needs a narrow transient-error classifier so invalid_grant, revoked refresh tokens, malformed token responses, and other permanent OAuth failures are not retried as temporary failures.
- The retry budget and backoff need to fit the existing hard refresh-call timeout and global refresh lock so waiting agents are not stalled unexpectedly.
- Provider plugin refresh hooks may already retry internally, so shared core retry could create double-retry semantics without an explicit contract.

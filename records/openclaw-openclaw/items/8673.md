- `impact:auth-provider`: The request directly concerns provider OAuth refresh, credential resolution, and auth failure handling.

## Summary

Current main and v2026.6.11 still make one ordinary provider refresh attempt; existing recovery covers serialization, credential adoption, timeouts, and refresh-token reuse rather than transient network or server failures. Keep this open for an auth-owner decision on the shared retry contract.

## What This Changes

Request bounded retries for transient OAuth token-refresh failures so temporary provider or network errors do not immediately fail agent work.

## Best Possible Solution

Define a provider-safe transient failure classifier, then use the shared retry utility for a small bounded retry inside the existing serialized refresh operation while preserving terminal-error, token-reuse, adoption, persistence, and timeout behavior.

Question: Should shared auth-profile refresh automatically retry transient provider/network failures, and which error classes and total time budget are allowed?

Rationale: The code has no canonical cross-provider retry contract, and the choice affects built-in providers plus plugin refresh hooks, rotating credentials, lock duration, and user-visible auth failure timing.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Retry classified transient failures (recommended):** Retry a bounded set such as network errors, timeouts, 5xx, and explicitly supported rate limits while excluding terminal OAuth and malformed-success failures.
- **Keep single-shot refresh:** Preserve the current contract and rely on credential adoption, provider-specific behavior, and a later agent request or gateway restart for recovery.
- **Make retries provider-owned:** Require each provider or plugin refresh implementation to declare and implement its own retry policy instead of applying a shared manager rule.

## Reproduction Assessment

Yes at source level: an expired credential reaches one provider/plugin refresh call, and an ordinary transient rejection proceeds to fallback and final error handling without another authority attempt. This read-only review did not inject a failure against a live upstream provider.

## Solution Assessment

No, the proposed retry-every-exception helper is too broad. The best fix is a bounded shared retry gated by a tested transient-versus-terminal classifier and constrained by the existing refresh lock and timeout contracts.

## Summary

Keep this issue open. The supplied maintainer review and current issue context still identify a one-shot ordinary OAuth refresh path; choosing a cross-provider transient-error classifier and total retry latency remains an auth-policy decision rather than a safe generic wrapper change.

## What This Changes

Add bounded retry handling for transient failures while refreshing OAuth credentials used by auth profiles.

## Best Possible Solution

Add a bounded auth-profile retry policy around only classified transient refresh failures, reuse the repository retry primitive, preserve locking/adoption/reused-token recovery, and cover success-after-retry, exhaustion, and non-retryable OAuth errors.

Rationale: The requested behavior changes cross-provider authentication failure semantics and lock-held latency; current code distinguishes terminal reuse/auth failures from recoverable paths, but no established generic retry contract is evidenced.

Owner confidence: high

Options:

- **Approve narrow transient retries (recommended):** Retry only transport/timeouts and explicitly classified retryable server responses within a short shared budget, then preserve the existing final error and failover path.
- **Keep single-attempt refresh:** Retain current locking and specialized recovery only, leaving ordinary transient failures to the existing failover and re-authentication behavior.
- **Define provider-owned policies:** Require each OAuth provider adapter to expose its own retryable-error classification before introducing shared retries.

## Solution Assessment

No: the proposed unconditional local withRetry helper is not the best fix because it would conflate transient transport failures with terminal OAuth errors; a shared bounded policy with an explicit classifier is safer.

## Summary

Keep this issue open. The current auth-profile flow still needs an explicit cross-provider decision on which OAuth refresh failures are transient and how bounded retries interact with the existing refresh lock, timeout, credential-adoption, and terminal-failure paths; the two directly related retry PRs were closed unmerged.

## What This Changes

Add bounded retry handling for transient OAuth token-refresh failures so an agent does not fail after one recoverable upstream refresh error.

## System Context

OpenClaw’s auth-profile manager resolves credentials for agent model calls and delegates OAuth refreshes to provider adapters. It coordinates concurrent refreshes and stored-credential adoption before returning usable credentials or an auth failure to the calling agent.

## Architecture Diagram

flowchart LR
  A[Agent model call] --> B[Auth-profile resolution]
  B --> C[OAuth refresh manager]
  C --> D[Refresh lock and timeout]
  D --> E[Provider OAuth refresh]
  E --> F[Credential adoption or persistence]
  F --> G[Usable credentials or auth failure]

## Best Possible Solution

Define a shared, bounded retry contract in the OAuth manager for clearly transient provider failures, reuse the repository retry primitive, preserve the current lock/adoption/reused-token behavior, and add focused coverage for recovery, exhaustion, and non-retryable failures.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Retry classified transient failures (recommended):** Define a small shared classifier for network, timeout, and selected retryable upstream failures, then use bounded retry with a lock-aware total latency budget.
- **Keep single-shot refresh:** Retain the existing timeout and fallback behavior if predictable auth latency is more important than recovering transient upstream failures.
- **Retry only in specific provider owners:** Keep the shared manager single-shot and let providers with reliable error contracts opt into their own retry behavior.

## Reproduction Assessment

No live current-main provider failure was reproduced in this review, but the source-level path is clear: an adapter refresh is single-shot except for the distinct refresh-token-reused credential-race recovery path.

## Solution Assessment

No—the proposed local retry wrapper is not the best final shape because it retries without a provider-safe error contract or lock-held latency policy; the shared manager should own any generic bounded retry behavior.

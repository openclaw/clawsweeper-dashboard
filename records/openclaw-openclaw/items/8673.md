## Summary

Keep this issue open: current main and v2026.6.11 still perform ordinary OAuth credential refresh as a single attempt, while a safe generic retry requires auth-owner agreement on retryable failures and the maximum latency added while refresh serialization is held.

## What This Changes

Requests bounded retry handling for transient OAuth token-refresh failures.

## Best Possible Solution

Add bounded retry at the shared manager/adapter refresh boundary using retryAsync, limited to provider-safe transient network, timeout, throttling, and server failures, while preserving credential adoption, refresh_token_reused recovery, final-error semantics, and focused non-retry coverage for permanent OAuth failures.

Owner confidence: high

Options:

- **Retry classified transient failures (recommended):** Use the shared retry primitive for a small bounded set of network, timeout, throttling, and 5xx failures while immediately surfacing permanent OAuth errors.
- **Keep retries provider-owned:** Require each provider plugin to classify and retry its own refresh failures, avoiding a generic core policy but producing provider-by-provider behavior.
- **Retain single-attempt refresh:** Keep current behavior and rely on credential adoption, fallback, restart, or reauthentication rather than adding refresh retries.

## Reproduction Assessment

No live current-main failure was reproduced in this review, but the source path is high-confidence: an adapter refresh that throws a transient network or server error is attempted once and then enters existing fallback/error handling.

## Solution Assessment

No—the proposed unconditional wrapper around getOAuthApiKey is not the best fix because it can retry permanent failures and misses provider-plugin refresh hooks; the shared manager boundary with an explicit transient classifier is narrower and more complete.

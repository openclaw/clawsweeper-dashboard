## Summary

Keep this issue open. The latest available source-backed review found the shared OAuth refresh path still makes one provider refresh call under a lock and timeout; ordinary transient failures are not retried, while the existing second-attempt behavior is limited to the changed-credential `refresh_token_reused` race. A retry policy is warranted for stability, but the cross-provider retryable-error contract and lock-held latency need an auth-owner decision before implementation.

## What This Changes

Add bounded retry handling for transient OAuth token-refresh failures so a temporary provider or network failure does not immediately fail an agent request.

## System Context

Auth profiles hold provider credentials used by model requests. When an OAuth access token is expired, the auth-profile manager refreshes it under coordination and then returns the refreshed credential or existing fallback/error outcome to provider routing.

## Architecture Diagram

flowchart LR
  A[Model request] --> B[Auth profile resolution]
  B --> C{OAuth token expired?}
  C -- No --> D[Use stored access token]
  C -- Yes --> E[Refresh lock and timeout]
  E --> F[Provider or plugin refresh]
  F --> G[Credential adoption, fallback, or error]
  G --> H[Provider routing]

## Best Possible Solution

Add a small auth-profile retry policy using the existing retry primitive: retry only provider-safe transient failures within a bounded total latency budget, preserve lock/adoption/fallback and `refresh_token_reused` semantics, and cover success-after-transient-failure, exhaustion, and non-retryable terminal failures.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which provider-error classes may be retried during a locked OAuth refresh, and what maximum lock-held latency is acceptable before the existing fallback/error path must run?

Rationale: The correct classifier varies by provider and token-rotation behavior; an unconditional generic retry would alter authentication failure semantics and contention behavior for existing deployments.

Likely owner: vincentkoc

Owner reason: The central OAuth-manager lifecycle and refresh flow are most closely tied to this history.

Owner confidence: high

Options:

- **Adopt a narrow shared transient classifier (recommended):** Retry only clearly transient transport, timeout, and selected 5xx/rate-limit failures with a short bounded budget, while never retrying terminal OAuth failures.
- **Keep single-shot refresh:** Retain the current lock, adoption, and fallback behavior until provider-specific retry contracts are defined.
- **Define provider-owned policies:** Let each provider/plugin explicitly opt into retryable refresh errors, trading a clearer contract for more implementation work.

## Reproduction Assessment

No high-confidence live reproduction is available in the current evidence; source and existing tests establish that ordinary transient refresh errors bypass the narrow reused-token recovery branch, but no current provider round trip was run.

## Solution Assessment

No—the issue's unconditional local retry helper is not the best fix because it retries terminal OAuth errors and ignores refresh-lock latency. A shared bounded retry primitive with an explicit transient classifier is the safer maintainable path.

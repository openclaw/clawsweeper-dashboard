## Label Justifications

- `P2`: Transient OAuth refresh failures can interrupt OAuth-backed provider calls, but the blast radius is limited to affected auth/provider workflows and has restart or later-retry workarounds.
- `impact:auth-provider`: The issue directly concerns OAuth token refresh and continued provider authentication.

## Summary

Keep open: current main still performs a single ordinary OAuth refresh attempt for transient provider/API failures, and the direct retry PRs are closed unmerged. A fix still needs auth-owner policy for retryable errors, timeout interaction, and provider-plugin semantics.

## What This Changes

The issue requests bounded retry/backoff for transient OAuth token-refresh failures so agents do not fail after a single network or provider API error.

## Best Possible Solution

Add bounded retry at the centralized OAuth manager boundary using retryAsync, an auth-owner-approved transient classifier, and tests that preserve locking, adoption/fallback, plugin hooks, and refresh-token-reuse recovery.

## Reproduction Assessment

Yes. The issue is source-reproducible: expired or forced OAuth refresh flows through one adapter.refreshCredential/getOAuthApiKey call, and current tests show HTTP 500 and network timeout do not match the existing refresh_token_reused recovery branch.

## Solution Assessment

No. The local withRetry wrapper proposed in the issue is plausible, but the maintainable fix belongs at the centralized OAuth manager boundary with retryAsync, a transient-error classifier, and explicit auth-owner timing semantics.

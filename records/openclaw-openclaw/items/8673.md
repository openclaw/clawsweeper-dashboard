## Summary

Keep open: current main and the latest release still lack generic bounded retry for ordinary transient OAuth refresh failures; existing recovery covers credential adoption and the specialized refresh-token-reuse path, but not HTTP 500/network-timeout style refresh failures.

## What This Changes

The issue requests bounded retry behavior for transient OAuth token refresh failures so agents do not fail immediately on a single network or provider timeout.

## Best Possible Solution

Add bounded retry at the centralized OAuth manager/auth-profile refresh boundary using retryAsync, an auth-owner-approved transient classifier, and tests that preserve locking, adoption/fallback, plugin hooks, and refresh-token-reuse recovery.

## Reproduction Assessment

Yes, by source inspection rather than a live transient-provider failure. An expired or forced OAuth refresh invokes one provider refresh call, and current tests show HTTP 500 and network timeout do not enter the only specialized recovery branch.

## Solution Assessment

No, the issue's local withRetry wrapper around getOAuthApiKey is not the best final shape. The safer solution belongs at the centralized OAuth manager/auth-profile boundary with retryAsync, a transient-error classifier, and auth-owner timing semantics.

## Summary

Keep this issue open. Current main and v2026.6.11 still make one ordinary OAuth provider refresh attempt, so the reported resilience gap remains; an auth owner should define the cross-provider transient-error and latency policy before implementation.

## What This Changes

Add bounded retry handling for transient OAuth token refresh failures.

## Best Possible Solution

Use the existing bounded retry primitive around the shared refresh boundary only for provider-safe transient failures, preserving locking, credential adoption, fallback, timeout, and refresh-token-reuse semantics with focused tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which OAuth refresh failures are safe to retry across providers, and what maximum added latency should the shared agent request path permit?

Rationale: Current adapters do not expose a confirmed provider-neutral transient-error contract, while unconditional retries could repeat permanent credential failures and delay every affected agent request.

Likely owner: vincentkoc

Owner reason: The feature history most strongly connects this person to the shared OAuth manager boundary and its current recovery policy.

Owner confidence: high

Options:

- **Shared classified retry (recommended):** Define a narrow transient-error classifier and bounded shared retry budget, with provider hooks for errors that cannot be classified generically.
- **Provider-owned retries:** Keep the shared manager single-shot and require each OAuth adapter to implement and test its own retry policy.
- **Retain single-shot behavior:** Continue relying on credential adoption, provider fallback, and re-authentication rather than adding retry latency to the shared path.

## Reproduction Assessment

No live current-main failure was reproduced, but the gap is high-confidence source-reproducible: ordinary provider refresh errors receive one attempt and are not covered by the existing refresh-token-reuse recovery branch.

## Solution Assessment

No, an unconditional three-attempt wrapper is not the best cross-provider fix; the narrow maintainable solution is bounded retry gated by a tested transient-error contract.

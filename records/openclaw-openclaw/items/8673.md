## Summary

Current main and v2026.6.11 still make one ordinary OAuth provider refresh attempt, so the reported resilience gap remains. Keep this issue open for an auth-owner decision because the safe fix requires a shared transient-error contract and bounded latency policy rather than unconditional retries.

## What This Changes

Add bounded retries for transient OAuth token-refresh failures without retrying terminal authorization errors.

## Best Possible Solution

Define one shared, provider-safe transient classification and total retry budget around the existing manager refresh call, reuse retryAsync, and preserve serialization, credential adoption, persistence, refresh-token-reuse recovery, and terminal-error semantics with focused tests.

Options:

- **Shared classified retry (recommended):** Core retries a narrow standardized set of transient transport, timeout, 429, and 5xx failures within a small total budget while excluding terminal OAuth errors.
- **Provider-owned retry:** Each built-in or plugin provider owns retry classification and timing, leaving the shared manager single-shot.
- **Keep current behavior:** Continue surfacing the first transient refresh failure and rely on subsequent requests, credential adoption, or operator restart.

## Reproduction Assessment

Yes at source level: once an OAuth refresh is required, current main performs one provider refresh call and does not retry an ordinary transient exception. The reporter's exact live incident, including why refresh occurred with reported token lifetime remaining, was not reproduced in this read-only review.

## Solution Assessment

No, the proposed unconditional three-attempt wrapper is not the best solution because it would also repeat terminal OAuth failures and ignores the existing timeout budget. A classified bounded retry in the shared manager is the narrowest maintainable direction after owner approval.

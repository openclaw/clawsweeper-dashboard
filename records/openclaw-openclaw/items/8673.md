## Summary

Keep open: current main and v2026.6.11 still perform ordinary OAuth token refresh as a single provider/plugin call, with retry-like behavior limited to refresh_token_reused recovery and adjacent MCP/auth-fallback work not covering transient refresh failures.

## What This Changes

The issue requests bounded retry logic for transient OAuth token refresh API failures so agents do not fail on a single network blip or timeout.

## Best Possible Solution

Define a bounded provider-safe transient retry policy in the shared OAuth manager path, preferably using `retryAsync`, while preserving lock/adoption/fallback/reused-token semantics and adding focused auth-profile tests.

## Reproduction Assessment

Yes at source level: expired OAuth credentials reaching the manager call one provider/plugin refresh attempt, and current tests show ordinary HTTP 500/network timeout errors are outside the only retry-like classifier. I did not run a live upstream OAuth transient-failure repro.

## Solution Assessment

No, the issue's inline `withRetry` sketch is only a plausible fix because it would duplicate existing retry infrastructure and retry too broadly. The best fix is a shared `retryAsync` policy with a transient-error classifier and explicit tests for retryable and non-retryable OAuth failures.

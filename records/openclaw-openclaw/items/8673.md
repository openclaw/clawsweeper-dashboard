- `impact:auth-provider`: The issue directly concerns OAuth token refresh and continued provider authentication.

## Summary

Keep open: current main and v2026.6.11 still do a single ordinary OAuth refresh attempt for transient provider/API failures, while the existing recovery logic only covers changed stored credentials and the refresh-token-reuse race.

## What This Changes

The issue requests bounded retry logic for transient OAuth token refresh failures so OAuth-backed agents do not fail after one network/API blip.

## Best Possible Solution

Add bounded retry at the centralized OAuth manager boundary using retryAsync, an auth-owner-approved transient classifier, and focused tests that preserve locking, adoption/fallback, plugin hooks, and refresh-token-reuse recovery.

## Reproduction Assessment

Yes, by source inspection rather than a live transient-provider failure. An expired or forced OAuth refresh invokes one provider refresh call, and current tests show HTTP 500 and network timeout do not enter the only specialized recovery branch.

## Solution Assessment

No, the issue's local withRetry wrapper around getOAuthApiKey is not the best final shape. The safer solution belongs at the centralized OAuth manager boundary with retryAsync, a transient-error classifier, and auth-owner timing semantics.

## Summary

This PR addresses a reproducible WhatsApp steering regression and remains necessary: current `main` still serializes a debounce key through the awaited flush path, while this branch releases debounce ownership after dispatch starts and retains an explicit shutdown-drain task. The patch has focused regression coverage and no concrete correctness or security defect was found in the supplied diff, but its body provides only test/autoreview claims rather than after-fix WhatsApp runtime evidence, so it needs real behavior proof before merge.

Likely related people: andersonjeccel is the low-confidence reproduction/reporting contact for the affected behavior; current-main ownership history could not be established from the supplied review material.

## What This Changes

The PR makes WhatsApp inbound debounce release a conversation key after session-lane delivery begins, allowing a later message in the same chat to steer an active agent run while shutdown still drains the in-flight turn.

## System Context

WhatsApp Web receives inbound messages, batches them by conversation through the shared inbound debouncer, and delivers each flush into the agent/session lane. The session lane then decides whether a later message steers an active run, so holding the debounce key for the entire agent turn prevents that downstream behavior.

## Architecture Diagram

  B --> C[Flush starts]
  C --> D[Session-lane delivery]
  D --> E[Active-run steering]
  C --> F[In-flight flush tracking]
  F --> G[Shutdown drain]

## Best Possible Solution

Keep the release of debounce ownership scoped to WhatsApp after durable session-lane adoption, retain shutdown draining of every started flush, and add redacted live evidence showing a second WhatsApp message steers an active run without losing either message.

## Summary

Keep open: current main and v2026.6.11 still leave the active GatewayClient reconnect scheduler without a retry ceiling, and the open linked implementation PR is unmerged, conflicting, and targets the stale facade-era file rather than the current package client.

## What This Changes

The issue asks for a maximum retry policy in `GatewayClient.scheduleReconnect()` so unreachable gateways stop causing indefinite reconnect loops and resource buildup.

## Best Possible Solution

Land or replace the linked PR with a package-level opt-in reconnect cap, maintainer-approved short-lived caller wiring, unchanged node-host recovery by default, focused tests, and redacted real reconnect proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should GatewayClient keep unlimited reconnects by default and expose an opt-in cap only for short-lived callers, or should OpenClaw change the default reconnect policy globally?

Rationale: The source-level unbounded scheduler is clear, but node-host currently relies on long-lived recovery, so the permanent retry contract is a compatibility and product decision rather than a purely mechanical bug fix.

Likely owner: steipete

Owner reason: The original Gateway WebSocket control-plane behavior traces to this owner path, and the decision is about the long-term gateway retry contract.

Owner confidence: high

Options:

- **Opt-in bounded reconnect (recommended):** Keep node-host unlimited by default, add the cap in `packages/gateway-client`, and wire only maintainer-approved short-lived clients to the bounded policy.
- **Global retry cap:** Make every GatewayClient stop after a fixed number of attempts, accepting the risk that long-lived node hosts no longer recover automatically after extended outages.
- **Keep current behavior:** Treat unlimited reconnect as intentional recovery behavior and close the issue only if maintainers accept and document the resource-risk tradeoff.

## Reproduction Assessment

Yes at source level: current package-client close handling reaches `scheduleReconnect()`, which schedules another `start()` without a max-attempt counter. I did not run a live long-duration reproduction of the reported zombie-process accumulation.

## Solution Assessment

No, the blanket max-retry suggestion is not the best final shape because node-host depends on long-lived recovery. The maintainable fix is an opt-in package-level policy wired only to maintainer-approved short-lived callers.

## Summary

Keep open: current main and the latest release still leave the active GatewayClient reconnect scheduler without a retry ceiling, and the open linked PR is the implementation candidate rather than a reason to close this issue early.

## What This Changes

Request to bound `GatewayClient` reconnect behavior so a permanently unreachable gateway does not keep retrying forever.

## Best Possible Solution

Land or replace https://github.com/openclaw/openclaw/pull/77961 with a package-level opt-in reconnect cap, maintainer-approved short-lived caller wiring, unchanged node-host recovery by default, focused tests, and redacted real reconnect proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should GatewayClient keep unlimited reconnects by default and expose an opt-in cap only for short-lived callers, or should OpenClaw change the default reconnect policy globally?

Rationale: The source-level bug is clear, but current node-host behavior intentionally relies on unlimited reconnect recovery, so the permanent retry contract is a product and compatibility decision rather than a purely mechanical fix.

Likely owner: steipete

Owner reason: The original Gateway WebSocket control-plane work and much of the gateway-client policy history trace through this owner path.

Owner confidence: high

Options:

- **Opt-in bounded reconnect (recommended):** Keep node-host unlimited by default, add a package-level cap option, and wire it only into maintainer-approved short-lived clients with proof for both capped and default behavior.
- **Global retry cap:** Make every GatewayClient stop after a fixed number of attempts, accepting the risk that long-lived node hosts no longer recover automatically after extended outages.
- **Keep current behavior:** Treat unlimited reconnects as by design and close the issue only if maintainers accept the resource-risk tradeoff and document the intended recovery model.

## Reproduction Assessment

Yes at source level: current package-client close handling reaches `scheduleReconnect()`, which schedules another `start()` without a max-attempt counter. I did not run a live long-duration reproduction of the reported zombie-process accumulation.

## Solution Assessment

No, the blanket max-retry suggestion is not the best final shape because node-host depends on long-lived recovery. The maintainable fix is an opt-in package-level policy wired only to maintainer-approved short-lived callers, with proof that the unlimited default remains intact.

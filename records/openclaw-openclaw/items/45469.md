## Summary

Keep open: current main and the latest release still leave the active GatewayClient reconnect scheduler without a retry ceiling, and the open linked PR is the implementation candidate rather than a reason to close this issue early.

## What This Changes

Add a maximum retry limit or equivalent bounded reconnect policy for GatewayClient.scheduleReconnect so permanently unreachable gateways do not retry forever.

## Best Possible Solution

Land or replace https://github.com/openclaw/openclaw/pull/77961 with a package-level opt-in reconnect cap, maintainer-approved short-lived caller wiring, unchanged node-host recovery by default, focused tests, and redacted live reconnect proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should GatewayClient gain an opt-in reconnect attempt ceiling, and which callers should use it while node-host keeps unlimited recovery?

Rationale: The source-level unbounded scheduler is real, but the existing node-host contract intentionally relies on indefinite reconnects, so the retry policy cannot be chosen safely by cleanup automation.

Likely owner: steipete

Owner reason: The history points to steipete for the original Gateway WebSocket control plane and current package-client ownership, making this the best available policy-routing owner.

Owner confidence: high

Options:

- **Opt-in cap for short-lived callers (recommended):** Keep the default unlimited for node-host, add a package-level maxReconnectAttempts option, and wire only maintainer-approved CLI/SDK/probe callers after real reconnect proof.
- **Global default cap:** Set a default retry ceiling for every GatewayClient user, accepting the upgrade risk that long gateway outages can strand node-host clients until an external supervisor restarts them.
- **No retry ceiling:** Leave reconnect attempts unlimited and instead focus follow-up work on listener cleanup, diagnostics, and clearer reconnect-paused events.

## Reproduction Assessment

Yes at source level: current package-client close handling reaches scheduleReconnect(), which schedules another start() without a max-attempt counter. I did not run a live long-duration reproduction of the reported zombie-process accumulation.

## Solution Assessment

No, the blanket max-retry suggestion is not the best final shape because node-host depends on long-lived recovery. The maintainable path is an opt-in package-level policy wired only to maintainer-approved short-lived callers, with proof that the unlimited default remains intact.

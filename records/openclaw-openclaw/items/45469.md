## Summary

Keep open: current main and the latest release still leave the active package-level GatewayClient reconnect scheduler without a retry ceiling, and the open linked PR is an unmerged/conflicting implementation candidate rather than a reason to close this issue early.

## What This Changes

The issue asks for a bounded reconnect policy in `GatewayClient.scheduleReconnect()` to avoid an unbounded retry loop when the gateway remains unreachable.

## Best Possible Solution

Land or replace the linked PR with a package-client reconnect policy that preserves unlimited node-host recovery by default and adds a maintainer-approved bounded option for short-lived callers.

Rationale: The source-level unbounded scheduler is clear, but node-host recovery intentionally benefits from indefinite reconnects, so the default retry contract is a compatibility and product decision.

Options:

- **Opt-in bounded reconnect (recommended):** Keep existing long-lived clients unlimited by default, add the cap to the package client, and wire it only into caller paths maintainers approve as short-lived.
- **Global retry cap:** Stop every GatewayClient after a fixed number of attempts, accepting that node hosts may not recover automatically after extended gateway outages.
- **Document unlimited retry as intended:** Keep the current retry model and close the report only if maintainers explicitly accept the resource-risk tradeoff.

## Reproduction Assessment

Yes at source level: current package-client close handling reaches `scheduleReconnect()`, which schedules another `start()` without a max-attempt counter. I did not run a live long-duration reproduction of the reported process buildup.

## Solution Assessment

No, the blanket max-retry suggestion is not clearly the best final shape because node-host depends on long-lived recovery. The maintainable fix is a package-client opt-in policy wired only to maintainer-approved short-lived callers, with proof that the unlimited default remains intact.

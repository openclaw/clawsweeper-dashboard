## Summary

Keep open: current main and the latest release still leave the active GatewayClient reconnect scheduler without a retry ceiling, and the linked implementation candidate remains open and unmerged.

## What This Changes

The issue asks for GatewayClient reconnect scheduling to avoid an unbounded retry loop when the gateway remains unreachable.

## Best Possible Solution

Land or replace the linked candidate with a package-level, maintainer-approved opt-in reconnect ceiling for selected short-lived callers while preserving unlimited node-host recovery by default.

## Reproduction Assessment

Yes from source: current main's active package-client close handling reaches scheduleReconnect(), which schedules another start() without a max-attempt counter. I did not run a live long-duration reproduction of the reported zombie-process buildup.

## Solution Assessment

No for the blanket max-retry suggestion as written; the safer solution is a package-level opt-in policy wired only to maintainer-approved short-lived callers, with unlimited node-host recovery preserved by default.

## Summary

Keep open: current main and the latest release still leave GatewayClient reconnect scheduling unbounded, and the open linked PR is an unmerged/stale implementation candidate rather than a reason to close this issue early.

## What This Changes

The issue requests a maximum retry policy for GatewayClient reconnect scheduling to prevent unbounded reconnect loops when the gateway remains unreachable.

## Best Possible Solution

Land or replace the linked PR with a package-level opt-in reconnect cap, maintainer-approved caller wiring, unchanged node-host recovery by default, focused tests, and real reconnect proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should GatewayClient keep unlimited reconnects by default with an opt-in cap for short-lived callers, or should OpenClaw change the default reconnect policy globally?

Rationale: The source-level unbounded scheduler is clear, but node-host recovery appears to rely on unlimited reconnects, so the permanent retry contract and caller opt-in surface require maintainer intent.

Likely owner: Peter Steinberger

Owner reason: Original Gateway WebSocket control-plane history and the sampled gateway-client contribution trail point here as the best available policy owner.

Owner confidence: high

Options:

- **Opt-in bounded reconnect (recommended):** Keep unlimited reconnects as the default and add a package-level `maxReconnectAttempts` policy only for maintainer-approved short-lived clients.
- **Global retry cap:** Make every GatewayClient stop after a fixed number of attempts, accepting upgrade risk for long-lived node hosts during extended outages.
- **Document unlimited retries:** Treat unlimited reconnects as intentional and close the report only if maintainers accept the resource-risk tradeoff and document the recovery model.

## Reproduction Assessment

Yes from source inspection: current main's close handler falls through to `scheduleReconnect()`, and `scheduleReconnect()` has no retry-count guard. I did not run a live gateway outage loop in this read-only review.

## Solution Assessment

No for a blanket cap: the safer final shape is an opt-in package-client policy because long-lived node hosts need automatic recovery after gateway outages. The existing linked PR is not sufficient on current main because it patches the stale facade-era implementation.

## Summary

Keep open: current main and the latest release still leave GatewayClient reconnect scheduling without a max-attempt ceiling, and the open linked PR is an unmerged implementation candidate that needs maintainer direction.

## What This Changes

The issue requests a bounded retry policy for GatewayClient reconnect scheduling to avoid unbounded reconnect loops when a gateway stays unreachable.

## Best Possible Solution

Land or replace the linked PR with a package-level opt-in reconnect cap, unchanged node-host unlimited recovery by default, maintainer-approved short-lived caller wiring, focused tests, and redacted real reconnect proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should GatewayClient keep unlimited reconnects by default and expose an opt-in cap only for selected short-lived callers, or should OpenClaw change the default reconnect policy globally?

Rationale: The source-level loop is clear, but node-host currently relies on unlimited reconnect recovery, so the permanent retry contract is a compatibility and product-policy decision.

Likely owner: steipete

Owner reason: The original Gateway WebSocket control-plane behavior and historical retry policy trace most directly through this owner path.

Owner confidence: medium

Options:

- **Opt-in bounded reconnect (recommended):** Keep node-host unlimited by default, add a package-level cap option, and wire it only into maintainer-approved short-lived clients with proof for capped and default behavior.
- **Global retry cap:** Make every GatewayClient stop after a fixed number of attempts, accepting the risk that long-lived node hosts no longer recover automatically after extended outages.
- **Document unlimited retries:** Keep current behavior as intentional recovery policy and document the resource-risk tradeoff instead of adding a retry ceiling.

## Reproduction Assessment

Yes at source level: current close handling reaches scheduleReconnect(), which schedules another start() without a max-attempt counter. I did not run a live long-duration reproduction of the reported zombie-process accumulation.

## Solution Assessment

No, the blanket max-retry suggestion is not the best final shape because node-host depends on long-lived recovery. The maintainable fix is an opt-in package-level policy wired only to maintainer-approved short-lived callers.

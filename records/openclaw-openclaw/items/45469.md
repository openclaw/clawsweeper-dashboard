## Summary

Keep open: current main and v2026.6.11 still leave GatewayClient reconnect scheduling without an attempt ceiling, while the linked fix PR is open, conflicting, and targets the stale facade-era file instead of the active package client.

## What This Changes

The issue asks for GatewayClient reconnect scheduling to stop or pause after a bounded number of failed reconnect attempts instead of retrying indefinitely.

## Best Possible Solution

Land a package-client fix that preserves long-lived node-host recovery by default while giving selected short-lived callers an explicit bounded retry path, with focused regression coverage and caller opt-in after maintainer policy is chosen.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should GatewayClient reconnect attempts stay unlimited by default with an opt-in cap for short-lived callers, or should OpenClaw impose a default reconnect ceiling across all clients?

Rationale: Both current code and the linked discussion show the code defect, but choosing the default retry policy can affect node-host recovery and exported GatewayClient API behavior.

Likely owner: RomneyDa

Owner reason: They most recently owned the package-client boundary where the durable fix now belongs.

Owner confidence: high

Options:

- **Adopt opt-in package-client cap (recommended):** Add maxReconnectAttempts to the active package client and wire only short-lived callers that should fail boundedly, keeping node-host unlimited unless explicitly changed.
- **Default cap everywhere:** Impose a finite retry ceiling for all GatewayClient users, accepting that existing long-lived node-host deployments may stop recovering automatically after prolonged outages.
- **Keep unlimited retries:** Treat endless reconnect as intentional for all GatewayClient users and close the issue only after documenting why short-lived clients should supervise themselves.

## Reproduction Assessment

Yes at source level: current close handling reaches scheduleReconnect(), which schedules another start after capped backoff without an attempt counter. I did not run a live long-duration process/zombie reproduction.

## Solution Assessment

Unclear pending maintainer policy: an opt-in cap is safer than an unconditional default cap, but the current linked PR targets the stale facade and does not wire caller opt-in. The best fix belongs in packages/gateway-client plus selected call sites.

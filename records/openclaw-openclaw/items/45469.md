## Summary

Keep open: current main and the latest release still leave the active GatewayClient reconnect scheduler without a retry ceiling, and the open linked PR is an unmerged, conflicting implementation candidate rather than a completed fix.

## What This Changes

The issue requests a bounded GatewayClient reconnect policy so permanently unreachable gateways do not cause unbounded reconnect/resource loops.

## Best Possible Solution

Land or replace the linked PR with a package-level opt-in reconnect cap, maintainer-approved caller wiring for short-lived clients, unchanged node-host recovery by default, focused tests, and real reconnect proof.

## Maintainer Decision

Question: Should GatewayClient keep unlimited reconnects by default and expose an opt-in maxReconnectAttempts policy, or should core impose a default reconnect ceiling?

Rationale: Current main has no cap, but issue discussion, node-host source, and the linked PR all show long-lived node-host recovery may rely on indefinite reconnects, so the permanent retry contract is a compatibility/product decision rather than a purely mechanical fix.

Likely owner: steipete

Owner reason: The original GatewayClient control-plane behavior and most historical ownership on this path trace to steipete, and this decision is about the core gateway retry contract.

Owner confidence: high

Options:

- **Default unlimited, opt-in cap (recommended):** Keep existing node-host behavior and let short-lived clients opt into bounded reconnects through a narrow GatewayClient option.
- **Default bounded reconnects:** Add a global default retry cap and require long-lived callers to explicitly opt out, accepting upgrade risk for existing deployments.
- **No reconnect cap:** Treat indefinite reconnect as intended and close the linked PR after confirming listener/process leaks are solved elsewhere.

## Reproduction Assessment

Yes for source reproduction: current main still has scheduleReconnect re-enter start() indefinitely with only a 30s backoff cap and no retry ceiling. I did not run a live gateway-outage repro or reproduce the reported long-duration zombie-process accumulation in this read-only review.

## Solution Assessment

No for the blanket max-retry suggestion; the safer fix is an opt-in package-level policy because node-host recovery may rely on unlimited reconnects. The open linked PR is the candidate path but still needs conflict, proof, and product-direction review.

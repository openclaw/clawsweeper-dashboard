## Summary

Keep open: current main and the latest release still leave the active GatewayClient reconnect scheduler without a retry ceiling, and the linked implementation PR is open, conflicting, and unmerged rather than a reason to close this issue early.

## What This Changes

The issue requests a bounded retry policy for `GatewayClient.scheduleReconnect()` to avoid unbounded reconnect attempts when the gateway remains unreachable.

## Best Possible Solution

Land or replace https://github.com/openclaw/openclaw/pull/77961 with a package-level opt-in reconnect cap, maintainer-approved short-lived caller wiring, unchanged node-host recovery by default, focused tests, and redacted real reconnect proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should GatewayClient gain an opt-in reconnect attempt ceiling, and which callers should set it while node-host remains unbounded by default?

Rationale: Current source proves the unbounded retry loop, but repository policy and node-host usage make a global cap compatibility-sensitive rather than a purely mechanical bug fix.

Likely owner: steipete

Owner reason: The gateway-client extraction and current scheduler history point to steipete as the strongest available owner for the compatibility policy decision.

Owner confidence: high

Options:

- **Opt-in cap for short-lived clients (recommended):** Add a package-level `maxReconnectAttempts` policy and wire it only for maintainer-approved short-lived callers while preserving node-host unlimited recovery.
- **Global retry cap:** Apply a default cap to all GatewayClient users, accepting the risk that long gateway outages can stop existing node-host workflows.
- **No cap, diagnostics only:** Keep reconnect behavior unbounded and focus on listener cleanup, warnings, or operator diagnostics instead of changing retry policy.

## Reproduction Assessment

Yes at source level: current package-client close handling reaches `scheduleReconnect()`, which schedules another `start()` without a max-attempt counter. I did not run a live long-duration reproduction of the reported zombie-process accumulation.

## Solution Assessment

No, the blanket max-retry suggestion is not the best final shape because node-host depends on long-lived recovery. The maintainable fix is an opt-in package-level policy wired only to maintainer-approved short-lived callers, with proof that the unlimited default remains intact.

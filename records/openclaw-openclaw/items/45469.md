## Summary

Keep open: current main and the latest release still leave the active GatewayClient reconnect scheduler without a retry ceiling, and the open linked pull request is an implementation candidate rather than a merged fix.

## What This Changes

The issue requests a retry ceiling for `GatewayClient.scheduleReconnect()` so a permanently unreachable gateway cannot trigger endless reconnect attempts.

## Best Possible Solution

Land or replace https://github.com/openclaw/openclaw/pull/77961 with a package-level opt-in reconnect cap, maintainer-approved short-lived caller wiring, unchanged node-host recovery by default, focused tests, and redacted real reconnect proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should GatewayClient keep unlimited reconnects by default and expose an opt-in retry cap only for short-lived callers, or should OpenClaw change the default reconnect policy globally?

Rationale: The source-level bug is clear, but node-host currently relies on GatewayClient for long-lived recovery, so the retry contract is a product and compatibility decision rather than a purely mechanical fix.

Likely owner: RomneyDa

Owner reason: The current package-client contract refactor makes this retry policy live in the surface RomneyDa recently consolidated.

Owner confidence: medium

Options:

- **Opt-in bounded reconnect (recommended):** Keep node-host unlimited by default, add a package-level cap option, and wire it only into maintainer-approved short-lived clients with proof for both capped and default behavior.
- **Global retry cap:** Make every GatewayClient stop after a fixed number of attempts, accepting the risk that long-lived node hosts no longer recover automatically after extended outages.
- **Keep unlimited retries:** Treat unlimited reconnects as intended behavior and document the resource-risk tradeoff instead of changing runtime policy.

## Reproduction Assessment

Yes at source level: current package-client close handling reaches `scheduleReconnect()`, which schedules another `start()` without a max-attempt counter. I did not run a live long-duration reproduction of the reported zombie-process accumulation.

## Solution Assessment

No, the blanket max-retry suggestion is not the best final shape because node-host depends on long-lived recovery. The maintainable fix is an opt-in package-level policy wired only to maintainer-approved short-lived callers, with proof that the unlimited default remains intact.

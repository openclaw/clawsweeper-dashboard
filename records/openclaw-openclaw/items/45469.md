## Summary

Keep open: current main and the latest release still leave the active GatewayClient reconnect scheduler without a retry ceiling, and the linked implementation PR remains open/unmerged rather than a reason to close this issue.

## What This Changes

The issue asks OpenClaw to bound GatewayClient reconnect attempts so permanently unreachable gateways do not cause indefinite reconnect loops.

## Best Possible Solution

Land or replace the linked candidate with a package-level opt-in reconnect cap, maintainer-approved short-lived caller wiring, unchanged node-host recovery by default, focused tests, and redacted real reconnect proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should GatewayClient keep unlimited reconnects by default and expose an opt-in cap only for short-lived callers, or should OpenClaw change the default reconnect policy globally?

Rationale: The source-level retry loop is clear, but node-host currently relies on unlimited recovery, so the permanent retry contract is a product and compatibility decision rather than a purely mechanical fix.

Likely owner: Peter Steinberger

Owner reason: The original Gateway WebSocket control plane and current package-client extraction history make this the strongest available routing owner for the retry-policy decision.

Owner confidence: high

Options:

- **Opt-in bounded reconnect (recommended):** Keep node-host unlimited by default, add a package-level cap option, and wire it only into maintainer-approved short-lived clients with proof for both capped and default behavior.
- **Global retry cap:** Make every GatewayClient stop after a fixed number of attempts, accepting the risk that long-lived node hosts no longer recover automatically after extended outages.
- **Keep current behavior:** Treat unlimited reconnects as intentional and close only after documenting the resource-risk tradeoff and supported recovery model.

## Reproduction Assessment

Yes at source level: current package-client close handling reaches scheduleReconnect(), which schedules another start without a max-attempt counter. I did not run a live long-duration reproduction of the reported zombie-process accumulation.

## Solution Assessment

No, the blanket max-retry suggestion is not the best final shape because node-host depends on long-lived recovery. The maintainable fix is an opt-in package-level policy wired only to maintainer-approved short-lived callers, with proof that the unlimited default remains intact.

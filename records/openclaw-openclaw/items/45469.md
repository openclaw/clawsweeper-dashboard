## Summary

Keep open: current main and v2026.6.11 still leave `GatewayClient` reconnect scheduling unbounded, and the linked closing PR is open rather than a merged fix.

## What This Changes

The issue requests a bounded retry policy for `GatewayClient` reconnects so a permanently unreachable gateway cannot loop forever.

## Best Possible Solution

Land or replace the linked PR with a package-level opt-in reconnect cap, maintainer-approved caller wiring, unchanged node-host recovery by default, focused tests, and real reconnect proof.

## Maintainer Decision

Required: true

Question: Should `GatewayClient` keep unlimited reconnects by default with an opt-in cap for short-lived callers, or should OpenClaw change the default reconnect policy globally?

Rationale: The unbounded scheduler is clear in source, but node-host recovery appears to rely on unlimited reconnects, so the permanent retry contract and caller opt-in surface require maintainer intent.

Likely owner: steipete

Owner confidence: high

Options:

- **Opt-in bounded reconnect (recommended):** Keep unlimited reconnects as the default and add a package-level `maxReconnectAttempts` policy only for maintainer-approved short-lived clients.
- **Global retry cap:** Make every `GatewayClient` stop after a fixed number of attempts, accepting upgrade risk for long-lived node hosts during extended outages.
- **Document unlimited retries:** Treat unlimited reconnects as intentional and close the report only if maintainers accept the resource-risk tradeoff and document the recovery model.

## Reproduction Assessment

Yes at source level: current main's close handler falls through to `scheduleReconnect()`, and `scheduleReconnect()` has no retry-count guard. I did not run a live gateway outage loop or reproduce the long-duration zombie-process buildup in this read-only review.

## Solution Assessment

No for a blanket cap: the safer final shape is an opt-in package-client policy because long-lived node hosts need automatic recovery after gateway outages. The linked PR is only a candidate because it is open and stale against the current package-client implementation.

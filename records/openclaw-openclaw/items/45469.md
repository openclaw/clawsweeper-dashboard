## Summary

Keep open: current main and the latest release still leave the active GatewayClient reconnect scheduler without a retry ceiling, and the open linked PR is unmerged work that needs maintainer policy direction before it can safely close this issue.

## What This Changes

The issue requests a maximum retry policy for GatewayClient `scheduleReconnect()` to avoid unbounded reconnect loops when the gateway stays unreachable.

## Best Possible Solution

Land or replace the linked PR with a package-client opt-in reconnect cap that preserves unlimited node-host recovery by default and wires bounded retry only into maintainer-approved short-lived callers.

## Maintainer Decision

Rationale: The unbounded scheduler is source-reproducible, but node-host recovery relies on indefinite reconnects, so the default retry contract is a compatibility and product decision.

Likely owner: steipete

Owner confidence: high

Options:

- **Opt-in bounded reconnect (recommended):** Keep existing long-lived clients unlimited by default, add the cap to the package client, and wire it only into short-lived caller paths maintainers approve.
- **Global retry cap:** Stop every GatewayClient after a fixed number of attempts, accepting that node hosts may not recover automatically after extended gateway outages.
- **Document unlimited retry:** Keep the current retry model and close the report only if maintainers explicitly accept the resource-risk tradeoff.

## Reproduction Assessment

Yes at source level: current package-client close handling reaches `scheduleReconnect()`, which schedules another `start()` without a max-attempt counter. I did not run a live long-duration reproduction of the reported process buildup.

## Solution Assessment

No, the blanket max-retry suggestion in the issue body is not clearly the best final shape because node-host depends on long-lived recovery. The maintainable fix is an opt-in package-client policy wired only to approved short-lived callers.

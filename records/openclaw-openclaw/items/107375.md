## Summary

Keep open for a maintainer product-direction decision. The documentation is coherent and clearly labels the proposed behavior as unimplemented, but publishing it in the public Technical Reference would endorse a broad new core persistence boundary and establish the foundation for four downstream implementation PRs. Current OpenClaw already has durable TaskFlow ownership for long-running orchestration, while VISION.md cautions against duplicative heavy orchestration in core, so correctness checks alone cannot settle whether this additional substrate should become product architecture. ([github.com](https://github.com/openclaw/openclaw/blob/main/skills/taskflow/SKILL.md?utm_source=openai))

## What This Changes

Adds two public durable-core RFC and test-plan pages, exposes them in Technical Reference navigation, refreshes the generated docs map, and adds Chinese glossary entries.

## Best Possible Solution

Establish one maintainer-approved durable-work ownership model: either approve this RFC with a precise non-overlap contract against TaskFlow and existing SQLite owners, or keep the proposal in design discussion and publish public Technical Reference pages only after that boundary is accepted.

## Summary

Keep open: the prior lifecycle concern was addressed, and registering CLI metadata before runtime access is correct, but the replacement guard is too broad because it also suppresses Codex tool registration during the dedicated tool-discovery mode.

## What This Changes

The PR registers Codex CLI descriptors before runtime wiring, returns early for every non-full registration mode, and adds lifecycle tests covering metadata, discovery, tool-discovery, setup-only, and full modes.

## Best Possible Solution

Split registration by lifecycle: keep CLI metadata state-free in metadata/discovery modes, expose state-free Codex tool factories and metadata during tool-discovery, and reserve durable binding-store acquisition, providers, harnesses, commands, services, and hooks for full activation.

No. Moving CLI metadata before runtime access is appropriate, but treating tool-discovery as CLI-only conflicts with the loader and shared plugin-entry lifecycle contract; the fix needs a separate state-free tool-registration path.

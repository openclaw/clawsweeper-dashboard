## Summary

Keep this PR open for maintainer review. The proposed separation addresses a plausible Workboard deadlock, but it changes the behavior of every existing caller that omits the new mode and the doctor migration can remove legacy dependency links whose original intent was not recorded; the submitted tests do not prove fresh-install and upgrade behavior in a real Workboard SQLite setup.

## What This Changes

The PR makes decomposed Workboard children orchestration-only by default, retains an explicit hard-dependency mode, and adds diagnostics plus doctor repair for older reciprocal decomposition links.

## System Context

Workboard stores cards and their parent/child relationships in plugin-owned SQLite state, then uses those relationships while claiming, completing, and dispatching work. This change alters how decomposition records are created, diagnosed, repaired, and exposed through gateway and agent-tool APIs.

## Architecture Diagram

flowchart LR

  B --> C{Decomposition mode}
  C -->|Orchestration| D[Child provenance only]
  C -->|Hard| E[Blocking parent-child links]
  D --> F[Claim and completion flow]
  E --> F
  G[Doctor migration] --> H[Legacy SQLite card links]
  H --> B

## Best Possible Solution

Preserve the established behavior for omitted decomposition mode, make non-blocking orchestration an explicit opt-in until maintainers approve a versioned contract change, and restrict doctor repair to links with independently provable legacy provenance or an explicit user-confirmed repair action.

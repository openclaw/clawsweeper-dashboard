## Summary

Keep open. Current main still does not classify unprefixed Anthropic-style `invalid_request_error` JSON bodies as fallback-worthy, and the linked candidate fix at https://github.com/openclaw/openclaw/pull/99184 is open rather than merged.

## What This Changes

The issue asks OpenClaw to classify structured provider `invalid_request_error` 400 bodies without a leading HTTP status so configured model fallbacks are attempted.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/99184 or an equivalent narrow classifier fix after redacted real-provider fallback proof or an explicit maintainer proof override.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: an unprefixed JSON `invalid_request_error` body reaches the message classifier, receives no failover reason, and then enters the silent error retry path. I did not run a live provider reproduction in this read-only pass.

## Solution Assessment

Yes, a narrow classifier and result-payload propagation fix is the right layer because current main already treats bodyful 400/422 provider rejections as `format` when a status is available. The linked PR appears to target that exact gap, but it still needs review and proof before the issue can close.

## Summary

Keep this PR open: the accepted fail-closed microphone policy is not enforced before bridge startup, so a recovered browser session with an unknown microphone state can still enter `ensureRealtimeBridge()` before returning the intended browser-unverified result.

## What This Changes

The branch hardens meeting-browser transcript retention, untargeted tab recovery, and talk-back microphone readiness, with focused Google Meet and meeting-runtime regression coverage.

## Best Possible Solution

Require `micMuted === false` before any talk-back bridge initialization for recovered browser sessions, then retain the existing browser-unverified retry result until that condition is observed.

No. The PR's readiness branch is the right policy outcome, but it runs too late to prevent bridge initialization; enforcing the same known-unmuted condition before bridge setup is the narrower complete fix.

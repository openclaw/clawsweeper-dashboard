## Summary

Keep this PR open: its intended fail-closed microphone policy is not enforced on the `speak()` path, because realtime bridge initialization can run while `micMuted` is still unknown. The recorded maintainer decision accepts the policy itself; this is a narrow implementation repair before merge.

## What This Changes

The branch prevents transcript cursor replay after retention gaps, prefers actual meeting tabs over sign-in tabs during recovery, and requires verified unmuted microphone state for talk-back readiness.

## Best Possible Solution

Gate browser-backed talk-back before `ensureRealtimeBridge()` unless health proves `inCall: true` and `micMuted: false`, then add a regression proving an unknown microphone state neither initializes the bridge nor reports ready.

No: the readiness change is directionally correct but is not the best complete fix while bridge initialization precedes it. A single known-unmuted guard shared by the speech and bridge-start paths is the narrower maintainable solution.

## Label Justifications

- `P1`: A successful channel login can silently associate OAuth credentials, usage, and cooldown state with the wrong OpenAI account, breaking an active authentication workflow.
- `impact:auth-provider`: The issue directly affects OAuth identity, auth-profile persistence, provider selection, and cooldown/usage state routing.
- `impact:session-state`: The initiating Telegram or channel session can remain pinned to a stale `authProfileOverride` after a different account authenticates.

## Summary

Current main still reproduces the reported identity overwrite: Telegram and the shared channel login path pass the session’s existing profile id into a fresh Codex device login, and the auth flow replaces the provider-derived profile id with that requested id before persistence. The linked fix at https://github.com/openclaw/openclaw/pull/104706 remains open and currently changes only the Telegram caller, so this issue should stay open until the shared invariant is covered and the fix merges. Likely related people: 100yenadmin, jalehman, and obviyus with high confidence; steipete with medium confidence.

## What This Changes

Prevent channel-triggered Codex login from storing a newly authenticated OpenAI account under the stale auth profile id selected by the existing session.

## Best Possible Solution

Make provider-derived profile identity canonical in the shared login boundary, then update the initiating session to the returned profile id for both Telegram-native and generic channel callers, with regression coverage and a redacted real two-account proof.

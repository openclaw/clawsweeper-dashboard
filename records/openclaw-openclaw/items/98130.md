## Summary

This PR is still useful: current main and the latest release still buffer newline-free JSONL socket responses without a size guard, while the current branch frames raw bytes and fails closed at a shared 16 MiB line budget. I found no concrete line-level correctness defect in the latest patch, but the shared response cap remains a compatibility decision for maintainers before merge.

## What This Changes

The branch refactors `requestJsonlSocket` to accumulate raw byte chunks, reject complete or unterminated response lines over 16 MiB, and adds Unix-socket regression tests for valid trailing data and oversized responses.

## Best Possible Solution

Land the byte-framed requester cap after maintainers accept the 16 MiB shared JSONL line ceiling or pair it with owner-side large-response handling.

## Reproduction Assessment

Yes. Current main and v2026.6.11 buffer newline-free response data without a size guard, and the contributor supplied real Unix-socket proof plus a current-main negative control.

## Solution Assessment

Mostly yes. Byte-framing in the shared requester is the narrow layer for hostile newline-free peers; the remaining question is maintainer acceptance of the shared 16 MiB budget or an owner-side large-response contract.

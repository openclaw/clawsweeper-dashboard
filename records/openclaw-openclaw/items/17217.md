## Summary

Keep open: current main defines session reset and compaction, but ordinary-conversation TTL expiry and privileged context-pruning APIs remain unresolved product and security decisions; recent maintainer discussion also explicitly retained the issue.

## What This Changes

Define session boundaries and provide immediate TTL-based context pruning plus explicit session reset and pruning controls.

## Best Possible Solution

Keep TTL pruning tool-result-only unless maintainers approve a separately named conversation-retention mode, and coordinate that decision with authenticated session-control, automatic-rotation, rolling-pruning, and manual-clear contracts.

Rationale: Both directions are plausible, but they have materially different retention, memory, cost, compatibility, and authorization semantics that cannot be selected from current implementation alone.

Likely owner: steipete

Options:

- **Keep TTL tool-result-only (recommended):** Clarify the documented contract and use compaction plus explicit session age or turn limits to bound normal conversation history.
- **Add explicit history retention:** Introduce a separately named retention mode with defined summarization, persistence, authorization, migration, and recovery behavior rather than changing `cache-ttl` semantics.

## Reproduction Assessment

Yes at source level: current main's documented and implemented `cache-ttl` behavior does not expire ordinary conversation messages, so the requested behavior is demonstrably absent. The reported token-cost figures were not independently reproduced in a live run.

## Solution Assessment

No, not as one combined API and semantic change: session reset, persistent compaction, tool-result pruning, and conversation retention have different ownership and safety contracts and should use explicit focused interfaces.

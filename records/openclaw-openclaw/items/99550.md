## Summary

Keep open: current main still lacks an OpenClaw upstream responses transport control, and the pinned Codex 0.142.4 source still retries failed responses_websocket streams through the stream retry budget before switching to HTTP; the newer comment adds a second deployment with the same upstream disconnect family and a harder failure mode.

## What This Changes

The issue reports that Codex/OAuth gpt-5.5 turns can spend about two minutes in failed upstream responses_websocket retries before a fast HTTP fallback succeeds.

## Best Possible Solution

Fix the upstream Codex responses transport so retryable WebSocket failures fall back to HTTP quickly, or add a narrowly documented OpenClaw upstream transport policy that stays distinct from local appServer.transport.

## Reproduction Assessment

Yes for source-level behavior: Codex 0.142.4 still uses the retry-budget-before-fallback path, and OpenClaw does not expose an upstream responses transport selector. The exact VPS websocket disconnect remains reporter-provided and needs live reproduction.

## Solution Assessment

No current implemented solution is best yet. The maintainable fix needs a maintainer-owned choice between upstream Codex retry behavior and a narrow OpenClaw integration control.

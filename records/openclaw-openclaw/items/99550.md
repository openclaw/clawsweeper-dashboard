## Label Justifications

- `P1`: Tiny Codex/OAuth gpt-5.5 turns can spend roughly two minutes in upstream WebSocket retries before a fast HTTP fallback, breaking an active chat workflow for affected users.
- `impact:auth-provider`: The affected path is the OpenClaw Codex app-server route using ChatGPT/Codex OAuth and upstream Codex responses transport selection.

## Summary

Keep open: current main still has the reported Codex/OAuth retry-before-fallback shape. OpenClaw only exposes the local Codex app-server transport, while the bundled Codex line still enables responses WebSockets for OpenAI/ChatGPT auth and switches to HTTP only after the stream retry budget is exhausted.

## What This Changes

The issue asks OpenClaw to avoid roughly 118 seconds of Codex/OAuth gpt-5.5 latency caused by repeated upstream responses_websocket retries before a fast HTTP fallback.

## Best Possible Solution

Fix the upstream Codex responses transport so failed WebSocket streams fall back to HTTP quickly, or add a clearly named OpenClaw-owned upstream transport policy without overloading appServer.transport.

## Reproduction Assessment

Yes for the source-level failure path: Codex still uses WebSocket for supported OpenAI/ChatGPT providers and switches to HTTP only after retry exhaustion. The exact VPS/OAuth disconnect is reporter-provided and was not live-reproduced from this checkout.

## Solution Assessment

No, the current behavior is not the best solution because it waits through the full WebSocket stream retry budget before using an HTTP path that can succeed quickly. The maintainable fix needs an upstream Codex retry-policy change or a narrow OpenClaw integration decision that keeps the local appServer.transport setting distinct.

## Label Justifications

- `P1`: The issue describes a real Codex/OAuth chat workflow taking about two minutes for a tiny prompt even though HTTP fallback succeeds in about two seconds.
- `impact:auth-provider`: The affected path is the OpenClaw-to-Codex-to-ChatGPT OAuth provider route and its upstream transport/fallback behavior.

## Summary

Current main still appears vulnerable to the reported Codex/OAuth latency path: OpenClaw exposes only the local app-server transport, while the upstream Codex retry logic still waits through the WebSocket stream retry budget before enabling HTTP fallback. This should stay open for owner review rather than being swept as implemented or duplicate.

## What This Changes

The issue asks OpenClaw to avoid multi-minute Codex/OAuth turns when upstream responses_websocket retries fail and HTTP fallback succeeds quickly.

## Best Possible Solution

Fix or configure the upstream Codex responses transport so failed WebSocket streams fall back to HTTP quickly without reusing the local appServer.transport setting for a different layer.

## Reproduction Assessment

Yes, source inspection provides a high-confidence path that matches the log shape: Codex uses responses_websocket when enabled and only flips to HTTP fallback after the configured stream retry budget. I did not live-reproduce the exact VPS/OAuth disconnects, so the observed network failure remains reporter-provided evidence.

## Solution Assessment

No, the current behavior is not the best solution because OpenClaw cannot tune the upstream responses transport and Codex waits through five stream retries before HTTP fallback. The maintainable fix is an upstream Codex fallback-policy change or a narrow OpenClaw-owned integration decision that does not overload the existing local transport setting.

## Summary

Keep this issue open. Current main has a low-level Baileys sticker sender, but normal WhatsApp sends still route every image through the image payload, the public message-action surface does not advertise `sticker`, and the ordinary outbound pipeline cannot express sticker intent. The remaining question is whether OpenClaw promises transport of sticker-ready WebP only or conversion of arbitrary static and animated media.

## What This Changes

Add a supported outbound WhatsApp sticker path through the message tool or send options instead of delivering WebP stickers as ordinary images.

## Best Possible Solution

Add an explicit plugin-owned WhatsApp `sticker` action that accepts sticker-ready WebP, preserves it outside generic image optimization, validates the supported transport contract, calls the existing `sendSticker` primitive, and documents conversion as a separate future capability rather than silently guessing from captions or file extensions.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should WhatsApp sticker support transport only explicitly supplied sticker-ready WebP, or also convert arbitrary static and animated media into WhatsApp-compliant stickers?

Rationale: The first option is a narrow channel contract using an existing sender; the second commits OpenClaw to image/video conversion, animation handling, metadata generation, additional dependencies, and broader failure semantics that cannot be selected safely from source behavior alone.

Likely owner: steipete

Owner reason: The strongest recent history signal spans both the WhatsApp send path and shared media behavior needed to define this contract.

Owner confidence: high

Options:

- **Transport sticker-ready WebP (recommended):** Add an explicit sticker action for validated WebP input and leave media conversion to external tools or a later feature.
- **Convert arbitrary media:** Add a send-as-sticker mode that converts static and animated inputs and owns encoding, metadata, limits, and diagnostics.
- **Defer public support:** Keep the low-level sender limited to QA and internal transport use until a broader media-conversion direction is sponsored.

## Reproduction Assessment

Yes at the source-contract level: current action discovery omits `sticker`, ordinary image sends always build an image payload, and the outbound options cannot carry sticker intent. A live WhatsApp run was not performed in this read-only review.

## Solution Assessment

No, automatic WebP detection or empty-caption inference is not the best solution because it creates an ambiguous competing interpretation of ordinary image sends. An explicit transport-only sticker action is the narrowest maintainable first step.

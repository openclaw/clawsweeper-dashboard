## Summary

Keep open: current main has a structured WhatsApp sticker transport primitive, but normal message-tool users still cannot reach it because WhatsApp does not advertise or dispatch a public sticker action. Both related implementation PRs closed unmerged, and maintainers still need to define the accepted media and conversion contract.

## What This Changes

Add first-class outbound WhatsApp sticker sending instead of delivering sticker-intended media as ordinary image attachments.

## Best Possible Solution

Complete a typed public sticker action at the WhatsApp plugin boundary, reuse the canonical structured sender, define explicit validation or conversion rules, document the input contract, and prove static and supported animated behavior with a live WhatsApp send.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should public WhatsApp sticker sending require sticker-ready WebP media, or should OpenClaw convert supported source images into valid WhatsApp stickers?

Rationale: The transport primitive and plugin ownership are established, but accepted source formats, animation support, conversion behavior, and rejection semantics are a user-facing product contract that source inspection cannot choose safely.

Likely owner: steipete

Owner reason: The current-main refactor introduced both the low-level sticker sender and the adjacent action descriptor where the public contract would be completed.

Owner confidence: high

Options:

- **Convert supported images (recommended):** Add an explicit sticker action that normalizes common static images into valid WhatsApp sticker WebP and clearly rejects unsupported animated inputs.
- **Prepared WebP only:** Expose the action but require callers to provide sticker-ready WebP meeting documented size, dimension, animation, and metadata requirements.
- **Infer ordinary media sends:** Automatically reinterpret qualifying captionless WebP files from the normal send path as stickers, accepting implicit behavior and weaker intent clarity.

## Reproduction Assessment

Yes at source level. Current main omits `sticker` from WhatsApp's advertised actions, and repository-wide caller inspection shows the structured sticker sender is reachable only from QA and test surfaces.

## Solution Assessment

No, automatic captionless-WebP inference is not the best durable fix. The narrowest maintainable direction is an additive typed sticker contract wired to the existing WhatsApp sender, with explicit media preparation rules.

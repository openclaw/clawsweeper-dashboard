## Summary

Keep open: current main and v2026.6.11 still do not expose a user-facing WhatsApp sticker-send path, even though the low-level Baileys sticker payload helper exists.

## What This Changes

Request outbound WhatsApp sticker support through a sticker action, explicit send option, or safe WebP sticker routing.

## Best Possible Solution

Add first-class WhatsApp plugin sticker sending with explicit sticker intent, scoped media preservation or validation, Baileys sticker payload routing, docs, and focused action/send-path tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which public WhatsApp sticker-send contract and encoding policy should OpenClaw support before implementation?

Rationale: The source gap is clear, but action=sticker, an asSticker/sendAsSticker option, and automatic WebP detection have different user-facing compatibility and encoding tradeoffs.

Likely owner: mcaxtr

Owner reason: mcaxtr has the strongest recent history on the structured WhatsApp send helper that already emits a Baileys sticker payload.

Owner confidence: high

Options:

- **Use explicit sticker intent (recommended):** Expose action=sticker or an explicit WhatsApp send option and route media as stickers only when that intent is present.
- **Use WebP heuristics:** Automatically treat qualifying WebP media as stickers, accepting misclassification risk for ordinary WebP image sends.
- **Defer public support:** Keep the low-level helper and inbound sticker handling until a broader cross-channel sticker contract is chosen.

## Reproduction Assessment

Yes, at source level: current main still rejects WhatsApp action=sticker through the action gate and routes image/webp through the generic image branch. I did not run a live WhatsApp send in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public contract. The implementation belongs in the WhatsApp plugin, and explicit sticker intent plus scoped media handling is safer than silent WebP heuristics alone.

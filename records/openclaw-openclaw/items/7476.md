## Summary

Keep open: current main and the latest release still expose only a low-level WhatsApp sticker sender for QA/driver use, not a public WhatsApp sticker send action or normal WebP sticker path. The related implementation PRs are closed unmerged, and the remaining API plus sticker-encoding policy needs maintainer direction.

## What This Changes

Requested WhatsApp outbound sticker send support so WebP sticker media can be delivered as native WhatsApp stickers rather than generic images.

## Best Possible Solution

Add first-class WhatsApp plugin sticker sending with explicit user-facing sticker intent, scoped sticker media preservation or preparation, Baileys sticker payload routing, docs, and focused tests for action dispatch plus payload selection.

Rationale: The source gap is clear, but choosing between `action=sticker`, a send option, automatic WebP detection, and optional re-encoding affects user-visible behavior and compatibility for ordinary WebP image sends.

Likely owner: mcaxtr

Options:

- **Use Explicit Sticker Intent (recommended):** Expose `action=sticker` or a WhatsApp send option and route media as stickers only when that intent is present.
- **Use WebP Heuristics:** Treat qualifying WebP media as stickers automatically, accepting misclassification and encoding-policy risk for normal WebP images.
- **Defer For Cross-Channel Contract:** Keep the low-level helper and inbound sticker handling while waiting for a broader sticker contract across message channels.

## Reproduction Assessment

Yes, at source level: current main still routes normal `image/*` sends through the generic image branch and the active listener/action contracts do not expose a public sticker send path. I did not run a live WhatsApp send in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public contract. The implementation belongs in the WhatsApp plugin, and explicit sticker intent plus scoped media handling is safer than silent WebP heuristics alone.

## Summary

Current main has a tested Baileys-level WhatsApp sticker sender, but the supported outbound pipeline still cannot express sticker intent: WebP media follows the image path, the active listener contract omits sticker sending, and WhatsApp action discovery does not advertise a sticker action. The issue remains necessary pending a product decision between transporting sticker-ready WebP and converting arbitrary media. ([github.com](https://github.com/openclaw/openclaw/blob/main/extensions/whatsapp/src/inbound/send-api.ts))

## What This Changes

Add a supported outbound WhatsApp sticker path through an explicit message action or send option instead of delivering sticker WebP files as ordinary images.

## Best Possible Solution

Add an explicit WhatsApp sticker action or typed sticker-ready media option in the WhatsApp plugin, preserve validated WebP bytes, dispatch through the existing low-level sendSticker method, return clear format errors, and treat arbitrary image or animated conversion as a separately approved formatter capability.

Options:

- **Sticker-ready transport first (recommended):** Expose an explicit sticker action or option that accepts validated WhatsApp-ready WebP and reports actionable errors for incompatible media, leaving conversion to a later capability.
- **Built-in conversion pipeline:** Accept broader image and animation inputs and own resizing, WebP encoding, animation chunks, metadata, limits, and failure handling in the WhatsApp plugin.

## Reproduction Assessment

Yes at source level: on current main, ordinary image and WebP sends enter the generic image branch, the active listener and channel action contracts expose no sticker intent, and only an unconnected low-level sendSticker method exists. A live failing run was not needed to establish that the requested public capability remains absent. ([github.com](https://github.com/openclaw/openclaw/blob/main/extensions/whatsapp/src/inbound/send-api.ts))

## Solution Assessment

No single proposed approach is yet the best confirmed solution. The narrowest maintainable first step is explicit transport of validated sticker-ready WebP through the existing plugin-owned sender, rather than caption-based auto-detection or an unapproved general conversion pipeline.

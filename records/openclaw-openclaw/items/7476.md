## Summary

Keep this issue open. Current main and v2026.6.11 include a tested Baileys sticker transport primitive, but the supported WhatsApp action, listener, outbound adapter, and docs still expose only ordinary media delivery; a maintainer must choose whether OpenClaw validates sticker-ready WebP only or also owns image conversion.

## What This Changes

Expose outbound WhatsApp sticker sending through the supported message action using explicit media input.

## Best Possible Solution

Implement `action=sticker` for WhatsApp using the message tool’s existing explicit media fields, validate sticker-ready WebP, dispatch through the canonical `sendSticker` path, preserve ordinary WebP image delivery, and document the accepted format plus a redacted live WhatsApp proof path.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should initial WhatsApp sticker support require sticker-ready WebP media, or should OpenClaw also convert arbitrary static and animated images into compliant stickers?

Rationale: The action name, generic media input, Baileys transport, and tests already exist; conversion ownership materially expands the supported contract, dependency behavior, and validation burden and cannot be selected safely from implementation evidence alone.

Likely owner: steipete

Owner reason: They have the strongest combined history across the shared message-action contract, WhatsApp outbound delivery, and prior product review of this exact issue.

Owner confidence: high

Options:

- **Require sticker-ready WebP (recommended):** Ship a bounded explicit sticker action that validates supplied WebP media and returns actionable errors for unsupported input.
- **Add full image conversion:** Accept common static and animated image formats and own resize, WebP encoding, animation, and sticker metadata compatibility.

## Reproduction Assessment

Yes, at source level. Current main and v2026.6.11 contain a tested low-level WhatsApp sticker sender, while action discovery, the active-listener contract, the outbound adapter, and public docs provide no supported route to call it.

## Solution Assessment

No, the closed PR approaches are not the best permanent solution. Automatic WebP detection conflates media format with intent, while a parallel `sendAsSticker` flag bypasses the existing action model; explicit `action=sticker` using current media fields and the canonical sender is narrower and more maintainable.

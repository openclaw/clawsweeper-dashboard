## Summary

Keep this issue open: the configured cap is an existing contract, and the reported load-then-write interleaving is a plausible time-of-check/time-of-use race. Current documentation establishes serialization for individual session-store mutations, but does not prove that the enqueue function’s complete read, deduplication, limit check, and append execute atomically; no merged fix or canonical related item was found.

## What This Changes

Make concurrent plugin next-turn injection enqueues reliably enforce the per-session upper limit.

## Best Possible Solution

Perform the read, deduplication, cap check, and append as one per-agent serialized session-accessor mutation or synchronous SQLite transaction, then add a barrier-controlled concurrency regression test proving the stored array never exceeds the cap.

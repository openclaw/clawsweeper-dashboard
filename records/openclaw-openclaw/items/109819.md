## Summary

Keep this PR open: moving LINE onto the canonical durable ingress drain is architecturally sound, but the polling loop can exceed the predecessor’s process-wide eight-delivery cap and start progressively more concurrent agent/reply runs during a multi-lane backlog.

## What This Changes

This PR replaces LINE’s private webhook replay worker with the shared SQLite channel-ingress drain, preserves durable-before-ack admission and per-source ordering, and moves deduplication to completion tombstones.

## Best Possible Solution

Keep the shared-drain migration, but make LINE drain scheduling single-flight or enforce a process-wide eight-delivery semaphore, then add a slow-delivery regression test proving repeated polling never exceeds the configured cap.

## Reproduction Assessment

Yes, the original durability problem and the introduced concurrency regression are source-reproducible: acknowledgment depends on durable admission, while repeated timer calls can each claim eight different lanes before earlier deliveries finish. A focused runtime test is still needed for the multi-tick concurrency case.

## Solution Assessment

No, not as submitted. Reusing the shared drain is the narrowest maintainable architecture, but the LINE adapter must preserve a global concurrency bound rather than treating the drain’s per-invocation start limit as one.

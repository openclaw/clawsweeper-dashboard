## Label Justifications

- `P2`: The issue breaks documented multi-turn webhook behavior and wastes transcript and token resources, but it has bounded scope, a workaround, and an open implementation PR.
- `impact:session-state`: Repeated hook turns with one logical session key lose conversation and native runtime-thread continuity.
- `impact:data-loss`: Earlier conversation history is silently omitted from subsequent turns and previous transcript files become orphaned from the active key mapping.
- `impact:security`: Persistent mode would let hook requests select stored conversation context, requiring explicit authorization and namespace controls.

## Summary

Current main still routes direct and mapped hook-agent requests through isolated execution, so stable session keys do not preserve transcript continuity. The issue remains necessary, but the open linked PR already owns implementation and maintainers must confirm the stored-session re-entry security boundary before landing it.

## What This Changes

Add an explicit opt-in persistent mode for webhook agent runs so stable session keys can retain multi-turn context while isolated execution remains the default.

## Best Possible Solution

Land an updated form of the linked PR after confirming explicit opt-in re-entry, isolated-by-default compatibility, strict request-key and prefix authorization, session freshness behavior, and aligned direct-payload, mapping, transform, dedupe, schema, documentation, and upgrade coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should authenticated hook callers be allowed to opt into re-entering an existing session when their supplied or templated session key passes the configured request-key and prefix policy?

Rationale: Persistent mode intentionally selects stored transcript and runtime context, while the session key is routing context rather than an independent authentication boundary; maintainers must confirm which callers may inherit that state.

Likely owner: steipete

Owner reason: The issue history records this reviewer framing both the preferred compatibility shape and the unresolved security decision.

Owner confidence: medium

Options:

- **Allow Explicit Persistence (recommended):** Permit sessionMode="persistent" only for authenticated hooks whose keys pass allowRequestSessionKey and allowedSessionKeyPrefixes policy, while keeping isolated as the default.
- **Keep Hooks Isolated:** Reject stored-session re-entry and revise the hook documentation to state that stable keys provide routing and metadata continuity only.
- **Create Separate Session API:** Keep hook-agent isolated and expose trusted existing-session delivery through a distinct API with stronger authorization and state controls.

## Reproduction Assessment

Yes at source level: current direct and mapped hook dispatch remains isolated, forces a new session, and exposes no persistent-mode field. Recent users also reproduced the behavior on released versions, although this read-only review did not execute a new live run.

## Solution Assessment

Yes, an explicit isolated-or-persistent mode is the narrowest maintainable solution because it restores documented multi-turn behavior without silently weakening existing isolation. Automatic reuse would be less upgrade-safe, while a reuseSession boolean would express the lifecycle contract less clearly.

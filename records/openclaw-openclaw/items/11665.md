## Label Justifications

- `P2`: The issue breaks bounded multi-turn webhook workflows but has an external-history workaround and does not disable the core runtime for all users.
- `impact:data-loss`: Each isolated invocation replaces the active session mapping, making earlier conversation history unavailable to later turns and leaving orphaned transcripts.
- `impact:session-state`: A stable hook session key does not preserve the conversation session identity or transcript across webhook turns.
- `impact:security`: Any persistence implementation must authorize which stored sessions externally triggered webhook content may re-enter.
- `maturity:stable`: The affected Gateway runtime and HTTP API feature is currently scored M4 Stable.

## Summary

Keep open. Current main still forces hook-agent requests through isolated execution, so stable session keys do not retain transcript continuity; the open linked pull request is the active candidate fix, pending an explicit stored-session security-boundary decision.

## What This Changes

Allow hook-agent calls with a stable session key to opt into reusing an existing conversation session across webhook turns.

## Best Possible Solution

Provide an explicit persistent mode only for authenticated, prefix-constrained hook-owned session keys, preserve isolated execution as the default, and prove isolation, concurrency, upgrade, and delivery-context behavior before landing the linked implementation.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should authenticated hook-agent requests be allowed to re-enter stored sessions through an explicit persistent mode, and must reuse be limited to hook-owned allowed-prefix keys rather than arbitrary existing channel sessions?

Rationale: The implementation gap is clear, but choosing the reusable session namespace determines whether external webhook content can cross conversation, agent, and delivery boundaries.

Likely owner: steipete

Owner reason: He already documented the preferred compatibility shape and is the strongest available routing candidate for the remaining product and security boundary.

Owner confidence: medium

Options:

- **Approve hook-scoped persistence (recommended):** Add explicit persistent mode with isolated default, retain hook authentication and allowed-prefix checks, and limit reuse to hook-owned session keys.
- **Keep hooks isolated:** Continue creating fresh sessions for hook-agent runs and revise documentation to clarify that stable keys do not preserve transcript continuity.
- **Allow general session re-entry:** Permit trusted hooks to target existing agent or channel sessions with a broader authorization policy and dedicated cross-channel security tests.

## Reproduction Assessment

Yes at source level: hook dispatch still creates isolated jobs and the runner converts that target into forced-new session resolution; multiple users also report the same behavior on released versions. A live current-main reproduction was not run during this read-only review.

## Solution Assessment

Yes, an explicit opt-in persistent mode is the narrowest maintainable direction. Automatic reuse would break isolation compatibility, while unrestricted existing-session targeting would unnecessarily widen the security boundary.

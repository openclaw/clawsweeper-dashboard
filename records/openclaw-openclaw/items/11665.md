## Summary

Keep this issue open. The requested persistent-session behavior is not documented on current main, and the still-open linked implementation candidate at https://github.com/openclaw/openclaw/pull/75918 explicitly closes this issue, so closing or dispatching a duplicate fix before that PR is reviewed would be premature.

## What This Changes

Add an explicit, backward-compatible persistent mode for hook-agent requests so authorized stable session keys can reuse an existing conversation session across webhook turns.

## Best Possible Solution

Land one narrowly scoped, rebased implementation that keeps hooks isolated by default and permits transcript reuse only through an explicit persistent mode guarded by existing hook authentication and session-key-prefix policy.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should authorized hook-agent calls be allowed to opt into resuming an existing stored session, and which key-prefix and agent-scope guarantees must that persistent mode enforce?

Rationale: The implementation is mechanically bounded, but it deliberately changes whether external webhook input can enter prior agent context; that authorization boundary requires maintainer intent.

Likely owner: steipete

Owner confidence: medium

Options:

- **Approve explicit persistent mode (recommended):** Adopt the linked PR’s opt-in `sessionMode: "persistent"` direction, retain isolated-by-default behavior, and require focused authorization and regression proof.
- **Keep hooks permanently isolated:** Clarify the API and documentation that hook runs cannot resume stored conversation state, leaving integrations to inject their own context.
- **Design a narrower session target contract:** Define a distinct existing-session target or tighter namespace policy before accepting any persistent hook-session surface.

## Reproduction Assessment

Yes, source-reproducible with high confidence: current documented hook input accepts an authorized `sessionKey` but exposes no persistent-session mode, while the traced isolated-runner path forces fresh session behavior. A live run was not performed in this read-only review.

## Solution Assessment

Unclear until maintainers confirm the authorization boundary. An explicit opt-in persistent mode is the narrowest maintainable direction because automatic reuse would weaken the established isolated default for hook invocations.

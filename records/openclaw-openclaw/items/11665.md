## Label Justifications

- `P2`: This is a concrete user-facing hook session continuity problem with a bounded hook/config surface, but not an emergency or live core-runtime outage.
- `impact:session-state`: Stable hook session keys do not preserve transcript/session identity across webhook turns, causing agent context drift.
- `impact:data-loss`: The reporter and later commenters describe previous webhook transcript context becoming unreachable for subsequent turns and orphaned transcript files accumulating.
- `impact:security`: Allowing external hooks to re-enter existing sessions changes routing and trust boundaries that must stay explicit and gated.
- `maturity:stable`: The issue affects Gateway HTTP hook APIs under gateway-runtime, which the scorecard marks M4 Stable.

## Summary

Keep open: current main and the latest release still route hook-agent requests through isolated cron-style sessions, and the open linked implementation PR should own the active review path before this issue closes.

## What This Changes

Webhook hook sessions should support an explicit persistent mode so stable hook session keys can preserve multi-turn context.

## Best Possible Solution

Review, narrow, and either land or reject https://github.com/openclaw/openclaw/pull/75918; the maintainable end state is explicit sessionMode with isolated as the default and documented security guidance.

Options:

- **Accept explicit persistent mode (recommended):** Review and land a narrow version of https://github.com/openclaw/openclaw/pull/75918 that keeps isolated as the default and gates persistence through existing hook auth and session-key policy.
- **Keep hooks isolated-only:** Reject the linked PR direction and update docs to state that hook sessionKey is routing metadata rather than transcript continuity.
- **Design broader session identity first:** Pause the linked PR and decide a wider trusted-hook identity and concurrency model before adding public config surface.

## Reproduction Assessment

Yes, source-reproducible: current main routes hook-agent requests as isolated jobs, the cron runner passes forceNew for isolated jobs, and the session helper only reuses IDs when forceNew is false. I did not run a live webhook scenario in this read-only review.

## Solution Assessment

Yes, the explicit sessionMode direction appears to be the best maintainable solution because it preserves current isolated defaults while giving trusted integrations deliberate persistence. Automatic reuse from any stable sessionKey would be a weaker security and compatibility fit.

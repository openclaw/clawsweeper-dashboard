## Label Justifications

- `P2`: This is a normal-priority user-facing hook/session improvement with concrete source proof and bounded gateway/config impact.
- `impact:session-state`: Stable hook `sessionKey` values currently cannot preserve the intended multi-turn session context across webhook invocations.
- `impact:data-loss`: The report describes conversation history becoming unusable for follow-up turns and orphaned transcript files accumulating under repeated stable hook keys.
- `impact:security`: The requested persistent mode changes how authenticated external hook callers can target session context and needs an explicit trust boundary.
- `maturity:stable`: The affected hook ingress HTTP API is part of `gateway-runtime`, which is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main and the latest release still route hook-agent requests through isolated cron runs, so stable hook `sessionKey` values cannot opt into multi-turn session reuse, and the live closing PR has not merged.

## What This Changes

The issue requests persistent multi-turn webhook hook sessions when callers provide a consistent `sessionKey`, preferably through an explicit hook session mode.

## Best Possible Solution

Review and either land or reject https://github.com/openclaw/openclaw/pull/75918 as the canonical fix path, preserving isolated default behavior while adding a documented persistent hook-session opt-in with schema, docs, security policy, and regression coverage.

## Reproduction Assessment

Yes. Source inspection on current main shows `/hooks/agent` creates an isolated cron job, the runner passes `forceNew=true`, and `resolveCronSession` only reuses an existing `sessionId` when `forceNew` is false.

## Solution Assessment

Yes for the explicit opt-in shape, but not for automatic reuse by default. The best visible solution is `sessionMode: "isolated" | "persistent"` because it preserves safe isolated defaults while giving trusted hooks a narrow, reviewable path to reuse session context.

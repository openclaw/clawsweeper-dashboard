## Summary

Keep open. Current main still routes hook-agent requests through isolated execution, so a stable hook session key cannot preserve transcript continuity; the open linked pull request is the active implementation candidate, but maintainers must approve the stored-session security boundary before it lands. 

## What This Changes

Add an explicit persistent hook-session mode so trusted webhook calls with a stable session key can continue an existing multi-turn conversation.

## Best Possible Solution

Land one explicit `sessionMode: "isolated" | "persistent"` contract across direct payloads, configured mappings, and transform results, keeping isolation as the default and permitting persistence only behind hook authentication, scoped allowed session-key prefixes, replay separation, and focused concurrency/security coverage.

Question: Should trusted hook-agent requests be allowed to re-enter an existing stored session when they explicitly select persistent mode and pass the configured session-key policy?

Rationale: Current session keys are routing identifiers rather than authorization boundaries, so source inspection cannot decide whether hook authentication plus allowed prefixes is the intended permanent authority model for durable-session access.

Likely owner: steipete

Owner confidence: medium

Options:

- **Approve scoped persistent mode (recommended):** Allow explicit persistent mode for direct and mapped hook-agent requests while retaining isolated defaults and enforcing hook authentication plus allowed session-key prefixes.
- **Limit persistence to mappings:** Permit persistent sessions only in operator-controlled mapping configuration and reject request- or transform-selected persistence to narrow the external authority surface.
- **Keep hooks isolated:** Retain fresh sessions for all hook-agent calls and document that external integrations must use another authenticated session-entry API for continuity.

## Reproduction Assessment

Yes at source level: direct and mapped hook-agent calls resolve to an isolated job, and that runner necessarily passes `forceNew: true`, so repeated stable keys cannot reuse their stored session ID. A new runtime reproduction was not executed during this read-only review.

## Solution Assessment

Yes at the architecture level: an explicit opt-in mode is narrower and safer than automatic reuse or deterministic session IDs. The exact authority boundary still requires maintainer approval before the linked implementation can be accepted.

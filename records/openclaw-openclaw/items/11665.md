## Summary

Keep open: current main still forces hook-agent requests through isolated cron execution, so stable hook sessionKey values cannot reuse the existing conversation session, and an open linked PR already owns the persistent-mode implementation path.

## What This Changes

The issue requests multi-turn webhook hook sessions by reusing an existing session when callers provide a stable sessionKey.

## Best Possible Solution

Review and land the linked backward-compatible persistent hook-session mode if it preserves isolated-by-default behavior, hook auth, and allowed session-key prefix checks.

## Reproduction Assessment

Yes, at source level: /hooks/agent dispatch uses sessionTarget="isolated", isolated cron passes forceNew=true, and resolveCronSession bypasses entry.sessionId reuse when forceNew is true. I did not run a live webhook repro in this read-only review.

## Solution Assessment

Yes on direction, pending PR review: the narrow maintainable solution is an explicit persistent mode that keeps isolated as the default and preserves hook session-key security boundaries.

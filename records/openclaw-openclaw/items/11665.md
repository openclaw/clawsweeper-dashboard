## Label Justifications

- `P2`: This is a normal-priority user-facing hook/session improvement with source proof and production workaround reports, but no emergency outage evidence.
- `impact:session-state`: Stable hook sessionKey values currently do not preserve the intended multi-turn session context across webhook invocations.
- `impact:data-loss`: The report describes prior conversation context becoming unavailable for follow-up turns and orphaned transcript files accumulating under repeated stable hook keys.
- `impact:security`: The requested persistent hook mode changes how external authenticated hook callers can target durable session context and needs an explicit trust boundary.
- `maturity:stable`: The affected hook ingress path is part of the M4 Stable gateway-runtime HTTP API surface in the checked-out maturity scorecard.

## Summary

Keep open: current main and the latest release still route hook-agent requests through isolated cron execution, so a stable hook sessionKey cannot reuse the existing session id; the issue is already paired with an open closing PR that should be reviewed instead of spawning another fix branch.

## What This Changes

The issue requests multi-turn webhook hook-agent support by reusing an existing session when callers provide a consistent sessionKey.

## Best Possible Solution

Review and either land or reject https://github.com/openclaw/openclaw/pull/75918 as the canonical fix, preserving isolated default behavior while adding an explicit documented persistent hook-session opt-in.

## Reproduction Assessment

Yes. Source inspection on current main shows /hooks/agent creates an isolated cron job, the runner passes forceNew=true, and resolveCronSession only reuses an existing sessionId when forceNew is false.

## Solution Assessment

Yes directionally, but the open PR still needs maintainer review. An explicit sessionMode-style opt-in is the best visible shape because it preserves isolated safe defaults while giving trusted hooks a narrow persistent-session path.

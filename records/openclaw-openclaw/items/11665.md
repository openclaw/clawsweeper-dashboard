## Label Justifications

- `P2`: This is a concrete user-facing hook/session continuity problem with bounded gateway, config, and cron surfaces, but no emergency outage evidence.
- `impact:session-state`: Stable hook sessionKey values currently do not preserve the active transcript/session identity across webhook turns.
- `impact:data-loss`: Reporters describe prior webhook conversation context becoming unreachable for later turns and orphaned transcript files accumulating.
- `impact:security`: Allowing external hook callers to re-enter existing sessions changes routing and trust boundaries and must preserve explicit security gates.
- `maturity:stable`: The affected hook HTTP ingress path maps to gateway-runtime HTTP APIs, and qa/maturity-scores.yaml marks gateway-runtime M4 Stable.

## Summary

Keep open: current main still routes hook-agent requests through isolated cron sessions, so stable hook sessionKey values cannot preserve transcript continuity; the open linked implementation PR is the active candidate and needs maintainer security/product review before this issue closes.

## What This Changes

The issue requests multi-turn webhook hook sessions by reusing an existing session when callers provide a stable sessionKey.

## Best Possible Solution

Review and either land or reject https://github.com/openclaw/openclaw/pull/75918; the desired end state is an explicit sessionMode option with isolated defaults, documented trust guidance, schema/docs coverage, and regression tests for direct payloads, mappings, transforms, and session reuse.

- **Keep Hooks Isolated-Only:** Reject the persistent-mode direction and update docs to say hook-agent sessionKey values do not provide transcript continuity.
- **Pause For Broader Session Identity Design:** Defer the linked PR and define a wider deterministic session identity model for trusted hooks before adding public config surface.

## Reproduction Assessment

Yes. Source inspection shows hook-agent requests are dispatched as isolated jobs, isolated jobs pass forceNew: true, and the session helper only reuses stored IDs when forceNew is false; I did not run a live webhook scenario in this read-only review.

## Solution Assessment

Yes for the explicit opt-in sessionMode shape, pending maintainer approval. Automatic reuse would be riskier because it changes current isolation semantics without making the trust boundary visible.

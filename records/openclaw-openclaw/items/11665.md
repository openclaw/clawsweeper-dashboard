## Label Justifications

- `P2`: This is a validated, user-affecting hook-session improvement with limited blast radius and an open implementation path, but it is not an emergency runtime failure.
- `impact:session-state`: Repeated hook turns using one stable key lose conversation continuity because each isolated dispatch receives a new session identity.
- `impact:data-loss`: The active session mapping silently moves to a new transcript while prior transcript files become detached from the expected multi-turn conversation.
- `impact:security`: The requested persistent mode changes whether an authenticated external hook caller may re-enter existing transcript state selected by a session key.

## Summary

Current main still forces hook-agent requests through detached isolated execution, so stable hook session keys cannot preserve transcript continuity. The issue remains necessary, but the open linked PR already owns implementation and the persistent-session security boundary needs explicit maintainer approval.

## What This Changes

Add an explicit opt-in persistent session mode so direct and mapped hook-agent requests can reuse a fresh existing session for a stable session key while isolation remains the default.

## Best Possible Solution

Expose one canonical `sessionMode: "isolated" | "persistent"` hook contract across direct payloads, mappings, and transforms; default to isolation, retain hook authentication and session-key prefix/agent scoping, reuse only fresh sessions in persistent mode, and document the trust model.

Options:

- **Approve explicit persistence (recommended):** Allow `sessionMode: "persistent"` only as an explicit opt-in while preserving isolated default behavior and existing auth, prefix, and agent-scoping checks.
- **Keep hooks isolated:** Reject persistent re-entry, keep every hook turn detached, and document that stable session keys provide routing metadata rather than transcript continuity.

## Reproduction Assessment

Yes at source level: direct and mapped hook-agent calls become isolated jobs, detached execution forces a new session ID, and no current payload or config field can disable that behavior. A current-main live reproduction was not run during this read-only review.

## Solution Assessment

Yes, the explicit opt-in mode is the safest maintainable direction; automatic reuse from every stable key would silently weaken the existing isolation default. The linked PR is the appropriate implementation candidate after current-main refresh and security-boundary approval.

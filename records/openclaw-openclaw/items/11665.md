## Label Justifications

- `P2`: This is a real production webhook/session-state problem with a bounded hook/config surface and an active PR candidate, not a core outage.
- `impact:session-state`: Stable hook `sessionKey` values currently do not preserve the intended conversation/session continuity across hook-agent turns.
- `impact:data-loss`: Each hook turn can roll to a fresh transcript/session id, orphaning prior conversation history from the user's intended thread.
- `impact:security`: The requested persistent mode would let trusted external hooks re-enter sessions, so hook auth and session-key prefix policy are part of the fix boundary.
- `maturity:stable`: The issue affects Gateway HTTP hook ingress, which belongs to the M4 Stable `gateway-runtime` / `HTTP APIs` maturity surface.

## Summary

Keep open: current main and the latest release still force hook-agent requests through isolated cron execution, so a stable hook `sessionKey` cannot yet provide multi-turn session reuse; the active closing work is an open implementation PR, not a merged fix.

## What This Changes

The issue requests persistent multi-turn hook-agent sessions when callers provide a stable `sessionKey`, preferably through an explicit backward-compatible hook session mode.

## Best Possible Solution

Land one explicit `sessionMode: "isolated" | "persistent"` hook path for direct `/hooks/agent`, mappings, and transform results, with `isolated` as the default and documented trusted-integration security boundaries.

## Reproduction Assessment

Yes. Source inspection on current main shows `/hooks/agent` creates an isolated cron job, the runner passes `forceNew=true`, and `resolveCronSession` only reuses an existing `sessionId` when `forceNew` is false.

## Solution Assessment

Yes, the explicit `sessionMode` direction appears to be the best maintainable shape because it preserves isolated defaults while letting trusted hook integrations opt into persistent session reuse.

## Label Justifications

- `P2`: This is a confirmed, bounded webhook session-continuity gap affecting real integrations, but it is a longstanding opt-in capability decision rather than an emergency or recent regression.
- `impact:data-loss`: Each isolated webhook turn silently drops prior conversation history from the active run and leaves older transcript artifacts disconnected from the current session entry.
- `impact:session-state`: The issue concerns stable session keys being remapped to fresh session identities instead of preserving transcript and native-thread state.
- `impact:security`: Allowing webhook callers to re-enter stored sessions changes the context-isolation boundary and requires strict authentication and session-key scoping.
- `maturity:stable`: The affected Gateway runtime HTTP API surface, including Hooks, is scored M4 Stable with 90% quality and completeness.

## Summary

Keep open. Current hook-agent behavior and current documentation still provide no persistent-session mode, while the open linked pull request is the active, proof-backed implementation candidate; maintainers must decide the stored-session security boundary before landing it.

## What This Changes

Allow trusted webhook agent calls with a stable session key to opt into reusing an existing conversation session for multi-turn interactions.

## Best Possible Solution

Land a current-main version of the linked pull request with explicit `sessionMode: "isolated" | "persistent"` support across direct payloads, mappings, and transforms; retain isolated as the default and require existing hook authentication and session-key prefix controls for persistent reuse.

Question: Should authenticated hooks be allowed to opt into re-entering an existing stored session through an explicit persistent mode under the current session-key prefix policy?

Rationale: The implementation is concrete and proof-backed, but choosing whether webhook callers may attach to stored conversation state defines a security and context-isolation boundary that automation cannot approve.

Likely owner: steipete

Owner confidence: high

Options:

- **Allow explicit persistent mode (recommended):** Accept persistent reuse only when explicitly requested, preserve isolated as the default, and enforce the existing hook-auth and allowed-session-prefix checks.
- **Keep hooks always isolated:** Reject stored-session attachment, close the linked pull request, and update webhook documentation so stable keys are not described as providing transcript continuity.

## Reproduction Assessment

Yes at source level: submit repeated authenticated `/hooks/agent` calls using the same permitted session key and observe fresh session identities and lost transcript continuity. Multiple users also reported the behavior on released versions, although this review did not execute a fresh runtime reproduction.

## Solution Assessment

Unclear pending the security-boundary decision. If persistent hook sessions are accepted, the linked pull request's explicit opt-in mode with isolation preserved by default is narrower and safer than automatic reuse for every stable key.

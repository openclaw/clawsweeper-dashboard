## Label Justifications

- `P2`: The gap breaks multi-turn webhook workflows and causes substantial token/latency overhead, but it is limited to hook-agent integrations and has an external-history workaround.
- `impact:session-state`: Repeated webhook turns using a stable session key do not retain the same stored conversation identity.
- `impact:data-loss`: Fresh session IDs disconnect prior transcripts from the stable key, making conversation history unavailable to later turns and leaving orphaned history artifacts.
- `impact:security`: The requested option determines whether externally triggered hooks may re-enter persisted agent context.

## Summary

Current main still runs hook-agent requests as isolated turns, so stable hook session keys cannot preserve transcript continuity. This issue should remain open because the viable linked implementation PR is still open and the persistent-session security boundary requires explicit maintainer approval before landing.

## What This Changes

Add an explicit persistent session mode for direct and mapped hook-agent requests so stable scoped session keys can retain multi-turn conversation state while isolation remains the default.

## Best Possible Solution

Land a refreshed current-main version of the linked PR that keeps omitted mode isolated, permits persistent reuse only through an explicit trusted option, preserves existing session-key authorization checks, and proves direct payload, mapping, transform, replay-dedupe, fresh-install, and upgrade behavior.

Kind: security_boundary

Question: Should authenticated hook-agent callers be allowed to opt into reusing existing stored sessions when their session keys satisfy the configured prefix policy?

Rationale: The option intentionally changes external hook execution from isolated state to re-entry into persisted agent context, so automation cannot choose the permanent authorization and trust boundary.

Likely owner: steipete

Owner reason: Peter documented the preferred compatibility shape and is the strongest available routing candidate for the product/security boundary decision.

Owner confidence: medium

Options:

- **Allow scoped persistent mode (recommended):** Approve explicit persistent reuse for authenticated hooks with restricted session-key prefixes while preserving isolated behavior as the default.
- **Keep all hooks isolated:** Disallow stored-session re-entry and update the hook API documentation to state that hook session keys do not retain transcript continuity.

## Reproduction Assessment

Yes. Current main deterministically creates an isolated hook-agent job and forces detached session behavior, so repeated calls with the same stable session key cannot reuse the existing transcript.

## Solution Assessment

Yes. An explicit `isolated | persistent` mode is the best proposed shape because it preserves current compatibility and makes the security-sensitive state-reentry choice operator-controlled; automatic reuse would silently broaden existing hook behavior.

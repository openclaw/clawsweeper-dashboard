## Label Justifications

- `P2`: This is a concrete hook/session-state feature gap with production workaround reports, but no emergency outage evidence.
- `impact:session-state`: Stable hook session keys currently do not preserve multi-turn session context across webhook invocations.
- `impact:data-loss`: The report describes conversation history becoming unusable for follow-up turns and orphaned transcript files accumulating.
- `impact:security`: The requested persistent hook mode changes how authenticated hook callers can target durable session context.
- `maturity:stable`: The affected hook ingress path maps to Gateway runtime HTTP APIs, which is scored M4 Stable.

## Summary

Keep open: current main still routes hook-agent requests through isolated cron runs, so stable hook session keys cannot reuse existing session ids, and an open closing PR already owns the implementation path.

## What This Changes

Webhook hook sessions with stable session keys should support multi-turn reuse instead of always creating a fresh isolated session.

## Best Possible Solution

Review and either land or reject the open explicit `sessionMode` implementation, preserving isolated defaults and documented hook trust boundaries.

## Reproduction Assessment

Yes. Source inspection on current main shows direct hook-agent dispatch sets `sessionTarget: "isolated"`, the runner passes `forceNew=true`, and the session helper only reuses stored ids when `forceNew` is false.

## Solution Assessment

Unclear until maintainers finish reviewing the open fix PR. The explicit opt-in `sessionMode` shape is the best visible direction because it preserves isolated defaults while enabling trusted persistent hooks.

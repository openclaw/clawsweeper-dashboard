## Summary

Keep open: current main and the latest release still route hook-agent requests through isolated cron-style sessions, so a stable hook session key cannot preserve multi-turn transcript state. The linked implementation PR is still open with closing syntax and should remain the active fix path rather than spawning a duplicate repair.

## What This Changes

The issue requests multi-turn webhook hook sessions by reusing an existing session when a stable hook session key is supplied.

## Best Possible Solution

Review and land or deliberately reject the linked persistent hook-session PR, preserving isolated hook runs as the default and making durable transcript reuse an explicit trusted-hook mode.

Options:

- **Land explicit persistent mode (recommended):** Adopt `sessionMode: "persistent"` for trusted direct and mapped hooks while preserving isolated as the default.
- **Keep hooks isolated:** Reject persistent hook sessions and update docs/API wording so stable hook keys are not presented as multi-turn transcript identity.

## Reproduction Assessment

Yes. Source inspection shows direct hook-agent dispatch still uses `sessionTarget: "isolated"`, and isolated cron turns pass `forceNew: true`, so `resolveCronSession` cannot reuse a stored session id for a stable hook key.

## Solution Assessment

Yes on direction, but not yet complete on main. An explicit persistent mode is safer than implicit reuse because it preserves the current isolated default and makes trusted durable context reuse visible.

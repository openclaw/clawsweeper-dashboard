## Summary

Keep open: the implemented `message_received` hook and the related outbound-silencing work do not establish the requested terminal WhatsApp ingestion mode. The latest discussion identifies an additional unresolved contract—preventing agent/session creation and raw core persistence before the normal inbound turn path—so this remains a maintainer product and channel-ownership decision rather than a safe cleanup close.

Likely related people: `gassenjean` supplied the current ingress/persistence analysis (low confidence); `Bluetegu` is connected through the earlier read-only-account implementation attempt (low confidence).

## What This Changes

Add a WhatsApp account or route mode that delivers inbound messages to opted-in plugin hooks while bypassing agent/model/session, outbound, and raw-persistence paths.

## Best Possible Solution

Define a WhatsApp-owned, account- or route-scoped hooks-only ingress contract that runs before `runChannelInboundEvent`, permits only the declared hook delivery, fails closed on hook failure, disables every outbound side effect, and specifies the minimal permitted core persistence before implementation.

No—the adjacent read-only account approach is not the best complete solution because it silences outbound transport while still permitting agent/session work. A terminal WhatsApp ingress branch before `runChannelInboundEvent`, with an explicit retention contract, is the narrower maintainable boundary for the requested guarantee.

- A hooks-only mode needs an explicit owner-approved retention and failure contract: whether a hook may claim the provider event, what metadata core may retain, and whether missing/throwing/timed-out hooks fail closed without an agent fallback.

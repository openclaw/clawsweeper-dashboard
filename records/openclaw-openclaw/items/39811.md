## Summary

Keep open: current main now surfaces active fallback state, but generic catalog-backed validation for configured model refs is still missing from `openclaw config validate` and doctor. The remaining choice is policy-sensitive because custom, proxy, local, and forward-compatible model refs need warning/error semantics before a repair lands.

## What This Changes

The issue requests config/doctor validation and visible fallback warnings for invalid configured model references.

## Best Possible Solution

Adopt warning-first catalog-backed `config validate` and doctor checks across configured model refs, with explicit semantics for custom or forward-compatible refs and the current fallback-status notices retained.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should unknown configured model refs be warning-only in doctor/config validate, hard validation errors, or left to startup/runtime handling when catalog authority is incomplete?

Rationale: The code can enumerate configured refs, but the behavior affects custom providers, forward-compatible model names, fail-closed validation, and upgrade safety, so automation should not choose the contract alone.

Likely owner: steipete

Owner reason: The decision crosses model-selection, config validation, doctor, and compatibility policy surfaces where steipete has the strongest observed ownership signal.

Owner confidence: high

Options:

- **Warning-first validation (recommended):** Add catalog-backed doctor/config warnings for likely invalid configured refs while distinguishing trusted catalog absence from custom or future model refs without hard-failing existing setups by default.
- **Strict validation:** Reject unknown configured refs during config validation, accepting a compatibility break unless maintainers also define an escape hatch or migration contract.
- **Runtime-only handling:** Keep config validation permissive and rely on startup warmup, runtime errors, and fallback notices instead of adding a configured-ref analyzer.

## Reproduction Assessment

Yes, at source level: the schema accepts arbitrary model strings, config validation only rejects manifest-suppressed refs, and doctor catalog validation is generic only for `hooks.gmail.model`. I did not run a live CLI repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose policy: warning-first doctor/config validation appears safest, while hard errors need an explicit compatibility decision for custom and forward-compatible model refs.

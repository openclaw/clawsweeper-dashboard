## Summary

Keep open: current main now exposes active auto-fallback state, but generic validation for invalid configured model references is still missing from config validation and doctor, and the warning-versus-error policy is compatibility-sensitive.

## What This Changes

The issue requests early validation and user-visible diagnostics when configured model names are invalid or silently fall back to another model.

## Best Possible Solution

Add warning-first catalog/runtime-equivalent config validate and doctor diagnostics across configured model refs, with explicit custom and forward-compatible semantics and the current fallback-status notices retained.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should unknown configured model refs be warning-only in doctor/config validate, hard validation errors, or left to startup/runtime handling when catalog authority is incomplete?

Rationale: The code can enumerate configured refs, but the behavior affects custom providers, forward-compatible model names, fail-closed validation, and upgrade safety, so automation should not choose the contract alone.

Likely owner: steipete

Owner reason: The decision spans model selection, config schema/validation, doctor repair, and compatibility policy where steipete has the strongest observed ownership signal.

Owner confidence: high

Options:

- **Warning-first validation (recommended):** Add catalog-backed doctor/config warnings for likely invalid configured refs while distinguishing trusted catalog absence from custom or future model refs without hard-failing existing setups by default.
- **Strict validation:** Reject unknown configured refs during config validation, accepting a compatibility break unless maintainers also define an escape hatch or migration contract.
- **Runtime-only handling:** Keep config validation permissive and rely on startup warmup, runtime errors, and fallback notices instead of adding a configured-ref analyzer.

## Reproduction Assessment

Yes, at source level: schema accepts arbitrary model strings, config validation only rejects manifest-suppressed refs, and doctor catalog validation is generic only for hooks.gmail.model; no live CLI repro was run in this read-only review.

## Solution Assessment

Unclear until maintainers choose policy: warning-first doctor/config validation appears safest, while hard errors need an explicit compatibility decision for custom and forward-compatible model refs.

## Summary

Keep open: current main has better runtime unknown-model errors and fallback telemetry, but it still does not generally validate configured model refs against a catalog in `config validate` or doctor; related closed reports point back to this issue as the canonical tracker.

## What This Changes

Validate configured model references early and surface warnings or notifications when invalid primaries, overrides, or fallbacks would otherwise fail or route unexpectedly at runtime.

## Best Possible Solution

Add a maintainer-approved catalog-backed advisory path in `config validate` and doctor for all collected model refs, with explicit semantics for trusted catalog misses, custom providers, and runtime fallback visibility.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should configured model-ref validation be advisory, strict fail-closed, or limited to known-retired/suppressed catalog entries?

Rationale: Repository policy treats provider routing, config validation, and fallback behavior as compatibility-sensitive, and the source shows the remaining fix depends on how much catalog authority maintainers want over custom or forward-compatible refs.

Likely owner: vincentkoc

Owner reason: The current validation and configured-ref collection blame points to this area, and the decision is closest to config/model validation ownership.

Owner confidence: medium

Options:

- **Advisory trusted-catalog validation (recommended):** Warn in `config validate` and doctor when a configured ref is absent from trusted runtime/catalog evidence, while allowing custom and future refs with clear wording.
- **Strict fail-closed validation:** Reject all configured refs not present in the trusted catalog, reducing runtime surprises but risking breakage for custom providers and newly released models.
- **Keep suppression-only validation:** Continue only blocking known-retired or explicitly suppressed refs, preserving maximum compatibility but leaving the reported class mostly unresolved.

## Reproduction Assessment

Yes at source level: current main collects configured model refs but only rejects refs found in static suppression metadata, so arbitrary unknown refs are not generally caught before runtime. I did not run a live gateway repro because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the validation policy; the best fix is likely an advisory doctor/config validation path rather than an unconditional fail-closed check for every catalog miss.

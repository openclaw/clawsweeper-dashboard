## Summary

Keep open: current main now has visible model-fallback notices, but arbitrary invalid configured model refs still are not catalog-validated by `openclaw config validate` or general doctor checks. The downstream `openclaw-extensions doctor` workaround at https://github.com/exisz/openclaw-extensions is useful in-the-wild evidence that users still need a core diagnostic path.

## What This Changes

The issue asks OpenClaw to warn or validate when configured model refs cannot be verified against provider catalogs and to notify users when fallback occurs.

## Best Possible Solution

Define warning-first catalog authority, then add shared runtime-equivalent doctor and config-validate coverage for configured model refs while preserving an explicit path for custom and forward-compatible provider models.

Question: Should unknown configured model refs be warning-only in doctor/config validate, hard validation errors, or startup/runtime warnings, and which catalog source is authoritative for custom and forward-compatible providers?

Rationale: The source can identify configured refs, but warning versus hard-fail behavior affects existing custom providers, upgrade safety, and forward-compatible model names.

Owner confidence: high

Options:

- **Warning-first validation (recommended):** Add catalog-backed doctor/config warnings for unknown configured refs with wording that distinguishes trusted catalog absence from custom or forward-compatible refs.
- **Strict validation:** Reject unknown configured refs at config validation or write time, accepting compatibility risk unless an explicit escape contract is added.
- **Runtime-only handling:** Keep config validation permissive and rely on startup warnings, runtime errors, fallback notices, and status/doctor diagnostics instead.

## Reproduction Assessment

Yes, at source level: current validation inventories configured model refs but only rejects manifest-suppressed refs, and doctor catalog validation is scoped to `hooks.gmail.model`. I did not run a live CLI repro in this read-only cleanup review.

## Solution Assessment

Unclear until maintainer policy is set: warning-oriented doctor/config-validate coverage looks safest, while hard errors need an explicit compatibility decision for custom and forward-compatible models.

## Summary

Keep open: current main still only rejects manifest-suppressed configured model refs and hook-scoped Gmail model catalog misses, so arbitrary invalid configured model refs can still pass config validation or doctor and fail later at runtime.

## What This Changes

Warn or validate when configured primary, fallback, per-agent, channel, hook, or media model refs cannot be verified against the model catalog/provider routing before runtime.

## Best Possible Solution

Define warning-first catalog authority, then add shared doctor/config validate coverage for configured model refs while preserving an explicit path for custom and forward-compatible models.

Question: Should unknown configured model refs be warning-only in doctor/config validate, hard validation errors, or runtime/startup-only warnings, and which catalog sources are authoritative for custom and forward-compatible providers?

Rationale: The source can identify configured refs and catalog status, but warning versus hard-fail behavior affects existing custom providers, upgrade safety, and intentionally future model names.

Likely owner: steipete

Owner confidence: high

Options:

- **Warning-first validation (recommended):** Add catalog-backed doctor/config warnings for unknown configured refs with wording that distinguishes trusted catalog absence from custom or forward-compatible refs.
- **Strict validation:** Reject unknown configured refs at validation or write time, accepting a compatibility break unless an explicit escape contract is added.
- **Runtime-only handling:** Keep config validation permissive and rely on startup warnings, runtime errors, fallback notices, and status/doctor diagnostics instead.

## Reproduction Assessment

Yes at source level: current validation enumerates configured refs but only rejects manifest-suppressed refs, and doctor catalog validation is limited to hooks.gmail.model.

## Solution Assessment

Unclear until maintainer policy is set: warning-oriented doctor/config validate coverage looks safest, while hard errors need an explicit compatibility decision for custom and forward-compatible models.

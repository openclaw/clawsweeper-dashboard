## Summary

Keep open: current main and v2026.6.11 still only reject manifest-suppressed configured model refs and only run catalog-backed doctor validation for `hooks.gmail.model`, so the broader invalid configured-model warning/doctor path remains unresolved. The downstream `openclaw-extensions doctor` workaround and the closed duplicate reports are useful evidence that this is a real model-routing reliability gap.

## What This Changes

The issue asks OpenClaw to warn or validate when configured model references are unknown or invalid so users do not silently run or fail through a different or fallback model.

## Best Possible Solution

Define warning-first catalog authority for configured model refs, then add doctor/config-validate coverage for default, per-agent, fallback, channel, hook, and agent-written refs while preserving an explicit path for custom or forward-compatible models.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should unknown configured model refs be warning-only in doctor/config validate, hard validation errors, or left to startup/runtime handling when catalog authority is incomplete?

Rationale: The code can enumerate the affected refs, but the product behavior affects custom providers, forward-compatible model names, fail-closed validation, and upgrade safety, so automation should not choose the warning/error semantics alone.

Likely owner: steipete

Owner reason: Peter Steinberger has the strongest observed history across the model-selection, config, doctor, and fallback policy surfaces that need the decision.

Owner confidence: high

Options:

- **Warning-first validation (recommended):** Add catalog-backed doctor/config warnings for unknown configured refs, clearly distinguishing untrusted/custom catalog absence from likely invalid refs without hard-failing existing setups by default.
- **Strict validation:** Reject unknown configured refs at config validation time, accepting a compatibility break unless maintainers also define an explicit escape or migration contract.
- **Runtime-only handling:** Keep config validation permissive and rely on startup warmup, runtime errors, and fallback notices rather than adding a new configured-ref analyzer.

## Reproduction Assessment

Yes at source level: current validation enumerates the relevant refs but only rejects manifest-suppressed models, and doctor catalog validation is hooks-specific. I did not run a live current-main CLI repro in this read-only review.

## Solution Assessment

Unclear until maintainer policy is set: a warning-oriented doctor/config validate analyzer appears safest, while hard errors need an explicit compatibility decision for custom and forward-compatible models.

## Summary

Keep open: current main still only rejects manifest-suppressed configured model refs, while doctor catalog checks are scoped to `hooks.gmail.model`; arbitrary invalid primary, fallback, and per-agent model refs can still pass up-front validation. The old same-repo fix PR was closed unmerged, and the May 7 downstream `openclaw-extensions doctor` workaround is useful evidence that this remains a real provider/model reliability gap.

## What This Changes

The issue requests catalog-aware validation or warnings for invalid configured model refs, plus user-visible fallback notification when a primary model fails.

## Best Possible Solution

Define warning-first catalog authority for configured model refs, then add `config validate` and doctor coverage for default, per-agent, fallback, channel, hook, and model-map refs while preserving an explicit path for custom or forward-compatible models.

Kind: product_direction

Question: Should unknown configured model refs be warning-only in `config validate`/doctor, hard validation errors, or left to startup/runtime handling when catalog authority is incomplete?

Rationale: The source seam is clear, but the behavior affects custom providers, user-declared catalog rows, forward-compatible model names, fail-closed validation, and upgrade safety, so automation should not choose the permanent policy.

Likely owner: steipete

Owner reason: Peter has the strongest observed history on the shared model-selection and compatibility boundary that the policy decision must preserve.

Owner confidence: high

Options:

- **Warning-first validation (recommended):** Add catalog-backed warnings in `config validate` and doctor, with wording that distinguishes trusted catalog misses from custom or forward-compatible setups.
- **Strict validation:** Reject unknown configured refs at validation time, accepting a compatibility break unless an explicit escape or custom-provider contract is added.
- **Runtime-only handling:** Keep config validation permissive and rely on startup/runtime errors plus fallback notices instead of adding a new config analyzer.

## Reproduction Assessment

Yes, at source level: current validation enumerates the relevant refs but only rejects manifest-suppressed models, and doctor catalog validation is scoped to `hooks.gmail.model`. I did not run a live CLI repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose policy: warning-oriented doctor/config validation looks like the safest narrow path, while hard errors need an explicit compatibility decision for custom and forward-compatible models.

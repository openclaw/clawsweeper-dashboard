## Summary

Keep open: current main still only rejects manifest-suppressed configured model refs, and current doctor catalog validation is hooks-specific. The merged fallback-status repair covers the visibility half, but generic configured-model validation and doctor recovery remain unresolved.

## What This Changes

The issue requests validation or doctor warnings for invalid configured model references, plus visible fallback notification when a primary model fails.

## Best Possible Solution

Adopt warning-first, runtime-equivalent config validate and doctor checks for configured model refs, with explicit semantics for custom or forward-compatible refs and the existing fallback-status notices left intact.

Kind: product_direction

Question: Should unknown configured model refs be warning-only in doctor/config validate, hard validation errors, or left to startup/runtime handling when catalog authority is incomplete?

Rationale: The code can enumerate configured refs, but choosing warning versus error affects custom providers, forward-compatible model names, fail-closed validation, upgrades, and existing user configs.

Likely owner: steipete

Owner reason: This decision spans config validation, doctor, model selection, provider routing, and compatibility policy, where the current source and history point to steipete as the strongest routing candidate.

Owner confidence: medium

Options:

- **Warning-first validation (recommended):** Add catalog-backed doctor/config warnings for unknown configured refs while distinguishing trusted catalog absence from likely invalid refs without hard-failing existing setups by default.
- **Strict validation:** Reject unknown configured refs during config validation or write/reload, accepting an upgrade-visible compatibility break unless an explicit escape or migration contract is added.
- **Runtime-only handling:** Keep config validation permissive and rely on startup warmup, runtime errors, and fallback notices rather than adding a configured-ref analyzer.

## Reproduction Assessment

Yes, at source level: current schema accepts arbitrary model strings, validation only rejects manifest-suppressed refs, and doctor catalog validation is scoped to `hooks.gmail.model`. I did not run a live CLI/provider repro in this read-only review.

## Solution Assessment

Unclear until maintainers choose policy: warning-oriented doctor/config validate coverage appears safest, while hard errors require an explicit compatibility decision for custom and forward-compatible models.

## Summary

Keep open: current main and v2026.6.11 still accept arbitrary configured model strings except manifest-suppressed refs, and generic catalog-backed validation for configured model refs is still missing. The remaining fix needs maintainer policy on catalog authority and warning-versus-error behavior for custom, proxy, local, and forward-compatible models.

## What This Changes

The issue requests catalog-aware validation for configured model refs and clearer user-facing warning when invalid primary models fall through to another model.

## Best Possible Solution

Adopt warning-first catalog-backed config validate and doctor checks across configured model refs, with explicit trusted-catalog semantics for custom or forward-compatible refs and separate handling for visible fallback status.

Question: Should unknown configured model refs be warning-only in doctor/config validate, hard validation errors, or left to startup/runtime handling when catalog authority is incomplete?

Rationale: The code can enumerate configured refs, but choosing the validation contract affects custom providers, forward-compatible model names, fail-closed config behavior, and upgrade safety.

Likely owner: steipete

Owner reason: This decision crosses model-selection, config validation, doctor, and compatibility policy surfaces where steipete has the strongest observed history signal.

Owner confidence: high

Options:

- **Warning-first validation (recommended):** Add catalog-backed doctor/config warnings for likely invalid configured refs while distinguishing trusted catalog absence from custom or future model refs without hard-failing existing setups by default.
- **Strict validation:** Reject unknown configured refs during config validation, accepting a compatibility break unless maintainers also define an escape hatch or migration contract.
- **Runtime-only handling:** Keep config validation permissive and rely on startup warmup, runtime errors, and fallback notices instead of adding a configured-ref analyzer.

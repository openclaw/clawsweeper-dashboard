## Summary

Keep open: current main has user-visible fallback notices and a narrow static-suppression check, but it still does not generally validate configured model refs against a trusted catalog in config validation or doctor. The same-repo fix PR was closed unmerged, and the remaining behavior needs a maintainer choice about advisory versus strict validation semantics.

## What This Changes

The issue requests upfront validation for configured model names and visible notice when an invalid primary model falls back at runtime.

## Best Possible Solution

Add trusted, runtime-equivalent advisory validation for configured model refs in config validate and doctor, while preserving dynamic provider refs unless maintainers explicitly choose stricter behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should configured model refs be catalog-checked as advisory warnings by default, or should invalid catalog misses become strict config errors?

Rationale: Current code intentionally supports dynamic provider model IDs, so automation should not choose fail-open versus fail-closed semantics without maintainer product direction.

Likely owner: steipete

Owner reason: steipete has the clearest recent history across model failover, provider identity, and the documented user-visible fallback behavior that shapes this product tradeoff.

Owner confidence: medium

Options:

- **Advisory validation by default (recommended):** Warn in config validate and doctor when trusted catalog evidence says a configured ref is unknown, while keeping dynamic or unverified refs usable.
- **Strict catalog errors:** Reject unknown configured refs during config writes/validation, accepting the compatibility risk for custom and forward-compatible provider models.
- **Fold into broader model reconcile work:** Keep this as part of the broader model-configuration reconcile discussion before landing a narrower validation change.

## Reproduction Assessment

Yes, at source level: current validation only checks configured refs against static manifest suppressions, so arbitrary unsuppressed provider/model refs can still pass structural validation. I did not run a live provider validation repro.

## Solution Assessment

Unclear as a strict fix: fail-closed validation is not automatically best because provider plugins may intentionally accept arbitrary model IDs. The safer likely path is advisory config validate/doctor warnings backed by trusted catalog evidence, with strict behavior only if maintainers choose it.

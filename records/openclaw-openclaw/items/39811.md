## Summary

Keep open: current main still only rejects manifest-suppressed configured model refs and doctor catalog validation is scoped to `hooks.gmail.model`, so the broader invalid configured-model warning/doctor path remains unresolved. The downstream `openclaw-extensions doctor` workaround and linked open fork PR are useful context, but no viable target-repo fix has landed.

## What This Changes

The issue asks OpenClaw to catch invalid configured model names before runtime fallback or failure.

## Best Possible Solution

Add warning-first catalog-backed `openclaw config validate` and `openclaw doctor` checks for all collected configured model refs, with explicit handling for custom/forward-compatible catalogs and legacy bare `default` values.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should unknown configured model refs be warning-only in doctor/config validate, hard validation errors, or left to startup/runtime handling when catalog authority is incomplete?

Rationale: The code can enumerate the refs, but choosing warning/error semantics affects custom providers, forward-compatible model names, fail-closed validation, and upgrade safety.

Likely owner: Peter Steinberger

Owner reason: Recent adjacent model-catalog work makes this the best available owner for the catalog-authority and compatibility-policy decision.

Owner confidence: medium

Options:

- **Warning-first validation (recommended):** Add catalog-backed warnings for unknown configured refs while distinguishing trusted catalog absence from likely invalid refs without hard-failing existing setups by default.
- **Strict validation:** Reject unknown configured refs at config validation time, accepting a compatibility break unless maintainers also define an explicit escape or migration contract.
- **Runtime-only handling:** Keep config validation permissive and rely on startup warmup, runtime errors, and fallback notices instead of adding a configured-ref analyzer.

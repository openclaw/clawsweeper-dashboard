## Summary

Keep open: current main and v2026.6.11 still only reject manifest-suppressed configured model refs, while doctor catalog validation remains scoped to hooks.gmail.model; the broader request to warn on arbitrary invalid configured model refs is unresolved.

## What This Changes

The issue requests validation and user-facing warnings for invalid configured model references instead of accepting arbitrary model names until runtime failure or fallback.

## Best Possible Solution

Define warning-first catalog authority, then add doctor/config validate coverage that uses runtime-equivalent model resolution and distinguishes trusted discovered catalog rows from custom or forward-compatible configured rows.

Question: Should unknown configured model refs be warning-only in doctor/config validate, hard validation errors, or left to startup/runtime handling when catalog authority is incomplete?

Rationale: The code can enumerate configured refs, but the desired behavior affects custom providers, forward-compatible model names, fail-closed validation, and upgrade safety.

Likely owner: steipete

Owner confidence: high

Options:

- **Warning-First Validation (recommended):** Add catalog-backed doctor/config warnings for unknown configured refs, with clear wording for untrusted or custom catalogs and no hard failure by default.
- **Strict Validation:** Reject unknown configured refs at config validation time, accepting a compatibility break unless an explicit escape contract is added.
- **Runtime-Only Handling:** Keep config validation permissive and rely on startup warmup, runtime errors, and fallback notices instead of adding a new analyzer.

## Solution Assessment

Unclear until maintainer policy is set: a warning-oriented doctor/config validate analyzer appears safest, while hard errors need an explicit compatibility decision for custom and forward-compatible models.

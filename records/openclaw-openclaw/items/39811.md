## Summary

Keep open: current main and the latest release still only reject configured model refs that match static catalog suppressions; arbitrary unknown model strings can pass config validation and fail later at runtime. Related closed reports preserve this issue as the canonical tracker, and the remaining fix needs maintainer policy on advisory versus strict catalog validation.

## What This Changes

Model configuration should warn or validate when configured model refs are unknown before users hit runtime unknown-model failures or fallback opacity.

## Best Possible Solution

Add a maintainer-approved advisory validation path in config validate and doctor for all collected configured model refs, with clear handling for trusted catalog misses, custom providers, future model IDs, and runtime fallback visibility.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should configured model-reference validation be advisory, strict fail-closed, or limited to known-retired/suppressed catalog entries?

Rationale: OpenClaw policy treats config validation, provider routing, and fallback behavior as compatibility-sensitive, and source inspection shows the remaining fix depends on how much authority a catalog miss should have over custom or forward-compatible refs.

Likely owner: vincentkoc

Owner reason: Model/runtime history and release ownership make this the best available owner for the cross-cutting provider/config policy choice, with input from config and doctor contributors.

Owner confidence: medium

Options:

- **Advisory trusted-catalog validation (recommended):** Warn in config validation and doctor when trusted runtime/catalog evidence cannot resolve a configured ref, while keeping custom and forward-compatible refs usable with clear wording.
- **Strict catalog validation:** Reject any configured ref outside the trusted catalog, reducing runtime surprises but risking breakage for custom providers and newly released models.
- **Suppression-only validation:** Keep current behavior limited to known retired or suppressed refs, preserving compatibility while leaving most of the reported class unresolved.

## Reproduction Assessment

Yes, at source level: current main collects configured model refs but config validation only rejects refs with manifest suppression metadata, so arbitrary unknown refs can pass until runtime. I did not run a live gateway repro because this review is read-only.

## Solution Assessment

Unclear until maintainers choose validation semantics; the safest direction is likely advisory config/doctor warnings rather than unconditional fail-closed catalog enforcement.

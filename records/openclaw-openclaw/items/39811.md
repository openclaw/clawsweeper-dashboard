## Summary

Keep open: current main and v2026.6.11 still only reject manifest-suppressed configured model refs and run catalog validation for `hooks.gmail.model`, so the broader request to warn on arbitrary invalid primary/fallback agent model refs remains unresolved.

## What This Changes

The issue asks OpenClaw to validate or warn on configured model names that do not resolve to a trusted provider catalog before they fail or fall back at runtime.

## Best Possible Solution

Define warning-first catalog authority for configured model refs, then add doctor/config validate coverage for default, per-agent, fallback, channel, and hook refs while preserving an explicit path for custom or forward-compatible models.

Rationale: The implementation seam is clear, but the behavior affects custom providers, future model names, provider auth/catalog availability, and upgrade safety, so automation should not choose the permanent warning/error contract alone.

Owner confidence: high

Options:

- **Warning-first validation (recommended):** Add catalog-backed doctor/config validate warnings for unknown configured refs, with clear wording for untrusted or custom catalogs and no hard failure by default.
- **Strict validation:** Reject unknown configured refs at config validation time, accepting a compatibility break unless an escape contract or migration path is added.
- **Runtime-only handling:** Keep config validation permissive and rely on runtime errors, status, and fallback notices instead of adding a new analyzer.

## Reproduction Assessment

Yes at source level: current validation collects configured model refs but only checks manifest suppressions, while doctor catalog validation is limited to `hooks.gmail.model`. I did not run a live current-main CLI repro in this read-only review.

## Solution Assessment

Unclear until maintainer policy is set: a warning-oriented doctor/config validate analyzer appears safest, while hard errors need an explicit compatibility decision for custom and forward-compatible models.

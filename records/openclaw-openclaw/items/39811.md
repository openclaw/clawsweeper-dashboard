## Summary

Keep open: current main and the latest release still do not provide the requested general warning for arbitrary invalid configured model refs. Main has partial coverage for manifest-suppressed retired models, hooks-specific doctor checks, and visible fallback notices, but the broader config/doctor validation semantics still need a maintainer product decision.

## What This Changes

The issue requests config and doctor validation plus user-visible warnings when configured model names are unknown, stale, or silently fall back at runtime.

## Best Possible Solution

Define warning-first catalog authority for configured model refs, then add doctor/config validate coverage for default, per-agent, fallback, channel, and hook refs while preserving an explicit path for custom or forward-compatible models.

Rationale: The code can identify configured refs, but the desired behavior affects custom providers, forward-compatible model names, fail-closed validation, and upgrade safety, so maintainer product policy is required before a repair lane is safe.

Owner confidence: high

Options:

- **Warning-first validation (recommended):** Add catalog-backed doctor/config warnings for unknown configured refs, with clear wording for untrusted or custom catalogs and no hard failure by default.
- **Strict validation:** Reject unknown configured refs at config validation time, accepting a compatibility break for custom and forward-compatible setups unless an escape contract is added.
- **Runtime-only handling:** Keep config validation permissive and rely on startup warmup, runtime errors, and fallback notices rather than adding a new config/doctor analyzer.

## Reproduction Assessment

Yes, at source level: current validation enumerates the relevant refs but only rejects manifest-suppressed models, and the general runtime path still fails late with model_not_found. I did not run a live current-main gateway repro in this read-only review.

## Solution Assessment

Unclear until maintainer policy is set: a warning-oriented doctor/config validate analyzer appears safest, while hard errors need an explicit compatibility decision for custom and forward-compatible models.

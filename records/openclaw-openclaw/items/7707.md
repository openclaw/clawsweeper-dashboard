## Summary

Keep open for a maintainer-owned security and product decision: current documentation provides manual provenance guidance and untrusted framing, but it explicitly does not enforce memory policy or supply the requested framework-authenticated trust, retention, review, and influence contract.

## What This Changes

Add durable source-derived trust metadata and retrieval policy for agent memory so untrusted content can be retained as evidence without gaining authority over later behavior.

## Best Possible Solution

First choose a minimal, framework-authenticated provenance-and-authority contract at the memory-plugin boundary, then implement it in the selected memory owner with explicit storage-versus-influence policy, migration/doctor behavior, and end-to-end tests; keep external MCP/plugin implementations as supported alternatives if core ownership is not selected.

Rationale: Current policy treats workspace memory as trusted operator state and current memory guidance is advisory; only maintainers can choose whether changing that model is a core security commitment, a default-memory-plugin responsibility, or an external extension concern.

Likely owner: steipete

Owner reason: The prior review already routed this exact cross-cutting memory/security design question through the current memory contract area.

Owner confidence: medium

Options:

- **Design a bounded shared memory contract (recommended):** Define framework-owned origin, review, expiry, and influence fields plus the minimum retrieval/promotion hooks, then let the selected memory plugin enforce the policy.
- **Keep it extension-owned:** Document the supported plugin/MCP route and require each memory implementation to own its trust semantics without changing the shared default contract.
- **Defer while retaining the provenance prerequisite:** Advance the narrower source-attribution work first and revisit enforcement once its storage and retrieval contract is proven.

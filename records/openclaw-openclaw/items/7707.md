## Label Justifications

- `P2`: The issue describes meaningful security and session-state design work, but it is a feature/product gap rather than an urgent active regression or emergency.
- `impact:session-state`: The requested trust metadata would change how persistent memories and retrieved context influence later sessions.
- `impact:security`: The request targets memory poisoning and indirect prompt-injection risk from untrusted sources entering durable memory.

## Summary

Keep this open: current main still lacks durable, host-authored memory trust metadata, trust-policy config, review/expiration gates, and trust-weighted retrieval across the native memory paths; the external MCP/world-model examples are useful prior art but do not close the OpenClaw memory-core/QMD/SDK gap.

## What This Changes

Request source-derived trust tagging for durable memory entries, with policy controls for expiration, review, isolation, and retrieval influence.

## Best Possible Solution

Define one host-authored durable memory provenance/trust contract, then persist and enforce it consistently across memory-core, QMD, session-memory, Active Memory, Memory Wiki bridges, SDK/config surfaces, UI/docs, and migrations while evaluating AKF/world-model-mcp as prior art.

## Reproduction Assessment

Yes, at source level: current main exposes memory source buckets, citations, MMR, and temporal decay, but the inspected storage, SDK, config, tool schema, and retrieval paths do not carry or enforce durable trust metadata. This is a feature/security gap rather than a failing command reproduction.

## Solution Assessment

Unclear as a final implementation plan: trust tagging is the right direction, but the proposed config alone is not enough without maintainer decisions on host-assigned provenance, persistence/migration, plugin SDK compatibility, and retrieval policy.

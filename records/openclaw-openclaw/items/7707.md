## Summary

Current main still lacks durable trust metadata and influence-policy enforcement, while the related provenance issue and open source-actor PR cover only prerequisites; this remains a valid security-sensitive product design item.

## What This Changes

Request persistent source-based trust metadata and policy enforcement for memory ingestion, storage, retrieval, review, and expiration.

## Best Possible Solution

Define framework-assigned provenance, endorsement, retention, and influence-policy fields at the memory host/plugin boundary, then migrate and enforce that single contract in the recommended memory implementation.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw make provenance and influence policy a native memory plugin contract, or leave trust-governed memory entirely to external plugins and MCP integrations?

Rationale: This choice controls who may assign trust, how persisted claims gain execution influence, and whether every memory implementation must preserve and enforce the policy; repository evidence cannot determine that security boundary without maintainer intent.

Likely owner: vincentkoc

Owner reason: Recent blame and log history directly connect him to the public memory contracts, persisted schema, and retrieval manager where the durable boundary would be defined.

Owner confidence: high

Options:

- **Native shared contract (recommended):** Add framework-assigned provenance and influence-policy fields to the memory host contract, with enforcement in the recommended memory implementation and compatibility guidance for plugins.
- **External-only policy:** Keep the host contract lightweight and document vetted plugin or MCP systems such as the implementation linked in the discussion for deployments needing governed memory.
- **Active Memory only:** Limit the first design to explicit trusted-versus-untrusted Active Memory injection modes without claiming durable cross-backend trust enforcement.

## Reproduction Assessment

Yes at source level: current memory result, persisted schema, config, and retrieval contracts can be inspected directly and do not contain the requested trust or influence-policy model. This is a feature gap rather than a failing runtime reproduction.

## Solution Assessment

No, not as a simple fixed mapping from source type to trust level; the discussion and current architecture support separating causal provenance, human endorsement, retention permission, and execution influence under framework-controlled assignment.

## Summary

Keep this issue open. Current memory guidance explicitly says that trust labels, provenance, and untrusted-context framing are not an enforcing security boundary, while the requested framework-assigned provenance and retrieval influence controls remain absent. The active prerequisite work is overlapping rather than a duplicate, and the permanent core-versus-plugin policy boundary needs a maintainer decision.

## What This Changes

Add framework-assigned origin metadata and separate review/influence controls for persistent memory so untrusted content can be retained as evidence without silently becoming authoritative agent context.

## System Context

OpenClaw memory collects workspace and session material, stores it through memory backends, and retrieves relevant results into agent turns. This request would add a provenance and policy layer between ingestion and retrieval so origin and review state can constrain later influence on planning or output.

## Architecture Diagram

flowchart LR
  A[Inbound user and tool content] --> B[Framework-assigned provenance]
  B --> C[Memory storage backends]
  C --> D[Memory search and recall]
  F[Review and influence policy] --> D
  D --> E[Agent context and actions]

## Best Possible Solution

First define and land the framework-assigned provenance invariant tracked by https://github.com/openclaw/openclaw/issues/42647; then add a narrow v1 memory policy that preserves immutable origin, keeps review and influence state separate, enforces retrieval-time blocking or gating in the selected owner, and proves direct, queued, collect, flush, merge, and recall behavior before considering expiry, scoring, UI, or cross-backend guarantees.

## Risks / Open Questions

- A trust label that an agent, tool payload, or persisted content can self-assign would not provide an injection boundary; origin must be assigned by the framework and survive queued, collect, merge, flush, and recall paths.
- A single scalar trust score would conflate causal source, review status, retention, and authority. The design needs separately auditable provenance and influence state before adding decay, expiry, or UI semantics.
- Changing persistence and retrieval behavior across builtin memory, QMD, session memory, and optional bridges without an explicit migration and compatibility plan could make existing memory unexpectedly disappear or stop influencing recall.

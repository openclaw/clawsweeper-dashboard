## Summary

Keep this open: current main converges safely superseded migration residue but deliberately keeps genuinely divergent rows fail-closed, and two independent released-version reports confirm that `meta` divergence can permanently block startup. The embedding-cache sibling does not cover `meta` or the higher-risk `chunks` policy.

## What This Changes

Make legacy Memory Core sidecar conflicts converge without permanently blocking Gateway startup when authoritative per-agent SQLite state already exists.

## Best Possible Solution

Adopt a table-specific convergence policy: safely retire stale `meta`, treat derived cache conflicts under the narrower sibling policy, and keep `chunks` fail-closed unless identity and coverage checks prove canonical state contains every legacy chunk, with Doctor offering an in-product backed-up repair path.

- **Prefer canonical for all tables:** Archive the whole legacy sidecar whenever canonical rows exist, accepting the risk that distinct legacy chunks may be discarded.
- **Keep all divergence fail-closed:** Preserve the current strict policy but add an in-product Doctor recovery chooser with backup, comparison, and explicit operator confirmation.

## Reproduction Assessment

Yes at high-confidence source and reported-live level: seed differing legacy and canonical `meta` values, retain the legacy sidecar, and start the Gateway on the affected migration path. Two users reproduced the released failure, although this review did not execute the scenario locally.

## Solution Assessment

No, blanket canonical-wins handling for every table is not the safest fix because conflicting chunks may contain unique memory content. The narrowest maintainable solution distinguishes metadata, derived cache data, and indexed content and gives Doctor a convergent recovery path.

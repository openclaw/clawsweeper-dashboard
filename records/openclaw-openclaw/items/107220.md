## Label Justifications

- `impact:crash-loop`: The unresolved migration warning makes gateway startup exit repeatedly under the service restart policy.
- `impact:ux-release-blocker`: Affected users cannot complete the upgrade or restore service through the instructed Doctor flow and currently need manual SQLite sidecar inspection and file moves.

## Summary

This is a current, independently confirmed upgrade regression that can make the released gateway permanently unavailable. The broader report remains necessary because the related embedding-cache item does not resolve the reproduced `meta` conflict, while automatically accepting every `chunks` conflict could discard distinct memory content.

## What This Changes

Make legacy Memory Core sidecar conflicts converge without crash-looping the gateway when canonical per-agent SQLite state is already authoritative, including a working Doctor recovery path.

## Best Possible Solution

Adopt a table-specific migration policy: preserve canonical metadata and derived cache values for duplicate identities, import non-conflicting legacy rows, keep content-bearing chunk conflicts fail-closed unless full supersession is proven, and make `openclaw doctor --fix` safely archive verified-superseded sidecars with focused upgrade tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which legacy Memory Core tables may use canonical-wins conflict resolution, and what proof is required before a content-bearing `chunks` sidecar can be archived?

Rationale: Metadata and derived-cache conflicts can plausibly prefer canonical state, but chunk conflicts may represent distinct user memory; the permanent persisted-state policy cannot be selected safely from implementation mechanics alone.

Likely owner: vincentkoc

Owner reason: The strongest available routing signal is ownership of the merged Memory Core SQLite migration and its conflict contract.

Owner confidence: high

Options:

- **Use table-specific conflict rules (recommended):** Treat duplicate metadata and derived cache identities as canonical-wins, while preserving strict verification or explicit reconciliation for content-bearing chunks.
- **Make all canonical rows authoritative:** Resolve every sidecar conflict by retaining canonical rows and archiving the legacy database, accepting the possibility that divergent legacy chunks are discarded.
- **Keep strict conflicts, improve recovery:** Continue blocking on every non-file conflict but add an explicit Doctor flow that explains, backs up, and resolves the sidecar with user confirmation.

## Reproduction Assessment

Yes at source level: seed canonical and legacy Memory Core databases with an equal `meta` identity but different values, then run the startup migration and observe the blocking conflict warning. Two independent v2026.7.1 installations also reported that exact gateway failure, although this review did not execute the fixture against current main.

## Solution Assessment

No, a blanket canonical-wins rule for every table is not yet the safest fix. The narrow maintainable solution is table-specific because metadata and derived cache values differ materially from content-bearing chunks.

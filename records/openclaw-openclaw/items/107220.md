## Summary

Keep this issue open: current main still treats divergent legacy `meta` and `chunks` rows as blocking conflicts, while two released-version reports show the resulting startup crash-loop. The narrower derived-cache case does not settle the authority policy for metadata or potentially unique chunks.

## What This Changes

Make legacy Memory Core sidecar conflicts converge safely instead of permanently blocking gateway startup after an upgrade.

## Best Possible Solution

Adopt a table-specific convergence policy: canonical keys should win for derived cache data, metadata should use an explicitly defined canonical authority rule, and divergent chunks should merge or remain fail-closed only when real content loss is possible; `doctor --fix` must archive verified-safe residue and offer a visible Fix/recovery path without manual SQLite inspection or file moves.

Options:

- **Use table-specific authority (recommended):** Keep canonical derived-cache rows, define canonical metadata ownership, and preserve or explicitly reconcile divergent chunks before archiving the sidecar.
- **Always keep canonical SQLite:** Treat every conflicting legacy table as superseded, archive the sidecar, and accept that divergent legacy chunk values may be discarded.
- **Keep fail-closed conflicts:** Preserve strict conflict blocking but make `doctor --fix` provide a safe inspected backup-and-resolution workflow that actually converges.

## Reproduction Assessment

Yes at source level: seed canonical and legacy sidecars with the same `meta` or chunk identity but differing values, then run the startup migration; the exact-match assertion deterministically reaches the blocking warning path. Two independent `v2026.7.1` installations also reported the resulting crash-loop.

## Solution Assessment

No, not as a blanket canonical-wins change across every table. The narrow maintainable fix is a table-specific authority and convergence policy with regression coverage for metadata, derived cache rows, unique chunks, repeated Doctor runs, and gateway readiness.

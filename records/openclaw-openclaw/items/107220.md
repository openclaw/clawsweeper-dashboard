- `impact:crash-loop`: The blocking migration warning exits gateway startup and service managers repeatedly restart the failed process.
- `impact:ux-release-blocker`: Affected upgrade users have no working in-product recovery path because Doctor repeats the conflict and recovery currently requires inspecting SQLite state and manually moving sidecar files.

## Summary

Keep this issue open: current main still converts divergent legacy `meta`, `chunks`, and `embedding_cache` rows into blocking migration warnings while recovering only `files` conflicts. Two independent 2026.7.1 upgrade reports confirm the resulting gateway outage, and the narrower embedding-cache PR closed without merging, so no current or shipped fix owns the remaining behavior.

## What This Changes

Make legacy Memory Core sidecar conflicts converge without crash-looping the gateway when canonical per-agent SQLite state is already authoritative.

## Best Possible Solution

Treat the per-agent database as runtime-authoritative once canonical identities exist, preserve the divergent legacy sidecar in a timestamped quarantine/retry archive, continue startup with a clear notice, and add separate regression cases for metadata, chunks, derived cache rows, mixed non-conflicting imports, and repeat Doctor convergence.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When a legacy Memory Core sidecar has the same row identities as the per-agent database but different values, which state should control startup and how should potentially divergent chunks be preserved?

Rationale: Source proves the outage, but changing fail-closed behavior requires an explicit authority and data-preservation policy: metadata/cache drift is derived, while blanket treatment of chunk conflicts could conceal meaningful divergence.

Likely owner: steipete

Owner reason: The broad migration convergence commit most directly frames the unresolved distinction between safely superseded residue and genuinely divergent state.

Owner confidence: high

Options:

- **Canonical DB plus quarantine (recommended):** Use canonical rows for runtime, preserve the entire conflicting sidecar under a recoverable timestamped archive, emit a notice, and allow startup to continue.
- **Split by table semantics:** Auto-resolve only derived metadata and cache conflicts while keeping divergent chunks blocking until a dedicated reconciliation rule exists.
- **Keep fail-closed with real repair:** Retain blocking conflicts but make `openclaw doctor --fix` present and execute a safe canonical-or-legacy recovery choice instead of repeating an unrepairable warning.

## Reproduction Assessment

Yes at source level: seed canonical and legacy rows with the same identity but different `meta`, `chunks`, or cache values, then run the startup migration and observe the non-`files` conflict become a blocking warning. Two independent v2026.7.1 installations also report the same `meta` crash-loop, although this review did not execute the stateful reproduction.

## Solution Assessment

No, extending the existing `files` exception indiscriminately is not yet the best fix because it lacks an explicit preservation rule for divergent chunks. The safer direction is canonical runtime authority plus recoverable sidecar quarantine, with table-specific regression coverage and convergent Doctor behavior.

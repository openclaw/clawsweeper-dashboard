## Summary

Keep this issue open. Current main still treats divergent legacy `meta`, `chunks`, and `embedding_cache` rows as blocking conflicts, while only `files` conflicts converge automatically; the open cache-specific fix does not cover the reported `meta` and `chunks` cases.

## What This Changes

Make legacy Memory Core sidecar conflicts converge without blocking Gateway startup when the canonical per-agent index is authoritative.

## Best Possible Solution

Adopt a table-specific migration policy: keep compatible canonical cache rows and canonical derived metadata, but archive conflicting chunk state only after proving it is fully represented or safely superseded; otherwise provide an explicit Doctor recovery flow that does not require manual SQLite or file operations.

## Maintainer Decision

Required: true

Kind: product_direction

Question: When legacy Memory Core `meta` or `chunks` rows conflict with the canonical per-agent index, what proof is sufficient to discard or archive the legacy copy without risking unique memory data?

Rationale: The outage is clearly reproducible, but choosing canonical-wins for every table changes the persisted-data preservation contract; source inspection alone cannot determine whether divergent chunk content may be discarded.

Likely owner: vincentkoc

Owner reason: They merged and co-authored the original persisted-state migration and have the strongest visible ownership signal for the Memory Core upgrade contract.

Owner confidence: high

Options:

- **Use table-specific convergence (recommended):** Treat compatible cache and derived metadata as canonical-wins, while requiring positive supersession or merge proof before archiving divergent chunks.
- **Keep every conflict fail-closed:** Preserve the current data-safety policy but add a guided Doctor repair that shows the conflict and lets the operator archive or reconcile it without manual file work.
- **Make canonical rows authoritative:** Archive the entire legacy sidecar whenever the canonical index is non-empty, accepting that unique divergent legacy chunks may be discarded.

## Reproduction Assessment

Yes, at source level with high confidence: seed the canonical and legacy databases with the same row identity but divergent values, then run startup migration. Two independent 2026.7.1 installations also reproduced the resulting crash loop.

## Solution Assessment

No, the suggested blanket extension of the `files` branch is not yet the safest fix because conflicting chunks may contain unique state. A table-specific canonical-authority rule plus a non-technical Doctor recovery path is safer.

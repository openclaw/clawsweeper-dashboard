## Summary

Keep open: the generic budget-deferral retry bug has landed, but current main still does not prove or implement the remaining Feishu transport-readiness recovery behavior after gateway restart.

## What This Changes

Issue reports pending Feishu outbound deliveries failing after gateway restart because delivery recovery can run before channel transport readiness and can exhaust retry accounting across restarts.

## Best Possible Solution

Keep the issue open and resolve it with a channel-aware restart recovery contract that preserves the landed budget fix, waits for or reacts to Feishu transport readiness, and proves a live Feishu gateway-restart recovery without resetting legitimate failure counts by default.

## Maintainer Decision

Required: true

Question: Which policy should own Feishu delivery recovery after gateway restart: channel-owned reconnect/readiness drain, global startup recovery gating, or retry-count reset across restart boundaries?

Rationale: Current source and the merged partial fix show the retry-accounting bug is solved, but choosing how recovery coordinates with channel transport readiness changes core/plugin ownership and retry semantics.

Likely owner: @vincentkoc

Owner reason: Recent gateway/release stability work and channel recovery history make this the best available routing owner for the policy choice.

Owner confidence: medium

Options:

- **Use channel-owned readiness drain (recommended):** Add a Feishu transport-ready or reconnect-triggered drain that replays eligible pending deliveries once the Feishu WebSocket or webhook listener reports ready, while keeping generic startup recovery best-effort.
- **Gate generic startup recovery:** Make outbound startup recovery wait for channel readiness before draining, accepting the added coupling and potential startup stalls across channels.
- **Reset retry counts on restart:** Treat a restart as a fresh delivery session for retry accounting, accepting that this could hide real permanent delivery failures unless narrowly constrained.

## Reproduction Assessment

Unclear for a live current-main Feishu run: the reporter supplied logs and a local patch, and source inspection shows immediate startup recovery plus no Feishu reconnect drain, but I did not establish the exact `0 recovered, N failed` live path on current main.

## Solution Assessment

No: the already-merged budget-deferral fix is correct for one sub-bug, but a fixed startup sleep or unconditional retry reset is not the best long-term solution without a maintainer-approved readiness or reconnect-drain policy.

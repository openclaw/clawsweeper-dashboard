## Summary

Keep this PR open: the follow-up correctly clears the closed retry handle, but the remaining teardown is still fire-and-forget and starts after the replacement provider has already been created. The central worker-overlap problem therefore remains unresolved, and the asserted RPi result still lacks inspectable real-behavior evidence.

## What This Changes

The PR starts closing the prior Memory Core embedding provider when a provider is replaced or provider initialization is reset for retry, aiming to prevent local embedding workers from lingering.

## System Context

Memory Core initializes an embedding provider for memory indexing and search, including local providers that can own worker processes. Provider replacement and retry paths feed directly into later embedding queries, so their shutdown ordering affects worker availability and resource cleanup.

## Architecture Diagram

flowchart LR
  A[Memory search or indexing request] --> B[Provider initialization]
  B --> C[Local embedding worker]
  C --> D[Provider replacement or retry]
  D --> E[Shutdown coordination]
  E --> F[New provider and worker]
  F --> G[Embedding query]

## Best Possible Solution

Move provider teardown to the initialization transition boundary, detach the old provider, and make replacement or retry wait on one tracked close promise before creating or activating another local provider; add a controlled asynchronous-close regression test and redacted live worker-lifecycle proof.

## Label Justifications

- `P2`: The missing WhatsApp approval confirmation is a normal-priority channel pairing gap with limited blast radius and a clear workaround of sending another message after approval.
- `impact:message-loss`: The same-channel approval confirmation is not delivered to the approved WhatsApp sender.
- `impact:ux-friction`: The approved sender has to guess when approval completed and retry manually, which adds avoidable pairing-flow confusion.

## Summary

Keep open: current main and the latest release still lack a WhatsApp pairing approval notifier, and the two linked implementation PRs are closed unmerged, so no active canonical fix owns the remaining work.

## What This Changes

Request that WhatsApp pairing approval send a same-channel confirmation to the approved sender, with optional follow-ups for replaying the blocked message or making notification configurable/defaulted.

## Best Possible Solution

Wire WhatsApp into the existing pairing approval `--notify` seam using the channel-owned outbound send path, add focused coverage, and leave default notification or blocked-message replay for a separate product decision.

Yes, at source level. Current main documents and exposes `openclaw pairing approve --notify`, but the shared notifier returns when the adapter lacks `notifyApproval`, and the WhatsApp adapter lacks that hook.

## Solution Assessment

Yes for the narrow repair. The maintainable fix is a WhatsApp-owned notifier on the existing pairing notification seam; default notification and original-message replay should remain separate choices unless maintainers explicitly choose them.

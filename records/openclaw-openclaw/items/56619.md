## Label Justifications

- `P2`: The issue is a bounded WhatsApp pairing UX and message-delivery gap with limited blast radius, not an emergency or core runtime outage.
- `impact:message-loss`: The approved sender does not receive the same-channel confirmation message that the pairing notification flow is intended to send.
- `impact:ux-friction`: The sender must guess when approval has happened or rely on an out-of-band update before trying again.

## Summary

Keep open: current main and v2026.6.11 still expose the pairing approval `--notify` path without a WhatsApp approval notifier, the direct fix PRs were closed unmerged, and the merged pairing-request hook is adjacent rather than a sender-after-approval notification.

## What This Changes

Request a same-channel WhatsApp notification to the approved sender after pairing approval, either through the existing `--notify` flow or a default/configured behavior.

## Best Possible Solution

Approve a narrow WhatsApp implementation for the existing `openclaw pairing approve ... --notify` path, using the gateway-backed outbound delivery seam, and keep default notification or original-message replay as separate product decisions.

## Label Justifications

- `P2`: The issue is a normal-priority WhatsApp pairing UX and delivery gap with limited blast radius.
- `impact:message-loss`: The approved sender does not receive the same-channel approval confirmation promised by the pairing notification flow.
- `impact:ux-friction`: The sender must guess when approval happened and retry manually, creating avoidable pairing confusion without fully blocking progress.

## Summary

Keep open: current main and the latest release still document and expose pairing approval notification, but the WhatsApp pairing adapter has no `notifyApproval` implementation, so `openclaw pairing approve whatsapp <CODE> --notify` silently has nothing to deliver. The two exact fix PRs are closed unmerged, and the open related hook PR is adjacent rather than a sender-after-approval fix.

## What This Changes

The issue asks OpenClaw to notify a WhatsApp sender after their DM pairing request is approved.

## Best Possible Solution

Add a WhatsApp-owned `notifyApproval` implementation on the existing pairing notification seam, with focused tests, and leave default-on notification or original-message replay for a separate product decision.

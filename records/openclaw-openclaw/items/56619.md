## Label Justifications

- `P2`: The missing WhatsApp approval notification is a normal-priority channel pairing delivery gap with limited blast radius.
- `impact:message-loss`: The approved sender does not receive the same-channel confirmation message promised by the pairing notification flow.
- `impact:ux-friction`: The sender can proceed only by guessing and sending another WhatsApp message after approval.

## Summary

Keep open: current main and v2026.6.11 still expose the shared `--notify` approval path, but WhatsApp has no pairing approval notifier, and both linked implementation PRs are now closed unmerged.

## What This Changes

The issue asks for WhatsApp senders approved through DM pairing to receive an approval confirmation instead of having to guess when to message again.

## Best Possible Solution

Wire WhatsApp into the existing `openclaw pairing approve --notify` path using the WhatsApp-owned outbound/gateway send surface, without adding a new config default or replaying blocked messages in the same fix.

## Repair Work Prompt

Fix the WhatsApp DM pairing approval notification gap for https://github.com/openclaw/openclaw/issues/56619. Current main already has `openclaw pairing approve --notify` and `notifyPairingApproved`; the bug is that `extensions/whatsapp/src/channel.ts` declares a pairing adapter without `notifyApproval`, so the shared path returns without sending. Add a WhatsApp-owned notifier that sends the shared pairing-approved message through the existing WhatsApp outbound/gateway send path for the approved sender and preserves account scoping. Keep the scope narrow: do not add a new config option, do not make notification default-on, do not replay the original blocked message, and do not widen plugin SDK surface unless unavoidable and justified. Add focused regression coverage for WhatsApp exposing/calling the notifier and for the CLI/adapter path as needed. Include live or gateway-level WhatsApp proof in the PR body if feasible; otherwise state the exact proof gap.

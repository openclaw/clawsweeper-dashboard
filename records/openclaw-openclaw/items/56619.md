## Summary

Keep open: current main still has no WhatsApp approval-notification delivery, the two direct fix PRs are closed unmerged, and the merged pairing-request hook is adjacent but does not notify the sender after approval.

## What This Changes

The issue requests a WhatsApp confirmation message to the sender after an owner approves their DM pairing code.

## Best Possible Solution

Add a WhatsApp-owned `notifyApproval` implementation on the existing pairing adapter that sends the shared approval message through the existing outbound send path; leave default-on notification and original-message replay for separate product decisions.

Yes, at source level: current main exposes `openclaw pairing approve --notify`, but the shared notifier returns when the channel adapter lacks `notifyApproval`, and the WhatsApp adapter lacks that hook. I did not run a live WhatsApp session in this read-only review.

## Solution Assessment

Yes for the narrow repair: wiring WhatsApp into the existing opt-in `--notify` seam is the smallest maintainable fix. Making notification default, configurable, or replaying the blocked message should stay out of this fix unless maintainers explicitly choose that broader behavior.

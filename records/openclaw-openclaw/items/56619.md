## Label Justifications

- `P2`: This is a normal-priority WhatsApp pairing UX bug with a narrow channel blast radius and no evidence of data loss or runtime unavailability.
- `impact:message-loss`: The requested approval confirmation is not delivered to the WhatsApp sender after pairing approval.
- `impact:ux-friction`: Approved WhatsApp senders have to guess when approval happened and retry manually before they can interact.

## Summary

Keep open: current main and v2026.6.11 expose `openclaw pairing approve ... --notify`, but WhatsApp still registers only an ID label and allowlist normalizer for pairing, so the approval notification path returns without sending anything. The two exact fix PRs are closed unmerged, and the currently open related hook PR covers pairing-request notification rather than post-approval sender notification.

## What This Changes

The issue asks for WhatsApp senders approved through DM pairing to receive an automatic approval notification instead of having to retry blindly.

## Best Possible Solution

Wire WhatsApp into the existing `notifyApproval` pairing adapter seam and existing outbound send path for `openclaw pairing approve whatsapp <CODE> --notify`, without adding new config/default behavior or replaying the original blocked message unless maintainers choose that separately.

## Summary

Keep open: current main and v2026.6.11 still expose the pairing approval notification path but WhatsApp has no approval notifier, and both linked fix PRs were closed unmerged. The open pairing-request hook PR is adjacent because it observes new requests before approval rather than notifying the requester after approval.

## What This Changes

The issue requests a WhatsApp confirmation message to the approved sender after an owner approves a DM pairing request.

## Best Possible Solution

Implement WhatsApp delivery for the existing pairing approval notification path, keep default-on/configurable/replay behavior out of scope unless maintainers choose it separately, and prove the requester receives the message.

## Reproduction Assessment

Yes, at source level: `openclaw pairing approve --notify` reaches `notifyPairingApproved`, that dispatcher returns when `notifyApproval` is absent, and the WhatsApp pairing adapter currently has no notifier. I did not run a live WhatsApp reproduction in this read-only review.

## Solution Assessment

Yes for the narrow repair: use the existing pairing notification seam and add WhatsApp delivery for the documented `--notify` path. Default-on notification, custom messages, and original-message replay should stay separate product decisions.

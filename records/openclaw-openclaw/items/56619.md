## Label Justifications

- `P2`: The missing WhatsApp approval confirmation is a normal-priority channel pairing gap with limited blast radius.
- `impact:message-loss`: The issue is about an approved WhatsApp sender not receiving the same-channel confirmation message advertised by the pairing notification flow.
- `impact:ux-friction`: The approved sender can only proceed by guessing when to message again, which creates avoidable user-facing confusion without fully blocking the workflow.

## Summary

Keep open: current main still has the WhatsApp sender approval-notification gap. The direct WhatsApp fix PRs were closed unmerged, and the merged `channel_pairing_requested` hook only observes newly created pairing requests; it does not notify the requester after approval.

## What This Changes

The issue requests a WhatsApp sender-facing confirmation after an operator approves a pending pairing code.

## Best Possible Solution

Implement a WhatsApp-owned `notifyApproval` on the existing pairing adapter so `openclaw pairing approve whatsapp <code> --notify` sends the shared approval message through the existing WhatsApp outbound path; keep default-on notification and original-message replay as separate product decisions.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, at source level. Current main exposes `openclaw pairing approve --notify`, but `notifyPairingApproved` returns when the adapter lacks `notifyApproval`, and the WhatsApp adapter currently lacks that hook.

## Solution Assessment

Yes for the narrow repair. The maintainable fix is to wire WhatsApp into the existing `--notify` notifier seam; adding config, default-on behavior, or original-message replay would be a broader direction than this repair needs.

## Label Justifications

- `P2`: The issue is a bounded WhatsApp pairing improvement with clear source evidence, not a core runtime outage or security emergency.
- `impact:message-loss`: The initial blocked WhatsApp DM is not replayed, and the requester receives no approval message to resume the conversation.
- `impact:ux-friction`: A sender must guess when approval has happened and manually retry, which adds avoidable confusion to the WhatsApp pairing flow.

## Summary

Keep open: current main and v2026.6.11 still lack WhatsApp approval notification delivery. The generic pairing `--notify` path exists, but WhatsApp declares only pairing normalization, so the notification path returns without sending; the exact fix PRs were closed unmerged and the open hook PR only partially overlaps.

## What This Changes

Request to notify a WhatsApp sender after the owner approves their DM pairing code, with possible default/configurable notification and optional replay of the blocked message.

## Best Possible Solution

Add WhatsApp support for the existing `openclaw pairing approve whatsapp <code> --notify` path through the plugin-owned outbound delivery surface, with focused tests and real WhatsApp proof; leave default notification, config knobs, and replay behavior for a separate maintainer decision.

## Reproduction Assessment

Yes, at source level: current main has the `--notify` approval path, but `notifyPairingApproved` exits when the adapter lacks `notifyApproval`, and the WhatsApp adapter lacks that hook. I did not run a live WhatsApp reproduction in this read-only review.

## Solution Assessment

Yes for the narrow supported path: implementing WhatsApp delivery for the existing `--notify` flag is the smallest maintainable fix. Default notification, configurable messages, or replaying the original blocked message should not be bundled without explicit maintainer direction.

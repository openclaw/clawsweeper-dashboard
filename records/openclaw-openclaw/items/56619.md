## Label Justifications

- `P2`: The issue is a normal-priority WhatsApp pairing UX and delivery gap with a bounded channel-specific blast radius.
- `impact:message-loss`: The approved WhatsApp sender does not receive the same-channel approval confirmation promised by the pairing notification flow.

## Summary

Keep open: current main and the latest release still expose the pairing `--notify` flow, but WhatsApp has no `notifyApproval` adapter, and the prior WhatsApp fix PRs closed unmerged without landing the behavior.

## What This Changes

The issue asks for WhatsApp senders approved through DM pairing to receive a same-channel confirmation instead of guessing when to retry.

## Best Possible Solution

Add a WhatsApp-owned `notifyApproval` implementation for the existing `openclaw pairing approve ... --notify` flow, using the shared approval message and existing WhatsApp outbound delivery; leave default notification and original-message replay as separate product choices.

## Maintainer Decision

## Reproduction Assessment

Yes, at source level. Current main documents and exposes `pairing approve --notify`, but `notifyPairingApproved` no-ops when a channel lacks `notifyApproval`, and WhatsApp lacks that hook.

## Solution Assessment

Yes for the narrow repair. The maintainable fix is to wire WhatsApp into the existing pairing notification seam, not add a new config default or replay blocked messages in the same change.

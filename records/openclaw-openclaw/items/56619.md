## Label Justifications

- `P2`: The missing WhatsApp approval notification is a bounded channel pairing bug with limited blast radius but real user confusion.
- `impact:message-loss`: The documented same-channel approval confirmation is not delivered to approved WhatsApp senders.
- `impact:ux-friction`: Approved WhatsApp senders currently have to guess when to retry because the approval state is not surfaced back in-channel.

## Summary

Keep open: current main and v2026.6.11 still expose `pairing approve --notify`, but the WhatsApp channel pairing adapter has no approval notifier, so the documented same-channel confirmation is a no-op for WhatsApp. The two linked fix PRs are closed unmerged, and the newer open pairing-request hook PR is adjacent rather than an active fix for sender notification after approval.

## What This Changes

The issue requests notifying a WhatsApp sender after their DM pairing request is approved so they do not have to guess when to retry.

## Best Possible Solution

Wire WhatsApp into the existing same-channel `pairing approve --notify` notification path, preferably through gateway-backed outbound delivery, without adding a new default, config option, or blocked-message replay unless maintainers separately choose that scope.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, at source level. Current main exposes `openclaw pairing approve --notify`, but `notifyPairingApproved` returns when the adapter lacks `notifyApproval`, and the WhatsApp adapter currently lacks that hook.

## Solution Assessment

Yes for the narrow repair: using the existing `--notify` approval path is the maintainable fix. Making notification the default, adding config, or replaying the original blocked message would be separate product scope.

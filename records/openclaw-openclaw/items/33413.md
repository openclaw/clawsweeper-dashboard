## Summary

Keep open: current main now sends generic Slack assistant-thread loading messages at reply start, but tool-start callbacks still update reactions and draft/progress previews rather than assistant-thread status text. The merged loading-message work partially reduces the static-status UX gap, but it does not implement the requested per-tool labels.

## What This Changes

Request Slack assistant thread status to switch from generic typing/loading text to tool-specific progress labels during agent runs.

## Best Possible Solution

Keep this issue as the canonical Slack assistant-thread per-tool status request until maintainers choose the Slack-visible status contract, then implement Slack-owned coarse labels from the shared progress display model with deduped writes, focused tests, docs, and live Slack proof.

## Reproduction Assessment

Yes, at source level. Current main starts Slack assistant thread status with generic typing/loading text and clears it at the end, while `onToolStart` only updates reactions and draft/progress previews.

## Solution Assessment

Unclear until maintainers choose the product contract. The Slack plugin is the right owner boundary, but a one-off tool-name map should not land before the safe visibility and configurable status/loading-message decisions are reconciled.

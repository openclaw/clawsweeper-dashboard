## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P1] Neutralize closing references before updating PR bodies:** `scripts/generate-microsoft-tracker.mjs:426`
  - body: When `--update-pr-body` is used, generated rows include raw titles such as `(fixes #93288)` and `(Fixes #84600)`. GitHub can interpret those in a PR body as issue-closing references for unrelated tracker rows, so the generator needs to escape or rewrite closing keywords before this mutation path lands.
  - confidence: 0.93
- **[P1] Preserve live priority labels before keyword fallback:** `scripts/generate-microsoft-tracker.mjs:151-153`
  - body: `priorityFor` derives P labels from title/label text and treats labels like `clawsweeper:needs-security-review` as P0 signals, so live-P1/P3 rows can be promoted to P0 in the tracker. Maintainer queue order should honor an existing `P0`-`P3` label first, then fall back to heuristics only when no live priority exists.
  - confidence: 0.91
- **[P2] Tokenize category matches before assigning tracker sections:** `scripts/generate-microsoft-tracker.mjs:140-145`
  - body: The title classifier uses raw `title.includes(term)`, which still admits false positives such as `WindowServer` under Windows and generic non-Microsoft rows that happen to contain broad terms. Tokenized/exact matching plus explicit exclusions is needed before this can be trusted as a maintainer queue.
  - confidence: 0.88
- **[P2] Add a check mode for generated tracker drift:** `scripts/generate-microsoft-tracker.mjs:422-423`
  - body: The script always writes the output file and there is no package-level check path, so CI cannot tell whether `MICROSOFT_TRACKER.md` matches the generator. Add a non-writing check mode and wire it into an appropriate verification path before treating the tracker as a maintained generated artifact.
  - confidence: 0.84
- **[P3] Remove the release-owned changelog entry:** `CHANGELOG.md:8`
  - body: OpenClaw release generation owns `CHANGELOG.md`, and normal PRs should carry release-note context in the PR body or commit message instead. This manual entry should be dropped from the branch.
  - confidence: 0.95

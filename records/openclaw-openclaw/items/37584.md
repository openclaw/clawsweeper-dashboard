## Best Possible Solution

Define one maintainer-approved agent-scoped web/tool credential contract covering precedence, SecretRef/redaction, plugin-owned `webSearch`, validation, reload, docs, and two-agent regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a first-class agent-scoped web/tool credential contract, and should it live under `agents.list[].tools.web` or a generic per-agent plugin/tool configuration surface?

Rationale: The config location and precedence define a credential isolation boundary across SecretRefs, plugin-owned `webSearch`, provider auto-detection, docs, and upgrade behavior, so automation cannot safely choose the permanent contract.

Likely owner: steipete

Owner reason: The decision spans the web-tools config surface and strict configuration policy introduced in the relevant history, with SecretRef/security input from adjacent owners.

Owner confidence: medium

Options:

- **Design a generic agent-scoped tool/plugin config contract (recommended):** Add a shared contract for agent-scoped provider/tool/plugin settings with explicit precedence, SecretRef handling, validation, reload, docs, and upgrade tests.
- **Add only `agents.list[].tools.web`:** Solve the immediate web-search credential use case faster, but accept a narrower surface that may later conflict with plugin-owned web provider configuration.
- **Keep web credentials global:** Leave web-search provider credentials as global/plugin-scoped settings and document separate gateways or provider-specific workarounds for billing isolation.

## Reproduction Assessment

Yes, at source level: current main has a strict per-agent tools schema with no `web` field, while web-search runtime and SecretRef targets still read global or plugin-owned webSearch config. I did not run a write-path config repro because this review is read-only.

## Solution Assessment

Unclear until maintainers choose the contract. `agents.list[].tools.web` is plausible, but a single agent-scoped credential/config design is safer than adding a second source that competes with plugin-owned webSearch settings.

## Summary

Keep open: current main and v2026.6.11 still do not provide an accepted per-agent web/tool credential surface, and the remaining work is a product and security contract rather than a narrow bug fix.

## What This Changes

The issue requests per-agent overrides for web/tool settings such as `tools.web.search.apiKey`, provider, and timeouts under `agents.list[].tools.web`.

## Best Possible Solution

Define one maintainer-approved agent-scoped web/tool credential contract that covers global tool settings, plugin-owned webSearch config, SecretRefs, redaction, docs, and two-agent regression coverage.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a first-class agent-scoped web/tool credential contract here, and should the durable surface be `agents.list[].tools.web`, a generic per-agent plugin/tool config contract, or both?

Rationale: The missing capability is source-proven, but automation cannot safely choose credential precedence, SecretRef scope, redaction, plugin-owned config interaction, and upgrade semantics without maintainer intent.

Likely owner: steipete

Owner confidence: medium

Options:

- **Design a generic agent-scoped web/tool contract (recommended):** Define one precedence and SecretRef contract covering `tools.web`, plugin-owned `webSearch`, docs, reload behavior, and regression tests before implementation.
- **Add only `agents.list[].tools.web`:** This would address the narrow issue faster but risks creating a second credential source that drifts from plugin-owned web-search config.
- **Keep web credentials global:** This preserves a lean config surface but leaves multi-agent billing, rate-limit, and credential isolation unresolved.

## Reproduction Assessment

Yes. Source inspection shows strict per-agent tool config has no `web` field, while web-search credential resolution still reads global `tools.web.search` or plugin-owned `webSearch` config without an agent-scoped merge.

## Solution Assessment

Unclear. `agents.list[].tools.web` is plausible, but the best fix needs a maintainer decision on precedence, SecretRef/redaction, validation, plugin-owned config, and upgrade behavior.

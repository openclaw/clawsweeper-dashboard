## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.93

Full review comments:

- **[P1] Preserve scoped-token auth for lifecycle requests:** `src/gateway/mcp-http.request.ts:73-76`
  - body: Current main supports authenticated GET/SSE startup and DELETE teardown on `/mcp`, but this implementation rejects every non-POST request before token resolution. A current-base scoped-token fix needs to authenticate those lifecycle requests with the same bearer contract or Streamable HTTP clients can list/call tools and then fail opening or closing the transport.
  - confidence: 0.93
- **[P1] Bind the full current loopback context:** `src/gateway/mcp-http.loopback-runtime.ts:7-12`
  - body: The token scope records only `sessionKey`, `accountId`, `messageProvider`, and `senderIsOwner`, while current main also carries session id, channel/thread/message ids, inbound audio, inbound event kind, delivery mode, and explicit-target policy into loopback tool resolution. Rebase the fix so every server-owned context field is authoritative on the token instead of dropping context or leaving a parallel header-controlled path.
  - confidence: 0.92
- **[P2] Revoke the token even when backend cleanup throws:** `src/agents/cli-runner.ts:124-127`
  - body: `runPreparedCliAgent` awaits `preparedBackend.cleanup` before unregistering the scoped token, so a cleanup exception skips revocation and leaves a bearer registered after the run. Put token revocation in its own `finally` so teardown failures cannot preserve authorization state.
  - confidence: 0.9
- **[P2] Revoke issued tokens on all prepare failures:** `src/agents/cli-runner/prepare.ts:173-178`
  - body: The token is registered before later preparation work, but only `prepareCliBundleMcpConfig` failures unregister it. If docs-path or skill/system-prompt preparation throws afterward, the scoped bearer remains in the registry without a returned cleanup hook.
  - confidence: 0.88

  - body: `McpLoopbackScope` only carries the April tuple, but current main now resolves session id, channel/thread/message ids, inbound audio, event kind, delivery mode, and explicit-target policy from the same request-header surface.   - confidence: 0.93
- **[P1] Guard runtime clearing to the closing server:** `src/gateway/mcp-http.ts:115`
  - body: `clearActiveMcpLoopbackRuntime()` clears the active runtime and registered token map unconditionally. If an old server finishes closing after a new loopback server has started, this can wipe the new server's tokens and make valid fresh backends receive 401s.
  - confidence: 0.91
- **[P2] Revoke tokens even when backend cleanup fails:** `src/agents/cli-runner.ts:123-125`
  - body: The new revocation happens after `await context.preparedBackend.cleanup?.()`, so any cleanup exception skips `unregisterMcpLoopbackToken` and leaves the bearer registered past run teardown.
  - confidence: 0.9
- **[P2] Revoke issued tokens on all prepare failures:** `src/agents/cli-runner/prepare.ts:173-177`
  - body: The catch only covers `prepareCliBundleMcpConfig`. Later preparation work can still throw before the returned cleanup handle exists, leaving the newly registered scoped token live in the process map.
  - confidence: 0.88
- **[P2] Remove the unrelated plugin-loader fallback:** `src/plugins/public-surface-loader.ts:114-118`
  - body: This security PR also changes public-surface module loading so some `MODULE_NOT_FOUND` failures fall back to Jiti. That changes plugin loader behavior without PR rationale or focused contract tests, and it should not ride along with the MCP loopback auth fix.

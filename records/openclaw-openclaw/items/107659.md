## Summary

Keep open: the latest stable release has a well-supported outage path, and current evidence does not show that main prevents ACPX dependency over-expansion or resumes official-plugin convergence when the updater dies between core replacement and plugin synchronization. The broader drift issue remains open, while this report contributes distinct OOM, incomplete-generation, and failed self-recovery evidence.

## What This Changes

Prevent ACPX managed updates from expanding incompatible platform binaries and make interrupted core/plugin updates recover to a runnable, version-aligned state.

## Best Possible Solution

Publish or resolve ACPX dependencies so managed installs materialize only host-compatible artifacts, then persist an update transaction that startup can resume or roll back before loading official plugins, with an in-product Doctor/Fix recovery action instead of terminal-only repair.

Rationale: Both approaches can restore a runnable core/plugin combination, but they establish different network, pin-preservation, package-manager rollback, and startup-readiness contracts that require maintainer intent.

Options:

- **Resume Interrupted Convergence (recommended):** Persist the intended channel and official-plugin targets before core replacement, then resume only that interrupted transaction before loading plugins.
- **Rollback Core On Failure:** Treat core and official plugins as one update unit and restore the previous core when convergence cannot finish.
- **Require Explicit Repair:** Keep startup network-free but provide a visible in-product Fix action and refuse stale official plugins with actionable recovery state.

## Solution Assessment

Unclear as one patch: reducing ACPX platform payload is necessary, but durable recovery should use a persisted interrupted-update transaction rather than an unconditional startup update or broad fallback stack.

## Summary

Keep open for a maintainer product decision: the related full reattach-first implementation is closed unmerged, and the available evidence does not establish that current main now recovers accepted disconnected runs before starting a fallback.

## What This Changes

Request a reattach-first recovery path for accepted `openclaw agent` gateway runs after a non-transient CLI connection loss, with isolated embedded fallback only after recovery cannot determine the original outcome.

## Best Possible Solution

Confirm a recovery contract that keeps a confirmed accepted gateway run authoritative, retrieves its terminal result when possible, and uses the isolated fresh-session fallback only after a bounded unknown outcome; validate both interactive and `--deliver` flows with a real gateway disconnect harness.

Likely owner: steipete

Owner confidence: medium

Options:

- **Adopt reattach-first (recommended):** Make the accepted gateway run authoritative, wait and replay its terminal result, then use the existing isolated fallback only after recovery becomes unknown or expires.
- **Keep recook-first:** Retain immediate embedded fallback for all modes, accepting rare duplicate execution in exchange for predictable local streaming and prompt stdout behavior.
- **Split by delivery mode:** Use reattach-first for `--deliver` while retaining recook-first for interactive stdout until a stronger interactive recovery UX is designed.

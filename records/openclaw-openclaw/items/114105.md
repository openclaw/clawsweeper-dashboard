## Summary

Keep this issue open. The official Token Plan exact-model allowlist excludes `qwen3-coder-next`, while the reported current picker catalog still offers it; the merged follow-up only restored direct-reference transport constraints, not picker correctness. Likely related people: steipete (high confidence, curation and adjacent runtime repair).

## What This Changes

Correct the Qwen Token Plan picker catalog so it does not offer an unsupported Coding Plan model and so its curated entries follow the intended Token Plan selection policy.

## System Context

The Qwen plugin exposes a static Token Plan model catalog to OpenClaw’s model picker and applies provider-specific request constraints when a selected model is used. A picker entry becomes a provider/model reference that is sent to Alibaba’s dedicated Token Plan endpoint, where unsupported IDs fail at request time.

## Architecture Diagram

flowchart LR
  A[Token Plan subscription] --> B[Qwen provider setup]
  B --> C[Static Token Plan catalog]
  C --> D[Model picker]
  D --> E[Qwen request wrapper]
  E --> F[Alibaba Token Plan endpoint]
  F --> G[Successful run or model-not-found error]

## Best Possible Solution

Remove the unsupported `qwen3-coder-next` Token Plan picker row, then define the curated shortlist from Alibaba’s Token Plan-specific exact allowlist with current per-family representatives and explicit treatment of subscription-tier availability.

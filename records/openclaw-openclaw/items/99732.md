## Summary

Keep open: the latest-stable crash evidence maps to the active-memory embedded subagent temp-session path, and current main still delegates that lock lifecycle to `@openclaw/fs-safe` 0.4.1, whose sidecar-lock sync cleanup path still fire-and-forgets `FileHandle.close()`. The only matching fix PR was closed unmerged and targeted the older 0.3.0 dependency shape.

## What This Changes

The issue reports recurring gateway exits on Node 26 when active-memory subagent `session.jsonl.lock` FileHandles are garbage-collected without explicit closure.

## Best Possible Solution

Land a focused maintainer-owned fs-safe/session-lock lifecycle fix that explicitly closes sidecar lock FileHandles on synchronous cleanup, then prove it with a Node 26 forced-GC active-memory or gateway soak path without changing active-memory product behavior.

## Reproduction Assessment

No live high-confidence reproduction was run in this read-only review. The reporter's crash logs are strong and current source maps the path to active-memory embedded session locking, but the remaining proof should be a Node 26 forced-GC or soak repro against current main.

## Solution Assessment

No current implementation can be called solved: current main still has a dependency-backed sync cleanup path that fire-and-forgets `FileHandle.close()`, and the matching attempted PR was closed unmerged. A plugin-level uncaught-exception catch is not the best fix because the safer owner boundary is the lock lifecycle itself.

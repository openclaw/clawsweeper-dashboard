## Summary

Keep open: the latest-stable crash evidence maps to the active-memory temporary embedded-session lock path that still exists on current main. Current source has normal awaited release paths, but `@openclaw/fs-safe@0.3.0` still has a sync reset/exit cleanup path that fire-and-forgets `FileHandle.close()`, and no merged fix or live current-main proof shows this fresh Node 26 signature is resolved.

## What This Changes

Investigate and fix recurring gateway crashes from Node 26 GC-finalized FileHandles on active-memory temporary `session.jsonl.lock`, avoiding lost in-flight requests.

## Best Possible Solution

Instrument or reproduce the Node 26 active-memory temp-session lock path with forced GC and FileHandle ownership tracing, then fix the exact OpenClaw or fs-safe close lifecycle with regression proof on Node 24/25/26.

## Reproduction Assessment

No, we do not have a high-confidence live current-main reproduction. The report has repeated production crash logs and current source maps the descriptor path to active-memory `runEmbeddedAgent`, but the exact unclosed FileHandle owner is not isolated.

## Solution Assessment

Unclear. Explicitly closing the leaked handle is the right end state, but current normal embedded lock release already awaits close, so the best repair should first identify whether the leak is in active-memory abort/timeout handling, embedded-runner retained-lock cleanup, or fs-safe reset/exit behavior.

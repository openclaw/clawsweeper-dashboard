## Summary

Keep open: the latest-stable crash report maps to current active-memory temp-session locks, and current main still delegates the lock handle lifecycle to the pinned fs-safe sidecar-lock implementation with a synchronous cleanup path that fire-and-forgets `FileHandle.close()`. There is not enough current-main proof to close this as fixed or duplicate-only.

## What This Changes

The issue asks OpenClaw to stop recurring Node 26 gateway crashes caused by GC-closed FileHandles on active-memory `session.jsonl.lock` files.

## Best Possible Solution

Keep this open for maintainer-led Node 26/macOS active-memory temp-session reproduction or instrumentation, then fix the exact fs-safe/session-lock close path with forced-GC regression proof and a dependency bump or approved patch if upstream owns it.

## Reproduction Assessment

No high-confidence live current-main reproduction was established in this read-only review. The reported crash logs are strong and current source maps the path to active-memory's embedded-session lock, but the exact FileHandle owner still needs Node 26 instrumentation or a forced-GC repro.

## Solution Assessment

Unclear. Explicitly closing the leaked handle is the right end state, but the best fix should first identify whether the owner is active-memory timeout cleanup, embedded-runner lock retention, or fs-safe `releaseAllLocksSync` rather than adding a broad crash downgrade.

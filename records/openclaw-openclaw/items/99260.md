## Summary

Keep this open: current main and v2026.6.11 still have the source-reproducible mismatch where an allowlisted non-bundled ACPX plugin can load while `openKeyedStore` still requires bundled or trusted-official provenance.

## What This Changes

The issue asks OpenClaw to make official ACPX keyed-state trust diagnostics and repair match the `plugins.allow` loading path, without weakening the plugin trust boundary.

## Best Possible Solution

Preserve the keyed-store provenance boundary and add provenance-aware `plugins inspect`/doctor/install repair for official ACPX installs, including the Docker config-write failure mode.

## Reproduction Assessment

Yes by source inspection: an allowlisted non-bundled ACPX plugin without `trustedOfficialInstall` still reaches the `openKeyedStore` throw, and ACPX calls that API during service startup. I did not run the Docker bind-mount scenario in this read-only review.

## Solution Assessment

No, making `plugins.allow` grant keyed-store access is not the best fix because docs define it as plugin-id trust, not source provenance. The safer path is provenance-aware diagnostics and repair/install behavior for official ACPX while preserving the keyed-state gate.

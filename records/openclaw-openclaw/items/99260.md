## Summary

Keep this open: current main and the latest stable release still gate keyed plugin state on bundled or trusted-official install provenance, while ACPX requires `openKeyedStore` and `plugins.allow` can hide the untracked-provenance warning without satisfying that runtime trust gate.

## What This Changes

The issue asks for official ACPX installs with `plugins.allow` to spawn ACP sessions successfully, or for `plugins inspect`/doctor to diagnose missing trusted provenance instead of implying the allowlist is enough.

## Best Possible Solution

Keep `openKeyedStore` tied to bundled or trusted official provenance, then fix `plugins inspect`, doctor, or install-record recovery so official ACPX installs with missing trusted provenance are diagnosed and repairable without making `plugins.allow` grant state trust.

## Reproduction Assessment

Yes, source-level: an allowlisted non-bundled ACPX plugin without trusted install provenance still hits the `openKeyedStore` throw, and ACPX calls that API during runtime service startup. I did not run the Docker bind-mount reproduction in this read-only review.

## Solution Assessment

No, making `plugins.allow` grant keyed-state access is not the best fix because docs define it as plugin-id trust, not source provenance. The safer path is provenance-aware diagnostics and repair/install behavior for official ACPX while preserving the keyed-state trust gate.

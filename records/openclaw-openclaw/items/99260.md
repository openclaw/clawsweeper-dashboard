## Summary

Keep this open: current main and v2026.6.11 still gate plugin keyed state on bundled or trusted-official provenance, while the ACPX plugin requires keyed state during startup and the untracked-provenance diagnostic can be silenced by plugins.allow without satisfying that runtime gate.

## What This Changes

The issue reports that official ACPX can load with plugins.allow but ACP sessions fail because openKeyedStore still requires bundled or trusted-official install provenance.

## Best Possible Solution

Keep openKeyedStore limited to bundled or trusted official installs, and fix inspect/doctor/plugin-install behavior so configured official ACPX installs that lack trusted provenance are diagnosed and repairable without adding a config escape hatch.

## Reproduction Assessment

Yes by source inspection: an allowlisted non-bundled ACPX plugin without trustedOfficialInstall still hits the openKeyedStore throw, and ACPX calls that API during service startup. I did not run the Docker bind-mount reproduction in this read-only review.

## Solution Assessment

No, making plugins.allow grant keyed-store access is not the best fix because docs define it as plugin-id trust, not source provenance. The safer fix is provenance-aware diagnostics and repair/install behavior for official ACPX, while preserving the keyed-state trust gate.

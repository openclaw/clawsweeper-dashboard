- `impact:security`: The report sits on the trusted-plugin authorization boundary for host-managed keyed state.
- `impact:session-state`: The failing API is the persistent plugin state used for ACPX gateway instance and process/session lease state.

## Summary

Keep open: current main and v2026.6.11 still have separate plugin-load and trusted-keyed-state gates, so `plugins.allow` can let ACPX load while `openKeyedStore` still rejects it when official install provenance is absent or not recognized. The open trust PR helps one part of the official ClawHub npm-only path, but it does not settle the Docker single-file config/provenance failure or the misleading allowlist diagnostic.

## What This Changes

The issue asks for ACPX trusted keyed-state access, or at least actionable `doctor`/`plugins inspect` diagnostics, when `plugins.allow` loads ACPX but ACP `sessions_spawn` still fails at `openKeyedStore`.

## Best Possible Solution

Keep the fail-closed keyed-state gate, land a narrow official ClawHub provenance fix if approved, and add an ACPX/Docker-safe provenance or diagnostic path so `plugins inspect` and `doctor` name the missing trusted install record instead of implying `plugins.allow` is enough.

## Reproduction Assessment

Yes, at source level. A non-bundled ACPX plugin without `trustedOfficialInstall` reaches `api.runtime.state.openKeyedStore`, which current main and v2026.6.11 reject; I did not run the Docker bind-mount reproduction in this read-only review.

## Solution Assessment

No to using `plugins.allow` as the direct trust grant without maintainer approval. The safer path is provenance-preserving official install recognition plus precise `doctor`/`plugins inspect` diagnostics for the missing trusted install record.

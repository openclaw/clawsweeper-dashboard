## Label Justifications

- `P2`: This is a normal-priority reliability bug with clear source-level evidence and bounded blast radius in realtime transcription sessions.
- `impact:crash-loop`: The issue is about an unbounded reconnect loop that can keep websocket transcription sessions retrying and consuming resources indefinitely.

## Summary

Keep open: current main and v2026.6.11 both reset `reconnectAttempts` on every realtime transcription websocket `open`, so a flapping-after-ready session keeps restarting at the base delay and never reaches the configured cap.

## What This Changes

Realtime transcription websocket sessions should preserve reconnect backoff and give-up accounting across flapping post-ready reconnects instead of resetting on each raw socket open.

## Best Possible Solution

Fix the shared realtime transcription websocket helper so reconnect attempts reset only at the intended stable boundary, add a regression test for repeated ready-then-close flapping, and keep provider APIs/config unchanged.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes at source level: current main resets the reconnect counter on raw websocket open, and the cap/backoff logic reads that same counter after close. I did not execute the reporter's harness locally or against live providers.

## Solution Assessment

Yes, the shared helper is the right layer because all five bundled websocket transcription providers use it. The fix should change counter reset semantics there and add one focused flapping-after-ready regression test, not patch each provider separately.

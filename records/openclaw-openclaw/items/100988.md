## Label Justifications

- `P1`: The issue blocks a real delegated agent workflow by removing core coding tools from spawned embedded children under a supported CLI-harness parent path.
- `impact:session-state`: The problematic state is persisted on the child session as `inheritedToolAllow`, causing later child tool resolution to drift from the target agent's configured coding profile.
- `impact:security`: The behavior sits on the delegated tool authorization boundary where any fix must preserve non-escalation for restricted parents.

## Summary

Keep open: current main and v2026.6.11 still treat a CLI-harness runtime allowlist as an inherited child allow policy, so a `claude-cli` parent can strip an embedded subagent's coding tools. The report is source-reproducible, but the fix needs maintainer security-boundary direction because inherited tool policy is also the non-escalation guard for genuinely restricted parents.

## What This Changes

Prevent `sessions_spawn` from persisting a CLI-harness parent's bridge-visible tool allowlist as the child session's inherited allowlist when that would remove embedded child coding tools.

## Best Possible Solution

Add a maintainer-approved CLI/harness-aware inherited tool policy path that preserves non-escalation for explicit restrictions but does not treat a CLI bridge MCP surface as the parent's full native capability set.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: How should OpenClaw model CLI-harness native coding capabilities when computing inherited child tool allowlists for `sessions_spawn`?

Rationale: The current behavior breaks CLI-harness delegated coding work, but changing inherited allow semantics can either widen or narrow a parent-to-child authorization boundary, so automation should not choose the permanent policy alone.

Likely owner: steipete

Owner reason: steipete is the strongest current area owner signal for sessions_spawn, scoped capability profiles, and the security-sensitive agent runtime policy boundary.

Owner confidence: high

Options:

- **Harness-aware inheritance (recommended):** Distinguish CLI bridge-visible tools from native CLI capabilities and persist inherited allowlists only for actual configured restrictions or translated native-capability policy.
- **Explicit inheritance switch:** Add a documented subagent inheritance opt-out or mode only if maintainers want operators to choose this compatibility/security tradeoff per setup.
- **Keep strict bridge-surface inheritance:** Preserve current non-escalating semantics and document that CLI-backend parents are not suitable delegators for embedded coding children without a different runtime path.

## Reproduction Assessment

Yes, source-reproducible with high confidence: runtime bridge allowlists enter inheritance, are stored on the child session, and are consumed as a child allow policy. I did not run a live `claude-cli` to embedded-child probe in this read-only review.

## Solution Assessment

Unclear without maintainer direction. The narrowest likely fix is a harness-aware inheritance rule that separates CLI bridge-visible tools from native CLI capabilities while preserving inherited restrictions for real configured allow policies.

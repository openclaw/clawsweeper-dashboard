## Summary

This should stay open: current main and the latest release still have a source-reproducible path where a restrictive runtime-visible tool allowlist is persisted into spawned child sessions and later intersects the child embedded tool surface. The remaining work is real, but the repair needs a maintainer security-boundary decision so it does not weaken intended non-escalation for genuinely restricted parents.

## What This Changes

The issue reports that `sessions_spawn` from a CLI-harness parent can persist only bridge-visible tools onto child sessions, causing embedded subagents to lose coding tools such as `exec`, `read`, and `write`.

## Best Possible Solution

Represent the parent’s actual spawnable capability for CLI-harness runtimes separately from the OpenClaw bridge-visible tool list, while still inheriting explicit operator denies and real restrictive policies into child sessions.

Kind: security_boundary

Question: For CLI-harness parent sessions, should subagent tool inheritance use the parent harness’s native file/shell capability instead of the OpenClaw bridge-visible tool list, and which explicit config denies must still be inherited?

Rationale: The source evidence supports the bug, but choosing how to avoid privilege escalation across native CLI harnesses is a security-boundary policy decision that should be made by an agent/security owner before an automated repair changes tool inheritance semantics.

Likely owner: vincentkoc

Owner reason: Vincent is both a listed Agents/Security owner and a recent contributor to the exact agent tool-policy files.

Owner confidence: high

Options:

- **Add canonical native-capability inheritance (recommended):** Model CLI-harness native file/shell capability as a distinct prepared fact and inherit that for child allowlists while preserving explicit denies and true restrictive config policies.
- **Exempt CLI-harness runtime allowlists:** Do not capture bridge-only runtime allowlists from native CLI parents, which is simpler but risks missing future harnesses with genuinely restricted native capability.
- **Add an operator config switch:** Make inheritance opt-out or mode-controlled, but this adds new config surface in an already sensitive tool-policy area.

## Reproduction Assessment

Yes from source inspection for the reported policy path: a bridge-only inherited allowlist is stored on the child and later intersects embedded child tool construction. I did not run a live `claude-cli` spawn, but the current source path is deterministic enough for a focused regression test.

## Solution Assessment

No final implementation should be chosen without the security-boundary decision above. The best direction appears to be a narrow runtime-policy repair rather than a new config switch, because existing inheritance is intentional for genuinely restricted parents and the repository sets a high bar for new config.

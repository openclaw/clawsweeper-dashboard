## Label Justifications

- `P1`: A shipped delegated-agent workflow can lose core coding tools whenever a claude-cli/CLI-harness parent spawns an embedded child.
- `impact:session-state`: The failure is persisted as child session `inheritedToolAllow` state and then reused during child tool-policy resolution.
- `impact:security`: The issue is about inherited file/shell tool authorization for delegated sessions, which is a security boundary.
- `impact:auth-provider`: The failure depends on the selected runtime/backend, so provider/runtime choice changes whether spawned children keep coding tools.

## Summary

Keep open: current main and latest release still build inherited subagent allowlists from the gateway/loopback-visible tool surface, so a CLI-harness parent can persist an allowlist that excludes native file and shell tools. The older closed deny-side claude-cli issues are useful precedent, but no exact open issue or PR fully owns this allow-side core-tool loss.

## What This Changes

The issue requests fixing `sessions_spawn` so subagents spawned from a `claude-cli`/CLI-harness parent do not inherit the bridge-only tool list and lose core coding tools.

## Best Possible Solution

Implement capability-aware inherited tool policy for CLI-harness parents: inherit real configured restrictions while representing native harness file/shell capabilities so embedded children keep their coding tools, with focused regression coverage for claude-cli loopback `sessions_spawn`.

## Maintainer Decision

Kind: security_boundary

Question: Should CLI-harness bridge-visible allowlists be treated as inheritable child restrictions, or should inheritance account for native harness file/shell capabilities that OpenClaw intentionally omits from the MCP bridge?

Rationale: This choice controls whether spawned children may retain file/shell tools when the parent harness has them natively; automation should not decide that authorization boundary without owner intent.

Likely owner: steipete

Owner reason: He fixed the closely related claude-cli loopback deny-side boundary in PR 88946 and is the strongest available owner signal for the security tradeoff.

Owner confidence: high

Options:

- **Use Capability-Aware Inheritance (recommended):** Treat native CLI-harness file/shell capabilities as part of the parent privilege model while still inheriting real configured/profile/group/sandbox restrictions into children.
- **Keep Bridge-Visible Clamp:** Preserve current non-escalation behavior and document that CLI-harness parents spawn children with only the OpenClaw bridge-visible tool set.
- **Add An Explicit Operator Knob:** Introduce an opt-in inheritance mode only if maintainers decide this boundary must stay configurable rather than automatic.

## Reproduction Assessment

Yes by source inspection, but not by a live claude-cli run in this read-only pass. The current loopback path excludes native tools, then inherited allowlist capture stores the filtered visible tool set and child policy resolution consumes it as an allow policy.

## Solution Assessment

Unclear until the security-boundary choice is confirmed. The maintainable direction is likely capability-aware inheritance rather than a config switch or removing inherited restrictions entirely, because real policy denies must still propagate.

## Summary

This should stay open: current main still persists a CLI-harness parent's runtime-visible bridge allowlist into spawned child sessions, so an embedded child can still lose coding tools through inherited allow intersection. The report is source-reproducible and important, but the fix needs a maintainer security-boundary decision so CLI-native privileges are not confused with genuinely restrictive parent policy.

## What This Changes

The issue asks OpenClaw to stop treating a CLI-harness parent's bridge-visible tool allowlist as the inherited privilege set for spawned embedded subagents.

## Best Possible Solution

Define the CLI-harness inheritance contract explicitly, then adjust the subagent tool policy so bridge-visible runtime allowlists do not clamp embedded child coding tools while genuinely restrictive parent policies still constrain delegation.

Options:

- **Model native harness capability (recommended):** Treat CLI-harness native file/shell capability as the inherited privilege basis while preserving restrictive parent policies when they are explicit user or config constraints.
- **Skip bridge allow inheritance:** Do not persist runtime bridge allowlists from CLI-harness parents, accepting that child runtime config becomes the main constraint for those spawns.
- **Add explicit policy control:** Introduce a carefully documented subagent inheritance setting or strict mode, with upgrade-safe defaults and tests for both compatibility and non-escalation.

Yes for source reproduction: current main still routes a runtimeToolAllowlist into inherited allow storage and later intersects the embedded child's tool set against it. I did not run a live claude-cli spawn, so this is source-reproducible rather than locally reproduced.

## Solution Assessment

Unclear until the security-boundary decision is made: the best fix is not a blanket removal of inherited allow, but a targeted distinction between bridge-visible CLI harness tools and explicit parent restrictions.

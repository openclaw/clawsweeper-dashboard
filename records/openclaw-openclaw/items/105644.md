## Label Justifications

- `P2`: Oversized imported histories are not fully retrievable through chat, but their source transcript remains preserved and ordinary sessions continue operating.
- `impact:session-state`: The request concerns complete, ordered, generation-consistent access to imported session transcript state.
- `impact:ux-friction`: The client can report that the snapshot was truncated but currently offers no supported route to retrieve the omitted rows.
- `maturity:stable`: The affected Gateway RPC APIs and Events category belongs to `gateway-runtime`, which is currently scored M4 Stable.

## Summary

Keep this issue open: current main still cannot page omitted imported CLI transcript rows, the broader scroll-back issue intentionally split this lifecycle problem out, and the protected `maintainer` label requires an explicit protocol and ownership decision. Open PR https://github.com/openclaw/openclaw/pull/87111 is adjacent but explicitly keeps imported CLI history first-page-only, so it does not supersede this request.

## What This Changes

Add stable snapshot-cursor paging for oversized merged CLI-import transcripts returned by `chat.history`.

## Best Possible Solution

Materialize imported history through one shared, lifecycle-owned, bounded snapshot abstraction, expose generation-consistent pages to gateway and TUI consumers, and use one canonical paging protocol with focused invalidation and oversized-transcript coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should imported CLI transcript paging extend current offsets through a shared implicit snapshot, or should the explicit cursor design in https://github.com/openclaw/openclaw/pull/87111 become the canonical `chat.history` contract?

Rationale: Both approaches add lifecycle-sensitive core behavior, but they differ in public protocol surface, stale-page semantics, client migration, and shared gateway/TUI ownership; code inspection cannot determine the intended permanent contract.

Likely owner: steipete

Owner reason: The strongest available protocol and feature-history evidence points to this person, who also authored the protected design issue.

Owner confidence: high

Options:

- **Shared implicit snapshot (recommended):** Materialize one bounded snapshot per session generation in the shared history layer and page it through the existing offset request shape.
- **Canonical explicit cursor:** Adopt and broaden the older PR’s cursor protocol to cover imported snapshot lifetime, expiry, invalidation, and all relevant consumers.
- **Defer imported paging:** Retain terminal-snapshot truncation honesty until gateway and TUI history are unified behind a broader service.

## Reproduction Assessment

Yes, at source level with high confidence. Offset requests use a local-transcript-only branch, while imported CLI history is added only to the terminal snapshot before response-byte budgeting; this read-only review did not execute a multi-megabyte imported fixture.

## Solution Assessment

The issue identifies the correct missing capability, but its two proposed cursor shapes are not equally settled. A shared generation-keyed snapshot behind existing offsets appears narrowest, provided maintainers first reconcile the explicit-cursor PR and confirm the gateway/TUI lifecycle owner.

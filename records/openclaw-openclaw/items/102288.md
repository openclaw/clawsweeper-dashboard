## Summary

Keep open: current main still has the `set-identity --workspace` locator/output mismatch, no public `openclaw agents` workspace-relocation command exists, and the right fix changes public CLI/JSON semantics enough to need maintainer direction.

## What This Changes

The issue asks for `openclaw agents set-identity --workspace` to stop implying that an existing agent workspace was updated when it only locates identity data.

## Best Possible Solution

Keep `set-identity --workspace` locator-only, make text/JSON output distinguish locator path from stored workspace, and add a dedicated documented CLI workspace-update path backed by `agents.update` if maintainers want relocation support.

Question: Should the public `openclaw agents` CLI solve this by adding a dedicated existing-agent workspace setter, or by clarifying that `set-identity --workspace` is locator-only?

Rationale: Both fixes are viable, but the choice changes public CLI semantics and JSON output compatibility, so automation should not choose it without maintainer intent.

Owner confidence: high

Options:

- **Add Dedicated Setter (recommended):** Add `agents set-workspace` or `agents update --workspace` backed by `agents.update`, and make `set-identity` output explicit about locator versus stored workspace.
- **Clarify Output Only:** Keep relocation out of the CLI for now and add additive output/docs fields so `set-identity` cannot be read as confirming a stored workspace update.
- **Repurpose Set Identity:** Make `set-identity --workspace` update stored workspace too, accepting compatibility risk against current help text and docs.

## Solution Assessment

Unclear until maintainers choose the CLI contract. The narrow repair is additive output/docs clarification, while the complete relocation workflow likely needs a dedicated setter using the existing `agents.update` API.

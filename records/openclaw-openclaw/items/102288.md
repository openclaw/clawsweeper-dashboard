## Summary

Keep open: current main still has the source-level CLI contract mismatch, and the existing Gateway workspace update API does not resolve the missing or ambiguous public `openclaw agents` relocation path.

## What This Changes

The issue asks for `agents set-identity --workspace` to either update an existing agent's stored workspace or stop reporting the locator path as if it were stored workspace state.

## Best Possible Solution

Keep `set-identity --workspace` locator-only, make the output distinguish locator from stored workspace, and add a documented `agents set-workspace` or `agents update --workspace` command backed by `agents.update` if maintainers want existing-agent relocation support.

Options:

- **Add Dedicated Setter (recommended):** Add an `agents set-workspace` or `agents update --workspace` command backed by `agents.update`, while making `set-identity` output explicit about locator versus stored workspace.
- **Clarify Output Only:** Keep relocation out of the CLI for now and add or rename output fields so `set-identity` cannot be read as confirming a stored workspace update.
- **Repurpose Set Identity:** Make `set-identity --workspace` update the stored workspace too, accepting compatibility risk against the current locator help text and docs.

## Reproduction Assessment

Yes. Source inspection shows `set-identity` uses `--workspace` as an identity locator and agent selector, writes only identity config, and echoes that locator as `workspace` in success output.

## Solution Assessment

Unclear until maintainers choose the CLI contract. The narrow bug repair is output/docs clarification, while the complete relocation workflow likely needs a dedicated setter using the existing `agents.update` API.

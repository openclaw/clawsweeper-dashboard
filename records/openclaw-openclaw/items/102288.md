## Summary

Keep open: current main still has the CLI contract mismatch, and the existing Gateway workspace update API does not give operators a documented `openclaw agents` relocation command or remove the misleading `set-identity --json` response.

## What This Changes

The issue asks OpenClaw to resolve the mismatch where `agents set-identity --workspace` uses the path as an identity locator but reports it as `workspace` without updating the agent's stored workspace.

## Best Possible Solution

Keep `set-identity --workspace` locator-only, make its text/JSON output distinguish locator path from stored workspace, and add a dedicated documented CLI workspace-update path backed by `agents.update` if maintainers want relocation support.

Rationale: Both repairs are plausible, but the choice changes public CLI semantics and JSON output compatibility, so automation should not choose the contract unilaterally.

Owner confidence: high

Options:

- **Add dedicated setter (recommended):** Add `agents set-workspace` or `agents update --workspace` backed by `agents.update`, and make `set-identity` output explicit about locator versus stored workspace.
- **Clarify output only:** Keep relocation out of the CLI for now and add or rename response fields so `set-identity` cannot be read as confirming a stored workspace update.
- **Repurpose set-identity:** Make `set-identity --workspace` update the stored workspace too, accepting compatibility risk against current help text and docs.

Yes. Source inspection on current main shows `set-identity` writes identity fields only while returning the locator directory as `workspace`; I did not run the CLI because this review is read-only.

Unclear until maintainers choose the CLI contract. The narrow bug repair is additive output clarification, while the complete relocation workflow likely needs a dedicated setter using the existing `agents.update` API.

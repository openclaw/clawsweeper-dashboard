## Label Justifications

- `P1`: The exact head can still execute under tightened approval policy and can mutate approval state through a rejected stale administrative operation.
- `merge-risk: 🚨 compatibility`: The PR changes persistence, missing-file initialization, synchronous helper behavior, and failure semantics for existing approval callers and upgrades.
- `merge-risk: 🚨 security-boundary`: Incomplete authorization binding and side-effectful CAS rejection can restore or consume command-execution authority after policy revocation.
- `merge-risk: 🚨 availability`: The new fail-closed locking and read behavior can temporarily block approval administration or execution when lock ownership is unverifiable.

## Summary

Keep this PR open: the transaction architecture is directionally right, but the exact head still permits stale explicit and auto-reviewed authorizations after policy tightening, and two rejected CAS writes can mutate or recreate approval state before returning conflict.

## What This Changes

The PR serializes exec-approval mutations and carries policy-bound authorization provenance across Gateway, node-host, CLI, and macOS execution and settings paths.

## Best Possible Solution

Use one canonical accepted-under-lock transaction on every host: capture a complete policy snapshot for every non-current authorization, perform a non-persisting state read, reject any authorization or CAS drift, and only then initialize, record usage, persist grants, or spawn the command.

## Summary

This is a well-evidenced feature PR, but it intentionally changes the approval contract for `skills.workshop.approvalPolicy: "pending"`: an approval shown for one proposal version cannot act on a later revision. The patch appears coherent and the supplied native Telegram proof covers the intended flow, yet that fail-closed operator behavior needs explicit maintainer endorsement before merge rather than being accepted solely from contributor and operator comments.

## What This Changes

Adds a read-only Skill Workshop `review` action that renders the canonical files for create proposals or a bounded unified diff for updates, then optionally binds later approval actions to the reviewed proposal version.

## System Context

Skill Workshop turns agent-created reusable-skill proposals into workspace `SKILL.md` files and support files. The new review projection reads the pending proposal and, for updates, the current workspace target, then passes a portable preview to the agent/channel layer before an operator applies, rejects, or quarantines the proposal.

## Architecture Diagram

flowchart LR
  Proposal[Pending Skill Workshop proposal] --> Review[Read-only review projection]
  Workspace[Current workspace skill files] --> Review
  Review --> Preview[Canonical create content or update diff]
  Preview --> Prompt[Agent and channel approval prompt]
  Prompt --> Decision[Apply, reject, or quarantine]
  Decision --> Lifecycle[Proposal lifecycle service]
  Lifecycle --> Outcome[Workspace change or bounded rejection]

## Best Possible Solution

Keep proposal-ID-only lifecycle calls compatible, but merge the version-bound approval behavior only after an owner explicitly confirms that pending approvals must remain fail-closed when their reviewed proposal changes.

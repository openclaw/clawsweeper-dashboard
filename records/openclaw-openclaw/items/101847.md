## Label Justifications

- `P2`: The issue affects every authenticated Control UI reload/open but does not block setup, cause data loss, or break an active agent workflow.
- `impact:ux-friction`: Authenticated operators see a misleading full login gate flash before a successful stored-credential handshake.
- `impact:session-state`: The UI presentation treats stored authenticated browser state like an unauthenticated first-connect state until hello completes.
- `maturity:stable`: The affected Control UI hosted web/auth/WebSocket startup path maps to the M4 Stable `gateway-runtime` feature in the maturity shortlist.

## Summary

Keep open: current main still renders the login gate during the first connection attempt, including stored-token startup, and the protected `maintainer` label requires maintainer handling. The merged reconnect work covers post-hello drops, not this first-load stored-credential flash.

## What This Changes

The issue requests an initial authenticated-loading state for Control UI startup so stored credentials do not show the full login gate before the first gateway hello resolves.

## Best Possible Solution

Add a narrow auth-candidate startup state that shows a small loading surface for tokenized URL, native auth injection, session token, or stored device-token attempts, while preserving the login gate for no credentials and explicit credential rejection.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Control UI treat stored credentials or startup auth candidates as a loading state instead of rendering the login gate before the first gateway hello?

Rationale: Current docs and tests intentionally reserve the login gate for first connects/page reload before connect, so changing that behavior needs maintainer UX direction despite the source-reproducible flicker.

Likely owner: steipete

Owner reason: They authored the related reconnect-state implementation and most recent Control UI app-host work, making them the clearest routing owner for this UX boundary.

Owner confidence: high

Options:

- **Add auth-candidate loading state (recommended):** Show the mascot/loading surface during startup when a credible token, native auth injection, or stored device credential exists, then fall back to the gate only on missing credentials or explicit rejection.
- **Keep first-connect gate:** Leave the current documented/tested behavior in place and accept the startup flash as the cost of making operator input immediately available.
- **Fold into reconnect UX follow-up:** Track this as a broader Control UI auth-state polish item alongside related login-gate flicker reports instead of making a narrow startup-only change now.

## Reproduction Assessment

Yes, at source level: current main publishes a first-start snapshot with `connected:false` and `reconnecting:false`, and `OpenClawApp.render` then mounts the login gate. I did not run a live browser reload timing capture.

## Solution Assessment

Unclear until maintainers choose the UX contract. The best likely shape is a narrow auth-candidate initial-handshake state, not broadening `reconnecting` to hide every first-connect failure.

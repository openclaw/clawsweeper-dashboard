## Summary

Keep open: the PR targets a real subagent allowlist bug, but the current patch can turn additive `alsoAllow` entries into a restrictive inherited allowlist and break spawned child tool surfaces; it also lacks real behavior proof.

## What This Changes

The PR changes subagent spawning to persist global subagent and target-agent `tools.alsoAllow` entries into child sessions' inherited tool allowlist, with regression tests.

## Best Possible Solution

Preserve target-agent additive grants without creating a restrictive inherited allowlist when the parent had none, then prove a real spawned subagent receives both its normal tools and the target-only tool.

Full review comments:

- **[P1] Preserve additive allow semantics:** `src/agents/subagent-spawn.ts:1335-1343`
  - body: This array can contain only `tools.subagents.tools.alsoAllow` or target-agent `tools.alsoAllow` when the caller has no restrictive inherited allowlist. After this patch, `inheritedToolAllowPatch` persists that as `inheritedToolAllow`, and `resolveInheritedToolPolicyForSession` later treats any stored list as a final restrictive allow policy. An otherwise unrestricted target with `tools.alsoAllow: ["gbrain_readonly"]` would be reduced to only that tool, dropping normal defaults. Preserve unrestricted/additive semantics when there was no parent allowlist, and add a regression for that case.

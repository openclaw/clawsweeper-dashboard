## Summary

Keep open. Current main does not provide a safe close: the code still has a plausible selected-session/runtime-state path where an OpenAI model displays and runs as OpenAI Codex once the Codex harness is registered, while the exact trigger that promotes a configured DeepSeek primary to that OpenAI selection remains unresolved.

## What This Changes

Issue reports that enabling the Codex plugin makes ordinary chat use OpenAI Codex instead of the configured DeepSeek primary model, leading to GPT-5.4-nano TPM failures.

## Best Possible Solution

Keep the issue open, confirm whether plugin hot reload or persisted session state promotes openai/gpt-5.4-nano, then repair that owner boundary without adding new config.

## Reproduction Assessment

No high-confidence full reproduction was run. The user provided concrete latest-release steps, screenshots, and logs, and source inspection explains how an OpenAI selected session becomes OpenAI Codex when the plugin is registered, but not why enabling the plugin changes a DeepSeek primary into that selected model.

## Solution Assessment

The best fix is not yet proven. The likely maintainable path is to centralize selected/runtime/display model-state interpretation or narrowly fix the hot-reload path that turns stale OpenAI runtime state into the active selected model after Codex enablement.

## Summary

Keep open. Current main and v2026.6.11 still restrict group admission to open, disabled, or allowlist behavior; the merged pairing-request hook only observes DM pairing requests, and related open work does not implement owner-approved group admission or define the pre-approval content boundary.

## What This Changes

Add owner-approved group admission, group-join notifications, approve/reject controls, and optional restricted observation for unconfigured groups.

## Best Possible Solution

Implement a shared pending-group approval state keyed by channel, account, and group; notify owners with bounded join metadata; require explicit authorized approval before messages reach sessions, hooks, or agents; and design any reader mode as a separate opt-in security feature.

Options:

- **Metadata only (recommended):** Create a pending approval from channel-provided join metadata and drop every message until approval.
- **First-message metadata:** Create a pending approval when the first message arrives but retain only group and sender identifiers plus display metadata.
- **Restricted content reader:** Allow an explicitly configured restricted agent to process message bodies before approval.

## Reproduction Assessment

Yes—source inspection provides a high-confidence reproduction: group messages return from group-policy evaluation before the DM pairing branch, and no group pairing policy, pending approval store, or group approval CLI exists.

## Solution Assessment

No, not as one combined feature. Owner-approved group admission is a coherent shared capability, but pre-approval reader-agent execution should be excluded or designed separately after maintainers settle the security boundary.

## Label Justifications

- `P2`: This is a normal-priority security and channel-admission feature with meaningful design impact, while existing allowlist and disabled modes already block unauthorized group execution.
- `impact:security`: The issue is about approving or rejecting untrusted groups before the bot can engage there and about safely handling unauthorized group additions.
- `impact:session-state`: The proposed pending group and reader-agent modes would add authorization state that controls which group contexts can reach agent sessions.

## Summary

Keep open: current main still keeps pairing scoped to DMs, while group admission remains allowlist/open/disabled with no pending group approval state, owner notification path, group approve/reject CLI, or safe reader-agent mode. Related Telegram and WhatsApp work overlaps but does not replace the requested cross-channel group-pairing contract.

## What This Changes

Request a cross-channel group pairing flow that notifies the owner when a bot joins an unconfigured group, lets the owner approve or reject it, and optionally routes pending groups through read-only observation.

## Best Possible Solution

Define a product/security-reviewed shared group admission contract with canonical pending approval state, redacted owner notifications, authorized approve/reject operations, and a separately explicit no-reply/no-tool observation mode before wiring Telegram and WhatsApp.

## Reproduction Assessment

Yes at source level, not as a bug: current main keeps group policies to open, allowlist, or disabled and keeps pairing on the DM path only.

## Solution Assessment

No current implementation is best yet. The maintainable path is a shared, product/security-reviewed group admission contract rather than stretching DM pairing or merging narrower channel-specific proposals independently.

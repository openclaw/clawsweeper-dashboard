- `impact:security`: The request governs authorization and owner control when a bot is added to an unapproved group.

## Summary

Current main still intentionally reserves pairing for DMs; group admission remains explicit open/disabled/allowlist policy, and the merged notification hook only observes DM pairing requests. Related issues address unknown-group warn/leave or sender-denial UX rather than owner-mediated group approval, so this remains necessary but needs a maintainer product/security decision before implementation.

## What This Changes

Add owner-notified approval for newly added groups and an optional restricted observation mode while approval is pending.

## Best Possible Solution

Define an additive shared pending-group authorization contract with durable channel/account/group identity, an owner-visible notification event, and authorized approve/reject operations while dropping all pending-group messages; scope any reader-agent observation as a separate sandboxed capability with explicit state isolation.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should unapproved groups remain completely unprocessed until owner approval, or may their messages enter a restricted reader context while approval is pending?

Rationale: The options create materially different authorization, prompt-injection, session-state, and privacy boundaries, and current source intentionally keeps DM pairing state separate from group authorization.

Likely owner: steipete

Owner reason: The shared authorization boundary and deliberate separation between DM pairing and group access are concentrated in Peter Steinberger's merged history.

Owner confidence: high

Options:

- **Notification-Only Pairing (recommended):** Create pending group state and notify the owner, but drop all group messages until explicit approval.
- **Sandboxed Observation:** Allow pending messages only in a separately isolated reader with no replies, privileged tools, or trusted-session memory.
- **Keep Explicit Configuration:** Retain configuration-only group authorization and address unknown groups through separate notification or warn/leave features.

## Reproduction Assessment

Yes for the capability gap: current source clearly shows that pairing is DM-only and group authorization supports only open, disabled, or allowlist behavior. This is a source-level verification of a missing feature, not a failing bug reproduction.

## Solution Assessment

Partly: pending approval plus owner notification is a coherent extension, but combining it with reader-agent processing is not the safest initial solution. The narrowest maintainable first step is notification-only group pairing with explicit authorization and no pre-approval message ingestion.

## Summary

Current main still has a real feature gap: group policy remains open, disabled, or allowlist; the merged pairing-notification hook is DM-only; and related items cover narrower warn, leave, or observation behavior. Keep this open for the product and security decision already identified in the discussion.

## What This Changes

Add owner-controlled group pairing, group-add notifications, approve/reject operations, and an optional restricted observation mode for unconfigured groups.

## Best Possible Solution

Implement a generic content-blind pending-group admission state keyed by channel, account, and native group identity, with trusted owner notification and authorized approve/reject operations; scope any reader-agent observation as a separate later feature with explicit sandbox, storage, hook, and content-retention limits.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should first-class group pairing be content-blind until owner approval, or should OpenClaw also support an explicitly configured restricted reader for pending groups?

Rationale: The choice defines a new cross-channel authorization and persistence contract, and reader mode changes whether unapproved group content crosses model, plugin, session, transcript, and memory boundaries.

Likely owner: steipete

Owner confidence: medium

Options:

- **Content-blind pairing (recommended):** Add pending group identity, owner notification, and approve/reject operations without ingesting group content before approval.
- **Pairing plus reader mode:** Add an opt-in pending reader only after defining sandbox, tools, hooks, storage, retention, and prompt-injection boundaries.
- **Keep explicit allowlists:** Retain current group admission and pursue only narrower warn, notify, or auto-leave behavior in channel-owned paths.

## Reproduction Assessment

Yes for the reported capability gap. Current-main types, schema, channel docs, and the DM-only hook contract consistently show that group pairing, pending approval, and group approve/reject operations do not exist.

## Solution Assessment

Unclear as one combined feature. Owner-controlled group admission is a maintainable direction, but pre-approval reader ingestion should be separated unless maintainers explicitly accept and specify the broader security boundary.

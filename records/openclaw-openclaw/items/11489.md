## Summary

Keep open. Current main deliberately keeps pairing on the DM path: group admission uses group allowlists and policy instead, while the recently merged pairing-request hook only observes newly created DM pairing requests. The requested pending-group approval state, owner notification trigger, and safe pre-approval observation policy therefore remain a real cross-channel product and security design decision.

## What This Changes

Add a cross-channel group-pairing flow that records unapproved groups, alerts the owner, supports approval or rejection, and optionally allows restricted observation before approval.

## System Context

Channel adapters receive group events and apply group admission policy before creating an agent session. DM pairing has a shared request store and notification hook, but group policy currently routes unapproved traffic through group allowlists rather than a pending-approval state.

## Architecture Diagram

flowchart LR

  B --> C{Configured and authorized?}
  C -->|Yes| D[Create agent session]
  C -->|No| E[Block or channel-specific action]
  F[DM pairing request] --> G[Pairing request store]
  G --> H[Trusted notification plugin hook]
  I[Proposed group pairing state] --> J[Owner approval or rejection]

## Best Possible Solution

Define a small shared group-admission state machine first: channel/account/group identity, owner-visible pending notification, explicit approve/reject lifecycle, canonical persistence and doctor migration, and channel adapters for Telegram and WhatsApp; scope read-only observation as a separate opt-in policy unless the approved design proves it shares the same security boundary.

## Summary

Keep open: current main and v2026.6.11 still keep pairing scoped to DMs while group admission is allowlist/open/disabled only; the related Telegram and WhatsApp items cover narrower mitigations, not owner-notified cross-channel group pairing.

## What This Changes

The issue requests a cross-channel group pairing flow with owner notification, approve/reject controls, and optional read-only handling for unconfigured groups.

## Best Possible Solution

Define a product/security-reviewed group admission contract that stores pending approvals by channel/account/group, sends redacted owner notifications, authorizes approve/reject operations, and treats read-only observation as an explicit isolated mode.

Options:

- **Design Shared Admission First (recommended):** Create one cross-channel approval contract with persistence, owner notification, approve/reject authority, and explicit isolation rules before channel-specific implementation.
- **Ship Channel-Specific Mitigations Only:** Let narrower Telegram/WhatsApp warn, leave, audit, or notification work proceed while deferring owner-notified group pairing.
- **Keep Allowlists Only:** Decline group pairing for now and document group allowlists, disabled policy, mention gating, and sandboxed sessions as the supported posture.

Yes, at source level: current main keeps group policies to open, allowlist, or disabled and keeps pairing on the DM path only. This is a missing feature rather than a failing existing-behavior bug.

## Solution Assessment

No current implementation is best yet. The maintainable path is a shared product/security-reviewed group admission contract rather than stretching DM pairing or landing narrower channel-specific proposals independently.

## Summary

Keep open. Current documented behavior still separates DM pairing from group access: unknown DMs can create pairing requests, while groups use `groupPolicy`, sender/group allowlists, and channel-specific group configuration. The merged DM-only pairing-request hook is useful for owner notifications, but it does not create pending group approvals, group approve/reject operations, or a safe pre-approval message-context contract. This needs a maintainer product and security decision before implementation.

## What This Changes

Add a cross-channel owner-controlled group admission flow for Telegram and WhatsApp, including owner notification, approval or rejection, and an optional restricted observation mode before approval.

## System Context

Inbound channel messages first pass group and sender access policy before OpenClaw creates an agent turn or writes conversational context. DM pairing already persists an approval request and can notify trusted plugins; this request would introduce an equivalent but materially different admission lifecycle for group identities and pending group messages.

## Architecture Diagram

flowchart LR
  A[Telegram or WhatsApp group added] --> B[Channel inbound preflight]
  B --> C[Group access policy]
  C -->|configured group| D[Agent session and reply pipeline]
  C -->|unknown group| E[Pending group admission decision]
  E --> F[Owner notification and approve or reject action]
  E --> G[Optional restricted observation]
  F --> C
  G --> H[Controlled context or audit output]

## Best Possible Solution

Define one additive, shared group-admission contract that denies agent execution by default, persists approval by channel/account/group identity, emits a minimal trusted notification event, and provides authorized approve/reject/optional-leave operations; keep read-only observation out of the initial contract unless maintainers explicitly define how unapproved content is isolated from normal agent state.

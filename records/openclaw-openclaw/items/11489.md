## Summary

Keep open. Current main and v2026.6.11 still keep pairing on the DM path; the merged pairing-request hook enables DM notifications but does not add pending group admission, owner approve/reject operations, or a defined pre-approval content boundary.

## What This Changes

Requests owner-notified group admission pairing plus an optional read-only pending-group mode across group-capable channels.

## Best Possible Solution

Add a shared, persistent group-admission state keyed by channel/account/group, notify an authenticated owner without exposing message content, and provide owner-gated approve/reject operations; design any silent reader-agent mode as a separate opt-in capability with explicit context, tool, transcript, and retention limits.

Options:

- **Admission Only First (recommended):** Create pending group records and metadata-only owner notifications, dropping all message content until approval and deferring reader mode to separate work.
- **Restricted Observation:** Include an opt-in reader-agent path now, with a separately specified sandbox, tool denial, isolated session store, retention policy, and no outbound delivery.
- **Keep Existing Allowlists:** Do not add group pairing and continue using explicit group allowlists plus separately scoped warn or auto-leave features.

## Reproduction Assessment

Yes—source and current documentation provide a high-confidence way to verify the missing capability: group policy has no pairing state, pairing approval remains DM-only, and unapproved groups are blocked rather than queued for owner approval.

## Solution Assessment

No—the proposal combines a sound group-admission need with the materially riskier reader-agent mode. The narrowest maintainable solution is metadata-only pending admission first, with pre-approval content observation designed separately.

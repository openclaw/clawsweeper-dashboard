## Summary

Keep this PR open. The current branch still changes the established provider retry setting from a per-provider-call SDK budget into a shared retry count for whole primary-to-fallback cycles, so configured retries can alter fallback ordering and repeat candidates rather than preserving the existing contract. It also needs refreshed real-process evidence from the final head for the configured retry path before merge.

## What This Changes

The branch makes embedded steering writes fence-aware, disables SDK retries during the released session-lock window, retries transient failures outside that window, and returns resend guidance instead of silently losing a reply after session takeover.

## System Context

Embedded agent turns release their session lock while a provider call runs, then reacquire it and verify that the transcript remains owned by the turn. The reply orchestrator selects providers and fallbacks, retries failures, and turns terminal outcomes into channel-visible messages.

## Architecture Diagram

flowchart LR
  Inbound[Inbound message] --> Turn[Embedded agent turn]
  Turn --> Lock[Released session-lock window]
  Lock --> Provider[Provider request]
  Provider --> Fallback[Retry and fallback orchestration]
  Lock --> Fence[Transcript ownership fence]
  Fence --> Outcome[Terminal outcome]
  Fallback --> Outcome
  Outcome --> Reply[Channel reply or resend guidance]

## Best Possible Solution

Keep SDK retries at zero inside the released lock window, but implement configured retries at a lock-safe per-candidate outer boundary so each configured retry reacquires the session lock without replaying unrelated fallback candidates; then attach redacted final-head terminal proof for single-model and multi-model configured retry cases.

## Summary

This PR still addresses a real message-loss and session-takeover path, but its current retry-budget implementation changes configured provider retries from per-request retries into repeats of the entire primary-to-fallback cycle. That can duplicate fallback selection, latency, and billable requests for existing multi-model configurations, so it needs a focused repair before merge.

## What This Changes

The branch makes embedded steering writes fence-aware, prevents SDK retries while the session lock is released, restores selected retries outside that window, and returns resend guidance for a session takeover rather than silently dropping the reply.

## System Context

The auto-reply runner selects a model and executes an embedded agent attempt while its session transcript is protected by a lock and fence. Provider transport errors, fallback selection, and concurrent steering writes all converge there before the resulting assistant payload is delivered to the originating channel.

## Architecture Diagram

flowchart LR
  Inbound[Inbound message] --> Runner[Reply runner]
  Runner --> Fallback[Primary and fallback selection]
  Fallback --> Attempt[Embedded agent attempt]
  Attempt --> Lock[Session lock and transcript fence]
  Attempt --> Transport[Provider SDK transport]
  Transport --> Retry[Retry owner]
  Lock --> Takeover[Takeover or resend guidance]
  Retry --> Delivery[Reply delivery]

## Best Possible Solution

Keep SDK retries disabled only during the released-lock window, but restore configured provider retries at a lock-safe per-candidate request boundary so existing primary/fallback ordering and retry counts remain unchanged; then publish fresh redacted real-process proof from the final head.

## What This Changes

The PR makes synchronous exec-approval reads bypass same-process lock contention, extracts the copy-based persistence fallback, and adds a focused regression test.

## Best Possible Solution

Same-process contention should return the last fully committed approval policy without bypassing write serialization, with regression coverage for both atomic-rename and in-place fallback writes plus a redacted live gateway concurrency run.

Question: What committed-state contract should synchronous approval reads use while the same process holds an asynchronous write lock?

Rationale: Choosing between eliminating the nested synchronous read and introducing an explicit process-local committed snapshot changes an authorization invariant; automation cannot safely choose which state is authoritative during an active or rollback-bound write.

Likely owner: steipete

Owner confidence: high

Options:

- **Remove the nested synchronous read (recommended):** Refactor the async owner path to carry its prepared policy state forward so no synchronous reader bypasses the active write lock.
- **Add a committed snapshot:** Maintain a process-local snapshot updated only after persistence commits and serve that snapshot during same-process contention.
- **Accept lockless reads:** Intentionally permit reads during active copy fallback writes and document that transient or rollback-bound policy state may be observed.

## Reproduction Assessment

No high-confidence live current-main reproduction was established in this review, although the linked issue provides a concrete production trace and the source exposes the same-PID contention path. The PR's added test reproduces only an idle same-PID lock file, not an active writer.

## Solution Assessment

No. Avoiding permanent same-process contention is necessary, but bypassing the read lock is not the safest fix while the store retains an in-place copy fallback; the read must instead remain tied to fully committed state.

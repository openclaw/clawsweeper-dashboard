## Summary

Keep open. Current main still lacks the requested generic runtime placeholder contract, and the active related pull requests address narrower Fireworks affinity, provider-specific affinity, or scoped static-header use cases. Maintainer direction is needed before implementation because the feature changes both core configuration semantics and which runtime identifiers may be disclosed to provider endpoints.

## What This Changes

Add runtime placeholders such as session, agent, and run identifiers to custom LLM provider header configuration.

## Best Possible Solution

Use provider-owned typed request hooks or explicit compatibility capabilities with opaque scoped identifiers, adding a broader allowlisted context contract only if provider hooks cannot cover demonstrated tracing use cases.

Options:

- **Provider-Owned Typed Hooks (recommended):** Use existing compatibility flags or provider plugin hooks with explicit opaque identifiers, adding generic API surface only for requirements those hooks cannot express.
- **Allowlisted Header Templates:** Permit a small documented placeholder set with explicit endpoint trust, escaping, missing-value, precedence, compaction, and retry semantics.
- **Generic Request Templates:** Create one template system spanning headers and request bodies and intentionally accept the larger security and compatibility surface.

## Reproduction Assessment

Yes at source level: current configuration and request-merging paths treat header values as literal strings, and the current documentation describes provider headers as static. No runtime test was executed during this read-only review.

## Solution Assessment

No—not yet. Unrestricted string interpolation is broader than necessary for Fireworks, which can use the existing typed session-affinity contract, while broader tracing requires a separately approved egress-safe API.

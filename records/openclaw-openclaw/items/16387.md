## Summary

Keep open. Current main still treats configured provider headers as literal strings, while related open PRs cover narrower affinity/schema/static-header paths rather than this issue's generic session/agent/run placeholder contract.

## What This Changes

The issue requests dynamic interpolation in custom LLM provider headers so runtime values such as session, agent, or run identifiers can be sent to providers like Fireworks.ai or LiteLLM.

## Best Possible Solution

Define one narrow, documented provider-request metadata contract that preserves static headers, SecretRef/auth handling, caller header precedence, retries, and attribution headers while expanding only approved runtime placeholders.

Options:

- **Approve narrow explicit placeholders (recommended):** Support only approved placeholders such as {{session.key}}, {{agent.id}}, and {{run.id}} in provider request headers, with docs and tests preserving static and SecretRef behavior.
- **Prefer explicit header mapping:** Use provider-specific affinity flags and typed run-context header mapping instead of arbitrary template strings inside configured header values.
- **Defer for privacy design:** Keep the issue open until maintainers define which runtime identifiers may be sent to external providers and how users opt in.

Yes. Source inspection is enough to reproduce the gap: a configured header value like {{session.key}} is copied and merged as a literal string rather than resolved from runtime session context.

## Solution Assessment

Unclear until maintainers choose the contract. A narrow approved-placeholder resolver is the best generic solution if templating is accepted, while provider-specific affinity and explicit mapping paths are safer if arbitrary templating is rejected.

## Label Justifications

- `P2`: This is a scoped provider-header feature gap with clear user value, not an emergency runtime outage or first-run blocker.
- `impact:security`: The requested feature would intentionally project runtime identity values into outbound third-party HTTP headers.
- `impact:auth-provider`: The affected surface is model-provider request construction, custom headers, and provider routing behavior.

## Summary

Current main still sends configured provider headers as static strings, so the generic session/agent/run placeholder request remains open. Narrow related PRs cover Fireworks/OpenAI-compatible affinity, OpenRouter/ZAI-specific forwarding, scoped static headers, or run-context header mapping, but none replaces this issue's requested dynamic header templating contract.

## What This Changes

Request support for explicit runtime placeholders such as `{{session.key}}`, `{{agent.id}}`, and `{{run.id}}` in custom LLM provider header configuration for provider prompt-cache affinity and observability integrations.

## Best Possible Solution

Define one narrow, documented provider-request metadata contract that preserves static headers and SecretRef behavior, expands only approved runtime fields, and leaves provider-specific affinity defaults to plugins or explicit compat flags.

Options:

- **Approve narrow generic placeholders (recommended):** Implement only explicit placeholders such as `{{session.key}}`, `{{agent.id}}`, and `{{run.id}}` in provider request headers with docs, security notes, and tests for unchanged static headers.
- **Prefer explicit header mapping:** Use the narrower run-context header mapping and provider-specific affinity paths instead of accepting template strings inside arbitrary header values.
- **Defer for privacy design:** Keep the issue open until maintainers define which runtime identifiers may be sent to external providers and how users should opt in.

## Reproduction Assessment

Yes. Source inspection is enough to reproduce the gap: current main copies configured provider and request headers as literal strings, so a value like `{{session.key}}` would be sent unchanged rather than resolved.

## Solution Assessment

Unclear until maintainers choose the contract. A narrow approved-placeholder resolver is the best generic solution, while the open provider-specific and run-context header PRs are safer if OpenClaw does not want arbitrary header templating.

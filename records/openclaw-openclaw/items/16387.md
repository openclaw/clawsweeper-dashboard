## Label Justifications

- `impact:security`: The requested feature would intentionally send runtime identity values through outbound third-party HTTP headers.

## Summary

Keep open. Current main still treats configured provider headers as literal strings, and the remaining question is the product/security contract for generic session/agent/run placeholder expansion rather than a missing obvious code patch.

## What This Changes

Request dynamic interpolation for custom provider header config so values can include runtime session, agent, or run identifiers for provider-side routing and tracing.

## Best Possible Solution

Define one narrow, documented provider-request metadata contract that preserves static headers, SecretRef/auth handling, retries, and attribution headers while expanding only approved runtime placeholders.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add a generic runtime placeholder contract for provider headers, or keep session-aware provider headers limited to typed/provider-specific features?

Rationale: Current main still has a source-level gap, but the requested config syntax can expose runtime identifiers to third-party providers and overlaps with open Fireworks, ZAI, ChatGPT Responses, schema, run-context, extra_body, and per-agent/per-cron header work.

Likely owner: Takhoffman

Owner reason: Takhoffman is the live assignee and best available owner for this product/security boundary decision.

Owner confidence: medium

Options:

- **Approve narrow explicit placeholders (recommended):** Support only approved values such as {{session.key}}, {{agent.id}}, and {{run.id}} in configured provider request headers with docs and tests preserving static and SecretRef behavior.
- **Prefer typed/provider-specific mapping:** Use provider-specific affinity flags or explicit run-context header mapping instead of arbitrary string templating in header values.
- **Defer for privacy design:** Keep the issue open until maintainers define which runtime identifiers may be sent to external providers and how users opt in.

## Reproduction Assessment

Yes. Source inspection is enough to reproduce the gap: a configured header value such as {{session.key}} is copied and merged as a literal string rather than resolved from runtime session context.

## Solution Assessment

Unclear until maintainers choose the contract. A narrow approved-placeholder resolver is the best generic solution, while provider-specific affinity and explicit mapping paths are safer if arbitrary templating is rejected.

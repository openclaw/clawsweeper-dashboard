## Summary

Keep this PR open: the targeted regression is real, but the new path-based detection also treats a shared `diagnostics.otel.endpoint` ending in `/v1/<signal>/?…` as signal-specific, so metrics and logs can be sent to the wrong path. The patch needs a small source-provenance refactor plus real collector proof before merge.

## What This Changes

The PR preserves trailing-slash, query-qualified OTLP signal endpoints instead of appending a second signal path.

## Best Possible Solution

Preserve endpoint source through resolution: use explicit signal config or signal environment endpoints as supplied, and append `v1/<signal>` only to the shared endpoint; prove both paths against a local OTLP HTTP receiver.

Yes, from source: a shared endpoint such as `https://collector.example.com/v1/traces/?timeout=30s` flows through the same resolver and the changed branch returns it unchanged for every enabled signal. The supplied test covers only explicit signal override fields, not that shared-source path.

## Solution Assessment

No. The patch infers endpoint semantics from the URL path, but the documented and OTLP-defined distinction is the configuration source; explicit signal endpoints should be preserved and shared endpoints should receive the signal suffix.

## Label Justifications

- `P2`: This is a focused Mattermost channel hardening fix with limited blast radius and no evidence of an urgent live regression.
- `merge-risk: 🚨 compatibility`: The new 4 MiB default can reject self-hosted or custom Mattermost WebSocket events that were previously accepted by the `ws` 100 MiB default.
- `merge-risk: 🚨 message-delivery`: A frame over the new cap closes the monitor before OpenClaw can parse or dispatch any Mattermost message in that event.

## Summary

Keep open for normal maintainer review: the force-pushed PR addresses the earlier too-low cap by using 4 MiB and adds proof for normal, large-valid, and oversized Mattermost frames. I found no blocking patch defect, but the new default intentionally narrows the accepted inbound frame envelope, so a maintainer should accept that compatibility boundary before merge.

## What This Changes

The PR adds a 4 MiB `maxPayload` to the Mattermost monitor WebSocket client and a loopback test for normal, large-valid, and oversized inbound events.

## Best Possible Solution

Land the 4 MiB transport cap once maintainers accept the supported Mattermost event envelope; if custom deployments need more headroom, raise the constant and keep the same focused test shape.

## Reproduction Assessment

Yes. A loopback WebSocket server can exercise `createMattermostConnectOnce()` with normal, large-valid, and `4 MiB + 1` frames, and current main/release omit `maxPayload` so they inherit the `ws` 100 MiB default.

## Solution Assessment

Yes, with maintainer acceptance of the compatibility envelope. The default Mattermost WebSocket factory is the narrow owner boundary for this resource guard, and the PR now keeps the cap above the upstream valid posted-event envelope covered by its loopback test.

## Summary

Keep open: this PR is a useful direct-path mitigation with visible WhatsApp proof, but it is not safe to merge as-is because the prior blockers remain at the same head. Routed fast-abort delivery still normalizes the configured prefix without a response-prefix context, and the new seed values come from config defaults rather than the active session/channel/fallback/catalog model state.

## What This Changes

The PR pre-seeds `createReplyPrefixContext()` with config-default provider, model, and thinking values and adds unit tests for seeded defaults and `onModelSelected` override behavior.

## Best Possible Solution

Carry a real `ResponsePrefixContext` through direct and routed fast-abort delivery, deriving model and thinking values from active session, channel override, fallback, and catalog state where available, with config defaults only as a fallback.

## Reproduction Assessment

Yes, source-level: configure a templated `messages.responsePrefix`, trigger `stop` or `/stop` while a run is active, and current main can normalize the fast-abort reply before live model/thinking context is populated. The PR screenshots also show the before/after behavior for the direct WhatsApp path.

## Solution Assessment

No. The PR is a useful mitigation, but the best fix must also cover routed-origin delivery and active model state rather than only pre-seeding config defaults.

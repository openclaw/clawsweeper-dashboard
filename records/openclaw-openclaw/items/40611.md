## Label Justifications

- `P1`: The issue describes a regression that can block active channel conversations for minutes during normal heartbeat scheduling.
- `impact:message-loss`: Heartbeat contention can delay or suppress visible Telegram, Feishu, or WebChat replies while users are actively chatting.
- `impact:session-state`: The failure is rooted in heartbeat scheduling, active run detection, and session/run lock contention.

## Summary

Keep open: current main and v2026.6.11 still send `requests-in-flight` heartbeat busy skips through the shared 1 second wake retry path, and the matching fix remains only an open PR candidate.

## What This Changes

The issue asks OpenClaw to stop heartbeat requests-in-flight skips from retrying after about 1 second because the resulting heartbeat run can block active Telegram and other channel conversations.

## Best Possible Solution

Keep this as the canonical narrow retry-cadence bug until https://github.com/openclaw/openclaw/pull/89989 or an equivalent wake-layer fix is reviewed, proven, and merged; keep broader idle-timeout and non-blocking heartbeat architecture work separate.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 still route `requests-in-flight` heartbeat busy skips through the shared 1 second wake retry path, and adjacent tests encode that cadence. I did not run a live Telegram, Feishu, or WebChat reproduction in this read-only review.

## Solution Assessment

Yes for the near-term direction: separating the `requests-in-flight` retry cadence in the heartbeat wake layer addresses the reported regression without reintroducing the old full-interval drift. The linked PR still needs its own correctness and proof review before it can be the merge vehicle.

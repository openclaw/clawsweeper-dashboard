## Label Justifications

- `P1`: The issue describes a regression that can block active channel conversations for minutes during normal heartbeat scheduling.
- `impact:message-loss`: Heartbeat lock contention can delay or suppress visible channel replies while users are actively chatting.
- `impact:session-state`: The failure is rooted in heartbeat scheduling, active run detection, and session/run lock contention.

## Summary

Keep this open: current main and the latest release still route `requests-in-flight` heartbeat busy skips through the shared 1 second wake retry path, and the open linked PR is the implementation candidate rather than a reason to close the issue early.

## What This Changes

The issue asks OpenClaw to stop retrying requests-in-flight heartbeat skips after about one second because that can let heartbeats grab the session lock immediately after active Telegram and similar channel turns.

## Best Possible Solution

Keep this issue as the canonical bug report until https://github.com/openclaw/openclaw/pull/89989 or an equivalent narrow heartbeat wake-layer fix is reviewed and merged; keep broader activity-based or non-blocking heartbeat work separate.

## Reproduction Assessment

Yes, at source level: current main and v2026.6.11 still route `requests-in-flight` heartbeat busy skips through the shared 1 second wake retry path. I did not run a live Telegram, Feishu, or WebChat reproduction in this read-only review.

## Solution Assessment

Yes for the near-term direction: separating the requests-in-flight retry cadence in the heartbeat wake layer addresses the reported regression without reintroducing the old full-interval drift. Broader activity-based or non-blocking heartbeat designs should remain separate product work.

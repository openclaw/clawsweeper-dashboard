## Label Justifications

- `impact:message-loss`: Heartbeat contention can delay or suppress visible channel replies while users are actively chatting.
- `impact:session-state`: The failure is rooted in heartbeat scheduling, active run detection, and session/run lock contention.

## Summary

Keep this open: current main and v2026.6.11 still route `requests-in-flight` heartbeat skips through the shared 1 second wake retry path, and https://github.com/openclaw/openclaw/pull/89989 is only an open candidate fix until reviewed and merged.

## What This Changes

The issue reports that the 2026.3.7 heartbeat no-drift fix made `requests-in-flight` skips retry too aggressively and block active Telegram conversations.

## Best Possible Solution

Review and either land or replace https://github.com/openclaw/openclaw/pull/89989 with a narrow wake-layer retry fix that separates `requests-in-flight` cadence from other busy reasons, while keeping idle-timeout and non-blocking heartbeat redesigns separate.

Yes, at source level: current main returns `requests-in-flight` busy skips and the wake layer schedules all retryable busy skips after `DEFAULT_RETRY_MS = 1_000`. I did not run a live Telegram, Feishu, or WebChat reproduction.

## Solution Assessment

Yes for the near-term direction: a narrow wake-layer retry separation is more maintainable here than adding a broad config surface or redesigning heartbeat execution. The linked PR still needs its own review and proof before it can close this issue.

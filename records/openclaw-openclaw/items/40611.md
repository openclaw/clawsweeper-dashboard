## Summary

Keep this open: current main and v2026.6.11 still retry `requests-in-flight` heartbeat skips through the shared 1 second wake retry path, and the open linked fix PR is only a candidate until reviewed and merged.

## What This Changes

The issue requests a fix for heartbeat busy-skip retry timing that can let heartbeat runs start immediately after active channel turns and block later Telegram/WebChat/Feishu messages.

## Best Possible Solution

Keep this issue as the canonical bug until https://github.com/openclaw/openclaw/pull/89989 or an equivalent narrow heartbeat wake-layer fix is reviewed, proven, and merged; keep broader non-blocking or idle-timeout heartbeat redesigns separate.

Yes, at source level: current main and v2026.6.11 still route `requests-in-flight` heartbeat busy skips through the shared 1 second wake retry path, and adjacent tests encode that cadence. I did not run a live Telegram, Feishu, or WebChat reproduction in this read-only review.

## Solution Assessment

Yes for the near-term direction: separating the `requests-in-flight` retry cadence in the heartbeat wake layer addresses the reported regression without reintroducing the old full-interval drift. The linked PR still needs its own correctness and proof review before it can be the merge vehicle.

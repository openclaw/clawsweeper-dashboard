## Summary

This PR remains necessary: current review context shows a focused, still-unmerged fix for the narrow case where a requester consumes a descendant completion but normal delivery accounting later treats it as undelivered. The patch is plausibly correct and has focused regression coverage, but it changes the meaning of durable `delivered` state in completion cleanup and still lacks contributor-provided after-fix runtime proof; a maintainer should confirm that lifecycle contract before merge.

## What This Changes

The branch records explicitly requester-consumed descendant completions as delivered, persists that credit, and carries the consumed run IDs through cron fallback and nested subagent-announcement paths.

## System Context

The subagent registry stores completion and delivery state for child runs. Cron fallback and requester announcement paths consume child output, then lifecycle cleanup uses the stored delivery state to decide whether a completion remains pending, is retried, or is settled.

## Best Possible Solution

Keep the credit path narrowly tied to explicit consumed run IDs and obtain a redacted runtime proof that shows the registry row becoming requester-consumed and remaining settled through cleanup; merge only after confirming that requester consumption is the intended durable-delivery contract.

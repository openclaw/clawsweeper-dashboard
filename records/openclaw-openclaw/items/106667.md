## Summary

Current main already serializes and debounces phase changes within each status-reaction controller, but that controller has no shared per-account or per-channel budget across many inbound messages. Keep this issue open as a plausible channel-reliability gap, while requiring a focused burst reproduction before choosing a cross-channel implementation.

## What This Changes

Add bounded cross-message throttling for automatic channel status reactions so reaction bursts cannot consume provider capacity needed for message delivery.

## Best Possible Solution

Use a bounded, keyed, best-effort reaction scheduler at the channel transport/account boundary: coalesce stale updates per message, prioritize or preserve terminal state, drop superseded nonterminal work under pressure, and keep critical message delivery on an independent path while provider adapters own retry-after handling.

No, not yet at high confidence. Source shows only per-controller coalescing and an immediate queued reaction, but a focused current-main burst test must prove the cross-message call rate and its effect on the same provider's message-send capacity.

## Solution Assessment

No, the suggested generic debounced queue is not the best fix because ordinary controller debouncing already exists and provider rate-limit semantics belong to transport owners. The narrow maintainable direction is a bounded keyed scheduler with provider-specific backoff and explicit delivery-priority tests.

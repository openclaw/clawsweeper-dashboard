## What This Changes

Prevent a cron job’s agent-controlled webhook destination from receiving the operator’s configured cron webhook bearer token unless the destination is explicitly trusted by the operator.

## System Context

Cron jobs can request webhook delivery after an agent run. The Gateway turns the job’s delivery destination and operator cron configuration into an outbound POST, so this boundary determines whether an operator credential accompanies a job-supplied URL.

## Architecture Diagram

flowchart LR
  A[Agent turn or cron update] --> B[Cron job record]
  C[Operator cron configuration] --> D[Gateway cron notification]
  B --> D
  D --> E[Webhook destination check]
  E --> F[Bearer header decision]
  F --> G[Outbound webhook POST]

## Best Possible Solution

Adopt a single Gateway-side credential gate at the shared webhook dispatch boundary that sends the bearer only to destinations derived from explicit operator trust, with a visible Doctor/setup recovery path for affected existing job-record receivers.

Rationale: Both choices materially affect existing operators: fail-closed protects the SecretRef boundary but requires an upgrade action, while compatibility-first retains a path for an agent-influenced job record to route the credential externally.

Options:

- **Fail closed with guided recovery (recommended):** Withhold the bearer for job-record destinations unless an operator-owned allowlist permits the host, and provide Doctor and runtime guidance for the required configuration.
- **Preserve compatibility by default:** Continue attaching the bearer when no allowlist is configured, while documenting and recommending an explicit opt-in host restriction.
- **Pause the rollout design:** Keep the issue open without implementation until a narrower trust model avoids both the disclosure and an upgrade-time authentication break.

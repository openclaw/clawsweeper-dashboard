## Summary

Keep open: current main and v2026.6.11 still only partially satisfy the request. Memory-core pre-compaction flush now uses `agents.defaults.userTimezone`, but the bundled `session-memory` hook still formats filenames, fallback HHMM slugs, and `# Session` headers from the gateway host/`TZ` local timezone, so changing that shipped artifact contract needs maintainer product approval.

## What This Changes

Request that memory artifact filenames and header timestamps respect `agents.defaults.userTimezone`, or a dedicated memory timezone, instead of always using UTC or host-local time.

## Best Possible Solution

Maintainers should decide whether bundled session-memory artifacts join the `userTimezone` contract; if accepted, reuse existing timezone helpers for the date, fallback HHMM slug, and header, then update focused tests and docs without adding a new knob unless explicitly approved.

## Maintainer Decision

Required: true

Question: Should bundled session-memory artifacts use `agents.defaults.userTimezone` instead of the gateway host timezone for filename date, fallback HHMM slug, and `# Session` header?

Rationale: Current docs and shipped behavior say session-memory uses host local dates, while memory-core auto-flush already uses configured user timezone; choosing the permanent artifact contract affects upgrade compatibility and config scope.

Owner confidence: medium

Options:

- **Extend userTimezone to session-memory (recommended):** Implement the narrow behavior change with existing configured-timezone helpers and update session-memory tests/docs, accepting the filename/header shift for host/user timezone mismatches.
- **Keep host-local session-memory:** Close or reframe the request and keep docs explicit that session-memory artifacts follow the gateway host timezone while auto-flush uses configured user timezone.
- **Add a memory-specific timezone knob:** Introduce a dedicated setting only if maintainers want memory artifacts decoupled from both host-local and `userTimezone`, with schema/docs/upgrade proof.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: set host `TZ` differently from `agents.defaults.userTimezone`, trigger bundled `session-memory` on `/new` or `/reset`, and the handler formats filenames and headers from host/`TZ` rather than the configured user timezone.

## Solution Assessment

Unclear until maintainers confirm the product contract. The narrowest maintainable fix, if accepted, is to reuse existing configured-timezone helpers in `session-memory`; a separate memory timezone config would be broader and needs stronger justification.

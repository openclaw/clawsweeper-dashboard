## Summary

This remains a concrete Google Meet recovery bug: the tool and CLI can invoke an untargeted recovery path that selects an unrelated tab in the shared OpenClaw Chrome profile, grants capture permissions, and runs join/status logic. The report provides a focused real-stack reproduction and identifies that the existing ownership guard is bypassed by the tool-facing caller; the earlier merged recovery PRs improve ranking and talk-back behavior but do not establish caller ownership. Likely related people: steipete (high confidence), whose recent meeting-bot extraction and recovery hardening commits own the shared controller and Google Meet recovery paths; Peter Steinberger (medium confidence), as the same history’s feature author identity where commit metadata does not expose a separate handle.

## What This Changes

Make Google Meet `recover_current_tab` refuse to attach to an unowned Meet tab when the caller supplies neither a meeting URL nor session ownership state.

## System Context

The Google Meet plugin exposes a tool and CLI recovery action that delegate to the shared meeting-bot browser controller. That controller enumerates Chrome tabs, selects a recoverable meeting, then focuses it, prepares browser permissions, and runs the platform’s inspection/join script.

## Architecture Diagram

flowchart LR
  A[Agent tool or CLI] --> B[Google Meet runtime]
  B --> C[Chrome or node transport]
  C --> D[Meeting tab selection]
  D --> E{URL or owned target?}
  E -->|owned or URL match| F[Focus and inspect tab]
  E -->|neither| G[Return no owned tab]
  F --> H[Permission and join-status actions]

## Best Possible Solution

Fail closed for the public untargeted recovery action: only recover a tab matched by a caller-supplied Meet URL or an ownership token tracked for that session, return a no-owned-tab result otherwise, and add regressions for Chrome, Chrome-node, and the CLI path.

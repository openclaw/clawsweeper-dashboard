## Summary

Keep open: current main and latest release still do not implement a provider-level `models.providers.<id>.enabled` contract, and the linked implementation attempts are closed unmerged. The remaining work is valid but needs maintainer product direction for the new public config surface and disabled-primary/fallback semantics.

## What This Changes

Add a provider-level `enabled` boolean under `models.providers.<id>` so operators can preserve provider config while excluding that provider from model resolution, generated model catalogs, fallback candidates, and status output.

## Best Possible Solution

Approve one shared provider eligibility contract that defaults omitted values to enabled, preserves disabled config blocks, and consistently gates schema, models.json planning, fallback, catalog/listing, status/probe output, docs, and focused tests.

## Reproduction Assessment

Yes, at source level: the strict provider config type/schema does not include `enabled`, and planning, fallback, catalog, and status paths consume configured providers without a disabled-provider eligibility gate. I did not run a live config because this review is read-only.

## Solution Assessment

Unclear pending maintainer product direction. A provider-level flag is plausible, but the maintainable fix should be a shared provider eligibility contract rather than scattered per-consumer filters.

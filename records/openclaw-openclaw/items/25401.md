## Summary

Keep open: current main and latest release still do not define a provider-level `models.providers.<id>.enabled` contract, and both linked implementation attempts are closed unmerged. The remaining work is real, but it needs maintainer product direction because it adds a public config surface and changes provider/fallback eligibility semantics.

## What This Changes

Request a provider-level `models.providers.<id>.enabled` flag that preserves provider config while excluding disabled providers from model resolution, fallback, and status output.

## Best Possible Solution

Approve one shared provider eligibility contract that defaults omitted values to enabled, preserves disabled config blocks, and consistently gates schema, models.json planning, fallback, catalog/listing, status/probe output, docs, and focused tests.

## Reproduction Assessment

Yes, at source level: current main lacks a provider-level `enabled` type/schema field, and the planning, fallback, catalog, and status paths consume configured providers without a disabled-provider gate. I did not run a live config because this review is read-only.

## Solution Assessment

Unclear pending maintainer product direction. A provider-level flag is plausible, but the best implementation should be a shared eligibility contract rather than scattered per-consumer filters.

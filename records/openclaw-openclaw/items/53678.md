## Summary

Keep open: current main and the latest release still expose the source-channel timestamp in agent-visible inbound metadata, but not a Gateway receipt timestamp. The related Discord, LINE, and iMessage reports reinforce the diagnostic need, but adding this field would define a cross-channel SDK/prompt metadata contract that needs maintainer product/API direction.

## What This Changes

Request to add a Gateway-received timestamp to agent-visible inbound metadata so agents can distinguish channel delivery delay from processing latency.

## Best Possible Solution

Define one generic Gateway receipt timestamp contract, then propagate it from channel ingress into inbound context formatting with focused cross-channel coverage.

Options:

- **Add a generic receipt timestamp (recommended):** Expose a single cross-channel field such as `gatewayReceivedAt` in the chosen metadata block and carry it through SDK/channel ingress with tests for at least one durable and one direct path.
- **Keep timing in diagnostics only:** Do not add agent-visible metadata and instead solve latency attribution through Gateway/channel stage logs or trace events.
- **Leave it to channel plugins:** Let each plugin expose its own receipt timing, accepting inconsistent field names and weaker cross-channel comparability.

I did not run a live latency scenario because the requested behavior is an absent cross-channel metadata field rather than an intermittent runtime failure.

## Solution Assessment

Unclear until maintainers choose the public contract. A generic cross-channel receipt timestamp is the maintainable direction, but the exact field name, trust block, and format should be decided before implementation.

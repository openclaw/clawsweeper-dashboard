## Summary

Keep open: current main still exposes only the source-channel message timestamp in generic inbound and agent-visible metadata, while internal receive-time fields remain queue/ack state and are not propagated to agents. The request is useful but requires a maintainer API/product decision because it would define a cross-channel timing contract.

## What This Changes

The issue requests a Gateway-received timestamp in inbound metadata so agents can distinguish source-channel delivery delay from OpenClaw processing latency.

## Best Possible Solution

Define one additive generic ingress timing contract, reuse existing internal receive-time sources where available, and expose it consistently through inbound context, agent-visible metadata, docs, and focused tests.

## Reproduction Assessment

Yes, from source inspection: current main accepts and projects a source `timestamp`, but no generic Gateway receipt timestamp reaches the inbound context or agent-visible conversation metadata. I did not run a live channel flow in this read-only review.

## Solution Assessment

Unclear until maintainers choose the public contract. The requested field is plausible, but the maintainable fix should be a single additive generic timing contract rather than a one-channel or prompt-only patch.

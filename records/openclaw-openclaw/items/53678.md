## Summary

Keep open: current main and the latest release still expose the source-channel timestamp in generic inbound agent metadata, but not a Gateway-received timestamp. The request is valid and source-reproducible, but the field name, timestamp semantics, and propagation boundary are cross-channel API/product decisions.

## What This Changes

Request adds a Gateway-received timestamp field to inbound metadata so agents can distinguish channel delivery delay from processing latency.

## Best Possible Solution

Define one additive generic ingress timing contract and expose it consistently through inbound context, agent-visible metadata, SDK/docs, and focused cross-channel tests.

- **Keep Timing Internal:** Expose receive-to-dispatch timing in logs, diagnostics, or telemetry instead of adding another agent-visible prompt metadata field.
- **Defer To Channels:** Let individual channel plugins add timing where needed, accepting less consistent cross-channel latency analysis.

## Reproduction Assessment

Yes, at source level. Current main and `v2026.6.11` carry only the source `Timestamp` into generic inbound context and conversation metadata, while receive-time state is internal and not agent-visible.

## Solution Assessment

Unclear until maintainers choose the public contract. A generic cross-channel receipt timestamp is the maintainable direction, but the exact field name, trust block, and format should be decided before implementation.

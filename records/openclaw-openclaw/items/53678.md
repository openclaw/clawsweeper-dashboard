## Summary

Keep open: current main and the latest release still do not expose Gateway receive time in the generic inbound or agent-visible metadata path. Internal receive-time state, telemetry counters, and channel-specific timing exist, but they do not satisfy the requested per-message agent metadata contract.

## What This Changes

Request to expose a Gateway-received timestamp alongside source message timestamps in inbound metadata for latency attribution.

## Best Possible Solution

Define one additive generic ingress timing contract, reuse internal receive-time facts where available, and expose it consistently through inbound context, agent-visible metadata, docs, and focused tests.

## Reproduction Assessment

Yes. Source inspection on current main shows the generic inbound context accepts only source `timestamp` and prompt metadata renders only `conversationInfo.timestamp`, while targeted searches find no `receivedAt` or `gatewayReceivedAt` in the public inbound metadata paths.

## Solution Assessment

Unclear until maintainers choose the public contract. The requested field is plausible, but the maintainable solution should be one additive generic timing contract rather than a per-channel or prompt-only patch.

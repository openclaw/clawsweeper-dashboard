## Summary

Keep open. Current main and v2026.6.11 only partially cover the request through the default-off admin HTTP RPC plugin: health/status and agents.list are available when enabled, but HTTP access to session list/detail data is still missing and needs an explicit API/security-boundary decision.

## What This Changes

Request lightweight bearer-authenticated HTTP endpoints for health, agents, session listing, and session detail queries to avoid polling the slow CLI or writing a WebSocket client.

## Best Possible Solution

Approve one authenticated HTTP query surface, preferably reusing admin HTTP RPC or a thin REST adapter over existing Gateway handlers, with docs, auth/scope tests, and no duplicated session logic.

Question: Should OpenClaw expose read-only session list/detail data through the existing default-off admin HTTP RPC plugin, through new dedicated REST GET endpoints, or keep this data on WebSocket/CLI surfaces for now?

Rationale: The source gap is clear, but exposing session data over HTTP changes a security-sensitive operator API boundary and creates a public integration contract.

Likely owner: steipete

Owner reason: This account authored the current admin HTTP RPC plugin and docs that define the relevant HTTP operator boundary.

Owner confidence: high

Options:

- **Extend admin HTTP RPC allowlist (recommended):** Add read-only session query methods to the default-off admin HTTP RPC plugin with docs and route/auth tests, reusing the existing trusted-operator surface.
- **Add dedicated REST endpoints:** Create thin authenticated GET routes for sessions and agents if maintainers want REST semantics instead of JSON-RPC for web integrations.
- **Defer HTTP session exposure:** Keep session list/detail access on WebSocket and CLI until maintainers are ready to own a broader HTTP control-plane contract.

## Reproduction Assessment

Yes for the source API gap. Current main exposes only partial HTTP access through health/status/agents paths, while session list/detail methods exist as Gateway RPC handlers and are not HTTP-exposed.

## Solution Assessment

Unclear until maintainers choose the API and security shape. The narrow maintainable answer is to reuse the existing admin HTTP RPC plugin or add a thin REST adapter over existing handlers, not to duplicate session query logic.

## Summary

Keep open. Current main partially covers the request through the default-off Admin HTTP RPC plugin, but it still does not expose session list/detail queries over HTTP, and that remaining session-data surface needs an explicit product/security decision.

## What This Changes

Request to add lightweight bearer-authenticated HTTP endpoints for read-only Gateway queries such as session list/detail and agent list, avoiding CLI cold start or WebSocket client setup.

## Best Possible Solution

Approve one authenticated HTTP query surface, preferably by extending the default-off Admin HTTP RPC plugin with read-only session query methods plus docs and auth/scope tests, while avoiding duplicated session-store logic.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw expose read-only session list/detail data through the existing default-off Admin HTTP RPC plugin, through new dedicated REST GET endpoints, or keep that data on WebSocket/CLI surfaces for now?

Rationale: The source gap is clear, but exposing session data over HTTP changes a security-sensitive operator API boundary and creates a public integration contract that automation should not choose alone.

Likely owner: steipete

Owner reason: This choice expands the Admin HTTP RPC and Gateway HTTP security boundary that steipete most directly touched in recent merged history.

Owner confidence: high

Options:

- **Extend Admin HTTP RPC allowlist (recommended):** Add read-only session query methods to the default-off Admin HTTP RPC plugin with explicit docs, auth/scope tests, and no duplicated session-store logic.
- **Add dedicated REST endpoints:** Create thin authenticated GET routes for session and agent queries if maintainers want REST semantics instead of JSON-RPC for web integrations.
- **Defer HTTP session exposure:** Keep session list/detail access on WebSocket and CLI until maintainers are ready to own a broader HTTP session-data contract.

## Reproduction Assessment

Yes, at source level. Current main exposes only partial HTTP access through the default-off Admin HTTP RPC plugin, while session list/detail methods exist as Gateway RPC handlers and are not HTTP-exposed.

## Solution Assessment

Unclear until maintainers choose the API and security shape. The narrow maintainable path is to reuse the existing Admin HTTP RPC plugin or add a thin REST adapter over existing handlers, not to duplicate session query logic.

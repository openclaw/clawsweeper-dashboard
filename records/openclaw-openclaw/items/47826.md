## Summary

Keep open. Current main and the latest release only partially cover the request through the default-off admin HTTP RPC plugin: `health`, `status`, and `agents.list` are available when enabled, but HTTP session list/detail access is still not exposed.

## What This Changes

The issue requests lightweight authenticated HTTP access to common Gateway read queries, especially sessions, agents, session detail, and health, without CLI cold-start or WebSocket client overhead.

## Best Possible Solution

Approve one authenticated HTTP query surface that reuses existing Gateway session handlers, documents the security contract, and avoids duplicating session business logic.

Rationale: The source gap is clear, but exposing session data over HTTP changes a security-sensitive operator API boundary and creates a public integration contract.

Owner confidence: high

Options:

- **Extend admin HTTP RPC allowlist (recommended):** Add read-only session query methods to the default-off admin HTTP RPC plugin with route/auth/docs tests, reusing the existing trusted-operator plugin surface.
- **Add dedicated REST endpoints:** Create thin authenticated GET routes for sessions and agents if maintainers want REST semantics instead of JSON-RPC for web integrations.
- **Defer HTTP session exposure:** Keep session list/detail access on WebSocket and CLI until maintainers are ready to own a broader HTTP control-plane contract.

## Reproduction Assessment

Yes, at source level. Current main and `v2026.6.11` expose only partial HTTP access through health/status/agents paths, while session list/detail methods exist only as Gateway RPC handlers and are not HTTP-exposed.

## Solution Assessment

Unclear until maintainers choose the API and security shape. The narrow maintainable answer is to reuse the existing admin HTTP RPC plugin or add a thin REST adapter over existing handlers, not to duplicate session query logic.

## Summary

Keep open. Current main and v2026.6.11 only partially address the request through the default-off admin HTTP RPC plugin: `health`, `status`, and `agents.list` are available when enabled, but HTTP session list/detail access is still not exposed.

## What This Changes

Request to add lightweight bearer-authenticated HTTP endpoints for common Gateway read queries such as sessions list/detail, agents list, and health/status.

## Best Possible Solution

Approve one authenticated HTTP query surface that reuses existing Gateway `sessions.*` and `agents.list` handlers, documents the security contract, and avoids duplicating session business logic.

Rationale: The source gap is clear, but exposing session data over HTTP changes a security-sensitive operator API boundary and creates a public integration contract.

Owner confidence: high

Options:

- **Extend admin HTTP RPC allowlist (recommended):** Add read-only session query methods to the default-off admin HTTP RPC plugin with docs and tests, reusing the existing trusted-operator plugin surface.
- **Add dedicated REST endpoints:** Create thin authenticated GET routes for sessions and agents if maintainers want REST semantics instead of JSON-RPC for web integrations.
- **Defer HTTP session exposure:** Keep session list/detail access on WebSocket and CLI until maintainers are ready to own a broader HTTP control-plane contract.

## Solution Assessment

Unclear until maintainers choose the API and security shape. The narrow maintainable answer is to reuse the existing admin HTTP RPC plugin or add a thin REST adapter over existing handlers, not to duplicate session query logic.

Question: Should configured `models.providers.*.models[*].input` accept audio/video as valid metadata, reject them for chat/runtime model inputs, or move them behind a separate explicit capability/override contract?

Rationale: Current main intentionally accepts and preserves audio/video metadata, while docs and several runtime paths only define text/image behavior; tightening validation without choosing the contract would break existing config/type behavior.

Likely owner: steipete

Owner reason: The related history shows broad ownership across provider catalog normalization and media routing, which is where the product/API contract needs to be settled.

Owner confidence: high

Options:

- **Set an explicit capability contract (recommended):** Define whether audio/video live in `input`, `mediaInput`, or an override-gated field, then update schema, docs, runtime selection, and tests together.
- **Reject unsupported modalities now:** Tighten configured model input validation to text/image and add any needed doctor migration or operator warning for existing audio/video configs.
- **Keep broad metadata acceptance:** Document audio/video as accepted metadata and add narrower runtime diagnostics/cross-checks only where a declared capability is actually used for routing.

## Reproduction Assessment

Yes, at source level. Current main accepts audio/video configured model inputs and can trust configured image metadata without a catalog-capability cross-check; I did not run a live invalid-provider deployment in this read-only review.

## Solution Assessment

No, not as a blanket schema-only rejection. The best fix needs a maintainer decision on whether audio/video are valid model metadata, unsupported runtime capabilities to reject, or values that need an explicit override contract.

## Summary

Keep open: current main still does not implement a capability-aware guardrail for configured model inputs, and the related open PRs mostly address the opposite generated-catalog audio/video acceptance problem rather than rejecting unsupported user-declared capabilities.

## What This Changes

Add validation guardrails, tests, and docs so unsupported `models.providers.*.models[*].input` modality declarations fail before deployment.

## Best Possible Solution

Define one canonical model-input capability authority, then align schema, exported types, registry validation, media-understanding selection, tests, docs, and any needed doctor migration around that contract.

## Reproduction Assessment

Yes, source inspection is enough to reproduce the gap: current main accepts audio/video configured model inputs and can trust configured image metadata without a catalog-capability cross-check. I did not run a live invalid-provider deployment in this read-only review.

## Solution Assessment

No, a blanket schema rejection is not yet the best fix. Maintainers first need to decide whether audio/video are valid model metadata, should be clamped for specific runtime paths, or require an explicit capability-override contract.

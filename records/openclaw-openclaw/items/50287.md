## Summary

Keep open: current main and v2026.6.11 still do not provide one authoritative guardrail for configured model input capabilities. The focused remaining decision is whether audio/video and user-declared image inputs are valid metadata to preserve, invalid deployment-blocking values, or runtime-gated capabilities.

## What This Changes

The issue requests schema, CI, tests, and docs guardrails that reject unsupported `models.providers.*.models[*].input` modality declarations before deployment.

## Best Possible Solution

Define one canonical model-input capability contract, then align schema, exported types, registry validation, media-understanding selection, tests, docs, and any needed doctor migration around that contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should configured model `input` values treat `audio` and `video` as valid metadata to preserve, invalid deployment-blocking values, or metadata that is valid only behind explicit runtime capability gates?

Rationale: Current main already preserves audio/video in the public config path while another registry path rejects them and media-understanding trusts user-declared image capability, so automation cannot safely choose the permanent contract.

Likely owner: steipete

Owner reason: This handle is the strongest current routing candidate from blame and issue timeline evidence across the schema/type/registry surfaces.

Owner confidence: high

Options:

- **Preserve Metadata, Gate Runtime Use (recommended):** Keep audio/video as valid catalog metadata, but add capability-aware runtime selection/diagnostics and clear docs for which paths can actually consume each modality.
- **Reject Unsupported Inputs:** Tighten configured model validation to fail deployment for unsupported modalities, with migration or doctor guidance for existing configs and generated catalogs.
- **Clamp Catalog Inputs:** Normalize unsupported modalities out of generated/configured catalog rows before registry use, trading metadata fidelity for a simpler text/image runtime contract.

## Reproduction Assessment

Yes, at source level. Current main accepts audio/video in the canonical config schema, rejects them in the session registry schema, and trusts configured image metadata during media-understanding selection; I did not run a live invalid-provider deployment in this read-only review.

## Solution Assessment

No, not as a blanket schema-only rejection. The best fix needs a maintainer decision on whether audio/video are valid model metadata, should be clamped for specific runtime paths, or require explicit capability gating.

## Summary

Keep open: current main still does not implement a capability-aware guardrail for configured model inputs, and this issue is now the canonical tracker for that product/API decision. The source still accepts and preserves audio/video model input metadata, while media-understanding can trust user-declared image capability before catalog validation, so a blanket schema rejection would conflict with current public config behavior and related generated-catalog work.

## What This Changes

The issue asks for schema, tests, CI, and docs guardrails that reject unsupported `models.providers.*.models[*].input` modality configurations before deployment.

## Best Possible Solution

Define one canonical model-input capability authority, then align schema, exported types, registry validation, media-understanding selection, tests, and docs around it with a migration or explicit opt-in path if any current config becomes invalid.

## Reproduction Assessment

Yes, from source inspection: current validation accepts audio/video configured model inputs and provider-catalog tests preserve them, while media-understanding still trusts configured image metadata before catalog validation. I did not run a live invalid-provider deployment in this read-only review.

## Solution Assessment

No, not as a blanket schema rejection yet. The maintainable fix needs a maintainer decision on whether audio/video are valid model metadata, should be clamped for specific runtime paths, or require an explicit capability-override contract.

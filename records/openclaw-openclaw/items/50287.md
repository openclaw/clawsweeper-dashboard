## Summary

Keep open: current main and v2026.6.11 still do not implement a capability-aware guardrail for configured model inputs, and the related open generated-catalog PR addresses the opposite audio/video acceptance path rather than rejecting unsupported user-declared capabilities.

## What This Changes

Request adds validation guardrails, tests, CI failure, and docs for unsupported `models.providers.*.models[*].input` modality declarations.

## Best Possible Solution

Define one canonical model-input capability authority, then align schema, exported types, registry validation, media-understanding selection, tests, docs, and any needed doctor migration around that contract.

## Reproduction Assessment

Yes. Source inspection shows current main accepts audio/video configured model inputs and can trust configured image metadata without a catalog-capability cross-check; I did not run a live invalid-provider deployment in this read-only review.

## Solution Assessment

No, a blanket schema rejection is not yet proven to be the best fix. Maintainers first need to decide whether audio/video are valid model metadata, should be clamped for specific runtime paths, or require an explicit capability-override contract.

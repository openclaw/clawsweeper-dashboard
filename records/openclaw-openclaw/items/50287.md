## Summary

Keep open: current main and the latest release still do not implement a capability-aware guardrail for configured model inputs. The inspected code accepts and preserves audio/video input metadata in the public config path, while related registry/catalog work is pulling in the opposite direction by accepting generated audio/video catalog rows, so this needs a maintainer product/API decision before implementation.

## What This Changes

The issue requests pre-deploy validation guardrails for unsupported `models.providers.*.models[*].input` modality declarations, plus targeted tests and docs.

## Best Possible Solution

Define one canonical model-input capability authority, then align schema, exported types, registry validation, media routing, docs, tests, and any needed doctor migration or override path around that contract.

## Reproduction Assessment

Yes. Source inspection shows current main accepts configured audio/video inputs, preserves them in provider catalog normalization, and lacks a semantic model-capability cross-check; no live invalid-provider deployment was run in this read-only review.

## Solution Assessment

No, a blanket schema rejection is not yet the best fix. Maintainers first need to decide whether audio/video are valid metadata, invalid chat inputs, or values requiring an explicit capability override and migration path.

## Summary

Keep open: current main now accepts and projects richer model-input metadata in more places, but it still lacks a single semantic guardrail for user-declared capabilities, and a schema-only rejection would be a product/API decision rather than a safe cleanup close.

## What This Changes

The issue requests validation guardrails for configured model input modalities so unsupported combinations fail before deployment.

## Best Possible Solution

Define one canonical configured-model capability contract, then align schema, exported types, registry projection, catalog/provider cross-checks, media-routing diagnostics, tests, and docs around that contract.

Rationale: Both paths have compatibility consequences: current schema/types/tests preserve audio/video metadata, while the requested guardrail wants invalid or unsupported combinations to fail early.

Owner confidence: high

Options:

- **Accept Metadata Plus Guardrails (recommended):** Keep audio/video as valid metadata, but add semantic checks and clear diagnostics when a runtime path cannot use those modalities.
- **Reject Unsupported Inputs:** Tighten validation to reject unsupported configured model inputs and add any needed doctor migration or override path for existing configs.
- **Defer Contract Change:** Leave current acceptance/projection behavior until the related media-output and fallback-policy issues settle the broader capability model.

## Reproduction Assessment

Yes, at source level. Current main accepts audio/video configured model inputs, projects runtime inputs down to text/image, documents only text/image semantics, and still has media-routing paths that trust configured image declarations without a capability cross-check.

## Solution Assessment

The direction is useful, but a schema-only rejection is not the best fix. The safer solution is a maintainer-approved capability contract that preserves valid metadata while rejecting or diagnosing unsupported runtime use consistently.

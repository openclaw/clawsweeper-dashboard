## Summary

Keep open: current main still lacks a capability-aware guardrail for `models.providers.*.models[*].input`; the schema accepts audio/video metadata, media selection still trusts configured image capability, and related open work covers adjacent or opposite modality-contract drift rather than this product/API decision.

## What This Changes

Request to add validation, tests, CI failure, and docs for rejecting unsupported configured model input modalities before deployment.

## Best Possible Solution

Define one canonical model-input capability authority, then align schema, exported types, registry validation, media selection, tests, docs, and any required doctor migration or explicit override path around that contract.

## Reproduction Assessment

Yes, at source level: current main accepts audio/video configured model inputs and can trust configured image metadata without a catalog-capability cross-check. I did not run a live invalid-provider deployment in this read-only review.

## Solution Assessment

No, a blanket schema rejection is not yet the best fix. Maintainers first need to decide whether audio/video are valid model metadata, should be clamped for specific runtime paths, or require an explicit capability-override contract.

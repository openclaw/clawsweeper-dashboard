## Summary

Keep open: current main and the latest release still do not provide a capability-aware guardrail for configured model input metadata. The remaining work is a provider/model capability contract decision, especially because current config accepts audio/video while media-understanding still trusts user-declared image capability.

## What This Changes

Add validation guardrails, tests, CI/docs expectations, and operator documentation for unsupported `models.providers.*.models[*].input` modalities.

## Best Possible Solution

Define one canonical model-input capability authority, then align schema, exported types, registry validation, media-understanding selection, tests, docs, and any migration or explicit override path around that contract.

## Reproduction Assessment

Yes, at source level: current main accepts audio/video configured model inputs and media-understanding still trusts configured image metadata before any catalog capability cross-check. I did not run a live invalid-provider deployment in this read-only review.

## Solution Assessment

No, not as a blanket schema rejection yet. The maintainable fix needs a maintainer decision on whether audio/video are valid model metadata, should be clamped for specific runtime paths, or require an explicit capability-override contract.

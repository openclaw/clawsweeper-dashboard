Keep open: current main and v2026.6.11 still do not implement a capability-aware guardrail for configured model inputs, and related open work mostly addresses the opposite generated-catalog audio/video acceptance problem rather than rejecting unsupported user-declared capabilities.

## What This Changes

Add pre-deployment validation, tests, and docs so unsupported `models.providers.*.models[].input` modality declarations fail early.

## Best Possible Solution

Define one canonical model-input capability authority, then align schema, exported types, generated/registry validation, media-understanding selection, tests, docs, and any needed doctor migration around that contract.

## Reproduction Assessment

Yes, source inspection reproduces the gap: current main accepts audio/video configured model inputs and still trusts configured image metadata without a catalog-capability cross-check. I did not run a live invalid-provider deployment in this read-only review.

## Solution Assessment

No, a blanket schema rejection is not yet the best fix. Maintainers first need to decide whether audio/video are valid model metadata, should be clamped for specific runtime paths, or require an explicit capability-override contract.

## Summary

Keep open: current main and the latest release still do not implement a capability-aware guardrail for configured model input metadata, and a direct schema rejection would conflict with the current public config/type contract and preservation tests.

## What This Changes

Add schema, test, CI, and docs guardrails so unsupported `models.providers.*.models[*].input` modality declarations fail before deployment.

## Best Possible Solution

Define one canonical model-input capability authority, then align schema, exported types, registry/catalog validation, media-understanding selection, tests, docs, and any override or migration path around that contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should configured model input modalities be constrained to currently runnable chat/media-understanding inputs, preserved as broad provider metadata, or allowed only behind an explicit capability-override contract?

Rationale: Current code intentionally accepts and preserves audio/video metadata while runtime and docs still mostly consume text/image semantics, so automation cannot safely choose a stricter contract without breaking existing config expectations.

Likely owner: Vincent Koc

Owner reason: Vincent is the clearest current routing candidate from recent schema, registry, and release-line history across the affected files.

Owner confidence: medium

Options:

- **Capability-aware guardrail with override (recommended):** Preserve broad metadata but reject or warn when a runtime path is about to trust a declared capability that conflicts with known catalog/runtime support, with an explicit override for custom providers.
- **Schema clamp to current runtime inputs:** Tighten `models.providers.*.models[].input` to the runtime-supported set and add migration/docs, accepting the compatibility break for existing audio/video metadata.
- **Metadata-only contract:** Document audio/video as descriptive metadata and avoid new rejection, leaving runtime-specific diagnostics to narrower follow-up issues.

## Reproduction Assessment

Yes, at source level: current main accepts and preserves audio/video configured model inputs while runtime paths still trust declared image metadata. I did not run a live invalid-provider deployment in this read-only review.

## Solution Assessment

No, not as a blanket schema-only rejection. The maintainable fix needs a product/API decision about capability authority and compatibility before code changes are safe.

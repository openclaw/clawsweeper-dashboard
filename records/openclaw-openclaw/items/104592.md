## Label Justifications

- `P1`: The PR addresses a credentialed SSRF path, but its production transport integration leaves a security-relevant DNS-pinning gap.
- `merge-risk: 🚨 security-boundary`: The changed fetch path can appear guarded while an explicit proxy fetch replaces the pinned dispatcher that enforces the network boundary.

## Summary

The PR targets the correct ClawRouter SSRF gap, but it passes the generic provider usage fetch wrapper into a guard that assumes explicit fetch implementations honor its pinned dispatcher. Production proxy fetches replace that dispatcher, so hostname redirects can still escape DNS pinning even though the loopback-literal test passes.

## What This Changes

Routes ClawRouter usage fetching through the shared SSRF-guarded fetch path and adds redirect-blocking coverage.

## Best Possible Solution

Keep the shared SSRF guard, but let it own the production transport or add a shared, explicitly recognized proxy mode; inject the guard rather than an arbitrary fetch for tests, then prove healthy usage and a hostname-based redirect or DNS-rebinding attempt with a controlled server.

- **[P1] Keep the SSRF guard in control of the network transport:** `extensions/clawrouter/usage.ts:97`
  - body: Passing `ctx.fetchFn` here does not guarantee DNS pinning in production. Provider usage can supply `resolveProxyFetchFromEnv()`, whose implementation replaces the guard's `dispatcher` with its own proxy agent, while `fetchWithSsrFGuard` assumes every explicit non-ambient fetch honors that dispatcher. A redirect to a hostname whose resolution changes between preflight and the actual proxy request can therefore still reach a private target; the new `vi.fn` test only covers a loopback literal and takes the mock-only branch. Use a guard-owned production transport or a shared recognized proxy mode, with guard-level injection for tests.

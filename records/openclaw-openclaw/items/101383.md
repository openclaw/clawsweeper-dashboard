- `impact:data-loss`: A rejected or unsettled start write can lose the persisted session start marker needed to recover active session state after restart.

- `maturity:stable`: The affected Gateway runtime surface maps to `gateway-runtime`, which the maturity shortlist reports as M4 Stable.

## Summary

Keep open: current main only logs rejected start lifecycle persistence; it still fire-and-forgets the write and has no start-phase recovery signal, so the central durability concern remains.

## What This Changes

The issue asks OpenClaw to stop dropping Gateway session start lifecycle markers when start-phase persistence rejects or the process exits before the async write settles.

## Best Possible Solution

Move start lifecycle durability to an explicit Gateway owner boundary: persist or verify the start marker before a run is considered recoverable, or record a clear recovery/failure state with regression coverage for rejected writes and restart behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should Gateway start lifecycle persistence become a blocking durability boundary for recoverable runs, or should OpenClaw keep the current best-effort log-only behavior?

Rationale: The current path logs write failures, but making start markers durable could change hot-path latency, failure semantics, and restart-recovery ownership, so automation should not choose that policy silently.

Likely owner: steipete

Owner reason: He merged the current start logging behavior and has recent adjacent ownership across Gateway session lifecycle persistence cleanup.

Owner confidence: high

Options:

- **Design A Bounded Durability Fix (recommended):** Make start marker persistence or an equivalent recovery record part of the admitted-run lifecycle, with tests for rejected writes and restart/crash recovery.
- **Keep Log-Only Semantics:** Accept that start marker loss is diagnosable but not recovered when storage rejects or the process exits before the write settles.
- **Fold Into Broader Restart Recovery:** Track this under a broader restart-recovery redesign if maintainers want one recovery-state model for start, terminal, crash, and cross-boot cases.

## Reproduction Assessment

Yes, at source level: current main still fire-and-forgets start lifecycle persistence and only logs rejection, while the persistence helper propagates write failures. I did not run a live crash/restart replay.

## Solution Assessment

Unclear as a concrete patch: awaiting in the handler is only one possible shape, and the better fix likely needs an explicit Gateway durability boundary for start markers rather than another local catch change.

## Summary

Keep open: this is a narrow, plausible fix for the linked token-auth channel `sessions_spawn` regression, but it still needs real after-fix behavior proof and maintainer attention on the internal synthetic `operator.write` boundary before merge.

## What This Changes

The PR forces in-process subagent Gateway dispatches to use a synthetic operator client and adds a seam test asserting that `agent` dispatch gets `forceSyntheticClient: true`.

## Best Possible Solution

Land the narrow synthetic-client fix after maintainer auth-boundary confirmation and redacted real token-auth `sessions_spawn` proof, while keeping admin-only cleanup pinned to admin scopes.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: the linked token-auth Google Chat report gives concrete failing steps, and current main shows non-admin in-process `agent` dispatch can inherit a caller client without `operator.write`; I did not run a live current-main channel repro.

## Solution Assessment

Is this the best way to solve the issue? Yes as a narrow chokepoint fix: it avoids broader `src/gateway/call.ts` device-identity churn and preserves explicit admin scopes for cleanup, but it is not merge-ready until the synthetic write boundary and real behavior proof are covered.

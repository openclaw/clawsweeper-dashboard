## Summary

Keep open: current main and v2026.6.11 still route dreaming through memory-core as the default/sidecar engine rather than exposing a public dreaming provider protocol. The linked ClawHub plugin is useful for LanceDB users today, and https://github.com/openclaw/openclaw/pull/88504 may add memory role slots, but neither settles the core/plugin-SDK product decision requested here.

## What This Changes

The issue asks OpenClaw to expose a plugin-SDK/runtime dreaming protocol so memory plugins other than memory-core can implement the Light, REM, and Deep consolidation lifecycle.

## Best Possible Solution

Maintainers should either define a public plugin-SDK dreaming provider contract coordinated with memory role-slot work, or explicitly document that generic dreaming orchestration remains plugin-owned through ClawHub packages.

Options:

- **Defer to ClawHub plugins:** Document that alternative memory backends should ship their own dreaming implementations on ClawHub and close this only after maintainers explicitly reject a core protocol.
- **Wait for role-slot landing:** Pause implementation until https://github.com/openclaw/openclaw/pull/88504 lands or closes, then revisit whether memory.dreaming needs a deeper provider interface.

## Summary

This is a credible fix for the linked Slack HTTP regression, but it is not merge-ready: the implementation reuses the relay completion marker and thereby disables OpenClaw retry for already-acknowledged HTTP events, while the PR provides only test-based rather than live behavior proof.

## What This Changes

The PR adds a Plugin SDK helper for independently admitted post-acknowledgement webhook work and uses it to retain Slack HTTP message processing through debounce dispatch.

## Best Possible Solution

Keep the independent gateway work root, but separate “wait for dispatch completion” from “external transport owns redelivery” so Slack HTTP events retain local retry eligibility, then prove a real acknowledged HTTP event reaches an agent reply.

Yes, from source and the linked logs: Slack Bolt returns from the HTTP listener while event processing continues, allowing inherited request admission to be released before debounced gateway work is enqueued. A live current-main reproduction was not run in this read-only review.

## Solution Assessment

No, not as currently implemented. An independent work root is the right lifecycle direction, but `awaitDispatch` must not also tell the retry path that an external relay will redeliver an already-acknowledged Slack HTTP event.

- **[P1] Preserve local retry for acknowledged HTTP events:** `extensions/slack/src/monitor/message-handler.ts:482`
  - body: Passing `awaitDispatch` whenever `runDetachedWork` exists gives every Slack HTTP entry a `dispatchCompletion`. A retryable reply-session initialization conflict can therefore be logged and permanently lose the message. Split dispatch waiting from retry ownership so HTTP entries remain locally retryable.

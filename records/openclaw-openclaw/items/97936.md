## Summary

Keep open. The bug this PR targets is real and paired with an open canonical issue, but the current branch still has credential-scrub ownership gaps: non-env refs can skip `.env` cleanup, and independent key/value sets can still cross-pair. The PR also still needs redacted real behavior proof from an after-fix `openclaw secrets apply --from ...` run.

## What This Changes

The PR changes `src/secrets/apply.ts` to collect migrated env ref IDs and pass them to `.env` scrubbing, with tests for same-value config and auth-profile migrations.

## Best Possible Solution

Add a maintainer-approved target-owned `.env` scrub contract, likely through secret target registry metadata, that pairs each eligible env key only with values owned by that same target or provider across env, file, exec, auth-profile, provider, and plugin targets.

## Reproduction Assessment

Yes, by source inspection and the linked issue proof. I did not execute the write path in this read-only review, but the PR head shows file/exec targets can add migrated values without env keys and the scrubber still receives independent key/value sets.

## Solution Assessment

No. The env-ref-ID filter is a plausible narrow mitigation, but the best fix is an explicit target-owned key/value scrub contract that covers sibling target classes without reintroducing over-scrub or under-scrub cases.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P1] Preserve file and exec cleanup coverage:** `src/secrets/apply.ts:365-367`
  - body: Because `scrubbedEnvKeys` is only populated when `target.ref.source === "env"`, a target migrated to a file or exec SecretRef can add an old plaintext value but no eligible env key, and `scrubEnvFiles` then skips `.env` cleanup entirely. That regresses cleanup for known `.env` secret keys whose values were migrated.
  - confidence: 0.91
- **[P1] Bind scrub keys to their owning values:** `src/secrets/apply.ts:705`
  - body: Passing separate `scrubbedValues` and `scrubbedEnvKeys` still forms a cross product: one target can contribute an env key while another contributes the matching value, causing `scrubEnvRaw` to delete a live env line that was not migrated as that key/value pair. Build a per-env-key value map from the target/provider that owns both sides instead.
  - confidence: 0.9

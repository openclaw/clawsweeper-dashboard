## Summary

Keep open; the PR addresses the right bug class, but the current branch still has two merge-blocking credential scrub defects: env keys are not bound to their owning migrated values, and file/exec migrations can leave stale plaintext `.env` credentials behind.

## What This Changes

The PR changes `secrets apply` to collect migrated env ref IDs for `.env` scrubbing and adds regression tests for same-value provider credential migrations.

## Best Possible Solution

Carry owned `.env` scrub data as env key to migrated value sets, preferably from explicit target or registry ownership, while preserving existing cleanup for file/exec migrations and blocking unrelated same-value deletion.

Yes. Source review shows current `main` has the original global value/key scrub behavior and PR head still computes independent global key and value sets; I did not execute tests because this review is read-only.

## Solution Assessment

No. The branch is a useful partial direction, but the best fix must bind each scrub key to its own migrated values and preserve file/exec cleanup coverage instead of using separate global sets.

Full review comments:

- **[P1] Bind scrub keys to their owning values:** `src/secrets/apply.ts:705`
  - body: This still feeds `scrubEnvRaw` one global value set and one global key set, so a mixed plan can delete `KEY_A=value_from_B` whenever `KEY_A` came from one migrated target and `value_from_B` came from another. The earlier review called for binding each scrub key to its owning migrated values; please carry a `Map<envKey, Set<value>>` or equivalent ownership shape instead of intersecting two independent global sets.
  - confidence: 0.92
- **[P1] Preserve file and exec cleanup coverage:** `src/secrets/apply.ts:697-698`
  - body: Because scrub keys are added only for `target.ref.source === "env"`, a plan that migrates a provider credential from plaintext to a file or exec ref now returns before reading `.env` and leaves the old provider env line behind. Current `main` scrubbed those stale known-secret env values; this security cleanup should remain covered while preventing unrelated same-value deletion.
  - confidence: 0.9

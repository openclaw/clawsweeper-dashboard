## Label Justifications

- `P1`: A real WebChat session workflow can lose model-visible history after restart or stale-session rollover while the UI still shows that history.
- `impact:session-state`: The report is about drift between displayed persisted transcript state and the session context sent to the model.
- `impact:ux-friction`: Affected users can continue only by manually copying prior context into the next prompt, which is a fragile workaround.

## Summary

Keep open: current main still has a source-level gap where WebChat can display restored history but ordinary follow-up sends do not automatically bypass stale-session rollover, and the linked closing fix is still open at https://github.com/openclaw/openclaw/pull/96391.

## What This Changes

Ensure WebChat `chat.send` uses the restored session transcript that `chat.history` displays after gateway/browser restart or idle/daily reset.

## Best Possible Solution

Review and land or replace https://github.com/openclaw/openclaw/pull/96391 with a narrow gateway/session fix that preserves the stored WebChat session for follow-up sends without weakening explicit reset or stale-session policies.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, source-reproducible: current main tests show ordinary sends with a matching WebChat session ID still roll over stale sessions, while the UI path only sends the private reconnect marker for one reconnect-resume case. I did not run a live gateway/browser repro in this read-only review.

## Solution Assessment

Yes, the best fix should stay at the gateway/session boundary because `chat.send` already has the backing session ID and `initSessionState` owns freshness decisions. The open linked PR follows that direction, but it still needs normal PR review for session-state and compatibility safety.

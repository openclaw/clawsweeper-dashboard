## Summary

The PR should remain open because both previously reported delivery blockers remain: the production reply pipeline does not carry the typed progress intent into the new Slack send option, and the suppression policy can discard progress that operators explicitly configured Slack to deliver. The supplied live Slack evidence exercises `sendMessageSlack` directly rather than the normal producer-to-reply-delivery path, so it does not clear those blockers.

## What This Changes

The PR adds typed Slack progress-chrome detection that converts thread-scoped tool progress to reactions, suppresses other progress-only sends, and prevents suppressed sends from advancing normal delivery state.

## Best Possible Solution

Carry the closed progress intent from the producer through `ReplyPayload` and `deliverReplies` into Slack, then react or suppress only internal chrome while preserving configured standalone progress delivery; cover both modes through the real reply pipeline and repeat redacted live Slack proof on the resulting head.

## Summary

Keep this PR open but do not merge it yet: the current patch does not route progress intent through normal Slack reply delivery, and wiring it as written would suppress progress messages that users explicitly configured for separate delivery. The supplied live proof exercises a direct send helper on an older head rather than the affected production route.

## What This Changes

The PR adds Slack-private progress-chrome detection, converts marked thread progress into reactions or suppression, adjusts suppressed-send bookkeeping, and adds focused Slack send tests.

## Best Possible Solution

Make progress disposition a typed upstream policy decision carried through `ReplyPayload`: preview-owned progress may react or suppress, while configured standalone progress remains a normal deliverable message.

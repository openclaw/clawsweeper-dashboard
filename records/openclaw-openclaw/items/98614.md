## Label Justifications

- `P1`: The issue reports a current release regression that blocks channel-triggered `sessions_spawn` multi-agent delegation for token-auth deployments.
- `impact:auth-provider`: The failure is an operator-scope/auth path problem where the `agent` Gateway method lacks `operator.write` in the effective client.
- `impact:message-loss`: The reported channel-triggered delegation fails before the child agent can run or produce the expected completion back to the requester.
- `maturity:stable`: The issue affects the M4 Stable `gateway-runtime` surface, specifically Gateway RPC/session APIs and operator scope enforcement.

## Summary

Keep open: current main still has the token-auth `sessions_spawn` path that can dispatch in process without forcing a synthetic write-scoped client, and the direct candidate fix at https://github.com/openclaw/openclaw/pull/99199 is open but not merged.

## What This Changes

The issue reports a regression where Google Chat-triggered `sessions_spawn` fails with `missing scope: operator.write` on token-auth Gateway deployments after upgrading to v2026.6.11.

## Best Possible Solution

Keep this issue open until https://github.com/openclaw/openclaw/pull/99199 or an equivalent token-auth `callSubagentGateway` fix lands with focused proof, and avoid closing it through the auth-none-only path.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: the report gives concrete token-auth Google Chat steps, and current main shows the in-process `agent` dispatch can inherit a caller client without `operator.write`; I did not run the live channel deployment.

## Solution Assessment

Is this the best way to solve the issue? Yes, the best path is a narrow fix at the `callSubagentGateway` in-process dispatch boundary, such as the open candidate PR, with proof that it preserves the intended auth boundary.

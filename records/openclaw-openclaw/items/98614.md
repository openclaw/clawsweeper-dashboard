## Label Justifications

- `P1`: The issue reports a latest-release regression that blocks channel-triggered `sessions_spawn` multi-agent delegation for token-auth deployments.
- `impact:message-loss`: The failed spawn prevents the child agent run and expected completion from reaching the requester.
- `impact:auth-provider`: The failure is an operator-scope/auth path problem where the effective Gateway client lacks `operator.write` for the `agent` method.
- `maturity:stable`: The affected Gateway RPC/session API and operator scope enforcement path belongs to the M4 Stable `gateway-runtime` surface.

## Summary

Keep open: current main still leaves the token-auth in-process `sessions_spawn` `agent` dispatch able to inherit a channel/plugin client without `operator.write`, and the direct candidate fix at https://github.com/openclaw/openclaw/pull/99199 is open but unmerged.

## What This Changes

The issue requests a fix for a v2026.6.11 regression where token-auth channel-triggered `sessions_spawn` fails with `missing scope: operator.write`.

## Best Possible Solution

Review and land https://github.com/openclaw/openclaw/pull/99199, or an equivalent narrow `callSubagentGateway` fix, with token-auth channel proof and auth-boundary confirmation before closing this issue.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: the report gives concrete token-auth Google Chat steps, and current main shows the in-process `agent` dispatch can inherit a caller client without `operator.write`; I did not run the live channel deployment.

## Solution Assessment

Is this the best way to solve the issue? Yes: the narrowest maintainable path is to fix the `callSubagentGateway` in-process dispatch boundary while preserving explicit admin scopes for admin-only cleanup calls.

## Label Justifications

- `P1`: The issue reports a release regression that blocks channel-triggered `sessions_spawn` multi-agent delegation in token-auth deployments.
- `impact:message-loss`: The failed spawn prevents the child agent run and its completion from reaching the requester.
- `impact:auth-provider`: The failure is caused by Gateway operator-scope selection for an internal `operator.write` call.
- `maturity:stable`: The affected Gateway runtime surface is scored M4 Stable in `qa/maturity-scores.yaml`, including Gateway RPC APIs and operator scope behavior.

## Summary

Keep open: current main still has the token-auth `sessions_spawn` path where the in-process `agent` dispatch can inherit a caller client without `operator.write`, and the direct candidate fix at https://github.com/openclaw/openclaw/pull/99199 is open but unmerged.

## What This Changes

The issue reports a v2026.6.11 regression where channel-triggered token-auth `sessions_spawn` fails with `missing scope: operator.write`.

## Best Possible Solution

Keep this issue open until https://github.com/openclaw/openclaw/pull/99199 or an equivalent token-auth `callSubagentGateway` fix lands with focused auth-boundary review and proof.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: current main starts the subagent through `callSubagentGateway({ method: "agent" })` without explicit scopes, while in-process dispatch can use the scoped caller client and `agent` requires `operator.write`.

## Solution Assessment

Is this the best way to solve the issue? Yes: the narrowest maintainable path is to fix the `callSubagentGateway` in-process dispatch boundary, as the open linked PR attempts, rather than closing through the auth-none-only fixes.

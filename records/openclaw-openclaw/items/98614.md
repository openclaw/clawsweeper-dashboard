## Label Justifications

- `P1`: The issue reports a current release regression that blocks channel-triggered `sessions_spawn` multi-agent delegation for token-auth deployments.
- `impact:message-loss`: The failed spawn prevents the child agent from running and returning the expected delegated result to the requester.
- `impact:auth-provider`: The failure is caused by the effective Gateway client lacking the `operator.write` authorization scope on the `agent` call path.
- `maturity:stable`: The affected Gateway RPC/session surface maps to `gateway-runtime`, which is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main still has the token-auth in-process `sessions_spawn` path that can dispatch `agent` without forcing a synthetic write-scoped client, and the direct candidate fix at https://github.com/openclaw/openclaw/pull/99199 is open but not merged.

## What This Changes

The issue reports a v2026.6.11 token-auth regression where channel-triggered `sessions_spawn` fails with `missing scope: operator.write`.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/99199 or an equivalent narrow `callSubagentGateway` fix with focused auth-boundary proof, then close this issue as implemented.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: the report gives concrete token-auth Google Chat steps, and current main shows the in-process `agent` dispatch can inherit a caller client without `operator.write`; I did not run the live channel deployment.

## Solution Assessment

Is this the best way to solve the issue? Yes, the narrowest maintainable path is to fix the `callSubagentGateway` in-process dispatch boundary so `agent` gets the intended write-scoped operator client without changing unrelated auth-none behavior.

## Label Justifications

- `P1`: The issue reports a current release regression that blocks channel-triggered `sessions_spawn` multi-agent delegation in token-auth deployments.
- `impact:message-loss`: The failed spawn prevents the child agent from running and returning the expected delegated result to the requester.
- `impact:auth-provider`: The failure is an operator-scope/auth path problem where the effective Gateway client lacks `operator.write` for the `agent` method.
- `maturity:stable`: The affected Gateway runtime RPC/operator-scope surface maps to `gateway-runtime`, which is scored M4 Stable in `qa/maturity-scores.yaml`.

## Summary

Keep open: current main still leaves the token-auth channel `sessions_spawn` path dependent on the inherited in-process caller client for non-admin `agent` dispatch, and the direct candidate fix is open but unmerged.

## What This Changes

The issue reports a regression where token-auth Google Chat-triggered `sessions_spawn` fails with `missing scope: operator.write` on v2026.6.11 after working on v2026.6.1.

## Best Possible Solution

Keep this issue open until https://github.com/openclaw/openclaw/pull/99199 or an equivalent token-auth `callSubagentGateway` fix lands with focused proof and auth-boundary review.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: the report gives concrete token-auth Google Chat steps, and current main shows the in-process `agent` dispatch can inherit a caller client without `operator.write`; I did not run the live channel deployment.

## Solution Assessment

Is this the best way to solve the issue? Yes, the best path is a narrow fix at the `callSubagentGateway` in-process dispatch boundary, such as the open candidate PR, with proof that it preserves the intended auth boundary.

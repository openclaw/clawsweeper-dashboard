## Label Justifications

- `P1`: The issue reports a current release regression that blocks channel-triggered `sessions_spawn` multi-agent delegation for token-auth deployments.
- `impact:message-loss`: The failed spawn prevents the child agent run from starting and returning the expected delegated result to the requester.
- `impact:auth-provider`: The failure is an operator-scope authorization problem where the effective client lacks `operator.write` for the Gateway `agent` method.
- `maturity:stable`: The affected Gateway runtime RPC/session and operator-scope surface maps to `gateway-runtime`, which is scored M4 Stable.

## Summary

Keep open: current main still has the token-auth in-process `sessions_spawn` path that can dispatch `agent` without forcing a synthetic write-scoped client, and the direct fix candidate at https://github.com/openclaw/openclaw/pull/99199 is open but unmerged.

## What This Changes

The issue reports a regression where token-auth channel-triggered `sessions_spawn` fails with `missing scope: operator.write` after upgrading from v2026.6.1 to v2026.6.11.

## Best Possible Solution

Keep this issue open until https://github.com/openclaw/openclaw/pull/99199 or an equivalent token-auth `callSubagentGateway` fix lands with focused proof and auth-boundary review.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes at source level: the report gives concrete token-auth Google Chat steps, and current main shows in-process `agent` dispatch can inherit a caller client without `operator.write`; I did not run the live channel deployment.

## Solution Assessment

Is this the best way to solve the issue? Yes, the narrowest maintainable path is at the `callSubagentGateway` in-process dispatch boundary, with proof that the synthetic write-scoped client is the intended internal authorization boundary.

## Label Justifications

- `P1`: The issue reports a current latest-release regression that blocks channel-triggered `sessions_spawn` multi-agent delegation in token-auth deployments.
- `impact:message-loss`: The failed spawn prevents the child agent from running and returning the expected delegated result to the channel requester.
- `impact:auth-provider`: The failure is in the effective Gateway operator-scope/auth path for the `agent` method, which lacks `operator.write` on the inherited client.
- `maturity:stable`: The affected Gateway runtime surface is scored M4 Stable in `qa/maturity-scores.yaml`, including Gateway RPC and auth/permission categories.

## Summary

Keep open: current main still allows the token-auth `sessions_spawn` path to dispatch `agent` in process without forcing a synthetic write-scoped client, and https://github.com/openclaw/openclaw/pull/99199 is the active open candidate fix rather than a merged implementation.

## What This Changes

The issue reports a regression where channel-triggered `sessions_spawn` on a token-auth local Gateway fails with `missing scope: operator.write` after upgrading from v2026.6.1 to v2026.6.11.

## Best Possible Solution

Keep this issue open until https://github.com/openclaw/openclaw/pull/99199 or an equivalent narrow `callSubagentGateway` token-auth fix lands with focused auth-boundary review and proof.

## Reproduction Assessment

Yes, source-reproducible: the report gives concrete token-auth Google Chat steps, and current main shows the in-process `agent` dispatch can inherit a caller client without `operator.write`. I did not run a live Google Chat deployment in this read-only review.

## Solution Assessment

Yes, the best path is a narrow fix at the `callSubagentGateway` in-process dispatch boundary; the closed auth-none PR does not cover the token-auth path, while the open candidate PR targets the relevant source behavior.

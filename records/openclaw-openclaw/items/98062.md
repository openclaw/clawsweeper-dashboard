## Summary

Keep open: current main still intentionally forces iOS manual connections for `.ts.net` and `100.64.0.0/10` hosts through TLS, while the reported direct Tailnet Gateway is plain `ws://` and the secure Serve/TLS route still needs a maintainer-approved trust path. Recent merged work improves LAN/Tailnet route advertisement, but it does not close the raw CGNAT/TLS policy gap reported here.

## What This Changes

The issue reports that the iOS app cannot connect to a Gateway over Tailscale CGNAT or Tailscale Serve because remote iOS paths require secure WebSocket/TLS behavior that the current Gateway setup does not satisfy.

## Best Possible Solution

Define one secure iOS Tailnet path and make it work end to end: preferably managed Tailscale Serve/MagicDNS WSS with visible fingerprint/trust recovery and clear diagnostics, or an explicit maintainer-approved Tailnet plaintext policy if that risk is accepted.

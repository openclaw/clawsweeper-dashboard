## Label Justifications

- `P1`: A gateway restart can leave an established ACP-bound channel unable to deliver subsequent user messages until technical manual recovery.
- `impact:message-loss`: Messages routed to the stale ACP binding may receive no reply or only a delayed failure.
- `impact:session-state`: Persisted ACP process and session identity outlive their runtime owner and are then treated as usable state.
- `impact:crash-loop`: The reported failure follows gateway restart and can leave the ACP workflow hanging indefinitely at process level.

## Summary

Keep open: current main still accepts persisted ACP metadata as ready without proving the runtime owner is live, while the reported recovery failure can suppress replies after a restart. The report is credible, but the proposed core-level PID check crosses the ACPX ownership boundary and needs current-main live verification before implementation.

## What This Changes

Detect and recover ACP binding sessions whose persisted runtime record references a process that died during a gateway restart.

## Best Possible Solution

Validate the gateway-restart path on current main, then make the ACPX runtime reject or invalidate a persisted process record when its lease or process owner is no longer live, perform one bounded fresh-session ensure, and cover both successful recovery and bounded failure without adding PID knowledge to the generic core manager.

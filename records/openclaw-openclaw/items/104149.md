## Label Justifications

- `P1`: The patch fixes a real provider workflow but can replace fast failure/fallback with unexpectedly long in-turn waits for existing users.
- `merge-risk: 🚨 compatibility`: The proposed delay resolver ignores the existing configured maximum server-requested retry delay and changes upgrade behavior for current retry settings.
- `merge-risk: 🚨 availability`: A single 429 can keep an agent turn sleeping for up to 24 hours, delaying fallback and making the session appear stalled.

## Summary

The bug and transport plumbing are valid, and the PR has convincing live proof, but the retry-delay policy is not safe to merge yet: it bypasses the existing maximum provider-requested wait and its parser drops overflowed numeric hints instead of applying the advertised safety clamp.

## What This Changes

The PR preserves Anthropic HTTP status and Retry-After metadata on transport errors, adds it to AssistantMessage, and uses it as a lower bound for AgentSession auto-retry delay with focused tests.

## Best Possible Solution

Keep the shared structured error metadata, but centralize Retry-After parsing and make AgentSession honor the existing provider maximum: use the server delay only when it is valid and within maxRetryDelayMs, otherwise stop auto-retrying so normal failure/fallback handling can proceed, while leaving the configured exponential schedule unchanged.

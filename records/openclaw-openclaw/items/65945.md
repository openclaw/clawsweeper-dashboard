## Summary

Keep open: current main and v2026.6.11 still do not auto-forward Node `agent.request` image attachments to IM delivery, and the remaining request is a new gateway/media relay contract that needs maintainer security and product direction.

## What This Changes

Request auto-forwarding image attachments from Node `agent.request` events to IM recipients when delivery is enabled.

## Best Possible Solution

Approve a narrow explicit opt-in protocol/API design with authorization, media limits, audit, target scoping, and agent override semantics, or document direct send/message-tool surfaces as the supported relay path.

Rationale: This changes a gateway-to-channel trust boundary and the current agent-controlled delivery contract, so code inspection cannot safely choose the permanent behavior without maintainer intent.

Likely owner: vincentkoc

Owner confidence: medium

Options:

- **Design explicit opt-in relay (recommended):** Add a protocol field only after defining route authorization, size/type limits, audit metadata, and how agent-authored media suppresses or replaces forwarded attachments.
- **Keep agent-controlled delivery:** Reject auto-forwarding on `agent.request` and document direct `send` or message-tool media delivery for dumb relay workflows.
- **Add automatic fallback forwarding:** Append original attachments whenever the agent emits no media, accepting a broader trust-boundary change and changed suppression semantics.

## Reproduction Assessment

Yes. Source inspection on current main and v2026.6.11 shows attachments become agent input while final delivery uses only media present in agent reply payloads; no live IM run was performed.

## Solution Assessment

Unclear. A narrow explicit opt-in is safer than automatic fallback forwarding, but maintainers must decide whether `agent.request` should become a media relay or whether direct send/message-tool surfaces remain the supported path.

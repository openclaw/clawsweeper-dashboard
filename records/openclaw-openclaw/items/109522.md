## Label Justifications

- `P1`: The requested API targets an active relay fan-out regression associated with gateway stalls, OOM pressure, and broken channel workflows on real small-host deployments.
- `impact:crash-loop`: Related live reports describe repeated resource exhaustion, severe event-loop starvation, gateway instability, and kernel OOM behavior from concurrent relay processes.
- `impact:message-loss`: The related production report includes inbound Telegram processing timing out and being marked failed while relay processes saturated the host.

## Summary

Current main still lacks per-tool registration scope, and the merged loop-only opt-out does not solve relay fan-out when hooks, policies, or result middleware are active. The proposal targets a real P1 failure mode, but the public plugin API shape and fail-closed matching contract need maintainer direction before implementation.

Likely related people: pashpashpash (high confidence, introduced the native relay path), marchpure (high confidence, recent loop-relay work), and steipete (medium confidence, recent fallback behavior work).

## What This Changes

Add exact tool-name scopes to hook, trusted-tool-policy, and tool-result-middleware registrations, then aggregate those scopes into Codex native PreToolUse and PostToolUse matchers.

## Best Possible Solution

Define one OpenClaw-owned exact tool-name scope contract across hooks, trusted policies, and Codex result middleware; apply it to in-process dispatch and relay aggregation, encode names as escaped anchored Codex regex alternatives, preserve omitted scope as byte-identical match-all behavior, and prove both policy coverage and reduced subprocess counts in a live Codex run.

## Maintainer Decision

Question: Should OpenClaw add a public exact-tool-name scope contract across plugin hooks, trusted-tool policies, and Codex tool-result middleware to control native relay installation?

Rationale: This changes compatibility-sensitive plugin API and security-policy routing, while unresolved choices include naming, tool aliases, dynamic-tool double dispatch, unscoped-union semantics, fallback behavior, and whether a resident relay architecture should be preferred.

Likely owner: pashpashpash

Owner confidence: high

Options:

- **Approve exact-name scope API (recommended):** Add one typed exact-name scope field across all relevant registrations, with deterministic aggregation and safely escaped Codex matcher serialization.
- **Keep scoping internal:** Expose no new plugin contract and derive relay scope only from existing owner-specific metadata where OpenClaw can prove complete coverage.
- **Defer to resident relay:** Avoid expanding the SDK now and prioritize an in-process or resident relay design that removes per-call process spawning more generally.

## Reproduction Assessment

Yes at source level: current registration metadata produces event-wide relay activation, while pinned Codex code filters matching hook groups before handler execution. A live current-main subprocess-count reproduction was not run during this read-only review.

## Solution Assessment

Unclear pending product direction. Moving the filter to the spawn gate is the right performance boundary, but the safest API should represent exact OpenClaw tool names and derive escaped, anchored upstream matchers rather than expose Codex regex semantics directly.

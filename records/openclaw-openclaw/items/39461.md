## Summary

Keep open: current main and the latest release still ignore `QQBOT_DATA_DIR` while QQBot diagnostics tells Windows users to set it, and https://github.com/openclaw/openclaw/pull/78253 is an open implementation candidate rather than a merged fix.

## What This Changes

The issue requests QQBot to honor `QQBOT_DATA_DIR` for its data directory so Windows users can avoid non-ASCII or space-containing home paths.

## Best Possible Solution

Settle one QQBot data-root contract in the linked PR: either support a validated, documented `QQBOT_DATA_DIR` path end to end, or replace the diagnostic with a supported recovery path.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should QQBot introduce `QQBOT_DATA_DIR` as a supported plugin-owned data-root override, or should the diagnostic stop recommending that env var?

Rationale: OpenClaw policy sets a high bar for new env/config surface, and recent QQBot storage work moved persistent runtime state toward SQLite while the current diagnostic already created user expectations around `QQBOT_DATA_DIR`.

Likely owner: steipete

Owner confidence: medium

Options:

- **Support the env override (recommended):** Make `QQBOT_DATA_DIR` a documented plugin-owned env surface with trimming, normalization, path-safety validation, focused tests, docs, and real diagnostic proof.
- **Remove the recommendation:** Change QQBot diagnostics to recommend an existing supported recovery path instead of adding another env-controlled storage root.
- **Defer to storage cleanup:** Keep this open until the remaining legacy data-directory uses are retired or formally migrated, then decide whether a custom root is still needed.

## Reproduction Assessment

Yes, at source level: set `QQBOT_DATA_DIR` and `runDiagnostics()` still reports `getQQBotDataDir()`, whose helper ignores that env var and uses the OS home path. I did not run a live Windows Gateway reproduction.

## Solution Assessment

Unclear until maintainers choose the contract. Supporting `QQBOT_DATA_DIR` is plausible because diagnostics already recommends it, but the safer implementation must validate the env path and align docs, diagnostics, legacy imports, and storage boundaries.

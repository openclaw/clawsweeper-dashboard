## Summary

Keep open: current main still has automatic cache-TTL pruning, manual session compaction, reset/delete, and overflow-oriented tool-result truncation, but not caller-directed clear/archive/recover for a stable tool-result entry. The related overflow issue and open PR are adjacent automatic recovery work, while this issue remains the narrower manual lifecycle-control request.

## What This Changes

Request a caller-directed way to purge or archive individual tool results from active context before automatic TTL pruning runs.

## Best Possible Solution

Define one canonical session/context lifecycle contract for stable tool-result release or archival, then expose approved CLI, agent, and tool-call adapters over that contract with explicit auth, persistence, replay, and recovery semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add caller-directed tool-result lifecycle control, and if so should it be destructive clear or recoverable archive?

Rationale: Current code has only automatic pruning/truncation and whole-session compaction/reset/delete; adding manual per-result control creates a new core session/API contract with replay, storage, and recovery consequences.

Likely owner: steipete

Owner reason: steipete is tied to cache-TTL pruning and the current moved implementation, and the decision crosses core session/runtime API boundaries.

Owner confidence: medium

Options:

- **Recoverable Archive Contract (recommended):** Add one canonical core operation that removes selected tool results from active model context while preserving enough metadata/content for audit and recovery, then layer CLI/agent/tool-call affordances on top.
- **Destructive Clear Only:** Expose a narrower delete-like operation that rewrites or masks selected tool results without recovery, accepting simpler implementation at higher workflow-state loss risk.
- **Defer To Automatic Pruning:** Keep this open as a product backlog item but do not implement manual lifecycle control until automatic pruning and overflow recovery prove insufficient after related work lands.

No, not as separate CLI, agent function, and per-tool-call implementations. The maintainable path is one canonical context/session lifecycle operation with explicit persistence, recovery, authorization, and transcript-integrity semantics.

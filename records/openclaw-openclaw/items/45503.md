## Label Justifications

- `P2`: Large short-lived tool results can bloat session context and cost, but existing pruning, truncation, compaction, and reset paths partially mitigate the impact.
- `impact:session-state`: The request changes which tool-result state remains active, hidden, rewritten, or recoverable across later session turns.

## Summary

Keep open: current main and v2026.6.11 still have automatic TTL pruning, pressure truncation, manual compaction, reset, and delete paths, but not the requested caller-directed clear, archive, or recover operation for a stable tool-result entry.

## What This Changes

The issue requests a user- or agent-directed way to remove obsolete tool-result content from active context before automatic TTL or overflow pruning runs.

## Best Possible Solution

Define one canonical session/context lifecycle contract for stable tool-result release or archival, then expose approved CLI, agent, and tool-call adapters over that contract with explicit auth, persistence, replay, and recovery semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add caller-directed tool-result clearing as destructive transcript rewrite, model-context-only masking, or recoverable archival, and which CLI, agent, and tool-call adapters should expose that contract?

Rationale: This adds core lifecycle/API semantics that affect session replay, persistence, compaction, authorization, and agent control, so automation should not choose the product and safety semantics.

Likely owner: Peter Steinberger

Owner reason: He authored cache-TTL pruning mode and is the strongest adjacent owner for choosing whether manual clearing should extend, replace, or stay separate from the current pruning behavior.

Owner confidence: medium

Options:

- **Design Canonical Archive/Clear Contract (recommended):** Define a single lifecycle operation with stable ids, auth, persistence, recovery, and replay semantics before adding CLI or agent-facing adapters.
- **Keep Automatic Pruning Only:** Decline manual clearing for now and improve docs or heuristics around TTL, truncation, /compact, /new, and /reset.
- **Implement Narrow Destructive Clear:** Add only a targeted clear-by-id operation, accepting that recovery and audit semantics are intentionally minimal.

Not applicable as a bug reproduction: this is a feature request. Source inspection gives medium-high confidence that current main lacks the requested caller-directed release/archive/recover API while adjacent automatic pruning paths exist.

## Solution Assessment

No, not as separate CLI, agent function, and per-tool-call implementations. The maintainable path is one canonical context/session lifecycle operation with explicit persistence, recovery, authorization, and transcript-integrity semantics.

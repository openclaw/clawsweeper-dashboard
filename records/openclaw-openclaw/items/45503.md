## Summary

Keep open: current main and v2026.6.11 have automatic tool-result pruning, overflow truncation, manual compaction, reset, and delete paths, but they still do not expose caller-directed clearing or archive/recover semantics for a specific no-longer-needed tool result. This remains a core session/context lifecycle product decision rather than conservative cleanup.

## What This Changes

The issue requests a way for users or agents to manually purge, archive, or auto-clear large tool results from active context before TTL-based pruning or compaction handles them.

## Best Possible Solution

Design one core-owned context-result lifecycle contract that can remove content from active prompts while preserving auditability and recovery, then expose it through the narrowest user/agent surface with replay and compaction tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add caller-directed tool-result lifecycle control, and if so should the first version be hard delete, soft archive with recovery, or only earlier automatic truncation/pruning improvements?

Rationale: The source gap is clear, but choosing the API changes session persistence, replay validity, recovery semantics, and agent authority; automation should not invent that contract.

Likely owner: Vincent Koc

Owner reason: Vincent Koc has the strongest available history across session-pruning docs, release context, and adjacent context-management work.

Owner confidence: medium

Options:

- **Soft Archive With Recovery (recommended):** Add a core lifecycle path that removes selected tool-result content from active prompts while retaining an inspectable/recoverable transcript placeholder and recovery handle.
- **Hard Delete Only:** Allow explicit removal of selected tool-result content from active context and transcript projection, accepting stronger risk around replay, audit, and later recovery.
- **No Manual Lifecycle API:** Keep improving TTL pruning, overflow truncation, compaction, and plugins such as Tokenjuice without adding a new user/agent clearing contract.

## Reproduction Assessment

Yes for the source-level gap: current main exposes automatic pruning, overflow truncation, manual compaction, reset, and delete, but no targeted tool-result clear/archive/recover operation. No live runtime repro was needed because this is a missing feature/API surface, not a failing existing contract.

## Solution Assessment

Unclear until maintainers choose the product contract. A recoverable soft-archive design looks safer than direct deletion because it can reduce prompt bloat without discarding audit/replay data outright.

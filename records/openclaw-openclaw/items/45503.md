## Label Justifications

- `P2`: Large short-lived tool results can bloat context and cost, but existing pruning, truncation, compaction, reset, and delete paths partially mitigate the impact.
- `impact:session-state`: The request changes which tool-result state remains active, hidden, rewritten, or recoverable across later session turns.

## Summary

Keep open: current main and v2026.6.11 still provide automatic TTL pruning, tool-result truncation, compaction, reset, and delete paths, but not a caller-directed clear, archive, or recover operation for a stable tool-result entry.

## What This Changes

Request manual controls to purge, clear, archive, or recover tool-result context once a large result is no longer useful.

## Best Possible Solution

Define one canonical session/context lifecycle contract for stable tool-result release or archival, then expose approved CLI, agent, and tool-call adapters over that contract with explicit auth, persistence, replay, and recovery semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw add caller-directed tool-result clearing as destructive transcript rewrite, model-context-only masking, or recoverable archival, and which CLI, agent, and tool-call adapters should expose that contract?

Rationale: The feature changes core session lifecycle semantics across persistence, replay, compaction, restart recovery, and agent authority, so automation should not choose the product and safety contract.

Likely owner: steipete

Owner reason: steipete has the strongest adjacent cache-TTL pruning history and product-review fit for this issue family.

Owner confidence: high

Options:

- **Design canonical archive/clear contract (recommended):** Define one lifecycle operation with stable ids, auth, persistence, recovery, and replay semantics before adding CLI or agent-facing adapters.
- **Keep automatic pruning only:** Decline manual clearing for now and improve docs or heuristics around TTL pruning, truncation, compaction, /new, and /reset.
- **Implement narrow destructive clear:** Add only a targeted clear-by-id operation and explicitly accept minimal recovery and audit semantics.

## Reproduction Assessment

Not applicable as a bug reproduction: this is a feature request. Source inspection gives high-confidence evidence that current main lacks the requested caller-directed release/archive/recover API while adjacent automatic pruning paths exist.

## Solution Assessment

No, not as separate CLI, agent function, and per-tool-call implementations. The maintainable path is one canonical context/session lifecycle operation with explicit persistence, recovery, authorization, and transcript-integrity semantics.

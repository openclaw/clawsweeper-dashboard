## Label Justifications

- `P2`: Large short-lived tool results can bloat context and cost, but existing pruning, truncation, compaction, reset, and delete paths partially mitigate the impact.
- `impact:session-state`: The request changes which tool-result state remains active, hidden, rewritten, or recoverable across later session turns.

## Summary

Keep open: current main still has automatic TTL/threshold pruning, overflow truncation, and whole-session compact/reset/delete paths, but no caller-directed clear/archive/recover operation for a stable tool-result entry.

## What This Changes

Request a manual way to purge or archive large tool results from active context after they are no longer needed.

## Best Possible Solution

Define one canonical session/context lifecycle contract for stable tool-result release or archival, then expose approved CLI, agent, and tool-call adapters with explicit auth, persistence, replay, and recovery semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support caller-directed tool-result lifecycle control as destructive clearing, model-context-only masking, or recoverable archival, and which public adapters should expose it?

Rationale: The implementation would create a new core context/session API surface that affects persistence, transcript replay, recovery, authorization, and compaction behavior; automation should not choose those product and safety semantics.

Likely owner: steipete

Owner reason: The strongest history signal is the cache-TTL pruning mode and adjacent product-review context for this exact issue family.

Owner confidence: medium

Options:

- **Design Canonical Archive/Clear Contract (recommended):** Define stable IDs, auth, persistence, recovery, replay, and adapter semantics before implementation.
- **Keep Automatic Pruning Only:** Decline manual clearing for now and improve the existing TTL pruning, truncation, compact, reset, and docs paths.
- **Implement Narrow Destructive Clear:** Add clear-by-id only, accepting that recovery and audit semantics are deliberately minimal.

## Reproduction Assessment

Not applicable as a bug reproduction: this is a feature request. Source inspection gives high confidence that current main lacks the requested caller-directed clear/archive/recover API while adjacent automatic pruning paths exist.

## Solution Assessment

No, not as independent CLI, agent-function, and per-tool-call implementations. The maintainable path is a single canonical lifecycle operation with explicit persistence, recovery, authorization, and transcript-integrity semantics.

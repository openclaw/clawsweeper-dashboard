## Label Justifications

- `P2`: Large short-lived tool results can bloat context and cost, but current pruning, truncation, compaction, reset, and delete paths partially mitigate the impact.
- `impact:session-state`: The request changes which tool-result state remains active, hidden, rewritten, or recoverable across later session turns.

## Summary

Keep open: current main and v2026.6.11 still provide automatic in-memory tool-result pruning, full-session compaction, reset, and delete, but not caller-directed clear/archive/recover for a stable tool-result entry. The remaining work is a product/API decision, not a narrow bug fix.

## What This Changes

The issue requests a manual way to purge large tool results from active context once they are no longer useful.

## Best Possible Solution

Define one canonical session/context-engine lifecycle operation for stable tool-result clear/archive/recover, then expose approved CLI, agent, and tool-call adapters over that operation with explicit auth, replay, persistence, and recovery semantics.

## Reproduction Assessment

Yes, at source level: current main lacks a caller-directed clear/archive/recover operation for stable tool-result entries, while the existing pruning path is automatic and policy-driven. I did not run a live Gmail-style workflow because the code and docs already define the missing surface clearly.

## Solution Assessment

No, not as separate CLI, agent function, and per-tool-call implementations. The maintainable path is one canonical session/context lifecycle operation with explicit persistence, recovery, authorization, and transcript-integrity semantics.

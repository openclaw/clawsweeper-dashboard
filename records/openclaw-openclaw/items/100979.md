## Summary

Keep open: current main still preserves `send_attempt_started` after observed send failures and refuses recovery without adapter reconciliation, while Discord does not advertise or implement `reconcileUnknownSend`. The linked reconnect PR documents this as the remaining full-outage gap, not as work it fixes.

## What This Changes

The issue asks OpenClaw to stop dropping Discord queued outbound messages that fail during a full network outage after they are marked `send_attempt_started`.

## Best Possible Solution

Add a duplicate-safe recovery path for provably unsent Discord failures, either by clearing/resetting the marker only for contract-proven pre-dispatch errors or by implementing Discord `reconcileUnknownSend`, while keeping the blind-replay guard for ambiguous sends.

Yes, at source level: a pending `send_attempt_started` entry with no adapter reconciliation is refused and moved to failed on recovery, and Discord does not currently provide that adapter capability. I did not run the live Wi-Fi outage scenario in this read-only review, but the issue and linked PR include live logs matching the source path.

## Solution Assessment

Unclear which proposed implementation is best without dependency/API proof: core pre-dispatch error classification and Discord nonce-based reconciliation are both plausible. The best fix is the narrow path that proves unsent status without weakening duplicate-send protection.

## Repair Work Prompt

Fix https://github.com/openclaw/openclaw/issues/100979 on current main. The bug is that a Discord outbound send during a full network outage can be marked `send_attempt_started`, then `failDelivery` preserves that marker after an observed pre-result transport failure, and recovery later refuses replay because Discord has no `reconcileUnknownSend`. Implement one narrow duplicate-safe repair: either prove and classify pre-dispatch/connect-phase failures so the queued entry remains replayable only when the request could not have reached Discord, or implement Discord `durableFinal.reconcileUnknownSend` with Discord-supported idempotency/nonce evidence. Do not remove the generic blind-replay guard, do not add config, do not replay ambiguous `unknown_after_send` or unproven `send_attempt_started` entries, and keep channel-specific Discord behavior in the plugin when the fix depends on Discord API semantics. Add focused regression coverage for the full-outage unsent path and for preserving the existing no-replay behavior on ambiguous sends; include live or artifact-backed Discord outage/reconnect proof before asking to land.

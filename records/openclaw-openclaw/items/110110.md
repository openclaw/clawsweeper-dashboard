## Summary

Keep open: bounding the map is appropriate, but the proposed FIFO eviction does not preserve the claimed active-IP recency and can reset an actively rate-limited client under high-cardinality traffic; the PR also provides automated route tests rather than real-setup proof.

## What This Changes

The PR sweeps expired Telegram Mini App authentication rate-limit entries, caps the map at 1,024 IP keys, and adds route-level regression tests.

## Best Possible Solution

Keep the expiry sweep and hard cap, but implement the documented recency policy by refreshing active entries before FIFO pruning, cover a non-expired active-key eviction case, and provide redacted live gateway HTTP output showing normal authentication and throttling behavior after the fix.

## Reproduction Assessment

Yes at source level: current main retains every one-shot IP entry until that same IP revisits after expiry, so unique clients can grow the module-level map for the process lifetime. The submitted regression test also reports a before-fix failure, but this review did not independently run it.

## Solution Assessment

No, not yet. Sweeping and capping are the correct narrow direction, but the implementation must either maintain true access recency or explicitly adopt and prove a weaker FIFO fail-open policy.

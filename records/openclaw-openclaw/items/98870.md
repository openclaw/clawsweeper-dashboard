- `impact:message-loss`: Newer Teams thread replies can be omitted from the context delivered to the agent.
- `impact:session-state`: The agent can receive stale thread context for long Teams conversations, affecting conversation state.

## Summary

Keep open: current main and the latest release still fetch only one Teams replies page, so long channel threads can omit newer replies from agent context. The closed related PRs attempted the right helper-level fix but did not land, leaving this issue as the canonical tracker until live Teams proof or explicit maintainer risk acceptance unblocks a fix.

## What This Changes

The issue asks OpenClaw to follow Microsoft Graph pagination for Teams channel thread replies so long threads contribute the newest replies to agent context.

## Best Possible Solution

Land a bounded `fetchThreadReplies` pagination fix that reuses `fetchAllGraphPages`, returns the newest requested reply window in chronological context order, and includes either redacted live Teams/Graph proof or explicit maintainer acceptance of the bounded fanout risk.

## Reproduction Assessment

Yes from source inspection: current main still clamps reply fetching to one `$top=50` Graph page and the monitor handler injects that result into thread context. I did not run a live Teams tenant in this read-only review.

## Solution Assessment

Yes for code shape: the narrow fix belongs in the Teams `fetchThreadReplies` helper and should reuse the existing Graph pagination helper. Another automated PR without live proof would likely repeat the closed PR loop, so the next useful step is maintainer/live proof or explicit acceptance of the bounded fanout risk.

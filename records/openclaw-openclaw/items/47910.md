## Summary

Keep open: current main has failure-class foundations and partial auth skip/cooldown behavior, but it still lacks the requested default auth-broken quarantine/status policy and the latest released-build restart subcase is not proven fixed.

## What This Changes

Request failure-class-aware provider fallback that quarantines auth-broken providers, treats rate/network/invalid-request failures differently, and exposes provider health in status output.

## Best Possible Solution

Define a maintainer-approved provider/profile health model that confirms transient 401s before marking auth broken, quarantines durable failures, avoids config-write restart loops, and exposes redacted health in status/doctor.

## Reproduction Assessment

Partly. Current source and docs reproduce the central gap because repeat auth skipping is opt-in and not a default provider quarantine/status model; the single-provider restart subcase remains reporter-log backed rather than live-reproduced here.

## Solution Assessment

No, closing is not the best path. Current main is a partial mitigation, and a blanket fail-closed quarantine is not automatically best without maintainer decisions on transient 401 handling, redaction, and upgrade behavior.

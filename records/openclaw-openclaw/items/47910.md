## Summary

Keep open: current main has useful failure-class classification and partial auth cooldown/skip foundations, but it still lacks the requested default hard-auth quarantine and normal status contract, and the latest released-build report describes gateway restarts/session disruption that is not proven fixed.

## What This Changes

The issue requests failure-class-aware provider fallback that quarantines auth-broken providers, treats transient classes differently, and exposes provider health in status output.

## Best Possible Solution

Define a maintainer-approved auth failure policy that confirms transient 401s before marking auth broken, quarantines durable provider/profile failures with redacted status visibility, and avoids config-write/restart loops when same-key retry succeeds.

## Reproduction Assessment

Yes for the central source-level gap: code and docs show repeat auth skipping is opt-in and not a default provider quarantine/status model; no for the July 2 single-provider restart subcase, which remains reporter-log backed without live reproduction.

## Solution Assessment

Unclear until maintainers choose the default policy; a blanket fail-closed quarantine is not automatically best because transient 401 recovery, status redaction, and upgrade-safe behavior all need explicit decisions.

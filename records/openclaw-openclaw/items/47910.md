## Summary

Keep open: current main has failure-class classifiers and partial auth-skip mitigations, but it still lacks the requested default hard-auth provider quarantine, invalid-request fail-fast policy, and normal status provider-health surface; fresh 2026.6.11 discussion also reports auth-triggered gateway restarts and session disruption.

## What This Changes

The issue requests failure-class-aware provider fallback that quarantines hard auth failures, treats rate limits and transient network failures differently, avoids fallback for invalid requests, and exposes provider health in status output.

## Best Possible Solution

Define a provider/profile incident-health model that confirms transient 401s before hard quarantine, applies durable failure-class backoff consistently, and exposes redacted status/doctor visibility without config-write restart loops.

Yes for the central source-level gap: default auth skip is disabled, primary candidates are not skipped, generic auth uses cooldown rather than default quarantine, and normal status lacks provider quarantine health; the restart-loop subcase still needs live proof.

## Solution Assessment

Unclear: the requested failure-class table is directionally useful, but blanket fail-closed quarantine is not automatically the best fix until maintainers choose the hard-auth versus transient-401 boundary and the redacted status contract.

## Summary

Keep open: current main has failure-class foundations and partial mitigations, including `auth_permanent` disabled windows, an opt-in session skip cache, JSON unusable-profile reporting, and the merged OpenAI expired-token probe fix, but it still does not implement the requested default auth-broken provider quarantine, transient-401 confirmation policy, or full operator-facing provider-health/status behavior.

## What This Changes

The issue requests failure-class-aware provider fallback that quarantines auth-broken providers, treats rate-limit/network/invalid-request failures differently, and surfaces quarantine state in status output.

## Best Possible Solution

Implement a maintainer-approved failure-class policy that confirms transient 401s before marking auth broken, disables or quarantines high-confidence credential failures, respects Retry-After and transient lanes, fails fast for invalid requests, and surfaces redacted provider health in status/doctor without config-write restart loops.

Rationale: The remaining work changes provider routing defaults, status visibility, and auth-state side effects for existing users, and current policy deliberately keeps some auth-looking failures recoverable to avoid false lockouts.

Owner confidence: high

Options:

- **Approve conservative default quarantine (recommended):** Classify only high-confidence revoked/invalidated credential and confirmed refresh failures into the disabled/quarantine lane, retry same-key transient 401s once first, and expose redacted status/doctor recovery state.
- **Keep skip behavior opt-in:** Leave current default retries unchanged and rely on `OPENCLAW_FALLBACK_SKIP_TTL_MS` plus existing `auth_permanent` handling for operators who want faster avoidance of known-bad candidates.
- **Split status and restart first:** Handle provider-health status and the single-key restart loop in a narrower issue before changing fallback routing defaults.

## Reproduction Assessment

Yes for the central source-level gap: current main documents that default auth skip is disabled, primary candidates are never skipped, and ordinary auth failures use cooldown rather than quarantine. The shipped-build single-key restart loop has detailed user logs but still needs live current-main confirmation.

## Solution Assessment

Unclear. Current main is a useful partial foundation, but the opt-in skip cache and `auth_permanent` disabled lane are not the full provider-level quarantine/status solution; the best fix needs a maintainer-approved hard-auth versus transient-401 policy boundary.

## Summary

Keep open: current main has partial failure-class handling and an opt-in session-scoped auth skip cache, but it still does not provide the requested default provider quarantine/status behavior, and the latest released-build comment adds a restart/session-disruption case that needs maintainer policy review.

## What This Changes

Request provider fallback behavior that classifies auth, rate-limit, network, and invalid-request failures, quarantines auth-broken providers, and exposes provider health in status output.

## Best Possible Solution

Define a maintainer-approved auth failure policy that distinguishes hard auth failure from transient 401s, avoids config-write/restart loops after a same-key retry succeeds, and exposes redacted provider/profile health in status without breaking existing fallback recovery.

## Reproduction Assessment

Yes for the central source-level gap: current docs and code show repeat auth skipping is opt-in and process-local, not a default provider quarantine/status model. No live reproduction was run for the new v2026.6.11 spurious 401-to-restart sequence, so that sub-case remains reporter-log backed.

## Solution Assessment

Unclear as an implementation until maintainers choose the default policy. The best path is not a blanket fail-closed quarantine alone; it should include transient 401 handling, redacted health/status visibility, and upgrade-safe defaults.

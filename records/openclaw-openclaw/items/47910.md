## Summary

Keep open: current main has failure-class classification, terminal format-error handling, and an opt-in auth skip cache, but it still does not provide the requested default hard-auth quarantine/provider-health policy or normal `openclaw status` provider-health surface; the latest stable release discussion still reports auth-triggered restarts and session disruption.

## What This Changes

The issue requests failure-class-aware provider fallback that quarantines hard auth-broken providers, treats rate limits/network/format failures differently, and exposes provider health in status output.

## Best Possible Solution

Define a provider/profile incident-health model that confirms hard auth before quarantine, preserves transient recovery, and exposes redacted status/doctor visibility without config-write restart loops.

Owner confidence: high

Options:

- **Default Incident-Health Model (recommended):** Implement hard-auth quarantine only after a documented confirmation boundary, preserve transient 401/OAuth recovery, and add redacted status/doctor visibility.
- **Keep Opt-In Skip Only:** Leave default fallback behavior unchanged and improve guidance around the existing operator-controlled skip TTL and `models status` diagnostics.
- **Split Restart Subcase First:** Repair the config-write restart loop for transient single-provider 401s before deciding the broader quarantine and provider-health policy.

## Reproduction Assessment

Yes for the central source-level gap: default auth skip is disabled, primary candidates are not skipped, generic auth uses cooldown rather than default quarantine, and normal status lacks provider quarantine health; the restart-loop subcase still needs live proof.

## Solution Assessment

Unclear: the failure-class direction is sound, but blanket hard-auth quarantine is not the best fix until maintainers choose the hard-auth versus transient-recovery boundary and redaction contract.

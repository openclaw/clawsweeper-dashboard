## Summary

Keep open: current main and v2026.6.11 have useful failure-class classification, auth cooldown, and opt-in skip-cache foundations, but they still do not provide the requested default auth-broken quarantine/status policy, and the latest released-build report adds a credible gateway restart/session-disruption subcase that is not proven fixed.

## What This Changes

The issue requests failure-class-aware provider fallback that quarantines auth-broken providers, treats rate limits/network/invalid requests differently, and exposes provider health in status output.

## Best Possible Solution

Define a maintainer-approved provider/profile health model that confirms transient 401s before marking auth broken, quarantines durable provider/profile failures with redacted status visibility, and avoids config-write or restart loops when same-key retry succeeds.

## Reproduction Assessment

Yes for the central source-level gap: current code and docs show repeat auth skipping is opt-in, non-primary, process-local, and absent from normal status. No for the July 2 single-provider restart subcase, which remains reporter-log backed without live reproduction.

## Solution Assessment

Unclear until maintainers choose the default policy; a blanket fail-closed quarantine is not automatically best because transient 401 recovery, status redaction, and upgrade-safe behavior all need explicit decisions.

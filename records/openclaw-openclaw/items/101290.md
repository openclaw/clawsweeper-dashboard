## Summary

Keep open: current main and the latest checked release still leave CLI/status/stability paths able to reach the shared SQLite state DB through normal WAL/checkpoint and migration-capable openers; the merged macOS WAL fullfsync work is adjacent, not a live-gateway ownership fix.

## What This Changes

The issue asks OpenClaw to prevent routine CLI health/status/stability checks from mutating or corrupting the live shared SQLite state DB while a gateway is running.

## Best Possible Solution

Define a gateway-owned shared DB access contract: health/status/stability use RPC when the gateway is running, file fallbacks are read-only with no WAL maintenance or migrations under a gateway lease, and malformed DBs are preserved/quarantined.

Question: Should CLI health/status/stability avoid direct shared-state DB WAL maintenance while a gateway is running by using an RPC-first read-only fallback, a single-writer lease, or both?

Rationale: The source evidence shows the issue crosses shared SQLite ownership, CLI observability, doctor migrations, gateway runtime, and recovery policy, so automation should not choose the permanent product boundary alone.

Likely owner: steipete

Owner confidence: high

Options:

- **RPC-first read-only observer (recommended):** Make gateway-owned RPC the normal path and allow direct file reads only in a no-migration/no-checkpoint observer mode when no running gateway owns the store.
- **Single-writer lease first:** Have the gateway hold an exclusive state-DB lease and make all other processes refuse read-write or maintenance access while it is active.
- **Recovery quarantine first:** Prioritize malformed-DB detection and quarantine before changing all CLI observer paths, accepting that the corruption vector may remain open longer.

## Summary

Keep open. Current main still has the reported risk surface: CLI health/status/config/plugin-index paths can open the shared state database through the normal opener, that opener enables WAL/autocheckpoint and close-time checkpoints, and plugin-state wraps the failure with the exact reported error. The merged macOS fullfsync work is adjacent but does not resolve CLI-vs-gateway state ownership.

## What This Changes

The issue asks OpenClaw to prevent routine CLI health/status startup paths from modifying or corrupting the live shared SQLite state database while a gateway is running.

## Best Possible Solution

Define a gateway-owned state boundary: health/status should prefer gateway RPC, direct file fallbacks should be read-only with no WAL maintenance, migrations, or checkpoints while the gateway is live, and malformed DB recovery should be doctor/quarantine driven.

Owner confidence: high

Options:

- **RPC/read-only owner boundary (recommended):** Make health/status prefer gateway RPC and ensure any direct DB fallback opens without WAL maintenance, schema migrations, writes, or checkpoints while the gateway is live.
- **Exclusive gateway lease:** Have the gateway own read-write state access and make CLI direct DB access fail closed with a clear doctor/RPC path while that lease is held.
- **Recovery-only hardening:** Keep current opener behavior but add malformed-DB quarantine and doctor repair, which reduces damage after corruption but leaves the suspected trigger path in place.

No deterministic live reproduction was established, but current source confirms the reported class: CLI-adjacent paths can open the shared DB and run WAL maintenance/checkpoints outside the gateway process.

## Solution Assessment

The suggested direction is plausible, but the best fix requires a maintainer policy choice around gateway-owned state, CLI direct-read fallback, and malformed DB recovery semantics.

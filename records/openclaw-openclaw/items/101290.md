## Summary

Keep open: current main still lets local gateway status paths reach the shared state database through the normal WAL/checkpointing opener, and the related reports cover adjacent corruption or durability work rather than this CLI/live-gateway ownership bug.

## What This Changes

The issue asks OpenClaw to prevent routine CLI health/status/stability checks from mutating or corrupting the shared state SQLite DB while a gateway owns it.

## Best Possible Solution

Define a gateway-owned shared SQLite access contract: health/status/stability use RPC when the gateway is running, file fallbacks are read-only with no WAL maintenance or migrations, and malformed DBs are preserved or quarantined with focused stress proof.

Rationale: The source boundary is clear, but the fix changes CLI observability, doctor/migration behavior, gateway ownership, and data-recovery policy for a persisted shared store.

Likely owner: steipete

Owner confidence: high

Options:

- **RPC-first/no-maintenance CLI (recommended):** Make health/status/stability prefer the running gateway and allow only read-only, no-checkpoint, no-migration file access while a gateway lease is active.
- **Single-writer lease first:** Have the gateway own write and WAL-maintenance access through an explicit lease, with other processes refusing writer-style shared DB opens while it is held.
- **Recovery/quarantine first:** Add malformed-DB preservation and availability recovery first while leaving prevention of concurrent CLI/gateway maintenance as a follow-up.

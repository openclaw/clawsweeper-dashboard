## Summary

Keep open: current main still permits CLI/gateway diagnostic paths to reach the shared SQLite opener with WAL/checkpointing and migration-capable startup code, and no merged fix owns the CLI/live-gateway database ownership contract.

## What This Changes

The issue asks OpenClaw to prevent CLI health/status/stability checks from mutating or corrupting the live shared state database while a gateway is running.

## Best Possible Solution

Define a gateway-owned shared DB access contract: diagnostic CLI paths prefer RPC, file fallbacks are read-only with no WAL maintenance or migrations, and malformed DBs are preserved/quarantined with focused regression and live stress proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should CLI health/status/stability avoid direct shared-state DB WAL maintenance while a gateway is running via RPC-first read-only fallback, or should OpenClaw add an explicit single-writer gateway lease first?

Rationale: Both directions can address the reported data-loss class, but the choice changes CLI observability, doctor migration timing, gateway ownership, and recovery behavior for a shared persisted store.

Likely owner: steipete

Owner reason: The strongest history signal for shared SQLite ownership is the shared state DB introduction, and this decision needs the owner of the DB/gateway contract.

Owner confidence: high

Options:

- **RPC-first/no-maintenance CLI (recommended):** Make diagnostic commands use the running gateway when available and permit only read-only, no-checkpoint, no-migration file fallback while a gateway owns the DB.
- **Single-writer lease first:** Have the gateway own write and WAL-maintenance access through an explicit lease, with other processes refusing writer-style shared DB opens while it is held.
- **Forensics before contract change:** Wait for the sanitized corrupt DB bundle and a throwaway runtime harness before choosing the DB ownership fix shape.

## Reproduction Assessment

No deterministic current-main live reproduction is available. The source path is clear enough to reproduce the risky behavior by inspection: gateway/status diagnostics can open the shared DB through the WAL/checkpointing opener while a gateway may also own the store.

## Solution Assessment

Unclear as an automated narrow fix. The best maintainable solution needs a maintainer-approved shared DB ownership and recovery contract, not a one-line checkpoint or status-command change.

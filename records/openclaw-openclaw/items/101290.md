## Summary

Keep open: current main still has mutable shared-state SQLite open/checkpoint paths reachable from CLI-adjacent state and plugin diagnostics, and the newer startup-migration lease work only covers foreground gateway startup, not the reported health/status probe ownership problem.

## What This Changes

The issue reports a regression where routine CLI health/status/stability invocations against a running macOS gateway appear to corrupt the live shared `openclaw.sqlite` state database.

## Best Possible Solution

Adopt a maintainer-approved shared-state ownership policy: health/status/stability should prefer running-gateway RPC, non-gateway fallback opens should be read-only and no-maintenance while the gateway owns the DB, and doctor/repair maintenance should require an explicit lease or maintenance mode.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should the shared state DB policy be RPC-first/no-maintenance CLI access, a stricter single-writer gateway lease, or both for health/status/stability and doctor repair paths?

Rationale: Current source confirms mutable CLI-side shared DB open and checkpoint paths, but the durable fix changes ownership between gateway RPC observability, plugin-state probes, doctor migrations, and operator recovery behavior.

Likely owner: steipete

Owner reason: The decision cuts across the DB-first runtime-state architecture and current gateway/CLI ownership boundaries traced to that work.

Owner confidence: high

Options:

- **RPC-first plus no-maintenance CLI (recommended):** Make status, health, and stability ask the running gateway first, and make fallback file opens read-only with no journal or checkpoint pragmas while a gateway is active.
- **Single-writer gateway lease:** Have the gateway own write and WAL-maintenance access to the shared state DB, with non-gateway processes failing closed or routing through gateway APIs unless they acquire an explicit maintenance lease.
- **Forensic harness first:** Pause implementation until the reporter's sanitized DB bundle or a native runtime harness confirms the exact OpenClaw helper/runtime interaction.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Source-reproducible, but not live-reproduced: current main still exposes mutable shared-state DB open/checkpoint paths, while the corruption race itself is supported by reporter forensics rather than a deterministic throwaway repro.

## Solution Assessment

Is this the best way to solve the issue? Unclear until maintainers choose the DB ownership policy; RPC-first/no-maintenance is the narrowest starting point, but a single-writer lease may be needed to close the whole class.

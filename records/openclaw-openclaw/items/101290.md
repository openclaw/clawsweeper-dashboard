## Summary

Keep open: current main still has CLI and diagnostic paths that can open the shared state database through normal write-capable SQLite/WAL helpers while a gateway may be running, and the reporter has recent forensic follow-up rather than stale or insufficient context.

## What This Changes

The issue asks OpenClaw to prevent CLI health/status/stability preflights from corrupting the live shared SQLite state database while the gateway is running.

## Best Possible Solution

Define a gateway-owned shared DB access contract: CLI health/status/stability should use RPC when the gateway is running, any file fallback should be read-only with no WAL maintenance or migrations, and malformed DBs should be preserved/quarantined with focused stress proof.

Owner confidence: high

Options:

- **RPC-first/no-maintenance CLI (recommended):** Health/status/stability prefer the running gateway and permit only read-only, no-checkpoint, no-migration file access while a gateway lease is active.
- **Single-writer lease first:** The gateway owns write and WAL-maintenance access through an explicit lease, and other processes refuse writer-style shared DB opens while it is held.
- **Recovery/quarantine first:** Malformed shared DBs are preserved and quarantined before prevention work, reducing post-corruption damage while leaving the concurrent-opener class for follow-up.

## Reproduction Assessment

No deterministic live current-main reproduction is available from this review. The source path is reproducible: gateway status/stability and migration-capable preflight can still reach the shared DB through write-capable SQLite/WAL helpers while the gateway may own the same store.

## Solution Assessment

No automated one-line fix is clearly the best solution. The maintainable fix should first settle the DB ownership contract, then add regression coverage and live stress proof around the selected prevention and recovery behavior.

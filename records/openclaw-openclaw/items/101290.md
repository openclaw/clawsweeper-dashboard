## Summary

Keep open: current main has narrowed some fast status paths, but it still lacks a settled shared-state ownership policy that prevents non-gateway CLI processes from doing mutable SQLite open, migration, or checkpoint work while the gateway owns the live DB.

## What This Changes

The issue asks OpenClaw to stop CLI health/status/stability startup paths from corrupting the live shared SQLite state DB while a gateway is running.

## Best Possible Solution

Define a gateway-owned state DB policy, then make health/status/stability use running-gateway RPC first and allow any CLI fallback only as read-only, no-maintenance access unless an explicit maintenance lease is held.

Owner confidence: high

Options:

- **RPC-first plus no-maintenance fallback (recommended):** Status, health, and stability should ask the running gateway first, and any fallback file access while the gateway is active should be read-only with no journal, checkpoint, or migration work.
- **Gateway single-writer lease:** The gateway should hold an explicit state DB ownership lease, and non-gateway processes should fail closed or route through gateway APIs for writes and maintenance.
- **Forensic harness first:** Pause implementation until the reporter's corrupt DB bundle and a native runtime harness identify the exact OpenClaw helper or runtime interaction.

## Reproduction Assessment

Source-reproducible, but not live-reproduced: current main still has mutable shared-state open/checkpoint and migration paths reachable from CLI startup surfaces, while the corruption race itself relies on reporter forensics rather than a deterministic throwaway repro.

## Solution Assessment

Unclear as a final fix: RPC-first/no-maintenance matches the source boundary and reporter preference, but maintainers should decide whether a gateway single-writer lease is also required before implementation.

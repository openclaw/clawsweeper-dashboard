## Summary

Keep open: current main still exposes shared-state SQLite openers that configure WAL and can checkpoint from non-gateway CLI/diagnostic paths, and no merged or open related item cleanly owns the live-gateway versus CLI database-ownership fix.

## What This Changes

The issue reports live `openclaw.sqlite` corruption after read-oriented CLI health/status/stability commands opened the shared state database while a gateway was running.

## Best Possible Solution

Adopt an explicit shared-state ownership model where health/status/stability prefer the running gateway and any CLI fallback while a gateway owns the DB is read-only and no-maintenance; if maintainers want stronger protection, add a single-writer lease and a clear maintenance/recovery mode.

Options:

- **RPC-first no-maintenance CLI (recommended):** Make health/status/stability ask the running gateway first and ensure any active-gateway file fallback opens shared state read-only without journal, checkpoint, or migration side effects.
- **Single-writer gateway lease:** Have the gateway own write and WAL-maintenance access, with non-gateway processes failing closed or routing through gateway APIs unless an explicit maintenance mode is active.
- **Forensic harness first:** Pause implementation until the reporter's sanitized DB bundle and a native runtime harness prove the exact SQLite helper/runtime interaction before selecting the policy.

## Reproduction Assessment

## Solution Assessment

Unclear as a final fix because the best policy boundary is not yet selected. RPC-first plus no-maintenance fallback is the narrowest user-facing mitigation, while a gateway-owned single-writer lease may be the more complete state-ownership fix.

## Summary

Keep open: current main still has mutable shared-state SQLite open/checkpoint paths that can be reached by health/status/probe surfaces, and the related fixes only address adjacent WAL durability or shutdown-close issues rather than the live-gateway ownership boundary reported here.

## What This Changes

The issue reports that routine CLI health/status/stability invocations against a running macOS gateway may mutate or checkpoint the shared state SQLite DB and corrupt it under concurrent write load.

## Best Possible Solution

Make live shared-state DB ownership explicit: while a gateway is active, status/health/stability should use Gateway RPC or a read-only no-maintenance open that never runs journal_mode, wal_checkpoint, schema migrations, or diagnostic writes, backed by a dedicated stress harness for this failure class.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw make gateway ownership of the live shared state DB enforceable by RPC-first/no-maintenance CLI access, by a stricter single-writer lease, or by combining both?

Rationale: The source-visible issue is not just a narrow bug in one command; it defines which process may configure, migrate, write, or checkpoint the shared state DB while the gateway is running.

Likely owner: steipete

Owner reason: The choice crosses core runtime state ownership and CLI/gateway product policy, and steipete authored the runtime SQLite refactor that established this boundary.

Owner confidence: high

Options:

- **RPC-first plus active lease guard (recommended):** Prefer Gateway RPC for health/status/stability and refuse CLI write/checkpoint/migration opens while the gateway owns the live DB, leaving explicit offline doctor repair as the migration path.
- **No-maintenance CLI reads only:** Keep CLI diagnostics file-backed where needed, but add a read-only open mode that skips WAL setup, checkpoints, schema migrations, and plugin-state probe writes under an active gateway.
- **Gateway-only SQLite ownership:** Make the gateway the sole process that ever opens the shared DB read-write during normal operation, pushing all live diagnostics through RPC and reserving file access for stopped-gateway recovery.

## Reproduction Assessment

No, not as a deterministic live reproduction on current main. The source path is clear and the reporter supplied detailed production forensics, but the corruption race still needs a throwaway better-sqlite3/node:sqlite harness or sanitized forensic bundle review.

## Solution Assessment

Unclear until maintainers choose the ownership policy. The narrowest maintainable direction appears to be gateway-owned live DB maintenance with CLI diagnostics going RPC-first or read-only/no-maintenance under an active gateway lease.

## Summary

Keep open: this PR targets a real P1 gateway watch crash-loop, but the current branch still stamps a `tsdown-build` shortcut as build-ready before it has followed the canonical `run-node` build, bundled plugin asset, runtime-postbuild, and stamp sequence. It also still lacks after-fix live `gateway:watch` proof for the reported race.

## What This Changes

The branch adds watch-node build-readiness checks, a background `tsdown-build` restart path with a clean-skip environment guard, a declaration for the exported helper, and watcher regression tests.

## Best Possible Solution

Prepare the replacement build through the canonical `run-node` build lock and full asset-build, tsdown, runtime-postbuild, and stamp sequence before signaling the healthy child, then prove it with redacted live `gateway:watch` output.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes for source-level reproduction: current main stops the watched child before proving the replacement build is ready, and the linked issue includes production crash-loop logs; I did not run the destructive systemd race locally.

## Solution Assessment

Is this the best way to solve the issue? No. The PR is a plausible mitigation, but the maintainable fix is to share or stage the full `run-node` build/runtime-postbuild contract before writing readiness stamps and stopping the healthy child.

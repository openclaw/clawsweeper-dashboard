## Summary

Keep open: the PR targets a real P1 gateway watch crash-loop, but the current patch moves the readiness check in front of the only normal path that starts `run-node`, so a normal source update can leave `gateway:watch` waiting forever for a build stamp that no process is creating.

## What This Changes

The PR adds a build-readiness guard and deferred polling to `scripts/watch-node.mjs`, plus tests for missing or stale `dist/entry.js` and `.buildstamp` scenarios.

## Best Possible Solution

Keep the healthy gateway alive while an actual replacement build is prepared, then restart or swap only after that build is proven ready, without breaking normal source-edit and git-pull hot reloads.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes from source inspection: after a git pull changes HEAD, the PR's readiness check returns false and `requestRestart()` returns before starting the `run-node` build path that would write a matching stamp.

## Solution Assessment

Is this the best way to solve the issue? No: the readiness check is in the wrong layer because it waits for `run-node` output before `run-node` has been started; a build-then-restart flow is the safer fix.

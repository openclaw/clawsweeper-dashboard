## Summary

Keep open: the undefined-field example does not match the current required warning type, but current main and the latest release still build the warning dedupe key with `.filter(Boolean)`, so zero-valued prune/max limits can collide and suppress a changed warning context.

## What This Changes

Fix session-maintenance warning dedupe keys so zero-valued limit fields remain positionally distinct and changed limits can re-warn.

## Best Possible Solution

Encode the warning context with fixed slots or named fields instead of Boolean filtering, then add a regression test proving distinct zero-valued limit configurations send fresh warnings.

## Reproduction Assessment

Yes for source-level reproduction: the current key expression can produce the same string for distinct zero-valued limit configurations. I did not run Vitest in this read-only cleanup review.

## Solution Assessment

Yes: changing only `buildWarningContext` to use positional or named stable encoding plus a regression test is the narrow maintainable fix; no config or product-policy change is needed.

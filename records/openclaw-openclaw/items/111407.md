## Label Justifications

- `P1`: An ordinary CLI agent workflow can potentially execute one user request twice once it crosses the default command deadline.
- `impact:message-loss`: The affected execution path can duplicate a submitted agent message rather than execute it exactly once.
- `impact:session-state`: The timeout path creates a separate fallback session/run instead of continuing the accepted Gateway-owned session.
- `impact:auth-provider`: The separate embedded fallback can fail to retain the accepted run's configured provider/model routing.

## Summary

Keep open: current documented behavior still falls back to a fresh embedded `gateway-fallback-*` run after the Gateway has accepted a CLI turn but misses the CLI deadline, so the duplicate-execution and provider-policy concern remains unresolved.

## What This Changes

The issue requests that `openclaw agent` not rerun a prompt through embedded fallback after an already accepted Gateway run reaches the CLI deadline.

## Best Possible Solution

Make Gateway acceptance a no-rerun boundary: after the CLI wait deadline, return an explicit in-flight result carrying the accepted run/session identity (or continue polling), and reserve embedded fallback for failures before Gateway acceptance; add focused coverage for both paths.

Question: For an accepted Gateway run that exceeds `openclaw agent`'s CLI deadline, should the CLI return an attachable in-flight result by default and prohibit embedded rerun, while retaining embedded fallback only for pre-acceptance transport failures?

Rationale: The current fallback is documented as an intentional availability behavior, but it conflicts with exactly-once execution and configured agent/provider policy for mutating work; selecting the default recovery contract requires maintainer intent.

Likely owner: HemantSudarshan

Owner confidence: medium

Options:

- **No rerun after acceptance (recommended):** Return an in-flight timeout with the accepted run and session identifiers, and use embedded fallback only when the Gateway never accepted the request.
- **Require explicit opt-in fallback:** Keep an opt-in CLI mode for a new embedded run after deadline expiry, with conspicuous output that it is a separate execution and may use different runtime routing.
- **Preserve current default:** Keep automatic timeout fallback and document that users must choose a timeout larger than any non-idempotent task.

Yes from current documented control flow: submit a Gateway-backed CLI turn that is accepted but does not finish within the command deadline; the documented path then creates a separate `gateway-fallback-*` embedded run. ## Solution Assessment

No, the current automatic fallback is not the safest solution for an already accepted request because it starts a distinct run; the narrower maintainable fix is a no-rerun accepted-run timeout outcome plus fallback only before acceptance.

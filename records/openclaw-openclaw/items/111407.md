## Summary

Keep open: the prior source review found that a CLI deadline can enter an embedded `gateway-fallback-*` run after the Gateway already accepted the turn, leaving a credible duplicate-execution and provider-policy hazard unresolved. The report is new and a safe repair depends on choosing the post-acceptance timeout contract rather than closing or dispatching an automatic fix.

## What This Changes

Prevent `openclaw agent` from re-running an already Gateway-accepted prompt through an embedded fallback session when the CLI response deadline expires.

## Best Possible Solution

Make post-acceptance timeout handling single-run: preserve and expose the accepted Gateway run for polling/reattachment, and permit an embedded fallback only after an authoritative successful abort with tests covering session and provider continuity.

## Maintainer Decision

Required: true

Kind: product_direction

Question: After a Gateway-accepted CLI turn exceeds the caller deadline, should the CLI keep tracking and return an in-flight accepted-run result, or may it fall back only after successfully aborting that accepted run?

Rationale: Both choices affect the public CLI timeout contract, liveness expectations, and whether callers can safely recover a long-running turn; source evidence supports avoiding a second execution but does not establish the intended user-facing timeout behavior.

Likely owner: MrNozz

Owner reason: The reporter has the only supplied production observations that distinguish a recoverable in-flight contract from an abort-before-fallback contract.

Owner confidence: low

Options:

- **Return accepted-run timeout state (recommended):** Preserve the accepted Gateway run and return an explicit in-flight timeout result containing its run/session identity for callers to reattach or poll.
- **Abort before fallback:** Retain embedded fallback only when the Gateway confirms that the accepted run was aborted, with the abort outcome surfaced to the caller.
- **Remove embedded fallback:** Make CLI deadline expiry terminal after Gateway acceptance and require a later explicit reattach command or invocation.

## Reproduction Assessment

Unclear for a fully high-confidence live reproduction: the report gives a concrete long-running accepted-turn scenario, and the prior source review found the corresponding fallback behavior, but this read-only review did not execute a current-main Gateway turn past the deadline.

## Solution Assessment

Unclear: preventing a second run after Gateway acceptance is the correct invariant, but maintainers must choose whether expiry returns recoverable in-flight state, performs an authoritative abort before fallback, or removes fallback entirely.

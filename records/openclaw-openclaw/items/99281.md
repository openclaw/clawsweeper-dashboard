## Summary

Keep open: the patch is aimed at the right shared Control UI modal boundary, but the `updated()`-only reopen path can miss queued approval swaps where the modal's own reactive properties do not change, and the PR still has only jsdom test output rather than browser-visible proof.

## What This Changes

The PR updates the shared Control UI modal dialog to reopen from Lit `updated()` using native `dialog.open`, and adds modal reuse regression tests.

## Best Possible Solution

Repair the modal so closed reused dialogs reopen on slot/content handoff or an active-approval key change, keep focused regression coverage for same-property queued approvals, and attach redacted browser proof before merge.

## Reproduction Assessment

Yes at source level: current main opens `openclaw-modal-dialog` only once and the approval queue can advance to a new active item inside the same modal surface. I did not run a live browser reproduction in this read-only review.

## Solution Assessment

No: moving reopen logic into the shared modal is the right boundary, but `updated()` alone is too narrow because slot-only or same-property queue shifts can bypass it. A slot/content-driven reopen path or active approval key plus browser proof is the safer fix.

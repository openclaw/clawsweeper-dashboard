## Summary

The empty scope list is intentional authorization hardening for a device-less custom WebSocket client, so the required correction belongs in the client handshake rather than OpenClaw core.

## What This Changes

Report that a custom WebSocket connect request receives an empty authorization scope list despite requesting operator read and write scopes.

## Best Possible Solution

Update the custom client to use operator mode, persist a stable device key, sign the `connect.challenge` nonce with the documented v3 payload, complete pairing, and reuse the issued device token instead of relying on requested scopes plus the shared gateway token.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes, at source level: a connect request without device identity follows the tested policy that clears unbound requested scopes; no live run is needed to establish the documented outcome.

## Solution Assessment

No, restoring the requested scopes server-side would reverse an intentional authorization boundary; the narrow supported solution is to implement the documented challenge, device identity, pairing, and device-token flow in the custom client.

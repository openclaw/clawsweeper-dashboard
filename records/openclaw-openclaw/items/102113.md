Keep open: current main still records `non_deliverable_terminal_turn` only as trajectory/display state while `message_tool_only` follow-up delivery suppresses automatic outbound fallback, and the open fix candidate has not merged.

## What This Changes

The issue requests a user-visible outbound notification for channel plugins when an agent turn ends as `non_deliverable_terminal_turn`.

## Best Possible Solution

Choose one generic delivery contract for non-deliverable terminal turns, then land or replace https://github.com/openclaw/openclaw/pull/102117 with focused tests and redacted real channel proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `non_deliverable_terminal_turn` bypass `message_tool_only` suppression as a narrow core fallback, or should OpenClaw expose a plugin-owned terminal-failure hook instead?

Rationale: Both paths change user-visible channel delivery semantics, and the hook path changes the public plugin contract, so automation should not choose the permanent boundary.

Likely owner: steipete

Owner reason: The decision centers on follow-up delivery and agent-runner fallback semantics, where this account has the strongest recent history.

Owner confidence: medium

Options:

- **Approve narrow core fallback (recommended):** Core sends one sanitized fallback only for confirmed non-deliverable terminal turns, with tests and redacted SDK-channel proof before merge.
- **Add plugin SDK terminal hook:** OpenClaw documents a terminal-failure callback and lets channel plugins decide how to surface fallback messages.
- **Keep strict message-tool-only behavior:** OpenClaw leaves automatic fallback suppressed in this mode and directs visible recovery to plugin-owned handling.

Yes at source level: current main records `non_deliverable_terminal_turn`, but the run result and `message_tool_only` outbound path do not expose a deliverable terminal-failure notification. I did not run a live Octo session.

## Solution Assessment

Unclear until maintainers choose the owner boundary: a core fallback is the broadest user protection, while an SDK hook gives plugins control at the cost of a new public contract.

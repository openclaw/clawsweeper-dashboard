## Label Justifications

- `P1`: A real channel workflow can complete with no outbound user-visible error when the agent turn becomes non-deliverable.
- `impact:message-loss`: The reported failure is that SDK channel plugins receive no outbound notification, leaving the user with no delivered failure message.

## Summary

Keep open: current main still records `non_deliverable_terminal_turn` for display/trajectory but does not expose a terminal-failure notification to SDK channel outbound delivery, and open PR #102117 is only a candidate pending maintainer contract direction and proof.

## What This Changes

The issue requests that `non_deliverable_terminal_turn` produce an outbound user-visible failure notification for SDK channel plugins instead of only a chat-display projection.

## Best Possible Solution

Choose one generic terminal-failure delivery contract, then land PR #102117 or a replacement with focused direct/follow-up tests and redacted SDK-channel proof that the fallback is delivered exactly once.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `non_deliverable_terminal_turn` bypass `message_tool_only` suppression through a narrow core fallback, or should OpenClaw add a plugin-owned terminal-failure hook instead?

Rationale: Both viable fixes change user-visible channel delivery semantics, and one option changes the public plugin SDK contract, so automation should not choose the permanent owner boundary.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve narrow core fallback (recommended):** Core sends one sanitized failure payload for confirmed non-deliverable terminal turns, after the candidate fix is refreshed and proven with a real SDK-channel run.
- **Add a plugin SDK hook:** OpenClaw exposes a documented terminal-failure callback so channel plugins own fallback delivery, accepting public API surface and per-plugin adoption work.
- **Keep strict message-tool-only delivery:** Core does not auto-send in `message_tool_only`, leaving visible recovery to plugin-owned workarounds or broader delivery-contract work.

## Reproduction Assessment

Yes at source level: current main records the terminal marker and projects fallback text for display, but the run result and SDK outbound contract do not notify channel plugins.

## Solution Assessment

Unclear until maintainers choose the owner boundary; core fallback gives broad user protection, while an SDK hook gives plugins control at the cost of new API surface.

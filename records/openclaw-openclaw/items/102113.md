## Label Justifications

- `P1`: A real channel workflow can leave users without an outbound error notification when a terminal agent turn is non-deliverable.
- `impact:message-loss`: The reported failure is that channel plugins receive no outbound notification for a terminal turn, leaving no delivered message.

- `maturity:stable`: The issue maps to gateway-runtime delivery fallback behavior, and `qa/maturity-scores.yaml` lists gateway-runtime as M4 Stable.

## Summary

Keep this issue open: current main still records `non_deliverable_terminal_turn` as trajectory metadata, but the auto-reply and follow-up outbound paths do not turn that marker into a channel-plugin notification, and the open linked PR remains the candidate fix pending maintainer delivery-contract direction.

## What This Changes

The issue asks OpenClaw to notify channel plugins when an agent turn ends as `non_deliverable_terminal_turn` so SDK channels do not silently drop the terminal failure.

## Best Possible Solution

Choose one generic terminal-failure delivery contract, then land https://github.com/openclaw/openclaw/pull/102117 or an equivalent SDK-hook implementation with focused regression coverage and redacted SDK-channel proof.

## Maintainer Decision

Kind: product_direction

Question: Should non-deliverable terminal turns produce an automatic core outbound fallback for channel plugins, or should OpenClaw add a plugin-owned terminal-failure hook instead?

Rationale: Both viable fixes change user-visible channel delivery behavior, and the repository policy treats fallback behavior plus plugin SDK seams as compatibility-sensitive.

Likely owner: steipete

Owner reason: This login has the strongest recent current-main history on the follow-up delivery file whose contract would change.

Owner confidence: medium

Options:

- **Approve core automatic fallback (recommended):** Core sends one sanitized fallback through normal outbound delivery for confirmed non-deliverable terminal turns, protecting current channel plugins by default.
- **Add plugin SDK hook:** OpenClaw adds a documented terminal-failure callback so plugins control delivery, accepting new public API surface and per-plugin adoption work.
- **Keep plugin-owned workaround:** Core leaves `message_tool_only` strict and expects Octo or other plugins to inspect run state or repair delivery in their own repositories.

## Reproduction Assessment

Yes at source level: current main records `non_deliverable_terminal_turn`, while the outbound paths do not consume that marker and still suppress automatic delivery in `message_tool_only`. I did not run a live Octo session.

## Solution Assessment

Unclear until maintainers pick the owner boundary; core fallback is the broadest user protection, while a plugin SDK hook is cleaner for plugin-owned delivery policy but requires public API adoption.

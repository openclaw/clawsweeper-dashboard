## Summary

Keep open: current main still treats the non-deliverable fallback as trajectory/display state rather than an outbound notification for SDK channel plugins, and the linked candidate PR is still open and product-direction blocked.

## What This Changes

The issue requests a core or plugin-SDK delivery path so channel plugins receive a user-visible fallback when a run ends as `non_deliverable_terminal_turn`.

## Best Possible Solution

Choose one generic delivery contract for non-deliverable terminal turns, implement it at the core/channel boundary or as a documented plugin SDK hook, and cover SDK-channel delivery with focused regression plus redacted real channel proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `non_deliverable_terminal_turn` be delivered automatically through the existing channel outbound path, exposed as a public plugin SDK terminal-failure hook, or left to individual channel plugins?

Rationale: Each viable fix changes a compatibility-sensitive boundary: core automatic fallback changes `message_tool_only` delivery semantics, while an SDK hook creates a new public plugin contract.

Likely owner: steipete

Owner reason: This account has the strongest recent history on the auto-reply/follow-up delivery files whose behavior would change.

Owner confidence: high

Options:

- **Approve core automatic fallback (recommended):** Core sends one sanitized fallback through the normal outbound path for confirmed non-deliverable terminal turns, protecting existing and future channel plugins by default.
- **Add plugin SDK terminal hook:** OpenClaw documents a terminal-failure callback so channel plugins control fallback delivery, accepting new API surface and per-plugin adoption work.
- **Keep fallback plugin-owned:** Core leaves `message_tool_only` strict and expects Octo or other plugins to inspect run state or repair their own delivery loops.

## Reproduction Assessment

Yes at source level: current main records the terminal marker and display fallback but still lacks a downstream channel-plugin notification path, and `message_tool_only` follow-up fallback remains suppressed. I did not run a live Octo session.

## Solution Assessment

Unclear until maintainers choose the owner boundary: core-side automatic fallback is the broadest user protection, while an SDK hook gives plugins control at the cost of a new public contract.

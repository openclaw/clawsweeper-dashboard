## Label Justifications

- `P1`: The issue concerns elevated host-exec authority for autonomous cron and heartbeat runs, a high-impact security boundary for real multi-user setups.
- `impact:security`: The requested change prevents prompt-injected or unauthorized scheduled and heartbeat paths from inheriting elevated execution authority through wildcard internal-source allowlists.

## Summary

Keep open: current main still authorizes elevated exec from provider/sender allowlists, while cron jobs and heartbeat runs still lack trusted per-job or heartbeat-specific elevated provenance; the merged agent cron caller-scope work only covers an adjacent ownership boundary.

## What This Changes

Request per-job elevated authority for cron jobs and heartbeat so internal scheduled runs no longer need wildcard elevated allowlists.

## Best Possible Solution

Define one security-reviewed provenance model for scheduled and heartbeat elevated execution, store operator-approved authority with cron/heartbeat state, and migrate users away from wildcard internal-source elevation with audit and docs.

Options:

- **Fold Into Scheduling Provenance (recommended):** Treat elevated execution as part of the broader non-forgeable scheduling provenance design so cron APIs, heartbeat state, audit, and upgrade handling share one authority model.
- **Implement Narrow Markers:** Add per-job and heartbeat-specific elevated approval metadata now, with execution-time checks and docs, while leaving broader scheduling provenance to a later RFC.
- **Fail Closed For Internal Sources:** Remove wildcard internal-source elevation by default and require explicit operator opt-in, accepting upgrade friction for existing cron and heartbeat setups.

## Solution Assessment

Unclear until maintainers choose the trust model; the per-job flag is plausible, but the best fix should cover cron create/update paths, execution-time checks, heartbeat provenance, audit, migration, and docs together.

## Summary

Keep open: current main still resolves elevated execution from provider/sender allowlists, including synthetic `cron-event` and `heartbeat` providers, while cron job records and heartbeat settings do not store the requested per-job or last-modified elevated provenance.

## What This Changes

Request per-job elevated-exec scoping for cron and heartbeat so trusted scheduled work can run elevated without wildcard internal-source access.

## Best Possible Solution

Define one security-reviewed provenance model for scheduled and heartbeat elevated execution, storing operator-approved authority with cron jobs or heartbeat configuration and migrating users away from wildcard internal-source elevation with explicit audit and docs.

## Reproduction Assessment

Yes, at source level: current main still authorizes elevated execution through provider/sender allowlists and synthetic `cron-event`/`heartbeat` providers, while cron jobs and heartbeat config lack per-job or last-modified elevated provenance.

## Solution Assessment

Unclear until maintainers choose the trust model; the per-job flag is plausible, but the best fix should also cover cron updates, execution receipts, heartbeat provenance, migration, and docs.

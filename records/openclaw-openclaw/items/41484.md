## Label Justifications

- `P1`: The issue concerns elevated host-exec authority for autonomous cron and heartbeat runs, a high-impact security boundary for multi-user setups.
- `impact:security`: The requested change prevents prompt-injected or unauthorized scheduled and heartbeat paths from inheriting elevated execution authority.

## Summary

Keep open: current main still resolves elevated execution from provider/sender allowlists, while cron jobs and heartbeat runs lack trusted per-job or last-modified elevated provenance. The merged caller-scope work in https://github.com/openclaw/openclaw/pull/96883 is useful adjacent hardening, but it does not implement this elevated-authority boundary.

## What This Changes

Request per-cron-job and heartbeat-scoped elevated execution provenance so internal cron and heartbeat runs no longer need wildcard elevated access.

## Best Possible Solution

Define one security-reviewed provenance model for scheduled and heartbeat elevated execution, store operator-approved authority with cron/heartbeat state, and migrate users away from wildcard internal-source elevation with audit and docs.

Rationale: The source gap is real, but choosing where trusted authority is created, stored, audited, migrated, and enforced changes the elevated host-exec trust boundary and compatibility behavior for existing cron and heartbeat users.

Owner confidence: high

Options:

- **Fold Into Scheduling Provenance (recommended):** Treat elevated execution as part of the broader non-forgeable scheduling provenance design so cron APIs, heartbeat state, audit, and upgrade handling share one authority model.
- **Implement Narrow Markers:** Add per-job and heartbeat-specific elevated approval metadata now, with execution-time checks and docs, while leaving broader scheduling provenance to a later RFC.
- **Fail Closed For Internal Sources:** Remove wildcard internal-source elevation by default and require explicit operator opt-in, accepting upgrade friction for existing cron and heartbeat setups.

Yes, source-reproducible: current main authorizes elevated execution through provider/sender allowlists and synthetic cron/heartbeat providers while cron job and heartbeat state lack trusted elevated provenance.

## Solution Assessment

Unclear until maintainers choose the trust model; the per-job flag is plausible, but the best fix should cover cron create/update paths, execution-time checks, heartbeat provenance, audit, migration, and docs together.

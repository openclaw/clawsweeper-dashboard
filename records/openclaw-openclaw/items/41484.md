## Label Justifications

- `P1`: The issue concerns elevated host-exec authority for autonomous cron and heartbeat runs, a high-impact security boundary in multi-user setups.
- `impact:security`: The requested change is about preventing unauthorized or prompt-injected scheduled/heartbeat paths from inheriting elevated execution authority.

## Summary

Keep open: current main still authorizes elevated exec through provider/sender allowlists and synthetic cron/heartbeat providers, while cron jobs and heartbeat state do not store trusted per-job or last-modified elevated provenance; https://github.com/openclaw/openclaw/pull/96883 only solved adjacent agent cron caller scoping.

## What This Changes

The issue requests per-job elevated execution authority for cron jobs and heartbeat so internal cron/heartbeat sources no longer need wildcard elevated allowlists.

## Best Possible Solution

Design one security-reviewed provenance model for scheduled and heartbeat elevated execution, store operator-approved authority with cron/heartbeat state, and migrate users away from wildcard internal-source elevation with audit and docs.

Options:

- **Fold Into Scheduling Provenance (recommended):** Treat elevated execution as part of the broader schedule-authority model so cron APIs, heartbeat state, audit, and upgrade handling share one non-forgeable authority contract.
- **Implement Narrow Markers:** Add explicit per-job and heartbeat elevated approval metadata now, with execution-time checks and docs, while leaving broader scheduling provenance for a later RFC.
- **Fail Closed For Internal Sources:** Remove wildcard internal-source elevated authority by default and require explicit operator opt-in, accepting compatibility friction for existing cron and heartbeat setups.

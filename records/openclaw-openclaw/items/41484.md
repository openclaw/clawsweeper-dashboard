## Label Justifications

- `P1`: The issue concerns elevated host-exec authority for autonomous cron and heartbeat runs in multi-user setups.
- `impact:security`: The requested change is about preventing unauthorized scheduled or heartbeat paths from inheriting elevated execution authority.
- `maturity:stable`: The issue affects Gateway runtime Approvals and Remote Execution, and Gateway runtime is scored M4 Stable.

## Summary

Keep open: current main has adjacent agent-scoped cron ownership, but cron jobs and heartbeat still lack persisted elevated approval/provenance, so wildcard internal-source elevation remains an unresolved security-boundary design item.

## What This Changes

Add per-job elevated execution scoping for cron plus heartbeat elevated provenance so internal cron/heartbeat events no longer rely on wildcard allowFrom elevation.

## Best Possible Solution

Design one security-reviewed provenance model for scheduled and heartbeat elevated execution, store operator-approved authority with cron/heartbeat state, and migrate users away from wildcard internal-source elevation with audit and docs.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should elevated cron/heartbeat authority be implemented as a narrow per-job/heartbeat marker now, or folded into the broader non-forgeable scheduling provenance design?

Rationale: The source gap is real, but the permanent trust boundary determines where elevated authority is created, stored, audited, migrated, and revalidated for host exec.

Likely owner: joshavant

Owner reason: They most recently owned the adjacent Gateway cron caller identity implementation and proof path that this authority model would extend.

Owner confidence: medium

Options:

- **Fold Into Scheduling Provenance (recommended):** Treat elevated execution as part of the broader schedule-authority model so cron APIs, heartbeat state, audit, and upgrade handling share one non-forgeable authority contract.
- **Implement Narrow Markers:** Add explicit per-job and heartbeat elevated approval metadata now, with execution-time checks and docs, while leaving broader scheduling provenance for a later RFC.
- **Fail Closed For Internal Sources:** Remove wildcard internal-source elevated authority by default and require explicit operator opt-in, accepting compatibility friction for existing cron and heartbeat setups.

## Reproduction Assessment

Yes. Source inspection reproduces the gap: cron schemas and normalization have no elevated field, heartbeat reply state has no last-modified provenance, and elevated exec still gates on provider allowlists.

## Solution Assessment

Unclear pending maintainer decision; per-job provenance is the right problem boundary, but it should likely align with the broader non-forgeable scheduling API in #71712 rather than adding an isolated flag without audit or migration semantics.

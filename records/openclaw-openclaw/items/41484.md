## Label Justifications

- `P1`: The issue concerns an elevated exec boundary that can affect real multi-user gateway setups using internal cron or heartbeat event elevation.
- `impact:security`: The reported problem is privilege escalation through elevated exec authorization, sandbox escape policy, and scheduled/autonomous run provenance.

## Summary

Keep open: current main has sender allowlists, cron owner scoping, and per-job toolsAllow caps, but it does not have a persisted per-job elevated/provenance gate for cron jobs or HEARTBEAT.md trust, so the central security request remains unresolved.

## What This Changes

Request per-job elevated execution scoping for cron jobs and heartbeat so internal cron/heartbeat event providers no longer need wildcard elevated allowFrom.

## Best Possible Solution

Adopt a provenance-backed scheduled-run elevation contract that removes wildcard internal-provider elevation and includes migration, docs, and tests for cron and heartbeat.

Rationale: This changes the elevated exec security boundary and persisted cron/heartbeat contract; automation should not choose that policy without maintainer intent.

Likely owner: Vincent Koc

Owner confidence: medium

Options:

- **Design provenance-backed elevation (recommended):** Add explicit scheduled-run elevation provenance so trusted owner-created cron/heartbeat work can run elevated without wildcard-elevating internal event providers.
- **Fold into scheduling provenance RFC:** Make issue 71712 the canonical design path and keep this issue as cron/heartbeat elevated acceptance criteria.
- **Keep config-only hardening:** Document avoiding `cron-event` and `heartbeat` wildcard elevation when multiple users can write schedules or heartbeat instructions, accepting reduced scheduled elevated capability.

## Reproduction Assessment

Yes from source inspection: elevated permission is provider/sender allowFrom based, heartbeat uses internal `cron-event`/`heartbeat` providers, and CronJob has owner metadata but no elevation/provenance field; I did not run a live privilege-escalation scenario.

## Solution Assessment

Partially: per-job elevation is a plausible direction, but the best fix should be designed with non-forgeable scheduling provenance rather than adding only a Boolean flag.

## Label Justifications

- `P1`: The issue concerns elevated host-exec authority for autonomous cron and heartbeat runs in multi-user setups.
- `impact:security`: The requested change is about preventing scheduled or heartbeat paths from inheriting elevated execution authority without durable approval provenance.

## Summary

Keep open: current main and v2026.6.11 still gate elevated exec through provider/sender allowlists, while cron jobs, cron storage, and heartbeat runs lack durable elevated-approval provenance; the merged cron caller-scope work only partially addresses the trust boundary.

## What This Changes

The issue asks for per-cron-job and heartbeat provenance controls so scheduled or heartbeat-triggered turns can use elevated exec only when explicitly approved.

## Best Possible Solution

Design one security-reviewed provenance model for scheduled and heartbeat elevated execution, store operator-approved authority with cron and heartbeat state, and migrate users away from wildcard internal-source elevation with audit and docs.

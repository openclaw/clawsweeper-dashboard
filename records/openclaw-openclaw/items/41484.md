## Summary

Keep open: current main has adjacent agent-scoped cron ownership, but it still lacks the requested elevated-exec provenance for individual cron jobs and heartbeat instructions.

## What This Changes

The issue requests per-job elevated execution provenance for cron jobs and heartbeat so internal scheduled/heartbeat sources no longer require broad wildcard elevated access.

## Best Possible Solution

Define a maintainer-approved trust model that records non-forgeable provenance for scheduled work and heartbeat instructions, then gate elevated exec from that provenance instead of internal wildcard senders.

## Maintainer Decision

Required: true

Question: Should OpenClaw add a core trust/provenance model for cron and heartbeat elevated execution, and should it be per-job, scheduling-API based, heartbeat-file metadata based, or folded into the broader scheduling-provenance RFC?

Rationale: The source gap is real, but solving it changes who can grant elevated exec to autonomous scheduled work and how existing cron/heartbeat workflows upgrade safely.

Likely owner: joshavant

Owner confidence: medium

Options:

- **Fold into scheduling provenance RFC (recommended):** Use the open non-forgeable scheduling API RFC as the canonical design and make elevated cron/heartbeat trust one requirement of that broader security boundary.
- **Narrow per-job elevated flag:** Add a focused cron job provenance/elevated field plus migration and tests while leaving broader agent scheduling API design for later.
- **Defer heartbeat trust:** Fix cron provenance first and leave heartbeat elevated behavior behind current `tools.elevated.allowFrom` guidance until a file-edit provenance model exists.

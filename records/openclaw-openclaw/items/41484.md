- `maturity:stable`: The issue affects Gateway runtime approval/remote-execution and security-control authority, and Gateway runtime is scored M4 Stable.

## Summary

Keep open: current main has adjacent agent-scoped cron ownership and isolated cron drops ambient elevation, but cron jobs and heartbeat still lack persisted elevated approval/provenance, so wildcard internal-source elevation remains a real security-boundary design item.

## What This Changes

Request per-job elevated execution provenance for cron jobs and heartbeat so privileged scheduled work can be approved without wildcard internal event-source elevation.

## Best Possible Solution

Design one security-reviewed provenance model for scheduled and heartbeat elevated execution, store operator-approved authority with cron/heartbeat state, and migrate users away from wildcard internal-source elevation with audit and docs.

## Maintainer Decision

Question: Should elevated cron/heartbeat authority be implemented as a narrow per-job/heartbeat marker now, or folded into the broader non-forgeable scheduling provenance design?

Rationale: The source gap is real, but the permanent trust boundary determines where authority is created, stored, audited, migrated, and revalidated for host exec.

Likely owner: joshavant

Owner confidence: medium

Options:

- **Fold Into Scheduling Provenance (recommended):** Treat elevated execution as part of the broader schedule-authority model so cron APIs, heartbeat state, audit, and upgrade handling share one non-forgeable authority contract.
- **Implement Narrow Markers:** Add explicit per-job and heartbeat elevated approval metadata now, with execution-time checks and docs, while leaving broader scheduling provenance for a later RFC.
- **Fail Closed For Internal Sources:** Remove wildcard internal-source elevated authority by default and require explicit operator opt-in, accepting compatibility friction for existing cron and heartbeat setups.

## Reproduction Assessment

Yes, source inspection reproduces the gap: cron schemas and normalization have no elevated field, heartbeat preflight/reply state has no last-modified provenance, and elevated exec still gates on provider allowlists.

## Solution Assessment

Unclear pending maintainer decision; per-job provenance is the right problem boundary, but it should likely align with the broader non-forgeable scheduling API in https://github.com/openclaw/openclaw/issues/71712 rather than adding an isolated flag without audit or migration semantics.

## Summary

Keep open: current main has partial adjacent mitigations for agent-scoped cron ownership and isolated-run ambient state, but it still lacks persisted per-job elevated approval and heartbeat provenance, so wildcard internal-source elevation remains an unresolved security-boundary design item.

## What This Changes

Request per-job elevated authority for cron jobs and heartbeat provenance so internal scheduled runs cannot inherit blanket elevated exec access.

## Best Possible Solution

Design one operator-approved scheduled and heartbeat elevated authority model with persisted provenance, execution-time checks, audit/docs, and a migration away from wildcard internal-source elevation.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should elevated cron/heartbeat authority be implemented as a narrow per-job/heartbeat marker now, or folded into the broader non-forgeable scheduling provenance design in #71712?

Rationale: The source gap is real, but the permanent trust boundary determines where host-exec authority is created, stored, audited, migrated, and revalidated for scheduled and heartbeat runs.

Likely owner: joshavant

Owner reason: They most recently owned the adjacent Gateway cron caller identity implementation and proof path that this authority model would extend.

Owner confidence: high

Options:

- **Fold Into Scheduling Provenance (recommended):** Treat elevated execution as part of the broader schedule-authority model so cron APIs, heartbeat state, audit, and upgrade handling share one non-forgeable authority contract.
- **Implement Narrow Markers:** Add explicit per-job and heartbeat elevated approval metadata now, with execution-time checks and docs, while leaving the broader scheduling RFC for later.
- **Fail Closed For Internal Sources:** Remove wildcard internal-source elevated authority by default and require explicit operator opt-in, accepting compatibility friction for existing cron and heartbeat setups.

## Reproduction Assessment

Yes. Source inspection shows current cron schemas and types lack elevated authority metadata, heartbeat lacks approval provenance, and elevated resolution still authorizes by provider/sender allowlists including wildcard.

## Solution Assessment

Unclear until maintainers choose the trust model; the per-job marker addresses the reported gap only if it is tied to Gateway-owned provenance, audit, execution-time revalidation, and migration semantics.

## Label Justifications

- `P1`: The issue concerns elevated host-exec authority for autonomous cron and heartbeat runs in multi-user gateway setups, but remains design-sensitive hardening rather than a confirmed emergency exploit.
- `impact:security`: The requested change prevents untrusted or later-added users from causing scheduled or heartbeat paths to inherit elevated execution privileges without trusted provenance.

## Summary

Keep open: current main still authorizes elevated exec through provider/sender allowlists and synthetic cron/heartbeat providers, while cron and heartbeat state lack the requested trusted per-job or last-modified elevated provenance.

## What This Changes

Request per-job/operator-approved elevated execution provenance for cron jobs and heartbeat so internal cron/heartbeat events no longer rely on wildcard elevated allowlists.

## Best Possible Solution

Define one security-reviewed provenance model for scheduled and heartbeat elevated execution, store operator-approved authority with cron jobs or heartbeat configuration, and migrate users away from wildcard internal-source elevation with audit and docs.

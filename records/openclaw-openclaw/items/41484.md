## Label Justifications

- `P1`: The issue concerns elevated exec authorization for cron and heartbeat automation, a security boundary that can affect real model-mediated scheduling workflows.
- `impact:security`: The request is about preventing less-trusted senders from escalating into elevated exec through scheduled or heartbeat-originated turns.
- `maturity:stable`: The affected elevated/Gateway RPC security boundary maps to `gateway-runtime` M4 Stable, especially Gateway RPC APIs and Events and Approvals and Remote Execution.

## Summary

Keep open: current main still authorizes elevated exec for heartbeat and cron through internal provider allowlists, while cron jobs and heartbeat configuration have no per-job or provenance-scoped elevated trust model.

## What This Changes

Request per-job and heartbeat elevated exec scoping so scheduled automation does not rely on wildcard internal provider allowlists.

## Best Possible Solution

Design one non-forgeable elevated authorization model for cron jobs and heartbeat, then persist and enforce it through Gateway cron RPC/schema/store, the agent cron tool, heartbeat runner, doctor/docs, and regression tests.

Options:

- **Unify With Scheduling Provenance (recommended):** Use #71712's Gateway-owned provenance model as the authority and add elevated approval as a decision receipt tied to a schedule or heartbeat definition.
- **Add Narrow Per-Job Elevated Approval:** Introduce a smaller cron `elevated` flag that only elevated senders can set, while separately tracking heartbeat approval metadata.
- **Remove Internal Elevated Wildcards:** Fail closed for `cron-event` and `heartbeat` elevated access until operators recreate trusted jobs through an approved path.

## Reproduction Assessment

Yes, source-level: heartbeat/cron turns use internal Provider values, elevated permissions accept provider wildcard allowFrom, and current cron/protocol/storage schemas have no per-job elevated approval field.

## Solution Assessment

The requested per-job flag is directionally right, but the best fix should tie elevation to non-forgeable schedule or heartbeat provenance rather than adding only a mutable boolean.

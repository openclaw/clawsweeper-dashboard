## Label Justifications

- `P1`: The issue concerns elevated host-exec authority for autonomous cron and heartbeat runs, a high-impact security boundary for real multi-user setups.
- `impact:security`: The requested change is about preventing prompt-injected or unauthorized scheduled/heartbeat paths from inheriting elevated execution authority.

## Summary

Keep open: current main still resolves elevated exec through provider/sender allowlists, while cron jobs and heartbeat runs lack trusted per-job or last-modified elevated provenance; PR #96883 only solved adjacent agent cron caller scoping.

## What This Changes

Request per-job elevated exec authority for cron jobs and heartbeat so internal cron/heartbeat runs cannot inherit wildcard elevated privileges without owner-approved provenance.

## Best Possible Solution

Define one security-reviewed provenance model for scheduled and heartbeat elevated execution, store operator-approved authority with cron/heartbeat state, and migrate users away from wildcard internal-source elevation with audit and docs.

- **Fail Closed For Internal Sources:** Remove wildcard internal-source elevation by default and require explicit operator opt-in, accepting upgrade friction for existing cron/heartbeat setups.

## Solution Assessment

## Label Justifications

- `P1`: The issue concerns elevated host-exec authority for autonomous cron and heartbeat runs in multi-user setups.
- `impact:security`: The requested change is about preventing unauthorized scheduled or heartbeat paths from inheriting elevated execution authority.
- `maturity:stable`: The elevated exec trust boundary maps to Gateway runtime approvals and remote execution, and Gateway runtime is scored M4 Stable.

## Summary

Keep open: current main and the latest stable release still resolve elevated execution through provider allowlists while cron jobs and heartbeat config lack durable approval provenance, so this remains an unresolved security-boundary design item.

## What This Changes

Request per-job and heartbeat-scoped elevated execution approval/provenance so scheduled internal runs do not require wildcard `allowFrom` entries for `cron-event` or `heartbeat`.

## Best Possible Solution

Design one security-reviewed provenance model for scheduled and heartbeat elevated execution, store operator-approved authority with cron/heartbeat state, and migrate users away from wildcard internal-source elevation with audit and docs.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should elevated cron and heartbeat authority be implemented as narrow per-job/heartbeat metadata now, or folded into the broader non-forgeable scheduling provenance design?

Rationale: The requested behavior changes the trust boundary for elevated host exec across persisted cron jobs, agent-created schedules, heartbeat files/config, and upgrade behavior, which cannot be safely chosen by automation.

Owner confidence: high

Options:

- **Fold into scheduling provenance (recommended):** Treat this issue as the elevated-exec requirement for the broader non-forgeable scheduling provenance design and keep heartbeat provenance in scope.
- **Implement narrow elevated markers:** Add per-job and heartbeat-modifier elevated approval state now, with explicit migration and tests for create, update, and execution-time checks.
- **Remove internal-source elevation:** Fail closed for cron-event and heartbeat elevated access unless maintainers intentionally preserve a separate compatibility path.

## Reproduction Assessment

Yes at source level: cron schemas and storage lack elevated authority metadata, heartbeat uses internal provider identities, and elevated exec still gates only on provider/sender allowlists.

## Solution Assessment

Unclear pending maintainer decision: per-job provenance is the right problem boundary, but it should likely align with the broader schedule-authority design rather than adding an isolated flag without audit or migration semantics.

## Label Justifications

- `impact:session-state`: The reported consequence is mis-association of a reply with an unrelated topic, including incorrect creation or update of persistent agent work.

## Summary

Keep open. The report supplies packaged-runtime evidence that a WhatsApp reply reached prompt compilation without its quote block, and current-main extraction still has a source-visible path that returns no reply context when the normalized quoted payload is absent. The safe repair policy is unresolved: cached text may not be appropriate to restore for deleted, restricted, or otherwise intentionally unavailable WhatsApp content.

## What This Changes

Preserve trustworthy WhatsApp reply context for the agent when a native reply arrives without an embedded quoted-message payload.

## System Context

WhatsApp inbound events are decoded from Baileys payloads, normalized into an inbound message, and then formatted into the agent prompt. Quote extraction determines whether the prompt receives the familiar reply block or only the new message text, which can affect how the agent associates a short reply with ongoing work.

## Best Possible Solution

Capture a privacy-redacted failing Baileys context shape, then implement a single WhatsApp-owned policy that preserves a structural reply reference when trustworthy metadata survives while exposing cached body text only under explicitly safe conditions, with regression coverage for both recoverable and unavailable cases.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: When a WhatsApp reply supplies an identifier but omits its quoted body, should OpenClaw show only a structural unavailable-reference by default, or may it recover cached body text under defined safe conditions?

Rationale: This is a user-visible context-recovery choice with a privacy boundary: an omitted body can mean transport loss, but may also mean the source intentionally did not provide the message content.

Likely owner: Bartok9

Owner reason: Their merged quote-metadata work is the strongest available current-main history connection to the relevant cache contract.

Owner confidence: medium

Options:

- **Default to structural context (recommended):** Preserve a trustworthy reply identifier and clearly mark the quoted body unavailable; recover text only after a narrowly specified safe-source contract is established.
- **Allow bounded cache recovery:** Use the existing TTL cache when the available Baileys fields prove the quote is ordinary recoverable content, with explicit tests for unavailable-content exclusions.
- **Keep current omission:** Continue dropping reply context unless WhatsApp supplies the body, avoiding any risk of re-exposing withheld content at the cost of ambiguous agent prompts.

A redacted live `messages.upsert` context shape is needed to distinguish recoverable omission from intentionally unavailable content.

## Solution Assessment

Unclear. A cache-based recovery alone is not yet the best fix because the missing payload may be a privacy or availability signal; the safest maintainable route first establishes a precise recovery contract and preserves structural context when text cannot safely be restored.

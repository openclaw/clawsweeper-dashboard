## Summary

Keep open: current main and v2026.6.11 include the partial metadata-padding fix, but the shared multi-action `message` schema still exposes poll fields and `message.send` still rejects content-bearing poll fields before channel delivery. The remaining behavior is a real source-visible bug, but the durable fix needs maintainer direction on the model-facing tool contract.

## What This Changes

The issue asks for ordinary `message.send` with attachments to stop being rejected when shared poll fields leak into non-poll sends on Feishu and other channels.

## Best Possible Solution

Keep the shipped metadata-padding fix, then land a maintainer-approved message-tool contract change: action-scoped poll fields or explicit send-side normalization with focused regression coverage and live Feishu or Telegram send proof.

## Maintainer Decision

Kind: product_direction

Question: For plain `message.send`, should OpenClaw hide poll content fields from send-capable schemas, strip accidental poll fields at runtime, or keep rejecting content-bearing poll fields as explicit poll intent?

Rationale: The remaining behavior affects the model-facing message tool contract across multiple channels, and changing it requires deciding whether send reliability or strict poll-intent validation wins when a model supplies contradictory fields.

Likely owner: gumadeiras

Owner reason: Their merged poll gating and schema-consistency history is the strongest signal for the shared send/poll contract boundary.

Owner confidence: high

Options:

- **Action-scope poll fields (recommended):** Expose poll creation fields only for poll actions or channel-specific poll tools so ordinary sends cannot inherit them from the shared schema.
- **Strip on send:** Treat `action="send"` as authoritative and drop poll creation fields before delivery, improving send reliability but potentially hiding callers that meant to create a poll.
- **Keep strict guard:** Continue rejecting content-bearing poll fields on send and require stronger live evidence before changing the shared tool contract.

## Reproduction Assessment

Partly yes: source inspection and existing tests show current main still rejects `message.send` when non-empty `pollQuestion` or `pollOption` are present. I did not establish a live model-driven Feishu or Telegram repro proving those fields are still auto-filled on current main.

## Solution Assessment

Unclear: the shipped validator narrowing is a good partial fix, but the durable solution depends on a maintainer choice between action-scoped schemas, send-time sanitization, or preserving the strict poll-intent guard.

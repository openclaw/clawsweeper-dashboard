## Label Justifications

- `P1`: The report describes a shared message-tool failure that can block real channel sends and attachment delivery for users, with multiple channel confirmations.
- `impact:message-loss`: Plain channel messages or file sends can fail before delivery when the model supplies poll fields on the shared `message` tool.

## Summary

Keep open: current main and v2026.6.11 fixed metadata-only poll padding, but the shared multi-action message schema still exposes poll fields in non-poll Feishu/Telegram-style send contexts and `message(action="send")` still rejects content-bearing poll fields before delivery.

## What This Changes

The issue asks OpenClaw to keep plain `message(action="send")` with attachments from being blocked by poll fields exposed on the shared message tool schema.

## Best Possible Solution

Land a maintainer-approved message-tool contract change that keeps plain sends free of poll-field pollution while preserving explicit poll creation semantics for channels/actions that actually support polls.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should the shared message tool solve this by action-scoping the LLM-facing schema, by sanitizing poll fields on `send`, or by keeping the current content-bearing poll rejection as the contract?

Rationale: The remaining choice changes the public tool contract: stripping content-bearing fields can hide mistaken poll intent, while keeping the guard leaves schema-driven models able to block ordinary sends when the broad schema is exposed.

Likely owner: Peter Steinberger

Owner reason: The central choice is about the shared message tool's product/API shape, and this history trail starts with Peter's message-tool and action-handling commits.

Owner confidence: medium

Options:

- **Action-scope the schema (recommended):** Recommended: stop exposing poll creation fields in send-oriented schemas for non-poll actions/channels, while preserving strict poll validation for explicit `action="poll"`.
- **Sanitize send params:** Strip poll fields from `action="send"` before the guard, accepting that a model's accidental real-looking poll payload will be treated as a plain send.
- **Keep current guard:** Document the current behavior and require models/operators to disable or avoid poll-capable schemas when plain sends are critical.

## Reproduction Assessment

Partly: source inspection gives a deterministic path where `message(action="send")` with non-empty `pollQuestion` or `pollOption` still throws before delivery. I did not establish a live current-main model/channel repro showing those fields are still auto-filled after the metadata-padding fixes.

## Solution Assessment

Unclear: current main is a partial fix, not the best final solution, because it narrows metadata false positives but leaves poll fields exposed in broad multi-action schemas. The best fix likely needs action-scoped schema generation or an explicitly approved sanitization policy.

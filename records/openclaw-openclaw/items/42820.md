## Summary

Keep open: current main and v2026.6.11 fixed metadata-only poll padding, but the generic message schema still exposes poll fields and `message.send` still rejects before delivery when content-bearing poll fields are present.

## What This Changes

The issue asks for the shared `message` tool to stop letting poll-schema fields make ordinary Feishu and other channel `action: "send"` calls fail before file/message delivery.

## Best Possible Solution

Keep the shipped metadata-padding fix, then have maintainers choose and land a durable message-tool contract: action-scoped schemas, action-aware sanitization, or an explicit decision that content-bearing poll params should keep failing on `send`.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For plain `message.send`, should OpenClaw prevent models from seeing poll content fields in the send schema, strip accidental poll fields at runtime, or keep rejecting content-bearing poll fields as explicit poll intent?

Rationale: Current code intentionally accepts schema-padded poll metadata but rejects non-empty poll content fields on send; changing that boundary affects shared channel delivery semantics across Feishu, Telegram, Discord, Slack, and other message-tool channels.

Likely owner: steipete

Owner reason: The remaining question is a shared model-facing tool contract decision, and the existing review discussion plus prior message-tool schema split history make this the best available routing candidate.

Owner confidence: medium

Options:

- **Action-scope poll fields (recommended):** Expose poll creation fields only for poll actions or channel-specific poll tools, reducing accidental model fill while preserving strict poll validation.
- **Strip on send:** Treat `action: "send"` as authoritative and drop poll fields before delivery, improving reliability but potentially masking poll intent mistakes.
- **Keep strict guard:** Continue rejecting content-bearing poll fields on send and require callers or schema discovery to avoid generating them accidentally.

## Reproduction Assessment

Yes at source level: current `message.send` still throws before delivery when non-empty `pollQuestion` or `pollOption` is present. I did not establish a live current-main Feishu or Telegram reproduction showing a model still emits those content fields after the metadata fix.

## Solution Assessment

Unclear: the shipped validator narrowing is a good partial fix for metadata padding, but the durable remaining solution depends on a maintainer choice between action-scoped schemas, send-side sanitization, or preserving strict poll-intent validation.

## Summary

Keep open: current main and v2026.6.11 include the metadata-padding fix, but the shared message tool still exposes poll fields on multi-action schemas and still rejects `send` before delivery when content-bearing poll fields are present. The linked closing PR is an open, conflicting, non-maintainer-modifiable fork PR, so it is not a safe canonical fix path.

## What This Changes

The issue requests that `message(action="send")` for Feishu and other channels not fail when poll fields from the shared message-tool schema are present during ordinary file or text sends.

## Best Possible Solution

Keep the shipped metadata-padding fix, then have maintainers choose and land a durable message-tool contract: action-scoped schemas, action-aware sanitization, or an explicit decision that content-bearing poll params should keep failing on `send`.

## Reproduction Assessment

Partly: we have a source-level reproduction for the remaining content-bearing variant because current `message.send` still throws when `pollQuestion` or `pollOption` is present. I did not establish a live current-main Feishu or Telegram reproduction showing a model still emits those content fields after the shipped metadata fix.

## Solution Assessment

Unclear: the shipped validator narrowing is a good fix for metadata padding, but the broader request needs a maintainer choice between narrowing schemas, stripping accidental content fields, or preserving strict poll-intent validation.

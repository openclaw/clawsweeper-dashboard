## Summary

Keep open: current main and v2026.6.11 fix metadata-only poll padding, but Feishu still uses the shared multi-action message schema that exposes poll fields, and `message.send` still rejects content-bearing poll params before channel delivery. The remaining question is a shared model-facing message-tool contract decision, not a stale Feishu-only report.

## What This Changes

The issue asks for ordinary `message(action="send")` calls with text or files on Feishu and other channels to stop failing because poll fields are exposed by the shared message-tool schema.

## Best Possible Solution

Keep the shipped metadata-padding fix, then choose a durable shared message-tool contract, preferably action-scoped or channel-scoped poll fields with focused send/poll tests and live Feishu or Telegram proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should ordinary `message(action="send")` stop seeing or stop honoring poll creation fields, or should non-empty `pollQuestion` and `pollOption` continue to reject send as explicit poll intent?

Rationale: Current code intentionally accepts metadata-only padding but still rejects content-bearing poll fields; changing that boundary affects shared tool schemas and channel delivery semantics across Feishu, Telegram, Discord, and other message-tool channels.

Likely owner: gumadeiras

Owner reason: Their merged poll gating and schema consistency work is the strongest history signal for the shared send/poll contract boundary.

Owner confidence: high

Options:

- **Action-scope poll fields (recommended):** Expose poll creation fields only for `poll` actions or channel-specific poll tools so normal sends cannot be polluted by poll schema fields while explicit poll validation stays strict.
- **Strip poll fields on send:** Treat `action="send"` as authoritative and remove poll creation params before delivery, improving send reliability but potentially hiding mistaken poll calls.
- **Keep strict content guard:** Continue rejecting non-empty poll content on send and require live evidence before changing the model-facing contract further.

## Reproduction Assessment

Partly: current source still rejects `message(action="send")` when non-empty `pollQuestion` or `pollOption` is present, and current tests preserve that rejection. I did not establish a live current-main Feishu or Telegram reproduction showing that models still emit those content fields after the metadata-padding fix.

## Solution Assessment

Unclear: the shipped validator narrowing is a good partial fix, but the best remaining solution depends on a maintainer choice between action-scoped schemas, send-side sanitization, or preserving strict content-bearing poll rejection.

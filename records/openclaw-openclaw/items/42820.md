## Summary

Keep open: current main and v2026.6.11 fixed the metadata/default poll-padding false positive, but the shared multi-action message tool still exposes poll creation fields and `message.send` still rejects content-bearing poll fields before channel delivery. The remaining fix needs a maintainer product/API decision rather than cleanup closure.

## What This Changes

The issue asks OpenClaw to make `message.send` for Feishu and other channels tolerate shared poll schema fields, by splitting/scoping the schema or sanitizing poll fields for send actions.

## Best Possible Solution

Settle one message-tool contract that keeps ordinary `send` free of poll creation semantics while preserving explicit `poll` validation, then lock it with focused regression coverage for content-bearing and metadata-only poll fields.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `message.send` ignore or strip content-bearing poll fields that were auto-filled, or should the model-facing schema be split/scoped so poll creation fields are not visible for send actions?

Rationale: Current main intentionally keeps strict rejection for `pollQuestion` and `pollOption` on `send`; deciding whether to preserve that guard, sanitize it away, or redesign the schema changes the model-facing tool/API contract.

Likely owner: @gumadeiras

Owner reason: They authored the original poll gating and message-tool discovery work that owns this API boundary.

Owner confidence: high

Options:

- **Scope poll fields out of send (recommended):** Make the model-facing `send` schema omit poll creation fields and keep strict poll validation inside the explicit `poll` action.
- **Sanitize poll fields on send:** Strip content-bearing poll creation fields for `action="send"` before the guard and rely on `action="poll"` for real poll creation.
- **Keep the strict guard:** Leave the current behavior and document that any non-empty poll content field means the caller must use `action="poll"`.

## Reproduction Assessment

Yes, source-reproducible: current source and tests show `message.send` still rejects non-empty `pollQuestion` or `pollOption` before channel delivery. I did not run a live Feishu or Telegram repro in this read-only review.

## Solution Assessment

Unclear: the current partial fix is not the full requested solution because it only allows metadata-only poll padding. The best fix depends on maintainer direction between schema scoping and send-time sanitization.

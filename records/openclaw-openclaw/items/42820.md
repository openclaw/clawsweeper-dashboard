## Label Justifications

## Summary

Keep open: current main fixed the metadata/default poll-padding subset, but Feishu still gets the non-send-only shared message schema with poll fields exposed, and `message.send` still rejects content-bearing poll params before channel delivery. The remaining fix is a shared message-tool contract decision, with an open but conflicting closing PR proposing one direction.

## What This Changes

Adjust the shared `message` tool so Feishu and other `action: "send"` file/message sends are not blocked by poll fields exposed through the shared schema.

## Best Possible Solution

Land one maintainer-approved shared contract: preferably action-scope poll creation fields away from ordinary `send`, or explicitly sanitize send-path poll fields while preserving real `poll` action validation, with Feishu/Telegram send+attachment and poll regression coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should `message.send` ignore schema-populated poll creation fields, or should the message tool schema be action/channel-scoped so ordinary sends never expose poll creation fields?

Rationale: Current main intentionally rejects `pollQuestion` or `pollOption` on `send`, while the issue asks for ordinary sends not to be blocked by fields exposed through the shared schema; choosing strip/sanitize versus schema split changes the shared tool contract for all channels.

Likely owner: vincentkoc

Owner reason: Recent current-main blame and PR history put this maintainer-routing decision closest to the current shared poll guard implementation.

Owner confidence: medium

Options:

- **Action-scope the schema (recommended):** Expose poll creation fields only when the `poll` action is available or selected, keeping ordinary sends small and preserving strict rejection for real misuse.
- **Sanitize send params:** Strip poll creation params from `action="send"` before the guard, matching the open PR direction but making explicit poll-looking content on send silently ignored.
- **Keep current guard:** Treat `pollQuestion` and `pollOption` on `send` as real poll intent and close only if maintainers decide the metadata-only fix is sufficient.

## Reproduction Assessment

Yes for the source-level failure: current tests and code show `action="send"` with `pollQuestion` or `pollOption` still throws before channel dispatch. I did not run a live Feishu file-send path in this read-only review.

## Solution Assessment

Unclear until maintainer direction: the current metadata-only narrowing is a useful partial fix, but it does not solve the shared schema overexposure that can still put content-bearing poll fields on ordinary sends. The safer long-term solution is likely action-scoped schema exposure rather than another broad runtime fallback.

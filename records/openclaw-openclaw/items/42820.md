## Summary

Keep open: current `main` and `v2026.6.11` narrowed the metadata-only false positive, but the shared multi-action message schema still exposes poll fields and `message.send` still rejects content-bearing poll fields before channel delivery. The remaining fix is a real message-delivery bug, but it needs maintainer direction on the model-facing tool contract.

## What This Changes

The issue asks for `message.send` to stop failing ordinary Feishu and other channel sends when model-populated poll fields are present in the shared tool schema.

## Best Possible Solution

Define an action-aware message-tool contract where ordinary `send` schemas do not invite poll creation fields, while explicit `poll` keeps its validation and channel-specific support.

Options:

- **Use action-scoped schemas (recommended):** Expose poll creation fields only for explicit poll actions or channel-owned poll schemas, so generic sends cannot be polluted by those fields.
- **Sanitize all poll fields on send:** Strip or ignore poll creation fields on `action="send"` before the guard, preserving delivery at the cost of masking accidental poll intent.
- **Keep the narrowed guard:** Treat `pollQuestion` or `pollOption` on send as a hard error and close the broader schema-shape request as not planned.

## Reproduction Assessment

Yes from source inspection: current `message.send` still rejects non-empty `pollQuestion` or `pollOption`, and Feishu’s multi-action schema path can still expose poll fields even though Feishu does not advertise a poll action. I did not run a live Feishu or Telegram delivery scenario in this read-only review.

## Solution Assessment

Unclear as an implementation choice: the shipped metadata-only fix is useful but does not fully solve the schema overexposure reported here. The best next solution is a maintainer-approved action-scoped schema or send-time sanitization policy with focused regression tests.

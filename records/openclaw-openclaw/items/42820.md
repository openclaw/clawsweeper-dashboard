## Summary

Keep open: current `main` and `v2026.6.11` fixed metadata-only poll padding, but the broader shared message-tool contract remains unresolved because multi-action message tools still expose poll fields and `message.send` still rejects content-bearing poll fields before delivery.

## What This Changes

The issue asks OpenClaw to prevent normal Feishu, Telegram, and other channel `message.send` calls with attachments from being blocked by poll fields exposed in the shared message-tool schema.

## Best Possible Solution

Keep the shipped metadata-padding fix, then choose a durable message-tool contract: action-scoped or channel-scoped poll schemas, or explicit send-side normalization, so plain sends cannot be blocked by schema-padded poll fields while real poll creation remains validated.

## Maintainer Decision

Kind: product_direction

Question: Should plain `message.send` prevent models from seeing poll content fields, strip accidental poll fields at runtime, or keep rejecting content-bearing poll fields as explicit poll intent?

Rationale: The current code intentionally accepts metadata-only padding but still rejects non-empty poll content fields; changing that boundary affects the shared model-facing message-tool contract across multiple channels.

Likely owner: gumadeiras

Owner confidence: high

Options:

- **Action-scope poll fields (recommended):** Expose poll creation fields only for poll actions or channel-specific poll tools, reducing accidental model fill while preserving strict poll validation.
- **Strip on send:** Treat `action="send"` as authoritative and drop poll creation fields before delivery, improving reliability but potentially hiding wrong-action callers.
- **Keep strict guard:** Continue rejecting content-bearing poll fields on send and require stronger live evidence before changing the tool contract further.

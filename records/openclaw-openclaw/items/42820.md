## Summary

Keep open: current main and v2026.6.11 fixed schema-padded poll metadata false positives, but the shared multi-action message schema still exposes content-bearing poll fields and `message.send` still rejects them before channel delivery. The remaining work is a shared message-tool contract decision, and an open closing PR still references this issue but is conflicting.

## What This Changes

The issue requests that plain `message.send` for Feishu and other channels not fail merely because poll fields are exposed by the shared message tool schema.

## Best Possible Solution

Keep the shipped metadata-padding fixes, then make a maintainer-approved message-tool contract change: action-scoped poll schemas or explicit send-time sanitization with focused regression coverage and live Feishu or Telegram send proof.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should ordinary `message.send` hide or strip poll creation fields, or should OpenClaw keep rejecting content-bearing poll fields such as `pollQuestion` and `pollOption` on send?

Rationale: Current main intentionally fixed metadata-only false positives but still rejects content-bearing poll fields, and changing that behavior affects the shared model-facing message-tool contract across channels.

Likely owner: gumadeiras

Owner reason: Their merged poll gating and schema consistency work is the strongest current history signal for the shared send/poll boundary.

Owner confidence: high

Options:

- **Action-scope poll fields (recommended):** Expose poll creation fields only for `poll` or channel-specific poll-capable surfaces so plain sends cannot inherit them from the shared schema.
- **Strip on send:** Treat `action="send"` as authoritative and remove poll creation fields before delivery, improving send reliability while possibly masking mistaken poll calls.
- **Keep strict guard:** Preserve the shipped content-bearing rejection and require stronger live evidence before changing the shared message-tool contract.

## Reproduction Assessment

Partly yes. Current main source and tests still reject `message.send` when non-empty `pollQuestion` or `pollOption` are present, but this review did not establish a live model-driven Feishu or Telegram reproduction after the metadata-padding fixes.

## Solution Assessment

Unclear. The shipped validator narrowing is a good partial fix, but the best remaining solution depends on a maintainer choice between action-scoped schemas, send-time sanitization, or preserving strict content-bearing poll rejection.

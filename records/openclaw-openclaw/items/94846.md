- `P2`: This is a real scheduled-cron delivery bug with operator impact, but it is bounded to isolated agentTurn cron outcome classification and delivery dispatch.
- `impact:message-loss`: The reported run produced final assistant output but did not dispatch it to the configured channel.
- `impact:session-state`: The parent cron run state diverges from the successful isolated session outcome by recording the recovered run as an error.

## Summary

Keep open: current main and the latest release still let recovered tool-warning runs on non-preferred channels be classified as fatal before delivery dispatch, and open linked PRs already cover the likely fix path.

## What This Changes

Fix recovered isolated cron agentTurn runs so final assistant output remains eligible for delivery when an earlier tool warning is non-terminal.

## Best Possible Solution

Land one narrow cron payload-outcome fix that treats recovered tool warnings with final assistant output as non-fatal for delivery on non-preferred channels, while preserving genuine fatal structured errors and run-level failures.

## Reproduction Assessment

Yes, at source level: current main still gates recovered `⚠️ 🛠️` tool-warning recovery on `preferFinalAssistantVisibleText`, and the fatal structured-payload branch returns before delivery dispatch when that warning remains fatal. I did not run the live WSL2/Feishu scheduled setup in this read-only review.

## Solution Assessment

Yes, the best fix is the narrow classifier/payload-selection change in cron isolated-agent helpers, not a broad cron status rewrite or new config flag. The open linked PRs should be reviewed and consolidated around that owner boundary.

## Summary

Keep open: the PR targets a real gateway/CLI bug, but the central `NodeRegistry.invoke` guard can reject currently capable desktop/headless nodes because current command policy filters `system.execApprovals.get/set` out of the live command surface before the new check runs.

## What This Changes

The branch adds a `NodeRegistry.invoke` capability check that returns `UNSUPPORTED_CAPABILITY` for connected nodes whose non-empty command list omits the invoked command, plus node-registry tests for that guard and the legacy empty-list path.

## Best Possible Solution

Land one canonical fix that preserves or advertises exec-approval commands for capable nodes, rejects true missing-capability cases with a structured error, and includes redacted real CLI/Gateway proof.

## Reproduction Assessment

Yes by source inspection for the PR defect: current command reconciliation filters exec-approval IDs out of `node.commands`, and the PR rejects on that filtered field before dispatch. I did not run a live Windows node or Docker setup in this read-only review.

## Solution Assessment

No, not as submitted. Gateway-side validation is the right direction, but the guard must be paired with the command-advertisement/policy fix or kept in the scoped exec-approvals handler so capable nodes are not misclassified as unsupported.

## Label Justifications

- `P2`: This is a normal-priority Telegram access-control improvement with real usability value and security-boundary impact, but no current core outage.
- `impact:security`: The requested policy changes who may trigger an agent from Telegram groups and how trusted group membership is verified.
- `impact:ux-friction`: Current users must manually add each new Telegram group chat ID, which creates repeated setup friction without fully blocking use.

## Summary

Keep open: current main and v2026.6.11 still expose only `open`, `disabled`, and `allowlist`; the closed `members` implementation PRs and the chat-only-trigger plugin are useful prior art/workarounds, not a shipped bundled Telegram access policy.

## What This Changes

The issue requests a Telegram `groupPolicy: "members"` mode that authorizes new groups when every current participant is trusted by user allowlist, avoiding per-group chat-ID allowlisting.

## Best Possible Solution

Define and land an explicit bundled Telegram `members` policy across config types/schema/metadata, inbound and native-command authorization, security audit semantics, docs, and focused tests while preserving existing policies.

## Reproduction Assessment

Yes for the missing capability: current-source inspection shows `groupPolicy: "members"` is not accepted by the shared type/schema and Telegram runtime authorization has no membership-verification branch. This is a feature request rather than a broken shipped policy, so no live Telegram repro was run.

## Solution Assessment

Unclear until maintainers choose the access-control contract. If accepted, the maintainable solution belongs in the bundled Telegram group-policy path rather than relying on the adjacent chat-only-trigger workaround, because inbound and native-command authorization own this safety boundary.

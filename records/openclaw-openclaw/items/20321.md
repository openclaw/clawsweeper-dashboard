## Label Justifications

- `P2`: This is a normal-priority Telegram access-control improvement with clear usability value and security-boundary impact but no current core outage.
- `impact:security`: The requested policy changes who may trigger an agent from Telegram groups and how trusted group membership is verified.
- `impact:ux-friction`: Users who create many Telegram groups must currently register each group chat ID or use weaker/open policies, which adds avoidable configuration burden.

## Summary

Keep open: current main and v2026.6.11 still expose only `open`, `disabled`, and `allowlist`; the closed `members` PRs and the chat-only-trigger plugin are useful prior art or workarounds, but they do not provide the requested bundled Telegram access policy.

## What This Changes

The issue requests a Telegram `groupPolicy: "members"` mode that authorizes new groups by verifying all current members against trusted user allowlists instead of pre-registering each group chat ID.

## Best Possible Solution

Define and land an explicit bundled Telegram `members` policy across config type/schema/metadata, inbound and native-command authorization, security audit semantics, docs, and focused tests while preserving existing policies.

## Reproduction Assessment

Yes for the missing capability: current-source inspection shows current main and v2026.6.11 reject `groupPolicy: "members"` at the type/schema layer and the Telegram runtime path has no membership-verification branch. This is a feature request rather than a broken shipped policy, so no live Telegram repro was run.

## Solution Assessment

Unclear until maintainers choose the access-control contract. If accepted, the maintainable solution belongs in the bundled Telegram group-policy path rather than relying on the adjacent chat-only-trigger plugin workaround, because inbound and native-command authorization own this safety boundary.

## Label Justifications

- `P2`: This is a normal-priority Telegram access-control improvement with real usability value and no current core outage.
- `impact:security`: The requested policy changes who may trigger an agent from Telegram groups and how trusted group membership is verified.
- `impact:ux-friction`: Users can work around the gap by manually allowlisting every group, but that adds avoidable setup friction and silent non-response when a group is missed.

## Summary

Keep open: current main and the latest release still only support `open`, `disabled`, and `allowlist`; the closed implementation PRs and chat-only-trigger plugin are useful prior art, not the requested bundled Telegram `members` policy.

## What This Changes

Request a Telegram `groupPolicy: "members"` mode that authorizes new groups from trusted current members instead of requiring each group chat ID to be pre-registered.

## Best Possible Solution

Define and land an explicit bundled Telegram `members` policy across config schema/metadata, inbound and native-command authorization, security-audit semantics, docs, and focused tests, with fail-closed behavior for uncertain membership checks.

## Reproduction Assessment

Yes for the missing capability: current-source inspection shows `groupPolicy: "members"` is rejected at the type/schema layer and Telegram group authorization has no membership-verification branch. This is a feature request rather than a broken shipped policy, so no live Telegram repro was run.

## Solution Assessment

Unclear until maintainers choose the access-control contract. If accepted, the maintainable path is a bundled Telegram policy in the existing config and authorization surfaces rather than relying on the adjacent chat-only-trigger plugin workaround.

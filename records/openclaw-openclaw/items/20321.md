## Label Justifications

- `P2`: This is a normal-priority Telegram access-control improvement with limited blast radius but real usability and security implications.
- `impact:security`: The requested policy changes who may trigger an agent from Telegram groups, which is an authorization boundary.
- `impact:ux-friction`: Current behavior forces users to manually register each new Telegram group chat ID, creating avoidable setup friction for heavy group use.

## Summary

Keep open: current main and v2026.6.11 still do not accept or implement a Telegram `groupPolicy: "members"` path, and the remaining work is a security-sensitive product decision rather than stale cleanup.

## What This Changes

Request a Telegram `groupPolicy: "members"` mode that authorizes newly created groups from trusted user membership instead of requiring every group chat ID to be allowlisted.

## Best Possible Solution

Land a maintainer-approved Telegram `groupPolicy: "members"` design in the Telegram plugin, config schema/metadata, docs, native-command auth, inbound auth, and security audit surfaces while preserving existing `open`, `disabled`, and `allowlist` behavior.

## Reproduction Assessment

Yes for source proof: current main rejects the requested policy at the config type/schema level and the Telegram authorization helper has no `members` branch. This is a feature request rather than a failing existing contract.

## Solution Assessment

Unclear until maintainer review: a bundled Telegram policy is the right layer if OpenClaw wants this behavior, but the final implementation must first settle the membership and fail-closed security semantics.

## Summary

Keep open: current main and v2026.6.11 still do not implement the requested bundled Telegram `groupPolicy: "members"` mode. The request is valid and scoped, but it changes Telegram group authorization and config semantics, so it still needs maintainer/security product judgment before a repair PR is safe.

## What This Changes

Request a Telegram group policy that allows new groups automatically when every current member is trusted, avoiding per-group chat ID allowlisting.

## Best Possible Solution

Define and land an explicit bundled Telegram `members` policy across config schema/metadata, inbound and native-command authorization, security audit semantics, docs, and focused tests while preserving existing `open`, `disabled`, and `allowlist` behavior.

## Reproduction Assessment

Yes for the missing capability: current-source inspection shows current main and v2026.6.11 accept only `open`, `disabled`, and `allowlist`, and the Telegram runtime path has no membership-verification branch. This is a feature request rather than a broken shipped policy, so no live Telegram repro was run.

## Solution Assessment

Unclear until maintainers choose the access-control contract. If accepted, the maintainable solution belongs in the bundled Telegram group-policy path rather than relying on the adjacent community plugin workaround, because inbound and native-command authorization own this safety boundary.

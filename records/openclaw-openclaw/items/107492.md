## Summary

The reported mechanism does not exist on current main: OpenClaw checks whether one of three CA bundle paths is readable while constructing managed-service startup environment, but it does not read or parse PEM certificates for HTTPS connections. Node owns loading `NODE_EXTRA_CA_CERTS` and documents that it is read when the process launches, so the proposed parsed-certificate cache would target the wrong layer. ([github.com](https://github.com/openclaw/openclaw/blob/main/src/bootstrap/node-extra-ca-certs.ts))

## What This Changes

Avoid alleged repeated synchronous CA-certificate parsing by resolving and caching certificates during startup.

## Best Possible Solution

Keep the current startup-path resolution; if latency is still observed, open a new report with a current-main CPU or synchronous-I/O profile identifying the exact repeated stack before changing bootstrap code.

## Maintainer Decision

No. Current-main source has only a bounded path-readability check during managed-service environment construction, while Node loads `NODE_EXTRA_CA_CERTS` at process launch; no per-connection OpenClaw parsing path was found.

## Solution Assessment

No. Caching parsed certificates in `node-startup-env.ts` is not applicable because OpenClaw never parses them; profiling any observed latency and fixing the attributed call path is the maintainable approach.

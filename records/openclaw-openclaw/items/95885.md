## Summary

Keep open: current head still has a concrete byte-compaction retry metadata bug. The PR is in the right runtime area and has useful proof, but when the active transcript comes from `followupRun.run.sessionFile` and the compactor omits an unchanged `result.sessionFile`, the retry guard can persist metadata for a stale entry file and allow the repeated byte-triggered compaction loop to continue.

## What This Changes

The PR adds persisted byte-triggered compaction retry metadata to session entries and suppresses same-file byte-triggered preflight compactions until the active transcript grows materially, while preserving token-triggered compaction.

## Best Possible Solution

Record byte-trigger retry metadata against the active post-compaction transcript that was actually compacted, then land only after maintainers accept the growth-threshold suppression policy.

## Reproduction Assessment

Yes at source level: current main recalculates the byte trigger every preflight with no memory of a prior byte-triggered compaction result. I did not run a live long-session reproduction in this read-only review.

## Solution Assessment

No as currently written: the PR is in the right runtime boundary, but retry state must be keyed to the active post-compaction transcript file instead of falling back to a stale entry when the compactor omits unchanged result fields.

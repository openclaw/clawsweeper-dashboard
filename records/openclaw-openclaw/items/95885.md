## Summary

Keep open for maintainer review: the previous active-transcript retry-state finding is addressed and I found no new blocking patch defect, but the PR intentionally changes persisted session-state behavior and needs maintainer acceptance of the byte-compaction retry hysteresis before merge.

## What This Changes

The branch adds persisted `SessionEntry` byte-compaction retry metadata and uses it to suppress repeated `maxActiveTranscriptBytes` preflight compactions until the active transcript file, threshold, or material byte growth changes.

## Best Possible Solution

Land after maintainers accept the additive retry metadata and 1 MiB/10% byte-growth hysteresis as the supported byte-compaction retry policy; otherwise tune the constants or lifecycle rule with matching tests before merge.

## Reproduction Assessment

Do we have a high-confidence way to reproduce the issue? Yes, at source level: current main recalculates the byte trigger each preflight with no retry metadata, so an oversized successor transcript can immediately trigger byte compaction again.

## Solution Assessment

Is this the best way to solve the issue? Yes for the code boundary: the guard lives in the preflight decision path, persists only the retry facts it needs, preserves token-triggered compaction, and covers active transcript drift; the remaining question is maintainer acceptance of the hysteresis policy.

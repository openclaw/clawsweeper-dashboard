## Summary

Keep open: current main still lacks a hook-time browser URL contract for `before_tool_call` on browser `act`/`type`, and the reporter's credential-vault workaround confirms the remaining security-sensitive plugin API gap rather than solving it in core.

## What This Changes

The issue requests that browser `before_tool_call` hooks receive the current page URL, or an equivalent query path, so domain-pinned credential plugins can validate the active browser origin before injection.

## Best Possible Solution

Add a narrow, additive browser/plugin contract that gives pre-action browser security hooks a policy-safe current tab URL for `act`/`type`, or an equivalent supported query seam, with tests for blocked/private URLs and supported browser profiles.

Options:

- **Add a scoped query helper:** Keep hook params unchanged and expose a browser state helper that trusted plugins can call when a policy check needs the current URL.
- **Keep plugin-local caching:** Leave core unchanged and require credential plugins to keep fail-secure tab URL caches from navigate/open and after-tool-call results.

Yes. Source inspection shows the pre-tool hook receives only the browser action params before route code resolves or redacts a current tab URL; I did not run a live browser/plugin scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the API shape. Native support is the right end state, but params enrichment versus a scoped query helper needs security-boundary review.

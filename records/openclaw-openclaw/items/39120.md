## Summary

Keep open: current main and v2026.6.11 still reject custom-basename extra bootstrap files, and the open closing PR remains the active but unmerged/conflicting implementation candidate, so this issue is still needed as the canonical product decision.

## What This Changes

The issue requests support for explicitly configured arbitrary workspace files in bootstrap context injection instead of only recognized bootstrap basenames.

## Best Possible Solution

Land https://github.com/openclaw/openclaw/pull/74735 or a narrow replacement that allows explicitly configured in-workspace custom basenames through existing realpath, size, budget, session-filtering, docs, and test guardrails after maintainer approval.

Question: Should OpenClaw accept explicitly configured custom-basename workspace files as part of the core bootstrap-extra-files hook contract?

Rationale: The requested behavior changes which workspace content enters deterministic startup context and expands user-facing hook configuration semantics, so automation cannot choose the product/security boundary on its own.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve explicit in-workspace files (recommended):** Allow custom basenames only when explicitly configured and still protected by workspace containment, size budgets, session filtering, docs, and focused tests.
- **Keep recognized basenames only:** Reject arbitrary file injection and keep operators on first-class workspace filenames or manual reads until a broader context API exists.
- **Defer to a broader context API:** Keep this issue open until maintainers design a larger context-loading contract covering discovery, trust, session scoping, and diagnostics.

## Solution Assessment

Unclear until maintainers choose the contract. The existing bundled hook is the narrow plausible owner boundary, but the active PR or replacement must preserve workspace guards, budgets, session filtering, docs, and focused tests.

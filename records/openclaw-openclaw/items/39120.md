## Summary

Keep open: current main and v2026.6.11 still reject explicitly configured extra bootstrap files whose basename is not recognized, and the open linked implementation PR remains the active product-review path.

## What This Changes

The issue requests deterministic bootstrap/session context injection for explicitly configured arbitrary workspace files instead of limiting extra bootstrap paths to recognized bootstrap basenames.

## Best Possible Solution

Keep this as the canonical tracker and resolve it by landing https://github.com/openclaw/openclaw/pull/74735 or a narrower maintainer-approved replacement that preserves workspace guards, prompt budgets, session filtering, docs, and focused tests.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw accept explicitly configured custom-basename bootstrap files as a core hook contract, and should that contract be global-only or exact-session scoped as proposed in https://github.com/openclaw/openclaw/pull/74735?

Rationale: This is feasible in code, but it changes deterministic prompt context, file-loading scope, and user-facing hook configuration semantics, which repository policy treats as product and compatibility-sensitive.

Likely owner: steipete

Owner reason: They merged the original hook work and later refactored the same boundary-safe bootstrap read path, making them the strongest decision-routing signal from history.

Owner confidence: high

Options:

- **Approve Repaired Hook Contract (recommended):** Allow custom-basename files through the existing bootstrap-extra-files path after the linked PR or a replacement preserves path guards, budgets, filtering, and clear docs.
- **Narrow To Global Extras:** Accept arbitrary explicitly configured global paths while deferring exact session-key selectors to a separate design.
- **Keep Recognized Basenames:** Reject arbitrary bootstrap injection for now and steer users toward first-class bootstrap files or manual workspace conventions.

## Reproduction Assessment

Yes. Source inspection shows a configured extra bootstrap path such as hooks/REGISTRY.yaml reaches loadExtraBootstrapFilesWithDiagnostics() and is skipped because REGISTRY.yaml is not in VALID_BOOTSTRAP_NAMES.

## Solution Assessment

Unclear pending maintainer direction. The linked PR is a plausible bounded implementation, but the best final shape depends on whether maintainers want global arbitrary extras, exact session-scoped extras, or no expansion of the current contract.

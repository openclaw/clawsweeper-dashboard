## Summary

Keep open: current main and v2026.6.11 still implement `openclaw agent --deliver` as delivery of agent-produced reply payloads, not literal delivery of the original message. The remaining direct-notification and session-injection directions need maintainer product and security decisions, and the only open closing PR is a stale/conflicting fork PR rather than a landed fix.

## What This Changes

The issue requests direct channel delivery for `openclaw agent --deliver` and a direct session-injection path instead of running a full agent turn.

## Best Possible Solution

Keep `message send` as the direct notification path unless maintainers approve an explicit direct mode, and split session injection into a separate authorized API with clear status, audit, and replay semantics.

## Reproduction Assessment

Yes, at source level: current main routes `--deliver` through the agent run and then delivers only agent-produced payloads. I did not run a live Signal delivery test in this read-only review.

## Solution Assessment

No. Redefining `agent --deliver` as literal send duplicates `message send` and conflicts with the documented command boundary; a separate direct mode or session-injection API needs maintainer product and security approval first.

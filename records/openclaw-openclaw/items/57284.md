## Summary

Keep open: current main and the latest release still define `openclaw agent --deliver` as agent-reply delivery, while literal direct notification delivery and direct session injection remain product/security decisions; the open linked fork PR is conflicting and the earlier same-direction PRs were closed unmerged after maintainer boundary feedback.

## What This Changes

The issue requests deterministic direct notification delivery for `openclaw agent --deliver` and a separate direct session-injection path instead of routing the message through a full agent turn.

## Best Possible Solution

Keep `openclaw message send` as the direct notification path, keep `agent --deliver` as agent-reply delivery unless maintainers approve a new explicit direct mode, and handle direct session injection through a separately authorized API design.

## Reproduction Assessment

Yes, at source level: current main routes `--deliver` through an agent run and then delivers only agent-produced payloads, with no-visible `NO_REPLY` output covered as suppressed delivery. I did not run a live Signal delivery test in this read-only review.

## Solution Assessment

No, not as originally requested: redefining `agent --deliver` as literal send duplicates `message send` and conflicts with the current documented command boundary. The maintainable path is either clearer status surfacing for suppressed agent replies or a separate explicit direct/session-injection API after product and security approval.

## Summary

Keep open: current main and v2026.6.11 still treat `agent --deliver` as agent-reply delivery, not literal notification send, and the remaining direct-session-injection/status behavior needs maintainer product and security review rather than cleanup closure.

## What This Changes

The issue requests direct channel delivery for `openclaw agent --deliver` and a non-LLM session injection path so notifications are not silently lost.

## Best Possible Solution

Keep `openclaw message send` as the direct notification path, improve `agent --deliver` suppressed-result docs/status behavior if maintainers want that safety net, and split direct session injection into a separate authorized API design such as the live-session wake work.

## Reproduction Assessment

Yes at source level: current main routes `--deliver` through an agent run and then delivers only agent-produced reply payloads, with no direct-delivery request field. I did not run a live Signal delivery test in this read-only review.

## Solution Assessment

No for the original requested shape: redefining `agent --deliver` as literal send duplicates the documented `message send` command and was already rejected in maintainer PR discussion. A separate explicit mode or session-injection API needs product and security approval first.

## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P2] Pass captureId through stop and cancel:** `apps/android/app/src/main/java/ai/openclaw/app/NodeRuntime.kt:1730-1736`
  - body: `InvokeDispatcher` forwards `paramsJson` for talk commands and the gateway leaves non-system params unchanged, but this adapter still drops those params and calls no-arg stop/cancel. A delayed stop or cancel for an older capture will therefore resolve the current `activePttCaptureId` and can tear down the newer session instead of returning `idle`; parse the requested `captureId` and pass it to the capture-scoped TalkModeManager methods.
  - confidence: 0.93
- **[P2] Let active-capture retries bypass preparation:** `apps/android/app/src/main/java/ai/openclaw/app/NodeRuntime.kt:1710-1713`
  - body: A foreground `talk.ptt.start` retry still enters `withPreparedTalkPttCommand` before TalkModeManager can return the existing capture. That path refreshes `talk.config` through the default 15s gateway request and stop/cancel take the same preparation mutex, so a user release can be stuck behind a retry that should have been idempotent; short-circuit the active capture before preparation or keep stop/cancel off that lock for retry-only work.
  - confidence: 0.89
- **[P2] Invalidate queued one-shot retries on completion:** `apps/android/app/src/main/java/ai/openclaw/app/NodeRuntime.kt:1883-1887`
  - body: `finishTalkCaptureIfIdleAfterPreparation` clears ownership for a completed one-shot but does not advance `talkPttCommandEpoch`; only explicit stop/cancel does that below. A duplicate `talk.ptt.once` that captured the old epoch and was delayed in preparation can still pass the epoch check after the original auto-stops and open a second microphone capture, so terminal one-shot cleanup needs to invalidate queued stale starts.
  - confidence: 0.86
- **[P3] Remove the release-owned changelog entry:** `CHANGELOG.md:45`
  - body: The changelog line from the earlier review is still present. Root AGENTS.md marks `CHANGELOG.md` as release-owned, so this normal PR should keep the release-note context in the PR body or squash message instead of editing the generated release log.
  - confidence: 0.96

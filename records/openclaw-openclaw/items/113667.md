## Summary

This is a focused Telegram reliability fix with credible controlled runtime proof and broad successful CI, but the branch retains a legacy dedupe-cache migration that writes V1 rows into a namespace the new runtime deliberately never reads. That dead quarantine path conflicts with the repository policy for transient cache state and should be removed before merge.

## What This Changes

The PR changes Telegram’s persistent dispatch-dedupe identity from account/chat/message to account/bot/chat/message, bypasses dedupe when bot identity is invalid, and separates legacy replay rows from new runtime claims.

## System Context

Telegram updates enter the bundled Telegram channel and pass through a persistent replay guard before OpenClaw dispatches inbound work. The guard stores short-lived replay claims in plugin state so same-bot redelivery can be suppressed even after a runtime restart.

## Architecture Diagram

flowchart LR
  A[Telegram update] --> B[Telegram handler]
  B --> C[Resolve bot identity]
  C --> D[Persistent replay guard]
  D -->|new claim| E[Inbound dispatch]
  D -->|duplicate claim| F[Suppress replay]
  C -->|identity unavailable| G[Fail-open dispatch]
  G --> E

## Best Possible Solution

Use only the canonical V2 replay cache at runtime and in migration/doctor handling: drop obsolete V1 replay-cache import rather than quarantining it, retain fail-open behavior for invalid identities, and keep the focused cross-bot and restart-persistence coverage.

## Summary

Keep open: current main has meaningful SecretRef, audit, redaction, command-scoped resolution, and plugin-hook mitigations, but it still does not provide the native masked-secret/process-isolation boundary requested for arbitrary agent-usable API keys.

## What This Changes

Request a native masked-secrets system so agents can use API keys without seeing raw values, including substitution, output redaction, blocked credential reads, and configuration.

## Best Possible Solution

Keep this open until secops/product either ships or explicitly rejects a native credential-boundary design for agent-executed commands, with raw values kept out of agent-readable files/env/context and plugin hooks documented as complementary mitigations.

Options:

- **Sponsor a core/secops design (recommended):** Define a native credential injection and redaction boundary, including config/API shape, migration/audit behavior, exec semantics, and plugin-provider extension points before implementation.
- **Defer to plugins and OS isolation:** Document the current SecretRef plus plugin-hook plus OS/container isolation model as the supported approach and keep core from promising arbitrary masked command secrets.
- **Close as not planned:** Explicitly reject native masked secrets in core and direct users to external credential proxies or ClawHub plugins for this threat model.

Yes, by source inspection: current docs state plaintext credentials in agent-readable files remain readable, and the exec path inherits process.env and returns command output. I did not run a live secret-leak repro because it would require creating or exposing credential-like data.

## Solution Assessment

Unclear until maintainers choose the security boundary; current SecretRefs and plugin hooks are good mitigations but not the native masked-secret design requested. The best maintainable path is a secops-owned design that names the credential owner, injection point, redaction guarantee, and migration/audit behavior before code work starts.

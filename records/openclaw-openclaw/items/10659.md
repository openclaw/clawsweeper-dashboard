## Summary

Keep this security feature request open for an explicit owner decision. The prior current-main review identifies useful mitigations—structured SecretRefs, runtime snapshots, redaction, and plugin hooks—but not the requested supported boundary that prevents an agent from reading raw credentials while still using them; the linked user-isolation guide and credential-vault plugin are valuable workarounds, not a core replacement.

## What This Changes

The issue requests a native credential-isolation design that lets agents use scoped API credentials without reading raw values or leaking them through tool output, context, or transcripts.

## Best Possible Solution

Define and implement a security-owned credential-execution boundary: secrets remain outside agent-readable files and ambient environments, are injected only into narrowly scoped execution/provider paths, and are redacted before persistence or model-visible output, with a documented threat model and plugin/SDK contract.

- **Adopt a plugin-first contract:** Document the existing hook surface as the supported extension route and specify any missing narrow SDK capability without promising core isolation.
- **Decline the guarantee:** Document that host-level separation remains the required boundary for arbitrary agent command execution and close the request only with that explicit policy decision.

## Reproduction Assessment

No high-confidence end-to-end reproduction was run in this read-only review. Source review maps the requested gap: current mitigations do not constitute a general isolation boundary for credentials readable by agent-executed processes.

## Solution Assessment

No—the proposed syntax and command blocking are not yet shown to be the best durable solution. A scoped credential-provider and process-injection design is safer than relying on string placeholders or an incomplete denylist of shell commands.

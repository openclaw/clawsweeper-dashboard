## Summary

Keep this issue open: current main documents that SecretRefs and redaction do not provide same-process isolation from an agent, while the discussion identifies a draft scoped credential-broker direction rather than an accepted replacement for the requested boundary. This security-sensitive feature needs an explicit owner decision before implementation.

## What This Changes

The issue requests a native credential boundary that lets agents use approved API keys without reading raw values from files, environment variables, command output, transcripts, or chat context.

## Best Possible Solution

Adopt one documented credential-isolation contract, preferably extending the scoped broker only after security and plugin owners define a narrow capability declaration, dispatch-time injection boundary, output/transcript treatment, and upgrade behavior; keep the Linux-isolation guide and credential-vault plugin as interim mitigations.

Rationale: Current protections reduce accidental disclosure but do not isolate a credential from code running in the same agent process; deciding the supported trust boundary determines whether core, plugin SDK, or external deployment owns the solution.

Options:

- **Broker-first core boundary (recommended):** Define a narrow broker-backed capability contract that injects credentials only at dispatch time and keeps plaintext outside model/tool arguments and ambient agent environment.
- **External and plugin boundary:** Document host isolation and credential-provider plugins as the supported solution and avoid adding an agent-exec secret contract to core.
- **Exec defense-in-depth only:** Add narrowly scoped named-environment removal and exact-value redaction while documenting that it is not credential isolation.

## Reproduction Assessment

Yes, at source level: a credential present in an agent-readable environment or file can be printed by ordinary command execution, and current secrets documentation says SecretRefs/redaction do not create same-process isolation. No fresh live reproduction was run in this read-only review.

## Solution Assessment

No—the proposed placeholder syntax and command blocklists are not the best primary fix because they cannot reliably isolate a same-process secret. A scoped broker or an explicitly external/plugin-owned isolation boundary is safer, but its contract requires owner approval.

## Summary

Keep open: current main and the latest release include substantial SecretRef, audit, migration, and redaction hardening, but they still explicitly do not provide the native masked-secret or process-isolation boundary requested here.

## What This Changes

Request native masked-secrets support so agents can use credentials without seeing raw API keys, including runtime substitution, output redaction, command blocking, and a mask-list config surface.

## Best Possible Solution

Keep this open until security/product maintainers either ship or explicitly supersede a native credential-isolation design for agent-executed commands and process output, with current plugin and OS-isolation mitigations documented as interim options.

## Maintainer Decision

Rationale: The gap is source-proven and security-sensitive, but the fix defines a credential trust boundary and public config/API behavior rather than a narrow bug repair.

Likely owner: openclaw/openclaw-secops

Options:

- **Sponsor a security-owned native design (recommended):** Define the credential boundary, dispatch-time injection, exact redaction, migration/docs, and plugin-provider integration before implementation.
- **Route through credential-broker/plugin seams:** Keep core lean by prioritizing the missing broker or plugin APIs that let external credential providers cover this safely.
- **Declare external hardening the supported path:** Close the core direction only after maintainers explicitly choose OS isolation, external proxies, and ClawHub plugins as the supported answer.

## Reproduction Assessment

Yes, source-reproducible: current docs explicitly say plaintext credentials in agent-readable files remain readable via file or shell tools, and current exec code still returns command output. I did not run a live secret-leak command because this read-only review should not handle real secrets.

## Solution Assessment

Unclear as proposed: placeholder substitution, output redaction, and command blocking are plausible mitigations, but they are not enough by themselves to define a reliable security boundary. The best path needs a maintainer-approved credential-isolation or CredentialProvider/broker design with bypass, upgrade, and plugin semantics spelled out.

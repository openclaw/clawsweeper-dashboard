## Summary

Keep open. Current main and v2026.6.11 provide substantial SecretRef storage, runtime-snapshot, migration, and redaction hardening, but they do not create the requested boundary between the general agent shell and credentials used by approved tools. The open security roadmap remains the canonical umbrella, and this protected security item still needs an explicit secops product decision.

## What This Changes

Add native credential capability isolation so agent-run actions can use secrets without exposing raw values to the model, general shell, transcripts, or plaintext local state.

## Best Possible Solution

Define a secops-owned credential capability contract that injects values only beyond the general agent boundary, reuses structured SecretRefs and exact-value redaction, and leaves backend-specific vault or broker implementations plugin-owned.

Question: Should OpenClaw support selected credentials that approved tools can use but the general agent shell and model cannot read?

Rationale: This changes the documented single-operator authority model and introduces compatibility-sensitive core and plugin contracts, so automation cannot safely choose the boundary.

Likely owner: @openclaw/openclaw-secops

Owner reason: CODEOWNERS assigns the relevant security model, source, configuration, and documentation surfaces to this team.

Owner confidence: high

Options:

- **Isolated capability injection (recommended):** Add a narrow core broker seam for isolated executors or outbound request owners without returning raw values to the agent.
- **External isolation only:** Keep core focused on SecretRef storage and redaction, with separate users, sandboxes, services, or plugins as the confidentiality boundary.
- **Best-effort masking:** Add placeholders and output masking while explicitly documenting that they do not form a security boundary.

## Reproduction Assessment

Yes. Current source and documentation establish that an unsandboxed same-user shell can inspect ordinary environment variables and readable credential files, while SecretRef and redaction paths do not create process isolation.

## Solution Assessment

No, not in the exact proposed form. Isolated scoped injection is stronger and more maintainable than placeholder substitution plus command blacklists, which cannot reliably protect secrets remaining in the same process or trust domain.

## Label Justifications

- `P1`: The issue concerns an agent-readable credential boundary that can expose real API keys in normal tool workflows.
- `impact:security`: The requested behavior is explicitly about preventing agents and transcripts from seeing raw secrets.
- `impact:auth-provider`: The affected surface is credential resolution and SecretRef/provider-backed auth material.

## Summary

Keep open: current main has SecretRef support, secret audit/scrub docs, redaction helpers, and plugin hooks, plus the linked external hardening/vault workarounds, but it still explicitly documents that readable plaintext credentials remain agent-readable and does not provide the requested native masked-secret boundary.

## What This Changes

Add a native masked-secrets system so agents can use configured credentials without seeing raw API key values.

## Best Possible Solution

Define and ship, or explicitly supersede, a native credential-isolation design with security-owner approval, migration/audit guidance, and clear core/plugin API boundaries.

## Reproduction Assessment

Yes at source level: current docs state readable plaintext remains agent-readable, and current config/exec source lacks the requested placeholder and mask-list boundary.

## Solution Assessment

The goal is valid, but the exact fix is not yet settled because existing plugin hooks and external vaults are mitigations rather than a maintainer-approved core security contract.

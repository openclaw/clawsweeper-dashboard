## Summary

Keep this issue open for security-owner direction. Current main provides structured SecretRefs, eager runtime snapshots, sentinel-backed command resolution, and redaction, but its published security contract still says agent-accessible processes and tools are not a supported secret-isolation boundary; the requested native guarantee therefore remains unresolved. citeturn576764view0turn136118view0

## What This Changes

Requests a native masked-secrets boundary that lets agents use credentials without reading raw values and redacts accidental disclosure.

## Best Possible Solution

Define a core security contract that keeps raw credentials outside agent-readable files, environment, prompts, and general-purpose subprocesses, then expose narrowly scoped capability or credential-provider APIs with dispatch-time injection, exact-value egress redaction, migration guidance, and explicit threat-model documentation.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw guarantee that agent-controlled tools and subprocesses cannot access raw credentials, and which enforceable boundary should provide that guarantee?

Rationale: The existing runtime intentionally trusts same-user processes, while arbitrary commands can exfiltrate any injected value; choosing process isolation, capability mediation, or an external-only boundary changes the core security and plugin contract.

Likely owner: @openclaw/openclaw-secops

Owner reason: This choice defines the repository's credential isolation and threat-model boundary across secrets, execution, plugins, and gateway behavior.

Owner confidence: high

Options:

- **Adopt a capability boundary (recommended):** Design a core-owned broker or isolated executor where agents request allowlisted capabilities and raw credentials are injected only after authorization outside the agent-readable process.
- **Support external isolation only:** Keep SecretRefs scoped to configuration-at-rest protection and document plugins, OS user isolation, and external gateways as the supported agent credential boundary.
- **Narrow to constrained tools:** Add credential injection only for explicitly declared tools and destinations, leaving arbitrary shell commands outside the guarantee.

## Reproduction Assessment

Yes, the exposure is source-reproducible: a secret placed in an agent-readable file or environment can be read through general-purpose tools, and the current security docs explicitly describe that trust boundary. No live command execution was needed to establish the documented behavior.

## Solution Assessment

No, placeholder substitution plus blocking commands such as `env`, `echo`, or `cat` is not the best complete solution because equivalent commands and external exfiltration remain available. A capability-mediated or isolated execution boundary is narrower, enforceable, and more maintainable, with redaction retained as defense in depth.

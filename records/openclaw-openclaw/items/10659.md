## Summary

Keep this issue open for explicit security-owner direction. Current main provides structured SecretRefs, runtime resolution, redaction, and plugin hooks, but its documentation explicitly does not treat SecretRefs as an agent-access boundary; the linked Linux-isolation guide and credential-vault plugin are useful mitigations rather than a native resolution.

## What This Changes

Request a native credential boundary that lets approved tools use secrets while preventing the general agent shell, context, transcripts, and outputs from exposing raw values.

## Best Possible Solution

Define a core security-owned capability broker that injects credentials only into approved operations, keeps raw values out of agent-readable files, environment, prompts, and transcripts, and exposes a narrow plugin provider contract with redaction as defense in depth.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw guarantee that credentials used by approved tools are inaccessible to the general agent shell through a core capability broker, or formally retain the current shared host-process trust boundary?

Rationale: The guarantee determines process isolation, plugin APIs, configuration and migration contracts, and whether arbitrary host exec can remain enabled; implementation cannot safely choose this boundary on its own.

Likely owner: @steipete

Owner reason: They supplied the latest explicit security assessment and are the clearest available owner for choosing whether this guarantee belongs in core.

Owner confidence: high

Options:

- **Create a core credential broker (recommended):** Add capability-scoped dispatch and plugin-provider APIs so approved operations receive credentials without exposing raw values to the general agent process.
- **Use plugin-managed isolation:** Keep core SecretRefs as configuration indirection and document supported plugin or OS-isolation patterns for stronger credential separation.
- **Retain the shared trust boundary:** Document that agents with arbitrary host exec share the credential trust domain and focus core work on warnings, least privilege, and redaction.

## Reproduction Assessment

Yes at source level: secrets placed in agent-readable files or its environment remain retrievable through general exec, and current documentation explicitly disclaims SecretRefs as an agent-access boundary. A live secret-exposure run was not required to establish that documented path.

## Solution Assessment

No, the exact placeholder, mask-list, and blocked-command proposal is not the safest complete solution because shell blocklists are bypassable. Capability-scoped credential dispatch with process isolation and a narrow plugin contract is the more maintainable boundary.

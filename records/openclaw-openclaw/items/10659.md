## Summary

Keep this issue open for security-owner direction. Current main substantially improves supported credential handling through structured SecretRefs, runtime snapshots, process-local sentinels, exact-value redaction, migration tooling, and plugin resolvers, but the published security contract still does not guarantee isolation from arbitrary agent-controlled tools or subprocesses. The Linux-isolation guide and credential-vault plugin are useful mitigations, while the recent maintainer-associated review explicitly says the native boundary remains unresolved. citeturn0search1turn0search2turn7view0

## What This Changes

Request a native secret-use boundary that lets agents invoke credentialed operations without exposing raw credentials through agent-readable files, environment variables, command output, or transcripts.

## Best Possible Solution

Define a capability-based credential boundary: keep raw values outside agent-readable files and environments, resolve credentials only at an owned dispatch boundary, inject them into the narrowest child or transport operation, redact exact values before persistence or delivery, and document which providers, channels, plugins, and arbitrary commands are covered. Do not treat command-name blocking as a security guarantee.

Question: What credential-confidentiality guarantee should OpenClaw provide when an agent invokes a tool or command that needs a secret?

Rationale: The choice determines whether core owns a capability broker, only strengthens managed SecretRefs, or formally delegates arbitrary-command isolation to plugins and the operating system; substitution and redaction mechanics cannot decide that threat model safely.

Likely owner: joshavant

Owner confidence: high

Options:

- **Capability broker boundary (recommended):** Add an owned broker or provider contract that gives tools capabilities rather than raw values and injects credentials only at final dispatch, with persistence-safe output redaction and upgrade tests.
- **Managed credentials only:** Guarantee protection only for OpenClaw-managed provider, channel, and plugin credentials, while documenting OS isolation or external proxies for arbitrary shell commands.
- **Plugin-led boundary:** Standardize and document the existing hook-based credential-provider pattern while keeping raw arbitrary-command credential isolation outside core.

## Reproduction Assessment

Yes, source-reproducible: current documentation expressly excludes process isolation from the SecretRef guarantee, so a plaintext credential reachable through an agent-readable file, environment, or deliberately credentialed subprocess remains observable without an external isolation boundary.

## Solution Assessment

No, not as proposed: placeholder substitution, output replacement, and blocking commands such as `env` or `cat` are bypassable mitigations rather than a reliable privilege boundary. A capability broker or narrowly defined managed-credential contract is the safer maintainable design.

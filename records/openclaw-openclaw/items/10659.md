## Summary

Current main substantially hardens secrets with SecretRefs, process-local sentinels, audits, exact-value redaction, and plugin hooks, but the documented contract explicitly remains same-process defense in depth rather than an agent-isolation boundary. The user-isolation guide and `openclaw-credential-vault` plugin are useful mitigations, while this protected security feature still needs a secops decision on the permanent credential capability boundary.

## What This Changes

Provide scoped credential use for agent-executed tools without exposing raw API keys to the agent, command output, transcripts, or chat.

## Best Possible Solution

Define a security-owned credential capability with a strong proxy or signer tier that never returns raw values to agent execution, adding only the minimal plugin SDK and core lifecycle seams needed to enforce redaction before model return, persistence, logs, and delivery.

Kind: security_boundary

Question: Must OpenClaw’s supported masked-credential guarantee keep raw values outside the OpenClaw and agent subprocess address spaces, or is same-process scoped injection an accepted security tier?

Rationale: Current SecretRefs and plugin hooks support same-process injection and defense-in-depth redaction, but they cannot provide the requested guarantee that a compromised agent execution path never accesses raw credentials.

Likely owner: @openclaw/openclaw-secops

Owner reason: This team owns the affected secret, sandbox, authentication, and security documentation contracts.

Owner confidence: high

Options:

- **Capability broker boundary (recommended):** Require the strong supported tier to proxy, sign, or dispatch scoped operations without returning raw credentials to OpenClaw or agent-controlled subprocesses.
- **Two documented tiers:** Add a strong external broker tier and retain same-process scoped injection as a clearly labeled lower-isolation compatibility option.
- **Same-process injection only:** Standardize the current exec-environment hook and redaction model while explicitly declining a raw-secret isolation guarantee.

## Reproduction Assessment

Yes at source level. An agent with exec or file access can request a readable plaintext credential or a credential injected into its subprocess environment, and foreground exec returns process output; current docs explicitly confirm that SecretRefs are not an agent-isolation boundary.

## Solution Assessment

No, the literal placeholder, mask-list, output filter, and command-blocking proposal is not the best fix because it is bypass-prone. A scoped capability broker that does not return raw values is the narrowest design that can satisfy the stated guarantee.

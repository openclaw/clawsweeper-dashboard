## Summary

Current main provides substantial SecretRef, sentinel, redaction, plugin-hook, and sandbox hardening, but its own secrets guide explicitly says these are not process isolation and that readable plaintext files and ordinary environment credentials remain agent-accessible. This security-sensitive feature remains necessary, has active related discussion, and requires a maintainer-owned security contract rather than cleanup closure.

## What This Changes

Add a native credential boundary that lets agent-executed operations use scoped secrets without exposing raw values to agent-readable files, environment, output, transcripts, or model context.

## Best Possible Solution

Extend the secops-owned SecretRef architecture into a typed capability broker: agents reference named operations and credentials, approved adapters authorize and inject values below the agent-facing interface, and exact values are redacted before model, transcript, log, or channel delivery.

Question: Should OpenClaw establish a native capability-scoped credential broker for agent-executed operations, and should that contract live in core or the plugin SDK?

Rationale: Current main intentionally provides separate SecretRef, sentinel, redaction, generic exec-hook, and sandbox primitives but does not promise agent-inaccessible credentials; maintainers must select the authorization model, supported adapters, and permanent owner.

Likely owner: @openclaw/openclaw-secops

Owner reason: CODEOWNERS and feature history place the secrets runtime and its security guarantees under this team.

Owner confidence: high

Options:

- **Core broker seam (recommended):** Add a generic core security contract for named capabilities and approved adapters, while allowing plugins to supply credential providers.
- **Plugin SDK broker:** Standardize plugin-owned credential resolution and operation authorization with core enforcing hook order and result redaction.
- **No native broker:** Require separate-user, container, or external proxy isolation for strong guarantees and document current primitives as mitigations only.

## Reproduction Assessment

Yes. Current docs and source establish that readable plaintext files and ordinary environment credentials remain accessible to an agent-controlled shell, while SecretRefs, sentinels, and redaction mitigate only supported migrated paths.

## Solution Assessment

No. The proposed placeholder plus blocked-command design is bypass-prone through alternate shell syntax and transformed output; a typed, scoped operation resolved inside the owning adapter is the narrower maintainable security boundary.

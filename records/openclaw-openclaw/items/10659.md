## Summary

Keep this issue open for explicit security-owner direction. Current main protects supported credentials with SecretRefs, process-local sentinels, exact-value redaction, migration tooling, and plugin-backed resolvers, but expressly does not guarantee that arbitrary agent-executed commands cannot read plaintext credentials reachable through files or environment variables. The linked Linux-isolation guide and credential-vault plugin are useful mitigations, while the latest maintainer-associated review also says the native boundary remains unresolved.

## What This Changes

Add a native masked-secrets boundary so agents can use credentials without receiving raw values through readable files, environment variables, command output, or chat history.

## Best Possible Solution

Define one generic core credential-use boundary: keep raw values outside agent-readable configuration, files, prompts, and tool arguments; inject credentials only at an owner-controlled final dispatch boundary; redact exact known values before logs, transcripts, and model-visible results; and expose a narrow plugin contract for external vault providers without adding parallel SecretRef syntax unless maintainers explicitly replace the current contract.

Options:

- **Isolation-only contract:** Keep SecretRefs as the supported core mechanism and formally require OS/container isolation or external proxies for credentials used by arbitrary commands.
- **Plugin-first experiment:** Standardize only the minimum SDK seam required for external credential-vault plugins, then reconsider a core guarantee after production proof.

## Reproduction Assessment

Yes at source level: current documentation explicitly states that plaintext credentials in agent-readable files remain readable through file or shell tools and that SecretRefs are not process isolation. A live secret-exfiltration scenario was not executed during this read-only security review.

## Solution Assessment

No, the literal proposal is not yet the best fix. Placeholder substitution, a mask list, and blocked command strings would be bypass-prone and duplicate parts of SecretRef; the safer direction is a maintainer-defined dispatch boundary with exact redaction and one credential-provider contract.

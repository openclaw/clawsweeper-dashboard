## Summary

The Matrix-owned limit is the right direction, but the patch places `pollMaxOptions` on the lazy runtime adapter while core validates polls against the plugin-visible static adapter; the merge result therefore still lets oversized Matrix polls pass shared preflight and dry-run before failing later in content construction. The previous generic-contract finding is fixed, but this current-head integration defect and missing real Matrix proof still block merge.

## What This Changes

The PR adds a 20-option Matrix poll limit to the runtime outbound adapter and poll content builder, with 20/21-option boundary tests and a generic normalization contract test.

## Best Possible Solution

Expose the 20-option maximum on the plugin-visible `matrixChannelOutbound` consumed by core, retain Matrix builder validation for direct callers, reuse a single Matrix-owned limit constant where the package boundary permits, and prove both shared preflight and an actual Matrix send.

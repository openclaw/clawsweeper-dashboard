## Summary

Keep open: current main still has the Telegram ingress-spool retry, deletion, and replay-loss behavior described, and the issue is protected by the `maintainer` label with an open linked fix PR awaiting review.

## What This Changes

The issue requests bounded backoff/dead-lettering for retryable Telegram spooled-update failures, durable requeue for transient replay store errors, and completed-update tombstones to prevent duplicate dispatch.

## Best Possible Solution

Review and land or reject https://github.com/openclaw/openclaw/pull/98776 so the final state has bounded retry backoff, dead-letter unblocking, replay-safe transient errors, and completed-update tombstones in the Telegram ingress spool.

Yes, from source inspection: current main requeues generic retryable Telegram spooled failures without a cap, delays only one error class, and drains on a 500ms interval. I did not run a live Telegram repro in this read-only review.

## Solution Assessment

Unclear until the linked PR is fully reviewed, but the requested fix belongs in the Telegram ingress spool and shared queue completion semantics rather than a new config or external workaround.

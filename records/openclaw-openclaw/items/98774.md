## Summary

Keep open: current main and the latest release still have the Telegram ingress-spool retry, deletion, and replay-loss paths described, and this issue has a protected `maintainer` label plus an open closing PR awaiting review.

## What This Changes

The issue asks for Telegram spooled updates to use bounded retry backoff, dead-letter poison rows, requeue transient replay store errors, and tombstone completed rows instead of deleting them.

## Best Possible Solution

Review and land or reject https://github.com/openclaw/openclaw/pull/98776 so the final implementation has bounded retry backoff, poison dead-letter unblocking, replay-safe transient errors, and completed-update tombstones in the Telegram ingress spool.

## Reproduction Assessment

Yes at source level: current main requeues generic retryable Telegram spooled failures without a cap, delays only one error class, drains on a 500ms interval, and deletes completed rows instead of tombstoning them. I did not run a live Telegram repro in this read-only review.

## Solution Assessment

Yes for the issue direction: the fix belongs in Telegram ingress-spool retry/completion handling and the shared queue semantics already present in current code. The exact linked PR still needs normal maintainer review before merge.

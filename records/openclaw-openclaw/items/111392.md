## Summary

The no-op write optimization addresses the linked Dreaming stall, and the final branch adds focused coverage for its behavior. However, it deliberately changes capacity-bound retention: unchanged rows no longer refresh `created_at`, so a full namespace can evict different persisted workspace rows. That is a product/state-ownership choice rather than a contributor-only documentation choice, so this PR needs explicit owner acceptance or a retention-preserving implementation before merge.

## What This Changes

The PR reads Dreaming workspace-state entries before writing, registers only new or changed canonical values, retains deletion of missing rows and sequential duplicate-key writes, and adds regression coverage including the capacity-eviction case.

## Best Possible Solution

Have the Memory Core and plugin-state owner explicitly choose the capacity policy; if refresh-based retention remains required, preserve it without reinstating full no-op serialization, otherwise record the approved upgrade behavior and keep the focused capacity regression.

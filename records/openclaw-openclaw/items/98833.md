## Summary

Keep open: the branch is a useful hardening step, but it is not merge-ready because it only bounds the hostedContents collection read while the same MS Teams media path still parses the main Graph message with an unbounded `msgRes.json()`, and the contributor proof is test-only.

## What This Changes

The PR replaces `fetchGraphCollection`'s raw `response.json()` call in the MS Teams Graph attachment path with `readResponseWithLimit` under a 256 KiB cap and manual JSON decoding.

## Best Possible Solution

Bound both Graph JSON reads in the MS Teams attachment media path, keep overflow versus malformed-JSON behavior explicit, and add focused overflow proof before merge.

## Reproduction Assessment

Yes, source-level but not live: current main and `v2026.6.11` visibly use raw `response.json()` for the hostedContents collection and raw `msgRes.json()` for the main message. I did not run a streaming/live reproduction because this review is read-only.

## Solution Assessment

No as submitted. Bounding the collection reader is a useful part of the fix, but the best fix also bounds the main-message Graph JSON read and adds representative overflow proof.

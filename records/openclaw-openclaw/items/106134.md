## Summary

The dead-end is clearly supported by the current workshop state gate, and this issue adds meaningful UI transparency beyond the older recovery report, so it remains necessary but should be coordinated with the existing issue rather than implemented independently.

**Likely related people:** shakkernerd is the strongest routing candidate from the original Skill Workshop work; ElieHalioua and Arpit55 are also connected through later Control UI and gateway work.

## What This Changes

Expose quarantine reasons and scanner findings, provide a safe recovery action for quarantined proposals, and optionally add a chat-assisted repair entry point.

## Best Possible Solution

Use one canonical lifecycle design across CLI, gateway, and Control UI: immediately display stored findings and status reason, permit rejection from quarantine, and require revision followed by a fresh scan before returning content to pending; treat chat-assisted repair as a separately approved enhancement using the same revision API.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What recovery transition should quarantined Skill Workshop proposals support without allowing unchanged scanner-blocked content to bypass or endlessly repeat the security gate?

Rationale: Source establishes the dead end, but whether quarantine may be cleared unchanged, only after revision and rescan, or only dismissed is an intentional security and product policy choice.

Likely owner: shakkernerd

Owner reason: The original Skill Workshop proposal lifecycle work is the strongest available ownership signal for choosing recovery semantics.

Owner confidence: high

Options:

- **Revise, rescan, then restore (recommended):** Allow quarantined proposals to be revised or rejected, returning them to pending only after the revised content receives a fresh scan.
- **Unchanged manual restore:** Permit an explicit quarantined-to-pending transition while retaining findings, accepting the risk that apply may immediately quarantine the same content again.
- **Dismissal only:** Allow rejection or deletion from quarantine but require users to create a new proposal for corrected content.

## Reproduction Assessment

Yes from source, though not through an executed live scenario: apply can quarantine a proposal, the mutation helper then rejects every non-pending proposal, and the UI renders actions only for pending records.

## Solution Assessment

Partly. Showing existing findings is the narrowest transparency fix, but an unconditional restore action is not the best recovery design; revision or dismissal should be allowed from quarantine, with a fresh scan required before pending status is restored.

## Summary

The owner-local `ws` timeout is a well-targeted availability fix with convincing controlled-server proof, but the regression currently makes every ClickClack test-file run wait roughly 30 seconds and should use deterministic option wiring instead. The hard fail after 30 seconds also deserves explicit maintainer acceptance as an upgrade-sensitive connection-policy change. Likely related people: `vincentkoc` (medium confidence, recent ClickClack reliability contributor) and `steipete` (medium confidence, adjacent ClickClack project/code ownership).

## What This Changes

The PR gives ClickClack websocket opening handshakes a fixed 30-second deadline and adds source-wiring plus controlled TCP-stall regression tests.

## Best Possible Solution

Keep the owner-local 30-second production deadline, replace the full-duration routine test with deterministic constructor-option coverage, and document or prove that a normal delayed handshake below the deadline still succeeds while the existing reconnect path handles timeout termination.

## Maintainer Decision

## Reproduction Assessment

Yes from source and the supplied controlled-server run: without a client handshake deadline, a TCP peer that accepts but never upgrades can leave the caller pending indefinitely. This read-only review did not independently rerun the 30-second scenario.

## Solution Assessment

Mostly yes: setting the dependency-owned `ws.handshakeTimeout` in the ClickClack client is the narrowest runtime fix and avoids new public configuration. The validation should assert constructor wiring deterministically rather than sleeping through the complete production deadline in routine tests.

## Summary

The timeout addresses a real unbounded wait, but the implementation leaves the losing body read active and the branch still suppresses genuine WhatsApp zero-delivery warnings. The linked ElevenLabs report also does not establish that this OpenAI-compatible provider path is its root cause, so the PR needs repair and real runtime proof before merge.

## What This Changes

The PR adds a deadline around OpenAI-compatible TTS response-body reads and narrows logging severity for selected WhatsApp delivery and gateway startup cases.

## Best Possible Solution

Use one cancellation-aware deadline spanning the request and body read, cancel or abort the response when it expires, clear timer state in a finally block, retain WARN unless a concrete WhatsApp partial-streaming signal is present, and prove the affected provider path with a real stalled-stream run.

## Reproduction Assessment

Yes at source level: a response-body reader that never settles leaves current main waiting indefinitely, and the added unit test models that path. There is no real current-main provider reproduction proving the linked ElevenLabs report follows this implementation.

## Solution Assessment

No. A Promise.race alone bounds the caller but does not cancel the stalled operation; a cancellation-aware deadline with unconditional cleanup is the narrower complete fix.

## Label Justifications

- `P1`: A real ACP session can remain unusable after /reset and currently requires restarting the whole gateway, disrupting active workflows.
- `merge-risk: 🚨 session-state`: Clearing the cache while the old cleanup operation remains active can leave stale runtime work racing with newly reset ACP metadata.
- `merge-risk: 🚨 availability`: The detached runtime may remain hung and unreachable by normal manager cleanup, allowing blocked actors or orphan processes to accumulate.

## Summary

This is a valid P1 recovery bug, but the patch does not yet prove or ensure recovery from a genuinely hung ACP operation: it drops the cache reference without terminating the old runtime or demonstrating that the occupied session actor can make progress. The overlapping https://github.com/openclaw/openclaw/pull/107374 has a more complete manager-owned detach-and-close design, but its real-behavior proof is also pending, so neither PR is currently a safe supersession target.

## What This Changes

The PR evicts cached ACP runtime handles after cancel or close cleanup timeouts and continues resetting ACP metadata so later turns can create a fresh runtime.

## Best Possible Solution

Use one manager-owned force-discard operation that atomically detaches the exact stale handle, initiates backend close and process-tree cleanup without awaiting the hung actor, resets ACP metadata, and has gateway regression tests proving both timeout branches followed by a fresh successful turn.

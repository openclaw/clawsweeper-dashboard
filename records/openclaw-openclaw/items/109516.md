## Summary

Both prior blockers remain on the latest head: the synchronous timeout cannot guarantee that startup returns, and timeout failure can still make an unknown network mount appear safe for WAL. The final commit only retriggers CI, so the implementation needs redesign and real behavior proof before merge.

Likely related people: vincentkoc, with high confidence from the merged network-filesystem WAL implementation history.

## What This Changes

The PR adds a 10-second `SIGKILL` timeout to the synchronous `mount` fallback used during SQLite WAL filesystem safety detection.

## Best Possible Solution

Move mount probing behind a boundary the startup path can abandon independently, preserve an explicit unknown/error classification, select rollback journaling on timeout or lookup failure, and cover success, timeout, and unkillable-child behavior with focused tests plus a real blocked-mount run.

## Reproduction Assessment

Yes at source level: startup invokes a synchronous `mount` lookup, and Node's documented semantics show the proposed timeout can still wait for child exit. The submitted evidence does not reproduce the blocked-filesystem state in a real environment.

## Solution Assessment

No. Adding timeout options to `execFileSync` neither creates a hard return boundary nor preserves the conservative rollback decision when classification fails; an abandonable probe with an explicit fail-closed result is the safer fix.

Overall correctness: patch is incorrect

Overall confidence: 0.9

Full review comments:

- **[P1] Target async timing to the originating UI connection:** `src/gateway/server-runtime-subscriptions.ts:80`
  - body: This async timing callback uses the gateway-wide broadcaster for `chat.send_timing`, but the maintained timing path targets `new Set([connId])` after checking the operator UI client. As written, first-output/completed timing for one chat send can be sent to unrelated connected clients instead of only the originating Control UI connection.
  - confidence: 0.93
- **[P2] Preserve the ACK timing baseline:** `src/gateway/server-runtime-subscriptions.ts:75-77`
  - body: `ackToPhaseMs` is computed from `receivedAtMs`, making it identical to `receivedToPhaseMs`. Existing `chat.send_timing` consumers distinguish time since receive from time since ACK, so the async phases need the stored ACK timestamp rather than a second receive-based value.
  - confidence: 0.9
- **[P1] Extend the existing first-assistant timing contract:** `src/gateway/server-chat.ts:624-626`
  - body: Current main already emits `first-assistant-event` through `ChatRunEntry.chatSendTiming`, including direct dispatch callbacks, throttled delta flushes, and final-flush-only replies. Adding separate `first-output` maps in `ChatRunState` creates a competing timing source and misses the maintained helper semantics; rebase and extend the existing timing entry instead.
  - confidence: 0.86
- **[P2] Drive the production emitter in the latency test:** `src/gateway/server.chat.gateway-server-chat-b.test.ts:1647-1669`
  - body: The new test calls `broadcastToConnIds` directly to append synthetic `first-output` and `completed` events, so it would pass even if the production event subscription never emits those phases. The test should stimulate the real agent event/final path and assert on the events it produces.
  - confidence: 0.97

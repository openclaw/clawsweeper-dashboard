Full review comments:

- **[P1] Target async timing to the originating UI connection:** `src/gateway/server-runtime-subscriptions.ts:82`
  - body: The existing `chat.send_timing` contract targets only the Control UI connection that sent `chat.send`; this new async path calls `params.broadcast`, which can fan the run/session/model timing frame out to every client allowed to read the event. Please carry the originating `connId`/timing entry through the existing chat-run timing path and use targeted delivery.
  - confidence: 0.9
- **[P2] Preserve the ACK timing baseline:** `src/gateway/server-runtime-subscriptions.ts:78-79`
  - body: `ackToPhaseMs` is computed from `receivedAtMs`, making it identical to `receivedToPhaseMs` and losing the ACK baseline that current timing consumers rely on. Store/use the ACK timestamp, as current main's `ChatRunTiming.ackedAtMs` does, before emitting post-ACK phases.
  - confidence: 0.88
- **[P1] Extend the existing first-assistant timing contract:** `src/gateway/server-chat.ts:641-642`
  - body: Current main already emits `first-assistant-event` for the first assistant payload, including final-only replies, and the UI parser recognizes that phase. Adding a separate `first-output` phase here creates a competing contract that current UI code drops and misses the existing final-flush coverage; please extend the maintained timing entry instead of adding a parallel phase.
  - confidence: 0.87
- **[P2] Drive the production emitter in the latency test:** `src/gateway/server.chat.gateway-server-chat-b.test.ts:1693-1705`
  - body: The new test manually pushes `first-output` and `completed` frames into `broadcastToConnIds`, so it would pass even if the production `emitServerTiming` wiring never fires or broadcasts to the wrong recipients. Exercise `createAgentEventHandler`/`startGatewayEventSubscriptions` and assert the real emitter output instead.
  - confidence: 0.86

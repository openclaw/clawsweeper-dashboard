## Summary

Keep open: several independent live reports show isolated cron sessions completing successfully while recovered tool or run-level diagnostics still force an error status, suppress delivery, increment failure state, and sometimes retry an already completed message send. The open related PR addresses recovered payload errors but explicitly leaves run-level `meta.error` fatal, so it does not resolve the broader report.

## What This Changes

Correct isolated cron status, delivery, retry, and diagnostics when useful work completes despite a recovered tool or run-level error.

## Best Possible Solution

Make the shared canonical agent terminal outcome authoritative for cron execution status, preserve recovered or post-run failures as typed diagnostics, and retry only when the canonical task outcome is unsuccessful and no committed delivery side effect makes replay unsafe.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Which terminal signal should isolated cron treat as authoritative when useful output or external side effects completed but the run record also contains an error?

Rationale: The choice controls persisted health, error counters, alerts, delivery suppression, and replay of non-idempotent side effects; a broad text-based recovery heuristic could also conceal genuine failures.

Likely owner: abnershang

Owner reason: Their merged work most directly owns the current recovered-error classifier and its regression coverage.

Owner confidence: medium

Options:

- **Canonical terminal outcome (recommended):** Use the shared agent terminal-outcome contract for success, retain recovered or post-run errors as warnings, and gate retries on both outcome and committed side effects.
- **Typed error distinction:** Keep run-level errors fatal by default but introduce explicit recovered and post-run error kinds that cron can safely exclude from failure classification.
- **Keep all run errors fatal:** Preserve current precedence and accept false failure state and retry risk whenever a late or recovered run-level error is recorded.

## Reproduction Assessment

Yes at source level: the classifier and finalization path explain how a recovered tool or run-level error can override successful terminal output, and several commenters supplied matching live traces. This review did not execute a controlled current-main cron run.

## Solution Assessment

No, the suggested rule that a normal stop and no final tool error always means success is too broad. The narrow maintainable solution should use the shared terminal-outcome contract while preserving genuine fatal signals and preventing unsafe retries after external side effects.

## Summary

Keep open: current main and the latest checked release still have transcript, wake-word, and realtime transcription pipelines, but no enrolled-speaker verification gate. This remains a product and security design item, not a stale cleanup candidate or narrow automated fix.

## What This Changes

The issue requests enrolled-speaker recognition for OpenClaw voice modes so background or unauthorized voices do not trigger or contaminate voice sessions.

## Best Possible Solution

Define a maintainer-approved speaker-gating design that covers local enrollment, profile storage, native capture hooks, realtime/provider diarization contracts, fallback semantics, and user-visible consent before implementation.

Rationale: Automation cannot safely choose whether voice matching is a security boundary, which platforms/providers should participate, or how biometric-like state and provider egress should be governed.

Options:

- **Design the speaker-gating contract first (recommended):** Create a product/security design for native capture hooks, local state, provider diarization, plugin API shape, fallback behavior, and user consent before any implementation PR.
- **Limit to a local macOS prototype:** Allow a default-off macOS-only local prototype while explicitly deferring mobile, browser, provider diarization, and command-authorization semantics.
- **Defer to plugin/API work:** Keep core unchanged until a plugin or ClawHub package can implement speaker verification through a documented generic audio/speaker API.

## Summary

Keep open: current main and the latest release cover the per-agent TTS voice half with `agents.list[].tts`, but Android Talk/Voice still has no agent/session selector and still routes Talk turns through the runtime `mainSessionKey`; the open Android chat-selector PR only partially overlaps and is currently conflicting.

## What This Changes

Requests companion-app Talk/Voice agent or session switching plus per-agent TTS voice identity for multi-agent setups.

## Best Possible Solution

Keep `agents.list[].tts` as the voice-identity contract and add a maintainer-approved Talk/Voice target model that reuses canonical session keys and presents a clear Android Voice selector or shared active-session behavior.

Rationale: The remaining work changes user-visible voice routing and session identity semantics across companion apps, and the safest implementation depends on the intended UX contract rather than a purely mechanical code fix.

Options:

- **Follow Chat Target (recommended):** Make Talk/Voice use the active Chat session or selected agent, matching the iOS/macOS direction and avoiding a second source of truth.
- **Separate Talk Picker:** Add an independent Talk/Voice selector so users can keep voice and text conversations on different agents, with explicit UI state and persistence.
- **Close As TTS-Only:** Declare only the per-agent TTS half in scope and reject companion-app Talk target selection for now, leaving Android voice pinned to the default session.

## Reproduction Assessment

Yes for source-level confirmation: Android `VoiceTabScreen` has no agent/session selection state, while `TalkModeManager` still sends Talk and `chat.send` traffic with `mainSessionKey`. This is a missing feature/UX path, not a broken existing contract bug.

## Solution Assessment

Unclear until maintainers choose the Talk target UX. The implemented per-agent TTS path is the right config shape, but the remaining Android routing should not be fixed by adding another ad hoc `talk.voiceId` or hidden session override.

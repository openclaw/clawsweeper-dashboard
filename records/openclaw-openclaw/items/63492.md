## Summary

Keep open: current main still exposes session storage as local path-backed session metadata plus transcript files, and the related database, SQLite, and horizontal-scaling items overlap without replacing this session-specific external storage decision.

## What This Changes

Request to add a configurable external shared session storage backend so multiple OpenClaw instances can read and write the same session state without sticky routing.

## Best Possible Solution

Keep this as the canonical session-specific external storage tracker, then design the backend boundary after maintainers settle how it coordinates with the session accessor, SQLite migration, and broader database abstraction work.

Options:

- **Coordinate Through Database Seam (recommended):** Use the broader backend-neutral database design to define the durable storage contract first, then implement session storage on that approved seam.
- **Sponsor A Session-Only Backend:** Approve a narrower session/transcript backend interface now, with explicit migration, secret handling, consistency, and compatibility tests.
- **Defer External Storage:** Keep local SQLite/session files as the supported runtime path for now and document sticky routing or single-Gateway deployment expectations.

## Reproduction Assessment

Yes for source confirmation: current main only accepts a string session.store and resolves it to local sessions.json plus local transcript files. This is not a bug reproduction; it is a missing feature visible in code and docs.

## Solution Assessment

No to the literal Redis/Mongo factory as proposed; the maintainable solution needs a maintainer-approved storage boundary covering session metadata, transcripts, migrations, pruning, credentials, consistency, and upgrade behavior.

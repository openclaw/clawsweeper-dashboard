## Label Justifications

- `P2`: The request targets real production scalability and reliability impact, but it is a broad feature/design item rather than an urgent confirmed regression.
- `impact:session-state`: The reported failure mode is lost or mismatched conversation context when different OpenClaw instances cannot share the same session state.
- `impact:data-loss`: The issue describes local session state disappearing from the user perspective when routing reaches an instance without the original local store or the owning instance is lost.

## Summary

Keep open: current main and v2026.6.11 still expose session storage as a local path-backed `sessions.json` store, while related SQLite and database-abstraction work is adjacent rather than an external shared session backend.

## What This Changes

Request a pluggable external session storage backend, such as Redis or MongoDB, so multiple OpenClaw instances can share stateless session state.

## Best Possible Solution

Keep this as the canonical session-specific external storage tracker, then design a maintainer-approved backend or plugin API boundary that covers session metadata, transcripts, migrations, credentials, lifecycle cleanup, and consistency semantics.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw support external shared session storage as a core backend, a plugin/API seam, or defer it until the broader database-abstraction direction is settled?

Rationale: The source gap is clear, but automation cannot choose dependency ownership, credential handling, config shape, migration semantics, transcript consistency, or core-versus-plugin support policy.

Likely owner: steipete

Owner reason: The decision is product/architecture-wide and steipete has the strongest prior routing signal for adjacent scaling/session architecture issues.

Owner confidence: medium

Options:

- **Design backend-neutral session storage (recommended):** Define a storage contract for session metadata and transcripts first, then allow Redis/Postgres/Mongo-style implementations only after migration and consistency requirements are explicit.
- **Fold into database abstraction:** Keep this issue open but block implementation on the broader backend-neutral database architecture in https://github.com/openclaw/openclaw/issues/94675 and https://github.com/openclaw/openclaw/issues/90370.
- **Document external deployment only:** Keep core local-store-first and document sticky sessions or external orchestration as the supported multi-instance deployment workaround for now.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: current main only accepts a string `session.store`, resolves it to local `sessions.json`, and reads it through filesystem JSON I/O. This is a missing feature rather than a failing bug repro.

## Solution Assessment

No, not as the literal Redis/Mongo key-value factory described. The best fix needs a maintained storage boundary that includes transcripts, lifecycle mutations, migrations, credentials, consistency, and upgrade behavior.

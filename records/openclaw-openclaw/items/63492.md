## Label Justifications

- `P2`: The request targets meaningful production scalability and reliability impact, but it is a broad feature/design item rather than an urgent confirmed regression.
- `impact:session-state`: The central failure mode is losing or mis-associating conversation/session context when traffic reaches an instance without the local session store.
- `impact:data-loss`: The issue describes session data disappearing from the user's perspective when local stores are not shared or an instance-local store is lost.

## Summary

Keep open: current main and v2026.6.11 still expose session storage as local path-backed `sessions.json` plus JSONL transcripts, while the open SQLite flip and broader database-abstraction work are adjacent prerequisites rather than an external shared session backend.

## What This Changes

Request support for a configurable external shared session-storage backend, such as Redis or MongoDB, so multiple OpenClaw instances can share session state without sticky routing.

## Best Possible Solution

Keep this as the canonical session-specific external storage tracker, then define a secure storage-neutral session/transcript backend contract after the SQLite migration and broader database-abstraction direction settle.

Owner confidence: medium

Options:

- **Design Session Storage Contract (recommended):** Define a storage-neutral session/transcript contract covering metadata, transcripts, migrations, credentials, consistency, cleanup, and proof before choosing Redis, MongoDB, Postgres, or another backend.
- **Defer To Database Abstraction:** Keep this issue as session-specific requirements input while https://github.com/openclaw/openclaw/issues/94675 decides the broader networked database architecture.
- **Document External-Only Stance:** Keep core on local SQLite/files and document sticky sessions or external orchestration as deployment guidance unless a plugin API gap is proven.

## Reproduction Assessment

Yes, source-level confirmation is high-confidence: current main only accepts a string `session.store` and resolves it to local `sessions.json` plus local JSONL transcripts. This is a missing feature rather than a failing current-main bug reproduction.

## Solution Assessment

No, not as the literal Redis/Mongo key-value factory proposed. The maintainable solution needs a maintainer-approved storage boundary that covers session metadata, transcripts, migrations, pruning, credentials, consistency, cleanup, and upgrade behavior.

## Label Justifications

- `P2`: The request targets meaningful production scalability and reliability, but it is a broad feature/design item rather than an urgent confirmed regression.
- `impact:session-state`: The reported failure mode is losing or mis-associating conversation context when requests for the same user reach different OpenClaw instances.
- `impact:data-loss`: The issue describes session history disappearing from the user's perspective when state exists only on another local instance or is lost with an instance-local store.

## Summary

Keep open: current main and v2026.6.11 still accept only a path-backed `session.store` and local `sessions.json` reads, so external shared session storage remains a real product/storage architecture decision rather than implemented or superseded work.

## What This Changes

The issue requests pluggable external session storage, such as Redis or MongoDB, so multiple OpenClaw instances can share session state without sticky routing.

## Best Possible Solution

Keep this as the canonical session-specific external-storage tracker, then design a backend-neutral session state boundary with explicit credentials, consistency, migration, pruning, archive, and transcript semantics before choosing Redis, MongoDB, Postgres, or a plugin seam.

Options:

- **Design backend-neutral session storage (recommended):** Define a core or plugin-facing contract for session metadata, transcripts, lifecycle cleanup, migration, credentials, and consistency before selecting Redis, MongoDB, Postgres, or another implementation.
- **Defer until database abstraction settles:** Keep this issue open but wait for the SQLite/session-accessor and broader networked database direction to settle before designing the session-specific backend.
- **Document external deployment only:** Keep OpenClaw local-state-first for now and document sticky sessions, external orchestration, or third-party plugins as the supported multi-instance pattern.

## Reproduction Assessment

Yes, source-level: current main only accepts a string `session.store`, resolves it to local `sessions.json`, and reads it with filesystem JSON I/O. This is not a bug repro, but the missing external shared backend is directly visible in source and docs.

## Solution Assessment

No, not as the literal Redis/Mongo key-value factory described. The maintainable solution needs a maintainer-approved storage boundary that covers session metadata, transcripts, lifecycle operations, migration, credentials, and distributed consistency.

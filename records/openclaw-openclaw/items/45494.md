## Summary

Issue #45494 should stay open because current main and the shipped structured `server_error` fix cover OpenAI/Codex-style JSON payloads, but they do not prove the reported plain `api_error: Internal server error` provider-outage path fast-fails before the cron watchdog consumes the run timeout.

## What This Changes

The issue requests cron/provider failure handling that classifies sustained LLM internal-server errors early enough for cron retry/fallback/alerts instead of missing scheduled runs after a full timeout.

## Best Possible Solution

Keep #45494 as the canonical plain API internal-server cron outage item until maintainers choose the failure class/cooldown semantics and land focused coverage for the plain SDK text plus cron fast-fail/retry behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: How should plain provider text such as `LLM error api_error: Internal server error` be classified for cron/fallback, and should that class affect shared auth-profile cooldown?

Rationale: Current code has separate semantics for `timeout`, `overloaded`, and `server_error`, and choosing the wrong class can either poison shared provider health, skip useful fallback, or leave cron jobs waiting for the watchdog.

Likely owner: altaywtf

Owner reason: They merged the overlapping structured `server_error` cron retry fix and have adjacent failover classification history.

Owner confidence: high

Options:

- **Use cron-local server_error (recommended):** Classify the plain SDK shape as a retryable `server_error` for cron/fallback while keeping shared auth-profile cooldown behavior local unless maintainers explicitly widen it.
- **Treat as overloaded cooldown:** Classify plain API internal-server errors as `overloaded` so same-provider profiles cool down and cross-provider fallback is favored, accepting broader provider-health side effects.
- **Keep timeout semantics:** Leave generic internal-server text as `timeout` and document that cron retry/backoff or stream-stall work, not failover classification, owns this recovery path.

Yes at source level, but not with a live outage replay: current main still lacks a landed exact path for plain `api_error: Internal server error` text and cron retry decisions occur only after the run returns or times out.

## Solution Assessment

Unclear pending maintainer policy: a narrow classifier patch is plausible, but the best fix must explicitly choose classification/cooldown semantics and prove cron fallback/retry happens before the watchdog loses the scheduled run.

## Summary

Keep open: current main and the latest release still treat the plain Anthropic-style `api_error: Internal server error` path as timeout-style handling, while the merged structured `server_error` cron retry work only partially overlaps this report. The remaining fix needs maintainer policy on classification and auth-profile cooldown behavior before a safe repair PR.

## What This Changes

The issue requests that cron agent jobs fast-fail, retry/back off, and notify on sustained LLM provider outage errors instead of burning the full cron timeout window and silently missing scheduled work.

## Best Possible Solution

Keep this as the canonical plain provider API internal-server cron outage item, choose the failure classification policy explicitly, then land focused coverage for plain SDK `api_error`, fallback timing, cron retry/backoff, and failure-alert behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: How should plain provider `api_error: Internal server error` failures from cron model runs be classified: cron-local transient, `server_error`, `overloaded`, or left as `timeout`?

Rationale: Each option changes retry matching, fast-fail semantics, and whether shared auth-profile cooldown is affected; repository policy treats provider routing, auth-profile state, and fallback behavior as compatibility-sensitive.

Likely owner: altaywtf

Owner reason: altaywtf has the strongest visible history on nearby api_error/server_error failover classification and cron retry policy work.

Owner confidence: high

Options:

- **Use Cron-Local Transient (recommended):** Treat the plain provider 500 as retryable and fast-failable for cron/fallback without marking shared auth profiles unhealthy unless a separate policy opts in.
- **Map To Server Error:** Reuse the existing structured `server_error` path so cron state and retry policy report server errors consistently while avoiding shared auth-profile cooldown.
- **Map To Overloaded:** Use overload cooldown to skip same-provider profiles sooner, accepting the risk that broad HTTP 500 outages affect shared provider health state.

## Reproduction Assessment

Yes, at source level but not as a live outage replay. Current main still maps the plain internal-server/API-error text to timeout-style handling, and cron retry only runs after the isolated job returns.

## Solution Assessment

Unclear pending maintainer policy. A narrow classifier patch is plausible, but the best fix must choose the error class and shared cooldown semantics before implementation.

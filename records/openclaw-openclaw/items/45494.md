## Summary

Keep open: current main and the latest release have useful cron retry, failure-alert, and structured `server_error` support, but the reported plain `LLM error api_error: Internal server error` outage path is still classified through timeout/server-error regexes after a completed run and is not proven to fast-fail before the cron wall-clock deadline.

## What This Changes

The issue requests cron agent jobs to fast-fail, retry with backoff, and notify delivery targets during sustained LLM HTTP 500/provider outages instead of consuming the full `timeoutSeconds` window.

## Best Possible Solution

Define a maintainer-approved provider-outage policy that lets plain 500-style cron failures fail early and retry/alert without unsafe shared provider-health poisoning, with focused tests for the cron fallback chain and failure-alert behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For plain provider messages like `LLM error api_error: Internal server error`, should OpenClaw treat them as cron-local retryable provider outages, shared auth-profile cooldown signals, or timeout-only failures?

Rationale: The choice changes provider cooldown blast radius, cron retry timing, and whether operators get early outage notifications, so source inspection cannot safely pick the permanent behavior without maintainer intent.

Likely owner: steipete

Owner reason: steipete has the strongest current-main provenance on the classifier/cron policy lines and prior review context for this decision boundary.

Owner confidence: high

Options:

- **Cron-local provider outage (recommended):** Classify plain 500-style cron run errors as retryable provider outages for cron/fallback timing and alerts without marking shared auth-profile cooldown unless the provider signal is structured enough.
- **Shared cooldown signal:** Treat plain API internal-server failures as provider cooldown evidence so same-provider candidates and later jobs skip faster, accepting broader suppression risk during ambiguous upstream incidents.
- **Timeout-only with proof:** Keep plain 500 text timeout-like only if a focused current-main test proves cron no longer burns the outer wall-clock deadline before retry or alert behavior starts.

## Reproduction Assessment

Yes at source level for the remaining policy gap: current main still treats plain internal-server text differently from structured `server_error` and only applies cron retry after the run result. I did not run a live provider-outage reproduction for the exact 180-second timing.

## Solution Assessment

Unclear until maintainers choose the provider-outage policy. The merged structured `server_error` work is useful, but the best fix for this issue should prove early cron/fallback behavior for plain provider 500s without over-broad shared cooldown poisoning.

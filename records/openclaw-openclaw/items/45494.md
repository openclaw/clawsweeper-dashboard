## Summary

Keep open: current main has structured `server_error` cron retry support, but the reported plain `api_error: Internal server error` provider-outage path still falls into timeout-style handling and does not prove fast-fail before the cron run window is consumed.

## What This Changes

Issue #45494 requests reason-aware cron/fallback handling so definitive LLM API outages fast-fail, retry with backoff, and surface user-visible failure instead of burning scheduled cron windows.

## Best Possible Solution

Keep this as the canonical plain API internal-server cron outage item, choose the failure classification/cooldown policy explicitly, then land focused coverage for plain SDK `api_error`, fallback timing, cron retry/backoff, and failure-alert behavior.

Options:

- **Use cron-local server outage semantics (recommended):** Treat the plain provider 500 shape as retryable provider outage for cron/fallback without marking shared auth profiles unhealthy, and require tests proving fast-fail plus retry/failure-alert behavior.
- **Map it to overloaded:** Skip same-provider profiles sooner through overload behavior, accepting the risk that broad HTTP 500 text can cool down healthy profiles if the match is too wide.
- **Defer to broader guardrails:** Keep timeout-style classification for now and solve it only as part of a wider reason-aware cron guard and stream-stall budgeting design.

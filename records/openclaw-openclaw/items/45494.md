## Summary

Keep open: current main partially addresses structured `server_error` cron retry, but the reported plain `LLM error api_error: Internal server error` path is still classified as timeout-like behavior and is not proven to fast-fail before the cron wall-clock deadline.

## What This Changes

The issue asks for cron agent runs to fail early, retry/back off, and notify when sustained LLM provider 500 errors make the fallback chain unusable.

## Best Possible Solution

Define and test a maintainer-approved policy where plain provider 500s fail early for cron without unsafe shared provider-health poisoning, with focused classifier, cron/fallback timing, retry, and failure-alert coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For plain provider messages like `LLM error api_error: Internal server error`, should OpenClaw treat them as cron-local `server_error`, shared provider cooldown, or generic timeout-only failures?

Rationale: The choice changes provider failover, cron retry semantics, failure notification behavior, and shared auth-profile cooldown safety, so automation should not pick the permanent policy without maintainer intent.

Likely owner: steipete

Owner reason: steipete has recent adjacent cron/failover commits and prior review context on the broader cron guardrail policy boundary.

Owner confidence: medium

Options:

- **Cron-local server_error (recommended):** Classify the cron-visible run error as retryable `server_error` and prove fast-fail/retry/alert behavior without marking shared auth-profile health for ambiguous plain text.
- **Shared provider cooldown:** Treat plain API internal-server failures as provider outage signals that can skip same-provider candidates across runs, accepting broader cooldown effects.
- **Keep timeout-only with proof:** Leave plain provider 500 text as timeout-like only if a focused cron/fallback test proves it fails before the outer deadline and still notifies operators.

## Reproduction Assessment

Yes at source level for the remaining classification/policy gap: current main still distinguishes structured `server_error` from plain internal-server text. No live provider outage run was executed, so the exact 180-second timing is not high-confidence reproduced here.

## Solution Assessment

Unclear until maintainers choose the policy. The merged structured `server_error` fix is useful but is not the best complete solution for the reported plain `api_error: Internal server error` cron fast-fail behavior.

The issue asks OpenClaw cron isolated agent jobs to fast-fail, retry, and surface delivery when sustained provider HTTP 500/API errors make model fallback consume the cron timeout.

Kind: product_direction

Question: How should plain provider `api_error: Internal server error` failures from cron model runs be classified: cron-local transient, `server_error`, `overloaded`, or left as `timeout`?

Rationale: Each option changes retry matching, fast-fail semantics, and whether shared auth-profile cooldown is affected; current code intentionally treats `server_error` as not poisoning auth-profile health while timeout can become profile cooldown after provider start.

Likely owner: altaywtf

Owner reason: altaywtf has the strongest available history on nearby internal-500 failover classification and was brought into the issue after the classification-policy split was raised.

Owner confidence: high

Options:

- **Use cron-local transient (recommended):** Treat the plain provider 500 as retryable and fast-failable for cron/fallback without marking shared auth profiles unhealthy unless a separate policy opts in.
- **Map to server_error:** Reuse the existing structured `server_error` path so cron state and retry policy report server errors consistently while avoiding shared auth-profile cooldown.
- **Map to overloaded:** Use overload cooldown to skip same-provider profiles sooner, accepting the risk that broad HTTP 500 outages affect shared provider health state.

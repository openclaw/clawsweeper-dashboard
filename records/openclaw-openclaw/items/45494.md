## Summary

Keep open: current main has structured `server_error` cron retry support, but the reported plain `LLM error api_error: Internal server error` provider shape is still not covered by a settled fast-fail/cooldown policy, and related issues only cover broader or adjacent cron failure modes.

## What This Changes

The issue reports cron agent jobs spending the full timeout window during sustained provider API 500 outages instead of quickly classifying the outage, retrying with backoff, and surfacing an operator notification.

## Best Possible Solution

Settle the provider-outage classification policy first, then land a focused repair with regression coverage for the plain Anthropic `api_error: Internal server error` shape, fallback-chain timing, cron retry scheduling, and failure-alert behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: How should OpenClaw classify and mitigate plain provider `api_error: Internal server error` failures in cron-backed agent runs?

Rationale: The same provider 500 text can be treated as a local transient `server_error`, a shared provider `overloaded` cooldown signal, or a cron-local outage/skip state; each choice changes fallback, auth-profile health, and operator notification semantics.

Likely owner: steipete

Owner reason: Recent blame points to steipete on the central classifier and cron retry surfaces where the policy needs to be encoded.

Owner confidence: medium

Options:

- **Use server_error, no shared cooldown (recommended):** Classify the plain API internal-server shape as `server_error`, keep shared auth-profile health unpoisoned, and prove cron retry/failure-alert behavior without changing cooldown semantics.
- **Use overloaded cooldown:** Treat this as provider overload so same-provider profiles cool down, accepting broader shared provider impact during 500 outages.
- **Add cron outage state:** Keep provider classification conservative and add a cron-local outage or skip state with explicit retry and notification semantics.

## Reproduction Assessment

Yes from source inspection, but not as a live provider outage: current main covers structured `server_error` and JSON `api_error` payloads, while the reported plain SDK string still needs policy-specific handling. A production-like repro should assert it fails or retries before the cron wall-clock timeout.

## Solution Assessment

Unclear until maintainers choose the policy: a narrow classifier-only patch is plausible, but the best fix must also prove fallback-chain timing, cron retry, and notification behavior without unexpectedly poisoning shared auth-profile health.

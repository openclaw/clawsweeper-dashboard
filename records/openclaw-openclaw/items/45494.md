## Best Possible Solution

Keep the issue open for a maintainer-owned policy and proof pass: plain provider 500s should fail early for cron without unsafe shared provider-health poisoning, with regression coverage for the real cron fallback chain.

## Maintainer Decision

Required: true

Kind: product_direction

Question: For plain provider messages like `LLM error api_error: Internal server error`, should OpenClaw treat them as shared provider cooldown signals, cron-local transient retry signals, or only generic timeouts?

Rationale: Classifying plain 500s as shared cooldown can fast-skip same-provider fallbacks but may poison provider health for ambiguous errors; keeping them as timeout may preserve safety but still needs proof that cron no longer burns the outer timeout.

Likely owner: clovericbot

Owner reason: Their merged structured `server_error` work is the closest recent provenance for this policy boundary.

Owner confidence: medium

Options:

- **Cron-local transient server error (recommended):** Classify the cron-visible run error as retryable `server_error` without marking shared auth-profile cooldown unless the provider error is structured enough.
- **Shared provider cooldown:** Treat plain API internal-server failures as provider outage signals and skip same-provider candidates across runs, accepting broader cooldown effects.
- **Keep timeout-only with proof:** Leave plain provider 500 text as timeout only if a focused cron/fallback test proves the run fast-fails before the outer deadline.

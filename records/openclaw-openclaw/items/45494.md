## Summary

Keep open: current main has useful cron retry and structured `server_error` handling, but it still does not prove the reported plain Anthropic-style `api_error: Internal server error` outage path fast-fails before the cron timeout window is consumed.

## What This Changes

The issue requests fast-fail, retry/backoff, and delivery notification behavior when cron agent LLM provider outages cause fallback runs to consume the full cron timeout window.

## Best Possible Solution

Choose the intended provider-outage class for plain `api_error: Internal server error`, then add focused classifier and cron/fallback coverage proving the run fails or retries before consuming the full cron timeout and emits the configured failure notification path.

## Reproduction Assessment

Yes, at source level: current main still routes the reported plain `api_error: Internal server error` shape through timeout-style handling rather than a stronger provider-outage class. I did not run a live Anthropic outage reproduction in this read-only review.

## Solution Assessment

No, the already-merged structured `server_error` retry work is a useful partial fix but not the best complete solution for this issue. The best path is a maintainer-chosen classification/cooldown policy with regression proof for the plain Anthropic-style error, cron retry timing, and failure notification behavior.

## Label Justifications

- `P1`: Sustained provider outages can block cron agent jobs for their full timeout window and miss scheduled background work for real users.
- `impact:data-loss`: The report describes missed backup/data-collection windows when cron jobs silently consume most of the schedule during provider outages.
- `impact:auth-provider`: The remaining fix depends on provider error classification, fallback routing, and whether provider/auth-profile cooldown state should be affected.

## Summary

Keep open: current main and the latest release include partial cron retry, failure-alert, structured `server_error`, and stream-stall mitigations, but the exact plain `LLM error api_error: Internal server error` cron fallback/cooldown path is still policy-sensitive and not proven to fast-fail before the cron wall-clock timeout.

## What This Changes

Requests cron agent jobs to treat sustained LLM provider 500/API-error outages as recoverable provider-outage failures that fail fast across fallbacks, reschedule with backoff, and notify configured delivery targets.

## Best Possible Solution

Keep this open until maintainers choose cron-local provider-outage semantics and land proof that plain Anthropic-style `api_error: Internal server error` fails or rotates quickly, schedules retry/backoff, and emits configured failure notification without unintended shared auth-profile cooldown.

## Summary

Keep open: current main has useful structured `server_error` cron retry support, but the reported plain `LLM error api_error: Internal server error` cron/fallback path still maps through timeout-like handling and is not proven to fast-fail or notify before the cron wall-clock deadline.

## What This Changes

Cron agent jobs should fast-fail, retry, and notify when sustained LLM provider 500/internal-server errors make the fallback chain unrecoverable.

## Best Possible Solution

Define a maintainer-approved cron/provider outage policy that classifies plain `api_error: Internal server error`, aborts or advances fallback without consuming the full cron timeout, keeps shared auth-profile cooldown semantics explicit, and covers retry plus failure-delivery behavior with tests/docs.

Rationale: The choice affects fallback timing, shared auth-profile health, scheduler retry semantics, and user-visible failure notifications, so automation cannot safely pick the default policy from source inspection alone.

Owner confidence: high

Options:

- **Cron-local provider outage (recommended):** Classify the cron-visible failure as retryable `server_error`, prove early fallback abort/advance, and avoid shared auth-profile cooldown unless the provider signal is structured enough.
- **Shared provider cooldown:** Treat plain internal-server API failures as provider outage signals that can skip same-provider candidates across jobs, accepting broader cooldown effects for faster recovery.
- **Timeout-only with proof:** Keep plain provider 500 text as timeout-like only if focused cron/fallback tests prove the run no longer burns the outer deadline and failure alerts are adequate.

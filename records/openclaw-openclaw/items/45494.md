## Summary

Keep open: current main and the latest release still route plain `api_error: Internal server error` text through timeout-style classification, so the reported cron fast-fail/reporting problem is not proved fixed. The remaining blocker is a maintainer policy choice for the error class and auth-profile cooldown behavior.

## What This Changes

Cron agent jobs should fast-fail, retry with backoff, and notify on repeated provider API 500 outages instead of burning the full job timeout window.

## Best Possible Solution

Recognize plain `api_error: Internal server error` as a provider-outage signal, preferably as `server_error` without shared auth-profile cooldown, and add focused cron/fallback/failure-alert coverage while keeping stream-stall work separate.

Required: true

Kind: product_direction

Question: How should plain provider text like `LLM error api_error: Internal server error` be classified for cron and model-fallback behavior?

Rationale: The code path is clear, but the right permanent class affects retry matching, cross-provider fallback, and whether shared auth profiles are cooled down during provider 500 outages.

Likely owner: altaywtf

Owner reason: altaywtf carried the closest merged structured `server_error` retry work and follow-up classification fixes, so they have the best recent context for the remaining policy choice.

Owner confidence: high

Options:

- **Classify as server_error without cooldown (recommended):** Map the plain api-error internal-server shape into the existing `server_error` reason so cron retry/state and model fallback can act on it without poisoning shared auth-profile health.
- **Classify as overloaded with cooldown:** Treat the plain provider 500 as provider overload so same-provider profiles are skipped faster, accepting broader shared cooldown impact during provider outages.
- **Keep timeout and add cron-local handling:** Leave global failover classification unchanged and add a cron-local provider-outage retry/alert rule, which reduces auth-profile risk but adds another decision path.

## Reproduction Assessment

Yes at source level for the classifier gap, but not as a live outage replay. Current main still classifies plain internal-server text as timeout-style, and cron retry/alert handling only starts after the isolated run returns an error.

## Solution Assessment

Unclear until maintainers choose the failure class. A narrow `server_error` classification with no auth-profile cooldown looks like the safest current shape, but `overloaded` or cron-local handling would change product behavior differently.

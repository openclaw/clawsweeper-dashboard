## Summary

Keep open: current main still does not prove that the reported plain `api_error: Internal server error` cron outage path fast-fails before consuming the cron run window. The structured `server_error` work is a useful partial fix, but the remaining classifier and cooldown policy needs maintainer direction.

## What This Changes

The issue asks OpenClaw cron agent jobs to fast-fail, back off, and notify on sustained LLM provider 500-style outages instead of spending the full cron timeout window.

## Best Possible Solution

Keep this as the canonical plain API internal-server cron outage item, choose the failure-classification policy explicitly, then land focused coverage for plain SDK `api_error`, fallback timing, cron retry/backoff, and failure-alert behavior.

Rationale: The code shows this is not only a regex gap because each classification changes cron retry matching, fallback behavior, and whether shared auth-profile health is affected.

Likely owner: altaywtf

Owner confidence: high

Options:

- **Use a cron-local outage classification (recommended):** Treat the plain provider 500 as retryable for cron/fallback without marking shared auth profiles unhealthy unless maintainers explicitly opt in.
- **Map it to server_error:** Use the existing structured `server_error` path so cron retry policy and state report server errors consistently while avoiding auth-profile cooldown.
- **Map it to overloaded:** Skip same-provider profiles sooner through overload cooldown behavior, accepting the risk of poisoning shared provider health during broad HTTP 500 outages.

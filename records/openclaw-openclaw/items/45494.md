## Label Justifications

- `P1`: The issue reports cron agent workflows missing scheduled runs during provider outages, which is an urgent broken automation path for real users.
- `impact:data-loss`: A failed daily cron can skip the intended run output entirely until the next schedule or manual intervention, effectively losing scheduled automation results.

## Summary

Keep open: current main has structured `server_error` retry handling and cron retry/alert plumbing, but the reported plain provider outage shape (`api_error: Internal server error`) still falls through timeout-style classification and there is no source or release proof that cron now fast-fails and retries this outage before exhausting its run window.

## What This Changes

The issue asks OpenClaw cron agent jobs to fast-fail, retry/back off, and notify on sustained LLM API outage errors such as `api_error: Internal server error` instead of silently consuming the whole cron timeout.

## Best Possible Solution

Keep #45494 as the canonical plain HTTP 500/API-internal-server cron outage item; choose the failure classification policy explicitly, then land focused coverage for plain SDK `api_error`, fallback fast-fail timing, cron retry/backoff, and alert delivery.

## Reproduction Assessment

Yes at source level: current classifier and cron paths show the plain `api_error: Internal server error` shape still lacks the structured fast-fail treatment, but this review did not force a live upstream outage.

## Solution Assessment

Unclear pending maintainer policy: a narrow classifier change is plausible, but the best fix must decide whether this error should become `server_error`, `overloaded`, or a cron-local transient because those choices affect fallback and cooldown behavior.

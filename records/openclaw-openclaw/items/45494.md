## Summary

Keep open: current main and v2026.6.11 still classify transient `api_error` / internal-server-error provider payloads as `timeout`, and the model fallback loop still walks candidates rather than proving a uniform provider-outage fast-fail before a cron timeout window is consumed.

## What This Changes

The issue reports cron agent jobs burning their full timeout during sustained LLM provider 500/API-error outages instead of classifying the provider outage, retrying with backoff, and notifying delivery.

## Best Possible Solution

Keep this as the canonical maintainer-owned bug for plain provider 500/API-error fast-fail, with focused tests for classification, fallback timing, cron retry/backoff, and failure-alert behavior while leaving stream-stall work to its separate issue.

## Reproduction Assessment

Yes, source-reproducible: current tests and source show transient `api_error` internal-server-error payloads still classify as `timeout`, and the fallback loop has no uniform provider-outage early-abort. I did not live-replay a sustained provider outage.

## Solution Assessment

Unclear as a single patch: the issue mixes classifier policy, cooldown behavior, retry/backoff, delivery alerts, and gap detection. The maintainable path is to split the plain provider-error classifier/cron proof from adjacent stream-stall and broader retry feature work.

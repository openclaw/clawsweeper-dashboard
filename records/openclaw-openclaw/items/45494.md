## Summary

Keep open: current main still does not prove the reported plain provider `api_error: Internal server error` cron outage path fast-fails before the cron timeout window is consumed. The merged structured `server_error` cron retry work is useful partial coverage, but the plain API-error classification and shared auth-profile cooldown policy still need maintainer direction.

## What This Changes

The issue asks OpenClaw cron agent jobs to fail or retry quickly, and notify when configured, during sustained LLM provider internal-server-error outages instead of consuming the whole cron timeout window.

## Best Possible Solution

Keep this as the canonical plain API internal-server cron outage item, choose the failure classification policy explicitly, then land focused coverage for plain SDK `api_error`, fallback timing, cron retry/backoff, and failure-alert behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: How should plain provider `api_error: Internal server error` be classified for cron/fallback behavior: `server_error`, `overloaded`, `timeout`, or a cron-local transient that avoids shared auth-profile cooldown?

Rationale: Each classification changes retry matching, fallback escalation, and whether shared auth-profile cooldown state is affected, so a narrow regex patch would encode product policy without maintainer intent.

Likely owner: altaywtf

Owner reason: They authored the closest merged structured server-error retry/classification follow-up and the overloaded failover behavior this decision would affect.

Owner confidence: high

Options:

- **Use cron-local outage classification (recommended):** Treat the plain provider 500 as retryable for cron/fallback without marking shared auth profiles unhealthy unless maintainers explicitly opt in.
- **Map it to `server_error`:** Reuse the structured server-error path so cron state and retry policy report provider 500s consistently while avoiding overload cooldown semantics.
- **Map it to `overloaded`:** Skip same-provider profiles sooner through existing overload cooldown behavior, accepting profile-health side effects during broad HTTP 500 outages.

## Reproduction Assessment

Yes at source level, but not as a live outage replay. Current main still classifies plain internal-server/api_error failures as timeout-style handling, and cron only retries or alerts after the isolated run result returns.

## Solution Assessment

Unclear pending maintainer policy. A narrow classifier patch is plausible, but the best fix must choose the error class and cooldown behavior before implementation.

## Summary

This PR remains necessary and looks technically sound, but it should stay open for explicit maintainer/security acceptance because it intentionally expands the trusted host-read HTML lifecycle from temp-root files to content-bound outbound-staged copies.

## What This Changes

The PR adds SQLite-backed sha256/size provenance for trusted generated HTML after outbound media staging, verifies the staged bytes on later host-read reloads, prunes stale provenance during media cleanup, and adds media regression tests.

## Best Possible Solution

Merge the content-bound SQLite provenance design after explicit security/media maintainer acceptance of the host-read lifecycle, then close the linked issue when the fix lands.

Question: Should OpenClaw accept sha256+size SQLite provenance as the trusted-host-read lifecycle for generated HTML that is staged into media/outbound and later reloaded?

Rationale: The patch fixes a real message-loss regression, but it deliberately extends a local HTML trust boundary and adds persisted trust metadata, which automation should not accept on behalf of maintainers.

Likely owner: steipete

Owner reason: They introduced the original trusted generated HTML host-read seam, so they have the strongest history signal for accepting or redirecting this boundary.

Owner confidence: high

Options:

- **Accept provenance-gated trust (recommended):** Treat the SQLite provenance row plus same-buffer sha256/size verification as sufficient to carry generated-HTML trust through outbound staging, then merge after normal exact-head gates.
- **Tighten lifecycle first:** Require extra storage lifecycle constraints such as TTL-based row pruning or chunked stale-row deletion before accepting the new persisted trust surface.
- **Reject staged HTML trust:** Keep outbound-staged HTML blocked and rely on PDF or another non-HTML workaround until a different security design is chosen.

## Reproduction Assessment

Yes. Current main stages local reply media into media/outbound and Telegram later reloads that staged .html through a host-read gate that only trusts temp-root realpaths; I did not run a live Telegram repro in this read-only review.

## Solution Assessment

Yes, with maintainer security acceptance. Path-only outbound trust is too broad, JSON sidecars conflict with repository state policy, and an in-memory allowlist would not survive delayed or restarted delivery, so content-bound SQLite provenance is the best fix shape I found.

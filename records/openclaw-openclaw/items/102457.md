- `impact:session-state`: The incorrect `reply_to_id` changes per-turn conversation metadata and reply-context coverage decisions that affect session/context interpretation.

## Summary

Keep open: current main and the latest release still compute Slack inbound `replyToId` as `incomingThreadTs ?? messageTs`, so non-reply Slack messages can still expose a self-referencing `reply_to_id`; the active closing path is the open fixing PR at https://github.com/openclaw/openclaw/pull/102462, not a merged fix yet.

## What This Changes

The issue requests omitting Slack inbound prompt metadata `reply_to_id` when a message is not a genuine Slack thread reply.

## Best Possible Solution

Land a Slack-owned fix that gates prompt-facing `replyToId` on genuine thread replies while preserving the separate message-tool thread anchor and regression coverage.

## Reproduction Assessment

Yes, at source level: call `resolveSlackThreadContext` for a Slack message with no `thread_ts`, or with `thread_ts == ts`, and current main returns `replyToId` equal to the current message timestamp. I did not run a live Slack workspace reproduction in this read-only review.

## Solution Assessment

Yes, the narrow best fix is in the Slack resolver plus the Slack tool-thread context: omit prompt-facing `replyToId` unless `isThreadReply` is true, while preserving a non-explicit current-message anchor for message-tool threading.

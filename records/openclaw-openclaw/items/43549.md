## What This Changes

## Best Possible Solution

Add session-store health diagnostics to channel status or doctor and provide backup-first reset guidance; defer automatic quarantine until maintainers choose the generic recovery policy.

## Maintainer Decision

Kind: product_direction

Question: Should bad Telegram/session-store JSON recovery be diagnostic-only, an explicit backup-first reset command, or automatic quarantine on load?

Rationale: All options address the outage, but they trade off operator control, data/session continuity, and overlap with the generic session-store recovery work.

Likely owner: steipete

Owner reason: Recent Telegram status and session-store history make this the strongest owner signal for the product-direction choice.

Owner confidence: high

Options:

- **Diagnostic plus explicit reset (recommended):** Status or doctor reports file health and points to a backup-first reset command, keeping destructive action operator-controlled.
- **Diagnostic only:** Status or doctor reports corrupt or oversized state and safe manual steps, leaving reset automation for later.
- **Automatic quarantine:** The gateway moves bad state aside and recreates state on load, maximizing recovery but taking the largest compatibility and continuity risk.

## Reproduction Assessment

Yes. Source inspection shows malformed or unreadable session-store JSON can collapse to an empty store, and the Telegram/channel status path does not inspect that file health; I did not run a live corrupt Telegram instance in this read-only review.

## Solution Assessment

Yes, the diagnostic and recovery direction is valid. The best first fix is non-destructive status/doctor detection plus backup-first reset guidance, with automatic quarantine left to maintainer policy.

## Summary

Keep open: current main still falls back to empty session state after bad `sessions.json` reads, while Telegram/channel status does not diagnose malformed, oversized, or unreadable persisted session state; the open generic session-store PR only partially overlaps this Telegram recovery UX gap.

## What This Changes

The issue requests Telegram status diagnostics and a safe recovery path for malformed, oversized, or otherwise poisoned persisted session JSON.

## Best Possible Solution

Add read-only status diagnosis for bad Telegram/session state, then repair through a maintainer-approved doctor/reset quarantine flow with backup rather than silent load-time deletion.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should bad Telegram/session-store state be repaired automatically, quarantined through doctor/reset, or only diagnosed in status?

Rationale: The source gap is clear, but recovery changes persistent session continuity and operator trust, so automation should not choose deletion, quarantine, or diagnostic-only semantics by itself.

Likely owner: steipete

Owner reason: The decision spans Telegram status diagnostics and session recovery behavior, and recent history shows repeated work on the Telegram status surface.

Owner confidence: high

Options:

- **Doctor/reset quarantine (recommended):** Status reports the bad artifact and `doctor --fix` or a first-class reset command backs it up, quarantines it, and recreates clean state.
- **Diagnostic-only status:** Status reports size, parse, and schema failures and points to documentation without changing files automatically.
- **Startup auto-quarantine:** Gateway startup moves bad state aside automatically and recreates it, accepting stronger self-heal behavior with higher data-continuity risk.

## Reproduction Assessment

Yes at source level: current `loadSessionStore` can fall back to empty state after invalid or empty reads, while Telegram/channel status does not inspect or report the bad session artifact; no live Telegram repro was run.

## Solution Assessment

The best direction is status-visible diagnosis plus doctor/reset-owned quarantine; unconditional startup deletion or self-heal is riskier because the data is persistent session state.

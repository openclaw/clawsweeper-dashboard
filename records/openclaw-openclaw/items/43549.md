## Best Possible Solution

Add non-destructive session-store health diagnostics to status or doctor, then provide an explicit backup-first reset/quarantine path once maintainers choose the recovery policy.

Question: Should bad Telegram/session-store JSON recovery be diagnostic-only, an explicit backup-first reset/doctor fix, or automatic quarantine on load?

Rationale: All options address the outage, but they trade off operator control, session continuity, and overlap with the generic session-store recovery work.

Likely owner: steipete

Owner confidence: medium

Options:

- **Diagnostic Plus Explicit Reset (recommended):** Status or doctor reports file health and points to a backup-first reset command, keeping destructive action operator-controlled.
- **Diagnostic Only:** Status or doctor reports corrupt or oversized state and safe manual steps, leaving reset automation for later.
- **Automatic Quarantine:** The gateway moves bad state aside and recreates state on load, maximizing recovery but taking the largest continuity risk.

## Reproduction Assessment

Yes. Source inspection shows malformed or unreadable session-store JSON can collapse to an empty store, while Telegram/channel status does not inspect that file health; no live corrupt Telegram instance was run in this read-only review.

## Solution Assessment

The best direction is status-visible diagnosis plus doctor/reset-owned quarantine; unconditional startup deletion or self-heal is riskier because the data is persistent user/session state.

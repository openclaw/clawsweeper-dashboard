## What This Changes

The issue requests explicit detection, status guidance, and a safe recovery path when bad persisted Telegram-related session JSON wedges Telegram routing.

## Best Possible Solution

Add read-only session-store health diagnostics to status/doctor first, then provide a guarded backup-and-reset repair path; automatic quarantine should only ship after explicit maintainer approval.

Question: Should malformed or oversized Telegram-related session-store JSON recovery be diagnostic-only, an explicit backed-up doctor/reset repair, or automatic load-time quarantine?

Rationale: The source gap is clear, but the permanent behavior affects persisted session continuity and operator trust, so automation should not choose the destructive recovery policy on its own.

Likely owner: steipete

Owner confidence: medium

Options:

- **Diagnostic plus explicit repair (recommended):** Status and doctor would report path, size, parse/schema status, and offer an operator-run backed-up reset or doctor repair command.
- **Diagnostic only:** Status and doctor would identify the bad artifact and recovery steps while leaving mutation to manual operator action.
- **Automatic quarantine:** Gateway load would move invalid state aside and recreate clean state automatically, accepting possible surprise loss of session continuity.

## Reproduction Assessment

Yes for the source failure mode: current main collapses malformed or empty session-store reads into an empty store, and Telegram status does not inspect file health. I did not establish the original live corruption trigger in this read-only review.

## Solution Assessment

Partly: status/doctor detection with a backed-up explicit repair path is the safest maintainable direction. Automatic quarantine or load-time reset is a product decision because it changes persisted session continuity behavior.

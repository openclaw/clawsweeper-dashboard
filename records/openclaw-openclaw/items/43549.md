## Summary

Keep open: current main still treats bad session-store JSON as empty state after retries, and Telegram/channel status does not surface a session-state diagnosis or safe recovery path; the open generic session-store PR only partially overlaps and does not close the Telegram status/recovery UX gap.

## What This Changes

The issue asks for Telegram/status diagnostics and a safe recovery flow when persisted Telegram or session JSON becomes oversized, malformed, or poisoned.

## Best Possible Solution

Add read-only status diagnosis first, then make repair a maintainer-approved doctor/reset quarantine flow with backup rather than silent load-time deletion or rewrite.

Rationale: The source gap is clear, but the recovery behavior affects persistent session continuity and operator trust, so automation should not choose deletion, quarantine, or diagnostic-only semantics by itself.

Likely owner: steipete

Owner confidence: medium

Options:

- **Doctor/reset quarantine (recommended):** Status reports the bad artifact and `doctor --fix` or a first-class reset command backs it up, quarantines it, and recreates clean state.
- **Diagnostic-only status:** Status reports size/parse/schema failures and points to documentation without changing files automatically.
- **Startup auto-quarantine:** Gateway startup moves bad state aside automatically and recreates it, accepting stronger self-heal behavior with higher data-continuity risk.

## Reproduction Assessment

Yes at source level: current `loadSessionStore` can fall back to empty state after invalid or empty reads, while channel/Telegram status does not inspect or report the bad session artifact; no live Telegram repro was run in this read-only review.

## Solution Assessment

The best direction is status-visible diagnosis plus doctor/reset-owned quarantine; unconditional startup deletion or self-heal is riskier because the data is persistent user/session state.

## Summary

Keep open. Current main and v2026.6.11 still lack Linux headless node-host delivery for `system.notify`; the remaining blocker is maintainer choice on Linux notification backend, dependency scope, and safe invocation policy.

## What This Changes

Add Linux desktop notification delivery for the existing `system.notify` / `openclaw nodes notify` path, likely through a Linux notification backend such as `notify-send`.

## Best Possible Solution

Choose the Linux notification backend contract, then add a safe core node-host `system.notify` handler with structured unavailable results, docs/CLI updates, focused regression coverage, and real Linux desktop-session proof while preserving existing macOS, iOS, and Android behavior.

Options:

- **Core notify-send first (recommended):** Implement a narrow core node-host handler that uses `notify-send` when a desktop session is present, returns structured unavailable results otherwise, and documents any optional OS package dependency.
- **Broader backend matrix:** Design a larger backend layer with D-Bus and/or `dunstify`, accepting extra implementation and support scope before work starts.
- **Defer to Linux companion app:** Keep headless node-host notifications unsupported and let the broader Linux companion app direction own desktop notification delivery later.

Yes, as a source-level reproduction. Current main allowlists `system.notify` for Linux but the headless node host does not declare or dispatch it, so I did not need a live Linux desktop session to verify the code gap.

## Solution Assessment

Unclear until maintainers choose the backend scope. If Linux support is accepted, the implementation belongs in core node-host code because `system.notify` is reserved by core and plugins cannot register the exact missing surface.

## Summary

This focused fix addresses a credible runaway loop and has no definite line-level correctness defect, but it should remain open until a maintainer confirms the shipped plugin-SDK `flush()` semantics and the contributor supplies real runtime proof rather than mocked unit execution.

## What This Changes

Caps each draft-stream flush at 20 consecutive sends, reschedules remaining pending text through the throttle timer, and adds a continuous-replenishment regression test.

## Best Possible Solution

Keep the bounded scheduler, explicitly define and test the public `flush()` completion contract so finalization cannot suppress queued text, and demonstrate the behavior with redacted instrumented runtime or live-channel evidence.

## Solution Assessment

Unclear pending the SDK contract decision: a bounded batch is the right primitive for preventing starvation, but the safest implementation must also specify what awaiting public `flush()` guarantees to plugin callers.

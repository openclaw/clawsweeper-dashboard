Full review comments:

- **[P1] Port location params to the active protocol schema:** `src/gateway/protocol/schema/agent.ts:106-115`
  - body: This adds the new SendParams fields under the old `src/gateway/protocol` schema, but current main validates gateway sends from `packages/gateway-protocol/src/index.js`, and that active schema is `additionalProperties: false` without these fields. After rebasing, protocol clients can still have `latitude`/`longitude` rejected unless the change is moved to the active package and regenerated there.
  - confidence: 0.91
- **[P2] Call the registered send RPC for fallback locations:** `src/infra/outbound/message.ts:571`
  - body: `sendLocation` still calls a standalone `location` gateway method, but this PR implements location handling inside the existing `send` handler and does not register a separate RPC. Any non-dry-run path that falls through to core `sendLocation` will fail at runtime instead of delivering the pin, so pass the location params through `method: "send"`.
  - confidence: 0.9
- **[P2] Return the resolved WhatsApp target for location sends:** `extensions/whatsapp/src/send.ts:300`
  - body: The active listener resolves outbound WhatsApp targets through the LID-aware send API, but this wrapper returns the pre-resolution `toWhatsappJid(to)`. For LID-mapped accounts, location sends can report the PN JID instead of the actual delivered remote JID, drifting from the text/media send behavior and confusing delivery/session metadata.
  - confidence: 0.82

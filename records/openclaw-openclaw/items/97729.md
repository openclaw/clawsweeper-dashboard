## Summary

Keep open: the final branch removed the earlier command-surface expansion, but the new preflight still uses the normal node command allowlist, so a capable desktop/headless node that declares `system.execApprovals.get/set` can be rejected before the scoped exec-approvals relay invokes it.

## Best Possible Solution

Keep the structured unsupported-capability error, but either make capable exec-approval commands survive the relevant command surface first or make this scoped handler check the correct declared capability without broad policy changes.

## Reproduction Assessment

Yes. Source inspection shows current main relays `exec.approvals.node.get/set` directly to `nodeRegistry.invoke`, while the PR's final preflight checks an allowlist that still excludes exec-approval command IDs by default.

## Solution Assessment

No. Gateway-boundary validation is the right layer for the raw TypeError, but this implementation gates the scoped exec-approvals RPC on the wrong command surface and can reject capable nodes.

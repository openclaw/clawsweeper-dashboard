- **[P1] Honor disabled history before listing or switching:** `src/auto-reply/reply/commands-sessions.ts:170`
  - body: This previous blocker is still present. `/sessions` builds switch targets from retained `sessionHistory` before checking `session.historyLimit`, so after an operator sets the limit to `0`, stale entries can still be listed and selected; the later trim-to-zero path then archives the current session while switching. Guard disabled history before list/target resolution and clear or archive stale retained entries deliberately.
  - confidence: 0.92
- **[P1] Reference retained history transcripts during cleanup:** `src/auto-reply/reply/session.ts:649`
  - body: This previous blocker remains. The PR intentionally leaves old transcripts switchable via `sessionHistory`, but the disk-budget sweep still only counts active store entries' `sessionId`/transcript path, so deployments with `session.maintenance.maxDiskBytes` can delete a retained history transcript while `/sessions` still advertises it. Include history entries in the referenced transcript set or archive them before dropping the reference.
  - confidence: 0.88
- **[P1] Restore the full session boundary before persisting:** `src/auto-reply/reply/commands-sessions.ts:280`
  - body: This previous blocker remains. The switch path rewrites the live `SessionEntry` and only reapplies a small metadata subset, leaving fields such as `authProfileOverride`, CLI session bindings, ACP runtime state, fast/usage, abort cutoff, runtime model/cost/fallback, and exec/elevated settings from the prior session. A resumed session can therefore run with the wrong credentials, provider-side thread, or execution policy.
  - confidence: 0.91

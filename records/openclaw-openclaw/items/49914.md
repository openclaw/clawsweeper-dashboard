## Review Findings

Overall correctness: patch is incorrect

Overall confidence: 0.92

Full review comments:

- **[P1] Honor disabled history before listing sessions:** `src/auto-reply/reply/commands-sessions.ts:170`
  - body: `/sessions` builds its list from persisted `sessionHistory` before checking `session.historyLimit`. If an operator changes the limit to `0`, stale prior sessions are still listed and can still be selected; the switch path then pushes the current session and immediately evicts it, so disabling history does not actually disable access to retained sessions.
  - confidence: 0.9
- **[P1] Keep retained history transcripts referenced by cleanup:** `src/auto-reply/reply/session.ts:649`
  - body: This assignment intentionally keeps old transcript files live while their sessions remain in `sessionHistory`, but the disk-budget sweep still only protects the active transcript for each store entry. With `session.maintenance.maxDiskBytes` enabled, retained history transcripts can be deleted as unreferenced primary transcripts while `/sessions` still offers them, so switching back can land in an empty conversation.
  - confidence: 0.88
- **[P1] Restore or clear the full session boundary:** `src/auto-reply/reply/commands-sessions.ts:280`
  - body: The switch path rewrites the live `SessionEntry` to the target `sessionId`, then reapplies only the small `SessionHistoryItem.metadata` subset. Fields outside that subset, including auth profile overrides, CLI/ACP handles, execution/elevated policy, runtime model fields, fallback state, cost, abort state, and system prompt reports, can be inherited from the session being left, so resumed sessions can run under the wrong credentials, runtime, or policy.
  - confidence: 0.92

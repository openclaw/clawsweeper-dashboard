## Summary

This issue remains necessary: current Feishu ingress still creates the per-chat queue with only a timeout log callback, while the queue defaults to five minutes and lets the original task continue after eviction. The proposed lifecycle and asynchronous-delivery surface needs a maintainer product decision rather than an isolated bugfix.

Likely related people: @m1heng is the documented community owner of the Feishu plugin (high confidence); @ngutman recently defined the adjacent per-chat sequencing boundary (medium confidence).

## What This Changes

Add a configurable Feishu per-chat queue timeout and a supported way to show or manage progress for agent turns that outlive the queue’s blocking cap.

## System Context

The Feishu plugin receives chat events, serializes ordinary same-chat turns through a per-key queue, and dispatches each turn to the agent runtime. That queue protects same-chat ordering, but once its blocking cap expires later messages can proceed while the original agent task still produces a reply.

## Architecture Diagram

flowchart LR
  A[Feishu inbound message] --> B[Message receive handler]
  B --> C[Per-chat sequential queue]
  C --> D[Agent turn dispatch]
  C --> E[Five-minute eviction decision]
  E --> F[Later same-chat messages]
  D --> G[Streaming or final Feishu reply]
  F --> G

## Best Possible Solution

Keep the five-minute safety cap by default, first define the user-facing progress and ordering contract, then add only a Feishu-plugin-owned, account-inheritable setting if operators demonstrably need to tune that cap; avoid generic lifecycle hooks or background-delivery APIs until their cross-channel contract is approved.

- **Keep the fixed policy:** Retain the present safety cap and rely on existing typing and streaming feedback without exposing a timeout control.

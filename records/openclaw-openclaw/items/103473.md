- `P2`: The deterministic bug omits intended media for a narrow scheme-casing input without crashing the wider runtime.
- `impact:message-loss`: Affected replies silently lose the intended attachment and expose the raw media directive instead.

## Summary

Current `main` and the latest release still use lowercase-only `file://` normalization, so the reported attachment omission remains valid. Keep this issue open while maintainers select and land one of the three linked candidate PRs; none has merged yet.

## What This Changes

Make `MEDIA:` extraction treat the `file://` URI scheme case-insensitively so uppercase and mixed-case local file URIs become attachments instead of visible text.

## Best Possible Solution

Land one focused case-insensitive file-URI parser fix with uppercase and mixed-case regression cases; broaden the change to other media entry points only where direct tests prove the same defect.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes. Adding the reported uppercase URI to the existing `splitMediaFromOutput` table deterministically exercises the unchanged lowercase-only normalization path; this read-only review confirmed the source path but did not execute tests.

## Solution Assessment

Yes for the reported defect: case-insensitive scheme removal at the parser boundary plus uppercase and mixed-case regression coverage is the narrowest maintainable fix. Downstream resolver changes should be included only with separate proof and tests.

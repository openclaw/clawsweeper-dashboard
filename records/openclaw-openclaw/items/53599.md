## Label Justifications

- `P1`: The issue reports a shipped regression that blocks remote browser control for managed-hosting and cross-machine users after the extension relay removal.
- `impact:security`: A restored relay would control authenticated browser sessions across extension, gateway, and network boundaries.

## Summary

Keep open: current main and the latest release still reject the legacy `driver: "extension"` path, migrate relay config to `existing-session`, and do not provide the one-click cross-machine Chrome extension relay workflow reported here. The active My Browser bridge PR is useful related work, but it is still open and stacked, so it is not a safe replacement close target yet.

## What This Changes

The issue reports that removing the legacy Chrome extension browser relay left no non-technical cross-machine browser-control replacement for managed remote OpenClaw deployments.

## Best Possible Solution

Keep this issue open until maintainers either land a vetted browser backend or extension-bridge replacement with migration, docs, tests, and security review, or explicitly decide to keep the legacy relay retired and document the supported alternatives.

## Reproduction Assessment

Yes, at source level: current main rejects `driver: "extension"`, migrates legacy extension config to `existing-session`, and has a contract test for the unsupported-driver response. I did not run a live cross-machine Chrome extension relay setup.

## Solution Assessment

No for an automatic direct restore. The issue is valid, but the best fix needs maintainer-approved browser strategy and security design, likely involving the browser-backend/plugin API or the open My Browser bridge work rather than only restoring an old driver string.

## Summary

Keep open: current main and v2026.6.11 still reject the legacy Chrome extension relay driver and migrate it to host-local Chrome MCP existing-session, while the reported one-click cross-machine relay workflow remains missing and security-sensitive.

## What This Changes

The issue asks to restore or replace the removed Chrome extension browser relay so remote OpenClaw hosts can control a user's local Chrome without local CLI, Node, or special Chrome launch setup.

## Best Possible Solution

Maintainers should explicitly choose either to keep the relay retired with clearer migration guidance, or to design a secure browser-backend/plugin API plus an optional relay implementation with migration, docs, tests, and security review.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw restore cross-machine Chrome extension relay support as a maintained profile driver/plugin path, or keep it retired until a browser-backend Plugin SDK seam and security model are designed?

Rationale: This choice controls remote browser-control authority over signed-in sessions and a public config/API surface, so automation cannot safely decide it by restoring the old driver string.

Likely owner: vincentkoc

Owner reason: He owns the strongest recent history for the removal and migration that created this compatibility and security decision.

Owner confidence: high

Options:

- **Design secure plugin/API seam (recommended):** Define the browser backend contract, relay permissions, auth, tab ownership, audit logging, migration, and tests before accepting an optional relay implementation.
- **Keep relay retired:** Treat existing-session, browser node, and remote CDP as the supported paths and document why the extension relay is no longer a supported OpenClaw runtime path.
- **Restore a first-party relay driver:** Bring back a maintained `extension` driver directly in the browser plugin, accepting core ownership of the relay lifecycle and security boundary.

## Reproduction Assessment

Yes, at source level: current main rejects `driver: "extension"`, doctor migrates it to `existing-session`, and a contract test asserts the unsupported-driver response. I did not run a live cross-machine Chrome extension relay setup.

## Solution Assessment

No for an automatic direct restore. The issue is valid, but the best fix needs maintainer-approved browser strategy and security design, likely involving the browser-backend/plugin API tracked at https://github.com/openclaw/openclaw/issues/19289 rather than only restoring an old driver string.

## Label Justifications

- `P1`: The report describes a shipped regression that blocks cross-machine browser control workflows for managed-hosting users and follow-up commenters.
- `impact:security`: Restoring or replacing the relay would grant remote browser-control authority over authenticated browser sessions across extension, gateway, and network boundaries.

## Summary

Keep open: current main and v2026.6.11 still reject the legacy Chrome extension relay driver and migrate it to host-local Chrome MCP, which does not replace the reported one-click cross-machine browser relay workflow. This remains the concrete canonical regression and needs maintainer product and security direction before any implementation.

## What This Changes

The issue requests restoration or a secure replacement for the removed Chrome extension browser relay path used for cross-machine browser control.

## Best Possible Solution

Maintainers should explicitly choose whether to keep the relay retired with clearer migration guidance, or design a secure browser-backend/plugin API plus an optional relay implementation with migration, docs, tests, and threat-model review.

## Reproduction Assessment

Yes. Current main has a source-level reproduction: driver: "extension" is rejected by config/schema and profile creation, doctor migrates legacy relay config away, and a browser contract test asserts the unsupported-driver response; I did not run a live cross-machine Chrome extension relay setup.

## Solution Assessment

No for an automatic direct restore. The issue is valid, but the maintainable fix needs maintainer-approved browser strategy and security design, likely involving the browser-backend plugin API tracked at https://github.com/openclaw/openclaw/issues/19289 rather than only widening the driver enum.

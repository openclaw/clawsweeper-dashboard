## Label Justifications

- `P1`: The issue reports a shipped regression that blocks remote browser control for managed-hosting and cross-machine users after the extension relay removal.
- `impact:security`: The requested relay would control authenticated browser sessions across extension, gateway, and network boundaries, making browser credentials and operator authority central to the issue.

## Summary

Keep open: current main and v2026.6.11 still reject `driver: "extension"`, remove/migrate the legacy relay config, and do not provide the one-click cross-machine Chrome extension relay workflow described by the reporter and follow-up users.

## What This Changes

The issue asks to restore or replace the removed Chrome extension relay so remote OpenClaw instances can control a user's local Chrome across machines without requiring a local CLI, node host, or CDP setup.

## Best Possible Solution

Maintainers should choose the browser-control strategy explicitly: keep the relay retired with clearer migration guidance, or design a secure browser-backend Plugin SDK seam plus an optional relay implementation with migration, docs, tests, and security review.

Options:

- **Design a secure backend seam first (recommended):** Define a versioned browser backend/driver contract, then evaluate an optional relay implementation against explicit tab scope, auth, audit, packaging, migration, and docs requirements.
- **Keep the relay retired:** Leave `driver: "extension"` unsupported and improve migration guidance toward node host, remote CDP, and external tools for users who can accept those tradeoffs.
- **Restore a first-party relay directly:** Reintroduce the old extension relay as an opt-in first-party driver, accepting the larger security and compatibility review burden in core.

## Reproduction Assessment

Yes, at source level: current main rejects `driver: "extension"`, migrates it away in doctor, and has a contract test for the unsupported-driver response. I did not run a live cross-machine Chrome extension relay setup.

## Solution Assessment

No for an automatic direct restore. The issue is valid, but the best fix needs maintainer-approved browser strategy and security design, likely involving the browser-backend/plugin API tracked at https://github.com/openclaw/openclaw/issues/19289 rather than only restoring an old driver string.

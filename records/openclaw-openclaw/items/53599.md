## Label Justifications

- `P1`: The issue reports a shipped regression that blocks remote browser control for managed-hosting and cross-machine users after the extension relay removal.
- `impact:security`: The requested relay would control authenticated browser sessions across extension, gateway, and network boundaries.

## Summary

Keep open: current main and v2026.6.11 still reject `driver: "extension"`, doctor migrates legacy extension relay config to `existing-session`, and the documented alternatives remain node-host or remote-CDP based rather than the one-click cross-machine Chrome extension relay described by multiple affected users.

## What This Changes

The issue asks OpenClaw to restore or replace the removed Chrome extension browser relay so remote OpenClaw hosts can control a user's local Chrome across machines without client-side CLI setup.

## Best Possible Solution

Maintainers should decide the browser-control strategy explicitly: keep the relay retired with clearer migration limits, or design a secure browser-backend/plugin API plus an optional relay implementation with migration, docs, tests, and security review.

## Reproduction Assessment

Yes, at source level: current main rejects `driver: "extension"`, has a profile-create contract test for that rejection, and doctor migrates legacy extension profiles to `existing-session`. I did not run a live cross-machine Chrome extension relay setup.

## Solution Assessment

No for an automatic direct restore. The issue is valid, but the best fix needs maintainer-approved browser strategy and security design, likely involving the browser-backend/plugin API tracked at https://github.com/openclaw/openclaw/issues/19289 rather than only restoring an old driver string.

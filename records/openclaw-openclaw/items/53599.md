## Summary

Keep open: current main and the latest release still reject the legacy Chrome extension relay driver and migrate old relay config to host-local Chrome MCP `existing-session`, while no merged replacement provides the reported one-click cross-machine browser relay workflow. The broad backend API tracker and My Browser PR are useful related work, but they do not safely supersede this concrete regression yet.

## What This Changes

The issue asks OpenClaw to restore or replace the removed Chrome extension browser relay so remote Gateway deployments can control a user's local Chrome across machines without a local CLI/node setup.

## Best Possible Solution

Keep this issue open until maintainers either land a vetted browser backend or extension-bridge replacement with migration, docs, tests, and security review, or explicitly decide to keep the legacy relay retired and document the supported alternatives.

## Reproduction Assessment

Yes, at source level: current main rejects `driver: "extension"` in config and profile creation, migrates legacy relay config away, and has a contract test expecting the unsupported-driver response. I did not run a live cross-machine Chrome extension relay setup in this read-only review.

## Solution Assessment

No for an automatic direct restore. The report is valid, but the best fix needs maintainer-approved browser strategy and security design, likely through a browser-backend/plugin API or vetted bridge replacement rather than only restoring the old enum value.

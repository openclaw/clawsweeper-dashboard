## Summary

Keep open: current main and v2026.6.11 still reject the legacy Chrome extension relay driver and migrate it to host-local Chrome MCP, while the linked browser-backend API issue is related design work rather than a replacement for this concrete cross-machine relay regression.

## What This Changes

The issue requests restoring or replacing the removed Chrome extension browser relay so remote OpenClaw hosts can control a user's local Chrome without requiring a local Node host, remote CDP flags, or CLI setup.

## Best Possible Solution

Maintainers should choose the browser-control strategy explicitly: keep the relay retired with clearer migration guidance, or design a secure browser-backend/plugin API plus an optional relay implementation with migration, docs, tests, and security review.

Options:

- **Design secure backend seam (recommended):** Add a maintainer-approved browser backend/plugin API and implement the relay as an optional vetted backend with scoped permissions, audit logs, migration, docs, and tests.
- **Keep relay retired:** Close or narrow the request after documenting that managed-hosting users must use node hosts, remote CDP, or an external relay outside OpenClaw core.
- **Restore first-party relay:** Bring back the legacy extension relay as a built-in driver, accepting the compatibility benefit and owning the renewed security and maintenance surface in core.

## Reproduction Assessment

Yes, at source level: current main rejects `driver: "extension"`, migrates it away in doctor, and has a contract test for the unsupported-driver response. I did not run a live cross-machine Chrome extension relay setup.

## Solution Assessment

No for an automatic direct restore. The maintainable solution needs a maintainer-approved browser strategy and security design, likely involving the browser-backend/plugin API tracked at https://github.com/openclaw/openclaw/issues/19289 rather than only restoring an old driver string.

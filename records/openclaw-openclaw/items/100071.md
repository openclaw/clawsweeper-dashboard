- `impact:security`: A workspace skill can silently replace a reviewed plugin or bundled skill in the active skill snapshot, changing trusted instruction behavior without operator signal.
- `impact:ux-friction`: The active skill list, Control UI, and doctor surfaces give operators no visible clue when a same-named lower-precedence skill is being shadowed.

## Summary

Keep open: current main and v2026.6.11 still implement same-name skill precedence by overwriting lower-precedence records without carrying collision metadata into status, CLI, Control UI, or doctor. The report is valid security/visibility hardening, but the fail-closed config piece needs maintainer product/security direction before a repair PR is safe.

## What This Changes

Request warnings, list/UI visibility, optional deny policy, and doctor lint for workspace skills that shadow same-named plugin or bundled skills.

## Best Possible Solution

Add first-class shadow metadata during skill loading, surface it in `openclaw skills list`, Control UI, and doctor lint, keep documented precedence as the default, and gate any fail-closed policy behind maintainer-approved config, docs, and tests.

## Reproduction Assessment

Yes, source-level. Create a same-named plugin or bundled skill and workspace skill: current loader precedence keeps only the workspace record, and the status/CLI/UI shapes have no shadow metadata to report the lower-precedence source.

## Solution Assessment

Unclear as a final implementation. Warning and visibility metadata are the right first step, but fail-closed shadow denial is a compatibility-sensitive config decision that maintainers should approve before implementation.

## Summary

Keep open. Current main and v2026.6.11 still record writable custom Docker bind metadata, but sandbox file mutations are rejected unless `workspaceAccess` is `"rw"`; the related open PR at https://github.com/openclaw/openclaw/pull/73385 only tries to hide write tools for `"none"` and is not a viable implementation of mount-aware writable binds.

## What This Changes

The issue requests least-privilege sandbox support so explicitly writable custom Docker binds can be edited while `workspaceAccess` remains `"none"`.

## Best Possible Solution

Approve one mount-aware sandbox write contract: file tools may mutate only resolved `source: "bind"` targets marked writable under `workspaceAccess: "none"`, while workspace mounts, read-only binds, protected skills, and blocked paths stay denied.

Question: Should `workspaceAccess: "none"` allow normal file tools to write explicitly configured `docker.binds` targets whose resolved mount is `:rw`?

Rationale: The source path is clear, but the choice changes sandbox host-write authorization and could conflict with the stricter fail-closed direction in the adjacent open PR, so automation should not choose the permanent security contract alone.

Likely owner: steipete

Owner reason: Recent sandbox bridge/mount/docs history and the security-boundary framing point most strongly to steipete for the product/security decision.

Owner confidence: medium

Options:

- **Approve Mount-Aware Writable Binds (recommended):** Implement write authorization from resolved mount metadata so only explicit `:rw` bind targets are writable under `workspaceAccess: "none"`, with Docker/bridge/docs/tests proving `:ro` and workspace paths remain blocked.
- **Keep None Fully Non-Writable:** Treat `workspaceAccess: "none"` as disabling all file-tool writes, close or reframe this request, and update docs so bind `:rw` does not imply normal file-tool writability in that mode.
- **Defer Into Broader None-Mode Policy:** Resolve this together with isolated `/workspace` writability in https://github.com/openclaw/openclaw/issues/37634 and the tool-surface gate in https://github.com/openclaw/openclaw/pull/73385.

## Reproduction Assessment

Yes. Source inspection shows current main records writable bind metadata but `ensureWriteAccess` still rejects mutations unless `workspaceAccess` is `"rw"`; no live Docker repro was run in this read-only review.

## Solution Assessment

Unclear until maintainers settle the security contract. If approved, the best fix is a narrow resolved-mount write policy, not broad `workspaceAccess: "rw"` and not simply hiding all write tools under `"none"`.

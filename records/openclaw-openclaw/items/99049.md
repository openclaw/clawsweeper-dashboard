## Summary

Keep open: current main and the latest release still call the WhatsApp Baileys socket without a shared per-socket send queue, and an open closing PR already owns the candidate fix path.

## What This Changes

The issue asks OpenClaw to serialize concurrent WhatsApp Web outbound `sendMessage` calls per active Baileys socket.

## Best Possible Solution

Review and either land or close https://github.com/openclaw/openclaw/pull/99050; if it lands, close this issue from the merge, and if it does not, keep this issue as the canonical bug report for a replacement fix.

## Reproduction Assessment

Yes, source-level: current main calls the same Baileys socket's `sendMessage` directly from the Web send facade and timeout-adapter path, so a mocked pending first send can observe a second raw send before the first settles. I did not run tests because this review is read-only.

## Solution Assessment

Yes for the issue direction: a per-socket FIFO at the Web send facade and shared timeout-adapter boundary is the narrow maintainable fix shape. The linked PR is the right candidate to review rather than starting a duplicate repair.

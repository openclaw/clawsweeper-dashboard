## Summary

Keep open; current main and the latest release still expose only memory manager/list/read helpers, while scan, watch, hash-diff, chunking, and stale cleanup remain owned by memory-core internals and need a maintainer-approved SDK/security design.

## What This Changes

Request to expose the memory file scanning, watching, incremental indexing, and deletion cleanup pipeline as a public Memory Plugin API for external memory backends.

## Best Possible Solution

Define a narrow documented memory-ingestion SDK contract with explicit file scope consent, startup and watch event semantics, chunking ownership, deletion/stale cleanup behavior, backpressure, retries, and contract tests against memory-core plus an external-style memory plugin.

Question: What public memory-ingestion SDK contract should OpenClaw support for third-party memory plugins that need file indexing from MEMORY.md, memory/, and extraPaths?

Rationale: The requested behavior adds public plugin API surface and changes the local-file trust boundary, so implementation should follow maintainer-approved semantics rather than the issue's callback sketch by default.

Likely owner: Peter Steinberger

Owner reason: The memory slot, memory-core extraction, and memory host SDK extraction history make Peter Steinberger the best available owner for the API direction call.

Owner confidence: high

Options:

- **Design a Narrow SDK Seam (recommended):** Add a reviewed memory-ingestion contract with explicit file scope, event batching, delete semantics, chunking ownership, and compatibility tests before external plugins consume it.
- **Expose Helpers Only:** Keep list/read helpers as the supported surface and let memory plugins own their own watchers and stale cleanup, accepting backend-specific drift.
- **Defer File Indexing for External Memory:** Leave external memory plugins conversation-only until memory plugin architecture converges on a recommended backend path.

Unclear. A host-delivered file event API is plausible, but maintainers should choose the stable SDK shape and security contract before implementation.

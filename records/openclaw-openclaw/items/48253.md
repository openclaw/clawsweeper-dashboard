## Label Justifications

- `P2`: This is a normal-priority memory/plugin API feature with ecosystem value, but it is not an urgent outage or blocked first-run path.
- `impact:session-state`: The request affects whether configured memory files and extraPaths become durable searchable agent memory across active memory backends.
- `impact:security`: The proposed API would expose local memory file contents and extraPaths data to third-party memory plugins, changing the file-access trust boundary.

## Summary

Keep open; current main and the latest release still expose memory helper/runtime surfaces but not a host-delivered scan, watch, hash-diff, chunking, and stale-cleanup API for memory plugins, and the remaining work needs maintainer product and security design.

## What This Changes

Request to expose the memory file scanning, watching, hash-diff, chunking, and stale cleanup pipeline as a public memory plugin API.

## Best Possible Solution

Define a narrow documented memory ingestion SDK seam with explicit file scope consent, event delivery semantics, chunking/deletion ownership, stale cleanup behavior, security review, and contract tests against memory-core plus an external-style memory plugin.

Options:

- **Design guarded SDK seam (recommended):** Add a documented file-ingestion contract with explicit plugin opt-in, file scope, event semantics, stale cleanup, security review, and compatibility tests.
- **Keep helpers only:** Leave list/read helpers as the supported surface and document that memory plugins must own their own watcher, diffing, and cleanup behavior.
- **Defer behind broader memory backend design:** Keep this issue open as an API design item until maintainers settle the related memory backend/provider abstraction.

## Reproduction Assessment

Yes, at source level: current main has no MemoryFileEvent, onMemoryFileChange, onMemoryFileScan, or equivalent fileIndexing capability, while memory-core still owns the scanner/watcher/sync path privately. No live repro is needed because this is an API absence rather than a runtime failure report.

## Solution Assessment

Unclear. A file-event API is plausible, but maintainers should choose the permanent SDK shape and security contract before implementation rather than accepting the exact proposed callback sketch as-is.

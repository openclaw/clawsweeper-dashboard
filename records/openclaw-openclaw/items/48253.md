## Summary

Keep open; current main still has memory-core-owned scan, watch, hash-diff, and stale-cleanup behavior, while the public memory plugin capability lacks a host-delivered file-ingestion API. This is a real SDK and security-boundary product decision, not a stale cleanup close.

## What This Changes

The issue requests a public Memory Plugin API so third-party memory plugins can receive memory file scan, change, delete, chunking, and extraPaths events instead of reimplementing memory-core's file pipeline.

## Best Possible Solution

Define a narrow documented memory ingestion SDK seam with explicit file-scope consent, event/batch/delete semantics, chunking ownership, retry/backpressure behavior, stale cleanup ownership, security review, and contract tests for memory-core plus an external-style memory plugin.

Question: Should OpenClaw add a public host-delivered memory file-ingestion API for active memory plugins, or keep scan/watch/hash-diff/stale-cleanup ownership inside each memory backend/plugin?

Rationale: The source gap is clear, but delivering local memory files and extraPaths contents to plugin code changes the public SDK contract and sensitive local-file trust boundary.

Likely owner: steipete

Owner confidence: high

Options:

- **Approve a narrow SDK design first (recommended):** Design and approve a minimal memory ingestion capability with explicit security, compatibility, and test requirements before implementation.
- **Keep scanning plugin-owned:** Document that memory plugins may use current list/read helpers but must own their own watchers, indexing, deletion, and cleanup behavior.
- **Fold into broader memory backend design:** Defer this issue until a broader memory backend/provider contract also decides file ingestion, search, get, writeback, and status ownership.

## Reproduction Assessment

Yes for the capability gap: current main has no MemoryFileEvent, onMemoryFileChange, onMemoryFileScan, or equivalent fileIndexing capability. Source inspection shows memory-core still owns scanner, watcher, hash diff, and stale cleanup privately.

## Solution Assessment

Unclear. A host-delivered file-event API is plausible, but the proposed callback sketch should not be treated as the best fix until maintainers choose the SDK shape, security contract, and compatibility boundary.

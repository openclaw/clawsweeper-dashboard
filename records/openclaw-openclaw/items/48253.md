## Summary

Keep open; current main and v2026.6.11 still do not expose host-delivered scan, watch, hash-diff, or stale-cleanup hooks for third-party memory plugins, and the remaining work is a public SDK plus local-file trust-boundary decision rather than cleanup closure.

## What This Changes

The issue requests a Memory Plugin API that lets active memory plugins consume the built-in file scanning, watching, incremental sync, chunking, and stale cleanup pipeline.

## Best Possible Solution

Define a narrow documented memory ingestion SDK seam with explicit file-scope consent, event/batch/delete semantics, chunking ownership, retry/backpressure behavior, stale cleanup ownership, security review, and contract tests against memory-core plus an external-style memory plugin.

- **Keep scanning plugin-owned:** Document that memory plugins may use current list/read helpers but must own their own watchers, indexing, deletion, and cleanup behavior.
- **Fold into a broader backend contract:** Defer this request until maintainers decide the larger memory backend contract for ingestion, search, read, writeback, and status ownership.

## Solution Assessment

Unclear. A file-event API is plausible, but the proposed callback sketch should not be treated as the best fix until maintainers choose the SDK shape, security contract, and compatibility boundary.

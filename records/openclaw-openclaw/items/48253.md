## Summary

Keep open; current main and v2026.6.11 expose file list/read helpers but not host-delivered scan, watch, hash-diff, and stale-cleanup hooks for memory plugins, and the change needs public SDK plus local-file trust-boundary design.

## What This Changes

Request to expose the built-in memory file scanning, watching, incremental sync, and stale cleanup pipeline as a Memory Plugin API.

## Best Possible Solution

Define a narrow documented memory ingestion SDK seam with explicit file scope consent, event delivery, chunking/deletion semantics, stale cleanup ownership, security review, and contract tests against memory-core plus an external-style memory plugin.

## Reproduction Assessment

Yes, at source level: current main has no MemoryFileEvent, onMemoryFileChange, onMemoryFileScan, or equivalent fileIndexing capability, while memory-core still owns the scanner/watcher/sync path privately. No live repro is needed because this is an API absence rather than a runtime failure report.

## Solution Assessment

Unclear. A file-event API is plausible, but maintainers should choose the permanent SDK shape and security contract before implementation rather than accepting the exact proposed callback sketch as-is.

## Summary

Keep open; current main and v2026.6.11 still do not expose host-delivered memory file scan/change/delete hooks for memory plugins, and the remaining work is a public SDK plus file-access trust-boundary decision rather than conservative cleanup.

## What This Changes

The issue requests a public memory plugin API for host-delivered file scan, watch, hash-diff, chunking, and deletion events so external memory backends can index configured memory files and extra paths.

## Best Possible Solution

Define a narrow documented memory ingestion SDK seam with explicit file-scope consent, event/batch/delete semantics, chunking ownership, retry/backpressure behavior, stale cleanup ownership, security review, and contract tests against memory-core plus an external-style memory plugin.

Question: Should OpenClaw add a public host-delivered memory file-ingestion API for active memory plugins, or keep file scanning owned by each memory backend/plugin?

Rationale: The source gap is clear, but the permanent SDK shape and local-file trust boundary are product and security decisions that should not be chosen by an automated fix.

Likely owner: steipete

Owner reason: steipete has the strongest recent history across memory host SDK, extraPaths, and memory-lancedb-adjacent plugin boundary work.

Owner confidence: high

Options:

- **Approve a narrow SDK design first (recommended):** Design and approve a minimal memory ingestion capability with explicit security, compatibility, and test requirements before implementation.
- **Keep scanning plugin-owned:** Document that memory plugins may use current list/read helpers but must own watchers, indexing, deletion, and cleanup behavior themselves.
- **Fold into broader backend design:** Defer this issue until a broader memory backend/provider contract also decides file ingestion, search, get, writeback, and status ownership.

## Reproduction Assessment

Yes. Source-level reproduction is high confidence: current main has no MemoryFileEvent, onMemoryFileChange, onMemoryFileScan, or equivalent fileIndexing capability, while memory-core still owns scanner, watcher, hash diff, and stale cleanup privately.

## Solution Assessment

Unclear. A file-event API is plausible, but the proposed callback sketch should not be treated as the best fix until maintainers choose the SDK shape, security contract, and compatibility boundary.

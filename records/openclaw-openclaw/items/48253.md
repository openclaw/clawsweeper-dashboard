## Summary

Keep open. Current main still has memory-core owning scan, watch, hash-diff sync, chunking, and stale cleanup internally; public memory plugins can register runtime/search/prompt/public-artifact surfaces, but not host-delivered memory file scan/change/delete events.

## What This Changes

Request to expose memory-core's file scanning, watching, incremental sync, chunking, and stale cleanup pipeline as a public Memory Plugin API for third-party memory backends.

## Best Possible Solution

Define a narrow documented memory ingestion SDK seam with explicit path consent, event delivery, chunking ownership, deletion/stale-cleanup semantics, and contract tests against memory-core plus an external-style memory plugin.

## Reproduction Assessment

Yes. At source level, current main has no memory file event hooks in `MemoryPluginCapability`, while memory-core privately owns file watching, sync, hash diffing, indexing, and stale cleanup.

## Solution Assessment

Unclear. A file-event seam is plausible, but maintainers should choose callbacks versus a shared scanner/manager protocol and define the security semantics before implementation.

## Summary

Keep open; current main and the latest release still do not expose host-delivered memory file scan/change/delete hooks for active memory plugins, and the remaining work is a public SDK plus local-file trust-boundary decision.

## What This Changes

The issue requests a Memory Plugin API that lets memory plugins consume OpenClaw's existing memory file scan, watch, hash-diff, chunking, and stale-cleanup pipeline.

## Best Possible Solution

Define a narrow documented memory ingestion SDK seam with explicit file-scope consent, event/batch/delete semantics, chunking ownership, retry/backpressure behavior, stale cleanup ownership, security review, and contract tests against memory-core plus an external-style memory plugin.

Options:

- **Keep scanning plugin-owned:** Document that memory plugins may use current list/read helpers but must own watchers, indexing, deletion, and cleanup behavior themselves.
- **Fold into broader backend design:** Defer this issue until a broader memory backend/provider contract also decides file ingestion, search, get, writeback, and status ownership.

## Reproduction Assessment

Yes. Source inspection is high confidence: current main has no MemoryFileEvent, onMemoryFileChange, onMemoryFileScan, or equivalent fileIndexing capability, while memory-core still owns scanner, watcher-triggered sync, hash diffing, and stale cleanup privately.

## Solution Assessment

Unclear. A host file-event API is plausible, but the proposed callback sketch should not be treated as the best fix until maintainers choose the SDK shape, security contract, and compatibility boundary.

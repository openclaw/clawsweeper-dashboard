- `impact:session-state`: The request affects whether configured memory files and extraPaths become durable searchable agent memory across active memory backends.

## Summary

Keep open; current main still lacks a host-delivered memory file scan/change/delete API for active memory plugins, and this remains a public SDK plus local-file trust-boundary decision rather than conservative cleanup.

## What This Changes

Expose the built-in memory file scanning, watching, incremental sync, and stale cleanup pipeline as a public memory plugin API for external memory backends.

## Best Possible Solution

Define a narrow documented memory-ingestion SDK seam with explicit file-scope consent, event/batch/delete semantics, chunking ownership, retry/backpressure behavior, stale cleanup ownership, security review, and contract tests for memory-core plus an external-style memory plugin.

Options:

- **Approve Narrow SDK Design First (recommended):** Design a minimal ingestion capability with explicit security, compatibility, and test requirements before implementation.
- **Keep Scanning Plugin-Owned:** Document that memory plugins may use current list/read helpers but must own watchers, indexing, deletion, and cleanup behavior themselves.
- **Fold Into Broader Memory Backend Contract:** Defer this until a broader memory backend contract decides file ingestion, search, get, writeback, and status ownership together.

## Reproduction Assessment

Yes. Source inspection is high confidence: current main has no MemoryFileEvent, onMemoryFileChange, onMemoryFileScan, or equivalent fileIndexing capability, while memory-core still owns scanner, watcher-triggered sync, hash diffing, and stale cleanup internally.

## Solution Assessment

Unclear. A host file-event API is plausible, but the proposed callback sketch should not be treated as the best fix until maintainers choose the SDK shape, security contract, and compatibility boundary.

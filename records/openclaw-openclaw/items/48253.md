## Summary

Keep open; current main has useful memory-host helper exports, but still does not expose host-delivered scan/change/delete events for active memory plugins. The remaining work is a public SDK and local-file trust-boundary decision, not conservative cleanup.

## What This Changes

Request to expose the built-in memory file scan/watch/index pipeline as a plugin API for third-party memory backends.

## Best Possible Solution

Define a narrow documented memory ingestion SDK seam with explicit file-scope consent, event/batch/delete semantics, chunking ownership, retry/backpressure behavior, stale cleanup ownership, security review, and contract tests against memory-core plus an external-style memory plugin.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should OpenClaw add a public host-delivered memory file-ingestion API for active memory plugins, or keep file scanning, watching, and stale cleanup owned by each memory backend/plugin?

Rationale: The source gap is clear, but the permanent SDK shape decides what local files third-party plugins may receive and how much of the core scanning pipeline becomes public compatibility surface.

Likely owner: steipete

Owner reason: steipete has the strongest recent history around the memory host SDK extraction and plugin-boundary design that this decision would extend.

Owner confidence: high

Options:

- **Approve Narrow SDK Design First (recommended):** Design and approve a minimal memory ingestion capability with explicit security, compatibility, batching, deletion, and test requirements before implementation.
- **Keep Scanning Plugin-Owned:** Document that memory plugins may use current list/read helpers but must own watchers, indexing, deletion, and cleanup behavior themselves.
- **Fold Into Broader Backend Design:** Defer this issue until a broader memory backend contract also decides file ingestion, search, get, writeback, and status ownership.

## Reproduction Assessment

Yes. Source inspection is high confidence: current main has no MemoryFileEvent, onMemoryFileChange, onMemoryFileScan, or equivalent fileIndexing capability, while memory-core still owns scanner, watcher-triggered sync, hash diffing, and stale cleanup privately.

## Solution Assessment

Unclear. A host file-event API is plausible, but the proposed callback sketch should not be treated as the best fix until maintainers choose the SDK shape, security contract, and compatibility boundary.

## Summary

Keep open: current main and the latest release still read only `timeoutMs` for Codex dynamic-tool hard-call deadlines, while `timeoutSeconds` remains a caller argument that can be forwarded unchanged by Codex dynamic tool requests. Two open PRs are candidate fixes, including one linked with closing syntax, so this issue should stay open until a fix merges.

## What This Changes

The issue asks for Codex dynamic-tool hard-call timeout resolution to use `timeoutSeconds` as the seconds-form fallback when `timeoutMs` is absent.

## Best Possible Solution

Review and land one narrow Codex extension fix that updates both dynamic-tool timeout readers and adds regression coverage for `timeoutMs` precedence, `timeoutSeconds` fallback, and invalid seconds values.

## Reproduction Assessment

Yes from source: current `main` reads `timeoutMs` only in the dynamic-tool hard timeout helper, so a call argument object containing only `timeoutSeconds` falls through to configured/default deadlines. I did not run a live tool-call repro in this read-only review.

## Solution Assessment

Yes: reusing the existing seconds-to-milliseconds helper as a fallback after `timeoutMs` is the narrow owner-local fix, with the side-thread copy updated at the same time.

## Summary

Keep open. The explicit Discord process-proxy direction is useful and has real behavior proof, but the PR currently lets a stale `OPENCLAW_PROXY_URL` authorize a non-loopback Discord proxy even when the effective managed process proxy is a different configured URL.

## What This Changes

The PR broadens Discord explicit proxy validation, docs, and tests so a non-loopback `channels.discord.proxy` endpoint is allowed when it matches process proxy configuration while Gateway ambient env fallback remains disabled.

## Best Possible Solution

Land a version that validates non-loopback Discord proxy URLs against the effective active process proxy endpoint only, preserves explicit Gateway proxying, and leaves broader proxy design in https://github.com/openclaw/openclaw/issues/60035.

## Solution Assessment

No. The explicit process-proxy direction is narrower than ambient Gateway fallback, but the validator must compare against the effective proxy endpoint rather than a stale fallback env var before this is the best fix.

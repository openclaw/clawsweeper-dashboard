## Summary

Keep this PR open: it addresses the reported rate-limit failure, but the production path still supplies only three attempts, so it waits about 10s then 20s before its final attempt rather than reaching the proposed 40s/60s rate-limit window. ## What This Changes

The branch classifies memory embedding rate-limit errors separately and gives batch embedding retries a 10s-to-60s exponential backoff schedule instead of the normal short transport-retry delay.

## Best Possible Solution

Make the rate-limit path honor a provider retry-after value when available and otherwise allocate enough rate-limit attempts to cover the intended cooldown, while preserving the existing short retry budget for ordinary transport failures.

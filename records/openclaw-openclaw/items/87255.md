## Summary

Keep open: the fresh-install basename guard addresses the source-reproducible nesting bug, but merging it as-is can move existing shipped users from an already-populated nested state root to an empty parent root without doctor recovery or upgrade tests.

## What This Changes

The PR changes state/config path resolution so an explicit `OPENCLAW_HOME` ending in `.openclaw` or `.clawdbot` is treated as the state/config directory instead of appending another `.openclaw`, and adds resolver regression tests plus mock updates.

## Best Possible Solution

Land the basename guard together with conflict-safe doctor recovery that migrates safe `$OPENCLAW_HOME/.openclaw` layouts, reports conflicts without overwriting user state, and avoids runtime read-through fallback or dual writes.

## Reproduction Assessment

Yes. Source inspection of current main and `v2026.6.11` shows explicit `OPENCLAW_HOME=/path/.openclaw` flows through helpers that append another `.openclaw`, matching the linked report without a live onboarding run.

## Solution Assessment

No. The basename guard is the right fresh-install fix, but the merge-ready solution also needs doctor-owned upgrade recovery for already-written nested state rather than a runtime fallback.

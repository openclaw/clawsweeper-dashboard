## Label Justifications

- `P2`: This is a normal-priority config path bug fix with limited but real blast radius for users who set `OPENCLAW_HOME` to a state-directory-shaped path.
- `merge-risk: 🚨 compatibility`: The PR changes the default runtime/config location for a shipped environment shape and can make existing nested state appear absent.
- `merge-risk: 🚨 auth-provider`: OAuth credentials and agent auth profile state derive from the resolved state directory, so the path switch can strand existing auth data under the old nested location.
- `merge-risk: 🚨 session-state`: Agent/session state and SQLite-backed runtime state derive from the resolved state directory, so existing nested state needs migration or an explicit recovery plan.

## Summary

Keep open: the fresh resolver guard fixes new nested paths, but merging it without doctor recovery can make state already written by released builds under the nested directory appear missing after upgrade.

## What This Changes

The PR changes state/config path resolution so an explicit `OPENCLAW_HOME` ending in `.openclaw` or `.clawdbot` is treated as the state/config directory instead of appending another `.openclaw`.

## Best Possible Solution

Land the basename guard together with conflict-safe doctor recovery that migrates safe `$OPENCLAW_HOME/.openclaw` layouts, reports conflicts without overwriting user state, and avoids runtime read-through fallback or dual writes.

## Reproduction Assessment

Yes. Current main and `v2026.6.11` source both show explicit `OPENCLAW_HOME=/path/.openclaw` flowing through helpers that append another `.openclaw`, matching the linked report without a live onboarding run.

## Solution Assessment

No. The basename guard is the right fresh-install fix, but the merge-ready solution also needs doctor-owned upgrade recovery for already-written nested state rather than a runtime fallback.

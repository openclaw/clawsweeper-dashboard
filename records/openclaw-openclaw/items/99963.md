## Label Justifications

- `P1`: A configured fallback chain can be bypassed during real main-turn timeouts, breaking a live agent workflow for affected users.
- `impact:session-state`: The failure depends on embedded session takeover cleanup state and whether that state should remain fatal for fallback.
- `impact:auth-provider`: The observable bug is provider/model fallback routing skipping configured fallback candidates after a provider timeout.

## Summary

Keep this issue open: current main and the latest release still encode the takeover-fatal behavior for provider prompt errors that carry cleanup takeover. The remaining question is an explicit session-state versus fallback policy decision, not a conservative cleanup close.

## What This Changes

The issue reports that main-turn provider timeouts preserved in EmbeddedAttemptPromptErrorWithCleanupTakeoverError are treated as pure embedded session takeover and bypass configured model fallback.

## Best Possible Solution

Maintainers should decide the contract, then either land or narrow a promptError-aware exception so provider timeouts can fall back while pure session takeovers still abort, or explicitly keep the current takeover-fatal behavior with tests/docs aligned.

## Reproduction Assessment

Yes, at source level: current main constructs a takeover-named wrapper with `.promptError`, and the fallback classifier aborts on the wrapper name before inspecting that field. I did not run a live timeout race, but the inspected path matches the reporter's logs.

## Solution Assessment

Unclear until maintainers decide the session-takeover versus provider-fallback contract. The suggested `promptError` unwrapping is a plausible narrow repair, but it would revise behavior that was intentionally merged for session-state safety.

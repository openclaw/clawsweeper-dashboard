## Best Possible Solution

Land the runtimePackages fix after a maintainer-approved Codex HOME migration/owned-profile strategy and explicit source-pinned Codex behavior, while keeping user path precedence and the before/after command-exec proof.

- **[P1] Preserve Codex state during the HOME switch:** `nix/scripts/openclaw-codex-app-server-wrapper.sh:13`
  - body: This still changes the app-server HOME from inherited HOME to `$CODEX_HOME/home` unconditionally. Existing Codex auth, config, or session state that upstream reads under the inherited native HOME will not be seen after upgrade unless the PR migrates or preserves that state, so existing Codex agents can look logged out or differently configured even though their runtime plugin choice did not change.
  - confidence: 0.88
- **[P1] Avoid failing startup on existing profile state:** `nix/scripts/openclaw-codex-app-server-wrapper.sh:36-38`
  - body: When `$CODEX_HOME/home/.nix-profile/bin` exists as a regular file or directory, this wrapper exits before `exec`ing Codex. A real upgrade can leave unexpected profile state there, so the managed launcher should use an owned path, repair safely, or keep Codex running while reporting the conflict instead of turning the runtime-path fix into an app-server startup failure.
  - confidence: 0.84
- **[P2] Gate source-pinned Codex plugins explicitly:** `nix/modules/home-manager/openclaw/codex-app-server.nix:49`
  - body: The adapter only offers the launcher when `inst.runtimePlugins` contains `codex`, while the repository also supports locked `runtimePluginSources`. A source-pinned entry with id `codex` can load the Codex plugin through the public source path but miss this runtimePackages fix, so please either support that path with the matching artifact or reject it with a focused assertion/test.
  - confidence: 0.78

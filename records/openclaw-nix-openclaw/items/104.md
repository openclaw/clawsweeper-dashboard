## Summary

Keep open for a narrow maintainer product decision: current documentation intentionally requires reproducible npm dependency metadata and forbids combining generated runtime-plugin configuration with raw `plugins.load.paths`, while ByteRover’s published package shape does not clearly satisfy that supported path. The manual local-path workaround demonstrates demand, but does not establish that arbitrary dependency-bearing npm plugins should become a supported Nix packaging mode.

## What This Changes

The issue requests a supported declarative way to install ByteRover as a context-engine plugin while composing it with catalog runtime plugins.

## Best Possible Solution

Choose one supported ownership model: preferably have ByteRover publish a self-contained or shrinkwrapped npm artifact that works through `runtimePluginSources`, then document its context-engine slot configuration; only add composable extra plugin paths if maintainers explicitly want that general capability and can preserve a single generated `plugins.load.paths` source of truth.

## Summary

Keep open for maintainer judgment: current main still cannot package ByteRover 4.0.0 through `runtimePluginSources`, and changing that would expand the repository's current deterministic runtime-plugin boundary.

## What This Changes

The issue asks how to install the ByteRover context-engine plugin declaratively without conflicting with existing runtime plugin configuration.

## Best Possible Solution

Keep the deterministic Nix runtime-plugin contract, and either have ByteRover publish bundled dependencies or `npm-shrinkwrap.json`, or make an explicit maintainer-approved policy change for unshrinkwrapped third-party plugins.

## Reproduction Assessment

Yes, at source level: ByteRover 4.0.0 declares a runtime dependency, its tarball lacks `node_modules` and `npm-shrinkwrap.json`, and current installer code fails that artifact shape. The raw-load-path conflict is also directly enforced by current module assertions.

## Solution Assessment

No automatic repo fix is clearly best: the current fail-closed behavior matches README and module policy. Installing ByteRover as published needs an upstream artifact change or a maintainer decision to expand nix-openclaw's dependency materialization model.

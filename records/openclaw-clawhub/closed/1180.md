## Label Justifications

- `P2`: The dashboard remains usable, but supported deployment modes can leave a persistent red warning that needs a bounded policy and implementation change.
- `impact:ux-friction`: Operators receive an alarming mismatch status without an in-product distinction between expected partial deployment and an actual release failure.

## Summary

The reported behavior remains on current main: the dashboard classifies every populated frontend/Convex SHA mismatch as a red deployment-drift alert, while the production workflow supports component-only deployments that can intentionally create that state. No canonical issue, merged fix, or documented policy establishes how those deployments should be represented, so this issue remains necessary pending an operations/product decision.

## What This Changes

Clarify or correct the persistent dashboard warning shown when frontend and Convex deployment versions differ.

## Best Possible Solution

Keep SHA drift detection, but persist enough deployment context to show expected component-only drift as a temporary lower-severity notice and escalate persistent or unintended skew with a clear operator action.

## Maintainer Decision

Question: How should the dashboard classify a SHA mismatch produced by the supported backend-only or frontend-only production deployment targets?

Rationale: Source and tests enforce a red alert for every complete mismatch while deployment automation explicitly permits operations that create one, so the intended severity, grace period, and convergence requirement cannot be inferred safely from code.

Likely owner: Patrick-Erichsen

Owner reason: Patrick is the strongest current-history owner across the warning implementation, deployment workflow, and recent release infrastructure.

Owner confidence: high

Options:

- **Make the warning deploy-aware (recommended):** Record deployment target and time, show expected partial drift as a temporary lower-severity notice, and escalate only persistent or unintended skew.
- **Require SHA convergence:** Keep the strict red alert and require every component-only production deployment to be followed by a same-SHA full deployment.
- **Move drift out of the UI:** Remove the dashboard alert and expose mismatches only through deployment automation, logs, or operator diagnostics.

## Reproduction Assessment

Yes at source level: current main deterministically renders the warning whenever both SHAs are populated and unequal, and the supported component-only deployment workflow provides a concrete path to that state. A live production run was not performed during this read-only review.

## Solution Assessment

No specific implementation is approved yet; simply hiding the banner is too broad, while keeping it permanently red ignores supported deployment modes. The narrow maintainable solution is deploy-aware classification after maintainers choose the convergence policy.

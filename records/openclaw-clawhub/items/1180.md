## Label Justifications

- `P2`: The dashboard remains functional, but the persistent deployment-health warning is a bounded correctness and operator-UX issue.
- `impact:ux-friction`: Users receive an alarming warning without an in-product distinction or recovery path for intentional single-target deployments.

## Summary

Current main still intentionally shows the warning for any populated frontend/Convex SHA mismatch, while production tooling supports single-target deploys that can create that state; no later fix or canonical replacement resolves whether such drift is an error or a tolerated rollout state.

## What This Changes

Clarify or correct the dashboard’s persistent deployment-version drift warning when the frontend and Convex report different build SHAs.

## Best Possible Solution

Retain deployment-integrity detection, but define single-target rollout semantics and either require immediate same-SHA convergence with clear recovery guidance or record enough rollout metadata to distinguish recent intentional partial deployment from persistent failed convergence.

## Maintainer Decision

Required: true

Question: Should backend-only or frontend-only production deploys be required to converge immediately to the same SHA, or should the dashboard treat their resulting mismatch as a tolerated rollout state?

Rationale: Current main contains both a strict same-SHA deployment invariant and supported single-target deployment modes, so changing warning severity or suppression requires an explicit operational policy choice.

Likely owner: Patrick-Erichsen

Owner confidence: high

Options:

- **Require immediate convergence (recommended):** Keep the red warning and require each single-target production deploy to be followed by a full same-SHA deployment or documented convergence operation.
- **Model partial rollout state:** Record deploy target and timing so recent intentional single-target drift is informational while persistent unexplained drift remains actionable.
- **Remove dashboard detection:** Rely on workflow checks and logs, accepting the loss of a user-visible signal for incomplete frontend/backend convergence.

## Reproduction Assessment

Yes at source level: a single-target deploy can update only one recorded SHA, and current helper and UI tests deterministically produce the alert when both populated SHAs differ. A fresh authenticated production browser reproduction was not performed.

## Solution Assessment

Unclear until maintainers define the supported production rollout contract; changing only the banner is too narrow because it could either hide failed convergence or preserve misleading severity.

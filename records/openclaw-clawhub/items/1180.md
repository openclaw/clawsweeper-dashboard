## Summary

Keep open: current main still renders the dashboard deployment-drift warning whenever the frontend and Convex build SHAs both exist and differ, and the repo also documents same-SHA deployment as the intended contract. The remaining question is whether this warning should stay strict or be downgraded for expected partial deploys.

## What This Changes

The issue asks for the dashboard’s persistent deployment-version drift warning to stop showing when the dashboard otherwise works.

## Best Possible Solution

Define the deployment contract, then update the banner, tests, and deploy docs so coordinated deploys use the same SHA and expected partial deploys are either informational or not warned as actionable drift.

Question: Should ClawHub treat frontend/Convex build-SHA mismatch as an actionable dashboard warning, or should expected frontend-only/backend-only deploy drift be downgraded or suppressed?

Rationale: Current source and tests intentionally warn on any unequal SHAs, while the deployment workflow supports separate frontend and backend targets; changing this without maintainer intent could either hide real skew or keep noisy expected warnings.

Likely owner: Patrick-Erichsen

Owner reason: He owns the current drift banner, metadata query, and deployment-stamping implementation in current-main history.

Owner confidence: high

Options:

- **Keep Strict Same-SHA Warning (recommended):** Treat the warning as correct when SHAs differ and fix deployment stamping or release ordering when production drifts.
- **Downgrade Expected Partial Drift:** If partial deploys are normal, make the banner copy or severity distinguish expected partial drift from actionable skew and update tests and docs together.
- **Disable Drift Detection:** Suppressing the check removes noisy warnings but loses the signal that catches real frontend/backend deployment skew.

Keep open for maintainer judgment: current main and the live ClawHub API fix the original publish-time global slug collision, but this issue is collaborator-authored and a later comment reports a remaining installed-skill UI `skill.not_found` symptom that was not reproduced in this checkout.

## What This Changes

The issue reports that skill publishing still blocks same-slug skills across different publisher namespaces because the write path treats `slug` as globally unique.

## Best Possible Solution

Keep the shipped owner-scoped ClawHub publish/API behavior, then have a maintainer either close this as fixed for ClawHub or split the remaining installed-skill UI symptom to the resolver surface that owns it.

## Reproduction Assessment

No for the original publish collision: current main resolves publish by owner publisher plus slug, and live owner-qualified `anysearch` API calls resolve both duplicate publishers. Unclear for the later OpenClaw UI `skill.not_found` symptom because that installed-skill management path was not reproduced here.

## Solution Assessment

Yes for the original ClawHub publish collision: resolving by `(ownerPublisherId, slug)` before migration checks is the narrow maintainable fix. Unclear for the newer UI symptom until maintainers decide whether that belongs in this repo or OpenClaw's installed-skill resolver.

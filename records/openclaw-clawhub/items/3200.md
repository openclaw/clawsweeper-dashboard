## Summary

Keep open: current documented behavior still prevents deletion of the active `latest` version, and the requested owner-authorized recovery path is not documented as available. The issue identifies both a concrete organization-membership authorization gap and a product-policy choice about rollback semantics. Likely related people: Patrick-Erichsen (recent skill/tag behavior) and vyctorbrzezowski (organization authorization groundwork).

## What This Changes

Add an organization-owner-authorized way to repoint a skill’s `latest` tag or safely recover from an accidental higher-version publish.

## System Context

ClawHub publishes immutable skill versions, assigns distribution tags such as `latest`, and exposes publisher operations through its CLI and authenticated backend. The selected `latest` version is the default version users install, so owner recovery must preserve publisher authorization and package-integrity safeguards.

## Architecture Diagram

## Best Possible Solution

Keep versions immutable and add a narrowly scoped, organization-aware owner recovery operation that explicitly repoints an existing public, scan-approved version to `latest`, records the rollback, and documents the install/update effect.

## Maintainer Decision

Question: Should organization publishers receive an explicit auditable rollback/repoint operation for `latest`, or should recovery remain limited to publishing a new higher version?

Rationale: Current deletion behavior intentionally protects the active distribution target, but the issue demonstrates that strict semver promotion leaves no self-service recovery when an organization publishes on the wrong higher version line. The choice affects package trust, installer expectations, and the permanent publisher API contract.

Likely owner: Patrick-Erichsen

Owner confidence: high

Options:

- **Add guarded latest rollback (recommended):** Authorize publisher owners through the existing organization-role checks to repoint `latest` only to an existing public, approved version, with explicit confirmation and an audit record.
- **Require a forward replacement:** Keep `latest` monotonic and require affected publishers to publish a new higher corrective version, preserving the current installer semantics.
- **Offer moderated recovery only:** Keep the CLI/API unchanged and handle exceptional tag corrections through staff moderation while product policy is refined.

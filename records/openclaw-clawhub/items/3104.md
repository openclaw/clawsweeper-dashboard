## Summary

Current main provides structured installation, dependency, compatibility, capability, and package-verification metadata, but not the proposed routing intents, task-verification hints, advisory risk contract, playbook hints, or candidate-ranking interface. This recent RFC therefore remains necessary and should stay open for a narrow product and trust-boundary decision.

## What This Changes

Requests optional skill and plugin metadata for routing, advisory risk, verification expectations, and playbook discovery through ClawHub APIs and CLI.

## Best Possible Solution

Define a versioned, optional advisory metadata subset in the existing skill and package manifest namespaces, expose raw validated fields through API and CLI, distinguish author claims from scanner-derived facts, and leave final ranking and runtime enforcement to consumers until evaluation data supports a stronger contract.

Kind: product_direction

Question: Should ClawHub standardize advisory routing and verification metadata for both skills and plugins, and should its first API expose only raw declarations or also produce ranked candidates?

Rationale: The choice fixes a public manifest/API contract and determines whether self-declared safety information remains descriptive or becomes an input to trusted routing behavior.

Likely owner: mahsumaktas

Owner reason: This is the strongest available history match for the existing structured skill metadata contract that the RFC would extend.

Owner confidence: medium

Options:

- **Start with raw advisory metadata (recommended):** Standardize a small versioned field set for intents, exclusions, and human-readable verification hints while deferring risk scoring and server-side ranking until provenance and evaluation rules are defined.
- **Adopt the full proposed contract:** Include routing, risk, verification, playbook, and ranked-candidate behavior in one broader initial schema with corresponding anti-gaming and trust requirements.
- **Keep routing external:** Continue exposing existing manifests and search APIs while requiring Harness-style systems to maintain their own routing and evaluation metadata.

## Solution Assessment

No, the full example contract is too broad for a first version; the narrower maintainable path is raw optional advisory metadata with explicit provenance, leaving ranking and enforcement outside ClawHub initially.

## Summary

Current ClawHub has structured installation, dependency, compatibility, and setup metadata, but it does not define the proposed routing, verification, risk, or playbook contract. This vision-aligned RFC should remain open for a narrow product and trust-boundary decision.

**Likely related people**
- `mahsumaktas` — high confidence; introduced the structured OpenClaw skill-metadata schema.
- `MunemHashmi` — medium confidence; recently extended parsing of setup and dependency metadata.
- `steipete` — medium confidence; likely product-direction owner based on `VISION.md`.

## What This Changes

Add optional skill and plugin manifest metadata for routing intent, advisory risk, verification expectations, and reusable playbook discovery through ClawHub APIs and CLI.

## Best Possible Solution

Define a versioned, optional manifest namespace that exposes raw advisory routing and verification declarations through existing package APIs and CLI, validates shape rather than truth, and defers server-side ranking or enforcement until an OpenClaw consumer and evaluation corpus prove the contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should ClawHub standardize advisory routing and verification metadata now, and should its first contract expose raw publisher declarations only or also compute candidate rankings?

Rationale: The code can support additional optional fields, but their stable semantics, trust status, abuse handling, and division of responsibility with OpenClaw routing cannot be inferred safely from existing behavior.

Likely owner: steipete

Owner reason: The decision is primarily about ClawHub's product boundary relative to harness and runtime responsibilities described in VISION.md.

Owner confidence: medium

Options:

- **Ship raw advisory metadata (recommended):** Add a small versioned namespace with shape validation, explicit untrusted semantics, API/CLI exposure, examples, and no ClawHub ranking or enforcement.
- **Wait for a consumer contract:** Defer schema work until the linked OpenClaw Harness proposal identifies a concrete consumer, essential fields, and executable evaluation fixtures.
- **Build registry ranking:** Let ClawHub validate metadata and return ranked candidates, accepting a larger long-term API, anti-abuse, quality-scoring, and compatibility commitment.

The general direction is reasonable, but adopting the entire proposed shape or adding ranking immediately is not yet the safest solution; a small versioned raw-metadata contract is the narrower maintainable first step.

## Risks / Open Questions

- Self-declared risk levels and verification claims could be mistaken for trusted enforcement unless the API explicitly marks them as untrusted advisory publisher metadata.
- ClawHub-computed rankings could create a second routing authority that drifts from OpenClaw's skill discovery and runtime policy.
- Keyword-based selection invites stuffing and inconsistent quality unless semantics, versioning, and evaluation fixtures are defined before ranking is introduced.
- Adding every proposed field at once would expand the public manifest contract before a concrete consumer has demonstrated which fields are stable and necessary.

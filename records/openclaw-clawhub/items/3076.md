## Summary

Keep open: current main preserves a deliberate boundary between client-declared source metadata and trusted server-resolved GitHub provenance, but it still lacks a clear retention, visibility, or deprecation contract for the CLI flags. Choosing the permanent behavior requires product and security ownership rather than an inferred implementation.

## What This Changes

Clarify whether CLI-declared skill source metadata should become server-verified provenance, remain separately visible as unverified attribution, or be explicitly deprecated as non-visible metadata.

## Best Possible Solution

Preserve trusted provenance exclusively for server-resolved sources, while storing and exposing CLI-declared repository data in a clearly labeled unverified-attribution field; document the distinction in CLI help and public docs, encode the trust invariant in a focused spec, and cover API/UI behavior with tests.

Question: Should ordinary skill-publish source flags be retained as clearly unverified public attribution, deprecated and rejected, or upgraded through a new server-verified GitHub publishing workflow?

Rationale: The choice defines both a public CLI/API contract and the security meaning of provenance, so implementation cannot safely infer the intended policy from existing code.

Likely owner: Patrick-Erichsen

Owner confidence: high

Options:

- **Expose Unverified Attribution (recommended):** Retain the declarations separately from trusted provenance and visibly label them as publisher-provided and unverified.
- **Add Verified Publishing:** Build server-side repository, commit, path, and content verification before CLI-published source can enter trusted provenance.
- **Deprecate Source Flags:** Reject or remove the ambiguous skill-publish flags and document GitHub import as the only trusted source path.

## Reproduction Assessment

Yes, at source and contract level: the report supplies a latest-release publish and verification transcript, and current documentation still limits trusted provenance to server-resolved GitHub imports. This review did not repeat the live publish operation.

## Solution Assessment

No implementation should start before maintainers choose the contract; after that decision, separately labeled unverified attribution is the narrowest way to preserve useful metadata without weakening verification.

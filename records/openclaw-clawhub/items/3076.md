## Summary

Keep open: current main intentionally limits trusted provenance to server-resolved GitHub sources, but ordinary CLI publish still accepts source metadata without a clear retention, visibility, or compatibility contract. The issue remains necessary because resolving that ambiguity requires an explicit product and security-boundary decision.

## What This Changes

Clarify whether source metadata declared during CLI skill publishing should become verified provenance, remain separately labeled attribution, or be explicitly unsupported.

## Best Possible Solution

Reserve trusted and publicly prominent provenance for server-resolved GitHub-backed sources, deprecate or reject ignored source flags on ordinary skill publishes, and document the contract in a focused security-sensitive spec plus CLI documentation.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should ordinary skill publishing deprecate the client-declared source flags in favor of the server-resolved GitHub-backed workflow, or retain them as a separate explicitly unverified attribution field?

Rationale: Both choices can preserve trusted provenance, but the permanent public data contract, compatibility policy, and acceptable risk of publisher-asserted repository links require maintainer intent.

Likely owner: Patrick-Erichsen

Owner reason: Their merged source-sync work provides the strongest available ownership signal for the adjacent trust architecture.

Owner confidence: high

Options:

- **Deprecate publish source flags (recommended):** Reject or phase out the flags for ordinary skill publishing and document server-resolved GitHub-backed sources as the supported public provenance path.
- **Expose unverified attribution:** Persist the declared repository, ref, commit, and path separately and label them as publisher-provided and unverified on every API and UI surface.
- **Verify uploaded contents:** Add repository authorization and content matching before promoting an ordinary CLI publish to trusted provenance.

## Reproduction Assessment

Yes, at source level. The report provides a concrete v0.23.1 publish and live API results, while current source and tests establish why client-declared metadata does not produce trusted provenance.

## Solution Assessment

No final implementation can be selected automatically because the public contract is unresolved. Deprecating the misleading flags in favor of the existing verified-source workflow is the narrowest security-preserving solution.

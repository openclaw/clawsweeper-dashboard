## Summary

Current main preserves the important security boundary—publisher-declared repository fields are not trusted provenance—but still accepts skill-publish source flags without a clear retention or visibility contract. This issue remains necessary because maintainers must choose whether those fields should be deprecated, exposed as explicitly unverified attribution, or trusted only through a server-verified publishing path.

## What This Changes

Clarify or preserve repository and commit metadata supplied by the CLI when publishing a skill.

## Best Possible Solution

Keep verification limited to server-resolved evidence, record the permanent trust model in `specs/`, and align CLI help, API schema, docs, and UI around either deprecated non-retained fields or separately labeled unverified attribution; trusted status should require repository authorization and content-to-commit verification.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What permanent contract should skill publishing use for CLI-declared GitHub repository and commit fields?

Rationale: The current behavior is intentionally safe but ambiguous, and choosing between deprecation, unverified attribution, and a verified publishing flow changes both the product surface and provenance trust boundary.

Likely owner: Patrick-Erichsen

Owner reason: Their merged GitHub-backed source work defines the nearest existing trusted path and the implementation boundaries this decision would extend or preserve.

Owner confidence: high

Options:

- **Separate unverified attribution (recommended):** Retain and expose the fields only as clearly unverified publisher attribution while reserving verification and trust decisions for server-resolved provenance.
- **Deprecate skill source flags:** Stop accepting the fields for skill publishing and document GitHub import or another trusted workflow as the only provenance path.
- **Build verified CLI provenance:** Add repository authorization and uploaded-file-to-commit verification before storing CLI publishes as trusted provenance.

## Reproduction Assessment

Yes for the current ambiguity: the supplied v0.23.1 command and API responses, together with the current CLI path and explicit trust-boundary test, provide a high-confidence source reproduction. There is no failing established visibility contract because the intended semantics remain undefined.

## Solution Assessment

No single implementation is yet the best solution because maintainers must first choose the trust contract. The narrowest safe direction is to preserve trusted verification as server-resolved and treat any client-declared link as separately and unmistakably unverified.

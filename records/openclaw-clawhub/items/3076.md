## Label Justifications

- `P2`: The ambiguity affects publisher expectations and registry trust semantics but does not currently make publishing or verification unavailable.
- `impact:security`: The issue concerns whether client-declared repository metadata may cross into trusted supply-chain provenance.
- `impact:ux-friction`: The CLI accepts source flags that appear to promise source association, yet the resulting public and verification surfaces provide no visible result or explanation.

## Summary

Current main intentionally separates publisher-declared source metadata from trusted GitHub provenance, but it still accepts the metadata without defining its visible or durable contract. The ambiguity therefore remains, and resolving it requires a maintainer choice about the product and security boundary rather than cleanup closure.

## What This Changes

Clarify whether GitHub source metadata supplied during CLI skill publishing should become verified provenance, remain explicitly untrusted attribution, or be documented as non-visible metadata.

## Best Possible Solution

Keep trusted provenance reserved for server-verified imports, preserve publisher-declared data only as clearly labeled unverified source attribution with no effect on trust decisions, document the distinction across CLI and API surfaces, and record the security invariant in a focused spec.

Options:

- **Add two-tier attribution (recommended):** Preserve and expose publisher-declared source as explicitly unverified metadata while reserving verification and trust indicators for server-resolved provenance.
- **Document or deprecate flags:** Keep direct skill publishes without visible source attribution and clearly document, warn on, or remove flags that currently imply a stronger result.
- **Build verified publishing:** Verify repository identity, commit, path, and uploaded content server-side before recording CLI-published source as trusted provenance.

## Solution Assessment

Unclear pending the maintainer decision; automatically trusting the supplied fields is not safe, while a two-tier model separating unverified attribution from server-verified provenance is the narrowest maintainable implementation direction.

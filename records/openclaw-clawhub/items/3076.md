## Summary

Keep open: current main deliberately separates publisher-declared source metadata from trusted server-resolved provenance, but it does not define whether the accepted CLI metadata should remain hidden, become visibly unverified attribution, or be deprecated. That unresolved trust and visibility contract requires product and security ownership.

## What This Changes

Clarify whether CLI skill-publish source flags should create trusted provenance, visible untrusted attribution, or intentionally non-visible metadata.

## Best Possible Solution

Adopt an explicit two-tier contract: retain server-resolved provenance as the only trusted signal, and either expose publisher-declared source as clearly unverified attribution or deprecate the skill-publish flags with direct CLI, API, and documentation guidance; record the chosen trust invariant in `specs/`.

Options:

- **Expose Unverified Attribution (recommended):** Persist and display the declared repository and commit under a clearly unverified field excluded from verification, trust badges, and install decisions.
- **Deprecate The Flags:** Warn and eventually reject these flags for hosted skill publishes, directing publishers to the server-managed GitHub-backed workflow for trusted provenance.
- **Verify Before Trust:** Add repository authorization and uploaded-content matching before storing a CLI claim as trusted provenance.

## Solution Assessment

No final implementation can be selected automatically because the intentional security boundary leaves a product choice between unverified attribution, deprecation, and new verification. A two-tier attribution model is the narrowest recommended direction because it preserves the trust boundary while making accepted metadata useful and explicit.

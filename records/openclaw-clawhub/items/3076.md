## Summary

Keep open: current main intentionally reserves trusted provenance for server-resolved GitHub sources, while ordinary skill publish still accepts client-declared source metadata without a defined retention, visibility, or deprecation contract. Choosing among unverified attribution, rejecting the flags, or adding verified CLI publishing requires an explicit product and security decision.

## What This Changes

Clarify or preserve CLI-declared GitHub source metadata for skill publishes without weakening trusted provenance.

## Best Possible Solution

Keep server-resolved provenance as the only trusted signal, define retained client-declared source as separately named and visibly unverified attribution, and document the distinction in CLI/API help plus a durable security-boundary spec.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: For ordinary CLI skill publish, should client-declared GitHub source be retained as explicitly unverified attribution, rejected as unsupported, or upgraded only through a new server-verified workflow?

Rationale: These directions create materially different trust, storage, API, UI, and compatibility contracts, so implementation cannot safely infer the intended boundary from existing code.

Likely owner: Patrick-Erichsen

Owner reason: The server-resolved GitHub source implementation is the strongest available ownership signal for this trust-contract decision.

Owner confidence: high

Options:

- **Separate unverified attribution (recommended):** Persist and expose the declared repository, ref, commit, and path under an explicitly unverified field while reserving verify provenance for server-resolved sources.
- **Reject unsupported source flags:** Stop accepting source flags for ordinary skill publish and direct publishers to the supported GitHub-backed import path.
- **Build verified CLI provenance:** Verify repository access and uploaded content against the claimed commit and path before storing trusted source provenance.

## Reproduction Assessment

Yes. The source path and API contract establish the mismatch: ordinary publish accepts source metadata while verification recognizes only server-resolved provenance, and the supplied live v0.23.1 response is consistent with that behavior.

## Solution Assessment

No final direction is established yet. Directly promoting client input to trusted provenance is unsafe; a separate unverified attribution contract is the narrowest maintainable behavior change, with rejecting the currently ambiguous flags as the safer no-feature alternative.

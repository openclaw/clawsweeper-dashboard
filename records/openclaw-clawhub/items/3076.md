## Label Justifications

- `P2`: This is a bounded but meaningful provenance-contract improvement without evidence of an active trust bypass or unusable publishing flow.
- `impact:security`: The issue directly concerns preventing publisher-declared repository claims from being represented as server-verified provenance.
- `impact:ux-friction`: The CLI accepts source flags successfully while publishers receive no clear indication that they will not create a repository link or trusted verification result.

## Summary

Keep open: current main intentionally separates publisher-declared source metadata from trusted GitHub provenance, but it still lacks a clear public contract for what the accepted CLI metadata means or whether it is retained and exposed. This unresolved trust and UX choice requires maintainer product/security direction.

## What This Changes

Clarify whether CLI-declared skill source metadata should become server-verified provenance, visible untrusted attribution, or explicitly non-visible metadata.

## Best Possible Solution

Preserve the rule that client claims never become trusted provenance; immediately define the flags as unverified or non-visible in CLI help and public docs, and use a separately authenticated GitHub import, App, or OIDC workflow if maintainers later choose to offer server-verified CLI provenance.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should skill-publish source flags be deprecated as non-visible client hints, stored and exposed as explicitly unverified attribution, or replaced by a server-verified GitHub publishing workflow?

Rationale: Each option changes the public trust model, compatibility contract, and UI/API semantics; source inspection can confirm the current boundary but cannot choose the permanent product contract.

Likely owner: Patrick-Erichsen

Owner reason: Their merged GitHub-backed source work defines the adjacent trusted-provenance architecture and its verification behavior.

Owner confidence: high

Options:

- **Clarify and deprecate hints (recommended):** Keep trusted provenance server-resolved, document the existing flags as non-visible client hints, warn on their use for skill publishing, and plan removal if no internal consumer requires them.
- **Expose unverified attribution:** Persist the client claim in a separately named and unmistakably unverified field that never influences verification, trust badges, or install decisions.
- **Build verified publishing:** Authenticate and resolve the repository, commit, path, and uploaded content server-side before storing trusted provenance.

## Reproduction Assessment

Yes, at source level: the CLI builds and submits source metadata, the API deliberately excludes it from trusted provenance, and verification only reads the trusted field. The supplied v0.23.1 commands also provide a concrete live reproduction, although no new live request was executed during this read-only review.

## Solution Assessment

No single implementation is established yet: blindly promoting client claims is unsafe, while silently accepting them preserves the ambiguity. The narrowest safe first step is explicit CLI and documentation semantics, with verified provenance designed separately if sponsored.

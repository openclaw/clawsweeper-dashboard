## Label Justifications

- `P2`: The ambiguity is reproducible and affects a public publishing contract, but current behavior preserves the security boundary and does not block publishing.
- `impact:security`: The issue concerns whether publisher-controlled repository claims may be represented as trusted provenance or must remain outside trust decisions.
- `impact:ux-friction`: The CLI accepts source-oriented flags successfully while giving publishers no clear indication that the resulting skill will expose no repository or provenance signal.

## Summary

Current main intentionally accepts publisher-declared source metadata without promoting it to trusted provenance, but the metadata's durable and visible contract remains undefined. Because exposing, discarding, or verifying these claims involves both spoofing risk and publisher UX, this issue remains necessary for a maintainer product/security decision.

## What This Changes

Clarify whether CLI-published skill source metadata should become server-verified provenance, remain separately labeled untrusted attribution, or be documented as non-visible.

## Best Possible Solution

Keep sourceProvenance restricted to server-resolved GitHub imports, define client claims separately as explicitly unverified attribution only if maintainers want them preserved, and document the distinction in CLI help, public docs, API naming, tests, and a focused security spec.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What contract should ClawHub enforce for source metadata supplied to `clawhub skill publish`: separately labeled unverified attribution, rejection/deprecation in favor of the trusted GitHub-import path, or server verification that can create sourceProvenance?

Rationale: Source inspection proves the current separation is deliberate, but the repository does not establish whether the accepted client claims should be retained, exposed, rejected, or verified; choosing among those outcomes changes the public trust model and compatibility contract.

Likely owner: Patrick-Erichsen

Owner reason: Their merged work introduced the trusted GitHub-backed source and verification architecture that this decision must preserve or extend.

Owner confidence: high

Options:

- **Separate Unverified Attribution (recommended):** Persist the claims in a clearly named unverified field, label them visibly, and prohibit them from affecting verify results or trusted Skill Card signals.
- **Trusted Import Only:** Deprecate or reject skill publish source flags and direct publishers to the existing server-managed GitHub-backed import workflow for provenance.
- **Verify CLI Claims:** Add server-side repository, commit, path, and artifact matching before storing the claims as trusted sourceProvenance.

## Reproduction Assessment

Yes at source level: the publish path accepts client source metadata, an explicit test keeps it out of trusted options, and verify reads only sourceProvenance. The supplied v0.23.1 API transcript also demonstrates the resulting unavailable provenance.

## Solution Assessment

Unclear until maintainers choose the public trust contract; blindly promoting the claims is unsafe. The narrowest maintainable direction is to preserve the trusted import boundary and either expose a separately named unverified field or deprecate the misleading publish flags.

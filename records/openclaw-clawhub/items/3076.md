## Summary

Keep open: the reported gap remains a real product and security-boundary decision. The documented CLI publish contract does not currently describe `--source-repo` or a visible attribution outcome, while the existing GitHub-backed path deliberately distinguishes server-resolved source from ordinary publish metadata; a maintainer must choose the permanent contract before a safe focused change can be scoped. citeturn1view1turn1view0turn2view0

## What This Changes

The issue asks ClawHub to clarify or define how CLI-supplied GitHub source fields relate to trusted, visible skill provenance.

## Best Possible Solution

Keep server-verified GitHub provenance exclusive to a server-resolved flow, then choose either a separately named unverified attribution field with clear UI/API treatment or explicit publish-help and documentation stating that these flags do not create public or trusted provenance.

- **Document non-visible metadata:** Keep the current trust boundary and update CLI help, API docs, and publish output to say these fields do not create visible or trusted provenance.
- **Design verified CLI publishing:** Add a server-side verification and file-match flow before CLI source data can become trusted provenance.

Unclear until maintainers select the trust contract. The safest default is to preserve the existing verified-provenance boundary and, if attribution is wanted, model it as a distinct unverified field rather than reusing trusted provenance.

## Label Justifications

- `P2`: Publishing succeeds and the trusted boundary remains intact, but the accepted flags create a real, bounded publisher-facing contract ambiguity.
- `impact:security`: The requested direction directly concerns whether client-declared repository information may influence trusted provenance and public trust signals.
- `impact:ux-friction`: Publishers can successfully supply source flags yet receive no clear warning that the metadata will not appear through verification or the public listing.

## Summary

Current main still accepts publisher-declared GitHub source metadata while the trusted verification and public skill surfaces do not expose it, so the reported ambiguity remains. The existing separation protects a meaningful security boundary, but maintainers must choose whether these flags should be documented or deprecated, exposed as explicitly unverified attribution, or backed by a new server-verification workflow.

## What This Changes

Clarify or preserve the source metadata supplied through CLI skill publishing without treating unverified publisher claims as trusted provenance.

## Best Possible Solution

Keep `verify` restricted to server-resolved provenance, immediately document the current limitation, and have maintainers choose either a clearly separate unverified-attribution contract or a fully verified GitHub publishing workflow before changing public trust signals.

## Summary

Keep open: current main deliberately prevents publisher-declared repository metadata from becoming trusted provenance, but the CLI still accepts that metadata without a documented retention or visibility contract. Choosing among verified provenance, explicitly unverified attribution, or deprecating the flags requires maintainer product and security direction.

## What This Changes

Clarify or preserve the repository, commit, ref, and path metadata supplied when publishing a skill through the CLI.

## Best Possible Solution

Preserve trusted provenance exclusively for server-resolved sources, introduce a clearly labeled unverified source-attribution field only if maintainers want publisher links retained, and document or deprecate the CLI flags according to that decision.

Rationale: The code intentionally protects the trusted provenance boundary, but only maintainers can decide whether unverified attribution belongs in the public product, whether CLI publishes should perform stronger server verification, or whether the currently ambiguous flags should be removed.

Likely owner: Patrick-Erichsen

Owner confidence: high

Options:

- **Separate Unverified Attribution (recommended):** Retain and expose the declared repository metadata under an unmistakably unverified field while keeping verification and trust decisions limited to server-resolved provenance.
- **Verify CLI Sources:** Add a server-controlled workflow that verifies repository access, commit identity, source path, and uploaded-content equivalence before recording trusted provenance.
- **Deprecate Source Flags:** Stop accepting or deprecate the flags and clearly document that ordinary CLI publishing cannot create GitHub-backed provenance.

Yes, there is a high-confidence source and API reproduction: the CLI submits the declared source, the server excludes it from trusted provenance, and the reported public verification request consequently returns unavailable provenance. ## Solution Assessment

Unclear until maintainers choose the trust contract. Directly promoting client data is unsafe; the narrowest maintainable default is separately labeled unverified attribution, with trusted provenance reserved for server verification.

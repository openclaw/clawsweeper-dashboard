## Summary

Keep open: the report identifies a real ambiguity at the boundary between client-declared source metadata and trusted, server-resolved provenance. The safe outcome requires an explicit security and product-contract decision before a focused documentation or implementation change can be scoped.

## What This Changes

Clarify whether CLI `--source-repo` and related publish flags create trusted provenance, untrusted visible attribution, or no public provenance signal.

## Best Possible Solution

Keep trusted provenance limited to server-resolved sources; first decide and document the CLI-publish contract, then separately design any visible untrusted attribution or server-verification flow with clear trust labeling.

Likely owner: Patrick-Erichsen

Options:

- **Document the current trust boundary (recommended):** Retain server-resolved provenance as the only trusted signal and make CLI help and publishing documentation state that source flags do not create verified or necessarily visible provenance.
- **Expose untrusted attribution separately:** Store and render publisher-declared source information under a clearly unverified field that never affects verify or trusted-signal UI.
- **Add verified CLI provenance:** Define a server-side ownership and content-verification protocol before allowing CLI source declarations to populate trusted provenance.

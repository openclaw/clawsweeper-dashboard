## Label Justifications

- `P2`: The ambiguity affects publishing ergonomics and provenance expectations but does not currently bypass the trusted verification boundary.
- `impact:security`: The issue concerns whether client-declared repository claims may be represented as trusted or untrusted supply-chain provenance.
- `impact:ux-friction`: Publishers can successfully provide source flags yet receive no warning or clear explanation that the metadata will not appear in verification or public skill surfaces.

## Summary

Current main deliberately keeps publisher-declared source metadata outside trusted GitHub provenance, while the CLI still accepts that metadata without defining a durable or visible user contract. The reported ambiguity remains and requires a maintainer product and security decision rather than cleanup closure.

## What This Changes

Clarify whether CLI-published skill source metadata should become server-verified provenance, remain explicitly untrusted attribution, or be documented as non-visible metadata.

## Best Possible Solution

Preserve the existing trusted-provenance boundary, immediately document the source flags as client-declared and non-verifying, and only expose them through a separately labeled unverified-attribution field if maintainers explicitly approve that security and UX contract; record the invariant in a focused provenance spec with regression coverage.

## Maintainer Decision

Required: true

Kind: product_direction

Question: What permanent contract should `clawhub skill publish --source-*` provide: documentation-only non-visible metadata, separately displayed unverified attribution, or a new server-verified publish workflow?

Rationale: Source inspection establishes the intentional security boundary but cannot determine whether accepted client metadata should remain hidden, become visibly untrusted, or trigger substantial server-side verification.

Likely owner: Patrick-Erichsen

Owner reason: The merged GitHub-backed source work provides the closest concrete ownership and architectural context for this trust-contract decision.

Owner confidence: high

Options:

- **Document Current Boundary (recommended):** Keep client source claims outside public and trusted provenance, clarify this in CLI help and docs, and consider deprecating flags that have no supported visible effect.
- **Expose Unverified Attribution:** Store and display the publisher claim under an unmistakably unverified field that never affects verify results, skill-card trust, or installation decisions.
- **Verify CLI Sources:** Add server-side repository, commit, path, ownership, and uploaded-content validation before creating trusted sourceProvenance.

Yes at the source level: current main accepts and forwards the declared source while intentionally withholding it from trusted sourceProvenance, matching the reporter's v0.23.1 API transcript. A fresh live publish is unnecessary to establish that contract mismatch.

## Solution Assessment

Directly promoting client claims to trusted provenance would be unsafe; the narrowest safe immediate solution is explicit documentation and CLI messaging while maintainers decide whether a separate attribution field or verified workflow is warranted.

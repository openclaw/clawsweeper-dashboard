## Summary

Current main intentionally keeps publisher-declared source metadata outside trusted GitHub provenance, but it still accepts that metadata without defining its visible or durable contract. The ambiguity remains and requires a maintainer product/security decision rather than cleanup closure.

## What This Changes

Clarify whether CLI-published skill source metadata becomes verified provenance, separately visible untrusted attribution, or explicitly non-visible metadata.

## Best Possible Solution

Adopt an explicit two-tier contract: reserve trusted provenance for server-resolved or attested GitHub workflows, expose client declarations only as clearly labeled unverified attribution, and record the trust invariant in specs plus user-facing CLI/API documentation.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What permanent contract should `clawhub skill publish --source-repo --source-commit` provide: server-verified provenance, clearly labeled unverified attribution, or no accepted source metadata for hosted skill uploads?

Rationale: The choice changes public API and UI semantics, storage expectations, and the supply-chain trust boundary; current code establishes what must not be trusted but not what product behavior maintainers intend.

Likely owner: Patrick-Erichsen

Owner reason: Their GitHub-backed source work established the verified provenance model that this client-declared path must safely complement or avoid.

Owner confidence: high

Options:

- **Expose Unverified Attribution (recommended):** Persist and return the declared source under a separately named, prominently unverified field while keeping verification and trust decisions limited to server-resolved provenance.
- **Build Verified Publishing:** Verify repository identity and uploaded bytes against the claimed commit through a server import or attested GitHub Actions workflow before storing trusted provenance.
- **Remove Ambiguous Flags:** Deprecate or reject skill source flags and document that hosted CLI uploads cannot create GitHub provenance.

## Reproduction Assessment

Yes at source level: current main constructs and accepts client source metadata while trusted verification uses the separate server-resolved GitHub path. The supplied v0.23.1 publish and verify transcript confirms the observable behavior.

## Solution Assessment

No final implementation is safe until maintainers choose the trust contract. A separate unverified-attribution field is the narrowest option that preserves useful information without weakening trusted provenance.

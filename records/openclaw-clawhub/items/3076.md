## Summary

Keep open: current main still accepts CLI-declared skill source metadata without documenting a visible attribution outcome, while provenance and trust remain deliberately distinct product surfaces. The requested contract therefore needs an explicit maintainer security and product-direction decision before implementation can be scoped safely.

## What This Changes

The issue asks ClawHub to clarify or define how CLI-declared GitHub source fields for skill publishing relate to visible attribution and trusted provenance.

## Best Possible Solution

Keep trusted provenance limited to independently resolved or authenticated GitHub flows, then either expose clearly labeled unverified attribution for skill publishes or document that those fields have no public provenance effect.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: What permanent contract should `clawhub skill publish --source-repo --source-commit --source-ref --source-path` have: no public effect beyond upload metadata, separately labeled unverified attribution, or a new server-verified provenance flow?

Rationale: The choice determines whether a publisher-supplied repository claim can appear publicly, what verification semantics users infer, and whether server-side repository/content validation or an authenticated publishing mechanism is required.

Likely owner: Patrick-Erichsen

Owner reason: The merged GitHub-backed source workflow is the closest existing implementation and trust-model precedent.

Owner confidence: high

Options:

- **Separate unverified attribution from verification (recommended):** Persist and display publisher-declared repository metadata under an explicitly unverified label while preserving existing server-resolved provenance as the only trusted verification signal.
- **Document non-visible metadata only:** Keep current skill publish behavior and update CLI help, publishing docs, and API wording to say source flags do not create public attribution or trusted provenance.
- **Add a verified skill-publishing flow:** Define an authenticated or server-validated GitHub publishing path that proves repository, commit, path, and uploaded content before reporting trusted provenance.

## Reproduction Assessment

Yes, at source level: current multipart parsing accepts and forwards `payload.source`, while the documented skill-publish contract does not specify a visible attribution or verification result. The report also supplies a concrete successful-publish and verify-endpoint observation.

## Solution Assessment

Unclear until maintainers choose the trust contract. Separately labeled unverified attribution is the narrowest direction that preserves publisher context without weakening server-resolved provenance semantics.

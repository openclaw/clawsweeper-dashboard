## Label Justifications

- `impact:security`: The issue concerns the boundary between user-declared repository metadata and server-verified supply-chain provenance.
- `impact:ux-friction`: The CLI accepts source flags without a documented or visible post-publication meaning, creating avoidable publisher confusion.

## Summary

Keep open: current main intentionally excludes publisher-declared source metadata from trusted provenance, but it still does not define or document a clear public contract for the accepted CLI metadata. The unresolved visibility and trust semantics require maintainer product/security direction.

## What This Changes

Clarify whether CLI-declared skill source metadata should become verified provenance, remain separately visible as untrusted attribution, or be documented as non-visible metadata.

## Best Possible Solution

Keep verified provenance limited to server-resolved sources; if publisher attribution is retained, expose it under a distinctly named, visibly unverified field and document the invariant in `specs/` plus the CLI/API behavior in `docs/`.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should skill-publish source flags create separately visible unverified publisher attribution, remain non-visible with explicit documentation, or be replaced by a server-verification workflow?

Rationale: This defines a public CLI/API contract and determines whether user-controlled metadata appears near trusted supply-chain signals, so source inspection cannot safely infer the permanent policy.

Likely owner: Patrick-Erichsen

Owner reason: The merged GitHub-backed source implementation is the strongest direct ownership signal for this provenance architecture.

Owner confidence: high

Options:

- **Separate unverified attribution (recommended):** Store and expose publisher-declared source under a distinct field and UI label that cannot be confused with verified provenance.
- **Document non-visible metadata:** Preserve current behavior and explicitly state that these flags do not create provenance, a GitHub-backed skill, or a public source link.
- **Build verified CLI publishing:** Verify repository access, commit and path identity, and uploaded-content equivalence before setting trusted provenance.

## Reproduction Assessment

Yes at the source level: skill publish submits source metadata, while the trusted options and verify path intentionally rely only on server-resolved provenance. The documented CLI contract omits this distinction, matching the reported behavior.

## Solution Assessment

Unclear until maintainers choose the permanent contract; separately labeled unverified attribution is the narrowest maintainable direction because it improves clarity without weakening verification.

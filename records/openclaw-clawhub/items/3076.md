## Summary

Keep open: current evidence supports an intentional distinction between client-declared publish metadata and trusted, server-resolved GitHub provenance, but the resulting CLI/API contract remains ambiguous for publishers. This needs an explicit maintainer security and product-direction decision before a focused implementation or documentation change can be selected.

## What This Changes

The issue asks ClawHub to clarify or support how CLI-declared GitHub source metadata is preserved and exposed without treating unverified client input as trusted provenance.

## Best Possible Solution

Choose and document one durable contract: retain invisible metadata, expose it as clearly labeled unverified attribution, or add a separately designed server-verification flow that writes trusted provenance only after verification succeeds.

- **Design verified CLI provenance:** Add a dedicated server verification protocol for repository access and claimed commit/path-to-upload correspondence before storing trusted provenance.

## Summary

Keep open: current main has useful temporal-stat foundations, but it still does not provide the RFC’s consistent period contract across all three browse surfaces. This member-authored RFC also requires explicit product decisions before implementation.

## What This Changes

Add consistent Weekly, Monthly, and All time popularity browsing for publishers, skills, and plugins.

## Best Possible Solution

Approve and document one trailing-window ranking contract—including scoring, publisher attribution, snapshot pagination, retention, and empty states—then implement the remaining rollups, APIs, and matched browse tabs in staged PRs.

Required: true

Question: Should ClawHub adopt one shared trailing-window popularity contract for publishers, skills, and plugins, and what scoring and publisher-ownership attribution rules should that contract use?

Rationale: Current code supplies only partial statistics infrastructure; scoring, ownership transfer, backfill, low-activity behavior, and rollout semantics cannot be safely inferred from existing behavior.

Likely owner: Ivan Katanic

Owner reason: The strongest available ownership signal is the prior daily-stat and leaderboard schema work central to the proposed contract.

Owner confidence: medium

Options:

- **Adopt Shared Contract (recommended):** Define one Weekly and Monthly contract across all three surfaces, record it in specs, and implement the missing backend and UI layers in stages.
- **Limit Initial Scope:** Expose periods only on surfaces with complete statistics and explicitly label any narrower entity-specific metric.
- **Defer Period Tabs:** Retain the existing all-time browse and seven-day skill-trending paths without adding the proposed cross-surface controls.

## Solution Assessment

Yes at the architectural level: deciding shared semantics before adding UI tabs is safer and more maintainable than exposing incomplete or inconsistent period metrics. The exact scoring, attribution, and rollout rules still require maintainer approval.

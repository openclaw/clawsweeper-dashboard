## Summary

Keep open. Current main and v0.23.1 still require authors to publish before using the supported scan workflow; existing local validation, repository-only scanning, and the newly linked external scanner each solve only part of the requested author experience.

## What This Changes

Requests a supported local CLI that validates plugin manifests, SKILL metadata, and security findings before publishing.

## Best Possible Solution

Adopt a coverage-aware workflow that composes ClawHub package validation with plugin-capable static scanning, clearly labels hosted-only checks, and provides stable redacted human and JSON output with documented exit semantics.

Rationale: The code proves several viable partial implementations, but choosing the authoritative public boundary requires maintainer intent about privacy, credentials, hosted parity, versioning, and long-term scanner compatibility.

Owner confidence: high

Options:

- **Adopt with ClawHub adapter (recommended):** Compose ClawScan static findings with ClawHub package and manifest validation, explicitly marking model-backed or registry-only checks as hosted-only.
- **Build ClawHub-native scanner:** Maintain the full pre-publish scanner and all compatibility guarantees directly in the ClawHub CLI and backend.
- **Keep separate tools:** Document `package validate`, repository tooling, and external ClawScan as independent surfaces without promising one authoritative pre-publish result.

## Reproduction Assessment

Yes, at source level. Current main and v0.23.1 explicitly reject local scan inputs, while `package validate`, the repository-only dry-run, and the external ClawScan candidate each cover only subsets of the requested workflow.

## Solution Assessment

No, the broad proposal should not initially promise full hosted parity. The narrowest maintainable solution is a composed, coverage-aware command that reuses existing validators and scanner components while clearly identifying hosted-only analysis.

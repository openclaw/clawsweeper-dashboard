## Summary

Keep open. Current main substantially improves pre-publish feedback through `clawhub package validate`, but the supported ClawScan command still explicitly rejects local artifacts, leaving the central local security-scanning request unimplemented.

## What This Changes

Requests a supported local CLI or package that validates plugin metadata and runs security-oriented pre-publish checks with structured CI output.

## Best Possible Solution

Retain `clawhub package validate` as the deterministic offline preflight, then extend the existing scan-job architecture with authenticated, ephemeral plugin artifact scans whose output labels best-effort security findings and states that hosted publish enforcement remains authoritative.

## Maintainer Decision

Kind: security_boundary

Question: Should the public scan service accept ephemeral local plugin artifacts, and if it does, should results be documented as best-effort preflight guidance or guaranteed to match hosted publish-time ClawScan decisions?

Rationale: Current main intentionally separates public deterministic Plugin Inspector validation from hosted security scanning, and choosing artifact handling plus parity semantics changes a durable security and CLI contract.

Likely owner: Patrick-Erichsen

Owner reason: Patrick has the strongest recent history across all three relevant surfaces: public scan UX, local dry-run scanning, and plugin validation.

Owner confidence: high

Options:

- **Best-effort authenticated preflight (recommended):** Accept bounded ephemeral plugin uploads, expose structured findings, and document hosted publish-time enforcement as authoritative.
- **Exact hosted parity:** Expose the complete hosted scanner locally and accept compatibility obligations for equivalent local and publish-time decisions.
- **Keep validation-only boundary:** Continue offering offline Plugin Inspector checks while limiting security scans to published artifacts and trusted repository tooling.

## Reproduction Assessment

Yes, at source level. Passing a local folder to `clawhub scan` deterministically reaches `rejectLocalScan()`, while `clawhub package validate` demonstrates the narrower local validation capability that already exists.

## Solution Assessment

No, not as one undifferentiated linter promising all hosted findings. The maintainable direction is deterministic offline Plugin Inspector validation plus a separately defined authenticated, ephemeral, best-effort security scan contract.

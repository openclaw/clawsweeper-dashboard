## Summary

Keep open: the recurring Scrapling visibility failure is not proven fixed on current main. ClawHub intentionally hides releases under moderation, but the public listing still does not expose usable skill content, prior reports show the same publisher repeatedly needing intervention, and the broader policy for scanner-triggered visibility remains under active discussion in https://github.com/openclaw/clawhub/issues/2321. ([clawhub.ai](https://clawhub.ai/d4vinci/scrapling-official))

## What This Changes

Prevent legitimate Scrapling updates from repeatedly hiding the skill and requiring manual maintainer restoration.

## Best Possible Solution

Preserve per-version security scanning, but add an owner-facing Review/Fix flow that shows redacted reason codes and file locations, permits rescan or appeal without support intervention, and supports a narrowly audited exception for confirmed recurring false positives without trusting changed payloads automatically.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should confirmed recurring Scrapling false positives receive a narrowly scoped clearance mechanism across updates, or must every new version remain hidden until an independent scan or human review clears it?

Rationale: The decision trades publisher continuity against the requirement that changed release contents receive fresh security evaluation; source inspection cannot safely choose that trust policy.

Likely owner: Patrick-Erichsen

Owner reason: They authored the active RFC covering hidden listings, human review, and scanner-based enforcement categories.

Owner confidence: medium

Options:

- **Keep per-version review (recommended):** Continue scanning every release, but add clear owner diagnostics, an in-product Fix/Appeal action, and timely review escalation for repeated false positives.
- **Carry forward clearance:** Persist approval for this publisher or skill lineage across updates, accepting the risk that changed files could inherit trust before review.
- **Retain manual unlocks:** Keep the current support-mediated process, preserving the strictest boundary but continuing the recurring release blocker.

## Reproduction Assessment

No, not with high confidence. Prior review evidence and the current empty public listing support the reported impact, but reproducing the update-triggered transition requires the private production moderation and scanner state for the latest Scrapling version.

## Solution Assessment

No, repeatedly un-hiding each version manually is not the best solution. The maintainable path is per-version scanning plus transparent self-service diagnostics and a narrowly defined false-positive recovery policy.

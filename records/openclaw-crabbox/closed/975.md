## Label Justifications

- `P0`: The issue concerns a security-boundary failure that can lead Crabbox cleanup to perform destructive Azure provider deletion without local ownership proof.
- `impact:security`: The report is about destructive provider authorization and ownership proof for Azure cleanup.
- `impact:data-loss`: Azure deletion includes the VM and disk path, so a wrong cleanup authorization can remove data-bearing resources.

## Summary

Keep open: current main still lets Azure cleanup delete an expired canonical-tagged VM after provider-side and live VM checks without an exact local lease claim, while the repository's lifecycle safety policy requires destructive ownership to be bound to provider, resource, and claim.

## What This Changes

The issue reports that Azure direct-provider cleanup can delete canonical-tagged expired VMs using provider-side metadata and live VM revalidation without an exact local lease claim.

## Best Possible Solution

Add an Azure exact-claim guard equivalent to AWS before any Azure cleanup deletion, binding lease ID, provider, Azure scope, cloud ID, slug, and immutable VM identity while retaining live VM/resource revalidation and skip diagnostics.

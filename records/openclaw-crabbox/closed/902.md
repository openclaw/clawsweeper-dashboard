## Summary

Keep open. Current main still checks GitHub org/team membership only during OAuth token issuance, while later `cbxu_` requests authenticate by token signature/expiry and reuse the old owner/org identity for coordinator authorization.

## What This Changes

The issue asks Crabbox to revoke or revalidate signed GitHub user-token access when a user loses required GitHub org or team membership instead of waiting for token expiry.

## Best Possible Solution

Define supported GitHub user-token revocation semantics, then implement membership revalidation or revocation state with bounded caching and focused Worker coverage for lease, run, bridge, and artifact access.

## Reproduction Assessment

Yes, by source inspection: issue a token after the OAuth membership check, remove the user from the required GitHub org/team, then present the same `cbxu_` token; the request path verifies only the signed token payload and expiry. I did not run a live GitHub OAuth revocation scenario in this read-only review.

## Solution Assessment

Unclear until maintainers choose the revocation policy. The maintainable direction is to enforce current allowed-org/team eligibility through cached membership or revocation state, rather than adding scattered route-specific checks.

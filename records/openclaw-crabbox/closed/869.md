## Summary

Keep open: the reported FastAPI Cloud bearer-token redirect gap is still present on current main, matches the repository’s documented credential-destination rule, and no related open or merged fix currently owns it.

## What This Changes

FastAPI Cloud provider requests should reject cross-origin redirects before replaying `Authorization: Bearer` credentials, matching adjacent provider clients.

## Best Possible Solution

Add a FastAPI Cloud same-origin redirect wrapper using the established provider pattern, preserve existing runtime `CheckRedirect`, and add cross-origin rejection plus same-origin redirect regression tests.

## Reproduction Assessment

Yes, from source inspection there is a high-confidence httptest-style reproduction path: configure the FastAPI Cloud client with a token, have the accepted API origin redirect to a sibling/subdomain destination, and observe Go’s default redirect handling on the bearer request. I did not execute that harness in this read-only cleanup review.

## Solution Assessment

Yes, the narrowest maintainable fix is to wrap the FastAPI Cloud HTTP client with the same origin-preserving redirect control already used by adjacent provider clients, then cover rejected cross-origin and allowed same-origin redirects.

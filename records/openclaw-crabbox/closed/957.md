## Summary

Keep open: current main fixed the closely related GitHub user-token bridge revocation path, but the non-admin shared-token/bearer bridge path still lacks revocable token provenance and still passes the active non-admin revalidation branch.

## What This Changes

The issue reports that active WebVNC, Code viewer, and egress bridge sessions created with `CRABBOX_SHARED_TOKEN` can keep forwarding after that shared token is rotated.

## Best Possible Solution

Bind non-admin bearer bridge grants to non-secret shared-token provenance or a deployment grant version, revalidate that binding in `activeBridgeGrantIsCurrent`, close WebVNC/Code/egress sessions on mismatch, and add focused Worker regression coverage for shared-token rotation.

Question: Should Crabbox treat `CRABBOX_SHARED_TOKEN` rotation as an immediate revocation event for already-open non-admin bearer WebVNC, Code viewer, and egress bridge sessions?

Rationale: The source shows the stale-session gap, but enforcing immediate failure changes live bridge semantics and requires deciding what non-secret shared-token provenance should be stored in bridge/session state.

Likely owner: steipete

Owner reason: steipete has the strongest current-main history on Worker bridge revocation, GitHub grant binding, and adjacent auth/security fixes.

Owner confidence: high

Options:

- **Enforce shared-token bridge revocation (recommended):** Add revocable shared-token provenance to non-admin bearer bridge grants and fail closed when the current configured token or grant version no longer matches.
- **Document bounded live-session survival:** Keep existing live shared-token bridges until disconnect or lease end and document that rotation only blocks new shared-token requests.
- **Fold into a broader bridge-auth design:** Hold this issue for a unified policy across bearer, GitHub, admin, control, restored, and ticketed bridge authorization.

## Reproduction Assessment

Yes. Source inspection shows a shared-token request becomes non-admin bearer auth, the bridge grant stores no revocable shared-token binding, and the active bridge guard returns true for non-admin non-GitHub attachments.

## Solution Assessment

Yes, with maintainer confirmation of the security boundary. The narrow maintainable fix is to extend the existing active bridge revalidation model with non-secret shared-token provenance rather than add per-route timeouts or a broad bridge rewrite.

## Label Justifications

- `P0`: The reported path can delete Azure VMs and disks without the documented current ownership proof when orphan-sweep delete mode is enabled.
- `impact:security`: The issue concerns Crabbox's destructive provider-action boundary and whether Azure resources are strongly identified as Crabbox-owned before deletion.
- `impact:data-loss`: The concrete failure mode can delete a same-name Azure VM and its OS disk or companion resources.

## Summary

Keep open: current main still has the Azure orphan-sweep delete path calling raw Azure deletion from a retained lease/name-region match, while the stronger owned-delete proof path exists but is not used by the sweep.

## What This Changes

The issue requests that Azure orphan-sweep delete mode require the same current ownership proof used by Azure owned cleanup before deleting VMs and companion resources.

## Best Possible Solution

Route Azure orphan-sweep deletion through deleteOwnedServer or an equivalent fail-closed proof that revalidates current labels, provider scope, companion resources, and disk identity before any Azure DELETE call.

## Summary

This should stay open: current main still accepts explicit Sprites API URL overrides without URL-shape or HTTPS validation, then uses that base for bearer-authenticated API calls. The earlier source-binding fix for repository-controlled destinations only partially overlaps and intentionally preserved explicit operator-approved endpoint overrides.

## What This Changes

The issue requests fail-closed validation for trusted Sprites API URL overrides before bearer-authenticated Sprites requests are created.

## Best Possible Solution

Add Sprites API URL validation before client creation, matching neighboring credentialed providers: absolute URL, HTTPS except loopback, no userinfo/query/fragment/opaque/ForceQuery, canonicalized host/default ports, focused regression tests, and preferably same-origin redirect protection.

## Reproduction Assessment

Yes, there is a high-confidence source-level reproduction path: set an explicit Sprites API URL override and the current client will concatenate it into API requests before adding the bearer token. I did not run a live network reproduction in this read-only review.

## Solution Assessment

Yes, the requested validation is the narrow maintainable fix because it follows existing E2B/OpenComputer/Freestyle URL-safety patterns without adding new config surface. The repair should complement, not replace, the repository credential-provenance guard.

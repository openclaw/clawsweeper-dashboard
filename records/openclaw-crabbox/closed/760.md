## Summary

Keep this issue open: current main still has the Go CLI direct-provider browser bootstrap importing Google's APT key into global trust without fingerprint verification, even though the sibling Worker and developer-tools paths were hardened by https://github.com/openclaw/crabbox/pull/755.

## What This Changes

The issue requests pinning and scoping Google's Chrome APT signing key in the Go CLI direct-provider cloud-init browser bootstrap.

## Best Possible Solution

Mirror the already-merged Worker/developer-tools pinned fingerprint and scoped `signed-by` keyring flow into `internal/cli/bootstrap.go`, then update `internal/cli/bootstrap_test.go` to assert the secure path and absence of `/etc/apt/trusted.gpg.d/google.asc`.

## Reproduction Assessment

Yes. Source inspection shows `--browser` reaches `cfg.Browser`, and direct cloud providers embed the Go `cloudInit` body that currently imports Google's APT key without pinning or repository scoping.

## Solution Assessment

Yes. The narrow maintainable fix is to reuse the pinned Google primary fingerprint, isolated GnuPG import/export, scoped keyring, and Chromium fallback pattern already present in the Worker and developer-tools implementations.

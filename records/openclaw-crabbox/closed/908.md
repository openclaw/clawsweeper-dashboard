## Label Justifications

- `P2`: This is a source-reproducible security bug in artifact credential and data destination handling with limited blast radius and redirect preconditions.
- `impact:security`: The issue concerns credential-bearing artifact URLs and upload grants being replayed or exposed to a redirect-selected cross-origin destination.

## Summary

Keep open: current main still sends artifact manifest reads, artifact downloads, and broker upload grants through Go's default redirect policy, while Crabbox already documents and implements same-origin redirect handling for other credential-bearing paths. The open related report at https://github.com/openclaw/crabbox/issues/900 covers the upload subset, but this issue adds broader artifact-transfer evidence that maintainers should consolidate deliberately.

## What This Changes

The issue requests applying Crabbox's same-origin credential redirect rule to artifact manifest fetches, artifact downloads, and broker upload grants.

## Best Possible Solution

Introduce a provider-neutral artifact transfer HTTP helper that rejects cross-origin redirects, or disables redirects if maintainers choose that stricter contract, then use it for manifest fetches, file downloads, and broker uploads with focused regression tests for blocked cross-origin and allowed same-origin behavior.

## Reproduction Assessment

Yes. Source inspection on current main shows the three artifact HTTP paths use http.DefaultClient without CheckRedirect while the Worker emits query-signed artifact URLs; I did not run a live redirecting S3/R2 endpoint in this read-only review.

## Solution Assessment

Yes on direction, with one maintainer decision left. A shared artifact transfer redirect policy is the narrow maintainable fix, but maintainers should choose same-origin redirects versus no redirects before implementation.

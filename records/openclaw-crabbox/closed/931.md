## Label Justifications

- `P0`: The issue reports a documented security-boundary failure that can cause destructive Azure VM, network, or disk deletion when deferred cleanup state points at a resource Crabbox cannot prove it owns.
- `impact:security`: The affected behavior is the ownership authorization check immediately before Crabbox uses Azure provider credentials for destructive API calls.
- `impact:data-loss`: Deleting the VM and derived OS disk can destroy machine-local workload state or availability outside the intended failed lease.

## Summary

Keep open: current main still stores Azure deferred cleanup by name/location/resource group only, and the alarm path calls `deleteServer(record.name)` without lease binding or provider-side ownership verification, matching the reported security boundary gap.

## What This Changes

The issue asks to harden Azure VM-create timeout deferred cleanup so alarm retries verify Crabbox ownership before deleting resources derived from a stored VM name.

## Best Possible Solution

Persist Azure deferred cleanup ownership context, read back the live Azure VM or companion metadata before deletion, require matching Crabbox lease/provider ownership, and retain diagnostics without deleting on mismatch.

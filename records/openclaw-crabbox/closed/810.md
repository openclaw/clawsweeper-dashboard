## Label Justifications

- `P2`: This is a source-reproducible provider credential disclosure risk with Morph/Railway-specific redirect preconditions and no evidence of active exploitation.
- `impact:security`: The issue concerns Crabbox replaying trusted provider bearer credentials to a redirect-selected destination outside its documented boundary.
- `impact:auth-provider`: The affected secrets are Morph and Railway provider API credentials used to authenticate provider API requests.

## Summary

Keep open: current main still leaves Morph and Railway bearer-token requests on the raw runtime/default Go HTTP redirect policy, while docs and sibling provider clients show Crabbox's stricter same scheme/hostname/effective-port redirect boundary.

## What This Changes

The issue requests Morph and Railway provider HTTP clients to reject redirect destinations outside the configured provider origin before bearer credentials can be replayed.

## Best Possible Solution

Add provider-local secure HTTP client wrappers for Morph and Railway that reject scheme, hostname, or effective-port redirect drift before invoking any caller redirect hook, then cover same-origin allow and credential-bearing redirect refusal in focused tests.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: Morph and Railway set Authorization headers and send requests through unguarded Go HTTP clients, while Go's default redirect handling is broader than Crabbox's documented same-origin provider rule.

## Solution Assessment

Yes. The narrow maintainable repair is to mirror existing provider redirect wrappers rather than changing provider configuration semantics or adding a new policy knob.

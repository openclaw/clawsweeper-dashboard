## Label Justifications

- `P2`: This is a source-reproducible provider credential disclosure risk with Morph-specific redirect preconditions and no evidence of active exploitation.
- `impact:security`: The issue concerns whether Crabbox can replay a configured provider bearer token to a lower-trust redirect destination.
- `impact:auth-provider`: The affected value is the Morph API credential used to authenticate provider API requests.

## Summary

Keep open: current main still builds the Morph client with the raw runtime/default HTTP client and sends the Morph bearer token through that client, while docs and sibling providers establish the stricter same-destination redirect rule.

## What This Changes

The issue requests that the Morph provider stop replaying its bearer token across redirects that do not preserve the configured API scheme, host, and effective port.

## Best Possible Solution

Add a Morph-specific secure redirect wrapper mirroring RunPod/Vast, preserve caller CheckRedirect/default redirect limits, and add focused tests proving Authorization is not forwarded to lower-trust redirect targets.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: Morph sends Authorization through an unguarded http.Client, and Go forwards sensitive headers to exact-domain or subdomain redirects unless Crabbox installs a stricter CheckRedirect policy.

## Solution Assessment

Yes. The requested fix is the narrow maintainable path because it mirrors already-merged provider redirect guards without changing Morph configuration or provider semantics.

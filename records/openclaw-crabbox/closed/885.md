## Label Justifications

- `P2`: This is a bounded provider diagnostic credential-exposure issue with local/operator prerequisites and no core runtime outage.
- `impact:security`: The issue concerns possible exposure of configured Proxmox provider token material in Crabbox-generated diagnostics.

## Summary

Keep open. Current main still sends the Proxmox `PVEAPIToken` header and returns summarized non-2xx response bodies through `ProxmoxError` without applying the existing Proxmox redactor; nearby closed items cover config output or live-smoke artifacts, not this normal provider HTTP error path.

## What This Changes

The issue asks Crabbox to redact Proxmox API token material from normal Proxmox HTTP error bodies, not only doctor and live-proof diagnostics.

## Best Possible Solution

Redact Proxmox HTTP error bodies before constructing `ProxmoxError`, covering token ID, token secret, full `PVEAPIToken=...`, and generic authorization fields, with a mock-server regression test through a normal non-doctor Proxmox operation.

## Reproduction Assessment

Yes, at source level: current main sets the `PVEAPIToken` authorization header and returns the summarized non-2xx response body directly in `ProxmoxError`. I did not execute a mock-server reproduction, so this is source-reproducible rather than tool-reproduced.

## Solution Assessment

Yes, the narrow maintainable fix is to enforce Proxmox credential redaction inside the client error path before errors reach callers. A helper should avoid import cycles with `internal/providers/shared` or move reusable redaction into a neutral package if maintainers want one shared implementation.

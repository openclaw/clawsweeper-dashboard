## Label Justifications

- `P0`: The issue reports a security boundary failure that can drive destructive deletion of provider resources Crabbox cannot strongly identify as its own.
- `impact:security`: The issue concerns Crabbox trusting provider metadata before destructive provider actions.
- `impact:data-loss`: The reported failure mode can delete another owner's VM or instance in a shared provider account.

## Summary

Keep open: current main still has the reported direct-provider ownership gap for DigitalOcean, Linode, Vultr, and Scaleway, and no merged related item covers those remaining delete paths.

## What This Changes

The issue reports that direct-provider cleanup can trust provider labels with non-canonical lease IDs before destructive deletes.

## Best Possible Solution

Require canonical lease IDs before the affected providers list, resolve, recover cleanup claims for, or delete resources, with regression tests for non-canonical labels on each provider.

## Reproduction Assessment

Yes. Source inspection on current main shows the affected ownership predicates accept non-empty, non-canonical lease labels and feed cleanup paths that can call provider delete APIs.

## Solution Assessment

Yes. Canonical lease ID enforcement at the provider ownership and destructive cleanup boundaries matches the existing AWS/Azure pattern and is narrower than adding a new config or policy mode.

## Label Justifications

- `P1`: This is a high-confidence security boundary issue in a destructive provider lifecycle path, but it is scoped to the RunPod provider and a configured RunPod account.
- `impact:security`: The report is about Crabbox performing destructive provider actions against resources it cannot strongly identify as its own.
- `impact:other`: The concrete user impact is provider-resource integrity and availability loss for a RunPod pod reachable by the configured API key.

## Summary

Keep open: current main still lets the RunPod release path resolve a caller-supplied raw pod ID, synthesize a Crabbox-looking lease identity for non-Crabbox pod names, and terminate the resulting CloudID without a final ownership check.

## What This Changes

The issue asks Crabbox to make RunPod destructive stop/release fail closed unless the target has an exact local claim or provable Crabbox ownership metadata.

## Best Possible Solution

Patch the RunPod provider so destructive resolve/release requires an exact local RunPod claim or a verifiable crabbox- named pod identity, with regression tests and docs for any explicit reclaim path.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: stop uses ReleaseOnly, RunPod accepts a raw GetPod result, non-Crabbox names synthesize an rpod identity, and ReleaseLease terminates the resulting CloudID; no live RunPod mutation was run in this read-only review.

## Solution Assessment

Yes. The narrow maintainable fix is to make the RunPod provider fail closed on destructive paths unless ownership is proven, while keeping any manual-pod visibility read-only or behind explicit reclaim.

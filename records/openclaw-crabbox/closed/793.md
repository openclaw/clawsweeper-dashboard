## Label Justifications

- `P1`: The issue reports a current security-boundary bug where normal stop paths can route destructive local-provider operations without exact ownership proof.
- `impact:security`: The report concerns provider resource ownership checks before destructive actions, a documented Crabbox security boundary.

## Summary

Keep open: current main still contains the reported release-only stop/delete paths for apple-container, local-container, and apple-vz, and no open or merged PR currently owns this local-provider fix.

## What This Changes

The issue asks Crabbox to require exact local lease ownership proof before destructive stop/delete operations against apple-container, local-container, and apple-vz resources.

## Best Possible Solution

Add provider-adapter exact-claim guards before stop/delete mutation, keep unclaimed cleanup behind explicit cleanup or reclaim flows, and add focused regression tests for each affected provider.

## Reproduction Assessment

Yes. Source inspection on current main shows release-only stop can resolve provider-labelled local resources and reach destructive delete calls without an immediate exact-claim guard; no live destructive provider run was needed.

## Solution Assessment

Yes, with a policy caveat. Exact local-claim validation before mutation is the narrowest safety fix, but maintainers should choose how lost-state recovery moves through explicit reclaim or cleanup without preserving raw-id deletion.

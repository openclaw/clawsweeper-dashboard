## Summary

Keep open: current main still lacks SSH credential-destination provenance for the reported parallels, ssh/static, and exe-dev paths, and the source-level boundary is credible under the repository security policy.

## What This Changes

The issue reports that repository-local SSH destination config for parallels, ssh/static, and exe-dev can be combined with higher-trust SSH credentials without the provenance guard used by other providers.

## Best Possible Solution

Extend the existing provenance framework to SSH-backed provider destinations, including explicit approval paths and regression tests, after maintainers scope ambient SSH authentication compatibility.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: repository config can set the affected SSH destinations, the provider-destination validator has no matching cases, and the provider sinks invoke SSH using configured or ambient authentication.

## Solution Assessment

Yes, with maintainer scoping. The narrow maintainable direction is to extend the existing credential-destination provenance pattern instead of adding ad hoc provider checks, but ambient SSH auth compatibility needs a deliberate policy decision.

## Summary

Keep this open: current main and v0.38.0 retain the XCP-ng credential-replay boundary, no open fix PR or exact duplicate owns the work, and maintainers still need to define which multi-host pool destinations are trusted.

## What This Changes

Require XCP-ng pool-master redirects to preserve an operator-trusted credential destination before replaying the pool username and password.

## Best Possible Solution

Enforce a provider-level trusted-master policy before either endpoint replacement, fail closed without sending credentials to rejected origins, and cover supported and rejected pool layouts with regression tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which XCP-ng pool-master destinations may receive password-bearing retries: only the configured origin, explicitly configured additional origins, or origins proven through another authenticated pool-membership mechanism?

Rationale: The replay is unsafe, but the source and tests do not define which cross-origin pool layouts are legitimate, so automation cannot safely choose the permanent credential-destination contract.

Likely owner: coygeek

Owner reason: The merged history shows the strongest XCP-ng domain context for the intended redirect behavior and supported pool layouts.

Owner confidence: high

Options:

- **Explicit master allowlist (recommended):** Trust the configured origin by default and permit additional pool-master origins only when the operator explicitly approves them.
- **Exact same origin:** Reject every scheme, hostname, or effective-port change, maximizing safety but potentially breaking existing multi-host pools.
- **Authenticated pool membership:** Allow a changed origin only after an independently authenticated mechanism proves that it belongs to the configured XCP-ng pool.

## Reproduction Assessment

Yes at source level: both redirect paths assign a response-derived endpoint before a password-bearing login, and existing tests demonstrate that login moving to another server. This read-only review did not operate a hostile live XCP-ng endpoint.

## Solution Assessment

The fail-closed direction is correct, but exact same-origin enforcement is not yet proven to be the best compatibility-safe policy; maintainers should first select an explicit trusted-master contract.

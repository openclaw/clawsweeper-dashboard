## Label Justifications

- `P1`: The issue reports a current security-boundary bug where a normal stop path can delete a local Hyper-V VM without exact ownership proof.
- `impact:security`: The report concerns Crabbox's documented provider-resource ownership boundary before destructive mutation.
- `impact:data-loss`: The affected path can remove a Hyper-V VM and its associated storage.

## Summary

Keep open: current main still allows Hyper-V release-only resolution to hand a raw `crabbox-` VM name to `ReleaseLease`, and no merged or open related item fixes the Hyper-V path.

## What This Changes

The issue requests an exact local Hyper-V lease-claim check before `crabbox stop --provider hyperv` deletes a `crabbox-` VM.

## Best Possible Solution

Add a Hyper-V provider-local exact-claim gate before `removeVM`, keep exact-claim missing-VM pruning, and add focused regression tests for matching, unclaimed, and mismatched release targets.

## Reproduction Assessment

Yes. Source inspection on current main shows release-only Hyper-V resolution can return a raw `crabbox-` VM target with an empty claim and `ReleaseLease` then calls `removeVM` without an exact-claim check.

## Solution Assessment

Yes. A provider-local exact-claim gate before the destructive Hyper-V release call is the narrowest maintainable fix and matches the Apple Container and Apple VZ pattern already on main.

## Label Justifications

- `P0`: The issue reports a security boundary failure where Crabbox can perform destructive EC2 deletion without exact ownership proof.
- `impact:security`: The affected behavior is a provider-resource ownership check before a destructive cloud API call.
- `impact:data-loss`: A successful cleanup path can terminate an unrelated or stale-claim EC2 instance and remove its tag-named provider key.

## Summary

Keep open: current main still allows AWS direct cleanup to delete an expired, canonically tagged EC2 instance without first proving an unchanged local lease claim for that exact cloud resource.

## What This Changes

The issue asks AWS direct cleanup to require exact local ownership claims before deleting EC2 resources discovered from provider tags.

## Best Possible Solution

Require AWS direct cleanup to skip tag-only candidates unless an unchanged local claim matches provider, lease ID, EC2 cloud ID, and region/scope; handle intentional lost-state recovery through an explicit reclaim/adoption path.

## Reproduction Assessment

Yes. Source inspection on current main shows AWS cleanup can delete a canonical tag-matching expired server without seeding a local claim, and the existing AWS cleanup test expects that deletion.

## Solution Assessment

Yes. Requiring an exact AWS-local claim before delete is the narrowest maintainable fix because Hetzner already uses that pattern and VISION.md rejects labels alone as ownership proof.

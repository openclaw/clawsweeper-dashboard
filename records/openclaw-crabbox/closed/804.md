## Label Justifications

- `P1`: The issue describes a current coordinator authentication boundary weakness that can expose and control an active WebVNC desktop when the attacker has a lease identifier and the victim has a portal session.
- `impact:security`: The affected behavior is cross-origin reuse of a portal session credential against an authenticated WebVNC bridge route.

## Summary

Keep open: current main still authenticates portal WebSocket requests from `crabbox_session`, and the WebVNC viewer path accepts the upgrade without an Origin guard; the related Code origin hardening does not cover this WebVNC sink.

## What This Changes

The issue reports that the portal WebVNC viewer WebSocket can authenticate via the operator's portal cookie without validating the browser Origin.

## Best Possible Solution

Add a Worker-side Origin/request-intent guard before portal-cookie WebVNC viewer upgrades, reject mismatched browser Origins with 403, preserve valid same-origin viewer behavior, and add focused Worker regression tests.

## Reproduction Assessment

Yes. Source inspection shows cookie-backed portal authentication reaching the WebVNC viewer WebSocket handler, and that handler accepts the upgrade without an Origin check; a live browser deployment was not exercised.

## Solution Assessment

Yes. The narrow maintainable fix is to add WebVNC viewer Origin validation for cookie-authenticated portal WebSocket handshakes, while coordinating any shared helper with the broader portal request-intent work in https://github.com/openclaw/crabbox/issues/803.

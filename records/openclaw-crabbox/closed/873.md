## Label Justifications

- `P0`: The issue reports a security boundary failure where Crabbox can perform destructive provider server deletion without exact ownership proof.
- `impact:security`: The affected behavior is a provider-resource ownership check before a destructive cloud API call.
- `impact:data-loss`: If the stored server ID is wrong, cleanup could destroy a Hetzner server and its machine-local state outside the intended lease.

## Summary

Keep open: current main still lets coordinator-side Hetzner cleanup delete a positive stored server ID without first proving that the provider server is Crabbox-owned and bound to the lease.

## What This Changes

The issue requests fail-closed ownership verification before coordinator Hetzner cleanup deletes a server from a persisted lease server ID.

## Best Possible Solution

Add a coordinator Hetzner release guard that fetches or source-selects the provider server, verifies Crabbox ownership labels and exact lease binding, and fails closed without DELETE when ownership is not proven.

## Reproduction Assessment

Yes. Source inspection on current main shows a positive Hetzner `serverID` reaches `HetznerProvider.releaseLease`, which sends `DELETE /servers/{id}` without a preceding server read or ownership-label check.

## Solution Assessment

Yes. The requested fail-closed ownership check is the narrowest maintainable fix because it matches SECURITY.md, VISION.md, and the existing direct Hetzner cleanup guard.

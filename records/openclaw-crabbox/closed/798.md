## Label Justifications

- `P2`: This is a source-reproducible medium-severity credential disclosure with provider-specific preconditions and no evidence of active exploitation.
- `impact:security`: The issue concerns configured provider credentials potentially appearing in Crabbox-generated error output and diagnostics.
- `impact:auth-provider`: The affected values are provider bearer tokens or API keys used to authenticate Crabbox provider API requests.

## Summary

Keep open: current main still has unredacted provider error-body paths in the seven named clients, while repository security docs and sibling provider fixes establish credential redaction as expected behavior.

## What This Changes

The issue asks Crabbox to redact configured provider credentials from upstream HTTP error bodies before those bodies are returned as provider errors.

## Best Possible Solution

Add provider-local redaction at each non-2xx error-body boundary and cover echoed raw-token and bearer/API-key forms with focused regression tests for the affected adapters.

## Reproduction Assessment

Yes. Source inspection gives a high-confidence path: each affected client sends a configured provider credential, reads a non-2xx response body, and returns that body in an error string without redacting the credential first.

## Solution Assessment

Yes. The narrow maintainable fix is to reuse the established sibling-provider pattern: replace the exact configured secret and common bearer/API-key forms before constructing user-visible errors.

## Label Justifications

- `P1`: The issue reports a source-supported live provider access credential disclosure across Crabbox's documented lease-share authorization boundary.
- `impact:security`: The affected behavior concerns credential disclosure and cross-owner access boundaries for shared leases.
- `impact:auth-provider`: The exposed Daytona `sshUser` value is the provider access identity used for direct SSH access to the sandbox.

## Summary

Keep open: current main still returns Daytona `sshUser` through the visibility-routed single-lease response, while docs limit `use` sharing to lease visibility and portal bridges rather than direct SSH credential transfer.

## What This Changes

The issue reports that share-visible single-lease GET responses can expose a live Daytona SSH access token to lower-privilege share recipients.

## Best Possible Solution

Land a focused Worker fix that redacts Daytona provider access credentials from lower-trust share-visible single-lease responses, with tests covering owner, `use`, `manage`, list, and portal paths.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should `manage` share recipients receive direct Daytona SSH access credentials from single-lease JSON responses, or should Daytona credentials be owner/admin-only while shared users use portal-mediated access?

Rationale: Source confirms `use` share disclosure, but `manage` credential semantics are a security-boundary policy choice that docs do not currently settle.

Likely owner: steipete

Owner reason: Recent Worker security and diagnostic credential-redaction commits make this the best available owner for the boundary decision.

Owner confidence: medium

Options:

- **Owner/admin only credentials (recommended):** Redact Daytona `sshUser` for every non-owner non-admin caller and keep shared users on portal-mediated access unless a credential-sharing feature is explicitly designed.
- **Manage gets credentials:** Allow `manage` share recipients to receive Daytona credentials but redact for `use`, with tests and docs making that elevated role meaning explicit.

## Reproduction Assessment

Yes. Source inspection shows a non-owner share-visible caller can resolve the lease, trigger Daytona access refresh, and receive the unredacted `sshUser` through `leaseForRequest`; I did not run Worker tests because this review is read-only.

## Solution Assessment

Mostly yes. Central credential redaction in lease serialization is the narrow repair for `use` disclosure, with the remaining solution choice limited to whether `manage` share recipients are owner-equivalent for direct Daytona credentials.

## Label Justifications

- `P2`: This is a source-supported security bug with provider-resource destruction impact but a limited Vast/local-invocation blast radius.
- `impact:security`: The issue crosses Crabbox's documented ownership boundary for destructive provider actions against resources not strongly identified as its own.
- `impact:data-loss`: The default Vast release action can destroy the target instance and its data after a label-only resource is converted into a local claim.

## Summary

Keep open: current main and v0.35.0 still contain the reported Vast path where numeric-id resolution can accept a provider `cbx1|...` label and write a local claim without `--reclaim`, enabling later stop or destroy through that manufactured claim.

## What This Changes

Require Vast raw instance-id reuse to have an exact matching local claim or explicit `--reclaim` before recording ownership and enabling later destructive release.

## Best Possible Solution

Add a Vast resolve guard that refuses label-only raw instance-id adoption unless an exact matching local claim exists, while keeping explicit `--reclaim` adoption and covering both paths with focused regression tests.

## Reproduction Assessment

Yes at source level: a fake Vast API with a `cbx1|...` labeled instance and no local claim can exercise `ResolveRequest{Repo: ..., ID: "8", Reclaim: false}` to show claim creation before release. I did not execute that regression in this read-only review.

## Solution Assessment

Yes, the proposed guard is the narrowest maintainable fix because it matches VISION.md, docs/security.md, and the existing Hetzner exact-claim-or-reclaim pattern without adding new config surface.

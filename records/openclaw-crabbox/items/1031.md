## Summary

This should stay open: current main still lets XCP-ng HOST_IS_SLAVE data retarget the XML-RPC endpoint and then replay session.login_with_password to that endpoint, and no canonical XCP-ng fix or duplicate owns the work.

## What This Changes

The issue requests a trusted-destination check for XCP-ng HOST_IS_SLAVE redirects before replaying XCP-ng username/password credentials.

## Best Possible Solution

Add fail-closed trusted-destination enforcement before any XCP-ng password-bearing retry, preserve legitimate pool-master redirects behind the chosen trusted policy, and cover login-time plus post-login redirects with regression tests.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which trusted destination policy should XCP-ng HOST_IS_SLAVE redirects use before Crabbox replays session.login_with_password?

Rationale: The source-confirmed bug crosses a provider credential boundary, and the permanent policy affects both secure defaults and legitimate XAPI pool-master behavior.

Likely owner: steipete

Owner reason: Recent XCP-ng hardening and current-main/release history make steipete the strongest available owner for the policy choice.

Owner confidence: medium

Options:

- **Same-origin default (recommended):** Allow only redirects that preserve the configured API origin's scheme, host, and effective port, and reject all others with a clear diagnostic.
- **Trusted allowlist:** Add trusted user configuration or environment variables for approved pool-master origins, and reject off-list redirects before credentials are replayed.
- **Pool-membership validation:** Validate the reported master against trusted XAPI pool metadata before replaying credentials, if maintainers want a richer provider-specific policy.

## Reproduction Assessment

Yes from source inspection. Current main still replaces c.endpoint from HOST_IS_SLAVE data and then calls session.login_with_password again; existing httptest coverage demonstrates replay to a second server but does not reject an off-policy destination.

## Solution Assessment

Unclear until maintainers choose the security boundary. A same-origin fail-closed default is the narrowest maintainable repair, while an allowlist or pool-membership policy would preserve more deployment layouts but adds product/config surface.

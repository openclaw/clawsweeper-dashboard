## Summary

Current main and v0.34.0 still have the reported Railway stop path: delegated CLI stop passes a caller-supplied service id into `railwayBackend.Stop`, which resolves the latest deployment and calls Railway's stop mutation without local claim or exact ownership proof. This should stay open for maintainer security/product review because the safe fix path depends on whether Railway stop should fail closed or gain an explicit adoption/binding contract.

## What This Changes

Require Railway stop to prove the target service or deployment belongs to a Crabbox lease or explicit adopted claim before performing the destructive provider stop.

## Best Possible Solution

Make Railway stop fail closed unless it can resolve an exact local or adopted claim bound to provider, Railway project, environment, and service/deployment, with focused regression coverage for both rejected unclaimed stops and any maintainer-approved adoption path.

## Reproduction Assessment

Yes, at source level: `StopRequest{ID: "svc-1"}` reaches `LatestDeployment` and `StopDeployment` without local claim setup, and the existing fake API test confirms the call. Live reproduction would require Railway credentials and a real service.

## Solution Assessment

The ownership-proof direction is the right fix, but the exact implementation needs maintainer choice because Railway services are created out of band. A fail-closed default is safest unless maintainers sponsor an explicit adoption or redeploy-claim contract.

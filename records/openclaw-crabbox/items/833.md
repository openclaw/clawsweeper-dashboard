## Label Justifications

- `P1`: A configured Railway operator path can perform a destructive provider action against a deployment without Crabbox ownership proof, creating urgent provider-resource availability and security-boundary impact.
- `impact:security`: The issue is about a supported security boundary: destructive provider actions against resources Crabbox cannot strongly identify as its own.
- `impact:other`: The concrete user impact is service availability disruption for Railway deployments, which is meaningful but not covered by the more specific issue impact labels.

## Summary

Current main still has the reported Railway stop path: delegated `stop` reaches `railwayBackend.Stop`, which resolves the latest deployment for the caller-supplied service id and calls Railway's stop mutation without resolving a local claim. The issue should stay open for security/product review because VISION.md and security docs align with requiring exact ownership proof, but preserving Railway stop likely needs an explicit adoption or fail-closed decision.

## What This Changes

Require Railway stop to prove a service or deployment belongs to a Crabbox lease or adopted claim before stopping it.

## Best Possible Solution

Make Railway stop fail closed unless it can resolve an exact local or adopted claim bound to provider, Railway project, environment, and service/deployment; if stop support remains, add focused adoption/redeploy-claim coverage and regression tests.

## Reproduction Assessment

Yes, at source level: `StopRequest{ID: "svc-1"}` reaches `LatestDeployment` and `StopDeployment` without any local claim setup, and the existing fake API test confirms the call. Live reproduction would require Railway credentials and a real service.

## Solution Assessment

The requested ownership-proof direction is right, but the exact implementation needs maintainer choice because Railway services are created out of band. A fail-closed default is safest unless maintainers sponsor an explicit adoption or redeploy-claim contract.

## Summary

Keep open: current main still installs a replacement CSP on proxied Browser Code responses without `frame-ancestors`, while the Code bootstrap and normal portal HTML already deny framing. The issue is source-reproducible and appears to be the canonical remaining anti-framing gap for isolated Code proxy responses.

## What This Changes

The issue reports that proxied Browser Code responses lack a `frame-ancestors` CSP directive, allowing same-site iframe clickjacking of active Code viewer sessions.

## Best Possible Solution

Add `frame-ancestors 'none'` or an equivalent reviewed anti-framing directive to the replacement Code proxy CSP and cover it with focused Worker regression coverage that preserves the existing VS Code-compatible directives.

## Reproduction Assessment

Yes, at source level: current main strips upstream CSP, installs a replacement Code proxy CSP without `frame-ancestors`, allows iframe-like GET/HEAD requests without Origin, and uses a SameSite=Lax Code viewer cookie. I did not run a live browser exploit proof.

## Solution Assessment

Yes. The narrow maintainable fix is to add the same anti-framing control already used by portal and handoff pages to proxied Code responses; a configurable allowlist should be a maintainer-approved follow-up only if needed.

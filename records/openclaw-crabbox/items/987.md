## Summary

Keep open: current main still allows the exact manage-share event-attribution path, while the earlier merged fix only tightened use-share re-tagging to require manage access. Prior maintainer discussion suggests manage may have been intended as the accepted boundary, so this needs an explicit security/product decision rather than cleanup closure.

## What This Changes

The issue reports that a run owner with manage-share access to another lease can post a run event whose lease ID rewrites the run's durable lease attribution into that shared lease's audit history.

## Best Possible Solution

Decide and document whether manage-share is trusted for post-create audit attribution; if not, restrict event-supplied lease IDs to existing run attribution or a server-validated replacement flow and add manage-share regression coverage.

Question: Should manage-share recipients be allowed to add owner-readable run audit attribution to a shared lease through post-create run events, or should that be limited to the lease owner/admin or a validated replacement flow?

Rationale: Current docs and VISION.md push against silent retargeting of ownership claims, but the recent related maintainer discussion accepted manage access as the guard, so automation should not choose the permanent authorization contract.

Likely owner: steipete

Owner reason: They authored the shared-lease audit model and made the related expected-behavior call, so they are the best available owner for the contract decision.

Owner confidence: high

Options:

- **Block event-only manage reattribution (recommended):** Reject or ignore manage-share event lease IDs unless the run already belongs to that lease or a server-validated replacement flow proves the backing lease relationship.
- **Confirm manage-share as trusted:** Document that manage-share recipients may create owner-readable audit attribution through run events and close this as accepted behavior after maintainer sign-off.
- **Add a dedicated attach path:** Keep ordinary events from expanding attribution and add a narrow API for post-create lease attachment with explicit validation and tests.

## Reproduction Assessment

Yes. Source inspection on current main shows an owned run plus a different manage-shared lease can pass the event endpoint guard, store the event lease ID, and add that lease owner to run attribution; I did not run the Worker harness in this read-only review.

## Solution Assessment

Unclear. Blocking manage-share event-only attribution is the safer reading of the docs and VISION.md, but the recent related fix intentionally made manage access the guard, so maintainers need to confirm the desired contract before implementation.

## Label Justifications

- `P1`: This is a concrete credential-destination security boundary report affecting Islo provider traffic in current main and the latest release.
- `impact:security`: The issue concerns bearer credentials and request bodies potentially leaving the configured provider destination after redirects.
- `impact:auth-provider`: The affected path is provider authentication and routing for Islo API clients using configured base URLs and API keys.

## Summary

Keep open. Current main and latest release still lack an Islo-specific redirect guard for credential-bearing SDK and raw HTTP requests, while repository docs define same scheme, hostname, and effective-port confinement for provider clients with custom endpoints.

## What This Changes

The issue asks Crabbox to confine Islo provider redirects to the configured API origin before replaying bearer authorization or request bodies.

## Best Possible Solution

Add an Islo redirect-checked HTTP client bound to the normalized base URL for both SDK and raw requests, with tests rejecting scheme, host, and effective-port changes before auth or body replay while preserving intended same-origin redirects.

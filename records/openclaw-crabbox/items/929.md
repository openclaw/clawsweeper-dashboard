## Label Justifications

- `P2`: The report is a source-backed security/session bug with limited availability impact and no credential theft, data access, or persistent compromise.
- `impact:security`: The issue crosses the documented cookie-authenticated portal same-origin boundary.
- `impact:session-state`: The observable effect is forced portal session termination and Code viewer session revocation.
- `impact:auth-provider`: The affected path is the portal auth cookie and logout flow built on the GitHub-backed session token.

## Summary

Keep open: current main and v0.36.0 still route GET /portal/logout around the portal origin gate, clear the SameSite=Lax session cookie, and revoke Code viewer sessions; I found no canonical fix PR or duplicate that owns this exact cross-site logout path.

## What This Changes

Require same-origin intent for portal logout so cross-site GET navigation cannot clear crabbox_session or revoke Code viewer sessions.

## Best Possible Solution

Make logout a same-origin state-changing portal action before any revocation or cookie clearing occurs, then add Worker tests for blocked cross-origin top-level GET logout and allowed same-origin logout.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Crabbox change portal logout from a cross-site navigable GET into a same-origin state-changing action, and what compatibility shape should that take?

Rationale: The vulnerability is source-backed, but the permanent fix changes a browser auth/session boundary and may affect existing portal logout links or cookie behavior.

Likely owner: steipete

Owner reason: Recent merged work on logout revocation and adjacent portal security makes this the strongest available routing signal.

Owner confidence: high

Options:

- **Require same-origin logout intent (recommended):** Convert logout to POST or add an explicit same-origin CSRF/intent token, apply the gate before revocation and cookie clearing, and cover both blocked and allowed flows in Worker tests.
- **Tighten cookie behavior only:** Changing crabbox_session to SameSite=Strict may reduce cross-site navigation exposure but needs login-flow compatibility proof and leaves a state-changing GET design in place.
- **Document GET logout as intentional:** Maintainers can accept forced logout as a low-availability tradeoff, but that would need explicit documentation because it conflicts with the current portal mutation boundary.

## Reproduction Assessment

Yes. Source inspection on current main shows a valid portal cookie can reach GET /portal/logout before the origin gate, and that handler clears the session cookie and revokes Code viewer sessions.

## Solution Assessment

Yes, directionally. The narrow maintainable fix is to require same-origin logout intent before side effects; the exact POST/token/cookie compatibility shape should be chosen in security review.

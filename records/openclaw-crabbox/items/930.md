## Label Justifications

- `P0`: The issue reports a documented security-boundary failure that can drive destructive cloud resource deletion when coordinator state points at the wrong provider object.
- `impact:security`: The affected behavior is the ownership check immediately before Crabbox uses provider credentials for destructive cloud API calls.
- `impact:data-loss`: If the stored provider identifier is wrong, release cleanup can destroy a VM or disk-backed resource and its machine-local state outside the intended lease.

## Summary

Keep open: current main still matches the report for Worker managed lease release. Hetzner now re-reads the provider server and checks ownership before deletion, but AWS, Azure, and GCP still delete directly from the lease cloud ID/name, which conflicts with the repository's documented destructive provider ownership boundary.

## What This Changes

The issue requests live provider ownership read-back before AWS, Azure, and GCP managed lease release deletes cloud resources.

## Best Possible Solution

Harden the AWS, Azure, and GCP Worker provider release paths to fetch the live provider resource, require canonical Crabbox ownership plus matching lease/provider identity before delete, preserve cleanup error state on mismatch, and add Worker regression coverage for manual release and expiry cleanup.

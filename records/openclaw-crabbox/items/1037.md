## Summary

Keep open: current main and the latest release still support local `actions/setup-node` hydration through a helper that downloads and extracts a Node.js archive without an integrity check before putting it on `PATH`. This is a source-reproducible security-boundary issue that needs maintainer security review before a repair is chosen.

## What This Changes

The issue asks Crabbox to verify local Actions `setup-node` Node.js archives before extracting them into the runner tool cache and placing them on `PATH`.

## Best Possible Solution

Verify the resolved Node archive against trusted release integrity metadata before extraction, extract into a private staging directory, tie tool-cache reuse to the verified digest, and add positive and negative regression coverage for the helper.

Question: What integrity control should local `actions/setup-node` hydration enforce before installing or reusing a downloaded Node archive?

Rationale: The source gap is clear, but choosing the trust root, fail-closed behavior, and cache invalidation marker defines a security boundary and may affect existing local hydration workflows.

Likely owner: steipete

Owner confidence: high

Options:

- **Verify release SHASUMS before install (recommended):** Fetch the selected version's published SHA-256 metadata, require an archive-name match, verify before extraction, mark cache entries by digest, and fail closed on missing or mismatched integrity data.
- **Disable local setup-node downloads:** Require a preinstalled compatible Node or `--github-runner` until maintainers approve a stronger signed-metadata design, preserving safety at the cost of local hydration coverage.
- **Keep HTTPS-only behavior:** Treat this as defense-in-depth and leave the current download path unchanged, accepting that documented local setup-node hydration trusts a network archive without a release integrity check.

## Reproduction Assessment

Yes. Source inspection reproduces the issue: a local `actions/setup-node` step emits `__crabbox_setup_node`, which downloads from `nodejs.org`, extracts into `RUNNER_TOOL_CACHE`, and puts that directory on `PATH` without a digest check.

## Solution Assessment

Yes for the core direction: verify the resolved archive before extraction and tie cache reuse to that verified identity. The exact trust root and fail-closed fallback should be confirmed by maintainers because this is a security boundary.

## Label Justifications

- `P1`: The issue describes a destructive provider-resource ownership boundary problem that can delete unrelated exe-dev VMs, but requires local operator credentials rather than remote unauthenticated access.
- `impact:security`: The affected path crosses Crabbox's provider-resource ownership boundary before a destructive provider action.
- `impact:data-loss`: The reported failure mode can delete unrelated VM state from a shared exe.dev account or automation profile.

## Summary

Keep open: current main and the latest release still route exe-dev raw name/host resolution into a destructive VM delete path without a proven Crabbox ownership predicate.

## What This Changes

The issue asks Crabbox to make exe-dev stop/release fail closed unless the target VM is proven to belong to the current lease or is explicitly adopted.

## Best Possible Solution

Make exe-dev release prove an exact local claim or matching Crabbox ownership tags before rm, keep name/host matching read-only, and document explicit reclaim/adoption if raw provider identifiers remain supported.

Rationale: The security docs and VISION.md point toward fail-closed behavior, but current stop docs describe raw VM-name deletion, so the compatibility and release-handling choice needs maintainer ownership.

- **Fail Closed On Unproven Targets (recommended):** Require exact claim or matching Crabbox tags before exe-dev rm and update docs/tests around the new destructive boundary.
- **Add Explicit Adoption First:** Preserve a raw-identifier workflow only through an explicit reclaim/adoption step that persists the binding before deletion.
- **Keep Legacy Raw Deletion:** Continue allowing claimless VM-name deletion and accept the documented provider-resource ownership risk.

## Reproduction Assessment

Yes at source level: a mocked exe.dev ls response with an untagged VM matching the supplied name or SSH host would flow through resolveVM/findVM/leaseIdentityForVM into deleteVM. I did not use a live exe.dev account.

## Solution Assessment

Yes, the maintainable direction is to fail closed before rm unless exact claim or provider tags prove ownership. If maintainers want to preserve raw-name stop, the safer alternative is an explicit reclaim/adoption path with regression coverage.

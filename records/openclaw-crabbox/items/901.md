- `impact:security`: The issue concerns credential issuance, signed user tokens, and coordinator authentication boundaries.

## Summary

Keep open. Current main still has the reported source/control/sink path: unauthenticated GitHub OAuth start returns a poll handle and authorization URL, callback stores a signed user token into the pending record selected by state, and poll releases it to the start-time secret; recent OAuth fixes only bind callback origin, not the browser authorizer to the polling client.

## What This Changes

The issue requests preventing an attacker-started GitHub OAuth CLI login from releasing a victim-completed signed user token to the attacker’s poll secret.

## Best Possible Solution

Add a maintainer-approved OAuth/login binding so a start-time poll holder cannot collect a token minted from a different user's browser authorization, with regression coverage for the attacker-started/victim-completed flow.

## Reproduction Assessment

Yes from source inspection: the current start, callback, and poll handlers expose the reported path without a separate browser-user binding proof. I did not run a live GitHub OAuth exchange or tests because this is a read-only review.

## Solution Assessment

Unclear; adding a callback-bound or token-release verifier is the right shape, but maintainers should choose the exact OAuth protocol and compatibility behavior for CLI login.

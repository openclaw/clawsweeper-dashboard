## Label Justifications

- `P2`: The issue is a bounded medium-severity provider-resource ownership boundary problem requiring configured Daytona credentials and authority to trigger stop.
- `impact:security`: The report is about Crabbox performing a destructive provider action without proving the Daytona resource is Crabbox-owned.
- `impact:data-loss`: Deleting an unowned Daytona sandbox can destroy or make unavailable provider-side sandbox state outside Crabbox's ownership boundary.

## Summary

Keep open: current main still lets the Daytona resolver accept a direct sandbox lookup after Crabbox label and local-claim checks miss, and `Stop` then passes that ID to `DeleteSandbox`. The report matches the repository's documented provider-resource ownership boundary and is not superseded by the recent local-provider ownership fix.

## What This Changes

The issue reports that Daytona stop can delete a Daytona sandbox that Crabbox cannot identify as Crabbox-owned.

## Best Possible Solution

Make Daytona destructive lifecycle paths fail closed unless the target sandbox is proven Crabbox-owned by matching Daytona labels or an exact local Daytona lease claim, with regression tests for rejected unlabeled direct IDs and allowed owned sandboxes.

## Reproduction Assessment

Yes by source inspection: current main resolves an arbitrary direct Daytona sandbox ID after ownership checks miss, and `Stop` deletes the resolved ID. I did not run a live Daytona reproduction because this review must keep the checkout read-only.

## Solution Assessment

Yes; fail-closed destructive resolution is the narrowest maintainable repair for the documented ownership boundary. A broader raw-ID reclaim workflow would be a separate product decision, not a prerequisite for this security fix.

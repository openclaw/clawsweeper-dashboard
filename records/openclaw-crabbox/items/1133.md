## Summary

Keep open: current main still conflates an omitted artifact size with an explicit zero-byte declaration, so local and remote pulls can accept non-empty content without satisfying the manifest’s declared size contract. The report is detailed, source-reproducible, security-relevant, and neither related artifact-integrity issue covers this distinct validation path.

## What This Changes

Require artifact pulls to distinguish an omitted manifest size from an explicit zero and enforce zero-byte declarations for both local and remote content.

## Best Possible Solution

Represent size presence explicitly, preserve omitted-size compatibility if required, enforce every present non-negative value including zero, cap remote reads at declared size plus one byte, and add local and HTTP regression coverage for omitted, zero, negative, exact, and oversized content.

- **Preserve optional size (recommended):** Decode size with explicit presence tracking, skip size verification only when omitted, and strictly enforce explicit zero and all other non-negative declarations.
- **Require size:** Reject manifests without a size and enforce equality for every non-negative value, accepting a stricter compatibility break for stronger default integrity.

## Reproduction Assessment

Yes at the source level: a local manifest declaring `size: 0`, omitting SHA-256, and referencing a non-empty file deterministically reaches the guarded comparison and succeeds on current main. The supplied checkout-only test description provides a focused red/green path, though this review did not execute it.

## Solution Assessment

Yes, with compatibility-aware presence tracking: the narrow maintainable fix is to distinguish omission from explicit zero and share those semantics between local verification and remote download bounds. Unconditionally making size required should occur only if maintainers intentionally change the manifest contract.

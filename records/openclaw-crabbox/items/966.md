## Summary

Keep open: current main still authorizes already-tagged Azure OS disks through tag and identity checks without rechecking `managedBy`, and no separate open item appears to own this exact stale-adopted-disk gap.

## What This Changes

The issue asks Crabbox to require fresh Azure disk-to-VM ownership proof before authorizing managed disk deletion after tag adoption.

## Best Possible Solution

Keep the fix in the Azure provider adapter and require contemporaneous disk association proof before disk deletion, with an explicit fail-closed or maintainer-approved orphaned-disk recovery path.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should Azure owned cleanup require `disk.managedBy` to match the releasing VM for every managed disk deletion, including already-tagged disks and retries after the VM has disappeared?

Rationale: The live-VM race fix is narrow, but current tests preserve cleanup of tagged companion resources after VM deletion, so maintainers need to choose the acceptable orphaned-disk boundary for a destructive security-sensitive action.

Likely owner: steipete

Owner reason: He authored the recent Azure provider-ownership hardening path and its tests, including the current disk adoption behavior.

Owner confidence: high

Options:

- **Require fresh association (recommended):** Fail closed unless the disk currently reports `managedBy` for the releasing VM, and add regression coverage for tagged and untagged disk paths.
- **Add orphaned-disk claim:** Permit post-VM disk cleanup only through an equally strong lease-bound claim that stale tag adoption cannot create by itself.
- **Accept tag-based cleanup:** Keep the current retry behavior and document that adopted Azure disk tags are sufficient ownership proof once Crabbox writes them.

## Reproduction Assessment

Yes, source-level: current main has a tagged-disk branch that authorizes through tags and identity without rechecking `managedBy`. A live Azure race was not reproduced in this read-only review.

## Solution Assessment

Yes for the live-VM case; requiring the disk association at deletion authorization is the narrowest maintainable fix. The orphaned-disk retry behavior needs a maintainer security-boundary choice before implementation changes it.

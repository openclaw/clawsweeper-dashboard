## Label Justifications

- `P1`: The issue is a source-backed destructive provider mutation boundary bug that can delete local Parallels VMs, but it is bounded to local/provider access rather than a core-wide emergency.
- `impact:data-loss`: The reported path can delete a local development VM and remove associated Crabbox local state without proving exact ownership.
- `impact:security`: The report targets Crabbox's documented boundary for destructive provider actions against resources it cannot strongly identify as its own.

## Summary

Keep this issue open: current main still lets the Parallels release path resolve raw inventory identifiers and delete a `crabbox-` VM without the exact local ownership claim required by the repo's security and lifecycle guidance.

## What This Changes

The issue asks Crabbox to require an exact local Parallels ownership claim before `crabbox stop --provider parallels` can delete a resolved `crabbox-` VM.

## Best Possible Solution

Add a Parallels-specific exact-claim ownership gate before `ParallelsClient.Delete`, verify CloudID/provider scope/name-derived lease binding, preserve state on rejection, and add focused regression tests for exact claim, unclaimed raw VM id, and mismatched claim cases.

## Reproduction Assessment

Yes, source inspection gives a high-confidence reproduction path: resolve a Parallels VM by raw id/name/slug and the release path reaches `prlctl delete` with only a `crabbox-` prefix check. I did not run a live Parallels VM fixture.

## Solution Assessment

Yes, the narrow fix is to mirror the existing local-provider exact-claim gate inside the Parallels adapter before deletion. That matches VISION.md, SECURITY.md, docs/security.md, and the sibling provider pattern without adding new config surface.

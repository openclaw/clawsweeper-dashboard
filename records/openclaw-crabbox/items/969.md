## Summary

Keep open: current main still writes WebVNC handoff records with raw username and password fields in Durable Object storage, and the repository security policy treats generated credential exposure as an in-scope boundary.

## What This Changes

The issue asks Crabbox to avoid persisting WebVNC handoff usernames and passwords as plaintext Durable Object records.

## Best Possible Solution

Preserve the existing ticket UX and authorization checks, but store the credential payload in a form that is not useful to a Durable Object storage reader without the ticket or a non-persisted/deployment secret.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Which secret boundary should protect WebVNC handoff credentials before they are written to Durable Object storage?

Rationale: The plaintext storage exposure is concrete, but the durable fix depends on whether maintainers want ticket-derived sealing, deployment-secret encryption, or another broker secret source.

Likely owner: steipete

Owner reason: This person authored the merged WebVNC handoff pull request that introduced the storage design and has the clearest recent ownership signal.

Owner confidence: high

Options:

- **Ticket-bound sealing (recommended):** Make the random handoff ticket necessary to decrypt the stored credential payload at redemption time, while keeping one-time consume and TTL semantics.
- **Deployment-secret encryption:** Encrypt active handoff records with a Worker or deployment secret kept outside Durable Object storage.
- **Security design review first:** Keep the issue open until maintainers define the accepted broker storage threat model and key source.

## Reproduction Assessment

Yes, source-level reproduction is high confidence: issue() stores the submitted username and password directly, and consume() returns those same stored fields after ticket validation. I did not run Worker tests because this cleanup review is read-only and the source path is direct.

## Solution Assessment

Unclear until maintainers confirm the key boundary, but ticket-bound sealing appears to be the narrowest maintainable direction because it preserves the existing random-ticket authority model without adding a new operator configuration requirement.

## Label Justifications

- `P0`: The report describes a security-boundary failure that can drive destructive cloud VM deletion when cleanup acts on stale ownership metadata.
- `impact:security`: The affected behavior is the ownership authorization check immediately before destructive provider API calls.
- `impact:data-loss`: A successful stale cleanup decision can delete a VM and its attached workload state or availability.

## Summary

Keep open: current main still deletes AWS, Azure, and GCP direct-cleanup candidates from list-time `Server` snapshots without fetching and revalidating the live resource immediately before the destructive provider call.

## What This Changes

The issue asks direct AWS, Azure, and GCP cleanup to re-read live cloud resources and verify current Crabbox ownership before deleting stale cleanup candidates.

## Best Possible Solution

Keep the issue open and harden each affected provider adapter so mutating cleanup fetches the live resource by immutable provider identity, verifies canonical Crabbox ownership and matching lease immediately before delete, and skips/report-only on any mismatch.

## Reproduction Assessment

Yes, source-level. Current main shows AWS, Azure, and GCP cleanup can reach provider delete calls from list-time snapshots, and the existing fake-client cleanup tests do not require a live `GetServer` recheck before deletion.

## Solution Assessment

Yes. The narrow maintainable fix is provider-local live revalidation before destructive cleanup, matching AGENTS.md provider boundaries and the stronger GCP release pattern already in current main.

## What This Changes

Reduce the duration of retained OAuth revalidation credentials for device tokens, avoid per-request membership-check amplification while failing closed, and make expired OAuth grants distinguishable to paired devices.

## System Context

The Worker coordinator would authenticate a read-only device credential, determine the paired owner’s current GitHub/org membership, then return a redacted lease-status view. The proposed follow-up changes how that authorization material is retained and revalidated without broadening the device’s read-only scope.

## Architecture Diagram

flowchart LR
  A[Paired device request] --> B[Device credential verification]
  B --> C[Stored owner revalidation material]
  C --> D[GitHub membership check]
  D --> E[Read-only lease authorization]
  E --> F[Redacted device status response]

## Best Possible Solution

After the baseline pairing design is accepted, retain only narrowly scoped and short-lived revalidation material or require a defined reauthorization flow, add a bounded fail-closed membership cache, expose `pairing_reauth_required` for expired grants, and cover revocation, expiry, and cache-boundary behavior with focused Worker tests and documentation.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: After device pairing is accepted, should device credentials retain a sealed owner OAuth grant for their full lifetime, use a short fail-closed membership cache, or require periodic owner reauthorization instead?

Rationale: The correct retention and caching policy sets the revocation window, OAuth credential blast radius, rate-limit behavior, and paired-device recovery contract; those are security-boundary choices rather than a mechanical patch decision.

Likely owner: steipete

Owner reason: The related implementation and this focused follow-up both originate from the same device-pairing security design work.

Owner confidence: medium

Options:

- **Define a short-lived revalidation model (recommended):** Require short-lived revalidation material or periodic owner reauthorization, cache successful membership checks only briefly while failing closed, and return a distinct reauthorization error when renewal is needed.
- **Keep per-request revalidation:** Preserve the strongest immediate revocation behavior and accept GitHub API amplification until real device traffic demonstrates a need for caching.
- **Defer pairing rollout:** Pause broader device-client rollout until the credential-retention and revocation model has an approved security design.

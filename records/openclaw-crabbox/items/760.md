## Summary

Keep this issue open: current main still leaves the Go CLI direct-provider browser bootstrap on the legacy unpinned global APT trust path, while the merged Google-key pinning work only covered the Worker and standalone Linux installer paths.

## What This Changes

The issue requests hardening the Go CLI direct-provider browser bootstrap so Google Chrome APT trust uses the pinned primary fingerprint, a scoped keyring, and `signed-by` with a Chromium fallback on verification failure.

## Best Possible Solution

Mirror the Worker/developer-tools pinned Google primary fingerprint and scoped `signed-by` keyring flow into `internal/cli/bootstrap.go`, then update `internal/cli/bootstrap_test.go` to reject the legacy global trust path while preserving Chromium fallback.

## Reproduction Assessment

Yes for source reproduction. Current main shows `--browser` reaches `cfg.Browser`, and the Go direct-provider `cloudInit` body still imports Google's APT key without fingerprint pinning or repository scoping.

## Solution Assessment

Yes. The narrow maintainable fix is to reuse the already-merged Worker and developer-tools pinning pattern in the Go bootstrap and update the Go regression test contract.

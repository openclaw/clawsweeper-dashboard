## Label Justifications

- `P1`: A source-supported security bug can purge local Multipass VM disk state through normal stop or cleanup, while still requiring local provider access.
- `impact:data-loss`: `multipass delete --purge` can remove a VM and its disk state when the instance is not proven to be the current Crabbox lease.
- `impact:security`: The issue is about a destructive provider action without strong ownership proof, which the repository security policy treats as an in-scope boundary.

## Summary

This issue should stay open: current main still has a source-traceable Multipass path where release-only resolution and cleanup can reach `multipass delete --purge` without proving an exact Crabbox claim for the instance.

## What This Changes

This issue asks Crabbox to prevent Multipass stop and cleanup from deleting instances unless an exact local Crabbox lease claim proves ownership.

## Best Possible Solution

Add a Multipass exact-claim ownership check before `removeInstance` in release and cleanup, preserve explicit reclaim/adoption for intended orphan handling, and cover unclaimed release plus stopped missing-claim cleanup in provider tests.

## Reproduction Assessment

Yes for source-level reproduction: the current code path from `crabbox stop --provider multipass <instance>` through release-only resolve to `multipass delete --purge` is clear. I did not run live Multipass commands during this read-only review.

## Solution Assessment

Yes, the requested exact-claim gate is the narrow maintainable fix because sibling local providers already use that pattern. The fix should avoid silently deleting orphaned instances and keep any adoption path explicit.

## Summary

Keep open: current main still lets effective `external.config` values become `{{config.*}}` lifecycle template values without sensitivity/source metadata, while the argv guard only blocks tracked sensitive values such as `{{env.*}}`. The report is narrower than the earlier expected-behavior discussion about repository-configured External commands because it targets inherited trusted credentials flowing to a lower-trust repository-selected argv destination.

## What This Changes

The issue reports that repository-defined External lifecycle commands can expand inherited trusted `external.config` values into process argv without source or sensitivity tracking.

## Best Possible Solution

Track source/sensitivity for External config template values so lower-trust lifecycle argv, steps, and resource-name templates cannot carry trusted credentials unless the operator explicitly opts into a non-secret argv path, while preserving same-source repository config workflows.

Options:

- **Track config provenance (recommended):** Mark trusted or environment-origin `external.config` template values sensitive and require the existing explicit argv/resource-name opt-ins or a non-argv channel when a lower-trust lifecycle references them.
- **Accept current behavior:** Treat inherited `external.config` argv expansion as part of repository executable automation and update docs/security text to remove the implied source-bound credential protection for this case.
- **Docs-only warning:** Warn operators not to store secrets in `external.config` without changing runtime behavior, which preserves compatibility but leaves the reported source-bound credential flow available.

Unclear pending maintainer security direction. The reported remediation is the narrow maintainable shape, but maintainers should choose the compatibility stance for existing non-secret External config values before a fix PR proceeds.

## Label Justifications

- `P1`: The report shows a current provider-resource ownership boundary issue that can route command execution, status reads, or stop actions to an unclaimed W&B sandbox within the configured credential scope.
- `impact:security`: The issue concerns Crabbox acting on provider resources it cannot strongly identify as its own, which is an explicit security-boundary class in this repository.

## Summary

Keep open: current main and the latest release still forward W&B caller-supplied sandbox IDs directly to Exec/Get/Stop, while the repository security docs require raw provider recovery to fail closed when ownership cannot be established.

## What This Changes

The issue reports that W&B `run --id`, `status --id`, and `stop --id` reuse caller-supplied sandbox IDs without proving Crabbox ownership.

## Best Possible Solution

Add W&B adapter ownership enforcement: record claims or provider metadata for Crabbox-created kept sandboxes and require that proof, or an explicit reclaim flow, before Exec/Get/Stop on existing IDs.

## Reproduction Assessment

Yes. The source path is high-confidence: a non-empty W&B `req.ID` skips acquisition and is forwarded to Exec, Status, or Stop, and existing tests assert the direct existing-ID path; I did not run live W&B mutation.

## Solution Assessment

Unclear. Fail-closed ownership proof is the right security direction, but the exact W&B-compatible migration or reclaim path needs maintainer decision because current docs explicitly support existing-ID reuse.

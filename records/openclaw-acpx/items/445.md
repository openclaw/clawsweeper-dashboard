## Summary

Current main at `a518ea909eb91296b0d05c76345f1c8403ba830b` still discards the detached queue owner’s output, does not observe its early failure, and reports only poll exhaustion. This is a narrow, source-reproducible diagnostics bug in a core queue lifecycle path, with no linked implementation PR and no evidence that v0.12.0 fixes it.

## What This Changes

Report the detached queue owner’s actual fatal startup cause instead of reducing every early startup failure to an opaque queue-owner timeout.

## Best Possible Solution

Keep detached startup, retain the child handle through the startup handshake, race IPC readiness against early `error` or `exit`, and throw a structured queue error containing the spawn cause or exit code and signal; add bounded stderr capture only if maintainers explicitly want persisted diagnostics.

Yes at source level: force the detached owner to fail before binding IPC, such as an EPERM from queue-directory chmod, and the parent reaches the generic startup timeout because it neither observes the child nor captures stderr. ## Solution Assessment

Yes, with a narrower preference: race owner readiness against early child `error` or `exit` and preserve the cause in a structured queue error. A persistent owner log is optional and should require deliberate lifecycle and sensitive-output handling.

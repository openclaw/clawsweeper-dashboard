## What This Changes

## Best Possible Solution

Require a non-empty `authToken` for initial completion and persistence, allow an empty `privateKey`, preserve the existing empty-key credentials header, and retain strict validation for refresh responses unless separate protocol evidence warrants changing it.

## Repair Work Prompt

Fix the SMAPI token-only authentication regression described in https://github.com/steipete/sonoscli/issues/20. On current main, `SMAPIClient.CompleteAuthentication` and `FileSMAPITokenStore.Save` reject credentials unless both `authToken` and `privateKey` are non-empty, but Sonos documents `privateKey` as refresh-only and a token-only `getDeviceAuthToken` response as valid. Change initial completion and persistence validation to require a non-empty `authToken` while allowing an empty `privateKey`; preserve the existing credentials-header behavior and do not loosen the separate token-refresh response validation unless protocol evidence and tests require it. Add regression tests for a token-only SOAP completion response, saving and loading a token-only pair, and an authenticated request that emits the token with an empty key. Update user-facing SMAPI documentation only if existing wording claims both fields are mandatory; do not edit CHANGELOG.md. Validate with focused package tests and the full Go test suite.

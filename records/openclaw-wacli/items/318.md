## Summary

This PR should remain open because its opt-in pacing logic can still dispatch a delegated send after the caller has timed out while waiting behind another send. The prior P1 remains on the unchanged head and has a narrow mechanical repair; the PR’s redacted live WhatsApp proof is otherwise strong.

## What This Changes

The PR adds an opt-in `sync --follow --send-spacing` flag that paces serialized delegated WhatsApp sends with either a fixed delay or random delay range.

## System Context

In follow mode, concurrent `wacli send` commands hand their requests to a long-running daemon when they cannot acquire the store lock. The daemon serializes those requests and sends them through WhatsApp; this PR adds optional pacing before each delegated dispatch.

## Architecture Diagram

## Best Possible Solution

Start one cancellable request deadline before queue acquisition, make queue acquisition honor it, and use that same context for pacing and dispatch with regression coverage for expiry while queued.

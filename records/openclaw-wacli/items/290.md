## Label Justifications

- `P1`: This is a current-release regression report where a daemonized WhatsApp sync workflow stopped capturing real messages for hours without an in-product reconnect or error signal.
- `impact:message-loss`: The issue is specifically about WhatsApp messages not being ingested into the local store while `sync --follow` appears connected.

## Summary

Keep open: current main and v0.11.2 only reconnect follow mode on disconnect-like events or whatsmeow `KeepAliveTimeout`, while this report describes current-release message ingestion going stale without any disconnect, reconnect, or stale event. The older issue was closed by a keepalive-bound fix, but this new report provides a concrete current-release case that the keepalive boundary may not cover.

## What This Changes

The issue asks for `sync --follow --stale-threshold` to recover when message/store freshness goes stale while the WhatsApp socket still appears connected, and to expose that stale health through diagnostics.

## Best Possible Solution

Define a follow-mode health contract for connected-but-not-ingesting sync, then implement a tested reconnect or unhealthy doctor status that covers stale application/store freshness without breaking quiet healthy sessions.

## Reproduction Assessment

No, we do not have a high-confidence live reproduction in this checkout. Source inspection does confirm the current code cannot react to the reported shape unless whatsmeow emits `KeepAliveTimeout`, `Disconnected`, or `StreamReplaced`, and the reporter provided detailed current-release operational evidence.

## Solution Assessment

Unclear: a freshness-based reconnect may be the right repair, but current main intentionally made `--stale-threshold` keepalive-only. Maintainers should decide whether to broaden that flag, add a separate health/watchdog surface, or change `doctor` semantics.

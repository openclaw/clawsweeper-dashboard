## Summary

Keep this issue open as the canonical product-direction request. Current main remains intentionally Cloudflare-native, and a portable deployment target would require a supported replacement contract for identity, authoritative budget enforcement, revocation, storage, queues, administration, and operations—not only Docker packaging.

## What This Changes

Requests a supported self-hosting deployment path without a hard Cloudflare dependency, ideally using Docker.

## Best Possible Solution

If maintainers sponsor portability, first define provider-neutral infrastructure interfaces and conformance requirements for identity, policy storage, budget transactions, queues, secrets, migrations, and operations; then implement one supported self-hosted runtime without changing provider routing semantics or weakening fail-closed enforcement.

## Maintainer Decision

Rationale: The requested path changes the deployment, support, durability, identity, and enforcement model across the product; repository evidence cannot determine that permanent support commitment without maintainer intent.

Likely owner: vincentkoc

Owner confidence: high

Options:

- **Keep Cloudflare-native for now (recommended):** Document Cloudflare as the supported production runtime and revisit portability only when a maintainer sponsors a concrete runtime contract.
- **Sponsor a portable runtime:** Define infrastructure adapter contracts and conformance tests before accepting a Docker or other self-hosted implementation.
- **Support development only:** Provide a clearly unsupported local development harness while retaining Cloudflare as the only production deployment target.

No, Docker packaging alone is not the best solution because the runtime depends on Cloudflare identity, storage, transaction, and queue semantics. The maintainable path is an explicitly sponsored infrastructure-adapter contract with conformance and upgrade testing.

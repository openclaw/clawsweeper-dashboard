## Label Justifications

- `P0`: The reported first-run setup path can fail after creating the local gateway, roll it back, and leave a community user blocked at setup with only logs/support-style recovery.
- `impact:ux-release-blocker`: Setup failure currently lands on a failure page with Close/log access rather than an in-product recovery path after the gateway is removed.

- `impact:auth-provider`: The failure occurs in operator/node pairing and device-pair credential setup, and the related mitigation is specifically for gateway pairing authorization.

## Summary

Keep open: current main now pins a newer gateway CLI and includes the merged old-`device-pair` diagnostic, but the reported rollback/deletion behavior remains the UI default and still needs maintainer direction for setup recovery policy.

## What This Changes

The issue reports that local gateway setup created and started `OpenClawGateway`, failed at `pair-node`, then rolled back setup and removed the gateway distro/state.

## Best Possible Solution

Adopt a stage-aware setup failure policy: preserve a created/running local gateway after late pairing or configuration failures with visible Retry, Doctor/Fix, Restart gateway, and Uninstall actions, while keeping destructive cleanup explicit or limited to early unsafe partial installs.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should end-user local gateway setup keep transactional rollback as the default after late pairing/configuration failures, or preserve the partially created gateway so users can recover in-product?

Rationale: Current code and docs make rollback-on-failure intentional for the UI, but the issue shows that policy can erase a usable created gateway after a late setup failure and leave first-run users without a non-technical recovery path.

Likely owner: ranjeshj

Owner reason: They are the strongest current setup/pairing follow-up signal from the issue discussion and related merged diagnostic PR.

Owner confidence: high

Options:

- **Use stage-aware recovery (recommended):** Preserve the gateway after late failures and add visible recovery actions, while still cleaning early unsafe partial installs.
- **Keep rollback default:** Retain transactional cleanup for all setup failures and instead improve the failure page with clearer retry/upgrade guidance.
- **Make rollback an explicit user choice:** Ask users whether to preserve or remove the local gateway after a failure, trading clarity for another setup decision.

## Reproduction Assessment

Yes at source/log level, but not as a live current-main Windows run. The reporter logs show `pair-node` failure followed by rollback, and current source still enables UI rollback and executes rollback of completed steps when a later setup step fails.

## Solution Assessment

Unclear for automation: changing rollback behavior is likely the right direction for user recovery, but current docs describe rollback as intentional UI policy, so maintainers should choose the preserve-versus-cleanup contract first.

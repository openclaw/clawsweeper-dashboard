## Summary

Keep open. Current main still depends on the in-repository FunctionalUI project and has no Reactor dependency or migration path, so the requested architectural change remains unimplemented; however, adopting a new UI framework and migrating every tray surface requires explicit maintainer direction before engineering begins.

## What This Changes

Migrate the tray’s bespoke FunctionalUI MVU/reconciler and screens to Microsoft.UI.Reactor or an agreed Reactor-style library while preserving behavior, accessibility, selection, and security invariants.

## Best Possible Solution

Approve a time-boxed feasibility spike that ports one low-coupling leaf screen, documents dependency and testing implications, and proves equivalent UIA, reconciliation, selection, and runtime behavior before deciding whether to sponsor an incremental full migration.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should the Windows tray adopt Microsoft.UI.Reactor as its supported UI architecture and dependency, beginning with a bounded leaf-screen spike, or continue investing in the in-repository FunctionalUI framework?

Rationale: Source inspection can establish that the migration is absent and technically motivated, but it cannot choose the repository’s long-term UI dependency, maintenance, and migration strategy.

Likely owner: shanselman

Owner reason: This choice governs the tray’s long-term architecture and external dependency strategy rather than one individual primitive implementation.

Owner confidence: medium

Options:

- **Sponsor a bounded spike (recommended):** Port one low-coupling screen alongside FunctionalUI and require dependency, testing, accessibility, selection, and runtime proof before approving further migration.
- **Retain FunctionalUI:** Keep the current framework and define a narrower policy for adding tested primitives only when concrete product needs arise.
- **Approve the full migration:** Commit to an incremental Reactor migration now, with one ownership seam per pull request and FunctionalUI removal only after all consumers and invariants move.

## Solution Assessment

Unclear as a full migration; a one-screen compatibility and maintainability spike is the narrowest safe way to determine whether Reactor is preferable to improving FunctionalUI incrementally.

## Summary

This appears to be a release-blocking installed-user bug: the shipped Voice & Audio Assistant surface can direct a normal installer user toward developer-only backend paths instead of a supported runtime or in-product recovery. Current-main source and installer contents could not be conclusively re-read in this review environment, so it should remain open for a maintainer decision rather than be closed as already fixed.

## What This Changes

Make the Windows Voice & Audio Assistant usable from a normal installer deployment, or prevent it from exposing a developer-checkout requirement to installed users.

## System Context

The Windows Hub exposes Voice & Audio controls that invoke an Assistant bridge. That bridge resolves an OpenClaw backend command before starting the Assistant, so an unavailable packaged backend currently turns a visible user action into a developer-environment error.

## Architecture Diagram

flowchart LR
  A[Installed Windows Hub] --> B[Voice and Audio Assistant control]
  B --> C[Assistant launch bridge]
  C --> D{Supported backend runtime available?}
  D -- Yes --> E[Start Assistant]
  D -- No --> F[Clear disabled state or supported setup]
  F --> G[User can recover in product]

## Best Possible Solution

Define one supported installed-user Assistant path: preferably detect runtime availability before exposing Start Assistant, provide an in-product disabled/recovery state with accurate setup guidance, and only package a backend after maintainers explicitly accept its installer and lifecycle cost.

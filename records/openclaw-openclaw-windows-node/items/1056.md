Keep open. The report gives a concrete v0.6.12 symptom, while the current Windows-node documentation excludes Browser control from the supported node-capability set. That mismatch warrants a maintainer decision and source-level check; there is not enough current-main provenance to conclude the behavior is already fixed.

## What This Changes

Clarify or repair the Windows node Browser control capability so an enabled-looking toggle does not remain permanently unapproved and unusable.

## System Context

Windows Hub advertises local node capabilities to a paired OpenClaw Gateway, which then exposes approved capabilities to operators and tools. The capability registry feeds the Permissions UI and determines what the remote gateway can target.

## Architecture Diagram

flowchart LR

  C --> D[Gateway capability list]
  D --> E[Browser tool routing]
  B --> F[Permissions status UI]
  F --> G[Operator warning or approved state]

## Best Possible Solution

Treat Browser control as unsupported in the Windows-node permissions UI until end-to-end gateway routing is intentionally supported, then add a focused UI/registry regression test; track any full remote-browser implementation as a separately scoped cross-component effort.

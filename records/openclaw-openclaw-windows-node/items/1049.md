## Summary

Keep this PR open. It implements the lock-step direction from the canonical issue, but its current routine-update design still creates a complete VHD rollback copy before every update, despite the collaborator review identifying that as operationally unsuitable and the contributor agreeing to redesign it. The submitted proof is test-only and names an earlier head, so it does not yet demonstrate the changed WSL update path on the current head.

## What This Changes

Adds a user-confirmed Windows Companion flow that checks a Companion-owned WSL Gateway against the Companion’s pinned version, updates it in place, and offers retained rollback points and recovery UI.

## System Context

The Windows Tray owns the local Companion-managed WSL Gateway lifecycle after onboarding. Once the keepalive path confirms the managed distro is available, the proposed coordinator compares its installed OpenClaw package to the Companion target, then either leaves it aligned or runs an update-and-recovery transaction before resynchronizing the gateway connection.

## Architecture Diagram

flowchart TD
  A[Companion startup] --> B[Managed WSL Gateway ready]
  B --> C[Read installed package version]
  C --> D{Matches Companion target?}
  D -->|Yes| E[Continue gateway connection]
  D -->|No, user confirms| F[Create rollback point]
  F --> G[Install pinned package and verify health]
  G --> E
  G -->|Failure| H[Confirmed recovery flow]

## Best Possible Solution

Adopt a layered recovery policy: use the official pinned package rollback plus verified Gateway-state backup for routine updates, reserve full VHD recovery for incompatible migrations or an explicit user choice, and add capacity preflight, storage visibility, cleanup, and current-head disposable-WSL proof before merge.

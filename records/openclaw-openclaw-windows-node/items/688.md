## Summary

Keep open: current main and v0.6.12 still expose the OpenClaw onboard wizard as a forward-only gateway-driven flow, and collaborator discussion says adding a Windows-only Back button is not the right fix without a gateway wizard protocol/product decision.

## What This Changes

Request a per-step Back navigation affordance in the setup/onboarding wizard so users can return to prior provider or configuration steps without restarting the flow.

## Best Possible Solution

Define the gateway wizard navigation contract first, preferably a declarative wizard manifest with local draft state and validation checkpoints, then implement Windows Back/Forward against that contract while keeping restart/skip recovery for irreversible phases.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should OpenClaw pursue wizard Back navigation through a declarative gateway-provided wizard manifest, a smaller gateway-owned wizard.back/wizard.previous RPC, or keep the current restart/skip recovery model for now?

Rationale: Current source proves the Windows client is only a thin renderer for gateway-owned wizard.start/wizard.next frames, so a safe implementation depends on the product/protocol contract maintainers want.

Likely owner: ranjeshj

Owner reason: They already gave the most detailed product/protocol direction on this issue and have merged setup engine work in the affected area.

Owner confidence: high

Options:

- **Declarative manifest with validation (recommended):** Have the gateway describe pages, fields, branching, and validation checkpoints up front so Windows owns draft state and normal Back/Forward navigation.
- **Gateway-owned Back RPC:** Add wizard.back or wizard.previous semantics to the gateway and have Windows call that for a smaller retrofit with server-owned session state.
- **Keep recovery-only model:** Decline per-step Back for now and document restart/skip recovery as the supported behavior until gateway protocol work is prioritized.

## Reproduction Assessment

Yes, source-level: current WizardPage renders only More options, secondary, and primary actions for the gateway-driven step, and the client sends wizard.start/wizard.next without any wizard.back or wizard.previous path. I did not run the Windows UI in this read-only cleanup review.

## Solution Assessment

No, not as a Windows-only Back button. The collaborator discussion and source model point to a gateway protocol or declarative manifest decision before a maintainable Windows implementation is safe.

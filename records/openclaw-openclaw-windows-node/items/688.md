## Label Justifications

- `P2`: The issue is a normal-priority setup UX gap with a restart workaround and no evidence of crash, data loss, or unusable core runtime.
- `impact:ux-friction`: The setup flow can force users to restart and re-enter answers to correct a prior choice, creating avoidable first-run friction without fully blocking progress.

## Summary

Keep open: current main and v0.6.12 still expose a forward-only gateway-driven setup wizard with no per-step Back affordance, and the collaborator discussion says the fix needs an explicit gateway wizard protocol/product decision rather than a Windows-only button.

## What This Changes

Add per-step Back navigation to the in-app gateway-driven setup wizard so users can correct earlier setup answers without restarting the flow.

## Best Possible Solution

Define the gateway wizard navigation contract first, preferably a declarative manifest with local draft state or an explicit back/previous RPC with side-effect boundaries, then update the Windows setup UI and regression tests around that contract.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should the gateway wizard support Back navigation through a declarative manifest/final-submit contract, a gateway-owned wizard.back RPC, or another explicit protocol boundary before Windows adds the UI affordance?

Rationale: The current Windows client only renders one gateway-owned step at a time, so local Back behavior would require guessing about prior steps, branching, validation, and irreversible side effects.

Likely owner: ranjeshj

Owner reason: The collaborator comment already frames the exact protocol choices and this person has nearby setup recovery history.

Owner confidence: high

Options:

- **Define a declarative wizard manifest (recommended):** Have the gateway describe the setup flow up front so Windows can own Back/Forward, draft values, validation checkpoints, and final commit boundaries.
- **Add gateway-owned back RPC:** Add wizard.back or wizard.previous semantics to the gateway and then wire Windows Back to that server-owned session state.
- **Defer Back navigation:** Keep restart/skip recovery as the supported behavior until the gateway flow is redesigned.

## Reproduction Assessment

Yes. Source inspection of current main shows the gateway setup wizard has forward, restart, skip, and cancel paths but no per-step Back action or wizard.back/previous RPC; no live Windows run was performed in this read-only review.

## Solution Assessment

No for a Windows-only Back button on the current one-step-at-a-time gateway protocol. The maintainable solution is to decide and implement gateway-supported navigation or a declarative wizard contract first.

## Summary

## What This Changes

Add authoritative setup-code claim and API base URLs so deployments can use separate public frontend/API origins or an API base path while preserving existing same-origin behavior.

## Best Possible Solution

Define a versioned, backward-compatible OpenAPI contract where the server emits a strictly validated exact claim endpoint, claiming returns the canonical API base URL, same-origin remains the default, and coordinated ClickClack/OpenClaw coverage verifies same-origin, split-origin, base-path, and upgrade behavior.

## Maintainer Decision

Required: true

Kind: product_direction

Question: Should ClickClack officially support separate public frontend and API origins and API base paths through an exact server-issued setup-code claim endpoint?

Rationale: Current architecture and documentation center one application origin, while this proposal adds configuration, deployment, security, OpenAPI, SDK, frontend, and OpenClaw consumer behavior that automation cannot select safely.

Likely owner: steipete

Owner reason: Available history connects this person most directly to repository-wide deployment-origin and authentication decisions.

Owner confidence: medium

Options:

- **Adopt exact endpoint contract (recommended):** Add a separate canonical API URL, emit an exact validated claim endpoint, return the API base URL after claiming, and preserve same-origin compatibility.
- **Support split origins only:** Allow a separate API origin but retain the root-mounted `/api` contract and explicitly defer base-path deployments.
- **Keep one public origin:** Continue supporting reverse-proxy routing as the deployment model and document separate public origins as unsupported.

## Reproduction Assessment

Yes, at the source-contract level: current documentation fixes claims at `/api/bot-setup-codes/claim`, restricts `CLICKCLACK_PUBLIC_URL` to a pathless origin, and describes a combined frontend/API deployment. A live split-origin deployment was not executed.

## Solution Assessment

Unclear pending maintainer direction: a server-issued exact endpoint is safer than browser-origin inference, but the permanent URI format, compatibility window, base-path scope, and CORS boundary require agreement across ClickClack and OpenClaw.

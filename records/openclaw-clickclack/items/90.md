## What This Changes

Add backend-authored setup-code claim and canonical API URLs so frontend and API origins or base paths may differ.

## Best Possible Solution

Introduce a separately validated canonical public API base with the existing same-origin value as its default, have the backend return both the exact claim endpoint and canonical API base, and update OpenClaw to consume those values without reconstructing paths.

## Reproduction Assessment

Yes at the contract level: the documented public URL accepts only an origin with no path, so it cannot encode the requested split-origin or path-mounted API topology. A deployment with `https://example.com` for the frontend and `https://api.example.com` for the API directly demonstrates the limitation described.

## Solution Assessment

Yes, conditionally: making the backend authoritative for both the exact claim endpoint and saved API base is narrower and safer than frontend URL inference. The unresolved choice is whether base paths, rather than only separate origins, become an officially supported topology.

- Changing the setup URI requires coordinated compatibility in both ClickClack and OpenClaw; deploying either side alone could make newly generated codes unclaimable.

- Returning absolute claim URLs makes canonical URL validation security-sensitive, including HTTPS enforcement, loopback exceptions, and rejection of credentials, queries, and fragments.

## Summary

This PR remains useful and well-proven, but it is not merge-ready because the unchanged workspace deletion sequence can permanently orphan stored upload objects after a storage deletion failure.

## What This Changes

The PR adds workspace administration APIs and UI, workspace icon persistence and upload lifecycle handling, regenerated web assets, and a cross-platform SDK build copy step.

## Best Possible Solution

Persist retryable cleanup records in the workspace deletion transaction, delete each object idempotently, and clear records only after confirmed storage deletion.

## Maintainer Decision

## Reproduction Assessment

Yes at source level: use upload storage whose `Delete` returns an error, then delete a workspace containing uploads; the database commit completes before the handler returns 500. The PR has no failure-path test for this sequence.

## Solution Assessment

No. Returning paths after committed cascade deletion is not durable; a transactional cleanup record or equivalent idempotent retry mechanism is the narrowest safe solution.

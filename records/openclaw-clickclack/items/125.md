## Summary

Keep open. The merged managed-channel foundation in https://github.com/openclaw/clickclack/pull/102 provides the metadata and lifecycle fields this proposal builds on, but the requested provider-scoped atomic reconciliation identity, API contract, and concurrency semantics remain a distinct product and storage decision. Likely related people: steipete is the high-confidence routing candidate for the adjacent managed-channel foundation.

## What This Changes

Add a provider-scoped atomic reconciliation API so external integrations can create or update exactly one managed channel for an external object without duplicate webhook races.

## System Context

ClickClack lets authorized bots create and lifecycle-manage channels that represent external work. This proposal would sit between provider webhook integrations and the channel store, turning desired external metadata into one durable channel and the corresponding channel event.

## Architecture Diagram

flowchart LR
  A[Provider webhook] --> B[Authorized integration]
  B --> C[Reconcile managed channel]
  C --> D[Provider plus external reference]
  D --> E[Durable channel store]
  E --> F[Channel created or updated event]
  E --> G[Stable ClickClack channel]

## Best Possible Solution

If maintainers sponsor this direction, add a narrowly scoped provider/reference reconciliation contract with additive migrations, database-level uniqueness, deterministic create/update/unchanged behavior, and real SQLite plus PostgreSQL concurrency proof while preserving legacy source-less managed channels.

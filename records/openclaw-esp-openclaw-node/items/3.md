## What This Changes

The PR adds an ESP OpenClaw Node scope registry/API, a Kconfig scope limit, README updates, and uses registered scopes in connect auth signing and JSON advertisement.

## Best Possible Solution

Land scope support only after the signed and transmitted scope representation is canonical and untruncated, overflow/duplicate/default behavior has coverage, the public API contract is confirmed, and redacted real ESP/gateway proof is posted.

## Reproduction Assessment

Yes for the PR-introduced defect from source inspection: register enough or long enough scopes to exceed 127 bytes, and the PR truncates only the signature input while still sending all registered scopes in JSON. The intended successful scoped-auth behavior has not been proven in a real ESP setup.

## Solution Assessment

No in its current form. Scope support belongs in the registry/connect path, but this branch needs one canonical signed/transmitted representation, explicit validation limits, tests, and maintainer confirmation of the public API contract.

- **[P1] Use one canonical scope set for signing:** `components/esp-openclaw-node/src/esp_openclaw_node_protocol.c:52-60`
  - body: The fixed `scopes_csv[128]` can stop adding scopes once the comma-separated form is too long, but the connect JSON still sends every registered scope.   - confidence: 0.97
- **[P2] Check duplicate scopes before capacity:** `components/esp-openclaw-node/src/esp_openclaw_node_registry.c:162-163`
  - body: When the scope registry is full, registering an already-present scope returns `ESP_ERR_NO_MEM` before the duplicate scan, contradicting the new README/API behavior that duplicate scopes are ignored and return `ESP_OK`. Move the duplicate check before the capacity check for this new registry.
  - confidence: 0.9
